### Title
Unvalidated controller swap routes can expose the caller’s authorization to attacker-selected contracts - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
XOXNO Lending forwards caller-supplied `swap` bytes to the configured router after granting authority for one token transfer. Because the route itself selects the venue/pool addresses below that call, a malicious route can introduce third-party code beneath the caller’s authorized invocation. That code may request an unrelated `transfer` from the caller; Soroban simulation records it as an additional child authorization, and it executes if the returned authorization tree is signed.

This is analogous to the urllib3 issue: the high-level controller path exposes the same authorization boundary as a low-level redirect/callback path, while route-selected downstream code can carry the caller’s authority across an unexpected trust boundary.

### Finding Description
The controller accepts opaque `StrategySwap` bytes and invokes `router.execute_strategy(&controller, &amount_in, swap)` without decoding or constraining the route’s venue addresses. Immediately before that call, it grants the router one exact `token_in.transfer(controller, router, amount_in)` invocation through `authorize_transfer_as_current`. The authorization itself allows no sub-invocations, but it does not constrain which contracts the router may subsequently call while processing the route.

The balance checks in `swap_tokens` cover only `token_in` and `token_out` at the controller. They do not cover unrelated caller-held tokens transferred by a rogue route component under the caller’s signed authorization tree.

### Impact Explanation
An attacker can steal unrelated token balances from a user who signs a transaction containing a malicious route. The stolen transfer is outside both:

- the controller’s measured input spending bound;
- the controller’s measured positive output check.

The harness demonstrates that a rogue hop can move `WALLET_BALANCE` from the caller to the attacker while still paying the expected swap output, and that the transfer succeeds once simulation returns a poisoned authorization tree and the caller signs it.

### Likelihood Explanation
Exploitation requires the victim to submit or sign a malicious route and its simulated authorization tree. That makes it less direct than a permissionless contract-state exploit, but it is realistic for off-chain quote/route flows because `swap` bytes are opaque to the controller and callers commonly rely on simulation output. The affected path is reachable through public strategy entrypoints that use `swap_tokens`, including `multiply`, `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`.

### Recommendation
Do not let route-selected third-party contracts execute beneath a caller’s general authorization tree without constraining the auth surface. At minimum, decode and allowlist venue/pool contracts before executing routes, or execute the route through an isolated contract identity so child token calls cannot join the caller’s authorization tree. Clients should additionally reject any simulated authorization tree containing token movements other than the expected exact input transfer.

### Proof of Concept
A concrete harness exists in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies USDC and calls `swap_collateral` with an attacker-controlled route.
2. `swap_tokens` authorizes the expected exact input transfer to the configured router and forwards the opaque route bytes.
3. The route invokes an attacker-deployed pool.
4. That pool calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`.
5. Simulation records the unrelated transfer as a child of Alice’s `swap_collateral` authorization.
6. If Alice signs that poisoned tree, the unrelated wallet token is transferred to the attacker while the swap itself still completes with fair output.
