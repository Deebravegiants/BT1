### Title
Escrow redemption permanently reverts for blacklisted beneficiaries, freezing intent funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The Hyperbridge IntentGateway/IntentsBase escrow-redemption path (`_withdraw` / `withdraw`), triggered by `onAccept` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` message, transfers escrowed ERC-20 tokens (including stablecoins like USDC) directly to a `beneficiary` address that was fixed at order-creation/fill time, with no ability to redirect to an alternate receiver if that transfer fails.

### Finding Description
`IntentsBase._withdraw` (and the Tron variant `IntentGatewayV2.withdraw`) loops over escrowed tokens and does: [1](#0-0) 
using `SafeERC20.safeTransfer(beneficiary, amount)`, which reverts the entire call if the token transfer fails — exactly what happens when `beneficiary` is on the USDC blacklist. The Tron variant is even more explicit about hard-reverting: [2](#0-1) 

This function is invoked from `onAccept`, which is called by the ISMP host (`EvmHost`/`HandlerV2`) when delivering the `RedeemEscrow`/`RefundEscrow` request — an unprivileged, permissionless message-delivery path driven by any relayer submitting a valid proof: [3](#0-2) 

Because the beneficiary address is embedded in the cross-chain `WithdrawalRequest` body (set at order creation/fill time and immutable thereafter), there is no mechanism analogous to `_receiver` override in the referenced Derby report — no owner/solver/relayer can specify a different destination for the escrowed funds. If the beneficiary is later added to the USDC blacklist (or any token with a similar freeze/blocklist feature), every delivery attempt of that `RedeemEscrow`/`RefundEscrow` message will revert at the `safeTransfer`/low-level `call` step, and the escrow can never be redeemed.

### Impact Explanation
This directly matches the "permanent freezing of funds" criteria: the escrowed principal amount for that order, plus any transaction fees held in the same commitment (`TRANSACTION_FEES` bucket, also paid to the same `beneficiary`), becomes permanently unrecoverable since no alternate withdrawal path exists. This affects any solver or user who becomes blacklisted on the underlying settlement token used by the intents system, which commonly settles in stablecoins such as USDC/USDT that maintain blacklists.

### Likelihood Explanation
Likelihood is low-to-moderate — it requires the beneficiary address associated with an in-flight or already-escrowed order to be added to a token blacklist. However, this is a realistic, externally-triggerable event (regulatory/compliance action, OFAC sanction, exchange freeze) entirely outside the protocol's control, and once it occurs there is no recovery path in-protocol, matching the severity class of the referenced Sherlock report.

### Recommendation
Add a pull-based/claimable fallback for failed redemptions: if the direct transfer to `beneficiary` fails, credit the amount to an internal claimable balance for that beneficiary (or allow the beneficiary/an authorized party to specify an alternate receiving address) rather than reverting the whole `onAccept` call. This mirrors the standard "push-then-pull" pattern used to avoid blacklist/DoS griefing on token transfers, and would let the fund owner nominate a non-blacklisted address to receive the funds.

### Proof of Concept
1. Solver/user completes an intent whose destination `beneficiary` is a normal address.
2. Before the corresponding `RedeemEscrow` (or `RefundEscrow`, e.g. after a cancellation) message is relayed and delivered, the `beneficiary` address gets added to the USDC blacklist.
3. A relayer submits the proof; the ISMP host calls `onAccept` → `withdraw`/`_withdraw`.
4. `IERC20(USDC).safeTransfer(beneficiary, amount)` (or the low-level `call` in the Tron variant) reverts because USDC's `transfer` reverts for blacklisted recipients.
5. Every subsequent redelivery attempt for the same commitment reverts identically; escrowed USDC for that order/commitment is permanently locked in the `IntentGateway`/`IntentsBase` contract with no available remediation path. [4](#0-3) [5](#0-4)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
