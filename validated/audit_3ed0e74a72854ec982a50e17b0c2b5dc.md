### Title
Unvalidated Source Bypass in Orb-Relay Client Allows Cross-Session Message Replay - (File: `orb-relay-client/src/client.rs`)

### Summary
The `orb-relay-client` crate, used by orb-core to exchange signup-state messages between the Orb and a user's phone app during self-serve signups, contains a source-validation bypass. Incoming relay messages are normally checked against the expected session partner (`src.id != self.config.dst_id`) before being accepted, but a special-cased branch for the `RequestState` payload type skips this check entirely and unconditionally triggers a resend of the Orb's last sent message.

### Finding Description
In `PollerAgent::main_loop`, incoming payloads from the relay stream are handled as follows: [1](#0-0) 

The `else if src.id != self.config.dst_id` branch exists specifically to reject/ignore messages that don't come from the expected session peer (the app paired to this specific signup session). However, the `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch is checked *first* and, if matched, immediately calls `sender_tx.send(self.last_message.clone())` — replaying the last outgoing message — without ever validating `src.id` against `self.config.dst_id`. This means any entity able to place a `RequestState`-typed payload onto this bidirectional relay stream (i.e., an unprivileged/unverified peer on the relay channel, not the Orb operator or a privileged actor) can force the Orb-side client to replay whatever it last sent, regardless of whether that "source" is the authenticated app-session peer.

This is the same defect class as the external report: an external/untrusted input (the relay message) is consumed and acted upon (triggering a send/replay action) without validating its origin, unlike the sibling code path a few lines below that does perform this validation. The last replayed message can include self-serve signup lifecycle state such as `CaptureStarted`, `CaptureTriggerTimeout`, or `SignupEnded` (see call sites), which are sent via this same client during `proceed_with_biometric_capture` and `after_signup`: [2](#0-1) [3](#0-2) 

The Orb identifies its relay session partner using `orb_relay_app_id`, sourced from backend-provided, per-signup user data: [4](#0-3) [5](#0-4) 

Because the `RequestState` fast-path ignores `src.id`, the identity binding this session establishes between an Orb and one specific app/session is not enforced for this message type, undermining the very check the code otherwise relies on to prevent cross-session interference.

### Impact Explanation
An unauthenticated/unverified relay participant can force replay of the last signup-lifecycle message the Orb sent for a specific self-serve signup session, without needing to prove it is the legitimate app for that session. This breaks the trust boundary between distinct signup sessions/apps on the relay channel (cross-signup state bleed), potentially causing a different or unauthorized client to receive signup state transitions (e.g., replayed `CaptureStarted`/`SignupEnded` messages) intended for another party's session, or to desynchronize state tracking on the app side. This does not require a malicious Orb operator, backend node, or hardware access — only the ability to send a message over the existing gRPC relay stream, which is the same posture as the external report's "external call without validation" class.

### Likelihood Explanation
Exploitability depends on whether the relay backend server can deliver a message on this stream from something other than the intended dst peer (e.g., stale/replayed data, another concurrent session, or a compromised/rogue app client authenticated toward the relay but not to this specific Orb session). Given the code explicitly special-cases this bypass (rather than it being a subtle omission), and self-serve mode is a production signup path, likelihood is moderate — comparable to the external report's likelihood rating (3/10) for unvalidated external calls generally.

### Recommendation
Remove the special-case bypass; always validate `src.id == self.config.dst_id` before acting on any incoming payload, including `RequestState`:
```rust
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await.wrap_err("Failed to send outgoing message")?;
} else {
    self.handle_message(...).await?;
}
```
This restores the existing source-validation guarantee uniformly for all payload types.

### Proof of Concept
1. A relay client (Orb or App) establishes a bidirectional stream with `dst_id` = a specific signup session identifier (`orb_relay_app_id`).
2. A message arrives on `response_stream` whose `payload` decodes as `self_serve::app::v1::RequestState`, but whose `src.id` does **not** equal `self.config.dst_id` (i.e., it did not originate from the expected session peer).
3. Per [6](#0-5) , the `src.id` check is never reached for this payload type — `self.last_message.clone()` is unconditionally resent, regardless of the sender's identity, whereas an identical mismatch on any other payload type is logged and dropped via the `else if src.id != self.config.dst_id` branch immediately below.
