### Title
Self-transfer safety check uses raw string equality for Zcash, allowing withdrawal to the token's own address via an equivalent Unified Address encoding - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses`, the function used by every bridge implementation to block a user from withdrawing a token to that token's own custody/origin address, dispatches per-chain. For most chains with multiple valid textual encodings (EVM checksum, TON raw/friendly, Tron base58/hex, Aptos/Sui/Starknet hex padding) it correctly normalizes before comparing. For `Chains.Zcash` it falls into the catch-all branch that does plain `a === b` string comparison: [1](#0-0) 

However, `validateAddress`'s Zcash branch (`validateZcashAddress`) accepts three structurally different encodings of a Zcash destination: transparent addresses (`t1`/`t3`), `tex1` addresses, and Unified Addresses (`u1...`), the latter of which can bundle a transparent receiver alongside Orchard/Sapling receivers inside a single opaque string: [2](#0-1) 

Because `compareAddresses` for Zcash never decodes the Unified Address to extract its embedded transparent receiver, two strings that resolve to the exact same on-chain transparent receiver (one as `t1...`, the other as a `u1...` UA embedding that identical transparent receiver) are treated as unequal.

### Finding Description
The bridges (`omni-bridge.ts`, `poa-bridge.ts`) call `compareAddresses(tokenOriginAddress, destinationAddress, blockchain)` specifically to break the equality "the address the user asked to withdraw to is NOT the token's own custody address," e.g.: [3](#0-2) [4](#0-3) 

`validateAddress` (the format gate that runs before this equality check) is deliberately permissive and accepts Unified Addresses as valid Zcash destinations, and the file even has a dedicated parser/validator for them (`validateZcashUnifiedAddress`, `zcash-unified-address.ts`) that is UA-format aware. But `compareAddresses` for Zcash is not: it is the raw fallback `a === b`, identical to the branch used for chains with a single canonical text form (Near, Solana, Cardano, etc.), even though Zcash — like TON, Tron, and the hex-address family that were explicitly special-cased — has multiple valid encodings of the same underlying receiver.

This is the same bug class as the reported Langroid issue: a defense-in-depth equality/blocklist enumerates specific forms exhaustively (`pg_read_server_file`, `pg_ls_dir`, ...) but misses a sibling form in the same family (`pg_read_file`, `pg_stat_file`, ...), so a functionally-equivalent input reaches the sink undetected. Here, the "family" is Zcash address encodings, and the equality that should be broken — "the caller-supplied destination is not the token's own address" — silently passes even when the caller-supplied UA's embedded transparent receiver *is* the token's own address, because the comparison never canonicalizes the UA down to its transparent receiver bytes before comparing.

### Impact Explanation
If a token's `origin_chain_address` / bridge custody address for Zcash is a transparent address, and a withdrawal request supplies a semantically-equivalent Unified Address that embeds that same transparent receiver, `compareAddresses` returns `false` (no match), so `DestinationAddressMatchesTokenAddressError` is never thrown, and the withdrawal proceeds. The withdrawn tokens are sent to the transparent receiver embedded in the UA — which is the token's own custody/origin address — resulting in funds delivered to the token's own address with no recovery path (the same "funds delivered to a wrong address/chain/contract with no recovery" class explicitly called out as Critical). This is a self-inflicted-looking but SDK-caused misdelivery: the caller supplied a *valid* Zcash address per `validateAddress`, and the SDK's own anti-self-transfer guard is the component that fails to break the equality it was written to enforce.

### Likelihood Explanation
Requires: (1) a Zcash-route asset whose origin/custody address is a transparent address (plausible given `validateZcashAddress`'s transparent-address-first design and Zcash's UA feature being explicitly supported and tested in this SDK), and (2) the caller/LLM/integrator constructing or receiving a Unified Address representation of that same address (a normal, wallet-generated form, not an exotic crafted string — Zcash wallets routinely emit UAs). No malicious relayer, operator, or price-feed assumption is needed; only an ordinary caller-supplied withdrawal request using a UA form of an address that happens to alias the bridge's own address. Likelihood is moderate: it depends on whether any currently-configured Zcash-route token's `origin_chain_address` is reachable/known/guessable as a transparent receiver embeddable in a UA, which cannot be fully confirmed from the indexed files (the live production `origin_chain_address` value for the Zcash token and the omni-bridge Zcash wiring were not found in the index).

### Recommendation
Extend `compareAddresses`'s Zcash branch to canonicalize both inputs before comparison the same way `validateZcashAddress`/`zcash-unified-address.ts` already parses UAs: decode any `u1...` Unified Address to its component receivers, extract the transparent receiver (or all receivers) and compare the canonical transparent-receiver bytes (and/or full receiver set) against the other side's canonical form (decoding `t1`/`t3` Base58Check to its 20-byte hash), instead of falling through to raw string equality. Add a regression test mirroring the existing `compareAddresses.spec.ts` cross-encoding tests (TON raw/friendly, Tron base58/hex) for "transparent address equals UA containing the same transparent receiver."

### Proof of Concept
1. Suppose Zcash token X's custody/origin address is transparent address `T_ADDR` (`t1...`).
2. Construct (or have a wallet construct) a Unified Address `UA_ADDR` (`u1...`) whose embedded transparent receiver decodes to the same 20-byte hash as `T_ADDR` (combined, per ZIP-316, with any Sapling/Orchard receiver — legal per the accepted "UA containing a transparent receiver alongside sapling" test case already present in `validateAddress.spec.ts`).
3. Call `bridge.validateWithdrawal({ assetId: "<zcash token X>", amount, destinationAddress: UA_ADDR })`.
4. `validateAddress(UA_ADDR, Chains.Zcash)` returns `true` (per `validateZcashAddress`'s UA branch).
5. `compareAddresses(T_ADDR, UA_ADDR, Chains.Zcash)` falls into `a === b` and returns `false` because the strings differ, even though they resolve to the same transparent receiver.
6. No `DestinationAddressMatchesTokenAddressError` is thrown; the withdrawal proceeds and delivers funds to the token's own custody address.

/**
 * Validates Zcash addresses
 * Supports:
 * - Transparent addresses (t1, t3)
 * - TEX addresses (tex1)
 * - Unified Orchard / Unified Addresses (UA)
 */
function validateZcashAddress(address: string) {
	// Transparent address validation
	if (address.startsWith("t1") || address.startsWith("t3")) {
		// t1 for P2PKH addresses, t3 for P2SH addresses
		return /^t[13][a-km-zA-HJ-NP-Z1-9]{33}$/.test(address);
	}

	// TEX address validation
	const expectedHrp = "tex";
	if (address.startsWith(`${expectedHrp}1`)) {
		try {
			const decoded = bech32m.decodeToBytes(address);
			if (decoded.prefix !== expectedHrp) {
				return false;
			}
			return decoded.bytes.length === 20;
		} catch {
			return false;
		}
	}

	// Unified address validation
	if (address.startsWith("u1")) {
		return validateZcashUnifiedAddress(address);
	}

	return false;
}
