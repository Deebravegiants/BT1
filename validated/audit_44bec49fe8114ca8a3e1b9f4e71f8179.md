### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking the HMAC over the raw request body, then dispatches the handler using a `shop` value taken from an HTTP header that is never covered by that HMAC. The identity binding "authenticated bytes == bytes acted upon" is broken: the signature proves the body wasn't tampered with, but it proves nothing about which shop the body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from caller-supplied headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC only against `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` uses this same validation and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header: [4](#0-3) 

Because the `shop-domain` header is not part of the signable string, `hmac == HMAC(secret, body)` holds for **any** value of the `shop-domain` header as long as the body and the correct `api_secret_key` are used. The equality the app relies on is:

`request.shop (header, unauthenticated) == "shop that produced/owns raw_body"`

but the code only ever proves:

`hmac == HMAC(api_secret_key, raw_body)`

These two are not equivalent, so trusting `request.shop` as the tenant identifier for `WebhookMetadata.shop` is unsound.

### Impact Explanation
An attacker who is a legitimate (unprivileged) merchant of the app can install the app on their own shop and receive one genuine webhook (with a body and a correctly computed HMAC over that body, since Shopify signs it with the real `api_secret_key`). The attacker can then replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop. Any application logic keyed off `data.shop` (e.g., writing/merging inventory, order, or customer data attributed to that shop, or triggering shop-scoped side effects) can be cross-contaminated between tenants — this is a cross-tenant data integrity/confusion vulnerability driven entirely by unprivileged internet-reachable input.

### Likelihood Explanation
The webhook HTTP endpoint is, by design, internet-reachable and unauthenticated apart from the HMAC check; the only "privilege" required is being any installed merchant able to generate one valid signed body, which is trivial to obtain by installing the app on a store the attacker controls. No access to `api_secret_key`, tokens, or TLS interception is required.

### Recommendation
Bind the identity fields into the HMAC-verified signable content, or otherwise independently corroborate `request.shop`/`request.topic` against a source that is provably tied to the same secret (for example, verify the shop against records of shops that installed the app rather than trusting the header verbatim), and document to consumers of `WebhookMetadata` that `shop` must not be treated as cryptographically authenticated by the HMAC check alone.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. body `{}` with headers including `x-shopify-hmac-sha256: <valid mac for body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Resend the identical body and HMAC header to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` and performs shop-scoped logic against the victim tenant, even though the request never actually originated for that shop.
