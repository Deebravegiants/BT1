## Title
Multisig payload substitution bypasses on-chain approval when `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled — ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction` only compares the payload actually being executed against the payload that owners approved on-chain when both `features::abort_if_multisig_payload_mismatch_enabled()` is true **and** the stored transaction has a full `payload` **and** the supplied payload is non-empty. If that feature bit is off (the default/unset state), this equality check is entirely skipped for the "full payload stored" case, so the module never verifies that the entry function about to be executed is the same one the owners voted on.

### Finding Description
`validate_multisig_transaction` (invoked by the VM prologue for every multisig transaction) performs quorum/timelock checks and then two separate payload-integrity checks: [1](#0-0) 

- If only a **hash** was stored (`transaction.payload_hash.is_some()`), the code unconditionally checks `sha3_256(payload) == *payload_hash`.
- If the **full payload** was stored (`transaction.payload.is_some()`), the equality check `payload == *stored_payload` only runs when `features::abort_if_multisig_payload_mismatch_enabled()` is true. When the feature bit is unset (default), this branch is skipped completely — no comparison happens at all.

The `payload` parameter here is not a cosmetic decoration: it is derived directly from the entry function that the VM is about to execute for the multisig account, both in the prologue (`run_multisig_prologue`) and in the main execution path (`execute_multisig_transaction`): [2](#0-1) [3](#0-2) 

Because the executing owner supplies this entry function as part of the *outer* transaction they sign (not something previously approved), any single owner who can satisfy quorum for sequence number N (their own implicit approval counts toward the threshold — see `validate_multisig_transaction` lines 1348–1352) can submit an execution transaction carrying an entirely different `EntryFunction` payload than what other owners approved for that sequence number, and — with the feature disabled — the module will not detect the mismatch. The only two remaining checks are approval-count/timelock (tied to the sequence-number record, not the payload content) and, for hash-only proposals, the hash check. For full-payload proposals, there is no cross-check at all, so execution of an unapproved payload (e.g., an `aptos_account::transfer` to the attacker's address, or a code-object/resource-account upgrade call) proceeds and succeeds.

This is precisely the class of bug that `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` (feature bit 70) was introduced to close, as documented in the code comment: "Whether the multisig v2 fix is enabled. Once enabled, the multisig transaction execution will explicitly abort if the provided payload does not match the payload stored on-chain." [4](#0-3) 

### Impact Explanation
This breaks the core custody invariant of the multisig account module: "only the payload that received the required threshold of owner approvals can be executed as the multisig account." With the fix disabled, a single owner (who is part of the quorum count and thus doesn't need additional collusion beyond meeting the numeric threshold with their own implicit vote) can substitute any entry function at execution time for a full-payload-stored proposal, e.g. redirect fund transfers, execute an unapproved code upgrade, or change auth-key/owners of the underlying resource account — all custody-grade actions (theft, freeze, or malicious upgrade) explicitly called out in the review scope.

### Likelihood Explanation
Exploitability requires only being one of the multisig owners with a proposal in the "full payload stored" state (i.e., `create_transaction` rather than `create_transaction_with_hash`) and enough votes to reach quorum (including one's own implicit vote) — no additional privilege beyond ordinary owner status is needed. The bug is entirely gated by feature flag state; I could not verify from the indexed code whether `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is currently enabled at mainnet genesis/governance state (the feature's own doc marks its "Lifetime" as "transient," i.e., an opt-in flag rather than one hard-coded to always-on like several neighboring flags marked "Enabled on mainnet, cannot be disabled"). If it is not yet enabled on mainnet, the vulnerability is live; if governance has already toggled it on, the described path is closed. This distinction could not be conclusively confirmed from the available indexed files.

### Recommendation
Make the payload-match check unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate) for both the hash-stored and full-payload-stored branches of `validate_multisig_transaction`, so that execution always verifies the supplied payload equals the approved one regardless of feature-flag state, and ensure the flag is enabled on all networks going forward.

### Proof of Concept
Move test sketch (feature left disabled) demonstrating execution of a mismatched payload succeeds:
```move
#[test(owner_1 = @0x123, owner_2 = @0x124)]
fun test_execute_with_mismatched_payload_when_feature_disabled(
    owner_1: &signer, owner_2: &signer,
) {
    // Setup with ABORT_IF_MULTISIG_PAYLOAD_MISMATCH NOT in the enabled set.
    let framework_signer = &create_signer(@0x1);
    features::change_feature_flags_for_testing(
        framework_signer,
        vector[features::get_multisig_accounts_feature(), features::get_multisig_v2_enhancement_feature()],
        vector[features::get_abort_if_multisig_payload_mismatch_feature()],
    );
    timestamp::set_time_has_started_for_testing(framework_signer);
    chain_id::initialize_for_test(framework_signer, 1);

    let owner_1_addr = address_of(owner_1);
    let owner_2_addr = address_of(owner_2);
    create_account(owner_1_addr);
    let multisig_account = get_next_multisig_account_address(owner_1_addr);
    create_with_owners(owner_1, vector[owner_2_addr], 2, vector[], vector[]);

    // Owner proposes payload A (approved payload) with full payload stored on-chain.
    create_transaction(owner_1, multisig_account, PAYLOAD_A);
    approve_transaction(owner_2, multisig_account, 1); // quorum reached (2/2)

    // Owner_1 calls validate_multisig_transaction with a DIFFERENT payload B
    // (simulating the VM prologue passing the entry function actually being executed,
    // which does not match PAYLOAD_A stored on-chain).
    validate_multisig_transaction(owner_1, multisig_account, PAYLOAD_B);
    // Expectation under fix: this assert should abort with EPAYLOAD_DOES_NOT_MATCH.
    // Actual behavior with feature disabled: no abort occurs, PAYLOAD_B validation
    // silently passes because the equality-check block is skipped entirely.
}
```
Running this with the feature flag unset should abort per the intended invariant but instead succeeds, confirming that `validate_multisig_transaction` permits execution of a payload that differs from the one that received owner approval whenever `abort_if_multisig_payload_mismatch_enabled()` is false.
