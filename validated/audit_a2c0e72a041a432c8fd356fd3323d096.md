## Title
Webhook HMAC only covers the request body, not the `shop-domain` header — shop identity used by handlers is unauthenticated - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop identity (`shop-domain` header) that is later trusted and forwarded to application webhook handlers is read from an HTTP header that is never included in that signed content. This breaks the intended binding `hmac_verified_bytes == bytes_that_determine_tenant_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` (and `topic`, `api_version`, `webhook_id`) are all pulled from HTTP headers that are not part of that signable string: [2](#0-1) 

`Webhooks::Registry.process` validates only the body-derived HMAC via `Utils::HmacValidator.validate(request)`, and then, having accepted the request as authentic, passes the *unverified* `request.shop` value straight to the app's handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [4](#0-3) 

Because the `shop-domain` header sits entirely outside the HMAC-covered bytes, the equality the library implicitly promises — "the shop that receives HMAC-verified trust equals the shop delivered to the handler" — does not hold. An unprivileged actor who obtains one legitimate `(raw_body, hmac)` pair (e.g. by intercepting/replaying a webhook delivery, or via any transport that lets them retransmit the exact bytes with modified headers) can resubmit it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still succeeds because the body and secret are unchanged, but `Registry.process` will dispatch the (attacker-chosen) `shop` value into `WebhookMetadata`, causing the app to process/store the payload under a different tenant than the one that actually generated it — a cross-tenant confusion analogous to "shop authenticated versus the shop stored/used as a session key."

### Impact Explanation
This is a cross-tenant data-integrity break: a payload cryptographically bound to shop A can be attributed to shop B in the consuming application, since the gem exposes `request.shop` as trusted data to `WebhookMetadata` without it ever being covered by the HMAC. Depending on how a host app keys its persistence layer off `WebhookMetadata#shop`, this can result in writing/deleting/exposing one merchant's webhook data under another merchant's identity — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires an attacker to have captured or otherwise obtained one valid `(raw_body, hmac)` pair for the target app (e.g., by controlling a network path that lets them retransmit an intercepted payload, or via any application logic that echoes webhook bytes back). This is a non-trivial precondition, but no possession of the app's `client_secret`/access token is required — only replay of already-signed bytes with a substituted header, which is consistent with the "verified bytes vs. parsed/acted-on bytes" analog class this scan targets.

### Recommendation
Include the shop domain (and any other header fields the application logic relies on for tenant identity, e.g. `topic`, `api_version`, `webhook_id`) in the HMAC-signable representation, or otherwise cryptographically bind the header values to the signed body before trusting them in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Legitimate webhook delivery arrives for `shop-a.myshopify.com` with body `{}` and a valid `x-shopify-hmac-sha256` computed over that body using the app's `client_secret`.
2. Attacker captures `(raw_body="{}", hmac=<valid>)` and re-POSTs it to the same webhook endpoint, substituting `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the signature: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "shop-b.myshopify.com"`, even though the signature never certified that shop value: [6](#0-5)
