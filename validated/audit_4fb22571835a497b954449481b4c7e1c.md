### Title
Fisherman veto of the latest EVM state-machine height resets the freshness watermark to a fixed sentinel instead of the true prior height, letting any relayer resubmit a stale consensus proof to regress trusted state - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` (the function backing `deleteStateMachineCommitment`, called by `HandlerV2` when a fisherman veto is processed) resets `_latestStateMachineHeight[stateMachineId]` to the hard-coded value `1` whenever the vetoed height happens to be the currently recorded latest height. It does not recompute or restore the *actual* previous legitimate height. This breaks the monotonicity invariant that `HandlerV2.handleConsensus` relies on (`intermediate.height > latestHeight`) to reject stale/superseded consensus updates, opening a window in which any unprivileged relayer can push an old-but-cryptographically-valid consensus proof (an "uncle"/historical leaf, since BEEFY's MMR is append-only) and have it accepted as the new "latest" state for that state machine — an authorization/freshness bypass directly analogous to CVE-2016-10026's failure to recheck permissions before accepting a reverted revision.

### Finding Description
`EvmHost.sol` tracks, per remote state machine, the highest height it has ever accepted a state commitment for: [1](#0-0) 

`storeStateMachineCommitment`, callable only by the handler, unconditionally sets this watermark to whatever height it is given: [2](#0-1) 

`HandlerV2.handleConsensus` uses that watermark as the sole gate deciding whether an intermediate state (extracted from a verified consensus proof) is fresh enough to be stored: [3](#0-2) 

When a fisherman (or the byzantine-detection bot) determines a stored commitment is fraudulent or forged, it calls `deleteStateMachineCommitment`, which runs `deleteStateMachineCommitmentInternal`: [4](#0-3) 

If the vetoed height happens to be the current latest height, the code resets the watermark to a fixed sentinel value `1` rather than to the true previous legitimate height (there is no stored "second highest height" to roll back to, and the code makes no attempt to compute one): [5](#0-4) 

Contrast this with the Substrate implementation of the identical operation, where vetoing the latest height correctly rolls the pointer back to the real prior height (10, not a sentinel), as pinned by test: [6](#0-5) 

The EVM implementation's use of a fixed `1` sentinel (rather than the real prior height) means that after a veto of, say, height 10,000, `_latestStateMachineHeight` collapses to `1`. Any subsequently delivered consensus proof whose intermediate parachain/L2 header height is merely `> 1` — including heights the protocol previously already superseded (e.g. 500, 2,000, 9,000) — will now satisfy `intermediate.height > latestHeight` in `HandlerV2.handleConsensus` and be accepted via `storeStateMachineCommitment`, which then unconditionally reassigns `_latestStateMachineHeight` to that stale height and refreshes `_stateCommitmentsUpdateTime` for it. Because BEEFY/MMR proofs are append-only, a relayer can hold onto (or freely re-derive/re-fetch) any historically valid consensus proof and replay it after observing a veto event (`StateCommitmentVetoed`), which is emitted publicly: [7](#0-6) 

This is functionally the same bug class as CVE-2016-10026: an action that is supposed to "revert" bad state (the fisherman veto) fails to recompute the authorization/freshness baseline that other privileged operations gate on, so a stale revision (state proof) that would normally be rejected can be pushed back in and accepted as canonical — resetting the state machine's freshness tracking to an attacker-controllable point far below where it legitimately should be.

### Impact Explanation
Regressing `_latestStateMachineHeight` to `1` after any veto of the current latest height allows any relayer to reassert an old, stale intermediate state as the new "latest" for that source chain. Because `stateMachineCommitmentUpdateTime` is also refreshed to `block.timestamp` for that stale height, this can be leveraged to manipulate challenge-period gating (`HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handlers all key off `stateMachineCommitmentUpdateTime(proof.height)`), and it corrupts the freshness invariant relied upon by the epoch/authority-rotation bookkeeping in `HandlerV2.handleConsensus` (lines 166-173), which credits relayers for authority-set epochs based on `nextAuthoritySetId` derived from the (now unreliable) sequencing of accepted intermediate states. In the worst case this is an unsound-state-commitment condition: the protocol's notion of "the freshest known state of chain X" can be forced backward by an unprivileged relayer, undermining state-membership/non-membership proof freshness guarantees that downstream applications (token bridges, intents) depend on for correctness.

### Likelihood Explanation
Fisherman vetoes are a routine, expected part of protocol operation (triggered automatically by the byzantine-detection bots on state-root/timestamp mismatch, as seen in `tesseract/messaging/substrate/src/byzantine.rs` and `tesseract/messaging/substrate-evm/src/lib.rs`), so the precondition (a veto landing on the then-current latest height) is not a contrived edge case — it is likely to occur during normal fisherman operation. Once it occurs, exploitation only requires an unprivileged relayer to resubmit any previously-valid consensus proof through `HandlerV2.handleConsensus`, which is a permissionless, unauthenticated entry point.

### Recommendation
On veto of the current latest height, do not hard-code the watermark to `1`. Either (a) maintain a rolling record of the previous legitimate height (mirroring the Substrate implementation's correct rollback-to-actual-prior-height behavior) and restore that, or (b) require a fresh consensus proof for a height strictly greater than the *pre-veto* highest never-vetoed height, tracked explicitly, rather than relying on the mutable `_latestStateMachineHeight` field as both the freshness gate and the veto-rollback target.

### Proof of Concept
1. Handler stores a legitimate `StateCommitment` for `stateMachineId = X` at `height = 10000` via `storeStateMachineCommitment`; `_latestStateMachineHeight[X] = 10000`.
2. A fisherman detects fraud (or a false positive/race) at height 10000 and the handler calls `deleteStateMachineCommitment(height=10000, fisherman)`. Since `_latestStateMachineHeight[X] == 10000`, the code sets `_latestStateMachineHeight[X] = 1` (`evm/src/core/EvmHost.sol:718-721`).
3. Any relayer (no privilege required) submits a previously valid consensus proof through `HandlerV2.handleConsensus`, whose verified intermediate carries, e.g., `height = 5000` for `stateMachineId = X` (a height that was already historically finalized/superseded before the veto).
4. `HandlerV2.handleConsensus`'s check `latestHeight != 0 && intermediate.height > latestHeight` evaluates `5000 > 1 == true`, so `host.storeStateMachineCommitment` is called, setting `_latestStateMachineHeight[X] = 5000` and refreshing `_stateCommitmentsUpdateTime[X][5000] = block.timestamp` — silently regressing the tracked freshness of chain X's state by 5000 blocks, using data the attacker did not need any special access to obtain.

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {

	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();

			host.store_state_machine_commitment(
				StateMachineHeight { id, height },

			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.

		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());

		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
