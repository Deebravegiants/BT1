### Title
`TokenFaucet.drip` per-address daily limit is trivially bypassed atomically via disposable caller contracts, enabling unbounded unbacked minting of the fee token - (File: `evm/src/utils/TokenFaucet.sol`)

### Summary
`TokenFaucet.drip()` restricts token issuance using a `mapping(address => uint256)` keyed on `msg.sender`, exactly the pattern flagged in the external report. Because the check/gate is purely `msg.sender`-based and the faucet holds `MINTER_ROLE` on the protocol's fee token (`HyperFungibleTokenImpl`), an attacker can deploy any number of throwaway contracts and call `drip()` from each of them within a single atomic transaction, minting an unbounded amount of the fee token that the ISMP host, dispatchers, and bandwidth purchasing flows all price and account in.

### Finding Description
`TokenFaucet.sol` implements a "once per day per caller" gate: [1](#0-0) 

```solidity
contract TokenFaucet {
    mapping(address => uint256) private consumers;

    function drip(address token) public {
        uint256 lastDrip = consumers[msg.sender];
        uint256 delay = block.timestamp - lastDrip;
        if (delay < 1 days) {
            revert("Can only request tokens once daily");
        }
        consumers[msg.sender] = block.timestamp;
        HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18);
    }
}
```

The gate assumes `msg.sender` is a stable, rate-limited identity, but any fresh contract address has `consumers[addr] == 0`, so `block.timestamp - 0` is always `>= 1 days` (unix time is always far larger than one day). A caller can deploy an unbounded number of one-shot "minter" contracts inside a single transaction (each doing `TokenFaucet(faucet).drip(token)` then forwarding the minted tokens to a collector), and call all of them from one aggregator contract in one atomic transaction — identical in structure to the `Minter`/`Aggregator` pattern from the external report.

This is reachable by any unprivileged EOA: the faucet is deployed with `MINTER_ROLE` on the protocol fee token whenever the deploy script is not targeting mainnet: [2](#0-1) 

```solidity
// Deploy our own feetoken contract & faucet
faucet = new TokenFaucet{salt: salt}();
feeTokenInstance = new HyperFungibleTokenImpl{salt: salt}(admin, "Hyper USD", "USD.h");
// Grant minter role to faucet so it can mint tokens
feeTokenInstance.grantMinterRole(address(faucet));
feeToken = address(feeTokenInstance);
```

`HyperFungibleTokenImpl.mint` has no supply cap beyond the `MINTER_ROLE` check, so any holder of that role — including this faucet — can mint arbitrary amounts: [3](#0-2) 

This fee token is the same token used to pay dispatch/relayer fees across the ISMP host and, per the bandwidth documentation, is the token pulled for bandwidth purchases (`IDispatcher(_host).feeToken()`), so unbounded unbacked minting directly devalues/distorts fee and reward accounting for every app relying on that host's fee token.

### Impact Explanation
An attacker bypasses the intended "1000 tokens per address per day" throttle entirely, minting arbitrary amounts of the fee token in a single atomic transaction by fanning out `drip()` calls through disposable contracts. This is an unbacked-mint bug in a contract that holds `MINTER_ROLE` on the chain's fee/reward token, which can be used to drain liquidity pools paired with the fee token, distort relayer fee/reward accounting, or exhaust bandwidth-purchase economics that price against this token's supply.

### Likelihood Explanation
Trivial to execute: deploying helper contracts and batching calls in one transaction requires no privileged access, no timing tricks, and no race condition — only ordinary `CREATE` + a multicall-style aggregator, exactly as described in the source report.

### Proof of Concept
```solidity
contract DripOnce {
    constructor(address faucet, address token, address collector) {
        TokenFaucet(faucet).drip(token);
        IERC20(token).transfer(collector, 1000 * 1e18);
    }
}

contract Aggregator {
    function drainFaucet(address faucet, address token, uint256 n) external {
        for (uint256 i = 0; i < n; i++) {
            new DripOnce(faucet, token, msg.sender); // fresh address each time => consumers[addr] == 0
        }
    }
}
```
Calling `Aggregator.drainFaucet(faucet, feeToken, N)` mints `N * 1000e18` fee tokens to the caller in a single transaction, regardless of the intended once-per-day-per-address limit.

### Recommendation
Do not gate faucet issuance on `msg.sender` alone. Options: require `tx.origin == msg.sender` (reject contract callers), tie the daily limit to an off-chain-verified identity (e.g., signature/allowlist), or better, remove `MINTER_ROLE` from any faucet contract used outside of isolated test/testnet deployments and replace it with a pre-funded balance transfer so the faucet can never mint beyond a fixed pre-allocated pool.
