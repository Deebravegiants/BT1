This confirms the vulnerability. The docs explicitly document `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the handler receives `data.shop` as the shop domain to key tenant-specific logic (`docs/usage/webhooks.md:12-14`). The gem's own `Registry.process` passes the unauthenticated `request.shop` header straight into `WebhookMetadata`, while the HMAC only ever covers `@raw_body`.### Title
`shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated HTTP headers while the webhook HMAC only covers the raw body, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" and then dispatches a `WebhookMetadata` struct — including the `shop` field the host app uses to route/attribute the webhook to a tenant — to the app's handler. However, the HMAC signature only authenticates the raw request body; the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed material, so any of them can be swapped by an attacker without invalidating the HMAC check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body only: [2](#0-1) 

`Registry.process` gates on that body-only HMAC, then immediately builds `WebhookMetadata` from the **unauthenticated** `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` header accessors and hands it to the app's handler: [3](#0-2) 

Those accessors read straight from attacker-suppliable headers with no cross-check against the signed body: [4](#0-3) 

The documented contract explicitly tells host apps that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook" to be used by the handler (e.g. to key tenant-specific job processing): [5](#0-4) [6](#0-5) 

The identity binding that should hold is: **bytes verified by HMAC == bytes the app treats as authenticated (including the shop the webhook is attributed to)**. Instead the equality that actually holds is only `HMAC(raw_body, api_secret_key) == received_hmac`; the `shop` header used for tenant attribution is completely outside that equality. Since every shop installed on the app shares the same `api_secret_key`, any body+HMAC pair that Shopify legitimately sent to the app for *shop A* remains a valid HMAC no matter what `x-shopify-shop-domain` value accompanies it. An attacker who controls (or has installed the app on) shop A can capture a legitimately-signed webhook (body + HMAC) that Shopify sent them, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim's shop domain (shop B) in the `x-shopify-shop-domain` / `shopify-shop-domain` header. `HmacValidator.validate` still passes (it never looked at the header), and the handler receives `WebhookMetadata(shop: "shop-B.myshopify.com", body: <shop A's data>, ...)`.

### Impact Explanation
This is a cross-tenant data/identity confusion vulnerability reachable purely through this gem's documented API (`Registry.process` + `Request.new`), not a misuse of undocumented behavior. Any host application that follows the documented pattern of using `data.shop` to route webhook payloads to the correct tenant's records (exactly as shown in the gem's own `docs/usage/webhooks.md` example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute one shop's webhook payload/data to a different shop, or to trigger topic/webhook_id-keyed idempotency and business logic incorrectly. Depending on the handler's use of `data.shop`, this can lead to cross-tenant data injection or corruption — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or knowledge of `api_secret_key`: an attacker merely needs to be a legitimate (even free/trial) installer of the target app on their own store to receive a genuinely-signed webhook, then replay it against the app's public webhook endpoint with a modified shop header. This is entirely within reach of an unprivileged internet user/merchant and requires only a single HTTP replay.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the `shop` value to the verified payload — e.g., verify the `x-shopify-shop-domain` header against a shop-specific secret/session record already known to the app (looked up before trusting the header), or require the HMAC computation to cover `shop + topic + raw_body` rather than the raw body alone.

### Proof of Concept
1. App has two merchants installed: Shop A (attacker-controlled) and Shop B (victim), sharing the same app `api_secret_key`.
2. Shopify sends a legitimate webhook to the app for Shop A:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of RAW_BODY>
   x-shopify-shop-domain: shop-a.myshopify.com
   RAW_BODY
   ```
   Attacker (who owns Shop A) intercepts/logs this request.
3. Attacker replays the exact same `RAW_BODY` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets:
   ```
   x-shopify-shop-domain: shop-b.myshopify.com
   ```
4. `HmacValidator.validate` recomputes `HMAC(RAW_BODY, api_secret_key)`, matches the (unchanged) received HMAC, and passes — `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's parsed body>, ...)` — `lib/shopify_api/webhooks/registry.rb:198-199` — and invokes the app's handler as if the payload legitimately belonged to Shop B.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
