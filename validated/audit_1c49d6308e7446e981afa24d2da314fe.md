## Title
Webhook HMAC only authenticates the request body, allowing the `shop`/`topic`/`webhook-id` fields to be forged - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds `Utils::HmacValidator` verification to the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and then handed to the host app's webhook handler as trusted identity data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` gates on that HMAC check and then constructs `WebhookMetadata` directly from the unauthenticated header-derived accessors (`request.topic`, `request.shop`, `request.webhook_id`, `request.api_version`), passing it to the app's `handler.handle`: [4](#0-3) 

The identity binding broken is: `shop (validated by HMAC) == shop (trusted by handler)`. In reality, only `raw_body (validated by HMAC) == raw_body (parsed by handler)` holds; `shop`/`topic`/`webhook_id` are never bound to the signature at all.

Because `Context.api_secret_key` is the app's single client secret shared across every merchant install (it is not per-shop), any attacker who is themselves a legitimate installer of the app can obtain one genuinely-signed `(raw_body, hmac)` pair from their own store's real webhook traffic. That pair remains valid HMAC-wise for the app forever (same secret across tenants). The attacker can then replay that exact body/HMAC to the app's webhook endpoint while freely rewriting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers, since none of those are covered by the signature. `Registry.process` will pass the HMAC check and dispatch `WebhookMetadata` carrying an attacker-chosen `shop` value that the handler treats as authenticated.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to select or act on a specific tenant's stored session/data (a documented, expected usage pattern for this gem) can be tricked into applying an attacker-controlled event body to a victim shop's tenant context, because the `shop` field carried in the validated webhook is not actually bound to the HMAC that "validated" the request. This is a cross-tenant identity-binding break rooted entirely in this gem's `Webhooks::Request`/`HmacValidator`/`Registry` code, not host-app misuse of an already-documented contract — the gem itself presents `request.shop`/`data.shop` as if it had been authenticated by `Utils::HmacValidator.validate`, when it has not.

### Likelihood Explanation
Exploitation requires the attacker to possess one genuinely Shopify-signed `(body, hmac)` pair for the target app — trivially obtainable by installing the app on the attacker's own shop and letting Shopify deliver any real webhook, since the same `api_secret_key` verifies webhooks for all shops that installed the app. From there, forging the shop/topic/webhook-id headers on a replayed HTTP request requires no additional secret. The constraint is that the attacker doesn't control the body content (it's whatever Shopify signed for their own shop's event), limiting fully-arbitrary payload attacks, but the shop-identity spoofing itself is unconditional and repeatable for any topic the attacker can trigger on their own store.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed string, or otherwise cryptographically bind them to the body (e.g., derive/verify shop authenticity independently by cross-checking `request.shop` against a shop already known to have a stored access token/session before trusting it), rather than passing header-derived, unauthenticated values straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`; the app registers a webhook (e.g. `orders/create`).
2. Shopify sends a real webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then re-sends it to the same endpoint unchanged except `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request#hmac`/`#to_signable_string` still validate against body `B` only: [5](#0-4) [6](#0-5) 
5. `Utils::HmacValidator.validate` passes since `B` and `secret` are unchanged.
6. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` and calls `handler.handle`, so the host app processes the attacker's data as though it legitimately originated from the victim shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
