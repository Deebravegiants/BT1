The `Utils::HmacValidator.validate(request)` call in `Registry.process` computes the HMAC solely over `request.to_signable_string`, which for `Webhooks::Request` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from unauthenticated HTTP headers via `shopify_header` (`lib/shopify_api/webhooks/request.rb:20-23,67-70`). `Registry.process` passes `request.shop` directly into `WebhookMetadata` without any cross-check against the body or against a shop the app expects (`lib/shopify_api/webhooks/registry.rb:188-199`).

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook shop-spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body (`request.to_signable_string` → `@raw_body`). The `shop` (and `topic`/`webhook_id`/`api_version`) values consumed by the handler are read directly from HTTP headers that are excluded from the signed payload. Since a single app-level `api_secret_key` is shared across all shops that install the app, any shop that receives a legitimately-signed webhook from Shopify can replay that same body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop domain.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is derived unchecked from a header that is never part of the signed material: [2](#0-1) 
`Registry.process` validates the HMAC and then trusts `request.shop` for dispatch without binding it to the signature: [3](#0-2) 

The broken identity binding is: `HMAC-authenticated tenant (shop that Shopify actually signed the payload for)` should equal `data.shop passed to the handler`, but the gem only proves "this body+hmac pair was produced with the app's secret for *some* shop", not "for *this* shop-domain header". Because the `api_secret_key` is the same across every shop installing a given app, any shop tenant that legitimately receives one authentic webhook (body B, hmac H, for their own shop) can resend `{body: B, hmac: H, shop-domain: <victim-shop>}` to the app's webhook endpoint. `HmacValidator.validate` will pass (it never looks at the shop header), and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
Host applications built on this gem rely on `WebhookMetadata#shop` to route webhook data to the correct tenant record (e.g., updating orders/customers/settings keyed by shop). An attacker who is a normal, unprivileged app-installing merchant can inject data attributed to another merchant's tenant, achieving cross-tenant data corruption/injection without ever needing the app's `client_secret`, an access token, or any other privileged material — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any shop that installs the app receives real webhooks; capturing one authentic `(body, X-Shopify-Hmac-Sha256)` pair only requires operating an ordinary endpoint that gets Shopify webhooks (or reusing mandatory compliance webhooks such as `customers/redact`). Forging the `X-Shopify-Shop-Domain` header on the replay is trivial since it is a plain outbound HTTP header controlled entirely by the attacker sending the replayed request to the app's own webhook endpoint. No secret material or race condition is required, making this readily reachable by any unprivileged internet user who has installed the app on at least one shop.

### Recommendation
Bind the shop identity to the signed payload rather than trusting the header in isolation: either include `shop-domain`/`topic`/`webhook-id` in the HMAC-signed string (`to_signable_string`), or require host applications to independently verify that `request.shop` matches an expected/allow-listed shop for the given webhook subscription (e.g., cross-check against the shop that originally registered that webhook topic) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are unauthenticated headers and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook for topic `orders/create` to the app's registered endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed with the app's `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` from this authentic delivery to their own endpoint/log.
3. Attacker crafts a new HTTP POST directly to the app's public webhook endpoint with the same raw body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` and calls `Registry.process`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(B, api_secret_key) == H`, which is unaffected by the shop header (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
6. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
