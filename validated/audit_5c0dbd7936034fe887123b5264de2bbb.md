### Title
Flash-loan fee truncates to zero on small amounts, letting an attacker split a large loan into many fee-free loans - ([File: contracts/pool/src/ops/flash.rs])

### Summary
The analog of the Endaoment `grant.value/100` truncation bug is the flash-loan fee in `flash_loan`. `terms` computes `fee = Bps::from(fee_bps).flash_loan_fee_on(env, amount)` (`contracts/pool/src/ops/flash.rs:107-108`), a floor-rounding `mul_div` by `BPS` (10_000). For any `amount` where `amount * fee_bps < BPS`, the fee evaluates to exactly `0` — the same "division truncates to zero" class. An unprivileged caller can call `flash_loan` repeatedly with sub-threshold amounts, obtaining arbitrarily large aggregate flash liquidity while paying no fee at all.

Notably, the codebase already contains the fix pattern for this class elsewhere: liquidation fees apply a one-unit minimum when a positive RAY fee rounds to zero asset units (`bumped_fee` at `contracts/controller/src/positions/liquidation/math.rs:477-481`), showing the floor-to-zero hazard is recognized but was not applied to the flash path.

### Finding Description
- `flash::terms` derives the fee as `amount * flashloan_fee / BPS` with floor rounding (`contracts/pool/src/ops/flash.rs:107-120`).
- `flash::apply` only enforces repayment of `amount + fee` via `collect_repayment`/`require_balance` (`contracts/pool/src/ops/flash.rs:166-189`), so a zero fee is fully accepted: the receiver repays only the principal and `book_fee` books zero revenue (`contracts/pool/src/ops/flash.rs:124-128`, `interest::add_protocol_revenue` returns early on zero fee at `contracts/pool/src/interest.rs:59-62`).
- Any unprivileged address can invoke `flash_loan` on a flashloanable market. With e.g. `flashloan_fee = 9` bps (0.09%), any `amount < ceil(10000/9) ≈ 1112` stroops/units yields `fee == 0`. To borrow a large sum `X` fee-free, the attacker performs `N = X / threshold` sequential or batched flash loans, each below the threshold — each one is an independent transaction that mints zero revenue shares and credits zero cash fee.
- Root cause: floor rounding in the basis-point fee with no minimum-fee floor and no aggregation across calls, directly mirroring `grant.value/100 == 0` for `grant.value < 100`.

### Impact Explanation
The protocol's entire flash-loan fee revenue is evadable: every economically meaningful loan can be fragmented into zero-fee pieces, so `revenue`/`supplied` never accrue the flash fee the parameters imply. This is theft of unclaimed yield (protocol revenue that the market configuration says should be collected is never booked), reachable by any unprivileged address through a legitimate entrypoint. Magnitude is bounded by configured `flashloan_fee` and actual usage, but the evasion is complete and repeatable, not a rare edge case.

### Likelihood Explanation
High reachability, moderate economic weight. The attacker only needs a WASM receiver implementing `execute_flash_loan` (or `flash_position`-adjacent flows that pull flash liquidity) and to size each call under the `amount * fee_bps < BPS` bound. Whether this is profitable depends on fee tier and asset decimals — for low-decimals assets the threshold is a few whole units, keeping individual evasion small; however the attack scales linearly and costs only transaction fees. The pattern matches the acknowledged-but-real character of the source finding.

### Recommendation
Apply the same minimum-fee logic already used for liquidation: when `amount > 0` and `flashloan_fee > 0`, enforce `fee = max(computed_fee, 1)` — mirroring `bumped_fee` in `calculate_seized_collateral`. Alternatively round the fee up (`mul_div_ceil`) so any nonzero configured fee always yields at least one unit, and/or set a minimum flash-loan `amount` such that `amount * fee_bps >= BPS`. Either change makes fragmentation strictly more expensive than a single loan.

### Proof of Concept
1. Market has `is_flashloanable = true`, `flashloan_fee = 9` bps, 7-decimal asset; pool cash is ample.
2. Attacker deploys a receiver contract whose `execute_flash_loan` approves `amount` (not `amount + fee`) back to the pool.
3. Attacker calls `flash_loan(hub_asset, receiver, amount = 1_000, data)` — `fee = floor(1000 * 9 / 10000) = 0`; `terms.total_repayment == amount`; balance checks pass; `book_fee(0)` books nothing.
4. Repeat the call in a loop to reach any desired aggregate liquidity `X` with total fee paid `0`, versus `floor(X * 9 / 10000)` had it been taken as one loan. Revenue shares and cash credited to the protocol remain unchanged, while the attacker captured the full utility of the flash liquidity (e.g., for their own Aquarius/Soroswap trades) for free.
