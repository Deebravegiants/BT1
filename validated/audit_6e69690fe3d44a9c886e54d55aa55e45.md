### Title
Unbounded, cycle-vulnerable ancestry walk in GRANDPA `AncestryChain::ancestry` allows an attacker-crafted finality proof to hang consensus verification, freezing the light-client route - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` walks parent-hash links from a target block back to a base block using a `while current_hash != base` loop with no iteration bound and no cycle detection. The `ancestry` map it walks is built entirely from `unknown_headers`/`votes_ancestries`, both of which are attacker-supplied fields inside the `ConsensusMessage` proof passed straight into `GrandpaConsensusClient::verify_consensus`. This mirrors the lighthouse `filter_block_tree`/`find_head` class of bug: an untrusted, attacker-shaped block/header graph is traversed without bounding the walk against cycles or excessive length, and the traversal is invoked once per precommit, multiplying the cost.

### Finding Description
`AncestryChain::ancestry` in [1](#0-0)  is:
```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```
The `self.ancestry: BTreeMap<H::Hash, H>` is populated in `AncestryChain::new` directly from the attacker-supplied header list ( [2](#0-1) ), with no validation that the headers form an acyclic chain toward any particular base before this function runs. Because each header's hash and `parent_hash` are attacker-chosen fields inside an unverified struct, a submitter can construct two (or more) headers `A` and `B` where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`, neither of which is `base`. Once the walk enters `{A, B}` it can never reach `base`, and the `while` loop spins forever consuming CPU with no way to terminate.

This is reachable from `verify_with_voter_set` in the same file, which calls `ancestry_chain.ancestry(base_hash, ...)` once per precommit via the `finality_grandpa::Chain` trait during `finality_grandpa::validate_commit` ( [3](#0-2) ), and again directly from `verify_grandpa_finality_proof` ( [4](#0-3) ) and `verify_parachain_headers_with_grandpa_finality_proof`. All of these are invoked from `GrandpaConsensusClient::verify_consensus` ( [5](#0-4) ), the `ConsensusClient` implementation that processes relayer-submitted consensus update messages in `pallet-ismp`. The same unbounded call also appears in `verify_fraud_proof` ( [6](#0-5) ).

### Impact Explanation
Any unprivileged relayer can submit a GRANDPA consensus-update message whose `unknown_headers`/`votes_ancestries` contain a two-node parent-hash cycle. When `verify_consensus` processes it, `AncestryChain::ancestry` enters an infinite loop, hanging the extrinsic/call that processes it. Because this runs inside the runtime's consensus-client verification path (both for regular relaychain finality updates and for equivocation fraud proofs), a successfully triggered hang can consume unbounded execution weight/CPU during block execution or off-chain validation, preventing any further GRANDPA consensus state updates for that route — i.e., the light client for that state machine becomes permanently unable to advance, which stalls all message delivery (dispatch/relay) that depends on updated state commitments from that consensus client.

### Likelihood Explanation
The malicious input is trivial to construct (two synthetic headers referencing each other's hash as parent) and requires no special privileges, only the ability to submit a consensus update or fraud-proof message — the exact same permission any relayer already has. There is no upstream check that rejects cyclic or non-descending ancestry chains before the walk begins.

### Recommendation
Bound the `ancestry` walk by the number of distinct headers supplied (e.g., `self.ancestry.len()`), returning `finality_grandpa::Error::NotDescendent` once that bound is exceeded, and/or track visited hashes in a `BTreeSet` to detect and reject cycles before they cause an infinite loop. Apply the same bound to every call site that walks attacker-supplied ancestry (`verify_with_voter_set`, `verify_grandpa_finality_proof`, `verify_parachain_headers_with_grandpa_finality_proof`, and `verify_fraud_proof`).

### Proof of Concept
1. Construct two headers `A` and `B` (arbitrary bodies) such that `A.parent_hash == B.hash()` and `B.parent_hash == A.hash()`.
2. Submit a `FinalityProof`/`ParachainHeadersWithFinalityProof` whose `unknown_headers` = `[A, B, ...]` (padded as needed so `min_by_key`/`max_by_key` pick a `base`/`target` outside `{A, B}` but whose justification precommit ancestry routes through `A`/`B`), and a `GrandpaJustification` with a precommit target hash equal to `A`'s or `B`'s hash so `verify_with_voter_set`'s `ancestry_chain.ancestry(base_hash, target_hash)` call enters the `{A, B}` cycle.
3. Submit this as the proof to `GrandpaConsensusClient::verify_consensus` (or as one of the two proofs to `verify_fraud_proof`).
4. Observe that `AncestryChain::ancestry` never returns, hanging the call indefinitely.
