### Title
Unchecked slice-length arithmetic on relayer-controlled `message.from` panics `on_accept` in pallet-hyper-fungible-token - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` decodes the ABI-encoded `Message` body of an incoming HFT POST request and, when the message carries `data` (calldata) with no signature, derives the calldata-dispatch origin directly from `message.from` using unchecked slice arithmetic and a fixed-size `copy_from_slice`. Unlike every other place in this same file that touches attacker-supplied length fields (`message.to`, and `message.from` in `on_timeout`), this path performs no length validation before indexing, so a malformed/short `from` field causes a runtime panic instead of a typed error — the same bug class as CVE-2023-46930 (SEGV via unchecked array index on attacker-controlled length in `gf_isom_find_od_id_for_track`).

### Finding Description
`IsmpModule::on_accept` for the HFT pallet is reached whenever a relayer delivers a valid ISMP POST message whose commitment matches a known (already-verified) source contract via `ContractToAsset::<T>::get(source, &from)` (line 55). The *outer* `from` here is the `PostRequest.from` field — the peer contract address, which is checked against a registered mapping. However, `message.from` is a **separate, ABI-decoded field inside the message body** (`Message::abi_decode(&body)`, line 59) representing "the original sender on the source chain" and is fully attacker/relayer-controlled arbitrary bytes; it is never length-checked before this branch is reached: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

If `from_bytes.len() < 20` and `source.is_evm()`, `from_bytes.len() - 20` underflows `usize` (panics with an arithmetic-overflow check in debug builds, or produces a value that immediately causes an out-of-range slice panic in release builds — either way, a panic, not a graceful `Result::Err`). If `source` is not EVM and `from_bytes.len() != 32`, `copy_from_slice` panics on the length mismatch (`assert_eq!` internally). Both panics occur *after* the token mint/transfer for the beneficiary has already executed at lines 94-117, i.e., after state has been mutated in the same extrinsic — the panic then aborts/reverts the extrinsic (since pallet dispatch is transactional in Substrate, a panic in `on_accept` would abort block execution or, if caught by the executive as an error, cause the whole message-handling batch to be rejected), denying delivery of that and any batched messages, and burning the block's execution.

This is a direct pattern match to the reported CVE: an untrusted, attacker-supplied length value used to index/slice a buffer without a bounds check, in the code path that decodes a specific record ("original sender") from adversarial input, causing the client (here, the collator/validator executing the block) to crash/panic.

Compare with the *correctly guarded* sibling logic just a few lines away in the same file, which validates lengths first and returns typed errors: [2](#0-1) [3](#0-2) 

The vulnerable branch at lines 176-187 omits this same defensive pattern.

### Impact Explanation
Any account (or contract) able to get a POST request routed to a registered HFT source contract (i.e., any legitimate bridged EVM/Substrate token deployment already configured via `ContractToAsset`) can craft `message.from` with length ≠ 20 (for EVM source) or ≠ 32 (for non-EVM source) while still supplying non-empty `message.data` and no signature. Delivering this message causes the executing node to panic mid-extrinsic, after the mint/transfer of tokens to `beneficiary` has already been performed. Depending on how Substrate/FRAME's panic-handling interacts with the pallet's dispatch (this handler is not marked `#[transactional]` at this call site and panics are not caught by `Result`), this can produce inconsistent state (tokens minted but calldata dispatch/event never emitted) or halt block production for the unsigned message-handling extrinsic, functioning as a remotely triggerable denial-of-service against the messaging pipeline for this token bridge — a Medium-severity liveness/soundness issue analogous to the CVE's crash impact, reachable from a single relayed message with no privileged access required.

### Likelihood Explanation
High reachability: the vulnerable branch executes whenever `message.data` is non-empty and `substrate_data.signature` is `None`, both attacker/relayer-controlled fields inside the ABI-encoded body that is otherwise unauthenticated for content (only `source`/`from` peer-contract identity is authenticated, not the inner `Message.from` field). No proof forgery or consensus break is required — this is purely a malformed-input bug on the standard message-delivery path (`handle_unsigned` → `pallet-ismp::execute` → router → `HyperFungibleToken::on_accept`), the same "any relayer" reachability class validated for this scan.

### Recommendation
Validate `message.from`'s length before slicing/copying, mirroring the pattern already used for `message.to` (lines 62-71) and `message.from` in `on_timeout` (lines 224-232): return `HftError::InvalidSenderLength(from_bytes.len())` (or a dedicated error) when the length doesn't match the expected 20 (EVM) or 32 (non-EVM) bytes, instead of performing unchecked arithmetic/`copy_from_slice`.

### Proof of Concept
1. Register a valid HFT peer contract for state machine `Evm(X)` via `ContractToAsset` (as in normal operation).
2. Craft an ISMP `PostRequest` whose body ABI-decodes to `Message { to: <valid 20 or 32 bytes>, amount: <valid>, data: <SCALE-encoded SubstrateCalldata with signature = None, runtime_call = <any allowed call>>, from: <e.g. 3 bytes> }`.
3. Submit via `pallet_ismp::handle_unsigned` (or the equivalent unsigned extrinsic) with a proof that verifies the request as coming from the registered peer contract on `source = Evm(X)`.
4. During `on_accept`, the mint/transfer to `beneficiary` (derived from `message.to`, which is valid) succeeds at lines 94-117.
5. Execution reaches `from_bytes.len() - 20` with `from_bytes.len() == 3`, causing a `usize` underflow/slice-index panic, aborting the extrinsic after the token mutation has already occurred.
