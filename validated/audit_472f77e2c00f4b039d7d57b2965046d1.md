### Title
Permanent market freeze via `i128` overflow in accrual's `scaled_to_original` — debt value overflows before the borrow-index cap engages, bricking every verb on the market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` multiplies the market's RAY-scaled borrowed shares by the borrow index via `scaled_to_original`, which panics with `GenericError::MathOverflow` when the product no longer fits `i128`. Because every pool verb (supply, borrow, withdraw, repay, liquidate, `update_indexes`) runs `global_sync` → `accrue_chunk` → `accrue_step` first, once `borrowed * borrow_index` crosses the `i128` ceiling the entire market is permanently frozen — before `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` cap can ever engage. Any unprivileged address can both create the precondition (permissionless `supply` + `borrow` under configured caps) and trip the freeze via permissionless `update_indexes`.

### Finding Description
The bug class of CVE-2020-15673 (memory corruption → arbitrary state violation) maps onto this codebase's analog of unguarded arithmetic: RAY-domain `i128` overflow in share valuation. [1](#0-0) 
`accrue_step` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` at the top of every compounding step, before any index clamping can bound the inputs. `scaled_to_original` is a half-up `shares * index / RAY` multiply; both operands are RAY-scale, so the RAY-domain ceiling on the product is `i128::MAX / RAY ≈ 1.7e11` whole-token-equivalents × index multiple — the "RAY value ceiling." [2](#0-1) 
`global_sync` iterates chunks and calls `accrue_chunk`, which unconditionally calls `accrue_step`. There is no pre-check comparing `borrowed * borrow_index` against the representable domain, and no `try_` fallback — the panic propagates out of the entrypoint. [3](#0-2) 
The `mul_div_half_up` fast path uses `checked_mul`/`checked_add` and falls back to exact `I256` only for the intermediate; `to_i128()` returns `None` when the *result* exceeds `i128`, which `mul_div_half_up` converts into a `MathOverflow` panic. Widening cannot rescue an over-domain result. [4](#0-3) 
`update_borrow_index` clamps only *after* the product is computed — and, critically, the clamp bounds `borrow_index`, not `borrowed * borrow_index`. The index ceiling `MAX_BORROW_INDEX_RAY` (10³⁶) therefore does not bound the value overflow: the repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proves empirically that `scaled_to_original` panics while `borrow_index < MAX_BORROW_INDEX_RAY`, and that subsequent `withdraw` and `repay` calls revert identically. [5](#0-4) 
The reference docs acknowledge the cliff: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first." Documentation of a limit does not make the permanent-loss-of-funds outcome acceptable — there is no escape hatch (no governance sweep, no cap on `borrowed` independent of value, no accrual bypass).

### Impact Explanation
Permanent freezing of all user funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `claim_revenue`/`clean_bad_debt`/`recapitalize` on that market all accrue first and revert. The pool's token balance for that book is stranded forever — protocol insolvency-by-freeze. An attacker holding both a large supply position and a collateralized borrow on the same market can deliberately drive the market to the cliff and then trigger it via the permissionless `update_indexes`, taking every other supplier's funds hostage.

### Likelihood Explanation
Reachable end-to-end by unprivileged calls: `supply` (up to the configured cap), `borrow` (against collateral on any spoke), then waiting out accrual while periodically calling `update_indexes` (explicitly permissionless per the fuzz target comment "update_indexes is permissionless, so the caller chooses how a span is partitioned"). Feasibility depends on the market's cap and the token's realistic supply: the RAY ceiling is ~170 billion whole tokens at 18 decimals, but falls to ~170 million whole tokens when the supply index is near its 10²⁴ floor after a bad-debt write-down — within reach of high-supply tokens. Interest does the rest: at the steep end of a kinked curve the index multiplies ~170× in a few years (harness test reaches the cliff in under 40 years at 98% utilization; faster at higher effective rates). Likelihood is gated by capital, not by permissions — consistent with a High-impact, Medium-likelihood finding.

### Recommendation
Guard the accrual: compute the borrowed value with `try_mul_div_half_up` (or compare `borrowed` against `i128::MAX / borrow_index` before calling `scaled_to_original`); on overflow, either (a) pin `borrow_index`/`supply_index` and skip the value computation so exits remain possible, or (b) route to a reduced-value mode that still allows `repay`, `withdraw`, and `liquidate` to burn shares proportional to a saturated value. At minimum, enforce an entry-side bound in `borrow`/`supply` so `scaled_to_original` can never exceed `i128` for admitted shares at the index ceiling — i.e., cap admitted scaled shares at `i128::MAX / MAX_BORROW_INDEX_RAY`, closing the gap the current cap system leaves (caps only bound token units, not shares × index product).

### Proof of Concept
Preconditions: a market (say 18-decimal `BIG`) with caps admitting the token-to-RAY maximum, and a collateral market.

1. Attacker supplies `~1e29` base units of `BIG` (`supply(hub, BIG, principal)`), minting ~`principal * 10^9` RAY shares.
2. Attacker supplies collateral on a second market and calls `borrow` for ~98% of `BIG`, pushing utilization onto the steep curve segment where `borrow_rate` approaches `max_borrow_rate`.
3. Accrual compounds; each permissionless `update_indexes` call advances `borrow_index` multiplicatively.
4. When `borrowed_shares * borrow_index / RAY` crosses `i128::MAX`, the next `update_indexes` (or any user's `withdraw`/`repay`/`liquidate`) reverts with `MathOverflow` inside `scaled_to_original` at `common/src/rates/simulate.rs:60`.
5. Every subsequent call on that market reverts identically — the index never reached `MAX_BORROW_INDEX_RAY`, so no cap stops interest math, and no operation can bypass accrual. Funds are permanently frozen, matching the harness test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` which asserts `MATH_OVERFLOW` on `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay`.
