### Title
`register_token` overwrites `ContractToAsset` reverse mapping of an existing asset, letting a new registration hijack inbound transfer routing for an older asset - (File: modules/pallets/hyper-fungible-token/src/lib.rs)

### Summary
`pallet-hyper-fungible-token::register_token` writes `ContractToAsset::<T>::insert(chain, token_contract, local_id)` for every `(chain, token_contract)` pair supplied, with no check for whether that `(chain, token_contract)` key is already bound to a *different* `local_id` from a prior registration. This mirrors the Vader finding: a mapping keyed on a coarser identifier (there, `foreignAsset`; here, `(StateMachine, contract address)`) is silently replaced when a new, unrelated entry is registered, redirecting behavior that depends on that mapping for the previously-registered entry.

### Finding Description
`ContractToAsset` is the sole authentication mechanism for inbound cross-chain messages in `on_accept`: [1](#0-0) . Every asset registered via `register_token` unconditionally inserts into both `TokenContracts` and its reverse map `ContractToAsset` keyed by `(chain, token_contract)`, with no guard against re-registering a contract address that is already bound to another asset: [2](#0-1) 

By contrast, `update_token` explicitly removes the stale reverse-mapping entry before inserting a new one when re-pointing the *same* `asset_id` to a different contract [3](#0-2) , but this collision-avoidance logic only fires within a single asset's own configuration — it does nothing to prevent a *different, brand-new* `asset_id` from being registered with a `(chain, token_contract)` pair that already belongs to an older asset. `register_token` performs no lookup of `ContractToAsset` at all before inserting, so `CreateOrigin` (governance) registering a new token whose declared `token_contract` for some chain accidentally (or via any mistake in an otherwise-legitimate proposal) matches an existing token's contract address silently repoints the older asset's inbound routing to the new `asset_id`.

The storage layout itself documents the coupling but not any uniqueness invariant: [4](#0-3) .

### Impact Explanation
Once `ContractToAsset::<T>::get(source, &from)` for the old contract now resolves to the new `local_id`, any legitimate, correctly-signed inbound `Send` message from the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract for the original asset will be processed under the wrong `local_id` in `on_accept`: decimals/precision are read from `Precisions` for the new asset, and `mint_into`/`transfer` credits the **new** asset to beneficiaries instead of the original asset [5](#0-4) . This can mint/release the wrong fungible asset to arbitrary beneficiaries, effectively an unbacked mint of the newly-registered asset backed by escrowed/burn accounting that belongs to the older asset, and permanently breaks inbound settlement (and refunds via `on_timeout`, which uses the same `ContractToAsset` lookup) for the original token — a fund-safety and message-delivery-soundness issue reachable purely by governance registering a subsequent token, without any code path validating uniqueness.

### Likelihood Explanation
`register_token`/`create_asset_mapping`-equivalent registrations are privileged (`CreateOrigin`/governance), so this is not directly triggerable by an unprivileged actor, but it requires no malicious intent — a legitimate governance proposal registering a new token that (by clerical error, address reuse across networks, or a compromised/adversarial contract address supplied in the proposal) shares a `(chain, contract)` pair with an existing token silently corrupts routing for the prior token, with no runtime check to reject or flag the collision. Given multiple independent registrations accumulate over time and are only reviewed by external voters (not enforced on-chain), the likelihood of an unintentional collision — or a governance proposal being crafted to include a plausible-looking but colliding contract address — is non-trivial and unmitigated by any explicit invariant in the pallet.

### Recommendation
In `register_token`, before inserting into `TokenContracts`/`ContractToAsset`, check `ContractToAsset::<T>::get(chain, &token_contract)` and reject the call (or require it to only succeed for the same `local_id`, mirroring `update_token`'s stale-removal behavior) if a different asset is already bound to that `(chain, token_contract)` key. Bind the reverse map by `(chain, contract, asset)` uniqueness invariant enforced at registration/update time rather than relying on off-chain governance review.

### Proof of Concept
1. Governance registers asset `A` via `register_token` with `chains = {Evm(1) -> ChainConfig { token_contract: 0xAAAA..., decimals: 18 }}`, populating `TokenContracts[(Evm(1), A)] = 0xAAAA...` and `ContractToAsset[(Evm(1), 0xAAAA...)] = A` (`modules/pallets/hyper-fungible-token/src/lib.rs:356-367`).
2. A subsequent governance proposal registers a new asset `B` via `register_token` reusing the same contract address for `Evm(1)`: `chains = {Evm(1) -> ChainConfig { token_contract: 0xAAAA..., decimals: X }}`. No check exists against the current value of `ContractToAsset[(Evm(1), 0xAAAA...)]`, so it is overwritten to `B`.
3. A relayer delivers a legitimate, previously-in-flight (or newly sent) `PostRequest` from `0xAAAA...` on `Evm(1)` intended for asset `A`. `on_accept` looks up `ContractToAsset::<T>::get(source, &from)` and now resolves `local_asset_id = B` (`modules/pallets/hyper-fungible-token/src/module.rs:54-56`), causing the pallet to mint/release asset `B` to the beneficiary instead of `A`, using `A`'s escrow/burn accounting to back `B`'s mint.
