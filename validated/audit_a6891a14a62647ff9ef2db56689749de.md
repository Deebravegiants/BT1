Webhook `shop` tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over `@raw_body` only, while the `shop` value used to route/tenant-scope the webhook is read from an HTTP header that is never part of the signed bytes. `Registry.process` verifies the HMAC but then trusts `request.shop` as-is when dispatching to the app's handler, so the value an attacker fully controls (the header) is used as the tenant identity while a different value (the body) is what's cryptographically authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which only checks `to_signable_string` (the body) against the `hmac` header — and then immediately forwards the unauthenticated `request.shop` to the handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body, and never mixes in the `shop` header: [4](#0-3) 

This is structurally the same class of bug as the external report: a field that is *acted on* (here, the tenant/shop identity used to scope the webhook data) is not covered by the cryptographic binding (here, the HMAC), while a different field (the raw body) is what is actually verified. The equality that should hold is:

`shop authenticated by HMAC == shop used to attribute/store webhook data`

but the code only guarantees `body authenticated by HMAC == body parsed`, and `shop` is taken from an out-of-band, unsigned header.

Because Shopify signs webhooks for every shop that installs a given app using the same app-level secret (`client_secret`)—not a per-shop secret—any unprivileged merchant who installs the app can trigger real, validly-HMAC-signed webhook deliveries for their own shop (e.g. by editing a product, placing an order, etc., with attacker-chosen field content). That attacker can capture the exact `raw_body` + valid `hmac-sha256` header pair (since it's their own endpoint/webhook subscription and they control the network path to their own listener), then replay the identical `(body, hmac)` pair to the app's real webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is legitimately signed), and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This crosses the tenant boundary explicitly called out as in-scope: an unprivileged, internet-reachable actor (any merchant who has installed the app — no special privilege, no access token, no `client_secret` needed) can make the app process and persist attacker-influenced webhook data under a victim shop's identity. Depending on the host application's webhook handler (which typically upserts/deletes records keyed by `shop`), this enables cross-tenant data corruption/injection — e.g. writing attacker-controlled body content into the victim shop's stored webhook data, deleting/updating the victim's stored resources, or triggering mandatory GDPR-style handlers (`shop/redact`, `customers/redact`, `customers/data_request`) against the wrong shop. This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any external actor able to install the app on a shop they control (a normal, unprivileged flow for public/embedded apps) can obtain valid `(body, hmac)` pairs at will, since the same `client_secret` signs webhooks for all shops. No leaked credential, TLS interception, or social engineering is required — only the ability to replay an HTTP POST with a modified header, which is trivial once a legitimate webhook payload has been observed from the attacker's own store.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) header values into the HMAC-verified signable string, or otherwise cryptographically tie the header-derived identity to the payload before trusting it — e.g. include `shop-domain` in `to_signable_string`, or independently validate that the shop asserted in the header matches a shop expected for the corresponding webhook subscription/topic before dispatching to the handler. At minimum, document/enforce that handlers must not treat `request.shop` as authenticated unless it is included in the signed payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker performs an action (e.g., updates a product) that causes Shopify to send a webhook to the app's registered endpoint. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header (both are visible to them since it's delivered to infrastructure they control, or they run their own receiver during development/testing).
3. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's production webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [5](#0-4) 
5. `Registry.process` dispatches the handler with `shop: request.shop` == `"victim.myshopify.com"`: [6](#0-5) 
6. The host app's handler processes/stores the attacker-supplied body content under the victim shop's tenant record.
