### Title
Webhook `shop-domain` header is trusted without being bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely by HMAC-signing the raw request body, then unconditionally trusts the `shop-domain` header value as the identity of the shop the webhook came from. Since the app's `client_secret` (the HMAC key) is identical for every shop that installs the app, and the `shop` field is never part of the signed material, a malicious but legitimately-installed shop can capture one of its own valid, correctly-signed webhook deliveries and replay the identical body/HMAC pair while substituting a victim shop's domain in the `shop-domain` header. The library will accept it as authentic and hand the victim's identity to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed payload: [2](#0-1) 

`Registry.process` verifies only that the body's HMAC is valid, then immediately forwards `request.shop` (the unauthenticated header) to the app-supplied handler as trusted tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the signature solely over `verifiable_query.to_signable_string` (i.e., the body) using the app's single, shop-independent `Context.api_secret_key`: [4](#0-3) 

Because the HMAC key is the same for all shops of the app and the signature covers only the body, the binding "the `shop` field acted on by the handler" == "the shop the HMAC actually authenticates" does not hold. Any entity that can obtain one valid (body, HMAC) pair for the app — trivially available to any merchant who installs the app and receives their own legitimate webhook — can present that same pair with an arbitrary `shop-domain` header value and have it pass `HmacValidator.validate` unchanged.

### Impact Explanation
This breaks the tenant-identity binding the whole gem relies on to hand data to per-shop webhook handlers. An attacker-controlled shop can forge webhook deliveries that appear to originate from any other shop using the same app, causing the app's handler to process attacker-supplied body content under a victim shop's identity (`data.shop`). Depending on how the host app's handler is written (e.g., persisting `orders/create`, `app/uninstalled`, or GDPR payloads keyed by `shop`), this enables cross-tenant data corruption/confusion — writing or triggering actions against a shop the attacker does not own, using data they fully control. This matches the Critical "cross-tenant access" impact class, since the boundary that is supposed to separate tenants (the shop domain) is unauthenticated by the library itself.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own store (a normal, unprivileged path for any public/embedded Shopify app) — no access token, secret key, or privileged account is required. They only need to capture one legitimate webhook delivery to their own shop (trivial to trigger, e.g. by placing an order) and replay it with a modified `shop-domain` header against the app's webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed material, or independently verify that the `shop-domain` header corresponds to a shop actually known/authorized for this app (e.g., cross-check against a stored session for that shop) before trusting `request.shop`. At minimum, document that `shop-domain` is unauthenticated and must not be used as a sole tenant-selection key without additional binding, and consider deriving tenant identity only from data that is cryptographically bound to the signed body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a legitimate webhook (e.g. `orders/create`) to the app's registered endpoint; Shopify sends a request with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body with app's client_secret>`, and some JSON body.
3. Attacker replays this exact `raw_body` + `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body/HMAC pair and succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)` and processes attacker data under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
