### Title
Intent-solver funding pricing trusts an unbounded, unguarded Uniswap V4 spot price - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
The Simplex intent solver ("filler") prices curveless cross-asset pairs and, separately, sizes its Uniswap V4 liquidity-withdrawal funding plan directly from a Uniswap V4 pool's *instantaneous* `sqrtPriceX96` / `token0Price`/`token1Price`, with no TWAP and no mandatory deviation guard. This mirrors the Caviar `Pair.price` finding: a price derived from live, directly-movable pool state (an AMM tick, analogous to raw token balances/reserves) is exposed as an oracle to downstream logic that pays out real funds, without an invariant (like Uniswap V2's K-check on new liquidity) protecting it.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` reads the pool's current `sqrtPriceX96`-derived `token0Price`/`token1Price` as the USD price of the "exotic" token and returns it unmodified: [1](#0-0) 

This raw pool mid is then used by `resolveLegRates` in the fill strategy to set the exchange rate for the whole leg's notional, with no size/impact term: [2](#0-1) 

The only defense is `checkPriceGuard`, which is **optional** — a position's `referencePrice`/`maxDeviationBps` pair is not required, and the docs explicitly state a chain is "unguarded" if both fields are omitted: [3](#0-2) 

The project's own decision log documents this precisely as an accepted risk: the fee tier is read but never applied, there is no size/impact term, and price-guard is the *only* defense, checking deviation from a static reference rather than execution cost: [4](#0-3) 

The funding-withdrawal path (`planWithdrawalForToken`) independently re-derives amounts from the same live pool state (`buildSdkPosition`, `findLiquidityForDeficit`) at plan time, again with no TWAP protection: [5](#0-4) 

This is structurally the same bug class as the Caviar `Pair.price` report: a price is computed from a spot/instantaneous on-chain value (there: raw ERC-20 balances of a pair; here: a pool's current tick/`sqrtPriceX96`) that any unprivileged actor can move with an ordinary swap in the same block, and that moved price is consumed directly by logic that transfers real value (fill pricing and LP-withdrawal sizing) with no cumulative/TWAP safeguard and only an optional, not-enforced deviation bound.

### Impact Explanation
An attacker who can swap against the configured Uniswap V4 pool (any unprivileged trader — no bridge privilege required) can move `sqrtPriceX96` before an intent order's phantom-bid/fill window, causing the solver's `resolveLegRates`/`getExoticTokenPrice` to quote and fill orders at the manipulated price. Because the mid price is applied linearly across "the whole priced quantity" with no impact term, a modest pool move can be leveraged into an outsized mispricing on a large fill, letting the attacker (acting as counter-party/user of the phantom order, or coordinating with one) extract value from the solver's inventory — a concrete funds-loss scenario for the intent solver operating this configuration, and, via `PhantomBidWindowExhausted` → `updateLiquidityPools`, the same manipulated price propagates into `LiquidityPool.sellRate`/`buyRate` consumed by the indexer/route discovery, corrupting a data feed other integrators may rely on for the same solver-pricing purpose.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) a solver operator to configure a curveless pair with `[vault.uniswapV4]` pricing and no `referencePrice`/`maxDeviationBps` guard (explicitly documented as a supported, "unguarded" configuration), and (b) sufficient capital/flash liquidity to move the specific pool's tick meaningfully within the fill window. Both are realistic for thinner exotic-token pools (the documented use case, e.g. cNGN), which is exactly the scenario the pricing docs call out as needing (optional) guards. The developers' own decision notes concede the price/impact defense is intentionally absent beyond the optional static-deviation check.

### Recommendation
Follow the same remediation pattern recommended in the Caviar report: replace or supplement the instantaneous pool price with a time-weighted (TWAP) read (e.g., Uniswap V4's truncated oracle/observations, or an external oracle) before using it to price fills or size LP withdrawals. Additionally: (1) make the `referencePrice`/`maxDeviationBps` guard mandatory whenever Uniswap V4 pool pricing is enabled rather than optional; (2) add a size/impact term to `computeDirectPoolPriceUsd`/`resolveLegRates` so large notionals are priced against expected slippage, not a single mid; (3) apply the pool's fee tier (`pos.fee`) to the quoted price, which is currently read but discarded.

### Proof of Concept
1. Configure a Simplex filler with a curveless pair priced via `[vault.uniswapV4]` and no `referencePrice`/`maxDeviationBps` (a supported, documented configuration).
2. Attacker submits a large swap against the configured Uniswap V4 pool in/near the block the phantom order's bid window is being evaluated, shifting `sqrtPriceX96` far from the pool's fair value.
3. `UniswapV4FundingPlanner.getExoticTokenPrice` reads the moved price via `computeDirectPoolPriceUsd`; `resolveLegRates` applies it unclamped to the leg's full notional (`checkPriceGuard` never trips because no reference/deviation is configured).
4. The solver fills the order at the manipulated rate, transferring more value out (or receiving less) than the pool's true price would justify; the attacker profits from the difference, and the same manipulated quote is published downstream via the phantom-price snapshot into `LiquidityPool` rates. 	/**
	 * Resolves the pricing rate (token1 per token0) for a leg: the venue quote
	 * when available (validated against the price guard; USD-stable token0
	 * pairs only), otherwise the pair's curve for the leg's direction at the
	 * pair's capped token0 notional. Returns null when the leg cannot be priced
	 * (guard tripped, or direction disabled).
	 */
	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}
		}

		const askRate = leg.pair.askPricePolicy?.getPrice(cappedPairNotional) ?? null
		const bidRate = leg.pair.bidPricePolicy?.getPrice(cappedPairNotional) ?? null

		const rate = leg.inputIsToken0 ? askRate : bidRate
		if (!rate) {
			this.logger.debug(
				{ orderId, pair: `${leg.pair.token0}/${leg.pair.token1}`, inputIsToken0: leg.inputIsToken0 },
				"Rejecting leg: direction disabled for one-sided LP",
			)
			return null
		}
		return { rate, oppositeRate: leg.inputIsToken0 ? bidRate : askRate, priceSource: "policy" }
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
