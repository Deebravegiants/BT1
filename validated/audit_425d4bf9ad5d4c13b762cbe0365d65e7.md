### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values that the registry hands to application handlers are read directly from unauthenticated HTTP headers. This breaks the intended binding `hmac_verified(body) == identity_of(shop)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is parsed straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately forwards `request.shop` (an unverified header value) to the application's webhook handler as the authoritative tenant identity: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC secret — it never incorporates the `shop`, `topic`, `webhook_id`, or `api_version` headers into the signed material: [4](#0-3) 

Because Shopify's shared secret signs only the body, any legitimately-signed `(body, hmac)` pair delivered to a shared/multi-tenant webhook endpoint (e.g. one produced by the attacker's own store, which they can freely trigger because installing an app and receiving its own webhooks requires no elevated privilege) can be replayed to the same endpoint with an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because the body and HMAC are untouched — only the header claiming the tenant was changed. The application-level handler then processes attacker-controlled body content while believing it originates from an arbitrary victim shop (`data.shop`), as shown in the documented usage pattern that trusts `data.shop` directly: [5](#0-4) 

The docs even claim that `Registry.process` "will verify the request did indeed come from Shopify," which is misleading since only the body — not the claimed shop — is verified: [6](#0-5) 

Equality broken: `shop_bound_by_hmac == shop_acted_on_by_handler` — the left side doesn't exist (shop is entirely outside the HMAC-signed string), while the right side (`request.shop`, used for `WebhookMetadata.shop`) is fully attacker-controllable header content.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability. Any unprivileged actor who is able to obtain one valid `(body, hmac)` pair for the shared webhook endpoint (trivially achievable by installing the app on their own store, since Shopify delivers signed webhooks for that shop to the same shared endpoint) can spoof the sending shop for that replayed payload to any other shop domain string of their choosing. Depending on how the host application uses `data.shop` (e.g., looking up the merchant session/access token, triggering `app/uninstalled` cleanup, updating shop-scoped records, or feeding data into a per-shop pipeline), this can lead to cross-tenant data corruption, false triggering of shop-lifecycle actions (like session/token deletion) against a victim shop, or injection of attacker-chosen data attributed to a victim's tenant — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on an attacker-owned store or otherwise obtain one valid signed webhook body/HMAC pair for the endpoint, and (2) the ability to send an HTTP POST with modified headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is needed — this is squarely reachable by an unprivileged internet user/merchant.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verified signable content, or otherwise cryptographically tie the claimed `shop-domain` header to the verified body (e.g., cross-check `request.shop` against a shop value embedded in the verified payload, or require that the webhook only be trusted for the shop that installed/registered it). At minimum, update `Webhooks::Request#to_signable_string` so the signature covers the identity headers actually relied upon by `Registry.process`, and update documentation to stop implying that `Registry.process` verifies webhook *origin/shop*, when it currently verifies body integrity only.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (unprivileged, self-service action).
2. Shopify sends a legitimately signed webhook to the shared app endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY using app secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   BODY: {...attacker-controlled order payload...}
   ```
3. Attacker captures this exact `BODY` and `x-shopify-hmac-sha256` value (both are visible to them since it's their own store/traffic).
4. Attacker replays the identical request to the same endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC as above>
   x-shopify-shop-domain: victim-shop.myshopify.com
   BODY: {...same attacker-controlled payload...}
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — this passes because the body is byte-identical to step 2's legitimately-signed payload.
6. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker payload>, ...)`, causing the host application to process attacker-controlled data as if it came from `victim-shop.myshopify.com`.
