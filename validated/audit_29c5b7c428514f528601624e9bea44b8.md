### Title
Dangling Emporium-held ERC20 approvals from unsigned CASE 2 ops let any unprivileged caller drain co-mingled/pulled funds via the shared, non-isolated Emporium balance - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` measures token balance deltas globally on the Emporium contract (`getBalancesForArray` before/after the ops loop) with no per-user accounting, and `verifyWallet` is a no-op when `stack.signerAddress == address(0)` (unsigned CASE 2 path). Because CASE 2 ops execute arbitrary `op.endpoint.call(op.callData)` directly from Emporium (e.g. an `approve()` to a limit-order protocol), any allowance or balance left standing on Emporium after one user's `transact()` call is fair game for the very next caller's `transact()`, even though that caller's own `deltaAmountChanges[i]` for the affected token is `0`.

### Finding Description
The broken equality is: **tokens leaving an action == `-deltaAmountChanges` it received**, per token index `i`. In `handleOut`: [1](#0-0) 

`balanceChange` is computed purely from `balancesAfter[i] - balancesBefore[i]` (contract-wide `balanceOf(address(this))`, see `getBalancesForArray`/`getERC20OrETHBalance` in `Transferer.sol`), adjusted only by that same call's `deltaAmountChanges[i]`. Nothing in this computation excludes value that entered Emporium's balance because of state (an approval, or an unswept token balance) left over from a *different, earlier* `transact()` call.

The unsigned path is reachable without any signature check: [2](#0-1) 

CASE 2 ops call arbitrary attacker/victim-chosen `op.endpoint` with arbitrary `op.callData` directly as Emporium: [3](#0-2) 

This lets a "deposit" op include an `approve()` call granting a third-party protocol (e.g. a limit-order book) an allowance over Emporium's own token balance, exactly as a maker/order-creation flow requires. This approval is never revoked at the end of `runAction`. The circuit does not prevent an attacker from including any token address at index `i` with `amountChanges[i] == 0`, since the only per-token constraint is `inTotal + amountChanges[i] === outTotal` (trivially satisfied with 0 inputs/0 outputs), confirmed in: [4](#0-3) 

and `dimensionsCheck`/`checkOnchainCreation` in `HinkalHelper.sol` only check array lengths and onchain-creation invariants, not token ownership.

Exploit flow:
1. Victim calls `transact()` with an unsigned CASE 2 op set that deposits token A into Emporium and creates a maker order on a limit-order protocol (an `approve(protocol, A_amount)` plus an order-creation call), with `Emporium` as the maker/beneficiary. The order is not immediately filled, so `balanceChange` for A and any counter-token B is `0` in this call, and it completes cleanly.
2. The `approve(protocol, A_amount)` allowance from Emporium to the protocol remains standing indefinitely - nothing in `runAction`/`handleOut` resets it.
3. Attacker calls `transact()` (also unsigned CASE 2, no signature needed) with their own `erc20TokenAddresses` including token A (with `deltaAmountChanges[i] == 0`, since attacker owns no shielded UTXO of A) and an op that calls the protocol's `fillOrder` against the victim's still-open order, or directly calls the protocol outside Hinkal to pull A out via the dangling allowance and route proceeds back into Emporium.
4. `handleOut` sees `balancesAfter[A] - balancesBefore[A] > 0` (the victim's filled proceeds landing on Emporium) attributed entirely to the attacker's `msg.sender`, creating a UTXO/token transfer for the attacker despite `deltaAmountChanges[A] == 0`.

Existing guards fail because: `verifyWallet` performs no check for unsigned mode by design; `onlyAllowedRecipient` only restricts who can call `runAction` (must be Hinkal), not what `op.endpoint`/`op.callData` may do; and the balance-diff check is purely a same-call delta with no cross-call/per-depositor isolation.

### Impact Explanation
Direct theft of another user's co-mingled/in-flight funds transiently held (or approved) on the shared Emporium contract - a Critical impact matching "direct theft of shielded or in-flight user funds." The victim's deposited or order-committed tokens can be routed to an unrelated attacker's shielded UTXO or wallet. This is repeatable against any victim who leaves an outstanding Emporium-granted approval or unswept balance between transactions, and costs the attacker only gas plus crafting a matching op.

### Likelihood Explanation
Requires: (1) some unsigned CASE 2 flow that legitimately leaves an approval/order open on Emporium across transactions (a natural pattern for maker-style limit orders, which are explicitly the scenario CASE 2 stateless mode targets), and (2) an attacker able to observe/target that state and submit a second `transact()` (or a direct call to the approved spender) before it is consumed or cancelled. Both are fully within an unprivileged attacker's capability (crafting `CircomData`, `EmporiumStack`, choosing `op.endpoint`/`op.callData`, and timing). No signature, whitelist, or admin role is required.

### Recommendation
Do not let Emporium hold standing, cross-transaction ERC20 approvals or idle balances for unsigned (CASE 2) flows: revoke (`approve(spender, 0)`) any approvals granted during an op sequence before `runAction` returns, or require immediate consumption (fill-or-revert) of any maker-style order created via CASE 2 within the same `transact()` call. Alternatively, track and enforce per-depositor/session ownership of funds and allowances on Emporium instead of relying on a single contract-wide `balanceOf` snapshot.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 token A/B, and a mock limit-order protocol whose `createOrder` records `(maker=Emporium, amount)` and whose `fillOrder` performs `transferFrom(maker, taker, amount)` using a pre-existing allowance, sending the counter-asset back to `maker`.
2. Victim tx: call Hinkal `transact()` with unsigned CASE 2 (`stack.signerAddress == address(0)`) ops = `[approve(mockProtocol, A_amount), createOrder(...)]`, depositing token A into Emporium; assert it completes with `balanceChange == 0` for A and B.
3. Attacker tx: call Hinkal `transact()` (unsigned CASE 2) with `erc20TokenAddresses` including token A (`deltaAmountChanges[A] == 0`) and an op calling `mockProtocol.fillOrder(...)` as taker.
4. Assert `handleOut` transfers/creates a UTXO for attacker with `balanceChange > 0` for token A, i.e., attacker's payout exceeds `-deltaAmountChanges[A]` (which is `0`), proving theft of the victim's Emporium-held/committed balance.
