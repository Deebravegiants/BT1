Based on the codebase analysis, I found a concrete analog of the reported bug class in `orb-relay-client`, the crate that mediates state exchange between the Orb and a companion App during self-serve signups.

### Title
Unauthenticated `RequestState` message bypasses source-identity check and triggers replay of the last signup-state message to any sender - ([File: orb-relay-client/src/client.rs])

### Summary
The 0x report describes a check-bypass pattern: an unprivileged actor manipulates pending/pool-membership state by exploiting a code path that skips the ownership/identity verification normally required. `orb-relay-client`'s `PollerAgent::main_loop` contains an analogous authorization bypass: for every incoming payload it validates that the message's claimed source (`src.id`) matches the expected counterparty (`self.config.dst_id`) before processing it — except when the payload is a `self_serve::app::v1::RequestState` message, in which case the identity check is skipped entirely and the Orb's cached `last_message` (the last signup-state message sent) is replayed straight back to the sender.

### Finding Description
In `PollerAgent::main_loop`, incoming `RelayPayload`s are matched and, in the normal case, are only accepted into the message buffer if `src.id == self.config.dst_id` — i.e., only if the message really originates from the expected app/orb counterparty for that signup session: [1](#0-0) 

```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx
        .send(self.last_message.clone())
        .await
        .wrap_err("Failed to send outgoing message")?;
} else if src.id != self.config.dst_id {
    tracing::error!(
        "Skipping received message from unexpected source: {:?}: {payload:?}",
        src.id
    );
} else {
    self.handle_message(...).await?;
}
```

The `RequestState` branch is checked first and unconditionally replays `self.last_message` regardless of the `src` field of the incoming payload — the `src.id != self.config.dst_id` guard that protects every other payload type is never evaluated for it. This is architecturally similar to the 0x staking bug: the code has an ownership/identity check (`makerPoolId != poolId` there, `src.id != dst_id` here) that is meant to bind state actions to the correct principal (a maker's own pool / a session's own counterparty), but a specific special-cased message type skips it, letting any sender reaching this stream trigger the state-affecting action.

The client-side comment on `PollerAgent::main_loop` acknowledges the risk explicitly: [2](#0-1) 

This confirms that the relay transport can multiplex messages from sources other than the intended counterparty over the same connection, which is precisely the scenario the `src.id != dst_id` check exists to defend against — a defense that `RequestState` circumvents.

`last_message` is populated from whatever signup-state message the Orb (or App) last sent over this session — e.g. `AnnounceOrbId`, `CaptureStarted`, `CaptureEnded`, `SignupEnded`, `CaptureTriggerTimeout`, or `AgeVerificationRequiredFromOperator`: [3](#0-2) 

### Impact Explanation
Because the identity check is bypassed for `RequestState`, an entity that is not the verified counterparty of a given signup session (e.g. a stale/second app connection, a message injected via the multiplexed relay stream) can force replay of the orb's most recent signup-state message for that session. This is a cross-signup state bleed: signup progression state (which stage a session is in — capture started, capture ended, signup ended, age-verification required, etc.) can be obtained or replayed by an unverified party without the ownership check that governs every other payload type, undermining the session-binding guarantee `src.id == dst_id` is meant to enforce elsewhere in the same function.

### Likelihood Explanation
The relay client's own inline comment acknowledges that the underlying transport can deliver messages from multiple sources onto the same stream without per-message authentication being fully separated from the connection-level auth/subscription, and the `RequestState` code path is the only message type explicitly carved out of the `src.id` verification that guards all other payloads. Any client capable of causing a `RequestState`-typed payload to be delivered on this stream (already an accepted, first-class, unauthenticated-by-this-check message in the protocol) triggers the bypass deterministically — no cryptographic or timing conditions are required, only reachability of the stream.

### Recommendation
Apply the same `src.id == self.config.dst_id` verification to `RequestState` payloads before replaying `self.last_message`, matching the same-session/same-counterparty check enforced for all other incoming payloads. If replay-to-a-different-entity is an intended feature, it must be explicitly and separately authorized (e.g. against a resolved pool/session identity) rather than left as an implicit carve-out.

### Proof of Concept
1. Orb and App connect to `orb-relay` for `session_id` S, and the Orb sends a real signup-state message (e.g. `CaptureStarted`), which becomes `last_message` on the Orb's `PollerAgent`.
2. A different entity (not authenticated as the App bound to session `S`, but able to have a `RequestState` payload delivered on the Orb's response stream, per the client's own multiplexing caveat) sends `self_serve::app::v1::RequestState {}`.
3. Because the check at `orb-relay-client/src/client.rs:436` matches `RequestState` before the `src.id != self.config.dst_id` guard is ever evaluated, the Orb unconditionally replays `last_message` to the sender — irrespective of whether that sender is the legitimate session's App. [4](#0-3) 

The existing manual test `orb_to_app_with_state_request` demonstrates the intended `RequestState` -> replay flow using the correct session pairing; the vulnerability is that nothing in `main_loop` restricts this replay to the session's true counterparty.
