### Title
Truncation of the untrusted ISMP `PostRequest.from` field before length validation lets one app's bandwidth subscription be drained by a colliding sender identity - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`BandwidthGate::try_consume` derives the storage key that identifies "which app is spending bandwidth" by truncating the caller-controlled `request.from` bytes to a fixed 32-byte `AppKey` *before* any check binds the gate decision to the untruncated value: [1](#0-0)

`AppKey` is a `BoundedVec<u8, ConstU32<32>>`: [2](#0-1) 

`app` here is `request.from` — a field on the incoming `PostRequest` that is fully attacker-controlled by whoever dispatches the message on the source chain (see `ProxyModule::on_accept`, called for every inbound ISMP POST before it reaches the destination module): [3](#0-2) 

### Finding Description
`AppKey::truncate_from` silently drops any bytes beyond the 32-byte bound instead of rejecting oversized input, exactly mirroring the root cause of the reference bug: a security-relevant identity check (here, "which subscription bucket does this sender belong to") is computed from a value that is *normalized/transformed after* the value was accepted, rather than validating the length first and then deriving the key. Because `ismp::router::PostRequest.from` has no length constraint enforced anywhere upstream of the gate (unlike, e.g., the `ModuleIdBound` = 64-byte cap pallet-relayer imposes on `from` for its own reward-key derivation, see `modules/pallets/relayer/src/lib.rs:53-60`), a `from` value longer than 32 bytes is accepted, truncated, and used as-is to look up `Allowance`/`Allowlist`.

If two distinct `from` values share the same first 32 bytes (one exactly matching a legitimately-subscribed or allowlisted app's key, the other padded with extra attacker-chosen trailing bytes), both map to the identical `AppKey` after truncation. Any actor able to dispatch a POST request whose `from` is longer than 32 bytes and shares a 32-byte prefix with a paying app's identifier consumes that app's prepaid `Subscription` FIFO list or rides its `Allowlist` bypass — without ever running `BandwidthManager.purchase()` or being registered.

### Impact Explanation
This is a theft/drain of a paid, on-chain resource: `Allowance` subscriptions are purchased with real fee tokens via `BandwidthManager.purchase()` on the EVM side and only decremented by `try_consume`. An attacker who can trigger the collision drains a victim app's `remaining_bytes` for free, while the victim — who paid for and expects that bandwidth — is later rejected with `GateError::NoAllowance`/`Insufficient` when it tries to actually dispatch its own messages, i.e. denial of message delivery for a paying customer plus economic loss of the purchased bandwidth. The `Allowlist` collision variant is more severe: it lets an unpaying app permanently bypass metering by colliding with a protocol-allowlisted app's key.

### Likelihood Explanation
Exploitability hinges on whether some source chain path can hand pallet-bandwidth a `request.from` longer than 32 bytes. On a strict EVM `IsmpHost`, `from` is normally forced to the dispatching contract's 20-byte address, which would not trigger this. However, ISMP is chain-agnostic and `PostRequest.from` is an unconstrained `Vec<u8>` at the protocol level (module identifiers elsewhere in this codebase are documented as going up to 64 bytes, see `modules/pallets/relayer/src/lib.rs:55-59`), and nothing in `pallet-bandwidth` or the router rejects an oversized `from` before it reaches `try_consume`/`allowances`. I could not fully verify within the available tools whether every currently-integrated source-chain client actually enforces a ≤32-byte `from`, or whether the padding convention ("usually a 20-byte EVM address right-padded", per the `AppKey` doc comment) makes a colliding prefix hard to construct in practice for currently deployed apps. This uncertainty should be resolved before treating the finding as fully proven exploitable in production.

### Recommendation
Reject (rather than truncate) any `app`/`request.from` value longer than the `AppKey` bound before deriving the key in `try_consume`, `allowances`, `remaining`, and the purchase-credit path, so two different sender identities can never collide into the same billing bucket. Consider switching to `AppKey::try_from` (or an explicit length check with early return) at every call site in `modules/pallets/bandwidth/src/lib.rs` and `modules/pallets/bandwidth/src/types.rs`.

### Proof of Concept
Not independently reproduced against a live/simulated chain in this session; the analysis is based on static code reading of `try_consume`'s truncate-then-check ordering and the unconstrained size of `PostRequest.from`. A concrete PoC would require: (1) a source `StateMachine` whose ISMP client accepts a `from` field >32 bytes, (2) a legitimate app already holding a funded `Subscription` or `Allowlist` entry keyed by `AppKey` bytes `X` (≤32 bytes), and (3) an attacker-dispatched `PostRequest` with `from = X ++ <arbitrary extra bytes>`, which `AppKey::truncate_from` would collapse to the same key `X`, letting `try_consume` drain the victim's `remaining_bytes`. Recommend a Devin session with local devnet access to confirm whether any integrated source-chain messaging client (tesseract) currently permits dispatching such an oversized `from` value.
