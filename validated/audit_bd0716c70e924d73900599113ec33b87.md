### Title
Quadratic-cost `bytes.concat` accumulation in `Codec.Encode(Commitment)` allows a relayer-submitted BEEFY consensus proof to cause disproportionate gas amplification - ([File: evm/src/consensus/Codec.sol])

### Summary
`Codec.Encode(Commitment memory commitment)` rebuilds the SCALE-encoded commitment payload by repeatedly calling `bytes.concat` on a growing `bytes memory payload` inside a `for` loop over `commitment.payload`, exactly the anti-pattern described in the markdown-it `replaceAt()` advisory (build-by-reslice/reconcatenate instead of a single-pass builder). This function is invoked from `EcdsaBeefy.verifyMmrUpdateProof`, which is reachable by any unprivileged relayer submitting a BEEFY consensus proof through `ConsensusRouter`/`EvmHost`.

### Finding Description [1](#0-0) 

```solidity
function Encode(Commitment memory commitment) internal pure returns (bytes memory) {
    uint256 payloadLen = commitment.payload.length;
    bytes memory payload = bytes("");
    for (uint256 i = 0; i < payloadLen; i++) {
        payload = bytes.concat(
            payload,
            abi.encodePacked(commitment.payload[i].id),
            ScaleCodec.encodeBytes(commitment.payload[i].data)
        );
    }
    ...
}
```

Each loop iteration allocates a brand-new `bytes` buffer sized to the *entire accumulated payload so far* plus the new chunk, and copies the whole prior content into it (this is what `bytes.concat` does under the hood in Solidity — same shape as `str.slice(0, index) + ch + str.slice(index + 1)` in the JS report: full-buffer copy per iteration). With `n` payload entries this makes the total copy work O(n²), and because EVM memory-expansion gas cost itself grows quadratically with the buffer size, this is compounded further versus the linear-time JS string case — i.e., the on-chain equivalent is even more punishing per byte than the JS analog.

`commitment.payload` (`Payload[]`, where `Payload { bytes2 id; bytes data; }`) is fully attacker-controlled: it is `abi.decode`d directly from calldata supplied by whoever calls `EvmHost`/`ConsensusRouter`'s consensus-update entrypoint with a BEEFY proof, with no cap on `payload.length` or on the size of `payload[i].data` before `Codec.Encode` is invoked: [2](#0-1) [3](#0-2) 

`verify()` on `EcdsaBeefy` (and the sibling BEEFY paths behind `ConsensusRouter`) is the standard consensus-update entrypoint for the ISMP host and is not gated to a privileged relayer role — it is meant to be called by any relayer/updater submitting fresh consensus state, which matches the required "unprivileged relayer" reach for this class of finding.

`Codec.Encode` is invoked twice per `verify()` call: once for the `Commitment` (line 152) and once for the `PartialBeefyMmrLeaf` (used in `verifyMmrLeaf`, though that second call is a fixed bytes.concat of scalar fields, not the loop — the quadratic risk is specifically in the `Commitment` payload loop).

### Impact Explanation
An attacker can submit a BEEFY consensus proof whose `commitment.payload` array contains many entries (each carrying at least the mandatory `mh` MMR-root payload plus arbitrary filler entries with small `data`), driving the number of `bytes.concat` reallocation/copy passes up. Because both the number of copies and the size of each copy grow with `n`, execution cost grows superlinearly (worse than the O(n²) purely due to Solidity's quadratic memory-expansion gas schedule on top of the O(n²) copy volume). This can be used to:
- Push a legitimate consensus-update transaction to consume dramatically more gas than its calldata size would suggest, making relaying economically or practically infeasible (griefing/DoS on the consensus update path used to keep the light client in sync), and
- In the worst case exceed the block gas limit for what should be a modestly sized proof, effectively creating a route that cannot process/deliver messages until this function is bypassed or fixed, which is the "route unable to deliver messages" outcome called out as a valid impact.

This directly threatens availability of the BEEFY consensus-update pipeline (CWE-400/CWE-407, matching the report's classification), which gates state commitment updates for all downstream message verification on the affected route.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged role, staking, or fee-market gating was found preventing an arbitrary caller from invoking the BEEFY `verify()` path with a crafted proof; `commitment.payload.length` and each entry's `data` length are unbounded by any check prior to `Codec.Encode` being called at line 152 of `EcdsaBeefy.sol`. The only cost to the attacker is calldata gas for `n` small payload entries, which is linear, while the victim contract call's internal execution cost is superlinear — a classic amplification/DoS setup, analogous in shape (though more severe in absolute terms due to EVM memory-expansion costs) to the markdown-it `replaceAt()` issue cited in the report.

### Recommendation
Rewrite `Codec.Encode(Commitment memory)` to compute the total output length up front (sum of the fixed 2-byte `id` + SCALE length-prefix + data length per payload entry) and allocate a single output buffer once, then copy each segment into its final position (e.g., via low-level `mstore`/`Bytes` helpers or `abi.encodePacked` applied only once at the end over pre-assembled arrays), eliminating the O(n) repeated whole-buffer reallocation/copy pattern. Additionally consider bounding `commitment.payload.length` (a legitimate BEEFY commitment normally carries very few payload items, e.g., just the MMR-root entry) before encoding, to remove the attack surface entirely regardless of the encoding strategy used.

### Proof of Concept
Not independently executed against the deployed contract (no test harness run in this session), but the mechanism is directly demonstrable by constructing a `RelayChainProof` whose `signedCommitment.commitment.payload` array contains, say, a few thousand `Payload` entries (one legitimate `mh` MMR-root entry plus many filler entries with small `data`), then calling `EcdsaBeefy.verify(previousState, proof)` (or via `ConsensusRouter`) and observing gas consumption for `Codec.Encode` growing superlinearly with the number of payload entries — mirroring the JS PoC's escalating timings for `replaceAt()` at 10k/20k/40k/80k/160k repetitions. Confirming exact gas numbers on this specific EVM configuration would require running Foundry's gas-report tooling against `EcdsaBeefyTest`/`ConsensusRouterTest`, which was not performed in this analysis.
