### Title
Emporium EIP-712 wallet signature omits `feeStructure.feeToken`, allowing relay to drain a `HinkalWallet` in an unauthorised token - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`HinkalWallet` owners pre-authorise Emporium operations via an EIP-712 signature over `EMPORIUM_SIGNATURE_TYPEHASH`, which only binds `emporiumMessage`, the ops hash, `maxFee`, and `deadline`. The `CircomData.feeStructure` (which selects the actual `feeToken` charged against the wallet) is never part of this signed struct, so the wallet owner never authorises *which* ERC-20 is debited - only a bare numeric cap.

### Finding Description
In `verifyWallet()` [1](#0-0) , the signed payload is:
```solidity
EMPORIUM_SIGNATURE_TYPEHASH, circomData.emporiumMessage, _hashEmporiumOps(stack.ops), stack.maxFee, stack.deadline
```
and the only fee-related check is `circomData.feeStructure.flatFee > stack.maxFee` revert. `feeStructure.feeToken` (and `variableRate`) are not part of the typed-data hash and are not otherwise constrained relative to the signer's intent.

Later, `payRelayFees()` picks whichever `erc20TokenAddresses[i]` equals `feeStructure.feeToken` and, for the wallet-signer branch, sets `relayFee = flatFee` unconditionally on that token: [2](#0-1) . This flows into `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [3](#0-2) , which the `HinkalWallet` executes unconditionally for any caller that is the registered `emporium` contract: [4](#0-3) .

Because `feeStructure` (including `feeToken`) is chosen by whoever builds `circomData` and generates the surrounding ZK proof for the shielded balance change (the "prover"), and that party can be a relay distinct from the wallet-owning signer, the prover/relay can set `feeToken` to any asset present in `circomData.erc20TokenAddresses` while keeping `flatFee`'s bare numeric value ≤ `maxFee`. The wallet owner's signature never fixes the currency, so a numeric cap the owner believed was denominated in, e.g., a stablecoin can be silently re-denominated into a token with vastly different value/decimals (e.g. WBTC), draining far more value from the wallet than the owner authorised - equivalent to the report's core issue where a field that should be bound to an authorising commitment (owner/manager identity in the original report; `feeToken` here) is left outside the checked/signed scope, breaking the "charged token == what signer approved" invariant.

### Impact Explanation
This is theft of user (wallet-owner) funds beyond what was cryptographically authorised: the relay/prover can extract `flatFee`-many units of an arbitrary ERC-20 held by the `HinkalWallet`, not the token the signer intended, while the signature still validates. This falls under "theft of shielded or in-flight user funds" / "executing calls or moving assets a wallet owner ... never authorised" per the impact rubric - Critical/High depending on token chosen.

### Likelihood Explanation
Requires a relay (or whoever assembles `circomData`/generates the proof for the transaction) to act maliciously by picking an unexpected `feeToken`, while `flatFee` stays under `maxFee` and `feeStructure` is consistent with `calldataHash`/proof (which it can be, since the prover fully controls `feeStructure` at proof-generation time). No wallet-owner cooperation or extra approvals are needed beyond the existing standing authorization signature; the wallet executes `doSendToRelay` for any `emporium`-issued call. This is directly reachable through normal `runAction` flow, no privileged access required.

### Recommendation
Include `feeStructure.feeToken` (and ideally `variableRate`) in the `EMPORIUM_SIGNATURE_TYPEHASH` payload that the wallet owner signs, so the owner explicitly authorises which token can be debited and at what rate, not just a bare numeric cap. Alternatively, require the caller to specify the expected `feeToken` as part of the signed `EmporiumOperation`/`EmporiumStack` structure and revert if `circomData.feeStructure.feeToken` doesn't match.

### Proof of Concept
1. Wallet owner signs `EmporiumSignature(message=M, ops=[...], maxFee=1000, deadline=D)` intending `maxFee` to be denominated in USDC (6 decimals) for a routine op.
2. A malicious relay builds `circomData` for the transaction with `erc20TokenAddresses` including WBTC and sets `feeStructure = {feeToken: WBTC, flatFee: 1000, variableRate: 0}`. It generates a proof (or, if it is the prover itself, controls the ZK inputs) consistent with `calldataHash`.
3. `verifyWallet()` recovers the correct `signerAddress` (since `feeStructure` isn't part of the signed struct) and only checks `1000 <= 1000` (maxFee) → passes.
4. `payRelayFees()` computes `relayFee = flatFee = 1000` for `erc20TokenAddress = WBTC`, and calls `sendToRelayFromWallet(relay, signerAddress, 1000, WBTC)` → `IHinkalWallet(signerAddress).doSendToRelay(relay, 1000, WBTC)`.
5. The wallet transfers `1000` (raw units, ~8-decimal WBTC ≈ 0.00001 BTC per unit granularity, but if `flatFee` uses larger raw values the value discrepancy vs. the USDC-equivalent the owner expected can be orders of magnitude) to the relay - the owner never approved WBTC being spent.
