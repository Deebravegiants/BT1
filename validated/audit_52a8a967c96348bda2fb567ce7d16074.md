**Rationale (brief technical justification):**

The premise conflates two independent subsystems in the Move VM: gas metering and type safety enforcement.

`GasMeter::charge_create_ty` (in `third_party/move/move-vm/types/src/gas.rs`) only receives a `NumTypeNodes` value computed by callers (e.g. `frame.rs`, `frame_type_cache.rs`) via `Type::num_nodes()`/`num_nodes_with_max_depth()`/`num_nodes_in_subst()` in `third_party/move/move-vm/types/src/loaded_data/runtime_types.rs`, and uses it purely to compute a gas cost. It has no bearing on whether a type is accepted or rejected.

Actual size/depth limit enforcement is performed independently by `TypeBuilder::check_final_size_and_depth` / `check_before_count_increment` in `runtime_types.rs`, which walk the real type structure during construction (`create_ty_with_subst`, etc.) and return `StatusCode::TOO_MANY_TYPE_NODES` / `VM_MAX_TYPE_DEPTH_REACHED` if exceeded — this check does not depend on the gas meter's counted value at all. [1](#0-0) 

Even hypothesizing a discrepancy between the gas-charged node count and the true node count would at most cause gas mis-pricing (an economic/DoS concern out of scope per the review bounds), not a bypass of the depth/size limiter, since that limiter is enforced by a separate, structurally-driven check.

Furthermore, "type confusion between two distinct object resource types sharing overlapping storage keys" is not a mechanism that exists in Move: resource/struct field access is resolved through `StructDefInstantiationIndex`/`FieldInstantiationIndex` bound to concrete, verifier-checked struct definitions in `frame_type_cache.rs`, not through node-count comparisons. [2](#0-1) 
There is no code path shown, nor found in review, where a gas-counting discrepancy could cause the interpreter to treat one struct's storage layout as another's — type identity and field offsets are determined by the bytecode verifier and module linking, independent of gas accounting.

No unprivileged entrypoint, storage-key collision, or type-witness confusion mechanism tied to `charge_create_ty` was identified that would let an attacker read/write another object's owner field.

    /// Given [`Type`]'s node count and depth, returns an error if these values exceed limits.
    pub fn check_final_size_and_depth(&self, count: u64, depth: u64) -> PartialVMResult<()> {
        // Note: must be greater than because we check for final node count.
        if count > self.max_ty_size {
            return self.too_many_nodes_error();
        }
        if depth > self.max_ty_depth {
            return self.too_large_depth_error();
        }
        Ok(())
