### Title
Unauthenticated cross-session `RequestState` handling causes orb-relay clients to replay their last message to any sender - ([File: orb-relay-client/src/client.rs])

### Summary
`PollerAgent::main_loop` in `orb-relay-client` checks incoming relay payloads for the `self_serve::app::v1::RequestState` type and, if matched, immediately replays `self.last_message` to the sender — without validating that the message actually originated from the paired `dst_id` (the Orb-App session partner). Every other payload type is source-checked against `src.id != self.config.dst_id` before being accepted, but the `RequestState` branch is checked and handled before that guard is reached, and it bypasses it entirely. This mirrors the audited `WellUpgradeable` bug class: a privileged operation (replaying/exposing session state) is missing the access-control check ("only the paired session partner") that every other code path enforces.

### Finding Description
In `orb-relay-client/src/client.rs`, the connection loop dispatches incoming `RelayConnectResponse` payloads as follows: [1](#0-0) 

```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx
        .send(self.last_message.clone())
        .await
        .wrap_err("Failed to send outgoing message")?;
} else if src.id != self.config.dst_id {
    tracing::error!(
        "Skipping received message from unexpected source: {:?}: {payload:?}",
        src.id
    );
} else {
    self.handle_message(...).await?;
}
```

The `src.id != self.config.dst_id` authorization check — the mechanism that restricts message processing to the currently-paired Orb/App session partner — is only evaluated in the `else if` branch. Because the `RequestState` check is placed first and unconditionally triggers a reply with `self.last_message`, any relay-connected entity capable of sending a `RequestState` payload addressed to this client's queue (i.e., any `App`/`Orb` counterpart reachable through the relay backend, not necessarily the one that is `dst_id`-paired for this session) will get `self.last_message` echoed back, regardless of `src.id`.

`self.last_message` is the last `RelayPayload` sent by this client to its (assumed) session partner — e.g., during a signup, this can carry self-serve session state such as `CaptureStarted`, `SignupEnded`, `CaptureTriggerTimeout`, or other signup-lifecycle payloads exchanged between the Orb and the App: [2](#0-1) 

This function is used by both `Mode::Orb` and `Mode::App` (the same client code drives orb-side and app-side relay clients), and is exercised in normal self-serve signup flow, e.g. waiting for `StartCapture`/emitting `CaptureStarted`/`SignupEnded`: [3](#0-2) 

### Impact Explanation
This breaks the intended trust boundary between paired Orb/App sessions on the relay channel. An unprivileged party that can address a `RequestState` message to another session's relay queue (relying only on relay routing, not on cryptographic session binding for this specific check) can force disclosure of the last signup-lifecycle message belonging to a different signup session — e.g. observing whether/when biometric capture started, or that a specific signup ended successfully/failed — which is a cross-signup state bleed. It does not directly disclose biometric image data itself, but it does leak signup-session state/status across session boundaries without authorization, and the pattern is structurally identical to the referenced report: a state-mutating/state-disclosing action ("replay last message") is missing the access check that every sibling code path in the same function enforces.

### Likelihood Explanation
Likelihood depends on whether the relay backend server (not present in this repo) enforces that a client can only ever receive payloads whose `src` equals its paired `dst_id`, in which case this is a defense-in-depth gap rather than an independently exploitable bug. This repo only contains the client-side implementation; the relay server-side routing/authorization logic is out of scope/not visible here, so it cannot be confirmed with full certainty whether the relay server already prevents cross-session payload delivery (which would make this an inert defect) or whether it, like every other payload type in this same handler, relies on the client's own `src.id` check for enforcement (in which case this is directly exploitable by any relay-connected peer). Given that the code explicitly performs this exact check for all *other* payload types, the omission for `RequestState` is very likely an intended-but-missed authorization check, consistent with the "modifier mistakenly omitted" root cause in the reference report.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special-case so that it applies uniformly to all payload types:

```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}: {payload:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await.wrap_err("Failed to send outgoing message")?;
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. Establish two relay sessions with the backend: session A (Orb `orb-A` ↔ App `app-A`) and session B (any relay-connected entity `X` that can route a payload addressed with `src` other than `app-A`/`orb-A` but delivered into `orb-A`'s or `app-A`'s response stream, depending on what the relay server's routing rules actually permit).
2. Have `orb-A` (or `app-A`) send at least one normal message during an active signup (e.g., `CaptureStarted`), which gets stored in `self.last_message`.
3. From entity `X`, send a `self_serve::app::v1::RequestState` payload that reaches `orb-A`'s (or `app-A`'s) `response_stream`.
4. Observe in `main_loop` that the `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch fires before the `src.id != self.config.dst_id` check, causing `self.last_message` (session A's signup-lifecycle state) to be sent back to whatever channel produced the response — without verifying that the request actually came from `app-A`/`orb-A`.

Note: I could not verify server-side relay routing/authorization behavior (it is not part of this repository), so exploitability ultimately hinges on relay-server routing guarantees that are outside the indexed codebase; this should be validated against the actual `orb-relay` backend service before treating this as conclusively exploitable in production.

async fn proceed_with_biometric_capture(orb: &mut Orb) -> Result<bool> {
    let Config {
        self_serve,
        self_serve_app_skip_capture_trigger,
        self_serve_app_capture_trigger_timeout,
        ..
    } = *orb.config.lock().await;
    if !self_serve || self_serve_app_skip_capture_trigger {
        // Biometric capture not gated by a user action. Continue.
        orb.ui.signup_start();
        return Ok(true);
    }

    let orb_relay = orb.orb_relay.as_mut().expect("orb_relay to exist");

    tracing::info!("Waiting for self-serve biometric-capture trigger...");
    if let Err(e) = orb_relay
        .wait_for_msg::<self_serve::app::v1::StartCapture>(self_serve_app_capture_trigger_timeout)
        .await
    {
        if let Err(e) = orb_relay.send(self_serve::orb::v1::CaptureTriggerTimeout {}).await {
            tracing::warn!("failed to send CaptureTriggerTimeout: {e}");
        };
        orb.ui.signup_fail(SignupFailReason::Timeout);
        tracing::warn!("Self-serve biometric-capture start was not triggered: {e}");
        return Ok(false);
    };

    tracing::info!("Self-serve biometric-capture start triggered");
    orb.ui.signup_start();

    tracing::info!("Self-serve: Informing orb-relay that biometric_capture has started");
    orb_relay
        .send(self_serve::orb::v1::CaptureStarted {})
        .await
        .inspect_err(|e| tracing::error!("Relay: Failed to CaptureStarted: {e}"))?;

    Ok(true)
}
