### Title
Webhook HMAC verification excludes the `shop` (and `topic`/`webhook-id`) header, allowing cross-tenant shop-domain spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature Shopify computes with the app's `client_secret` binds nothing but the payload bytes. The `shop-domain`, `topic`, and `webhook-id` headers — which `ShopifyAPI::Webhooks::Registry.process` trusts to identify the tenant and dispatch the handler — are never covered by that signature.

### Finding Description
`Utils::HmacValidator.validate` verifies `HMAC(secret, verifiable_query.to_signable_string) == verifiable_query.hmac`: [1](#0-0) 

For OAuth callbacks, `AuthQuery#to_signable_string` deliberately folds `shop` into the signed string, so `shop` is bound to the signature: [2](#0-1) 

For webhooks, however, `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated headers: [3](#0-2) 

`Registry.process` validates only this body-only HMAC and then dispatches the handler using the unauthenticated `request.shop`: [4](#0-3) 

The equality the identity binding is supposed to enforce is:
`HMAC-verified bytes == bytes that determine the tenant (shop) the event is attributed to`

Here it is broken: `to_signable_string == raw_body`, but `request.shop` (used to build `WebhookMetadata` passed to the handler) is taken from a header outside that signed string. Any request whose body+HMAC pair is valid for the app's secret — regardless of which shop actually produced it — will pass verification no matter what `shop-domain` header accompanies it.

### Impact Explanation
An unprivileged internet user who controls (or has legitimately triggered) a Shopify store — even their own free/test store using the same app — can capture one genuine webhook delivery (valid `raw_body` + HMAC computed by Shopify with the app's real secret) and resend it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. Because the gem's HMAC check never covers the shop header, `Registry.process` accepts the forged request as valid and calls the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop. Any handler logic that scopes data writes/reads by `data.shop` (the normal, documented usage pattern for this gem) can be tricked into acting on the wrong tenant — a cross-tenant integrity/confusion issue reachable without any credentials, access tokens, or `client_secret` knowledge by the attacker.

### Likelihood Explanation
The attacker only needs the ability to receive one legitimately signed webhook (e.g., from a store they control that installed the same app) and then replay/rewrite the `shop-domain` header when POSTing to the app's public webhook URL. No secret material, session, or privileged access is required — only network reachability to the endpoint that this gem's `Registry.process` exposes.

### Recommendation
Include the trusted shop/topic/webhook identifiers in the signed material verified for webhooks, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., verify the shop against session/subscription records rather than relying solely on the header), so `Registry.process` cannot attribute a validly-signed body to an attacker-chosen tenant.

### Proof of Concept
1. Attacker installs the target app on their own (or any) Shopify store and triggers a real event (e.g., `orders/create`), causing Shopify to POST a webhook to the app's endpoint with a body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker intercepts/replays this exact request but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-webhook-id`/`topic`, which are also unauthenticated) and resends it to the same endpoint.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` (per `Webhooks::Request#to_signable_string` returning only `@raw_body`) and it still matches, since `B` and the HMAC are unchanged. [5](#0-4) 
4. `Registry.process` proceeds and invokes the app's handler with `shop: request.shop` set to `victim-shop.myshopify.com`, even though the payload actually originated from the attacker's own shop. [6](#0-5)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
