### Title
Storage-Deposit Cache Key Collision via Unseparated Concatenation Can Cause Withdrawals to Skip Required NEAR Storage Deposit - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its cache key by naively concatenating `contractId` and `accountId` with no delimiter. Because NEAR account IDs can contain arbitrary combinations of lowercase letters, digits, `.` and `-`, two different `(contractId, accountId)` pairs can produce an identical concatenated string. A collision causes `estimateWithdrawalFee`/`validateWithdrawal` to read back a previously cached storage-balance result that was computed for a *different* token/account pair, exactly analogous to the reported bug class where a stale/incorrectly-scoped state value is reused instead of being freshly (re)computed for the current call.

### Finding Description
`getCachedStorageDepositValue` is the sole gate that decides whether a NEAR withdrawal needs an extra `storage_deposit` fee before transferring NEP-141 tokens to `destinationAddress`: [1](#0-0) 

The cache key is formed as:
```
const key = `${contractId}${accountId}`;
```
with no separator between the two components. This means the equality the code relies on — "the cached `[minStorageBalance, userStorageBalance]` pair belongs to exactly this `(contractId, accountId)`" — can be broken: any two distinct pairs `(contractId1, accountId1)` and `(contractId2, accountId2)` whose concatenations are byte-identical (e.g. `contractId1` is a prefix of `contractId2 + accountId2` at the exact boundary) collide in the `LRUCache`, so a query for one pair silently returns the cached result for the other.

The result feeds directly into a decision that skips the NEAR storage-deposit fee: [2](#0-1) 

If `minStorageBalance <= userStorageBalance` (from a colliding, unrelated cache entry) is wrongly returned as true for an account that is *not* actually registered/funded on the real token contract, the SDK builds a withdraw intent without the required `storage_deposit`, per `createWithdrawalIntents`: [3](#0-2) 

The codebase itself documents the consequence of skipping this check in the sibling `OmniBridge` implementation: if the storage balance is insufficient, "funds will be refunded to the intents contract account instead of the original withdrawing account": [4](#0-3) 

The `DirectBridge`'s NEAR-native flow has the same underlying failure mode: a NEP-141 `ft_transfer`/withdraw to an unregistered account fails or is refunded on-chain, and because the SDK believed no storage deposit was needed, the funds end up stuck at the token contract / intents contract rather than at `destinationAddress`.

### Impact Explanation
This breaks the equality "storage balance data returned equals the data queried for the specific (token, account) pair", enabling a withdrawal to bypass the mandatory storage-deposit fee for an account that actually needs it. The consequence — a withdrawal whose funds are not delivered to the destination and instead get stuck/refunded to the intents/bridge account, requiring manual intervention to recover — matches the High-severity class ("a withdrawal stuck until manual intervention").

### Likelihood Explanation
`accountId` (the withdrawal `destinationAddress`) is fully attacker/user-controlled, and NEAR account-ID syntax (lowercase letters, digits, `.`, `-`) allows constructing strings that reproduce another valid `contractId+accountId` concatenation boundary. Any shared long-lived `DirectBridge`/SDK instance (e.g., a backend service processing withdrawals for many users) accumulates cache entries over time (`ttl: 3600000`ms, `max: 100`), increasing the chance that some future request's concatenation collides with an existing entry. The bug is triggered purely by SDK-side caching logic, requires no privileged action from an integrator, relayer, or bridge operator, and does not depend on external RPC/price-feed trust assumptions.

### Recommendation
Use a collision-free cache key, e.g. a delimiter guaranteed not to appear unescaped, or a structured key (array/tuple) or a JSON-stringified `{contractId, accountId}` object, or hash the two fields separately, e.g.:
```ts
const key = `${contractId}\u0000${accountId}`;
```
Apply the same fix defensively to any other concatenation-based cache keys in the bridges (e.g. verify `omni-bridge.ts`'s `${omniChainKind}:${contractId}` key cannot collide given the fixed `ChainKind` enum values).

### Proof of Concept
1. A withdrawal for token `contractId1 = "tkn.factory.near"` to a registered/funded account `accountId1 = "alice.near"` is processed; since `userStorageBalance >= minStorageBalance`, the result is cached under key `"tkn.factory.nearalice.near"`.
2. An attacker (or an unrelated legitimate user) later requests a withdrawal for a different token `contractId2 = "tkn.factory.nearalice"` (a distinct, valid NEAR account usable as a token contract ID) to `accountId2 = ".near"`-style constructed destination such that `contractId2 + accountId2 === "tkn.factory.nearalice.near"`.
3. `getCachedStorageDepositValue` returns the cached (unrelated) result for step 1's pair, wrongly reporting sufficient storage balance for `accountId2` on `contractId2`.
4. `estimateWithdrawalFee` returns a `0n` storage-deposit fee, and `createWithdrawalIntents` builds the withdraw intent without `storage_deposit`.
5. On-chain, since `accountId2` is not actually registered on `contractId2`, the NEP-141 transfer fails/refunds to the bridge account rather than reaching `accountId2`, leaving the withdrawer's funds stuck pending manual recovery.

```typescript
	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
```
