## Title
No Slippage/Price Bound on Native-Token-to-FeeToken Swap Enables Sandwich Attacks in `EvmHost.dispatch()` / `fundRequest()` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all let a caller pay Hyperbridge's dispatch fee in native token by forwarding `msg.value` straight into `IUniswapV2Router02.swapETHForExactTokens`, with the entire `msg.value` acting as the implicit `amountInMax` and no independent price/slippage bound. This mirrors the reported SteadeFi bug class: a swap where `amountIn` is set to a much larger pool of funds than strictly required to reach a fixed `amountOut`, with no oracle- or slippage-based ceiling on the effective execution price, letting an attacker sandwich the swap and capture the difference. [1](#0-0) 

### Finding Description
In `dispatch(DispatchPost memory post)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The identical pattern is repeated in `dispatch(DispatchGet)` and `fundRequest()`. [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` targets an exact output (`post.fee` feeToken units) and uses the full `msg.value` sent as the maximum acceptable input — there is no separate, independently-computed `amountInMax` tied to a fair/oracle price, and no minimum-price guard at all. This is structurally the same root cause as the SteadeFi report: the contract lets `amountIn` float up to the entire balance/value made available for the swap, bounded only by whatever the caller happened to send, rather than by a manipulation-resistant price check. The docs for this same host function explicitly acknowledge that the companion `quote()` helper (which calls `getAmountsIn` on the same router) "is vulnerable to sandwich attacks" and should only be used off-chain — but no on-chain protection exists at the point where the actual swap executes. [4](#0-3) 

Because the local UniswapV2 pool used for this swap can be shallow/thin (it exists purely to let Hyperbridge accept native-token payment on each supported chain), an attacker can front-run a `dispatch()`/`fundRequest()` call, skew the WETH/feeToken reserves so that filling the fixed `post.fee`/`get.fee`/`amount` output consumes far more ETH than the fair-market price would require, and back-run to restore the pool — extracting the difference as sandwich profit. Any application or end user that dispatches a cross-chain message paying with native token (a completely unprivileged, single-transaction action) is exposed.

### Impact Explanation
This is directly reachable from any unprivileged, single transaction: any user or `IApp` dispatching a POST/GET request or funding a request with native token calls `IDispatcher(host()).dispatch{value: msg.value}(...)`, a normal top-level entry point of the protocol (`EvmHost`/`IDispatcher`, used pervasively across the SDK and docs for message dispatch). [5](#0-4) [6](#0-5) 

An attacker who monitors the mempool can sandwich any such native-token-paid dispatch to skim value out of the sender's `msg.value` beyond what the natural market price would require, i.e., theft of the depositor's native token funds via price manipulation of a swap with no real slippage protection — the exact bug class ("Front-Run Attacks Due Slippage Mishandling") described in the report, applied here to Hyperbridge's core fee-payment swap rather than a GMX vault swap.

### Likelihood Explanation
Likelihood is high wherever the local Uniswap V2 pool used for `feeToken`↔native swaps has shallow liquidity relative to typical dispatch amounts (a very plausible situation for a bridge fee token pool on many chains), since:
- No governance/admin permission is required to trigger the vulnerable code path — dispatching with `msg.value > 0` is a normal user action.
- The transaction is broadcast to the public mempool before inclusion, giving a searcher-bot ample opportunity to sandwich it.
- No slippage/oracle bound exists to make sandwiching unprofitable or bounded.

### Recommendation
Do not rely purely on the size of `msg.value` as the implicit slippage bound. Instead:
1. Compute an expected fair price via a manipulation-resistant oracle (e.g., a TWAP from the same pool, or a Chainlink price feed for the native/feeToken pair) and enforce that the swap's effective price stays within an acceptable band of that oracle price, reverting otherwise.
2. Alternatively/additionally, expose an explicit `maxNativeIn` parameter that callers set based on their own off-chain quote (with a bounded buffer), rather than treating the entire `msg.value` as automatically spendable, and refund any leftover native token immediately to the original caller (not simply retained by the host) so callers aren't implicitly penalized for buffer overestimation and are not incentivized to send more than a tightly-bounded amount.
3. Consider using `swapTokensForExactTokens`/`swapETHForExactTokens` together with a router or aggregator that supports the `deadline` and `amountInMax` explicitly validated against an oracle-derived ceiling, per the report's suggested fix.

### Proof of Concept
1. Attacker observes a pending `dispatch(DispatchPost)` (or `DispatchGet`/`fundRequest`) transaction in the mempool with `msg.value = X` and a target `post.fee = F` feeToken.
2. Attacker front-runs with a large ETH→feeToken swap on the same local Uniswap V2 pool (`_hostParams.uniswapV2`), shifting reserves so more ETH is needed to buy `F` feeToken.
3. The victim's transaction executes `swapETHForExactTokens{value: X}(F, [WETH, feeToken], address(this), block.timestamp)`; because the pool is now skewed, the amount of ETH actually consumed to fill `F` is much closer to (or exceeds, causing a revert/DoS) `X`, instead of the fair-market cost the user computed off-chain.
4. Attacker back-runs, selling feeToken back for ETH, capturing the price impact created in step 2 as profit — funded by ETH that would otherwise have stayed unspent/refunded from the victim's `msg.value`.
5. Repeated for every dispatch paid in native token, this can systematically drain excess native-token value from any user or `IApp` using this payment path, with no protocol-level protection against it.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
