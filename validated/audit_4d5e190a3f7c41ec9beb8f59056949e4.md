Confirmed: for OAuth, `AuthQuery#to_signable_string` includes `shop` and `host` in the HMAC-signed payload [1](#0-0) , so `shop`/`host` cannot be tampered with without invalidating the HMAC. By contrast, the webhook path signs only the raw body and leaves the `shop`-domain header completely outside the signature.

### Title
Webhook shop-domain attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (the tenant identifier the app attributes the webhook payload to) is read from an unauthenticated header. `Registry.process` validates the HMAC and then unconditionally dispatches `request.shop` to the app's handler, so the value used for tenant attribution is never bound to the value that was actually signed.

### Finding Description
`HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` is defined as just the raw body: [3](#0-2) 

`shop` is pulled from the `shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [4](#0-3) 

`Registry.process` validates the HMAC (over the body only) and then hands `request.shop` straight to the registered handler as the authoritative tenant identifier: [5](#0-4) 

This is the exact bug class described in the external report: a value that participates in a security-relevant computation (`fees` incremented by `_redeemWstEth` but treated as `Ether`) is misattributed because the accounting/binding does not track the value's true origin. Here, the equality that should hold is:
`shop-domain header == the shop bound inside the HMAC-signed payload`
but nothing in the code enforces this — the header can be swapped for a different value without breaking the signature, exactly as `AuthQuery#to_signable_string` demonstrates is achievable (it explicitly folds `shop` and `host` into the signed string) but `Webhooks::Request` does not do the same.

### Impact Explanation
Any actor able to obtain one legitimately-signed webhook body for their own shop (e.g., by installing the app on their own store — no special privilege required) can resend that exact body with a modified `x-shopify-shop-domain` header naming a different, victim merchant. The HMAC still validates because it never covered the shop header, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any host application that uses `data.shop` from `WebhookMetadata` to look up/update per-tenant records will act on the wrong tenant's data — a cross-tenant access/confusion condition, which is classified Critical per the report's impact taxonomy.

### Likelihood Explanation
Obtaining one validly-signed webhook is trivial for anyone able to install the app on a store they control (own dev/test shop), since Shopify will deliver real signed webhooks for that store. Replaying the body with a modified shop header requires no cryptographic secret and no privileged access — only observation of one's own legitimate webhook traffic, which is within reach of an ordinary internet user/merchant.

### Recommendation
Include the shop domain (and other headers this gem treats as authoritative, e.g., `api-version`, `webhook-id`) inside the HMAC-signed material, or otherwise cryptographically bind them to the payload, mirroring what `AuthQuery#to_signable_string` already does for `shop`/`host` in the OAuth flow. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a shop the merchant is known to have installed the app for.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1}` with headers `x-shopify-hmac-sha256: <valid signature over body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the identical body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `HmacValidator.validate` succeeds (it only ever hashed the body) [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"` [5](#0-4) , causing the host app to apply the attacker's payload to the victim's tenant data.
