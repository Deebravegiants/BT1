This confirms the vulnerability: the webhook `shop-domain` header is never covered by the HMAC signature — the HMAC (`lib/shopify_api/utils/hmac_validator.rb`) is computed only over `to_signable_string`, which for `ShopifyAPI::Webhooks::Request` is the raw body (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop` is read straight from the `shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) with no cross-check against the signed content.

### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body via `Utils::HmacValidator.validate`, but the `shop` value that is forwarded to the app's handler as the tenant identity comes from the `shop-domain` HTTP header, which is completely outside the HMAC's coverage.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` does: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature only over `request.to_signable_string`: [2](#0-1) 

Meanwhile `request.shop`, which is passed unchanged into `WebhookMetadata` and handed to the app's handler as the authoritative tenant identifier, is read directly from the `shop-domain` header: [3](#0-2) 

This breaks the identity binding `shop_bound_by_hmac == shop_used_by_handler`: the HMAC only proves "this body byte-string was signed with the app's client secret at some point" — it says nothing about which shop that signature was issued for. Since the app's `client_secret` (and thus the HMAC key) is the same across every shop that installs the app, any merchant who legitimately installs the app on their own store receives genuinely-signed webhook bodies/HMACs for events on their store. That merchant (an "unprivileged" actor with respect to any other tenant) can capture one such valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` re-computes the signature only from the body and will still pass, because it never checks that the signature was produced for the claimed shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker who is a legitimate, unprivileged customer of the app (no `api_secret_key`, access token, or other credential needed) can make the app process attacker-controlled webhook data under an arbitrary victim shop's identity. Depending on how the host app's handler uses `data.shop` (e.g., to look up the shop's session/access token and perform an action, update per-shop state, or key a cache/database record), this can lead to cross-tenant data corruption, unauthorized actions performed against another merchant's store context, or downstream state confusion — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high for any app that trusts `data.shop` from the webhook handler as an implicit authentication signal, which the gem's own documentation encourages by describing `shop` as "The shop domain of the webhook" without ever noting that it is unauthenticated relative to the signature (see `docs/usage/webhooks.md` lines 12-17, 125-135). The gem itself provides no mechanism to cross-check `shop` against the signed payload or against the shop actually registered for that webhook subscription, so any host app that follows the documented `handle(data:)` pattern verbatim is exposed.

### Recommendation
Include the shop domain (and ideally webhook id/topic) as part of the signed material used for validation, or otherwise explicitly bind the `shop-domain` header to the verified signature before trusting it — e.g., verify that the resolved shop has an active, matching session/subscription for the given `webhook_id`/topic before invoking the handler, and document clearly that `shop` is unauthenticated header data that must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app: headers include `x-shopify-hmac-sha256: <valid HMAC over raw_body>` and `x-shopify-shop-domain: attacker.myshopify.com`; attacker captures `raw_body` and the HMAC value from their own traffic (e.g., via a proxy on their own webhook endpoint, or by using the app on their own infrastructure).
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate` succeeds because it only checks the raw body signature, per `lib/shopify_api/utils/hmac_validator.rb:13-22` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled order data>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
