### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are trusted from unauthenticated headers while only the raw body is covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, which verifies the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers are included in the signed material, yet these values are extracted directly from unauthenticated headers and handed to the merchant's handler as trusted identifiers.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field on the query object. [1](#0-0) 

For webhooks, `to_signable_string` is defined to be exactly the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` to authenticate the whole request, then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed to the app's handler — with no additional check that the shop identified in the header actually matches the tenant whose data is in the signed body: [3](#0-2) 

The identity binding that should hold is:
`shop header used by handler == shop that produced/owns the signed body`

But the code only enforces:
`HMAC(secret, raw_body) == received_hmac`

with the `shop-domain` header entirely outside the signed scope. Because a single app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, a webhook payload that is genuinely and validly signed for shop A's data can have its `x-shopify-shop-domain` header rewritten to shop B's domain, and the signature will still validate — since the signature never covered that header. Any principal who can get the app's endpoint to reprocess a webhook body (e.g., a merchant replaying their own legitimately-received webhook with a modified `shop-domain` header, or a party positioned to intercept/relay webhook HTTP requests) can cause the host application to attribute one shop's webhook body/content to a different shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: it is a cross-tenant identity-confusion vector where webhook data can be processed under an incorrect shop identity because the "shop" binding is asserted by an unauthenticated header rather than verified content. Host applications that use `WebhookMetadata#shop` to select which merchant's records to create/update/delete (a very common and endorsed pattern per this gem's own webhook docs) can be made to write or act on the wrong tenant's data. This matches the "Critical - cross-tenant access" impact category, since the field driving tenant selection is unauthenticated relative to the payload it is imputed to describe.

### Likelihood Explanation
Requires an actor with an existing, legitimate ability to receive genuinely signed webhooks (e.g., any merchant that has installed the app and thus receives real signed webhooks for their own shop) or the ability to intercept/replay traffic to the app's webhook endpoint. No possession of `api_secret_key` or a stolen access token is required — a signature computed by Shopify itself for one shop's payload remains valid after the `shop-domain` header is swapped, because the header was never part of the signed bytes. This is a design gap in this gem's own webhook-verification logic (`Request#to_signable_string` / `HmacValidator`), not merely host-application misuse, so it is in scope.

### Recommendation
Do not treat header-derived `shop`, `topic`, `api_version`, or `webhook_id` as authenticated merely because the raw body's HMAC is valid. At minimum:
- Document clearly (and ideally enforce in `Registry.process`) that `WebhookMetadata#shop` must be cross-checked by the host application against an independently known/authorized shop for that webhook subscription (e.g., matched against the shop that registered the specific `webhook_id`, or against session data), rather than trusted outright.
- Consider extending `to_signable_string` (or adding a secondary check) to bind the `shop-domain`/`webhook_id` headers to the signed payload where the delivery mechanism allows it, or provide an API that returns the topic/shop only after validating it against Shopify's registered webhook subscription for that ID.
- At minimum, surface a prominent warning in the webhook processing API/docs that `request.shop`/`request.topic`/etc. are not covered by the HMAC and must not be used as the sole tenant-routing key without additional verification.

### Proof of Concept
1. A merchant with shop domain `attacker.myshopify.com` installs the app and receives a legitimately signed webhook: body `B`, headers `{x-shopify-hmac-sha256: HMAC(secret, B), x-shopify-shop-domain: attacker.myshopify.com, x-shopify-topic: orders/create, ...}`. [4](#0-3) 
2. The merchant crafts a new request to the app's webhook endpoint reusing the exact same body `B` and HMAC header, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(secret, B)` — unchanged since only the body is signed — and the check passes. [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, and invokes the app's handler as if the (attacker's) payload legitimately belongs to `victim.myshopify.com`. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
