Based on my investigation, I've confirmed the vulnerability pattern. Here's the finding:

### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` fields are trusted without HMAC coverage, allowing cross-tenant webhook attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` directly from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC over the raw body (`to_signable_string` returns `@raw_body` alone). `Registry.process` then passes the header-derived `shop` straight to the host app's handler as the tenant identifier, without any binding between that value and the HMAC-covered content.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256` header [2](#0-1) . Critically, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from headers with no cryptographic binding to the signed body at all [3](#0-2) .

`Registry.process` validates only the HMAC-vs-body relationship, then forwards the unauthenticated `request.shop` value into `WebhookMetadata` given to the host app's handler as the tenant identity for the event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The gem's own documentation instructs apps to key business logic directly off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), confirming this is the documented, intended trust boundary for tenant attribution [5](#0-4) .

The equality this breaks: `shop_that_HMAC_authenticates == shop_the_handler_acts_on` is assumed by the gem's API but never enforced — the HMAC only authenticates `raw_body`, while `shop` (and `topic`/`webhook_id`/`api_version`) are read from headers outside that signed scope. Since all shops installing a given app share the same `api_secret_key`, any tenant that receives a legitimately-signed webhook for its own shop can replay that exact signed body with the `shop-domain` (and/or `topic`/`webhook-id`) header substituted for a different, victim shop. `HmacValidator.validate` still returns `true` because the signature only ever covered `raw_body`, which is unchanged.

### Impact Explanation
This is a cross-tenant boundary break for any multi-tenant Shopify app built with this gem's documented pattern: a merchant (unprivileged relative to other tenants of the same app) who has installed the app and can capture/replay one of their own legitimately-signed webhook deliveries can forge the `shop-domain` header to make the host app process that (attacker-controlled) body under a different shop's identity — e.g., triggering `customers/redact`/`shop/redact`/order/product update logic keyed by `data.shop` against a victim tenant, or polluting a victim's local data store keyed by the spoofed shop domain. This matches the "Critical - cross-tenant access" impact category, since the gem's `process`/`WebhookMetadata` API provides no mechanism to bind `shop` to the signed payload.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one validly-signed webhook body from Shopify (obtainable simply by being any merchant who installs the public app and receives their own webhooks, or by intercepting one in transit) to reuse against `HmacValidator.validate`. No knowledge of `api_secret_key` is needed since the signature check is purely `HMAC(raw_body)`. This is a realistic path for any self-serve/public Shopify app, which is the common deployment model for apps using this gem.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified content instead of trusting raw headers post-hoc:
- Include the `shop-domain` (and `topic`) header values in `to_signable_string` so they participate in the HMAC computation, or
- Require host apps to independently confirm `request.shop` against a known/authorized shop list (e.g., cross-check with an existing offline session for that shop) before acting on `WebhookMetadata`, and document this requirement clearly in `docs/usage/webhooks.md`, or
- Cross-validate `webhook_id`/`shop` pairs against Shopify's Admin API (`get_webhook_id`) before dispatching to the handler.

### Proof of Concept
1. App merchant A installs the app and receives a legitimate webhook (e.g. `orders/create`) with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-raw-body>`, and some `raw_body`.
2. Attacker (merchant A, or anyone who intercepts this HTTP request) resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (a different tenant of the same app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — unchanged — so validation passes [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the body originally destined for shop A, and acts on it as if it were a legitimate event for shop B [7](#0-6) .

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
