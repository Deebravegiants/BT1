**Analysis of the claim:**

The `view_filter.allows` check compares the exact same `module.address()`, `module.name().as_str()`, and `function.as_str()` values that are subsequently used to actually execute the view function via `AptosVM::execute_view_function` [1](#0-0) . There is no separate resolution, normalization, or aliasing step between the filter check and the execution — both operations consume the identical `ViewFunction` struct fields.

The `module` and `function` values are of type `Identifier` (Move's `Identifier`), which is parsed and validated once, either from the JSON `EntryFunctionId` conversion (`convert_view_function`) or BCS deserialization [2](#0-1) . Move's `Identifier` type enforces a strict character set at construction time and is inherently case-sensitive — there is no canonicalization, whitespace-trimming, or case-folding performed anywhere in this path. Because `"Foo"` and `"foo"` are distinct, non-equal `Identifier`/`String` values, they would refer to genuinely different (and likely non-existent) on-chain modules/functions rather than being treated as aliases of a blocked one. An attacker cannot use alternate casing to reach a *different, disallowed* function while having the filter believe it's checking an *allowed* one, because the filter's `ViewFunctionId` comparison in `ViewFilter::allows` (`config/src/config/api_config.rs`, lines 230-241) uses plain `==`/`PartialEq` on `AccountAddress` and `String`, which is exactly what the VM will later resolve against the module table using the same bytes [3](#0-2) .

There is also no whitespace-injection vector: Move identifiers cannot contain whitespace at all (enforced by the Move identifier grammar/validator at parse time), so any attempt to submit `" foo"` or `"foo "` as a module/function name would fail identifier parsing before ever reaching the filter check, rather than silently matching/bypassing it.

Since the exact same validated, canonical identifier strings are used both for the allow/deny decision and for the actual function dispatch, there is no divergence point that would let an attacker's request be evaluated against one identity while being executed against another. This does not cross a real custody boundary — it requires the filter's own comparison logic to diverge from the VM's actual resolution logic, and no such divergence exists in this code path.

impl ViewFilter {
    /// Returns true if the given function is allowed by the filter.
    pub fn allows(&self, address: &AccountAddress, module: &str, function: &str) -> bool {
        match self {
            ViewFilter::Allowlist(ids) => ids.iter().any(|id| {
                &id.address == address && id.module == module && id.function_name == function
            }),
            ViewFilter::Blocklist(ids) => !ids.iter().any(|id| {
                &id.address == address && id.module == module && id.function_name == function
            }),
        }
    }
