### Title
Cross-chain transfer timeout refunds can be permanently blocked while the token is paused - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.onPostRequestTimeout` — the function that re-mints a user's burned tokens back to them after a cross-chain transfer times out — is gated by `whenNotPaused`. Since `pause()`/`unpause()` are owner-only, a paused state (whether from an incident response, admin action, or governance delay) blocks the only recovery path for tokens that are already burned and in flight, exactly analogous to the reported Olympus issue where withdrawal/claim functions guarded by `onlyWhileActive` froze already-deposited user assets when the vault was deactivated.

### Finding Description
`send()` burns the caller's tokens immediately and dispatches an ISMP POST request to the destination chain [1](#0-0) . If that request never resolves (destination unsupported, relayer unavailability, congestion, etc.), the ISMP host eventually delivers a timeout to `onPostRequestTimeout`, which is the sole mechanism to re-mint the burned tokens back to the sender [2](#0-1) . This function carries the `whenNotPaused` modifier in addition to `onlyHost` [3](#0-2) . `pause()`/`unpause()` are restricted to the contract owner [4](#0-3) .

Once a user's tokens are burned by `send()`, they exist only as an in-flight cross-chain message; the user has no other means of recovering them except via the timeout callback. If the owner pauses the contract (for any legitimate or precautionary reason) while such a message is outstanding, the host's `onPostRequestTimeout` delivery reverts, and — unlike a normal function call the user could simply retry — ISMP timeout delivery is a one-shot event triggered by the host/relayer; if it reverts, the funds are left stranded with no user-callable retry path until the owner unpauses. The identical pattern is present in the sibling contracts `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol` [5](#0-4) .

### Impact Explanation
This can result in a permanent (until owner action, which the affected user cannot compel) freezing of funds that have already left the user's control (burned) and are not yet restored. This mirrors the accepted bug class of the source report: guarding the exit/recovery path with an availability-style modifier turns a temporary operational pause into a potential permanent freeze for funds already committed to the protocol. Depending on the underlying delivery/retry semantics of the host for timeouts, this could require governance/manual intervention to unpause before recovery is possible, which is a Medium-severity freezing-of-funds condition.

### Likelihood Explanation
Likelihood is moderate: it requires the owner to pause the contract while at least one cross-chain transfer is in flight and subsequently times out. Pausing is a normal operational lever (e.g., in response to a suspected exploit elsewhere in the token or bridge), making the overlap with in-flight/timing-out transfers plausible, especially for tokens with meaningful cross-chain volume.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout` (and its equivalents in `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`), or otherwise ensure refund/recovery paths for already-burned/escrowed funds remain callable regardless of pause state, so that pausing only blocks new transfers (`send`) and new mints (`onAccept`) rather than the return of funds already removed from user custody.

### Proof of Concept
1. User calls `send()` with `amount = X`; tokens are burned immediately [6](#0-5) .
2. Owner calls `pause()` for any reason while the request is still pending [7](#0-6) .
3. The destination never delivers (or delivery fails), and the ISMP host eventually submits a timeout proof, invoking `onPostRequestTimeout` on the source-chain token contract.
4. The call reverts due to `whenNotPaused` [3](#0-2) , so the user's `X` tokens are never re-minted; the tokens remain unrecoverable until the owner unpauses (an action the user cannot trigger), constituting a freeze of the user's funds already removed from circulation by the burn.
