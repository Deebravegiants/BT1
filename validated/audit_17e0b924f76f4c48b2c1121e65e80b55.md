## Analog Found

### Title
Excess native `msg.value` sent to `EvmHost.dispatch`/`fundRequest` is permanently lost — Uniswap refund goes to `EvmHost`, not the depositing caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native token payment for relayer fees and internally swap the entire `msg.value` for an *exact* amount of fee tokens via Uniswap V2's `swapETHForExactTokens`. Any unspent native ETH from that swap is refunded by the router to `msg.sender` of the swap call — but since `EvmHost` itself is the caller of the router (not the original transaction sender), the refund lands in `EvmHost`'s own balance instead of being returned to the depositing user. This mirrors the Sherlock report's root cause: Ether sent by a user is not fully and correctly credited/returned based on the actual value transferred, resulting in silently trapped user funds.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

the same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(exactFeeAmount, path, address(this), ...)` is called with the *entire* `msg.value` forwarded, but only `exactFeeAmount` (the fee token output) is actually required. Uniswap V2's router computes the exact ETH input needed and refunds any leftover ETH to `msg.sender` of that call — which is `EvmHost` itself, since `EvmHost` is the direct caller of the router. The refunded dust is never routed back to `_msgSender()` (the original depositing account/app), nor is it credited anywhere in `_requestCommitments`/`FeeMetadata`. It simply becomes part of `EvmHost`'s native balance, unreachable by the depositor.

This is not a purely negligible dust issue: any caller who does not send the *exact* wei amount required to purchase `post.fee` fee-tokens (which is normal, since callers estimate via off-chain quoting, slippage, or send round-number `msg.value`) will have the surplus silently absorbed by `EvmHost`. There is no `receive`/refund path, and the only recovery mechanism is the privileged `IHostManager.withdraw` (governance-only), which the affected end user cannot invoke. This is directly analogous to `LMPVaultRouterBase`'s failure to reconcile actual Ether sent against the amount used, leaving user funds trapped in the contract instead of returned to the depositor.

This is reachable by every unprivileged path that dispatches a POST/GET request or funds an existing request with native currency, including `HyperFungibleToken.send()`, `WrappedHyperFungibleToken.send()`/`WrappedHyperFungibleTokenUpgradeable.send()`, and any third-party `IApp` calling `IDispatcher(host()).dispatch{value: msg.value}(...)` as documented: [4](#0-3) 

### Impact Explanation
Users overpaying (even slightly) native ETH for dispatch fees permanently lose the excess — it is swept into `EvmHost`'s balance and is not recoverable by the user; only a privileged `HostManager` withdrawal can move it, and even then it goes to a beneficiary chosen by governance, not back to the original depositor. Across many dispatches/apps built on top of `EvmHost` (token bridges, intents, HFT transfers) this results in continuous unrecoverable loss of user funds, which qualifies as a fund-freezing/loss defect.

### Likelihood Explanation
High likelihood: it is virtually impossible for a caller to send `msg.value` that exactly matches the wei price required for `swapETHForExactTokens` at execution time (price can move between quote and execution, and callers commonly round up `msg.value` for safety margin). Every such call results in silent fund loss with no user-facing revert or refund.

### Recommendation
After calling `swapETHForExactTokens`, compute the actual ETH spent (`amounts[0]` returned by the router) and refund `msg.value - amounts[0]` back to `_msgSender()` via a low-level call, mirroring the refund logic already implemented in `UniV3UniswapV2Wrapper.swapETHForExactTokens`: [5](#0-4) 

### Proof of Concept
1. Alice calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.9 ether` worth of ETH to purchase via Uniswap at execution time.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), ...)` spends `~0.9 ether`, and Uniswap V2 router refunds `~0.1 ether` to `msg.sender`, which is `EvmHost`, not Alice.
3. Alice's request is dispatched successfully but she has permanently lost `~0.1 ether` — it is now indistinguishable from `EvmHost`'s own balance and can only be moved by governance via `HostManager.withdraw`, never back to Alice.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
