### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, but the signable string used for HMAC verification is only the raw body — the `shop` domain (and `topic`/`webhook-id`/`api-version`) headers are never included in the signed material. This breaks the identity binding: `hmac == HMAC(secret, body)` while the handler acts on `shop == header("x-shopify-shop-domain")`, a value the HMAC never covers.

### Finding Description
`Registry.process` validates a webhook purely with: [1](#0-0) 

and `HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and the `shop`, `topic`, `webhook_id`, and `api_version` fields are all pulled from raw, unauthenticated HTTP headers, entirely outside of what is HMAC-signed: [3](#0-2) 

The identity binding the code depends on is: **`hmac` proves `body`**, but the handler is invoked with `shop = request.shop` derived from a header that carries no cryptographic binding to that same `hmac`:

```
before: hmac signs {body}                shop taken from unauthenticated header
after:  handler.handle(shop: <attacker-controlled header>, body: <hmac-verified body>)
```

Because the shop domain is never part of the signed payload, any HTTP request whose body+HMAC pair was legitimately produced by Shopify for one shop (e.g., a shop the attacker controls and has installed the app on) can be replayed to the same webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to point at an arbitrary victim shop. `HmacValidator.validate` will still pass because the signature only ever validated the body bytes, not the shop identity, and the app-side handler will process the event as if it originated from the victim's tenant: [4](#0-3) 

### Impact Explanation
This satisfies the Critical bar for cross-tenant access: an unprivileged internet user who legitimately receives even a single valid webhook (e.g., by installing the app on their own store) can forge the shop-domain header on replay and have the host application's webhook handler execute business logic (data updates, GDPR/compliance actions, order/customer processing, etc.) attributed to a different, arbitrary merchant/tenant, without ever needing that merchant's credentials. The HMAC gives false assurance that the whole request — including which shop it's "from" — is authentic, when in fact only the byte content of the body is authenticated.

### Likelihood Explanation
Likelihood is high for any app that (a) can obtain at least one genuine webhook (trivial — install the app on any store, including the attacker's own), and (b) trusts `WebhookMetadata#shop` from `Registry.process` for tenant-scoping decisions, which is the documented/intended use of this field per `lib/shopify_api/webhooks/registry.rb` and `lib/shopify_api/webhooks/request.rb`. No secret, access token, or privileged access is required — only the ability to send an HTTP POST with attacker-controlled headers and a previously-observed valid raw body/HMAC pair.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-verified signable string, or independently bind/verify the shop header against a value derived from the signed body/session (e.g., by requiring the body itself to carry an authenticated shop identifier that is cross-checked), so `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot be satisfied while the `shop` field is swapped.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — this pair is valid per `HmacValidator.validate`.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because only `@raw_body` is signed (`lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, and any tenant-scoped side effects (e.g., data writes keyed by shop) are executed as if the event genuinely originated from the victim shop.

          received_signature = verifiable_query.hmac
