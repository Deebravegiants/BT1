### Title

Unvalidated route-selected pool can execute arbitrary authorized token transfers - (File: `contracts/swap-aggregator/src/execute/mod.rs`)

### Summary

`execute_strategy` accepts a caller-controlled `assets` registry and packed route, then treats every `idx_a` address as a trusted venue pool without checking whether that address belongs to the venue named by the opcode. An attacker can therefore encode a malicious contract as a Phoenix, Soroswap, Sushi, Aquarius, or Comet pool and have the router invoke it. Because venue code executes beneath the sender-authorized `execute_strategy` invocation, a malicious pool can request an additional `token.transfer(sender, attacker, amount)` that appears as a child of the sender’s authorization tree. If the resulting authorization tree is signed, the rogue transfer succeeds alongside a superficially valid swap.

### Finding Description

The route payload contains a freely supplied `assets` registry, and each swap instruction resolves `idx_a` directly into `SwapHop.pool` [1](#0-0) . `Program::decode` validates structural fields, indices, opcodes, chaining, and weights, but performs no venue-address authentication or allowlist check [2](#0-1) . Dispatch then selects only the opcode’s adapter and calls the supplied pool address [3](#0-2) .

For example, the Phoenix adapter invokes `pool.swap(...)` on the payload-selected address [4](#0-3) . The sender authorization is established once at the router entry point [5](#0-4) , while the expected input pull occurs later [6](#0-5) . A malicious pool can make an unrelated sender-funded token transfer during its callback; Soroban records that transfer as a child of the caller’s authorized invocation and executes it when the caller signs that tree [7](#0-6) [8](#0-7) .

The final balance checks do not constrain this behavior: they only require a positive measured `token_out` increase and the expected `token_in` decrease for the routed amount [9](#0-8) . A funded rogue pool can satisfy those checks while also performing the unrelated authorized transfer.

### Impact Explanation

This enables theft of user funds beyond the declared swap input. The attacker can select any token held by the victim and encode the malicious pool to transfer that token to an attacker address during the route call. The route’s `token_in`, `token_out`, `total_min_out`, measured output checks, and final lending risk checks do not bound an unrelated sender-token transfer. In the composed controller path, the analogous risk applies to contract-controlled balances and authorizations associated with the `sender`; in direct router use, it applies directly to the signer’s wallet.

### Likelihood Explanation

Exploitation requires the victim or its client to sign an authorization tree containing the rogue child transfer. That is plausible when users receive opaque `routeXdr` or prebuilt transaction envelopes and wallets do not clearly disclose nested Soroban authorization children. No privileged protocol role, leaked key, router compromise, oracle manipulation, or token nonconformity is required; the pool address is caller-controlled by design and is invoked without validation.

### Recommendation

Bind route hops to authenticated venues rather than accepting arbitrary `assets[idx_a]` pool addresses. Maintain an on-chain registry of approved pool addresses for each `SwapVenue`, or store venue-specific immutable deployment/pool identifiers and reject any route whose pool is not registered. Authentication should happen before dispatch, not merely through measured balance deltas. Until such validation exists, clients must decode the complete signed authorization tree and reject any child invocation other than the exact expected input transfer, but client checks alone do not remove the contract-level unsafe dispatch.

### Proof of Concept

1. Deploy `RoguePhoenixPool`, funded with enough `token_out` to satisfy the route minimum. Store `(victim, victim_token, attacker, steal_amount)` in the contract.
2. Construct a one-hop `StrategyPayload`:
   - `assets = [token_in, rogue_pool, token_out]`
   - `amounts = [min_out]`
   - `ops` header: version `1`, `token_in = 0`, `token_out = 2`, `min_out = 0`, `referral_id = 0`, `op_count = 1`, `weight_count = 0`
   - instruction: Phoenix opcode `2`, `Mode::All = 0`, `idx_a = 1`, `idx_b = 0`, `idx_c = 2`
3. Have the victim call `Router::execute_strategy(victim, total_in, swap_xdr)` or sign a generated envelope for that call.
4. The router authenticates `victim` and pulls `token_in`, then the Phoenix adapter invokes `rogue_pool.swap(...)` because the pool address came directly from `assets`.
5. Inside `swap`, the rogue contract:
   - completes the expected router input pull or receives it through the venue flow;
   - calls `victim_token.transfer(victim, attacker, steal_amount)`;
   - transfers at least `min_out` of `token_out` to the router.
6. Simulation records both the normal `token_in` pull and the unrelated `victim_token` transfer as children of the victim’s authorization. If the victim signs that tree, the transaction satisfies the router’s measured spend/output checks and the unrelated token theft persists.

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
                // Liquidity legs spend the full vault balance, so only `Mode::All` is valid.
                Opcode::Burn | Opcode::Mint => {
                    if mode != Mode::All {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_c >= amounts_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                }
            }
