Based on my investigation, I found a race-condition analog in the cross-chain cancellation path of `ExtrinsicIntents.sol`, structurally similar to the kernel bug: an async confirmation (`onGetResponse`, analogous to `DEREGISTER_DONE`/G2H response) can act on stale state because a competing state-changing path (a fill landing on the destination, or a duplicate cancel) is not fenced against the in-flight request the way it should be.

### Title
Cross-chain order cancellation race allows escrow refund/redeem to be finalized against stale `_filled` state - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromSource` dispatches a Hyperbridge GET request to check the destination chain's `_filled[commitment]` slot at a caller-supplied height [1](#0-0) , and only much later, when `onGetResponse` fires, does it act on the read value to refund escrow via `_withdraw` [2](#0-1) . Nothing marks the order as "cancel pending" on the source chain when the GET is dispatched — `_orders`/`_filled` on the source chain are untouched until the async response lands, exactly the same "state not staged before initiating an async operation, decided only when the response returns" pattern behind CVE-2024-56552.

### Finding Description
In the kernel bug, `suspend_pending` was set, a `disable_scheduling` request was sent, and by the time its G2H response returned, `suspend_pending` had already been cleared by an unrelated close, causing the response handler to reach an unintended branch (a spurious deregister) because the intervening state transition was not accounted for.

The analogous pattern here: `_cancelFromSource` only validates `_orders[commitment][token] != 0` at dispatch time and does not set any local "cancellation in flight" flag or lock on the source chain [3](#0-2) . The correctness of the eventual refund depends entirely on the destination-chain `_filled` slot proof being read at `options.height`, and the response is trusted unconditionally by `onGetResponse` once it arrives — there is no re-check that the order is still in the same escrow state on the source chain at the time the response is processed, nor any guard preventing a second, concurrent `_cancelFromSource` call for the same commitment before the first GET response lands. Two GET requests can be dispatched back-to-back for the same commitment (nothing prevents it — `_orders[commitment][token]` is only read, never zeroed, until `_withdraw` runs), and both can return "unfilled" if raced before either destination-side fill/finalization is observed at the respective proof heights, or before the first response's `_withdraw` finalizes. The first `onGetResponse` call finalizes via `_withdraw(body, true, true)`, marking `_filled[body.commitment] = beneficiary` and decrementing `_orders[commitment][token]` [4](#0-3) . A second in-flight `onGetResponse` for the same commitment, if it arrived before the first, or if `_orders[commitment][token]` still shows a nonzero balance because only a subset of tokens were decremented, is not fully guarded against re-entry through repeated dispatch of `_cancelFromSource`, since nothing marks a "cancellation already dispatched" flag analogous to `suspend_pending` that would prevent duplicate/racing async operations from being started to begin with.

### Impact Explanation
If two `_cancelFromSource` calls are dispatched concurrently for the same commitment (e.g., by two watchers/relayers acting on behalf of the user, or the user retrying because the first appeared stuck), and both GET requests resolve to an "unfilled" proof (plausible since neither dispatch marks the order as cancellation-pending), `onGetResponse` could execute `_withdraw` twice for overlapping token sets before `_orders[commitment][token]` is fully zeroed for every token, each decrementing token balances that were already reduced by the first call for tokens not yet exhausted — resulting in an under-collateralized escrow release (loss of funds) parallel to the kernel bug's "queue gets torn down twice" defect. This is theft/permanent loss of escrowed funds if double-processing is achievable.

### Likelihood Explanation
Requires two concurrent GET dispatches for the same order commitment to be relayed and resolved before the first's `_withdraw` fully finalizes — plausible for a permissionless flow with automated relayers/solvers racing to complete a stale/expired order for fee capture, but requires timing alignment across two Hyperbridge GET round-trips. I could not fully confirm on the given code whether Hyperbridge's underlying GET/response pipeline (pallet-ismp) itself deduplicates identical concurrent GET requests for the same commitment — that check lives outside `ExtrinsicIntents.sol`/`IntentsBase.sol` and I was unable to verify it within the available iterations.

### Recommendation
Mark `_filled[commitment]` (or a dedicated "cancellation pending" flag) at the time `_cancelFromSource` dispatches its GET request, and have `onGetResponse` re-validate that no other cancellation/fill has finalized the order in the interim before calling `_withdraw`, mirroring the kernel fix's approach of tightening the ordering between issuing an async request and consuming its response so a competing state transition can't be missed.

### Proof of Concept
I was unable to construct a concrete calldata-level PoC within the available tool budget; this assessment is based on static analysis of `_cancelFromSource`, `onGetResponse`, and `_withdraw`, and the double-dispatch/double-finalize path is a code-flow inference, not a runtime-verified exploit. A background engineering session with test-harness/foundry access would be needed to confirm whether the ismp-GET machinery blocks duplicate concurrent GET dispatches for the same commitment before treating this as confirmed rather than a plausible analog.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

        _checkRelayer(incoming.relayer);
        if (incoming.response.values[0].value.length != 0) revert Filled();

        WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
        _withdraw(body, true, true);
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
