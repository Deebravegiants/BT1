## Analysis

The reported bug class — minting/crediting based on the *nominal* transfer amount instead of the *actual* post-fee balance received — has a direct analog in the `raydium-amm--013` `Deposit` instruction handler.

### Title
Fee-on-transfer tokens cause under-collateralized LP minting in `process_deposit` - (File: `program/src/processor.rs`)

### Summary
`process_deposit` computes `deduct_coin_amount`/`deduct_pc_amount` from the pool's current on-chain vault balances and the user-specified `max_coin_amount`/`max_pc_amount`, then mints LP tokens proportional to these *nominal* deduct amounts before actually moving the tokens into the vaults. If either `coin_vault_mint` or `pc_vault_mint` is a fee-on-transfer ("reflection") SPL token, the vault will receive strictly less than `deduct_coin_amount`/`deduct_pc_amount`, yet the LP supply is inflated as if the full nominal amount arrived.

### Finding Description
In `process_deposit`, `total_coin_without_take_pnl` / `total_pc_without_take_pnl` are read live from vault balances via `Self::unpack_token_account` before the transfer: [1](#0-0) 

The mint amount is derived purely from `deduct_coin_amount`/`deduct_pc_amount` against the pre-transfer pool totals: [2](#0-1) 

The actual token movement is then performed with a plain SPL `transfer` CPI, with no verification that the vault's balance increased by the full amount transferred: [3](#0-2) 

`Invokers::token_transfer` is a thin wrapper around `spl_token::instruction::transfer` with no pre/post balance diffing: [4](#0-3) 

If `coin_vault_mint`/`pc_vault_mint` charges a transfer fee, `amm_coin_vault`/`amm_pc_vault` receive `deduct_amount - fee`, but `mint_lp_amount` was computed and minted as though the full `deduct_amount` had arrived. This mirrors the referenced Allo.sol `_fundPool` bug exactly: crediting a *pool accounting unit* (there, `poolAmount`; here, LP supply/backing ratio) using the pre-fee transfer amount rather than the observed balance delta.

### Impact Explanation
Each deposit with a fee-on-transfer coin/pc mint mints LP tokens that are not fully backed by the tokens actually held in the vault. This permanently dilutes the claim of all existing LP holders on redemption (`process_withdraw` and swap math both operate on the actual vault balances, so the shortfall is baked into the invariant permanently — it isn't self-correcting, since the mismatch shows up as a lower per-LP-token backing forever). Repeated deposits let an attacker/depositor accumulate LP tokens disproportionate to what they contributed, effectively extracting value from other LPs at withdrawal time — an insolvent-pool-accounting condition affecting LP funds.

### Likelihood Explanation
Reachable by any unprivileged user issuing a single `Deposit` instruction (opcode 3) against a pool whose `coin_mint`/`pc_mint` was created (via `Initialize2`, also open to any account since the pool creator chooses the mints) using a fee-on-transfer SPL token extension/mint. No privileged signer or special build is required — it is a normal deposit flow with an adversarially-chosen mint. This matches medium severity as fee-on-transfer tokens are not the common case among SPL tokens, but nothing in the program prevents such mints, and the transfer-amount-vs-balance-delta check is entirely absent.

### Recommendation
In `process_deposit` (and analogously in `process_initialize2`/`process_withdraw` where nominal amounts are trusted), capture the vault's token balance immediately before and after each `Invokers::token_transfer` call, and use the observed delta (not the nominal `deduct_coin_amount`/`deduct_pc_amount`) to compute `mint_lp_amount` and to update `target_orders.calc_pnl_x/y`.

### Proof of Concept
1. Create a pool via `Initialize2` using a fee-on-transfer SPL token (e.g., Token-2022 with a `TransferFeeConfig` extension, or a custom fee-charging mint) as `coin_mint`.
2. Call `Deposit` with `base_side = 0`, `max_coin_amount = N`. `process_deposit` computes `deduct_coin_amount = N` and `mint_lp_amount` from `N` against the pre-transfer pool totals: [5](#0-4) 
3. `Invokers::token_transfer` moves `N` nominal tokens, but the vault's actual balance increases by `N - fee` due to the fee-on-transfer mechanism.
4. `amm.lp_amount` is incremented by the full `mint_lp_amount`, computed as if `N` (not `N - fee`) had been deposited: [6](#0-5) 
5. Subsequent `Withdraw` calls redeem against the now-diluted, under-collateralized pool, letting the depositor extract more value per LP token than they actually contributed, at the expense of pre-existing LPs.
