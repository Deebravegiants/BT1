### Title
`BandwidthManager.purchase` reverts (DoS) for fee tokens with more than 18 decimals due to unchecked `18 - dec` underflow - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`purchase()` computes `uint256 scale = 10 ** (18 - dec);` where `dec` is the host's `feeToken()` decimals, read via `IERC20Metadata(feeToken).decimals()`. This is the same underflow pattern as the reported `UniswapV2Oracle.getPrice` bug (`36 - token0.decimals() - token1.decimals()`): if the configured fee token has more than 18 decimals, `18 - dec` underflows a `uint8`/`uint256` subtraction and reverts in Solidity 0.8.x's checked-arithmetic mode.

### Finding Description
`purchase()` scales an 18-decimal tier price down to the fee token's native decimals: [1](#0-0) 

`dec` comes directly from an external, admin-configurable `feeToken()` (`IDispatcher(_host).feeToken()`), and there is no upper bound enforced on its decimals anywhere in this contract. If `feeToken()` is ever set (or migrated via the host's own configuration) to a token whose `decimals()` returns a value greater than 18 (e.g., 24, as with real-world tokens like YAM-V2), the expression `18 - dec` underflows, and the subtraction reverts unconditionally for every call to `purchase()`.

### Impact Explanation
This bricks the entire bandwidth-purchasing entry point of `BandwidthManager` for any fee token configured with >18 decimals — no user can call `purchase()` to top up bandwidth for any app on any chain, permanently freezing this ISMP dispatch path until the fee token is reconfigured back to ≤18 decimals. This matches the "route unable to deliver messages" / permanent freezing-of-funds-adjacent impact class (bandwidth purchases fund message delivery credits), reachable from a single unprivileged `purchase()` transaction attempt.

### Likelihood Explanation
Likelihood depends on whether the host's fee token is ever set to a >18-decimal ERC20. This requires either an unusual token choice at deployment or a fee-token migration governed by the pallet-side `Withdraw`/host configuration; the contract itself performs no validation preventing such a token from being selected. Given decimals values >18 are rare but real (documented precedent in the referenced report), and the contract has no guard, this is a plausible medium-severity configuration-triggered DoS rather than a routinely-hit bug.

### Recommendation
Guard the subtraction, e.g.:
```solidity
uint8 dec = IERC20Metadata(feeToken).decimals();
uint256 amount;
if (dec <= 18) {
    uint256 scale = 10 ** (18 - dec);
    if (total18d % scale != 0) revert PriceNotRepresentable();
    amount = total18d / scale;
} else {
    uint256 scale = 10 ** (dec - 18);
    amount = total18d * scale;
}
```
This mirrors the recommended fix in the referenced report (divide vs. multiply depending on which side has more decimals), avoiding the underflow entirely.

### Proof of Concept
1. Configure (or have the host report) `feeToken()` as an ERC20 with `decimals() == 24` (e.g., a token modeled on YAM-V2).
2. Call `BandwidthManager.purchase(app, tier, months, chain)` with a valid, configured `tier`.
3. Execution reaches `uint256 scale = 10 ** (18 - dec);` with `dec = 24`; `18 - 24` underflows a `uint256` computation and reverts under Solidity ^0.8.17's checked arithmetic, aborting the transaction before any fee is pulled — `purchase()` is permanently unusable for this fee token configuration.     function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
