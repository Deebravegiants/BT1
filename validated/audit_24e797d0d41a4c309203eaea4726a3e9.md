### Title
Duplicate `address(0)` entries in `circomData.erc20TokenAddresses` allow minting 2x shielded ETH value from a single `msg.value` deposit - ([File: contracts/Hinkal.sol])

### Summary
The balance-reconciliation loop in `Hinkal.transact` (not `OwnerHinkal.sol`, which contains no transact logic — the code in question lives in `contracts/Hinkal.sol`) computes `balanceDif` per array index using a full re-query of `address(this).balance` at both `oldBalances`/`newBalances` snapshot points, and unconditionally re-adds the *entire* `msg.value` for every row whose token address is `address(0)`. There is no check enforcing uniqueness of `erc20TokenAddresses`, so an attacker can list `address(0)` twice and have the same `msg.value` validated as backing two independent `amountChanges` entries.

### Finding Description
The equality the contract intends to enforce is: `sum(amountChanges over the address(0) rows) == real ETH received by the contract (msg.value)`. This is broken when `address(0)` appears twice.

Trace:
- `oldBalances = getBalancesForArray(circomData.erc20TokenAddresses)` [1](#0-0)  queries `address(this).balance` once per array slot — for two `address(0)` entries, `oldBalances[0] == oldBalances[1]`.
- Same for `newBalances` after `_internalTransact`/`_externalTransact` runs [2](#0-1) .
- For the deposit path, `_internalTransact` calls `transferERC20TokenFromOrCheckETH(address(0), sender, address(this), amountChanges[i])` for each row with `deltaAmountChange > 0` [3](#0-2) . In `Transferer.sol`, this only asserts `msg.value == _value` and, since `_to == address(this)`, performs no actual transfer [4](#0-3) . `msg.value` is a fixed scalar for the whole transaction, so this check is trivially satisfied identically for both duplicate rows — no ETH balance actually changes and no ETH is "spent" tracking-wise.
- Back in the reconciliation loop, for each `address(0)` row: `balanceDif = newBalances[i] + msg.value - oldBalances[i]`. Since `newBalances[i] == oldBalances[i]` (no real ETH moved), `balanceDif == msg.value == V` for **both** rows independently [5](#0-4) .
- The final equality check `balanceDif == amountChanges[i] + utxoAmount` is then evaluated per row independently [6](#0-5) . If the attacker sets `amountChanges = [V, V]` for the two duplicate `address(0)` rows, both checks pass (`V == V` twice), authorizing two separate output UTXOs of value `V` each — total `2V` of shielded value created — even though only `V` of real ETH was ever received by the contract.

Root cause: (1) no uniqueness constraint on `circomData.erc20TokenAddresses`, and (2) the `address(0)` branch treats `msg.value` as an independently-available credit per loop iteration rather than a single value that can only back one row's deposit accounting.

None of the existing guards prevent this: `performHinkalChecks`/`dimensionsCheck` validate array-length consistency across `Dimensions`, not token-address uniqueness; `verifyProof` only enforces the circuit's local per-row balance equation (`inTotal + amountChanges === outTotal`), which has no notion that two rows share the same real-world token/ETH backing; `rootHashExists` and nullifier insertion are orthogonal to this accounting bug.

### Impact Explanation
An unprivileged attacker can mint shielded ETH value unbacked by real funds: sending `V` real ETH via `msg.value`, they can create shielded UTXOs totalling `2V` (or more, with more duplicate rows), directly causing protocol insolvency and enabling later withdrawal of value that was never deposited. This matches the Critical category: "minting shielded value without backing." It is repeatable per transaction, limited only by the attacker's ability to craft a valid proof and a correctly-shaped `Dimensions`/`erc20TokenAddresses` array with duplicate `address(0)` entries.

### Likelihood Explanation
The attacker needs only: (1) the ability to call `transact` with `msg.value = V`, (2) craft `circomData.erc20TokenAddresses` with two `address(0)` entries, (3) generate a valid proof for a circuit instance whose two rows each independently satisfy `inTotal + amountChanges === outTotal` locally (trivial since each row is a fresh deposit with no input UTXOs, `amountChanges[i] = V`, one output UTXO of `V`), and (4) set `onChainCreation[i] = false` for both rows. All of this is within the stated attacker capabilities (their own funds, own proofs, own array crafting), no privileged role required. Cost is exactly `V` ETH plus gas; gain is `2V` (or more) of withdrawable shielded value.

### Recommendation
- Enforce uniqueness of `circomData.erc20TokenAddresses` in `performHinkalChecks`/`dimensionsCheck`, rejecting any transaction where a token address (including `address(0)`) appears more than once.
- Alternatively/additionally, restructure the balance-diff accounting to consume `msg.value` exactly once globally (e.g., subtract it from the contract's real balance snapshot a single time before entering the per-token loop, or assert that only one row may correspond to `address(0)`), rather than re-adding the full `msg.value` for every native-ETH-tagged row.

### Proof of Concept
Hardhat test:
1. Deploy Hinkal system, mint no ERC20s needed (native ETH path only).
2. Build `circomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [1e18, 1e18]`, `onChainCreation = [false, false]`, `slippageValues = [1e18, 1e18]`, empty input UTXOs/nullifiers, two fresh output commitments (one per row) each carrying `1e18`.
3. Generate a valid proof locally for two independent rows, each satisfying `inTotal(0) + amountChanges(1e18) == outTotal(1e18)`.
4. Call `hinkal.transact(a, b, c, dimensions, circomData, { value: ethers.parseEther("1") })`.
5. Assert: `tx` succeeds; `await ethers.provider.getBalance(hinkal.target)` increased by exactly `1e18` (only `V` received); but two output commitments each encoding `1e18` were inserted (`insertCommitments` emitted two leaves), i.e. total claimed shielded value == `2e18` while actual contract ETH increase == `1e18` — proving the equality `sum(amountChanges) == msg.value` is broken (`2V != V`).
