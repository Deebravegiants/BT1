### Title
Webhook shop identity spoofing via HMAC coverage gap in `Request#to_signable_string` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) field is read from an unauthenticated HTTP header and passed downstream to the webhook handler untouched. Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app, any shop that installs the app can capture a validly-signed `(body, hmac)` pair for a webhook it legitimately triggers on itself, then replay that exact body/hmac to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still report success because it never checks the shop field, yet `Registry.process` forwards the attacker-chosen shop value straight to the handler as the trusted tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read from a header that is never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only recompute and compare the HMAC over `to_signable_string` (i.e., the body), never over `shop`: [3](#0-2) 

`Registry.process` gates only on this HMAC check and then unconditionally forwards `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`HMAC-verified bytes (raw_body) == identity bytes acted upon (shop header used as WebhookMetadata#shop)`

Since the app's `api_secret_key` is a single shared per-app secret (not per-shop), any shop that has installed the app can obtain a genuinely-signed `(body, hmac)` pair by triggering a real webhook event on its own store, and then replay that pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. The signature still validates because the header is outside the signed payload, and `WebhookMetadata#shop` presented to the handler will contain the attacker-supplied value rather than the shop whose secret actually produced the HMAC.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is merely an installed (unprivileged, from the victim's perspective) merchant of the app can cause the library to hand the app's business logic a webhook payload authenticated as coming from a shop the attacker does not control. Any host application that uses `WebhookMetadata#shop` (as documented and demonstrated by this gem's own `Registry.process` flow) to select which tenant's records to create/update/delete is exposed to cross-tenant data injection or corruption — matching the "cross-tenant access" Critical impact category, since no access token, session, or `api_secret_key` for the victim is required, only the app's public webhook endpoint and the attacker's own legitimate installation.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: obtaining a valid signed webhook body only requires performing an ordinary, permitted action (e.g., creating an order) on the attacker's own store, which is available to any merchant/developer who installs the app. Replaying the captured body with a substituted `shop` header requires no cryptographic secret knowledge, only basic HTTP tooling.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically/authoritatively re-derive the shop from data covered by the signature (e.g., include the shop domain in the signed payload) instead of trusting `x-shopify-shop-domain`/`shopify-shop-domain` header contents as-is once HMAC validation only covers the body. At minimum, the library should document/enforce that `WebhookMetadata#shop` must be cross-checked against the app's own stored/expected shop-secret mapping before being used as a tenant key, and consider incorporating the shop header into `to_signable_string` for verification when feasible.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook-eligible action (e.g., `orders/create`), causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` (correctly computed as `HMAC_SHA256(api_secret_key, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker intercepts this legitimate delivery (their own webhook endpoint traffic, fully within their control) and re-sends the same body `B` and header `H` to the app's webhook endpoint, but replaces the shop header with `x-shopify-shop-domain: victim.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers))`.
4. `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(api_secret_key, B)`, which still equals `H`, so validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to act on attacker-controlled data under the victim's tenant identity.
