## Title
Cross-chain replay of `SubstrateCalldata` signatures leads to unauthorized arbitrary `RuntimeCall` dispatch — (`modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler lets a bridged token transfer carry an optional signed payload that authorizes dispatching an arbitrary `T::RuntimeCall` as the beneficiary's own account. The signature only covers `(nonce, runtime_call_bytes)` — it has no chain/domain separator (no genesis hash, `StateMachine` id, contract address, or asset id). Because the same pallet code is deployed unmodified across many parachains/state machines connected to Hyperbridge, a signature a user creates to authorize one call on one chain can be re-submitted (via a crafted cross-chain `PostRequest`) to any other chain running the same pallet where the beneficiary account happens to share the same nonce, causing the identical raw bytes to be decoded by a *different* `RuntimeCall` enum layout and dispatched with `Signed(beneficiary)` origin.

### Finding Description
In `on_accept`: [1](#0-0) 

the signed payload used for verification is built as:
```rust
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
```
for both `Ed25519`/`Sr25519` and (with an Ethereum prefix) `Ecdsa` signatures. There is no inclusion of:
- the chain/genesis identifier of the destination runtime,
- the `source`/`from` contract address that produced the message,
- the local asset id or pallet instance,
- any Hyperbridge-specific commitment (e.g. request nonce/commitment hash).

After verification, the decoded call is dispatched directly, bypassing the normal extrinsic submission pipeline entirely: [2](#0-1) 

Only `BaseCallFilter` is applied — none of the `SignedExtension`s (fees, weight, era/nonce validity as normally enforced by `CheckNonce`, etc.) that would guard a normally-submitted signed extrinsic from this same beneficiary are applied here. The only protection against replay is the manually tracked `frame_system::Pallet::<T>::account_nonce(beneficiary)`, which is **local to the chain executing `on_accept`**.

Because `handle_unsigned` in `pallet-ismp` is a free, unsigned extrinsic that anyone with a valid membership/consensus proof can submit: [3](#0-2) 

and because `pallet-hyper-fungible-token` is intended to be deployed identically across many connected parachains, an attacker can:
1. Obtain (or induce) a beneficiary's signature over `(nonce=N, runtime_call_bytes)` intended for chain A (e.g., a harmless call whose bytes happen to be the SCALE encoding of `(pallet_index, call_index, args…)` for something benign on chain A).
2. Send a bridged token transfer via `HyperFungibleToken.send()`/equivalent on any registered source contract targeting chain B (a different parachain running the same pallet, where the same `(nonce=N)` still applies to the beneficiary — trivially true for any beneficiary account that has never transacted on chain B, or made to align), embedding the *same* `signature`/`runtime_call_bytes` in `data`.
3. On chain B, `T::RuntimeCall::decode` reinterprets the identical bytes according to chain B's own `construct_runtime!` call-index layout, which can map to a completely different, more privileged pallet call than what the beneficiary actually authorized.
4. The call is dispatched with `RawOrigin::Signed(beneficiary)`, executing an action the beneficiary never intended, using their own account authority on a chain they never targeted.

This mirrors the analog bug class from CVE-2022-35978: an authorization/execution boundary (mod-provided menu script in Minetest; a beneficiary-signed calldata payload here) is not properly scoped/sandboxed to the context it was created for, letting attacker-controlled routing (choice of destination `PostRequest`/state) reinterpret and execute the payload in an unintended, more privileged environment.

### Impact Explanation
Successful replay causes unauthorized dispatch of arbitrary runtime calls as the victim account's origin on a chain the victim never authorized, which can result in unauthorized transfers, staking/governance actions, or any other privileged dispatchable reachable under `BaseCallFilter`, directly enabling theft of funds or unauthorized app actions from the victim's account — satisfying the "unauthorized app action" / "unbacked mint or theft" impact bar for a High-severity analog.

### Likelihood Explanation
Exploitation requires the attacker to (a) obtain a beneficiary-signed `(nonce, runtime_call)` payload (often available since users routinely sign and broadcast these for legitimate transfers, and the message/data is publicly visible on-chain once dispatched) and (b) find/wait for a nonce match on a second chain running the same pallet, or target freshly created accounts where nonce = 0 is common. Given Hyperbridge's explicit design of deploying this same pallet across many connected state machines, and that nonce=0 collisions are common for newly bridged/newly created accounts, this is realistically reachable by any relayer/attacker capable of submitting an unsigned `handle_unsigned` message with a valid proof — a capability the protocol grants to anyone.

### Recommendation
Include a domain separator in the signed payload: the destination `HostStateMachine`/genesis hash, the pallet's own module id, and the source `PostRequest` commitment (or at minimum the source chain id and source contract address), e.g.:
```rust
let payload = (T::HostStateMachine::get(), PALLET_ID, source, from, nonce, substrate_data.runtime_call.clone()).encode();
```
Additionally, consider routing this dispatch path through the same `SignedExtension` validation used by ordinary extrinsics (or explicitly document/enforce that it is intentionally exempt), and reject calldata execution if the module id/pallet instance issuing the message isn't the exact same one whose call encoding was signed.

### Proof of Concept
1. Deploy/observe `pallet-hyper-fungible-token` configured identically (same `construct_runtime!` call ordering for the relevant pallet) on two connected state machines, Chain A and Chain B.
2. Victim signs `(nonce=0, runtime_call_bytes)` intending a harmless call on Chain A (e.g., `remark` at call index `(x, y)`), and this signature/payload becomes visible via the on-chain `PostRequest` body once relayed.
3. Attacker crafts a new `Message` with `data = SubstrateCalldata { signature: <same sig>, runtime_call: <same bytes> }`, sets `to = victim_beneficiary_bytes`, and dispatches it from a registered contract targeting Chain B instead of Chain A.
4. On Chain B, if the victim's nonce is still 0, `on_accept` re-verifies the same signature successfully (payload `(0, runtime_call_bytes)` matches), decodes `runtime_call_bytes` under Chain B's `RuntimeCall` layout — which may resolve to an entirely different, more sensitive call — and dispatches it with `RawOrigin::Signed(victim)`, executing an action the victim never authorized on Chain B.
