### Title
Webhook `shop-domain` (and topic/webhook-id) header is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` authenticates the body bytes but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` passes the unauthenticated `shop` value straight to the app's `WebhookHandler` as the tenant identifier, breaking the intended binding of `signed_body == body_delivered_for(shop)`.

### Finding Description
The identity binding that should hold is:
`hmac_valid(body) ⇒ shop == shop_that_produced(body)`

In this gem that binding does not exist:
- `hmac` is computed only over `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
- `shop`, `topic`, and `webhook_id` are parsed independently from headers (`lib/shopify_api/webhooks/request.rb:15-33`), which are not part of the signed material.
- `Registry.process` validates only `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`) and then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), handing the *header-derived, unauthenticated* `shop` value to the merchant-facing handler as the tenant key.

Because every shop that installs the same app shares the same `api_secret_key` used to compute webhook HMACs, any merchant who installs the app receives genuinely-HMAC-signed webhook deliveries for their own store. That merchant (an "unprivileged internet user" relative to any other tenant) can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the untouched body, and `Registry.process` will dispatch the forged event to the handler labeled with the victim's `shop`.

### Impact Explanation
This breaks the cross-tenant boundary the webhook subsystem is supposed to enforce: an app that keys any state, side effects, or authorization decisions off `WebhookMetadata#shop` (e.g., updating per-shop billing/subscription records, triggering per-shop workflows, or writing to a shop-scoped data store) can be made to apply attacker-supplied payloads under a victim shop's identity. That constitutes cross-tenant access/data-integrity compromise, matching the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
Low-to-moderate: exploitation requires the attacker to be an actual merchant with the app installed on their own shop (so they receive a real HMAC-signed webhook), and requires the host application to trust `request.shop`/`WebhookMetadata#shop` for tenant-sensitive logic without independently re-validating shop identity (e.g., against an active session or a shop recorded at webhook registration time). No compromise of `api_secret_key` or TLS interception is needed — only a legitimately-installed, malicious/curious merchant account.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before exposing `WebhookMetadata#shop` to handlers. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not authenticated by the HMAC check and must be independently cross-checked (e.g., against the shop that owns the corresponding registered webhook subscription) before being used for any tenant-scoped decision.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a genuine webhook (e.g., `orders/create`) to the app's public webhook endpoint. Attacker captures the raw request: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(api_secret_key, B)`, per `lib/shopify_api/utils/hmac_validator.rb:33-40`).
2. Attacker crafts a new HTTP request to the same endpoint, reusing body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)`, matches `H`, and returns true (`lib/shopify_api/utils/hmac_validator.rb:13-22`), because the shop header is never part of `to_signable_string`.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which now believes attacker-controlled payload `B` legitimately originated from `victim.myshopify.com`.
