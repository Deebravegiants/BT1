### Title
Non-constant-time PIN comparison in `isCorrectPin` enables timing side-channel PIN recovery - (File: `features/auth-mobile/module/auth.js`)

### Summary
The `Auth#isCorrectPin` method compares the user-supplied PIN against the stored PIN using JavaScript's `===` operator on strings, which short-circuits (returns as soon as it finds a mismatching character/length). This is the same class of bug as the reported `common_ancestor_distance_of_peers` issue: a secret-dependent comparison that is not constant time, allowing an attacker who can measure response timing to progressively recover the secret.

### Finding Description
`isCorrectPin` retrieves the stored PIN from the keystore and compares it directly with the caller-supplied `input` using `pin === input`: [1](#0-0) 

JavaScript engines implement string equality by comparing length first, then scanning characters and stopping at the first difference, exactly analogous to the `je` short-circuit in the report's disassembly of `common_ancestor_distance_of_peers`. This means the time taken by `isCorrectPin` leaks information about how many leading characters of a guess match the real PIN, exactly the kind of secret-dependent timing variance flagged in the report.

This method is part of the public `auth` module (`public: true`) and is re-exported unmodified through the feature's API layer: [2](#0-1) 

The SDK's generic API aggregator exposes every feature API method (including `auth.isCorrectPin`) over the RPC/port boundary used to talk to the UI/renderer process: [3](#0-2) 

In multi-process deployments (as documented, "In multi-process apps, you'll need a transport layer"), the caller of `exodus.auth.isCorrectPin(...)` sits in a separate, less-trusted process/renderer than the code holding the secret PIN, making this a genuine cross-boundary timing oracle rather than a same-process, self-inflicted timing leak.

### Impact Explanation
`isCorrectPin` is the gate used to unlock/verify access to the wallet (PIN authentication), which in turn protects the seed/mnemonic and signing capability. A timing side-channel on this comparison can let an attacker who can invoke the RPC/API repeatedly and measure latency perform a character-by-character (or prefix) brute-force of the 6-digit PIN far faster than blind guessing, since each guess leaks whether more leading digits are now correct. Combined with any lack of throttling/rate limiting at this layer, this significantly reduces the effective entropy of the PIN and can lead to unauthorized access, i.e., auth bypass of the local authentication gate protecting the wallet.

### Likelihood Explanation
Exploitation requires a way to invoke `auth.isCorrectPin` repeatedly and measure timing with sufficient precision (e.g., an untrusted renderer/webview process making RPC calls, or local malware/co-resident process). Given the method is exposed unauthenticated (no separate access control beyond process boundary) through the generic public API surface, and a 6-digit numeric PIN has low entropy to begin with, a patient local attacker with API access has a realistic path to exploit this. Network-based timing attacks are unlikely due to noise, but same-device/inter-process timing measurements are plausible.

### Recommendation
Replace the `===` comparison in `isCorrectPin` with a constant-time comparison, e.g., using Node's `crypto.timingSafeEqual` on fixed-length buffers (after normalizing/padding both operands to equal length before comparison, since `timingSafeEqual` itself throws/varies on length mismatch — compare a hash of both values, or always compare fixed-length encodings). Additionally, apply rate limiting/lockout and constant response-time padding around PIN verification to reduce the value of any remaining timing signal.

### Proof of Concept
1. Set a PIN: `await exodus.auth.setPin('123456')`.
2. From the RPC/API-consuming process, repeatedly call `await exodus.auth.isCorrectPin(guess)` for guesses that share increasing correct prefixes (e.g., `'1xxxxx'`, `'12xxxx'`, `'123xxx'`, ...), measuring the elapsed time of each call over many trials to average out noise.
3. Guesses with more correct leading digits take marginally longer due to `pin === input`'s per-character comparison, allowing the attacker to iteratively determine each digit of the PIN faster than exhaustive 10^6 brute force.

        // our RPC wrapped features use the proxy client which targets a function (https://github.com/ExodusMovement/exodus-hydra/blob/0e66207c3318051664e57e6b02627169eb7e10b5/libraries/sdk-rpc/src/client.ts#L41),
