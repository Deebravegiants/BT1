### Title
Webhook Tenant Identity (`shop`) Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (and `topic`) values used to identify which tenant a webhook belongs to are read directly from unauthenticated HTTP headers. Because the `Utils::HmacValidator` only verifies that the body matches the signature, and never binds the claimed `shop` to that signature, an attacker who legitimately installs the app on their own store (and therefore receives genuinely-signed webhooks) can replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. The library will accept the request as authentic and dispatch it to the host application's webhook handler under the victim's identity.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled unauthenticated from HTTP headers set by the caller: [3](#0-2) 

Because `shop` is not part of `to_signable_string`, the identity binding `signed_shop == processed_shop` never holds — the HMAC only proves "this body was signed with our secret for *some* shop," not "this body belongs to *this* shop." Any request whose body+HMAC pair was validly produced for shop A can be re-submitted with the `shopify-shop-domain` (or legacy `x-shopify-shop-domain`) header rewritten to shop B, and it will still pass `HmacValidator.validate`. `Registry.process` then hands the request straight to the app's handler using the attacker-chosen `shop`: [4](#0-3) 

An ordinary Shopify merchant who installs the target app is issued a shared `client_secret`/api key relationship that causes Shopify to send them real, validly-HMAC-signed webhooks for their own store — no privileged access or credential theft is required to obtain a valid `(body, hmac)` pair, only a normal install. That attacker can then replay the pair with a forged shop-domain header pointing at any other tenant of the same app.

### Impact Explanation
This breaks the tenant boundary the app relies on: the library asserts a webhook is authentic for whatever `shop` value happens to be in the header, without that value being covered by the cryptographic proof. A host application using this gem's `Webhooks::Registry`/`Webhooks::Request` API as documented has no way to distinguish a legitimately-scoped webhook from one where only the body was legitimate but the tenant claim was forged. This enables cross-tenant data injection — e.g., faking `app/uninstalled`, `customers/redact`, `shop/update`, or order/webhook events attributed to a victim shop, corrupting or exfiltrating another tenant's data/state within the host app. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Any user of the target app (an unprivileged merchant who installs it, which is a self-service, credential-free action) can capture one of their own legitimately signed webhook deliveries and replay it with an altered shop-domain header. No `api_secret_key`, access token, or social engineering is required — only ordinary use of the app's install flow followed by direct HTTP requests to the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values within the string covered by the HMAC verification, or otherwise cryptographically bind the claimed shop to the signed payload, so that `HmacValidator.validate` cannot succeed unless the `shop` used for tenant dispatch was itself part of what Shopify signed.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker.myshopify.com`, receiving genuine webhook deliveries signed with the app's real `api_secret_key`.
2. Attacker captures one such delivery: raw body `B` and header `shopify-hmac-sha256: H` (valid because `HMAC-SHA256(secret, B) == H`).
3. Attacker sends the same body `B` and the same `shopify-hmac-sha256: H` header to the app's public webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` and, if desired, changes `shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (no consistency check between shop/topic and hmac), and `Utils::HmacValidator.validate` succeeds because it only recomputes the signature over `B`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the host app to treat attacker-controlled data as authentic for `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
