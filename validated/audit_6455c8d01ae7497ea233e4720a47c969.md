### Title
Attacker-controlled route XDR injects unauthorized calls under the victim's signed authorization tree, enabling theft of the caller's wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The UAC CVE-2026-41449 class — untrusted data reaching a privileged execution primitive — maps onto XOXNO Lending's strategy-swap path: the attacker-controlled `swap` XDR passed to `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` determines which external contract code executes **below the caller's signed `require_auth` tree**. Neither the controller nor the router constrains which pool/token addresses the route names, so a crafted route can place attacker code on the call stack that issues `token.transfer(victim, attacker, amount)` for any token the victim holds. In Soroban recording mode, that transfer is attached as a child of the victim's authorization entry; when the victim signs the simulation-produced tree (the standard wallet flow), the theft executes. This is authorization-tree injection: untrusted input (route XDR) is executed with the victim's privilege, the direct analog of shell-metacharacter injection into `run_command.sh`.

### Finding Description
`swap_tokens` calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is the caller-supplied `StrategySwap` XDR, and the router is invoked under the strategy entrypoint's `caller.require_auth()` root [1](#0-0) . The controller grants only one exact input-transfer authorization and measures balance deltas afterward, but performs no validation of which contracts the route invokes [2](#0-1) .

The router dispatches each hop to the venue adapter at the payload-named `hop.pool` address; `dispatch_hop` validates only the router's own input/output balance deltas and keeps no allowlist of pool or token addresses [3](#0-2) . A route can therefore name an attacker-deployed contract as a "pool". During that hop, the rogue contract calls `token::Client::transfer(&victim, &attacker, &amount)` on an unrelated wallet token. Because `from.require_auth()` resolves against the in-flight authorization of the transaction's signer, the host records this transfer as a sub-invocation of the victim's `swap_collateral` (or `multiply`, etc.) auth entry.

This is proven in-tree by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the rogue transfer recorded inside Alice's `swap_collateral` auth invocation and her entire `WALLET_BALANCE` of an unlisted token moved to the attacker [4](#0-3) , and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the theft executes once the victim signs the simulation-produced tree [5](#0-4) . The threat model confirms no allowlist exists and that the loss "is then the caller's wallet, not the routed amount" [6](#0-5) .

The contract-side defense is absent: `dispatch_hop` checks output deltas, the controller checks `RouterOverspend`/`NoSwapOutput` and final account risk, and none of these inspect the auth tree [7](#0-6) . Protection is pushed entirely to an off-chain client obligation ("A client must decode the route it signs"), which wallets do not generally fulfill — they display and sign the auth tree simulation returns, and the rogue child entry is indistinguishable without route-decoding logic.

### Impact Explanation
Theft of user funds. A victim who executes a strategy swap with an attacker-supplied route loses arbitrary amounts of any token in their wallet, independent of the routed amount and unbounded by `min_out` or the post-swap health check. The stolen token need not be a protocol-listed asset. Severity: High (Critical impact bounded by the UI:P-style requirement that the victim sign the poisoned tree — the same user-interaction vector as CVE-2026-41449).

### Likelihood Explanation
Any unprivileged attacker can deploy a rogue "pool" contract and craft a valid route XDR; the malicious route can be delivered through a phishing frontend, a compromised/malicious quote source, or social engineering ("use this route for better output"). Every signer who submits the simulated transaction is exposed — the auth tree the wallet presents legitimately contains the theft as a child of the entry the user intended to sign. Reachable entrypoints: `controller.swap_collateral`, `controller.multiply`, `controller.swap_debt`, `controller.repay_debt_with_collateral`, and direct `router.execute_strategy` calls.

### Recommendation
Constrain routes on-chain rather than relying on client-side inspection: maintain a governance/router-level allowlist of venue pool (and token) addresses that hops may invoke, or pin per-venue pool discovery to canonical registries so `hop.pool` cannot be arbitrary third-party code. Short of an allowlist, the controller/router could require that every token contract touched during a route appear in the payload's declared asset registry. Document prominently that wallets must render and verify auth-tree children, but treat that as defense-in-depth, not the primary control.

### Proof of Concept
A complete executable PoC exists in the repository: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Attacker deploys `RogueHopPool`, whose `swap()` executes `token.transfer(victim, attacker, WALLET_BALANCE)` on an arbitrary token the victim holds [8](#0-7) .
2. Attacker delivers route XDR naming the rogue pool as the hop venue with a fair `min_out` so the swap itself looks honest [9](#0-8) .
3. Victim calls `controller.swap_collateral(alice, account, USDC, amount, ETH, route)`; simulation records the rogue `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` entry [4](#0-3) .
4. Victim signs the simulation-produced tree; enforcement accepts the rogue transfer, Alice's wallet token balance goes to 0 and the attacker's to `WALLET_BALANCE`, while the swap itself still produces the promised ETH output and the position remains healthy [5](#0-4) .

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
