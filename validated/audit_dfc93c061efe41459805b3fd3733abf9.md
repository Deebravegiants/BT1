### Title
Fisherman veto of the latest state commitment can be undone by replaying the same consensus proof, reinstating a vetoed state - ([File: modules/ismp/core/src/handlers/consensus.rs])

### Summary
This mirrors the Ambire "recovery replayed after cancellation" bug class: an invalidating action (veto/cancel) removes state, but the underlying authorization artifact (a signed consensus proof) is never consumed/blacklisted, so any unprivileged relayer can replay it verbatim to reinstate exactly what was just invalidated.

### Finding Description
`update_client` in `modules/ismp/core/src/handlers/consensus.rs` (lines 51-80) accepts and stores a `StateCommitment` for a given `StateMachineHeight` whenever `commitment_height.height >= previous_latest_height` and no commitment already exists at that height: [1](#0-0) 

When a fisherman detects a bad/disagreeing state commitment, `pallet_fishermen::veto_state_commitment` deletes only the `StateCommitment` at that height via `delete_state_commitment` — it does **not** invalidate the underlying consensus proof or mark the height as permanently closed: [2](#0-1) 

Crucially, when the vetoed height happens to be the chain's *latest* height, deleting it also rolls back `latest_commitment_height`/`_latestStateMachineHeight` to the prior height, as confirmed by the project's own regression test: [3](#0-2) 

Because (a) the commitment slot at that height is now empty and (b) the latest-height pointer has been rolled back below that height, the exact same `ConsensusMessage`/consensus proof that produced the original (vetoed) commitment satisfies both gating conditions in `update_client` again (`previous_latest_height > commitment_height.height` is now false, and `state_machine_commitment(state_height).is_ok()` is now false). Any relayer — an unprivileged actor — can therefore resubmit the identical consensus proof bytes and have the vetoed commitment reinstated, with `store_latest_commitment_height` re-advancing the latest pointer past the veto.

The EVM-side handler (`HandlerV2.handleConsensus` / `EvmHost.storeStateMachineCommitment` + `_latestStateMachineHeight`) implements the same gating logic and is subject to the identical replay: [4](#0-3) [5](#0-4) 

This is the direct structural analog of the Ambire recovery bug: the cancellation/veto clears derived state (`scheduledRecoveries` / `_stateCommitments`) but does not invalidate the replayable authorization (the recovery signature / the consensus proof), and rolling back a pointer (nonce / latest height) re-opens the exact same slot for the same artifact to be replayed.

### Impact Explanation
A fisherman veto is Hyperbridge's sole on-chain safety valve against a fraudulent or disagreeing L2/consensus state commitment (per `docs/content/developers/explore/fishermen.mdx`, vetoes require no cryptographic proof and rely purely on the fisherman's trust). If the vetoed height is the latest height, any relayer can trivially resubmit the same consensus proof to reinstate the vetoed `StateCommitment` before governance or another fisherman can react again, since the height is no longer "vetoed" from the protocol's perspective (only the specific commitment slot was cleared, and the pointer rewound). This nullifies the fisherman defense for the class of attacks it exists to stop — messages, storage proofs and non-membership proofs anchored to the reinstated (attacker-favorable/incorrect) `StateCommitment` become deliverable again through `HandlerV2`/`Handler` request/response/timeout paths, enabling forged message delivery or unsound state acceptance. This satisfies the "unsound state commitment" / "forged message delivery" impact bar.

### Likelihood Explanation
Likelihood is high once a veto lands on the latest height (a routine scenario, since vetoes typically target the most-recently-finalized/contested commitment). No special privilege is needed to replay — resubmitting a consensus proof is a normal, permissionless relayer action (`update_client`/`handleConsensus` are open entry points), and the original proof bytes remain valid indefinitely (they were legitimately verified once; nothing marks them as consumed or the height as burned).

### Recommendation
- Track vetoed heights explicitly (e.g., a `VetoedHeights` set per `StateMachineId`) and have `update_client`/`HandlerV2.handleConsensus` permanently reject any `commitment_height` matching a vetoed height, regardless of the current `latest_commitment_height` pointer.
- Do not roll back `latest_commitment_height`/`_latestStateMachineHeight` on veto of the latest height; instead, keep the pointer at the vetoed height (marking it "poisoned") so no fresh commitment — honest or replayed — can reuse that height without an explicit, deliberate re-open by governance.
- Alternatively, require any resubmission at a previously-vetoed height to include additional confirmation (e.g., a challenge-period reset plus fresh fisherman quorum silence) rather than accepting the first proof that satisfies the naive `height > latest` check.

### Proof of Concept
1. Consensus proof `P` for state machine `S` is submitted, advancing `latest_commitment_height(S)` to height `H` and storing `StateCommitment(H)`.
2. A fisherman detects disagreement and calls `veto_state_commitment(height = H)`. This deletes `StateCommitment(H)` and, because `H` was the latest height, rolls `latest_commitment_height(S)` back to `H-1` (see `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early` test).
3. Any relayer resubmits the identical consensus message/proof `P` via `update_client`/`HandlerV2.handleConsensus`. Since `previous_latest_height (H-1) > H` is false and `state_machine_commitment(H)` no longer exists, the handler re-stores `StateCommitment(H)` and re-advances `latest_commitment_height` to `H`, fully undoing the veto.
4. Requests/responses/timeouts proven against the reinstated `StateCommitment(H)` are now deliverable again through `HandlerV2`/pallet-ismp handlers, exactly as if the veto never happened.

// Vetoing the *latest* height resets the latest pointer, which re-opens that height
// for honest resubmission. The resubmission gets a second queue entry, and the stale
// twin ahead of it evicts the live commitment one insertion early. This pins that
// wart: it costs the height one insertion of retention and burns one queue slot,
// which is negligible against the configured caps but is not a no-op.
#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
