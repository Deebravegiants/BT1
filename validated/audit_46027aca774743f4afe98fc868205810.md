### Title
Tokens transferred directly to the pool or controller are permanently locked — no sweep or recovery path exists — ([File: contracts/pool/src/cache/cash.rs])

### Summary
The pool and controller contracts hold real token balances, but neither exposes any entrypoint that can return tokens not tracked by the internal `cash` book (pool) or by measured balance deltas (controller). An unprivileged address that transfers tokens directly to the pool contract, or pushes an undeclared token to the controller (e.g., inside a `flash_position` callback), loses them permanently. The original report's bug class — a contract can receive funds with no way to withdraw them — maps directly onto this shape.

### Finding Description
- The pool's outbound transfers only happen inside `borrow`, `withdraw`, `repay` (overpayment refund), `recapitalize` (excess refund), `claim_revenue`, `create_strategy`, and `flash_loan`, all of which draw against the tracked `cash` book or a measured receipt delta. `debit_cash` rejects debits above `cash`, and `require_reserves` gates every cash-backed payout (`contracts/pool/src/cache/cash.rs:15-41`).
- A direct `token.transfer(user, pool, amount)` raises `token.balance(pool)` but not `cash` — the docs state plainly: "Direct donations do not rewrite those books" (`docs/explanation/threat-model.md:129-130`) and "Cash is the reserve book; token donations alone do not increase it" (INV-ACCT-02, `docs/reference/invariants.md`). The fuzz invariant only asserts `tracked_cash <= balance`, so an excess balance is expected and unclaimable.
- After all suppliers withdraw, `cash` reaches zero while the donated amount remains in `token.balance(pool)` forever — confirmed by `pool_all_money_paths_preserve_books_and_shared_token_custody`, which shows a 7-unit donation sitting outside every market's cash book.
- On the controller, every outbound path refunds only a measured balance *delta* since the call began (`refund_controller_balance_delta` in `contracts/controller/src/payments.rs:41-51` preserves pre-existing balances). The endpoints reference states: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (`docs/reference/endpoints.md:86`).
- The code even enshrines this: `withdraw`/`borrow` to the pool or controller are rejected precisely because "the tokens would sit in the controller where no balance-delta measurement ever claims them" (`certora/controller/spec/market_guard_rules.rs:157-159`, `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-5`) — acknowledging that anything that does land there is stranded, yet no recovery path exists for the direct-transfer route, which is not blocked.
- Unlike the swap-aggregator, which has owner-only `sweep_balance` for stray tokens (`contracts/swap-aggregator/src/lib.rs:189-203`), neither the pool nor the controller has an equivalent.

### Impact Explanation
Permanent freezing of funds. Any token balance held by the pool above tracked `cash`, or held by the controller at all, is unrecoverable by anyone — user, admin, or governance. The pool's own Wasm `upgrade` is owner-gated to the controller and there is no governance operation to recover balances; for the controller there is no sweep at all. For pool-market tokens this is at best a dormant subsidy that suppliers can never withdraw (withdrawals are capped by `cash`), and for non-market tokens or controller balances it is a pure burn.

### Likelihood Explanation
Reachable by a single unprivileged address via `token.transfer` to the pool address (explicitly in scope), or via a `flash_position` receiver contract that pushes a token that is neither a declared collateral nor a listed refund asset — the callback succeeds and the token is stranded (`docs/explanation/threat-model.md:172-173`, `skills/xoxno-lending-contracts/flash-loans.md:134`). The threat model also documents real sources of stray pool balance: Aquarius venue rewards can be pushed to the pool permissionlessly by any caller, so the pool *will* accumulate unbooked balance in normal operation (`docs/explanation/threat-model.md:134-140`). Severity Medium: accidental misdirected transfers and permissionless reward pushes are plausible, but each event only strands what is sent.

### Recommendation
Add a bounded recovery path for unbooked balances, mirroring the router's `sweep_balance` design: a governance-executed operation (or pool owner call) that transfers `token.balance(pool) - total_tracked_cash` of each asset to the accumulator, and an equivalent controller sweep for balances above in-flight measured deltas. Until then, document the address prominently so integrators never pay the contracts directly.

### Proof of Concept
1. Anyone calls `token.transfer(attacker_or_user, pool_addr, X)` on a listed asset (or rewards are pushed to the pool by Aquarius's permissionless claim).
2. `pool.get_reserves(hub_asset)` is unchanged — `cash` does not reflect `X`; the donation "belongs to no market's cash book" (`tests/test-harness/tests/pool_money_flow_audit.rs:86-96`).
3. All suppliers withdraw to zero (`withdraw` with amount `0` = MeansAll). `cash` drains to 0 while `token.balance(pool) == X`.
4. No entrypoint — `borrow`, `withdraw`, `repay`, `recapitalize`, `claim_revenue`, `seize_positions`, `flash_loan` — can move `X`: cash-backed payouts reject via `InsufficientLiquidity`, and refunds only return the *measured* receipt of the current call (`contracts/pool/src/cache/cash.rs:15-53`). `X` is locked permanently.

Controller variant: inside `execute_flash_position`, the receiver transfers a token that is neither in `collaterals` nor `refund_assets`. The call succeeds; the controller retains it, and `refund_controller_balance_delta` never touches pre-existing balances — permanently stranded (`contracts/controller/src/payments.rs:41-51`).
