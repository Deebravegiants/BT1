### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is refunded to the Host contract instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are `payable` functions reachable by any unprivileged user/app dispatching a cross-chain message. When `msg.value > 0`, they swap the supplied native token for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, using `address(this)` as the swap's "to" recipient for the output tokens. Any leftover ETH from `swapETHForExactTokens` (when the user overpays `msg.value` beyond what's needed for the exact fee) is refunded by the Uniswap router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender. This mirrors the reported bug class: payable functions that don't validate/refund `msg.value` precisely, causing accidental ETH to be lost by the user.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

In all three, `swapETHForExactTokens{value: msg.value}(exactFeeAmount, path, address(this), block.timestamp)` is invoked. Uniswap V2's `swapETHForExactTokens` only consumes the ETH necessary to obtain `exactFeeAmount` of the output token and refunds the remainder of `msg.value` to `msg.sender` of that call — in this context, that is the `EvmHost` contract itself, not the EOA/app that originally called `dispatch`/`fundRequest` with the excess `msg.value`. There is no logic in these functions computing the required native amount up front, capping accepted `msg.value`, or forwarding the router's ETH refund back to `_msgSender()`. Any user who supplies more native token than exactly required for the fee swap (a very easy mistake to make, since the router determines the exchange rate at execution time and callers must estimate/quote the value beforehand) permanently loses the excess to the Host contract's own balance, with no visible `withdraw`/`sweep` function found for these swap refunds in `EvmHost.sol`.

This is the same root cause described in the referenced report for `Periphery.sol`: payable functions that accept `msg.value` without validating that the exact intended amount is consumed, causing accidental loss of user ETH. Here it manifests in the core dispatch/fee-funding path of `EvmHost`, which is the entry point used by every app (including `HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`, `HyperbridgeLzEndpoint`, etc.) to pay Hyperbridge dispatch fees in native token: [4](#0-3) 

### Impact Explanation
Any unprivileged user dispatching a message or funding a request with native token, and overestimating the required `msg.value` (e.g., due to slippage between quoting and execution, or simply rounding up to be safe), will have the excess ETH silently retained by the `EvmHost` contract rather than refunded to them or applied to their fee balance. Since there's no sweep/refund path surfaced for this trapped ETH back to the depositor, this constitutes a permanent loss of user funds — meeting the "concrete theft or permanent freezing of funds" bar. The impact scales with the frequency of native-fee dispatches across every ISMP-integrated app on the affected EVM host.

### Likelihood Explanation
High likelihood: this triggers on the ordinary, expected code path (native-token fee payment) any time a caller's `msg.value` exceeds the exact amount consumed by the Uniswap swap — which is common since the caller must supply `msg.value` before the swap executes and cannot know the exact on-chain price at call time without a race-free quote. No malicious actor is required; it happens from normal usage/user error, exactly as the source report describes.

### Recommendation
- Capture and refund any leftover ETH from `swapETHForExactTokens` back to `_msgSender()` (e.g., check `address(this).balance` before/after the swap, or use the router's return value, and forward the difference to `_msgSender()`), in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `evm/src/core/EvmHost.sol`.
- Alternatively/additionally, require the caller to specify the exact expected native amount and revert if `msg.value` does not match, similar to the recommended `require(msg.value == expectedAmount)` pattern from the referenced report, or expose a public `getAmountsIn`-based quote that the swap-consuming code enforces exactly.

### Proof of Concept
1. App `A` calls `EvmHost.dispatch{value: X}(DispatchPost{..., fee: F, ...})` where `X` is meant to cover the exact-output swap for `F` units of `feeToken`.
2. Inside `dispatch`, `swapETHForExactTokens{value: X}(F, path, address(this), deadline)` executes; suppose only `X' < X` ETH is required at execution price.
3. Uniswap V2 Router refunds `X - X'` ETH to `msg.sender`, i.e., to `EvmHost` (the caller of the router), per standard `swapETHForExactTokens` semantics.
4. `EvmHost` never forwards this `X - X'` refund back to `A` or `_msgSender()`; the request proceeds and `X - X'` ETH remains stuck in `EvmHost`'s balance indefinitely. [1](#0-0)
