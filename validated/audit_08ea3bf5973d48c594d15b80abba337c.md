## Title
Webhook HMAC validates only the raw body, not the `shop` header — allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The external report describes a class of bug where an equality check is performed over an incomplete set of inputs — a value used for downstream accounting is not actually covered by the verification the code relies on, letting attacker-controlled data slip through unbound to the verified value. The `shopify-api-ruby` analog is in webhook processing: the HMAC signature only binds the request body, but the `shop` identity used by webhook handlers is taken from an unauthenticated header that is never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` value exposed to consumers of the request comes from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly from `to_signable_string` (i.e., the raw body) and the app's `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC over the body and then immediately trusts `request.shop` (from the unsigned header) when building the metadata handed to app-registered handlers: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(raw_body, api_secret_key) == true` should imply `shop_header == shop_that_actually_generated(raw_body)`

But the code only proves `hmac_valid(raw_body, api_secret_key) == true`; it never proves the second half. Since `api_secret_key` is shared across every shop that installs the app, any shop that installs the app receives (from Shopify) genuine `(raw_body, hmac)` pairs for its own webhook deliveries. An attacker who installs the app on their own store obtains a legitimate `raw_body`+`hmac` pair signed with the developer's real `api_secret_key`. They can then replay that exact `raw_body`/`hmac` to the same webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looked at the shop header), and `Registry.process` dispatches the payload to the app's handler tagged with the victim's shop.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC is supposed to enforce. Any application handler that uses `WebhookMetadata#shop` to decide which tenant's data to update, delete, or act on (e.g., `app/uninstalled` cleanup, GDPR `customers/redact`/`shop/redact`, `orders/create` inventory sync, billing state changes) can be tricked into applying attacker-supplied webhook content to a different (victim) shop's tenant record — a cross-tenant data integrity/confusion issue reachable by any unprivileged internet user who can install the app on their own store once and then freely replay the captured request against the shared public webhook endpoint.

### Likelihood Explanation
High likelihood: any developer can create a free Shopify partner/dev store, install the target app, capture one legitimate webhook delivery (body + `X-Shopify-Hmac-Sha256`), and replay it with a forged `X-Shopify-Shop-Domain` header. No secrets, tokens, or elevated privileges are required beyond a standard trial-store install, which is the normal, unprivileged way any third party can interact with an app.

### Recommendation
Bind the shop identity into the verified material: include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload verification, or independently cross-check `request.shop` against a shop known to have legitimately triggered the specific body content (e.g., verify the `shop` header against a shop-to-secret/session mapping instead of trusting it blindly whenever the shared app secret validates the body).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers any webhook event (e.g. updates a product) and captures the raw POST to the app's webhook endpoint, including headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and the JSON body.
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the body against the secret.
5. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled webhook content as if it originated from the victim shop.
