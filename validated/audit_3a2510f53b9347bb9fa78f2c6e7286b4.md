## Title
Under-supply of `feeToken` permanently blocks GET-response and timeout delivery in `EvmHost` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` all pay out the accumulated relayer/payer `feeToken` fee via an unconditional `IERC20(feeToken()).safeTransfer(...)` call placed *after* the state-mutating callback succeeds, with no check that the host actually holds enough `feeToken` balance to cover the fee, and no try/catch isolating the transfer from the rest of the state transition.

### Finding Description
In `dispatchIncoming(GetResponse memory response, address relayer)`: [1](#0-0) 

the response receipt is written first (replay protection), `onGetResponse` is invoked on the destination module, and only if that succeeds does the function attempt `IERC20(feeToken()).safeTransfer(relayer, fee)`. This transfer is not wrapped in a low-level `.call` with a success check the way the module callback is — it is a direct `safeTransfer`, which reverts the *entire* transaction (including the receipt write and the successful module delivery) if the ERC20 transfer fails, e.g. because `EvmHost`'s `feeToken` balance is lower than `fee`.

The same unconditional-transfer-after-success pattern exists for GET and POST timeouts: [2](#0-1) 

Here `meta.fee` is refunded to `meta.sender` via `safeTransfer` after `onGetTimeout`/`onPostRequestTimeout` succeeds — again with no balance check and no isolation from the rest of the state transition.

`EvmHost`'s `feeToken` balance is not a fixed, pre-funded pool guaranteed to always cover outstanding obligations: it accumulates from `dispatch()` fee payments (`post.fee`, swapped via Uniswap or pulled via `safeTransferFrom`) and is drawn down by governance withdrawals via `IHostManager.withdraw` as well as by exactly these relayer-fee/timeout-refund payouts. Because many requests can be dispatched with fees attached and only later delivered or timed out, and because `withdraw` can drain accumulated revenue via governance, it is entirely possible for the instantaneous `feeToken` balance to fall below the sum of fees owed for requests that are still pending delivery/timeout — the same "under-supply" condition described in the referenced MasterChef report, just manifesting as a hard revert here instead of a silent partial payment.

### Impact Explanation
Once the host's `feeToken` balance is insufficient to cover a given `fee`, any relayer submitting a valid consensus/state proof to deliver that specific GET response, GET timeout, or POST timeout will have their entire transaction revert, even though the underlying membership/non-membership proof and the destination module's callback both succeeded. Because the receipt/commitment write, module callback, and fee payment happen in a single atomic call with no fallback path (unlike `dispatchIncoming(PostRequest, ...)`, which explicitly early-returns and preserves retryability when the destination call fails), there is no way to "retry without the fee" — the message simply cannot be delivered until the host is refunded/topped up with `feeToken`. This is a concrete "route unable to deliver messages" condition: requests/responses become permanently stuck, and the relayer or payer entitled to the reward/refund also cannot recover it in the interim. This matches Medium severity for the same reason the original finding was judged Medium: it is a situational but clearly demonstrable loss-of-liveness/loss-of-fee-recovery condition triggered by ordinary protocol activity (fee accumulation/drawdown imbalance) rather than by any malicious actor.

### Likelihood Explanation
Reachable by any unprivileged relayer simply delivering an already-dispatched GET response or a legitimate timeout proof — no special privileges are required. The triggering condition (feeToken balance dropping below the fee owed for a specific commitment) is a natural consequence of protocol operation: fees for many outstanding requests can be denominated in feeToken while the pool is drawn down by governance `withdraw` calls or by prior relayer payouts for other commitments, making this plausible under real operational patterns rather than a contrived edge case.

### Recommendation
In `dispatchIncoming(GetResponse, ...)` and both `dispatchTimeOut` overloads, cap the transferred amount to the actual available `feeToken` balance (e.g. `uint256 payout = Math.min(fee, IERC20(feeToken()).balanceOf(address(this)))`) or track any shortfall in a per-recipient claimable mapping that can be drained later once the host is replenished, rather than performing an unconditional `safeTransfer` that can revert and block the entire delivery/timeout. Alternatively, wrap the fee transfer in a low-level call with a success check (mirroring the pattern already used for the module callback) so that a payout failure does not roll back the receipt write and the message delivery/timeout processing.

### Proof of Concept
1. Dispatch several `DispatchGet` requests (or `DispatchPost` requests that later time out) on `EvmHost`, each attaching a non-zero `fee` in `feeToken`, so that the sum of outstanding fees exceeds what remains in the host's `feeToken` balance (e.g. after governance calls `IHostManager.withdraw` to sweep accumulated revenue via `WithdrawParams`).
2. Have a relayer submit a valid consensus/state proof through `HandlerV2`, causing it to call `EvmHost.dispatchIncoming(GetResponse, relayer)` for one of these requests.
3. The destination module's `onGetResponse` call succeeds, but `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts because `feeToken.balanceOf(address(this)) < fee`.
4. The entire `dispatchIncoming` call reverts; the `_responseReceipts[commitment]` write is rolled back along with the successful delivery, and there is no code path to retry delivery without also requiring the fee payment to succeed — the message is stuck until the host's `feeToken` balance is replenished.
5. The identical scenario applies to `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)`, blocking legitimate timeout refunds in the same way.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
