### Title
Out-of-bounds memory read in `HeaderImpl.stateCommitment()` via unvalidated ISMP consensus digest length - (File: `evm/src/consensus/Types.sol`)

### Summary
`HeaderImpl.stateCommitment()` extracts a BEEFY-verified parachain header's `overlayRoot`/`stateRoot` by slicing the raw `ISMP` consensus digest bytes at fixed offsets (`Bytes.substr(data, 0, 32)` and `Bytes.substr(data, 32)`) without first checking that `data.length >= 64` [1](#0-0) . This mirrors the CVE-2023-2934 bug class: a message field is consumed and copied without validating its length against the offsets used to parse it, causing an out-of-bounds read.

### Finding Description
`Codec.DecodeHeader` decodes an arbitrary, relayer-supplied `bytes` blob into a `Header` with a `Digest[]` array, where each digest's `data` field length is attacker-controlled (bounded only by the SCALE compact-length prefix, itself attacker supplied) [2](#0-1) . `EcdsaBeefy.verifyParachainHeaderProof` calls `Codec.DecodeHeader(para.header)` on each parachain header inside a `BeefyConsensusProof` supplied by any caller of `EcdsaBeefy.verify` / the consensus-update dispatch path, then calls `header.stateCommitment()` [3](#0-2) .

Inside `stateCommitment()`, once a digest with `consensusId == ISMP_CONSENSUS_ID` ("ISMP") is found, the code unconditionally does:
```
mmrRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 0, 32));
childTrieRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 32));
```
with no check that `consensus.data.length >= 64` [4](#0-3) . Because `consensus.data` for that digest kind is fully attacker-controlled (any relayer can encode a header with an `ISMP`-tagged consensus digest of any length, e.g. 1 byte), `Bytes.substr(data, 32)` is invoked with a start offset that can exceed `data.length`. This is the direct analog of CVE-2023-2934's root cause: the message layer trusted a length/offset relationship supplied by the sender instead of validating it before reading, leading to out-of-bounds memory access ("heap corruption" in the Chrome/Mojo case; out-of-bounds memory read/copy in the Solidity `bytes`-slicing case here).

By contrast, every other proof-parsing path found in this codebase that reads at attacker-chosen offsets has an explicit length guard added as a hardening fix (e.g. `modules/trees/ethereum/src/node_codec.rs` rejecting empty HP-encoded partial keys [5](#0-4) ; `modules/consensus/pharos/primitives/src/spv.rs` bounding `nibble_at_depth` and proof depth [6](#0-5) ; `modules/consensus/beefy/verifier/src/lib.rs` guarding `mmr_proof.leaf_indices.len() != 1` [7](#0-6) ; `modules/consensus/bsc/verifier/src/primitives.rs` guarding validator-section vs turn-byte length [8](#0-7) ; `modules/consensus/sync-committee/verifier/src/lib.rs` guarding `multi_proof.len()` [9](#0-8) ). The `HeaderImpl.stateCommitment()` call site in `Types.sol` is the one place in the consensus-verification surface that still performs an unchecked fixed-offset slice on fully attacker-controlled digest bytes.

### Impact Explanation
`EcdsaBeefy.verify` is invoked as part of the permissionless BEEFY consensus-update path that any relayer can submit. If `Bytes.substr` (from the external `solidity-merkle-trees` library) does not itself bound-check `start <= data.length` before computing/copying, an adversarial parachain header with a short `ISMP` digest causes an out-of-bounds memory read in Solidity, which can revert unpredictably, read adjacent unrelated memory into `childTrieRoot`/`mmrRoot`, or — depending on the library's exact implementation — corrupt returned memory. Either outcome is a denial-of-service against the consensus-update path (a relayer can craft a header that reliably reverts/breaks parsing for a specific parachain height, making that route unable to deliver its state commitment) or, in the worst case, causes the contract to accept and act on garbage `overlayRoot`/`stateRoot` values that were sliced from out-of-bounds memory, undermining the soundness of the state commitment recorded for that parachain — which downstream feeds message membership/non-membership proofs for that state machine.

### Likelihood Explanation
Likelihood is moderate-to-high in terms of reachability (any relayer can submit a `BeefyConsensusProof` containing a crafted parachain header with an arbitrary-length `ISMP` digest; no privileged role is required), but the exploitability depends on the internal behavior of the external `Bytes.substr` implementation, which is outside this repository and could not be directly inspected in this pass. If `Bytes.substr` already reverts safely on out-of-range `start`, this degrades to a pure DoS/liveness bug for that specific header (still valid — "a route unable to deliver messages" is in-scope). If it does not bound-check, this is a genuine out-of-bounds memory access matching the CVE's root cause exactly.

### Recommendation
In `HeaderImpl.stateCommitment()`, validate `self.digests[j].consensus.data.length == 64` (or `>= 64`) before slicing, mirroring the explicit length check already used for the MMR-root payload in `EcdsaBeefy.verifyMmrUpdateProof` (`commitment.payload[i].data.length == 32`) [10](#0-9) . Reject or skip digests that don't match the expected fixed length instead of unconditionally slicing at offsets 0 and 32.

### Proof of Concept
1. Craft a `BeefyConsensusProof` whose `parachain.parachains[i].header` SCALE-encodes a valid Substrate header containing a single digest of kind `DIGEST_ITEM_CONSENSUS` with `consensusId = bytes4("ISMP")` and `data` of length 1 (or any length `< 64`), per `Codec.decodeDigestItem` [2](#0-1) .
2. Submit this proof to `EcdsaBeefy.verify(previousState, proof)` (reachable via the consensus-update dispatch path used by any relayer).
3. `Codec.DecodeHeader` successfully decodes the header (digest parsing only requires the SCALE length prefix to match the supplied `data`, which it does) [11](#0-10) .
4. `verifyParachainHeaderProof` → `header.stateCommitment()` executes `Bytes.substr(data, 32)` with `data.length == 1`, triggering an out-of-bounds read/undefined behavior inside the external `Bytes` library [4](#0-3) .

Note: I was unable to inspect the implementation of `Bytes.substr` itself, since it lives in the external `@polytope-labs/solidity-merkle-trees` dependency rather than this repository, so the precise runtime behavior (clean revert vs. actual OOB memory read) could not be confirmed from in-repo code alone.

    // @dev Deserializes a substrate header
    function DecodeHeader(bytes memory encoded) internal pure returns (Header memory) {
        ByteSlice memory slice = ByteSlice(encoded, 0);
        bytes32 parentHash = Bytes.toBytes32(Bytes.read(slice, 32));
        uint256 blockNumber = ScaleCodec.decodeUintCompact(slice);
        bytes32 stateRoot = Bytes.toBytes32(Bytes.read(slice, 32));
        bytes32 extrinsicsRoot = Bytes.toBytes32(Bytes.read(slice, 32));

        uint256 length = ScaleCodec.decodeUintCompact(slice);
        Digest[] memory digests = new Digest[](length);

        for (uint256 i = 0; i < length; i++) {
            uint8 kind = Bytes.readByte(slice);
            Digest memory digest;
            if (kind == DIGEST_ITEM_OTHER) {
                digest.isOther = true;
            } else if (kind == DIGEST_ITEM_CONSENSUS) {
                digest.isConsensus = true;
                digest.consensus = decodeDigestItem(slice);
            } else if (kind == DIGEST_ITEM_SEAL) {
                digest.isSeal = true;
                digest.seal = decodeDigestItem(slice);
            } else if (kind == DIGEST_ITEM_PRERUNTIME) {
                digest.isPreRuntime = true;
                digest.preruntime = decodeDigestItem(slice);
            } else if (kind == DIGEST_ITEM_RUNTIME_ENVIRONMENT_UPDATED) {
                digest.isRuntimeEnvironmentUpdated = true;
            }
            digests[i] = digest;
        }

        return Header(parentHash, blockNumber, stateRoot, extrinsicsRoot, digests);
    }
