Based on the codebase, there's a genuine analog in the webhook processing path.

## Title
Webhook `shop`/`topic` identity fields are trusted for handler routing without being covered by the HMAC signature — enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are then used to route to a handler and passed downstream as the trusted tenant identity are read straight from HTTP headers and are never included in the signed content [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/verifies the HMAC solely over that signable string [4](#0-3) . Meanwhile `Request#shop`, `Request#topic`, `Request#webhook_id`, and `Request#api_version` are all derived from headers (`shopify-shop-domain`, `shopify-topic`, etc.) that sit entirely outside the HMAC's coverage [5](#0-4) .

`Registry.process` uses `request.topic` to look up the handler and forwards `request.shop` into `WebhookMetadata` as the trusted tenant identifier, with the only gate being the body-only HMAC check [6](#0-5) . The equality the code implicitly (and incorrectly) assumes is:

`bytes verified by HMAC (raw_body) == identity acted upon (shop header, topic header)`

These are not the same thing. A given `(raw_body, hmac)` pair is only proof that *the body* was produced by Shopify with the app's `client_secret` for *some* event — it says nothing about which shop or which topic the caller claims it belongs to.

### Impact Explanation
An unprivileged attacker who has legitimately installed the target app on their own shop receives genuine Shopify-signed webhooks (valid `raw_body` + `hmac`) for events on their own store. Because the shop/topic headers are unauthenticated, the attacker can replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting:
- `x-shopify-shop-domain` with a victim shop's domain, and/or
- `x-shopify-topic` with a different (potentially more sensitive) registered topic.

The HMAC check still passes (same body, same secret), but the handler is invoked believing the event came from the victim shop / a different topic than actually occurred. Depending on the host application's webhook handler logic (e.g., updating shop-scoped records, processing `app/uninstalled` or `shop/redact`-style compliance topics, syncing order/customer data keyed by `data.shop`), this breaks the tenant isolation boundary the HMAC check is supposed to enforce — a cross-tenant access primitive.

### Likelihood Explanation
Any user with valid access to install the app on any store (i.e., any merchant who can install a public/dev app) can obtain a legitimately-signed `(body, hmac)` pair for their own shop, then directly issue an HTTP POST to the app's webhook endpoint with attacker-controlled headers. No access token, `client_secret`, or privileged account is required — only the ability to install/trigger one webhook event on any shop.

### Recommendation
Bind the routing identity to the signed content instead of trusting bare headers:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them), or
- Cross-validate the header-derived `shop`/`topic` against values independently confirmed via a signed source (e.g., look up the webhook subscription by `webhook_id` through the Admin API using a session already known to belong to that shop) before dispatching to a handler.

### Proof of Concept
1. Attacker installs app `App` on `attacker-shop.myshopify.com`; app registers `orders/create` webhook handler at `/callback/orders/create`.
2. Shopify sends a legitimately signed webhook: `raw_body = B`, `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker captures `(B, HMAC(secret,B))` and issues a direct POST to `App`'s `/callback/orders/create` endpoint with body `B` unchanged, but headers rewritten: `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against the HMAC [7](#0-6) .
5. The handler executes with `data.shop == "victim-shop.myshopify.com"` even though the event never occurred for that shop [8](#0-7) .
