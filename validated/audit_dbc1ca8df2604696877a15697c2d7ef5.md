Audit Report

## Title
Chainlink bridge and external-initiator API responses expose plaintext `outgoingToken`/`accessKey` credentials to any authenticated Viewer/Run-role user, unmasked - (File: core/web/presenters/bridges.go)

## Summary
`BridgeResource` and `ExternalInitiatorResource` unconditionally embed the stored `OutgoingToken` (and, for external initiators, `AccessKey`) in cleartext, and the routes that return them (`GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, `GET /v2/external_initiators`) are only guarded by base session/token authentication, not by `auth.RequiresEditRole`. Any authenticated user — including one with only the lowest `UserRoleView` role — can retrieve these secrets.

## Finding Description
`BridgeResource` declares `OutgoingToken string `json:"outgoingToken"`` with no `omitempty` or redaction, unlike `IncomingToken` which is documented as "only provided when creating a Bridge" [4](#0-3) . `NewBridgeResource` copies `b.OutgoingToken` straight from the DB-backed `bridges.BridgeType` with no masking [3](#0-2) .

The route table registers `GET /bridge_types` and `GET /bridge_types/:BridgeName` (and `GET /external_initiators`) inside the `authv2` group without `auth.RequiresEditRole`, while `POST`/`PATCH`/`DELETE` on the same resources are explicitly wrapped with `auth.RequiresEditRole` [2](#0-1) . `RequiresEditRole` rejects `UserRoleView` and `UserRoleRun`, proving these are meaningfully different, more-restrictive gates that the GET handlers deliberately lack [1](#0-0) . Since `authv2` only requires `AuthenticateByToken` or `AuthenticateBySession` [5](#0-4) , a `UserRoleView` session/API-token holder can call these GET endpoints successfully.

The same unmasked pattern exists for `ExternalInitiatorResource.AccessKey`/`OutgoingToken`, returned by the equally unguarded `GET /v2/external_initiators` route.

This breaks the implicit security assumption that "read-only"/View-role credentials should not expose secrets usable to impersonate the node's outbound webhook/EA calls or replay requests against systems trusting that token.

## Impact Explanation
`OutgoingToken` (bridges) and `AccessKey`/`OutgoingToken` (external initiators) are shared secrets used to authenticate the node's own outbound calls to external adapters/webhooks. Disclosure to a low-privileged authenticated user (View or Run role, which normally cannot create/modify bridges or initiators) lets that user impersonate the node toward the external adapter, replay/spoof authenticated requests, or use the token elsewhere it's trusted. This is a genuine secret-exfiltration issue (CWE-312 analog) mapping to the "key/secret exfiltration" impact category, reachable purely through the node's own API by an authenticated but under-privileged client — not requiring admin/edit access, host access, or a malicious peer.

## Likelihood Explanation
High and trivially repeatable: any node operator that provisions a View-only (or Run-only) API key/session for a lower-trust consumer inadvertently grants that consumer full read access to every bridge's and external initiator's outgoing secret, with a single unauthenticated-relative-to-secret-owner HTTP GET call, no rate limiting or special conditions beyond having any valid session/token.

## Recommendation
- Remove `OutgoingToken`/`AccessKey` from `BridgeResource`/`ExternalInitiatorResource` responses for callers below Edit/Admin role, or mask them (e.g., return only a boolean "is set" or a truncated suffix) as is already done conceptually for `IncomingToken`.
- Gate `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` with `auth.RequiresEditRole`, or add role-aware field redaction in the presenter layer.
- Apply equivalent redaction to the GraphQL `Bridge.outgoingToken` resolver.

## Proof of Concept
1. As an Admin, create a Viewer-role API token (`clsessions.UserRoleView`) and create a bridge via `POST /v2/bridge_types {"name":"test","url":"https://ea.example.com"}`.
2. Using the Viewer-role token's `X-API-KEY`/`X-API-SECRET` headers, call `GET /v2/bridge_types/test`.
3. Observe the JSON response body contains `"outgoingToken":"<plaintext secret>"`, even though the caller's role is rejected by `auth.RequiresEditRole` used on the mutating routes for the same resource.
4. Repeat with `GET /v2/external_initiators` after creating an external initiator, observing `accessKey`/`outgoingToken` returned in plaintext to the same Viewer-role caller.

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)

			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
