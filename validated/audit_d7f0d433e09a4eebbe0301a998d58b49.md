### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The shop identity that the handler receives and acts upon — `request.shop`, taken from the `X-Shopify-Shop-Domain` header — is never included in the signed material. Any party that can obtain one genuinely-signed webhook for the app (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will report the webhook as valid and hand the handler a spoofed tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body — headers are explicitly excluded from the signed bytes: [2](#0-1) 

`shop` is read straight from the `shop-domain` header with no cross-check against anything in the HMAC-covered payload: [3](#0-2) 

`Registry.process` validates only the HMAC, then forwards `request.shop` directly to the application handler as the authoritative tenant identifier for that event: [4](#0-3) 

The equality the gem is supposed to guarantee is:
`shop-domain header used to route/attribute the event == shop that the signed body actually originated from`

But the HMAC only proves: `raw_body was signed with Context.api_secret_key`. It proves nothing about which shop the header claims the body came from. Since Shopify signs webhooks with the app's single `api_secret_key` (shared across every shop that installs the app), a valid signature for shop A's webhook remains a valid signature no matter what shop-domain header is attached to the same body when replayed. This is exactly the "field acted on but not covered by the HMAC" identity-binding gap called out in scope.

### Impact Explanation
An unprivileged party who legitimately installs the app on their own (attacker-controlled) shop will receive genuinely-signed webhooks for that shop. By capturing one such raw body + `X-Shopify-Hmac-Sha256` value and re-POSTing it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header (naming a victim shop that also uses the app), the request passes `HmacValidator.validate` unchanged, and `Registry.process` invokes the handler with `WebhookMetadata.shop` set to the victim's domain while the body content is attacker-controlled. Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's records to update (the standard integration pattern demonstrated in this gem's own tests) will apply attacker-supplied webhook data to another merchant's tenant — i.e., cross-tenant data injection/corruption using only the credentials of a legitimately-onboarded low-privilege attacker shop.

### Likelihood Explanation
Requires only installing the app as a normal customer (no `api_secret_key`, access token, or privileged account needed) and capturing one of your own app's inbound webhook deliveries, which is trivial to log. Forging the header on replay is a one-line HTTP change. This is fully reachable through the gem's documented, intended processing path (`Registry.process`), not by the host app ignoring the gem's API.

### Recommendation
Include the shop (and ideally topic/webhook-id) in the HMAC-verified material, or otherwise cryptographically bind `shop-domain` to the signed payload before it is trusted, e.g. by having `Request#to_signable_string` incorporate the shop/topic headers, or by requiring/verifying a per-shop secret/session lookup keyed off an already-authenticated identifier rather than the raw header value.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, receives a legitimate webhook:
   - Body: `{"id":123,"event":"orders/create"}`
   - Header `X-Shopify-Hmac-Sha256: <valid signature over that body using app secret>`
   - Header `X-Shopify-Shop-Domain: attacker.myshopify.com`
2. Attacker replays the identical body and HMAC header to the app's webhook endpoint, but changes:
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` runs:
   - `Utils::HmacValidator.validate(request)` succeeds (per [1](#0-0) ) because it only checks the unchanged raw body.
   - The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` (per [5](#0-4) ).
4. Any handler that trusts `data.shop` to select the tenant record now mutates/creates data under `victim.myshopify.com` using attacker-controlled body content.
