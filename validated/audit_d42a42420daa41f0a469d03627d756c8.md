## Title
Webhook `shop` (and topic/api-version) Identity Not Bound to HMAC Signature — Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the shop identity used to route and process the webhook is taken from an unsigned HTTP header. This breaks the binding `hmac == HMAC(secret, shop || body)` down to `hmac == HMAC(secret, body)`, letting an attacker who controls a valid `(raw_body, hmac)` pair for one tenant replay it while claiming to be a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are pulled straight from HTTP headers, entirely outside of what is HMAC-verified: [2](#0-1) 

`Utils::HmacValidator.validate` only ever signs/compares `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` that is handed to the app's own webhook handler — the value the app uses to attribute the event to a specific merchant/tenant: [4](#0-3) 

Because the shared secret (`client_secret`) used for HMAC is per-app, not per-shop, any shop that has installed the app can legitimately receive a real, validly-signed `(raw_body, hmac)` pair from Shopify for its own webhook events. An attacker who owns/controls such a shop can capture that pair and replay it to the app's webhook endpoint while overriding the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim shop. `HmacValidator.validate` will still succeed because it only checks the (unmodified) body against the same shared secret, and the code has no check binding the claimed `shop` header to the signature. This exactly matches the "field acted on but not covered by the HMAC" class of bug from the reference report (there, `token1` balance was computed with the wrong ordering relative to what was charged; here, `shop` is trusted for routing/processing despite not being part of what is charged/verified in the HMAC).

### Impact Explanation
This is a cross-tenant data-confusion vector: the app's webhook handler (built on top of this gem) receives `WebhookMetadata#shop` claiming to be a different, victim shop than the one whose secret-signed payload actually produced the HMAC. Any app logic keyed off `shop` (e.g., updating per-shop records, redact/GDPR flows, billing, inventory sync) can be tricked into acting on/for the wrong tenant, since the gem provides no protection against a spoofed shop header once the body-only HMAC passes. This aligns with the "cross-tenant access" Critical impact bucket in scope.

### Likelihood Explanation
Exploitation requires the attacker to possess a shop that has installed the target app (to obtain a validly-signed webhook body/HMAC pair) and the ability to POST directly to the app's public webhook endpoint with custom headers — both are within reach of any unprivileged internet user who can install a free/dev app instance, no privileged credentials or access tokens are required. The gem performs no additional binding, so likelihood of a working replay is moderate-to-high once an attacker has any valid webhook sample.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the string that gets HMAC-verified, or otherwise cryptographically bind them to the signed payload, e.g. by having `to_signable_string` concatenate the shop domain header with the raw body before computing/verifying the digest, matching what Shopify's HMAC generation is documented to guarantee is tamper-evident. Alternatively, have `Registry.process` independently confirm the shop against a trusted source (such as a shop derived from a previously stored, session-bound webhook subscription) rather than trusting the raw header once only the body has been verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers any subscribed webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and processes the attacker's data as if it belonged to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
