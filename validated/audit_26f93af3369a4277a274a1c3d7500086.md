## Analysis

Investigation confirms a genuine identity-binding gap in the webhook processing path of this gem.

**The binding that should hold:** `hmac_verified(raw_body) == true` should imply `shop_header` (the tenant identity attached to that payload) is authentic for that specific body. In this gem, the HMAC only authenticates the *body bytes*; the `shop-domain` header used to attribute the webhook to a tenant is a completely separate, unauthenticated channel.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `#hmac` reads the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop` is read from a separate, unsigned header, with no cryptographic tie to the body or to the HMAC: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string` (i.e., the body), never the shop header: [4](#0-3) 

`Registry.process` performs exactly this check and then trusts `request.shop` to attribute the event to a tenant when building `WebhookMetadata` handed to the app's handler: [5](#0-4) 

So `HmacValidator.validate(request) == true` only proves "this body byte-string was signed with the app's secret at some point" — it says nothing about which shop it belongs to. The `shop` field that the handler acts on (to look up sessions, apply billing changes, GDPR data operations, etc.) is not covered by the signature at all.

### Exploitability without any secret

Any store that has legitimately installed the app (an ordinary, unprivileged merchant, not an app developer, and with no access to `api_secret_key`) can trigger their own store to generate a legitimate webhook (any topic they can cause, e.g. `orders/create`), which arrives at the app's endpoint with a valid `hmac-sha256` computed over that body using the app's shared secret. Since the app's webhook endpoint is reachable at a known, often documented, URL, that same merchant can then submit their own captured `(raw_body, hmac)` pair again to the same endpoint, this time with an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header value naming a different, victim tenant. `Utils::HmacValidator.validate` still passes (body unchanged, hmac unchanged), and `Registry.process` will invoke the app's handler with `shop: "victim-shop.myshopify.com"` attached to attacker-supplied/attacker-triggered event data — a cross-tenant identity spoof achieved purely with data an ordinary internet-facing merchant can generate themselves, no `api_secret_key` required.

### Title
Webhook shop identity is not bound to the HMAC-verified bytes, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates only the raw webhook body via HMAC (`to_signable_string` returns `@raw_body`), while the `shop` (tenant) attribute used downstream by `ShopifyAPI::Webhooks::Registry.process` to build `WebhookMetadata` is taken from a separate, unauthenticated header. The two are never cryptographically bound together.

### Finding Description
`HmacValidator.validate` verifies `hmac == HMAC(api_secret_key, raw_body)` [6](#0-5) , but the `shop` used to route/attribute the event [3](#0-2)  plays no part in that computation. `Registry.process` trusts this unverified `shop` field to construct the metadata handed to the app's webhook handler [7](#0-6) . Any actor able to obtain one valid `(raw_body, hmac)` pair for the shared app secret — trivially available to any merchant who has installed the app, since the same `api_secret_key` signs every tenant's webhooks — can replay that pair with a forged `shop-domain` header and have it accepted as belonging to a different tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: `hmac_valid(body) ⇒ shop_header authentic for body` does not hold. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up a stored session/access token for that shop, updating billing/subscription state, processing GDPR redact/data-request webhooks, or triggering per-shop business logic), this enables cross-tenant data corruption or an attacker forcing shop-scoped state changes attributed to a victim store — a cross-tenant access violation.

### Likelihood Explanation
Requires only an ordinary app installation by the attacker (no elevated privileges, no `api_secret_key`, no TLS interception) plus knowledge of the app's public webhook endpoint — a realistic and low-effort scenario for any SaaS-style multi-tenant Shopify app built on this gem.

### Recommendation
Bind the shop identity into the verified bytes, e.g. include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signable string, or independently verify that the resolved shop has an active session/install record consistent with the specific webhook delivery (Shopify also signs per-topic API version headers that could be cross-checked). At minimum, document and/or enforce that consumers must not treat the `shop` header as authenticated on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates an order) so Shopify POSTs a signed webhook to the app's endpoint: headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `B`.
3. Attacker (having full control of network requests to the app's public webhook URL) resends the exact same body `B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds.
5. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, processing attacker-controlled data as if it originated from the victim's store.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
