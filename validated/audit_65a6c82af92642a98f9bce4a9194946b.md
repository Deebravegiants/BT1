### Title
Caller-supplied `verifying_contract` overrides SDK-enforced contract binding in `IntentExecuter.signAndSendIntent` - (File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts)

### Summary
`signAndSendIntent` explicitly pins `verifying_contract` to the SDK's trusted `envConfig.contractID`, but then spreads the caller-supplied `...intentParams` *after* that assignment, letting a caller-supplied `verifying_contract` field silently overwrite the trusted value before the payload is signed.

### Finding Description
`signAndSendIntent` destructures its arguments and treats the rest as `intentParams`, typed as `Partial<Parameters<IntentPayloadFactory>[0]>`, i.e. `Partial<IntentPayload>` — which includes `verifying_contract`: [1](#0-0) 

The method builds the payload like this: [2](#0-1) 

The intent is that `verifying_contract` is a fixed, protocol-derived value (`this.envConfig.contractID`) that can never be influenced by the caller — it establishes which NEAR contract the signature is scoped to. However, because `...intentParams` is spread *after* `verifying_contract: verifyingContract` in the object literal, any `verifying_contract` key present in `intentParams` (which the public type signature explicitly allows, since `IIntentExecuter.signAndSendIntent`'s parameter type is `Parameters<IntentPayloadFactory>[0] & {...}` = `IntentPayload & {...}`) overwrites the trusted value: [3](#0-2) 

`defaultIntentPayloadFactory` itself performs the same unguarded merge — spreading `...params` (which can contain `verifying_contract`) at the end of its returned object, after the explicit `verifying_contract` field it received: [4](#0-3) 

The resulting `intentPayload` — now containing an attacker/caller-controlled `verifying_contract` — is passed directly to `this.intentSigner.signIntent(intentPayload)` with no re-validation that `verifying_contract === envConfig.contractID`: [5](#0-4) 

This is the direct structural analog of the Velocity.js bug class: a downstream sink (`Function` constructor / here, `intentSigner.signIntent`) trusts a field that was supposed to be constrained by an earlier "blocking" assignment, but a later unfiltered merge/spread re-introduces attacker influence over that field. The equality that should hold — "the contract that receives the signed payload equals the contract configured in `envConfig`" — is broken.

### Impact Explanation
If any caller-facing code path (e.g. an integrator's API surface that forwards user-supplied fields into `signAndSendIntent`, or any wrapper that spreads request data as `intentParams`) allows `verifying_contract` to reach this call, the user's NEP-413/ERC-191 signature will be produced for a contract ID chosen by the caller rather than the SDK's `intents.near` (or configured environment contract). This is a "signature bound to the wrong contract" defect (High impact per the rubric): the signed multiPayload would validate against an unintended verifying contract, potentially enabling the intent to be replayed/accepted by a different contract than the one the signer believed they were authorizing, or causing the signature to be rejected/misdirected during settlement.

### Likelihood Explanation
The vulnerability is reachable purely through the public, documented API surface — `IIntentExecuter.signAndSendIntent` and the exported `IntentPayloadFactory`/`IntentPayload` types explicitly include `verifying_contract` as a settable field in the parameter type, so there is no type-level barrier preventing it from being passed. Exploitation likelihood depends on whether some caller of `signAndSendIntent` forwards an object containing a `verifying_contract` key (e.g., a naive spread of user-supplied JSON) — this is plausible for any integrator building generic "sign this JSON payload" flows around the SDK, since the type system does not flag it as disallowed.

### Recommendation
- In `signAndSendIntent`, strip/omit `verifying_contract` from `intentParams` before merging, or explicitly re-assert `verifying_contract: verifyingContract` *after* spreading `...intentParams` so the trusted value always wins.
- Apply the same fix in `defaultIntentPayloadFactory`: place the explicit `verifying_contract` assignment after `...params` in the returned object, not before.
- Tighten `IIntentExecuter.signAndSendIntent`'s parameter type to `Omit<Parameters<IntentPayloadFactory>[0], "verifying_contract">` (and similarly for other SDK-enforced fields like `nonce`) so callers cannot even type-check code that attempts to override protocol-controlled fields.

```typescript
export function defaultIntentPayloadFactory(
	salt: Salt,
	{
		intents,
		verifying_contract,
		...params
	}: Partial<IntentPayload> & Pick<IntentPayload, "verifying_contract">,
): IntentPayload {
	// remove `undefined` properties
	params = Object.fromEntries(
		Object.entries(params).filter(([, value]) => value !== undefined),
	);

	const deadline =
		params.deadline != null
			? new Date(params.deadline)
			: new Date(Date.now() + DEFAULT_DEADLINE_MS);
	const nonceDeadline = new Date(
		deadline.getTime() + DEFAULT_NONCE_DEADLINE_OFFSET_MS,
	);

	return {
		verifying_contract,
		deadline: deadline.toISOString(),
		nonce: VersionedNonceBuilder.encodeNonce(salt, nonceDeadline),
		intents: intents == null ? [] : intents,
		signer_id: undefined, // or you can specify intent user id
		...params,
	};
```
