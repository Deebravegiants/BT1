Based on the analysis, I found a valid identity-binding vulnerability in the webhook processing flow.

### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook data spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` header as the tenant identity passed to the handler. Because the shop-domain header is never included in the signed material, any party capable of obtaining one genuine, validly-signed webhook payload for the app (e.g., an unprivileged merchant with the app installed on their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process the data as if it originated from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor used for tenant identification is read straight from an HTTP header, with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `to_signable_string`, i.e., the raw body, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding the library implicitly promises to callers is: `shop value delivered to the handler == shop that Shopify authenticated via the signature`. Because the HMAC only covers the body, this equality does not hold — `shop-domain` header is fully attacker-controllable while `hmac` remains valid for any request carrying the same body, regardless of which shop's header value is attached. Since the app's `api_secret_key` (used to sign webhooks) is a single value shared across all shops installing the app, a valid `(body, hmac)` pair obtained from one tenant's genuine webhook remains valid when replayed with a different `shop-domain` header.

### Impact Explanation
An unprivileged holder of one valid webhook delivery (any merchant/shop that has installed the app, which is not a privileged position) can cause the app's webhook handler to attribute foreign shop identity to data it controls, resulting in cross-tenant confusion: the app may write, associate, or act upon another merchant's tenant record using attacker-supplied body content that only passed integrity validation for the *body*, not for the *shop* it's claimed to belong to. This matches the "cross-tenant access" criterion for Critical severity, since the trust boundary between tenants is what the HMAC verification is meant to enforce and it fails to bind the `shop` field.

### Likelihood Explanation
Exploitation requires only:
1. Being a legitimate (unprivileged) merchant with the target app installed, sufficient to receive at least one real webhook delivery with a valid HMAC.
2. Replaying that same raw body with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to the app's public webhook endpoint.

No access to `api_secret_key`, access tokens, or any privileged credential is required, and the header name/format is documented/public. This is straightforward to perform against any app built on this library that trusts `WebhookMetadata#shop` for tenant-scoped operations, which is the documented usage pattern.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the `shop-domain` header to the verified body (e.g., have `Request#to_signable_string` incorporate the shop header, and have `Registry.process` re-verify that the header used for handler dispatch is the same one covered by the signature). At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is not authenticated by the HMAC check and instruct integrators to cross-reference it against their own list of installed/authorized shops before trusting it for tenant-scoped writes.

### Proof of Concept
1. App has two shops installed: `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim).
2. Attacker's own store triggers a webhook event; Shopify delivers:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw body, using app's shared api_secret_key>
   x-shopify-shop-domain: shop-a.myshopify.com
   Body: {"id": 1, "note": "attacker-controlled content"}
   ```
3. Attacker captures this exact `(body, hmac)` pair and resends it directly to the app's webhook endpoint, changing only the header:
   ```
   x-shopify-shop-domain: shop-b.myshopify.com
   ```
4. `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see [5](#0-4) .
5. `Registry.process` builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the attacker-controlled body, dispatching it to the handler as if it were genuine data from the victim shop — see [6](#0-5) .
