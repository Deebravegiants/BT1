### Title
Unserialized read-modify-write in `ConnectedOrigins` allows a lost-update race that can revert `untrust`/`disconnect` and preserve unauthorized dApp origin access - (File: features/connected-origins/module/connections.js)

### Summary
`ConnectedOrigins` exposes `add`, `untrust`, `connect`, `disconnect`, `setAutoApprove`, `setFavorite`, and `updateConnection` — all reachable directly from the public `connectedOriginsApi` used by the web3 RPC bridge [1](#0-0)  — and every one of them performs a non-atomic "read snapshot → compute new value → write back full array" sequence against the same shared `connectedOriginsAtom`, with no queue, lock, or compare-and-swap protecting the critical section, analogous to the `Option` contract's cache/balance TOCTOU pattern described in the report.

### Finding Description
`#setAttributes`, `connect`, `disconnect`, `untrust`, and `#addNewItem` each independently call `#getOrigin`/`#getData` (a read of `connectedOriginsAtom`), compute a new array/object based on that snapshot, and later call `#setData`, which itself re-reads current data only inside `#setAttributes` but still overwrites the entire `connectedOrigins` array based on data captured earlier in the call: [2](#0-1) 

For example, `connect` reads `value.activeConnections`, computes `newConnections`, then calls `#setAttributes`, which re-fetches `data` and writes `newData` (a full-array `set`) to `connectedOriginsAtom`: [3](#0-2) 

There is no `makeConcurrent`/queue mechanism (unlike, e.g., the `balances` module which explicitly serializes writes via `#pushIntoSharedQueue = makeConcurrent(...)` [4](#0-3) ). Because `connectedOriginsAtom.set` simply replaces the whole array rather than doing an atomic merge, two concurrent calls that both read the old array before either write will race: whichever call's `#setData` resolves last "wins" and its stale snapshot of all *other* fields (including `activeConnections`, `trusted`, `autoApprove`) silently overwrites the effect of the other call.

Concretely: if a dApp origin sends two RPC calls back-to-back — e.g., `connect({id, origin})` (called on every provider connection) racing with `untrust({origin})` or `disconnect({id, origin})` (called when the user revokes access from the UI) — the read of both operations can occur before either write completes. If `connect`'s write lands after `untrust`'s, the origin/connection is silently restored to the connected-origins list even though the user just revoked it, because `connect`'s in-memory `newData`/`attributes` were computed from the pre-untrust snapshot and `#setAttributes` only re-checks `#getOrigin` for existence at the very start of its own call, not atomically with the write.

### Impact Explanation
`isTrusted`, `isAutoApprove`, and `getConnectedAccounts` — which gate whether a webpage origin can auto-connect and receive wallet account addresses without a fresh user approval popup — all read from the same `connectedOriginsAtom` state [5](#0-4) [6](#0-5) . A lost update that reinstates a previously-untrusted/disconnected origin (or fails to persist a revoked `autoApprove`/`trusted` flag) means a malicious or compromised website can retain silent, unauthorized access to the user's wallet addresses and auto-approved connections after the user believed they had disconnected/revoked it — an origin-isolation/authorization-bypass condition directly analogous to the funds-loss-via-lost-update pattern in the report (merged/overwritten state due to non-atomic read-then-write operations triggered by transaction/message ordering).

### Likelihood Explanation
Exploitability requires two `connectedOrigins` mutations to race in a narrow window — plausible in the browser-extension RPC bridge where a malicious page can fire multiple provider requests (e.g., repeated `connect`/`eth_requestAccounts` calls) in rapid succession while the user is simultaneously interacting with the UI to disconnect/untrust the site, or where the extension processes multiple concurrent messages from the same or different origins. This is a timing-dependent race rather than a guaranteed one-shot exploit, so likelihood is moderate: it depends on message scheduling/microtask ordering in the runtime, which an attacker-controlled page has some ability to influence (e.g., firing requests in tight loops around user actions), but it is not fully attacker-controlled compared to a blockchain miner controlling ordering.

### Recommendation
Serialize all mutating operations on `connectedOriginsAtom` through a single concurrency-limited queue (as already done in the `balances` module via `makeConcurrent`), or switch `#setData`/`#setAttributes` to perform an atomic compare-and-swap / functional `atom.set(current => ...)` update that recomputes from the latest state at write time rather than from an earlier snapshot, so that `connect`, `disconnect`, `untrust`, and `setAutoApprove` cannot lose each other's updates.

### Proof of Concept
Not independently executable from static analysis alone (requires instrumenting the in-memory/async storage atom to interleave two concurrent calls); the race is demonstrated structurally as follows:
1. Origin `evil.com` is trusted and connected: `activeConnections = [{id: 'A'}]`.
2. User clicks "Disconnect" in UI → `connectedOrigins.untrust({origin: 'evil.com'})` begins: reads `isTrusted` (true), then reads `data` (still shows evil.com trusted).
3. Concurrently, `evil.com`'s page script fires another provider `connect` request → `connectedOrigins.connect({id: 'B', origin: 'evil.com'})` begins: reads `value` (still shows evil.com trusted, `activeConnections: [{id:'A'}]`), computes `newConnections = [{id:'A'},{id:'B'}]`.
4. `untrust`'s `#setData(newData)` (evil.com removed) resolves first, writing the origin list without evil.com.
5. `connect`'s `#setAttributes` re-reads `#getOrigin({origin: 'evil.com'})` — if this re-read happens before step 4 completes, `item` is still found, and its subsequent `#setData(newData)` (which re-adds evil.com's full connection object with `activeConnections: [{id:'A'},{id:'B'}]`, `trusted: true`) overwrites the untrust, leaving `evil.com` connected and trusted despite the user's explicit disconnect action.   connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  disconnect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnections = activeConnections.filter((connection) => connection.id !== id)

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
