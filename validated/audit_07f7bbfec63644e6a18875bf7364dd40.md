### Title
Webhook `shop-domain` (and topic/webhook-id) header is not covered by the HMAC signature, allowing shop-spoofing/cross-tenant confusion on webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read directly from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header, which is never part of the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the body and then forwards the unverified `request.shop` to the app's handler as the tenant identifier.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac-sha256` header value: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, meaning the HMAC binds only the payload bytes to the app's secret — it does not bind the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and other header-derived fields) to build `WebhookMetadata` handed to the app's handler, with no cross-check that the shop is bound to the signed body: [3](#0-2) 

The identity binding that should hold is: `shop attributed to this event == shop whose secret produced the HMAC over this exact body`. Because the shop header is outside the signed material, this equality is never checked — the gem only proves "this body was signed with our secret," not "this body belongs to shop X." Any unprivileged actor who can obtain one genuinely-signed webhook body+HMAC pair (e.g., by triggering a webhook on their own store, which any merchant/developer can do without special credentials) can replay that exact body/HMAC pair to the target app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (it only checks the body), and the forged shop value flows unchecked into the app's business logic via `WebhookMetadata#shop`.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an app relying on `shopify_api`'s webhook verification to determine "which shop does this event belong to" can be made to attribute a webhook payload to the wrong merchant. Depending on how the host app uses `data.shop` (e.g., to look up/update per-tenant records, provision resources, or grant access), this enables cross-tenant data confusion/injection — one merchant's automatically-verified webhook can be relabeled as belonging to a different, victim shop.

### Likelihood Explanation
Exploitation requires no credentials, tokens, or privileged access — only the ability to receive one legitimately HMAC-signed webhook for any shop (trivial for any developer/merchant using the API) and the ability to POST arbitrary headers to the target app's public webhook endpoint, which by design accepts unauthenticated inbound HTTP requests from "Shopify." The gem provides no additional binding to prevent this replay-with-relabeled-shop attack.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-verified signable material, or otherwise cryptographically bind the shop identity to the signed payload before it is exposed via `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated header data and must not be trusted by host applications without additional verification (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker owns/operates their own Shopify dev store `attacker-shop.myshopify.com` and configures a webhook (or app) so Shopify delivers a genuine webhook to an endpoint they control, capturing the exact `raw_body` and its valid `X-Shopify-Hmac-Sha256` value (computed by Shopify using the target app's `client_secret`, since the same app is installed on the attacker's own store).
2. Attacker replays the identical `raw_body` + `X-Shopify-Hmac-Sha256` to the victim app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds. [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was actually generated by/for `attacker-shop.myshopify.com`, and processes it as if it legitimately belongs to the victim shop.
