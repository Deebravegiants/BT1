### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop spoofing on otherwise-valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unrelated `shop-domain` header as the tenant identity handed to the app's handler. Because the header is not part of the signed material, an attacker who can obtain one legitimately-signed body/HMAC pair (e.g., by installing the target app on a shop they control) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value, causing the request to be processed as if it belongs to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) .

`Registry.process` performs exactly one authentication check — the HMAC over the body — and then unconditionally forwards `request.shop` (and other unauthenticated headers) into `WebhookMetadata` for the handler to act on: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes and compares a signature over `to_signable_string` (the raw body), never over headers such as `shop`, `topic`, or `webhook-id`: [4](#0-3) 

This breaks the intended identity binding: `shop header used by the handler == shop the HMAC actually authenticates`. In reality the HMAC authenticates only "this body was produced/signed by Shopify for *some* installation of this app using this `client_secret`" — it says nothing about which shop the body is for. An attacker who has legitimate access to their own shop's install of the app (any user can install an app on a shop they control, e.g. a free development store) can:
1. Trigger a real webhook delivery for their own shop (any topic, e.g. `products/update`), capturing the raw body and the valid `X-Shopify-Hmac-Sha256` value Shopify computed with the real `client_secret`.
2. Replay that exact body + HMAC to the app's webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to the victim shop's domain (and optionally the `webhook-id`/`api-version` headers, which are equally unauthenticated).
3. `HmacValidator.validate` succeeds (body and HMAC still match), so `Registry.process` calls the registered handler with `WebhookMetadata.shop` set to the victim's domain.

If the host application scopes any effect of the webhook handler by `data.shop` (e.g., writing/looking up records, invalidating caches, triggering resyncs, revoking data, uninstall/GDPR-style side effects) keyed by that shop value, the attacker has crossed the tenant boundary using only a signature that was never meant to vouch for shop identity.

### Impact Explanation
This crosses a tenant boundary using a validly-verified (per this gem's own check) request whose shop attribution is entirely attacker-controlled — matching the "cross-tenant access" criterion. The gem's documented webhook processing API (`Registry.add_registration` / `Registry.process` / `WebhookMetadata`) is exactly what is exploited; no misuse of undocumented behavior by the host app is required, since the gem itself hands out an unauthenticated `shop` field as if it were verified.

### Likelihood Explanation
Requires only an unprivileged attacker capable of installing the target app on a shop they control (trivial, e.g., a free Shopify dev/partner store) to harvest one legitimate body+HMAC pair per topic of interest, then replaying it with a forged `shop-domain` header — no access to `client_secret`, access tokens, or any privileged account is needed.

### Recommendation
Bind the shop identity into the signed material actually verified, or verify it out-of-band against a trusted source before trusting `request.shop`:
- Reject/flag webhook processing where the shop header cannot be independently corroborated (e.g., cross-check `request.shop` against the shop associated with the resource IDs in `parsed_body`, or require callers to pass an expected `shop`/session and compare).
- At minimum, document prominently in `WebhookMetadata`/`Registry.process` that `shop` is unauthenticated and must not be used for tenant-scoped side effects without additional verification, and consider including the shop domain in the HMAC-covered signable string if a future webhook format allows it.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `products/update`). Capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify (computed as `HMAC-SHA256(client_secret, B)`).
2. Send a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` and any desired `X-Shopify-Webhook-Id`/`X-Shopify-Topic`.
3. In the gem:
   ```ruby
   request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {
     "x-shopify-hmac-sha256" => H,
     "x-shopify-topic" => "products/update",
     "x-shopify-shop-domain" => "victim.myshopify.com",
   })
   ShopifyAPI::Webhooks::Registry.process(request)
   ```
   `Utils::HmacValidator.validate(request)` returns `true` (it only checks `B` against `H`), and the registered handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the body/content actually originated from the attacker's own shop. [3](#0-2)
