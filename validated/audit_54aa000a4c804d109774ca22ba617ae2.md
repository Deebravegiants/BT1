### Title
Missing issuer (`iss`) binding check in `JwtPayload` allows non-admin session tokens (e.g. checkout extension tokens) to be used for OAuth Token Exchange - (File: `lib/shopify_api/auth/jwt_payload.rb`, `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::JwtPayload` validates only that a JWT's `aud` claim equals the app's `api_key` [1](#0-0) . It never checks that the token's `iss` claim identifies it as an **admin** session token before the token is trusted as a source of the `shop` identity. The `admin_session_token?` predicate exists but is only used internally to gate `shopify_user_id`, never to reject non-admin tokens at construction time [2](#0-1) . As shown by the gem's own test fixtures, Shopify issues JWTs with the exact same `aud` (client id) but a different `iss`/`dest` shape for checkout UI extensions (`iss: ".../checkouts"`, `sub: "gid://shopify/Customer/..."`) as for admin App Bridge sessions (`iss: ".../admin"`) [3](#0-2) . Both token shapes pass `JwtPayload.new` identically.

`Auth::TokenExchange.exchange_token` takes this unrestricted `shop` value (`jwt_payload.shop`, derived from the raw `dest` claim) and uses it, without any additional call to `Utils::ShopValidator.sanitize!`, to build the session and HTTP request that sends the app's `client_id`/`client_secret` to `https://{shop}/admin/oauth/access_token` in exchange for an access token [4](#0-3) . Every other credential-issuing method in the same file/module (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the shop value [5](#0-4) [6](#0-5) [7](#0-6) , but `exchange_token` is the exception — it trusts the JWT's `dest` claim directly.

### Finding Description
The identity binding that should hold is: `session_token.iss (session context) == "admin session"` before that token's `dest` claim is trusted as the tenant identity for a token-exchange request carrying the app's `client_secret`. Instead the gem checks only `aud == api_key`, so:

- Before request: `token.aud == api_key` (checked) AND `token.iss ends_with "/admin"` (NOT checked).
- After request: `dest_shop` (from unchecked `dest`) is used as `session.shop` and as the host that receives `client_id` + `client_secret` in `TokenExchange.exchange_token`.

Because the same `client_secret` is used by Shopify to sign both admin session tokens and checkout/other extension session tokens (as demonstrated by the gem's own fixtures), any code path that hands a non-admin, but validly-signed, session token to `exchange_token` will pass `JwtPayload` validation and proceed to request an offline/online admin access token scoped to the `dest_shop` embedded in that token.

### Impact Explanation
If an app (or a compromised/careless part of the host application) ever forwards a non-admin session token — such as one obtained through a checkout UI extension, which is delivered into the customer's browser and is thus attacker/customer-observable — into `TokenExchange.exchange_token`, the gem does not block it. This use of an unprivileged, customer-scoped identity token to mint a full-privilege offline/online admin access token constitutes a scope/authentication boundary bypass consistent with the report's "High" impact bucket. The root cause is entirely within this gem's own validation code (`JwtPayload#initialize`), independent of any Shopify server-side behavior.

### Likelihood Explanation
This requires either app code error (passing the wrong token to `exchange_token`) or an attacker being able to influence which token gets exchanged, since the token must still be signed with the app's `client_secret`. This is a real gap in the library's defense-in-depth: the gem promises to validate "the session token" for token exchange but does not enforce which *type* of session token is acceptable, unlike its sibling methods, which do apply `ShopValidator.sanitize!`. Whether Shopify's backend independently rejects non-admin subject tokens for the `token-exchange` grant is unknown from this codebase alone, so the ultimate exploitability partly depends on server-side behavior outside this gem — this is the main uncertainty in the assessment.

### Recommendation
In `JwtPayload#initialize`, reject tokens where `admin_session_token?` is false (i.e., enforce `iss.end_with?("/admin")`) before exposing `shop`/`sub` for use in credential-issuing flows, or add an explicit check in `TokenExchange.exchange_token` requiring `jwt_payload` to be an admin session token before proceeding, mirroring the `Utils::ShopValidator.sanitize!` pattern used by the other credential-granting methods in the same module.

### Proof of Concept
1. Obtain a validly-signed checkout UI extension session token for a shop (issued by Shopify to the customer's browser context), shaped as: `{ iss: "https://shop.myshopify.io/checkouts", dest: "shop.myshopify.io", aud: <app client_id>, sub: "gid://shopify/Customer/123" }`, matching the gem's own `@checkout_ui_extension_jwt_payload` fixture [8](#0-7) .
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: checkout_token, requested_token_type: OFFLINE_ACCESS_TOKEN)`.
3. `JwtPayload.new(checkout_token)` succeeds because only `aud == Context.api_key` is checked [1](#0-0) .
4. `dest_shop` is taken unchecked and used to build a request sending `client_id`/`client_secret` to `https://shop.myshopify.io/admin/oauth/access_token` requesting an offline admin access token [9](#0-8) .
