### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` identifier used by the application to attribute the webhook to a tenant is read from an HTTP header that is never part of the signed material. Because the app's single `client_secret`/`api_secret_key` is shared across every shop that has installed the app, any merchant who can trigger a legitimately-signed webhook for their own store can replay that same body+HMAC pair to the app's endpoint while substituting a different `shopify-shop-domain` header, and `HmacValidator.validate` will still accept it.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `to_signable_string` returns only `@raw_body` — the header is completely excluded from the signed payload.

`Utils::HmacValidator.validate` verifies exactly (and only) `to_signable_string` against the computed HMAC: [2](#0-1) 

`Webhooks::Registry.process` then trusts `request.shop` directly and hands it to the handler as the tenant identifier without any additional binding to the verified bytes: [3](#0-2) 

This is the exact break-of-identity-binding pattern the review targets: **the field acted on (`shop`, used to route/attribute the webhook to a tenant) is not covered by the HMAC that is supposed to authenticate the message.** The gem's own OAuth callback code shows the correct pattern was known and applied elsewhere — `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed string: [4](#0-3) 
The webhook `Request` class does not follow this same discipline, creating the asymmetry.

Because Shopify signs *all* webhooks for a given app installation with the app's single `client_secret` (there is no per-shop secret), any shop that installs the app is a valid HMAC oracle: it can receive a real webhook (body + `hmac-sha256` header) for an event in its own store, computed with the shared app secret, and forward/replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` only re-hashes `raw_body`, so verification passes, and `WebhookMetadata.shop` will be the attacker-chosen victim domain rather than the shop that actually produced the signed bytes.

### Impact Explanation
This lets an unprivileged actor (any merchant who has installed the target app — i.e., an "unprivileged internet user" relative to other tenants) cause the app to process attacker-supplied webhook data as if it originated from a different, victim merchant's store. Depending on how the host app keys its data/session lookups off `WebhookMetadata#shop` (which is the gem's documented, intended usage), this can lead to cross-tenant data corruption or cross-tenant action execution — a Critical-tier cross-tenant access issue per the rubric, achieved purely through the gem's webhook verification API and without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is meaningful in any multi-tenant app built on this gem: the attacker only needs to be a legitimate (even free/trial) install of the target app to obtain a validly-signed webhook body/HMAC pair for their own shop, then can trivially rewrite the shop-domain header when replaying the request to the app's public webhook endpoint. No secret material or privileged access is required — only observation of one's own webhook traffic and the ability to send an arbitrary HTTP request to the app's callback URL.

### Recommendation
Bind the shop identity into the verified material. Either:
- Include the `shopify-shop-domain` header value in `to_signable_string` (analogous to how `AuthQuery` includes `shop`), so any tampering with the header invalidates the HMAC, or
- Have `Registry.process`/`HmacValidator` independently authenticate the shop domain (e.g., cross-check against a known/allow-listed set of installed shops for the deployment) before trusting `request.shop`, rather than relying solely on body-only HMAC validation.

### Proof of Concept
1. App "MyApp" is installed by both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `client_secret`.
2. Attacker triggers a real event (e.g., updates a product) in `attacker-shop.myshopify.com`; Shopify sends MyApp a webhook with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the HMAC value, then sends a new HTTP request to MyApp's webhook endpoint with the same body `B`, the same (valid) `shopify-hmac-sha256` header, but `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`to_signable_string`) — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing MyApp to treat attacker-controlled data as if it came from the victim's store.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
