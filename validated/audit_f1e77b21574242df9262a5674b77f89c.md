## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body alone and then hands the (unauthenticated) header-derived `shop` straight to the app's webhook handler as the tenant identifier, breaking the equality between "bytes covered by the HMAC" and "bytes trusted as the tenant identity."

### Finding Description
`Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never part of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., body integrity/authenticity against the app's `client_secret`) and then immediately trusts `request.shop` (a raw header value) to build the `WebhookMetadata` passed to the app's handler, with no cross-check that the signed body actually originated for that shop: [3](#0-2) 

The identity binding that should hold is: `shop header == shop that the signed body was generated for`. Because the HMAC only covers `raw_body`, this equality is never enforced by the library. Any two webhook deliveries with identical bodies (e.g., empty-body webhooks like `app/uninstalled` acknowledgements, or any two deliveries with coincidentally/deliberately identical payloads) will produce the exact same HMAC regardless of which shop they originated from, since the app's `client_secret` is shared across all shops/tenants. An attacker who controls their own shop installation can capture a legitimately-signed `(raw_body, hmac)` pair from Shopify (e.g., a webhook fired for their own store) and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks `raw_body` against the secret, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` provides no library-level guarantee that the `shop` value handed to the app handler was actually authenticated as part of the signed request. For any host application that relies on the gem's HMAC validation as authentication of the whole webhook (including which shop it's for) — which is the natural reading of `Registry.process` raising `InvalidWebhookError` "unless HMAC valid" before dispatch — this allows attacker-controlled cross-tenant attribution of webhook events, matching the Critical category of "cross-tenant access."

### Likelihood Explanation
Exploitability requires the attacker to have their own legitimate app installation (to receive real, validly-signed webhook deliveries) and the ability to replay an HTTP POST to the app's public webhook endpoint with a modified header — both are unprivileged-internet-user-level actions given a merchant account, no `client_secret` or victim credentials needed. The main constraint is finding/crafting a body whose content is either irrelevant to the exploit (e.g., empty-body compliance/system webhooks) or identical across shops.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC-verified signable string, or otherwise have `Registry.process`/`HmacValidator` explicitly bind the verified body to the specific shop header before constructing `WebhookMetadata`, so the header used for tenant routing cannot diverge from what was authenticated.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook with an empty/known body (e.g., a mandatory compliance webhook that Shopify sends with `{}`), capturing the valid `X-Shopify-Hmac-Sha256` header for that raw body.
2. Attacker POSTs the same raw body and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only compares the HMAC of the raw body against the app's secret (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:13-22`).
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim.myshopify.com"`, even though Shopify never signed anything tying this payload to that shop. [4](#0-3)
