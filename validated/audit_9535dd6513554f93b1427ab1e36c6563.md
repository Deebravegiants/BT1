### Title
Panic due to unset `compute_usage` on the `TxVerdict::DepositFailed` transaction-processing path - (File: `runtime/runtime/src/lib.rs`)

### Summary
`process_transaction` unconditionally calls `.expect("`process_transaction` must populate compute usage")` on `outcome.outcome.compute_usage` for every transaction outcome it builds, assuming this field is always `Some`. [1](#0-0) 

### Finding Description
`ExecutionOutcome.compute_usage` is an `Option<Compute>` marked `#[borsh(skip)]`, whose default (via `SmartDefault`) is `None` unless explicitly set. [2](#0-1) 

Inside the transaction-processing loop, only the `TxVerdict::Success` branch explicitly sets `compute_usage: Some(result.compute_burnt)` on the outcome it constructs. [3](#0-2) 

The `TxVerdict::DepositFailed` branch instead builds its outcome via `ExecutionOutcomeWithId::failed_with_gas_burnt(tx, error, cost.gas_burnt, cost.burnt_amount)` — a helper distinct from the `Success` path that does not take a compute value as a parameter, and (unlike the `Success` and plain-`Failed` branches) does **not** `continue` afterward; execution falls through to the shared epilogue that performs the `.expect(...)` on `compute_usage`. [4](#0-3) [5](#0-4) 

This mirrors the TON Gateway bug class exactly: a downstream consumer (`exitCodeFromTx` in the TON case, the `.expect()` in nearcore) assumes a variant/field is always populated (`TrPhaseComputeVm` / `compute_usage: Some(...)`), but one code path (`compute.skipped` / `DepositFailed`) can legitimately produce the "unpopulated" state, and the consumer has no fallback — it panics instead of handling the case explicitly.

### Impact Explanation
If `failed_with_gas_burnt` does not populate `compute_usage`, any submitted gas-key transaction that fails the deposit check inside `verify_and_charge_gas_key_tx_ephemeral` (a condition reachable by an ordinary, unprivileged account) would drive the `DepositFailed` branch and trigger the `.expect()` panic when applying the chunk. Because this runs inside chunk application (`process_transaction`), a panic here would crash/abort the node applying the chunk — a chain-halting condition for that shard's validators, not merely a client-side crash as in the TON analog.

### Likelihood Explanation
This path can be triggered by any unprivileged account submitting a gas-key transaction crafted to fail the deposit check (e.g., insufficient balance/allowance on the gas key) — no privileged or validator-only access is required, matching the "malicious low-value message" trigger pattern in the original TON report. The exact trigger condition and whether `failed_with_gas_burnt` truly omits setting `compute_usage` could not be fully confirmed from the index within the available search budget, since the body of `ExecutionOutcomeWithId::failed_with_gas_burnt` in `core/primitives/src/transaction.rs` was not retrieved in full.

### Recommendation
Ensure `ExecutionOutcomeWithId::failed_with_gas_burnt` (and any other outcome constructor used before reaching the `.expect()` at `runtime/runtime/src/lib.rs:2259-2262`) always explicitly sets `compute_usage: Some(...)`, or replace the `.expect()` with a safe default (e.g., treat gas_burnt as compute usage, or `unwrap_or_default()`) so a missing value degrades gracefully instead of panicking.

### Proof of Concept
Not executed — this analysis is based on static code review of `runtime/runtime/src/lib.rs` (lines 2159-2264) and `core/primitives/src/transaction.rs` (lines 571-659). Confirming exploitability requires inspecting the full implementation of `ExecutionOutcomeWithId::failed_with_gas_burnt` and the conditions under which `TxVerdict::DepositFailed` is returned, which should be validated with a background Devin session (full file access) before treating this as confirmed.
