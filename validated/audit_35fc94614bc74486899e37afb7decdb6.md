### Title
Newly-delegated stake captures previously-accumulated `pending_delegator_rewards` block revenue, effectively stealing block-revenue owed to no one / diluting it - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward` distributes a vote account's `pending_delegator_rewards` (SIMD‑0123 block‑revenue‑sharing balance) to stake delegators in proportion to their stake relative to `total_active_stake` for the **current** state of `pending_delegator_rewards`, without any accounting for how long each delegation has actually been active while that revenue accrued. Because `pending_delegator_rewards` can also be topped up by *anyone* via the permissionless `DepositDelegatorRewards` vote instruction, a staker who delegates to a vote account only after a large, unclaimed `pending_delegator_rewards` balance has built up can claim a pro‑rata share of revenue that accrued before their stake existed — the exact "first depositor captures pre‑existing yield" bug class described in the report.

### Finding Description
`calculate_block_reward` reads the vote account's live `pending_delegator_rewards` value and divides it among stake delegations using the stake's share of `total_active_stake` (the previous epoch's delegated-stake snapshot): [1](#0-0) 

`pending_delegator_rewards` is a single running balance on the vote account (`VoteStateV4::pending_delegator_rewards`) that can be incremented in two ways:
1. Automatically, as block revenue accrues from leader-slot fee collection while the validator identity is leader.
2. Permissionlessly, via the `DepositDelegatorRewards` vote instruction, which lets *any* signer transfer lamports into the vote account and add to `pending_delegator_rewards` with no authorization check against the vote account's authorities: [2](#0-1) [3](#0-2) 

The balance is not segmented by "when it accrued" or "who was staked when it accrued" — it is a single pot. When rewards are computed at the epoch boundary, `calculate_block_reward` splits the *entire current* `pending_delegator_rewards` pot proportionally by `stake / total_active_stake`, where `stake` is each delegation's effective (warmed-up) stake for `rewarded_epoch`: [4](#0-3) 

This mirrors the Tranche bug exactly: the Tranche's `realisedLiquidityOf[tranche]` (interest pot) accrues before any depositor exists and is claimable in full by whoever holds shares at redemption time; here, the vote account's `pending_delegator_rewards` pot accrues (via leader block revenue or a permissionless deposit) irrespective of who is delegated, and whoever is delegated (with active/warmed-up stake) at the reward epoch boundary claims a share of the *entire accumulated pot*, including the portion that accrued before their delegation existed or before it finished warm-up. There is no tracking of a "rewards observed at time of delegation" checkpoint analogous to `credits_observed` for inflation rewards — `redeem_delegation_rewards`/`calculate_alpenglow_points` do use a `credits_observed` checkpoint for the **inflation** portion of rewards, but `calculate_block_reward` for the **block-revenue** portion has no equivalent checkpoint; it uses the raw, un-checkpointed `pending_delegator_rewards` value.

### Impact Explanation
A staker (or a validator operator colluding with a staker) can:
1. Let block revenue (or a permissionless `DepositDelegatorRewards` deposit from an unrelated party) accumulate a large `pending_delegator_rewards` balance on a vote account with little or no delegated stake.
2. Delegate a large stake to that vote account and wait for it to warm up (one epoch under normal warmup rules).
3. At the next reward-epoch boundary, receive a share of `pending_delegator_rewards` proportional to their stake — including the portion of the pot that accumulated entirely before their delegation existed.

This results in value being redirected to a party who did not "earn" it through having stake at risk while the revenue accrued, at the expense of stakers who were delegated during that period and whose share is diluted, or at the expense of a depositor who funded the vote account via `DepositDelegatorRewards` expecting existing delegators to receive it. This is a concrete misallocation of value in the fee/rewards accounting path.

### Likelihood Explanation
Medium. It requires: (a) block-revenue-sharing feature active, (b) an interval during which a vote account accumulates `pending_delegator_rewards` with disproportionately low total_active_stake (either naturally low delegated stake, or via a permissionless `DepositDelegatorRewards` deposit which requires no special privilege and is trivially triggerable by anyone), and (c) a delegation timed to warm up before the next reward distribution. All of these are attacker-controllable using only ordinary, unprivileged transactions (delegate stake, call `DepositDelegatorRewards`), matching the "unprivileged-user reachable" scope for bank commit / fee accounting paths.

### Recommendation
Track `pending_delegator_rewards` accrual against the stake that was actually active while it accrued, analogous to the `credits_observed` checkpoint used for inflation rewards. For example, checkpoint the `pending_delegator_rewards` balance (or an equivalent "block-revenue-per-stake" accumulator) each time the active-stake set for the vote account changes materially, or accrue/distribute block revenue continuously per active-stake-epoch rather than as a lump-sum pot split by point-in-time stake proportions. At minimum, gate the permissionless `DepositDelegatorRewards` instruction so it cannot inject rewards attributable to stake that wasn't present when the underlying revenue was earned, or require the deposit to be attributed only to delegators active at deposit time.

### Proof of Concept
1. Validator `V` produces blocks as leader while having a small/zero delegated stake; `pending_delegator_rewards` accumulates block revenue over several epochs (or attacker calls `DepositDelegatorRewards` with a large lamport amount, permissionless per `deposit_delegator_rewards`) [2](#0-1) .
2. Attacker delegates a large stake to `V`'s vote account and waits for warm-up (`delegation_effective_stake`/`calculate_activated_stake`) so it counts in `total_active_stake` for the next `rewarded_epoch` [5](#0-4) .
3. At the next epoch boundary, `calculate_stake_rewards_and_commissions` calls `calculate_block_reward` for the attacker's delegation, which computes `pending_delegator_rewards * stake / total_active_stake`, granting the attacker a share of the entire pre-existing pot [6](#0-5) .
4. Existing unit tests confirm the mechanics of this proportional, unattributed split (`test_calculate_block_reward_specific`) but do not test for/guard against rewards accrued prior to delegation activation [7](#0-6) .

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
