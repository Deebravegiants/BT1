### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw HTTP body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are parsed independently and handed to the application's webhook handler unverified. This breaks the intended identity binding `authenticated_shop == shop_acted_on`, since the `shop` value trusted by `Registry.process` is not bound by the HMAC that `Utils::HmacValidator` checks.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` (which calls `validate_signature` -> `compute_signature(verifiable_query.to_signable_string, secret)`) covers exclusively the request body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and, on success, immediately forwards the unauthenticated `request.shop` (along with `topic`/`webhook_id`) to the app-registered handler as trusted tenant identity: [4](#0-3) 

Because the signature check only proves "this body was produced by Shopify using our secret," and not "this body was produced by Shopify *for this shop*," an unprivileged internet user who obtains one valid `(raw_body, hmac)` pair for any shop (e.g., by observing/replaying a webhook delivery, which is not itself protected by TLS-pinning or nonce/replay checks in this gem) can resubmit the exact same body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true`, because it only recomputes the HMAC over `raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is attacker-chosen and not bound to the value used in the signature. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `hmac_signed_shop == request.shop`, but the gem never establishes or checks that equality — it treats `hmac(raw_body)` as sufficient proof of `shop`.

### Impact Explanation
Applications built on this gem are expected to use the `shop` value supplied in `WebhookMetadata` (derived from `request.shop`) as the authoritative tenant identifier to look up sessions/access tokens and apply webhook side effects (e.g., uninstall handling, GDPR data requests, order/customer updates) for that merchant. Because the gem never binds `shop` to the HMAC, a replayed or header-tampered webhook can cause the host application to process a payload under the wrong shop's identity — a cross-tenant data/action confusion at the trust boundary this gem is specifically responsible for enforcing (`Registry.process` is the gem's own verification gate).

### Likelihood Explanation
Low-to-moderate: exploitation requires the attacker to first obtain one valid `(body, hmac)` pair (e.g., via a captured/leaked webhook delivery, a misconfigured proxy/log, or a shop the attacker owns sending itself a webhook with a body it controls in part, such as `orders/create` payloads which contain attacker-influenced shop data). Once obtained, no secret material is needed to replay it with a different `shop-domain` header, since header tampering does not invalidate the signature. This is a self-contained gap in the gem's own verification logic, not a hypothetical dependent on host misconfiguration.

### Recommendation
Include the trust-sensitive headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used by `Request#to_signable_string`, or alternatively require `Registry.process` to independently verify that the `shop-domain` header matches an expected/allow-listed value tied to the session context before dispatching to the handler. At minimum, document and enforce that `WebhookMetadata#shop` must never be trusted as an authenticated tenant identifier unless corroborated by out-of-band binding (e.g., correlating with an active, previously established session for that shop).

### Proof of Concept
```ruby
# Attacker captures (or self-generates via their own shop) a valid webhook delivery:
raw_body = '{"id":123}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)

# Attacker replays it against the app's webhook endpoint, substituting the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # still valid, only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unverified
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true (only checks raw_body)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# -> host app processes the payload as if it legitimately came from victim-shop
