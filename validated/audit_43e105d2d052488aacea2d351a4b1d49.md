I've confirmed the code exactly matches the claim: `handleTokenExchange` in `core/sessions/oidcauth/oidc.go` has two missing-`return` bugs, breaking the check-then-abort pattern used consistently elsewhere in the same function.

Audit Report

## Title
Missing `return` after failed email-claim extraction and session-insert error checks in OIDC token exchange allows session establishment on unchecked failure paths - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
`oidcAuthenticator.handleTokenExchange` writes an HTTP 500 error body when the `email` claim cannot be extracted from the ID token or when the `INSERT INTO oidc_sessions` fails, but in both cases execution continues instead of returning, unlike every other error branch in the same function. [1](#0-0) [2](#0-1)  As a result, the handler proceeds to audit-log a successful login, set the session cookie, and return `HTTP 200 {"Success": true}` even though the email claim was invalid/missing or the session row was never persisted.

## Finding Description
In `handleTokenExchange`, every other validation failure (`ShouldBindJSON`, state check, `Exchange`, `id_token` extraction, `Verify`, `Claims`, `ExtractIDClaimValues`, `IDClaimsToUserRole`, `ginSession.Save`) correctly calls `return` immediately after writing the error response. [3](#0-2)  Two branches deviate from this pattern:

1. `email, ok := claims["email"].(string)` — on `!ok`, an error is logged and a 500 is written, but there is no `return`, so `email` remains `""` and execution falls through to role mapping and session creation. [4](#0-3) 
2. The `oi.ds.ExecContext(...)` insert into `oidc_sessions` — on error, a 500 is written but again no `return`, so the handler still executes `oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, ...)`, sets `ginSession.Set(webauth.SessionIDKey, clSession.ID)`, saves the session, and returns `HTTP 200 {"Success": true}`, despite the row never being persisted. [5](#0-4) 

The ID token itself is cryptographically verified against the configured provider before claims are read (`oi.provider.Verifier(oi.oidcConfig).Verify`), so an attacker cannot arbitrarily forge the claims payload without control of, or a legitimate response from, the trusted IdP. [6](#0-5)  This means the missing-`return` on the email-claim branch is only reachable when the configured, trusted identity provider itself omits/mistypes the `email` claim — this is a provider-configuration-dependent condition, not something an unprivileged attacker can force at will. The DB-insert-failure branch requires a genuine (typically transient/operational) database error during login, which is not attacker-triggerable on demand either.

## Impact Explanation
Where reachable, the bug does produce a real state confusion: a session cookie tied to `clSession.ID` is issued and `AuthLoginSuccessNo2FA` is audited even though (a) the email claim was invalid and stored as an empty string, or (b) the session row was never written to `oidc_sessions` at all. This matches an in-scope "cross-user response corruption" / erroneous session-state category, since downstream authorization (`AuthorizedUserWithSession`) would either look up a non-existent session ID (in case b, likely just failing later) or find a row with `user_email = ""` but a role derived from group claims (in case a) — a real inconsistency, though not demonstrated in the report to constitute privilege escalation beyond the role already computed from the presented, provider-verified group claims.

## Likelihood Explanation
The email-claim branch is only reachable if the trusted, administrator-configured OIDC provider itself returns an ID token without a usable `email` claim — this is a legitimate provider/IdP behavior/misconfiguration scenario, not something an unprivileged network attacker can induce against a correctly configured provider. The DB-insert branch requires an actual database fault at exactly that moment. Both are real code defects, but neither is freely and repeatably triggerable by an unprivileged remote attacker against a properly configured node; they depend on IdP-side data/configuration or backend faults rather than attacker-supplied input to the node's HTTP API.

## Recommendation
Add `return` immediately after both error-reporting blocks:
- After `c.String(http.StatusInternalServerError, "Failed to get email from claims")`.
- After `c.String(http.StatusInternalServerError, "Error creating session")`.

This ensures the session cookie is never set and no "success" response is returned unless the email claim was validly extracted and the session row was actually persisted.

## Proof of Concept
1. Configure OIDC auth against a test/mock provider that returns an ID token without an `email` claim (or with a non-string `email` field).
2. Drive the standard sign-in → provider redirect → `/session/exchange` flow.
3. Observe `handleTokenExchange` logs `"Failed to get email from claims"` and writes a 500 body, but still proceeds to call `IDClaimsToUserRole`, insert into `oidc_sessions` with `user_email = ""`, audit `AuthLoginSuccessNo2FA`, set `webauth.SessionIDKey` in the gin session, and return `HTTP 200 {"Success": true}`.
4. Separately, simulate a DB error on the `INSERT INTO oidc_sessions` statement (e.g., via test double) and observe the same fall-through: audit log, cookie set, and 200 response despite the insert failure.

func (oi *oidcAuthenticator) handleTokenExchange(c *gin.Context) {
	// parse and validate the incoming JSON request
	var req ExchangeTokenRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		c.JSON(http.StatusBadRequest, ExchangeTokenResponse{
			Success: false,
			Message: "Invalid request: " + err.Error(),
		})
		return
	}

	// check state matches stored value on the session
	ginSession := sessions.Default(c)
	storedState := ginSession.Get("state")
	if storedState == nil || req.State != storedState.(string) {
		c.JSON(http.StatusBadRequest, ExchangeTokenResponse{
			Success: false,
			Message: "Invalid state parameter",
		})
		return
	}
	ginSession.Delete("state")

	// Begin token exchange to retrieve attested claims of authenticated user
	ctx := context.Background()
	oauth2Token, err := oi.oauth2Config.Exchange(ctx, req.Code)
	if err != nil {
		oi.lggr.Errorf("Failed to exchange token: %v", err)
		c.JSON(http.StatusInternalServerError, ExchangeTokenResponse{
			Success: false,
			Message: "OIDC exchange failed",
		})
		return
	}

	// Request token from provider for claims lookup and verification
	rawIDToken, ok := oauth2Token.Extra("id_token").(string)
	if !ok {
		oi.lggr.Errorf("No id_token field in oauth2 token: %v", err)
		c.String(http.StatusInternalServerError, "Missing id_token field in response")
		return
	}

	// Verify claim and retrieve attested user id claims
	idToken, err := oi.provider.Verifier(oi.oidcConfig).Verify(ctx, rawIDToken)
	if err != nil {
		oi.lggr.Errorf("Failed to verify ID token: %v", err)
		c.String(http.StatusInternalServerError, "Failed to verify ID token")
		return
	}

	var claims map[string]any
	if err = idToken.Claims(&claims); err != nil {
		oi.lggr.Errorf("Failed to parse OIDC return claims: %v", err)
		c.String(http.StatusInternalServerError, "Failed to parse OIDC return claims")
		return
	}
	idClaims, err := oi.ExtractIDClaimValues(claims, oi.config.ClaimName())
	if err != nil {
		oi.lggr.Errorf("Failed to extract ID claims from ID token. ClaimName: '%s': error %v", oi.config.ClaimName(), err)
		c.String(http.StatusInternalServerError, "Failed to extract ID claims from claims")
		return
	}
	email, ok := claims["email"].(string)
	if !ok {
		oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
		c.String(http.StatusInternalServerError, "Failed to get email from claims")
	}
	oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)

	// Map the claims to a role and insert a newly created session paired with role mapping for user
	role, err := oi.IDClaimsToUserRole(
		idClaims,
		oi.config.AdminClaim(),
		oi.config.EditClaim(),
		oi.config.RunClaim(),
		oi.config.ReadClaim(),
	)
	if err != nil {
		oi.lggr.Errorf("Failed to map configured RBAC role name against received list of group claims: %v", err)
		c.String(http.StatusBadRequest, "No matching role within attested user group claims")
		return
	}
