### Title
Unprivileged third-party supply can restamp victim liquidation parameters - (File: contracts/controller/src/positions/supply.rs)

### Summary
A third party can deposit a dust amount into an existing collateral market of another account and force that collateral leg's full cached risk tuple, including liquidation parameters, to refresh. This bypasses the safer `update_account_threshold(..., has_risks=true)` path, which enforces a post-refresh health factor of at least 1.05 WAD.

### Finding Description
`process_supply` authenticates only the paying caller and permits third-party deposits when every supplied market is already present in the victim's `supply_positions`. [1](#0-0)  After deposit, `merge_supply_leg` calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, not the LTV-only scope. [2](#0-1)  The public supply flow then finalizes without running `enforce_post_pool_solvency` or requiring the health-factor floor used by threshold maintenance. [3](#0-2)  In contrast, `update_account_threshold` maps `has_risks=true` to `FullTuple`, while the separate threshold path is documented and implemented to enforce a final health factor of at least 1.05. [4](#0-3) 

### Impact Explanation
If governance lowers a collateral's liquidation threshold while victim accounts retain stale cached parameters, an attacker can force the stale parameters to update by supplying a small amount to each affected existing collateral position. A victim whose health factor falls below one can then be liquidated through the permissionless `liquidate` entrypoint, allowing the attacker to seize discounted collateral. This is unauthorized manipulation of another account's liquidation state and can result in theft of user collateral through liquidation.

### Likelihood Explanation
The attacker needs only a funded address and a victim account with an existing supply position in a market whose risk parameters become less favorable. The attacker authorizes their own deposit, so no victim signature, delegate grant, NFT approval, or privileged role is required. The attack depends on stale beneficial cached liquidation parameters, but that state is expected because the protocol deliberately caches per-position parameters and provides a separate keeper refresh endpoint.

### Recommendation
Prevent `process_deposit` / `merge_supply_leg` from using `RiskRefreshScope::FullTuple` for third-party top-ups, or perform the same post-refresh health-factor gate used by `update_account_threshold` before committing a full risk refresh. A robust rule is:

- owner/delegate supply: full refresh may proceed subject to normal accounting;
- third-party supply: credit shares without restamping the existing collateral leg's risk tuple, or refresh LTV only;
- any path that can worsen cached liquidation parameters should reject if the resulting account health factor is below the maintenance threshold.

### Proof of Concept
1. Governance schedules and later executes a market configuration operation that reduces the liquidation threshold for collateral asset `C`; the victim account still contains a previously cached, higher liquidation parameter for `C`.
2. The attacker calls:
   ```text
   supply(
     caller = attacker,
     account_id = victim_account_id,
     spoke_id = victim_spoke_id,
     assets = [(C, dust_amount)]
   )
   ```
   The call succeeds because the attacker only needs to authorize spending their own `dust_amount`, and third-party supply is allowed when `C` is already in the victim's `supply_positions`. [1](#0-0) 
3. During the pool-result merge, the victim's `C` position is refreshed using `RiskRefreshScope::FullTuple`, replacing the cached liquidation parameters. [2](#0-1) 
4. Because ordinary supply does not run the post-operation solvency gate, the reduced liquidation collateral can make the victim's health factor less than one even though the equivalent maintenance refresh would reject below 1.05. [3](#0-2) 
5. The attacker calls `liquidate(attacker, victim_account_id, debt_payments, SeizeMode::Transfer)` and receives victim collateral under the liquidation bonus rules.

/// factor >= 1.05. Rejects execution during a flash loan.
pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
