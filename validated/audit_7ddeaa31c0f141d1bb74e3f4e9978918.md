Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook purely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through as the authenticated tenant identity in `WebhookMetadata`. Because the header is never part of the signed material, the binding "HMAC-verified request == the shop the request claims to be from" does not hold, letting an attacker who controls one tenant's valid, HMAC-signed webhook body relabel it as belonging to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers with no cryptographic tie to the body: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and the other header-derived fields) to build `WebhookMetadata`, which is the only tenant-identifying data delivered to the app's handler: [4](#0-3) [5](#0-4) 

Because `client_secret`-based HMAC keys are shared across every shop that installs the same app (there is no per-shop signing key), a malicious merchant who installs the app on their own store can capture a legitimately signed webhook (valid HMAC over the body, computed with the app's single `client_secret`), then replay it to the app's webhook endpoint after swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds because the header is never covered by the signature, and `WebhookMetadata#shop` reports the victim's domain to the handler. This breaks the identity binding `HMAC-authenticated request == shop field trusted by the handler`, exactly the pattern called out in the analog list ("a field acted on but not covered by the HMAC").

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which tenant's session/data to act on (a documented, intended use of this field, since it is the only shop identifier the gem exposes for webhook processing) can be made to attribute attacker-controlled webhook content to an arbitrary victim shop. This is a cross-tenant integrity violation — attacker-controlled data or events (e.g. spoofed `orders/create`, `app/uninstalled`, or the mandatory `customers/redact`/`shop/redact` topics) can be injected under a victim's identity without ever compromising the victim's credentials. Per the given impact classification this constitutes cross-tenant access/manipulation (Critical).

### Likelihood Explanation
Any developer/merchant who can install the target app (a completely unprivileged, unauthenticated-relative-to-other-tenants action) can obtain at least one validly HMAC-signed webhook body from their own store and then freely replay it with a forged `shop-domain` header, since no part of the library ties the header to the signature. No secrets, tokens, or privileged access to the victim are required — only that the same app's shared `client_secret` was used to sign a webhook the attacker legitimately received for their own shop.

### Recommendation
Bind the tenant identity into the authenticated material: either include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used by `HmacValidator`, or require handlers to cross-check `request.shop` against an independently verified/authenticated session (e.g. looked up via the topic/body payload) rather than trusting the raw header. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. for `customers/redact`, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and body `B`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only against `raw_body` (`to_signable_string`) and succeeds since the body/HMAC pair is untouched: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and performs whatever tenant-scoped action it takes for that topic against the victim shop's records, believing the event legitimately originated from Shopify for that shop.
