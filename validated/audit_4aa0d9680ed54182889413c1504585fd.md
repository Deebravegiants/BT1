Confirmed: `VerifiableQuery#to_signable_string` is the only content HMAC-verifies, and for webhooks that resolves to `@raw_body` alone.This confirms the vulnerability path: `Registry.process` builds `WebhookMetadata` (including `shop`) directly from the unauthenticated header, and passes it to the app's `handler.handle`, trusting `request.shop` as if it were HMAC-verified.### Title
Webhook `shop-domain` header is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shopify-shop-domain` / `x-shopify-shop-domain` header value as the tenant identity handed to the app's handler. The header is never covered by the HMAC, so the binding "HMAC-verified sender == shop attributed to this webhook" does not hold.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `shop` is read straight from a header that is never part of that signable string: [3](#0-2) [4](#0-3) 

The shared secret used for the HMAC (`Context.api_secret_key`) is the app-wide `client_secret`, identical for every shop the app serves, not a per-shop secret. Consequently any merchant that installed the app can legitimately obtain a `(raw_body, valid_hmac)` pair for a webhook addressed to their own shop, then replay that exact body+hmac to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` passes the forged `shop` value straight into `WebhookMetadata` delivered to the app's `WebhookHandler#handle`: [5](#0-4) 

This breaks the identity binding: `hmac-authenticated origin == shop field trusted by the handler`. Before the attack, `shop` legitimately equals the origin shop that produced the signed body. After the attacker's replay with a substituted header, the HMAC still validates while `shop` now equals an arbitrary victim domain chosen by the attacker, with no re-derivation of `shop` from anything HMAC-covered.

### Impact Explanation
Any application built on this gem that keys authorization, data lookups, or side effects (e.g., "process this order/customer/redact event for `data.shop`") off `WebhookMetadata#shop` will act on attacker-chosen tenant identity while believing it was Shopify-authenticated. This is a cross-tenant confusion vector reachable by any unprivileged actor who has installed the app on at least one shop (no access token, no `api_secret_key`, and no privileged account are required) — they only need one legitimate webhook delivery to their own shop to obtain a valid `(body, hmac)` pair, which they can then replay against arbitrary target shop identities. This matches the Critical "cross-tenant access" category since it allows misattributing verified webhook data to a different tenant than the one that actually produced it.

### Likelihood Explanation
High. No secrets need to be recovered — the attacker only needs to install the target app once as a normal merchant to receive an authentically-signed webhook, then can freely modify the unsigned `shop-domain` header (and mandatory topics, e.g. `customers/redact`, `shop/redact`, are especially sensitive) on replay. The gem provides no additional verification (e.g., checking that the shop is a known/registered session, or including shop in the signable string) before dispatching to the handler.

### Recommendation
Include the shop domain (and other webhook headers used for authorization decisions, such as topic and webhook id) in the signed/verified material before trusting them, or independently verify that `request.shop` corresponds to a shop with an active session/installation known to the app prior to invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted for tenant-scoping decisions without additional verification — but since this gem is the security boundary consumers rely on, the safer fix is for `Registry.process` (or `HmacValidator`) to bind the `shop` header into the value being verified, matching how the OAuth `AuthQuery` binds `shop` into its HMAC signable string: [6](#0-5) 

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g. `customers/data_request`, with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Attacker replays an HTTP POST to the app's webhook endpoint with the same raw body `B`, the same `shopify-hmac-sha256: H`, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H` [2](#0-1) .
4. `WebhookMetadata.new(..., shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` [7](#0-6) , and delivered to the app's handler as an "authenticated" webhook for the victim shop, even though it never originated from Shopify for that shop.
