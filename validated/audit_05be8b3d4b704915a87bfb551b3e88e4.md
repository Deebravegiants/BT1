### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC over the raw request body only, but the shop identity used for tenant routing is read from the `X-Shopify-Shop-Domain` HTTP header, which is not part of the signed bytes. This breaks the binding `hmac_valid(body) == authenticated(shop)`, letting anyone who possesses one valid `(body, hmac)` pair replay it while claiming an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the received HMAC [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But the `shop` method used for tenant identification is pulled straight from an unauthenticated header, never included in the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then hands `request.shop` straight to the handler as the tenant identity: [4](#0-3) 

Contrast this with the OAuth callback path, where every field that is acted upon (`code`, `host`, `shop`, `state`, `timestamp`) is explicitly included in the signable string [5](#0-4) , so tampering with `shop` there invalidates the HMAC. The webhook path lacks this binding for `shop`.

This is the same bug class as the StRSR report: an action (`_payoutRewards()`/staking) is gated on one piece of state while a *different*, unsynced piece of state is used to attribute the effect. Here, HMAC validity (over `body`) is treated as proof of authenticity for the `shop` header, but the two are never cryptographically bound.

### Impact Explanation
Any unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair — trivially achievable by installing the public app on their own development/test store and triggering a webhook of interest, since Shopify signs it with the same `client_secret` for all shops using that app — can POST that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks body integrity, and `Registry.process` dispatches the payload to the handler tagged with the attacker-chosen `shop` value [6](#0-5) . Any host application that uses `WebhookMetadata#shop` to look up/update per-tenant records (the intended and documented use, per `webhook_id`/`shop`/`topic` fields) will process attacker-controlled data under the victim tenant's identity — a cross-tenant integrity/data-injection issue.

### Likelihood Explanation
Requires only: (1) ability to install the app or otherwise trigger one legitimate webhook for the attacker's own shop (public/embedded apps typically allow free installation), and (2) ability to send an arbitrary HTTP request to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged account needed. This satisfies the "unprivileged internet user" and "no credential/token required" scope constraints.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signed material verified against the HMAC, or otherwise cryptographically bind the header-derived shop to the request before it is trusted — mirroring how `AuthQuery#to_signable_string` binds `shop` in the OAuth flow. At minimum, document that host applications must not treat `Request#shop` as authenticated, and/or validate it against Shopify's known/allow-listed shop registered for the receiving webhook subscription.

### Proof of Concept
```ruby
# Attacker installs the target public app on their own store "attacker.myshopify.com"
# and captures a real webhook delivery, e.g. orders/create:
raw_body = '{"id": 1, "note": "malicious payload"}'
real_hmac_b64 = "<value Shopify computed with the real client_secret for attacker's own store>"

# Attacker replays it against the app's public webhook endpoint, changing only the
# unauthenticated shop header to a victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_b64,       # still valid, since it only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # NOT covered by HMAC
  "x-shopify-webhook-id" => "spoofed-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
# HmacValidator.validate(request) => true  (only checks raw_body integrity)
ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)
# even though the payload/HMAC actually originated from "attacker.myshopify.com"'s own webhook.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
