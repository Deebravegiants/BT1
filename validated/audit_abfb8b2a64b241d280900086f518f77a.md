### Title
Missing re-initialization guard in `LockupContract::new` allows a permissionless attacker to reinitialize and take over any already-deployed lockup contract - (File: lockup/src/lib.rs)

### Summary
The external report's root cause is a missing/inherited-away initialization guard that lets an unprivileged attacker call an `#[init]` constructor on an already-live contract and take ownership of it, then drain funds through the newly-controlled admin surface. `core-contracts` has its own, independent instance of this exact root-cause class in `lockup/src/lib.rs`: `LockupContract::new` is missing the `assert!(!env::state_exists(), ...)` re-initialization guard that every other production contract in this repository implements.

### Finding Description
Every other `#[init]` constructor in this repository explicitly guards against re-initialization by checking `env::state_exists()` before writing new state: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`LockupContract::new`, however, contains no such check: [7](#0-6) 

The near-sdk version used here (`#[near_bindgen]`/`#[init]` macros from the SDK release used across this whole codebase, e.g. `near-sdk = "2.0.0"` per the changelog note in `lockup/README.md`) does not itself enforce single-invocation semantics on `#[init]` methods — that is exactly why every sibling contract adds its own explicit `env::state_exists()` assertion. `LockupContract::new` is the only production initializer that omits it, meaning `new` can be called again on an account that has already been created and initialized, fully overwriting `LockupContract`'s Borsh state (`owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, `staking_pool_whitelist_account_id`, `foundation_account_id`): [8](#0-7) 

Because `new` is a public, unauthenticated entry point (no predecessor/owner check — unlike `owner.rs`/`foundation.rs` methods, which are gated on `self.owner_account_id`/`self.foundation_account_id`), any account can call it directly against a live lockup contract account ID.

### Impact Explanation
An attacker calling `LockupContract::new` again on a deployed, funded lockup contract can:
1. Set `owner_account_id` to their own account.
2. Set `transfers_information` to `TransfersEnabled { transfers_timestamp: 0 }` (already-enabled transfers) and omit `vesting_schedule`/`lockup_timestamp`/`lockup_duration`, so `lockup_information.lockup_amount` is recomputed from `env::account_balance()` at call time but no further lock/vesting constraints are re-applied.
3. Immediately call owner-only methods (e.g. `transfer`) in `owner.rs`, which are gated only on `self.owner_account_id == predecessor` — now satisfied because the attacker is the newly-set owner — to withdraw the entire NEAR balance held by the lockup contract.

This is a Critical impact per scope: "Unauthorized transfer, withdrawal, spending, or release of locked, vested, pooled, or multisig-controlled NEAR through public-call, callback, approval, or accounting failure reachable by an unprivileged user," and also results in "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release... flows" for the legitimate owner, since the entire locked balance can be drained. Given the widespread use of the lockup contract for NEAR Foundation / team / investor token lockups, exploitation is a full drain of any deployed lockup account, analogous in severity to the $29M drain described in the external report.

### Likelihood Explanation
Likelihood is high wherever it's reachable: any already-deployed `LockupContract` instance is a public account with a callable `new` function and no code-level protection preventing re-invocation. The only mitigating factor is that the initial deployment (`create_account` + `transfer` + `deploy_contract` + `function_call("new", ...)`) is normally submitted as a single atomic batch of actions in one transaction (as shown in `lockup-factory/src/lib.rs`'s `create` method and in `README.md`'s manual deployment instructions), so an attacker cannot front-run the very first initialization. However, this atomicity only protects the first call — it does not add any on-chain check preventing subsequent calls to `new` after the contract is live, which is the actual vulnerability. Any already-live lockup account remains permanently exposed to this attack for its entire lifetime.

### Recommendation
Add the standard re-initialization guard to `LockupContract::new`, consistent with every other contract in this repository:
```rust
#[init]
pub fn new(
    owner_account_id: AccountId,
    ...
) -> Self {
    assert!(!env::state_exists(), "The contract is already initialized");
    ...
}
```
This must be the first statement in the function body, mirroring `whitelist/src/lib.rs:34`, `staking-pool/src/lib.rs:179`, `staking-pool-factory/src/lib.rs:106`, `multisig/src/lib.rs:104`, `voting/src/lib.rs:36`, and `lockup-factory/src/lib.rs:80`.

### Proof of Concept
1. Deploy and initialize `LockupContract` normally (atomic `create_account` + `deploy_contract` + `function_call("new", ...)`), funding it with N NEAR under the intended `owner_account_id`.
2. From any unprivileged account, call:
```
near call <lockup-account> new '{
  "owner_account_id": "<attacker.near>",
  "lockup_duration": "0",
  "lockup_timestamp": null,
  "transfers_information": { "TransfersEnabled": { "transfers_timestamp": "0" } },
  "vesting_schedule": null,
  "release_duration": null,
  "staking_pool_whitelist_account_id": "<any-valid-account>",
  "foundation_account_id": null
}' --accountId attacker.near --gas 25000000000000
```
Because `LockupContract::new` performs no `env::state_exists()` check, this succeeds and overwrites the contract state, making `attacker.near` the new `owner_account_id` with fully unlocked, non-vested transfer conditions.
3. Attacker calls the owner-only `transfer` method in `lockup/src/owner.rs` to withdraw the entire NEAR balance of the lockup contract to themselves, since `self.owner_account_id` now equals `attacker.near`: [9](#0-8)

```rust
    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
```
