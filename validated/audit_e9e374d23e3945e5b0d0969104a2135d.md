Confirmed: the `shop` field in `ShopifyAPI::Webhooks::Request` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, and `Registry.process` only verifies the HMAC over the raw body, never over the shop header, before handing `request.shop` to the app's handler as trusted tenant identity.This confirms the vulnerability is fully reachable through the gem's own documented API surface (`ShopifyAPI::Webhooks::Registry.process` / `ShopifyAPI::Webhooks::Request`), with no dependency on leaked secrets or privileged access — the attacker only needs a body/HMAC pair that is valid for *some* shop (which any merchant installing the app on their own store legitimately receives) and can freely relabel it via the unsigned `x-shopify-shop-domain` header.

### Title
Webhook shop identity is read from an unauthenticated header and is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop` identity handed to the app's handler, however, comes from `ShopifyAPI::Webhooks::Request#shop`, which simply reads the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header with no cryptographic binding to the signed payload [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the signature strictly over that signable string against `Context.api_secret_key` [4](#0-3) . The shop-domain header is never included in the bytes that are signed. Once the HMAC check passes, `Registry.process` immediately trusts `request.shop` and forwards it, unchecked, to the app's handler as the tenant identity for the event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) .

Because Shopify signs webhooks with a secret shared by the app across **all** installed shops (not per-tenant), any shop that has legitimately installed the app can capture a valid `(raw_body, hmac)` pair from its own genuine webhook deliveries. For topics whose body carries no shop-specific content (e.g. minimal/empty JSON payloads), that captured pair remains HMAC-valid forever and for any shop. An attacker who controls one installed shop can replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will pass because it never inspected the shop header, and the app's handler will act on the request believing it originates from the victim shop — this is the same "field acted on but not covered by the HMAC" class of identity-binding break as the referenced report's registry/owner mismatch. The equality the gem should be enforcing — `shop header used by handler == shop cryptographically bound to the authenticated bytes` — does not hold; before and after the attacker's request the left side changes freely while the right side (the actual HMAC-authenticated identity, which is really "no shop at all") stays fixed.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide (`webhooks.md` explicitly tells app authors that `data.shop` is "The shop domain of the webhook" and is safe to key work off of). A host application that follows this documented contract and uses `data.shop` to select which tenant's records to update, delete, or deactivate (e.g. on `app/uninstalled`, `shop/redact`, or similarly low-content-body topics) can be tricked into performing that action against a shop the attacker does not own — a cross-tenant integrity impact reachable by any unprivileged internet user who has installed the app on their own store, without ever needing the app's `client_secret` or another merchant's access token.

### Likelihood Explanation
Likelihood is high for topics with static or shop-agnostic bodies, since the attacker only needs one legitimately received webhook of that topic on a shop they control, then can replay the header-modified request as many times as desired; the endpoint is a public HTTP callback URL with no other authentication layer, and the vulnerable code path (`HmacValidator.validate` + `Request#shop`) is on every processed webhook by design, not an edge case.

### Recommendation
Bind the shop domain into the value being authenticated (e.g., have `Request#to_signable_string` incorporate the `shop` header, or otherwise cryptographically tie the header to the payload) or require the host application to independently authorize the resolved shop against a known/expected list of installed shops before trusting it; document that `data.shop` is not itself byte-for-byte authenticated by the HMAC and must not be used as the sole tenant key for consequential actions.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com` and legitimately receives a real webhook for topic `app/uninstalled` (or any topic with a fixed/empty body such as `"{}"`) with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-"{}"...>`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` builds a `Request`, calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and finds it matches — the header substitution is invisible to the check [6](#0-5) .
4. `Registry.process` calls the app handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"`, taken straight from the attacker-controlled header [5](#0-4) .
5. Any handler logic keyed on `data.shop` (per the documented contract in `docs/usage/webhooks.md`) now executes against `victim.myshopify.com`'s tenant data on the basis of a forged, unauthenticated field.
