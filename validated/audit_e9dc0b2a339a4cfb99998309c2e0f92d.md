Audit Report

## Title
LDAP Authentication Allows Unauthenticated Bind via Empty Password on `CreateSession` and `TestPassword` - ([File: core/sessions/ldapauth/ldap.go])

## Summary
`ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` forward the attacker-supplied `Password`/`password` value directly into `conn.Bind(searchBaseDN, ...)` with no check that the value is non-empty. Per RFC 4513 §5.1.2, a bind with a valid DN and a zero-length password is a defined "unauthenticated bind" primitive, and on LDAP servers that permit this pattern (a documented, non-default-hardened LDAP behavior), the bind call will succeed for any email resolving to a valid DN, causing the application to treat the request as an authenticated login.

## Finding Description
`CreateSession` builds `searchBaseDN` from the caller-supplied, only lower-cased/escaped email, and binds with the raw `sr.Password` with no emptiness check: [1](#0-0) . If the bind returns no error, the code proceeds to call `FindUser` and creates a persisted `ldap_sessions` row and returns a live session ID: [2](#0-1) . The identical unguarded pattern exists in `TestPassword`, reachable from the API-token creation/validation flow: [3](#0-2) .

`sessions.SessionRequest.Password` is declared as a plain `string` with no length constraint enforced at the transport layer: [4](#0-3) . Unlike the local/OIDC path (`localLoginFallback`), which always compares against a stored bcrypt hash via `utils.CheckPasswordHash`, the LDAP bind path has no defense-in-depth check preventing an empty-password bind attempt from reaching the upstream server: [5](#0-4) . The connection wrapper (`LDAPConn.Bind`) is a thin pass-through to the underlying `go-ldap/ldap/v3` client with no additional guard: [6](#0-5) . `NewLDAPAuthenticator` enforces TLS in production and requires role-group mappings to be configured, but performs no check or requirement that the upstream LDAP server disables unauthenticated binds: [7](#0-6) .

## Impact Explanation
If triggered against an LDAP server configured to permit unauthenticated binds, an attacker who knows or can enumerate a valid directory user's email could obtain a valid `ldap_sessions` entry and impersonate that user with whatever role (`admin`, `edit`, `run`, `view`) is mapped from their LDAP group membership — a node API authentication/role bypass, which is an in-scope Chainlink bounty impact category.

## Likelihood Explanation
This is not universally exploitable: it requires the target's upstream LDAP server to permit unauthenticated/anonymous-style binds for the target's DN, which is a server-side setting outside of the chainlink codebase and is disabled by default on many modern LDAP deployments (e.g., hardened OpenLDAP/AD configurations). The chainlink code path itself, however, performs no defense-in-depth validation (no `sr.Password == ""` check) before dispatching the bind, unlike the local-auth path which always hashes/compares. Exploitability is therefore conditional on this external server configuration, which weakens — but does not eliminate — the finding's standalone severity, since the application should not rely on upstream server hardening for this specific well-known LDAP bind pitfall.

## Recommendation
Add an explicit rejection of empty/whitespace-only passwords in `CreateSession` and `TestPassword` before calling `conn.Bind`, e.g., return an error immediately if `sr.Password == ""` (and similarly `password == ""` in `TestPassword`), so the LDAP server is never given the opportunity to interpret the request as an unauthenticated bind regardless of its own configuration.

## Proof of Concept
1. Identify a valid directory user's email that maps to a resolvable DN under `BaseUserAttr`/`UsersDN`/`BaseDN`.
2. POST to `/sessions` with `{"email": "<valid-user-email>", "password": ""}`.
3. `CreateSession` calls `conn.Bind(searchBaseDN, "")` (`core/sessions/ldapauth/ldap.go:408`).
4. On an LDAP server configured to accept unauthenticated binds for that DN, `Bind` returns nil, `FindUser` resolves the role, and a session is created and returned to the caller (`core/sessions/ldapauth/ldap.go:413-456`).
5. A Go unit test can substitute a mock `LDAPConn.Bind` that mimics unauthenticated-bind-accepting semantics (returns nil for empty password + valid DN) to demonstrate `CreateSession` returns a valid session ID without any password validation being exercised.
