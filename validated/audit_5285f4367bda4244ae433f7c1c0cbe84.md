### Title
Webhook shop identity spoofing — `X-Shopify-Shop-Domain` header is not covered by HMAC verification - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `HmacValidator.validate` cryptographically authenticates the body bytes but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry#process` nonetheless treats `request.shop` as a trusted tenant identifier and forwards it, unauthenticated, into `WebhookMetadata` that is handed to application webhook handlers. This is the same class of bug as the external report: a field ("aggregator roundId"/here, "shop") is *acted upon* by downstream trust-sensitive logic while a *different, narrower* value ("iteration count via `_latestAggregatorRoundId`"/here, "raw body") is what is actually verified.

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined as `@raw_body` only: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly out of HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry#process` validates only the HMAC (i.e., body integrity) and then unconditionally trusts `request.shop` to construct the tenant-identifying metadata passed to the app's webhook handler: [4](#0-3) 

**The broken identity binding, stated as an equality that fails:**
`shop used by handler (request.shop, from header)` ≠ `shop bound by the verified signature (none — signature covers only @raw_body)`.

Before the attack: a legitimate Shopify webhook has `hmac = HMAC(secret, body)` and headers `{shop-domain: legit-shop.myshopify.com, topic: orders/create, ...}` all originating from Shopify and mutually consistent.

After the attack: an attacker who operates their own shop and app installation receives a genuine webhook (valid `body` + valid `hmac`, since they are a legitimate tenant of the app) for that body. They then replay the identical `body`/`hmac` pair to the app's public webhook endpoint, substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header to name a victim shop. `HmacValidator.validate` still returns `true` because it only checks `@raw_body` against `hmac`, which are unchanged. `Registry#process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: <victim-shop>, body: ..., ...)`, i.e., the application logic executes as though the (attacker-crafted or attacker-known) body arrived from the victim's shop.

### Impact Explanation
This breaks the identity binding this gem is supposed to provide to consuming apps: the `shop` value the app relies on to select the tenant's session/access token/data scope is not authenticated, only the body bytes are. An attacker (any internet user who is an unprivileged, legitimately installed tenant of the app, requiring no secret key, no leaked credentials, and no privileged account) can cause the app to process attacker-chosen webhook bodies under a victim shop's identity — a cross-tenant confusion in the identity primitive the gem exposes as verified (`process`/`WebhookMetadata`). Depending on how the consuming handler uses `data.shop` (e.g., to fetch/act on the tenant's stored session or data), this can result in cross-tenant data corruration or actions being attributed to/executed against the wrong merchant, which falls under the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker is a genuine (even free/unprivileged) installer of the app, which lets them harvest a valid `(body, hmac)` pair for at least one real webhook topic they control. Webhook endpoints are public HTTP(S) endpoints with no other authentication, and nothing in `Request#initialize` or `Registry#process` ties the header-derived `shop` to the signed content. No access token, `client_secret`, or privileged access is needed.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material that is authenticated, or otherwise independently verify that the `shop` on record for the receiving app installation matches an installation for which this specific webhook subscription/topic was registered before invoking the handler. At minimum, document (and consider enforcing) that consumers must cross-check `request.shop` against their own subscription records rather than trusting it as an authenticated value derived from the HMAC check.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers an event (e.g. updates a product) causing Shopify to send a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` from their own webhook delivery logs (available to them as the shop owner) or from the app's own logging/debug endpoint.
3. Attacker replays an HTTP POST to the app's `/webhooks` endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (unchanged) [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker-controlled body `B` as if it came from the victim shop [6](#0-5) .

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
