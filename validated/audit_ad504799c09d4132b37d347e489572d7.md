### Title
Webhook shop-domain identity spoofing via HMAC binding gap in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by HMAC-verifying the raw request body, yet the `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler as the trusted tenant identifier are read directly from unauthenticated HTTP headers that are never included in the signed bytes. This breaks the identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == the_shop_that_actually_sent_this_body`, but the code never establishes that equality.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC over that body via `Utils::HmacValidator.validate`, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator` only proves that "someone holding the app's shared `client_secret` produced this exact HTTP body" — it never proves which shop that body belongs to: [4](#0-3) 

Because a Shopify app's `client_secret` is a single value shared across **all** shops that install the app (not a per-shop secret), any user who installs the app on their own (attacker-controlled) shop legitimately receives real webhook deliveries with a valid `(body, hmac)` pair signed with that same shared secret. The attacker can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and `x-shopify-webhook-id`/`topic`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body and secret haven't changed), so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain instead of the attacker's own shop — a cross-tenant identity spoof.

The documentation explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," reinforcing that host apps are expected to trust this value as authenticated: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any handler that uses `data.shop` to key persistence, authorization, or business logic (the exact usage pattern the gem's own docs recommend — e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to attribute another merchant's webhook body to an attacker-chosen shop, or attacker-supplied body to a victim shop, resulting in cross-tenant data corruption/injection — a Critical-tier "cross-tenant access" impact, since the tenant boundary (`shop`) is the exact security boundary this gem is responsible for asserting once `process` returns success.

### Likelihood Explanation
Any internet user can freely install a public Shopify app (or a dev store) to obtain a valid, freshly-signed `(body, hmac)` pair for their own tenant — no leaked credentials, `api_secret_key`, TLS interception, or privileged access is required. They only need to replay that pair to the app's public webhook callback URL with a forged `shopify-shop-domain` header, which `ShopifyAPI::Webhooks::Request` accepts without complaint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the bytes covered by the HMAC (i.e. bind them into `to_signable_string`, or otherwise require the host app to independently verify `request.shop` against a known/installed-shops list before trusting it), so that a valid HMAC cannot be replayed across different header values.
