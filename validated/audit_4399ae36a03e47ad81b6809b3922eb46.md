### Title
Governance disabling an `OutboundRequestDeliveryReward` (or `OutboundConsensusDeliveryReward`) allowlist entry permanently strands the reward already earned by a relayer for a delivery it already proved - (File: modules/pallets/relayer/src/outbound_request.rs)

### Summary
`pallet-relayer` pays relayers a per-`module_id` (or per-destination, for consensus rotations) reward for delivering Hyperbridge-originated requests/consensus proofs. The reward is only checked and read **at claim time**, not reserved or escrowed at dispatch time. Governance can change (including zero out) the reward for a `module_id`/destination at any time via `set_outbound_request_delivery_reward` / the analogous consensus-reward setter. If this happens after a relayer has already honestly delivered a message (the commitment/receipt already exists on the destination) but before the relayer submits its claim, the claim becomes permanently rejected with `OutboundRequestNoRewardConfigured`/`OutboundNoRewardConfigured` — this is exactly the "removed plugin still has an unclaimed reward, and there is no path left to claim it" bug class from the external report.

### Finding Description
`OutboundRequestDeliveryReward` is a single storage value keyed by `module_id`, and the value `0` is deliberately overloaded to mean both "no reward configured" and "module not on the allowlist": [1](#0-0) 

```rust
/// Governance-set per-`module_id` reward for delivering a
/// hyperbridge-originated request from that module. Setting
/// `amount = 0` removes the module from the allowlist.
#[pallet::call_index(6)]
pub fn set_outbound_request_delivery_reward(
    origin: OriginFor<T>,
    module_id: BoundedVec<u8, ModuleIdBound>,
    amount: BalanceOf<T>,
) -> DispatchResult {
    T::RelayerOrigin::ensure_origin(origin)?;
    OutboundRequestDeliveryReward::<T>::insert(&module_id, amount);
    ...
}
``` [1](#0-0) 

The claim path (`process_outbound_request_delivery_claim`) re-reads this same live storage value at claim time — well after the request commitment has already been produced and even after the relayer has already delivered it to the destination (proven by a `RequestReceipts[commitment]` state proof): [2](#0-1) 

```rust
let module_id: BoundedVec<u8, ModuleIdBound> = request
    .from
    .clone()
    .try_into()
    .map_err(|_| Error::<T>::OutboundRequestModuleIdTooLong)?;
let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);
``` [2](#0-1) 

There is no snapshot/escrow of the reward amount at dispatch time and no check that a `module_id` still has commitments pending in `pallet_ismp::child_trie::RequestCommitments` before governance is allowed to zero its reward. The exact analog to `StakingModule.removePlugin` is present: a relayer performs the (unprivileged, permissionless) work of delivering the request — the "SimplePlugin" here is the reward being "held" for a module — and a subsequent, ordinary parameter update ("plugin removal") by governance permanently forecloses the only code path (`claim_outbound_request_delivery_reward`) capable of releasing it, because the check is re-evaluated against current storage rather than the state at the time the obligation was incurred.

The identical pattern exists for consensus-rotation rewards: `OutboundConsensusDeliveryReward::<T>::get(destination)` is likewise read fresh inside `process_outbound_consensus_delivery_claim`, after the relayer has already proven delivery via the `_epochs[set_id]` slot proof: [3](#0-2) 

### Impact Explanation
Any relayer (an unprivileged, permissionless actor that races to deliver hyperbridge-originated system messages — host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's own withdrawal requests, and future modules like bandwidth) can perform real, already-completed and already-provable work and then find its earned reward permanently unclaimable through no fault or malicious action of its own, simply because governance adjusted a reward schedule for a module in the ordinary course of operating the allowlist. Once a `module_id`'s reward is reduced to `0` (or reduced to a different, lower amount) after dispatch but before claim, `OutboundRequestNoRewardConfigured` is unconditionally returned and the relayer has no other extrinsic to recover the originally-owed amount for that specific commitment — the `OutboundRequestsClaimed` idempotency map is never set for it, so the funds tied to that delivery are neither paid nor freed for any other purpose; the specific reward obligation is simply permanently lost. This is a medium-severity, fund-accounting freezing bug analogous to the referenced report (funds tied to a specific, already-incurred obligation become permanently unclaimable once the entity that would authorize payout is altered/removed).

### Likelihood Explanation
This requires no malicious actor. It is triggered by the intended, expected governance workflow of tuning `OutboundRequestDeliveryReward`/`OutboundConsensusDeliveryReward` (e.g. lowering an inflated reward, temporarily disabling a misbehaving module, or reallocating budget) at any point after messages begin flowing for a module but before every relayer that delivered messages for that module has submitted its claim. Given rewards are meant to be adjustable governance parameters (as documented) and delivery-to-claim always has a real-world delay (state proof of the destination must first be available on Hyperbridge), this window realistically occurs during normal operation, not just in a contrived edge case.

### Recommendation
Do not let the claim path depend on the module's *current* reward configuration. Either:
1. Snapshot the reward amount into `RequestMetadata`/a per-commitment map at dispatch time (mirroring how `RequestPayments`/`FeeMetadata` capture the fee at dispatch for user-funded requests), and have `process_outbound_request_delivery_claim` (and the consensus equivalent) pay out the snapshotted amount rather than re-reading the live `OutboundRequestDeliveryReward`/`OutboundConsensusDeliveryReward` map; or
2. If a module's reward is being lowered/disabled, require governance to drain/settle all outstanding unclaimed commitments for that module (or grandfather the previous reward for commitments dispatched before the change) before the reward can be reduced, analogous to requiring `totalClaimable() == 0` before allowing removal in the original report.

### Proof of Concept
1. Governance sets `OutboundRequestDeliveryReward[module_id] = R` (`set_outbound_request_delivery_reward`), enabling module `module_id` on the allowlist. [4](#0-3) 
2. `pallet-host-executive` (or another allowlisted module) dispatches a hyperbridge-originated `PostRequest` with `from = module_id`; the commitment lands in `pallet_ismp::child_trie::RequestCommitments`.
3. A relayer delivers this request to the destination chain; the destination's ISMP host records `RequestReceipts[commitment] = relayer`.
4. Before the relayer submits its claim, governance calls `set_outbound_request_delivery_reward(module_id, 0)` (a routine parameter change, e.g. disabling a deprecated module or rebalancing rewards).
5. The relayer submits `claim_outbound_request_delivery_reward` with a valid state proof of the destination receipt.
6. `process_outbound_request_delivery_claim` reads `OutboundRequestDeliveryReward::<T>::get(&module_id)` which is now `0`, and reverts with `OutboundRequestNoRewardConfigured`. [2](#0-1) 
7. `OutboundRequestsClaimed[commitment]` is never set, and there is no other extrinsic path to pay this relayer for the delivery it already proved — the reward for this specific commitment is permanently unclaimable.

			module_id: BoundedVec<u8, ModuleIdBound>,
			amount: BalanceOf<T>,
		) -> DispatchResult {
			T::RelayerOrigin::ensure_origin(origin)?;
			OutboundRequestDeliveryReward::<T>::insert(&module_id, amount);
			Self::deposit_event(Event::OutboundRequestDeliveryRewardUpdated {
				module_id,
				new_reward: amount,
			});
			Ok(())
		}
