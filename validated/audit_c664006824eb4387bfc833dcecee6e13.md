### Title
Unchecked-length ABI `from` field causes a runtime panic in `HyperFungibleToken::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `IsmpModule::on_accept` handler ABI-decodes an attacker-influenced `Message` from the ISMP `PostRequest.body` and, when the message carries calldata without a signature, slices/copies the message's `from` bytes into fixed-size buffers **without validating their length**, unlike the sibling `to` field a few lines above which is explicitly length-checked. A malformed `from` field of the wrong byte length triggers an unsigned-integer underflow / out-of-bounds slice or a `copy_from_slice` length-mismatch panic — the same bug class as ALPINE-CVE-2020-9366 (crafted input driving a fixed-size buffer operation past its bounds and crashing the process), reachable by any relayer delivering a cross-chain token message.

### Finding Description
In `on_accept` [1](#0-0)  the incoming ISMP `PostRequest.body` is ABI-decoded into a `Message` struct that is fully attacker-controlled bytes (only `source`/`from` contract pairing is authenticated via `ContractToAsset`, not the *contents* of the message body).

The `to` field is correctly defended: it is only accepted at exactly 20 or 32 bytes, otherwise the handler returns an error: [2](#0-1) 

However, the analogous `message.from` field — used only in the optional-calldata unsigned-origin branch — has no such length check before being sliced/copied into fixed-size buffers: [3](#0-2) 

Two distinct panics are reachable depending on `source`:
- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize` (panics in debug builds; wraps to a huge value in release, which then panics on the out-of-bounds slice index either way).
- If `source` is not EVM and `from_bytes.len() != 32`, `account.copy_from_slice(from_bytes)` panics immediately on the length mismatch (`copy_from_slice` requires equal lengths).

This is exactly the bug class described by the CVE: a fixed-size buffer operation (terminal escape buffer in the CVE; here a `[u8;20]`/`[u8;32]` copy) that is driven off adversarial input length without a bounds check, causing memory-unsafety/abort rather than a controlled error path. The codebase elsewhere explicitly recognizes and fixes this exact pattern (e.g. `copy_from_slice` on `consensus_state_id` fixed to check length first, with the comment "wasm trap reachable from untrusted input") [4](#0-3)  and in the SCALE `ByteVector<N>::decode` hardening [5](#0-4)  — but this instance in `hyper-fungible-token` was missed.

### Impact Explanation
`on_accept` is the dispatch entry point invoked automatically by `pallet-ismp` when any relayer delivers a `PostRequest` targeting the HFT module ID — no special privilege is required beyond submitting/relaying a message, matching the "unprivileged message dispatcher... HandlerV2 dispatch and delivery" reachable-path criterion. A Rust panic inside runtime/module-dispatch code is not caught by `Result`-based error handling in this file; it surfaces as a wasm trap during block/extrinsic execution. This can abort execution of the extrinsic/block that delivers the message, causing the route to be unable to deliver that (and potentially subsequent) messages through the HFT channel — a denial-of-service on the bridge's token-transfer path, and in the worst case, on the node processing it.

### Likelihood Explanation
High. Any relayer can construct and submit a `PostRequest` whose ABI-encoded body sets `data` to a non-empty `SubstrateCalldata` with `signature: None` and a `from` field of an incorrect byte length (e.g. 0, 19, or 33 bytes) — a single crafted, well-formed ABI message is sufficient, no signature or governance action required.

### Recommendation
Add the same explicit length validation used for `to_bytes` to `from_bytes` before use: require exactly 20 bytes when `source.is_evm()` and exactly 32 bytes otherwise, returning a `HftError` (e.g. a new `InvalidFromLength` variant) on mismatch instead of panicking.

### Proof of Concept
1. Attacker (any relayer) crafts an ISMP `PostRequest` addressed to a `ContractToAsset`-registered HFT source/contract pair.
2. The ABI-encoded `body` decodes to a `Message` with:
   - valid `to` (20 or 32 bytes) and `amount`,
   - non-empty `data` that decodes as `SubstrateCalldata { signature: None, runtime_call: <any valid call bytes>, from: <e.g. 5 bytes> }`.
3. Relayer submits this via `pallet_ismp::Call::handle_unsigned` (or the equivalent dispatch path) so `Pallet::<T>::on_accept` runs.
4. Execution reaches the `else` branch at [3](#0-2) : for `source.is_evm()` with `from.len() = 5`, `from_bytes.len() - 20` underflows/produces an out-of-bounds slice and panics; for a substrate source with `from.len() != 32`, `copy_from_slice` panics on mismatched length — aborting extrinsic/block execution.
