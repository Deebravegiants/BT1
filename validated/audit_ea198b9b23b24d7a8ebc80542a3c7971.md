### Title
Extreme mint pre-seed permanently seeds the graduated LP away from the curve-close price, freezing locked-LP value below intended - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` defends against a front-run/hostile mint pre-seed of the HyperSwap V2 TOKEN/LT pair by swapping the pool back toward the curve-close ratio before depositing the protocol's `(tokensForLP, ltFromPair)` inventory. That rebalance swap is deliberately capped at 99% of the available per-side inventory by `_swapBudget` [1](#0-0)  to preserve brick-resistance. When an attacker (any unprivileged address, since `factory.createPair` and `pair.mint` are permissionless) seeds the pair with a sufficiently lopsided ratio (e.g. LT reserve ~200x the target vs. TOKEN reserve ~1% of target), the optimal rebalancing swap required to correct the ratio exceeds this 99% budget cap, so the swap is clamped and the pool is deposited while still materially off the curve-close price.

### Finding Description
The permissionless pre-seed attack surface is documented in `packages/contracts/AGENTS.md` [2](#0-1) : between phase 1 (`_enterGraduating`, which caches `tokensForLP`/`ltFromPair`) and phase 2 (`finalizeGraduation`), any address can `factory.createPair(token, lt)`, transfer arbitrary token/LT amounts to the pair, and call `pair.mint(attacker)` to bake a hostile reserve ratio into the pool before the protocol seeds its own liquidity.

`_seedRebalancing` handles this "mint pre-seed" (Regime 3) by computing a no-fee rebalance swap size via `_noFeeSwapInput`, capped at `_swapBudget(inventory)` = 99% of the available LT or TOKEN inventory [3](#0-2) , then executes it directly against the pair via `_pairRebalance` [4](#0-3) , and finally deposits the remaining balanced inventory through `_routerDepositAndDispose` with `amountAMin/amountBMin = 1` [5](#0-4) .

The 99% cap exists specifically because an unconstrained swap could consume 100% of one side and leave `_routerDepositAndDispose` unable to deposit anything, producing a zero-liquidity `LPLock.recordLock` (a total brick) [6](#0-5) . However, this same cap means that for a sufficiently extreme pre-seed ratio, the swap cannot fully correct the pool, and the pool is deposited materially away from the curve-close price. This is not a hypothetical: the protocol's own regression test `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` constructs exactly this scenario (TOKEN reserve at 1% of target, LT reserve at 200x target) and explicitly asserts that the final pool price is more than 20% off the curve-close price after `finalizeGraduation` completes [7](#0-6) . The test frames this only as "the attacker must not profit," but the *protocol's own locked LP* — the assets the launch (creator + traders' curve-raised LT and the reserved 250M tokens) is worth at graduation — permanently opens at this incorrect, off-market price. `LPLock.recordLock` is a one-shot call that cannot be repeated or corrected once `finalizeGraduation` completes [8](#0-7) , so the mispriced LP is permanent — the only way to close the gap is external arbitrage, which itself extracts value from the mispriced pool at the protocol's expense before converging.

This is the smart-contract analog of the reported bug class: a "design flaw" lets an unprivileged party permanently overwrite a piece of protocol-trusted state (here, the AMM pool's opening reserves/price) via a crafted, low-cost input (a lopsided pre-seed), and the flaw's own bounded defense (the 99% cap, chosen for brick-resistance) is insufficient to always correct it — mirroring how the reader's design flaw permanently overwrote a trusted file (`.bashrc`) that was later blindly relied upon.

### Impact Explanation
Any launch's graduated LP can be permanently seeded at a price materially different (empirically >20% in the documented worst case, worse for larger reserve-ratio disparities within the pre-seed's cost budget) from the fair curve-close price computed by the bonding curve. Since `LPLock.recordLock` is one-shot and non-reversible [8](#0-7) , this loss is baked into the protocol's locked liquidity permanently. This is direct value loss to the locked LP (owned collectively by the protocol/creator on behalf of curve participants), satisfying the "LP seeded away from the curve close price" impact criterion. The attack cost is bounded (an LT-rich pre-seed sized to survive the 99% swap cap) but well below the value it can misprice at scale, since the LP inventory being seeded scales with the graduating token's raised liquidity.

### Likelihood Explanation
Reachable by a fully unprivileged address using only public functions: `factory.createPair`, plain ERC20 `transfer` to the pair, and `pair.mint(attacker)` — all permissionless per the documented exploit model [9](#0-8) . The trigger condition (reserve ratio skew that exceeds the 99% rebalance budget) is a known, deliberately tested edge case in the codebase itself (`test_hostilePreSeed_budgetCappedSwap_isNotProfitable`), meaning it is a repeatable, deterministic griefing vector rather than a rare accident — any token nearing graduation is exposed during the window between `_enterGraduating` and `finalizeGraduation`.

### Recommendation
Since the codebase has already made an explicit brick-resistance-over-price-accuracy tradeoff (accepting this residual as documented), a robust fix requires either: (1) uncapping/raising the rebalance budget while independently guaranteeing a non-zero deposit remainder through separate accounting (e.g., reserving a small fixed epsilon rather than a percentage of a variable, possibly-tiny inventory) so it can fully correct even extreme ratios without reopening brick risk, or (2) detecting when the achievable post-swap price gap exceeds a safety threshold and routing the excess pre-seed reserves to protocol-owned recovery (e.g., extending `_sweepLTToOwner`-style disposal further) rather than accepting a permanently mispriced LP. Any change here must re-run `test/GraduationInvariants.t.sol`, `test/TwoPhaseGraduation.t.sol`, and `test/NoFeeSwapInput.t.sol` per the project's own stated invariant-preservation policy [10](#0-9) .

### Proof of Concept
1. Launch a token and drive it into `Lifecycle.Graduating` via `_enterGraduating`, caching `(tokensForLP, ltFromPair)`.
2. As an unprivileged attacker, call `factory.createPair(token, lt)`, then `transfer` `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200` to the pair, then call `pair.mint(attacker)`.
3. Call `bonding.finalizeGraduation(tokenAddr)` (permissionless).
4. Observe (as asserted by the project's own `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` [11](#0-10) ) that the pool's final price is more than 20% off the curve-close price, and this state is permanently locked via `LPLock.recordLock`, with no remediation path afterward.

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
```

```markdown
### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

This is the same exploit class as the four.meme Feb 2025 incident (~$183K loss).
```

```markdown
### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. In either case `_pairRebalance` returns `false`, and `_seedRebalancing` overpowers the dust with a direct `transfer + pair.mint` at the cached `tokensForLP / ltFromPair` ratio (`_seedDirectMint`), opening the pool on-ratio. This is safe specifically because the swap only rounds to zero when the reserves are negligible against this graduation's inventory: the V2 `min()` donation to the attacker's pre-existing LP is then bounded by `max(reserveToken/tokensForLP, reserveLT/ltFromPair)`, which vanishe ... (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
- **No external dependency on the router slot being correct post-deploy.** `uniswapV2Router` is set at `initialize` time alongside `uniswapV2Factory` and is rejected if zero. There's no live setter — rotation requires a UUPS upgrade so the change is visible on-chain ahead of any in-flight graduation.

Tested end-to-end by the brick-resistance regression tests in `test/TwoPhaseGraduation.t.sol` (notably `test_brick_resistance_frontRun_dust_seed`).
```

```text
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
```
