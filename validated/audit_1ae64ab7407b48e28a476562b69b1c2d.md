### Title
`findMatchingWithdrawal()` cross-matches batched POA withdrawals of the same asset, causing wrong destination tx hash/status to be reported - (File: `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
For POA-bridge withdrawals, the SDK matches an in-flight withdrawal to the POA relayer's status list purely by `assetId` (`near_token_id`), ignoring `destinationAddress`, `amount`, and the withdrawal's index/position in the batch. When a caller creates a batch of withdrawals (`sdk.processWithdrawal`/`sdk.waitForWithdrawalCompletion` with an array of `withdrawalParams`) that includes two or more withdrawals of the *same* NEP-141 asset to different destination addresses/amounts within the same settled intent transaction, the code will report the wrong destination transaction hash/status for one of them.

### Finding Description
`findMatchingWithdrawal()` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` matches purely by token id: [1](#0-0) 

The function's own doc comment acknowledges the limitation: [2](#0-1) 

The same pattern is used in `PoaBridge.describeWithdrawal()`, which is called once per withdrawal (per `index`) but the matching function receives only `assetId`, discarding `destinationAddress`, `amount`, and `index`: [3](#0-2) 

This is invoked from `watchWithdrawal()`/`createWithdrawalCompletionPromises()` once independently per withdrawal entry in a batch: [4](#0-3) [5](#0-4) 

Batch withdrawals with multiple entries of the same asset are an explicitly supported feature (`signAndSendWithdrawalIntent` accepts arrays and creates one intent per entry): [6](#0-5) 

Because `Array.prototype.find` returns the *first* array element whose `near_token_id` matches, when two withdrawals for the same asset (e.g., two BTC withdrawals to different addresses/amounts in one batch) are pending simultaneously, both `watchWithdrawal()` calls (one per index) resolve against the same first-matching relayer record. This breaks the equality "the tx hash reported for withdrawal at index i corresponds to the withdrawal actually requested at index i (same destination address and amount)" — an integrator could receive withdrawal B's completion (destination address/amount/tx hash) while polling for withdrawal A, or vice versa.

### Impact Explanation
This is a status/hash misreport bug: an integrator using `processWithdrawal`/`waitForWithdrawalCompletion` for batched same-asset withdrawals can be told the wrong `destinationTx` hash for a given withdrawal request, potentially causing double-crediting, wrong-recipient bookkeeping, or premature completion confirmation for a withdrawal that in reality landed at a different address/amount. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact class from the rules.

### Likelihood Explanation
Requires no privileged action — it is triggered purely by a normal, documented SDK use case (README explicitly documents "Batch Withdrawals" with the same POA-bridge asset appearing more than once in one call), combined with the withdrawals for the same token completing close together (a realistic timing scenario for the relayer). No malicious actor needed; the bug is deterministic given >1 pending withdrawal of the same POA asset.

### Recommendation
Match POA withdrawal status entries using a more specific criteria set (e.g., destination address + amount, or an out-of-band withdrawal id/index returned by the relayer) instead of `assetId` alone. If the POA relayer API cannot currently disambiguate multiple same-asset withdrawals, the SDK should either: (1) reject/warn when a batch contains duplicate assetIds routed through POA bridge, or (2) implement the ordering-by-amount heuristic mentioned in the existing code comment, consistently applied across both `findMatchingWithdrawal` implementations.

### Proof of Concept
1. Caller submits `processWithdrawal({ withdrawalParams: [ {assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA"}, {assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: "addrB"} ] })`.
2. Both intents settle in the same NEAR tx; POA relayer processes both withdrawals and eventually returns a `withdrawals` array containing both COMPLETED records (with different `transfer_tx_hash`/`address`).
3. `sdk.createWithdrawalCompletionPromises` calls `watchWithdrawal` independently for index 0 and index 1; each internally calls `PoaBridge.describeWithdrawal`, which calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")` — both calls return the same first matching element from the array (order defined by the relayer response, which is documented as unsorted).
4. Both promises resolve to the identical `{status:"completed", txHash: <first-match-tx-hash>}`, even though the two withdrawals had different destination addresses/amounts — the caller cannot tell which destination actually received which transaction.

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {

		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
