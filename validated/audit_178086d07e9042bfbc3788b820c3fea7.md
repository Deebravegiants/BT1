Audit Report

## Title
Overweight messages that structurally exceed the XCM recursion depth limit can never be resolved by `execute_overweight` (`Error::TemporarilyUnprocessable` forever) - ([File: substrate/frame/message-queue/src/lib.rs])

## Summary
An XCM message whose nested-instruction depth exceeds `xcm_executor::RECURSION_LIMIT` (10) can be enqueued, weighed successfully during `prepare()`, and marked `Overweight` purely due to insufficient budget - but when later replayed via `MessageQueue::execute_overweight`, `XcmExecutor::execute()` will deterministically hit `XcmError::ExceedsStackLimit` regardless of the `weight_limit` supplied, so `do_execute_overweight_inner` always returns `Error::TemporarilyUnprocessable`, and the message can never transition to `Processed`.

## Finding Description
`MessageExecutionStatus::StackLimitReached` and `Unprocessable{permanent:false}` are both mapped in `do_execute_overweight_inner` (`substrate/frame/message-queue/src/lib.rs:1112-1115`) to `Err(Error::TemporarilyUnprocessable)`, never to `AlreadyProcessed` or a permanent error. `XcmExecutor::process()` (`polkadot/xcm/xcm-executor/src/lib.rs:843-903`) enforces a fixed nesting-depth counter (`RECURSION_LIMIT = 10`, defined at line 66-72), which is reset via `recursion_count::using_once` on every fresh top-level call, whether that call originates from normal block servicing or from the `execute_overweight` extrinsic. This means the recursion check is a deterministic function of the message payload's nesting structure alone - independent of `weight_limit`, of the calling context, or of how many times it is retried. If an attacker crafts a message with nesting depth > 10 it will always produce `XcmError::ExceedsStackLimit` → `ProcessMessageError::StackLimitReached` → `MessageExecutionStatus::StackLimitReached`. Separately, the weigher used during `prepare()` enforces a *total instruction count* limit, distinct from the nesting-depth counter; a message can pass weighing (and thus be classified `Overweight` for budget reasons) while still structurally exceeding the nesting-depth limit at actual execution time.

The `reap_page` cleanup path (`do_reap_page_inner`, `substrate/frame/message-queue/src/lib.rs:1150-1213`) requires `page_index < book_state.begin` (line 1155), so a stuck page can only be culled once the origin's queue has advanced past it — this is origin-traffic-dependent, not an unconditional remedy for the specific failure mode.

## Impact Explanation
For the affected origin's queue, one specific message can never reach `Processed` and will keep returning `TemporarilyUnprocessable` on every `execute_overweight` retry, regardless of the caller-supplied `weight_limit`. The `OverweightEnqueued` event/state persists, and the message's contribution to `BookStateFor::size`/`message_count` for that origin is not released until either (a) the origin queue advances enough pages for `reap_page`'s staleness-based culling to apply, or (b) the message payload itself is otherwise removed. This is a stuck-message/availability defect scoped to the specific origin and message, not an unbounded pallet-wide DoS.

## Likelihood Explanation
Feasibility requires constructing a message whose nested-instruction structure exceeds `RECURSION_LIMIT=10` while still weighing successfully under `prepare()`'s separate instruction-count limit, and getting it classified `Overweight` (not immediately discarded, since a message hitting `StackLimitReached` at first top-level service is discarded, not queued as overweight, per `process_discards_stack_ov_message`). This is plausible via `pallet_xcm::execute`/`send` or routed HRMP/UMP messages carrying attacker-influenced instructions. Once triggered, the failure is fully deterministic and repeatable on every retry since the recursion counter depends only on message structure.

## Recommendation
- Treat `StackLimitReached` returned from a manual `execute_overweight` call as a permanent condition (drop/mark permanently unprocessable and emit an event) rather than mapping it to `TemporarilyUnprocessable`, since `execute_overweight` is a top-level call and no plausible retry will succeed.
- Alternatively, decouple the weigher's instruction-count limit from the executor's nesting-depth limit so a message that will structurally exceed `RECURSION_LIMIT` at execution time is rejected/discarded during weighing.
- Provide an explicit permissionless path to purge overweight pages whose message consistently fails with `StackLimitReached`, independent of whether the origin's `book_state.begin` ever advances past the stuck page.

## Proof of Concept
1. Build a message that passes `Config::Weigher::weight()` (finite computed weight) but has nested `SetAppendix(Xcm(vec![ClearOrigin]))` chained 11+ levels deep, submitted with a `ServiceWeight` too small to cover the computed weight on first service, so it is enqueued as `OverweightEnqueued` (mirrors `execute_overweight_keeps_stack_ov_message` in `substrate/frame/message-queue/src/tests.rs:1899-1991`).
2. Call `MessageQueue::execute_overweight(origin, page_index, index, weight_limit)` with `Weight::MAX`.
3. Assert the call returns `Err(Error::TemporarilyUnprocessable)` and a `ProcessingFailed`/`ExceedsStackLimit`-style event is emitted.
4. Repeat step 2 with varying `weight_limit` values; assert the result is always `Err(Error::TemporarilyUnprocessable)` and `BookStateFor` `message_count`/`size` never decrease.
5. Assert `reap_page` returns `Err(Error::NotReapable)` while `book_state.begin == page_index`, demonstrating that in this configuration neither `execute_overweight` nor `reap_page` resolves the stuck message until further pages are serviced for the same origin.
