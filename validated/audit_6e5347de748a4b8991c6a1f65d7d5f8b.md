### Title
Webhook HMAC Only Covers the Raw Body, Not the Shop/Topic Headers, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` verifies the HMAC exclusively against the raw body, so an attacker who possesses any one validly-signed webhook body/HMAC pair (e.g. from their own store's webhook delivery, since the same `client_secret` signs webhooks for every shop of the app) can replay it to the app's webhook endpoint with forged `shop-domain` and `topic` headers pointing at a victim shop/topic, and the HMAC check will still pass.

### Finding Description
The equality this breaks is:

`shop authenticated by HMAC == shop acted upon by the webhook handler`

`Request#to_signable_string` binds the HMAC to `@raw_body` only: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates only this HMAC (covering the body) and then dispatches the handler using the attacker-controllable `request.topic` and `request.shop`: [3](#0-2) 

The `HmacValidator` itself is generic and simply compares the computed HMAC of `to_signable_string` against the received HMAC — it has no way to know that `shop`/`topic` aren't included in the signed string: [4](#0-3) 

Because Shopify signs webhooks for all shops of a given app with the same `client_secret`, an unprivileged attacker who installs the app on their own (attacker-controlled) store receives real, validly-HMAC'd webhook deliveries for that store. Since the HMAC only binds the body — not the shop or topic — the attacker can capture one such `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain (and/or the `X-Shopify-Topic` header changed to a different, more sensitive topic that the attacker's own store never actually triggered). `HmacValidator.validate` still returns `true` because it never checked those headers, and `Registry.process` will hand the forged `shop`/`topic`/body combination to the registered handler as if it authentically originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook signature is meant to guarantee: an app cannot trust that `WebhookMetadata#shop` genuinely corresponds to the shop that produced the signed payload. Depending on how a host app's webhook handler uses `shop` (e.g., looking up/mutating per-shop records, triggering `shop/redact` or `customers/data_request` compliance flows, or acting on order/product data under a different tenant's identity), this enables cross-tenant data confusion/tampering driven entirely by attacker-controlled headers, which the gem presents as verified. This matches the Critical "cross-tenant access" impact class.

### Likelihood Explanation
The prerequisite is low: any unprivileged user can install the app on a store they control (a normal, unprivileged app installation, not requiring the app's `client_secret` or any merchant credential) to obtain a legitimately signed webhook body/HMAC pair, then replay it against the same public webhook endpoint with modified `shop-domain`/`topic` headers. No access token, refresh token, or `client_secret` is needed — only observation of one's own store's webhook deliveries, which is standard, unprivileged access.

### Recommendation
Bind the shop, topic, and other routing-relevant fields into the HMAC-signed content (or independently verify `shop`/`topic` headers against out-of-band trusted state, such as the shop stored for the corresponding installation) rather than trusting them as bare headers. At minimum, `to_signable_string` should incorporate the `shop-domain` and `topic` headers so that `HmacValidator.validate` cryptographically proves the tuple `(shop, topic, body)`, not just `body`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service action).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-raw-body>`
   - Body: `{"id": 123, ...}`
3. Attacker captures `raw_body` and `X-Shopify-Hmac-Sha256`.
4. Attacker sends a forged HTTP request directly to the app's public webhook endpoint with the same `raw_body`/HMAC but:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or any topic registered by the app)
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds because the body/HMAC pair is genuinely valid.
6. The handler receives `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: <attacker body>, ...)`, believing it is an authentic Shopify-issued webhook for the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
