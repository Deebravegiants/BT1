### Title
Stale delegate grant re-arms after NFT round-trip: a former owner's delegate regains spending authority when the position NFT returns to `granted_by` — (File: contracts/controller/src/storage/account.rs)

### Summary
The Electron bug class is a use-after-free: an authorization/resource handle that should be dead is dereferenced later. In XOXNO Lending the analog is the `DelegateGrant` stored under `ControllerKey::Delegates(account_id)`. The grant is stamped only with `granted_by` (an address), not with an ownership epoch. When the account NFT is transferred, the grant is not deleted — it merely stops matching the new owner. If the NFT ever returns to the original grantor before an intervening owner writes delegates, the dormant delegate list becomes live again and the old delegate regains full account spending authority. This is a dangling authorization: a "freed" capability silently resurrects.

### Finding Description
`get_delegates` filters a stored `DelegateGrant` solely on `grant.granted_by == *owner` (contracts/controller/src/storage/account.rs:176-181). Nothing clears `Delegates(account_id)` on NFT transfer — the position-NFT contract has no transfer hook into the controller, and `transfer`/`transfer_from` on the NFT only move the token. The docs confirm the resurrection: "If the NFT returns to `granted_by` before such a write, the original delegate list is live again" (common/src/types/controller.rs:63-67), and "The stale grant stays in storage and re-arms if the token returns to `granted_by`" (contracts/position-nft/README.md:174-179). `remove_account_and_burn_nft` also does not purge the delegate entry (contracts/controller/src/account.rs:159-163), though id reuse is impossible so that leg is inert.

Once re-armed, `is_owner_or_delegate` accepts the delegate if it is an active position manager (contracts/controller/src/account.rs:115-127), and `require_owner_or_delegate` then authorizes `borrow`, `withdraw`, `migrate_from_blend`, `multiply`, and `flash_position` on the account — with delegates able to choose their own payout recipient, per the documented model that "delegates can borrow/withdraw to their chosen recipient within account gates" (docs/explanation/threat-model.md:86-87).

### Impact Explanation
Theft of user funds. After the NFT round-trips back to the original grantor, the stale delegate can `withdraw` the account's collateral to an arbitrary `to` address, or `borrow` up to the LTV limit and keep the proceeds, leaving the victim over-levered or drained. The victim's only signal is that they once granted this delegate — possibly long ago and for a different purpose (e.g., a keeper contract). The re-arm requires no action from the victim at the time of theft.

### Likelihood Explanation
Medium. Pre-conditions: (1) the victim previously called `add_delegate` granting a delegate that remains a governance-activated position manager; (2) the NFT left the victim and later returned (marketplace sale/buy-back, OTC transfer, custodial shuffle) without any intervening `add_delegate`/`remove_delegate` write by an intermediate owner. `remove_delegate` does purge stale grants when invoked by a non-grantor owner (storage/account.rs:236-238), but an intermediate owner who never touches delegates — the common case — leaves the grant intact indefinitely, with only persistent-storage TTL as the eventual expiry. The drain itself is a plain unprivileged `borrow`/`withdraw` call by the delegate.

### Recommendation
Bind grant validity to an ownership epoch rather than a bare address. Options:
- Stamp `DelegateGrant` with an `nft_transfer_epoch` maintained by the controller and incremented on a new `touch`-style entrypoint, or
- Compare `granted_by` against both the current owner and the account creation/restamp event, or
- Document-and-mitigate: make `account` reads on owner mismatch opportunistically delete the stale `Delegates` entry (the same purge `remove_delegate` performs), so the grant cannot survive a full ownership cycle.

### Proof of Concept
Using the harness primitives from tests/test-harness/tests/controller/position_nft.rs:

1. `t.enable_delegate(ALICE, "MANAGER", account_id)` — Alice grants MANAGER (an active position manager).
2. `t.nft_transfer(ALICE, BOB, account_id)` — grant goes dormant (`get_delegates(env, id, bob)` is empty) but persists in storage; Bob never calls `add_delegate`/`remove_delegate`.
3. `t.nft_transfer(BOB, ALICE, account_id)` — NFT returns to `granted_by`; the stale grant is now live again.
4. `t.borrow_as_to("MANAGER", account_id, "USDC", X, "MANAGER")` or `withdraw` — succeeds under the resurrected grant; MANAGER receives the funds. There is no `assert_reentry`-style test covering this round-trip resurrection: `remove_delegate_purges_stale_grant_preventing_resurrection` only covers the path where the intermediate owner explicitly purged (contracts/controller/tests/storage/account.rs:180-225), leaving the no-intervening-write path resurrectable by construction.
