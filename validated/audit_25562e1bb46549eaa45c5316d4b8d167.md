### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then hands the handler a `shop` value (and `topic`/`webhook_id`) that is read from an HTTP header never included in that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) that are not part of the signed payload: [2](#0-1) .

`Registry.process` validates authenticity with `Utils::HmacValidator.validate(request)`, which computes the signature only over `to_signable_string` (i.e. the raw body) using the app's `api_secret_key`, and if it matches, immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) . `HmacValidator.validate`/`validate_signature` confirms this - it only ever signs `verifiable_query.to_signable_string`: [4](#0-3) .

The identity binding broken is: `hmac == HMAC(secret, body)` is treated as proof that `shop == <the tenant that owns this body>`, when in fact `shop` is an independently-supplied, unsigned header. Any request whose body+HMAC pair was genuinely issued by Shopify for **some** shop can be replayed with a different `shop-domain` (and `topic`/`webhook-id`) header and will still pass `HmacValidator.validate`, because the header values play no role in the signature computation.

An unprivileged internet user can obtain a valid `(body, hmac)` pair simply by installing the target public/public-facing app on their own store - Shopify will deliver genuinely signed webhooks to that installer for their own shop. The installer/attacker can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a victim shop's domain. `Registry.process` will pass HMAC validation (the body/HMAC pair is untouched) and dispatch the handler with `WebhookMetadata.shop` set to the victim's domain, `topic` set to whatever the attacker chooses, exactly as documented for the app author to trust: [5](#0-4) .

### Impact Explanation
This is a cross-tenant identity-confusion bug at the gem level: the primitive this gem exposes for verifying "this webhook is authentically for shop X" does not actually bind the shop (or topic) to the signature it validates. A host application that follows the gem's documented contract - trusting `data.shop`/`data.topic` after `Registry.process` returns without error - will act on forged tenant/topic attribution (e.g. process a fabricated `app/uninstalled`, `orders/create`, or GDPR `shop/redact` event as if it originated from a victim shop it does not control), which is a cross-tenant access impact reachable by any unprivileged user who can install the app once.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (a normal, low-privilege action for any Shopify merchant/developer testing a public app) and be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint - both trivially satisfied by an "unprivileged internet user," with no access token, `client_secret`, or elevated credential required.

### Recommendation
Include the security-relevant identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable payload validated by `HmacValidator`, or otherwise cryptographically bind them to the body (e.g., verify them server-side against Shopify's known webhook metadata/registered shop list) before constructing `WebhookMetadata` and dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a legitimate webhook (e.g. `orders/create`) with a genuine `X-Shopify-Hmac-SHA256` header computed over the JSON body using the app's real `client_secret`.
2. Attacker captures the raw body and its valid HMAC.
3. Attacker POSTs that identical body + HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)`. [3](#0-2) 
5. The registered handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"`, letting the attacker inject events attributed to a shop they do not own/control.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
