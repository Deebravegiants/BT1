## Finding: Webhook shop/topic identity not bound by HMAC, enabling cross-tenant replay

The `ShopifyAPI::Webhooks::Request` HMAC signature only covers the raw request body, while the tenant-identifying `shop`, `topic`, `webhook_id`, and `api_version` values are taken directly from unauthenticated HTTP headers and passed straight through to app-provided webhook handlers.

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , but `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC signature [2](#0-1) . `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the body, then forwards `request.shop`, `request.topic`, and `request.webhook_id` unchecked to the registered handler as `WebhookMetadata` [3](#0-2) .

### Finding Description
This is the same bug class as the external report: a value that gates/identifies an action (there, `minValue`/`maxValue` parameter constraints; here, the `shop`/`topic` identity of a webhook) is not actually covered by the check meant to authenticate it (there, the range validation; here, the HMAC signature), so it can be substituted with attacker-controlled data after the "authentic" check passes.

The equality this code implicitly and incorrectly assumes is:
```
shop_used_by_handler (request.shop, from header) == shop_authenticated_by_hmac (bound only to raw_body)
```
Since `to_signable_string` binds only `@raw_body`, this equality does not hold. Any two requests with identical bodies but different `x-shopify-shop-domain`/`x-shopify-topic`/`x-shopify-webhook-id` headers produce identical HMACs, because `OpenSSL::HMAC.hexdigest` is computed only over `signable_string` (the body) [4](#0-3) .

Confirmed by the test fixture: the HMAC is computed solely over `"{}"`, entirely independent of the `x-shopify-shop-domain`/`x-shopify-topic` header values used in the same request [5](#0-4) .

An attacker who legitimately operates their own Shopify store (an unprivileged actor with no special access to the app's `client_secret` or another merchant's data) receives genuine webhooks from Shopify for their own shop, each with a valid HMAC for a given body. Because the HMAC never binds `shop`/`topic`/`webhook_id`, the attacker can resend that exact body to the app's public webhook endpoint while swapping `x-shopify-shop-domain` to a victim shop's domain (or `x-shopify-topic` to a different, more sensitive topic). `Registry.process` still finds `HmacValidator.validate(request)` true (HMAC only checks the body) [6](#0-5) , and dispatches to the handler with `shop: request.shop` set to the victim's shop and/or an unintended `topic` [7](#0-6) . Any app whose webhook handler trusts `WebhookMetadata#shop` as the authenticated tenant identifier (which is the gem's own documented usage pattern) will act on behalf of, or write records against, a shop the attacker does not control — a cross-tenant confusion enabled entirely by this gem's own `Request`/`Registry` design.

### Impact Explanation
This breaks a tenant/authentication boundary: the `shop` value trusted by downstream app code as "this webhook was authenticated as belonging to shop X" is not actually bound by the cryptographic check that is supposed to authenticate it. This falls under the "cross-tenant access" Critical impact category — an attacker can cause the app to process/act on data under the identity of a shop they do not own, using only a body+HMAC pair they legitimately obtained from their own store's webhooks.

### Likelihood Explanation
Requires only that the attacker operate any shop with the app installed (or otherwise capture one legitimate webhook body+HMAC pair) and be able to reach the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or other merchants' credentials is needed. This is a realistic, low-effort attack path.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the HMAC-signed payload used by `to_signable_string`, or otherwise independently verify that these header values match Shopify-issued, signed metadata before trusting them in `Registry.process`. At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as authenticated merely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `{"id":123}`, headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker resends the identical body to the app's public webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the raw body only) and it still matches, since headers are excluded [1](#0-0) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [7](#0-6) , causing the app to perform actions/writes attributed to `victim.myshopify.com` triggered entirely by the attacker.
