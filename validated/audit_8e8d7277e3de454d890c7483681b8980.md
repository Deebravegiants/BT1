### Title
Webhook `shop` (and other Shopify-supplied identity headers) are not covered by the HMAC signature verified by `Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC signature it checks only covers the raw request body. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values that are handed to the handler as trusted, verified data come from HTTP headers that are excluded from the signed bytes. This is the same class of bug as the report: a field that is *acted on* (here, the shop/tenant binding) is not covered by the authentication check (here, the HMAC), so an attacker who possesses one validly-signed webhook body can rebind it to an arbitrary shop identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`, and `Registry.process` gates dispatch on this check: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the Shopify headers are included in the signed material: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cross-check against the signed body: [3](#0-2) 

These header-derived, **unauthenticated** values are then passed into `WebhookMetadata` and delivered to the app's handler as if they were verified: [1](#0-0) 

The gem's own documentation reinforces that the handler is expected to trust this identity binding, stating that `process` "will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and lists `shop` as one of the trusted fields passed to `data`: [4](#0-3) [5](#0-4) 

The broken identity equality is:
`hmac_signed_bytes(raw_body) == valid` should imply `(shop, topic, webhook_id) == (Shopify-issued shop, topic, webhook_id)`, but in fact only `raw_body` is bound by the HMAC — `shop` is not part of the equality Shopify's signature protects.

### Impact Explanation
An attacker who runs their own installed instance of the app (a legitimate, but adversarial, tenant) receives real Shopify webhooks for their own shop, correctly HMAC-signed over the JSON body. Because the header fields are excluded from the signature, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a different, victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body bytes), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the victim's domain while the `body` is attacker-controlled content from the attacker's own shop. Any app logic keyed by `data.shop` (the tenant the gem asserts is Shopify-verified) will process attacker-supplied data under another tenant's identity — a cross-tenant data-integrity/impersonation issue that maps to the "Critical - cross-tenant access" impact category, since it lets one tenant inject or spoof events attributed to another tenant purely through this gem's own webhook verification API.

### Likelihood Explanation
Likelihood is bounded by the same constraint that made the original report a legitimate but "no loss of funds" finding: the attacker needs at least one legitimately signed webhook body (obtainable trivially by installing the app on any shop they control) and the ability to send arbitrary HTTP requests with attacker-chosen headers to the app's public webhook endpoint (also trivial, since that endpoint is by design internet-reachable and unauthenticated at the transport layer). No secret material, session, or token is required — only observation of one's own legitimate webhook traffic.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise cryptographically bind them to the raw body before trusting them in `WebhookMetadata`. At minimum, `Registry.process` (or `Request`) should require the caller to independently confirm `request.shop` corresponds to a shop with an active session/installation known to the app, rather than presenting it as data that has already been "verified... did indeed come from Shopify" per the current documentation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers `orders/create`, and captures the real webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's registered webhook route with the same body `B` and same `x-shopify-hmac-sha256: H`, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`B`) — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, so attacker-controlled data `B` is processed and stored/acted upon as if it belongs to `victim-shop.myshopify.com`.
