### Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) it hands to app webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. The `shop` value is never bound to the signed content, so any request bearing a *valid* body+HMAC pair (which an attacker with access to any single shop can legitimately obtain, since the app's HMAC secret is a single global `client_secret` shared across all installs) can be replayed with an arbitrary `shop-domain` header, causing the receiving app to attribute authenticated webhook data to a different tenant.

### Finding Description
`Registry.process` only asserts that the HMAC over the body is valid: [1](#0-0) 

The HMAC validator computes/verifies signatures using `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` returns only `@raw_body` — the shop, topic, webhook id, and api version headers are excluded from what is signed: [3](#0-2) 

`shop` is read straight from an attacker-controllable header with no cross-check against the signed body: [4](#0-3) 

That unverified `shop` value is then trusted and forwarded to the app's `WebhookHandler.handle`, which apps use to scope data (e.g., look up shop records, store data, or resolve per-shop configuration): [5](#0-4) [6](#0-5) 

The identity binding broken here is: `HMAC(secret, raw_body)` proves "signed by this app's secret" but is asserted by the code to also mean `shop == the tenant that owns the body`. Since `secret` is a single value shared across every shop that installs the app (verified via `Context.api_secret_key` / `old_api_secret_key` in `HmacValidator.validate`), any shop that has legitimately installed the app can obtain a validly-signed `(body, hmac)` pair for its own webhook traffic, then resend that exact pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. The signature still validates because it never covered the shop field.

### Impact Explanation
This is a cross-tenant identity confusion: a low-privileged actor (an operator of their own shop that has installed the target app) can cause the app to process a webhook body it authenticated as "real" while impersonating a different tenant. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to write/associate incoming order, customer, or app-uninstalled data to a shop record, or to trigger data-redaction/GDPR flows for `customers/redact` or `shop/redact`), this can lead to cross-tenant data corruption, unauthorized redaction/deletion for an unrelated shop, or injection of attacker-controlled data into another tenant's records — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Likelihood is moderate-to-high for any app relying on this gem's webhook signature check for tenant-binding: the mandatory topics (`shop/redact`, `customers/redact`, `customers/data_request`) are exactly the security/privacy-sensitive events this mechanism is used for. Any entity capable of installing the target app on a shop it controls (a completely unprivileged internet action) can harvest valid `(raw_body, hmac)` pairs and then send crafted HTTP requests directly to the app's public webhook endpoint with a forged `shop-domain` header, since the gem provides no other integrity check binding shop to body.

### Recommendation
Include the `shop` (and ideally `topic`) in the signed material verified for webhooks, or independently verify that the shop asserted in the header is one the app has an active install/session for before trusting `WebhookMetadata#shop`, e.g., extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to require the header-derived shop to be consistent with a per-shop record instead of relying solely on the body HMAC.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify sends (both are valid because they're signed with the app's single global `client_secret`).
2. Replay that exact body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`), `Registry.process` validates the HMAC successfully because `to_signable_string` only checks `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`), and the handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) — the app now processes attacker-supplied data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
