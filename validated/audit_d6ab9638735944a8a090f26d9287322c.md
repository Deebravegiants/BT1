### Title
Missing domain separator in relayer beneficiary-redirect signature allows cross-instance replay to steal accumulated fees - (File: modules/pallets/relayer/src/accumulate.rs)

### Summary
The `beneficiary_message` function that a relayer signs to redirect its accumulated fees to a different beneficiary address omits any chain/genesis/pallet-instance identifier from the signed payload. The signature is bound only to `(nonce, state_machine, beneficiary)`, where `state_machine` identifies the *remote source chain* the relayer delivered on, not the Hyperbridge instance verifying the signature. This mirrors the reported "signature proof not including a domain separator" bug class.

### Finding Description
`accumulate()` accepts an unsigned `WithdrawalProof` whose optional `beneficiary_details` field carries `(beneficiary_address, signature)`. The message that is actually signed is: [1](#0-0) 

```
pub fn beneficiary_message(nonce: u64, state_machine: StateMachine, beneficiary: &[u8]) -> [u8; 32] {
    sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
```

This hash contains no domain separator tying it to the specific Hyperbridge chain/runtime instance verifying it (e.g. no genesis hash, no local parachain/consensus-state identifier, no contract/pallet address analog). It only binds to the *nonce* (local to `Nonce::<T>::get(delivery_address, state_machine)`) and the *remote* `state_machine` id being withdrawn from — the same `state_machine` values (e.g. Ethereum, Arbitrum, a given parachain id) recur identically across every separate Hyperbridge deployment (mainnet, testnets, or any other runtime instance that reuses this pallet), because `StateMachine` values are defined by the external chain being bridged, not by the verifying instance.

The verification path: [2](#0-1) 

recovers the signer from `msg` and only checks it equals `delivery_address`; it never checks anything specific to *this* runtime/genesis. Because relayer operators commonly run the same signing key across multiple Hyperbridge deployments that track fees for the same set of remote chains, and because the `Nonce` counter independently starts at `0` in every fresh deployment, a signature a relayer produces to redirect fees on one Hyperbridge instance (e.g. a testnet, or any instance where `Nonce[relayer][state_machine]` happens to equal the value used elsewhere) is byte-for-byte valid and replayable on a different Hyperbridge instance where the corresponding nonce coincides.

The call itself is dispatched via the unsigned `accumulate_fees` extrinsic, reachable by anyone who can submit a transaction: [3](#0-2) 

An attacker who observes (or obtains, e.g. by tricking the relayer into signing on a lower-stakes/test deployment) a valid `beneficiary_message` signature can replay it against a target instance's `accumulate_fees` call, redirecting that relayer's fee accrual on the target instance to an attacker-controlled `beneficiary_address`.

### Impact Explanation
This is a cross-domain signature replay that lets an attacker redirect a legitimate relayer's earned fees to an address of the attacker's choosing on a different Hyperbridge deployment/instance, resulting in theft of relayer fee funds without the relayer's on-that-instance consent. This satisfies "concrete theft ... of funds" under the validation criteria.

### Likelihood Explanation
Exploitability depends on an attacker obtaining a validly-signed `beneficiary_message` from a context outside the target instance (e.g., a testnet/staging deployment sharing relayer keys with production, or any other Hyperbridge deployment tracking the same remote `state_machine`s) and on the target's per-`(delivery_address, state_machine)` nonce coinciding with the one used when the signature was produced. This is plausible in a multi-deployment/multi-network ecosystem like Hyperbridge (mainnet + testnets + potentially other parachains all running `pallet-ismp-relayer`), especially since nonces for a fresh relayer/state_machine pair always start at `0`, making the very first redirect signature on any instance trivially replayable on any other instance where that pair has not yet been used.

### Recommendation
Include an instance-specific domain separator in `beneficiary_message` — e.g. the destination runtime's genesis hash (`frame_system::Pallet::<T>::block_hash(0)`), or another unique instance identifier plus the pallet's own identifier (`MODULE_ID`) — analogous to adding `chain.id` and the verifying contract address as done in the referenced `hashForKYC()` fix, so a signature produced for one Hyperbridge instance cannot be replayed against another.

### Proof of Concept
1. Relayer `R` delivers requests on remote chain `X` on Hyperbridge deployment `A` (e.g. a testnet), accruing fees; `Nonce[R][X]` on `A` is `0`.
2. `R` signs `beneficiary_message(0, X, attacker_or_test_beneficiary)` for a legitimate redirect on `A`.
3. Deployment `B` (e.g. mainnet, or another parachain instance) independently also tracks fees for `R` on remote chain `X`, and `Nonce[R][X]` on `B` also happens to be `0` (true for any relayer/state_machine pair not yet used on `B`).
4. An attacker who has observed the signature from step 2 constructs a `WithdrawalProof` on `B` with `beneficiary_details = (attacker_address, signature)` and submits `accumulate_fees` (unsigned, permissionless) on `B`.
5. `accumulate()` on `B` verifies `beneficiary_message(0, X, attacker_address)`... — actually the signed beneficiary bytes must match, so the attacker replays exactly the beneficiary that was signed on `A`; if that beneficiary is attacker-controlled (e.g. `R` was tricked into signing a "test" redirect to an address the attacker also controls), the fees accrued by `R` on `B` for chain `X` are now redirected to the attacker's address on `B` as well, without `R` ever intending or authorizing this on `B`.
