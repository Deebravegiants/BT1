This confirms the finding: `Index` and `Show` both call `presenters.NewBridgeResource` which unconditionally sets `OutgoingToken: b.OutgoingToken` in plaintext, and the router wires `GET /v2/bridge_types`/`GET /v2/external_initiators` without `RequiresEditRole`, while POST/PATCH/DELETE do have it. The RBAC test matrix and controller tests corroborate that `view` role users can reach these GET endpoints and that `OutgoingToken` is present in the response body.

The claim is well-supported by the actual code: root cause (asymmetric field exposure vs. `IncomingToken`), broken assumption (GET routes assumed safe for all authenticated roles, but they leak outbound credentials), concrete reachable exploit path (authenticate as `view` role → `GET /v2/bridge_types` or `/v2/external_initiators` → plaintext `outgoingToken` in response), and a verifiable impact (credential/secret exfiltration enabling node impersonation towards external adapters). This matches the in-scope impact category "key/secret exfiltration." Nothing in `SECURITY.md` excludes this — it's not a leaked-credential-dependent issue (the credential is disclosed by the bug itself), not requiring operator/admin access (only a `view` role, the lowest privilege tier), not a test/mock/config-only issue.

Audit Report

## Title
Unprivileged "view"-role users can read plaintext `OutgoingToken` webhook credentials for all Bridges and External Initiators via `GET /v2/bridge_types` and `GET /v2/external_initiators` - (File: `core/web/presenters/external_initiators.go`, `core/web/presenters/bridges.go`)

## Summary
The `BridgeType.OutgoingToken` and `ExternalInitiator.OutgoingToken`/`OutgoingSecret` fields are plaintext credentials the node uses to authenticate its outbound calls to adapters/external initiators. Unlike `IncomingToken`, which uses `omitempty` and is only populated on creation, `OutgoingToken` is unconditionally serialized by `NewBridgeResource` and `NewExternalInitiatorResource`, and the `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` routes are registered without `auth.RequiresEditRole`, meaning any authenticated `view`-role user can retrieve them.

## Finding Description
`core/web/presenters/bridges.go` defines `OutgoingToken string \`json:"outgoingToken"\`` with no `omitempty`, and `NewBridgeResource` at [1](#0-0)  populates it from `b.OutgoingToken` unconditionally, so both `BridgeTypesController.Index` and `.Show` return it (`core/web/bridge_types_controller.go` [2](#0-1)  and [3](#0-2) ). The analogous `ExternalInitiatorResource` in `core/web/presenters/external_initiators.go` does the same for `ExternalInitiator.OutgoingToken`.

`core/web/router.go` wires `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` directly to the `Index`/`Show` handlers without any `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, while `Create`/`Update`/`Destroy` are wrapped with `auth.RequiresEditRole`. `core/web/auth/auth.go`'s `RequiresEditRole` explicitly rejects `UserRoleView` and `UserRoleRun`, confirming these GET routes are the only ones in this group that permit `view`-role access. This is corroborated by the RBAC test matrix in `core/web/auth/auth_test.go`, which lists these GET routes as `viewOnlyAllowed = true`, and by `core/web/external_initiators_controller_test.go`, which asserts `OutgoingToken` is present in the list response body.

The security assumption broken here is that GET (read) endpoints for these resources are safe for the lowest-privilege `view` role — but that assumption fails for the `OutgoingToken` field specifically, since it is a credential (not merely descriptive metadata), unlike everything else exposed to `view` users elsewhere in the API.

## Impact Explanation
A `view`-role user (or a `run`-role user, since `run` is also excluded only from `RequiresEditRole`, not from unguarded GET routes) can enumerate every configured Bridge and External Initiator and obtain plaintext `OutgoingToken`/`OutgoingSecret` values via a single authenticated GET request. These tokens authenticate the node's outbound calls to external adapters and initiators; obtaining them lets a low-privilege account impersonate the node's outbound identity toward those external services. This is a concrete secret/credential exfiltration issue reachable from a low-privilege but authenticated actor, matching the in-scope "key/secret exfiltration" impact category.

## Likelihood Explanation
The exploit requires only a valid `view`-role session or API token — a routinely provisioned, low-privilege role intended for read-only/monitoring access — and a single unauthenticated-role-gated GET call. No additional bypass, timing, or race condition is needed; the exposure is deterministic and reproducible on every call to these endpoints on any node with configured bridges/external initiators.

## Recommendation
- Do not return `OutgoingToken`/`OutgoingSecret` in `Index`/`Show` responses; mirror the `IncomingToken` pattern (`omitempty`, only populated at creation time in `BridgeTypesController.Create`).
- Alternatively, gate `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, `GET /v2/external_initiators` (and the GraphQL `Bridge.outgoingToken` resolver) behind `auth.RequiresEditRole` or `auth.RequiresAdminRole`.
- Apply the redaction pattern used elsewhere for secrets (e.g., masking to a fixed placeholder) to these presenter fields on read paths.

## Proof of Concept
1. Create a chainlink node user with role `view` (e.g., via `chainlink admin users create --role=view`).
2. Authenticate as that user and issue `GET /v2/bridge_types` and `GET /v2/external_initiators`.
3. Observe the JSON response includes `outgoingToken` populated in plaintext for each bridge/external initiator, as verified by the existing assertions in `core/web/external_initiators_controller_test.go` (`assert.Equal(t, eiBar.OutgoingToken, externalInitiators[0].OutgoingToken)`) and the `viewOnlyAllowed = true` RBAC test entries for these routes in `core/web/auth/auth_test.go`.
4. Use the retrieved `OutgoingToken` to authenticate outbound requests as if from the node, demonstrating impersonation capability toward the external adapter/initiator.
