**Analysis:**

`WriteSet::update_total_supply` in `types/src/write_set.rs` has exactly one caller in production code: `TransactionOutput::update_total_supply`, which itself has exactly one caller: `aggregate_and_update_total_supply` in `aptos-move/aptos-vm/src/sharded_block_executor/sharded_aggregator_service.rs`. [1](#0-0) [2](#0-1) 

This is a purely internal, executor-side post-processing routine used only when sharded block execution is enabled. It reconciles the total-supply aggregator value across shards after the VM has already independently computed each shard's transaction outputs, using a delta computed from `DeltaU128::get_delta` applied to values that were themselves produced by VM execution (`txn_output.write_set().get_total_supply()`), not from any externally supplied or attacker-controlled value. [3](#0-2) 

Critically, `update_total_supply` internally asserts `.is_some()` on the map insert, meaning it only *overwrites* an existing total-supply write op that the VM already produced for that transaction — it cannot inject a brand-new total-supply write into a transaction that didn't already touch the aggregator key. [1](#0-0) 

There is no unprivileged transaction, package, view, authenticator, API, bytecode, or proof-input path that reaches this function with an attacker-controlled `u128`. It is not invoked from transaction execution entrypoints, Move VM dispatch, resource writes, or any externally-facing API — it is strictly an internal reconciliation step within the sharded executor's aggregator overriding mechanism (`AggregatorOverriddenStateView`), used to correct for the placeholder base value (`TOTAL_SUPPLY_AGGR_BASE_VAL`) injected during sharded execution. [4](#0-3) 

Since no unprivileged entrypoint can supply an arbitrary value into `update_total_supply`, and the function cannot fabricate a total-supply key that wasn't already present, the proposed attack path does not cross a real custody boundary. This does not meet the review's decision standard for a valid finding.
