### Title
Unchecked zero `uniswapV2` router permanently disables native-token message dispatch - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` unconditionally call `IUniswapV2Router02(_hostParams.uniswapV2).WETH()` and `.swapETHForExactTokens()` whenever a caller pays with `msg.value > 0`. `HostParams.uniswapV2` has no non-zero validation anywhere in the constructor or `updateHostParams`, and production tooling explicitly deploys with it set to `address(0)` (Tron migration script), mirroring the external report's root cause: a dependency address left as the zero address that a core, unprivileged path calls unconditionally.

### Finding Description
`HostParams.uniswapV2` is stored without any zero-address validation: [1](#0-0) 

`dispatch(DispatchPost)` and `dispatch(DispatchGet)`, both externally callable by any unprivileged sender, branch on `msg.value > 0` and unconditionally invoke the configured router: [2](#0-1) [3](#0-2) 

The same unconditional call pattern exists in the shared `HyperApp.quote()` helper that every app built on top of `EvmHost` uses to price native-fee dispatch: [4](#0-3) 

Deployment tooling for Tron explicitly defaults `uniswapV2` to the zero address: [5](#0-4) 

and the mainnet deploy script only sets a real router when `UNISWAP_V2`/`UNIVERSAL_ROUTER` env vars are present, otherwise leaving `uniswapV2` at its zero-value default: [6](#0-5) 

Calling `WETH()` on an address with no code causes the ABI decoding of the return value to fail, reverting the entire transaction. Because there is no guard (`uniswapV2 != address(0)`) before this call, any transaction that includes `msg.value > 0` on a chain where `uniswapV2` is zero reverts unconditionally, permanently disabling the native-token payment path for dispatch on that chain — exactly analogous to `StableOracleDAI.getPriceUSD()` always reverting because `ethOracle` is hardwired to the zero address.

### Impact Explanation
This is reachable by any unprivileged caller invoking `EvmHost.dispatch(...)` with native value, or any `HyperApp`-derived contract calling `quote()`/`dispatchWithFeeToken` fee-estimation helpers that route through the same zero router. The native-fee dispatch route becomes a message route that is permanently unable to process native-token-funded requests on any chain where `uniswapV2` is unset/zero (e.g. Tron by default, or any EVM deployment where the router env var is omitted), meeting the "route unable to deliver messages" bar. It does not directly cause fund loss (the call reverts atomically, so `msg.value` is not lost), but it is a persistent denial of the native-payment dispatch functionality that governance cannot self-heal without a full `updateHostParams` proposal, and any app relying on `HyperApp.quote()` for gas estimation before dispatch will also be perpetually broken on that host.

### Likelihood Explanation
High for any deployment that leaves `uniswapV2` unset — the Tron deploy script defaults to the zero address, and the general `DeployIsmp.s.sol` script only assigns a router conditionally, so a misconfigured or partial deployment silently ships with a broken native-fee path. No malicious actor is required; a routine "post via native ETH" call from any user triggers the revert once misconfigured.

### Recommendation
Add an explicit `uniswapV2 != address(0)` check (and ideally a `.code.length != 0` contract check, mirroring the pattern already used for `consensusClient` in `updateHostParams`) both in `EvmHost`'s constructor/`updateHostParams` and defensively in `dispatch()`/`HyperApp.quote()` before invoking `IUniswapV2Router02`. If a router is genuinely unavailable on a given chain (e.g., Tron), the native-payment branch should revert with an explicit `NativePaymentUnsupported`-style error rather than an opaque low-level ABI-decode revert, and deployment scripts should fail loudly instead of silently defaulting to the zero address.

### Proof of Concept
1. Deploy `EvmHost` (or Tron's `TronHost`) with `HostParams.uniswapV2 = address(0)` — the default when `UNISWAP_V2` env var is unset, per `evm/tron/migrations/2_deploy_ismp.js` lines 55-62.
2. Any user calls `dispatch(DispatchPost)` (or `DispatchGet`) with `msg.value > 0`.
3. Inside `dispatch`, `IUniswapV2Router02(address(0)).WETH()` is called; since `address(0)` has no code, the external call returns no data and Solidity's ABI decoding of the expected `address` return value reverts the transaction.
4. Every native-funded dispatch call on this host reverts indefinitely until governance pushes an `updateHostParams` request through `HostManager` pointing `uniswapV2` at a real router — a governance round-trip is required to unblock a route that should never have shipped broken.

struct HostParams {
    // The fee token contract address. This will typically be DAI.
    // but we allow it to be configurable to prevent future regrets.
    address feeToken;
    // The admin account, this only has the rights to freeze, or unfreeze the bridge
    address admin;
    // Ismp message handler contract. This performs all verification logic
    // needed to validate cross-chain messages before they are dispatched to local modules
    address handler;

    // which receives governance requests from the Hyperbridge chain to either

    address hostManager;

    // The consensus client contract which handles consensus proof verification
    address consensusClient;

}
