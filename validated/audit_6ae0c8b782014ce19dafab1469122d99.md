Audit Report

## Title
User existence disclosure via distinguishable login error messages on unauthenticated `/sessions` endpoint - (File: core/sessions/localauth/orm.go)

## Summary
The `orm.CreateSession` function in the local-auth login flow returns different, distinguishable error messages depending on whether the submitted email does not correspond to a user or the password does not match an existing user's hash. These raw errors are propagated verbatim by `SessionsController.Create` to the HTTP client as a 401 response, and the `/sessions` POST route is not gated by `auth.Authenticate` middleware, making it reachable by any unauthenticated caller.

## Finding Description
`orm.CreateSession` first calls `o.FindUser(ctx, sr.Email)`; if no matching user row exists, the raw database error (e.g., `sql: no rows in result set`) is returned immediately [1](#0-0) . If a user is found, the code then performs an email compare and returns `"Invalid email"` on mismatch, or `"Invalid password"` if the password hash check fails [2](#0-1) . In either scenario, the "user does not exist" case produces a message text distinct from the "wrong password for existing user" case.

`SessionsController.Create` forwards this error directly into the HTTP response with no normalization: `jsonAPIError(c, http.StatusUnauthorized, err)` [3](#0-2) . The `/sessions` route group is registered via `sessionRoutes(app, api)` in the top-level router alongside `debugRoutes`/`healthRoutes`, without any `auth.Authenticate` middleware wrapping it (unlike the GraphQL `/query` endpoint, which explicitly uses `auth.AuthenticateGQL`) [4](#0-3) . This confirms the endpoint is reachable pre-authentication by design (it is the login endpoint itself).

The same email-then-password branching pattern, producing distinguishable lowercase `"invalid email"` / `"invalid password"` errors, is duplicated in the LDAP and OIDC local-fallback authenticators [5](#0-4) [6](#0-5) .

## Impact Explanation
An unauthenticated network client that can reach the node's API can distinguish "no such user" responses from "user exists but wrong password" responses by observing the error text returned from `/sessions`. This is a CWE-200-class user enumeration issue that lowers the bar for targeted credential stuffing/brute force against known-valid Control Panel/API accounts, consistent with the impact described in the referenced advisory, and here achievable from a fully unauthenticated starting point rather than an authenticated low-privilege one.

## Likelihood Explanation
High. The `/sessions` endpoint is intentionally reachable without authentication (it is the login mechanism), requires no special setup, and the difference in returned error text is a deterministic, code-level behavior triggerable on every request with no timing or race dependency.

## Recommendation
Normalize all login failure paths in `orm.CreateSession` (email not found, email mismatch, password mismatch) to a single generic message such as `"invalid credentials"` before returning to the caller, and apply the same normalization in the LDAP and OIDC `localLoginFallback` equivalents. Ensure `SessionsController.Create` never forwards provider-internal error text verbatim to unauthenticated clients, and perform equivalent-cost work (e.g., dummy hash comparison) regardless of whether the email exists to avoid a timing side channel reintroducing the same disclosure.

## Proof of Concept
1. `POST /sessions` with `{"email": "known-admin@example.com", "password": "wrongpassword"}` → observe HTTP 401 body containing `"Invalid password"`.
2. `POST /sessions` with `{"email": "doesnotexist@example.com", "password": "wrongpassword"}` → observe HTTP 401 body containing a distinct message (the raw "no rows" database error, or `"Invalid email"` in edge cases where the query normalizes case but the compare fails).
3. The differing error text between steps 1 and 2 confirms whether `known-admin@example.com` is a registered user, without any authentication or prior access — verifiable via a Go integration test hitting `SessionsController.Create` with a seeded existing user and a non-existent email, asserting the two distinct response bodies.
