### Title
Unauthenticated arbitrary call execution in `CallDispatcher.dispatch()` allows theft of in-flight escrow/output funds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated function that executes an attacker-supplied array of arbitrary `(to, value, data)` calls against whatever balance the contract currently holds, with no caller restriction and no reentrancy guard of its own. Because a single canonical `CallDispatcher` instance is shared across `IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleToken`, and their Tron equivalents, and each of these apps temporarily routes real user/solver funds through it mid-transaction (predispatch assets, swept order inputs, solver-delivered fill outputs, minted/unlocked HFT tokens), any actor able to get code executed during one of the app's own `dispatch()` calls can re-enter `CallDispatcher.dispatch()` directly — bypassing the calling app entirely (and therefore bypassing that app's own `nonReentrant` guard, which only protects its own entry points) — and redirect the balance the dispatcher is holding at that instant to an address of the attacker's choosing.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes a `Call[]` and executes each entry with `to.call{value: call.value}(call.data)`, with no `msg.sender` check at all: [1](#0-0) 

This contract is deployed once and reused as `_params.dispatcher` by `IntentGatewayV2`/`IntentsBase` for both predispatch (swap-before-escrow) and postdispatch (fill-then-act) calldata, and by `HyperFungibleToken`/`WrappedHyperFungibleToken` for calldata execution after mint/unlock, per the documented design: [2](#0-1) 

In `IntentGatewayV2.placeOrder`, the attacker's own `order.predispatch.call` (fully attacker-controlled) is executed by the dispatcher while it holds the attacker's just-transferred predispatch assets, before a second dispatcher call sweeps the resulting balance back to the gateway: [3](#0-2) 

More critically, in `IntentsBase._execute` (invoked from `fillOrder`), the order's `output.call` — also set by the order's original placer, not by the solver — is executed against the balance the *solver* just delivered to the dispatcher as fill payment, before the dust-sweep call: [4](#0-3) 

Because `to.call(...)` inside `CallDispatcher.dispatch()` hands full control to an attacker-nominated `to` address, that contract's callback can itself invoke `CallDispatcher.dispatch()` a second time with a fresh, attacker-chosen `Call[]` — this call goes directly to `CallDispatcher`, never back through `IntentGatewayV2` or `IntentsBase`, so any `nonReentrant` modifier on those contracts (confirmed present on `IntentGatewayV2`) provides no protection. The only requirement for exploitation is that the dispatcher hold a nonzero, attacker-reachable balance at some point — which is guaranteed by design during predispatch/postdispatch/HFT calldata execution, since those flows explicitly park real user or solver funds on the dispatcher before sweeping.

This is the closest reachable analog to the CVE-2024-24811 bug class ("unauthenticated arbitrary [instruction] execution against the resource an unauthenticated caller is not supposed to control"): here the "resource" is the token/ETH balance the shared `CallDispatcher` holds mid-transaction, and the "unauthenticated execution" is the missing caller restriction on `dispatch()`.

### Impact Explanation
An attacker who places an order with a malicious `predispatch.call`/`output.call` target can drain funds that are momentarily custodied by the shared `CallDispatcher` — most severely, a solver's freshly delivered fill-output tokens in `IntentsBase._execute`, before they are paid to the order beneficiary and before dust is swept — resulting in direct theft of solver-provided liquidity per exploited fill. This meets the "concrete theft of funds" bar: the loss is not bounded to the attacker's own deposited assets, since the same dispatcher instance is shared across concurrent apps/flows and its balance at the moment of the nested `dispatch()` call is not restricted to funds belonging to the calling order.

### Likelihood Explanation
High for a determined intent solver/order-placer: reaching `output.call`/`predispatch.call` execution requires only placing an ordinary order through `IntentGatewayV2` (a permissionless, unprivileged action) with a crafted output/predispatch target contract. No proof forgery, consensus compromise, or privileged role is needed — only a single submitted order/transaction, matching the "single submitted order" reachability bar in scope.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., `onlyRegisteredCaller`/`onlyOwner`-configured per deploying app) or, preferably, make `CallDispatcher` non-shared/ephemeral per invocation (deploy a fresh minimal-proxy instance per `dispatch` invocation, or use a `msg.sender`-scoped balance accounting model) so that a nested `dispatch()` call can never touch value belonging to a different logical operation. Additionally add a reentrancy guard directly on `CallDispatcher.dispatch()` itself, independent of any guard in the calling app.

### Proof of Concept
1. Attacker deploys `Reenterer`, a contract that, when called by `CallDispatcher`, immediately calls back into `CallDispatcher.dispatch()` with a new `Call[]` transferring the dispatcher's current token balance to the attacker's address: [1](#0-0) 
2. Attacker (as order placer) creates an `IntentGatewayV2` order whose `order.output.call` targets `Reenterer` with a no-op payload, and whose real output assets are DAI/USDC as in the existing fixture flow: [5](#0-4) 
3. When a solver calls `fillOrder`, `_execute` sends the solver's delivered output tokens to `dispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`, which invokes `Reenterer`: [6](#0-5) 
4. Inside that callback, `Reenterer` calls `dispatcher.dispatch(stealCalls)` directly (not through `IntentGatewayV2`, so its `nonReentrant` guard never triggers) and transfers the dispatcher's current token balance — the solver's just-delivered output — to the attacker, before `IntentsBase._execute`'s own sweep-back logic runs.

Note: I was not able to execute this scenario end-to-end in a live Foundry run (no code execution available here), so gas/ordering edge cases (e.g., whether `IntentGatewayV2`'s transient-storage solver-selection check could incidentally block a specific variant of this path) are not fully verified; the root cause — `CallDispatcher.dispatch()` having no caller authentication or reentrancy protection while custodying shared, cross-app value — is confirmed directly from the source.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }
