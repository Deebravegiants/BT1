### Title
Permissionless dust-donation to `Pair` permanently disables the supply-side graduation trigger, freezing curve-raised LT and the reserved LP allocation - (File: `packages/contracts/src/Bonding.sol`)

### Summary
Any unrelated wallet can call `IERC20(token).transfer(pair, 1)` directly on the launched `Token` (no access control gates plain ERC20 transfers) to permanently keep `IPair.tokenBalance() > 0`, which is the exact live-balance read `canGraduate()` uses for the supply-side graduation trigger. This mirrors the Samba bug class: a state-mutating operation reachable at a lower layer (raw ERC20 `transfer`, analogous to filesystem-level writes) bypasses the higher-layer access control that the protocol relies on (`Pair`'s `onlyRouter` gate on `swap`/`mint`/`transferAsset`) to keep the metadata the higher layer trusts (`tokenBalance()`) consistent with intended state.

### Finding Description
`Bonding.canGraduate` composes two triggers: a USD trigger from stored reserves, and a supply trigger that reads the pair's *live* ERC20 balance: [1](#0-0) 

The supply trigger's live read is documented as intentionally donation-resistant only in the direction that donations "can only INCREASE the balance and can never satisfy `== 0`" — i.e. the design explicitly acknowledges that a donation blocks the supply trigger, and unconditionally burns any donated tokens, but only at the point graduation actually fires: [2](#0-1) 

`Pair`'s state-changing entry points (`mint`, `swap`, `transferAsset`, `transferToken`) are gated `onlyRouter`: [3](#0-2) 

But `Pair.tokenBalance()`/`assetBalance()` are plain `balanceOf` reads with no access control on who can move the underlying ERC20 balance into the pair address — anyone can call `Token.transfer(pair, amount)` directly, entirely outside the `onlyRouter`-gated interface: [4](#0-3) 

The supply trigger the protocol relies on to graduate "flat/bear markets where $9K is never reached" is therefore trivially and repeatably neutralizable by any wallet, for the cost of transferring dust `Token` (freely obtainable by buying 1 wei worth on the curve) to the `Pair` address after every buy that would otherwise zero out `tokenBalance()`. This is the same class of bug as the Samba CVE: a low-level write path (`ERC20.transfer`, like SMB's underlying filesystem write) mutates state that a higher-layer access-controlled subsystem (`Bonding`'s graduation logic, analogous to the SMB read-only share policy) trusts to reflect only sanctioned mutations.

### Impact Explanation
With the supply trigger permanently defeated, a token can only graduate via the USD trigger `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ graduationThresholdUsd`. If the LT's `exchangeRate()` never appreciates enough (a realistic outcome the supply trigger was specifically built to cover, per the "flat/bear markets" language in the docs), the token is permanently stuck in `Lifecycle.Curve`:
- The curve-raised real LT sitting in the `Pair` (`ltFromPair`, the actual funds traders paid in) can never be drained into an LP — `_prepareGraduationLiquidity`/`Router.graduate` are only reachable from `_enterGraduating`, which never fires.
- The 250M `LP_RESERVE` tokens permanently parked in `Bonding` (`lpReserve`) can never be minted into the graduated LP or locked via `LPLock.recordLock`, permanently freezing that allocation.
- Traders can still exit via `Bonding.sell`/`Zap.sell` on the curve, but the token can never reach the post-graduation HyperSwap venue, permanently freezing the protocol's intended LP formation and the funds earmarked for it.

This is a concrete, permanent freeze of creator/LP-earmarked funds triggerable by any unprivileged wallet at negligible cost.

### Likelihood Explanation
High. The attack requires only owning (or buying) a negligible amount of the launched `Token` and calling a plain, unguarded `transfer(pair, amount)` — no special role, no timing precision beyond "before the curve would otherwise hit zero remaining supply," and it is cheap to repeat every time curve sales approach exhaustion. It is fully reachable by an "unrelated wallet," matching the in-scope reachable-path list (direct ERC20 transfers of a launched Token into `Pair`).

### Recommendation
Do not rely on a raw, unauthenticated `balanceOf` read for a security-critical trigger. Either (a) track real curve-sold supply via router-mediated accounting (a stored counter updated only inside `Pair.swap`) instead of `tokenBalance() == 0`, or (b) skim/burn any balance in the pair that exceeds the stored `tokenReserve` accounting before evaluating the supply trigger (mirroring the `skim`-then-burn pattern already used defensively in `_seedUniswapV2Direct`/`_prepareGraduationLiquidity`), so a donation cannot indefinitely suppress the trigger.

### Proof of Concept
1. Launch a token via `Zap.createToken`; let it trade near curve exhaustion (`Pair.tokenBalance()` approaching but not equal to `0`).
2. Before the sale that would zero out `tokenBalance()`, an unrelated wallet buys a negligible amount of the launched `Token` on the curve (or otherwise acquires 1 wei of it) and calls `Token.transfer(pairAddress, 1)` directly — no interaction with `Router`/`Bonding` required, and no access control blocks this call.
3. `IPair.tokenBalance()` is now `>= 1`, so `Bonding.canGraduate`'s supply leg (`IPair.tokenBalance() == 0`) can never be satisfied again for this token, regardless of how much real curve supply remains sellable.
4. Repeat step 2 after every subsequent buy that would otherwise drain the pair to zero.
5. If the paired LT's `exchangeRate()` never appreciates enough to satisfy the USD trigger, the token remains permanently in `Lifecycle.Curve`: `finalizeGraduation` is never reachable, the curve-raised LT and the 250M `LP_RESERVE` tokens held by `Bonding` are permanently stuck, and no LP is ever formed for the token.

    modifier onlyRouter() {
        if (msg.sender != router) revert OnlyRouter();
        _;
    }

    constructor(
        address router_,
        address launchedToken_,
        address assetToken_
    ) {
        if (router_ == address(0) || launchedToken_ == address(0) || assetToken_ == address(0)) revert ZeroAddress();
        if (launchedToken_ == assetToken_) revert IdenticalTokens();
        router = router_;
        launchedToken = launchedToken_;
        assetToken = assetToken_;
    }

    function mint(
        uint256 tokenReserve,
        uint256 assetReserve
    ) external onlyRouter returns (bool) {
        if (_pool.k != 0) revert AlreadyMinted();
        _pool = Pool({tokenReserve: tokenReserve, assetReserve: assetReserve, k: tokenReserve * assetReserve});
        emit Mint(tokenReserve, assetReserve);
        return true;
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    function transferAsset(
        address recipient,
        uint256 amount
    ) external onlyRouter {
        IERC20(assetToken).safeTransfer(recipient, amount);
    }

    function transferToken(
        address recipient,
        uint256 amount
    ) external onlyRouter {
        IERC20(launchedToken).safeTransfer(recipient, amount);
    }
