### Title
Malicious/blacklisting token among an order's multi-token escrow permanently blocks redemption of the whole order - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` (mirrored by `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) releases every token entry in `body.tokens` in a single atomic loop, using `safeTransfer`/low-level `.call` that reverts the whole function if any single transfer fails. Since an order's `inputs` array (the set of tokens escrowed) is attacker-controlled at `placeOrder()` time and can contain any arbitrary ERC-20, this reproduces the Velodrome `notifyRewardAmount`/`deliverBribes` DOS pattern: one poisoned token in a list that is iterated atomically can block delivery/release for every other (legitimate) token in that same list.

### Finding Description
`placeOrder()` in `evm/src/apps/IntentGatewayV2.sol` (lines 194-373) lets any caller construct an `Order` with an arbitrary `TokenInfo[] inputs` list — there is no allowlist check on the token addresses [1](#0-0) . Those tokens are escrowed per-commitment in `_orders[commitment][token]` [2](#0-1) .

When the order is filled cross-chain and a `RedeemEscrow`/`RefundEscrow` message comes back, `IntentsBase._withdraw()` iterates `body.tokens` (which mirrors the order's original `inputs`) and transfers each one out with `safeTransfer`, reverting the *entire* call if any single token transfer fails: [3](#0-2) 

There is no per-token isolation (no try/catch, no skip-and-continue, no governance "swap out bad token" escape hatch as Velodrome added after the C4 finding). If any one of the escrowed input tokens is a malicious or blacklist-style token (e.g. a token whose `transfer()` reverts unconditionally for the beneficiary, or a Circle-style USDC that blacklists the specific solver/beneficiary address after the order is placed), the whole `_withdraw` call reverts on every retry, and since `_filled[body.commitment]` is written *before* the loop but rolled back together with the revert, the order commitment can never finalize.

This is functionally identical to the Velodrome bug class: a single caller-supplied entry in a token list that gets atomically transferred in a loop can permanently deny release of every other (legitimate) balance bundled with it, with no privileged recovery path.

### Impact Explanation
An order can escrow multiple input tokens simultaneously (multi-asset orders are explicitly supported — see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` multi-input/output tests). An attacker who places an order bundling a legitimate high-value token together with a token they control that reverts on transfer (or a real stablecoin they get blacklisted after order placement) causes the solver who fills the order to be unable to ever redeem their escrowed proceeds via `RedeemEscrow`, and/or the depositor unable to get a `RefundEscrow` — the legitimate token bundled with the poison token is frozen forever in the gateway contract, since `_withdraw`'s atomicity gives no way to release only the good tokens. This is a permanent freezing-of-funds impact matching the "Accept" criteria.

### Likelihood Explanation
Reachable directly from a single permissionless `placeOrder()` call — no privileged access required, and token addresses in `order.inputs` are entirely attacker-chosen. The only precondition is that a solver is willing to fill an order containing an unusual/blacklistable token, which is realistic since solvers typically only inspect the *output* side they must provide, not necessarily vet every input token for hostile transfer semantics; likewise a legitimate stablecoin (USDC/USDT) can retroactively blacklist an address after order placement, producing the same effect without any attacker-authored malicious contract at all.

### Recommendation
Make `_withdraw`'s per-token release resilient to individual transfer failures: wrap each token transfer in a low-level call with `try/catch` (or manual `call` + track success) so a single bad token does not block release of the others; credit the failed token's amount to a separate "stuck" balance that can be retried or swept by governance later (mirroring Velodrome's remediation of moving to `swapOutRewardToken`-style token allow/deny lists, or by validating/whitelisting escrow input tokens at `placeOrder` time).

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer()` always reverts (or reverts specifically when `to == solver`).
2. Attacker calls `IntentGatewayV2.placeOrder()` with `order.inputs = [ {token: USDC, amount: 10_000}, {token: EvilToken, amount: 1} ]`, escrowing both tokens under one `commitment`.
3. A solver fills the order on the destination chain via `fillOrder`, triggering a `RedeemEscrow` cross-chain message back to the source chain naming the solver as beneficiary with `body.tokens = [USDC, EvilToken]`.
4. On `onAccept` → `_withdraw(body, isRefund=false, finalize=true)`, the loop reaches `EvilToken` and `IERC20(EvilToken).safeTransfer(solver, 1)` reverts, unwinding the entire transaction — including the USDC transfer that had already "succeeded" in the same call.
5. Every retry of the same `RedeemEscrow` message reverts identically since `EvilToken.transfer` always reverts; the solver's 10,000 USDC proceeds are permanently stuck in escrow with no code path to release them independent of `EvilToken`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
