Confirmed. The webhook `shop` identity field is not covered by the HMAC signature, unlike the OAuth flow where `shop` is explicitly included in `AuthQuery#to_signable_string`.

### Title
Webhook shop-domain header is not covered by HMAC, allowing shop identity spoofing in processed webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (tenant) identifier is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the signed bytes. This breaks the intended binding `shop_header == shop_bound_by_hmac`, letting anyone who possesses one valid `(raw_body, hmac)` pair (e.g. from their own shop's legitimately delivered webhook) replay it to the app's webhook endpoint with an arbitrary `shop` header while still passing `HmacValidator.validate`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

- `hmac` is read from the `hmac-sha256` header.
- `shop` is read from the `shop-domain` header (line 21-23).
- `to_signable_string` returns only `@raw_body` (line 36-38) — it does **not** include `shop`, `topic`, or any header.

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the received `hmac`: [2](#0-1) 

Because `to_signable_string` is body-only, the HMAC proves nothing about which shop the request claims to originate from — it only proves the body bytes were signed with the app's `api_secret_key` (the same secret used across every shop that has this app installed / every legitimate webhook Shopify sends to this app).

`Registry.process` then uses the **unauthenticated** `request.shop` value directly as the tenant identity handed to the app's business logic: [3](#0-2) 

Contrast this with the OAuth callback verification path, where `shop` is explicitly folded into the signable payload: [4](#0-3) 

This shows the library's own design intent — `shop` should be part of the HMAC-protected material to bind the tenant identity to the signature — but this binding was omitted for `Webhooks::Request`. An unprivileged internet user who has captured (or otherwise obtained) any single valid `(raw_body, hmac)` pair delivered for topic X (e.g. from a webhook to their own store after installing the target app) can POST that same body+hmac to the app's public webhook endpoint while substituting any `x-shopify-shop-domain` value. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` calls the registered handler with `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
This is a cross-tenant identity-binding break: the value used to select/act on tenant-scoped data (`shop`) is not covered by the same cryptographic proof that authenticates the payload. Any host app that trusts `WebhookMetadata#shop` (as documented/intended usage of this gem) to route webhook side effects (e.g., updating billing status, uninstall/redact flows, shop-scoped records) can be made to apply another shop's legitimately-signed webhook body under an attacker-chosen shop identity, or apply the attacker's own body under a victim shop's identity. This matches the "Critical: cross-tenant access" category since it crosses a tenant boundary purely through the gem's own webhook verification code, not by the host ignoring documented API.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one valid `(raw_body, hmac)` pair — trivially available to any developer/merchant who installs the target Shopify app on their own store and receives one webhook delivery (e.g. `app/uninstalled`, `orders/create` with attacker-controlled order body on their own shop). No access to `api_secret_key` or any privileged credential is needed; only the gem's own signable-string construction is at fault.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`) in `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the `shop` value used in `WebhookMetadata` to the verified HMAC — mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`. At minimum, document that host apps must not trust the `shop-domain` header for tenant scoping without independent verification (e.g., cross-checking against the shop stored for the given `webhook_id`/topic subscription).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook delivery, capturing the raw JSON body `B` and its `x-shopify-hmac-sha256` header value `H` (a valid HMAC over `B` using the app's `api_secret_key`, which the attacker never needs to know).
2. Attacker POSTs to the app's public webhook endpoint with:
   - `x-shopify-topic: <same topic>`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds: [5](#0-4) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the body/HMAC were never associated with that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
