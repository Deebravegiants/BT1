### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw request body, but the `shop` identity used to route the payload to the host application's handler is read from an HTTP header that is never part of the signed material. Any party who receives one legitimately-signed webhook can replay it with an arbitrary `shop-domain` header while keeping the exact same body and HMAC, and the gem will accept it as authentic for the forged shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is instead pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` only compares the received HMAC against a signature computed over `to_signable_string` (the body), never touching the `shop` header: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then forwards the attacker-controlled `request.shop` straight to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `shop_header == shop_that_signed_the_body` is assumed by every downstream handler, but the gem never checks it. The binding that should hold is `signed_bytes ⊇ {shop, body}`, but in reality `signed_bytes == {body}` only, so the "shop" field is a value that is acted on (used to select/mutate per-tenant records) but not covered by the HMAC — precisely the bug class from the analog report, where an identity field was decoupled from the entity actually authorized/authenticated.

### Impact Explanation
Any merchant/installer of the app (an ordinary, unprivileged actor from the app's perspective, holding no `api_secret_key`) naturally receives real Shopify webhooks for their own shop, complete with a valid `x-shopify-hmac-sha256` signature computed over the body. Because the HMAC never covers the `shop-domain` header, that same attacker can resend the identical body/HMAC pair to the app's webhook endpoint while substituting any other victim shop's domain in the header. `HmacValidator.validate` still returns `true` (it re-derives the same signature over the same body), and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application that uses `data.shop` to look up/update per-tenant session or store records (the intended and documented use of `WebhookMetadata`) will act on the victim tenant's records using attacker-controlled body content — a cross-tenant data integrity/confidentiality break driven entirely by this gem's failure to bind `shop` into the authenticated payload.

### Likelihood Explanation
Exploitation only requires: (1) the attacker be a legitimate, existing user of the app on their own store (trivial for any public app), (2) capturing one real, signed webhook delivered by Shopify to their own endpoint (visible if the app logs/echoes it, or on their own receiving infrastructure), and (3) replaying it with a modified `shop-domain` header at the shared webhook endpoint of a multi-tenant app. No access to `api_secret_key`, access tokens, or victim credentials is needed, making this practically reachable by an unprivileged internet-facing actor.

### Recommendation
Include the shop domain (and other routing-relevant headers such as topic/webhook-id/api-version) inside the HMAC-signed material, or independently authenticate the header against the body/topic by having `to_signable_string` incorporate them, e.g.:
```ruby
def to_signable_string
  "#{shop}\n#{topic}\n#{@raw_body}"
end
```
and compute/verify the HMAC accordingly (this requires coordinating the signing scheme with Shopify's webhook delivery, or independently validating `shop` against a session store keyed by webhook_id/topic before trusting it). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be used by host applications to select tenant records without additional verification.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant "attacker.myshopify.com" using the app.
# Shopify sends them a real, validly-signed webhook:
raw_body = '{"id": 1, "note": "hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the exact same body+hmac to the app's shared webhook endpoint,
# but swaps the shop-domain header to a victim tenant:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),   # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (HMAC only covers raw_body)
# => handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
#    even though the payload/HMAC never originated for that shop.
``` [4](#0-3)
