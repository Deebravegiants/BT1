The main `evm/src/apps/intentsv2` `IntentsBase._withdraw` already guards against zero-amount transfers with `if (amount == 0) continue;` [1](#0-0) , so the exact bug class does not reproduce there. ### Title
Unconditional zero-amount ERC20 transfer in IntentGatewayV2 `withdraw()` can permanently freeze escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` transfers every token in a `WithdrawalRequest.tokens` array without skipping zero amounts, unlike the guarded `IntentsBase._withdraw` used elsewhere in the codebase.

### Finding Description
`Order.inputs` amounts are attacker/solver/user-controlled at `placeOrder` time (subject only to `amount == 0` reverting at order creation for the *initial* deposit, but that check is on the pre-fee amount; downstream, `reducedInputs[i].amount` after protocol-fee deduction can legitimately be small, and more importantly, nothing prevents a multi-token order where one input's escrowed amount ends up zero from fee rounding or a token with rebasing/deflationary behavior before the reduced amount is escrowed). When the destination fills the order or the source cancels it, a `WithdrawalRequest` is built from `order.inputs` and dispatched via Hyperbridge as `RedeemEscrow`/`RefundEscrow` [6](#0-5) [7](#0-6) . On delivery, `withdraw()` in the Tron contract loops over `body.tokens` and calls `token.call(transfer(...))`, requiring `success` for every entry, including a zero-amount transfer to a reward/input token that reverts on zero-value transfers (a documented weird-ERC20 pattern, analogous to the FactoryDAO M-15 report). If any one of the escrowed input tokens is such a token, and its escrowed/reduced amount is zero for that leg, the whole `withdraw()` call reverts, and since this is invoked from `onAccept`/`onGetResponse` (the sole exit path for the escrow), the escrowed funds for that commitment become permanently stuck — this pattern is not deduplicated across other input tokens because a full loop-wide revert blocks the entire withdrawal, not just the offending token's leg.

### Impact Explanation
This freezes user/solver funds held in escrow with no way to complete a `RedeemEscrow` or `RefundEscrow`, matching the medium-severity fund-freeze root cause described in the referenced report: an unprivileged path (placing/filling/cancelling an order and relaying the resulting message) can trigger a permanently reverting exit route once such a token is included in the order's input set.

### Likelihood Explanation
Requires an order whose input token set includes a revert-on-zero-transfer ERC20 and a code path that produces a zero amount for that token in the withdrawal body (e.g., protocol-fee rounding to zero to a non-zero reduced value is unlikely to hit exactly zero, but tokens with transfer-tax/fee-on-transfer behavior combined with `order.inputs[i].amount` being fully consumed by protocol fee, or partial-refund logic elsewhere zeroing one leg, can produce this). This depends on external token behavior and specific amount conditions, making it a real but conditional boundary case, consistent with the "medium, acknowledged boundary condition" judgment in the original report.

### Recommendation
Add the same zero-amount guard used in `IntentsBase._withdraw` (`if (amount == 0) continue;`) to the Tron `IntentGatewayV2.withdraw()` loop before attempting the token transfer, for both the per-token loop and the `TRANSACTION_FEES` transfer.

### Proof of Concept
1. A user places a cross-chain order whose `order.inputs` includes a token `T` that reverts on zero-value transfers, with an escrowed amount that resolves to `0` for `T` in the eventual `WithdrawalRequest` (e.g., via fee/dust accounting reducing that leg to zero while other inputs remain non-zero).
2. The order is filled/cancelled, and a `RedeemEscrow`/`RefundEscrow` message with `tokens[i].amount == 0` for `T` is dispatched and delivered to the source chain gateway.
3. `withdraw()` iterates the tokens; when it reaches `T`, `token.call(transfer(beneficiary, 0))` reverts because `T` disallows zero-value transfers.
4. The `(bool success,)` check causes `revert TransferFailed()`, reverting the entire `withdraw()` call — the escrow for this commitment (all tokens, not just `T`) can never be released, permanently freezing the funds. [8](#0-7)
