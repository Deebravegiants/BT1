### Title
Shopify webhook HMAC signs only the raw body, not the `shop-domain` header — replaying a genuine `(body, hmac)` pair with a spoofed shop header passes verification and attributes forged webhook data to a victim shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only binds the request body to the HMAC. The `shop-domain`, `topic`, `api-version` and `webhook-id` headers are read straight from unauthenticated request headers and are never included in the signed material. Any unprivileged internet user who obtains one genuine `(raw_body, hmac)` pair (e.g. from a webhook fired for their own shop) can POST it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop, and `Registry.process` will accept it as authentic and hand the victim's shop identity to the app's webhook handler together with attacker-controlled body content.

### Finding Description
`Webhooks::Request` exposes `shop` from `shopify_header("shop-domain")` [1](#0-0) , while the HMAC is only computed over `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly that signable string against the HMAC header and returns a boolean; it never inspects `shop`, `topic`, or any other header: [3](#0-2) 

`Webhooks::Registry.process` trusts `HmacValidator.validate(request)` as the sole authenticity check, then immediately forwards `request.shop` (the unsigned header) to the app's handler: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop delivered to handler`. In reality the code enforces only `hmac(secret, raw_body) == received_hmac`, while `shop` is taken from a header outside that computation. Because Shopify's webhook signature never covers the shop/topic headers in this gem, two different requests can carry an identical, fully valid `raw_body` + `hmac` pair while differing only in the `shop-domain` header. The gem's `Registry.process` cannot distinguish "the real webhook for shop A" from "the same bytes replayed and relabeled as shop B" — it will pass verification either way and hand the (spoofed) shop identity straight to the app's handler.

### Impact Explanation
An unprivileged internet user who legitimately operates a shop that has this app installed receives (or can otherwise obtain) a valid `(raw_body, hmac)` pair for one of their own webhook events. The app's webhook endpoint is a plain public HTTP endpoint reachable directly over the internet (not gated by IP allow-listing enforced by this gem). By POSTing the captured body/HMAC unchanged but substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop's domain, `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` invokes the registered handler with `WebhookMetadata#shop` set to the victim's domain. Any app logic that trusts this `shop` value to select which merchant's records to create/update/delete (a common pattern, since `Registry.process` is the gem's documented mechanism for delivering the authenticated shop identity to app code) can be tricked into writing attacker-controlled webhook payload data into a different tenant's context — a cross-tenant integrity/confidentiality break achieved with no access token, no `client_secret`, and no TLS interception, satisfying the "Critical - cross-tenant access" bar.

### Likelihood Explanation
Reachability requires only: (1) the attacker's own legitimate use of the app to generate one authentic webhook and observe its `raw_body`/`hmac`, and (2) network access to the app's public webhook URL. No secrets, TLS interception, or privileged access are needed — the exploit path is entirely internal to how this gem verifies and routes webhook requests.

### Recommendation
Bind the `shop`, `topic`, and other Shopify-supplied identity headers into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the shop identity to the payload before it is forwarded to handlers (e.g., verify the `shop-domain` header against a known/installed shop for the caller, or require the webhook registration/lookup itself to authenticate the shop rather than trusting the header verbatim). At minimum, document to consumers of `WebhookMetadata#shop` that it is unauthenticated and must not be used to make trust decisions.

### Proof of Concept
1. As a legitimate merchant, receive a real webhook delivery to the app; capture `raw_body` and the `X-Shopify-Hmac-Sha256` header value (a valid `(body, hmac)` pair for shop `attacker-shop.myshopify.com`).
2. POST directly to the app's webhook endpoint with the same `raw_body` and `hmac` header, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <same or different registered topic>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `raw_body` and succeeds [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [6](#0-5) , causing the app to process attacker-controlled data under the victim's shop identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
