## Analog Analysis: HMAC-covered content excludes the `shop` identity field in `Webhooks::Request`

### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, breaking the binding `hmac(signed_bytes) == hmac(claimed_shop)` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header that is never included in the bytes that are HMAC-verified, yet this unverified value is forwarded to the host application's webhook handler as the authoritative shop/tenant for the event.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

But `shop` is read from a separate, unsigned header: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (the body only) and, once that check passes, unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version` — all header-derived) and hands it to the host app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`: [4](#0-3) 

This is the exact bug-class the analog rule calls out: "a field acted on but not covered by the HMAC." Compare with `Auth::Oauth::AuthQuery`, where `shop` **is** folded into `to_signable_string` and therefore is bound to the HMAC: [5](#0-4) 

The webhook path has no equivalent binding for `shop`. The identity equality the gem should be enforcing is:
`hmac_valid(body) == true` implies `shop_header == shop_that_actually_generated(body)`

But because `shop` is outside the signed bytes, that implication does not hold: any two valid `(body, hmac)` pairs are interchangeable across different `shop` header values without invalidating the signature, as long as the body itself (JSON payload) contains no shop-specific field that the host app cross-checks. For many topics (e.g., `app/uninstalled`, `shop/redact`, `customers/redact` — all in `MANDATORY_TOPICS`) — see: [6](#0-5) 
— the payload shape is generic and shop identity is conveyed *only* by the header, not by any field inside the signed body.

### Impact Explanation
This breaks the tenant-authentication boundary this gem is responsible for enforcing before invoking the merchant's webhook handler. Since `WebhookMetadata.shop` is the field host applications use to look up the merchant session/store record for the event (e.g. to deactivate a shop's stored access token on `app/uninstalled`, or to redact/purge a specific shop's data on `shop/redact`), a request whose `shop` header can be swapped while the HMAC still validates on the *body* can produce cross-tenant effects (e.g. triggering a redact or uninstall action attributed to a shop that never sent that event). This satisfies "High - cross-tenant access" under the given impact taxonomy, since the identity used to select which merchant's data/session is acted upon is not authenticated by the same signature the gem presents as proof of authenticity.

### Likelihood Explanation
Exploitability from an unprivileged internet user requires only the ability to send POST requests with attacker-chosen headers and a body+HMAC pair that is valid for *any* shop — which any Shopify merchant/app installer can trivially obtain by triggering one real webhook delivery for their own shop (e.g., installing/uninstalling a test app, or, for generic bodies like `shop/redact`/`customers/redact`, any shop's genuine delivery). The unsigned `shop` header can then be freely substituted before replaying the request to the app's webhook endpoint. Likelihood is High given the low barrier (no secret needed, no privileged account, just receipt of one legitimate webhook).

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the signable content, or otherwise cryptographically bind them to the payload before exposing them via `WebhookMetadata`. Since Shopify's HMAC scheme for webhooks is fixed to sign only the raw body, the gem should, at minimum, clearly document that `shop`/`topic`/`webhook_id` headers are unauthenticated relative to the HMAC and are not to be trusted as tenant-identifying without additional verification (e.g., cross-checking against a known/registered shop list, or against a shop identifier embedded in the payload where the topic guarantees one). This mirrors the acknowledged mitigation pattern in the referenced report — document the boundary and recommend/implement a workaround rather than silently trusting unauthenticated fields.

### Proof of Concept
1. Attacker (an app installer) installs and then uninstalls the target app on their own shop `attacker-shop.myshopify.com`, capturing the real webhook delivery for `app/uninstalled`: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `(B, H)` pair to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `to_signable_string = B` — unchanged.
4. `HmacValidator.validate` re-computes the HMAC over `B` (per `lib/shopify_api/webhooks/request.rb#to_signable_string` and `lib/shopify_api/utils/hmac_validator.rb#validate_signature`) — it matches `H`, since `B` was not modified.
5. `Registry.process` passes `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` to the host app's handler, which — trusting that `shop` was authenticated by "Invalid webhook HMAC" check — performs an uninstall/redact/session-teardown action against `victim-shop`, a shop the attacker never controls.           received_signature = verifiable_query.hmac

        end
