No vulnerability found for this question.

**Reasoning:**

The premise misdescribes how `resource_addr` is computed. In `account_abstraction.move`, `resource_addr` is not derived from an attacker-controlled `abstract_public_key` byte string — it's derived from the signer's actual account address: [1](#0-0) 

`update_dispatchable_authenticator_impl` computes `resource_addr` from `signer::address_of(account)`, i.e., the address of the actual transaction signer, not from any attacker-chosen byte vector: [2](#0-1) 

The `abstract_public_key` parameter only appears in the *derivable account abstraction* path, in `derive_account_address`, which uses a distinct domain-separation scheme (`DERIVABLE_ABSTRACTION_DERIVED_SCHEME = 5`) that is entirely unrelated to `create_user_derived_object_address`'s scheme: [3](#0-2) 

`create_user_derived_object_address` (used by `resource_addr`, with the second argument fixed to `@aptos_fungible_asset`) uses domain separator `0xFC` and computes `sha3_256(source || derive_from || 0xFC)`: [4](#0-3) [5](#0-4) 

Even granting an attacker full freedom to choose the `source` value fed into this function (which they don't — it's tied to their own signer address, not an arbitrary byte string), causing two different `source` values to hash to the same `resource_addr` under a fixed `derive_from` requires finding a SHA3-256 collision/second-preimage against another party's specific 32-byte output. This is computationally infeasible (2^128+ work for collision, effectively 2^256 for a targeted preimage), and is not a Move-logic bug — every derived-address scheme in the framework (`create_object_address`, `create_guid_object_address`, `create_user_derived_object_address`) relies on this same SHA3-256 collision-resistance assumption. There is no code path where an attacker supplies raw hash-preimage bytes directly as the `source`/`derive_from` inputs bypassing the address type — `source` is always a native `AccountAddress` (16/32-byte type), and `derive_from` here is the fixed constant `@aptos_fungible_asset`, so the "input domain" available to an attacker is just their own controllable address space, not free-form bytes.

Additionally, resource creation at `resource_addr` uses `create_signer::create_signer(resource_addr)`, which is framework-internal and not reachable by an unprivileged caller for an arbitrary target address independent of this hash derivation: [6](#0-5) 

Since exploiting this requires breaking SHA3-256 preimage/collision resistance rather than a logic flaw in access control or address derivation code, this does not meet the custody-impact bar for a real, unprivileged-input-triggerable vulnerability.

fn native_create_user_derived_object_address_impl(
    context: &mut SafeNativeContext,
    ty_args: &[Type],
    mut args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert!(ty_args.is_empty());
    debug_assert!(args.len() == 2);

    context.charge(OBJECT_USER_DERIVED_ADDRESS_BASE)?;

    let object_context = context.extensions().get::<NativeObjectContext>();
    let derive_from = safely_pop_arg!(args, AccountAddress);
    let source = safely_pop_arg!(args, AccountAddress);

    let derived_address = *object_context
        .derived_from_object_addresses
        .borrow_mut()
        .entry((derive_from, source))
        .or_insert_with(|| {
            AuthenticationKey::object_address_from_object(&source, &derive_from).account_address()
        });

    Ok(smallvec![Value::address(derived_address)])
}
