### Title
Balance-per-declared-address accounting lets an aliased "double-entry" token credit `amountChanges` twice for a single real transfer - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots and diffs token balances independently for every entry of `circomData.erc20TokenAddresses`, and for internal transactions (`externalActionId == 0`) checks only `balanceDif == amountChanges[i]` per index (since `utxoSet` is never populated in `_internalTransact`, so `utxoAmount` is always `0`). Because the attacker fully controls the token contracts and can deploy two distinct addresses that both report the same underlying `balanceOf` while only one of them performs real token movement, a single real deposit can be used to satisfy the balance equation at two different array indices simultaneously, crediting `amountChanges` twice against one real inflow.

### Finding Description
The equality that should hold is: **real tokens received by the vault for a given declared token identity == the shielded credit granted for that identity (`amountChanges[i]`)**. This is enforced only via: [1](#0-0) 

```
UTXO[] memory utxoSet;
uint256[] memory oldBalances = getBalancesForArray(circomData.erc20TokenAddresses);
if (circomData.externalActionData.externalActionId == 0) {
    _internalTransact(circomData);
} else {
    utxoSet = _externalTransact(circomData);
}
uint256[] memory newBalances = getBalancesForArray(circomData.erc20TokenAddresses);
```

and the per-index check: [2](#0-1) 

Because `utxoSet` is never assigned when `externalActionId == 0`, `utxoAmount` is `0` for every index in the internal-transact path, so the required equality collapses to `balanceDif[i] == amountChanges[i]` for each token index, and `onChainCreation[i]` must be `false` (enforced in `checkOnchainCreation` in `contracts/HinkalHelper.sol`).

`getBalancesForArray` reads `balanceOf(address(this))` on **whatever contract address is listed** in `erc20TokenAddresses[i]`: [3](#0-2) 

The attacker fully controls `erc20TokenAddresses` and can deploy the token(s) themselves. Nothing in `dimensionsCheck`/`performHinkalChecks` (contracts/HinkalHelper.sol) requires that the addresses in `erc20TokenAddresses` be unique, whitelisted, or represent independent balances — they are only length-checked against `dimensions.tokenNumber`.

**Exploit construction:** the attacker deploys two contracts, A and B, that both proxy `balanceOf(address(this))` to the same real underlying token balance, but only A's `transferFrom` actually moves real tokens (B's `transferFrom`/`transfer` is a no-op returning `true`). In a single `transact` call:
- index `i`: `erc20TokenAddresses[i] = A`, `amountChanges[i] = D` (deposit). `_internalTransact` (via `_calculateDeltaAmount`/`transferERC20TokenFromOrCheckETH`, `contracts/Hinkal.sol` lines 172-187) actually pulls `D` real tokens into the vault through A. `balanceDif[i] = D`, matching `amountChanges[i] = D` — check passes legitimately.
- index `i'`: `erc20TokenAddresses[i'] = B`, `amountChanges[i'] = D` (also declared as a deposit). The call to B's no-op `transferFrom` moves nothing real, but `newBalances[i'] - oldBalances[i']` is computed via `balanceOf(B)`, which mirrors the SAME shared real balance that A's deposit already increased by `D`. So `balanceDif[i'] = D` too, and the check `D == amountChanges[i'] (D)` passes — even though no tokens actually flowed through B.

Total real tokens entering the vault: `D`. Total `amountChanges` credited to the attacker's shielded ledger (constrained by the SNARK's `inTotal + amountChanges === outTotal` per declared token identity) across the two token identities: `2D`. The circuit only verifies internal arithmetic consistency of the shielded tree per declared token address; it has no way to know that addresses A and B alias the same real balance, so it cannot catch this. The on-chain guard that was supposed to catch it (`balanceDif == amountChanges[i]`) is defeated because it is evaluated per-index against a balance source the attacker controls and can duplicate.

### Impact Explanation
The attacker mints unbacked shielded value: they receive `D` of legitimate shielded credit under token identity A (backed) plus `D` of shielded credit under token identity B (unbacked), for a real cost of only `D`. This is a direct instance of "minting shielded value without backing" — Critical severity, matching protocol insolvency, since the attacker (or downstream holders of UTXOs derived from the phantom `B` credit) can later attempt to redeem/spend shielded value that has no real token backing in the vault. The attack is self-contained in a single `transact` call and is repeatable at will (bounded only by gas and the attacker's ability to keep minting more alias pairs / repeating the pattern), so it does not strictly require a sandwiching front-run/back-run structure as framed in the question title — the minimal reproducible version occurs entirely within one atomic call.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: deploying arbitrary "ERC20-like" contracts, choosing `erc20TokenAddresses`, `amountChanges`, and generating a valid proof for their own private inputs (the circuit's arithmetic constraint on `amountChanges` per declared token index is satisfiable by any legitimately-constructed private witness, since the circuit has no knowledge of real-world token identity/aliasing). No whitelist/allowlist of ERC20 addresses was found in `dimensionsCheck`/`performHinkalChecks` restricting which token contracts may appear in `circomData.erc20TokenAddresses`. Cost to the attacker is simply the token deployment plus one real deposit of `D`.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries within a single `transact` call (revert on duplicates in `dimensionsCheck`), and/or require that all token contracts referenced in `erc20TokenAddresses` be members of a permissioned/whitelisted `erc20TokenRegistryAddress` list rather than arbitrary attacker-supplied addresses, so that balance snapshots taken per index are guaranteed to correspond to independent, non-aliased balances.

### Proof of Concept
Foundry test plan:
1. Deploy `TokenA` (real ERC20) and `TokenB` (proxy contract whose `balanceOf` forwards/reads the same storage slot / calls `TokenA.balanceOf(address(this))`, but whose `transferFrom`/`transfer` are no-ops returning `true`).
2. Fund attacker with `D` of `TokenA`.
3. Craft `circomData` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [D, D]`, `onChainCreation = [false, false]`, generating a valid witness/proof for a shielded internal transaction that credits `D` shielded value under each of the two token identities.
4. Call `Hinkal.transact(...)`.
5. Assert: `TokenA.balanceOf(Hinkal) - oldBalanceA == D` (only `D` real tokens entered the vault), while the emitted commitments / shielded ledger reflect `2D` total credited value across the two token identities — i.e., `sum(amountChanges) (2D) != actual real tokens received (D)`, violating the stated invariant `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)`.

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }

    function getBalancesForArrayMemory(
