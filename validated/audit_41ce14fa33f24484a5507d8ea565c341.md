### Title
`GetResponse` delivery on Hyperbridge's runtime router bypasses the bandwidth gate that `PostRequest` delivery enforces - ([File: parachain/runtimes/gargantua/src/ismp.rs])

### Summary
`ProxyModule::on_accept` (the `PostRequest` entrypoint of the ISMP router) explicitly meters every non-purchase request against `pallet_bandwidth`'s `try_consume` before routing it to a destination pallet. `ProxyModule::on_response` (the `GetResponse` entrypoint) carries a comment claiming it "mirrors the request path in `on_accept`" for bandwidth accounting, but the code contains no `try_consume` call at all — it only checks `dest_chain()` and dispatches straight to the destination module.

### Finding Description
In `parachain/runtimes/gargantua/src/ismp.rs` (and identically in `parachain/runtimes/nexus/src/ismp.rs`), `on_accept` runs: [1](#0-0) 
which meters `request` bytes against `(request.source, request.from)` via `BandwidthGate::try_consume` before any further processing, skipping only genuine bandwidth-purchase messages via `is_purchase_message`.

`on_response`, however, is: [2](#0-1) 
The doc-comment says this "mirrors the request path in `on_accept`," but there is no corresponding `BandwidthGate::try_consume` invocation anywhere in the function body — it goes directly from the `dest_chain()` check to dispatching `on_response` on the destination pallet.

This matters because `GetResponse` delivery is the counterpart data-return leg of the exact same metered channel that `on_accept` protects on the request leg. The bandwidth model (documented in `docs/content/developers/evm/bandwidth/overview.mdx`) is Hyperbridge's access-control mechanism restricting which `(source chain, app)` pairs may consume Hyperbridge's processing/storage capacity — an app must hold a paid subscription (or be allowlisted) to have its traffic accepted; unmetered traffic is supposed to be uniformly rejected once a subscription is exhausted. A `GetResponse` is unauthenticated, permissionless data (per the ISMP spec, "a GET request can be processed offchain by any interested party") whose payload size is attacker/relayer-influenced (RLP-encoded storage values, one per requested key, batched arbitrarily by `handleGetResponses`/`ResponseMessage`). Because `on_response` skips the meter entirely, any relayer can flood Hyperbridge's runtime storage/processing with GetResponse payloads for a depleted or never-subscribed `(chain, app)` pair — the exact resource the bandwidth gate exists to ration — without ever needing bandwidth, i.e., the equivalent of "watching a file" (observing/consuming a resource) without holding the "read" permission (bandwidth) that the analogous write-side (`on_accept`) path enforces.

### Impact Explanation
This is a broken/bypassable access-control gate on a core dispatch path reachable directly from a single relayed message (`handleGetResponses`), matching the required class ("a route unable to deliver messages" / unauthorized app action / access-control bypass analogous to the Node.js report). It lets any relayer force the Hyperbridge runtime to process and pass to destination modules an unlimited volume of `GetResponse` traffic for apps that have zero or exhausted bandwidth allowance, undermining the entire economic/DoS-prevention design pallet-bandwidth exists to provide, and letting an attacker cause the destination module (and Hyperbridge's own state/weight accounting) to do metered work for free — a direct violation of the "close the same gate on both directions of a channel" invariant the codebase otherwise enforces meticulously everywhere else (as seen in the extensive `HostManager`/`IntentGatewayV2`/`SimplexPaymaster` relayer-gate hardening documented across `sdk/packages/core/docs/ai/changelog/`).

### Likelihood Explanation
High likelihood of being exploitable if genuine: `handleGetResponses`/`ResponseMessage` delivery is permissionless (any relayer with a valid state proof can submit it), `GetRequest`/`GetResponse` traffic is explicitly designed to be processable by "any interested party," and the only gate protecting resource consumption on this leg (per the codebase's own bandwidth documentation) is `BandwidthGate::try_consume`, which the code shows is simply absent from `on_response`. No proof forgery or governance compromise is needed — only a normal GetResponse for an app whose bandwidth subscription is unset or depleted.

### Recommendation
Add the same `BandwidthGate::try_consume(&response.get.source, &response.get.from, bytes)` call to `ProxyModule::on_response` in both `parachain/runtimes/gargantua/src/ismp.rs` and `parachain/runtimes/nexus/src/ismp.rs`, sized from `ismp::abi::encode_get_response(&response).len()` (mirroring the `on_accept` pattern and the bandwidth charge already applied earlier in `pallet-state-coprocessor::handle_get_requests`), before dispatching to the destination pallet. Confirm whether the state-coprocessor's own bandwidth charge (charged once when producing the response) is intended to be the sole charge point instead — if so, document that explicitly and remove the misleading "mirrors on_accept" comment from `on_response`; if not, this is the fix needed to close the gap.

### Proof of Concept
1. Do not register/purchase any bandwidth subscription for `(sourceChain, appModule)` (or exhaust an existing one, matching `gate_no_allowance_rejects`/`gate_insufficient_across_subscriptions_does_not_deduct` test semantics in `modules/pallets/testsuite/src/tests/pallet_bandwidth.rs`).
2. Have a relayer submit a `ResponseMessage` containing a `GetResponse` addressed to that `(sourceChain, appModule)` via `handleGetResponses`/`pallet_ismp::handle_unsigned`, following the normal `response.rs` handler path (`modules/ismp/core/src/handlers/response.rs`), which only checks proof validity/timeouts/duplication — not bandwidth.
3. Observe that `ProxyModule::on_response` dispatches the response to the destination pallet's `on_response` without ever calling `BandwidthGate::try_consume`, unlike the equivalent `on_accept`/`PostRequest` path which would revert with `GateError::NoAllowance`/`Insufficient` for the same `(chain, app)`.

Note: I was unable to independently confirm, from the index alone, whether a compensating bandwidth charge inside `pallet_state_coprocessor::handle_get_requests` (which does call `BandwidthGate::try_consume` before inserting the response into the MMR) is considered by the maintainers to fully substitute for a charge in `on_response` — the two charge points key on different call sites (coprocessor charges at response-production time; `on_accept` charges the router at delivery time), so I flagged the router-level gap as the concrete, code-visible discrepancy relative to the `on_accept` pattern the comment claims to mirror.

impl IsmpModule for ProxyModule {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Always-enforce unless the `no-bandwidth` flag
		// is set; skipped for purchase messages so the recharge flow
		// itself doesn't need bandwidth. With the flag on the gate is a
		// no-op and this block is compiled out entirely.
		#[cfg(not(feature = "no-bandwidth"))]
		if !pallet_bandwidth::Pallet::<Runtime>::is_purchase_message(&request) {
			let bytes = ismp::abi::encode_post_request(&request).len() as u32;
			<pallet_bandwidth::Pallet<Runtime> as pallet_bandwidth::BandwidthGate>::try_consume(
				&request.source,
				&request.from,
				bytes,
			)
			.map_err(|err| {
				anyhow!(
					"bandwidth gate: {err} (source={:?}, from={:x?})",
					request.source,
					request.from
				)
			})?;
		}

	fn on_response(&self, response: GetResponse) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Mirrors the request path in `on_accept`: the chain
		// and module that produced the response pay for the bytes they
		// deliver. Compiled out when the `no-bandwidth` flag is on.
		if response.dest_chain() != HostStateMachine::get() {
			return Ok(Weight::from_parts(0, 0));
		}

		let dest = &response.get.from;

		let pallet_id = ModuleId::from_bytes(dest).map_err(|err| Error::Custom(err.to_string()))?;

		match pallet_id {
			pallet_ismp_demo::PALLET_ID =>
				pallet_ismp_demo::IsmpModuleCallback::<Runtime>::default().on_response(response),
			_ => Err(anyhow!("Destination module not found")),
		}
	}
