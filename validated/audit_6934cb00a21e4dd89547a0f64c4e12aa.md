## Analysis

Found a valid analog. The DNN CVE is about an **unauthenticated, public entry point performing expensive computation before any anti-spam/economic gate is applied**, allowing a low-cost attacker to exhaust server resources. Hyperbridge's `pallet-state-coprocessor::handle_unsigned` has the same shape: it is `ensure_none`-gated (fully unauthenticated), performs full cryptographic state-membership/non-membership proof verification for an **unbounded** batch of requests/keys, and only meters/charges the caller (via `BandwidthGate::try_consume`) *after* that expensive verification work is already done — and this whole path runs inside `validate_unsigned`, i.e., it is executed by every node during mempool/gossip validation, for free, with no signature required.

### Title
Unbounded free proof verification in `pallet-state-coprocessor::handle_unsigned` enables unauthenticated computational DoS - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`GetRequestsWithProof::requests` is a plain `Vec<GetRequest>` (no `BoundedVec`), and each `GetRequest.keys` is likewise an unbounded `Vec<Vec<u8>>`. `handle_get_requests` runs full membership and per-key state-proof verification (`verify_membership`, `verify_state_proof`) over this entire unbounded structure before the only economic gate (`BandwidthGate::try_consume`) is ever consulted, and the whole call is reachable unsigned (`ensure_none`) through `ValidateUnsigned::validate_unsigned`, meaning it executes on every node's transaction-pool validation for free, unauthenticated, and repeatable. ### Finding Description
`handle_unsigned` in `pallet-state-coprocessor` accepts a `GetRequestsWithProof` message with origin `ensure_none` (unsigned/unauthenticated) both in the dispatchable and, critically, in `ValidateUnsigned::validate_unsigned`, which re-runs `Self::handle_get_requests(message.clone())` to decide transaction validity: [4](#0-3) 

Inside `handle_get_requests`, before the `BandwidthGate::try_consume` economic check is reached, the pallet performs:
1. `source_state_machine.verify_membership(&host, commitments, state_root, &source)` over the full `requests` vector.
2. For every request in the batch, `dest_state_machine.verify_state_proof(&host, req.keys.clone(), state_root.state_root, &response)` — a per-key cryptographic Merkle/trie proof verification.

Only after this verification completes for the *entire* batch does the code call `BandwidthGate::try_consume`, and the code comment explicitly states this ordering is intentional ("Charged after proof verification so the value sizes are final") — meaning the bandwidth/economic gate cannot reject oversized or unauthorized requests before the expensive cryptography runs: [5](#0-4) 

Because `requests: Vec<GetRequest>` and `GetRequest.keys: Vec<Vec<u8>>` carry no `BoundedVec`/length cap at the type level (unlike, e.g., `pallet-bandwidth`'s `MAX_APP_LENGTH` bound noted elsewhere in the codebase), an attacker can craft a single unsigned extrinsic containing many `GetRequest`s, each with many keys, up to the block/extrinsic size limit, and submit it repeatedly with trivially varied content (to avoid the `provides`-tag transaction-pool dedup) to force every full/collator node in the network to repeatedly perform expensive proof verification during mempool validation, for zero cost, before the transaction is ultimately rejected (e.g., for referencing a non-existent commitment or bad proof).

### Impact Explanation
This is the direct analog of the DNN "public registration form" DoS: an unauthenticated, public-facing entry point performs unbounded, expensive server-side work before any gating check can reject the malformed/oversized input. Here, sustained submission of such crafted unsigned extrinsics can degrade validator/collator CPU and mempool throughput network-wide, delaying legitimate cross-chain message delivery (a route unable to deliver messages), which matches the accepted impact criteria.

### Likelihood Explanation
The call requires no signature, no fee, and no prior state (any syntactically valid-looking `GetRequestsWithProof` triggers verification attempts). The only friction is crafting `GetRequest`/`Proof` fields that pass early cheap checks (timeouts, state-machine ID matches) before reaching the expensive verification calls, and varying content per submission to defeat the `provides`-tag pool dedup — both are within an unprivileged attacker's control.

### Recommendation
- Bound `GetRequestsWithProof.requests` and each `GetRequest.keys` with `BoundedVec` limits enforced at decode/validation time, before any proof verification runs.
- Move or duplicate a cheap size/limit check (and ideally a coarse bandwidth pre-check keyed only on declared sizes) to the very start of `handle_get_requests`/`validate_unsigned`, ahead of `verify_membership`/`verify_state_proof`, mirroring the pattern already used in `pallet-call-decompressor::decompress` where the size bound was moved to the single choke point every caller passes through.

### Proof of Concept
1. Attacker builds a `GetRequestsWithProof` with `requests` containing the maximum number of `GetRequest`s that fit under the extrinsic/block length limit, each with `keys` populated with many distinct byte vectors, and a `source`/`response` `Proof` whose `height` fields match a real, currently tracked consensus state (so the cheap `validate_state_machine`/`state_machine_commitment` checks pass).
2. Submit as `pallet_ismp`-style unsigned extrinsic `StateCoprocessor::handle_unsigned(message)` via RPC with `system_dry_run_unsigned`/`submit_and_watch`, as done in the existing test/tesseract harness patterns. [6](#0-5) 
3. `validate_unsigned` invokes `handle_get_requests`, which runs `verify_membership` and per-request `verify_state_proof` over the full batch — full cryptographic cost is paid by the validating node — before the (deliberately invalid/garbage) proof or bandwidth check ultimately causes the call to fail.
4. Repeat with trivially mutated `keys`/dummy proof bytes per submission (changing the `provides` tag) to bypass pool dedup and repeatedly force this expensive, free verification work across the network.
