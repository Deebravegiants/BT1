### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from separate, unsigned HTTP headers. `Registry.process` validates only the body HMAC and then forwards the unverified `shop` value straight to the app's webhook handler, so the identity binding "shop that produced a validly-HMAC'd payload" == "shop the handler is told the payload came from" does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers that are never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the HMAC computed from `to_signable_string` (the body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC passes, and then builds `WebhookMetadata` directly from the unauthenticated `request.shop` header, handing it to the app's handler as the trusted tenant identifier: [4](#0-3) 

This is structurally the same misscaling/miswiring bug class described in the external report: a value that is treated as authenticated (`price`/`decimals` in the report, `shop` here) is not actually the value the signature covers. Here, the equality the code implicitly assumes is:

`shop header value == shop that produced the HMAC-signed body`

but nothing enforces this — the HMAC binds only the body bytes, not the shop header, so any party who can obtain one valid `(raw_body, hmac)` pair (e.g., by triggering a webhook on their own, unprivileged, self-owned shop) can resend that exact body with a different `shop-domain` header value and still pass `HmacValidator.validate`, since the validator never inspects `shop` at all.

### Impact Explanation
Host applications commonly use `WebhookMetadata#shop` to select which merchant/tenant's session, access token, or database row to act on for the delivered payload. Because `shop` is outside the HMAC's protection, an attacker who owns any shop with the app installed can capture a legitimately-signed webhook body/HMAC pair from their own store and replay it against the app's webhook endpoint with an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header pointing at a victim shop. `Registry.process` will accept it as valid and hand the attacker-controlled body to the handler labeled as coming from the victim shop — this is a cross-tenant identity binding break, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker needs only to be a legitimate, unprivileged owner/installer of the app on some shop (no `api_secret_key`, access token, or privileged account required) to generate one valid signed body, then can freely vary the `shop-domain` header on replays since it is never checked against the signature. This requires no credential theft, TLS interception, or social engineering — only crafting an HTTP POST with headers under the attacker's control.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC verification, e.g., by including the shop domain in `to_signable_string`, or by independently validating that the `shop-domain` header corresponds to a shop for which this exact HMAC/body pairing is expected (for example, cross-checking against a session/store already known to be associated with that HMAC secret variant), rather than trusting an unauthenticated header for tenant attribution downstream.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook event (e.g., `orders/create`) to capture a real `(raw_body, x-shopify-hmac-sha256)` pair delivered to the app's webhook endpoint.
2. Replay the exact same POST body and HMAC header to the same webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only recomputes the HMAC over `raw_body`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
