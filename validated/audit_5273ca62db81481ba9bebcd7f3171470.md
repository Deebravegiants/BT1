Found a genuine tenant-binding gap in the webhook processing path.

### Title
Webhook `shop` identity is trusted from an HMAC-unsigned header, breaking the tenant binding between the signed body and the shop dispatched to the handler - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identifier from the `X-Shopify-Shop-Domain` HTTP header, but `Registry.process` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value used to build `WebhookMetadata` and passed to the handler is never covered by that signature, so the equality the code implicitly assumes — "HMAC-verified bytes == tenant identity delivered to the handler" — does not hold.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac-sha256` header: [1](#0-0) 
`to_signable_string` is defined as the raw body only: [2](#0-1) 
Meanwhile, `shop` (the tenant identity forwarded to the app's handler) is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed payload: [3](#0-2) 
`Registry.process` then constructs `WebhookMetadata` using this unauthenticated `request.shop` value and hands it directly to the app-supplied handler: [4](#0-3) 

The equality this code needs to hold is: `shop bound by HMAC == shop delivered to handler`. In this gem's implementation, the right-hand side comes from a header, not from anything covered by the HMAC digest of `@raw_body`. Any attacker who can replay or forward a validly-signed webhook body (e.g., a webhook is valid HMAC-wise for *any* shop, since Shopify signs webhooks with the app's single `client_secret` shared across all shops installing the app) can pair that same signed body with an arbitrary `X-Shopify-Shop-Domain` header value, and the gem will report the request as HMAC-valid and dispatch it to the handler tagged with attacker-chosen shop.

This is a cross-tenant risk purely from this gem's own logic: the library never binds `shop` into the signable string, so it cannot distinguish "body signed for shop A, relabeled as shop B" from a legitimate webhook for shop B.

### Impact Explanation
This matches the "Critical - cross-tenant access" category: an app that trusts `WebhookMetadata#shop` from `Registry.process` (as instructed by this gem's own API, since the gem is the one performing HMAC validation and handing this value to handlers as authenticated) can be made to apply another shop's webhook data (e.g., orders/customers/redact payloads) under an attacker-selected tenant identity, since the `shop` claim carries no cryptographic binding to the HMAC verification this gem performs.

### Likelihood Explanation
Exploitation requires the attacker to possess one validly HMAC-signed webhook body for the app (which Shopify signs identically regardless of destination shop, using the single app `client_secret`) and to control or spoof the HTTP headers of the request delivered to the app's webhook endpoint. Because delivery method and header handling are the host application's responsibility, but this gem is the one that performs the "validation" and asserts trust in `request.shop`, this is a real gap in the gem's `Utils::VerifiableQuery` contract rather than something the host app can be expected to compensate for. Likelihood is Medium: it depends on the attacker's ability to relay/replay a signed body with different headers to the app's public webhook endpoint, which is plausible since webhook endpoints are unauthenticated by design and Shopify's HMAC is not shop-specific.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) inside the HMAC-signable string, or otherwise cryptographically bind the tenant identity to the verified payload, rather than trusting a bare header value once the raw-body HMAC passes. At minimum, document and enforce that `request.shop` must be independently cross-checked by the host app against the payload contents before being treated as authenticated tenant context.

### Proof of Concept
1. Attacker obtains one legitimately Shopify-signed webhook delivery for shop A (e.g., by installing the app on shop A themselves, which is available to any developer/tester of a public app).
2. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` header value from that delivery.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, raw_body)` [5](#0-4) , and `request.shop` returns the attacker-controlled header value [3](#0-2) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, causing the app to process shop A's webhook data attributed to victim-shop.
