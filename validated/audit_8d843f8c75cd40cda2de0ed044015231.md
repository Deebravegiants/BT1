I found a genuine binding flaw in the webhook HMAC validation matching the requested analog pattern (a field acted upon but not covered by the HMAC).### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated by `Utils::HmacValidator.validate`, which recomputes an HMAC over `to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` returns only the raw request body: [2](#0-1) 

However, the `shop` identity used downstream is taken from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, not from the signed body: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the application's handler, without any binding between the verified body and the shop that is claimed to own it: [4](#0-3) 

This is the same bug class as the referenced report: a field that is *acted upon* (here, `shop`, used to attribute the webhook event to a tenant) is not part of the data actually *covered by the HMAC*. The equality that should hold is:

`shop_verified_by_signature == shop_used_by_handler`

but in this code, `shop_used_by_handler = request.shop` (raw header, unauthenticated) while `shop_verified_by_signature` doesn't exist at all — the signature only binds the body bytes, never the shop header. Because the app's `client_secret` (`Context.api_secret_key`) is a single shared secret used for *all* shops/tenants of the app (not shop-specific), the HMAC is valid for any body regardless of which shop header accompanies it. An attacker who can obtain one valid `(raw_body, hmac)` pair — e.g., by installing the app on their own shop and capturing a legitimate webhook delivery to the app's public endpoint, or replaying a delivery they otherwise have access to — can resubmit the exact same body and HMAC to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` will still succeed because the header is never part of `to_signable_string`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop, with a body the attacker controls (from their own installation).

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: shop attribution for an HMAC-"verified" webhook is fully attacker-controlled. Any application built on this gem's `Webhooks::Registry.process` — which is the gem's documented entry point for webhook handling — will process attacker-forged events falsely attributed to any shop, satisfying the "cross-tenant access" impact category: an unprivileged internet user (any merchant able to install the app once) can inject events, including sensitive ones (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or business data payloads), that are attributed to a shop they do not own or control, without needing that other shop's credentials, access token, or the app's `client_secret`.

### Likelihood Explanation
Likelihood is high for any app that relies on `Registry.process`/`request.shop` per the gem's own documented workflow: no privileged credentials, TLS interception, or `api_secret_key` knowledge are required — only a normal app install (to obtain one legitimate body+HMAC pair) and the ability to send an HTTP POST to the public webhook endpoint with a modified header, which is standard unprivileged-attacker capability.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material actually verified, or otherwise cross-check `request.shop` against a shop known/expected for the delivery (e.g., a lookup keyed by a value that *is* covered by the HMAC, or requiring the handler layer to independently verify the shop is one that installed the app and matches the topic's expected sender). At minimum, document/enforce that `request.shop` must not be trusted as an authenticated tenant identifier since it's outside the HMAC's covered bytes, and change `to_signable_string`/`HmacValidator` usage for webhooks so shop-domain header spoofing cannot pass validation while claiming a different tenant than the one whose secret-derived signature was actually checked.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and `api_secret_key` is shared across all shops of the app).
2. Replay the same body `B` and the same `H` to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` still returns `B`; `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it still equals `H`, so validation passes: [2](#0-1) [5](#0-4) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, even though the body/HMAC pair originated entirely from the attacker's own shop: [4](#0-3)
