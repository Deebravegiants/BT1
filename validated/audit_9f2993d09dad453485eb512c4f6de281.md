### Title
Unsigned `feeStructure.feeToken` and `relay` in `EmporiumUpgradeable.payRelayFees` let a caller redirect wallet-fee payments to an arbitrary token/recipient outside the signer's authorization - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet` only binds `EMPORIUM_SIGNATURE_TYPEHASH` to `emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline`, and additionally checks that `circomData.feeStructure.flatFee <= stack.maxFee`. Neither `circomData.feeStructure.feeToken` nor `circomData.relay` are part of the signed digest or otherwise validated, so an unprivileged caller assembling `circomData` for `Hinkal.transact` can set these fields to values the signer never approved, causing `payRelayFees` to pull `flatFee` (bounded only in amount, not in token/destination) out of the signer's `HinkalWallet` to an attacker-chosen `relay`.

### Finding Description
The claimed equality — (assets leaving wallet, destination) == (what was signed via `ops`, `maxFee`) — is broken because `feeToken` and `relay` are outside the EIP-712 payload: [1](#0-0) 

The only fee constraint applied is a numeric cap, not an asset/destination constraint: [2](#0-1) 

Worse, `payRelayFees` contains an unconditional fallback branch that fires whenever `feeStructure.feeToken` does not match any entry in `circomData.erc20TokenAddresses` (i.e. a token completely unrelated to any op the signer authorized), and it still pays `flatFee` from the signer's wallet to `circomData.relay`: [3](#0-2) 

`payRelay` then routes to `sendToRelayFromWallet`, which calls `doSendToRelay` on the signer's `HinkalWallet` — the only guard on that wallet call is `onlyEmporium`, i.e. it trusts whatever `feeToken`/`relay`/`relayFee` the Emporium contract passes in: [4](#0-3) [5](#0-4) 

Attacker call: submit `Hinkal.transact` with a valid Groth16 proof for the attacker's own shielded UTXOs (unrelated to the victim), an `externalActionMetadata` that decodes to the victim's legitimately-signed `EmporiumStack` (`v,r,s,signerAddress,ops,maxFee,deadline` unchanged, so `verifyWallet` passes), but with `circomData.feeStructure.feeToken` set to any ERC20 the victim's `HinkalWallet` holds (e.g. USDC never referenced by `ops`) and `circomData.relay` set to an attacker-controlled address. Since `feeToken`/`relay` are never hashed, the signature check still succeeds. `foundToken` remains `false` because the arbitrary `feeToken` is absent from `circomData.erc20TokenAddresses`, so the fallback branch unconditionally sends `flatFee` (up to the previously-signed `maxFee`) of that arbitrary token from the victim's wallet to the attacker's `relay`.

None of the existing guards prevent this: `verifyWallet`'s signature check only binds `ops`/`maxFee`/`deadline`; `dimensionsCheck`/`rootHashExists`/slippage checks in `Hinkal.transact` operate on the attacker's own shielded balances, not on the victim wallet's ERC20 holdings; and `HinkalWallet.doSendToRelay`'s `onlyEmporium` modifier only checks the caller is the Emporium contract, not that the token/relay were authorized by the signer.

### Impact Explanation
An attacker can drain, per valid `emporiumMessage` signature they can observe/replay-decode (message nonce is single-use via `usedMessages`, so this is once per signed message, but any relayer/caller submitting that message can exploit it before/instead of the legitimate flow), up to `flatFee` (bounded by the signed `maxFee`) of any arbitrary ERC20 token the victim's `HinkalWallet` holds, to a relay address the signer never authorized. This is moving assets from a wallet owner that were never authorized for that token/destination, matching the "High: theft or ... moving assets a wallet owner ... never authorised" impact category. The size of theft is bounded by `maxFee`, but `maxFee` is provided by the signer for legitimate fee purposes and may be set generously; the attacker can also target any token balance the wallet holds regardless of relevance to the signed operations.

### Likelihood Explanation
Feasibility is high: the attacker needs no special privilege beyond being able to call `Hinkal.transact` with a valid proof of their own shielded funds (any deposit is achievable trivially, even in the fallback-branch scenario no `erc20TokenAddresses`/`deltaAmountChanges` correlation with the feeToken is even required). They need visibility into a not-yet-submitted, validly-signed `EmporiumStack` (e.g., front-running a legitimate relay submission, or being handed the signed payload as an intended relay), and the ability to control `circomData.feeStructure.feeToken`/`circomData.relay` fields, which the contract does not constrain. This is repeatable once per distinct `emporiumMessage`.

### Recommendation
Include `feeStructure.feeToken` and `relay` (and any other economically meaningful `circomData` fields such as `erc20TokenAddresses` set actually used for wallet debits) in the `EMPORIUM_SIGNATURE_TYPEHASH` digest so the signer explicitly authorizes the fee token and relay destination, not just the numeric cap. Alternatively, restrict `payRelayFees`'s fallback branch so it can only charge a token/amount that is provably tied to a balance change actually caused by the signed `ops`.

### Proof of Concept
Foundry plan:
1. Deploy `EmporiumUpgradeable`, `HinkalWallet` for a victim signer holding e.g. 1000 USDC and 1000 DAI.
2. Victim signs an `EmporiumStack` (`ops` = benign DAI-only operation, `maxFee` = 50 DAI-equivalent, `deadline` = future) via `EIP712` producing `(v,r,s)`.
3. Attacker deposits a trivial amount into the shielded pool for themselves and builds a valid Groth16 proof/`CircomData` where `externalActionMetadata` decodes to the victim's signed stack unchanged, but `circomData.feeStructure = {feeToken: USDC, flatFee: 50, variableRate:0}` and `circomData.relay = attackerAddress`, with `erc20TokenAddresses` containing only DAI (not USDC).
4. Call `Hinkal.transact`; assert it succeeds (signature check passes because USDC/relay aren't hashed).
5. Assert USDC balance of victim's `HinkalWallet` decreased by 50 and `attackerAddress` received 50 USDC, while `stack.ops`/`maxFee`/`deadline` never referenced USDC — i.e., assert `signed_set = {opsHash, maxFee, deadline}` did not change but `assets_moved = {USDC, attackerRelay}` diverged from any token in `ops`, proving the equality is broken.
