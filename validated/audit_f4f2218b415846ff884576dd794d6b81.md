### Title
Cross-Tenant Session Hijack via Predictable, Unsigned Session Cookie ID - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw value of the session cookie as the authoritative session identifier, with no cryptographic binding to prove that value actually originated from this gem's own OAuth flow. Combined with `ShopifyAPI::Auth::Session`'s deterministic, non-random id format, an unprivileged attacker can forge the cookie value for any known shop and cause the host application to load and use that shop's stored session (including its access token).

### Finding Description
The equality that should hold is:

`shop_id_bound_to_cookie == shop_id_cryptographically_verified_by_this_gem`

For the JWT-based (embedded) path this equality holds: `SessionUtils.session_id_from_shopify_id_token` derives the id only after `Auth::JwtPayload.new(id_token)` verifies the HS256 signature with `Context.api_secret_key`. [1](#0-0) 

For the cookie-based (non-embedded, or embedded-without-token fallback) path, however, `cookie_session_id` simply returns whatever value is present in the `Cookie` header, unverified: [2](#0-1) [3](#0-2) 

The value that legitimately gets placed into that cookie comes from `Auth::Oauth.validate_auth_callback`, which sets the cookie's value to `session.id` for non-embedded apps: [4](#0-3) 

`session.id` is not a random secret — it is deterministically derived from public/guessable inputs: `"offline_#{shop}"` for offline sessions, or `"#{shop}_#{associated_user.id}"` for online sessions: [5](#0-4) 

Because `cookie_session_id` never verifies an HMAC or signature over this value (unlike the JWT path, which is checked via `Auth::JwtPayload`, or the OAuth callback, which is checked via `Utils::HmacValidator`), any client that can set an HTTP `Cookie` header for a request to the host application can supply `offline_#{victim_shop}` directly. The host app (following this gem's documented `SessionUtils.current_session_id` API) will treat that as the "current session id", look it up in its session store, and load the victim shop's `Session` object — including its real access token — for use on the attacker's request.

### Impact Explanation
This is a cross-tenant access vulnerability: an unprivileged internet user who merely knows (or guesses) a target shop's `myshopify.com` domain — public information, since it's visible in install URLs, storefronts, and app listings — can construct a forged session identifier and, if the host app relies on `SessionUtils.current_session_id`/`cookie_session_id` as documented, retrieve and use that shop's stored offline (or online, if the associated user id is known/enumerable) access token. This satisfies the Critical bar: theft/use of a merchant access token and cross-tenant access, achieved purely through this gem's own trust of an unauthenticated, predictable identifier as a session-binding key.

### Likelihood Explanation
Exploitability depends on the host app storing sessions keyed by exactly this id and relying on `SessionUtils` to recover the "current" session from cookies, which is the pattern this gem's own documentation and `SessionUtils` API establish. The offline session id format `offline_#{shop}` requires no secret knowledge at all — only the shop domain — making this trivial for the common offline-access-token flow. The online case additionally requires guessing/knowing the associated user's numeric id, which is a smaller but still feasible search space (Shopify staff/user ids are often small integers, and are sometimes observable via other Shopify surfaces).

### Recommendation
Do not use the raw session id as the trust anchor for cookie-based session resolution. Either (a) sign/HMAC the cookie value (similar to `Utils::HmacValidator`) so the host app can verify it originated from this gem's OAuth flow before using it to look up a session, or (b) use a cryptographically random opaque token stored in the cookie that maps indirectly to the deterministic session id server-side, instead of exposing the deterministic id (`offline_#{shop}`, `#{shop}_#{user_id}`) directly as the bearer credential in the cookie.

### Proof of Concept
1. Attacker learns/guesses a victim's shop domain, e.g. `victim-shop.myshopify.com` (public information).
2. Attacker sends a request to the host application with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which (per `cookie_session_id`) returns `"offline_victim-shop.myshopify.com"` unverified. [2](#0-1) 
4. Host app looks up this id in its session storage and loads the victim shop's stored `Session` (with the real Shopify access token), then serves the attacker's request as if they were that shop — cross-tenant access achieved with no credentials beyond the public shop domain.

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end
