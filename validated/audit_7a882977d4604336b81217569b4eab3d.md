## Title
Sell-side erosion of `Pair.swap`'s `+1` K-invariant slack can push `assetReserve` below the recovered `virtualLtReserve`, causing an unguarded underflow revert in `_prepareGraduationLiquidity` that permanently bricks graduation - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._prepareGraduationLiquidity` computes `ltFromPair = assetReserve - _launchTimeVirtualLtReserve(...)` with no underflow guard [1](#0-0) . This subtraction is safe only as long as the pair's live `assetReserve` never dips below the launch-time virtual reserve recovered as `Pair.k() / Token.TOTAL_SUPPLY()` [2](#0-1) . That bound is normally guaranteed by the K-invariant, but `Pair.swap` enforces the invariant with `+1` slack rather than exactly: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k()` reverts, allowing the true product `newTokenReserve * newAssetReserve` to land below `k` by up to `newTokenReserve + newAssetReserve` [3](#0-2) . Because reserves scale to `~1e27` wei territory (1B-token supply at 18dp), this "1-wei" style rounding slack is not bounded to 1 wei in absolute terms — it scales with reserve size on every single sell, and each `Router.sell` call applies it once via `_computeSell`/`Pair.swap` with no cumulative check [4](#0-3) .

### Finding Description
`_prepareGraduationLiquidity` is invoked unconditionally from `_enterGraduating`, which itself fires inline at the end of any buy that trips `canGraduate` (the dual USD/supply trigger), or via the permissionless `triggerGraduation` [5](#0-4) . The documented invariant `assetReserve >= virtualLtReserve` is asserted to hold "because `_pool.k` is set once and never modified by swap," but that claim relies on the K-invariant being *exact*, when `Pair.swap`'s `+1` formulation only enforces it approximately, with slack proportional to reserve magnitude:

`(newTokenReserve+1)*(newAssetReserve+1) >= k` ⟺ `newTokenReserve*newAssetReserve >= k - newTokenReserve - newAssetReserve - 1`

A sequence of many small sells (each individually valid under this loosened check) can ratchet `assetReserve` down by slightly more than the "fair" curve amount each time, accumulating drift. Once the supply trigger fires (`tokenBalance() == 0`, i.e. the curve fully sold out via repeated buys interleaved with these draining sells) or the USD trigger fires at a point where accumulated slack has pushed `assetReserve` marginally under `virtualLtReserve`, the very next call into `_prepareGraduationLiquidity` underflows on `assetReserve - virtualLtReserve` and reverts with a Solidity `Panic(0x11)`.

Because this call is unconditional and inline inside the threshold-crossing buy, the revert propagates and reverts the *entire buy transaction* — meaning:
1. The buy that would have crossed the graduation threshold (and every subsequent buy attempt) reverts every time, since `canGraduate` remains true and `_enterGraduating` is retried and underflows again.
2. `triggerGraduation`, the designed escape hatch for stuck curves (used elsewhere for the BounceTech-mint-floor case), calls the same `_enterGraduating` → `_prepareGraduationLiquidity` path and therefore cannot rescue the token either [6](#0-5) .

The token becomes permanently stuck in `Lifecycle.Curve`, unable to graduate, with all curve-raised LT (creator's seed plus every trader's buy-in) and the 250M `LP_RESERVE` tokens locked in `Bonding`/`Pair` with no admin rescue path documented for this state.

### Impact Explanation
This is a permanent freezing-of-funds bug: once the drift condition is hit, the token can never graduate, and the LT raised by the curve (which would normally be drained via `Router.graduate` and paired into the HyperSwap LP) stays trapped, unreachable by creators or traders — `LPLock` and post-graduation exit paths are never reached. Traders can still `sell` back into the curve as long as `tokenBalance() != 0`/lifecycle stays `Curve`, but the token can never reach the HyperSwap venue, and any trader caught holding the token when the curve exhausts (`tokenBalance()==0` triggers the bug) loses the ability to trade further since `Bonding.buy`/`sell` both gate on lifecycle and the curve is drained. This satisfies the "permanent freezing of trader, creator or LP funds" bar in the validation criteria.

### Likelihood Explanation
Reaching this requires an attacker (or organic trading) to execute enough sells to accumulate slack drift comparable to the gap between `assetReserve` and `virtualLtReserve` at the moment a trigger fires — this gap shrinks toward zero specifically near full sellout (as shown by the `k/(tokenReserve+1)` bound getting closer to `virtualLtReserve` as `tokenReserve` shrinks toward `LP_RESERVE`). Any unprivileged address can call `Zap.sell`/`Bonding.sell` repeatedly; no special role is required. The exact per-call slack bound and whether it is large enough in practice (vs. the invariant-test suite's assertions, e.g. `test_inv_virtualReserveAlwaysExceedsRealBalance`) could not be fully re-derived numerically within this review — the codebase's own fuzz/invariant tests target exactly this property, which suggests the team is aware of it as a risk surface, but I was not able to confirm from the available context whether the existing tests exhaustively rule out the drift scenario for adversarial (rather than random) sell sequences timed at the sellout boundary.

### Recommendation
Add an explicit, saturating check in `_prepareGraduationLiquidity` (mirroring the saturating-subtraction pattern already used elsewhere, e.g. `_ltSwapInventory`/`_sweepLTToOwner`'s `bal > keep ? bal - keep : 0`) so that `ltFromPair` clamps to `0` instead of underflowing when `assetReserve <= virtualLtReserve`, and audit/tighten `Pair.swap`'s K-invariant check to remove or bound the `+1` slack relative to absolute reserve size so it cannot be exploited by repeated small trades to erode the `assetReserve >= virtualLtReserve` invariant.

### Proof of Concept
1. Launch a token via `Zap.createToken` with the standard seed.
2. Have an unprivileged trader alternate large buys with many small sells through `Zap.buy`/`Zap.sell` (which route to `Bonding.buy`/`Bonding.sell` → `Router._computeBuy`/`_computeSell` → `Pair.swap`), each sell exploiting the `+1` slack in `Pair.swap`'s K-check to shave a small amount of `assetReserve` beyond what the exact curve math would allow.
3. Continue until `tokenBalance()` on the pair approaches zero (near full sellout) so that the margin between `assetReserve` and the recovered `virtualLtReserve = Pair.k()/Token.TOTAL_SUPPLY()` is minimal.
4. Submit the final buy that would otherwise trip the supply trigger (`tokenBalance()==0`) and call `_enterGraduating` → `_prepareGraduationLiquidity`.
5. Observe the transaction revert with an arithmetic underflow panic on `assetReserve - virtualLtReserve` [7](#0-6) , and that every subsequent buy and `triggerGraduation` call reverts identically, leaving the token permanently stuck pre-graduation with curve-raised LT and the 250M LP reserve inaccessible.

    ///      inline at end of the threshold-crossing buy. Pinning `tokensForLP`
    ///      and `ltFromPair` here (at the last curve price) is what preserves
    ///      the zero-gap invariant across the tx split.
    function _enterGraduating(
        address tokenAddress
    ) internal {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        info.lifecycle = Lifecycle.Graduating;

        (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) =
            _prepareGraduationLiquidity(tokenAddress);

        $.pendingGraduation[tokenAddress] = PendingGraduation({
            tokensForLP: tokensForLP, ltFromPair: ltFromPair, lpBurned: lpBurned, unsoldBurned: unsoldBurned
        });

        emit TokenGraduating(tokenAddress, tokensForLP, ltFromPair, lpBurned, unsoldBurned);
    }

    /// @notice Permissionless trigger for phase 1 of graduation. Same flow as
    ///         the inline post-buy trigger inside `_executeBuy`, but callable
    ///         without any buy. Closes the case where `canGraduate` is true
    ///         (LT appreciation pushed the curve past the USD threshold) but
    ///         the closing buy on the curve would mint below the BounceTech
    ///         LT mint floor and revert with `BelowMinTransactionSize`,
    ///         making the token un-graduatable via `Zap.buy`.
    /// @dev    `_enterGraduating` reads pair reserves and the launch-time
    ///         virtual reserve only — it does not depend on a buy having
    ///         just landed, so the same logic is safe to expose as a
    ///         standalone entry point. The lifecycle pre-checks mirror
    ///         `Bonding.buy`; the launch trading delay is intentionally
    ///         not enforced because `canGraduate` already requires either
    ///         the USD threshold or full curve sellout, both of which are
    ///         unreachable from a fresh launch within the delay window.
    function triggerGraduation(
        address tokenAddress
    ) external nonReentrant {
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        if (!canGraduate(tokenAddress)) revert NotGraduatable();
        _enterGraduating(tokenAddress);
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
