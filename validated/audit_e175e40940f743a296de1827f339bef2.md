### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook data misattribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via HMAC-SHA256 over the raw request body, then trusts the `shop` value taken from an unauthenticated HTTP header to attribute the payload to a tenant. The `shop` field is never part of the signed bytes, so the binding "HMAC-verified bytes == the shop the app acts on behalf of" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `shop` accessor independently reads the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string`, i.e. `@raw_body`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to dispatch the handler, without any cross-check that `shop` corresponds to the signed body: [4](#0-3) 

Because only the raw body bytes are covered by the HMAC, the `shop-domain` header can be swapped by any party sitting between Shopify and the app's endpoint (a reverse proxy misconfiguration, header-injection point, or a malicious intermediary the merchant's infrastructure trusts) while keeping the same body+HMAC pair. The resulting `WebhookMetadata` passed to the handler will carry an attacker-chosen `shop` value paired with a body that was actually signed for a different shop — the equality `shop_verified_by_hmac == shop_used_for_dispatch` is broken because the left side doesn't exist at all; only the body is verified, not the shop.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to select the merchant's session/access token, tenant-scoped datastore, or authorization context (a normal, documented usage pattern for this gem's webhook API), an attacker who can influence only the `shop-domain` header of an otherwise-valid signed webhook delivery can cause the payload to be processed under a different tenant's identity — a cross-tenant data integrity/attribution issue. This matches the "field acted on but not covered by the HMAC" analog class from the rules.

### Likelihood Explanation
Exploitation requires the attacker to control or tamper with the `shop-domain` header while a legitimately-signed body from Shopify passes through (e.g., a proxy/CDN layer that forwards headers independently from the body, or any component that rewrites headers before the body reaches the app). This is a plausible but non-trivial "man in the middle within the merchant's/host's own delivery path" precondition rather than a pure unauthenticated internet attack against Shopify directly, since directly forging the HMAC without the `client_secret`/webhook secret is not possible. Likelihood is Medium: it depends on an intermediary that decouples header and body integrity, which is a real-world possibility with reverse proxies, load balancers, or webhook relay services, but not a "click a link" style unauthenticated bypass.

### Recommendation
Bind the `shop` (and `topic`/`api_version`) into the value that is authenticated, e.g. by including the shop-domain header value in the signable string alongside the raw body, or by requiring the host application to independently confirm the `shop-domain` header value against a shop known to be currently installed/authorized before dispatching the webhook to a handler. At minimum, document explicitly that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Shopify sends a webhook for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. An intermediary component in the app's own delivery chain (proxy, gateway, or any header-rewriting layer) rewrites the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com` while leaving the body `B` and the HMAC header untouched.
3. The app calls:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers_with_rewritten_shop)
ShopifyAPI::Webhooks::Registry.process(request)
```
4. `HmacValidator.validate(request)` succeeds because it only checks `B` against the HMAC header, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`.
5. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:198-199` builds `WebhookMetadata` with `shop: request.shop` = `shop-b.myshopify.com`, so the handler processes shop A's body under shop B's identity.
