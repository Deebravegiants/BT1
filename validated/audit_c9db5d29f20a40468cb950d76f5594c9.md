### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the trusted tenant identifier. Because the HMAC never covers the `shop` field, any two requests with the same body/signature pair are indistinguishable regardless of which shop domain header accompanies them — exactly the "field acted on but not covered by the HMAC" identity-binding break called out in scope.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (i.e., body only) and, if it passes, dispatches to the app handler using `request.shop` as the tenant identity, with no cross-check that the signed body actually originated for that shop: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that has installed the app — it is not per-shop: [4](#0-3) 

The `shop` value is then packaged as the trusted tenant identifier and forwarded to the app's `WebhookHandler#handle`: [5](#0-4) [6](#0-5) 

**Broken identity binding:** the gem implicitly assumes
`HMAC-verified(body) == HMAC-verified(body, shop)`,
i.e., that verifying the body cryptographically also vouches for the `shop` header. That equality does not hold: the `shop` header is attacker-controlled and outside the MAC. Any unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own shop, which is a normal unprivileged action, and capturing the real webhook Shopify sends them) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header naming a victim shop. `Utils::HmacValidator.validate` will still pass because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will invoke the app's handler believing the payload came from the victim shop.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability. Any application built on this gem that uses `WebhookMetadata#shop` to decide which tenant's data to read, write, or act on (a documented, expected usage pattern — the field exists specifically to identify the originating shop) can be tricked into applying attacker-controlled webhook content under a victim shop's identity. Depending on the host app's logic, this enables cross-tenant data corruption, unauthorized state changes attributed to another merchant, or injection of fabricated events (e.g., fake `orders/create`, `app/uninstalled`, GDPR webhooks) into the victim tenant's processing pipeline — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required beyond the ability to install the app on one's own shop (a normal, unprivileged action any internet user can take) and to send an HTTP request to the app's public webhook endpoint with a custom `shop-domain` header. The library performs no binding whatsoever between the signed bytes and the shop header; the vulnerability is exercised through the gem's own documented `Registry.process`/`Request` API, not by the host app violating documented usage.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signable content, or independently verify that `request.shop` matches an expected/registered shop for the webhook subscription before dispatching to the handler, so the HMAC binds the tenant identity as well as the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering Shopify to send a real webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `api_secret_key`.
2. Attacker captures this `(raw_body, hmac)` pair (trivial — it's their own inbound HTTP traffic).
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks for presence, not shop-body binding): [7](#0-6) 
5. `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `@raw_body`, which is unchanged.
6. `Registry.process` invokes the app handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to process attacker-controlled content as if it originated from the victim tenant.

          end
        end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
