### Title
Missing Reentrancy Guard on `IntentGatewayV2.placeOrder` (Tron) Enables Arbitrary-Call Reentrancy Through the Shared `CallDispatcher` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2.placeOrder` executes fully attacker-controlled `order.predispatch.call` calldata via the shared, access-control-free `CallDispatcher` *before* it finishes accounting for and sweeping escrowed balances back from that same dispatcher — and, unlike its EVM sibling, does so **without a reentrancy guard**. This reproduces the exact bug class in the external report: an unprivileged caller supplies arbitrary `target/data` that gets executed from a shared, trusted contract context (`CallDispatcher`, standing in for the vulnerable rebalancer), letting the attacker hijack that context mid-flow to corrupt shared escrow/balance state before the legitimate flow validates it.

### Finding Description
`CallDispatcher.dispatch` has no caller restriction whatsoever — any account or contract can invoke it, and it blindly executes attacker-supplied `Call[]` entries with `to.call{value: call.value}(call.data)`: [1](#0-0) 

In `IntentGatewayV2.placeOrder`, when an order carries `predispatch` calldata, the gateway transfers the order's predispatch assets into this shared `CallDispatcher`, then invokes `dispatch(order.predispatch.call)` — calldata that is **entirely chosen by the order placer** — before reading `CallDispatcher`'s balance to compute how much to sweep back into escrow: [2](#0-1) 

Critically, `placeOrder` in this Tron contract carries **no `nonReentrant` modifier**: [3](#0-2) 

This is a direct behavioral regression from the canonical EVM implementation, which explicitly guards the equivalent function: [4](#0-3) 

Because `order.predispatch.call` is attacker-supplied and executed by the unrestricted `CallDispatcher`, an attacker can embed a call to a contract they control inside `predispatch.call`. That contract can reenter `IntentGatewayV2.placeOrder` (or other state-mutating entry points such as `cancelOrder`) *while the outer call's predispatch assets are still sitting in the shared `CallDispatcher`* and before the outer call has swept/accounted for them. The escrow-crediting logic trusts `IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance` at sweep time (lines 424-449) without any binding to which order actually deposited those funds — the balance is a shared, mutable resource with no per-order isolation, exactly like the rebalancer in the report trusted whatever `msg.sender`/borrow context it was called with to authorize a `Pool.borrow()` on behalf of the victim's delegated credit. Here, the "delegated credit" is the implicit trust that whatever balance the `CallDispatcher` holds when a given order's sweep step runs belongs to that order.

### Impact Explanation
An attacker can use a nested/reentrant `placeOrder` (or interleave with `cancelOrder`, which mutates `_filled` and triggers cross-chain withdrawal flows) invoked from within their own `predispatch.call` to manipulate which order's escrow ends up crediting a given token balance sitting in the shared `CallDispatcher`, and to distort the nonce/duplicate-output-token bookkeeping that exists in the canonical EVM contract but is not mirrored here. This can result in the protocol crediting more escrow to an attacker-controlled order than assets it actually deposited, or double-accounting of dust/balances across orders placed in the same transaction — a direct theft or permanent-freezing vector against user-escrowed funds held by the IntentGateway.

### Likelihood Explanation
The attack requires only a single `placeOrder` transaction with a `predispatch.call` pointing at an attacker-controlled contract — this is available to any unprivileged user of the intents flow, with no special permissions, governance access, or off-chain collusion required, matching the "single submitted transaction" reachability bar. The missing `nonReentrant` modifier (present in the sibling EVM contract but absent here) makes exploitation a straightforward reentrancy rather than a complex multi-block race.

### Recommendation
Add the same `nonReentrant` protection (or transient-storage reentrancy lock, consistent with the EVM `IntentGatewayV2.sol`) to `placeOrder`, `fillOrder`, and `cancelOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`. Additionally, consider isolating `CallDispatcher` balances per-order (e.g., ephemeral per-call dispatcher instances, or pre/post balance deltas scoped strictly to the initiating call) so that a shared dispatcher balance can never be attributed to the wrong order even if reentrancy is otherwise possible.

### Proof of Concept
Exact drained amounts require full protocol simulation (nonce sequencing, fee-token swap paths, and duplicate-output bookkeeping differences between the Tron and EVM variants were not fully traceable from static review alone), but the reachable exploit skeleton is:
1. Attacker deploys `Evil`, a contract that, when called, re-enters `IntentGatewayV2.placeOrder` with a second `order2` targeting the same input token.
2. Attacker calls `placeOrder(order1, graffiti)` where `order1.predispatch.call = abi.encode([Call({to: address(Evil), value: 0, data: ...})])` and `order1.predispatch.assets` funds the dispatcher with token `T`.
3. Inside the dispatcher's execution of `order1.predispatch.call`, `Evil` reenters `placeOrder(order2, ...)`, whose own predispatch/sweep step reads `IERC20(T).balanceOf(dispatcher)` — which still includes `order1`'s just-deposited funds — and sweeps that combined balance to `address(this)`, crediting `_orders[commitment2][T]` from a balance that partly belongs to `order1`.
4. Depending on how the outer call's later balance check on the now-drained dispatcher resolves, the attacker either forces a revert (griefing/DoS) or, by carefully sizing `order2`'s claimed `inputs[i].amount` relative to the combined balance, credits its own escrow using `order1`'s deposited assets.
