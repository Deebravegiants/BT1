### Title
`clear()` does not synchronize with in-flight `#replaceAll`/`#savePublicKeys` writes, allowing post-logout resurrection of pre-clear fusion data - (File: `features/wallet-accounts/src/module/wallet-accounts.ts`)

### Summary
`WalletAccounts#clear` resets `#walletAccountsInternalAtom`, `#hardwareWalletPublicKeysAtom`, and `#externalWalletAddressesAtom`, and re-arms `#loaded` with a fresh `pDefer()`, but it never waits for or cancels an already in-flight `#replaceAll` call (queued via `makeConcurrent`) or its dependent debounced `#savePublicKeys`/`#updateFusion` calls. Because these operations read from/write to the same atoms and the in-memory `#hardwareWalletPublicKeys` field without any generation check, a `#replaceAll` invocation that started before `clear()` can complete and persist its stale/attacker-influenced data after the reset has already happened, effectively resurrecting cleared state.

### Finding Description
`clear()` is implemented as: [1](#0-0) 

It reassigns `this.#loaded = pDefer()` and resets the three atoms, but it does not `await` on the `#replaceAll` mutex (`makeConcurrent`) nor cancel any pending debounced `#savePublicKeys`/`#updateFusion` calls.

`#replaceAll` is queued via `makeConcurrent({ concurrency: 1 })` and gated on `await this.#loaded.promise`: [2](#0-1) 

If a fusion payload (attacker-controlled, per the stated precondition) triggers `processOne` → `#replaceAll(data)` while `#loaded` is already resolved (i.e., the app was already loaded/unlocked), the `await this.#loaded.promise` line resolves the already-resolved promise captured at the moment execution reaches it, so the call proceeds without blocking. Between that point and the eventual `this.#walletAccountsInternalAtom.set(updatedWalletAccounts)` write at line 323, there are multiple `await` points (`this.#wallet.getPrimarySeedId()`, `this.#getInternalWalletAccountsWithFallback()`), which yield the event loop. If `clear()` executes during one of these yields (e.g., a user-triggered logout/lock racing a fusion sync down-push), the sequence becomes:

1. `#replaceAll` reads `currentWalletAccounts` (possibly already `{}` after `clear()`'s reset, or the pre-clear value, depending on exact interleaving).
2. `clear()` resets `#walletAccountsInternalAtom` to `undefined` and re-arms `#loaded`.
3. `#replaceAll` finishes its computation using the (possibly stale/attacker) `walletAccounts` argument captured in its closure at call time — not `#rawFusionData` fetched anew — and calls `this.#walletAccountsInternalAtom.set(updatedWalletAccounts)` *after* the clear's reset has completed, overwriting the fresh empty state with attacker data.
4. Similarly, `#savePublicKeys`, a zero-delay `pDebounce` at line 223-229, can be scheduled by the in-flight `#replaceAll` before `clear()` runs but fire (write `this.#hardwareWalletPublicKeys`, which was set from attacker `accounts` at line 256) into `#hardwareWalletPublicKeysAtom` after `clear()`'s `hardwareWalletPublicKeysAtom.reset()`.

Nothing in `clear()`, `#replaceAll`, or `#savePublicKeys` checks a generation/epoch token to detect that a clear happened mid-flight, and `clear()` does not await the `#replaceAll` concurrency queue to drain before returning. This is confirmed by the module's own code comment acknowledging the fragility of this exact critical section against interleaved writes: [3](#0-2) 
— the comment only calls out `.update()`/`.create()` as hazards, not `clear()`, indicating the clear-vs-in-flight-sync race was not considered when this comment was written.

### Impact Explanation
If the interleaving occurs, wallet-account and hardware-wallet-public-key state that should have been wiped at logout/wallet-switch (e.g., `clear()` triggered from `onClear` in `features/wallet-accounts/src/plugins/lifecycle.ts` lines 127-129) can be repopulated with attacker-influenced data from a fusion payload delivered before the clear. This breaks the "locked/cleared means cleared" invariant across session boundaries: stale wallet account entries (including hardware wallet public keys) can persist or reappear after logout/wallet-switch, potentially causing account/address confusion for the next session (e.g., wrong-account exposure, unexpected hardware wallet public key state) tied to data the attacker controlled in a prior session.

### Likelihood Explanation
Exploitability depends on winning a narrow timing window: the attacker's fusion payload must be in-flight through `#replaceAll` (already past the `#loaded` gate) precisely when the user triggers `clear()` (logout/lock/switch-wallet). Node's single-threaded event loop microtask/macrotask ordering makes this a real but timing-sensitive race rather than a deterministic bug — feasible to trigger reliably in a controlled test (as the PoC below demonstrates) but requiring the attacker to time payload delivery relative to the victim's logout action in production.

### Recommendation
Make `clear()` synchronize with all in-flight/pending write paths before (or instead of) resetting state:
- Have `clear()` await the `#replaceAll` `makeConcurrent` queue draining (e.g., call and await a no-op through the same concurrency-limited function, or expose a `flush`/`cancel` hook on `makeConcurrent`) before performing the atom resets, or perform the resets and then re-run `#replaceAll`'s gating logic against a generation counter.
- Introduce a per-clear "generation" counter incremented in `clear()`; capture the generation at the start of `#replaceAll`/`#savePublicKeys`/`#updateFusion` and no-op the final `.set()` calls if the generation has changed by the time they complete.
- Cancel/flush the debounced `#savePublicKeys`/`#updateFusion` (`pDebounce`) calls in `clear()` before resetting the underlying atoms.

### Proof of Concept
Integration test plan (extends the existing test suite in `features/wallet-accounts/src/module/__tests__/index.test.ts`, which already demonstrates the `#loaded`-gated queuing pattern in "should inherit compatibility mode when syncing down before load"):

1. `prepare()` the module with `load: true` so `#loaded` starts resolved.
2. Manually delay the internal atom's `.get()`/`getPrimarySeedId()` resolution (e.g., via a deferred promise on the `wallet.getPrimarySeedId` mock) so that a `channelOptions.processOne({ data: { walletAccounts: attackerPayload } })` call starts executing `#replaceAll` and is suspended mid-flight at one of its `await` points.
3. While suspended, call `await walletAccounts.clear()`.
4. Resolve the deferred `getPrimarySeedId` promise, allowing the suspended `#replaceAll` to finish and call `walletAccountsInternalAtom.set(...)`.
5. Assert that `await walletAccountsInternalAtom.get()` (or `walletAccounts.getAll()`) is `undefined`/empty and does **not** contain the `attackerPayload` accounts — i.e., the clear was not overwritten by the stale in-flight write.
6. Repeat similarly for `#hardwareWalletPublicKeysAtom`, asserting it remains reset (not repopulated by a debounced `#savePublicKeys` call that was scheduled before `clear()`).
