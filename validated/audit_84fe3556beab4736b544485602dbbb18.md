## Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant) identifier that the registry later trusts and hands to the app's webhook handler is read from an HTTP header that is completely outside the signed payload. Any two requests that ever produce the same signed body (e.g., a replayed genuine webhook payload) can be paired with an attacker-chosen `shop-domain`/`x-shopify-shop-domain` header and will still pass HMAC validation, letting an unprivileged actor make the app process events under an arbitrary shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is pulled straight from the `shop-domain`/`x-shopify-shop-domain` header, which plays no part in the signed string: [3](#0-2) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` — which in turn calls `verifiable_query.to_signable_string` (the body) against the shared `api_secret_key` — and then immediately forwards the *unverified* `request.shop` to the app's handler as the tenant identity: [4](#0-3) [5](#0-4) 

Because `api_secret_key` is the app's single `client_secret` shared across every installed shop (not a per-shop key), the HMAC only proves "this body was signed by this app's secret" — it proves nothing about which shop the body belongs to. The equality the gem should enforce but does not is:

`shop authenticated by the signature == shop delivered to the handler`

Concretely, `hmac == HMAC(api_secret_key, raw_body)` is verified, but `shop` is never an input to that HMAC, so `request.shop` can be swapped freely by anyone who can reach the webhook endpoint and possesses (or observes) any one valid `(raw_body, hmac)` pair for the same app (e.g., their own shop's legitimate webhook delivery, which they can capture as a merchant/installer of the app). This breaks the identity binding the rest of the gem relies on when dispatching `WebhookMetadata.new(... shop: request.shop ...)` to app handlers.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who merely has one valid, previously-observed `(body, hmac)` pair (trivial to obtain by installing the app themselves and capturing their own genuine webhook) can replay that pair to the same endpoint with a forged `x-shopify-shop-domain` header naming any other shop. `Registry.process` will accept it as authentic and invoke the registered handler believing the event originated from the victim shop, since the only verification performed is on the body/secret pair, not on the shop claim. Any host application that keys persistence, access-control, or side effects (e.g., "does this order belong to shop X", session lookups, data writes scoped by `data.shop`) off `WebhookMetadata#shop` is exposed to cross-tenant data corruption or disclosure — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that has at least one active install (needed to legitimately capture a `(body, hmac)` pair) and reuses the identical `api_secret_key` for all its shops, which is the standard single-tenant-secret model this gem uses (`Context.api_secret_key`/`Context.old_api_secret_key`). No access token, no shop-specific secret, and no privileged access are required — only network access to the app's public webhook endpoint and a previously observed webhook body.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the signature before trusting it. Concretely, either:
- Reject/flag replayed bodies by tracking `webhook_id` uniqueness (Shopify already sends a unique `webhook-id` per delivery) and refuse to reprocess a previously seen `webhook_id`, and/or
- Validate that the `shop` header, together with the body, forms part of what's authenticated (e.g., verify the request's shop against a store of shops for which this app instance holds an active access token/session before dispatching), so a header alone cannot redirect a genuine signature to an unintended tenant.

### Proof of Concept
1. App installs are done for `attacker-shop.myshopify.com`; the app owner (attacker) receives one genuine webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid for the app's shared `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and header `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...changed shop header...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and compares to `H` — this still matches because the body and secret are unchanged. [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if `victim-shop` sent this webhook, even though it never did.
