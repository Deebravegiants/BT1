### Title
Webhook shop/topic/webhook_id/api_version headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then unconditionally builds `WebhookMetadata` from those unauthenticated headers, breaking the intended binding "header shop == HMAC-authenticated shop".

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers via `shopify_header`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly over `to_signable_string`: [3](#0-2) 

`Registry.process` checks this body-only HMAC, then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` (all header-derived) to build the `WebhookMetadata` delivered to the app-defined handler: [4](#0-3) 

The equality the gem should guarantee is: `shop bound to the HMAC-signed content == shop delivered to the handler as data.shop`. Instead, the gem verifies only `HMAC(secret, raw_body) == received_signature`, and separately trusts `headers["shopify-shop-domain"]` for `data.shop` — these are two independent, unbound values. Any entity capable of producing one valid `(raw_body, hmac)` pair for the app's secret (e.g., a real, unrelated merchant who owns a genuine app installation and therefore legitimately receives real signed webhook deliveries for their own shop) can resend that exact `raw_body`/`hmac` pair directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`/`x-shopify-api-version`) headers to name a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will happily hand the handler `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically-authenticated payload and the shop it is attributed to. Any app that uses `data.shop` from `WebhookMetadata` to decide which tenant's local records/session/state to update (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into applying data for shop A against shop B's tenant context — this is a cross-tenant data confusion/injection primitive rooted entirely in this gem's verification logic, not requiring the app to deviate from documented usage.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately Shopify-signed `(raw_body, hmac)` pair, which any real merchant installing the vulnerable app obtains automatically via ordinary webhook delivery to their own endpoint (or by directly capturing/replaying traffic to the app's public webhook URL, since delivery is over HTTP without additional binding to Shopify's IP or TLS-client identity in the gem). No secret key, session, or elevated privilege is needed — only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers and a previously captured valid signed body.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the signable string used for HMAC verification, or independently re-derive/verify the shop domain from a source bound to the signature (e.g., cross-check against a known/expected shop for the target endpoint) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook: `raw_body = '{"id":1}'`, header `x-shopify-hmac-sha256 = <base64 HMAC of raw_body with app secret>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged headers and invokes the app handler with `data.shop == "victim-shop.myshopify.com"`, even though this data was never actually authenticated as originating from that shop: [6](#0-5)
