### Title
Stale delegate grant silently re-arms when the position NFT returns to its original owner — (File: contracts/controller/src/storage/account.rs)

### Summary

`DelegateGrant` entries keyed by `ControllerKey::Delegates(account_id)` are never deleted on NFT transfer. `get_delegates` filters grants by `granted_by == current_owner`, so a grant stamped by owner Alice lapses while Bob holds the token — but the same grant reactivates the moment the NFT returns to Alice, with no new `add_delegate` call and no on-chain signal. A delegate ("position manager") that the owner believes was revoked can then exercise full account spending authority — `borrow`, `withdraw`, and every owner/delegate-gated strategy — to steal the account's collateral.

### Finding Description

- Delegates are stored as a single `DelegateGrant { granted_by, delegates }` under `ControllerKey::Delegates(account_id)` (`storage/account.rs:176-199`).
- `is_owner_or_delegate` authorizes a caller when it is an active position manager listed in `get_delegates(env, account_id, owner)`, where `owner` is resolved live from the position NFT (`account.rs:114-127`, `storage/account.rs:35-44`).
- On transfer, nothing touches `Delegates(account_id)`: the NFT contract emits `Transfer` and updates `Owner(token_id)` only; the controller has no hook. The grant merely fails the `granted_by == owner` filter while someone else holds the token (`get_delegates`, lines 176-181).
- When the NFT returns to the original `granted_by` address, the stored grant passes the filter again — the delegate's authority resurrects invisibly. The README's own security notes state "The stale grant stays in storage and re-arms if the token returns to `granted_by`" (`contracts/position-nft/README.md:174-179`).
- The authors demonstrably treat resurrection as a defect in the adjacent path: `remove_delegate` explicitly deletes a *stale* grant (owner mismatch) precisely "preventing those grants from reactivating if the NFT returns to their original owner" (`storage/account.rs:223-239`, pinned by `remove_delegate_purges_stale_grant_preventing_resurrection` in `tests/storage/account.rs:180-226`). The same protection is missing for the transfer path — the grant survives unless someone happens to call `add_delegate` (overwrite) or `remove_delegate` (purge) during the window when another address owns the NFT.

This is the on-chain analog of UI spoofing: the user performs a benign-looking gesture (moving the account NFT out and back — e.g., consolidating wallets, a sale that falls through, or a "revoke by transfer" flow suggested by a UI that knows delegates "lapse on transfer") that silently restores an authorization the UI no longer displays as live. `get_delegates` returns an empty list while the grant is dormant, so off-chain tooling also reports no delegate.

### Impact Explanation

Theft of user funds (High-end Medium). A re-armed delegate is an active `PositionManagerConfig` address that satisfies `require_owner_or_delegate`, so it can call `withdraw` (pulling collateral up to the risk gates) and `borrow` (drawing debt the owner must repay or be liquidated on). For a collateral-only account, the delegate can borrow against it to the LTV limit and then let liquidation strip the remainder — full economic loss of the collateral net of liquidation bonus. No further signature from the owner is required once the grant re-arms.

### Likelihood Explanation

Medium. It needs: (1) the owner to have granted a delegate, (2) the owner to transfer the NFT away and back without calling `remove_delegate`/`add_delegate` in between, and (3) the delegate to still hold an active manager registration. The phished-gesture scenario is realistic: a malicious or compromised manager can itself induce the round trip (e.g., offer to "buy" the position NFT and sell it back, or get the user to transfer for a supposed security migration) precisely because the dormant grant is invisible to the owner and to any off-chain reader of `get_delegates`. The permissionless entrypoint table documents `add_delegate`/`remove_delegate` as owner-only (`scripts/permissionless_entrypoints.txt:57-58`), but neither is required for the resurrection — only the NFT round trip.

### Recommendation

Purge or invalidate `ControllerKey::Delegates(account_id)` at transfer time. Since the controller is not invoked by the NFT on transfer, the practical fix is to stamp grants with a transfer-resistant epoch rather than `granted_by` alone — e.g., include a per-account generation counter incremented by a small controller entrypoint the NFT calls on `transfer`/`transfer_from` (the controller already owns `mint`/`burn` cross-contract calls), or store grants keyed under `(account_id, granted_by, ownership_epoch)`. Absent an NFT callback, the minimal mitigation is to treat the stored `granted_by` as sufficient only if a fresh grant was written *after* the latest observed owner change — short of that, documentation should warn that a round-trip transfer re-arms delegates and `remove_delegate` must always be called before transferring.

### Proof of Concept

```text
// Built on the harness primitives used in
// tests/test-harness/tests/controller/position_nft.rs

let mut t = LendingTest::new().with_market(usdc_preset()).build();
t.supply(ALICE, "USDC", 1_000.0);
let account_id = t.account_id(ALICE);
t.enable_delegate(ALICE, "MANAGER", account_id);   // grant stamped granted_by=ALICE

// Alice "revokes" the manager by moving the account NFT, believing
// delegates lapse on transfer (README security rules).
t.nft_transfer(ALICE, BOB, account_id);
// get_delegates(account_id, BOB) == [] — UI shows no delegate; stored grant persists.

// ...time passes; NFT returns to ALICE (sale unwound, wallet migration back, etc.)...
t.nft_transfer(BOB, ALICE, account_id);

// No add_delegate call occurred, yet the stale grant re-arms:
// MANAGER is again a valid delegate for account_id and can draw funds.
t.borrow_as_to("MANAGER", account_id, "USDC", 900.0, "MANAGER"); // succeeds — funds leave to MANAGER
```

Confirmed mechanics: `get_delegates` filters on `granted_by == owner` only (`storage/account.rs:176-181`); the NFT `transfer` emits only the stock `Transfer` event with no controller callback (`contracts/position-nft/README.md:127-134`); `is_owner_or_delegate` then admits the manager for `borrow`/`withdraw` (`account.rs:114-127`, permissionless-entrypoint justification lines 49-58).

Uncertainty note: the README documents the re-arm as a factual storage property; if the project classifies that sentence as an accepted design decision rather than an oversight, this would fall under the excluded "documented ADR choices". The `remove_delegate` purge logic and its dedicated resurrection-prevention test indicate the authors treat grant resurrection as a bug class, so the residual transfer path is reported here.
