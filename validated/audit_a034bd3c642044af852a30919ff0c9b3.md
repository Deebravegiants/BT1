### Title
Unauthenticated `changeLockTimer()` mutates `autoLockTimerAtom` even while wallet is locked, letting an attacker pre-set the TTL used by the next unlock's passphrase cache - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache.changeTtl()` unconditionally writes the caller-supplied TTL into `#autoLockTimerAtom` before checking whether a passphrase is currently cached, so the guard that gates the rest of the method (storage write + reschedule) does not actually prevent the TTL value from being persisted. Because `set()` (called on unlock) derives its stored TTL from `#autoLockTimerAtom.get()`, a call made while the wallet is locked silently seeds the TTL that will govern the *next* unlocked session.

### Finding Description
`changeTtl` is implemented as:
```
async changeTtl(ttl: number) {
  const newTtl = Math.min(this.#maxTtl, ttl)
  await this.#autoLockTimerAtom.set(newTtl)   // <- unconditional
  const passphrase = await this.#storage.get(PASSPHRASE_KEY)
  if (passphrase) {
    await this.#storage.set(TTL_KEY, newTtl)
    void this.#scheduleClear()
  }
}
``` [1](#0-0) 

The `if (passphrase)` check only protects the `TTL_KEY` storage write and the alarm reschedule — it does **not** guard the `#autoLockTimerAtom.set(newTtl)` call, which runs regardless of lock state. `Application.changeLockTimer` forwards directly to this method with no lock-state check of its own:
```
changeLockTimer = async ({ ttl }: { ttl: number }) => {
  return this.#passphraseCache.changeTtl(ttl)
}
``` [2](#0-1) 

Later, when the wallet is unlocked, `Application.unlock` calls `passphraseCache.set(opts.passphrase)`:
```
if (opts?.passphrase) {
  void this.#passphraseCache.set(opts.passphrase)
}
``` [3](#0-2) 

and `set()` reads the TTL straight from the atom:
```
async set(passphrase: string) {
  const ttl = await this.#getTtl()      // this.#autoLockTimerAtom.get()
  await this.#storage.batchSet({
    [PASSPHRASE_KEY]: passphrase,
    [ADDED_AT_KEY]: Date.now(),
    [TTL_KEY]: ttl,
  })
}
``` [4](#0-3) 

So the sequence `lock()` → `changeLockTimer({ttl:X})` (no-op branch, but atom is still mutated) → `unlock({passphrase})` results in the freshly cached passphrase inheriting the attacker-supplied `X` (capped at `#maxTtl`) as its TTL, even though no passphrase existed in cache when `changeLockTimer` was invoked. `restartAutoLockTimer` (`scheduleClear()`) is properly gated by the `passphrase` check for its side effects, but it still reads `#getTtl()` from the same shared, ungated atom via `#scheduleClear`.

### Impact Explanation
This lets an unprivileged/unauthenticated caller (per the stated precondition that `changeLockTimer`/`restartAutoLockTimer` RPCs have no unlock gate) influence how long the passphrase will remain cached in memory/storage for the *next* session, up to the configured `maxTtl` ceiling. This extends the window during which a cached passphrase is available to `get()`/auto-unlock logic, increasing the attack surface for extracting or reusing the cached secret (e.g., via a subsequent compromise of the storage or an autounlock path) beyond what the user configured for that session. Impact is bounded by `#maxTtl` (default 60 minutes), so it is a session-persistence/timing integrity issue rather than a direct secret-disclosure or signing bypass.

### Likelihood Explanation
Feasible and repeatable as long as the RPC surface exposes `changeLockTimer`/`restartAutoLockTimer` without an unlock/auth gate (stated precondition). The call sequence lock → changeLockTimer → unlock is trivial to reproduce and requires no privileged state, keys, or social engineering — only ordinary RPC access to the `application` module, which is marked `public: true` [5](#0-4) .

### Recommendation
Move the `#autoLockTimerAtom.set(newTtl)` call inside the `if (passphrase)` branch in `PassphraseCache.changeTtl`, so the atom (and therefore the TTL used by the next `set()`) is only updated when there is an active cached passphrase / unlocked session. Additionally, add an explicit locked-state check in `Application.changeLockTimer` / `restartAutoLockTimer` to reject calls while `lockedAtom` is true, ensuring TTL state can never be derived from a call made outside an active unlocked session.

### Proof of Concept
Unit/invariant test in `passphrase-cache` test suite:
1. Instantiate `PassphraseCache` with a mock `storage`, `alarms`, and `autoLockTimerAtom`.
2. Ensure no passphrase in storage (locked state).
3. Call `changeTtl(attackerTtl)` where `attackerTtl` differs from the default/current atom value.
4. Assert `autoLockTimerAtom.get()` now equals `min(maxTtl, attackerTtl)` even though no passphrase existed (demonstrating the ungated mutation).
5. Call `set('unlockedPassphrase')` to simulate a subsequent unlock.
6. Assert the stored `TTL_KEY` equals `attackerTtl` (capped), proving the attacker-supplied TTL from the locked-state call carried over into the new unlocked session — violating the invariant that TTL state must only derive from values set during an active unlocked session.
