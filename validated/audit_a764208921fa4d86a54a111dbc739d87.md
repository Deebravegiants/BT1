### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC computed over the raw request body only, but then trusts the `X-Shopify-Shop-Domain` header — which is completely outside the HMAC's coverage — as the authoritative tenant identity passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`: [2](#0-1) 

Yet `Request#shop` is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` straight to the app's `WebhookHandler#handle` via `WebhookMetadata`, with no additional binding between the shop and the signed body: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop attributed to the payload == shop cryptographically vouched for by Shopify's HMAC`. In this implementation, the HMAC vouches only for the body bytes, not the shop attribute, so the equality never actually holds — the `shop` value is trusted without being bound to the signature at all (a field acted on but not covered by the HMAC).

### Impact Explanation
An attacker who operates their own Shopify store and installs the target app receives genuine webhooks for their own shop — real `raw_body` + valid `hmac-sha256` header pairs signed with the app's `api_secret_key`. Because the signature never covers the `shop-domain` header, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (the body is unmodified and its HMAC matches), and `Registry.process` calls the app's handler with `WebhookMetadata` claiming the victim's shop but carrying the attacker's data/topic. Any handler that uses `data.shop` to look up a stored session, write per-tenant records, or trigger tenant-scoped side effects (the pattern this gem's webhook API is designed to support) can be induced to associate attacker-controlled webhook content with a victim tenant — a cross-tenant data-injection primitive reachable purely through this gem's own `process` method, without needing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Exploitation only requires the ability to become an app-installing merchant (trivial — anyone can install most public/embedded Shopify apps on their own development or trial store) and standard internet access to the app's public webhook endpoint. No credentials, tokens, or privileged access are needed; only the header value needs to be forged, which is fully attacker-controlled in any raw HTTP request.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header claims to the signed payload before trusting them. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (mirroring how Shopify's own webhook signature scheme is documented to work), and `HmacValidator`/`Request` should reject any mismatch between a body-embedded shop identifier (if present) and the header-derived one.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for the app's `api_secret_key`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `Utils::HmacValidator.validate(request)` recomputes HMAC over `to_signable_string` (`= B`) and it matches `H`, so validation passes: [6](#0-5) 
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, despite the payload never having been authenticated for that shop.
