**Reasoning:**

`AccessPath::get_struct_tag` simply pattern-matches on the deserialized `Path` enum and returns the inner `StructTag` for either variant: [1](#0-0) 

The `Path` enum (`Code`, `Resource`, `ResourceGroup`) is a standard BCS-tagged enum, so the discriminant is embedded unambiguously in the serialized bytes at construction time — `bcs::from_bytes::<Path>` cannot "confuse" a `Resource` variant for a `ResourceGroup` variant or vice versa; the byte layout for each variant is fixed by its ordinal position: [2](#0-1) 

Crucially, the decision of whether a given struct is stored/read as `Path::Resource` vs `Path::ResourceGroup` is not attacker-controlled at query time. It is derived from the Move struct's compile-time `#[resource_group_member(group = ...)]` attribute, which the VM resolves via `get_resource_group_member_from_metadata` in the data cache when constructing state keys/access paths: [3](#0-2) 

For `fungible_asset::FungibleStore` (which holds the `frozen` field checked by dispatchable hooks), this attribute is a fixed annotation in the framework source, not something an unprivileged caller can flip via any "REQUIRED_STATE" input: [4](#0-3) 

Resource-group members are read back through group-aware resolution (e.g., `try_into_resources_from_resource_group` / `find_resource` in the API layer, or `ResourceGroupAdapter`/`StorageAdapter` in the VM), which decode the `BTreeMap<StructTag, Bytes>` blob and look up the specific `StructTag` key rather than relying on `get_struct_tag`'s output alone to select a group member: [5](#0-4) 

There is no code path in this codebase where an unprivileged transaction, view function, or authenticator input can cause the VM or API layer to reinterpret a `ResourceGroup(tag)` access path as a `Resource(tag)` one (or vice versa) for the same `StructTag`, since the group/non-group classification is a static property of the Move type definition, not a runtime/attacker-supplied value. The proof idea in the question does not identify an actual mechanism by which attacker-controlled input reaches this discriminant decision — it assumes a decoding ambiguity that does not exist in the BCS-tagged `Path` enum.
