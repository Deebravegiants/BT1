### Title
Backend-controlled `operator_qr_expiration_time` re-evaluated with a fresh (not pinned) value, allowing stale operator-authorization state to be reused beyond its originally intended freshness window - (File: `src/plans/mod.rs`)

### Summary
This is the same bug class as the StRSR `unstakingDelay` finding: a single time-bound authorization state (there, a pending unstake "draft"; here, the scanned/validated `operator_data`) is checked against a duration value that is *reloaded from live config* rather than pinned to the value in effect when that state was created. When the backend-controlled duration changes mid-session, different code paths in the same signup flow enforce the freshness check with different values, producing an inconsistent, unintentionally extended validity window for already-validated operator authorization data.

### Finding Description
`MasterPlan::run` reads `operator_qr_expiration_time` from the shared config **once**, before entering its main loop, and reuses that same locally-captured value across the entire lifetime of the loop for `scan_initial_qr_codes` and `idle_wait_for_signup_request`: [1](#0-0) [2](#0-1) 

Meanwhile `do_signup`, invoked on every loop iteration, re-reads `orb.config.lock().await` **fresh** each time, picking up whatever value the backend has pushed in the interim (config is polled every `CONFIG_UPDATE_INTERVAL` = 10s): [3](#0-2) [4](#0-3) 

That freshly-read value is then used inside `scan_remaining_qr_codes` to decide whether the *already scanned* `operator_data` (whose `timestamp` was fixed at the moment it was captured) is still considered valid, and if so, it is reused directly without re-invoking `verify_operator_qr_code` against the backend: [5](#0-4) 

The freshness gate itself is the pending-state timestamp compared against a duration read at a different point in time than when the state was created: [6](#0-5) 

If the backend increases `operator_qr_expiration_time` (e.g. from a short default window to `Duration::from_secs(60*60*23)`) after `operator_data.timestamp` was recorded, the elapsed-time check performed in `scan_remaining_qr_codes` (and in `idle_scan_user_qr_code`'s remaining-timeout calculation) will use the *new, larger* value rather than the value that was in effect when the operator badge was validated: [7](#0-6) 

This is functionally identical to the `unstakingDelay` bug: a time-bound authorization artifact created under one policy value is later re-evaluated under a different (changed) policy value fetched at a different point in the code, producing enforcement that the original design never intended.

### Impact Explanation
`operator_data` carries the operator's validated location/identity binding (`location_data`, `qr_code`) that is subsequently used to validate the user QR-code, gate self-serve underage flows, and populate the personal-custody-package credentials and location metadata reported to the backend. If the operator-authorization freshness window is silently extended by a live config change, a previously-scanned operator context can be reused for signups occurring long after the operator's presence/validity was originally intended to expire, without the code re-confirming with the backend via `verify_operator_qr_code`. That means signups occurring in the extended window are attributed to operator/location data that was only ever validated against the shorter, original window — a form of stale/misattributed signup context that the freshness check exists specifically to prevent.

### Likelihood Explanation
This requires only an ordinary backend-driven config change (`operator_qr_expiration_time` is a normal, remotely-settable `Config` field polled every 10 seconds) combined with the orb running in self-serve/long-lived mode where `MasterPlan::run`'s outer loop and `initial_qr_codes`/`operator_data` persist across many signups. No hardware access, malicious peer, or malicious operator action is needed — it is purely a consequence of inconsistent value-capture timing between `MasterPlan::run`'s one-time config snapshot and `do_signup`'s fresh per-iteration snapshot.

### Recommendation
Pin the `operator_qr_expiration_time` (and any other duration used to gate a previously-created timestamped state) to the value that was in effect at the moment the state (`operator_data`) was created, and store it alongside the timestamp rather than re-reading it from the live config at each check site. Alternatively, require the freshness/expiration check to always use the *minimum* of the value at creation time and current time, so that increasing the config value can never retroactively extend the validity of already-captured operator authorization state.

### Proof of Concept
1. Orb runs in self-serve mode; operator scans QR code, `operator_data.timestamp` is set to `Instant::now()`, and `scan_initial_qr_codes`/`idle_wait_for_signup_request` are gated on `operator_qr_expiration_time = T1` captured once at the top of `MasterPlan::run` (`src/plans/mod.rs:329-350`).
2. Some time later, before `T1` has elapsed, the backend management console increases `operator_qr_expiration_time` to a much larger value `T2` (`src/backend/config.rs:74`, `src/config.rs:135`), which is picked up by the 10-second config poll.
3. A subsequent loop iteration calls `do_signup`, which re-reads config and obtains `T2` (`src/plans/mod.rs:497-506`), then calls `scan_remaining_qr_codes` with `T2` (`src/plans/mod.rs:788-793`).
4. Because `operator_data.timestamp.elapsed() < T2` (the newly-increased value) even though it would have already exceeded `T1`, the `QrCodes::Operator { operator_data } if operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch (`src/plans/mod.rs:806-820`) reuses the stale operator authorization without re-calling `verify_operator_qr_code`, extending its effective validity beyond what was intended at the time it was captured.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
