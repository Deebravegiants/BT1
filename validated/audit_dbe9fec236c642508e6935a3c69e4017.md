Audit Report

## Title
`EngineMeter::charge_ref_time` never actually deducts fuel, allowing a contract to run extra Wasm instructions beyond its charged gas — (File: `substrate/frame/contracts/src/gas.rs`)

## Summary
`EngineMeter::charge_ref_time` computes `amount = ref_time / ref_time_by_fuel()` and calls `self.fuel.checked_sub(amount)` only to test for underflow via `.ok_or_else(...)?`, discarding the `Some(value)` result instead of assigning it back to `self.fuel`. `self.fuel` is therefore never actually decremented, and the stale, pre-host-call value is returned as `Syncable(self.fuel)`, which is written directly into wasmi's fuel counter via `__caller__.set_fuel(fuel)` in the proc-macro-generated `sync_gas_after` block.

## Finding Description
The gas-sync protocol is: on host-function entry, `sync_from_executor(fuel)` calls `EngineMeter::set_fuel`, which correctly computes `consumed = self.fuel.saturating_sub(fuel) * ref_time_by_fuel()` and reassigns `self.fuel = fuel` [1](#0-0) . This confirms the intended pattern of assigning the recomputed fuel back into `self.fuel`.

On host-function exit, `sync_to_executor(before)` computes `ref_time_consumed` and calls `self.engine_meter.charge_ref_time(ref_time_consumed)` [2](#0-1) . But `charge_ref_time` itself is broken:

```rust
fn charge_ref_time(&mut self, ref_time: u64) -> Result<Syncable, DispatchError> {
    let amount = ref_time
        .checked_div(T::Schedule::get().ref_time_by_fuel())
        .ok_or(Error::<T>::InvalidSchedule)?;

    self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
    Ok(Syncable(self.fuel))
}
``` [3](#0-2) 

The `checked_sub` result (`Some(new_fuel)`) is used only for its discriminant to detect underflow; the actual decremented value is discarded, and `self.fuel` is left unmodified. `Syncable(self.fuel)` therefore returns the stale pre-host-call fuel value, which the proc-macro then writes straight into wasmi via `__caller__.set_fuel(fuel)` [4](#0-3) . This restores wasmi's Wasm-instruction fuel counter to what it was before the host call, ignoring the weight consumed by the host function body.

This is confirmed as a genuine asymmetry between `set_fuel` (correctly mutates `self.fuel`) and `charge_ref_time` (does not), both operating on the same `EngineMeter<T>::fuel` field [5](#0-4) . Notably, the equivalent code path for the `revive` pallet (`substrate/frame/revive/src/metering/weight.rs`) uses a different, correct implementation — `sync_remaining_ref_time` directly reassigns `self.fuel = remaining_ref_time.saturating_div(...)` [6](#0-5)  — showing that the `pallet-contracts` version is the outlier and demonstrating what the correct pattern should look like.

`GasMeter::gas_left` (the pallet's own weight ledger) is decremented correctly via ordinary `charge()` calls independent of this bug, so the pallet eventually detects `OutOfGas`. However, wasmi's separate fuel counter — the actual mechanism halting raw Wasm-instruction execution — is repeatedly "topped up" with un-deducted host-function overhead on every chargeable host-function call, letting the contract execute extra real Wasm instructions before `gas_left` (checked at the next `sync_from_executor`) finally catches the discrepancy.

## Impact Explanation
This is a metering-bypass bug: on every chargeable host-function call, wasmi's fuel counter is not properly reduced by the host-function's own cost, so real Wasm-instruction execution can exceed what `gas_limit` authorized before the pallet's own ledger (`gas_left`) catches up and aborts with `OutOfGas`. The magnitude of "banked" extra fuel scales with the number of host-function calls the attacker chooses to make. This is a genuine, in-scope weight-metering correctness issue in `pallet-contracts`, reachable through ordinary, permissionless contract execution.

## Likelihood Explanation
The bug is deterministic and fires on every single `sync_to_executor` call regardless of remaining fuel — no races, reentrancy, or special preconditions are required. Any contract that calls a chargeable host function (essentially all non-trivial contracts) triggers it, and an attacker fully controls the number of host-function calls made (to accumulate "banked" fuel) followed by a pure-Wasm compute loop (to spend it).

## Recommendation
Assign the decremented value back to `self.fuel` in `charge_ref_time`:
```rust
fn charge_ref_time(&mut self, ref_time: u64) -> Result<Syncable, DispatchError> {
    let amount = ref_time
        .checked_div(T::Schedule::get().ref_time_by_fuel())
        .ok_or(Error::<T>::InvalidSchedule)?;

    self.fuel = self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
    Ok(Syncable(self.fuel))
}
```
This mirrors the correct pattern already used in `EngineMeter::set_fuel` in the same file, and in the analogous `revive` implementation.

## Proof of Concept
1. Unit test in `substrate/frame/contracts/src/gas.rs`: construct `GasMeter::<Test>::new(gas_limit)`, call `sync_from_executor(engine_fuel)` to simulate host-function entry, call `gas_meter.charge(some_token)` to simulate host-function body cost, then call `sync_to_executor(before)` and assert the returned `Syncable` fuel value is strictly less than the pre-call fuel by `ref_time_consumed / ref_time_by_fuel`. Under the current code, the returned value equals the pre-call fuel (no decrement), failing this assertion.
2. Integration-level test: deploy a contract that loops calling a cheap chargeable host function (e.g., `seal_set_storage`) N times, then spins in a pure-Wasm busy loop; measure actual wasmi fuel consumed and confirm it exceeds `gas_limit / ref_time_by_fuel` by approximately `N * hostfn_cost_in_fuel_units` before `OutOfGas` is triggered.
