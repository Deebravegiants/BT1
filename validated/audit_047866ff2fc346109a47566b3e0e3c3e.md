### Title
Permanent market freeze: `scaled_to_original` overflows i128 during accrual before the borrow-index cap engages, bricking all operations on a large high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
The bug class in CVE-2022-21254 is an availability failure: a reachable code path that crashes the system. In XOXNO Lending the analogous shape is the interest-accrual path that every pool mutation runs first. `accrue_step` multiplies the scaled debt (`borrowed`) by the current `borrow_index` inside `scaled_to_original` before the borrow index is clamped. On a large market held at high utilization, index growth pushes that product past `i128::MAX` *before* `update_borrow_index` ever reaches `MAX_BORROW_INDEX_RAY`, so the accrual panics with `MathOverflow`. Because `interest::global_sync` runs at the head of every market verb, the panic bricks `supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `update_indexes`, `claim_revenue` and liquidation settlement for that market — permanently, since the stored index never decreases.

### Finding Description
`common/src/rates/simulate.rs:60` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` where `scaled_to_original` is a plain `Ray::mul` (`common/src/rates/scaling.rs:14-16`) that panics on i128 overflow. The cap in `update_borrow_index` (`common/src/rates/index.rs:13-19`) is applied to the *index*, not to the *debt value* `borrowed * index`, so the value ceiling (~1.7e38 RAY-units, far below the index cap of 1e36 RAY times a whale book) is hit first. `contracts/pool/src/interest.rs:20-33` runs `global_sync` unconditionally before every mutation, and the test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) confirms the end state: `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. There is no recovery path — accrual cannot be skipped, and `replace_rate_model` also accrues under the old model first (`contracts/pool/src/ops/market.rs:52-58`).

### Impact Explanation
Permanent freezing of funds: once the market crosses the RAY-value cliff, suppliers cannot withdraw, borrowers cannot repay, liquidations cannot settle, and protocol revenue cannot be claimed. Every entrypoint touching that `(hub, asset)` book reverts inside `global_sync`. The frozen book still physically holds the pool's token balance for that market, so supplier principal and accrued yield are locked indefinitely.

### Likelihood Explanation
A single unprivileged address can set up the state using only `supply` and `borrow`: supply a large amount of a high-decimal asset, then borrow ~98% of it and hold the position at high utilization. The market's own listed caps can be raised by normal usage on an uncapped or generously capped market; no privileged action is required. The remaining ingredient is elapsed time — the attacker cannot advance ledger time, so the freeze is not instantaneous, but it is deterministic: interest accrual alone carries the market over the cliff, and once there, no transaction can unwind it. The protocol's own test demonstrates the cliff is reached in a few years on the XLM-style rate curve at 98% utilization, and the docs acknowledge the same bound ("Finite RAY value capacity can be exhausted before the index ceiling… then fail before an otherwise risk-reducing operation", `docs/explanation/threat-model.md:319-321`).

### Recommendation
Make accrual saturate instead of panicking: in `accrue_step`, compute `scaled_to_original` via a saturating `mul_div` (e.g. `mul_div_floor_saturating`) or clamp `borrowed * borrow_index` at `MAX_RAY_VALUE` so utilization calculation degrades gracefully at the cliff rather than trapping. Additionally, when `borrow_index` reaches `MAX_BORROW_INDEX_RAY`, stop accruing early before computing the overflowed product. A governance `update_params`/rate-model replacement path should also be able to run with accrual skipped or capped so a near-cliff market can be defused.

### Proof of Concept
1. On a market with an 18-decimal asset and a steep rate curve, call `supply` with `1e9 * 10^18` units (permissionless; caps lifted or generous).
2. Supply collateral on a second market and call `borrow` for ~98% of the first market's liquidity.
3. Let time pass; each `update_indexes` call compounds the borrow index at the steep segment.
4. After the index grows ~170x, `borrowed * borrow_index` exceeds `i128::MAX`; the next `update_indexes`, `withdraw`, `repay`, or `liquidate` on that market panics in `scaled_to_original` with `GenericError::MathOverflow` — verified by `large_positions_and_long_horizons.rs:343-356`, which asserts `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with error 33 while `borrow_index < MAX_BORROW_INDEX_RAY`.
