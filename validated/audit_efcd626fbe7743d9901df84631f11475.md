### Title
Missing enforcement of operator QR-code expiration before signup-critical actions in `scan_remaining_qr_codes` - (File: `src/plans/mod.rs`)

### Summary
The ERC-7683 bug involves a missing deadline check (`fillDeadline`) before executing an action (`fill()`), allowing the action to proceed after its validity window and causing state/reward inconsistency elsewhere in the system. The closest unprivileged-user analog in orb-core is the operator QR-code expiration (`operator_qr_expiration_time`) check in the signup flow in `src/plans/mod.rs`, which similarly gates whether a signup-authorizing credential (the operator QR code) is still valid before proceeding to bind a user identity to that operator session.

### Finding Description
`scan_remaining_qr_codes` in `src/plans/mod.rs` decides whether to reuse a previously scanned operator QR code based on `operator_data.timestamp.elapsed() < operator_qr_expiration_time`: [1](#0-0) . If the elapsed time is within the expiration window at the moment this branch is evaluated, the code proceeds directly to `scan_user_qr_code`, binding the user identity to the previously captured `operator_data` (including `location_data` and permissions tied to that operator session) without re-validating the operator credential at the point the user QR is actually processed/committed [2](#0-1) .

Similarly, `idle_scan_user_qr_code` computes a remaining timeout for the user QR scan as `operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())` [3](#0-2) , but this is only used to bound the *scan* timeout — there is no final re-check comparing `block.timestamp`-equivalent (`Instant::now()`) against `operator_data.timestamp + operator_qr_expiration_time` immediately before `handle_user_qr_code` commits the signup binding at line 479 [4](#0-3) . Because the expiration check and the actual identity-binding action (`handle_user_qr_code`) are separated by scan latency (user interaction, camera exposure, QR decoding), a TOCTOU-style gap exists where the operator credential could be treated as valid at the "check" instant but is actually past its intended validity window by the time the signup-binding action executes — the same structural class of bug as the ERC-7683 report (deadline checked in a supporting function/path but not enforced at the point where the state-changing action commits).

### Impact Explanation
If the operator QR expiration is not strictly re-validated at the moment of committing the user-to-operator identity binding, a signup could be attributed to an operator session that should have already expired, similar in structure to the reward loss/misattribution class in the original report — here it would manifest as a misattributed signup (wrong/stale operator association) rather than fund loss, since orb-core has no filler-reward analog. This is an unprivileged-user-reachable path since it occurs during the ordinary signup flow with an unprivileged user presenting a QR code.

### Likelihood Explanation
Low. This requires the scan/processing latency between the expiration check and the `handle_user_qr_code` call to straddle the exact `operator_qr_expiration_time` boundary, which is a narrow race window and not something a user can reliably engineer without also controlling scan timing precisely.

### Recommendation
Add a final, explicit expiration check (e.g., `operator_data.timestamp.elapsed() < operator_qr_expiration_time`) immediately before or inside `handle_user_qr_code` at `src/plans/mod.rs:479`, and in the corresponding call in `idle_scan_user_qr_code`, so that the operator credential is validated at the point of state commitment rather than only at branch-selection time.

### Proof of Concept
Not independently verifiable from the indexed code alone — the exact latency between the `operator_data.timestamp.elapsed() < operator_qr_expiration_time` check at [5](#0-4)  and the `handle_user_qr_code` commit at [4](#0-3)  depends on runtime QR scan behavior not present in the excerpted source. I recommend a Devin session with full repo/terminal access to trace `handle_user_qr_code`'s implementation and confirm whether it performs its own expiration re-check, which would rule out or confirm exploitability.
