### Title
Order withdrawal permanently reverts and freezes an order's entire escrow when any single output token transfer fails (e.g. blacklist) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` iterates over every token in a `WithdrawalRequest` and performs a `safeTransfer` (or native `_sendValue`) to a single fixed `beneficiary` derived from `order.user`. If any single token in that loop reverts on transfer to the beneficiary (a blacklist-style ERC-20 such as USDC/USDT refusing a sanctioned/blacklisted address, or a non-payable/reverting beneficiary for native value), the entire `_withdraw` call reverts, which reverts `onAccept`, so none of the order's escrowed tokens (including unrelated, non-blacklisted assets in the same order) are ever released. [1](#0-0) 

### Finding Description
Both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) settlement paths route through `_withdraw`, which fixes the beneficiary once (`address(uint160(uint256(body.beneficiary)))`) and loops over all `body.tokens`, transferring each unconditionally: [2](#0-1) 

Because `IERC20.safeTransfer` reverts if the underlying token itself reverts (e.g., a blacklisted recipient on centralized stablecoins, or a token with transfer hooks/fee-on-transfer edge cases that revert), and `_sendValue` reverts if the native-token recipient cannot accept ETH [3](#0-2) , a single poisoned token or unreceivable beneficiary aborts the whole withdrawal.

This is delivered through `onAccept`, which is called by the ISMP host after a cross-chain `RedeemEscrow`/`RefundEscrow` message is authenticated [4](#0-3) . Per the documented dispatch semantics, when the app's `onAccept` call fails, the host deletes the receipt and lets the relayer resubmit the exact same message later — it never re-derives a different beneficiary or splits the transfer set. Redelivery of the identical payload hits the identical revert every time, so the failure is not merely "retryable" but is **deterministically permanent**: the beneficiary (`order.user`) is baked into the order at placement time and cannot be changed by the user, a relayer, or governance after the fact.

The `beneficiary` for a `RefundEscrow`/`RedeemEscrow` message is always `order.user` (see `_cancelFromDest`, which sets `WithdrawalRequest.beneficiary: order.user` unconditionally) [5](#0-4)  — there is no mechanism for a keeper/relayer to redirect the payout to a non-blacklisted address, and the docs confirm "An outside caller cannot redirect the refund." [6](#0-5) 

The blueberry analog is structurally identical: a single blocked operation (there, `repay`; here, one token's `transfer`) that is a hard dependency of the settlement/liquidation path causes the entire recovery mechanism to be permanently unusable, locking funds that should have been recoverable.

### Impact Explanation
Any multi-token order where one of the escrowed input tokens is a blacklist-capable stablecoin (USDC, USDT, and similar tokens are explicitly supported input assets in the Intent Gateway) becomes permanently frozen if the order's `user` address is later blacklisted by that token's issuer, or if the beneficiary cannot receive native value. Because `_withdraw` releases the *entire* token set atomically per finalize call, this also blocks the release of all co-escrowed, non-blacklisted tokens in the same order — not just the offending one. Funds become permanently unrecoverable through the protocol's own mechanisms (no admin override or force-withdraw path was found in the code shown), constituting a permanent freeze of user/solver funds.

### Likelihood Explanation
This is reachable by any ordinary, unprivileged actor: a user places a cross-chain order with a blacklistable input token and a compliant/frozen `order.user` address (or one that later becomes blacklisted before settlement finalizes), or a solver fills an order whose output the solver cannot receive. No admin, governance, or consensus compromise is required — only normal usage of the Intent Gateway with a widely used token that has centralized freeze/blacklist functionality (USDC, USDT). Given how common such tokens are as bridge assets, the likelihood of a legitimate blacklisting event colliding with an in-flight order over the system's lifetime is non-trivial.

### Recommendation
Make per-token failures non-fatal to the overall withdrawal: wrap each token transfer in a try/catch (or low-level call) so that a failing transfer for one token does not block the release of the others, and/or move failed transfers into a separate pull-based "claimable" escrow bucket that the beneficiary (or a redirect they authorize) can later claim to a different address, rather than looping unconditional `safeTransfer`/`_sendValue` calls whose failure reverts the entire `_withdraw`.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2`/`ExtrinsicIntents` with two escrowed input tokens: USDC and DAI, `order.user = Alice`.
2. Before the order is filled/cancelled, Alice's address is added to USDC's blacklist (a real, permissionless-to-trigger-by-issuer but out-of-protocol-control event).
3. Alice cancels from the destination chain (or the order expires and anyone triggers `_cancelFromDest`), dispatching a `RefundEscrow` message with `beneficiary = Alice` and `tokens = [USDC, DAI]`. [5](#0-4) 
4. On the source chain, `onAccept` calls `_withdraw`, which attempts `IERC20(USDC).safeTransfer(Alice, amount)`; USDC's blacklist causes this call to revert, reverting the whole `_withdraw`/`onAccept` transaction. [1](#0-0) 
5. The host records the delivery as failed and allows resubmission, but the identical message will revert identically every time since `beneficiary` and `tokens` cannot be altered by anyone. Both the USDC and DAI escrow for this order remain permanently locked in the contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
