### Title
pf-floor bypass via ALT-unaware cost/priority computed in `calculate_priority_from_bytes` diverging from the ALT-resolved cost used everywhere downstream - (File: `core/src/transaction_priority.rs`, `core/src/sigverify.rs`, `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`)

### Summary
`calculate_priority_from_bytes` (used only as the sigverify-stage pf-floor gate in `apply_priority_floor_to_batch`) parses the packet into a plain `SanitizedTransactionView` and never resolves Address Lookup Table (ALT) addresses before calling `calculate_priority_and_cost`, whereas the downstream buffering path in `TransactionViewReceiveAndBuffer::try_handle_packet` fully resolves ALTs via `translate_to_runtime_view`/`load_addresses_for_view` before calling the very same `calculate_priority_and_cost`. For a versioned V0 transaction that loads additional writable accounts through an ALT, the unresolved view undercounts write-locks/account totals relative to the resolved view, so `cost.sum()` differs between the two call sites and `priority = reward*MULTIPLIER/(cost+1)` is inflated at the floor-check stage.

### Finding Description
`calculate_priority_from_bytes` in [1](#0-0)  builds a `RuntimeTransaction<SanitizedTransactionView<_>>` directly from raw packet bytes with no ALT resolution step, then feeds it into `calculate_priority_and_cost`, which computes `cost = CostModel::calculate_cost_for_executed_transaction(...).sum()` [2](#0-1) .

This is invoked exclusively from the sigverify-stage pf-floor filter `apply_priority_floor_to_batch`, which drops a packet outright (`packet.meta_mut().set_discard(true)`) whenever the computed priority is `<= floor` [3](#0-2) .

By contrast, once a packet survives sigverify, `TransactionViewReceiveAndBuffer::try_handle_packet` first calls `translate_to_runtime_view`, which resolves any V0 address-table lookups into a `LoadedAddresses` set via `bank.load_addresses_from_ref` and constructs a `RuntimeTransaction<ResolvedTransactionView<D>>` before computing the buffered/queued cost and priority with the *same* `calculate_priority_and_cost` function [4](#0-3) [5](#0-4) .

Because the ALT-loaded writable accounts (and any instruction data referencing them) are only visible after resolution, the write-lock count and total account count used by the cost model can be strictly smaller in the sigverify-time unresolved view than in the buffering-time resolved view for the same bytes. Since cost is in the denominator of the priority formula, an undercounted cost at the floor-check stage yields an inflated priority, letting a genuinely expensive ALT-heavy transaction slip past `apply_priority_floor_to_batch`'s discard check even though its true (resolved) cost — the one actually charged for block-limit/queue-priority purposes — is higher. The repo's own regression test, `floor_priority_from_bytes_matches_typed_path` [6](#0-5) , only exercises a legacy (non-versioned, no-ALT) transfer plus a compute-budget instruction, so it does not cover this divergence.

### Impact Explanation
This is a load-shedding/backpressure bypass, not a fund-loss or consensus-divergence bug: it undermines the sigverify pf-floor's purpose (dropping low-value transactions ahead of expensive signature verification and buffering under saturation) by letting an attacker craft ALT-referencing transactions whose apparent (unresolved) cost looks artificially low, so they evade the floor while genuinely consuming more real capacity once queued/scheduled downstream — where the correctly-resolved cost is used for actual block-cost accounting. This matches an "materially underpriced/undervalued gatekeeping check" category rather than value loss.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: craft and broadcast an ordinary V0 versioned transaction that references one or more writable accounts solely through an address lookup table (a completely standard, unprivileged transaction shape), during a period when the scheduler has published a non-zero priority floor (`priority_floor.get() > 0`, i.e., under load). No validator/leader control, keys, or special access needed — just normal TPU/RPC submission, repeatable at will.

### Recommendation
Make the pf-floor bytes-path cost/priority calculation consistent with the resolved typed path: either (a) resolve ALT addresses (as `translate_to_runtime_view` does) before calling `calculate_priority_and_cost` inside `calculate_priority_from_bytes`, or (b) apply a conservative worst-case cost adjustment (e.g., assume max possible ALT-loaded writable accounts) when the unresolved view indicates the transaction is versioned with address table lookups, so the floor check never underestimates cost relative to the resolved cost used everywhere else.

### Proof of Concept

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)

pub(crate) fn translate_to_runtime_view<D: TransactionData>(
    data: D,
    bank: &Bank,
    transaction_account_lock_limit: usize,
    sanitize_config: &SanitizeConfig,
) -> Result<(RuntimeTransaction<ResolvedTransactionView<D>>, u64), PacketHandlingError> {
    // Parsing and basic sanitization checks
    let Ok(view) = SanitizedTransactionView::try_new_sanitized(data, sanitize_config) else {
        return Err(PacketHandlingError::Sanitization);
    };

    let Ok(view) = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Discard non-vote packets if in vote-only mode.
    if bank.vote_only_bank() && !view.is_simple_vote_transaction() {
        return Err(PacketHandlingError::Sanitization);
    }

    if usize::from(view.total_num_accounts()) > transaction_account_lock_limit {
        return Err(PacketHandlingError::LockValidation);
    }

    let (loaded_addresses, deactivation_slot) = load_addresses_for_view(&view, bank)?;

    let Ok(view) = RuntimeTransaction::<ResolvedTransactionView<_>>::try_new(
        view,
        loaded_addresses,
        bank.get_reserved_account_keys(),
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Validate no duplicate accounts (must be after resolution to catch ALT duplicates)
    if validate_account_locks(view.account_keys(), transaction_account_lock_limit).is_err() {
        return Err(PacketHandlingError::LockValidation);
    }

    Ok((view, deactivation_slot))
}
