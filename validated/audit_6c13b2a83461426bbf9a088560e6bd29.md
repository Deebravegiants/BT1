### Title
Escrow release in IntentGatewayV2's `_withdraw`/`withdraw` will permanently revert (and lock escrowed funds) if the beneficiary is blacklisted by the escrowed ERC20 token - (File: evm/src/apps/intentsv2/IntentsBase.sol, evm/src/apps/intentsv2/ExtrinsicIntents.sol, evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
Just like the Cooler `repayLoan` bug (a push-only `safeTransferFrom` to a lender who may later be blacklisted causes the borrower's repayment to permanently revert), the IntentGateway's escrow-release path pushes ERC20 tokens directly to a `beneficiary` address with no pull-based fallback. If that beneficiary (the solver/filler on `RedeemEscrow`, or the user on `RefundEscrow`/cancel) is later blacklisted by the escrowed token (e.g., USDC), the transfer reverts and the message that delivers the escrow release can never be processed.

### Finding Description
`IntentsBase._withdraw()` iterates the withdrawal request's tokens and unconditionally pushes them to the `beneficiary`: [1](#0-0) 

This function is invoked from `ExtrinsicIntents.onAccept()` when a `RedeemEscrow` or `RefundEscrow` cross-chain POST request is delivered by Hyperbridge, and from `onGetResponse()` for source-chain cancellations: [2](#0-1) 

The identical unsafe push pattern also exists in the Tron variant, using low-level `.call` to `IERC20.transfer` with an explicit revert on failure: [3](#0-2) 

There is no attempt/fallback to let the beneficiary claim funds via a pull-based mechanism, and no try/catch is used around `onAccept` in the ISMP delivery path, so a blacklisted beneficiary makes the underlying `IERC20.safeTransfer`/`.call` revert and the entire `onAccept` transaction (i.e., the settlement message delivery) fails.

Because ISMP POST/GET-response messages are delivered exactly once via relayer-submitted proofs, and delivery always re-executes the same reverting transfer, this is not a retryable "temporary revert" — the message can never be successfully delivered while the beneficiary remains blacklisted, differing from the reported Cooler issue only in that Cooler's `repayLoan` is a repeatable user-initiated call (so the borrower could try again after being unblacklisted), whereas here the *specific settlement message* is bound to a single beneficiary address that was fixed when the order was placed/filled and cannot be changed after the fact.

### Impact Explanation
- On `RedeemEscrow`: if the solver/filler address that filled a cross-chain order gets blacklisted by the input token (escrowed asset) between fill and settlement delivery, the escrowed input tokens on the source chain can never be released to the filler — the tokens are frozen in the gateway contract indefinitely (the solver already delivered the outputs to the user on the destination chain, so this is a genuine loss/freeze of the solver's expected proceeds and a stuck state for the order).
- On `RefundEscrow`/cross-chain cancellation: if the original order `user` (or `order.user` for `_cancelFromSource`/`_cancelSameChain`) is or becomes blacklisted by the escrowed token, their refund can never be delivered — permanently freezing the escrowed input funds.
- Because `_filled[commitment]` is only marked in the same transaction that performs the transfer (`finalize=true`), a reverting transfer means the order's finalization state is never updated either — the order remains stuck in a state where it cannot be finalized, refunded, or otherwise recovered through any documented governance/sweep path in these files.

This satisfies "permanent freezing of funds" for a route reachable by any user/solver placing/filling orders and by Hyperbridge relaying delivery of a cross-chain settlement message — a core, unprivileged intents flow.

### Likelihood Explanation
Medium likelihood: it requires a centrally-blacklistable escrowed token (e.g., USDC, USDT) and requires the specific beneficiary address (filler or user) to become blacklisted after order fill/cancellation but before the settlement message is delivered — a scenario outside the control of the affected party but realistic for any regulated stablecoin, exactly mirroring the reported Cooler class of bug. A malicious/targeted beneficiary that anticipates blacklisting could also intentionally use an address they know will be sanctioned to grief the counterparty (e.g., a solver deliberately choosing to be blacklisted after filling to block a user's refund path, or vice versa), though the primary vector is passive (real-world blacklisting events).

### Recommendation
Change `_withdraw` (and the Tron `withdraw`) to use a pull-based claim pattern for beneficiaries when a direct push fails: wrap `IERC20(token).safeTransfer(beneficiary, amount)` in a try/catch (or a low-level call check) and, on failure, credit an internal `claimable[beneficiary][token]` balance that the beneficiary (or anyone, on their behalf) can withdraw later via a separate function, instead of reverting the whole settlement/refund processing. This decouples message delivery/finalization from the beneficiary's ability to receive tokens directly, avoiding permanent fund freezing.

### Proof of Concept
1. User places a cross-chain order on chain A escrowing USDC as `order.inputs`, with `order.output.beneficiary = user` and destination on chain B.
2. Solver `S` fills the order on chain B, delivering outputs to `user`, and the fill dispatches a `RedeemEscrow` message back to chain A naming `S` as the `beneficiary` in the `WithdrawalRequest` (see `_fillCrossChain` dispatch of `RedeemEscrow`): [4](#0-3) 
3. Before the relayer submits the ISMP proof to chain A, Circle blacklists `S`'s address in USDC.
4. The relayer submits the `RedeemEscrow` POST request proof to chain A; `EvmHost` calls `IntentGatewayV2.onAccept()` → `_authenticate` → `_withdraw(body, false, true)`.
5. Inside `_withdraw`, `IERC20(usdc).safeTransfer(S, amount)` reverts because `S` is blacklisted (`transfer to blacklisted account` revert in USDC).
6. The whole `onAccept` transaction reverts. Any relayer resubmission with the same proof produces the same revert. The escrowed USDC on chain A is now permanently stuck — the order can never be finalized, and `S`'s input funds are unrecoverable while the beneficiary address remains blacklisted, with no pull-based recovery path in the current code.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
