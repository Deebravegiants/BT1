Confirmed: `WebhookMetadata.shop` is a plain field passed directly to app handlers, sourced entirely from the unauthenticated `shop-domain` header.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by calling `Utils::HmacValidator.validate(request)`, which relies on `Request#to_signable_string`. That method returns only the raw HTTP body (`@raw_body`) — it does **not** include the `shop-domain`/`x-shopify-shop-domain` header. The `shop` value that is later handed to the app's `WebhookHandler` (as `WebhookMetadata#shop`) is read directly and unverified from that header, so the identity binding "shop authenticated == shop acted upon" is broken. ### Finding Description
The HMAC validation utility computes and checks the signature purely against `verifiable_query.to_signable_string`: [4](#0-3) 

For webhooks, `Request#to_signable_string` is defined as simply the raw body: [5](#0-4) 

Meanwhile `Request#shop` is parsed straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cryptographic tie to the HMAC: [6](#0-5) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only) before dispatching to the app handler, passing `request.shop` unmodified into `WebhookMetadata`: [2](#0-1) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata.shop`

But because only the body is HMAC-covered, the equality actually enforced is:
`body authenticated by HMAC != shop header authenticated by HMAC`

The gem's own documentation confirms `data.shop` is treated by app authors as the trusted tenant identifier for the webhook, e.g. used to look up `shop_domain` in the receiving app and drive per-tenant business logic: [7](#0-6) 

### Impact Explanation
Any party capable of producing an HTTP request whose body+HMAC pair is genuinely valid for the shared `client_secret` (this includes any real, even low-privilege, merchant install of the app, or anyone who has observed a single legitimately-delivered webhook body/HMAC pair for that topic and JSON payload) can replay that exact body with a **different** `shop-domain` header value. Because the gem's own `HmacValidator` only checks the body, `Registry.process` will accept the forged request as authentic and invoke the app's handler with `WebhookMetadata#shop` set to an arbitrary victim shop domain. Downstream apps (as shown in the documented usage pattern) key their persisted data, background jobs, or session lookups off `data.shop`, so this allows cross-tenant data confusion/impersonation of a webhook as if it originated from a different merchant's store — a cross-tenant boundary violation that is a direct, reachable consequence of this gem's code, not merely a host-application misuse, because the gem itself defines and hands the unauthenticated field to the app as if it were verified ("came from Shopify").

### Likelihood Explanation
Medium-High. No secret, access token, or privileged account is required for the identical-body replay: because JSON bodies for a given topic (e.g., `orders/create` with static test data) are often repeatable/predictable across shops (or the attacker legitimately receives one authentic delivery for their own installed shop), an attacker only needs to alter one HTTP header (`shop-domain`) that the receiving endpoint trusts implicitly via this gem's `WebhookMetadata`. The endpoint is a public HTTP route (webhook receivers must be internet-reachable), so this is exploitable by an unprivileged internet user with no TLS interception, no leaked credentials, and no social engineering.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id/api-version) in the HMAC-covered signable content, or otherwise cryptographically bind the shop identity to the signature — e.g., change `Request#to_signable_string` to concatenate `@raw_body` with the shop-domain header value (matching how Shopify actually intends the HMAC to attest the whole delivery), so that any tampering with the `shop-domain` header invalidates the HMAC.

### Proof of Concept
1. App has installed and is receiving webhooks from shop A (`shop-a.myshopify.com`), a store the attacker legitimately controls/operates as a merchant.
2. Attacker captures one authentic webhook delivery: raw body `B` and its valid `x-shopify-hmac-sha256` header `H`, computed by Shopify as `HMAC(secret, B)`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since it only covers `B`)
   - `x-shopify-shop-domain: shop-victim.myshopify.com` (changed)
   - `x-shopify-topic`, `x-shopify-webhook-id`: unchanged/reused
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`.
5. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata#shop == "shop-victim.myshopify.com"`, even though the payload never originated from Shopify for that shop — demonstrating the cross-tenant identity spoof enabled entirely by this gem's webhook verification logic.
