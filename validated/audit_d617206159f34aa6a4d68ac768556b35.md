### Title
Cross-tenant webhook spoofing via `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only that the HMAC of the raw body matches the app's shared `api_secret_key`, but the `shop` value that is subsequently trusted and handed to the app's handler is taken from an HTTP header that is **not** part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `#hmac` is decoded solely from the `hmac-sha256` header: [2](#0-1) 

`shop` is read from a separate, unauthenticated header: [3](#0-2) 

`Registry.process` validates the request by calling `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (the body) against `Context.api_secret_key`: [4](#0-3) [5](#0-4) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is passed straight into `WebhookMetadata` and forwarded to the app's handler: [6](#0-5) 

Because `Context.api_secret_key` is the same shared secret for **every** shop that installs the app, any tenant that legitimately receives a real webhook from Shopify (i.e., knows one valid `body + hmac` pair produced with the app's own secret, from their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. The HMAC validation, which only covers the body, will still succeed, and the handler will process the payload believing it originated from the victim tenant.

This is the same class of defect flagged in the source report: a value that participates in a security-sensitive equality binding (which tenant a body belongs to) is not covered by the cryptographic check that is supposed to authenticate the request, while other code paths (`Registry.process`, `WebhookMetadata`) implicitly assume `hmac_valid ⇒ shop_is_authentic`. The binding broken is:
`shop_that_signed_body == shop_attributed_to_request` — this equality is never checked; only `hmac(body, secret) == received_hmac` is checked, and `shop` is disjoint from `body` in the signable string.

### Impact Explanation
This permits cross-tenant confusion at the webhook boundary: a malicious merchant who is a legitimate install of the app can spoof webhook data as coming from a different merchant's shop. If the host application's webhook handlers key any state, data writes, feature-flag toggles, GDPR/redact actions, or entitlement updates off `data.shop` (as the gem's own `WebhookMetadata` structure explicitly encourages), an attacker can inject data or trigger actions attributed to a victim tenant, or exfiltrate/replay-confirm knowledge tied to another shop. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) the attacker's own real, unmodified webhook body+HMAC (trivially obtainable by any merchant who installs the app and receives at least one webhook), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — both are within reach of any unprivileged internet user / installed merchant, no access to `api_secret_key` or any privileged credential is needed.

### Recommendation
Bind the `shop` identity into the authenticated material, e.g., include the `x-shopify-shop-domain` header (and/or `topic`) in the HMAC-signed message, or independently verify the shop against a value that is bound to app-controlled state (e.g., cross-check against an actively-registered webhook/shop record) rather than trusting the unauthenticated header for dispatch and business-logic tenant attribution. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant-sensitive authorization decisions without additional verification.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant "attacker-shop.myshopify.com" of the app
# and has captured one real webhook delivery for their own shop:
raw_body = '{"id":123,"note":"hello"}' # genuine payload signed by Shopify for attacker's shop
real_hmac = "<value from real x-shopify-hmac-sha256 header on that delivery>"

# Attacker replays the identical body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,               # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (body unchanged), handler invoked with
#    WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```

          received_signature = verifiable_query.hmac
