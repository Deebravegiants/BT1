### Title
Token Exchange trusts an unvalidated JWT `dest` claim as the OAuth request host, unlike every other credential-bearing flow in the gem - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the OAuth token-exchange request host directly from the session token's `dest` claim without passing it through `Utils::ShopValidator`, while every sibling flow that sends the app's `client_secret` (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, and the authorization-code callback's HMAC-bound `shop` param) does validate/derive the host from a trusted source.

### Finding Description
`JwtPayload#shop` returns the raw `dest` claim with only the `https://` prefix stripped, with no check that it is a `*.myshopify.com`/trusted Shopify domain: [1](#0-0) 

`JwtPayload.new` verifies the JWT signature and only checks `aud == Context.api_key`; it never validates `dest` against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) 

`TokenExchange.exchange_token` takes this unvalidated `dest_shop` and uses it directly to build the `Session` whose `shop` becomes the request host, then sends `client_id`/`client_secret` to that host: [3](#0-2) 

`Clients::HttpClient` builds `@base_uri` straight from `session.shop`: [4](#0-3) 

Contrast this with the two other flows in the same file/module that also ship `client_secret` in the body — both explicitly sanitize the shop first: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: **host that receives `client_secret` == a Shopify-trusted domain (`Utils::ShopValidator`-approved)**. In `exchange_token`, the host instead equals **whatever string is in the JWT's `dest` claim**, an equality the gem enforces nowhere for this specific method.

### Impact Explanation
If the equality is broken — i.e., a session token can carry a `dest` claim that is not a genuine Shopify shop domain — the gem will POST the app's `client_id` and `client_secret` (an SSRF carrying the app's credentials) to that attacker-influenced host. This matches the "High - SSRF with the app's credentials" impact category.

### Likelihood Explanation
The severity of this is capped by the fact that `dest` sits inside a JWT that must verify against `Context.api_secret_key` via HS256 (`JwtPayload#decode_token`), a secret known only to Shopify and the app owner. I could not find, within this gem's code, any mechanism by which an unprivileged internet user — without already possessing the app's `api_secret_key` — could get a validly-signed token whose `dest` claim differs from the legitimate shop domain that Shopify itself assigns when it mints session tokens for an installed app. Shopify's own token-issuance behavior (which sets `dest` to the shop's real domain) is outside this gem's code, so I cannot confirm from the library's contents alone whether `dest` can ever diverge from a trusted domain in a token that still verifies. Because exploitation appears to require either control over `api_secret_key` (explicitly out of scope per the rules) or a gap in Shopify's own token issuance (unverifiable from this repository), I cannot elevate this beyond a code-quality/defense-in-depth gap: the missing `ShopValidator.sanitize!` call is a real inconsistency with the rest of the module, but I found no reachable exploitation path using only capabilities available to an unauthenticated/unprivileged internet user and this gem's own logic.

### Recommendation
For defense-in-depth and consistency with `client_credentials.rb` and `migrate_to_expiring_token`, run `dest_shop` through `Utils::ShopValidator.sanitize!` (or an equivalent allow-list check against `TRUSTED_SHOPIFY_DOMAINS`) inside `TokenExchange.exchange_token` before using it to construct the request host, so the binding "host receiving `client_secret` == trusted Shopify domain" is enforced uniformly across all OAuth flows regardless of any future issuance-side assumptions.

### Proof of Concept
Not applicable — no proof-of-concept exploit could be constructed strictly within this gem's code without assuming access to `api_secret_key` or an unverified gap in Shopify's own token-issuance validation of the `dest` claim, both of which are out of scope per the rules.
