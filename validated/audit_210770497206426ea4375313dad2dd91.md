### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant shop-domain spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw body only, never to the `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (parsed straight from that unauthenticated header) as the tenant identity dispatched to the app's webhook handler.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`, and for webhook requests that method is defined as: [1](#0-0) 
Meanwhile `shop` is read independently from a header that is not part of the signed material: [2](#0-1) 
`Registry.process` only checks the HMAC against the body, then forwards the unauthenticated `shop` value to the handler: [3](#0-2) 
Because the signature is `HMAC(secret, body)` and does not depend on the `shop-domain` header, any actor capable of delivering an HTTP request to the app's webhook endpoint (e.g. one who intercepts or is otherwise able to resend a previously-observed legitimate webhook body+HMAC pair — such as via logs, a shared proxy, or any channel where a valid webhook delivery is observable) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header. The HMAC check in `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-22) still succeeds because it never inspects the header, so `Registry.process` accepts the forged tenant identity and calls the host application's handler with `shop: request.shop` bound to the attacker-chosen value instead of the shop that produced the signed body. This breaks the equality that the library implicitly promises to handler authors: `shop-domain header == shop that produced the signed body`.

### Impact Explanation
Handlers are documented to trust `data.shop` from `WebhookMetadata` to select which merchant/tenant record the webhook body should be applied to (see docs/BREAKING_CHANGES_FOR_V15.md's webhook handler examples). Because the gem does not bind `shop` into the signature, an attacker who can obtain one valid (body, HMAC) pair for any shop can cause the host application to process that payload under a different, victim shop's tenant context — a cross-tenant data-confusion/write primitive attributable to this gem's own signature-construction choice, not a documented API misuse by the host app.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid raw body + HMAC pair (e.g. from webhook logs, a shared debugging proxy, or a delivery they can observe) and the ability to POST to the app's webhook endpoint with a modified `shop-domain` header — no possession of `api_secret_key` or an access token is needed, since the header is entirely outside the signed material. This is a moderate-likelihood, credential-free bypass of the tenant-binding guarantee webhook consumers rely on.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in the material that is HMAC-verified, or otherwise cryptographically bind them to the payload, so that `Registry.process` cannot be fed a mismatched shop identity for a validly-signed body.

### Proof of Concept
```ruby
# Attacker captures one legitimate webhook delivery for shop-a.myshopify.com:
raw_body = '{"id":1,"note":"legit order"}'
valid_hmac_header = "<base64 hmac captured from a real delivery>"

# Attacker replays it, claiming it is from a different (victim) shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header, # unchanged - still valid, HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body against the HMAC.
# The handler now receives WebhookMetadata with shop: "victim-shop.myshopify.com",
# even though the signed body never originated from that shop.
```
