### Title
Webhook `shop` and `topic` are trusted from HTTP headers without HMAC coverage, allowing forged webhook shop/topic values with a stolen/replayed HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC signature over the raw request body only, but the `shop` and `topic` values that the host application acts on (routing the webhook, attributing it to a tenant, looking up per-shop credentials) are read directly from unauthenticated HTTP headers, which are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string`: [2](#0-1) 

Yet `Request#shop` and `Request#topic` — the fields consumers use to determine *which tenant* and *which event* the webhook belongs to — are pulled straight from the `shopify-shop-domain` / `shopify-topic` headers, with no binding to the HMAC at all: [3](#0-2) 

Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, where `shop` is explicitly part of the signed parameter set: [4](#0-3) 

For webhooks there is no equivalent binding — `shop` is "verified" only in the sense that the raw body's HMAC is valid, but the raw body and the `shop` header are two independent inputs. An identity binding equality that should hold is:
`HMAC(raw_body, secret) valid ⟺ shop_header == shop_that_produced(raw_body)`
This equality is never enforced; the gem authenticates only `raw_body` and silently trusts `shop_header` as if it too were authenticated.

### Impact Explanation
Any attacker who obtains one valid `(raw_body, hmac)` pair for their own shop (trivially available since they run their own store and can trigger any webhook to themselves) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. The gem's `Request#verify?`/`HmacValidator.validate` will report success because it only checks the body signature, and the host application will process the webhook attributing it to whatever shop domain the attacker chose in the header — a cross-tenant identity confusion. Any app that uses `Request#shop` to key its per-shop side effects (e.g., updating billing state, disabling a shop, deleting shop data) without independently confirming the shop against its own webhook subscription registry can be tricked into acting on the wrong tenant. This crosses the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's `Webhooks::Request` abstraction as the sole verification mechanism, since the vulnerable header-trust path (`shop`/`topic`) is the documented, intended way to consume verified webhook data — the gem gives no indication that `shop` is unauthenticated. An attacker needs only network access to the app's webhook endpoint and one legitimately-signed payload from their own store to mount the attack; no privileged credentials, `api_secret_key`, or access tokens are required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or minimally `shop`) in the signable string used for HMAC computation, or otherwise cryptographically bind these header values to the request before exposing them via `Request#shop`/`Request#topic`. Alternatively, document explicitly that `shop`/`topic` are unauthenticated and must be revalidated by the host app against its own webhook subscription records before being trusted, and consider raising if the header-derived `shop` doesn't match an expected/registered shop.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers any subscribed webhook (e.g., `orders/create`), capturing the raw POST body and the genuine `X-Shopify-Hmac-Sha256` header — both correctly signed by Shopify with the app's real secret.
2. Attacker replays this exact `(body, hmac)` pair to the app's webhook endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally `X-Shopify-Topic` to a different event name).
3. The host app constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls the HMAC validator:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because it only checks raw_body
request.shop  # => "victim.myshopify.com" (attacker-controlled, unauthenticated)
request.topic # => attacker-controlled, unauthenticated
```
4. `HmacValidator.validate` returns `true` per [5](#0-4)  because the signature check only covers `@raw_body`, and the host app — trusting the gem's "verified" `Request` object — processes the event as belonging to `victim.myshopify.com`, even though nothing in the HMAC ties the body to that shop domain.
