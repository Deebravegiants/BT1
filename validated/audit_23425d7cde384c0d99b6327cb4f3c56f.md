Confirmed: the `shop` field passed to the handler is taken directly from the `x-shopify-shop-domain` header and is not covered by the HMAC signature, since the signature only covers the raw body.### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` value that is subsequently handed to the app's handler as the authenticated tenant identifier comes from an HTTP header that is **not** included in the signed material. Because the webhook secret (`Context.api_secret_key`) is the app-level `client_secret` shared by every shop that installs the app, any shop that can trigger a webhook to itself possesses a valid `(body, hmac)` pair that will pass verification for *any* shop-domain header, breaking the identity binding between "body whose signature was verified" and "shop asserted to the handler."

### Finding Description
The `Request#to_signable_string` method used for HMAC verification returns only the raw body: [1](#0-0) 

`shop` (and `topic`, `api_version`, `webhook_id`) are read directly from attacker-controllable HTTP headers and are never part of the signed data: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only compares the computed HMAC of `to_signable_string` (the raw body) against the received signature — it has no knowledge of, and does not bind, the `shop` header: [4](#0-3) 

`Registry.process` then trusts the header-derived `request.shop` as the authenticated tenant identifier once HMAC validation of the body succeeds, and forwards it to the application's handler unmodified: [5](#0-4) 

`WebhookMetadata.shop` is documented as the trusted "shop domain of the webhook" that the app is expected to use for per-tenant data routing/storage: [6](#0-5) [7](#0-6) 

The identity binding that should hold is:
`shop that produced the HMAC-authenticated body == shop delivered to the handler`

Because `api_secret_key` (the value used to compute the HMAC, see `Context.api_secret_key` usage in `HmacValidator.validate_signature`) is a single per-app secret shared across every installed shop — not a per-shop secret — a `(body, hmac)` pair valid for shop A's webhook is *equally valid* for any other value placed in the `shop` header, since the header plays no role in signature computation or verification. An attacker who installs the app on their own shop (an "unprivileged internet user" relative to other tenants of the app) can:
1. Trigger a webhook delivery to their own shop and capture the raw body and its valid `X-Shopify-Hmac-Sha256` value.
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` with a victim shop's domain.
3. `HmacValidator.validate` succeeds (body+hmac are cryptographically valid), and `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-chosen `body`/`topic`.

### Impact Explanation
This crosses a tenant boundary using only the gem's documented, verified webhook data: the host application, following the documented pattern of keying storage/processing by `data.shop`, will attribute attacker-controlled body content and topic to a shop it does not belong to. This is a cross-tenant data-injection/spoofing primitive achievable without any credentials beyond installing the app as any tenant, satisfying the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Any shop that installs the app can obtain a valid `(body, hmac)` pair for at least one topic (e.g., by causing an order/product update on their own store) since the shared app secret is identical across shops. Replaying it with a forged `X-Shopify-Shop-Domain` header requires no special access — HTTP headers on the webhook POST are fully attacker-controlled at the network layer once an attacker can reach the app's public webhook endpoint. Likelihood is high given the trivial exploitation path and reliance purely on the gem's documented API surface.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the value that is cryptographically authenticated before trusting it, e.g.:
- Include the shop domain (and other identifying headers) in the string that is HMAC-verified, or
- Independently verify that the `shop` header value corresponds to a shop with an active, previously-established session/installation before allowing the webhook to be dispatched to per-shop storage, and reject/flag any mismatch between the shop the webhook was registered under (if resolvable) and the shop header presented at delivery time.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook delivery, capturing:
raw_body = '{"id":123,"malicious":"payload"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)
# (attacker can get this pair for real by triggering the event on their own store)

# Attacker replays the exact same body/hmac pair, but forges the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes signature verification because only raw_body is checked:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...))
```
The handler receives attacker-controlled `body` attributed to `victim-shop.myshopify.com`, despite `victim-shop` never having produced or authorized this webhook.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
