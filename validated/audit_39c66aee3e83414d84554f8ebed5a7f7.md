## Title
Unchecked multiplication in `Bank::calculate_reward_and_burn_fee_details` can panic/overflow when computing the per-slot fee burn - (File: `runtime/src/bank/fee_distribution.rs`)

### Summary
`Bank::calculate_reward_and_burn_fee_details` computes the amount of the slot's accumulated transaction fee to burn using a raw, non-checked expression:

```rust
let burn = fee_details.transaction_fee * self.burn_percent() / 100;
``` [1](#0-0) 

This mirrors the reported bug class: code was written assuming a particular arithmetic overflow behavior (implicit wraparound / "it will never overflow in practice") without protecting the operation with checked/saturating arithmetic, the same class of issue flagged for Solidity's `TickMath` relying on undefined-but-relied-upon overflow semantics across compiler versions.

### Finding Description
`fee_details.transaction_fee` is `CollectorFeeDetails::transaction_fee`, which is accumulated slot-wide via `saturating_add` every time a batch of transactions is processed:

```rust
pub(crate) fn accumulate(&mut self, fee_details: &FeeDetails) {
    self.transaction_fee = self.transaction_fee.saturating_add(fee_details.transaction_fee());
    ...
}
``` [2](#0-1) 

Because `saturating_add` is used at the accumulation site, `transaction_fee` is explicitly allowed to reach `u64::MAX` over the course of a slot (e.g., under adversarial fee-flooding or extreme fee-market conditions). When `distribute_transaction_fee_details` is later called at the end of the slot:

```rust
pub(super) fn distribute_transaction_fee_details(&self) {
    let fee_details = self.collector_fee_details.read().unwrap();
    let FeeDistribution { deposit, burn } =
        self.calculate_reward_and_burn_fee_details(&fee_details);
    ...
}
``` [3](#0-2) 

it invokes `calculate_reward_and_burn_fee_details`, whose `transaction_fee * self.burn_percent()` step uses a plain `*` operator rather than `checked_mul`/`saturating_mul` [4](#0-3) . `burn_percent()` returns `DEFAULT_BURN_PERCENT` (50) [5](#0-4) . Any `transaction_fee` value greater than `u64::MAX / 50` (~3.68×10^17 lamports) will overflow the multiplication.

The rest of the function (`saturating_add`, `saturating_sub`) demonstrates the developers were clearly aware that saturating arithmetic is required in this exact function, yet the burn computation on the preceding line was left as raw arithmetic — an inconsistency of the same nature as the report: some operations in a compilation unit were updated to be overflow-safe, while a sibling operation implicitly depends on arithmetic never overflowing.

The build-time consequence depends on whether `overflow-checks` is enabled for the compiled binary:
- If compiled with `overflow-checks = true` (debug builds, or any release profile that opts in — many validator/consensus-critical crates enable this for exactly the reason of catching silent corruption), this line will **panic**, crashing/halting the validator process inside bank-freezing logic that runs on every leader slot.
- If compiled with the default release profile (`overflow-checks = false`), the multiplication silently **wraps**, producing an incorrect (and potentially tiny or zero) `burn` value that is then used to update `self.capitalization` via `fetch_sub` — corrupting the ledger's tracked total token supply relative to the true, intended burn amount.

I was not able to determine from indexed sources whether the workspace `Cargo.toml` sets `overflow-checks = true` for the production release profile (the profile section was found but its exact settings for `overflow-checks` were not returned by the tool). This is a limiting factor for pinpointing whether panic-on-overflow or silent-wraparound is the operative outcome in mainnet-validator builds; either outcome is a valid, concrete impact (halt vs. capitalization corruption).

### Impact Explanation
- If overflow-checks are active in the build: an attacker who can drive a single slot's summed `transaction_fee` above `u64::MAX / 50` can trigger a panic in bank freezing/fee-distribution logic, which is invoked once per slot for every validator — a straightforward remote/economic-inducible **liveness/halt** vector affecting the whole cluster (not merely a single node), since every validator processing/replaying that slot hits the same code path and panics identically.
- If overflow-checks are inactive: the wraparound silently produces a wrong `burn` amount, which is subtracted from `self.capitalization` [6](#0-5) , permanently corrupting the tracked total supply relative to what should have been burned — an undeclared/incorrect value creation-or-destruction bug in bank commit accounting.

Reaching `u64::MAX / 50` in real economic terms requires an extraordinarily large sum of same-slot transaction fees (lamports), which is a high bar under today's fee markets, but is not bounded by any code-level cap — `compute_unit_price` can be `u64::MAX` and `get_prioritization_fee` explicitly clamps only the price*limit product, not the aggregate slot sum [7](#0-6) , so the potential for a large aggregate exists as fee markets or compute limits evolve.

### Likelihood Explanation
Medium-to-low likelihood under current fee levels (requires an astronomically large aggregate slot fee, ~3.68×10^17 lamports, i.e., hundreds of millions of SOL-equivalent in fees within one slot), but the code path itself is on every slot-freeze / fee-distribution call, and there's no defensive check preventing the theoretical trigger as compute/fee-market parameters change over time (e.g., raised `MAX_COMPUTE_UNIT_LIMIT`, fee bump proposals, or future fee-market SIMDs). The asymmetry between this line and its neighboring `saturating_add`/`saturating_sub` calls suggests it was simply missed when the function was hardened, exactly analogous to the original TickMath report where most operations were adjusted but one was not.

### Recommendation
Replace the raw multiplication/division in `calculate_reward_and_burn_fee_details` with checked or saturating arithmetic consistent with the rest of the function, e.g.:
```rust
let burn = fee_details.transaction_fee.saturating_mul(self.burn_percent()) / 100;
```
or use `checked_mul`/`checked_div` and fail closed (clamp to `transaction_fee`) to guarantee the burn can never exceed the collected fee regardless of build profile.

### Proof of Concept
Not independently reproducible from static analysis alone; the existing unit test `test_distribute_transaction_fee_details_overflow_failure` demonstrates the codebase already anticipates overflow scenarios for the *deposit* side (`u64::MAX` account balance) [8](#0-7) , but no analogous test exists for `transaction_fee` values near `u64::MAX` exercising the `burn` multiplication itself — confirming this specific arithmetic path is untested for overflow.
