Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content as only the raw request body [1](#0-0) , while `topic`, `shop`, `api_version`, and `webhook_id` are all read verbatim from HTTP headers that are never included in the HMAC computation [2](#0-1) . `Registry.process` validates only the HMAC over the body and then trusts `request.topic` and `request.shop` to dispatch the handler and construct `WebhookMetadata`, without any cross-check binding those header values to the signed payload [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac(secret, raw_body) == received_hmac` AND `shop header == shop that produced this exact (topic, body) pair`. In this gem, `HmacValidator.validate` only proves the first equality — it proves the raw body was signed by an entity holding `Context.api_secret_key` (Shopify itself) [4](#0-3) . It says nothing about which shop, topic, api_version, or webhook_id that body was originally delivered for, because those fields are excluded from `to_signable_string` [1](#0-0) .

Since the shared secret used to sign webhooks (the app's `client_secret`) is common to *all* shops that install the app, any merchant who legitimately installs the app receives real, validly-HMAC-signed `(headers, body)` pairs from Shopify for their own store. Because the header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) are not bound to the HMAC, a merchant/attacker who controls the HTTP request reaching the app's webhook endpoint (e.g., by replaying the request through a proxy they control, or by directly POSTing to the app's public webhook URL) can take a validly-signed body from their own shop and swap in a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `Utils::HmacValidator.validate(request)` will still return `true` because it only re-derives the HMAC from `@raw_body` [5](#0-4) , and `Registry.process` will happily route the forged request to the topic's handler, attributing the payload to the spoofed shop [6](#0-5) .

This breaks the equality: `shop that Shopify actually generated this webhook body for == shop the handler believes it received data from`. The attacker fully controls the right-hand side while the left-hand side remains fixed to their own (attacker-owned) store's data, letting them inject data or trigger side effects (e.g., `orders/create`, `app/uninstalled`, GDPR handlers) under an arbitrary victim shop's identity in the host application.

### Impact Explanation
This is a cross-tenant confusion: an unprivileged internet user who is merely a legitimate installer of the target app on their own store can forge webhook events that the host application will process as if they came from a different, victim shop. Depending on how the host app's `WebhookHandler` uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, trigger `app/uninstalled` cleanup, or fulfill GDPR `customers/redact`/`shop/redact` requests), this can lead to cross-tenant data corruption or triggering privileged per-shop actions for a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to already be an installer of the target app on some shop (unprivileged, not requiring `api_secret_key`, an access token, or social engineering) and the ability to intercept/replay their own inbound webhook HTTP request with a modified header before it reaches the app's endpoint (e.g., via a local proxy, since the endpoint is a normal internet-facing HTTP listener). No knowledge of the app secret is needed since the attacker reuses a genuinely Shopify-issued `(body, hmac)` pair. This makes the likelihood realistic for any host app that trusts `WebhookMetadata#shop`/`#topic` for authorization-sensitive logic.

### Recommendation
Bind the `shop`, `topic`, `api_version`, and `webhook_id` headers into the HMAC-verified signable content (or otherwise cryptographically bind them, e.g., by validating `shop` against the session/shop that is expected to receive this specific webhook subscription), so that `Utils::HmacValidator.validate` fails if any of these header values are altered relative to what Shopify originally signed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and headers including `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker intercepts this outbound-from-Shopify request before it's processed by the app (e.g. runs the app behind a proxy they control) and rewrites the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or `X-Shopify-Topic`), leaving body `B` and `X-Shopify-Hmac-Sha256: H` untouched.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` then `Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only [1](#0-0)  — validation succeeds despite the spoofed shop header.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the host app to process attacker-controlled data under the victim shop's identity.
