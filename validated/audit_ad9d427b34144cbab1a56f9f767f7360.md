### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature to the raw request body only, while the `shop` (tenant) identity used by `ShopifyAPI::Webhooks::Registry.process` is read from an unauthenticated HTTP header that the HMAC never covers. This breaks the equality `shop_authenticated_by_hmac == shop_used_by_handler`, allowing a request with a genuine HMAC (computed on a body the attacker legitimately obtained) to be replayed with a forged `shop-domain` header claiming to originate from a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop` is derived from a separate, unsigned header: [3](#0-2) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the body) against the HMAC, never touching `shop`: [4](#0-3) 

`Registry.process` accepts the request once the body HMAC passes, then trusts `request.shop` as the tenant identity handed to the app's handler, with no additional binding between the verified body and the claimed shop: [5](#0-4) 

Because the same `api_secret_key` is shared across all shops installed on a multi-tenant app, an attacker who controls their own shop can install the app, receive a genuinely Shopify-signed webhook for their own store (valid HMAC over that body), and then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will dispatch to the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application a `shop` value it did not actually authenticate, while presenting it as verified ("the HMAC passed"). Any app logic that uses `WebhookMetadata#shop` to select which merchant's session/data to update (a common and encouraged pattern) can be tricked into acting on behalf of, or writing data attributed to, a shop the attacker does not control — a cross-tenant access primitive.

### Likelihood Explanation
High likelihood: the attacker only needs to be a legitimate (unprivileged) merchant who installs the app to obtain one authentic signed webhook payload from Shopify for their own store. No `api_secret_key`, access token, or privileged access is required — only the ability to intercept/replay their own store's webhook HTTP call with a modified header, which is trivial for anyone controlling the receiving path or a proxy in front of it.

### Recommendation
Include the tenant-identifying fields (at minimum `shop-domain`, ideally `topic` and `webhook-id` as well) in the signable string that `Utils::HmacValidator` verifies, rather than signing the raw body alone. Alternatively, bind `shop` cryptographically to the payload (e.g., require it to appear in the JSON body, or derive the trusted shop by parsing it from a signed claim rather than a bare header) so `to_signable_string` in `Webhooks::Request` cannot diverge from the `shop` exposed via `Webhooks::Request#shop`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic, capturing the genuine request Shopify sends: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact request to the app's webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) and `Utils::HmacValidator.validate` returns `true` because it only recomputes the HMAC over `B`, which is unchanged.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
