### Title
Passphrase cache TTL/expiry bypass via un-reset `inactiveAt` timestamp on re-caching - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
`PassphraseCache.set()` writes a fresh `addedAt`/`ttl` pair whenever a passphrase is (re-)cached but never clears the previously-written `inactiveAt` timestamp. `get()` gives `inactiveAt` priority over `addedAt`, so a stale `inactiveAt` value from an earlier caching session can be combined with a fresh (and unclamped) `ttl` to keep returning the decrypted wallet passphrase well past the intended `maxTtl` cap. This is the same bug class as the Venus Prime.sol issue: a timestamp used to gate a security-relevant time window is not reset when the object it belongs to is re-issued/re-granted through an alternate code path, letting old state satisfy a check it should not be able to satisfy.

### Finding Description
`PassphraseCache` caches the user's decrypted wallet passphrase in local storage so the wallet can auto-unlock without re-prompting, subject to an inactivity timer (`ttl`) and an absolute cap (`maxTtl`): [1](#0-0) 

`set()` always overwrites `PASSPHRASE_KEY`, `ADDED_AT_KEY`, and `TTL_KEY`, but it does **not** delete/reset `INACTIVE_AT_KEY`. If a passphrase was cached previously and the app called `scheduleClear()` (which stamps `INACTIVE_AT_KEY = Date.now()` when the app becomes inactive/backgrounded): [2](#0-1) 

...and then the user unlocks again (calling `set()` with a fresh passphrase/`addedAt` without the intervening `clear()` having wiped storage), the old `inactiveAt` value from the *previous* session survives in storage alongside the *new* `addedAt`/`ttl`.

`get()` then evaluates expiry using whichever branch is reached first: [3](#0-2) 

Because `inactiveAt` is truthy (stale), the `addedAt + maxTtl` absolute-cap check (the security backstop, analogous to `STAKING_PERIOD` in the Venus report) is **skipped entirely**, and the decision is instead based on `inactiveAt + ttl`. Critically, the `ttl` value written in `set()` comes straight from `#getTtl()` (`autoLockTimerAtom.get()`) and is **not clamped** to `#maxTtl` — clamping (`Math.min(this.#maxTtl, ttl)`) only happens in the separate `changeTtl()` method: [4](#0-3) [5](#0-4) 

So if `autoLockTimerAtom` ever holds/returns a value larger than `maxTtl` (e.g., it was set directly, or via a path other than `changeTtl()`), a subsequent `set()` will persist that oversized `ttl`, and a leftover `inactiveAt` from a prior background/inactive period will let `get()` keep returning the plaintext passphrase for `inactiveAt + ttl`, which can exceed the operator-configured `maxTtl` window — the exact same "stale state variable not reset on re-grant, defeating the time-based gate" pattern as the `stakedAt` bug in Prime.sol's `issue()`.

### Impact Explanation
`PassphraseCache` stores the plaintext master passphrase used to decrypt the wallet and authorize signing. The `maxTtl` value is the hard security ceiling meant to force periodic re-authentication. Bypassing that ceiling via a leftover `inactiveAt` extends the window in which the app will silently hand back the decryption secret without prompting the user — a direct wallet-compromise / secret-disclosure risk if the device is later accessed by someone other than the owner (lost/stolen/borrowed device, malicious co-installed app reading local storage on a compromised OS, etc.), all within the "encrypted storage / auth" trust boundary of the SDK.

### Likelihood Explanation
The stale-`inactiveAt`-survives-`set()` condition is deterministic and requires no privileged access — it occurs through normal app usage (background → `scheduleClear()` stamps `inactiveAt` → foreground/unlock again before the alarm fires → `set()` called without an intervening `clear()`). I was not able to fully confirm from the available context whether every real unlock path always calls `clear()` (which wipes all keys via `#storage.clear()`) before `set()`, nor whether `autoLockTimerAtom` can actually be persisted with a value greater than `maxTtl` outside of `changeTtl()`; both would materially affect real-world exploitability and I could not verify them with the tools available (index size limits meant I could not inspect all call sites, e.g. `application.ts`, `auto-lock-timer.js` atom validation, in full). This should be verified with a full checkout of the repository.

### Recommendation
- In `PassphraseCache.set()`, explicitly delete/reset `INACTIVE_AT_KEY` whenever a new passphrase is cached, mirroring how `stakedAt` should have been reset in Prime.sol's `issue()`.
- Always clamp `ttl` to `#maxTtl` at the point it is persisted in `set()` (not only in `changeTtl()`), and re-validate the absolute `addedAt + maxTtl` cap in `get()` even when `inactiveAt` is present, so the inactivity-based check can only ever *shorten*, never *extend*, the cache lifetime beyond `maxTtl`.

### Proof of Concept
Conceptual reproduction against `PassphraseCache` (features/application/src/modules/passphrase-cache.ts):
1. Call `passphraseCache.set(passphrase)` → stores `addedAt = T0`, `ttl = T_normal`.
2. Simulate app backgrounding: call `passphraseCache.scheduleClear()` → stores `inactiveAt = T1` (T1 > T0).
3. Before the scheduled alarm fires, simulate the app foregrounding/re-unlocking and call `passphraseCache.set(newPassphrase)` again (without any `clear()` in between) — note `INACTIVE_AT_KEY` is never touched by `set()`, so `inactiveAt = T1` remains in storage while `addedAt` is refreshed to `T2` and `ttl` is refreshed to whatever `autoLockTimerAtom.get()` currently returns (uncapped).
4. Advance time past `T2 + maxTtl` (the intended absolute cutoff) but keep it below `T1 + ttl`.
5. Call `passphraseCache.get()` — because `inactiveAt` is still truthy, the code takes the `inactiveAt + ttl > Date.now()` branch and returns the plaintext passphrase, even though the `addedAt + maxTtl` cap has already been exceeded.

This confirms the `maxTtl` security ceiling can be bypassed purely because `inactiveAt` is never reset by `set()`, directly mirroring the root cause of the referenced Prime.sol finding.

  async get() {
    const [passphrase, addedAt, inactiveAt, ttl] = (await this.#storage.batchGet([
      PASSPHRASE_KEY,
      ADDED_AT_KEY,
      INACTIVE_AT_KEY,
      TTL_KEY,
    ])) as [string, number, number, number]

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

      this.#logger.log('fetched expired passphrase, clearing and preventing unlock')
      void this.clear()
    }

    this.#logger.log('passphrase not in cache')
  }

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(TTL_KEY, newTtl)

      void this.#scheduleClear()
    }
  }
