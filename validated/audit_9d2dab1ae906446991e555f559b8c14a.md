### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `Registry#process` proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers of the request — only that the body bytes match a signature computed with the app's secret. Those headers are nevertheless treated as authenticated facts: `topic` selects the handler, and `shop` is forwarded to the handler as the identity of the tenant that produced the payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` is read from the `hmac-sha256` header, and the value that is HMAC-verified is defined by: [1](#0-0) 

which is just `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from headers that are not part of `to_signable_string`: [2](#0-1) 

`Registry#process` validates the HMAC and then trusts `request.topic` to pick the handler and `request.shop` as the tenant identity passed into the handler's `WebhookMetadata`: [3](#0-2) 

The equality this breaks: the gem implicitly assumes `signed_body == (shop_header, topic_header, body)`, but it only ever verifies `signed_body == body`. `shop` (and `topic`) are fields "acted on" by `Registry#process` (tenant identity, dispatch key) that are not covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
An unprivileged internet user who can reach the app's public webhook endpoint (this is a normal internet-facing HTTP route the host app exposes, not a privileged channel) and who has obtained one legitimate `(body, hmac)` pair for any topic — e.g. by triggering a real webhook delivery to their own store, which they are fully entitled to do as a merchant/dev-store owner — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`) header value. `HmacValidator.validate` will still succeed because it only recomputes the signature over `@raw_body`: [4](#0-3) 

The handler then executes with `WebhookMetadata#shop` set to the attacker-chosen shop domain, causing the application to attribute another tenant's data/event to the attacker's chosen shop (or to dispatch to a different handler than the one Shopify actually intended for that payload). This is a cross-tenant identity-binding break in the gem's own webhook-processing code, not a misuse of the documented API by the host app — the host is expected to call exactly `Registry.process(request)` as designed.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus one legitimate webhook capture — both attainable by an unprivileged party who installs/uses the app on their own store (no `api_secret_key`, no access token, no privileged account needed). No cryptographic material needs to be forged; the existing valid signature is reused verbatim.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable content used for HMAC verification (or otherwise cryptographically bind them to the body before trusting them), so that `Registry#process` cannot be fed a genuine signature paired with attacker-controlled routing/tenant metadata.

### Proof of Concept
1. As a legitimate (unprivileged) app user, install the app on `attacker-shop.myshopify.com` and trigger any webhook (e.g. `orders/create`) to capture the real HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `shop`/`topic`; `Registry#process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `@raw_body` and matches `H`, so validation passes.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` even though `victim-shop` never sent this payload.
