### Title
Webhook HMAC verification does not bind the shop identity to the signed payload, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the shop identity used by the handler comes from a separate, unauthenticated header. Because the app's `api_secret_key` is shared across every shop that installs the app, a legitimately signed `(body, hmac)` pair obtained from one shop's own webhook traffic remains valid when replayed with a different shop's domain in the `X-Shopify-Shop-Domain` header, letting an attacker who controls one tenant inject spoofed webhook events attributed to another tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is read from a completely separate header that is never included in the HMAC computation: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC using exactly `to_signable_string` (the body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once HMAC validation passes on the body, then dispatches the handler using `request.shop`, the unauthenticated header value, without any check that it corresponds to the shop that actually produced the signed content: [4](#0-3) 

The equality broken is: `shop authenticated by HMAC (none, since shop is excluded from to_signable_string)` ≠ `shop used as the tenant/session key for dispatch (request.shop, the raw header)`. Because `api_secret_key` is one value per app shared by all installed shops, any shop that has installed the app can generate its own legitimately-signed `(body, hmac)` pairs (e.g., by triggering a webhook-producing action on its own store) and then replay that exact body+hmac to the app's webhook endpoint with the `shop-domain` header swapped to a victim tenant. The signature still validates because it never covered the shop field.

### Impact Explanation
This crosses a tenant boundary: an attacker who is merely one authorized installer of the app (an "unprivileged" actor relative to other merchants) can cause the app's own webhook-processing code to believe attacker-controlled data originated from a different shop. Depending on which webhook topics the host app registers, this can be used to inject or corrupt data under another merchant's identity (e.g., spoofing `shop/update`, `app/uninstalled`, or order/customer webhooks) purely by replaying a validly-signed payload with a forged shop header — a cross-tenant access impact.

### Likelihood Explanation
Any developer using the gem's documented `Registry.process` / `HmacValidator.validate` path exactly as designed is exposed, since the vulnerability is in the gem's own verification logic, not misuse by the host app. The only requirement is that the attacker has (or can obtain) installer access to the same app on their own shop, which is inherent to public app distribution and not a "privileged" credential.

### Recommendation
- Short term: include the shop domain (and ideally webhook id / topic) in the HMAC-covered content, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting `request.shop` in `Registry.process`.
- Long term: treat all Shopify-supplied identity headers as part of the trust boundary that must be covered by signature verification, and add regression tests asserting that HMAC validation fails when the shop header is altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal app installation, no special privilege).
2. Attacker performs an action on their own shop that triggers a registered webhook topic (e.g. updates shop settings), causing Shopify to POST a body `B` with a valid `X-Shopify-Hmac-Sha256` header `H` (computed with the app's shared `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H`, then sends a new POST to the app's webhook endpoint with the same `B`/`H` but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (called from `Registry.process`) passes because it only checks `B` against `H`; `Registry.process` then invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, spoofing a webhook event under the victim's tenant identity.
