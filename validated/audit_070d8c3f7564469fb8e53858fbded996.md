## Title
Webhook `shop` domain (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC against that body alone. The `shop`, `topic`, and `webhook_id` values are read directly from unauthenticated HTTP headers and are never part of the signed data, yet `Registry.process` treats a successful HMAC check as proof that the whole request — including which shop it came from — is authentic.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e. the raw body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` gates on that HMAC check, then forwards `request.shop` (and `request.topic`, `request.webhook_id`) as trusted identity fields to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop_domain_header == shop_that_actually_produced(raw_body)` is never checked — only `hmac_header == HMAC(api_secret_key, raw_body)` is checked, and the shop domain is not an input to that HMAC.

Because a single app has one `client_secret`/`api_secret_key` shared across every shop that installs it, an unprivileged internet user who installs the target app on a shop they control (a normal, unprivileged action) will legitimately receive real webhook deliveries with a valid `(raw_body, hmac)` pair signed with the app's real secret. That user can then replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the event came from the victim shop: [5](#0-4) 

This is the same class of bug as the referenced report: a piece of state that downstream logic depends on for correctness/authorization (`assets`/`depositedBase` there; `shop` here) is derived from data that was never actually covered by the authenticating check (`previewYield` incrementing unaccounted assets there; the unsigned `shop-domain` header here).

For comparison, the OAuth callback correctly includes `shop` inside the signed query string via `AuthQuery#to_signable_string`, showing that the webhook path is the outlier that fails to bind the tenant identifier to the signature.

### Impact Explanation
Any app built on this gem that trusts `WebhookMetadata#shop` (as the gem's own README/API surface encourages, since it is the only tenant identifier the gem exposes post-HMAC-validation) can be made to process attacker-controlled webhook bodies under an arbitrary victim shop's identity. Depending on the handler, this enables cross-tenant data corruption/impersonation (e.g., an app that syncs inventory, cancels orders, or updates billing state keyed by `shop` on webhook receipt can be tricked into applying the attacker's own shop's event data to a victim shop's records), which is a cross-tenant access violation.

### Likelihood Explanation
The prerequisite is only that the attacker be a legitimate, unprivileged merchant who installs the target app on their own store — a normal, unauthenticated-to-the-target-tenant action available to anyone. No access to the app's `client_secret`, access tokens, or victim credentials is required; only capturing one's own legitimately-received webhook HTTP request and replaying it with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is actually verified — e.g., include the `shopify-shop-domain` header value in `to_signable_string` (Shopify's real webhook HMAC is computed over the raw body only by design, so instead the gem should independently confirm the `shop` header corresponds to a session/shop the app actually has an active installation record for before trusting it), rather than exposing `request.shop` as an implicitly-authenticated field once `HmacValidator.validate` passes.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a genuine webhook delivery, e.g. `orders/create`, noting `raw_body` and the valid `x-shopify-hmac-sha256` value (computed by Shopify with the app's real, shared `api_secret_key`).
2. Replay the identical HTTP POST to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) passes because it only checks `raw_body` against the HMAC.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to act on attacker-supplied data attributed to the victim's tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
