## Title
Rounding drift in scaled `calc_pnl_x`/`calc_pnl_y` invariant tracking can permanently revert `Withdraw` via `CalcPnlError`, freezing LP funds - (File: `program/src/processor.rs`)

## Summary
The reported P2P bug class is: a fee/config value that is not properly bounded causes an internal balance check to underflow/fail permanently, so `withdraw`-style functions revert forever and funds become stuck. In `raydium-amm--009` the analogous mechanism is `Processor::calc_take_pnl`, which is invoked from both `process_deposit` and the LP `process_withdraw` path. It enforces a strict invariant check with no rounding tolerance; once tripped it returns `AmmError::CalcPnlError` unconditionally, and there is no unprivileged way to unstick it.

## Finding Description
`calc_take_pnl` requires the *actual* current pool value (in native, unscaled units) to be `>=` the previously recorded, decimal-scaled "last k" tracked in `TargetOrders.calc_pnl_x` / `calc_pnl_y`: [1](#0-0) 

If this comparison fails, the function immediately returns `AmmError::CalcPnlError`: [2](#0-1) 

`calc_pnl_x`/`calc_pnl_y` are updated on every deposit and withdraw using `normalize_decimal_v2` (floor-divides when converting native amounts into the shared `sys_decimal_value` scale) and `restore_decimal` (scales back up by multiplying then floor-dividing): [3](#0-2) 

Both `process_deposit` and `process_withdraw` compute the new `calc_pnl_x`/`calc_pnl_y` by adding/subtracting these floor-rounded, decimal-scaled quantities: [4](#0-3) [5](#0-4) 

Because `pc_decimals` and `coin_decimals` frequently differ across pools (e.g. a 6-decimal token paired with a 9-decimal token), each `normalize_decimal_v2`/`restore_decimal` round trip truncates fractional units. Over a sequence of ordinary, unprivileged deposits/withdraws performed by any LP, this truncation can accumulate such that the tracked `calc_pnl_x * calc_pnl_y` ends up larger, relative to the actual current vault balances, than the invariant check tolerates. When that happens, `calc_take_pnl` returns `CalcPnlError` for **every subsequent call**, and since `process_withdraw` calls it unconditionally whenever `amm.status != AmmStatus::WithdrawOnly`: [6](#0-5) 

...normal LP withdrawal becomes permanently unavailable to any unprivileged user. The only way to unblock withdrawals is for a privileged admin to flip the pool into `WithdrawOnly` status via `SetParams`, which is out of reach for a normal LP and is not an automatic recovery path.

## Impact Explanation
This is directly analogous to the reported issue: an unconditional, non-recoverable revert path guards fund movement, and normal usage (not attacker malice) can trip it, permanently freezing LP principal in the pool with no unprivileged recovery mechanism. This is a concrete freezing-of-funds condition reachable purely through the in-scope `Deposit`/`Withdraw` instructions.

## Likelihood Explanation
Likelihood scales with the number of deposit/withdraw cycles and the decimal mismatch between the pool's coin and pc mints; pools pairing tokens with different decimal counts accumulate truncation on every `normalize_decimal_v2`/`restore_decimal` round trip in `calc_take_pnl`'s callers, making the strict `>=` check increasingly fragile over the pool's lifetime rather than requiring any single crafted transaction.

## Recommendation
Replace the strict `>=` comparison in `calc_take_pnl` with a tolerance-based check (e.g., allow a small epsilon reflecting worst-case rounding loss from `normalize_decimal_v2`/`restore_decimal`), or recompute `calc_pnl_x`/`calc_pnl_y` using round-nearest/ceiling semantics consistently so the tracked invariant can never legitimately exceed actual reserves. Additionally, provide an unprivileged-safe fallback (e.g., clamp/resync the invariant instead of hard-reverting) so a single stuck state cannot permanently block `Withdraw`.

## Proof of Concept
1. Create a pool via `Initialize2` with mismatched decimals (e.g., coin_decimals = 9, pc_decimals = 6).
2. Repeatedly call `Deposit` and `Withdraw` (unprivileged, attacker/any LP controlled amounts) with amounts chosen to maximize floor-rounding loss in `normalize_decimal_v2`/`restore_decimal` on each cycle (see `program/src/processor.rs:1352-1371` and `program/src/math.rs:96-116`).
3. After enough cycles, the recorded `target_orders.calc_pnl_x * calc_pnl_y` product exceeds the actual `total_pc_without_take_pnl * total_coin_without_take_pnl`, so the check at `program/src/processor.rs:190-192` fails.
4. Any subsequent `Withdraw` call by any LP now unconditionally hits `program/src/processor.rs:267-278` and returns `CalcPnlError`, reverting the transaction and leaving all LP funds locked in the vaults until a privileged admin changes the AMM status.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {

        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();

        ret
