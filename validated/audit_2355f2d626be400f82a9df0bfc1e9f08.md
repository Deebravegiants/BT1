Audit Report

## Title
Missing `return` after failed OIDC email-claim extraction lets `handleTokenExchange` create an authenticated session with an unverified/empty email - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
In `oidcAuthenticator.handleTokenExchange`, the type assertion `email, ok := claims["email"].(string)` is checked, and on failure the handler logs an error and writes an HTTP 500 body via `c.String(...)`, but does not `return`. Execution falls through into role mapping and session creation using the zero-value empty `email`, resulting in a persisted `oidc_sessions` row with `user_email = ''`, a saved session cookie, and a final `200 {"success":true}` JSON response despite the earlier 500 write.

## Finding Description
The vulnerable code is confirmed exactly as described: [1](#0-0) 

Unlike every other error branch in the same function — which all correctly call `return` after writing an error response (e.g. lines 195, 203, 211, 218, 224, 244, 270) — the `!ok` branch for the email claim at lines 226-230 omits it. Execution continues to role mapping via `IDClaimsToUserRole` and then to session persistence: [2](#0-1)  and finally the cookie is saved and a success response returned: [3](#0-2) 

Downstream, `AuthorizedUserWithSession` trusts the `user_email`/`user_role` stored at session-creation time without re-deriving it, so any request presenting the resulting session cookie is authenticated as the empty-email user with the mapped role.

Note this path is reachable only after the ID token has already passed `oi.provider.Verifier(...).Verify(ctx, rawIDToken)` (signature/issuer verification) and `ExtractIDClaimValues` succeeded for role-mapping claims — it requires a token legitimately issued by the configured trusted OIDC provider that simply lacks a string `email` claim (a common, non-malicious scenario e.g. when the `email` scope isn't granted, or a directory-backed identity lacks an email attribute, while group/role claims are still present). This is not a case of forging arbitrary claims past signature verification.

## Impact Explanation
Any legitimately authenticating OIDC user whose ID token lacks a string `email` claim but satisfies the configured role-mapping group claims will still be granted a valid, cookie-backed Chainlink node session, persisted with `user_email = ''`. This breaks the invariant that every session maps to a real user identity, enabling audit-trail corruption and identity collision across such "ghost" empty-email sessions in `oidc_sessions`, consistent with the "cross-user response corruption" impact class for the node's authentication layer.

## Likelihood Explanation
The bug is deterministic and reachable via the public token-exchange endpoint with no prior node authentication; the only precondition is a legitimately-issued ID token that omits the `email` claim while still carrying claims sufficient for role mapping — a realistic OIDC configuration/identity edge case rather than a need to compromise or spoof the identity provider's signature.

## Recommendation
Add a `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call in the `!ok` branch at `core/sessions/oidcauth/oidc.go` lines 226-230, halting execution before role mapping and session persistence occur. Audit the function for any other response-write-without-return patterns (e.g. line 257-260's error branch also lacks `return` after the session-insert failure) and ensure every failure path halts before further session state is created.

## Proof of Concept
1. Configure the node with OIDC auth (`AdminClaim`/`EditClaim`/etc. role-mapping claims configured).
2. Have the configured, legitimately-trusted identity provider issue a valid, signature-verifiable ID token whose `email` claim is absent or non-string, but whose group claims satisfy `IDClaimsToUserRole`.
3. Complete the OAuth2 authorization-code exchange against the route wired to `handleTokenExchange`.
4. Observe: the handler logs "Failed to get email from claims", writes a 500 body, but continues to execute the `INSERT INTO oidc_sessions (... user_email='' ...)`, saves the session cookie via `ginSession.Save()`, and returns `200 {"success":true}`.
5. Use the returned session cookie against authenticated node API routes; it authenticates as `user_email = ""` with the mapped role, confirmed by `AuthorizedUserWithSession` reading `user_email`/`user_role` directly from the `oidc_sessions` row at `core/sessions/oidcauth/oidc.go` lines 349-391.
