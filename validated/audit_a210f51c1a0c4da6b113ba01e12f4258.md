### Title
Unvalidated `shop` Parameter in `Oauth.begin_auth` Enables Forced OAuth Completion / Session Fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization redirect URL directly from the caller-supplied `shop:` argument, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!` the way every other OAuth-adjacent entry point in this gem does. This mirrors the reported bug class: a value that identifies "which external target to act on" is used without the equality check ("is this shop a trusted Shopify domain?") that the same codebase enforces everywhere else, so the wrong external endpoint can be selected.

### Finding Description
`ShopValidator.sanitize!` exists specifically to ensure a `shop` string resolves to a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is used to build a URL: [1](#0-0) 

It is consistently applied before a `shop` value is used to construct a security-sensitive request in every other credential-issuing flow:
- `ClientCredentials.client_credentials`: [2](#0-1) 
- `RefreshToken.refresh_access_token`: [3](#0-2) 
- `TokenExchange.migrate_to_expiring_token`: [4](#0-3) 

However, `Oauth.begin_auth` — the very first, most attacker-reachable step of the standard Authorization Code Grant flow — takes `shop:` straight from the caller (typically a raw HTTP query/header parameter, as shown in the gem's own docs: `shop = request.headers["Shop"]`) and feeds it unchecked into the redirect target: [5](#0-4) [6](#0-5) 

`auth_base_uri(shop)` performs no domain validation — it simply prepends `https://` to whatever string is passed and appends `/admin`. This breaks the identity binding "the domain the user's browser is redirected to for authorization == a trusted `*.myshopify.com`/Shopify domain," which is exactly the equality `ShopValidator` was built to enforce elsewhere.

Because `begin_auth` also mints and stores the CSRF `state` nonce for that flow (`cookie = SessionCookie.new(value: state, ...)`), and `validate_auth_callback` later trusts whichever `shop` shows up in the signed callback to construct the resulting `Session` (`Auth::Session.new(shop: auth_query.shop)` / `Session.from(shop: auth_query.shop, ...)`), an attacker who controls a real, legitimately-owned Shopify store can cause a victim's browser to begin and complete a valid OAuth flow against the attacker's store instead of the shop the victim intended. The application ends up creating/persisting a `Session` bound to the attacker's shop under the victim's browser session/cookie — a forced OAuth completion / session-fixation primitive — because the library never confirmed that the `shop` used to drive the flow is the one the developer/user actually intended, only that it's *a* Shopify store.

### Impact Explanation
This matches the report's High-severity category: "session fixation or forced OAuth completion." An unprivileged internet user (an attacker who merely owns any Shopify test/dev store) can supply an arbitrary `shop` to `begin_auth` via a crafted link to the host application, hijacking the OAuth session/cookie state for a victim without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
`begin_auth`'s `shop` parameter is explicitly documented and demonstrated to come directly from an unauthenticated request header/query parameter, and no other layer of this gem performs the domain check before the redirect is built — unlike the three sibling flows that all call `ShopValidator.sanitize!`. Any host application that follows the gem's own documented usage pattern is exposed.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (and use the sanitized value for `auth_base_uri`), mirroring the pattern already used in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, so the redirect target is always confirmed to be a trusted Shopify domain before the OAuth flow begins.

### Proof of Concept
1. Host application implements the documented pattern:
   ```ruby
   def login
     shop = request.headers["Shop"] # or params[:shop]
     auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
     ...
   end
   ```
2. Attacker (who owns a legitimate store `attacker-store.myshopify.com`) sends the victim a link that causes the app to call `begin_auth(shop: "attacker-store.myshopify.com", ...)`.
3. `begin_auth` sets the CSRF `state` cookie on the victim's browser and redirects to `https://attacker-store.myshopify.com/admin/oauth/authorize?...` — a domain never validated against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.
4. The attacker (as the legitimate owner of that store) approves the OAuth consent screen; Shopify redirects back to the victim's browser with a validly-signed callback for `attacker-store.myshopify.com`.
5. `validate_auth_callback` succeeds (HMAC and state cookie both check out because they were both generated for this exact flow) and creates a `Session` for `attacker-store.myshopify.com`, which the host application now associates with the victim's authenticated browser/user context — completing a forced OAuth session-fixation against the victim.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
