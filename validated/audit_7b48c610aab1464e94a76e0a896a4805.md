### Title
Unprivileged stake-account mutation during epoch reward distribution can trigger a validator-crashing `assert_eq!`, halting reward distribution for all stakers - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
The `GiantMevAndFeesPool`/`GiantLP` finding shows that an unprivileged user can trigger a supposedly-privileged hook (an ERC20 `transfer`) that mutates shared reward-accounting state in a way that corrupts/locks rewards for *all* other participants. The closest reachable analog in Agave is in the partitioned epoch-reward distribution path, where a hard `assert_eq!` compares a stake account's *live* on-chain delegation (read from `StakesCache` at distribution time) against a value computed during the earlier *calculation* phase. If those two values diverge — which can happen because the stake account's delegation can be mutated by its own (unprivileged) owner between the calculation block and a later distribution block of the same epoch-reward interval — the assertion panics deterministically on every validator, aborting reward distribution for the remaining stake accounts in that partition/epoch.

### Finding Description
Reward distribution is split into two phases across many blocks: a single "calculation" block computes `PartitionedStakeReward` values (see `calculate_stake_rewards_and_commissions`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`), and then, over subsequent blocks, `distribute_partitioned_epoch_rewards` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:80`) applies those pre-computed rewards to the stake accounts as they currently exist in `StakesCache`. [1](#0-0) 

In `build_updated_stake_reward`, when the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is not active, the code asserts that the stake account's *current* `delegation.stake` (fetched live from `stakes_cache_accounts` at distribution time) plus the reward computed earlier equals the `new_stake.delegation.stake` value that was baked into `partitioned_stake_reward` during the calculation phase: [2](#0-1) 

The surrounding comment on `store_stake_accounts_in_partition` explicitly assumes this can never diverge: "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned." [3](#0-2) 

I was unable to locate any explicit check in the stake program (`programs/stake*`) that rejects stake-modifying instructions (e.g. deactivate, split, merge, redelegate, or a withdrawal that changes `Delegation::stake`) while `Bank::epoch_reward_status` is `Active`/`get_reward_interval() == InsideInterval`. The `RewardInterval`/`get_reward_interval()` gate exists only in `runtime/src/bank/partitioned_epoch_rewards/mod.rs` and is used by the bank/runtime itself, not surfaced as an instruction-level restriction enforced by the stake program against user transactions. Reward distribution can span many blocks (`get_reward_distribution_num_blocks`), so there is a real time window between when a stake account's reward is computed (calculation block) and when it is applied (a later distribution block), during which the stake account's own authority could submit ordinary stake instructions that change `delegation.stake`.

If such a divergence occurs and `adjust_delegations_for_rent` is false, the `assert_eq!` in `build_updated_stake_reward` panics. This function is called from `store_stake_accounts_in_partition`, which is called for every stake account in the partition, in turn invoked by `distribute_epoch_rewards_in_partition` from `distribute_partitioned_epoch_rewards`, all of which execute deterministically inside bank-freeze/commit for every validator processing that block. [4](#0-3) 

### Impact Explanation
A panic inside this deterministic bank-processing path is triggered identically on every validator replaying the same block, which is a consensus-halting condition rather than a mere logic bug — a stronger form of the original "rewards locked for all users" impact, because instead of merely blocking claims it can crash the network's block-processing for that slot, denying reward distribution to every other stake account still pending in that partition and any subsequent partitions of the same epoch's payout. This satisfies the "cross-node divergence or halt" acceptance criterion, assuming the divergence is actually reachable by an ordinary, unprivileged stake-account owner (see caveat below).

### Likelihood Explanation
Likelihood is **uncertain and not fully confirmed**. The comment in the code asserts that "further state mutation [is] prevent[ed] by stake-program restrictions," implying the Agave developers believe this scenario is already closed off (e.g., by disallowing stake mutations, or because subsequent code paths recompute/refresh state defensively). I could not find and verify the specific stake-program-side enforcement mechanism that prevents delegation-changing instructions from being processed for accounts with pending rewards mid-interval, nor could I rule out that `adjust_delegations_for_rent`/`relax_post_exec_min_balance_check` is already permanently active in production (which would make the vulnerable branch dead code). Given the reasoning-effort and search budget available, this should be treated as a **candidate finding requiring confirmation** of (a) whether stake-modifying instructions are actually blocked during an active reward interval, and (b) whether the `adjust_delegations_for_rent` feature is fully activated on mainnet (in which case the vulnerable `else` branch is unreachable in practice).

### Recommendation
- Confirm whether `relax_post_exec_min_balance_check` (`adjust_delegations_for_rent`) is fully activated on all live Agave clusters; if so, this `assert_eq!` branch is already unreachable and this should be downgraded/closed.
- If the branch is still reachable, replace the `assert_eq!` with a recoverable `Result`/`DistributionError` (as already done for `AccountNotFound`, `ArithmeticOverflow`, and `UnableToSetState` in the same function) so a mismatch degrades to burning that one stake account's reward (as documented) instead of panicking the entire node.
- Explicitly verify and, if missing, add enforcement in the stake program (or in transaction-level checks) that rejects delegation-mutating instructions for stake accounts while `Bank::get_reward_interval() == InsideInterval` and that account has a pending, uncalculated/uncredited reward.

### Proof of Concept
No cluster-executable PoC was constructed. A conceptual repro path is: (1) get a stake account included in the reward calculation for an epoch boundary (multi-block distribution, e.g. via `stake_account_stores_per_block` small enough to span multiple blocks, as exercised by `test_rewards_computation_and_partitioned_distribution_multi_blocks`, `runtime/src/bank/partitioned_epoch_rewards/mod.rs:943`); (2) between the calculation block and the block that distributes that account's partition, submit an ordinary stake instruction from the stake account's own authority that changes `Delegation::stake` (e.g. partial deactivation/withdraw or merge) without going through the reward-aware adjustment path; (3) when the distribution block for that account's partition is processed, `build_updated_stake_reward`'s `assert_eq!` fires because `stake.delegation.stake` (now mutated) plus the reward no longer equals the value computed during calculation, panicking `store_stake_accounts_in_partition` and therefore the whole block-processing path for every validator. This has not been executed against the codebase and the feasibility of step (2) (i.e., whether such an instruction is actually accepted mid-interval) remains unverified.

    fn build_updated_stake_reward(
        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
        use_fixed_point_stake_math: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;

        let mut new_stake = partitioned_stake_reward.inflation.stake;
        if adjust_delegations_for_rent {
            let minimum_balance = rent.minimum_balance(account.data().len());
            // The rewarded epoch is right before the distribution epoch
            let rewarded_epoch = distribution_epoch.saturating_sub(1);
            // The entry in `partitioned_stake_reward` contains the rewards,
            // calculated during the calculation phase
            let delegation_with_rewards = new_stake.delegation.stake;
            adjust_delegation_for_rent(
                &mut new_stake.delegation,
                rewarded_epoch,
                delegation_with_rewards,
                account.lamports(),
                minimum_balance,
            );
        } else {
            let expected_delegation = stake
                .delegation
                .stake
                .saturating_add(partitioned_stake_reward.inflation.stake_reward);
            assert_eq!(
                expected_delegation, new_stake.delegation.stake,
                "stake reward delegation must be consistent with the updated stake account \
                 lamport balance"
            );
        }
