### Title
Nonce account close (full withdrawal) can be griefed via a permissionless lamport transfer that defeats an exact-equality balance check - (File: `programs/system/src/system_instruction.rs`)

### Summary
`withdraw_nonce_account` decides whether a `WithdrawNonceAccount` instruction is closing the account (full withdrawal) purely by testing `lamports == from.get_lamports()`. Because any unprivileged account can permissionlessly increase a nonce account's lamport balance with an ordinary `SystemInstruction::Transfer` (nonce accounts are owned by the System Program and are valid transfer destinations), an attacker can invalidate this exact-equality check right before a legitimate close/withdraw-all transaction lands, forcing it into the wrong code path and causing it to fail with `InstructionError::InsufficientFunds`.

### Finding Description
`withdraw_nonce_account` is dispatched from `system_processor.rs` for the `WithdrawNonceAccount` instruction: [1](#0-0) 

Inside it, for an `Initialized` nonce account, the branch used to fully close the account (deinitializing it, skipping the rent-exempt minimum check, and skipping the "nonce can only advance once per slot" duplicate-advance guard bypass logic) is selected only when the withdrawal amount is *exactly equal* to the current balance: [2](#0-1) 

If the amount does not exactly equal the balance, the code instead takes the partial-withdrawal branch, which requires `lamports + min_balance <= from.get_lamports()`. When a griefer transfers even 1 extra lamport into the nonce account via a normal, permissionless `SystemInstruction::Transfer` (the `transfer`/`transfer_verified` path only requires the `from` account's data to be empty, and puts no restriction on the recipient account, so nonce accounts can freely receive lamports), the equality check `lamports == from.get_lamports()` becomes false for a transaction that was built to withdraw the full previously-observed balance. The withdrawal then falls into the partial-withdrawal branch and fails with `InstructionError::InsufficientFunds`, since `lamports + min_balance` now exceeds the (griefed) balance by `min_balance - 1`.

This is the same bug class as the external report: an unprivileged party can grief an action that relies on an exact-equality balance check by unilaterally inflating the balance the check depends on, since the caller who built the transaction cannot know about lamports sent to the account after they observed its balance.

### Impact Explanation
A user (or an automated service/dApp) attempting to close a durable nonce account and reclaim its rent (a full `WithdrawNonceAccount` for the entire balance) can have that transaction griefed for the trivial cost of one lamport transfer by any third party observing the pending transaction. The withdrawal fails, the transaction fee is wasted, and the account remains open/initialized, requiring the authority to re-query the balance and resubmit. This is a low-cost, permissionless denial-of-service/griefing primitive against a common wallet/dApp operation (nonce-account cleanup), directly analogous to the original UniswapHelper migration-griefing report, though it does not directly create or destroy value—it forces failed transactions and re-submission.

### Likelihood Explanation
Likelihood is straightforward: any account can send an ordinary `SystemInstruction::Transfer` of 1 lamport to any target nonce account with no special permission, and can watch the mempool/RPC for pending `WithdrawNonceAccount` transactions attempting a full withdrawal to time the griefing transfer. No privileged role, validator access, or race with block production timing precision is required beyond normal transaction submission.

### Recommendation
Change the full-close condition in `withdraw_nonce_account` from an exact equality check to `lamports >= from.get_lamports()` (treating any withdrawal that would drain the account, not just an exact match, as the "close" case), mirroring the recommended fix in the original report (`>=` instead of `==`).

### Proof of Concept
1. Authority `A` owns an initialized nonce account `N` with balance `B` and wants to close it, so it builds `WithdrawNonceAccount(B)` sending all lamports to itself/another destination.
2. Before `A`'s transaction lands, attacker `E` sends `SystemInstruction::Transfer` of 1 lamport from any funded account to `N`. This succeeds unconditionally via `transfer`/`transfer_verified` in `system_processor.rs`.
3. `N`'s balance is now `B + 1`. When `A`'s `WithdrawNonceAccount(B)` executes, `lamports (B) == from.get_lamports() (B+1)` is false, so `withdraw_nonce_account` takes the partial-withdrawal branch:
   - `amount = checked_add(B, min_balance)` where `min_balance = rent.minimum_balance(nonce_data_len) > 1`.
   - `amount > from.get_lamports() (B+1)` is true, so the instruction returns `InstructionError::InsufficientFunds` and the transaction fails.
4. `A` must observe the new balance and resubmit with `B+1`, which `E` can grief again indefinitely at 1 lamport per attempt. [2](#0-1) [3](#0-2)

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
