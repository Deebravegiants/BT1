### Title
Permanent market freeze via i128 RAY-value overflow in accrual — every pool verb panics before mutating - ([File: common/src/rates/index.rs])

### Summary
The mongodb advisory is a denial-of-service class: an unhandled arithmetic condition crashes the caller instead of degrading gracefully. The analog in XOXNO Lending is the unchecked RAY-domain value multiplication inside interest accrual. Once a market's scaled totals times its index exceed `i128::MAX`, `accrue_step` panics, and because every market entrypoint accrues first (`Cache::load → interest::global_sync → mutate`), the market is permanently frozen: no repay, withdraw, liquidation, `clean_bad_debt`, or `claim_revenue` can ever execute again. The borrow-index ceiling (`MAX_BORROW_INDEX_RAY` = 10^36) does not save it, because the value product overflows at roughly index ×170 while the index cap allows ×10^9 growth.

### Finding Description
Every accrual step computes debt and supply values by multiplying scaled RAY shares by the index:

- `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` — `common/src/rates/index.rs:80-81`.
- `update_supply_index` computes `supplied.mul(env, old_index)` — `common/src/rates/index.rs:34`.
- `scaled_to_original` is `scaled.mul(env, index)` — `common/src/rates/scaling.rs:14-16`.

`Ray::mul` routes through `fp_core` mul-div, which widens to `I256` only as an intermediate and panics with `GenericError::MathOverflow` when the result exceeds `i128`. The only caps are on the *indexes* (`MAX_BORROW_INDEX_RAY`, `MAX_SUPPLY_INDEX_RAY` — `common/src/rates/index.rs:15-17,43-44`), not on `shares × index`. `protocol_fee_shares` even saturates share minting at `i128::MAX` headroom (`common/src/rates/index.rs:97-98`), which pushes `supplied` *toward* the overflow boundary instead of bounding it.

`global_sync` runs unconditionally at the top of every market mutation (`contracts/pool/src/interest.rs:20-33`), so once the product overflows, `accrue_chunk` panics before any state transition. The protocol's own test proves the freeze end-to-end: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`) shows `update_indexes` failing with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and then both `withdraw` and `repay` reverting with the same error. The docs concede the gap: "valid caps and bounded indexes do not guarantee that future accrual fits. Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first" (`docs/reference/formulas.md:434-437`).

### Impact Explanation
Permanent freezing of funds for an entire `(hub, token)` market. Once the panic point is crossed, all suppliers' claims and all borrowers' collateral backing that debt are unreachable forever: `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `net_settle`, `claim_revenue`, and `update_indexes` all panic in `global_sync` before touching state. There is no recovery path — no setter writes the index or totals without accruing first, and `recapitalize` only adds cash, it cannot lower `borrowed` or the index. This meets the "permanent freezing of funds" / "contract unable to operate" acceptance bar directly.

### Likelihood Explanation
Reachable by a single unprivileged address through `controller.supply` and `controller.borrow` (or `multiply`/`flash_position`) given a market whose spoke caps are set anywhere near the admitted maximum. `max_cap_for_decimals` admits caps up to `i128::MAX / 10^(27-d)` (≈170 billion whole tokens at 7 decimals, `common/src/validation.rs:48-56`), and the value ceiling is reached when the borrow index grows ≈170× — only ~2.6 years at the maximum 200% APR (`MAX_BORROW_RATE_RAY`), or longer at lower sustained utilization on whale-scale markets. The attacker does not need admin keys: an attacker with sufficient capital can supply to the cap, borrow to max utilization, hold the position (or simply let any existing whale position age), and wait. Because accrual is also triggered by third-party calls (`update_indexes`, other users' borrows), the freeze is irreversible the moment it lands. Note the honest caveat: practical reachability depends on governance-configured caps being large enough that `borrowed_scaled × borrow_index` can approach `i128::MAX` before `max_utilization` or caps throttle growth.

### Recommendation
Make accrual value computations saturating or explicitly bounded rather than panicking:

- Clamp `borrowed.mul(new_borrow_index)` / `supplied.mul(supply_index)` inside `calculate_supplier_rewards` and `update_supply_index` (e.g., a `mul_saturating` variant or an `I256` compare that caps the product at `i128::MAX`), mirroring the `mul_div_floor_saturating` pattern already used in `calculate_scaled_cap` and `protocol_fee_shares`.
- Alternatively, enforce a market-level invariant at `borrow`/`supply` time that `scaled_total × MAX_BORROW_INDEX_RAY` fits `i128`, so the value ceiling can never be reached before the index cap.
- Add a governance-visible alarm when a market approaches the bound, since the docs note "no dedicated ceiling alarm is emitted."

### Proof of Concept
Already demonstrated by the in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
let principal = BILLION * 10i128.pow(18);      // ~i128-scale 18-decimal supply
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;               // 98% utilization
t.borrow_raw(ALICE, "BIG18", debt);
// advance years on the steep XLM rate curve until:
assert_contract_error(failed, errors::MATH_OVERFLOW);          // update_indexes panics
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// market permanently frozen; borrow_index < MAX_BORROW_INDEX_RAY
```

The panic originates in `accrue_step` → `scaled_to_original`/`calculate_supplier_rewards`/`update_supply_index` (`common/src/rates/simulate.rs:60-71`, `common/src/rates/index.rs:34,80-81`), reached through `interest::global_sync` at the head of every pool verb (`contracts/pool/src/interest.rs:20-33`).
