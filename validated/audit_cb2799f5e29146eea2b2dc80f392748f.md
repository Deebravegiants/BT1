### Title
Webhook `shop-domain` (and `topic`) header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler uses to identify which tenant/event the webhook belongs to are read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) [3](#0-2) , but `to_signable_string` — the value the HMAC is actually computed over — returns only `@raw_body` and does not include any of those headers [2](#0-1) . This breaks the identity binding: `hmac_valid(raw_body, client_secret) == true` is treated as proof that `(shop, topic, body)` as a whole originated from Shopify for that shop, when in fact only `body` is authenticated.

### Finding Description
Because the app's `client_secret` (and thus the webhook signing secret) is the same across every shop that has installed the app, any merchant who installs the app can generate their own legitimately-signed webhook (e.g. by triggering an `orders/create` event in their own store) and capture the exact `(raw_body, hmac)` pair Shopify sends them. Since the `shop-domain` and `topic` headers are never part of the signed payload, that same attacker can replay the identical `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header (pointing at a victim shop) and/or a different `x-shopify-topic` header. `Registry.process` will still validate the HMAC successfully (it only checks the body) and will dispatch the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [4](#0-3) , attributing attacker-controlled body content to a victim shop, or making the host app process a benign body under an unrelated topic handler.

### Impact Explanation
This crosses a tenant boundary: an unprivileged attacker who is merely a legitimate (even trial) installer of the app can forge webhook deliveries that the host application will process as if they came from a different merchant's shop, because `shop` is never cryptographically bound to the signature. Depending on how the host app's webhook handlers use `data.shop` (e.g. to look up which merchant's records to update), this enables cross-tenant data injection/spoofing — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on their own store (a normal, unprivileged action for any Shopify merchant): they only need to capture one legitimately-signed webhook body/HMAC pair from their own shop and replay it with a forged `shop-domain` header to the same public webhook endpoint. No secrets, tokens or elevated access are required beyond what any app installer already has.

### Recommendation
Bind `shop`, `topic`, and any other header used to route/attribute the webhook into the HMAC-signed payload verification, e.g. reconstruct the signable string from `raw_body` plus the pinned header values (or independently confirm, via the Admin API using a session tied to the claimed shop, that the webhook was actually registered for that shop/topic) before dispatching to a handler. At minimum, reject requests where the claimed `shop` is not the one your app's persisted state expects for that specific webhook delivery id.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g. creates an order) so Shopify sends a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(B, client_secret)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker replays the exact same POST to the app's webhook endpoint, keeping `raw_body = B` and the same valid `x-shopify-hmac-sha256`, but changes the header to `x-shopify-shop-domain = victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` and succeeds [6](#0-5) .
4. The handler is invoked with `shop: "victim-shop.myshopify.com"` and attacker-supplied `body`, even though Shopify never sent this webhook for `victim-shop`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
