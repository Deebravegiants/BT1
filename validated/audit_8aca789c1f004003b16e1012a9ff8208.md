### Title
Webhook `shop-domain` Header Used as Tenant Identity Is Not Covered by HMAC Verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `HmacValidator.validate` computes and checks the HMAC exclusively against that body. The `shop-domain` header, which becomes `WebhookMetadata#shop` and is documented as the tenant identifier for host applications to act on, is read from the request headers but never included in the signed payload, so it is fully attacker-controllable independent of HMAC validity.

### Finding Description
`HmacValidator.validate` accepts any `VerifiableQuery` and checks `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is derived from `verifiable_query.to_signable_string`. [1](#0-0) 
For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`; none of `topic`, `shop`, `api_version`, or `webhook_id` (all parsed from headers via `shopify_header`) participate in the signature. [2](#0-1) 
`Registry.process` validates the HMAC and then forwards `request.shop` unchanged into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity for the event: [3](#0-2) 
The library's own documentation instructs apps to key per-tenant side effects (background jobs, tenant lookups) directly off `data.shop`: [4](#0-3) 

The equality this breaks: the gem implicitly asserts `shop used for tenant dispatch == shop authenticated by HMAC`, but in fact `shop used for tenant dispatch == shop parsed from an unauthenticated header`. Any request whose body byte content and HMAC pairing are valid for the app's secret (e.g., a genuine webhook delivery that an attacker can intercept/replay, or — more directly — any party who can produce a body+HMAC pair for one shop, which is trivial since the body content itself doesn't have to relate to a specific shop for many topics/replays) can have its `shop-domain` header altered in transit or by any intermediary/log-replay mechanism without invalidating the signature, because that header is outside the signed scope.

### Impact Explanation
Because the tenant-identifying field is not bound to the signature, a party able to influence the `shop-domain` header of an otherwise-valid webhook POST (e.g., a proxy, load balancer, logging/replay tooling, or any component between Shopify and the app that is not identical for signature purposes) can cause the app to process and attribute webhook data to a different shop than the one Shopify authenticated the payload for — a cross-tenant data/action confusion. This matches the Critical "cross-tenant access" category: the gem provides no binding between the authenticated bytes and the tenant identity it hands to the app, so the security guarantee "this event belongs to shop X" is not actually established by `HmacValidator.validate`.

### Likelihood Explanation
Exploitation requires control over request headers independent of the body (e.g., via an intermediary or misconfigured deployment that terminates/reconstructs headers separately from the signed body) — this is a documented gap in the gem's design; the gem's `README`/HMAC validator never advertises header authentication, so apps that trust `WebhookMetadata#shop` (as the docs instruct) inherit the exposure with no gem-level warning. Likelihood is bounded by the requirement of some header-rewriting capability between Shopify and the app.

### Recommendation
Bind the tenant-identifying header to the HMAC verification, or explicitly document that `shop`, `topic`, `api_version`, and `webhook_id` are unauthenticated and must not be trusted for tenant-sensitive dispatch without an independent cross-check (e.g., verifying `shop` against the session/store the app already has on record before acting). At minimum, `Registry.process` should cross-validate `request.shop` against an expected/known shop set before invoking the handler.

### Proof of Concept
```ruby
raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Valid signature for raw_body, but shop-domain is swapped to a victim shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives data.shop == "victim-shop.myshopify.com"
# even though nothing about that value was verified by HmacValidator.validate.
```
`HmacValidator.validate` returns `true` because `to_signable_string` never includes the header value being altered. [5](#0-4)
