### Title
User-Centric Signup Path Bypasses Backend Enrollment/Duplicate-Check Gate - (File: src/plans/mod.rs)

### Summary
For signups flagged as `user_centric_signup` by the backend-issued QR data, `MasterPlan::do_signup` determines final signup success purely from the orb's own local `signup_reason` value, skipping the call to `enroll_user::Plan::run` that normally submits the capture to the backend and polls for a verified, authoritative enrollment result (including backend duplicate/fraud detection).

### Finding Description
In `do_signup`, once biometric capture and pipeline processing finish, `signup_reason` is computed locally as `Normal`, `Failure`, or `Fraud` based on pipeline success and `detect_fraud`'s result [5](#0-4) . Later, the code branches on `user_centric_signup`:
```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(...)).await.is_success()
};
``` [1](#0-0) 

When the `user_centric_signup` branch is taken, `enroll_user::Plan::run` — the only code path that submits the signup to the backend via `signup_post::request` and polls `signup_poll::request` for a server-verified outcome (duplicates, backend-side fraud, legacy signup, inflight matches) — is never invoked [2](#0-1) . Instead, `signup_reason` is treated as authoritative for success, but its only real gating input, `detect_fraud`, is a stub that always returns `false` in this codebase because all fraud checks were deleted (`N_FRAUD_CHECKS: usize = 0`) [3](#0-2) [4](#0-3) . This is analogous to the `mint` bug in the report: a safety-critical check (server-side enrollment/duplicate verification) exists and is enforced on one code path but is skippable via a state flag (`user_centric_signup`, controlled by backend-issued QR data) on another, letting a signup be marked `Success` locally without any authoritative backend confirmation that the identity/biometric is unique or unblocked.

### Impact Explanation
An unprivileged signing-up user whose QR data sets `user_centric_signup = true` can have their signup locally marked `Success` and have PCP tiers uploaded to the backend, without the orb ever confirming with the backend that the iris/enrollment is not a duplicate or otherwise blocked. Because local fraud detection is a no-op stub, any biometric capture that completes the pipeline is treated as `Normal`, causing `success = true` regardless of whether the individual is a duplicate signup, previously flagged, or otherwise ineligible per backend policy — undermining the intended anti-fraud/duplicate-signup gate analogous to the missing paused-market check in the original report.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `ignore_user_centric_signups` is `false` (the default posture for supporting the app-centric flow) and the backend legitimately (or is tricked into) issuing `user_centric_signup = true` in the QR-linked user data returned to the orb; no privileged access or hardware tampering is required — an unprivileged signing-up user simply needs to go through the normal QR scan and capture flow.

### Recommendation
Do not treat `signup_reason` alone as authoritative for `user_centric_signup` paths. Always route the signup outcome through (or otherwise obtain confirmation from) the backend verification performed in `enroll_user::Plan::run`, or reintroduce equivalent server-side/duplicate verification before the orb locally marks the signup as `Success` and uploads PCP tiers.

### Proof of Concept
1. Backend issues a user QR with `authenticated_app_data.user_centric_signup = true` (per `orb_qr_link::UserData`, propagated into `backend::user_status::UserData` at [6](#0-5) ).
2. User completes biometric capture; pipeline succeeds; `detect_fraud` returns `false` (always true in this build) [7](#0-6) , so `signup_reason = SignupReason::Normal`.
3. `do_signup` takes the `user_centric_signup` branch, sets `enrollment_status = Success`, and `success = true`, entirely skipping `enroll_user::Plan::run`'s backend `signup_post`/`signup_poll` verification cycle [1](#0-0) .
4. PCP tiers are uploaded as if the signup were backend-verified, even though no backend duplicate/fraud check was actually performed for this specific enrollment result.
