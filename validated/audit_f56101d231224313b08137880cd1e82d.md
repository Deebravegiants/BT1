The Raydium AMM has an analogous issue in the `Withdraw` instruction: unlike the swap instructions (where `minimum_amount_out` is a mandatory `u64` checked unconditionally), the withdraw path makes slippage protection **optional and skippable**.

### Title
Optional/Skippable Slippage Protection in `process_withdraw` Exposes LPs to Sandwich Attacks - (File: program/src/processor.rs)

### Summary
`WithdrawInstruction` defines `min_coin_amount` and `min_pc_amount` as `Option<u64>` [1](#0-0) , and the slippage check in `process_withdraw` is only executed when **both** fields are `Some`: [2](#0-1) . If either is `None` (e.g. via `WithdrawInstruction::unpack` when the instruction data omits the trailing 16 bytes, defaulting to `(None, None)`), no minimum-amount check is applied at all before the coin/pc token transfers occur [3](#0-2) .

### Finding Description
Contrast this with the swap instructions, where `minimum_amount_out` is a non-optional `u64` and is unconditionally checked against `swap_amount_out` before any transfer: [4](#0-3)  (and identically in `process_swap_base_in_v2` at [5](#0-4) ). The `Deposit` path similarly always validates that the computed `deduct_pc_amount`/`deduct_coin_amount` doesn't exceed the caller-supplied max amounts [6](#0-5) , an unconditional slippage guard.

The `Withdraw` path is the outlier: `coin_amount` and `pc_amount` are computed purely from the current pool ratio via `InvariantPool::exchange_pool_to_token` [7](#0-6) , and then transferred to the user with no enforced floor unless the caller happened to populate both `Option` fields [8](#0-7) . This mirrors exactly the reported Balancer/Aura bug class: the exit-liquidity path lacks mandatory slippage protection, leaving the received amount fully dependent on the pool state at execution time.

### Impact Explanation
An LP who submits a `Withdraw` instruction without the optional min-amount fields (or whose client/SDK constructs it that way, since the fields are optional by design) receives whatever the pool ratio dictates at execution time, with no on-chain floor. An attacker (MEV searcher) can sandwich the withdrawal — front-run it with a swap that skews the coin/pc ratio unfavorably for the withdrawer, let the withdraw execute at the skewed ratio, then swap back — extracting value from the withdrawing LP's proceeds. This is concrete theft of LP funds via price manipulation around an unprotected instruction.

### Likelihood Explanation
Reachable by any unprivileged LP holder simply calling `Withdraw` with default/omitted min-amount parameters, which is a valid and unpack-supported instruction encoding (`rest.len() < 16` branch in `unpack`). No privileged signer or special conditions are required; only an attacker capable of ordering transactions around the victim's withdraw (a standard, low-barrier MEV technique) is needed to realize the loss.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-`Option`) fields, or reject the withdraw instruction entirely when either field is `None`, so that slippage protection can never be silently bypassed — analogous to how `minimum_amount_out` is enforced unconditionally in the swap paths.

### Proof of Concept
1. Victim submits `Withdraw { amount, min_coin_amount: None, min_pc_amount: None }` (or a client library that omits these optional fields by default).
2. Attacker front-runs with a swap (`SwapBaseIn`/`SwapBaseOut`) that shifts `total_coin_without_take_pnl` / `total_pc_without_take_pnl` unfavorably relative to the victim's expected withdrawal ratio.
3. `process_withdraw` computes `coin_amount`/`pc_amount` from the skewed ratio via `InvariantPool::exchange_pool_to_token`, and because `min_coin_amount.is_some() && min_pc_amount.is_some()` is `false`, the `ExceededSlippage` check at [9](#0-8)  is skipped, and the transfer proceeds at the manipulated ratio.
4. Attacker swaps back afterward, pocketing the difference extracted from the victim's withdrawal.
