Webhook shop-domain and topic headers are trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but then dispatches the handler using the `shop` (and `topic`) values taken from unauthenticated HTTP headers. Because a single app-wide `client_secret` is used to sign webhooks for *every* installed shop, any merchant who has legitimately installed the app can capture one of their own genuinely-signed webhook deliveries (valid body + HMAC) and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. The signature still validates because the header is never part of the signed content, letting the attacker make the app process foreign, attacker-supplied body data under another tenant's identity.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — no header data is included in the signed content: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are authenticated: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then trusts `request.shop`/`request.topic` from those same unauthenticated headers to select the handler and populate `WebhookMetadata`: [4](#0-3) 

Because the app's `client_secret` (used to compute `x-shopify-hmac-sha256`) is identical across every shop that has the app installed, any merchant is capable of producing a "genuinely" signed body/HMAC pair for their own store's real webhook traffic. That HMAC only binds the body, not the shop-domain header, so the identity binding the host application relies on — `signed_hmac ⇒ (body, shop)` — actually only holds as `signed_hmac ⇒ body`. A merchant can therefore replay a captured valid `(body, hmac)` pair to the public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value, and the library will report the request as valid and hand the attacker-chosen body to the handler tagged with a different shop's identity.

### Impact Explanation
This breaks the tenant identification boundary the webhook handler relies on: an app that keys any state, authorization, or side effects (e.g., updating billing, provisioning, revoking access, GDPR redaction handling) off `WebhookMetadata#shop` can be made to perform actions against or on behalf of a shop the attacker does not own, using data the attacker fully controls (their own webhook body content). This is a cross-tenant boundary violation that stems directly from this gem's `HmacValidator`/`Webhooks::Request` design not binding the shop identifier into the signed payload, matching the High-severity "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires: (1) the attacker be a legitimate app-installing merchant (no special privilege, secret, or credential of the app itself is needed — the ordinary per-install webhook delivery already gives them a valid signed body/HMAC pair for their own data), and (2) the ability to send an arbitrary POST to the app's public webhook endpoint with modified headers, which any internet client can do. No knowledge of `api_secret_key` is required since the attacker reuses an HMAC that Shopify itself already computed and delivered to them.

### Recommendation
Bind the shop identity into the authenticated content used for webhook verification instead of trusting the raw header value post-hoc — e.g., include `shop` (and ideally `topic`/`webhook_id`) in the signable string used by `HmacValidator`, or require host applications to cross-check `request.shop` against the shop that owns the specific `webhook_id`/subscription before invoking the handler, and document this requirement clearly given that Shopify's own HMAC scheme signs only the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a real webhook (e.g. `orders/create`) delivery. They capture the raw POST: `raw_body` and header `x-shopify-hmac-sha256: <valid HMAC over raw_body computed with the app's client_secret>`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — matching the header value — and returns `true`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker-controlled data under the victim shop's tenant identity.
