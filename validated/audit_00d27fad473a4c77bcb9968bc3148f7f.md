### Title
Webhook `process` trusts unauthenticated `shop`, `topic`, and `webhook_id` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only the raw request body against the HMAC signature, then hands the caller-supplied `shop`, `topic`, and `webhook_id` HTTP headers to the app's handler as if they were verified. Those fields are not covered by the signature, so any party who can obtain one valid `(body, hmac)` pair for the app's shared `api_secret_key` can relabel that payload as belonging to an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`, and for webhook requests that method returns only the raw body: [1](#0-0) [2](#0-1) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

`Registry.process` validates the HMAC against the body, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all pulled straight from headers that are never part of the signable string) and forwards them to the app's handler as authoritative identifiers: [3](#0-2) 

The documentation explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify," which implies the whole event — including which shop it came from — is authenticated: [4](#0-3) 

The broken binding is: `shop header used to attribute the event ≠ shop bound by the HMAC signature`. Since the same `api_secret_key` is shared across every shop that installs the app, any entity that can trigger one legitimate webhook delivery for their own store (installing a public app is unprivileged and self-service) obtains a `(raw_body, valid hmac)` pair signed with the app's shared secret. They can then POST that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This lets an unprivileged attacker (anyone who can install the target app on their own store) inject arbitrary attacker-controlled webhook payloads that the host application will attribute to an arbitrary other tenant/shop. Any app that keys per-tenant state, order/customer records, or business logic off `WebhookMetadata#shop` — exactly as the library's own API surface encourages — can be tricked into writing or acting on attacker data under a victim shop's identity, a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
The attacker only needs the ability to install the app on their own shop (a normal, unprivileged action for any public Shopify app) and a way to POST to the app's public webhook endpoint (which is, by design, a public URL). No access token, `client_secret`, or session is required, and no part of the signature scheme protects the header fields, so the attack is straightforward to reproduce.

### Recommendation
Do not treat header-derived `shop`, `topic`, or `webhook_id` as authenticated. At minimum, `Registry.process`/`WebhookMetadata` should require callers to cross-check `request.shop` against a shop that the app itself knows has this webhook/topic registered (e.g. via the app's own installed-shops store) before acting on the payload, and the docs' claim of full verification should be corrected to clarify that only the body is HMAC-verified.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`), capturing the raw body and its valid `X-Shopify-Hmac-Sha256` value.
2. Attacker POSTs that exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which only checks the body — validation passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_body, ...)` [6](#0-5) , and the host app processes attacker-controlled data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
