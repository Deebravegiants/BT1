## Title
Unchecked External-Call Target in Emporium Wallet Calls Lets an Attacker No-Op the Fee/Wallet Callback and Steal Relay Fees - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` and its fee-payment helper trust the boolean `success` returned by a low-level `.call()` to `stack.signerAddress` as proof that the "wallet" actually executed the requested operation or paid the relay. Solidity's low-level `call` to an address with no code always returns `success = true` and empty data without executing anything. Because `stack.signerAddress` is fully attacker-chosen and only required to match an ECDSA-recoverable EIP-712 signature (which the attacker can trivially produce with their own EOA key), an attacker can set `signerAddress` to their own externally-owned account instead of a real `HinkalWallet` contract. Every "wallet" call — the stateful operation call and the relay-fee payment call — silently becomes a no-op that reports success, while the surrounding balance-equation checks still pass.

### Finding Description
`Hinkal._externalTransact` pre-funds the Emporium contract with the withdrawn token amount before calling `runAction` whenever `deltaAmountChanges[i] < 0`: [1](#0-0) 

Inside `EmporiumUpgradeable.runAction`, the `EmporiumStack` (including `signerAddress` and the operation list) is decoded directly from user-supplied `externalActionMetadata`, and `verifyWallet` only checks an EIP-712 signature that recovers to `stack.signerAddress` — there is no check that this address is a contract, let alone a genuine `HinkalWallet`: [2](#0-1) 

For the "Stateful Interaction" branch, the contract calls `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)` and treats the returned `success` as authoritative: [3](#0-2) 

If `signerAddress` is an EOA (or any address without the `HinkalWallet` bytecode), this low-level call performs no state change yet still returns `success = true`, so `CallFailed` never reverts. Consequently `balancesAfter == balancesBefore` (the pre-funded withdrawal amount is untouched), and the accounting correction `balanceChange -= deltaAmountChanges[i]` turns this into a positive `balanceChange` equal to the withdrawn amount: [4](#0-3) 

`handleOut` then simply returns the full withdrawn amount back to Hinkal and mints a fresh output UTXO for the same value, so `Hinkal`'s balance equation (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied with `balanceDif = 0`, `amountChanges[i] = -X`, `utxoAmount = X`: [5](#0-4) [6](#0-5) 

Separately, `payRelayFees`/`sendToRelayFromWallet` route the flat relay fee through the very same unchecked call pattern (`IHinkalWallet(signerAddress).doSendToRelay(...)`), which is also silently no-op'd when `signerAddress` has no code: [7](#0-6) 

Nowhere in `HinkalFactory`/`HinkalWallet` or `EmporiumUpgradeable` is `extcodesize`/`code.length` (or any registry lookup) used to confirm `signerAddress` is a deployed `HinkalWallet`: [8](#0-7) 

This mirrors the report's bug class ("unchecked flash-loan callback"): a contract executes privileged logic based on an unverified callback target/response rather than validating that the callee is the legitimate, expected contract.

### Impact Explanation
The relay-fee flat fee (`feeStructure.flatFee`) that is supposed to be pulled from the signer's wallet is never actually transferred — the call that should move it silently "succeeds" without moving any funds. The attacker completes a full withdraw-and-recreate cycle (consuming input nullifiers, minting a new same-value UTXO to themselves) while completely evading the relay fee obligation for that Emporium-routed transaction. This is theft/permanent avoidance of protocol/relay fees, matching the "High" impact category (theft of protocol/relay fees).

### Likelihood Explanation
The attack requires only an unprivileged EOA: the attacker signs the EIP-712 `EmporiumSignature` message with their own private key (setting `stack.signerAddress` to their own EOA), constructs a normal Hinkal proof with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `deltaAmountChanges[i] < 0`, and any dummy `ops` entry, and submits the transaction. No admin/relay/oracle/other-user's key is needed, and no revert occurs anywhere in the call path, so the transaction is straightforward to construct and always succeeds.

### Recommendation
Before invoking `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)` or `.doSendToRelay(...)`, verify that `signerAddress` has code (`signerAddress.code.length > 0`) and, ideally, that it is a wallet actually deployed/registered by the protocol (e.g., verified against a deterministic `CREATE2` address derived from a known `HinkalWallet` bytecode hash and the signer's key), rather than relying solely on the ECDSA-signature check and the `success` flag of a low-level call.

### Proof of Concept
1. Attacker holds a shielded UTXO of token `T` worth `X` and generates a valid Hinkal proof calling `Hinkal.transact` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = [T]`, `amountChanges = [-X]` (a withdrawal), and `externalActionMetadata` ABI-encoding an `EmporiumStack` where:
   - `signerAddress = attackerEOA` (an address the attacker controls the private key for, not a deployed `HinkalWallet`)
   - `ops = [{ endpoint: anyAddress, invokeWallet: true, value: 0, callData: 0x }]`
   - `v, r, s` = a valid EIP-712 signature over `EMPORIUM_SIGNATURE_TYPEHASH` produced with `attackerEOA`'s key
   - `feeStructure.flatFee = <normal relay flat fee>`, `relay = <a relay address>`
2. `Hinkal._externalTransact` sends `X` of token `T` from Hinkal to Emporium (pre-funding) since `deltaAmountChanges[0] < 0`.
3. `EmporiumUpgradeable.runAction` calls `verifyWallet`, which succeeds because the signature recovers to `attackerEOA`.
4. The `ops` loop calls `IHinkalWallet(attackerEOA).callHinkalWallet(...)` — since `attackerEOA` has no code, this returns `(true, "")` without doing anything; no `CallFailed` revert occurs.
5. `payRelayFees` → `sendToRelayFromWallet` → `IHinkalWallet(attackerEOA).doSendToRelay(relay, flatFee, T)` — again a no-op call that returns success without transferring any fee to `relay`.
6. `balancesAfter == balancesBefore` (unchanged from the pre-funded state), so `balanceChange = 0 - (-X) = X`; `handleOut` sends `X` back to Hinkal and mints a new UTXO of value `X` for the attacker.
7. Back in `Hinkal.transact`, `balanceDif = 0` and `amountChanges[0] + utxoAmount = -X + X = 0`, satisfying the balance equation; the transaction completes successfully with the attacker's nullifiers consumed and a fresh same-value UTXO created, while the relay receives none of the expected `flatFee`.

import {Transferer} from "../../Transferer.sol";
import {IHinkalWallet} from "../../types/IHinkalWallet.sol";

contract HinkalWallet is Transferer, IHinkalWallet {
    address public immutable emporium;

    event EthReceivedOnWallet(address indexed sender, uint256 amount);

    error NotAllowedToCallWallet();

    constructor(address _emporium) {
        emporium = _emporium;
    }

    modifier onlyEmporium() {
        if (msg.sender != emporium) {
            revert NotAllowedToCallWallet();
        }
        _;
    }

    function callHinkalWallet(
        address endpoint,
        bytes calldata data,
        uint value
    ) external onlyEmporium returns (bool success, bytes memory err) {
        (success, err) = endpoint.call{value: value}(data);
    }

    function doSendToRelay(
        address relay,
        uint256 actualAmount,
        address erc20TokenAddress
    ) external onlyEmporium {
        sendToRelay(relay, actualAmount, erc20TokenAddress);
    }
