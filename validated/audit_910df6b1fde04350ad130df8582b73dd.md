### Title
Webhook shop-domain and topic are not covered by the HMAC signature, allowing cross-tenant webhook forgery via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` verifies nothing but the body bytes. [1](#0-0)  The `shop` and `topic` values that `Registry.process` uses to select a tenant-scoped handler and to build the `WebhookMetadata` delivered to the app come from the `x-shopify-shop-domain` / `x-shopify-topic` HTTP headers, which are never included in the HMAC-signed content. [2](#0-1) [3](#0-2) 

### Finding Description
The bug class from the report is "a field acted on is not covered by the cryptographic check that is supposed to authenticate it" (fee computed on `pairedLpDesired` instead of the amount actually verified/used). The analog here is the same shape of binding failure: `HMAC-verified bytes == raw_body` but `tenant identity used by the handler == shop-domain header`, and these two are never proven equal.

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. [4](#0-3)  For `Webhooks::Request`, that signable string is defined as `@raw_body` only:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from the HTTP headers with no cryptographic binding to the signed body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` only checks `HmacValidator.validate(request)` (i.e., that the body bytes are authentic for *some* previously-signed payload) and then unconditionally trusts `request.shop`/`request.topic` to route to a handler and populate `WebhookMetadata`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The binding that should hold is: `shop_claimed_by_header == shop_that_produced_the_signed_body`. Because the header is outside the signed content, an unprivileged holder of any one genuine `(raw_body, hmac)` pair for the app (e.g., from their own shop's legitimately delivered webhook) can resend the same body/HMAC to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body bytes against the signature, so `Registry.process` accepts the request and hands the app's handler a `WebhookMetadata` claiming to be from a different (victim) shop while carrying the attacker's own body content.

### Impact Explanation
This crosses a tenant boundary inside data the gem hands to the application: the `shop` field the app relies on for tenant isolation is attacker-controlled and unauthenticated, while only the body is authenticated. Any consumer that keys per-tenant storage, side effects, or business logic off `WebhookMetadata#shop` (exactly as the gem's own `webhook_handler.rb`/example usage implies it should) can be made to apply attacker-supplied webhook content under a victim shop's identity — i.e., cross-tenant data confusion/injection, matching the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair generated by Shopify for the target app — trivially obtainable if the attacker's own store has the app installed and receives any webhook (no privileged credentials, access tokens, or `client_secret` needed). They only need to intercept/replay their own legitimately-received webhook request while forging the `x-shopify-shop-domain` header, which is a header they fully control on their own HTTP client, requiring no MITM or leaked secret.

### Recommendation
Bind the shop (and ideally topic) identity into the same value that is authenticated, or cross-check it against a trusted source before use:
- Prefer verifying `request.shop` against the shop stored in an existing, previously-established session (offline session for that shop) before dispatching the handler, rather than trusting the header outright.
- Where possible, include the `shop` value from the header in the value passed to `HmacValidator`, or require callers to supply the expected shop and compare it against `request.shop` prior to processing, raising `InvalidWebhookError` on mismatch.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook POST to `https://app.example.com/webhooks`, with body `B` and headers including `x-shopify-hmac-sha256: H` (valid for `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, unmodified except for `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts it (all required headers present), and `HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and compares it to `H` — this matches because `B` is unchanged, per `to_signable_string` returning only `@raw_body`. [1](#0-0) 
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)`, i.e., attacker-controlled content is delivered under the victim shop's identity. [3](#0-2)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
