### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reported bug class is a race/identity-binding gap: code acts on a value while the trust check verifies something else. In `AuctionWithBuyoutLoanLiquidator.sol`, `settleWithBuyout` acted on "no bids placed" while `placeBid` could still be settled at the same instant, breaking the invariant the settle path relied on. The analogous gap in this gem is that `ShopifyAPI::Webhooks::Request` computes and validates the HMAC only over the raw request body, while the tenant identity (`shop`) that downstream handler code trusts and acts on is taken from an unauthenticated header that is never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`: [2](#0-1) 

`Registry.process` validates that HMAC and then immediately trusts `request.shop` (sourced from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is **not** part of the signed bytes) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) [4](#0-3) 

The equality the code should enforce is: `shop-bound-by-HMAC == shop-acted-on-by-handler`. Instead, the gem enforces only `hmac(body) == hmac(body)`, while `shop` used for tenant attribution is read from an out-of-band header with no cryptographic binding to the signed payload. Because a single app's `api_secret_key`/`client_secret` is shared across every merchant install of that app, any merchant who receives one legitimate webhook for their own shop (a completely unprivileged, self-service action — installing the app and triggering any webhook-firing event) obtains a `(raw_body, valid hmac)` pair that remains cryptographically valid regardless of which `shop-domain` header value accompanies it. That merchant can then replay the same body/HMAC to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim tenant. `Utils::HmacValidator.validate` will accept it because it never inspects `shop`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to preserve for webhook processing: the app's handler code executes under the identity of an attacker-chosen `shop` value that was never verified against the signed payload. Any app that uses `shop` from `WebhookMetadata` to key persistence, cache invalidation, session lookups, or business logic can be made to attribute one tenant's legitimate event data to another tenant, or trigger tenant-scoped side effects (e.g. uninstall/reinstall handling, order/customer data writes) against a shop the attacker does not own. This matches the "cross-tenant access" criterion for High/Critical impact, since the tenant-scoping guarantee that HMAC validation is supposed to provide is silently not enforced over the field (`shop`) that actually drives per-tenant behavior.

### Likelihood Explanation
Exploitability requires no privileged credentials, access tokens, or the app's `api_secret_key`: the attacker only needs to be a normal, self-service merchant of the target app (or otherwise legitimately trigger one webhook delivery to the same endpoint), capture the resulting `(body, hmac)` pair, and resend it with a different `shop-domain` header. This is a standard HTTP replay with header substitution — well within reach of an unprivileged internet user interacting with the app's publicly reachable webhook endpoint. Whether it is remotely triggerable end-to-end further depends on host-application code trusting `WebhookMetadata#shop` for tenant-sensitive decisions, which is the intended and documented use of that field.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`/`webhook_id`) inside the HMAC-covered signable content, or independently bind/validate the `shop-domain` header against a value derived from the signed payload (e.g., embedding `shop` in the body-derived signature material, or requiring the host app to cross-check the header against a known/installed shop record before trusting it as delivered by Shopify). At minimum, document prominently that `WebhookMetadata#shop` is not HMAC-verified and must not be trusted as an authenticated tenant identifier by itself.

### Proof of Concept
1. App merchant "Attacker" installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no special privilege).
2. Attacker triggers any webhook event on their own shop (e.g. `orders/create`), and captures the resulting POST to the app's webhook endpoint, including the raw body and the `shopify-hmac-sha256` header — this HMAC is valid because `HmacValidator.validate` only signs `raw_body` [1](#0-0) .
3. Attacker resends the identical `raw_body` and `shopify-hmac-sha256` header to the same endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it never checks `shop` [5](#0-4) , then dispatches to the handler with `shop: request.shop` set to `victim-shop.myshopify.com` [6](#0-5) .
5. The host app's handler processes the attacker's own order payload as if it belonged to `victim-shop.myshopify.com`, demonstrating cross-tenant data/action confusion.
