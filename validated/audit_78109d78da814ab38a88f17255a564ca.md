## Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed downstream are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` to identify the tenant for the webhook handler without that value ever being bound to the HMAC. Any merchant who installs the host app can capture one of their own genuinely-signed webhook deliveries and replay it with a forged `shopify-shop-domain` header pointing at a victim shop, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers with no cryptographic binding to the body or the signature: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC using exactly `to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because Shopify signs webhooks with the app's single `api_secret_key`, which is identical for every shop that installs the app, an HMAC computed for a legitimate webhook delivered to the app for **Shop A** remains valid for the exact same body regardless of which `shopify-shop-domain` header value is presented — that header is never part of the signed content. This breaks the intended identity binding: `shop authenticated (via HMAC) == shop the handler acts on (request.shop)`. Before the attack: HMAC covers `raw_body`, and `request.shop` is read from a header not covered by that HMAC — these are already unequal domains of trust. After the attack: an unprivileged merchant (Shop A) intercepts/replays their own valid webhook body+HMAC while substituting the `shopify-shop-domain` header with a victim's domain (Shop B); `Utils::HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` invokes the handler with `shop: "shop-b.myshopify.com"` and Shop A's payload.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (but unprivileged) merchant of the host app can cause the app's webhook handler to process attacker-controlled data under another merchant's shop identity. Depending on how the host application's handler uses `WebhookMetadata#shop` (typically as a lookup/foreign key into the merchant's own database record), this enables cross-tenant data injection/corruption — e.g., writing attacker-chosen order/product/customer data into another shop's records, or triggering business logic (like uninstalling app state, updating billing, etc.) against the wrong tenant. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker only needs to be a merchant with the app installed (no elevated privileges, no leaked secrets, no access token required) to legitimately receive a validly-signed webhook, and then replay it with a modified header at the app's public webhook endpoint. No cryptographic secret needs to be broken — the vulnerability is structural (header not covered by signature), making this reliably reproducible.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the data that is verified against the HMAC, or otherwise cryptographically bind them to the signed payload, so that a forged/replayed header cannot be substituted independently of the signed body. At minimum, `Registry.process` should not trust `request.shop` for any tenant-scoping decision unless it has been validated as part of the signed content.

### Proof of Concept
1. Attacker installs the host app on their own shop, `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's webhook endpoint with headers:
   - `shopify-topic: orders/create`
   - `shopify-shop-domain: attacker-shop.myshopify.com`
   - `shopify-hmac-sha256: <valid HMAC of raw_body computed with the app's api_secret_key>`
   - body: `{"id": 1, ...attacker-controlled order fields...}`
3. Attacker captures this raw body and its (still-valid) HMAC header value.
4. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC only over `raw_body` (via `Request#to_signable_string`) and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and invokes the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker's body content — impersonating a webhook from the victim's shop.
