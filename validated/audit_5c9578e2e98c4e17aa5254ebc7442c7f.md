### Title
Hostile HyperSwap V2 pre-seed can exceed Bonding's rebalance budget, seeding the graduation LP away from the curve-close price - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The external report flags reliance on a live, attacker-influenceable spot price (Uniswap V3 `slot0`) for critical liquidity math. alt.fun's analog is `Bonding._seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose`, which read the live, permissionlessly-writable reserves of the HyperSwap V2 TOKEN/LT pair (`IUniswapV2Pair(pair).getReserves()`) and use them, together with a swap capped by *Bonding's own graduation inventory*, to steer the pool back toward the curve-close ratio before depositing liquidity [1](#0-0) . When the size of a hostile pre-seed exceeds what that inventory-bounded correction swap can offset, the final deposit lands at whatever ratio the pool sits at post-swap — not the cached curve-close ratio — because the deposit uses the V2 router's `quote()`-based split at the *current* (still skewed) reserve ratio [2](#0-1) .

### Finding Description
`finalizeGraduation` is permissionless and seeds the graduated pool via `_seedUniswapV2Direct` → `_seedRebalancing` [3](#0-2) . When the HyperSwap pair already has LP supply (an attacker called `pair.mint()` against a self-funded, hostile TOKEN:LT ratio before `finalizeGraduation` landed), the code computes the live pool ratio from `getReserves()` and attempts to rebalance it toward the cached curve-close ratio (`tokensForLP`, `ltFromPair`) via a single direct `pair.swap` [4](#0-3) .

Crucially, the rebalance swap's input is capped at 99% of *Bonding's own graduation-inventory* for that side (`_swapBudget(_ltSwapInventory(...))` or `_swapBudget(IERC20(tokenAddress).balanceOf(address(this)))`) [5](#0-4) , not by how far the live pool ratio is from the target. The natspec explicitly acknowledges the cap exists "for catastrophic pre-seeds beyond our budget capacity, where the alternative is bricking" [6](#0-5) , but the mitigation for exceeding the budget is simply to not brick — not to guarantee the resulting deposit lands at the curve-close price. After the capped swap, `_routerDepositAndDispose` deposits Bonding's remaining `tokensForLP`/`ltFromPair` inventory via `router.addLiquidity(..., 1, 1, lpLock_, ...)`, which pulls the *optimal amounts at whatever ratio the pair is at post-swap* [7](#0-6)  — i.e., not necessarily the curve-close ratio if the pre-seed was large enough relative to `tokensForLP`/`ltFromPair` that the capped correction swap could not fully close the gap.

Because pair creation on the underlying V2 factory (`_ensureUniswapV2Pair`) is permissionless [8](#0-7) , any unrelated wallet can pre-create the TOKEN/LT pair and `pair.mint()` a large, arbitrarily skewed self-funded liquidity position ahead of `finalizeGraduation`. This is exactly the class of bug the report describes for `slot0`: a critical financial computation (here, the amount/ratio deposited into a permanently-locked LP) is anchored to a live, cheaply-manipulable AMM state that an unprivileged actor fully controls, and the built-in defense only bounds it by Bonding's fixed inventory rather than by the size of the attack.

### Impact Explanation
If the pre-seed exceeds the swap-budget correction capacity, the graduation LP — locked forever in `LPLock` with no rescue path (`_seedDirectMint`/`_seedRebalancing` natspec explicitly notes `LPLock` has no rescue path in v1) [9](#0-8)  — opens at a price that deviates from the curve's actual close price. This breaks the "zero price gap" invariant the protocol relies on (invariant #1 in `docs/contracts-scope.md`) [10](#0-9) . The attacker's pre-existing LP shares are proportionally entitled to the resulting pool reserves at whatever price the pool settles at; a mispriced pool invites arbitrage that transfers value away from the newly seeded (permanently locked, protocol/community-owned) liquidity toward the attacker's pre-existing LP position — a permanent value leak from locked LP funds, which the rules classify as a valid Medium/High impact ("an LP seeded away from the curve close price").

### Likelihood Explanation
Requires an attacker with enough capital to fund both a large TOKEN-side and LT-side (or a single very lopsided side) pre-seed exceeding Bonding's own `tokensForLP`/`ltFromPair` inventory for that specific graduating token. This is capital-intensive and token-specific (largest for tokens with a small `ltFromPair`/`tokensForLP`, e.g. tokens that graduate via the supply trigger with modest LT raised), so likelihood is bounded by attack capital versus the size of the graduating curve's own raised liquidity — plausible for smaller/thinly-raised graduations but not universal.

### Recommendation
Do not fall back to "deposit at whatever post-swap ratio results" when the pre-seed exceeds the rebalance budget. Instead, when the required no-fee swap input to reach the target ratio exceeds the available budget, either (a) revert/defer `finalizeGraduation` for that pre-seed size rather than silently accepting an off-ratio deposit, or (b) size the deposit itself (not just the swap) proportionally so the *deposited* liquidity, not just the swap, is bounded to preserve the target ratio — e.g., only deposit the subset of `tokensForLP`/`ltFromPair` that the corrected reserves can absorb at the exact target ratio, burning/sweeping the remainder exactly as already done for other off-ratio remainders.

### Proof of Concept
Conceptual sequence (cannot be executed here, no code-execution tools available in this session — recommend validating in `packages/contracts/test/TwoPhaseGraduation.t.sol` / `test/NoFeeSwapInput.t.sol` harnesses, which already model pre-seed scenarios):
1. Attacker calls `IUniswapV2Factory.createPair(token, lt)` for a not-yet-graduated token (permissionless).
2. Attacker mints a large, deliberately skewed self-funded liquidity position into that pair (`pair.mint(attacker)`) sized so that `reserveToken`/`reserveLT` deviates from the eventual `tokensForLP`/`ltFromPair` ratio by more than `_swapBudget` (99% of Bonding's own `tokensForLP` or `ltFromPair`) can correct.
3. The token's curve later graduates; `Bonding.triggerGraduation` / the threshold-crossing buy calls `_enterGraduating`, caching `tokensForLP`/`ltFromPair` at the curve-close ratio.
4. Anyone calls `finalizeGraduation`; `_seedRebalancing` detects the hostile pre-seed, executes `_pairRebalance` capped at `_swapBudget`, and — because the pre-seed exceeds the budget — the swap only partially corrects the ratio.
5. `_routerDepositAndDispose` deposits the remaining inventory via `router.addLiquidity(..., 1, 1, lpLock_, ...)` at the still-skewed post-swap ratio, locking the LP in `LPLock` at a price away from the curve's close price, to the attacker's benefit via their pre-existing LP shares.

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    /// @dev Deposit leg: add liquidity at the post-swap pool ratio via the
    ///      router. The router's `quote()`-based balanced split only pulls
    ///      the optimal amounts (no `min()` donation); off-ratio remainder
    ///      stays in this contract and is disposed: TOKEN burned here, LT
    ///      auto-swept to the owner by `finalizeGraduation`'s post-bookend.
    ///
    ///      `min0=1, min1=1` is intentional. Slippage protection on
    ///      `addLiquidity` exists to defend against a third party moving
    ///      the pool ratio between quote and execution; here we just set
    ///      the ratio ourselves in `_pairRebalance` in the same atomic
    ///      tx, so there's no third party to defend against. The `=1`
    ///      (rather than `=0`) trips V2 router's degenerate-ratio guard
    ///      so the call can't silently land at near-zero.
    ///
    ///      Approvals are reset to zero after `addLiquidity` returns.
    ///      The router only pulls the matched-ratio subset, so unconsumed
    ///      desired amounts leave a residual allowance — clearing it
    ///      keeps the no-dangling-allowance invariant tidy.

        address tokenAddress,
        address lt,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        BondingStorage storage $ = _s();
        address routerAddr = $.uniswapV2Router;
        address lpLock_ = $.lpLock;
        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
        // Subtract `protectedLT` (LT that doesn't belong to this graduation
        // — concurrent escrows or stray dust, snapshotted at the top of
        // `finalizeGraduation`) so the deposit allowance can never pull
        // another graduation's earmark or accidentally absorb dust into a
        // locked LP.
        uint256 ltBal = IERC20(lt).balanceOf(address(this));
        uint256 remLT = ltBal > protectedLT ? ltBal - protectedLT : 0;

        if (remToken > 0 && remLT > 0) {
            IERC20(tokenAddress).forceApprove(routerAddr, remToken);
            IERC20(lt).forceApprove(routerAddr, remLT);
            (,, liquidity) = IUniswapV2Router02(routerAddr)
                .addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp);
            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);
        }
