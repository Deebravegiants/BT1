### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop identity (`shopify-shop-domain` header) used to route the webhook to a tenant's handler is taken from an unauthenticated header and never enters the signed bytes.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely by calling `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [1](#0-0) 

The `hmac` and `to_signable_string` methods on `Request` show exactly what is protected by the signature: [2](#0-1) 

`to_signable_string` returns only `@raw_body`; `shop` (line 21-23) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header`, which is never mixed into the signed bytes. `HmacValidator.validate` in turn only recomputes and compares the digest over `to_signable_string`: [3](#0-2) 

The identity binding that should hold is:
`bytes_signed_by_Shopify == (raw_body, shop)` for the request that is authorized to act as shop `S`.

What is actually verified is:
`bytes_signed_by_Shopify == raw_body` only, while the `shop` value that the app's `WebhookMetadata.shop` (and therefore any per-tenant lookup/authorization in the host app) relies on comes from an **unsigned** header.

Because `Context.api_secret_key` (the app's `client_secret`) is a single shared secret used to sign webhook payloads for *every* shop that has the app installed, an HMAC computed for a payload delivered for shop A remains numerically valid for the exact same body regardless of which `shopify-shop-domain` header value accompanies it. The header is attacker-controlled input at the HTTP layer (the gem does not derive it from anything cryptographically tied to the signature), so nothing in this code proves the `shop` value the app relies on.

### Impact Explanation
An attacker who can capture (or self-generate, e.g. by installing the app on their own store) one valid `(raw_body, hmac)` pair can replay that exact request to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will build `WebhookMetadata` claiming the payload came from the victim shop, causing the host application to process/act on this body under the wrong tenant's identity. This breaks the shop-tenant authentication boundary that the whole webhook HMAC mechanism exists to enforce, matching a cross-tenant access impact.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to obtain at least one legitimately-signed webhook body for the target app (trivial if the attacker can install the app on their own store, since offline access/HMAC secret is shared per-app, not per-shop) and to be able to freely set the `shopify-shop-domain` header value when delivering to the app's public webhook endpoint, which any host consuming this gem's `Registry.process` allows since the header is only used for routing/metadata, not verified.

### Recommendation
Bind the shop identity into the signed material actually verified, e.g. reject/re-derive `shop` only from a value that Shopify has cryptographically bound (Shopify's own recommendation is that the HMAC is computed over the raw body sent for that specific delivery, so the app must not treat `shop`, `topic`, or other headers as trusted beyond "this exact body was signed by the API secret"); at minimum, document/enforce that consumers cannot rely on `request.shop`/`request.topic` for authorization decisions without additional binding, or extend `to_signable_string` to fail closed when the delivered body's declared topic/shop is inconsistent with any out-of-band registration expectations (e.g. compare against the webhook_id/topic combination that was registered for that specific shop's session) before dispatching to the handler.

### Proof of Concept
1. App is installed on attacker-owned shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H`, computed as `HMAC-SHA256(client_secret, B)`.
2. Attacker replays `POST /webhooks` to the target app with the same body `B`, same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` — identical to `H` — and passes: [4](#0-3) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` built from attacker-controlled body `B`, even though `B` was never authorized for `victim.myshopify.com`.
