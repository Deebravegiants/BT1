### Title
`PoaBridge.describeWithdrawal` matches by `nep141:<near_token_id>` only, ignoring `index` — status/txHash misreport for duplicate-token withdrawals in one batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`describeWithdrawal` looks up a withdrawal's status by `assetId` alone via `findMatchingWithdrawal`, never consulting `WithdrawalIdentifier.index`. When a batch contains two or more withdrawals of the same NEP-141 token, both indices poll the same NEAR tx hash and resolve to the *same* array entry, so the SDK can report `pending` for an index whose real transfer already completed, or attach the wrong `txHash` to an index once the other entry does complete.

### Finding Description
The broken equality: for two withdrawals of the same asset submitted atomically in one NEAR tx, the SDK should guarantee `describeWithdrawal({index: i}) ⇔ i-th signed withdrawal for that route`. Instead:

- `createWithdrawalIdentifier` [1](#0-0)  stores `index` in the `WithdrawalIdentifier` but that `index` is never used for matching.
- `describeWithdrawal` fetches all withdrawals for the shared NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) .
- `findMatchingWithdrawal` is a plain `.find()` keyed only by `nep141:<near_token_id> === assetId` [3](#0-2) , and the comment explicitly notes: "multiple withdrawals of the same token in a single transaction are not supported."

Because the POA status endpoint response is documented as unsorted ("Response list is unsorted, so we match by assetId instead of index"), when a batch has two same-asset withdrawals, both `describeWithdrawal({index:0,…})` and `describeWithdrawal({index:1,…})` issue the identical underlying `getWithdrawalStatus({withdrawal_hash: tx.hash})` call and apply the identical `.find()` predicate — so they always resolve to the *same* array element, regardless of which conceptual withdrawal (0 or 1) is actually being polled.

Concrete exploit flow:
1. An unprivileged caller composes a withdrawal batch with two entries for the same `assetId` (e.g., two BTC withdrawals) via `IntentsSDK.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`, which builds identifiers through `createWithdrawalIdentifiers` [4](#0-3)  — nothing rejects duplicate-asset batches.
2. `watchWithdrawal` polls `describeWithdrawal` independently for each index [5](#0-4) .
3. The real withdrawal at index 0 completes on-chain, while index 1 is still pending. The POA API returns both entries in one unsorted array. If the still-`PENDING` entry happens to be first, `.find()` returns it for **both** index-0 and index-1 queries — so the SDK keeps reporting `{status: "pending"}` for index 0 even though its transfer is already finalized on the destination chain.
4. Later, once index 1 also completes, `.find()` will deterministically return one of the two `COMPLETED` entries (order still unspecified) for both indices — so an integrator polling index 0 may receive index 1's `transfer_tx_hash`, and vice versa.

Existing guards do not prevent this: `validateWithdrawal`, `supports()`, `FeeExceedsAmountError`, `getUnderlyingFee`, and the on-chain intents contract's signature/nonce checks all operate on intent correctness and fee math, not on POA off-chain status attribution, and none of them enforce uniqueness of `assetId` within a batch or bind `WithdrawalIdentifier.index` into the POA lookup.

### Impact Explanation
An integrator that keys its ledger by the `(status, txHash)` returned per index can (a) treat a genuinely completed withdrawal as `pending` indefinitely and manually re-send/refund it — a double payout — or (b) record the wrong destination `txHash` against the wrong internal withdrawal record once both complete, breaking reconciliation and enabling a double-credit/refund. This matches the High-severity category: "a status or hash misreport making an integrator credit or refund twice." The bug is fully repeatable any time a batch contains ≥2 withdrawals for the same POA-bridge asset.

### Likelihood Explanation
Preconditions: only that a caller (ordinary user or an integrator forwarding user-supplied `withdrawalParams[]`) submits ≥2 withdrawals for the same `assetId` routed through `PoaBridge` in one call. No privileged access, no reliance on a malicious relayer/RPC — only normal, permitted batch composition. Attacker cost is a single normal withdrawal request; it is trivially repeatable for any POA-bridge-supported asset.

### Recommendation
Make `findMatchingWithdrawal` index-aware for same-asset withdrawals: filter POA API `withdrawals` by matching `assetId` first, then disambiguate among same-asset entries deterministically (e.g., sort matches by `data.amount` and pair with same-asset `withdrawalParams` sorted by amount, as the existing comment suggests), or reject/serialize batches containing duplicate `assetId` for the same route at `createWithdrawalIdentifiers`/`supports()` time until the POA API supports per-withdrawal correlation.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock the status endpoint to return two entries for the same `near_token_id`/`assetId`, one `PENDING` and one `COMPLETED` with `transfer_tx_hash: "hash-completed"`, in an order where `PENDING` is first in the array.
2. Call `bridge.describeWithdrawal({ index: 0, withdrawalParams: { assetId: A, ... }, tx })` and `bridge.describeWithdrawal({ index: 1, withdrawalParams: { assetId: A, ... }, tx })`.
3. Assert the broken equality: both calls return `{ status: "pending" }` — i.e. `result0 === result1` — even though the underlying data proves one of the two real withdrawals is `COMPLETED`. The correct behavior would require `result0` and `result1` to independently reflect their own withdrawal's real status/hash, which the current implementation cannot produce since it has no index-based disambiguation.
4. Swap the array order (COMPLETED first) and show both indices now flip to `{ status: "completed", txHash: "hash-completed" }`, demonstrating that the returned `txHash` is not stably bound to either index.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
