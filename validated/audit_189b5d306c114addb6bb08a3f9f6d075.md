### Title
XRPL X-address embedded destination tag is never decoded or reconciled against a separately-supplied `destinationMemo`, allowing a signed withdrawal memo with mismatched tags - ([File: packages/intents-sdk/src/lib/validateAddress.ts], [File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts], [File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts])

### Summary
`validateAddress` accepts XRPL X-addresses (which encode a classic address + destination tag) via `xrp_isValidXAddress`, but nowhere in the PoA withdrawal path is that embedded tag ever decoded. `PoaBridge.validateWithdrawal`'s `requireDestinationTag` check only inspects the truthiness of a separately supplied `args.destinationMemo`, and `createWithdrawIntentPrimitive`/`createWithdrawMemo` place the raw X-address string and the raw `destinationMemo` into the signed memo unmodified and unreconciled.

### Finding Description
The broken equality is: **tag encoded in the validated `destinationAddress` (T1) == tag actually signed into the withdrawal memo (T2, from `destinationMemo`)**.

- `validateXrpAddress` in `packages/intents-sdk/src/lib/validateAddress.ts:333-335` accepts either a classic address or an X-address (`xrp_isValidClassicAddress(address) || xrp_isValidXAddress(address)`), but never extracts/returns the tag embedded in an X-address.
- `PoaBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:232-257`) only checks `requireDestinationTag && !args.destinationMemo` — it never decodes the X-address to compare its embedded tag with `args.destinationMemo`. If `destinationMemo` is truthy for any reason (including an attacker-/counterparty-supplied value unrelated to the X-address), the check passes regardless of what tag the X-address actually encodes.
- `createWithdrawIntentPrimitive` → `createWithdrawMemo` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts:6-49`) builds the signed memo as `WITHDRAW_TO:<receiverAddress>[:<xrpMemo>]` using the **raw, un-decoded** `destinationAddress` string and the raw `destinationMemo`. If `destinationAddress` is an X-address encoding tag T1 and `destinationMemo` is T2 (T2 != T1), the resulting signed memo literally contains both an X-address whose canonical form implies T1 and an explicit tag T2, with no code path ever comparing or reconciling the two.

Existing guards do not catch this: `validateAddress` only checks format, `compareAddresses` is for token-address collision, and `requireDestinationTag` never decodes the X-address's tag at all — so there is no code anywhere in this repo that computes T1 from the X-address to compare against T2.

### Impact Explanation
The withdrawal intent is signed with a memo carrying an ambiguous/conflicting destination-tag signal (raw X-address possibly implying T1, explicit `destinationMemo` T2). Depending on how the tag is ultimately interpreted downstream, funds can be sent without the tag the account actually requires, or with the wrong tag, resulting in funds landing in an exchange's omnibus account without the correct tag attribution — a withdrawal stuck until manual intervention, matching the **High** impact category. This is repeatable on every XRPL PoA withdrawal call where a caller (end user or an integrator forwarding counterparty-supplied `destinationAddress`/`destinationMemo` strings) supplies an X-address alongside an independent `destinationMemo`.

### Likelihood Explanation
Preconditions: an XRPL PoA withdrawal where the caller supplies a valid X-address as `destinationAddress` (which `validateAddress` happily accepts) and a differing `destinationMemo`. No special privilege is needed — any SDK caller, or any counterparty string forwarded by an integrator, can trigger this in one call. The bug is deterministic and always reproducible given these inputs; it does not depend on RPC/bridge trust assumptions to demonstrate at the SDK layer, since the divergence is fully visible in the signed memo constructed by `createWithdrawIntentPrimitive`.

### Recommendation
- Decode X-addresses in `validateAddress`/`validateWithdrawal` using `ripple-address-codec`'s `xAddressToClassicAddress` to extract the embedded classic address and tag.
- Normalize `destinationAddress` to the classic address before it is placed into the withdrawal memo, and derive `destinationMemo` from the X-address tag when present.
- If both an X-address-embedded tag and an explicit `destinationMemo` are supplied and they differ, reject the withdrawal with a explicit error instead of silently signing an ambiguous memo.
- Update `requireDestinationTag` logic in `PoaBridge.validateWithdrawal` to check the decoded tag (from either source) rather than only `args.destinationMemo`'s truthiness.

it("signs a memo with conflicting X-address tag and destinationMemo without reconciliation", async () => {
  const bridge = new PoaBridge({
    envConfig: configsByEnvironment.production,
    xrplRpcUrls: configureXrplRpcUrls(PUBLIC_XRPL_RPC_URLS, {}),
  });

  vi.mocked(poaBridge.httpClient.getSupportedTokens).mockResolvedValueOnce({
    tokens: [{ intents_token_id: "nep141:xrp.omft.near", min_withdrawal_amount: "1",
      standard: "", near_token_id: "", asset_name: "", decimals: 0,
      min_deposit_amount: "", withdrawal_fee: "", defuse_asset_identifier: "a:m",
      origin_chain_address: "" }],
  });
  vi.mocked(xrpl.httpClient.getAccountInfo).mockResolvedValueOnce({
    account_data: { Account: "Account" },
    account_flags: { requireDestinationTag: true, depositAuth: false },
  });

  // X-address below encodes classic address + tag T1 (e.g. 111)
  const xAddress = "X7AcgcsBL6XDcUb289X4mJ8djcdyKaB5hJDWMArnXr61cqZ"; // encodes tag 111
  const conflictingMemo = "999"; // T2 != T1

  await expect(
    bridge.validateWithdrawal({
      assetId: "nep141:xrp.omft.near",
      amount: 5000n,
      destinationAddress: xAddress,
      destinationMemo: conflictingMemo,
    }),
  ).resolves.toBeUndefined(); // passes despite T1 != T2 mismatch

  const intent = createWithdrawIntentPrimitive({
    assetId: "nep141:xrp.omft.near",
    destinationAddress: xAddress,
    destinationMemo: conflictingMemo,
    amount: 5000n,
  });

  // Assert broken equality: memo carries raw X-address (implying T1) AND explicit T2,
  // with no reconciliation/decoding of the X-address's embedded tag.
  expect(intent.memo).toBe(`WITHDRAW_TO:${xAddress}:${conflictingMemo}`);
});

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	destinationAddress: string;
	destinationMemo: string | undefined;
	amount: bigint;
}): Extract<IntentPrimitive, { intent: "ft_withdraw" }> {
	const { contractId: tokenAccountId } = utils.parseDefuseAssetId(
		params.assetId,
	);
	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: tokenAccountId,
		amount: params.amount.toString(),
		memo: createWithdrawMemo({
			receiverAddress: params.destinationAddress,
			xrpMemo: params.destinationMemo,
		}),
		min_gas: MIN_GAS_AMOUNT,
	};
}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
