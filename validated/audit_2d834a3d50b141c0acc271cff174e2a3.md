### Title
Unprotected native-to-fee-token swap in `EvmHost.dispatch`/`fundRequest` uses `swapETHForExactTokens` with `msg.value` as implicit max-in, exposing dispatchers to sandwich/MEV extraction - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` each swap the caller's native token for the exact `feeToken` amount needed via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. This is the direct on-chain analog of the reported "unused slippage params" bug class: there is no independent slippage/price-bound check on the swap — the only "protection" is `msg.value` itself acting as `amountInMax`, and the deadline is `block.timestamp` (i.e., no real deadline protection either, since it is set at execution time, not chosen by the payer in advance to bound staleness).

### Finding Description
In [1](#0-0) , any unprivileged caller dispatching a POST request with native token payment triggers:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
The same pattern repeats for `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest` [3](#0-2) .

`swapETHForExactTokens` requires the caller to pass `amountInMax` as `msg.value` — this is exactly the amount the user chose to send, generally derived off-chain from the `HyperApp.quote()` helper, which itself explicitly warns it must not be used on-chain because it is sandwich-attack-prone: `getAmountsIn` in [4](#0-3)  and the docs explicitly state: *"Do not call `quote()` in smart contract transactions. It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks. Only use it off-chain for frontend fee estimation"* .

Because `EvmHost.dispatch` performs this swap unconditionally and unprivileged (any message dispatcher can trigger it just by sending `msg.value` with a POST/GET request), an MEV searcher observing a pending dispatch transaction in the mempool can front-run the AMM pool (e.g., via a large trade that moves the WETH/feeToken price), causing the victim's `swapETHForExactTokens` call to either:
1. Consume the caller's entire `msg.value` for the exact `post.fee` output (Uniswap V2's `swapETHForExactTokens` refunds only unused ETH, but if manipulated the caller may pay near or at their full `amountInMax`, extracting the price difference as MEV), or
2. Revert entirely (`INSUFFICIENT_INPUT_AMOUNT`/`EXCESSIVE_INPUT_AMOUNT`-style Uniswap V2 errors), griefing the dispatcher and burning gas, since the deadline (`block.timestamp`) offers no protection against price movement within the same block.

This differs from the SimplexPaymaster's `swapAndDeposit`, which *does* compute an oracle-derived `amountOutMin` and enforce a slippage bound [5](#0-4) , and from `UniV3UniswapV2Wrapper.swapExactTokensForETH`, which accepts a real `amountOutMin` parameter [6](#0-5) . `EvmHost.dispatch`, by contrast, has no independent minimum-output/maximum-price guard other than `msg.value` chosen ahead of time by an off-chain, sandwich-vulnerable `quote()` estimate.

### Impact Explanation
This is directly reachable by any unprivileged user or app dispatching a Hyperbridge message with native-token payment — the most common entry point into the protocol (`EvmHost.dispatch`, called by `HyperApp.dispatch{value: msg.value}` throughout the docs and SDK) [7](#0-6) . An MEV searcher can:
- extract value from every native-paid dispatch by sandwiching the pool used for the WETH→feeToken swap, effectively taxing dispatchers beyond the true fee cost, or
- cause dispatch reverts (denial of service / wasted gas) for time-sensitive cross-chain messages, delaying message delivery and relayer fee collection.

Because the fee token backs relayer compensation and protocol revenue accounting, systematically manipulated swaps also distort the fee actually collected by the protocol relative to what `feeToken()` is supposed to receive, though the router enforces the exact `post.fee` output is delivered (so the protocol itself is not underpaid) — the loss falls on the dispatching user/app, and repeated exploitation degrades the reliability of native-token dispatch across all `EvmHost` deployments (medium-severity value-extraction/griefing, not a direct protocol insolvency).

### Likelihood Explanation
High: this triggers on essentially any transaction that dispatches a Hyperbridge request paying in native token, which is normal, expected usage documented across the SDK/docs. No special conditions (privileged role, chain reorg, governance action) are required — only mempool visibility and enough capital to move the target AMM pool. The lack of a real slippage-tolerance parameter passed by the caller (only the implicit `msg.value` cap) makes exploitation a straightforward generalized MEV strategy against every dispatch call, matching the reported bug class.

### Recommendation
- Add an explicit `amountInMax`/slippage tolerance parameter (or per-config max acceptable native premium) to `DispatchPost`/`DispatchGet`/`fundRequest` payloads, distinct from `msg.value`, so the caller/app can bound the swap's execution price on-chain rather than relying on an off-chain `quote()` snapshot.
- Alternatively, route native payments through a mechanism (e.g., a TWAP-based or oracle-bounded price check similar to `SimplexPaymaster.swapAndDeposit`'s `amountOutMin` derivation) before calling `swapETHForExactTokens`, so manipulated pool prices cannot silently consume the payer's full `msg.value`.
- Consider requiring callers to pass a real deadline parameter rather than `block.timestamp`, and document/enforce a minimum acceptable refund threshold.

### Proof of Concept
1. Attacker observes a pending transaction calling `EvmHost.dispatch(DispatchPost)` (or `DispatchGet`/`fundRequest`) with `msg.value = X` intended to cover `post.fee` in `feeToken`, based on an off-chain `HyperApp.quote()` estimate.
2. Attacker front-runs with a large trade on the WETH/feeToken pool referenced by `_hostParams.uniswapV2`, moving the price so that `X` native tokens are now needed almost entirely (or insufficiently) to produce `post.fee` feeToken via `swapETHForExactTokens`.
3. The victim's transaction executes at the manipulated price: `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` either consumes far more of `X` than expected (attacker profits from the price impact via a back-run trade restoring the pool) or reverts (`UniswapV2: EXCESSIVE_INPUT_AMOUNT`/`INSUFFICIENT_LIQUIDITY`), wasting the dispatcher's gas and blocking timely message delivery.
4. Reference logic: [1](#0-0) .

    /**
     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

    function swapAndDeposit(address token, uint256 amountIn) external {
        if (msg.sender != treasury) revert UnauthorizedCall();

        if (router == address(0)) revert InvalidRouter(router);

        uint256 balance = IERC20(token).balanceOf(address(this));

    function swapExactTokensForETH(
        uint256 amountIn,
        uint256 amountOutMin,
        address[] calldata path,
        address to,
        uint256 deadline
    ) external returns (uint256[] memory) {
        address weth = _params.WETH;
        if (path[1] != weth) revert InvalidWethAddress();
        address token = path[0];

        IERC20(token).safeTransferFrom(msg.sender, address(this), amountIn);
        IERC20(token).forceApprove(_params.swapRouter, amountIn);

        IV3SwapRouter.ExactInputSingleParams memory params = IV3SwapRouter.ExactInputSingleParams({
            tokenIn: token,
            tokenOut: weth,
            fee: _params.maxFee,
            recipient: address(this),
            amountIn: amountIn,
            amountOutMinimum: amountOutMin,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactInputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 amountOut = abi.decode(results[0], (uint256));

        IWETH(weth).withdraw(amountOut);
        (bool sent,) = to.call{value: amountOut}("");
        if (!sent) revert RefundFailed();

        uint256[] memory amounts = new uint256[](2);
        amounts[0] = amountIn;
        amounts[1] = amountOut;

        return amounts;
    }
