### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` and compares it to the `hmac` value extracted from the request headers [1](#0-0) . Crucially, `Request#to_signable_string` only ever returns the raw request body — it never includes the `topic`, `shop-domain`, `api-version`, or `webhook-id` headers [2](#0-1) . The `hmac` itself is decoded straight from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [3](#0-2) , and `HmacValidator.validate_signature` simply compares that against `HMAC(api_secret_key, raw_body)` [4](#0-3) .

After this HMAC check passes, `Registry.process` reads `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` directly from the (unauthenticated) headers and forwards them unmodified into the `WebhookMetadata` struct handed to the app's handler [5](#0-4) . The `shop` field the handler code trusts (`data.shop`) is therefore a field acted upon (used to select/attribute the tenant) that is not covered by the HMAC — the binding "HMAC-verified request == request whose `shop` header the handler trusts" does not hold. Only the body bytes are signed; the header claiming which shop the webhook is "from" is not.

The `api_secret_key` used to sign webhooks is a single app-level secret, not a per-shop secret — the same key is used to sign webhooks for every shop that has installed the app [6](#0-5) . Consequently, a merchant/attacker who has installed the app on their own store can obtain a validly HMAC-signed `(raw_body, hmac)` pair from a legitimate webhook Shopify sends them, then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop's domain). Because `HmacValidator.validate` only checks `raw_body` against the HMAC and never checks that the `shop-domain` header is consistent with anything cryptographically bound to it, the forged request passes validation, and the handler receives `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (per `Webhooks::WebhookMetadata`) to look up per-shop state, credentials, sessions, or to key any tenant-scoped side effect (a common and encouraged pattern per the gem's own docs, which show `ShopifyAPI::Webhooks::Registry.process` as the canonical entry point and expose `shop` on the resulting metadata) [7](#0-6) , an attacker with a legitimate low-privilege install of the app can make the app believe a spoofed webhook body originated from a different, victim shop. This is a cross-tenant data confusion / cross-tenant access vector entirely reachable from this gem's own webhook-processing code (`Registry.process` → `Request#shop`/`#topic`/`#webhook_id` → `WebhookMetadata`), without needing the victim's or the app's `client_secret`/access token.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that has at least one other shop's install (which is the normal state for any multi-tenant Shopify app): the attacker needs only to be a legitimate merchant of the app (no elevated privilege) to capture one genuine `(body, hmac)` pair from their own store's webhook traffic, and then can freely relay that pair against the app's webhook endpoint with a forged `shop-domain` header, since no part of the validation binds the header to the signature.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable payload verified by the HMAC, or otherwise cryptographically bind the claimed shop to the signed body (e.g., verify the `shop-domain` header against a shop the app has an active/known session for, in addition to the raw HMAC check) before constructing `WebhookMetadata` and dispatching to handlers in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`; attacker captures a legitimate webhook POST Shopify sends them, including the raw body and the `x-shopify-hmac-sha256` value (both valid, since `HmacValidator` signs only `raw_body` with the single app `api_secret_key`) [4](#0-3) .
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Request.new` accepts the request (all required headers present) [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC [9](#0-8) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-forged `shop-domain` header and invokes the app's handler with it [10](#0-9) , causing the handler to process attacker-controlled body content attributed to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
