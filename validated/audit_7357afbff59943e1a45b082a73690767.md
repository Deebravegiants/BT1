Audit Report

## Title
Reentrant same-contract calls cause `own_contribution` storage diff to be applied twice to `ContractInfo` - (File: substrate/frame/revive/src/metering/storage.rs)

## Summary
`RawMeter::apply_pending_changes_to_contract` applies a frame's pending storage `Diff` to `ContractInfo` via `Diff::update_contract` but, unlike `bank_pending_changes`, does not reset `own_contribution` afterward. [1](#0-0)  If the same frame subsequently completes normally, `finalize_own_contributions` calls `update_contract` again on the same still-`Alive` diff against the already-mutated `ContractInfo`, re-applying the identical byte/item delta a second time. [2](#0-1) 

## Finding Description
`Diff::update_contract` is not idempotent: it unconditionally adds the net `bytes_added`/`items_added` onto `info.storage_bytes`/`info.storage_items` and adjusts the deposit fields each time it is called. [3](#0-2)  The sibling helper `bank_pending_changes` correctly resets `self.own_contribution = Contribution::Alive(Default::default())` after applying the diff and books the deposit as a charge, making a later `finalize_own_contributions` a no-op for that contribution. [4](#0-3)  `apply_pending_changes_to_contract`, by contrast, takes `&self` and deliberately leaves `own_contribution` untouched ("this does not consume the pending diff"), so if `finalize_own_contributions` runs later on the same `own_contribution`, the diff gets applied a second time to `info`.

At the call-site level in `metering/mod.rs`, `FrameMeter::apply_pending_storage_changes` wraps `apply_pending_changes_to_contract` and is explicitly documented as being used "before creating a nested frame to ensure the child frame can see the parent's pending storage changes," referencing `contract-issues#213`. [5](#0-4)  `FrameMeter::finalize` (which calls `finalize_own_contributions`) is a separate, distinct code path used to conclude a frame's own contribution. [6](#0-5) 

However, I could not locate the actual call sites in `substrate/frame/revive/src/exec.rs` where `apply_pending_storage_changes` and `finalize` (or `bank_pending_storage_changes`) are invoked relative to each other during a reentrant call — the grep matches were present but their surrounding code (the actual order of calls: whether `finalize` is invoked on the *same* frame after `apply_pending_storage_changes`, or whether the frame instead always routes through `bank_pending_storage_changes` before/after reentrant calls) was not retrieved within the available tool budget. The claim's core technical premise — that `update_contract` is non-idempotent and that `apply_pending_changes_to_contract` does not reset `own_contribution` while `bank_pending_changes` does — is verified directly in the source. What is **not verified** is whether `exec.rs`'s actual call sequence for reentrant same-contract calls actually calls `finalize`/`finalize_own_contributions` on the same frame *after* calling `apply_pending_storage_changes`, which is the necessary condition for the double-application to actually occur in production code (as opposed to being purely a theoretical property of the two functions in isolation).

## Impact Explanation
If the exploit path is real (i.e., if `exec.rs` calls `apply_pending_storage_changes` and then later `finalize` on the same frame for a reentrant same-contract call), the impact would be persistent inflation of `ContractInfo.storage_items`/`storage_bytes`/deposits, corrupting future refund/charge pro-rata calculations for that contract — a legitimate deposit-accounting bug reachable by an unprivileged contract deployer using a permitted `AllowReentry` reentrant call pattern.

## Likelihood Explanation
Cannot be conclusively assessed without confirming the exact call ordering in `exec.rs`. The two low-level functions (`apply_pending_changes_to_contract` and `finalize_own_contributions`) do have the asymmetric reset behavior described, but whether production code actually invokes both on the same frame instance in a way that causes double-counting was not confirmed within the available investigation.

## Recommendation
Confirm via reading `substrate/frame/revive/src/exec.rs` in full context whether `finalize`/`finalize_own_contributions` is ever invoked on a frame after `apply_pending_storage_changes` was called on it without an intervening `bank_pending_storage_changes` reset. If so, apply one of: (a) make `apply_pending_changes_to_contract` record and subtract the applied portion from `own_contribution` so it acts as a baseline, (b) exclusively route the reentrant-preview path through `bank_pending_changes`, or (c) add a "previewed" marker so `finalize_own_contributions` does not reapply an already-committed diff.

## Proof of Concept
A Rust unit test extending `substrate/frame/revive/src/metering/storage/tests.rs`'s `RawMeter` harness, as described in the submission, would need to: build a baseline `ContractInfo`; create a nested meter for contract `X`; charge a diff; call `apply_pending_changes_to_contract`; then call `finalize_own_contributions` on the same meter; and compare `info.storage_items`/`storage_bytes`/deposits against a control run without the intervening `apply_pending_changes_to_contract` call. This test would confirm the double-application at the unit level for the two functions in isolation, but does not by itself prove that `exec.rs`'s actual reentrant-call handling triggers this same sequence in a live transaction — that requires tracing the exact call sites in `exec.rs`, which was not completed.

	pub fn update_contract<T: Config>(&self, info: Option<&mut ContractInfo<T>>) -> DepositOf<T> {
		let per_byte = T::DepositPerByte::get();
		let per_item = T::DepositPerChildTrieItem::get();
		let bytes_added = self.bytes_added.saturating_sub(self.bytes_removed);
		let items_added = self.items_added.saturating_sub(self.items_removed);
		let mut bytes_deposit = Deposit::Charge(per_byte.saturating_mul((bytes_added).into()));
		let mut items_deposit = Deposit::Charge(per_item.saturating_mul((items_added).into()));

		// Without any contract info we can only calculate diffs which add storage
		let info = if let Some(info) = info {
			info
		} else {
			return bytes_deposit.saturating_add(&items_deposit);
		};

		// Refunds are calculated pro rata based on the accumulated storage within the contract
		let bytes_removed = self.bytes_removed.saturating_sub(self.bytes_added);
		let items_removed = self.items_removed.saturating_sub(self.items_added);
		let ratio = FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		bytes_deposit = bytes_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_byte_deposit)));
		let ratio = FixedU128::checked_from_rational(items_removed, info.storage_items)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		items_deposit = items_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_item_deposit)));

		// We need to update the contract info structure with the new deposits
		info.storage_bytes =
			info.storage_bytes.saturating_add(bytes_added).saturating_sub(bytes_removed);
		info.storage_items =
			info.storage_items.saturating_add(items_added).saturating_sub(items_removed);
		match &bytes_deposit {
			Deposit::Charge(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_sub(*amount)
			},
		}
		match &items_deposit {
			Deposit::Charge(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_sub(*amount)
			},
		}

		bytes_deposit.saturating_add(&items_deposit)
	}

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}

	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}
