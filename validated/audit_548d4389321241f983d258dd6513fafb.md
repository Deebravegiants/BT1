### Title
POA Bridge withdrawal status matched only by `assetId` causes cross-reporting of completion status/txHash between distinct withdrawals in a batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a withdrawal by looking up the bridge's response list using only the `assetId`, not the withdrawal's `index`/amount/destination. When a batch withdrawal intent contains two or more withdrawals of the same asset (e.g. two payouts of the same token to different destination addresses in one intent), `findMatchingWithdrawal` will return the *first* matching record for every lookup, so a completed withdrawal's `txHash`/status can be reported for a different, still-pending (or failed) withdrawal at another index.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which finds a withdrawal purely by comparing `nep141:${w.data.near_token_id} === assetId`: [1](#0-0) [2](#0-1) 

The code comment explicitly acknowledges the gap: "multiple withdrawals of the same token in a single transaction are not supported," attributing it to a POA API limitation, but the SDK does not guard against this case — it silently returns whatever withdrawal record it finds first as `{status:"completed", txHash: ...}` regardless of which array index actually produced it.

The identical pattern exists in the sibling implementation used for the alternate completion-tracking API: [3](#0-2) 

This status is consumed by `watchWithdrawal`/`createWithdrawalCompletionPromises`, which resolve per-index promises directly from this status without any additional verification (amount, destination) that the reported completion belongs to that specific index: [4](#0-3) 

The equality broken here is: *the withdrawal-completion status/hash reported for index `i` is not necessarily the on-chain outcome of the withdrawal actually initiated at index `i`.* Two distinct withdrawal legs (different destination addresses and/or amounts) can be conflated because they share only the `assetId` key.

### Impact Explanation
An integrator using `sdk.createWithdrawalCompletionPromises` or `waitForWithdrawalCompletion` for a batch of same-asset withdrawals could:
- Have `promises[0]` and `promises[1]` (or more) both resolve with the same `txHash`/`completed` status even though only one of the underlying withdrawals actually settled on-chain, leading the integrator to credit/mark-as-completed two distinct payouts (to two different destination addresses) based on a single real completion — a double-credit/double-settlement misreport.
- Conversely, cause a genuinely completed withdrawal at index `1` to be reported as `pending`/`failed` because the matcher greedily returns the first record for index `0`'s lookup, and the second lookup for the same `assetId` returns the same first record again (since `Array.prototype.find` is not consuming/removing matched items), never surfacing the second withdrawal's real record.

This matches the class of "status reported that is not the on-chain outcome," which per the given impact classification can make an integrator credit or refund twice.

### Likelihood Explanation
Requires only that a caller construct a batch withdrawal intent containing two or more withdrawal legs with the same `assetId` (e.g., splitting one asset to two destination addresses) — a legitimate, unprivileged usage pattern explicitly supported by the SDK's batch-withdrawal/array-of-promises design (see `docs/design/rfc-batch-withdrawal-granular-control.md`) and not blocked by any validation in `PoaBridge` or `sdk.ts`. No malicious actor or privileged party is needed; the ambiguity manifests for any ordinary caller who batches two same-asset withdrawals through the POA route.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate between multiple same-asset withdrawal records — e.g., match by `(assetId, destinationAddress, amount)` or, if the POA API cannot yet disambiguate, explicitly reject/validate batch withdrawal params containing duplicate `assetId`s at intent-construction time so integrators cannot silently rely on ambiguous per-index status.

### Proof of Concept
1. Build a withdrawal intent with `withdrawalParams = [{assetId: "nep141:btc.omft.near", amount: A, destinationAddress: X}, {assetId: "nep141:btc.omft.near", amount: B, destinationAddress: Y}]` and submit via `sdk.signAndSendWithdrawalIntent`/`processWithdrawal`.
2. Call `sdk.createWithdrawalCompletionPromises({ intentTx, withdrawalParams })`.
3. Suppose only the withdrawal to `X` settles on-chain (POA bridge response contains one `COMPLETED` record with `near_token_id = btc.omft.near`); the withdrawal to `Y` is still `PENDING` on-chain.
4. `PoaBridge.describeWithdrawal` is invoked independently for index 0 and index 1; both calls run `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the same `COMPLETED` record for both, per [5](#0-4) .
5. Both `promises[0]` and `promises[1]` resolve with `{status:"completed", txHash: <X's tx>}`, so the integrator marks the payout to `Y` as completed and credits accordingly, even though `Y` has not yet (or may never) receive funds.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
