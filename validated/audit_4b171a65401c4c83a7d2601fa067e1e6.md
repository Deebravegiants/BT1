### Title
Accrued RAY value can exceed `i128` before the index cap and permanently freeze a market - ([File: common/src/rates/simulate.rs](https://example.com))

### Summary
A market whose scaled debt or supply value grows beyond `i128::MAX` causes every accrual-first operation to revert with `MathOverflow`, permanently freezing withdrawals, repayments, liquidations, and index updates for that market. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` first expands `borrowed * borrow_index` and `supplied * supply_index` into RAY-denominated `i128` values through `scaled_to_original`. [3](#0-2)  It later repeats the debt expansion at both the old and new borrow indexes in `calculate_supplier_rewards`. [4](#0-3) 

The configured `MAX_BORROW_INDEX_RAY` bounds the index itself, but it does not bound the market-specific product `borrowed * index / RAY`; therefore a large market can cross the `i128` value ceiling while the stored index is still below its nominal cap. [5](#0-4) [6](#0-5) 

Every pool mutation loads a synced market before accounting, and `update_indexes` uses the same accrual path, so once either aggregate expansion overflows there is no ordinary path that skips the failing multiplication. [2](#0-1) [7](#0-6) 

### Impact Explanation
This permanently freezes supplier principal and yield in the affected market because `withdraw`, `repay`, `supply`, `borrow`, `flash_loan`, `recapitalize`, `claim_revenue`, liquidation pool legs, and explicit index updates all depend on successful accrual. [2](#0-1) [8](#0-7) 

The regression test demonstrates that after the overflow, both `withdraw` and `repay` fail with `MathOverflow`; because ledger time cannot move backward, the condition is persistent rather than a transient liquidity rejection. [9](#0-8) 

### Likelihood Explanation
The trigger requires a very large market and sustained interest accrual, but it is reachable through normal `supply` and `borrow` usage when governance-configured caps permit the position size and the configured rate curve permits sufficient index growth. [10](#0-9) [11](#0-10) 

The repository’s own scenario uses an 18-decimal market with one billion whole tokens, 98% utilization, and a steep but otherwise accepted rate curve; repeated yearly accrual reaches the RAY-value ceiling before the static index cap. [12](#0-11) 

### Recommendation
Make accrual value arithmetic wide-end-to-end or bound indexes by the market’s maximum representable scaled value before multiplying. [13](#0-12) 

At minimum, compute utilization and debt/supply deltas using `I256`, or derive per-market dynamic index ceilings that guarantee `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` fit in `i128`. [14](#0-13) [4](#0-3) 

The saturation behavior should stop index growth at the dynamic ceiling and continue processing exits and repayments instead of raising `MathOverflow` during accrual. [5](#0-4) [2](#0-1) 

### Proof of Concept
1. Configure an 18-decimal market with a supply/borrow cap large enough for one billion whole tokens and the steep rate curve used by the repository test: 175% maximum borrow APR, 75% optimal utilization, and 20% reserve factor. [10](#0-9) 
2. Through the controller, `supply` `1_000_000_000 * 10^18` base units to the market. [15](#0-14) 
3. Supply collateral in another market and `borrow` `980_000_000 * 10^18` base units, leaving the first market at 98% utilization. [16](#0-15) 
4. Advance ledger time and call `update_indexes` until `borrowed * borrow_index / RAY` exceeds `i128::MAX`; the test reaches this while `borrow_index < MAX_BORROW_INDEX_RAY`. [17](#0-16) 
5. Call `withdraw` for one base unit or `repay` for one whole token; both revert with `MathOverflow` before their accounting runs because each first calls `global_sync`. [2](#0-1) [18](#0-17)

```rust
pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {

    cache
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
