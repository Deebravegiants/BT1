Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing domain-boundary check - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway's `isAllowedOrigin` function matches wildcard CORS allowlist entries (e.g. `https://*.ethereum.org`) using `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, without requiring a `.` boundary before the matched suffix. This allows an attacker who registers a suffix-colliding domain (e.g. `evilethereum.org`) to be treated as an allowed origin, causing the gateway to reflect `Access-Control-Allow-Origin` for an untrusted origin.

## Finding Description
In `isAllowedOrigin`, wildcard host entries are matched with a raw suffix comparison: [1](#0-0)  This strips `*.` from `*.ethereum.org` to get `ethereum.org`, then checks `strings.HasSuffix(originHost, "ethereum.org")`. This is true for `remix.ethereum.org` (intended) but also for `evilethereum.org` or `notethereum.org` (unintended), since no domain separator is required before the matched suffix. The exact host/scheme/port pre-checks earlier in the function do not add a boundary check for the wildcard branch: [2](#0-1) 

This function is invoked directly on the `Origin` header of every incoming request when CORS is enabled, and on a match reflects the attacker-controlled origin back into `Access-Control-Allow-Origin`: [3](#0-2) 

The existing test suite for this behavior only exercises the negative case of a different TLD/domain that shares no suffix collision (`https://ethereum.remix.org` vs `*.ethereum.org`), not the suffix-substring case, so the gap is untested: [4](#0-3) 

## Impact Explanation
CORS allowlists are a security boundary preventing arbitrary websites from having their cross-origin requests' responses read by browser JavaScript. This flaw allows an attacker who controls a domain sharing a suffix with an allowlisted wildcard pattern to bypass that boundary and be granted `Access-Control-Allow-Origin` privileges, letting a victim's browser leak gateway response data to the attacker's page. This is a concrete allowlist-bypass / cross-origin response exposure at the gateway, matching the in-scope "allowlist bypass" / "gateway request impersonation" impact category.

## Likelihood Explanation
Exploitation requires only that the operator configure a wildcard entry in `CORSAllowedOrigins` — a documented, supported configuration option (see `core/scripts/gateway/sample_config.toml`) — and that the attacker register/control a domain sharing the suffix without the separating dot (e.g. `evilethereum.org` for `*.ethereum.org`). Domain registration is trivial, requires no privileged access to any Chainlink node, and the attack is fully repeatable against any gateway deployment using wildcard CORS entries.

## Recommendation
Require a boundary check when matching wildcard hosts by comparing against the suffix including the leading dot, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // keep leading "."
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures `evilethereum.org` no longer matches `*.ethereum.org` while `remix.ethereum.org` still does.

## Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the gateway endpoint with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the boundary-unaware suffix match in `isAllowedOrigin` at `core/services/gateway/network/httpserver.go:184-190` incorrectly allows a non-subdomain, suffix-colliding origin. This can be added as a new Go test case in `httpserver_test.go` alongside `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, asserting `Access-Control-Allow-Origin` is set for `https://evilethereum.org` against allowlist `https://*.ethereum.org` (currently it would incorrectly pass, proving the bug).
