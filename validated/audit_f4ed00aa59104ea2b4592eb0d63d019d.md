### Title
Unbounded escrow crediting for fee-on-transfer tokens in Tron IntentGatewayV2.placeOrder allows draining other users' escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrow credit for input tokens from the user-specified `order.inputs[i].amount` (minus protocol fee), but pulls the actual tokens via a single `safeTransferFrom` without verifying how many tokens the contract actually received. For fee-on-transfer ERC20 tokens, the amount received is less than `order.inputs[i].amount`, so the internal `_orders` accounting mapping is overcredited relative to the contract's real token balance — the same root cause as the referenced "Cally" fee-token bug, applied to Hyperbridge's intents escrow.

### Finding Description
In `placeOrder` on the Tron gateway [1](#0-0) , `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the amount the caller *claims* to be sending), with a protocol-fee deduction — it never inspects the actual token balance received by the contract.

In the non-predispatch branch, tokens are pulled with a plain `safeTransferFrom` and the escrow mapping is incremented unconditionally by the *reduced but not fee-adjusted* amount: [2](#0-1) 

This is in stark contrast to the mainline EVM `IntentGatewayV2.sol`, which was explicitly hardened against fee-on-transfer tokens: it snapshots `balanceOf` before and after `safeTransferFrom`/sweeps and mutates `order.inputs[i].amount` to the *actual received* delta before computing the commitment and crediting escrow: [3](#0-2) [4](#0-3) 

The predispatch branch on Tron has the same flaw — it only checks `balance < requiredAmount` and computes `dust = balance - requiredAmount` for excess, but never reduces `reducedInputs[i].amount` (used for escrow crediting) when the received amount is less than requested: [5](#0-4) 

Because `_orders[commitment][token]` is the accounting ledger used by `withdraw()` (called from `cancelOrder`, `fillOrder`/`IntrinsicIntents`, and `onAccept` for `RedeemEscrow`/`RefundEscrow`) to release tokens, any order placed with a fee-on-transfer token results in the ledger being credited for more tokens than the contract actually holds for that token. The `_orders` mapping is a shared pool keyed by `(commitment, token)`, but the underlying ERC20 balance of the gateway contract is a single shared pot across all commitments for that token. Once one order overcredits itself, a subsequent legitimate order/withdrawal for the same token can be starved of funds — i.e., the contract becomes insolvent for that token, exactly mirroring the Cally vault scenario where an attacker can "self-serve" the shortfall by creating and then cancelling/withdrawing their own order to extract tokens that rightfully belong to other users' escrows.

### Impact Explanation
This directly causes loss of user funds / permanent freezing of funds: legitimate solvers or the order owner may be unable to withdraw the full escrowed amount because the contract's real balance of the fee-on-transfer token is less than what `_orders` claims to hold. An attacker who is aware that a token used in an order is fee-on-transfer can front-run/exploit this by creating their own order with the same token and immediately cancelling (same-chain path calls `withdraw` synchronously), extracting real tokens funded by the shortfall left over from other users' orders, since the mapping bookkeeping (not real balance) governs how much each commitment can withdraw. This satisfies "concrete theft or permanent freezing of funds" via the unprivileged, single-transaction `placeOrder`/`cancelOrder` path.

### Likelihood Explanation
Reachable by any unprivileged user who submits a `placeOrder` transaction with a fee-on-transfer ERC20 as the input token — no special privileges required. The mainline `evm/src/apps/IntentGatewayV2.sol` was already patched for this exact class of bug (as shown by the explicit fee-on-transfer handling and dedicated tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), indicating the team recognizes this bug class as real and reachable; the Tron fork simply lacks the same fix, making exploitation only dependent on finding/deploying (or using an existing) fee-on-transfer token on the Tron deployment.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure the gateway's actual token balance before and after each `safeTransferFrom` (and after predispatch sweep transfers), and use the delta — not the caller-specified `order.inputs[i].amount` — as the basis for `reducedInputs`, the commitment hash, and the `_orders` escrow credit. This ensures the escrow ledger never exceeds the contract's real token holdings.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) on the Tron-deployed `IntentGatewayV2`.
2. User A calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`. The gateway calls `safeTransferFrom(A, this, 1000e18)` but only receives 990e18 due to the fee [6](#0-5) . `_orders[commitmentA][FOT]` is nonetheless credited with `reducedInputs[0].amount` computed from the full 1000e18 (minus protocol fee), i.e., more than the 990e18 actually held.
3. Attacker observes this and places their own order with the same FOT token, then immediately calls `cancelOrder` (same-chain path) to trigger `withdraw`, extracting tokens funded by the shortfall belonging to User A's escrow.
4. When User A's order is later filled/cancelled, `withdraw` attempts to pay out the full credited (uncorrected) amount, but the contract's real FOT balance is insufficient, causing either a revert (permanent freeze of User A's funds) or, if other orders' balances cover the gap, silent draining of other users' escrowed tokens.
