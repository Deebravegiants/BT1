### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-covered material. `Registry.process` validates only that HMAC (body-only) and then trusts the unauthenticated `shop` header value to route the payload as the tenant identity passed to the app's webhook handler.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. The `shop` accessor, however, is read straight from an attacker-controllable header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` verifies the HMAC of the body via `Utils::HmacValidator.validate(request)`, and — once that (body-only) check passes — forwards `request.shop` unchecked to the handler as the tenant-identifying field: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e., only the body, using the single, app-wide `api_secret_key` shared across every shop that installs the app: [4](#0-3) 

This breaks the identity binding: `shop header authenticated by HMAC` should equal `shop used to route the webhook payload`, but in fact `hmac covers {body}` while `handler routing key = header["shop-domain"]`, which is never included in the signed bytes.

Because the `api_secret_key` is one value per app (not per shop), any unprivileged internet user who installs the app on their **own** Shopify development/trial store can capture a fully valid, correctly-HMAC'd webhook delivery (body + `x-shopify-hmac-sha256`) for their own tenant. Since the HMAC never covers the `shop-domain` header, that attacker can replay the identical `raw_body`/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain (and freely choosing `topic`/`webhook-id`, which are likewise unsigned). `Registry.process` will accept the forged request as valid (HMAC still matches, since it only checks the body) and hand it to the topic handler labeled with the victim's shop.

### Impact Explanation
This meets the Critical bar of "cross-tenant access": the webhook processing pipeline in this gem authenticates only the payload bytes, not the tenant claim it exposes to the app (`WebhookMetadata#shop`). Any application that uses `shop`/`WebhookMetadata` to look up or mutate per-merchant state (the very purpose this field is exposed for) can be made to act on forged data attributed to a different, victim shop, using only credentials the attacker already legitimately possesses for their own store — no access to the victim's tokens or the app's `client_secret` is required.

### Likelihood Explanation
Likelihood is high for any deployer of this gem's webhook handling: the attack requires no privileged knowledge beyond installing the target app on any real/dev shop the attacker controls (a normal, low-barrier action for a "public app"), capturing one webhook delivery, and replaying it with a modified header. No secret material needs to be recovered or guessed.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise verify it out-of-band before trusting it:
- Require callers of `Registry.process` to supply the expected/registered shop for the webhook, and reject when it doesn't match a previously known/authorized shop (e.g., cross-check against a `SessionStorage`-resolved shop) instead of trusting the raw header value directly, and/or
- Extend `VerifiableQuery`/`to_signable_string` for `Webhooks::Request` to explicitly acknowledge that `shop`, `topic`, and `webhook_id` are **not** authenticated by the HMAC, and document/require that consuming apps perform an authoritative shop lookup (e.g., confirm they hold an active session for that shop) before trusting `WebhookMetadata#shop` for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (an ordinary, unprivileged action requiring no special credentials).
2. Shopify sends the attacker's app endpoint a legitimate webhook, e.g. for `orders/create`, with:
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `raw_body` only) and finds it matches — validation succeeds since `shop-domain` was never part of the signed bytes: [3](#0-2) 
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)`, and any tenant-scoped logic in the host app now processes attacker-supplied data as if it came from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
