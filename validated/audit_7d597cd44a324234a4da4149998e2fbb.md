### Title
Response cache key omits `WorkflowID`, allowing cross-workflow disclosure of cached HTTP responses within the gateway `v2` HTTP capability handler - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `v2` HTTP-action response cache (`core/services/gateway/handlers/capabilities/v2/response_cache.go`) is documented as being "scoped by workflow ID to prevent cross-workflow data leakage" (per `core/services/gateway/handlers/capabilities/v2/README.md`), but the actual cache key generated by `gateway_common.OutboundHTTPRequest.Hash()` does not include `WorkflowID` at all, as proven by the handler's own test suite. This mirrors the filebrowser bug class: a documented/intended access-scoping guarantee ("Workflow Isolation") is not actually enforced by the code path that serves cached content, so one principal can receive content that was fetched/cached on behalf of a different scope.

### Finding Description
The cache is a package-level, non-per-workflow map keyed by `req.Hash()`: [1](#0-0) [2](#0-1) 

The doc comment claims the key is derived from "method, URL, headers, body, workflowOwner": [3](#0-2) 

But the handler's own unit tests explicitly assert that two requests differing only by `WorkflowID` produce the **same** hash (i.e., collide in the cache), while requests differing by `WorkflowOwner` produce different hashes: [4](#0-3) [5](#0-4) 

This directly contradicts the `README.md`'s stated design goal that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage": [6](#0-5) 

The cache is invoked from the untrusted node-message path `makeOutgoingRequest`, which is reachable whenever a workflow DON node sends an outbound HTTP action request (`gateway_common.MethodHTTPAction`) through `HandleNodeMessage`: [7](#0-6) 

If `req.CacheSettings.Store` is true and `CacheSettings.MaxAgeMs > 0`, the cache is read/written keyed solely by `req.Hash()` — which, per the tests, does not distinguish `WorkflowID`.

### Impact Explanation
Because `WorkflowID` is not part of the cache key, if two different workflows belonging to the same `WorkflowOwner` issue outbound HTTP action requests with the same method/URL/headers/body (a realistic scenario for shared integrations, e.g., a shared API-key/token endpoint or a templated workflow reused with different logic but the same external call signature), a workflow can be served the cached response that was actually fetched and stored on behalf of a *different* workflow. This breaks the intended per-workflow isolation the README promises, and can result in stale or cross-workflow response confusion including leaking response bodies/headers (which can contain secrets, tokens, or per-workflow-specific data returned by the external endpoint) to an unrelated workflow execution context.

The blast radius is bounded by `WorkflowOwner` (different owners do not collide), so this is not a cross-tenant/cross-customer leak, but it is a genuine violation of the documented workflow-level isolation guarantee and a "cross-user [cross-workflow] response confusion" bug within a single owner's account — the same bug class as the filebrowser report (a documented content/permission scoping guarantee silently not enforced in one specific serving code path, while the design intends stricter isolation).

### Likelihood Explanation
Likelihood is moderate: it requires (a) an owner running multiple workflows, (b) `CacheSettings.Store=true` and `MaxAgeMs>0` used by those workflows' outbound HTTP actions, and (c) identical method/URL/headers/body across workflows within the TTL window (default 10 minutes, `defaultOutboundRequestCacheTTLMs`). These conditions are plausible for shared/templated workflow patterns and are entirely under the control of the workflow author, not an external attacker — but they demonstrate a real inconsistency between the documented isolation model and the enforced one.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`, method, URL, headers, and body) in `OutboundHTTPRequest.Hash()` so that the cache key matches the isolation guarantee documented in the README, or update the README to accurately describe owner-level (not workflow-level) cache scoping if that is the intended behavior.

### Proof of Concept
Not independently reproducible from the indexed code alone since `Hash()` is implemented in the `chainlink-common` dependency, not in this repo; the finding is proven by the handler's own test assertions rather than an external PoC:
1. `TestRequestHash/having different workflowID results in same Hash` in `response_cache_test.go` (lines 139-149) creates two requests identical except for `WorkflowID` and asserts `hash1 == hash2`.
2. Given `makeOutgoingRequest` in `http_handler.go` (lines 404-442) uses this same `Hash()` as the sole cache key when handling `MethodHTTPAction` node messages, a second workflow (same owner) issuing an identical outbound request within the TTL will retrieve the first workflow's cached response via `responseCache.Fetch`.

**Uncertainty**: The exact byte-level implementation of `Hash()` lives in the `github.com/smartcontractkit/chainlink-common` module, which is outside this repo's index, so I could not directly inspect its source to confirm exactly which fields are hashed beyond what the tests in this repo prove behaviorally. If a full walkthrough of `Hash()`'s implementation is needed, a Devin session with access to the vendored/module source would be required.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

## 3. HTTP Action Message Handling

### 3.1 Process Flow

1. **Request Reception**: Gateway receives HTTP action request from a workflow node
2. **Rate Limiting**: Validates node rate limits
3. **Request Parsing**: Extracts `OutboundHTTPRequest` from the JSON-RPC message
4. **Cache Check**: Determines if request should use cached response or fetch fresh data
5. **HTTP Execution**: Makes actual HTTP request to external endpoint
6. **Response Caching**: Stores cacheable responses (2xx, 4xx status codes) only if `CacheSettings.Store` is `true`
7. **Node Response**: Sends HTTP response back to requesting node

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
