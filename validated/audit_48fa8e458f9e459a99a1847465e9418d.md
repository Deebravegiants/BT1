### Title
RAY-value overflow in `accrue_step` permanently freezes a live market before the borrow-index cap engages - ([File: common/src/rates/index.rs])

### Summary
The protocol documents the borrow-index ceiling `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` as the safety bounds for index growth, mirroring the report's "documented bounds" that imply accrual cannot revert for in-range inputs. However, `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` — scaled debt shares times the new index — in RAY, and this product overflows `i128` when `borrowed` is large, well before `new_borrow_index` reaches `MAX_BORROW_INDEX_RAY`. The `MathOverflow` panic aborts accrual inside `accrue_chunk`, and because every user-facing verb (supply/withdraw/borrow/repay/liquidate/claim_revenue/recapitalize) runs `global_sync` accrual first, the entire market freezes permanently. [1](#0-0) [2](#0-1) 

### Finding Description
The analog of the Cobb–Douglas revert: a core arithmetic path reverts for inputs that satisfy every documented bound.

- `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` after computing `new_index`, so the index itself stays in bounds. [3](#0-2) 
- But `calculate_supplier_rewards` then computes `new_total_debt = borrowed.mul(env, new_borrow_index)`. `borrowed` is RAY-denominated scaled shares (up to ~`i128::MAX / 10^(27-d)` per market admission), so `borrowed * new_borrow_index / RAY` exceeds `i128::MAX` once `new_borrow_index` grows past roughly `i128::MAX * RAY / borrowed`. [1](#0-0) 
- `Ray::mul` → `mul_div_half_up` panics with `GenericError::MathOverflow` when the quotient does not fit `i128`; there is no saturating fallback here (unlike `update_supply_index`, which uses `mul_div_floor_saturating`). [4](#0-3) [5](#0-4) 
- `accrue_chunk` calls `accrue_step` on every accrual, and `global_sync` is invoked by all market operations, so one overflowed chunk bricks every entrypoint touching that market. [6](#0-5) 
- The docs acknowledge only that "value overflow can occur before the index ceiling and block repayment/withdrawal," but no bound prevents reaching it: admitted caps and bounded indexes do not bound `borrowed * index`. [7](#0-6) 

### Impact Explanation
Permanent freezing of funds. Once `borrowed * new_borrow_index` exceeds `i128`, every path that accrues reverts: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, revenue cannot be claimed. The panic is self-reinforcing — `borrow_index` only grows, and no unprivileged or privileged operation reduces `borrowed` shares without first accruing. A dedicated end-to-end test confirms the freeze: after the overflow point, `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow` while `last.borrow_index < MAX_BORROW_INDEX_RAY` (the cap never engages). [8](#0-7) 

### Likelihood Explanation
Medium. An unprivileged borrower pushes utilization toward the steep slope-3 segment (`calculate_annual_borrow_rate` clamps utilization at 1 and the rate at `max_borrow_rate`, up to 2 RAY = 200% APR), which maximizes index growth per unit time. [9](#0-8)  Triggering requires a large market (debt in the hundreds of billions of units) sustained at high utilization — organic growth plus time reaches the same state without attacker capital, and the crossing point is market-specific and not alarmed. `update_indexes` is callable by any authenticated caller, so no privileged action is needed to hit the panic.

### Recommendation
Bound the product, not just the index, as the report suggests for its `bound` parameter:
- Enforce an admitted-supply/debt cap such that `borrowed * MAX_BORROW_INDEX_RAY / RAY` (and the symmetric supply value) fits `i128`, applied in market creation and borrow gates rather than relying on the index cap.
- Or make `calculate_supplier_rewards` overflow-safe: split `borrowed`/`index` into halves before multiplying, saturate `new_total_debt` and clamp the resulting index the way `update_supply_index` clamps via `mul_div_floor_saturating`, so accrual degrades gracefully instead of panicking.
- Add a pre-panic guard in `accrue_chunk` (e.g., cap the chunk or index when the debt value approaches `i128::MAX`) and emit an event before the bound is reached so governance can act while the market is still operable.

### Proof of Concept
The repo's own harness test demonstrates the exploit path end to end:

1. Create an 18-decimal market with a steep rate curve; supply ~1e27 units and borrow ~98% of it (all unprivileged `supply`/`borrow` calls).
2. Advance time repeatedly; each `update_indexes` call runs `global_sync` → `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards`.
3. Once `borrowed * new_borrow_index / RAY > i128::MAX`, `Ray::mul` panics `MathOverflow`; `last.borrow_index` is still below `MAX_BORROW_INDEX_RAY`.
4. Subsequent `update_indexes`, `withdraw` (even 1 unit), and `repay` all revert with `MathOverflow` — the market is permanently frozen, and nothing in the code path can unwind it. [10](#0-9) 

Uncertain: whether `require_authorized_caller` restricts `update_indexes` beyond self-auth was not verified, but the harness drives it as a normal user call, and the freeze affects every verb regardless of who triggers accrual.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
