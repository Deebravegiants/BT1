### Title
`RequestState` messages bypass source-identity validation in `orb-relay-client`, allowing unauthenticated signup state disclosure - (File: `orb-relay-client/src/client.rs`)

### Summary
In `PollerAgent::main_loop`, every regular relayed payload is checked against `src.id != self.config.dst_id` before being accepted into the message buffer, rejecting payloads that don't originate from the expected counterparty. However, the special-cased `self_serve::app::v1::RequestState` message is handled *before* that check and unconditionally triggers a reply containing `self.last_message` — the most recently sent signup/session message — regardless of who sent the request.

### Finding Description
The DebtDAO `close()` bug lets a caller skip an existence/ownership check (`credit.lender`/borrower) for one code path (`_close`), causing state to be finalized/leaked incorrectly. The analogous pattern here is in the relay client's inbound message dispatcher: [1](#0-0) 

```
message = response_stream.next() => {
    match message {
        Some(Ok(RelayConnectResponse {
            msg: Some(relay_connect_response::Msg::Payload(RelayPayload {
                src: Some(src), dst, seq, payload: Some(payload),
            })),
        })) => {
            if self_serve::app::v1::RequestState::matches(&payload).is_some() {
                sender_tx.send(self.last_message.clone()).await...
            } else if src.id != self.config.dst_id {
                tracing::error!("Skipping received message from unexpected source: ...");
            } else {
                self.handle_message(...).await?;
            }
        }
```

The `else if src.id != self.config.dst_id` guard is the mechanism this file uses to ensure a payload really came from the paired counterparty (the orb for a given `session_id`/`orb_id`, or vice versa) before trusting it. That is the "does this credit/session actually exist and belong to this caller" check. But the `RequestState::matches(&payload)` branch is evaluated first and unconditionally replies with `self.last_message` — the last outgoing signup-related payload (e.g. `AnnounceOrbId`, `SignupEnded`, or other self-serve state messages) — without ever checking `src.id` against `self.config.dst_id`.

This mirrors the `LineOfCredit.close()` root cause exactly: a state-affecting operation (here, disclosure/replay of the last session payload) is performed for a message type that was carved out of the normal identity/ownership validation path, on the assumption that it isn't security sensitive.

### Impact Explanation
If the underlying relay transport ever permits multiplexing or an attacker-influenced `src` field on the stream (e.g., a compromised/rogue peer able to open a stream and inject a `RequestState` payload attributed to any `src`), this bypass would leak the most recent signup-flow message intended for a specific `orb_id`/`session_id` pair to an entity that was never validated as the legitimate counterparty — a cross-session state bleed of unprivileged-user signup state (e.g., `SignupEnded` success/failure feedback, `AnnounceOrbId`). This is exactly the kind of "operation completes for a non-validated/non-existent counterparty" bug class described in the reference finding, applied to signup-session data disclosure rather than fund transfer.

### Likelihood Explanation
The vulnerable code path is reachable by any peer capable of sending a `RequestState`-shaped payload over an established relay stream; the check that would normally filter foreign senders (`src.id != self.config.dst_id`) is structurally skipped for this one message type. Exploitability depends on how strictly the backend/relay server enforces `src` authenticity per connection, but at the client level there is no defense-in-depth check — the same defect pattern flagged in the reference report (skipping the validation that every other code path enforces).

### Recommendation
Move the `RequestState::matches` branch after the `src.id != self.config.dst_id` check (or add the same identity check inside that branch) so that replies containing `self.last_message` are only ever sent in response to requests verified to originate from the expected counterparty, consistent with how every other payload type in this loop is validated.

### Proof of Concept
1. Establish a relay connection as an `App`/`Orb` peer using `Client::new_as_app`/`new_as_orb` as shown in `orb-relay-client/src/bin/manual-test.rs`.
2. From a third, unrelated stream/session (i.e., with `src.id` not equal to the target's `dst_id`), send a payload matching `self_serve::app::v1::RequestState`.
3. Observe that `PollerAgent::main_loop` executes the `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch first and sends back `self.last_message` (the last real signup-flow payload) without ever evaluating the `src.id != self.config.dst_id` guard that protects every other message type.
