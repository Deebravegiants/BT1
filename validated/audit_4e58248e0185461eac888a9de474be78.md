Audit Report

## Title
Stale oracle price data can be consumed indefinitely because `pallet-oracle`'s aggregated `Values` storage is never re-validated for freshness at read time - (File: `substrate/frame/honzon/oracle/src/lib.rs`)

## Summary
`pallet-oracle`'s `DefaultCombineData::combine_data` only filters stale feeder submissions when new data is fed via `do_feed_values`, and the resulting aggregated value is stored indefinitely in `Values<T, I>` with no re-validation at read time. `Pallet::get()` and the `DataProvider::get()` trait implementation return this stored value without any timestamp/expiry check, and `DataProvider::get()` even discards the timestamp entirely, so a consumer has no way to detect staleness through the intended interface.

## Finding Description
The staleness filter (`values.retain(|x| x.timestamp.saturating_add(expires_in) > now)`) executes only inside `combine_data`, which is only called from `Pallet::combined`, which is only called from `do_feed_values`: [1](#0-0) [2](#0-1) 

The final aggregated `Values` storage map is returned as-is by `Pallet::get()` with no freshness check: [3](#0-2) 

The `DataProvider` trait implementation — the intended integration point for other pallets per the pallet's own module documentation ("This design allows for... Efficient access to final aggregated values") — strips the timestamp entirely, returning only the bare value: [4](#0-3) 

If all oracle members stop feeding a given key (e.g., go offline, are removed via `ChangeMembers::change_members_sorted`, or simply stop submitting), `combined()`/`do_feed_values` is never invoked for that key again, so `Values[key]` retains its last value forever, with no hook (e.g., `on_finalize`) re-checking or clearing it. Confirmed no on-chain hook other than `HasDispatched` cleanup exists in `on_finalize`: [5](#0-4) 

## Impact Explanation
The vulnerable pattern is real and confirmed in code: the `DataProvider::get()` API — documented as the primary way "other pallets can use the `DataProvider` trait to read the aggregated data" — provides no freshness signal, unlike `read_raw_values`/`Values` which retain timestamps. However, I searched this repository for any in-tree pallet that actually consumes `pallet_oracle::Pallet` via `DataProvider` for a security-critical decision (price feed for CDP/lending/liquidation/stablecoin logic) and found none. `substrate/frame/psm` exists in this codebase but contains **no reference to `pallet_oracle`** at all, and no other pallet under `substrate/frame/` references `pallet_oracle::Pallet`, `OraclePriceProvider`, or similar integration outside of the oracle pallet's own test module (`substrate/frame/honzon/oracle/src/tests.rs`). The only in-tree usage of `pallet_oracle` is its registration in the node runtime (`substrate/bin/node/runtime/src/lib.rs`) and exposure via a generic runtime API (`get_value`/`get_all_values`) that is not wired into any consuming pallet's dispatchable logic. Thus, while the API design flaw exists, there is no demonstrated reachable path in this codebase where an unprivileged user's action leads to a concrete state-changing financial loss (e.g., unfair liquidation, incorrect minting) — the necessary consuming pallet simply does not exist or does not integrate with `pallet-oracle` in this repository.

## Likelihood Explanation
The staleness precondition (feeders stopping submissions) is realistic and requires no privilege to trigger by omission, but this alone does not constitute an exploitable vulnerability without a downstream consumer that relies on `DataProvider::get()` for a security-critical decision. No such consumer exists in-tree in this codebase (`pallet-psm` does not integrate with `pallet-oracle`, and no other pallet does either). The finding therefore describes a defensive-design weakness in `pallet-oracle`'s public API contract rather than a demonstrated exploitable vulnerability with concrete on-chain impact in this repository.

## Recommendation
- Add an explicit staleness check inside `pallet_oracle::Pallet::get()` (or an additional `get_checked` view) that compares `TimestampedValue::timestamp` against `T::Time::now()` and a configurable max-age, returning `None` when stale.
- Change `DataProvider::get()` to expose the timestamp alongside the value (or add a `DataProviderExtended`-style method returning `TimestampedValue`) so that any future or existing downstream consumer can enforce its own freshness policy at the point of use.
- If/when a financial pallet (e.g., a CDP, lending, or stablecoin pallet) is integrated with `pallet-oracle` in this codebase, that integration must independently enforce a maximum acceptable data age before using the price for state-changing decisions.

## Proof of Concept
Not independently reproducible as an on-chain exploit with concrete impact in this codebase: no in-tree consumer of `pallet_oracle::DataProvider` for a security-critical decision was found. The API-level weakness can be demonstrated as follows:
1. Deploy the node runtime with `pallet_oracle::Config::CombineData = DefaultCombineData<Runtime, MinimumCount, ExpiresIn>`.
2. Feed a value for key `K` at time `T0` via `feed_values`, causing `Values[K] = (value, T0)`.
3. Stop all further submissions for `K` (feeders idle/removed).
4. Advance time past `ExpiresIn`.
5. Call `pallet_oracle::Pallet::<Runtime>::get(&K)` or the `OracleApi::get_value` runtime API — both return the original stale `value` with no error or staleness indicator.
This demonstrates the described API gap, but without an identified downstream financial consumer in this repository, there is no concrete, reproducible impact test (unit/fork/invariant) showing fund loss or unfair liquidation.
