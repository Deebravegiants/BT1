## Custody Analog: Timelock Override Threshold Can Permanently Block Multisig Owner Removal (`multisig_account.move`)

### Title
Owner removal from a multisig can be permanently blocked by the timelock override threshold check - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
This repo's `multisig_account.move` has been extended with a `MultisigAccountTimeLock` feature (`override_threshold`, `timelock_period`) that is not present in upstream `aptos-core`. Inside `update_owner_schema`, every owner-list mutation is followed by a strict invariant check requiring `override_threshold > num_signatures_required` [1](#0-0) . Because `override_threshold` is auto-clamped down to the *new* owner count whenever it exceeds it, a multisig configured with `override_threshold` equal to its owner count is permanently unable to remove even a single owner through the single-purpose `remove_owner`/`remove_owners` entry functions — this is the exact same class of bug as the external report's `owners.length > threshold` self-ejection lock.

### Finding Description
`update_owner_schema` is the single choke-point used by `add_owner(s)`, `remove_owner(s)`, `swap_owner(s)`, and `update_signatures_required` [2](#0-1) . After owners are removed and/or `num_signatures_required` is optionally updated, the function recomputes `num_owners` and, if a `MultisigAccountTimeLock` resource exists, clamps `override_threshold` down to `num_owners` when it would otherwise exceed it, then asserts that the (possibly just-clamped) `override_threshold` is **strictly greater than** `num_signatures_required`: [1](#0-0) 

This mirrors the reported Solidity pattern: a threshold-style check computed *after* a state-mutating removal can become unsatisfiable in a legitimate boundary case (`owners.length == threshold`), aborting the very operation meant to reduce owner count. Here, the boundary case is `override_threshold == num_owners` (a natural "require full-owner consensus to override" configuration). Removing a single owner via `remove_owner`/`remove_owners` (which pass `option::none()` for the new signature count) leaves `num_signatures_required` unchanged, clamps `override_threshold` to the new (smaller) `num_owners`, and the equality `override_threshold == num_signatures_required` (both now equal to the post-removal owner count when the multisig had also set `num_signatures_required == old num_owners - ...`) causes `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` to abort the transaction.

This is directly confirmed by an in-repo test: [3](#0-2) 

The comment on this test explicitly states: *"But num_signatures_required is also 2, so override (2) is NOT > threshold (2). This should fail."* — i.e., the framework itself acknowledges that a single-purpose owner removal can be made permanently unexecutable by this check, exactly analogous to the external report's `owners.length > threshold` self-ejection lock.

### Impact Explanation
Multisig accounts on Aptos custody APT, fungible assets, and can be the designated controller of resource accounts and code objects. If such an account is configured with a timelock override (a security feature meant to require broader/unanimous consent to bypass timelocks), and its `override_threshold` equals its owner count, the owners lose the ability to eject a compromised, lost-key, or otherwise problematic owner using the normal single-purpose `remove_owner`/`remove_owners` entry functions — every such call aborts. To regain the ability to change owners, the account must instead route through `swap_owners_and_update_signatures_required`/`add_owners_and_update_signatures_required` and simultaneously lower `num_signatures_required`, which forces a security downgrade (weakening the required signature threshold) as the price of removing an owner. In the worst case (owners unwilling to weaken the threshold, or unaware of the workaround), this can permanently lock governance of the multisig — and therefore of any resource account, code object, or asset it controls — preventing removal of a compromised co-owner, which is a custody-relevant, non-recoverable loss-of-control condition.

### Likelihood Explanation
This requires a multisig owner (not an external attacker) to have configured `MultisigAccountTimeLock` with `override_threshold` equal to (or clamped to equal) the current owner count — a plausible and even security-conscious configuration (e.g., "require all owners to override the timelock"). Once in that state, the very next owner-removal attempt via the single-owner-removal entry points will deterministically abort, as proven by the repo's own test. This does not require any privileged bypass; it is a naturally reachable state through normal, documented multisig configuration entry points (`upsert_timelock`, `remove_owner`).

### Recommendation
Change the invariant to allow `override_threshold >= num_signatures_required` (or otherwise decouple the override check from blocking the ordinary owner-removal path), and/or allow `remove_owner`/`remove_owners` to auto-adjust/clamp `override_threshold` and `num_signatures_required` together atomically, rather than requiring owners to discover and use the combined `swap_owners_and_update_signatures_required` function to avoid a full ownership-management lockout. At minimum, `remove_owner`/`remove_owners` should not silently abort in this boundary case without a clear recovery path that does not require weakening the signature threshold.

### Proof of Concept
1. Create a 3-owner multisig with `num_signatures_required = 2` (see `setup_timelock_multisig` used by the test).
2. Call `upsert_timelock(multisig_signer, 3600, option::some(3))`, setting `override_threshold = 3` (equal to owner count) — a "full unanimity to override" configuration.
3. Call `remove_owner(multisig_signer, owner_3)` directly (without first lowering `num_signatures_required`).
4. `update_owner_schema` removes the owner (3 → 2 owners), clamps `override_threshold` from 3 to 2, then asserts `override_threshold (2) > num_signatures_required (2)`, which is false, and the transaction aborts with `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD`.
   This exact sequence is codified in `test_owner_removal_fails_if_override_becomes_invalid` [3](#0-2) .

**Note on completeness:** I was unable to retrieve the full body of `upsert_timelock` and the transaction-execution code path that consumes `override_threshold` (e.g., how it bypasses/enforces the timelock during `validate_multisig_transaction`) before this session's tool budget was exhausted. The finding above is fully supported by the `update_owner_schema` code and the repo's own regression test, but I could not independently verify whether additional guardrails exist elsewhere (e.g., in `upsert_timelock`) that might prevent this exact boundary configuration from being reachable in practice. If precise confirmation of end-to-end exploitability is required, review `upsert_timelock` and the execution-time use of `override_threshold` directly in the source.
