Confirmed: the docs explicitly document `data.shop` as "The shop domain of the webhook" `docs/usage/webhooks.md:14`, and the code passes `request.shop` straight from headers into `WebhookMetadata` without it being part of the HMAC-signed content [1](#0-0) .

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `X-Shopify-Shop-Domain` header verbatim as the webhook's tenant identity, even though that header is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC [3](#0-2) . `HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac` [4](#0-3) , so it never touches the shop header. `Registry.process` then forwards `request.shop` unchanged into `WebhookMetadata`, which the gem's own documentation tells app authors to trust as "The shop domain of the webhook" and use to key tenant data [5](#0-4) .

This breaks the identity binding `shop authenticated == shop the HMAC was computed for`. Because Shopify apps share a single `client_secret`/`api_secret_key` across every merchant that installs the app, any merchant who has legitimately installed the app on their own store (an "unprivileged internet user" with respect to any other tenant) can capture one of their own genuine webhook deliveries — a valid `(raw_body, hmac)` pair signed with the app's shared secret — and resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim shop. Since the header is not part of `to_signable_string`, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the forged request to the handler with `data.shop` equal to the attacker-chosen victim domain.

### Impact Explanation
Any app whose webhook handler uses `data.shop` to look up a tenant's session/access-token or to gate which tenant's records get created/updated/deleted (the exact pattern the gem's own docs recommend, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into performing actions against, or leaking data about, a shop the attacker does not own. This is cross-tenant access driven purely by manipulating a header that is documented and treated as trustworthy after "HMAC validation," which meets the Critical "cross-tenant access" bar since it lets one merchant's traffic impersonate another merchant's webhook identity without possessing that merchant's credentials.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop, a normal unprivileged action; (2) capturing one legitimate webhook (trivial via a proxy on the attacker's own receiving endpoint); (3) resending the same body/HMAC with a different `shop-domain` header. No access token, `client_secret`, or privileged access to the victim's data is required, which makes this straightforward to reproduce.

### Recommendation
Bind the shop identity to the signed content, e.g. verify the `shop` header against an actively-registered session/webhook subscription for that exact shop (looking up by `webhook_id` returned from Shopify's GraphQL API, which is tenant-scoped) before dispatching to the handler, rather than trusting the header value directly. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not cryptographically bound by the HMAC and must be independently verified against a known, previously-registered shop/session before being used for authorization or tenant-scoping decisions.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a legitimate webhook whose body/HMAC were signed with the shared
# api_secret_key.
raw_body = capture_of_real_webhook_body # e.g. '{"id":123,...}'
real_hmac = capture_of_real_webhook_hmac_header

# Attacker resends the exact same body/HMAC pair but swaps the shop header
# to a victim shop that also has the app installed.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => real_hmac,          # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The app's handler now believes this event belongs to "victim-shop.myshopify.com".
```
