### Title
`withdraw()` in the Tron `IntentGatewayV2` uses low-level `.call()` with only success-check, not verifying the ERC20 boolean return value, allowing silent-failure tokens to be marked as paid without transferring funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` (the Tron port of the Intent Gateway) settles escrow releases and fee payouts using raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks the low-level `success` boolean of the call, never decoding/validating the ERC20 return data. [1](#0-0) 

This is the exact bug class from the referenced Cooler report (H-1): tokens that return `false` on failure instead of reverting (the classic ZRX/weird-ERC20 pattern) will make the low-level `call` succeed (`success == true`) even though no tokens moved, because `success` only reflects whether the call itself didn't revert — it says nothing about the ABI-decoded boolean return value.

By contrast, the canonical EVM contract at `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which reverts on both call failure and a `false` return value: [2](#0-1) 

### Finding Description
The Tron variant's `withdraw()` function is the settlement path invoked when a cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered via `onAccept`, or from `onGetResponse` for cancellations. It iterates over the withdrawal's token list and, for ERC20 tokens, does:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and similarly for fee payouts:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 

Before this, the accounting state has already been mutated unconditionally:
```solidity
address beneficiary = address(uint160(uint256(body.beneficiary)));
_filled[body.commitment] = beneficiary;
...
_orders[body.commitment][token] -= amount;
``` [4](#0-3) 

Because `token.call(...)` only reverts if the target has no code or the call itself throws, any ERC20 implementation that returns `false` on a failed transfer (instead of reverting) will pass the `success` check while `TransferFailed()` is never triggered — the escrow accounting is decremented and the order is marked `_filled`/settled, but the beneficiary never actually receives the tokens. On Tron in particular, TRC20 tokens frequently mirror this weird-ERC20 "return false instead of revert" behavior, so this is not a purely theoretical edge case for this specific deployment target.

The same pattern also appears in `placeOrder`'s call-dispatcher sweep path in the same file:
```solidity
data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
```
executed through `ICallDispatcher(dispatcher).dispatch(...)`, which similarly does not validate the ABI-decoded boolean return of the transfer. [5](#0-4) 

### Impact Explanation
This directly maps to "unauthorized app action" / "concrete theft or permanent freezing of funds" impact classes:
- A solver/filler or user who has escrowed a "no-revert-on-failure" ERC20 (or any TRC20 with the same semantics) can have their `withdraw()` call silently no-op the token transfer while the contract still marks `_filled[commitment] = beneficiary` and decrements `_orders[...]`. The result is escrowed funds becoming permanently stuck/unaccounted for in the contract (frozen), while the protocol's internal bookkeeping believes settlement succeeded, and the order can never be retried (since `_filled` is already set and escrow is already zeroed).
- Fee funds (`TRANSACTION_FEES`) can similarly be "paid" to a beneficiary without an actual transfer taking place, resulting in a loss for whoever was supposed to receive that fee (typically the solver), and once deleted from `_orders[...][TRANSACTION_FEES]` those fees become unrecoverable.
- Since this settlement path is reachable by any relayer submitting a valid cross-chain proof for a `RedeemEscrow`/`RefundEscrow` request, or via any GET-response-triggered cancellation, an unprivileged relayer or a user placing an order with a specially crafted (or naturally silent-failing) token can trigger the loss condition without any privileged access.

### Likelihood Explanation
Likelihood is contract/asset-dependent: it only manifests for ERC20/TRC20 tokens whose `transfer` function returns `false` rather than reverting on failure. This is a well-documented "weird-ERC20" pattern (see `weird-erc20` catalogue referenced in the original report) and is common enough among TRC20 tokens on Tron that a Tron-specific port of this contract is a realistic target for such tokens being listed as intent-gateway assets. The trigger requires no special privilege — only that such a token is used as an input/output/fee asset in an order that later needs settlement (a state reachable through normal, permissionless `placeOrder`/`fillOrder`/cross-chain delivery flow).

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` (and the analogous sweep-call construction in `placeOrder`) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, exactly as already done in the canonical `evm/src/apps/intentsv2/IntentsBase.sol`. The contract already imports `SafeERC20` and has `using SafeERC20 for IERC20;` declared at the top — it should actually apply it in `withdraw()` and any other place performing raw ERC20 transfers, rather than falling back to a manual low-level call that only checks call-level success.

### Proof of Concept
1. Deploy an ERC20/TRC20-like token whose `transfer(address,uint256)` returns `false` on failure instead of reverting (e.g., insufficient balance triggers `return false;` rather than a revert — matches the ZRX/ weird-ERC20 pattern referenced in the source report).
2. A user places an order via `placeOrder` using this token as an input asset; tokens are escrowed into `_orders[commitment][token]`.
3. A solver fills the order cross-chain; Hyperbridge delivers the `RedeemEscrow` POST request, and `onAccept` → `withdraw(body, false)` executes.
4. Arrange for the contract's token balance to be insufficient/blocked at the moment of `withdraw` (e.g., another prior call drained the balance, or the token enforces a transient blacklist/pause) so `transfer` internally returns `false`.
5. `token.call(...)` still returns `success == true` (the call itself doesn't revert), so `TransferFailed()` is never raised.
6. `_filled[commitment]` is already set and `_orders[commitment][token] -= amount` already executed before the call — the beneficiary receives nothing, yet the order is marked as settled and cannot be retried or refunded, permanently freezing the escrowed funds.
