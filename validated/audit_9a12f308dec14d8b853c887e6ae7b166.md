### Title
Webhook `shop` (and `topic`) header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content solely from the raw request body, while the `shop` (and `topic`) values used downstream to identify which merchant a webhook belongs to come from unauthenticated HTTP headers. `Registry.process` validates only that the HMAC matches the body, then blindly forwards `request.shop` to the handler. This breaks the identity binding `HMAC-authenticated bytes == identity used by the app`, the same class of flaw as the report's "field acted on but not covered by the signature" pattern.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes/compares the HMAC purely against that signable string: [2](#0-1) 

Meanwhile, `shop` and `topic` are read straight from the `shopify-shop-domain` / `shopify-topic` HTTP headers, which are never part of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC over the body, but then passes `request.shop` (and `request.topic`) through to the handler without any check binding them to the authenticated payload: [4](#0-3) 

Because the `api_secret_key`/client secret used to sign webhooks is shared across every shop that installs a given app (it is an app-level secret, not a per-shop one), a merchant who legitimately installs the app on their own shop receives genuine `(body, hmac)` pairs signed with that shared secret. Since the header carrying `shop-domain` is not part of the signed material, that merchant can replay the exact same `body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop that also has the app installed). `Utils::HmacValidator.validate` still returns `true` because it only checks the body against the shared secret; `Registry.process` then constructs `WebhookMetadata` with the attacker-chosen `shop` value, and the host application's handler processes attacker-controlled webhook data as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding failure: the equality `hmac-authenticated body == shop the app attributes it to` does not hold. A host application that (as this gem's documentation instructs) treats `WebhookMetadata#shop` as the authenticated tenant identifier to look up sessions/access tokens or write per-shop data will process forged, attacker-controlled webhook payloads under a victim shop's identity. This matches the "Critical - cross-tenant access" impact bucket: an unprivileged app-installing user can inject data or trigger side effects (order/customer data, GDPR redact triggers, app/uninstalled handling, etc.) attributed to another merchant, without ever needing that merchant's or the app's credentials.

### Likelihood Explanation
Any user who can install the target app on their own store (a normal, unprivileged action) obtains valid `(body, hmac)` pairs for arbitrary webhook topics they can trigger on their own shop (e.g., placing an order, editing a customer). Because the HMAC secret is shared across all installs of the app, and the signature covers only the body, replaying that pair to the same public webhook endpoint with a spoofed `shop-domain` header requires no cryptographic secret and no TLS interception — only knowledge of the endpoint URL, which is typically public/documented.

### Recommendation
Bind the `shop` (and `topic`) identity to the authenticated content instead of trusting bare headers:
- Include `shop`, `topic`, and `webhook-id` in the HMAC-signable string (`to_signable_string`) alongside the body, mirroring how `Auth::Oauth::AuthQuery` signs all relevant fields, so any tampering with these headers invalidates the HMAC.
- Alternatively/additionally, require host applications to cross-check `request.shop` against an independently known active session for that shop before trusting the payload, and document this explicitly since the current API design implicitly encourages trusting `WebhookMetadata#shop` post-`Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimate webhook POST from Shopify for topic `orders/create` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker crafts a new POST to the app's public webhook endpoint containing the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this request; `Utils::HmacValidator.validate` recomputes HMAC over `B` only (`to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38`) and it matches `H`, so validation succeeds.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`.
5. The host application processes attacker-controlled order data as belonging to `victim.myshopify.com`, achieving cross-tenant data injection without ever possessing `victim`'s credentials or the app's `client_secret`.
