### Title
Webhook `shop` identity used by app handlers is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the raw request body. The `Registry.process` method then hands this unauthenticated `shop` value straight to the app's webhook handler as the trusted tenant, breaking the intended binding of "HMAC-authenticated payload" == "shop the payload came from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from a header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely over `to_signable_string` (the raw body) using the app's single, shop-agnostic `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards `request.shop` (the unauthenticated header value) as the authoritative tenant identifier to the handler: [4](#0-3) 

The equality the code implicitly assumes is:
`shop that produced/authorized this HMAC-signed body == request.shop (header value passed to the handler)`

But because the HMAC secret (`api_secret_key`) is identical for every shop that installs the app, and the header is excluded from the signed bytes, any merchant who has installed the app can generate a body that legitimately HMAC-verifies (from their own store's genuine webhook deliveries or by replaying one), then resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop. `HmacValidator.validate` still returns `true` because the body bytes and secret are unchanged, and `Registry.process` will happily dispatch the handler with the attacker-chosen `shop` value.

### Impact Explanation
This breaks the tenant boundary: an app that uses `WebhookMetadata#shop` (as returned by this gem) to select which merchant's data/session to update (a very common pattern — e.g., writing order data, redacting a customer, or updating shop-level settings keyed by `shop`) can be tricked into applying data intended for the attacker's own store to a different merchant's tenant context. This is a cross-tenant data-integrity/confusion issue: the trust boundary that the gem hands the host app (an "authenticated shop") is not actually authenticated by the HMAC check the gem itself performs.

### Likelihood Explanation
Requires only that the attacker (or their own shop) have installed the app to receive at least one genuinely HMAC-signed webhook body they control the content of (e.g., by placing a test order in their own store), and network-level ability to POST to the app's webhook endpoint with a modified header — no access to the app's `client_secret`, no privileged account, and no third-party dependency defect is needed. This is fully reachable through the gem's own public `Registry.process`/`Request` API as documented.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified surface, or otherwise have `HmacValidator`/`Registry.process` cryptographically or contractually tie the header-derived `shop` to the verified body (e.g., require callers to additionally verify `shop` against their own known/installed-shop list before trusting `WebhookMetadata#shop`, and document this loudly in `Webhooks::Request`/`Registry.process`), so host apps aren't implicitly encouraged to trust an unauthenticated header as tenant identity.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook (or crafts a body and independently HMACs it using knowledge that the secret is shared across shops if they can obtain a valid signed body via any means, e.g., their own store triggering the event).
2. Attacker resends the same raw body/HMAC pair to the app's webhook endpoint but sets the header `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` returns `true` because it only checks `@raw_body` against `Context.api_secret_key`: [5](#0-4) 
4. `Registry.process` dispatches to the handler with `shop: request.shop` == `"victim.myshopify.com"`, even though the payload's content actually originated from the attacker's own shop: [6](#0-5)
