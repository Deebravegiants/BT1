### Title
Rounding-to-zero in ERC20↔local decimal conversion lets `on_accept`/`on_timeout` mint/refund 0 tokens while the source-side escrow/burn is non-zero, causing permanent loss of bridged funds - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` in `pallet-hyper-fungible-token` scales an incoming ERC20 `U256` amount down to local balance by dividing by `10^(erc_decimals - local_decimals)`, exactly analogous to the reported SolverVaults integer-division rounding bug. No caller checks that the resulting `amount` is non-zero before minting/transferring, so a legitimately non-zero amount sent on the EVM side can be silently converted to `0` on the Polkadot side.

### Finding Description
`convert_to_balance` divides the ERC20 amount by `10 ** (erc_decimals - local_decimals)`: [1](#0-0) 

Whenever `erc_decimals > local_decimals` (the documented/benchmarked configuration — EVM side is 18 decimals, local asset can be configured with fewer, and `register_token`'s only constraint per the benchmarking comment is that the EVM side must have *at least* as many decimals as the local asset, i.e. the gap can be arbitrarily large): [2](#0-1) 

any incoming `amount < 10 ** (erc_decimals - local_decimals)` divides to `0`. This value is used directly in `on_accept` to mint or transfer to the beneficiary, with no check that `amount > 0`: [3](#0-2) 

The same unchecked conversion is used again in `on_timeout` to compute the refund amount released from escrow: [4](#0-3) 

On the EVM side, the corresponding `send()`/burn or lock of the source token already happened for the full non-zero amount before the message was dispatched, since the EVM contract escrows/burns first and only then dispatches the cross-chain `Send` message. So a user (or filler/relayer delivering a dust-sized cross-chain post request) can cause funds to be irrecoverably locked/burned on the source chain while the beneficiary receives `0` on the destination — and if the request times out, the refund path (`on_timeout`) is subject to the identical rounding, so even the timeout-refund safety net can zero out and strand the escrowed value.

This is the direct analog of the reported `SolverVaults.deposit` bug: `amountInSolverVaultTokenDecimals` rounding to `0` on division when `solverVaultTokenDecimals < collateralDecimals`, breaking the 1:1 ratio and leaving the user's already-transferred collateral unredeemable.

### Impact Explanation
This is a concrete, permanent loss of user funds reachable from a normal cross-chain token transfer:
- On `on_accept`: the beneficiary is minted/credited `0` tokens for a non-zero cross-chain transfer whose source-side collateral (escrow lock or burn) is real and non-zero — user funds are permanently lost with nothing minted to compensate.
- On `on_timeout`: the refund to the original sender can also round to `0`, so even the fallback recovery path for a failed/timed-out transfer can fail to return the escrowed funds, making the loss unconditional rather than merely a griefing vector.

Both paths are pallet-ismp message handlers (`IsmpModule::on_accept` / `on_timeout`) invoked by relayer-delivered proofs, so any dust-sized cross-chain transfer between a high-decimal EVM asset and a lower-decimal local asset triggers unbacked value destruction.

### Likelihood Explanation
Likelihood is high wherever `register_token`/`update_token` configures an EVM chain with more decimals than the local asset (the common case — EVM ERC20s are typically 18 decimals while many Substrate assets use 6, 10, or 12 decimals, as shown in the benchmarking constants `LOCAL_DECIMALS = 12` vs `EVM_DECIMALS = 18`). Any sender (a user, filler, or an attacker deliberately sending dust amounts) can trigger the zero-mint/zero-refund outcome with a single small-value transfer; no privileged role is required.

### Recommendation
In `convert_to_balance`, and at both of its call sites (`on_accept` and `on_timeout` in `module.rs`), explicitly reject (revert the message handling / return an error) whenever the input amount is non-zero but the converted local amount is zero, rather than silently proceeding to mint/transfer `0`. This mirrors the recommended fix for the original report: check the converted amount and revert instead of allowing a non-zero deposit/transfer to produce zero credited tokens.

### Proof of Concept
1. `register_token` configures an asset with `local_decimals = 6` and an EVM chain entry with `erc_decimals = 18` (a valid, benchmarked configuration since EVM decimals ≥ local decimals is the only enforced constraint).
2. A user calls the EVM `HyperFungibleToken.send()` (or equivalent) with `amount = 10^11` (i.e., `0.0000000001` in 18-decimal terms), which is burned/escrowed on the EVM side and dispatched as a `Send` post request.
3. On delivery, `on_accept` computes `erc_decimals.saturating_sub(local_decimals) = 12`, so `convert_to_balance` computes `10^11 / 10^12 = 0`.
4. `Mutate::mint_into`/`Currency::transfer` is called with `amount = 0`; the beneficiary receives nothing, while `10^11` units were already burned/locked on the EVM side — a permanent, unbacked loss of the sender's funds.
5. If instead the request times out, `on_timeout` performs the identical division when computing the refund, so the escrowed funds can also fail to be returned to the original sender.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
