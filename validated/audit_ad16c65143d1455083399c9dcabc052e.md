## Finding [1](#0-0) 

### Title
Permanent freezing of a creator's accrued USDC fees if the creator's wallet is blacklisted by USDC - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` unconditionally pays a creator's accrued fee balance to `msg.sender`, with no alternate-recipient parameter and no owner-assisted recovery path. If a creator address is ever added to USDC's blacklist (a real risk on Circle's centralized USDC), their entire `creatorBalance` becomes permanently and irrecoverably locked inside the vault, mirroring the "USDC Blacklisting Risk" bug class from the referenced Sherlock report, but here the freeze is worse: unlike `claimProtocol()`/`sweepDonations()`, which pay out to an owner-rotatable `feeTo`, there is no equivalent admin lever for creator balances.

### Finding Description
`FeeVault` accrues creator fees per-address via `accrue()` [2](#0-1)  and only exposes a single withdrawal path, `claim()`, which hardcodes the recipient to `msg.sender`:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [3](#0-2) 

If `msg.sender` (the token creator, an unprivileged, permissionless role reachable simply by calling `Bonding.launch`/`Zap.createToken`) is later placed on USDC's `isBlacklisted` list, `$.usdc.safeTransfer(msg.sender, amount)` will revert every single time `claim()` is called, because USDC's `transfer` reverts when either party is blacklisted. There is:
- No `claim(address to)` variant to redirect the payout to a clean address.
- No owner-only rescue/reassign function for `creatorBalance[creator]`.
- No way for the creator to move the balance to a different `creator` key (only `accrue`, called by trusted `Zap` depositors on new fee events, ever writes to `creatorBalance`).

By contrast, the protocol-fee path explicitly designed around this exact risk: `claimProtocol()` and `sweepDonations()` both pay to `feeTo`, which the owner can rotate via `setFeeTo()` [4](#0-3)  specifically so a bad/blacklisted recipient doesn't brick the payout. `creatorBalance` has no analogous mitigation.

This is the exact bug class in the external report: a USDC-blacklisted recipient makes `_token.safeTransfer(receiver, amount)` revert, permanently blocking that party's reward/fee claim. Here, alt.fun's `Zap._accrueFee` deposits creator/protocol fee shares into `FeeVault` on every buy/sell [5](#0-4) , so any actively-trading token continuously grows a doomed, unclaimable `creatorBalance` for a blacklisted creator.

### Impact Explanation
- The creator's entire lifetime accrued USDC fee balance (`creatorBalance[creator]`) becomes permanently frozen inside `FeeVault` the moment the creator's wallet is blacklisted by USDC — with **zero on-chain recovery mechanism**, not even by the protocol owner.
- Because `totalAccruedCreator` keeps this stuck amount in its running tally forever [6](#0-5) , that USDC is also permanently walled off from `sweepDonations()`'s surplus calculation, so it can never even be reclaimed as an "orphaned" donation.
- This is a genuine, concrete freezing of a legitimate protocol participant's funds (the creator role is explicitly in-scope, unprivileged, and reachable via `Zap.createToken`), satisfying the "permanent freezing of ... creator ... funds" bar.

### Likelihood Explanation
Requires only that Circle blacklist a creator's wallet address at any point after they've accrued fees — an externally-triggered event outside the protocol's control, exactly as assumed by the original report's threat model for USDC-denominated reward/fee systems. No privileged action or malicious code is needed on alt.fun's side; the vulnerability is purely the missing recovery path in `FeeVault.claim()`.

### Recommendation
Add either:
1. An owner-only rescue function that can redirect a specific creator's stuck `creatorBalance` to a new address (analogous to `setFeeTo`), gated so it can only move funds already attributed to that creator; or
2. A `claim(address to)` variant allowing the caller to specify a non-blacklisted destination for their own accrued balance, with `msg.sender` still required to authorize the withdrawal (no third-party siphoning).

### Proof of Concept
1. `creator` launches a token via `Zap.createToken`, and it trades actively; `Zap._accrueFee` repeatedly calls `feeVault.accrue(token, creator, creatorShare, protocolShare, isBuy)` [5](#0-4) , growing `creatorBalance[creator]`.
2. Circle blacklists `creator`'s address on USDC (independent, off-chain/off-protocol event).
3. `creator` calls `FeeVault.claim()`. `$.usdc.safeTransfer(msg.sender, amount)` reverts because `creator` is blacklisted [7](#0-6) .
4. No other function can move `creatorBalance[creator]` elsewhere — verified by inspecting every mutator of `creatorBalance` in `FeeVault.sol`: only `accrue` (increments) and `claim` (only path out, fixed to `msg.sender`) touch it. The funds are permanently stuck.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```
