### Title
Missing storage gaps in the upgradeable abstract base contracts `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` risk corrupting live escrow storage on future upgrades - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2` is a UUPS-upgradeable, ERC1967-proxied contract composed via diamond inheritance from two abstract contracts, `IntrinsicIntents` and `ExtrinsicIntents`, both of which inherit `IntentsBase` [1](#0-0) [2](#0-1) . `IntentsBase` declares all of the gateway's live escrow state (`_filled`, `_nonce`, `_params`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, `_relayer`) directly in the abstract contract with no trailing storage-gap reservation [3](#0-2) . This is exactly the bug class from the referenced Sherlock finding on `GranularRoles.sol`: an upgradeable abstract base contract that is meant to be extended must reserve gap slots, because any storage variable it adds later shifts the slot positions of every variable declared in its subclasses.

### Finding Description
`IntentGatewayV2` is deployed behind an `ERC1967Proxy` and uses `Initializable`/`reinitializer` for versioned migrations, and its own tests explicitly assert exact storage slots (e.g. `_filled` at slot 2, `_paused`/`_relayer` packed at slot 13) that must survive an implementation upgrade [4](#0-3) . The developers' own decision log confirms this fragility is already recognized: "Params occupies slots 4 to 8 and _orders starts at slot 9. Adding a field to the struct would push every mapping behind it and corrupt escrow on the live proxy" [5](#0-4) . Despite this documented awareness of storage-layout fragility, `IntentsBase` has no `__gap` reservation, unlike `SimplexPaymaster.sol`, which does reserve `uint256[48] private __gap` [6](#0-5) . Because `IntentsBase` is an abstract contract meant to be extended by two sibling contracts (`IntrinsicIntents`, `ExtrinsicIntents`) before being composed into the final `IntentGatewayV2`, any future addition of a new state variable to `IntentsBase` (which is the natural place to add gateway-wide state, exactly as `_paused` and `_relayer` were "Appended last to preserve existing storage slots" per the inline comment [7](#0-6) ) risks colliding with storage that downstream logic in `IntrinsicIntents`/`ExtrinsicIntents` or `IntentGatewayV2` itself relies on, if such a variable is appended anywhere but the exact tail end, or if any sibling contract independently gains its own state in a future revision. The whole design already relies on manual, comment-driven slot bookkeeping instead of a structural safeguard.

### Impact Explanation
If a future upgrade adds a new storage variable to `IntentsBase` without extremely careful manual accounting across all inheriting/sibling contracts, the proxy's existing storage slots for `_filled`, `_orders`, `_params`, `_destinationProtocolFees`, etc. shift. This can corrupt escrowed order accounting (`_orders`), the fill-tracking map (`_filled`), or governance parameters (`_params`) on the live `IntentGatewayV2` proxy, leading to loss of escrowed user/solver funds, double-fills, or bricked authorization checks (`_relayer`, `_paused`). This maps to concrete permanent freezing/loss of escrowed funds on an upgrade path that is otherwise carefully tested for other classes of regression (as seen in `testFilledMappingStaysAtSlotTwo` and `testOnAcceptUpgradeContractPreservesState`).

### Likelihood Explanation
Likelihood depends on future maintenance discipline: the current deployed bytecode's layout is fine as tested. But the project has already shown it adds new base-level state fields over time (`_paused`, then `_relayer`, tracked by explicit ADRs about exact slot numbers), and the pattern of "append a field to the abstract base for a future governance feature" is the normal way this codebase evolves the gateway. Without a structural gap, this manual, ad hoc slot-tracking process is one missed review away from corrupting live escrow on the canonical CREATE2-deployed `IntentGatewayV2` proxy across every supported chain.

### Recommendation
Add explicit storage gaps to the abstract base contracts that are diamond-inherited before composition into the upgradeable `IntentGatewayV2`, mirroring the pattern already used in `SimplexPaymaster.sol`:
```solidity
uint256[50] private __gap;
```
placed at the end of `IntentsBase` (and consider gaps in `IntrinsicIntents`/`ExtrinsicIntents` too, since they are also abstract and diamond-inherited), so future additions to gateway-wide state consume gap slots instead of shifting existing storage.

### Proof of Concept
1. `IntentGatewayV2` composes `IntrinsicIntents` and `ExtrinsicIntents`, both extending `IntentsBase`, and is deployed behind an `ERC1967Proxy` [8](#0-7) .
2. `IntentsBase` declares 9 storage variables with no trailing gap [3](#0-2) .
3. A future governance upgrade (delivered via the host-only `Execute`/`upgradeToAndCall` path already exercised in tests [9](#0-8) ) adds a new field to `IntentsBase`, e.g. a new `mapping` or `address` inserted before the tail, or added to a sibling abstract contract that itself picks up state — this shifts every subsequent slot.
4. Because the live proxy's storage was laid out against the old ordering (as directly asserted by `testFilledMappingStaysAtSlotTwo`), the shifted layout causes `_filled`, `_orders`, and `_params` reads/writes on the upgraded implementation to resolve to the wrong slots, corrupting escrow accounting and governance parameters without any code-level detection, since Solidity's storage layout collisions are silent.

        assertEq(intentGateway._filled(filledCommitment), filler, "precondition: order A filled");
        assertEq(

        // The proxy now points at the new implementation and its new logic is reachable.
        assertEq(_implementationOf(address(intentGateway)), address(newImpl), "implementation slot updated");

        assertEq(intentGateway._nonce(), nonceBefore, "_nonce preserved");

        assertEq(intentGateway._orders(escrowedCommitment, inputToken), escrowedAmount, "_orders preserved");

    function testFilledMappingStaysAtSlotTwo() public {
        (bytes32 filledCommitment,,,) = _seedUpgradeState();

        // _filled is `mapping(bytes32 => address)` declared at storage slot 2. The cross-chain
        // cancel proof (FILLED_SLOT_BIG_ENDIAN_BYTES) depends on this exact slot.

        assertEq(filledFromSlot, intentGateway._filled(filledCommitment), "slot-2 read matches getter");
