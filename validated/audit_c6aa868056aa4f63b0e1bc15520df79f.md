### Title
Webhook Shop/Topic/Webhook-ID Identity Spoofing via HMAC That Only Covers the Request Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` only proves that the *body bytes* match a value signed with the app's secret — it does not bind the `shop`, `topic`, `webhook_id`, or `api_version` headers to that signature. `Webhooks::Registry.process` nonetheless treats those headers as authenticated when dispatching to handlers, breaking the binding `shop authenticated == shop acted upon`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the `@raw_body` is included. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived fields to select the handler and populate `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC purely from `to_signable_string` (the body) and compares it to the received signature: [4](#0-3) 

Because the signature is a function of the body alone, any `(body, hmac)` pair that was legitimately produced by Shopify for one shop/topic/webhook remains valid when replayed with a different `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header. An unprivileged internet user can install the app on their own (free/dev) shop, capture one genuine webhook delivery (any topic whose body they influence, e.g. a `products/update` or `customers/update` webhook containing data they control as the shop owner), and replay the identical body + HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop and/or the `topic`/`webhook-id` header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the data originates from the victim shop/topic, even though the signature never covered those fields.

### Impact Explanation
This breaks the equality `shop that produced a valid signature == shop attributed to the processed event`, letting an attacker who controls only their own shop's webhook deliveries inject events that the host application will attribute to an arbitrary victim shop domain (cross-tenant confusion). If the host app uses `WebhookMetadata#shop` to look up stored sessions/tokens, trigger per-shop side effects, or route to shop-specific logic (a documented, expected usage per `webhooks/registry.rb`), this enables cross-tenant data manipulation or state corruption without ever needing the victim's or the app's credentials.

### Likelihood Explanation
Requires only: (1) the ability to receive at least one legitimate webhook delivery for any shop, which any developer can obtain by installing the app on a free development store, and (2) sending a replayed HTTP request with modified headers to the app's public webhook endpoint. No secrets, tokens, or privileged access are required — only knowledge of the gem's documented behavior that headers are not part of the signed payload.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, document that consumers must not treat `WebhookMetadata#shop`/`#topic`/`#webhook_id` as authenticated and must independently corroborate them (e.g., against the session/shop context expected for the endpoint) before use.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; trigger a webhook (e.g., `products/update`) whose body content is attacker-controlled.
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` value Shopify sent for that delivery.
3. Replay an HTTP POST to the app's webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) — i.e., the body — against the secret, and succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never issued this shop/topic combination with this signature.
