### Title
Borrow/withdraw recipient check only excludes pool and controller — protocol contract recipients still strand tokens permanently - (File: contracts/controller/src/positions/mod.rs)

### Summary
`require_external_recipient` guards the user-supplied `to` address on `borrow` and `withdraw`, but it rejects only the pool and the controller itself. Every other in-scope protocol contract — the position NFT, governance, price aggregator, and any DeFindex/strategy contract address — is still accepted as a payout destination. Tokens transferred to those contracts are unclaimable: none of them expose a token-rescue or forwarding entrypoint, so the payout is permanently frozen. This is the same bug class as the BitVM `burn` finding (unvalidated destination → irreversible loss), partially mitigated by the GH-17 fix but not closed.

### Finding Description
`Controller::withdraw` and `Controller::borrow` accept `to: Option<Address>`; `to.unwrap_or_else(|| caller.clone())` resolves the recipient, and `require_external_recipient` is the only validation applied:

- `contracts/controller/src/positions/supply.rs:152-154` — recipient resolution and guard call in `process_withdraw`.
- `contracts/controller/src/positions/debt.rs:45-47` — same for `process_borrow`.
- `contracts/controller/src/positions/mod.rs:36-43` — the guard itself:

```rust
assert_with_error!(
    env,
    *recipient != env.current_contract_address() && *recipient != pool,
    FlashLoanError::InvalidFlashloanReceiver
);
```

Only `current_contract_address()` (the controller) and `cached_pool_address()` are blocked. The position NFT contract, governance contract, price aggregator, and strategy contracts are all valid `Address` values that pass this check. The pool then executes `transfer_out(receiver, net_transfer)` (`contracts/pool/src/ops/withdraw.rs:48`) / the borrow equivalent, sending SAC tokens to the chosen contract address.

The comment at `mod.rs:33-35` states the intent: "controller receipts would remain unclaimed by balance-delta accounting" — but the same stranding applies to any protocol contract that has no token-spending path. The GH-17 test suite (`tests/test-harness/tests/controller/recipient_is_protocol_contract.rs`) only exercises the pool and controller addresses, confirming the rest of the protocol surface was never considered.

### Impact Explanation
Permanent freezing of funds. Once tokens land on, e.g., the position-NFT or governance contract, there is no entrypoint that can move them out (no sweep/rescue function exists on these contracts); the SAC balance sits there forever. This also applies to `borrow`, so a user can additionally be left holding real debt while the borrowed funds are unrecoverable. Beyond self-inflicted loss, any delegated caller (`require_owner_or_delegate`) can specify such a recipient, and the design intent of `to` (paying a third party) makes contract-address destinations plausible in normal use.

### Likelihood Explanation
Reachable by a single unprivileged call: `withdraw(caller, account_id, withdrawals, Some(<position_nft_addr>))` or `borrow(..., Some(<governance_addr>))`. No privileged state, oracle manipulation, or timing is required — only that the caller names a protocol contract address other than pool/controller. Likelihood is moderate since it requires an unusual-but-plausible recipient; the loss is deterministic once it happens.

### Recommendation
Extend `require_external_recipient` to reject all known protocol contract addresses — position NFT, governance, price aggregator, swap aggregator, and registered strategy contracts — not just pool and controller. Alternatively invert the check: require the recipient to be an account address (or a contract on an explicit allowlist), so any contract address is refused by default and future protocol contracts are covered automatically.

### Proof of Concept
1. Alice supplies USDC and obtains `account_id` (standard `supply`).
2. Alice calls `Controller::withdraw(alice, account_id, [(hub_asset(USDC), amount)], Some(position_nft_address))`.
3. `require_external_recipient` passes: `position_nft != controller && position_nft != pool`.
4. Pool `apply` runs `cache.transfer_out(position_nft, net_transfer)` — SAC `transfer` to a contract address succeeds (contracts can hold SAC balances without a trustline).
5. The USDC now sits on the position-NFT contract, which exposes no token-transfer or rescue entrypoint → Alice's withdrawal is permanently frozen. Same result via `borrow` with `Some(governance_address)`, additionally leaving debt on the account.

One uncertainty: whether any of the other protocol contracts happen to expose a generic token-forwarding function was not fully verified (e.g., governance executing an arbitrary ready operation could in principle move tokens it holds, which would reduce — but not eliminate — the exposure for that specific contract).
