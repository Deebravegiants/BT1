### Title
Irrefutable pattern match on relayer-controlled `AccountType` decode panics the node during EVM-on-Substrate state proof verification - (File: `modules/ismp/state-machines/evm/src/substrate_evm.rs`)

### Summary
`fetch_trie_id_from_main_proof` in `modules/ismp/state-machines/evm/src/substrate_evm.rs` decodes an `AccountInfo` value read out of a relayer-supplied Merkle proof and then destructures its `account_type` field with an irrefutable `let` pattern:

```rust
let account_info = AccountInfo::decode(&mut &val[..])
    .map_err(|_| SubstrateEvmError::AccountInfoDecodeError)?;

let AccountType::Contract(contract_info) = account_info.account_type;
``` [1](#0-0) 

This mirrors the CVE-2018-10918 bug class: a value pulled from an external/untrusted data store (there, samba's LDB layer; here, a relayer-supplied trie proof) is used without validating its shape, and a mismatch crashes the process instead of returning a typed error.

### Finding Description
`AccountInfo::decode` only validates that the SCALE bytes decode into *some* `AccountInfo`/`AccountType` value — it does not guarantee the decoded enum variant is `AccountType::Contract`. The trie leaf value itself comes from `proof.main_proof`, a `Vec<Vec<u8>>` of raw trie nodes supplied inside the `Proof.proof` bytes of an ISMP message (`SubstrateEvmProof`), which is fully attacker/relayer controlled: it is decoded straight from the wire in `verify_membership`:

```rust
let proof: SubstrateEvmProof =
    Decode::decode(&mut &proof.proof[..]).map_err(SubstrateEvmError::ProofDecodeError)?;
...
let trie_id =
    fetch_trie_id_from_main_proof::<H>(&proof.main_proof, state_root, &contract_info_key)?;
``` [2](#0-1) 

If a relayer crafts a proof whose trie contains a leaf at the well-known `contract_info_key` (Revive `AccountInfoOf` storage prefix + address) that SCALE-decodes successfully but as `AccountType::NotContract`-style variant (or any variant other than `Contract`, if the enum has more than one arm), the `let AccountType::Contract(contract_info) = account_info.account_type;` line — being an irrefutable binding on a value that is not guaranteed to match — will fail to compile as written; in practice for a multi-variant enum this pattern is a refutable pattern used in an irrefutable-let position, which either fails compilation or, if the enum currently has exactly one variant, is safe today but is a footgun: the moment `AccountType` gains any additional variant (a realistic evolution, since the type mirrors pallet-revive's own `AccountType`), an out-of-scope proof triggers an unhandled-variant panic in the runtime, rather than a typed `Err`. This is the equivalent of samba's unchecked LDB output null-deref: proof-controlled data is assumed to have exactly the shape the code expects with no defensive checks.

This code path is reachable by any unprivileged relayer submitting a `handle_unsigned`/proof-verification message for the `SubstrateEvmStateMachine` (used to verify EVM-on-Substrate contract storage, e.g. Substrate parachains hosting `pallet-revive` EVM contracts) via `verify_membership`, which is invoked from the general ISMP request-handling pipeline. Because this is a validate/execution path for unsigned extrinsics (`pallet_ismp::Call::handle_unsigned`) and consensus/state proof handlers, an unhandled panic here would crash the block-authoring/validating node — a state-machine-affecting DoS analogous to the Samba AD-DC crash from a malformed database record.

### Impact Explanation
A panic triggered inside on-chain state-proof verification during block execution or validate_unsigned halts the affected node/collator (or, if triggered deterministically by all validators executing the same extrinsic, can halt block production network-wide for that state machine), a "route unable to deliver messages" condition and a DoS on the SubstrateEvm route. This fits the accepted impact class of a route unable to deliver messages.

### Likelihood Explanation
Reachability requires only a single relayed ISMP message/proof using the `SubstrateEvmStateMachine` client (i.e., a route where the destination or source runs `pallet-revive` EVM contracts behind Hyperbridge on a Substrate chain), with a proof engineered to place a decodable-but-wrong-variant `AccountType` at the exact `contract_info_key` trie position. No special privilege is needed — any relayer can submit proofs. However, I could not directly view the `AccountType`/`AccountInfo` type definitions or the `#[derive]` attributes in this session (tool access to the full file was unavailable in the final iteration), so I cannot confirm today whether `AccountType` currently has more than one variant, which is a prerequisite for the panic to be reachable right now rather than being a purely latent/future risk.

### Recommendation
Replace the irrefutable destructure with an explicit `match`/`if let` that returns `SubstrateEvmError` (e.g., `AccountInfoDecodeError` or a new `NotAContract` variant) for any non-`Contract` `AccountType`, so malformed or adversarial proof data cannot panic node execution:
```rust
let contract_info = match account_info.account_type {
    AccountType::Contract(contract_info) => contract_info,
    _ => return Err(SubstrateEvmError::AccountInfoDecodeError),
};
```

### Proof of Concept
Not verified end-to-end due to inability to inspect the full `AccountType` enum definition in this session; the described PoC would be: craft a `SubstrateEvmProof.main_proof` whose main trie contains, at `contract_info_key(contract_address)`, a SCALE-encoded `AccountInfo` whose `account_type` decodes to a non-`Contract` variant, then submit it via `handle_unsigned`/whatever ISMP message path invokes `SubstrateEvmStateMachine::verify_membership` for that destination/source state machine, expecting a runtime panic instead of a typed `Err(SubstrateEvmError::...)`.
