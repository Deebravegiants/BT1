## Finding

The Sherlock report's pattern — a critical value used to act on state without being verified as part of the same trust boundary — maps directly onto `ShopifyAPI::Webhooks::Request` in this gem: the `shop` (tenant) identifier that is handed to webhook handlers is never covered by the HMAC signature, only the raw body is.

### Title
Webhook `shop`/`topic`/`webhook-id` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers and are excluded from what `Utils::HmacValidator` verifies.

### Finding Description
`to_signable_string` binds the HMAC solely to the request body: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` — the values that identify *which tenant* and *which event* the webhook concerns — are pulled from headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e. only the body) and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values: [3](#0-2) 

The equality the app's HMAC check is supposed to guarantee is: `hmac == HMAC(secret, shop ‖ topic ‖ body)`. What is actually enforced is only `hmac == HMAC(secret, body)`. This breaks the intended binding between the authenticated payload and the tenant (`shop`) it is attributed to.

### Impact Explanation
An attacker who is themselves a merchant that has installed the app receives genuine, validly-HMAC'd webhook deliveries from Shopify for their **own** shop (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`). Because the app's webhook endpoint is just an HTTP endpoint under attacker control at the network layer (nothing authenticates that the POST truly originated from Shopify's infrastructure beyond the HMAC-over-body check this gem performs), the attacker can replay that captured `(raw_body, hmac)` pair to the same endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate(request)` still passes because it only checks the body/hmac, and the app's `WebhookHandler` receives `WebhookMetadata` claiming the event is for the victim shop. Any app logic keyed off `data.shop` (writing to per-tenant storage, processing GDPR/mandatory webhooks such as `shop/redact` or `customers/redact`, revoking access on `app/uninstalled`, etc.) can be triggered against a tenant the attacker does not own — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Requires only that the attacker install the app on any shop they control (or obtain any single genuine webhook payload) — no credentials, tokens, or `client_secret` access are needed, and the attack is a simple replay against the app's own public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string used for HMAC validation (or otherwise cryptographically bind them to the body, e.g. re-deriving `shop` only from a Shopify-verified source), so that a valid signature can only be produced for the exact `(shop, topic, body)` tuple actually sent by Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook (e.g. `customers/redact`).
2. Shopify delivers a POST with a valid `X-Shopify-Hmac-Sha256` (computed over body only) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `hmac` against `@raw_body`.
5. The registered handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing tenant-scoped side effects (data deletion, uninstall handling, etc.) to run against the victim's tenant.
