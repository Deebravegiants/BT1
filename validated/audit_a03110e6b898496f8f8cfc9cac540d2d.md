### Title
Webhook HMAC signs only the raw body, not the `shop-domain`/`topic` headers, allowing cross-tenant/topic confusion - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`HmacValidator.validate_signature` only proves that `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` equals the received HMAC. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from attacker-visible HTTP headers and are never part of the signed string [2](#0-1) . `Registry.process` then dispatches to a handler using `request.topic` (to pick the handler) and passes `request.shop` into `WebhookMetadata` as trusted, authenticated data, based solely on the fact that the body/HMAC pair validated [3](#0-2) .

### Finding Description
The broken binding is:
`HmacValidator.validate(request) == true` is treated as `⟺ request.shop and request.topic were authenticated by Shopify for this payload`.

In reality:
`validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it via `OpenSSL.secure_compare` to `verifiable_query.hmac` [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop` and `topic` accessors read from `@headers` (`shopify-shop-domain`, `shopify-topic`) which are ordinary HTTP headers supplied with the request, not part of the signed material [5](#0-4) .

Attack: an attacker registers their own development shop and installs the app, exposing the same app webhook endpoint that serves all merchants. Shopify sends the attacker a genuinely signed webhook (e.g., topic `orders/create`, `shop-domain: attacker-shop.myshopify.com`, some raw body, and a valid HMAC computed over that raw body using the app's `client_secret`). The attacker captures this raw body + HMAC pair and replays it directly to the app's webhook endpoint themselves (not via Shopify), substituting the `shop-domain` header with a victim shop and/or the `topic` header with a different registered topic (including a mandatory topic like `customers/data_request` or `shop/redact`). Because `HmacValidator.validate` only checks the body against the HMAC, the check still passes — `OpenSSL.secure_compare` sees an identical `computed_signature` and `received_signature` regardless of the forged headers. `Registry.process` then looks up the handler by the forged `request.topic`, and constructs `WebhookMetadata` with the forged `request.shop`, handing the app a payload it believes to be an authentic message from Shopify about the victim shop and/or a different event type [6](#0-5) .

None of the existing guards prevent this: `HmacValidator.validate` has no knowledge of headers [7](#0-6) ; `Registry.process` performs no independent check that `request.shop` corresponds to a shop that actually has a session/installation matching the topic, nor that `request.topic` matches what was registered for that specific webhook subscription [3](#0-2) ; and `VerifiableQuery` only requires `hmac` and `to_signable_string`, giving no structural guarantee that all header-derived fields consumed downstream are included in the signable string [8](#0-7) . By contrast, `Auth::Oauth::AuthQuery#to_signable_string` does include `shop`, `host`, `state`, `code`, and `timestamp` in the signed string [9](#0-8) , so this specific coverage gap is confined to the webhook path.

### Impact Explanation
A valid webhook HMAC only proves "Shopify (or someone holding the secret) signed this exact body at some point," not "this body belongs to this shop" or "this body is of this topic." An attacker who legitimately receives one webhook for their own shop can replay it to the shared app endpoint with forged `shop-domain`/`topic` headers, causing the app's webhook handler to act on attacker-controlled body content while believing it is an authenticated message for an arbitrary victim shop and/or arbitrary registered topic (including mandatory GDPR topics like `customers/data_request`, `customers/redact`, `shop/redact`). This is a cross-tenant authentication bypass: the app trusts unauthenticated header data as if it were covered by the signature. Repeatable per attacker-controlled webhook received, against any shop/topic combination registered by the app.

### Likelihood Explanation
Preconditions: the app must use `ShopifyAPI::Webhooks::Registry.process` (as documented) to validate and dispatch webhooks — this is the standard, documented usage pattern. The attacker needs only to install the app on a self-created development shop, capture one legitimately delivered webhook, and directly POST a modified-header copy to the app's public webhook endpoint. No secrets, no privileged access, and no session are required. Cost is very low and the attack is trivially repeatable.

### Recommendation
Bind `shop`, `topic`, `api_version`, and `webhook_id` into the signed material, or otherwise cryptographically bind the header values used downstream to the HMAC verification (e.g., verify against a canonical string that includes these header values, matching how `AuthQuery#to_signable_string` includes all downstream-consumed fields). At minimum, `Registry.process` should not trust `request.shop`/`request.topic` from headers alone; it should be validated against the specific webhook subscription/session context, not merely "does the raw body match some previously-issued HMAC."

### Proof of Concept
```ruby
# test/webhooks/registry_forgery_test.rb (conceptual)
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryForgeryTest < Test::Unit::TestCase
      def setup
        super
        ShopifyAPI::Webhooks::Registry.clear
        @handler = FakeWebhookHandler.new
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "customers/data_request", delivery_method: :http, path: "/webhooks", handler: @handler,
        )
      end

      def test_forged_shop_and_topic_pass_validation
        raw_body = '{"order_id":123}'
        secret = ShopifyAPI::Context.api_secret_key
        hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), secret, raw_body)
        b64_hmac = [hmac].pack("H*").then { Base64.strict_encode64(_1) } rescue Digest.hexencode(Base64.decode64(Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body))))

        # legit body+hmac, but attacker-forged shop/topic headers
        request = ShopifyAPI::Webhooks::Request.new(
          raw_body: raw_body,
          headers: {
            "x-shopify-topic" => "customers/data_request", # forged to a mandatory/sensitive topic
            "x-shopify-hmac-sha256" => Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body)),
            "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, attacker doesn't own this shop
          },
        )

        assert(ShopifyAPI::Utils::HmacValidator.validate(request)) # passes despite forged headers
        ShopifyAPI::Webhooks::Registry.process(request)
        assert_equal("victim-shop.myshopify.com", @handler.data.shop) # handler trusted forged shop
      end
    end
  end
end
```
Assertion pair demonstrating the broken binding: `HmacValidator.validate(request)` returns `true` while `request.shop`/`request.topic` (unsigned headers) differ from the shop/topic that actually produced the HMAC — i.e. `computed_signature(raw_body) == received_signature` holds, but `request.shop == "victim-shop.myshopify.com"` was never covered by that equality.
