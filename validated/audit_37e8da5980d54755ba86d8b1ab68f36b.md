## Title
HyperFungibleToken burns sender tokens before dispatch, but both delivery (`onAccept`) and refund (`onPostRequestTimeout`) are gated by `whenNotPaused`, letting an admin pause trap already-burned funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` irreversibly burns the sender's tokens and dispatches a cross-chain POST request before any confirmation that the message will ever be delivered or refunded. The two on-chain paths that can make the sender whole again — successful minting via `onAccept` on the destination, and re-minting via `onPostRequestTimeout` on the source after expiry — are both restricted by the `whenNotPaused` modifier. If the contract is paused (by the owner, for any operational reason) at the moment either path would execute, both revert, and the burned value has no other recovery route until the owner unpauses.

### Finding Description
`send()` burns tokens unconditionally and only then dispatches the ISMP request: [1](#0-0) 

The success path that would make the recipient (or, on timeout, the original sender) whole is `onAccept`, which mints the destination amount, but only when the contract is not paused: [2](#0-1) 

The recovery path for a request that never gets delivered is `onPostRequestTimeout`, which re-mints the burned amount back to the sender as a refund — but it is likewise gated by `whenNotPaused`: [3](#0-2) 

Both `pause()`/`unpause()` are owner-only and toggle the same `Pausable` state that both callbacks check: [4](#0-3) 

This mirrors the reported bug class exactly: a user's asset is destroyed/committed in one transaction (`_burn`), while every remaining path to either complete or reverse that action is blocked by the same pause flag. There is no alternate unprivileged function that lets a user reclaim burned tokens while paused — neither a normal delivery nor a timeout-triggered refund can execute. The documentation itself confirms this design: "When paused, `HyperFungibleToken` blocks all ERC20 transfers ... in addition to cross-chain `send()` and `onAccept()`." No mention is made of pause exempting refunds, and the `onPostRequestTimeout` code confirms the `whenNotPaused` modifier applies there too. [5](#0-4) 

The same pattern is duplicated verbatim in the upgradeable variant: [6](#0-5) 

### Impact Explanation
A user calling `send()` has their tokens burned immediately and irreversibly. If the owner pauses the contract for any reason (e.g., precaution during an unrelated incident) before the message is delivered on the destination chain, and the pause is still active once the request's `timeoutTimestamp` elapses, the user has no way to recover their funds: `onAccept` cannot mint on the destination, and `onPostRequestTimeout` cannot re-mint the refund on the source. The funds remain frozen for as long as the pause persists — this can be indefinite, since there is no time bound on how long the owner may leave the contract paused. This is a freezing-of-funds condition directly analogous to the reported `redeemDollar`/`collectRedemption` issue: value is already extracted from the user, but the sole recovery mechanisms are gated by the same switch that caused the delay.

### Likelihood Explanation
This requires no attacker — any ordinary `send()` call is at risk any time the owner pauses the contract across a POST request's lifecycle boundary (mid-flight delivery or right around timeout expiry), which is a foreseeable operational scenario (e.g. pausing during a security incident affecting an unrelated chain or token) rather than a contrived edge case. Because pausing is intended precisely to be usable during emergencies — exactly when in-flight cross-chain messages are most likely to be pending — the overlap between "contract is paused" and "a user has an unresolved in-flight burn" is a realistic, not merely theoretical, occurrence.

### Recommendation
Do not gate the recovery/refund path (`onPostRequestTimeout`) — and arguably delivery (`onAccept`) as well — behind the same `whenNotPaused` flag that governs new outbound `send()` calls. At minimum, `onPostRequestTimeout` should always be callable regardless of pause state so that a user whose tokens were burned before the pause can always recover them once the timeout has legitimately elapsed. If pausing `onAccept` is required for security (e.g., to stop malicious inbound mints), consider using a separate flag from the one that blocks refunds, so an emergency pause cannot simultaneously trap funds that are strictly owed back to users.

### Proof of Concept
1. User calls `HyperFungibleToken.send()` with `timeout = T` seconds; `_burn(msg.sender, amount)` executes immediately (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:265`), and an ISMP POST request is dispatched.
2. Before the request is delivered to the destination, the contract owner calls `pause()` (e.g., for reasons unrelated to this specific transfer).
3. The destination relayer attempts to deliver the request via `onAccept`; the call reverts due to `whenNotPaused` (`:292`). No mint occurs.
4. Time passes; the request's `timeoutTimestamp` elapses while the contract is still paused.
5. A relayer or the user attempts to process the timeout via `onPostRequestTimeout` to reclaim the burned tokens; this call also reverts due to `whenNotPaused` (`:321`).
6. As long as the owner keeps the contract paused, the user's burned tokens cannot be minted on the destination nor refunded on the source — the value is frozen with no user-callable path to reclaim it.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
