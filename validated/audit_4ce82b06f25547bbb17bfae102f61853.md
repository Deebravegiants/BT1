## Title
Webhook `shop-domain` (and other Shopify headers) are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers that are never included in the signed payload. `Registry.process` validates the HMAC over the body only and then forwards `request.shop` to the app's handler as the tenant identifier, so the "authenticated" byte range (body) and the "trusted" tenant claim (`shop-domain` header) are not the same data.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then dispatches the handler using `request.shop`, `request.topic`, etc., taken from those same unsigned headers: [3](#0-2) 

The security-relevant equality that should hold is:
`shop authenticated by HMAC == shop used to attribute the webhook to a tenant`

In this implementation that equality does not hold — the HMAC only proves "this body was signed with the app's `api_secret_key`", not "this body was signed for shop X". Because the app's `api_secret_key` is the same across every merchant/tenant that installs the app, any attacker who controls their own shop with the app installed can capture a legitimately-signed webhook (body + HMAC) generated by their own store activity (e.g. `orders/create`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. The HMAC check in `HmacValidator.validate` still passes because it only checks the untouched body, and the forged `shop` value flows unchecked into `WebhookMetadata` for handler processing.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker with no access to any victim credentials can make the app process (and attribute) webhook data as if it originated from a shop they do not own. Depending on how the host application's webhook handlers use `data.shop` (as most Shopify apps do, to key session/database lookups, update per-shop caches, trigger per-shop side effects, etc.), this can be leveraged for cross-tenant data confusion/corruption — reading, associating, or mutating data under an incorrect shop's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user with a merchant/dev store where the target app is installed (trivial for any public app, and common for apps in dev/free-trial stores) — no access to the app's `client_secret`, no stolen token, no social engineering, and no privileged account. It only requires network access to the app's public webhook endpoint, which is inherently internet-reachable.

### Recommendation
Include the tenant-identifying and message-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) inside the signed payload that is HMAC-verified, or otherwise cryptographically bind the header values to the specific signature (e.g., validate that the `hmac` was computed over `shop + topic + body`, not just `body`). At minimum, document that `Request#shop`/`#topic` are unauthenticated and must not be trusted for tenant attribution without additional binding.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a real webhook event (e.g., creates an order), capturing the legitimate raw body and its valid `x-shopify-hmac-sha256` value (both signed using the app's shared `api_secret_key`).
2. Attacker replays the exact same raw body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the HMAC — it passes because the body is unmodified: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though the payload was never signed for that shop, resulting in the app processing forged tenant data. [5](#0-4)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
