## Title
Any single invalid/duplicate/timed-out message in a `handle_unsigned` batch aborts delivery of every other valid message in that batch - (File: `modules/pallets/ismp/src/impls.rs`)

## Summary
`pallet-ismp`'s `handle_unsigned` extrinsic (and its underlying `execute()` helper) processes an entire `Vec<Message>` batch as a single atomic, transactional unit. If any one message in the batch is invalid — a duplicate request, a request that has since timed out, or one that targets the wrong destination — the whole extrinsic returns `Err`, `#[frame_support::transactional]` rolls back every state change, and none of the other, perfectly valid messages in the batch get delivered. This is the same bug class as Karak's `[M-05]`: an atomic batch of independent operations where a single "poisoned" element (whose validity can change between the time the batch is assembled and the time it executes) causes the whole batch to fail, blocking delivery of unrelated, legitimate items.

## Finding Description
`Pallet::<T>::execute()` maps `handle_incoming_message` over every message in the batch and immediately short-circuits via `.collect::<Result<Vec<_>, _>>()`: [1](#0-0) 

Any individual message failure inside the per-request handler — e.g. a duplicate receipt or a timed-out request — surfaces as an `Err` for the *whole* batch: [2](#0-1) 

`handle_unsigned` wraps `execute()` in `#[frame_support::transactional]`, so on that single `Err` every storage write performed for every other message in the batch — including legitimate `on_accept` callbacks that already executed for earlier messages in the iteration — is rolled back: [3](#0-2) 

This behavior is explicitly documented as intended: "this will short-circuit and revert if any of the provided messages are invalid," both in the pallet call docs and the doc site: [4](#0-3) [5](#0-4) 

This is validated as an unsigned extrinsic, so it is fully permissionless — `validate_unsigned` itself calls `Self::execute(messages.clone())` and rejects the whole submission (`InvalidTransaction::BadProof`) if any message fails: [6](#0-5) 

Notably, the EVM side of the protocol (`HandlerV2`/`EvmHost`) deliberately does **not** have this failure mode for per-request delivery: `EvmHost.dispatchIncoming` isolates each individual `onAccept` call behind a low-level `.call` and swallows a revert by simply not storing the receipt (allowing retry), rather than reverting the whole batch: [7](#0-6) 

The Substrate side lacks this isolation for message-level validity failures (duplicate/timeout/destination checks happen *before* any isolation boundary, at the batch level), so it inherits exactly the atomicity problem the Karak report describes: a state that can shift between "batch assembly" and "batch execution" (here, a request being independently delivered/timed-out by someone else, or simply timing out due to elapsed time) can invalidate one element and sink the entire batch.

## Impact Explanation
A relayer (or anyone building `handle_unsigned` batches for efficiency) that bundles N independent requests/responses/timeouts into one extrinsic risks having the entire batch fail — and all its storage effects rolled back — because of a single stale/duplicate/timed-out element. Since `handle_unsigned` is permissionless and unsigned (free to submit), an attacker can also race a relayer's multi-message batch: front-run it with a single-message submission that delivers one of the same requests first, turning that request into a "duplicate" by the time the relayer's larger transactional batch executes, and causing that larger batch to revert in its entirety. The net effect is a route that legitimately cannot deliver otherwise-valid, correctly proven cross-chain messages within the same block/transaction, requiring the relayer to detect the poisoned message, exclude it, and resubmit — with no partial progress recorded despite the transactional wrapper having already computed/verified proofs and dispatched module callbacks for the valid entries before the rollback. This matches the "route unable to deliver messages" impact category.

## Likelihood Explanation
Likelihood is inherent to normal relayer operation, not just theoretical attacker behavior: any relayer that batches multiple pending requests for gas efficiency (a documented and expected usage pattern) is exposed whenever timing windows or duplicate deliveries from another relayer intersect with their batch composition. Because `handle_unsigned` is a free, permissionless, unsigned extrinsic, griefing via front-running a chosen message inside a larger batch requires no special privilege or stake, only observing the pending batch/mempool.

## Recommendation
Mirror the EVM host's isolation strategy on the Substrate side: process each message in the `handle_unsigned` batch independently (e.g., use `Weight`-tracked per-message dispatch with `frame_support::dispatch::PostDispatchInfo`-style partial success, or drop `#[frame_support::transactional]` in favor of per-message try/catch semantics), so that a duplicate/timed-out/misdirected message only fails to deliver itself (leaving it retryable later, as is already done for module-callback failures via `delete_request_receipt`) instead of reverting storage for every other message that was otherwise valid and already verified by the same membership proof.

## Proof of Concept
1. Relayer A observes N pending, deliverable requests (valid proofs, not yet timed out, no receipts) and assembles them into a single `handle_unsigned` batch to save gas.
2. Before Relayer A's transaction lands, Relayer B (or an attacker) submits a single-message `handle_unsigned` extrinsic that delivers request #k from that same set (a legitimate, permissionless action).
3. Relayer A's batch is now included: `execute()` iterates the messages; when it reaches request #k, `host.request_receipt(&req).is_some()` is true, producing `Err(Error::DuplicateRequest)`.
4. `.collect::<Result<Vec<_>, _>>()` in `impls.rs::execute` short-circuits on this `Err`; `handle_unsigned`'s `#[frame_support::transactional]` rolls back all storage writes performed for the batch, including the `on_accept` side effects and receipts already written for the first `k-1` valid, non-conflicting requests.
5. Relayer A's entire N-message batch fails and must be resubmitted (after filtering out request #k), even though N-1 of the messages were fully valid and independently deliverable.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
