### Title
Stranded/residual token balance in `LifiExternalAction` can be swept into an attacker's own swap output via the standing `approveUnlimited` allowance - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol` / `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap` measures `swappedAmount` purely as the output-token balance delta around an attacker-supplied `externalActionMetadata` call to the LI.FI router, while `LifiExternalAction.callRouter` grants the router an unlimited, persistent ERC-20 allowance over the action contract via `approveUnlimited`. Neither function checks that the router actually consumed exactly `inputAmount` of `inputToken`. Any input-token balance left sitting in the action contract from a prior transaction (dust, partial-fill refund, or a direct token transfer) can be pulled by the router using the already-standing allowance and swapped together with the current transaction's funds, and the entire resulting output is credited to the current caller's own UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving the action contract in a transaction == `-deltaAmountChanges[0]`* that Hinkal transferred to it for that transaction, and the resulting `swappedAmount`/output UTXO should derive solely from that amount.

In `contracts/external-actions/swaps/ExternalActionSwap.sol::swap` (lines 44-101), `inputAmount` is derived from `deltaAmounts[0]` [1](#0-0) , and `swappedAmount` is whatever `callRouter` reports, which then is wholly sent to `msg.sender` (Hinkal) and used to construct the sole output `UTXO` [2](#0-1) . There is no check that the input token balance of the action actually decreased by exactly `inputAmount`.

In `contracts/external-actions/swaps/LifiExternalAction.sol::callRouter`, the allowance to `router` is set to `type(uint256).max` and, critically, is only *re-approved if it has decayed below half of max* [3](#0-2) , meaning the max allowance persists across transactions and blocks once set. `callRouter` then blindly executes attacker-controlled `externalActionMetadata` against the router and measures `swappedAmount` solely as `outputToken` balance-after minus balance-before [4](#0-3) .

Because `externalActionMetadata` is raw calldata forwarded verbatim to `router.call(...)`, the attacker (who is also the prover/signer of their own proof) fully controls which amount of `inputToken` the router pulls via `transferFrom` under the pre-existing unlimited allowance. The circuit and `performHinkalChecks`/`calldataHash` binding (`CircomDataBuilder.getHashedCalldata`) only ensure the metadata is self-consistent with the attacker's own signed proof [5](#0-4)  — they do not constrain what the metadata itself instructs the router to pull, nor tie it to `inputAmount`. If, from a prior transaction, any input-token balance is left in the `LifiExternalAction` contract (e.g., a partial-fill refund from LI.FI that isn't swept back, rounding dust, or an ERC-20 `transfer` sent directly to the action address by anyone, since it is a plain external contract that can receive tokens), the attacker can construct `externalActionMetadata` in their own transaction that causes the router to consume that residual balance together with their own `inputAmount`. The resulting extra output is indistinguishable from the transaction's legitimate swap output and is credited entirely to the attacker's own UTXO via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)` [6](#0-5) .

`Hinkal.sol::transact` only checks Hinkal's own overall balance delta against `erc20TokenAddresses`/`amountChanges` for the two swap tokens [7](#0-6) ; it never checks the action contract's balance before/after the call, so it cannot detect that more value left the action than was sent to it.

### Impact Explanation
An attacker can capture value that does not belong to their declared `deltaAmountChanges`: any residual/stranded ERC-20 balance sitting in the `LifiExternalAction` contract (which may originate from another user's dust/partial-fill refund, or from tokens directly transferred there) is routed into the attacker's own shielded output UTXO. This is theft of value the protocol/other users left "parked" in the action, matching the Critical category "direct theft of shielded or in-flight user funds." It is repeatable across blocks as long as residual balance and the standing unlimited allowance exist, and the attacker can even self-seed the residual (by sending tokens directly to the action address) to test/trigger sweeps, though the more damaging case is capturing genuinely stranded third-party residue.

### Likelihood Explanation
Preconditions: (1) the LI.FI router allowance from the action contract must already be at `type(uint256).max` (true after any prior successful ERC-20 swap through this action, since it is never revoked), and (2) some input-token balance must be sitting in the action contract beyond what the current transaction funded (from dust/partial fills, or attacker-seeded). Both conditions are attacker-achievable and cost-free beyond gas — the attacker only needs to submit their own valid Hinkal proof with crafted `externalActionMetadata`, which is fully within an unprivileged user's control. Likelihood is moderate-to-high given LI.FI/router-style aggregators commonly leave small unswept remainders and the allowance mechanism is designed to persist.

### Recommendation
Enforce a strict balance-based accounting in `callRouter`/`swap`: record the input-token balance before and after the router call and require the decrease equals exactly `inputAmount` (revert otherwise), rather than trusting the router calldata implicitly. Additionally, avoid unlimited persistent allowances — approve only the exact `inputAmount` needed per call and reset to zero afterward, so no standing allowance can be exploited across transactions using stray or maliciously placed balances.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI router), and a mock ERC-20 `inputToken`/`outputToken`.
2. Simulate residual state: directly `inputToken.transfer(address(lifiExternalAction), residualAmount)` from an unrelated address (or via a mock "prior tx" that leaves a partial-fill refund), and separately perform one legitimate swap through the action so `approveUnlimited` sets the router allowance to `type(uint256).max`.
3. As the attacker, generate a valid Hinkal proof/`circomData` with `deltaAmountChanges[0] = -smallInputAmount`, but craft `externalActionMetadata` so the mock router's call pulls `smallInputAmount + residualAmount` from the action via `transferFrom` (using the existing unlimited allowance) and returns proportional `outputToken`.
4. Call `Hinkal.transact(...)` as attacker.
5. Assert: `outputToken` balance the attacker's UTXO/`msg.sender` receives (`amountToSendToHinkal`) is strictly greater than the amount that would correspond to swapping only `smallInputAmount`, i.e., assert `swappedAmount > f(smallInputAmount)` and that `tokens_leaving_action != -deltaAmountChanges[0]`, demonstrating the attacker captured `residualAmount`'s worth of output beyond what Hinkal sent to the action for this transaction.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
