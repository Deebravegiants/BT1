### Title
Attacker-controlled swap route executes arbitrary pool code and hijacks the caller’s authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
Controller strategy entrypoints accept opaque route bytes and pass them to the configured router without identifying or allowlisting the venues they name. A malicious route can place attacker-controlled code inside the caller’s invocation tree, where it can request and execute additional token transfers from that caller if the simulated authorization tree is signed.

### Finding Description
`swap_collateral` accepts a caller-provided `swap: Bytes` argument and forwards it to `process_swap_collateral` without inspecting its contents. [1](#0-0)  The strategy processor requires owner or delegate authorization, withdraws the selected collateral, and sends the opaque route to the shared swap helper. [2](#0-1)  The helper checks only that the route is nonempty, authorizes one exact input transfer to the configured router, invokes `execute_strategy`, and then measures token deltas. [3](#0-2) 

The decoded route supplies an address registry containing pool and token addresses, while each instruction selects a venue and indexes that registry. [4](#0-3)  Swap instructions resolve `pool`, `token_in`, and `token_out` directly from caller-controlled registry indices before dispatching the hop. [5](#0-4)  The router dispatch selects an adapter by venue but performs no venue/pool allowlist check; it only measures input and output balance changes around the external call. [6](#0-5) 

This is analogous to command injection: attacker-controlled route data is treated as trusted executable routing instructions, including the address of code to execute. The protocol’s threat model confirms that pool addresses are payload-selected, unallowlisted, and can place third-party code below the caller’s authorization. [7](#0-6)  Once that malicious code requests `token.transfer(victim, attacker, amount)`, Soroban records it as a child authorization beneath the caller’s strategy entry; if the caller signs the simulated tree, the unrelated wallet transfer executes. [8](#0-7) 

The same opaque route argument is reachable through `swap_debt` and `repay_debt_with_collateral`, so the issue is not limited to collateral conversion. [9](#0-8) [10](#0-9) 

### Impact Explanation
A malicious venue can steal arbitrary tokens held by the caller, including tokens unrelated to the lending position and outside the protocol’s routed amount. The test demonstrates Alice’s entire unrelated wallet-token balance moving to an attacker while the strategy still receives a fair output and completes successfully. [11](#0-10) 

Measured router output, route minimum-output checks, and final account health checks do not bound this loss because the stolen transfer targets the caller’s wallet rather than the controller’s input or output balance. [12](#0-11)  The accepted impact is theft of user funds.

### Likelihood Explanation
An unprivileged attacker can deploy a contract that implements the selected venue interface, encodes it as a hop pool, and lure or integrate a victim into submitting a strategy containing that route. The route can otherwise produce a valid output, so it can satisfy the controller’s measured-output and solvency checks while the malicious transfer appears as an authorization child generated by simulation. [13](#0-12) 

The exploit requires the victim to sign the poisoned authorization tree; an attacker cannot execute the victim’s transfer without that authorization. However, the repository’s test shows that transaction simulation presents the malicious transfer beneath the otherwise legitimate `swap_collateral` entry, making it feasible for a user or wallet that does not independently decode every route and authorization child to approve it. [14](#0-13) 

### Recommendation
Maintain an on-chain venue/pool registry and reject any route pool that is not registered for its selected venue, rather than treating payload-supplied pool addresses as executable endpoints. Alternatively, decode and validate the complete route at the controller boundary against a signed venue manifest before calling `execute_strategy`. Clients should additionally reject any authorization tree containing children beyond the single expected input transfer or the documented contract-authorization entries.

### Proof of Concept
The repository contains a complete authorization-injection scenario in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice supplies USDC and holds an unrelated wallet token.
2. The attacker deploys a rogue pool configured with `(victim=alice, token=wallet_token, to=attacker, amount=wallet_balance)`. [15](#0-14) 
3. The route names that pool while retaining a valid USDC input, ETH output, and positive output amount. [16](#0-15) 
4. Alice calls:

```rust
controller.swap_collateral(
    alice,
    account_id,
    usdc_hub_asset,
    50_000_000_000,
    eth_hub_asset,
    malicious_route,
);
```

The public entrypoint passes those exact arguments into the strategy processor. [1](#0-0) 

5. During the router call, the rogue pool invokes `wallet_token.transfer(alice, attacker, wallet_balance)`. Simulation records that token transfer as a child beneath Alice’s `swap_collateral` authorization. [17](#0-16) 
6. If Alice signs the simulated tree, the strategy succeeds, the pool receives fair collateral output, Alice’s wallet-token balance becomes zero, and the attacker receives the full wallet balance. [18](#0-17)

    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,

    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
