## Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once the HMAC over the raw request body validates, then hands the caller-supplied `shop` header straight to the app's handler as the tenant identifier — without that header ever being part of the signed material. This breaks the intended identity binding `shop (verified) == shop (used by handler)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled from HTTP headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then dispatches using the unauthenticated `request.shop`: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app — it is not shop-specific: [4](#0-3) 

Consequences: any entity that can obtain one *valid* `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a real webhook for it) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. Because `to_signable_string` never includes the `shop` header, the HMAC check in `Utils::HmacValidator.validate` still passes, and `Registry.process` calls the handler with `WebhookMetadata` carrying the attacker-chosen `shop` value: [5](#0-4) 

The documented handler contract explicitly tells implementers to trust `data.shop` as "The shop domain of the webhook" and to use it directly (e.g. as a tenant key for enqueuing work): [6](#0-5) 

This is the exact analog called out in the rules: a field (`shop`) that is *acted on* by the gem's own dispatch logic but is *not covered by the HMAC* that is supposed to authenticate the request. The equality that should hold is:
`shop bound by HMAC == shop delivered to handler`
but in this implementation the left side does not exist — the gem asserts authenticity of the body only, then unconditionally trusts a disjoint, attacker-controllable header for tenant attribution.

### Impact Explanation
This allows cross-tenant impersonation: an attacker who is themselves a legitimate (even trial) merchant of the app can generate a validly-signed webhook body for their own shop, then submit it directly to the app's public webhook callback URL with a forged `shopify-shop-domain` header pointing at a victim shop. The gem will accept it as authentic (HMAC passes) and dispatch it to the app's business logic tagged as belonging to the victim shop. Depending on what the host application does with `data.shop` (as documented, using it to key state/DB writes, `perform_later(shop_domain: data.shop, ...)`), this can lead to cross-tenant data corruption, spoofed events attributed to another merchant, or triggering privileged per-shop workflows (e.g. mandatory GDPR webhooks `shop/redact`, `customers/redact`, `customers/data_request`) against a shop the attacker does not control. This satisfies the "Critical — cross-tenant access" bar since the identity boundary between tenants is broken using only the gem's own webhook-verification code path, without any credential belonging to the victim.

### Likelihood Explanation
Likelihood is meaningful: the webhook endpoint is by definition internet-reachable (Shopify posts to it over the open internet), and the only thing an attacker needs is one legitimately-signed body from their own account — trivially obtainable by installing the target app on a dev/trial store and observing a real webhook delivery. No secret material belonging to the app or the victim is required; only knowledge that the endpoint accepts arbitrary transport-layer requests (nothing in this gem enforces that requests originate from Shopify's IP ranges or over an authenticated channel — that verification is left entirely to the HMAC, which does not cover `shop`).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) claim to the signed material, or otherwise verify it independently of the header before it is handed to application handlers:
- Extend `VerifiableQuery#to_signable_string` for `Webhooks::Request` to include the `shop`, `topic`, and `webhook_id` headers in the signable string (this requires coordinating with Shopify's signing scheme, since currently only the body is signed by Shopify's webhook HMAC), or
- Document and/or enforce that host applications must cross-check `data.shop` against a shop that is known to have a valid, currently-registered webhook subscription/session before trusting it as a tenant key, and make this an explicit, mandatory step in `Registry.process` rather than an unstated expectation left to the integrator.
- At minimum, update `docs/usage/webhooks.md` to clearly warn that `data.shop` is derived from an HTTP header not covered by the HMAC signature and must not be trusted as an authenticated tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with a body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`. The attacker captures `B` and the valid HMAC value.
3. Attacker sends their own POST request directly to the same public webhook endpoint URL, reusing body `B` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` calls `to_signable_string` (which returns only `@raw_body == B`), computes `HMAC(secret, B)`, and it matches the header value supplied by the attacker → validation succeeds.
5. `Registry.process` proceeds, builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the registered handler, which — per the documented contract — treats `data.shop` as authoritative, causing the app to process/store data as if it came from `victim-shop.myshopify.com`. # typed: strict

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
