### Title
`Webhooks::Request#to_signable_string` signs only `@raw_body`, letting an attacker reuse a validly-signed body under forged `shop-domain`/`topic`/`webhook-id`/`api-version` headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Utils::VerifiableQuery` requires only `hmac` and `to_signable_string`, with no requirement that the signable string cover every field a consumer later trusts. `Auth::Oauth::AuthQuery#to_signable_string` [1](#0-0)  covers all of its consumed attributes (`code`, `host`, `shop`, `state`, `timestamp`), but `Webhooks::Request#to_signable_string` returns only the raw HTTP body [2](#0-1)  while `Webhooks::Registry.process` trusts `request.topic`, `request.shop`, `request.api_version`, and `request.webhook_id` — all parsed from unsigned headers — to dispatch the handler and populate `WebhookMetadata` [3](#0-2) .

### Finding Description
The invariant that should hold is: `HmacValidator.validate(request)` passing ⇒ every field the app subsequently trusts (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`, `request.body`) was part of the signed payload. Concretely: `to_signable_string == f(shop, topic, webhook_id, api_version, body)` should hold for the webhook implementation, mirroring how `AuthQuery#to_signable_string` binds `code`/`host`/`shop`/`state`/`timestamp`.

Instead, `Webhooks::Request#to_signable_string` is defined as `@raw_body` only [4](#0-3) , while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, `shopify-webhook-id`) via `shopify_header` [5](#0-4) . `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(..., verifiable_query.to_signable_string)` and compares it against the header `hmac-sha256` value [6](#0-5) , so the HMAC never covers those headers.

`Registry.process` then uses the already-validated `request` object to route to a handler by `request.topic` and construct `WebhookMetadata` with `shop: request.shop`, `api_version: request.api_version`, `webhook_id: request.webhook_id` [3](#0-2)  — none of which the HMAC check attested to.

Attacker flow: per the rules, an attacker may create their own dev shop, install the app, and receive a legitimately-signed webhook (raw body + correct `hmac-sha256`) for their own shop/topic. They can replay that exact body and HMAC to the app's webhook endpoint while substituting `shopify-shop-domain` (to impersonate a different/victim shop), `shopify-topic` (to trigger a different handler, e.g. `shop/redact` or `customers/data_request`), or `shopify-webhook-id`/`shopify-api-version`. Because `HmacValidator.validate` only checks the raw body against the secret, the forged headers pass verification unchanged, and `Registry.process` will happily route the payload under the attacker-chosen shop/topic/id.

No other guard closes this gap: `HmacValidator.validate` only compares `to_signable_string` output [7](#0-6) ; there is no `ShopValidator.sanitize!` call in the webhook path (that helper is only used in OAuth/token-exchange flows, not `Registry.process`); `WebhookMetadata` is a plain `T::Struct` with no additional integrity checks [8](#0-7) .

### Impact Explanation
An app relying on `request.shop` for tenant attribution (a very common pattern — e.g., looking up an `OfflineSession` by `shop` to act on data) can be induced to process a webhook it believes originated from shop B when it was, in fact, signed for and captured from the attacker's own shop A. This is a genuine cross-tenant confusion / forged-webhook-acceptance class of bug: the signature check passes (`Critical - authentication bypass`, since the app is deceived into treating unauthenticated header data as if it had been verified by HMAC), and repeat requests can be sent against arbitrary target shop names since `shop-domain` is arbitrary attacker-controlled text with no further validation in the webhook path.

### Likelihood Explanation
Preconditions are modest and fully within the described attacker capability: register a dev shop, subscribe a webhook, capture one legitimately signed callback (body + hmac header), then replay it to the target app's webhook endpoint with modified headers. No secret material is needed. This is repeatable for every replay and works against any topic/shop string the attacker chooses, limited only by what the app itself does with `request.shop`/`request.topic` downstream (severity depends on how the app uses these unauthenticated-but-"validated" fields, but the gem's `VerifiableQuery`/`HmacValidator` contract gives no protection here).

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or `HmacValidator`) to bind the header values the app trusts — at minimum `shop`, `topic`, `webhook_id`, and `api_version` — into the signed material, or otherwise document/enforce that only `body` is authenticated and require consumers to independently verify `shop`/`topic` via a separate channel (e.g., cross-check `shop` against an existing session). Alternatively, strengthen the `VerifiableQuery` interface contract to require implementations assert (via a shared test or Sorbet-level check) that `to_signable_string` covers every attribute exposed by the implementer and consumed by `HmacValidator`'s callers.

### Proof of Concept
```ruby
# test/utils/verifiable_query_coverage_test.rb
require "test_helper"

module ShopifyAPITest
  module Webhooks
    class SignatureCoverageTest < Minitest::Test
      def test_signed_body_replay_with_forged_shop_and_topic_passes_hmac
        secret = ShopifyAPI::Context.api_secret_key
        body = '{"id":1}'
        hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

        # Attacker's own legitimately-signed webhook (their own shop/topic)
        legit_headers = {
          "shopify-topic" => "orders/create",
          "shopify-hmac-sha256" => Base64.encode64(hmac),
          "shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: legit_headers)
        assert(ShopifyAPI::Utils::HmacValidator.validate(legit_request))

        # Replay same body+hmac but forge shop-domain and topic
        forged_headers = legit_headers.merge(
          "shopify-shop-domain" => "victim-shop.myshopify.com",
          "shopify-topic" => "customers/redact",
        )
        forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

        # BUG: HMAC still validates even though shop/topic changed, because
        # to_signable_string only covers @raw_body.
        assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))
        assert_equal("victim-shop.myshopify.com", forged_request.shop)
        assert_equal("customers/redact", forged_request.topic)
      end
    end
  end
end
```
This demonstrates that `to_signable_string`'s coverage (raw body only) does not match the fields (`shop`, `topic`, `webhook_id`, `api_version`) that `Webhooks::Registry.process` trusts once `HmacValidator.validate` returns `true`, confirming the divergence between `AuthQuery` (full coverage) and `Webhooks::Request` (partial coverage) breaks the signature-coverage invariant.
