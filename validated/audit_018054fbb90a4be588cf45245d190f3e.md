### Title
Precision loss in `pallet-hyper-fungible-token`'s decimal conversion permanently burns/locks dust on cross-chain token transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance`, used in `on_accept` to scale an incoming ERC20-denominated amount down to the local (substrate) asset's decimal precision, truncates via integer division. Since the EVM `send()` allows an arbitrary `uint256` amount to be burned, any amount that is not an exact multiple of the decimal-scaling factor loses its remainder permanently: it is burned in full on the EVM side but minted short on the substrate side, with no accounting, refund, or dust-recovery mechanism.

### Finding Description
`convert_to_balance` scales an ERC20 `U256` amount down to local decimals by plain division: [1](#0-0) 

This is invoked in `on_accept`, which is the module handler reached when a relayer delivers a message dispatched by the peer EVM `HyperFungibleToken` contract: [2](#0-1) 

`register_token`/`update_token` only enforce `erc_decimals >= local_decimals` (e.g. 18 on EVM vs 12 on substrate, scale factor `10^6`); they never enforce that transferred amounts are multiples of that scale factor: [3](#0-2) 

On the EVM side, any signed-in user can call `send()` with an arbitrary `uint256 amount`, which is fully burned before dispatch: [4](#0-3) 

When the relayer delivers this message to the substrate chain, `on_accept` divides `message.amount` by `10^(erc_decimals - local_decimals)` and mints/releases only the truncated (floor) result to the beneficiary. Any remainder below one local-decimal unit (up to `10^(erc_decimals-local_decimals) - 1` ERC20 sub-units, e.g. up to `999999` wei-equivalent units per transfer at a 6-decimal gap) is burned on the source chain but never minted anywhere on the destination — it disappears with no event, no dust ledger, and no recovery path. This mirrors the reported `WIchiFarm#pendingRewards` bug class exactly: two independently-scaled decimal domains (9dp vs 18dp there; `local_decimals` vs `erc_decimals` here) combined via integer division causes systematic truncation loss instead of trivial rounding.

### Impact Explanation
Every cross-chain transfer from an EVM chain to the substrate chain through this pallet can lose up to `10^(erc_decimals - local_decimals) - 1` units of value to truncation, with no compensating mechanism. For tokens with a wide decimal gap (the common case: 18dp ERC20 vs 6/10/12dp substrate assets), this is not negligible dust — it is a deterministic amount that a user can be made to lose on every transfer, and which accumulates value permanently removed from circulation (burned on EVM, never minted on substrate) with no owner. This is a permanent, protocol-level loss of user funds triggered by a single unprivileged transaction (`send()`), matching the "concrete... permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
High. This triggers on every ordinary transfer whose amount (in ERC20 units) is not an exact multiple of the configured decimal scale factor — the overwhelmingly common case for arbitrary user-chosen amounts. No malicious actor is needed; a normal user calling `HyperFungibleToken.send()` with a typical amount will trigger this loss, and the relayer/dispatch path requires no special privilege to reach `on_accept`.

### Recommendation
- Either reject transfers whose ERC20 amount is not an exact multiple of `10^(erc_decimals - local_decimals)` (return the excess to the sender / revert `send()`), or
- Track and carry forward the truncated remainder (e.g., accumulate dust per asset/chain pair and allow it to be reconciled/withdrawn once it exceeds one local unit), similar to how `WConvexPools` was recommended to reduce precision loss by computing the reward/amount difference before scaling rather than scaling each side independently and subtracting.
- At minimum, emit an event with the truncated remainder amount so operators can detect and account for the loss, and consider validating on the EVM `send()` side that `amount % scaleFactor == 0` before burning, preventing the dust from being destroyed in the first place.

### Proof of Concept
1. Register a token with `erc_decimals = 18` (EVM) and `local_decimals = 12` (substrate) — passes the `ensure!(config.decimals >= local_decimals, ...)` check at `modules/pallets/hyper-fungible-token/src/lib.rs:352-355`, scale factor `10^6`.
2. A user calls the EVM `HyperFungibleToken.send()` with `amount = 1_000_000_999_999` (i.e., not a multiple of `1e6`), which is fully burned:
   `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:264-266`.
3. A relayer delivers the message; `on_accept` on substrate computes
   `amount = convert_to_balance(1_000_000_999_999, 18, 12)` → `1_000_000_999_999 / 10^6 = 1_000_000` (floor), discarding `999_999` units — `modules/pallets/hyper-fungible-token/src/module.rs:82-91`, `modules/pallets/hyper-fungible-token/src/impls.rs:43-52`.
4. The beneficiary receives `1_000_000` local units instead of the equivalent of `1_000_000_999_999` ERC20 units; the `999_999`-unit remainder was burned on EVM and is never minted or refunded anywhere — a permanent loss of value.
