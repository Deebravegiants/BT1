## Custody Analysis: Denylist Bypass via Store-Ownership Reassignment in `usdk` Stablecoin Example

### Title
Denylist check keyed on live `object::owner(store)` instead of the account whose funds are held — a denylisted holder can transfer store ownership to launder frozen balance - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
The `usdk` module's dispatchable `withdraw`/`deposit` hooks re-derive the "is this account denylisted" check from the **current** owner of the `FungibleStore` object at call time, via `object::owner(store)`, rather than from a fixed identity bound to the store when it was created/frozen. [1](#0-0) 

### Finding Description
The blacklist primitive here (`denylist`/`undenylist`) sets the `frozen` flag on the denylisted account's **primary** store: [2](#0-1) 

But the actual enforcement in the dispatchable withdraw/deposit hooks does not check the `frozen` flag of the specific store being acted on — it re-derives the account to check via `object::owner(store)` and checks *that* account's primary store frozen status: [1](#0-0) [3](#0-2) 

Because `FungibleStore` objects are themselves `Object<T>` with a mutable `owner` field in `ObjectCore`, and `object::transfer`/`object::owns` allow ownership reassignment whenever `allow_ungated_transfer` is true on that object [4](#0-3) , the invariant "denylisted funds cannot move" only holds if **every** store an account can control is also made untransferable. `usdk::init_module` only calls `fungible_asset::set_untransferable(constructor_ref)` on the **metadata object's own constructor_ref** at asset-creation time [5](#0-4) . Whether this actually renders every subsequently-created `FungibleStore` (primary or non-primary) untransferable, versus only the metadata object, is something I could not fully confirm from the index — I was not able to load `fungible_asset::create_store`'s implementation in this session (my last grep for `create_store`/`ENO_UNGATED_TRANSFERS` returned truncated/empty results due to running out of tool iterations). The existing regression test `test_untransferrable_store` [6](#0-5)  explicitly documents that this was a known risk the authors tried to close ("test the ability of a denylisted account to transfer out newly created store"), which confirms the underlying custody concern is real and previously exercised by the project itself, but I cannot independently verify from the available index whether the guard fully covers every code path (e.g., stores created before `set_untransferable` was in effect, or stores under a different `T: key` object type that isn't marked `Untransferable` at creation).

### Impact Explanation
If any path exists where a `FungibleStore` object retains `allow_ungated_transfer = true` after the owning account is denylisted (e.g., a store created via a route that isn't covered by the blanket `set_untransferable` call, or an already-existing store from before denylisting), a denylisted account could call `object::transfer` to reassign that store's `owner` field to an unrestricted address. Because the withdraw/deposit hooks check `object::owner(store)` (the *new* owner) rather than a persistent binding of the store to its original holder, the frozen/denylist check would evaluate against the new, non-denylisted owner and pass — allowing withdrawal of value that compliance intended to freeze. This is a custody/compliance-bypass of exactly the same shape as the reported ERC-4626 bug: the enforcement checks the wrong identity in the authority chain (current object owner) instead of the identity the restriction was meant to bind (the actual custodian of the frozen funds).

### Likelihood Explanation
Likelihood is **uncertain/unconfirmed** rather than demonstrated. This is an example/reference module (`move-examples`), not core framework code, and the project's own test suite already targets this exact scenario, suggesting the authors were aware and added the blanket `set_untransferable` mitigation. Without being able to fully trace `fungible_asset::create_store`'s untransferability defaults across all object types (`T: key`) and all creation entry points, I cannot confirm whether a gap remains (e.g., non-primary stores, stores created before roles were fully wired, or objects nested under other Object types where `verify_ungated_and_descendant`'s chain-walk could behave unexpectedly).

### Recommendation
- Confirm that `fungible_asset::create_store` (and every public entry point that creates a `FungibleStore`) unconditionally marks the resulting object `Untransferable` whenever the asset's `DispatchFunctionStore` denylist logic depends on `object::owner(store)`.
- Alternatively (defense in depth), change `usdk::withdraw`/`usdk::deposit` to check `fungible_asset::is_frozen(store)` directly (the frozen bit on the specific store) rather than re-resolving `object::owner(store)` and checking that account's *primary* store — this removes the dependency on ownership immutability entirely and mirrors the original report's recommendation (check the actual custody-holder, not a value that can be reassigned).
- Add regression coverage for non-primary stores and pre-existing stores created before denylisting, not just the "create after denylist" case already tested.

### Proof of Concept
Only a partial PoC could be constructed from available context (mirrors the project's own `test_untransferrable_store` test, which currently expects failure):
1. `usdk::denylist(denylister, receiver_address)` — freezes `receiver_address`'s primary store.
2. If any `FungibleStore` object under `receiver_address`'s control has `allow_ungated_transfer == true` (not covered by `set_untransferable`), call `object::transfer(receiver, store, new_address)`.
3. Call `dispatchable_fungible_asset::withdraw` on that store; `usdk::withdraw` computes `object::owner(store)` as `new_address` (not denylisted) and `assert_not_denylisted` passes, releasing the frozen funds.

I was unable to execute or fully trace step 2's precondition against `fungible_asset::create_store`'s source in this session due to tool-call limits, so this finding should be treated as **an area requiring verification** rather than a confirmed exploit. Given that confidence gap, and per the task's instruction to report only when local code independently proves the broken invariant, I present this as a flagged concern rather than a certified high/critical finding.

    /// Attempts to transfer using addresses only. Transfers the given object if
    /// allow_ungated_transfer is set true. Note, that this allows the owner of a nested object to
    /// transfer that object, so long as allow_ungated_transfer is enabled at each stage in the
    /// hierarchy.
    public fun transfer_raw(
        owner: &signer,
        object: address,
        to: address,
    ) {
        let owner_address = signer::address_of(owner);
        verify_ungated_and_descendant(owner_address, object);
        transfer_raw_inner(object, to);
    }

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };
    }
