### Title
Operator QR-code expiration is checked once before signup begins but never re-validated at the point of enrollment, allowing a signup to be completed and attributed to an operator whose authorization window has already lapsed - (File: src/plans/mod.rs)

### Summary
The Sherlock report's root cause is that a state check (pool exchange rate / `totalAssets`) is validated only at the moment a transaction is submitted, but the actual value transfer happens later after the underlying state has changed, with no re-check at execution time. The same "check-then-drift" pattern exists in `orb-core`'s signup flow: the operator QR-code's authorization window (`operator_qr_expiration_time`) is checked once when the QR codes are resolved, but the subsequent multi-second/minute pipeline (relay announcement, biometric capture, biometric pipeline, enrollment) never re-validates that the operator's authorization is still valid before the signup is finalized and attributed to that operator.

### Finding Description
In `scan_remaining_qr_codes`, the operator authorization check is only `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, evaluated once when selecting which branch to take: [1](#0-0) 

Once this check passes, `operator_data` (carrying the "still valid" timestamp) is bundled into `ResolvedQrCodes` and handed to `do_signup`, which then runs a long sequence of async operations — relay announcement, a fixed 3-second sleep, biometric capture, and the full biometric pipeline — before it ever uses `operator_data` again (e.g. for PCP credentials / enrollment): [2](#0-1) 

None of these steps re-check `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time`. `enroll_user` is later called using `debug_report.operator_qr_code`, which was captured from the same stale `operator_data`: [3](#0-2) 

This is structurally identical to the reported bug class: a validity condition ("exchange rate acceptable" / "operator badge still valid") is satisfied at check time, but the actual state-changing action (asset transfer / signup enrollment) completes after the underlying state has drifted past the point where the original check would have failed, with no re-validation guarding the final commit.

### Impact Explanation
If biometric capture and the pipeline (which can legitimately take longer than `operator_qr_expiration_time`, especially on retries/timeouts) run past the operator authorization window, the signup still completes and is recorded/attributed to an operator QR-code that had already expired by the time enrollment occurred. This is a misattributed-signup condition: the enrollment record (`debug_report.operator_qr_code`) reflects an operator whose authorization to be present during the signup is no longer guaranteed to hold, undermining the accountability/attribution guarantee that the operator-expiration mechanism is meant to enforce.

### Likelihood Explanation
Likelihood is moderate: `operator_qr_expiration_time` is a configurable value and the intervening steps (`orb_relay_announce_orb_id` with retries, a fixed 3s sleep, `biometric_capture`, and `biometric_pipeline`) are variable-length operations that can legitimately stall (retries, slow network, failed capture attempts) long enough to cross the expiration boundary without any code path aborting or re-scanning the operator QR-code once the pipeline is underway.

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` immediately before the enrollment-committing step (`enroll_user` / PCP credential build), and abort or force a re-scan of the operator QR-code if the window has elapsed by that point, mirroring the recommendation to enforce slippage/state bounds at the point of final execution rather than only at submission time.

### Proof of Concept
1. Operator scans QR, `operator_data.timestamp` recorded; `scan_remaining_qr_codes` passes the expiration check.
2. User QR is scanned; `do_signup` proceeds through `orb_relay_announce_orb_id` (with retries) and the 3s sleep.
3. `biometric_capture` takes longer than `operator_qr_expiration_time - elapsed_so_far` (e.g., due to repeated re-attempts inside the capture plan).
4. `enroll_user` is invoked using the original, now-expired `operator_data`/`operator_qr_code` — no code path re-checks expiration, so the signup completes and is attributed to the expired operator authorization.
