### No vulnerability found for this question.

Analysis: `ShopValidator.uri_from_shop_domain` rejects any shop string containing a literal `"@"` [1](#0-0) . The proposed bypass (percent-encoded `%40` instead of a literal `@`) relies on the userinfo/host split happening on the *decoded* string, but RFC 3986 authority parsing (and Addressable's implementation) splits userinfo from host on the literal `@` delimiter present in the raw string before that component is percent-decoded. A string containing `%40` instead of `@` therefore never gets split into userinfo+host at all — the entire string (including the literal `%40` characters) becomes part of `uri.host`. That malformed host will not equal any `TRUSTED_SHOPIFY_DOMAINS` entry, and `uri.domain` (Addressable's public-suffix-based registrable-domain extraction) will not resolve it to a trusted domain either, so the loop in `sanitize_shop_domain` falls through `uri_domain.nil?`/mismatch checks and returns `nil` [2](#0-1) , which causes `sanitize!` to raise `Errors::InvalidShopError` [3](#0-2) .

The existing test suite already asserts rejection for the literal-`@` userinfo case (`"shop.myshopify.com@evil.com"`) [4](#0-3) , and there is no separate "fully normalised string" distinct from the returned `uri.host`/`myshopify_domain_from_unified_admin(uri)` value that callers use — every caller (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb#migrate_to_expiring_token`) takes the exact return value of `sanitize!` and assigns it once to `validated_shop`, which is then used consistently both for `Session.new(shop: validated_shop)` and for the outgoing HTTP request via `Clients::HttpClient.new(session: shop_session, ...)` [5](#0-4) [6](#0-5) [7](#0-6) . There is no reachable path where the verified value (what passed the trusted-domain check) differs from the value subsequently interpolated into the session id or used as the request host — the function either returns the exact validated host/domain or rejects the input outright.
