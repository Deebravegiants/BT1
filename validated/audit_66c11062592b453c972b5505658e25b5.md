### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` authenticates the JSON payload but not the `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated header when building `WebhookMetadata` and dispatching to the app's handler.

### Finding Description
`Request#hmac` reads the HMAC from a header [3](#0-2) , and `to_signable_string` only returns `@raw_body` [1](#0-0) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [4](#0-3) . This means the equality being enforced is `HMAC(body) == received_hmac`, not `HMAC(body + shop) == received_hmac`. The `shop` value returned by `Request#shop` [2](#0-1)  is read straight from a header and is never part of the signed bytes.

`Registry.process` validates only this body HMAC, then passes the unauthenticated `request.shop` straight into `WebhookMetadata` for the handler [5](#0-4) . The documented contract is that `process` "will verify the request did indeed come from Shopify," and that `data.shop` is "The shop domain of the webhook" — i.e., host apps are told they can rely on `data.shop` as an authenticated tenant identifier, per `docs/usage/webhooks.md`.

Because Shopify uses one shared app-level `api_secret_key` HMAC for all shops that have installed the app (not a per-shop secret bound into the signed bytes), any actor who has legitimately installed the app on their own store can capture a validly-signed webhook body+HMAC pair from their own store, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. The HMAC still validates (it only checks the body), but `Registry.process` reports the payload as originating from the victim shop.

### Impact Explanation
This breaks the identity binding `authenticated_bytes == shop_identity` for webhook processing. If a host application uses `data.shop` returned by this gem to select which tenant's records to create/update/mark-fulfilled/etc. (which is exactly the intended, documented use), an attacker with their own low-privilege store installation can inject falsified webhook events attributed to an arbitrary victim shop, resulting in cross-tenant data corruption within the host app.

### Likelihood Explanation
Requires only an actor with a normal, unprivileged app installation (any developer can install most public apps on a development store) and the ability to know or guess a target shop's `myshopify.com` domain (which is often public/discoverable) and knowledge of the app's webhook endpoint URL (also typically discoverable/predictable). No possession of `api_secret_key` or an access token is required — only a replay of body bytes the attacker already legitimately received for their own shop, with a substituted header.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the bytes that are HMAC-verified, e.g. change `Request#to_signable_string` to combine `@raw_body` with the `shop`, `topic`, and `webhook_id` header values in a canonical, delimited form, and validate the same combination in `HmacValidator`. At minimum, document that `data.shop` from `ShopifyAPI::Webhooks::Registry.process` is not cryptographically bound to the verified payload and must not be trusted for tenant selection without independent verification (e.g., cross-checking against the shop of the session/webhook subscription that was registered).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends `POST /webhook` to the app's endpoint with the same body `B` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [8](#0-7) , causing the host app to process attacker-controlled webhook content as if it belonged to the victim shop.
