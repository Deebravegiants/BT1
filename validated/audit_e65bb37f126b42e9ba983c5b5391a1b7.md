### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the trusted shop identity, with no binding between the two.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read directly and unvalidated from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate and then immediately forwards `request.shop` (the unauthenticated header value) to the registered handler: [4](#0-3) 

The documented contract tells integrators to trust `data.shop` as "the shop domain of the webhook": [5](#0-4) 

This is the same bug class as the report: an identity/status field (`shop`, analogous to `subnet.status = Status.Active`) is acted upon by downstream logic without being bound to the value that was actually validated (the HMAC, analogous to the `s.minStake` check). The equality that should hold — `shop asserted in header == shop bound by the verified HMAC` — is never checked; the HMAC binds only `raw_body`.

### Impact Explanation
Any actor able to obtain one valid `(body, HMAC)` pair signed with the app's `api_secret_key` — for example a user who installs the target app on their own (even free/dev) Shopify store and triggers a webhook event there — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it never looked at the header, and the handler will receive `WebhookMetadata` claiming the event belongs to the victim shop. This breaks the tenant boundary the app relies on: any webhook-driven action keyed off `data.shop` (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request`, or ordinary `orders/create`-style handlers that write per-shop records) can be triggered and attributed to a shop the attacker does not control, i.e., cross-tenant access using only credentials the attacker legitimately possesses for their own store.

### Likelihood Explanation
Likelihood is high for any app that trusts `data.shop` for anything beyond logging, since this is the exact usage the gem's own documentation recommends. No secret material beyond a single legitimately-obtained webhook (from the attacker's own shop) is required, and no privileged account or credential of the app or the victim shop is needed.

### Recommendation
Extend `Request#to_signable_string` (or add a companion binding check in `Registry.process`) so that the `shop-domain` header is cryptographically bound to the verified request — e.g., include it in the signed material, or independently corroborate it against a value obtained through an authenticated channel (such as the `webhook_id` correlated with a registration made for a known shop/session) before passing it to handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay the captured request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and finds it equal to `H`, so `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the event body and HMAC never involved the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
