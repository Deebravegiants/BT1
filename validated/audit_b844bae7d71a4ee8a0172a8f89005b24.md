### Title
Unauthenticated arbitrary external call from `EmporiumUpgradeable.runAction` lets an attacker drain any ERC20 balance held by the Emporium contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` decodes an attacker-supplied `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and, for every "Stateless Interaction" op, executes `op.endpoint.call{value: op.value}(op.callData)` with the Emporium contract itself as `msg.sender` [1](#0-0) . The only guard on this call is a selector blacklist against `IHinkalWallet.callHinkalWallet` and `IHinkalWallet.doSendToRelay` [2](#0-1) ; `endpoint` and `callData` themselves are never checked against a whitelist. This is the same bug class as the `Controller._qTokenPermit` finding: an arbitrary, attacker-chosen address is invoked with the protocol's own asset-bearing contract as `msg.sender`, protected only by a negative check instead of a positive one.

### Finding Description
When `stack.signerAddress == address(0)`, `verifyWallet` immediately returns without any EIP-712 signature check — it only marks `circomData.emporiumMessage` as used and returns [3](#0-2) . In this mode, the entire `EmporiumStack.ops` array (endpoints, calldata, value) is attacker/prover controlled, and its only cryptographic tie-in is being hashed into `calldataHash` / `signedMessageHash`, which merely proves the *prover* chose these values — it does not restrict what those values may be.

For each op with `invokeWallet == false` (or `signerAddress == address(0)`), the "Stateless Interaction" branch runs:
```solidity
bytes4 selector = bytes4(op.callData);
if (selector == IHinkalWallet.callHinkalWallet.selector || selector == IHinkalWallet.doSendToRelay.selector) {
    revert UnauthorizedWalletCall();
}
(success, err) = op.endpoint.call{value: op.value}(op.callData);
``` [1](#0-0) 

`op.endpoint` can be any address, and `op.callData` can be any function call. Since the Emporium contract (`EmporiumUpgradeable`) is `msg.sender` for this `.call`, an attacker can direct it to call `IERC20(token).transfer(attacker, amount)` (or `approve`) on any ERC20 token for which Emporium currently holds a balance — this is exactly the "precooked contract called by an asset-bearing contract" pattern from the referenced Controller/QToken finding, just with a token-transfer target instead of `permit()`.

Crucially, Emporium is designed to hold ERC20 balances mid-flow: before `runAction` is invoked, `Hinkal._externalTransact` transfers deposit amounts (`deltaAmountChanges[i] < 0`) into the external action address (Emporium) [4](#0-3) . If a batch of `ops` deposits multiple tokens for legitimate swap/DeFi steps and one op fails to fully sweep a token, or if dust/leftover balances remain from prior transactions (e.g., rounding remainders that are silently dropped, since `handleOut` treats `balanceChange <= 0` as "nothing to return" without ever tracking such leftovers as a spendable UTXO) [5](#0-4) , that balance sits in the Emporium contract, unbacked by any UTXO/commitment. Because there is no whitelist check on `op.endpoint`/`op.callData`, any subsequent caller can supply a stateless op that calls `transfer()`/`approve()` on that leftover token balance to themselves, stealing value that was never accounted for in the protocol's balance equation (`balanceChange`/UTXO minting logic) — breaking the equality between Emporium's actual token balance and the UTXOs it is supposed to represent.

### Impact Explanation
This qualifies as Critical/High under the theft-of-shielded-or-protocol-funds category: any ERC20 balance sitting in the Emporium contract (whether dust, an in-flight deposit from a legitimate multi-op transaction, or a value not fully swept back into a UTXO) can be moved out by an unprivileged attacker via an arbitrary `.call` executed with Emporium as `msg.sender`, with no on-chain verification that `endpoint`/`callData` correspond to any protocol-approved interaction.

### Likelihood Explanation
The `signerAddress == address(0)` path is a normal, documented mode of the Emporium (used when the relay/prover itself signs off, e.g. `relay != address(0)` with `originalSender == address(0)` per `HinkalHelper.performHinkalChecks`) [6](#0-5) , so no special privilege is needed to reach `verifyWallet`'s no-signature branch and craft an arbitrary `ops` array. The prerequisite (Emporium holding a spare token balance) is plausible given the multi-op batched design and the fact that leftover balances are not swept into UTXOs by `handleOut`.

### Recommendation
Restrict the stateless `.call` target to a protocol-maintained allow-list of router/protocol addresses (mirroring `onlyAllowedRecipient`/`allowedRecipients` pattern already used elsewhere in the codebase, e.g. `ExternalActionBaseUpgradeable._isAllowedRecipient`) [7](#0-6) , rather than only blacklisting two selectors. Additionally, ensure any leftover/dust balance left in Emporium after `runAction` is either impossible (revert if balance isn't fully consumed) or is properly minted into a UTXO so it can never sit unbacked and drainable.

### Proof of Concept
1. Attacker (or colluding relay) submits a valid ZK proof for a Hinkal `transact` call that routes through `Hinkal._externalTransact` to `EmporiumUpgradeable.runAction`, with `circomData.relay != address(0)` and `circomData.originalSender == address(0)` (satisfying `performHinkalChecks`).
2. `circomData.externalActionData.externalActionMetadata` is set to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation` where `invokeWallet = false`, `endpoint = <ERC20 token address Emporium currently holds a balance of>`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)`.
3. `verifyWallet` returns immediately (no signature required) since `signerAddress == address(0)`.
4. The loop in `runAction` executes `op.endpoint.call(op.callData)`, i.e., `token.transfer(attacker, amount)` with Emporium as `msg.sender`, transferring `amount` of that token from Emporium's balance to the attacker — independent of whether that balance was ever backed by a UTXO owed to the attacker.
