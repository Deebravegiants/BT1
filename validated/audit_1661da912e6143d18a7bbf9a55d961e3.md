### Title
Shallow `Object.freeze` on remote config allows a consumer to mutate nested config properties, corrupting security-relevant values (sunsetAssets, disabledPurposes, dapps.fiatOnramp) shared with all other consumers - ([File: features/remote-config/module/index.ts])

### Summary
`RemoteConfig#update`/`#current` freezes the top-level config object with the injected `freeze` adapter (`this.#current = this.#freeze(config)`), and every production adapter wires this to plain `Object.freeze`, which is a shallow freeze. Any caller holding the object returned by `getAll()` can mutate a nested object (e.g. `config.core.wallet.sunsetAssets`, `config.assets.*.disabledPurposes`, `config.dapps.fiatOnramp`) and that mutation is visible to every subsequent consumer via `get()`/`getAll()`, since they all read the same shared `#current` reference.

### Finding Description
`RemoteConfig#getAll` and `#get` return/derive from the single shared `this.#current` object [1](#0-0) . That object is produced by `this.#freeze(config)`, where `freeze` is an injected adapter [2](#0-1) . In every real (non-test) adapters wiring found in the repo, `freeze` is bound directly to `Object.freeze` [3](#0-2) [4](#0-3) [5](#0-4) . `Object.freeze` only freezes the top-level object's own properties; nested objects/arrays remain fully mutable. Since `getAll()` returns the actual shared `#current` reference (no deep clone, no deep freeze), any consumer of the SDK (UI code, a feature module, or any code with a reference obtained via `remoteConfig.getAll()`) can do:

```js
const config = await remoteConfig.getAll()
config.core.wallet.sunsetAssets.push('bitcoin')
config.dapps.fiatOnramp.enabled = true
```

and this mutation persists in the shared `#current` object because nested objects are the same references across every `get()`/`getAll()` call. This is documented as the primary consumption pattern (`exodus.remoteConfig.getAll()`, `remoteConfig.get('core.wallet.sunsetAssets')`) [6](#0-5) , and is also the pattern used to build derived atoms via `remote-config-atoms` (e.g., `dapps.fiatOnramp`) which are consumed feature-wide [7](#0-6) . No deep-freeze, deep-clone-on-read, or per-consumer copy exists anywhere in `RemoteConfig`, `#fetchConfig`, or `update` to prevent this.

### Impact Explanation
This breaks the invariant that remote config must be authentic and uniform for all consumers of a single wallet session/process. A caller (e.g. a compromised or buggy UI component, or any code path that has legitimate access to `remoteConfig.getAll()`) can locally tamper with security-relevant thresholds/allowlists such as `core.wallet.sunsetAssets`, per-asset `disabledPurposes`, or `dapps.fiatOnramp` provider/enable flags, and that tampered value will silently propagate to every other consumer within the same process reading the same `remoteConfig` instance (via `get()`/`getAll()`/derived remote-config atoms) for the remainder of the session, or until the next successful remote fetch overwrites `#current`. This can, in the worst case, cause other in-process logic that trusts these values (e.g., dapp-connection allow/deny decisions, sunset/deprecation gating, disabled-purpose enforcement) to make decisions based on attacker/bug-tampered data rather than the authentic server-provided config.

However, this requires "any consumer holding a reference" — i.e., some other in-process JS code with legitimate access to the SDK's `remoteConfig.getAll()` API — to actually perform the mutation. There is no cross-origin/dapp-reachable path shown in the provided code that lets an arbitrary web page or RPC caller directly mutate this shared object; the `remoteConfig` module itself is an internal SDK dependency, not something exposed raw to untrusted dapp origins. I could not find, within the indexed context, any exposed RPC/dapp-facing endpoint that returns `remoteConfig.getAll()`'s live object (rather than a serialized copy) to an external/untrusted caller, so the "unprivileged remote/dapp attacker" reachability required by the audit rules is not established from the code inspected. This is a design weakness / shared-mutable-state bug within the wallet's own JS heap, not a demonstrated externally-triggerable compromise.

### Likelihood Explanation
Preconditions: some code executing in the same JS realm as `remoteConfig` must call `getAll()` (or `get()` returning a nested object) and then mutate a nested field. This is trivially reproducible in a unit test and would affect any first-party or third-party module sharing the process (e.g., a malicious/compromised dependency, or a bug in first-party code) but is not shown to be reachable from an unprivileged external dapp/origin/RPC caller based on the provided code — that link is unproven in this context.

### Recommendation
Deep-freeze (recursively) the config object before storing it in `#current`, or return a structured-clone/deep-frozen snapshot from `getAll()`/`get()` so that no caller can obtain a mutable reference to shared nested state. Alternatively, use a proven deep-freeze utility (the codebase already has `proxy-freeze` used elsewhere, e.g. `libraries/atoms/src/enforce-rules.ts`) instead of `Object.freeze` for the `freeze` adapter used by `remoteConfig`.

### Proof of Concept
```ts
// features/remote-config/module/index.test.ts (illustrative)
it('nested mutation of getAll() result leaks to other consumers', async () => {
  const remoteConfigAtom = createInMemoryAtom({ defaultValue: { config: { core: { wallet: { sunsetAssets: [] } } } } })
  const remoteConfig = createRemoteConfig({
    freeze: Object.freeze, // production wiring
    fetch: fetchStub, // returns same nested config
    remoteConfigAtom,
    logger, errorTracking, getBuildMetadata,
  })
  void remoteConfig.load()

  const config1 = await remoteConfig.getAll()
  config1.core.wallet.sunsetAssets.push('bitcoin') // mutate nested array

  const config2 = await remoteConfig.getAll()
  expect(config2.core.wallet.sunsetAssets).not.toContain('bitcoin') // FAILS: mutation leaked
})
```
Expected (secure) behavior: `config2` should be unaffected by the mutation performed via `config1`; current behavior shows the mutation is visible, confirming the lack of deep immutability/isolation.
