### Title
GRANDPA `AncestryChain::ancestry` walk has no cycle detection, allowing a relayed consensus proof with self-referential headers to hang verification in an infinite loop - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` walks backward from a target block hash to a base hash by repeatedly looking up `parent_hash` in an attacker-supplied header map, with no bound on iterations and no tracking of already-visited hashes. Because the headers (and therefore their `parent_hash` fields) are fully attacker-controlled SCALE-decoded structs coming straight off an untrusted GRANDPA consensus proof, an attacker can construct two (or more) synthetic headers whose `parent_hash` fields point at each other, forming a cycle. When the walk enters that cycle without ever reaching `base`, the `while current_hash != base` loop never terminates — the classic "cycle in references" pattern from CVE-2016-6131, here manifesting as an unbounded loop instead of unbounded recursion.

### Finding Description
`AncestryChain` is built directly from attacker-controlled data: [1](#0-0) 

The `ancestry` walk has no cycle protection: [2](#0-1) 

This function is invoked on two attacker-controlled sources:

1. `votes_ancestries: Vec<H>` inside `GrandpaJustification`, itself decoded from the raw proof bytes, and walked in `verify_with_voter_set`: [3](#0-2) [4](#0-3) 

2. `unknown_headers: Vec<H>` inside `FinalityProof`, walked in `verify_grandpa_finality_proof`: [5](#0-4) 

The full path from an unprivileged relayer to this code is:
- `pallet_ismp::Call::handle_unsigned` (callable by anyone, `ensure_none` origin) accepts `Vec<Message>` including `Message::Consensus`. [6](#0-5) 
- The GRANDPA `ConsensusClient::verify_consensus` decodes the untrusted `proof: Vec<u8>` into a `ConsensusMessage`/`FinalityProof` with `codec::Decode::decode`, with no structural validation of the header ancestry graph before it is walked. [7](#0-6) 

An attacker fully controls every field of each `H: Header` in `unknown_headers`/`votes_ancestries` — `number`, `state_root`, `extrinsics_root`, `digest`, and critically `parent_hash`. The map key is `header.hash()`, computed purely from the encoded bytes the attacker chose, so they can trivially compute two headers `A` and `B` where `A.parent_hash == B.hash()` and `B.parent_hash == A.hash()`. Setting `finality_proof.block` (or a precommit `target_hash`) to `A.hash()`, with `base` chosen so it is never reached, causes `ancestry()` to loop forever alternating between `A` and `B`, since both hashes are always found in `self.ancestry` (never returning `Err(NotDescendent)`) and the loop condition `current_hash != base` never becomes false.

Compared to nearby code in this same codebase — e.g. `verify_with_voter_set`'s own top-level loop, which does track `visited_hashes` for double-counting/consistency checks, but only *after* `ancestry()` has already returned — there is no protection inside `ancestry()` itself against a cyclic parent chain.

### Impact Explanation
This is reachable by any unprivileged party submitting an unsigned `handle_unsigned` extrinsic carrying a `Message::Consensus` for a GRANDPA-based consensus client (used for Polkadot/Kusama relay-chain-anchored consensus updates and fraud proofs on Hyperbridge). Because verification for `handle_unsigned` runs both in `validate_unsigned` (mempool / transaction validity checks on every node) and in `execute` at block-inclusion time, an attacker-crafted cyclic-ancestry proof:
- Hangs any node's transaction pool validation, and
- If ever mined into a block, hangs block execution/import itself.

This qualifies as "a route unable to deliver messages" and a broader liveness/DoS impact on the consensus-client update path (and thus outgoing/incoming message delivery relying on that consensus client), meeting the High-severity bar analogous to the demangler infinite-loop DoS in CVE-2016-6131.

### Likelihood Explanation
High. No signature check, fee, or special privilege gates the ability to submit `handle_unsigned` with an arbitrary GRANDPA consensus proof, and constructing two mutually-referencing headers requires no cryptographic break — only picking arbitrary header field values (the hash function used for the map key has no additional binding to real GRANDPA validator signatures at this stage of the walk).

### Recommendation
Add cycle detection / an iteration bound to `AncestryChain::ancestry`: track visited hashes in a `BTreeSet` (or cap the walk to `ancestry.len()` iterations, since a genuine acyclic ancestry proof can visit each supplied header at most once) and return an error (e.g. `Error::NotDescendent`) as soon as a hash is revisited or the iteration bound is exceeded.

### Proof of Concept
1. Construct header `B` with arbitrary fields (e.g. `number = 1`).
2. Construct header `A` with `parent_hash = B.hash()`.
3. Recompute `B.parent_hash = A.hash()` (re-encode `B` with this new field, which changes `B.hash()`; iterate this fixed-point construction, or more simply, freely choose non-hash-dependent fields for `A` and `B` and solve for `parent_hash` fields directly since `parent_hash` does not feed back into its own hash computation — assign `A.parent_hash = hash(B_bytes)`, `B.parent_hash = hash(A_bytes)`, which is self-consistent and requires no fixed-point iteration).
4. Build a `FinalityProof { block: A.hash(), unknown_headers: vec![A.clone(), B.clone()], justification: <matching but otherwise-irrelevant-to-this-loop encoding> }` (or embed `A`, `B` as `votes_ancestries` in a `GrandpaJustification`) such that `base` (the min-height header, or `consensus_state.latest_hash`) is neither `A.hash()` nor `B.hash()`.
5. Submit this as the `proof` bytes of a `Message::Consensus` inside a `pallet_ismp::Call::handle_unsigned` unsigned extrinsic.
6. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())`, which enters the `A → B → A → B → …` cycle and never returns, hanging the calling thread (mempool validation and/or block execution).

pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,
}

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
