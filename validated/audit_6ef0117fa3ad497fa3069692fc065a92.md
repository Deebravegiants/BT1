Confirmed: `placeOrder` uses `_orders[commitment][token] += reducedInputs[i].amount;` (not `=`), so duplicate token addresses in `order.inputs` accumulate into a single shared balance, and `order.inputs[i].amount == 0` is rejected. This means, within the Tron `IntentGatewayV2`, the exact "some deposits already drained → revert blocks the rest" scenario requires either (a) a duplicate-token entry whose *second* iteration in `withdraw()` sees an already-zeroed balance from the first iteration, or (b) a peer-gateway-controlled multi-message sequence against the same commitment. Both are plausible but not as cleanly single-transaction-provable as the original OpenQ bug. Given the incomplete verification, I present the finding with appropriately scoped confidence.

### Title
Missing zero-amount guard in `IntentGatewayV2.withdraw()` lets one drained escrow slot permanently block release of all other tokens in the same order - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` iterates `body.tokens` (derived from `order.inputs`) and reverts with `UnknownOrder()` the moment `_orders[commitment][token] == 0` for *any* entry, with no check that `amount == 0` for that same entry [1](#0-0) . The parallel, non-Tron implementation in `IntentsBase._withdraw()` explicitly guards against this by skipping zero-amount entries before checking escrow state: `if (amount == 0) continue;` [2](#0-1) . The Tron variant lacks this guard, so any multi-token order whose commitment has one token's escrow already reduced to zero causes the entire `withdraw()` call — and thus the release/refund of every *other* still-escrowed token in the same order — to revert unconditionally, exactly mirroring the reported OpenQ `claimBounty`/NFT-refund class of bug (one already-settled item in a loop poisons the whole batch).

### Finding Description
`withdraw()` is the single choke point for both `RedeemEscrow` (successful fill payout) and `RefundEscrow` (cancellation refund) on the Tron gateway, reached from `cancelOrder()` (same-chain path, line 536-539) and from `onAccept()` for cross-chain `RedeemEscrow`/`RefundEscrow` messages (lines 629-635) [3](#0-2) . It also gates the source-side cancellation pre-check, which loops over every input token and reverts with `UnknownOrder()` if any single token's escrow is already zero, before a Hyperbridge GET request is ever dispatched [4](#0-3) .

Inside `withdraw()` itself:
```solidity
for (uint256 i; i < len;) {
    address token = ...;
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
    _orders[body.commitment][token] -= amount;
```
There is no `if (amount == 0) continue;` before the escrow check, unlike the mainline `IntentsBase._withdraw()`. Consequently, if `_orders[commitment][token]` for any single entry in the batch is already `0` — whether legitimately (a zero-amount slot) or because it was already consumed — the loop reverts for the *entire* transaction, including tokens that still hold non-zero, legitimately claimable escrow for the same order/commitment. Because `placeOrder` accumulates escrow per `(commitment, token)` with `+=` [5](#0-4) , any order construction or message sequence that causes one token's balance to be depleted independently of the rest of the batch (e.g., a duplicate-token input entry consumed on an earlier loop iteration, or a peer gateway dispatching a prior partial `WithdrawalRequest` for the same commitment) leaves the remaining tokens permanently stuck: every future `withdraw()` call over the full `order.inputs` set will hit the zero-balance entry and revert before it can decrement or transfer the still-escrowed tokens.

### Impact Explanation
A multi-token order's remaining, legitimately escrowed funds become permanently unrecoverable once any single token slot for that commitment reaches zero ahead of the others, since every subsequent redemption or refund attempt (via `cancelOrder`, `onAccept` RedeemEscrow/RefundEscrow) replays the same full-batch check and reverts on the drained entry. This is a permanent freezing-of-funds condition for the affected order's remaining tokens, matching the Medium-severity classification of the analogous OpenQ finding.

### Likelihood Explanation
The Tron gateway does not expose an obvious single-transaction primitive to zero one token's escrow while leaving a sibling token's escrow intact within the same order/commitment in the code paths reviewed (no partial-fill function was found in this file, and `placeOrder` accumulates rather than overwrites duplicate token entries). Triggering the condition therefore likely requires either an order with a duplicate token address whose first `withdraw()` iteration consumes the shared balance and whose second iteration finds it already zero, or a scenario where the trusted peer gateway (on the other chain) issues more than one distinct cross-chain `RedeemEscrow`/`RefundEscrow` message referencing the same commitment with different `body.tokens` subsets. I was not able to fully confirm within the available context whether either path is reachable from a single unprivileged transaction without cooperation from a duplicate-token order or a specific peer message sequence, so likelihood should be treated as uncertain pending further code review of the full withdraw/authenticate flow and any duplicate-token validation elsewhere in the contract.

### Recommendation
Add the same zero-amount guard used in `IntentsBase._withdraw()` to the Tron `IntentGatewayV2.withdraw()`:
```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) { unchecked { ++i; } continue; }
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
```
Additionally, reject orders whose `order.inputs` contain duplicate token addresses at `placeOrder()` time, and/or track per-token settlement independently so a message referencing an already-consumed token slot does not block the release of unrelated, still-escrowed tokens for the same order.

### Proof of Concept
Not fully constructible from the indexed context alone — a duplicate-token-input trigger or a two-message peer-gateway sequence against the same `commitment` would need to be validated in a local Foundry test against `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm reachability from a single unprivileged submission. I recommend a background engineering session write a Foundry PoC that (1) places an order with a duplicated token address in `order.inputs`, (2) drives `withdraw()` so the first occurrence zeroes the shared `_orders[commitment][token]` slot, and (3) shows the second occurrence causes `UnknownOrder()` to revert the whole call, or alternatively simulates two sequential `onAccept` `RefundEscrow`/`RedeemEscrow` messages for the same commitment with different token subsets to confirm the stuck-fund condition.
