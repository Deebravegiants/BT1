### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`api_version`/`webhook_id`) values that the handler subsequently trusts and dispatches on are read from HTTP headers that are never included in the signed payload. This breaks the intended binding "HMAC-valid request == request genuinely originated for this shop", exactly analogous to the report's root cause: different pieces of data (the value that is cryptographically verified vs. the value that is actually acted upon) are inconsistent.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` verifies only that the HMAC over the body matches, then immediately trusts `request.shop` (and the other header-derived fields) to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`HMAC_valid(raw_body, api_secret_key) == true` should imply `shop header is authentic for that body`.

In reality the code only proves `HMAC(raw_body) == received_hmac`; it proves nothing about `shop-domain`, `topic`, `webhook-id`, or `api-version`, since none of those are part of the signed string. Because `api_secret_key` is a single secret shared by the app across every shop that installs it (not a per-shop secret), any unprivileged user who installs the app on their own store legitimately receives real webhooks with valid `(body, hmac)` pairs. That user can then replay the exact same `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim merchant's domain). `HmacValidator.validate` still succeeds because it only recomputes the HMAC over the body, and `Registry.process` will happily hand `WebhookMetadata` with the attacker-chosen `shop` value to the host application's handler.

### Impact Explanation
This allows an unprivileged attacker (any merchant who can install the app once) to inject arbitrary webhook events that the host application will attribute to a victim shop of the attacker's choosing — i.e., cross-tenant data injection/spoofing. Depending on how the host app's webhook handlers use `data.shop` (e.g., to look up/update per-tenant records, trigger billing events, or write data keyed by shop), this can lead to cross-tenant state corruption or unauthorized actions being recorded against another merchant's tenant, which maps to the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook validation with no additional binding: exploitation requires no access to `api_secret_key`, no leaked credentials, and no TLS interception — only the ability to install the app once (a normal, unprivileged action) and replay an HTTP POST with a forged header to the app's own public endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the verified payload before trusting it — e.g., include the shop domain in the signable string, or independently confirm the shop against a value already associated with a known, previously-established session/webhook registration for that topic, rather than trusting an unauthenticated header verbatim.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; Shopify sends a legitimate webhook to the app with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Attacker captures this `(raw_body, hmac)` pair.
3. Attacker crafts a new HTTP POST to the same app webhook endpoint, keeping the identical body and `x-shopify-hmac-sha256` header, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body) == hmac header` — this still passes: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"`, even though the body/content actually belongs to the attacker's own shop. [5](#0-4)
