### Title
Consensus-incentive reward misattribution lets a relayer collect payouts for state-machine updates it did not deliver - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives`'s `FeeHandler::on_executed` derives the rewarded relayer identity from only the **first** message in the processed batch, then pays that single relayer for **every** `StateMachineUpdated` event produced anywhere in the batch — exactly the "double incentive without matching work" pattern from the reference report, where a single actor is credited for outcomes it did not individually cause because the code never checks that each credited event actually originated from that actor's own authenticated action.

### Finding Description
`on_executed` receives the full list of processed ISMP messages and the full list of resulting events for one `handle_unsigned` batch: [1](#0-0) 

It extracts a single relayer account by decoding the signature on `messages[0]` only (via `Signature::verify_and_get_sr25519_pubkey`), completely ignoring `messages[1..]`: [2](#0-1) 

It then collapses all `StateMachineUpdated` events in the batch to one entry per `state_machine_id` (this collapsing only fixes double-counting of *repeated* events for the *same* chain within a batch) and pays the relayer extracted from `messages[0]` for **every distinct `state_machine_id`** update present in the event list, regardless of which message in the batch actually produced it: [3](#0-2) 

Since `pallet_ismp::handle_unsigned` is an unsigned extrinsic that accepts a `Vec<Message>` (confirmed by the test harness calling `Pallet::<Test>::handle_unsigned(RuntimeOrigin::none(), vec![consensus_message])`), any account can submit a single transaction that bundles its own valid `Message::Consensus` for state machine A together with one or more other valid, independently-signed `Message::Consensus` items for state machines B, C, … If all of them process successfully and emit `StateMachineUpdated`, the submitter (whose signature sits in `messages[0]`) is paid the full `calculate_reward` for A, B, C, … even though only A's proof was theirs — the reward for B and C rightfully belongs to whoever produced/signed those other consensus updates.

This is structurally identical to the `UbiquityDollarToken` bug: a hook credits an entity for events without verifying that the entity is actually the party responsible for each individual credited event, so a single submission yields payouts disproportionate to the actual work performed.

### Impact Explanation
Treasury funds (`T::TreasuryAccount`) are transferred via `T::Currency::transfer` and reputation tokens are minted via `T::ReputationAsset::mint_into` for every state machine in the batch, all attributed to one signer: [4](#0-3) 
A single attacker can drain treasury rewards intended for multiple distinct relayer deliveries by packaging others' already-produced consensus proofs alongside their own in one unsigned submission, extracting unbacked/duplicated reward payouts and reputation-asset mints from the treasury — a direct fund-drain / unbacked-mint impact on the incentive treasury.

### Likelihood Explanation
`handle_unsigned` is permissionless (no origin restriction beyond `ensure_none`), and consensus messages/proofs for different state machines are public data once broadcast (proofs and signer info are not secret). Any party monitoring the network for pending or recently-relayed consensus updates for other chains can trivially construct a multi-message batch with their own message first, at negligible extra cost, making this practically reachable from a single crafted extrinsic.

### Recommendation
Attribute each `StateMachineUpdated` reward to the relayer whose `Message::Consensus` produced that specific state machine's update, rather than defaulting to `messages[0]`'s signer for the whole batch. Concretely, iterate `messages`, decode each consensus message's own signer, associate it with the state-machine id(s) its proof advances, and only pay the `highest_per_state_machine` reward to the relayer that actually submitted the corresponding message — rejecting or ignoring updates whose source message cannot be matched to a signer in the same batch.

### Proof of Concept
1. Relayer B (honest) submits (or has queued/broadcast) a valid `Message::Consensus` proof advancing `StateMachineId::Polkadot(2000)` from height 100 to 200, correctly signed by B.
2. Attacker A observes this valid consensus proof (public data — same as any consensus proof relayers gossip/broadcast) and separately holds a trivially cheap valid `Message::Consensus` proof for a chain it also monitors, e.g. advancing `StateMachineId::Kusama(3000)` by 1 block, signed by A.
3. Attacker A submits `pallet_ismp::Pallet::handle_unsigned(RuntimeOrigin::none(), vec![A's message, B's message])` as a single unsigned extrinsic.
4. `pallet-ismp` processes both messages successfully, producing two `StateMachineUpdated` events (Polkadot(2000) and Kusama(3000)).
5. `on_executed` in `modules/pallets/consensus-incentives/src/impls.rs` decodes `messages[0]` (A's signature) as `maybe_relayer_account`, then loops over both `StateMachineUpdated` events and calls `Self::process_message(..., relayer_account.clone().into())` for **both**, per lines 147-156 above.
6. Result: Account A receives the treasury reward and reputation mint for *both* the Kusama(3000) advance it performed **and** the Polkadot(2000) advance B performed — B receives nothing for its own valid work, while A is paid double relative to the work it actually did in that transaction.
