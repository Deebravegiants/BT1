### Title
`createWithdrawalIntents` skips `FeeExceedsAmountError` re-check, allowing negative-amount signed intents when `feeEstimation` is attacker/caller-supplied - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents` (sdk.ts:342-344) recomputes `actualAmount = amount - feeEstimation.amount` without ever validating `feeEstimation.amount < amount`, unlike `_estimateWithdrawalFee` (sdk.ts:421-424) which explicitly throws `FeeExceedsAmountError` in that case. Several bridges' `validateWithdrawal` implementations perform no positivity/minimum check on `amount`, so a negative `actualAmount` reaches `bridge.createWithdrawalIntents` and gets serialized via `bigint.toString()` into a signed intent with a negative amount string.

### Finding Description
Broken equality: `actualAmount == amount - fee.amount` should always satisfy `actualAmount >= 0` (amount conservation: a debit must be non-negative) before it is embedded into a signed intent. `_estimateWithdrawalFee` enforces this via `FeeExceedsAmountError` (sdk.ts:421-424), but `createWithdrawalIntents` (sdk.ts:340-364) does not repeat this check — it blindly computes `actualAmount` and forwards it to `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`.

Whether this is exploitable depends on whether the selected bridge's `validateWithdrawal` independently rejects a negative/too-small `amount`:
- `IntentsBridge.validateWithdrawal` (intents-bridge.ts:59-72) only validates the destination address — no amount check at all — and `createWithdrawalIntents` (intents-bridge.ts:37-54) directly does `args.withdrawalParams.amount.toString()` into a `transfer` intent's `tokens` map, so a negative amount produces a malformed signed intent.
- `DirectBridge.validateWithdrawal` (direct-bridge.ts:154-192) also performs no amount check (only destination-address/account-existence checks), and `createWithdrawIntentPrimitive` (direct-bridge-utils.ts:19-61) does `params.amount.toString()` directly into `ft_withdraw`/`native_withdraw` amount fields, producing a negative amount string.
- `AuroraEngineBridge.validateWithdrawal` similarly only checks the destination address, no amount check.
- `PoaBridge.validateWithdrawal` (poa-bridge.ts:170-230) and `OmniBridge.validateWithdrawal` (omni-bridge.ts:332-531) DO perform minimum-amount validation (`MinWithdrawalAmountError`/`verifyTransferAmount`) that would reject a negative `amount` for those two routes.

So the vulnerability is real for the `InternalTransfer` (`IntentsBridge`), `NearWithdrawal` (`DirectBridge`), and virtual-chain (`AuroraEngineBridge`) routes, where an attacker (an integrator forwarding a caller-controlled `feeEstimation` object, or a caller directly invoking the SDK) can call `createWithdrawalIntents` directly with `withdrawalParams.feeInclusive = true` and a self-constructed `feeEstimation.amount > withdrawalParams.amount`, bypassing `estimateWithdrawalFee`/`_estimateWithdrawalFee` entirely. No re-validation exists to reject this before `bridge.createWithdrawalIntents` builds and returns the intent primitive for signing.

### Impact Explanation
For the affected routes (internal transfer, NEAR direct withdrawal, virtual-chain/Aurora withdrawal), a negative `amount`/`ft_withdraw.amount`/`native_withdraw.amount` string is embedded into an intent that the SDK returns for the caller to sign via `IntentSigner`. This is a malformed intent construction bug reachable purely through the public `createWithdrawalIntents(...)` API with attacker-controlled `feeEstimation`. The signed artifact does not represent a valid non-negative debit, which matches "a fee error draining a material share of the amount" / manipulated intent construction category, though the ultimate on-chain effect (whether intents.near itself rejects a negative `U128`/string amount) is outside this repo's control and not verified here — the contract's own parsing of the amount string is the final backstop, which is out of scope per the rules (defects inside intents.near are excluded). Within this repo, the SDK itself provides no defense-in-depth check that `_estimateWithdrawalFee` provides.

### Likelihood Explanation
Preconditions: the caller must invoke `createWithdrawalIntents` directly (bypassing `estimateWithdrawalFee`) with `withdrawalParams.feeInclusive = true` and a `feeEstimation.amount` they construct themselves that exceeds `withdrawalParams.amount`, and the resolved bridge must be `IntentsBridge`, `DirectBridge`, or `AuroraEngineBridge` (routes without amount validation). This is directly reachable by any SDK consumer/integrator with no privileged access, and is repeatable per call at no cost.

### Recommendation
Add the same `FeeExceedsAmountError` guard in `createWithdrawalIntents` (sdk.ts:340-364) that exists in `_estimateWithdrawalFee`: when `withdrawalParams.feeInclusive` is true, throw `FeeExceedsAmountError` if `withdrawalParams.amount <= feeEstimation.amount` before computing `actualAmount`. Additionally, consider adding a defensive `assert(actualAmount >= 0n, ...)` inside `IntentsBridge.createWithdrawalIntents`, `DirectBridge.createWithdrawalIntents`/`createWithdrawIntentPrimitive`, and `AuroraEngineBridge`'s withdrawal-intent construction, mirroring the amount sanity checks already present in `PoaBridge`/`OmniBridge`.

// packages/intents-sdk/src/sdk.createWithdrawalIntents.negative-amount.test.ts
it("should reject feeEstimation.amount > withdrawalParams.amount for internal transfer route", async () => {
  const sdk = new IntentsSDK({ /* ...minimal config with IntentsBridge only, mock HTTP as needed */ });

  const withdrawalParams = {
    assetId: "nep141:some-token.near",
    amount: 100n,
    feeInclusive: true,
    destinationAddress: "alice.near",
    routeConfig: { route: RouteEnum.InternalTransfer },
  };

  // Attacker-crafted feeEstimation, never returned by estimateWithdrawalFee
  const feeEstimation = {
    amount: 1000n, // > withdrawalParams.amount
    quote: null,
    underlyingFees: { [RouteEnum.InternalTransfer]: null },
  };

  // Equality under test: actualAmount = amount - feeEstimation.amount should be rejected when negative,
  // matching the guard in _estimateWithdrawalFee (FeeExceedsAmountError).
  await expect(
    sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation }),
  ).rejects.toThrow(FeeExceedsAmountError); // currently FAILS: no such throw occurs

  // Demonstrate the actual (buggy) outcome today:
  const intents = await sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation });
  const transferIntent = intents.find((i) => i.intent === "transfer");
  const amountStr = transferIntent!.tokens[withdrawalParams.assetId];
  expect(amountStr.startsWith("-")).toBe(true); // -900, a negative signed amount
});
