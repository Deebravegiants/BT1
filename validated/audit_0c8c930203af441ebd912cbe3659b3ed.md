## Analysis

The external report's root cause class is **input/account binding without authorization**: `MintableNonFungibleToken.mint` let anyone claim an arbitrary token *id* (the debt-issuance hash) ahead of the legitimate actor, permanently blocking that specific future operation.

The equivalent pattern exists in `core-contracts` `lockup-factory`. `LockupFactory::create` derives the lockup contract's account id **deterministically and solely from the caller-supplied `owner_account_id`**, and is callable by *anyone* who simply attaches the minimum deposit — there is no check that the caller is the owner, the NEAR Foundation, or any authorized funder. [1](#0-0) 

Because NEAR only allows the direct account (or a contract's own promise) to create its own subaccounts, an outside attacker cannot pre-create the subaccount directly — but they don't need to: they can simply call the public `create` entrypoint themselves for any `owner_account_id` they choose, with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and — critically — `staking_pool_whitelist_account_id`. [2](#0-1) 

Once that call succeeds, the deterministic account name (`sha256(owner_account_id)[..20] + factory`) is permanently occupied. A subsequent legitimate `create` call for the same `owner_account_id` (e.g. by the real funder/NEAR Foundation) fails at `create_account()` because the account already exists; the factory's callback simply refunds the deposit to whoever called it, it does not detect or flag the squatting: [3](#0-2) 

The `staking_pool_whitelist_account_id` baked in by the attacker at creation time cannot be changed later by the real owner — `lockup/src/owner.rs` has no setter, and `select_staking_pool` always checks against whatever whitelist was set at `new()`: [4](#0-3) 

### Title
Unauthenticated `create` in `LockupFactory` allows account-id squatting for arbitrary target owners - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` is a fully public, unauthenticated, payable method that computes the resulting lockup contract's account id purely as a deterministic hash of the attacker-supplied `owner_account_id` parameter, with no check that the caller is that owner or an authorized funder.

### Finding Description
`create` accepts any `owner_account_id` and only requires the caller to attach `MIN_ATTACHED_BALANCE` (3.5 NEAR). The resulting lockup account name is `sha256(owner_account_id)[..20].<factory>` — fully public/derivable and containing no per-call nonce, salt, or authorization token tied to the true funder. This is the same "id/target binding without authorization" flaw as the referenced `DebtToken.mint` bug: an unprivileged party can pre-claim the id that legitimately belongs to a specific future operation (here, a specific employee/investor's lockup grant) before the rightful party acts.

### Impact Explanation
Any unprivileged account can call `create` for a victim's known `owner_account_id` first, permanently occupying that deterministic account name with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration` and, most importantly, an attacker-controlled `staking_pool_whitelist_account_id`. This:
- Permanently prevents the legitimate funder (e.g. NEAR Foundation) from ever creating the intended lockup for that owner through the factory — subsequent `create` calls fail at `create_account()` and only refund the deposit, they do not remediate the squat.
- Plants an attacker-chosen staking-pool whitelist into a contract whose `owner_account_id` is the real victim, with no owner-facing way to later fix the whitelist (`lockup/src/owner.rs` has no setter for `staking_pool_whitelist_account_id`), so if the real funds are later sent to this pre-existing account instead of failing safely, the victim's `select_staking_pool` calls would be checked against an attacker-controlled whitelist contract, letting the attacker steer delegated NEAR into a malicious staking pool.

This matches the account-binding / duplicate-effect failure class called out for pool-creation flows.

### Likelihood Explanation
High for the denial-of-service component: it only requires knowledge of the target's `owner_account_id` (typically public, e.g. published grant recipients) and the minimum attached deposit; no privileged role, keys, or timing race against the factory internals is needed since the attacker calls the same public entrypoint directly. The escalation to fund theft requires the funder to subsequently top up the pre-existing squatted account instead of treating the failed `create` as a hard stop, which is an additional operational precondition.

### Recommendation
Require `create` to only be callable by (or on behalf of, with signed authorization from) the account matching `owner_account_id`, or incorporate an unpredictable/funder-controlled salt into the lockup account id so it cannot be squatted by observing a public target account name. Additionally, surface/alert when `create` fails due to a pre-existing account so operators do not attempt manual remediation transfers into a potentially attacker-configured contract.

### Proof of Concept
1. Attacker observes/knows a target grant recipient's account id, e.g. `victim.near`.
2. Attacker calls `lockup_factory.create({ owner_account_id: "victim.near", lockup_duration: ..., whitelist_account_id: "attacker-whitelist.near" }, attached_deposit = 3.5N)`.
3. The lockup account `sha256("victim.near")[..20].lockup_factory.near` is created and initialized with `staking_pool_whitelist_account_id = attacker-whitelist.near`.
4. NEAR Foundation later calls `create` with the real grant amount for `owner_account_id: "victim.near"` — the `create_account()` action fails because the account already exists, the deposit is refunded, and the intended lockup is never created as designed.
5. If Foundation instead funds the pre-existing account directly, `victim.near`'s future `select_staking_pool` calls are validated against `attacker-whitelist.near`, which the attacker fully controls.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
