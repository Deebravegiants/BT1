### Title
Unsigned `shop-domain` header lets any app-installer forge cross-tenant webhook attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#shop` (and `#topic`, `#api_version`, `#webhook_id`) are read straight from HTTP headers that are never part of the HMAC-signed payload. `HmacValidator.validate` only checks `to_signable_string`, which is `@raw_body`, so the `shop-domain` header can be swapped without invalidating the signature. Because `Context.api_secret_key` is one shared secret for the whole app (not per-shop), any attacker who installs the app on their own shop can obtain a genuinely-signed webhook body and then replay it to the target app's endpoint with an arbitrary victim `shop-domain` header, causing `WebhookMetadata#shop` to report an attacker-chosen shop.

### Finding Description
The claimed binding is: `shop authenticated by HMAC == shop trusted by the handler`. Tracing the code shows this never holds for webhooks:

- `Request#shop` simply returns the raw header value: `T.cast(shopify_header("shop-domain"), String)` [1](#0-0) .
- `to_signable_string` returns only `@raw_body`, never the headers [2](#0-1) .
- `HmacValidator.validate` / `validate_signature` compute the HMAC solely over `verifiable_query.to_signable_string` (the body) and compare it to the `hmac-sha256` header; the `shop-domain`/`topic` headers are never fed into the signature [3](#0-2) .
- `Registry.process` validates only the HMAC and then blindly constructs `WebhookMetadata.new(... shop: request.shop ...)`, handing this unauthenticated value to the host app's handler [4](#0-3) .
- The documented usage pattern feeds `data.shop` directly into business logic (`shop_domain: data.shop`) with no independent verification expected from the host app [5](#0-4) .

The header-normalization detail cited in the question (`headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }`) [6](#0-5)  is one possible mechanism for smuggling/duplicating a header key onto `shopify-shop-domain` when a host framework passes raw (non-Rack-normalized) header names straight through, since `sub` only removes the first literal occurrence of `"http_"` and duplicate resulting keys collapse in `to_h` with last-write-wins. But this mechanism is not actually necessary for the exploit: since the attacker is the direct originator of the HTTP request hitting the webhook endpoint, they already fully control every header name/value they send, including `shop-domain`, independent of any collision trick.

The real root cause is simpler and more fundamental: `shop-domain` is never cryptographically bound to the HMAC at all. `Context.api_secret_key` is one value shared by every shop that installs the app, so an attacker can legitimately install the target app on their own development shop, trigger a real webhook event, receive a validly-HMAC'd body from Shopify, and then relay that exact body (unmodified, so the HMAC still validates) to the app's webhook endpoint while setting `shopify-shop-domain` to an arbitrary victim shop string. `HmacValidator.validate` returns `true` because only the body is checked, and `Registry.process` calls the handler with `WebhookMetadata#shop` equal to the attacker's chosen string.

### Impact Explanation
The host app's webhook handler receives `data.shop` believing it identifies the shop that generated the event, and typically uses it to key data access, queue jobs, or run destructive operations (`shop/redact`, `customers/redact`, `customers/data_request`, order/product sync, etc.) as shown in the gem's own documentation example. Since `shop` is fully attacker-controlled while the HMAC still passes, an attacker who has installed the app on any shop (including a free development store they create themselves) can cause the host app to execute handler logic under an arbitrary victim shop's identity. This is a cross-tenant integrity/confidentiality issue at the app level, matching the "cross-tenant access" Critical class, because it lets one tenant's forged event be attributed to and acted upon for a different tenant's shop.

### Likelihood Explanation
Preconditions: the app must be installed on at least one shop the attacker controls (trivial — Shopify allows free development stores) and must expose an HTTP webhook endpoint that calls `Registry.process` as documented (the standard, documented usage). No secrets, tokens, or victim credentials are required. The attacker's cost is low (create a dev store, install the app, trigger one event, capture/relay the raw body with a modified `shop-domain` header) and the attack is fully repeatable against any victim shop string, for every webhook topic the app subscribes to.

### Recommendation
Include the shop-identifying headers (at minimum `shop-domain`, ideally `topic` and `webhook-id`) in the HMAC-signed material, or — since Shopify's real webhook HMAC scheme signs only the body — have `Registry.process`/the host app cross-check `request.shop` against the app's own session/shop storage (a shop that is actually installed and has an active access token) before invoking the handler, rather than trusting the header value outright. Also harden header normalization in `Request#initialize` to only strip a literal `HTTP_` prefix (anchored, e.g. `sub(/\Ahttp_/, "")`) rather than the first occurrence anywhere in the key, to remove the secondary collision vector.

### Proof of Concept
```ruby
# test/webhooks/shop_spoof_test.rb
require "test_helper"

class ShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "products/update", delivery_method: :http, path: "cb", handler: SpyHandler
    )
  end

  def test_shop_header_is_not_covered_by_hmac
    body = { "id" => 1 }.to_json
    hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), "secret", body)
    hmac_b64 = Base64.encode64(Digest.hexdecode(hmac) rescue nil) # matches Request#hmac decoding

    legit_headers = {
      "x-shopify-topic" => "products/update",
      "x-shopify-hmac-sha256" => Base64.strict_encode64([hmac].pack("H*")),
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2023-10",
      "x-shopify-webhook-id" => "id-1",
    }
    request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: legit_headers)
    assert ShopifyAPI::Utils::HmacValidator.validate(request) # signature still valid

    # attacker relays SAME body/hmac but swaps only the shop-domain header
    spoofed_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
    spoofed_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)

    assert ShopifyAPI::Utils::HmacValidator.validate(spoofed_request) # STILL true: proves shop is unauthenticated
    assert_equal "victim-shop.myshopify.com", spoofed_request.shop

    ShopifyAPI::Webhooks::Registry.process(spoofed_request)
    assert_equal "victim-shop.myshopify.com", SpyHandler.last_data.shop # handler acted on the forged shop
  end
end
```
This demonstrates that `to_signable_string`/`HmacValidator.validate` accept an identical body with an arbitrary `shop-domain` header, proving `Webhooks::Request#shop` is unauthenticated and reaches the handler as-is.
