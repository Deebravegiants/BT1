### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header — HMAC only covers the request body, not the shop claim - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which for this class is defined as `@raw_body` alone. The header carrying the shop identity is never included in the signed material, so it is not covered by the HMAC binding that the gem claims to enforce.

### Finding Description
`Webhooks::Registry.process` gates webhook handling on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The validator computes the signature purely from `verifiable_query.to_signable_string` and compares it with the `hmac` field, using the app's `client_secret`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body: [3](#0-2) 

But the `shop` value that is later trusted and handed to the app's webhook handler is pulled straight from an HTTP header, which is not part of the signed bytes at all: [4](#0-3) [5](#0-4) 

`Registry.process` passes this unauthenticated `request.shop` straight into the `WebhookMetadata` given to the app's handler as the tenant identifier: [1](#0-0) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted on by the handler`. In reality, the HMAC only authenticates `raw_body`; the `shop` claim delivered to the consumer of this library is derived from bytes (the header) that were never verified. Because the app's `client_secret` is shared across all shops that install the app (it is not per-tenant), any HMAC computed over a given body with that secret is valid for every tenant using that app — the signature does not bind to a specific shop at all. A user who controls or can replay a validly-signed webhook body for their own shop (e.g., by triggering `carts/update`, `products/create`, or any webhook whose body they influence) can then re-send that exact body with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain, and `HmacValidator.validate` still returns `true`, because it never looked at the header.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: `Registry.process` hands the handler a `shop` value that the attacker fully controls despite the "validated" HMAC check, leading to cross-tenant confusion in any application logic keyed off `WebhookMetadata#shop` (e.g., writing attacker-supplied `body` content into another merchant's records, or firing shop-scoped side effects — including the mandatory `shop/redact`/`customers/redact`/`customers/data_request` compliance topics — against a shop the attacker never authenticated for). This is a cross-tenant identity binding failure caused directly by this gem's own signing/validation code, not a downstream app choice to ignore documentation.

### Likelihood Explanation
Exploitation requires only unprivileged internet access to the app's public webhook HTTP endpoint plus the ability to obtain one validly-HMAC'd payload for any shop (trivial for an attacker who owns/installs the app on their own store — webhooks routinely echo attacker-influenced content, e.g. product/customer/cart payloads). No access token, `client_secret`, or privileged account is needed; the attacker never sees the secret, they simply replay a legitimately-signed body with a forged header.

### Recommendation
Bind the shop identity into the signed material or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the verified request, e.g. by including the shop header (and ideally topic/webhook-id) in `to_signable_string`, or by requiring callers to independently corroborate the header's shop against a known/expected shop before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers a webhook (e.g., `products/create`) whose payload body the attacker can influence by creating a product with attacker-chosen fields.
2. Shopify sends: `POST /webhooks` with headers `X-Shopify-Hmac-Sha256: <hmac(body, client_secret)>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and the JSON body.
3. Attacker intercepts/replays this exact request but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, leaving `hmac-sha256` and body untouched.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; validation succeeds because it only recomputes HMAC over `@raw_body`, matching the untouched value. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, even though the payload and signature originated from the attacker's own shop. [7](#0-6) 
6. Any application logic that trusts `WebhookMetadata#shop` for tenant-scoped writes/side effects now operates on the wrong (victim) tenant using attacker-controlled data.
