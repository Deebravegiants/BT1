### Title
Missing sanity check before `assetReserve - virtualLtReserve` subtraction lets `Pair.swap`'s `+1` K-slack grind reserves into a permanent graduation/trading-freeze underflow — ([File: packages/contracts/src/Bonding.sol])

### Summary
`_prepareGraduationLiquidity` and the dual-trigger check both recover the launch-time virtual LT reserve and subtract it from the live stored `assetReserve` with no bound check that `assetReserve >= virtualLtReserve` before doing so [1](#0-0) . Exactly like the f2fs bug class — trusting an on-disk/derived value's consistency and only discovering the violation deep inside a later, unguarded arithmetic op — alt.fun trusts that `assetReserve` (a value mutated only through `Pair.swap`'s rounding-tolerant K-invariant check) can never fall below the immutable `virtualLtReserve` baked in at mint. `Pair.swap` enforces the invariant with a `+1` slack, `(newTokenReserve+1)*(newAssetReserve+1) < k`, rather than a strict `>= k` check [2](#0-1) , which is the exact off-by-one AMM rounding tolerance this class of bug lives in.

### Finding Description
`virtualLtReserve` is recovered as `Pair.k() / Token.TOTAL_SUPPLY()`, which is provably equal to the exact `assetReserve` value passed into `Pair.mint` at launch (because the virtual token reserve is set to `totalSupply`) [3](#0-2) . `_prepareGraduationLiquidity` then computes:

```
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
```

with zero sanity/clamp guard before the subtraction [1](#0-0) . The AGENTS.md documentation confirms the dual USD graduation trigger performs this same unguarded subtraction live on every buy: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` [4](#0-3) .

The invariant "`assetReserve` never drops below its launch-time value" is only true if `Pair.swap`'s K check is exact. It is not: the check is `(newTokenReserve + 1) * (newAssetReserve + 1) < k`, a documented, deliberate `+1` slack [2](#0-1) , called out in the project's own docs as one of the load-bearing AMM primitives to scrutinize (`Pair.swap's +1 K slack`). This class of off-by-one tolerance is a textbook grinding vector in constant-product AMMs: an attacker who round-trips many small buy/sell pairs through `Bonding.buy`/`Bonding.sell` → `Router._computeBuy`/`_computeSell` can, trade by trade, exploit rounding favorable to the trader within the `+1` tolerance band, incrementally pushing the stored `assetReserve` below the launch-time virtual baseline without ever tripping `KInvariantViolated`.

Once `assetReserve < virtualLtReserve` for a token, every subsequent call into the unguarded subtraction underflows and reverts with Solidity's Panic(0x11):
- Any buy that triggers the dual-trigger check (`canGraduate`/`_enterGraduating` inline path) reverts, since the USD-trigger computation performs the same subtraction.
- The permissionless `triggerGraduation` entry point reverts identically [5](#0-4) .

This is precisely the f2fs analog: a value assumed internally consistent (block address / SIT table state ↔ `assetReserve` / virtual-reserve baseline) is used in a downstream operation (`f2fs_invalidate_blocks` ↔ the underflowing subtraction) with no sanity check, and the inconsistency is only reachable through a crafted sequence of otherwise-legal operations (fuzzed image ↔ ground-down rounding slack), producing a hard crash/panic (`BUG_ON` ↔ Solidity underflow revert) instead of a graceful error.

### Impact Explanation
Once ground below the virtual baseline, the token is permanently bricked:
- `Lifecycle.Curve` can never transition to `Graduating` (both `_enterGraduating`'s inline trigger and the permissionless `triggerGraduation` revert) [6](#0-5) .
- The token's 250M `LP_RESERVE` tokens remain permanently parked in `Bonding`, unreachable — graduation is the only path that ever mints/burns them [7](#0-6) .
- Every subsequent buy that would need to evaluate the USD trigger reverts, freezing the curve for that token and trapping the creator's seed and all subsequent traders' curve-held LT/tokens with no graduation, no LP, and no recovery path (`LPLock` has no v1 rescue path per the docs).

This is a permanent freeze of trader, creator, and protocol funds for the affected token — satisfying the "Validate" bar of concrete permanent freezing of funds.

### Likelihood Explanation
The prerequisite — repeated small buy/sell round trips through the standard `Zap`/`Bonding` buy/sell path grinding the `+1` K-slack — is reachable by any unprivileged trader using only `Zap.buy`/`Zap.sell` (or `Bonding.buy`/`Bonding.sell` via an allowlisted router/Zap), requires no privileged role, and costs only gas plus curve fees, which the AMM's `+1` slack is specifically documented to permit as rounding-favorable-to-trader dust. The exact number of round trips needed to grind a meaningful gap depends on the token's `TOTAL_SUPPLY`/reserve magnitudes and was not fully re-derived numerically in this pass (Router's exact `_computeBuy`/`_computeSell` rounding direction per trade was not re-examined line-by-line before the tool budget ran out), so the concrete trade count and dollar cost of the grind are unconfirmed and should be validated with a fuzz/invariant test before treating this as fully proven.

### Recommendation
Add an explicit sanity check before every `assetReserve - virtualLtReserve` subtraction (in `_prepareGraduationLiquidity` and in the dual-trigger USD check), clamping to zero (`ltFromPair = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0`) exactly as the codebase already does elsewhere for the analogous `ltBalance - p.ltFromPair` saturating subtraction in `finalizeGraduation` [8](#0-7) . Separately, tighten `Pair.swap`'s K-invariant check (remove or shrink the `+1` slack, or track cumulative rounding loss) so that reserves cannot be legally ground below their launch-time floor through repeated legitimate trades.

### Proof of Concept
1. Launch a token via `Zap.createToken` (creator seed buy establishes `assetReserve = virtualLtReserve` baseline + seed).
2. As an unprivileged trader, repeatedly call `Zap.buy` then `Zap.sell` (or `Bonding.buy`/`sell` directly if allowlisted) with amounts chosen to sit on the rounding-favorable side of `Pair.swap`'s `(newTokenReserve+1)*(newAssetReserve+1) < k` check each round trip.
3. After enough round trips, the stored `_pool.assetReserve` in `Pair.sol` drifts to a value below `Pair.k() / Token.TOTAL_SUPPLY()` (the recovered `virtualLtReserve`).
4. Any further call that evaluates the USD graduation trigger (a normal buy, or the permissionless `Bonding.triggerGraduation`) executes `storedAssetReserve - virtualLtReserve` and reverts with a Solidity arithmetic-underflow Panic, permanently freezing the token in `Lifecycle.Curve` with `LP_RESERVE` tokens stranded in `Bonding` and no further trading/graduation possible.

(Note: step 2's exact iteration count/cost to realize the underflow was not numerically confirmed against `Router._computeBuy`/`_computeSell`'s precise rounding formulas within this investigation; this should be validated with a Foundry fuzz test before remediation prioritization.)

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }

- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
