### Title
Webhook Tenant Attribution (`shop`, `topic`, `webhook_id`) Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook to a tenant are read from unauthenticated HTTP headers that are never part of the HMAC-signed payload. `ShopifyAPI::Webhooks::Registry.process` only validates that the body matches the HMAC, then blindly hands `request.shop` to the app's handler as the tenant identifier. This breaks the identity binding the documentation itself promises ("This will verify the request did indeed come from Shopify").

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the unauthenticated `request.shop` to the app handler as the tenant identity: [3](#0-2) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and describes `shop` as "The shop domain of the webhook" that apps are expected to trust and use directly (e.g., `shop_domain: data.shop`): [4](#0-3) [5](#0-4) 

This is the same class of bug as the reference report: a validity check (`HMAC-valid`) is treated as proof of an unrelated binding (`shop == authenticated shop`) that it never actually covers — analogous to the reference bug where `coin.amount` was checked only conditionally while `locked_amount` was unconditionally incremented for the caller's identity. Here, the *body* is bound to the secret, but the *shop attribution* used for every downstream tenant-scoped action is not, so:

`shop_signed (⊆ HMAC(raw_body, secret)) ≠ shop_used_for_tenant_routing (request.shop, from header)`

### Impact Explanation
Because `shop` is not covered by the HMAC, any party capable of obtaining one legitimately-signed `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store and receives a real webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `Topic`/`Webhook-Id`) headers to name a victim shop. `Registry.process` will accept it as valid (HMAC only checks the body) and dispatch it to the handler with `data.shop` set to the victim's domain. Any app that uses `data.shop` to key data storage, trigger tenant-scoped side effects (e.g., "shop redact", "customers/data_request" GDPR webhooks, order/inventory sync) will process attacker-controlled content under another merchant's tenant — a cross-tenant data integrity/confidentiality violation, which meets the Critical bar (cross-tenant access).

### Likelihood Explanation
Any developer or merchant who signs up for the app (an "unprivileged internet user" relative to other tenants) can capture one valid `(body, hmac)` pair from their own legitimate webhook traffic and replay it against the shared public webhook endpoint with a forged shop header — no access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the value that is HMAC-verified (or otherwise cryptographically bind them to the raw body), or independently validate that the `shop` header corresponds to a shop with an active installation/session before dispatching to the handler, rather than trusting the header solely because the body's HMAC is valid.

### Proof of Concept
1. Install the target app as `attacker-shop.myshopify.com`; trigger a subscribed webhook (e.g., `orders/create`) so Shopify sends a real request with a valid `X-Shopify-Hmac-Sha256` header for that body.
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` value.
3. Send a forged HTTP POST directly to the app's public webhook endpoint, reusing the captured body and HMAC header unchanged, but setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks the (unchanged) body against the (unchanged) HMAC — validation succeeds.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, causing the app to process/store attacker data under the victim's tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
