The bug-class analog is present in `IntentGatewayV2`'s fill logic. While the input/escrow side (`placeOrder`) explicitly measures balances before/after transfers to support fee-on-transfer tokens, the output side (`fillOrder`) that pays the beneficiary does not — it uses a fixed-amount `safeTransferFrom` and treats the nominal amount as "delivered," releasing the full escrow to the solver regardless of what the beneficiary actually received.

### Title
Deflationary/fee-on-transfer output token lets solver claim full escrow while beneficiary receives less - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` deliver order output tokens to the beneficiary via a fixed-amount `IERC20.safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)`, then unconditionally treat `fillAmount`/`totalRequired` as "amount filled" without verifying the beneficiary's actual balance increase. [1](#0-0)  The same nominal-amount pattern appears in the cross-chain fill path. [2](#0-1)  If the order's output token is deflationary/fee-on-transfer, the beneficiary receives less than `totalRequired`, yet the escrow (input tokens) is fully released to the solver as if the fill were complete.

### Finding Description
For same-chain fills, `beneficiaryTotal = fillAmount + beneficiaryShare` tokens are pulled from the solver and sent to `beneficiary` via `safeTransferFrom`; `amountFilled = alreadyFilled + fillAmount` is then recorded using the nominal `fillAmount`, not the beneficiary's actual received balance: [3](#0-2)  when `amountFilled == totalRequired`, `isFullyFilled` stays true and the full escrowed input (`escrowedAmount = _orders[commitment][...]`) is released to the solver via `_withdraw`. [4](#0-3) 

For cross-chain fills, the same pattern occurs: `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` is issued without a balance check, and `outputFills[i]` records the nominal `totalRequired`, which is what gets posted in the `RedeemEscrow` message dispatched back to the source chain to release the full escrow to the solver. [5](#0-4) 

This is inconsistent with the protocol's own handling of fee-on-transfer tokens on the input/escrow side in `IntentGatewayV2.placeOrder`, where balances are explicitly snapshotted before and after transfers so the escrow reflects only what was actually received. [6](#0-5)  No equivalent actual-balance verification exists for the beneficiary-facing transfer in the fill path.

### Impact Explanation
Any order whose output asset is a deflationary or fee-on-transfer token causes the beneficiary (the user who placed the order) to receive less than the amount they were promised, while the solver still claims full escrow release for the input tokens and the order is marked as fully filled. This is a direct, unbacked value loss for the order-placing user — funds committed as escrow are released in full even though the counter-payment was short, matching the "deflationary token makes counterparty lose money" bug class from the referenced report.

### Likelihood Explanation
Reachable by any unprivileged solver calling the public `fillOrder` entrypoint with an order whose output token is fee-on-transfer — no special privileges are required. It can occur unintentionally with any legitimate deflationary/fee-charging ERC20 configured as an output asset, and could also be exploited by a solver who deploys/uses such a token deliberately (or in collusion) to pay less than agreed while still claiming the full input escrow.

### Recommendation
Mirror the input-side pattern already used in `placeOrder`: snapshot the beneficiary's token balance before the transfer and compute the actually-received amount after the transfer, then use that actual amount (not the nominal `fillAmount`/`totalRequired`) when updating `_partialFills`, determining `isFullyFilled`, computing `escrowedAmount`, and building the `outputFills`/`RedeemEscrow` body for cross-chain fills.

### Proof of Concept
1. Create an order whose `output.assets[0].token` is a fee-on-transfer ERC20 (e.g., 1% fee), with `totalRequired = 1000e18`.
2. Solver calls `fillOrder` supplying `solverAmount = 1000e18`; `safeTransferFrom(solver, beneficiary, 1000e18)` executes, but the beneficiary's balance only increases by `990e18` due to the token's transfer fee.
3. `fillAmount = 1000e18` (nominal) is recorded in `_partialFills`; since `alreadyFilled + fillAmount == totalRequired`, `isFullyFilled = true`.
4. The full escrowed input (e.g., `1000e6` USDC) is released to the solver via `_withdraw`, and `OrderFilled` is emitted — even though the beneficiary only actually received `990e18` of the output token, a 1% loss versus what the order guaranteed.
