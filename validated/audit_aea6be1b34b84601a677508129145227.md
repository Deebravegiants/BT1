### Title
Webhook Shop Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating its HMAC signature, then unconditionally trusts the `X-Shopify-Shop-Domain` header to identify which tenant the webhook belongs to. The HMAC signature, however, only covers the raw request body, not the shop-domain header, breaking the binding between "the shop whose secret produced this HMAC" and "the shop the library tells the host app this webhook is for."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is pulled directly from an HTTP header supplied by whoever sends the request, with no cryptographic linkage to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which only checks `to_signable_string` (the body) against the secret — and then, once that check passes, immediately trusts `request.shop` to construct the tenant-identifying `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms this: it only ever calls `verifiable_query.to_signable_string`, never touching headers like shop-domain: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop_whose_secret_signed_the_body == shop_attributed_to_the_webhook_by_the_library`

Since the shop-domain header is entirely outside the signed content, any party who can produce one legitimately-signed `(raw_body, hmac)` pair — trivially achievable by installing the app on their own store and triggering any webhook topic, since they are a legitimate tenant with a real installation — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the (attacker-controlled) body came from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately installs the app on their own shop (an unprivileged action requiring no special credentials or access to the app's `client_secret`) can cause the library to attribute attacker-controlled webhook payloads to any other shop domain of their choosing. Depending on how the host application uses `WebhookMetadata#shop` (e.g., looking up the corresponding session/access token, gating GDPR-redaction logic, updating per-shop state, or triggering shop-scoped side effects), this can lead to cross-tenant data injection or actions performed against a victim tenant's context — matching the "cross-tenant access" impact category, since the library itself provides the tenant-identity field to the host app without validating that it corresponds to the signer of the payload.

### Likelihood Explanation
Likelihood is High for any host app that relies on the library's `Registry.process`/`WebhookMetadata` shop attribution without independently re-verifying the shop (which is the documented, intended usage pattern). The attacker needs no privileged credential — only their own legitimate app installation, which the gem's own webhook-processing model implicitly trusts to prove nothing about the victim shop referenced in the forged header.

### Recommendation
Include the shop-domain (and topic/webhook-id) header value in the signed payload verified by `HmacValidator`, or otherwise cryptographically bind `request.shop` to the HMAC-covered content, e.g., by including it in `to_signable_string`, or by cross-checking `request.shop` against a shop value independently derived from a trusted, signed source (such as an authenticated session lookup) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` (a legitimate, unprivileged action).
2. Attacker triggers any registered webhook topic on their shop, capturing the resulting `raw_body` and its valid `X-Shopify-Hmac-Sha256` value — genuinely signed with the app's real `api_secret_key` server-side, without the attacker ever needing to know the secret.
3. Attacker resends this exact `raw_body` + `hmac` pair to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) , which passes because it only checks the body.
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)` using the forged `victim-shop.myshopify.com` value [6](#0-5) , and passes it to the host app's handler as if it were a legitimate webhook from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
