### Title
`EvmHost.withdraw` can drain the shared feeToken pool below outstanding relayer-fee obligations, causing `dispatchTimeOut`/`dispatchIncoming` fee payouts to permanently revert - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` uses a single, un-partitioned `feeToken()` balance held by the contract itself to fund two distinct obligations: (1) relayer rewards / refunds owed against every outstanding `_requestCommitments[commitment].fee` for requests dispatched but not yet delivered or timed out, and (2) "bridge revenue" that can be swept out via `withdraw()`. Because `withdraw()` accepts an arbitrary `amount` with no check that the remaining balance still covers the sum of all pending `FeeMetadata.fee` obligations, a legitimate withdrawal can leave the contract without enough `feeToken` balance to pay out fees it already promised, causing the `safeTransfer` calls in `dispatchTimeOut` and `dispatchIncoming(GetResponse,...)` to revert.

### Finding Description
Every `dispatch(DispatchPost)`/`dispatch(DispatchGet)` call collects `post.fee`/`get.fee` into the `EvmHost` contract itself and records it in `_requestCommitments[commitment] = FeeMetadata({sender, fee})`: [1](#0-0) 

This fee is later paid out from the same pooled balance, keyed only by the commitment's `FeeMetadata`, in three places:
- On a GET response delivery, `safeTransfer(relayer, fee)`: [2](#0-1) 
- On a GET timeout, `safeTransfer(meta.sender, meta.fee)`: [3](#0-2) 
- On a POST timeout, `safeTransfer(meta.sender, meta.fee)`: [4](#0-3) 

None of these three payout paths verify the contract's actual `feeToken` balance beforehand; they rely entirely on the invariant that "balance held ≥ sum of unpaid `_requestCommitments[*].fee`" always holding.

That invariant can be broken by `EvmHost.withdraw`, which is restricted only to `_hostParams.hostManager` and transfers an arbitrary caller-supplied `params.amount` of any token (including the `feeToken`) out of the contract with no accounting check against the outstanding fee obligations tracked in `_requestCommitments`: [5](#0-4) 

`withdraw` is reachable through the normal, non-malicious relayer-fee-withdrawal flow: `pallet-ismp-relayer::withdraw` lets *any relayer* that has accumulated fees sign a withdrawal request; this is dispatched as an ISMP POST to the destination chain's `HostManager`, which calls `IHostManager(_params.host).withdraw(withdrawParams)` unconditionally once the relayer/admin restriction and Hyperbridge-source check pass: [6](#0-5) [7](#0-6) 

Because the `available_amount` computed by the relayer pallet is based purely on proven deliveries and is entirely decoupled from the destination `EvmHost`'s live `_requestCommitments` bookkeeping, nothing prevents a legitimate, routine fee-withdrawal round (or a "bridge revenue" withdrawal by governance) from pulling the `feeToken` balance below the sum still owed for in-flight (undelivered/not-yet-timed-out) requests dispatched from that chain. This is structurally identical to the Symmetrical `LibQuote.returnTradingFee` issue: a shared balance is debited by an unrelated authorized action (fee collector withdrawal / fee collector rotation), after which a legitimate refund operation that assumes the balance is always sufficient reverts.

### Impact Explanation
Once the `feeToken` balance drops below an outstanding commitment's `fee`, any subsequent `dispatchTimeOut` (POST or GET) or `dispatchIncoming(GetResponse,...)` call touching that commitment (or any commitment competing for the same insufficient pool) permanently reverts on the `safeTransfer`. Since `HandlerV2`/`EvmHost` retry logic re-stores `_requestCommitments[commitment] = meta` on failure so it "can be retried," the message is stuck in a revert loop until the contract is refunded — a route becoming unable to deliver/timeout messages, and relayers/payers being permanently denied fees they are legitimately owed. This is a Medium-severity DoS/fund-freezing condition on the messaging pipeline, matching the accepted impact classes (permanent freezing of funds / a route unable to deliver messages).

### Likelihood Explanation
The withdrawal path is part of standard, expected relayer operation (accumulate fees → withdraw), not an attack requiring compromised keys or malicious intent — any relayer that has legitimately earned fees on other chains can trigger a `withdraw()` call against a chain whose `EvmHost` currently holds fee token earmarked for other in-flight requests. Because there is no accounting check tying `withdraw()`'s allowed amount to the sum of unpaid `_requestCommitments`, this can occur during ordinary operation whenever outstanding relayer fees and claimable withdrawals happen to overlap in timing, making the likelihood non-trivial.

### Recommendation
Track the total amount reserved for outstanding `_requestCommitments` (or equivalently the "free"/withdrawable surplus) separately from the total `feeToken` balance, and have `EvmHost.withdraw` (and any governance/relayer-triggered path that reaches it) revert or clamp when `params.amount` would reduce the balance below the sum of all pending relayer-fee obligations. Alternatively, maintain a running `reservedFees` counter incremented on `dispatch`/`fundRequest` and decremented on payout, and enforce `balance - amount >= reservedFees` inside `withdraw`.

### Proof of Concept
1. On chain A's `EvmHost`, a user dispatches a POST request with `fee = X`, transferring `X` `feeToken` into `EvmHost` and recording `_requestCommitments[c] = {sender, X}` (`evm/src/core/EvmHost.sol:930-948`).
2. Before this request is delivered or times out, a relayer who separately earned `Y` `feeToken` worth of fees on chain A (from prior, unrelated deliveries) calls `pallet-ismp-relayer::withdraw` for chain A, where `Y > (feeTokenBalance(EvmHost) - X)`. This dispatches an ISMP POST that `HostManager.onAccept` forwards unmodified to `EvmHost.withdraw({beneficiary: relayer, amount: Y, token: feeToken})` (`evm/src/core/HostManager.sol:134-159`, `evm/src/core/EvmHost.sol:647-660`).
3. `EvmHost.withdraw` performs `safeTransfer(relayer, Y)` unconditionally, leaving `EvmHost`'s `feeToken` balance `< X`.
4. When the original request in step 1 times out, `HandlerV2`/`EvmHost.dispatchTimeOut` attempts `IERC20(feeToken()).safeTransfer(meta.sender, X)` (`evm/src/core/EvmHost.sol:901-905`), which reverts due to insufficient balance, permanently blocking that request's timeout processing (and any future request competing for the same shortfall) until additional `feeToken` is deposited into `EvmHost`.

        }

    function onAccept(IncomingPostRequest calldata incoming)
        external
        override
        restrict(msg.sender, _params.host)
        restrict(incoming.relayer, _params.admin)
    {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        } else if (action == OnAcceptActions.SetAdmin) {
            // Rotates the governance relayer.
            address newAdmin = abi.decode(request.body[1:], (address));
            if (newAdmin == address(0)) revert InvalidAdmin();
            emit AdminUpdated({previous: _params.admin, current: newAdmin});
            _params.admin = newAdmin;
        }
    }
