## Title
Unbounded ancestry-walk loop in GRANDPA finality proof verification allows an attacker-crafted consensus proof to hang the chain (endless data attack) - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` walks parent-hash pointers from a submitted header back to a base hash, but the header set it walks over (`unknown_headers` / `votes_ancestries`) is fully attacker-controlled data submitted alongside a GRANDPA consensus proof. The walk has no cycle detection and no bound on iteration count, mirroring the cosign `FetchAttestations` bug class: an attacker who controls the content of a "batch" (there, attestations from a registry; here, headers in a finality proof) can force the verifier into an endless or extremely long loop.

### Finding Description
`AncestryChain::ancestry` in [1](#0-0)  is:
```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```
The `ancestry` map is built directly from the submitted `unknown_headers`/`votes_ancestries` in [2](#0-1) , with no validation that these headers form an acyclic chain converging on `base` before the walk begins.

This function is called from two places that consume attacker-submitted proof content directly:
1. `verify_with_voter_set`, once per precommit, using `self.votes_ancestries` [3](#0-2) .
2. `verify_grandpa_finality_proof`, using `finality_proof.unknown_headers` [4](#0-3) .

Because every header's `parent_hash` field is attacker-chosen (headers here are just decoded structures, not chain-verified before this point), an attacker can submit two or more headers whose `parent_hash` pointers form a closed cycle that does not include `base` (`consensus_state.latest_hash` or a precommit's `target_hash`). In that case `current_hash` will cycle among the same finite set of hashes forever, since every lookup in `self.ancestry` succeeds (`Some`) and `current_hash` never equals `base`. The loop never returns `Err(NotDescendent)` and never terminates.

This verification path is reachable from a single unprivileged submission: GRANDPA is one of the supported consensus clients used by `pallet-ismp`'s consensus message handling (`modules/ismp/core/src/handlers/consensus.rs`) and by `GrandpaConsensusClient::verify_consensus` (`modules/ismp/clients/grandpa/src/consensus.rs`), both of which are invoked from `pallet_ismp::Call::handle_unsigned`, an **unsigned, permissionless** extrinsic [5](#0-4) . `validate_unsigned` for that call executes the messages (including consensus verification) directly in the transaction-pool validation path [6](#0-5) , meaning the infinite loop can be triggered purely by broadcasting a malicious extrinsic to the pool — before it is even included in a block.

### Impact Explanation
An infinite/extremely long native loop inside consensus verification, triggered from transaction-pool validation (`validate_unsigned`) or block execution (`handle_unsigned`), halts the node performing verification indefinitely. Since every full node validates unsigned transactions before including them, and GRANDPA-anchored parachains rely on this path to advance the state machine, a single crafted message can render nodes unresponsive, effectively producing a "route unable to deliver messages" outcome for the affected consensus client (denial-of-service to relaying and message delivery for that state machine, and potentially to block production if hit during execution). This is a Medium/High severity liveness issue analogous to the cited cosign endless-data DoS.

### Likelihood Explanation
The attack requires no privilege beyond crafting and submitting an unsigned ISMP message with a GRANDPA consensus proof containing self-referential headers — something any user or relayer can construct offline. No signatures on the crafted headers pointer-graph are checked before the ancestry walk executes, so validity of individual header content is irrelevant to triggering the loop.

### Recommendation
Bound the ancestry walk: track visited hashes and abort with an error (e.g., a `CyclicAncestry` error) if a hash is revisited before reaching `base`, or cap the maximum number of iterations to the number of submitted headers (`self.ancestry.len()`), returning an error once exceeded. Apply this fix to both call sites (`verify_with_voter_set`'s per-precommit ancestry call and `verify_grandpa_finality_proof`'s ancestry call).

### Proof of Concept
1. Construct two headers `A` and `B` where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)` (a 2-cycle), with `A.number > B.number` so `A` is picked as `target` by `max_by_key`.
2. Set `finality_proof.block = hash(A)` and include `A`, `B` in `unknown_headers` and/or `votes_ancestries`, with `consensus_state.latest_hash` (`base`) set to any hash not in `{hash(A), hash(B)}`.
3. Submit this as a `ConsensusMessage` inside a `pallet_ismp::Call::handle_unsigned` extrinsic (or as a `handleConsensus` proof against a GRANDPA-backed EVM light client, if wired similarly).
4. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())`, which loops forever bouncing between `hash(A)` and `hash(B)`, never equal to `base`, hanging the calling thread/node.

Note: I was unable to trace the exact runtime wiring showing which live parachain deployments actually enable the GRANDPA consensus client (only the primitives/verifier crates and generic pallet call paths were confirmed); confirming production exposure would require checking each runtime's registered consensus clients, which was not fully explorable within the available context.
