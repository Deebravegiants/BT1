### Title
`Zap._sellInternal`'s hardcoded 18dp→6dp normalisation miscalculates the sell-side USD floor check on real (6-decimal) USDC, bricking `Zap.sell`/`sellWithPermit` for all traders - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._sellInternal` computes a manual pre-check estimate of sale proceeds and divides it by a hardcoded `1e12` before comparing it against `minUsdcAmount()`. This divisor was added ("Regression for issue #313") to reconcile the estimate's decimal scale with `minUsdcAmount()`'s scale, but the reconciliation is derived from the test suite's non-standard 18-decimal mock USDC, not from the real, 6-decimal USDC used in production, per the codebase's own comments. On the real deployment the two values are already in the same scale, and the extra `/1e12` collapses the estimate to near zero for any realistic trade, causing the floor check to spuriously fire on every sell.

### Finding Description
`IBounceLeveragedToken.ltToBaseAmount(ltAmount)` is defined as `ltAmount * exchangeRate / 1e18` [1](#0-0)  and is documented as the inverse of `baseToLtAmount`, i.e. it returns a value in the exact same units that `mint`/`redeem`'s `baseAmount` parameter uses [2](#0-1) . Since `Zap` feeds `netUsdc`/`baseToConvert` — raw, native-decimal USDC pulled directly via `safeTransferFrom` from the real USDC contract — straight into `mint()` with no scaling [3](#0-2) , `baseAmount`/`ltToBaseAmount` must operate in the real base asset's native decimals (6dp for real USDC, as the code repeatedly documents: "real USDC, 6dp" and "Live BounceTech mint/redeem floor in USDC (6dp)") [4](#0-3) [5](#0-4) .

In `_sellInternal`, the pre-check is computed with the identical formula:
```
uint256 grossUsdcEstimate = (ltReceived * IBounceLeveragedToken(lt).exchangeRate()) / 1e18;
if (grossUsdcEstimate / 1e12 < minUsdcAmount()) revert BelowMinAmount();
``` [6](#0-5) 

Because `grossUsdcEstimate` is mathematically identical to `ltToBaseAmount(ltReceived)` (same formula), it is already denominated in the real base asset's native decimals (6dp on mainnet) — the same scale as `minUsdcAmount()`, which reads `bonding.bounceGlobalStorage().minTransactionSize()` directly, also in 6dp [5](#0-4) . No further scaling is needed. The `/1e12` divisor was justified purely by the test harness's use of an 18-decimal mock USDC ("Mock USDC in `_deployCore` uses the OZ default of 18 decimals" [7](#0-6) ) combined with a `minTransactionSize` value deliberately chosen to "mirror the $10 mainnet value" using a 6dp-style literal (`10e6`) [8](#0-7) . That mismatch exists only because the test fixture intentionally uses non-production decimals for USDC; it does not exist on the real deployment, where both `grossUsdcEstimate` and `minUsdcAmount()` are natively 6dp.

Applying `/1e12` unconditionally in production code therefore divides an already-6dp quantity by another `1e12`, so `grossUsdcEstimate / 1e12` rounds down to `0` for essentially any real-world sell size (real USDC amounts on the order of `1e0`–`1e12` raw units, i.e. up to ~$1,000,000). Since `minUsdcAmount()` is non-zero (mainnet floor ~`10e6`), the check `0 < minUsdcAmount()` is always true, and `BelowMinAmount` fires unconditionally on every call to `Zap.sell`/`sellWithPermit`, regardless of trade size — including the on-curve-to-graduation-trigger path.

This is a decimals-incompatibility bug in alt.fun's own reserve-asset accounting layer, directly analogous to the reported ERC4626 issue: a hardcoded assumption about the relationship between two decimal scales (here, LT/exchangeRate-derived USD estimate vs. the BounceTech `minTransactionSize` floor) that only holds under a non-representative configuration, causing the code to spuriously reject/exclude all valid production inputs instead of handling the real scale correctly.

### Impact Explanation
Every unprivileged trader attempting `Zap.sell`/`sellWithPermit` on any bonding-curve or post-graduation token — the only sanctioned path for exiting a position back to USDC — reverts unconditionally with `BelowMinAmount`, regardless of trade size. This permanently freezes traders' ability to redeem tokens for USDC through the protocol's intended exit mechanism. Since curve-stage tokens have no other sanctioned redemption path (curve liquidity lives in `Pair`/`Bonding`, gated behind `Zap`), this is a full, protocol-wide denial of the sell side, trapping trader funds in illiquid token/LT positions.

### Likelihood Explanation
This triggers on every single call to `Zap.sell`/`sellWithPermit` on a production deployment using real (6-decimal) USDC — no attacker action, special conditions, or privileged role is required. It is not a probabilistic or edge-case bug; it is a deterministic, always-on failure of the core sell path once the divisor's underlying decimals assumption is invalidated by the real asset's decimals.

### Recommendation
Do not hardcode a fixed `1e12` normalisation between the LT-estimate scale and `minUsdcAmount()`'s scale. Since `grossUsdcEstimate` is already computed with the same formula as `ltToBaseAmount` (which is guaranteed to match `mint`/`redeem`'s native `baseAmount` units), compare it directly against `minUsdcAmount()` without any additional scaling, or derive the correction factor dynamically from the actual USDC contract's `decimals()` (and, if truly needed for test purposes, from the LT's own decimal convention) rather than encoding a constant that is only valid for the test fixture's artificial 18-decimal mock.

### Proof of Concept
1. Deploy `Zap`/`Bonding` against the real (6-decimal) USDC token, mirroring production configuration (as opposed to the test suite's 18-decimal mock USDC).
2. Launch a token via `Zap.createToken` and have a trader buy tokens via `Zap.buy` with any realistic USDC amount (e.g., `$1000` = `1000e6`).
3. Trader calls `Zap.sell(tokenAddr, tokensOut, 0)`.
4. Inside `_sellInternal`, `grossUsdcEstimate` computes to a 6dp-scale value (e.g., on the order of `~1e9` raw units for a `$1000`-scale trade). Dividing by `1e12` yields `0`.
5. `0 < minUsdcAmount()` (non-zero, e.g. `10e6`) is true, so the call reverts with `BelowMinAmount` even though the trade is far above the real floor. This occurs for every possible sell size, since only trades yielding proceeds ≥ `$1,000,000` (raw ≥ `1e12` in 6dp units, i.e. `1e12 * 1e-6 = 1,000,000` USDC) would pass — an economically unreachable bar for ordinary curve trades — meaning `Zap.sell` is effectively permanently broken in production.
