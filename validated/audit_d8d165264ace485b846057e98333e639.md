No `MaxMessages` bound exists anywhere in `pallet-ismp`. This confirms the vulnerability: `handle_unsigned` accepts an arbitrarily large `Vec<Message>` while being charged a fixed, size-independent weight.

### Title
Unmetered Batch Processing in `pallet-ismp::handle_unsigned` Allows Weight-Bypassing Resource Exhaustion - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is a free, unsigned, permissionless extrinsic that accepts an unbounded `Vec<Message>` and charges it a constant, size-independent weight of `300_000_000` picoseconds regardless of how many messages, requests, or proofs the batch contains. This mirrors the root cause of CVE-2022-22971 (an unauthenticated/low-cost endpoint whose processing cost scales with attacker-controlled input while accounting/throttling does not), letting a relayer submit a single transaction whose declared cost is trivial but whose actual verification workload (membership proofs, request hashing, per-request module dispatch) is unbounded.

### Finding Description
`handle_unsigned` is declared with a static weight function that ignores the size of its input: [1](#0-0) 

```rust
#[pallet::weight(weight())]
#[pallet::call_index(0)]
#[frame_support::transactional]
pub fn handle_unsigned(
    origin: OriginFor<T>,
    messages: Vec<Message>,
) -> DispatchResultWithPostInfo {
    ensure_none(origin)?;
    Self::execute(messages.clone())?;
    Ok(().into())
}
```

`weight()` returns a fixed constant independent of `messages.len()`: [2](#0-1) 

The dispatchable returns `Ok(().into())`, which does not set `actual_weight` in the `PostDispatchInfo`, so Substrate's block-weight accounting (`frame_system::CheckWeight`) only ever charges the static `300_000_000` weight for this call — no matter how large `messages` is.

`Self::execute` then iterates the entire, unbounded `Vec<Message>` — for every message it performs full ISMP verification: membership/non-membership proof checks, `hash_request` over every request, and dispatch into the router's `IsmpModule::on_accept`/`on_response` callbacks for every request in every message: [3](#0-2) [4](#0-3) 

Because `messages: Vec<Message>` has no `BoundedVec`/`MaxMessages` cap anywhere in `pallet-ismp` (confirmed by search — no such bound exists), the only practical limit on batch size is the substrate extrinsic/block **length** limit, not weight. An attacker-relayer can therefore submit a transaction that is small enough to pass block-length limits but whose message count/complexity is far larger than the ~0.3ms of weight it is charged for.

Worse, this same unbounded computation is performed **for free, by every full node**, during mempool validation, since `validate_unsigned` calls the identical `Self::execute(messages.clone())` before a block is even produced: [5](#0-4) 

Any full node relaying/validating the extrinsic pays the real verification cost (proof checks, hashing, module dispatch) at pool-admission time, with no fee and no weight throttling — closely analogous to the Spring STOMP CVE where an authenticated-but-otherwise-unprivileged user could trigger unbounded server-side resource consumption through a "free" protocol path.

### Impact Explanation
This is a route-availability / denial-of-service class issue reachable by any unprivileged relayer submitting a single transaction:
- A crafted `handle_unsigned` call (or a burst of them) that under-reports its true computational weight can be included in blocks alongside other transactions whose weight estimates assumed the block had spare capacity, causing actual block-production/import time to blow past the expected budget — degrading or stalling block production and the message-delivery route for all Hyperbridge applications relying on that chain.
- Because the identical, unmetered `execute()` path also runs during `validate_unsigned` for every node that receives the transaction over the network, an attacker can force full nodes to perform expensive cryptographic/state-proof verification work for free, repeatedly, as the transaction propagates and is re-validated — a classic unbounded resource-consumption vector (CWE-770).

### Likelihood Explanation
`handle_unsigned` is intentionally permissionless and free (by design, to let relayers submit valid ISMP messages without fees), and there is no cap on `Vec<Message>` size or per-message complexity anywhere in `pallet-ismp`. Any relayer capable of assembling messages with real (or even resource-intensive-but-eventually-failing) proofs can trigger this without needing any privileged role, satisfying the "unprivileged message dispatcher/relayer" reachability bar.

### Recommendation
- Compute `handle_unsigned`'s weight as a function of `messages.len()` and the size/kind of each message (e.g., number of requests per message, proof size) rather than a flat constant, and set `actual_weight` in the returned `PostDispatchInfo` based on real work performed (via `total_weights`/`MessageWithWeight`, which is already computed in `execute` but currently discarded for block-weight-accounting purposes).
- Enforce an explicit, configurable maximum on the number of messages/requests per `handle_unsigned` call (`BoundedVec` or a runtime-configurable `MaxMessagesPerBatch`), rejected during `validate_unsigned` before any proof verification is attempted.
- Consider cheap fail-fast validation before expensive verification in `validate_unsigned` (e.g., pre-checking batch size and per-request key counts) as already done for the zstd decompression bomb, but applied to `pallet-ismp`'s own dispatchables.

### Proof of Concept
1. An attacker constructs a `RequestMessage`/`ResponseMessage`/`GetRequestsWithProof` batch (or a `Vec<Message>` with many such batches) containing a very large number of requests/keys, each backed by a valid but expensive-to-verify state proof (or a proof crafted to maximize hashing/dispatch work before failing).
2. The attacker submits this as a single `Ismp::handle_unsigned(messages)` unsigned extrinsic.
3. `validate_unsigned` (and later block execution, if included) fully executes `Pallet::<T>::execute(messages.clone())`, iterating every request, hashing it, verifying membership proofs, and invoking every destination module's callback — real work scaling with `messages.len()` and its nested `requests.len()`.
4. Despite this, the extrinsic is charged the fixed `weight()` of `300_000_000`, so block-weight accounting treats it as trivial, allowing it to be packed alongside other transactions whose combined actual execution time exceeds the intended per-block budget, and forcing every peer node to redo the same expensive validation for free during mempool propagation.
