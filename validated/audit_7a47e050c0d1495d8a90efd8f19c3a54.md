### Title
Webhook shop-domain identity spoofing due to HMAC covering only the request body, not the shop header - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw JSON body, then unconditionally trusts the `shop`/`shop-domain` value taken from an HTTP header that is *not* part of the signed material. Because the app's webhook secret (`api_secret_key`) is shared across every shop/tenant that installs the app, any shop can legitimately obtain a valid `(body, hmac)` pair for its own webhook traffic and then replay that exact pair to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to spoof a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` defines the bytes that are HMAC-verified as only the raw body: [1](#0-0) 

and separately exposes `shop` from an HTTP header that is never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes `HMAC-SHA256(secret, to_signable_string)` (body-only) and compares it against the received signature — the shop identity plays no role in this proof: [3](#0-2) 

`Registry.process` performs exactly one check — the body HMAC — and then immediately hands the *unauthenticated* `request.shop` value to the application handler as trusted tenant identity: [4](#0-3) 

The identity binding that should hold is:
`hmac_covers(shop) == true`

but the actual code enforces:
`hmac_covers(body) == true` while `shop` is read from an unauthenticated header — i.e. **bytes verified (body) ≠ bytes acted on for tenant identity (shop header)**.

Because Shopify signs webhooks for an app using the single `api_secret_key` shared by *all* shops that installed that app (not a per-shop secret), any shop is an "unprivileged internet user" relative to every other merchant tenant of the same app. Such an attacker can:
1. Install the target app on their own (attacker-controlled) shop — ordinary, unprivileged action.
2. Receive one or more real webhooks for their own shop, each with a valid `x-shopify-hmac-sha256` value computed over the body only.
3. Replay that exact `(body, hmac)` pair to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop's domain.
4. `Registry.process` validates the (unchanged) body HMAC successfully and invokes the handler with `shop: <attacker-chosen victim domain>`, `body: <attacker's own captured payload>`: [5](#0-4) 

Any host application that keys tenant-scoped logic off `WebhookMetadata#shop` (session lookup, data writes, deletion flows such as `shop/redact` or `app/uninstalled`, order/inventory sync, etc.) will process attacker-supplied content under a spoofed victim identity.

### Impact Explanation
This crosses a tenant boundary: an attacker who only has legitimate low-privilege access as one tenant (their own shop) can make the host application believe and act on data as if it originated from an arbitrary other tenant (victim shop). Depending on how the host app implements its webhook handlers, this can lead to cross-tenant data corruption, spoofed mandatory-compliance webhooks (e.g., forged `shop/redact`, `customers/redact`, or `app/uninstalled` causing unauthorized deletion/deactivation of a victim's data or session), or injection of attacker-controlled payloads processed under a victim shop's tenant context. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
The attack requires no credentials belonging to the victim or to the app owner. It only requires the ability to install the app as any shop (typically self-service for public apps) and to send an arbitrary HTTP request with attacker-controlled headers and a previously captured, legitimately-signed body — both trivial with standard HTTP tooling. The root cause is structural (HMAC never covers the shop identity), so it is reliably reproducible, not a corner case.

### Recommendation
- Do not treat `Webhooks::Request#shop` as authenticated tenant identity on its own. Cross-check it against data derived from a source that is bound to the signature (e.g., correlate `webhook_id`/`topic` against the app's own webhook subscription records fetched via an authenticated API call, or require the host app to independently verify the resource referenced in the body belongs to the claimed shop before trusting it).
- Document prominently in `Webhooks::Registry`/`Webhooks::Request` that `shop` is derived from an unauthenticated header and is not covered by the HMAC, so host applications must not use it as an unverified tenant key for privileged or destructive actions.
- Where feasible, provide (or recommend) an additional verification step, such as confirming the `shop` header value against a shop the app has an active session/access token for, and rejecting mismatches before invoking handlers.

### Proof of Concept
1. Attacker registers/installs the target app on their own store `attacker-shop.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Shopify delivers a real webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over BODY, using the app's shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id":1,"...attacker-controlled JSON..."}
   ```
3. Attacker captures this request, then resends it unmodified except the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC, unchanged>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id":1,"...attacker-controlled JSON..."}   <-- identical bytes, so HMAC still verifies
   ```
4. `HmacValidator.validate` succeeds because it only checks the (unchanged) body bytes against the (unchanged) hmac: [6](#0-5) 
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's forged body, as if `victim-shop` genuinely sent this webhook: [4](#0-3)
