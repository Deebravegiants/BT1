## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once the HMAC check passes, and then hands the caller-supplied `shop-domain` header straight to the app's webhook handler as the tenant identifier. The HMAC, however, is computed only over the raw request body — never over the shop domain header — so the "shop that produced a valid signature" and the "shop the handler is told the data belongs to" are two different, independently-controlled values.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor is read directly from an attacker-controllable HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) with no cross-check against the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately forwards `request.shop` to the app handler as the authoritative tenant identifier: [4](#0-3) 

Because the webhook HMAC secret (`Context.api_secret_key`) is a single shared per-app secret (not per-shop), any store that has installed the app can obtain a request with a cryptographically valid HMAC for *some* body. Since the `shop-domain` header sits outside the signed bytes, that same attacker can substitute an arbitrary victim shop domain in the header while keeping the (still-valid) HMAC over the body untouched, or replay/re-emit a body of their choosing together with a spoofed victim shop header, as long as the signature for the body matches. The library documentation explicitly claims that processing "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md`), which is misleading — it only verifies the body bytes, not the identity binding host apps rely on (`data.shop`) to route/persist per-tenant data.

This breaks the intended identity binding: `shop domain verified by HMAC` should equal `shop domain delivered to the handler`, but the gem only guarantees `HMAC(body) == valid`, and lets `shop` be anything the request-sender chooses.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged user who has merely installed the app on their own store (no special privilege, no leaked credentials) can cause the host application's webhook handler to process/attribute data as belonging to a different, victim shop domain, since `WebhookMetadata#shop` is trusted by host apps (as instructed in `docs/usage/webhooks.md`) to key their per-tenant persistence/session lookups. Depending on how the host app uses `data.shop` (e.g., to look up the session/access token for that shop, or to write data keyed by shop), this can lead to cross-tenant data corruption or being used as a stepping stone to act using another tenant's stored session — matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Any actor able to install the app on a shop they control (a standard, permissionless action for any Shopify merchant) already possesses a source of validly-HMAC-signed webhook bodies for their own shop's events. Swapping the `shop-domain` header on the HTTP request they send to the app's public webhook endpoint requires no cryptographic material beyond what a normal webhook delivery already contains, since the header is entirely outside the signed content. This makes the attack straightforward to mount against any app relying on the gem's documented "verified" claim.

### Recommendation
Bind the shop identity into the value that is actually authenticated, e.g. include the `shop-domain` header in `to_signable_string` (or otherwise cryptographically bind shop to body before computing/verifying the HMAC), and/or require callers of `Registry.process` to supply the expected shop (from their own trusted session/install record) and assert it matches `request.shop` before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`; Shopify sends a legitimate webhook to the app with a valid `x-shopify-hmac-sha256` for the raw body and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same raw body/HMAC pair to the app's webhook endpoint but rewrites the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` still returns `true`.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host app processes/attributes the (attacker-chosen) payload as belonging to `victim.myshopify.com`. [5](#0-4)
