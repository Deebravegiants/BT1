Confirmed root cause. The webhook HMAC signature covers only the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers and passed downstream unchecked.

### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature verified by `Utils::HmacValidator.validate` only covers `@raw_body` [1](#0-0) . This breaks the identity binding `shop_verified_by_hmac == shop_used_for_business_logic`, since the shop actually authenticated by the HMAC is "whatever body bytes were signed," not "whatever shop-domain header claims."

### Finding Description
`Registry.process` validates only the HMAC over the raw body and then trusts `request.shop`, `request.topic`, and `request.webhook_id` straight from headers to build `WebhookMetadata` handed to the app's handler [2](#0-1) . `Request#shop`, `#topic`, `#webhook_id`, `#api_version` read `shopify_header` values [3](#0-2) , none of which are part of `to_signable_string` (only `@raw_body` is signed) [1](#0-0) . `HmacValidator.validate` computes the signature purely from `to_signable_string` and the app secret, and compares it to the `hmac-sha256` header via `OpenSSL.secure_compare` [4](#0-3) ; it has no visibility into `shop-domain`, `topic`, or `webhook-id` at all.

Since a legitimate Shopify-generated webhook's HMAC is valid for any (`shop-domain`, `topic`, `webhook-id`) header combination as long as the body bytes match, an attacker who has captured one legitimate webhook delivery (e.g., from a shop they themselves installed the app on, or via any request logging/proxy they control) can replay the exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting a different `shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because it never inspected the header, and `Registry.process` will hand the forged `shop` value straight to the app's handler.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality the gem is supposed to enforce, `shop authenticated by HMAC == shop passed to the handler`, does not hold. A host application built on this gem's documented `WebhookMetadata.shop` (used, per the gem's own webhook framework, to key merchant data/sessions) can be made to process attacker-supplied body content under an arbitrary victim shop identity, e.g. injecting or corrupting data associated with a shop the attacker doesn't operate — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid (raw_body, hmac) pair, which is trivial to obtain by installing the app (even a free/dev install) on their own store and capturing their own genuine webhook delivery — no access token, `client_secret`, or privileged account is needed. The webhook HTTP endpoint is by design internet-reachable and unauthenticated aside from the HMAC check, so replaying the captured request with a swapped `shop-domain`/`topic`/`webhook-id` header is straightforward for any external actor.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise cryptographically tie `shop-domain`/`topic`/`webhook-id` to the verified request (e.g., include them in `to_signable_string`, or require the host app to cross-check `request.shop` against an independently-verified session/shop before trusting it for tenant-scoped operations). At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are not covered by the HMAC and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store and triggers/receives a legitimate webhook (e.g. `orders/create`), capturing the exact raw request body and the `X-Shopify-Hmac-Sha256` header value Shopify computed for it.
2. Attacker replays this exact body and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `@raw_body` only and it matches, returning `true`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body content, even though that body was never actually generated by Shopify for the victim shop.
