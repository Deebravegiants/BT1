Confirmed: `WebhookMetadata.shop` is a trusted field passed to every app's `WebhookHandler#handle` implementation, sourced directly from the unauthenticated `x-shopify-shop-domain` header, while `Utils::HmacValidator.validate` only signs/verifies `Webhooks::Request#to_signable_string` (the raw body).

### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then blindly forwards the unauthenticated `x-shopify-shop-domain` header as the `shop` identity to the app's handler. The binding the gem should enforce — "the shop the HMAC secret vouches for" == "the shop the handler is told the event belongs to" — is broken because the header is not part of the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as authenticating the entire request, then builds `WebhookMetadata` using `request.shop`, which is read straight from the `shop-domain` header without any cross-check against the signed bytes: [3](#0-2) [4](#0-3) 

Because the `shop-domain` header is excluded from the HMAC input, two different `x-shopify-shop-domain` values can be paired with the exact same `body` + `hmac-sha256` pair and both will pass `Utils::HmacValidator.validate`. The equality the gem is supposed to guarantee — `hmac_verified_shop == data.shop delivered to handler` — does not hold: the HMAC only proves "this body was signed with our secret for *some* shop event," not "this body belongs to the shop named in this header."

### Impact Explanation
Any party who can obtain one legitimately-signed webhook body/HMAC pair for a shop they control (trivial: install the app on a store they own and capture an outgoing webhook, or simply reuse a previously delivered webhook) can resend that identical body+HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming the event came from the victim shop. Any host application that uses `data.shop` (as the gem's own webhook_handler.rb documents as the identity field) to look up the target tenant/session and perform per-shop actions (e.g., writing order/customer data, revoking access, updating billing state) will act on the victim shop using attacker-supplied — but "verified" — data. This is a cross-tenant identity-confusion primitive rooted entirely in this gem's own webhook verification contract.

### Likelihood Explanation
No secret, token or privileged access is required beyond the ability to send an HTTP POST to the app's public webhook route and to have captured (or replayed) one valid, previously-delivered body/HMAC pair — something any user with their own shop installation of the app can obtain from webhooks addressed to their own tenant. The forged request differs from a legitimate one only in an HTTP header that the gem never authenticates.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable string, or independently verify `request.shop` against session/tenant state established outside of attacker-controlled headers, before handing `WebhookMetadata` to handlers. At minimum, document in `Webhooks::Request`/`Registry` that `shop` is unauthenticated and must not be trusted as a tenant key without an additional binding check.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs to the same app's public webhook endpoint with unchanged body `B` and header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `request.to_signable_string` (`= B`) — it succeeds because `B`/`H` are unchanged: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., an attacker-controlled `shop` value that the gem itself certified as HMAC-valid.
