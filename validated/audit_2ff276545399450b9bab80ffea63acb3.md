## Title
Cross-chain amount conversion silently mis-scales when local decimals exceed remote decimals in `pallet-hyper-fungible-token` — (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers, `convert_to_erc20` and `convert_to_balance`, assume the remote-chain (`erc_decimals`) precision is always greater than or equal to the local asset's (`decimals`) precision. They compute the scale factor with `erc_decimals.saturating_sub(local_decimals)`, which silently clamps to `0` — instead of reverting — whenever the local decimals are larger than the configured remote decimals. This is the same bug class as the reported Teller `getRequiredCollateral` issue: an amount-scaling formula that implicitly assumes a fixed sign for the decimal difference, and silently produces a wrong (over- or under-scaled) result instead of failing loudly when that assumption doesn't hold.

### Finding Description
`convert_to_erc20` (used in `send`) and `convert_to_balance` (used in `on_accept`/`on_timeout`) are defined as: [1](#0-0) 

Both only handle the case `erc_decimals >= local_decimals`. If the token's local decimals (`decimals`, from `T::Decimals` for the native asset or `Assets::decimals` for other assets) exceed the `Precisions` value registered for the destination/source chain (`erc_decimals`), `saturating_sub` returns `0`, so the multiply/divide factor becomes `10^0 = 1` — i.e., **no scaling is applied at all**.

In `send`, this path is: [2](#0-1) 

When `decimals > erc_decimals`, `erc20_amount` is not divided down to the destination's precision; the raw local-precision amount is dispatched as-is inside the `Message.amount` field, inflating it by `10^(decimals - erc_decimals)` in the destination contract's units.

The mirror bug exists in `on_accept`/`on_timeout`, which use `convert_to_balance` to translate an inbound ERC20 amount back to local precision: [3](#0-2) 

When local `decimals > erc_decimals`, the divisor collapses to `1`, so the amount is credited/minted at the *smaller* erc-decimal magnitude instead of being scaled up to local precision — silently under-crediting the beneficiary.

`Precisions` values are governance/`CreateOrigin`-configured per `(asset, chain)` pair via `register_token`/`update_token`: [4](#0-3) 

The pallet documentation nowhere requires `erc_decimals >= local_decimals`; the docs only state ERC6160 assets "should" use 18, which is a convention, not an enforced invariant. Any asset registered locally with decimals higher than the value configured for a given remote chain (e.g., a locally 18-decimal asset, or a mis-set/lower `Precisions` entry) trips this silent mis-scaling on every `send` and `on_accept` call for that asset/chain pair — reachable by any signed account calling `send`, and by delivery of any valid `on_accept` post request.

### Impact Explanation
- On `send`: the dispatched ERC20 `amount` is inflated by `10^(decimals - erc_decimals)`, causing the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract to mint or release far more tokens than were escrowed/burned on the source chain — an unbacked-mint condition that can drain the destination side's backing/escrow.
- On `on_accept`/`on_timeout`: the credited/minted local amount is deflated by the same factor, permanently reducing what a legitimate sender/beneficiary receives (loss of funds) once the affected precision configuration is used, silently rather than reverting.
- Because the arithmetic never reverts (it just multiplies/divides by 1 instead of erroring), the bug is undetectable at call time and manifests as either counterfeit minting on one side of the bridge or fund loss on the other — matching the "unbacked mint / permanent freezing-or-loss of funds" bar for Medium/High severity.

### Likelihood Explanation
Likelihood depends on the relationship between an asset's local decimals and its configured `Precisions` entry for a given remote chain. Given the pallet supports arbitrary local assets via `pallet-assets` (which permits any decimals value, including 18+ or higher than 18), and `Precisions` is set independently per chain by `CreateOrigin` without any enforced ordering, it is easy for a legitimately-configured asset (not requiring malicious governance) to fall into this branch — e.g., an 18-decimal local asset bridged to a chain whose registered contract precision is set to something lower, or any future high-decimal token. Once such a configuration exists, every ordinary user transaction via `send` (unprivileged, signed) triggers the mis-scaling automatically.

### Recommendation
Remove the reliance on `saturating_sub` silently clamping to zero. Explicitly branch on whether `erc_decimals >= local_decimals` or vice versa, and perform the correct multiply-or-divide in each direction (mirroring `VWAPOracle::_normalizeAmount`'s explicit `<`/`>=` branching), or reject/assert configurations where the scale relationship is inverted from what the helper assumes, so a misconfiguration reverts instead of silently mis-scaling funds.

### Proof of Concept
1. Register an asset via `register_token` with local `Assets::decimals` = 18 for some `local_id`, and set `Precisions::<T>::insert(local_id, dest_chain, 6)` (a plausible/legitimate low-decimal remote token).
2. A user calls `send` with `amount = 1_000_000_000_000_000_000` (1 token, 18 decimals).
3. In `send`, `decimals = 18`, `erc_decimals = 6`; `convert_to_erc20` computes `erc_decimals.saturating_sub(decimals) = 0`, so `erc20_amount = amount` unchanged = `1e18` instead of the intended `1e6` — a `1e12`-times inflation dispatched to the destination contract, which will mint/release `1e12` times too many tokens relative to what was escrowed/burned locally.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
