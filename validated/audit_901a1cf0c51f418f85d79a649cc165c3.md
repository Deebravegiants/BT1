### Title
Webhook `shop` field is trusted by handlers but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature over the raw request body only, but exposes `shop` (the `shopify-shop-domain`/`x-shopify-shop-domain` header) as a trusted, verified field to the webhook handler. The shop identity is never part of the signed material, so it can be freely set by anyone able to produce a body with a valid signature for their own shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it validates the body bytes, never the shop header: [3](#0-2) 

`Registry.process` calls this same validator and then forwards `request.shop` — the unauthenticated header — directly into `WebhookMetadata` as the shop identity passed to the app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no further verification, and the interface contract (`WebhookHandler#handle`) gives no indication to implementers that `shop` is unauthenticated: [5](#0-4) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop bytes verified by HMAC` ⧧ `shop bytes delivered to handler`

Concretely: an attacker who controls any shop that has installed the target app (trivial — anyone can install a public/dev app on their own store) receives genuine webhooks with a valid HMAC computed over a body of their choosing (they can trigger events with attacker-controlled body content, e.g. product/order fields). They then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop domain. `HmacValidator.validate` still passes (it only checks body bytes), and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-chosen `body`.

### Impact Explanation
Any app whose `WebhookHandler#handle` implementation uses `data.shop` to select which merchant's session/tenant record to update (the intended and documented use, since `Session#shop` is the tenant key throughout this library) can be made to write attacker-controlled webhook data into another tenant's context — a cross-tenant data-integrity/spoofing issue. This matches the "cross-tenant access" impact category: the gem's own webhook-processing API provides no authenticated binding between the payload and the shop it claims to originate from, so any host application that follows the library's documented `WebhookMetadata.shop` field can be tricked into cross-tenant behavior without any code defect on the host's side.

### Likelihood Explanation
Likelihood is High for any app accepting inbound webhooks from more than one merchant (i.e., any multi-tenant Shopify app, which is virtually all of them): the attacker only needs their own working app installation (a normal, unprivileged capability — no API key or `client_secret` needed) to obtain validly-signed webhook bodies, then simply swaps one HTTP header when POSTing to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic / webhook id) in the HMAC-signed material, or independently verify that the `shop` header matches a shop domain associated with a resource actually referenced inside the verified body (where feasible), before constructing `WebhookMetadata`. At minimum, document prominently in `WebhookHandler`/`WebhookMetadata` that `shop` is derived from an unauthenticated header and must be independently reconciled by host applications (e.g., against `topic`+ resource IDs in a known session store) before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with attacker-controlled order fields.
2. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed for that body.
3. Attacker replays the same body and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) returns `true` since it only checks the (unchanged) body bytes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to process attacker data under the victim's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
