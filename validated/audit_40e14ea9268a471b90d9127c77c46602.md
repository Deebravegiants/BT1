### Title
Unvalidated `shop` in `Oauth.validate_auth_callback` leaks `client_secret` to attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request destination directly from `auth_query.shop` without validating it against `Utils::ShopValidator`'s trusted-domain allow-list, unlike every other credential-issuing flow in this gem (`ClientCredentials`, `TokenExchange#migrate_to_expiring_token`). This lets the host that receives the app's `client_secret` and authorization `code` diverge from a Shopify-trusted domain.

### Finding Description
`validate_auth_callback` only checks that the HMAC on the incoming query is valid and that the `state` cookie matches [1](#0-0) . It never calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on `auth_query.shop`. That unvalidated value is used to build the `Session` used to derive the request host, and the token-exchange POST — containing `client_id`, `client_secret`, and the authorization `code` — is sent to `"https://#{shop}/admin"` via `Clients::HttpClient` / `auth_base_uri` [2](#0-1) [3](#0-2) .

Contrast this with the gem's other credential-issuing paths, which explicitly sanitize `shop` through `ShopValidator` (an allow-list of `shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, plus any configured custom domain) before using it as the request host: `ClientCredentials.client_credentials` [4](#0-3)  and `TokenExchange.migrate_to_expiring_token` [5](#0-4) . `TokenExchange.exchange_token` avoids the issue entirely by deriving the shop from a verified JWT `dest` claim rather than a raw query field [6](#0-5) . `validate_auth_callback` is the outlier: it trusts `auth_query.shop` as the destination host for a credentialed request without going through `ShopValidator`.

The binding that should hold is: *host that receives `client_secret`/`code` == a Shopify-trusted domain*. Instead the code enforces only: *host that receives `client_secret`/`code` == whatever `shop` value was present in the (HMAC-covered) callback query*. Because the query is HMAC-signed by Shopify's OAuth server rather than the app itself, this weaker binding is exploitable whenever an attacker can get Shopify to redirect with an attacker-controlled `shop` string (e.g., a shop using a custom/alternate domain configuration, or any value Shopify itself echoes back unmodified in the signed redirect), or whenever the host application forwards a callback whose `shop` field was not itself independently constrained — the gem provides no defense-in-depth here even though it does so everywhere else.

### Impact Explanation
If a request reaches `validate_auth_callback` with a `shop` value pointing to a non-Shopify host, the app's `client_id`, `client_secret`, and the OAuth authorization `code` are POSTed to that attacker-controlled server — a direct SSRF that exfiltrates the app's `client_secret` (Critical, per the exfiltration-of-`client_secret` impact category) and also hands the attacker the authorization code that they could otherwise redeem themselves.

### Likelihood Explanation
Every other credential-issuing code path in this same gem (`ClientCredentials`, `TokenExchange#migrate_to_expiring_token`) treats `shop` as untrusted input and funnels it through `ShopValidator` before using it as a request host — demonstrating that the gem authors recognize `shop` as attacker-influenced and requiring validation. `validate_auth_callback` is the sole exception, so the missing check is a concrete, local gem defect (an incomplete "identity binding" between the HMAC-signed callback and the token-exchange destination host) rather than a theoretical concern.

### Recommendation
In `lib/shopify_api/auth/oauth.rb#validate_auth_callback`, sanitize `auth_query.shop` through `Utils::ShopValidator.sanitize!` (as done in `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`) before constructing `null_session`/`auth_base_uri` and before using it in the `Session.from` call, raising `Errors::InvalidShopError` for any shop outside the trusted domain list.

### Proof of Concept
1. An attacker triggers/observes a legitimate Shopify OAuth redirect where the `shop` query parameter is not restricted to `*.myshopify.com` (e.g., via a custom-domain or proxied shop scenario), producing a callback query whose `hmac` is valid under the app's secret key but whose `shop` value resolves to a host the attacker controls.
2. The app calls `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)` with this query.
3. `Utils::HmacValidator.validate(auth_query)` succeeds (the signature only proves the query wasn't tampered with, not that `shop` is a trusted domain) [7](#0-6) .
4. `auth_base_uri(auth_query.shop)` builds `"https://<attacker-host>/admin"` and the gem POSTs `{client_id, client_secret, code, expiring}` to `https://<attacker-host>/admin/oauth/access_token` [2](#0-1) .
5. The attacker-controlled server receives the app's `client_secret` and authorization `code`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state
