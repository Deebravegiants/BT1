Found a concrete analog to the report's fee-on-transfer accounting mismatch, isolated to the relayer/transaction-fee (`order.fees`) path in `IntentGatewayV2.placeOrder`, unlike the input-token path which is already hardened.

### Title
Fee-on-transfer relayer fee token causes escrowed `TRANSACTION_FEES` accounting to exceed actual balance, permanently locking part of the escrow and reverting relayer/beneficiary fee redemption - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
In `placeOrder`, all order **input** tokens are measured by balance-before/balance-after diffing so fee-on-transfer input tokens are correctly accounted for (`evm/src/apps/IntentGatewayV2.sol:319-323`, confirmed by the dedicated `FeeOnTransferToken` tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2440-2686`). However, the **relayer/dispatch fee** (`order.fees`, the "protocol"-analog fee here) is collected with a raw `safeTransferFrom` for the exact requested amount and that exact, unadjusted amount is recorded into on-chain escrow accounting, with no balance check.

### Finding Description
`IntentGatewayV2.placeOrder` handles `order.fees` separately from the input-token loop: [1](#0-0) 

Unlike the input-asset loop just above it (which does `balBefore`/`balAfter` diffing, e.g. [2](#0-1) ), the fee path assumes `safeTransferFrom(msg.sender, address(this), order.fees)` delivers exactly `order.fees` tokens, and unconditionally writes that nominal amount into escrow:
`_orders[commitment][TRANSACTION_FEES] = order.fees;`

If `feeToken` (returned by `IDispatcher(hostAddr).feeToken()`) is, or is later upgraded/reconfigured to be, a fee-on-transfer token, the gateway contract actually receives less than `order.fees`. The escrow accounting (`_orders[commitment][TRANSACTION_FEES]`) is now inflated relative to the gateway's real token balance.

Later, on withdrawal/redemption, the exact same nominal amount is paid out using a low-level/`safeTransfer` call rather than a balance-checked amount, as seen in the equivalent redemption path in the Tron variant of this contract: [3](#0-2) 

Because every order created up to that point (and any order sharing the same fee token pool) was escrowed for the *nominal* fee, but the gateway's actual `feeToken` balance is short by the cumulative transfer-fee leakage, eventually a redemption for one order's `TRANSACTION_FEES` will attempt to transfer more tokens than the gateway actually holds, reverting that specific withdrawal (denial of the fee/beneficiary payout) and permanently freezing the corresponding escrow entry for both funds recovery and future redemption, exactly mirroring the referenced report's `withdrawableFees` desync/DoS pattern.

### Impact Explanation
This is a direct analog of the referenced Medium finding: the protocol's fee-tracking ledger (`_orders[commitment][TRANSACTION_FEES]`) can drift from the true on-chain balance of the fee token, causing (a) real loss of fee revenue proportional to the transfer-fee rate, and (b) a stuck/irredeemable escrow entry once the shortfall causes the fixed-amount transfer in `withdraw()` to revert — a permanent freezing-of-funds condition for the fee/beneficiary payout, reachable by any unprivileged user simply calling `placeOrder` with a fee-on-transfer-configured `feeToken`.

### Likelihood Explanation
Likelihood depends on the whitelisted/network-configured `feeToken` (from `IDispatcher.feeToken()`) becoming (or already being) a fee-on-transfer/rebasing token, which the referenced report explicitly calls out as a realistic upgrade path for ERC-20s over time (`weird-erc20` "fee-on-transfer" class). Since the gateway already treats this exact threat model as in-scope and mitigates it for the input-token path but not for `order.fees`, the omission is a genuine inconsistency in the codebase's own security model rather than a purely theoretical edge case.

### Recommendation
Apply the same balance-diff pattern used for input assets to the `order.fees` collection:
```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        ... // swap path unaffected (Uniswap output measured via `amounts[0]`)
    } else {
        uint256 balBefore = IERC20(feeToken).balanceOf(address(this));
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
        order.fees = IERC20(feeToken).balanceOf(address(this)) - balBefore;
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```
Additionally, redemption of `TRANSACTION_FEES` (and any other fixed-amount transfer path) should never revert the whole withdrawal on a shortfall — consider clamping to `min(amount, balanceOf(this))` or using balance-checked transfers, consistent with the sherlock report's `withdrawFees` recommendation.

### Proof of Concept
1. Configure/whitelist a `feeToken` in `IDispatcher` that charges, e.g., 1% on transfer (as modeled by the `FeeOnTransferToken` test helper at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2735`).
2. User calls `placeOrder` with `order.fees = 1000e18` and no `msg.value` (non-swap path).
3. `safeTransferFrom` delivers only 990e18 to the gateway, but `_orders[commitment][TRANSACTION_FEES]` is set to `1000e18`.
4. Repeat for multiple orders — the gateway's real `feeToken` balance is now systematically less than the sum of all `TRANSACTION_FEES` escrow entries.
5. When `withdraw()` is invoked to redeem a `TRANSACTION_FEES` entry (`evm/tron/contracts/apps/IntentGatewayV2.sol:716-721`), it attempts to transfer the full nominal `fees` amount; once the accumulated shortfall exceeds the gateway's spare balance, the transfer fails/reverts, freezing that order's fee payout permanently (and the escrow entry can never be zeroed since the code only decrements after `success`).
