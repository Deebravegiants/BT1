### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant impersonation via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `shop-domain` (and `topic`/`webhook-id`/`api-version`) header to identify which merchant/tenant the webhook belongs to. Because the signed bytes and the tenant-identifying bytes are disjoint, a valid `(body, hmac)` pair can be replayed with a substituted `shop` header and will still pass validation, letting an attacker make the host application process a payload as if it came from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines the signable payload as the raw body only: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers, which are attacker-controlled and never fed into the signature: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` as the tenant identity, handing it to the application's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no cryptographic binding to the verified bytes: [5](#0-4) 

This breaks the identity binding: `hmac-verified(body) == authenticated(shop)` is assumed by the library and by any host application relying on it, but in reality `hmac` verifies only `body`; `shop` (and `topic`/`webhook_id`/`api_version`) are unauthenticated. Before the request: an attacker observes/records one legitimate `(body, hmac)` pair delivered to the endpoint (e.g., from their own shop's webhook delivery logs in the Shopify Partner/Admin "recent deliveries" UI, which shows raw body and signature for their own installed app). After the request: the attacker resubmits the same `body` and `hmac` to the app's public webhook endpoint but with the `x-shopify-shop-domain` header changed to a victim/target shop domain (or any arbitrary tenant). `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, ...)`, causing the host application to act on data intended for a different tenant, attributed to a tenant of the attacker's choosing.

### Impact Explanation
This is a cross-tenant confusion in the shipped verification primitive: the gem's own `process` method certifies a header value (`shop`, the tenant key most host apps use to look up sessions/access tokens for that webhook) as authentic when it is not. Any application that relies on `ShopifyAPI::Webhooks::Registry.process`'s HMAC check as proof that the `shop` in the resulting `WebhookMetadata` is genuine is exposed to cross-tenant data processing/injection — e.g., writing data under the wrong shop's tenant, or triggering shop-scoped side effects (billing, redaction, fulfillment) attributed to an unintended shop. No `api_secret_key`, access token, or other privileged credential is required by the attacker — only a previously observed valid `(body, hmac)` pair for the app's own topic (obtainable via a legitimately-installed low-privilege dev/test shop).

### Likelihood Explanation
Moderate. The attacker must first obtain a genuine `(body, hmac)` pair for the app's webhook endpoint — achievable cheaply by installing the app on an attacker-controlled/free development store and inspecting webhook delivery details, or by observing one's own webhook traffic. Once obtained, replaying the pair with a modified `shop` header is trivial and requires no cryptographic secret. This is a design gap in the shipped `HmacValidator`/`Webhooks::Request` pairing rather than a one-off coding bug, so it is reliably reproducible.

### Recommendation
Bind the tenant-identifying and topic-identifying header values into the signed material that `HmacValidator` checks, or require the host application to cross-check `shop` against a value obtained through an independently authenticated channel (e.g., the shop associated with the session/access token used to register the webhook) before trusting `WebhookMetadata.shop`. At minimum, document prominently that `shop`, `topic`, `webhook_id`, and `api_version` returned by `Webhooks::Request`/`WebhookMetadata` are not covered by the HMAC and must not be used as an authoritative tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on an attacker-owned development store and lets Shopify deliver one legitimate webhook (e.g., `orders/create`), recording the raw `body` and the `x-shopify-hmac-sha256` value from the delivery log.
2. Attacker sends a new HTTP request to the app's public webhook endpoint with the identical `body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain` to `victim-shop.myshopify.com` (a shop the attacker does not control).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` — i.e., over `body` only — and matches, per [1](#0-0)  and [6](#0-5) .
4. `process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, per [7](#0-6) , even though the payload actually originated from the attacker's own shop — demonstrating that the HMAC check does not authenticate the `shop` field consumed by the application.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
