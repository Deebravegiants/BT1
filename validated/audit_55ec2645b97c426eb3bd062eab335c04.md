### Title
Webhook shop attribution bypass via unauthenticated `shop-domain` header not covered by HMAC — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the `shop-domain` HTTP header as trusted shop identity, but the HMAC signature that authenticates the webhook only covers the raw request body — never the header. Because the app-level `client_secret` (and therefore the webhook signing key) is shared across every shop that installs the app, any merchant can generate their own genuinely-signed webhook (body + valid HMAC) and then replay it against the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, producing a request that passes `HmacValidator.validate` while being falsely attributed to the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header with no relation to the signed payload: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `to_signable_string` (i.e. the body), never the shop header: [3](#0-2) 

`Registry.process` validates only that HMAC, then hands `request.shop` straight to the webhook handler as the tenant identity, with no cross-check that the header shop is the shop that actually produced the signed body: [4](#0-3) 

This breaks the intended binding `shop authenticated == shop the signed bytes belong to`. The HMAC only proves "this body was produced using the app's secret," not "this body belongs to shop X." Since the webhook signing secret (`Context.api_secret_key` / the app's `client_secret`) is identical for every installed shop, any malicious merchant can:
1. Install the app on their own store (unprivileged, self-service — no special credentials needed).
2. Trigger a real webhook (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`, `products/update`) addressed to their own shop, capturing the genuine `raw_body` and its valid `x-shopify-hmac-sha256`.
3. Replay that exact body + HMAC to the app's webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain.
4. `HmacValidator.validate` passes (the HMAC really was computed with the shared secret over that body), and `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: request.shop, ...)` set to the victim's domain.

### Impact Explanation
This is a cross-tenant confusion: an attacker with no privileges beyond installing the app on their own store can cause the app to execute shop-scoped webhook logic (session teardown on `app/uninstalled`, GDPR data deletion on `shop/redact`/`customers/redact`, inventory/catalog mutation triggers, etc.) attributed to an arbitrary victim shop domain, without ever compromising that shop's credentials. Depending on how the host app's handlers use `WebhookMetadata#shop`, this can lead to unauthorized deletion of another tenant's data or state corruption/DoS-by-uninstall for a shop the attacker doesn't control — a cross-tenant impact.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own shop (self-service, unprivileged) and control the HTTP headers of the request delivered to the app's webhook endpoint (trivial if the attacker controls where their own webhook traffic is forwarded, or via any request-tampering proxy in front of the shared webhook endpoint). No possession of the app's `client_secret` or another shop's credentials is required — only a genuinely-signed body from the attacker's own shop.

### Recommendation
Bind the shop domain into the signed material, or independently verify that `request.shop` corresponds to a shop your app has an active session/installation for and that the webhook actually originated from Shopify for that shop (e.g., include shop in the HMAC signable string if the platform supports it, or cross-validate via a server-to-server API call, or track per-shop webhook secrets/session state rather than trusting the header value directly).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers `app/uninstalled` (or any registered topic), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker POSTs to the app's webhook endpoint with headers:
   - `x-shopify-topic: <same topic>`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body: `B`
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC_SHA256(client_secret, B)`, which equals `H`, so validation succeeds.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to perform the topic's action against the victim shop's stored state.
