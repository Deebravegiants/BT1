### Title
Webhook HMAC validation does not bind `shop`/`topic` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes/compares the signature over `request.to_signable_string` — the raw request body only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values used to route and tag the event are pulled from the `X-Shopify-*` headers, which are never part of the signed content [2](#0-1) . The gem's own `VerifiableQuery` interface only requires `hmac` and `to_signable_string` [4](#0-3) , so nothing in `HmacValidator` or `Registry` enforces that the header-derived `shop`/`topic` match the entity the HMAC was actually issued for.

### Finding Description
The identity binding that should hold is:
`hmac_valid(raw_body) == true` should imply `shop_header == shop_that_shopify_actually_signed_this_payload_for`.

In this gem that equality does not hold, because the HMAC only covers `@raw_body` [1](#0-0)  and is verified with `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator.validate_signature`, using only `verifiable_query.to_signable_string` [5](#0-4) . The `shop`, `topic`, `api_version`, and `webhook_id` are read directly from headers with no cryptographic tie to the body or to each other [6](#0-5) .

`Registry.process` then trusts `request.topic` for handler dispatch and forwards `request.shop` directly into `WebhookMetadata` passed to the app's handler as the tenant identity [3](#0-2) , with no cross-check that this shop is the one Shopify actually generated the HMAC for.

### Impact Explanation
Any party who can obtain one genuine `(raw_body, hmac)` pair signed by the app's own `api_secret_key` — trivially available to any merchant who installs the app on their own store and receives one real webhook — can replay that exact body/HMAC pair to the app's shared webhook endpoint while substituting arbitrary `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will dispatch the forged shop/topic straight to the app's handler as if Shopify itself vouched for that shop and topic. This is a cross-tenant identity-confusion vector: the app's webhook handler will process/store data under an attacker-chosen shop domain, potentially corrupting per-tenant state, spoofing events (e.g. `app/uninstalled`, order/customer topics) for a victim shop, or triggering tenant-scoped side effects the attacker does not have legitimate access to.

### Likelihood Explanation
Any account holder capable of installing the app on a Shopify store (a normal, unprivileged action requiring no special credentials) can capture one legitimate `(body, hmac)` pair from their own webhook deliveries and replay it with forged headers against the app's public webhook endpoint. No access to `api_secret_key`, tokens, or victim credentials is required, matching the "unprivileged internet user" threat model in scope here.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or independently authenticate them, e.g., by requiring the host app to compare `request.shop` against the shop associated with the session/subscription that registered the webhook) rather than trusting header values whose integrity is not covered by `to_signable_string`. At minimum, `Registry.process` should validate that the resolved handler's expected shop/topic scope is consistent with an independently verified value before invoking application logic.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it register a webhook (e.g., `orders/create`).
2. Shopify delivers a real webhook to the app's shared endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's `api_secret_key`.
3. Attacker captures this raw body and HMAC header value.
4. Attacker (or any script) resends the identical body and HMAC header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
5. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged [7](#0-6) ; `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body [8](#0-7) .
6. `Registry.process` dispatches the forged event to the handler with `shop: "victim-shop.myshopify.com"`, causing the app to treat attacker-controlled data as authoritative for the victim tenant [9](#0-8) .
