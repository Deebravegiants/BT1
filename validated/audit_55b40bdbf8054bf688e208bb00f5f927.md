### Title
Webhook `shop-domain` (and other Shopify headers) are not covered by the HMAC digest, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields consumed downstream by `Registry.process` are taken from HTTP headers that are never part of the signed payload. This breaks the identity binding `HMAC(secret, raw_body) == received_hmac` ⇏ `shop_header == shop_that_generated(raw_body)`. An attacker who can obtain one genuinely-signed `(raw_body, hmac)` pair (trivially available to them by causing/observing any webhook event on any shop where the app is installed, e.g. their own dev/trial store) can replay that same body+hmac to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, since the HMAC never validates that header.

### Finding Description
The digest verified by `ShopifyAPI::Utils::HmacValidator.validate` is computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns solely the raw HTTP body: [2](#0-1) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic binding to that body: [3](#0-2) 

`Registry.process` validates only the HMAC (which covers the body) and then unconditionally trusts `request.shop`, `request.topic`, etc., forwarding them to the host application's handler as authenticated-looking metadata: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across all shops using the same app, and the HMAC only proves "this body was signed by Shopify for *some* event," it does not prove *which shop* that event belongs to. An attacker who has legitimate access to their own shop (installed the app) can trigger a webhook-eligible action, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair from their own publicly reachable webhook endpoint, and then re-POST that identical body+hmac to the target app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body`, never over the header, so `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the victim's domain while the body content is fully attacker-controlled (from their own shop's event).

### Impact Explanation
This is a cross-tenant identity-binding break: a value (`shop`) that is acted upon by the host application (e.g., to look up/update the correct shop's record, to decide multi-tenant data placement, to route redact/compliance requests) is presented to the handler as if it were authenticated, when in fact it was never covered by the signature. Any host application that trusts `WebhookMetadata#shop` to attribute the webhook body to the correct tenant (which is the documented, expected usage pattern of this field) can be tricked into writing/deleting/processing attacker-controlled data under a victim shop's identity — satisfying the "cross-tenant access" impact bucket, since the boundary broken is exactly `shop_header_verified_by_signature == shop_header_trusted_by_handler`.

### Likelihood Explanation
Exploitability requires only: (1) the attacker's own shop to have the app installed (a normal, unprivileged action any Shopify merchant/developer can do — installing your own app on your own dev store), (2) triggering any webhook-eligible event on that shop, and (3) capturing and replaying the body+HMAC header pair to the target endpoint with a modified shop header — no `api_secret_key`, stolen tokens, or privileged access are needed. This is a purely internet-reachable, unauthenticated-header manipulation.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values in the signed material that `to_signable_string` returns (or otherwise verify them out-of-band against a per-shop expectation before trusting them), so the HMAC binds the full authenticated context, not just the JSON body. Concretely, `Request#to_signable_string` should incorporate the Shopify-provided headers used to populate `WebhookMetadata`, mirroring how the referenced Story Protocol remediation folded the previously-uncovered contextual value (the StoryNFT contract address) into the signature digest.

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
