**Rationale:**

The premise that read timing could cause `Environment::new` to observe inconsistent `Features` state within a single execution does not hold given how the code is structured:

1. **Single environment per block, not per-transaction.** `AptosEnvironment::new_with_delayed_field_optimization_enabled` is invoked once at block-execution setup time via `AptosModuleCacheManager::try_lock_inner`, producing one `Environment` (and its `runtime_environment.vm_config().delayed_field_optimization_enabled` flag) that is passed by reference (`&RuntimeEnvironment`) to every transaction task (`execute`, `execute_v2`, `execute_txn_after_commit`) for the entire block. [1](#0-0) [2](#0-1) 

2. **Feature fetch and hash are computed atomically from one state view snapshot.** `Environment::new` fetches `Features` (and other configs) from a single `state_view` and folds the serialized bytes into a SHA3-256 `hash` used to detect environment changes across blocks; there is no per-transaction re-fetch that could observe a different value mid-block. [3](#0-2) [4](#0-3) 

3. **`try_enable_delayed_field_optimization` is deterministic given a fixed `Features` value**, simply flipping `vm_config.delayed_field_optimization_enabled` once, before any transaction in the block runs. [5](#0-4) 

4. **Aggregator/delayed-field resolution during merge/burn always goes through the same `TDelayedFieldView`/`MVHashMap` machinery** (`LatestView`, `versioned_delayed_fields`) driven by that single, block-wide `RuntimeEnvironment`, with explicit validation (`validate_and_commit_delayed_fields`, `record_change`) enforcing consistency; there's no code path where two different `delayed_field_optimization_enabled` states are consulted for the same resource within one block. [6](#0-5) 

Changing the underlying `Features` on-chain resource requires a governance/reconfiguration transaction (a privileged path explicitly excluded by the review scope), and even then the change only takes effect for the *next* block's freshly-constructed `Environment` — not mid-block, and not via any unprivileged transaction, view function, or bytecode input. No unprivileged entrypoint exists that can force two divergent `Environment`/feature readings to be applied concurrently over the same aggregator-backed state during a single mint/burn sequence, so there is no custody-boundary crossing here.

    fn validate_and_commit_delayed_fields(
        txn_idx: TxnIndex,
        versioned_cache: &MVHashMap<T::Key, T::Tag, ValueWithLayout<T::Value>, DelayedFieldID>,
        last_input_output: &TxnLastInputOutput<T, E::Output>,
    ) -> Result<bool, PanicError> {
        if last_input_output.is_speculative_failure(txn_idx) {
            return Ok(false);
        }
        let read_set = last_input_output
            .read_set(txn_idx)
            .ok_or_else(|| code_invariant_error("Read set must be recorded"))?;

        if !read_set.validate_delayed_field_reads(versioned_cache.delayed_fields(), txn_idx)? {
            return Ok(false);
        }

        let delayed_field_ids = last_input_output
            .delayed_field_keys(txn_idx)
            .ok_or_else(|| code_invariant_error("Delayed field keys must be recorded"))?;
        if let Err(e) = versioned_cache
            .delayed_fields()
            .try_commit(txn_idx, delayed_field_ids)
        {
            return match e {
                CommitError::ReExecutionNeeded(_) => Ok(false),
                CommitError::CodeInvariantError(msg) => Err(code_invariant_error(msg)),
            };
        }

        Ok(true)
    }
