### Title
Webhook HMAC only covers the raw body, allowing a captured webhook to be replayed with a forged `shop-domain`/`topic` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` HMAC-verifies exactly that string. The `shop`, `topic`, `webhook_id`, and `api_version` values that are subsequently trusted and handed to the app's webhook handler are read straight from HTTP headers that are never included in the signed material. This breaks the identity binding `HMAC-authenticated bytes == bytes acted upon`: the signature authenticates the body only, while the tenant-identifying `shop` field is accepted unauthenticated.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all pulled from headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC, then trusts `request.topic` and `request.shop` (both header-derived, unauthenticated) to route and label the payload for the handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the digest solely from `verifiable_query.to_signable_string`, which for `Request` is the raw body — never the `shop-domain` header: [4](#0-3) 

Consequence: any two webhook deliveries whose *bodies* are byte-identical will pass HMAC validation with the same signature regardless of which `shop-domain` header accompanies them. A user with their own legitimate app installation (an unprivileged internet user with respect to *other* merchants' tenants) can capture one authentic `(body, hmac)` pair from their own shop's webhook traffic and resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` (it never looks at the header), and `Registry.process` forwards `WebhookMetadata` labeled with the attacker-chosen `shop` to the app's handler, which will act on it as if it were a genuine event for the victim tenant.

### Impact Explanation
This crosses a tenant boundary without any of the victim's credentials: the `shop` identity field is entirely decoupled from the cryptographic authentication, so an attacker can inject data/events attributed to another merchant's shop into the app's webhook processing pipeline (cross-tenant access), satisfying the High/Critical "cross-tenant access" impact bar defined in scope.

### Likelihood Explanation
Requires only: (1) the attacker holds a valid app installation on some shop (any unprivileged merchant can install a public app), (2) they can observe/capture one authentic webhook delivery for their own shop (trivial, since apps typically log/receive them), and (3) they can send an HTTP POST to the app's webhook endpoint with a forged `shop-domain`/`x-shopify-shop-domain` header. No secret material is required — the exact byte-for-byte body/HMAC pair is reused verbatim. This is straightforward to execute for any topic where the body content doesn't inherently encode the correct shop (e.g., generic body shapes, or replaying the exact same body across shops for topics with shop-independent payload shapes).

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in the signed/verified material, or otherwise cryptographically bind them to the request before trusting them — e.g., verify the HMAC over a canonical string that concatenates the raw body with the `shop-domain` header, and reject requests where header-derived tenant identifiers are not covered by the signature.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers/observes a webhook delivery and records `raw_body` and the `x-shopify-hmac-sha256` header value (both valid/authentic for their own shop).
2. Attacker POSTs to the app's webhook endpoint with headers:
   - `x-shopify-topic`: same or attacker-controlled topic
   - `x-shopify-hmac-sha256`: the captured, valid HMAC value
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - body: the exact captured `raw_body`
3. `ShopifyAPI::Webhooks::Request.new` parses these headers/body successfully.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) and compares it to the attacker-supplied signature — it matches because the body is unchanged.
5. `handler.handle` receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process/attribute the event to the victim shop, even though the underlying signed bytes prove nothing about which shop originated the request.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
