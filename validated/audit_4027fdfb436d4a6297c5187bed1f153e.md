This confirms the vulnerability. The HMAC validation (`Utils::HmacValidator.validate`) only signs and verifies `request.to_signable_string`, which returns `@raw_body` [1](#0-0) . The `shop` value used downstream comes from the `x-shopify-shop-domain` header, which is never part of the signed content [2](#0-1) . `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's shared `Context.api_secret_key`/`old_api_secret_key`, with no binding to any header [3](#0-2) . `Registry.process` then trusts `request.shop` directly to build `WebhookMetadata`, which is passed to the host app's handler [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC signature, allowing replay with forged shop attribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` verifies the HMAC solely against that raw body. The `shop` value returned by `Request#shop` is read from the unauthenticated `x-shopify-shop-domain` header, which is never part of the signed content, so a validly-signed webhook body can be replayed with a swapped shop-domain header and still pass validation.

### Finding Description
The broken binding is: **shop authenticated by HMAC** (implicitly, the shop that legitimately received the body signed with the app's shared secret) **≠ shop acted on by the handler** (`request.shop`, taken from `x-shopify-shop-domain`).

Code path:
- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header` [2](#0-1) , [5](#0-4) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC header — the shop-domain header plays no role in this computation [3](#0-2) .
- `Registry.process` raises only if the HMAC check fails, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and calls `handler.handle(data: ...)`, trusting `request.shop` unconditionally [4](#0-3) .

Root cause: the HMAC secret (`Context.api_secret_key`) is a single shared secret for the whole app across all shops that install it — it is not shop-specific — and the gem does not bind the verified signature to a particular tenant identity in any header. An attacker who installs the app on their own shop (`attacker.myshopify.com`) legitimately receives real webhook deliveries signed with the exact same shared secret used for every other shop that installed the same app. They can capture one such delivery's raw body and valid HMAC header, then resend that identical body/HMAC pair to the target endpoint with `x-shopify-shop-domain: victim.myshopify.com` substituted. Since `to_signable_string` never includes the header, `HmacValidator.validate` still returns `true`, and `Registry.process` proceeds to invoke the host app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`.

No existing guard in this gem prevents this: `HmacValidator.validate` only checks body integrity/origin from the app secret, not shop binding [6](#0-5) ; there is no `ShopValidator`, session, or OAuth-derived shop check anywhere in `Registry.process`.

### Impact Explanation
If the host app's `WebhookHandler#handle` uses `WebhookMetadata#shop` to select which tenant's records to read/write/delete (the documented and intended usage pattern per `docs/usage/webhooks.md`), an attacker can cause the handler to mutate or query data attributed to an arbitrary victim shop domain — a cross-tenant data mutation using an attacker-controlled, unsigned header. This is repeatable against any victim shop domain (the attacker doesn't even need the victim to be a real installed shop, since nothing validates the shop is legitimate/installed) and requires only one legitimately-received webhook per topic to replay indefinitely. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions: attacker needs to install the target app on their own development shop (freely available, no special privilege) and register a webhook for a topic — entirely within the attacker capabilities described. Attacker cost is trivial (capture one real webhook delivery, replay with modified header). The severity depends on whether the host app trusts `WebhookMetadata#shop` for authorization/scoping of mutations without any additional shop-existence/session check — this is the documented intended use of the field, so it's realistic. Feasibility is high and fully reproducible offline with WebMock, without live shops or secrets, since the HMAC validation logic itself is the flaw, independent of any specific shop.

### Recommendation
Do not treat `x-shopify-shop-domain` as trusted merely because the body's HMAC is valid. At minimum: incorporate the shop-domain header into the signable content for the internal check, or independently verify the shop domain against the session/access-token records the app itself created during OAuth for that shop (matching by webhook_id/topic/shop combination known to the app), or use per-shop webhook secrets/registration records that bind `webhook_id` to a specific shop and reject if `request.shop` doesn't match the shop the app registered `webhook_id` for. Documentation should also make explicit that the raw-body HMAC alone does not vouch for the `shop-domain` header, since app secrets are shared across all installs.

```ruby
require "test_helper"

class WebhookShopDomainSpoofTest < Test
  def setup
    super
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", api_version: "2022-01",
      host_name: "app.example.com", scope: "read_products", is_private: false,
      is_embedded: true, session_storage: ShopifyAPI::Auth::FileSessionStorage.new
    )

      topic: "orders/create", delivery_method: :http, path: "webhooks",

    )
  end

  def test_replay_with_swapped_shop_domain_still_validates
    raw_body = '{"id":123}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", raw_body)
    )

    attacker_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "attacker.myshopify.com",
      }
    )
    assert ShopifyAPI::Utils::HmacValidator.validate(attacker_request)

    victim_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body, # identical body, identical hmac
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "victim.myshopify.com",
      }
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(victim_request)
    ShopifyAPI::Webhooks::Registry.process(victim_request)

    assert_equal "victim.myshopify.com", @spy_handler.last_metadata.shop
  end
end
```
