### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body, while the shop identity (`shop-domain` header) used downstream to attribute the webhook to a tenant is taken from an unauthenticated header that plays no part in the signature computation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from client-supplied HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC, then forwards the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`) straight into the handler as the trusted tenant identity for the event: [3](#0-2) 

`HmacValidator.validate` confirms only that `computed_signature = HMAC(api_secret_key, raw_body)` matches the received signature — it never incorporates the shop, topic, or webhook id into the signed material: [4](#0-3) 

This is the same bug class as the referenced report: a field the application acts on (`storedTotalAssets`/yield accounting in the analog; here, tenant identity `shop`) is not covered by the value that's cryptographically verified (`lastRewardAmount` release condition in the analog; here, the HMAC digest). The binding the code implicitly assumes but never enforces is:
`shop-domain header == shop bound inside the HMAC-signed payload`
but in reality the equality is:
`shop-domain header == arbitrary attacker-chosen value`, while `HMAC(api_secret_key, raw_body) == HMAC(api_secret_key, raw_body)` — the only equality actually checked.

### Impact Explanation
Because the `api_secret_key` is a single global app secret (not shop-specific), any actor who can obtain one valid `(raw_body, hmac)` pair — for example by installing the app on their own store and capturing a legitimate webhook delivery, since the merchant fully controls what reaches their own endpoint listener/logs — can replay that exact body to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes (it only checks the body), so `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a victim shop chosen by the attacker. Depending on how the host app's handler acts on `data.shop` (e.g. `shop/redact`, `customers/redact`, `customers/data_request`, or inventory/order sync handlers that write to a per-shop record keyed by `data.shop`), this enables cross-tenant data corruction or spoofed mandatory-compliance actions attributed to a shop that never sent the event. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only unauthenticated network access to the app's public webhook endpoint, plus one legitimate `(body, hmac)` sample obtainable by installing the app on any store (including the attacker's own trial store) — no leaked credentials, access tokens, or `api_secret_key` needed. The attack surface (webhook receiver) is public by design.

### Recommendation
Bind the shop identity cryptographically to the payload verification step: either require the host application to independently confirm the `shop-domain` header corresponds to a shop with a valid, previously stored offline session/access token before trusting `request.shop`, or extend `VerifiableQuery`/`to_signable_string` for webhooks to include the `shop`, `topic`, and `webhook_id` headers in the HMAC computation (matching how Shopify signs OAuth callback query params in `AuthQuery#to_signable_string`), rejecting requests where the header-derived identity is not part of the verified digest.

### Proof of Concept
1. Attacker installs the target app on their own development/trial store and registers any webhook topic (e.g. `orders/create`).
2. Shopify (or the attacker directly, since they control the store) delivers a webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(api_secret_key, B)`.
3. Attacker captures `(B, hmac)` and replays it directly to the app's public webhook endpoint, replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` recomputes the HMAC over `B` only, matches, and returns `true`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-199` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-controlled event data under the victim shop's identity.
