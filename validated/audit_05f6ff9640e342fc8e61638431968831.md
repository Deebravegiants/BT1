## Custody Analog Found

### Title
Signature-based `transfer_from` approval in the USDK stablecoin example can be replayed indefinitely because the nonce is bound to the *never-incremented* on-chain sequence number of the approving account - ([File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move])

### Summary
`usdk::transfer_from` implements an ERC20-`permit`-style "approve by signature" flow: the `from` account signs an off-chain `Approval` message (owner, spender, amount, nonce, chain_id) and any account (the `spender`) can later submit `transfer_from` to move `amount` out of `from`'s primary fungible store. The "nonce" used to prevent replay is `account::get_sequence_number(from)` [1](#0-0) . That sequence number is Aptos's transaction-replay counter, which is only incremented when `from` itself submits a transaction as the sender through the normal prologue/epilogue flow [2](#0-1) . `transfer_from` itself never touches or increments any nonce/sequence-number state for `from` — it only reads it for verification and then performs the withdrawal [3](#0-2) .

### Finding Description
The intended custody invariant of a signature-based approval is "one signed approval authorizes exactly one withdrawal of `amount`." `transfer_from` builds the challenge message with `nonce: account::get_sequence_number(from)` and calls `account::verify_signed_message` to check the signature [1](#0-0) . `account::verify_signed_message` performs pure signature verification and has no side effects on any stored state (no nonce table, no sequence-number bump) [4](#0-3) .

Since `from` is not the transaction sender in this flow (`spender` is), `from`'s account sequence number is completely independent of how many times `transfer_from` has been called against it. If `from` is a passive custody address that never submits its own transactions (a very common pattern for asset-holding accounts that only sign off-chain approvals, e.g. contract-controlled treasuries, cold-storage-style EOAs, or accounts whose only interaction with the chain is via this approval mechanism), its sequence number remains `0` (or otherwise static) forever. Consequently, a single signed `Approval` message for amount `X` can be submitted as `transfer_from` an unbounded number of times by the same `spender`, each one succeeding because the nonce check compares against the same unchanged sequence number every time.

This directly parallels the ERC4626 bug's root cause: a mismatch between the "authorization" bookkeeping unit and the "amount actually consumed" bookkeeping unit lets subsequent calls succeed/fail incorrectly. Here the analogous defect is worse — instead of blocking further calls, it fails open and permits unlimited replays, silently corrupting the "authorized once" custody invariant and moving value to the spender repeatedly instead of once.

### Impact Explanation
Any spender who has ever obtained one valid `Approval` signature and proof from an owner can drain that owner's entire USDK balance over time (as balance is replenished or simply by repeating whenever there is any positive balance), well beyond the amount the owner intended to authorize. This is a direct theft-of-fungible-asset custody violation: value moves to a holder (the spender) that the owner never re-authorized, and there is no recovery mechanism once funds are transferred out. Because `usdk` is a fungible-asset stablecoin reference module in `aptos-move/move-examples` that is expected to be deployed largely as-is by real projects, this is mainnet-relevant asset-custody code, not a test/mock.

### Likelihood Explanation
Exploitation requires only that the attacker (any spender who received one legitimate signed approval, e.g. via a dApp integration or payment flow) resubmit the exact same `proof`/`from`/`from_account_scheme`/`from_public_key`/`to`/`amount` parameters multiple times. No additional privilege, admin action, or race condition is needed — `transfer_from` is a `public` function callable by anyone holding the previously-issued proof, and nothing in the module or in `account::verify_signed_message` prevents replay when `from`'s sequence number is static. Likelihood is high whenever an owner account does not otherwise transact on-chain between approvals, which is a realistic and common operational pattern for asset-holding accounts.

### Recommendation
Do not reuse the account's transaction-replay `sequence_number` as the approval nonce. Maintain a dedicated, monotonically-incrementing (or one-time-use) nonce/allowance state inside the `usdk` module (e.g., a `Table<address, u64>` of used nonces or a per-owner allowance counter keyed by `(owner, spender)`), increment/consume it inside `transfer_from` itself before or after the transfer, and include that dedicated nonce in the signed `Approval` message instead of `account::get_sequence_number(from)`.

### Proof of Concept
1. Owner `A` (an account that never submits its own transactions on-chain, so `account::get_sequence_number(A) == 0` permanently) signs an `Approval { owner: A, to: B, nonce: 0, chain_id, spender: S, amount: 1000 }` and hands the resulting signature/proof to spender `S`.
2. `S` calls `usdk::transfer_from(S, proof, A, scheme, pubkey_A, B, 1000)`. The nonce check passes because `account::get_sequence_number(A) == 0` matches the signed nonce; 1000 USDK moves from `A` to `B` [5](#0-4) .
3. `S` calls `usdk::transfer_from` again with the *identical* arguments. `account::get_sequence_number(A)` is still `0` (unchanged, since `A` never submitted a transaction), so `verify_signed_message` succeeds again, and another 1000 USDK is withdrawn from `A`.
4. Repeat indefinitely — every call succeeds as long as `A` holds a balance, draining far beyond the originally authorized 1000 USDK.

    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,

        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }

    fun check_for_replay_protection_regular_txn(
        sender_address: address,
        gas_payer_address: address,
        txn_sequence_number: u64,
    ) {
        if (
            sender_address == gas_payer_address
                || account::exists_at(sender_address)
                || !features::sponsored_automatic_account_creation_enabled()
                || txn_sequence_number > 0
        ) {
            assert!(account::exists_at(sender_address), error::invalid_argument(PROLOGUE_EACCOUNT_DOES_NOT_EXIST));
            let account_sequence_number = account::get_sequence_number(sender_address);
            assert!(
                txn_sequence_number < (1u64 << 63),
                error::out_of_range(PROLOGUE_ESEQUENCE_NUMBER_TOO_BIG)
            );

            assert!(
                txn_sequence_number >= account_sequence_number,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_OLD)
            );

            assert!(
                txn_sequence_number == account_sequence_number,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_NEW)
            );
        } else {
            // In this case, the transaction is sponsored and the account does not exist, so ensure
            // the default values match.
            assert!(
                txn_sequence_number == 0,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_NEW)
            );
        };
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
