### Title
Emporium Min-proof path allows unauthenticated arbitrary calls draining Emporium-held funds with zero balance accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol, contracts/CircomDataBuilder.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a statement the attacker can trivially satisfy since they choose `messageSeed` themselves. Combined with `EmporiumUpgradeable.runAction`'s empty balance-accounting loop and `verifyWallet`'s early return when `stack.signerAddress == address(0)`, an attacker can submit an arbitrary `EmporiumStack` whose stateless op performs any external call (e.g., an ERC20 `transfer` or a LiFi router call) from the Emporium contract's identity, moving any tokens/ETH Emporium holds to themselves with no accounting check anywhere in the call path.

### Finding Description
The broken equality: **assets Emporium can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`**. This holds only if `circomData.erc20TokenAddresses` enumerates every asset the `stack.ops` calls can touch. The Min-proof path breaks this by construction.

Path:
1. `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` [1](#0-0) . When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it returns `formInputEmporiumMin`, whose only public inputs are `emporiumMessage`, `timeStamp`, `calldataHash` [2](#0-1) .
2. The corresponding circuit `MainEVMCircuitMin` only constrains `message == Poseidon(messageSeed)` [3](#0-2) . Since `messageSeed` is attacker-chosen, this proof carries no authentication weight — it does not bind any nullifier, root membership, or UTXO ownership.
3. Back in `Hinkal.transact`, because `circomData.erc20TokenAddresses.length == 0`, the outer balance-accounting loop that computes `balanceDif` and enforces `balanceDif == amountChanges[i] + utxoAmount` never executes [4](#0-3) .
4. `_externalTransact` calls `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)` with an empty `deltaAmountChanges` array [5](#0-4) .
5. `EmporiumUpgradeable.runAction` decodes the attacker-supplied `EmporiumStack` from `externalActionData.externalActionMetadata`, computes `balancesBefore`/`balancesAfter` over the same empty `erc20TokenAddresses` array, and calls `verifyWallet`, which returns immediately without any signature check when `stack.signerAddress == address(0)` (only recording `usedMessages[emporiumMessage] = true`) [6](#0-5) .
6. The op loop's stateless branch (`signerAddress == 0` or `!invokeWallet`) executes `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's identity, blocking only the `callHinkalWallet`/`doSendToRelay` selectors — any other call (e.g., `ERC20.transfer(attacker, emporiumBalance)`, or a call to a LiFi router with attacker-crafted calldata) is permitted [7](#0-6) .
7. Since `erc20TokenAddresses` is empty, the post-loop reconciliation (`balanceChange` computation, `BalanceChangeShouldBePositive` check, UTXO creation) never inspects the token actually drained [8](#0-7) .

`onlyAllowedRecipient` on `EmporiumUpgradeable.runAction` only checks `msg.sender == Hinkal contract` [9](#0-8)  — any unprivileged EOA calling `Hinkal.transact` satisfies this trivially, since Hinkal itself is the caller of `runAction`.

None of the standard guards stop this: `performHinkalChecks` only checks calldata-hash self-consistency and dimensions, not fund authorization [10](#0-9) ; `rootHashExists` just requires a publicly known valid historical Merkle root, trivially satisfiable; and `verifyProof`/`buildVerifierId` correctly verify the (vacuous) Min-circuit statement.

### Impact Explanation
Any unprivileged attacker can drain any ERC20 tokens or ETH held by the `EmporiumUpgradeable` contract (protocol fees, in-flight/leftover balances from other users' multi-step swap/deposit flows, or funds transiently routed through Emporium) to their own address, via an arbitrary call injected as an `EmporiumOperation`. This is direct theft of shielded/in-flight user or protocol funds, matching the Critical severity category, and is repeatable for every unique `emporiumMessage` value (trivial to generate) as long as Emporium holds any balance.

### Likelihood Explanation
No privileged role, whitelisted relay, or victim cooperation is required. The attacker needs only: (1) to call `Hinkal.transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, dimensions matching a registered Min-circuit verifier, and a self-chosen `messageSeed`/`emporiumMessage`; (2) to generate the trivial min-circuit proof themselves (no secret knowledge required); (3) Emporium must hold a non-zero balance of some asset at the time of the call (plausible given normal Emporium/swap flows that transiently route funds through it). This is low-cost and fully attacker-controlled.

### Recommendation
Remove or heavily restrict the unauthenticated `stack.signerAddress == address(0)` stateless path in `EmporiumUpgradeable.runAction`, or require that every asset an op can move be included and accounted in `erc20TokenAddresses`/`balancesBefore`/`balancesAfter` regardless of the Min-proof path. At minimum, disallow arbitrary `op.endpoint.call` when `signerAddress == address(0)`, and/or forbid `erc20TokenAddresses.length == 0` transactions from executing stateless ops that can call arbitrary token/router contracts holding Emporium balances.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, verifiers; register Emporium as allowed recipient and register a Min-circuit verifier for dimensions `(tokenNumber=0, nullifierAmount=0, outputAmount=0)` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`.
2. Fund `EmporiumUpgradeable` directly with `1000e18` of a test ERC20 (simulating leftover/in-flight balance).
3. Craft `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: testERC20, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))}], ...})`, `emporiumMessage` = attacker-chosen unused value, `calldataHash` computed to match.
4. Generate a valid Min-circuit proof locally using attacker-chosen `messageSeed` such that `Poseidon(messageSeed) == emporiumMessage`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker EOA.
6. Assert: `testERC20.balanceOf(attacker)` increases by `1000e18` and `testERC20.balanceOf(Emporium)` decreases by `1000e18`, while `balancesBefore == balancesAfter == []` inside `runAction` (both empty arrays, i.e., no accounting occurred) and the transaction does not revert — demonstrating assets moved (`1000e18`) != assets accounted (`0`).
