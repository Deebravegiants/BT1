### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that is computed **only over the raw request body**, but then uses the unauthenticated `shop-domain` (and `topic`/`webhook-id`) HTTP headers as the trusted tenant identity that gets handed to the app's webhook handler. Because the shop identity is never part of the signed material, any party who can produce one valid `(body, hmac)` pair can replay that body against the endpoint with an arbitrary `shop-domain` header and have the library report it as an authenticated webhook "from" a different shop.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable string as the raw body only: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers, which are attacker-controllable input on any public webhook endpoint: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC over `to_signable_string` (the body) only: [4](#0-3) 

`Registry.process` calls this validator and, once it passes, immediately forwards `request.shop` (and `request.topic`, `request.webhook_id`) — none of which were part of the signed bytes — to the app's handler as authenticated metadata: [5](#0-4) 

This is the same class of bug as the referenced Vault report: a value that is *acted upon as if verified* (the payout/claim amount there; the tenant identity here) is not actually covered by the binding mechanism that is supposed to guarantee its integrity (the accounting invariant there; the HMAC here). Concretely, the equality the code implicitly assumes is:

`hmac_valid(body) == shop_header_is_authentic`

but the real invariant computed is only:

`hmac_valid(body) == body_is_unmodified`

There is no cryptographic binding between the signed body and the `shop-domain` header at all.

### Impact Explanation
Any unprivileged internet user who can obtain a single legitimate `(raw_body, hmac)` pair — trivially available to anyone who installs the app on their own store and captures one real webhook delivery — can replay that exact body to the app's public webhook endpoint while substituting a different `shop-domain` header value. `HmacValidator.validate` will still return `true` (the body is untouched and the HMAC matches), and `Registry.process` will invoke the app's handler with `shop: <attacker-chosen shop>`. Any host application that relies on this gem's `request.shop`/`WebhookMetadata#shop` value to scope data access, look up per-tenant access tokens, or attribute the payload to a merchant will process attacker-controlled data under a victim shop's identity — a cross-tenant confusion/impersonation condition.

### Likelihood Explanation
Webhook endpoints are, by design, public and unauthenticated except for the HMAC, so the entry point is directly reachable by any internet user. Obtaining one valid signed body is straightforward (install the app on any store, since Shopify signs every real webhook body with the app's secret and delivers it to the registered endpoint) — no possession of `api_secret_key`, access tokens, or privileged accounts is required to mount this replay.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them (e.g., verify a full canonical string of headers+body, or independently validate the shop against session/installation state before dispatching to handlers). At minimum, document clearly that `request.shop` is unauthenticated header data and must not be trusted for tenant scoping without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop, `attacker-shop.myshopify.com`, and receives a real webhook delivery with a valid `X-Shopify-Hmac-Sha256` header for some raw JSON body `B`.
2. Attacker replays the exact same body `B` and the exact same `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: <any registered topic>`
3. `Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only and finds it matches (since `B` and the HMAC are unmodified) — see [6](#0-5) .
4. `Registry.process` proceeds to call the handler with `shop: "victim-shop.myshopify.com"` — see [5](#0-4) .
5. The host application's webhook handler now processes attacker-supplied data as if it originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
