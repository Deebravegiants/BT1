### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates covers only the raw request body, never the shop header. Any party who possesses one valid `(raw_body, hmac)` pair signed with the app's shared `client_secret` can replay it with an arbitrary shop-domain header and have it accepted as an authentic webhook for a different, unrelated tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`, and `Registry.process` treats HMAC success as proof the whole request is authentic: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; the `shop` accessor is read from a header that is completely outside the signed material: [2](#0-1) 

Because Shopify signs app webhooks with the app's single `client_secret` (the same secret is valid regardless of which installed shop generated the event), the HMAC only proves "this body was produced by Shopify for some shop using this app," not "this body belongs to shop X." The equality the code implicitly (and incorrectly) assumes is:

`hmac_valid(raw_body) == (shop_header is authentic for raw_body)`

but the real invariant that must hold is:

`shop_header == shop_that_the_signed_raw_body_actually_belongs_to`

Since `shop` is never included in `to_signable_string`, this invariant is never checked. `Registry.process` passes the attacker-controllable `request.shop` straight into `WebhookMetadata`, which is the only tenant-identifying field handed to the host application's handler: [3](#0-2) [4](#0-3) 

An unprivileged internet user who can install the app on their own (attacker-controlled) shop can capture a genuine, validly-signed webhook delivery — `(raw_body, hmac)` — for that shop, and then replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a victim shop. `HmacValidator.validate` still returns `true` because the header is not part of the signed string, so `Registry.process` will happily dispatch the (attacker-crafted-timing, but Shopify-signed) payload tagged as belonging to the victim shop.

### Impact Explanation
This breaks the tenant/shop binding that host applications rely on for cross-tenant data isolation. Any host app that keys its Shopify data updates (order/product/customer state changes, GDPR redact triggers, etc.) off `WebhookMetadata#shop` can be made to apply attacker-controlled webhook bodies to a victim shop's records — this is cross-tenant access/data injection, one of the Critical impact categories (cross-tenant access) explicitly in scope.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker's own development/test shop (something any unprivileged user with a Shopify Partner account can do for free), (2) capturing one legitimate webhook delivery to their own endpoint, and (3) replaying it with a different shop header value. No access token, `client_secret`, or privileged account for the victim shop is needed — the attacker only ever uses credentials belonging to their own shop's webhook delivery. This is a low-effort, repeatable network operation.

### Recommendation
Bind the shop domain into the signed material, or otherwise independently verify it, before trusting `request.shop`:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-covered signable string used by `Webhooks::Request#to_signable_string`, and require host apps validating against a per-shop record (offline access token / installed-shop list) to confirm the shop is actually installed and expected to receive that topic — analogous to the fix pattern in the report, which closes a gap where an action (auction completion / here, tenant attribution) is permitted without the necessary check being tied to the specific, verified entity.
- At minimum, document and enforce that host apps must cross-check `WebhookMetadata#shop` against their own list of currently-installed shops with a live session before acting on the payload, since the gem does not — and structurally cannot, given the current `to_signable_string` — verify that binding itself.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no privileged access needed).
2. Attacker triggers a webhook event for a subscribed topic (e.g. `orders/create`) on their own shop, capturing the raw POST body and its legitimate `x-shopify-hmac-sha256` header sent by Shopify.
3. Attacker resends the identical body and the identical, still-valid HMAC header to the same app endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header set successfully (only header *presence*, not content-shop binding, is checked) — [5](#0-4) .
5. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because the HMAC only ever covered `raw_body` — [6](#0-5) .
6. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, and acts on it as if it were a genuine event for the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
