### Title
Fraud detection is completely disabled (hardcoded to always pass), allowing fraudulent/duplicate signups to bypass anti-fraud enforcement - (File: `src/plans/fraud_check.rs`, `src/plans/mod.rs`)

### Summary
Analogous to the Pendle report where slippage-protection parameters were hardcoded to `0` (i.e., "accept anything"), `orb-core`'s fraud-check subsystem hardcodes the number of fraud checks to `0` and its detection routine to always return "no fraud," effectively disabling the entire anti-fraud enforcement path for every signup that reaches this code.

### Finding Description
`N_FRAUD_CHECKS` is hardcoded to `0` with the comment "we manually deleted all fraud checks," and every downstream method built on it becomes a no-op: [1](#0-0) 

`fraud_checks()`, `enabled_checks_from_config()`, and `feedback_messages()` all return empty arrays, so `fraud_detected()` and `fraud_detected_with_config()` can never report `true`: [2](#0-1) 

The `FraudChecks::run()` plan simply returns an empty `Report {}` unconditionally: [3](#0-2) 

The main signup orchestration in `MasterPlan::detect_fraud` explicitly documents this and always returns `Ok(false)` (no fraud) regardless of the biometric pipeline output, which then flows into `SignupReason::Normal` for the enrollment/PCP build path: [4](#0-3) [5](#0-4) 

This is the exact same bug class as the Pendle report: a security-critical parameter/enforcement path (there, `minAmountOut`/slippage bound; here, fraud/liveness-abuse detection) is hardcoded to a value that disables the protection entirely, rather than being computed from real signals or a configurable/enforced threshold.

### Impact Explanation
Because `detect_fraud` unconditionally returns `false`, no signup on this Orb build can ever be flagged as fraudulent by the on-device fraud engine, regardless of what the biometric pipeline (occlusion, contact lenses, multiple faces, underage, low image quality, etc. — all enumerated in `PipelineFailureFeedbackMessage`) actually observed: [6](#0-5) 
This allows fraudulent or abuse-pattern signups (e.g., attempts that should be flagged as `Underaged`, `MultipleFaces`, spoofing artifacts, etc.) to proceed to `enroll_user`/PCP construction as `SignupReason::Normal`, undermining the enrollment integrity guarantees that the fraud-check subsystem is meant to enforce, with impact on unauthorized/misattributed signups.

### Likelihood Explanation
This is not a probabilistic or hard-to-trigger bug — it is unconditional and deterministic on every single signup that reaches `detect_fraud`, requiring no special attacker capability beyond going through the normal, unprivileged signup flow.

### Recommendation
Restore real fraud-check rule evaluation (the `fraud-engine` crate already provides a generic `Pipeline`/`Rule` DSL usable for this) so `N_FRAUD_CHECKS`, `fraud_checks()`, and `detect_fraud` reflect actual pipeline signals instead of being hardcoded to values that disable detection. At minimum, gate this "all checks deleted" stub behind a clearly separated build feature that cannot be shipped to production Orbs, and add an explicit compile-time/runtime assertion preventing `N_FRAUD_CHECKS == 0` in production builds.

### Proof of Concept
1. Run any signup end-to-end on this build; regardless of biometric pipeline output (e.g., synthetic underage-classifier score, occlusion, multi-face detection), observe that `detect_fraud` in `src/plans/mod.rs` always returns `Ok(false)`.
2. Confirm `fraud_check::Report::fraud_detected()`/`fraud_detected_with_config()` can never return `true` since `fraud_checks()` always yields an empty array (`N_FRAUD_CHECKS = 0`).
3. Observe the signup proceeds with `SignupReason::Normal` and reaches `enroll_user`, i.e., the on-device fraud gate provides zero protection — analogous to a swap function whose `minAmountOut` is hardcoded to `0`.

impl Report {
    const DATADOG_TAGS: [&'static str; N_FRAUD_CHECKS] = [];

    fn fraud_checks(&self) -> [Option<bool>; N_FRAUD_CHECKS] {
        []
    }

    /// If fraud data are missing, we assume fraud is detected.
    fn fraud_checks_strict(&self) -> [bool; N_FRAUD_CHECKS] {
        self.fraud_checks().map(|v| v.unwrap_or(true))
    }

    fn enabled_checks_from_config(_config: &BackendConfig) -> [bool; N_FRAUD_CHECKS] {
        []
    }

    fn feedback_messages() -> [Option<PipelineFailureFeedbackMessage>; N_FRAUD_CHECKS] {
        []
    }

    /// Get the || result of all fraud checks, but under the Orb configuration.
    /// The end result might be different from the || of all fraud booleans as
    /// we might decide to not block a signup even if it's fraudulent.
    #[must_use]
    pub fn fraud_detected_with_config(
        &self,
        config: &BackendConfig,
    ) -> (bool, Vec<PipelineFailureFeedbackMessage>) {
        let enabled_checks = Self::enabled_checks_from_config(config);
        let fraud_results = self.fraud_checks_strict();
        let feedback_msgs = Self::feedback_messages();

        let feedback: Vec<PipelineFailureFeedbackMessage> = enabled_checks
            .iter()
            .zip(fraud_results.iter())
            .zip(feedback_msgs.iter())
            .filter_map(
                |((&enabled, &result), feedback_msg)| {
                    if enabled && result { feedback_msg.clone() } else { None }
                },
            )
            .collect();

        (!feedback.is_empty(), feedback)
    }

    /// If any fraud check fails or is missing data, fraud is reported.
    #[must_use]
    pub fn fraud_detected(&self) -> bool {
        self.fraud_checks_strict().iter().any(|&v| v)
    }
