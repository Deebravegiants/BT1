### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string as only the raw request body [4](#0-3) , while `shop`, `topic`, `api_version`, and `webhook_id` are all taken from unauthenticated HTTP headers [5](#0-4) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` as the tenant identity [6](#0-5) .

### Finding Description
The intended binding is: `hmac == HMAC(secret, shop || topic || body)`, i.e. the signature should cover every field the application trusts, including which shop the webhook is "from." Instead the actual binding implemented is `hmac == HMAC(secret, body)` — the `shop` header is verified against nothing [7](#0-6) .

Any entity capable of installing the app on their own store (an unprivileged internet user, since app installation itself requires no special privilege) will receive genuine Shopify webhooks addressed to their own shop, each with a valid HMAC signed by the app's `client_secret` over the raw body only. Because the header carrying `shop-domain` is excluded from the signable string, that attacker can replay the same raw body + HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g. a victim shop's domain). `HmacValidator.validate` will still pass because it only recomputes HMAC over `@raw_body` [8](#0-7) , and the forged `shop` is handed straight into `WebhookMetadata.shop` for the handler to trust [3](#0-2) .

### Impact Explanation
This is a tenant/identity-binding break analogous to the audited bug class (a field acted upon — here the `shop` used for tenant routing — is not covered by the authentication mechanism that is supposed to bind it). If the host application uses `WebhookMetadata#shop` to decide which merchant's local data/session to update (the intended and documented usage pattern), an attacker who legitimately installs the app on their own shop can inject webhook events that the app processes as belonging to a different, victim shop — a cross-tenant data-confusion vector.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop to obtain genuinely signed webhook deliveries (no elevated privilege, no leaked secret needed), and (2) sending a crafted HTTP request to the app's public webhook endpoint with the captured raw body/HMAC pair and a modified `shop` header. Both steps are within reach of an unprivileged internet user and require no interaction with `api_secret_key` material.

### Recommendation
Include `shop` (and ideally `topic`) in the HMAC-signable payload, e.g. by having `Request#to_signable_string` combine the shop/topic headers with the raw body in a canonical, unambiguous encoding, and re-verify these fields against the values embedded in/derived from the signed payload rather than trusting the bare headers.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; capture a genuine webhook delivery (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`).
2. Resend the request to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds [8](#0-7) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes body `B` as if it originated from `victim.myshopify.com` [6](#0-5) .
