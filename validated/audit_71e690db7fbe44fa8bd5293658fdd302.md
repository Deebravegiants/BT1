### Title
Accrued debt valuation overflows `i128` and permanently freezes a large market - (File: `common/src/rates/index.rs`)

### Summary
Interest accrual calculates total debt as `borrowed * borrow_index` in RAY using fallible fixed-point multiplication. A sufficiently large borrowed share total can reach the `i128` result ceiling before the borrow index reaches `MAX_BORROW_INDEX_RAY`, after which every operation that accrues the market panics with `MathOverflow`. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_supplier_rewards` computes both `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`. The index itself is capped only after `update_borrow_index` multiplies the old index by the interest factor, while the much larger `borrowed * index` valuation can overflow first. [3](#0-2) [4](#0-3) 

`Cache::load` loads the committed share total and index, and `global_sync` accrues every elapsed interval before the market mutation proceeds. Consequently, an overflow inside this accrual step reverts the entire transaction before a withdraw, repay, borrow, liquidation settlement, index update, recapitalization, or parameter update can alter the oversized book. [5](#0-4) [6](#0-5) [7](#0-6) 

An unprivileged user can build the prerequisite state through the controller's public `supply` and `borrow` entrypoints, subject only to collateral, liquidity, utilization, and configured caps. The user can later trigger the failure through the public index-update path or any market action that accrues first. [8](#0-7) [9](#0-8) 

### Impact Explanation
All suppliers' underlying in the affected hub market can become permanently inaccessible: withdrawals and debt repayments must pass through the same overflowing accrual path, so neither ordinary users nor liquidators can make progress once the threshold is crossed. Because administrative pool operations such as `update_params` and `update_indexes` also accrue before committing, they do not provide a reliable recovery path. [10](#0-9) [11](#0-10) 

The loss mechanism is permanent freezing of user funds and protocol insolvency processing failure rather than direct theft: cash remains in the pool, but its accounting operations repeatedly revert. [6](#0-5) [12](#0-11) 

### Likelihood Explanation
The attack requires a very large market: the scaled debt total and index product must exceed the RAY-domain `i128` ceiling, which implies hundreds of billions of token base units or equivalently extreme decimal-normalized balances. It also requires sustained high utilization long enough for index growth to make the debt valuation unrepresentable, so exploitation is capital- and market-condition-dependent rather than immediate. [4](#0-3) [13](#0-12) 

No privileged access, forged authorization, oracle manipulation, or malformed token behavior is needed; the attacker only uses public supply/borrow flows and later triggers ordinary accrual. [8](#0-7) [14](#0-13) 

### Recommendation
Make accrual total-value calculations saturating or explicitly bounded before `borrowed.mul(index)` can panic, and clamp the borrow index before evaluating the debt delta. In particular, compare `borrowed` and `index` against a precomputed product ceiling and cap the new index at the largest value that keeps `borrowed * index / RAY` representable, then continue accrual at that safe bound. [3](#0-2) [4](#0-3) 

The same bound should be applied consistently to `update_supply_index`'s `supplied * old_index` calculation, because supplier valuation has the same fixed-point overflow boundary. [15](#0-14) 

### Proof of Concept
1. Through `supply`, deposit an extremely large amount of a listed high-decimal asset into a spoke, creating account `A`.
2. Using sufficient collateral, call `borrow` to take nearly all available liquidity in that same market, producing a very large `borrowed` scaled balance.
3. Leave the market at high utilization until its borrow index has grown enough that `borrowed * new_borrow_index / RAY` exceeds `i128::MAX`.
4. Call the public controller `update_indexes` path or attempt `repay`, `withdraw`, or `liquidate`.
5. The transaction reaches `global_sync`, then `calculate_supplier_rewards`, and reverts in the `borrowed.mul(new_borrow_index)` valuation before any repayment or withdrawal state change can commit. Subsequent attempts repeat the same revert because the oversized shares and index remain committed. [6](#0-5) [4](#0-3) [16](#0-15)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }
