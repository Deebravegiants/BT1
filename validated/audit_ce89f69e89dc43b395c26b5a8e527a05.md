### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unsigned HTTP headers while the HMAC only covers the request body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC computed by `Utils::HmacValidator.validate` authenticates *only the JSON payload bytes*. The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` extracts and forwards to the app's handler come exclusively from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never included in the signed string. This breaks the identity binding `hmac_signed_bytes == bytes_the_app_acts_on`.

### Finding Description [1](#0-0) 
`hmac` is read from the `hmac-sha256` header, but `to_signable_string` returns only `@raw_body`. `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers via `shopify_header`, with no cryptographic tie to the signature. [2](#0-1) 
`Registry.process` validates the HMAC over the body only (`Utils::HmacValidator.validate(request)`), then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler using the *unsigned* header values as the tenant/topic identity.

Because the HMAC never covers `shop-domain`, `topic`, or `webhook-id`, any request carrying a body+HMAC pair that is valid for *some* topic/shop can be replayed to the same endpoint with the `shop-domain` and/or `topic` headers swapped for a different value, and `Utils::HmacValidator.validate` will still return `true` since it only recomputes the HMAC over the untouched body bytes. The equality the gem should enforce — "the shop/topic asserted to the handler == the shop/topic Shopify actually signed for" — does not hold.

### Impact Explanation
An unprivileged internet user who controls any shop that installs the app (e.g., a free development store) can trigger a real webhook delivery to the app's endpoint, capturing a body+HMAC pair that Shopify legitimately signed for their own shop/topic. They can then resend that exact body and HMAC to the same endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`) with an arbitrary victim shop domain or a different, more sensitive topic. `Registry.process` will accept it as valid (HMAC check passes) and hand the host application a `WebhookMetadata` claiming the data belongs to the victim shop/topic. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to update (a documented, expected usage pattern of this gem) will act on attacker-controlled webhook content under another merchant's identity — cross-tenant access/confusion, which meets the Critical impact bar in the rules.

### Likelihood Explanation
High. No secrets, access tokens, or privileged accounts are required — only the ability to receive one legitimate webhook (trivially obtained by installing the app on any shop, including the attacker's own free dev store) and replay it with a modified header to the public webhook endpoint. The gem itself performs no binding check between the signed bytes and the header-derived `shop`/`topic`, so nothing in this library prevents the substitution.

### Recommendation
Include the shop domain, topic, and webhook id in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. via a canonicalized header+body concatenation agreed with Shopify's signing scheme), so `Utils::HmacValidator.validate` fails whenever any of these fields is altered independently of the body.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the `shopify-hmac-sha256` header `H` that Shopify computed over `B`.
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `shopify-hmac-sha256: H`, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`, unchanged) and matches `H` — validation succeeds. [2](#0-1) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's body `B`, even though Shopify never signed anything for `victim-shop.myshopify.com`.
