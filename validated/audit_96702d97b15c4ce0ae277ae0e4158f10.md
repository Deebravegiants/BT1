### Title
Creator fee balances in FeeVault are permanently frozen if the creator's address is blacklisted by USDC - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` pays a creator's entire pooled `creatorBalance[msg.sender]` via `$.usdc.safeTransfer(msg.sender, amount)` with no ability to specify an alternate recipient. Since the vault's reserve asset is real USDC — a token with an issuer-controlled blacklist — any creator address that becomes blacklisted can never again receive its accrued balance, and there is no admin or self-service path to redirect or recover it.

### Finding Description
`claim()` zeroes `creatorBalance[msg.sender]` and `totalAccruedCreator` before calling `safeTransfer`: [1](#0-0) 

If `msg.sender` is blacklisted by USDC's issuer, `safeTransfer` reverts, the whole `claim()` call reverts, and the entire transaction (including the balance zeroing) is rolled back — so the funds are not lost from the ledger, but they are permanently unclaimable, because:
- `claim()` hard-codes the recipient as `msg.sender`; there is no `claim(address to)` variant.
- `Bonding.transferCreator(tokenAddress, newCreator)` only reassigns *future* fee attribution in `Bonding`'s `TokenInfo.creator` for a given token; it does not touch the already-accrued `FeeVault.creatorBalance` mapping, which is keyed by the old (now-blacklisted) address: [2](#0-1) 
- `FeeVault`'s only owner-controlled functions are `addDepositor`, `removeDepositor`, and `setFeeTo` — none can reassign or sweep a specific creator's stuck `creatorBalance`: [3](#0-2) 

This is the same root-cause class as the referenced report: a claim path that unconditionally pushes funds to a fixed, potentially-non-transfer-receiving address, with no fallback, causing a permanent freeze of otherwise-legitimate claimable funds. Here it manifests not via a batched multi-token loop (ClaimManager's bounty-token list) but via the single reserve asset used across the whole `FeeVault`/`Zap` fee-accrual pipeline, which the docs confirm is real USDC: [4](#0-3) 

### Impact Explanation
Any creator whose address is later blacklisted by Circle (sanctions, exploit association, false positive, etc.) permanently loses access to their already-accrued 0.25% creator fee share held in `FeeVault`, with no recovery mechanism — this is a permanent freeze of creator funds, satisfying the Medium/High bar for concrete, permanent loss of funds.

### Likelihood Explanation
USDC blacklisting of specific addresses is a documented, real-world occurrence (sanctioned addresses, exploiter addresses, etc.), and any active creator address accumulating fees over time is exposed to this risk without needing any attacker action — it is triggered by an external, out-of-protocol event rather than a privileged/administrative bug, but the protocol design provides zero mitigation once it happens.

### Recommendation
Add a rescue/redirect mechanism for stuck creator balances, e.g., allow the owner to reassign a specific `creatorBalance[oldCreator]` to a new address (similar in spirit to `transferCreator`, but applied to the already-accrued `FeeVault` balance), or add a `claim(address to)` variant that lets the creator designate a receiving address distinct from `msg.sender`, subject to appropriate access control (e.g., signed by the current creator).

### Proof of Concept
1. Creator `A` accrues fees over time via normal `Zap.buy`/`Zap.sell` activity; `FeeVault.creatorBalance(A)` grows.
2. USDC's issuer blacklists address `A` (independent, external event).
3. `A` calls `FeeVault.claim()`; `$.usdc.safeTransfer(A, amount)` reverts because `A` is blacklisted, reverting the whole call.
4. `A` calls `Bonding.transferCreator(token, B)` to redirect future accruals to `B`, but `FeeVault.creatorBalance(A)` — the already-accrued balance — remains keyed to `A` and is unreachable by `B` or anyone else; `A` can never call `claim()` successfully again.

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
