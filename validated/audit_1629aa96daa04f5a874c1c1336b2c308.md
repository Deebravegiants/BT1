## Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identity) used for webhook dispatch entirely from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. Any unprivileged party able to send requests to the app's public webhook endpoint can replay a legitimately-signed webhook body while substituting an arbitrary `shop-domain` header, causing the gem to attribute that webhook to a different (victim) tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `#shop` (the value used as the tenant identifier passed to the app's webhook handler) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC against `Utils::HmacValidator`, which only checks `to_signable_string` (the body) against `request.hmac`: [3](#0-2) [4](#0-3) 

Since the HMAC only authenticates the body bytes and never binds the `shop-domain` header, the equality the code implicitly (and incorrectly) assumes is:

`verified(hmac, raw_body) == trusted(shop_header)`

but the header is attacker-controlled and outside the signed scope, so this equality does not hold. An attacker who owns any shop where the target app is installed can capture a legitimately-signed webhook (body + `hmac-sha256` header) sent by Shopify to their own endpoint, then resend the identical body/HMAC pair to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never looks at the header, and `Registry.process` dispatches to the handler with `shop: request.shop` set to the forged victim domain: [5](#0-4) 

Any app logic keyed off `WebhookMetadata#shop` (e.g., updating stored merchant state, triggering per-shop side effects, or honoring `shop/redact`/`customers/redact` semantics) is then executed under the wrong tenant identity, using data that was never actually generated by or associated with that tenant.

### Impact Explanation
This breaks tenant isolation: an unprivileged actor with access to any single shop's legitimately-signed webhook traffic can cause the app to process webhook data under an arbitrary victim shop's identity — a cross-tenant confusion the gem's HMAC check is supposed to prevent. This matches the Critical "cross-tenant access" category, since the trust boundary between tenants is broken purely through the gem's own signature-verification logic, without requiring the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs at least one genuine signed webhook body+HMAC pair, which any unprivileged merchant/developer can obtain simply by installing the target app on a shop they control and letting Shopify send a normal webhook. Replaying that exact body with a modified header against the app's public webhook endpoint requires no secret material — only network access to the endpoint, which is public by design.

### Recommendation
Bind the shop identity into the material that is actually HMAC-verified, or otherwise authenticate the shop header against Shopify per-request rather than trusting it implicitly:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string`, matching what Shopify actually signs for the header set, or
- Cross-check the `shop` header value against the shop domain embedded in the parsed body's own identifying fields where available, or
- At minimum, document/require host applications to independently verify that the resolved `shop` corresponds to a shop with which they've completed OAuth, and reject webhooks for unknown/unassociated shops before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends.
2. Attacker replays that exact captured request to the app's public webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (the unmodified raw body) and it matches, since only the body was signed: [6](#0-5) 
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop == "victim.myshopify.com"`, even though the payload never originated from or pertained to that shop: [7](#0-6)
