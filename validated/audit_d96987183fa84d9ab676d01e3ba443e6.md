### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `ShopifyAPI::Utils::HmacValidator.validate` binds solely to the JSON body bytes. The `shop` value that `ShopifyAPI::Webhooks::Registry.process` hands to every app's `WebhookHandler` (as `WebhookMetadata#shop`) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed material at all.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — the `shop` (and `topic`, `webhook_id`, `api_version`) header values are never mixed into the signed string. `HmacValidator.validate` computes the signature purely over `to_signable_string` and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts any request whose body+hmac pair is valid, and then trusts `request.shop` (the header) as the tenant identity forwarded to the app's handler: [4](#0-3) 

This creates an equality break: the gem verifies `HMAC(secret, raw_body) == received_hmac`, but the identity binding the rest of the library and every downstream handler relies on is `shop_header == originating_shop`. Those are two different things. Any request carrying a raw body Shopify has genuinely signed for **some** shop (e.g., a webhook that was legitimately delivered to the attacker's own shop where the attacker also runs an app), can have its `shopify-shop-domain` header rewritten to any other shop domain and will still pass `HmacValidator.validate`, since the header is not part of the signed payload. `Registry.process` then dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
This is a tenant-identity boundary violation: the gem-documented contract is that `data.shop` in `WebhookHandler#handle` identifies which merchant the webhook body belongs to, and app code (per the gem's own docs) is expected to key persistence/business logic off it directly. Because `shop` is unauthenticated relative to the signature, an attacker who controls one legitimately-signed webhook (from their own installed app instance) can replay that body while claiming it belongs to a different, victim shop domain, causing the host application to attribute/store data under the wrong tenant — a cross-tenant contamination without needing the app's `client_secret` or any privileged credential.

### Likelihood Explanation
Exploitation only requires an attacker who can install the app on their own store (an unprivileged, ordinary flow) and can trigger any webhook topic they are subscribed to — the resulting HMAC over the body is valid and known to the attacker's environment. They then only need to replay the same POST to the app's webhook endpoint with the `shopify-shop-domain` header changed. No secret material is needed beyond what a normal merchant installation already exposes to the attacker (the webhook payload delivered to their own endpoint), because the signature never covered the header in the first place.

### Recommendation
Include the shop domain (and ideally topic, api_version, webhook_id) in the HMAC-signed material, or otherwise cryptographically bind the `shop` value to the verified payload, e.g. have `Request#to_signable_string` incorporate the shop header, or require host apps to independently look up/verify the shop against a stored, previously-authenticated session before trusting `WebhookMetadata#shop`. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked against the app's own installation registry before being used for tenant attribution.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a legitimately Shopify-signed webhook for topic "orders/create":
raw_body = '{"id":123,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# The attacker now crafts a new request re-using the SAME body+hmac, but swaps
# the shop-domain header to a victim's shop:
spoofed_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, not signed
  "shopify-webhook-id" => "any-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
# Utils::HmacValidator.validate(request) still returns true, since HMAC only covers raw_body.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled order data as if it belonged to victim-shop.
```
