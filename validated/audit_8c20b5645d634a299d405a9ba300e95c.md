### Title
`describeWithdrawal()` in HotBridge reports "failed" without checking already-completed on-chain delivery - (File: `packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts`)

### Summary
`HotBridge.describeWithdrawal()` short-circuits and returns a `"failed"` status the moment `getGaslessWithdrawStatus()` reports `HotWithdrawStatus.Canceled`, without ever consulting the bridge indexer (or HOT API fallback) to check whether the destination transfer had, in fact, already landed on-chain.

### Finding Description
In `describeWithdrawal()` [1](#0-0) , the code fetches the gasless withdraw status from the HOT contract/API and immediately returns:
```
if (status === HotWithdrawStatus.Canceled) {
    return { status: "failed", reason: "Withdrawal was cancelled" };
}
```
before reaching the bridge-indexer lookup that is otherwise treated as "the source of truth for destination hashes" [2](#0-1) .

For EVM/Stellar/TON destinations, the function's own comment states the bridge indexer — not the HOT gasless-status call — is the source of truth for whether funds actually reached the destination [3](#0-2) . Yet the `Canceled` early-return bypasses that authoritative check entirely: if the nonce is later marked `CANCELED` by the HOT relayer/contract (e.g. due to a race between execution and cancellation, a stale/side-channel cancellation, or the relayer flag lagging actual on-chain settlement), the SDK will report `failed` even in cases where the bridge indexer would show the transfer already `completed` with a valid destination `txHash`.

This breaks the equality that should hold: *the status reported by the SDK equals the actual on-chain settlement outcome*. Here, "failed" can be reported even though the destination transfer already executed and delivered funds.

### Impact Explanation
Consumers of `describeWithdrawal()` — including `watchWithdrawal()` [4](#0-3)  and `processWithdrawal()` [5](#0-4)  — treat `"failed"` as a terminal, actionable outcome (`WithdrawalFailedError` is thrown and propagated to the integrator). An integrator that receives this failure signal for a withdrawal that actually completed on-chain may re-issue/refund the withdrawal to the user, resulting in a double credit for a single underlying transfer — matching the High-impact class "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires the HOT gasless-withdraw status API/contract to report `CANCELED` for a nonce whose underlying transfer nonetheless settled on the destination chain (visible via the bridge indexer). This is a timing/consistency dependency on an external system rather than something the caller controls directly, so likelihood depends on how often HOT's cancellation flag can trail or contradict actual settlement — this could not be fully confirmed from the SDK code alone, since the semantics of `HotWithdrawStatus.Canceled` are defined externally by the HOT relayer/contract, not in this repository.

### Recommendation
Do not treat `HotWithdrawStatus.Canceled` as an unconditional terminal failure. Before returning `"failed"`, still query the bridge indexer (and HOT API fallback) for a destination hash for the given nonce; only return `"failed"` if no completed transfer is found there. This preserves the documented invariant that the bridge indexer is the source of truth for destination-chain settlement and prevents a stale/erroneous cancellation flag from masking an already-completed transfer.

### Proof of Concept
1. A withdrawal is submitted via `HotBridge`; the underlying HOT relayer executes the transfer and the bridge indexer eventually records a completed transfer with a valid destination `txHash` for the nonce.
2. Due to an out-of-band condition on the HOT side (e.g., a stale cancellation flag or a race between the "canceled" and "completed" state transitions), `getGaslessWithdrawStatus(nonce)` returns `HotWithdrawStatus.Canceled`.
3. `describeWithdrawal()` at [6](#0-5)  immediately returns `{ status: "failed", reason: "Withdrawal was cancelled" }` without ever calling `fetchWithdrawalHashBridgeIndexer()`.
4. The caller (e.g., `watchWithdrawal()`) throws `WithdrawalFailedError`, and an integrator built on top of the SDK treats the withdrawal as failed and reissues funds to the user — even though the original transfer already delivered funds on the destination chain, as the bridge indexer would have shown had it been checked.
