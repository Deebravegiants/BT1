### Title
HOT Bridge withdrawal status reports "completed" without checking `verified_withdraw` flag - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.fetchWithdrawalHashFromApi` parses the HOT API response with `HotApiWithdrawalSchema`, which includes a `verified_withdraw: boolean` field, but the method never reads or checks that field before returning the hash as a completed withdrawal. `describeWithdrawal` then reports `{ status: "completed", txHash }` to the caller purely because a `hash` string is present in the API response, regardless of whether HOT itself considers the withdrawal verified.

### Finding Description
`HotApiWithdrawalSchema` explicitly models `verified_withdraw` as part of each withdrawal record returned by the HOT API: [1](#0-0) 

However, in `fetchWithdrawalHashFromApi`, once the response is validated against the schema, the code only checks that a `hash` exists and is hex, then returns it — `verified_withdraw` is parsed but discarded: [2](#0-1) 

This hash flows directly into `describeWithdrawal`'s fallback branches, which report `{ status: "completed", txHash: ... }` to the caller as soon as `fetchWithdrawalHashFromApi` returns a non-null value: [3](#0-2) [4](#0-3) 

The existing test suite confirms the schema/field is present and parsed (`verified_withdraw: true` in the mock), but no test exercises `verified_withdraw: false` to prove the code branches differently — because it doesn't: [5](#0-4) 

The equality that should hold is: *status reported to the integrator == the actual on-chain verified outcome*. Since `verified_withdraw` is the field the HOT API exposes specifically to signal that the destination-chain transfer has been verified, ignoring it breaks that equality — a `hash` can be present (e.g., broadcast/pending/unverified tx) while `verified_withdraw` is `false`, yet the SDK still reports `"completed"`.

### Impact Explanation
An integrator or relayer that treats `describeWithdrawal`'s `"completed"` status as authoritative (per the documented contract that `failed`/`completed` mean "I checked, and this is the outcome" — see `WithdrawalStatus` docs) may release downstream funds, mark internal ledgers as settled, or stop retry/refund flows based on a hash that HOT has not actually verified as delivered. If the underlying destination-chain transaction associated with that hash later fails, reverts, or was never actually the finalized transfer, this results in the classic double-credit / premature-settlement scenario: the integrator credits the user based on an unverified status. [6](#0-5) 

### Likelihood Explanation
This path is reachable purely through the HOT API's own response content — the SDK's own fallback path (`fetchWithdrawalHashFromApi`) is used whenever the bridge indexer fails or the on-chain contract has not yet finalized status, which is a documented and tested fallback path, not a rare edge case: [7](#0-6) 
No malicious actor input is required; a normal HOT API response with a hash but `verified_withdraw: false` (e.g., a broadcast-but-not-yet-confirmed transaction) is enough to trigger the misreport.

### Recommendation
In `fetchWithdrawalHashFromApi`, require `withdrawal.verified_withdraw === true` in addition to a valid hex hash before returning the hash as verified/completed. If `verified_withdraw` is `false`, return `null` so `describeWithdrawal` continues to report `"pending"` until HOT confirms verification.

### Proof of Concept
1. Mock `hotSDK.api.requestApi` to return a withdrawal entry with `hash: "0xDEADBEEF"` but `verified_withdraw: false`.
2. Call `bridge.describeWithdrawal(wid)`.
3. Observe the result is `{ status: "completed", txHash: "0xDEADBEEF" }` — identical to the `verified_withdraw: true` case shown in the existing test at lines 687-720 of `hot-bridge.test.ts` — even though HOT has not verified the withdrawal. [2](#0-1)

/**
 * Represents the current state of a withdrawal as returned by bridge adapters.
 *
 * Error handling follows AWS SDK "describe" API patterns:
 * - **Thrown errors**: Infrastructure failures (network, auth, service unavailable).
 *   Meaning: "I couldn't check the status."
 * - **`failed` status**: Job-level failure reported by the bridge.
 *   Meaning: "I checked, and the withdrawal failed."
 *
 * @see https://docs.aws.amazon.com/AmazonS3/latest/userguide/batch-ops-job-status.html
 */
export type WithdrawalStatus =
	| { status: "pending" }
	| { status: "completed"; txHash: string | null }
	| { status: "failed"; reason: string };
