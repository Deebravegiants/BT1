This confirms the vulnerability: the docs explicitly promise that `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and the handler is told it can trust `data.shop` as "The shop domain of the webhook" [2](#0-1) , yet the HMAC only signs the raw body, not the shop header.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)` [3](#0-2) , but the `Request#to_signable_string` used for that signature is just the raw body: `@raw_body` [4](#0-3) . Meanwhile `request.shop`, `request.topic`, and `request.webhook_id` are read directly from HTTP headers with no cryptographic binding to that signature [5](#0-4) . These unverified values are then handed to the host application's handler as trusted identity fields via `WebhookMetadata` [6](#0-5) [7](#0-6) .

### Finding Description
This is the same bug class as the report: a signature/authorization check answers "valid" while a value that the application actually acts on lies outside what was authenticated — analogous to `secondsDebtDeltaX96` being computed uniformly while `secondsDebtX96`'s directional meaning (add vs. subtract) is what the protocol actually depends on. Here, `HmacValidator.validate(request) == true` only proves "`raw_body` bytes were HMAC-signed with `Context.api_secret_key`" [8](#0-7) . It does **not** prove "`shop-domain` header equals the merchant who produced this body." The identity binding the library implicitly promises — `hmac_valid(body) ⇒ shop_header == originating_shop` — does not hold, because `shop` is parsed straight from `@headers["shopify-shop-domain"]` without being part of `to_signable_string`.

Because Shopify signs every webhook with the **same** per-app `client_secret` regardless of which installed shop triggered it, any merchant who has installed the app can trigger a webhook for their own store (e.g., `orders/create`), capture the genuinely Shopify-signed `(raw_body, hmac)` pair, and then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `Shopify-Shop-Domain` header (e.g., a victim shop). `HmacValidator.validate` still returns `true`, since it only checks `raw_body` against the HMAC, and `Registry.process` proceeds to invoke the host handler with `shop: request.shop` set to the victim's domain [9](#0-8) .

### Impact Explanation
Per the docs, host applications are told the `shop` field is reliable and are shown patterns like `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [10](#0-9) . Any host app that keys tenant-scoped work (billing state, GDPR redaction records, inventory/order sync, per-shop cache invalidation) off `data.shop` as attested by this gem is exposed to cross-tenant data confusion/injection: an attacker-controlled webhook body gets attributed to a shop the attacker does not control, without needing that victim's access token, `api_secret_key`, or any other credential of the gem's host application — only their own (possibly free/trial) installation.

### Likelihood Explanation
The attacker only needs to be an unprivileged installer of the target app (a real but attacker-controlled tenant) — no leaked secrets, no MITM, no social engineering. The header spoofing itself is trivial (plain HTTP header value); the gem performs no defense against it because `Webhooks::Request#to_signable_string` never includes `shop`, `topic`, or `webhook_id` [4](#0-3) .

### Recommendation
Bind the shop (and ideally topic/webhook_id) to the signature check, e.g. by requiring/verifying the shop domain against the caller's registered/active sessions before trusting `request.shop`, or by including these header values in the HMAC-covered signable string if the delivery contract can be changed. At minimum, document and encourage host apps to cross-check `data.shop` against a known-installed-shop list rather than treating it as authenticated by `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers `orders/create` (a real order), receiving a genuine webhook POST from Shopify with body `raw_body` and header `Shopify-Hmac-Sha256: <valid hmac>` plus `Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the identical `raw_body` and `Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes the header to `Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the spoofed header [11](#0-10) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds since the body/HMAC pair is untouched [12](#0-11) .
5. The host handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, believing this data is authenticated as originating from the victim's store.
