## Title
Webhook shop-identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then uses `request.shop` — read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header — as the tenant identifier passed to the app's handler. The HMAC, however, is computed only over the raw body, never over the shop header, so the "verified" webhook and the shop it is attributed to are not cryptographically bound to each other.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from request headers with no relation to the signature: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then forwards `request.shop` to the app's handler as the authenticated tenant identity: [3](#0-2) 

Because the app's `api_secret_key` (the HMAC key) is the same for every merchant that installs the app, and the HMAC never covers the shop header, any body+HMAC pair that is valid for one shop is also a valid HMAC for the exact same body claimed to originate from a *different* shop. An attacker who legitimately installs the app on their own (attacker-controlled) shop can capture one of their own valid webhook deliveries (body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain`/`shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` (it only checks the body signature), and the handler is invoked with `WebhookMetadata` claiming the data belongs to the victim shop: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," reinforcing that host apps are expected to treat the `shop` field on `WebhookMetadata` as trustworthy once `process` succeeds, when in fact only the body's origin (knowledge of the shared app secret) is verified, not the shop attribution: [5](#0-4) 

This breaks the identity binding: `shop` (used by the handler as the tenant key) ≠ shop actually covered by the HMAC (none — the HMAC covers only the body, which is shop-agnostic).

### Impact Explanation
An unprivileged attacker (any developer who can install the app on their own store, which is the normal, unprivileged install flow) can cause the app to process attacker-supplied webhook payloads under the identity of an arbitrary victim shop domain. Depending on how the host app's handler uses `data.shop` (e.g., looking up the victim's stored session/access token to react to the event, writing attacker data into the victim's tenant records, or triggering downstream actions scoped to the victim), this yields cross-tenant data confusion/access driven entirely from the webhooks primitives this gem provides, satisfying the "cross-tenant access" criticality bar.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-owned shop (the standard, unprivileged app install flow) to receive one legitimate webhook delivery, and (2) replaying that captured body+HMAC to the app's public webhook endpoint with a forged shop header. No access to `api_secret_key`, tokens, or any privileged account is required.

### Recommendation
Do not trust the `shop` header as an authenticated identity signal from `Registry.process` alone. Either bind the shop domain into the HMAC computation (as Shopify's admin/OAuth HMAC does for `AuthQuery`), or require host apps to independently confirm that `data.shop` corresponds to a shop with an active, previously-established session/installation before acting on the payload, and clearly document that `WebhookMetadata#shop` is unauthenticated header data, not something verified by `HmacValidator`.

### Proof of Concept
1. Install the target app on an attacker-controlled dev shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate delivery: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`, independent of shop).
2. Replay to the app's webhook endpoint:
```
POST /callback/orders/create
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim.myshopify.com
x-shopify-webhook-id: <any>
x-shopify-api-version: 2024-01
Body: B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — matches, since `B` and `H` are unchanged. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed B, ...)`, even though the payload actually originated from `attacker.myshopify.com`. [6](#0-5)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
