### Title
Unbound `context` field in GET-response handling lets a relayer redirect an escrow refund to an arbitrary order and beneficiary — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The NATS advisory describes a restore operation where the identifier used for the permission check (the stream name a user is allowed to restore) is not the same identifier actually acted upon at execution time, letting an authorized-for-one-target operation act on a different target. The same authorization-target mismatch pattern exists in `IntentGatewayV2.onGetResponse`: the state proof verified by the ISMP host attests to a value at the storage keys embedded in `incoming.response.request` (i.e. whether *some* order was filled on the destination), while the entity that is actually mutated — which order's escrow is released and to which beneficiary — is taken from `incoming.response.request.context`, a field that is not cryptographically bound to the verified keys.

### Finding Description
```solidity
function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
    if (incoming.response.values[0].value.length != 0) revert Filled();
    WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
    withdraw(body, true);
}
``` [1](#0-0) 

`onlyHost` guarantees that `incoming` is a genuine ISMP `GetResponse` whose `values` were verified by the host against a state proof at `incoming.response.request.keys` — that is the *only* thing the ISMP proof machinery authenticates. `incoming.response.request.context`, however, is opaque payload attached to the original `GetRequest` by whoever dispatched it; it is never checked against `keys`, `from`, or any commitment recorded when the order was created. The handler:
1. Confirms the *queried key* returned an empty value (`Filled()` guard), then
2. Decodes an arbitrary `WithdrawalRequest` (containing `commitment`, `beneficiary`, `tokens`) straight out of `context`, and
3. Calls `withdraw(body, true)`, which pays out `_orders[body.commitment][token]` to `body.beneficiary`:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
``` [2](#0-1) 

The only guard on `body.commitment` is that it must correspond to an order with non-zero escrowed balance (`UnknownOrder`) — it does **not** have to be the order whose fill status was queried via `keys`. Since `request.keys` and `request.context` are two independent fields on the same `GetRequest`, and the ISMP proof only authenticates `keys`/`values`, an attacker can dispatch (or induce dispatch of) a `GetRequest` whose `keys` point at a storage slot they know/control to be empty (satisfying the `Filled()` check trivially), while setting `context` to `abi.encode(WithdrawalRequest{ commitment: <victim's real, active order commitment>, beneficiary: <attacker>, tokens: [...] })`. Once the empty-value response comes back and is delivered through `handleGetResponses`/`dispatchIncoming`, `onGetResponse` releases the victim order's real escrowed funds to the attacker — exactly the NATS pattern of "authorized to restore stream A, but the restore lands on stream B" because the checked identifier and the acted-upon identifier are decoupled.

### Impact Explanation
If exploitable, this is a direct theft-of-funds primitive against `IntentGatewayV2`'s escrow: any order with locked tokens/fees can be redirected to an attacker-chosen beneficiary as long as the attacker can get a `GetResponse` delivered whose `context` names that order but whose `keys` resolve to an empty value. This satisfies "concrete theft ... of funds" per the validation criteria, and is reachable from a single relayed GET response — no privileged role required, matching the report's unprivileged-dispatcher reachability requirement.

### Likelihood Explanation
Medium-to-High if, as the code shows, `context` is genuinely free-form and not derived/verified from `keys` or from the original order at dispatch time. The `Filled()` check only guards against re-processing an *already filled* order at the `keys` location, not against `context` naming an unrelated order. Exploitation requires being able to originate (or otherwise obtain) a `GetRequest`/`GetResponse` pair with attacker-controlled `context`, which is plausible since `context` is set at request-dispatch time by intent solvers/callers of the gateway.

### Recommendation
Bind `context` to the same order identity that `keys` proves against: derive `keys` deterministically from `body.commitment` (or vice versa — derive/validate `commitment` from `keys`) so the verified state and the acted-upon order can never diverge. At minimum, recompute the expected storage key for `body.commitment` inside `onGetResponse` and assert it equals `incoming.response.request.keys[0]` before calling `withdraw`.

### Proof of Concept
Conceptual (full request-dispatch side of `IntentGatewayV2.sol` was not fully inspected due to tool-call budget, so the exact call site that sets `context` is not confirmed with a line citation — this should be verified against the `fill`/order-placement code before treating this as confirmed exploitable):
1. Victim places an order, escrowing tokens under `commitment = C_victim`, `_orders[C_victim][token] > 0`.
2. Attacker dispatches (or crafts) a `GetRequest` whose `keys` point at a storage slot guaranteed empty (e.g., the fill-record slot for a bogus/never-filled commitment), and whose `context = abi.encode(WithdrawalRequest{ commitment: C_victim, beneficiary: attacker, tokens: victim's tokens })`.
3. Relayer/host delivers the resulting `GetResponse` (empty `values[0].value`) to `onGetResponse`.
4. `Filled()` check passes (queried key was empty); `withdraw` decodes `C_victim` from `context` and transfers `_orders[C_victim][token]` to `attacker`.

**Uncertainty note:** I was unable to review the code path that constructs the original `GetRequest.context` (the `fill`/dispatch functions in `IntentGatewayV2.sol`) within the available tool budget. It is possible additional binding exists there that ties `context` to `keys` that I did not see — this should be verified directly in the file before treating the finding as fully confirmed.
