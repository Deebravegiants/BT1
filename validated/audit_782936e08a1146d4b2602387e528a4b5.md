### Title
Draining an Aquarius pool below `min_pool_value_wad` bricks liquidation and bad-debt cleanup for any account holding that LP token - (contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The bug class in CVE-2025-50089 is an easily triggered denial of service. The analog in XOXNO Lending: every Aquarius LP price source carries a governance-set `min_pool_value_wad` floor, and `providers::aquarius::read` returns `OracleError::InsufficientAquariusLiquidity` when the pool's total value falls below it. Because required valuations fail closed (INV-ORACLE-01), a single unpriceable collateral leg aborts `liquidate`, `clean_bad_debt`, and `withdraw` for the whole account. An unprivileged attacker who is a liquidity provider in the underlying Aquarius pool can push the pool below the floor with an ordinary withdrawal — an own-trade on Aquarius, inside scope — and an unprivileged borrower can plant the fragile leg cheaply since `supply` performs no price check.

### Finding Description
`read` computes `pool_value_wad` from the LP fair price times total shares and rejects the observation when it is under `lp.min_pool_value_wad`. [1](#0-0)  The error propagates through `engine::resolve_nested`, so the controller's strict price read fails for that asset. Liquidation valuation and seizure planning need strict prices for every collateral leg, so one LP leg — even a dust amount — bricks the entire multi-leg plan. The codebase confirms both halves: the threat model states that for an Aquarius LP leg "liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`" and that "the same leg blocks bad-debt cleanup and force-socialization" (DoS.1). [2](#0-1)  Tests show the symmetric failure mode: a dust collateral leg on an unpriceable feed makes `try_liquidate` and `try_clean_bad_debt` revert while a twin account without the leg liquidates normally. [3](#0-2)  Mainnet LP listings carry floors of 1e5–1e6 USD WAD, so the floor is a real operational boundary, not a negligible edge. [4](#0-3) 

### Impact Explanation
While the floor breach persists: (a) every account holding the LP token as collateral is unliquidatable regardless of health factor, (b) `clean_bad_debt` reverts so insolvent accounts cannot be socialized, and (c) borrowers cannot withdraw. An attacker can open a leveraged borrow against LP collateral, drain the pool below the floor, and keep the borrowed assets while their underwater position is immune to liquidation and cleanup — interest accrues against suppliers with no recourse. This is temporary freezing of funds plus a direct path to protocol insolvency if the collateral's true value stays impaired or keeps falling.

### Likelihood Explanation
Medium. The attacker needs to control enough of the Aquarius pool's liquidity to push its measured value under `min_pool_value_wad` (or wait until organic exits bring it near the floor — the ops alert `LendingLpPoolValueNearFloor` exists precisely because this happens). Planting the leg costs only dust because `supply` requires no valid price. The attack is self-limiting in duration (restoring liquidity un-bricks the account) and requires an LP-token market to be listed as collateral, which the mainnet config shows is the case.

### Recommendation
Treat the LP floor breach as a partial-failure mode rather than a hard valuation failure for liquidation paths: e.g., value unpriceable collateral legs at zero for health-factor/seizure planning so the remaining legs can still be liquidated and bad debt cleaned, or allow `clean_bad_debt` to skip legs whose price resolution fails. Operationally, lower the floor or add a second non-LP source so LP withdrawals alone cannot silence the feed.

### Proof of Concept
1. Attacker supplies an Aquarius LP token (e.g. `XAUMUSDC_LP`, hub 3) as collateral to `account_id` 0 via `controller::supply` — no price needed.
2. Attacker borrows a liquid asset against it via `controller::borrow` up to the LTV limit.
3. On Aquarius, the attacker withdraws their liquidity from the LP's underlying pool until `price_wad * total_shares / share_unit < min_pool_value_wad`.
4. Any collateral decline or interest accrual pushes the account below HF 1. Every `liquidate` call now reverts with `InsufficientAquariusLiquidity` (error 235) because the strict price read fails; `clean_bad_debt` reverts identically since it also requires collateral valuation.
5. The attacker's debt stays on the books, interest compounds, and suppliers cannot be made whole until governance acts or the pool is refilled.
