Audit Report

## Title
Authenticated-but-unauthorized disclosure of sensitive runtime data via `/v2/debug/pprof/*` and `/debug/vars` endpoints - (File: core/web/router.go)

## Summary
The Chainlink node web server exposes Go's `net/http/pprof` profiling endpoints and the `expvar` debug endpoint behind generic session/token authentication only, with no per-role authorization check. Any authenticated account, including the lowest-privilege `UserRoleView` role, can pull heap dumps, goroutine stacks, CPU/execution traces, and runtime variable dumps that may contain sensitive in-memory data.

## Finding Description
`debugRoutes` registers `/debug/vars` guarded only by `auth.Authenticate(...)`, with no role check applied [1](#0-0) . `metricRoutes`, which registers the full set of pprof handlers (`/`, `/cmdline`, `/profile`, `/symbol`, `/trace`, `/allocs`, `/block`, `/goroutine`, `/heap`, `/mutex`, `/threadcreate`), is called from `v2Routes` on the already-authenticated `authv2` group without any `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper [6](#0-5) [2](#0-1) . This is inconsistent with every other sensitive route registered in the same `authv2` block, such as user management (`RequiresAdminRole`) and vault/forwarder operations (`RequiresEditRole`) [7](#0-6) [4](#0-3) . The role-check primitives exist and are actively used elsewhere in the file, confirming their omission here is a gap rather than an intentional design choice [5](#0-4) .

## Impact Explanation
`pprof`'s `/heap`, `/goroutine`, `/allocs`, and `/profile` outputs can leak in-memory secrets (API keys, keystore private keys, session tokens, decrypted config) and internal application state — CWE-200 Information Exposure with confidentiality impact. `/debug/vars` exposes internal counters/memstats useful for reconnaissance. Any `view`-role account (intended for read-only dashboard access) can reach these endpoints, violating the intended privilege boundary between `view`, `run`, `edit`, and `admin` roles.

## Likelihood Explanation
Exploitation requires only a valid low-privilege session or API token and a single HTTP GET — no timing, race, or additional conditions. This is realistic in any multi-operator deployment where accounts with different roles share a node. The RBAC regression test table (`routesRolesMap`) does not include `/v2/debug/pprof/*` or `/debug/vars`, indicating no automated test coverage currently catches this gap.

## Recommendation
Wrap `metricRoutes(authv2)` and the `/debug/vars` handler with an explicit role check (e.g., `auth.RequiresAdminRole`), consistent with other sensitive internal endpoints (user management, vault operations). Add corresponding entries to `routesRolesMap` in `auth_test.go` to prevent regression.

## Proof of Concept
1. As an admin, create a low-privilege user via `POST /v2/users` with role `view`.
2. Authenticate as that user via `POST /sessions` to obtain a session cookie.
3. Issue `GET /v2/debug/pprof/heap?debug=1` (or `/debug/pprof/goroutine?debug=2`, `/debug/vars`) using only the `view` session — no admin/edit role.
4. Observe HTTP 200 with a full heap/goroutine dump or `expvar` JSON returned despite the account holding only `view`-level privileges, confirming the missing authorization check in `core/web/router.go`.

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
