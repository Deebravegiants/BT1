### Title
Unsynchronized concurrent seed add/remove in `Wallet` module can silently drop newly added seeds, causing loss of wallet access - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#addSeed` and `Wallet#removeManySeeds` both perform an unsynchronized read-modify-write cycle on the same `extraSeeds` persisted list. Unlike `create`/`import`, which are wrapped in `makeConcurrent({ concurrency: 1 })`, these two methods have no concurrency guard, so two calls racing against each other can cause one write to silently clobber the other, permanently dropping a seed that the keychain believes is still active.

### Finding Description
`addSeed` reads the current extra seeds list, pushes the new seed, and persists the whole array back: [1](#0-0) 

`removeManySeeds` independently reads the current extra seeds list, computes a `remainingSeeds` array by filtering out the seeds to remove, and persists that array back: [2](#0-1) 

Both methods share the same `#getExtraSeeds` / `#setExtraSeeds` storage key (`EXTRA_SEEDS_KEY`) with a classic time-of-check-to-time-of-use pattern: read snapshot → mutate in memory → write back the whole snapshot: [3](#0-2) 

If `addSeed(seedB)` and `removeManySeeds([seedA])` are invoked concurrently while `extraSeeds = [seedA]`:
1. `addSeed` reads `[seedA]`, computes `[seedA, seedB]`, calls `#setExtraSeeds([seedA, seedB])`, then calls `this.#keychain.addSeed(seedB)` — seedB becomes usable in the in-memory keychain.
2. `removeManySeeds` reads the stale `[seedA]` (before or interleaved with step 1's write), computes `remainingSeeds = []`, and calls `#setExtraSeeds([])`.

If step 2's write lands after step 1's write, the persisted `extraSeeds` storage ends up `[]` — `seedB` is silently dropped from persistent storage even though it was just successfully added and is live in the in-memory keychain. This mirrors the reported Ditto bug class: a concurrently-added state update (the short order fill / here, the newly added seed) is lost because a deletion/rewrite path operates on a stale pre-update snapshot instead of verifying the current state before overwriting it.

The `wallet-accounts.ts` module explicitly documents awareness of this exact class of bug in `#replaceAll` (guarded with `makeConcurrent`) with the comment "may lead to concurrency issues... await yields execution and may allow .update(), .create(), etc to execute before fusion syncing is done", confirming the codebase is aware such races are dangerous, yet `Wallet#addSeed`/`removeManySeeds` lack the same protection: [4](#0-3) 

### Impact Explanation
On lock/unlock, only seeds present in the persisted `extraSeeds` list are re-added to the keychain: [5](#0-4) 

Because `seedB` was dropped from persisted `extraSeeds`, once the wallet is locked (e.g., app restart, timeout, or explicit lock), `seedB`'s key material is no longer restored on `unlock()`. Any wallet accounts derived from `seedB` become permanently inaccessible through the wallet's normal signing/derivation flow, which is a direct funds-access-loss condition analogous to the reported collateral loss — the user's asset (seed-backed private key access) exists momentarily but is silently discarded by a racing delete/rewrite operating on stale state.

### Likelihood Explanation
Both `addSeed` and `removeManySeeds` are user-triggered public API methods exposed by `@exodus/wallet` (used for multi-seed support). No special privileges are needed to trigger either — a normal user managing multiple seeds (e.g., adding a new imported seed while removing an old one from the UI, or via automated/scripted SDK usage, or two rapid taps) can trigger overlapping invocations. Since neither call is queued/serialized (`makeConcurrent`) like sibling methods `create`/`import` are, the race is reachable without any exotic timing control, though it does require genuine interleaving of two async calls, which JS event-loop scheduling around encrypted-storage I/O (`walletStorage.get`/`set`) makes plausible.

### Recommendation
Wrap `addSeed`, `removeManySeeds` (and ideally `updateSeed`) in the same `makeConcurrent({ concurrency: 1 })` guard already used for `create`/`import`, so that read-modify-write cycles on `extraSeeds` are serialized. Alternatively, implement `#setExtraSeeds` as an atomic compare-and-swap: re-read the current list immediately before writing and merge changes, or use an atom-based CAS/dedupe pattern similar to `#walletAccountsInternalAtom` combined with `#replaceAll`'s `makeConcurrent` protection.

### Proof of Concept
```js
// Pseudocode illustrating the race
const wallet = createWallet({ ...opts, config: { maxExtraSeeds: 5 } })
await wallet.create()
await wallet.unlock()

const seedAId = await wallet.addSeed({ mnemonic: mnemonicA })

// Fire concurrently without awaiting sequentially
const p1 = wallet.addSeed({ mnemonic: mnemonicB })      // reads extraSeeds=[A], writes [A,B]
const p2 = wallet.removeManySeeds([seedAId])             // reads extraSeeds=[A], writes []

await Promise.all([p1, p2])

// Depending on interleaving, persisted extraSeeds can end up as []
const extraSeeds = await seedStorage.namespace('wallet').get('extraSeeds')
console.log(extraSeeds) // seedB silently missing despite addSeed() having resolved successfully

await wallet.lock()
await wallet.unlock()

// seedB's key material is gone from keychain because it was never persisted
await expect(keychain.exportKey({ seedId: seedBId, keyId })).rejects.toThrow()
```

  removeManySeeds = async (seedIds) => {
    this.#assertMultiSeedSupport()
    await this.#assertWalletIsUnlocked()

    const primarySeedId = await this.#primarySeedIdAtom.get()
    if (seedIds.includes(primarySeedId)) {
      throw new Error('Cannot remove primary seed')
    }

    const extraSeeds = await this.#getExtraSeeds()
    const extraSeedsIds = new Map(
      await Promise.all(extraSeeds.map(async (seed) => [seed, await getSeedId(seed.seed)]))
    )

    const remainingSeeds = extraSeeds.filter((seed) => !seedIds.includes(extraSeedsIds.get(seed)))
    const seedsToRemove = extraSeeds.filter((seed) => seedIds.includes(extraSeedsIds.get(seed)))

    await this.#setExtraSeeds(remainingSeeds)
    this.#removeManySeedsMetadata(seedIds)
    await this.#keychain.removeSeeds(seedsToRemove.map((seed) => seed.seed))
