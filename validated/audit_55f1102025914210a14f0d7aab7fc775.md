### Title
Unallowlisted route pools inject token transfers into the caller's signed auth tree — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The shell-injection analog is instruction-stream injection into a privileged execution context: the controller's swap strategies accept attacker-supplied `swap_xdr` that names **arbitrary pool and token contract addresses**. The router invokes whatever pool contract the payload names, and code running inside that hop can issue `token.transfer(victim, attacker, x)` — which Soroban attaches as a child of the caller's own `require_auth` entry. When the victim signs the simulated auth tree (the normal wallet flow), the injected transfer executes, draining wallet balances far beyond the routed `amount_in`. Neither the payload `min_out` nor the controller's final risk gate bounds the loss.

### Finding Description
- `swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply` take caller-supplied `swap_xdr` and invoke the configured router, granting one exact input-transfer auth (`INV-STRAT-01`) — but the **router keeps no allowlist of the pool/token addresses the payload names** and calls them via `dispatch_hop` / `env.invoke_contract`. [1](#0-0) 
- The threat model confirms the exposure verbatim: "a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount." [2](#0-1) 
- The harness test proves reachability: `UnlistedPoolRouter::execute_strategy` calls the payload-named `hop_pool`, whose `swap()` performs `wallet_token.transfer(victim, attacker, amount)`; simulation records it under Alice's `swap_collateral` auth entry, and after signing, Alice's `77_770_000_000` wallet-token balance is fully stolen while the swap itself still settles fairly. [3](#0-2) [4](#0-3) 

This is structurally identical to the Akeneo shell injection: user-controlled data (route XDR `assets` registry → `hop_pool` address) reaches an execution primitive (`invoke_contract` under the caller's auth context) without a whitelist of permitted interpreters/targets.

### Impact Explanation
Critical — theft of user funds. A malicious route drains **any token in the caller's wallet**, unrelated to the listed assets or the `amount_in` routed. The attack scales to every user of `execute_strategy` directly and every controller strategy caller (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`), since all accept arbitrary `swap_xdr` and produce a single signed auth tree that honest simulation populates with the rogue child. The on-chain invariants (`INV-STRAT-01`, `INV-STRAT-02`) bound only the controller's own grant; they explicitly do not bound wallet loss. [5](#0-4) 

### Likelihood Explanation
High reachability, medium exploit friction. Any unprivileged attacker can deploy a rogue pool contract and craft a valid payload in one transaction. The friction is that the victim must sign the poisoned auth tree — the theft transfer appears as a sub-invocation — so exploitation depends on clients/wallets auto-signing simulated trees without inspecting children (the documented normal flow; mitigation is shifted entirely to off-chain client decoding). Pool and token addresses in the `assets` registry are decoded with only index/format checks (`Program::decode`), never validated against any whitelist. [6](#0-5) 

### Recommendation
Whitelist the pool/token addresses a route may invoke. The router should check each `hop.pool` (and LP `share_id` target) against a governance-managed venue-pool registry — or verify on-chain that the pool is a known deployment of an approved Wasm hash — before `dispatch_hop` calls it. Alternatively, isolate the caller's auth: perform venue hops under a sub-contract/callback so code inside a hop can never be recorded as a child of the caller's `require_auth` entry. At minimum, reject hops whose `token_in`/`token_out`/`pool` aren't registered protocol assets or verified venue pools.

### Proof of Concept
Executable proof already in-repo: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice holds 77,770,000,000 units of an unlisted `wallet_token` and 10,000 USDC supplied.
2. Attacker registers `RogueHopPool` with plan `(victim=Alice, token=wallet_token, to=attacker, amount=WALLET_BALANCE)` and crafts `swap_xdr` naming it as `hop_pool`. [7](#0-6) 
3. Alice calls `controller.swap_collateral(alice, account_id, USDC, 5_000, ETH, route)`. Simulation records `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child of her `swap_collateral` auth entry. [8](#0-7) 
4. Alice signs; the swap pays fair ETH output (final risk gates pass), and her entire `wallet_token` wallet balance moves to the attacker (`wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`). [9](#0-8)

```rust
            .instance()
```

```rust
    let s = Scene::new();
```

```markdown
### INV-STRAT-01 — Controller router authority binds one input transfer

The controller authorizes one exact
`token_in.transfer(controller, configured_router, amount_in)` invocation,
without sub-invocations. This grants invocation authority, without a token
allowance.

The controller ignores the router's return value, rejects input-balance growth
and rejects measured spending above `amount_in`.

<a id="inv-strat-02"></a>
<a id="inv-strat-02--strategy-settlement-is-measured-and-solvent"></a>

### INV-STRAT-02 — Account strategies settle measured flows and final risk

Distinct-token swaps require positive measured controller output. The current
swap's unspent controller-held input returns to the caller. Router-held residue
instead becomes admin revenue within the router's per-token limit; larger
residue reverts.

The router checks the route minimum against its output vault after fees and
before payout. This does not guarantee measured recipient receipt. The
controller independently checks positive output and final account risk,
without checking the payload minimum.

All six account strategies refresh listed supply LTV and apply final collateral
coverage, health and collateral-floor gates before persistence. Debt-free
accounts skip those three numerical gates. Cash flash loans settle separately;
ordinary supply and repayment do not universally apply that final account gate.
```
