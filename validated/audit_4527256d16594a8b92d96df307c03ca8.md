### Title
Direct LT donations to the curve Pair are permanently unreachable after graduation, with no owner or router recovery path - (File: packages/contracts/src/Router.sol, packages/contracts/src/Pair.sol)

### Summary
Any unprivileged wallet can `transfer` the reserve LT token directly to a token's bonding-curve `Pair` address before graduation. `Router.graduate` — the only function with `BONDING_ROLE` authority to move LT out of the `Pair` via `Pair.transferAsset` — drains only the explicitly computed `ltFromPair = assetReserve - virtualLtReserve` amount, not the pair's live LT balance. Once the token's lifecycle passes `Lifecycle.Curve` (i.e. after `_enterGraduating`/`finalizeGraduation`), `Bonding` never calls `Router.graduate` again for that token, and `Pair.transferAsset` is gated `onlyRouter` with `Router`'s only two callers (`sell` and `graduate`) both requiring `BONDING_ROLE`. This is analogous to the Cooler `delegate()` finding: an owner/permissionless-reachable balance sits in a contract with a privileged-gated withdraw surface, but the withdraw surface by design excludes exactly the donated excess, leaving it stuck forever.

### Finding Description
`_prepareGraduationLiquidity` computes `ltFromPair` from *stored* pair reserves (`getReserves()`), deliberately excluding any LT balance that arrived via a bare `IERC20.transfer` rather than through the AMM's `swap`/`mint` accounting: [4](#0-3) 

`Router.graduate(token, amount)` then transfers exactly that pinned `amount`, not `pair.assetBalance()`: [5](#0-4) 

The natspec on `Router.graduate` even documents this as a "trust-assumption claim, not an on-chain guarantee," explicitly stating the leftover LT is "unreachable as long as (a) `BONDING_ROLE` is not granted to any other address, and (b) future `Bonding` upgrades preserve the lifecycle gate" — i.e., the code authors acknowledge no recovery function exists: [6](#0-5) 

After `finalizeGraduation` moves the token to `Lifecycle.Graduated`, `Bonding` never again invokes `Router.graduate` for that token — the pair is retired and all future trading routes through the HyperSwap V2 pool via `Zap`. There is no `sweepLT`/`rescue` function on `Pair`, `Router`, or `Bonding` for the curve `Pair`'s leftover LT, unlike the LT-rescue mechanism (`_sweepLTToOwner`) that exists specifically for `Bonding`'s own balance during `finalizeGraduation`: [7](#0-6) 

### Impact Explanation
Any LT directly transferred to the `Pair` — whether by accident (a user confusing the `Pair` address with the LT/`Zap` deposit target) or intentionally (a donation, or a griefer wanting to waste funds) — becomes permanently locked. This is unbacked, unrecoverable value loss with no privileged or permissionless recovery mechanism anywhere in the contract set, matching the Cooler analog's "reward locked in contract forever" impact class. Given LT here represents real USDC-backed leveraged-token value, any amount donated to a `Pair` (pre- or post-graduation) is a permanent freeze of real funds.

### Likelihood Explanation
Reachable by any unrelated wallet with a single unprivileged `IERC20.transfer(pairAddress, amount)` call — no special permissions, no protocol interaction required, and the `Pair` address is publicly discoverable via `Factory.getPair`/`Bonding.getTokenInfo`. The documentation shows the team is aware of and has explicitly accepted this behavior as a design tradeoff ("trust assumption") for pre-graduation donations, but the same mechanism traps *any* LT sent to the pair, including post-graduation dust, with certainty and no time bound.

### Recommendation
Add a permissionless sweep function (analogous to `FeeVault.sweepDonations` or `Bonding._sweepLTToOwner`) that lets an owner-designated recipient claim `pair.assetBalance() - trackedReserve` from a `Pair` once it is confirmed `Graduated` (or otherwise no longer tradable), so that direct-transfer donations don't remain permanently stranded. Ensure this sweep cannot be invoked while the pair is still on `Lifecycle.Curve` to preserve the existing donation-resistance invariants for the graduation triggers.

### Proof of Concept
1. `Bonding.launch(...)` creates a token; its `Pair` address is read via `Bonding.getTokenInfo(token).pair`.
2. An unrelated wallet calls `IERC20(ltAddress).transfer(pairAddress, X)` — a direct donation, bypassing `Zap`/`Router` entirely.
3. Trading continues normally; buys/sells only ever move funds computed from `getReserves()`, never touching the donated `X`.
4. The token graduates: the threshold-crossing buy calls `_enterGraduating` → `_prepareGraduationLiquidity`, which computes `ltFromPair` strictly from stored reserves (excludes `X`), then `Router.graduate(token, ltFromPair)` drains only that amount.
5. `finalizeGraduation` moves the token to `Lifecycle.Graduated` and clears `pendingGraduation`; `Router.graduate` is never called again for this token.
6. `X` LT remains in `Pair` forever — `Pair.transferAsset` requires `onlyRouter`, and `Router`'s only paths to it (`sell`, `graduate`) both require `BONDING_ROLE` held solely by `Bonding`, which has no remaining call path to invoke either for a `Graduated` token's retired curve pair.

`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).

        uint256 keep

        IERC20(lt).safeTransfer(recipient, amount);
