## Finding

### Title
Webhook `shop-domain` (and `topic`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop` and `topic` values that the registry later trusts to route and process the webhook are taken from unauthenticated HTTP headers. This breaks the binding `shop verified-by-HMAC == shop acted-upon-by-handler`, letting anyone who possesses one valid `(body, hmac)` pair (e.g., from their own shop) replay it against the app's webhook endpoint while claiming an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop`/`request.topic` to route and execute the handler: [3](#0-2) 

Because the same `api_secret_key` is used for HMAC computation across all shops of a given app (there is no per-shop secret), a `(body, hmac)` pair that is valid for shop A's webhook is also a byte-for-byte valid HMAC for the exact same body claimed to originate from shop B — the signature says nothing about which shop or topic produced it. The equality the code implicitly assumes, `shop_verified_by_hmac == shop_delivered_to_handler`, does not hold: the left side does not exist at all, since `shop` is entirely outside the signed content.

### Impact Explanation
An unprivileged internet user who can install the target app on any shop they control (or otherwise capture one legitimate `(raw_body, x-shopify-hmac-sha256)` pair) can forge the `x-shopify-shop-domain` (and `x-shopify-topic`) headers to any victim shop domain and POST it directly to the app's public webhook endpoint. `HmacValidator.validate` will report success because it only checks the body against the same globally-known-format signature, and `Registry.process` will hand the attacker-chosen `shop`/`topic`/`body` combination to the app's registered handler as if it genuinely came from the victim's shop. Depending on the handler (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, order/product mutation handlers), this allows cross-tenant data injection or triggering of tenant-scoped actions (e.g. wiping/altering a victim shop's locally stored data) attributed to a shop the attacker does not control — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint and one legitimately-signed webhook body (trivially obtainable by installing the app on a free/dev shop, since Shopify sends real signed webhooks to any installed shop). No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the shop domain and topic (and ideally webhook ID) in the HMAC-covered signable string, or otherwise cryptographically bind them to the verified body (e.g., derive an HMAC over `shop + topic + body` instead of body alone), so `Utils::HmacValidator.validate` cannot succeed for a `(body, hmac)` pair claiming a different shop/topic than the one it was actually issued for. At minimum, document prominently that host applications must independently verify `WebhookMetadata#shop` against a shop they have on record before acting on webhook data.

### Proof of Concept
1. Install/enable the app on attacker-controlled shop `attacker.myshopify.com`; capture a real, Shopify-delivered webhook request, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-for-body>`.
2. Send a forged HTTP POST to the app's webhook endpoint using the same body and HMAC header, but replace:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any topic the app has a handler for)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (body/HMAC match, as demonstrated in [4](#0-3) ), then dispatches to the app's handler with `shop: "victim-shop.myshopify.com"`.
4. The app's handler executes tenant-scoped logic (e.g. deleting the victim's stored session/data on `app/uninstalled`) believing it originated from the victim shop.
