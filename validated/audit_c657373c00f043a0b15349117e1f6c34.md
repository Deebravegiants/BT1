### Title
Pool and controller permanently trap tokens received outside custody flows — no recovery or distribution path exists - (File: contracts/pool/src/cache/cash.rs)

### Summary
The reported bug class is "contract can hold an asset but exposes no function to move it out," leaving funds frozen in a non-upgradeable treasury. The XOXNO Lending analog is stronger: both the pool and the controller accept inbound token transfers (SAC `transfer` needs no receiver authorization), yet neither contract exports any sweep/rescue/distribution entrypoint. Any token balance that arrives outside a measured flow — a direct donation to the pool, or a residual/pre-existing balance on the controller — is permanently locked. The controller is explicitly designed to preserve such balances rather than recover them.

### Finding Description
`LiquidityPool`'s only outbound token primitive is `Cache::transfer_out`, which always moves `self.params.asset_id` — the market's own asset — and is only invoked on paths bounded by booked `cash` or position state (`borrow`, `withdraw`, `repay` refund, `recapitalize` refund, `flash_loan`, `create_strategy`, `claim_revenue`). There is no entrypoint that transfers an arbitrary token or the unbooked surplus. `cash` is a bookkeeping number that inbound flows credit on the controller's word, while direct transfers to the pool address never touch it: "Supply, repayment, and recapitalization credit the tokens actually received; direct donations do not automatically increase booked cash." `recapitalize` only applies the measured receipt up to the backing shortfall and refunds the excess to the payer in the same call — it cannot adopt a pre-existing surplus.

The controller has the same shape. `refund_controller_balance_delta` computes the balance increase since a snapshot and refunds only that delta, explicitly "preserving the pre-existing balance." Any balance the controller held before a flow — from a direct token transfer, an airdrop, or dust left by a fee-on-transfer leg — has no outbound path; no controller entrypoint sweeps it.

So a single unprivileged address can permanently freeze funds by calling `token.transfer(user -> pool, amount)` (or to the controller) with any SAC token, including a listed market asset. For the market asset the surplus is doubly stuck: it is above booked `cash`, and `flash_loan`'s strict-equality balance checks mean it can never be withdrawn as principal, fee, or revenue.

### Impact Explanation
Permanent freezing of funds: tokens transferred to the pool or controller outside a crediting flow are irrecoverable by anyone — not the sender, not governance, not the controller owner. Neither contract has a generic token-transfer or admin-sweep entrypoint; the pool's owner-gated functions all route through `transfer_out` bounded by internal accounting, and the controller's refund helper deliberately preserves pre-existing balances. For a listed market asset the frozen surplus also sits inside the same physical balance backing deposits, so it cannot even be socialized or claimed as revenue — `claim_revenue` pays only `min(cash, revenue)`.

### Likelihood Explanation
Reaching the trap requires only an ordinary SAC `transfer` to a contract address — fully unprivileged and irreversible on-chain. The probability driver is user/integrator error (sending to the pool instead of supplying through the controller) or stranded residuals (a token that delivers less/more than reported, balance snapshots in `snapshot_balances` that predate the flow). Each individual loss may be modest, so the finding sits at Medium/Low-Medium rather than High, matching the report's own severity band for a missing distribution path.

### Recommendation
Mirror the report's fix: add an explicit recovery path for unbooked balances rather than relying on "never send tokens directly." Concretely:

- Add an owner-gated (controller-routed, governance-timelocked) `sweep(token, recipient, amount)` on the pool that only permits amounts above what booked `cash` plus in-flight obligations require for the market asset, and arbitrary amounts for foreign tokens.
- Add the analogous recovery on the controller for its pre-existing balances, or document and enforce (via the strict-equality flash-loan check) that surplus balances are a known invariant break.

Until then, `refund_controller_balance_delta`'s "preserve the pre-existing balance" semantics guarantee those funds stay frozen.

### Proof of Concept
```rust
// Any address; no protocol entrypoint needed.
let token = token::StellarAssetClient::new(&env, &usdc_id);
token.mint(&user, &1_000_000);
token::Client::new(&env, &usdc_id)
    .transfer(&user, &pool_id, &1_000_000); // direct transfer to the pool

// Pool books cash == 0 for this market (or unchanged); the 1_000_000 is
// real balance with no matching shares. Enumerating LiquidityPoolInterface:
// borrow/withdraw/claim_revenue all bound by cash/shares; recapitalize
// credits only the *new* measured receipt up to the shortfall and refunds
// the rest in-call; flash_loan requires strict balance equality.
// No entrypoint moves the surplus — the 1_000_000 is permanently locked.
```

pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
}
