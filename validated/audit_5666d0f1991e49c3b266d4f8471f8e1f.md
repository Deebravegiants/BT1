### Title
Webhook shop attribution (`WebhookMetadata.shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts an unauthenticated HTTP header (`X-Shopify-Shop-Domain`) to attribute the webhook to a tenant. Because the shop identifier is never part of the signed material, an attacker who possesses one valid `(body, hmac)` pair (e.g. from a webhook sent to their own store, which they legitimately control) can replay it against the app's webhook endpoint with an arbitrary `shop-domain` header and have it processed as if it originated from a different, victim shop.

### Finding Description
`Request#hmac` computes the received signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC-SHA256(secret, verifiable_query.to_signable_string)`, i.e. only over the body — the `shop` value plays no role in the equality being checked: [3](#0-2) 

`Registry.process` performs exactly one authentication check — the body HMAC — and then dispatches to the handler using the unauthenticated `request.shop` value as the tenant identity for the webhook payload: [4](#0-3) 

The binding that should hold is://
`shop-domain header == tenant whose secret produced hmac(body)`

but the code only checks:
`hmac == HMAC(client_secret, body)`

with `shop` entirely outside that computation. Since a single app-wide `client_secret` is used to sign webhooks for *every* installed shop, a `(body, hmac)` pair captured from a webhook delivered to any shop that runs the same app (including one the attacker installs on their own store) is valid HMAC-wise for a request bearing a completely different `shop-domain` header. `Registry.process` will accept it and pass the attacker-chosen `shop` value straight into `WebhookMetadata`, which application code typically uses to look up/create per-tenant sessions or records — a cross-tenant identity confusion.

### Impact Explanation
An attacker who operates their own shop with the target app installed can capture legitimate `(raw_body, hmac-sha256)` pairs from webhooks sent to their own store, then replay them to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header set to a victim shop. Because `shop` is not covered by the HMAC, `Utils::HmacValidator.validate` still succeeds, and `Registry.process` forwards `WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...)` to the app's handler as if the (attacker-controlled) body genuinely came from the victim tenant. Depending on how the host app's handler keys data by `shop` (session lookup, per-tenant record creation/update, GDPR redaction triggers, etc.), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Requires only an unprivileged internet user who can install the target app on a shop they control (a normal, low-privilege action for any Shopify merchant/developer) and can send arbitrary HTTP requests to the app's publicly reachable webhook endpoint. No access token, `api_secret_key`, or privileged account is needed — only observation of one's own legitimately delivered webhook headers/body.

### Recommendation
Bind the tenant identity into the verified material, e.g., include `shop-domain` (and ideally `webhook-id`/`api-version`) in the signable string, or perform a secondary out-of-band verification that the `shop` in the webhook matches a shop known to have an active app installation/session before trusting it, mirroring the `AuthQuery` pattern where every identity-relevant field (`shop`, `host`, `state`, etc.) is part of `to_signable_string`: [5](#0-4) 

At minimum, document and enforce that consumers of `WebhookMetadata#shop` must cross-check it against a shop with a currently valid, independently-authenticated session before acting on the payload, since the gem itself provides no such binding today.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and subscribes to a webhook topic the app processes (e.g. `orders/create`), producing a legitimately signed webhook `POST` with headers `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and body `B`.
2. Attacker replays the exact same body `B` and the same `X-Shopify-Hmac-Sha256: <H>` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without validating any relationship between `shop-domain` and the HMAC: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares it to `<H>` — this still matches because `B` and `<H>` are unchanged and the same app-wide `client_secret` was used originally: [7](#0-6) 
5. Validation passes, and the handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the app to act on attacker-supplied data under the victim shop's identity: [8](#0-7)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
