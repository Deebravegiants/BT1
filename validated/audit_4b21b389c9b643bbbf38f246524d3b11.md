## Title
Vote account commission collector (SIMD-0232) is resolved from an end-of-epoch snapshot instead of a delayed snapshot, letting a newly-authorized withdrawer redirect an entire epoch's already-earned commission away from the party who actually ran the vote account during that epoch - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Agave already recognizes and mitigates this exact bug class for the commission **rate**: `commission_bps` is deliberately read from a vote-account snapshot taken a full epoch earlier, specifically "to prevent last minute commission rugs." However, the commission **recipient** (`inflation_rewards_collector`, SIMD-0232 custom commission collector) is *not* protected by this same delay mechanism - it is read from the snapshot taken at the very end of the rewarded epoch. Combined with the fact that vote-account withdrawer authority (which controls the collector field) can be transferred instantly with no delay, a party who only gains control of the vote account at the boundary of an epoch can redirect that entire epoch's commission to itself, even though it did not operate the vote account (earn the credits) during that epoch. This is structurally identical to the reported "curator loses reward if vault ownership changes after epoch end but before distribution" bug.

### Finding Description
`Bank::get_cached_vote_accounts` explicitly snapshots vote-account state early to delay the effect of ownership/config changes before they can affect reward calculation: [1](#0-0) 

This produces a `CachedVoteAccounts` struct with three views: a snapshot from a full epoch before the rewarded epoch, one from the beginning of the rewarded epoch, and `distribution_epoch_vote_accounts` - explicitly documented as "Vote account state from the end of the rewarded epoch / beginning of the distribution epoch": [2](#0-1) 

In `redeem_delegation_rewards`, the commission *rate* deliberately prefers the delayed snapshots (`snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`) over the live/current vote state, with a comment stating this is done "to attempt to delay the effect of commission updates by at least one full epoch": [3](#0-2) 

But the commission *recipient* - `commission_pubkey`, derived from `vote_state.inflation_rewards_collector()` - is taken from `vote_state`, which comes straight from `distribution_epoch_vote_accounts` (the end-of-rewarded-epoch snapshot), with no equivalent delay: [4](#0-3) 

Both the vote account's withdrawer authority and the commission-collector field it controls can be changed with no cooldown. `VoteAuthorize::Withdrawer` is updated immediately in the same instruction that authorizes it: [5](#0-4) 

`update_commission_collector` (SIMD-0232) only requires the current authorized withdrawer's signature and applies instantly, with no snapshot delay analogous to `delay_commission_updates`: [6](#0-5) 

and is dispatched unconditionally behind only the `custom_commission_collector` feature gate, with no equivalent to the `delay_commission_updates` gate used for `UpdateCommissionBps`: [7](#0-6) 

**Root cause:** the codebase demonstrates awareness that vote-account configuration must be delayed by a full epoch to prevent "last minute rugs" on reward calculation, but that protection was applied only to `commission_bps` and not to the commission collector pubkey that actually receives the lamports. This is the same class of bug as the reported Suzaku issue: rewards for a whole period are paid to whoever is designated at distribution-snapshot time, not to whoever held that role during the period the rewards were earned.

### Impact Explanation
A withdrawer authority transfer (`Authorize`/`AuthorizeChecked` with `VoteAuthorize::Withdrawer`) followed immediately by `UpdateCommissionCollector` at/just before the epoch boundary lets the new withdrawer capture the entire rewarded epoch's inflation-rewards commission - lamports that were "earned" by the vote account operating under the prior withdrawer/collector configuration for essentially the whole epoch. This is a concrete, undeclared value redirection at bank-commit reward-distribution time: the previous operator/collector loses commission it was economically entitled to, and the new controller receives it without having operated the vote account during that epoch. It does not require a validator/consensus-level attack - any vote account's withdrawer authority (a permissionless, user-controlled key) can trigger it via two ordinary instructions.

### Likelihood Explanation
This requires only two ordinary, permissionless vote-program instructions (`Authorize`/`AuthorizeChecked` for withdrawer, then `UpdateCommissionCollector`) executed near an epoch boundary - no special validator privilege, leader status, or malicious consensus behavior is needed. The precondition (withdrawer authority changing hands, e.g. via sale/transfer of a validator's vote account, or an operator opportunistically front-running its own commission redirection) is realistic and entirely within existing, intended program capabilities. Since the delay protection was clearly designed for exactly this timing class of bug (as shown by the `delay_commission_updates` comments) but was not extended to the collector field, the gap appears to be an oversight rather than an intentional design choice.

### Recommendation
Apply the same delayed-snapshot mechanism used for `commission_bps` to `inflation_rewards_collector` (and `block_revenue_collector`): resolve the commission-collector pubkey from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` (or otherwise a snapshot from at least one full epoch prior to distribution) instead of from `distribution_epoch_vote_accounts`, mirroring the logic in `redeem_delegation_rewards` at `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:709-724`.

### Proof of Concept
1. Vote account `V` operates normally through epoch `N`, accruing `pending_delegator_rewards`/credits under `inflation_rewards_collector = A`.
2. Near the very end of epoch `N` (or in the epoch-boundary block before `compute_new_epoch_caches_and_rewards` snapshots `distribution_epoch_vote_accounts`), the current authorized withdrawer signs `Authorize(new_withdrawer, VoteAuthorize::Withdrawer)` transferring control to `B` (`programs/vote/src/vote_state/mod.rs:727-731`, takes effect immediately).
3. `B`, now the authorized withdrawer, immediately signs `UpdateCommissionCollector(InflationRewards, collector=B)` (`programs/vote/src/vote_state/mod.rs:907-933`), which succeeds instantly with no epoch delay.
4. When rewards for epoch `N` are calculated/distributed, `redeem_delegation_rewards` resolves `commission_pubkey` from `distribution_epoch_vote_accounts` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:750-757`), which reflects the state after step 3 - so `B` receives the full commission for stake activity that occurred while `A` was actually running the vote account.

    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
