### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identity) and `topic` (dispatch key) values are read directly from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values to route the webhook to a handler and to stamp the resulting `WebhookMetadata` with a shop identity, without those values ever being covered by the cryptographic signature it just validated.

### Finding Description
`Utils::HmacValidator.validate` authenticates a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it (constant-time) against the `hmac` attribute: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to be only the raw HTTP body: [2](#0-1) 

But `shop` and `topic` — the values actually acted upon by the library — are parsed straight from headers that are entirely outside the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC-over-body, then uses the unauthenticated `request.topic` to select a handler and the unauthenticated `request.shop` to populate the tenant identity passed to the application's handler: [4](#0-3) 

This is precisely the binding break described in the reference report's bug class: a field that the code acts on (`shop`, used as the tenant key; `topic`, used for dispatch) is not covered by the identity/integrity check (the HMAC) that is supposed to authenticate the whole request. The equality that should hold — `shop header used for dispatch == shop that produced/authorized the signed body` — is never enforced. Only `body-bytes-verified == body-bytes-parsed` is checked; `shop` and `topic` are unconstrained.

### Impact Explanation
An unprivileged user who operates their own Shopify store with the target app installed will legitimately receive webhooks addressed to their own shop, each with a valid HMAC computed over the JSON body using the app's `client_secret` (known only to Shopify and the app, not to the attacker — but the attacker doesn't need it). The attacker can capture one such legitimately-signed request and replay it to the app's webhook endpoint after rewriting only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim shop. Because the HMAC never covered these headers, `HmacValidator.validate` still returns `true`, and `Registry.process` will hand the attacker-chosen body to the handler tagged with the victim's shop domain (`WebhookMetadata#shop`) — a cross-tenant data-injection primitive into whatever storage/business logic the host application keys by `shop`. This matches the Critical impact category "cross-tenant access."

### Likelihood Explanation
High likelihood: any user who can install the app on their own store (a normal, unprivileged onboarding flow) can generate arbitrarily many genuinely-signed webhook bodies for the topics they control (e.g. `orders/create`, `products/update` on their own store), then trivially resend them with a forged shop/topic header — no cryptographic secret is ever required from the attacker's side.

### Recommendation
Include the tenant-identifying and dispatch-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signable string for webhook requests, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`, so that an attacker cannot swap these values without invalidating the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a POST with a body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends this exact request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (body `B` and the HMAC header untouched).
3. `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` (unchanged) and it matches — validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`, `lib/shopify_api/webhooks/request.rb:20-23`), causing the host application to process attacker-controlled data under the victim shop's tenant identity.

          received_signature = verifiable_query.hmac

        end
