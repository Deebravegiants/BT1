### Title
Bad-debt write-down frees the wrong resource — supply index is clamped up to `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing wiped supply shares, leaving phantom claims that drain fresh deposits - ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs))

### Summary
The kernel bug frees a pooled item with plain `kfree()` instead of the pool-aware `qla24xx_free_purex_item()`, corrupting the allocator. The analog here is the same bug class — a write-down/release path that "frees" supplier value through the wrong mechanism. When bad debt equals or exceeds total supplied value, `apply_bad_debt_to_supply_index` should annihilate supplier claims; instead it clamps `supply_index` **up** to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`), resurrecting every wiped position as a claim worth 0.1% of face value that pays out of whatever cash later enters the pool.

### Finding Description
In `contracts/pool/src/interest.rs`, `apply_bad_debt_to_supply_index` computes `reduction_factor = (total_supplied_value - capped_bad_debt) / total_supplied_value` and then applies `new_supply_index.max(SUPPLY_INDEX_FLOOR_RAW)`. When `capped == total_supplied_value` (full wipeout), the mathematically correct index is 0, but the floor forces it to `RAY/1000`. Every existing scaled supply share then unscales to `scaled * floor > 0` — a phantom claim backed by nothing. The pool's own tests confirm the consequence: after the floor clamp, `unscale_supply_floor(old_scaled) > 0`, and `resolve_withdrawal(i128::MAX, old_scaled)` pays real tokens out of a subsequent supplier's deposit until `cash` hits zero, leaving the honest supplier undercollateralized. The same-floor logic is reachable from production entrypoints: a liquidation or `clean_bad_debt` triggers `seize_positions` (`ops::seize::apply`), whose borrow-side leg socializes bad debt through this function, while `supply`/`withdraw` are ordinary user calls.

### Impact Explanation
Permanent theft of user funds and protocol insolvency. Once a market's supply index is clamped to the floor, all pre-wipeout suppliers hold claims totaling `supplied * RAY/1000` despite the socialization having nominally absorbed their entire value. The first wiped holder to call `withdraw(amount = 0/i128::MAX)` receives real tokens paid for by the next honest depositor — demonstrated in the in-repo tests `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard`, where the wiped claim drains exactly a fresh deposit and leaves the honest supplier's claim uncovered. There is no supply guard preventing new deposits into a floor-clamped market, so the window stays open indefinitely.

### Likelihood Explanation
An unprivileged attacker can force the precondition themselves: open an account, supply collateral in one market, borrow the maximum in a second market, then abandon the position (or manipulate utilization/time so it accrues into bad debt) and invoke `liquidate`/`clean_bad_debt` to trigger the borrow-side `seize_positions` write-down. Any market whose bad debt meets or exceeds `total_supplied_value` — trivially satisfiable in a small or drained market — lands the index on the floor. The attacker (or any prior supplier, including dust positions) then waits for or induces a fresh `supply` and withdraws. No privileged role, oracle manipulation, or leaked key is required; all steps use the listed reachable entrypoints (`supply`, `borrow`, `liquidate`, `clean_bad_debt`, `withdraw`).

### Recommendation
Distinguish the two "freed" states the way the kernel fix distinguishes pooled vs. dynamic items: when `capped == total_supplied_value` the market's supplier claims must be fully released — burn the residual scaled supply (or set the index to a true zero-equivalent) rather than clamping the index upward to `SUPPLY_INDEX_FLOOR_RAW`. Concretely, in `apply_bad_debt_to_supply_index`, short-circuit the full-wipeout case (e.g., zero `supplied` shares or record the market as wiped and gate `supply`/`withdraw` until `recapitalize` restores backing) so a floor-clamped index can never unscale to a positive claim. Additionally, reject new `supply` into a market sitting at the floor until recapitalization covers the stranded claims.

### Proof of Concept
1. Attacker supplies a small amount to market M and borrows (from collateral elsewhere) such that M accrues bad debt; attacker calls `clean_bad_debt`/`liquidate` so `seize_positions` runs a borrow-side entry with `bad_debt >= total_supplied_value`.
2. `apply_bad_debt_to_supply_index` sets `supply_index = max(0, SUPPLY_INDEX_FLOOR_RAW)` → `RAY/1000`. Attacker's wiped scaled shares `S` now represent `unscale_supply_floor(S) > 0`.
3. Victim calls `supply` on M, crediting `cash = C`.
4. Attacker calls `withdraw` with full-close semantics (`i128::MAX`); `resolve_withdrawal` pays `gross = C`, `debit_cash(C)` empties the pool, and the victim's shares cannot be paid — theft completed.

This mirrors the harness test `pool_loss_floor_recapitalization_returns_only_unused_funding` and `test_raw_cache_floor_clamp_strands_claim_without_supply_guard`, which assert `gross == fresh_cash` and `cash < fresh_claim` after the floor clamp.

Note: I verified the pool-side root cause and the reachable controller entrypoints (`seize_positions` via liquidation/clean-bad-debt, `supply`, `withdraw`) but did not fully trace the controller's `clean_bad_debt` dust-threshold gating, so the exact minimal path to force `bad_debt >= total_supplied_value` through that specific entrypoint remains partially unverified.
