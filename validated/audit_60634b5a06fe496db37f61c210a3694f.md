### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant data injection - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by verifying only the HMAC of the raw request body, then forwards the `shop` value taken from the unauthenticated `x-shopify-shop-domain` header to the app's webhook handler as the tenant identifier. Because the shop domain is never part of the signed payload, an attacker can reuse a validly-signed body/HMAC pair (e.g. from a webhook obtained via their own installed shop) while substituting an arbitrary `x-shopify-shop-domain` value, producing a request that passes `HmacValidator.validate` yet claims to belong to a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the `hmac` accessor of the object passed in [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, and `shop`/`hmac`/`topic` are all read directly from HTTP headers with no cryptographic tie between the `shop` header and the signature [2](#0-1) .

`ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof that the *entire request*, including the shop identity, is authentic, and passes `request.shop` straight into `WebhookMetadata` given to the app's handler: [3](#0-2) 

This breaks the intended identity binding `HMAC(body) == received_hmac ⇒ shop header is authentic`. In reality the equality only proves the body is authentic; the `shop` header is attacker-controlled bytes that were never verified. The gem's own documentation instructs host apps to trust `data.shop` as the authoritative tenant identifier for the webhook (e.g., enqueuing background jobs keyed by `shop_domain`) [4](#0-3) , so any host app that follows the documented pattern inherits this tenant-binding gap directly from the gem.

### Impact Explanation
An attacker who can obtain one validly HMAC-signed webhook body (trivial: install the app on a shop they control, or replay any previously observed webhook whose raw body is still valid for a given topic) can resend the exact same `raw_body` + `hmac-sha256` header while forging the `x-shopify-shop-domain` header to name a victim shop. `Registry.process` will validate the HMAC successfully and dispatch the payload to the app's handler tagged with the victim's shop domain. Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's records to update (the exact pattern shown in this gem's own documentation) will process attacker-supplied data under another merchant's identity — a cross-tenant data integrity/confidentiality issue reachable purely from the internet with no credentials beyond a webhook endpoint URL and one legitimately-signed payload.

### Likelihood Explanation
Likelihood is high for apps that expose a webhook endpoint accepting any topic body shape they already handle (e.g. `orders/create`, `app/uninstalled`) and use `data.shop` as documented. No secret key, access token, or privileged position is required — only a previously observed or self-generated valid `(raw_body, hmac)` pair for the shared topic and endpoint, since `api_secret_key` is shared across all shops installing the same app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or independently verify that the `x-shopify-shop-domain` header matches a shop record already known to have that HMAC/topic association before trusting it as the tenant key. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should bind the shop header into what is verified, or `Registry.process` should require host apps to cross-check `request.shop` against an existing, previously-authenticated session/shop record rather than trusting the header outright.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the shared `api_secret_key`).
2. Replay a POST to the app's webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B` only) and matches `H` — validation passes [5](#0-4) .
4. `handler.handle` receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process/store attacker-controlled data attributed to `victim-shop.myshopify.com` [6](#0-5) .
