## Analysis

The Sherlock report's bug class — a permissionless/whitelisted user can trigger a state change (`setProtocolBlacklist`) but has **no function to undo a mistaken call** — maps onto `Bonding.transferCreator`.

`Bonding.transferCreator` is a single-step, unilateral creator-role transfer with no two-step accept/confirm mechanism, unlike other privileged-role transfers in this same codebase (`Ownable2StepUpgradeable` is deliberately used on `LPLock` and `Bonding`'s owner role specifically so that "a bad `transferOwnership` can be cancelled ... before it takes effect"). [1](#0-0) 

The two-step-ownership rationale documented on `LPLock` explicitly calls out this exact risk class for one-shot single-address writes: [2](#0-1) . `transferCreator` does not follow that pattern — it writes `info.creator = newCreator` in the same call with no acceptance step and no way to reverse a bad transfer if `newCreator` is fat-fingered, or is a contract/address the caller does not actually control.

Fee attribution for both buys and sells routes exclusively through `info.creator`, and `FeeVault.claim()` pays out to whichever address currently holds that role: [3](#0-2) .

### Title
Single-step, irreversible `Bonding.transferCreator` permanently strands a token's future creator fee stream on a mistaken address - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.transferCreator(address tokenAddress, address newCreator)` performs the creator-role handoff atomically and irreversibly in one transaction. There is no `pendingCreator` / `acceptCreator` two-step confirmation, and no way for the original creator (or anyone) to correct a mistaken call once made.

### Finding Description
`transferCreator` is callable only by the current `info.creator`, and on success immediately overwrites `info.creator = newCreator` with no staging or acceptance step: [1](#0-0) 

`FeeVault.accrue` is called from `Zap._accrueFee` using `bonding_.creatorOf(tokenAddress)` as the attribution key for every subsequent buy/sell fee on that token: [4](#0-3) , and per the documented fee model, `FeeVault.claim()` pays out pooled USDC per-creator address [5](#0-4) .

If `transferCreator` is called with a typo'd address, a contract that cannot itself call `transferCreator` back (e.g. no fallback/receive-compatible logic, or simply an address whose private key the caller doesn't hold), the token's entire future 0.25% creator fee stream is permanently rerouted to that unrecoverable address. There is no owner override, no correcting function, and no acceptance step that would let the mistake be caught before it takes effect — in direct contrast to the `Ownable2StepUpgradeable` pattern this same codebase deliberately uses elsewhere specifically to prevent this class of mistake.

### Impact Explanation
Every future creator-side fee accrual (0.25% of all buy/sell volume on the affected token, indefinitely) becomes permanently unclaimable by the real creator once `transferCreator` is mis-called. This is a permanent freezing of creator funds for the life of the token — a growing, unbounded loss with no on-chain recovery path, matching the Medium severity of the original "missing function" finding (an unrecoverable, mistake-prone operation with no way to undo it).

### Likelihood Explanation
`transferCreator` is a normal, expected operation (e.g. creators handing tokens to a DAO, multisig, or new wallet) and is directly reachable by any token creator with a single transaction and no confirmation step. A single typo, wrong-network address reuse, or copy-paste from an incompatible address format is sufficient to trigger the loss — no attacker action or privileged intervention is required, only ordinary user error, which is a realistic and previously-flagged (per the analogous audit finding) failure mode for exactly this kind of single-step role transfer.

### Recommendation
Convert `transferCreator` to a two-step pattern mirroring the `Ownable2StepUpgradeable` design already used elsewhere in this codebase: stage the transfer in a `pendingCreator[tokenAddress]` mapping, and require the new address to call an `acceptCreator(tokenAddress)` function before `info.creator` is actually updated. This lets a mistaken `newCreator` be caught and cancelled by the original creator before it takes effect, consistent with the rationale already documented for `LPLock`'s and `Bonding`'s owner-transfer paths.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`, becoming `info.creator`.
2. Token accrues buy/sell volume and creator fees in `FeeVault`.
3. Creator calls `bonding.transferCreator(tokenAddress, newCreator)` with a mistyped or otherwise uncontrolled `newCreator` address (see `test_transferCreator` in `Bonding.t.sol` for the call pattern: [6](#0-5) ).
4. `info.creator` is now permanently set to the unreachable address; there is no `transferCreator` call the original creator can make to reclaim the role (they are no longer `info.creator`), and the new address cannot execute the reverse transfer since it does not exist/is not controlled.
5. All subsequent creator-side fee accrual for that token is credited to `FeeVault` under the unreachable address and can never be claimed.

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }

```markdown
## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```
