### Title
Unbounded LT-appreciation past the launch-time `uint112` headroom bricks `finalizeGraduation` and can permanently strand the curve's raised LT and 250M LP-reserve tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2021-45960 is a class of bug where a value used to size a later allocation/buffer (the `storeAtts` left-shift) is checked/derived at one point in time but the actual quantity that flows into the fixed-size slot at a later point can exceed what that check accounted for, corrupting the allocation. The closest reachable analog in alt.fun is the `virtualLtReserve` / HyperSwap `uint112` reserve-slot sizing in the two-phase graduation path: the bound is enforced once, at `launch()`, off a single `exchangeRate()` snapshot, but the quantity that actually has to fit into the HyperSwap V2 pair's `uint112` reserve slot is fixed only at `_enterGraduating` (end of the threshold-crossing buy), using whatever `exchangeRate()` is live *then* — for a leveraged token this can have moved arbitrarily from the launch snapshot.

### Finding Description
At launch, `Bonding._deployAndSeed` snapshots the LT's `exchangeRate()` once and derives `virtualLtReserve = VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate`, then guards it against the HyperSwap `uint112` reserve slot with 4x headroom: [1](#0-0) 

The comment explicitly ties this bound to the eventual HyperSwap V2 `uint112` reserve write: "the raised LT reserve peaks at `3 * virtualLtReserve` (curve sell-out) and is later deposited into a HyperSwap V2 pair, whose reserves are `uint112`."

This bound is computed entirely from the launch-time `exchangeRate()` snapshot. It is never re-checked at graduation time. `_prepareGraduationLiquidity` computes the amount that will actually be deposited into the HyperSwap pair's `uint112` reserve slot as `ltFromPair = assetReserve - virtualLtReserve` (recovered via `Pair.k() / TOTAL_SUPPLY()`): [2](#0-1) 

Because the reserve asset is a BounceTech **leveraged** token, `exchangeRate()` is explicitly documented elsewhere in the codebase as capable of moving multiples in either direction between launch and graduation (that's the entire premise of the USD graduation trigger — "HYPE pumps raise the USD value of already-raised LT above the threshold"). The `3 * virtualLtReserve` bound assumed at launch is a static property of the *curve's own sell-out math* (`tokensForLP(sold)` parabola), but `ltFromPair`'s *absolute LT-wei size* is not itself re-derived against the live rate anywhere before it is fed to `_seedUniswapV2Direct` → `_seedDirectMint`/`_seedRebalancing`, which transfer `ltFromPair` LT into the HyperSwap V2 pair and call `IUniswapV2Pair(pair).mint(...)`/`swap(...)` — operations that internally cast the post-transfer balance into `uint112` reserves (standard V2 `_update`). The launch-time 4x headroom bounds `virtualLtReserve` itself, but does **not** bound how much *additional* real LT the curve can raise (`ltFromPair`) once the LT's exchange rate has drifted at the moment `_enterGraduating` snapshots reserves — a token launched when the LT is expensive (small `virtualLtReserve`, satisfies the launch guard easily) followed by a large downward move in the LT's exchange rate before graduation inflates the *LT-wei* amount users must deposit to reach the same $9K USD threshold, i.e. `ltFromPair` (a raw wei quantity) can grow far past what the launch-time 4x/uint112 headroom assumed, because that headroom was sized against the *launch* rate, not the rate in force when the curve actually fills.

Once `ltFromPair` (or the sum of `ltFromPair` plus a pre-existing/attacker-donated LT balance skimmed by `_seedUniswapV2Direct`) pushes the pair's real balance past `type(uint112).max`, the downstream HyperSwap V2 pair's reserve-storing arithmetic silently truncates/wraps on the standard V2 `_update`'s `uint112(balance)` cast (this is exactly the CVE's shape: a size-governing value validated once against a fixed cap is not re-validated against the live conditions actually present when the value is consumed, and the fixed-width sink silently truncates rather than reverting). This corrupts the pair's stored `(reserve0, reserve1)`, which is then used by every subsequent V2 swap/mint math (`getAmountOut`, `mint`'s `min(amount0·S/r0, amount1·S/r1)`), permanently mispricing the LP and/or making `finalizeGraduation` compute a bogus `liquidity` that gets locked via `LPLock.recordLock` — a one-shot, unfixable operation per the AGENTS.md note ("`LPLock.recordLock` that `finalizeGraduation` cannot skip").

### Impact Explanation
If it triggers, the effect is a corrupted/underflowed on-chain reserve accounting for the graduated HyperSwap pool — either freezing the curve's entire raised LT and the 250M `LP_RESERVE` tokens inside a pool whose reserves silently wrapped (permanent value freeze/mispricing for LPs and future traders), or opening the graduated pool at a wildly wrong price that lets an attacker drain the mismatched reserve side via a normal swap immediately post-graduation (concrete theft of curve-raised funds). Because `LPLock.recordLock` is one-shot and irreversible, there is no recovery path once `finalizeGraduation` completes against a corrupted pair.

### Likelihood Explanation
This requires the reserve LT to move by roughly two to three orders of magnitude (from launch rate to graduation rate) in the LT's exchange rate for a single curve to accumulate enough raw LT wei to overflow `uint112` (`~5.2 x 10^15` LT at 18 decimals) — a large but not impossible move for a genuinely leveraged asset over the lifetime of an unfinalized curve, and the launch-time guard gives a false sense that this is bounded when it is only bounded against the *launch* snapshot, not the *live* rate at fill time. No privileged action is required: any trader pushing the curve to graduate while the LT is severely devalued relative to its launch-time rate reaches this path through ordinary `Zap.buy` calls.

### Recommendation
Re-validate the actual LT quantity that will be deposited into the HyperSwap pair (`ltFromPair`, and the sum with any pre-existing pair balance skimmed in `_seedUniswapV2Direct`) against `type(uint112).max` at `_prepareGraduationLiquidity` / `_enterGraduating` time (i.e., against the live rate at fill), not only at launch against the launch-time snapshot, and revert or clamp before any V2 `mint`/`swap` call that would silently truncate a `uint112` reserve.

### Proof of Concept
1. Attacker or any user calls `Zap.createToken` against a BounceTech LT whose `exchangeRate()` is currently high (e.g., deep into its leveraged appreciation), so `virtualLtReserve = VIRTUAL_LIQUIDITY_USD*1e18/exchangeRate` is small and easily passes `_deployAndSeed`'s `type(uint112).max/4` guard [3](#0-2) .
2. Over time (or via a single large adverse move reported by the LT's own price feed, outside this contract's control), the LT's `exchangeRate()` collapses by several orders of magnitude while the curve has not yet graduated.
3. Ordinary traders call `Zap.buy` repeatedly; because the USD trigger is `(storedAssetReserve - virtualLtReserve) x exchangeRate >= $9K`, a collapsed rate means traders must deposit proportionally far more raw LT wei to reach the same USD threshold, inflating `ltFromPair` computed in `_prepareGraduationLiquidity` [4](#0-3)  well past the launch-time 4x/uint112 headroom that only bounded the launch-time `virtualLtReserve`, not this later live-rate-driven quantity.
4. `_enterGraduating` caches this oversized `ltFromPair` in `pendingGraduation`; the permissionless `finalizeGraduation` then calls `_seedUniswapV2Direct` → `_seedDirectMint`/`_seedRebalancing`, transferring `ltFromPair` LT into the HyperSwap pair and calling `mint`/`swap` [5](#0-4) , whose reserve bookkeeping is a standard V2 `uint112` cast that silently wraps once the pair's real LT balance exceeds `type(uint112).max`.
5. `LPLock.recordLock` finalizes the (now-corrupted) LP position with no rescue path.

I was not able to directly inspect the deployed HyperSwap V2 pair's `_update`/`swap` bytecode (out of scope: "bugs inside ... HyperSwap V2 themselves" are excluded per the rules), so this finding targets only the alt.fun-side gap — the launch-time-only, snapshot-based `uint112` guard in `Bonding._deployAndSeed` — rather than the mechanics of the truncation itself, consistent with the scoping rules.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
