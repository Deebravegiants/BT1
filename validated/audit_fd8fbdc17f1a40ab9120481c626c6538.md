### Title
Attacker-crafted swap route executes arbitrary pool code that steals the caller's wallet tokens via the signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The CVE class is "crafted uploaded artifact is executed" — user-supplied data reaching a code-execution sink. In XOXNO Lending, the analog is the user-supplied `swap: StrategySwap` route accepted by the controller's strategy entrypoints (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`). The controller passes this payload verbatim to the router, which calls whatever pool addresses the payload names with no allowlist. A rogue "pool" contract inside the route runs on the call stack beneath the victim's `require_auth`, and any `token.transfer(victim, attacker, x)` it makes is recorded by simulation as a child of the victim's authorization entry — executing if the victim signs the simulated tree. This is proven by the dedicated harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` snapshots balances, authorizes exactly one `token_in.transfer(controller, router, amount_in)` invocation, then calls `router.execute_strategy(&controller, &amount_in, swap)` on the caller-provided `swap` bytes. Neither the controller nor the router restricts which contract addresses the route may name as venues/pools — the threat model explicitly states "the router calls the pool and token addresses its payload names and keeps no allowlist of them." [3](#0-2) 

The measured-delta guards (`RouterOverspend`, `NoSwapOutput`, final risk gates) only bound the routed amount. They do not bound what the rogue pool does under the *user's* auth: because `swap_collateral` requires the user's `require_auth` at the entrypoint, a nested `transfer` from the user's address rides on that same authorization tree. The harness test demonstrates a `RogueHopPool.swap()` that calls `token::Client::transfer(&victim, &attacker, &amount)`; under enforcing auth the transaction succeeds and drains Alice's entire balance of a token the protocol never listed (77,770 units → 0) once the simulated tree includes the rogue transfer. [4](#0-3) [5](#0-4) 

### Impact Explanation
Theft of user funds. The loss is "the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" — an attacker who supplies a poisoned route to a victim (via a compromised/malicious quote source or phishing route XDR) can drain every token the victim holds, not merely the swap input. All controller strategy entrypoints that take `swap` bytes, plus direct `execute_strategy` calls, carry this exposure. [6](#0-5) 

### Likelihood Explanation
Exploitation requires the victim to sign an authorization tree containing the extra child transfer. Standard wallets sign whatever `simulateTransaction` returns, and simulation faithfully attaches the rogue transfer under the victim's entry — so a victim using an un-hardened client signs it without decoding. The protocol's own mitigation is client-side only ("a client must decode the route it signs and refuse an authorization tree with any other child"), which most integrations will not implement. No privileged access, timing, or market condition is needed; the attacker's route executes within a single transaction. [7](#0-6) 

### Recommendation
Enforce the venue/pool allowlist on-chain rather than in clients. Options: (a) governance-maintained approved-pool registry checked by the router before dispatching each hop (mirroring the Blend-pool approval list in INV-STRAT-03); (b) reject any sub-invocation beyond the single input transfer by having the controller/router verify the authorization tree shape; (c) route execution through a context where the user's `require_auth` is not on the stack for arbitrary venue calls (not fully achievable on Soroban today, so (a) is the practical fix). Until fixed, the SDK should ship and default the `verifyRouteBytes` check.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `UnlistedPoolRouter.execute_strategy` invokes `route.hop_pool.swap` named entirely by the payload; `RogueHopPool.swap` executes `transfer(alice → attacker, WALLET_BALANCE)` on a token unrelated to the swap; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the signed simulated tree drains Alice's full `WALLET_BALANCE` while the honest tree is refused by the host. The same path is reachable through `controller.swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` since all forward caller-supplied `swap` bytes via `swap_tokens`. [8](#0-7)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
