### Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only. The `shop-domain` (and `topic`/`webhook-id`/`api-version`) HTTP headers are never included in the signed material, so an attacker who possesses one legitimately-signed webhook (e.g., delivered to their own installed app) can replay the exact same body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and `ShopifyAPI::Utils::HmacValidator.validate` will still accept it.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#hmac` is parsed from the `hmac-sha256` header, decoded, and compared against `HMAC-SHA256(secret, raw_body)`: [2](#0-1) 

`HmacValidator.validate_signature` performs a constant-time comparison of that computed value against the header-supplied HMAC, again using only the signable string (the body): [3](#0-2) 

`Registry.process` trusts `request.shop` (read straight from the unauthenticated `shop-domain` header) once `HmacValidator.validate(request)` passes, and forwards it to the app's handler as the tenant identifier: [4](#0-3) 

Because the `shop` field that the handler treats as the authenticated tenant identity is never part of the HMAC-signed content, `shop == HMAC-bound shop` does not hold. Anyone able to obtain one validly-signed webhook payload (for instance, the developer's own installed test shop, which legitimately receives real Shopify webhooks) can resend that identical body/HMAC pair with a different `shop-domain` header value. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` dispatches the (attacker-chosen) `shop` value to the handler as if it were authentic.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to route webhook data (e.g., `shop/redact`, `app/uninstalled`, order/customer updates) to the correct merchant record. An attacker can cause the app to process a validly-HMAC'd payload under an arbitrary victim shop domain, resulting in cross-tenant data corruption/injection or triggering privileged lifecycle events (like redaction/uninstall handling) against a shop the attacker doesn't control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only one real webhook delivery that the attacker can observe (trivial for an app developer's own test/dev shop, or any shop where they can trigger a webhook-firing action), plus the ability to POST an HTTP request with a spoofed header to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged account is needed.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values (in addition to the body) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop-domain header to the signature so that these fields cannot be altered independently of a valid signature.

### Proof of Concept
1. Attacker's own app installation on `attacker-shop.myshopify.com` receives a legitimate webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: H` (valid for `B`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and header `X-Shopify-Hmac-Sha256: H` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H`, returning `true`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to process attacker-controlled data under the victim's shop identity.
