### Title
Webhook `shop` identity not covered by HMAC allows cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC that `Registry.process` validates only covers the raw request body. Because `to_signable_string` excludes the shop header, an attacker who obtains one genuinely signed webhook (e.g., by installing the app on their own store) can replay that valid `(body, hmac)` pair while substituting the `shop-domain` header to impersonate any other shop, causing the host application to process attacker-controlled data under a victim tenant's identity.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which checks the HMAC against `request.to_signable_string`: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256` header, while `Request#shop` independently reads the `shop-domain` header — none of which is bound into the signed payload: [2](#0-1) 

This produces an identity-binding gap analogous to the reported bug class: a field the code acts on (`shop`) is not covered by the cryptographic check (`HMAC`) that gates trust in the request. `Registry.process` then forwards `request.shop` directly into `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The equality the code implicitly assumes is: `shop header == shop that produced/authorized this HMAC-signed body`. In reality, `shop` and `hmac`/`raw_body` are independently attacker-suppliable header/body values; only `raw_body` is bound to the secret via HMAC. An attacker who has ever received one legitimately-signed webhook body for their own shop (trivial — install the app on a store they control, e.g. a free development store, and receive a real `orders/create`, `customers/data_request`, or similar webhook) can resend that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while setting `shopify-shop-domain` to a victim shop's domain. `HmacValidator.validate` still passes because it only checks `raw_body` against the secret, and `Registry.process` will happily label the payload as belonging to the victim shop.

### Impact Explanation
This breaks the tenant isolation boundary the gem is expected to provide: the whole purpose of validating the webhook HMAC is to let the host app trust `shop`/`body` as coming from Shopify for that specific shop. Because `shop` is not part of the signed data, an attacker can inject cross-tenant events (e.g. a forged `customers/data_request`/`shop/redact` for a shop they don't own, or a forged order/inventory update) that a naive but reasonably-written handler (using `data.shop` to select the tenant record to act on) will apply to the wrong shop. This matches the "cross-tenant access" criterion (Critical/High impact) since it lets one merchant's app installation forge inbound events attributed to a merchant they have no relationship with.

### Likelihood Explanation
Requires no possession of the app's `client_secret`, access token, or any victim credential — only that the attacker can install the app themselves (or otherwise obtain one valid signed webhook body/HMAC pair) and can reach the app's public webhook endpoint. Replaying a captured `(body, hmac)` with a swapped header is trivial and fully within reach of an unprivileged internet user who is also a legitimate (if low-privilege) merchant/installer of the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise cryptographically tie the header-derived shop to the signed body — e.g., include the shop domain in `to_signable_string`, or require the caller to supply/validate the expected shop out-of-band (matching it against a known installed-shop list) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. Attacker installs the target app on a store they control (`attacker.myshopify.com`) and receives a legitimate webhook, e.g. `customers/data_request`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Topic: customers/data_request`
   - body: `{"customer": {...}}`
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `Context.api_secret_key` — validation succeeds because the body/hmac pair is unchanged: [5](#0-4) 
4. `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` is dispatched to the host app's handler, which now processes attacker-controlled data as if it originated from `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
