### Title
Accrual-time `i128` value overflow permanently freezes large markets - (File: `common/src/rates/scaling.rs`)

### Summary
**Severity: High.** A sufficiently large supply or debt share balance can grow to a market index where `shares * index / RAY` no longer fits in `i128`; the next accrual panics before persisting state, permanently blocking repayment, withdrawal, borrowing, supplying, and index updates for that market. [1](#0-0) [2](#0-1) 

### Finding Description
Every accrual begins by unscaling both total borrowed and total supplied shares through `scaled_to_original`, which evaluates `scaled.mul(index)` before the borrow index is capped. [3](#0-2) [4](#0-3) 

`Ray::mul` ultimately uses half-up multiply-divide arithmetic that returns `MathOverflow` when the exact result does not fit in `i128`; the widened `I256` path only protects the intermediate product, not the unrepresentable final value. [5](#0-4) [6](#0-5) 

The static index ceiling is `10^36`, equivalent to a 1,000,000,000× index, but a book holding `10^36` scaled RAY units reaches the `i128` result ceiling at approximately 170.14×; therefore, the configured ceiling can be reached only after the arithmetic already overflows. [7](#0-6) [8](#0-7) 

An unprivileged caller can force the condition through `Controller::update_indexes(caller, vec![hub_asset])`; the controller requires only that caller’s authorization and forwards the selected market to the pool’s `update_indexes`. [9](#0-8) [10](#0-9) 

The pool accrues in chunks and calls `mark_accrued` only after all chunks succeed, so a panic at the crossing point leaves `last_timestamp` unchanged and causes every subsequent call to attempt the same overflowing accrual. [2](#0-1) [11](#0-10) 

Supply, borrow, withdraw, and repay all enter `ops::load_leg`, which calls `synced_market`; `synced_market` performs `interest::global_sync` before the requested mutation. [12](#0-11) [13](#0-12) [14](#0-13) 

The repository’s own long-horizon regression reproduces the cliff: a billion-unit 18-decimal market at 98% utilization eventually makes `update_indexes` return `MathOverflow`, after which both withdrawal and repayment also return `MathOverflow`. [15](#0-14) [16](#0-15) 

### Impact Explanation
The impact is permanent freezing of user funds in the affected market because suppliers cannot withdraw and borrowers cannot repay after the first crossing attempt. [17](#0-16) 

It also creates a permanent market liveness failure because the public accrual entrypoint can never advance `last_timestamp` past the overflowing interval. [2](#0-1) [11](#0-10) 

A borrower who has already withdrawn the borrowed assets can leave them unrepaid while the market remains frozen, leaving suppliers without an executable recovery path. [18](#0-17) [14](#0-13) 

### Likelihood Explanation
The trigger is deterministic once a market’s scaled supply or debt and its index cross the representable RAY-value bound; no oracle deviation, reentrancy, or privileged action is required. [1](#0-0) [9](#0-8) 

The main prerequisites are a very large admitted market, sustained borrowing so the borrow index grows, and enough elapsed time for the index to approach the unsafe bound. [19](#0-18) 

The final trigger remains permissionless even when the large position was accumulated organically by other users, because any address can authorize and call `update_indexes` for the affected `HubAssetKey`. [9](#0-8) 

### Recommendation
Cap each market’s borrow and supply index at a dynamic safe bound derived from its current scaled totals, such as `min(MAX_INDEX_RAY, floor(I256(i128::MAX) * RAY / scaled_shares))`, before calling `scaled_to_original`. [1](#0-0) [7](#0-6) 

Apply the same safe bound inside `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall`, because those paths perform additional `shares * index` and checked additions that must remain representable after the borrow index is clamped. [20](#0-19) [21](#0-20) [22](#0-21) 

Alternatively, enforce market supply and borrow caps low enough that the configured `10^36` index ceiling cannot overflow either share book, but that bound is substantially lower than the currently admitted asset-domain maximum. [23](#0-22) [24](#0-23) 

### Proof of Concept
The checked-in reproduction constructs a `BIG18` market, supplies `1_000_000_000 * 10^18` base units, supplies collateral, borrows 98% of the `BIG18` liquidity, advances ledger time, and calls `update_indexes` until it returns `MathOverflow`. [25](#0-24) 

```rust
let principal = 1_000_000_000i128 * 10i128.pow(18);
let debt = principal / 100 * 98;

// Establish the oversized book and sustained utilization.
controller.supply(supplier, 0, spoke_id, vec![(big18, principal)]);
controller.supply(borrower, borrower_account, spoke_id, vec![(collateral, required_collateral)]);
controller.borrow(borrower, borrower_account, vec![(big18, debt)], None);

// Any unprivileged caller can eventually force the crossing.
controller.update_indexes(trigger, vec![big18]); // MathOverflow

// The market is now frozen.
controller.withdraw(supplier, supplier_account, vec![(big18, 0)], None); // MathOverflow
controller.repay(anyone, borrower_account, vec![(big18, 1)]);            // MathOverflow
```

The test verifies that the configured borrow-index ceiling had not engaged when the overflow occurred and that subsequent withdrawal and repayment calls fail with the same `MathOverflow`. [26](#0-25)

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);

        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```markdown
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
