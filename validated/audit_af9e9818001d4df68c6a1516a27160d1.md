### Title
Missing validation of the app-supplied `self_custody_user_public_key` allows a low-order/degenerate Curve25519 key to defeat `sealedbox::seal` encryption of biometric Personal Custody Packages - (File: src/backend/user_status.rs)

### Summary
`decode_public_key()` in `src/backend/user_status.rs` decodes any 32-byte base64 blob into a `sodiumoxide::crypto::box_::PublicKey` with no check that the value is not the identity element, an all-zero value, or another low-order/invalid Curve25519 point. This key — sourced from the user's own app-supplied `self_custody_public_key` returned via `authenticated_app_data` — is later passed unchecked into `encrypt()`/`sealedbox::seal()` in `src/plans/personal_custody_package.rs` to encrypt the tier0/tier1/tier2 Personal Custody Packages containing iris codes, normalized iris images, and face data. This mirrors the reported bug class of "critical value accepted without a non-degenerate/non-zero check before being permanently relied upon for a security guarantee."

### Finding Description
`decode_public_key` only validates length, not curve-point validity: [1](#0-0) 

It is used to construct `self_custody_user_public_key` directly from data returned by the backend, which in turn is `authenticated_app_data.self_custody_public_key` — a value originated by the *user's own device/app*, not something the orb or backend independently generates: [2](#0-1) 

The resulting `UserData.self_custody_user_public_key` flows unchecked into `personal_custody_package::Credentials`: [3](#0-2) 

and is used as the encryption key for the entire tier0/tier1/tier2 packages, which bundle the raw and normalized iris images and face-identifier data: [4](#0-3) [5](#0-4) 

`sealedbox::seal` (libsodium) performs X25519 Diffie-Hellman with an ephemeral key against the supplied "public key." Curve25519 clamps arbitrary 32-byte inputs, so no length/format error occurs, but if the supplied bytes represent a low-order point (e.g., all-zero, or one of the other seven known small-order points), the resulting shared secret can only take one of a handful of fixed values, independent of the ephemeral secret. Anyone who obtains the ciphertext can brute-force this tiny keyspace and decrypt the "protected" data without knowledge of any real private key — the encryption is effectively neutralized. Because there is no check in `decode_public_key` (or anywhere downstream) rejecting the zero/low-order point, a user can supply such a key when generating their signup QR/app data and force their own PCP tier archives to be encrypted with a broken key.

### Impact Explanation
The self-custody tier archives contain the user's raw and normalized iris images, iris codes/shares, and face-identifier embeddings/thumbnails — highly sensitive biometric data. If the encryption key is degenerate, the confidentiality guarantee that only the paired self-custody app (holding the real private key) can decrypt this data is broken: any party with access to the uploaded/stored ciphertext (e.g. on the backend, S3, or via debug reports) can trivially decrypt it. This is a concrete biometric-data-disclosure impact stemming directly from the missing "is this a valid, non-degenerate key" check — the same root-cause pattern as the reported `MainToken.set_mint_multisig()` issue (an externally supplied critical value is accepted and permanently relied upon without a validity check).

### Likelihood Explanation
Any unprivileged signup participant controls the app-side generation of `self_custody_public_key` before or during the signup QR flow; the orb never independently validates that this key is well-formed/non-degenerate before using it to encrypt biometric data. No special privileges, hardware access, or backend/operator compromise are required — a standard user-flow value is sufficient to trigger the condition.

### Recommendation
In `decode_public_key` (and anywhere else public keys are decoded from external/app-supplied data, including `self_custody_user_public_key` and the backend keys), reject known invalid/low-order Curve25519 points (all-zero point and the other small-order points) before constructing the `PublicKey`, and fail the signup if validation does not pass, analogous to adding a "value must not be the degenerate/zero point" check before it is trusted for a security-critical operation.

### Proof of Concept
1. During the app-centric signup flow, have the paired app submit an all-zero (or otherwise known low-order) 32-byte value as `self_custody_public_key` in the QR-link/`authenticated_app_data` payload.
2. The orb decodes it via `decode_public_key` (`src/backend/user_status.rs:273-278`) with no validity check, producing `self_custody_user_public_key`.
3. During `Package::build` (`src/plans/personal_custody_package.rs:282-327,774-779`), the tier0/tier1/tier2 archives (containing iris/face biometric data) are encrypted with `sealedbox::seal` using this degenerate key.
4. Because the shared secret derived from a low-order point takes one of only a few fixed values, anyone with access to the resulting ciphertext (e.g., intercepted upload, backend storage, or debug report) can decrypt the "self-custody-protected" biometric package without the legitimate private key, defeating the intended confidentiality guarantee.

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}

fn encrypt<T: AsRef<[u8]>>(data: T, public_key: &PublicKey) -> Vec<u8> {
    let encrypted = sodiumoxide::crypto::sealedbox::seal(data.as_ref(), public_key);
    assert_ne!(data.as_ref(), encrypted);
    encrypted
}
