### Title
Unchecked scaled-debt value overflow freezes a market permanently - (File: common/src/rates/index.rs)

### Summary
Interest accrual computes `borrowed * borrow_index` without bounding the resulting total-debt `Ray` value. At very large market scale and high utilization, `new_total_debt` can overflow `i128` before the intended `MAX_BORROW_INDEX_RAY` cap is reached. Because every pool mutation accrues first, the market can permanently reject withdraws, repayments, liquidations, borrows, supplies, bad-debt cleanup, revenue claims, and index updates.

### Finding Description
The permissionless controller entrypoint `update_indexes(caller, assets)` authorizes the caller and invokes the pool's `update_indexes` for the supplied `Vec<HubAssetKey>` [1](#0-0) [2](#0-1) .

Pool accrual loads the market, repeatedly calls `accrue_step`, and commits the resulting indexes [3](#0-2) [4](#0-3) . Within each step, `update_borrow_index` caps the new index only after computing it [5](#0-4) . `calculate_supplier_rewards` then multiplies the scaled debt by both indexes to recover total debt:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

Both products are `Ray` values and therefore panic on an `i128` result overflow [6](#0-5) [7](#0-6) .

The capped borrow index does not protect this calculation: a capped or merely large index can still make `borrowed * index` exceed `i128`. The accrual therefore fails with `MathOverflow` before `global_sync` can call `mark_accrued`, leaving `last_timestamp` in the past [8](#0-7) .

All other mutating pool paths share this gate through `synced_market` or `load_leg` [9](#0-8) . For example, repay accrues before resolving or burning debt [10](#0-9) , and withdraw accrues before resolving or burning supply [11](#0-10) .

The repository already contains a reproduction demonstrating that the borrow index remains below `MAX_BORROW_INDEX_RAY`, while accrual and subsequent withdraw/repay attempts all return `MATH_OVERFLOW` [12](#0-11) .

### Impact Explanation
This is a permanent freeze of user funds and market functionality:

- suppliers cannot withdraw;
- borrowers cannot repay;
- liquidators cannot liquidate;
- new borrows, supplies, flash operations, revenue claims, bad-debt processing, and recapitalization all hit the same accrual panic;
- `update_indexes` itself cannot advance the stuck market.

The issue is not a fail-closed validation error on a malformed call. The market becomes permanently unable to operate even for valid calls because `last_timestamp` is not committed when the overflowing accrual panics.

### Likelihood Explanation
The trigger requires a market whose scaled debt value approaches the `i128` `Ray` ceiling while interest continues to compound. The in-tree reproduction constructs this state using only normal operations: a very large high-decimal supply, sufficient collateral, a 98%-utilization borrow, lifted caps, disabled max-utilization, and repeated permissionless `update_indexes` calls [13](#0-12) .

No privileged entrypoint is needed to trigger the final failure: `update_indexes` requires caller authorization but is public [14](#0-13) . Creating the initial whale market depends on deployed market parameters, oracle-supported collateral, liquidity, and configured caps being large enough; those are economic/configuration prerequisites rather than privileged exploit actions.

### Recommendation
Bound the scaled-debt value before multiplying, rather than relying only on `MAX_BORROW_INDEX_RAY`.

A robust fix should:

1. Compute `new_borrow_index` against a limit that accounts for `borrowed`, or check `borrowed <= i128::MAX / factor` before evaluating `borrowed * new_borrow_index`.
2. On overflow, clamp `new_total_debt` to `i128::MAX` or otherwise define an explicit saturation invariant instead of panicking.
3. Ensure `accrue_step` remains total for all representable `(borrowed, index)` pairs.
4. Add regression coverage based on `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` showing that `update_indexes`, `withdraw`, `repay`, and `liquidate` continue to execute after reaching the value ceiling.

### Proof of Concept
Use the existing harness scenario:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();

lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        assert_contract_error(Err(e), errors::MATH_OVERFLOW);
        break;
    }
}

assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The stored borrow index remains below `MAX_BORROW_INDEX_RAY`, confirming that the panic comes from the unbounded scaled debt-value multiplication rather than an index-limit violation [15](#0-14) .

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

            years <= 40,
