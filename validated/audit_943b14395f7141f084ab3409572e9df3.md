### Title
Fraud/liveness detection is permanently disabled, making `Report::fraud_detected()` always return `false` regardless of scene content - (File: src/plans/fraud_check.rs)

### Summary
`N_FRAUD_CHECKS` is hardcoded to `0`, and every method that should populate fraud-check results (`fraud_checks`, `enabled_checks_from_config`, `feedback_messages`) returns an empty array. Since `fraud_detected()` reduces to `.any()` over an empty array, it is vacuously `false` for every signup, irrespective of what is captured (printed photo, screen replay, second face, etc.).

### Finding Description
`Report::fraud_checks()` is defined to always return `[]` because `N_FRAUD_CHECKS` is a compile-time constant set to `0`, with the comment "FOSS: This is set to 0 because we manually deleted all fraud checks" [1](#0-0) . `fraud_checks_strict()` maps over this empty array, so it also always evaluates to `[]` [2](#0-1) . `fraud_detected()` is implemented as `self.fraud_checks_strict().iter().any(|&v| v)`, which is vacuously `false` on an empty iterator [3](#0-2) . `FraudChecks::run()` simply constructs an empty `Report {}` regardless of pipeline input [4](#0-3) . This `Report` flows into `MasterPlan::do_signup`'s `detect_fraud` call, whose boolean result determines whether `signup_reason` is set to `SignupReason::Fraud` versus `SignupReason::Normal`, which in turn gates PCP building/uploading and user enrollment [5](#0-4) . Because `fraud_detected()` can never be `true`, this path is unconditionally treated as non-fraudulent, and enrollment/PCP upload proceeds for any physical presentation.

### Impact Explanation
This disables the "fail-closed" liveness/fraud invariant described in the code's own docstring ("If fraud data are missing, we assume fraud is detected") [6](#0-5) , but the implementation never fails closed because there is no data to be "missing" from — the check array is empty by construction. Any unprivileged person presenting a printed photo, replayed video, or someone else's face to the Orb during a normal signup will have `fraud_detected() == false`, allowing capture, encryption, and upload of biometric data (iris/face images, iris codes) under a fraudulent signup context, and enrollment to proceed as if it were a legitimate live biometric capture.

### Likelihood Explanation
No special privileges are required — a normal, unprivileged signup session triggers `FraudChecks::new` → `FraudChecks::run` → `Report {}` → `fraud_detected()` deterministically for every signup, so this is 100% reproducible with any physical presentation, not tied to a specific attack scene.

### Recommendation
Restore actual fraud/liveness checks (or reintroduce checks with `N_FRAUD_CHECKS > 0`) so `fraud_checks()` reflects real detector outputs. At minimum, if fraud checks are intentionally absent in this build variant, `fraud_detected()` should not silently default to `false`; it should either fail closed (treat "no checks configured" as fraud-suspect) or the caller in `MasterPlan::do_signup` should not rely on this signal as an authoritative liveness/fraud gate for enrollment and PCP upload decisions.

### Proof of Concept
Unit test in `src/plans/fraud_check.rs`:
```rust
#[test]
fn fraud_detected_is_always_false() {
    let report = Report::default();
    assert!(!report.fraud_detected());
}
```
Property/invariant test: for any `FraudChecks::run()` invocation (regardless of the `biometric_pipeline::Pipeline` passed to `FraudChecks::new`), assert the resulting `Report::fraud_detected()` is always `false`, demonstrating that no captured scene — however fraudulent — can ever set it to `true`.
