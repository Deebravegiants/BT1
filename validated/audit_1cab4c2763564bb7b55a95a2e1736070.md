### Title
Webhook `shop-domain` header (and `topic`/`webhook-id`/`api-version` headers) are trusted for tenant identification but are **not covered by the HMAC signature** - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the authoritative tenant identifier. Because the HMAC only signs the body, the `shop` value that the handler uses to key its per-tenant logic is unauthenticated attacker-controlled input, exactly matching the "field acted on but not covered by the HMAC" bug class from the report (the vault contract trusted the group-position assumption instead of verifying the actual `OnCompletion`, letting an attacker substitute a different, unverified execution path).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over exactly that signable string and compares it to the `hmac-sha256` header value: [2](#0-1) 

`Registry.process` treats HMAC success as full authentication of the request, then immediately builds `WebhookMetadata` using `request.shop` (i.e., the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header) with no additional validation such as `Utils::ShopValidator.sanitize!`: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

The identity binding the gem implicitly promises is: `HMAC-valid request ⇒ shop header == the tenant that Shopify actually generated this payload for`. In reality the equality that holds is only `HMAC-valid request ⇒ body bytes are unmodified`; the `shop` header is disjoint from what is verified. Any party who can obtain one genuine, HMAC-signed webhook delivery (e.g., a merchant who installed the app receiving webhooks for their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the `shopify-shop-domain` header. `Registry.process` will pass HMAC validation (because the body/HMAC pair is untouched) and dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any app logic keyed on that field (looking up/updating per-tenant records, provisioning, deauthorization flows such as `shop/redact` or `app/uninstalled`, billing state, etc.) will then act against the wrong tenant.

This mirrors the report's root cause precisely: the contract assumed a structural property (group position / "first tx is app-vault approval") was sufficient proof of authorization, when the actual verified property (HMAC over the group's approval program) did not cover the bypassable dimension (`OnCompletion`/clear-state). Here, the gem assumes "HMAC valid" is sufficient proof that the whole webhook envelope (including `shop`) is authentic, when the HMAC only covers the JSON body.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged webhook sender who legitimately receives at least one signed webhook for their own store can cause the app to process that payload under an arbitrary victim shop's identity, all with a request that passes the gem's own signature check. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (session/token lookup, per-shop metafield writes, `shop/redact`/uninstall side effects), this can lead to cross-tenant state corruption or triggering of privileged per-tenant actions for a shop the attacker does not own — matching the "Critical: cross-tenant access" impact tier.

### Likelihood Explanation
Requires the attacker to have legitimately received (or be able to trigger) at least one genuine signed webhook delivery for a shop under their control — realistic for any developer/merchant who can install the app being targeted (a webhook subscription is created automatically for every installing shop) and then replay it with a forged header at the same public HTTP endpoint. No access to `api_secret_key`, tokens, or TLS interception is needed. The gem itself performs no cross-check between the signed body's shop/order identifiers and the `shop-domain` header, so exploitability depends only on whether the host app trusts `WebhookMetadata#shop` without independent verification — which is the documented, expected usage pattern shown in this gem's own webhook examples.

### Recommendation
- Short term: Document prominently that `WebhookMetadata#shop` (and `topic`/`webhook_id`) are **not authenticated by the HMAC** and must never be trusted as a tenant identifier on their own; require host apps to cross-check `shop` against an independently known active session/shop record before acting.
- Long term: Extend `Utils::VerifiableQuery`/`HmacValidator` (or add a webhook-specific validator) so that the signable string incorporates the header fields the app relies on for authorization (at minimum `shop`), or require callers to pass an expected shop and fail closed if it doesn't match a previously established relationship, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a genuine webhook, e.g. `orders/create`, to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of body>`
   - body: `{"id": 1, ...}`
2. Attacker captures this exact HTTP request (body + `x-shopify-hmac-sha256` unchanged).
3. Attacker resends the identical body/HMAC to the same webhook endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the unmodified HMAC: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and any app logic keyed on `data.shop` now executes as if this were a genuine event from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
