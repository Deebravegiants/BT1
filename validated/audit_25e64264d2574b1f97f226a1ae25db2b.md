### Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks proves nothing about the `shop`, `topic`, or `webhook_id` headers. `Registry.process` nonetheless takes `request.shop` straight from the unauthenticated header and hands it to the app's handler as the tenant identifier, breaking the binding `hmac_signed_bytes == bytes_acted_on`.

### Finding Description
`Request#to_signable_string` is defined as just `@raw_body` [1](#0-0) , and `hmac`/`shop`/`topic`/`webhook_id` are all pulled independently from HTTP headers with no cryptographic relationship to each other [2](#0-1) .

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header [3](#0-2) . Because `to_signable_string` is only the body, this check proves the body bytes came from Shopify (using the app's shared `client_secret`), but it proves nothing about which shop header accompanied that body.

`Registry.process` uses this validation as the sole gate, then immediately trusts `request.shop` as the tenant key passed into the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because the same `api_secret_key`/`client_secret` is shared by the app across every merchant that installs it, any tenant that legitimately receives a webhook (with a valid HMAC over some body) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC still validates (it only checks the body), yet `Registry.process` reports the forged shop as the origin of that body to the handler. This breaks the identity binding: `shop_the_HMAC_authenticates == shop_the_gem_acts_on` does not hold — the left side is undefined/empty, the right side is attacker-chosen.

### Impact Explanation
This allows cross-tenant confusion: an attacker who controls one legitimate shop installation can cause the gem to hand an app's webhook handler a payload it will process as belonging to a different (victim) shop, since `Registry` performs no binding between the authenticated body and the shop header before dispatching. Any app that uses `WebhookMetadata#shop` to select the shop's session/access token or to write tenant-scoped data is exposed to cross-tenant data injection/confusion, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the ability to send HTTP requests to the app's public webhook endpoint (unprivileged internet capability) plus possession of one genuine, previously-delivered webhook body/HMAC pair for the same app (obtainable by installing the app on an attacker-controlled shop and capturing its own webhooks). No access token, `api_secret_key`, or victim credentials are needed — only header manipulation on replay.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the `shop-domain` header to the HMAC-validated body before it is trusted — e.g., include the shop header in `to_signable_string`, or require the caller to independently verify `request.shop` against a known/registered shop before invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a real webhook: body `B`, header `x-shopify-hmac-sha256: H` where `H = HMAC(client_secret, B)`.
2. Replay the identical request to the app's webhook endpoint, keeping body `B` and header `H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) .
4. `Registry.process` invokes `handler.handle` with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` [7](#0-6) , causing the app to act on attacker-supplied data under the victim shop's identity.
