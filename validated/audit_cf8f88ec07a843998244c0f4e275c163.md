### Title
Unchecked subtraction panic in `calc_take_pnl` permanently freezes Deposit/Withdraw due to attacker-controlled vault donation - (File: program/src/processor.rs)

### Summary
The CVE-2021-40944 hint describes a null-pointer dereference reachable with attacker-controlled input that crashes the target process (DoS). The closest reachable analog in this Solana program is a set of unchecked, panicking arithmetic operations (`.unwrap()` on `checked_sub`/`checked_mul`/`checked_div`) in `Processor::calc_take_pnl`, which is invoked from the unprivileged, user-reachable `Deposit` and `Withdraw` instructions. Because vault token balances (used to compute `x1`/`y1`) can be altered by anyone via a direct SPL token transfer into the AMM's coin/PC vault (a "donation"), without going through the AMM program at all, an attacker can distort the pool's coin/PC ratio relative to the stored `target_orders.calc_pnl_x`/`calc_pnl_y` baseline enough to make the assumption `x1 >= x2` / `y1 >= y2` false, triggering an underflow panic that aborts the transaction.

### Finding Description
`calc_take_pnl` computes a "pnl-adjusted" `x2`/`y2` pair from the pool's current normalized reserves (`x1`, `y1`) and the previously stored baseline (`target.calc_pnl_x`, `target.calc_pnl_y`), then unconditionally computes: [1](#0-0) 
`diff_x = x1 - x2` and `diff_y = y1 - y2` are computed with `.checked_sub(...).unwrap()`, which panics (aborts the instruction) if `x2 > x1` or `y2 > y1`. This is only safe if the AMM's own invariant guarantees `x2 <= x1` and `y2 <= y1` for every possible vault state, but the vault balances feeding `x1`/`y1` are read directly from the SPL token vault accounts: [2](#0-1) [3](#0-2) 
Any unprivileged party can call `spl_token::instruction::transfer` to send extra tokens directly into `amm_coin_vault` or `amm_pc_vault` — these are ordinary SPL token accounts, not gated by any AMM-specific authority for deposits. This directly changes `pc_amount`/`coin_amount` seen by `calc_total_without_take_pnl_no_orderbook`, and therefore `x1`/`y1`, without any corresponding update to `target_orders.calc_pnl_x`/`calc_pnl_y`. A sufficiently skewed donation (e.g., a large one-sided transfer into only one vault) changes the pool's current price ratio enough that the `sqrt(last_k * current_price)`-derived `x2`/`y2` value can exceed the corresponding `x1`/`y1`, causing the `.unwrap()` on `checked_sub` to panic.

`calc_take_pnl` is reachable from:
- `process_deposit` (unprivileged, any depositor) — [4](#0-3) 
- `process_withdraw` (unprivileged, any LP token holder) unless `amm.status == WithdrawOnly` — [5](#0-4) 

Once the underflow condition is met given the vaults' post-donation balances, **every** subsequent call to `Deposit` or `Withdraw` recomputes the same `x1`/`y1` from the same (now-corrupted) vault balances and baseline, and will panic identically, since nothing in the instruction path recovers or resets `target_orders.calc_pnl_x`/`calc_pnl_y` on failure (the transaction aborts before any state write). This makes the condition persistent rather than a one-off failure.

### Impact Explanation
A successful trigger permanently blocks the unprivileged `Deposit` and `Withdraw` instructions for the affected pool, denying liquidity providers the ability to withdraw their principal or add liquidity — a permanent freezing of LP funds. This satisfies the required impact bar (permanent freezing of user/LP funds) via a purely on-chain, attacker-chosen-data path (a plain SPL token transfer to a public vault account), not requiring any privileged signer.

### Likelihood Explanation
Likelihood is Medium: triggering requires the attacker to donate tokens to a vault in a ratio-distorting way relative to the pool's stored `calc_pnl_x`/`calc_pnl_y` baseline, and the exact magnitude needed depends on pool state (recent trading activity, decimals, fee parameters). It does not require any special privilege or non-default build — only a standard SPL token transfer plus a subsequent call to `Deposit`/`Withdraw` (which can be the attacker's own transaction, or any other user's, since the corrupted state affects all callers equally).

### Recommendation
Replace the panicking `.checked_sub(...).unwrap()` calls in `calc_take_pnl` (and the analogous `checked_mul`/`checked_div` `.unwrap()`s in that function) with saturating/clamped arithmetic or explicit error returns (`ok_or(AmmError::CalcPnlError)?`) so that an adverse vault/state ratio results in a graceful `ProgramError` rather than a panic, and consider clamping `x2`/`y2` to `min(x2, x1)` / `min(y2, y1)` before subtracting so the pnl-taking mechanism degrades safely instead of bricking `Deposit`/`Withdraw`.

### Proof of Concept
1. Create/observe an existing Raydium pool with vaults `amm_coin_vault` and `amm_pc_vault`, and note `target_orders.calc_pnl_x`/`calc_pnl_y` (baseline reserves at last pnl-take).
2. Attacker, using an unprivileged wallet holding the pool's coin or PC mint, issues a standard `spl_token::instruction::transfer` sending a large amount of tokens directly into `amm_pc_vault` (or `amm_coin_vault`), skewing the pc:coin ratio far from the ratio implied by `calc_pnl_x`/`calc_pnl_y`.
3. Attacker (or anyone) then calls `Withdraw` (or `Deposit`) on the pool. `process_withdraw`/`process_deposit` recompute `x1`,`y1` from the now-skewed vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook` and pass them into `Processor::calc_take_pnl`.
4. Inside `calc_take_pnl`, the computed `x2` (or `y2`) from `sqrt(last_k * current_price)` exceeds `x1` (or `y1`), so `x1.checked_sub(x2).unwrap()` panics, aborting the transaction with a Rust panic instead of a controlled `ProgramError`.
5. Because the vault balances and `target_orders` state remain unchanged after the aborted transaction, every subsequent `Deposit`/`Withdraw` call reproduces the identical panic, permanently denying withdrawals/deposits for the pool until the vault ratio is somehow restored (which is not possible through any exposed instruction).

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
