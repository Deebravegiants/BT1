### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies an inbound webhook by validating an HMAC over the request's raw body only, then forwards the caller-supplied `shop-domain` header — completely unauthenticated by that same HMAC — to the app's handler as trusted tenant metadata. Because the signing secret (`api_secret_key`) is shared across *every* shop that has installed the app, any unprivileged merchant who installs the app on their own store can capture a legitimately Shopify-signed webhook body/HMAC pair and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a webhook event the host app will process as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor pulls the tenant identity purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC solely against `to_signable_string` (i.e., the body bytes), never the headers: [3](#0-2) 

`Registry.process` gates on that body-only HMAC check and then constructs `WebhookMetadata` using the unauthenticated `request.shop`, handing it directly to the app's handler as the tenant identity: [4](#0-3) 

The gem's own documentation instructs developers to treat `data.shop` as verified, trustworthy tenant data ("This will verify the request did indeed come from Shopify... `shop`, `String` - The shop domain of the webhook"), reinforcing that host apps are expected to rely on this value as authenticated: [5](#0-4) [6](#0-5) 

**Identity binding broken (as an equality):** the gem asserts `hmac_verified(raw_body) == true` implies `shop-domain header == authentic tenant of that body`, but the actual guarantee is only `hmac_verified(raw_body) == true` implies `raw_body was HMAC-signed with this app's shared api_secret_key` — nothing more. Since `api_secret_key` is the same across all shops that installed the app, any shop's genuine webhook body/HMAC pair remains valid regardless of which `shop-domain` header accompanies it.

**Attacker sequence:**
1. Attacker (an unprivileged internet user) installs the target app on their own free/dev Shopify store — no special privilege required beyond normal app installation.
2. Attacker triggers a webhook event on their own store (e.g., `orders/create`) and captures the exact `raw_body` and `x-shopify-hmac-sha256` value Shopify sent to the app's public webhook endpoint.
3. Attacker crafts a new POST to the app's webhook endpoint using the same `raw_body` and `hmac` value, but sets `x-shopify-shop-domain` to the victim's `victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (body bytes/HMAC are genuinely valid, since both were signed by the same shared secret). `Registry.process` calls the handler with `data.shop == "victim-shop.myshopify.com"`.
5. Any host logic keyed on `data.shop` (session/access-token lookup, order/customer record creation, uninstall/GDPR triggers, audit logs, etc.) now operates under the victim's tenant identity using attacker-supplied body content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook ingestion: an unprivileged installer of the app (attacker) can forge webhook events that are processed as belonging to any other merchant/shop using the same app, without needing that victim's access token, credentials, or any privileged access. Depending on what data the handler acts on (creating fake orders/customers records, invoking session lookups, triggering downstream side effects attributed to the victim shop), this is a cross-tenant access/data-integrity issue directly enabled by the gem's design of exposing an unauthenticated `shop` field as if it were verified.

### Likelihood Explanation
High likelihood for any app that follows the gem's documented usage pattern exactly as shown in `docs/usage/webhooks.md` (trusting `data.shop`). The only prerequisite is that the attacker can install the app on a store they control (a normal, low-barrier action for any Shopify app that is publicly listed or installable), and that they can send arbitrary HTTP POSTs with attacker-chosen headers to the app's public webhook route (which by definition must be internet-reachable to receive Shopify webhooks).

### Recommendation
- Do not rely on the `shop-domain` header as authenticated data. Either:
  - Include the shop domain in the HMAC-signed payload verification path (e.g., compare `request.shop` against the shop registered for the specific webhook subscription/topic looked up independently), or
  - Look up/derive the shop identity from a source that is itself authenticated (e.g., cross-check against Shopify's `X-Shopify-Webhook-Id` via an API call, or maintain a per-shop webhook secret if Shopify's API supports it) rather than trusting the header value directly.
- Update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by HMAC verification and must not be trusted for authorization decisions without additional validation.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker-shop.myshopify.com"
#    and triggers e.g. orders/create, capturing what Shopify sent:
raw_body = '{"id":1,"note":"legit order from attacker shop"}'
hmac_b64 = "captured-valid-x-shopify-hmac-sha256-value"

# 2. Attacker replays it to the target app's public webhook endpoint,
#    but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,       # still valid: same api_secret_key for all shops
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. HMAC validation passes because it only checks raw_body against api_secret_key
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process happily calls the handler attributing the event to the victim shop
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ...))
``` [4](#0-3)
