### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (merchant identity) is read from a separate, unsigned header. `Registry.process` validates the HMAC and then forwards the attacker-controlled `shop` value directly to the app's webhook handler as trusted tenant metadata.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and the HMAC is verified against that same raw body via `HmacValidator.validate` [2](#0-1) . The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header and is never included in the signed bytes: [3](#0-2) .

`Registry.process` validates the HMAC and, on success, immediately passes `request.shop` (the unauthenticated header value) into `WebhookMetadata` given to the app's handler as the tenant identity, alongside the (correctly signed) body: [4](#0-3) .

The equality that should hold is: `shop bytes verified by HMAC == shop bytes handed to the handler as tenant identity`. In fact: the HMAC only verifies `raw_body` bytes; the `shop` value delivered to the handler comes from a header outside that signature. Any party capable of producing a validly-signed body/HMAC pair for the app's shared `api_secret_key` — most plausibly a merchant who has installed the app themselves and can capture one of their own legitimate webhook deliveries (body + HMAC are only shop-independent function of body content and the app's single, non-per-shop secret) — can replay that exact body+HMAC pair while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim shop. `Registry.process` will accept the HMAC (it only checks the body) and dispatch the payload to the handler tagged with the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism exists to enforce: hosts that key persistence, session lookups, or business logic off `WebhookMetadata#shop` (as the gem's own webhook flow encourages, since `shop` is the only per-tenant field exposed by `Request`/`WebhookMetadata`) can be made to apply attacker-supplied webhook data to another merchant's tenant/shop record, i.e. cross-tenant data injection/spoofing without any credential belonging to the victim shop. This matches the "cross-tenant access" class of Critical impact.

### Likelihood Explanation
Requires the attacker to be a legitimate but unprivileged installer of the app (any merchant can install a public app) capable of receiving genuine webhooks for their own shop and replaying the captured body+HMAC with a different `shop-domain` header value to the app's webhook endpoint. No secret material beyond what a normal, unprivileged tenant already has access to (their own webhook deliveries) is needed, and the header substitution is a simple HTTP replay — no cryptography to break.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise independently authenticate the tenant identity before dispatch — e.g., require the caller to supply/derive the expected shop out-of-band (such as from the route or a previously established session) and reject the request if it disagrees with the header, rather than trusting the unsigned `shop-domain` header as-is in `Registry.process`.

### Proof of Concept
1. App installs on `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (where `H = HMAC-SHA256(api_secret_key, B)`), `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H})` is constructed [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `B` [6](#0-5) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)` [7](#0-6) , so the app processes attacker-controlled data as belonging to the victim shop.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
```
