### Title
Webhook Handler Trusts Unauthenticated `shop` Header Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook HMAC signature validated by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body, never the `shop-domain` header. That header is read verbatim and handed to the app's handler as the authoritative tenant identifier, breaking the binding `shop (verified by HMAC) == shop (acted on by handler)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature against `verifiable_query.to_signable_string` (i.e., the body only) — it never incorporates the `shop` field into what is signed or verified: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC and then dispatches `request.shop` directly into `WebhookMetadata`, which is passed to the app's handler as the trusted tenant/shop context: [5](#0-4) 

Because the HMAC is computed only over `@raw_body`, the equality that should hold — "the shop bound by the HMAC == the shop the handler acts on" — never actually holds: the shop value used by the handler is taken from an unauthenticated header, while the HMAC only authenticates that *some* valid body was sent by someone in possession of `api_secret_key` (i.e. Shopify, for any of that Shopify partner's shops using the same app credentials). This gem provides no mechanism to bind headers to the signature; the entire header set including `shop-domain`, `topic`, `api-version`, and `webhook-id` is unsigned metadata.

### Impact Explanation
A legitimate webhook delivery for Shop A (valid HMAC over some body B, since the app's single `client_secret` is shared across all shops using that app) can be replayed with the `shop-domain` header rewritten to Shop B. `Utils::HmacValidator.validate` will still pass because it only checks the body signature, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop == "Shop B"` even though the payload actually originated for Shop A. Any app that uses `request.shop` from the metadata to select the tenant's session/data store (which is the documented, expected usage of `WebhookMetadata`) will attribute Shop A's webhook payload to Shop B's tenant context — a cross-tenant data confusion issue reachable by any party who can capture or otherwise obtain one valid `(body, hmac)` pair for the shared app secret and resend it with a different shop header.

### Likelihood Explanation
Exploitation requires only network access to the app's webhook endpoint and one previously observed valid `(body, hmac)` pair for the app (obtainable e.g. by installing the app on an attacker-controlled store, or by intercepting/replaying a webhook not protected by additional transport-level binding). No `api_secret_key`, access token, or privileged account is required — the attacker never needs the secret, only a captured signature/body pair and the ability to alter the plaintext `shop-domain` header. Since Shopify's own HMAC scheme (as consumed by this gem) does not bind `shop` into the signature, and this gem performs no supplementary origin/tenant check, the likelihood is high for any app relying on `WebhookMetadata#shop` for tenant scoping without independent verification.

### Recommendation
- Document/enforce that `shop` from `WebhookMetadata` must never be trusted as tenant-authoritative without independently confirming that shop is one the app currently has an active session for, and reject processing otherwise.
- Preferably, extend `VerifiableQuery`/`HmacValidator` (or a webhook-specific validator) to include the `shop-domain` (and other identity-relevant headers) in the signable string so the HMAC binds the full identity context, not just the body.
- At minimum, add a check in `Registry.process` that rejects requests whose `shop` cannot be correlated to a known, previously-installed store for the topic before invoking the handler.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` using the same Shopify app (`client_id`/`client_secret`) as the victim tenant.
2. Attacker triggers any webhook event on their own shop and captures the resulting `(raw_body, x-shopify-hmac-sha256)` pair — this HMAC is valid because it was legitimately computed by Shopify using the shared `api_secret_key`.
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` returns `true`.
5. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's raw body>, ...)` and invokes the app's handler, which — if it uses `data.shop` to select the tenant context, as documented — processes attacker-controlled webhook data under the victim shop's tenant.
