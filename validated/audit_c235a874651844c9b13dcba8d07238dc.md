Based on my investigation, the strongest analog to the "missing whenNotPaused" pattern is `PATCH /v2/resume/:runID`, which is deliberately routed outside any authentication middleware while every other state-mutating endpoint in the router requires session/token/EI auth plus a role check.

### Title
Unauthenticated pipeline-run resume endpoint allows any unprivileged caller to inject arbitrary task results - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
`v2Routes` mounts `PATCH /v2/resume/:runID` on `unauthedv2`, a route group created with no auth middleware at all, whereas every other mutating v2 endpoint sits under `authv2`/`userOrEI` and is wrapped with `auth.Authenticate(...)` plus `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`.

### Finding Description
`v2Routes` creates two groups: `unauthedv2 := r.Group("/v2")` with `unauthedv2.PATCH("/resume/:runID", prc.Resume)`, and `authv2 := r.Group("/v2", auth.Authenticate(...))` for everything else [1](#0-0) . All other mutation-capable routes (jobs, keys, transfers, bridges, external initiators, replay, etc.) are explicitly wrapped in `auth.Authenticate` plus a role gate (`RequiresRunRole`, `RequiresEditRole`, or `RequiresAdminRole`) as seen throughout the same function [2](#0-1) [3](#0-2) . Even the job-run creation endpoint under `userOrEI` requires `RequiresRunRole` [4](#0-3) .

`PipelineRunsController.Resume` parses the `runID` as a UUID, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and calls `prc.App.ResumeJobV2(ctx, taskID, result)` directly — with zero authentication or ownership check on the caller [5](#0-4) . The audit log entry name `audit.UnauthedRunResumed` [6](#0-5)  confirms this route is intentionally designed to be reachable without authentication (likely to support asynchronous/webhook-style external task callbacks resuming a specific pending pipeline task by its UUID). However, the security of that design relies entirely on the `runID` UUID being unguessable and single-use; there's no rate limiting comparable to other unauthenticated endpoints, and no additional secret/token check tying the resume call to the specific bridge invocation that spawned the task.

This mirrors the LensHub bug class: most external mutating entry points enforce a protective check (auth/role there; auth+role here), but one function was carved out without that check, entirely by design intention, yet it silently reintroduces a broad unauthenticated write path (arbitrary task-result injection) if the assumption of UUID secrecy/rate-limiting is violated.

### Impact Explanation
If a `runID` (task UUID) is disclosed or brute-forced (e.g., via logs, error messages, or a predictable/leaked source), any unauthenticated network client can call `PATCH /v2/resume/:id` to inject an arbitrary `pipeline.ResumeRequest` result into a running pipeline task, potentially forcing an in-flight job run to complete with attacker-controlled data (e.g., a fabricated external adapter response), or repeatedly hitting the endpoint to interfere with legitimate resumes. Because there is no role or session gate, this endpoint can be hit by anyone with network access to the node's API, unlike all comparable mutation endpoints which require at least the `run` role.

### Likelihood Explanation
Likelihood depends on whether the UUID `runID` for a suspended task can be discovered by an unprivileged actor (e.g. via a bridge/external-adapter-visible callback URL, logs, or error responses) — this is the same "unguessable ID as sole protection" pattern often exploited in bug bounty findings. Given the endpoint is explicitly unauthenticated by design (webhook-style external callback), it is the single most likely edge to be probed by an external attacker with no credentials, and the absence of any secondary secret (e.g., a per-run token or HMAC) increases the risk relative to the rest of the node's admin-gated surface.

### Recommendation
Require a corresponding secret/token bound to the resume request (analogous to bridge outgoing tokens/external-initiator secrets already used elsewhere in the codebase, e.g. `bridges.ExternalInitiator.OutgoingSecret`/`OutgoingToken` [7](#0-6) ), or otherwise validate the caller against the task's expected external adapter callback before invoking `App.ResumeJobV2`. At minimum, rate-limit this route distinctly and ensure `runID`s are never leaked in logs/errors, since it is currently the only mutating v2 endpoint reachable with zero authentication.

### Proof of Concept
1. Observe that `unauthedv2.PATCH("/resume/:runID", prc.Resume)` is registered without any `auth.Authenticate` middleware [8](#0-7) .
2. Obtain or guess a valid task UUID for a currently suspended pipeline run (e.g., leaked via an external adapter's callback configuration, logs, or timing/enumeration).
3. Send `PATCH /v2/resume/<taskUUID>` with a crafted JSON body matching `pipeline.ResumeRequest` from any unauthenticated client.
4. `PipelineRunsController.Resume` decodes the body and calls `App.ResumeJobV2` with attacker-supplied `result`, completing the pipeline task with attacker-controlled data [9](#0-8) .

func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
