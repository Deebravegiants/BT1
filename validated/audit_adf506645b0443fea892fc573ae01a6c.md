Audit Report

## Title
Time-of-check/time-of-use race in gateway JWT replay-protection allows single-use trigger token to be reused - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` is intended to enforce that each JWT (identified by `jti`) authorizes exactly one HTTP-triggered workflow execution, but the replay check (`isReplay`) and the state update (`recordUsage`) are two separate, non-atomic critical sections separated by unrelated verification logic. This allows two concurrent requests bearing the same JWT to both pass the replay check before either records usage, letting a single-use token authorize multiple executions.

## Finding Description
`jwtReplayCache` guards its map with a `sync.RWMutex`, but `isReplay` takes an `RLock`/`RUnlock` and returns, and `recordUsage` separately takes a `Lock`/`Unlock` later — these are not combined into one atomic check-and-set operation: [1](#0-0) 

`Authorize` calls `h.jwtCache.isReplay(claims.ID)` first, then performs unrelated work (authorized-key map lookup, signer authorization check), and only afterward calls `h.jwtCache.recordUsage(claims.ID)`: [2](#0-1) 

Because the check and the record are not performed under a single lock, two goroutines invoking `Authorize` concurrently with the same JWT can both observe `exists == false` from `isReplay` before either calls `recordUsage`, so both proceed past the replay guard and both receive a valid `*gateway.AuthorizedKey`. The codebase's own Vault package demonstrates the correct pattern for exactly this problem — `RequestReplayGuard.CheckAndRecord` performs the lookup and the write under one `Lock`: [3](#0-2) 

The existing test only exercises the sequential (non-concurrent) rejection path, so it does not detect this race: [4](#0-3) 

## Impact Explanation
This defeats the single-use guarantee of gateway trigger JWTs. An unprivileged client that can send two near-simultaneous HTTP trigger requests with the same signed JWT can trigger `MethodWorkflowExecute` twice (or more) from one authorization, causing duplicate workflow runs, DON resource exhaustion, or duplicated on-chain/off-chain side effects. This maps to the in-scope "unauthorized job run" / gateway request impersonation-adjacent impact category since it defeats a security control meant to bound execution to a single authorized invocation per token.

## Likelihood Explanation
The race window is narrow but requires no special privilege — only the ability to send two concurrent requests with a previously obtained valid JWT, which is trivially scriptable (e.g., two parallel HTTP calls). Likelihood is moderate: exploitation depends on timing but not on any elevated access, and can be repeated at will by any client holding a valid token.

## Recommendation
Combine the check and the record into a single atomic operation under one write lock, following the pattern already used in `RequestReplayGuard.CheckAndRecord`:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false
    }
    cache.cache[jti] = time.Now()
    return true
}
```
Call this single method from `Authorize` immediately after verifying `claims.ID`, and remove the separate `isReplay`/`recordUsage` calls so there is no window between check and write.

## Proof of Concept
1. Generate one valid signed JWT for `MethodWorkflowExecute` with a given `jti`, authorized for a test workflow (as in the existing test setup at `workflow_metadata_handler_test.go` lines 1193-1217).
2. Launch two goroutines that concurrently call `handler.Authorize(workflowID, tokenString, req)` with the same token.
3. Add a synchronization point (e.g., a channel or `sync.WaitGroup` with both goroutines calling `isReplay` before either calls `recordUsage`, which can be forced deterministically by inserting a brief sleep between the two operations in a test build, or observed via `-race`/repeated runs) to demonstrate both calls return `err == nil` and a non-nil `*gateway.AuthorizedKey`, proving the same token authorized two executions.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
