### Title
Webhook shop-domain, topic and webhook-id are trusted but never covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw HTTP body only, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers and are never part of the HMAC-covered payload. `Registry.process` verifies only the body's HMAC, then hands the unauthenticated header values directly to the merchant's handler.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that string is defined as `@raw_body` alone [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are not folded into the signed string at all [2](#0-1) . `Registry.process` validates the HMAC and, on success, immediately builds `WebhookMetadata` from these unauthenticated fields and dispatches it to the app's handler without any further binding check between the signed body and the claimed shop/topic: [3](#0-2) .

The broken binding is: `hmac(raw_body) == valid` should imply `shop header == shop that produced raw_body`, but the code only proves `hmac(raw_body) == valid`; the `shop` (and `topic`/`webhook_id`) values used by the handler are never part of what was authenticated. Since `Context.api_secret_key` is a single value shared for all shops that install one Shopify app, any request whose body/HMAC pair was legitimately produced for *some* installed shop will pass validation in `Registry.process` regardless of which shop's identifier is placed in the header, because the header is not covered by the signature.

### Impact Explanation
This breaks the tenant identity binding between the authenticated payload and the shop context that the merchant handler subsequently trusts (`WebhookMetadata.shop`). An attacker who can obtain one valid `(raw_body, hmac)` pair for the app's secret (e.g., by operating a shop that has the app installed and observing/replaying its own legitimate webhook deliveries) can re-submit the same body with a forged `shopify-shop-domain` header naming a different, victim tenant. `Registry.process` will validate the HMAC successfully and route the (unrelated) body content into the victim's tenant handling path, causing cross-tenant data confusion/corruption in host applications that trust `WebhookMetadata.shop` as the tenant key (a pattern this gem's own `WebhookHandler`/`WebhookMetadata` API explicitly encourages). This matches the report's bug class: a field acted upon (`shop`) that is not covered by the integrity check (`HMAC`).

### Likelihood Explanation
Requires the attacker to control (or previously capture traffic from) at least one shop with the target app installed, which is realistic for any public/free-install Shopify app, and does not require possession of `api_secret_key` or an access token — only replay of a webhook payload the attacker already legitimately received for their own store, with a modified header value.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed data (or otherwise cryptographically bind the header claims to the signed body), and have `Registry.process` reject requests where the header-derived identifiers are not verifiably tied to the signature, rather than trusting raw headers post-validation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for `Context.api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B`/`H` pair to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (`request.to_signable_string`), matching `H` — validation succeeds [1](#0-0) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"` and dispatched to the handler [4](#0-3) , causing the host app to process attacker-controlled body content under the victim shop's identity.
