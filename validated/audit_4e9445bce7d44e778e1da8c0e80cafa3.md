### Title
Min-circuit Emporium path lets an attacker skip all authorization/accounting and drive `EmporiumUpgradeable.runAction` with `signerAddress == 0` to run arbitrary `approve()`/exfiltration ops - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` as public signals. This lets an attacker submit an `EmporiumStack` with `signerAddress == address(0)`, which makes `verifyWallet` skip signature verification entirely, and drive `EmporiumUpgradeable.runAction` to execute arbitrary low-level calls from the Emporium contract's identity while the balance-accounting loop iterates zero tokens and enforces nothing.

### Finding Description
The broken equality is: **assets Emporium can move/authorize in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**.

- `CircomDataBuilder.formInputForCircom` (contracts/CircomDataBuilder.sol:134-148) selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`.
- `formInputEmporiumMin` (contracts/CircomDataBuilder.sol:150-161) produces only 3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash`. It does not constrain `rootHashHinkal`, `inputNullifiers`, `outCommitments`, `amountChanges`, or `erc20TokenAddresses` in any circuit signal beyond what's baked into `calldataHash` — and since the token array is empty, none of these arrays exist to constrain anyway.
- `Hinkal.transact` → `_externalTransact` (contracts/Hinkal.sol:234-261) builds `deltaAmountChanges` from `circomData.erc20TokenAddresses` (empty), so no deposit into Emporium happens and no per-token bookkeeping array is populated.
- `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160) decodes an attacker-controlled `EmporiumStack` from `externalActionData.externalActionMetadata`, computes `balancesBefore`/`balancesAfter` over `circomData.erc20TokenAddresses` (length 0, so these arrays are empty and the loop at line 132 does nothing), then executes `stack.ops` — including `op.endpoint.call{value: op.value}(op.callData)` (line 112) — with no assertion tying the specific ops to any real value movement.
- `verifyWallet` (lines 302-349): if `stack.signerAddress == address(0)`, it returns immediately after marking the message used — no ECDSA check occurs. This path is presumably intended for cases where the caller (`msg.sender`, which is checked by `onlyAllowedRecipient`... actually `onlyAllowedRecipient` gates who can call `runAction`, not who authorized the ops) is trusted, but combined with the min-circuit path there is no cryptographic tie between the prover (any unprivileged attacker who can produce a valid Groth16 proof for the min circuit, which only proves knowledge of a Poseidon preimage for `emporiumMessage`) and the contents of `stack.ops`.
- Because `erc20TokenAddresses` is empty, the balance-accounting invariant in `runAction` (and in `Hinkal.transact`'s post-action balance-diff/slippage checks at lines 97-147) is vacuous — it iterates zero entries. Any op that does not change a tracked balance (e.g., calling `approve()` on some ERC20 token that Emporium holds tokens of, or that Emporium will later receive) is completely unaccounted for. An `approve()` call does not itself move balance, so even a full accounting loop over that token wouldn't catch it as a "loss" in the same transaction — the theft materializes later via `transferFrom`, in a follow-up transaction, from any balance Emporium is later found to be holding (residual dust, in-flight funds, or funds deposited by other users through the same allowed-recipient contract in adjacent operations).

Attacker's call: `Hinkal.transact` with `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: someToken, invokeWallet: false, value: 0, callData: approve(attacker, type(uint256).max)}]})`, and a proof for the min circuit proving only that `emporiumMessage == Poseidon(messageSeed)` for a self-chosen `messageSeed`.

Existing guards do not stop this:
- `performHinkalChecks` only checks `getHashedCalldata(circomData) == circomData.calldataHash` (calldata integrity, which the attacker self-computes correctly), relayer validity, `dimensionsCheck` (trivially satisfied with `tokenNumber == 0`), and `checkOnchainCreation` (loop over zero-length array, no-op).
- `verifyProof` only checks the min circuit's 3 signals, which say nothing about `stack.ops` content or `signerAddress`.
- `rootHashExists` only checks `rootHashHinkal`, unrelated to Emporium op authorization.
- No nullifiers are spent (`inputNullifiers` empty), so `insertNullifiers` is a no-op — the attacker spends nothing of their own.
- `onlyAllowedRecipient` only checks that the caller of `runAction` is the registered `Hinkal`/action router, not that the op's contents were authorized by a signer.

### Impact Explanation
This is a bypass of Emporium's op-authorization and balance-accounting invariants: an unprivileged attacker can, via the near-empty "Min" proof, make the Emporium contract execute arbitrary external calls (e.g., `approve()` granting the attacker an allowance over tokens Emporium holds/will hold) with zero economic accounting and no signature check. Any subsequent `transferFrom` drains funds sitting in or passing through Emporium — this is direct theft of protocol/relay/in-flight or other users' funds via calls the wallet/protocol never authorized, matching Critical ("direct theft of shielded or in-flight user funds") or at minimum High ("executing calls or moving assets a wallet owner or prover never authorised"). It's repeatable per transaction as long as Emporium holds or is about to hold any balance, and costs the attacker only gas plus proof generation for the trivial min circuit.

### Likelihood Explanation
Preconditions: Emporium contract must hold (or transiently hold) some token balance at the time of exploitation — this can happen via dust left from `handleOut`'s `balanceChange <= 0` skip, in-flight multi-step Emporium flows, or funds deposited by other users through the same allowed-recipient action in a composable/batched context. The attacker needs no special role: they can deploy the proof themselves (min circuit is public and only requires a Poseidon preimage), and craft `EmporiumStack`/`externalActionMetadata` freely since these are plain calldata fields hashed only for self-consistency, not signed by anyone. This is low-cost and fully repeatable.

### Recommendation
Do not allow `EmporiumUpgradeable.runAction` to be reached (or executed with attacker-supplied unsigned ops) via the min-circuit/empty-token path. Concretely:
- Require `stack.signerAddress != address(0)` (mandatory signature verification) whenever `erc20TokenAddresses.length == 0`, or disallow the min-circuit path entirely for Emporium actions that contain `ops`.
- Constrain `externalActionMetadata` (or a hash of `stack.ops`) as an actual public/private circuit signal in the min circuit, and/or tie `emporiumMessage` cryptographically to `_hashEmporiumOps(stack.ops)` so a valid min-proof cannot be replayed with attacker-chosen ops.
- Ensure Emporium never carries idle balances across transactions (sweep/zero-balance invariant), or add an explicit check that `runAction` cannot execute if `erc20TokenAddresses.length == 0` and `stack.ops.length > 0` with `signerAddress == address(0)`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium under `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund Emporium directly with e.g. 1000 `TestERC20` (simulating residual/in-flight balance) — assert `token.balanceOf(emporium) == 1000`.
3. As an unprivileged attacker EOA, build `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))})], maxFee: 0, deadline: 0, v:0, r:0, s:0}))`, all nullifier/commitment arrays empty, `calldataHash` set via `getHashedCalldata`.
4. Generate a valid Groth16 proof for `MainEVMCircuitMin` proving `emporiumMessage == Poseidon(messageSeed)` for attacker-chosen `messageSeed`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker — assert it succeeds (no revert), and `token.allowance(emporium, attacker) == type(uint256).max`.
6. Call `token.transferFrom(emporium, attacker, 1000)` — assert `token.balanceOf(attacker) == 1000` and `token.balanceOf(emporium) == 0`.
7. Assert equality violated: pre-tx invariant "Emporium balance moved == balancesBefore/After accounted amount" (accounted amount == 0 for token not in `erc20TokenAddresses`) vs. post-tx reality (1000 tokens later exfiltrated), confirming funds moved outside of any accounted `balanceChange`/`slippage` check.
