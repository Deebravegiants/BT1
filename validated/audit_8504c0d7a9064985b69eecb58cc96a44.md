### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers. These identity/tenant-attribution fields are never included in the signed payload, so the binding "HMAC-covered bytes == bytes used to identify the tenant" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors are all pulled from HTTP headers that are not part of the signable string: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string` (the raw body): [4](#0-3) 

`Registry.process` only calls this body-only HMAC check, and then builds the dispatched `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values: [1](#0-0) 

Because every shop that installs the app shares the same `api_secret_key` (the app's `client_secret`, not a per-shop secret), any tenant that has legitimately installed the app can capture a real, validly-signed webhook body+HMAC pair delivered to their own endpoint, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a different (victim) shop. The gem's own verification logic has no way to detect this, because the header values used to attribute the event to a tenant are never covered by the HMAC it checks.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended) to decide which tenant's records to create/update/delete in response to the webhook, an attacker-controlled shop can forge webhook events "from" an arbitrary victim shop, since the identity-binding equality `signed_bytes == tenant_identifying_bytes` is false. This is a cross-tenant data-integrity/confusion issue: the app will process attacker-supplied webhook payloads under a victim shop's identity, potentially triggering shop-scoped side effects (data writes, notifications, downstream actions keyed off `shop`) for a shop the attacker does not own.

### Likelihood Explanation
The only prerequisite is having legitimate access to the app on any shop (e.g., a free/dev install), which lets the attacker obtain valid `(raw_body, hmac)` pairs signed with the shared `api_secret_key`. No access token, refresh token, or `client_secret` theft is required — this is achievable purely through the app's own documented webhook signing scheme combined with unauthenticated header trust in `Registry.process`.

### Recommendation
Bind the tenant-identifying fields into the authenticated payload before trusting them, e.g.:
- Require the host application (or the gem itself, if it has that context) to cross-check `request.shop` against a known/registered shop for the webhook subscription/topic rather than trusting the header value outright, or
- Extend webhook verification to also validate that the `shop`, `topic`, and `webhook_id` headers match values recorded when the specific webhook subscription was registered (e.g., via the webhook id look-up already available in `Registry`), rejecting mismatches before dispatching the handler.

### Proof of Concept
1. Attacker installs the target app on Shop A (a shop they control) and receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against the raw body — it succeeds because `B` and its HMAC are unchanged: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload actually originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
