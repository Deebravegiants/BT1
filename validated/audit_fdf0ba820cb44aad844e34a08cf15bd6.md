### Title
Webhook HMAC Only Covers the Raw Body, Not the `Shop-Domain` Header — Enables Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unsigned HTTP headers. `Webhooks::Registry.process` validates the HMAC over the body only and then dispatches the (attacker-influenceable) `shop` value straight to the app's webhook handler as the tenant identifier. This breaks the intended identity binding: `hmac(raw_body) == valid` should imply `shop-domain header == the shop that actually produced raw_body`, but that equality is never checked.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read from a header that is never part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only from `to_signable_string`, i.e. `@raw_body`: [3](#0-2) 

`Registry.process` checks only this body-bound HMAC, then forwards `request.shop` (unauthenticated) to the app's handler as the tenant identity: [4](#0-3) 

Because a Shopify app typically exposes a single shared webhook callback URL for all installed shops, `raw_body` + `hmac-sha256` pairs are portable across shops: a valid `(raw_body, hmac)` pair generated by Shopify for shop A's own data remains a valid pair regardless of which `shop-domain` header accompanies it, since that header is not part of the signed content. This is exactly the bug class from the report — "a field [is] acted on but not covered by the HMAC" (`shop`, `topic`, `webhook_id` are acted upon by `Registry.process`/handlers, but the signature only covers `raw_body`).

### Impact Explanation
An attacker who can get an app installed on their own store (unprivileged — any developer/merchant can install a public app on a free dev store) can:
1. Trigger a Shopify-originated webhook containing attacker-chosen content in fields they control (e.g. customer name/email fields, order notes, product metafields) for **their own** shop. Shopify computes a legitimate `X-Shopify-Hmac-Sha256` over that raw body using the app's real `api_secret_key`.
2. Capture that `(raw_body, hmac)` pair from their own delivery endpoint (which they control).
3. Replay it directly via HTTP POST to the app's public webhook endpoint, substituting the `X-Shopify-Shop-Domain` header (and, if useful, `topic`) with the victim shop's domain.
4. `Utils::HmacValidator.validate` accepts it because the signature only binds `raw_body`. `Registry.process` then invokes the app's handler with `shop: <victim-shop>` and attacker-controlled `body`.

This lets an unprivileged actor inject attacker-controlled data attributed to an arbitrary tenant (cross-tenant data injection), potentially triggering privileged app-side logic keyed off `shop` (e.g. updating stored data, triggering GDPR/compliance flows, or corrupting per-shop state) — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that: (a) is publicly installable (so an attacker can obtain a store to generate legitimate webhook signatures), and (b) uses a single shared webhook URL across shops (the common integration pattern documented in `docs/usage/webhooks.md`). No secrets, tokens, or privileged accounts are required — only a free/dev Shopify store and the ability to replay one authenticated HTTP request with a modified header.

### Recommendation
Bind the tenant/shop identity into the verified signature material, or otherwise cryptographically tie the `shop-domain` (and `topic`) header to the accepted signature — e.g., include the relevant headers in `to_signable_string`, or have `Registry.process` re-verify that the `shop` header matches a shop-specific expectation (such as an active, previously-established session/shop mapping) before dispatching to handlers. At minimum, document that `request.shop` must not be trusted as an authenticated tenant identifier unless additional binding is performed by the host application.

### Proof of Concept
```ruby
raw_body = '{"id": 1, "note": "attacker payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# ^ this is a REAL hmac obtained from a genuine Shopify webhook delivered to the attacker's own shop

forged_headers = {
  "x-shopify-topic" => "customers/update",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped, NOT covered by hmac
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes (only checks raw_body),
# handler is invoked with shop: "victim-shop.myshopify.com" and attacker-controlled body
```
