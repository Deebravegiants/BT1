### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant spoofing via body/HMAC replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the `X-Shopify-Hmac-SHA256` header, but the `shop` value that is subsequently trusted as the tenant identifier and forwarded to the app's handler is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate before dispatching to the app handler, and it passes `request.shop` — sourced from the unsigned `shopify-shop-domain` header — straight into `WebhookMetadata` as the tenant identity for the handler: [3](#0-2) [4](#0-3) 

The identity binding broken is:
`shop authenticated by HMAC` ≠ `shop trusted for tenant routing (WebhookMetadata#shop)`

Because the header carrying `shop` is not part of `to_signable_string`, any `(raw_body, hmac)` pair that is valid for one shop's webhook remains valid when replayed with an arbitrary `shop` header value — the signature check passes identically regardless of which shop header accompanies the body.

### Impact Explanation
An unprivileged internet user can install the target app on a shop they control (no privileged credentials, access token, or `client_secret` needed) and trigger a legitimate webhook subscription (e.g. `orders/create`) whose body content they fully control through normal store actions. Because the endpoint is a single shared HTTP callback across all merchants in a typical multi-tenant deployment, and the HMAC only binds the body — not the shop — the attacker can capture a validly-signed `(body, hmac)` pair from their own shop and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the spoofed victim domain, causing the app to process/store attacker-controlled data under another tenant's identity — a cross-tenant access/integrity violation.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to (a) be able to install the app on a shop they control (typical, unprivileged), and (b) be able to send an arbitrary HTTP request to the app's public webhook endpoint with a custom `shopify-shop-domain` header while reusing the captured raw body — both straightforward for any internet-facing webhook receiver that doesn't perform network-level restriction (e.g. Shopify IP allow-listing) on top of the library's HMAC check. The library itself provides no additional binding between the signed body and the shop header, so any host application that follows the documented `Registry.process` flow inherits this gap.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable material used for verification, or have `Registry.process` independently re-derive/verify the shop identity from a value covered by the signature before constructing `WebhookMetadata`. At minimum, document that host applications must not treat `request.shop` as authenticated and must cross-check it against the session/shop that originally registered the webhook.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and subscribes to `orders/create`.
2. Attacker creates an order, causing Shopify to deliver a webhook to the app's shared endpoint with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures `(B, H)` (e.g., via a webhook proxy/relay they control) and issues a new POST to the same app endpoint with:
   - Body: `B` (unchanged)
   - `shopify-hmac-sha256: H` (unchanged, still valid since HMAC only covers `B`)
   - `shopify-shop-domain: victim.myshopify.com` (forged)
   - `shopify-topic: orders/create`
4. `Utils::HmacValidator.validate` in `hmac_validator.rb` returns `true` because it only checks `HMAC(B) == H`.
5. `Registry.process` in `registry.rb` dispatches the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)`, causing the app to act on attacker-controlled data under the victim shop's tenant context. [5](#0-4) [6](#0-5)
