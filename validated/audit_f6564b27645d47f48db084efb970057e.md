### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are unauthenticated header values not covered by the HMAC verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` for HMAC verification. Its `to_signable_string` returns only `@raw_body` [3](#0-2) , and `hmac` is read from the `X-Shopify-Hmac-Sha256` header [4](#0-3) . `HmacValidator.validate` computes an HMAC over `to_signable_string` (the body only) and compares it to the header-supplied `hmac` [5](#0-4) .

However, `Request#shop`, `Request#topic`, `Request#api_version`, and `Request#webhook_id` are all pulled directly from separate, unsigned HTTP headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) [6](#0-5) . `Registry.process` verifies only the HMAC of the body and then dispatches the handler using these unverified header values: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [2](#0-1) .

The equality this breaks: `shop (HMAC-verified identity)` == `shop (bytes handed to the handler)`. In reality, only the raw body is bound by the HMAC; the `shop` (and `topic`/`webhook_id`) values consumed by the application are never bound to that signature at all. Since a genuine Shopify webhook for shop A and a genuine Shopify webhook for shop B can have byte-identical bodies for the same topic/payload shape (e.g., two different `app/uninstalled` or generic topic payloads with the same JSON, or bodies that are empty/constant), the HMAC computed over the body is identical across tenants. An attacker who has ever received one legitimate webhook delivery from Shopify for **any** shop (including their own free/dev store, where they are an unprivileged installer of their own app) can capture that raw body + valid HMAC and replay it to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a **different** shop's domain and/or a different `X-Shopify-Webhook-Id`. The HMAC still validates (it only covers the body), and the handler is invoked believing the event came from the spoofed shop.

### Impact Explanation
This breaks the tenant binding of an inbound webhook: `Registry.process` treats the request as authentic for whatever `shop-domain` header is present, but that field is never covered by the cryptographic signature. Downstream handlers built on `WebhookMetadata.shop` (e.g., to select the merchant's stored session/access token, or to trigger per-shop side effects such as data deletion, resync, or uninstall handling) can be tricked into acting on an attacker-chosen shop identity while still passing signature validation. This is a cross-tenant identity confusion / spoofing issue reachable by any internet user who can trigger or capture one legitimate webhook delivery (e.g., by installing the app on their own store), matching the "shop authenticated versus the shop stored/used as the tenant key" analog class.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker needs a body+HMAC pair that is valid for the same secret and produces the desired effect when replayed under a different shop header — trivially achievable for topics with constant/empty bodies (e.g., mandatory compliance topics, or any topic whose payload doesn't include the shop id inside the JSON itself), and (2) the impact depends on the handler trusting `metadata.shop` for authorization/lookup rather than independently verifying shop ownership. Where handlers do this (the documented, expected usage pattern per `docs/usage/webhooks.md` and `WebhookMetadata`), the spoof is directly usable.

### Recommendation
Include the shop domain (and ideally topic and webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop`/`topic`/`webhook_id` values to the verified payload — e.g., require verification of the shop domain returned by `Request#shop` against the session/API-key context before dispatch, and/or fold these header values into `to_signable_string` if Shopify's on-wire signing supports it, or independently authenticate the shop via a secondary lookup instead of trusting the header at all in `Registry.process`.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` (or any topic with a body that is constant/predictable, e.g. `{}` as used in the gem's own tests) via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. As an unprivileged attacker, install the app on your own store (or otherwise trigger one legitimate webhook delivery) and capture the raw POST: headers include `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of raw body>`, `X-Shopify-Topic: orders/create`.
3. Replay the identical raw body and HMAC to the same endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or a different `X-Shopify-Webhook-Id`).
4. `Utils::HmacValidator.validate(request)` in `HmacValidator#validate_signature` succeeds because it only hashes `@raw_body` [3](#0-2)  — the same bytes as the legitimate delivery — so `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` [2](#0-1) , even though Shopify never sent this webhook for that shop.
