### Title
Consensus `update_client` accepts state commitments with regressed timestamps as long as height increases, corrupting timeout gating - ([File: modules/ismp/core/src/handlers/consensus.rs])

### Summary
`update_client` in the ISMP core only enforces that a new `StateCommitmentHeight` has a `height` greater than the previously recorded latest height for a given `StateMachineId`; it never checks that the embedded `StateCommitment.timestamp` is monotonically increasing relative to the timestamp already stored for that state machine. Since this same `timestamp` field is later used verbatim to decide whether pending requests/responses have timed out, a cryptographically valid but timestamp-regressed commitment (the exact "phase change" pattern from the Chainlink report, where a new data source/aggregator/prover run produces a height that is higher but a clock that is behind) can be persisted and used to gate fund-releasing timeout logic.

### Finding Description
In `update_client`, for every intermediate state returned by a `ConsensusClient::verify_consensus` call, the only ordering guard is on `height`: [1](#0-0) 

There is no comparison against `host.state_machine_update_time(...)` or against the `timestamp` field of the previously stored `StateCommitment` at `previous_latest_height`. The `IsmpHost` interface only exposes storage of the commitment and its (host-observed) update time, with no monotonicity check performed by the caller: [2](#0-1) [3](#0-2) 

`ConsensusClient` implementations (BEEFY, GRANDPA, BSC, Polygon/Tendermint) derive the `StateCommitment.timestamp` from the counterparty chain's own header/digest data and hand it back to `update_client` without any cross-check against the client's own previously accepted timestamp for that same `StateMachineId`, e.g.: [4](#0-3) [5](#0-4) 

That stored, unchecked timestamp is subsequently trusted as the authoritative "chain time" for settling message timeouts. On the Substrate/ISMP side: [6](#0-5) 

And identically on the EVM `HandlerV2`: [7](#0-6) [8](#0-7) 

Any relayer can submit consensus proofs for any state machine the client tracks; the protocol has no requirement that the *chronologically* latest header be the one submitted, only that its height exceed what's on record. A relayer therefore controls which valid header (and thus which timestamp) becomes "the latest" commitment as long as its height clears the bar — this is structurally identical to the Chainlink bug where a new phase/aggregator can return an `updatedAt` earlier than what was already recorded, because nothing in the consuming contract enforces timestamp monotonicity independently of the "round"/height counter.

### Impact Explanation
Because `state.timestamp()` (or `state.timestamp` on EVM) is the sole clock used to decide `post.timed_out(...)`/`request.timeout() > state.timestamp`, a regressed timestamp accepted at a higher height can:
- Cause `RequestTimeoutNotElapsed` to keep reverting even long after the real-world timeout has passed if the stored timestamp is anomalously low relative to prior state, permanently freezing in-flight requests/relayer fee refunds tied to `on_request_timeout`.
- Or, conversely, allow a request to be prematurely declared timed out (deleting its commitment and invoking `on_timeout`) if a later commitment with an inflated timestamp had previously been accepted and now a "corrected" lower one follows, creating inconsistent commit history for downstream light clients/relayers reconciling state.

This directly affects fund-bearing flows (message delivery vs. timeout-triggered refunds) gated purely on this trusted timestamp value, matching the "permanent freezing of funds" / "route unable to deliver messages" impact classes.

### Likelihood Explanation
Reaching this requires only a relayer submitting a `ConsensusMessage` via the permissionless `update_client` handler with a legitimately-signed/finalized proof for a height greater than the current latest — no privileged or malicious-validator assumption is required, since the underlying consensus clients (BEEFY MMR replay guards, BSC epoch handling, GRANDPA/Tendermint header selection) do not themselves guarantee that the *height-ordering* they enforce implies *timestamp*-ordering relative to what Hyperbridge has already recorded for that specific `StateMachineId`. The complexity is in constructing/selecting such a proof (which depends on the specific consensus client's freshness rules), which is why this is best treated as Medium/High rather than a trivially triggerable Critical.

### Recommendation
In `update_client` (`modules/ismp/core/src/handlers/consensus.rs`), after fetching `previous_latest_height`'s stored `StateCommitment`, additionally require that `commitment_height.commitment.timestamp` is strictly greater than (or equal to, per desired semantics) the timestamp of the previously stored commitment for that `StateMachineId` before persisting it as the new latest height; reject (or skip, mirroring the existing height-skip behavior) any commitment that would otherwise regress the recorded clock. Apply the equivalent check in `EvmHost.storeStateMachineCommitment` / `HandlerV2` if EVM hosts can independently receive consensus updates.

### Proof of Concept
1. A consensus client for state machine `S` has `latest_commitment_height = H0` with `StateCommitment.timestamp = T0` stored via `store_state_machine_commitment`/`store_latest_commitment_height` (`modules/ismp/core/src/handlers/consensus.rs` lines 68-79).
2. A relayer submits a `ConsensusMessage` whose `verify_consensus` cryptographically validates (e.g., a BEEFY MMR leaf/parachain header, or a BSC finalized header) at height `H1 > H0`, but whose embedded `StateCommitment.timestamp = T1 < T0` (e.g. from a parachain/header with a lagging or reset clock, or a proof path the relayer chooses instead of the most recent one).
3. `update_client`'s loop only checks `previous_latest_height > commitment_height.height` (false, since `H1 > H0`), so it proceeds to `store_state_machine_commitment` and `store_latest_commitment_height(H1)` with `timestamp = T1`.
4. Any subsequent `TimeoutMessage::Post` handling evaluates `post.timed_out(state.timestamp())` against `T1` (`modules/ismp/core/src/handlers/timeout.rs` lines 75-81) or `HandlerV2.handlePostRequestTimeouts` compares `request.timeout() > state.timestamp` against `T1` (`evm/src/core/HandlerV2.sol` lines 258-270) — using the regressed clock to make an incorrect timeout determination for requests that should already be considered timed-out (or not), demonstrating the freeze/incorrect-settlement impact.
