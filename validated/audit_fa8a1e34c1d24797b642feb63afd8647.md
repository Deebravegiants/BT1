Found a concrete SSRF-with-credentials analog in `TokenExchange.exchange_token`.

### Title
Token Exchange sends `client_secret` to an unvalidated `shop` host taken from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the `shop` used as the request host directly from the caller-supplied `session_token`'s `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling OAuth flow (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and even `TokenExchange.migrate_to_expiring_token` in the same file) which all call `Utils::ShopValidator.sanitize!` before using the shop as a request host.

### Finding Description
`exchange_token` decodes the session token with `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` [1](#0-0) , where `shop` is simply `@dest.gsub("https://", "")` [2](#0-1) .

`JwtPayload` verifies the signature and `aud` claim [3](#0-2) , but never validates that `dest`/`iss` is an actual `*.myshopify.com` (or configured `myshopify_domain`) host — it only checks `iss.end_with?("/admin")` for a different purpose (`shopify_user_id`) [4](#0-3) . Because a session token is merely HS256-signed with the app's own `api_secret_key`, any embedded-app frontend context (which legitimately holds a session token for its own shop) could still control the `dest` string value, and the library places no independent bound on `dest_shop`'s value/format.

`dest_shop` is then used unsanitized to build the request host: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` and passed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [5](#0-4) . `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` when `Context.api_host` is not configured [6](#0-5) . The POST body containing `client_id` and `client_secret` (the app's own `client_secret`) is then sent to that host [7](#0-6) .

This breaks the intended binding: *the host that receives the app's `client_secret` == a validated Shopify domain*. Contrast with `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, all of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host [8](#0-7) [9](#0-8) [10](#0-9) . `exchange_token` is the one path that skips this check entirely, sending the value straight from JWT `dest` claim to the HTTP host.

### Impact Explanation
This is an SSRF carrying the app's own `client_id`/`client_secret` to a host derived from `dest`, which is not independently constrained to be `*.myshopify.com`/the configured `myshopify_domain`. If any application flow allows influence over the `dest` value that ends up in a session-token-like structure passed to this API (e.g., a custom/dev token-issuance path, or a signing key shared across environments/apps as flagged by the `old_api_secret_key` fallback in `JwtPayload#initialize`), the gem will POST the merchant/app credentials to that attacker-influenced host — satisfying "SSRF with the app's credentials."

### Likelihood Explanation
Likelihood is moderate: exploitation requires the ability to produce (or obtain) a validly-signed session token whose `dest` claim is not a real Shopify shop domain. This is a narrower bar than arbitrary attacker input, but the library provides no defense-in-depth check here (unlike its sibling functions), so any weakness in how a host app obtains/validates session tokens directly translates into an SSRF-with-credentials condition in this gem's own code path.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop, myshopify_domain: ShopifyAPI::Context.myshopify_domain)` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before constructing `shop_session`, and raise `Errors::InvalidShopError` on failure.

### Proof of Concept
1. Configure `ShopifyAPI::Context` normally (`api_key`, `api_secret_key`, embedded app).
2. Craft/obtain a session token whose payload has `dest` set to an attacker-controlled host (e.g. `https://attacker.example.com`) and `aud` equal to `Context.api_key`, signed with the key used by `JwtPayload` (`Context.api_secret_key` or `Context.old_api_secret_key`).
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
4. Observe that `Clients::HttpClient` builds `@base_uri = "https://attacker.example.com"` and POSTs `client_id`/`client_secret` to `https://attacker.example.com/admin/oauth/access_token`, per `lib/shopify_api/auth/token_exchange.rb:51-65` and `lib/shopify_api/clients/http_client.rb:16-19`, with no `ShopValidator` check in between.
