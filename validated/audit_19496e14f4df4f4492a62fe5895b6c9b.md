### Title
Webhook HMAC only signs the raw body, allowing shop identity spoofing via unauthenticated headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC of the raw request body only, but the `shop` (tenant) identity, `topic`, `webhook_id`, and `api_version` that are handed to the app's handler are all taken from HTTP headers that are not part of the signed payload. Any actor who can obtain one valid `(raw_body, hmac)` pair for the app's own `client_secret`-signed content can replay that pair with an arbitrary `shopify-shop-domain` header and have it accepted as an authentic webhook for a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [5](#0-4) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from attacker/network-controlled HTTP headers, with no cryptographic binding to the HMAC: [6](#0-5) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header — i.e., it verifies the body bytes, not the header bytes: [7](#0-6) 

`Registry.process` treats a passing HMAC check as proof of the whole request's authenticity and forwards `request.shop` (an unauthenticated header) into `WebhookMetadata`, which app handlers use as the tenant identifier: [2](#0-1) [8](#0-7) 

The documented handler contract explicitly instructs apps to key work off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), i.e. this gem's own documented API establishes `shop` from the webhook object as the tenant boundary: [9](#0-8) 

Because the same `api_secret_key` signs webhooks for every shop that installs the app, and many webhook topics produce identical (or attacker-predictable/replayable) bodies — e.g. an empty body `"{}"`, as used in the gem's own test fixtures — the pair `(raw_body="{}", hmac=HMAC(secret, "{}"))` is valid for any shop. An attacker who installs the app on their own store receives a legitimate webhook with such a body and a valid HMAC computed with the app's real `client_secret`. They can then resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting `shopify-shop-domain` (and optionally `topic`/`webhook_id`) with a victim shop's domain. `HmacValidator.validate` still passes (only the body is checked), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain, i.e., a cross-tenant data/event injection into the app's per-shop logic (e.g. triggering `shop/redact`, `customers/redact`, `app/uninstalled`-style side effects, or poisoning shop-scoped background jobs) as if it originated from the victim's store.

### Impact Explanation
This breaks the equality the app's handler relies on: `shop (HMAC-authenticated tenant)` == `shop (header value forwarded to WebhookMetadata)`. In practice this is a cross-tenant access vector — the gem allows an unprivileged internet user (any merchant able to install the app on their own store) to make the host application believe an event happened for a different, unrelated shop, since the identity used for tenant scoping is never covered by the cryptographic signature the gem verifies.

### Likelihood Explanation
Moderate-to-high. The attacker only needs their own installation of the target app (installing an app on a free/dev store is trivial and requires no privileged credentials of the victim), the ability to capture one webhook body+HMAC that is independent of shop-specific content, and the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is needed.

### Recommendation
Include the shop domain, topic, and webhook id in the value that is HMAC-verified (or otherwise cryptographically bind `shop` to the signed payload), or, at minimum, validate that the shop domain in the header matches the shop domain independently known/expected for the endpoint before constructing `WebhookMetadata`. Since Shopify's own HMAC design intentionally only signs the body, the mitigation belongs in this gem's `Registry.process`/`WebhookMetadata` construction: require the host application to additionally verify the `shop` header against its own list of installed/authenticated shops before trusting it, and document this requirement prominently, since currently the gem's documentation and API surface encourage trusting `data.shop` directly after `Registry.process` succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic whose body content is constant/predictable, e.g. `shop/redact` or any topic that (for a given event) sends `"{}"` as the body — matching the gem's own test fixture at: [10](#0-9) 
2. Attacker's webhook receiver captures the real Shopify request: `raw_body = "{}"`, header `x-shopify-hmac-sha256 = Base64.encode64(HMAC_SHA256(client_secret, "{}"))`, along with `x-shopify-topic` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends this exact body and HMAC header to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `HmacValidator.validate(request)` recomputes `HMAC(client_secret, "{}")`, which matches, so validation succeeds: [11](#0-10) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host app — following this gem's documented pattern of trusting `data.shop` — performs shop-scoped actions (e.g., queuing redaction/uninstall logic, updating tenant-scoped records) against `victim-shop.myshopify.com` even though that shop never sent this webhook.
