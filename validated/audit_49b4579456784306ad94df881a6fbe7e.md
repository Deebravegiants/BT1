## Custody Analog Found

### Title
Unbounded ownership-chain walk in `root_owner()` allows a self-cyclic object to permanently brick lazy module (re)initialization for a code object - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
The bug report's core lesson generalizes to: *"any invariant that is enforced with a bound/threshold in some code paths but not in an equivalent path will let stale/inconsistent state be treated as valid."* In Aptos object custody code, the analogous invariant is the `MAXIMUM_OBJECT_NESTING` bound that every ownership-chain walker enforces — except `root_owner()`, which walks the same `owner` chain with **no depth bound and no cycle guard**. [1](#0-0) 

### Finding Description
`object::owns` and `object::verify_ungated_and_descendant` both walk the ownership chain (`ObjectCore.owner`) while incrementing a `count` and aborting once `count >= MAXIMUM_OBJECT_NESTING` (8): [2](#0-1) [3](#0-2) 

`root_owner()`, however, performs the identical upward chain walk with an unbounded `while (is_object(obj_owner))` loop and no counter:
```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [4](#0-3) 

A self-referential ownership cycle (`obj.owner == obj`'s own address) is achievable in a single `transfer` call, as demonstrated by the framework's own test: the *first* self-transfer succeeds (because `verify_ungated_and_descendant` short-circuits once `owner == current_address` on the very first hop), and only the *second* attempt aborts on the depth check: [5](#0-4) 

Once an object's `owner` field points back to itself (or forms any longer cycle that still satisfies the depth-8 bound at creation time), `root_owner()` on that object loops forever, consuming gas until the transaction runs out of gas — there is no graceful abort path, unlike every other ownership traversal in the same module.

`root_owner()` is the function used to gate lazy module initialization for object-hosted code. `code::publish_package` records the *root owner* of a code object at (re)publish time when the `lazy_module_initialization` feature is on: [6](#0-5) 

and `init::assert_may_self_initialize` re-derives the *current* root owner via the same `root_owner()` call on every attempted lazy self-initialization, aborting if it doesn't match the recorded owner: [7](#0-6) 

This makes `root_owner()` a load-bearing custody-authority check: it is the mechanism that decides whether an object-hosted module is allowed to mint itself a signer (`create_signer::create_signer(addr)`) to run its own initializer — the same signer that a vault/FA-holding module typically uses to move refs, mint/burn capabilities, or register stores during `init_module`. [8](#0-7) 

### Impact Explanation
Because `root_owner()` is unbounded, an attacker who controls a code object (e.g., one deployed via `object_code_deployment::publish`, which is itself an `ExtendRef`-controlled object) can, before transferring/selling that object (and any assets/capabilities it is meant to custody) to a victim, transfer the object to itself, creating a self-cycle in `ObjectCore.owner`. Any subsequent call path that must derive `root_owner()` for that address — including `code::publish_package`'s owner-recording logic and `init::assert_may_self_initialize`'s owner-verification logic used by every lazy `init_module` call on that object — will thereafter always run out of gas and abort. This permanently and non-recoverably blocks re-publishing/upgrading code at that object address under the lazy-init feature and blocks any lazy self-initialization that a vault-style module deployed to that object relies on to (re)establish its custody state (e.g., re-registering `TransferRef`/`MintRef`/`BurnRef` holders after an upgrade). Any object-held or code-object-managed value whose lifecycle depends on this init/upgrade path becomes stuck with no unfreeze/rescue path, satisfying the "permanent lock or non-recoverable loss of object-held or code-object-held value" impact class.

### Likelihood Explanation
Creating the self-cycle requires only a single `object::transfer` call by the object's current owner to its own address — this is demonstrated as a *successful* operation by the framework's own test suite (only the second attempt aborts). No privileged access beyond normal object ownership is required, and the corrupted state (`owner == self`) is permanent since no on-chain path can reset `ObjectCore.owner` for such an object without going through the same unbounded `root_owner()`-dependent logic in some cases, or without external correction. The main precondition for the custody-relevant severity is that the `lazy_module_initialization` feature flag is enabled and that value-custody logic in a real module relies on `internal_maybe_initialize`; I could not fully confirm from indexed code whether any first-party or widely-deployed value-holding module currently depends on this exact lazy-init path in production, so likelihood of *maximal* real-world exploitation is uncertain pending that confirmation.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING` depth-bound/counter used in `owns()` and `verify_ungated_and_descendant()` to `root_owner()`, aborting with `EMAXIMUM_NESTING` once the bound is exceeded, so a cyclic or excessively deep ownership chain cannot cause an unbounded/DoS loop in a function that gates custody-relevant self-initialization authority.

### Proof of Concept
1. Create object `O` owned by account `A` (owner of a code object deployed via `object_code_deployment::publish`, with `lazy_module_initialization` enabled).
2. `A` calls `object::transfer(A, O, address_of(O))` — this succeeds per existing test `test_cyclic_ownership_transfer_should_fail`'s first transfer, setting `O.owner == O`'s own address.
3. `A` transfers/sells the code object `O` (and any deposited value) to victim `V`, or simply leaves a module deployed there that depends on `internal_maybe_initialize`.
4. Any subsequent call that triggers `init::assert_may_self_initialize(O, module_id)` — i.e., any lazy-initialized entry function on a module hosted at `O` — calls `root_owner()` on `O`, which loops forever on the self-cycle and aborts only via out-of-gas, permanently denying self-initialization (and thus any custody logic gated behind it) for that object.

*Note: I could not verify from the indexed code whether a first-party or commonly deployed value-custody module actually uses `internal_maybe_initialize`/lazy init in a way that directly gates fund movement (e.g., mint/burn/transfer refs) — this would need to be confirmed with a live Devin session that can build/run the Move test suite, since the index does not show all downstream consumers of this primitive.*

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let current_address = object.owner;

        let count = 0;

            count += 1;

            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
