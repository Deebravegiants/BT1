### Title
Caller-selected flash receiver can ride the caller's authorization to drain unrelated wallet tokens - (File: contracts/controller/src/strategies/flash_loan.rs)

### Summary
`flash_loan` authenticates `caller`, accepts a caller-selected Wasm `receiver`, and reaches a pool callback into that receiver with the original caller passed as `initiator`. [1](#0-0) [2](#0-1)  The receiver can request additional `initiator` authorization during its callback, causing an unrelated token transfer to appear as a child of the caller's signed authorization tree. [3](#0-2) [4](#0-3) [5](#0-4)  If the victim signs the simulated tree, the protocol's repayment checks still pass while the receiver steals unrelated wallet assets. [6](#0-5) 

### Finding Description
`Controller::flash_loan(caller, asset, amount, receiver, data)` calls `caller.require_auth()` before accepting `receiver` and `data`. [7](#0-6)  The only receiver validation is that its executable is Wasm; there is no receiver allowlist or restriction on which authenticated calls it requests. [8](#0-7)  The controller forwards `caller`, `receiver`, and `data` to the pool, which transfers the principal and invokes `execute_flash_loan(initiator, asset, amount, fee, pool, data)` on that arbitrary receiver. [9](#0-8) [10](#0-9) [4](#0-3) 

During the callback, the receiver can invoke an unrelated token contract with `transfer(initiator, attacker, amount)`. Soroban records that nested request under the caller's authorization entry, and it executes when the caller signs the tree containing it. [5](#0-4)  After callback return, the pool validates only its loaned asset's balance, receiver allowance, and `principal + fee` collection; it does not detect unrelated withdrawals made from `initiator`. [11](#0-10) [12](#0-11) 

### Impact Explanation
A crafted receiver can steal any wallet asset for which the victim signs the extra `transfer` child, including assets unrelated to the lending market. [5](#0-4)  The theft is not bounded by `amount`, the flash fee, or the protocol's settlement checks because those checks concern only the pool's loaned asset. [12](#0-11)  This permits theft of user funds while preserving normal flash-loan settlement. [13](#0-12) 

### Likelihood Explanation
The attacker must deploy a malicious Wasm receiver and socially engineer the victim into invoking `flash_loan` with that receiver, then signing the simulated authorization tree containing the extra transfer. [1](#0-0) [8](#0-7)  No privileged role, leaked key, protocol parameter change, or oracle manipulation is required. [2](#0-1)  The same caller-selected callback shape also exists in `flash_position`, whose controller invokes `execute_flash_position` with `initiator` and opaque `data`. [14](#0-13) [15](#0-14) 

### Recommendation
Do not require `caller` authorization for cash `flash_loan`: repayment authority comes from the receiver's token allowance, so the caller-auth root currently provides an unnecessary authorization scope that callback code can extend. [2](#0-1) [12](#0-11)  For `flash_position`, constrain receivers to governance-reviewed implementations or introduce a narrowly scoped callback mechanism that cannot request unrelated `initiator` authorization. [15](#0-14)  Until contract-level isolation exists, clients should reject any simulated authorization tree containing children beyond the expected protocol operations. [16](#0-15) 

### Proof of Concept
Deploy this malicious receiver, preloading it with enough of the loan asset to cover the flash fee:

```rust
#[contractimpl]
impl MaliciousReceiver {
    pub fn execute_flash_loan(
        env: Env,
        initiator: Address,
        asset: Address,
        amount: i128,
        fee: i128,
        pool: Address,
        _data: Bytes,
    ) {
        // Requests an extra authorization from `initiator`.
        token::Client::new(&env, &TARGET_TOKEN).transfer(
            &initiator,
            &ATTACKER,
            &VICTIM_TARGET_BALANCE,
        );

        // Keep the flash-loan settlement valid.
        token::Client::new(&env, &asset).approve(
            &env.current_contract_address(),
            &pool,
            &(amount + fee),
            &(env.ledger().sequence() + 1),
        );
    }
}
```

Convince the victim to call:

```rust
controller.flash_loan(
    victim,
    HubAssetKey { hub_id: 1, asset: usdc },
    loan_amount,
    malicious_receiver,
    Bytes::new(&env),
);
```

The pool transfers `loan_amount` to the malicious receiver and invokes `execute_flash_loan` with `victim` as `initiator`. [10](#0-9) [4](#0-3)  Simulation records the malicious `TARGET_TOKEN.transfer(victim, attacker, ...)` beneath the victim's `flash_loan` authorization; after the victim signs it, the pool still recovers `amount + fee` through the receiver allowance and the unrelated token theft remains successful. [5](#0-4) [12](#0-11)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's

caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
