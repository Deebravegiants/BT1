## Title
Predictable, unsigned session cookie enables session fixation across shops (offline session ID is `"offline_" + shop_domain`) - (File: lib/shopify_api/auth/session.rb, lib/shopify_api/auth/oauth.rb, lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets a plaintext, unsigned browser cookie whose value is the `Session#id`. That id is not a random secret — it is deterministically derived from public information (the shop's `.myshopify.com` domain), e.g. `"offline_#{shop}"` for offline sessions, or `"#{shop}_#{associated_user.id}"` for online sessions. Any unprivileged user who knows (or guesses) a target shop's domain can construct this exact string and present it as their own `shopify_app_session` cookie value; the library's own helper (`SessionUtils.current_session_id` → `cookie_session_id`) reads that cookie's raw value and returns it, unverified, as "the" session id for the host app to use to fetch the real stored `Session` (containing the real access token) for that shop.

### Finding Description
The binding that should hold is:

`session_id_presented_by_client == an_id_that_only_a_party_who_completed_OAuth_for_that_shop_could_know`

Instead, the library breaks this by using a fully deterministic, secret-free identifier and storing it verbatim as the cookie's cleartext value:

- `Session.from` builds the id purely from public/guessable data: [1](#0-0) 
- `Oauth.validate_auth_callback` sets the plaintext cookie value to that same predictable `session.id` for non-embedded apps: [2](#0-1) 
- `SessionUtils.cookie_session_id`/`current_session_id` trust the raw cookie value directly, with no HMAC/signature check, to determine "the" session id used to look up the stored session (and thus the real access token) for API calls: [3](#0-2) [4](#0-3) 
- The `SessionCookie` struct carries only `name`, `value`, `expires` — no signature/MAC field at all: [5](#0-4) 
- The gem's own documented flow instructs storing this raw value directly as the browser cookie: [6](#0-5) 

Because `"offline_#{shop}"` contains no secret component, and the shop's domain is public, an attacker only needs to know a target shop's `.myshopify.com` domain (trivially discoverable, e.g. from the storefront) to compute the exact cookie value that would identify that shop's stored session in the host application's session repository. This is a session-fixation-style identity binding failure squarely inside the gem's own code — the gem manufactures a predictable identifier and hands it to the host app/browser as if it were an authenticated proof.

### Impact Explanation
If a host application (following this gem's documented pattern) uses the `SessionCookie`/`SessionUtils.current_session_id` value directly as a key into its session store to retrieve a `Session` (which holds the real Shopify access token), an attacker can forge that cookie for any known shop and be handed back that shop's session/access token — a cross-tenant session hijack without ever completing OAuth for that shop. This matches the High-impact category "session fixation or forced OAuth completion" from the identity-binding classes in scope.

### Likelihood Explanation
Likelihood is high for any non-embedded app built per this gem's own documented OAuth callback example, since: (1) shop domains are public/discoverable, (2) the id format (`offline_#{shop}`) is fixed and documented via the code shape itself, and (3) no cryptographic binding (HMAC, random nonce tied to a per-session secret) protects the cookie value — only transport-layer cookie flags (`http_only`, `secure`), which do not stop a client from sending an arbitrary `Cookie` header value it chooses.

### Recommendation
Do not use a deterministic, secret-free string as the bearer session identifier stored in a plaintext cookie. Either (a) sign/MAC the cookie value (e.g., HMAC with `Context.api_secret_key` over the session id, verified on read), or (b) use a random, unguessable session identifier (as `Session.new`'s default `SecureRandom.uuid` already does) instead of overriding it with the deterministic `offline_#{shop}` / `#{shop}_#{user_id}` form in `Session.from`, and update `SessionUtils.cookie_session_id` to validate authenticity before trusting the cookie value.

### Proof of Concept
1. Identify any target shop's public domain, `victim-shop.myshopify.com`.
2. As an unauthenticated attacker, send a request to the host app (built per this gem's documented callback flow) with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim from `cookie_session_id` with no verification: [7](#0-6) 
4. The host app looks up its stored `Session` by that id and, if found, uses its `access_token` to serve the attacker's request as though it were `victim-shop`, without the attacker ever completing OAuth for that shop.
