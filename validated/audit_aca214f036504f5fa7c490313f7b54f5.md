### Title
Webhook `shop` and `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`) identity fields that are handed to the application's webhook handler are taken from unauthenticated HTTP headers that are never included in the HMAC computation. This breaks the binding "shop verified by HMAC == shop attributed to processed webhook data," allowing a party who can obtain one valid `(body, hmac)` pair for their own tenant to replay it against the shared webhook endpoint while claiming to be a different shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`. For webhook requests, `Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), which are not part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the application-registered handler: [3](#0-2) 

Because the identity binding "shop verified == shop reported" is only enforced for the body bytes, and not for `shop`, an attacker with a legitimate but unprivileged relationship to the app (e.g., anyone can install a public Shopify app on their own store) can:
1. Install the app on their own shop and receive a real, HMAC-signed webhook delivery for their tenant — capturing the exact `raw_body` and `hmac` header pair.
2. Replay that captured `(raw_body, hmac)` pair to the app's shared webhook endpoint, substituting the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because the signature check only re-derives the HMAC of `raw_body`, which the attacker did not modify.
4. `WebhookMetadata.shop` is now the attacker-chosen victim domain, so the application's handler processes/stores attacker-controlled webhook content under the victim tenant's identity.

This is analogous to the reported `WellUpgradeable._authorizeUpgrade` bug class: a security-critical action (`upgradeTo`/webhook processing) is gated by a check (`_authorizeUpgrade`/`HmacValidator.validate`) that does not actually bind the acting/attributed identity (owner/shop) to the verified data.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem, following its documented API exactly (`Registry.process`), can be made to attribute attacker-supplied webhook data to another merchant's session/records, since `shop` is the primary tenant key used throughout the library (e.g., session lookup keys such as `"offline_#{shop}"`, `"#{shop}_#{user_id}"`). This matches the in-scope "cross-tenant access" High-impact category.

### Likelihood Explanation
Requires only an unprivileged actor capable of installing the app on any shop (a normal, permitted action for public Shopify apps) to capture one valid webhook, then replay it with a modified header to the shared webhook endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable material used for HMAC verification (or independently verify the `shop` header against a per-shop secret/session before trusting it), so the verified signature actually binds to the identity fields the handler consumes, not just the raw body bytes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook to the app's shared endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker records `raw_body` and `shopify-hmac-sha256` value.
3. Attacker crafts a new POST to the same webhook endpoint using the identical `raw_body` and `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` at [4](#0-3)  — validation passes because it only checks `raw_body` against the secret.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` at [5](#0-4)  now carries `shop = "victim-shop.myshopify.com"` with attacker-controlled body content, and the registered handler processes it as if it legitimately originated from the victim shop.
