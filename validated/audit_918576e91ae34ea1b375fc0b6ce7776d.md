## Finding: Multisig-approved transaction payload can diverge from the executed payload when full-payload verification is feature-gated and conditionally skipped

### Summary
The `mintWithPermit` bug pattern reduces to one custody invariant: **a privileged operation proceeds on the unverified assumption that a prior authorization step actually matches what is being executed.** In Aptos' `multisig_account` module, the analogous invariant is: *"a `MultisigTransaction` may only execute the exact payload that reached quorum approval."* That invariant is not unconditionally enforced for the full-payload storage path.

### Finding Description
`validate_multisig_transaction` is the VM-invoked prologue check that gates execution of a multisig-controlled transaction [1](#0-0) . After confirming quorum and timelock, it is supposed to bind the payload actually being executed to the payload the owners voted on:

```
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, ...);
}
``` [2](#0-1) 

For transactions created via `create_transaction` (full payload stored on-chain, no hash) [3](#0-2) , `transaction.payload_hash` is `None`, so the unconditional hash check never runs. The *only* remaining guard that the payload being executed equals the approved payload is the second `if`, and it is gated entirely by `features::abort_if_multisig_payload_mismatch_enabled()`. If that feature is not active on a given network/deployment, the equality assertion is skipped unconditionally — quorum approval on a *sequence number* is treated as sufficient authorization to execute *any* payload, without ever checking that the content matches what owners actually approved.

This differs qualitatively from the hash-committed path (`create_transaction_with_hash`), which always checks `sha3_256(payload) == payload_hash` regardless of feature flags [4](#0-3) . The full-payload path was retrofitted with an equivalent guarantee only behind a feature flag, meaning the base invariant ("approved content == executed content") is not structurally guaranteed by the resource/data model — it depends on an external on-chain feature toggle staying enabled.

### Impact Explanation
The multisig account is a resource account with no auth key; it is controlled solely through this approval flow [5](#0-4) . If `abort_if_multisig_payload_mismatch_enabled` is disabled (e.g., on a fresh network/devnet before governance activates it, or is later disabled), any owner who can gather quorum approvals for *a* sequence number can execute a **different transaction payload** than the one owners reviewed and voted on — e.g., approve "transfer 1 APT to Bob" but execute "transfer all APT to attacker" or "rotate auth key to attacker's key" — because the module never checks payload equality for the full-payload storage path in that state. This is a direct custody-accounting corruption: value held by the multisig resource account can be redirected to an unapproved holder, and multisig control itself (via auth-key rotation payloads) could be reassigned to an unprivileged party.

### Likelihood Explanation
Exploitability depends entirely on the state of the `abort_if_multisig_payload_mismatch_enabled` feature flag on the target network. I could not confirm from the available index whether this flag defaults to enabled or disabled on mainnet, nor find the feature's introduction history in this single-commit repository snapshot (`get_recent_commits` returned only one squashed "Initial commit"). This uncertainty is material: if the flag is unconditionally enabled on mainnet, this finding is not exploitable there; if it can be disabled or is disabled on any deployment where multisig accounts hold real value, it is directly exploitable by a coordinated/malicious owner subset.

### Recommendation
Make payload-matches-approval verification for the full-payload storage path **unconditional** (not feature-gated), mirroring the unconditional hash check already used for the hash-committed path. At minimum, remove the `!payload.is_empty()` short-circuit so an empty/omitted payload argument cannot silently bypass verification when a full payload is stored on-chain.

### Proof of Concept
Conceptual reproduction (cannot be fully validated without confirming the feature flag's on-chain state, which was not resolvable from this index):
1. Create a multisig account with owners A, B, C, 2-of-3 required.
2. Owner A calls `create_transaction` with payload P1 = "transfer 1 APT to Bob" (full payload stored, `payload_hash = None`) [3](#0-2) .
3. Owner B approves via `approve_transaction`, reaching the 2-of-3 quorum for that sequence number [6](#0-5) .
4. On a network where `abort_if_multisig_payload_mismatch_enabled` is not active, owner A submits a `MultisigTransaction` execution with payload P2 = "transfer all APT to attacker". Because `transaction.payload_hash` is `None` and the feature-gated check is skipped, `validate_multisig_transaction` never asserts `P2 == P1` and execution proceeds [7](#0-6) .

Given the inability to confirm the feature flag's default/mainnet state from available index data, this should be treated as a conditional finding pending verification of `abort_if_multisig_payload_mismatch_enabled`'s actual activation status — I recommend starting a full Devin session with repository access to check `types/src/on_chain_config/aptos_features.rs` and on-chain feature activation records to confirm exploitability before treating this as confirmed-critical.
