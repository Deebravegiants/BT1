## Analysis

**Equality claimed to hold:** `tokens leaving LifiExternalAction during a swap == -deltaAmountChanges[inputTokenIndex]` (the single input amount Hinkal transferred to it for *this* transaction).

**Trace:**

`Hinkal._externalTransact` transfers only `uint256(-deltaAmountChanges[i])` of the declared `circomData.erc20TokenAddresses[i]` to `LifiExternalAction` before calling `runAction` [1](#0-0) . `ExternalActionSwap.swap` then calls `callRouter(inputToken, inputAmount, outputToken, externalActionMetadata)` where `externalActionMetadata` is **fully attacker-authored raw calldata**, taken verbatim from `circomData.externalActionData.externalActionMetadata` [2](#0-1) .

`LifiExternalAction.callRouter` grants a **persistent, unbounded, per-token** allowance to the immutable `router` via `approveUnlimited(inputToken, router)`, then forwards the attacker-controlled bytes verbatim: `router.call(externalActionMetadata)` [3](#0-2) . `approveUnlimited` only tops-up the allowance if it's currently low, so an allowance set for `TokenA` in one user's swap persists indefinitely for all future calls to this shared, singleton `LifiExternalAction` contract [4](#0-3) .

There is **no on-chain constraint** tying the bytes of `externalActionMetadata` to `inputToken`/`inputAmount`: it is opaque calldata forwarded 1:1 to `router.call()`. The only post-call check is `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`, which only measures the *outputToken* delta, not what was pulled from the contract [5](#0-4) .

Critically, `Hinkal.transact`'s balance-conservation loop (`balanceDif == amountChanges[i] + utxoAmount`) only iterates over the tokens **declared in `circomData.erc20TokenAddresses`** for *this* transaction [6](#0-5) . `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency and structural fields of `CircomData`; none of them inspect or constrain the *content* of `externalActionMetadata` [7](#0-6) . The circuit constraint `inTotal + amountChanges[i] === outTotal` likewise only binds the declared token set's amounts — it says nothing about what an off-circuit `router.call()` actually does [8](#0-7) .

**Consequence:** an attacker submitting their own legitimate-looking swap (e.g. `TokenA -> TokenB`) can craft `externalActionMetadata` whose selector/params instruct the router to pull a **different, previously-`approveUnlimited`'d token** (`TokenC`, left over/dust from an earlier unrelated user's swap through the same shared `LifiExternalAction`) via `transferFrom`, and route its proceeds to the attacker. Since `TokenC` is not in the current `erc20TokenAddresses` array, Hinkal's balance-diff/slippage checks never observe or object to its disappearance from `LifiExternalAction`. `swappedAmount` for the declared `outputToken` can even be inflated by the drained value, letting the attacker mint themselves a larger legitimate-looking UTXO while an unrelated token's balance vanishes from the shared contract untracked.

This matches the "File: contracts/types/TokenWithAmount.sol" scope tag loosely (note: `approveUnlimited` actually lives in `TransfererBase.sol`, and the exploitable call sites are `LifiExternalAction.callRouter`/`ExternalActionSwap.swap`, not `TokenWithAmount.sol`, which is just a plain data struct with no logic) — but the underlying mechanism described is real and independent of any Emporium involvement (a direct `Hinkal.transact` call with `externalActionData.externalAddress = LifiExternalAction` suffices).

### Title
Persistent unlimited router approval combined with fully attacker-controlled `externalActionMetadata` allows draining of unrelated tokens held/approved by `LifiExternalAction` outside the accounted token set - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/TransfererBase.sol`)

### Summary
`LifiExternalAction.callRouter` grants the immutable `router` a persistent `type(uint256).max` allowance per ERC-20 via `approveUnlimited`, and forwards the caller's fully attacker-crafted `externalActionMetadata` bytes directly to `router.call()` with no constraint tying that calldata to the declared `inputToken`/`inputAmount`. Because Hinkal's on-chain balance-conservation checks only cover the token addresses declared in the current `circomData.erc20TokenAddresses`, any residual balance of a *different* token previously approved to `router` by an earlier unrelated swap can be siphoned out via crafted calldata without tripping any check.

### Finding Description
The broken equality is: `value leaving LifiExternalAction during callRouter == -deltaAmountChanges[inputTokenIndex]` (the single amount Hinkal transferred in for this swap). Because `externalActionMetadata` is opaque, attacker-chosen bytes forwarded verbatim to a router holding unlimited, persistent approvals for every token ever swapped through this shared contract, and because Hinkal's balance/slippage accounting loop only inspects tokens listed in the current transaction's `erc20TokenAddresses`, an attacker can embed router instructions that pull an unrelated, previously-approved token from `LifiExternalAction` in addition to (or instead of) the declared `inputToken`. That drained value is invisible to `Hinkal.transact`'s per-token balance-diff requirement, so it is neither refunded nor reverted.

### Impact Explanation
Any residual/dust balance of previously-swapped tokens sitting in the shared `LifiExternalAction` contract (which persists indefinitely as approvals, and can accrue token balance from rounding/partial fills across many users' swaps) can be stolen by any unprivileged user through a self-authored swap transaction, by encoding router calldata that acts on a token outside the declared set. This is theft of protocol/residual balances via calls the depositor of that residual value never authorized — matching the High severity category ("theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised").

### Likelihood Explanation
Preconditions: `LifiExternalAction` must hold or have approved a spendable balance of at least one other token from a prior swap (plausible over time since `approveUnlimited` never revokes and any router rounding/dust remains in the contract). The attacker needs only to be an ordinary Hinkal user able to submit their own `transact` call with a legitimate proof for their own UTXOs and freely chosen `externalActionMetadata` — no privileged role required. Cost is a single transaction; repeatable each time residual balance/approval exists.

### Recommendation
Do not forward raw, unconstrained `externalActionMetadata` to a contract holding unlimited approvals. Either (a) decode and validate that the router call only references `inputToken`/`outputToken`/`inputAmount` as declared in `circomData`, (b) replace `approveUnlimited` with an exact, single-use approval of `inputAmount` set immediately before the call and reset to 0 after, or (c) sweep/verify that `LifiExternalAction`'s balance of every token it has ever approved to `router` is zero (or unchanged) after each call, reverting otherwise.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router that implements `transferFrom`-based pulls driven by calldata selector/params.
2. Simulate swap #1: `Hinkal` transfers `TokenA` to `LifiExternalAction`; `callRouter` calls `approveUnlimited(TokenA, router)`; mock router's fake swap leaves a small dust balance of `TokenA` in `LifiExternalAction` (simulate rounding).
3. Simulate swap #2 with a different token `TokenB` becoming `inputToken`, but craft `externalActionMetadata` so the mock router's logic, upon seeing this specific calldata, additionally calls `TokenA.transferFrom(LifiExternalAction, attacker, dustAmount)` using the still-live unlimited approval from step 2.
4. Assert: `TokenA.balanceOf(attacker)` increased by `dustAmount`, `TokenA.balanceOf(LifiExternalAction)` decreased accordingly, while `Hinkal.transact`'s balance-diff assertion for `circomData.erc20TokenAddresses = [TokenB, outputToken]` passed with no revert — proving the `TokenA` outflow was never checked against `deltaAmountChanges` or `slippageValues`.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
