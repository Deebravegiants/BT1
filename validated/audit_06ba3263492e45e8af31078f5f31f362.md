Confirmed: `SwapFirstAssetTrader` is actively used as a live `Trader` in production runtime XCM configs, not just tests/mocks — it's wired into Asset Hub Westend/Rococo (per `prdoc/stable2506/pr_8376.prdoc`), Penpal (`cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs:404-412`), and the staking-async parachain runtime.

### Title
Unbounded slippage (no `amount_out_min`) in `SwapFirstAssetTrader::refund_weight` XCM fee-refund swap - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader::refund_weight` performs an AMM swap via `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, allowing unlimited slippage. This is the same vulnerability class as the reported `LPBase._convertToken` bug (`IPool.swap(..., 0, ...)`), applied to a Substrate/Cumulus DEX-swap call site.

### Finding Description
`SwapFirstAssetTrader` is a `WeightTrader` used when an XCM message pays execution fees in a non-native asset that is exchangeable via `pallet_asset_conversion`. During `buy_weight`, the trader correctly swaps with a fixed target output (`swap_tokens_for_exact_tokens`), enforcing exactness on the amount received. However, on `refund_weight`, when converting unused fee (held in the `Target` asset) back into the asset the user originally paid with, it calls: [1](#0-0) 

```
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) {
```

The `amount_out_min` parameter is passed as `None`, meaning `pallet_asset_conversion::Pallet::do_swap_exact_credit_tokens_for_tokens` (see `substrate/frame/asset-conversion/src/lib.rs:1075-1109`) skips the `ProvidedMinimumNotSufficientForSwap` check entirely and accepts whatever output the pool state yields at execution time: [2](#0-1) 

This mirrors the LPBase pattern exactly: the caller passes a "no minimum" sentinel (`0` in Solidity, `None` in Rust) instead of deriving a bound from a fresh quote, exposing the swap to price manipulation immediately before it executes.

### Impact Explanation
Any actor able to influence AMM pool reserves for the `(Target, refund_swap_asset)` pair in the same block as the XCM message's execution (e.g., a block-authoring collator, or a user submitting swap extrinsics that get included before the XCM message is processed) can manipulate the pool price downward just before `refund_weight` executes, causing the refund swap to return far less than the fair-market amount. The difference is extracted by immediately reversing the manipulation afterward — a textbook sandwich attack. The victim is the XCM message sender, who receives a diminished refund of their unused execution fee; the extracted value flows to the attacker via arbitrage on the AMM pool, which is the same impact category the external report describes for LPBase (value siphoned from a min-amount-unprotected swap).

### Likelihood Explanation
- No trusted role is required to execute the sandwich — front-running/back-running an AMM pool within the same block is achievable by anyone controlling adjacent extrinsics or by a collator ordering transactions, both realistic in a live parachain.
- The vulnerable code path is real production configuration (Asset Hub Westend/Rococo previously, currently Penpal and the staking-async runtime), not merely a test mock — this satisfies "reachable attacker-controlled entry path" and rules out the "mocked-only" disqualifier.
- The magnitude of loss scales with pool depth/liquidity and the size of the refund, so it is more a griefing/value-extraction issue than a critical fund-drain, but it is a concrete, non-theoretical accounting flaw.

### Recommendation
Compute a fresh quote via `QuotePrice::quote_price_exact_tokens_for_tokens(Target::get(), refund_swap_asset, refund_amount, true)` immediately before the swap and pass a bounded `Some(min_acceptable_amount)` (e.g., quote minus a small configurable tolerance) to `swap_exact_tokens_for_tokens` instead of `None`, mirroring the exactness enforcement already used correctly in `buy_weight`.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader<Target=Native, ...>` as an XCM `Trader` (as done in `penpal/src/xcm_config.rs`), with a shallow `pallet_asset_conversion` pool between `Native` and asset `X`.
2. A user sends an XCM message that overpays execution fees in asset `X`; `buy_weight` swaps enough `X` into `Native` to cover the (over-)estimated weight.
3. Before the message finishes executing (or in the same block, ordered by the attacker/collator), the attacker swaps a large amount into the `Native`/`X` pool to depress the `Native → X` exchange rate.
4. `refund_weight` executes `swap_exact_tokens_for_tokens([Native, X], refund, None)` — with no minimum, it accepts the manipulated (low) output, returning a diminished `X` refund to the original sender.
5. The attacker reverses their initial swap, capturing the price-impact profit extracted from the refund.
