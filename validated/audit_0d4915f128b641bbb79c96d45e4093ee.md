### Title
Lowering `challengePeriod` via governance retroactively shortens the dispute window for already-finalized state commitments - (File: evm/src/core/HandlerV2.sol, modules/ismp/core/src/handlers.rs)

### Summary
The reported issue is that Nexus's `_configureRegistry` mutates a global security parameter (attesters/threshold) without re-checking already-installed modules against the new configuration, silently changing the security guarantees those modules were installed under. Hyperbridge has the same bug class in its optimistic-verification challenge period: the challenge period used to gate message delivery is looked up live, at delivery time, rather than being pinned to the value that was in effect when the underlying state commitment was finalized.

### Finding Description
`challengePeriod` is a single governance-controlled parameter updated through `EvmHost.updateHostParams` / `updateHostParamsInternal` [1](#0-0)  and, on the Substrate side, through `store_challenge_period`/`ChallengePeriod::<T>::insert` reachable from `create_client`/`update_host_params` flows [2](#0-1) .

When a message, response, or timeout is later delivered, both the EVM handler and the core ISMP handler re-fetch the *current* challenge period and compare it against the elapsed time since the state machine commitment (or consensus state) was stored — they do not use the challenge period that was configured when that commitment was originally written:

- EVM: `handlePostRequests`/`handleGetResponses`/timeout handlers compute `delay = timestamp - host.stateMachineCommitmentUpdateTime(...)` and compare it to `host.challengePeriod()`, the live value [3](#0-2) .
- Core ISMP: `verify_delay_passed` reads `host.challenge_period(proof_height.id)` live and compares it to `current_timestamp - update_time` [4](#0-3) .

Nowhere in the state-commitment storage path (`store_state_machine_commitment`/`store_state_machine_update_time` in `update_client`, or `storeStateMachineCommitment` in `EvmHost`) is the challenge period value snapshotted alongside the commitment [5](#0-4) . This is exactly the same defect pattern as the registry report: a global config change is applied instantly and universally, with no per-entity (per-module / per-state-commitment) reconciliation against the state that already exists under the old configuration.

### Impact Explanation
If governance (via `updateHostParams`/`update_host_params`, reachable by the cross-chain `HostManager`/`host-executive` pallet governance flow) reduces `challengePeriod` — even for legitimate operational reasons — every state machine commitment that was already stored under the old, longer challenge period instantly becomes eligible for message delivery the moment `now - update_time > new_challenge_period`, regardless of whether the originally-promised dispute window (during which fishermen could submit fraud proofs against a byzantine consensus update, per the optimistic-bridging design described in the protocol docs) has actually elapsed. This can allow a state commitment that was finalized by a byzantine/short-lived validator set to be used to process requests/responses/timeouts before it would have otherwise been challengeable, resulting in forged/unauthorized message delivery based on a state root that should still have been under dispute.

### Likelihood Explanation
This requires a governance-authorized `updateHostParams`/`update_host_params` call lowering the challenge period (or a chain misconfiguring/rotating parameters), which is a privileged but legitimate and expected operational action (not malicious governance) — the report's premise is that *any* authorized reconfiguration of a security parameter that doesn't account for already-existing state is exploitable, exactly mirroring the acknowledged Nexus finding.

### Recommendation
Snapshot the challenge period value alongside the state machine commitment/update time when it is stored (in `update_client`/`storeStateMachineCommitment`), and use that pinned value — rather than the live, current `challengePeriod` — when verifying delay in `verify_delay_passed` and the EVM `HandlerV2` delivery paths. Alternatively, when `updateHostParams`/`update_host_params` lowers the challenge period, only apply the new (shorter) value to state commitments recorded after the change, preserving the originally-promised dispute window for pre-existing commitments.

### Proof of Concept
1. Governance calls `updateHostParams` (or the pallet `update_host_params`) to reduce `challengePeriod` from, e.g., 7 days to 0/1 hour, while a state machine commitment was stored 2 hours ago under the old 7-day assumption [6](#0-5) .
2. A relayer immediately calls `handlePostRequests` with a proof against that already-stored commitment; `delay = 2 hours`, `challengePeriod = 1 hour`, so `challengePeriod > delay` is false and the message is processed [7](#0-6) .
3. Had the challenge period remained at 7 days, this message would have been rejected with `ChallengePeriodNotElapsed`, giving fishermen time to submit a fraud proof against the underlying consensus update; the retroactive parameter change removes that guarantee for commitments already in flight.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
