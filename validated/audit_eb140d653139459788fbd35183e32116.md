### Title
Webhook `shop` identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that the body's HMAC matches, using the app-wide `Context.api_secret_key` (shared across every shop that installs the app) [3](#0-2) , and then forwards the unauthenticated `request.shop` value directly into the `WebhookMetadata` passed to the merchant's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`shop_verified_by_HMAC == shop_acted_on_by_handler`

Here it does not: `HmacValidator.validate` (via `VerifiableQuery#to_signable_string`) only signs the raw body [1](#0-0) , so the `shop` (and `topic`/`webhook_id`/`api_version`) header value is never part of what is cryptographically bound to the signature. Because the webhook HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, identical for every shop that installs the app, any merchant who legitimately installs the app receives real webhook deliveries with a valid HMAC over an arbitrary-but-legitimate body for their own shop. That attacker-controlled merchant can capture a body+HMAC pair from their own legitimate webhook and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `Registry.process` will accept it because the signature check only covers the body [5](#0-4) , and the handler receives `WebhookMetadata` with `shop` set to the forged, victim tenant value [4](#0-3) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged app-installing merchant can make the host application (using this gem's documented `Registry.process` API exactly as intended) execute webhook-driven logic (e.g., data updates, uninstall/GDPR handling, order/customer processing) attributed to a different shop than the one that actually authorized/sent the event. This is a cross-tenant identity confusion caused entirely by this gem's HMAC scope choice, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any developer/merchant who can install the app (an unprivileged action) automatically obtains a stream of validly-signed webhook bodies for their own shop, since the signing key is shared across all tenants of the app. No secret, token, or privileged access to the victim's data is required — only the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is fully within the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed content, not just the body. Concretely, change `Request#to_signable_string` (and the corresponding validator) to incorporate the `shop-domain` header (and other identity-bearing headers) into the value that is HMAC-verified, or independently verify that `request.shop` corresponds to a shop with a known, previously-registered access token/session before dispatching to the handler, rejecting the webhook if no such binding exists.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends the attacker a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(app_secret, B)`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical `B` and `H` to the same app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(app_secret, B)` and compares to `H` — it matches, since the body and secret are unchanged [5](#0-4) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [4](#0-3) , causing the host app to act on victim-shop's tenant record using attacker-supplied body data.
