### Title
Escrow withdrawal treats a non-reverting `false` ERC20 return as success, permanently marking escrow "filled/refunded" while tokens remain stuck - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The `Timelock::executeTransaction()` report's "Depth 2" bug class — a low-level `call` returning the dummy `success == true` while the target token's actual transfer silently fails (returns `false` instead of reverting) — has a direct analog in `IntentGatewayV2.withdraw()` on the Tron deployment, where escrowed order state is marked as settled before/without verifying that the ERC20 `transfer` truly moved funds.

### Finding Description
`withdraw()` redeems escrowed tokens for a `RedeemEscrow`/`RefundEscrow` request delivered via `onAccept`. For each token it performs a raw low-level call and only checks the boolean "call did not revert" flag, never decoding/validating the ABI-encoded return data: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

Per Solidity semantics, `success` here only reflects whether the callee reverted — it does not verify that the returned `bool` (if any) is `true`. Any ERC20-like token on Tron that returns `false` on a failed transfer instead of reverting (a well-known non-standard-token pattern, which is exactly why OpenZeppelin's `SafeERC20` exists — and which this same file already imports and aliases via `using SafeERC20 for IERC20;`) will pass this check even though no tokens moved.

Despite this unverified "success," the function unconditionally marks the commitment as settled before the loop even runs: [2](#0-1) 

and decrements the internal accounting for the (unsent) amount: [3](#0-2) 

The identical anti-pattern also appears in the `SweepDust` handling inside `onAccept`, which is reachable by anyone able to get a valid Hyperbridge governance-originated dust-sweep request delivered: [4](#0-3) 

This is the same root cause the external report describes: the code treats a non-reverting call as proof of the intended effect, and once that (false) success is observed, the "queued" state — here, the escrow commitment/order accounting — is destroyed, with no retry path. Unlike `EvmHost.dispatchIncoming` elsewhere in the codebase, which correctly reverts/deletes-and-restores receipts on an actually failed (reverting) call so it can be retried, `withdraw()` has no such recovery: once `_filled[body.commitment]` is set and `_orders[...]` is decremented, the commitment can never be redeemed again, even though the beneficiary never received the tokens.

### Impact Explanation
If the input token used for an intent's escrow is a non-standard ERC20 (returns `false` rather than reverting on failure — e.g., due to a paused/blacklist state, insufficient allowance quirks, or fee/transfer edge cases on some token implementations deployed on Tron), the escrow-redemption flow will silently "succeed": the order is marked filled/refunded and internal accounting is decremented, but the beneficiary receives nothing. This is a permanent freezing/loss of escrowed user funds with no mechanism to re-trigger withdrawal, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
This path is reached through the normal, unprivileged intents flow: any solver/filler completes an order and any relayer/user can drive the resulting `RedeemEscrow`/`RefundEscrow` GET-response or POST message to `onAccept`, which unconditionally calls `withdraw()`. No privileged role is required to trigger the vulnerable code path; the only precondition is that the configured input token exhibits the non-reverting-`false` transfer behavior, which is common enough among ERC20 implementations (and is exactly the risk `SafeERC20` — already used elsewhere via `using SafeERC20 for IERC20` in this same contract — is designed to close).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and in the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)` (the `SafeERC20` library is already imported and aliased in this file), so that both a reverting call and a non-reverting `false` return are treated uniformly as failure, causing the whole `onAccept` invocation to revert. That in turn lets the surrounding ISMP handler treat it as an undelivered message (receipt not persisted / retriable), rather than silently marking escrow as settled while funds remain stuck.

### Proof of Concept
1. Configure (or have a solver select) an escrow input token that implements `transfer` to return `false` on failure rather than reverting (a legal, though non-standard, ERC20 behavior).
2. Have a solver fill the order normally; source-chain escrow holds the input tokens under `_orders[commitment][token]`.
3. Cause the token transfer to fail in a way the token signals via `return false` (e.g., temporary blacklist/pause of the beneficiary, or insufficient token-side state) instead of reverting.
4. Deliver the resulting `RedeemEscrow` request to `onAccept`, which calls `withdraw()`:
   - `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));` returns `success == true` (call didn't revert) even though the token internally returned `false` and moved no funds.
   - `_filled[body.commitment]` is already set, and `_orders[body.commitment][token]` is decremented to 0.
5. Beneficiary balance is unchanged, but the commitment is now permanently marked as filled/refunded with zero remaining order balance — the escrowed tokens are stuck in the `IntentGatewayV2` contract with no code path left to reclaim them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
