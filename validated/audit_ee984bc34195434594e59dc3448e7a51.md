### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (and `topic`/`webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant are taken from unauthenticated HTTP headers that are never covered by that signature. This breaks the identity binding `HMAC(secret, signed_bytes) == HMAC(secret, bytes_acted_on)`, since `signed_bytes` is `raw_body` only while `bytes_acted_on` includes `shop-domain`, `topic`, and `webhook-id` headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string`, i.e. the raw body bytes, with no header material mixed in: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then dispatches to the app's handler using `request.shop` (and `request.topic`/`webhook_id`) taken straight from the unauthenticated headers: [4](#0-3) 

Because Shopify's real webhook signature (`X-Shopify-Hmac-SHA256`) is computed only over the request body, this is consistent with what the gem verifies — but it means the gem provides no cryptographic binding between "the body that was HMAC-signed" and "the shop/topic that this body is attributed to." A subscriber to this gem's webhook processing pipeline (i.e. an unprivileged actor who can trigger any legitimate webhook delivery for a shop they control, such as `orders/create` in their own development store) obtains a valid `(raw_body, hmac)` pair signed with the app's real `api_secret_key`. They can then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a different shop. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the registered handler with `WebhookMetadata` attributing the (attacker-authored) body to the victim's `shop`, `topic`, and `webhook_id`.

Equality broken: `shop_covered_by_hmac == shop_acted_on_by_handler` is false — the HMAC covers `raw_body` only, while the handler acts on `request.shop` from an unauthenticated header.

### Impact Explanation
This is a cross-tenant identity-confusion primitive at the library's trust boundary: the gem hands the host application data it labels as originating from an arbitrary shop, verified only by an HMAC that never bound that shop identity. Any application that keys business logic off `WebhookMetadata#shop` (e.g. to update per-tenant records, trigger tenant-scoped side effects, or select which access token/session to use) can be made to act on attacker-chosen data under a victim tenant's identity, using only a webhook signature the attacker legitimately obtained for their own shop. This matches the "Critical - cross-tenant access" impact category, since it lets one authenticated tenant inject data attributed to another tenant purely through this gem's own verification logic.

### Likelihood Explanation
Any Shopify merchant/developer (an unprivileged, non-credentialed actor with respect to the target app) can trigger real webhook deliveries for their own store and thus legitimately obtain valid `(raw_body, hmac)` pairs signed with the app's secret. Replaying that pair with a modified `shop-domain`/`topic`/`webhook-id` header requires no secret knowledge and no privileged access — only the ability to POST to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cross-check `request.shop` against a shop that is independently authenticated (e.g. an active, stored session/offline token for that shop) before dispatching to a handler. At minimum, document that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be trusted without additional verification by the host application.

### Proof of Concept
1. As a Shopify merchant/developer, register the app's webhook endpoint and trigger a real webhook (e.g. `orders/create`) for your own store `attacker-shop.myshopify.com`, capturing the raw request body `B` and header `X-Shopify-Hmac-SHA256: H` (valid against the app's real `api_secret_key`).
2. Replay a POST to the same endpoint with the same body `B` and header `X-Shopify-Hmac-SHA256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it came from `victim-shop.myshopify.com`.
