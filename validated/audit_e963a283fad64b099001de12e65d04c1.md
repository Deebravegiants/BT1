### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate`, but the HMAC signing string is limited to the raw request body. The `shop` identity used downstream by `Registry.process` to dispatch webhook data to handlers is read from a separate, unsigned HTTP header, breaking the binding `shop that produced the signed payload == shop attributed to the event`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (i.e., the body), so a signature is valid as long as the body bytes match, regardless of what the `shop-domain` header claims: [3](#0-2) 

`Registry.process` trusts the header-derived `request.shop` value directly when constructing the data passed to the app's webhook handler, without any cross-check against the body contents or any other authenticated identity: [4](#0-3) 

Because the HMAC only binds the *body*, not the *(body, shop)* pair, an attacker who possesses one legitimately-signed webhook payload (e.g., from their own shop's installation of the app, which they can freely receive) can resend it to the app's webhook endpoint with the `shop-domain` header modified to name a different, victim shop. `HmacValidator.validate` will still succeed since the body bytes and signature are untouched. This equality that the gem should enforce — `authenticated shop (bound into HMAC) == shop passed to handler` — is broken: the code verifies the bytes of the body but trusts unauthenticated header bytes for tenant attribution.

### Impact Explanation
This crosses the "cross-tenant access" bar in scope: application code built on this gem (e.g., following `docs/usage/webhooks.md`) generally uses the `shop` field of `WebhookMetadata` to decide which merchant's data/session/token to act on. An attacker who can produce or capture one validly-signed webhook (trivially available to them for their own store, since Shopify sends real signed webhooks to every installed app) can relabel it as belonging to a different shop, causing the host application to process/write data under, or trigger actions scoped to, another tenant's identity — a cross-tenant confusion the app cannot detect because the gem does not include `shop` in the authenticated bytes.

### Likelihood Explanation
Medium-High. No secrets are required beyond a normal unprivileged merchant/app-install workflow: any user who installs the app on their own shop receives legitimately HMAC-signed webhooks addressed to their own shop and can immediately replay them with the `shop-domain` header rewritten. The exploit requires only HTTP access to the app's public webhook endpoint and does not require the `api_secret_key`, an access token, or any privileged credential.

### Recommendation
Bind the `shop` identity into the authenticated payload rather than trusting an out-of-band header:
- Include the `shop-domain` header value (and ideally `topic`/`api-version`) in the string used for HMAC computation (`to_signable_string`), matching how Shopify's real webhook delivery model expects verification of the full payload/headers combination.
- Alternatively/additionally, cross-validate that the header's `shop` value belongs to a shop that has a stored/active session for this app (i.e., verify tenancy against local session storage) before dispatching to handlers, rather than trusting the header verbatim.

### Proof of Concept
1. App installed for `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both receive real webhooks from Shopify signed with the same app `client_secret`.
2. Attacker captures one legitimate webhook delivered to their own endpoint for `attacker-shop.myshopify.com`, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid signature over raw body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   body: B
   ```
3. Attacker resends the identical request to the app's webhook endpoint but changes only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   body `B` and `x-shopify-hmac-sha256` are unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks body `B` (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`). The host application now processes attacker-controlled event data under the victim tenant's identity.
