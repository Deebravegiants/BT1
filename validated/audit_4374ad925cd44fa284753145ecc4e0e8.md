### Title
Webhook shop/topic/id headers are trusted by the app despite not being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from unsigned HTTP headers when building the `WebhookMetadata` passed to the app's handler. This breaks the identity binding `hmac_verified_bytes == data_the_app_acts_on`: the signature proves the *body* came from a request signed with the app's `api_secret_key`, but it proves nothing about which shop or topic that body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, while `shop`, `topic`, and `webhook_id` are read from separate, unrelated headers: [2](#0-1) 

`Utils::HmacValidator.validate` only calls `verifiable_query.to_signable_string` (the raw body) through `compute_signature`/`OpenSSL.secure_compare`; it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, and then immediately trusts `request.shop` and `request.topic` (unsigned) to route the payload to a handler and build the metadata object the app acts on: [4](#0-3) 

Because the HMAC is computed with the app's single, shared `Context.api_secret_key` (the same secret is used for every shop the app serves), any tenant that has the app installed can obtain a genuinely-signed webhook body from Shopify for their own shop and events. Nothing in this gem prevents that attacker from replaying that authentic `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` then calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is the attacker-chosen, unauthenticated value.

This is precisely the "field acted on but not covered by the HMAC" class of bug: the equality that should hold — `shop_bound_by_signature == shop_the_handler_acts_on` — is false. Any host application that (as intended by this gem's design) uses `WebhookMetadata#shop` to select which tenant's data/session to update will process attacker-supplied content under a different tenant's identity, i.e. cross-tenant data injection into a victim store's webhook processing pipeline.

### Impact Explanation
This meets the Critical bar of "cross-tenant access": an app relying on this gem's webhook verification (`HmacValidator.validate` + `WebhookMetadata.shop`) as its sole authenticity/tenant-identification mechanism can be made to process a fully valid, gem-approved webhook whose claimed shop does not match the shop that actually produced/authorized the signed body. This crosses the tenant boundary that the HMAC check is meant to enforce.

### Likelihood Explanation
Requires only that the attacker have (or create) their own shop with the target app installed — no privileged credentials, no access to `api_secret_key`, and no interaction with the victim beyond an HTTP POST to the app's public webhook endpoint with modified headers. Because Shopify signs webhooks per-app (not per-shop) with one secret, this is straightforward for anyone in the "unprivileged internet user with a normal storefront/app install" position described in scope.

### Recommendation
- Bind the `shop`, `topic`, and `webhook_id` values into the signed payload (or otherwise cryptographically bind them to the request) before trusting them, e.g., include them in `to_signable_string`, or independently verify `shop` against Shopify by an authenticated lookup rather than trusting the header.
- Short term: document/require host apps to cross-check `WebhookMetadata#shop` against a known, previously-registered shop record (e.g., existing session) rather than treating it as authenticated by the HMAC check, and update `Utils::HmacValidator`/`Webhooks::Request` naming/docs to make clear the header fields are unauthenticated.
- Longer term: incorporate the shop domain into the HMAC-covered signable string wherever the gem exposes a "validated" webhook request object, so `HmacValidator.validate` returning `true` actually implies the claimed `shop`/`topic` are authentic.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends the attacker a legitimate webhook: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — signed with the app's single shared secret.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and compares to `H` via `OpenSSL.secure_compare` — it matches because `to_signable_string` is only `B`: [1](#0-0) [3](#0-2) 
5. `Registry.process` passes validation and invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`: [4](#0-3) 
6. Any host application logic keyed off `data.shop` (as this gem's own docs/tests treat it, e.g. `assert_equal(@shop, data.shop)` in `test/webhooks/registry_test.rb`) now applies attacker-controlled webhook content to the victim shop's tenant context.
