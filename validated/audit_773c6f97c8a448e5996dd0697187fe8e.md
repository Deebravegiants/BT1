### Title
Panic-inducing fixed-length buffer copy from attacker-controlled ABI-decoded signature bytes in BEEFY naive-proof conversion path - (File: `evm/rust/src/conversions.rs`)

### Summary
The FriBidi CVE is a classic "attacker-controlled length used against a fixed-size buffer" bug class: a mismatch between a counted/expected length and the actual data drives a write past the buffer. The closest reachable analog in this repository is the `Vote -> SignatureWithAuthorityIndex` conversion used when decoding a BEEFY "naive" consensus proof submitted through the permissionless `submit_proof` extrinsic of `pallet-beefy-consensus-proofs`.

### Finding Description
`evm/rust/src/conversions.rs` defines: [1](#0-0) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        ...
    }
}
```

`Vote.signature` is a Solidity-ABI `bytes` field (dynamic length) that alloy decodes without any length constraint. `TSignature` is a fixed `[u8; 65]` array. `copy_from_slice` panics whenever the source slice length does not exactly equal the destination length — this is the same defect class as the FriBidi bug: an attacker-controlled length field is trusted to match a fixed buffer size without validation before the copy.

This conversion is reached from `impl From<RelayChainProof> for MmrProof`: [2](#0-1) 
which maps `value.signedCommitment.votes.into_iter().map(Into::into).collect()` directly into `MmrProof.signed_commitment.signatures`, and `RelayChainProof` is itself produced by ABI-decoding the bytes supplied to `pallet-beefy-consensus-proofs::submit_proof`, an extrinsic callable by any signed account: [3](#0-2) 
The naive proof path (`types::PROOF_TYPE_NAIVE => None`) skips the SP1 signer/nonce check that the SP1 path performs, and (per the surrounding logic) is expected to decode the remaining bytes as an ABI-encoded `BeefyConsensusProof`/`RelayChainProof` before calling `verify_and_apply`. Any `Vote.signature` whose length is not exactly 65 bytes will panic during this decode/convert step.

### Impact Explanation
A panic inside dispatch of a permissionless extrinsic is a denial-of-service condition: it can abort block execution for the runtime executing the transaction, and because the same submitted bytes are replayed by every validator applying the block, this is a *deterministic* panic reachable by any account that can submit a naive BEEFY proof — i.e., a route unable to deliver/verify consensus messages, blocking finality/consensus updates for the coprocessor state machine that all bridged messages depend on.

### Likelihood Explanation
High: `submit_proof` is a public, unsigned-origin-agnostic extrinsic (any account can call it, as shown by the `PROOF_TYPE_NAIVE` and malformed-proof tests in `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`), and the ABI-encoded `bytes` field for a signature has no on-chain length check prior to the fixed-size copy.

### Recommendation
Validate `value.signature.len() == 65` (return an error/`TryFrom` instead of an infallible `From`) before calling `copy_from_slice`, mirroring the length checks already applied elsewhere in the codebase (e.g., `to_bytes_32` in `modules/ismp/state-machines/evm/src/utils.rs:118-128`, or `WithdrawParamsAbi::try_from` in `evm/rust/src/host_params.rs:250-267`).

### Proof of Concept
1. Craft a naive BEEFY proof: prefix byte `PROOF_TYPE_NAIVE` followed by an ABI encoding of `BeefyConsensusProof` whose `relay.signedCommitment.votes[0].signature` is set to a `bytes` value of length ≠ 65 (e.g., 64 or 66 bytes) — this is a fully valid ABI encoding since `bytes` is dynamic-length.
2. Submit via `BeefyConsensusProofs::submit_proof(origin, proof)` from any signed account.
3. During conversion (`RelayChainProof -> MmrProof -> Vote -> SignatureWithAuthorityIndex`), `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting the transaction/block execution deterministically for all validators processing the extrinsic.

### Caveat
I was not able to fully trace `Pallet::verify_and_apply` inside `modules/pallets/beefy-consensus-proofs/src/lib.rs` to directly confirm the exact decode path used for `PROOF_TYPE_NAIVE` (its body was not returned by search), so the call chain from `submit_proof` into `From<RelayChainProof> for MmrProof` is inferred from the surrounding types and comments rather than a directly observed function body. If a Devin session with full repository access confirms `verify_and_apply` uses a different decode path for the naive proof type, this analog should be re-validated against the actual code.

```rust
		fn do_submit_proof(submitter: T::AccountId, proof: Vec<u8>) -> DispatchResultWithPostInfo {
			// Size is enforced by the `BoundedVec<u8, T::MaxProofSize>` parameter on
			// `submit_proof` — oversized payloads fail SCALE decoding inside the txpool
			// and never reach this dispatch.
			// The set of accepted proof types is gated by `ismp-beefy`'s
			// `BeefyClientConfig::allowed_proof_types` during `verify_and_apply`. Unknown bytes
			// fall through to the `_ => UnknownProofType` arm below.
			let proof_type = *proof.first().ok_or(Error::<T>::UnknownProofType)?;

			// For SP1 proofs, decode the committed nonce and require it to equal the extrinsic
			// signer. The nonce is committed into the proof's public values, so it can only be
			// changed by re-running the SP1 program — a copied proof verifies cryptographically
			// but is bound to the *original* prover's account, so a different signer cannot claim
			// it. This is the anti-theft gate and also the dedup key: see [`AcceptedProvers`].
			//
			// Binding to the committed nonce also makes dedup robust without canonical
			// re-encoding: Groth16 re-randomization (or re-proving) yields different proof bytes
			// for the same statement, but all of them carry the same committed nonce, so they
			// collapse to a single per-account slot regardless of trailing padding or alternate
			// encodings.
			let account = match proof_type {
				types::PROOF_TYPE_SP1 => {
					let p =
						<ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof as SolType>::abi_decode_params(
							&proof[1..],
						)
						.map_err(|_| Error::<T>::AbiDecodeFailed)?;
					let nonce = H256(p.nonce.0);
					// `T::AccountId` is `AccountId32` in hyperbridge runtimes, which SCALE-encodes
					// to its 32 raw bytes; compare those against the committed nonce.
					if submitter.encode().as_slice() != nonce.as_bytes() {
						Err(Error::<T>::UnauthorizedProof)?
					}
					Some(nonce)
				},
				types::PROOF_TYPE_NAIVE => None,
				_ => Err(Error::<T>::UnknownProofType)?,
			};
```
