### Title
Webhook `shop-domain` and `topic` identity fields are excluded from HMAC verification, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields consumed by the handler are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then blindly trusts those header-derived fields when dispatching to the app's webhook handler, breaking the binding between "bytes verified by HMAC" and "bytes the handler acts on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata` from the unauthenticated header fields and hands it to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms the equality being checked is solely over `to_signable_string` (i.e., the body): [4](#0-3) 

The identity binding the design implicitly assumes is:
`HMAC-verified bytes == bytes the handler treats as belonging to a given shop/topic`

That equality does not hold: `HMAC-verified bytes = raw_body` while `bytes acted on by handler = raw_body + shop-domain header + topic header + webhook-id header + api-version header`. The header fields are outside the cryptographic envelope, so anyone who can produce one legitimately-signed `(body, hmac)` pair for the app (e.g., a merchant who has the app installed on their own store, an "unprivileged" tenant relative to other merchants using the same app) can replay that exact `(body, hmac)` pair while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain and/or the `X-Shopify-Topic` header to a different registered topic. `Registry.process` will accept it as valid because the HMAC only covers the body, and will dispatch a `WebhookMetadata` claiming the (forged) `shop` and `topic` to the handler.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately controls one shop's webhook stream (via installing the app on a store they own — a normal, unprivileged action, not requiring the app's `client_secret` or any Shopify-side credential) can cause the host application's webhook handler to process attacker-supplied body content while it is attributed to a different, victim shop, or attributed to a different topic than what actually generated the body. Depending on how the host app's `WebhookHandler#handle` implementation keys its side effects off `data.shop` and `data.topic` (which is the documented/expected usage pattern of this gem), this enables cross-tenant data corruption/write-primitives, e.g., forcing an app to apply another merchant's data mutation, redaction, or state change under the attacker's chosen shop identifier — satisfying the "cross-tenant access" bar via a break of the merchant-boundary identity binding that this class is supposed to enforce.

### Likelihood Explanation
Medium-High. No secrets are required beyond having the app installed on an attacker-owned store (a normal unprivileged merchant action) — obtaining one valid `(raw_body, hmac)` pair from Shopify's own webhook delivery to that store is trivial and repeatable at will. Swapping unauthenticated headers on an HTTP replay is straightforward. The only precondition is that the host application relies on `WebhookMetadata#shop`/`#topic` for tenant-scoped or topic-scoped logic, which is exactly the pattern the gem's `WebhookHandler` interface encourages by construct.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` values in the string that is HMAC-verified (or otherwise cryptographically bind them, e.g., by having `Registry.process` cross-check `request.shop` against the session/tenant the current handler invocation is scoped to), so `Utils::HmacValidator.validate` cannot succeed unless all identity-bearing fields consumed by the handler are covered by the signature, not just the raw body.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid hmac over raw body>`, and a JSON body the attacker fully controls (order payload content is attacker-editable within their own store).
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker replays the exact same request to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` to another registered topic).
5. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [4](#0-3)  — it matches, since the body is unchanged.
6. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged headers [5](#0-4)  and invokes the app's handler as if this were a legitimate webhook for `victim-shop.myshopify.com`.
