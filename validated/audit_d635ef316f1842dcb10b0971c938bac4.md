### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong withdrawal to be reported as completed in batch withdrawals with duplicate tokens - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the standalone `waitForWithdrawalCompletion()` helper in `internal-utils` both resolve the on-chain status of a specific withdrawal by matching the POA bridge API response solely on `assetId` (`near_token_id`), ignoring the `index` that uniquely identifies which withdrawal in a batch is being queried. When a single settled intent contains two or more withdrawals of the *same* token (a supported, documented use case — batch withdrawals), each `describeWithdrawal` call returns the *first* matching record from the API response regardless of which withdrawal (`index`) is actually being polled, breaking the equality "status reported == actual on-chain outcome for *this* withdrawal".

### Finding Description
`findMatchingWithdrawal` in `poa-bridge.ts` looks up a withdrawal purely by asset id: [1](#0-0) 

This is used by `describeWithdrawal`, which is the per-withdrawal, per-`index` status API defined by the `Bridge` interface: [2](#0-1) 

The `Bridge.describeWithdrawal` contract is explicitly index-based — every `WithdrawalIdentifier` carries an `index` that is supposed to disambiguate multiple withdrawals in the same NEAR tx: [3](#0-2) 

`watchWithdrawal()` and `createWithdrawalIdentifiers()` build one `WithdrawalIdentifier` per withdrawal, each with its own `index`, and independently poll `describeWithdrawal` per identifier: [4](#0-3) [5](#0-4) 

However, `findMatchingWithdrawal` never consults `index` — it just returns `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`. If a batch contains two withdrawals of the identical token (e.g., 2 different destination addresses/amounts of `btc.omft.near` in one intent), both `index: 0` and `index: 1` polling calls will match the **same** array entry (whichever `Array.prototype.find` returns first), so:
- Both indices can report `status: "completed"` with the **same `transfer_tx_hash`**, even though that hash corresponds to only one of the two withdrawals.
- If one withdrawal fails and the other succeeds, both `index`es could still resolve to the first entry found, misreporting the failed withdrawal as completed (or vice versa).

The same defect pattern independently exists in `internal-utils`'s `waitForWithdrawalCompletion`: [6](#0-5) 

The code even documents this as a known, unaddressed gap: [7](#0-6) 

This is structurally identical to the source bug class: a status is reported for a specific identity (index/withdrawal) without validating that it actually corresponds to that identity's on-chain record — just as `_healthcheck()` reported `LIQUIDATABLE` without validating that the underlying zero-collateral state actually meant "unhealthy."

### Impact Explanation
An integrator using `createWithdrawalCompletionPromises`, `waitForWithdrawalCompletion`, or `processWithdrawal` for a batch of same-token withdrawals can receive a `completed` status with a `txHash` for the wrong withdrawal index. This is a status/hash misreport that can cause an integrator to:
- Credit/mark as completed a withdrawal that has not actually landed (using another withdrawal's tx hash as "proof"), or
- Refund/retry a withdrawal that actually did complete, believing it failed, because the failed sibling's status was reported instead.

This matches the "High" impact bucket: a status or hash misreport making an integrator credit or refund twice.

### Likelihood Explanation
This is not an edge case: batch withdrawals of multiple assets are a documented, supported feature (`processWithdrawal` accepts `WithdrawalParams[]`), and nothing prevents a caller from including two withdrawals of the same `assetId` (e.g., splitting a large BTC withdrawal into two addresses/amounts, or repeated same-token payouts). No attacker action is required beyond constructing a normal, allowed batch withdrawal request; the SDK itself has no validation rejecting duplicate `assetId`s in a batch.

### Recommendation
Match `describeWithdrawal`/`waitForWithdrawalCompletion` results using an identifier that is unique per withdrawal, not just `assetId`. Options:
- Sort both the API's returned withdrawals and the local `withdrawalParams` by `(assetId, amount)` and match positionally, as hinted in the existing code comment.
- If the POA API surfaces a per-withdrawal transaction/withdrawal id tied to order-of-execution, use that instead of `near_token_id` alone.
- At minimum, add a runtime check that throws/flags when a batch contains duplicate `assetId`s so silent misreporting can't happen, until proper matching is implemented.

### Proof of Concept
1. Build a batch withdrawal with two entries for the same token, e.g. two withdrawals of `nep141:btc.omft.near` to different destination addresses/amounts, submitted via `sdk.processWithdrawal({ withdrawalParams: [w0, w1] })`.
2. NEAR intent settles; POA bridge indexer eventually returns withdrawal statuses for both: e.g. `w0` → `COMPLETED` with `transfer_tx_hash: "hashA"`, `w1` → still `PENDING` (or `REFUNDED`).
3. SDK polls `describeWithdrawal` for `index: 0` and `index: 1` (both `assetId = nep141:btc.omft.near`). Both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the *same* first match (`w0`'s record) for both indices.
4. Both promises returned by `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` resolve to `{ status: "completed", txHash: "hashA" }`, even though `w1` never completed (or completed with a different tx hash). An integrator relying on this signal to release funds/credit a user would incorrectly treat `w1` as settled. [8](#0-7)

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
