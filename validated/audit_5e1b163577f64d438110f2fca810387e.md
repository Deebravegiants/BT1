### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
### Finding Description
The RIPEMD-160 report's root cause is a check that trusts/acts on data whose scope does not match what was actually integrity-protected. The equivalent pattern exists in this gem's webhook processing: `ShopifyAPI::Webhooks::Registry.process` verifies a webhook exclusively via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the raw JSON body of the webhook. [2](#0-1) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, which are never included in the HMAC-signed content: [3](#0-2) 

Once `HmacValidator.validate` returns true (which only proves the *body* bytes are authentic and untampered), `Registry.process` immediately forwards `request.shop` — an unauthenticated field — to the handler: [4](#0-3) 

This is the same class of bug as the RIPEMD-160 finding: a field that is *acted upon* (`shop`) is not *covered by the verification* (the HMAC only binds the body). The binding that should hold is:
`verified(hmac) == shop-domain-used-by-handler`
but in reality:
`verified(hmac) == raw_body only`, while `shop` is taken from an arbitrary, unauthenticated header.

### Impact Explanation
An attacker who can obtain one legitimately HMAC-signed `(raw_body, hmac)` pair — for example by installing the target app on their own trial/development shop and receiving a real webhook Shopify sends them — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different, victim merchant. Because `HmacValidator.validate` never binds the `shop` header to the signature, the forged request passes validation and the handler executes believing the webhook data pertains to the victim shop (`WebhookMetadata#shop` will be attacker-chosen). This is a cross-tenant identity binding break: authenticated payload bytes from tenant A are relabeled and delivered as tenant B's data to the host application's webhook handler, potentially triggering shop-scoped side effects (data writes, deletions, access revocation, mandatory-topic handling such as `customers/redact` or `shop/redeact`) attributed to the wrong tenant.

### Likelihood Explanation
Requires only an unprivileged actor capable of installing/using the target app on any shop they control (a normal, low-privilege action for any Shopify developer/merchant) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — only knowledge of the gem's exact validation logic, which is public.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC verification instead of trusting header values independently of the signed payload. At minimum, `Utils::HmacValidator` should include`shop-domain` in the signable content it verifies, or `Registry.process`/`WebhookMetadata` construction should cross-check the `shop` header against another authenticated source (e.g., an already-provisioned session/shop record) before dispatching to handlers.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; capture a real Shopify webhook delivery, e.g. body `{"id":123}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: customers/redact`
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but change:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the HMAC — the `shop-domain` header is irrelevant to that check. [5](#0-4) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"`, even though the payload was never actually signed/sent by Shopify for that shop. [4](#0-3)
