### Title
Webhook shop identity spoofing — HMAC signs only the raw body, not the `shopify-shop-domain` header ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant (`shop`) for an incoming webhook from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body. The shop identity is never cryptographically bound to the authenticated bytes, breaking the equality `shop verified-by-HMAC == shop acted-upon`.

### Finding Description
`Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` returns `@raw_body` only — the shop, topic, and webhook-id headers are excluded from the signed content: [3](#0-2) 

Yet `shop` — read straight from the unauthenticated `shopify-shop-domain` header — is exactly the value passed downstream into `WebhookMetadata` and handed to the app's handler as the trusted tenant identifier for the event: [4](#0-3) [1](#0-0) [5](#0-4) 

Because an app typically shares one `client_secret` (the HMAC key) across all merchants/shops installed on it, any party who legitimately installs the app on their own shop receives genuine, correctly-HMAC'd webhook deliveries for that shop. Since the signature covers only `@raw_body` and never binds it to `shop-domain`, that same `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` will still pass, `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` even though the payload actually originated from — and was signed for — the attacker's own shop.

This directly mirrors the report's bug class: an identity-defining field (`shop`) is acted upon by downstream logic (tenant attribution/authorization) while not being covered by the same authentication mechanism (HMAC) that gates whether the request is trusted at all.

### Impact Explanation
An app built on this gem that trusts `WebhookMetadata#shop` for tenant-scoped operations (e.g., updating that shop's stored data, disabling/enabling features, processing `shop/redact` or `customers/redact` compliance topics) can be made to apply an attacker-controlled, self-signed payload against an arbitrary victim shop's tenant record — a cross-tenant confusion/write primitive achieved without ever possessing the victim's credentials or the app's `client_secret`. This satisfies the "cross-tenant access" Critical impact category, since the attacker (who only needs to be able to install the app on their own store — an unprivileged action) can forge Shopify-attributed events for shops they do not control.

### Likelihood Explanation
Medium-to-High: exploitation requires only that (1) the attacker can install the target app on a shop they control (freely available to any developer/merchant), and (2) the app relies on `WebhookMetadata#shop` from this gem as an authoritative tenant identifier without independently cross-checking it against a known/registered shop list — a very natural pattern given the gem's own `WebhookMetadata` struct presents `shop` as verified data once `Registry.process` succeeds.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the verified payload before it is trusted (e.g., verify the reporting shop against the session/shop the webhook was registered for). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be independently validated by the consuming application against known installed shops.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) so Shopify sends a legitimately HMAC-signed POST to the app's webhook endpoint, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and body `B`.
2. Attacker captures `(B, valid-hmac-of-B)` and replays it directly to the same public webhook endpoint, only changing the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request whose `hmac` matches, because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) never included the shop header.
4. `HmacValidator.validate` returns `true` (`lib/shopify_api/utils/hmac_validator.rb:12-31`), so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — a payload the app now treats as an authenticated event belonging to `victim-shop`, despite it never having originated from or been signed for that shop.
