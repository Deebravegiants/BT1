## Analog Found

### Title
DoS in relayer fee withdrawal — `withdraw_fees` zeroes the `Fees` balance before confirming the destination `EvmHost` actually holds enough fee token to disburse it - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The original report describes a Balancer withdraw path where the amount requested by a user can exceed the pool's actual `cash` on hand, causing the withdrawal transaction to revert. The equivalent pattern exists in Hyperbridge's relayer-fee withdrawal flow: `Pallet::withdraw` dispatches a cross-chain disbursement instruction for `available_amount` and immediately zeroes the local `Fees` entry, without any guarantee that the destination `EvmHost`/`RELAYER_FEE_ACCOUNT` actually holds that much of the fee token at delivery time.

### Finding Description
`Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`) reads the relayer's accrued balance, dispatches an ISMP POST instructing the destination to pay it out, and unconditionally zeroes the source-side accounting right after the dispatch call returns: [1](#0-0) 

The actual payout on an EVM destination happens later, when a relayer delivers the proof and `EvmHost.dispatchIncoming` calls `HostManager.onAccept`, which calls `EvmHost.withdraw`: [2](#0-1) 

`EvmHost.withdraw` performs an unconditional `IERC20(params.token).safeTransfer(...)` (or a raw ETH `call`) for the *full* `available_amount` computed at withdrawal-request time on the source chain — with no check that the host's current fee-token balance actually covers it. This is functionally identical to the Balancer pool paying out from `cash` regardless of what the caller "thinks" is owed: the amount to disburse is decided independently of what's actually available at execution time. This is confirmed by the test harness, which shows the call reverting outright when the host has insufficient fee tokens: [3](#0-2) 

The `EvmHost`'s fee-token balance is not a static reserve — it is drawn down by every relayer's `withdraw` calls, by `HostManager`-driven governance sweeps (`IHostManager.withdraw`), and its balance is not proportionally reserved per relayer at accrual time (`accumulate_fees`). Because `dispatchIncoming` deletes the request receipt and returns (rather than reverting the whole handler batch) when the module callback fails: [4](#0-3) 

...and the withdrawal message is dispatched with `timeout: 0` (never expires) at `modules/pallets/relayer/src/withdrawal.rs:166`, the failed disbursement is retryable, but not resolvable — the message will keep failing as long as `EvmHost`'s fee-token balance stays below the (already-committed, already-zeroed-on-source) `available_amount`. The Substrate leg of the same flow has an equivalent unconditional transfer: [5](#0-4) 

### Impact Explanation
A relayer's legitimately earned fees become permanently stuck in a failing retry loop whenever the destination `EvmHost`'s available fee-token balance falls below the withdrawn amount (e.g., due to concurrent withdrawals by other relayers draining the same pool, or a governance `HostManager.withdraw` sweep of "bridge revenue" competing for the same balance). Since `Fees::<T>` was already zeroed on the source chain at dispatch time, the relayer cannot re-derive or resubmit a smaller/adjusted withdrawal — their entitlement is locked to the stale `available_amount` and the message can only ever succeed once the host reaccumulates enough of the fee token, which is not guaranteed on chains with low subsequent traffic. This is a route/message that becomes permanently unable to deliver until an unrelated, uncontrolled condition (host fee-token inflow) is met — a valid Medium-severity finding under the fund-freezing class.

### Likelihood Explanation
No malicious actor is required. Any state machine with modest fee-token turnover where multiple relayers withdraw around the same period, or where governance periodically sweeps `HostManager.withdraw` revenue, can push the host's fee-token balance below an already-approved relayer withdrawal, triggering the stuck/retry condition. This is a normal-usage race, not an attacker-triggered edge case, matching the reachable-by-unprivileged-relayer criteria (any relayer that accrues and withdraws fees).

### Recommendation
Before zeroing `Fees::<T>` and dispatching the withdrawal, or as part of the destination-side `EvmHost.withdraw`, cap the disbursed amount to the currently available fee-token balance and either (a) settle a partial amount and retain the remainder in `Fees` for a follow-up withdrawal, or (b) reserve/escrow relayer-earned fees separately from bridge-revenue funds so that a `HostManager` governance sweep cannot compete with pending relayer payouts for the same balance.

### Proof of Concept
1. Relayer A accrues 1000 fee-token-units of rewards on Hyperbridge, calls `withdraw_fees` for chain X; `Fees[A][X]` is zeroed and an ISMP POST for 1000 units is dispatched.
2. Before A's proof is delivered on chain X, `HostManager.withdraw` (governance) or another relayer's withdrawal drains `EvmHost`'s fee-token balance on X below 1000 (see `evm/src/core/EvmHost.sol` `withdraw`, no balance check).
3. When A's proof is finally submitted, `EvmHost.dispatchIncoming` → `HostManager.onAccept` → `EvmHost.withdraw` reverts via `SafeERC20.safeTransfer` (demonstrated by `test_host_manager_insufficient_balance`), the request receipt is deleted, and delivery must be retried indefinitely — while A's `Fees` entry on the source chain is already zero, so A has no accounting fallback.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),

	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
