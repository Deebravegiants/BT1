### Title
`calc_take_pnl` assumes pool `k` can never decrease and permanently reverts all deposits/swaps/withdrawals when it does - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` requires that the current, un-normalized pool invariant (`x1 * y1`) be `>=` the last recorded invariant (`target.calc_pnl_x * target.calc_pnl_y`), and hard-errors with `AmmError::CalcPnlError` otherwise. This mirrors the Sense-PT bug class: the code assumes a "no-loss" invariant that legitimate conditions can violate, and instead of handling the loss gracefully it reverts the operation entirely, freezing the pool.

### Finding Description
`calc_take_pnl` computes the pool's normalized reserves `x1`/`y1` from the *current* vault balances (via `Calculator::normalize_decimal_v2`, which uses **floor** (truncating) division) and compares `x1 * y1` against `target.calc_pnl_x * target.calc_pnl_y`, the invariant recorded after the previous PNL-taking pass: [1](#0-0) 

If the current product is smaller, the function does not tolerate the loss — it logs and returns `Err(AmmError::CalcPnlError)`: [2](#0-1) 

This function is invoked, unconditionally, from every core user-facing path that mutates the pool: `process_deposit` [3](#0-2) , `process_swap_base_in`/`process_swap_base_in_v2`/`process_swap_base_out` (via the shared swap flow) [4](#0-3) , `process_withdrawpnl` [5](#0-4) , and `process_withdraw` for every status *except* `WithdrawOnly` [6](#0-5) .

The "no-loss" assumption is not actually guaranteed on-chain:
- `normalize_decimal_v2`/`restore_decimal` perform **floor division** on every call [7](#0-6) [8](#0-7) . Each deposit/swap/withdraw round-trips reserves through normalize → restore conversions when updating `calc_pnl_x`/`calc_pnl_y` (see the `checked_sub` update logic at the end of deposit/withdraw), so truncation losses accumulate over many operations, especially when `coin_decimals` and `pc_decimals` differ from `sys_decimal_value` (a scenario the test `test_calc_pnl_precision` explicitly exercises) [9](#0-8) .
- Any token pair whose actual on-chain balance can legitimately drop relative to the AMM's internally tracked math (e.g., accumulated rounding drift, or reserves that shrink for reasons outside the constant-product formula) will eventually make `x1 * y1 < calc_pnl_x * calc_pnl_y`.

Because there is no recovery path reachable by an ordinary user — only an admin can transition the pool to `AmmStatus::WithdrawOnly`, which is the *only* status that skips the `calc_take_pnl` call in `process_withdraw` [10](#0-9)  — once the invariant check starts failing, every deposit, swap, and normal-status withdrawal for that pool reverts, and users cannot get their funds out via any permissionless instruction.

### Impact Explanation
This is a **permanent freezing of user/LP funds** in the affected pool: swaps, deposits, and withdrawals (outside of `WithdrawOnly` status) all call `calc_take_pnl` and all revert identically once the invariant is violated. Unlike the Sense case (where an adapter loss blocks only PT redemption), here the failure blocks the entire pool's liquidity-management surface — LPs cannot exit, traders cannot swap, and new deposits are rejected — until a privileged admin manually flips the pool to `WithdrawOnly` (an action outside the reach of an unprivileged swapper/LP).

### Likelihood Explanation
Likelihood is moderate-to-low but plausible without any privileged or malicious actor: the floor-division round-tripping in `normalize_decimal_v2`/`restore_decimal` guarantees a systematic downward bias in the tracked invariant baseline, and this bias compounds across many deposit/withdraw/PNL cycles, especially for token pairs with differing decimal counts (a normal, permissionless configuration, not requiring any privileged or malicious setup). Given enough transaction volume, the accumulated truncation can push the live invariant below the stored `calc_pnl_x * calc_pnl_y`, triggering the hard revert for all subsequent operations.

### Recommendation
Do not hard-error when the live invariant is below the recorded one. Instead:
- Treat a decrease as a legitimate loss condition: clamp `delta_x`/`delta_y` to zero and re-baseline `calc_pnl_x`/`calc_pnl_y` to the current `x1`/`y1` rather than reverting, or
- Skip PNL-taking (returning zero deltas) while still allowing the surrounding deposit/swap/withdraw operation to proceed, and
- Ensure `process_withdraw` always has a permissionless fallback (not gated behind an admin-only `WithdrawOnly` status change) so LPs can never be permanently locked out by an invariant mismatch.

### Proof of Concept
Precondition: an AMM pool with `pc_decimals != coin_decimals` relative to `sys_decimal_value` (a normal, permissionless pool configuration reachable via `Initialize2`).

1. Perform repeated permissionless `Deposit`/`Withdraw`/`SwapBaseIn` operations. Each operation recomputes `x1`, `y1` via `normalize_decimal_v2` (floor division) and updates `calc_pnl_x`/`calc_pnl_y` via `restore_decimal` round-trips [11](#0-10) .
2. Because both conversions floor-truncate, each cycle can lose up to `sys_decimal_value`/`10^native_decimal` unit of precision, biasing the recorded `calc_pnl_x * calc_pnl_y` baseline slightly upward relative to what a perfectly precise invariant would be.
3. Once accumulated drift causes `pool_pc_amount * pool_coin_amount < calc_pnl_x * calc_pnl_y` on any subsequent call, `calc_take_pnl` returns `Err(AmmError::CalcPnlError)` [2](#0-1) .
4. From this point on, every `Deposit`, `SwapBaseIn`/`SwapBaseOut`, `WithdrawPnl`, and normal-status `Withdraw` transaction for the pool reverts, because all of them call `calc_take_pnl` unconditionally (except `Withdraw` while the pool is already in `WithdrawOnly` status, which requires a privileged admin action to reach).

I was not able to fully verify within the available searches the exact byte-for-byte magnitude of the rounding drift per operation or definitively confirm that no other permissionless instruction resets `calc_pnl_x`/`calc_pnl_y` outside of `SetParams`/admin actions; a background agent with fuzzing/unit-test access could construct a concrete numeric sequence of deposits/withdraws to empirically trigger `CalcPnlError` and confirm the pool becomes stuck.
