### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` are all taken straight from unauthenticated HTTP headers. Since Shopify's HMAC only signs the body, any party who possesses one genuine, validly-signed webhook delivery (e.g., a webhook sent to their own store, which they legitimately receive) can replay that exact body+HMAC pair to the same app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The HMAC check still passes because it never covered the `shop` field, so the handler is invoked believing the event originated from a different, victim shop.

### Finding Description
`Registry.process` enforces exactly one authentication check: `Utils::HmacValidator.validate(request)`, which compares an HMAC computed over `request.to_signable_string` (the raw body only) against the `hmac` header [3](#0-2) [4](#0-3) . After that check passes, the code trusts `request.shop`, `request.topic`, and `request.webhook_id` — all parsed directly from headers with no cryptographic binding to the body — and forwards them to the app's handler as `WebhookMetadata` [5](#0-4) . This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == shop_that_actually_sent_this_event`, but the HMAC never actually attests to the shop.

### Impact Explanation
Any user who operates (or has previously operated) a legitimate shop connected to the target app can capture one valid webhook payload+HMAC from their own store and replay it against the same endpoint with a forged `shop-domain` header pointing to another merchant. Any app logic that trusts `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a common pattern, since this is literally the field the gem exposes for that purpose) can be tricked into writing or acting on data under a different shop's identity — a cross-tenant data integrity/confusion issue reachable purely from the public webhook endpoint with no credentials beyond having been a legitimate merchant of the app at some point.

### Likelihood Explanation
Low-to-medium: it requires the attacker to have previously received (or otherwise obtained) at least one genuine, validly HMAC-signed webhook body from Shopify for some shop, plus knowledge of the app's public webhook endpoint (routes are typically fixed/known). No secret key, access token, or privileged account is required — only the ability to receive a legitimate webhook once and replay it with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) identifiers into the HMAC-verified content, or otherwise cross-check the header-derived `shop` against an independently authenticated source (e.g., verify the shop is one for which a session/subscription is on record, or extend `to_signable_string` to canonicalize headers + body the way Shopify's other signed payloads do) before dispatching to handlers.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and has the app installed; a genuine webhook fires with real body `B` and valid `x-shopify-hmac-sha256` header `H` computed over `B`.
2. Attacker replays a POST to the app's webhook controller route with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...spoofed shop...})` is built; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [2](#0-1) , causing the app to act on `B`'s content attributed to the victim shop.
