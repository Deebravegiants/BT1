### Title
Webhook `shop` (tenant) Identity Not Bound to HMAC Signature Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw request body only, while the `shop` (tenant identifier) that the library later hands to the app's webhook handler is read from an unsigned HTTP header. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to attribute the payload to a merchant, so the tenant binding `shop_verified_by_hmac == shop_used_by_handler` never actually holds.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that value: [2](#0-1) 

`HmacValidator.validate` (invoked by `Registry.process`) only checks that the HMAC over `to_signable_string` (i.e., the body) matches the app's secret — it never incorporates `shop`: [3](#0-2) 

`Registry.process` then passes `request.shop` straight into the handler as the tenant identity, after only checking the body's HMAC: [4](#0-3) 

The binding the library implicitly claims to enforce is:
`shop_authenticated_by_hmac == shop_delivered_to_handler`

But because the HMAC signable string never includes `shop`, the true state is:
`hmac_valid(body, secret) ⇏ shop_is_authentic`

Any request whose body+HMAC pair is valid for *some* shop (e.g., one produced by a genuine webhook delivery to the attacker's own store, which anyone can obtain by installing the app on a free/trial Shopify store) remains valid if the `shop-domain` header is swapped for a different shop's domain — the signature check still passes because it never covered that header. This is the same class of defect as the reported issue (a value that is acted upon — the debt / the shop identity — but excluded from the value that's actually verified — collateral / the HMAC).

### Impact Explanation
An attacker who legitimately installs the app on their own shop (something any unprivileged internet user can do by creating a free Shopify store) receives real webhook deliveries with valid HMACs computed only over the body. By replaying such a body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain, the attacker gets the app to process attacker-influenced webhook content under the identity of a different tenant. Depending on the handler, this enables cross-tenant data injection/corruption (e.g., orders, customer, or inventory webhook data attributed to a shop that never sent it) — a cross-tenant access impact.

### Likelihood Explanation
The attacker needs no access to `api_secret_key`, access tokens, or any other privileged credential — only the ability to install the app once on any Shopify store (self-service, free) and to send arbitrary HTTP requests to the app's public webhook endpoint. The only "difficulty" is capturing one legitimate delivery to learn a valid body/HMAC pair for content they control (they can shape body content by performing the corresponding action, e.g. creating an order, in their own store), which is straightforward.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the string that is HMAC-verified, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted by `Registry.process`/handlers. At minimum, document that consuming applications must independently verify `request.shop` belongs to a session/shop they know is currently authorized for the app before acting on the payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger an event (e.g., create an order) causing Shopify to deliver a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_of_body>`, and the raw JSON body.
2. Capture that raw body and its accompanying valid HMAC (attacker controls both ends of this legitimate delivery, e.g. via a proxy they own in front of their own endpoint, or by simply reading their own server logs).
3. Replay an HTTP POST to the same app endpoint with the identical body and identical `x-shopify-hmac-sha256`, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks the body's HMAC — `request.shop` (`lib/shopify_api/webhooks/request.rb:20-23`) now returns `victim.myshopify.com`, and the handler processes attacker-supplied data as if it came from the victim.
