## Title
`claimProtocol()`/`sweepDonations()` permissionless payout can be front-run against `setFeeTo()` rotation, redirecting protocol fees to a stale/compromised address - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claimProtocol()` and `FeeVault.sweepDonations()` are permissionless: anyone can call them, but the payout always goes to whatever `feeTo` is stored *at call time* [1](#0-0) . When the protocol owner needs to rotate `feeTo` (e.g. the current `feeTo` key is lost or compromised) via `setFeeTo()`, any unrelated address can front-run that transaction by calling `claimProtocol()` and/or `sweepDonations()` first, forcing the entire outstanding `protocolBalance` and any sweepable USDC surplus to be paid to the *old*, soon-to-be-replaced `feeTo` — exactly the class of bug described in the referenced Sherlock report for `AvailBridge.withdrawFees()`.

### Finding Description
`claimProtocol()` reads `$.feeTo` fresh on every call and immediately transfers the full `protocolBalance` to it, with no restriction on `msg.sender`: [1](#0-0) 

`sweepDonations()` behaves the same way for any USDC surplus above backed balances: [2](#0-1) 

`setFeeTo()` is a single-step, immediate rotation with no timelock or two-phase commit — the owner submits one transaction and the new `feeTo` takes effect as soon as it's mined: [3](#0-2) 

The NatSpec on `setFeeTo` itself flags the race: *"rotating here redirects the entire outstanding `protocolBalance` — and any sweepable donations — to `feeTo_`. Call `claimProtocol()` (and `sweepDonations()`) first to settle the pending balance to the current recipient before rotating."* [4](#0-3)  — this confirms the code path is race-sensitive, but it relies on the owner remembering to pre-settle, and does nothing to stop a third party from racing the owner's `setFeeTo` transaction in the mempool.

Concretely: if the current `feeTo` address is compromised (private key leaked) or otherwise needs urgent rotation, the owner's `setFeeTo(newFeeTo)` call sits in the mempool. Any unprivileged address (including the attacker who compromised the old `feeTo` key, or an accomplice) can observe this and submit `claimProtocol()` ahead of it, draining `protocolBalance` — and `sweepDonations()` to drain any donation surplus — to the compromised/stale address before the rotation lands.

### Impact Explanation
This results in permanent loss of accrued protocol fees (and any swept donation surplus) to an address the protocol is actively trying to move away from, precisely because that address is no longer trusted. Since `claimProtocol`/`sweepDonations` are fully permissionless and reachable by any unprivileged wallet, and the payout destination is resolved dynamically from mutable storage rather than pinned at accrual time, this is a real fund-diversion vector rather than a benign design choice.

### Likelihood Explanation
Triggering the race only requires monitoring the mempool for a `setFeeTo` call and submitting a `claimProtocol`/`sweepDonations` transaction with higher gas/priority — no special privileges, capital, or complex preconditions are needed. The likelihood is highest exactly when it matters most: during an active `feeTo` key-compromise response, when there may already be an adversary motivated to race the rotation.

### Recommendation
Either (a) have `setFeeTo` auto-settle outstanding `protocolBalance`/donation surplus to the *old* `feeTo` atomically within the same transaction before updating storage, or (b) restrict `claimProtocol`/`sweepDonations` payout target to a value snapshotted/locked at accrual time rather than the live `feeTo`, or (c) add a pending/confirmed two-step `feeTo` rotation with a cool-down that also pauses claims during the transition.

### Proof of Concept
1. Owner detects that the current `feeTo` private key is compromised and submits `setFeeTo(newFeeTo)`.
2. Before that transaction is mined, attacker (or the party holding the compromised key) submits `claimProtocol()` with higher gas price; it succeeds, reading the *old* `feeTo` and transferring the entire `protocolBalance` to it [1](#0-0) .
3. Attacker also submits `sweepDonations()` in the same block window if any USDC surplus exists, draining it to the same old address [2](#0-1) .
4. `setFeeTo(newFeeTo)` then lands, but `protocolBalance` is already zero — all protocol fees have been irrecoverably paid to the compromised address.

    function claimProtocol() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.protocolBalance;
        if (amount == 0) revert NothingToClaim();
        $.protocolBalance = 0;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit ProtocolFeesClaimed(feeTo_, amount);
    }

    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
