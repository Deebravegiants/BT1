### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) Identity Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The reported Move bug describes a state-mutating operation (`queue::remove`) that updates one linkage (`head`) but fails to update another dependent field (`tail`) that later code trusts as authoritative, breaking the invariant that `tail` always reflects the true last node. The direct analog in this gem is `ShopifyAPI::Webhooks::Request`: the cryptographic integrity check (HMAC) is only bound to the request body, while the `shop` identity field that downstream code treats as the authoritative tenant identifier is read straight from an unauthenticated header, breaking the invariant that "verified bytes == bytes acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, which are not part of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately hands the unauthenticated `shop` header to the application handler as the trusted tenant identity: [3](#0-2) 

This is exactly the documented, intended usage: the gem's own documentation instructs apps to key business logic (e.g. job queues, per-shop persistence) off `data.shop`, taking it at face value as tied to the signed body: [4](#0-3) 

Because `HmacValidator.validate` only proves "these bytes of `raw_body` were signed by `api_secret_key`" and says nothing about which shop or topic the payload is "for," the equality the gem implicitly asserts — `shop_that_generated_the_HMAC == shop_header_value` — does not hold. Any request with a `raw_body`+HMAC pair that is valid for *some* installed shop can be replayed to the shared webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, and the library will accept it as valid and dispatch it to the handler as if it originated from that other shop.

### Impact Explanation
Any user can install the public app on their own store (a completely unprivileged action), causing Shopify to send a legitimately HMAC-signed webhook to the app's shared endpoint with the attacker's own shop domain and attacker-influenced body content (e.g., by creating/naming resources that get serialized into the webhook body). The attacker can then capture that valid `raw_body` + HMAC pair and resend it to the same public endpoint with the `shop-domain` header rewritten to any victim shop. `HmacValidator.validate` still passes (it only checks body bytes against the HMAC), and `Registry.process` forwards the forged `shop` value to the app's handler. This lets an unprivileged attacker inject spoofed webhook events attributed to an arbitrary other tenant — corrupting per-shop state, triggering unintended actions (order/customer create events, `app/uninstalled`, `customers/data_request`, etc.) against a victim shop's records — a cross-tenant integrity/confidentiality violation that maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires no credentials beyond installing a public instance of the target app (something any internet user can do), and only involves replaying a captured HTTP request with a modified header to a public, unauthenticated endpoint. No access token, `api_secret_key`, or privileged account is required, and the shared webhook endpoint is internet-reachable by design. This is realistically exploitable by any external actor able to install the app once.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value verified by the HMAC check — e.g., include the `shop-domain` header (and other identity headers used by handlers) in the canonical string checked by `HmacValidator`, or require the application to independently verify that the `shop` header corresponds to a shop with an active app installation/session before trusting it, rather than passing the raw header value straight into `WebhookMetadata`.

### Proof of Concept
1. Install the target public Shopify app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) with attacker-chosen content, capturing the exact `raw_body` and `X-Shopify-Hmac-Sha256` header sent by Shopify to the shared webhook URL.
2. Replay that exact `raw_body` and HMAC header directly to the same webhook URL, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which only checks `raw_body` against the HMAC — validation succeeds.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, processing it as if it were a genuine event for the victim shop.
