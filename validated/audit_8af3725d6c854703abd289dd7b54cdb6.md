### Title
Deposit and Withdraw instructions support an unprotected encoding with no slippage checks, enabling sandwich-attack theft of LP funds - (File: `program/src/instruction.rs`, `program/src/processor.rs`)

### Summary
Unlike the four swap instructions (`SwapBaseIn`, `SwapBaseOut`, `SwapBaseInV2`, `SwapBaseOutV2`), which unconditionally enforce `minimum_amount_out`/`max_amount_in` checks and abort with `AmmError::ExceededSlippage` on failure, the `Deposit` and `Withdraw` instructions accept an *optional* slippage-protection field (`other_amount_min`, `min_coin_amount`/`min_pc_amount`). When a caller submits the shorter instruction-data encoding that omits these fields, the on-chain program performs the deposit/withdraw exchange-rate calculation entirely without any bound, exactly mirroring the reported `Omnipool.swapForGem()` bug class where a swap is executed with effectively infinite slippage tolerance.

### Finding Description
`DepositInstruction` and `WithdrawInstruction` declare their protective fields as `Option<u64>`: [1](#0-0) 

The unpacker only populates these fields with `Some(...)` when extra trailing bytes are present in the instruction data; otherwise they are left as `None`: [2](#0-1) 

In `process_deposit`, the `other_amount_min` bound is checked only `if deposit.other_amount_min.is_some()`: [3](#0-2) 

Similarly for the pc-based branch: [4](#0-3) 

In `process_withdraw`, the `min_coin_amount`/`min_pc_amount` bounds are likewise only checked `if ... .is_some()`: [5](#0-4) 

By contrast, every swap-processing path (`process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`) treats `minimum_amount_out`/`max_amount_in` as a mandatory `u64` (not optional) and always checks it: [6](#0-5) [7](#0-6) 

This asymmetry means `Deposit`/`Withdraw` — reachable by any unprivileged liquidity provider in a single transaction with attacker-chosen instruction data — can be submitted in a mode that performs the coin/pc exchange-rate conversion (`invariant.exchange_coin_to_pc`, `exchange_pool_to_token`, etc.) against whatever pool ratio exists at execution time, with zero enforced bound, just like the Balancer `batchSwap()` call in the referenced report that used `type(int256).max` limits.

### Impact Explanation
An attacker can sandwich a victim's `Deposit` or `Withdraw` transaction that omits the optional minimum-amount fields:
1. Front-run: swap into the pool to skew the coin/pc ratio unfavorably for the victim's upcoming deposit (or, for withdraw, skew it so the victim's LP burn returns less value than expected).
2. Victim's `Deposit`/`Withdraw` executes at the manipulated ratio with no check rejecting the bad rate, since `other_amount_min`/`min_coin_amount`/`min_pc_amount` are `None`.
3. Back-run: attacker reverses the initial swap, restoring the pool ratio and capturing the value extracted from the victim's LP position.

This can result in theft of a significant portion of the value a liquidity provider intends to deposit or withdraw — directly matching the "theft of funds via sandwich attack due to missing slippage protection" bug class from the report, just manifesting in the LP deposit/withdraw path instead of a reward-claim swap.

### Likelihood Explanation
Any wallet, SDK, or integrator that builds `Deposit`/`Withdraw` instructions using the shorter (no-min-amount) encoding — which is explicitly supported by the packer/unpacker as a valid instruction format — exposes its users to this risk. Because MEV searchers on Solana actively monitor the transaction pool for AMM interactions, and because this omission is silent (the transaction does not fail, it simply provides no protection), the likelihood of exploitation is high wherever the optional fields are not populated.

### Recommendation
Make the minimum/maximum amount fields mandatory (non-optional) for `Deposit` and `Withdraw`, consistent with the mandatory `minimum_amount_out`/`max_amount_in` enforcement already present in all four swap instructions. If backward compatibility requires keeping the optional encoding, reject `None` values at the instruction-unpacking or processing level (or require a caller-supplied explicit "no protection" opt-in flag with strong warnings), so that a slippage bound is always enforced against the exchange rate calculated at execution time.

### Proof of Concept
1. Attacker observes a pending `Deposit` (or `Withdraw`) transaction in the mempool that was built without the optional `other_amount_min` (or `min_coin_amount`/`min_pc_amount`) fields — i.e., the packed instruction data is exactly `1 + 8 + 8 + 8 = 25` bytes for `Deposit` (tag 3) rather than `33` bytes, per the packer at [8](#0-7) .
2. Attacker submits a `SwapBaseIn`/`SwapBaseInV2` swap immediately before the victim's transaction to shift `total_pc_without_take_pnl`/`total_coin_without_take_pnl` in `Deposit`'s pool-ratio calculation.
3. Victim's `process_deposit` runs `invariant.exchange_coin_to_pc(...)` against the skewed ratio; since `deposit.other_amount_min.is_some()` is `false`, the `ExceededSlippage` check at [9](#0-8)  is skipped entirely, and the deposit proceeds with an unfavorable `deduct_pc_amount`/`mint_lp_amount`.
4. Attacker submits a reverse swap to restore the pool ratio, realizing the extracted value at the victim's expense.
