### Title
Webhook shop attribution is unauthenticated, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Registry.process` treats `request.shop`, read directly from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header, as trusted tenant identity after only validating the HMAC over the raw body via `to_signable_string`. Because `Context.api_secret_key` is a single app-wide secret shared by every shop that installs the app, any unprivileged attacker who installs the app on their own shop can obtain a legitimately signed `body`+`HMAC` pair and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, producing a webhook that passes `HmacValidator.validate` while the handler is invoked with `shop: "victim-shop.myshopify.com"`.

### Finding Description
The claimed binding is: `shop asserted in shopify-shop-domain header == shop whose bytes were HMAC-verified via to_signable_string`. Tracing the code:

- `Webhooks::Request#to_signable_string` returns only `@raw_body`, never incorporating the `shop-domain` header value: [1](#0-0) 
- `Webhooks::Request#shop` reads the header verbatim with no cross-check against the HMAC-covered content: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body) and compares against the received `hmac` header, with no involvement of `shop-domain`: [3](#0-2) 
- `Registry.process` validates the HMAC, then hands `request.shop` straight into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because `Context.api_secret_key` is one value shared by the app across all installing shops (not shop-specific), an attacker who installs the app on their own shop legitimately receives a real webhook callback: a body and a correctly computed `X-Shopify-Hmac-Sha256` for that body under the app's secret. Since the header is excluded from the signed bytes, the attacker can resend that exact body+HMAC pair to the app's public webhook endpoint while changing only the `X-Shopify-Shop-Domain` header to any victim's `*.myshopify.com` domain. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though none of the verified bytes originated from or reference that shop.

No existing guard closes this gap: `HmacValidator.validate` only proves "the body was signed by an entity holding the app's secret" (any installer, including the attacker), not "the body/shop pair was issued by Shopify for this specific shop." There is no code anywhere in `lib/shopify_api/webhooks/**` that ties the `shop-domain` header to the signed payload.

### Impact Explanation
Any app handler that trusts `WebhookMetadata#shop` (e.g., to find a merchant record, revoke access, apply GDPR redaction, mark uninstall, credit/debit merchant balances, etc.) can be triggered for an arbitrary victim shop domain by an attacker who only needs to install the app once on a shop they control. This is a cross-tenant integrity/authentication issue: forged events are attributed to any shop the attacker names, for topics the attacker chooses (limited to topics the attacker's own installation legitimately receives, since they must supply a genuinely-signed body for some topic, but the shop label on that body is fully attacker-controlled). This is repeatable indefinitely and against arbitrary victim shop domains without any credentials belonging to those victims.

### Likelihood Explanation
Preconditions are minimal and squarely within the declared attacker capability: install the app on an attacker-owned development/free shop, capture one legitimate webhook delivery (body + `X-Shopify-Hmac-Sha256`), and replay it to the app's public webhook endpoint with a modified `shop-domain` header. No secrets, no victim interaction, and no race conditions are required. This is trivially repeatable.

### Recommendation
Bind the asserted shop to the verified content: include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material (`to_signable_string`) so the signature covers the tenant claim, or independently corroborate `request.shop` against a shop the app has actually installed for/expects to receive events from before dispatching to the handler.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

class RegistryShopSpoofTest < Test::Unit::TestCase
  def test_shop_domain_header_not_covered_by_hmac
    body = '{"id":1}'
    secret = ShopifyAPI::Context.api_secret_key
    valid_hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
    )

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "app/uninstalled",
        "x-shopify-hmac-sha256" => valid_hmac,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker sets arbitrary victim
        "x-shopify-api-version" => "2023-10",
        "x-shopify-webhook-id" => "abc",
      },
    )

    # Binding under test: header shop == HMAC-verified shop
    assert ShopifyAPI::Utils::HmacValidator.validate(request)
    assert_equal "victim-shop.myshopify.com", request.shop
    # request.to_signable_string never referenced "victim-shop.myshopify.com"
    refute request.to_signable_string.include?("victim-shop")
  end
end
```
This demonstrates the HMAC passes while `request.shop` is fully attacker-controlled and disjoint from the verified bytes, confirming the broken binding.
