### Title
Delimiter-free cache key in `DirectBridge.getCachedStorageDepositValue` allows storage-deposit-check collision across unrelated token/destination pairs, causing withdrawals to skip a required NEP-141 storage deposit — (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating the token contract ID and the destination account ID with no separator: `` `${contractId}${accountId}` ``. Because NEAR account IDs are themselves composed of dots, hyphens and alphanumerics, this concatenation is not injective — two different `(contractId, accountId)` pairs can produce the exact same string, exactly the bug class described in the Traefik advisory (non-injective identity construction from hyphen/字符-concatenated fields, later entry silently reusing/overwriting the earlier one).

### Finding Description
`getCachedStorageDepositValue` is used from `estimateWithdrawalFee` to decide whether a NEAR withdrawal needs to carry a storage-deposit top-up fee: [1](#0-0) 

The key is computed as:
```
const key = `${contractId}${accountId}`;
```
with no delimiter between the two fields. Since both `contractId` (the NEP-141 token contract, taken from `parseDefuseAssetId(assetId)`) and `accountId` (`withdrawalParams.destinationAddress`) are attacker/caller-controlled, arbitrary-length NEAR-style strings, the split point between the two fields is not fixed in the resulting key string. Two completely different withdrawal requests:

- Request A: `contractId = "abc.near"`, `accountId = "def.near"`
- Request B: `contractId = "abc.neard"`, `accountId = "ef.near"`

both produce the identical cache key `"abc.neardef.near"`. Both `"abc.near"`/`"def.near"` and `"abc.neard"`/`"ef.near"` are syntactically valid NEAR account IDs, so this is a genuine, realistic collision, not merely theoretical — NEAR account names commonly share long common suffixes (`.near`, `.testnet`, `.factory.bridge.near`, etc.), making unintentional or intentional collisions statistically reachable in production traffic through a shared, process-wide `LRUCache` instance (`storageDepositCache`) used for all withdrawals handled by that `DirectBridge` instance.

The consequence: whichever of the two colliding requests populates the cache first (only cached when `result[1] >= result[0]`, i.e., "storage is sufficient") causes the *other*, unrelated request to hit the cache and be told "storage is sufficient" for a token/destination pair it never actually queried: [2](#0-1) 

This breaks the equality "the storage-deposit sufficiency check reflects the actual on-chain state for *this* `(contractId, destinationAddress)` pair" — the check reported is not the on-chain outcome for the request actually made.

### Impact Explanation
When the collision causes a false "sufficient storage" result, `estimateWithdrawalFee` returns `storageDepositFee: 0n`, and `createWithdrawalIntents` builds the withdrawal intent with `storageDeposit: 0`: [3](#0-2) 

If the destination account is in fact not registered (no storage deposit) on that specific NEP-141 token contract, the resulting `ft_transfer`/withdraw intent executed on-chain will fail for lack of storage, leaving the withdrawal stuck and requiring manual intervention/re-submission with a corrected fee — this matches the "withdrawal stuck until manual intervention" High-impact criterion. It can also silently under-collect the storage-deposit fee that should have been charged to the user, an accounting mismatch between the fee reported to the caller and the fee actually required on-chain.

### Likelihood Explanation
No privileged action is required — any two ordinary withdrawal requests (from the same user across two different tokens/destinations, or from different users sharing the bridge instance/cache) can collide if their `contractId`/`accountId` strings concatenate to the same value, which is plausible given common NEAR naming conventions (shared `.near`/`.testnet` suffixes). The `LRUCache` (`max: 100, ttl: 3600000`) is shared across all callers of a given `DirectBridge` instance, so the collision window is wide (up to one hour TTL, 100 slots).

### Recommendation
Use a collision-safe key, e.g. include a fixed delimiter that cannot appear unescaped in either field, or better, construct the key as a tuple/JSON-safe encoding, e.g.:
```
const key = `${contractId}:${accountId}`;
```
This alone is still technically not fully injective if either field could contain `:`; a more robust option is to key on `` `${contractId.length}:${contractId}:${accountId}` `` or use a `Map` keyed by `` `${contractId}\u0000${accountId}` `` with a control character guaranteed not to appear in valid NEAR account IDs, or simply key the cache as a nested `Map<string, Map<string, ...>>`.

### Proof of Concept
1. Call `directBridge.estimateWithdrawalFee` for `assetId` resolving to `contractId = "abc.near"` and `destinationAddress = "def.near"`, where `def.near` genuinely has sufficient NEP-141 storage on `abc.near`. This populates `storageDepositCache` with key `"abc.neardef.near"` → `[min, balance]` where `balance >= min`.
2. Call `directBridge.estimateWithdrawalFee` for a different, unrelated `assetId` resolving to `contractId = "abc.neard"` and `destinationAddress = "ef.near"`, where `ef.near` has **not** registered storage on `abc.neard`.
3. `getCachedStorageDepositValue("abc.neard", "ef.near")` computes the same key `"abc.neardef.near"`, hits the cache from step 1, and returns the sufficient-storage result even though the real on-chain storage balance for `("abc.neard", "ef.near")` was never checked.
4. `estimateWithdrawalFee` returns `storageDepositFee: 0n`; the subsequent withdrawal intent is built with `storageDeposit: 0`, and the on-chain transfer to the unregistered `ef.near` account on `abc.neard` fails, leaving the withdrawal stuck.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
