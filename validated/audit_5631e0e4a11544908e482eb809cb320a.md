### Title
Webhook HMAC signature does not bind the `shop-domain` (or `topic`/`webhook-id`) header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that raw body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and are never included in the signed payload, yet `ShopifyAPI::Webhooks::Registry.process` trusts those header values to route the event and to build `WebhookMetadata.shop` used by the app's handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. body bytes only: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The identity binding the gem is supposed to enforce is: `shop authenticated by HMAC == shop the handler is told to act on`. Because the `X-Shopify-Shop-Domain` header sits outside the signed bytes, this equality does not hold: **any bytes that produce a valid signature for the app's `api_secret_key` remain valid for *any* header-declared shop**. A user who controls one shop (e.g. a developer/free trial store) can legitimately trigger a real webhook for their own shop, capture its valid `raw_body` + `X-Shopify-Hmac-Sha256`, and replay that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (a victim shop). `HmacValidator.validate` still succeeds because it only hashes the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC check exists to provide, giving an unprivileged internet user (attacker's own shop) the ability to inject or spoof webhook events under a different, victim tenant's identity — for example forging `customers/data_request`, `shop/redact`, `orders/create`, or app-specific business-logic webhooks as if they originated from a different shop. Depending on how the host app persists or acts on `WebhookMetadata.shop`, this can lead to cross-tenant data corruption, unauthorized data deletion/redaction actions being attributed to the wrong shop, or forged business events being recorded against another merchant's account — a cross-tenant access impact.

### Likelihood Explanation
Medium: the attacker needs their own valid Shopify shop/app-install to generate one authentic webhook (any topic works, since the vulnerability is header-independent of payload content), which is trivial to obtain (development stores are free). No access to the app's `client_secret` or another merchant's credentials is required — the attacker only reuses their own legitimately signed payload with forged headers.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., require the host application to independently authenticate/authorize the shop the webhook claims to be for, separately from raw-body HMAC verification) before trusting `request.shop` for any tenant-scoped action. At minimum, the gem's documentation/API should make explicit that `request.shop` is unauthenticated and must not be trusted for tenant identification without additional verification.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, installs the app, and triggers any webhook topic registered by the app (e.g., `orders/create`). Shopify sends a POST with body `raw_body` and header `X-Shopify-Hmac-Sha256: H` computed as `HMAC-SHA256(api_secret_key, raw_body)`.
2. Attacker records `raw_body` and `H` (both fully visible to them since it's their own shop's webhook).
3. Attacker POSTs the exact same `raw_body` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `raw_body` only, matches `H`, and passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the host app's handler as if the event belongs to `victim-shop.myshopify.com`, even though it was never sent by Shopify for that shop. [5](#0-4)
