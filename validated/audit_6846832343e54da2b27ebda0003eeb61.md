### Title
`limitSecretReferences` fails to enumerate all PodSpec secret-reference surfaces, allowing bypass of `LimitSecretReferences` via Projected/CSI/AzureFile/FlexVolume/RBD/ScaleIO/ISCSI/StorageOS/Cinder/CephFS secret refs - ([File: plugin/pkg/admission/serviceaccount/admission.go])

### Summary
The `serviceaccount.Plugin.limitSecretReferences` function only validates a narrow subset of Secret-reference fields in a Pod spec — `Volumes[].VolumeSource.Secret`, container/init-container `Env[].ValueFrom.SecretKeyRef` and `EnvFrom[].SecretRef`, and `ImagePullSecrets` — while the codebase's canonical secret-reference enumerator `podutil.VisitPodSecretNames` covers a much larger surface (AzureFile, CephFS, Cinder, FlexVolume, Projected volume Secret sources, RBD, ScaleIO, ISCSI, StorageOS, CSI `NodePublishSecretRef`). Because `limitSecretReferences` was never updated to match this superset, a Pod referencing a Secret only through one of the unchecked fields (most notably a Projected volume Secret source, which directly mounts secret content into the container filesystem) passes admission even when `LimitSecretReferences` enforcement is enabled and the Pod's ServiceAccount does not reference that Secret.

### Finding Description
`Plugin.Validate` (`plugin/pkg/admission/serviceaccount/admission.go:231-235`) calls `s.limitSecretReferences(serviceAccount, pod)` when `enforceMountableSecrets` is true. `limitSecretReferences` (`plugin/pkg/admission/serviceaccount/admission.go:317-379`) manually walks the pod spec and only inspects:
- `volume.VolumeSource.Secret`
- `container.Env[].ValueFrom.SecretKeyRef` and `container.EnvFrom[].SecretRef` for `InitContainers` and `Containers`
- `pod.Spec.ImagePullSecrets`

Compare this to `podutil.VisitPodSecretNames` (`pkg/api/pod/util.go:123-188`), which is the authoritative reference implementation for "every secret referenced by the pod spec" and additionally covers `AzureFile.SecretName`, `CephFS.SecretRef`, `Cinder.SecretRef`, `FlexVolume.SecretRef`, `Projected.Sources[].Secret`, `RBD.SecretRef`, `ScaleIO.SecretRef`, `ISCSI.SecretRef`, `StorageOS.SecretRef`, and `CSI.NodePublishSecretRef`. There is a dedicated regression test, `TestPodSecrets` in `pkg/api/pod/util_test.go:351`, that uses reflection to assert `VisitPodSecretNames` covers every field containing "secret" in the Pod type — but no equivalent totality test exists for `limitSecretReferences`.

Exploit flow: an attacker with only `create pods` RBAC in a namespace where `LimitSecretReferences` is enabled (globally or via the SA's `kubernetes.io/enforce-mountable-secrets` annotation) creates a Pod whose ServiceAccount does not reference the target Secret, but adds a volume such as:
```yaml
volumes:
- name: leak
  projected:
    sources:
    - secret:
        name: <victim-secret>
```
`limitSecretReferences` never inspects `volume.VolumeSource.Projected`, so the check silently passes, the Pod is admitted, and the kubelet mounts the victim Secret's keys as plaintext files inside the container — fully readable by the attacker's workload. This defeats the entire purpose of `LimitSecretReferences`, which is to prevent a Pod from mounting a Secret its ServiceAccount is not authorized to reference. Referencing a Secret by name in a volume/env source does not require separate RBAC on the Secret object itself (the kubelet fetches it using its own credentials), so `LimitSecretReferences` is the only control designed to block this class of cross-secret disclosure within a namespace.

### Impact Explanation
This is unauthorized disclosure of Secret contents within a namespace: any user able to create Pods can read any Secret's data by name via a Projected volume (or the other unchecked volume-secret fields), completely bypassing the `LimitSecretReferences` admission control. This matches the Kubernetes bounty "sensitive data disclosure / admission bypass" impact class — it defeats a security boundary (`LimitSecretReferences`) that is specifically documented (comment in `NewServiceAccount`, `admission.go:97`) as rejecting "the pod if the pod references Secret objects which the pod's ServiceAccount does not reference."

### Likelihood Explanation
Preconditions: `LimitSecretReferences=true` (or SA annotation `kubernetes.io/enforce-mountable-secrets=true`) and ordinary `create pods` RBAC — no elevated privileges are needed. The Secret name must be known/guessable, which is common in shared namespaces. The exploit is fully reproducible with a single Pod creation containing a `projected` volume (or any of the other unchecked fields) and requires no timing or race conditions, making it deterministic and repeatable.

### Recommendation
Refactor `limitSecretReferences` to use (or be kept in sync with) `podutil.VisitPodSecretNames` so it validates every secret-reference surface, including `Projected.Sources[].Secret`, `AzureFile.SecretName`, `CephFS.SecretRef`, `Cinder.SecretRef`, `FlexVolume.SecretRef`, `RBD.SecretRef`, `ScaleIO.SecretRef`, `ISCSI.SecretRef`, `StorageOS.SecretRef`, and `CSI.NodePublishSecretRef`, in addition to the currently checked fields. Add a struct-reflection based totality test (mirroring `TestPodSecrets` in `pkg/api/pod/util_test.go`) for `limitSecretReferences` to guarantee future new secret-reference fields cannot silently bypass the check.

### Proof of Concept
Table test plan (extend `plugin/pkg/admission/serviceaccount/admission_test.go`):
1. Build a Pod stub containing one entry per known secret-reference field (Volumes[].Secret, Projected.Sources[].Secret, AzureFile, CephFS, Cinder, FlexVolume, RBD, ScaleIO, ISCSI, StorageOS, CSI.NodePublishSecretRef, Env/EnvFrom SecretRef in Containers/InitContainers, ImagePullSecrets), each referencing a distinct Secret name **not** listed in the ServiceAccount's `Secrets`/`ImagePullSecrets`.
2. Set `LimitSecretReferences: true` and call `Plugin.Validate` (or `limitSecretReferences` directly) for each stub individually.
3. Assert that every case returns a non-nil error (`admission.NewForbidden`) rejecting the Pod, matching the totality guaranteed by `podutil.VisitPodSecretNames`.
4. Currently, the Projected/AzureFile/CephFS/Cinder/FlexVolume/RBD/ScaleIO/ISCSI/StorageOS/CSI cases will incorrectly return `nil` (no error), proving the bypass; add a reflection-based test analogous to `TestPodSecrets` (`pkg/api/pod/util_test.go:351`) enumerating all `*.Secret*` field paths on `api.Pod` and asserting `limitSecretReferences` covers each one, to prevent regression when new fields are added.
