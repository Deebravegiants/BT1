### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` binds only the body's authenticity, not the `shop` (or `topic`/`webhook_id`) header value. An attacker who possesses any valid `(raw_body, hmac)` pair for the shared app secret (trivially obtainable by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC pair while forging the `X-Shopify-Shop-Domain` header to name a victim shop. The gem will treat the request as authentic and hand it to the registered handler tagged with the attacker-chosen shop identity.

### Finding Description
`Request#hmac` is derived from the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers via `shopify_header`, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, which recomputes the signature over `to_signable_string` (the body only) and compares it to the received HMAC — it never checks that the `shop` header is consistent with anything signed: [3](#0-2) [4](#0-3) 

Because the app's `api_secret_key` (client secret) is shared across every shop that installs the app, and only the body is part of the signed message, the equality the gem is supposed to enforce — `shop that received the webhook == shop attributed to the payload by Registry.process` — does not hold. An attacker can satisfy the HMAC check with a body/HMAC pair legitimately produced for their own store, then forge the `shop` header to any other value (e.g., a victim shop domain) when replaying the request to the app's webhook endpoint. `Registry.process` will pass this spoofed `shop` value straight into `WebhookMetadata`, so the host application's handler executes believing the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant-isolation binding the HMAC is meant to provide: a malicious merchant can inject data or trigger business logic (e.g., mandatory `customers/redact`, `shop/redact`, or app-specific handlers) under an arbitrary victim shop's identity, since the shop field used by the handler is not authenticated. This is a cross-tenant confusion vector reachable by any unprivileged user who can install the app once on their own store to obtain a valid signed payload, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: any developer/attacker who installs the target app on a store they control receives genuinely signed webhook bodies for that store. Replaying that exact body and HMAC to the app's public webhook endpoint with only the `X-Shopify-Shop-Domain` header changed requires no secrets, no privileged access, and no interaction with Shopify's platform beyond a normal app install.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or independently verify that the `shop` header corresponds to a shop for which a session/installation actually exists and matches other trusted webhook metadata, before invoking the handler with `request.shop`. At minimum, document that consumers must not trust `WebhookMetadata#shop` without separately confirming the shop is a currently installed tenant.

### Proof of Concept
1. Install the victim app on attacker-controlled store `attacker.myshopify.com`; capture a legitimate webhook delivery: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's shared secret).
2. Send a request to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, so the app processes attacker-controlled content as belonging to the victim shop.
