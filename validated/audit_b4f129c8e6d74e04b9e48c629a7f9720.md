### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body, not headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)`, and that validator computes/verifies the HMAC exclusively over `request.to_signable_string`, which returns just `@raw_body`. However, `Registry.process` then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never included in the signed material.

### Finding Description
The identity binding the gem implicitly asserts to host apps is: `hmac_valid(body) == this event genuinely belongs to shop_header`. In reality the code only proves `hmac_valid(body)`; the `shop`, `topic`, and `webhook_id` values are unauthenticated attacker-controlled input. [1](#0-0) [2](#0-1) [3](#0-2) 

Because a Shopify app uses a single shared `client_secret` (`api_secret_key`) for HMAC signing across every shop that installs it, any unprivileged attacker who is themselves a legitimate (even free-trial) merchant of the target app receives real, validly-signed webhooks for their own shop. Since the HMAC is computed only over the raw body, and the `shop-domain`/`topic`/`webhook-id` headers are outside the signed scope, the attacker can capture one of their own legitimate webhook deliveries (`raw_body` + valid `X-Shopify-Hmac-Sha256`) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop (and/or the topic/webhook-id changed). `HmacValidator.validate` will still pass because the body bytes and signature are unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing. If the host application uses `WebhookMetadata#shop` (as documented/intended) to look up the target shop's session/store record and applies the (attacker-controlled) body to that shop's data, an attacker can inject or corrupt data cross-tenant, or trigger shop-scoped side effects (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` handling, inventory/order updates) against a victim shop they do not own — all while sailing through the gem's own HMAC check. This matches the "cross-tenant access" Critical impact category, since the gem provides no mechanism to bind the authenticated bytes to the claimed tenant identity.

### Likelihood Explanation
Requires only that the attacker be able to install/use the target app on their own (attacker-owned) shop to legitimately receive a validly-HMAC'd webhook, then replay it with a forged shop header to the app's public webhook endpoint — no access token, `client_secret`, or victim credentials needed. This is a realistic, low-effort attack path for any external, unprivileged party.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the payload before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document that host applications must not treat the header-derived `shop` as authenticated by the HMAC check alone.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `raw_body` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, raw_body)`.
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256: H` to the app's webhook route, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app calls:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
   )
   ```
4. `Utils::HmacValidator.validate(request)` computes `HMAC(client_secret, raw_body)` and compares against `H` — it matches, since only `raw_body` is signed. [4](#0-3) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)`, and the handler processes the attacker's payload as if it were an authentic event from the victim shop. [2](#0-1)
