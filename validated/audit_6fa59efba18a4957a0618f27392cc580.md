### Title
Flash-position solvency checks reuse oracle prices fetched before an arbitrary receiver callback - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` prefetches all required prices into the invocation-local `Context` before minting debt and invoking the receiver callback. The callback can execute an already-ready governance operation that replaces the price-aggregator oracle configuration. After the callback returns, the controller still evaluates and finalizes the position using the pre-callback cached `PriceFeedRaw`, even though the oracle configuration committed during the same transaction.

### Finding Description
`process_flash_position` calls `prefetch_strategy_prices` before entering the guarded callback section, loading prices for the debt asset, declared collateral assets, and all existing account assets. [1](#0-0)  It then invokes the attacker-selected receiver contract before collecting collateral and finalizing the account. [2](#0-1) 

`Context` deliberately retains each fetched price for the rest of the invocation and only fetches missing assets. [3](#0-2)  `cached_price` therefore returns the old `PriceFeedRaw` after a later aggregator write. [4](#0-3) 

Governance `execute` accepts a ready, non-expired operation with no executor identity when `executor` is `None`. [5](#0-4)  A scheduled `ConfigureAssetOracle` operation resolves its oracle arguments and invokes `set_oracle` on the price aggregator. [6](#0-5) 

The callback is not reentering the controller or pool when it calls governance, so neither the flash guard nor the Soroban same-contract reentry rule blocks this sequence. `strategy_finalize` then performs solvency and health checks against `Context`, whose token-price entries remain stale. [7](#0-6) 

### Impact Explanation
An attacker can open or extend a leveraged account that is solvent only under the oracle price fetched before the callback. During the callback, the attacker executes the ready oracle reconfiguration and supplies the minimum declared collateral. The controller validates the resulting debt with the old price, while the committed oracle configuration immediately exposes the account's actual undercollateralized state to later liquidation or bad-debt cleanup.

A sufficiently adverse configuration change can therefore create protocol-insolvent debt. At minimum, it lets the attacker complete a risk-increasing strategy under an oracle snapshot that no longer represents the protocol's committed pricing configuration.

### Likelihood Explanation
Exploitation requires three conditions:

1. A `ConfigureAssetOracle` operation must already be scheduled and ready.
2. Its committed oracle output must differ enough from the previously fetched output to change the solvency result.
3. The attacker must control a flash-position receiver capable of calling `governance.execute` and then delivering the declared collateral.

The attacker does not need a governance role because ready operations can be executed with `executor: None`. [8](#0-7)  The vulnerability is conditional on governance timing, but the callback gives the attacker precise control over when the ready operation becomes visible relative to the controller's cached valuation.

### Recommendation
Do not let strategy risk checks reuse prices fetched before an arbitrary callback.

- Reload all required `PriceFeedRaw` values after `invoke_receiver`, before `process_deposit` and `strategy_finalize`; retaining cached values is unsafe across that boundary.
- Alternatively, record an oracle-registry version/config epoch before prefetching and require it to remain unchanged after the callback.
- Apply the same boundary rule to any router, Blend, token-hook, or receiver callback that occurs between price prefetching and final solvency evaluation.

### Proof of Concept
1. Governance schedules `ConfigureAssetOracle` for a collateral token, replacing its current source with a validated source that reports a lower price. The operation reaches `Ready`.
2. Attacker owns an existing `Multiply` account whose collateral is priced by that token.
3. Attacker calls:

   ```rust
   controller.flash_position(
       attacker,
       account_id,
       spoke_id,
       PositionMode::Multiply,
       debt_key,
       debt_amount,
       attacker_receiver,
       callback_data,
       collateral_minimums,
       refund_assets,
   )
   ```

   `debt_amount` is chosen so the account is solvent at the prefetched collateral price but insolvent under the oracle configuration committed by the ready operation.
4. Inside `execute_flash_position`, the receiver calls:

   ```rust
   governance.execute(
       None,
       price_aggregator,
       "set_oracle",
       resolved_set_oracle_args,
       predecessor,
       salt,
   )
   ```

   The receiver then transfers the declared collateral minimum to the controller.
5. After the callback returns, `collect_collateral_deposits` accepts the measured collateral, but `enforce_post_pool_solvency` still reads the collateral price cached before the governance execution.
6. The transaction commits both the new oracle configuration and the undercollateralized debt position.
