## Title
Webhook `shop` identity is not bound by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` value that webhook handlers treat as the tenant identity is taken from an HTTP header that is completely outside the signed payload. This breaks the binding `shop authenticated by HMAC == shop acted upon by the handler`.

## Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac == HMAC-SHA256(secret, verifiable_query.to_signable_string)`, i.e. it authenticates the body bytes, never the `shop` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header) to the app's handler as the trusted tenant identity, without any further check that this shop matches the shop the payload was actually generated for: [4](#0-3) 

Because the header is not part of `to_signable_string`, an attacker can change the `shop-domain` header on a request while keeping the body and its HMAC byte-for-byte identical, and the signature will still validate — the identity equality `shop bound by HMAC == shop delivered to handler` does not hold.

## Impact Explanation
A merchant who installs the target app on their own store (`attacker-shop.myshopify.com`) receives genuinely Shopify-signed webhooks for their own shop (valid body + valid HMAC using the app's real secret, since Shopify itself signs and delivers it). That merchant can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns true (body unchanged), `Registry.process` still dispatches to the handler, and `WebhookMetadata.shop` reports the victim's domain. Any app that keys per-tenant side effects (updating orders, inventory, billing state, GDPR redaction, etc.) off `data.shop` will apply the attacker's payload to the victim's tenant, i.e. cross-tenant access/manipulation without ever needing the victim's credentials.

## Likelihood Explanation
Likelihood is low-to-moderate: the attacker must be able to install the app themselves (or otherwise legitimately receive a signed webhook body they control the timing/content of, e.g. `orders/create` with attacker-chosen order fields) and must know/guess a victim shop domain, which is often discoverable/public. No secret material or privileged access is required — only normal merchant self-service installation, matching the "unprivileged internet user" threat model.

## Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material that `Utils::HmacValidator` checks, or otherwise cryptographically tie the header claims to the body — e.g., have `Registry.process` (or a documented consuming app) re-validate that `request.shop` corresponds to a shop with a known/expected relationship for this webhook subscription before invoking the handler, and update the docs to explicitly warn integrators not to trust `WebhookMetadata#shop` as authenticated unless cross-checked against the app's own registered-shop records.

## Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, gets the app to send/receive a legitimate webhook (e.g. `orders/create`) with a real `X-Shopify-Hmac-Sha256` computed over `raw_body` using the app's secret.
2. Attacker replays this exact `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`@raw_body` only) — validation succeeds because the body is untouched.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, causing the app to process attacker-supplied webhook content under the victim's tenant identity.
