## Title
Webhook `shop-domain` header is trusted for tenant identification without being cryptographically bound by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to app-registered webhook handlers directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` covers only the raw request body. Because the shop header is never part of the signed bytes, any caller who can obtain one genuine `(body, hmac)` pair for a shop can replay that exact pair to the same public webhook endpoint with an arbitrary, forged `shopify-shop-domain` header, and the request will still pass HMAC validation while being processed as if it originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from HTTP headers and are never included in the signed bytes: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header value: [3](#0-2) 

`Webhooks::Registry.process` performs no additional check that the `shop` header is consistent with anything else; once `HmacValidator.validate(request)` passes, it forwards `request.shop` (the raw header value) straight into `WebhookMetadata`, which the app-registered handler consumes as the tenant identifier: [4](#0-3) 

This is the exact bug class described in the reference report generalized to this gem: a field that is *acted on* (here, the `shop` used to attribute the webhook to a tenant and dispatched to the handler) is not covered by the cryptographic binding (the HMAC) that is supposed to authenticate the whole request. The identity equality that should hold is:

`shop_bound_by_signature == shop_used_for_tenant_dispatch`

but in this code it is actually:

`shop_used_for_tenant_dispatch = shop_header (unauthenticated)` while `shop_bound_by_signature` doesn't exist at all — only the body is signed.

Because `api_secret_key` (the app's `client_secret`) is a single value shared across every shop that installs the app, a genuine webhook delivery for any one tenant (including a shop the attacker legitimately controls, e.g. a free development/test store where they installed their own copy of the app) produces a `(raw_body, hmac)` pair that is valid *regardless of which shop it is replayed for*. An unprivileged attacker can:
1. Install the target app on a shop they control (or capture any legitimately delivered webhook, since delivery endpoints are public HTTP(S) URLs reachable by anyone, not just Shopify's IPs).
2. Record one valid `(raw_body, x-shopify-hmac-sha256)` pair from a webhook topic the app processes (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, or any topic whose handler performs a tenant-scoped side effect).
3. Replay that identical body/HMAC to the app's public webhook endpoint, but with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header set to an arbitrary victim shop domain.
4. `HmacValidator.validate` still returns `true` (it never looks at the shop header), so `Registry.process` dispatches the handler with `shop: <victim shop>` and the attacker-controlled body — causing the host application to perform tenant-scoped actions (session/token deletion on uninstall, data redaction, order/customer data processing, etc.) against the wrong tenant, entirely under attacker control of the payload content.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC check is meant to enforce: any shop→handler action taken in response to a webhook can be attributed to an arbitrary, attacker-chosen shop domain while carrying attacker-influenced body content, purely because the shop identity is read from an unsigned header. Depending on which webhook topics an integrating app registers, this enables cross-tenant data corruption/exfiltration or forced processing of privileged lifecycle events (e.g. `app/uninstalled`) against a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (a) the ability to install the app on any single shop (even a free development store, which is standard and requires no privileged access) or otherwise obtain one valid `(body, hmac)` pair, and (b) the ability to send an HTTP POST to the app's public webhook URL with custom headers, which is trivially available to any internet user since the webhook endpoint must be internet-reachable for Shopify to call it. No access to `api_secret_key`, access tokens, or any privileged credential is required.

### Recommendation
Bind the `shop` (and ideally `topic`) claim used for dispatch to the HMAC-verified content, e.g. by requiring `HmacValidator`/`Webhooks::Request#to_signable_string` to include the shop domain and topic in the signed material it checks, or by cross-checking `request.shop` against a shop that is independently known to have an active, previously-established session/installation before dispatching to handlers, rather than trusting the header value on its own once only the body's HMAC has been verified.

### Proof of Concept
```ruby
# Attacker has legitimately installed the target app on their own shop "attacker.myshopify.com"
# and observed a real webhook delivery for it (any topic the app registers, e.g. "app/uninstalled"):
raw_body = '{"id":1,...}'          # exact bytes Shopify sent
hmac     = "base64-hmac-from-shopify-for-that-body"  # valid because it's the real delivery

# Attacker replays the identical body+hmac to the same public webhook endpoint,
# but forges the shop header to point at a victim shop they do NOT control:
headers = {
  "x-shopify-topic"        => "app/uninstalled",
  "x-shopify-hmac-sha256"  => hmac,               # unchanged, still verifies against raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because only raw_body is checked
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with WebhookMetadata.shop == "victim-shop.myshopify.com",
#    even though the payload/HMAC were never issued for that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
