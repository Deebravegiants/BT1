### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never included in the HMAC-signed material. Since the `api_secret_key` used to compute the webhook HMAC is the same for every shop that has installed a given app, any party who legitimately receives one genuine webhook for their own shop can replay the identical body/signature pair to the app's webhook endpoint while substituting the `shop-domain` (and `topic`/`webhook_id`) headers, causing the app to process it as if it originated from a different shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler — none of which were part of the signed bytes: [4](#0-3) 

This breaks the identity binding `bytes_verified == bytes_acted_on`: the bytes verified by the HMAC are `{raw_body}`, but the bytes acted on to select the tenant are `{shop-domain header}`, which is disjoint from the signed content. Because the `api_secret_key` is shared across all shops that install the same app (it is not per-shop), a webhook payload legitimately delivered for shop A carries a signature that remains valid for the exact same body regardless of which shop's name is placed in the `x-shopify-shop-domain` header. An unprivileged party — for example, someone who has simply installed the app on their own free/dev store and thus legitimately receives real, validly-signed webhooks for that store — can capture one such payload and HMAC, then submit it again to the app's public webhook endpoint with the `shop-domain` header changed to point at a different merchant. `HmacValidator.validate` will report success because it never inspected the header, and the handler will receive `WebhookMetadata` claiming it is from the victim shop.

### Impact Explanation
This crosses a tenant boundary (Critical: cross-tenant access) without requiring the app's `client_secret`/`api_secret_key`, an access token, or TLS interception — only knowledge of one's own genuine webhook traffic, which any app installer legitimately possesses. Depending on how the host application's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up or mutate per-shop records, queue jobs, or update billing/usage state), this allows injecting attacker-controlled webhook bodies attributed to a victim shop, corrupting that shop's data or triggering shop-scoped side effects the attacker does not own.

### Likelihood Explanation
Any developer/merchant who installs the target app on a shop they control automatically receives real webhook deliveries signed with the app's shared `api_secret_key`. Replaying the exact same bytes with a modified `shop-domain` header requires no cryptography knowledge, only capturing one HTTP request and resending it with an edited header — a trivial, repeatable action from an "unprivileged internet user" position relative to any other tenant of the same app.

### Recommendation
Bind the tenant-identifying and routing fields into the signed material (or otherwise assert their authenticity) before they are trusted:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or perform a secondary check that the previously-verified body's own `shop_id`/`shop_domain` fields, when present in the JSON payload for the topic, match the header used for routing), or
- Document/require that consuming applications independently re-validate `request.shop` against their own installed-shop registry (verifying the shop is currently installed and matches the session that ownership of the webhook_id implies) before trusting it for any per-tenant state change, rather than trusting the header value outright.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and legitimately receives a real webhook, e.g. for "orders/create":
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the identical body+signature but swaps the shop-domain header
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC only covers raw_body

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though this payload never originated from Shopify for that shop.
```
