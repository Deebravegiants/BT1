### Title
Webhook `shop` identity not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw body, then unconditionally trusts the `X-Shopify-Shop-Domain` header as the tenant identity passed to the app's handler. Because the shop-domain header is not part of the signed material, the binding `shop authenticated by HMAC == shop delivered to the handler` does not hold, letting a merchant who has installed the app (an ordinary, unprivileged tenant) forge webhooks that are attributed to a different, victim shop.

### Finding Description
`Registry.process` is the entry point host apps are documented to call for every inbound webhook request: [1](#0-0) 

It performs exactly one authenticity check — `Utils::HmacValidator.validate(request)` — and, if that passes, hands `request.shop` straight into `WebhookMetadata`, which is the tenant-identifying value host apps are told to key their processing on: [2](#0-1) [3](#0-2) 

The HMAC check, however, is computed only over the raw request body: [4](#0-3) 

`hmac` is read from the `hmac-sha256` header and `to_signable_string` returns `@raw_body` — the shop-domain, topic, api-version and webhook-id headers are excluded from the signed data: [5](#0-4) 

Crucially, the `api_secret_key` used to compute/verify the HMAC is the app's single client secret — it is **not** per-shop. Any shop that has installed the app receives webhooks signed with that same secret. Consequently, an unprivileged attacker who installs the app on their own store can:
1. Trigger a webhook delivery to their own store and capture a request with a body `B` and a **valid** `hmac-sha256` value (since it was legitimately computed by Shopify with the shared app secret over `B`).
2. Replay that exact `(raw_body=B, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain.
3. `HmacValidator.validate` still succeeds — the HMAC only vouches for `B`, not for the shop header — and `Registry.process` forwards `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` to the app's handler.

This breaks the identity binding "shop authenticated by the cryptographic check == shop stored/used as the tenant key," a pattern explicitly called out as in-scope. Because Shopify's own documented `X-Shopify-Shop-Domain` header is unauthenticated relative to the HMAC, this gem's `Webhooks::Request`/`Registry` API provides no mechanism (and no warning) that would let a host app correctly bind body-authenticity to shop-identity — it is a defect in the gem's own webhook-verification contract, not merely host-application misuse, because the documented processing example (`docs/usage/webhooks.md`) trusts `data.shop` without any additional caveat.

### Impact Explanation
This maps to the Critical "cross-tenant access" impact category: an attacker who is a legitimate (but malicious) merchant of the app can cause the app to process attacker-supplied webhook data as if it originated from an arbitrary victim shop. If the host app's handler uses `data.shop` to decide which tenant's local records to create/update/delete (the exact usage pattern shown in this gem's own documentation), the attacker can inject or corrupt data attributed to another merchant's tenant — a cross-tenant data-integrity/access violation achieved purely through the credentials this gem exposes (its own webhook-verification API), without needing the victim's access token or any privileged access.

### Likelihood Explanation
Exploitation only requires installing the app as an ordinary merchant (a normal, unprivileged action any developer/attacker can take on a public app), capturing one legitimate webhook delivery, and replaying it with a modified header to the app's public webhook endpoint. No secrets, tokens, or elevated privileges are required, and the header-substitution step is trivial with any HTTP client. Likelihood is High for apps that key business logic off `data.shop` in the way the gem's own documentation recommends.

### Recommendation
Bind the verified body to the claimed shop, e.g., include `shop-domain` (and ideally `webhook-id`, `topic`, `api-version`) in the HMAC signable string, or have `Registry.process` cross-check the shop header against a server-side record (e.g., the webhook subscription previously registered for that specific shop/session) rather than trusting the header as authenticated purely because the raw body's HMAC validated. At minimum, document prominently that `data.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., matching against a known, pre-registered session for that shop).

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives a genuine webhook, e.g. for topic "customers/update":
raw_body = '{"id":1,"email":"attacker@example.com"}'
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key,  # shared app secret, same for every shop
  raw_body,
)

# Attacker replays the same body+hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "customers/update",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because it only checks raw_body against the shared secret
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(raw_body), ...))
# Host app now processes attacker-controlled data as belonging to "victim-shop.myshopify.com"
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
