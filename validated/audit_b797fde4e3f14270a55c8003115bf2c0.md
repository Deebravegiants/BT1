### Title
Webhook shop-domain (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but binds the HMAC only to the raw HTTP body, not to the `shop-domain`, `topic`, or `webhook-id` headers. `Webhooks::Registry.process` validates only that HMAC and then trusts the unauthenticated `shop` header to attribute the webhook to a tenant. Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app, any attacker who can obtain one validly-signed webhook body (e.g., from their own store) can replay that exact `(body, hmac)` pair while swapping the `shop-domain` header to a victim shop, and the gem will accept it as an authentic webhook "from" the victim.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight off HTTP headers with no cryptographic binding to the body or signature: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC purely over `to_signable_string` (i.e. the body): [3](#0-2) 

`Registry.process` gates on this HMAC check and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata handed to the app's handler: [4](#0-3) 

The equality the code implicitly assumes is:

`shop_header_value == shop_that_the_secret-holder(Shopify)_actually_signed_for`

But since the HMAC covers only the body bytes, the true invariant enforced is only:

`HMAC(body, api_secret_key) == received_hmac`

These two are not the same claim. `api_secret_key` is identical for every shop that installs a given app (it is the app's `client_secret`, not a per-shop secret), so a valid `(body, hmac)` pair computed for shop A's webhook delivery remains a valid `(body, hmac)` pair regardless of which `shop-domain` header accompanies it. An attacker who controls shop A (any developer/merchant who installs the app, which is an "unprivileged internet user" with respect to shop B) can:
1. Trigger a webhook delivery to their own app endpoint for a topic/body they control or can predict (many webhook payloads are deterministic or attacker-influenced, e.g. `app/uninstalled`, `shop/update`, or custom app metafield webhooks where the attacker owns the underlying resource).
2. Capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — this is a valid signature under the shared `api_secret_key`.
3. Replay that exact body+hmac to the app's webhook endpoint, but substitute `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it never looked at the shop header, and `Registry.process` calls the topic handler with `shop: "victim-shop.myshopify.com"` and the attacker's own (fully attacker-controlled) body content.

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on: the gem asserts "this data came from Shopify for shop X" whenever `HmacValidator.validate` passes, but `shop` (X) is not part of what was verified. A host application that keys any state (installation status, order records, GDPR data requests, customer data, `app/uninstalled` deprovisioning, etc.) off `WebhookMetadata#shop` as returned by this gem can be made to apply attacker-controlled webhook bodies to a victim shop's tenant record — i.e., cross-tenant access/data corruption, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action any merchant/developer can perform for a public or unlisted app) and obtain one webhook delivery whose body they can predict or influence, plus the ability to send an arbitrary HTTP request to the app's webhook endpoint with a forged `shop-domain` header — no access token, `client_secret`, or privileged credential is needed. The main constraint is finding a topic/body combination whose content is attacker-controlled or deterministic enough to be useful against a victim, which is realistic for topics like `app/uninstalled`, `shop/update`, or metafield/webhook subscriptions the attacker's own store can generate.

### Recommendation
Include the authenticating tenant identifier (`shop-domain`) — and ideally `topic`/`webhook-id` — inside the signable material that `HmacValidator` verifies for webhook requests, or otherwise cryptographically bind the header values to the signature, so that `Registry.process` cannot be made to attribute an attacker-supplied body to an arbitrary shop. At minimum, document prominently that `request.shop` is unauthenticated and that host applications must independently verify shop ownership/installation state before trusting webhook payload attribution.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Attacker triggers (or crafts, for a topic whose payload is attacker-controlled) a webhook delivery, capturing:
   - `raw_body = B`
   - `x-shopify-hmac-sha256 = HMAC-SHA256(B, api_secret_key)` (valid, since `api_secret_key` is the same for all installs of this app)
2. Attacker sends a forged HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged, still validly signed)
   - Headers: `x-shopify-topic: <topic>`, `x-shopify-hmac-sha256: <captured hmac>`, `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` runs:
   - `Utils::HmacValidator.validate(request)` → `true`, because it only recomputes `HMAC(B, api_secret_key)` per [1](#0-0)  and [5](#0-4) .
   - `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"` per [6](#0-5) , even though the body `B` was signed for `attacker-shop.myshopify.com`.
4. The host app's handler executes business logic (e.g., updates records) attributing attacker-controlled body content to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
