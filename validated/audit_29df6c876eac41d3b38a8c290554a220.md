### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate(request)` succeeds, and then hands `request.shop` — taken verbatim from the unauthenticated `X-Shopify-Shop-Domain` header — to the app's webhook handler as the tenant identifier. The HMAC signature, however, only covers the raw request body, never the `shop` header, so "the shop whose signature was verified" and "the shop the handler is told to act on" are two different, unbound values.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, with no relation to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately forwards `request.shop` to the handler as the authenticated tenant: [3](#0-2) 

`HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and the app's shared `api_secret_key`: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret (not per-shop), any shop that installs the app can receive legitimately Shopify-signed webhooks for itself. An attacker who controls such a shop can capture a genuine `(raw_body, hmac)` pair from their own webhook deliveries, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), but `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain — the equality the library implicitly assumes, `hmac-authenticated shop == request.shop`, does not hold.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to key persistence, side effects, and access-token lookups by webhook `shop`. Any handler that trusts `WebhookMetadata#shop` (as the documented and only means of tenant attribution provided by this gem) can be made to process attacker-supplied data (payload content the attacker fully controls via their own shop's install) under a victim shop's identity — i.e., cross-tenant data injection/confusion via a forged-but-"validated" webhook. This matches the Critical "cross-tenant access" impact category, since the boundary crossed is enforced entirely within this gem's own webhook verification code path.

### Likelihood Explanation
Any user can freely install the target app on a shop they control (a normal, unprivileged action) and thereby obtain arbitrarily many genuinely-signed `(body, hmac)` pairs for that shop, since `api_secret_key` is shared across all installs of the app. No leaked credentials, TLS interception, or privileged access are required — only crafting an HTTP request with a substituted header, which is directly reachable through the gem's own `Webhooks::Registry.process`/`Webhooks::Request` API.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the HMAC-signable content, or otherwise require the caller/framework to independently corroborate `request.shop` against a known-installed-shop list before treating the header as authenticated. At minimum, `Registry.process` should document/enforce that `request.shop` must not be treated as verified purely because `Utils::HmacValidator.validate(request)` passed, and should provide a validated binding between the two.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`, receiving genuine webhooks from Shopify signed with the app's `api_secret_key`, e.g. body `{"foo":"attacker-controlled"}` with header `X-Shopify-Shop-Domain: attacker.myshopify.com` and a valid `X-Shopify-Hmac-Sha256`.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, replacing only `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this request; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the (correct, shared) HMAC.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: {"foo"=>"attacker-controlled"}, ...)`, causing the host app to act on attacker-controlled data as if it originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
