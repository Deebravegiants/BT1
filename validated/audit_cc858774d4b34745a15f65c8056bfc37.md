### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), event type (`topic`) and idempotency key (`webhook_id`) exclusively from HTTP headers, while the HMAC signature that `Registry.process` relies on to authenticate the request only covers the raw request body. Any actor who can obtain one authentically-signed webhook body/HMAC pair for their own (attacker-controlled) shop can replay that exact body to the app's webhook endpoint with a forged `shop-domain` header claiming to belong to a different, victim tenant, and the signature check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `api_version` and `webhook_id` are all read straight from attacker-controllable HTTP headers, with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the *entire* request, then dispatches the handler using the unauthenticated `shop` header as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`hmac_verified(shop_header) == shop_that_actually_sent_the_event`

What is actually verified is:
`hmac_verified(raw_body) ⟂ shop_header` (no relation)

**Before the attack**: Shopify signs webhook payload `B` with the app's shared `client_secret` and delivers it to the attacker's own shop, `attacker-shop.myshopify.com`, with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC(B)`.

**Attacker's request sequence**: The attacker (any user able to install the app on a store they control — no privileged credentials needed) captures this legitimate `(B, HMAC(B))` pair, then sends a new HTTP request to the same app's webhook endpoint reusing body `B` and `HMAC(B)`, but substitutes `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).

**After the attack**: `HmacValidator.validate` still succeeds because it only checks `B` against `HMAC(B)`; `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though Shopify never sent this event for that shop.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a documented, expected usage pattern — see `handler.handle(data: WebhookMetadata.new(topic:, shop:, body:, ...))`) can be made to apply attacker-supplied data to a different merchant's records, i.e., cross-tenant access/data injection, satisfying the "Critical - cross-tenant access" bar. No access token, `api_secret_key`, or leaked credential is required — only the ability to install the app on one's own store and observe one genuine webhook delivery.

### Likelihood Explanation
Any Shopify App Store install is normally open to any merchant, so obtaining one authentic `(body, hmac)` pair is trivial for an unprivileged actor. Sending a forged HTTP POST with modified headers to the app's public webhook endpoint requires no special access. The only constraint is that the replayed body's content must be usable against the victim's tenant context (attacker-controlled resource IDs, generic topics like `app/uninstalled` or `shop/update`, etc.), which is easily engineered by choosing which webhook topic to capture.

### Recommendation
Include the tenant-identifying and dispatch-relevant fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload, or otherwise verify that the `shop-domain` header used for dispatch matches an out-of-band, trusted source (e.g., the currently active/expected session shop) before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be trusted as strong tenant identifiers by consuming apps.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own store and receives a real webhook.
raw_body = '{"id": 1, "note": "hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# This is exactly what Shopify would send to the attacker's shop.
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# 2. Attacker forges the shop header, reusing the *same* body/hmac.
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation still passes because it only checks the raw body.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches the handler believing this event is for victim-shop.
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...}, ...))
```
