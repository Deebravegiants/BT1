### Title
No fallback when Chainlink oracle is stale/non-positive causes total denial-of-service of `SimplexPaymaster` gas payment path - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices every ERC-20 gas payment via `_getOraclePrice`, which unconditionally reverts if the Chainlink feed returns a non-positive answer or a stale `updatedAt`, with no fallback oracle, cached price, or graceful degradation path. Because `_fetchDetails` (called during ERC-4337 validation on every UserOperation) and `swapAndDeposit` both depend on this function, an oracle outage, admin pause, or heartbeat miss deterministically bricks the paymaster for all users of the affected token — an unprivileged bandwidth purchaser cannot get their Hyperbridge-related UserOperation sponsored via this token, exactly mirroring the reported bug class ("no fallback if oracle goes down or price reaches 0").

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and reverts with `InvalidOraclePrice` or `StaleOraclePrice` on any non-positive or stale answer, with no fallback: [1](#0-0) 

This is invoked from `_tokenPrice`, which is invoked from `_fetchDetails` — the function `PaymasterERC20` (and thus the ERC-4337 `EntryPoint`) calls on every single UserOperation validation to determine what token/price to charge: [2](#0-1) 

`swapAndDeposit`, the only mechanism to recycle collected stablecoin fees into native EntryPoint deposit (which keeps the paymaster funded/staked so bundlers keep relaying), has the identical unconditional dependency on both `nativeOracle` and the token oracle: [3](#0-2) 

The project's own design-decision log confirms this stale-oracle DoS was identified and explicitly deferred rather than fixed: [4](#0-3) 

There is no try/catch, no secondary price source, no cached last-good price, and no manual override path — `_registerToken`'s comment notes re-registration via governance is the "recovery path," but that requires a governance round-trip (proposal → dispatch → relayer delivery → `onAccept`) which cannot happen instantly and does not help while the feed is merely stale/paused rather than replaced.

### Impact Explanation
Any transient Chainlink outage (feed pause, sequencer/heartbeat miss, multisig pause as OpenZeppelin's blog describes, or a temporarily non-positive answer) permanently blocks every ERC-4337 UserOperation attempting to pay gas through this token via `SimplexPaymaster` — this is the sole entry point `PaymasterERC20`/`EntryPoint` route through, so no unprivileged UserOp can bypass it while affected. Because `swapAndDeposit` shares the same code path, the paymaster's own EntryPoint deposit also cannot be topped up during the outage, risking the paymaster running out of stake/deposit and being dropped by bundlers entirely — a broader denial-of-service beyond a single stale price. This matches the "route unable to deliver messages/transactions" impact bar, since any Hyperbridge-related dispatch bundled behind a UserOperation sponsored by this paymaster cannot execute.

### Likelihood Explanation
Chainlink feed staleness/pauses are a well-documented, non-hypothetical occurrence (referenced directly in the original report), and `maxOracleAge` is configurable per chain down to as little as needed for BSC feeds (~27s heartbeats per the code comment), making even brief feed delays trigger the revert. No attacker action is required — this is a passive external dependency failure with guaranteed DoS impact, and the project's own documentation shows the team was aware and chose not to fix it for this pass.

### Recommendation
Add a bounded fallback: cache the last valid `(price, updatedAt)` per oracle and allow use of the last-known-good price within a wider "emergency" staleness window when the primary check fails, or support a secondary oracle/price source configurable via the existing governance `RegisterToken`/`UpdateParams` flow. At minimum, expose a governance-gated manual price override that can be set in a single transaction without waiting for a new oracle deployment, so the recovery path does not require re-registering an entirely new feed.

### Proof of Concept
1. Governance registers `tokenOracle` for USDC and `nativeOracle` for the chain's native asset via `RegisterToken`/`UpdateParams`.
2. The Chainlink aggregator backing `nativeOracle` is paused by its own multisig/DVT for maintenance, or its `updatedAt` exceeds `maxOracleAge` due to a heartbeat miss (a real, documented Chainlink behavior).
3. Any user submits a UserOperation with `paymasterData` mode `0x00`/`0x02` targeting USDC. `EntryPoint` calls `validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(nativeOracle, ...)`, which reverts with `StaleOraclePrice`.
4. Every UserOperation using this paymaster now reverts at validation, for as long as the oracle remains stale/paused — with no code path to recover the paymaster's operation short of a governance round-trip to swap the oracle, which cannot be a real-time fix for a temporary feed disruption.
5. Simultaneously, `treasury` cannot call `swapAndDeposit` (same revert path), so the paymaster's EntryPoint deposit cannot be replenished during the outage.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }

# 2026-08-19 — Not adopted: soft-failing the prefund, and oracle-derived validity bounds (#1071)

Rejected: returning `prefunded = false` instead of reverting in the mode-2 `_prefund`.
