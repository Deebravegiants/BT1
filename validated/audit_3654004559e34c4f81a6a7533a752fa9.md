### Title
Permissionless position-map pollution: any stranger can inject attacker-chosen `HubAssetKey` entries into a victim's `SupplyPositions` map, blocking the victim from adding collateral — (`contracts/controller/src/account.rs` + `contracts/controller/src/positions/supply.rs`)

### Summary
The keyget bug class is prototype pollution: an attacker-controlled key (`set`, `push`, `at`) is written into an object the victim relies on, so later logic iterates/reads properties the victim never created. The on-chain analog in this codebase is the per-account `SupplyPositions` map stored under `ControllerKey::SupplyPositions(account_id)`. The `supply` path is callable by an unprivileged third party against any existing `account_id`, and each call inserts a new `HubAssetKey` key into the victim's supply map. The victim's risk engine then iterates that polluted map on every borrow, withdraw, liquidation, and `update_account_threshold`, and the account's position-slot limit is consumed by dust entries the owner never asked for.

### Finding Description
Supply-side entrypoint resolution goes through `load_or_create_account` with `AccountGuard::Supply`. For `Supply`, the only check is `require_spoke_match` — there is no owner/delegate authorization, so any caller may supply into any existing account [1](#0-0) . This is confirmed by harness tests where `CAROL` supplies dust into `ALICE`'s account (`t.supply_to(CAROL, account, "USDC", 0.0000001)`) [2](#0-1) .

Each such call creates or grows an entry in the victim's `Map<HubAssetKey, AccountPositionRaw>` under `ControllerKey::SupplyPositions(account_id)`, which is persisted wholesale by `write_side_map` [3](#0-2) . The account's usable position slots are bounded by `PositionLimits.max_supply_positions`, and every risk evaluation iterates `account.supply_positions.keys()` — both in `sync_account_thresholds` [4](#0-3)  and in `calculate_account_risk_totals`, which also forces a fresh, in-band oracle price for every listed key [5](#0-4) .

The pollution has two attacker-relevant effects beyond gas:

1. **Slot exhaustion.** The attacker supplies one stroop of each listed asset in the victim's spoke until `SupplyPositions` reaches `max_supply_positions`. The victim can no longer supply the collateral asset of their choice to rescue a declining health factor — the supply fails on the position limit. The dust entries are economically useless (sub-dust balances) but occupy real slots.
2. **Forced restamp surface.** Each injected supply triggers `refresh_supply_risk_params` on the victim's account [6](#0-5) , and every subsequent `update_account_threshold`/supply must load the spoke config and oracle price for each injected key. The victim cannot remove a key without withdrawing it fully, and withdrawal is gated on post-withdraw HF — so a near-limit victim cannot shed poisoned collateral entries without first reducing debt.

### Impact Explanation
This maps to **temporary freezing of funds** and, in the worst case, **theft of user funds via forced liquidation**. A victim whose collateral ratio is decaying (interest accrual or price drift) normally rescues the position by supplying additional collateral. With the supply map filled to `max_supply_positions` by attacker dust, that rescue path is closed: `supply` reverts on the slot limit for any *new* `HubAssetKey`, and the dust keys the attacker chose may be assets the victim holds none of. The victim's remaining escape is repaying debt, which requires holding the debt asset — not always available, especially for leveraged/multiply positions. If HF crosses 1.0 while the rescue path is blocked, a liquidator seizes the victim's collateral with bonus — a concrete loss attributable to the injected keys. Severity is bounded to **Medium**: the attack costs real transfers (one nonzero supply per slot, bounded by dust thresholds and the position cap, e.g. `max_supply_positions: 5` in the admin flow [7](#0-6) ), the victim retains the repay path, and dust/cap parameters dilute the attack.

### Likelihood Explanation
Fully permissionless: `supply(caller, account_id, spoke_id, assets)` requires only `caller.require_auth()` and a spoke match — no owner or delegate check on the target account [1](#0-0) . The attacker needs only funded balances of the spoke's listed assets and knowledge of victim `account_id`s (public NFT token ids). No oracle manipulation, privileged role, or timing window is required — the pollution persists until the victim withdraws the dust positions, which itself consumes a transaction and HF headroom per key.

### Recommendation
Gate third-party supply so it cannot create *new* position entries on accounts the caller does not control. Concretely: in the `AccountGuard::Supply` path of `load_or_create_account`, when `account_id != 0` and `caller != owner`/delegate, require that every supplied `HubAssetKey` already exists in `get_supply_positions(account_id)` — i.e., strangers may top-up existing legs but may not insert new keys into the map. Alternatively, credit unsolicited new-asset supplies to a separate claimable balance rather than materializing a position slot, or enforce a minimum first-supply amount per key so slot exhaustion is uneconomical.

### Proof of Concept
1. Attacker `EVE` observes victim `ALICE`'s account `A` in spoke `S` with `max_supply_positions = N` and `k < N` existing supply positions.
2. `EVE` calls `controller.supply(caller=EVE, account_id=A, spoke_id=S, assets=[(hub_asset_i, 1 stroop) for i in 1..(N-k)])` — each call passes `AccountGuard::Supply` (spoke match only) and inserts a new `HubAssetKey` into `SupplyPositions(A)` via `write_side_map` [8](#0-7) .
3. `A`'s supply map now holds `N` entries, `N-k` of which are dust. `ALICE` attempts `supply` of a new collateral asset to improve HF → reverts with the position-limit error (no free slot).
4. `ALICE` attempts `withdraw` of an attacker dust key to free a slot → permitted only if post-withdrawal HF stays ≥ 1; near the liquidation boundary this reverts.
5. Debt interest accrues (`millisecond chunked accrual` on the pool index), HF crosses 1.0, and a liquidator executes `liquidate` against `A`, seizing collateral with the stored bonus — loss realized while the rescue path was blocked by injected keys.

Note on residual uncertainty: the exact revert site for the position-limit check (likely in `positions/supply.rs`/`risk/validation.rs` consuming `PositionLimits`) was not read line-by-line in this pass, so the precise error name is unverified — but the limit's existence and enforcement are established by `set_position_limits` and `PositionLimits` usage [7](#0-6) .

/// Stores a nonempty position map without renewing TTL; deletes an empty map.
fn write_side_map<V: TryFromVal<Env, Val> + IntoVal<Env, Val>>(
    env: &Env,
    key: &ControllerKey,
    map: &Map<HubAssetKey, V>,
) {
    let persistent = env.storage().persistent();
    if map.is_empty() {
        persistent.remove(key);
    } else {
        persistent.set(key, map);
    }
}
