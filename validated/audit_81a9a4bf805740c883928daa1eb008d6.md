### Title
`Oauth.validate_auth_callback` sends the app's `client_secret` to a shop host that is never checked against the trusted Shopify domain allow-list - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds an `HttpClient` whose request host is derived directly from `auth_query.shop` and then POSTs a body containing `Context.api_secret_key` to that host. Unlike every other credential-issuing flow in this gem — `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` — this path never calls `Utils::ShopValidator.sanitize!` on the shop value before it is used to construct the request destination that receives the `client_secret`.

### Finding Description
The equality that should hold before the app's `client_secret` is sent over the wire is:

`host that receives client_secret == host validated against ShopValidator::TRUSTED_SHOPIFY_DOMAINS`

In `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`, this equality is enforced explicitly: [1](#0-0) [2](#0-1) 

Both call `Utils::ShopValidator.sanitize!(shop)` — which restricts the shop to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the `Session`/`HttpClient` that will carry `client_secret`: [3](#0-2) 

`Oauth.validate_auth_callback`, however, takes `auth_query.shop` unchanged, builds a `null_session` directly from it, and sends the `client_secret`-bearing request through that session: [4](#0-3) 

`HttpClient#initialize` derives the request host straight from `session.shop` with no domain allow-list check of its own: [5](#0-4) 

The only guard applied before this is `Utils::HmacValidator.validate(auth_query)`, which authenticates the *signable string* (`code`, `host`, `shop`, `state`, `timestamp`) against the app's `api_secret_key`: [6](#0-5) [7](#0-6) 

That HMAC binds the *content* of `shop` to a value Shopify's servers signed, but it says nothing about whether that value is a Shopify domain — it will happily validate for any string Shopify chose to sign (which is expected to always be a real `*.myshopify.com` host, but the library never independently verifies this). Because `shop` is only checked for tamper-evidence, not domain trust, the field that is bound (signature integrity) is not the same field this specific code path relies on for safety (destination-host trust) — exactly the "field acted on but not covered/validated the same way as the sibling flows" pattern.

### Impact Explanation
If the value in `auth_query.shop` is ever not constrained to a genuine Shopify-owned domain (e.g. bugs upstream in Shopify's redirect construction, or any caller/environment where the callback's `shop` parameter can diverge from a myshopify-style host — the gem's own `ShopValidator` module exists specifically because "verify shop domain is a subdomain of `.myshopify.com` when creating the session" was previously identified as necessary defense-in-depth, per the CHANGELOG), the app's `client_secret` and `code` are transmitted directly to that host with no allow-list enforcement inside this function. That is a High-impact credential-leakage vector: the app's `client_secret`, which lets an attacker mint OAuth access tokens for the app, would be sent to an untrusted destination.

### Likelihood Explanation
Likelihood is limited by the fact that a valid HMAC over the query (computed with the shared `api_secret_key`) is still required, and legitimate Shopify callbacks are expected to only ever carry a trusted myshopify domain in `shop`. The finding is therefore a defense-in-depth gap/inconsistency rather than a demonstrated remote forgery: this codebase cannot prove an attacker can produce a valid-HMAC `auth_query` with an arbitrary `shop` value without already possessing `api_secret_key`. The library's own design pattern (sanitizing `shop` in `client_credentials.rb` and `refresh_token.rb` before it reaches `HttpClient`) shows that the intended invariant is "always sanitize/validate the shop domain before it is used as a client_secret-carrying request destination," and `oauth.rb#validate_auth_callback` is the one flow that skips this step.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring the pattern already used in `client_credentials.rb` and `refresh_token.rb`, so the host that receives the `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently demonstrable within this gem's own code without already holding `api_secret_key` to forge a valid HMAC, since `HmacValidator.validate` gates the call. This is reported as a defense-in-depth/consistency gap relative to the equivalent, sanitized flows (`client_credentials.rb`, `refresh_token.rb`) rather than a proven exploit chain.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
