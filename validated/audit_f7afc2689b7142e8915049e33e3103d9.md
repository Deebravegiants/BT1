### Title
Webhook HMAC verification does not bind the `shop`/`topic` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts an inbound webhook if `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is computed only over the raw request body. The `shop`, `topic`, `webhook-id`, and `api-version` values are taken directly from unauthenticated HTTP headers and are never covered by the signature, so any internet-facing party who possesses one genuinely-signed `(body, hmac)` pair for the app can replay that pair while freely substituting the `shop-domain` (and `topic`) header to impersonate a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read straight from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` only checks that `hmac == HMAC-SHA256(secret, to_signable_string)`, i.e. it authenticates the body bytes against the app's single, shop-agnostic `api_secret_key` — it never authenticates which shop or topic the request claims to be for: [3](#0-2) 

`Registry.process` then trusts `request.shop` and `request.topic` (both parsed from headers, not from the signed payload) to build `WebhookMetadata` and dispatch it to the registered handler: [4](#0-3) 

The equality the code implicitly assumes but never enforces is:
`shop_that_produced_the_signed_body == request.shop_header_used_by_the_handler`

Because `api_secret_key` is one value per app (shared across every shop that installs the app), any attacker who legitimately installs the app on their own store can trigger a real webhook, capture the valid `(raw_body, hmac)` pair Shopify sent, and then send that exact body/HMAC pair directly to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain (and/or a different `x-shopify-topic`). `HmacValidator.validate` still returns `true` because the body bytes are unchanged, and `Registry.process` passes the attacker-chosen `shop`/`topic` straight to the handler as if it were authentic.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce: the host application's handler receives `WebhookMetadata` tagged with an arbitrary victim shop domain that it has no independent way to distinguish from a real webhook, since the library exposes no verified binding between the cryptographic proof and the claimed tenant. Depending on how the host app's handler uses `shop` (e.g., looking up/updating records, triggering side effects, invalidating data) keyed by that field, this enables cross-tenant data corruption or cross-tenant action injection under the guise of a verified webhook — matching the report's underlying bug class of "identity field acted upon but not covered by the HMAC," adapted here to the `shop`/`topic` headers instead of body-only replay.

### Likelihood Explanation
Exploitation only requires an attacker to be a normal, unprivileged merchant/user who can install the target app on a store they control (a routine, low-privilege action for public or trial apps) to obtain one valid `(body, hmac)` pair, then issue a direct HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No `api_secret_key`, access token, or elevated access is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the value that is HMAC-verified, or independently cross-check that the `shop` header matches a shop that is known to have a currently active registration/session for this app before dispatching to the handler, rather than trusting header-derived `shop`/`topic` values whose authenticity was never covered by the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (no special privilege needed).
2. Attacker triggers any subscribed event (e.g., `orders/create`) on their own shop; Shopify sends a webhook to the app with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's `api_secret_key`.
3. Attacker captures the exact raw body and HMAC header value from this legitimate delivery.
4. Attacker crafts a new HTTP POST directly to the app's public webhook endpoint, using the identical raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body bytes and returns `true`; it then invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, so the host app processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.           if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
