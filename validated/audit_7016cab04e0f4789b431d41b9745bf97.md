### Title
Unsigned `shopify-shop-domain` / `shopify-topic` headers are trusted as webhook identity — `Registry.process` binds `WebhookMetadata#shop` to an unauthenticated header ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#topic`, `#shop`, and `#api_version` return raw values from the `shopify-*` / `x-shopify-*` HTTP headers with no cryptographic protection, and `Utils::HmacValidator.validate` (called from `Registry.process`) only verifies the HMAC over `to_signable_string`, which is `@raw_body` — the headers are never included in the signable string. `Registry.process` then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.api_version` and hands it to the host app's handler, so the "shop" and "topic" the handler acts on are unauthenticated.

### Finding Description
The binding that should hold is: `shop authenticated by the HMAC signature == shop delivered to the handler (WebhookMetadata#shop)`. Tracing the code:

- `Request#topic`, `#shop`, `#api_version` simply read `shopify_header(...)`, which pulls straight from `@headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]` with no validation: [1](#0-0) , [2](#0-1) .
- `Request#to_signable_string` returns only `@raw_body`, not the headers: [3](#0-2) .
- `HmacValidator.validate` / `validate_signature` compute the HMAC solely over `to_signable_string` (the body) and compare against `request.hmac`: [4](#0-3) . The `shopify-shop-domain`, `shopify-topic`, and `shopify-api-version` headers are never part of the signed material.
- `Registry.process` validates the HMAC, then dispatches purely on the unauthenticated `request.topic`, and constructs `WebhookMetadata` from `request.shop`, `request.topic`, and `request.api_version` — all unauthenticated header values — before calling `handler.handle(data: ...)`: [5](#0-4) .
- `WebhookMetadata#shop` is a plain `T::Struct` field with no independent verification: [6](#0-5) .

Attacker flow: an unprivileged attacker creates their own development shop, installs the app, and registers their own webhook endpoint (or simply captures any legitimately-signed webhook delivery for their own shop, which is signed with the app's `api_secret_key` — the same secret used for every shop on the app). That HMAC is valid over the request body regardless of which headers accompany it, because headers are excluded from the signable string. The attacker then replays that exact body + valid HMAC to the target app's real webhook endpoint, but substitutes the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-api-version` headers to name an arbitrary victim shop/topic. `HmacValidator.validate` still passes (it only checks the body signature), `Registry.process` dispatches to the handler registered for the forged topic, and the host app receives `WebhookMetadata#shop` = victim shop even though the payload actually originated from the attacker's own shop and was never sent by Shopify for that victim.

Existing guards do not prevent this: `HmacValidator.validate` checks only body integrity, not header authenticity; there is no `ShopValidator.sanitize!` call on `request.shop`; there is no session, JWT, or host binding anywhere in this webhook code path — `Auth::Session`, `JwtPayload`, and `@base_uri` are simply not part of this flow, so those specific cross-checks the question invokes do not exist here and cannot be relied upon to catch the divergence.

### Impact Explanation
The host app's handler (`WebhookHandler#handle`) is the only consumer of `WebhookMetadata`, and per the gem's documented contract it is expected to trust `data.shop` and `data.topic` to decide which merchant's records to update, delete, or redact (this is exactly the intended use for topics like `shop/redact`, `customers/redact`, `customers/data_request`, and ordinary business-data webhooks). Because `shop` and `topic` are unauthenticated header values, an attacker can cause the host app to attribute attacker-supplied webhook content to an arbitrary victim shop of the attacker's choosing. This is cross-tenant data corruption/confusion at the webhook-processing layer — an attacker's payload is processed under a victim shop's identity — matching the Critical "cross-tenant access" impact class. It is repeatable against any shop identifier the attacker chooses to put in the header, with no per-victim secret needed.

### Likelihood Explanation
Preconditions are minimal and fully within the attacker's stated capability set: register or observe one legitimately-signed webhook body for their own shop (trivial, self-service), then replay the body with forged `x-shopify-shop-domain` / `x-shopify-topic` headers to the target app's public webhook endpoint. No `api_secret_key`, access token, or victim cooperation is required. This is inexpensive and repeatable at will.

### Recommendation
Include the shop domain, topic, and API version headers in the HMAC-signed material (or otherwise cryptographically bind them to the body), and/or have `Registry.process` independently validate `request.shop` against `ShopValidator.sanitize!`/a known-installed-shop check before constructing `WebhookMetadata`, rather than trusting the raw unauthenticated headers for tenant attribution.

### Proof of Concept
```ruby
# test/webhooks/registry_forged_shop_test.rb
require "test_helper"

class RegistryForgedShopTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @captured = nil
    handler_class = Class.new do
      include ShopifyAPI::Webhooks::WebhookHandler
      define_method(:handle) { |data:| RegistryForgedShopTest.captured = data }
    end
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/x", handler: handler_class.new
    )
  end

  def self.captured; @captured; end
  def self.captured=(v); @captured = v; end

  def test_body_signed_for_attacker_shop_is_accepted_with_forged_shop_header
    body = '{"id":1}'
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", body)).strip

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-hmac-sha256" => hmac,          # valid for attacker's own shop's body
        "x-shopify-topic" => "orders/create",
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unsigned
        "x-shopify-api-version" => "2024-01",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    assert_equal "victim-shop.myshopify.com", RegistryForgedShopTest.captured.shop
    # demonstrates handler received attacker-controlled body attributed to an arbitrary
    # victim shop, despite HMAC validation succeeding, because the shop header is unsigned.
  end
end
```
Both sides of the intended binding (`hmac-verified identity` vs `WebhookMetadata#shop`) diverge: the HMAC only proves the body's origin, while `shop`/`topic` are freely attacker-chosen, confirming the vulnerability.
