### Title
Webhook HMAC Only Covers Request Body, Not the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only ever covers the raw request body. Any party who can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` — e.g. by installing the app on their own store — can replay that same body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The signature still validates because the header is never part of the signed material, so the handler is invoked believing the event belongs to a victim shop it never came from.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are all read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` uses this validation result as the sole authentication check, then trusts `request.shop` and `request.topic` to build the metadata handed to the app's business logic: [4](#0-3) 

The identity-binding equality the library implicitly claims is:
`hmac_valid(body) == authenticated(shop, topic, webhook_id)`
but the actual guarantee is only `hmac_valid(body) == authenticated(body)`. The `shop` (and `topic`/`webhook_id`) fields that the handler acts on are never bound to the signature, breaking the equality that `Registry.process` relies on to authenticate which tenant an event belongs to.

Because `api_secret_key` is the app's single shared client secret (identical for every installed shop, per `ShopifyAPI::Context`), any unprivileged party who installs the app on their own store can receive real, validly-signed webhooks. They can then take the `(raw_body, x-shopify-hmac-sha256)` pair from a webhook triggered on their own shop and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop's domain. `HmacValidator.validate` will still pass, since it never inspects that header, and the app's webhook handler will process the payload as if it originated from the victim shop.

### Impact Explanation
This breaks the cross-tenant boundary the webhook mechanism is supposed to enforce: an attacker-controlled event body can be attributed to any target shop. Depending on what a host application does with `WebhookMetadata#shop` (session/token lookups, data writes, triggering `app/uninstalled` cleanup, etc.), this enables cross-tenant data injection or corruption for shops the attacker does not control — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires the ability to install the app on a shop the attacker controls (an ordinary, unprivileged action available to any merchant) and the ability to send an HTTP POST to the app's public webhook URL — no secret key, access token, or privileged access is required. The forged request is a byte-for-byte replay of a real webhook body/signature with only an HTTP header changed.

### Recommendation
Include the identity-relevant fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g., by having the handler independently verify that the `shop` header corresponds to an installation with a session/token on record before trusting it), so that the signature check actually authenticates the tenant, not just the body bytes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` sent by Shopify (valid because it's HMAC-SHA256(`B`, app's `client_secret`)).
2. Attacker crafts a new POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - Header `x-shopify-topic`: same or different topic as desired
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, secret) == H`.
4. The webhook handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-supplied data as belonging to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
