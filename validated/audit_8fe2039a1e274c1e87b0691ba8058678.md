### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable HMAC over `@raw_body` only [1](#0-0) , yet exposes `shop`, `topic`, `api_version`, and `webhook_id` as plain header reads that are never included in the signed content [3](#0-2) . `Registry.process` accepts the request once `Utils::HmacValidator.validate(request)` succeeds against the body, then forwards `request.shop` and the other unsigned fields straight into `WebhookMetadata` for the app's handler [4](#0-3) .

### Finding Description
`HmacValidator.validate_signature` recomputes the HMAC exclusively from `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare` [2](#0-1) . For webhooks, `to_signable_string` is defined as `@raw_body` alone [1](#0-0) . This means the cryptographic guarantee provided by the HMAC is: "this body was produced using the app's `client_secret`" — nothing more. It says nothing about which shop, topic, or webhook the body is associated with.

The binding that should hold is: `hmac_signed_bytes == bytes_the_handler_trusts_as_identity`. In this code, the actual equality is `hmac_signed_bytes == @raw_body`, while `handler_trusted_identity == headers["shop-domain"]/["topic"]/["webhook-id"]`, i.e. bytes that are read from the HTTP request but excluded from the signable string. Since Shopify apps share one `client_secret` (and therefore one HMAC key) across all shops that install the app, any entity capable of receiving one genuinely-signed webhook body (e.g. by installing the app on a shop they control) possesses a `(body, valid_hmac)` pair that remains valid no matter what `shop-domain`, `topic`, `webhook-id`, or `api-version` header values accompany it. Replaying that body with substituted headers passes `HmacValidator.validate` unchanged, because those headers were never part of what was hashed.

### Impact Explanation
An app that owns/controls one shop (attacker-controlled tenant) can capture a legitimately-signed webhook for their own shop and resend the identical `raw_body`/HMAC pair to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. Because `Registry.process` only checks the HMAC of the body and unconditionally trusts `request.shop`, the app's `WebhookHandler` will process the payload believing it originated from the victim shop [5](#0-4) . Any app logic that keys writes, cache invalidation, entitlement changes, or state transitions off `WebhookMetadata#shop` is exposed to cross-tenant data corruption/spoofing — one tenant can inject events attributed to another tenant. This matches the Critical "cross-tenant access" impact category: an unprivileged installer of the app for their own shop can make the gem attribute forged events to a shop they do not own.

### Likelihood Explanation
Likelihood is realistic: obtaining a validly-signed webhook body requires nothing more than installing the app on any shop (which any merchant can do, satisfying the "unprivileged internet user" bar) and having the app trigger a webhook of a topic whose body content the attacker wants to replay/spoof. No access to `client_secret`, access tokens, or the victim shop is needed — only capturing one's own legitimately delivered webhook and re-POSTing it with different headers to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload (e.g., verify `shop` against a shop the app has an active session/installation record for before trusting `WebhookMetadata#shop`). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must be cross-checked by the host application against a known-installed shop list before being used for any state-changing decision.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` (no privilege required).
2. Trigger a webhook topic (e.g. `orders/create`) so Shopify sends `raw_body` `B` with a valid `x-shopify-hmac-sha256` computed over `B` using the app's shared `client_secret`.
3. Capture `B` and its accompanying HMAC value `H`.
4. POST to the app's webhook endpoint with headers `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: victim.myshopify.com`, and body `B`.
5. `ShopifyAPI::Webhooks::Request.new` parses these headers [6](#0-5) ; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation succeeds [7](#0-6) .
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [4](#0-3) , causing the app to act on data `B` as if it belonged to `victim.myshopify.com`.
