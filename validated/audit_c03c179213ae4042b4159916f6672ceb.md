### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identifier) is read from a separate, unsigned header. `Registry.process` trusts this unsigned `shop` value and passes it straight to the app's webhook handler. Any user who can obtain one validly-signed webhook from Shopify (by simply installing the app on their own store) can replay that same body/HMAC pair while substituting the `shopify-shop-domain` header, and the library will accept it as an authentic webhook for the substituted shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from a header that plays no part in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`: [3](#0-2) 

`Registry.process` only checks that HMAC, then forwards the (unverified) `request.shop` value straight to the handler as the tenant identity for the webhook: [4](#0-3) 

The binding that should hold is:
`shop value covered/authenticated by the HMAC == shop value used to attribute the webhook to a tenant`

In this implementation that equality never holds — the left side does not exist (the HMAC covers no shop identity at all), and the right side (`request.shop`) is taken from a header a client fully controls. Any party that can get one authentic webhook delivered to them (i.e., any merchant who installs the app) obtains a valid `(body, hmac)` pair signed with the app's shared secret. They can then re-POST that identical body/HMAC to the app's webhook endpoint while changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), so `Registry.process` dispatches the forged request to the app's handler with `WebhookMetadata#shop` set to the victim's shop — a cross-tenant identity confusion the app has no way to detect using this library's primitives.

### Impact Explanation
This breaks the tenant/identity boundary the HMAC is supposed to guarantee. A handler that uses `WebhookMetadata#shop` to decide which tenant's data to create/update/delete (a very common pattern, e.g. `SessionRepository.find_by(shop: data.shop)` then act on it) can be tricked into performing actions attributed to a shop that never sent the webhook. Depending on the handler, this enables cross-tenant data manipulation/exfiltration using only a webhook that was legitimately, validly signed for the attacker's own shop — this matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any internet user can trigger this: they only need to install the target app on a store they control (or trigger any webhook topic they subscribe to), capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair, and replay it against the app's webhook endpoint with a different `shop-domain` header value. No access to `api_secret_key`, access tokens, or any other privileged material is required — only interaction with the app as an ordinary merchant.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind `shop` to the signed body before it is trusted by `Registry.process`/handed to handlers. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be independently corroborated (e.g., cross-checked against the shop referenced in the JSON payload) before being used for any authorization or tenant-scoping decision.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
   - Body: `{"id": 1, "...": "..."}`.
2. Attacker re-sends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) validates successfully because it only checks the body's HMAC.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload/HMAC were never produced for that shop — confirming the cross-tenant spoof.
