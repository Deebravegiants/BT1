### Title
Webhook `shop` (and `topic`) identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then passes the unauthenticated `shop` header straight to the app's handler as the tenant identifier, breaking the intended binding `shop authenticated == shop acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC against `to_signable_string` (i.e. the body only), then immediately trusts `request.shop` as the tenant/shop identity forwarded to the app-supplied handler: [3](#0-2) 

Because the HMAC is computed with the app's single shared `api_secret_key` (`HmacValidator.validate` → `compute_signature`) and does not bind the `shop` header at all, any actor who has legitimately received one correctly-signed webhook (e.g., by installing the same public app on their own store and triggering an event topic they control) possesses a body+HMAC pair that will pass validation regardless of which `shop` header is attached to it: [4](#0-3) 

The library's own documentation instructs implementers to trust `data.shop` from `WebhookMetadata` as the authoritative tenant identity and to key downstream jobs by it (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this gem's documented contract treats the header-derived `shop` as authenticated when it is not.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who controls a shop with the app installed (a low-privilege, publicly obtainable relationship) can replay a validly-HMAC-signed webhook body to the victim app's webhook endpoint while attaching an arbitrary victim `shop` domain header. Since `Registry.process` only validates body HMAC and blindly forwards the header-derived `shop`, the app's handler — following this gem's documented pattern — will process/attribute data as belonging to a different, unrelated merchant. Depending on how the host app models data with the `shop` key, this enables cross-tenant data injection/corruption, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that is publicly installable (the normal Shopify App Store distribution model): any unprivileged internet user can install the app on their own development/trial store, capture one legitimately Shopify-signed webhook for a topic/body they control, and then send arbitrary POST requests directly to the app's public webhook endpoint with the same body/HMAC but a forged `shop` header, since nothing in this gem's verification path binds the shop identity to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the material that is authenticated, or otherwise cryptographically bind them: e.g., verify the caller's `shop` header against a shop that has an active, previously-registered webhook subscription/session known to the app, rather than trusting the header outright. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked by the host application against known installed shops before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`) via the app's own registration flow.
2. Shopify sends a legitimately signed webhook to the app's endpoint: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `B` and `H`, then sends a new POST directly to the app's public webhook URL with the same `B` and `H`, but header `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` succeeds because it only checks `B` against `H`: [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim.myshopify.com`, even though the payload actually originated from the attacker's shop, causing the host app to misattribute the data to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
