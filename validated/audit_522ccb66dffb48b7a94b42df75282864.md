### Title
Webhook HMAC only signs the raw body, not the `shop` (tenant) identity, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity using an HMAC that covers only the raw request body, while the `shop` field used to identify the tenant for handler dispatch is read from an unsigned HTTP header. Because the webhook HMAC secret (`Context.api_secret_key`) is shared by a single app across *all* shops that install it, any shop with the app installed can obtain a genuinely-signed `(body, hmac)` pair and replay it to the app's webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header, causing the app to process the payload as if it belonged to a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` using `Context.api_secret_key`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be exactly the raw HTTP body — nothing else: [2](#0-1) 

Meanwhile, the `shop` accessor — used by `ShopifyAPI::Webhooks::Registry.process` to identify which tenant a webhook belongs to and passed to app handlers — is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is not part of the signed content at all: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then dispatches to the handler using `topic`/`shop` taken from these unsigned headers, as confirmed by the test harness building a `HandlerData` object with `data.shop` from the request: [4](#0-3) 

The identity binding that should hold is: `shop header == shop bound by HMAC`. In reality the equality is `shop header ∈ {anything}` while `HMAC covers body only`, i.e. `verified_bytes (body) ≠ trusted_identity_bytes (shop header)`. Since the same `api_secret_key` is used to compute the webhook HMAC for every shop that has a given app installed (it is the app's client secret, not a per-shop secret), a merchant/attacker who installs the app on their own store (Shop A) can:
1. Trigger any webhook event on Shop A, capturing the genuine `raw_body` and its correctly computed `X-Shopify-Hmac-Sha256` value from Shopify.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook receiving endpoint, but with the `X-Shopify-Shop-Domain` header rewritten to Shop B (the victim shop, on which the app is also installed).
3. `HmacValidator.validate` succeeds, because it only checks the untouched body/hmac pair, and `Registry.process` invokes the handler believing the event originates from Shop B.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide: the `shop` value handed to application handlers is not cryptographically bound to the same request whose authenticity was verified. An app that uses the `shop` field returned from `ShopifyAPI::Webhooks::Request`/`Registry.process` to look up per-tenant sessions, update per-tenant data, or make authenticated API calls on behalf of "the shop that sent this webhook" can be tricked into acting on behalf of, or writing data into, a different tenant's context — i.e., cross-tenant access using data forged by an unprivileged (but app-installing) attacker.

### Likelihood Explanation
Any user who can install the target app on their own store satisfies all preconditions: they can generate a validly-HMAC-signed webhook body without ever seeing `api_secret_key`, and they fully control HTTP headers of the forged request sent to the app's public webhook endpoint. No admin access, leaked secrets, or privileged account is required, only that the app registers webhooks and the attacker can install it on at least one shop while targeting another shop that also has it installed.

### Recommendation
Bind the shop identity into the verified content, e.g., include the `shop-domain` header value (and ideally `topic`/`webhook-id`) into the HMAC-signable string, or otherwise cryptographically bind the header claims to the signed body (per-shop shared secret, or a MAC over `header + body`) before trusting `Webhooks::Request#shop` for tenant dispatch.

### Proof of Concept
1. Configure the app with webhooks registered, `Context.api_secret_key = SECRET`.
2. Install the app on `attacker-shop.myshopify.com`; trigger any webhook event; capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify (H is HMAC-SHA256(SECRET, B) — valid because computed by Shopify itself).
3. Send a new HTTP request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. In the gem: `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `HmacValidator.validate` calls `to_signable_string` → returns `B` only (`lib/shopify_api/webhooks/request.rb:35-38`), computes HMAC(SECRET, B) which equals `H`, so validation passes.
5. `Registry.process` proceeds to call the topic handler with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:20-23`), even though the webhook actually originated from `attacker-shop.myshopify.com`. The app now processes/attributes the webhook event to the victim tenant.
