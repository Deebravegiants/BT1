### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once `Utils::HmacValidator.validate` succeeds, and then forwards `request.shop` (the `x-shopify-shop-domain`/`shopify-shop-domain` header) to the host application's handler as the trusted shop identity. However, the HMAC only ever covers the raw body — the shop-domain header is never part of the signed material — so the "verified" identity (comes from Shopify) and the identity actually handed to the app (the `shop` header) are two different bindings that are never checked against each other.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate`/`validate_signature` compute/compare the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile `shop` is read straight from an HTTP header with no cryptographic binding to the body or its HMAC: [3](#0-2) 

`Registry.process` gates entirely on the HMAC of the body, then passes `request.shop` on to the app's handler as if it were equally authenticated: [4](#0-3) 

The gem's own documentation reinforces the misleading equivalence, stating that `Registry.process` "will verify the request did indeed come from Shopify" and describing `data.shop` simply as "The shop domain of the webhook" with no caveat that this value is unauthenticated: [5](#0-4) [6](#0-5) 

This is the same class of defect as the M-3 report: a validation primitive (`HmacValidator.validate`, designed to confirm the *body bytes* originated from Shopify) is repurposed/relied upon by `Registry.process` and its documentation to also vouch for a completely different, unrelated value (the `shop` header) that the check never inspects. Concretely: `shop_authenticated_by_hmac == request.shop_header` is assumed by the library and its docs, but the HMAC computation never includes `shop_header`, so this equality does not hold.

### Impact Explanation
Any party capable of obtaining one validly-HMAC-signed webhook body for a given app (e.g., by installing the app — even a free/public app — on their own store and receiving a real webhook, since Shopify signs every webhook for that app with the same shared `client_secret` regardless of which shop it is for) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the handler with `shop: <victim-domain>` and the attacker-controlled body. Any host application that follows the documented contract (trusting `data.shop` to select which merchant's data/session to act on, as shown in the gem's own example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied data under a different tenant's identity — a cross-tenant confusion/spoofing primitive.

### Likelihood Explanation
Exploitation requires no secrets beyond installing the target app on any shop the attacker controls (or otherwise obtaining one legitimately-signed webhook delivery) and does not require the `api_secret_key` or an access token to be leaked — the HMAC used is validly produced by Shopify itself for the attacker's own installation. Constructing and sending the forged HTTP request to the app's public webhook endpoint is trivial once a legitimate body+HMAC pair is captured.

### Recommendation
Do not treat `request.shop`/`data.shop` as authenticated merely because the body HMAC validated. Either:
- Bind the shop domain into the signed material used for verification (e.g., require host apps to cross-check the header against a shop looked up independently, such as via `shop_id`/`admin_graphql_api_id` inside the verified body, or a shop already known from OAuth), or
- Clearly document that `shop` is unauthenticated header data and must be independently verified/looked up by the host application (e.g., confirm a session/install exists for that shop) before being trusted for authorization decisions, and update the docs/example in `docs/usage/webhooks.md` to stop implying `Registry.process` fully "verifies the request" including the shop identity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a public/free app requires no special privilege).
2. Attacker triggers a webhook (e.g., `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared secret) plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker crafts a new HTTP request to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes HMAC over `B`.
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host application to process attacker-controlled data as if it belongs to `victim-shop`.
