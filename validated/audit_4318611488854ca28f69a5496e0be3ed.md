### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once the HMAC over the raw body passes, but the `shop` field it forwards to the app's handler as the tenant identity comes from an HTTP header that is completely outside the HMAC's coverage.

### Finding Description
The gem's webhook authenticity model is: `Utils::HmacValidator.validate(request)` computes `HMAC-SHA256(api_secret_key, request.to_signable_string)` and compares it to the `x-shopify-hmac-sha256` header [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are all pulled from separate headers via `shopify_header` [6](#0-5)  and are never fed into the signed string.

`Registry.process` performs exactly one authenticity check — the HMAC — and then immediately trusts `request.shop` as the tenant that the payload belongs to, passing it into `WebhookMetadata` for the handler [1](#0-0) . This breaks the identity binding that the equality `hmac_signer_shop == request.shop` is expected to hold: the gem verifies "bytes signed by our `api_secret_key`" but acts on "shop header supplied by whoever sent the HTTP request," and these are two different things.

Concretely: since the app's own `api_secret_key` signs only the raw body, any party who can obtain one validly-signed webhook body/HMAC pair for *any* topic and *any* shop (e.g., their own shop, on which they installed the same app, or a body they can predict/observe) can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary value in `x-shopify-shop-domain`. `Utils::HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain rather than the shop that actually produced the payload.

### Impact Explanation
Downstream handlers are documented/expected to key their per-tenant logic (which merchant's data to update, which session to look up, which store record to write to) off `WebhookMetadata#shop`, since that is the only shop-identifying field the library exposes for a webhook. Because that field is unauthenticated relative to the signature the library itself validates, an attacker can make the app believe a webhook body originated from a different shop than the one that actually holds the signing secret's session — i.e., cross-tenant data confusion in the layer the app relies on this gem to authenticate. This matches the Critical "cross-tenant access" category: the gem's own `process` entry point, not a documented-but-ignored caller convention, is what asserts (falsely) that `hmac_valid? ⇒ shop_is_authentic`.

### Likelihood Explanation
Exploitation only requires the ability to deliver an HTTP request to the app's public webhook endpoint (a capability any internet host has, since webhook endpoints are necessarily internet-facing) plus one legitimately-signed `(raw_body, hmac)` pair, which an attacker who runs their own store using the same app can freely generate by triggering a real webhook topic on their own shop. No possession of `api_secret_key`, tokens, or any other credential is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the payload before exposing it via `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header so `HmacValidator.validate` fails whenever the shop header has been altered relative to the body that was actually signed by Shopify for that shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [7](#0-6) ; since only `B` is hashed, validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [4](#0-3) , causing the app to process attacker-controlled data under the victim shop's identity.
