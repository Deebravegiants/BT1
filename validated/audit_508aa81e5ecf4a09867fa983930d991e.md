### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (tenant identity) is read from an unauthenticated header. This breaks the binding: `hmac == HMAC(secret, body)` should imply `shop == owner_of(body)`, but `shop` is never part of the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC [2](#0-1) . `Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field [3](#0-2) . `Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, then forwards `request.shop` unchecked into `WebhookMetadata` for the app's handler [4](#0-3) . Any party that possesses one genuinely-signed webhook body/HMAC pair for the app (trivially obtainable by installing the app on their own shop and receiving a real webhook, e.g. `app/uninstalled` or `shop/redact`) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. The signature still validates because the header is outside the signed content, so the app processes the event as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who controls their own legitimate app installation can make the host application believe an event (e.g., uninstall, GDPR redact/erasure, order/customer data change) came from a different merchant's shop. Depending on how the host app's `WebhookHandler` uses `data.shop` (session/token lookup, deleting or exporting merchant data, disabling a shop), this can lead to cross-tenant data manipulation or destruction of another merchant's stored session/access token — meeting the Critical "cross-tenant access" bar, since the boundary crossed is the shop/tenant identity that the app trusts as the source of the webhook.

### Likelihood Explanation
Requires no privileged credentials, no `api_secret_key`, and no interception — the attacker only needs their own real app installation (which any merchant/developer can obtain) to harvest a validly-signed body+HMAC pair, then send a crafted HTTP POST with a spoofed `X-Shopify-Shop-Domain` header directly to the app's public webhook endpoint.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the signed content, or independently verify the shop-domain header against a value derived from data actually covered by the HMAC (e.g., include headers in the signable string per Shopify's documented webhook verification, or cross-check the `shop` header against the shop referenced inside the verified JSON body where available). At minimum, document that host apps must not trust `WebhookMetadata#shop` without additional verification, and consider deriving tenant identity only from body fields that are within `to_signable_string`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g. `app/uninstalled`), capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid for that body under the app's secret.
2. POST that same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic` as desired.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [5](#0-4)  and succeeds since the body/HMAC pair is genuinely valid.
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim.myshopify.com"` [6](#0-5) , and the host app processes the (attacker-controlled) event as if it came from the victim shop.
