### Title
Webhook `shop` field is not covered by the HMAC, allowing cross-tenant shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `WebhookMetadata` built from `request.shop`, which is read straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header. The HMAC, however, is computed only over the raw request body — the shop-domain header is never included in the signed bytes. This breaks the identity binding `shop_domain_header == origin_shop_of(signed_body)` that host apps rely on to attribute webhook data to the correct tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read independently from a header, with no cryptographic tie to the body or its HMAC: [2](#0-1) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — again, only the body is part of the signed material: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and passes it straight to the app's handler: [4](#0-3) 

The documented contract explicitly tells host apps that `data.shop` is "The shop domain of the webhook" and to use it to route/enqueue tenant-specific work: [5](#0-4) 

Because only the body is signed, an unprivileged user who owns any shop where the app is installed can receive a legitimately-signed webhook (valid body + valid HMAC, computed with the app's real `client_secret`/`api_secret_key` by Shopify itself for their own store), and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The HMAC check still passes because it never inspects the header, so `Registry.process` will invoke the handler with `shop: <victim-domain>` even though the signed payload never actually originated from, or was intended for, that shop.

### Impact Explanation
This is a cross-tenant identity confusion: the "shop" identity that library-conforming host apps use as the tenant key (to store data, revoke sessions, invalidate access tokens, update webhook-driven state, etc., per the documented `data.shop` field) is fully attacker-controlled and not bound by the cryptographic check the gem performs. A malicious merchant/app-installer can:
- Forge `app/uninstalled` processing effects against an arbitrary target shop's identifier tied to the merchant's own signed payload, or
- Inject/attribute fabricated order/product/customer data (from their own legitimately-signed webhook body) onto another shop's tenant space in the host application's storage.

This matches the "cross-tenant access" critical-impact category: the gem's webhook processing pipeline is the enforcement point that fails to bind the tenant identifier to the authenticated bytes.

### Likelihood Explanation
Likelihood is realistic for any unprivileged party who can install the target app on a shop they control (the normal, free way to become "a legitimate" webhook source) and can send arbitrary HTTP requests to the app's public webhook endpoint (a normal capability of any internet user, no special credentials, TLS interception, or leaked secrets required). No knowledge of `api_secret_key` is needed — the attacker uses the real HMAC Shopify computed for their own shop's webhook, and simply changes an unsigned header on replay.

### Recommendation
Include the shop domain (and ideally the webhook topic/ API version) in the material covered by the HMAC/signature check, or otherwise cryptographically bind `request.shop` to the verified body (e.g., by validating that the shop header matches a shop for which a webhook subscription/session was actually registered before dispatching to the handler). At minimum, document loudly that `data.shop` is unauthenticated and that host apps must independently verify shop identity (e.g., against known-installed shops) before using it as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) so Shopify sends a request with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and the HMAC value from the received request (attacker fully controls their own inbound traffic/log).
3. Send a new HTTP POST directly to the app's webhook endpoint with the identical body `B`, identical `x-shopify-hmac-sha256` value, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (only `B` is checked), `Registry.process` dispatches to the app handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process attacker-supplied data under the victim shop's tenant identity.
