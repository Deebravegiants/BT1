### Title
Unbounded recursive SCALE decode of attacker-controlled cross-chain calldata in `hyper-fungible-token::onAccept` (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The HackerOne report is a case of unbounded/unsafe deserialization of untrusted input (`unserialize()` on a user-controlled cookie) leading to remote code execution via a gadget chain. The reachable analog in Hyperbridge is not PHP object injection, but the equivalent bug class in a Rust/Substrate context: deserializing attacker-supplied bytes from an incoming cross-chain message using `Decode` **without** the depth-limited variant that the codebase otherwise uses elsewhere for exactly this reason.

### Finding Description
`pallet-hyper-fungible-token`'s `onAccept`/message-processing path decodes the optional `data` field of an incoming token-transfer `message` twice: [1](#0-0) 

using `SubstrateCalldata::decode(&mut &message.data[..])` and then [2](#0-1) 

`T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)`.

Both calls use the plain `Decode::decode` trait method rather than `decode_all_with_depth_limit`, the depth-bounded decoder that the codebase deliberately introduced elsewhere (`modules/pallets/call-decompressor/src/lib.rs`, `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT`) specifically to stop a fee-less/unprivileged submitter from crafting a deeply-nested SCALE payload that blows the decode stack. The comment in `call-decompressor/src/lib.rs` explicitly documents this class of attack: [3](#0-2) 

`RuntimeCall` in a Substrate runtime is a deeply-nested enum (nested pallet calls, `Utility::batch`, nested calls, etc.), so an attacker who controls the raw bytes decoded as `RuntimeCall` can build a payload whose recursive variant nesting overflows the decode stack, causing an unrecoverable panic/crash of the block-execution thread — a denial-of-service on `handle_unsigned`/ISMP delivery, not merely "no impact." This is the direct structural analog of the report's core weakness class ("Deserialization of Untrusted Data" without validating the decoded structure before acting on it).

### Impact Explanation
`message.data` originates from the source chain's HFT contract `Message.data` field embedded in an ISMP POST request body, which is delivered to `onAccept` once the request passes proof verification. Because the destination pallet only validates the `source`/`from` address of the message (the configured peer HFT contract) and not the *shape* of the attacker-influenced `data` payload before calling `Decode::decode` (no depth limit), a message whose `data` encodes a maliciously deep/recursive `RuntimeCall` structure can crash the collator/validator processing block execution (denial of service to the whole parachain's ISMP message delivery pipeline), and — depending on how the peer HFT source contract permits users to set the `data`/calldata field for a bridged transfer (typically end users control the executed calldata for the "execute calldata on receipt" feature) — this is reachable by an ordinary unprivileged bridge user or relayer relaying a legitimate but adversarially crafted message.

### Likelihood Explanation
Medium-High: reaching this code path requires only a standard cross-chain token transfer with a non-empty `data`/calldata field, which is a normal, permissionless HFT feature (see docs `hyper-fungible-token.mdx`), and a relayer delivering the corresponding ISMP proof — both routine, unprivileged actions. The codebase's own existing defensive comment about identical attacks against `RuntimeCall::decode_all_with_depth_limit` in `call-decompressor` demonstrates the authors are aware unconstrained recursive `RuntimeCall` decoding is exploitable; the same protection was not applied consistently to the HFT calldata-execution path.

### Recommendation
Replace both `Decode::decode` calls in `modules/pallets/hyper-fungible-token/src/module.rs` (`SubstrateCalldata::decode` and `T::RuntimeCall::decode`) with the depth-limited `decode_all_with_depth_limit` (or an equivalent bounded decode) as already used in `call-decompressor/src/lib.rs`, and additionally bound `message.data`'s raw byte length before attempting to decode it, mirroring the size/claimed-length checks already enforced in `call-decompressor::decompress`.

### Proof of Concept
Not independently executable from static analysis alone; the concrete PoC would require constructing an ISMP `PostRequest` whose body decodes to an HFT `Message` with a `data` field containing a SCALE-encoded `SubstrateCalldata { runtime_call: <deeply nested RuntimeCall bytes>, signature: None }`, then delivering it through the normal relayer path to `onAccept`/message execution at [1](#0-0)  and [4](#0-3) , observing a stack-overflow panic instead of a graceful `Err(HftError::RuntimeCallDecodeError)`. I was unable to fully verify (index truncation) whether an outer size cap on `message.data` exists elsewhere in the pallet's `Config`/dispatch path that would mitigate this before decode is reached; a Devin session with full repository access should confirm this and, if no cap exists, apply the fix above.
