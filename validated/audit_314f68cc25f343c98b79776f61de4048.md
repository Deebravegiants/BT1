### Title
`register_token` in `pallet-hyper-fungible-token` allows overwriting an already-registered asset's cross-chain contract mapping without ownership checks - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet_hyper_fungible_token::register_token` inserts into `TokenContracts`, `ContractToAsset`, `NativeAssets`, and `Precisions` for any `local_id` supplied by the caller, with no check that the asset was already registered by someone else. Any account holding `T::CreateOrigin` can call `register_token` a second time on an asset_id that is already mapped, silently repointing the destination EVM contract address and the native/custody flag that governs mint vs. burn / lock vs. unlock semantics for that asset. This mirrors the referenced Jenkins CVE-2017-2599 bug class: a caller permitted to "create" an item can instead overwrite an existing item it does not own/control.

### Finding Description
`register_token` is a pallet call gated only by `T::CreateOrigin::ensure_origin(origin)?`: [1](#0-0) 

There is no `ensure!(!TokenContracts::<T>::contains_key(...))` or any check that `registration.local_id` has not already been registered (by this or another `CreateOrigin` account) before it unconditionally overwrites:
- `NativeAssets::<T>::insert(registration.local_id, registration.native)` — this flips the custody model (lock/unlock vs. burn/mint) for an asset that may already have live escrowed balances or in-flight cross-chain transfers under the previous model.
- `TokenContracts::<T>::insert(chain, local_id, token_contract)` — this is the destination address used as the `to` field for every future `send()` dispatched for this asset (see `send()` at lines 251-253/304-309 of the same file).
- `ContractToAsset::<T>::insert(chain, token_contract, local_id)` — the reverse lookup used by `on_accept` to resolve an incoming EVM message to a local asset.

`update_token` has the same shape and is also gated only by `T::CreateOrigin`: [2](#0-1) 

The pallet's own documentation and example runtime wiring configure `CreateOrigin` as `frame_system::EnsureSigned<AccountId>` — i.e., any signed account, not a privileged/governance origin: [3](#0-2) 

Under that (documented, expected) configuration, any signed account that is permitted to register a *new* token can instead call `register_token`/`update_token` again against an `asset_id` it does not own, overwriting the existing `TokenContracts`/`ContractToAsset` entry with an attacker-controlled EVM contract address, or flipping the `native` flag for an asset with existing escrowed/circulating balance.

I was not able to fully confirm, within the available indexing, what `CreateOrigin` is concretely bound to in the production `gargantua`/`nexus` runtimes (`parachain/runtimes/gargantua/src/ismp.rs` and `parachain/runtimes/nexus/src/ismp.rs` reference the pallet, but the exact `CreateOrigin` type binding for it was not retrieved before the tool budget ran out). If the production runtimes bind `CreateOrigin` to a narrow governance/root origin, the practical blast radius is limited to that origin misusing the call rather than an arbitrary user — this should be verified directly in those two files before treating this as exploitable by an arbitrary unprivileged account in production.

### Impact Explanation
If `CreateOrigin` is (or ever is configured as) a broad signed origin, as the pallet's own reference documentation shows, this is a direct fund-theft / fund-freezing primitive:
- Repointing `TokenContracts[chain][asset_id]` to an attacker-controlled contract address causes every subsequent `send()` for that asset to dispatch funds/messages to the attacker's contract instead of the legitimate token contract, effectively hijacking the bridge leg for that asset.
- Flipping `NativeAssets[asset_id]` after the asset already has funds under the opposite custody model (lock vs. burn) breaks the accounting invariant that `send()`/`on_accept()` rely on, which can permit unbacked mint or permanently stuck (frozen) escrowed funds.
- Corrupting `ContractToAsset` misroutes incoming cross-chain messages to the wrong local asset.

Even scoped to a governance-controlled `CreateOrigin`, the missing "already registered" check is a real correctness/authorization gap matching the CVE's bug class (create-permission is being used to silently clobber someone else's existing item), and should be fixed with an explicit ownership/idempotency check regardless of the final origin binding.

### Likelihood Explanation
Likelihood depends entirely on the concrete `CreateOrigin` binding in the deployed runtime, which I could not fully verify. Given the pallet's own documentation configures it as `EnsureSigned<AccountId>` (any signed account), and multiple tokens/asset registrations are expected to accumulate over the pallet's operation, the likelihood of a non-owning `CreateOrigin` holder re-registering an existing `asset_id` — accidentally or maliciously — is non-trivial once more than one party can call `register_token`.

### Recommendation
Add an explicit check in `register_token` that rejects (or requires an explicit, differently-authorized "reassign" path for) an `asset_id`/`(chain, asset_id)` pair that is already present in `TokenContracts`/`NativeAssets`, mirroring the ownership check pattern already used elsewhere in the codebase (e.g., `Error::NotBidOwner` in `pallet-intents-coprocessor`). At minimum, `register_token` should require `!NativeAssets::<T>::contains_key(&local_id)` before allowing the native-flag and contract mappings to be set, and any legitimate re-registration should go through `update_token` (which already understands "updating an existing token") rather than through `register_token` silently overwriting state.

### Proof of Concept
1. Deploy `pallet-hyper-fungible-token` with `CreateOrigin = EnsureSigned<AccountId>` (the pallet's documented reference configuration).
2. Account A calls `register_token` for `asset_id = X`, `chains = { Evm(1): ChainConfig { token_contract: LEGIT_CONTRACT, decimals: 18 } }`, `native = true`. Users begin escrowing funds via `send()` against asset `X`.
3. Account B (unrelated, but also permitted by `CreateOrigin`) calls `register_token` again for the same `asset_id = X` with `chains = { Evm(1): ChainConfig { token_contract: ATTACKER_CONTRACT, decimals: 18 } }`.
4. `TokenContracts::<T>::insert` and `ContractToAsset::<T>::insert` are silently overwritten (no existence/ownership check in the code shown at `modules/pallets/hyper-fungible-token/src/lib.rs:344-367`), so all subsequent `send()` calls for asset `X` to `Evm(1)` now target `ATTACKER_CONTRACT` instead of `LEGIT_CONTRACT`. 		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}
