### Title
Webhook `shop-domain` identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the body bytes against `Context.api_secret_key` [2](#0-1) . The `shop` (and `topic`/`webhook_id`) values are read straight from HTTP headers via `shopify_header`, entirely outside the HMAC computation [3](#0-2) . `Registry.process` validates the HMAC and then unconditionally forwards `request.shop` as the authoritative tenant identity to the app's handler [4](#0-3) .

### Finding Description
The equality the system is supposed to enforce is: `bytes covered by the HMAC == identity fields the app acts on`. Here that equality is broken:

- HMAC-covered bytes: `@raw_body` only.
- Identity field acted on: `shop` header, delivered via `WebhookMetadata.new(... shop: request.shop ...)` to the handler, unauthenticated.

This mirrors the analog report's `burn`/`availableBalance` inconsistency: one code path (`HmacValidator.validate`) verifies against a narrow, incomplete data set (body only), while another path (`Registry.process` → handler dispatch) acts on a broader claim (`shop`) that was never covered by that verification. An unprivileged internet user who has ever received one legitimate webhook delivery for their own installed shop (a valid `raw_body` + HMAC pair, delivered to them because they legitimately installed the app on their own store) can capture that exact `raw_body`/`hmac-sha256` pair and replay it to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim merchant's `*.myshopify.com` domain). Because the HMAC only signs `raw_body`, which is unchanged, `HmacValidator.validate` returns `true`, and `Registry.process` dispatches the handler with `shop: <victim-shop>` and the attacker's own webhook body content.

### Impact Explanation
Any application built on this gem that keys tenant-scoped writes (e.g., "update order/product/customer record for `data.shop`") directly off `WebhookMetadata#shop` without an independent, out-of-band check that the shop is the one the payload actually belongs to, will process attacker-supplied data under another tenant's identity — a cross-tenant data-integrity/access violation, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is bounded by the precondition that the attacker must possess at least one legitimate `raw_body` + HMAC pair (trivially obtainable by installing the app on their own free/dev store and capturing one webhook delivery), after which the header substitution and replay require no secret material and can be repeated for any topic/shop combination whose body content the attacker controls (e.g., self-triggered `orders/create` on their own shop, replayed with a spoofed `shop-domain`).

### Recommendation
- Short term: `Request#to_signable_string` / the signable content should not be the only authenticated unit; `Registry.process` (or the gem's public API) should require callers to cross-check `request.shop` against a list of shops with an active, known installation/session before dispatching, and the gem should surface this requirement prominently, since it is currently silent about the header's authentication status.
- Long term: Adopt a consistent identity-binding strategy — either extend the HMAC-covered signable string to include the identity headers actually acted upon (`shop-domain`, `topic`, `webhook-id`), or add an explicit `verified_shop` accessor that only returns a value once corroborated against stored session/shop state, so the same trust boundary is enforced everywhere the value is consumed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify (valid, since Shopify computed `H` from `B` with the real `api_secret_key`).
2. Attacker sends a new HTTP POST to the app's webhook endpoint with body `B` unchanged, headers `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's order data>, ...)` [7](#0-6)  and, if the host app trusts this `shop` field for tenant scoping, writes/overwrites data under the victim tenant's context.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
