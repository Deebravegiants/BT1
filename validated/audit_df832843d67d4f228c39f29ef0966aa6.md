### Title
Webhook HMAC only signs the request body, not the `shop`, `topic`, `webhook-id`, or `api-version` headers, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` validates only the body HMAC and then dispatches to the app's handler using those unverified header values, so a party that legitimately receives one genuine, signed webhook (e.g. for their own installed store) can replay the same body/HMAC pair while forging the shop-domain/topic headers to make the host application process it as if it came from a different merchant or topic.

### Finding Description
`Request#to_signable_string` is defined as just the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are derived purely from HTTP headers, which are not part of the signed data at all: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` (i.e., the body HMAC) and then immediately trusts the header-derived `topic`/`shop`/`webhook_id`/`api_version` fields to route and label the payload for the handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC solely from `verifiable_query.to_signable_string`, i.e. the raw body, using the app's single, shared `api_secret_key`: [4](#0-3) 

The equality this breaks is: **shop authenticated by HMAC (none — body only) vs. shop attributed to the webhook and delivered to the handler (`request.shop` from the unauthenticated `x-shopify-shop-domain` header)**. Since the same `api_secret_key` is shared across all shops that installed a given app, any shop that legitimately receives one valid webhook (body + HMAC) can capture that exact body/HMAC pair and resend it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) header. The HMAC still validates because it never covered those fields, and `Registry.process` will invoke the host application's handler with attacker-chosen `shop`/`topic` metadata alongside a genuinely-signed body, exactly analogous to the reported issue where a signature valid for one context (one chain) is replayed unmodified in a different context (a different chain) because the binding field was never part of the signed payload.

### Impact Explanation
This is a cross-tenant data/action forgery vector: an attacker who controls one shop that has the app installed can produce forgeries that are indistinguishable (per this gem's verification logic) from genuine webhooks for **any other shop** using the same app, since only the body — not the shop identity, topic, or webhook id — is authenticated. Any host application that uses `WebhookMetadata`'s `shop`/`topic` fields (which come straight from `request.shop`/`request.topic`) to scope tenant data, trigger merchant-specific side effects, or route mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) would act on the wrong tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem: the attacker only needs to be a legitimate, unprivileged merchant of the app (no special credentials, no access token, no `api_secret_key` needed) to capture one authentic webhook body+HMAC pair and then replay it with modified headers against the same public webhook endpoint.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string (or otherwise cryptographically bind them to the body) in `lib/shopify_api/webhooks/request.rb#to_signable_string`, so that `Utils::HmacValidator.validate` fails if any of those fields are altered independently of the signed body.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, body `B`, and `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Merchant A (or anyone able to observe this traffic, e.g. via their own server logs) captures body `B` and the HMAC value.
3. Merchant A resends the identical body `B` and HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop) and/or a different `x-shopify-topic`/`x-shopify-webhook-id`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still succeeds because it only checks `B` against the shared secret; `Registry.process` in `lib/shopify_api/webhooks/registry.rb` then calls `handler.handle` with `shop: "shop-b.myshopify.com"`, causing the host app to process attacker-controlled body content under victim shop B's identity.
