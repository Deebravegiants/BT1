### Title
Webhook shop/topic/webhook-id identity is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity (`x-shopify-shop-domain`), topic, webhook id, and API version are read from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body-only HMAC validates, then trusts the unauthenticated `shop` header to identify which tenant the webhook belongs to. This breaks the identity binding `HMAC(body) == HMAC(body)` from `(body, shop)` — the signature authenticates the body bytes but not the shop that the app dispatches the event to.

### Finding Description
The webhook signature check is implemented as: [1](#0-0) 

which only signs `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC and then hands the unauthenticated `shop` header straight to the app's handler as trusted tenant identity: [3](#0-2) 

Because Shopify signs the body with the shared `api_secret_key`, and the same app-level `client_secret`/`api_secret_key` is shared across *all* shops installed on that app, any merchant that has installed the app can trigger a legitimately HMAC-signed webhook for their own store (e.g. by creating an order), capture the signed body+HMAC before it's delivered to the app, and resubmit that exact `(raw_body, hmac)` pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different (victim) shop that also has the app installed. `HmacValidator.validate` only recomputes and compares the digest of the body, which is byte-for-byte identical to what the attacker captured, so validation succeeds: [4](#0-3) 

The handler then receives `data.shop` equal to the victim's domain, along with attacker-chosen body content, topic, and webhook id — the app has no way, using only the primitives this gem exposes, to distinguish this from a genuine webhook belonging to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged (but app-installed) user for shop A can make the host application process forged webhook data (body, topic, webhook_id) as if it originated from shop B. Any app logic keyed off `data.shop` (record lookup, authorization scoping, state updates) can be poisoned across tenants using only a validly-signed payload from the attacker's own store. This matches the "Critical – cross-tenant access" impact criterion, since the boundary broken is exactly a tenant/shop identity check that the app relies on this gem to enforce via HMAC.

### Likelihood Explanation
Any merchant who installs the target app is, by definition, capable of generating validly-signed webhook bodies (by performing actions in their own store that trigger webhooks) and can freely replay them with a different `shop` header value, since nothing in this gem ties the header to the signature. No secret material, privileged access, or app misconfiguration is required beyond normal app installation.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the signable string used for `Utils::HmacValidator`, or otherwise cryptographically bind these header values to the signature, so that swapping the shop-domain header invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and on any second shop context they have access to for testing (or simply captures their own legitimately delivered webhook).
2. Attacker triggers `orders/create` on their own store; Shopify sends a webhook with body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and identical `hmac` header to the same app endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute a digest solely over `B`; `HmacValidator.validate` succeeds because `B` is unchanged.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on victim-shop data using attacker-controlled content.
