### Title
Rebasing/deflationary escrow tokens permanently freeze intent orders in `IntentsBase._withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`/`IntentsBase` tracks escrowed input amounts for an order in the `_orders[commitment][token]` mapping, a "stored balance" that is set once at `placeOrder` time and only ever decremented at redemption/refund time via `_withdraw`. This is the same accounting pattern flagged in the external report for Curve's `stored_balances`: a manually tracked balance that is assumed to always match the actual ERC20 balance held by the contract. If the escrowed token is rebasing (e.g. stETH-style) or otherwise has its balance reduced out-of-band while sitting in escrow, the stored accounting no longer matches the real balance, and the unconditional `safeTransfer` in `_withdraw` reverts, permanently freezing the entire order's escrow (and any co-escrowed inputs/fees for that commitment) since the contract is non-upgradeable-by-users and there is no recovery path for this state.

### Finding Description
`IntentGatewayV2.placeOrder` credits escrow using the *actual received amount* only at deposit time (it diffs `balanceOf` before/after the transfer to handle fee-on-transfer tokens), then stores that fixed amount in `_orders[commitment][token]`: [1](#0-0) [2](#0-1) 

This stored value is treated as ground truth for the lifetime of the order. When the order is later redeemed or refunded, `IntentsBase._withdraw` reads the stored escrow amount, decrements it, and unconditionally attempts to transfer that exact amount out to the beneficiary: [3](#0-2) 

There is no diff-based accounting on the way out (unlike the deposit path), and no fallback that clamps the transfer to the contract's *actual* current balance of that token. If the escrowed token's balance held by the gateway decreases between `placeOrder` and the `RedeemEscrow`/`RefundEscrow` delivery — e.g. a negative rebase, a token with fee-on-transfer *and* fee-on-transfer-out semantics, or any ERC20 whose balance can shrink independent of explicit `transfer` calls out of the contract — then `IERC20(token).safeTransfer(beneficiary, amount)` will revert because the contract's real balance is now less than the `amount` the escrow accounting believes it holds.

Because `_withdraw` is invoked from `onAccept` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` (dispatched via a Hyperbridge cross-chain message that any relayer can deliver once proven), and the amounts it tries to move are fixed at order-placement time, once the on-chain balance drops below the stored escrow amount there is no way to complete withdrawal: every relayer delivery attempt for that commitment reverts. Since `_orders[commitment][token]` is only ever decremented inside the same reverting call, the escrow can never be reduced to match the smaller real balance, and the tokens are permanently stuck — the same "stuck stored balance, real balance diverges, transfer/assert reverts forever" failure mode as the Curve `stored_balances` report, just realized in `IntentGatewayV2`'s escrow bookkeeping instead of a stableswap pool's balance cache.

### Impact Explanation
Any escrowed input amount for an order using a rebasing-down (or externally balance-decreasing) ERC20 becomes permanently unrecoverable: neither the depositing user (on refund/cancel) nor the filling solver (on redeem) can ever withdraw it, because the withdrawal path always reverts on the balance mismatch. Since `_withdraw` loops over all tokens for the commitment in one call and any single token transfer reverting reverts the whole transaction, this also blocks release of any other, non-rebasing token escrowed in the same order and blocks release of accumulated `TRANSACTION_FEES` for that commitment. This is a permanent freezing-of-funds bug with no admin/upgrade recovery path assumed by the design (the contract does support UUPS upgrades via governance `Execute`, but a governance upgrade would be required for every stuck order — this is not a self-service recovery for users).

### Likelihood Explanation
Requires an order that escrows a rebasing/balance-decreasing ERC20 as an input token. `IntentGatewayV2` does not restrict which ERC20 tokens can be used as `TokenInfo.token` in `Order.inputs`, and the contract already explicitly acknowledges deflationary/fee-on-transfer intricacies on the deposit side (dedicated `FeeOnTransferToken` test suite), showing the token surface is intentionally broad and permissionless. A negative rebase or any token whose balance can decrease while custodied (which the deposit-time diff logic does not protect against, since it only diffs once at deposit) is a realistic, single-order-placement trigger, making this reachable by any ordinary user placing an intent order with such a token.

### Recommendation
On the withdrawal path (`_withdraw`), do not rely purely on the stored `_orders[commitment][token]` amount to determine what to transfer out. Either (a) clamp the transferred amount to `min(storedAmount, IERC20(token).balanceOf(address(this)))` and account for any shortfall separately (e.g. socialize the loss or emit a distinct event rather than reverting), or (b) explicitly disallow/flag rebasing and balance-mutable tokens from being used as intent input/output assets, similar to how many escrow/vault systems maintain a `totalDeposited` counter reconciled against `balanceOf` with a documented non-rebasing-token restriction. At minimum, ensure a partial-failure path exists so a balance shortfall for one token in a multi-token order commitment does not block release of the other tokens/fees for that same order.

### Proof of Concept
1. User places an order via `IntentGatewayV2.placeOrder` with `order.inputs[0].token` = a rebasing ERC20 `R` and `amount = 1000e18`. `placeOrder` transfers `1000e18` `R` into the gateway and sets `_orders[commitment][R] = 1000e18` (see `IntentGatewayV2.sol:363-373`).
2. Before the order is filled/redeemed, `R` undergoes a negative rebase (e.g., a validator slashing event for a liquid-staking token), reducing the gateway's actual `R.balanceOf(address(this))` to `900e18` (all else being equal, since escrow accounting never adjusts).
3. Solver fills the order on the destination chain; a `RedeemEscrow` request is relayed back and delivered to `onAccept`, which calls `IntentsBase._withdraw` with `body.tokens[0] = {token: R, amount: 1000e18}`.
4. `_withdraw` reads `escrowed = _orders[commitment][R] == 1000e18`, sets `_orders[commitment][R] = 0`, then calls `IERC20(R).safeTransfer(beneficiary, 1000e18)` — this reverts because the contract only holds `900e18` of `R`.
5. The entire `onAccept` transaction reverts. Because there is no other path to reduce the escrow amount or complete the withdrawal, every subsequent relayer delivery attempt for this commitment reverts identically, and the `900e18` of `R` (plus any co-escrowed tokens/fees under the same commitment) remain permanently locked in the `IntentGatewayV2` contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
