### Title
Relayer fee ledger can be dispatched for withdrawal without any guarantee the destination host actually holds enough balance to pay it, permanently losing the relayer's accrued reward - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer`'s `Fees` storage is an off-chain-verified accounting ledger (populated by `accumulate_fees` from state proofs of fee payments and delivery receipts, potentially on a different chain than the payout destination) analogous to the audited protocol's Merkle-root-based reward ledger. `withdraw()` reads this ledger's `available_amount`, zeroes it immediately, and dispatches a cross-chain "pay this amount" instruction — with no check that the destination chain (`EvmHost`/`HostManager`) actually holds a balance sufficient to cover it, exactly the "amount not guaranteed to be covered by balance" bug class from the report.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  reads `available_amount` purely from the `Fees` map (accumulated separately, over time, via `accumulate_fees`/`validate_results` in [2](#0-1) , which sums fees observed in *source*-chain state proofs and credits them to a relayer keyed by an arbitrary *destination* chain). It never queries or reconciles this figure against the actual token balance the destination `EvmHost` holds.

`withdraw()` then zeroes the `Fees` entry and dispatches an unbounded-timeout (`timeout: 0`) ISMP POST instructing the destination `HostManager`/`EvmHost` to pay `available_amount`, as documented in [3](#0-2)  ("the `Fees` entry is zeroed so the same balance cannot be withdrawn twice... never time out"). The corresponding on-chain payout in `EvmHost.withdraw()` performs a plain `safeTransfer` [4](#0-3)  which reverts outright if the host's fee-token balance is insufficient — confirmed by `test_host_manager_insufficient_balance` [5](#0-4) .

Because the Hyperbridge-side `Fees` entry is already zeroed at dispatch time (line 116-123 read + subsequent zeroing after building the request body, per the module doc), a revert on the destination due to insufficient balance leaves the relayer with no accounted balance to re-claim from, while the delivery either fails permanently or must be retried against a destination balance whose replenishment the relayer cannot control (it depends on unrelated future protocol fee collection on that specific host). This is structurally identical to the reported issue: an amount computed from an internally-tracked ledger (there: Merkle root; here: `Fees<T>`) is pushed for payout without validating it against the actual spendable balance at the payout location.

### Impact Explanation
A relayer that has legitimately earned fees can have its `Fees` entry zeroed by its own `withdraw_fees` call while the actual payout fails or is unrecoverable because the destination `EvmHost`'s fee-token balance does not cover the claimed amount. This results in a permanent loss of the relayer's rightfully accrued reward — freezing/loss of funds for the relayer, which the rules explicitly list as in-scope ("relayer fee and reward accounting").

### Likelihood Explanation
This requires no malicious actor: it triggers whenever the relayer's Hyperbridge-side accrued balance for a destination chain exceeds that specific `EvmHost`'s current fee-token balance — a routine condition since fees accrue from proofs of payments made on arbitrary source chains while payout draws from a single destination host's balance which fluctuates with unrelated protocol activity. Any relayer calling the ordinary, permissionless `withdraw_fees` extrinsic can hit this.

### Recommendation
Before zeroing `Fees<T>` and dispatching the withdrawal request, either (a) query/verify via a state proof that the destination host's balance covers `available_amount`, or (b) do not zero the ledger until a confirmed successful delivery receipt is observed, allowing safe retry/reclaim if the destination transfer reverts, mirroring the audited recommendation to validate the amount against the actual balance before committing to distribution.

### Proof of Concept
1. Relayer accrues `Fees::<T>[EVM_CHAIN][relayer] = 1000` via `accumulate_fees` after proving deliveries whose fees, in aggregate, were paid on various source chains (accumulate.rs `validate_results`).
2. `EvmHost` on `EVM_CHAIN` currently holds `< 1000` fee tokens (e.g., protocol fee inflow has been low or previously withdrawn by governance via `HostManager`/`host-executive::withdraw`, [6](#0-5) ).
3. Relayer calls `withdraw_fees` (withdrawal.rs) — `Fees` is zeroed, a POST with `amount: 1000` is dispatched to `HostManager`.
4. On delivery, `EvmHost.withdraw()` reverts (`SafeERC20` insufficient balance, as reproduced by `test_host_manager_insufficient_balance`).
5. The relayer's `Fees` entry is already zero on Hyperbridge; the relayer has no ledger balance to retry a claim from, and the failed delivery's eventual success depends on unrelated future balance top-ups it cannot control — resulting in loss of the earned reward.

	pub fn validate_results(
		proof: &WithdrawalProof,
		source_keys: Vec<Vec<u8>>,
		dest_keys: Vec<Vec<u8>>,
		source_result: BTreeMap<Vec<u8>, Option<Vec<u8>>>,
		dest_result: BTreeMap<Vec<u8>, Option<Vec<u8>>>,
	) -> Result<(BTreeMap<Vec<u8>, U256>, Vec<H256>), Error<T>> {
		let mut result = BTreeMap::new();
		// Only store commitments that were claimed
		let mut commitments = Vec::new();
		for ((commitment, source_key), dest_key) in
			proof.commitments.clone().into_iter().zip(source_keys).zip(dest_keys)
		{
			let encoded_metadata =
				if let Some(encoded) = source_result.get(&source_key).cloned().flatten() {
					encoded
				} else {
					// If fee is a null value skip it, evm returns non membership proof for
					// zero values
					continue;
				};

			let fee = match proof.source_proof.height.id.state_id {
				s if crate::is_pharos(&s) =>
					if encoded_metadata.len() == 32 {
						U256::from_big_endian(&encoded_metadata)
					} else {
						return Err(Error::<T>::ProofValidationError);
					},
				s if s.is_evm() => {
					use alloy_rlp::Decodable;
					let fee = alloy_primitives::U256::decode(&mut &*encoded_metadata)
						.map_err(|_| Error::<T>::ProofValidationError)?;
					U256::from_big_endian(&fee.to_be_bytes::<32>())
				},
				s if s.is_substrate() => {
					use codec::Decode;
					let fee: u128 = pallet_ismp::dispatcher::RequestMetadata::<T>::decode(
						&mut &*encoded_metadata,
					)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.fee
					.fee
					.into();
					U256::from(fee)
				},
				// unsupported
				_ => Err(Error::<T>::MismatchedStateMachine)?,
			};
			let encoded_receipt = dest_result
				.get(&dest_key)
				.cloned()
				.flatten()
				.ok_or_else(|| Error::<T>::ProofValidationError)?;
			let address = Self::decode_receipt_relayer(
				proof.dest_proof.height.id.state_id,
				&encoded_receipt,
			)?;
			let entry = result.entry(address).or_insert(U256::zero());
			*entry += fee;
			commitments.push(commitment);

					DispatchRequest::Post(post),

				)
