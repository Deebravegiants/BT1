Webhook `shop-domain`, `topic`, and `webhook-id` headers are dispatched to the app handler without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates that the *body bytes* were signed with the app's `client_secret` — but it says nothing about which shop, topic, or webhook-id the message is "for." Those three identity-carrying values are read straight from unauthenticated HTTP headers and forwarded verbatim into `WebhookMetadata`, which host applications use to route/act on a specific merchant's data. This is structurally the same class of bug as the Balancer report: a value that participates in the trust decision (`shop`) is not part of the bytes actually verified by the authenticator (the HMAC), so an attacker who can obtain *any* validly-signed webhook body for the app can re-present it while forging the identity field.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are never mixed into `to_signable_string`: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`: [4](#0-3) 

`Registry.process` treats a passing HMAC check as authorization to trust `request.shop`/`request.topic` and hands them to the registered handler as identity fields: [5](#0-4) [6](#0-5) 

**Broken identity binding (as an equality):**
`request.shop` (used by the host app to select the tenant/session to act on) is asserted to equal "the shop this signed message originated from," but the HMAC only proves `raw_body` came from Shopify's/the app's shared `client_secret` — it never binds `raw_body` to a particular `shop-domain`, `topic`, or `webhook-id`. Because a single app has one `client_secret` shared across every merchant that installs it, the same signing key produces valid signatures for every tenant. Before vs. after the header swap:

- Before (legitimate delivery to shop A): `hmac = HMAC(secret, body)`, `shop header = "shop-a.myshopify.com"` → `validate()` true, handler dispatched with `shop: "shop-a.myshopify.com"`.
- After (attacker replay): same `body`/`hmac` pair, `shop header` rewritten to `"shop-b.myshopify.com"` (or `topic`/`webhook_id` rewritten) → `validate()` is still true because it only re-derives the HMAC from `body`, and the handler is dispatched believing the event is for `shop-b.myshopify.com`.

### Impact Explanation
An unprivileged internet user who can obtain one legitimately-signed webhook payload for the target app (trivially achievable by installing the app on their own free/dev store and triggering an event such as `orders/create`) can replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header for a victim shop. Because this gem's `Registry.process` never revalidates that the claimed shop/topic match anything cryptographically bound to the body, the host application's handler executes attacker-controlled business logic under the belief that it is processing a genuine event for the victim shop. Depending on what the handler does with `WebhookMetadata#shop` (e.g., look up the victim's session/access token and perform an action, write attacker-supplied `body` data into the victim's tenant record, or trigger side effects keyed by shop), this crosses the tenant boundary — a cross-tenant data-integrity/action-injection issue satisfying the Critical "cross-tenant access" impact class, since it lets one merchant's authentic signature be repurposed to impersonate delivery for another merchant.

### Likelihood Explanation
High. No secrets, tokens, or elevated privileges are required beyond the ability to install the target app on any store (the normal, unprivileged path every merchant can take) and to send a raw HTTP POST with attacker-chosen headers to the app's public webhook endpoint — something explicitly supported by this gem's documented `Webhooks::Request.new(raw_body:, headers:)` / `Registry.process` API. No changes to Shopify's own webhook delivery are needed; the vulnerable surface is entirely inside this gem's verification logic, which the host app is instructed to rely on as sufficient proof of authenticity.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed material that `to_signable_string` returns, or otherwise cryptographically bind them to the body (e.g., verify them as part of the HMAC input, similarly to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`/`host`/`code` alongside the other fields it authenticates). At minimum, document and/or enforce that host apps must independently verify `request.shop` corresponds to an existing, `orders_id`-consistent shop record rather than trusting it as an authenticated value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g. updates an order), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H = base64(HMAC-SHA256(client_secret, B))` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `B` and `H`.
3. Attacker sends a new POST to the app's webhook endpoint with the same `raw_body = B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equal to `H` — validation succeeds because the shop header was never part of the signed input (see `Request#to_signable_string` above).
5. The handler for the topic is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the host app to act as if `B` were a genuine event for `victim.myshopify.com`.
