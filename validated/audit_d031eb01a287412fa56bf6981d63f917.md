### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` directly from unauthenticated HTTP headers, while `Utils::HmacValidator` (via `Request#to_signable_string`) only verifies the raw request body. Any attacker who possesses one valid `(body, hmac)` pair for the app — trivially obtainable by installing the app on their own store and receiving a legitimate webhook — can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` (and other) headers, producing a request that passes `Registry.process`'s HMAC check yet reports an arbitrary victim shop to the handler.

### Finding Description
The HMAC binding breaks the equality: `shop_authenticated_by_hmac == shop_delivered_to_handler`.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all read straight from attacker-controllable HTTP headers, with no cryptographic linkage to the body: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e., only the body, never the headers: [4](#0-3) 

`Registry.process` trusts the HMAC-validated request wholesale and forwards `request.shop` (an unauthenticated header) straight to the app's handler as the tenant identifier: [5](#0-4) 

Since a single `api_secret_key` HMACs the same way regardless of which shop installed the app, any merchant who is a genuine, unprivileged install of the app can capture a body+HMAC pair from their own legitimate webhook traffic and resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a different, victim shop. The signature still validates (it only covers the body), but `WebhookMetadata#shop` now reports the attacker-chosen victim domain to the host application's handler.

### Impact Explanation
If the host application uses `data.shop` from `WebhookMetadata` to key which merchant's data/session gets updated (a common pattern — e.g., updating order/inventory state, disabling features, or writing metafields tied to "the shop from the webhook"), a malicious but legitimately-installed merchant can inject arbitrary, apparently-legitimate webhook events attributed to another shop. This is a cross-tenant data integrity/access issue: state belonging to shop B can be mutated or read using no more than the attacker's own valid installation and this gem's own header-parsing logic — no access token or secret theft is needed.

### Likelihood Explanation
Any merchant who installs the app is, by definition, an unprivileged internet user relative to other tenants of the same app. Obtaining a valid `(body, hmac)` pair only requires triggering a webhook on their own store (e.g., an `orders/create` webhook), which is trivial and requires no special access. Forging the HTTP headers on the replayed request requires only a normal HTTP client. This makes the analog highly reachable through this gem's own supported webhook-processing API (`Webhooks::Registry.process` / `Webhooks::Request.new`), not a misuse of undocumented behavior.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated material, or otherwise re-derive/validate them independently of the raw headers:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (this would require coordination since Shopify computes the HMAC over the body only — if that's fixed, the gem should instead require the application to independently confirm the `shop` header corresponds to a shop with a known/registered session before trusting it), or
- Document explicitly, and enforce in `Registry.process`, that `request.shop` must be cross-checked by the caller against an existing, previously-established session/webhook registration before being treated as trusted tenant data.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged install).
2. Attacker triggers any webhook subscribed by the app (e.g. `orders/create`) and captures the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify — `H` is a valid HMAC of `B` under the app's `api_secret_key`.
3. Attacker replays the exact same request to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic`/`x-shopify-webhook-id` as desired
   - keeps the original body `B` and `x-shopify-hmac-sha256: H` unchanged.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host application to act on the victim shop's tenant data using attacker-supplied content, despite the request never having been authenticated as originating from Shopify on behalf of `victim.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
