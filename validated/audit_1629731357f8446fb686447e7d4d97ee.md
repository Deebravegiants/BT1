### Title
Webhook `shop` domain is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `X-Shopify-Hmac-SHA256` header against the raw request body, then extracts the `shop` (tenant) identifier from a separate, unsigned header and hands it directly to the host application's handler. Because the shop domain is a field acted upon (used as the tenant/session key by the host app) but is not part of the HMAC-covered payload, the binding `hmac_signed_bytes == tenant_identifying_bytes` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never mixed into the signable string: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, i.e. body bytes only: [4](#0-3) 

`Webhooks::Registry.process` performs this HMAC check, then immediately constructs `WebhookMetadata` from `request.shop` (the unauthenticated header) and passes it to the application's `handler.handle`, with no cross-check that the header-supplied shop is consistent with anything cryptographically bound to the verified body: [5](#0-4) 

By contrast, the OAuth `AuthQuery` verifiable object explicitly folds `shop` into `to_signable_string`, so the shop cannot be swapped without invalidating the HMAC: [6](#0-5) 

This shows the gem is capable of, and elsewhere does, bind `shop` to the signature — but for webhooks it does not. Any consumer relying on `request.shop`/`WebhookMetadata#shop` returned by this gem as an authenticated tenant identifier is exposed to header spoofing: since the HMAC only proves "this body byte-for-byte came from Shopify (or someone with the secret) at some point," not "this body was addressed to shop X," an attacker who can replay or relay a validly-signed webhook body (e.g., a webhook legitimately delivered to their own shop's endpoint in a multi-tenant app) can resubmit it with an altered `shop-domain` header, and this gem will report it to the host application as originating from the attacker-chosen shop.

### Impact Explanation
If a host application uses the `shop` value returned by `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata` to look up per-tenant offline sessions, apply data (e.g. process an `orders/create` payload as belonging to a different merchant, trigger `shop/redact` data deletion for the wrong tenant, or write attacker-controlled body content into another merchant's records), this results in cross-tenant data corruption or disclosure — one of the explicitly in-scope "Critical" outcomes (cross-tenant access).

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly HMAC-signed webhook body (trivially obtainable by installing the app on their own store and capturing a real webhook delivery), then resend it to the app's webhook endpoint with a modified `shop-domain` header. No secret key or credential compromise is required, matching the "unprivileged internet user" threat model. The severity ultimately depends on how the host app uses `request.shop`, which is outside this gem, but the gem provides no primitive to detect or prevent the mismatch, unlike the OAuth path where `shop` is explicitly bound into the signed payload.

### Recommendation
Bind the `shop` (and `topic`) header values into the value that is HMAC-verified, or otherwise cryptographically/structurally tie the header-derived tenant identifier to the verified body (for example, requiring host apps to independently confirm the delivered shop against a known/registered shop before trusting it, and documenting this prominently). At minimum, `Webhooks::Request#to_signable_string` should not silently diverge from the pattern used in `Auth::Oauth::AuthQuery`, where the `shop` field is included in the signable content.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures a legitimately delivered webhook: raw body `B` and header `X-Shopify-Hmac-SHA256: H` (valid for `B` under the app's secret), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same `B`/`H` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and it matches `H`, so validation passes: [7](#0-6) 
4. `WebhookMetadata` is built with `shop: request.shop`, now returning `"victim.myshopify.com"`, and the host app's handler processes the (attacker-controlled) body `B` as if it were sent by `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
