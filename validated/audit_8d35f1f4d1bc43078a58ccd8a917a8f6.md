### Title
Webhook shop/topic identity spoofing via headers not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by the registry and handed to app handlers are read from unauthenticated HTTP headers. The identity binding "shop the HMAC was computed for" == "shop the handler is told to act on" does not hold, allowing a party who possesses one valid `(raw_body, hmac)` pair for the app's shared `client_secret` to relabel that payload as belonging to any other shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates only that HMAC via `Utils::HmacValidator.validate(request)`, which in turn hashes `verifiable_query.to_signable_string` (the raw body) with `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, the registry constructs `WebhookMetadata` using the unauthenticated header-derived `request.shop`, `request.topic`, and `request.webhook_id`, and dispatches it to the app-registered handler: [5](#0-4) 

Crucially, the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that has installed the same app — Shopify does not use a per-shop signing key for webhooks. Consequently, the equality this mechanism is supposed to enforce — "the shop bound to the HMAC-verified bytes" == "the shop the handler is told the payload came from" — is broken: HMAC verifies *that the body is genuine for this app*, but not *which shop it belongs to*. Any tenant of a multi-tenant app can obtain a genuinely-signed `(raw_body, hmac)` pair from their own store's webhook delivery, then replay that exact raw body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a different, victim shop. `HmacValidator.validate` still returns `true` because it never inspects those headers, and the handler receives `WebhookMetadata` claiming the forged shop.

### Impact Explanation
This crosses the tenant boundary required for a "High" impact analog: cross-tenant confusion via a scope/identity check that answers permissively (HMAC validated on bytes not bound to the acted-upon shop identity). Any app that keys its tenant-scoped side effects (e.g., "look up merchant record for `data.shop` and apply the payload", GDPR redact routines for `shop/redact`, `customers/redact`, `customers/data_request`, or state transitions keyed by `data.shop`) off `WebhookMetadata#shop` is exposed to another tenant injecting data/events attributed to a shop they do not control, because this gem's contract for that value is only "read from an HTTP header," not "cryptographically bound to the signed payload."

### Likelihood Explanation
Any user who can install the app onto their own Shopify store (an ordinary, unprivileged action available to any merchant/internet user for public apps) can capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from their own webhook deliveries — no leaked secrets, TLS interception, or privileged access required. They can then directly POST that raw body with a forged `X-Shopify-Shop-Domain` header to the app's own registered webhook endpoint. `Registry.process` performs no additional binding check between the header-derived shop and the HMAC-covered content.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them, e.g. via a signed envelope) so `Utils::HmacValidator.validate` fails whenever any header used to build `WebhookMetadata` has been tampered with. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be trusted for tenant-scoping decisions without independent verification (e.g., cross-checking against a known/installed shop list) by the host application.

### Proof of Concept
1. App installs on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (or attacker simply owns any shop with the app installed).
2. Shopify delivers a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   - Body: `{"id": 1, ...}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker captures this exact `(raw_body, hmac)` pair and re-POSTs it to the app's webhook endpoint, replacing only the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - Keeping the same `raw_body` and `X-Shopify-Hmac-Sha256`.
4. `Registry.process` → `Utils::HmacValidator.validate(request)` succeeds because it recomputes the HMAC solely over `raw_body`: [6](#0-5) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is passed to the app's handler with `shop == "victim-shop.myshopify.com"`, even though the payload originated from `attacker-shop`: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
