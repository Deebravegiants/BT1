### Title
Relayer fee balance is zeroed on withdrawal-request dispatch before the cross-chain payout is confirmed delivered, permanently losing funds if destination execution fails - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-ismp-relayer`'s `Pallet::withdraw` dispatches a cross-chain ISMP POST request instructing the destination `HostManager`/`EvmHost` (or the substrate `HYPERBRIDGE_MODULE_ID` handler) to disburse a relayer's accrued fees, and unconditionally zeroes the relayer's `Fees` entry on hyperbridge immediately after dispatch — without any confirmation that the destination-side transfer actually succeeds.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` does the following in order:
1. Reads `available_amount` from `Fees::<T>::get(...)`.
2. Calls `dispatcher.dispatch_request(...)` which only enqueues the POST request commitment — it does not, and cannot, wait for the destination chain to execute and confirm the payout.
3. Immediately after (`modules/pallets/relayer/src/withdrawal.rs:177`), sets `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero())`.

This mirrors the M-27 pattern precisely: state representing entitlement to funds (`Fees`) is zeroed based only on *initiating* an action, not on its confirmed *completion*. The request is built with `timeout: 0` (`modules/pallets/relayer/src/withdrawal.rs:166`), which per the docs (`docs/content/developers/network/relayer.mdx:742`) means "This request will not timeout, allowing it to be submitted to the destination chain at any time" — i.e. there is no automatic timeout/refund path if delivery never succeeds.

On the EVM destination, the payout is executed by `EvmHost.withdraw()` (`evm/src/core/EvmHost.sol:651-660`), invoked via `HostManager.onAccept()` (`evm/src/core/HostManager.sol:134-159`). If the host's fee-token balance is insufficient, `IERC20(token).safeTransfer` reverts, which is confirmed by the test `test_host_manager_insufficient_balance` (`evm/tests/rust/src/tests/host_manager.rs:152-182`), which asserts the whole `onAccept` call reverts. A reverted `onAccept` call means the ISMP delivery transaction itself reverts, so the destination relayer must retry delivery of the same commitment later once liquidity is available — this part is potentially recoverable if the relaying can be retried indefinitely (no timeout).

The unrecoverable failure mode is when the destination-side execution can fail *without ever being retriable*, or is never delivered at all (e.g. no relayer picks up the message, the destination host manager configuration is stale/misconfigured, `MissingMangerAddress`/`InvalidPublicKey`-class conditions on retry, or the destination account rejects funds). Because the source-side `Fees` balance was already zeroed at dispatch time and there is no timeout to trigger a refund, and `accumulate_fees` cannot be re-run for the same delivered messages (the relayer's proof-of-delivery has already been consumed to credit `Fees` once), the relayer has no path to reclaim the fee if the withdrawal message is permanently stuck or its destination-side effect can never be completed.

### Impact Explanation
If the destination-side withdrawal message fails to ever complete successfully (liquidity permanently insufficient in the `EvmHost`/host-manager fee pool, misconfigured `host_manager`/`fee_token` params, or the message is simply never relayed and no operator resubmits it), the relayer's earned fees are permanently frozen/lost: `Fees` is already zero on hyperbridge, so the relayer cannot re-initiate withdrawal, and there is no protocol-level refund or retry-credit mechanism tied to delivery failure. This is a Medium-severity fund-freezing/loss issue affecting relayer reward accounting, directly analogous to the Derby M-27 report where state was zeroed without confirming the corresponding withdrawal fully completed.

### Likelihood Explanation
Likelihood is non-trivial but not high: EVM-side reverts due to insufficient host balance are retryable (no receipt is stored on revert), so a single insufficient-balance revert alone doesn't strand funds. However, once `timeout: 0` is combined with any prolonged failure to relay/deliver (operational unavailability, permanently misconfigured host manager address/fee token after a governance change, or the destination chain repeatedly rejecting delivery), the funds become effectively frozen indefinitely with no on-chain fallback, since the source has already discarded the accounting record of the debt.

### Recommendation
Do not zero the `Fees` balance until destination-side settlement is confirmed. Instead:
- Track a pending withdrawal state per `(relayer, dest_chain, nonce)` keyed to the dispatched request commitment, and only clear `Fees` once a delivery/settlement confirmation (or `PostResponse`/receipt observation) is received back on hyperbridge.
- Alternatively, restore (re-credit) `Fees` on `on_timeout` for the given commitment, and set a bounded (non-zero) timeout rather than `timeout: 0`, so a stuck request can eventually revert and refund the relayer's balance rather than being unrecoverable forever.

### Proof of Concept
1. A relayer accumulates fees on hyperbridge for chain `dest_chain` via `accumulate_fees`, crediting `Fees::<T>::get(dest_chain, relayer)`.
2. Relayer calls `withdraw_fees` → `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81`). This dispatches an ISMP POST with `timeout: 0` to the destination `HostManager`, then immediately sets `Fees` to zero (line 177), before any confirmation of delivery.
3. Suppose the destination `EvmHost`'s fee-token balance is (or later becomes) insufficient, or the `host_manager`/`fee_token` params configured in `pallet-ismp-host-executive::HostParams` become stale/misconfigured before delivery. Every delivery attempt of the withdrawal POST reverts in `HostManager.onAccept` → `EvmHost.withdraw` (as reproduced by `test_host_manager_insufficient_balance`), and because `timeout: 0`, the request never times out to trigger any refund path.
4. The relayer's on-chain fee record is already zero and cannot be reclaimed by any other pallet call, permanently freezing the funds until (if ever) an operator manually notices, tops up host balance, and successfully relays — a condition outside the relayer's control and unenforced by protocol logic.     /**
     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

    function onAccept(IncomingPostRequest calldata incoming)
        external
        override
        restrict(msg.sender, _params.host)
        restrict(incoming.relayer, _params.admin)
    {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        } else if (action == OnAcceptActions.SetAdmin) {
            // Rotates the governance relayer.
            address newAdmin = abi.decode(request.body[1:], (address));
            if (newAdmin == address(0)) revert InvalidAdmin();
            emit AdminUpdated({previous: _params.admin, current: newAdmin});
            _params.admin = newAdmin;
        }
    }

## Withdrawing Fees

Tesseract maintains a local sqlite database where it keeps track of successfully delivered messages. The withdrawal process happens in two phases, the first phase is the fee accumulation on hyperbridge, then withdrawal on any of the connected chains.
In the fee accumulation phase, tesseract submits state proofs of messages all delivered to hyperbridge. If the proof verification is successful, the total amount of unclaimed fees for the relayer address is updated onchain. Next, the relayer can submit a withdrawal transaction to hyperbridge. This initiates potentially multiple ISMP requests to any chain where it has unclaimed fees, that instructs the Hyperbridge contract to credit the relayer their owed funds. This request will not timeout, allowing it to be submitted to the destination chain at any time.
