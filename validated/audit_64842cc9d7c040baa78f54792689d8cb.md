### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching it to the app's handler, but the HMAC verification only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are taken straight from unauthenticated HTTP headers — are handed to the handler as if they were verified, breaking the binding `hmac_valid(body) == shop_header_is_authentic`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are read directly from headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` signs/compares exactly `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop`/`request.topic` to build the metadata object passed to the app's handler: [4](#0-3) 

The gem's own documentation tells integrators that calling `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop identity — is authenticated: [5](#0-4) 

In reality, the `api_secret_key` used for the HMAC is shared by every shop that has the same app installed (it's the app's client secret, not a per-shop secret). Consequently, any merchant who has legitimately installed the app can:
1. Receive/observe a legitimate webhook body + valid HMAC signature for their own shop.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint over the internet, but substitute the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a different shop's domain.
3. `Utils::HmacValidator.validate` still succeeds (it only checks the body against the app's secret), so `Registry.process` calls the app's handler with `WebhookMetadata` claiming the data belongs to the victim shop.

The equality that should hold — `hmac_signed_fields ⊇ {shop, topic}` — does not; the HMAC binds nothing about which shop or topic the payload is "for," only that the body bytes were produced with knowledge of the app secret (which every installer effectively can do by triggering webhooks on their own store).

### Impact Explanation
This breaks the identity binding between "HMAC-verified" and "attributed to shop X," letting one tenant's merchant inject data into another tenant's webhook processing pipeline within the host app, as long as the host app relies on `WebhookMetadata#shop`/`#topic` (as the gem's own docs instruct) to select which tenant's records to update. This is a cross-tenant data-confusion vector reachable by any user who can install the app in their own shop and reach the app's public webhook endpoint — no privileged credentials required.

### Likelihood Explanation
Any developer using the library as documented (verify via `Registry.process`, then trust `WebhookMetadata.shop`/`.topic`) is exposed. The only requirement for the attacker is: (a) install the app on a shop they control (a normal, unprivileged action any merchant can do) to obtain a valid `(body, hmac)` pair, and (b) send a crafted HTTP POST to the app's public webhook URL with a forged `shop`/`topic` header. No secret material beyond what's already exposed through normal app installation is needed.

### Recommendation
Include the shop domain (and ideally topic) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop`/`topic` fields to the authenticated payload before constructing `WebhookMetadata`. At minimum, update `HmacValidator`/`Request#to_signable_string` so the signable string incorporates the `shop-domain` header, and document clearly that `request.shop` is not itself authenticated unless it is covered by the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook (e.g. `orders/create`) and capturing the raw POST body and its `x-shopify-hmac-sha256` header value.
2. Attacker sends a new POST request to the app's webhook endpoint with:
   - The same captured `raw_body` and `x-shopify-hmac-sha256`.
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. `Utils::HmacValidator.validate` returns `true` because only the body is checked against `Context.api_secret_key` (same secret for all shops of the app).
4. `Registry.process` (see `lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker's own order data>, ...)`, causing the host app to act on attacker-controlled data believing it originates from `victim-shop.myshopify.com`.
