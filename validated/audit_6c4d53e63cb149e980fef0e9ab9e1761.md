### Title
Webhook `shop` attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by HMAC-signing the raw JSON body, while the `shop` domain that the app attributes the webhook to is read from an unauthenticated HTTP header. Because the app's `client_secret` (and therefore the HMAC key) is identical across every shop that installs the app, any merchant who receives a legitimately-signed webhook for their own shop can replay that exact body with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a different shop, and the signature check still passes. This breaks the intended identity binding `authenticated(body) == authenticated(shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from an HTTP header that is never included in the signed content: [2](#0-1) 

`Registry.process` validates the request using `HmacValidator.validate(request)`, which calls `to_signable_string` (i.e., only the body) and compares it against `Context.api_secret_key`: [3](#0-2) 

Once the HMAC check passes, `Registry.process` unconditionally trusts `request.shop` and hands it to the app's handler as the tenant identifier, with no cross-check that the signed body actually belongs to that shop: [4](#0-3) 

Since `Context.api_secret_key` is the single app-wide secret shared by every merchant who installs the app (it is not per-shop), any merchant is able to generate a validly-signed webhook body for their own shop and then present that same signed body under an arbitrary `shop-domain` header value. The signature verification (`OpenSSL.secure_compare` over the body only) has no way to detect the substitution, because the `shop` field is never part of the signed material.

This is exactly the identity-binding gap called out in the report's bug class: a field ("shop") acted upon by the caller is not covered by the HMAC that is supposed to authenticate the whole request.

### Impact Explanation
An app that relies on `WebhookMetadata#shop` (as populated at `lib/shopify_api/webhooks/registry.rb:198`) to select, key, or scope per-tenant data — e.g., to look up which merchant record to update, or to decide which tenant's resources the payload affects — can be made to attribute attacker-supplied webhook content to a victim shop chosen by the attacker. This is a cross-tenant confusion/injection vector: data or actions intended for shop A can be attributed to shop B purely by rewriting an unauthenticated header, without ever needing the victim's credentials or `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any account that can install the app (an "unprivileged internet user" from the perspective of any other tenant) automatically receives real, validly HMAC-signed webhooks for their own shop. Replaying one of these with a modified `shop-domain` header requires no secret material beyond what every installer already legitimately possesses (a signed webhook of their own). The exploit path requires only basic HTTP replay capability, making it straightforward once the gem's webhook consumer (`Registry.process`) is wired into an app that trusts `request.shop`/`WebhookMetadata#shop` for tenant scoping — a usage pattern the library's own API surface (passing `shop` straight through to the handler) encourages.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the signed body, before it is handed to application handlers — e.g., include the shop domain in the signable string, or require the app to independently confirm the shop against a value derived from a source that is itself covered by the signature (or from the recipient's own known-active shop/access-token record) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. App merchant M installs the target app; M's shop is `attacker.myshopify.com`. Shopify sends a legitimate webhook to the app for topic `orders/create` with body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and `x-shopify-hmac-sha256` computed as `HMAC-SHA256(client_secret, B)` — verified as in `lib/shopify_api/utils/hmac_validator.rb:26-31`.
2. M captures this HTTP request (their own webhook; no secrets required beyond what they legitimately received).
3. M resends the identical body `B` and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against the shared `client_secret` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though the payload actually originated from M's own shop — demonstrating the shop-attribution spoof.
