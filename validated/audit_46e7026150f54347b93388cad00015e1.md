### Title
Webhook `shop` and `topic` identifiers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, but `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` headers when dispatching to the registered handler. This breaks the identity binding `shop verified by HMAC == shop acted upon by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and the HMAC validation in `Utils::HmacValidator.validate_signature` computes/compares the signature against that string alone: [1](#0-0) [2](#0-1) 

Meanwhile, `Request#shop`, `Request#topic`, `Request#webhook_id`, and `Request#api_version` are all read directly from HTTP headers, which are entirely unauthenticated inputs: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body's integrity/authenticity, not the header values), then immediately dispatches the handler using `request.shop` and `request.topic` straight from the unauthenticated headers: [4](#0-3) 

Because the shop/topic identifiers used to attribute the webhook to a specific tenant are never part of the signed material, any raw body + valid HMAC pair (which an attacker can legitimately obtain from a webhook delivered to their own store, since they control that store and see its genuine deliveries) can be replayed with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. The signature still validates because it only checks the body against the app's `api_secret_key`, and the handler will process the payload as if it belongs to the shop named in the (forged) header — the classic "field acted on but not covered by the HMAC" binding break named in the rules.

### Impact Explanation
This allows a merchant who has legitimately installed the app on their own store (an unprivileged, non-credentialed attacker with respect to any other tenant) to make the app attribute arbitrary webhook data to a different, victim shop domain, since the `shop` claim consumed by `WebhookMetadata` and handed to the app's handler is never cryptographically bound to the signature. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up per-tenant session/API credentials, write to per-tenant records, or trigger per-tenant side effects), this enables cross-tenant data corruption/impersonation, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any party who has installed the app (or otherwise has one authentic webhook body+HMAC pair for their own store) can trivially replay it to the app's public webhook endpoint with a substituted `shop-domain` header — no access to `client_secret`, access tokens, or privileged accounts is required. The only requirement is network reachability to the webhook endpoint, which by design is internet-facing.

### Recommendation
Bind the trusted identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) into the HMAC-signed material, or otherwise cryptographically tie the `shop-domain` header to the signature (e.g., include it in `to_signable_string`, or validate it against a shop known to have provided the secret used). At minimum, cross-check the `shop-domain` header against an independently trusted source (such as a session store keyed by an already-authenticated relationship) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and receives a genuine webhook delivery, e.g., `orders/create`, with raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint, keeping `raw_body: B` and `x-shopify-hmac-sha256: H`, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (line 198) builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged `victim-shop.myshopify.com` value, and the host application's handler processes/persists the data as belonging to `victim-shop`, despite it never having sent this webhook.
