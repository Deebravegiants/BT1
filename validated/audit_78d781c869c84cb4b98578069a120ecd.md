Based on my analysis, I found a strong custody-grade analog: the `bonding_curve_launchpad::swap` entry function performs constant-product-formula swaps against a liquidity pair's live APT/FA reserves with **no minimum-output/slippage parameter at all**, unlike the sibling `swap` DEX module (`aptos-move/move-examples/swap/sources/router.move`) which requires `amount_out_min` and enforces `assert!(fungible_asset::amount(&out) >= amount_out_min, ...)`.

### Title
Permissionless `bonding_curve_launchpad::swap` lacks slippage protection, enabling sandwich-attack theft of pool reserves - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move`)

### Summary
`bonding_curve_launchpad::swap` [1](#0-0)  is a permissionless entry function that any account can call to trade APT against a launched FA through the constant-product `liquidity_pairs` reserves. It forwards directly to `liquidity_pairs::swap_fa_to_apt`/`swap_apt_to_fa` [2](#0-1) [3](#0-2)  with only `amount_in` — there is no `amount_out_min`/expected-output parameter or check anywhere in the call path, and `get_amount_out` computes the output purely from the current on-chain reserves at execution time [4](#0-3) .

### Finding Description
The reserves (`fa_reserves`/`apt_reserves`) held in the `LiquidityPair` object are custody-critical state: the FA is escrowed in `fa_store` (a `FungibleStore` on the pair object) and APT is escrowed via the pair object's own account, both governed exclusively by `transfer_ref`/signer-extension held internally [5](#0-4) . Because `swap` takes no minimum-output guarantee, an unprivileged attacker can:
1. Observe a victim's pending `swap` transaction in the mempool.
2. Front-run it with their own `swap_apt_to_fa` (or `swap_fa_to_apt`) call that shifts reserves unfavorably against the victim's expected price.
3. Let the victim's swap execute at the manipulated price, receiving far less output than the fair-market amount implied by the reserves at submission time.
4. Back-run with an opposite swap to restore reserves and capture the value difference extracted from the victim.

This is functionally the exact "sandwich attack on a permissionless AMM function without slippage control" pattern from the external Mochi report, translated to the Aptos custody model: the corrupted value is the FA/APT amount actually transferred out of the escrowed `fa_store`/pair-object APT balance to the attacker instead of the honest counterparty, i.e., a custody-accounting corruption that moves value to the wrong holder. Contrast this with the companion module `swap/sources/router.move`, which explicitly documents and enforces `amount_out_min` for this exact reason [6](#0-5) , confirming the missing check in `bonding_curve_launchpad` is a genuine omission relative to the project's own established mitigation pattern.

### Impact Explanation
Every swapper interacting with `bonding_curve_launchpad::swap` is exposed to value extraction bounded only by the depth/thinness of the liquidity pair's reserves (which start artificially thin due to `INITIAL_VIRTUAL_APT_LIQUIDITY` [7](#0-6) , making early trades especially susceptible to large slippage manipulation). This is a direct, repeatable theft of escrowed FA/APT value from legitimate users' swap outputs — a custody-grade impact under "Theft ... of APT, fungible assets, token objects... held value" and "Supply or custody accounting corruption that moves value to the wrong holder."

### Likelihood Explanation
High. The function is `public entry`, fully permissionless, requires no special privilege, and the attack only needs ordinary transaction ordering/front-running capability (readily available on any chain with a public mempool/ordering window) plus enough capital to move the thin reserves — no flash loan primitive is even required on Aptos to be effective given the shallow virtual-liquidity design.

### Recommendation
Add a `min_amount_out` (or `max_amount_in`) parameter to `bonding_curve_launchpad::swap` and thread it through to `liquidity_pairs::swap_fa_to_apt`/`swap_apt_to_fa`, aborting if the computed output/price deviates beyond the caller's specified bound — mirroring the pattern already used in `swap/sources/router.move`'s `swap_entry`/`swap` functions [6](#0-5) .

### Proof of Concept
1. Attacker monitors mempool for a victim's `bonding_curve_launchpad::swap(name, symbol, /*swap_to_apt=*/false, amount_in=X)` (buying FA with APT).
2. Attacker submits `swap(..., swap_to_apt=false, amount_in=Y)` with higher gas/priority to execute first, pushing `apt_reserves` up and `fa_reserves` down per `get_amount_out` [8](#0-7) .
3. Victim's transaction executes next at the now-worse price, receiving materially less FA than expected, with no `amount_out_min` to revert the trade.
4. Attacker submits `swap(..., swap_to_apt=true, ...)` to sell the FA back to the pair, extracting the value taken from the victim, restoring reserves near their original ratio. [9](#0-8)

        };

    public fun get_amount_out(
        fa_reserves: u128,
        apt_reserves: u128,
        swap_to_apt: bool,
        amount_in: u64
    ): (u64, u64, u128, u128) {
        if (swap_to_apt) {
            let divisor = fa_reserves + (amount_in as u128);
            let apt_gained = (math128::mul_div(apt_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves + (amount_in as u128);
            let apt_updated_reserves = apt_reserves - (apt_gained as u128);
            assert!(apt_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (amount_in, apt_gained, fa_updated_reserves, apt_updated_reserves)
        } else {
            let divisor = apt_reserves + (amount_in as u128);
            let fa_gained = (math128::mul_div(fa_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves - (fa_gained as u128);

            (fa_gained, amount_in, fa_updated_reserves, apt_updated_reserves)
        }

    /// Facilitate swapping between a given FA to APT.
    public(friend) fun swap_fa_to_apt(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of APT, when given swapper-supplied amount_in of FA.
        let (fa_given, apt_gained, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            true,
            amount_in
        );
        // Verify the swapper holds the FA.
        let swapper_address = signer::address_of(swapper_account);
        let does_primary_store_exist_for_swapper = primary_fungible_store::primary_store_exists(
            swapper_address,
            fa_object_metadata
        );
        assert!(does_primary_store_exist_for_swapper, EFA_PRIMARY_STORE_DOES_NOT_EXIST);
        // Perform the swap.
        // Swapper sends FA to the liquidity pair object. The liquidity pair object sends APT to the swapper, in return.
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        let from_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        fungible_asset::transfer_with_ref(transfer_ref, from_swapper_store, liquidity_pair.fa_store, fa_given);
        aptos_account::transfer(&liquidity_pair_signer, swapper_address, apt_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: false,
                gained: (apt_gained as u128),
                swapper_address
            }
        );
    }

    /// Swap an amount of fungible assets for another fungible asset. User can specifies the minimum amount they
    /// expect to receive. If the actual amount received is less than the minimum amount, the transaction will fail.
    public entry fun swap_entry(
        user: &signer,
        amount_in: u64,
        amount_out_min: u64,
        from_token: Object<Metadata>,
        to_token: Object<Metadata>,
        is_stable: bool,
        recipient: address,
    ) {
        let in = primary_fungible_store::withdraw(user, from_token, amount_in);
        let out = swap(in, amount_out_min, to_token, is_stable);
        primary_fungible_store::deposit(recipient, out);
    }

    /// Similar to swap_entry but returns the fungible asset received for composability with other modules.
    public fun swap(
        in: FungibleAsset,
        amount_out_min: u64,
        to_token: Object<Metadata>,
        is_stable: bool,
    ): FungibleAsset {
        let from_token = fungible_asset::asset_metadata(&in);
        let pool = liquidity_pool::liquidity_pool(from_token, to_token, is_stable);
        let out = liquidity_pool::swap(pool, in);
        assert!(fungible_asset::amount(&out) >= amount_out_min, EINSUFFICIENT_OUTPUT_AMOUNT);
        out
    }
