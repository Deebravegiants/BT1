- `Resolver.Bridge`/`Resolver.Bridges` gate access solely with `authenticateUser(ctx)`, which requires only a valid session ("view" access), confirmed in `core/web/resolver/query.go` and `core/web/resolver/auth.go`. [1](#0-0)

[3](#0-2) [4](#0-3)

[5](#0-4) 

I could not find any indication in `SECURITY.md`, `RESEARCHER.md`, `CHANGELOG.md`, or code comments that this behavior is intentional, documented, or already fixed/acknowledged. The `OutgoingToken` is a real bearer credential used by the node to authenticate to external adapters (per `core/bridges/bridge_type.go` field naming and usage), so its disclosure to the lowest-privilege `view` role is a genuine credential-exposure issue distinct from the excluded "leaked credential" or "operator-only" categories in `SECURITY.md` — the credential is not leaked by external means, it is disclosed by the application's own API to an authenticated-but-unprivileged user, which is squarely in-scope as key/secret exfiltration via authorization/role bypass.

The exploit path requires only creating a `view`-role user (an unprivileged, non-admin action available via normal node administration) and issuing a standard GraphQL query or REST GET — no operator/admin/host access is needed to *trigger* the disclosure itself.

Audit Report

## Title
View-role users can read bridge `OutgoingToken` credentials via GraphQL/REST bridge queries - (File: core/web/resolver/bridge.go, core/web/presenters/bridges.go)

## Summary
The `Bridge`/`Bridges` GraphQL resolvers and the `GET /v2/bridge_types` REST endpoints only enforce a session-presence check (`authenticateUser`, granting the lowest "view" role) before returning the bridge's `OutgoingToken`, a live credential Chainlink uses to authenticate itself to external adapters. There is no field-level authorization separating "can see a bridge exists" from "can see its outbound secret," unlike `IncomingToken`, which is deliberately withheld except at creation time.

## Finding Description
`Resolver.Bridge` and `Resolver.Bridges` in `core/web/resolver/query.go` call `authenticateUser(ctx)`, which per its own doc comment only confirms "presence of user inherently provides 'view' access" [1](#0-0) . The returned `BridgeResolver.OutgoingToken()` unconditionally exposes `r.bridge.OutgoingToken` [2](#0-1) . The REST equivalent, `BridgeTypesController.Index`/`Show`, serializes the same field via `presenters.NewBridgeResource`, whose `BridgeResource.OutgoingToken` has no `omitempty` gating (unlike `IncomingToken`, which is explicitly documented as "only provided when creating a Bridge") [4](#0-3) , and the RBAC route table confirms these REST reads are `viewOnlyAllowed: true` [3](#0-2) . The codebase does define stricter role middleware (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` in `core/web/auth/auth.go`) but none of it is applied to these bridge-read paths, confirming the item-level/field-level conflation.

## Impact Explanation
Any authenticated node user provisioned with only the `view` role — intended strictly for read-only observability — can retrieve the `OutgoingToken` for every configured bridge. Since this token is the credential the node presents to external adapters, its disclosure to a nominally-unprivileged role enables impersonation of the node toward the external adapter and misuse of the credential outside its intended trust boundary. This maps to the in-scope "key/secret exfiltration" and "node API authentication/role bypass" impact categories.

## Likelihood Explanation
High. Exploitation requires only a standard `view`-role user account (the lowest privilege tier, explicitly meant for read access) and a single GraphQL query or REST GET request — no additional exploitation steps, timing, or race conditions are needed.

## Recommendation
Add field-level authorization to `BridgeResolver.OutgoingToken()` and `presenters.NewBridgeResource` so that `OutgoingToken` is only populated for callers with at least `edit`/`admin` role (mirroring the treatment already given to `IncomingToken`), rather than relying on the coarse `authenticateUser`/`viewOnlyAllowed` route-level gate.

## Proof of Concept
1. Create a node user with role `view` (e.g. `chainlink admin users create --role=view`).
2. Authenticate as that user and issue either:
   - GraphQL: `query { bridges { results { name outgoingToken } } }`
   - REST: `GET /v2/bridge_types`
3. Observe `outgoingToken` values returned for existing bridges despite the caller holding only the `view` role.
