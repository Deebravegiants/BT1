### Title
Webhook `shop-domain` (and `topic`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds only the raw request body to the HMAC signature check. The `shop-domain` and `topic` headers — which `Registry.process` uses to dispatch and identify the tenant for the webhook — are read directly from unauthenticated headers and never included in the signed content, breaking the identity binding "shop authenticated == shop acted upon."

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

`Request#shop` and `Request#topic` are pulled straight from HTTP headers with no cryptographic binding to those values: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values: [4](#0-3) 

Because Shopify signs webhooks with a single per-app secret (`Context.api_secret_key`) shared across every shop that installs the app, an unprivileged attacker who legitimately installs the app on their own store can trigger a webhook and capture a valid `(raw_body, hmac)` pair. Since `shop-domain` and `topic` headers are not part of the signed content, the attacker can replay the exact same body/HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` (and/or a different `topic`). `Utils::HmacValidator.validate` will still return `true` because the body is unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 

The equality the gem is supposed to enforce is: `shop cryptographically authenticated by Shopify's HMAC == shop the handler acts on`. In this implementation that equality does not hold — the HMAC authenticates only the byte content of the body, not the tenant (`shop`) or event (`topic`) metadata that the handler trusts to decide what data belongs to which merchant.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), one of the qualifying Critical impacts. A host application that persists or acts on `WebhookMetadata#shop`/`#topic` (as the gem's own documentation and `Registry.process` API imply is safe once `HmacValidator.validate` passes) can be tricked into applying data intended for the attacker's shop to a victim shop's records, or into processing a forged event type for a shop that never sent it — entirely without needing the app's `client_secret`, an access token, or any privileged access. Any internet user who can install the public app (a completely unprivileged action) can mount this attack against any other installed shop.

### Likelihood Explanation
High. No secrets are required beyond ordinary app installation, which is available to any unprivileged internet user for public apps. Capturing a legitimate `(body, hmac)` pair from one's own store and replaying it with forged `shop-domain`/`topic` headers requires only basic HTTP tooling.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers in the HMAC-signed content (or otherwise cryptographically bind them), so `Utils::HmacValidator.validate` fails if any of these values are altered relative to what Shopify actually signed. At minimum, `to_signable_string` should incorporate the headers that `Registry.process`/`WebhookMetadata` treat as trusted identity fields.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker-shop.myshopify.com"
# and receives a legitimate webhook, capturing:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac_b64 = "..." # captured from the real Shopify-sent header x-shopify-hmac-sha256

# Attacker replays the exact same body + hmac, but swaps identity headers:
forged_headers = {
  "x-shopify-topic" => "customers/data_request",      # topic not covered by HMAC
  "x-shopify-hmac-sha256" => valid_hmac_b64,           # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # shop not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/signature match),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com" and
#    topic: "customers/data_request", neither of which Shopify actually signed.
```
