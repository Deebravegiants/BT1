## Analysis: Optimism Fault Dispute Game finality bypass in Hyperbridge's `op-verifier`

The external report is about `FaultDisputeGame.sol` — a well-funded challenger can grief an honest root-claim defender out of bond funds by opening many parallel countering sub-games, eventually winning a subgame by timeout even though the honest root claim was correct. That is an OP Stack contract issue Coinbase acknowledged but has not fixed.

Hyperbridge doesn't deploy `FaultDisputeGame.sol`, but it **consumes** it as a trust anchor for its Optimism (Base/OP-stack) consensus client, which reads Ethereum L1 state to authenticate L2 state roots that get admitted onto Hyperbridge and propagated to every connected chain.

### Root cause
`verify_not_challenged` in the `op-verifier` — used both on-chain by the `ismp-optimism` consensus client and off-chain by the `op-host` tesseract relayer that assembles the proof — accepts a `FaultDisputeGame` as valid proof of an L2 output root purely by checking that `claimData.length == 1` (i.e., nobody has called `move()` yet): [1](#0-0) 

This check never inspects the game's `status` field (`DEFENDER_WINS`/`CHALLENGER_WINS`/`IN_PROGRESS`), never checks `resolvedAt`, and never waits for the game's clock/challenge period (`maxClockDuration`) to elapse: [2](#0-1) 

The tesseract-side proof assembly (`op-host`) mirrors this exact "unchallenged" test with `game_is_challenged`, again only comparing `claimData.length` to `1`, with no resolution/time check: [3](#0-2) 

### Why the report's bug class applies here
The report shows that an honest challenger/defender's ability to keep a `FaultDisputeGame` in the "properly disputed" state depends on having enough bond funds to counter every attack the adversary throws at intermediate depths of the game tree. Hyperbridge's finality condition for admitting an L2 state root is even weaker than "the game resolved correctly" — it only requires the game to *currently* show no counter-move at all (`claimData.length == 1`). A well-resourced attacker acting as a malicious L2 proposer can:

1. Post `DisputeGameCreated` with a false `rootClaim`.
2. Use superior capital (the same capital asymmetry the report describes) to grief any honest challenger who attempts to counter — either by exhausting the honest challenger's bond via parallel sub-game claims before their first `move()` lands, or simply by front-running/outlasting them during the same block/short window the relayer polls.
3. As long as the game shows `claimData.length == 1` at the moment `op-host`/`ismp-optimism` builds and submits the proof, Hyperbridge accepts the (false) state root as final — regardless of the 7-day OP Stack dispute window, regardless of `status`, and regardless of whether the game will eventually resolve `CHALLENGER_WINS`.

This lets a capital-advantaged attacker force Hyperbridge to accept an unsound/forged L2 state commitment, which then flows into cross-chain message verification (state/non-membership proofs, token bridge mint/burn, ISMP request delivery) for every chain that trusts Hyperbridge's view of that Optimism/Base state machine.

### Title
Hyperbridge's Optimism dispute-game consensus client treats a merely-unchallenged `FaultDisputeGame` as final, letting a better-funded attacker force acceptance of a forged L2 state root - (File: `modules/ismp/clients/optimism/src/lib.rs`)

### Summary
`verify_not_challenged` (and its off-chain mirror `game_is_challenged`) authenticates an Optimism/Base L2 output root solely by checking `claimData.length == 1` on the `FaultDisputeGame` proxy. It never checks the game's `status`/`resolvedAt`, nor whether the dispute clock has run out. Because countering a false claim depends on an honest challenger having enough bond funds to survive griefing at every level of the game tree (the exact vulnerability class the OP Stack fault-dispute-game report describes), a capital-advantaged attacker can suppress/outlast honest counters long enough for the game to still read as "unchallenged" when Hyperbridge's relayer builds its proof, causing Hyperbridge to accept a forged state root well before (or without) the game legitimately resolving in the proposer's favor.

### Finding Description
`op-verifier::verify_not_challenged` for `DisputeGameImpl::FaultDisputeGame` reads only the dynamic-array length of `claimData` at a fixed storage slot and treats length `1` as proof of finality: [1](#0-0) 
This is the sole "not challenged" gate consulted by `verify_optimism_dispute_game_proof` before minting an `IntermediateState` for the destination state machine: [4](#0-3) 
The relayer-side (`op-host`) proof-building path applies the identical logic to decide which dispute games are eligible for propagation: [3](#0-2) 
None of these paths verify `FaultDisputeGame.status()`, `resolvedAt`, or that the OP Stack `maxClockDuration`/air-gap period has elapsed — which is what the OP Stack protocol relies on to guarantee that a `claimData.length == 1` game is actually free of a live, pending challenge rather than one whose honest challenger has been priced out of countering (the exact capital-asymmetry mechanism in the external report).

### Impact Explanation
If a malicious (or compromised) OP Stack proposer submits a false root claim and can outlast/out-spend any honest challenger attempting to counter it — the same economic attack the report describes — Hyperbridge's consensus client will accept that false state commitment as authoritative for the Optimism/Base state machine. Every downstream consumer of that state (ISMP state/non-membership proofs, token bridge mint/burn, intents settlement, cross-chain message delivery) inherits the forged state, enabling unbacked mint, forged message delivery, or theft of escrowed funds routed through Hyperbridge for that state machine.

### Likelihood Explanation
This requires an attacker to control (or collude with) a proposer and to out-capitalize honest challengers during the narrow window before Hyperbridge's relayer captures the "unchallenged" proof — a non-trivial but bounded capital cost, exactly as characterized by Coinbase's own "Acknowledged, will fix later" response to the underlying `FaultDisputeGame.sol` issue. The likelihood is elevated by the fact that Hyperbridge's check is strictly weaker than the OP Stack's own intended security model (which expects the full dispute window and resolution status to matter, not merely momentary non-challengedness).

### Recommendation
Require `FaultDisputeGame.status() == DEFENDER_WINS` (or equivalent resolved state) and that the game's `resolvedAt`/clock has fully elapsed the configured `maxClockDuration`/air-gap, in addition to (or instead of) the `claimData.length == 1` heuristic, before treating an Optimism/Base dispute game's root claim as final in both `verify_not_challenged` and `game_is_challenged`.

/// Whether the game's "not challenged" storage slot, read as a 32-byte big-endian word,
/// indicates the game has been challenged. `OPSuccinct` games have no challenge mechanism and
/// are never challenged. For the other two kinds the check follows the verifier's on-chain
/// contract layouts exactly so filtered games are precisely those that `verify_not_challenged`
/// would reject.
pub fn game_is_challenged(kind: &DisputeGameImpl, slot_value: alloy::primitives::U256) -> bool {
	match kind {
		DisputeGameImpl::OPSuccinct => false,
		DisputeGameImpl::FaultDisputeGame => {
			// `claimData` is a dynamic array; its slot stores the element count. An unchallenged
			// game holds exactly the root claim (length 1); every `move()` appends an entry. So
			// the game is challenged iff `claimData.length != 1`.
			slot_value != alloy::primitives::U256::from(1)
		},
		// `counteredByIntermediateRootIndexPlusOne == 0` iff unchallenged.
		DisputeGameImpl::AggregateVerifier => !slot_value.is_zero(),
	}
}
