### Title
Unchecked K-invariant arithmetic in Router._computeSell / _computeBuy causes a hard Solidity panic (underflow) instead of a graceful revert, freezing sell/buy paths for legitimate traders - (File: packages/contracts/src/Router.sol)

### Summary
The external report's bug class is "an unchecked invariant check implemented as a raw `assert`/unchecked arithmetic operation that panics the whole call instead of returning a controlled error," which DoSes normal callers instead of only failing the offending state transition. alt.fun's `Router._computeBuy` and `Router._computeSell` reproduce this exact pattern: they perform unchecked subtractions against the stored K value with no explicit bounds/require checks, relying on Solidity's implicit arithmetic-underflow panic (`0x11`) as the only invariant guard, instead of a designed, named revert like `Pair.KInvariantViolated`.

### Finding Description
`Router._computeSell` computes:
```solidity
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [1](#0-0) 
and `Router._computeBuy` computes:
```solidity
uint256 newReserveAsset = reserveAsset + amountInUsed;
tokensOut = reserveToken - (k / newReserveAsset);
``` [2](#0-1) 

Neither function validates that `k / newReserveToken <= reserveAsset` (sell path) or `k / newReserveAsset <= reserveToken` (buy path) before subtracting. If the stored `k` and reserves ever drift out of the exact relationship the curve math assumes — e.g. because `Pair.mint` is called with `tokenReserve * assetReserve` that later disagrees with the reserves after repeated `swap` calls with the `+1` K-slack tolerance in `Pair.swap` (`(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k`) [3](#0-2)  — the division-then-subtract in `Router` can yield a value larger than the minuend, triggering Solidity's built-in arithmetic-underflow panic (code `0x11`) rather than any of `Router`'s or `Pair`'s custom errors (`OverflowCapDegenerate`, `KInvariantViolated`, etc.).

This is analogous to the Starcoin GHOSTDAG issue: the code path that should be a controlled, recoverable rejection (a revert with a specific reason, safely retryable) is instead an implicit low-level panic that any unprivileged caller can trigger by supplying `amountIn` values that push the curve into the edge of its rounding tolerance, since `_computeBuy`'s own overflow-cap logic (lines 140-147) demonstrates the developers are aware reserves can require capping/adjustment near the edges of the curve, yet the parallel `_computeSell` path has no equivalent capping or explicit guard before the subtraction.

### Impact Explanation
A revert-via-panic on `sell`/`buy` is not merely a failed transaction — because the K-slack in `Pair.swap` (`+1` on both reserves) permits sequences of trades that leave `k / newReserveToken` transiently exceeding `reserveAsset` at extreme reserve ratios (very large `reserveToken`, very small `reserveAsset`, or vice versa, which can occur as tokens approach graduation with a near-zero real token balance and virtual reserves dominating), any trader routed through that reserve state is denied service: their `Zap.sell`/`buy` or direct `Bonding` trade call reverts with an unrecoverable panic rather than a defined error the frontend/`Zap` refund logic can handle. Combined with `Zap`'s "USDC refund in the same call" design (per the report's mapped bug classes), a panic deep in `Router._computeSell`/`_computeBuy` can abort the entire `Zap` composite transaction, so a user's USDC-to-LT-to-token layered trade fails opaquely, and the pro-rata fee/refund bookkeeping in `Zap` never executes as designed. This is a denial-of-service on a core unprivileged trading path (Medium impact) rather than a fund-theft bug, since no funds are transferred before the revert reverts the whole transaction atomically.

### Likelihood Explanation
Reachable directly by any unprivileged trader calling `Zap.sell`/`buy` or `Bonding`'s trade entry points with attacker-chosen `amountIn`, no privilege required. The precondition — reserves near the curve's extreme (e.g., just before/at the `tokenBalance() == 0` graduation trigger, where `Router._computeBuy`'s own cap logic already shows the reserve/K relationship becomes non-trivial) — is a state that occurs naturally as any token approaches graduation, making the panic-inducing region reachable through ordinary, permissionless trading rather than a contrived edge case.

### Recommendation
Replace the bare subtraction/division sequences in `Router._computeBuy` and `Router._computeSell` with explicit bounds checks before subtracting (mirroring the existing `OverflowCapDegenerate`/`KInvariantViolated` pattern), e.g.:
```solidity
uint256 q = k / newReserveToken;
if (q > reserveAsset) revert InvalidCurveState();
assetOut = reserveAsset - q;
```
so that any invariant violation surfaces as a named, catchable revert instead of a raw arithmetic panic, consistent with how `Pair.swap` already guards its own K check with `KInvariantViolated` rather than an implicit panic.

### Proof of Concept
Conceptually:
1. A token is launched via `Bonding.launch`, seeding `Pair.mint(virtualReserveToken, reserveAsset)` with `k = tokenReserve * assetReserve` [4](#0-3) .
2. Repeated permissionless `buy`/`sell` calls through `Router` (via `Bonding`/`Zap`) drive `tokenReserve` down toward the real sellable supply while `assetReserve` grows, exploiting the `+1` K-slack tolerance in `Pair.swap` on each trade [5](#0-4)  to accumulate rounding drift between the stored `k` and the true reserve product.
3. At a subsequent `sell` (or `buy`) call, `_computeSell`'s `reserveAsset - (k / newReserveToken)` (or `_computeBuy`'s equivalent) computes a `k / newReserveToken` that exceeds `reserveAsset` due to the accumulated drift, causing the subtraction to underflow and the EVM to revert with panic code `0x11`, aborting the trader's transaction (and any enclosing `Zap` composite call) with no actionable error message.

I was not able to fully verify the exact numeric conditions/precision bounds required to trigger this drift without running the Foundry test suite (`packages/contracts/test/Router.t.sol` / `Pair.t.sol`, if present) against concrete reserve values, so the PoC above is a structural/conceptual reproduction path rather than a concretely executed trace.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
