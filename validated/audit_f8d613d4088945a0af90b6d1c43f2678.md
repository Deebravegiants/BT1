### Title
Domain-Unseparated Off-Chain Signature Scheme in `pallet-hyper-fungible-token` Allows Cross-Chain/Cross-Deployment Replay to Dispatch Arbitrary Runtime Calls - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The Snipe-IT advisory (CVE-2024-48987) is rooted in a bespoke serialization/authentication scheme (PHP cookie serialization keyed by `APP_KEY`) that lacks context binding, so a forged/replayed serialized payload is accepted as authentic and drives remote code execution. `pallet-hyper-fungible-token`'s `on_accept` implements an analogous bespoke, insufficiently domain-separated authentication mechanism: it accepts a `SubstrateCalldata{ signature, runtime_call }` blob carried inside cross-chain message `data`, verifies a signature over `(account_nonce, runtime_call).encode()`, and then dispatches `runtime_call` with `RawOrigin::Signed(beneficiary)` — full privileged authority as that account — with no binding to the chain, the specific bridge route, the source contract, or the message itself.

### Finding Description
In `on_accept` [1](#0-0) , once tokens are minted/transferred to `beneficiary`, an optional `SubstrateCalldata` is decoded from the cross-chain message body and, if it carries a `signature`, that signature is checked against a payload consisting only of `(nonce, runtime_call)`: [2](#0-1) 

The recovered/verified key must equal `beneficiary`, after which the pallet dispatches the attacker-decoded `runtime_call` as `RawOrigin::Signed(beneficiary)`: [3](#0-2) 

The signed payload `(nonce, runtime_call)` is *not* bound to:
- the genesis hash / chain identity of the destination runtime,
- the `source` state machine, source contract, or asset being bridged,
- the specific `PostRequest`/commitment that carried the calldata,
- a spec version or any other replay-protection domain tag that standard Substrate `SignedExtension`s (`CheckGenesis`, `CheckSpecVersion`, `CheckEra`) normally provide.

The only replay protection is the destination account's on-chain nonce, which is public, low-entropy, monotonic, and identical in format on every deployment of this pallet. Any user's Ed25519/Sr25519/ECDSA public key (i.e., `AccountId32`/`H160`) is the same cryptographic object across every Substrate/EVM chain that shares the same key derivation, so a signature a user produces for `(nonce=N, call_bytes)` intended for one hyper-fungible-token deployment (one parachain, one source chain route) is valid for **any** other deployment of this pallet where that same account currently has nonce `N` — which is trivially true for any account that has never transacted on that other chain (nonce 0), or can be made true by an attacker driving the account to a matching nonce. Because the check never verifies `source`, `dest`, or the request commitment, a relayer or any party who can observe (or induce) such a signature can replay it through a different bridge route/asset/chain to force dispatch of the same `runtime_call` (or any call the attacker separately convinces the user to sign under this generic, unqualified scheme) with the beneficiary's full authority.

This mirrors the CVE-2024-48987 bug class precisely: a custom serialization/signature format with no context/domain binding is treated as sufficient proof of authorization, so knowledge/reuse of a validly produced artifact (there: a cookie forged with a known `APP_KEY`; here: a signature over an under-specified message) lets an attacker drive privileged execution (arbitrary `RuntimeCall::dispatch`) as the victim.

### Impact Explanation
Successful exploitation lets an attacker cause `pallet-hyper-fungible-token` to dispatch an arbitrary `RuntimeCall` (subject only to the runtime's generic `BaseCallFilter`) as `RawOrigin::Signed(beneficiary)` — i.e., full account authority, including balance transfers, asset transfers, staking/governance actions, or any other dispatchable the runtime does not explicitly filter. This is a concrete "unauthorized app action" / theft-of-funds vector reachable from a single relayed cross-chain message, matching the required impact bar (unauthorized app action, potential theft of funds).

### Likelihood Explanation
Exploitation requires the attacker to obtain a signature the victim produced for this scheme once (e.g., by social-engineering a "harmless" cross-chain calldata authorization, or because the same pallet is deployed identically on a testnet/sibling network where the nonce coincidentally matches) and then relay it through an unauthenticated `data` field of a `PostRequest` that this permissionless `IsmpModule::on_accept` will process for any inbound message from a registered `source`/`from` contract pairing. No privileged relayer or governance role is needed — anyone who can get a valid ISMP-verified message delivered (the normal relayer path) can trigger `on_accept` with attacker-chosen `data`, so likelihood is high once a usable signature exists.

### Recommendation
Bind the signed payload to a full authorization context before dispatch: include the genesis hash (or a chain/pallet-specific domain separator), the `source` state machine and `from` contract address, the `dest` and message commitment/nonce (ISMP request nonce), and the encoded `runtime_call`, e.g. `(GENESIS_HASH, PALLET_DOMAIN, source, from, request_nonce, account_nonce, runtime_call).encode()`. Additionally consider binding to the specific `PostRequest` commitment hash so a signature can only ever authorize the exact message it was created for, eliminating any possibility of cross-chain or cross-route replay independent of the account nonce.

### Proof of Concept
1. Victim signs `(nonce=0, runtime_call=Balances::transfer_allow_death{ dest: victim_controlled, value: X }).encode()` with their Sr25519 key, believing it authorizes a specific bridging action on Chain A (as shown by the pallet's own test at [4](#0-3) ).
2. An attacker (or malicious relayer) observes this signature (e.g. leaked from a UI, mempool, or a second bridge deployment) and repackages it as `SubstrateCalldata{ signature: Some(multisignature), runtime_call }` inside a fresh `Message.data` for a `PostRequest` targeting Chain B's identically-configured `pallet-hyper-fungible-token`, where the victim's account also currently has `nonce == 0`.
3. Chain B's relayer delivers the ISMP message; `on_accept` decodes `SubstrateCalldata`, verifies the signature succeeds (identical `beneficiary`, identical `nonce`, identical `runtime_call` bytes — nothing about the payload differs across chains), and dispatches the call with `RawOrigin::Signed(beneficiary)` per [5](#0-4) , executing a call the victim never authorized for Chain B.
