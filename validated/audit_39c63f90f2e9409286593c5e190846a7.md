### Title
Missing role check on `GET /v2/external_initiators` exposes all External Initiator `AccessKey`/`OutgoingToken` credentials to any authenticated view-only user - (File: core/web/router.go)

### Summary
The GitLab advisory (CVE-2021-22206) describes pull-mirror credentials being readable in plaintext by lower-privileged maintainers due to missing access restriction on credential-bearing endpoints. Chainlink has a directly analogous unprivileged-actor bug: the `GET /v2/external_initiators` route returns every External Initiator's `AccessKey` and `OutgoingToken` to *any* authenticated user, including users with only the `view` role, while the sibling create/delete routes for the same resource correctly require `RequiresEditRole`.

### Finding Description
In `v2Routes`, the External Initiator collection endpoint is registered without any role guard, unlike its siblings: [1](#0-0) 

```go
eia := ExternalInitiatorsController{app}
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))
```

`eic.App.BridgeORM().ExternalInitiators` fetches *all* initiator rows and `Index` serializes them via `NewExternalInitiatorResource`, which includes the `AccessKey` and `OutgoingToken` fields: [2](#0-1) [3](#0-2) 

The project's own RBAC contract test confirms the endpoint is reachable by `viewOnlyAllowed` accounts, while `POST`/`DELETE` on the same resource require edit/admin privileges: [4](#0-3) 

`AccessKey` is the identifier used to authenticate inbound "Run"-role requests via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, and `OutgoingToken` is one of the two secrets (`OutgoingSecret`, `OutgoingToken`) the node uses to authenticate itself when POSTing job results back to the external initiator's endpoint. Any node user with the lowest privilege level (`view`) can pull the full list of `AccessKey`/`OutgoingToken` values for every configured External Initiator, information that is otherwise meant to be scoped to users with edit/admin privileges (since only they can create/rotate/destroy these credentials).

### Impact Explanation
An attacker or low-privileged internal user who only has a `view` role API key/session can enumerate all External Initiators configured on the node and harvest their `AccessKey` and `OutgoingToken` values. This is a cross-role credential/secret disclosure: it does not itself grant full inbound-auth bypass (the `Secret` used for `AuthenticateExternalInitiator` is hashed and not part of this response), but it discloses `OutgoingToken`, which is one of the two outbound secrets used by the node to authenticate itself to third-party endpoints, and it discloses `AccessKey`, halving the entropy needed to brute-force/guess inbound auth alongside the (separately obtainable) `Secret`. This mirrors the GitLab issue's core problem: sensitive per-integration credentials are readable by users who should not have that level of access, breaking the intended privilege boundary between `view` and `edit`/`admin` roles.

### Likelihood Explanation
High reachability: this is a standard authenticated HTTP GET with no special preconditions beyond having any valid low-privilege API/session credential (`view` role, the lowest tier), which is explicitly permitted per the RBAC test table. No race conditions, no external-initiator-specific header knowledge, and no elevated role is required.

### Recommendation
Wrap the `GET /v2/external_initiators` route with a minimum role check (e.g., `auth.RequiresEditRole` or a new "view credentials" gate) consistent with the `POST`/`DELETE` handlers for the same resource, or strip `AccessKey`/`OutgoingToken` from the `Index` response for non-edit/admin roles, returning only non-sensitive fields (`Name`, `URL`, timestamps) to `view`-role callers.

### Proof of Concept
1. Create a user with the `view` role (lowest privilege) and obtain a session/API token for them.
2. As an `edit`/`admin` user, create an External Initiator: `POST /v2/external_initiators {"name":"foo","url":"http://x"}` — note the returned `AccessKey`/`OutgoingToken`.
3. Authenticate as the `view`-role user and call `GET /v2/external_initiators`.
4. Observe the response includes the same `accessKey` and `outgoingToken` values for the initiator created in step 2, despite the caller lacking edit/admin privileges — confirmed by the existing test `TestExternalInitiatorsController_Index` asserting these fields are present in the response body and by the RBAC matrix in `auth_test.go` marking this route `viewOnlyAllowed: true`. func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
```go
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
type ExternalInitiatorResource struct {
	JAID
	Name          string         `json:"name"`
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`
}

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
```
