### Title
Webhook topic and shop headers are unauthenticated (HMAC covers only raw body) enabling topic/tenant confusion - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`HmacValidator.validate` only verifies the integrity of the raw request body via `Request#to_signable_string`, which returns `@raw_body` and nothing else. `Request#topic` and `Request#shop` are read straight from HTTP headers that are never included in the signed payload, yet `Registry.process` packages them together with the validated body into `WebhookMetadata` as if they were equally trustworthy. An attacker who legitimately receives one valid `(raw_body, hmac)` pair (e.g. from their own development-shop installation) can replay it to the app's public webhook endpoint with forged `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers while the HMAC still validates.

### Finding Description
The binding the handler implicitly relies on is:
`topic/shape used by handler.handle(data) == topic cryptographically bound to data.body`

This is false in the gem:
- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Request#topic` and `Request#shop` are pulled from headers with no cryptographic tie to the body [2](#0-1) .
- `Registry.process` validates only the HMAC of the body, then unconditionally trusts `request.topic` and `request.shop` to select the handler and build `WebhookMetadata` [3](#0-2) .
- `HmacValidator.validate_signature` computes the signature only over `to_signable_string`, i.e. the body, using `Context.api_secret_key` (or `old_api_secret_key`) [4](#0-3) .

Since the app's `api_secret_key` is a single shared secret for the whole app (not per shop), any body Shopify signs for the attacker's own dev-store installation is signed with the same key used for every other merchant's webhooks. Attack flow:
1. Attacker installs the app on their own development shop and registers/receives a genuine webhook for some topic A, capturing `(raw_body, X-Shopify-Hmac-Sha256)`.
2. Attacker sends a direct HTTP POST to the app's public webhook-processing endpoint (the route documented in `docs/usage/webhooks.md`, lines 125-136) with the unmodified `raw_body`/`hmac`, but sets `X-Shopify-Topic: B` and `X-Shopify-Shop-Domain: <victim-shop>`.
3. `HmacValidator.validate` still passes because the body bytes are unchanged.
4. `Registry.process` dispatches to the handler registered for topic B, constructing `WebhookMetadata` with `topic: "B"`, `shop: "<victim-shop>"`, and `body` parsed from topic A's JSON shape.

No component in this repo (`ShopValidator`, `Context`, etc.) is invoked in this path to cross-check `shop` against a known/allow-listed value or to bind `topic`/`shop` to the signed bytes.

### Impact Explanation
A downstream handler that trusts `data.topic` to select a JSON schema, or trusts `data.shop` to select the tenant record to mutate/redact, can be made to act on attacker-chosen tenant identifiers and attacker-shaped data using a signature that was only ever meant to prove "some genuine Shopify payload, for the attacker's own shop, arrived intact." This is a cross-tenant confusion vector at the gem's trust boundary. Whether it becomes full cross-tenant data corruption/exfiltration depends on host-handler logic (schema/shop validation on the handler side), which is outside this gem, but the gem itself supplies zero binding between the validated bytes and the `topic`/`shop` fields it hands to every handler.

### Likelihood Explanation
Cost to the attacker is low: create a development shop, install the target app (this is explicitly an allowed attacker capability), capture one genuine webhook delivery, then replay it directly to the shared webhook endpoint with modified headers. No credentials or `api_secret_key` are needed. It is repeatable against any topic/shop string, limited only by which handlers are registered and whether those handlers perform additional validation of `data.shop`/`data.body` shape (many implementations, as shown in the gem's own docs example, do not: `docs/usage/webhooks.md` lines 20-29 simply consume `data.topic`/`data.shop`/`data.body` as trusted values).

### Recommendation
Bind `topic` and `shop` into the signed material, or otherwise let handlers cryptographically verify them: e.g., include topic/shop in the HMAC computation performed by this gem (would require Shopify to also sign that data, which it doesn't for the current header scheme), or, more practically, have `Registry.process` independently validate that the parsed `body`'s implied resource type matches the declared `topic`, and document/enforce that `shop` must be cross-checked against the set of shops the app knows have installed it (e.g. an active `Auth::Session`) before dispatch. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `topic` and `shop` in `WebhookMetadata` are not covered by the HMAC and must be independently revalidated by host handlers.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
def test_forged_topic_and_shop_headers_pass_hmac_with_replayed_body
  real_body = '{"id":111,"note":"legit order for attacker\'s own shop"}'
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)
  captured_hmac_header = Base64.encode64(hmac)

  handler_b_received = nil
  handler_b = TestHelpers::FakeWebhookHandler.new(lambda { |data| handler_b_received = data })
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/redact", delivery_method: :http, path: "path", handler: handler_b,
  )

  forged_headers = {
    "x-shopify-topic" => "customers/redact",       # forged: attacker's real webhook was for a different topic
    "x-shopify-hmac-sha256" => captured_hmac_header, # unchanged, body-only signature still valid
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged: not attacker's real shop
    "x-shopify-webhook-id" => "attacker-controlled-id",
    "x-shopify-api-version" => "2024-01",
  }

  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers),
  )

  # Equality check: topic/shop bound to the signed body?
  assert_equal("customers/redact", handler_b_received.topic)
  assert_equal("victim-shop.myshopify.com", handler_b_received.shop)
  assert_equal(111, handler_b_received.body["id"]) # order id from topic-A-shaped body misparsed as topic-B data
end
```
This demonstrates that `Registry.process` accepts a body signed under one context and dispatches it, unmodified, to an arbitrary registered topic with an arbitrary claimed shop, purely because `HmacValidator.validate` never checks `topic` or `shop` against the signature.
