Webhook `shop` domain is trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the `X-Shopify-Hmac-Sha256` header, but then hands the caller-supplied, unauthenticated `X-Shopify-Shop-Domain` header value to the handler as the tenant identifier. Since the app's `client_secret` (and therefore the HMAC key) is shared across every shop that installs the app, a valid HMAC only proves "Shopify produced this body for this app," not "this body belongs to this shop." An unprivileged attacker who installs the app on their own store can capture a genuine, validly-signed webhook and replay it with a forged `Shop-Domain` header pointing at a victim shop, and the gem will accept it as authentic for that victim shop.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop used to key/route the webhook data`

Concretely:
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  — the HMAC computed over this string never includes the `shop`, `topic`, or `webhook-id` headers.
- `Request#shop` is read directly and unauthenticatedly from the `x-shopify-shop-domain`/`shopify-shop-domain` header: [2](#0-1) .
- `HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the received signature: [3](#0-2) . Because `to_signable_string` is body-only for webhooks, this check passes for *any* header set as long as the body+secret produce the given signature — it says nothing about which shop the body came from.
- `Registry.process` uses this HMAC check as its sole authentication gate, then immediately forwards the unauthenticated `request.shop` to the handler: [4](#0-3) .

Because `client_secret` (the HMAC key) is identical for every merchant that installs a given app — it is not per-shop — a webhook body genuinely emitted by Shopify for shop A carries a signature that is equally "valid" for the same bytes claimed to be from shop B. The `shop` field is exactly the kind of "field acted on but not covered by the HMAC" that breaks the intended identity binding, analogous to the external report's unvalidated `prizeManager`/`chainSelector` inputs that let an unprivileged caller redirect the effect of an already-authenticated action.

### Impact Explanation
Any host application built on this gem that keys per-tenant state, session/access-token lookup, dedup, or data-redaction (`shop/redact`, `customers/redact`, `customers/data_request` are exactly the topics this gem special-cases: [5](#0-4) ) off of `WebhookMetadata#shop` is exposed to cross-tenant data confusion: an attacker who is a legitimate, unprivileged installer of the app on their own shop can make the gem hand their handler a self-crafted `(shop: victim, body: attacker's real webhook body)` pair that passes `HmacValidator.validate`. This crosses a tenant boundary using only a body/signature pair the attacker legitimately possesses for their own shop — no leaked secret, access token, or privileged account is required, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only: (1) the attacker installs the app on their own store (standard, unprivileged action for any public/embedded Shopify app), (2) the attacker receives a normal webhook for their own shop and captures its raw body + `X-Shopify-Hmac-Sha256` value, and (3) the attacker sends that same body/HMAC pair to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header. No cryptographic secret needs to be broken since the shop field was simply never bound into the signature.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) inside the signed material, or otherwise cross-check the header-provided `shop` against a value that is itself authenticated (e.g. validate that the shop is consistent with a subscription/registration record keyed by an authenticated identifier) before constructing `WebhookMetadata`. At minimum, document prominently that `request.shop` from `ShopifyAPI::Webhooks::Request` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier by host applications.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a real webhook, e.g. for "orders/create", with body B and a valid
# signature computed by Shopify using the shared api_secret_key:
raw_body = '{"id":1,"note":"hi"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the captured body+hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim.myshopify.com" # not part of signed bytes
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because shop is not part of to_signable_string
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))
```
