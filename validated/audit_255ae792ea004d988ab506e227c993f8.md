### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's `topic`, `shop`, `api_version`, and `webhook_id` from HTTP headers (`X-Shopify-*`), but its `to_signable_string` — the value the HMAC is actually computed over — is only the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity for the handler. This breaks the binding: `HMAC(secret, bytes_verified) == HMAC(secret, bytes_used_for_shop_identity)` does not hold, since the "shop" identity is parsed from bytes that were never part of what was verified.

### Finding Description
`Webhooks::Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Request` that method returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

But `shop` (the tenant identity handed to the app's handler) is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed bytes:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

The identity equality that should hold is:
`shop_bound_by_HMAC == shop_used_by_handler`

Here it is actually:
`shop_used_by_handler = header value (unauthenticated)` while `HMAC covers only raw_body (no header)`.

Because a single app has one `client_secret`/`api_secret_key` shared across *all* merchant installations, any valid `(raw_body, hmac)` pair legitimately produced for one shop's webhook delivery remains cryptographically valid when replayed to the same endpoint with a different `shopify-shop-domain` header. The gem's `HmacValidator.validate(request)` call will still return `true`, since it only recomputes the HMAC over `@raw_body` and never incorporates `shop`.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem, following the documented `Webhooks::Registry.process` flow, will invoke the shop-specific `WebhookHandler#handle` with a `shop` value that has no cryptographic binding to the payload that was actually verified. An unprivileged actor who is a merchant of the app (and therefore has visibility into a genuine `(raw_body, hmac)` pair delivered to the app for their own shop, e.g., via a proxy sitting in front of their own installation's webhook endpoint before the app's own webhook consumer) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header value. The receiving app, trusting `WebhookMetadata#shop` as authenticated per this gem's contract, will process attacker-controlled webhook content as if it originated from a victim shop — leading to cross-tenant data writes/state changes keyed by the forged `shop` value. This meets the High-severity bar for "cross-tenant access" via a scope/identity check that answers permissively.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one legitimately-signed `(raw_body, hmac)` pair, which any merchant who has installed the app can obtain from their own shop's webhook deliveries (e.g., by fronting the webhook endpoint with a logging proxy, or via Shopify's webhook delivery logs/replays in the Partner/Admin dashboard). No access to the app's `client_secret`, access tokens, or any privileged account is required — only participation as an ordinary merchant/tenant of the app, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind the trusted `shop` identity to the verified bytes instead of an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in `to_signable_string`, matching whatever canonicalization Shopify itself uses to compute the HMAC, so a header swap invalidates the signature; or
- If Shopify's HMAC for webhooks is documented to cover the header set already, verify that assumption explicitly in code (e.g., by cross-checking the header-derived `shop` against a shop already known/authorized for the app, or requiring that the caller correlate `request.shop` with an existing, previously-verified session before trusting it) rather than relying solely on `Utils::HmacValidator.validate(request)` returning `true`.
- At minimum, document prominently (and enforce in code, not just docs) that `WebhookMetadata#shop` must be cross-validated by the consuming app against known/installed shops before being used to key any tenant-specific state change.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimately delivered webhook: raw body `B` and its valid `hmac-sha256` header `H` (computed by Shopify using the app's single shared `api_secret_key`).
2. Attacker (or a compromised intermediary they control) resends a request to the app's webhook endpoint with:
   - Body: `B` (unchanged, so `HMAC` verification passes)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it was never bound to shop)
3. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes over `request.to_signable_string == B`. [4](#0-3) 
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop = "victim.myshopify.com"`, taken straight from the forged header. [3](#0-2) 
5. The app's `WebhookHandler#handle` executes attacker-controlled body content attributed to `victim.myshopify.com`, causing cross-tenant state corruption in any app that trusts this gem's webhook shop identity as authenticated.
