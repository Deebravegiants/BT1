### Title
Signup signature omits `distributorId`, allowing operator/distributor misattribution of signups - (File: `src/plans/enroll_user.rs`, `src/backend/signup_post.rs`)

### Summary
The Solana report describes a scheme where a cryptographic signature covers only some fields (`user`/`mint`/`amount`/nonce) while a security-critical field (the destination token account) is left unsigned and unvalidated, letting an attacker redirect funds to themselves by substituting that field after the signature was produced. The same structural flaw exists in orb-core's signup flow: the iris-code signature computed by the secure element binds `ORB_ID`, the user's `user_id`, and the iris pipeline data, but it never binds `operator_qr_code.user_id` (`distributorId`) — a field that is nonetheless sent to the backend in the same signup request and used to attribute the signup to a specific operator/distributor.

### Finding Description
`make_signature` in `src/plans/enroll_user.rs` builds the signed payload from `ORB_ID`, `user_qr_code.user_id`, and the iris pipeline version/code/mask fields only: [1](#0-0) 

The resulting signature is then submitted via `signup_post::request`, alongside `distributorId` (derived from `operator_qr_code.user_id`) and `userId`, but `distributorId` is never part of the signed digest: [2](#0-1) 

This mirrors the Solana finding exactly: the signature is meant to attest that a specific biometric enrollment happened for a specific `userId` on a specific orb, but a materially significant field — which operator/distributor gets credit/attribution for the signup — is transmitted outside the cryptographic commitment. Anything downstream that trusts the presence of a valid signature as proof that *all* fields in the signup request are authentic (including `distributorId`) is misled: the signature will still validate on the backend even if `distributorId` differs from what was scanned/intended, because it was never covered by the signed bytes.

### Impact Explanation
If `distributorId` is used by the backend for operator crediting, referral rewards, or fraud/liveness accounting tied to a specific operator, a party able to influence the value transmitted for `distributorId` between signing and network submission (e.g., a compromised/rogue operator app, a modified request en route, or a malicious operator terminal reusing this client) can misattribute a genuine, signature-valid signup to an arbitrary distributor/operator identity — without needing to forge or break the iris-code signature. This is a misattributed-signup class of impact: the backend cannot distinguish "the legitimate distributor for this signup" from "any distributor ID an attacker chooses" purely from the presence of a valid signature, since the signature says nothing about `distributorId`.

### Likelihood Explanation
Likelihood depends on whether any component between "signature computed" and "request sent" is attacker-influenced (e.g. a modified/rebuilt client binary, a compromised or malicious operator app instance, or interception of the multipart form prior to TLS). Within the same trusted orb-core process this is not exploitable by an external unprivileged party without additional access, so likelihood is lower than the original Solana bug (where anyone holding a valid signature could freely pick the destination account on-chain). It is best characterized as a design gap rather than a directly remotely-exploitable bug from the outside, but it is a genuine violation of the "signature should bind all security-relevant fields" invariant that the C-01 report calls out.

### Recommendation
Include `distributorId` (and `signup_id`/`reason` if they carry any attribution or payout significance) inside the signed digest computed in `make_signature`, so that the backend can verify the operator/distributor attribution is exactly what was cryptographically attested by the secure element, not merely what was appended to the outgoing multipart form:

```rust
fn make_signature(
    user_qr_code: &qr_scan::user::Data,
    operator_qr_code: &qr_scan::user::Data,
    pipeline: &Pipeline,
) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(operator_qr_code.user_id.as_bytes()); // bind distributorId
    // ... existing pipeline fields ...
}
```
And have the backend re-derive/verify `distributorId` from the signed payload rather than trusting the unsigned form field.

### Proof of Concept
1. Orb performs a legitimate enrollment: secure element signs `ORB_ID || user_id || iris pipeline data` via `secure_element::sign` in `make_signature` (`src/plans/enroll_user.rs:290-304`).
2. `signup_post::request` builds the multipart form independently, adding `distributorId` from `operator_qr_code.user_id` (`src/backend/signup_post.rs:125-133`) — a value the signature never covers.
3. Any actor able to alter the `distributorId` field between step 1 and the actual HTTP submission (e.g., a modified client build, a compromised operator terminal, or interception of the outgoing multipart body) can submit a different `distributorId` while keeping the original valid `signature` and `userId`/iris data.
4. The backend, verifying only that `signature` matches `orbId + userId + iris data`, has no way to detect the substitution of `distributorId`, resulting in a signup credited to an operator/distributor who did not perform it.

Note: I could not fully trace the backend-side verification logic (outside this repo) that consumes `distributorId`/`signature`, so the precise downstream monetary/reward impact could not be confirmed from orb-core alone; this assessment is limited to what is provable from the client-side signing and request-construction code shown above.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
