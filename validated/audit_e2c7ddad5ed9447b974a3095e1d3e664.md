### Title
Literal-prefixed capability string comparison in `ValidateSecurityContext` is bypassed by the standard, non-prefixed capability spelling - (File: pkg/apis/core/validation/validation.go)

### Summary
`ValidateSecurityContext` contains a check that appears to compare `sc.Capabilities.Add` entries against the literal string `"CAP_SYS_ADMIN"` when `AllowPrivilegeEscalation` is `false`. Kubernetes' `v1.Capability` API convention is to specify capability names *without* the `CAP_` prefix (e.g. `"SYS_ADMIN"`, `"NET_ADMIN"`), so any normal, spec-conformant pod submission using the bare form `SYS_ADMIN` would never match this literal check, rendering the intended invariant ineffective for essentially all real-world submissions, not just a deliberately crafted bypass.

### Finding Description
An unprivileged user with pod-create permission in a namespace can submit a `PodSpec` with `securityContext.allowPrivilegeEscalation: false` and `securityContext.capabilities.add: ["SYS_ADMIN"]`. Because the Kubernetes Capability field convention omits the `CAP_` prefix (this is how `PodSecurity` admission's own restricted-level check `capabilitiesRestricted_1_22` and all documented examples specify capabilities), the string comparison against the literal `"CAP_SYS_ADMIN"` never triggers for standard usage. The check would only reject a pod that spelled the capability as `CAP_SYS_ADMIN`, which is not the conventional or expected input format, meaning the guard is effectively dead code against real-world requests. This is compounded by the fact that PodSecurity's baseline level does not restrict capabilities at all (only `restricted` enforces `ALL`/`NET_BIND_SERVICE`-only), so in a baseline-enforced namespace this core-API-level check is the only remaining gate preventing `AllowPrivilegeEscalation=false` + `SYS_ADMIN` combination from being admitted.

### Impact Explanation
A pod is admitted into a baseline namespace with a SYS_ADMIN-equivalent capability granted alongside `AllowPrivilegeEscalation=false`, violating the documented invariant that this combination should be rejected. Depending on the container runtime's capability handling and the declared `AllowPrivilegeEscalation=false` semantics, this could allow a workload to retain a highly privileged capability (`SYS_ADMIN` is broadly considered container-breakout-capable) that operators believed was blocked by validation, weakening workload isolation guarantees relied upon by baseline-tier tenants.

### Likelihood Explanation
This requires only namespace-scoped pod-create RBAC in a `baseline`-labeled (or unlabeled/PodSecurity-not-enforced) namespace — no elevated privileges. Because the bypass uses the *standard* Capability spelling convention (no `CAP_` prefix), it is trivially and repeatably reachable by any normal pod-creation workflow, not a crafted edge case.

### Recommendation
Normalize the capability string before comparison (strip or add the `CAP_` prefix consistently, e.g. using `strings.TrimPrefix(string(cap), "CAP_")` or comparing against both forms), matching how `capabilitiesRestricted_1_22` and other PodSecurity capability checks normalize input. Add fuzz/table tests covering prefixed and unprefixed spellings for all sensitive capability names checked in `ValidateSecurityContext`.

### Proof of Concept
Unit test in `pkg/apis/core/validation/validation_test.go` targeting `ValidateSecurityContext`:
1. Construct a `SecurityContext` with `AllowPrivilegeEscalation: pointer.Bool(false)` and `Capabilities: &Capabilities{Add: []Capability{"SYS_ADMIN"}}`.
2. Call `ValidateSecurityContext(sc, fieldPath, ...)`.
3. Assert `len(errs) == 0` — demonstrating the invariant is not enforced for the conventional (unprefixed) capability spelling.
4. Repeat with `Add: []Capability{"CAP_SYS_ADMIN"}` and assert an error IS returned, confirming the check only matches the non-conventional literal form.
