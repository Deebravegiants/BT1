Audit Report

## Title
Unauthenticated MessageID collision in Gateway Web API handler causes cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` stores the caller's response callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageID`, overwriting any existing entry unconditionally. Since `MessageID` is fully attacker-controlled and only length/character-validated (not checked for uniqueness or bound to the caller's identity), a second client reusing an in-flight `MessageID` can silently replace the first caller's stored callback, causing the eventual DON node response to be delivered to the wrong client.

## Finding Description
The externally-reachable `ProcessRequest` entry point in `core/services/gateway/gateway.go` routes legacy DON-ID requests directly to `h.HandleLegacyUserMessage(ctx, msg, callback)` after only calling `msg.Validate()`, which checks signature length and `MessageID` length/character constraints but not uniqueness. [1](#0-0)  `HandleLegacyUserMessage` then performs an unconditional map write: `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}`, with no existence check. [3](#0-2) 

When a node later responds, `HandleNodeMessage` only verifies that `msg.Body.Sender == nodeAddr` — i.e., that the responding node isn't spoofed — not that the `MessageID` still belongs to the original requester. [4](#0-3)  The response is dispatched purely by `MessageID` lookup in `handleWebAPITriggerMessage`, delivering the node's response to whichever callback is currently stored for that ID. [5](#0-4) 

This is inconsistent with sibling implementations in the same codebase (`requestcache.go`'s `NewRequest`, keyed by `(Sender, MessageID)` with an existence check, and `http_trigger_handler.go`'s `setupCallback`, which rejects duplicate in-flight request IDs), both of which explicitly guard against this exact class of bug. The `MessageID`'s own validation in `api/message.go`'s `Message.Validate()` only checks length and null-byte suffix — no uniqueness or sender-binding constraint exists there either.

## Impact Explanation
This maps to the in-scope "cross-user response corruption" impact class. An unprivileged external client can cause another concurrent caller's node response (an HTTP trigger response payload, potentially containing sensitive data returned from an external endpoint) to be misdelivered to itself, while the legitimate caller experiences a request timeout. This is a genuine trust-boundary violation reachable via a single HTTP POST to the gateway's public user-facing port, requiring no special credentials beyond being a normal external caller.

## Likelihood Explanation
Exploitability requires the attacker to predict or intentionally reuse a `MessageID` value belonging to another party's concurrently in-flight (within the ~120-second default `CallbackMaxAgeSec` window) request. Since `MessageID` is entirely client-chosen, an attacker controlling or observing a client application's ID generation scheme (or targeting a victim using a predictable/sequential/short/reused ID scheme) can trigger the race deterministically and repeatably. Given that two other handlers in the same package already implement the fix (dedup/reject-on-collision), the absence of this check in the legacy path is a genuine oversight rather than a documented design trade-off.

## Recommendation
Add an existence check in `HandleLegacyUserMessage` before writing to `h.savedCallbacks`, rejecting the request if `msg.Body.MessageID` is already in-flight, mirroring `requestcache.go`'s `NewRequest` and `http_trigger_handler.go`'s `setupCallback`. Consider keying `savedCallbacks` by `(Sender, MessageID)` rather than `MessageID` alone to eliminate cross-client collisions entirely.

## Proof of Concept
1. Attacker sends a legacy Web API trigger JSON-RPC request to the gateway's user HTTP port with `Body.DonID` set and `Body.MessageID = "X"`, valid signature; `ProcessRequest` routes it to `HandleLegacyUserMessage`, storing `savedCallbacks["X"] = callbackAttacker` (`core/services/gateway/handlers/capabilities/handler.go:411-414`).
2. Before the DON responds, victim's legitimate concurrent request (also using `MessageID = "X"`, e.g., due to a colliding/predictable ID scheme) is processed — order can be reversed to have the attacker overwrite the victim's entry instead.
3. A DON node responds for `MessageID = "X"`; `HandleNodeMessage` validates only `msg.Body.Sender == nodeAddr` (`handler.go:253-255`) and `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, delivering the response to whichever callback is currently stored (`handler.go:148-161`).
4. The party whose callback was overwritten receives the other party's response data; the other party's HTTP request times out.

A Go integration test can construct two `handlers.Callback` instances, call `HandleLegacyUserMessage` twice with the same `MessageID` from different simulated callers, invoke `HandleNodeMessage` once, and assert which callback received the response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()
