## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `#shop` reads the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. `Registry.process` verifies the HMAC over the body only, then forwards `request.shop` straight into `WebhookMetadata`, which the host app's `WebhookHandler#handle` uses to decide which tenant's data the payload belongs to. The identity binding `authenticated_shop == acted_upon_shop` is broken: the HMAC authenticates the *body*, not the *shop* field that the handler trusts.

### Finding Description [1](#0-0) 

`shop` is derived directly from an attacker-controllable HTTP header:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```
Compare this with the OAuth `AuthQuery`, where every field that is trusted downstream (`shop`, `code`, `state`, `host`, `timestamp`) is explicitly included in `to_signable_string` and therefore covered by the HMAC: [2](#0-1) 

For webhooks, `Registry.process` validates the HMAC (which only proves the body was signed by Shopify with the app's shared secret) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which participate in the signature — when building the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

Because `hmac-sha256` is computed over `raw_body` only, an attacker who can obtain one valid `(raw_body, hmac)` pair for a given app (e.g., from a webhook that Shopify sends for the attacker's own shop, or any topic whose body is attacker-controlled/predictable, such as `app/uninstalled` with an empty body `{}` as shown in the gem's own tests) can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still pass because it only recomputes the signature over `raw_body`: [5](#0-4) 

The resulting `WebhookMetadata.shop` fed to the app's handler is now attacker-chosen, even though the HMAC check "passed."

### Impact Explanation
This crosses the tenant boundary the HMAC is supposed to enforce. Any multi-tenant app whose `WebhookHandler#handle` branches or writes data keyed by `data.shop` (a documented, expected usage pattern of this gem's webhook API) can be made to process a validly-HMAC'd payload under the wrong shop identity — e.g., triggering `shop/redact` or `customers/data_request` handling, or persisting webhook data, against a shop the attacker does not control. This matches the "Critical - cross-tenant access" impact category, since the security guarantee the library markets (`Registry.process` raising `InvalidWebhookError` unless the HMAC is valid) is silently insufficient to bind the payload to the claimed shop.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain at least one valid `(raw_body, hmac)` pair for the target app's shared secret — trivially possible for topics with fixed/empty bodies, or for any shop where the attacker can install the app themselves and receive genuine webhooks, then replay the captured body+HMAC against the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged credential is required — only the ability to send arbitrary HTTP requests to the app's publicly reachable webhook endpoint, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed content that `to_signable_string` covers, or otherwise cryptographically bind the shop-domain header to the HMAC before trusting it — mirroring how `Auth::Oauth::AuthQuery#to_signable_string` incorporates every field ultimately relied upon by callers. At minimum, document that `Registry.process`/`WebhookMetadata.shop` must not be trusted as an authenticated tenant identifier, or have the library cross-check `request.shop` against Shopify's known-registered shop domains before dispatch.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "secret", host: "example.com",
  scope: "read_products", is_embedded: false, is_private: false,
  api_version: "2024-01"
)

raw_body = "{}"
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
valid_hmac_b64 = Base64.encode64(hmac_digest) # attacker captures this from a genuine webhook to their own shop

# Attacker forges a request claiming to be from a victim shop, reusing the captured body+hmac
forged_headers = {
  "shopify-topic" => "app/uninstalled",
  "shopify-hmac-sha256" => valid_hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
  "shopify-webhook-id" => "attacker-chosen-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes (it only checks raw_body), and the registered handler
# receives WebhookMetadata.shop == "victim-shop.myshopify.com" despite the
# payload never having been produced/signed for that shop.
```
