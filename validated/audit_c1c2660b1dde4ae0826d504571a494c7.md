This confirms the vulnerability class. The documented protocol invariant is explicit: `pallet-ismp` does **not** persist a request receipt when `IsmpModule::on_accept` returns `Err`, which "effectively allows messages to be re-executed until they time out," so "the `IsmpModule` is responsible for maintaining all invariants before modifying its internal state to prevent partial state changes" [1](#0-0) [2](#0-1) . `pallet_hyper_fungible_token`'s `on_accept` violates exactly this invariant.

### Title
Irreversible token mint/transfer committed before calldata signature verification enables replay-driven double-mint - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` mints/transfers the bridged amount to the beneficiary first, and only afterward decodes and validates the optional `SubstrateCalldata` (signature verification, base-call-filter check, `RuntimeCall` dispatch) [3](#0-2) . Any failure in the calldata path (bad signature, undecodable call, filtered call, failing inner dispatch) causes `on_accept` to return `Err` **after** the token mint/transfer has already been committed to storage.

### Finding Description
This mirrors the Zephyr WireGuard bug class: state mutations are committed before the step that determines whether the operation should be treated as valid/final, and the "invalid" path does not roll back the earlier mutation.

Order of operations in `on_accept`:
1. Resolves `local_asset_id`, decodes `Message`, computes `amount`.
2. Mints or transfers `amount` to `beneficiary` (lines 93-117) — an **irreversible, committed** storage write (`NativeCurrency::transfer` / `Assets::mint_into`).
3. Only then decodes `SubstrateCalldata`, verifies the `MultiSignature` (Ed25519/Sr25519/Ecdsa) over `(nonce, runtime_call)`, checks `BaseCallFilter`, and dispatches `runtime_call` (lines 119-202).

If any step in (3) fails, `on_accept` returns `Err(...)`. Per the documented ISMP request-handling contract, `pallet-ismp`'s `handle` function deletes the just-written request receipt when the module callback errors: `if res.is_err() { host.delete_request_receipt(&wrapped_req)?; }` [4](#0-3) . That receipt deletion is meant to let a genuinely-failed message be retried or eventually time out — but here the token mint/transfer from step 2 is **not rolled back**, because `pallet-ismp` does not wrap `on_accept` in a transactional storage boundary (no `#[transactional]`/`with_transaction` was found wrapping this call path).

Consequently: a relayer can submit the same underlying membership-proved `PostRequest` again (since no receipt exists for it), and it will pass proof re-verification (the source request itself is legitimately proven on the source chain — nothing about the proof is "replayed" in the anti-replay sense, it's the destination-side non-idempotency that's exploited) and re-run `on_accept`, minting the same amount again while the attacker's crafted calldata is designed to fail every time (e.g., a bogus signature or a call that always reverts through `BaseCallFilter`/dispatch failure), so the receipt is deleted again — enabling **the beneficiary to be credited multiple times for a single source-chain PostRequest** simply by re-relaying it and always taking the calldata-fails branch.

### Impact Explanation
This is a destination-side unbacked/duplicate mint of bridged tokens: each replay of the same (still-unrecorded) `PostRequest` re-executes the escrow release/mint step, letting an attacker accumulate balance disproportionate to what was actually escrowed/burned on the source chain. This directly matches the required impact class: "concrete theft or ... unbacked mint" via a token-bridge mint/burn path reachable by any relayer resubmitting an already-proven request with attacker-controlled calldata.

### Likelihood Explanation
Reachable by a single relayed message with no special privilege: any account can send an HFT transfer to itself with a non-empty `data` field containing calldata that will deterministically fail signature verification or dispatch (e.g., garbage signature bytes, or a `RuntimeCall` blocked by `BaseCallFilter`). The relayer role is permissionless for delivering already-membership-proved requests, and nothing prevents resubmitting the identical `PostRequest` once its receipt has been deleted by the failed `on_accept`. This requires no consensus forgery, no governance compromise, and no race condition — only the ordinary "no receipt ⇒ retryable" ISMP semantics combined with mint-before-verify ordering in this one module.

### Recommendation
Reorder `on_accept` so all fallible/irreversible operations happen before the mint/transfer: decode and fully validate `SubstrateCalldata` (signature verification, `BaseCallFilter`, and — ideally — dispatch the `RuntimeCall`) first, and only mint/transfer tokens to the beneficiary after every validation and dispatch step that can return `Err` has succeeded. Where the `RuntimeCall` dispatch must happen after funds are available to it, wrap the whole `on_accept` body (mint + calldata dispatch) in `frame_support::storage::with_transaction` so a later failure atomically rolls back the earlier mint, guaranteeing the module never leaves committed state changes behind for a request whose receipt gets deleted.

### Proof of Concept
1. Register `HftNativeAssetId` / native asset with a peer EVM contract as in the test setup [5](#0-4) .
2. Craft a `PostRequest` whose `Message.data` is a SCALE-encoded `SubstrateCalldata` with `signature: Some(<garbage 65 bytes>)` (any `MultiSignature` variant) so `sp_io::crypto::*_verify` deterministically fails at line 138/149/163 of `module.rs`.
3. Submit this `PostRequest` (with a valid source-chain membership proof) via `pallet-ismp`'s `handle`. `on_accept` mints `amount` to `beneficiary` (lines 93-117), then fails signature verification (`HftError::SignatureVerificationFailed`) and returns `Err`.
4. `modules/ismp/core/src/handlers/request.rs` observes `res.is_err()` and calls `host.delete_request_receipt(&wrapped_req)` — no receipt is stored for this commitment.
5. Resubmit the identical `PostRequest`/proof. `dedup_requests` and the receipt-existence check both pass (no receipt exists), so `on_accept` runs again and mints `amount` a second time to the same `beneficiary`, with the calldata step failing identically and the receipt deleted again.
6. Repeat step 5 arbitrarily to accumulate unbacked balance, confirmed by observing `beneficiary`'s asset/native balance increase on each replay despite only one message ever having been dispatched from the source chain.
