### Title
Webhook processing trusts unauthenticated `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `#shop` is read directly and unauthenticated from the `X-Shopify-Shop-Domain` HTTP header [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (the body) using the app's single `api_secret_key`, and never incorporates the shop header into the signed data [3](#0-2) . `Webhooks::Registry.process` accepts any request that passes this HMAC check and forwards `request.shop` directly to the app's handler as the trusted tenant identifier, with no additional binding check [4](#0-3) .

### Finding Description
This is the same bug class as the ZetaChain report: a field that is *acted upon* (there, the abort-destination address; here, the tenant/shop identity) is not included in the data that is cryptographically authenticated (there, the HMAC over `RevertOptions`; here, the HMAC over the webhook payload). The binding that should hold is:

`shop authenticated by HMAC == shop used to identify the tenant/session for processing`

Before the attacker's request: for a legitimate Shopify-originated webhook, the HMAC (computed server-side with the app's shared secret over the body) and the `shop-domain` header both correctly describe the same installation event, because Shopify itself sets both.

After the attacker's request: since `api_secret_key` is a single value per app (not per-shop) [5](#0-4) , any merchant who has installed the app (i.e., any unprivileged internet user who can create a Shopify dev/trial store, install the target app, and trigger a webhook such as `orders/create` on their own store) legitimately receives a validly-HMAC'd webhook for their own shop. Because the HMAC is computed only over the body, that attacker can replay/forge an HTTP POST to the app's webhook endpoint with:
- the same raw body and its correspondingly-valid HMAC (both under their own control, since the body is entirely attacker-influenced content from their own store), and
- an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop.

`HmacValidator.validate` will return `true` (the HMAC only certifies "signed by this app's secret", not "for this shop"), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain [6](#0-5) . Host applications are documented to treat `data.shop` as the authoritative tenant key (e.g., to look up the merchant's session/access token and process the payload) [7](#0-6) , so this directly breaks the identity binding between "who the HMAC proves the sender is" and "which tenant's data/session gets acted on."

### Impact Explanation
This allows cross-tenant data injection/impersonation: an unprivileged attacker who has merely installed the app on their own store (no special privilege, no leaked secret) can make the host application believe attacker-controlled webhook content originated from a different merchant's shop. Depending on how the host app uses `data.shop` (e.g., to fetch/act with that shop's stored access token, to write into that shop's records, or to key background jobs as shown in the gem's own documented usage pattern `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this can lead to cross-tenant access/contamination, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's `Webhooks::Registry.process`/`Request` exactly as documented: the only precondition is installing the app on an attacker-owned shop (a normal, unprivileged action), which is sufficient to obtain a validly-signed webhook body/HMAC pair that can then be replayed with a spoofed `shop-domain` header.

### Recommendation
Do not treat the `shop-domain` header as authenticated data. Either include the shop domain in the HMAC-signed payload validation path (not possible since Shopify doesn't sign the header), or require host apps to cross-check `request.shop` against an independently known/authorized shop (e.g., verify the shop is one that completed OAuth and has a stored session/webhook registration ID matching `webhook_id`) before trusting it as a tenant key. At minimum, the gem's documentation should explicitly warn that `data.shop` is not authenticated by the HMAC check and must not be used as a sole tenant-identity source.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker triggers a real webhook (e.g., `orders/create`) on their own store, capturing the raw body `B` and the resulting valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify using the app's `api_secret_key` over `B`).
3. Attacker replays a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (still valid, since only `B` is signed), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop == "victim-shop.myshopify.com"` [2](#0-1) .
5. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `B` against `H` [8](#0-7) .
6. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` [4](#0-3) , causing the host app to process attacker data under the victim's tenant identity.
