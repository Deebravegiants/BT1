### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed over that string never covers the `shopify-shop-domain` / `x-shopify-shop-domain` header. Since the webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app, any party who can obtain one valid `(body, hmac)` pair — e.g. an ordinary merchant that installed the app and can trigger webhooks for their own store — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. `Registry.process` accepts the request as valid and dispatches it to the app's handler with the attacker-chosen shop identity, breaking the binding between "HMAC-authenticated bytes" and "shop identity acted upon."

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMACs only that string against `Context.api_secret_key`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` only checks the HMAC of the body, then forwards `request.shop` (and other unsigned header fields) straight to the app-provided handler as trusted metadata: [4](#0-3) 

Because `Context.api_secret_key` is the single app-level secret (not a per-shop secret), any legitimate merchant who has installed the app can obtain a genuine `(body, hmac)` pair from their own store's webhooks. That pair remains valid for any `shop-domain` value, since the header is never part of the signed material. Replaying the pair with a different `shop-domain` header lets the attacker impersonate another merchant to the host application's webhook handler — a broken equality between "bytes verified by HMAC" and "shop identity trusted by the handler."

### Impact Explanation
This is a cross-tenant identity spoofing vector: the host application's `WebhookMetadata` (specifically `shop`) is treated as authenticated because it arrives alongside a valid HMAC, but the HMAC never actually certifies that field. An attacker with any valid app install can forge webhook deliveries that appear to originate from a victim merchant's shop, potentially causing the host app to create/modify/delete tenant data, trigger uninstall/GDPR flows, or leak state under the wrong tenant — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even trial) installer of the app so they can receive one authentic webhook delivery with a valid HMAC for a body they control or can predict (e.g., a webhook whose body content is attacker-influenced, or a topic with a small/predictable body). No access to `api_secret_key` or any privileged credential is required — only observation of one legitimate webhook and the ability to POST to the app's public webhook endpoint.

### Recommendation
Include the shop-scoping headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or have `Registry.process` cross-check `request.shop` against an out-of-band trusted value (e.g., the shop associated with the queried webhook subscription) before dispatching to the handler. At minimum, document that consumers of `WebhookMetadata#shop` must not treat it as cryptographically authenticated by the gem's `HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook whose body is fixed/predictable (e.g. an empty-body test topic, or a topic whose payload the attacker fully controls, e.g. a metafield they set).
2. Attacker captures the resulting `x-shopify-hmac-sha256` header value `H` for raw body `B`.
3. Attacker sends a POST to the app's public webhook endpoint with:
   - `x-shopify-topic`: any topic the app has a handler for
   - `x-shopify-hmac-sha256`: `H`
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - body: `B`
4. `HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true`; `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"`, even though the payload never originated from that shop. [4](#0-3)
