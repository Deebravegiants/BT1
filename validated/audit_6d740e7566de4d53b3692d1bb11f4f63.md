### Title
Hostile mint pre-seed can force `Math.mulDiv` to revert inside `_noFeeSwapInput`, permanently bricking `finalizeGraduation` and freezing curve-raised LT and the 250M LP reserve - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2019-9749 is a class of bug where an attacker-controlled packet drives an internal size computation into an out-of-range value that a low-level primitive (`memmove`) cannot handle, crashing the whole process. The structural analog here is `Bonding._noFeeSwapInput`, the load-bearing math of the hostile-pre-seed defense: an attacker who fully controls the two inputs that feed a multiplication (`reserveIn`, `reserveOut`, read straight from a HyperSwap V2 pair the attacker pre-seeded) can drive `Math.mulDiv`'s *final* result past `type(uint256).max`, which OpenZeppelin's `mulDiv` handles by reverting rather than truncating. Because `finalizeGraduation` never catches this revert, the entire two-phase graduation permanently bricks for that token, exactly the outcome the protocol's own comments say must never happen.

### Finding Description
`_noFeeSwapInput` computes the rebalance-swap size for the "hostile mint pre-seed" defense: [1](#0-0) 

```
uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
uint256 newIn = Math.sqrt(product);
```

`reserveIn`/`reserveOut` are the HyperSwap V2 pair's live reserves, and `targetN`/`targetD` are `ltFromPair`/`tokensForLP` (or their inverse), all of which are read/derived in `_seedRebalancing`: [2](#0-1) 

The reserves come straight from `IUniswapV2Pair(pair).getReserves()` — a pair the attacker created and seeded via the documented front-run flow (`factory.createPair` → `transfer` → `pair.mint`), described in `AGENTS.md`'s "HyperSwap Pre-Seed Defense" section: [3](#0-2) 

`Math.mulDiv(a, b, c)` computes `a*b` in a 512-bit intermediate space and only requires the *final* `a*b/c` to fit in 256 bits — the developers acknowledge this precisely in the function's own natspec, calling a revert here "the correct failure mode" *because* they believed no real call site could construct inputs that violate the invariant: [4](#0-3) 

That belief is falsifiable: `reserveIn`/`reserveOut` are uint112-bounded V2 reserves that an attacker fully controls up to their own TOKEN/LT holdings (TOKEN up to real circulating supply, LT up to whatever the attacker can acquire — unbounded by this protocol), while `tokensForLP` — the denominator in the "pool TOKEN-rich" branch — can be arbitrarily small for a token that graduates cheaply (e.g. a token graduated via the permissionless, buy-free `triggerGraduation` right after a minimal seed buy, where only a tiny fraction of the curve was ever sold, per the parabola `tokensForLP(sold) = sold·(S−sold)/S`). When the attacker sizes a pre-seed so that `reserveIn·reserveOut·targetN` exceeds `tokensForLP · type(uint256).max`, `Math.mulDiv` reverts, `_pairRebalance` reverts, `_seedRebalancing` reverts, and `finalizeGraduation` reverts: [5](#0-4) 

This directly contradicts the protocol's own stated invariant that `_seedUniswapV2Direct` "MUST never revert under any pre-seed shape... a brick locks every holder in `Graduating` forever": [6](#0-5) 

Once `finalizeGraduation` cannot execute, the token is stuck permanently in `Lifecycle.Graduating`: trading is frozen (`_enterGraduating` already flipped lifecycle and drained/parked the curve's real LT plus the 250M `LP_RESERVE` tokens inside `Bonding`), and there is no alternate finalize path or way to remove the hostile pre-seed from the HyperSwap pair, since `pendingGraduation[token]`'s `(tokensForLP, ltFromPair)` are immutable once cached: [7](#0-6) 

### Impact Explanation
A successfully bricked graduation permanently freezes: (1) all real LT raised by the bonding curve for that token (`p.ltFromPair`), (2) the 250M `LP_RESERVE` tokens reserved for LP seeding, and (3) every holder's tokens, since trading was frozen at `_enterGraduating` and can never resume (no path back to `Lifecycle.Curve`, and `finalizeGraduation` is the only way to `Lifecycle.Graduated`). This is unrecoverable creator/trader fund freezing, matching the severity bar required (permanent freezing of curve-raised LT and LP funds).

### Likelihood Explanation
The attack requires: (a) front-running pair creation for the target token/LT pair (permissionless, standard V2 behavior, already the documented threat model), (b) acquiring a TOKEN balance from the curve (any buyer can do this cheaply on the shallow early curve) and an LT balance whose magnitude, combined with the token side, pushes the `mulDiv` discriminant over `type(uint256).max / tokensForLP`, and (c) targeting a token whose `tokensForLP` is small — most naturally a token that graduates via the USD/rate trigger with little real supply sold (a scenario the protocol explicitly supports via permissionless `triggerGraduation`). This is entirely reachable by a single unprivileged wallet with no special role, using only public entry points (`Factory.createPair`, direct `IERC20.transfer` + `pair.mint`, `Bonding.triggerGraduation`, `Bonding.finalizeGraduation`).

### Recommendation
Wrap `_noFeeSwapInput`'s `Math.mulDiv` computation in a bounds pre-check (or a `try/catch`-equivalent guard, since it's a `pure` internal call — refactor to check `reserveIn`, `reserveOut`, `targetN`, `targetD` magnitudes against a safe product bound before calling `Math.mulDiv`) and treat an out-of-range discriminant the same way an `s == 0` result is treated today: fall back to `_seedDirectMint` instead of letting the revert propagate. This preserves the brick-resistance contract the codebase already promises for every other degenerate pre-seed shape.

### Proof of Concept
1. Launch a token normally via `Zap.createToken` with the minimum seed (`MIN_SEED_USDC`).
2. Pump the paired LT's `exchangeRate()` so the USD-value trigger crosses the graduation threshold with almost none of the curve sold (this makes `tokensForLP` tiny per the parabola formula).
3. Call `Bonding.triggerGraduation(token)` (permissionless) — `_enterGraduating` caches a small `tokensForLP`.
4. Before `finalizeGraduation` runs, front-run: `Factory`-equivalent `HyperSwapFactory.createPair(token, lt)`, then `transfer` a large TOKEN balance (accumulated from the curve) and a large LT balance to the pair, then call `pair.mint(attacker)` — sizing both reserves so that, combined with the small cached `tokensForLP`, `reserveIn * reserveOut * targetN / tokensForLP` exceeds `type(uint256).max`.
5. Call `Bonding.finalizeGraduation(token)` — it reverts inside `_noFeeSwapInput`'s `Math.mulDiv`, and every subsequent call to `finalizeGraduation` reverts identically, permanently bricking the token in `Lifecycle.Graduating` with its curve-raised LT and 250M `LP_RESERVE` tokens locked in `Bonding`.

    /// @dev Smallest swap input that drives the pool's reserve ratio
    ///      `(reserveIn + s) / (reserveOut - out)` to `targetN/targetD`

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. In either case `_pairRebalance` returns `false`, and `_seedRebalancing` overpowers the dust with a direct `transfer + pair.mint` at the cached `tokensForLP / ltFromPair` ratio (`_seedDirectMint`), opening the pool on-ratio. This is safe specifically because the swap only rounds to zero when the reserves are negligible against this graduation's inventory: the V2 `min()` donation to the attacker's pre-existing LP is then bounded by `max(reserveToken/tokensForLP, reserveLT/ltFromPair)`, which vanishe ... (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
- **No external dependency on the router slot being correct post-deploy.** `uniswapV2Router` is set at `initialize` time alongside `uniswapV2Factory` and is rejected if zero. There's no live setter — rotation requires a UUPS upgrade so the change is visible on-chain ahead of any in-flight graduation.

Tested end-to-end by the brick-resistance regression tests in `test/TwoPhaseGraduation.t.sol` (notably `test_brick_resistance_frontRun_dust_seed`).
