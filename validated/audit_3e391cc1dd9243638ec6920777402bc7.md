## Title
Excess native-token payment in `EvmHost.dispatch`/`fundRequest` is never refunded and becomes permanently stuck in the host - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native-token payment via `msg.value` and swap it for the exact fee-token amount needed using `swapETHForExactTokens`, but none of them capture the unused native token returned by the swap or refund it to the caller. This is the same "overspend and lose the difference" bug class as the reported Allo `_createPool` issue, except here the codebase itself demonstrates the correct fix (`IntentGatewayV2`) right next to the vulnerable code that omits it.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

`swapETHForExactTokens` only spends the amount needed to obtain exactly `post.fee` tokens; the Uniswap V2 router refunds any unspent ETH to whoever called it — which here is `EvmHost` itself (the router's `msg.sender` is `EvmHost`, not the original caller `_msgSender()`). The return value (an `amounts` array containing the actual ETH spent) is discarded, and no code path forwards the refunded ETH back to the original transaction sender. The exact same pattern (discard the swap result, no refund) recurs in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest` [3](#0-2) .

Contrast this with `IntentGatewayV2._createOrder`, which performs the identical swap but correctly tracks the spent amount and refunds the remainder to the caller:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [4](#0-3) 

This is confirmed by dedicated tests (`testPlaceOrder_RefundsExcessNativeToken`, `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`) that assert IntentGatewayV2 refunds overpayment [5](#0-4) . `EvmHost` has no analogous refund logic or test, and the documentation actually instructs callers to send extra native tokens as a safety buffer against price volatility (e.g. "Apply a generous 2x buffer... Excess native is refunded by the uniswap router" — a claim that is only true if the refund lands with the original sender, which it does not for `EvmHost`) [6](#0-5) .

### Impact Explanation
Every dispatcher/app (including `HyperFungibleToken.send`, `WrappedHyperFungibleTokenUpgradeable.send`, `HyperbridgeLzEndpoint.send`, or any third-party `IApp`) that pays Hyperbridge fees in native token via `IDispatcher(host).dispatch{value: msg.value}(...)` and sends more than the exact cost — which the SDK/docs explicitly recommend doing to hedge against price movement between off-chain quoting and on-chain execution — will have the surplus permanently trapped in `EvmHost`. Unlike the Allo case, no `recoverFunds`-equivalent sweep function was found on `EvmHost`/`HostManager` in scope, so this ETH is not merely inconvenient to recover by an admin — it appears to have no code path back to any account at all, i.e., a genuine permanent loss of user funds for every native-token overpayment.

### Likelihood Explanation
High. This triggers on ordinary usage by any unprivileged caller dispatching a message and paying with native token, since exact fee-token pricing via Uniswap cannot be predicted precisely on-chain (docs explicitly warn against calling `quote()` on-chain due to sandwich risk and recommend buffering `msg.value`) [7](#0-6) . Every such buffered call loses the unspent difference.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2._createOrder` [4](#0-3) .

### Proof of Concept
1. Fee token price of `post.fee` requires 1 ETH via Uniswap.
2. Caller (e.g. `HyperFungibleToken.send`) sends `dispatch{value: 2 ether}(post)` to buffer against slippage, per documented guidance.
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: 2 ether}(post.fee, ...)` spends only 1 ETH and the router refunds 1 ETH — to `EvmHost` (the caller of the router), not to the original sender.
4. `EvmHost`'s native balance permanently increases by 1 ETH with no accounting entry and no function to return it to the original sender. [1](#0-0)
