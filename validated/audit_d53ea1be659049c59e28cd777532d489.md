### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values that the gem hands to the app's handler as the tenant identifier are read from HTTP headers that are never included in the signed content, so a valid `(body, hmac)` pair is not bound to any particular shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string` as the signed content [4](#0-3) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are pulled directly out of headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic tie to the body or the signature at all [2](#0-1) .

`Registry.process` then does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

The identity binding that should hold is: `shop attributed to the processed webhook == shop that the HMAC-signed bytes originated from`. Because the header carrying `shop` is excluded from `to_signable_string`, this equality is never enforced by the gem. Since the same `client_secret`/HMAC key is shared across every shop that installs a given app, any actor who can obtain one genuine `(raw_body, X-Shopify-Hmac-SHA256)` pair for a webhook topic (trivially achievable by installing the app, which any merchant/dev-store owner can do, on their own shop and triggering an event whose payload content they control, e.g. an `orders/create` webhook with attacker-chosen line items/customer data) can resend that exact body/signature pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the untouched body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the app relies on: webhook handlers built on this gem receive attacker-controlled data falsely attributed to an arbitrary victim `shop`, without any bypass of a secret. Depending on how the host app persists/keys off `WebhookMetadata#shop` (e.g., updating per-shop order/customer/product records, provisioning, billing state), this enables cross-tenant data injection/corruption — matching the Critical "cross-tenant access" impact category, since an unprivileged actor (any merchant that can install the app) can inject data attributed to a shop they do not own.

### Likelihood Explanation
Exploitation requires no possession of `api_secret_key`: the attacker only needs to be an installer of the app on their own store (which is available to any user with a free Shopify partner/dev store) and the ability to resend an HTTP request with a modified header, both of which are unprivileged-internet-user actions. The only friction is capturing one legitimate `(body, hmac)` pair, which is straightforward for attacker-controlled webhook content (e.g., choosing values in an order/customer they create on their own store).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content used for webhook verification, or perform an explicit secondary check after HMAC validation that `request.shop` matches an expected/registered shop for the given HMAC/topic before constructing `WebhookMetadata`. At minimum, document and enforce that `Registry.process` callers must independently verify `request.shop` against a shop that is expected to receive that specific webhook (e.g., cross-check against an active session/install record) rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target app on their own development shop `attacker.myshopify.com` and configures an `orders/create` webhook subscription (apps commonly do this automatically via `Registry.register`).
2. Attacker creates an order on their own shop with attacker-chosen payload fields, causing Shopify to deliver a genuine webhook: raw body `B`, header `X-Shopify-Hmac-SHA256: H` (valid because `H = HMAC-SHA256(client_secret, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the exact same body `B` and header `H` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this still passes [5](#0-4) .
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, and the host app processes/persists this data as if it legitimately originated from `victim.myshopify.com`.
