### Title
Fee-on-transfer underlying tokens cause unbacked cross-chain unlocks in `WrappedHyperFungibleToken` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom` but dispatches the cross-chain message with the user-requested `params.amount` rather than the amount actually received by the contract. For fee-on-transfer underlying tokens, the destination chain's `onAccept()` unlocks the full requested amount even though less was actually locked on the source chain, permanently under-collateralizing the bridge.

### Finding Description
In `send()`, the contract pulls tokens with `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` [1](#0-0) , but the outgoing message body encodes `params.amount` verbatim as the locked amount, with no balance-before/after measurement of what the contract actually received [2](#0-1) .

On the destination chain, `onAccept()` unconditionally transfers `message.amount` — the unmodified requested amount — to the beneficiary from the contract's own token/WETH reserves: `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` [3](#0-2) .

This is the exact bug class described in the external report: any deviation between the amount specified for a transfer and the amount actually received due to a fee-on-transfer mechanism is not reconciled before the value is propagated onward. The codebase's own `IntentGatewayV2.placeOrder()` already defends against this pattern by snapshotting `balanceOf` before and after `safeTransferFrom` and using the delta for escrow accounting and commitment hashing (see e.g. `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;`) [4](#0-3) , confirming this exact discrepancy is a recognized, previously-fixed hazard elsewhere in the codebase — but the fix was not applied to `WrappedHyperFungibleToken`.

### Impact Explanation
If the configured `_underlying` token charges a transfer fee (a legitimate and common ERC20 behavior, not requiring malicious configuration), every `send()` call locks less than `params.amount` on the source chain while the destination-chain deployment unlocks the full, un-discounted `params.amount`. Repeated use drains the destination chain's token reserve faster than it is replenished by locked collateral, resulting in an unbacked release of tokens and eventual insolvency of the bridge (later legitimate users cannot redeem because reserves are depleted) — a direct instance of "unbacked mint"/permanent freezing of funds for other users of the wrapper.

### Likelihood Explanation
Reachable by any unprivileged caller of `send()` once the token wrapper is configured (by design) for a fee-on-transfer ERC20 — no privileged or malicious action is required beyond normal use of the bridge with a standard token category. This mirrors the reporter's original claim precisely, just manifesting as a cross-chain lock/unlock accounting bug instead of an escrow/collateral bug.

### Recommendation
In `send()`, measure the actual amount received via balance-before/after (as already done in `IntentGatewayV2.placeOrder()`) and encode that actual received amount in the dispatched `HyperFungibleToken.Message`, not the caller-supplied `params.amount`. Alternatively, explicitly disallow fee-on-transfer tokens as `_underlying` via a documented invariant/check at `configure()` time.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a token that charges e.g. 1% fee on every `transfer`/`transferFrom`.
2. User calls `send({dest, to, amount: 1000, ...})`.
3. `safeTransferFrom` pulls 1000 tokens from user, but due to the 1% fee the contract only receives 990.
4. `_buildDispatchPost` still encodes `amount: 1000` in the message body; this is dispatched cross-chain.
5. On the destination chain, `onAccept()` calls `safeTransfer(beneficiary, 1000)`, paying out 1000 tokens even though only 990 were actually locked on the source chain.
6. Repeating this drains 10 tokens of un-backed value from the destination reserve per 1000 sent, eventually insolvent for future redemptions.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
