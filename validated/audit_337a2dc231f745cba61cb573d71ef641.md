### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (and `topic`) values used to route the webhook to a handler and identify the tenant are taken from unauthenticated HTTP headers that are never included in the signable content. An unprivileged internet user who can obtain any one legitimately-signed webhook (e.g. by installing the target app on their own store) can replay that exact body/HMAC pair to the same public webhook endpoint while forging the `shopify-shop-domain` header to name a different, victim shop. `HmacValidator.validate` will accept the request because it only checks the body against the HMAC, and `Webhooks::Registry.process` will then hand the attacker's payload to the handler tagged with the victim's `shop`, breaking the equality: `shop asserted to the app === shop actually bound by the HMAC`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (the body), never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop`, the unauthenticated header value, as the tenant identity for the webhook data: [4](#0-3) 

Because the HMAC only binds the body, any request with a body/HMAC pair that is valid for shop A remains valid when the `shopify-shop-domain` (or `x-shopify-shop-domain`) header is changed to shop B. The library provides no mechanism (e.g., binding shop into the signed content, or requiring a per-shop secret/shop allow-list check) to prevent this substitution.

### Impact Explanation
This breaks the identity binding `shop authenticated by HMAC == shop acted upon by the handler`. An attacker who legitimately installs the target app on their own store (a routine, unprivileged action) will receive real webhooks from Shopify with valid `body`/`hmac` pairs for their own shop. By re-POSTing that exact body and hmac to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain, the attacker forces the host application's webhook handler to process attacker-controlled data under the victim tenant's identity. Depending on how the host application's handler uses `WebhookMetadata#shop` (e.g., to write/delete records keyed by shop, to trigger data sync, or to react to `app/uninstalled`), this results in cross-tenant data injection or corruption — a cross-tenant access impact.

### Likelihood Explanation
High likelihood: no secrets, tokens, or privileged access are required. The attacker only needs to be a legitimate (even free) merchant able to install the target app on a store they control, capture one of their own real webhook deliveries, and replay it to the app's internet-facing webhook endpoint with a modified header. This is well within reach of any unprivileged internet user.

### Recommendation
Bind the tenant identity into the verified content instead of trusting an unauthenticated header:
- Require host applications to independently verify that the `shop` claimed in the webhook belongs to a shop that has the app installed with a stored, shop-specific credential, and reject if unknown/mismatched, and/or
- Extend `VerifiableQuery`/`HmacValidator` usage for webhooks so the `shop` (and `topic`) values are incorporated into the signed payload validation (e.g., by cross-checking against Shopify's registered webhook subscription for that topic/shop combination) rather than accepted from headers alone.
- At minimum, document prominently in `Webhooks::Request`/`Webhooks::Registry` that `shop` is not covered by the HMAC and must be independently corroborated (e.g., against an installed-shop list) by the consuming application before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because it only signs the body)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or attacker-chosen registered topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data under the victim's tenant identity.
