### Title
Non-constant-time PIN comparison with no attempt throttling in `isCorrectPin` - ([File: features/auth-mobile/module/auth.js])

### Summary
`Auth#isCorrectPin` compares the stored 6-digit PIN to caller-supplied input using plain `===` and never applies any rate limiting, delay, or lockout counter. The method is re-exported unmodified into `authApi.auth` (via `features/auth-mobile/api/index.js`), so any caller with access to that API surface can invoke it an unlimited number of times.

### Finding Description
`isCorrectPin` retrieves the secret and does a direct strict-equality check: [1](#0-0) 
There is no counter, delay, exponential backoff, or lockout state tracked anywhere in the `Auth` class — `#mergeIntoAtom`/atom state only tracks `hasPin`, `hasBioAuth`, `hasDeviceAuth`, `shouldAuthenticate`, none of which relate to failed-attempt tracking: [2](#0-1) 
The method is spread verbatim into the public `authApi.auth` object with no wrapper adding throttling: [3](#0-2) 
Note: the file path named in the question (`features/auth-mobile/atoms/auth.js`) actually only contains the in-memory atom factory [4](#0-3)  and does not define `isCorrectPin`; the real implementation lives in `features/auth-mobile/module/auth.js`.

Given a 6-digit numeric PIN (10^6 = 1,000,000 possibilities), an unbounded number of `isCorrectPin` calls make brute force computationally trivial with no code-level obstacle. The `pin === input` string comparison also short-circuits on the first mismatched character, which is a classic non-constant-time comparison pattern, though JS string comparison timing differentials are generally very small and noisy over an RPC/IPC boundary, making a practical timing side-channel far less reliable than the brute-force/lockout-absence issue itself.

### Impact Explanation
If `authApi.isCorrectPin` (or the underlying `auth.isCorrectPin`) is reachable by a caller that does not already need the correct PIN (e.g., a compromised/malicious in-app webview context or any RPC consumer that can address the `authApi` id), an attacker can brute-force the PIN within ~1,000,000 attempts with no lockout, recovering the secret that gates downstream "unlock" actions protected by the PIN (e.g., approving transactions, revealing seed/keys, disabling security). This matches Hydra's "secret disclosure leading to downstream wallet compromise" impact class, scoped to whatever the PIN protects.

### Likelihood Explanation
Exploitability is conditioned entirely on `authApi.isCorrectPin` being reachable by an unprivileged/unauthenticated caller. The `api` module (`features/auth-mobile/api/index.js`) is registered generically as an "api" id string with no visible per-call origin/permission gate in this file; whether the RPC/IPC dispatcher that exposes registered `api` definitions to less-trusted contexts (e.g., dapp bridge, webview) enforces its own access control is not visible in the files inspected here. Assuming the stated precondition (an unprivileged caller can invoke `authApi.isCorrectPin` an unbounded number of times) holds, the brute force is fully repeatable and requires no special conditions — every call is stateless and unthrottled.

### Recommendation
Add explicit attempt throttling/lockout state (e.g., persisted failed-attempt counter with exponential backoff or hard lockout after N failures) inside `Auth#isCorrectPin` or at the `authApi` boundary before the comparison runs, and use a constant-time comparison (e.g., `crypto.timingSafeEqual` on fixed-length buffers) instead of `pin === input`. Additionally, verify/restrict which callers can reach `authApi.auth.isCorrectPin` at the RPC/IPC dispatch layer.

### Proof of Concept
Unit/fuzz test plan for `features/auth-mobile/module/auth.js`:
1. Construct `Auth` with a mocked `keystore` whose `getSecret` resolves a fixed 6-digit PIN (e.g., `"123456"`).
2. In a loop, call `auth.isCorrectPin(guess)` for a large number (e.g., 10,000+) of incorrect guesses in rapid succession.
3. Assert: (a) no exception/lockout error is ever thrown, (b) `keystore.getSecret` is called once per invocation with no growing delay between calls, (c) no atom/state field reflecting failed-attempt count is ever set — confirming absence of throttling.
4. Optional timing test: measure wall-clock latency of `isCorrectPin` calls for guesses that share an increasing correct prefix vs. fully incorrect guesses over many trials, and statistically compare distributions (expect this to show negligible/no reliable signal in JS engine string comparison, weakening the timing-attack sub-claim but not the throttling-absence claim).
