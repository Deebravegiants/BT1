### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then passes the header-derived `shop` value straight to the app's webhook handler as the trusted tenant identifier. Since `shop` is never part of the signed material, an attacker who can obtain any one validly-signed webhook delivery (e.g., by installing the app on their own shop and receiving a genuine webhook) can replay that exact signed body while substituting an arbitrary `shop-domain` header, and the gem will report it as valid and originating from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read from mutable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the raw body), so it never verifies that the `shop-domain` header matches the shop the body was actually signed for: [3](#0-2) 

`Registry.process` raises only on HMAC failure, then forwards `request.shop` directly into the `WebhookMetadata` passed to the app's handler as the trusted tenant identity — with no additional check that this header value is consistent with the signed content: [4](#0-3) 

This breaks the intended identity binding: `verified_hmac_body == body-for-shop(S)` should imply `request.shop == S`, but the code only enforces `verified_hmac_body == body`, independent of any shop value. Two requests with identical bodies but different `shop-domain` headers both pass validation and are attributed to whichever shop the header claims.

### Impact Explanation
The `shop` value handed to `WebhookMetadata` is the only tenant-identifying signal the host application receives from this gem for webhook processing (see `docs/usage/webhooks.md`'s documented flow, where apps key their per-shop side effects off `data.shop`). Because `shop` is not bound to the signed body, a party who can obtain one real, validly-signed webhook body from Shopify for the topic they want to forge (trivially achievable by installing the target app on a shop they control and triggering that webhook topic themselves) can replay the identical signed body to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to point at any other shop the app is installed on. The gem will pass this through as authentic, causing the host app to apply attacker-controlled webhook content to a different tenant's data — a cross-tenant integrity/access violation attributable to a spoofable identity binding in this gem.

### Likelihood Explanation
Likelihood is high for any developer who has installed (or can install) the target app on a shop they control: they need only capture one legitimately signed webhook body/HMAC pair for the topic of interest, then send an HTTP request to the app's webhook endpoint with that body/HMAC and a forged `shop-domain` header value. No secrets, tokens, or privileged access are required — only a standard app installation available to any merchant/developer.

### Recommendation
Include the shop domain (and ideally topic/api_version/webhook_id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the request before trusting it — e.g., have `to_signable_string` incorporate the shop header, or independently verify the `shop-domain` header against a known/expected value (such as an active session for that shop) before invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the resulting request: raw body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), original header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Construct a new POST to the app's webhook endpoint with the exact same body `B` and HMAC header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds since `B` and `H` are unchanged: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled B>, ...)`, causing the host app to process forged data as belonging to `victim-shop.myshopify.com`.
