### Title
Blacklisted beneficiary permanently blocks intent-order escrow settlement, freezing input tokens with no delivery fallback - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` unconditionally `safeTransfer`s escrowed input tokens (and accumulated fee-token amounts) to a `beneficiary` address decoded from an incoming cross-chain `RedeemEscrow`/`RefundEscrow` message, with no fallback if that transfer reverts (e.g. a USDC/USDT blacklist).

### Finding Description
`_withdraw()` iterates the withdrawal request's tokens and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each, and separately transfers accrued fee-token amounts to the same `beneficiary`. [1](#0-0) 

This is invoked from `onAccept()` for both `RedeemEscrow` (beneficiary = the filler/solver) and `RefundEscrow` (beneficiary = the original order creator, `order.user`) after an ISMP settlement message is delivered. [2](#0-1) 

If `beneficiary` is blacklisted by the escrowed token contract (USDC/USDT-style tokens implement blacklists), `safeTransfer` reverts and the entire `onAccept` call reverts.

Crucially, `EvmHost.dispatchIncoming` catches this failure via a low-level `.call` and **deletes the request receipt "so that it can be retried"**: [3](#0-2) 

This retry mechanism assumes failures are transient. But a blacklist status is persistent — every retry of the same commitment will decode the same immutable `beneficiary` from the `WithdrawalRequest` and fail identically forever. The message can never be delivered, and the `_orders[commitment][token]` escrow balance can never be released because there is no alternate beneficiary path, no admin override, and no way to redirect the transfer once the order is placed (the `order.user`/filler address is fixed in the signed order / fill call).

The same issue exists in the Tron port, which reverts explicitly with `TransferFailed()`: [4](#0-3) 

and in the same-chain fill path, which also routes through `_withdraw`: [5](#0-4) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged user/solver interacting with the Intent Gateway:
- **RefundEscrow to `order.user`**: if the order creator's address is later blacklisted by the escrowed stablecoin (or is blacklisted at cancellation time for any reason), the cross-chain cancellation/refund message can never be delivered. The user's escrowed input tokens are permanently locked in the gateway contract with no recovery mechanism.
- **RedeemEscrow to filler**: a griefing filler (or one blacklisted after filling) permanently blocks settlement of that specific order's escrow, and since `EvmHost` deletes the receipt to allow "retry," the message sits in an infinite failure loop, effectively acting as "a route unable to deliver messages" for that commitment — corrupting relayer economics for it as well since no relayer can ever successfully deliver it.
- Because the escrow decrement and transfer happen atomically inside `_withdraw`, there is no partial-fill or partial-withdrawal workaround; the whole settlement for that commitment is stuck.

This satisfies the required impact bar: concrete permanent freezing of escrowed funds and an inherently undeliverable message route.

### Likelihood Explanation
Any Intent Gateway user placing an order that resolves in USDC/USDT (very common stablecoin pairs) is at risk if they, or their chosen filler, are ever blacklisted by the token issuer before settlement/cancellation completes. This requires no privileged action — it is a normal usage path (place order → fill/cancel → cross-chain settlement) — and blacklisting real-world addresses on USDC/USDT is a real, externally-triggered event outside the protocol's control.

### Recommendation
Do not let a failed transfer to `beneficiary` block finalization of the order's accounting. Options:
- Wrap the per-token transfer in a try/catch (or low-level call ignoring failure) and, on failure, credit the amount to an internal "claimable" balance for `beneficiary` that can be withdrawn later to a different address, rather than reverting the whole settlement.
- Allow the beneficiary (or governance) to redirect a stuck claim to an alternate address after a failed transfer.
- At minimum, decouple escrow accounting finalization (marking `_filled`, decrementing `_orders`) from the token transfer, so a transfer failure doesn't force the entire cross-chain message into a permanent retry loop.

### Proof of Concept
1. `Order.user` (or filler) address `A` places/fills an order with `inputs`/settlement token = USDC.
2. Before the order's `RefundEscrow`/`RedeemEscrow` ISMP message is delivered, USDC's issuer blacklists address `A`.
3. Relayer delivers the settlement `PostRequest`; `EvmHost.dispatchIncoming` calls `IntentGateway.onAccept` → `_withdraw` → `IERC20(usdc).safeTransfer(A, amount)` reverts because `A` is blacklisted.
4. `dispatchIncoming` catches the failure, deletes `_requestReceipts[commitment]`, and returns normally (no revert bubbles to the relayer transaction) — logged as retryable.
5. Every subsequent relayer retry decodes the same `WithdrawalRequest.beneficiary = A` and fails identically. The escrowed USDC for this commitment is permanently stuck in the `IntentGateway` contract; `_orders[commitment][usdc]` can never be zeroed via the withdraw path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
