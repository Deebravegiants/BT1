Based on the investigation, the strongest custody analog is in `staking_contract::distribute_internal`.

### Title
Operator-controlled `beneficiary_for_operator` address can permanently lock a shared staking-contract distribution pool - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
The Halborn finding shows a pattern: an admin-settable address field (`fee_collector_vault`) is stored without validating that it is capable of actually receiving funds, and that field is later used unconditionally as a payout destination, so a bad value permanently DoSes the payout instruction. The same shape exists in `staking_contract.move`: `set_beneficiary_for_operator` lets an operator set an arbitrary `new_beneficiary` address with zero validation, and `distribute_internal` later force-pays that address for *every* distribution call, with no fallback if the payment aborts.

### Finding Description
`set_beneficiary_for_operator` stores an operator-supplied address with no checks at all: [1](#0-0) 

`distribute_internal` iterates over every shareholder in the shared `distribution_pool` (which holds shares for the staker(s) and the operator together) and, when it reaches the operator's share, redirects the payout to `beneficiary_for_operator(operator)` and calls `aptos_account::deposit_coins` unconditionally: [2](#0-1) 

`aptos_account::deposit_coins` auto-creates the destination account and auto-registers the `CoinStore` *unless* the destination account exists and has explicitly opted out of direct coin transfers via `DirectTransferConfig`, in which case it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [3](#0-2) 

Because Move transactions are all-or-nothing, if the operator sets `beneficiary_for_operator` to an address that either aborts on deposit (opted out of direct transfers) or is otherwise unable to receive coins, the *entire* `distribute()`/`distribute_internal()` call reverts. Since the same `distribution_pool` and the same `while (distribution_pool.shareholders_count() > 0)` loop pays out every shareholder in one atomic transaction, a single unpayable beneficiary blocks payout for the staker and any other shareholders in that pool as well — there is no partial success and no alternate redemption path (the `OwnerCapability`/`SignerCapability` needed to withdraw from the underlying `stake::StakePool` are held only inside `StakingContract`, reachable only through `distribute_internal`).

### Impact Explanation
This breaks the custody invariant that unlocked/inactive stake, once eligible for withdrawal, must remain recoverable by its rightful owner(s). An operator (not the staker/owner, and not a full "admin" of the pool) can, intentionally or accidentally, brick the only withdrawal path for the shared stake pool by pointing their beneficiary at an address configured to reject direct transfers. This is a non-recoverable-until-fixed lock of pooled value belonging to third parties (the staker and any other shareholders), matching the report's "denial of service until the configuration is corrected" pattern, but here it is triggered by an operator rather than by the staking-pool owner, and it can freeze funds that are not the operator's own.

### Likelihood Explanation
Likelihood is moderate: it requires the operator to either misconfigure the beneficiary or deliberately weaponize it (e.g., griefing a staker they have a dispute with, or an operator who wants to force renegotiation by locking commission distributions for everyone). No special permissions beyond being the registered operator are needed, and `update_coin_transfer_config`-style opt-outs (`DirectTransferConfig`) are a normal, unprivileged user feature, making the "poison" address trivially obtainable.

### Recommendation
- Validate `new_beneficiary` in `set_beneficiary_for_operator` (e.g., require the account to exist and be registered for `AptosCoin`, or require `can_receive_direct_coin_transfers`).
- In `distribute_internal`, don't let one recipient's failure abort the whole distribution: wrap the payout to the operator/beneficiary so failures are isolated (e.g., retain the operator's share in the pool, or fall back to depositing to the operator address itself) rather than reverting the entire multi-party distribution.

### Proof of Concept
1. Staker creates a staking contract with `operator`.
2. `operator` calls `aptos_account::set_allow_direct_coin_transfers(&operator_alt_signer, false)` on some address `A` they control (opting `A` out of direct transfers), or simply designates any account that has already opted out.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, A)` — no validation is performed, per [4](#0-3) .
4. Rewards accrue; stake becomes inactive/pending_inactive.
5. Anyone calls `staking_contract::distribute(staker, operator)`. `distribute_internal` reaches the operator's share, resolves `recipient = beneficiary_for_operator(operator) = A`, and calls `aptos_account::deposit_coins(A, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The whole transaction reverts — the staker's own already-unlocked stake (and any other shareholders') remains stuck, since this is the only distribution path, until the operator changes the beneficiary again (which they may refuse to do).

**Uncertainty / limitation:** I could not confirm from the indexed code whether `distribution_pool` in practice ever holds more than one non-operator shareholder (i.e., whether multiple distinct stakers can share a single `StakingContract`/`distribution_pool`) — the `add_distribution`/`buy_in` calls I found only show the staker and operator as parties in the examples I could trace, and this analog's severity is significantly higher for the "shared pool" case than for the single-staker case (single-staker: the staker's own funds are only locked by their own operator's misbehavior, which is a somewhat expected trust relationship). If `distribution_pool` is effectively always a 1:1 staker↔operator pairing, then the impact is closer to "operator can only hurt itself + one staker who chose that operator" rather than a broader multi-party custody break — I recommend a Devin session with full repo/build access to trace all callers of `add_distribution`/`distribution_pool.buy_in` to confirm the shareholder cardinality before treating this as high/critical severity.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
