### Title
Webhook shop identity not covered by HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant identity) is read directly from an unauthenticated header. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_tenant_identity`, allowing an unprivileged party who has obtained one valid `(raw_body, hmac)` pair for the app's `client_secret` (e.g. by installing the app on their own store and capturing Shopify's webhook call) to replay that body against the app's webhook endpoint while supplying an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header naming a victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from request headers, independent of the signed bytes: [3](#0-2) 

`Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-only verification) before dispatching the handler with the *header-derived* `shop`: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is shared across all shops that install the app, any actor who installs the app on their own store — an unprivileged action — receives genuine Shopify webhook calls whose `(raw_body, hmac)` pair is valid under that same secret. Since `shop` is excluded from the signed string, that captured `(raw_body, hmac)` pair remains valid when replayed with a different `shopify-shop-domain` header. The library will accept it as authentic and hand the handler a `WebhookMetadata` object whose `shop` field names an arbitrary (victim) shop while the body content actually originated from the attacker's own shop.

The equality that should hold but doesn't:
`shop_used_for_tenant_dispatch (header, unauthenticated) == shop_covered_by_hmac (none, since to_signable_string omits it)`

### Impact Explanation
This is a cross-tenant integrity break at the library layer: the gem hands host applications a `shop` value in `WebhookMetadata` that is *not* cryptographically bound to the payload it certifies as authentic. Any host application that trusts `WebhookMetadata#shop` (the documented, intended way to identify which merchant a webhook concerns) to select the session/store context for processing the webhook body can be made to apply attacker-controlled data under another tenant's identity — e.g., writing forged order/product/customer data attributed to a victim shop, or triggering shop-scoped side effects (uninstall handling, GDPR data requests, etc.) against a shop the attacker doesn't control. This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
The only precondition is that the attacker can install the app on a store they control (a normal, unprivileged flow for any public/embedded Shopify app) and can send arbitrary POST requests with custom headers to the app's public webhook endpoint — both are true for any external, unauthenticated internet user. No access token, `client_secret`, or privileged account is required; the attacker never needs to know the secret, only to capture one legitimately-signed body/hmac pair addressed to their own shop and resend it with a different shop header.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`/`webhook_id`) in the signed material verified against the HMAC, or otherwise cryptographically bind `shop` to the verified body before it is handed to handlers — e.g., compute the signable string from `shop + topic + raw_body` (matching what Shopify actually signs, if it does) rather than `raw_body` alone, so `to_signable_string` cannot be satisfied by a body captured from a different shop's webhook call.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-topic: orders/create`
   - Body: `{...attacker's own fabricated order data...}`
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker replays a POST to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` succeeds because `Webhooks::Request#to_signable_string` only hashes `raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
6. `Registry.process` dispatches the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host app to process attacker-controlled data as belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
