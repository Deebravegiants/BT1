### Title
Accrual arithmetic overflow panics on every market verb and permanently freezes all user funds in a market - ([File: common/src/math/fp.rs])

### Summary
The `get_vlc2` NULL-deref bug class maps onto XOXNO Lending as a **crafted-state crash**: an attacker pushes a market's borrow index into the regime where RAY-scaled value reconstruction overflows `i128`, after which `update_indexes` and every accrual-first verb (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`) panics inside `scaled_to_original`. The market's index cap is supposed to prevent this, but the panic fires *before* the cap engages, so the market is frozen permanently — all suppliers' cash and all borrowers' collateral become unrecoverable.

### Finding Description
Interest accrual reconstructs raw token values from RAY-scaled shares via `checked_add_raw`/`checked_sub_nonneg`-style checked math that panics with `GenericError::MathOverflow` when `scaled_amount * index` exceeds `i128::MAX` (~1.7e38). [1](#0-0) 

The protocol defines `MAX_BORROW_INDEX_RAY` as a cap that should bound index growth, but accrual computes the new index (and unscales balances) *before* the cap check runs. The test-harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proves this ordering bug empirically: a market at ~98% utilization on the steep XLM rate curve drives the borrow index past ~170× in a few years, `update_indexes` then panics with `MATH_OVERFLOW`, and the stored `borrow_index` is still *below* the cap — the cap "did not engage before the value overflow". [2](#0-1) 

Because every state-changing controller entrypoint accrues interest first, the same panic bricks `withdraw` and `repay` for that market (the test asserts both revert with `MATH_OVERFLOW`), and likewise `liquidate`, `clean_bad_debt`, and any route through `apply_liquidation_repayments`, since they all flow through the same accrual path before any state mutation. [3](#0-2)  This is the direct analog of the CVE's NULL-deref crash: an unchecked arithmetic boundary (index × scaled value vs. `i128::MAX`) reached through a normal public entrypoint crashes execution, with the difference that the Soroban panic doesn't just kill one request — the poisoned index is persisted, so it kills *every* future request touching the market.

### Impact Explanation
**Permanent freezing of funds.** Once the index crosses the overflow threshold, every supplier's deposit and every borrower's collateral in that (hub, token) book is locked forever: withdrawals and repayments panic during accrual, and liquidation — the only path to recover underwater collateral — panics for the same reason. There is no admin verb that can rewind the stored index without an upgrade. The overflow is monotonic (indexes only grow), so the freeze is irreversible, matching the "permanent freezing of funds" acceptance criterion rather than a transient fail-closed revert.

### Likelihood Explanation
**Low-to-medium, gated by capital and curve slope, not by permissions.** Triggering requires driving a market to sustained very high utilization with whale-scale balances so index growth compounds past the ~170× boundary within a few years — the harness needed ~1B-unit positions with caps lifted. An attacker cannot unilaterally raise supply/borrow caps, so feasibility depends on a market whose configured caps and token supply permit the required scale (a low-decimal or low-cap market may be unreachable). No privileged call is needed to *detonate* it: `update_indexes` is permissionless, so once ordinary growth plus attacker-supplied utilization cross the threshold, anyone can fire the accrual that freezes the market. Attacker cost is opportunity cost of capital plus whatever positions they cannot exit before the cliff.

### Recommendation
- Check the index cap **before** reconstructing/unscaling values during accrual: compute `new_index`, clamp to `MAX_BORROW_INDEX_RAY`, *then* unscale — so the cap is the guard, not a post-condition that overflow preempts.
- Make the accrual path saturating or explicitly clamping rather than panicking at the `i128` value ceiling; a market must never reach a state where `update_indexes` cannot execute.
- Add a regression boundary test asserting `update_indexes` succeeds (with cap engaged) at `borrow_index` values just below `i128::MAX / scaled_amount` for the largest permitted position size.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`): supply ~1e9·10¹⁸ units of `BIG18`, borrow ~98% of it from a collateralized account, advance time in one-year steps until `try_update_indexes` fails — it returns `errors::MATH_OVERFLOW` with `borrow_index < MAX_BORROW_INDEX_RAY` (cap never engaged). Afterwards `try_withdraw_raw` and `try_repay` also revert with `MATH_OVERFLOW`, demonstrating the permanent freeze of all positions in the market.

fn checked_add_raw(env: &Env, a: i128, b: i128) -> i128 {
    a.checked_add(b)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Subtracts `b` from `a`, panicking with `GenericError::MathOverflow` if either
/// operand is negative or the subtraction would go negative.
fn checked_sub_nonneg(env: &Env, a: i128, b: i128) -> i128 {
    if a < 0 || b < 0 || b > a {
        panic_with_error!(env, GenericError::MathOverflow);
    }
    a - b

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
