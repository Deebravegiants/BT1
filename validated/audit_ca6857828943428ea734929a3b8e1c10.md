### Title
Reused `(outAmounts, erc20TokenAddress, outPublicKey, outTimeStamp)` quadruple produces identical `outCommitments`/nullifiers, permanently freezing the second UTXO - (`contracts/HinkalBase.sol`, `circuits/OriginalCommitmentCalculator.circom`, `circuits/NullifierCalculator.circom`)

### Summary
`OriginalCommitmentCalculator` computes an output commitment as `Poseidon(amount, erc20TokenAddress, publicKey, timeStamp)` with no per-UTXO nonce/blinding factor, and none of these four fields are constrained on-chain to be unique or tied to `block.timestamp`. A prover can therefore submit two separate `transact` calls whose outputs share the same quadruple, producing bit-identical `outCommitments[i][j]`, which `insertCommitments` accepts without any duplicate-leaf check. Because the nullifier is a pure function of `(commitment, nullifyingPrivateKey)`, spending either resulting leaf produces the same nullifier, so redeeming the first leaf permanently blocks redemption of the second, identical-value leaf.

### Finding Description
The equality claimed broken: two distinct leaves `outCommitments[i][j]` from two different `transact` calls end up bit-identical, i.e. `L_a == L_b`, while the Merkle tree treats them as separate leaves at separate indices with separate, spendable balances.

Root cause chain:
- `calcOutCommitment[i][j].out === outCommitments[i][j]` in `circuits/MainEVMCircuit.circom:152-165` only forces the public `outCommitments[i][j]` to equal `Poseidon(outAmounts[i][j], erc20TokenAddresses[i], outPublicKeys[i][j], outTimeStamp)` (`circuits/OriginalCommitmentCalculator.circom:6-23`) — there is no randomness/nonce/leaf-index term.
- `outPublicKeys[i][j]` is a free private witness, never constrained to equal the circuit's own `outStealthAddress` output (computed once, separately, at `circuits/MainEVMCircuit.circom:80-89`); the prover can choose it freely per output.
- `circomData.timeStamp` (mapped to the circuit's public `outTimeStamp`, shared by every output in the call per `circuits/MainEVMCircuit.circom:48`) is copied verbatim into the public input array by `CircomDataBuilder.formBasicInput` (`contracts/CircomDataBuilder.sol:227`) and never checked against `block.timestamp` anywhere in `HinkalHelper.performHinkalChecks` (`contracts/HinkalHelper.sol:208-236`).
- `insertCommitments` (`contracts/HinkalBase.sol:72-133`) inserts whatever leaves are supplied via `insertMany` with no check that a commitment value has never been seen before.
- `NullifierCalculator` (`circuits/NullifierCalculator.circom:6-19`) and `Signature` (`circuits/Signature.circom:5-14`) compute `nullifier = Poseidon(commitment, Poseidon(nullifyingPrivateKey, commitment))`, a function only of `(commitment, nullifyingPrivateKey)` — independent of tree position or Merkle path.
- `insertNullifiers` (`contracts/HinkalBase.sol:135-152`) is the sole double-spend guard and keys exclusively on this nullifier value.

Exploit flow: an unprivileged depositor calls `transact` twice (any two blocks/timestamps, since `timeStamp` is prover-chosen, not `block.timestamp`-derived), each time crafting an output with identical `(outAmounts[i][j], erc20TokenAddresses[i], outPublicKeys[i][j], circomData.timeStamp)`. Both proofs verify independently (each call's own `MainEVMCircuit` constraints are locally satisfied), both `outCommitments[i][j]` values are bit-identical, and `insertCommitments` inserts two leaves `L_a` and `L_b` with the same commitment `C` at different tree indices. Later, when the depositor proves a spend of `C` using their `nullifyingPrivateKey` (with a Merkle path to either `L_a` or `L_b`), the on-chain nullifier is the same regardless of which leaf's path was used. `insertNullifiers` marks that nullifier used on the first spend; any subsequent proof attempting to spend the other, still-unwithdrawn leaf reverts with `"Nullifier cannot be reused"` (`contracts/HinkalBase.sol:143-146`), even though its funds were never paid out.

None of the existing guards catch this: `dimensionsCheck` and `checkOnchainCreation` only validate array shapes; `rootHashExists`/`ForceEqualIfEnabled` only verify the input leaves used for spending are included in some past root, not that output leaves are unique; the balance equations in `Hinkal.sol` (`contracts/Hinkal.sol:134-146`) balance token amounts per-call, not commitment uniqueness across calls; `insertCommitments` performs no duplicate-leaf check.

### Impact Explanation
The second, bit-identical leaf becomes permanently unspendable once the first is redeemed — the deposited value backing it is stranded forever with no code path to release it, matching "permanent freezing of user funds" (Critical). The affected party is the depositor themselves for self-generated collisions, and by the same primitive, any UTXO owner whose wallet software or ephemeral-key selection causes an output quadruple to repeat (e.g., non-random `H0Ax/H0Ay`/`outPublicKeys` reuse combined with prover-controlled `timeStamp`) is exposed identically. This is repeatable per distinct commitment collision the prover chooses to create, at the cost of the deposit itself.

### Likelihood Explanation
Preconditions are trivial for an unprivileged attacker: they only need to call `transact` twice with self-chosen calldata reusing the same `outAmounts[i][j]`, `erc20TokenAddresses[i]`, `outPublicKeys[i][j]`, and `circomData.timeStamp`. No special tree state, no relay/owner privilege, and no interaction with other users is required to freeze one's own second output; generating two snarkjs proofs with matching public/private inputs for the second output is straightforward and costs only the price of two deposit transactions.

### Recommendation
Bind commitment uniqueness to data the prover cannot freely repeat: include a per-output random blinding factor (`rho`)/nonce as a private input hashed into `OriginalCommitmentCalculator`, and/or fold in the current tree insertion index (`m_index`) or a monotonically-enforced `block.timestamp` (verified on-chain rather than accepted as arbitrary calldata) into the commitment. Additionally, add an on-chain guard in `insertCommitments` (or a mapping check prior to `insertMany`) that rejects insertion of a leaf value already present in the tree.

### Proof of Concept
Hardhat fork test plan:
1. Deploy Hinkal stack; fund a test EOA (Attacker) with ERC20 tokens.
2. Construct `CircomData` for `transact` call #1: choose fixed `outAmounts[0][0] = X`, `erc20TokenAddresses[0] = T`, `outTimeStamp = TS`, and a self-chosen `outPublicKeys[0][0] = K` (private witness) and `H0Ax/H0Ay` such that `outCommitments[0][0] = Poseidon(X, T, K, TS)`. Generate a valid snarkjs proof; call `transact`. Capture emitted `NewCommitment(leaf1, index1, ...)`.
3. Construct `CircomData` for `transact` call #2 with identical `X, T, TS, K` (reusing/deriving the same `outPublicKeys` value), generate a second independent valid proof; call `transact`. Capture emitted `NewCommitment(leaf2, index2, ...)`.
4. Assert `leaf1 == leaf2` (the equality claimed broken) while `index1 != index2`.
5. Build a spend proof for `leaf1` using Attacker's `nullifyingPrivateKey`, submit `transact` to redeem it; assert success and that `nullifiers[N]` is set to `true` for the derived nullifier `N`.
6. Build a second spend proof targeting `leaf2` (same commitment `C`, same `nullifyingPrivateKey`, valid Merkle path to index2); submit `transact`; assert it reverts with `"Nullifier cannot be reused"`, proving the second leaf's value is permanently frozen despite never being paid out.
