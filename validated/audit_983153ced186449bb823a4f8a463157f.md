### Title
Untrusted swap-route contracts can join the caller authorization tree and drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Medium severity. The controller accepts an opaque caller-supplied `StrategySwap` byte route and invokes the configured swap router while the account owner or delegate’s authorization is active. [1](#0-0) [2](#0-1) 

If the route executes attacker-chosen third-party code, that code can invoke `token.transfer(victim, attacker, amount)`; an honest simulation records the transfer as an additional child under the victim’s strategy authorization, and enforcement accepts it if the victim signs the expanded tree. [3](#0-2) [4](#0-3) 

### Finding Description
The reachable entrypoints are `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, each accepting attacker-influenceable `Bytes` route data and requiring owner or delegate authorization. [5](#0-4) [6](#0-5) [7](#0-6) 

For example, `swap_collateral` authorizes the caller, verifies account authority, withdraws collateral, and passes the supplied route into `withdraw_and_swap_from_supply`. [8](#0-7) 

`withdraw_and_swap_from_supply` forwards the same route to `swap_tokens_or_passthrough`. [9](#0-8) 

The swap boundary grants only the controller’s exact `token_in.transfer(controller, router, amount_in)` invocation and then calls `router.execute_strategy(controller, amount_in, swap)`. [10](#0-9) [11](#0-10) 

Those checks bound the controller’s routed input and measured output, but they do not prevent third-party code reached by the opaque route from making a separate caller-authorized token transfer. [12](#0-11) [13](#0-12) 

### Impact Explanation
A malicious route can steal unrelated tokens held directly by the caller, including tokens that are neither supplied collateral nor listed protocol assets. [14](#0-13) [15](#0-14) 

The swap can still deliver a fair protocol output and pass positive-output and final-risk checks, so the strategy succeeds while the hidden wallet transfer drains the victim. [16](#0-15) [17](#0-16) 

This is theft of user funds beyond the declared swap input and therefore matches the Li.finance arbitrary-route/calldata bug class. [13](#0-12) 

### Likelihood Explanation
An attacker can construct and distribute the malicious route without privileged access, but exploitation requires the account owner or delegate to submit and sign it. [18](#0-17) [19](#0-18) 

The attack is feasible because the encoded route is opaque to the controller, while the additional wallet transfer appears only as an authorization-tree child during simulation or signing. [2](#0-1) [20](#0-19) 

A wallet or client that signs the simulation-produced tree without rejecting unexpected child invocations enables the theft. [13](#0-12) 

### Recommendation
Require route venue/pool addresses to resolve through an explicit governance-controlled allowlist before execution, and reject routes containing unapproved call targets rather than treating route bytes as an opaque trusted program. [10](#0-9) [21](#0-20) 

As immediate client-side mitigation, simulate every strategy transaction and reject any caller authorization tree containing children other than the expected account operation and input transfer. [22](#0-21) 

### Proof of Concept
1. Alice owns a debt-free account with USDC collateral and also holds an unrelated wallet token not listed by the protocol. [23](#0-22) 
2. The attacker supplies a `swap_collateral(caller=Alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)` route whose venue call reaches attacker-deployed code. [24](#0-23) [25](#0-24) 
3. The attacker code calls `token.transfer(Alice, attacker, WALLET_BALANCE)` while the strategy authorization is active. [26](#0-25) 
4. Simulation records that transfer as a child under Alice’s `swap_collateral` authorization while the route still pays the expected ETH output. [27](#0-26) 
5. If Alice signs that poisoned tree, enforcing mode executes the unrelated transfer, leaving Alice’s wallet-token balance at zero and the attacker’s balance at `WALLET_BALANCE`. [28](#0-27)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
