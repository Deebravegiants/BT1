### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant identification despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw HTTP body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only the body-derived HMAC and then unconditionally forwards `request.shop` (and the other header-derived fields) to the app's handler as trusted tenant-identifying metadata: [3](#0-2) 

The gem's own documentation instructs app authors to treat `data.shop` as "The shop domain of the webhook" and to use it directly for tenant-scoped work (e.g., `shop_domain: data.shop`) without any additional cross-check: [4](#0-3) 

The binding that should hold is: `verified_bytes == (body, shop, topic)`, i.e., the cryptographic verification should cover every field that is subsequently *acted upon* as an authenticated tenant identifier. Instead, the actual binding enforced is only `verified_bytes == raw_body`, while `claimed_shop` is an arbitrary, unauthenticated header value with no cryptographic tie to the signed body.

### Impact Explanation
Any actor capable of triggering (or having received) one validly HMAC-signed webhook body for a given topic — which, notably, is not limited to Shopify itself in every deployment, since the gem never checks the header against the body content — can replay that exact `raw_body` + `hmac-sha256` header pair while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will accept the request as valid (the HMAC check only validates the body against the app's `client_secret`) and dispatch it to the registered handler labeled with the attacker-chosen `shop`. Since the gem's documented API explicitly encourages developers to key persistence, queuing, and business logic off `data.shop` (`WebhookMetadata#shop`), this allows cross-tenant data confusion: a webhook payload can be attributed to a shop it never originated from, corrupting tenant-scoped processing, job queues, or datastores keyed by `shop`. This falls under "cross-tenant access," a Critical-impact category per the rules.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that logs, proxies, retries, or otherwise persists raw webhook deliveries (a very common operational pattern, e.g. queueing raw payloads for reprocessing, replaying stored webhook fixtures, or handling webhook forwarding infrastructure), since nothing in the gem enforces that the `shop-domain` header travels attached to the exact HMAC-verified body it was originally delivered with. No access token, `api_secret_key`, or privileged credential is required — only possession of one previously-delivered valid `(body, hmac)` pair, which is routinely visible in logs, retries, or shared infrastructure.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify the header-declared shop against an application-registered set of expected values, or fold the headers into the HMAC digest calculation in `VerifiableQuery#to_signable_string`). At minimum, document prominently that `data.shop` and `data.topic` are unauthenticated and must not be trusted for tenant selection without an independent binding check.

### Proof of Concept
1. App receives a legitimate webhook delivery for `shop-A.myshopify.com` with body `B` and a valid `hmac-sha256` header `H = HMAC(secret, B)` computed per `lib/shopify_api/webhooks/request.rb:35-38`.
2. An intermediary/log/queue exposes `(B, H)` (common in retry/replay tooling, shared proxies, or webhook forwarding setups).
3. Attacker resends a request to the app's webhook endpoint with the same raw body `B` and the same `hmac-sha256` header `H`, but sets `shopify-shop-domain: shop-B.myshopify.com` (a different tenant).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), independent of any header.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "shop-B.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process shop-A's data as if it belonged to shop-B.
