## Missing reentrancy guard analog found in Hyperbridge's Tron `IntentGatewayV2`

### Title
Tron `IntentGatewayV2` fill/withdraw flow lacks a reentrancy guard present in its EVM sibling - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2` inherits OpenZeppelin's `ReentrancyGuardTransient` and applies checks-effects-interactions (CEI) fixes specifically because prior reentrancy issues were found and fixed in its fill logic (documented by the dedicated regression suite `IntrinsicIntentsReentrancyTest.sol`). The parallel Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not inherit any reentrancy guard at all.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol` declares: [1](#0-0) [2](#0-1) 

using `ReentrancyGuardTransient` (EIP‑1153 transient-storage based guard), which is required after a previously-fixed reentrancy vulnerability in `_fillSameChain`/`_fillCrossChain`. The regression test suite explicitly documents the pre-fix attack window where a malicious beneficiary's `receive()` callback (triggered by a native-ETH payout) could re-enter `fillOrder` before `_filled[commitment]` was set: [3](#0-2) 

The Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` re-implements the same intent-fulfillment logic as a standalone contract (`contract IntentGatewayV2 is HyperApp, EIP712`) but does **not** inherit `ReentrancyGuardTransient` or any other reentrancy lock: [4](#0-3) 

This is a meaningful gap because EIP-1153 transient storage (`TSTORE`/`TLOAD`), which `ReentrancyGuardTransient` depends on, is not guaranteed to be supported identically on the TVM (Tron Virtual Machine) — which is presumably why this contract was forked into a separate Solidity file rather than reused directly — yet no alternative (e.g., a standard storage-based `nonReentrant` modifier) was substituted. The file retains the same escrow/withdrawal state machine, including low-level native-token payouts to externally-controlled beneficiaries (`.call{value: amount}("")`) inside the withdrawal/fill paths that were the original source of the reentrancy bug on the EVM side: [5](#0-4) 

### Impact Explanation
If the same-chain/cross-chain fill entrypoints in this Tron contract do not consistently apply the CEI ordering fix that was retrofitted into the EVM `IntrinsicIntents`/`ExtrinsicIntents` libraries (setting `_filled[commitment]` before any external native-token transfer), a malicious beneficiary contract can re-enter `fillOrder` during the native payout callback to double-claim escrowed input tokens or transaction fees — the exact theft scenario (`testReentrancy_FeeTheft`, `testReentrancy_EscrowTheft_MultiOutput`) that the EVM regression suite was written to prevent. This would result in direct theft of escrowed user funds on the Tron deployment.

### Likelihood Explanation
Medium-to-High: the reachability requires only a single `fillOrder` transaction from an unprivileged solver where the beneficiary is a malicious contract, exactly mirroring the previously real (and fixed) EVM bug. Likelihood is tempered because I was unable to fully confirm, within tool budget, whether the Tron file's `fillOrder`/`_filled` assignment ordering independently replicates the CEI fix without relying on `ReentrancyGuardTransient` — the `withdraw` internal function I was able to inspect does set `_filled[body.commitment]` before the transfer loop, which is CEI-compliant for that specific inbound-message path. I could not verify the ordering in the local (non-message) fill path within the available iterations.

### Recommendation
- Audit every function in `evm/tron/contracts/apps/IntentGatewayV2.sol` that performs a native/ERC20 transfer to an order-supplied beneficiary (fill, withdraw, sweep-dust) and confirm `_filled[commitment]` (or an equivalent lock) is written **before** any external call.
- Since TVM support for EIP-1153 transient storage is uncertain, add an explicit standard-storage `nonReentrant` modifier (OpenZeppelin's non-transient `ReentrancyGuard`) to this contract rather than relying solely on CEI ordering, to match the defense-in-depth used on the EVM deployment.

### Proof of Concept
Not independently reproduced against the Tron contract within the available investigation; the attack pattern to replicate is the one already proven against the pre-fix EVM contract in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` (`ReentrantBeneficiary.receive()` re-entering `fillOrder` during the native ETH/TRX payout, lines 50-83), which should be ported as a Tron-side Foundry/TVM test to confirm whether the same reentrant self-fill is possible against `evm/tron/contracts/apps/IntentGatewayV2.sol`. [6](#0-5)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
