### Title
Solver's proportional escrow share silently rounds to zero and is skipped without reverting during same-chain partial fills - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the solver's proportional escrow entitlement for a partial fill as `(order.inputs[i].amount * fillAmount) / totalRequired`, and passes the result to `IntentsBase._withdraw`, which silently `continue`s (skips the transfer entirely) whenever the computed amount is `0`, instead of reverting. A solver can pay the full output amount to the beneficiary but receive zero input tokens back if the rounding truncates to zero, and the transaction still succeeds.

### Finding Description
In `_fillSameChain`, the proportional escrow released for a partial fill is: [1](#0-0) 

For a small `fillAmount` relative to `totalRequired`, integer division floors `escrowedAmount` to `0` whenever `order.inputs[i].amount * fillAmount < totalRequired`. This `TokenInfo{amount: 0}` is included in `escrowedInputs`, which is forwarded to `_withdraw`: [2](#0-1) 

`_withdraw` explicitly skips any zero-amount token entry without reverting and without decrementing the escrow mapping: [3](#0-2) 

Meanwhile, before this proportional computation runs, the solver has already fully paid the beneficiary the requested output amount for that fill: [4](#0-3) 

and the fill is recorded as a legitimate `PartialFill` (cumulative fill state is advanced, an event is emitted), even though the solver received nothing in exchange: [5](#0-4) [6](#0-5) 

This directly mirrors the reported bug class: a proportional-share calculation that can legitimately evaluate to zero is not guarded by a revert, so the state-mutating side of the operation (paying the beneficiary, advancing partial-fill accounting) proceeds while the compensating transfer silently no-ops.

### Impact Explanation
Any unprivileged party calling `fillOrder` (the reachable, unprivileged entrypoint for `_fillSameChain`) with a sufficiently small `solverAmount`/`fillAmount` relative to the order's output/input ratio pays full output value to the beneficiary and receives zero input tokens in return — a real, uncompensated loss of the caller's funds with no revert to protect them. Because there is no minimum fill-size enforcement and no explicit check that the computed `escrowedAmount` is non-zero for a non-zero `fillAmount`, this can also be used to grief an order: an attacker can submit a minimal partial fill purely to advance `_partialFills` accounting and consume part of the fill window while contributing negligible real value, with the truncation loss falling on themselves or a targeted party who is induced to fill in small increments.

### Likelihood Explanation
Reaching this path requires only a single unprivileged `fillOrder` call on an existing same-chain order with a partial-fill size chosen (or induced) small enough that `order.inputs[i].amount * fillAmount < totalRequired`. This condition is common for any order pair where the input token amount is smaller than or comparable to the output token amount and a solver fills a small fraction of the order — no special privileges, timing, or governance action is needed.

### Recommendation
In `_fillSameChain`, revert (or reject the fill) when the computed `escrowedAmount` for a non-final partial fill rounds to zero for a non-zero `fillAmount`, e.g. `if (escrowedAmount == 0) revert InvalidInput();` before constructing `escrowedInputs[i]`. Alternatively, enforce a minimum fill amount that guarantees `order.inputs[i].amount * fillAmount >= totalRequired`, or track fractional remainders across partial fills so no solver's contribution is ever compensated with zero tokens without an explicit revert.

### Proof of Concept
1. Place a same-chain order with `inputs[0].amount = 100` and `output.assets[0].amount = 1_000_000` (`totalRequired`).
2. A solver calls `fillOrder` with `options.outputs[0].amount = 1` (a tiny, valid, non-zero partial fill: `remaining=1_000_000 > 0`, `solverAmount=1 != 0`, so it is accepted).
3. `fillAmount = 1`; `escrowedAmount = (100 * 1) / 1_000_000 = 0` (Solidity integer division).
4. The solver's `beneficiaryTotal = fillAmount = 1` output token is transferred to the beneficiary via `safeTransferFrom` in `_fillSameChain`.
5. `_withdraw` receives `TokenInfo{amount: 0}` for the input token and executes `if (amount == 0) continue;`, transferring nothing to the solver and not reverting.
6. The transaction succeeds, `PartialFill` is emitted, and the solver has paid `1` unit of output token for `0` units of escrowed input token, with no revert protecting them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
