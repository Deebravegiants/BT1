### Title
Unvalidated strategy route bytes can inject a caller-authorized token transfer through a nested venue call - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller treats `swap` as opaque bytes and forwards it to the configured router while relying only on input-spend and output-receipt measurements. A route-selected contract can therefore perform an additional token transfer requiring the caller’s authorization; if the victim signs the poisoned authorization tree produced during simulation, that transfer moves arbitrary wallet tokens to an attacker. This maps the command-injection class onto Soroban authorization-tree injection rather than shell execution.

### Finding Description
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all accept caller-controlled `Bytes`/`StrategySwap` payloads, while `StrategySwap` is only an alias for raw `Bytes` with no controller-side route validation. [1](#0-0)  For example, `swap_collateral` authenticates the caller, verifies account ownership, and passes the uninterpreted `swap` payload into `withdraw_and_swap_from_supply`. [2](#0-1) 

`swap_tokens` forwards that payload to `router.execute_strategy` and subsequently checks only the controller’s token-input decrease and token-output increase. [3](#0-2)  Those checks do not constrain which contracts the route invokes or prevent such a contract from adding a caller-authorized transfer below the controller call. [4](#0-3) 

The regression fixture demonstrates the issue directly: a route identifies an attacker-controlled `hop_pool`, the router invokes it, and that contract calls `token.transfer(victim, attacker, amount)` for an unrelated wallet asset. [5](#0-4)  Simulation records the malicious transfer as a child invocation under the victim’s `swap_collateral` authorization, and signing that tree causes the victim’s full unrelated-token balance to move to the attacker. [6](#0-5) 

### Impact Explanation
A malicious route can steal wallet tokens that were never supplied to the lending protocol and are unrelated to the requested swap. [7](#0-6)  The exploit succeeds even though the strategy returns a fair collateral amount and the account’s final solvency checks pass, because the theft occurs as an authorization side effect rather than as a lending-account balance change. [8](#0-7) 

### Likelihood Explanation
The attacker must induce the victim to execute a strategy using attacker-constructed route bytes and sign the authorization tree containing the injected transfer. [9](#0-8)  The victim’s own signature is required: a route attempting the transfer under a normal root-only authorization tree is rejected and rolled back. [10](#0-9)  This makes the issue a user-funds theft vector rather than a permissionless protocol-drain, but the opaque route bytes and simulated authorization tree make the extra child invocation difficult for users to audit.

### Recommendation
Do not forward arbitrary opaque routes without constraining the external contracts they may reach. Restrict route venues/pools through a protocol-managed allowlist or another router mechanism that prevents arbitrary contract invocation beneath the caller’s authorization, and require wallets or quote integrations to reject any authorization tree containing children beyond the expected input transfer. At minimum, document and enforce at the client boundary that controller strategy authorization trees must contain no unrelated token-transfer children. [11](#0-10) 

### Proof of Concept
1. Deploy a malicious “pool” contract whose `swap` function reads a stored `(victim, token, attacker, amount)` plan and calls `token.transfer(victim, attacker, amount)`. [12](#0-11) 
2. Construct route bytes naming that contract as a hop while preserving a fair `token_out` payment. [13](#0-12) 
3. Have the victim call `swap_collateral(caller=victim, account_id, current=USDC-market, amount, new=ETH-market, swap=route)`. [14](#0-13) 
4. Simulation records `token.transfer(victim, attacker, victim_wallet_balance)` beneath the victim’s `swap_collateral` authorization. [15](#0-14) 
5. Submitting the transaction with that signed tree leaves the victim’s unrelated wallet-token balance at zero and gives the full amount to the attacker, while the swap still deposits the fair `ETH` output. [16](#0-15)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
