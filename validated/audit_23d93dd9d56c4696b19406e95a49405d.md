### Title
Webhook shop-domain, topic, api-version and webhook-id are trusted despite not being covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers and then acted on by `Registry.process` without ever being covered by the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, `shopify-webhook-id`) that are completely outside the HMAC computation [2](#0-1) .

`Registry.process` validates only that `Utils::HmacValidator.validate(request)` succeeds — i.e., that the body's HMAC matches the app's `api_secret_key` — and then dispatches to the handler using `request.topic` and `request.shop`, both taken from the unauthenticated headers [3](#0-2) . `HmacValidator.validate` in turn calls `verifiable_query.to_signable_string`, which for a webhook request is body-only [4](#0-3) .

Because the same `api_secret_key` is used for HMAC across all shops installed on a given app (single-tenant app credential, multi-tenant shops), any actor who can install the app on their own store (an unprivileged internet user, not requiring the app's `client_secret` or any privileged account) can:
1. Trigger a legitimate webhook delivery on their own shop (e.g., create an order), obtaining a request with a genuinely valid `hmac-sha256` value for a known raw body.
2. Replay that exact raw body and HMAC to the app's webhook endpoint, but with the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header rewritten to point at a different, victim shop.

The HMAC check in `Registry.process` still passes because it only validates the raw body — it never verifies that `shop`/`topic` were the values Shopify actually attached to that specific signed payload. Any downstream handler code that trusts `WebhookMetadata#shop` to select the tenant record to update (a documented, intended usage pattern of this gem's `handler.handle(data: WebhookMetadata.new(topic:, shop:, ...))` call) will act on attacker-supplied tenant data using a signature that was never bound to that tenant. This breaks the identity binding: `shop` used to select the tenant == `shop` authenticated by the HMAC, which does not hold here.

### Impact Explanation
This allows cross-tenant confusion: an attacker with their own (unprivileged) shop installation can cause the app to process webhook events (and any resulting side effects, e.g. data sync, order/customer updates) as if they originated from an arbitrary victim `shop-domain`, while still passing this gem's HMAC validation. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (shop identity) is not actually authenticated by the cryptographic check the library performs.

### Likelihood Explanation
Likelihood is bound by how a host application uses `WebhookMetadata#shop`/`#topic`: apps that trust these fields for tenant selection (the intended, documented way to consume `Registry.process`) are directly affected. The attacker only needs their own legitimate shop install to obtain a valid `(raw_body, hmac)` pair and the ability to send an HTTP request directly to the app's public webhook endpoint with modified headers — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-covered signable content, or otherwise cryptographically bind the shop/topic to the signed body (e.g., via a canonical string that includes these header values before hashing), matching what `Auth::Oauth::AuthQuery#to_signable_string` does by including all identity-relevant fields (`code, host, shop, state, timestamp`) in its signable string [5](#0-4) . At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a known/stored shop from a prior OAuth session).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (an unprivileged action any merchant can perform) and configures a webhook (e.g. `orders/create`) via `Registry.register`.
2. Attacker creates an order on their own shop; Shopify sends a POST to the app's webhook path with headers:
   - `shopify-topic: orders/create`
   - `shopify-hmac-sha256: <valid HMAC of raw body, computed with the app's api_secret_key>`
   - `shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{"id": 123, ...}`
3. Attacker captures this exact `(raw_body, hmac-sha256)` pair.
4. Attacker replays the same raw body and `hmac-sha256` header directly to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [1](#0-0)  — this still matches, since the body and secret are unchanged.
6. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it belongs to the victim tenant.
