### Title
Webhook `shop` identity is derived from an unauthenticated header not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value read directly from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to that value: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)` and then constructs `WebhookMetadata` using `request.shop`, passing it to the app-supplied handler as the trusted tenant identity: [3](#0-2) 

The identity binding that should hold is: `shop bound by HMAC == shop used by handler`. Instead, only the body is authenticated (`HMAC(body) == received_hmac`), while `shop` is taken from an attacker-controllable header outside that computation. Because the HMAC is computed with the app's `api_secret_key` over the body only, any body+HMAC pair the attacker can legitimately obtain (e.g., a genuine webhook delivered for the attacker's own shop, which is installed on the same app) remains valid for *any* `x-shopify-shop-domain` value the attacker chooses to send. The documentation itself instructs handler authors to treat `data.shop` as the authoritative tenant identifier (`docs/usage/webhooks.md:12-27`), reinforcing that downstream apps rely on this field for tenant routing without additional verification, exactly the "field acted on but not covered by the HMAC" break in identity binding.

### Impact Explanation
An attacker who has legitimately received one valid webhook body+HMAC pair for their own (attacker-controlled) shop installation of the app can replay that exact payload to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` header to any victim merchant's domain. Because `Registry.process` only checks the HMAC of the body, the forged request passes validation, and the handler is invoked with `WebhookMetadata#shop` set to the victim's shop. Any app that uses `data.shop` to determine which merchant's records to create, update, or associate data with (the pattern explicitly recommended in the gem's own documentation) will misattribute the webhook body to the wrong tenant — a cross-tenant data injection/confusion vulnerability rooted in this gem's own webhook processing code.

### Likelihood Explanation
The attack requires only that the attacker control one shop that has the target app installed (a low bar for any public/multi-tenant Shopify app), and one accepted webhook topic whose body content is attacker-influenceable or at least reusable across shops (many webhook bodies, e.g., `app/uninstalled`, contain no shop-specific secret and are simple to replay). No access token, `client_secret`, or privileged credential is required — an unprivileged internet user who can install the app on their own store can mount this.

### Recommendation
Bind the `shop` (and ideally `topic`) into the signed/verified material, or independently verify the `x-shopify-shop-domain` header against a known set of shops the app is actually installed on before trusting it in `WebhookMetadata`. At minimum, document/require that the header's shop value not be treated as authoritative on its own since the current HMAC does not cover it, and consider extending `VerifiableQuery`/`to_signable_string` for webhooks to include shop domain and topic in the value hashed for comparison, matching how Shopify itself binds these fields at the platform level.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event whose body is attacker-controlled or reusable (e.g., an event with generic content, or captures any legitimate webhook body/HMAC issued for their shop).
3. Attacker sends a forged HTTP POST to the app's webhook endpoint with:
   - Body: the captured/legitimate raw body bytes (unchanged, so `HMAC-SHA256(body, api_secret_key)` remains valid)
   - Header `x-shopify-hmac-sha256`: the original, still-valid signature for that body
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (replacing the attacker's own domain)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds, because it only re-computes the HMAC over `@raw_body`.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's body> ...)`, i.e., the app processes attacker-supplied webhook content as if it originated from the victim's shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
