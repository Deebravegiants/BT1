### Title
Unprotected spot-price AMM swap in `EvmHost.dispatch()`/`fundRequest()` enables fee-payment manipulation and dispatch griefing - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` convert a user's native-token payment into `feeToken` by calling `IUniswapV2Router02.swapETHForExactTokens` directly against the live reserves of the configured `uniswapV2` pool, with no TWAP, no minimum-output guard beyond the caller-chosen `msg.value`, and a `deadline` of `block.timestamp` (i.e. no real deadline protection). This is the same root-cause bug class as the reported `underlying()`/`underlyingMint()` finding: a critical value (here, the ETH cost of a cross-chain dispatch fee) is derived from a single manipulable on-chain spot price instead of a manipulation-resistant oracle.

### Finding Description
`dispatch()` swaps native ETH for an exact amount of `feeToken` (`post.fee`) using the pool's current reserves: [1](#0-0) 

The same unguarded pattern recurs in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

The companion `HyperApp.quote()` helper, used off-chain and on-chain by apps (e.g. `HyperFungibleToken`) to size `msg.value` for a dispatch, similarly reads the router's live `getAmountsIn` reserve ratio with no staleness or TWAP check: [4](#0-3) 

`IntentGatewayV2` uses the identical live-swap pattern to escrow order fees: [5](#0-4) 

Because the Uniswap V2 pool's reserves are the sole price input and there is no bound on acceptable slippage other than the amount of ETH the caller happens to send, an attacker can sandwich a victim's `dispatch()` call: push the pool price against the feeToken/WETH pair with a flash-loan swap immediately before the victim's transaction, let the victim's `swapETHForExactTokens` execute at the manipulated price, then reverse the price-push swap and capture the difference. Any leftover ETH from the swap is refunded by the router to `address(this)` (`EvmHost`), not to `_msgSender()`, so victims who supply a safety margin above the fair-value fee lose that margin to the contract/attacker rather than getting it back.

### Impact Explanation
- **Fee overpayment / value extraction**: A sandwiching attacker can force the dispatching account to pay substantially more ETH than fair value for the same `feeToken` amount, extracting the price-impact spread as MEV profit at the sender's expense — a direct value-theft path reachable from any single `dispatch()` transaction that pays with native token.
- **Denial of message delivery**: If the manipulated price makes the required ETH-in exceed the `msg.value` supplied, `swapETHForExactTokens` reverts, causing the entire `dispatch()` call (and therefore the cross-chain message submission) to fail — a route made unable to deliver messages, which is an explicitly accepted impact category for this reachable surface.
- This affects `EvmHost.dispatch()`/`fundRequest()`, which are the primary unprivileged entry points for message dispatch on Hyperbridge, as well as `IntentGatewayV2.placeOrder()`'s fee-escrow path.

### Likelihood Explanation
Uniswap V2 pools configured as the `uniswapV2Router`/fee-token pair are typically shallow relative to flash-loan capital, and any address can call `dispatch()` with `msg.value` at any time; sandwiching a pending `dispatch()` transaction requires only standard front-run/back-run MEV tooling, no privileged role, and no special network conditions. The attack is fully executable within ordinary transaction ordering on public EVM chains where Hyperbridge is deployed.

### Recommendation
Do not size or execute the native→feeToken conversion from the pool's instantaneous reserves alone. Either (a) require callers to pre-quote off-chain and pass an explicit `amountInMax`/slippage bound enforced on-chain, (b) use a TWAP-based price for computing the expected ETH cost and revert if the live quote deviates beyond a bounded tolerance, or (c) route the refund from `swapETHForExactTokens` back to `_msgSender()` explicitly and clamp acceptable slippage so a manipulated quote cannot silently overcharge the sender.

### Proof of Concept
1. Attacker takes a flash loan and swaps a large amount of WETH → `feeToken` (or vice versa) on the pool configured as `EvmHost.uniswapV2()`, moving the spot price sharply.
2. Victim's `dispatch(DispatchPost)` transaction (already in the mempool, paying with `msg.value`) executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` against the now-skewed reserves — either consuming far more ETH than fair value for `post.fee` tokens, or reverting outright if `msg.value` is insufficient at the manipulated price.
3. Attacker reverses their initial swap in the same block, repays the flash loan, and pockets the price-impact spread extracted from the victim's swap (or, in the revert case, the victim's cross-chain message dispatch is denied for that block).

**Uncertainty**: I could not fully verify from the indexed code whether any downstream logic elsewhere refunds excess ETH captured by `address(this)` back to `_msgSender()` after the swap in `dispatch()`; the snippets reviewed show no such refund within `dispatch()` itself. Confirming this — and checking whether `uniswapV2` is realistically a thin/manipulable pool per deployed chain configs — would benefit from a full Devin session with repository access, since the indexer may not surface all downstream contract logic.
