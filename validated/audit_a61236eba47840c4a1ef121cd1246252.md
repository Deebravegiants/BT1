### Title
Webhook `shop-domain` header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking an HMAC computed over the raw request body. The `shop` (and `topic`, `webhook_id`) values are read straight out of unauthenticated HTTP headers and handed to the app's webhook handler as trusted tenant identity, without being covered by the signature that was just verified.

### Finding Description
The reentrancy report's underlying pattern is "state trusted for one purpose is used for another before/without being properly bound." The analogous break here is an identity-binding gap: the equality that should hold is `hmac == HMAC(secret, body ‖ shop ‖ topic)`, but the gem only checks `hmac == HMAC(secret, body)`.

`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` verify exactly that signable string against the secret, with no other fields folded in: [2](#0-1) 

`Registry.process` performs only this body-only HMAC check, then immediately trusts `request.shop` (parsed from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, with no cryptographic binding to the signature) and forwards it to the app's handler as the tenant identity: [3](#0-2) 

The `shop` accessor is a bare header read: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant/shop that has installed the app, any shop that has installed the app can observe a legitimate `(body, hmac)` pair delivered to its own webhook endpoint. That exact `(body, hmac)` pair remains valid for `Registry.process` no matter what `shop-domain` header accompanies it, since the header is never part of the signed material.

### Impact Explanation
An attacker who controls one tenant of the app (a free/dev shop that installs the app — an "unprivileged internet user" relative to other merchants) can replay a body+HMAC pair they legitimately received while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Registry.process` will accept the HMAC (it never checked the shop) and dispatch to the handler with `shop: <victim-shop>`. Any host application relying on `WebhookMetadata#shop` from this gem to key session/tenant lookups (the documented pattern shown throughout the webhook API) will process attacker-supplied data as if it originated from, or apply mutations to, the victim tenant — a cross-tenant access break, satisfying the Critical impact bar.

### Likelihood Explanation
Likely to be reachable in any app using this gem's documented `Registry.process` webhook pipeline: it requires no possession of the target's secret and no MITM — only that the attacker themselves has (or creates) an app installation to observe one valid signed webhook body, then replays it with a forged shop header. This is a realistic capability for any unprivileged actor able to install the app on a shop they control.

### Recommendation
Fold the shop domain (and ideally topic/webhook id) into the signable string verified by `HmacValidator`, or independently verify that `request.shop` corresponds to a shop the app has an active session/installation for before trusting it in `WebhookMetadata`. At minimum, document and enforce that `Registry.process` callers must not use the header-derived `shop` as an authenticated tenant key without an additional installation/session check.

### Proof of Concept
1. App has two shops installed: `victim.myshopify.com` and `attacker.myshopify.com` (attacker owns the latter).
2. Shopify delivers a webhook to the app for `attacker.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`, body `B`.
3. Attacker captures `(B, HMAC)` and replays the request to the app's webhook endpoint, changing only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`, keeping `x-shopify-hmac-sha256` and body `B` unchanged.
4. `HmacValidator.validate` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `HMAC(secret, B)`.
5. `Registry.process` (per `lib/shopify_api/webhooks/registry.rb:188-200`) calls the handler with `shop: "victim.myshopify.com"`, causing the host app to act on data as if it came from the victim tenant.
