## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `shop` value parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header as a verified tenant identifier once `Utils::HmacValidator.validate` succeeds, but the HMAC only ever signs the raw request body, never the shop header. A holder of any single valid `(body, hmac)` pair for the app (trivially obtained by any merchant who has installed the app and received one real webhook) can replay that pair with a forged `shop-domain` header and have it accepted as an event for a different tenant.

## Finding Description
`Registry.process` gates all further processing on a single check: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which validates the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — the `shop`, `topic`, `webhook_id`, and `api_version` headers are excluded from the signed material: [3](#0-2) 

After the HMAC check passes, `request.shop` (parsed straight from the unauthenticated header) is forwarded as the trusted tenant identifier to the handler: [4](#0-3) 

The gem's own documentation instructs developers to treat `data.shop` as the verified shop domain of the webhook once `Registry.process` has run ("This will verify the request did indeed come from Shopify"), and lists `shop` as an authoritative field of `WebhookMetadata`: [5](#0-4) [6](#0-5) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop authenticated by HMAC` ≠ `shop consumed by the handler as WebhookMetadata#shop`.

Because Shopify apps share a single `client_secret` (`Context.api_secret_key`) across every shop that installs the app, any merchant who is a legitimate (but low-trust, unprivileged w.r.t. other tenants) install of the app can capture one real, correctly-signed webhook delivered to their own callback URL for their own shop. Since the signature covers only the body, that same `(raw_body, hmac)` pair remains valid for any header combination. The attacker can resend the identical body/HMAC to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming the event is for the victim's shop.

## Impact Explanation
This is a cross-tenant boundary violation: an actor scoped to Shop A's installation can make the host application believe and act on data as if it originated from Shop B. Any app that keys its per-shop persistence, job dispatch, or business logic off `WebhookMetadata#shop` (exactly as the documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can have Shop A's attacker-controlled payload processed and stored under Shop B's tenant, corrupting Shop B's data or triggering actions attributed to Shop B. This matches the "cross-tenant access" criterion.

## Likelihood Explanation
Exploitation requires only that the attacker has (or once had) a legitimate installation of the target app receiving at least one real webhook — a low bar for any SaaS app with self-serve installs. No access to `api_secret_key`, access tokens, or Shopify infrastructure is needed; the attacker only replays a body+signature pair they legitimately possess while forging an unauthenticated header, which is directly reachable through the app's public webhook endpoint.

## Recommendation
Bind the tenant identity into the verified material: either include `shop`, `topic`, and `webhook_id` in the HMAC-signed string (would require Shopify platform changes), or — within this gem — require callers to supply the expected shop for the webhook out-of-band (e.g., cross-check `request.shop` against the shop associated with the registered webhook path/session before invoking the handler), and document clearly that `WebhookMetadata#shop` is not itself cryptographically authenticated by the HMAC check.

## Proof of Concept
1. App "ExampleApp" is installed by Shop A and Shop B, both sharing the same `Context.api_secret_key`.
2. Shopify sends a legitimate webhook to ExampleApp's callback for Shop A: body `{"id":123}`, header `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
3. Attacker (owner/operator of Shop A) captures this request.
4. Attacker resends the identical body and HMAC header to the same callback URL, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks the (unchanged) body against the (unchanged) HMAC — validation succeeds: [1](#0-0) 
6. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload was authored/originated for Shop A, demonstrating cross-tenant spoofing.

```ruby
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
```

```ruby
          received_signature = verifiable_query.hmac
```

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
