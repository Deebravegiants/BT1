### Title
Webhook shop/topic identity not covered by HMAC allows cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to dispatch and attribute the webhook are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body HMAC and then trusts those header-derived values when building `WebhookMetadata` and invoking the app's handler, breaking the binding between "bytes verified" and "identity acted on."

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors, by contrast, are pulled straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`Registry.process` checks `Utils::HmacValidator.validate(request)` — which only proves the body bytes weren't tampered with — and then unconditionally forwards the header-derived `shop`/`topic`/`api_version`/`webhook_id` into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant/event identity: [3](#0-2) 

`HmacValidator.validate` itself only compares the `hmac` value against a signature computed from `to_signable_string`, so it can never catch a header substitution, since headers are excluded from the signable input: [4](#0-3) 

**The broken equality:** the gem should guarantee `shop-that-produced-the-signed-bytes == shop-attributed-to-the-processed-event`. Because `shop` (and `topic`/`webhook_id`/`api_version`) sit outside the HMAC's signed input, an attacker who possesses *any* validly-signed `(body, hmac)` pair — trivially obtainable by installing the target app on their own store and capturing one of their own legitimate webhook deliveries — can replay that same body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature still validates (it only covers the body), yet `Registry.process` dispatches the handler with `data.shop` set to the attacker-chosen victim domain. This is exactly the "field acted on but not covered by the HMAC" class described in the report's bug analogy — here, `shop`/`topic` are the unauthenticated fields, analogous to `totalDecayRate` being updated with data computed under stale/desynced state before the security-relevant check is finalized.

This differs from `Auth::Oauth::AuthQuery`, which correctly includes `shop`, `code`, `host`, `state`, and `timestamp` in its `to_signable_string`, so all identity-relevant fields there are bound to the HMAC: [5](#0-4) 

### Impact Explanation
An app relying on `Registry.process`/`WebhookMetadata#shop` to key persistence, billing, or entitlement decisions per-tenant would process attacker-controlled events under an arbitrary victim shop identity while the HMAC check reports success. This is a cross-tenant identity confusion: the security guarantee "an HMAC-valid webhook implies the header-declared shop actually sent it" does not hold, letting a low-privileged actor (any merchant who can install the app once to obtain one genuine signed payload) inject events attributed to a shop they don't own.

### Likelihood Explanation
Any unprivileged internet user who can install the target Shopify app on a store they control can capture one legitimate signed webhook (body + HMAC), then replay it to the app's public webhook endpoint with a forged `shop-domain`/`topic` header. No access to `api_secret_key` or any credential is required, and the exploit condition (headers excluded from `to_signable_string`) is present in every install of this gem version.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for webhook HMAC verification (or otherwise cryptographically bind these header values to the signed body before trusting them in `WebhookMetadata`), matching the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Install the target app on an attacker-owned test store; trigger any webhook (e.g. `orders/create`) and capture the raw HTTP request Shopify sends to the app's webhook endpoint, including `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: attacker-store.myshopify.com`, and the JSON body.
2. Replay the exact same body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-store.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the body bytes against the secret-derived HMAC.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-store.myshopify.com"` and invokes the app's handler, which now processes attacker-supplied data as if it came from the victim shop — confirmed by tracing `Request#shop`/`#to_signable_string` (`lib/shopify_api/webhooks/request.rb:21-38`) into `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`).

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
