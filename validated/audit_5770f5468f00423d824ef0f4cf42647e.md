## Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body — ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers when dispatching to the app's handler. Because the shop identity is never cryptographically bound to the signed payload, any unprivileged user who can obtain one valid `(body, HMAC)` pair for the app — e.g. by installing the app on their own store and receiving a legitimate webhook — can replay that same body/HMAC with a forged `X-Shopify-Shop-Domain` header to make the library assert the webhook came from a different (victim) shop.

### Finding Description
`HmacValidator.validate` computes/compares the HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw body — nothing else: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never part of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands the *header-derived* (unsigned) `shop`/`topic`/`webhook_id`/`api_version` to the handler as trusted identity data: [4](#0-3) 

The equality the library implicitly claims is: `shop authenticated by HMAC == shop delivered to the handler`. In reality, the HMAC only authenticates `(app_secret, raw_body)`; the `shop` field is asserted, not verified. Since the app's `api_secret_key` is shared across every merchant that installs the app (it is not per-tenant), any tenant that legitimately receives one valid signed body can replay it with an arbitrary `shop-domain` header value and the signature still validates.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing. A malicious merchant (an ordinary, unprivileged installer of the app — no access token, secret, or special privilege required beyond installing the app on their own store) can:
1. Install the app to receive a legitimate webhook, capturing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair.
2. Replay that exact body/HMAC to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `topic`) with a victim shop's domain/topic of choice.
3. `Registry.process` accepts it as authentic and calls the handler with `shop: "victim-shop.myshopify.com"`.

If the host application's handler uses `WebhookMetadata#shop` to look up the corresponding merchant's stored session/access token or to gate/attribute business logic per tenant (the documented and expected usage pattern), the attacker can trigger actions attributed to, or affecting, a different tenant's data — a cross-tenant access impact.

### Likelihood Explanation
Any user can create/install the target app on a store they control and thereby obtain a validly-signed webhook body without needing the `client_secret`, an access token, or any privileged access. Replaying the request with a different `shop-domain`/`topic` header is a trivial HTTP-level manipulation. The likelihood is high wherever a host app's webhook handler keys tenant lookups off `WebhookMetadata#shop`/`#topic`, which is exactly the intended usage documented for this gem's webhook API.

### Recommendation
Bind the shop (and, ideally, topic/webhook id) to the signed content, or require the host app to independently verify that the `shop` header matches a store known to have that webhook subscribed (e.g., cross-check against subscriptions registered via `Registry.register` for that shop and topic) before trusting it. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are **not** authenticated by the HMAC and must not be used as the sole tenant-identification mechanism, or extend `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop/topic headers so `HmacValidator` actually authenticates them.

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on "attacker-shop.myshopify.com"
# and captured a real Shopify-delivered webhook:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = "<hmac Shopify computed for raw_body with the app's shared client_secret>"

# Attacker replays it with a forged shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,   # unchanged, still validates - body untouched
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, NOT covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only checks raw_body + secret)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
``` [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
