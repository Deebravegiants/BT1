### Title
Unbounded route hops can execute caller-authorized token theft - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller swap strategies pass caller-supplied opaque route bytes to the configured router while the caller remains the transaction’s authorization root. A malicious route can therefore place attacker-controlled pool code beneath that authorization and add an unexpected token transfer from the caller to the recorded authorization tree; if signed, the victim loses unrelated wallet assets even when the swap itself satisfies the controller’s measured-output and account-risk checks. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` retrieves the configured router, grants only the exact controller-to-router input transfer, invokes `execute_strategy`, and afterward validates only controller-side input spending plus positive output receipt. [3](#0-2) 

The swap payload is opaque to the controller: `swap_collateral` accepts `swap: Bytes` and forwards it after proving ownership/delegation of the account. [4](#0-3) [5](#0-4) 

The router’s instruction format resolves an arbitrary `pool` address from the caller-controlled `assets` registry for each swap hop, and venue adapters invoke that address. [6](#0-5) [7](#0-6) [8](#0-7) 

Consequently, attacker-controlled code executes inside the transaction below the victim’s `caller.require_auth` scope. The controller’s authorization constrains only the controller’s own input transfer; it does not constrain unrelated authorization children that route code requests from the caller. [9](#0-8) [10](#0-9) 

The same unchecked `swap` argument reaches the router through `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and Multiply’s third-asset `convert_swap`. [11](#0-10) [12](#0-11) 

### Impact Explanation
A victim can lose arbitrary wallet tokens unrelated to the requested strategy amount. The repository’s hostile-route test demonstrates a `swap_collateral` call that returns the expected collateral and passes settlement while a nested rogue pool transfers the caller’s entire unrelated token balance to an attacker. [2](#0-1) 

This is theft of user funds rather than a bad price or route-quality issue: the rogue hop can return a legitimate output while adding a separate caller-authorized transfer. [13](#0-12) 

### Likelihood Explanation
Any unprivileged account owner can submit a crafted `swap` payload through `swap_collateral`, and an attacker can distribute such a payload through a malicious interface, quote service, or transaction builder. The victim must sign the resulting authorization tree, but wallets and integrations that only display the root operation or expected swap input may not make the unrelated child transfer sufficiently visible. [14](#0-13) [15](#0-14) 

The exploit does not require compromised privileged keys, an upgrade, an oracle failure, protocol liquidity, or a vulnerable listed asset; any token held by the victim can be selected as the rogue transfer target. [16](#0-15) 

### Recommendation
Do not allow route-selected contracts to execute under the user’s unconstrained authorization tree. Prefer an allowlist/registry of approved venue implementations, or restructure execution so route hops run under router authority without inheriting the account owner’s authorization scope. At minimum, expose a canonical decoded authorization summary and reject any route whose simulated auth tree contains children beyond the single expected controller input transfer; clients must refuse every unexpected child before signing. [17](#0-16) [10](#0-9) 

### Proof of Concept
1. Victim supplies collateral and invokes `swap_collateral(caller=victim, account_id, current=USDC, amount=5_000 USDC, new=ETH, swap=malicious_route)`. [18](#0-17) 
2. `malicious_route` names an attacker-deployed contract as a hop pool. That contract calls `unrelated_token.transfer(victim, attacker, victim_balance)`. [19](#0-18) 
3. Simulation records the token theft as a child of the victim’s `swap_collateral` authorization while the swap still pays the expected ETH output. [20](#0-19) 
4. If the victim signs only the honest root, the host rejects the rogue transfer; if the victim signs the returned tree, the unrelated wallet balance moves to the attacker and the protocol-level swap checks still pass. [13](#0-12)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
