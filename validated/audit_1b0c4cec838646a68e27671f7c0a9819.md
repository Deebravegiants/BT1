Based on my research, I found a concrete analog in `IntentsBase._addDeployment` / `ExtrinsicIntents.onAccept` in the `evm/src/apps/intentsv2/` package.

### Title
Overwriting an IntentGateway remote instance via `NewDeployment` breaks authentication for escrow already committed against the old instance address - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_addDeployment` unconditionally overwrites `_instances[keccak256(chain)]` with a new gateway address whenever Hyperbridge governance dispatches a `NewDeployment` action, with no check for outstanding escrow that still depends on the previous instance address, and no migration path. This mirrors the `LiquidityProviders.setLpToken` bug class: a governance-controlled pointer to a "trusted counterpart" is rewritable at any time, and everything downstream that authenticates against it silently starts rejecting messages that were valid before the change.

### Finding Description
`_instances` maps `keccak256(stateMachineId) → gateway address` and is described as being "used for authenticating cross-chain messages and routing dispatches" [1](#0-0) . It is written only by `_addDeployment`, which performs a bare overwrite with no previous-value check, no zero-check, and no versioning:

```solidity
function _addDeployment(Deployment memory body) internal {
    _instances[keccak256(body.chain)] = body.gateway;
    emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
}
``` [2](#0-1) 

`_instance` is read by `_authenticate`, which gates every incoming `RedeemEscrow`/`RefundEscrow` settlement message against whichever address is currently stored:

```solidity
function _authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (_instance(request.source) != module) revert Unauthorized();
}
``` [3](#0-2) 

and `onAccept` uses exactly this check before releasing or refunding escrow:

```solidity
if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
    _authenticate(incoming.request);
    WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
    return _withdraw(body, kind == RequestKind.RefundEscrow, true);
}
``` [4](#0-3) 

If a user places a cross-chain order while `_instances[dest]` points at gateway `A`, and the solver fills it on the destination chain deployed at `A`, that fill dispatches a `RedeemEscrow` message whose `request.from` is `A`. If, before that message is delivered (it can be delayed arbitrarily — proof generation, relaying, timeouts, etc.), Hyperbridge governance dispatches a `NewDeployment` re-pointing `_instances[dest]` to a redeployed/upgraded gateway `B` (a routine operation e.g. after a contract migration on the destination chain), then `_authenticate` on the pending `RedeemEscrow` message will now compare `_instance(source) == B` against `module == A` and revert with `Unauthorized`. The escrowed input tokens on the source chain, already locked in `_orders[commitment][token]`, become permanently unreachable through the intended settlement path — the solver who filled the order and delivered outputs to the user cannot claim the escrow, since the message is refused forever (there is no expiry/retry-with-new-address mechanism, and the message commitment/relayer content cannot be recomputed against the new address after the fact because `request.from` is fixed at dispatch time on the remote chain).

### Impact Explanation
This is a permanent freezing-of-funds bug reachable from a completely unprivileged flow: any user's `placeOrder` and any solver's `fillOrder` on the destination chain create a `RedeemEscrow` message bound to the instance address live at fill time. A subsequent, routine governance `NewDeployment` action (which the docs describe as normal chain-onboarding/redeployment tooling, not an attack) permanently breaks settlement of all orders in flight against that chain at the time of rotation. Because escrow is only released by `_withdraw`, called exclusively via the authenticated `onAccept`/`onGetResponse` paths, there is no owner/relayer override to re-deliver the message once the instance address has moved — the same-severity mitigation available in the LP-token case (owner resets the mapping back to the old value) is also viable here only if governance is aware of every commitment mid-flight and willing to briefly revert the mapping, which is not guaranteed and is itself unsafe (it also un-authenticates messages meant for the new instance).

### Likelihood Explanation
`NewDeployment` is a normal governance action for onboarding or redeploying a chain's gateway, and settlement messages routinely take multiple blocks/epochs to be proven and relayed across chains, especially for consensus clients with long finality (BEEFY, sync-committee). A rotation landing while orders are in flight is a realistic, non-adversarial timing collision, not a contrived edge case.

### Recommendation
Do not perform a destructive overwrite of `_instances[chain]`. Instead, either (a) keep a set/history of previously-valid instance addresses per chain and accept `_authenticate` against any of them for some grace period, or (b) require a completely different `Deployment` body validated to only append/replace only if the chain has no outstanding escrow tied to the previous address (mirrors "only allow setting the LP token once" mitigation), or (c) add a governance-triggered fallback path to manually re-authenticate/settle orders that were mid-flight at rotation time using the historical mapping.

### Proof of Concept
1. Governance dispatches `NewDeployment{chain: DEST, gateway: A}` → `_instances[keccak256(DEST)] = A` (`_addDeployment`, `IntentsBase.sol:581-584`).
2. User calls `placeOrder` on the source chain, escrowing `_orders[commitment][token] = amount`.
3. Solver calls `fillOrder` on the destination chain (deployed at `A`), delivers outputs, and the destination gateway dispatches a `RedeemEscrow` `PostRequest` with `from = A`.
4. Before this message is relayed/proven on the source chain, governance dispatches `NewDeployment{chain: DEST, gateway: B}` → `_instances[keccak256(DEST)] = B`.
5. The relayer delivers the pending `RedeemEscrow` message to the source-chain host, which calls `onAccept`. `_authenticate` computes `_instance(DEST) == B` but `module == A`, so it reverts `Unauthorized` (`ExtrinsicIntents.sol:63-67`, `333-337`).
6. The escrowed `amount` stays locked under `_orders[commitment][token]` with no code path to release it — the solver who already delivered outputs is unpaid and the escrow is stuck.
