### Title
Aliased "double-entry" ERC20 addresses in `erc20TokenAddresses` let a single real balance change be double-counted, minting unbacked shielded UTXOs - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots balances per index of `circomData.erc20TokenAddresses` via `getBalancesForArray` and independently checks, for each index, that `balanceDif == (onChainCreation ? 0 : amountChanges[i]) + utxoAmount`. Nothing in this loop, in `EmporiumUpgradeable.runAction`, or in the circuit constraints enforces that the addresses listed at different indices refer to distinct underlying token balances, so an attacker who deploys two ERC20-interface contracts that share the same real balance-of-vault storage can list both as separate entries and have one real (and, for a fee-on-transfer token, already-reduced) balance movement satisfy the equality twice, crediting UTXOs for double the value actually delivered.

### Finding Description
The equality claimed to hold is:
`newBalances[i] - oldBalances[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` for every index `i` independently [1](#0-0) .

`getBalancesForArray` is invoked purely on the raw addresses supplied in `circomData.erc20TokenAddresses`, before and after `_externalTransact`/`_internalTransact` [2](#0-1) . There is no on-chain check anywhere in `transact`, `_externalTransact`, or `EmporiumUpgradeable.runAction` that the addresses at different indices of the array are distinct *underlying assets* — only that they are distinct *array slots*. `EmporiumUpgradeable.runAction` performs the identical per-index balance snapshot pattern around the external calls it executes [3](#0-2) .

The circuit (`MainEVMCircuit.circom`) enforces `inTotal + amountChanges === outTotal` per token index, but this is a purely internal accounting constraint over the shielded ledger keyed by array index/token-id; it has no way to know that two different `erc20TokenAddresses` entries alias the same real-world balance, since the circuit only receives the addresses as opaque public-input identifiers.

Exploit flow:
1. Attacker deploys a pair of ERC20-compatible contracts, `TokenA` and `TokenB`, that both read/write a shared underlying storage/ledger (e.g., both delegate `balanceOf`/`transfer` accounting to one common contract) — a "double-entry" token where `balanceOf(vault)` returns the same number regardless of whether it is queried through `TokenA` or `TokenB`. To sharpen the exploit, the shared ledger applies a fee-on-transfer, so a stated transfer of `S` delivers `D < S` to the vault.
2. Attacker crafts a `CircomData` where `erc20TokenAddresses = [TokenA, TokenB, ...]`, drives a deposit of `S` tokens through the Emporium external action (or `_internalTransact`), and sets `amountChanges` and generates a proof claiming `amountChanges[iA] = D` and `amountChanges[iB] = D` (or equivalent split via `onChainCreation`/UTXO amounts), consistent with the circuit's `inTotal + amountChanges === outTotal` constraint per index — the circuit has no notion that index `iA` and `iB` are the same real asset, so this is provable.
3. On-chain, the *single* physical balance increase of `D` is read twice: once as `newBalances[iA] - oldBalances[iA] = D` and once as `newBalances[iB] - oldBalances[iB] = D`, because both addresses expose the same underlying balance [4](#0-3) .
4. Both per-index `require` checks pass independently, so `transact` mints/accepts shielded value corresponding to `2D`, while the vault's real net inflow is only `D` (already reduced from `S` by the fee-on-transfer). The attacker can later redeem the "TokenA" UTXO and the "TokenB" UTXO separately via `transferERC20TokenOrToken`-style withdrawal, each pulling `D` out of the *same* shared physical balance, draining `2D` from a pool that only ever received `D`.

None of the referenced guards close this gap: `performHinkalChecks`/`dimensionsCheck` validate array-length/dimension consistency, not asset distinctness; `rootHashExists`, `insertNullifiers`, and `onlyAllowedRecipient` govern proof/nullifier and caller-permission integrity, not token identity aliasing; and the circuit's `inTotal + amountChanges === outTotal` is enforced per opaque index, which is exactly the property being abused.

### Impact Explanation
This mints shielded UTXO value with no matching on-chain backing — a direct protocol-insolvency primitive (Critical: minting shielded value without backing). The attacker can drain the excess (`D` per repetition) from the shared vault balance, effectively stealing from other depositors' pooled funds. The attack is repeatable for every deposit routed through a freshly deployed aliased token pair, and scales with the deposit size and the number of aliased indices the attacker is willing to list.

### Likelihood Explanation
Preconditions: the attacker needs to deploy custom token contracts (fully within an unprivileged EOA's capability), route the transaction through the Emporium external action (or a plain deposit), and generate a valid proof for their own UTXOs — all explicitly listed as attacker capabilities. No privileged role, whitelisted relay, or victim key is required. The main uncertainty is whether `HinkalHelper.performHinkalChecks`/`dimensionsCheck` (whose implementation could not be fully retrieved within the available tool budget) impose any implicit uniqueness constraint on `erc20TokenAddresses`; based on all code paths inspected (`Hinkal.sol`, `EmporiumUpgradeable.sol`, `CircomDataBuilder.sol`), no such check exists — the balance-diff logic treats each array slot independently via raw `balanceOf` calls. Cost is limited to gas plus deploying the aliasing token contracts, and the exploit is repeatable indefinitely until patched.

### Recommendation
Enforce that all addresses in `circomData.erc20TokenAddresses` are pairwise distinct at the contract level (e.g., `require` no duplicates, and additionally consider tracking a canonical "seen balance snapshot" per unique address only once per transaction, reusing it for any repeated index) so a single real balance movement cannot be attributed to more than one shielded-ledger token index. Additionally, consider binding token addresses to an allowlist/registry so that the aliasing scenario (two independently deployed contracts intentionally sharing one balance ledger) cannot be introduced by an unprivileged depositor.

### Proof of Concept
Foundry test plan:
1. Deploy `SharedLedger` holding a `mapping(address => uint256) balances` with a `transferFrom`-style deposit that applies a 10% fee-on-transfer.
2. Deploy `TokenA` and `TokenB`, both implementing `IERC20.balanceOf`/`transfer` by delegating reads/writes to `SharedLedger`.
3. Fund attacker with `S` units of the underlying asset accepted by `SharedLedger`; deposit `S` such that `SharedLedger` records `D = 0.9 * S` credited to the vault (fee-on-transfer).
4. Construct `CircomData` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [D, D]`, and locally generate a valid proof satisfying the circuit's `inTotal + amountChanges === outTotal` per index (each index is a separate valid shielded ledger from the circuit's point of view).
5. Call `Hinkal.transact(...)`. Assert:
   - `TokenA.balanceOf(hinkal) - oldBalanceA == D` and `TokenB.balanceOf(hinkal) - oldBalanceB == D` (both true because they alias the same storage) — i.e., both `require(balanceDif == ... )` checks at contracts/Hinkal.sol lines 137–146 pass.
   - Real net token inflow into the vault (measured via the single underlying `SharedLedger` balance delta) equals `D`, not `2D`.
   - Total shielded UTXO value credited by the transaction equals `2D`.
   - Assert `2D > D` (vault balance delta) to demonstrate the invariant "net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)" is broken: LHS = `D`, RHS = `2D`.
6. Follow-up: redeem both shielded UTXOs (TokenA-denominated and TokenB-denominated) and assert the vault's real balance goes negative/insufficient relative to other depositors' claims, confirming insolvency.
