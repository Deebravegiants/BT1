## Finding

This is a valid, reproducible gap between the cost model's per-block accounts-data-size accounting and actual account growth achievable via CPI.

### Title
`CostModel::calculate_allocated_accounts_data_size` under-counts CPI-nested `SystemInstruction` allocations, allowing `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` to be bypassed - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only iterates `transaction.program_instructions_iter()`, i.e. top-level instructions, and statically deserializes only those whose `program_id` is the system program to detect `CreateAccount`/`Allocate`/`CreateAccountWithSeed`. Any account creation performed by a CPI from a user program is invisible to this estimate, both pre-execution (banking-stage scheduling) and post-execution (`check_block_cost_limits` in replay/commit), so the `CostTracker`'s `allocated_accounts_data_size` counter used to enforce `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` can be driven to near zero while real account-data growth is large.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` [1](#0-0)  loops over `instructions` supplied by `transaction.program_instructions_iter()`, and for each `(program_id, instruction)` calls `calculate_account_data_size_on_instruction`, which only recognizes system-program instructions found directly at the top level of the message [2](#0-1) . This helper is invoked from both `calculate_cost` (pre-execution estimate used by scheduling/cost tracking) and `calculate_cost_for_executed_transaction` (the "actual" cost recorded after execution) [3](#0-2) .

The post-execution "actual" cost is what gets fed into `check_block_cost_limits`, which is applied both during normal block production and during replay (`apply_cost_tracker_during_replay`), and which is the sole gate for `WouldExceedAccountDataBlockLimit` / `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` [4](#0-3) . Even though `calculate_cost_for_executed_transaction` receives the real `actual_loaded_accounts_data_size_bytes`, the `allocated_accounts_data_size` component is still derived from `transaction.program_instructions_iter()` — it never consults the actual `accounts_resize_delta` computed from execution.

That real, correct delta does exist elsewhere in the codebase: `bank.rs` computes `accounts_resize_delta` from `processing_results` per-instruction execution deltas and updates a separate global `accounts_data_size_delta_on_chain` counter [5](#0-4) , and the low-level resize check in `transaction-context/src/transaction_accounts.rs::can_data_be_resized` correctly limits growth per account/per-transaction regardless of whether the resize happens via a top-level instruction or CPI [6](#0-5) . However, that per-transaction cap (`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) is a different, much larger-scoped protection than the per-block `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes) enforced exclusively through `CostTracker::try_add`'s `allocated_data_size` check [7](#0-6) , which is fed entirely by the flawed top-level-only estimate.

Because a normal, unprivileged user can deploy an arbitrary BPF program that internally invokes `system_instruction::create_account` (or `allocate`/`create_account_with_seed`) via CPI, and then submit a top-level instruction calling into that program, `calculate_account_data_size_on_instruction` sees only the *outer* instruction (whose `program_id` is the attacker's program, not the system program) and returns `SystemProgramAccountAllocation::None`, contributing zero to `allocated_accounts_data_size` for that transaction — even though the CPI genuinely allocates a large new account.

### Impact Explanation
An attacker can pack many such CPI-based account-creation transactions into blocks (their own leader slot or via forwarding to any leader) and have the `CostTracker`'s per-block `allocated_accounts_data_size` counter stay at (or near) zero while the bank's actual on-chain accounts-data size (as reflected by `accounts_data_size_delta_on_chain`) grows without the intended per-block throttle. This materially undermines the safety mechanism whose entire purpose is to bound how fast accounts-db/state can grow per block, independent of the (correctly-enforced) per-transaction/per-account resize cap. This falls in the "materially underpriced execution" / resource-exhaustion category — it does not cause consensus divergence (all validators apply the same flawed estimate deterministically) but it does let the protection meant to bound state growth per block be evaded via a code path that any unprivileged CPI-capable user program can trigger.

### Likelihood Explanation
Fully feasible with a single deployed, non-privileged BPF program that CPIs into the system program for `CreateAccount`/`Allocate`/`CreateAccountWithSeed`; no special network position, leader control, or leaked keys required — an ordinary user submitting transactions to any RPC/TPU endpoint can trigger it repeatedly across blocks.

### Recommendation
Extend the accounts-data-size cost/tracking logic to account for account creations performed via CPI, not just top-level instructions — e.g., by walking the full (nested) instruction trace at cost-calculation time where available, or by having `calculate_cost_for_executed_transaction`'s `allocated_accounts_data_size` component use the real `accounts_resize_delta`/`accounts_uninitialized_size` computed during execution (as already tracked in `runtime/src/bank.rs`) rather than re-deriving it from static top-level instruction parsing.

### Proof of Concept
Integration test plan (analogous to existing tests in `runtime/src/bank/tests.rs` such as `test_accounts_data_size_with_good_transaction` [8](#0-7) ):
1. Deploy a mock/native builtin (or BPF) program that, on invocation, issues a CPI to `system_program::create_account` with a large `space` (e.g. close to `MAX_PERMITTED_DATA_LENGTH`).
2. Build and submit a transaction whose only top-level instruction targets this program (no top-level `SystemInstruction` present).
3. After `bank.process_transaction(...)`, assert:
   - `bank.load_accounts_data_size_delta_on_chain()` increased by the allocated `space` (real growth, matching `test_accounts_data_size_with_good_transaction`'s pattern).
   - `bank.read_cost_tracker().unwrap()`'s `allocated_accounts_data_size` (or the `TransactionCost::allocated_accounts_data_size` produced by `CostModel::calculate_cost_for_executed_transaction`) is `0`, diverging from the real growth.
4. Repeat across many transactions/blocks until real on-chain accounts-data growth exceeds `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` while the cumulative `CostTracker::allocated_accounts_data_size` never triggers `WouldExceedAccountDataBlockLimit`, proving the estimate fails to upper-bound real growth.

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())
}

) -> Vec<Option<TransactionCost<'a, Tx>>> {

    commit_results
        .iter()
        .zip(sanitized_transactions)

                ))
            } else {
                None
            }
        })
        .collect()
}

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }

/// Test processing a good transaction correctly modifies the accounts data size
#[test]
fn test_accounts_data_size_with_good_transaction() {
    const ACCOUNT_SIZE: u64 = MAX_PERMITTED_DATA_LENGTH;
    let (genesis_config, mint_keypair) = create_genesis_config(1_000 * LAMPORTS_PER_SOL);
    let bank = Bank::new_for_tests(&genesis_config);
    let (bank, _bank_forks) = bank.wrap_with_bank_forks_for_tests();
    let transaction = system_transaction::create_account(
        &mint_keypair,
        &Keypair::new(),
        bank.last_blockhash(),
        genesis_config
            .rent
            .minimum_balance(ACCOUNT_SIZE.try_into().unwrap()),
        ACCOUNT_SIZE,
        &solana_system_interface::program::id(),
    );

    let accounts_data_size_before = bank.load_accounts_data_size();
    let accounts_data_size_delta_before = bank.load_accounts_data_size_delta();
    let accounts_data_size_delta_on_chain_before = bank.load_accounts_data_size_delta_on_chain();
    let result = bank.process_transaction(&transaction);
    let accounts_data_size_after = bank.load_accounts_data_size();
    let accounts_data_size_delta_after = bank.load_accounts_data_size_delta();
    let accounts_data_size_delta_on_chain_after = bank.load_accounts_data_size_delta_on_chain();

    assert!(result.is_ok());
    assert_eq!(
        accounts_data_size_after - accounts_data_size_before,
        ACCOUNT_SIZE,
    );
    assert_eq!(
        accounts_data_size_delta_after - accounts_data_size_delta_before,
        ACCOUNT_SIZE as i64,
    );
    assert_eq!(
        accounts_data_size_delta_on_chain_after - accounts_data_size_delta_on_chain_before,
        ACCOUNT_SIZE as i64,
    );
}
