### Title
Unfunded repay/recapitalize overpayment refund drains pool custody to an arbitrary payer - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` leg trusts the *declared* `action.amount` and refunds any "excess over debt" back to `payer` out of real token custody, without verifying that any tokens were actually transferred in. Calling `pool.repay` on a market with no (or small) outstanding debt lets an unprivileged address name itself `payer`, declare an arbitrary amount, and receive a "refund" of funds it never paid. The same shape exists in `recapitalize` (excess over the shortfall is refunded from custody).

The mrpack-install advisory is a path-traversal class: a trusted component writes to an attacker-controlled location based on unvalidated input. The analog here is that the pool writes real assets to an attacker-controlled destination (`payer`) based on an attacker-controlled declared path (`action.amount`/`hub_asset`), where the correct behavior is to measure what actually arrived.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `apply` computes `(burned, overpayment) = cache.resolve_repay(amount, position)` from the caller-supplied `action.amount` and then executes `outcome.cache.transfer_out(payer, outcome.overpayment)`. `accounting` explicitly allows the zero-work case: the `RepayRoundsToZeroShares` assertion passes whenever `net_repay == 0`. On a market with zero debt, `resolve_repay` takes the full-close branch, `overpayment == amount`, and the entire declared amount is refunded from pool custody while `credit_cash(0)` leaves the book untouched — custody and cash diverge by the stolen amount.

The repo's own test pins the reachability: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `client().repay(&payer, &t.ract(0, custody_before))` with nothing transferred in and asserts custody is drained to `payer` (`contracts/pool/tests/flows.rs:3589-3611`). `test_unfunded_recapitalize_is_bounded_by_custody_not_by_the_declared_amount` shows `recapitalize` pays up to live custody (`contracts/pool/tests/flows.rs:3488-3512`). Neither refund path debits `cash` nor passes `require_reserves`, per the comments at `flows.rs:3578-3588`.

Because the refund goes to `payer` — an argument the caller picks — this is exactly the traversal shape: the "output path" (recipient) and the "file content" (amount) are both attacker-chosen while the write hits the shared physical pool balance backing all (hub, token) book balances.

### Impact Explanation
An attacker steals pool-held underlying tokens up to the token contract's custody bound, with no collateral, no position, and no funds of their own (the SAC transfer is the only bound — the attempted drain must fit inside real holdings). The book's `cash` is not reduced, so supplier shares remain nominally backed while custody is gone: subsequent withdrawals/borrows revert on the token transfer, permanently freezing remaining suppliers' funds and rendering the market insolvent (book cash > actual balance). This satisfies both theft of user funds and protocol insolvency.

### Likelihood Explanation
A single unprivileged transaction: call `pool.repay(payer = attacker, PoolAction { position: <zero/empty position>, amount: <custody>, hub_asset: <any market with no debt> })`. Any market whose debt rounds to zero at call time is eligible, and `recapitalize` provides the same primitive on any market without a shortfall. No oracle manipulation, flash loan, or privileged role is needed; the only constraint is choosing `amount <= token.balance(pool)`.

### Recommendation
Make both legs measured-settlement like the rest of the protocol:

1. In `ops::repay::apply` and `ops::recapitalize::apply`, bound the refund by the measured inbound delta (`balance_after − balance_before` of the market asset around/into the pool), not the declared `action.amount`. If `amount > received`, cap or revert.
2. Alternatively, require the controller (or a privileged settlement address) as the only allowed caller for `repay`/`recapitalize`, since only the controller sequences an actual `token.transfer` before the pool call — matching the "controller transfers before this call" contract stated in `repay.rs:3`.
3. Route refunds through `cash`/reserve checks so an over-refund cannot pay out unbacked custody.

### Proof of Concept
From `contracts/pool/tests/flows.rs` (already executable in-repo):

```rust
// No tokens transferred in; market has zero debt (borrowed == 0).
let custody = token.balance(&t.pool);
let credited = t
    .client()
    .repay(&attacker, &t.ract(0, custody))   // PoolAction { position: <none>, amount: custody, hub_asset }
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                     // nothing retired
// assert_unfunded_refund_drained_custody: attacker balance == custody,
// pool custody == 0, book cash unchanged -> custody < cash.
```

The refund path is `repay.rs:44` (`resolve_repay` returns `overpayment = amount`) and `repay.rs:32` (`transfer_out(payer, overpayment)`), gated only by `RepayRoundsToZeroShares` which is satisfied when `net_repay == 0` (`repay.rs:48-52`).

Uncertainty: I could not confirm whether `pool.repay` performs a `require_auth`/caller check restricting it to the controller, since the auth-grep on `contracts/pool/src/lib.rs` returned only match counts. If repay is controller-gated, the same drain remains reachable through `controller.repay`/`recapitalize` only to the extent the controller pre-transfers funds — in that case the residual exposure is the controller-to-payer refund path rather than a direct call; the fix (measured inbound) is identical either way.
