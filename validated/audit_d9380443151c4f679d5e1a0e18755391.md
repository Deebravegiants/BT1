### Title
Webhook `shop` field is not covered by HMAC, allowing cross-tenant webhook spoofing via signature replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw webhook body, so `Utils::HmacValidator.validate` verifies the HMAC over the body alone. The `shop` (and `topic`/`webhook_id`) header values are never part of the signed payload, yet `Registry.process` trusts `request.shop` when building `WebhookMetadata` and dispatching it to the host app's handler as the tenant identity for that webhook event. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The equality that should hold but doesn't: `shop authenticated by HMAC == shop delivered to the handler`. The gem's `HmacValidator.validate` recomputes `HMAC(secret, raw_body)` and compares it to the `hmac` header using `OpenSSL.secure_compare` — this only binds the *body bytes* to the secret. It never includes `shop`, `topic`, or `webhook_id` in `to_signable_string`. [4](#0-3) 

Because Shopify webhook bodies are frequently identical or predictable across shops for a given topic (e.g., `shop/redact`, `app/uninstalled`, or any webhook whose payload doesn't embed the shop domain), a merchant who has legitimately installed the app on their own store receives a validly-signed webhook (`raw_body`, `hmac`) pair from Shopify using the app's real `client_secret`. That same `(raw_body, hmac)` pair remains valid for *any* `shopify-shop-domain` header value, since the header is not part of the signed string. `Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` to construct `WebhookMetadata`, forwarding it to the app's `WebhookHandler#handle`. [5](#0-4) 

An attacker (any merchant with the app installed, i.e., an unprivileged multi-tenant user of the host app) can therefore replay their own genuine webhook request to the app's webhook endpoint while substituting the `shopify-shop-domain` (or legacy `x-shopify-shop-domain`) header with a victim shop's domain. The signature check still passes because it only re-verifies the body bytes, and the host app's handler receives `WebhookMetadata#shop` pointing at the victim tenant, potentially triggering cross-tenant state changes (e.g., processing a fake `shop/redact`/`app/uninstalled` event for a shop the attacker doesn't own, deleting or resetting the victim's stored session/data).

### Impact Explanation
This is a **Critical - cross-tenant access** issue: an unprivileged attacker (a legitimate app installer on their own store) can spoof webhook events attributed to a different merchant's shop, because the gem's own signature-verification code (`HmacValidator`, `Webhooks::Request`) never binds the `shop` identity into the HMAC it checks. Any host application that uses `WebhookMetadata#shop` from this gem (as the sample/generated pattern and tests demonstrate) as the trusted tenant key inherits this cross-tenant confusion.

### Likelihood Explanation
Likelihood is high for topics with fixed, shop-independent, or highly predictable bodies (mandatory compliance topics like `shop/redact`, `customers/redact`, `customers/data_request`, or lifecycle topics like `app/uninstalled` sent with `{}` body as shown in this gem's own test fixtures). Any attacker who can install the app on a shop they control automatically obtains a validly-signed `(body, hmac)` pair usable against arbitrary victim shop headers, requiring no secret leakage or privileged access.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values in the signed material verified by `HmacValidator`, or verify the HMAC against the raw body first and then independently establish shop identity via an authenticated channel (e.g., look up the shop by matching a session/token that was itself bound to that shop at OAuth/installation time) rather than trusting the unauthenticated `shopify-shop-domain` header directly. At minimum, document/emit this binding gap so host apps do not treat `WebhookMetadata#shop` as an authenticated tenant identifier without additional verification (e.g., cross-checking against a shop for which the app holds an active, previously-established session).

### Proof of Concept
1. App merchant Alice (attacker) installs the app on `alice-shop.myshopify.com`. Shopify sends a webhook for topic `shop/redact` with body `{}` and a valid `hmac` computed as `HMAC-SHA256(client_secret, "{}")`.
2. Alice captures this `(raw_body="{}", hmac=X)` pair.
3. Alice sends a forged HTTP POST to the app's webhook endpoint with body `{}`, `shopify-hmac-sha256: X`, `shopify-topic: shop/redact`, but `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, "{}")`, matching `X`, so validation succeeds: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: {}, ...)` and invokes the host app's handler as if Shopify itself sent a redact/uninstall event for the victim shop: [5](#0-4) 
6. If the host app acts on `data.shop` (e.g., purges data, revokes sessions, marks the shop uninstalled), Alice has triggered a cross-tenant action against a shop she does not control, using only her own legitimately-issued webhook signature.
