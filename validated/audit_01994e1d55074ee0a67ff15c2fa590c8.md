### Title
Unconstrained public signals `outTimeStamp`/`calldataHash` in `MainEVMCircuitMin` allow a Min-circuit proof to be replayed against arbitrary `calldataHash`/`timeStamp` values - ([File: circuits/MainEVMCircuitMin.circom])

### Summary
`MainEVMCircuitMin` declares `outTimeStamp` and `calldataHash` as public inputs but never references them in any constraint — the only computation in the template is `message <== Poseidon(1)([messageSeed])`. Because these two signals never appear in any R1CS row, their corresponding verification-key `IC` coefficients are the zero group element, so Groth16 verification is mathematically independent of the values submitted for them, meaning a proof generated for one `(calldataHash, timeStamp)` pair will still pass `verifyProof` for any other pair.

### Finding Description
The equality claimed to hold is: *the `calldataHash`/`timeStamp` baked into the witness at proof-generation time == the values later supplied on-chain as public inputs to `verifyProof`*.

Tracing the circuit, `circuits/MainEVMCircuitMin.circom` is: [1](#0-0) 

`outTimeStamp` and `calldataHash` are declared `signal input` (public, since this is the "Min" no-token-transfer flow) but appear on neither the left nor right side of any constraint — only `messageSeed` feeds `Poseidon` to compute `message`. In an R1CS, a variable that never appears as a nonzero coefficient in any constraint row produces an all-zero column in the `A`/`B`/`C` matrices. In the Groth16 trusted setup this column maps to a zero `IC[i]` element in the verification key. Groth16's verifier computes `vk_x = IC[0] + Σ public_input[i] * IC[i]` from the values passed by the caller; if `IC[i] = 0`, the term `public_input[i] * IC[i]` is always the identity element regardless of what value is supplied — the pairing check `e(A,B) = e(alpha,beta) * e(vk_x,gamma) * e(C,delta)` therefore holds for *any* value of that public input, not just the one used to build the witness.

On the Solidity side, `formInputEmporiumMin` packs exactly these three values (in the same order as the circuit's public signals: output `message`, then `outTimeStamp`, then `calldataHash`) into the public-input array passed to `verifyProof`: [2](#0-1) 

This path is only taken for the Emporium/min flow (`erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`), selected in `formInputForCircom`: [3](#0-2) 

`performHinkalChecks` in `HinkalHelper.sol` does verify `getHashedCalldata(circomData) == circomData.calldataHash` (an internal self-consistency check on the calldata itself), but this check only ensures the `calldataHash` field is consistent with the rest of `circomData` supplied in *that* call — it does not, and cannot, force the SNARK to reject a `calldataHash`/`timeStamp` value different from what was used at proof-generation time, because the circuit itself places no constraint linking those signals to the witness (`messageSeed`) that actually produces `message`/`a,b,c`. [4](#0-3) 

Given a valid `(a,b,c)` proof generated once for `(emporiumMessage=M, timeStamp=T1, calldataHash=C1)`, an attacker can call `Hinkal.transact` supplying the same `(a,b,c)` but a different `circomData` whose `timeStamp=T2` and/or whose other fields make `getHashedCalldata(circomData) = C2 != C1` (satisfying the self-consistency require above with the *new* `C2`), and the on-chain `verifyProof(a,b,c,[M,T2,C2], verifierId)` call will still return `true`, because the verifier is mathematically blind to `T2`/`C2` for this circuit.

### Impact Explanation
This is a proof/nullifier-verification bypass at the Critical severity tier: an attacker can bind a single previously-proven `emporiumMessage` (used, e.g., to authorize a specific `externalActionMetadata`/relay/fee structure inside `EmporiumUpgradeable.runAction` via `verifyWallet`) to an entirely different, attacker-chosen `calldataHash` (and hence a different `externalActionMetadata`, `feeStructure`, `relay`, etc.) without the SNARK enforcing any relationship between what was proven and what is executed on-chain. Because `calldataHash` is meant to be the binding commitment that ties the zero-knowledge proof to the exact transaction payload being executed, breaking this binding lets an attacker attach unvetted/unauthorized external-action data to a proof, potentially routing funds, hooks, or fee structures that were never part of the proven statement — a direct violation of the "proof never constrained this field" impact criterion in the rules.

### Likelihood Explanation
Feasibility is high for the erc20TokenAddresses.length == 0 (Min/Emporium) circuit path specifically: any unprivileged EOA can generate one valid proof with `snarkjs` for their own `emporiumMessage`/`messageSeed`, then submit that same `(a,b,c)` again through `Hinkal.transact` with a different `CircomData` (different `timeStamp`, different `externalActionData`/`feeStructure`/`relay` fields that hash to a different `calldataHash`), since `getHashedCalldata` is recomputed fresh from the new fields and will match the new `circomData.calldataHash` supplied in the same call — satisfying `performHinkalChecks`'s internal check while defeating the SNARK's supposed binding. This is fully repeatable per generated proof with no special preconditions beyond having minted one valid Min-circuit proof.

### Recommendation
Add explicit constraints in `MainEVMCircuitMin` (and audit `MainEVMCircuit` for the same pattern) that bind `outTimeStamp` and `calldataHash` into the witness, e.g. compute `message <== Poseidon(3)([messageSeed, outTimeStamp, calldataHash])` (or otherwise force-equal these signals against committed/private values) so that every public signal actually participates in at least one constraint and therefore has a nonzero `IC` coefficient in the verification key, restoring the binding property Groth16 is expected to provide.

### Proof of Concept
1. Compile `MainEVMCircuitMin.circom`, run trusted setup, generate witness/proof for `messageSeed=s`, public inputs `(message=Poseidon(s), outTimeStamp=T1, calldataHash=C1)` via `snarkjs groth16 fulldprove`.
2. In a Foundry/Hardhat test, deploy `VerifierEVMMin0v4` (or the corresponding registered verifier) and call `verifier.verifyProof(a,b,c,[message,T1,C1], verifierId)` — assert `true`.
3. Call `verifier.verifyProof(a,b,c,[message,T2,C2], verifierId)` with `T2 != T1` and/or `C2 != C1` (no proof regeneration) — assert this **unexpectedly returns `true`** (confirming the vulnerability) instead of the expected `false`/revert.
4. End-to-end: craft a `CircomData` whose `timeStamp=T2` and whose `externalActionData`/`feeStructure` hash (via `getHashedCalldata`) to `C2`, call `Hinkal.transact` reusing the original `(a,b,c)`, and show `performHinkalChecks` + `verifyProof` both succeed, allowing the attacker-chosen `externalActionMetadata` to execute under the original prover's proof.

        CircomData calldata circomData,
        Dimensions calldata dimensions,
        address sender
    ) external view returns (uint256[] memory) {
        require(
            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||
                (circomData.originalSender == sender &&
                    circomData.relay == address(0)),
            "invalid value for originalSender"
        );

        require(
            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,
            "Calldata Hash Integrity Check Failed"
        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
    }
