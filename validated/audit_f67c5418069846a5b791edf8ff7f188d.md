### Title
POA Bridge withdrawal status matches by `assetId` only, ignoring destination address and amount, causing a wrong `txHash` to be reported as `completed` - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal-status API response entry to the caller's specific withdrawal using only the asset identifier via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [1](#0-0) . It never re-checks that the matched entry's `data.address` (destination) or `data.amount` equals the `destinationAddress`/`amount` that were supplied in `args.withdrawalParams` before reporting `{ status: "completed", txHash: withdrawal.data.transfer_tx_hash }` [2](#0-1) .

### Finding Description
This is the same equality-breaking bug class as CVE-2022-35929: a verification/matching routine reports success as soon as it finds *any* record satisfying a coarse filter (there, "any attestation exists"; here, "any withdrawal of this `assetId` exists"), instead of confirming the record actually corresponds to the specific request being checked (there, the requested attestation `--type`; here, the requested `destinationAddress`/`amount`).

`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that embeds `withdrawalParams` (including `destinationAddress` and `amount`) together with an `index` [3](#0-2) , because a single NEAR transaction can contain multiple withdrawal intents (batched). The code comment explicitly acknowledges the response list is unordered and multiple items may exist: "Response list is unsorted, so we match by assetId instead of index" [4](#0-3) . However switching from `index`-based lookup to `assetId`-based lookup only fixes ordering — it does not disambiguate between two or more withdrawals of the *same* `assetId` present in the same NEAR tx (e.g., a batch withdrawal sending the same token to two different destination addresses/amounts in one transaction). In that case `findMatchingWithdrawal` can return the wrong entry, and the SDK will report `completed` with a `transfer_tx_hash` that actually belongs to a different destination/amount than the one the caller asked about.

The equality that should hold — "the `txHash` reported for withdrawal request X is the on-chain outcome of withdrawal request X" — can break: the reported `txHash` may instead be the on-chain outcome of a *different* withdrawal request Y that happens to share the same `assetId` within the same batch transaction.

### Impact Explanation
`watchWithdrawal` treats a `completed` status as the definitive on-chain outcome and returns the reported `txHash` to the caller [5](#0-4) , and SDK consumers use this to mark a withdrawal as settled/credited. If the wrong batch member is matched, an integrator could treat withdrawal X as completed using withdrawal Y's transaction hash — this is a status/hash misreport that can cause an integrator to credit or consider settled a withdrawal that did not actually land at the expected destination/amount, matching the "High" impact bucket ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires that a single NEAR transaction contain two or more withdrawal intents for the same `assetId` (a legitimate, supported usage pattern given the SDK explicitly supports multiple withdrawals per tx and defends against unordered responses), and that the POA Bridge API returns multiple entries for that asset in the withdrawal-status response for that tx. No malicious actor input is required beyond normal batching — it's a correctness/equality gap in matching logic, not a needed adversarial trust upgrade.

### Recommendation
In `findMatchingWithdrawal`, disambiguate strictly using additional identifying fields from `withdrawalParams` (destination address and amount, normalized/compared the same way `compareAddresses`/`validateAddress` do elsewhere in this file) in addition to `assetId`, or fall back to `index` when the API guarantees a stable per-request ordering. `describeWithdrawal` should refuse to report `completed` when the matched entry's destination/amount do not equal the requested `withdrawalParams`, returning `pending` (or a distinct `ambiguous`/error state) instead.

### Proof of Concept
1. Trigger a NEAR transaction containing two withdrawal intents for the same `assetId` (e.g., `nep141:btc.omft.near`) but different `destinationAddress`/`amount` (a legitimate batched-withdrawal use case).
2. Call `describeWithdrawal` for withdrawal index 0 (destination A) after the POA Bridge API has recorded completion for withdrawal index 1 (destination B) but not yet for index 0.
3. `findMatchingWithdrawal(response.withdrawals, assetId)` — filtering only on `assetId` — can return the entry for destination B.
4. `describeWithdrawal` returns `{ status: "completed", txHash: <B's transfer_tx_hash> }` for the caller who requested status for destination A's withdrawal, exactly analogous to `cosign verify-attestation --type` reporting success on the basis of an unrelated attestation that happens to exist.
