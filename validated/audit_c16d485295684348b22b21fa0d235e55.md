### Title
Attacker-controlled route venues execute arbitrary token transfers under the caller's authorization tree, draining wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The CVE-2026-55799 class — untrusted input reaching a script engine that executes attacker-supplied code — maps directly onto XOXNO Lending's router strategy path. `swap_tokens` in `contracts/controller/src/strategies/swap.rs` forwards user-supplied `swap` bytes verbatim to the configured swap aggregator, which invokes the pool/token addresses the payload names with no allowlist. A venue "pool" named by a malicious route is arbitrary code running inside the caller's `require_auth` tree, exactly like attacker-controlled script code running inside GraalScriptEngine. That code can call `token.transfer(victim, attacker, amount)` for any token the caller holds, and a signed simulation records the theft as a legitimate child of the caller's `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` auth entry. This is demonstrated end-to-end by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

### Finding Description
`swap_tokens` authorizes one exact input transfer to the router and invokes `router.execute_strategy(&controller, &amount_in, swap)` inside the flash guard, without decoding or constraining the route contents (`contracts/controller/src/strategies/swap.rs:34-38`). The aggregator dispatches hops to whatever pool and token addresses the payload registries name — the repo's own threat model states the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-160`).

The test fixture proves the primitive: `UnlistedPoolRouter.execute_strategy` calls `env.invoke_contract(&route.hop_pool, "swap", ...)`, and `RogueHopPool::swap` performs `token::Client::transfer(&victim, &to, &amount)` against an unrelated wallet token (`tests/.../rogue_hop_pool_transfer_joins_caller_auth_tree.rs:44,62-70`). The assertion at line 222 shows the recorded auth tree places the stolen `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` as a direct child of Alice's `swap_collateral` invocation, and lines 224-226 confirm Alice's wallet is drained to zero while the swap itself settles fairly. Every entrypoint that reaches `swap_tokens` is exposed: `multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, plus direct router `execute_strategy` calls (`docs/explanation/threat-model.md:160-165`).

### Impact Explanation
Theft of user funds: the full balance of any token in the victim's wallet can be transferred to the attacker, unbounded by the routed `amount_in`, the payload's `min_out`, or the post-action health-factor gate — the threat model explicitly notes "neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:159-161`). The stolen transfer is authorized because Soroban executes any child recorded in the signed auth tree, and a standard `simulateTransaction` + sign workflow records the rogue call as a child of the legitimate swap the user intended to authorize.

### Likelihood Explanation
Any unprivileged attacker can craft route bytes naming a malicious hop pool (route bytes are opaque `Bytes` the controller never decodes — `swap.rs:37`). Exploitation requires the victim to sign a poisoned route, which is realistic whenever routes come from a quote service or a compromised/malicious frontend, since clients are expected to pass `routeXdr` "untouched" (`skills/xoxno-swap-aggregator/composition.md:55-58`). The only mitigation is client-side route decoding — the contract enforces nothing. One honest caveat: this exposure is documented in the threat model as a client responsibility, which may reduce it from a pure contract bug to a documented trust assumption; it remains a Critical-severity reachable primitive on the in-scope `swap_tokens` path.

### Recommendation
Constrain venue code reachable under the caller's auth: enforce an allowlist of pool/token addresses per venue in the router (or a controller-side venue registry the aggregator must consult), and/or have the controller simulate-or-verify that the route only touches declared market tokens. At minimum, reject routes whose `token_in`/`token_out` registries contain addresses not matching the strategy's declared market assets, and document prominently that any child entry in the auth tree beyond the single input transfer is a theft vector.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` already implements it: register `UnlistedPoolRouter` as the aggregator, deploy `RogueHopPool` with a plan `(alice, wallet_token, attacker, WALLET_BALANCE)`, build a `RoutedSwap` naming that pool, call `ctrl.swap_collateral(alice, account_id, usdc, SWAP_IN_USDC, eth, route)`, and observe `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, with the theft recorded as a child of Alice's signed `swap_collateral` auth entry (lines 194-227).
