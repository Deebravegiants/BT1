## Title
Unchecked ERC20 boolean return value in `withdraw()`/SweepDust payout path permanently burns escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` uses `SafeERC20` for the deposit/escrow side of orders (`safeTransferFrom`), but the payout side — `withdraw()` and the `SweepDust` handler in `onAccept` — uses raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the external call did not revert (`success`). It never inspects the returned boolean/return-data, so a non-compliant ERC20 that returns `false` on failure instead of reverting will be silently treated as a successful transfer.

### Finding Description
In `withdraw()`: [1](#0-0) 

and in the `SweepDust` branch of `onAccept`: [2](#0-1) 

Both use `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only revert when the low-level call itself fails (`!success`). They never decode/validate the returned `bool`. For any ERC20 token whose `transfer` function returns `false` on failure rather than reverting (a common pattern for older/non-standard tokens, and explicitly the bug class flagged in the referenced Kairos report), `success` will be `true` even though no tokens moved.

Meanwhile, `withdraw()` unconditionally decrements the escrow accounting and marks the order filled regardless of whether the transfer truly succeeded: [3](#0-2) 

Note that elsewhere in the same contract, `SafeERC20.safeTransferFrom` (which does validate return values) is used consistently for escrowing inbound tokens: [4](#0-3) 

showing the payout path is an inconsistent, unsafe deviation from the pattern used elsewhere in the same file — the exact class of bug described in the reference report, manifesting in its inverse form (false negative instead of false positive on ERC20 return-value checking).

### Impact Explanation
When a fill/refund `WithdrawalRequest` or a `SweepDust` request is delivered from Hyperbridge and the underlying token misbehaves this way, the beneficiary receives zero tokens, yet:
- `_orders[body.commitment][token]` is decremented (escrow record zeroed/reduced) so the funds cannot be claimed again,
- `_filled[body.commitment] = beneficiary` marks the order as settled, preventing any retry or refund path,
- for `SweepDust`, tokens are permanently stuck in the contract with no re-sweep mechanism for that commitment.

This results in permanent loss of user/solver funds escrowed in the intents system for any token that returns `false` instead of reverting on transfer failure.

### Likelihood Explanation
Triggering requires only that the configured input/output token for an order (or a swept dust token) is a non-standard ERC20 that returns `false` rather than reverting on failure (e.g., insufficient balance edge cases, blacklist/pausable tokens, or other legacy tokens). Since `IntentGatewayV2` is a generic, permissionless intents gateway accepting arbitrary ERC20 tokens configured by users/solvers in orders, this is reachable by any solver/relayer settling an order or the protocol issuing a `SweepDust` request for such a token — no privileged access is required to trigger the loss once such a token is used in an order.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` usage already present elsewhere in the contract. This ensures both revert-on-failure and false-boolean-return tokens are handled correctly before escrow state is mutated.

### Proof of Concept
1. Create an order whose input/output token is a non-standard ERC20 whose `transfer` implementation returns `false` (without reverting) when, e.g., the recipient is blacklisted or another internal condition fails.
2. Deposit succeeds via `safeTransferFrom` (escrowed correctly).
3. On fill/refund, Hyperbridge delivers the `WithdrawalRequest`; `withdraw()` calls `token.call(...transfer...)`, which returns `(true, abi.encode(false))` — `success` is `true` so no revert occurs.
4. `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set, even though `beneficiary` received 0 tokens — funds are permanently lost from the beneficiary's perspective and cannot be re-claimed.
