### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identifier) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then hands the *header-derived* shop value straight to the app's handler as the trusted tenant identity, breaking the intended binding `verified(hmac) == acted-upon(shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely independent of the signed content: [2](#0-1) 

`Registry.process` validates `Utils::HmacValidator.validate(request)` — which only checks `request.hmac` against `request.to_signable_string` (the raw body) — and then forwards `request.shop` unchecked into `WebhookMetadata` that is delivered to the app's handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever operate on `verifiable_query.to_signable_string`, so the shop header plays no role in the cryptographic check at all: [4](#0-3) 

The equality that should hold is: `shop-bound-by-hmac(request) == shop-acted-upon-by-handler(request)`. In this implementation that equality is false — the HMAC binds only `(raw_body)`, while the handler acts on `shop-domain header`, an entirely separate, unauthenticated value.

The gem's own documentation confirms apps are meant to trust `data.shop` as "The shop domain of the webhook" once `Registry.process` has "verif[ied] the request did indeed come from Shopify" — i.e., using the gem exactly as documented still exposes this gap, so this is not a case of the host app ignoring the documented API.

### Impact Explanation
An unprivileged attacker who owns a legitimate (even free/trial) shop installation of the target app will receive real webhooks from Shopify — correctly HMAC-signed over the raw body — addressed to their own shop. Because the shop identity lives in a header that is excluded from the signed payload, the attacker can replay that same body+HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched and valid), so `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any app logic that uses `data.shop` to key storage, dedupe, enqueue background jobs, or attribute state (exactly as shown in the gem's own documented example, `perform_later(shop_domain: data.shop, ...)`) will process/store attacker-controlled data under the victim tenant's identity — a cross-tenant data-integrity/confusion issue reachable purely through the gem's documented API surface, with no access token, `client_secret`, or privileged account required.

### Likelihood Explanation
Requires only: (1) attacker has any legitimate app install to receive at least one real webhook, and (2) attacker can replay an HTTP request with a modified header to the app's public callback URL — both trivially available to an ordinary internet-facing merchant/attacker with no elevated privilege, no secret material, and no TLS interception.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the value that is cryptographically bound to the HMAC, or independently verify that the `shop-domain` header matches a shop for which the app holds an active session/installation before trusting it, e.g. reject/re-derive `shop` from a source verified as part of the signed request rather than trusting the raw header value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the attacker's registered callback with headers `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-shop-domain: attacker-shop.myshopify.com`, and a JSON body.
3. Attacker resends this exact request to the target app's callback endpoint, keeping body and `shopify-hmac-sha256` unchanged but replacing `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks the untouched raw body against the untouched HMAC. [3](#0-2) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the body content actually belongs to the attacker's shop, causing the app to act on/store data under the victim's tenant identity.
