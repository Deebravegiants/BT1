This confirms the vulnerability path clearly. The docs explicitly document `Registry.process` as verifying "the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125), but the `shop` field passed to the handler is never covered by that verification.

### Title
Webhook `shop` domain is trusted from an unauthenticated header while only the request body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC solely over that signable string [2](#0-1) . The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) which are never part of the HMAC-signed material [3](#0-2) . `Registry.process` validates the HMAC and, if it passes, forwards `request.shop` straight into `WebhookMetadata` given to the app's handler [4](#0-3) .

### Finding Description
The equality the gem is supposed to guarantee is: *the tenant (`shop`) the app acts on == the tenant that Shopify's HMAC signature actually authenticates*. In reality the HMAC only authenticates the byte-for-byte JSON body; it says nothing about which shop produced that body. `Registry.process` treats a valid body signature as sufficient proof of authenticity for the whole request, including the `shop-domain` header, and passes that unauthenticated field on to the app's webhook handler as trusted tenant identity [4](#0-3) . The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4) , and lists `shop` as one of the trusted keys handed to the handler [6](#0-5) , reinforcing that the header is meant to be relied upon as authenticated tenant data — but it is not bound to the signature.

An unprivileged internet user who can obtain (or replay) one legitimately-signed webhook body for any shop (e.g. their own installed instance of the app, or a captured/leaked payload whose body content is not shop-specific/secret) can resend it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header while keeping the original valid `X-Shopify-Hmac-Sha256` header, since the HMAC does not depend on that header at all.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is supposed to enforce for webhook delivery: `HMAC verified == shop is authentic` does not hold, since `shop` is outside the signed material. Depending on how the host application uses `data.shop` from `WebhookMetadata` (e.g., to look up the shop's session/access token, update per-tenant records, or trigger tenant-scoped side effects), this enables cross-tenant data confusion/write — data or actions intended for shop A can be attributed to shop B purely by header manipulation, without needing any of shop B's credentials. This matches the "cross-tenant access" class of Critical impact.

### Likelihood Explanation
Exploitation requires only: (1) the ability to make an HTTP POST to the app's public webhook endpoint (no auth needed), and (2) possession of any single validly-signed body+HMAC pair for the configured `api_secret_key` app (trivially obtainable by installing the app on an attacker-controlled dev store, since Shopify signs webhooks with the app's shared secret regardless of which shop sent them). No leaked credentials, TLS interception, or privileged access is required — only the app's `client_secret`-derived webhook secret, which the attacker never needs to see because Shopify signs the attacker's own shop's webhook bodies for them.

### Recommendation
Include the shop-identifying and topic-identifying headers in the HMAC-signed material (or require the application to independently verify `shop` against a known/installed-shop list before trusting it), rather than trusting header-derived fields once only the body HMAC has been checked. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated and must be cross-checked by the host app against its own shop/session store before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`, triggering Shopify to send a legitimately HMAC-signed webhook (e.g. `orders/create`) to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker captures `B` and `H`.
3. Attacker (or a compromised network intermediary/replay) sends a new POST to the same webhook endpoint with the same body `B` and same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes [7](#0-6) .
5. `Registry.process` calls the app handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [8](#0-7) , even though the payload actually originated from the attacker's own shop, causing the host app to act on `victim-shop.myshopify.com`'s behalf with attacker-controlled data.
