### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the target host for the OAuth token-exchange HTTP request directly from the session token's `dest` claim, and never runs that value through `ShopifyAPI::Utils::ShopValidator`. The sibling method `migrate_to_expiring_token`, which performs the same kind of outbound request carrying the app's `client_secret`, does apply `ShopValidator.sanitize!` to the `shop` before using it as the request host. This creates an identity-binding gap: the host that receives the app's `client_secret` is not validated against the trusted Shopify domain allow-list, only the JWT `aud` claim is checked.

### Finding Description
In `lib/shopify_api/auth/token_exchange.rb`: [1](#0-0) 

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = {
  client_id: ShopifyAPI::Context.api_key,
  client_secret: ShopifyAPI::Context.api_secret_key,
  ...
}
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```

`JwtPayload#shop` only strips the `https://` prefix off the raw `dest` claim; it performs no allow-list check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) 

The only identity check performed in `JwtPayload#initialize` is that `aud == Context.api_key`: [3](#0-2) 

That check validates the app identity (`aud`), but the host that actually receives the `client_secret` (`dest_shop`, used to build `Clients::HttpClient`'s base URL) is a completely different value and is left unvalidated.

Contrast this with `migrate_to_expiring_token` in the same file, which sends an equivalent request (also carrying `client_secret`) but explicitly sanitizes the shop first: [4](#0-3) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` exists precisely to guarantee the destination host is one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`), rejecting look-alike or attacker-controlled hosts: [5](#0-4) 

`exchange_token` bypasses this defense-in-depth entirely, relying solely on the JWT's HMAC signature (over the whole payload, including `dest`) to guarantee `dest` is a legitimate Shopify domain. This is an equality mismatch between "the identity that is checked" (`aud == api_key`) and "the host that actually receives the secret" (`dest_shop`, unchecked), matching the report's bug class of a check that validates one field while a different field drives the sensitive action.

### Impact Explanation
If `dest_shop` is ever attacker-influenced (e.g., a non-Shopify-controlled JWT issuer accepted by a misconfigured/relaxed verification path, a proxy/relay that forwards a modified `dest` while keeping a valid signature from a differently-scoped key, or any future regression in `JwtPayload` signature handling), the app's `client_id` and `client_secret` would be sent directly to that host — this is SSRF carrying the app's own OAuth credentials, which can lead to full credential exfiltration of the app's `client_secret`, matching the "High – SSRF with the app's credentials" impact category in scope.

### Likelihood Explanation
Under the current, correctly-functioning JWT verification, `dest` is bound by the HMAC signature and can't be independently forged by an attacker who lacks the `api_secret_key`. However, the missing allow-list check removes a defense-in-depth layer that the maintainers evidently consider necessary — they added it for the near-identical `migrate_to_expiring_token` flow and for OAuth callback shop handling elsewhere. The exposure is real whenever the JWT-verification guarantee is weakened (e.g., old-secret rollover mismatches, a future bug in `decode_token`, or a caller passing an already-parsed/less-trusted token payload), at which point exploitation requires no privileged credentials — this inconsistency is a directly reachable code path with every legitimate `exchange_token` call.

### Recommendation
Route `dest_shop` through `ShopifyAPI::Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`, raising `Errors::InvalidShopError` on failure) in `exchange_token` before constructing `shop_session`/`Clients::HttpClient`, exactly as already done in `migrate_to_expiring_token`, so the host receiving `client_id`/`client_secret` is always independently verified against the trusted Shopify domain list rather than trusting the raw `dest` claim alone.

### Proof of Concept
Conceptual PoC (illustrates the missing check by comparison with the sibling method):
```ruby

dest_shop = jwt_payload.shop        # <-- no ShopValidator.sanitize! applied
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
