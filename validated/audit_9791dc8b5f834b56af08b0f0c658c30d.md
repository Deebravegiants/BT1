### Title
Withdrawal status/tx-hash misreport due to asset-only matching in `findMatchingWithdrawal` - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the withdrawal outcome for a given `WithdrawalIdentifier` by looking up the PoA relayer's status list and matching entries **only by `assetId`** (via `near_token_id`/`defuse_asset_identifier`), explicitly ignoring the batch `index` that uniquely identifies which specific withdrawal instruction the caller is asking about.

### Finding Description
`describeWithdrawal` calls:
```
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
``` [1](#0-0) 

The comment above the call and the accompanying tests confirm this is deliberate: "Response list is unsorted, so we match by assetId instead of index" and a dedicated test titled "matches withdrawal by assetId, not by index" verifies the matcher selects an entry purely from the token identifier (`near_token_id`), not from `index`, destination address, or amount. [2](#0-1) 

`describeWithdrawal` is invoked per-`WithdrawalIdentifier` (which carries a unique `index` for "per-bridge withdrawal sequence number") [3](#0-2) 
and its result feeds directly into `watchWithdrawal`, which treats a `"completed"` status/`txHash` as authoritative proof of on-chain settlement: [4](#0-3) 

The equality that should hold is: *the `txHash`/`status` returned for withdrawal N equals the actual on-chain outcome of withdrawal N*. Because matching keys only on `assetId`, if a caller performs two (or more) withdrawals of the **same asset** to **different destination addresses** within a batch (or issues repeated withdrawals of the same token while a prior one is still pending on the relayer side), `findMatchingWithdrawal` can return the relayer record belonging to a different withdrawal instruction that merely shares the token identifier. The `index` field that exists precisely to disambiguate batched withdrawals is never consulted.

### Impact Explanation
This breaks the "status reported that is not the on-chain outcome" equality called out in the rules. A caller (or integrator built on top of the SDK, e.g. wallet/back-end crediting user balances once `watchWithdrawal` resolves) could receive a `"completed"` status with a `txHash` belonging to a *different* withdrawal of the same asset. Consequences:
- An integrator may credit/mark-as-settled the wrong withdrawal, while the actual withdrawal it queried about is still pending or failed.
- Conversely, a failed/refunded status of a *different* withdrawal with the same asset could be misattributed to the queried withdrawal, causing premature refund or double handling.

This matches the High-impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
The scenario requires nothing malicious by any party — it only requires an ordinary, unprivileged user (or the SDK's own batch-withdrawal helper) to submit more than one PoA-bridge withdrawal of the same token within the relayer's unresolved window (the relayer's status list is explicitly "unsorted", and lookups do not filter by index/destination/amount). Given the SDK explicitly supports batched/multiple withdrawals, this is a realistic occurrence, not a contrived edge case.

### Recommendation
Update `findMatchingWithdrawal` (in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and the analogous helper in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate entries using additional identifying fields beyond `assetId` — e.g., destination `address`, `amount`, and/or a per-tx sequence/index correlated with the relayer's response ordering — so that the returned status/tx hash can be proven to correspond to the specific withdrawal being queried, not merely to "any withdrawal of the same token."

### Proof of Concept
1. Caller submits, within the same NEAR transaction (or in quick succession), two POA-bridge withdrawals of `nep141:usdt.omft.near`: withdrawal #0 to address `A` for 100 USDT, and withdrawal #1 to address `B` for 50 USDT.
2. Caller calls `sdk`'s withdrawal watcher for withdrawal #1 (`index: 1`, `destinationAddress: B`).
3. The PoA relayer's `getWithdrawalStatus` response list contains both entries; `findMatchingWithdrawal` scans for the first entry whose `near_token_id`/`defuse_asset_identifier` equals `usdt.omft.near`.
4. If withdrawal #0 (to `A`) appears first in the (unsorted) list, `describeWithdrawal` returns `{ status: "completed", txHash: <tx to A> }` for the query about withdrawal #1 (to `B`), even though withdrawal #1 might still be pending/failed.
5. `watchWithdrawal` resolves with the wrong `txHash`, and any integrator relying on this "completed" result treats withdrawal #1 as settled using the tx hash belonging to withdrawal #0.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
