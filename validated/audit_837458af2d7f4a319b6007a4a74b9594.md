### Title
Empty `order.output.assets` array permanently locks escrowed input tokens in same-chain intent fills - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`placeOrder` in `IntentGatewayV2.sol` only validates that `order.inputs.length != 0`; it never validates that `order.output.assets.length != 0`. When a same-chain order is later filled with an empty `output.assets` array, `_fillSameChain` sizes its escrow-release arrays to `outputsLen` (0) instead of `inputsLen`, so no escrowed input tokens are ever transferred, yet the order is still marked as fully filled/finalized — permanently freezing the escrowed funds, exactly the "unvalidated empty array causes fund lock" bug class from the referenced OpenQ report (empty `payoutSchedule` array on `TieredFixedBountyV1.initialize`).

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` only checks `order.inputs.length == 0` [1](#0-0) . It never enforces `order.output.assets.length > 0`, and the duplicate-output-token check simply iterates zero times for an empty array without reverting [2](#0-1) , so a user can freely mint an order with non-empty `inputs` (tokens get escrowed) and an empty `output.assets` array.

When a solver later calls `fillOrder` for a same-chain order (`order.source == order.destination`), execution routes to `_fillSameChain`. This function derives its escrow-release size from the **output** array length, not the input array length:

```solidity
uint256 outputsLen = order.output.assets.length;
...
bool isFullyFilled = true;
TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

for (uint256 i; i < outputsLen; i++) { ... }
``` [3](#0-2) 

With `outputsLen == 0`, the loop body that would set `isFullyFilled = false` and populate `escrowedInputs`/`outputFills` never runs, so `isFullyFilled` stays `true` (its initialized value) and `escrowedInputs` remains a zero-length array. The function then calls:

```solidity
WithdrawalRequest memory body = WithdrawalRequest({
    commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
});
_withdraw(body, false, isFullyFilled);

if (isFullyFilled) {
    _execute(order, outputsLen);
    emit OrderFilled(...);
}
``` [4](#0-3) 

`_withdraw` with `finalize == true` (`isFullyFilled == true`) sets `_filled[commitment] = beneficiary`, permanently marking the order as finalized [5](#0-4) , but its token-release loop iterates over `body.tokens` (the empty `escrowedInputs` array), so it releases nothing [6](#0-5) . The original escrow entries in `_orders[commitment][token]` (credited during `placeOrder`, see `_orders[commitment][token] = reducedInputs[i].amount;`) are never decremented or transferred out [7](#0-6) .

Because `_filled[commitment]` is now non-zero, the order is considered finalized: a subsequent `cancelOrder`/refund attempt would be rejected as already filled, and no other code path reclaims the escrow. The user's input tokens are trapped in the gateway contract with no route to recover them, exactly analogous to the OpenQ report where an unvalidated empty `payoutSchedule` array caused the bounty to be marked claimed while leaving funds stuck.

### Impact Explanation
Any unprivileged order placer can permanently freeze their own (or induce freezing of) escrowed input tokens by submitting `output.assets = []`. Once any solver calls `fillOrder` on such an order (even trivially, since `options.outputs` can also be empty and the loop simply does nothing), the order is marked filled with zero tokens transferred to the solver and zero tokens returned to the user — the escrowed input amount is permanently locked in the `IntentGatewayV2` contract. This meets the "permanent freezing of funds" impact bar (High), since there is no recovery path once `_filled[commitment]` is set.

### Likelihood Explanation
Likelihood is high: `placeOrder` is fully permissionless and takes an arbitrary `Order` struct from any caller, and there is no length check preventing `output.assets` from being empty. Triggering the freeze requires only a single additional permissionless `fillOrder` call (which anyone, including the order placer themselves via a colluding/throwaway address, can issue) — no privileged role, governance, or malicious solver behavior is needed.

### Recommendation
In `placeOrder` (or in `_fillSameChain`), require `order.output.assets.length > 0` and reject a fill/mismatch where `escrowedInputs`/`outputFills` sizing diverges from `order.inputs.length`. Concretely:
- Add `if (order.output.assets.length == 0) revert InvalidInput();` in `placeOrder` in `evm/src/apps/IntentGatewayV2.sol`.
- Defensively, in `_fillSameChain`, derive `isFullyFilled` from actual escrow release coverage of all `order.inputs`, not merely from an uninitialized `true` flag over a possibly-empty output loop, so a mismatched or empty output array cannot finalize an order without releasing its full escrow.

### Proof of Concept
1. Attacker (or any user) calls `IntentGatewayV2.placeOrder` with `inputs = [{token: USDC, amount: 1000e6}]` and `output = {beneficiary: X, assets: [], call: "0x"}` — this passes validation because only `inputs.length == 0` is checked [1](#0-0) . The 1000 USDC is escrowed under the resulting `commitment`.
2. Any address calls `fillOrder(order, FillOptions({..., outputs: []}))`. Since `order.source == order.destination`, execution reaches `_fillSameChain`, where `outputsLen = 0`.
3. The for-loop body never executes; `isFullyFilled` stays `true`; `escrowedInputs` is a 0-length array [3](#0-2) .
4. `_withdraw(body, false, true)` is called with `body.tokens` empty: `_filled[commitment]` is set (order finalized) but the loop over `body.tokens` does nothing, so the escrowed 1000 USDC is never moved [8](#0-7) .
5. `OrderFilled` is emitted, the order is permanently finalized, and the 1000 USDC remains stuck in the `IntentGatewayV2` contract with no remaining code path (cancel is blocked once `_filled` is set) to recover it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
