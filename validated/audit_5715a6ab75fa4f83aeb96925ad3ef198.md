Found it. The Tron deployment of `IntentGatewayV2` (a separate production contract from the main EVM app) uses raw low-level `.call()` for ERC20 transfers in `withdraw()` and the `SweepDust` handler, checking only that the call didn't revert (`success`) but never decoding/verifying the boolean return value of `transfer()`. This is the exact bug class from the DODO report: an external call's return value that signals success/failure is not validated, so a non-standard ERC20 that returns `false` on failure instead of reverting would let escrow accounting decrement while the beneficiary silently receives nothing.

### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` allows silent transfer failure while escrow is debited - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` and the `SweepDust` handler in the Tron `IntentGatewayV2` release escrowed tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call did not revert (`success`), never decoding the returned `bool`. Non-standard/broken ERC20 tokens that return `false` on failure instead of reverting will pass this check even though no tokens moved.

### Finding Description
In `withdraw()`, escrowed balances are decremented unconditionally right after the `.call` succeeds at the EVM level: [1](#0-0) 
and the fee-redemption path exhibits the identical pattern: [2](#0-1) 
The `SweepDust` request handler in `onAccept` has the same gap: [3](#0-2) 

By contrast, the primary EVM app (`IntentsBase.sol`) uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value (or requires a revert for non-standard tokens): [4](#0-3) 
The Tron variant of the gateway does not use `SafeERC20` for these paths, relying only on `success` from the raw call, which only reflects whether the callee reverted — not whether `transfer` returned `true`.

### Impact Explanation
This is directly analogous to the DODO “Check return value of sellQuote/sellBase” finding: an external call whose return value communicates success/failure is not validated. Here, if any escrowed input token is a non-reverting ERC20 that returns `false` on failure (e.g., due to a paused state, blacklist, or non-standard implementation), `withdraw()` will decrement `_orders[commitment][token]` and mark the order filled/refunded while the beneficiary (solver or user) receives zero tokens — the escrowed value is permanently lost from the beneficiary's perspective, and the accounting state is falsely finalized (`EscrowReleased`/`EscrowRefunded` emitted, order marked filled) even though funds never moved.

### Likelihood Explanation
Reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` message through Hyperbridge, or by Hyperbridge dispatching a `SweepDust` request — i.e., any completion of the standard cross-chain intent settlement flow. It requires the escrowed token to be a non-standard ERC20 that returns `false` rather than reverting on failure; such tokens are common enough (and the IntentGateway's token allowlisting model does not appear to exclude such tokens) to make this a realistic path to fund loss for solvers/users on the Tron deployment.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee-redemption branch) and in the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, matching the approach already used in `evm/src/apps/intentsv2/IntentsBase.sol`. At minimum, decode the returned bytes and require `abi.decode(result, (bool)) == true` when `result.length > 0`, in addition to checking `success`.

### Proof of Concept
1. Escrow a malicious/non-standard ERC20 token (that returns `false` on `transfer` failure instead of reverting, e.g., after being paused by its own admin, or simply hard-coded to return `false`) via `placeOrder`.
2. Trigger a `RedeemEscrow` (or `RefundEscrow`) message that reaches `onAccept` → `withdraw()`.
3. Have the token's `transfer` call return `false` (but not revert) for the beneficiary.
4. Observe that `withdraw()` proceeds: `success` is `true` (the call itself didn't revert), so `_orders[body.commitment][token] -= amount` executes and `EscrowReleased`/`EscrowRefunded` is emitted, while `beneficiary`'s token balance is unchanged — funds are permanently unaccounted for and unrecoverable through the normal flow.
