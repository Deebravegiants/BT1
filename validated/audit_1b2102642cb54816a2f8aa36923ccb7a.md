### Title
Market-wide permanent freeze from RAY debt-value overflow during accrual - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large borrowed position can make `borrowed * borrow_index` exceed the `i128` accounting domain during interest accrual. Because every market mutation accrues before acting, the resulting `MathOverflow` permanently blocks repayment, withdrawal, liquidation, and future index updates for that market. Severity: Medium. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` computes utilization by unscaling the stored RAY share totals with `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [3](#0-2)  `scaled_to_original` delegates to `Ray::mul`, which evaluates `scaled * index / RAY` through `mul_div_half_up` and rejects a quotient that cannot fit `i128`. [4](#0-3) [5](#0-4) 

The borrow index itself is capped only after its multiplication succeeds, and that cap does not bound the separate `borrowed * borrow_index` valuation. [6](#0-5)  For an 18-decimal asset, one billion whole tokens become `10^36` RAY-scaled shares, so a borrow index around 170 times its initial value makes the unscaled debt value exceed `i128::MAX`. [7](#0-6) 

The public controller `update_indexes` path reaches the owner-only pool entrypoint with `hub_assets: Vec<HubAssetKey>`; the pool loads each market and invokes `global_sync`. [8](#0-7) [9](#0-8)  `global_sync` calls `accrue_chunk` for each elapsed interval and only calls `mark_accrued` after all chunks complete, so an overflow reverts without advancing `last_timestamp` or committing the market. [10](#0-9) [11](#0-10) 

The same `global_sync` is performed by `synced_market`, which is used by pool mutation legs before supply, borrow, withdraw, repay, settlement, seizure, strategy, recapitalization, or revenue logic executes. [12](#0-11)  Consequently, once the stored scaled debt and index cross the product bound, every later entrypoint touching that market fails at the same accrual expression. [13](#0-12) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected `(hub_id, asset)` market. [13](#0-12)  Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce the debt, and explicit index updates cannot advance the market because all of those paths run the same overflowing accrual first. [2](#0-1) [14](#0-13)  The panic also prevents `mark_accrued`, so there is no partial progress that would later allow the market to recover. [15](#0-14) 

### Likelihood Explanation
An unprivileged attacker can establish the state using ordinary `supply` and `borrow` calls when configured caps, collateral value, and token liquidity permit roughly `10^36` RAY-scaled debt, then trigger the failure through `update_indexes` with `hub_assets = vec![HubAssetKey { hub_id, asset }]`. [8](#0-7) [9](#0-8)  The requirement is economically substantial because the attacker must control enough collateral and liquidity to create the oversized borrow, and the index must grow enough for its product with scaled debt to exceed `i128::MAX`. [16](#0-15) 

The repository already contains a directed reproduction using a one-billion-token, 18-decimal market at 98% utilization; it reaches `MathOverflow` before `MAX_BORROW_INDEX_RAY` and subsequently rejects both withdrawal and repayment. [17](#0-16) 

### Recommendation
Add an explicit market-value ceiling before accrual and reject new supply or borrow when `scaled_total * current_index / RAY` is near `i128::MAX`, rather than allowing the market to enter an unrecoverable state. [18](#0-17) [19](#0-18)  A complementary recovery mechanism should allow accrual to stop or clamp safely at a configured market-total ceiling, while preserving liquidation and repayment paths instead of panicking inside `scaled_to_original`. [10](#0-9) [2](#0-1) 

### Proof of Concept
The directed harness test creates an 18-decimal market, deposits `1_000_000_000 * 10^18` base units, borrows 98%, advances ledger time until `update_indexes` fails, and proves that subsequent withdraw and repay calls fail with `MathOverflow`. [17](#0-16)

    t.try_repay(ALICE, "BIG18", 1.0),

```rust
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
```

```markdown
| Bound | Consequence |

| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
