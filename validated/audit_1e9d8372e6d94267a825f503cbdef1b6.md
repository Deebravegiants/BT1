## Finding

### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the shop-domain header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value taken from an **unauthenticated** header. Because the `shop-domain` header is not part of the signed material, any party who can obtain one valid `(body, hmac)` pair signed with the app's shared secret — e.g., an attacker who installs the app on their own store and captures a legitimate webhook delivery — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. The HMAC check still passes (it only checks the body bytes), and the webhook handler is invoked believing the event belongs to a different, victim shop.

### Finding Description
The webhook HMAC validator computes/verifies the signature only over `to_signable_string`, which for `Webhooks::Request` returns `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read from HTTP headers that are never fed into the signable string: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever operate on `verifiable_query.to_signable_string` (the body) compared against the HMAC header — no header field, including `shop`, is part of what is authenticated: [3](#0-2) 

`Registry.process` performs only this HMAC check, then unconditionally trusts `request.shop` and forwards it to the handler as the identity of the shop the event came from: [4](#0-3) 

The broken identity binding is:
`shop header used to attribute the webhook event` ≠ `bytes actually covered by the HMAC (raw body only)`

Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app (it is not per-shop), an unprivileged attacker can:
1. Install the app on their own (attacker-controlled) shop.
2. Trigger a webhook event and capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — this is a legitimately, correctly-signed pair.
3. Replay the identical body and HMAC value to the app's webhook endpoint, but with `x-shopify-shop-domain` changed to a victim shop's domain (and optionally a different `x-shopify-webhook-id`, which is also unauthenticated).
4. `HmacValidator.validate` succeeds because the signed bytes (the body) are unchanged, and `Registry.process` calls the handler with `WebhookMetadata` whose `shop` is the attacker-chosen victim domain.

If the host application's webhook handler uses `data.shop` to look up per-tenant session/data (a documented, expected usage pattern, since `WebhookMetadata#shop` is the field this gem exposes specifically for that purpose), this lets an attacker cause the app to process/act on data attributed to a shop they do not own — a cross-tenant identity confusion rooted entirely in this gem's webhook verification logic, not in host-application misuse.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the gem's own API (`WebhookMetadata#shop`) hands callers a shop identity that was never actually authenticated, only the payload bytes were. This maps to the report's "cross-tenant access" category — a Critical impact per this gem's own webhook verification contract, since any consumer built per the gem's documented usage inherits the spoofable `shop` binding.

### Likelihood Explanation
Moderate-to-high: it requires no privileged credentials, TLS interception, or leaked secrets. It only requires the attacker to be able to install the target app onto any shop they control (a normal, unprivileged capability for any Shopify merchant/developer) and capture one legitimate webhook delivery for that shop, then replay it with a forged header against the same app's public webhook endpoint.

### Recommendation
Include the authenticated identity fields (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the signable string that `HmacValidator` verifies, rather than only the raw body, so that the `shop` value handed to handlers is cryptographically bound to the same secret-backed signature. Alternatively/additionally, cross-check `request.shop` against an app-known/authorized shop list before dispatching to the handler, and document to consumers that `WebhookMetadata#shop` is not currently covered by the HMAC.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a real webhook delivery, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over BODY>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: <id>

BODY
```
2. Replay the exact same `BODY` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, only changing the header:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts this request as valid, because the HMAC only covers `BODY`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the request never actually originated for that shop.

          received_signature = verifiable_query.hmac
