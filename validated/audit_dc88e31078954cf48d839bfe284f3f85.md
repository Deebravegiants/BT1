Confirmed: `process_withdraw` ( [1](#0-0) ) bundles the coin-vault transfer, pc-vault transfer, and LP burn into one instruction with no ability to skip a bad leg, and no freeze/pausable checks are performed anywhere in the file (`freeze`/`Frozen` do not appear in `processor.rs`).

### Title
Withdrawal permanently blocked if either pooled token becomes frozen/paused, trapping LP funds in the other token - (File: program/src/processor.rs)

### Summary
`process_withdraw` performs two sequential SPL-token transfers (coin vault → user, pc vault → user) and an LP burn, all inside a single atomic instruction, with no fallback path if one of the two transfers reverts.

### Finding Description
Raydium AMM pools pair two arbitrary SPL tokens chosen at `Initialize2` time. During withdrawal, `Processor::process_withdraw` computes `coin_amount` and `pc_amount` and then unconditionally issues both transfers before burning the LP tokens: [1](#0-0) 
Neither `unpack_token_account` nor any other check in `process_withdraw` inspects the SPL token account's `state` field (frozen/initialized) or otherwise anticipates a transfer that reverts for reasons outside amount/balance checks. If the mint of either the coin or the pc side has a freeze authority (extremely common for real-world stablecoins/tokens) and that authority freezes the AMM's vault token account or the user's destination token account, `spl_token::instruction::transfer` invoked via `Invokers::token_transfer_with_authority` will fail: [2](#0-1) 
Because Solana instructions execute atomically, a revert on the second transfer (e.g., the pc-side) unwinds the successful first transfer (coin-side) and the LP burn. Since `process_withdraw` provides no per-token or partial-withdraw path (both transfers and the burn are mandatory in one instruction), every LP holder is permanently unable to withdraw their principal in *either* token, even though only one of the two tokens is frozen/malicious. The same atomic bundling pattern (deposit both coin+pc, or take pnl both coin+pc) exists in `process_deposit` and `process_withdrawpnl`: [3](#0-2) [4](#0-3) 

### Impact Explanation
This results in permanent freezing of LP funds: once one side of the pool becomes untransferable (frozen account, paused/blacklist-style token, or a token with a reverting transfer hook), all liquidity providers lose the ability to redeem their share of *both* pooled assets, not just the problematic one. There is no admin or user-level mechanism in `process_withdraw` to bypass or isolate the failing leg, so funds are stuck indefinitely.

### Likelihood Explanation
Likelihood is Medium-High in practice: pool creation via `Initialize2` is permissionless with respect to token choice (any SPL mint tied to an OpenBook/Serum market can be paired), so an attacker or the token issuer itself can create a pool with a token whose freeze authority is later exercised, or engineer a mint that fails transfers for non-approved destinations. Because both legs of `process_withdraw` are required to succeed atomically with no isolation, a single frozen/paused token traps all LPs' funds, mirroring the reported bug class where one malicious/paused asset in a batch operation blocks recovery of unrelated, otherwise-healthy assets.

### Recommendation
Add a withdrawal path that lets an LP redeem the healthy side of the pool even if the other token's transfer fails (e.g., split withdrawal into two independent instructions/CPIs with partial-success handling, or allow specifying which side to skip). At minimum, detect vault/user token account freeze state (`spl_token::state::Account::state`) before transferring and return a distinguishable error, and consider an admin-gated "isolate/skip token" mechanism analogous to the recommendation in the reported OpenQ issue.

### Proof of Concept
1. Pool creator initializes an AMM pool (`Initialize2`) pairing a normal token (coin) with a token whose mint has a freeze authority (pc).
2. LPs deposit into the pool via `process_deposit`, receiving LP tokens.
3. The pc token's freeze authority freezes the AMM's `pc_vault` account (or any user's `user_dest_pc` destination account) — this is entirely outside the AMM program's control.
4. Any LP calls `process_withdraw`; the coin-side `Invokers::token_transfer_with_authority` succeeds, but the pc-side transfer fails because the vault/destination account is frozen, causing the whole instruction (including the earlier coin transfer and the pending LP burn) to revert atomically.
5. No instruction in the program allows the LP to withdraw only the coin side — all LPs' coin and pc principal remains permanently locked in the vaults.

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
