### Title
Opaque swap routes can inject unauthorized token transfers into the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
An attacker can deploy a malicious venue contract and encode a swap route that invokes it through a position operation such as `swap_collateral`. [1](#0-0)  The malicious venue can call `token.transfer(victim, attacker, amount)` while the route executes, causing Soroban simulation to attach that unrelated transfer as a child invocation under the victim's authorized controller call. [2](#0-1)  If the victim signs the generated authorization tree, the unrelated token transfer executes even though the lending operation itself completes normally. [3](#0-2) 

### Finding Description
`swap_collateral` accepts `swap` as opaque `Bytes`, authenticates the caller, verifies that the caller owns or manages the account, withdraws collateral, and passes the opaque route into the swap helper. [4](#0-3) 

`swap_tokens` does not parse, validate, or restrict the route's destination contracts; it snapshots input/output balances, authorizes one exact controller-to-router input transfer, and forwards the bytes to `SwapAggregatorClient::execute_strategy`. [5](#0-4) 

The router interface accepts the untrusted `swap_xdr` argument directly. [6](#0-5)  Route instructions select a pool address and dispatch execution to it, so route bytes function as executable control data rather than merely swap parameters. [7](#0-6) 

A route-selected contract therefore runs inside the transaction while the account owner's `caller.require_auth()` authorization is active. [8](#0-7)  The repository's authorization test demonstrates that a rogue hop pool's `token.transfer(caller, attacker, amount)` is recorded beneath the victim's `swap_collateral` authorization and succeeds when the victim signs the poisoned tree. [9](#0-8) 

This is analogous to the referenced argument-injection bug: attacker-controlled route data crosses a trust boundary and is interpreted as executable arguments, while the authorization prompt conflates the intended swap with unrelated privileged token calls. [10](#0-9) 

### Impact Explanation
A malicious route can transfer arbitrary token balances from the signing user's wallet to an attacker while still returning a valid output and satisfying the controller's measured-output check. [11](#0-10)  The demonstrated path drains an unrelated wallet token while the collateral swap succeeds and deposits the expected output. [3](#0-2)  This constitutes theft of user funds rather than only route-quality loss, because the stolen token need not be the swap input, swap output, or a protocol-listed asset. [12](#0-11) 

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-constructed route and sign the authorization tree containing the malicious transfer, so it is conditional on malicious quoting, route injection, or insufficient wallet disclosure. [13](#0-12)  No privileged role, leaked key, contract upgrade, or compromised router configuration is needed to deploy a route-selected contract and encode the malicious behavior. [14](#0-13)  The controller's positive-output and account-risk checks do not bound unrelated wallet-token transfers, so a fair-looking swap can still carry the malicious child authorization. [15](#0-14) 

### Recommendation
Do not allow user-controlled route bytes to select arbitrary venue contracts. Enforce an on-chain allowlist or registry of governance-approved pool contracts and venue adapters before dispatching each hop. At a minimum, decode routes before execution, reject unrecognized venue addresses, and ensure the signed authorization tree cannot gain unrelated token-transfer children through route-selected code. [16](#0-15)  Client-side route decoding should remain a secondary defense, because the vulnerability is the protocol's unbounded execution of route-selected contracts under the user's authorization context. [17](#0-16) 

### Proof of Concept
1. Deploy a malicious contract that implements the expected route-hop entrypoint but internally calls `token.transfer(victim, attacker, wallet_balance)`. [18](#0-17) 
2. Encode a route whose selected pool is that contract, using the victim's collateral token as input and a listed collateral token as output. [14](#0-13) 
3. Have the victim invoke `swap_collateral(caller, account_id, current, amount, new, swap)` with that route. [19](#0-18) 
4. Simulation records `token.transfer(victim, attacker, wallet_balance)` as a child of the victim's `swap_collateral` authorization. [2](#0-1) 
5. Signing that authorization tree makes the unrelated transfer succeed, after which the victim's unrelated wallet balance is zero while the protocol position receives the expected swapped collateral. [9](#0-8)
