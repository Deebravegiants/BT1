### Title
Permanent freeze of pool funds via unrecoverable `calc_take_pnl` invariant check in `Deposit`/`Withdraw`/`WithdrawPnl` - (File: `program/src/processor.rs`)

### Summary
`calc_take_pnl` enforces a hard invariant — the pool's current value (`pool_pc_amount * pool_coin_amount`) must be `>=` the last recorded snapshot value (`calc_pnl_x * calc_pnl_y` stored in `TargetOrders`) — and returns a fatal `AmmError::CalcPnlError` if this does not hold, with **no state mutation on the failing path**. [1](#0-0) [2](#0-1) 

This function is invoked unconditionally in `process_deposit`, in `process_withdraw` (except when `amm.status == WithdrawOnly`), and in `process_withdrawpnl`. [3](#0-2) [4](#0-3)  Because `target_orders.calc_pnl_x`/`calc_pnl_y` are only ever advanced *after* `calc_take_pnl` succeeds, once the invariant is violated there is no unprivileged transaction that can ever move the pool back into a state where the check passes again — every future `Deposit` and `Withdraw` call (both reachable by any LP with attacker-chosen accounts/data) will keep hitting the same `else` branch and abort. [5](#0-4) [6](#0-5) 

### Finding Description
The only way to bypass the invariant check in withdrawal is `amm.status == AmmStatus::WithdrawOnly`, which is a value set exclusively through the privileged `SetParams` instruction controlled by the AMM owner/config authority — not something an ordinary LP can trigger themselves. [7](#0-6)  This mirrors exactly the reported bug-class structure: a legitimate user action (deposits/withdraws/PnL bookkeeping updating a stored snapshot value) can leave behind an internal state (`calc_pnl_x`/`calc_pnl_y`) that a later required check (`pool value >= snapshot value`) can never satisfy again through the normal unprivileged exit path (`Withdraw`), permanently freezing the funds of every remaining LP in the pool unless the privileged owner manually intervenes — and even then only `Withdraw` is unblocked, not `Deposit` or `WithdrawPnl`.

The `calc_pnl_x`/`calc_pnl_y` bookkeeping is a running approximation maintained across successive `Deposit`/`Withdraw`/`WithdrawPnl` calls via decimal normalization/restoration (`normalize_decimal_v2`/`restore_decimal`) and `checked_add`/`checked_sub` arithmetic in system-decimal space, while the comparison in `calc_take_pnl` is re-derived independently from live vault balances each call. [8](#0-7)  Any accumulated rounding drift between these two independently-computed quantities (both driven by ordinary, unprivileged LP deposit/withdraw sequences with attacker-chosen amounts) can push `calc_pnl_x * calc_pnl_y` above the live `pool_pc * pool_coin` product, tripping the `else` branch permanently.

### Impact Explanation
Once triggered, `process_deposit`, `process_withdraw` and `process_withdrawpnl` become permanently unusable for the affected pool (outside of a privileged status change), which halts all liquidity entry/exit and PnL settlement — a direct freezing of user and LP funds inside the AMM vaults, matching "permanent freezing of user or LP funds" in the acceptance criteria.

### Likelihood Explanation
The precise numeric conditions required to invert the invariant depend on rounding behavior of `Calculator::normalize_decimal_v2`/`restore_decimal`/`calc_x_power`, which I was not able to fully verify from the indexed source in this session. I flag this as the strongest structural analog to the reported bug class (an unprivileged, non-owner-reversible state that blocks the normal exit-check for all users), but I cannot confirm from the available code whether the arithmetic actually admits the drift needed to trip the `else` branch under realistic swap/deposit/withdraw sequences — this needs concrete numerical PoC verification (e.g., a Rust test iterating deposit/withdraw combos with adversarial decimal ratios) before treating it as a confirmed, exploitable finding.

### Recommendation
- Make `calc_take_pnl`'s failure path recoverable by an unprivileged actor: e.g., clamp/resync `calc_pnl_x`/`calc_pnl_y` to the live pool totals instead of hard-erroring, or skip PnL-delta extraction (delta = 0) when the invariant does not hold rather than aborting the whole instruction.
- Ensure `Withdraw` (and ideally `Deposit`) can never be permanently gated behind a value that only a privileged `SetParams` caller can unstick.
- Add fuzz/property tests that repeatedly interleave `Deposit`/`Withdraw` with adjacent decimal configurations (`pc_decimals` vs `coin_decimals`) to confirm whether `calc_pnl_x * calc_pnl_y` can exceed `pool_pc * pool_coin` through normal rounding.

### Proof of Concept
Not constructed — a working PoC requires concrete numeric inputs into `Calculator::normalize_decimal_v2`/`restore_decimal` to demonstrate that ordinary deposit/withdraw sequences can push `target_orders.calc_pnl_x * calc_pnl_y` above the live `pool_pc_amount * pool_coin_amount`, which the current search/read tooling did not allow me to fully validate. The reference test harness for this logic exists at [9](#0-8)  and would be the starting point for constructing such a PoC.
