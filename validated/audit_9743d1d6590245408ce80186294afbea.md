## PoA Bridge withdrawal status matching ignores the withdrawal index, causing status/tx-hash misreport for batched same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific withdrawal item in a batch by matching only on `assetId`, ignoring the `index` that `createWithdrawalIdentifier` assigns to disambiguate multiple withdrawals of the same token within one NEAR transaction. This breaks the equality "the status/tx-hash returned for withdrawal N" == "the on-chain outcome of withdrawal N", letting an unprivileged caller who batches two or more withdrawals of the same token to different destinations get the wrong item's completion status and transaction hash.

### Finding Description
`IntentsSDK.createWithdrawalCompletionPromises` builds a `WithdrawalIdentifier` per withdrawal via `createWithdrawalIdentifier`, which records a per-bridge `index`: [1](#0-0) 

For PoA bridge this index is stored in the identifier but never used again: [2](#0-1) 

`describeWithdrawal` then resolves the status by calling `findMatchingWithdrawal`, which filters the POA bridge API response only by `assetId` and returns the *first* array match, regardless of which index/destination it actually belongs to: [3](#0-2) [4](#0-3) 

The code comment explicitly documents that this collapses distinct withdrawals of the same token into one match: "This means multiple withdrawals of the same token in a single transaction are not supported." That means if a user (unprivileged, no cooperation from relayer/admin needed) submits a single NEAR intent transaction containing two `ft_withdraw` intents for the same `assetId` but different destination addresses/amounts, `watchWithdrawal` for *both* `WithdrawalIdentifier`s (index 0 and index 1) will resolve against the same underlying POA withdrawal record — because `.find()` returns the same first matching element for every call, irrespective of the caller-supplied index.

### Impact Explanation
Because the reported `status`/`txHash` for index 1 is actually the outcome of the withdrawal at index 0 (or vice versa), a consuming integrator that watches the promises returned by `createWithdrawalCompletionPromises` can:
- Treat a still-pending or failed withdrawal as `completed` with a transaction hash that belongs to a different withdrawal, potentially crediting the user or clearing a refund workflow prematurely for a withdrawal that never actually landed.
- Attribute one txHash to two logically distinct withdrawal legs, matching the "status or hash misreport making an integrator credit or refund twice" criterion.

This requires no malicious relayer, bridge operator, or off-chain party — only a normal user submitting a batch of same-asset withdrawals to different destinations, which is a supported feature of `IntentsSDK.createWithdrawalCompletionPromises`/`processWithdrawal` batch flows.

### Likelihood Explanation
Any integrator or end user that withdraws the same POA-bridged token to two different destinations (or amounts) in one batched transaction triggers this immediately; no timing race or privileged access is required. The only precondition is using >1 withdrawal of the same `assetId` in a single batch, which is an ordinary usage pattern the SDK's batch APIs advertise.

### Recommendation
Have `findMatchingWithdrawal` disambiguate using more than `assetId` — e.g., match on `(assetId, destinationAddress, amount)` combined with positional/ordinal matching against the POA API response, or track already-consumed matches so each `WithdrawalIdentifier.index` maps to a distinct API record instead of always resolving to the first array hit.

### Proof of Concept
1. User calls `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` with two `withdrawalParams` entries: `{assetId: "nep141:usdc.omft.near", destinationAddress: A, amount: 100}` and `{assetId: "nep141:usdc.omft.near", destinationAddress: B, amount: 200}` in the same intent transaction.
2. `createWithdrawalIdentifiers` assigns `index: 0` to the first, `index: 1` to the second (both route through `PoaBridge`). [5](#0-4) 
3. Assume the withdrawal to `A` completes first and the withdrawal to `B` is still pending/fails at the relayer. The POA bridge status API returns (at least) one `COMPLETED` record for `nep141:usdc.omft.near`.
4. `watchWithdrawal` for `index:1` (destination `B`) calls `describeWithdrawal`, which calls `findMatchingWithdrawal(withdrawals, "nep141:usdc.omft.near")` — this returns the same completed record belonging to destination `A`'s withdrawal.
5. The caller watching withdrawal #2 (destination `B`) observes `{status: "completed", txHash: <A's tx hash>}`, even though `B`'s withdrawal has not completed (or failed), because the match ignores `index`/destination/amount entirely.

```typescript
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
