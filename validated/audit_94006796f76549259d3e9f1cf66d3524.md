### Title
Zcash TEX addresses are not case-normalized before being wrapped into `recipient`, unlike Bitcoin - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts`)

### Summary
`deriveOmniWithdrawIntentParams` lowercases the destination address only when `params.omniChainKind === ChainKind.Btc`, even though `isUtxoChain` treats `ChainKind.Zcash` identically to `ChainKind.Btc` and Zcash `tex1...` addresses are the same bech32m encoding family that is case-sensitive on-chain. A caller-supplied uppercase (or otherwise non-canonical-case) `tex1...` address that passes `validateZcashAddress` is forwarded unnormalized into `omniAddress`, producing a `recipient`/signed payload whose casing may not match what the Zcash connector accepts.

### Finding Description
The broken equality: `recipient` string encoded into the signed intent (`omniAddress(ChainKind.Zcash, destinationAddress)`) should equal the canonical-case form the Zcash UTXO connector expects on-chain. For BTC this equality is enforced by an explicit normalization step: [1](#0-0) 

The condition is `params.omniChainKind === ChainKind.Btc`, so for `ChainKind.Zcash` the `destinationAddress` used to build `recipient` is the raw, unnormalized string the caller supplied, even though the UTXO-fee-handling branch a few lines above explicitly groups Zcash with Bitcoin as a UTXO chain: [2](#0-1) 

`validateZcashAddress` accepts a `tex1...` address purely on bech32m checksum/HRP/length grounds via `bech32m.decodeToBytes(address)`: [3](#0-2) 

Note one correction to the premise in the question: per BIP-173/350, `@scure/base`'s bech32/bech32m decoder rejects strings that mix upper and lower case letters — it only accepts a string that is *entirely* lowercase or *entirely* uppercase (internally normalizing case for the checksum computation). I could not fully verify this from the vendored source in this index (the `@scure/base` package contents are not indexed here), so this should be confirmed in a Devin session with full file access. Assuming that behavior holds, the exploitable input is not an arbitrary mixed-case string but a fully **uppercase** `TEX1...` address (e.g. `TEX1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KYGT08`), which `validateZcashAddress` accepts and which the BTC-only branch does not touch, so `recipient` retains the uppercase form.

Attacker input: an ordinary NEAR Intents user or integrator-forwarded `destinationAddress` for a Zcash withdrawal, supplied in uppercase `tex1` form. Call sequence: `validateWithdrawal` → `OmniBridge.createWithdrawalIntents` → `deriveOmniWithdrawIntentParams`, which builds `recipient = omniAddress(ChainKind.Zcash, destinationAddress)` without any case normalization, then includes it in the signed intent and in `calculateStorageAccountId`'s input. None of `compareAddresses`, `validateWithdrawal`, or the intents contract's signature/nonce checks touch address casing — they only check equality/format, not canonical case for UTXO chains.

### Impact Explanation
If the Zcash connector indeed requires canonical-case bech32m (matching the BTC connector's documented behavior, per the code's own comment "Omni contract only accepts lowercase bech32 addresses"), a withdrawal signed with an uppercase `recipient` would be accepted by the intents contract (which does no chain-specific case checks) but could be rejected or misdirected by the downstream Zcash connector after the funds have already left the user's NEAR balance. This matches the High category: "a withdrawal stuck until manual intervention," since there is no automatic recovery path once the intent is signed and submitted.

### Likelihood Explanation
Preconditions: `routeConfig` targets Zcash, the asset is a Zcash-bridged nep141 token, and the caller supplies (or an integrator forwards) a `tex1` address in non-canonical case. This costs the attacker/caller nothing extra beyond choosing an oddly-cased but validly-encoded address — no privilege escalation needed, any ordinary NEAR Intents user or integrator-forwarded string can trigger it. It is repeatable per withdrawal that uses such an address. The precise on-chain sensitivity of the Zcash connector to case (confirmed for BTC in this codebase's own comment, unconfirmed for Zcash from the code available in this index) should be verified in a full session, since it determines whether the impact materializes.

### Recommendation
Extend the normalization branch in `deriveOmniWithdrawIntentParams` to cover `ChainKind.Zcash` bech32/bech32m addresses (`tex1...`) the same way it does for BTC's `bc1...`, i.e. change the guard from `params.omniChainKind === ChainKind.Btc` to also match `ChainKind.Zcash` with the `tex1` prefix (leaving transparent `t1`/`t3` and unified `u1` addresses as-is, consistent with how BTC leaves base58 addresses untouched).

import { describe, it, expect } from "vitest";
import { ChainKind } from "@omni-bridge/core";
import { deriveOmniWithdrawIntentParams } from "../src/bridges/omni-bridge/omni-withdraw-params";

describe("deriveOmniWithdrawIntentParams - Zcash case normalization", () => {
  const baseParams = {
    assetId: "nep141:zec.omni.near", // Zcash-bridged nep141 token id
    actualAmount: 100_000n,
    intentsContract: "intents.near",
    feeEstimation: {
      // ...populate underlyingFees for RouteEnum.OmniBridge:
      // relayerFee, storageDepositFee, utxoMaxGasFee, utxoProtocolFee
    } as any,
  };

  it("BTC branch lowercases bc1 addresses", () => {
    const result = deriveOmniWithdrawIntentParams({
      ...baseParams,
      omniChainKind: ChainKind.Btc,
      destinationAddress: "BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4",
    });
    expect(result.recipient).toContain("bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4");
  });

  it("Zcash branch does NOT lowercase TEX1 addresses (asymmetry / bug)", () => {
    const result = deriveOmniWithdrawIntentParams({
      ...baseParams,
      omniChainKind: ChainKind.Zcash,
      destinationAddress: "TEX1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KYGT08",
    });
    // Equality claimed broken: recipient should equal the canonical lowercase
    // form the connector expects, but it preserves the caller's original case.
    expect(result.recipient).toContain(
      "TEX1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KYGT08",
    ); // documents current (buggy) behavior
    // Desired assertion after fix:
    // expect(result.recipient).toContain("tex1qw508d6qejxtdg4y5r3zarvary0c5xw7kygt08");
  });
});
