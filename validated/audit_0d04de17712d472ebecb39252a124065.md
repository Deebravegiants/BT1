### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that raw body. The `shop-domain` header, which the gem exposes to host-application handlers as the tenant identifier, is never part of the signed payload. Anyone who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared secret — for example a malicious merchant who has installed the app and can trigger a real webhook for their own store — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header. `Utils::HmacValidator.validate` will report the request as valid, and `Webhooks::Registry.process` will dispatch the attacker-chosen body to the handler tagged with a victim shop's domain.

### Finding Description
The binding that should hold is: `shop (bound by HMAC)` == `shop (delivered to the handler)`. In this gem it does not:

- `Request#hmac` reads the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `Request#shop` simply reads the unauthenticated `shop-domain` header, with no cryptographic tie to the body or HMAC: [2](#0-1) 

- `HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely over `verifiable_query.to_signable_string` (i.e., the body for webhooks), never touching `shop`: [3](#0-2) 

- `Registry.process` validates the HMAC and then trusts `request.shop` (from the unauthenticated header) when building the `WebhookMetadata` passed to the host's handler: [4](#0-3) 

Because the app's webhook HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, any tenant that can generate one legitimate webhook for their own store obtains a `(body, hmac)` pair that will pass `HmacValidator.validate` regardless of which `shop-domain` header accompanies it. The gem provides no mechanism, and documents none, for verifying that the `shop-domain` header actually corresponds to the signed body.

### Impact Explanation
This breaks the tenant isolation the host application relies on `ShopifyAPI::Webhooks::Registry.process` to enforce: an attacker-controlled webhook body (fully valid per HMAC) can be delivered to a handler under a victim shop's identity. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up per-shop settings/tokens, writing data scoped to that shop, or triggering shop-specific side effects), this enables cross-tenant data injection/corruption — a Critical-severity cross-tenant access issue per the scoring rubric.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on their own shop (or otherwise obtain one valid signed webhook payload) and be able to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers — both are unprivileged, internet-reachable capabilities. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed payload used for verification, or otherwise cryptographically tie the `shop-domain` header to the specific webhook delivery (e.g., by validating it against a known/expected shop for the given API credentials/session, or including it in the value hashed for comparison) instead of trusting an unauthenticated header once the body-only HMAC succeeds.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g., `orders/create`) so Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)`.
3. Attacker sends a forged HTTP POST directly to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B`, as shown in `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:10-38`.
5. `ShopifyAPI::Webhooks::Registry.process` dispatches `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` to the app's handler (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to process attacker-controlled content as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
