### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. The `shop` field is therefore never cryptographically bound to the signature that authenticates the webhook, breaking the identity binding `verified_bytes == (body, shop)` down to `verified_bytes == body` only.

### Finding Description
`Request#shop` simply reads an HTTP header with no cryptographic protection: [1](#0-0) 

The value that is actually signed/verified is `to_signable_string`, which returns only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (from the unauthenticated header) as the tenant identity and forwards it to the application's handler: [4](#0-3) 

The gem's own documentation instructs integrators to key their persistence/business logic directly off `data.shop`: [5](#0-4) 

This is structurally the same class of bug as the M-12 report: a field that is part of the authenticated intent (there, the fee amount; here, the shop identity) is silently decoupled from the value that is actually protected by the cryptographic check (there, truncated storage; here, an HMAC that doesn't cover the header). The equality that should hold — "the shop bound by the signature equals the shop acted on by the handler" — does not hold, because `shop` can be swapped independently of the signature.

### Impact Explanation
Any unprivileged internet user who can install the target app on their own (attacker-controlled) shop can capture a legitimate webhook delivery (raw body + `X-Shopify-Hmac-Sha256`) sent to their own endpoint, then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim shop's domain). Because `HmacValidator.validate` only checks the body against the secret, the forged request passes verification, and `Registry.process` dispatches it to the app's handler carrying the attacker-chosen `shop`. Depending on how the host app persists/acts on `data.shop` (as documented), this can cause cross-tenant data contamination or trigger tenant-scoped actions (including mandatory compliance topics like `customers/redact`, `customers/data_request`, `shop/redact`) attributed to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to first obtain one valid `(body, hmac)` pair, which they can trivially do by installing the app on a shop they control (a "free" and unprivileged action) and observing/logging the webhook Shopify sends to their own registered callback. From there, forging the header is a one-line HTTP replay with no further secrets required. This does not require the `api_secret_key`, an access token, or any privileged account belonging to the victim shop.

### Recommendation
Bind the shop (and other identity-relevant fields like topic/api_version) into the value that is HMAC-verified, or otherwise validate that the `shop`/`X-Shopify-Shop-Domain` header corresponds to an install that is expected to be sending this specific webhook body (e.g., cross-check against a known/registered shop record before trusting `request.shop`, or require the host app to independently verify shop ownership of the webhook subscription id). At minimum, document prominently that `shop`/`data.shop` from `ShopifyAPI::Webhooks::Request`/`WebhookMetadata` is NOT covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`), pointing at their own controlled callback endpoint outside the app (or intercepts the delivery to the app's real endpoint).
2. Attacker captures the exact raw POST body and the `X-Shopify-Hmac-Sha256` header value Shopify sent for that delivery — this pair is valid because it was legitimately signed by Shopify using the app's secret.
3. Attacker resends the identical `(raw_body, X-Shopify-Hmac-Sha256)` to the app's real webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`Request#to_signable_string`), never inspecting the shop header.
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and executes tenant-scoped business logic as though the (attacker's own) order/webhook content belongs to `victim-shop`.
