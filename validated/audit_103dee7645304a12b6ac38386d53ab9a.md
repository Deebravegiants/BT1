### Title
Webhook `shop` identity is read from an unauthenticated HTTP header while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Because the `shop` value is never part of the signed material, any request whose body carries a valid HMAC (e.g., a webhook the attacker legitimately received for their own store) can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, and it will pass HMAC validation while being processed by the handler under the wrong tenant's identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only ever look at the raw body: [1](#0-0) [2](#0-1) 

`shop` (`Request#shop`) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of `to_signable_string` and therefore is never covered by the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC of the body only, then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

Contrast this with the OAuth callback path, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameters so the HMAC binds `shop == signed shop`: [5](#0-4) 

The webhook path breaks the equivalent binding: `verified bytes (raw_body) != acted-upon identity (shop header)`. Any user who can get Shopify to send them a legitimately-signed webhook (e.g., by installing the app on their own development/free store) obtains a `(raw_body, hmac)` pair that is valid for *any* `shop-domain` header value, because the header is not part of the signed content. Replaying that pair with an attacker-chosen `shop-domain` causes `Registry.process` to invoke the app's handler with `WebhookMetadata#shop` set to an arbitrary value while `HmacValidator.validate` still returns `true`.

### Impact Explanation
This breaks the tenant binding `signed_shop == acted_upon_shop` that the app relies on to route webhook side effects (e.g., updating records, revoking data, syncing state) to the correct merchant. An attacker controlling the body content (from their own legitimately-installed shop) can direct the app to apply that body's effects under a victim shop's identity, resulting in cross-tenant data confusion/access - one of the Critical impact categories in scope (cross-tenant access).

### Likelihood Explanation
Likelihood is moderate: the attacker needs no secrets - they only need one legitimately signed webhook payload (obtainable by installing the target app on any shop, including a free development store) and the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header, both of which are available to any unprivileged internet user/app-installer. The `Registry.process`/`HmacValidator` code in this gem performs no cross-check between the header-derived `shop` and the signed body, so the forged request is accepted as valid by the library itself.

### Recommendation
Bind `shop` to the signed content before it is trusted downstream. Concretely:
- Extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to include or independently verify the `shop-domain` header against data actually present in the signed body/topic, or
- Require the calling application to additionally verify that `request.shop` matches the shop associated with any session/state the handler is about to act on, and document this requirement clearly since the gem's own `HmacValidator.validate` currently gives no guarantee about header integrity, only body integrity.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) so Shopify sends a request with a valid `x-shopify-hmac-sha256` computed over the JSON body and headers `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture the raw body and the `x-shopify-hmac-sha256` value.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC: [6](#0-5) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"` and the attacker-controlled body, even though the signature never certified that pairing. [4](#0-3)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
