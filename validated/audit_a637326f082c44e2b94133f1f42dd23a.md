### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant data injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, but `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (and `topic`/`webhook_id`/`api_version`), which come from unauthenticated HTTP headers, when dispatching to the app's `WebhookHandler`. This is exactly the bug class described in the reference report: a field acted on by the handler (`shop`) is not covered by the value that the HMAC actually authenticates (`raw_body`).

### Finding Description
`HmacValidator.validate` computes `HMAC(client_secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field via `OpenSSL.secure_compare`. For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body`. [4](#0-3) [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers, none of which are part of the signed material: [5](#0-4) 

`Registry.process` validates the HMAC against the body, then unconditionally trusts `request.shop` as the tenant identity passed to the handler: [6](#0-5) 

Because the same `api_secret_key` (`client_secret`) is used to sign webhooks for every shop that has installed a given app, any merchant who has legitimately installed the app receives real webhooks with a valid `(body, hmac)` pair signed with that shared secret. That merchant — an "unprivileged" party with respect to any *other* tenant of the app — can replay the exact same body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. Since the HMAC only binds `raw_body`, the forged request passes `HmacValidator.validate` unchanged, and the handler receives `shop: "victim-shop.myshopify.com"` together with the attacker's own webhook payload.

The identity binding that should hold is:
`shop conveyed to the handler == shop cryptographically bound by the HMAC-signed payload`

but the actual binding enforced by the gem is only:
`hmac == HMAC(client_secret, raw_body)`, independent of `shop`.

This breaks the equality `shop_header == shop_authenticated_by_signature`, letting an attacker substitute any shop identity for a signature that was never bound to it.

### Impact Explanation
This is a cross-tenant boundary break: an app-installing merchant (an unprivileged party relative to other merchants of the same app) can cause the host application to process attacker-controlled webhook data under a victim shop's identity. Any host logic that keys per-tenant state, order/inventory records, redaction/GDPR actions, or downstream side effects off `WebhookMetadata#shop` will act on the wrong tenant, resulting in cross-tenant data corruption/injection. Per the rules, this maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate but unprivileged user of the app (i.e., has installed it on their own shop and thus legitimately receives webhooks with valid signatures), and that they can send arbitrary HTTP requests (with attacker-chosen headers) to the app's public webhook endpoint — both of which are realistic for "unprivileged internet user" threat model. No knowledge of `client_secret`, access tokens, or other privileged material is needed; only a replay of a previously received legitimate webhook body+signature with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook_id/api_version) into the signed material, or otherwise verify that the shop conveyed in headers matches the shop the webhook was actually delivered for (e.g., cross-check against a nonce/webhook id registered per shop, or include the shop domain in `to_signable_string` if consistent with Shopify's signing scheme). At minimum, document that `Webhooks::Request#shop` is untrusted with respect to the HMAC and host applications must not use it as an unguarded tenant key without additional verification (e.g., confirming the shop has a corresponding active session/installation before trusting the payload).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(client_secret, B)`.
2. Attacker resends the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all required headers present).
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and finds it equal to `H` — validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked, and the host app's handler now processes attacker-supplied data under the victim's tenant identity.
