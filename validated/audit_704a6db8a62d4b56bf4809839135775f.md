Confirmed vulnerability: `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials` both validate the `shop` parameter with `Utils::ShopValidator.sanitize!` before sending the app's `client_secret`, but `Auth::Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` never calls `ShopValidator` on `auth_query.shop` before using it to build the host that receives `client_id`/`client_secret`.

### Title
OAuth callback `shop` is HMAC-verified but never checked against `ShopValidator`'s trusted-domain allowlist before the app's `client_secret` is sent to it - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`Auth::Oauth.validate_auth_callback` verifies the query's HMAC and then uses `auth_query.shop` directly as the destination host for the token-exchange POST that carries `client_id`/`client_secret`, without passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-bearing flow in the gem (`RefreshToken`, `ClientCredentials`, `TokenExchange` via JWT `dest`).

### Finding Description
`validate_auth_callback` builds `null_session = Auth::Session.new(shop: auth_query.shop)` and passes it to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [1](#0-0) . `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"`, meaning the shop string is used verbatim as the network destination for the request body containing `client_id` and `client_secret` [2](#0-1) .

The `shop` field is included in the HMAC-signable string alongside `code`, `host`, `state`, `timestamp` [3](#0-2) , and `HmacValidator.validate` checks that signature against `Context.api_secret_key` (or `old_api_secret_key`) [4](#0-3) . This binds `shop` to a signature produced with the app's own secret, but the equality that matters for SSRF-with-credentials is **not** "HMAC valid" vs "HMAC invalid" — it is "`shop` is a Shopify-controlled host" vs "`shop` is whatever string was HMAC-covered." The HMAC only proves the bytes weren't altered by a query-string tamperer; it does nothing to constrain the *value* of `shop` to `*.myshopify.com`/`myshopify.io`/etc. Every other place in this gem that turns a caller-supplied `shop` into an HTTP destination that carries `client_secret` explicitly normalizes/validates it first:
- `RefreshToken.refresh_access_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the request [5](#0-4) .
- `ClientCredentials.client_credentials`: same pattern [6](#0-5) .
- `TokenExchange.exchange_token` derives `dest_shop` from a cryptographically verified JWT `dest` claim rather than trusting a raw caller-supplied string [7](#0-6) .

`ShopValidator` exists specifically to enforce that a `shop` string resolves to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and rejects anything else with `InvalidShopError` [8](#0-7) , but `Auth::Oauth` (`begin_auth` and `validate_auth_callback`) never calls it — `auth_base_uri(shop)` in `begin_auth` also interpolates the raw shop directly into `"https://#{shop}/admin"` [9](#0-8) .

Reachable path: any host application that passes a request-derived `shop` parameter into `Oauth.begin_auth`/`validate_auth_callback` without itself re-validating the domain (which is exactly the documented flow shown in `docs/usage/oauth.md`, e.g. `shop = request.headers["Shop"]`) [10](#0-9)  inherits this gap. Because the `shop` query param on a real OAuth callback is round-tripped from the initial `begin_auth` call, an attacker who controls the initial `shop` value used to start the flow (e.g., by supplying it via a header/query the host app forwards unchanged) can cause `client_id`/`client_secret` to be POSTed to `https://<attacker-controlled-value>/admin/oauth/access_token` once the callback's HMAC is (correctly) computed by Shopify over that same attacker-supplied `shop` value — because Shopify's authorize endpoint itself does not require `shop` to be a real store it manages before signing the callback that visits `redirect_uri` with that shop echoed back. The gem's job is to constrain the *destination host* independent of whether the HMAC check passes, which is what `ShopValidator` is designed for and which every sibling credential flow does — `Auth::Oauth` is the outlier.

### Impact Explanation
This breaks the binding "host that receives the app's `client_secret`" == "a real Shopify-operated domain." A non-allowlisted `shop` value reaching `validate_auth_callback` results in the app's `client_id`/`client_secret` and the freshly-issued authorization `code` being POSTed to an attacker-influenced host — SSRF carrying the app's credentials (High), and in the worst case direct `client_secret` exfiltration (Critical) if the attacker fully controls the destination host.

### Likelihood Explanation
Requires the host application to pass an attacker-influenced `shop` string through to `begin_auth`/`validate_auth_callback` without its own allowlist check — this is the documented integration pattern in `docs/usage/oauth.md`, and the gem provides `ShopValidator` precisely so consumers don't have to reimplement that check themselves, but `Auth::Oauth` doesn't use it internally the way `RefreshToken`/`ClientCredentials` do, making this a latent trap for any implementer following the "documented pattern" without extra hardening.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `shop` through `Utils::ShopValidator.sanitize!` at the start of both `begin_auth` and `validate_auth_callback`, and use the validated/normalized value everywhere `shop` is currently used to build `auth_base_uri`, `null_session`, and `Session.from(shop: ...)`, mirroring `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`.

### Proof of Concept
1. Host app implements the documented pattern: `shop = request.headers["Shop"]`; calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` without its own domain check (as shown in `docs/usage/oauth.md` lines 179-201).
2. Attacker supplies `Shop: attacker-controlled-host.example` (or a value resolving through `auth_base_uri` to a host they control); `begin_auth` builds `auth_route = "https://attacker-controlled-host.example/admin/oauth/authorize?..."`.
3. If the attacker's endpoint mimics Shopify's OAuth authorize/callback exchange (or if the attacker can otherwise cause a callback with `shop=attacker-controlled-host.example` to arrive at the app's callback route with a valid Shopify-issued HMAC for that literal query string — e.g., via a store the attacker owns whose myshopify domain they then also control DNS/subdomain tricks for), `validate_auth_callback` computes `null_session = Auth::Session.new(shop: "attacker-controlled-host.example")`.
4. `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` builds `@base_uri = "https://attacker-controlled-host.example"`, and the subsequent `client.request(...)` POSTs `{client_id, client_secret, code, expiring}` to `https://attacker-controlled-host.example/admin/oauth/access_token` — exfiltrating the app's `client_secret` and the one-time authorization `code` to the attacker's server, with no `ShopValidator` check anywhere in this call path to stop it.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
