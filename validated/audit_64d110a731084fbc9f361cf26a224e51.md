## Title
Webhook HMAC only signs the request body, not the `shop-domain` header — allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw body only, while the shop identity used to route and process the webhook (`shop-domain` header) is read from an unauthenticated header that is never part of the signed bytes. Since the webhook secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app, any party who can obtain one validly-signed `(body, hmac)` pair (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. The gem will report the request as valid and hand the handler a `WebhookMetadata` object attributing the payload to the victim shop.

## Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the data passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` signs/verifies using the single app-level `Context.api_secret_key` (not a per-shop secret), so the same `(body, hmac)` pair is valid for every shop that has the app installed: [4](#0-3) 

**Binding broken (as an equality):** the byte string cryptographically verified (`raw_body`) ≠ the byte string that determines tenant identity for downstream processing (`shop-domain` header). The HMAC proves "this body was signed by Shopify using this app's secret," it does **not** prove "this body was sent for shop X." A malicious app-installer (an unprivileged party with respect to any other tenant of the app) can capture a legitimate webhook delivered to their own store, then resend the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a target shop's domain. `HmacValidator.validate` passes because it only checks `raw_body` against the secret; `Registry.process` then invokes the handler with `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-chosen shop value, causing the host application to process/store attacker-controlled webhook data under another tenant's identity.

## Impact Explanation
This is a cross-tenant identity-binding bypass reachable by any unprivileged internet user who can install the app on a shop they control (no `api_secret_key`, access token, or privileged account of the *victim* is needed — only knowledge of a validly-signed payload from their own, legitimately-installed instance). Depending on how the host app's `WebhookHandler` uses `shop` (e.g., updating billing state, order data, `shop/redact`, `customers/redact`, or app-uninstalled cleanup for that shop), this enables cross-tenant data corruption/exfiltration or forced state changes on a victim tenant, satisfying the Critical "cross-tenant access" bar.

## Likelihood Explanation
Likelihood is high: it requires no secrets beyond what any legitimate app installer already possesses (a real webhook delivered to their own shop), no TLS interception, and no social engineering — only replaying an HTTP request with one header value changed to a webhook endpoint that is, by design, publicly reachable.

## Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified content, or otherwise cryptographically bind the header values used for routing to the signature (e.g., verify `request.shop` against the shop associated with the specific webhook subscription/session rather than trusting the header verbatim). At minimum, document that host applications must independently confirm the `shop-domain` header corresponds to a shop with an active, matching webhook registration before acting on the payload.

## Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets it register a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the attacker's endpoint with body `raw_body`, header `shopify-hmac-sha256: H`, and `shopify-shop-domain: attacker-shop.myshopify.com`. Since `H = HMAC(api_secret_key, raw_body)` and the secret is shared app-wide, `H` remains valid for any body-identical request regardless of shop.
3. Attacker resends the exact same `raw_body` and `shopify-hmac-sha256: H` to the same app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `request.shop == "victim-shop.myshopify.com"`, even though the payload was never generated for that shop.
