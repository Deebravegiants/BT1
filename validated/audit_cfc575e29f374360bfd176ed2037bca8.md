### Title
Accrued market value overflow panics inside accrual before the borrow-index cap, permanently freezing every pool verb — ([File: common/src/rates/simulate.rs])

### Summary
The reference bug is an edge-value input (`u64::MAX`) stored harmlessly, only to overflow later inside `ranges()` and panic every subsequent touch. XOXNO Lending has the same shape in its interest accrual: scaled share balances near the RAY domain ceiling are accepted by `supply`/`borrow`, and every later state mutation first calls `accrue_step`, which computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. Once the index grows enough that `scaled × index` exceeds `i128`, these mul-divs panic with `MathOverflow` — before `update_borrow_index` can clamp the index at `MAX_BORROW_INDEX_RAY`. The market is then bricked forever.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` unscales both books each chunk:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` is `scaled.mul(env, index)` — a `mul_div_half_up` that panics on `i128` overflow (`common/src/rates/scaling.rs:14-16`, `common/src/math/fp_core.rs`). The index clamp in `update_borrow_index` only limits the *index* to 1e36; the *value product* `borrowed × index` can hit `i128::MAX ≈ 1.7e38` well before that, since valid caps admit ~170 billion whole tokens (`i128::MAX / RAY`) and `supplied` also accumulates revenue shares each chunk.

The pool runs `global_sync` → `accrue_chunk` → `accrue_step` at the head of every mutating leg (`contracts/pool/src/interest.rs:20-53`), and controller verbs route through the pool. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`) demonstrates the delayed panic concretely: after ~a few years at 98% utilization, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all revert with `MATH_OVERFLOW`, while `last.borrow_index < MAX_BORROW_INDEX_RAY` — the cap never engages. Like `bf.unset(u64::MAX)`, the dangerous input (a domain-max scaled book) is accepted at write time and only detonates inside a later, unavoidable computation.

Entry path for an unprivileged attacker: `controller.supply` a listed asset up to the admitted cap, then `controller.borrow` ~98% of it against separately supplied collateral, then let time pass (or just leave the book while normal users' `update_indexes` calls push the product over `i128::MAX`). No privileged call is involved; `update_indexes` is permissionless.

### Impact Explanation
Permanent freezing of funds on that market. Once `borrowed × borrow_index` or `supplied × supply_index` exceeds `i128::MAX`, every entry point that touches the market — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `claim_revenue`, `update_indexes`, and all router verbs (`flash_position`, `multiply`, `swap_*`, `repay_debt_with_collateral`) — accrues first and panics. Suppliers cannot exit, borrowers cannot repay, liquidators cannot clear bad debt, and treasury revenue cannot be claimed. The funds are locked permanently because there is no path that skips accrual, and no way to reduce `borrowed`/`supplied` without executing the very accrual that overflows.

### Likelihood Explanation
Medium. It requires a whale-scale position (on the order of the ~170B-whole-token RAY ceiling) at sustained high utilization and years of accrual on a steep curve segment; the test reaches the cliff within 40 years on the XLM curve at 98% utilization. For a low-priced listed asset, reaching the scale is a capital problem rather than a permission problem — any unprivileged address can supply up to the cap and borrow against its own collateral. Once conditions are set, the freeze triggers through ordinary user activity; no attacker timing is needed. The docs acknowledge the limit exists (`docs/reference/formulas.md:432-437`) but the protocol has no mitigation, alarm, or unwind path.

### Recommendation
Saturate rather than panic at the value ceiling, mirroring how `calculate_scaled_cap` already saturates at `i128::MAX` (`common/src/rates/scaling.rs:26-33`). In `accrue_step`, compute `borrowed_original`/`supplied_original` through a saturating mul (or clamp `supplied`/`borrowed` at admission so `scaled × MAX_INDEX` fits `i128` with the 20× pre-clamp headroom the index ceiling already reserves). Alternatively, clamp the borrow index before unscaling so the product is provably in-domain, and add an explicit market freeze flag with an escape hatch (e.g., forced bad-debt write-down path that bypasses accrual) rather than relying on the panic being unreachable.

### Proof of Concept
```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply up to cap
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // unprivileged borrow ~98%

// advance time; eventually any accrual panics:
t.advance_time(YEAR_SECS);
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
let last = book(&t, "BIG18");
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
Each failure originates in `accrue_step`'s `scaled_to_original` mul overflowing `i128` before `update_borrow_index` can clamp, permanently bricking the market — the same delayed-panic-on-stored-extreme-value class as `bf.unset(u64::MAX)` breaking `bf.ranges()`.
