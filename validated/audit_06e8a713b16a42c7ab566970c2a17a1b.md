### Title
Unbounded router calldata + persistent max allowance lets an attacker swap stranded `inputToken` balance in `LifiExternalAction`, stealing prior depositors' unspent funds - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` grants the LI.FI `router` an unlimited, persistent ERC20 allowance via `approveUnlimited` and then forwards fully attacker-crafted `externalActionMetadata` as raw calldata, without ever checking how much `inputToken` the router actually pulled. Because `swap()` never refunds unconsumed `inputToken` and `swappedAmount` is computed purely from the `outputToken` balance delta, any `inputToken` balance left stranded in the shared `LifiExternalAction` contract by a prior transaction can be swept into a subsequent attacker's swap and paid out to them as legitimate swap proceeds.

### Finding Description
Equality that must hold: the amount of `inputToken` the router consumes from `LifiExternalAction` during `callRouter` for a given transaction must equal `inputAmount == uint256(-deltaAmounts[0])`, i.e., exactly what Hinkal transferred into the action for that call [1](#0-0) . That equality is never enforced.

`approveUnlimited` only resets the allowance when it has dipped below half of `type(uint256).max`; a normal swap that consumes a fraction of the max approval leaves the allowance effectively unlimited forever [2](#0-1) . `callRouter` for the ERC20 branch calls `approveUnlimited(inputToken, router)` and then blindly executes `router.call(externalActionMetadata)`, measuring success only and computing `swappedAmount` solely from the `outputToken` balance delta — there is no `inputToken` balance check before/after the call [3](#0-2) . Because `externalActionMetadata` is attacker-controlled raw calldata (the attacker generates their own proof and signs their own message), the amount of `inputToken` actually pulled by the router via `transferFrom` is whatever the calldata encodes, bounded only by the unlimited allowance and `LifiExternalAction`'s actual token balance — not by `inputAmount`.

`swap()` never refunds unused `inputToken` after `callRouter` returns, so any `inputToken` a router leaves un-consumed from a prior legitimate transaction (e.g. partial fill, router dust, or a directly-transferred balance) remains stranded in the shared `LifiExternalAction` contract, unaccounted by any `deltaAmountChanges` [4](#0-3) .

Hinkal's own top-level balance-equality check (`balanceDif == amountChanges[i] + utxoAmount` in `Hinkal.sol`) only measures Hinkal's own balance change and the UTXO amount reported by the external action, both of which are self-consistent with whatever `LifiExternalAction` reports as `swappedAmount` [5](#0-4) . It cannot detect that `swappedAmount` was inflated by consuming a stranded balance that belonged to a different transaction, since that check has no visibility into `LifiExternalAction`'s internal token accounting. Similarly, `calldataHash`/`getHashedCalldata` in `performHinkalChecks` only binds the calldata to the proof/signature for integrity against relay tampering; it does not semantically constrain what the (self-authoring) attacker puts inside `externalActionMetadata` [6](#0-5) .

Exploit flow:
1. A prior transaction (any user, or the attacker themselves seeding it — but critically also possible from a genuine third-party partial-fill swap) leaves `X` extra units of `inputToken` stranded in `LifiExternalAction` beyond what its own `swap()` call consumed/forwarded.
2. Attacker submits their own `transact` call with a real (small) `inputAmount` transferred by Hinkal into `LifiExternalAction`, but crafts `externalActionMetadata` so the router's calldata pulls `inputAmount + X` from `LifiExternalAction` (permitted because allowance is `type(uint256).max`).
3. The router swaps the larger amount and returns proportionally larger `outputToken` to `LifiExternalAction`.
4. `swappedAmount = balanceAfter - balanceBefore` of `outputToken` reflects the inflated swap; `amountToSendToHinkal` (all of it, minus fees) is forwarded to `msg.sender` (Hinkal) and minted as the attacker's UTXO [7](#0-6) .
5. The attacker walks away with shielded value corresponding to the stranded `X`, which they never deposited.

### Impact Explanation
This is theft of another depositor's stranded funds (Critical: "direct theft of shielded or in-flight user funds"), since the attacker obtains a real, spendable shielded UTXO backed by tokens they never contributed. It is repeatable any time `LifiExternalAction` accumulates unconsumed `inputToken` balance from a prior swap (partial fills, router dust, or any other transaction leaving residual balance), since the persistent max allowance and unchecked `router.call(externalActionMetadata)` never get remediated between calls.

### Likelihood Explanation
Preconditions: (1) `LifiExternalAction` must hold residual `inputToken` balance beyond what any pending transaction's `deltaAmounts[0]` accounts for — plausible because `swap()` performs no post-call refund of unconsumed `inputToken`, and LI.FI routes/aggregators routinely can leave dust or fail to fully consume an approved amount; (2) attacker must know the router's calldata format to specify a pull amount larger than their own declared `inputAmount`, which they fully control since `externalActionMetadata` is opaque, attacker-authored calldata. Attacker cost is a single ordinary swap transaction with self-generated proof; no privileged role is required, matching the stated threat model.

### Recommendation
In `LifiExternalAction.callRouter` / `ExternalActionSwap.swap`, record `inputToken` balance before the router call and require that the balance decreased by exactly `inputAmount` (or refund any unspent portion to the original transaction's UTXO/output instead of leaving it in the contract). Additionally, avoid `approveUnlimited`; approve only the exact `inputAmount` needed for each swap (reset to zero after use) so a standing allowance can never be exploited to pull unrelated stranded balances.

### Proof of Concept
Foundry test outline:
1. Deploy `LifiExternalAction` with a mock router.
2. Simulate a "stranding" transaction: have Hinkal transfer `inputAmount1` of `TokenA` into `LifiExternalAction`, and have the mock router's calldata for that call only consume `inputAmount1 - X`, leaving `X` `TokenA` stuck in `LifiExternalAction` (assert `TokenA.balanceOf(LifiExternalAction) == X` after the tx).
3. Run a second `transact` as the attacker with `inputAmount2` `TokenA` transferred by Hinkal into `LifiExternalAction`; craft `externalActionMetadata` so the mock router's `transferFrom` call pulls `inputAmount2 + X` from `LifiExternalAction` and returns proportional `outputToken`.
4. Assert the attacker's resulting UTXO amount (`amountToSendToHinkal`) exceeds what `inputAmount2` alone should produce by exactly the value derived from `X`, and assert `TokenA.balanceOf(LifiExternalAction) == 0` after — proving the stranded balance from transaction 1 was drained into transaction 2's attacker-controlled swap, i.e., `swappedAmount(tx2) - swappedAmount_expected(inputAmount2) == f(X) > 0`, breaking the intended equality "output credited to attacker == output derived solely from their own -deltaAmountChanges[0]".

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
