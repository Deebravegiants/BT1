### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body. The `shop` value that the handler receives and is expected to use as the tenant/session key comes from the unauthenticated `shopify-shop-domain` HTTP header, so "the HMAC is valid" and "the shop this data belongs to" are two different, unlinked pieces of information.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read directly from a header that is never part of the signed data: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) with the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs the HMAC check and then unconditionally trusts `request.shop` (from the header) to build `WebhookMetadata`, which is handed to the application's handler as the identity of the tenant that produced this data: [4](#0-3) 

The equality that should hold — `shop authenticated by HMAC == shop used as tenant key in WebhookMetadata` — does not hold. The `api_secret_key` used for HMAC signing is the **app's** client secret, shared across every shop that installs the app; it is not a per-shop secret. Any unprivileged user can install the app on their own (e.g. trial) shop, causing Shopify to send a webhook with a body they fully control (order/customer/product data they created) and a valid HMAC over that body. Because the header carrying `shop-domain` is excluded from the signed bytes, that same `(raw_body, hmac)` pair remains valid if the `x-shopify-shop-domain` header is swapped for an arbitrary victim shop domain before being delivered to the app's webhook endpoint. The `Registry.process` check still passes (HMAC only ever validated the body), and `WebhookMetadata.shop` is now the attacker-chosen victim domain, with attacker-controlled body content.

The gem's own documentation reinforces this misplaced trust — it states that `Registry.process` "will verify the request did indeed come from Shopify" and instructs developers to key downstream work off `data.shop`: [5](#0-4) [6](#0-5) 

So a developer following the documented API is led to treat `data.shop` as authenticated, when in fact only the body bytes are.

### Impact Explanation
This breaks the tenant-identity binding: `shop` reported to the handler is not bound to the HMAC that gates processing. An attacker who can trigger any webhook delivery for a shop they control (trivial — install the free/trial app, perform an action) can forge webhook events that the app attributes to an arbitrary victim shop, injecting attacker-controlled data (order/customer/product payloads) into the victim's tenant context inside the host application. This is cross-tenant data injection/spoofing enabled purely by the gem's webhook verification design, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's documented `Registry.process`/`WebhookMetadata` flow: no access token, `client_secret`, or privileged account is required — only the ability to install the target app on an attacker-controlled shop (a normal, unprivileged action) and knowledge of the victim's public `myshopify.com` domain, then replaying the captured request with a modified header, which most naive/typical HTTP-framework-based webhook endpoints will happily forward unmodified.

### Recommendation
Bind the `shop` (and other identity fields such as `topic`/`webhook_id`, if used for authorization decisions) into the HMAC-signed material, or otherwise cryptographically tie the `shopify-shop-domain` header to the signed payload before exposing it as trusted in `WebhookMetadata`. At minimum, the gem should document explicitly that `shop` is unauthenticated and must be independently cross-checked by the host application against a known set of installed shops before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, obtaining a legitimate webhook subscription (e.g. `orders/create`).
2. Attacker creates an order in their own store with attacker-chosen content, causing Shopify to POST a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this request to the same endpoint, rewriting only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (the HMAC header and body `B` are left untouched).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it validates only `B` against the unchanged HMAC: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, causing the host application to process/store attacker data under the victim's tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
