The `WebhookMetadata.shop` field is explicitly documented as "The shop domain of the webhook" that host applications use for tenant identification (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)` per the gem's own docs), yet it is derived purely from an HTTP header that is never covered by the HMAC signature.

### Title
Webhook shop-domain header is not covered by HMAC, breaking the shop↔body binding used for tenant identification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` in `Registry.process` verifies solely that the *body* bytes were signed with the app's shared `api_secret_key`. The `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and `topic`/`webhook_id` fields are never part of the signed material, yet `Registry.process` forwards `request.shop` directly into `WebhookMetadata` as the tenant identifier consumed by the host app's handler.

### Finding Description
The intended invariant is: `HMAC(api_secret_key, signable_string)` should authenticate everything the handler treats as coming "from Shopify for shop X." Instead:
- `hmac` method: [1](#0-0) 
- `shop` method reading an unauthenticated header: [2](#0-1) 
- Signable string excludes shop/topic entirely: [3](#0-2) 
- `Registry.process` validates only this body-only HMAC then trusts `request.shop`/`request.topic` for dispatch: [4](#0-3) 

Because a single app-level `api_secret_key` is shared across *all* shops installing the app, any merchant who has legitimately installed the app can capture a genuine `(raw_body, hmac)` pair from a real webhook Shopify sends to their own store (this requires no privilege beyond being a normal, unprivileged app user/merchant — an "unprivileged internet user" relative to other tenants of the same app). They can then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass, since it only checks the raw body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with that forged/replayed body.

This directly breaks the identity binding: **shop-authenticated (via HMAC) ≠ shop stored/used as the tenant key (`WebhookMetadata#shop`)**. The header can be freely chosen by the client while the body signature is independent of it.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` — as this gem's own documentation instructs (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) — to select which tenant's records to create/update/delete will process attacker-controlled webhook content under another tenant's identity. This is a cross-tenant write/data-integrity issue: an attacker-controlled but validly-HMAC'd payload from their own store can be attributed to and applied against a different merchant's account/data in the host app, since the gem provides no binding between the authenticated bytes and the shop identifier it hands to the handler.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented usage pattern of trusting `data.shop`: the attacker only needs an active installation on any single shop (no elevated privilege), the ability to send one webhook to their own store to capture a valid signature, and the ability to POST an HTTP request to the app's public webhook endpoint with a modified header — all standard, unprivileged capabilities.

### Recommendation
Bind the shop identity to the authenticated material. Options:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed string (would require Shopify-side signing changes), or, since that's not under this gem's control,
- Require host apps (and update this gem's `WebhookMetadata`/docs) to cross-check `request.shop` against a shop that is independently known to have an active session/registration for the given `webhook_id`/topic before trusting it, and explicitly document that `shop-domain` is unauthenticated header data, not a verified claim.
- At minimum, update the documentation and `WebhookHandler` guidance to make clear that `data.shop` is not covered by the HMAC and must not be used as a sole tenant key without additional verification (e.g., matching against a known shop that has that webhook subscription/`webhook_id`).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (normal merchant flow, no special privilege).
2. Shopify sends a real webhook (e.g., `orders/create`) to the app's endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker captures `raw_body` and the valid `hmac` value (they legitimately received it).
4. Attacker crafts a new HTTP POST to the same webhook endpoint using the identical `raw_body` and `shopify-hmac-sha256` header, but sets `shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` [5](#0-4) .
6. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...))`, and any host app following the documented pattern applies the attacker's data to the victim's tenant record.
