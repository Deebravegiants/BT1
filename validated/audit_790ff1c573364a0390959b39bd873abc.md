### Title
Missing audience (`aud`) verification in gateway JWT authentication allows cross-context token replay - (File: `core/utils/jwt.go`)

### Summary
`VerifyRequestJWT` in `core/utils/jwt.go`, used by internet-facing gateway handlers (e.g. `WorkflowMetadataHandler.Authorize` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`) to authenticate signed JWTs on JSON-RPC requests, never validates the `aud` (audience) claim of the token, even though the JWT creation path (`CreateRequestJWT`) explicitly supports specifying an audience via `WithAudience`. This mirrors the root cause of GHSA-ch68-7cf4-35vr in Fleet: an audience field exists in the protocol to scope a token to its intended recipient, but the verifier never checks it, so a token minted for one recipient/context can be replayed against a different recipient/context.

### Finding Description
`CreateRequestJWT` builds tokens with `jwt.RegisteredClaims{ ... Audience: jwt.ClaimStrings(audience), ... }` when the `WithAudience` option is supplied: [1](#0-0) [2](#0-1) 

However, `VerifyRequestJWT`, which is the function actually used to authenticate inbound gateway requests, performs signature recovery, checks `jti` (replay), `exp`, `iat`, and digest match, but at no point inspects or enforces `verifiedClaims.Audience`: [3](#0-2) 

Contrast this with the sibling authenticator `jwtBasedAuth.validateToken` in the Vault capability, which correctly enforces the audience via `jwt.WithAudience(v.audience)`: [4](#0-3) 

This confirms audience verification is a recognized, intentional security control elsewhere in the same codebase, but it is absent from the `VerifyRequestJWT`/`CreateRequestJWT` code path used by gateway handlers such as `WorkflowMetadataHandler.Authorize`: [5](#0-4) 

Because only the request digest (derived from method/params), `jti` replay protection, and expiry are checked — not the intended audience/recipient — a validly-signed token intended for one endpoint/handler/tenant context can be accepted by any other verifier instance that happens to compute the same request digest, exactly analogous to how Fleet's SAML flow failed to bind a SAML response to the intended Service Provider.

### Impact Explanation
If the same signing key is used to authorize requests across multiple distinct handlers/contexts (e.g., different gateway endpoints, shards, or workflow-scoped authorization boundaries) that share a request-shape/digest scheme, a JWT crafted or captured for one context could be replayed to gain authorization in another context where it was never intended to be valid. This is a request-impersonation / authorization-boundary-confusion class bug (CWE-284/CWE-287), matching the Fleet advisory's "reuse of SAML response for another SP" analog. The severity is bounded by how strongly `req.Digest()` already scopes tokens in practice, but the complete absence of audience enforcement removes a designed defense-in-depth boundary that the codebase itself uses elsewhere (Vault JWT auth).

### Likelihood Explanation
Exploitation requires an attacker to obtain or induce generation of a validly-signed JWT (bound to their own key, or a captured one) for a request whose digest is accepted in a different authorization context served by the same `VerifyRequestJWT` call path. Given `CreateRequestJWT` supports and presumably is intended to set an audience for exactly this reason, and it's silently unenforced, the likelihood is non-trivial for any deployment/topology where multiple handlers or tenants share verification logic without additional binding beyond method/param digest.

### Recommendation
Add audience validation to `VerifyRequestJWT` (mirroring `jwtBasedAuth.validateToken`'s `jwt.WithAudience(...)` usage), requiring callers such as `WorkflowMetadataHandler.Authorize` to pass the expected audience (e.g., workflow ID, shard/DON ID, or handler identity) and rejecting tokens whose `aud` claim doesn't match.

### Proof of Concept
1. A workflow owner signs a JWT via `CreateRequestJWT` intended for handler/context A, optionally setting an audience for A (or the audience field is simply omitted/ignored).
2. The signed token — still valid signature, `jti`, `exp`, and matching digest — is submitted to handler/context B, which also uses `VerifyRequestJWT` via the same `Authorize`-style flow.
3. Because `verifiedClaims.Audience` is never checked in `core/utils/jwt.go:VerifyRequestJWT`, the token is accepted by B as if it had been minted for B, granting authorization in a context the signer/token was never scoped to.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
