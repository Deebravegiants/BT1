### Title
First relayer to trigger a state-machine update after `update_cost_per_block` is enabled can claim rewards for blocks finalized before the reward was configured - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::calculate_reward` computes a relayer reward as `(latest_height - baseline) * block_cost`, where `baseline` falls back to `previous_commitment_height` the first time a state machine is rewarded [1](#0-0) . This is analogous to the reported bug: a reward-bearing counter (`lastRewardTime`/here `LastRewardedHeight`) is initialized lazily on first use to a value that can predate the point at which rewards were actually "started" (`startTimestamp_`/here the block at which governance called `update_cost_per_block`), letting the first claimant collect rewards for a span that occurred before incentives were enabled.

### Finding Description
`update_cost_per_block` is a purely storage-mutating governance call that sets `StateMachinesCostPerBlock[state_machine_id]` with no reference to the chain's current commitment height [2](#0-1) . It does not seed `LastRewardedHeight` for that state machine.

When the very next consensus message for that state machine is delivered and processed via `FeeHandler::on_executed` → `process_message` → `calculate_reward`, the baseline used is:
```
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
```
`previous_height` comes from `host.previous_commitment_height(...)`, i.e., the state machine's commitment height from *before* incentives were ever configured for it [3](#0-2) . If that state machine had already been running and finalizing blocks on Hyperbridge for a long time prior to governance calling `update_cost_per_block`, the gap `latest_height - previous_height` can span many blocks that were never intended to be paid for, because the reward schedule "started" only at the moment governance enabled it — mirroring the `startTimestamp_` vs. `lastRewardTime` mismatch in the source report. The first relayer to submit any qualifying consensus message after enablement collects the full backdated reward for that entire pre-existing span in one shot.

### Impact Explanation
This allows unbacked/over-large payouts from the treasury to a single relayer for work (state machine advancement) that occurred before the reward schedule existed, directly draining `T::TreasuryAccount` funds beyond what governance intended when sizing `block_cost` for future blocks only. This is a fund-drain/economic-accounting flaw reachable by any relayer submitting a consensus message, requiring no privileged access.

### Likelihood Explanation
Any operator running a relayer for a state machine that is later configured with `update_cost_per_block` (a normal governance action expected to occur regularly as new chains are onboarded or reward parameters change) can trivially trigger this by simply relaying the next consensus proof. No race condition or unusual timing is required; it is the deterministic first-call behavior.

### Recommendation
When `update_cost_per_block` first sets a reward for a state machine (i.e., `StateMachinesCostPerBlock` transitions from `None` to `Some`), immediately seed `LastRewardedHeight[state_machine_id]` to the state machine's current `latest_commitment_height` at that moment, rather than letting `calculate_reward` lazily default to `previous_commitment_height` on first use. This ensures block-span rewards only ever accrue for blocks finalized after incentives were enabled.

### Proof of Concept
1. State machine `X` has been continuously finalizing consensus updates on Hyperbridge; its `latest_commitment_height` is 100,000 and `previous_commitment_height` is 99,999 (or further back if updates batch several heights).
2. Governance calls `update_cost_per_block(X, block_cost)` for the first time — no height is recorded, `LastRewardedHeight[X]` remains `None` [4](#0-3) .
3. A relayer submits the next `Message::Consensus` update for `X`. `on_executed` collapses `StateMachineUpdated` events and calls `process_message` → `calculate_reward` [5](#0-4) .
4. `calculate_reward` reads `baseline = previous_height` (99,999, or lower if this is genuinely the first-ever tracked height for that chain, e.g. 0), and `blocks = latest_height - baseline`, paying `blocks * block_cost` to that one relayer [6](#0-5) .
5. The relayer is paid for a large span of blocks that were finalized before the reward was ever configured, at the expense of the treasury.

		// the first reward is recorded for this chain. The watermark only moves forward, so a

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)

		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}
