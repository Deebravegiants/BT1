### Title
Non-embedded session cookie lookup trusts raw, unsigned cookie value derived from a deterministic offline session ID (`offline_#{shop}`) - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, `SessionUtils.current_session_id` passes the raw `shopify_app_session` cookie value straight through to `cookie_session_id`, which performs zero cryptographic verification of that value. Because offline session IDs are generated deterministically as `"offline_#{shop}"` by `Auth::Session.from`, an attacker who knows a target shop's `myshopify.com` domain (public information) can forge the cookie for their own HTTP request and cause the host app's session storage to return the victim shop's session object, including its access token.

### Finding Description
The broken binding: `SessionUtils.cookie_session_id(cookies)` returns `cookies[SessionCookie::SESSION_COOKIE_NAME]` verbatim [1](#0-0)  with no equality check against any value derived from `Context.api_secret_key`. This value is fed into `current_session_id` for the non-embedded branch without any signature validation [2](#0-1) .

The root cause is upstream: offline session IDs are not random secrets, they are a deterministic function of the public shop domain: `id = "offline_#{shop}"` in `Auth::Session.from` [3](#0-2) . This exact string is what gets written into the `shopify_app_session` cookie for non-embedded apps after OAuth completes [4](#0-3) . `SessionCookie` is a plain `T::Struct` with `name`/`value`/`expires` fields and no HMAC or signature field at all [5](#0-4) .

Exploit flow: attacker sends `GET /` to the target app with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `current_session_id(nil, cookies, false)` returns that string unchanged. The host app (as documented in `docs/getting_started.md`, "Cookie" section [6](#0-5) ) then loads whatever session object its own storage keeps under that id, which — if the victim shop previously completed OAuth — is the victim's real offline session containing its access token. The attacker never needed the victim's cookie or any secret; the "credential" (session id) is entirely public/derivable.

Existing guards do not prevent this: `HmacValidator.validate` only checks OAuth callback query params, not this cookie path; `state` comparison only applies during the OAuth callback itself, not to subsequent session lookups; `JwtPayload`'s `aud`/HMAC checks apply only to the embedded/JWT branch, not the cookie branch; `Context.embedded?` merely selects which unguarded branch runs.

### Impact Explanation
An attacker who knows or guesses a shop's `*.myshopify.com` domain (trivially enumerable/public) can, without ever installing the app on that shop or possessing any secret, cause a non-embedded app built on this gem to attach the victim shop's stored session (and access token) to the attacker's own request, once the victim shop has ever completed OAuth. This is a cross-tenant session-fixation/IDOR issue: the "session id" that functions as the sole authorization key for session-storage lookup is not a secret, is not signed, and requires no cryptographic knowledge to forge. This is repeatable against any shop whose domain the attacker can learn.

### Likelihood Explanation
Preconditions: app is non-embedded, uses `SessionUtils.current_session_id(nil, cookies, false)` per the gem's documented cookie flow, and the host app's session storage is keyed directly by this session id (the documented and expected usage pattern). Attacker cost is trivial — no secrets, no XSS, no MITM; just knowledge of the victim's shop domain and the ability to set an arbitrary `Cookie` header on their own outbound request (always possible for any HTTP client). This makes the attack highly feasible and cheap to repeat against many shops.

### Recommendation
Do not rely on a deterministic, guessable string as the trust boundary for session lookup. Either (a) make the session id itself high-entropy/random (e.g., `SecureRandom.uuid`, as already used as the default in `Session.new`) rather than `"offline_#{shop}"`, and/or (b) sign the cookie value with an HMAC keyed by `Context.api_secret_key` and verify that HMAC in `cookie_session_id` before treating the value as trusted, rejecting any cookie whose signature doesn't validate.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_offline_session_id_is_deterministic_and_unsigned_cookie_is_trusted
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  victim_shop = "victim-shop.myshopify.com"
  forged_id = ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop)
  # forged_id == "offline_victim-shop.myshopify.com", fully derivable from public shop name,
  # with no dependency on ShopifyAPI::Context.api_secret_key

  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_id }

  # No HMAC/signature check performed anywhere in this call chain
  assert_equal(
    forged_id,
    ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false),
  )
end
```
This demonstrates that `current_session_id` returns an attacker-forgeable, shop-derived string with zero cryptographic binding to `Context.api_secret_key`, which a host app then uses as the key to load another tenant's session/access token from storage.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
