## Title
Cross-chain order cancellation permanently locks escrow when the immutable refund beneficiary cannot receive tokens - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

## Summary
`IntentGatewayV2.cancelOrder` → `_cancelFromDest` irreversibly marks a cross-chain order as settled on the destination chain (`_filled[commitment] = order.user`) and dispatches a `RefundEscrow` message whose beneficiary is hard-coded to `order.user`. This mirrors the reported Gitcoin bug class: an operation flips an irreversible "done" flag before the corresponding payout is guaranteed to succeed, and the payout target address baked into that operation can never be updated. If the source-chain `_withdraw` call for that beneficiary permanently reverts (e.g. the token blacklists `order.user`, or `order.user` is a contract that cannot receive the escrowed asset), the escrow is frozen forever with no recovery path.

## Finding Description
`cancelOrder` in `evm/src/apps/IntentGatewayV2.sol` (lines 505-537) is the single entrypoint for all three cancellation routes and, before routing, checks:

```solidity
if (_filled[commitment] != address(0)) revert Filled();
```

For the destination-initiated route, `_cancelFromDest` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:297-307`) does:

```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    _filled[commitment] = address(uint160(uint256(order.user)));
    _post(order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value);
}
```

`_filled[commitment]` is set **immediately and permanently** on the destination chain, before the refund is known to succeed. This closes every other recovery route for this commitment:
- `fillOrder` refuses because `_filled[commitment] != address(0)` (line 462 of `IntentGatewayV2.sol`).
- `cancelOrder` (any route, including the source-side "not filled" GET proof route) refuses with `Filled()` at line 508 of `IntentGatewayV2.sol`.

The only remaining path to release the source-chain escrow is delivery of the `RefundEscrow` message to `onAccept` on the source chain:

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    _checkRelayer(incoming.relayer);
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        _authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return _withdraw(body, kind == RequestKind.RefundEscrow, true);
    }
    ...
}
```
(`evm/src/apps/intentsv2/ExtrinsicIntents.sol:330-337`)

`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-485`) transfers the escrowed tokens directly to `beneficiary = order.user`:

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    ...
    IERC20(token).safeTransfer(beneficiary, amount);
    ...
}
```

`order.user` is fixed at order placement and is part of the hashed `Order` commitment; there is no way to change it for an existing commitment. If the token's `safeTransfer` to `order.user` reverts deterministically (e.g., a blacklist-capable stablecoin such as USDC/USDT blacklists that address, or `order.user` is a contract without appropriate ERC-20 receiving logic that always reverts on transfer, or a native-asset order whose beneficiary is a non-payable contract so `_sendValue` always fails), then:
1. Delivery of `RefundEscrow` to `onAccept` will always fail (the "so it can be retried" retry semantics of `EvmHost.dispatchIncoming` only helps for *transient* failures — a deterministic revert will fail on every retry).
2. Because `_filled[commitment]` is already set on the destination, no other cancellation route (same-chain, source-side GET-proof route) or fill route can be used to reach this commitment again.
3. Because the message has no expiry that helps here (a POST timeout would just make the situation refund-eligible on the *destination* side via `onPostRequestTimeout`, but the destination side never escrowed anything for a cross-chain order — the escrow sits on the source chain and only `onAccept` releases it), the tokens locked in `_orders[commitment][token]` on the source chain remain stuck permanently.

This is structurally identical to the reported bug: an irreversible "ready" flag (`isReadyForPayout` / here `_filled[commitment]`) is set before the payout is confirmed, and the payout recipient address embedded in the operation cannot be corrected after the fact, so a deterministic delivery failure permanently strands funds.

## Impact Explanation
Escrowed input tokens on the source chain for any cross-chain order cancelled from the destination become permanently unrecoverable if `order.user` cannot receive the refunded asset. This is a direct, permanent freezing-of-funds condition reachable by a normal user flow (order placement + destination-side cancellation), not requiring any privileged or malicious actor. Given Hyperbridge's Intent Gateway is meant to support arbitrary ERC-20 assets (including blacklist-capable stablecoins) and arbitrary `order.user` addresses (which can be any 32-byte value, including a contract address), this qualifies as Medium-severity permanent freezing of user funds.

## Likelihood Explanation
Likelihood is realistic but not trivial to trigger unintentionally: it requires either (a) a blacklist-capable token (USDC/USDT-style) blacklisting the exact `order.user` address after order placement but before refund delivery, or (b) a smart-contract `order.user` that cannot correctly receive the refunded token/native asset (e.g., no payable fallback, or a paused/reverting receiver). Both scenarios are plausible in production given the gateway's generality (it accepts arbitrary tokens and arbitrary beneficiary addresses), and the destination-side cancel route is explicitly designed to be triggerable by "anyone" after the deadline, which does not require the user's own cooperation or awareness that their configured `order.user` cannot receive funds.

## Recommendation
Do not treat destination-side cancellation as final before the corresponding source-chain refund is durably deliverable. Options:
- Add a recovery/override path (e.g., an owner- or governance-gated `retryRefund`/`redirectRefund` for a given commitment) that allows resubmitting the `RefundEscrow` message with an updated beneficiary once the original is proven undeliverable, analogous to how `updateDistribution` should have been made reachable even after `isReadyForPayout` in the referenced report.
- Alternatively, decouple "settled" (blocks further fills) from "refund beneficiary is fixed forever": allow the source chain's `onAccept`/`_withdraw` failure path to fall back to a pull-based claim mechanism (e.g., credit an internal balance keyed by commitment that any address controlling `order.user`'s private key, or a designated recovery address, can later claim to a different address), instead of relying solely on a push `safeTransfer` to a hard-coded address.
- At minimum, document and mitigate the risk that a permanently reverting beneficiary transfer strands escrow indefinitely, and consider a timeout/escape hatch keyed off of repeated `onAccept` failures for the same commitment.

## Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` on chain A with `order.user` set to an address `U` and input token `T` (a blacklist-capable ERC-20, e.g. USDC-style), escrowing `amount` of `T`.
2. Before the order is filled, `U` is blacklisted on token `T` (external event, outside the protocol's control).
3. After `order.deadline`, anyone calls `cancelOrder(order, options)` on the destination chain (chain B), which routes to `_cancelFromDest`:
   - `_filled[commitment] = U` is set immediately (`ExtrinsicIntents.sol:302`).
   - A `RefundEscrow` POST message naming beneficiary `U` is dispatched to chain A.
4. The relayer delivers the message to chain A's `onAccept` → `_withdraw`. `IERC20(T).safeTransfer(U, amount)` reverts because `U` is blacklisted.
5. `EvmHost.dispatchIncoming`'s failure handling deletes the request receipt so it "can be retried" — but every retry hits the exact same deterministic revert, since the beneficiary `U` is immutably encoded in the committed `Order`.
6. On chain B, `_filled[commitment]` is already non-zero, so `cancelOrder` (any route) and `fillOrder` both revert with `Filled()` for this commitment.
7. Result: `amount` of `T` remains locked in `_orders[commitment][T]` on chain A indefinitely, with no on-chain path to redirect the refund to a non-blacklisted address or otherwise recover the funds.
