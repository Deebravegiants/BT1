### Title
Fraud detection stub causes fail-open `SignupReason` and unconditional Normal-path uploads/signing - (File: src/plans/mod.rs)

### Summary
`detect_fraud` in `src/plans/mod.rs:1392-1406` unconditionally returns `Ok(false)` for any non-`None` pipeline, since all real fraud checks were removed ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS"). This means `SignupReason::Fraud` in `src/backend/signup_post.rs:73-95` can never be set from this path, so any presented biometric/pipeline data — however anomalous — is always tagged `SignupReason::Normal` and proceeds through the normal enrollment/upload/signing flow.

### Finding Description
`detect_fraud(&mut self, orb, _debug_report, pipeline)` (`src/plans/mod.rs:1392-1406`) is the sole on-orb fraud gate feeding into whichever call site sets `SignupReason::Fraud` vs `SignupReason::Normal`. Its logic is:
- If `pipeline` is `None`, return `Ok(false)`.
- Otherwise, the pipeline's contents (occlusion errors, face-identifier fraud check results, etc., which are logged/collected elsewhere e.g. `src/plans/mod.rs:1355-1359`) are never inspected — the function returns `Ok(false)` unconditionally, per the explicit comment that fraud checks were deleted.

Since the boolean returned by `detect_fraud` is the only signal used to decide whether `SignupReason::Fraud` is assigned (as implied by the question's premise and the enum definition in `src/backend/signup_post.rs:73-95`, where `Normal` is `#[default]`), any adversarial pipeline — including one with `occlusion` errors or failed `face_identifier` checks — will still resolve to `SignupReason::Normal`. This value is then passed into `enroll_user::Plan` (`src/plans/mod.rs:1408-1420` passes `signup_reason` forward) and into the backend `signup_post::request` call, and correspondingly gates whichever upload/signing path (`upload_pcp_tier_0`, tier1/tier2 uploads referenced around `src/plans/mod.rs:558-638`) is taken for `secure_element::sign`-backed enrollment. The fail-open stub means there is no on-orb mechanism left to force the `Fraud` branch under any input.

### Impact Explanation
This corresponds to a liveness/fraud-bypass class finding: a presented physical fraud attempt (e.g., photo/mask presentation triggering occlusion or face-identifier failures) is never labeled as fraud on-device, so it is enrolled and uploaded through the same tier0/tier1/tier2 paths as a legitimate signup, and the secure element signs/attests it as a normal signup. This defeats an on-orb defense-in-depth control; the practical severity is bounded by whatever independent backend-side fraud checks exist (the code comment "not to be confused with the backend fraud checks" at `src/backend/signup_post.rs:80` explicitly acknowledges a separate server-side layer), so this is a loss of the on-orb fail-closed fraud gate rather than a guaranteed full identity-binding compromise.

### Likelihood Explanation
Fully deterministic and always reachable: any signup session that produces a `Some(pipeline)` will always get `Ok(false)` from `detect_fraud` regardless of pipeline content, with no dependency on attacker sophistication, timing, or race conditions. The only precondition is completing a signup attempt through the normal flow (unprivileged, attacker's own signup session), which is squarely in scope.

### Recommendation
Restore fraud-signal evaluation inside `detect_fraud`: inspect `pipeline.occlusion` (propagate `Err` as fraud), `pipeline.face_identifier_fraud_checks` results, and any other adversarial indicators already collected into `debug_report` (e.g., `occlusion_error`, `face_identifier_results` at `src/plans/mod.rs:1355-1358`), and return `Ok(true)` when any such indicator is present, fail-closed. At minimum, until real checks are reinstated, treat pipeline failure/anomaly conditions as fraud rather than defaulting to `Ok(false)`.
