### Title
`createWithdrawalIntents` skips the `FeeExceedsAmountError` guard present in `_estimateWithdrawalFee`, allowing a negative `actualAmount` when a stale/oversized `feeEstimation` is reused with `feeInclusive: true` - ([File: packages/intents-sdk/src/sdk.ts])

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = withdrawalParams.amount - feeEstimation.amount` when `feeInclusive` is true, but unlike `_estimateWithdrawalFee` it never checks `amount <= fee.amount` before subtracting. An unprivileged caller who supplies a `feeEstimation` object (obtained from an earlier, larger quote) alongside a smaller `withdrawalParams.amount` can drive `actualAmount` negative before any bridge-specific validation occurs.

### Finding Description
The broken equality is: **fee-consistency invariant** — `feeEstimation.amount` must be `<` `withdrawalParams.amount` whenever `feeInclusive` is true, so that `actualAmount = amount - fee.amount ≥ 0`. This invariant is enforced in `_estimateWithdrawalFee` [1](#0-0)  via `FeeExceedsAmountError`, but the analogous check is **absent** in `createWithdrawalIntents` [2](#0-1) , where `actualAmount` is computed directly at lines 342-344 without any bound check against `args.feeEstimation.amount`.

`createWithdrawalIntents` accepts `feeEstimation` as caller-supplied data (it does not re-fetch or re-validate it against the current `amount`), so it trusts that the `feeEstimation` passed in corresponds to the same `amount`. Nothing in the SDK enforces that the `feeEstimation` object was produced for this exact `withdrawalParams.amount` — it's plain data the caller constructs/reuses. If an attacker calls `estimateWithdrawalFee` for a large amount, caches the resulting `FeeEstimation`, and then calls `createWithdrawalIntents` with a much smaller `amount` and `feeInclusive: true`, `actualAmount` becomes negative (a `bigint`), and this negative `bigint` then flows into `bridge.validateWithdrawal(...)` and `bridge.createWithdrawalIntents(...)` as `amount: actualAmount`.

Whether this negative value is caught depends on the specific bridge's `validateWithdrawal` implementation (e.g. `poa-bridge.ts`, `intents-bridge.ts`, `omni-bridge.ts`, `hot-bridge.ts`, `direct-bridge.ts`, `aurora-engine-bridge.ts`). I was not able to fully confirm from the available context whether any of these bridges explicitly reject `amount <= 0` before serializing it into the intent's `amount` string field (e.g. via `.toString()`) for `ft_withdraw`/`mt_withdraw` intents. This is a gap in my verification — the grep results for `validateWithdrawal` in each bridge file were inconclusive for a definitive negative-amount guard, and the index's coverage of these files may be incomplete.

### Impact Explanation
If no downstream `validateWithdrawal` guard exists for negative/non-positive amounts, the resulting intent contains a negative `amount` string. Depending on how NEAR's `intents.near` contract or the specific token contract parses this field, this could revert (leaving the flow stuck) or be misinterpreted. Determining actual on-chain drain/misroute impact requires inspecting the intents contract's parsing of the `amount` field, which is outside this repo's control (`intents.near` and token contracts are explicitly out of scope per the rules). Within this SDK's own code path, the confirmed defect is: **the guard that exists in `_estimateWithdrawalFee` is missing in `createWithdrawalIntents`**, which is a real inconsistency and an SDK bug, but I cannot confirm a fund-draining Critical impact without visibility into every bridge's `validateWithdrawal` and the intents contract's amount handling.

### Likelihood Explanation
The precondition is that the caller controls the `feeEstimation` argument passed to `createWithdrawalIntents` independent of the `amount` in `withdrawalParams` — this is straightforward since these are two separate fields in the call and the function does not cross-check them against a corresponding stored quote. Calling `estimateWithdrawalFee` for a large amount and then `createWithdrawalIntents` for a smaller one costs the attacker nothing beyond two SDK calls, and is repeatable. However, most integrators call `signAndSendWithdrawalIntent`/`processWithdrawal`, which internally call `estimateWithdrawalFee` and pass the matching result to `createWithdrawalIntents` in the same flow [3](#0-2) , so the mismatch requires the caller to directly invoke `createWithdrawalIntents` with a manually-constructed/stale `feeEstimation`, rather than a normal API usage pattern.

### Recommendation
Add the same `FeeExceedsAmountError` guard from `_estimateWithdrawalFee` to `createWithdrawalIntents`:
```ts
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
  throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```
placed before computing `actualAmount` at [4](#0-3) .

### Proof of Concept
```ts
// vitest, mocking only HTTP-backed bridge internals (or stubbing bridge.supports/validateWithdrawal)
it("createWithdrawalIntents allows negative actualAmount with stale feeEstimation", async () => {
  const sdk = new IntentsSDK({ referral: "test" });
  const withdrawalParams = {
    assetId: "...", amount: 10n, feeInclusive: true,
    destinationAddress: "...", /* ... */
  };
  const staleFeeEstimation = { amount: 1000n /* from a prior BIG quote */, quote: null };

  // Assert equality before: amount (10n) vs fee.amount (1000n) -> amount <= fee.amount is true,
  // so actualAmount should never be computed without throwing.
  const intents = await sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation: staleFeeEstimation });

  // Currently: no FeeExceedsAmountError is thrown, and the resulting intent's amount is negative.
  const last = intents[intents.length - 1];
  expect(last.amount.startsWith("-")).toBe(true); // demonstrates the missing guard
});
```
Note: this PoC demonstrates the SDK-level guard omission; confirming exploitability further (e.g., whether the on-chain contract rejects, mishandles, or the specific bridge's `validateWithdrawal` already blocks non-positive amounts) requires additional investigation into each bridge implementation and the `intents.near` contract, which I was unable to complete within the available context.
