### Title
Webhook `shop` and `topic` values are trusted from unauthenticated HTTP headers while the HMAC only signs the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), but the HMAC signature that this gem verifies via `Utils::VerifiableQuery`/`to_signable_string` covers only the raw request body, not these headers.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Request#hmac` reads the HMAC value out of the `hmac-sha256` header [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated headers with no cryptographic binding to the body or the HMAC [3](#0-2) . The identity binding broken is: `bytes verified (raw_body) != bytes used for tenant/topic attribution (shop-domain / topic headers)`.

Because HMAC validation (via `Utils::HmacValidator.validate`, the same primitive used for OAuth callback/webhook checks elsewhere in the gem) only proves that the *body* was produced with knowledge of `api_secret_key` — it proves nothing about which shop or topic header accompanied that body. An app that uses `request.shop` (as this gem's own API surface encourages, per `Webhooks::Request#shop`) to key session/tenant lookups, without independently confirming that the `shop-domain` header actually corresponds to the store whose data lives in the body, is exposed to a cross-tenant confusion: a valid `(body, hmac)` pair recorded from Shop A's webhook can be resubmitted with the `shop-domain` header swapped to Shop B, and the HMAC check performed by this gem's own `hmac`/`to_signable_string` contract will still pass, because it only ever re-verifies the body.

This matches the report's underlying bug class (a resource being acted upon while a required binding — “equality” between the trusted authenticator and the used attribute — is not actually enforced), applied here as: `hmac(raw_body) valid` is treated by the API surface as if it also authenticates `shop-domain` and `topic`, when in truth it only authenticates `raw_body`.

### Impact Explanation
If an app built on this gem uses `ShopifyAPI::Webhooks::Request#shop` to select which merchant's session/data record to update (a very natural and gem-documented usage pattern, since the class exposes `shop` as a first-class accessor alongside the HMAC-guarded `hmac` method), an attacker who can capture or replay a body+HMAC pair (e.g., a mandatory GDPR/compliance webhook they receive for their *own* development store, or any webhook whose body content is not itself sensitive/tenant-specific) can pair it with a forged `shop-domain` header naming a different merchant. Because the gem's `Request` object offers no indication that `shop` is unauthenticated relative to the signature, downstream tenant-keyed logic can be tricked into acting on/for the wrong shop — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitability depends heavily on the host application's use of `request.shop`/`request.topic` and whether it treats these values as authenticated because the gem's `hmac` check passed. Since this gem is a thin request-verification veneer and does not itself perform privileged actions with `shop`, whether this is actually reachable to a real world "authentication bypass"/"cross-tenant access" depends on host-app trust assumptions this gem does not control or document as unsafe. This weakens confidence that the impact reaches the required bar without host-application cooperation, per the exclusion "analogs that depend on the host application ignoring this gem's documented API."

### Recommendation
Document explicitly that `shop`, `topic`, `webhook_id`, and `api_version` on `Webhooks::Request` are NOT covered by the HMAC and must not be used as sole tenant/routing identifiers without additional verification (e.g., cross-checking against a known/installed shop list). Consider incorporating these header values into the signable string used for verification, or provide a combined verification API that binds shop/topic to the signature check.

### Proof of Concept
Conceptual, since this requires a host application using `request.shop` as a trust boundary:
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives (or triggers) any webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header.
2. Attacker resends the same `raw_body` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (called against `Webhooks::Request`, whose `to_signable_string` is `@raw_body`) returns `true`, since the body is unchanged. `request.shop` now returns `victim.myshopify.com`.
4. If the host app trusts `request.shop` post-HMAC-check to route the webhook body to a tenant record, it processes attacker-supplied body content under the victim's tenant.

---
Note: this finding is conditioned on host-application usage of `Webhooks::Request#shop` as an authenticated value, which the gem itself does not enforce or prevent — it is a plausible but not conclusively proven exploit path purely inside this gem's own code, given the ambiguity flagged in "Likelihood Explanation." I was unable to find a stronger, fully self-contained (no host-app assumption) analog: all OAuth/JWT paths I examined (`lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/auth/jwt_payload.rb`, `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/utils/hmac_validator.rb`) bind `shop`/`host` values inside the HMAC- or JWT-signed payload itself, and forging those requires knowledge of `api_secret_key`, which is out of scope per the rules.
