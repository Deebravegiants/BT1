**Analysis:**

`code::publish_package` operates only on the `PackageRegistry` resource stored at `addr = signer::address_of(owner)` [1](#0-0) . Both the read (`borrow_global<PackageRegistry>(addr)`) and the write (`borrow_global_mut<PackageRegistry>(addr)` followed by `packages.borrow_mut(index)`) are keyed to that same `addr`, which is derived directly from the transaction signer, not from any attacker-supplied address argument [2](#0-1) .

Move's global storage model means `borrow_global_mut<PackageRegistry>(addr)` can only ever target the resource stored under `addr`, and that `addr` is fixed to `signer::address_of(owner)` — there is no code path where a different signer B can cause `publish_package` to fetch or mutate the `PackageRegistry` living at A's address. An attacker calling `publish_package_txn` as signer B will only ever create/mutate `PackageRegistry` at B's own address, matching on package names within B's own registry, never A's [3](#0-2) .

The only place where a *different* signer than the object owner is used to call `publish_package_txn` is `object_code_deployment::upgrade`, where a synthetic `code_signer` is generated from an `extend_ref` — but that generation is gated by an explicit `object::is_owner(code_object, publisher_address)` authority check performed immediately before, so an unprivileged caller cannot obtain that signer for someone else's code object [4](#0-3) . The formal spec also documents this as an audited high-criticality invariant: "Updating a package should fail if the user is not the owner of it" [5](#0-4) .

Since `vector::borrow_mut(index)` is applied to the `packages` vector inside a `PackageRegistry` resource that is address-scoped to the caller's own signer (or to an owner-authorized extend-ref signer), there is no way for an unprivileged signer B to reach or overwrite a `PackageMetadata` slot belonging to owner A's registry. The premised attack path does not exist — the custody boundary (resource address = signer address, or owner-checked extend_ref) already closes it.
