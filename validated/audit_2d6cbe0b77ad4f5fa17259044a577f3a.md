Confirmed: `docs/usage/webhooks.md:12-17` explicitly documents `data.shop` as an authoritative field the handler is meant to trust and act on (e.g., dispatching jobs "per shop"), and the library's own webhook processing pipeline never binds that field to the HMAC signature.

### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant spoofing of webhook origin - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw body, then hands `request.shop` — a value read straight from an HTTP header — to the app's handler as trusted metadata, without that value ever being part of the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes `HMAC(api_secret_key, request.to_signable_string)` — i.e. `HMAC(api_secret_key, raw_body)` — and compares it to the `hmac` header value: [3](#0-2) 

After that check passes, `request.shop` (unauthenticated header value) is forwarded unchanged into `WebhookMetadata`, which the app's handler is documented to treat as authoritative: [4](#0-3) [5](#0-4) 

The identity binding broken is: **shop claimed in the `shop-domain` header ≠ shop bound into the HMAC-signed bytes**. Since `api_secret_key` is the app's single shared client secret (identical across every shop that installs the app, not a per-shop secret), any merchant who installs the app on their own store legitimately receives correctly-signed webhooks. Such a merchant is an "unprivileged internet user" relative to *other* tenants of the same app. They can capture a genuine `(raw_body, hmac)` pair from their own shop's webhook deliveries and replay it to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a victim shop. Because the signature never covers the shop field, `HmacValidator.validate` still succeeds, and the forged request is dispatched to the app's handler tagged with the victim's shop domain.

### Impact Explanation
This is a cross-tenant identity confusion: data that is verified to have been signed by the app's secret (proving only "some installed shop sent this") is presented to the handler as if it were scoped to an attacker-chosen shop. Any app that follows the documented contract and uses `data.shop` to select which merchant's records to update, enqueue jobs against, or attribute the payload to (as shown in the gem's own usage example) can be made to process attacker-supplied webhook bodies under a victim shop's identity, corrupting that victim's data/state — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action available to anyone using Shopify) and be able to send arbitrary HTTP requests to the app's public webhook route — no access token, `client_secret`, or leaked credentials are needed. The replayed body/signature pair is legitimately obtained by the attacker for their own shop.

### Recommendation
Bind the shop domain (and other headers relied upon downstream) into the value that is HMAC-verified, or otherwise cross-check `request.shop` against a shop the app has an active, previously-established relationship/session for before trusting it, rather than trusting an unsigned header field as the tenant identifier.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, completing OAuth normally.
2. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(api_secret_key, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the same `raw_body`/`hmac` pair to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in [6](#0-5)  succeeds because it only checks `raw_body` against the shared secret.
5. `Registry.process` in [4](#0-3)  dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` to the app's handler, which acts on it as victim-shop data.
