### Title
Webhook shop-domain identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header, while the HMAC signature computed by `HmacValidator` only covers the raw request body. This breaks the identity binding `shop_verified_by_hmac == shop_acted_on`, letting any party who can obtain one validly-signed webhook body forge the shop identity attached to it.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (attacker/network-controllable) header, independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key` using `OpenSSL.secure_compare`, but never incorporates `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant for dispatch, with no secondary check binding it to what was actually signed: [4](#0-3) 

Because `Context.api_secret_key` is a single secret shared across every shop that has the app installed (this is standard Shopify OAuth app design), any shop that installs the app receives genuinely-HMAC-valid webhook bodies signed with that same shared secret. Such an installer — an "unprivileged" tenant relative to other merchants using the same app — can take one of their own validly-signed webhook deliveries (or any body they can get validly signed, e.g. via triggering an event on their own store) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value used to select/attribute per-shop data (session, tenant DB row, GDPR/redaction processing, etc.) is not covered by the same cryptographic check as the payload. A malicious app-installing merchant can make the host application process attacker-chosen webhook content under a different, victim merchant's shop identity, which can lead to cross-tenant data corruption or spoofed shop-scoped actions (e.g., forging `shop/redact`, `orders/create`, etc. as coming from another shop).

### Likelihood Explanation
Likelihood is limited to actors who can obtain at least one genuinely-signed webhook body for the shared app secret (i.e., any merchant who installs the app, which is an ordinary, unprivileged step for a public app), combined with the ability to send a crafted HTTP request with a modified `shop-domain` header to the app's public webhook endpoint. No secret leakage, TLS interception, or privileged account is required beyond normal app installation.

### Recommendation
Bind the shop identity into the verified material, e.g., include `shop`/`topic`/`webhook_id` fields (or a per-shop lookup) as part of `to_signable_string`, or independently verify that the `shop-domain` header corresponds to a session/shop that is expected to have generated the exact signed body, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of "{}" with the app's shared api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) still returns `true` because it only checks the body against the HMAC.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `shop: request.shop` equal to `victim-shop.myshopify.com`, even though the payload never originated from or was validated for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
