### Title
Webhook `shop`/`topic` headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, so any unprivileged party who can produce (or replay) a valid `(raw_body, hmac)` pair can attach arbitrary `shop-domain`/`topic` header values and have them accepted by `Registry.process`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body, using `OpenSSL.secure_compare`: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from the (attacker-controllable) HTTP headers: [3](#0-2) 

`Registry.process` validates only the HMAC, then dispatches to the handler keyed by `request.topic` and forwards `request.shop` into `WebhookMetadata` verbatim: [4](#0-3) 

Because the signable string is body-only, the `shop-domain` header is not bound to the signature at all: an unprivileged attacker who legitimately receives a webhook for their own installed/dev shop (a normal, valid `(raw_body, hmac)` pair sent by Shopify to any shop that installs the app) can resend that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` will still return `true`, since it never inspects those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop. Any app that trusts `data.shop` from the documented webhook handler contract to select which shop's session/access token/tenant data to act on — the documented, intended usage per `docs/usage/webhooks.md` and `BREAKING_CHANGES_FOR_V15.md` — is exposed to cross-tenant confusion, because the binding `shop_used_by_handler == shop_that_actually_sent_this_body` is never enforced by the gem.

### Impact Explanation
This breaks the identity binding between the authenticated bytes (body) and the acted-upon field (`shop`), enabling cross-tenant impersonation: a hostile merchant/attacker can cause an app to process/act on data intended for a completely different, unrelated shop, as long as they can supply *any* previously-observed valid body+HMAC pair (trivially available to them from their own legitimate webhook traffic) alongside a forged shop-domain header. This matches the "Critical - cross-tenant access" impact bucket, since the gem's own webhook processing API provides no way for a consuming app to detect the mismatch.

### Likelihood Explanation
High likelihood: any entity that has ever installed the app on a shop they control receives real Shopify webhook deliveries (valid raw_body + hmac) and can trivially replay that exact payload against the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are required — only observation of one's own legitimate webhook traffic and the ability to send an HTTP POST to the app's webhook route.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string that `HmacValidator` verifies, or otherwise cryptographically bind them to the HMAC (Shopify's HMAC is computed only over the raw body by design, so the gem should treat the `shop`/`topic` headers as unauthenticated metadata and document/enforce that consuming apps must independently verify that the reported `shop` for a webhook actually has this app installed with a matching webhook subscription before acting on the payload, rather than trusting `WebhookMetadata#shop` at face value).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the app's `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — true — via [5](#0-4)  and [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload never originated from Shopify for that shop, per the construction at [7](#0-6) .
