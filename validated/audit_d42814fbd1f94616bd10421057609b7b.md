### Title
`WrappedHyperFungibleToken.send()` locks fee-on-transfer underlying tokens but dispatches the full nominal amount, causing the contract to owe more than it holds - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable counterpart) pulls the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` without verifying that the contract's balance actually increased by `params.amount`. It then unconditionally dispatches a cross-chain message encoding `params.amount` as the locked/escrowed amount. If the underlying token charges a transfer fee (or otherwise delivers less than the nominal amount, e.g. rebasing tokens), the contract receives less than `params.amount` but promises the full `params.amount` to the destination chain, which will release/mint that full amount to the recipient on `onAccept`.

### Finding Description
In `send()`: [1](#0-0) 

the ERC20 branch simply calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then immediately builds and dispatches the cross-chain `DispatchPost` using `params.amount`, with no balance-before/balance-after check to determine the *actual* amount received. This is the exact bug-class from the external report: `depositExactToMintPrimeCash()` fails to check `netTransferExternal == actualTransferExternal` before crediting an exact amount; here, `send()` fails to check `balanceAfter - balanceBefore == params.amount` before committing to deliver `params.amount` cross-chain.

The identical pattern (and thus identical vulnerability) exists in the upgradeable variant: [2](#0-1) 

By contrast, the codebase's own `IntentGatewayV2.placeOrder()` demonstrates that the team is aware of this exact issue class and defends against it by snapshotting `balanceOf` before/after `safeTransferFrom` and mutating the escrowed/committed amount to the actual received value: [3](#0-2) 

`WrappedHyperFungibleToken.send()` has no equivalent protection.

On the receiving side, `onAccept()` unconditionally transfers out the full `message.amount` that was encoded in the message: [4](#0-3) 

So any deficit between "amount the sender-side contract actually locked" and "amount promised in the message" becomes a real shortfall paid out of the wrapper's other users' locked balances on the destination chain (or drains the local underlying reserve on `onPostRequestTimeout` refunds, which also refund the full nominal `message.amount`).

### Impact Explanation
This is a direct, unauthorized-underfunded-mint/escrow-drain class bug: an attacker (or simply any user bridging a standard fee-on-transfer/rebasing ERC20 through this wrapper) can systematically cause the wrapper contract to promise more underlying tokens than it actually custodies. Over repeated `send()` calls, the aggregate liability (sum of all `message.amount`s promised across all deployments of the wrapper on all chains) grows faster than the actual escrowed balance, permanently under-collateralizing the wrapper and eventually causing insolvency — later legitimate users' `onAccept` unlocks/timeout refunds will fail or drain the pool for the token, i.e. concrete freezing/loss of user funds. This satisfies the "unbacked mint" / "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Reachable by any single unprivileged call to `send()` on `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` when the configured `underlying` token has a transfer fee, is deflationary/rebasing, or otherwise doesn't deliver the exact requested amount via `transferFrom`. The contract's `configure()` allows the owner to pick any ERC20 as `underlying`; whether fee-on-transfer tokens are in scope depends on deployment configuration, but nothing in the contract prevents or checks for this, unlike `IntentGatewayV2`, which explicitly handles it. Given Notional's own audit flagged this exact pattern as Medium severity, and the fix (balance-diff check) is trivial and already used elsewhere in this codebase, this is a real and reachable gap.

### Recommendation
In `send()` (both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`), snapshot `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call, compute `actualReceived = balanceAfter - balanceBefore`, and either (a) revert if `actualReceived != params.amount`, or (b) use `actualReceived` (not `params.amount`) as the amount encoded into the dispatched `Message`/`DispatchPost`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder()`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `underlying` = a fee-on-transfer ERC20 (e.g., 1% fee, as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User calls `send({ amount: 1000e18, ... })`.
3. `safeTransferFrom(user, address(this), 1000e18)` actually delivers only `990e18` to the contract (fee taken).
4. `send()` still builds `Message({ amount: 1000e18, ... })` and dispatches it cross-chain.
5. On the destination chain, `onAccept()` calls `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)` (or mint, in the peer implementation), releasing 10e18 more than was ever actually escrowed by this transaction — a shortfall that compounds with each fee-on-transfer send and must ultimately be paid out of other users' locked balances.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
