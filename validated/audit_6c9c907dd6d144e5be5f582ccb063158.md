I have enough evidence to identify a concrete, in-scope analog: the webhook `shop` identity field is trusted for tenant routing but is not covered by the HMAC signature that the gem itself computes and verifies.

### Title
Webhook tenant identity (`shop` domain) is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then unconditionally forwards `request.shop` (and `request.topic`) to the app's handler as the tenant identifier, without any check that the header value was produced by Shopify for that specific webhook delivery.

### Finding Description
The relevant binding that should hold is: `shop header value` == `shop the HMAC was computed for`. In this gem that equality is never checked. [1](#0-0) 
- `hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header.
- `shop`, `topic`, `webhook_id`, `api_version` are derived from separate headers.
- `to_signable_string` returns only `@raw_body` — none of the identity headers are part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over that same body-only string, then trusts `request.shop` for routing without re-checking it against anything the signature covers: [3](#0-2) 

Because the webhook HMAC secret (`Context.api_secret_key`, the app's client secret) is the same for every shop that has installed the app, any merchant who installs the app on their own store legitimately receives real webhook deliveries with a valid `hmac-sha256` signature computed over a given body. That merchant (an unprivileged internet user relative to any *other* shop) can replay the exact same `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds because the signature only ever covered the body, and `Registry.process` passes the attacker-chosen `shop` straight through to `WebhookMetadata` and the app's handler: [4](#0-3) 

This is the same class of bug as the H-11 report: a value that is *acted upon* (there, `feeGrowthOutside0/1`; here, the tenant-identifying `shop`) is not the value that is *actually covered* by the integrity check (there, the wrong global fee counter was subtracted; here, the `shop` header is outside the HMAC's scope entirely).

### Impact Explanation
Any handler that uses `data.shop` from `WebhookMetadata` to select which tenant's records to create/update (exactly as shown in the gem's own documentation and breaking-changes guide) can have data attributed to, or actions taken against, a different merchant's tenant than the one that actually triggered the webhook event, i.e., cross-tenant access/data confusion, consistent with the "cross-tenant access" High/Critical impact category. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
Reachable by any unprivileged actor who can install the target app on a store they control (a normal, unprivileged flow), then capture and replay a legitimately-signed webhook body while modifying the `shop-domain` (or `x-shopify-shop-domain`) header on the replayed request — no access to `client_secret`, access tokens, or any privileged credential is required, since the shared HMAC secret only signs the body.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed payload that `HmacValidator` verifies, or otherwise cryptographically bind the `shop-domain` header to the HMAC before `Registry.process` trusts and forwards it — mirroring the H-11 fix pattern of ensuring the value that is checked is the same value that is subsequently acted upon.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker.myshopify.com`, triggering a real webhook delivery with body `B` and a valid header `x-shopify-hmac-sha256: HMAC_SHA256(client_secret, B)` for shop `attacker.myshopify.com`.
2. Attacker captures `B` and the HMAC header value.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B`, the same (still-valid) `x-shopify-hmac-sha256` header, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (= `B`) and matches the header — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which processes/records data as if it originated from `victim.myshopify.com`.
