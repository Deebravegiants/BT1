### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then attributes the request to whatever `shop-domain` header value is present, without any binding between the verified bytes and that header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop`/`#topic`/`#webhook_id`/`#api_version` are read directly from HTTP headers with no cryptographic tie to the signed payload [2](#0-1) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header [3](#0-2) . Once that check passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` and hands it to the app's handler [4](#0-3) .

This breaks the identity binding `verified_bytes == attributed_shop`: the HMAC only proves "this body was signed by Shopify with our shared secret," not "this body belongs to shop X." Contrast this with `Auth::Oauth::AuthQuery`, where `shop` (along with `code`, `host`, `state`, `timestamp`) is explicitly included in `to_signable_string` so it is cryptographically bound to the signature [5](#0-4) . The webhook path has no equivalent binding for `shop-domain`.

An unprivileged internet user who has ever observed one legitimate webhook delivery for shop A (e.g., their own store's `orders/create` webhook, or a body/HMAC pair intercepted from a non-TLS-terminated proxy/log) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for shop B. Since `to_signable_string` never includes the shop header, the HMAC check in `HmacValidator.validate` still succeeds, and the handler receives `WebhookMetadata(shop: "shop-b.myshopify.com", body: <shop A's data>, ...)`. Any app logic that trusts `data.shop` to key per-tenant state (as the gem's own webhook documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process/store shop A's webhook payload under shop B's tenant record.

### Impact Explanation
This is a cross-tenant data confusion vulnerability: an attacker who is a legitimate merchant of shop A (or who otherwise obtains one valid signed webhook body/HMAC pair) can cause the receiving app to attribute that payload to an arbitrary victim shop of their choosing, since the shop identity is not bound to the signature. Depending on how the host app keys its per-shop database updates from `data.shop`, this can corrupt or leak another tenant's data — a cross-tenant access outcome.

### Likelihood Explanation
Exploitation requires only one legitimate webhook body+HMAC pair signed with the developer's own shared secret (trivially obtainable by any merchant/attacker who installs the app, since `shop-domain` is never checked against the signed content) and the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no access to `api_secret_key`, tokens, or the real target shop is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) header values in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the payload before exposing it via `WebhookMetadata`, mirroring the approach used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker-shop.myshopify.com`, and receives a legitimate webhook delivery: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC over `B` with the app's shared secret).
2. Attacker sends a forged HTTP request to the app's webhook endpoint with the same raw body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` [7](#0-6) , causing the app to process attacker-controlled data under the victim shop's identity.
