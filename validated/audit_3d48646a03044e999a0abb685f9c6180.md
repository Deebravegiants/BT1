Audit Report

## Title
`ERC20Transactor` credits full nominal amount to XCM holding without verifying actual balance change on the checking account, enabling fee-on-transfer / deflationary ERC20 tokens to mint phantom XCM asset credit - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` invokes `IERC20::transferCall` on an arbitrary contract selected purely by its `AccountKey20` location shape (no allow-list/registration check), and credits the full requested nominal `amount` into the XCM `AssetsInHolding` register based solely on the boolean return value of `transfer()`, never verifying the checking account's actual balance delta. [1](#0-0)  The symmetric `deposit_asset_with_surplus` has the same flaw in reverse. [2](#0-1)  Any fee-on-transfer/deflationary ERC20 contract can therefore generate XCM asset credit exceeding what is actually escrowed in the checking account.

## Finding Description
`ERC20Matcher` matches any location shaped `(0, [AccountKey20 { .. }])` and converts it directly to an `H160` contract address — there is no registration/allow-list gate restricting which contract addresses may be used as an XCM asset kind. [3](#0-2)  Because `pallet-revive` supports permissionless contract instantiation, any unprivileged user can deploy their own ERC20-ABI-compatible contract and immediately reference it in an XCM program via its `AccountKey20`.

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` on the arbitrary contract, and inspects only the decoded boolean return value of `transfer()`; if `true`, it unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the full nominal `amount`, not the amount actually received by `TransfersCheckingAccount`. [4](#0-3)  A fee-on-transfer/deflationary ERC20 legally returns `true` while delivering less than `value` to the recipient, so this check is provably insufficient to establish that the checking account's balance actually increased by `amount`. `Erc20Credit` itself performs no runtime-level balance enforcement — its doc comment explicitly states balance constraints are assumed to be enforced by the ERC20 contract, which fee-on-transfer tokens violate by design. [5](#0-4)  The transactor is live in Asset Hub Westend's `AssetTransactors` tuple. [6](#0-5)  An existing test (`smart_contract_does_not_return_bool_fails`) confirms the transactor's validation logic is limited to decoding/interpreting the raw boolean-like return value and does not perform any balance-delta check on the checking account. [7](#0-6) 

## Impact Explanation
Each `WithdrawAsset` against a fee-on-transfer ERC20 mints `amount` worth of XCM-holding credit while the checking account only actually receives `amount - fee`. This "phantom credit" is fungible within the XCM executor and can be deposited to any beneficiary or moved cross-chain via reserve transfer, letting the attacker realize more nominal value than was ever escrowed. Repeated exploitation increases the shortfall between the checking account's real ERC20 balance and the aggregate amount notionally backed by outstanding XCM credit for that asset kind, which can eventually cause legitimate `deposit_asset_with_surplus` calls for the same asset to fail with `"ERC20 contract transfer failed"` once the checking account cannot cover promised amounts — a fund-lock/DoS condition for honest holders of that asset kind. This is an in-scope accounting/insolvency defect in an SDK-provided XCM asset transactor, not a bridge-only or governance-only issue.

## Likelihood Explanation
No privileged role is required. An attacker can (1) deploy a self-controlled ERC20-ABI contract on `pallet-revive` implementing fee-on-transfer semantics that still returns `true`, (2) reference it directly as an `AccountKey20` XCM asset kind — since `ERC20Matcher` performs no registration check, this step requires no permission — and (3) submit ordinary `WithdrawAsset`/`DepositAsset` XCM programs against it. The attack is fully repeatable and entirely within an unprivileged user's control.

## Recommendation
Do not rely solely on the ERC20 `transfer()` boolean return value. In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the destination account's ERC20 balance before and after the `bare_call` and use the actual observed delta rather than the requested nominal `amount` when constructing/crediting `AssetsInHolding`. If the observed delta is less than requested, either fail the operation or credit only the amount actually received.

## Proof of Concept
1. Deploy a `EvilERC20` contract via `pallet-revive` that implements `IERC20`, deducting e.g. 5% on `transfer()` (burning or redirecting it) while still returning `true`.
2. Reference `EvilERC20`'s address as an `AccountKey20` XCM asset (matched automatically by `ERC20Matcher`, no registration needed).
3. Submit an XCM program: `WithdrawAsset { EvilERC20, amount: 1000 }` from the attacker's account, followed by `DepositAsset` to a second attacker-controlled account.
4. Observe that `withdraw_asset_with_surplus` credits `Erc20Credit(1000)` into holding (per `erc20_transactor.rs` L197-203) even though `TransfersCheckingAccount`'s real `EvilERC20` balance only increased by 950.
5. Repeat the sequence; the checking account's real balance for `EvilERC20` progressively falls behind the aggregate XCM-credited amount, eventually causing `deposit_asset_with_surplus` for honest holders of the same asset to fail with `"ERC20 contract transfer failed"`.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
