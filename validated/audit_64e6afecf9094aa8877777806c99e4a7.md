### Title
Untested/unverified hostile-pre-seed graduation defense can let an attacker capture the HyperSwap V2 LP at a manipulated price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`packages/contracts/AGENTS.md` explicitly documents that the end-to-end regression suite validating the hostile-pre-seed graduation defense (`test/HostilePreSeed.t.sol`) was removed after deployment, and that the specific properties it enforced — "wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation" — are **no longer enforced by automated tests**. [1](#0-0) 

### Finding Description
`finalizeGraduation` is a permissionless phase-2 call that seeds a HyperSwap V2 TOKEN/LT pair with the curve's raised LT and the 250M reserved tokens, using `_ensureUniswapV2Pair` / `_seedUniswapV2Direct` and its fallbacks `_seedRebalancing`, `_pairRebalance`, `_routerDepositAndDispose`. [2](#0-1) 
This logic is explicitly designed to defend against an attacker who front-runs phase 1→2 by pre-creating the V2 pair and dust-seeding or hostile-minting into it to distort the opening price ("hostile-pre-seed"), per the AGENTS.md design notes. [3](#0-2) 
However, the dedicated integration suite that proved the defense actually prevents a wrong opening price / LP capture, guarantees the attacker earns no profit, and correctly isolates concurrent graduations sharing the same LT was removed, per the maintainers' own admission. [4](#0-3) 
Only unit-level tests in `TwoPhaseGraduation.t.sol` and `GraduationInvariants.t.sol` remain, and these primarily validate the "honest" empty-pair / no-attacker path (`test_phase2_anyone_can_finalize`, `test_phase1_caches_pendingGraduation_state`, etc.), not the hostile-attacker scenario. [5](#0-4) [6](#0-5) 
`finalizeGraduation` is reachable by any unprivileged address once a token enters `Lifecycle.Graduating` (phase 1), and the two-phase split intentionally parks all curve-raised LT and the 250M reserved tokens on `Bonding` in the window between phase 1 and phase 2 — precisely the window an attacker can exploit by pre-seeding the HyperSwap pair before calling (or waiting for) `finalizeGraduation`. [7](#0-6) 

### Impact Explanation
Without the removed regression coverage, there is no automated verification that:
1. A hostile pre-seed cannot force the LP to open at a price divorced from the curve's closing price (an "LP seeded away from the curve close price"), which would let the attacker extract value from the newly seeded pool at the expense of the token's LP/creator/traders.
2. The attacker "no-profit" guarantee holds, i.e., that the rebalancing fallbacks (`_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose`) cannot be gamed for a net gain.
3. Concurrent graduations sharing the same LT correctly isolate each other's escrowed `protectedLT`, so one token's `finalizeGraduation` cannot consume or leak another token's curve-raised LT.

Any regression in this security-critical, previously-tested code path (e.g. during a future edit to `_seedUniswapV2Direct`/`_pairRebalance`/`_routerDepositAndDispose`) would now go undetected by CI, and could manifest as a mispriced/attacker-captured LP or cross-token LT leakage — both of which are in-scope, concrete impacts (LP mispricing, fund freezing/theft).

### Likelihood Explanation
`finalizeGraduation` is permissionless and callable by any address the moment a token is `Lifecycle.Graduating`, and pre-seeding a V2 pair before that point is a normal, unprivileged on-chain action (deploying/donating to the not-yet-existing TOKEN/LT pair). The attack surface is reachable purely through public transactions (create pair, donate/mint, wait for or trigger phase 2), matching the allowed unprivileged-caller scope. The gap here is specifically a *verification* gap: the code claims to be "brick-proof" and "no-profit" against this exact scenario, but that claim is no longer backed by the automated tests that once proved it, so any subtle regression or edge case introduced by future changes to the graduation/rebalance code is likely to ship undetected.

### Recommendation
Reinstate (or re-derive) `test/HostilePreSeed.t.sol` covering: (a) wrong-opening-price / LP-capture attempts via pre-created + hostile-minted pairs, (b) an assertion that the attacker's net LT/token position after the full attack sequence is non-positive ("no profit"), (c) leftover/residue recovery accounting, and (d) concurrent-graduation isolation with `protectedLT` when two tokens share an LT and both reach `Lifecycle.Graduating` before either finalizes. Gate any future change to `_enterGraduating`, `finalizeGraduation`, `_prepareGraduationLiquidity`, `_seedUniswapV2Direct`, `_seedRebalancing`, `_pairRebalance`, `_routerDepositAndDispose`, or `_sweepLTToOwner` on these tests passing, consistent with the "Tests you MUST re-run" policy already documented for the rest of the graduation invariants.

### Proof of Concept
Not applicable as a standalone exploit transaction — this finding is a verification/coverage gap rather than a demonstrated state-changing bug. The concrete risk is that a future edit to the hostile-pre-seed defense code paths (`_seedUniswapV2Direct` and its `_seedRebalancing`/`_pairRebalance`/`_routerDepositAndDispose` fallbacks, invoked from the permissionless `finalizeGraduation`) could reintroduce a wrong-opening-price LP capture, attacker profit, or concurrent-graduation LT leakage without any automated test catching it, since the maintainers' own documentation confirms the suite that checked exactly these properties was deleted post-deployment. [4](#0-3)

```markdown
## Graduation — Two-Phase, Dynamic LP Seeding (Read This Before Touching Graduation Code)

This is the most bespoke piece of the protocol. Full rationale + invariants live in [`docs/contracts-scope.md`](../../docs/contracts-scope.md#graduation); the short version:

- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
- **Virtual token reserve.** At launch, `Pair.reserve0 = totalSupply (1B)` while only `curveSupply = 75%` (750M) of real tokens are transferred to the pair. The other 250M (`LP_RESERVE`) sit in `Bonding` for graduation. This extends the curve beyond the sellable supply, which is what makes dynamic LP seeding work cleanly.
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
- **Parabola invariant.** With `V_t_init = totalSupply` and `curveSupply = 75%`, the function `tokensForLP(sold) = sold·(S−sold)/S` peaks at `S/4 = LP_RESERVE`. The cap in `_prepareGraduationLiquidity` is defensive — it can never bind in normal operation.
- **Overflow buy cap.** `Router.buy` caps `tokensOut` at the pair's real balance and back-calculates the LT consumed, so the last buy cannot exceed remaining supply. `Zap.buy` returns the unused LT (`ltMinted - amountInUsed`) directly as LT — not redeemed, to avoid re-incurring the LT redemption fee on dust — while unconverted USDC and the fee over-charge are refunded in USDC. `Bonding.buy` returns `(tokensOut, amountInUsed)` for this reason.

**If you change `_enterGraduating`, `finalizeGraduation`, `_prepareGraduationLiquidity`, `_seedUniswapV2Direct` (or any of its `_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose` / `_noFeeSwapInput` helpers), `Router.buy`'s capping logic, or the seeding in `_deployAndSeed`:** you MUST re-run `test/GraduationInvariants.t.sol`, `test/TwoPhaseGraduation.t.sol`, and `test/NoFeeSwapInput.t.sol`. All 7 zero-gap invariants must still pass; the phase-1-fits-in-small-block budget assertion (1.8M) must still hold; the brick-resistance regression test must still pass. These invariants are the product — do not loosen their assertions to make a change go green.
```

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```
