### Title
Webhook HMAC covers only the raw body, not the `shop`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies the HMAC exclusively over the JSON body bytes. The tenant identifier (`shop`), topic, webhook id and API version are all read straight from HTTP headers that are never covered by the signature. Because the same `api_secret_key` is used for HMAC verification across every shop that installs the app, any actor who legitimately receives one correctly-signed webhook (e.g. by installing the app on their own store) can replay that exact `body`+`hmac` pair to the app's public webhook endpoint while swapping the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header to point at a different, victim shop. The signature still validates because it never covered those header fields, so the forged event is processed and handed to the host app's handler as if it genuinely originated from the victim tenant.

### Finding Description
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all derived from HTTP headers: [1](#0-0) 
- `Request#to_signable_string` is defined to be just the raw body, excluding all header values from the signable content: [2](#0-1) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This breaks the intended identity binding of `shop == shop covered by HMAC`. The gem's contract is that a webhook whose HMAC validates should be attributable to the shop it claims to be from; in fact the HMAC only proves "this body was produced by someone who received an event signed with the app's secret," not "this body belongs to this shop." Since the `client_secret`/`api_secret_key` is shared across every install of the app, any tenant that receives one real webhook can mint arbitrary (topic, shop, webhook_id) combinations that still pass `HmacValidator.validate`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: a malicious/unprivileged merchant who installs the app on their own shop can forge webhook deliveries that `Registry.process` will accept as coming from a different shop, injecting attacker-controlled body content and metadata into the host application's per-tenant webhook handling. Depending on how the host app keys its data on `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or disclosure, matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any app developer/merchant who can install the app (no special privilege, no access to `api_secret_key` needed) can capture a real webhook payload+signature delivered to their own endpoint and replay it directly to the app's public webhook URL with a modified `shopify-shop-domain`/`shopify-topic` header. No TLS interception or credential theft is required — only the ability to receive one legitimate webhook and to send a normal HTTP POST to the app's own webhook endpoint.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify header values against values embedded in the payload where Shopify provides them). At minimum, document that `request.shop`/`request.topic` are unauthenticated header values and that host applications must not treat a passing `HmacValidator.validate(request)` as proof that the request's `shop` header is trustworthy.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, body `B`, and a valid `shopify-hmac-sha256` computed as `HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, hmac)` and crafts a new POST to the same app webhook endpoint with headers changed to `shopify-shop-domain: victim.myshopify.com` (and/or a different `shopify-topic`), keeping body `B` and the captured `hmac` unchanged.
3. `Utils::HmacValidator.validate(request)` calls `Request#to_signable_string`, which returns only `B`; the HMAC recomputed over `B` matches, so validation succeeds: [4](#0-3) 
4. `Registry.process` builds `WebhookMetadata` using the forged `shop`/`topic` from the headers and invokes the host app's handler as if the event genuinely came from `victim.myshopify.com`.
