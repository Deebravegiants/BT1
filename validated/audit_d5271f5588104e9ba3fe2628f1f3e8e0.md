### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` enables cross-network signer-capability offer replay - ([File: aptos-move/framework/aptos-framework/sources/account/account.move])

### Summary
`account::offer_signer_capability` authorizes delegation of full signer authority over an account to a `recipient_address` based on a signature over `SignerCapabilityOfferProofChallengeV2`. Unlike its sibling struct `RotationCapabilityOfferProofChallengeV2`, which was explicitly patched to include `chain_id` "to prevent replaying the challenge message," `SignerCapabilityOfferProofChallengeV2` still omits `chain_id`. This is the exact bug class from the external report (missing chain-domain separation in a signed authorization payload), reproduced natively within the same Move module.

### Finding Description
`account.move` defines two "V2" proof-challenge structs used to authorize delegation of account capabilities via an off-chain signature: [1](#0-0) 

- `RotationCapabilityOfferProofChallengeV2` includes `chain_id` — the doc comment explicitly states this "prevents replaying the challenge message."
- `SignerCapabilityOfferProofChallengeV2` has no `chain_id` field, only `sequence_number`, `source_address`, `recipient_address`.

`offer_signer_capability` constructs and verifies this challenge without any chain binding: [2](#0-1) 

Because the struct is not domain-separated by `chain_id`, a signature produced by an account owner authorizing a signer-capability offer to `recipient_address` on one Aptos network (e.g., a testnet, devnet, or private/forked network sharing the same address-derivation scheme and having the account at the same `sequence_number`) is bit-for-bit identical to and valid on any other network. `offer_signer_capability` never checks `chain_id::get()` against anything in the signed payload, so the signature can be replayed verbatim on a different network to grant capability offers there.

This directly parallels the reported bug: the signed authorization is not bound to the execution context, so the same authorization is valid in a context the signer never intended.

### Impact Explanation
`signer_capability_offer` grants `create_authorized_signer` the ability to synthesize a fully-authoritative `signer` for the source account: [3](#0-2) 

A signer obtained this way has unrestricted custody over everything the account owns — coins, objects, fungible-asset stores, resource-account capabilities reachable through it, etc. If a replayed signature installs an attacker-controlled `recipient_address` as the signer-capability holder on a network where the victim did not intend to grant it, the attacker can call `create_authorized_signer` there and drain/transfer/burn any assets held by that account address on that network. This is a custody-grade, full account/asset takeover impact.

### Likelihood Explanation
Exploitation requires: (1) the same account address exists on two networks sharing Aptos's key-derivation scheme (common for testnet/devnet/mainnet address reuse, local forks, or migrations), and (2) the account's `sequence_number` matches at signing time on both networks (plausible for freshly created or low-activity accounts, or deliberately engineered by an attacker who controls timing/replay on a low-traffic secondary network). This is a narrower window than the original EIP-4337 report (which had no sequence-like binding at all), but it is a genuine, code-provable inconsistency versus the already-fixed sibling struct in the same file, and the impact (full signer capability) is more severe than the paymaster case.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and populate it with `chain_id::get()` in `offer_signer_capability`, then bump to a new versioned struct/entry function if backward compatibility with existing tooling/signatures is required.

### Proof of Concept
Not independently executable within this review (no test harness run); the PoC path is inferential from code inspection:
1. Attacker observes/derives a signature `sig` = Ed25519(`SignerCapabilityOfferProofChallengeV2 { sequence_number: N, source_address: A, recipient_address: R }`) submitted by victim `A` on Network 1 via `offer_signer_capability`.
2. On Network 2, where account `A` also exists (same derivation) with `sequence_number == N`, attacker (as `R`, or having `R` under their control) calls `account::offer_signer_capability(A, sig, scheme, pubkey, R)` — this passes verification because the signed struct has no `chain_id` to distinguish networks.
3. Attacker then calls `account::create_authorized_signer(R_signer, A)` on Network 2 to obtain full signer authority over `A`'s assets there. [4](#0-3) 

Given the tool-call limit, I was unable to trace `verify_signed_message`'s exact source (only test-only helper and call sites were retrieved) or confirm all call sites consuming `SignerCapabilityOfferProofChallengeV2` outside `account.move`; this should be verified further, along with checking whether any newer AIP has since added chain binding to this specific struct.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
