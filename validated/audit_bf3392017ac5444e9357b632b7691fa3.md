### Title
Requesters have no way to bound the protocol fee applied to their order — a governance-updated `protocolFeeBps` can be raised right before `placeOrder` executes, silently deducting far more than the requester expected - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` fetches the protocol fee rate (`protocolFeeBps`) from mutable storage (`_destinationProtocolFees[destinationHash]` or the fallback `_params.protocolFeeBps`) at the moment the transaction executes, not at the moment the requester approved/signed their intent. The `Order` struct the requester submits carries no field expressing the maximum fee they are willing to accept, so there is nothing on-chain to compare the live rate against — mirroring exactly the MechMarketplace bug class where a requester's parameters are fetched fresh from mutable state with no requester-supplied ceiling to validate against.

### Finding Description
`placeOrder` computes the protocol fee this way: [1](#0-0) 

This value is read live from storage that governance can update at any time via `_updateParams`: [2](#0-1) 

The only bound enforced during update is `feeBps < 10_000` for destination-specific overrides (i.e., up to 99.99% is accepted), and the deduction is applied directly against the requester's escrowed input: [3](#0-2) 

A requester builds an `Order`, approves the exact `amountIn` to the gateway (per the SDK/docs flow), and expects a fee close to what they quoted off-chain (e.g. 5–30 bps per the docs and tests). Because `order.inputs[i].amount` and the escrowed `reducedInputs[i].amount` are derived from `protocolFeeBps` read at execution time — not a value the requester attested to inside the `Order` struct — a governance/admin update to `_params.protocolFeeBps` or `_destinationProtocolFees[dest]` submitted just before the requester's `placeOrder` transaction lands can inflate the deducted fee arbitrarily up to just under 100% of the input, with no on-chain check comparing it to what the requester expected.

This is structurally identical to the MechMarketplace issue: a requester's transaction depends on a parameter (delivery rate / payment type there; protocol fee bps here) fetched from mutable state at execution time, with the requester providing no attested ceiling for that parameter to be validated against.

### Impact Explanation
If the protocol-fee-setting authority (or a compromised/malicious governance path, or simply an unlucky race between a legitimate fee update and a pending user transaction) raises `protocolFeeBps` right before a pending `placeOrder` transaction executes, the requester's escrowed input is reduced by an amount they never agreed to — up to nearly the entire deposited amount, since the only cap is `< 10_000` bps (100%). Because `commitment = keccak256(abi.encode(order))` is computed from the already-fee-reduced `order.inputs`, the requester's escrow and the amount available to solvers/output guarantee are both computed off the inflated fee, and the dust is emitted/collected as protocol revenue (`DustCollected`) with no recourse for the requester. This is a direct fund-loss vector for a normal, unprivileged order-placing user.

### Likelihood Explanation
Exploitation requires either malicious/compromised control of the parameter-update path (a `RequestKind.UpdateParams` message delivered by Hyperbridge governance) or a legitimate fee change racing a user's pending transaction in the mempool. Given the rules exclude "malicious-governance" as an accepted threat model on its own, the more relevant and reachable scenario is the race condition: any parameter update transaction that is public/pending can be observed and a requester's `placeOrder` can be sandwiched, or a requester's `placeOrder` can simply land after an intervening legitimate fee bump they didn't anticipate, with no protection. The lack of a requester-supplied fee ceiling means this is always exploitable whenever the fee is adjustable, independent of whether the adjustment itself is malicious.

### Recommendation
Add a requester-supplied maximum acceptable protocol fee (e.g., `order.maxProtocolFeeBps`) and enforce `protocolFeeBps <= order.maxProtocolFeeBps` in `placeOrder`, reverting otherwise — directly analogous to the MechMarketplace fix that requires the requester to supply `paymentType`/`maxDeliveryRate` and validates them against the live mech values before proceeding.

### Proof of Concept
1. Requester quotes an order off-chain via `quoteOrderFees`/`quote.amountIn`, observing current `protocolFeeBps` (e.g., 5 bps), approves `amountIn` to `IntentGatewayV2`, and submits `placeOrder(order, graffiti)`.
2. Before the transaction is mined, the governance-authorized `onAccept` path delivers an `UpdateParams` request that raises `_params.protocolFeeBps` (or sets a destination-specific override in `_destinationProtocolFees`) to, e.g., 9999 bps, as permitted by [4](#0-3) .
3. The requester's `placeOrder` transaction then executes, reading the new inflated `protocolFeeBps` at [5](#0-4)  and deducting nearly the entire input as "protocol fee" per [3](#0-2) , escrowing only dust for the requester's actual order while the rest is collected as `DustCollected`.
4. The requester receives an order with an unusable/near-zero escrowed amount, effectively losing their deposited funds to the fee, with no on-chain check that would have reverted the transaction against their originally expected fee ceiling.
