### Title
Webhook shop-tenant attribution not covered by HMAC signature enables cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body against the app's shared `api_secret_key`. The `shop` (and `topic`/`webhook_id`) values that identify *which merchant* the webhook belongs to are read straight from HTTP headers and are never included in the signed payload. This is the same bug class as the AMM report: a value that is *acted upon* (the tenant/shop identifier used to route data into per-shop application logic) is not *covered by* the cryptographic binding (the HMAC) that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all pulled directly from headers with no cryptographic linkage to the body/signature: [2](#0-1) 

`Registry.process` verifies only the HMAC of the body, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC using the shared `Context.api_secret_key`: [4](#0-3) 

Because a single app's `client_secret`/`api_secret_key` is shared across **every merchant that installs the app**, not scoped per shop, a `(body, hmac)` pair that is valid for the attacker's own shop is *also* a cryptographically valid pair for any other shop — the HMAC never binds the body to a specific `shop-domain`. This breaks the intended identity binding: `shop_header == shop_that_produced(hmac)`. In reality the equality that holds is only `hmac == HMAC(body, shared_secret)`, with no relation to the `shop-domain` header at all.

### Impact Explanation
An unprivileged internet user who can install the target app on their own (attacker-controlled) shop — the normal way any merchant obtains and receives real, validly-HMAC'd webhooks — can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair delivered to their own shop, then replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. `Registry.process` will accept the forged request as authentic (HMAC still validates, since it only signs the body) and dispatch it to the app's handler tagged with the victim's shop, per the documented `data.shop` contract used by host applications to route data: [5](#0-4) 

If the host application's handler uses `data.shop` to look up sessions, write per-tenant records, or trigger downstream actions (as the docs' example itself does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), the attacker can inject or corrupt data attributed to a different, victim tenant — a cross-tenant integrity/confidentiality violation stemming directly from a gap in this gem's own webhook authentication code, not from any host-app misuse.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the target Shopify app on any shop the attacker controls (a normal, unprivileged action for any Shopify merchant/developer), and (2) knowledge of the app's public webhook callback URL (typically discoverable/guessable, or the same URL used for the attacker's own shop). No access to `api_secret_key`, tokens, or the victim's credentials is required — satisfying the "unprivileged internet user" and "no privileged access" constraints. This is a realistic, low-effort forgery, not merely theoretical.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, e.g. by requiring host apps to verify that `request.shop` corresponds to a shop with a currently valid, previously-established session/webhook registration before trusting `data.shop`, or by extending `to_signable_string` semantics/documentation so the gem itself enforces that the reported shop matches an expected, independently-authenticated shop before invoking the handler (e.g. cross-check against the registry of shops that have active registrations for the given `webhook_id`/topic, or require the consuming app to correlate `webhook_id` with a call back to Shopify's Admin API for confirmation).

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, using the app's real `client_id`. Shopify sends the attacker a real webhook, e.g. `orders/create`, with:
   - body: `{"id":1,...}`
   - header `x-shopify-hmac-sha256: <valid HMAC of body under the app's shared api_secret_key>`
   - header `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker captures the exact `(raw_body, hmac_header)` pair.
3. Attacker replays an HTTP POST to the app's public webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` (lib/shopify_api/utils/hmac_validator.rb:13) succeeds because it only recomputes HMAC over `raw_body`, matching the replayed header.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-supplied data as though it originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
