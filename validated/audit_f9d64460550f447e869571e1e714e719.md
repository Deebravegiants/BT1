Confirmed root cause: in `Registry.process`, `request.shop` (from the `x-shopify-shop-domain` header, `lib/shopify_api/webhooks/request.rb:20-23`) is passed straight into `WebhookMetadata` and handed to the app's `handle` callback, while the HMAC signature only authenticates `@raw_body` via `to_signable_string` [1](#0-0) . The `shop` header is never part of the signed bytes, so it is "verified" only in the sense that the request passed HMAC — the `shop` field itself is unauthenticated and attacker-controlled.

### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate(request)` in `Registry.process` only proves that the caller knows the app's `client_secret`/API secret and that the body bytes are unmodified [2](#0-1) . The `shop` value used to identify *which tenant* the webhook belongs to is read straight from the `x-shopify-shop-domain` header via `shopify_header`, which is never included in the signed payload [3](#0-2) . This is the same bug class as the report: the field acted upon (identity/refund target, here `shop`) is not bound by the cryptographic check (HMAC/signable string), so it can be set independently of the verified data (analogous to `refundAccount` not being covered by the message that was validated).

### Finding Description
- `Registry.process(request)` validates HMAC over the request, then immediately trusts `request.shop` to build `WebhookMetadata` and dispatches it to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .
- `request.shop` is `shopify_header("shop-domain")`, sourced purely from HTTP headers [3](#0-2) .
- The HMAC signable string is `@raw_body` only [1](#0-0) ; `topic`, `shop`, `api_version`, and `webhook_id` are all excluded from the signature.
- Because any subscriber who has legitimately received one signed webhook body from Shopify (or replays/forwards it) controls the headers independently of the signature, they can pair a validly-signed body with a forged `x-shopify-shop-domain` header for a *different* shop and have the app process it under the wrong tenant's identity.

### Impact Explanation
This is a cross-tenant identity-binding gap: the equality that should hold — "the `shop` acted upon by the handler == the `shop` that produced/authorized the signed bytes" — is not enforced by this gem. Downstream apps that use `WebhookMetadata#shop` to select tenant records, sessions, or scoped data (as `docs`/host apps are told to do) can be made to attribute one shop's webhook payload to another shop, i.e., cross-tenant access, matching the report's "Critical" cross-tenant category.

### Likelihood Explanation
Exploitation requires the attacker to control or influence the raw HTTP headers reaching `ShopifyAPI::Webhooks::Request.new` (e.g., a proxy, a shared/misconfigured webhook endpoint, or any component that forwards a validly HMAC'd body from Shopify but with attacker-modifiable headers) while the body's HMAC still validates against the app's own secret — this is plausible for apps that terminate webhook headers via infrastructure not fully controlled end-to-end, or via naive body-forwarding/replay from a legitimate shop’s previously-received webhook to a shared handler. It does not require the `client_secret` itself, only the ability to supply headers alongside an already-validly-signed body.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC signable string (or otherwise cryptographically bind them, e.g., derive `shop` only from a value verified against the stored session/webhook registration rather than trusting the header), so `HmacValidator.validate` actually authenticates the tenant-identifying fields, not just the body bytes.

### Proof of Concept
1. Attacker captures a legitimately Shopify-signed webhook body+HMAC delivered for `victim-shop.myshopify.com` (e.g., via a shared proxy/load balancer that lets header values be attacker-influenced, or a component that re-emits webhook bodies).
2. Attacker resends the same raw body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. `Request.new` accepts it (all required headers present) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC [6](#0-5) .
5. `handler.handle` receives `WebhookMetadata` with `shop: "attacker-shop.myshopify.com"` even though the payload is really `victim-shop`'s data, causing the app to process/store victim data under the attacker's tenant record.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
