### Title
Unbounded ancestry-chain walk lets a crafted GRANDPA consensus/fraud proof drive `AncestryChain::ancestry` into an infinite loop - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks parent-hash pointers taken directly from attacker-supplied `unknown_headers` until it reaches a trusted `base` hash, with no visited-set/step bound. Because the header set (and every header's `parent_hash` field) is fully attacker-controlled input to `verify_grandpa_finality_proof`, an attacker can submit two or more headers whose `parent_hash` fields point at each other, forming a cycle that never resolves to `base`. This is directly analogous to CVE-2018-16789: a crafted, structurally-valid-looking input drives a parsing/traversal loop into never terminating, exhausting CPU.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The loop only terminates when `current_hash == base` or when the next hash is *absent* from the map. The map (`self.ancestry`) is built directly from `finality_proof.unknown_headers`, an attacker-controlled `Vec<H>` decoded from the wire message: [2](#0-1) 

Each header's key is its own computed hash, but its `parent_hash` field is arbitrary attacker data. An attacker can submit two headers A and B where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`. Both A and B are present in the map, so the lookup always succeeds and `current_hash` will oscillate forever between `hash(A)` and `hash(B)`, never equalling `base` and never hitting the `None` branch that would return `NotDescendent`.

This function is invoked by `verify_grandpa_finality_proof`, which is the primary entry point for verifying an incoming GRANDPA `ConsensusMessage` (not just fraud proofs): [3](#0-2) 

Critically, the ancestry walk (`headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())`) executes **before** `justification.verify(...)` (the actual signature check): [4](#0-3) 

This means an attacker does not need a valid GRANDPA justification/signature at all — only crafted `unknown_headers` satisfying two cheap checks (`target.hash() == finality_proof.block` and `justification.commit.target_hash == finality_proof.block`, which just requires decoding a syntactically valid justification struct, not a verified one) to reach the vulnerable loop.

The call chain from an unprivileged submitter is:
`pallet_ismp::Pallet::handle_unsigned` (unsigned extrinsic, `ensure_none`) → `execute` → `handle_incoming_message` → `GrandpaConsensusClient::verify_consensus` → `verify_parachain_headers_with_grandpa_finality_proof` / directly → `verify_grandpa_finality_proof` → `AncestryChain::ancestry`: [5](#0-4) [6](#0-5) 

Because `handle_unsigned` is validated via `ValidateUnsigned::validate_unsigned`, which itself calls `Self::execute(messages.clone())` to check validity before admission to the transaction pool: [7](#0-6) 

...the infinite loop is triggered during **transaction-pool validation**, on every full node/validator that receives the gossip'd unsigned extrinsic — before it is even included in a block. This is a network-wide DoS vector, not merely an extrinsic-execution one.

The same primitive is reused verbatim by the fraud-proof path in `modules/ismp/clients/grandpa/src/consensus.rs::verify_fraud_proof` (lines 309-320), giving a second, equally reachable trigger.

### Impact Explanation
An unbounded loop with no step counter, visited-set, or weight-metered yield point means a single malicious (or even accidentally malformed) unsigned message can hang the WASM execution of every node that attempts to validate or execute it. Since Substrate FRAME extrinsics are not instruction-metered (weight is charged based on declared/benchmarked weight, not actual instruction count), this loop will not be pre-empted by the block weight limit — it can consume CPU indefinitely, i.e. an unresponsive/stalled node, which for a validator amounts to denial of service and can stall block production or network liveness for the state machine relying on GRANDPA finality (a "route unable to deliver messages" condition per the validation criteria).

### Likelihood Explanation
High. The trigger requires only:
1. Two synthetic headers with cross-referencing `parent_hash` fields (trivial to construct off-chain; the header type/hash algorithm is public).
2. `target.hash() == finality_proof.block` (attacker sets `finality_proof.block` to match a header they created).
3. A syntactically decodable `GrandpaJustification` (no valid signatures needed since the walk runs before signature verification).

No signature, no funds, no special privilege, and no valid consensus state advance is needed — this is submittable by literally any party as an unsigned `Message::Consensus` via `handle_unsigned`, which is explicitly designed to be free/unsigned/permissionless.

### Recommendation
Bound the `ancestry` walk with an explicit step limit (e.g., equal to `self.ancestry.len()` or `MAX_PROOF_DEPTH`-style constant) and/or maintain a visited-hash set, returning `NotDescendent`/an error once the limit is exceeded or a hash is revisited. Additionally, consider validating `unknown_headers` forms a strictly monotonically-decreasing-by-number chain from `target` down to `base` before doing hash-pointer chasing, and/or moving signature verification (`justification.verify`) before any ancestry traversal so malformed proofs are rejected cheaply first.

### Proof of Concept
1. Construct two `SubstrateHeader` (or `DefaultHeader`) values, A and B, with arbitrary/zero state roots, but:
   - `A.parent_hash = B.hash()`
   - `B.parent_hash = A.hash()`
2. Set `finality_proof.unknown_headers = vec![A, B]`, `finality_proof.block = A.hash()` (so `target = A`, satisfying `target.hash() == finality_proof.block`).
3. Set `finality_proof.justification` to any SCALE-encodable `GrandpaJustification` whose `commit.target_hash == A.hash()` (does not need valid signatures — only `Decode` needs to succeed at this stage).
4. Ensure `base = min_by_key(number)` resolves to B (or A) so that `base.number() < consensus_state.latest_height` triggers the `headers.ancestry(base.hash(), consensus_state.latest_hash)` call, or simply rely on the subsequent `headers.ancestry(from, target.hash())` call where `from = consensus_state.latest_hash` differs from both A and B's hashes.
5. Wrap this in a `ConsensusMessage::Polkadot`/relay-chain finality-proof envelope and submit as `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(...)] }` via an unsigned extrinsic.
6. Any node validating this extrinsic (via `ValidateUnsigned::validate_unsigned`) invokes `AncestryChain::ancestry`, which loops forever between A and B's hashes, hanging that node's execution thread.

Note: I could not fully trace whether `unknown_headers` is size-bounded at the SCALE-decode/extrinsic layer (e.g., via a `BoundedVec`) in every code path (the type shown, `Vec<H>`, appears unbounded at the primitive level), but this is immaterial to the vulnerability since only two headers are needed to form the cycle.
