### Title
Escrowed funds can be permanently frozen when a beneficiary's address is blocklisted by the escrowed token - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (used by both the `ExtrinsicIntents`/`IntentGatewayV2` cross-chain settlement path) transfers escrowed input tokens directly to a `beneficiary` address taken from an on-chain `WithdrawalRequest` (either the filling solver or the order's `user`), with no fallback if that transfer reverts. Because `EvmHost.dispatchIncoming` treats any reverting `onAccept` call as "retryable" rather than reverting the whole batch, a permanently-reverting transfer (e.g. a USDC/USDT blocklisted address) leaves the escrow forever undeliverable, with no way to change the beneficiary or otherwise recover the funds.

### Finding Description
`_withdraw` in `IntentsBase.sol` resolves the beneficiary from the message body and unconditionally calls `IERC20.safeTransfer(beneficiary, amount)` for each escrowed token: [1](#0-0) 

The same pattern (`token.call(...transfer...)`, reverting the whole call on failure) exists in the Tron variant's `withdraw`: [2](#0-1) 

The beneficiary is untrusted, cross-chain-controlled data: for a `RedeemEscrow` message it is the solver address that filled the order on the destination chain, and for a `RefundEscrow`/GET-response cancellation it is `order.user`: [3](#0-2) [4](#0-3) 

If a USDC/USDT-style token blocklists that beneficiary address (or the token is paused) after the order was placed/filled, every subsequent `safeTransfer` call reverts. Delivery of this settlement message goes through `EvmHost.dispatchIncoming`, which does not propagate the revert to the whole batch — it just deletes the request receipt and returns so the message can be "retried": [5](#0-4) 

But retrying delivers the exact same immutable `WithdrawalRequest.beneficiary`, so the transfer fails identically every time. There is no function anywhere in `IntentsBase`/`IntentGatewayV2`/`ExtrinsicIntents` that lets a beneficiary update their receiving address, and no admin/governance "sweep" path exists for a specific order's escrow — `SweepDust`/`sweepDust` only operates on protocol-owned dust, not on a live order's `_orders[commitment][token]` balance: [6](#0-5) 

This is the direct analog of the Sherlock finding against `QVBaseStrategy::_distribute`, where a blocklisted `recipient.recipientAddress` permanently traps payout funds with no recipient-address-update function and no manager withdraw path for that stuck balance.

### Impact Explanation
The escrowed input tokens (`_orders[commitment][token]`) become permanently unreachable: they cannot be delivered to the intended beneficiary (transfer always reverts), cannot be redirected (no beneficiary-update function), and cannot be swept by governance (sweep only targets protocol dust, not order escrow). This is a genuine freezing of user/solver funds reachable from a single relayed cross-chain settlement message, satisfying the "permanent freezing of funds" bar. Impact scope is limited to the specific order(s) whose beneficiary becomes blocklisted/paused on the relevant token, which is consistent with Medium severity.

### Likelihood Explanation
Likelihood is not attacker-controlled in the sense of an active exploit, but it is a realistic operational condition: escrowed input tokens are frequently stablecoins (USDC/USDT) with centralized blocklist authority, and solvers/users interacting with regulated stablecoins can be sanctioned or blocklisted between order placement/fill and settlement delivery. Since the beneficiary is fixed at message-construction time and cannot be updated, any blocklisting event occurring before final delivery is sufficient to trigger permanent freezing — no cooperation from a malicious actor is required.

### Recommendation
- Wrap per-token transfers in `_withdraw` (and the Tron `withdraw`) in a try/catch (or low-level call check) so that a failing transfer for one token does not need to abort the whole settlement, and/or fall back to crediting an internal, separately claimable balance for that beneficiary/token pair instead of a direct push transfer.
- Add a recovery mechanism (e.g., a permissioned or beneficiary-signed function) allowing the stuck balance to be redirected to an alternate address, or allow governance to sweep a specific order's escrow to a designated address after some grace period, analogous to `RFPSimpleStrategy`/`DonationVotingMerkleDistributionBaseStrategy`'s `withdraw()` functions referenced in the source report.
- Consider switching from push-transfers to a pull-based claim pattern for `_withdraw`, so a blocklisted address cannot block finalization state changes (`_filled[commitment]`) from occurring.

### Proof of Concept
1. User places a cross-chain order on the source chain escrowing USDC as `order.inputs`, with a solver expected to fill on the destination chain.
2. Solver fills the order on the destination chain (`fillOrder`), and the destination gateway dispatches a `RedeemEscrow` `WithdrawalRequest{beneficiary: solverAddress, tokens: order.inputs}` back to the source chain (see `ExtrinsicIntents.sol` `_cancelFromDest`/fill-path construction and `onAccept` RedeemEscrow handling, lines 297-337).
3. Before the relayer delivers this message, Circle blocklists `solverAddress` on USDC (or the solver's address gets sanctioned for any other reason).
4. A relayer calls `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IntentGatewayV2/ExtrinsicIntents.onAccept` → `_withdraw`, which calls `IERC20(usdc).safeTransfer(solverAddress, amount)`; this reverts due to the blocklist.
5. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and returns without reverting the batch, per lines 794-818, marking the message as "retryable."
6. Every subsequent retry re-decodes the same fixed `beneficiary = solverAddress` and reverts identically — the escrowed USDC in `_orders[commitment][usdc]` is now permanently unreachable, with no beneficiary-update or per-order sweep function anywhere in the contract to recover it.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
