Based on my investigation, I found a genuine identity-binding gap in the webhook HMAC verification path.

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) attribution is not covered by the HMAC signature, allowing shop/topic spoofing on a validly-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` uses the HMAC check to prove the request is legitimate, then trusts `request.shop` as the tenant identity for dispatching to the registered handler, without that value ever being part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is extracted from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers with no relation to the signed bytes: [3](#0-2) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. only the body bytes are checked; the `shop` header used later for tenant dispatch is never part of what is verified: [4](#0-3) [5](#0-4) 

This is the exact "field acted on but not covered by the HMAC" bug class named in the rules: the identity binding that should hold is `shop header == shop bound into the signed bytes`, but the gem only enforces `hmac(raw_body) == received_hmac`.

### Impact Explanation
Any component upstream of this gem that terminates TLS and forwards the request to the app (a shared reverse proxy, a load balancer, a misconfigured multi-tenant ingress, or any code path that re-emits the same body with attacker-influenced headers) can cause the same, validly HMAC-signed webhook body to be attributed to a different `shop-domain` than the one that actually produced it. Because `Registry.process` trusts `request.shop`/`request.topic` for dispatch after only checking the body HMAC, this can result in cross-tenant data being routed to the wrong shop's webhook handler logic, or a shop's legitimate webhook being reprocessed under a different topic/api_version pairing without failing signature verification. This satisfies the "cross-tenant access" bar via a broken identity binding, since the tenant-identifying field is completely outside the cryptographic proof the gem relies on.

### Likelihood Explanation
Likelihood is bounded by the fact that an unprivileged internet attacker cannot forge the HMAC itself (that still requires the `client_secret`); the exposure only materializes when something between Shopify and the final `Request.new` call (proxy, gateway, queue, internal relay) can be induced to alter or duplicate headers independent of the signed body — a realistic scenario in the kind of multi-shop/multi-tenant deployments this gem explicitly targets (it accepts a `shop` header/`SessionRepository`-style multi-tenant pattern throughout `docs/`). It is not exploitable purely over the open internet without such an intermediary, so it is best framed as a design gap rather than a directly remotely-exploitable bug on its own.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the value that is cryptographically checked — e.g., require callers to pass the header values into `to_signable_string` alongside the raw body (mirroring how `Oauth::AuthQuery#to_signable_string` composes multiple fields), or document/enforce that consumers must independently verify `shop-domain` against a known/expected value obtained through a channel outside these headers before using it for tenant dispatch.

### Proof of Concept
1. Capture a legitimate Shopify webhook: body `B`, header `x-shopify-hmac-sha256: H`, header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay the same `B`/`H` pair with `x-shopify-shop-domain: shop-b.myshopify.com` through any component that can rewrite headers but preserve the body untouched.
3. `ShopifyAPI::Utils::HmacValidator.validate` still succeeds (it only checks `B` against `H`), and `Registry.process` dispatches the handler as if the webhook came from `shop-b`, using `request.shop` at [6](#0-5) 
as the trusted tenant identity.
