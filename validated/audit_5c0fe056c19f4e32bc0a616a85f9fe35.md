Confirmed: `begin_auth` never sanitizes/validates `shop` before it's embedded in the authorize URL, unlike the other OAuth flows that call `Utils::ShopValidator.sanitize!`.

### Title
Unsanitized `shop` in `Oauth.begin_auth` allows authorize-URL injection via `auth_base_uri` string interpolation - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorize URL by raw string interpolation of the caller-supplied `shop` value (`"https://#{shop}/admin"` in `auth_base_uri`), with no call to `Utils::ShopValidator.sanitize!`, unlike `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, which all validate `shop` before use. Since the documented integration pattern (`docs/usage/oauth.md:182`) takes `shop` directly from an attacker-controllable request header, a value like `attacker.com/oauth/authorize?client_id=x#` breaks the intended URL structure and can inject extra path/query into the final `auth_route`.

### Finding Description
Binding under test: `auth_base_uri(shop) == "https://{trusted Shopify domain}/admin"`. In practice this binding is broken because `auth_base_uri` performs no validation:

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [1](#0-0) 

`begin_auth` then concatenates this with an encoded query string:
```ruby
query_string = URI.encode_www_form(query)
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
``` [2](#0-1) 

No call to `Utils::ShopValidator.sanitize!` exists anywhere in `begin_auth` or `auth_base_uri` — `grep_search` for `sanitize!` across the repo shows it used only in `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/auth/token_exchange.rb`, not `oauth.rb`. `Utils::ShopValidator.sanitize!` (`lib/shopify_api/utils/shop_validator.rb:56-64`) is exactly the guard that would reject a non-Shopify-domain `shop` string, raising `Errors::InvalidShopError` for anything outside `TRUSTED_SHOPIFY_DOMAINS`.

Attacker request: per the gem's own documented usage pattern, a host app reads `shop = request.headers["Shop"]` and passes it straight to `begin_auth(shop: shop, redirect_path: ...)` (`docs/usage/oauth.md:182,185`). An attacker sends `Shop: attacker.com/oauth/authorize?client_id=stolen&state=x#` (or similar). Because `auth_base_uri` does `"https://#{shop}/admin"` with no encoding, the resulting `auth_route` is `https://attacker.com/oauth/authorize?client_id=stolen&state=x#/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=...`. Note that `#` truncates everything after it when the URL is actually navigated to in a browser (fragment), so the legitimate `redirect_uri`/`state`/`scope` query parameters after the `#` are dropped client-side and never sent to Shopify — instead the browser is sent to `attacker.com`'s own crafted query string.

However, evaluate the actual security boundary: this app-controlled `auth_route` is a URL the *app itself* returns to *its own* server-side controller, which then 307-redirects the *merchant's browser*. The victim being redirected is the merchant admin visiting their own app's login route, not a third party who didn't initiate anything. The state cookie set alongside it (`SessionCookie` with the correct random `state` nonce) is still set on the app's own domain, and `validate_auth_callback` still requires `state == auth_query.state` sourced from that cookie plus a valid Shopify HMAC (`Utils::HmacValidator.validate`) on the callback — those checks are unaffected by this bug since they don't depend on `auth_base_uri`. This finding is therefore a real defect (missing input validation compared to sibling flows) but the "attacker action" as framed requires the attacker to control the `Shop` header for a *victim's* browser session directed at the *app's own* login endpoint — i.e., the attacker must get the victim to visit `myapp.com/login?...` with an attacker-chosen `Shop` header (which browsers don't let a remote attacker set on someone else's request — headers are set by the browser/app, not by the remote page, unless the app itself sources `shop` from a query parameter under attacker control, e.g. reflected in a link the victim clicks). This is the standard "open redirect via missing shop-domain validation" pattern, which is a known, real weakness, but it takes the merchant themselves navigating to an attacker-supplied link/parameter — this is attacker-initiated but victim-driven navigation, consistent with the threat model (attacker controls params/headers of a request they can get delivered).

### Impact Explanation
If the app takes `shop` from a query/header value reachable by a link the attacker gets a merchant to click, the app's OAuth redirect can be steered to leak `client_id` and constructed `scope`/`redirect_uri`/`state` query components to an attacker-controlled host, and — since browsers treat `#` as a fragment — the real Shopify authorize parameters after it never reach Shopify, letting the attacker's page harvest the `state` nonce and, on a phishing page mimicking Shopify's consent screen, capture whatever the merchant enters or observes. This does not by itself steal an existing access token or bypass `validate_auth_callback`'s HMAC/state checks (which still function correctly on the app's genuine callback path); it is a scope/redirect confusion in the *outbound* leg of the flow, matching a High severity (SSRF/open-redirect-style forced-redirection issue) rather than a full Critical authentication bypass, since no forged webhook/callback/session token is accepted and no token or `client_secret` is exfiltrated through this path alone.

### Likelihood Explanation
Requires the host app to source `shop` for `begin_auth` from attacker-influenced input (query param or header) exactly as the gem's own docs recommend, and requires the attacker to deliver a crafted `shop` value to a victim merchant (e.g., via a phishing link to the app's login route with `?shop=attacker.com/oauth/authorize?...#`). No secrets are needed; cost is a single crafted URL. This is repeatable against any merchant who clicks the link, but not exploitable against an already-authenticated session or without victim interaction.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or equivalent trusted-domain validation) at the top of `Oauth.begin_auth`, before it is passed into `auth_base_uri`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, and reject/raise `Errors::InvalidShopError` for any `shop` value that doesn't resolve to a trusted `*.myshopify.com`/trusted domain.

### Proof of Concept
In `test/auth/oauth_test.rb`, add:
```ruby
def test_begin_auth_rejects_non_shopify_shop_domain
  malicious_shop = "attacker.com/oauth/authorize?client_id=stolen&state=x#"
  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/auth/callback")
  end
end

def test_begin_auth_current_behaviour_leaks_attacker_host_in_auth_route
  malicious_shop = "attacker.com/oauth/authorize?client_id=stolen&state=x#"
  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/auth/callback")
  refute_match(/\Ahttps:\/\/[^\/]*\.myshopify\.com\/admin\/oauth\/authorize/, result[:auth_route])
  assert_match(/\Ahttps:\/\/attacker\.com\/oauth\/authorize\?client_id=stolen&state=x#/, result[:auth_route])
end
```
The first test documents the desired fixed behavior (raising `InvalidShopError` as sibling flows do); the second demonstrates the current unpatched behavior where `auth_route` starts with the attacker's host/query/fragment instead of a trusted `myshopify.com` domain, proving the missing `sanitize!` call in `lib/shopify_api/auth/oauth.rb` lets unsanitized `shop` break the intended authorize-URL structure.
