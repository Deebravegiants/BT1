## Analysis

The CVE (CVE-2025-50084) is an Oracle MySQL **Optimizer** bug that lets an authenticated but unprivileged-relative-to-data attacker trigger a **hang/crash (complete DoS)** of the server through ordinary, protocol-level operations — no data corruption, purely an availability failure caused by the optimizer's internal math/state assumptions being violated. The closest analog in alt.fun's own code is a math/state-invariant break in the bonding-curve AMM that permanently disables one of the two graduation triggers, freezing curve funds instead of crashing a process.

### Title
Direct token donation to a curve `Pair` permanently disables the supply-exhaustion graduation trigger, freezing creator/LP funds - (File: packages/contracts/src/Router.sol, packages/contracts/src/Bonding.sol)

### Summary
`Bonding.canGraduate` relies on two triggers: a USD-value trigger and a supply trigger `IPair.tokenBalance() == 0` [1](#0-0) . The supply trigger is only reachable because the pair maintains the invariant `tokenBalance() < tokenReserve` (real balance strictly below the virtual reserve) throughout normal trading, which is what lets `Router._computeBuy`'s overflow cap eventually drive the real balance to exactly zero [2](#0-1) . Any unprivileged holder can break that invariant with a plain `IERC20.transfer` of the launched `Token` directly to the `Pair`, inflating `tokenBalance()` up toward (or beyond) `reserveToken`. Once `tokenBalance() >= reserveToken`, the AMM math (`tokensOut = reserveToken - k/newReserveAsset`, which is mathematically always `< reserveToken`) can never drive the live balance to exactly `0` again — the supply trigger becomes permanently unreachable for that token, no matter how many buys follow.

### Finding Description
`Router._computeBuy` caps a buy's output at the pair's live `tokenBalance()` and back-computes `amountInUsed`, relying on the documented invariant that `tokenBalance() < tokenReserve` always holds during curve trading [2](#0-1) . The team's own test explicitly frames this as a property that "makes the `cappedReserveToken == 0` branch in `Router._computeBuy` unreachable; if it ever ceased to hold, that branch would revert...” [3](#0-2) .

That invariant holds only because buys decrease `tokenReserve` and `tokenBalance` by the identical `tokensOut` each time (`Pair.swap`), keeping the gap between them fixed at `LP_RESERVE` (250M) [4](#0-3) . Nothing prevents an unrelated address from directly `transfer`-ing the freely-tradable launched `Token` to the `Pair` address — a plain ERC20 transfer that bypasses `Router`/`Bonding` entirely and only *increases* `tokenBalance()` while leaving the stored `tokenReserve` untouched. If an attacker accumulates and donates enough tokens (up to the ~250M gap) to make `tokenBalance() >= tokenReserve`, then for every future buy `tokensOut = reserveToken - k/newReserveAsset` is provably `< reserveToken <= tokenBalance()`, so the overflow-cap branch in `_computeBuy` can never fire and `tokenBalance()` can never again reach exactly `0`.

`Bonding.canGraduate`'s supply leg, `IPair(pair).tokenBalance() == 0` [5](#0-4) , is thereby permanently disabled for that token. The protocol's own documentation describes this leg as the safety net "for flat/bear markets where $9K is never reached" [6](#0-5)  and explicitly frames donations as merely making the trigger "donation-resistant" in a way that can only delay it, not permanently kill it [6](#0-5)  — the actual math shows a sufficiently large donation makes the condition unreachable outright, not merely delayed. If the USD trigger is also never crossed for that token (low-volume/flat token, or a token deliberately targeted by the attacker before real trading volume builds), the token can never graduate: the creator's 250M `lpReserve` tokens and all curve-raised LT stay parked in `Bonding`/`Pair` forever, since `_enterGraduating`/`finalizeGraduation` are only reachable through `canGraduate` returning true [7](#0-6) .

### Impact Explanation
This permanently freezes the creator's LP allocation and the curve's raised LT reserve for the targeted token — no code path other than the two graduation triggers ever moves those funds out of `Bonding`/`Pair` into `LPLock`. This is a concrete, permanent freezing of creator/LP funds reachable purely from an unprivileged wallet's own token holdings and a plain ERC20 transfer, matching the accepted impact classes (permanent freezing of creator or LP funds).

### Likelihood Explanation
The action requires only tokens the attacker already legitimately owns (bought via the normal curve `Zap.buy`/`Bonding.buy` path) and a direct `IERC20.transfer` to the `Pair` address — both are explicitly in-scope, unprivileged actions per the analog rules. The attacker must accumulate close to the `LP_RESERVE` gap (up to 250M tokens, priced by the curve — cheapest near launch), which is a real cost but not privileged access; it is economically comparable to (or cheaper than) the $9K USD graduation threshold since it can be executed with tokens bought at the lowest point of the curve. It is most attractive against low-liquidity/abandoned tokens the attacker wants to permanently strand (e.g., to trap a competitor's launch or to lock in a favorable curve price forever without DEX competition).

### Recommendation
Do not trust a live `balanceOf` read for the supply trigger; use a value that can only move via `Router`/`Pair.swap` (e.g., track cumulative `tokensOut` sold via curve state, or compare against `tokenReserve - LP_RESERVE` derived purely from swap-updated state) so direct donations cannot influence graduation reachability. Alternatively, skim/burn unsolicited token donations to the pair before they affect `tokenBalance()`, or gate the supply check on `reserveToken` (swap-driven) reaching its terminal value rather than the raw ERC20 balance.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }

    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
