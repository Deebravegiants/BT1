### Title
Webhook `shop` (and `topic`) identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (and `topic`) values used downstream to identify which tenant the webhook belongs to are read from HTTP headers that are **not** included in the signed payload, so they can be freely substituted by anyone who possesses a validly-signed body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are pulled from separate, unsigned headers: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which — via `VerifiableQuery` — only checks `hmac` against `to_signable_string` (the raw body): [3](#0-2) [4](#0-3) 

Because the HMAC secret is the app's `client_secret`, which is identical for **every** shop that installs the app, any unprivileged user can install the app on their own store, receive a validly-signed webhook (valid HMAC over some body), and then replay that exact body to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to a victim shop's domain. `Registry.process` never checks that the `shop` header corresponds to a shop that actually owns that body/signature — it only checks the HMAC of the body, then forwards `request.shop` verbatim into `WebhookMetadata`: [5](#0-4) 

This breaks the intended identity binding: `hmac(raw_body, client_secret) == valid` should imply `shop header == the shop that generated this body`, but the gem only proves the former, not the latter. The library's own documentation shows the natural (and vulnerable) usage pattern where `data.shop` is trusted directly for tenant routing/persistence: [6](#0-5) 

This is the direct analog of the referenced bug class: a field (`shop`) that is *acted upon* (used to route/attribute data to a tenant) is not covered by the authentication primitive (`hmac`) that is supposed to bind it.

### Impact Explanation
An unprivileged attacker who legitimately installs the app on their own (attacker-controlled) shop can obtain arbitrarily many validly-HMAC-signed webhook bodies for known topics (e.g. `customers/create`, `orders/create` with attacker-chosen content), then replay them against the app's webhook endpoint with the `shop-domain` header changed to any victim shop that also uses the app. Any host application that follows this gem's documented pattern (trusting `WebhookMetadata#shop` for tenant attribution, as literally shown in this gem's own docs) will process attacker-controlled data as if it originated from the victim tenant — a cross-tenant data injection / attribution bypass. This matches the Critical "cross-tenant access" impact category, since the shop identity boundary is defeated using only a self-service app install (no privileged credentials, TLS interception, or social engineering required).

### Likelihood Explanation
High. Installing an app in a development/trial store is available to any internet user, and capturing a legitimate signed webhook (or triggering one, e.g. by creating a customer/order on your own store) requires no special access. Replaying the body with a modified header is trivial HTTP tooling. The vulnerable pattern (`data.shop` trusted for routing) is exactly what this gem's own documentation instructs developers to do.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) claim to the HMAC-verified payload rather than trusting an unauthenticated header. Concretely:
- Include the `shop`, `topic`, and `webhook_id` header values in the string that is HMAC-verified (mirroring how `AuthQuery#to_signable_string` binds `shop`/`host` into its signed string), or
- Have `Registry.process` cross-check `request.shop` against a shop that the app has an active webhook registration/session for, rejecting webhooks for shops that are not expected recipients of that specific signed body, and clearly document that host apps must not use the `shop` header from `WebhookMetadata` as an unauthenticated tenant identifier without such a check.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, obtaining the ability to trigger legitimate webhooks (app's `client_secret` is shared across all installs, so HMACs are portable across shops).
2. Attacker triggers/creates a webhook payload (e.g. `orders/create`) on their own store and captures the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(B, client_secret)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds successfully; `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(B, secret) == H`, per [4](#0-3) .
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)`, per [7](#0-6) , and any app following this gem's documented pattern persists/attributes attacker-controlled data to the victim tenant.
