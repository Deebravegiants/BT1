### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identifier) is read from an unsigned header. `Registry.process` verifies only that the body's HMAC is valid, then hands the caller's handler the unauthenticated `shop` value as the tenant to act on. This breaks the invariant `verified_bytes == acted_on_bytes`: the field the host application uses to select/attribute a merchant (`shop`) is not part of what the HMAC actually authenticates.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in that signable string: [2](#0-1) 

`HmacValidator.validate` only checks `hmac == HMAC(secret, to_signable_string)`, i.e. it authenticates the body bytes, not the shop header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unsigned header) as the tenant identifier passed to the app's handler: [4](#0-3) 

This is structurally the same defect pattern as the referenced report: an amount/field is mutated/used (there: `margin_amount`; here: the tenant-binding `shop`) without updating/including it in the authoritative, verified record (there: `self.margin[...]` mapping; here: the HMAC-signed payload). The equality that should hold is:

`shop_used_by_handler == shop_bound_by_hmac(raw_body)`

but in fact `shop_used_by_handler` is read from a header entirely outside the HMAC's scope, so the equality never holds — any value can be placed in that header and it will pass validation as long as the body's HMAC matches for *some* accepted request.

Because Shopify apps use a single `api_secret_key` shared across all installed shops (not a per-shop secret), any HMAC-valid webhook body (e.g. one legitimately delivered for the attacker's own installed shop, or one captured via a dev tunnel/log) retains a valid HMAC even if the `shop-domain` header is changed to a different, victim shop. `Registry.process` will accept it and invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
An unprivileged user who has installed the app on their own shop can obtain a validly-HMAC'd webhook payload (Shopify sends these to the app's public endpoint), then replay it with the `shopify-shop-domain` header rewritten to point at a different merchant's shop domain. Because the gem does not bind `shop` into the authenticated content, the forged request passes `HmacValidator.validate` and is dispatched to the handler as if it originated from the victim shop, with attacker-controlled body content attributed to that victim tenant. Any host application that uses `WebhookMetadata#shop` (as documented/intended by this gem) to look up the merchant's session, update per-shop data, or trigger per-shop side effects will process attacker data under a different tenant's identity — a cross-tenant integrity/confusion issue rooted entirely in this gem's verification logic.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as any legitimate low-privilege merchant to receive a genuine webhook (or otherwise obtaining a webhook body/HMAC pair), and (2) resending it to the same public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, tokens, or the target shop is required — only network access to replay an HTTP request with different headers, which is exactly the "unprivileged internet user" capability in scope.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-verified signable content, or otherwise cryptographically bind them to the payload, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{@raw_body}"
end
```
This requires computing the signature server-side over the same composite string when Shopify signs it — since Shopify's actual HMAC only covers the raw body by protocol design, the correct mitigation within the gem is instead to document/require host applications to authenticate the `shop` header via a side channel (e.g. verifying it against a shop already known to have valid installation/session state) rather than trusting the header value alone, or to expose a `Request` API that explicitly warns callers that `shop` is unauthenticated relative to the HMAC.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers any webhook topic they control (e.g., updates a product), causing Shopify to POST a validly HMAC-signed webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid hmac over raw_body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: products/update`
2. Attacker captures this raw request (own traffic, no special access needed).
3. Attacker resends the identical body and HMAC header to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`@raw_body` only) — unaffected by the header change — and passes: [5](#0-4) 
5. The handler receives `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload/HMAC never involved that shop, demonstrating the tenant-binding break.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
