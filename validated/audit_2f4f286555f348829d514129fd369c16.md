## Analysis

I looked for an unprivileged-user analog to the "arbitrary receiver address" class of bug (accepting an unauthenticated identifier and using it to perform privileged/costly actions attributed to someone else) in the QR-parsing / signup-authorization code paths of `orb-core`.

### Title
Legacy "V2" user QR-code format allows signup/enrollment to be initiated for an arbitrary, unauthenticated user ID — ([File: src/plans/qr_scan/user.rs])

### Summary
The user QR-code parser accepts a legacy plaintext format (`userid:<uuid>:<data_policy>`) that carries no cryptographic binding between the QR-code contents and its holder. Anyone who can read or reproduce this string (it is not a secret — it can be photographed, screen-captured, or otherwise copied) can present it to an Orb, and the code will drive the entire signup/enrollment flow — including uploading biometric imagery/personal-custody-package data — under that victim's `user_id`, without any proof of possession or consent from the actual account owner.

### Finding Description
`qr_scan::user::Data::try_parse` first attempts `orb_qr_link::decode_qr` (the newer format, which embeds a `user_data_hash`), but falls back to the plain `QR_CODE_V2` regex which only captures `user_id` and `data_policy` with no hash/signature material: [1](#0-0) [2](#0-1) 

Downstream, `backend::user_status::request` validates the code against the backend, but when the backend does not return `authenticated_app_data`/`backend_keys` (i.e., the "old QR-code format" branch), it does not require or check any `user_data_hash` at all and returns a valid `UserData` unconditionally as long as `qr_code.user_data_hash` is `None`: [3](#0-2) 

This validated `user_qr_code.user_id` is then used directly to run the full signup pipeline — signature/upload requests, polling, and personal-custody-package upload — all tagged with that `user_id`: [4](#0-3) [5](#0-4) [6](#0-5) 

The structural parallel to the flash-loan report is direct: in the reported bug, `LendingPool.flashLoan` accepts an arbitrary `receiverAddress` and performs a privileged, fee-incurring action attributed to that address without proof the caller controls it. Here, the legacy QR path accepts an arbitrary `user_id` string with no proof-of-possession and performs a privileged, resource-consuming action (biometric signup, PCP upload, consumption of the user's one signup slot) attributed to that identifier.

### Impact Explanation
An attacker who obtains a victim's plaintext V2 QR-code string (e.g., by photographing it during display, or via any other channel where the string leaks) can walk up to an Orb and force a full biometric enrollment/signup flow to be executed and reported to the backend under the victim's identity — without the victim's knowledge or physical presence. This can (a) consume/burn the victim's legitimate signup opportunity (denial of service on the victim's account, mirroring the "griefing" impact in the original report), and (b) result in personal-custody-package/biometric material from an unrelated capture session being bound to the victim's `user_id` on the backend — a cross-signup identity-binding/misattribution issue.

### Likelihood Explanation
Likelihood depends on the legacy V2 format still being accepted in production and on how easily a QR string can be captured/replayed outside its intended single presentation (it is fundamentally a bearer string with no signature, unlike the newer `decode_qr` format that binds a `user_data_hash`). Because `try_parse` unconditionally tries the V2 regex as a fallback with no feature gate, this path is reachable in normal operation, not just in a test-only build.

### Recommendation
Retire or gate the unauthenticated legacy V2 QR format behind a deprecation/removal plan, and require every user QR-code to carry a cryptographically verifiable binding (as already done for the `decode_qr`/`user_data_hash` path) before it is accepted as proof of the presenting user's identity for any signup/enrollment action.

### Proof of Concept
1. Obtain a victim's legacy-format user QR-code string, e.g. `userid:<victim-uuid>:<policy>` (via photograph, shared screenshot, or any leak channel).
2. Present this string to any Orb (or supply it via the `user_qr_code` override path used in `scan_user_qr_code`) as the scanned user QR-code.
3. `verify_user_qr_code` → `backend::user_status::request` validates it via the "old QR-code format" branch (no hash check) and returns `Ok(Some(UserData{ .. }))`.
4. The enrollment plan proceeds to call `signup_post::request` and `upload_pcp_tier_0` using the victim's `user_id`, completing a full signup attributed to the victim under attacker control.

    fn try_parse(code: &str) -> Option<Self> {
        if let Ok((user_id, user_data_hash)) = decode_qr(code) {
            return Some(Self {
                user_id: user_id.hyphenated().to_string(),
                signup_extension: false,
                signup_extension_config: None,
                user_data_hash: Some(user_data_hash),
            });
        }
        if let Some(captures) = QR_CODE_V2.captures(code) {
            return Some(Data::from_v2(&captures));
        }
        #[cfg(feature = "internal-data-acquisition")]
        if let Some(captures) = QR_CODE_SIGNUP_EXTENSION.captures(code) {
            return Some(Data::from_signup_extension(&captures));
        }
        None
    }
