## Title
Webhook Shop Identity Spoofing via HMAC Coverage Gap - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` never covers the `X-Shopify-Shop-Domain` header. `Webhooks::Registry.process` nevertheless trusts `request.shop` (parsed straight from that header) and hands it to the app's webhook handler as the authoritative tenant identity. Any party that can obtain one validly-signed webhook body (e.g. by installing the app on their own store) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the forged shop value will pass verification and be delivered to the handler as trusted.

### Finding Description
The webhook HMAC binding should enforce: `hmac == HMAC(secret, body || shop)`, i.e. the shop identity acted upon by the handler must be the same bytes that were authenticated. Instead:

- `to_signable_string` only serializes `@raw_body`: [1](#0-0) 
- `shop` is read independently from a header that is not part of the signed material: [2](#0-1) 
- `HmacValidator.validate` only re-computes the signature over `to_signable_string`, so it can never detect a tampered `shop` header: [3](#0-2) 
- `Registry.process` verifies the HMAC, then unconditionally forwards `request.shop` to the handler as the trusted tenant: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any user who installs the app on their own store legitimately receives real, validly-signed webhook deliveries. That user can capture one such `(body, hmac)` pair and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. Since the signature never covers that header, `HmacValidator.validate` still returns `true`, and `Registry.process` treats the forged shop as authentic, breaking the intended binding `shop-header == shop-that-produced-this-signature`.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: a party with no relationship to the victim shop can cause the app to process attacker-supplied (but validly-HMAC'd) webhook data under the victim shop's identity. Depending on how the host app keys business logic off `WebhookMetadata#shop` (e.g., updating shop-scoped records, triggering shop-specific side effects, or attributing events), this can lead to cross-tenant data corruption or cross-tenant side effects — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install/use the target app on any shop (including the attacker's own free/dev store) to obtain a legitimately signed webhook body, and (2) sending a crafted HTTP POST to the app's public webhook endpoint with a substituted shop header — both of which are within reach of any unprivileged internet user/app installer, with no access token, `client_secret`, or privileged account required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string used for HMAC verification, or otherwise cryptographically bind the header values to the signature before trusting them, e.g.:
```ruby
def to_signable_string
  "#{shop}|#{topic}|#{@raw_body}"
end
```
Note: since real Shopify webhook signatures are computed by Shopify over the raw body only, a safer fix is for `Registry.process`/`HmacValidator` to require pinning `request.shop` against session/shop records already known to the app (registered install list) rather than trusting the header outright, since the header itself is not authenticated by Shopify's HMAC scheme.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Compute `H = HMAC-SHA256(api_secret_key, B)` — verifiable to be independent of the shop header since `to_signable_string` returns `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`).
3. Send a POST to the app's webhook endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`) and `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never sent this webhook for `victim.myshopify.com`.
