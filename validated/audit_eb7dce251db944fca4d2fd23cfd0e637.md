This confirms the root cause. The `WebhookMetadata.shop` field passed to the app's handler is sourced from the `x-shopify-shop-domain` HTTP header, but `Request#to_signable_string` (used for HMAC verification) only returns `@raw_body` — the shop header is never part of the HMAC-signed content.### Title
Webhook `shop-domain` header not covered by HMAC allows cross-tenant shop spoofing in webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value passed to app webhook handlers from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the identity binding `shop-header == HMAC-signed-shop`, allowing a request with a genuinely valid HMAC (computed over a given body with the app's `client_secret`) to carry an arbitrary, attacker-chosen `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` value, which itself is also parsed straight from the `x-shopify-hmac-sha256` header: [2](#0-1) [3](#0-2) 

However, `Request#shop` — used to identify the tenant the webhook is "for" — is read straight from the `x-shopify-shop-domain` header without any binding to the HMAC-covered content: [4](#0-3) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC, then forwards `request.shop` verbatim into `WebhookMetadata`, which is delivered to the app's `WebhookHandler#handle`: [5](#0-4) [6](#0-5) 

The gem's own documentation confirms that `data.shop` is the trusted tenant identifier apps are expected to key their downstream logic on (e.g., look up a store's session, enqueue store-scoped work): [7](#0-6) 

Because a merchant's `client_secret` (the HMAC key) is shared across *all* shops that have the app installed, a merchant who legitimately controls Shop A can receive an authentic, correctly-HMAC-signed webhook for Shop A (whose body may be generic or replayable, e.g. `app/uninstalled`, minimal `shop/redact` payloads, or any topic whose body doesn't self-identify the shop), then resend the exact same raw body and HMAC value to the app's webhook endpoint while substituting `x-shopify-shop-domain` with Shop B's (victim) domain. `HmacValidator.validate` will report the signature as valid (it never looks at the shop header), `Registry.process` will proceed, and the handler will be called with `shop: "victim-shop.myshopify.com"` even though the payload was never actually generated by or for that shop.

The equality that should hold but is broken:
`shop asserted in WebhookMetadata (from x-shopify-shop-domain header) == shop cryptographically bound by the HMAC (none — HMAC only covers the body)`

### Impact Explanation
This is a cross-tenant identity confusion: the app-facing API of this gem hands the host application a `shop` value in `WebhookMetadata` that is *not* authenticated, despite the API's contract (and the surrounding `Registry.process` call) implying that a passing HMAC check means the entire webhook — including which shop it is "for" — is verified. Any application that follows the gem's documented pattern (`data.shop`) to route/scope work per-tenant based on this field is exposed to processing an attacker-controlled shop identity attached to otherwise-legitimately-signed data, i.e., cross-tenant data corruption/confusion, satisfying the Critical "cross-tenant access" impact category, since the boundary broken here is enforced entirely inside `shopify_api`'s own webhook-verification code, not by an omission in the host app.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant with the app installed on at least one shop (an unprivileged actor from the perspective of any *other* tenant of the app) — no access to `api_secret_key`, access tokens, or another shop's credentials is needed. They can capture one authentic webhook delivery to their own shop (trivial, since it is delivered to their own registered endpoint or can be intercepted via any HTTP tooling on infrastructure they control) and replay the raw body + HMAC header with a modified `shop-domain` header. No MITM, timing race or race condition is required, unlike the analog's original report. Likelihood is High for apps that trust `data.shop` for tenant scoping, which is the exact usage pattern promoted by the gem's own documentation.

### Recommendation
Bind the shop identity to the HMAC-verified content. Options:
1. Include the `x-shopify-shop-domain` header value in the signable string used for HMAC computation/verification (matching how Shopify signs webhook payloads is not possible to change, so instead cross-validate the shop domain against the resolved webhook subscription/registration for that topic, or against a shop that the app has an active session/install record for, before calling the handler).
2. At minimum, document and/or enforce in `Registry.process` that `request.shop` must be independently confirmed by the host application (e.g., checked against a known installed-shop list) before being trusted for any tenant-scoped action, since it is not itself HMAC-protected by this gem.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (attacker controls Shop A only).
2. Shopify delivers a legitimate webhook (e.g., `app/uninstalled`) to Shop A's registered endpoint:
   - Headers: `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, body `B`.
3. Attacker captures `B` and the valid HMAC value, then sends a forged POST to the app's webhook endpoint with:
   - Same raw body `B`
   - Same `x-shopify-hmac-sha256` value
   - `x-shopify-shop-domain: shop-b.myshopify.com` (victim)
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` — the shop header is irrelevant to this computation: [8](#0-7) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed_body, ...))`, delivering attacker-controlled/replayed data attributed to Shop B to the app's business logic: [9](#0-8)
