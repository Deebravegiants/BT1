### Title
Full-snapshot `accounts_current_len` metadata omits tombstone-byte subtraction while the archived bytes for the same storage do exclude tombstones, producing a length mismatch that corrupts snapshot restore — (`runtime/src/serde_snapshot/storage.rs` + `snapshots/src/archive.rs`)

### Summary
`SerializableAccountStorageEntry::new` computes `accounts_current_len` as `accounts.len() - get_obsolete_bytes(snapshot_slot)` only, never subtracting tombstone bytes [1](#0-0) . But `archive_snapshot` selects `TombstonesFilter::Exclude` for full snapshots and pipes the storage through `AccountStorageReader`, which subtracts an *additional* `tombstone_offsets.len() * tombstone_stored_size` from `num_alive_bytes` on top of `get_obsolete_bytes` for that same filter setting [2](#0-1) [3](#0-2) . The two computations of "current length" for the same storage entry diverge whenever the storage carries tombstones, so the metadata written into the full-snapshot's `SlotAccountStorageEntries` overstates the number of bytes actually present in the archived file for that slot.

### Finding Description
`tombstone_offsets` are zero-lamport accounts that have been fully removed from the accounts index but whose bytes are kept in the on-disk storage purely so a later incremental snapshot can still observe/propagate the deletion [4](#0-3) . They are tracked in a set distinct from `obsolete_accounts`/`ObsoleteAccounts` (used by `get_obsolete_bytes`), as shown by `num_zero_lamport_single_ref_accounts` explicitly adding tombstone count on top of the zero-lamport-single-ref count [5](#0-4) , and by `get_obsolete_bytes` only reading `obsolete_accounts_read_lock()`, never `tombstone_offsets` [6](#0-5) .

When archiving a full snapshot, `archive_snapshot` sets `tombstones_filter = TombstonesFilter::Exclude` with the comment "Full snapshots do not need to persist tombstones..." [2](#0-1) , and the `AccountStorageReader` constructed with that filter explicitly zeroes out tombstone bytes from `num_alive_bytes` in addition to obsolete bytes [7](#0-6) ; `reader.len()` (i.e. the actual bytes written into the tar archive, see `header.set_size(reader.len() as u64)`) reflects this reduced size [8](#0-7) .

However, the *metadata* field describing "how many bytes are valid in this storage" — `SerializableAccountStorageEntry::accounts_current_len`, serialized alongside the archive in the bank snapshot manifest — is computed independently via `SerializableAccountsDb::new` → `SerializableAccountStorageEntry::new(entry, slot)` [9](#0-8) , which does **not** know about, or subtract, tombstone bytes at all [1](#0-0) .

Consequently, for a full-snapshot storage entry that still contains tombstone offsets, the archived file on disk is *shorter* than the `accounts_current_len` value recorded in the manifest for that same slot/entry. Test code elsewhere in the codebase shows the expected consumer pattern for this length value — `AccountsFile::new_from_file(temp_file_path, current_len)` — where `current_len` is meant to exactly match the number of valid bytes at the start of the file [10](#0-9) [11](#0-10) . If the deserialized `accounts_current_len` from a full-snapshot archive is used analogously to size the restored `AccountsFile`, the restoring node would treat trailing bytes beyond the true end of stored (non-tombstone) data as part of the AppendVec's valid region — data that was never written to the archive (it was skipped by `AccountStorageReader`). This is a genuine, code-provable asymmetry between the write-time byte accounting for the archive contents (`TombstonesFilter::Exclude` path in `account_storage_reader.rs`) and the write-time byte accounting for the manifest metadata (`SerializableAccountStorageEntry::new`), triggered purely by ordinary account lifecycle activity (close/zero-lamport followed by shrink promoting the entry to a tombstone) that any unprivileged user can produce by closing and never needing to touch privileged paths.

I could not locate the read-side (deserialization) code that consumes `accounts_current_len` when rebuilding `AccountStorageEntry`/`AccountsFile` from an unpacked snapshot archive within the indexed portion of the repo (only the two write-side occurrences in `runtime/src/serde_snapshot/storage.rs` were found by search). This limits my ability to state with full certainty whether the mismatch is silently tolerated, causes a panic/`assert`, or leads to genuine account-data corruption/divergence on restore — that final link needs to be confirmed by tracing the deserialization path (likely in `runtime/src/serde_snapshot.rs` or accounts-db's storage-rebuild code) in a full checkout, since index size limits may have excluded some file contents from my search.

### Impact Explanation
If the mismatched `accounts_current_len` is used to reconstruct the `AccountsFile` length on restore (the strongly implied purpose of the field, consistent with the `new_from_file(path, current_len)` pattern seen in tests), a validator restoring from a full snapshot containing tombstoned storages would compute a different `AccountStorageEntry`/effective account set than one that never had such a mismatch, or than the same logical state reconstructed via full+incremental restore (where the incremental uses `TombstonesFilter::Include` and does not have this particular discrepancy). This falls into the cross-node bank-hash divergence / fork category described in the audit question, since two honest nodes bootstrapping from snapshots generated with different tombstone contents at the full-snapshot slot could disagree on live account state and hashes.

### Likelihood Explanation
Tombstones are produced through completely ordinary transaction activity — a user closing an account (bringing it to zero lamports) followed by the account-storage shrink path carrying it forward as a tombstone [4](#0-3) . Any unprivileged user can trigger this by repeatedly closing/recreating an account they control. Whether the tombstone survives specifically into the storage entry chosen for a *full* snapshot slot depends on shrink/snapshot scheduling timing, which is feasible but not always guaranteed on the first attempt — making this a realistic but timing-dependent condition, reproducible with repeated attempts or by directly driving the internal APIs in a unit/integration test.

### Recommendation
Make `SerializableAccountStorageEntry::new` mirror exactly the byte accounting performed by `AccountStorageReader` for the corresponding `TombstonesFilter`: pass the `TombstonesFilter` used for the given snapshot kind into `SerializableAccountStorageEntry::new` (or compute `accounts_current_len` via the same helper `AccountStorageReader::len()`/shared function used when actually writing the archive), so that for `TombstonesFilter::Exclude` (full snapshots) the tombstone bytes are also subtracted from `accounts_current_len`, guaranteeing manifest metadata and archived byte length are always identical.

    /// Returns the number of bytes that were marked obsolete as of the passed
    /// in slot or earlier. If slot is None, then slot will be assumed to be the
    /// max root, and all obsolete bytes will be returned.
    pub fn get_obsolete_bytes(&self, slot: Option<Slot>) -> usize {
        let obsolete_bytes: usize = self
            .obsolete_accounts_read_lock()
            .filter_obsolete_accounts(slot)
            .map(|(offset, data_len)| {
                self.accounts
                    .calculate_stored_size(data_len)
                    .min(self.accounts.len() - offset)
            })
            .sum();
        obsolete_bytes
    }
