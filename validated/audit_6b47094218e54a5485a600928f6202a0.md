This confirms the root cause. `Registry.process` binds the webhook's tenant identity to `request.shop`, which is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [1](#0-0) , while the only cryptographic check performed is `Utils::HmacValidator.validate(request)`, whose signable string is `to_signable_string`, defined as just `@raw_body` [2](#0-1) . The HMAC computation itself only ever hashes `verifiable_query.to_signable_string` against the secret [3](#0-2) . So the shop-domain header is never part of the signed bytes, yet `Registry.process` trusts it to attribute the payload to a tenant: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC solely over that string. The `shop-domain` header, which `Registry.process` treats as the authoritative tenant identifier passed on to the app's webhook handler, is never bound by the signature.

### Finding Description
This is a direct analog of the report's flaw: the signature there covered `artId` but omitted `chainId`, so a validly-signed payload from one chain could be replayed on another. Here, the Shopify webhook HMAC covers the JSON body but omits the `shop-domain` header, so a validly-signed payload delivered for shop A's webhook can be replayed with a substituted `shop-domain` header for shop B, and it will still pass `Utils::HmacValidator.validate` because the signable string (`@raw_body`) is unchanged.

The binding that should hold is:
`hmac == HMAC(secret, body || shop)` (or equivalent, i.e., the signature must be over the *entire* tuple that is trusted downstream)

but what is actually enforced is:
`hmac == HMAC(secret, body)`, with `shop` taken unauthenticated from a header and forwarded to `WebhookMetadata` as attributed tenant.

`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) never cross-checks `request.shop` against anything derived from the signed bytes — it only checks the HMAC validity and then passes `request.shop` straight to the handler.

### Impact Explanation
An app that installs the same webhook handler across multiple merchant stores and dispatches per-tenant logic based on `WebhookMetadata#shop` (exactly the pattern this gem's own webhook registry API is designed to encourage) can be made to process a payload under the wrong shop's identity if an attacker can influence or replay the `shop-domain` header while keeping a body+HMAC pair that was legitimately generated for a different shop (e.g., an attacker who operates their own store with the app installed, captures a legitimately signed webhook delivery for their shop, and re-delivers it to the app's webhook endpoint with the header rewritten to a victim shop's domain). Since the HMAC never binds the shop, the app has no cryptographic way to detect the substitution, leading to cross-tenant data being misattributed/processed as belonging to the victim shop.

### Likelihood Explanation
Requires the attacker to control at least one legitimate installation of the app (to obtain a validly signed body+HMAC pair) and the ability to deliver an arbitrary HTTP request with attacker-chosen headers to the app's public webhook endpoint — both of which are realistic for an unprivileged but authenticated third-party merchant/attacker, with no need for the app's `api_secret_key` or client secret.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header value as part of the signed/verified string, or independently verify that the shop asserted in the header matches a shop already known/authorized for the webhook subscription before dispatching to handlers. At minimum, document that `WebhookMetadata#shop` is not cryptographically bound and host apps must not use it as a sole tenant-isolation boundary — but the safer fix is to bind it in `to_signable_string`/`HmacValidator`.

### Proof of Concept
1. App installs on Shop A and Shop B, both with the same webhook handler registered.
2. Shopify delivers a webhook to Shop A with body `B1` and header `x-shopify-shop-domain: shop-a.myshopify.com`, producing `hmac1 = HMAC(secret, B1)`.
3. Attacker (who controls Shop A, or intercepts/replays the request) resends the exact same body `B1` and `hmac1`, but rewrites the header to `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B1)` — unchanged — and passes.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed(B1), ...))` is invoked, so the app processes Shop A's data as if it belonged to Shop B. [5](#0-4) [6](#0-5) [7](#0-6)

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
