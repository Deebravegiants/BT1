## Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then forwards the `shop-domain` HTTP header—an unauthenticated value that plays no part in that computation—to the host application's handler as the trusted tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` derive the signable content exclusively from `@raw_body`: `to_signable_string` returns `@raw_body` and nothing else [1](#0-0) . `Request#shop` simply reads the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the body or the HMAC [2](#0-1) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body's HMAC), and then unconditionally builds `WebhookMetadata` using `request.shop` — the unauthenticated header — as the tenant identifier delivered to the app's business logic: [3](#0-2) .

`HmacValidator.validate` / `validate_signature` compute the signature strictly from `verifiable_query.to_signable_string`, so for `Request` objects the shop header is never part of what is verified: [4](#0-3) .

This breaks the intended identity binding: `shop authenticated == shop trusted by handler`. In reality, `shop authenticated` (covered by HMAC) is empty — only the body is authenticated — while `shop trusted by handler` is taken verbatim from an attacker-controllable header. Any request reaching the app's webhook endpoint with a body+HMAC pair that is valid for the app's secret (for example, a body legitimately delivered to the merchant's own shop, replayed with a different `shop-domain` header) will be processed and passed to the handler as if it originated from the spoofed shop.

### Impact Explanation
Applications built on this gem are expected to trust `WebhookMetadata#shop` to route webhook data to the correct tenant/store record (this is the field's entire purpose, per `Registry.process` passing it straight into the handler). Since the gem itself performs no binding between the verified body/HMAC and the shop header, a single valid (body, HMAC) pair can be relayed with an arbitrary shop-domain header and will pass `Registry.process` unmodified. This allows cross-tenant data injection/impersonation: an app could store or act on webhook data attributed to Shop B while the payload was only ever validly signed for Shop A (or generically for the app's secret). This matches the Critical/High "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires possession of any single valid `(raw_body, hmac)` pair for the app (e.g., a webhook the attacker's own shop legitimately received while running the app, or any webhook capture) and the ability to send an HTTP request directly to the app's webhook endpoint with a modified `shop-domain` header while keeping body and HMAC unchanged. No access to `api_secret_key` or another merchant's credentials is required — the gem never checks that the header matches anything the signature covers. Likelihood is high for any app that trusts `WebhookMetadata#shop` without additional out-of-band verification (which the gem's own docs and API surface implicitly encourage, since `shop` is provided as trusted metadata).

### Recommendation
Bind the shop identity into the verified material. Options include: (1) including the `shop-domain` header value in the string that's HMAC-verified for webhook requests (not just the raw body), (2) requiring/validating the delivered `shop-domain` against an expected value known to the app (e.g., cross-checking with `webhook_id`/topic subscription records) before constructing `WebhookMetadata`, or (3) explicitly documenting that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant resolution without independent verification by the host application.

### Proof of Concept
1. App has `shopify_api` registered webhook handler; secret is `S`.
2. Attacker (or any user with an installed instance of the app) receives one legitimate webhook delivery to their own shop `attacker-shop.myshopify.com`, capturing `raw_body B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(S, B)`).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same `raw_body B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(S, B)` and matches `H` — validation succeeds because the shop header is not part of `to_signable_string` [1](#0-0) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the app to process/store data as if it belonged to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
