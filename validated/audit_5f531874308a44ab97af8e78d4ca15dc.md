## Analysis Result

### Title
Deposit path checks `amm.lp_amount == 0` but divides by `total_coin_without_take_pnl` / `total_pc_without_take_pnl`, allowing a mismatched-invariant division-by-zero DoS analogous to the BlueberryBank `totalShare`/`totalDebt` bug - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`Processor::process_deposit` only guards against a zero divisor by checking `amm.lp_amount == 0` [1](#0-0) , yet the actual divisors used afterwards are `total_coin_without_take_pnl` / `total_pc_without_take_pnl` (via `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin`) and again as `token_total` in `InvariantPool::exchange_token_to_pool` [2](#0-1) . This is exactly the same class of bug as the BlueberryBank report: the guard is on one accounting variable (`totalShare`/`amm.lp_amount`) while the divide is performed on a different, independently-derived variable (`totalDebt`/`total_coin_without_take_pnl`).

### Finding Description
`total_pc_without_take_pnl` and `total_coin_without_take_pnl` are computed by subtracting the protocol's accrued-but-unwithdrawn PnL (`amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin`) from the raw vault balances [3](#0-2) . These `need_take_pnl_*` counters are monotonically incremented every time `calc_take_pnl` runs (on `deposit`, `withdraw`, and swap flows) whenever the pool price has moved favorably [4](#0-3) , and are only ever decremented by the privileged `process_withdrawpnl` call [5](#0-4) . If `need_take_pnl_pc`/`need_take_pnl_coin` is not withdrawn promptly and grows close to (or, in the exact-equality edge case, up to) the real vault balance, `calc_total_without_take_pnl_no_orderbook`'s `checked_sub` can yield `0` (rather than error, since it only errors on strict underflow) [6](#0-5) .

Once either total reaches `0`, the very same `calc_take_pnl` function used by deposit/withdraw/swap performs `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` using the normalized total as denominator [7](#0-6) , and the deposit-specific math (`InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin`, `InvariantPool::exchange_token_to_pool`) divides by `self.token_coin`/`self.token_pc`/`self.token_total` which are set to these same zero totals [8](#0-7) [9](#0-8) . All of these use `.unwrap()` on `checked_div`, so a zero denominator causes a panic (transaction abort), not a graceful `AmmError`. Critically, the only guard that exists checks `amm.lp_amount == 0`, not the totals actually being divided by — the wrong variable is checked, mirroring the report's core defect.

### Impact Explanation
If the divisor totals reach zero while `amm.lp_amount` remains non-zero, every future `Deposit` call (and any other instruction path that invokes `calc_take_pnl`, including swaps) for that pool will panic and revert unconditionally. This permanently freezes the ability of LPs to add liquidity to (and, depending on which side hits zero, use) that pool, matching the "permanent freezing" impact bar in the validation rules, and is directly analogous to the cited report's "borrow will always revert" DoS.

### Likelihood Explanation
Reaching this state requires `need_take_pnl_pc`/`need_take_pnl_coin` to grow to exactly match (or exceed, which is separately rejected by the overflow check) the corresponding vault balance before the privileged `pnl_owner` calls `process_withdrawpnl`. This is a narrow, precise condition — the code path and missing check are real and confirmed, but I could not fully verify from static review alone that an unprivileged attacker can drive the counters to hit this boundary exactly (as opposed to merely approaching it) purely through swap/deposit calls without administrator inaction over an extended period. This uncertainty mirrors the original reporter's own admission that they "couldn't get [a] proof of concept to work."

### Recommendation
In `process_deposit` (and anywhere else `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are used as a divisor), explicitly check these totals for zero (returning an `AmmError`) instead of relying solely on `amm.lp_amount == 0`. Additionally, replace `.checked_div(...).unwrap()` calls in `InvariantToken`, `InvariantPool`, and `calc_take_pnl` with proper `ok_or(AmmError::...)` error propagation so a zero denominator degrades to a handled error rather than an unrecoverable panic.

### Proof of Concept
Not independently reproduced; the root-cause code path (mismatched zero-check vs. actual divisor, and unconditional `.unwrap()` on `checked_div` in `calc_take_pnl`/`InvariantToken`/`InvariantPool`) is confirmed by static analysis as cited above, but the exact sequence of transactions needed to drive `need_take_pnl_pc`/`need_take_pnl_coin` to precisely equal the vault balance was not verified through execution/simulation.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
