### Title
Webhook HMAC signature covers only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator recomputes the HMAC over whatever `to_signable_string` returns and compares it to the `hmac` value [2](#0-1) .

For webhooks, `Request#to_signable_string` returns only `@raw_body` [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` values that the rest of the library treats as trusted, authenticated identity fields are all read directly from HTTP headers and are never mixed into the signed string [4](#0-3) . Yet `Registry.process` uses exactly these unbound header values to select the handler and to build the `WebhookMetadata` that is handed to app code as if it were authenticated: `handler = @registry[request.topic]&.handler` and `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [5](#0-4) .

This is the same class of bug as the referenced report: a field that the application logic acts on (`shop`, `topic`, `webhook_id`) is not covered by the integrity check (`hmac`) that is supposed to bind it. The equality that should hold is:

`shop header used by the app == shop that produced/authorized the signed HMAC payload`

but the gem only proves `HMAC(secret, raw_body) == received_hmac`; it proves nothing about which shop or topic produced that body.

### Impact Explanation
Because a single app-level `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any merchant that has installed the app (including an attacker who installs it on their own store) can obtain a validly HMAC-signed body for a webhook triggered on their own store. That attacker can then replay the exact same body to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to name a different, victim shop. `Utils::HmacValidator.validate` will still succeed because it only checks the body bytes, and `Registry.process` will hand the forged `shop`/`topic` values to the host app's handler as though Shopify itself vouched for that shop/topic pairing. This is a cross-tenant identity-binding break: it lets one tenant's authenticated payload be attributed to another tenant, which can lead to cross-tenant data corruption or unauthorized actions being taken against a victim shop's records inside the host application.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged installer of the same app (any internet user can install a public app on their own development/trial store), then capture one webhook delivery from their own shop and replay it with modified headers to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the identity fields into the signed material instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them, e.g. by having the host app additionally verify shop/topic against its own webhook subscription records) in `Webhooks::Request#to_signable_string`, mirroring the fix pattern in the referenced report where the missing bindings were added back to the trusted/verified set. At minimum, document and enforce that `shop`/`topic` must be cross-checked against records the app itself created when registering the webhook (e.g. the `webhook_id` returned by `Registry.register`) rather than trusted purely from headers accompanying a validly-signed body.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `products/update`) and capture the raw POST, including the valid `X-Shopify-Hmac-Sha256` header (computed with the app's shared `client_secret` over the body only, per `lib/shopify_api/webhooks/request.rb`).
2. Replay the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because the signature only ever covered `@raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload was never produced by or authorized for the victim shop.
