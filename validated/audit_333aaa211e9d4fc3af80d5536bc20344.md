Confirmed: there is no reclaim/sweep function anywhere in `bonding_curve_launchpad.move` or `liquidity_pairs.move` for the FA/APT dust left behind after graduation. This confirms the vulnerability.

### Title
Permanent lock of 10% of pool reserves (APT and FA) on every graduation due to `graduate()` migrating only 90% of reserves with no reclaim path - ([File: aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move])

### Summary
When a bonding-curve pair "graduates" to the external DEX, `graduate()` disables the pair (`is_enabled = false`) and permanently moves only 90% of the accumulated APT/FA reserves to the new DEX pool, deliberately leaving 10% behind in the `LiquidityPair` object's `fa_store` and in the liquidity-pair account's APT balance. Because `is_enabled` is now `false`, the only two functions capable of moving assets out of the pair (`swap_fa_to_apt`/`swap_apt_to_fa`) are permanently blocked, and no other function in either `liquidity_pairs.move` or `bonding_curve_launchpad.move` can access the pair's `ExtendRef`/`fa_store` to withdraw the residual funds.

### Finding Description
`graduate()` computes the amounts sent to the new DEX pool as 90% of the final reserves:
<cite repo="Alyssadaypin/aptos-core--019" path="aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move" start="339-355" />
```
liquidity_pair.is_enabled = false;
liquidity_pair.is_frozen = false;
router::create_pool_coin<AptosCoin>(fa_object_metadata, false);
...
add_liquidity_coin_entry_transfer_ref<AptosCoin>(
    transfer_ref, &liquidity_pair_signer, liquidity_pair.fa_store, fa_object_metadata, false,
    ((apt_updated_reserves - (apt_updated_reserves / 10)) as u64),
    ((fa_updated_reserves - (fa_updated_reserves / 10)) as u64),
    0, 0
);
``` [1](#0-0) 

`add_liquidity_coin_entry_transfer_ref` withdraws exactly `optimal_amount_1`/`optimal_amount_2` (which, for a brand-new pool created immediately beforehand by `router::create_pool_coin`, equal the desired 90% amounts since there are no existing reserves to constrain the ratio) from the liquidity-pair signer's APT balance and from `liquidity_pair.fa_store`: [2](#0-1) 

The remaining 10% of APT (native coin balance of the liquidity-pair object's address) and 10% of FA (still held in `liquidity_pair.fa_store`, owned by the pair object) are never moved anywhere. `LiquidityPair.extend_ref`, the only capability that can generate the pair's signer to move that residual value, is stored inside the `LiquidityPair` resource and is only ever used inside `swap_fa_to_apt`, `swap_apt_to_fa`, and `graduate()` - all three of which are gated by `assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED)` and `graduate()` itself is only invoked once, from inside `swap_apt_to_fa` when the threshold is crossed. After `graduate()` runs, `is_enabled` is permanently `false`, so both swap entrypoints (the only ones dispatched from `bonding_curve_launchpad::swap`) revert forever. No other public/entry function in the module exposes the pair's `ExtendRef` or a withdraw path for `fa_store`/the pair's APT balance.

### Impact Explanation
This is a custody-accounting corruption bug: 10% of the FA supply held for this pair (an object-held fungible-asset store) and 10% of the pair's native APT balance become permanently non-recoverable for every single successful graduation. There is no privileged or unprivileged path — creator, admin, or user — capable of ever withdrawing this stranded value, since the module holds no reclaim/sweep function and the pair's `ExtendRef` is never exposed outside the disabled swap functions. This constitutes a guaranteed, deterministic, non-recoverable loss of object-held APT and FA value, which is a High-severity custody impact (permanent lock of value with no privileged-admin escape hatch even considered).

### Likelihood Explanation
Likelihood is High/Certain: this occurs automatically and unavoidably on every graduation event (i.e., every time a bonding-curve FA reaches the APT liquidity threshold), which is the designed, expected end-state of every successful launch on this platform. No attacker action or special conditions are required.

### Recommendation
Modify `graduate()` to migrate 100% of `apt_updated_reserves`/`fa_updated_reserves` to the new DEX pool (subject to whatever legitimate LP-minting rounding is unavoidable), or add an explicit, permissioned sweep function that uses `liquidity_pair.extend_ref` to transfer any residual APT/FA dust after graduation to a designated recipient (e.g., the creator or a treasury), so no object-held value is ever permanently stranded.

### Proof of Concept
1. Call `bonding_curve_launchpad::create_fa_pair` to launch a new FA/APT pair.
2. Repeatedly call `bonding_curve_launchpad::swap(swap_to_apt = false, ...)` until `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD`, triggering `graduate()` inside `swap_apt_to_fa` [3](#0-2) .
3. Observe that `graduate()` moves only 90% of `fa_updated_reserves`/`apt_updated_reserves` to the new `swap::liquidity_pool`, and sets `is_enabled = false`.
4. Attempt to call `bonding_curve_launchpad::swap` again on the same `name`/`symbol` — it reverts with `ELIQUIDITY_PAIR_DISABLED` for both directions.
5. Query `liquidity_pair.fa_store`'s balance and the liquidity-pair object address's APT balance — both retain ~10% of the pre-graduation reserves, with no remaining function in the module able to move them out.
