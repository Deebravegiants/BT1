### Title
Accumulated K-slack in `Pair.swap`'s `+1` rounding tolerance can permanently DoS `Router.sell` via an underflow revert - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Router.sol])

### Summary
`Pair.swap` enforces the K-invariant with a `+1` rounding slack — `(newTokenReserve + 1) * (newAssetReserve + 1) >= k` — rather than the strict `newTokenReserve * newAssetReserve >= k`. [1](#0-0)  This slack allows the *actual* reserve product to drift slightly below `k` on every swap. `Router._computeBuy` defends against overflow/degenerate states with an explicit cap and `OverflowCapDegenerate` revert, but `Router._computeSell` has no equivalent guard: it computes `assetOut = reserveAsset - (k / newReserveToken)` as a raw unchecked subtraction. [2](#0-1)  If accumulated rounding drift ever pushes `k / newReserveToken` above the live `reserveAsset`, every call to `sell()` for that token reverts with an arithmetic-underflow panic — permanently, since the state that caused the drift does not self-heal by more selling (selling only increases `tokenReserve`, which can widen the gap further).

### Finding Description
`Router._computeBuy` explicitly plans for the case where the naive K-derived output would push the curve past physical bounds, backing off to a capped, back-calculated `amountInUsed` and reverting with `OverflowCapDegenerate` only in the truly unreachable case (guarded by the documented `tokenBalance() < tokenReserve()` invariant). [3](#0-2)  `_computeSell` has no analogous cap or degenerate check — it assumes `k / newReserveToken <= reserveAsset` will always hold and performs unguarded subtraction. [2](#0-1) 

That assumption relies on `reserveToken * reserveAsset >= k` holding as a strict invariant after every swap. But `Pair.swap`'s check only enforces the padded form `(newTokenReserve + 1) * (newAssetReserve + 1) >= k`, which is satisfiable even when the *unpadded* product `newTokenReserve * newAssetReserve` is strictly less than `k` (by up to `newTokenReserve + newAssetReserve + 1`, per the K-invariant algebra). [4](#0-3)  Any unprivileged trader can drive many small buy/sell round trips through `Bonding.buy` / `Bonding.sell` → `Router.buy` / `Router.sell` → `Pair.swap`, each one potentially eating into this slack in the direction that shrinks the true product below `k`. Once enough drift has accumulated that `k / newReserveToken > reserveAsset` for some subsequent sell size, `Router._computeSell`'s subtraction underflows and reverts (Solidity Panic 0x11) for every sell attempt at or above that size — with no cap/branch to fall back to, unlike the buy side.

### Impact Explanation
Because `Router.sell` is the only on-curve exit path before graduation (`Bonding.sell` → `Router.sell`), a token whose curve state has drifted into this degenerate zone becomes **un-sellable on the curve** for any trader attempting a sell of the affected size or larger. Since `Router._computeSell` has no capped-fallback branch (unlike `_computeBuy`'s `OverflowCapDegenerate` handling, which caps and continues), this is a hard revert with no recovery path from within the AMM math itself — traders' tokens are effectively frozen on the curve until/unless the token happens to graduate via a different path (e.g., a buy that trips `canGraduate`), which a stuck seller cannot force. This is a freezing-of-trader-funds impact reachable purely through unprivileged `buy`/`sell` calls.

### Likelihood Explanation
The `+1` slack is small per swap, so a very large number of adversarial-shaped round-trip trades (buy then sell at sizes chosen to maximize the padding effect) would likely be needed to accumulate enough drift to matter in practice — this is a griefing/self-DoS style attack requiring sustained capital cycling and gas expenditure by the attacker, with no direct profit motive beyond harming a specific token's tradability. Likelihood is therefore Medium: mechanically reachable by any trader with no privileged access, but not a cheap one-shot exploit.

### Recommendation
Add an explicit degenerate/underflow guard in `Router._computeSell` mirroring `_computeBuy`'s defensive cap — e.g., detect `k / newReserveToken > reserveAsset` and either cap `assetOut` at `reserveAsset` (draining the curve, analogous to the buy-side supply cap) or revert with a named error rather than a raw arithmetic panic, and consider tightening `Pair.swap`'s K-check to the strict (non-`+1`) form if the slack is not otherwise load-bearing.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a modest seed.
2. As an unprivileged trader, repeatedly call `Bonding.buy` / `Bonding.sell` with adversarially chosen small amounts designed to always land on the rounding-favorable side of `Pair.swap`'s `(newTokenReserve + 1) * (newAssetReserve + 1) >= k` check (i.e., swaps that pass the padded check but leave the true `tokenReserve * assetReserve` product below `k`).
3. Repeat until the accumulated drift is large enough that `k / (reserveToken + amountIn) > reserveAsset` for some realistic sell size.
4. Any subsequent `Bonding.sell` call at or above that size reverts with an arithmetic-underflow panic in `Router._computeSell`, with no fallback path — bricking selling for that token.

        uint256 tokenIn,

        uint256 assetIn,

    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
