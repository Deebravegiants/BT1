### Title
Native-token overpayment on `EvmHost.dispatch`/`fundRequest` is permanently trapped with no sweep mechanism - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` (and `fundRequest`) accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, ...)`, where `EvmHost` itself is the `msg.sender` to the router. `swapETHForExactTokens` only spends the amount required to buy the exact `post.fee`/`get.fee` output and refunds any unspent ETH back to its caller — which is `EvmHost`, not the original transaction sender. `EvmHost` has a `receive()` function that silently accepts this refunded ETH, but the contract exposes no function to withdraw or forward that native balance back out. Any user who sends slightly more native token than the exact amount needed for the swap (a very common case, since off-chain fee estimation via `quote()` is explicitly documented as imprecise and subject to slippage) will have the difference permanently stuck in the host contract.

### Finding Description
`dispatch(DispatchPost)`: [1](#0-0) 

performs the same swap pattern in `dispatch(DispatchGet)`. In both cases:
- The router's `swapETHForExactTokens` is an exact-output swap; the caller (`EvmHost`) provides `msg.value` as an upper bound and receives back any unused ETH.
- `EvmHost` never captures or forwards this refund to `post.payer`/`get.payer` or to `_msgSender()`.
- `EvmHost` implements `receive() external payable` (confirmed present in the contract), so the refund is accepted rather than reverting, and it is never referenced again — there is no `withdraw`/`sweep` function found in `EvmHost.sol` that lets the admin, a user, or the protocol move accumulated native balance back out.

Because a caller determines `msg.value` off-chain (the docs explicitly warn `quote()` is imprecise and subject to sandwiching, telling integrators to over-provision it), routine, honest use of the dispatch API will generate leftover ETH balance inside `EvmHost` on every call where the estimate exceeds the exact amount consumed by the swap.

### Impact Explanation
Every dispatch/fundRequest call made with native token payment that overestimates the required amount leaves the excess permanently locked inside `EvmHost`, with no recovery path for the payer or the protocol. This is a direct, unprivileged, single-transaction path (any user dispatching a POST/GET request or funding a request with native token) to permanent freezing of user/protocol funds, satisfying a Medium-severity fund-freezing impact.

### Likelihood Explanation
High likelihood: this occurs on ordinary, expected usage of the native-token payment path (not an attack), since exact fee-token pricing cannot be perfectly predicted off-chain due to AMM price movement between quoting and execution, and the documentation itself instructs callers to estimate off-chain via `quote()`, acknowledging imprecision.

### Recommendation
Capture the ETH balance/refund from the Uniswap swap and forward it back to `_msgSender()`/`payer` at the end of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, e.g. by tracking `address(this).balance` before/after the swap and returning the delta via a low-level call, or by adding a permissionless `sweepExcessNative()` function that lets a caller reclaim ETH attributable to their own transaction.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value` computed from an off-chain `quote(post.fee)` estimate plus a safety buffer (as advised by the project's own documentation).
2. Inside `dispatch`, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is executed with `EvmHost` as the router's `msg.sender`.
3. The router spends only the exact ETH needed to acquire `post.fee` units of `feeToken` and refunds the remainder to `EvmHost` (the caller), which accepts it via `receive()`.
4. `dispatch` returns without forwarding any refund to the user; the leftover ETH remains in `EvmHost`'s balance indefinitely, as no function in `EvmHost.sol` withdraws native token out of the contract. [2](#0-1)

     * @dev Dispatch a POST request to Hyperbridge

     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in

     *
     * @param post - post request
     * @return commitment - the request commitment

        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();

                post.fee, path, address(this), block.timestamp
