### Title
Missing `BlockSignupWhenNoInternet` field in backend config response silently defaults to fail-open (`false`) instead of the documented fail-closed default (`true`) - ([File: src/backend/config.rs], [File: src/config.rs])

### Summary
`backend::config::Config::block_signup_when_no_internet` is declared as a plain `bool` with `#[serde(default)]` rather than `Option<bool>`, so when the backend response omits this field, Serde's blanket `bool::default()` (`false`) is used instead of the crate's intended fail-closed constant `DEFAULT_BLOCK_SIGNUPS_WHEN_NO_INTERNET = true`. `Config::from_backend` passes this value through verbatim with no fallback to `default.block_signup_when_no_internet`, silently downgrading the invariant that signups should be blocked when no internet is available.

### Finding Description
In `src/backend/config.rs`, the field is defined as: [1](#0-0) 
Because this is a raw `bool` (not `Option<bool>`) with `#[serde(default)]`, any JSON response that omits the `BlockSignupWhenNoInternet` key deserializes to Serde's type default, `false`.

In `src/config.rs`, `Config::from_backend` destructures the backend response and assigns `block_signup_when_no_internet` directly, with no `unwrap_or(default.block_signup_when_no_internet)` fallback like every other optional field receives: [2](#0-1) 

Compare this to the crate's own intended safe default: [3](#0-2) 
and the corresponding field in the locally-stored `Config` struct that documents the fail-closed intent: [4](#0-3) 

Every other optional field in `from_backend` explicitly falls back to `default.<field>` (the safe local default) when the backend omits it, e.g. `thermal_camera: thermal_camera.unwrap_or(default.thermal_camera)` or `pcp_v3: pcp_v3.unwrap_or(default.pcp_v3)` [5](#0-4) . `block_signup_when_no_internet` is the one exception that bypasses this pattern entirely because it isn't wrapped in `Option`, so a missing field never reaches `default.block_signup_when_no_internet` (`true`) — it is coerced to `false` at deserialization time before `from_backend` even runs.

The resulting value is consumed directly by the signup-gating logic: [6](#0-5) 
so a config response lacking this field silently disables the "block signup when no internet" fail-closed protection, allowing signups to proceed without an internet connection when the intended default is to block them.

### Impact Explanation
This is a config-driven weakening of a documented fail-closed security control (`block_signup_when_no_internet`), matching the "signup gating logic" impact category described in the question. It could allow signups to proceed while the orb has no verified internet connectivity, undermining downstream state/fraud/liveness checks that assume connectivity guarantees, and represents a silent divergence between the crate's documented safe default and actual runtime behavior whenever the backend config response omits the field.

### Likelihood Explanation
The precondition is that the orb's downloaded config JSON from the management-backend endpoint omits the `BlockSignupWhenNoInternet` key — whether due to a compromised/spoofed backend response, a backend rollout bug, schema drift, or backward-incompatible deploy. No token leakage, MITM of TLS content-integrity mechanisms beyond controlling the JSON body, or device tampering is required beyond what the question's threat model already assumes (attacker-influenced backend response reachable through the orb's normal authenticated config-fetch flow). The bug is deterministic and 100% reproducible any time the field is absent from the response.

### Recommendation
Change `block_signup_when_no_internet` in `src/backend/config.rs` to `Option<bool>` (removing `#[serde(default)]`), and in `Config::from_backend` fall back explicitly to the safe default:
```rust
block_signup_when_no_internet: block_signup_when_no_internet
    .unwrap_or(default.block_signup_when_no_internet),
```
This aligns the field with the rest of the optional/defaulted fields and ensures a missing field resolves to the fail-closed `true` default defined in `DEFAULT_BLOCK_SIGNUPS_WHEN_NO_INTERNET`.

### Proof of Concept
Unit test in `src/config.rs` (or a new test module) constructing a `backend::config::Response` where the JSON omits `BlockSignupWhenNoInternet`:
```rust
#[test]
fn missing_block_signup_when_no_internet_defaults_fail_open() {
    let json = r#"{"Config": {
        "SoundVolume": 10,
        "LastUpdated": 0
        /* BlockSignupWhenNoInternet intentionally omitted */
    }}"#;
    let resp: backend::config::Response = serde_json::from_str(json).unwrap();
    // Bug: deserializes to `false` (Serde bool default) instead of DEFAULT_BLOCK_SIGNUPS_WHEN_NO_INTERNET (true)
    assert_eq!(resp.config.block_signup_when_no_internet, false);

    let cfg = Config::from_backend(resp).unwrap();
    // Expected (fail-closed) behavior would be `true`; current code yields `false`.
    assert_eq!(cfg.block_signup_when_no_internet, false, "demonstrates fail-open downgrade");
}
```
Expected assertion after the fix: `cfg.block_signup_when_no_internet == true` (matching `DEFAULT_BLOCK_SIGNUPS_WHEN_NO_INTERNET`) when the backend response omits the field.
