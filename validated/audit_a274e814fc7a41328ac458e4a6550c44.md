Confirmed: the webhook HMAC binds only to the raw request body via `Request#to_signable_string` returning `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers with no cryptographic binding to that signature.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler receives and acts on are read straight from unauthenticated HTTP headers that are never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` decodes the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from other, separate headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are not included in `to_signable_string` at all [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching to the handler with `request.shop`, `request.topic`, and `request.webhook_id` taken verbatim from the unauthenticated headers [4](#0-3) .

The identity binding that should hold is:
`hmac_signed_bytes == bytes_the_app_trusts_for_tenant_attribution`

Here, `hmac_signed_bytes = raw_body` but `bytes_the_app_trusts_for_tenant_attribution = raw_body + shop-domain header + topic header + webhook-id header`. Since the header set is disjoint from the signed set, the equality is broken: an attacker can present a valid `(raw_body, hmac)` pair captured from a webhook legitimately sent to their own shop's app installation (all merchants of a multi-tenant app share the same `client_secret`, hence the same HMAC key), and swap the `X-Shopify-Shop-Domain` header to name a victim shop. The signature still validates because it only covers `raw_body`, but the application's webhook handler will process the payload as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an unprivileged attacker who has (or creates, e.g. by installing the app on a shop they control) at least one legitimately signed webhook body can replay it against the same app's webhook endpoint while forging the shop attribution to any other tenant of that app. Downstream `WebhookHandler` implementations typically use `data.shop` to look up/act on a specific merchant's stored session or state (e.g., process `orders/create`, `app/uninstalled`, GDPR topics), so this is a cross-tenant data/state confusion primitive delivered entirely through this gem's webhook verification API, consistent with "Critical - cross-tenant access."

### Likelihood Explanation
Requires: (1) attacker has network access to the app's public webhook endpoint (any internet user, per rule), and (2) attacker possesses one valid `(raw_body, hmac)` pair, obtainable trivially by installing the target app on a shop they control (a normal, unprivileged action) and capturing one of their own inbound webhooks. No access token, `client_secret`, or privileged account is needed — only a legitimately received webhook that any merchant of the app already gets. This is straightforward to reproduce.

### Recommendation
Include the trust-relevant header values (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the bytes covered by the HMAC comparison — or, at minimum, require the caller/host application to independently corroborate `request.shop` against the shop associated with the actual webhook subscription/session before dispatching to a handler, rather than trusting the header value implicitly once the raw-body HMAC passes. `Request#to_signable_string` (or the verification code path in `Registry.process`) should bind headers used for tenant attribution into the signed payload, e.g. failing verification if a header-derived value cannot be independently confirmed to belong to the same webhook delivery as the signed body.

### Proof of Concept
1. App `M` is installed on both `attacker-shop.myshopify.com` (controlled by the attacker) and `victim-shop.myshopify.com`.
2. Shopify sends a real webhook to the app for `attacker-shop`, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over raw body, computed with the app's shared client_secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: <id>
   Body: {"id": 1, ...order json...}
   ```
   The attacker captures this raw body and its HMAC header (they have full visibility into their own webhook traffic).
3. Attacker replays the identical body and HMAC header to the same app endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. In `ShopifyAPI::Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only checks the untouched `raw_body` against the untouched HMAC [5](#0-4) ; `request.shop` returns `"victim-shop.myshopify.com"` from the forged header [6](#0-5) , and the handler is invoked believing the webhook came from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
