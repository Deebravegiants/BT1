## Analog Found

### Title
Missing zero-address check on cross-chain message recipient causes permanent loss of native funds in `WrappedHyperFungibleTokenUpgradeable.onAccept` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`WrappedHyperFungibleTokenUpgradeable.onAccept` derives the beneficiary from an attacker/user-controlled `to` field decoded via `_toAddr`, which validates only the byte length (20 bytes) and never checks for the zero address, before using that beneficiary directly in a raw native-value `.call`.

### Finding Description
`send()` lets any caller specify an arbitrary destination-chain recipient in `SendParams.to`, which is packed unmodified into the cross-chain `Message.to` field: [1](#0-0) 

On delivery, `onAccept` decodes `message.to` through `_toAddr`, which only checks the byte length and never rejects the zero address: [2](#0-1) 

When `_isWeth` is true, the resulting `beneficiary` is used directly in a low-level native-value transfer rather than through an ERC20 `_mint`/`_transfer` (which would internally revert on `address(0)`): [3](#0-2) 

A raw `address(0).call{value: amount}("")` succeeds (it is functionally equivalent to sending ETH to a burn address with no receive logic), so the check `if (!sent)` never triggers and the WETH-rewrap fallback is never taken. The locked underlying value is unlocked as native ETH and sent irretrievably to `address(0)`.

This differs from the sibling contract `HyperFungibleTokenUpgradeable.onAccept`, which relies on OpenZeppelin's `_mint(beneficiary, amount)`, and OZ's `ERC20Upgradeable` internally reverts on `address(0)` recipients — so that mint-based contract is naturally protected. `WrappedHyperFungibleTokenUpgradeable`'s native-ETH branch bypasses that protection entirely because it never routes through ERC20's own zero-address guard.

### Impact Explanation
Any single cross-chain transfer whose `to` bytes decode to the zero address (whether from a user mistake, a wallet/integration bug when constructing `SendParams.to`, or deliberate griefing since `to` is fully attacker-controlled) results in permanent, unrecoverable loss of the locked underlying value once the message is delivered on the WETH-configured destination chain. This is a concrete, permanent freezing/loss of funds triggered by an ordinary unprivileged user transaction (`send()`), matching the audit report's "missing zero address check" bug class applied to value-moving state rather than a governance setter.

### Likelihood Explanation
Reachable from a single unprivileged `send()` call with no special preconditions beyond the destination deployment having `_isWeth == true` (the standard configuration for wrapping a chain's native asset, e.g., WETH). No proof forgery, no privileged role, and no consensus compromise is required — only a `to` value that decodes to 20 zero bytes.

### Recommendation
In `WrappedHyperFungibleTokenUpgradeable._toAddr` (or immediately after computing `beneficiary` in `onAccept`/`onPostRequestTimeout`), reject the zero address, e.g.:
```solidity
function _toAddr(bytes memory b) internal pure returns (address addr) {
    if (b.length != 20) revert InvalidAddress(b.length);
    addr = address(bytes20(b));
    if (addr == address(0)) revert InvalidAddress(0);
}
```
This causes delivery to revert (leaving the message retryable/refundable through the timeout path) instead of silently burning the unlocked native value.

### Proof of Concept
1. Deploy `WrappedHyperFungibleTokenUpgradeable` on chain B configured with `_isWeth = true` and a valid `_underlying` WETH-like token, peered with chain A.
2. On chain A, any user calls `send()` with `SendParams.to` set to 20 zero bytes and a nonzero `amount`, locking the underlying token as usual: [4](#0-3) 
3. The relayer delivers the resulting POST request to chain B; `onAccept` passes the source checks, decodes `message.to` to `address(0)` via `_toAddr`, and executes `IWETH(_underlying).withdraw(message.amount)` followed by `beneficiary.call{value: message.amount}("")`, which succeeds against `address(0)`.
4. The unlocked native value is now permanently unrecoverable, while chain A's original locked underlying tokens were legitimately debited — a net permanent loss of funds.
