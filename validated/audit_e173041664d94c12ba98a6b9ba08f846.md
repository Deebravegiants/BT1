Based on my analysis, I found a genuine analog: the `shop` field in `ShopifyAPI::Webhooks::Request` is asserted/acted upon by the app but is not covered by the HMAC signature that `Registry.process` validates.

### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body, not the shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, which HMACs only `request.to_signable_string` (the raw body). The `shop` value handed to the host app's handler is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled unauthenticated from HTTP headers [2](#0-1) . `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value [3](#0-2) . `Registry.process` calls this validator and, on success, forwards `request.shop` (the raw header) directly to the handler as the authoritative tenant identifier: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [4](#0-3) .

This reproduces the report's bug class exactly: a field (`shop`) is acted upon by the application logic but is not covered by the cryptographic binding (HMAC) that is supposed to prove authenticity of the whole request. The equality that should hold is `shop_header == shop_bound_by(hmac)`, but in fact `hmac` binds only `body`, so `shop_header` is fully attacker-controlled while `hmac_valid == true`.

An attacker who has legitimate access to a real webhook delivery for their own store (e.g., they install the app on their own free/attacker-controlled shop and trigger a webhook such as `orders/create`) receives a genuine `(body, hmac)` pair signed with the app's `api_secret_key` by Shopify. Since the `api_secret_key` is shared across all shops using the same app, the same HMAC-signed body remains valid regardless of which `shop-domain` header accompanies it. The attacker can then replay that same body+hmac to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` even though the body actually belongs to the attacker's own shop.

### Impact Explanation
If the host application (as documented in `docs/usage/webhooks.md`, which explicitly tells developers that `data.shop` is "the shop domain of the webhook" and shows using it to key work, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) uses `data.shop` to select which tenant's records to update, this allows an attacker to inject their own attacker-controlled webhook content into another shop's data stream — a cross-tenant data-integrity/confusion issue. This meets the Critical "cross-tenant access" bar: an unprivileged user (any merchant who installs the app on their own store) can make the app process attacker-supplied data under an arbitrary victim shop identity, without needing the app's `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
Likelihood is high in any app that relies on the gem's provided `data.shop` value as the trust boundary for tenant identity, as the documentation directly encourages doing (`docs/usage/webhooks.md` lines 12–29). The attack requires no secret knowledge, no interception of another tenant's traffic, and no special privileges — only a normal, self-service app installation to legitimately obtain one valid signed webhook body, plus the ability to send an HTTP request with a forged header.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed material, or require callers to separately verify that `request.shop` matches an install/session record they already trust before acting on webhook contents. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated and must be cross-checked against a known installed-shop list before being used to key any write/side-effecting operation.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and triggers a real webhook (e.g. orders/create). Shopify sends:
#      headers: {
#        "x-shopify-topic" => "orders/create",
#        "x-shopify-hmac-sha256" => "<valid HMAC of raw_body with the app's real api_secret_key>",
#        "x-shopify-shop-domain" => "attacker.myshopify.com"
#      }
#      raw_body: '{"id":1,"note":"hello"}'

# 2. Attacker captures (raw_body, hmac) from step 1, then replays it to the
#    same webhook endpoint but swaps only the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_valid_hmac,       # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only hashes raw_body.
# The handler is invoked with data.shop == "victim-shop.myshopify.com",
# even though the payload actually originated from the attacker's own shop.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
