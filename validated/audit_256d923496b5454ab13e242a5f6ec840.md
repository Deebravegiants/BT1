### Title
Webhook shop-tenant confusion via HMAC that covers only the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, while the `shop` value that is handed to the app's handler is taken from an unauthenticated header. This breaks the intended binding "HMAC-authenticated bytes == the shop the payload is attributed to," letting a low-privileged actor who can obtain any one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` attribute that payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies exactly that signable string against the received `hmac`, using the shared `Context.api_secret_key`: [2](#0-1) 

`Registry.process` only calls this HMAC check, and then reads `request.shop` (derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes) to build the `WebhookMetadata` passed to the handler: [3](#0-2) [4](#0-3) 

Because `api_secret_key` is one shared value per app across every installed shop, and `shop-domain` is not included in `to_signable_string`, the equality that should hold is:

`HMAC(body, api_secret_key) valid` ⟹ `shop header == shop that produced body`

but the code only checks the left side, not the binding to the specific shop. Any tenant that installs the app (a normal, unprivileged action — e.g., a free/dev store) can request delivery of a legitimate webhook to their own endpoint, capture a valid `(raw_body, hmac)` pair for content they influence, then replay that exact body+HMAC to the app's webhook endpoint while spoofing the `shopify-shop-domain` header to name a different (victim) shop. The signature still validates because it never covered the shop identity, so the handler executes believing the data originated from the victim shop.

### Impact Explanation
This is a cross-tenant data/identity confusion: an app that keys any per-shop logic (billing, inventory sync, audit trail, webhook-driven writes to the shop's own records) off `WebhookMetadata#shop` can be made to attribute attacker-controlled webhook content to another merchant's tenant. This matches the "Critical – cross-tenant access" impact category, since the trust boundary between tenants sharing one `api_secret_key` is not enforced for the `shop` field, only for the body bytes.

### Likelihood Explanation
Any actor able to install the app on a shop they control (a normal onboarding action, not requiring any credential leak or privileged access) can obtain a validly-signed `(body, hmac)` pair by triggering a webhook topic whose body they can influence (e.g., order/product create with attacker-supplied fields), then forge the HTTP headers of the delivery to the app's public webhook endpoint. No access token, `client_secret`, or TLS interception is needed — only the ability to author an HTTP request with attacker-chosen headers and a previously-observed valid body/HMAC pair.

### Recommendation
Bind the identity fields to the signed content instead of trusting the unauthenticated headers:
- Extend `VerifiableQuery#to_signable_string` (or a new check in `Registry.process`) so that the HMAC covers `shop-domain`, `topic`, and `webhook-id` in addition to the raw body, or
- Require the consuming app to cross-check `request.shop` against a shop with an active, previously-stored session/installation before invoking the handler, and reject the webhook if there is no matching record for that shop, and
- Consider deriving/whitelisting shops server-side (e.g., via Shopify's originating IP ranges or per-shop webhook secrets) rather than relying purely on a globally shared `api_secret_key`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (unprivileged, ordinary signup).
2. Attacker triggers a webhook topic whose body they control, e.g. by creating an order with a custom note/field, and captures the resulting `raw_body` and `x-shopify-hmac-sha256` value delivered to their own endpoint — this HMAC is valid because it's signed with the same shared `Context.api_secret_key`: [5](#0-4) 
3. Attacker replays this exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any `x-shopify-topic`/`x-shopify-webhook-id` of their choosing.
4. `HmacValidator.validate` returns `true` since it only checks `raw_body` against the HMAC: [6](#0-5) 
5. `Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though that body never originated from the victim shop: [7](#0-6)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
