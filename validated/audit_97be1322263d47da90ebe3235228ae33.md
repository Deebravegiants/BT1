## Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, while the `shop` attribute that the library hands to application webhook handlers is read from a separate, unsigned HTTP header. Because the HMAC never binds the `shop-domain` value, any party who can produce one validly-signed webhook body (e.g. by triggering a real webhook on their own, legitimately installed store) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the request will still pass `HmacValidator.validate`.

## Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Webhooks::Request#shop` and `#hmac` are read independently from headers, with `shop` completely outside the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e., the body) and compares it to the `hmac` header value — it never incorporates `shop`: [3](#0-2) 

`Webhooks::Registry.process` only checks this body HMAC, then immediately trusts `request.shop` (the unsigned header) and forwards it to the application's handler as the authenticated tenant identifier: [4](#0-3) 

This breaks the identity binding: `hmac-verified content == body` but `shop attributed to the event == unauthenticated header value`. Since a single app's `api_secret_key` is shared across every shop that installs the app, a body+HMAC pair captured from one legitimately-installed (even free/dev) shop remains cryptographically valid when replayed with a different `shop-domain` header pointed at a different tenant of the same app. The library performs no check that the `shop` header is consistent with anything cryptographically tied to that specific shop (there is no per-shop secret, nonce, or shop-bound MAC input), so `WebhookMetadata.shop` handed to handlers can be attacker-controlled independent of which shop actually produced the signed payload.

## Impact Explanation
Applications built on this gem are documented to key their internal shop/session lookups off `data.shop` from `WebhookMetadata` (as returned by `Registry.process`). An attacker who controls one legitimate installation of the app (any unprivileged actor with a Shopify store) can forge webhook deliveries that the app attributes to an arbitrary victim shop, achieving cross-tenant data confusion/injection through the webhook processing pipeline — for example, triggering handler logic that writes attacker-supplied data (via the still-valid signed body) under a spoofed victim `shop` value, or racing/replaying benign events across tenants. This matches the "cross-tenant access" criterion for this analysis.

## Likelihood Explanation
Exploitation requires only: (1) reachability of the app's public webhook receiver endpoint, which is required to be internet-reachable by design, and (2) the attacker's own legitimate app installation to harvest one valid signed body/HMAC pair — no access token, `client_secret`, or privileged account is needed. This is realistic for any developer/attacker who can install the target app on a free or trial store.

## Recommendation
Bind the shop identity into the authenticated bytes rather than trusting an unsigned header:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used by `HmacValidator`, or
- Cross-validate the `shop` header against a value embedded in the signed payload / a per-shop secret, and
- Reject webhooks where the `shop` header cannot be tied to the HMAC-verified content.

## Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate request with headers `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and raw body `B`.
2. Replay the exact same body `B` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the (unchanged) body against the HMAC.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, i.e., attacker-controlled body content is now processed as if it originated from the victim tenant.
