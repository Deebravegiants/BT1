### Title
Unsanitized `shop` in `Oauth.begin_auth` allows SSRF/open-redirect of OAuth authorize flow - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.begin_auth` never validates the `shop` parameter against `Utils::ShopValidator.sanitize!`, unlike every other OAuth entry point in this gem (`RefreshToken`, `ClientCredentials`, `TokenExchange`). Any caller that forwards attacker-controlled input (e.g. a request header, as the gem's own docs suggest) directly to `begin_auth` will have `client_id`, `scope`, `redirect_uri`, and the CSRF `state` nonce sent to an arbitrary host chosen by the attacker.

### Finding Description
The broken binding: `Utils::ShopValidator.sanitize!(shop)` (the trust check used everywhere else in this gem's OAuth code) should equal the host embedded in `auth_route` produced by `begin_auth`. In practice, `begin_auth` never calls `sanitize!` at all — `auth_base_uri(shop)` at [1](#0-0)  returns `"https://#{shop}/admin"` for any string, and `begin_auth` appends the OAuth query directly onto that unsanitized host: [2](#0-1) . Contrast this with `RefreshToken.refresh_access_token`, which calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before doing anything else: [4](#0-3) . The same pattern exists in `ClientCredentials` and `TokenExchange`, confirming `begin_auth` is the outlier.

The gem's own documentation instructs apps to implement the login route as `shop = request.headers["Shop"]` followed immediately by `ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")`: [3](#0-2) . An unprivileged attacker can send `GET /login` with `Shop: evil.example`, causing `begin_auth` to return `auth_route = "https://evil.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=<nonce>"`. If the host app follows this documented pattern (or any pattern that passes unsanitized shop input to `begin_auth`), the victim's browser is redirected to the attacker's host along with the app's `client_id`, requested `scope`, and the CSRF `state` value paired with the session cookie.

None of the existing guards catch this: `Context.setup?` and `Context.private?` checks only gate whether OAuth is configured at all, not the shop value; there is no `state`-comparison or HMAC check in `begin_auth` (those only apply in `validate_auth_callback`); and Sorbet's `params(shop: String)` sig only enforces the type, not the domain.

### Impact Explanation
The app's `client_id` and requested `scope` are disclosed to an attacker-controlled host, and the CSRF `state` nonce (paired with a cookie the victim's browser will also receive) is sent to that host, enabling the attacker to pre-populate a valid `state`/cookie pair for later use in a state-fixation attempt against the callback flow. This is an SSRF/open-redirect of the authenticated authorize flow, matching the High severity category ("SSRF driving an authenticated request to an unintended host, session fixation or forced OAuth completion"). It is repeatable against any victim who visits the attacker-crafted login link, since a fresh `state`/cookie pair is generated per request.

### Likelihood Explanation
The precondition is that the host app follows the gem's documented integration pattern of deriving `shop` from user-controlled input (header, query param, etc.) and passing it straight to `begin_auth` without independently calling `ShopValidator.sanitize!` — which is exactly what `docs/usage/oauth.md` shows. No credentials, secrets, or special access are required; the attacker only needs to get a victim to click a crafted `/login`-style link with a manipulated `shop`/`Shop` value. This is low-cost and highly feasible for any app built per the documented pattern.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (and use the sanitized value in `auth_base_uri`), mirroring the pattern already used in `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange`.

### Proof of Concept
```ruby
# test/auth/oauth_test.rb (new test)
def test_begin_auth_rejects_untrusted_shop_host
  ShopifyAPI::Context.setup(
    api_key: "key",
    api_secret_key: "secret",
    host_name: "app.example.com",
    scope: "read_products",
    is_embedded: false,
    is_private: false,
    api_version: ShopifyAPI::LATEST_API_VERSION,
  )

  # Sanity: sanitize! rejects the untrusted host directly
  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Utils::ShopValidator.sanitize!("evil.example")
  end

  # But begin_auth happily builds an auth_route pointing at it
  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.example", redirect_path: "/cb")
  assert result[:auth_route].start_with?("https://evil.example/admin/oauth/authorize"),
    "expected auth_route to target attacker host, got: #{result[:auth_route]}"
end
```
This demonstrates the divergence: `ShopValidator.sanitize!("evil.example")` raises `InvalidShopError`, while `Oauth.begin_auth(shop: "evil.example", ...)` succeeds and returns an `auth_route` pointing at `evil.example`, carrying `client_id`, `scope`, and `state` to that host.

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
