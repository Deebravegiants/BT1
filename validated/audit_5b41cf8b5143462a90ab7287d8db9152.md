## Title
Webhook `shop` (and `topic`/`webhook_id`) header values are trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then hands the handler a `shop` value that is read from an unauthenticated HTTP header. The identity binding `shop_used_for_tenant_attribution == shop_covered_by_hmac` does not hold, so a party that owns any shop where the app is installed can capture one of their own legitimately-signed webhook deliveries and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header, causing the app to process the payload as if it belonged to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and the `shop` accessor is read straight from a header that is never mixed into the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks that `verifiable_query.hmac` matches `HMAC(api_secret_key, verifiable_query.to_signable_string)` - i.e., only the body: [4](#0-3) 

Equality that should hold: `shop_attributed_to_payload == shop_that_the_signed_bytes_were_generated_for`. In this gem, the signed bytes are only the JSON body, while the `shop` used to attribute/store/act on that payload comes from an out-of-band header that carries no cryptographic tie to the body. Any entity that receives a genuinely-signed webhook for shop A (e.g. by installing the app on a shop they control - no `api_secret_key`, access token, or privileged account required) can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting `shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `webhook-id`/`topic` combination consistent with the body). The HMAC check still passes because it never inspected the header, and the app's `WebhookHandler` receives `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: it lets an unprivileged internet user (any merchant/tester who can install the app on their own shop) inject attacker-controlled webhook payloads under a victim shop's identity into the host application's data model, since the library gives the host application no cryptographic assurance that the `shop` value is bound to the signed body. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up/mutate per-shop records, trigger per-shop side effects, or attribute compliance/GDPR events), this enables cross-tenant data injection/confusion, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: exploitation only requires the attacker to install the target app on a shop they control (a normal, unprivileged action) and capture one legitimate webhook delivery, then replay it with a modified header to the app's public webhook endpoint. No secrets, tokens, or elevated privileges are needed, and webhook endpoints are typically public and discoverable.

### Recommendation
Do not trust header-derived `shop`/`topic`/`webhook_id` values for tenant attribution unless they are cryptographically bound to the verified payload. Options: include the shop domain (and other identity headers) in the HMAC signing input where Shopify's webhook signature scheme allows it, or require the host application to independently correlate the header-provided `shop` against the body content/an authenticated session/subscription record before acting, and document this gap clearly for consumers of `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook (e.g., `orders/create`) that Shopify signs and delivers to the app's webhook endpoint. Attacker intercepts/records the raw body and the `X-Shopify-Hmac-Sha256` header.
2. Attacker resends the same raw body and HMAC to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (`to_signable_string` only reflects the body), and `Utils::HmacValidator.validate` succeeds because the signature only ever covered the body.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, and the host application processes attacker-controlled data as belonging to `victim-shop.myshopify.com`.
