### Title
Webhook shop-domain and topic are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator` binds nothing but the JSON body bytes. The `shop` and `topic` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's webhook handler are read straight from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`), never included in the signed content.

### Finding Description
`Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header and `Request#to_signable_string` returns only the raw request body: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate_signature` computes the signature strictly over `verifiable_query.to_signable_string` and compares it with `verifiable_query.hmac`: [5](#0-4) 

`Registry.process` validates only that body-bound HMAC, then immediately trusts `request.shop` and `request.topic` — both sourced from headers that were never part of the signed bytes — to build the `WebhookMetadata` object handed to the app's handler: [6](#0-5) 

This breaks the identity binding `hmac(signed_bytes) == hmac(received_bytes)` versus the actual claim being trusted: `shop_used_by_handler == shop_header_value`. The signature proves the *body* originated from someone holding `api_secret_key` (i.e., genuinely came from Shopify for *some* webhook delivery), but it proves nothing about which shop or topic that body belongs to, because those fields are parsed from headers outside the signed payload.

An unprivileged internet user who operates their own Shopify store (trivial to obtain, e.g. via a free development store) will legitimately receive real webhook deliveries with a valid `X-Shopify-Hmac-Sha256` for their own shop's body. They can capture one such body+HMAC pair and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will dispatch the handler with `data.shop` equal to the attacker-chosen victim shop while `data.body` is the attacker's own (fully attacker-controlled, since it's their own store's webhook payload) content.

### Impact Explanation
Any app built on this gem's webhook handling that uses `data.shop` to key persistence, trigger per-tenant side effects, or otherwise scope authorization (a documented, intended usage per `docs/usage/webhooks.md` and `BREAKING_CHANGES_FOR_V15.md`, which describe `data.shop` as "The shop domain of the webhook") will process attacker-controlled data under a victim tenant's identity. This is a cross-tenant data injection / cross-tenant access primitive: the attacker fully controls the JSON body (their own real webhook payload, or any topic/body combination they can get Shopify to sign for their own store) while impersonating an arbitrary victim shop domain, without needing the app's `client_secret`, any access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is realistic: obtaining one legitimately signed webhook body+HMAC pair only requires operating any Shopify store (including a free development store) that has the target app installed, or observing any publicly-triggerable webhook topic. No secret material of the app or of the victim shop is needed — only a network-observable legitimate webhook delivery and the ability to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signed content — e.g., by having `Request#to_signable_string` incorporate `shop` and `topic` alongside the raw body — so the signature binds the shop/topic claims to the same secret-derived proof as the body. Alternatively, require app developers to independently verify that `data.shop` corresponds to a shop with an active, previously-established session/installation record before trusting it for tenant-scoped operations, and document this requirement prominently since the gem currently offers no such binding.

### Proof of Concept
1. Attacker registers a Shopify development store `attacker-shop.myshopify.com` and installs the target app, or otherwise triggers/observes a legitimate webhook delivery to the app (e.g. `orders/create`) with valid headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body B>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body `B` (attacker fully controls contents of their own store's order, or any topic body they can trigger).
2. Attacker resends the exact same body `B` and the same `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (no cross-header binding is enforced), `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B`, and `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`.
4. The app's handler processes attacker-supplied data under `victim-shop.myshopify.com`'s identity, achieving cross-tenant data injection without any credential belonging to the victim or the app.
