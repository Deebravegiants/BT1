### Title
Unauthenticated network access to live biometric IR/RGB video feed via livestream Upstream TCP listener - ([File: src/agents/livestream/upstream.rs])

### Summary
The livestream agent's `Upstream::new` binds a `TcpListener` on `0.0.0.0:9201` and accepts any incoming TCP connection with no authentication, token, or signup-session validation whatsoever. Upon `Event::Connected`, `src/agents/livestream/mod.rs` immediately creates a `Downstream` bound to the connecting peer's raw IP address and begins pushing rendered camera frames (IR eye/face, RGB) to it over UDP, so any network-adjacent peer that can reach port 9201 receives the live biometric video of whoever is in front of the Orb.

### Finding Description
`Upstream::new` in [1](#0-0)  binds a plaintext TCP listener on all interfaces with no TLS, no credential exchange, and no check tying the connection to a signup session. `poll_next` in the same file unconditionally accepts any connection and emits `Event::Connected(addr)` for it: [2](#0-1) . The livestream agent's main loop in `src/agents/livestream/mod.rs` handles this event by directly constructing a `Downstream` streaming target using the raw source IP of the TCP client, with no identity or authorization check: [3](#0-2) . Once a downstream exists, every rendered frame (IR eye, IR face, RGB, thermal, depth as fed via `Input::*Frame` variants) is pushed to that peer via `gpu.render(events, move |buffer| downstream.push(&buffer))`: [4](#0-3) . `Downstream::new` then opens a GStreamer UDP sink pointed at the connecting client's IP on port 9200 with H.264-encoded video containing the composited camera view: [5](#0-4) . There is no code path anywhere in `upstream.rs` or `mod.rs` that validates a signup-scoped credential/token supplied by the connecting client before frames begin flowing.

### Impact Explanation
Any device with L2/L3 reachability to port 9201 on the Orb (e.g., same LAN/subnet or any network path with no firewall in between) can open a raw TCP connection and immediately start receiving the live IR/RGB video feed of whichever person is physically in front of the Orb — a real-time biometric video disclosure to an unrelated, non-consenting third party. This breaks the identity-binding invariant that only the scanned user (or an authorized operator session tied to that signup) should ever receive their own biometric frames. This maps to a biometric data disclosure impact under Orb bounty categories.

### Likelihood Explanation
The vulnerability is only reachable when the `livestream` cargo feature is compiled in and the agent is explicitly enabled via the `--livestream` CLI flag at operator startup (`src/bin/orb-core.rs:92-95`, gated by `#[cfg(feature = "livestream")]`). This is intended as an operator/support debugging tool, not an attacker-controlled path, and is not enabled in production Orb builds by default. Given the question's stated precondition that this feature is compiled in and enabled, the exploit itself requires no authentication at all — a single TCP `connect()` from an unprivileged network peer is sufficient, and the code repeatably accepts any and all connections. There is no rate limiting, IP allow-listing, or credential requirement gating the accept path.

### Recommendation
Require the connecting client to present a signup-scoped credential/token (e.g., mutual TLS, a pre-shared session token issued only to the authorized operator/technician tooling, or binding the listener to a loopback/VPN-only interface) before `Upstream` accepts a connection or before `Downstream` is created. At minimum, bind the listener to localhost or a private management interface rather than `0.0.0.0`, and add an authentication handshake in `Upstream::poll_next` prior to emitting `Event::Connected`.

### Proof of Concept
Integration test plan:
1. Start the livestream agent with the `livestream` feature enabled (as in test harness), bound to `127.0.0.1:9201` for test isolation.
2. From a separate, unauthenticated test client, `TcpStream::connect` to port 9201 without sending any token/credential.
3. Assert that `Upstream::poll_next` should return `Poll::Pending` (or reject/close) rather than `Poll::Ready(Some(Ok(Event::Connected(addr))))`, i.e., that no `Downstream` is constructed for this connection — currently the existing code fails this assertion because `poll_accept` unconditionally succeeds and `Event::Connected` is emitted at [2](#0-1) , and `mod.rs` then unconditionally calls `Downstream::new(addr.ip())` at [3](#0-2) .
4. As a secondary check, assert that after a `RgbFrame`/`IrEyeFrame` input is pushed into the agent's port, no UDP packets are sent to the unauthenticated test client's IP on port 9200 unless a valid signup-scoped token was presented during the TCP handshake.
