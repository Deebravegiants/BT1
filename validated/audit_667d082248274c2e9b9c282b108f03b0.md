### Title
Global `usedMessages[emporiumMessage]` namespace lets any EOA front-run and permanently block a specific Emporium transaction - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.cancelEmporiumMessage()` allows *any* caller to mark an arbitrary `emporiumMessage` id as used, as long as they sign a fresh EIP-712 message that recovers to their own address. Because `usedMessages` is a single global mapping keyed only by the numeric `emporiumMessage` value (not scoped per intended signer/user), an attacker who observes a pending Emporium transaction in the mempool can extract its `emporiumMessage` value from the calldata and pre-emptively call `cancelEmporiumMessage` with a signature of their own, setting `usedMessages[emporiumMessage] = true` before the legitimate transaction lands.

### Finding Description
`verifyWallet()` enforces a strict one-time-use guard: [1](#0-0) 

```
if ($.usedMessages[circomData.emporiumMessage]) {
    revert UsedMessage();
}
$.usedMessages[circomData.emporiumMessage] = true;
```

This is analogous to `MinterUpgradeable.nudge()`'s `proposals[_period]` one-time guard in the external report: a shared, globally-keyed flag is set by *any* caller's transaction, and a later, legitimate transaction targeting the same key is unconditionally blocked because the guard doesn't verify that the caller who set the flag was actually authorized to consume that specific slot on behalf of the real transaction's owner.

`cancelEmporiumMessage()` is meant ("Lets a signer burn `emporiumMessage` before it's used ... so no one else can cancel it for them") to let the *original* intended signer cancel their own pending message. However, the only check performed is that the ECDSA signature recovers to `msg.sender`: [2](#0-1) 

```
function cancelEmporiumMessage(uint256 emporiumMessage, uint8 v, bytes32 r, bytes32 s) external {
    ...
    (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(hashedMessage, v, r, s);
    bool verified = err == ECDSA.RecoverError.NoError && recoveredAddress == msg.sender;
    if (!verified) {
        revert InvalidSignature();
    }
    $.usedMessages[emporiumMessage] = true;
}
```

Nothing ties `emporiumMessage` to the caller: **any** address can pick an arbitrary `emporiumMessage` value, sign the `EmporiumCancel(uint256 message)` typed-data hash with their own private key (which trivially recovers to `msg.sender`), and successfully call `cancelEmporiumMessage`. The function does not check that the caller is the `stack.signerAddress` embedded in the real, pending Emporium operation, nor any relationship to the true owner of that message id.

Because `emporiumMessage` (derived from `Poseidon(1)([messageSeed])`, see `circuits/MainEVMCircuit.circom:98`) is transmitted in plaintext as part of `CircomData` in the `Hinkal.transact()` calldata, it becomes publicly visible the moment a legitimate user's transaction is broadcast to the mempool. An attacker can read this value off the pending transaction and race it with their own `cancelEmporiumMessage` call using a fresh, self-signed cancellation for that same id.

The `verifyWallet()` guard blocks the legitimate transaction: [3](#0-2) 

`Hinkal.transact()` calls `_externalTransact` → `EmporiumUpgradeable.runAction()` → `verifyWallet()`, which will now revert with `UsedMessage()`, causing the entire `transact()` call (including proof verification, nullifier insertion, and UTXO creation) to revert. This equality break maps to the rule "a `CircomData` field acted on but outside `calldataHash`/`signedMessageHash`/the public-input vector" — here `emporiumMessage`'s *consumption guard* (`usedMessages`) is a state variable that is set via a code path (`cancelEmporiumMessage`) that is entirely disconnected from the proof/signature that actually authorizes the transaction, letting an unrelated party mutate state that gates a specific user's proven, signed transaction.

### Impact Explanation
Any unprivileged EOA monitoring the mempool can permanently deny a specific pending Emporium transaction from ever executing with that `emporiumMessage`/proof, forcing the legitimate user to discard the proof and regenerate a new one (with a new `messageSeed`) off-chain. This is a temporary freezing of user funds/operations (High): funds queued for an Emporium action (deposit/withdraw/wallet-invocation) cannot be executed until the user restarts the flow with a new proof, and the attack is repeatable indefinitely by simply watching the mempool for future attempts, effectively enabling a persistent targeted denial-of-service against any specific user's Emporium interactions, at negligible cost to the attacker (one signature + one transaction).

### Likelihood Explanation
Likelihood is high: the attack requires no privileges, no capital at risk beyond gas, and only the ability to observe a pending transaction's calldata and race it — a routine mempool front-running capability. The `emporiumMessage` value is trivially extractable from the plaintext calldata of any pending `transact()` call that targets the Emporium external action.

### Recommendation
- Bind `cancelEmporiumMessage` to the actual owner of the message: require that the caller (or a signature recovering to `stack.signerAddress`/the originally intended signer) matches the party who created the message, e.g. by having the canceller supply and be checked against the original `stack.signerAddress` from the corresponding pending operation, or by deriving `emporiumMessage` cancellation rights from the same key/signature scheme used to authorize the operation itself.
- Alternatively, scope `usedMessages` per-signer (e.g. `mapping(address => mapping(uint256 => bool))`) so that an attacker's self-signed cancellation cannot collide with another user's message id.
- Consider requiring that `cancelEmporiumMessage` only be callable for messages that have not yet been observed on-chain, or add a challenge/commitment step so an unrelated address cannot preemptively consume another party's `emporiumMessage` slot.

### Proof of Concept
1. Legitimate user Alice builds a Hinkal Emporium transaction with `CircomData.emporiumMessage = M` (deterministically derived from her secret `messageSeed`), signs the corresponding `EmporiumOperation`/`EmporiumSignature` payload with her `stack.signerAddress` key, and broadcasts `Hinkal.transact(...)` to the mempool.
2. Attacker Bob observes the pending transaction's calldata and extracts `M = circomData.emporiumMessage` (plaintext, no cryptographic protection is needed to read it).
3. Bob signs the `EmporiumCancel(uint256 message)` EIP-712 struct for `message = M` with his own private key (`recoveredAddress == msg.sender` trivially satisfied) and submits `cancelEmporiumMessage(M, v, r, s)` with higher gas/priority to be mined first.
4. `EmporiumUpgradeable.cancelEmporiumMessage` succeeds and sets `usedMessages[M] = true`.
5. Alice's original transaction is mined afterward; `Hinkal.transact()` → `_externalTransact` → `EmporiumUpgradeable.runAction` → `verifyWallet()` checks `usedMessages[M]` (now `true`) and reverts with `UsedMessage()`, causing Alice's entire proven, signed transaction to fail and her funds/action to be blocked until she generates a brand-new proof with a different `messageSeed`.

    function cancelEmporiumMessage(uint256 emporiumMessage, uint8 v, bytes32 r, bytes32 s) external {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

            keccak256(abi.encode(EMPORIUM_CANCEL_TYPEHASH, emporiumMessage))
