This is confirmed to be a non-issue. The `check_status_cache` / `update_transaction_statuses` ordering described in the question is not the mechanism that prevents double execution — account write-locking is, and it is acquired *before* `check_status_cache` is ever consulted, and held for the entire check→execute→commit lifecycle of the batch.

#No vulnerability found for this question.

**Reasoning:**

Two identical signed copies of the same transaction necessarily share the same writable accounts (at minimum the fee payer, which is always writable) [1](#0-0) . Before any batch reaches `check_transactions_with_processed_slots`/`check_status_cache` (`runtime/src/bank/check_transactions.rs:103-127`), the bank (or scheduler) must acquire per-account locks:

- In the central-scheduler/banking-stage path, `Bank::try_lock_accounts_with_results` takes a global `AccountLocks` mutex via `Accounts::lock_accounts` (`accounts-db/src/accounts.rs:455-474`, `accounts-db/src/account_locks.rs:22-40`) and additionally rejects intra-batch duplicate message hashes outright with `TransactionError::AlreadyProcessed` (`runtime/src/bank.rs:3702-3716`). Cross-batch conflicts on the same writable account fail with `AccountInUse` — exactly demonstrated by `test_bank_process_and_record_transactions_account_in_use` (`core/src/banking_stage/consumer.rs:1565-1639`), which explicitly notes: "with a duplicate transaction, we get a conflict from message hash equality in the batch... with no duplicate, we must take a cross-batch lock on an account to create a conflict."
- In the unified-scheduler/worker-thread path (the concurrency scenario the question raises), `ThreadAwareAccountLocks::try_lock_accounts` (`scheduling-utils/src/thread_aware_account_locks.rs:89-107`) is the gate that determines which thread a transaction batch is even dispatched to; a writable account can only be locked by one thread at a time, so two duplicate transactions sharing a fee payer cannot be scheduled onto two worker threads concurrently — one is held back until the other's batch completes and calls `complete_batch`/`unlock_accounts` (`core/src/banking_stage/transaction_scheduler/scheduler_common.rs:301-318`).

Because this locking happens at the scheduling layer, strictly before dispatch to the workers that call `check_status_checks`/`check_transactions_with_processed_slots` (`core/src/banking_stage/consume_worker.rs:923-940`), the race window described in the question — "both pass `check_status_cache` before either has committed" — cannot occur for two transactions that share a writable account, which any two copies of the *same signed transaction* always do. The second copy is blocked at the lock-acquisition step (returning `AccountInUse`, or simply not being scheduled) well before it ever reaches `check_status_cache`, so the status-cache write ordering gap described in the question is not actually reachable by an unprivileged attacker submitting duplicate signed transactions. Additionally, replay-side entry validation independently rejects intra-entry duplicate message hashes (`ledger/src/blockstore_processor.rs:253-272`), and `test_process_entry_duplicate_transaction` (`ledger/src/blockstore_processor.rs:3728-3781`) confirms `AlreadyProcessed` is returned for duplicate transactions within the same processing unit.         tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {

        // We collect to fully evaluate before taking the account_locks mutex.

            .zip(results)
            .map(|(tx, result)| {

                    .and_then(|_| validate_account_locks(tx.account_keys(), tx_account_lock_limit))
                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

    /// with existing locks. Returns a vector of `TransactionResult` indicating
    /// success or failure for each transaction in the batch.
    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    /// Returns the `ThreadId` if the accounts are able to be locked
    /// for the given thread, otherwise `None` is returned.
    /// `allowed_threads` is a set of threads that the caller restricts locking to.
    /// If accounts are schedulable, then they are locked for the thread
    /// selected by the `thread_selector` function.
    /// `thread_selector` is only called if all accounts are schdulable, meaning
    /// that the `thread_set` passed to `thread_selector` is non-empty.
    pub fn try_lock_accounts<'a>(
        &mut self,
        write_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        read_account_locks: impl Iterator<Item = &'a Pubkey> + Clone,
        allowed_threads: ThreadSet,
        thread_selector: impl FnOnce(ThreadSet) -> ThreadId,
    ) -> Result<ThreadId, TryLockError> {
        let schedulable_threads = self
            .accounts_schedulable_threads(write_account_locks.clone(), read_account_locks.clone())
            .ok_or(TryLockError::MultipleConflicts)?;
        let schedulable_threads = schedulable_threads & allowed_threads;
        if schedulable_threads.is_empty() {
            return Err(TryLockError::ThreadNotAllowed);
        }

        let thread_id = thread_selector(schedulable_threads);
        self.lock_accounts(write_account_locks, read_account_locks, thread_id);
        Ok(thread_id)
    }

    /// Mark a given `TransactionBatchId` as completed.
    /// This will update the internal tracking, including account locks.
    fn complete_batch(&mut self, batch_id: TransactionBatchId, transactions: &[Tx]) {
        let thread_id = self.in_flight_tracker.complete_batch(batch_id);
        for transaction in transactions {
            let account_keys = transaction.account_keys();
            let write_account_locks = account_keys
                .iter()
                .enumerate()
                .filter_map(|(index, key)| transaction.is_writable(index).then_some(key));
            let read_account_locks = account_keys
                .iter()
                .enumerate()
                .filter_map(|(index, key)| (!transaction.is_writable(index)).then_some(key));
            self.account_locks
                .unlock_accounts(write_account_locks, read_account_locks, thread_id);
        }
    }

/// Validate an entry's transactions before scheduling: each transaction's account
/// locks (count and duplicates), and rejection of duplicate message hashes within
/// the entry. Does not take account locks - the unified scheduler orders conflicts.
/// Post-SIMD-83 the duplicate-message-hash check is what rejects an entry that
/// replays the same transaction twice (it no longer conflicts on locks).
fn validate_entry_transactions(
    transactions: &[RuntimeTransaction<SanitizedTransaction>],
    tx_account_lock_limit: usize,
) -> Result<()> {
    let mut batch_message_hashes = AHashSet::with_capacity(transactions.len());

    for transaction in transactions {
        validate_account_locks(transaction.account_keys(), tx_account_lock_limit)?;
        if !batch_message_hashes.insert(transaction.message_hash()) {
            return Err(TransactionError::AlreadyProcessed);
        }
    }

    Ok(())
}
