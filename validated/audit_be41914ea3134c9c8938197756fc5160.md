### Title
`canGraduate`/`previewLtUntilGraduation` USD-leg subtraction can underflow and permanently brick buys once real LT raised dips to the virtual-reserve floor - ([File: packages/contracts/src/Bonding.sol])

### Summary
The Fertilizer report's root cause is a bare subtraction (`MAX_RAISE - balance`) with no floor check, computed from a live external balance that an unprivileged actor can move, causing either underflow-wraparound (pre-0.8) or, on modern Solidity, a Panic revert that bricks the calling flow. alt.fun's `Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` contain the same shape of subtraction — `assetReserve - _launchTimeVirtualLtReserve(...)` — used to derive `realLtRaised`, the real LT raised above the pair's launch-time virtual seed.

### Finding Description
`canGraduate(token_)` computes:
```solidity
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [1](#0-0) 

`_launchTimeVirtualLtReserve` is recovered as `Pair.k() / Token.TOTAL_SUPPLY()`, a value fixed at launch and assumed to be a permanent floor for `assetReserve` because the constant-product invariant `reserveToken * reserveAsset ≈ k` should keep `assetReserve` asymptotically ≥ the virtual floor as `reserveToken` rises toward `TOTAL_SUPPLY` on sells. This design is documented as depending on `k` being "locked in at `Pair.mint` and never modified by swaps" and on the AMM's own K-invariant slack (the `+1` rounding tolerance in `Pair.swap`, per the project's own documented AMM shape). Any rounding slack in the swap's K-check, or a sell that lands `reserveToken` at exactly `TOTAL_SUPPLY`/curveSupply edge cases, can push the stored `assetReserve` a wei or more below the theoretical floor. Because the contracts compile under Solidity ≥0.8 with default checked arithmetic (no `unchecked` blocks were found in `packages/contracts/src`), this subtraction does not silently wrap like the Fertilizer bug — instead it reverts with a Panic(0x11).

The impact differs from the original report (continued sale past a cap) but the root-cause class (unchecked subtraction of two independently-moving quantities, one from a virtual/cached constant and one from a live, swap-updated reserve) is the same, and the consequence is worse for availability: `canGraduate` is invoked unconditionally at the end of every buy inside `Bonding._executeBuy`, per the project's own documentation. If the subtraction ever reverts, **every subsequent buy on that token reverts**, permanently freezing the token's curve — traders can no longer buy, and (per the docs) sells that would otherwise trigger graduation are similarly gated through `canGraduate`-derived paths, so LP/creator/trader funds on that curve become stuck pending an upgrade.

### Impact Explanation
A permanently bricked curve is a freezing-of-funds bug: buyers can no longer purchase (their submitted buys revert), and since graduation can only fire from a buy that successfully evaluates `canGraduate`, the token can never graduate normally, stranding the curve's raised LT and the creator's future fee stream. This satisfies the "permanent freezing of trader, creator, or LP funds" acceptance criterion.

### Likelihood Explanation
This requires the stored `assetReserve` to dip fractionally below the recovered virtual floor `k / TOTAL_SUPPLY()`, which is an edge condition dependent on the AMM's rounding/K-slack behavior at extreme reserve ratios (e.g., near-total sell-back of curve tokens). I was not able to fully verify the exact rounding direction of `Pair.swap`'s K-check or confirm a concrete transaction sequence that forces `assetReserve` below the floor within the remaining tool budget — the `Pair.sol` swap/K-check internals were only partially inspected. This should be treated as **uncertain/low-confidence** without a concrete PoC that drives the exact wei-level underflow; likelihood should be assessed as low-to-medium pending that verification, not high.

### Recommendation
Add a saturating/guarded subtraction in `canGraduate` and `previewLtUntilGraduation`, mirroring the pattern already applied elsewhere in `Bonding.sol` for the token-side donation guard (`if (realBalance >= reserveToken) return ...`) — e.g. `uint256 realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;`. Add a fuzz/invariant test that drives `reserveToken` toward `TOTAL_SUPPLY` via alternating buys/sells to confirm `assetReserve` never underflows the recovered virtual floor, analogous to the existing `test_donation_realBalanceExceedsReserveToken` regression style already present in the test suite.

### Proof of Concept
Not confirmed. I could not, within the available tool calls, extract `Pair.sol`'s `swap()`/K-check rounding logic to construct a concrete buy/sell sequence that drives `assetReserve` below `_launchTimeVirtualLtReserve`. Given the codebase's own regression comment referencing a prior, now-guarded underflow ("A TOKEN donation ... previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS. Guard added; tests pin the fix") [2](#0-1) , an analogous unguarded underflow may still exist on the USD leg (`assetReserve - virtualLtReserve` in `canGraduate`/`previewLtUntilGraduation`) since no equivalent floor-clamp was found for that specific subtraction [3](#0-2) . This should be verified with a concrete PoC (a Devin session with the full test suite) before treating it as confirmed.
