## Title
`begin_auth` builds the OAuth authorization redirect from an unsanitized `shop` parameter, enabling forced OAuth completion — ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the merchant-facing OAuth "authorize" redirect URL directly from the caller-supplied `shop:` argument, with no validation that it is a real Shopify domain. Every other credential-issuing entry point in the same library version (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) was updated to call `Utils::ShopValidator.sanitize!(shop)` before using the shop value, but `begin_auth` (and `auth_base_uri`) were not, leaving a hole in the same defense that `ShopValidator` was introduced to close.

### Finding Description
`begin_auth` takes an arbitrary `shop:` string and passes it straight into `auth_base_uri`, which builds `https://#{shop}/admin/oauth/authorize?...` with no host allow-listing: [1](#0-0) [2](#0-1) 

The library's own documentation instructs implementers to source `shop` from an unauthenticated request header/param and pass it directly to `begin_auth`: [3](#0-2) 

Contrast this with the sibling flows that were hardened with `Utils::ShopValidator.sanitize!` in the same release (see `CHANGELOG.md` #1443): [4](#0-3) [5](#0-4) [6](#0-5) 

`Utils::ShopValidator` exists precisely to prevent an attacker-controlled string being treated as a trusted Shopify host, restricting hosts to `TRUSTED_SHOPIFY_DOMAINS`: [7](#0-6) 

`begin_auth` never calls it, so `auth_route` embeds the app's real `client_id`, requested `scope`, and — critically — the app's real `redirect_uri` (the OAuth callback URL) as query parameters targeting an attacker-chosen host: [8](#0-7) 

The binding that should hold is: `host redirected to for OAuth authorize == a Shopify-trusted domain`. Because `begin_auth` skips `ShopValidator.sanitize!`, the actual invariant becomes `host redirected to == attacker-controlled string`, breaking that equality.

By contrast, the callback validator (`validate_auth_callback`) does not have this exact hole because `auth_query.shop` is covered by the HMAC signature computed with the app's `api_secret_key`, so an attacker cannot forge a `shop` value there without the secret: [9](#0-8) [10](#0-9) 

The vulnerable step is exclusively the unauthenticated, pre-HMAC `begin_auth` redirect construction.

### Impact Explanation
An attacker who can influence the `shop` value passed to `begin_auth` (e.g. via a crafted login link using the pattern shown in the gem's own docs, `shop = request.headers["Shop"]`) causes the merchant's browser to be redirected to `https://attacker-controlled-host/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=<real-app-callback>&state=<nonce>`. Because the attacker's server receives the real `state` nonce and the real callback `redirect_uri`, they can immediately bounce the merchant's browser back to the legitimate app's OAuth callback with a `code`/`hmac` pair that Shopify legitimately signed for a shop the attacker controls (e.g., a free dev store the attacker owns), while reflecting the correct `state`. `validate_auth_callback`'s state and HMAC checks both pass, since the `state` cookie matches and the HMAC is genuinely valid for the attacker's own shop. This binds the merchant's browser session/cookie to the attacker's shop identity rather than the merchant's own store — a forced OAuth completion / session fixation across tenants, one of the explicitly in-scope High-impact categories.

### Likelihood Explanation
The `shop` parameter to `begin_auth` is, per the gem's own documented usage, sourced from unauthenticated request input (a header or query parameter) before any OAuth state exists — no credential or prior authentication is required to trigger this path. The only actor required is a merchant clicking a crafted "install"/login link, which is the standard entry point of the OAuth flow.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain` with an explicit rejection) at the top of `begin_auth`, exactly as done in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, before the value is used in `auth_base_uri`. This closes the gap left when `ShopValidator` was introduced but not applied uniformly across all shop-consuming entry points.

### Proof of Concept
1. App's login controller (per the gem's documented example) does:
   ```ruby
   shop = request.headers["Shop"] # or params[:shop], unauthenticated
   ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
   ```
2. Attacker sends the victim merchant a link that causes this controller to be hit with `shop = "attacker.example"`.
3. `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=<real client_id>&scope=<real scope>&redirect_uri=https://real-app.com/auth/callback&state=<real nonce>"`, and the victim's browser is redirected there, with the legitimate `state` cookie already set in the browser.
4. Attacker's server at `attacker.example` immediately 302-redirects the browser to `https://real-app.com/auth/callback?code=<code from attacker's own real Shopify shop>&shop=<attacker-owned-shop>.myshopify.com&hmac=<valid HMAC for that shop>&state=<the reflected nonce>&host=...`.
5. `validate_auth_callback` sees a valid HMAC (legitimately produced by Shopify for the attacker's own shop) and a matching `state` cookie, and completes OAuth — binding the victim's browser session to the attacker's shop.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```

```ruby
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
```
