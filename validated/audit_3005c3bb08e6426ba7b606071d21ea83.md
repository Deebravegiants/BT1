### Title
Tokens held by the pool above tracked `cash` can never be withdrawn — no sweep path exists — (File: contracts/pool/src/cache/cash.rs)

### Summary
The pool contract treats `cash` as a pure bookkeeping field: every outbound transfer is gated by `debit_cash`/`require_reserves` against the *accounted* `cash` value, never against the real `token.balance()` of the pool address. No function reads the physical balance except `flash_loan`'s strict-equality reconciliation for its own loan leg, and no function (including `claim_revenue`, `recapitalize`, `seize_positions`, `net_settle`) can transfer out the surplus. Any tokens that reach the pool outside an accounting `credit_cash` — a direct token transfer from any user, an inexact-delivery token that transfers more than the measured receipt, or rounding residue — are locked forever, including from the owner.

### Finding Description
`transfer_out` in `contracts/pool/src/cache/cash.rs` sends tokens but explicitly "does not adjust accounting cash" and is only invoked with amounts already validated against `cash` (`debit_cash` calls `require_reserves`, which asserts `self.cash >= amount`). The pool README confirms `cash` is a bookkeeping number whose only reconciliation with `token.balance()` is `flash_loan`'s three strict-equality checks (contracts/pool/README.md lines 61–63) — those checks can fail on a surplus but never release it. `claim_revenue` pays `min(cash, floor(revenue))` (`burn_claimable_revenue`, contracts/pool/src/cache/shares.rs:54–56), so surplus tokens cannot exit as revenue either. There is no `skim`/`sweep`/`recover` entrypoint anywhere in the pool surface (contracts/pool/README.md:67–82 lists all 12 mutators; none moves unaccounted balance).

This mirrors the reported bug class — a balance is held by the contract that the intended flows can never use — but in XOXNO's shape it is worse than the QuailFinance case: there is no owner-includable mechanism (no Merkle-tree equivalent) to retrieve it at all.

### Impact Explanation
Permanent freezing of funds. A direct token transfer to the pool contract — an explicitly permitted unprivileged path per the engagement rules — locks those tokens in the pool address forever. The same applies to legitimate flows that leave a physical surplus: an inexact-delivery / fee-on-transfer token that credits more than `actual_amount`, or a contract address that receives tokens via `claimable_balance`/refund paths, accumulates balance that no entrypoint can distribute to suppliers, borrowers, or revenue.

### Likelihood Explanation
Medium. Any Soroban token holder can `transfer` to the pool address at any time (token transfers require only the sender's auth), and integration teardowns already tolerate nonzero pool residue (`TEARDOWN_POOL_DUST` in tests/integration/flows/teardown.sh:13). Additionally, a surplus doesn't just strand itself — `flash_loan`'s strict-equality reconciliation means surplus physical balance can make the loan's balance assertions misbehave, though the frozen-funds impact stands alone.

### Recommendation
Add a `skim`/`sweep` entrypoint that computes `token.balance(pool) - cash` (per market asset) and transfers the surplus to the owner/accumulator, or explicitly fold surplus detection into `claim_revenue`/`recapitalize`. Alternatively, relax `flash_loan`'s strict equality to `>=` accounting so surplus is at least tolerated, and document that donations are unrecoverable.

### Proof of Concept
1. Deploy pool + controller; user supplies and borrows normally so `cash` tracks `token.balance(pool)`.
2. An unprivileged address calls `token.transfer(sender, pool, X)` directly on the market's `asset_id` token (no controller involvement needed).
3. `token.balance(pool) == cash + X`. Exercise every pool entrypoint: `withdraw`/`borrow` are capped by `cash`; `claim_revenue` pays `min(cash, revenue)`; `repay`/`recapitalize` only refund up to inbound amounts; `flash_loan`'s strict-equality check sees `balance > cash`. No call can emit `X`.
4. `X` remains in the pool address permanently — verified by `token.balance(pool)` unchanged after a full teardown (all positions withdrawn, revenue claimed).
