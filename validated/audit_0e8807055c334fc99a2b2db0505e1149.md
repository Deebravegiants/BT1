### Title
Unbacked cross-chain mint via decimals invariant enforced only at registration time, not at transfer time — (`modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` enforces `erc_decimals >= local_decimals` only once, inside `register_token`/`update_token`. The actual scale factor used on every `send()` and `on_accept()` is computed from `local_decimals` read *live* from `fungibles::metadata::Inspect::decimals(asset_id)` at call time, not from a value frozen at registration. If the underlying local asset's decimals ever legitimately change after registration (a `pallet-assets` metadata concern, independent of this pallet's own `CreateOrigin`), the invariant silently breaks and `convert_to_erc20`/`convert_to_balance` compute a scale factor of `10^0 = 1` instead of the real up/down-scale factor, because both helpers use `erc_decimals.saturating_sub(local_decimals)`, which floors to zero whenever `local_decimals > erc_decimals`.

Both `convert_to_balance` and `convert_to_erc20` compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. This is only correct while `erc_decimals >= local_decimals`. `local_decimals` for a non-native asset is fetched fresh from the `Assets` pallet at call time in both `send()` and `on_accept()`: [3](#0-2) [4](#0-3) 

`Precisions` (the `erc_decimals` recorded for the pair) is fixed at registration/update time and never re-validated against the asset's current decimals. If the asset's decimals metadata is later changed (via `pallet-assets::set_metadata`, which is controlled by that specific asset's own admin/owner — a distinct authority from this pallet's `CreateOrigin`) to a value greater than the registered `erc_decimals`, the invariant is silently violated. From that point on, `saturating_sub` floors to `0`, so both helpers stop scaling at all: `convert_to_erc20` no longer multiplies by the correct `10^(erc_decimals-local_decimals)` up-scale factor, and the raw local balance value is embedded verbatim as the destination chain's ERC-20 `message.amount`.

Critically, the EVM side performs **no independent decimals validation** — `HyperFungibleToken.onAccept` mints `message.amount` directly: [5](#0-4) 
All precision-correctness is trusted to have been enforced on the substrate side. Once the scale factor collapses to `1` instead of the intended `10^(erc_decimals-local_decimals)`, a modest `send()` burn/escrow of local tokens is embedded as a `message.amount` that is off by the full missing scale factor, and the destination `HyperFungibleToken` mints that inflated (or, in the reverse direction on `on_accept`, deflated) amount unconditionally.

### Impact Explanation
This is structurally the same class of bug as the Haven Protocol incident: a conversion/verification step trusted to preserve a fixed exchange rate between two token representations is not re-validated at the point of mint, so a state drift (decimals changing after the rate was fixed) turns into unbacked minting on one side of the bridge relative to what was escrowed/burned on the other. Because `HyperFungibleToken`/`BridgeToken` on the EVM side mint `message.amount` unconditionally with no cross-check against the true backing, the destination chain can end up minting far more (or crediting far less) value than was actually locked on the source chain, i.e., either an unbacked mint (value creation) or a permanent freezing/loss of the difference for legitimate senders — both are High severity outcomes for a production token bridge.

### Likelihood Explanation
Exploitation requires the asset's decimals metadata to increase above the `erc_decimals` value recorded at registration. This is not something the hyper-fungible-token pallet's own governance (`CreateOrigin`) controls — it is controlled by whichever origin owns/administers that specific asset in `pallet-assets`, which can be a separate, less-trusted authority (e.g., an asset creator who registered a foreign asset that governance later wired into the bridge without re-validating precisions). Once that drift occurs, every subsequent `send()`/`on_accept()` call — reachable by any ordinary user via a single signed extrinsic or by any relayer delivering an already-in-flight message — silently uses the broken scale factor. The precondition is a config/administration issue outside this pallet's direct control rather than attacker-supplied malicious input, which lowers but does not eliminate likelihood; the trigger itself (an ordinary transfer) is fully unprivileged.

### Recommendation
- Freeze/snapshot `local_decimals` at `register_token`/`update_token` time (store it alongside `erc_decimals` in `Precisions`) instead of re-reading `Assets::decimals()` live on every `send`/`on_accept`/`on_timeout`.
- Alternatively, re-validate `erc_decimals >= local_decimals` inside `convert_to_balance`/`convert_to_erc20` (or at the call sites) and hard-fail the transfer instead of silently flooring the exponent to zero via `saturating_sub`.
- Add an invariant check/migration hook that detects `Assets::decimals()` drift for already-registered assets and freezes the pallet for that asset until governance re-registers it.

### Proof of Concept
1. Governance registers asset `X` (local decimals = 6 at registration time) for EVM chain `C` with `erc_decimals = 18` via `register_token` — passes the `config.decimals >= local_decimals` check (`modules/pallets/hyper-fungible-token/src/lib.rs:352-355`).
2. `X`'s own `pallet-assets` admin (a different authority than `CreateOrigin`) later calls `set_metadata` to change `X`'s decimals to `24` (a legitimate, permissioned-but-independent action).
3. A user calls `send()` with a small `amount` of `X`. `decimals = 24` is read live (`lib.rs:287-289`); `erc_decimals = 18` is read from `Precisions`. `convert_to_erc20` computes `erc_decimals.saturating_sub(local_decimals) = 18.saturating_sub(24) = 0`, so `erc20_amount = amount` unscaled instead of being divided down by `10^6`.
4. The oversized `message.amount` is delivered and minted verbatim by the destination `HyperFungibleToken.onAccept` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:292-300`), crediting the beneficiary roughly `10^6`× more ERC-20 tokens than the value actually escrowed/burned on the source chain.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
