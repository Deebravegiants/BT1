### Title
Webhook shop-domain and topic headers are not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `Utils::HmacValidator.validate` binds solely to the body bytes. The `shop` and `topic` values that `ShopifyAPI::Webhooks::Registry.process` trusts to route and attribute the webhook to a tenant are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`) that are never included in the signed content.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop` and `topic` are parsed purely from headers, outside the signed payload: [2](#0-1) 

`HmacValidator.validate` only recomputes the signature over `to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used to attribute/process the webhook`. Because only the body bytes are signed, this equality does not hold — the `shop-domain`/`topic` headers can be swapped independently of the signed body.

Since the app's `api_secret_key` (the HMAC signing key for webhooks) is shared across every merchant that installs the app — it is not shop-specific — an attacker can install the app on their own shop (fully unprivileged with respect to any other tenant), trigger a real webhook event, and capture a **genuinely valid** `raw_body` + `hmac` pair signed with the app's secret. Because the header fields are excluded from the signature, the attacker can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` reporting the victim shop as the source, per the documented handler contract: [5](#0-4) 

Any host application logic keyed on `data.shop` (session lookup, tenant-scoped side effects, data writes attributed to a shop) is spoofed by an unprivileged attacker who only needs their own app installation to mint a validly-HMAC'd body.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: an attacker with no access to a victim's credentials, session, or access token can inject webhook events that the host application attributes to an arbitrary victim shop, corrupting per-tenant state or triggering shop-scoped side effects under a false identity — a cross-tenant confusion vulnerability.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial) installer of the app to obtain one valid `(raw_body, hmac)` pair, plus the ability to send arbitrary HTTP headers to the app's public webhook endpoint — both trivially available to an unprivileged internet user, with no dependency on the victim's or app's secret.

### Recommendation
Include the `shop-domain` and `topic` header values (and any other headers the handler relies on for tenant/topic attribution) in the HMAC-signed content, e.g. bind them by hashing `"#{shop}|#{topic}|#{raw_body}"` (or an equivalent canonical, delimiter-safe encoding) instead of `raw_body` alone, so that spoofing the shop or topic invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev/trial store and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sends — both signed with the app's shared `api_secret_key`.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the same `raw_body`/`X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `victim-shop.myshopify.com` from the forged header.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
