## Title
Missing shop-domain validation in `TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the network host that receives the app's `client_secret` directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other OAuth-credential-issuing code path in this gem (`client_credentials.rb`, `refresh_token.rb`, and even the sibling `TokenExchange.migrate_to_expiring_token` method in the very same file) enforces that the destination host belongs to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before building the request. `exchange_token` breaks this identity binding.

### Finding Description
The intended invariant, enforced everywhere else in `lib/shopify_api/auth/`, is:

`host that receives client_id/client_secret == validated member of ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [1](#0-0) [2](#0-1) [3](#0-2) 

In each of these three flows, `Utils::ShopValidator.sanitize!(shop)` is called and its return value (`validated_shop`) — not the raw caller-supplied value — is what gets wrapped in a `Session` and handed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, which builds the URL that the `client_id`/`client_secret` POST body is sent to.

`exchange_token`, however, takes the shop straight from the decoded JWT and skips this step entirely: [4](#0-3) 

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```

`JwtPayload#shop` performs no domain validation whatsoever — it only strips the `https://` prefix from the `dest` claim: [5](#0-4) 

`JwtPayload#initialize` also only checks `aud == Context.api_key`; it never checks `iss` against `/admin` for `exchange_token` (that check, `admin_session_token?`, is only consulted by `shopify_user_id`), and it accepts tokens signed with either the current or `old_api_secret_key`: [6](#0-5) [7](#0-6) 

So the "host validated" side of the equation collapses to "whatever string is in `dest`, minus an `https://` prefix," while the "host receiving `client_secret`" side is that exact unvalidated string. This is precisely the class of bug the report describes generically as trusting an unbound/uncovered field: here the field that ends up controlling where the credential is sent (`dest`) is exempted from the sanitizer that every sibling flow applies.

### Impact Explanation
If `dest` can carry (or be made to carry, e.g. via a non-`/admin` issuer such as the checkout/customer-account token surfaces which are accepted by this same decoder, or via any future change to how `dest` is populated/propagated) a value outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, the gem will construct `https://#{dest_shop}/admin/oauth/access_token` and POST the app's `client_id` and `client_secret` to it — i.e., SSRF carrying the app's credentials to an attacker-influenced host, matching the report's High-impact category ("SSRF with the app's credentials" / "credential leakage"). This is a direct architectural inconsistency versus the three other flows that were explicitly hardened with `ShopValidator.sanitize!`.

### Likelihood Explanation
Exploitation strictly requires a validly-signed JWT (HS256, correct `aud`) whose `dest` value is not constrained to a Shopify domain, since `JwtPayload` performs no format/domain assertion on `dest` beyond stripping a scheme prefix, and `exchange_token` never checks `admin_session_token?`. Given this gem accepts tokens signed by either the current or the rotated-out `old_api_secret_key`, and imposes no domain allow-listing on the resulting request host — unlike its three sibling methods — the missing check is a genuine, reachable code-path gap rather than a purely theoretical one, and it is the exact "host validated vs. host receiving the credential" identity-binding break called out in scope.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session`/`HttpClient`, exactly as done in `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`, and use the validated value both for the session and for the returned `Session.from(shop: ...)`. Additionally consider requiring `admin_session_token?` for this flow, consistent with the rest of the admin-authentication surface.

### Proof of Concept
Conceptual diff illustrating the missing binding:
```ruby
# lib/shopify_api/auth/token_exchange.rb, exchange_token
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
# MISSING: dest_shop = Utils::ShopValidator.sanitize!(dest_shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
# -> POST https://#{dest_shop}/admin/oauth/access_token with client_id + client_secret in body
```
Compare with the sanitized sibling path, which never sends the credential body unless `sanitize!` succeeds: [8](#0-7)
