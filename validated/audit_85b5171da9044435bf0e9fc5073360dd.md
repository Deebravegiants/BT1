### Title
Webhook HMAC verification does not bind the `shop-domain` header, allowing cross-tenant webhook forgery via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over that signable string alone. The `shop` value that the registry hands to the application's webhook handler (`request.shop`, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never part of the signed material. An unprivileged internet user who obtains one legitimate `(body, hmac)` pair — trivially available by installing the app on their own store and triggering any webhook — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the validator will still return `true`.

### Finding Description
`Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and secure-compares it to the received HMAC: [4](#0-3) 

For webhooks, `to_signable_string` is defined as just `@raw_body`: [5](#0-4) 

Meanwhile `shop` is read straight from the (attacker-controlled, unauthenticated at the transport layer) `shopify-shop-domain` header: [6](#0-5) 

`Registry.process` only checks the HMAC over the body, then dispatches the handler using `request.shop`, which is not part of what was signed: [3](#0-2) 

This breaks the intended identity binding: `shop authenticated by HMAC == shop used to key application state/handler logic`. Since the header is outside the signed scope, any `(body, hmac)` pair valid for shop A's webhook can be replayed with shop B's domain in the header and will still pass `HmacValidator.validate`, causing the handler to treat attacker-controlled content as though it originated from shop B.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker can make the app process fabricated webhook events under a victim shop's identity while HMAC validation still succeeds. Depending on how the hosting application's `WebhookHandler` uses `shop` (e.g., `app/uninstalled` cleanup, billing/subscription webhooks, GDPR/customer data webhooks, or any handler that mutates per-shop state keyed by `data.shop`), this enables cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker doesn't control, without needing the app's `client_secret`, access token, or any privileged access — only the ability to trigger and capture one webhook delivery to their own installed instance of the app.

### Likelihood Explanation
Any developer/user who can install the target app on their own (attacker-controlled) Shopify store can trigger any subscribed webhook topic and capture a genuine `(raw_body, hmac)` pair from a normal delivery. Replaying it with a different `shop-domain` header value against the same public webhook endpoint requires no additional secrets and no special access, making this readily reachable by any unprivileged internet user with an app-installable shop.

### Recommendation
Bind the shop identity to the HMAC-verified material, or otherwise cryptographically or out-of-band verify that the `shop-domain` header value matches the shop that Shopify actually delivered the webhook for (e.g., look up the expected shop by webhook_id/topic registration rather than trusting the header value verbatim), and reject webhook processing when they diverge.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a subscribed webhook topic (e.g., `orders/create`).
2. Capture the delivered request: `raw_body`, and headers `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`.
3. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `raw_body` against the secret; `Registry.process` dispatches to the handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, causing the app to act on victim-shop state using attacker-supplied body content.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
