Found the missing consistency check in the Optimism consensus client — unlike every other consensus client examined (BSC epoch/rotation binding, sync-committee period binding, Pharos epoch monotonicity, BEEFY MMR-leaf freshness), `ismp-optimism`'s `verify_consensus` never checks that the incoming `l1_height` (and the L1 state it's read against) is not older than a previously-accepted update, and never rejects a decrease in `finalized_height`.

### Title
Optimism consensus client accepts a stale/regressed L2 finality update with no monotonicity check on `l1_height`/`finalized_height` - ([File: modules/ismp/clients/ismp-optimism/src/lib.rs])

### Summary
`OptimismConsensusClient::verify_consensus` decodes an `OptimismUpdate{ l1_height, proof }`, reads the L1 state commitment at `l1_height`, and verifies either an OP L2 output-oracle proof or a fault-proof-game proof against that L1 state root. Every other consensus proof path in this codebase enforces that an update cannot regress or replay an older attested value relative to the currently trusted consensus state (BSC's `ExpiredUpdate`/epoch-rotation guard, sync-committee's period/slot ordering checks, Pharos's `StaleUpdate`/`EpochRegressed`, BEEFY's `StaleHeight`/MMR-leaf-freshness pinning). The Optimism client has none of that: it never compares `l1_height` (or the resulting output/game finality) against `consensus_state.finalized_height`, and unconditionally overwrites `consensus_state.finalized_height = state.height.height` with whatever the proof reports.

### Finding Description
In `modules/ismp/clients/ismp-optimism/src/lib.rs:159-260`, `verify_consensus`:
1. Decodes the untrusted `l1_height` from the caller-supplied proof.
2. Fetches `host.state_machine_commitment(l1_state_machine_height)` for that L1 height — any L1 height for which a state commitment currently exists satisfies this, including an L1 height *older* than the one used for a prior, already-accepted Optimism consensus update.
3. Calls `verify_optimism_payload` / `verify_optimism_dispute_game_proof` against that (possibly stale) L1 state root.
4. Sets `consensus_state.finalized_height = state.height.height` directly, with **no check that `state.height.height > consensus_state.finalized_height`**, unlike BSC's `ExpiredUpdate` guard at `modules/ismp/clients/bsc/src/lib.rs:88-93` or Pharos's `StaleUpdate` guard at `modules/consensus/pharos/verifier/src/lib.rs:52-57`, or BEEFY's `StaleHeight` guard at `modules/consensus/beefy/verifier/src/lib.rs:112-117`.

This is the direct analog of CVE-2023-30456: nVMX in the referenced CVE failed to cross-check `CR0`/`CR4` consistency between two related pieces of guest-controlled state before trusting them; here, the client fails to cross-check the newly claimed finality height against the previously trusted finality height (and against the L1 height used) before trusting and persisting it. Since an L2-output/fault-game proof that is valid for an *old* L1 checkpoint remains cryptographically valid forever (the L1 state root at that height doesn't change), a relayer can resubmit an old, valid `OptimismUpdate` — say for an L1 height still within the `state_machine_commitment` history, but whose corresponding L2 output is stale/reorged relative to what has already been finalized — and the client will happily roll `finalized_height` backward or replay an old output as if it were newer relative to whatever the pallet's downstream consumers assume monotonic finality means.

### Impact Explanation
`finalized_height` on the Optimism consensus state directly gates `handle_unsigned`/`handle` message processing for the destination OP-stack chain: state membership/non-membership proofs for ISMP request/response delivery and timeouts are checked against `StateCommitmentHeight`s recorded per height. A relayer able to submit a stale/regressed update can:
- Roll back the recorded finality height for the OP-stack chain, reintroducing an already-superseded (or forked) state commitment as the "latest" one, which can be used to forge non-membership proofs for timeouts on requests that were, in reality, already delivered under a later, legitimate state root — leading to double-delivery/double-refund (unbacked mint/duplicate payout) style outcomes on any app built atop this consensus client (e.g. token bridges, intents settlement).
- Grief the state machine into rejecting legitimate newer updates if downstream logic assumes height monotonicity elsewhere (denial of message delivery / "route unable to deliver messages").

This satisfies the required impact bar (forged/duplicated message delivery, unsound state commitment) at Medium-to-High severity, matching the reachable class allowed by the rules (consensus verification path, single relayed proof).

### Likelihood Explanation
Medium. `verify_consensus` is reachable by any unprivileged relayer submitting an unsigned `handle_unsigned` consensus message, exactly like the other consensus clients I found had explicitly hardened against this exact bug class. Exploitation requires only re-submitting (or crafting) a proof for an `l1_height`/L2 output that is behind the currently trusted `finalized_height` — no signing key compromise, no governance/admin action, and no need for new cryptographic material since the proof format itself (L2 output oracle / dispute game proof) is valid independent of freshness.

### Recommendation
Add an explicit staleness/monotonicity guard in `OptimismConsensusClient::verify_consensus`, mirroring the pattern already used everywhere else in the codebase:
```rust
if state.height.height <= consensus_state.finalized_height {
    return Err(OptimismError::StaleUpdate {
        current: consensus_state.finalized_height,
        update: state.height.height,
    }.into());
}
```
placed immediately after `verify_optimism_payload`/`verify_optimism_dispute_game_proof` returns `state`, before `consensus_state.finalized_height` is overwritten, for both the `OpL2Oracle` and `OpFaultProofGames` branches.

### Proof of Concept
1. A relayer submits `OptimismUpdate { l1_height: H1, proof: OpL2Oracle(payload_1) }` where the L1 state at `H1` proves an L2 output at L2 height `N`. The client accepts it, setting `consensus_state.finalized_height = N`.
2. Later, the pallet still has `state_machine_commitment` for an earlier L1 height `H0 < H1` (challenge-period/finality windows keep multiple recent heights available, and nothing purges them synchronously with consensus updates for this client).
3. The relayer resubmits (or crafts) `OptimismUpdate { l1_height: H0, proof: OpL2Oracle(payload_0) }`, a proof that was valid before step 1 and proves an L2 output at height `M < N`.
4. `verify_consensus` fetches the L1 commitment at `H0` (still present), verifies `payload_0` successfully (it is a legitimate proof for that L1 height), and sets `consensus_state.finalized_height = M`, silently regressing the recorded finality height — with no code path in this file rejecting it.
