### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking the HMAC-SHA256 signature of the raw request body only, then trusts the `shop`/`shop-domain` value taken from an unauthenticated HTTP header as the tenant identifier passed to the app's handler. Since the header is not part of the signed data, an attacker who possesses one valid `(body, hmac)` pair (e.g., a webhook Shopify delivered for a shop they control) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value, and the signature check still passes.

### Finding Description
`Webhooks::Registry.process` performs:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method is defined to return only the raw body:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

The `shop` accessor, however, is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

This `shop` value is what gets forwarded to the host application's webhook handler as the tenant identifier:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [4](#0-3) 

Because the HMAC only binds `body → signature` and never binds `shop → signature`, the equality the gem implicitly relies on — "the shop that produced a valid signature == the shop the handler is told the webhook is for" — does not hold. An attacker who owns a development shop can capture a legitimately signed webhook (valid `raw_body` + valid `hmac`, both computed by Shopify with the app's real `client_secret`), then replay that same body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the (attacker-controlled) body to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: the handler receives attacker-influenced webhook payloads while believing they originate from a different merchant/shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up which merchant's records to mutate, or which access token/session to act on), this enables cross-tenant data injection or corruption — an app could update, delete, or misattribute data for shop B based on a payload actually crafted/triggered by the operator of shop A.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a shop they control (which is normal, unprivileged app installation) in order to obtain at least one genuinely-signed `(body, hmac)` pair, then replay it against the same public webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret` or to a victim's credentials is required, and no interaction with the host application beyond calling `ShopifyAPI::Webhooks::Registry.process` is needed, since the gem itself never binds `shop` into the verified data.

### Recommendation
Include the shop domain (and other headers relied upon by the handler, e.g. `topic`, `api-version`) inside the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body before trusting them in `WebhookMetadata`. At minimum, document/enforce that `request.shop` must not be trusted as an authenticated tenant identifier unless it is included in the signable payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook Shopify signs with the app's real `client_secret`, yielding `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same `raw_body = B` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`, lines 26-31) recomputes the HMAC solely from `to_signable_string` (`@raw_body`), matches, and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-199) proceeds and calls `handler.handle` with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, even though the payload/HMAC were generated for `attacker-shop.myshopify.com`.
