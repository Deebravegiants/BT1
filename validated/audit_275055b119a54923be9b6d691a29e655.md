Based on my investigation, I found a genuine analog in the `RequestReplayGuard` used by the Vault gateway/node authorizer.

### Title
JWT/Request Replay Protection Is Purely In-Memory and Reset by Any Process Restart, Allowing Signed Vault Requests to Be Replayed Within Their Validity Window - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
The Vault authorizer's replay protection (`RequestReplayGuard`) is the direct analog of `cooldownWindow`/`unpauseTime` in the report: a security-critical time window meant to guarantee "used once" semantics for a signed, unprivileged-actor-controlled request. Like the TaikoL1 pause bug where a `pauseProving()`/unpause cycle silently reset the state that enforced the contest window, any restart of the process hosting `authorizer` silently resets the in-memory replay-guard map, re-opening the replay window for any previously captured, still-unexpired signed request.

### Finding Description
`NewAuthorizer` constructs a fresh `RequestReplayGuard` with an empty in-memory map on every process start: [1](#0-0) . All replay state lives only in `RequestReplayGuard.seen`, a plain Go map with no persistence backing: [2](#0-1) . `CheckAndRecord` is the sole enforcement point — it rejects a digest only if it is still present in this in-memory map: [3](#0-2) . This guard is invoked once per authorized request, for both allowlist-based and JWT-based auth paths, as the single choke point preventing reuse of an already-authorized request digest before its `ExpiresAt` (JWT `exp` + validation leeway, up to the `jwtValidationLeeway` window) elapses: [4](#0-3) , [5](#0-4) .

This mirrors the report's root cause exactly: a security window (`cooldownWindow` there, the JWT validity/replay window here) is enforced only via mutable, resettable state (pending state transitions there, an in-memory `seen` map here), and any external event that clears/pauses that state (owner's `pauseProving`/unpause there, a process restart/redeploy here) silently reopens the window without re-validating whether it is safe to do so.

An unprivileged client that has captured one valid signed/JWT-authorized Vault request (e.g., by observing network traffic, a compromised intermediary, or simply retaining its own previously-sent request) can replay that exact request again after any restart of the gateway/node process, as long as the JWT `exp` claim (plus leeway) has not yet passed — which for typical clock skew tolerances and long-lived tokens can be a substantial window. The `WorkflowMetadataHandler`'s parallel `jwtReplayCache` for HTTP-trigger JWTs has the identical structural weakness — it is a bare in-memory `map[string]time.Time` seeded fresh on `NewWorkflowMetadataHandler`: [6](#0-5) , [7](#0-6) .

### Impact Explanation
A restart (rolling deploy, crash/OOM recovery, container reschedule, config reload creating a new handler) resets replay protection network-wide with no compensating control. Any previously-observed, unexpired signed Vault request — including mutating operations like `vault.secrets.create`/`update`/`delete` — can be resubmitted and will be re-authorized and re-executed, since owner-binding validation (`validateSecretOwnersMatchAuthorized`) only checks that the digest's *bound* owner matches, not that the request is fresh: [8](#0-7) . This is a concrete request-impersonation/replay bypass of an authentication control on an internet-facing gateway path.

### Likelihood Explanation
Process restarts of gateway/vault node services are routine operational events (deploys, autoscaling, crash recovery) — no attacker action is required to trigger the reset; the attacker only needs to have captured one valid signed request beforehand and wait for/observe a restart, which is a realistic and low-effort precondition.

### Recommendation
Persist replay-guard state (or at minimum a high-water-mark expiry per signer/digest) outside process memory (e.g., a shared datastore or distributed cache) so that restarts do not reset the "already seen" set. Alternatively, bind single-use semantics to a monotonically increasing per-signer nonce/sequence checked against durable storage rather than a fully volatile digest cache.

### Proof of Concept
1. Client sends a valid JWT-authorized `vault.secrets.create` request; `RequestReplayGuard.CheckAndRecord` records `digest -> expiresAt` and the request executes normally.
2. Attacker/observer retains the exact signed request (JWT + payload), whose `exp` is still, say, 10 minutes in the future.
3. Operator performs a routine restart/redeploy of the gateway or vault-node process; `NewAuthorizer` is reconstructed with a brand-new, empty `RequestReplayGuard{seen: map[string]int64{}}` (`core/capabilities/vault/request_replay_guard.go:23-28`).
4. Attacker resubmits the identical captured request before its JWT expires. `CheckAndRecord` finds no matching entry (map is empty) and returns `nil`, so the request is re-authorized and re-executed — a successful replay of an unprivileged client's prior request past intended single-use protection.

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func newJWTReplayCache(cleanupPeriod time.Duration) *jwtReplayCache {
	return &jwtReplayCache{
		cache:         make(map[string]time.Time),
		cleanupPeriod: cleanupPeriod,
	}
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
