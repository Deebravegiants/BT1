### Title
Webhook `shop` header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` — the data that `HmacValidator.validate` authenticates — returns only the raw request body. The `shop-domain` header, which is passed on to webhook handlers as the authoritative tenant identifier, is never included in the signed bytes. Any actor who can obtain one validly-signed webhook body/HMAC pair for the app (e.g. a merchant installing the app, receiving their own webhooks) can replay that exact body+HMAC with a different `shopify-shop-domain` header value, and `Registry.process` will accept it as authentic, handing the handler attacker-controlled tenant attribution for genuinely-signed data.

### Finding Description
`Registry.process` authenticates a webhook purely via:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

and `Request#to_signable_string` is defined as only the raw body: [3](#0-2) 

Meanwhile `Request#shop` is read directly from an unauthenticated HTTP header: [4](#0-3) 

and that unauthenticated value is passed straight into the handler as the tenant identity: [5](#0-4) 

The equality the system implicitly relies on is: `shop authenticated by HMAC == shop delivered to handler`. In reality, `shop authenticated by HMAC` is undefined (HMAC binds only to body bytes), while `shop delivered to handler` is taken from an attacker-controllable header. Because the webhook HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any tenant of the app can capture a legitimately-signed webhook payload for their own shop and resubmit the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting a victim shop's domain in the `shopify-shop-domain` header. `HmacValidator.validate` will still succeed because it never inspects the header, and `WebhookMetadata.shop` will report the attacker-chosen victim domain to the app's handler.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged tenant of a multi-tenant app can make the app's webhook handler believe genuinely-signed data belongs to a different shop. Depending on what the host app's handler does with `WebhookMetadata.shop` (e.g., look up records, credentials, or trigger actions scoped "by shop"), this can lead to cross-tenant data exposure or state corruption purely through this gem's own HMAC-verification/webhook-parsing code, without needing any of the excluded credentials (access token, `client_secret` leakage, etc.) — only knowledge of one's own previously-received legitimate webhook.

### Likelihood Explanation
Any merchant that installs the app already receives real webhooks (body + valid HMAC) for topics they subscribe to. Replaying that exact payload with a modified `shop-domain` header requires no special access beyond normal use of the app as an installed merchant, making this reachable by any unprivileged/low-privilege tenant.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) to the authenticated material — e.g., include the shop domain header in `to_signable_string`, or independently verify that the shop domain in the header matches a shop this specific webhook subscription/HMAC secret is associated with — before trusting it in `WebhookMetadata`.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker (an installed merchant of shop-a, or anyone who intercepted this delivery) POSTs to the app's webhook endpoint with the same raw body `B` and the same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body successfully.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `request.to_signable_string` (`= B`) — this matches `H`, so validation passes.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed B, ...)`, i.e., data intended for `shop-a` is now attributed to `shop-b` inside the app.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
