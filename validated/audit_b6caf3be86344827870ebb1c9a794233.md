## Finding

### Title
Gateway webapi trigger handler fans out unauthenticated, un-allowlisted messages to every DON node before authorization - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The MOOS `pShare` bug accepts UDP input from any source and republishes it downstream carrying the attacker's self-asserted identity, with no authorization gate before the message is propagated and consumed by the rest of the system. The chainlink gateway's webapi-trigger `HandleLegacyUserMessage` path has the analogous shape: it accepts a JSON-RPC message from any internet-facing client whose only requirement is a self-generated ECDSA keypair, and unconditionally forwards it to **every member of the target DON** before any allowlist or rate-limit check is performed, deferring authorization entirely to a later hop.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates payload shape (JSON decoding, timestamp staleness, method name) but explicitly skips authorization: [1](#0-0) 

Right after this comment, the handler builds a request and fans it out to **all** DON members unconditionally: [2](#0-1) 

The caller-facing gateway entrypoint `gateway.ProcessRequest` only requires `msg.Validate()` to succeed — i.e., a syntactically correct message with *any* valid ECDSA signature — before routing to this handler: [3](#0-2) 

`Message.Validate()` derives `Body.Sender` from whatever key signed the message via `ExtractSigner()`; it does not check that signer against any allowlist at the gateway layer: [4](#0-3) 

The real "is this sender authorized for this workflow/trigger" check only happens later, inside the capability itself (e.g., the webapi trigger capability rejects unknown senders with `"unauthorized Sender ..."`): [5](#0-4) 

This gap is acknowledged directly in the test suite for the gateway handler: [6](#0-5) 

The net effect: any unprivileged client that can generate an ECDSA keypair (trivial, requires no registration or credential) can send a signed message to the gateway's public HTTP/WS endpoint, and the gateway will broadcast it to every node in the DON — consuming node-side network/compute resources — *before* any allowlist or per-sender rate limit is applied at the gateway hop, exactly mirroring the "unauthenticated input is trusted/forwarded downstream unconditionally" root cause of the pShare CVE, even though final per-workflow authorization does correctly occur one hop later inside the capability logic.

### Impact Explanation
Because the gateway does not gate on allowlist or per-sender rate limits before fan-out, an unauthenticated remote client can force amplified traffic to every node in a DON with a single self-signed request, repeated at will (self-generated keys are free and unlimited). This is a quota/rate-limit bypass reachable from an unprivileged internet-facing client, and is the closest concrete analog to the report's "accepts input from any source and forwards it downstream" pattern, differing from a full identity-spoofing bug only because the final authorization decision is deferred to (and correctly enforced by) the capability layer rather than being skipped entirely.

### Likelihood Explanation
High: the code path is reachable directly from the internet-facing gateway HTTP endpoint with no prerequisite other than generating an arbitrary ECDSA keypair and signing a well-formed `MessageBody`; the missing gateway-level check is explicitly flagged as an unresolved `TODO` in both the handler and its test file.

### Recommendation
Apply allowlist and per-sender/global rate-limiting checks in `HandleLegacyUserMessage` (and any sibling legacy-message handlers with the same `// TODO: apply allowlist and rate-limiting here` gap) before fanning the message out to DON members, rather than relying solely on the downstream capability to reject unauthorized senders after the DON has already been contacted.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration required).
2. Construct and sign an `api.Message` with `Method: MethodWebAPITrigger`, a valid-looking `TriggerRequestPayload`, and a fresh timestamp, per `msg.Sign(privateKey)` semantics in `core/services/gateway/api/message.go`.
3. POST this as a legacy JSON-RPC request (with `DonID` set) to the gateway's public endpoint, repeated at high volume.
4. Observe that `handler.HandleLegacyUserMessage` forwards the request to every member of `h.donConfig.Members` (`core/services/gateway/handlers/capabilities/handler.go:417-419`) with no allowlist or per-sender rate-limit check at the gateway, before any node ultimately rejects it as `"unauthorized Sender ..."`.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
