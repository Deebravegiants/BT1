### Title
Fee-on-transfer / non-standard ERC20 underlying tokens allow inflated cross-chain transfer amounts, draining the destination lock pool - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom` for the caller-supplied `params.amount`, but never verifies the token balance actually received by the contract before committing `params.amount` into the dispatched ISMP message. On the destination chain, `onAccept` unconditionally releases `message.amount` of the underlying token from its own custody pool. Any underlying token that takes a fee/deflationary cut on transfer (or otherwise delivers less than the nominal amount) lets a caller lock less than `params.amount` on the source chain while the destination side still unlocks the full nominal amount, silently draining the destination-chain reserve.

### Finding Description
In `send()`:
```solidity
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    ...
    IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    ...
    DispatchPost memory request = _buildDispatchPost(params); // encodes params.amount, not actual received
``` [1](#0-0) 

`_buildDispatchPost` encodes `params.amount` directly into the `Message.amount` field that is dispatched cross-chain, with no adjustment for what the contract actually received: [2](#0-1) 

On the receiving chain, `onAccept` trusts `message.amount` completely and unlocks that exact amount from its own token reserve:
```solidity
} else {
    IERC20(_underlying).safeTransfer(beneficiary, message.amount);
}
``` [3](#0-2) 

The identical pattern exists in the upgradeable variant: [4](#0-3) [5](#0-4) 

Unlike `HyperFungibleToken` (the mint/burn variant, where `_burn`/`_mint` operate on the token's own accounting and cannot desync), `WrappedHyperFungibleToken` locks a *separate*, pre-existing ERC20 deployed independently on each chain. This makes the source-side "locked" balance and the destination-side "released" balance two physically distinct pools that must stay in sync via the committed `amount` — exactly the invariant the ZKsync report's analog breaks. Note that this contract's own `IntentGatewayV2.sol` in the same repository already recognizes and defends against this exact bug class by measuring `balanceOf` before/after transfers for fee-on-transfer tokens (see `evm/src/apps/IntentGatewayV2.sol` lines 230-328), confirming the project is aware fee-on-transfer tokens are a real risk that must be explicitly handled — but that mitigation was not applied to `WrappedHyperFungibleToken`.

### Impact Explanation
Any unprivileged user calling `send()` with a fee-on-transfer (or otherwise lossy) `_underlying` token can lock strictly less than `params.amount` on the source chain while the destination `onAccept` releases the full `params.amount` from its independent reserve. Repeated over time, this permanently drains the destination-chain lock pool beyond what was ever actually deposited, causing insolvency of the wrapper's reserve — later legitimate senders/holders on that chain cannot redeem their locked tokens (permanent freezing of funds) while the attacker (or any user of a fee-charging token) extracts more value on the destination chain than they deposited on the source chain (unbacked release, effectively theft of the shared reserve). This is High severity: it can be triggered with a single `send()` transaction by any external caller for any underlying token configured with transfer fees or rebasing/deflationary behavior, and there's no on-chain safeguard preventing an owner from configuring (or a token later upgrading itself into) such behavior.

### Likelihood Explanation
Likelihood depends on whether a deployment's `_underlying` token has fee-on-transfer, rebasing, or otherwise non-1:1 transfer semantics — the owner sets `_underlying` once via `configure()` and it isn't restricted to "vanilla" ERC20 tokens anywhere in the contract or interface. Given many real-world tokens (deflationary/tax tokens, some rebasing tokens) exist and the contract makes no attempt to detect or reject them, this is a realistic misconfiguration/compatibility risk rather than a theoretical one, exactly mirroring the reported ZKsync issue.

### Recommendation
In `send()`, measure the underlying token balance of `address(this)` before and after `safeTransferFrom`, and use the actual delta (not `params.amount`) when building the dispatched `Message`, e.g.:
```solidity
uint256 balBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 received = IERC20(_underlying).balanceOf(address(this)) - balBefore;
// use `received` instead of params.amount when building the dispatch body
```
Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`. Alternatively, explicitly document/enforce (e.g. via a governance-gated allowlist or a runtime balance-delta check that reverts) that only standard, non-fee, non-rebasing ERC20 tokens may be configured as `_underlying`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A and chain B, `configure()`d with `_underlying` set to a fee-on-transfer ERC20 (e.g. one that burns 10% on `transferFrom`), and fund the destination-chain contract's reserve via a prior legitimate transfer.
2. Attacker calls `send({ amount: 1000, ... })` on chain A. `safeTransferFrom` moves only 900 tokens into the contract (100 burned as fee), but `_buildDispatchPost` still encodes `amount: 1000` in the dispatched `Message`.
3. Once delivered, `onAccept` on chain B executes `IERC20(_underlying).safeTransfer(beneficiary, 1000)`, releasing 1000 tokens from chain B's reserve even though only 900 were ever locked on chain A.
4. Repeating this drains chain B's reserve by 100 tokens (10%) per round-trip, eventually leaving it unable to honor other users' legitimate unlocks — matching the "unbacked mint / permanent freezing of funds" impact class.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
