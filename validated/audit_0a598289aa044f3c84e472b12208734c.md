### Title
Webhook `shop-domain`, `topic`, `api-version` and `webhook-id` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all of which are read straight from unauthenticated HTTP headers — to the registered handler. Because none of these header values are part of the signed payload, an attacker who obtains one genuine, validly-signed webhook (trivially available by installing the app on their own store) can freely rewrite the `X-Shopify-Shop-Domain` header to any victim shop and replay the request; the signature still validates and the handler executes with attacker-chosen tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` verifies the HMAC and then immediately trusts these unauthenticated header-derived fields to build `WebhookMetadata`, which is the tenant-identifying object handed to the app's webhook handler: [4](#0-3) 

This breaks the identity binding: `HMAC-verified(raw_body)` ≠ `shop attributed to that body`. The gem verifies bytes (`raw_body`) but acts on bytes (`shop-domain` header) that were never verified — the exact "bytes verified vs. bytes parsed"/"field acted on but not covered by the HMAC" analog called out in the rules.

### Impact Explanation
Any unprivileged internet user who can install the app on their own (attacker-controlled) shop receives genuine, correctly-signed webhook deliveries for that shop. They can capture the raw body + `X-Shopify-Hmac-Sha256` header from one such delivery, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the handler with `shop: <attacker-chosen victim domain>`. Any app logic that uses `WebhookMetadata#shop` to look up sessions, attribute data changes, or make cross-tenant decisions is now operating on forged tenant identity — a cross-tenant access/spoofing condition, which is a Critical-severity impact.

### Likelihood Explanation
The prerequisite (owning any shop that installs the app, or intercepting one delivery) is trivial for any external actor since Shopify apps are typically installable by any merchant, and this is an unprivileged-internet-user scenario per scope. No secrets, tokens, or privileged access are required — only replay of a message the attacker legitimately received for their own tenant.

### Recommendation
Bind the shop/topic/webhook identity to the HMAC signature, or otherwise ensure it cannot be forged: include `shop-domain`, `topic`, `api-version`, and `webhook-id` in the signed material in `Webhooks::Request#to_signable_string`, or independently corroborate the shop header against the shop associated with the session/access token that registered the webhook before dispatching to a handler in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any registered webhook topic and capture the POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent to the app's webhook endpoint.
2. Replay the identical body `B` and header `H` to the same endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` (it only checked `B` against `H`) [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`, i.e., the app processes attacker-supplied data as if it originated from `victim.myshopify.com` [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
