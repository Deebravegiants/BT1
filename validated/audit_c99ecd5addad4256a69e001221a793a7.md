Confirmed: `WebhookMetadata` (`lib/shopify_api/webhooks/webhook_handler.rb:6-12`) carries `shop`, `topic`, `webhook_id`, `api_version` straight from `Request`'s header accessors, and `Request#to_signable_string` only returns `@raw_body`, so none of those header-derived fields are covered by the HMAC that `Registry.process` checks.

### Title
Webhook `shop-domain` (and topic/webhook-id) header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator`, but its `to_signable_string` method returns only the raw request body, never the `shop`, `topic`, `webhook_id`, or `api_version` values that are read from HTTP headers. `Registry.process` trusts `request.shop` for tenant attribution after HMAC validation succeeds, even though `shop` was never part of what the HMAC actually authenticates.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Request`, `to_signable_string` is defined to be only the raw JSON body: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controlled HTTP headers, not from the signed body: [4](#0-3) 

These unauthenticated values are then packaged into `WebhookMetadata` and handed to the app's handler as if they were verified: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header value == shop that produced the HMAC-signed body`. In reality the gem only proves `body == body signed by app_secret`; it never proves `shop header == shop that owns this body`. Anyone who has ever received one genuine, HMAC-signed webhook delivery for their own store (trivial: install the target app on any free Shopify dev/trial store and trigger any webhook topic with attacker-controlled body content, e.g. an order webhook with attacker-chosen line-item/customer fields) can replay that exact `raw_body` + `hmac` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the forged victim domain.

### Impact Explanation
This breaks the shop-authentication boundary the whole webhook mechanism exists to enforce: the app will process attacker-controlled webhook payloads under an arbitrary victim shop's identity. Since most host applications (as the gem's own docs illustrate) key their per-tenant data directly off `data.shop` from `WebhookMetadata`, this enables cross-tenant data injection/corruption — writing or triggering side effects (e.g. order sync, inventory updates, uninstall handling) into a shop's records that the attacker does not own or have installed the app on. This matches the "cross-tenant access" criterion in the Critical impact bucket.

### Likelihood Explanation
The prerequisite (installing a public app on a free/dev Shopify store to obtain one legitimate signed webhook body) is available to any unprivileged internet user for any app that allows open installation, and the webhook receiver endpoint is by design a public, unauthenticated HTTP endpoint. No access token, `client_secret`, or privileged account is required — only observation of one's own legitimately received webhook traffic.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed content that `to_signable_string` returns, or otherwise require the caller to supply and independently cross-check the expected shop for a given webhook against a value obtained from a trusted, authenticated source (e.g. session storage) rather than trusting the unauthenticated header directly. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be used for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body containing attacker-chosen data. Shopify signs it with the app's real `api_secret_key`, producing a legitimate `(raw_body, hmac)` pair delivered with header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures this exact HTTP request.
3. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process attacker-controlled data as belonging to the victim tenant.
