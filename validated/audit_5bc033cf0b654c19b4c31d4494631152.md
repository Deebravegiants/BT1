## Title
Webhook Shop-Domain Spoofing via HMAC Scope Gap — Cross-Tenant Event Forgery (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while the shop identity (`X-Shopify-Shop-Domain` header) that the framework uses to attribute the webhook to a tenant is never covered by the HMAC. Any actor who can obtain one validly-signed webhook payload (trivially done by installing the app on their own store) can replay that exact `body + hmac` pair against the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and `HmacValidator.validate` will accept it.

### Finding Description
The re-entrancy report's underlying lesson is that a function trusted an externally-influenced field/actor identity that wasn't actually bound by the protection mechanism guarding the operation. The direct analog here is an identity-binding gap between what the HMAC signs and what the gem uses as the tenant identifier.

`Webhooks::Request` exposes `shop` from a header, completely independent from the HMAC: [1](#0-0) 

But the value that is actually HMAC-verified is only the raw body: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature strictly over `to_signable_string`, i.e., the body alone — the shop header plays no role in the cryptographic check: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity forwarded to the app's handler, alongside the (HMAC-covered) body: [4](#0-3) 

Equality that should hold but doesn't:
`shop bound by HMAC == shop delivered to handler`

In reality: `shop delivered to handler` is attacker-controlled header data, while `HMAC` only certifies `body`. Any party that can legitimately obtain a `(body, hmac)` pair for topic T (by simply installing the app on their own shop and triggering an event that produces attacker-influenceable body content, e.g. `customers/create`, `orders/create` with attacker-chosen name/email/address fields) can present that exact pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming any other shop that has the app installed. `HmacValidator.validate` returns `true` because the body is unmodified, and `Registry.process` dispatches to the handler with `WebhookMetadata.shop` set to the victim shop while the body content is attacker-chosen.

### Impact Explanation
This breaks the cross-tenant boundary the gem is expected to enforce for webhook dispatch: the `shop` value handed to the application's webhook handler is not cryptographically bound to the payload the app trusts as authentic. A host application using this handler's `shop` to select tenant context/session/database record while trusting `body` content (a very common integration pattern, and the one the gem's own `WebhookMetadata` structure encourages) can be made to write, act on, or emit attacker-supplied data attributed to a victim merchant — i.e., cross-tenant data injection/corruption using forged events.

### Likelihood Explanation
No secrets are required. An attacker only needs to be a legitimate installer of the target app on their own store (a normal, low-privilege interaction any internet user/merchant can do) to receive one real, validly-signed webhook, and then issue a normal unauthenticated HTTP POST to the app's public webhook endpoint with a modified header. This is a low-effort, repeatable exploit path entirely within the unprivileged-internet-user threat model.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie `request.shop` to the verified payload before it is trusted:
- Include the shop domain (and/or topic) in `to_signable_string`, or
- Independently verify that `request.shop` corresponds to a shop for which the app has an active, previously-established session/installation record before invoking the handler, and document this as a mandatory step for consumers of `Registry.process`.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker-shop.myshopify.com"
# and receives a real webhook from Shopify:
raw_body = '{"email":"attacker-controlled@example.com","note":"payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the SAME (raw_body, hmac) pair but swaps the shop header
forged_headers = {
  "x-shopify-topic" => "customers/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation because HmacValidator only checks raw_body:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler invoked with data.shop == "victim-shop.myshopify.com"
#    and data.body == attacker-controlled JSON
```
