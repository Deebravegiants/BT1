### Title
PoA bridge `describeWithdrawal` matches withdrawal status/tx-hash only by `assetId`, mis-reporting completion for a different withdrawal of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal()` in the PoA bridge selects a withdrawal record from the POA API purely by matching `nep141:${near_token_id}` to `withdrawalParams.assetId`, ignoring the withdrawal's index, destination address or amount. The same shortcut exists in `waitForWithdrawalCompletion` in `internal-utils`. When a single NEAR transaction contains more than one withdrawal of the same token (e.g. a user/integrator batches two withdrawals of `btc.omft.near` to two different destination addresses in one call), `describeWithdrawal` can match the wrong entry of the POA API's unsorted `withdrawals` array and report the wrong `txHash`/status for a caller's `WithdrawalIdentifier`.

### Finding Description
`PoaBridge.describeWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, and `findMatchingWithdrawal` (same file, lines 418-427) is documented to only match by `assetId`:

```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// ...
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [1](#0-0) 

The `WithdrawalIdentifier` created by `createWithdrawalIdentifier` carries an `index` field [2](#0-1)  that is meant to distinguish multiple withdrawals produced from the same NEAR transaction, but `describeWithdrawal`/`findMatchingWithdrawal` never consult `index` (or destination address/amount) — they only filter by `assetId` from an API response the code itself calls "unsorted":

```
async describeWithdrawal(
	args: WithdrawalIdentifier & { logger?: ILogger },
): Promise<WithdrawalStatus> {
	const response = await this.getWithdrawalStatusWithRetry(args);
	// Response list is unsorted, so we match by assetId instead of index
	const withdrawal = findMatchingWithdrawal(
		response.withdrawals,
		args.withdrawalParams.assetId,
	);
	...
``` [3](#0-2) 

The equivalent `internal-utils` helper has the identical limitation:
```
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
): ... {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
``` [4](#0-3) 

Because the first matching entry in the (unsorted) `withdrawals` array is always returned regardless of index/destination/amount, if a NEAR transaction issues two or more `ft_withdraw` intents of the same asset (a legitimate, supported use case — the SDK explicitly builds arrays of `IntentPrimitive` per withdrawal and tracks them by `index`), the SDK can return the `txHash`/status belonging to withdrawal #0 when the caller actually asked about withdrawal #1 (or vice-versa), because both withdrawals share the same `assetId` and the matcher stops at the first one found.

### Impact Explanation
This breaks the equality "status/txHash reported == actual on-chain outcome for *this* withdrawal identifier." An integrator polling `describeWithdrawal`/`watchWithdrawal` for withdrawal index 1 of a batch could receive the `txHash` and `completed` status that actually belongs to withdrawal index 0 (or the reverse). Per the rules, "a status or hash misreport making an integrator credit or refund twice" is explicitly listed as a High-impact category. If an integrator uses the reported `txHash`/completion signal to release/settle funds or mark a withdrawal record as fulfilled, a duplicate token+different-destination batch could cause them to mark the wrong withdrawal (or both withdrawals) as completed against a single on-chain event, or miss detecting that one of the two withdrawals is still pending/failed while reporting it complete.

### Likelihood Explanation
The vulnerable condition — two or more withdrawals of the same underlying asset created within a single NEAR transaction — requires no malicious action by an admin, relayer, or bridge operator; it is a normal caller/integrator behavior (e.g., batching payouts to multiple users in one tx via the intents SDK, which builds a list of `IntentPrimitive`s and assigns sequential `index` values per withdrawal). The code's own comment acknowledges the limitation ("Currently only matches by assetId... This means multiple withdrawals of the same token in a single transaction are not supported"), confirming the root cause is real and reachable, though it is a known, documented gap rather than a silent unknown bug.

### Recommendation
`findMatchingWithdrawal` in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` should disambiguate withdrawals of the same asset within one transaction by also matching on `destinationAddress`/`amount` (and consuming matched entries so they aren't reused for a second identifier with the same asset), or by having the POA API return and the SDK consume a stable per-withdrawal index/ordering that ties back to on-chain intent order, instead of returning the first `assetId` match unconditionally.

### Proof of Concept
1. Caller submits one NEAR transaction containing two `ft_withdraw` intents for `nep141:btc.omft.near`: one to `destinationAddress = A`, one to `destinationAddress = B`.
2. SDK builds two `WithdrawalIdentifier`s with `index: 0` and `index: 1`, same `assetId`.
3. Caller calls `describeWithdrawal` for `index: 1` (destination `B`). The POA API returns an unsorted `withdrawals` array where the entry for destination `A` (still pending or with a different `transfer_tx_hash`) appears first.
4. `findMatchingWithdrawal` returns the entry for `A` because it only checks `nep141:${near_token_id} === assetId`; `describeWithdrawal` then reports `{ status: "completed", txHash: <A's tx hash> }` for the query about withdrawal to `B`, even though `B`'s withdrawal may still be pending or use a different `txHash`.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
