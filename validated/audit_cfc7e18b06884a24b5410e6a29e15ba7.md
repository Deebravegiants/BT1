### Title
Unbounded accumulation of `need_take_pnl_pc`/`need_take_pnl_coin` never re-synced to actual vault balance can permanently freeze Deposit/Withdraw/Swap - (File: program/src/processor.rs, program/src/math.rs)

### Summary
The external report's bug class is: a piece of state that a privileged/administrative flow forgets to reset to its "initial" value, so that a subsequent legitimate, unprivileged action becomes permanently unable to succeed for that entity, even though nothing was stolen directly. The closest reachable analog in this AMM is the `need_take_pnl_coin` / `need_take_pnl_pc` bookkeeping fields in `AmmInfo.state_data`, which are incremented on every unprivileged `Deposit`/`Withdraw`/swap call via `calc_take_pnl`, but are only ever reset by the privileged `WithdrawPnl` instruction. Because every unprivileged accounting path (`calc_total_without_take_pnl_no_orderbook`) subtracts these accumulators from the live vault balance using a `checked_sub` that errors on underflow, once the accumulators are not withdrawn in time relative to vault balance (e.g., large LP withdrawals draining the vault), all subsequent Deposit/Withdraw/Swap calls fail permanently with `CheckedSubOverflow`, freezing the pool for every user.

### Finding Description
`calc_take_pnl` [1](#0-0)  is invoked on every `Deposit`, `Withdraw`, and non-V2 swap path. Whenever the pool's real invariant (`pool_pc_amount * pool_coin_amount`) grows past the last recorded `calc_pnl_x * calc_pnl_y`, it increments `amm.state_data.need_take_pnl_pc` and `amm.state_data.need_take_pnl_coin` unboundedly: [2](#0-1) 

These accumulators are only ever cleared to `0` inside `process_withdrawpnl`, which is a privileged, admin/pnl-owner-only instruction: [3](#0-2) 

Every unprivileged instruction that touches the pool (Deposit, Withdraw, `SwapBaseIn`/`SwapBaseOut`, and their V2 variants) computes the "real" tradable liquidity via `calc_total_without_take_pnl_no_orderbook`, which performs a `checked_sub` of these never-decaying accumulators from the *current* vault token balance: [4](#0-3) 

This call site is repeated identically across Deposit [5](#0-4) , Withdraw [6](#0-5) , `SwapBaseIn` [7](#0-6) , `SwapBaseOut` [8](#0-7) , `SwapBaseInV2` [9](#0-8) , and `SwapBaseOutV2` [10](#0-9) .

The analog to the VTVL bug is structural: the field is a "one-directional counter" that is bumped by ordinary, unprivileged user activity but is reset only by a privileged action that the protocol depends on being executed frequently/promptly. If the counter is not reset before it exceeds the current vault balance — which unprivileged LPs can hasten simply by withdrawing large amounts of liquidity (shrinking `amm_pc_vault.amount`/`amm_coin_vault.amount` while `need_take_pnl_*` stays fixed) — then `checked_sub` in `calc_total_without_take_pnl_no_orderbook` returns `None`, which is mapped to `AmmError::CheckedSubOverflow`, and the instruction aborts. Because this check runs unconditionally at the top of every Deposit/Withdraw/Swap handler, every one of those instructions becomes permanently unusable for that pool once triggered — precisely the "cannot re-create/-use" pattern described in the report, except here it is "cannot ever operate on the pool again" rather than "cannot re-claim."

### Impact Explanation
If `need_take_pnl_pc`/`need_take_pnl_coin` ever exceed the corresponding vault's live token balance (achievable by unprivileged LPs draining liquidity via legitimate `Withdraw` calls, since `Withdraw` itself doesn't cap withdrawal against `need_take_pnl_*` headroom before subtracting), then:
- All subsequent `Deposit` calls revert (LPs can never add liquidity again).
- All subsequent `Withdraw` calls revert (remaining LPs' funds become permanently locked in the vaults — this is a fund freeze).
- All subsequent swaps (`SwapBaseIn(V2)`/`SwapBaseOut(V2)`) revert, halting all trading.
- The only theoretical recovery, `WithdrawPnl`, is itself gated by the same `calc_total_without_take_pnl_no_orderbook` call and would also revert with `CheckedSubOverflow` [11](#0-10) , meaning there is no on-chain recovery path once triggered.

This meets the bar of "permanent freezing of user or LP funds" since remaining coin/pc vault balances become permanently unwithdrawable.

### Likelihood Explanation
This requires a combination of organic events rather than a single attacker-controlled transaction: sustained trading volume causing `need_take_pnl_*` to accumulate, combined with large legitimate LP withdrawals shrinking vault balances relative to the accumulators, and the admin/pnl-owner failing to call `WithdrawPnl` frequently enough to keep the accumulators below the shrinking vault balance. It is not directly attacker-triggerable in one transaction with fully attacker-chosen accounts/data the way the four swap/Deposit/Withdraw instructions normally are — it depends on state built up over many prior transactions and on admin cadence. This lowers likelihood relative to a single-transaction exploit, though the structural absence of any invariant enforcing `need_take_pnl_* <= vault_balance` at Withdraw time (or any automatic decay/cap) makes the condition reachable purely through unprivileged Deposit/Withdraw/Swap activity.

### Recommendation
- Enforce an invariant in `process_withdraw` that `withdraw` cannot reduce `amm_coin_vault.amount`/`amm_pc_vault.amount` below `amm.state_data.need_take_pnl_coin`/`need_take_pnl_pc`, or clamp/re-derive `need_take_pnl_*` against the live balance before subtracting.
- In `calc_total_without_take_pnl_no_orderbook`, use `saturating_sub` (or explicitly cap `need_take_pnl_*` to the vault balance) instead of a hard `checked_sub` that aborts the entire instruction, so a bookkeeping overshoot degrades gracefully instead of permanently freezing all pool operations.
- Consider making `WithdrawPnl` reachable/executable even when `need_take_pnl_* > vault balance` (e.g., withdraw `min(need_take_pnl_*, vault_balance)` and reset the remainder or emit a warning) so there is always a recovery path that doesn't itself depend on the same failing invariant.

### Proof of Concept
1. Pool is initialized via `Initialize2`; `need_take_pnl_pc`/`need_take_pnl_coin` start at 0 [12](#0-11) .
2. Unprivileged users trade via `SwapBaseIn`/`SwapBaseOut` over time; each swap that grows the pool invariant increments `need_take_pnl_pc`/`need_take_pnl_coin` through `calc_take_pnl` [2](#0-1) , and the admin/pnl-owner does not call `WithdrawPnl` promptly.
3. An unprivileged LP (or several) calls `Withdraw` to redeem a large fraction of LP tokens, shrinking `amm_coin_vault.amount`/`amm_pc_vault.amount` while `need_take_pnl_*` remains unchanged (Withdraw does not check remaining headroom against `need_take_pnl_*`).
4. Once `need_take_pnl_pc > amm_pc_vault.amount` (or coin analog), the next call to `calc_total_without_take_pnl_no_orderbook` from any Deposit/Withdraw/Swap (including `WithdrawPnl` itself) performs `pc_amount.checked_sub(amm.state_data.need_take_pnl_pc)`, which underflows and returns `AmmError::CheckedSubOverflow` [13](#0-12) , permanently reverting every subsequent instruction against the pool, including the admin-only recovery path.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
