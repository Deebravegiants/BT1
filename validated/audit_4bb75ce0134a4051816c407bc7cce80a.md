### Title
Webhook shop-domain (and topic/webhook-id) headers are trusted for tenant identity without HMAC coverage - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values it exposes to handlers come from unauthenticated HTTP headers that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values (in particular `shop`) to build `WebhookMetadata` passed to the app's registered handler, creating a binding mismatch between "bytes verified" (raw body) and "bytes acted on" (headers).

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header value — it never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` gates on this body-only HMAC check and then forwards the *unverified* header values (`request.shop`, `request.topic`, `request.webhook_id`) directly to the app's handler as trusted tenant identity: [4](#0-3) 

The equality the code implicitly assumes is:
`hmac_valid(raw_body) == hmac_valid(raw_body, shop, topic, webhook_id)`

but only the left side is actually checked. Because the app's api_secret_key is fixed per-app (not per-shop), any merchant who installs the app on their own store legitimately receives webhook deliveries whose body+HMAC pair is valid for that shared secret. Since `shop-domain`, `topic`, and `webhook_id` headers are not part of the signed material, an unprivileged merchant (an installer of the app, not a privileged operator) can capture one of their own genuinely-signed webhook deliveries and re-POST it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header rewritten to reference a different (victim) shop. The HMAC check still passes because it only validates the raw body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the library asserts to the consuming application that a webhook event legitimately originated for shop X, when only the body's authenticity (not its shop attribution) was actually verified. Depending on how the host handler uses `data.shop` (e.g., updating per-shop state, correlating orders/customers, triggering `app/uninstalled` cleanup, or feeding shop-scoped business logic), this can let an unprivileged app-installing merchant inject events attributed to another merchant's shop, corrupting or exfiltrating cross-tenant state — a cross-tenant access issue at the credential/tenant-binding boundary this gem is responsible for enforcing via `HmacValidator`.

### Likelihood Explanation
Exploitability requires only that the attacker be an ordinary, unprivileged merchant capable of installing the app (a normal, low-privilege action already available to any Shopify merchant) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no `api_secret_key`, access token, or other privileged credential is needed, since the shared per-app secret's HMAC validity is body-scoped only. This satisfies the rule's "field acted on but not covered by the HMAC" identity-binding break criterion directly.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., have `to_signable_string`/`HmacValidator` incorporate the canonicalized header values, not just the raw body) so that `Registry.process` cannot be made to attribute a validly-signed body to an attacker-chosen shop/topic/webhook_id.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (ordinary, unprivileged action).
2. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, headers `x-shopify-hmac-sha256: H(B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-webhook-id: W`.
3. Attacker captures this request and replays it to the same public webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-webhook-id`), leaving `B` and `x-shopify-hmac-sha256` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it matches — validation passes [5](#0-4) .
5. The handler is invoked with `WebhookMetadata` whose `shop` is `victim.myshopify.com`, even though the actual signed content originated from and pertains to `attacker.myshopify.com` [6](#0-5) .

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
