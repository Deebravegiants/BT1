### Title
Direct-donation of the launched Token into `Pair` causes an unrecoverable arithmetic-underflow revert in `Router._computeBuy`'s overflow cap, permanently freezing curve inventory and blocking curve sell-out - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's live real balance (`pair.tokenBalance()`) whenever the uncapped constant-product quote would exceed it, then derives `cappedReserveToken = reserveToken - tokensOut`. This subtraction assumes `reserveToken` (the internal virtual reserve tracked in `Pool.tokenReserve`) is always ≥ the live ERC20 balance of the launched token held by `Pair`. An unprivileged attacker can break that assumption with a plain `IERC20.transfer` of the launched Token directly into the `Pair` contract — a path this contest explicitly treats as in-scope — permanently reverting any buy sized to exhaust the remaining curve supply.

### Finding Description
`Router._computeBuy` computes the uncapped output and then re-caps against the real token balance: [1](#0-0) 

`realBalance` comes from `Pair.tokenBalance()`, a raw `IERC20.balanceOf`: [2](#0-1) 

Under normal operation `reserveToken - realBalance` is a protocol-controlled constant equal to `LP_RESERVE` (the 25% of supply that is virtual-only and never held by the pair), so `cappedReserveToken` is always a large positive number and the explicit `OverflowCapDegenerate()` guard (only checking the `== 0` case) is the only expected failure mode: [3](#0-2) 

An attacker can inflate `realBalance` independently of `reserveToken` by buying launched Token on the curve (via `Zap.buy` → `Bonding.buy` → `Router.buy`) and then sending it straight back to the `Pair` address with a bare `transfer`, which the contest scope explicitly allows as a reachable path ("direct ERC20 transfers of a launched Token ... into ... Pair"). This raises `pair.tokenBalance()` above `reserveToken - LP_RESERVE` without touching `_pool.tokenReserve` (only `Pair.swap`, called exclusively by `Router`, mutates that field): [4](#0-3) 

Once the donation exceeds `LP_RESERVE` (250,000,000 ether tokens), any subsequent buy whose uncapped `tokensOut` would exceed the (now inflated) `realBalance` sets `tokensOut = realBalance > reserveToken`, so `cappedReserveToken = reserveToken - tokensOut` underflows and reverts with a raw arithmetic-underflow Panic rather than a handled error. This is precisely the crafted-input crash the CVE describes, adapted to alt.fun's bonding-curve AMM math instead of an HTTP parser. The developers were aware that donations can inflate `realBalance` — `previewLtUntilGraduation` explicitly special-cases it: [5](#0-4) 

but the equivalent handling was never added to `Router._computeBuy`'s cap branch, leaving the underflow path unguarded.

### Impact Explanation
Any buy attempting to purchase the tail end of the curve (a "closing" buy near supply depletion) permanently reverts once the donation is in place. This:
- Permanently freezes the un-sellable remainder of curve token inventory in `Pair` — no `buy()` call can ever drain it, since the cap branch is unconditionally broken for any output size at or above the (now unreachable) real balance.
- Blocks the supply-sellout graduation trigger (`IPair(pair).tokenBalance() == 0` in `Bonding.canGraduate`), since `tokenBalance()` can never reach zero via `buy()` again.
- Denies legitimate large buyers/creators the ability to complete the curve, a concrete freezing of curve inventory reachable purely through unprivileged transactions (`Zap.buy`/`Zap.buyWithPermit` plus a raw `transfer`).

### Likelihood Explanation
High reachability: no privileged role is required. The attacker only needs to (1) buy some amount of the launched Token through the normal curve (`Zap.buy`), and (2) `transfer` that Token balance directly to the `Pair` address — both are ordinary ERC20/Zap operations available to any wallet. The donation size needed (> `LP_RESERVE`, i.e. > 250M of the 750M curve-circulating supply) is large but achievable well before graduation on tokens with low LT price/exchange rate or where the USD graduation threshold is set high relative to curve depth, and is economically rational for an attacker seeking to permanently disable a competing/target token's sell-out path.

### Recommendation
In `Router._computeBuy`, treat `realBalance > reserveToken` the same way `_ltSwapInventory`/`_routerDepositAndDispose` already saturate-subtract elsewhere in the codebase: clamp the cap so `cappedReserveToken` cannot underflow (e.g., `if (tokensOut >= reserveToken) revert OverflowCapDegenerate();` before the subtraction, or saturate `tokensOut` at `reserveToken` first), and/or exclude donated balance from `realBalance` the way `_prepareGraduationLiquidity`/`previewLtUntilGraduation` already exclude LT donations, so a direct-transfer donation of the launched Token can never brick the curve's closing buy.

### Proof of Concept
1. Launch a token via `Zap.createToken`; note `Bonding.getTokenInfo(token).pair`.
2. Attacker calls `Zap.buy(token, usdcAmount, 0, address(0))` repeatedly (or in one large buy) to acquire > `LP_RESERVE` (250,000,000e18) of the launched Token.
3. Attacker calls `Token(token).transfer(pair, purchasedAmount)` — a plain ERC20 transfer directly to the `Pair` contract, inflating `Pair.tokenBalance()` without touching `_pool.tokenReserve`.
4. Any subsequent buyer submits a `Zap.buy` sized so `Router._computeBuy`'s uncapped `tokensOut` exceeds the now-inflated `pair.tokenBalance()` (i.e., an attempt to buy out the remaining real curve supply).
5. `_computeBuy` sets `tokensOut = realBalance` (> `reserveToken`), then computes `cappedReserveToken = reserveToken - tokensOut`, which underflows and reverts with a Solidity Panic instead of `OverflowCapDegenerate`, permanently DoS-ing that buy size and any buy that would fully drain the pair going forward.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```
