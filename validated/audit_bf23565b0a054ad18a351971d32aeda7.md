Audit Report

## Title
Cheap, deposit-refunding HRMP open/cancel-request loop lets a single para spam a victim para's `DownwardMessageQueuePages` with unbounded system notifications, saturating its DMQ and blocking new downward messages - ([File: polkadot/runtime/parachains/src/dmp.rs], [File: polkadot/runtime/parachains/src/hrmp.rs])

## Summary
`Pallet::init_open_channel` in `hrmp.rs` unconditionally injects an `HrmpNewChannelOpenRequest` XCM notification into the *recipient's* DMQ via `Self::send_to_para` → `dmp::Pallet::<T>::queue_downward_message`, without recipient consent, and `cancel_open_request` fully unreserves the sender's deposit and decrements `HrmpOpenChannelRequestCount`, resetting the attacker's per-para outbound-channel quota. This lets an onboarded parachain repeat `init_open_channel(victim, ...)` → `cancel_open_request` to inject one free downward message per cycle toward an arbitrary victim, bounded only by the hard cap `dmq_max_length = MAX_POSSIBLE_ALLOCATION / max_downward_message_size`, since `can_queue_downward_message` only rejects once that hard limit is exceeded.

## Finding Description
`init_open_channel` (`polkadot/runtime/parachains/src/hrmp.rs:1443-1526`) validates only the *caller's* own per-origin limits (`egress_cnt + open_req_cnt < channel_num_limit`), takes a refundable `hrmp_sender_deposit`, and then unconditionally calls `Self::send_to_para` targeting `recipient` with an `HrmpNewChannelOpenRequest` notification — the recipient has no ability to reject or rate-limit this injection. [1](#0-0) 

`cancel_open_request` (`hrmp.rs:1578-1600+`) removes the `HrmpOpenChannelRequests`/`HrmpOpenChannelRequestsList` entry, calls `Self::decrease_open_channel_request_count(channel_id.sender)` to decrement the attacker's quota counter, and unreserves the sender's deposit — fully resetting the attacker's state to allow another iteration at negligible net cost (only extrinsic weight/tx fees). [2](#0-1) 

`send_to_para` forwards directly into `dmp::Pallet::<T>::queue_downward_message`: [3](#0-2) 

`can_queue_downward_message`/`queue_downward_message` in `dmp.rs` only reject a message once the queue's hard cap is exceeded, per the module's own documented design as an "extra defensive measure" against OOM, not a per-sender rate limit: [4](#0-3) [5](#0-4) 

Importantly, I verified that `queue_downward_message` does call `Self::increase_fee_factor(para, serialized_len)` once queue length exceeds `threshold` regardless of message origin (line 319-323), so `DeliveryFeeFactor` congestion pricing is *not* entirely bypassed as the report's Finding Description claims — it applies to any message queued to that para, including HRMP notifications. However, this mechanism only raises the *quoted delivery fee* for future explicit XCM senders using the `Sender`/fee-charging interface; it does not charge or throttle the attacker's own `init_open_channel`/`cancel_open_request` calls, which remain free of any such penalty since HRMP channel management does not go through that fee-charging path. So while one sub-claim in the report (complete bypass of `DeliveryFeeFactor`) is slightly imprecise, the core mechanism — attacker pays no incremental cost for injecting into the victim's queue — holds. [6](#0-5) 

## Impact Explanation
Once `dmq_length(victim)` exceeds `dmq_max_length(max_downward_message_size)`, `can_queue_downward_message` rejects *all* further downward messages to that para, including legitimate governance/XCM messages from unrelated senders, until the victim processes/prunes enough of its backlog via `prune_dmq`. This is a genuine, code-confirmed denial-of-service vector against a specific victim para's downward message channel, temporary and self-healing but sustainable as long as the attacker keeps flooding at or above the victim's drain rate. It is not a fund-loss or consensus-safety bug. [7](#0-6) 

## Likelihood Explanation
The attacker needs only to control a single onboarded parachain able to dispatch `hrmp_init_open_channel`/`hrmp_cancel_open_request` (or the internal `init_open_channel`/`cancel_open_request` calls invoked from XCM `Transact`) — no cooperation from the victim or a second colluding para is required, since the recipient never needs to accept the request. The loop is cheap (deposit refunded on cancel; only extrinsic/UMP throughput and weight limits bound the attack rate) and fully repeatable across blocks. Because `MAX_POSSIBLE_ALLOCATION` is large, saturating a victim's queue requires many iterations across many blocks, but nothing in the current checks (`egress_cnt + open_req_cnt < channel_num_limit`, which is reset by cancellation) prevents sustained repetition.

## Recommendation
Rate-limit or fee-meter HRMP channel-management notification injection independent of the refundable deposit — e.g., charge a small non-refundable fee per `init_open_channel`/`cancel_open_request` cycle, or track open+cancel churn per `(origin, recipient)` pair over a session/time window and cap it so cancellation cannot fully reset the attacker's quota. Additionally, consider applying `DeliveryFeeFactor`-based cost or explicit rate limiting to the HRMP system-notification injection path itself (not just to XCM senders using the `Sender` interface), so repeatedly injecting into an already-congested victim queue becomes progressively more expensive for the originating para.

## Proof of Concept
Integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` style:
1. Register attacker para `A` and victim para `V` via `register_parachain`.
2. Loop N times: `assert_ok!(Hrmp::hrmp_init_open_channel(A_origin, V, cap, size))`; then `assert_ok!(Hrmp::hrmp_cancel_open_request(A_origin, HrmpChannelId{sender:A, recipient:V}))`.
3. After each iteration, assert `Dmp::dmq_length(V)` increases by 1 while the attacker's reserved balance returns to its baseline after cancel (confirming the deposit is fully refunded and net cost is zero apart from tx fees).
4. Continue looping until `Dmp::dmq_length(V) > Dmp::dmq_max_length(max_downward_message_size)`, then assert that a subsequent legitimate `dmp::Pallet::<Test>::queue_downward_message(&config, V, legit_msg)` call returns `Err(QueueDownwardMessageError::ExceedsMaxMessageSize)`.
5. Assert that after `Dmp::prune_dmq(V, N)` (simulating V processing its backlog), the legitimate message can then be enqueued — demonstrating the congestion is real but recoverable, and quantifying the number of spam iterations required.

//! To prevent Out of Memory errors on the `DownwardMessageQueue`, an
//! exponential fee factor (`DeliveryFeeFactor`) is set. The fee factor
//! increments exponentially after the number of messages in the
//! `DownwardMessageQueue` passes a threshold. This threshold is set as:
//!
//! ```ignore
//! // Maximum max sized messages that can be send to
//! // the DownwardMessageQueue before it runs out of memory
//! max_messages = MAX_POSSIBLE_ALLOCATION / max_downward_message_size
//! threshold = max_messages / THRESHOLD_FACTOR
//! ```
//! Based on the THRESHOLD_FACTOR, the threshold is set as a fraction of the
//! total messages. The `DeliveryFeeFactor` increases for a message over the
//! threshold by:
//!
//! `DeliveryFeeFactor = DeliveryFeeFactor *
//! (EXPONENTIAL_FEE_BASE + MESSAGE_SIZE_FEE_BASE * encoded_message_size_in_KB)`
//!
//! And decreases when the number of messages in the `DownwardMessageQueue` fall
//! below the threshold by:
//!
//! `DeliveryFeeFactor = DeliveryFeeFactor / EXPONENTIAL_FEE_BASE`
//!
//! As an extra defensive measure, a `max_messages` hard
//! limit is set to the number of messages in the DownwardMessageQueue. Messages
//! that would increase the number of messages in the queue above this hard
//! limit are dropped.

	pub fn can_queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size
		if Self::dmq_length(*para) > Self::dmq_max_length(config.max_downward_message_size) {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// If the head exists, we assume the parachain is legit and exists.
		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	/// Enqueue a downward message to a specific recipient para.
	///
	/// When encoded, the message should not exceed the `config.max_downward_message_size`.
	/// Otherwise, the message won't be sent and `Err` will be returned.
	///
	/// It is possible to send a downward message to a non-existent para. That, however, would lead
	/// to a dangling storage. If the caller cannot statically prove that the recipient exists
	/// then the caller should perform a runtime check.
	pub fn queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: ParaId,
		msg: DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len();
		Self::can_queue_downward_message(config, &para, &msg)?;

		let inbound = InboundDownwardQueue::<T>::push_back(para, msg)
			.map_err(|_| QueueDownwardMessageError::ExceedsMaxQueueSize)?;
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		// obtain the new link in the MQC and update the head.
		DownwardMessageQueueHeads::<T>::mutate(para, |head| {
			let new_head =
				BlakeTwo256::hash_of(&(*head, inbound.sent_at, T::Hashing::hash_of(&inbound.msg)));
			*head = new_head;
		});

		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len > threshold as u64 {
			Self::increase_fee_factor(para, serialized_len as u128);
		}

		Ok(())
	}
