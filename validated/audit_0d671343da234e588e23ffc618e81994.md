### Title
Unbounded order.inputs array lets a user permanently freeze escrowed funds via undeliverable RedeemEscrow/RefundEscrow messages - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` accepts an `Order` whose `inputs` (and `output.assets`) array length is entirely user-controlled, with no upper bound enforced anywhere in `placeOrder`, `_fillCrossChain`, `_cancelFromSource`, or `_withdraw`. This is the same bug class as the SkyWeaver `mineGolds` issue: a cheap "commit" step (`placeOrder`) allows the user to set up state that a later, more gas-expensive step (`_withdraw`, invoked from `onAccept`/`onGetResponse` during ISMP message delivery) must fully process in one shot, with no cap on iteration count.

### Finding Description
`placeOrder` only checks `order.inputs.length == 0` [1](#0-0)  but never enforces a maximum. The escrow-crediting loop and reduced-input computation both iterate over the full, attacker-chosen `inputsLen` [2](#0-1) [3](#0-2) .

For a cross-chain order, when a solver fills it, `_fillCrossChain` re-posts the *entire* `order.inputs` array as the `WithdrawalRequest.tokens` field of a Hyperbridge `RedeemEscrow` message dispatched to the source chain [4](#0-3) . Likewise, a cancellation dispatches the same unbounded `order.inputs` as a `RefundEscrow`/GET-response payload [5](#0-4) [6](#0-5) .

On the source chain, delivery of that message is a permissionless call to `HandlerV2.handlePostRequests`, which verifies the MMR proof and then calls `host.dispatchIncoming(leaf.request, _msgSender())` [7](#0-6) , which in turn invokes the gateway's `onAccept`. `onAccept` decodes the body and unconditionally calls `_withdraw`, which loops over `body.tokens.length` doing an escrow-balance check and an ERC20/native transfer per entry [8](#0-7) [9](#0-8) . There is no batching, pagination, or partial-processing mechanism for `_withdraw` — the whole array must be processed in a single EVM call inside a single transaction that also carries MMR-proof verification overhead.

This mirrors the reported SkyWeaver pattern exactly: `_commit`-equivalent (`placeOrder`) is cheap relative to the array size because it's a straightforward loop of storage writes/transfers paid for voluntarily by the user, while the later mandatory step (`_withdraw` via `onAccept`, analogous to `mineGolds`) must iterate the same unbounded array but is executed by a third party (the relayer/handler) whose gas budget is bounded by the block gas limit and by tesseract's gas estimation/handling logic, and who has no way to selectively skip entries.

### Impact Explanation
If a user places an order with a sufficiently large number of distinct input tokens (there is no cap, and duplicate tokens are rejected but distinct token addresses are not limited — an attacker can deploy many trivial ERC20 contracts or use many already-existing tokens with dust amounts), the resulting `RedeemEscrow`/`RefundEscrow` message body becomes proportionally large. Delivering it via `HandlerV2.handlePostRequests` requires executing the entire `_withdraw` loop (with external `SafeERC20` calls, i.e. `CALL` opcodes, each ~2600+ gas cold-access plus ERC20 logic) in one transaction, on top of MMR multiproof verification gas. Past a certain input count this transaction can no longer fit under the destination chain's block gas limit, meaning:
- The `RedeemEscrow`/`RefundEscrow` message can never be successfully delivered.
- The escrowed input tokens become permanently locked — the user cannot get a refund (cross-chain cancel path also loops over the same unbounded array), and the solver who filled the order and already paid out the output tokens can never redeem the escrow either.

This is a concrete, permanent freezing-of-funds vulnerability reachable by a single `placeOrder` transaction (unprivileged, one submitted order/escrow), matching the required severity bar (Medium/High/Critical, concrete freezing of funds).

### Likelihood Explanation
The trigger is entirely permissionless and requires only a single `placeOrder` call with a large `inputs` array — no governance, no admin, no relayer/node compromise, and no special privileges. The bug is also self-inflicting in the sense that even a griefer wanting to lock up *their own* funds (or trick a solver into losing outputs while inputs stay stuck) can do it. The barrier is purely economic (gas cost of escrowing N tokens at `placeOrder` time and possibly deploying N cheap ERC20s), which is bounded and can be made arbitrarily low per-token, so the attack is practical.

### Recommendation
Enforce a maximum length on `order.inputs` (and `order.output.assets`) in `placeOrder`, sized so that the worst-case `_withdraw` loop (including SafeERC20 transfer overhead) plus MMR-proof verification always fits comfortably under the target chains' block gas limits. Consider also supporting incremental/paginated withdrawal (processing a subset of `body.tokens` per call) as a defense in depth, so that even an oversized order created before the fix (or one that becomes oversized due to future gas-cost changes) cannot lock funds forever.

### Proof of Concept
1. Attacker deploys `N` minimal ERC20 tokens (or reuses N cheap real tokens) and approves the `IntentGatewayV2` for 1 unit of each.
2. Attacker calls `placeOrder` with `order.inputs` containing `N` distinct `TokenInfo{token, amount:1}` entries and a cross-chain `destination`. This succeeds because only `inputs.length == 0` is checked [1](#0-0) .
3. A solver fills the order on the destination chain via `fillOrder` → `_fillCrossChain`, which dispatches a `RedeemEscrow` `PostRequest` whose body embeds all `N` `TokenInfo` entries [4](#0-3) .
4. A relayer attempts to deliver this request via `HandlerV2.handlePostRequests` on the source chain; `dispatchIncoming` invokes `onAccept` → `_withdraw`, which must loop `N` times performing external token transfers [10](#0-9) . For `N` large enough, this single transaction exceeds the destination (source-of-order) chain's block gas limit and can never be mined.
5. The escrow for the order remains locked forever in `_orders[commitment][token]`: the solver already paid the output tokens and cannot ever claim the input escrow, and cross-chain cancellation (`_cancelFromSource`/`onGetResponse` → `_withdraw`) suffers the identical unbounded-loop problem, so the user cannot recover the inputs either.
