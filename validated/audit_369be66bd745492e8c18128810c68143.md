Based on my investigation, I found a concrete instance of the bug class in `lib/shopify_api/webhooks/request.rb`.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value that the gem hands to the app's `WebhookHandler` (and that apps use to attribute webhook data to a specific merchant/tenant) is read from the `x-shopify-shop-domain` HTTP header, which is completely outside the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. `HmacValidator.validate` verifies exactly that string against the `hmac-sha256` header: ` [2](#0-1) `. Meanwhile `Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, never checked against, or included in, the HMAC-signed material: ` [3](#0-2) `.

`Registry.process` only calls `Utils::HmacValidator.validate(request)` (which checks body integrity) before forwarding `request.shop` straight into the handler as the tenant identity: ` [4](#0-3) `. The documented handler contract explicitly treats `data.shop` as "The shop domain of the webhook" and expects apps to key their per-tenant logic (e.g. `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) off of it, per the gem's own webhook usage docs.

This breaks the intended binding: `HMAC-verified(shop) == acted-upon(shop)`. In reality only `HMAC-verified(body) == acted-upon(body)` holds; the `shop` binding is unauthenticated. An attacker who controls a shop that has this app installed receives genuinely-signed webhook deliveries for their own shop. Because the signature never covers the `shop-domain` header, the attacker can replay that same signed body to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header value — the HMAC check still passes (body is byte-identical and correctly signed), but the app will process the payload as if it belongs to the victim shop.

### Impact Explanation
This qualifies as cross-tenant access (Critical): a webhook payload the attacker legitimately owns (e.g., `orders/create`, `customers/data_request`, `app/uninstalled`) can be attributed to a different merchant's shop domain purely by header manipulation, since the gem's own `process`/`Request` machinery provides no cryptographic binding between the verified body and the shop identity it hands to the app. Depending on how the host app persists or acts on `data.shop` (e.g., updating that shop's local records, triggering per-tenant side effects, or acting on `shop/redact`/`customers/redact` mandatory compliance topics), this can corrupt or leak data across tenant boundaries.

### Likelihood Explanation
Any developer using the gem exactly as documented (`docs/usage/webhooks.md`) is affected, since the vulnerable code path is entirely inside the gem: `Request.new` extraction of `shop` and `Registry.process`'s sole reliance on `HmacValidator.validate(request)`. No access token, API secret, or privileged account is needed by the attacker — only the ability to receive/capture one legitimately-signed webhook body addressed to a shop they control (a normal, unprivileged use of the app) and the ability to POST it to the app's public webhook endpoint with a forged header.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is trusted (e.g., have `to_signable_string` incorporate a canonical representation of the relevant headers, not just `@raw_body`), so that `Registry.process` cannot be fooled into attributing a genuinely-signed body to an attacker-chosen shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets the app register a webhook (e.g. `orders/create`).
2. Shopify sends a legitimately-signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid signature over raw_body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker crafts a new HTTP POST to the same app endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the signature — this passes because `raw_body` and the HMAC are unchanged (` [5](#0-4) `).
6. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)`, i.e., the app processes attacker-controlled body content as if it originated from the victim shop ` [6](#0-5) `.
