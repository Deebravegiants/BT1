### Title
Catastrophic hostile-mint pre-seed caps the HyperSwap rebalance swap at 99% of graduation inventory, letting LP open away from the curve-close price - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding._seedRebalancing` / `_pairRebalance` defend `finalizeGraduation`'s HyperSwap V2 LP seeding against a hostile `pair.mint()` pre-seed by swapping the pool back toward the curve-close ratio before depositing via the router's `addLiquidity(min=1, min=1)`. That rebalance swap is capped at 99% of the graduation's own inventory (`_swapBudget`), and the natspec on `_swapBudget` explicitly acknowledges that for a pre-seed large enough, "the unconstrained `_noFeeSwapInput` [drives] past our per-side budget" so the swap "consumes 100%\[/99%\] of one side," meaning the post-swap pool is left at a ratio still skewed from the curve-close price, not corrected.

### Finding Description
`_seedRebalancing` branches on the relative size of the attacker's pre-existing reserves vs. the cached `(tokensForLP, ltFromPair)`. It only takes the safe direct-mint fallback (`_seedDirectMint`) when **both** sides of the attacker's reserves are below `DIRECT_MINT_PRESEED_BPS` of the target amounts: [1](#0-0) 

Once above that "dust" band on at least one side, it goes into the rebalance path, computing the no-fee swap input `s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn` and capping it at `maxSwap = 99% of the graduation's own inventory on that side`: [2](#0-1) [3](#0-2) 

The swap math itself is: [4](#0-3) 

Critically, `maxSwap` is bounded by `_ltSwapInventory` (Bonding's own LT balance for this graduation, i.e. `ltFromPair`) or by `IERC20(tokenAddress).balanceOf(address(this))` (i.e. `tokensForLP`) — the **entire LP-bound inventory of this graduation**, not an unlimited external budget: [5](#0-4) 

The `_swapBudget` natspec spells out exactly what happens when the attacker's pre-seed is large enough that the required corrective swap `s` exceeds this cap: [6](#0-5) 

When the cap binds, `_pairRebalance` still executes the swap (it only returns `false`/falls back to a direct mint when the *quote* rounds to zero, not when the swap is merely truncated by the budget): [7](#0-6) 

so the pool's post-swap ratio is only *partially* corrected toward the curve-close target. `_routerDepositAndDispose` then deposits the graduation's remaining inventory at whatever ratio the pool is actually at post-swap (the router's `quote()`-based split only avoids the V2 `min()` donation — it does not re-target the curve-close price): [8](#0-7) 

Because the design deliberately reserves this 1% headroom "for the deposit leg [to] always land AND mint non-zero LP" rather than to guarantee price correctness, a sufficiently large hostile mint pre-seed produces exactly the failure mode described in the Jimbos Protocol incident (which the report's rules explicitly flag as the reachable analog: "an LP seeded away from the curve close price"): the permanently-locked HyperSwap LP (`LPLock.recordLock`, one-shot, no rescue path) opens at a price meaningfully off the bonding curve's true close, letting the attacker arbitrage the mispriced pool against the true price once trading resumes, at the expense of the protocol's locked liquidity and post-graduation traders.

### Impact Explanation
This directly matches the "Validate" criteria in the report's own rules: "an LP seeded away from the curve close price." The mis-seeded LP is locked one-shot via `LPLock.recordLock`, which `finalizeGraduation` cannot skip or retry, so the mispricing is permanent for that token's pool — traders who buy immediately post-graduation transact at the skewed price, and the attacker who engineered the pre-seed can extract the resulting arbitrage. This is a concrete loss of trader/LP value, qualifying as at least a Medium/High severity per the class defined in the scan rules (contract-vulnerability-driven imbalanced LP price range, directly analogous to the Jimbos Protocol root cause).

### Likelihood Explanation
Reachable entirely from permissionless, unprivileged actions: an attacker (1) front-runs `factory.createPair(token, lt)` or waits for `finalizeGraduation`'s on-the-fly pair creation, (2) `transfer()`s a large, self-funded quantity of the launched `Token` and the reserve LT to the pair at an extreme ratio, (3) calls `pair.mint(attacker)` to seed hostile reserves whose magnitude is engineered so the corrective `_noFeeSwapInput` swap size `s` exceeds 99% of the graduation's own `tokensForLP`/`ltFromPair` inventory — plausible whenever the attacker's available capital is comparable to or exceeds the curve's raised inventory (the graduation threshold is only ~$9K per the AGENTS.md dual-trigger doc, a modest capital requirement), then (4) calls the permissionless `finalizeGraduation(tokenAddress)` (or lets the keeper call it) to lock in the skewed LP. No privileged role, upgrade, or off-chain component is required.

### Recommendation
Either (a) revert `finalizeGraduation` in the rare case the rebalance-swap cap binds (i.e., surface a `RebalanceBudgetExceeded`-style failure and require a governance/permissioned rescue for that specific catastrophic pre-seed, since the docs already accept brick-resistance is subordinate to price-correctness in this one edge case), or (b) size `maxSwap`/`_swapBudget` against a true no-op/degenerate detection rather than an arbitrary 99%-of-inventory cap, so that when the corrective swap would be truncated, the code falls back to a documented and audited price-preserving disposal path instead of silently depositing at an unquantified residual skew. At minimum, add an explicit bound/test asserting the maximum achievable opening-price deviation under the swap-cap-bound branch, and reduce/remove the current unguarded 1%-headroom assumption if it cannot be shown to keep the deviation within an acceptable bps tolerance for all inventory sizes.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken` with the minimal $20 seed, and let the bonding curve accumulate only the minimum LT needed to reach the ~$9K USD graduation trigger (per `AGENTS.md`'s dual-trigger description), so `pendingGraduation[token].ltFromPair` and `.tokensForLP` are small.
2. Before `finalizeGraduation` is called (phase 1 → phase 2 window, or by pre-creating the pair before phase 1 ever fires), the attacker acquires/mints a quantity of the `Token` and the reserve LT that is a large multiple of `tokensForLP`/`ltFromPair` (feasible because `Token` is freely tradable pre-graduation and the LT is an external liquid asset), `transfer()`s both into the not-yet-liquid HyperSwap pair at a deliberately skewed ratio, and calls `pair.mint(attacker)`.
3. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedRebalancing` detects the reserves are above `DIRECT_MINT_PRESEED_BPS` (so it does not fall back to `_seedDirectMint`), computes `_noFeeSwapInput`, and finds the required swap exceeds `_swapBudget(balanceOf(this))` — per the code's own natspec, the swap consumes the full 99% cap without achieving the target ratio.
4. `_routerDepositAndDispose` deposits the remaining inventory via `addLiquidity(min=1, min=1)` at the still-skewed post-swap ratio; `LPLock.recordLock` locks this LP permanently, and `TokenGraduated` fires with an LP open price measurably off the true curve-close price, which the attacker (or any MEV searcher) then arbitrages against for profit at the expense of the protocol's locked LP value and post-graduation traders.

Note: the exact numeric threshold at which the cap binds (i.e., the precise attacker capital required relative to `ltFromPair`/`tokensForLP` for a given graduation) depends on `_noFeeSwapInput`'s sqrt-based formula and was not independently computed/simulated here — Devin's static review confirms the code path and its documented acknowledgment of the truncation, but a full quantitative bound on the resulting price deviation would require running the existing `test/NoFeeSwapInput.t.sol` / `test/TwoPhaseGraduation.t.sol` fuzz harnesses with an intentionally out-of-band pre-seed, which the ask-only review tools here cannot execute.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
