### Title
Relayer fee balance is zeroed at dispatch time, before the destination-chain disbursement is confirmed, permanently losing the relayer's fee if the withdrawal message fails on delivery - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-relayer::withdraw` reads a relayer's accumulated `Fees` balance, dispatches an ISMP POST request instructing the destination chain to disburse that amount, and *then* unconditionally zeroes the `Fees` entry — all in the same extrinsic, before there is any confirmation that the destination-side disbursement will actually succeed. This mirrors the Derby `pullFunds()` pattern: an accounting variable is decremented based on an *intended* action rather than the *actual, confirmed* result of that action, so a failure or partial completion downstream desyncs the ledger from reality and the underlying funds/credit are unrecoverably lost.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs`: [1](#0-0) 

computes `available_amount` from `Fees::<T>::get(...)`, builds a `WithdrawalParams`/`WithdrawalRequest` body carrying that exact amount, dispatches it via `dispatcher.dispatch_request(...)`, and immediately afterward does:

```rust
Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
```

This zeroing happens purely as a consequence of the dispatch succeeding (i.e., the message was accepted into the outbound queue/MMR) — it has nothing to do with whether the destination chain actually transfers the funds to the beneficiary. The dispatch is set with `timeout: 0` specifically so it never expires and "must eventually" be delivered, but delivery execution is a separate, later step performed by an off-chain relayer and the destination-chain module, and it can fail:

- On the EVM side, `HostManager.onAccept` calls `IHostManager(_params.host).withdraw(withdrawParams)`, which ends in `EvmHost.withdraw`: [2](#0-1) 
  If the host contract's fee-token balance is insufficient, or the beneficiary is a contract that reverts on receiving native value, `safeTransfer`/the native `call` reverts. Per `EvmHost.dispatchIncoming`: [3](#0-2) 
  a reverted `onAccept` call deletes the request receipt "so it can be retried" — but that retry mechanism only protects EVM-local replay bookkeeping; it does nothing to restore the relayer's zeroed `Fees` entry on Hyperbridge, because that state was already wiped in the earlier `withdraw` extrinsic, independent of and prior to this destination-side execution.

- On the Substrate side, `HyperbridgeWithdrawalModule::on_accept` calls `T::Currency::transfer(&RELAYER_FEE_ACCOUNT, &account, amount, Preservation::Expendable)`: [4](#0-3) 
  If `RELAYER_FEE_ACCOUNT` does not hold sufficient balance (e.g., depleted by concurrent relayer withdrawals, or accounting drift), the transfer errors out and the whole message's on-chain handling fails — again with no path back to restoring the relayer's already-zeroed accrual on Hyperbridge.

In both cases, the source-of-truth ledger (`Fees` on Hyperbridge) is mutated to zero *before* the corresponding real-world payment is guaranteed, exactly analogous to Derby's `savedTotalUnderlying -= amountToWithdraw` being applied before/regardless of whether `withdrawFromProtocol` actually delivers `amountToWithdraw`.

### Impact Explanation
Any relayer that races a withdrawal against destination-chain conditions it does not control (insufficient host balance, a hostile/reverting beneficiary contract, or a destination-chain state change between accumulation and delivery) permanently loses its accrued fee: the credit is deleted from `Fees` at dispatch time, but the token transfer that was supposed to realize it can fail non-atomically on delivery. Because `Fees` is the sole source of truth for what a relayer is owed and it is unconditionally zeroed regardless of outcome, this is a permanent, protocol-level loss of relayer funds with no compensating retry or reissue path in the pallet itself. Given the fee-accumulation/withdrawal flow runs continuously and automatically (per `docs/outbound-request-incentivization.md` and the relayer service), the failure condition is reachable by any relayer through the ordinary unsigned `withdraw_fees` extrinsic.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: EVM host contracts don't pre-reserve a "sinking fund" per relayer, so any timing gap between fee accrual and cross-chain disbursement (congestion, host balance mismanagement, governance withdrawal of host revenue via `HostManager`, or a race between multiple relayers withdrawing against the same host balance) can cause the destination-side transfer to revert after the `Fees` entry has already been zeroed on Hyperbridge. No malicious privileged actor is required — an unprivileged relayer submitting the standard, permissionless `withdraw_fees`/`accumulate_fees` unsigned extrinsics is sufficient to trigger the desync.

### Recommendation
Do not zero `Fees` synchronously with dispatch. Instead:
- Keep the relayer's balance "in flight" (e.g., a separate `PendingWithdrawals` map) rather than deleting the accounted amount immediately.
- Only clear/finalize the `Fees` debit once a delivery/receipt confirmation (or equivalent settlement proof) comes back from the destination chain confirming the transfer succeeded.
- On confirmed failure (or via a timeout/retry path), restore the balance to `Fees` so the relayer can re-attempt withdrawal instead of losing the credit permanently.

### Proof of Concept
1. Relayer accrues `Fees[dest_chain][relayer] = X` via `accumulate`.
2. Relayer calls `withdraw_fees` with `dest_chain = EVM chain`. The pallet dispatches `WithdrawalParams{ beneficiary, amount: X, token }` to `HostManager` and immediately sets `Fees[dest_chain][relayer] = 0` (`modules/pallets/relayer/src/withdrawal.rs:177`).
3. Before the relayer delivers the message, the host contract's fee-token balance drops below `X` (e.g., governance drains bridge revenue via `EvmHost.withdraw`/`HostManager` "Withdraw" governance action, or another relayer's withdrawal consumed the balance first).
4. The relayer (or anyone) delivers the ISMP POST to the destination; `HostManager.onAccept` → `EvmHost.withdraw` reverts inside `IERC20.safeTransfer` due to insufficient balance.
5. `EvmHost.dispatchIncoming` catches the revert and deletes only the local `_requestReceipts[commitment]` so the *EVM-side* delivery can be retried — but retrying does not help, because the payout amount (`X`) is fixed in the already-dispatched message body, and there is no mechanism to top up the host balance atomically with the retry.
6. Meanwhile, on Hyperbridge, `Fees[dest_chain][relayer]` is permanently `0`. The relayer has irrecoverably lost `X` in fee credit despite never having received the funds.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
