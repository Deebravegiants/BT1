## Analysis

The CVE describes Vim's omni-completion executing code from an **implicitly-trusted, attacker-plantable context** (the buffer's working directory on `sys.path`) rather than from a properly-scoped, isolated location — turning a "read/complete" action into unintended code execution because state left in a shared/ambient location is picked up by a later, unrelated operation.

The closest reachable analog in Hyperbridge is the **`CallDispatcher`** contract used by `HyperFungibleToken` / `WrappedHyperFungibleToken` (and their upgradeable variants) to execute attacker-supplied cross-chain calldata. It is a single, shared, permissionless contract with no access control on `dispatch()`, and it is documented to *temporarily hold tokens* during composed operations (e.g., "approve then swap"). Any balance or ERC20 allowance left behind in it after one `onAccept` calldata-execution completes is not cleared, isolated, or attributed to a specific caller — it simply sits in the shared contract's storage until the next, entirely unrelated call to `dispatch()` (or a direct call to the approved token) sweeps it. [1](#0-0) 

The dispatcher has no `onlyHost`/ownership guard — anyone can invoke `dispatch()` directly with arbitrary `Call[]` data, and it executes with the dispatcher's own funds/allowances as `msg.sender` context. [2](#0-1) [3](#0-2) 

The documentation itself acknowledges the residual-balance risk as a caller responsibility rather than an enforced protocol invariant: [4](#0-3) 

### Title
Permanent theft of residual funds/allowances left in the shared, permissionless `CallDispatcher` - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a public, access-control-free function used by `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` to execute attacker-supplied `Call[]` payloads embedded in the ISMP `Message.data` field. When a message's `to` recipient is set to the `CallDispatcher` address (the documented pattern for "transfer-and-swap" workflows), tokens are minted/unlocked directly into the dispatcher before its embedded calls run. Because `dispatch()` has no caller restriction and the contract is a single, chain-wide shared instance, any balance or ERC20 allowance that is not fully consumed by the embedded `Call[]` (dust from slippage, an intentionally- or accidentally-crafted `approve` that is larger than what the downstream call consumes, a fee-on-transfer token, or simply a caller who never issues a follow-up spend call) remains inside the dispatcher after the transaction completes. Any unrelated third party can subsequently call `dispatch()` (or, in the allowance case, call the token directly) to sweep those residual funds to themselves.

### Finding Description
`dispatch()` blindly forwards each `Call` in the caller-supplied array to `to.call{value: call.value}(call.data)` with the dispatcher itself as `msg.sender`, with no restriction on who may call `dispatch()` and no bookkeeping of "whose" funds are currently held by the contract: [1](#0-0) 

The token apps route the cross-chain `data` field straight to this shared dispatcher after minting/unlocking tokens to the destination address specified in the message, which — per the documented pattern — can itself be set to the dispatcher's own address so a subsequent call in the same payload can spend those tokens (e.g., `approve` then `swap`): [2](#0-1) 

There is no mechanism ensuring the embedded `Call[]` fully drains whatever balance/allowance it just created, and no reentrancy or ownership guard preventing a later, unrelated caller from invoking `dispatch()` (or calling the approved token contract directly with `transferFrom`) to claim any leftover balance/approval. Because the contract is shared across all bridging users on a chain (a single deployed instance, as documented on the contract-addresses page), residual state from one user's cross-chain message becomes a pool any other user can drain.

### Impact Explanation
This allows theft of funds that were legitimately minted/unlocked to a real user via the bridge but happen to be routed through the shared dispatcher for a multi-step calldata action. Any dust, over-approval, or unconsumed balance is permanently and trustlessly stealable by any third party monitoring the dispatcher's balance/allowances, since `dispatch()` imposes no restriction on the caller or the target of the forwarded calls. This is a concrete theft-of-funds vector reachable by an unprivileged token bridger through the standard, documented "calldata execution" feature.

### Likelihood Explanation
Likelihood is elevated because the vulnerable pattern is the *documented, intended* usage for composable transfer-and-swap flows (`to = CallDispatcher`, `approve` + downstream spend), and the docs explicitly flag the risk ("approvals in the `Call[]` should use exact amounts rather than unlimited allowances") without the protocol enforcing it — leaving safety entirely to how each relayer/user constructs the calldata payload. Any slippage, partial-fill DEX behavior, fee-on-transfer token, or simple misconfiguration in the `Call[]` (or a deliberately crafted "self-approve" payload) creates directly sweepable residue, and sweeping requires no special privilege or timing beyond a subsequent transaction.

### Recommendation
Do not allow the `to`/beneficiary of a cross-chain token transfer to resolve to the shared `CallDispatcher` address, or alternatively make the dispatcher single-use/per-message (e.g., deploy an ephemeral executor per `onAccept` invocation, or require the dispatcher to `require(token.balanceOf(address(this)) == 0)`/revoke residual allowances at the end of `dispatch()`). At minimum, restrict `dispatch()` to be callable only by the token app's `onAccept` flow for the specific message that funded it (e.g., via a one-time capability/nonce), so residual state cannot be claimed by unrelated callers.

### Proof of Concept
1. Attacker (or a normal user, even unintentionally) calls `HyperFungibleToken.send()` on the source chain with `params.to` set to the destination chain's `CallDispatcher` address and `params.data` encoding a single `Call`: `token.approve(attackerAddress, type(uint256).max)` (or any amount) targeting the underlying HFT token.
2. A relayer delivers the message; `onAccept` mints `params.amount` tokens directly to `CallDispatcher`, then executes the embedded `Call[]`, granting `attackerAddress` an allowance over the dispatcher's token balance: [5](#0-4) 
3. `attackerAddress` calls `token.transferFrom(CallDispatcher, attackerAddress, amount)` directly on the token contract to drain the balance — or, more generally, waits for *any other user's* transfer-and-swap message to leave dust/over-approval in the same shared `CallDispatcher` and sweeps that instead.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

            from: message.from,
            to: beneficiary,
            source: string(request.source),

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
