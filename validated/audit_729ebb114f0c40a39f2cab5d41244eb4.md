Audit Report

## Title
Missing `return` after failed `email` claim extraction in OIDC token exchange allows an authenticated session to be created with a corrupted (empty) identity - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, the type assertion `email, ok := claims["email"].(string)` at [1](#0-0)  logs an error and writes an HTTP 500 body via `c.String(...)` when the `email` claim is missing or not a string, but does not `return`. Execution continues into role mapping, session persistence, cookie setting, and session save, all using the zero-value empty `email`.

## Finding Description
The code path is confirmed exactly as described: after ID token signature verification and claims parsing succeed [2](#0-1) , the handler extracts `email` from the raw claims map without validating it against the already-verified `idClaims`, and the failure branch lacks a `return` statement [1](#0-0) . Because Gin does not abort the handler chain on `c.String`, execution proceeds to `IDClaimsToUserRole` (which is independent of `email`), inserts a row into `oidc_sessions` with `user_email=''` [3](#0-2) , and then unconditionally sets the session cookie and saves it [4](#0-3) . This means a valid session cookie is issued and persisted to the `oidc_sessions` table even though the identity extraction step failed — the state/CSRF check and ID token signature verification that precede this code do not protect against this specific defect, since they only validate that the token came from the trusted provider, not that all required claims are present. The same missing-`return` anti-pattern also exists at the `oidc_sessions` insert-error branch [5](#0-4) .

## Impact Explanation
This is a genuine authentication-integrity defect: a session tied to an empty-string email can be created and a working session cookie handed to the browser, regardless of the HTTP status ultimately observed by the client. Any downstream logic keying off `user_email` (audit attribution, per-user lookups, session identification) can be corrupted or collide via this empty identity. This falls within the in-scope "node API authentication / role bypass"-adjacent category as a cross-user/session identity-integrity flaw in the authentication path, though the impact is bounded since the RBAC role is still derived correctly from valid, verified group claims (only the `email` field of the session record is corrupted).

## Likelihood Explanation
The trigger condition is a verified, correctly-signed ID token from the configured trusted OIDC provider that simply lacks the `email` claim (or has an email claim of a non-string type) — a scenario that is plausible without any host/database access or malicious peer involvement, since `email` is an optional standard OIDC claim and legitimately absent for some provider configurations or user accounts. It requires no operator/admin privileges and is reachable through the standard `/signin` → provider redirect → token-exchange flow that any user of the configured IdP can traverse, making it a realistic, non-speculative, unprivileged-triggerable defect in production authentication code.

## Recommendation
Add a `return` immediately after the failed `email` claim assertion to reject the login with an error response:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Also add a `return` after the `oidc_sessions` insertion failure branch to prevent setting a session cookie for a session that failed to persist correctly.

## Proof of Concept
1. Configure `WebServer.OIDC` against an OIDC provider (or a test double implementing the `oidc.Provider`/`oauth2.Config` interfaces) that returns a validly signed ID token containing a valid group claim matching `ReadClaim`/`EditClaim`/etc., but omitting the `email` claim.
2. Drive the flow: `GET /signin` (sets `state`) → simulate provider redirect → `POST` to the token-exchange endpoint with the corresponding `code`/`state`.
3. Observe that `oi.provider.Verifier(...).Verify` succeeds, `claims["email"].(string)` fails the type assertion, and the handler does not return.
4. Confirm via a Go handler integration test that `IDClaimsToUserRole` still returns a role, a row is inserted into `oidc_sessions` with `user_email=''`, `ginSession.Set(webauth.SessionIDKey, ...)` is called, and `ginSession.Save()` succeeds — i.e., a session cookie is issued despite the failed email extraction, confirmable by inspecting the `Set-Cookie` header and the `oidc_sessions` row in the test database.
