Confirmed: `APPROVE_SELECTOR` is defined in `contracts/Constants.sol` but never referenced anywhere else in the codebase — it is dead code, not enforced as a guard in `EmporiumUpgradeable.runAction`.

### Title
Unbounded token approvals from CASE-2 stateless ops in `EmporiumUpgradeable.runAction` let a dangling allowance drain pooled Emporium funds outside Hinkal's balance accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE-2 "Stateless Interaction" branch performs an arbitrary `op.endpoint.call(op.callData)` from Emporium's own context, blocking only the `callHinkalWallet`/`doSendToRelay` selectors. Nothing prevents an op from calling `approve` (either directly on an ERC20 token, or on a router such as Permit2) with an arbitrary spender and amount, and Hinkal's balance-diff accounting (`getBalancesForArray`/`getBalancesForArrayMemory`, `balancesBefore`/`balancesAfter`) only measures token *balances*, never allowance state, so the approval is invisible to and never revoked by Hinkal's checks. That allowance persists on-chain after the transaction, letting the spender later call `transferFrom` (or `Permit2.transferFrom`) completely outside of Hinkal, draining whatever ERC20 balance Emporium is currently holding — a shared pool that may include other users' in-flight funds.

### Finding Description
The claimed broken equality is **AUTHORITY / VALUE CONSERVATION**: `balanceDif == deltaAmountChanges + utxoAmount` is enforced only for the balances measured *within* the same `runAction` call [1](#0-0) . It says nothing about allowance state granted during CASE-2 (`op.endpoint.call{value: op.value}(op.callData)`) [2](#0-1) . The only selectors blocked in this branch are `callHinkalWallet` and `doSendToRelay`; `approve`-type selectors (e.g. `IERC20.approve`, `Permit2.approve`) are not filtered [3](#0-2) . Notably, `APPROVE_SELECTOR` is declared in `contracts/Constants.sol` [4](#0-3)  but is never referenced anywhere else in the codebase, so no code path actually uses it to block or specially handle approvals in `runAction`.

Because `getBalancesForArray`/`getBalancesForArrayMemory` only read `balanceOf`/ETH balance for the listed `erc20TokenAddresses` [5](#0-4) , an `approve()` call produces zero balance delta and passes every check in `Hinkal.transact` and `EmporiumUpgradeable.runAction` unremarked — `balanceDif` stays `0`, satisfying slippage and the balance-equation `require` [6](#0-5) .

Exploit flow:
1. A user (could be the attacker themselves, or anyone whose proof the attacker convinces to include such an op) submits a valid `transact`/`Hinkal.transact` whose `circomData.externalActionData` targets Emporium with a CASE-2 op: `endpoint = <token or Permit2>`, `callData = approve(spender=attacker, amount=MAX_UINT)` (or `Permit2.approve(token, attacker, amount, expiration)`).
2. This op is either signed by an EIP-712 wallet signer via `verifyWallet` (if `stack.signerAddress != 0`) or authorized purely by the ZK proof's `calldataHash` constraint (if `signerAddress == 0`) [7](#0-6) . Either way, once executed, `token.allowance(Emporium, attacker)` is now set and permanently persists — Hinkal has no mechanism to reset it.
3. `runAction` finishes normally: balances before/after are unchanged by `approve`, so all `require`s pass and legitimate UTXOs/commitments are recorded as if nothing unusual happened.
4. At any later point, the attacker calls `token.transferFrom(Emporium, attacker, amount)` (or `Permit2.transferFrom(Emporium, attacker, amount, token)`) directly — a plain external call to the token/Permit2 contract, entirely outside `Hinkal.sol`/`EmporiumUpgradeable.sol`. This drains whatever token balance Emporium currently holds, up to the approved amount, regardless of whose funds are in transit through the shared Emporium contract at that time.

Existing guards fail to catch this because: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the balance/slippage `require`s in `Hinkal.transact` all validate balances and proof-authorized fields for the *current* transaction only [8](#0-7) ; none of them track or constrain allowance state left behind after `runAction` returns. The circuit constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`) similarly only bind token amounts moved within the proven transaction, not allowances granted to third parties for future, unconstrained transactions [9](#0-8) .

### Impact Explanation
An attacker who can get one CASE-2 `approve()` op executed by Emporium (either as their own legitimate user, or as a spender named in someone else's op) gains a standing allowance over Emporium's real ERC20 balance. Since Emporium is a shared contract holding pooled/in-flight balances for many users at once (deposits, swap intermediates, etc.), draining it via `transferFrom`/`Permit2.transferFrom` steals funds that were never authorized to leave to that recipient by any of the victims whose funds happen to be sitting in Emporium at drain time. This is a direct theft of shielded/in-flight user funds not accounted for by any nullifier or proof — matching the **Critical** severity category. It is fully repeatable: each successful approve-op creates a new standing drain vector, and the attacker can re-arm it repeatedly as Emporium's balance refills from other users' activity.

### Likelihood Explanation
Preconditions are modest: the attacker needs the ability to get one `runAction` call through Emporium containing a CASE-2 op whose `callData` is an `approve`-style call — something fully within an unprivileged user's control when submitting their own `transact`, since `externalActionMetadata`/ops are attacker-supplied and only constrained by `calldataHash`/EIP-712 signature that the attacker (as their own signer) controls for their own transaction. No special role, no relay collusion, no oracle assumption is needed. The only timing dependency is that Emporium must hold a nonzero balance of the approved token at drain time, which naturally occurs as other users route deposits/swaps/withdrawals through Emporium.

### Recommendation
In `EmporiumUpgradeable.runAction`'s CASE-2 branch, block any `callData` whose selector is `IERC20.approve`, `IERC20.increaseAllowance`, `Permit2.approve`, `Permit2.permit`, or any other allowance-granting selector (reusing/wiring up the already-declared but unused `APPROVE_SELECTOR` constant, and extending it to cover Permit2-style approvals). Alternatively, force every allowance set during CASE-2 to be revoked to zero at the end of `runAction` (snapshot `allowance(address(this), spender)` before/after each call and require it returns to zero, or explicitly call `approve(spender, 0)` after use), and add allowance-diff accounting mirroring the existing balance-diff loop so the balance equation also constrains outstanding allowances left on Emporium.

### Proof of Concept
Foundry fork test plan:
1. Deploy `EmporiumUpgradeable` (or use fork addresses) with a real ERC20 token and, optionally, the real Permit2 contract at its canonical address.
2. Fund Emporium with token balance representing pooled/in-flight user funds (e.g., via a legitimate deposit flow).
3. Construct a valid `CircomData`/`Dimensions`/proof for a `transact` call whose `externalActionData` invokes Emporium with one CASE-2 `EmporiumOperation`: `endpoint = token`, `invokeWallet = false`, `callData = abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))`. Generate a locally valid proof/signature so `verifyProof`/`verifyWallet` pass.
4. Call `Hinkal.transact(...)` with this data; assert it succeeds and `token.allowance(address(emporium), attacker) == type(uint256).max`, while `balancesBefore == balancesAfter` for that token in `runAction`'s own accounting.
5. As `attacker`, directly call `token.transferFrom(address(emporium), attacker, drainAmount)` with no Hinkal call at all.
6. Assert Emporium's token balance decreases by `drainAmount` with `assertEq` on `token.balanceOf(address(emporium))` before/after, and assert no corresponding nullifier was inserted for `drainAmount` in Hinkal's nullifier tree (`insertNullifiers` never called for this movement), proving the drain is entirely uncounted by Hinkal's proof/nullifier system.

        EmporiumStack memory stack,
        CircomData calldata circomData

            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;

        bytes32 hashedMessage = _hashTypedDataV4(

                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );

            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
