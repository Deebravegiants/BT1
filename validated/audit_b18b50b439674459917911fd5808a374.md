### Title
User enumeration and MFA-status disclosure via distinct error messages on the `/sessions` login endpoint - ([File: core/web/sessions_controller.go])

### Summary
The Operator UI login endpoint (`POST /sessions`) returns the raw, unmodified internal error string from the authentication layer instead of a generic, unified authentication failure message. Depending on whether the submitted email is unregistered, registered with a wrong password, or registered with WebAuthn/MFA enabled, the HTTP response body and status code differ in observable ways, allowing an unauthenticated client to enumerate valid Chainlink node user accounts and their MFA status — the same class of bug as the Shopware Store API login enumeration (CWE-204, GHSA-gqc5-xv7m-gcjq).

### Finding Description
`SessionsController.Create` first fetches WebAuthn data for the submitted email *before* any credential check, then forwards the raw `error` from `CreateSession` straight into the JSON:API error response: [1](#0-0) 

The underlying `orm.CreateSession` (local auth) returns distinct, differently-worded errors depending on the failure reason:
- Unregistered email → the error returned by `FindUser` (e.g. `sql.ErrNoRows`-derived error)
- Registered email, wrong password → `"Invalid password"`
- Case-mismatched/malformed email edge case → `"Invalid email"` [2](#0-1) 

These distinct error values are passed unchanged to `jsonAPIError`, which serializes `err.Error()` into the JSON:API error `detail` field returned to the client, exactly mirroring the Shopware flaw where `CustomerNotFoundException` and `BadCredentialsException` produced distinguishable payloads.

An even stronger oracle exists for accounts with WebAuthn/MFA enabled: if the submitted email has registered MFA tokens, the server takes a completely different, successful-looking branch — returning an HTTP 401 with a JSON-encoded WebAuthn *challenge* payload instead of a generic authentication error, and does so **before** the password is even checked: [3](#0-2) 

This means an attacker can definitively confirm both (a) that an email is registered, and (b) whether that account has MFA enabled, by observing whether the response body contains a WebAuthn challenge versus a generic invalid-credentials message — with no password guessing required.

### Impact Explanation
An unauthenticated attacker hitting `/sessions` can:
1. Enumerate valid Chainlink node operator/API user emails by diffing error text (`"Invalid password"` vs. the not-found error string) — enabling targeted credential stuffing or phishing against node operators.
2. Determine which accounts have WebAuthn/MFA enabled without any credentials, which is valuable reconnaissance for prioritizing attacks (e.g., targeting non-MFA accounts for credential stuffing) and for social-engineering/phishing campaigns tailored to a specific account's security posture.

This does not by itself grant authentication or role bypass, but it materially weakens the authentication boundary by providing a reliable oracle for account existence and MFA state, consistent with the CWE-204 classification of the referenced advisory.

### Likelihood Explanation
The endpoint is unauthenticated and internet-facing (`POST /sessions`) and requires only a single request per probed email to observe a status/response distinction. Rate limiting exists on this route (see `TestSessions_RateLimited`) but it is keyed per email+IP and does not prevent a single-probe enumeration, mirroring the "rate limiting is present but insufficient" observation in the original Shopware report. [4](#0-3) 

### Recommendation
- In `SessionsController.Create`, do not forward the raw authenticator error into `jsonAPIError`. Return a single generic `"invalid credentials"` message and a constant HTTP status for all failure paths (unknown email, wrong password, WebAuthn-required-but-missing).
- In `orm.CreateSession`, normalize `FindUser` "not found" errors to the same generic error used for bad password, so callers cannot distinguish account existence.
- Avoid branching on `GetUserWebAuthn` results in a way that is observable prior to a successful password check; only reveal the WebAuthn challenge after credentials have been validated, or make the “credentials-required” response indistinguishable in timing/shape from a normal failure.

### Proof of Concept
1. Send `POST /sessions` with `{"email":"unknown@example.com","password":"x"}` — observe the error `detail` field (derived from `FindUser`'s not-found error).
2. Send `POST /sessions` with `{"email":"<real-user-email>","password":"wrong"}` — observe `detail: "Invalid password"`.
3. Compare responses: the differing `detail` strings confirm account existence for the real user's email.
4. For an account with WebAuthn/MFA enabled, submit any password for that email and observe the response contains a serialized WebAuthn challenge object rather than an authentication-failure message, confirming both account existence and MFA-enabled status without needing the correct password. Corresponding code path: [5](#0-4)

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)
	defer ts.Close()

	client := clhttptest.NewTestLocalOnlyHTTPClient()
	input := `{"email":"brute@force.com", "password": "wrongpassword"}`

	for range 5 {
		request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
		require.NoError(t, err)

		resp, err := client.Do(request)
		require.NoError(t, err)
		assert.Equal(t, http.StatusUnauthorized, resp.StatusCode)
	}

	request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
	require.NoError(t, err)

	resp, err := client.Do(request)
	require.NoError(t, err)
	assert.Equal(t, 429, resp.StatusCode)
}
