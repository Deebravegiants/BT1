### Title
Unbounded post-launch growth of curve-raised LT (`ltFromPair`) can exceed HyperSwap V2's `uint112` reserve slot at `finalizeGraduation`, permanently bricking graduation and freezing all curve funds - ([File: packages/contracts/src/Bonding.sol])

### Summary
The reported CVE class is an integer-overflow condition triggered by a live, user/attacker-influenceable size parameter (`proto-max-bulk-len`) that is checked only loosely and later drives a fixed-width buffer past its bounds. alt.fun has a structurally identical gap: `Bonding._deployAndSeed` bounds only the *launch-time* virtual LT reserve against the HyperSwap V2 pair's `uint112` reserve ceiling, but never re-checks the *actual* real LT raised by the curve (`ltFromPair`) before depositing it into that same `uint112`-limited pool at `finalizeGraduation`.

### Finding Description
At launch, `_deployAndSeed` computes `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` and explicitly guards it against the HyperSwap V2 pair's fixed-width reserve slot: [1](#0-0) 

```
uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
if (exchangeRate == 0) revert ZeroExchangeRate();
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
// The raised LT reserve peaks at `3 * virtualLtReserve` (curve sell-out) ...
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
```

This bound only protects against a *low launch-time* exchange rate. It says nothing about the LT's exchange rate afterward. `canGraduate`/`previewLtUntilGraduation` compute the *real* LT raised (`ltFromPair`) purely from live pair reserves and the LT's live `exchangeRate()`: [2](#0-1) 

At graduation time, `_prepareGraduationLiquidity` derives `ltFromPair` with no upper bound check at all: [3](#0-2) 

The contract's own comment on `PendingGraduation.ltFromPair` explicitly acknowledges the field is kept as `uint256` (not narrowed) *because* "a malicious LT returning a tiny `exchangeRate` could legitimately push it past 2^128": [4](#0-3) 

This value is later transferred directly into the real HyperSwap V2 pair's `uint112`-width reserve slots at `_seedDirectMint`/`_seedRebalancing`: [5](#0-4) [6](#0-5) 

A real (canonical) UniswapV2/HyperSwap V2 pair's `_update` enforces `require(balance0 <= type(uint112).max && balance1 <= type(uint112).max, ...)`. If `ltFromPair` (real LT deposited on top of any pre-existing HyperSwap reserves) exceeds `type(uint112).max`, every code path in `_seedUniswapV2Direct` (`_seedDirectMint`, `_seedRebalancing`, `_routerDepositAndDispose`) reverts on `mint`/`addLiquidity`, since the whole design assumes `_prepareGraduationLiquidity`'s launch-time headroom bound is still valid — which it is not once the LT's `exchangeRate()` has drifted from its launch-time value.

The path to this state is entirely reachable by unprivileged traders: any unrestricted set of `Zap.buy` calls against a live curve continuously grows the pair's stored `assetReserve` (raw LT units). Because `exchangeRate` is an external, live, rebasing value (per the protocol's own graduation-drift and USD-trigger documentation), a rate that falls well below its launch-time value after the curve has been trading means the same USD-denominated graduation threshold requires proportionally more raw LT units to satisfy — pushing `ltFromPair` toward, and potentially past, `type(uint112).max`, with `Bonding._enforceLaunchDelay`/launch-time `ExchangeRateTooLow` doing nothing to stop it because that check only ran once, at launch, against the *original* rate.

### Impact Explanation
Once phase 1 (`_enterGraduating`) fires, `Lifecycle` flips to `Graduating` and trading freezes permanently on the curve (`Bonding.buy`/`sell` reject non-`Curve` lifecycle). If `finalizeGraduation` then unconditionally reverts because the real HyperSwap pool's `OVERFLOW` guard trips, the token is stuck in `Graduating` forever: no `un-graduate` path exists, `LPLock.recordLock` (a one-shot call) never fires, and all of the curve-raised LT plus the 250M `LP_RESERVE` tokens sitting on `Bonding` are permanently frozen — unreachable by traders, the creator, or LP holders. This is a concrete, permanent freezing-of-funds outcome, matching the CVE's own theme of a configurable/live parameter driving an unguarded value into a fixed-width slot with severe consequences.

### Likelihood Explanation
No privileged action or admin misconfiguration is required — only ordinary unprivileged `Zap.buy` calls over the life of a curve, combined with the LT's exchange rate drifting materially below its launch-time value (which the protocol's own docs describe as an expected, "accepted," live/rebasing behavior of the reserve LT, not a hypothetical). The scenario is more likely to bite tokens paired against volatile or long-decaying leveraged tokens and low-value/long-lived curves, and the protocol's own natspec on `PendingGraduation.ltFromPair` already flags this exact overflow potential as a recognized (if previously "accepted") design gap rather than a purely theoretical edge case.

### Recommendation
Re-validate the graduation-time `ltFromPair` (and any pre-existing HyperSwap reserve it will be summed with) against `type(uint112).max` inside `_prepareGraduationLiquidity`/`finalizeGraduation`, independent of the launch-time `ExchangeRateTooLow` gate, and provide a safe degradation path (e.g., cap the LP deposit and route any un-depositable excess LT to a rescuable location, or allow forced settlement/redemption of a token stuck in `Graduating`) rather than relying on an unconditional revert from the external HyperSwap pair.

### Proof of Concept
1. Launch a token against an LT with `exchangeRate = R0` (passes `ExchangeRateTooLow` at launch since `virtualLtReserve` is small relative to `uint112.max`).
2. Over time / across many `Zap.buy` calls (all from unprivileged traders), the curve accumulates real LT into the pair's `assetReserve`.
3. The LT's live `exchangeRate()` drops substantially below `R0` (a normal, protocol-acknowledged rebasing behavior of the leveraged reserve asset).
4. Because the USD graduation threshold is fixed in USD terms, achieving it now requires proportionally more raw LT units; `ltFromPair` computed in `_prepareGraduationLiquidity` grows toward `type(uint112).max`.
5. `_enterGraduating` fires inline on the threshold-crossing buy, freezing curve trading (`Lifecycle.Graduating`), caching the oversized `ltFromPair`/`tokensForLP` in `pendingGraduation`.
6. Anyone calls `finalizeGraduation` — `_seedDirectMint`'s `IUniswapV2Pair(pair).mint(...)` (or the rebalancing/`addLiquidity` variants) reverts against the real HyperSwap pair's `uint112` `OVERFLOW` guard.
7. `finalizeGraduation` can never succeed for this token; it is permanently stuck in `Lifecycle.Graduating`, and all curve-raised LT plus the 250M `LP_RESERVE` tokens on `Bonding` are frozen with no recovery path.

Note: I could not directly execute or simulate this scenario against a live HyperSwap V2 deployment/mainnet fork from this environment, so the exact numeric threshold at which `ltFromPair` would realistically exceed `type(uint112).max` for a given BounceTech LT's real-world exchange-rate volatility is unverified here and would need to be confirmed via a Foundry fork test before treating this as fully proven in production conditions.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
