### Title
Unprivileged `TransferToGasKey` action lets anyone front-run and block `DeleteAccount`/`DeleteKey` by forcing `GasKeyBalanceTooHigh` - (File: `runtime/runtime/src/actions.rs`)

### Summary
`check_actor_permissions` explicitly exempts `Action::TransferToGasKey` from the actor-equals-account check that gates self-only actions like `DeleteAccount`, meaning any account can send a receipt that deposits funds into another account's existing gas key. [1](#0-0)  Because `action_delete_key`/`action_delete_account` reject deletion when a gas key's balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), an attacker can watch the mempool for a victim's `DeleteKey`/`DeleteAccount` transaction and front-run it with a `TransferToGasKey` deposit that pushes the gas key's balance above the burn cap, causing the victim's transaction to fail with `GasKeyBalanceTooHigh`.

### Finding Description
The DYAD bug allowed any address to front-run a "remove" action by depositing a small amount into the victim's position, since the removal path required the position/vault to be empty of assets, and deposits into another party's position were permissionless.

Nearcore has a directly analogous unprivileged-deposit-blocks-removal pattern involving gas keys (NEP-591 prepaid-balance access keys):

1. `action_transfer_to_gas_key` in `runtime/runtime/src/access_keys.rs:257-288` looks up the target account's gas key purely by `account_id` + `public_key` and adds `action.deposit` to `gas_key_info.balance` — there is no check that the caller is the account owner.
2. `check_actor_permissions` in `runtime/runtime/src/actions.rs` is the function responsible for enforcing "must be your own account" for sensitive actions such as `DeleteAccount` (`actor_id != account_id` → `ActorNoPermission`), but `Action::TransferToGasKey` is grouped with `CreateAccount`/`FunctionCall`/`Transfer` in the no-op branch that performs *no* actor check at all. [2](#0-1) 
3. Both `delete_gas_key` (invoked from `DeleteKey`) and `action_delete_account` (invoked from `DeleteAccount`) reject the operation if a gas key's balance is above `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), returning `GasKeyBalanceTooHigh` and leaving the key/account intact:
   - `delete_gas_key`: `runtime/runtime/src/access_keys.rs:103-111`. [3](#0-2) 
   - `action_delete_account`: sums *all* gas-key balances on the account via `compute_gas_key_balance_sum` and fails the whole `DeleteAccount` if the sum exceeds the 1 NEAR cap, per `runtime/runtime/src/actions.rs:354-363`. [4](#0-3) 

Since gas-key public keys are discoverable via RPC (`ViewGasKeyNonces`/access-key queries) and a transaction's actions/receiver are visible in the mempool before inclusion, an attacker can:
- Observe a pending `DeleteKey` (targeting a gas key) or `DeleteAccount` transaction from the victim.
- Submit a cheap `TransferToGasKey` transaction targeting the same account/public key with a deposit that pushes the gas key balance above 1 NEAR (e.g., topping off a key that is already near the threshold).
- Cause the victim's deletion transaction to fail with `GasKeyBalanceTooHigh`, exactly mirroring the DYAD "dust deposit blocks removal" pattern.

### Impact Explanation
This is a griefing/DoS vector, not fund theft: the victim cannot delete a gas key or their entire account as long as an attacker keeps topping up any gas key above the burn threshold. For `DeleteAccount`, this can permanently block account closure/beneficiary refund since the check sums *all* gas keys on the account, so an attacker only needs to inflate one key's balance. Repeated dust transfers are cheap (bounded by NEAR's low gas price and TransferToGasKey deposit costs) relative to the friction imposed on the victim, similar to the "almost no cost" characterization in the original report.

### Likelihood Explanation
Requires: (a) the victim account to actually have a gas key with a known public key (gas keys are an intentional multi-key gas-payment feature, discoverable on-chain), and (b) mempool visibility of the victim's `DeleteKey`/`DeleteAccount` transaction, which is standard on any public network. No validator or privileged role is needed — the `TransferToGasKey` action is reachable by any unprivileged account sending an ordinary transaction. The exploit is deterministic once the pre-conditions are met (gas key balance strictly compared against a fixed 1 NEAR constant), so likelihood is moderate: it requires knowledge that gas keys are in use and are near the threshold, or a griefer willing to fund a large one-time top-up.

### Recommendation
Restrict `TransferToGasKey` to self-only interactions, matching the treatment of `DeleteAccount`/staking-style state mutations: require `actor_id == account_id` in `check_actor_permissions` for `Action::TransferToGasKey` (and audit `WithdrawFromGasKey` similarly, though that action already implicitly requires signer permission via the access-key verification path for the *nonce_index* used to sign it — it should be confirmed that no delegated/relayed path allows a third party to invoke it against another account). Alternatively/additionally, reconsider gating deletion (`DeleteKey`/`DeleteAccount`) on gas-key balance thresholds so that a third party depositing funds cannot itself become a blocking condition — e.g., allow the account owner to force-burn/close a gas key above the cap rather than unconditionally rejecting deletion.

### Proof of Concept
Conceptual reproduction using existing nearcore test infrastructure (`test-loop-tests/src/tests/gas_keys.rs` already exercises `Action::TransferToGasKey` and `delete_gas_key`/`action_delete_account` gas-key-balance checks, e.g. `test_delete_gas_key_balance_too_high` / `test_delete_account_gas_key_balance_too_high` in `runtime/runtime/src/access_keys.rs:1218-1332`): [5](#0-4) 

1. Victim account `victim.near` creates a gas key `gas_key` via `AddKey` with `AccessKey::gas_key_full_access(n)`.
2. Victim funds it lightly (e.g., 0.5 NEAR) via `Action::TransferToGasKey`.
3. Victim broadcasts a `DeleteKey { public_key: gas_key }` (or `DeleteAccount`) transaction to remove the key/account.
4. Attacker, observing the mempool, submits `Action::TransferToGasKey { public_key: gas_key, deposit: 0.6 NEAR }` targeting `victim.near`'s account with a higher gas price / earlier inclusion, pushing the gas key balance to 1.1 NEAR (> `GasKeyInfo::MAX_BALANCE_TO_BURN`).
5. Victim's `DeleteKey`/`DeleteAccount` transaction then executes against a gas key balance > 1 NEAR and fails with `ActionErrorKind::GasKeyBalanceTooHigh`, per the checks at `runtime/runtime/src/access_keys.rs:103-111` and `runtime/runtime/src/actions.rs:354-363`, leaving the key/account intact and the victim unable to delete it until the balance is brought back under the cap (which the victim cannot force since `WithdrawFromGasKey` is the only balance-reduction action and it credits `account.amount`, not eliminate the block by itself if the attacker keeps re-funding).

I was not able to fully verify from the indexed source whether `WithdrawFromGasKey` has any authorization gap that would let the victim's own remediation attempt also be griefed, nor whether there is a rate limit on `TransferToGasKey` transactions; a Devin session with full repository/test access could confirm this by running the existing `gas_keys.rs` test-loop tests with an added adversarial `TransferToGasKey` step.
