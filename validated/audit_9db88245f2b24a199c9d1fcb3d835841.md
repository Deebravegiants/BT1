### Title
Webhook Tenant (Shop) Identity Not Bound to HMAC Signature Enables Cross-Tenant Shop Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, but exposes `shop` as a separate, HMAC-uncovered field taken from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. `Registry.process` validates only that the body's HMAC is correct, then forwards the header-derived, unauthenticated `shop` value to the app's webhook handler as the identified tenant.

### Finding Description
The equality that should hold is: `shop authenticated by HMAC == shop passed to handler`. In this gem it instead is: `shop passed to handler == shop header value (unauthenticated)`, while `HMAC covers only == raw_body` [2](#0-1) .

`Request#shop` reads directly from the `shop-domain` header without any cryptographic binding to the signed payload [3](#0-2) . `HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. against the body only [5](#0-4) . `Registry.process` raises only if this body HMAC check fails, then immediately constructs `WebhookMetadata` using `request.shop` for the handler to key its tenant-scoped logic [1](#0-0) .

Because the shop value is never part of the signed content, any raw body + valid HMAC pair generated for one shop can be resubmitted to the app's webhook endpoint with a different, attacker-chosen `shop-domain` header, and the gem will still report the HMAC as valid and hand off the attacker-controlled shop identity to the app.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is meant to provide: host applications rely on `WebhookMetadata#shop` (sourced from this gem) as the authenticated tenant identifier when processing webhook side effects (e.g., updating per-shop records, redacting/creating data). Since `shop` is not bound to the HMAC, an attacker who can obtain one legitimately-signed webhook body (e.g., by installing the app on their own store, which is unprivileged) can replay that body with a spoofed `shop-domain` header to make the app process data belonging to, or under the identity of, a different shop — a cross-tenant confusion enabled purely by this gem's verification design.

### Likelihood Explanation
Moderate-to-low. The attacker must first obtain at least one validly-signed webhook body (trivially achievable by installing the app on their own shop, a normal unprivileged action for any public/development app), then send a crafted HTTP request with the same body and HMAC but a different shop header directly to the app's webhook endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is required — only the gem's own webhook verification logic, which never checks that the header-provided shop is consistent with anything signed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified for webhooks, or otherwise cryptographically bind `shop` to the payload before trusting it, mirroring how OAuth's `HmacValidator` binds `shop` into the `AuthQuery`'s `to_signable_string`. At minimum, document that host applications must independently corroborate `request.shop` against an existing, HMAC-covered installation record before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header — both valid for `Context.api_secret_key`.
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — this matches, since `shop` is not part of `to_signable_string` [2](#0-1) .
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` is `"victim-shop.myshopify.com"` — a value entirely controlled by the attacker and never authenticated [1](#0-0) .
