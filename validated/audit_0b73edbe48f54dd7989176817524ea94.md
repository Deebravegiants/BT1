### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by the HMAC signature in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC, but the HMAC is computed only over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which identify *which tenant and event* the payload belongs to — are read straight from unauthenticated HTTP headers and handed to the app's handler without ever being covered by the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are plain header readers with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts these unauthenticated fields to route the payload to a handler and construct `WebhookMetadata`: [4](#0-3) 

This breaks the identity binding: **HMAC-covered bytes (body) ≠ bytes trusted for tenant/topic identity (headers)**. An attacker who owns any Shopify development/trial store can register a webhook for that store, capture one legitimate `(raw_body, hmac)` pair delivered by Shopify, and then directly POST that same body+HMAC to the victim app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with an arbitrary value. Because the signature never covers these headers, `HmacValidator.validate` still returns `true`, and the app's handler receives `WebhookMetadata` with an attacker-chosen `shop`/`topic` bound to attacker-controlled body content.

### Impact Explanation
This can be leveraged for cross-tenant access/confusion: the app processes the attacker's own webhook payload as if it belonged to a victim shop (or under a topic it wasn't actually generated for). Any host application that uses `WebhookMetadata#shop` or `#topic` to key persistence, authorization, or business logic (which is exactly the pattern the library's own documentation and tests demonstrate — `data.shop`, `data.topic`) can be tricked into attributing forged data to another tenant, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only: (1) attacker control of any Shopify store capable of receiving at least one real webhook (trivial via a free dev/partner store), (2) the ability to POST to the victim app's public webhook endpoint (which is exposed to the internet by design), and (3) no knowledge of `api_secret_key` or any privileged credential — the attacker replays real, previously-observed signed bytes, only tampering with headers that were never protected in the first place.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them (e.g., verify `shop` against a session/store known to be associated with the specific webhook subscription id) rather than trusting header values unconditionally after only verifying the body's HMAC.

### Proof of Concept
1. Attacker installs the target app (or any Shopify app) on their own store `attacker.myshopify.com` and registers a webhook subscription for topic `orders/create`.
2. Shopify delivers a legitimate webhook to the attacker's own endpoint (or the attacker points the webhook callback URL at a listener they control) with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(secret, B)`.
3. Attacker sends `POST /webhook` directly to the victim app's real webhook endpoint with the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, even though that payload never originated from `victim-shop`.
