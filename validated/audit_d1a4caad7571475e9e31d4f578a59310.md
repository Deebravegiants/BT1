### Title
Webhook shop identity spoofing via unsigned `shop-domain` header — cross-tenant data confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC signature covers only the raw request body, while the `shop` value attributed to a webhook (and delivered to the app's handler as ground truth) is read from an unsigned HTTP header. This breaks the intended identity binding `shop verified by signature == shop acted upon`, letting an attacker who legitimately receives one signed webhook replay its exact body+signature pair while substituting an arbitrary `shop-domain` header, causing the app's handler to process the payload as if it came from a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are not included in the signed material: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC — it never binds the `shop` claim into the signed data: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field the handler receives as authoritative tenant identity: [5](#0-4) 

The Shopify app secret (`api_secret_key`) is shared across every shop that has the app installed — it is not per-tenant. Consequently, the HMAC only proves "this body was signed by *some* installation of this app's client secret," not "this body pertains to shop X." Because `shop` is excluded from the signed string, any `(raw_body, hmac)` pair that is valid for one shop is equally valid for a webhook request claiming to be from any other shop, as long as the raw body is unchanged.

The identity binding that should hold is:
```
shop_bound_by_signature == shop_delivered_to_handler
```
Here, no `shop` is bound by the signature at all — `shop_delivered_to_handler` is taken from an attacker-controlled/unauthenticated header, so the equality is vacuously broken: the left side doesn't exist, and the right side is fully attacker-controlled while the HMAC still validates.

### Impact Explanation
An unprivileged internet user who operates their own (unprivileged) shop install of a target app can capture a genuine webhook body+HMAC pair addressed to their own tenant (they legitimately receive this webhook at their own server/endpoint — no secret access needed), and then replay that exact `(raw_body, x-shopify-hmac-sha256)` pair to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a victim shop. `Utils::HmacValidator.validate` will report the signature as valid (it only checks the body against the shared app secret), and `Registry.process` will construct a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-supplied `body`/`topic`, which the host app's handler will process as authentic data belonging to the victim tenant. This is a cross-tenant data-confusion vector: an app that keys any DB writes, order/customer records, or state transitions off `WebhookMetadata.shop` without independent shop verification will attribute attacker-controlled webhook content to a shop the attacker doesn't control.

### Likelihood Explanation
High likelihood for any app author who trusts `WebhookMetadata.shop` as-is (which the gem's own API surface encourages, since `Registry.process` hands it directly to `handler.handle`). Any developer/tenant with legitimate but unprivileged access to the app (i.e., anyone who can install the app on a shop they control) can capture their own valid webhook and replay it with a forged shop header — no `api_secret_key`, access token, or elevated privilege is required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed payload used for HMAC verification, or independently verify that the `shop-domain` header corresponds to a shop the app actually expects/has an active session for before trusting it. At minimum, `Registry.process`/`WebhookMetadata` should not present the header-derived `shop` as an unconditionally trusted value to consuming apps without documenting that it is unauthenticated and must be cross-checked against known installed shops.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (ordinary unprivileged merchant action).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-HMAC-of-body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 123, ...}`
3. Attacker (who controls the receiving endpoint/observes the request, e.g. via a proxy they run, or by re-sending it themselves to another instance of the same shared app endpoint) resends the identical body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this fine (all required headers present) — [6](#0-5) 
5. `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and compares — passes because body is untouched — [7](#0-6) 
6. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {...}, ...))` — [8](#0-7)  — the host app now processes attacker-controlled data under the victim's tenant identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
