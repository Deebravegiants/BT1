### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` never authenticates the `shop`, `topic`, `webhook-id`, or `api-version` headers of an incoming webhook. `Webhooks::Registry.process` nevertheless trusts `request.shop` (parsed straight from the unauthenticated `x-shopify-shop-domain` header) when building `WebhookMetadata` and dispatching to the app's handler. Because a single app-wide `client_secret` is used to sign webhooks for every installed shop, any unprivileged internet user who controls one shop that has the app installed can capture a legitimately-signed webhook body and replay it to the app's public webhook endpoint with the `shop` header swapped to a victim shop, and the HMAC check still passes.

### Finding Description
`Request#hmac`/`#to_signable_string` only bind the raw body to the signature: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC purely from `to_signable_string`: [2](#0-1) 

`Registry.process` gates only on this HMAC check, then trusts `request.shop` (an unauthenticated header value) to build the metadata handed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used to route/attribute the webhook`. Since `shop`/`topic`/`webhook-id`/`api-version` are read from headers outside the signed body: [4](#0-3) 
that equality is not enforced — only `body == HMAC(body, client_secret)` is checked. Because Shopify apps use one `client_secret` for all installed shops, an attacker who installs the app on their own (attacker-controlled) shop will receive genuinely-signed webhooks. They can then resend that exact body/HMAC pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain. The signature remains valid because it never covered those headers, so `Registry.process` will invoke the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker-controlled shop can inject forged, self-authored webhook events that are attributed to a different (victim) tenant. Depending on how the host app's handler uses `shop` (e.g., `customers/redact`, `shop/redact`, `app/uninstalled`, or any handler that persists/acts on data keyed by `shop`), this can lead to cross-tenant data corruption, spoofed compliance/redaction actions against a shop the attacker doesn't own, or injection of attacker-controlled data into a victim tenant's records — a cross-tenant access impact.

### Likelihood Explanation
The webhook HTTP endpoint is by definition internet-reachable and unauthenticated apart from the HMAC. The only prerequisite is that the attacker controls one shop with the app installed (a normal, unprivileged app install, not a privileged account) so they can obtain one validly-signed body/HMAC pair, since all shops share the same app `client_secret` for signing. No access token, `api_secret_key` leak, or TLS interception is required — only replay of a header the gem does not bind to the signature.

### Recommendation
- **Short term:** Have `Registry.process` (or `Request`) authenticate the `shop`, `topic`, and `webhook-id` header values as part of the signable material, or independently verify that the reported `shop` matches an app-known/expected shop context before dispatching to handlers; alternatively document clearly that handlers must not trust `WebhookMetadata#shop` without additional verification (e.g., cross-checking against a stored session for that shop).
- **Long term:** Extend `VerifiableQuery`/`HmacValidator` so header-derived identity fields used for routing (`shop`, `topic`, `webhook_id`) are included in the signable string, closing the gap between "bytes verified" (body only) and "bytes acted upon" (body + headers).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com`. The app's single `client_secret` is shared across all installs.
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: HMAC(B, client_secret)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value.
4. Attacker POSTs directly to the app's public webhook endpoint, reusing `B` and the same HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, `x-shopify-topic` to a topic they want triggered).
5. `Registry.process` computes `Utils::HmacValidator.validate(request)` — this still succeeds because only `B` is checked: [5](#0-4) 
6. The app's registered handler for that topic executes with `shop: "victim-shop.myshopify.com"` and attacker-chosen body content, even though the request never actually originated from Shopify on behalf of that victim shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
