### Title
POA Bridge withdrawal status/hash misattribution across same-asset batched withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain destination-transaction hash for a specific withdrawal by matching entries returned from the POA Bridge status API using only the `assetId`, not the withdrawal's `index`, destination address, or amount.

### Finding Description
`describeWithdrawal` fetches all withdrawals associated with a NEAR transaction hash and picks the one matching `args.withdrawalParams.assetId` via `findMatchingWithdrawal`: [1](#0-0) 

The inline comment explicitly documents the reasoning: *"Response list is unsorted, so we match by assetId instead of index"*. This was clearly a deliberate design decision to work around API ordering, validated by a test where a single NEAR tx contains withdrawals of two *different* assets (ETH and BTC): [2](#0-1) 

The SDK explicitly supports batching multiple withdrawals into one NEAR transaction (`sdk.createWithdrawalIntents`/`estimateWithdrawalFee` accepting arrays), and `createWithdrawalIdentifier` differentiates withdrawals purely by `index` for callers to later query status: [3](#0-2) 

However, if two (or more) withdrawals of the **same** `assetId` — but to different destination addresses/amounts — are included in the same NEAR transaction (a legitimate batching scenario, e.g. paying out the same token to two different recipients in one call), `findMatchingWithdrawal` has no way to disambiguate them: it only keys off `assetId`. The `withdrawal.data` object returned by the API does carry `address` and `amount` fields (as seen in the mocked test fixtures), but these are not used in the matching logic shown at the call site.

I was not able to view the full body of `findMatchingWithdrawal` (defined further in the file / re-exported from `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) before running out of tool budget, so I cannot confirm with certainty whether it internally falls back to any additional disambiguation (e.g., destination address) for same-asset duplicates. This is the key remaining uncertainty.

### Impact Explanation
If the match is asset-only (as the comment and call site strongly suggest), an integrator polling `describeWithdrawal` for withdrawal index `1` (say, destination B) could receive the `txHash`/`status` belonging to withdrawal index `0` (destination A) whenever both move the same asset in one NEAR transaction. This is a **status/hash misreport**: an integrator could credit/refund based on a transaction hash that does not correspond to the queried withdrawal — matching the "status reported that is not the on-chain outcome" class in scope, with potential double-credit or a withdrawal falsely marked complete while the real transfer is still pending or failed.

### Likelihood Explanation
Requires only routine SDK usage: batching two or more withdrawals of the *same* token in a single NEAR transaction — no malicious actor needed, no privileged access. If `findMatchingWithdrawal` truly disambiguates only by `assetId`, this triggers deterministically whenever such a batch occurs.

### Recommendation
Confirm the implementation of `findMatchingWithdrawal` (in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`). If it matches solely by `assetId`, extend matching to also compare `destinationAddress` and/or `amount` (or track consumed indices) so that same-asset, multi-recipient batches resolve to the correct on-chain transaction per logical withdrawal index.

### Proof of Concept
Not fully verified — contingent on confirming `findMatchingWithdrawal`'s exact matching keys, which I could not inspect within the available tool budget. The strongest evidence is the explicit code comment and test at `poa-bridge.ts:318-322` and `poa-bridge.test.ts:1054-1111`, which only exercises differing-asset disambiguation, not same-asset multi-destination disambiguation.

**Note on scope/confidence**: Due to running out of tool-call iterations, I could not open the actual `findMatchingWithdrawal` function body to verify whether it uses only `assetId` or also secondary fields. This finding should be treated as a lead requiring confirmation of that function's source before being treated as conclusively proven.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}
