### Title
Divide-by-zero DoS in `Zap._executeBuy` fee proration when `ltMinted == 0` - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._executeBuy` computes `effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted` at [1](#0-0)  without ever checking that `ltMinted != 0`. This is structurally the same bug class as the reported Cooler issue: an unchecked divisor sourced from an external call is assumed to always be non-zero, and if it is zero the transaction reverts with an EVM division-by-zero panic instead of a clean, handled error.

### Finding Description
`ltMinted` comes directly from the external, unprivileged-caller-reachable BounceTech LT call `IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0)` at [2](#0-1)  (post-graduation branch) and [3](#0-2)  (curve branch). `Zap` only guards the *input* side — `baseToConvert`/`netUsdc` must be `>= minUsdcAmount()` (checked at [4](#0-3)  and the floor-bump logic at [5](#0-4) ) — but it never validates the *output* of `mint`, i.e. that `ltMinted > 0`, before using it as a division denominator at line 386.

`minUsdcAmount()` is alt.fun's own static USDC floor; it is not derived from the LT's live `exchangeRate()`. Because the LT is an external, rebasing-priced instrument whose `exchangeRate()` can drift over time (this is explicitly documented elsewhere in the codebase as something the protocol must tolerate, e.g. the USD-trigger exchange-rate drift discussion), a fixed USDC floor is not guaranteed to always convert to a non-zero LT share amount under every possible/future exchange rate. If BounceTech's own internal floor (`MinTransactionSize`) is expressed in terms of the LT's own base unit rather than being perfectly synchronized with alt.fun's `minUsdcAmount()`, or if a future exchange-rate regime shifts the rounding boundary, `mint()` can return `ltMinted == 0` for an input that still passes `Zap`'s own floor checks and does not revert on the BounceTech side.

When that happens, execution proceeds past the mint call and reaches `effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted`, which triggers Solidity's `Panic(0x12)` (division by zero) regardless of the numerator, unwinding the entire `buy()` call.

### Impact Explanation
This is a denial-of-service on `Zap.buy()` for the affected token/LT pair at the specific input size that hits the zero-mint edge case. Because `_executeBuy` is on the sole entry point for buys pre- and post-graduation, and there is no fallback path (sells still work via `redeem`, buys do not), it can degrade the token to a sell-only market at that USDC/LT price point — matching the "DOS attack which could cause inconsistent record keeping"-style impact class called out in the source report. It is a Medium-severity availability/DoS bug rather than a fund-theft bug, consistent with the reported issue's own severity rating.

### Likelihood Explanation
The precondition (`ltMinted == 0` while `baseToConvert >= minUsdcAmount()`) is not proven reachable purely from alt.fun's own code — it depends on BounceTech LT's internal rounding/floor behavior, which is out of scope and cannot be fully verified from this repository's index. This makes the exact trigger condition uncertain: if BounceTech's `MinTransactionSize` check always guarantees `mint()` returns `>0` shares whenever it doesn't revert, then this exact division can never fire in practice. I could not confirm this guarantee from the available interface/mock code in `packages/contracts/src/interfaces/IBounceLeveragedToken.sol`, so likelihood should be treated as **Low-to-Medium** and reported as an unhandled invariant/missing defensive check rather than a confirmed exploit.

### Recommendation
Add an explicit check immediately after each `mint()` call in `Zap._executeBuy` (lines 320 and 360) that reverts with a clear custom error (e.g. `ZeroLtMinted()`) if `ltMinted == 0`, before it is ever used as a division denominator at line 386. This converts an opaque panic into an explicit, auditable revert and removes any dependency on BounceTech's internal rounding guarantees.

### Proof of Concept
Conceptual (cannot be fully constructed without access to BounceTech LT's real/mocked rounding behavior at the relevant exchange rate):
1. Configure the mock/real LT so that `exchangeRate()` is set such that `baseToLtAmount(minUsdcAmount())` rounds down to `0` while `mint(address(this), minUsdcAmount(), 0)` does not revert (i.e., BounceTech's own floor check is expressed differently than alt.fun's `minUsdcAmount()`).
2. Call `Zap.buy(tokenAddress, minUsdcAmount(), 0, address(0))` from any unprivileged trader address.
3. `_executeBuy` passes the `netUsdc >= minUsdcAmount()` check, calls `mint()`, receives `ltMinted == 0`, and then panics on `(amountInUsed * baseToConvert) / ltMinted` at [1](#0-0) , reverting the whole buy.
