### Title
Webhook shop/topic identity spoofing via HMAC signature that covers only the raw body, not the routing headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by recomputing an HMAC over the raw HTTP body and comparing it to the `X-Shopify-Hmac-Sha256` (or `shopify-hmac-sha256`) header [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values used to route and act on the payload are read from separate HTTP headers that are never included in the signed material [2](#0-1) . This is analogous to the reported EIP712 bug class: a value that is *used* by the trust decision (which tenant/shop the event belongs to) is not actually *covered* by the cryptographic binding (the HMAC) that is meant to authenticate the message.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) . `HmacValidator.validate_signature` HMACs exactly that string with `Context.api_secret_key` and does a constant-time compare against the `hmac` header [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read separate, unauthenticated headers [5](#0-4) .

`Registry.process` validates the HMAC, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which participated in the signature check — and dispatches it to the app's registered handler [1](#0-0) .

Because the HMAC only binds the JSON body, any entity that possesses one valid `(raw_body, hmac)` pair for their *own* shop (e.g., a merchant who has installed the app and legitimately receives real webhooks from Shopify for their own store) can replay that exact body and HMAC to the app's webhook endpoint while freely rewriting the `shopify-shop-domain` and/or `shopify-topic` headers. `HmacValidator.validate` will still pass — it only ever checks the body against the secret — while `WebhookMetadata.shop`/`.topic` now claim a different (victim) shop or a different event type than what Shopify actually signed. This breaks the identity binding: `shop authenticated by HMAC == shop the handler acts on`.

### Impact Explanation
Any app built on this gem that keys per-tenant logic off `WebhookMetadata#shop` (which the documented webhook usage pattern encourages, since `shop` is the only tenant identifier provided in the callback) can be made to process attacker-supplied data under a victim shop's identity, or receive a fabricated event topic. This is a cross-tenant integrity/identity-spoofing issue reachable by any unprivileged user who is themselves a merchant/installer of the target app (no `api_secret_key`, access token, or privileged account required) — they only need one legitimately-signed webhook for their own store to derive `(body, hmac)` pairs they can splice with a different `shop`/`topic` header value.

### Likelihood Explanation
High reachability: webhook endpoints are public HTTP endpoints by design, headers are fully attacker-controlled by anyone able to send an HTTP request, and no secret material beyond a self-obtained valid webhook is needed. The gem's own header-normalization code even treats `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` as independent, unauthenticated inputs to `Request` [6](#0-5) .

### Recommendation
Bind the routing metadata into the authenticated material rather than trusting bare headers: either (a) include `topic`, `shop-domain`, `webhook_id`, and `api_version` in the string that is HMAC'd (mirroring the fix pattern recommended for EIP712 — don't trust cached/unauthenticated context, bind everything relevant into the signature), or (b) have `HmacValidator`/`Registry.process` cross-check the `shop` header against the shop associated with the session/registration that is expected to receive that specific `topic`, rejecting mismatches before dispatching to the handler.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and trigger any webhook subscribed by the app (e.g. `orders/create`). Shopify sends: body `B`, headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Capture `(B, H)` — no secret is exposed to the attacker, only the pair.
3. Replay a new HTTP request to the app's webhook endpoint with the same body `B` and the same `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim-shop.myshopify.com` (and/or a different registered `shopify-topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it still equals `H` [4](#0-3) , so validation passes.
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` [7](#0-6) , causing the app to process attacker-controlled order data as if it belonged to `victim-shop.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
