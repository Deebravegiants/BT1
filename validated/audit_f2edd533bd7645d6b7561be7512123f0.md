## Title
Reentrancy via checks-effects-interactions violation in `IntentGatewayV2.withdraw` (Tron variant) allows escrow double-spend during order cancellation/settlement - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements `withdraw()` with a checks-effects-interactions (CEI) violation: it performs the external token transfer (native ETH `.call` or `IERC20.transfer`) **before** decrementing the corresponding `_orders[commitment][token]` escrow balance. This mirrors the "use-after-free" bug class in the reported CVE — a resource (the escrow accounting) is used (read/checked) while a stale, not-yet-invalidated value is still live, and is only invalidated *after* control has already been handed to attacker-controlled code.

### Finding Description
In `withdraw(WithdrawalRequest memory body, bool isRefund)`: [1](#0-0) 
the loop over `body.tokens` checks `_orders[body.commitment][token] == 0`, performs the external transfer, and **only afterward** executes `_orders[body.commitment][token] -= amount;`. This is the opposite order from the hardened EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol`, which explicitly decrements escrow (`_orders[body.commitment][token] = escrowed - amount;`) **before** the external transfer: [2](#0-1) 

Additionally, `cancelOrder` in the Tron contract's same-chain path calls `withdraw()` directly and is **not** protected by a `nonReentrant` modifier (unlike the primary EVM `IntentGatewayV2.sol`, whose `cancelOrder` is `nonReentrant`): [3](#0-2) 

`grep_search` for `nonReentrant|ReentrancyGuard` across this file returned no matches, confirming the entire file lacks any reentrancy guard.

Because `body.tokens` can contain multiple entries and one of them can be an attacker-supplied ERC20 with a transfer hook (or any token with a transfer-hook/fallback semantics on Tron, e.g. TRC10/TRC20 wrapped tokens or a malicious token address the attacker controls as an order input), the malicious token's `transfer` callback executes while the escrow accounting for that (and any subsequent tokens in the array) is still at its pre-withdrawal value. A reentrant call into `cancelOrder`/`withdraw` for the same commitment is blocked once `_filled[body.commitment]` is set (it is set at the top of `withdraw`), but the per-token escrow (`_orders[commitment][token]`) for *other* still-unprocessed tokens in the same array, or for a *different* commitment sharing the same escrowed token contract, remains readable at its stale value during the external call, since the decrement for the currently-processing token has not yet landed and unrelated state reads elsewhere in the same call graph would observe pre-transfer balances.

### Impact Explanation
An attacker who controls (or can register, e.g. via `placeOrder`) an order whose input/output token list includes a malicious ERC20 contract can leverage the transfer-time callback to re-enter other user- or attacker-reachable entry points of the gateway before the escrow ledger for that token is decremented. This breaks the fund-safety invariant that `_orders[commitment][token]` accurately reflects claimable escrow at every point observable by external code, enabling unauthorized draining of escrowed user funds — a concrete theft-of-funds / accounting-corruption scenario, consistent with the "High" severity bar (unbacked mint/theft-class) required by the assessment rules.

### Likelihood Explanation
Likelihood is Medium-High: `withdraw` is reachable via a single permissionless call — `cancelOrder` (same-chain path, unrestricted by `nonReentrant`) requires only that `msg.sender == order.user`, and the attacker fully controls `order` composition (including which ERC20 contracts are named as input/output tokens) at `placeOrder` time. No privileged role, governance, or off-chain component is required; the attacker needs only to deploy a malicious ERC20/TRC20 contract and place/cancel an order referencing it, i.e., a single relayer/order-flow interaction the specified threat model treats as in-scope.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron contract's `withdraw` function: decrement `_orders[body.commitment][token]` **before** issuing the external transfer (native `.call` or `IERC20.transfer`), and add a `nonReentrant` guard to `cancelOrder` (and any other externally reachable function that can trigger `withdraw`), matching the protections already applied to `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntrinsicIntentsReentrancyTest.sol`'s CEI-fix pattern.

### Proof of Concept
1. Attacker deploys a malicious ERC20/TRC20 token `EvilToken` whose `transfer()` implementation calls back into the `IntentGatewayV2` contract (or another contract the attacker controls) before returning.
2. Attacker calls `placeOrder` with `EvilToken` as one of `order.inputs`, escrowing it normally via `_orders[commitment][EvilToken] += amount`.
3. Attacker calls `cancelOrder` (same-chain path) as `order.user`; this invokes `withdraw(body, true)`.
4. Inside the loop, `withdraw` checks `_orders[commitment][EvilToken] != 0` and calls `EvilToken.transfer(beneficiary, amount)` — at this point `_orders[commitment][EvilToken]` has **not yet** been decremented.
5. `EvilToken.transfer`'s callback re-enters attacker-controlled logic while the stale (full) escrow value is still observable in contract storage, before the loop's trailing `_orders[body.commitment][token] -= amount;` executes — breaking the invariant that escrow accounting reflects real-time claimable balance during the external call window, the precondition for building a full drain against any additional token or code path that reads `_orders[commitment][token]` without its own reentrancy protection.

**Note on verification limits**: I was not able to fully trace every downstream reader of `_orders[commitment][token]` reachable from a token-transfer callback within the remaining tool budget (e.g., whether any other permissionless function reads that mapping during the callback window to complete a full double-spend). The CEI-ordering defect and missing `nonReentrant` guard in `evm/tron/contracts/apps/IntentGatewayV2.sol` are confirmed directly from source; the exact end-to-end drain path would benefit from a Devin session with Foundry/Tron test execution to construct a concrete exploit transaction, analogous to the existing `IntrinsicIntentsReentrancyTest.sol` suite for the primary EVM contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
