## #Vulnerability found

### Title
Unchecked ERC20 return value in `withdraw()`/`onAccept` (SweepDust) permanently burns escrow accounting without delivering funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) settles escrow payouts using a raw low-level `.call()` with the `IERC20.transfer` selector and only checks that the call did not revert, never validating the returned boolean. Any ERC20 that returns `false` on a failed transfer instead of reverting will be treated as a successful payout, while the internal escrow ledger is unconditionally decremented and `EscrowReleased`/`EscrowRefunded` is emitted.

### Finding Description
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages (settlement messages delivered by any relayer after proof verification) and from `onGetResponse()` for cancellation: [1](#0-0) 

For every escrowed token payout and for fee redemption, the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This checks only that the external call itself did not revert — it never decodes/verifies the ABI-encoded boolean return value that `IERC20.transfer` is supposed to return. Per EIP-20, a compliant implementation can legitimately return `false` (rather than revert) on failure (e.g., paused token, blacklisted recipient, insufficient balance in some non-standard implementations). In that case `success` is `true` (the low-level call completed without reverting) even though no tokens moved.

Immediately after this unchecked "success", the code does:
```solidity
_orders[body.commitment][token] -= amount;
```
and marks the order filled (`_filled[body.commitment] = beneficiary`), emitting `EscrowReleased`/`EscrowRefunded`. The escrow record is deleted/decremented as if the beneficiary was paid, but if `transfer()` returned `false`, the beneficiary received nothing. The same unchecked pattern is used in the `SweepDust` handler and for `TRANSACTION_FEES` redemption.

Notably, this is inconsistent with the primary EVM implementation and with the input-transfer path in the very same file, both of which use `SafeERC20.safeTransferFrom`/`safeTransfer` (which does decode and check the return value): [2](#0-1) 
The escrow-release import even declares `using SafeERC20 for IERC20;` but the outgoing transfer paths bypass it entirely in favor of the unchecked raw call.

### Impact Explanation
Once a relayer delivers a valid `RedeemEscrow`/`RefundEscrow` proof (or a valid empty-proof `onGetResponse` for cancellation), `withdraw()` runs unconditionally clears the escrow bookkeeping for that commitment/token regardless of whether the token transfer actually succeeded. For any token that returns `false` instead of reverting on transfer failure (paused/blacklist-capable tokens, several non-standard EIP-20 tokens), the escrowed user or solver funds become permanently unrecoverable: the on-chain escrow state (`_orders[commitment][token]`) is zeroed out and the order is marked filled/refunded, so no retry path exists, yet the tokens remain stuck in the gateway contract. This is a permanent freezing of escrowed user funds reachable by the ordinary settlement/cancellation flow — no privileged role required.

### Likelihood Explanation
Likelihood depends on the specific ERC20 token used as an intent input/output/fee token supporting this contract deployment. Any token in that category that can return `false` on transfer (e.g., paused, allowance-limited by non-standard rules, or non-reverting failure semantics) triggers this on the very first settlement/cancellation after the failure condition is met (e.g., token gets paused between order placement and fill/redeem). Given the report scope explicitly states "any" ERC20 is expected to interact with this protocol, this is a realistically reachable condition on a permissionless flow driven purely by relayer message delivery.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer()` (already imported and used elsewhere in the same file), which decodes and enforces the boolean return value (or absence thereof) per EIP-20, and reverts on failure instead of silently marking escrow as released.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an escrow token `T` whose `transfer()` implementation returns `false` (rather than reverting) when, e.g., the contract is paused or the recipient is blacklisted (a legal EIP-20 pattern).
2. A user places an order escrowing `T`; a solver fills it, or the user cancels; Hyperbridge relays the `RedeemEscrow`/`RefundEscrow` (or `onGetResponse`) message to the source chain gateway.
3. Before delivery, token `T` is paused (or the beneficiary is blacklisted).
4. `onAccept`/`onGetResponse` → `withdraw()` executes `token.call(...transfer...)`; `T.transfer` returns `false` but does not revert, so `success == true`.
5. `_orders[commitment][token] -= amount` zeroes the escrow record and `EscrowReleased`/`EscrowRefunded` is emitted, while the beneficiary's `T` balance is unchanged — the tokens remain stuck in the gateway with no further code path to reclaim them for that commitment.
