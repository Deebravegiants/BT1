Confirmed: `WebhookMetadata` carries `shop` as a plain `const :shop, String` handed directly to the host app's handler, with no cross-check against the HMAC-covered payload.

### Title
Webhook `shop-domain` header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC-signed material [2](#0-1) . `Registry.process` validates the HMAC over the request (which only covers the body) and then forwards the unverified `request.shop` straight into `WebhookMetadata` passed to the app's handler [3](#0-2) . `WebhookMetadata.shop` is a plain, unauthenticated string field consumed by the host application to identify the tenant [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop-domain header == shop bound by the HMAC signature`. In this gem, the HMAC secret (`Context.api_secret_key`) is shared across all shops installed on a given app (it's the app's client secret, not per-shop), and `HmacValidator.validate` only proves that the raw body was signed by an entity holding that shared secret — it never binds the signature to the specific `shop-domain` header value [5](#0-4) . Because `to_signable_string` for `Webhooks::Request` returns only `@raw_body` [1](#0-0) , two different values of the `shop-domain` header can be paired with the exact same body+HMAC and both validate successfully. An attacker who controls one shop tenant (Shop A) that has this app installed will legitimately receive real webhooks from Shopify signed with the app's shared secret. The attacker can capture a `(raw_body, hmac)` pair from their own genuine webhook deliveries and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header to name a victim shop (Shop B). `Registry.process` will validate the HMAC (it only checks the body signature, which is untouched) and dispatch the handler with `WebhookMetadata.shop == "shop-b.myshopify.com"` even though the payload actually originated from Shop A [3](#0-2) .

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as intended/documented) to key its per-tenant session or data store, this yields cross-tenant data injection/confusion: an attacker-controlled shop's webhook payload gets attributed and written under an arbitrary victim shop identifier, since the shop value is never checked against anything bound by the signature. This crosses a tenant boundary using only unprivileged access to one's own shop/app installation, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any merchant/developer who has legitimate access to their own shop's webhook deliveries (a completely unprivileged position relative to other tenants of the same app) — replaying captured webhook bodies with a modified header is trivial and requires no secret material, since the shared `api_secret_key` HMAC only ever covers the body.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed material, or independently verify that the `shop-domain` header value is consistent with an out-of-band trusted source (e.g., cross-check against a known installed-shop registry) before trusting `WebhookMetadata.shop`. At minimum, document prominently that `WebhookMetadata.shop` is not authenticated by the HMAC and must not be used as a sole tenant identifier without additional verification.

### Proof of Concept
1. Shop A installs the app; Shopify sends a real webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (owner/operator of Shop A) captures this exact request.
3. Attacker resends the same body `B` and same HMAC header, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only verifies `B` against the HMAC [6](#0-5) .
5. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing the host app to process/store Shop A's data under Shop B's tenant identity [7](#0-6) .
