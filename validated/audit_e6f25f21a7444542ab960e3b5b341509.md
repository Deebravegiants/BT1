Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body via `Utils::HmacValidator.validate(request)`. The `shop`, `topic`, and `webhook_id` values that the gem hands to the app's handler as the tenant/event identity come from unauthenticated HTTP headers that are never included in the signed bytes. This breaks the equality the HMAC is supposed to guarantee: `hmac_valid(body) == identity(shop, topic, webhook_id, body)` — the signature proves the body was signed with the app's `client_secret`, but says nothing about which shop or topic that body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet the same `Request` object also exposes `shop`, `topic`, `api_version`, and `webhook_id`, all parsed from HTTP headers that are not part of the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body), then immediately forwards the unauthenticated `request.shop` and `request.topic` to the app-provided handler as the trusted tenant identity: [4](#0-3) 

`Utils::HmacValidator.validate` confirms this — it calls `verifiable_query.to_signable_string` (body only) and compares against the HMAC header, never touching `shop`/`topic`/`webhook_id`: [5](#0-4) 

The gem's own documentation instructs app authors to treat `data.shop` from `WebhookMetadata` as the authoritative tenant identifier used to route/process the webhook payload: [6](#0-5) [7](#0-6) 

Because `shop`/`webhook_id`/`topic` sit outside the HMAC's protected scope (analogous to the reentrancy-guard bug class: a field acted on but not covered by the integrity check), any party who has ever obtained one genuine `(raw_body, hmac)` pair signed with the app's secret — e.g. by legitimately installing the app on their own shop and receiving one real webhook delivery — can replay that exact body/HMAC pair directly to the app's public webhook endpoint (bypassing Shopify's platform entirely) while substituting the `shop-domain` header for a victim shop, or the `webhook-id`/`topic` headers for a different event. `Utils::HmacValidator.validate` still returns `true`, because it only re-derives the signature over `raw_body`, and `Registry.process` proceeds to dispatch that body to the handler labeled with the attacker-chosen shop/topic.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged internet user who has ever received one legitimate webhook (via installing the app, a low bar) can forge deliveries that the app will process as belonging to a different, arbitrary merchant (`shop` field), or as a different topic/webhook id than what was actually signed. Depending on how the app implements its handler (which the gem's docs explicitly steer toward trusting `data.shop`/`data.topic` for record lookup/dedup), this enables cross-tenant data confusion, spoofed order/fulfillment/app-uninstall events being attributed to a victim shop, or duplicate-suppression (`webhook_id`) bypass — all without ever needing the app's `client_secret`.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have at least one genuine `(body, hmac)` pair, which is trivially obtainable by installing the target app on an attacker-controlled shop (many Shopify apps allow free/dev-store installs) and capturing any webhook delivery. After that, forging the shop/topic headers on a direct POST to the app's public webhook route requires no cryptographic secret. This is a fully in-gem root cause — the gem never enforces or documents that `shop`/`topic`/`webhook_id` must be independently trusted, and its own sample handler code in `docs/usage/webhooks.md` encourages using `data.shop` as the tenant key.

### Recommendation
Include the security-relevant header values (`shop`, `topic`, and ideally `webhook_id`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the body (e.g., validate that the `shop` header matches a shop for which the app currently holds an active session/registration before dispatching). At minimum, update `lib/shopify_api/webhooks/request.rb`'s `to_signable_string` and `lib/shopify_api/utils/hmac_validator.rb` to cover these fields, and document clearly in `docs/usage/webhooks.md` that `data.shop`/`data.topic` are not currently HMAC-protected so app authors don't rely on them as an authentication boundary.

### Proof of Concept
1. Install a target Shopify app on an attacker-controlled shop `attacker.myshopify.com` and trigger any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` sent to the app's webhook endpoint — `H` is a valid signature for `B` under the app's `client_secret`.
2. Send a direct HTTP POST to the same app's public webhook route with:
   - body = `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (attacker-controlled)
   - `X-Shopify-Topic`/`X-Shopify-Webhook-Id` optionally altered as well
3. `ShopifyAPI::Webhooks::Registry.process` builds a `ShopifyAPI::Webhooks::Request`, calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds: [4](#0-3) 
4. The handler registered for that topic receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` and processes body `B` as though it originated from `victim.myshopify.com`, despite the victim shop never having sent this webhook.
