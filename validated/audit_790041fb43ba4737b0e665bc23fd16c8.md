This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never included in the HMAC-signed payload [2](#0-1) . `Registry.process` validates the HMAC over the request (i.e., over the raw body only) and then trusts `request.topic` and `request.shop` from headers to route to a handler and construct `WebhookMetadata` [3](#0-2) . ### Title
Webhook HMAC validation does not cover `shop`/`topic`/`webhook_id`/`api_version` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body [1](#0-0) , but the identity-defining fields `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from HTTP headers that are entirely outside the HMAC's coverage [2](#0-1) . `Utils::HmacValidator.validate` only checks that the computed signature over `to_signable_string` matches the received signature [5](#0-4) ; it never binds the header values into that signature.

### Finding Description
The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant_and_action`. In this gem, `hmac_signed_bytes` is only `@raw_body` [6](#0-5) , whereas `bytes_that_determine_tenant_and_action` are the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers [2](#0-1) . Because the app's `api_secret_key` is shared across every shop that installs the app, any legitimately delivered webhook (e.g., from the attacker's own store) yields a raw-body/HMAC pair the attacker fully controls and can replay. The attacker can take that valid `(raw_body, hmac)` pair and resubmit it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header (a victim shop) and/or an arbitrary `shopify-topic` header, and `Registry.process` will still pass HMAC validation before dispatching to the handler with the attacker-chosen `shop` and `topic` [7](#0-6) .

### Impact Explanation
Because `WebhookMetadata.shop` is the value host applications are documented to use directly for tenant-scoped side effects (e.g., dispatching background jobs keyed by `shop_domain`) [4](#0-3) , an attacker who controls one legitimate install of the app can forge webhook deliveries attributed to a different, victim shop, or claim a different topic than what was actually signed (e.g., turning a benign `app/uninstalled` body payload into a spoofed `customers/data_request` or `shop/update` event for another tenant). This crosses a tenant boundary using only the attacker's own legitimate webhook traffic and the app's shared `client_secret`, without needing the victim's credentials, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker (1) installs the app on their own store to receive at least one legitimately signed webhook (any topic with a body they can influence or a body reusable across topics/shops, such as `{}`), and (2) resends that raw body with the same computed HMAC but altered `shop`/`topic` headers to the app's public webhook endpoint. No access token, TLS interception, or victim credential is required — this is fully reachable by an unprivileged internet user who is themselves an app installer.

### Recommendation
Include the identity-defining headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body before verification — e.g., by having `to_signable_string` concatenate a canonical representation of these header values together with `@raw_body`, and re-deriving `Registry.process`'s trust in `request.shop`/`request.topic` only from that verified binding rather than raw headers alone.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; receive a legitimate webhook delivery with raw body `{}` and topic `orders/create`, HMAC computed over `{}` with the shared `client_secret`.
2. Replay a POST to the app's webhook route with the same raw body `{}` and the same valid `shopify-hmac-sha256` value, but set `shopify-shop-domain: victim.myshopify.com` and `shopify-topic: customers/data_request`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the HMAC [1](#0-0) .
4. `Registry.process` looks up the handler for `customers/data_request` and invokes it with `shop: "victim.myshopify.com"` [7](#0-6) , causing the host application to perform tenant-scoped actions against the wrong or attacker-chosen shop.
