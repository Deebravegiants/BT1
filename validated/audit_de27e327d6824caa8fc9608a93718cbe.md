### Title
`CallDispatcher.dispatch()` has no access control, allowing any address to hijack another order's approvals or in-flight balances - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a permissionless, unauthenticated entry point used as the shared calldata-execution proxy for every `IntentGatewayV2` order's predispatch/postdispatch step, and for `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata delivery. Unlike the Noya `Connector.sendTokensToTrustedAddress()` bug (which at least restricted the caller to `registry.flashLoan()`), this function has **no caller restriction whatsoever** — anyone can call `dispatch()` directly with an arbitrary `Call[]` and have the dispatcher execute it "in its own context." Because the dispatcher is a single shared contract that legitimately holds transient token approvals and balances belonging to whichever order/app is mid-execution, any third party can race a pending transaction or exploit a persisted approval to redirect funds meant for a different order/beneficiary, exactly analogous to how the Noya flash-loan contract let one vault's keeper reach into another vault's connector.

### Finding Description
`CallDispatcher.dispatch()`: [1](#0-0) 
is `external` with no `onlyOwner`/`onlyGateway`/`msg.sender` check at all. It decodes an arbitrary `Call[]` and executes each `to.call{value}(data)` from the dispatcher's own address/context.

This single dispatcher address is reused by every order placed through `IntentGatewayV2` for both predispatch and postdispatch calldata: [2](#0-1) [3](#0-2) 

and by `HyperFungibleToken`/`WrappedHyperFungibleToken` for cross-chain calldata execution on `onAccept`: [4](#0-3) 

The docs explicitly acknowledge the dispatcher temporarily holds tokens/approvals mid-execution and warn integrators to use exact, non-unlimited approvals for calls routed through it — but this is only advisory; the contract itself performs no verification that the caller invoking `dispatch()` is the gateway/app that is supposed to own the balance currently sitting at the dispatcher: [5](#0-4) 

Because `dispatch()` is open to any caller, and the same dispatcher address accumulates balances/approvals from unrelated orders and unrelated apps, an attacker can:
1. Monitor the mempool for a `placeOrder`/`fillOrder` transaction whose predispatch/postdispatch flow transfers tokens to the dispatcher and grants it an approval to a router (see test pattern using `IERC20.approve(uniswapRouter, type(uint256).max)` executed by the dispatcher itself) — front-run or back-run that transaction with a direct call to `CallDispatcher.dispatch()` carrying a `Call{to: token, data: transferFrom(...)}` or a call that spends the outstanding approval before/after the legitimate sequence completes, redirecting the victim order's escrowed/solver-provided tokens.
2. More generally, since the dispatcher is one contract shared across *all* gateway instances and all HFT deployments referencing it, any lingering balance or approval left by one integration is reachable by literally anyone, not just the intended gateway — there is no "trusted-caller" gate analogous to even the flawed one in the Noya report.

This mirrors the Noya root cause precisely: a shared, cross-tenant contract (`BalancerFlashLoan` / `CallDispatcher`) is trusted by per-tenant logic (`Connector` / `IntentGatewayV2`/`HFT`) to only be invoked in the context of the tenant that owns the funds, but the shared contract itself enforces no such binding — `msg.sender` (or here, the complete absence of any sender check) does not tie the call back to a specific order/vault context.

### Impact Explanation
Any funds or unlimited/lingering ERC20 approvals momentarily routed through the shared `CallDispatcher` (across `IntentGatewayV2` predispatch/postdispatch legs and `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata delivery) can be stolen by an unrelated third party who calls `dispatch()` directly, since the function performs no access control and the dispatcher's balance/allowances are not bound to a specific caller or order. This is a direct theft-of-funds vector reachable from a single unprivileged transaction — High severity, consistent with the original Noya finding's "steal all funds through a shared trusted contract" pattern.

### Likelihood Explanation
Likelihood is elevated because: (a) the docs themselves flag that unlimited approvals to the dispatcher are dangerous, indicating this is a known, real usage pattern in production flows (e.g., router approvals set inside predispatch/postdispatch `Call[]`); (b) `dispatch()` requires no privilege at all, so exploitation only requires observing a pending transaction or an existing dangling approval and submitting an ordinary transaction; (c) the dispatcher is shared across multiple apps/chains per the "Existing CallDispatcher deployments" reference, widening the attack surface beyond a single gateway instance.

### Recommendation
Add caller authentication to `CallDispatcher.dispatch()` — e.g., restrict callers to a fixed, immutable, single trusted caller (one dispatcher instance per app, not shared), or require the caller to prove ownership/context of the funds being moved. Alternatively, redesign so that the dispatcher never holds standing approvals or balances outside of an atomic call initiated and fully consumed by the legitimate owner in the same transaction, and enforce that any approval granted to the dispatcher is scoped and revoked within that same atomic call.

### Proof of Concept
1. A user submits `IntentGatewayV2.placeOrder` (or a solver submits `fillOrder`) whose `predispatch.call`/`output.call` includes a `Call` that sets `IERC20.approve(uniswapRouter, type(uint256).max)` from the `CallDispatcher`'s context, as shown in the codebase's own test pattern (`postdispatchCalls[0]` approving the Uniswap router for `type(uint256).max`): [6](#0-5) 
2. Before the swap call consumes/decreases that approval (or if the sequence reverts/partially completes leaving the approval outstanding), an attacker calls `CallDispatcher.dispatch()` directly with `Call{to: token, data: abi.encodeWithSelector(IERC20.transferFrom.selector, dispatcher, attacker, amount)}` or similarly interacts with `uniswapRouter` using the dispatcher's standing approval, since `dispatch()` performs no caller check: [7](#0-6) 
3. Because `dispatch()` executes any provided `Call[]` from the dispatcher's own address regardless of who calls it, the attacker successfully spends the token balance/approval that was intended only for the specific order being processed by `IntentGatewayV2`.

Note: full exploitation depends on how much residual approval/balance the dispatcher retains between statements within one atomic transaction versus across transactions; a definitive confirmation of a persisted (cross-transaction) window would require deeper end-to-end tracing of every integration that grants approvals to the dispatcher, which was not fully verifiable from the indexed code alone.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
