### Title
Permanent market freeze from debt-value overflow during interest accrual - (File: common/src/rates/index.rs)

### Summary
A market with sufficiently large scaled debt can reach a state where the next accrual overflows while calculating the new total debt. Because every pool mutation loads and synchronizes the market before acting, the overflow permanently prevents repayment, withdrawal, liquidation settlement, recapitalization, and index updates for that market. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_supplier_rewards` computes `borrowed * new_borrow_index` using non-saturating RAY arithmetic. [3](#0-2)  Although `update_borrow_index` caps the index itself at `MAX_BORROW_INDEX_RAY`, it does not ensure that `borrowed * index` remains representable as an `i128`. [4](#0-3) 

Consequently, a market can be admitted while below the index cap but already too large to multiply by the next index. Once ledger time advances enough to produce that index, `global_sync` panics inside `accrue_step` and never reaches `mark_accrued`. [5](#0-4) [6](#0-5)  Since the failed transaction is atomic, `last_timestamp` remains stale, so every subsequent accrual retries the same overflowing calculation. [7](#0-6) 

The path is reachable through unprivileged controller operations: `supply` and `borrow` create the oversized debt position, while `update_indexes`, `repay`, `withdraw`, `liquidate`, and `recapitalize` all cross pool paths that synchronize the affected market before mutation. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
The market becomes permanently unable to process state-changing operations that require accrual. Supplier cash cannot be withdrawn, borrower debt cannot be repaid, collateral cannot be recovered through liquidation, and recapitalization cannot inspect or repair the market because `recapitalize` also calls `renewed_market`. [11](#0-10) [12](#0-11) [13](#0-12) 

This permanently freezes user funds in the affected market and can leave otherwise collectible bad debt inaccessible. [14](#0-13) 

### Likelihood Explanation
Triggering the condition requires a very large borrow book and enough accrued index growth for `borrowed * new_borrow_index` to exceed `i128::MAX`; the configured caps, asset decimals, rate model, utilization, and token supply must permit that state. [15](#0-14)  The regression test demonstrates that this can happen before `MAX_BORROW_INDEX_RAY` is reached, after which both withdrawal and repayment revert with `MathOverflow`. [16](#0-15)  No privileged action is required to trigger the already-admitted state once the market size is present. [17](#0-16) 

### Recommendation
Do not let debt-value multiplication become a fatal precondition for market operations. Compute the new index and accrued debt with saturating or explicitly bounded value arithmetic, and cap the effective accrued debt value at the same representable bound before deriving supplier rewards. Alternatively, enforce borrow caps against `scaled_debt * MAX_BORROW_INDEX_RAY` so no admitted market can cross the representable-value cliff. Add a regression covering withdrawal, repayment, liquidation, recapitalization, and `update_indexes` at the largest configured market size. [3](#0-2) [4](#0-3) 

### Proof of Concept
1. In a listed market `H = {hub_id, asset}`, supply a very large amount through `Controller::supply(caller, supplier_account, spoke_id, [(H, supply_amount)])`. [18](#0-17) 
2. Supply collateral on another listed market and borrow most of `H` through `Controller::borrow(caller, borrower_account, [(H, borrow_amount)], None)`, leaving scaled `borrowed` large enough that the next admissible index makes `borrowed * new_borrow_index > i128::MAX`. [19](#0-18) 
3. Advance ledger time and call `Controller::update_indexes(caller, [H])`. [17](#0-16) 
4. `pool_update_indexes_call` invokes `Pool::update_indexes`, which calls `interest::global_sync` for `H`. [20](#0-19) [21](#0-20) 
5. `calculate_supplier_rewards` multiplies scaled debt by the new borrow index and panics with `MathOverflow`, so `last_timestamp` is not committed. [1](#0-0) 
6. Repeating `update_indexes` fails identically, and `repay`, `withdraw`, liquidation settlement, and `recapitalize` on `H` also fail because they synchronize the same stale market first. [22](#0-21) [16](#0-15)

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }
```

```rust
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```
