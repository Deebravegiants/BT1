### Title
Stale `{ xpub, publicKey }` disclosure from `MemoizedKeychain` cache survives `removeSeeds()`/`removeAllSeeds()` - (File: features/keychain/module/memoized-keychain.js)

### Summary
`MemoizedKeychain#exportKey` caches `{ xpub, publicKey }` in an in-memory (and persisted-storage-backed) map keyed only by `keyId`, never keyed to or invalidated by seed lifecycle events. After a seed is removed via `Keychain#removeSeeds`/`removeAllSeeds`, calling `exportKey` for the same `keyId` again returns the previously cached public data instead of throwing the base class's `seed with id "..." is not initialized` error.

### Finding Description
`MemoizedKeychain#exportKey` at [1](#0-0)  checks `#getCachedKey(keyId)` before calling into `super.exportKey`, and if a cache hit exists it returns immediately without ever touching `#masters`/`#seedLockStatus` in the base `Keychain` class. The cache is populated in `#setCachedKey` at [2](#0-1)  and keyed purely by `stableStringify(keyId)` — no `seedId` binding, no invalidation hook.

The base `Keychain#removeSeeds`/`removeAllSeeds` at [3](#0-2)  only clears `#masters` and `#seedLockStatus`; `MemoizedKeychain` does not override these methods to purge `#publicKeys`. The only cache-clearing path is `MemoizedKeychain#clear`, at [4](#0-3) , which is a distinct, separate operation from `removeSeeds`/`removeAllSeeds`.

Reproduction:
1. `addSeed(seed)` → derives `seedId`.
2. `exportKey({ seedId, keyId })` (no `exportPrivate`) → cache miss, calls `super.exportKey`, then `#setCachedKey` stores `{ xpub, publicKey }`.
3. `removeAllSeeds()` (or `removeSeeds([seed])`) → wipes `#masters`/`#seedLockStatus` in base class, but `#publicKeys` on `MemoizedKeychain` is untouched.
4. `exportKey({ seedId, keyId })` again → `#getCachedKey` hits, returns stale `{ xpub, publicKey }` without calling `super.exportKey`, so the base class's `seed with id "..." is not initialized` assertion in `#getPrivateHDKey` ( [5](#0-4) ) is never reached.

This directly contradicts the documented invariant and existing test expectations that `exportKey` throws `seed with id "..." is not initialized` after seed removal, as demonstrated for the base `Keychain` class in [6](#0-5)  and [7](#0-6) ; those tests exercise the plain `Keychain`, and there is no equivalent regression test for `MemoizedKeychain`.

The `MemoizedKeychain` module is registered as the actual `keychain` IoC module (`id: 'keychain', public: true`) at [8](#0-7) , and `exportKey` is exposed unmodified through `keychainApi` at [9](#0-8) , which is further surfaced as an RPC feature (`sdks/headless/src/features/keychain-rpc/index.js`) reachable by SDK/dapp consumers. `wallet.lock()` calls `keychain.removeAllSeeds()` ( [10](#0-9) ) and `wallet.removeManySeeds` calls `keychain.removeSeeds` ( [11](#0-10) ) without any coordinated cache purge in `MemoizedKeychain`.

### Impact Explanation
An unprivileged caller with access to `keychain.exportKey`/`keychainApi.exportKey` (e.g., via RPC or in-process API) that previously observed a given `seedId`/`keyId`'s public data can continue to retrieve `{ xpub, publicKey }` after the wallet has locked or explicitly removed that seed, bypassing the "seed not initialized" enforcement that the base `Keychain` guarantees. This is a metadata/address-disclosure issue (xpub/publicKey, not private key material) that persists past intended seed removal — a "locked means locked" violation for secret-adjacent metadata, scoped as stale address/xpub disclosure rather than private-key compromise.

### Likelihood Explanation
Highly reproducible and requires no special privileges: any code path that can call `keychain.exportKey` once while a seed exists, then again after `removeSeeds`/`removeAllSeeds`, triggers the bug deterministically. Preconditions (seed added, `exportKey` called once, then seed removed) are ordinary wallet lock/remove-seed flows.

### Recommendation
Override `removeSeeds`/`removeAllSeeds` (and any other seed-removal path) in `MemoizedKeychain` to purge corresponding entries from `#publicKeys`/`#storage`, or bind cache keys to seed identity so removed seeds' entries are invalidated. At minimum, invalidate/clear the entire `#publicKeys` cache whenever `removeSeeds`/`removeAllSeeds` is invoked, mirroring what `clear()` already does for `#storage`.

### Proof of Concept
```js
// memoized-keychain removeAllSeeds cache invalidation
import memoizedKeychainDefinition from '../memoized-keychain.js'
import { mnemonicToSeed } from '@exodus/bip39'
import { getSeedId } from '../crypto/seed-id.js'
import KeyIdentifier from '@exodus/key-identifier'

test('exportKey does not leak cached public data after removeAllSeeds', async () => {
  const storage = createInMemoryStorage() // stub with get/set/delete
  const keychain = memoizedKeychainDefinition.factory({ storage, legacyPrivToPub: {} })

  const seed = await mnemonicToSeed({ mnemonic: 'menu '.repeat(12) })
  const seedId = await getSeedId(seed)
  const keyId = new KeyIdentifier({ derivationAlgorithm: 'SLIP10', derivationPath: "m/0'/2'/1'", keyType: 'nacl' })

  await keychain.addSeed(seed)
  const first = await keychain.exportKey({ seedId, keyId })
  expect(first.publicKey).toBeDefined()

  keychain.removeAllSeeds()

  // Expected: throws "seed with id ... is not initialized"
  await expect(keychain.exportKey({ seedId, keyId })).rejects.toThrow(
    `seed with id "${seedId}" is not initialized`
  )
})
```
Currently this test fails: the second `exportKey` call resolves with the stale cached `{ xpub, publicKey }` instead of throwing.
