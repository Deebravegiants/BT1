### Title
Owner-controlled `whenNotPaused` on cross-chain timeout refunds can permanently freeze user funds - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol, sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol, sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol, sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable` burn/lock a user's tokens in `send()` before dispatching an ISMP POST request, and only return the funds to the user via `onPostRequestTimeout()` if the message is not delivered in time. All of these `onPostRequestTimeout` functions carry a `whenNotPaused` modifier, controlled solely by the owner's `pause()`/`unpause()`. This is the exact bug class described in the referenced report: a user exit/claim path is gated behind a modifier the protocol owner controls, letting the owner (maliciously, by mistake, or by losing key control / renouncing ownership) trap already-locked/burned user funds with no way for the user to recover them.

### Finding Description
In `send()`, the sender's tokens are already removed from circulation before the cross-chain message is dispatched: [1](#0-0) 

If the request times out (never delivered on the destination chain), the *only* path back to the user is the timeout callback, invoked by the host once a relayer submits a timeout proof: [2](#0-1) 

The identical pattern exists in the lock/unlock wrapper, where underlying ERC20/WETH is refunded from escrow only through this same gated path: [3](#0-2) 

All four contracts inherit OpenZeppelin `Pausable`, with `pause()`/`unpause()` restricted to `onlyOwner`: [4](#0-3) 

Because `onPostRequestTimeout` is marked `whenNotPaused`, if the owner pauses the contract (maliciously, via a compromised key, or simply leaves it paused and later renounces ownership per the original report's scenario), any user whose transfer times out cannot reclaim their burned/locked tokens — the refund call reverts. Since the tokens were already burned (in the burn/mint variant) or already escrowed (in the lock/unlock wrapper), the user has no alternative recovery mechanism once the underlying send already succeeded and only the timeout/refund step remains blocked.

This mirrors the reported bug class 1:1: `whenNotPaused` sits on a user-triggered exit/claim function (here, the timeout-refund entrypoint that returns previously escrowed/burned value to the user) rather than only on state-changing entry (`send`)/inbound (`onAccept`) functions, letting a single admin action freeze funds that are otherwise unrecoverable through any other path in the contract.

### Impact Explanation
High. Funds that are already burned or escrowed in the contract (as a direct consequence of the user's own `send()` transaction) become permanently unreachable if the owner pauses the contract and either keeps it paused or renounces ownership. There is no other function in any of these contracts that lets a user recover funds outside of `onPostRequestTimeout`.

### Likelihood Explanation
Low-to-Medium. It requires the owner (or a compromised owner key) to pause the contract while a timeout is pending and not unpause it. This is lower likelihood than an unprivileged-attacker path, but the report explicitly frames this class as valid because a malicious/compromised/negligent owner is a realistic threat model for pausable escrow-style contracts holding user funds.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout` (and any other function that returns previously locked/burned funds to users) in `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable`. Pausing should only gate new outbound transfers (`send`) and new inbound mints (`onAccept`), never the refund/exit path that returns funds already debited from a user.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`; `params.amount` tokens are burned from the user and an ISMP POST request is dispatched.
2. The destination chain never processes the request before `params.timeout` elapses (e.g., relayer downtime, congestion).
3. Before a relayer submits the timeout proof, the owner calls `pause()`.
4. A relayer (or anyone) submits the timeout proof to the ISMP host, which calls `onPostRequestTimeout()` on the token contract; the call reverts due to `whenNotPaused`.
5. As long as the contract remains paused (owner inaction, compromised key, or renounced ownership), the user's burned tokens can never be re-minted back — the refund path is permanently blocked while the funds are permanently gone.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
