### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identifier passed to the host application's handler. Because the `shop` field is never included in the HMAC-signed material, an attacker who can obtain one genuine `(raw_body, hmac)` pair (e.g., from their own shop's webhook deliveries) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem's verification will accept it as authentic, mis-attributing attacker-controlled data to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` value pulled from the same request: [2](#0-1) 

Meanwhile, `Request#shop` is read directly and unauthenticatedly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` as the trusted tenant identifier to the app-provided handler, without any additional binding check between `shop` and the signed body: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" pattern: the identity-binding equality that should hold is `shop_header == shop_that_produced(raw_body, hmac)`, but the code only proves `hmac == HMAC(secret, raw_body)`. It never proves any relationship between the `shop` header and the body/signature. The documented handler contract confirms `shop` is treated as an authenticated field that apps are expected to trust for tenant-scoped processing: [5](#0-4) 

### Impact Explanation
Because a single API secret key (`Context.api_secret_key`) is shared across all shops using the app (Shopify does not use a per-shop signing secret for standard webhooks in this gem's model), any valid `(raw_body, hmac)` pair produced for shop A's webhook remains cryptographically valid for any other `shop` value the attacker chooses to send. An attacker who operates or controls a Shopify store that has the same app installed (a routine, unprivileged, self-service action) can:
1. Trigger a legitimate webhook delivery to a listener they control (or intercept it), capturing a valid `raw_body` and its `hmac`.
2. Replay that exact body/HMAC pair to the app's public webhook endpoint while setting `x-shopify-shop-domain` to a victim shop's domain.
3. `HmacValidator.validate` returns `true` (only body is checked), and `Registry.process` calls the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload never originated from that shop.

Any host application that uses `data.shop` from `WebhookMetadata` to scope database writes, cache keys, background jobs, or business logic (exactly as shown in the gem's own usage docs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied data under a foreign tenant's identity — a cross-tenant data-integrity/confusion issue satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have access to at least one legitimate `(body, hmac)` pair for the same app (trivially obtainable by installing the target app on their own store, which is normal, unprivileged behavior for any developer/merchant), and it requires the host application to trust `data.shop` for tenant scoping — which is the exact pattern the gem's own documentation recommends. No credentials, TLS interception, or privileged access are needed; only public HTTP access to the app's webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the value that is authenticated, or independently verify that the `shop` header corresponds to a shop that actually has an active session/installation before trusting it, e.g.:
- Include `shop`, `topic`, and `api_version` in the signable string used by `HmacValidator`, if Shopify's webhook signing were extended to support this (not currently possible since Shopify itself only signs the body) — so at minimum, document this prominently and provide a built-in cross-check.
- Alternatively/additionally, provide a built-in check in `Registry.process` that requires the caller to supply the expected/registered shop(s) and reject webhooks whose `shop` header isn't part of a known/active session set, rather than blindly trusting the header value forwarded to `WebhookMetadata`.
- At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the HMAC and must not be used as the sole tenant-authorization signal without corroboration (e.g., checking it against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no special privilege).
2. Attacker triggers any subscribed webhook topic (e.g. `orders/create`) on their own shop and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's webhook endpoint.
3. Attacker replays the identical HTTP POST to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. In `Registry.process`:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
# validate() only recomputes HMAC over request.to_signable_string == raw_body -> still matches -> passes
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
# request.shop == "victim-shop.myshopify.com" (attacker-controlled, unauthenticated)
```
5. The host app's handler processes attacker-controlled webhook `body` believing it belongs to `victim-shop.myshopify.com`, corrupting that tenant's data/state or triggering tenant-scoped side effects (e.g., queued jobs, cache writes, order records) under the wrong shop identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
