## Title
`update_token` mutates `Precisions`/`TokenContracts` decimal and contract-address metadata that in-flight cross-chain messages implicitly depend on, breaking amount conversion and message authentication for already-dispatched, not-yet-delivered transfers - (File: modules/pallets/hyper-fungible-token/src/lib.rs)

### Summary
`pallet-hyper-fungible-token` lets `CreateOrigin` call `update_token` at any time to change a registered token's per-chain `token_contract` address and ERC20 `decimals`, with no check for outstanding in-flight messages. `on_accept` (the inbound delivery handler) resolves both the source-contract identity and the decimal-scaling factor from the *current* value of `ContractToAsset`/`Precisions` at delivery time, not from anything bound to the original message. This is the same root-cause class as the reported `OffRamp.setStableManagement()` bug: a privileged config update silently repoints state that pending/in-flight requests still implicitly rely on, and there is no `pendingRequestsCounter`-style guard.

### Finding Description
- `send()` dispatches an outgoing ISMP `Send` message to `TokenContracts[dest, asset]`, with the amount converted using the erc20 decimals *from the currently-configured* `Precisions` for that `(asset, dest)` pair (`modules/pallets/hyper-fungible-token/src/lib.rs:251-295`).
- On the EVM counterpart, `HyperFungibleToken.send()` burns tokens and encodes the raw amount in the deployed ERC20's own (immutable) `decimals()`, then dispatches a POST that sits in-flight until a relayer delivers it (subject to challenge periods, timeouts, and relayer availability) - see `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:264-282`.
- When that message is finally delivered, `Pallet::on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:50-118`) does **not** use any decimals/contract-address value carried in the message. It re-reads live storage:
  - `ContractToAsset::<T>::get(source, &from)` to identify the asset from the sending contract address (line 55).
  - `Precisions::<T>::get(local_asset_id, source)` to get the erc20 decimals used to scale `message.amount` into the local balance (lines 82-83).
- `update_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:384-433`) lets `CreateOrigin` rewrite exactly these two values for a live `(chain, asset)` pair at any time:
  - For `add_chains`, it deletes the old `ContractToAsset` reverse mapping and inserts a new `token_contract`/`decimals` pair (lines 407-420).
  - For `remove_chains`, it deletes both `TokenContracts` and `Precisions` entirely (lines 423-430).
- There is no counter or guard preventing this call while messages dispatched under the *old* configuration are still in flight (unlike `EvmHost.updateHostParamsInternal`, which does gate a fee-token swap on the fee-token balance being drained first, at `evm/src/core/EvmHost.sol:617-621`. No analogous protection exists here).

Two concrete failure modes follow, both mirroring the M-02 pattern of "operator updates a config the request is implicitly bound to, and pending requests can no longer be processed correctly":

1. **Decimals mismatch → wrong minted/released amount.** If governance calls `update_token` to correct or change `decimals` for a chain while a `Send` from that chain's contract is still in flight, `on_accept` will scale the already-fixed on-chain `amount` (encoded per the *old* real ERC20 decimals) using the *new* `Precisions` value. This produces an incorrect local amount - either far larger (over-mint from the pallet's escrow/mint, i.e. unbacked mint) or far smaller (silent fund loss for the beneficiary) than what was actually burned/locked on the source chain.
2. **Contract repoint → permanently unresolvable source.** If governance repoints `token_contract`/`ContractToAsset` to a new deployment (a legitimate migration) while a message dispatched by the *old* contract address is still pending, the old reverse mapping is deleted. When that pending message is eventually relayed, `ContractToAsset::get(source, &from)` returns `None` and `on_accept` reverts with `UnknownSourceContract` (`modules/pallets/hyper-fungible-token/src/module.rs:55-56`). Because there is no facility to keep two contracts mapped to the same asset simultaneously, the funds already burned/locked on the source chain for that specific in-flight message cannot be delivered, and can only be recovered if the source-side timeout eventually fires (`on_timeout`, `modules/pallets/hyper-fungible-token/src/lib.rs`) - which only happens if a non-zero timeout was set at `send()` time; a zero-timeout send has no recovery path at all.

### Impact Explanation
- Case 1 is a direct fund-safety violation: an unprivileged user's pre-existing in-flight transfer can be minted/released at the wrong amount purely because of a later, unrelated admin action, producing either an unbacked mint (protocol insolvency) or a permanent fund loss for the recipient.
- Case 2 is a permanent freezing of funds for any message caught mid-flight during a legitimate contract migration, with no path to redress unless a timeout was explicitly configured by the sender.
- Both routes are reachable from ordinary user activity (calling `send()` on the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract) combined with a routine governance action (`update_token`), with no attacker privilege required beyond normal relaying/timing.

### Likelihood Explanation
`update_token` is documented as the normal way to "add or remove chains from an existing token's configuration" and to fix contract addresses/decimals (`modules/pallets/hyper-fungible-token/README.md:53`), so it is expected to be called in production as tokens are onboarded, corrected, or migrated. Given normal cross-chain relay latency (proofs, challenge periods, relayer scheduling), it is plausible that in-flight `Send` messages exist at the moment such an update is applied, especially during a contract migration where the old and new addresses briefly coexist. No special conditions or malicious actors are required - this is a straightforward operational hazard.

### Recommendation
- Bind the erc20 decimals (and ideally the contract-identity check) used for conversion to values captured *in the message itself* at `send()` time, or at minimum version the `Precisions`/`ContractToAsset` entries so an in-flight message's originally-observed configuration remains valid until it is delivered or times out.
- Alternatively, adopt the same mitigation pattern the report recommends for `OffRamp`: track a per-(chain, asset) in-flight counter (incremented on `send`, decremented on `on_accept`/`on_timeout`) and require it to be zero before `update_token` may change `token_contract` or `decimals` for that pair, or require an explicit migration window where both old and new contract mappings resolve to the same asset until all in-flight messages drain.

### Proof of Concept
1. Governance registers asset `X` for `StateMachine::Evm(C)` with `token_contract = A`, `decimals = 18` via `register_token`.
2. A user calls `HyperFungibleToken(A).send(...)` on chain `C`, burning tokens and dispatching an ISMP POST that encodes `amount` per contract `A`'s real 18 decimals. The message sits unrelayed (e.g., awaiting challenge period).
3. Before it is relayed, governance calls `update_token` on the pallet with `add_chains = { C: { token_contract: A, decimals: 6 } }` (a decimals correction) - or with `remove_chains = [C]` followed later by `add_chains` pointing `C` to a new contract `B` (a migration).
4. The relayer finally delivers the original message from `A`. `on_accept` reads the *current* `Precisions`/`ContractToAsset` state:
   - In the decimals-correction scenario, it scales the amount using `6` instead of the `18` the sender actually used, minting/releasing a grossly incorrect amount.
   - In the migration scenario, `ContractToAsset::get(source, A)` no longer resolves (only `B` is mapped), and `on_accept` reverts with `UnknownSourceContract`, leaving the user's burned funds unrecoverable absent a configured timeout.
