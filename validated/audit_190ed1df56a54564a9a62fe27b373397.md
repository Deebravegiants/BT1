### Title
Webhook `shop` and `topic` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via HMAC replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id` and `api_version` are read straight from HTTP headers and are never included in the signed bytes. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity handed to the app's webhook handler. Because the signature never binds to `shop`, a previously-observed valid `(raw_body, hmac)` pair can be replayed with a different `shopify-shop-domain` header and will still pass HMAC validation, letting an unprivileged webhook sender impersonate a different shop's webhook delivery.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are completely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over that same `to_signable_string` (i.e., only the body) via `Utils::HmacValidator.validate`, then immediately forwards `request.shop` (an unverified header) as the tenant identity to the registered handler: [3](#0-2) [4](#0-3) 

The equality the app relies on is: `HMAC_valid(raw_body) == true` implies `shop header == true origin shop of this body`. That implication does not hold, because the HMAC digest is computed only over `raw_body`; `shop` (and `topic`/`webhook_id`) are excluded from the signable string entirely. Any actor capable of causing (or merely receiving) one legitimately-signed delivery for *any* shop — including their own store, which they legitimately control as an app installer — obtains a `(raw_body, hmac)` pair that remains valid for arbitrary `shopify-shop-domain` header values, since that header plays no role in signature verification.

### Impact Explanation
This breaks the tenant-authentication boundary the gem provides to host applications: `Registry.process` is documented and used as the authoritative "is this webhook really from shop X" check, and `WebhookMetadata.shop` is the tenant key passed to app logic (e.g., to load/update per-shop resources). An attacker who has captured one valid signed webhook body (trivial if they are themselves an installed merchant of the app, since every shop uses the same `api_secret_key`) can re-POST that exact body with a forged `shopify-shop-domain` header, and the app will process it as legitimate data belonging to a different, arbitrary shop — a cross-tenant data-confusion primitive within webhook processing.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus one previously observed valid `(body, hmac)` pair — easily obtained by any merchant who installs the app (an unprivileged actor with respect to *other* shops' tenants) and inspects their own webhook deliveries. No access to `api_secret_key`, tokens, or the target shop's data is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body before trusting `request.shop`), so that changing the header values invalidates the HMAC, not just the body.

### Proof of Concept
1. App installed on `attacker-shop.myshopify.com`; attacker triggers a webhook event on their own store and captures the raw POST: headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
2. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only (per `to_signable_string`) and it matches `H`, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though this delivery never originated from Shopify for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
