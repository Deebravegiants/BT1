### Title
Webhook `shop` (and topic/version/id) identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that gets handed to application webhook handlers from an HTTP header, but the HMAC signature that `Utils::HmacValidator.validate` checks is computed solely over the raw request body. The `shop` field is never part of the signed material, so it can be swapped freely by anyone who can produce one validly-HMAC'd payload for their own shop, breaking the binding `hmac_signed_bytes == identity_bytes_trusted_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC using only this signable string and, once that passes, unconditionally forwards `request.shop` (a header value never covered by the signature) to the handler as authoritative tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that the given `secret` produced the given `hmac` over `to_signable_string`; it says nothing about which shop that payload/HMAC pair was originally issued for: [4](#0-3) 

Because Shopify signs webhooks with a single app-wide `client_secret` (not a per-shop secret), the HMAC over the body proves only "some shop belonging to this app produced this body," not "this specific shop produced this body." An attacker who controls (or installs the app trial on) any shop can capture one legitimately-signed webhook delivery (body + `hmac-sha256` header) for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` passes `shop: <victim-domain>` into `WebhookMetadata`, so the application's handler processes attacker-supplied body content as if the victim shop sent it.

### Impact Explanation
This crosses the tenant boundary: an unprivileged attacker who merely operates (or trials) any shop installed on the app can inject attacker-controlled webhook payloads that are attributed to an arbitrary other shop of their choosing, without any credentials belonging to that victim shop. Depending on how the host app uses the `shop` field from `WebhookMetadata` (e.g., to key data updates, trigger redactions, or update per-shop state), this enables cross-tenant data poisoning/confusion, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled or trial shop to receive one genuine signed webhook, and (2) sending an HTTP POST to the app's webhook endpoint with the captured body/HMAC and a forged `shopify-shop-domain` header — all achievable by an ordinary internet user with no special access, no leaked secrets, and no privileged account.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`/`api_version`) in the HMAC-signable string, or otherwise independently bind the header-derived shop to the signed payload/secret used for verification, so the shop identity forwarded to `WebhookHandler#handle` is cryptographically tied to the same bytes that were HMAC-verified.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and trigger a webhook (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header.
2. Build a new webhook request with the same raw body and the same `hmac-sha256` header, but set `shopify-shop-domain` (or `x-shopify-shop-domain`) to `victim.myshopify.com`.
3. Construct `ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)` and pass it to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the app secret, per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38.
5. The registered handler is invoked with `WebhookMetadata` where `shop == "victim.myshopify.com"`, as constructed in `lib/shopify_api/webhooks/registry.rb` lines 198-199, even though `victim.myshopify.com` never sent this webhook.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
