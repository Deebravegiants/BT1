### Title
Native-fee order placement in `IntentGatewayV2.placeOrder` always reverts when the host's Uniswap V2 router is unconfigured - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` (and the same pattern in `EvmHost.dispatch`/`fundRequest`) unconditionally calls `IUniswapV2Router02(uniswapV2).WETH()` / `swapETHForExactTokens` whenever a user pays order fees with native token (`msgValue > 0`), without ever checking that the host's configured `uniswapV2` router is non-zero. `EvmHost.updateHostParamsInternal` validates `hostManager`, `handler`, `consensusClient`, `hyperbridge`, and `stateMachines` as non-zero/interface-conforming, but never validates `uniswapV2`, so the router can legitimately be `address(0)` (e.g. on chains without a Uniswap V2 deployment, or simply an unconfigured/misconfigured host). This mirrors the reported Fraxlend bug class: an external call is made to an address that may be zero, with no guard, silently breaking a core user-facing entry point.

### Finding Description
`EvmHost.HostParams.uniswapV2` is a plain configurable address with no zero/contract check enforced in `updateHostParamsInternal`: [1](#0-0) 

Yet `IntentGatewayV2.placeOrder` reaches into it unconditionally as soon as an order carries `order.fees > 0` and the caller pays those fees with native token (`msgValue > 0`): [2](#0-1) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(...);
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    ...
}
```

There is no `if (uniswapV2 != address(0))` guard analogous to the `externalAssetVault != address(0)` check the external report calls out. When `uniswapV2` is `address(0)`, `WETH()` is called on an address with no code, which reverts, so the entire `placeOrder` transaction reverts — even though the ETH the user sent could otherwise have paid the input assets/predispatch escrow successfully.

The exact same unguarded pattern also exists in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest`, all of which call `_hostParams.uniswapV2` without a zero check whenever `msg.value > 0`: [3](#0-2) [4](#0-3) 

### Impact Explanation
This is Medium impact/likelihood, matching the analog's classification: it does not itself cause fund loss, but it blocks a documented, user-reachable path — placing an intent order (or dispatching an ISMP message/fee top-up) with native-token fee payment — on any host deployment where the Uniswap V2 router parameter is left unset or set to zero (a state that passes `updateHostParamsInternal`'s validation with no error). Any unprivileged caller/order-solver interacting with `placeOrder` and paying fees in native token on such a deployment cannot complete the transaction at all, even though the fee-token path works fine, so this degrades (rather than fully disables) the intents entry point, and is fully reachable from a single submitted transaction without any privileged actor.

### Likelihood Explanation
Likelihood is Medium: it requires a host configuration where `uniswapV2` was never set (or intentionally left `address(0)` on a chain with no Uniswap V2 deployment) combined with a user/solver choosing to pay order fees in native token rather than the fee token. Both conditions are realistic — nothing in the validated `HostParams` invariants forces `uniswapV2` to be non-zero, and native-fee payment is an explicitly supported, documented payment mode (see `EvmHost.dispatch` and the IntentGateway docs referencing native payment).

### Recommendation
Add an explicit check before dereferencing the router in `IntentGatewayV2.placeOrder` (and in `EvmHost.dispatch`/`fundRequest`), e.g.:
```solidity
if (msgValue > 0) {
    address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
    if (uniswapV2 == address(0)) revert UniswapV2RouterUnset();
    ...
}
```
Additionally, consider enforcing a non-zero (and interface-conforming, where feasible) `uniswapV2` in `EvmHost.updateHostParamsInternal`, the same way `hostManager`, `handler`, and `consensusClient` are validated, so misconfiguration is caught at parameter-update time rather than surfacing as a revert at every native-fee call site.

### Proof of Concept
1. Deploy/initialize `EvmHost` (or update its params via `updateHostParams`) with `uniswapV2 = address(0)` — this passes all current validation in `updateHostParamsInternal`, since only `hostManager`, `handler`, `consensusClient`, `hyperbridge`, and `stateMachines` are checked.
2. Deploy `IntentGatewayV2` wired to this host.
3. Any user calls `placeOrder` with an `order.fees > 0` and sends `msg.value > 0` to cover those fees.
4. Execution reaches `IUniswapV2Router02(uniswapV2).WETH()` with `uniswapV2 == address(0)`; the call reverts (no code at target), reverting the whole `placeOrder` transaction — order placement with native fee payment is permanently unusable on this host until `uniswapV2` is set. The identical failure occurs for `EvmHost.dispatch{value: msg.value}(...)` and `EvmHost.fundRequest{value: msg.value}(...)` under the same host configuration.
