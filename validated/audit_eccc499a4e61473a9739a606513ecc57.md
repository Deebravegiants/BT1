## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only HMAC-validates the webhook's raw body. The `shop` (and `topic`/`webhook_id`) values that are handed to the host application's handler as trusted, verified data come from HTTP headers that are **not** part of the signed payload. Any actor able to obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` (e.g., by triggering a webhook on their own, legitimately installed shop) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report the request as verified and dispatch it under the attacker-chosen shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string` (i.e. the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authenticity of the request, then forwards the unauthenticated `shop` header value straight to the application handler as trusted metadata: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that produced/authorized this body`. In reality the gem only proves `hmac == HMAC(body, api_secret_key)`; it never proves the `shop-domain` header is bound to that body. Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any tenant that can legitimately trigger a webhook for their own store obtains a `(body, hmac)` pair that is valid for **any** shop-domain header value, since the header is excluded from the signed content.

The library's own documentation reinforces the false guarantee: it states that `Registry.process` "will verify the request did indeed come from Shopify" with no caveat that the shop attribution is unauthenticated: [5](#0-4) 

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a host application that trusts `WebhookMetadata#shop` (as the gem's API and docs imply it should) to decide which tenant/session a webhook event applies to can be made to process attacker-supplied body content under a victim shop's identity. This can lead to data being attributed to, or actions being taken against, the wrong merchant/tenant purely by an attacker who controls their own (legitimately installed) shop — no access token, `client_secret`, or `api_secret_key` needed.

### Likelihood Explanation
Any developer/merchant who can install the app on a shop they control (a common, unprivileged capability for public apps) can capture one authentic `(raw_body, x-shopify-hmac-sha256)` pair from their own webhook delivery and replay it against the app's webhook endpoint with a modified `x-shopify-shop-domain` header. `Registry.process`'s only check — `Utils::HmacValidator.validate(request)` — will still pass, since it never inspects the header.

### Recommendation
- Include the shop domain (and ideally topic/webhook id) as part of the data verified for authenticity, or require the host application to independently correlate `WebhookMetadata#shop` against a currently-installed session/shop record before trusting it for tenant-scoped operations.
- Update `docs/usage/webhooks.md` to clearly state that `Registry.process` only authenticates the request body, not the `shop-domain` header, and that consuming applications must independently validate the shop is one of their currently-installed/authorized shops before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event with body `B` (e.g. `orders/create` on a controlled test order).
2. Attacker's endpoint (or a network capture) records the delivered headers `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, and body `B`.
3. Attacker POSTs the exact same headers/body to the victim app's webhook route, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` over body `B` only — it still matches `H`, because the header change did not affect `to_signable_string`.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e. the host application processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
