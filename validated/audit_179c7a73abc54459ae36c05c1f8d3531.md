## Title
Webhook `shop` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery via signature replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC over the raw request body, then dispatches the handler and builds `WebhookMetadata` using the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers — none of which are covered by that HMAC. An attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's secret (e.g. by installing the app on their own store and capturing a legitimate webhook delivery) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header values. The signature check still passes because it only verifies the body bytes, so the handler executes believing the event originated from an arbitrary victim shop and topic.

## Finding Description
The identity binding that should hold is: **HMAC-verified bytes ⇒ the shop/topic attributed to the event**. In this gem that binding is broken.

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns solely `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.topic` for handler lookup and `request.shop` for the metadata passed into the handler: [4](#0-3) 

Because the webhook endpoint is a public, unauthenticated HTTP endpoint exposed to the internet (there is no other authentication besides this HMAC check), any external actor who can obtain one valid signed body — trivially done by installing the app on their own store, which is a normal, unprivileged action, and capturing any webhook Shopify sends them — can resend that exact `raw_body` + `hmac` to the app's webhook URL with a forged `x-shopify-shop-domain` header naming a victim shop and/or a forged `x-shopify-topic` header naming a different topic than the one that was actually signed. `HmacValidator.validate` will accept it since it never inspects `shop` or `topic`, and `Registry.process` will happily route the handler and build `WebhookMetadata` attributing the body to the forged shop/topic.

## Impact Explanation
This is a cross-tenant identity confusion: the app's webhook-handling logic (which is typically keyed by `shop` for storage lookups, session invalidation, billing, deprovisioning, etc.) is invoked with an attacker-chosen `shop` value that has no cryptographic relationship to the actual signed payload. For example, replaying a legitimate `app/uninstalled` (or any) payload from the attacker's own store while spoofing the `shop` header to a victim's domain will cause the host application to run its handler logic (e.g., "wipe shop data", "revoke shop session") against the victim shop, since the gem provides no protection against this and the handler only has `request.shop` to trust. This satisfies the Critical "cross-tenant access" bar since the confused shop identity is the only tenant boundary the webhook subsystem offers to host applications.

## Likelihood Explanation
Likelihood is high for any application that exposes its webhook endpoint publicly (as required by Shopify's webhook delivery model) and that is a public/multi-tenant app. Any actor can independently install the target app on a store they control (an ordinary unprivileged action) and receive genuinely-signed webhook deliveries, giving them a valid `(raw_body, hmac)` pair usable to spoof the `shop` (and `topic`) headers against the same shared endpoint.

## Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string (or otherwise cryptographically bind them to the payload before verification), and/or independently verify that the `shop`/`topic` headers correspond to a webhook actually registered/expected for that shop before dispatching to a handler in `ShopifyAPI::Webhooks::Registry.process`.

## Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures `(B, H)` from network traffic to their own endpoint (they control the receiving server/proxy for their own store's webhooks in many setups, or can otherwise capture the delivered payload).
4. Attacker sends a new HTTP POST to the same app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: orders/create` (or any registered topic, forged)
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — this succeeds because `B` and `H` are unchanged. [5](#0-4) 
6. The handler for the forged topic is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is the attacker-forged `victim-shop.myshopify.com` value. [6](#0-5) 
7. The host application's business logic executes as if the event legitimately originated from the victim shop, despite the HMAC never having authenticated that shop attribution.
