### Title
Legacy (pre-SIMD-186) fee-only rollback path under-reports `loaded_accounts_data_size`, allowing underpriced cost-model billing for fully-loaded large accounts - ([File: svm/src/account_loader.rs])

### Summary
When `load_transaction_accounts` fails after already loading every account in the transaction (e.g. due to `ProgramAccountNotFound`/`InvalidProgramForExecution` discovered only in the final program-ownership check), `load_transaction` in `svm/src/account_loader.rs` decides how to report `loaded_accounts_data_size` for the resulting `FeesOnlyTransaction`. If the `define_ltds_fee_only_semantics` feature is not yet active, it falls back to `RollbackAccounts::data_size()`, which only sums the bytes of the nonce and fee-payer accounts, silently discarding the bytes of every other (potentially huge) account that was actually loaded before the failure.

### Finding Description
The attacker-reachable path is:
`validate_transaction_fee_payer` (`svm/src/transaction_processor.rs:781-831`) builds `RollbackAccounts` via `RollbackAccounts::new` [1](#0-0) , which for distinct nonce/fee-payer addresses produces `RollbackAccounts::SeparateNonceAndFeePayer` [2](#0-1) .

`load_transaction` then calls `load_transaction_accounts`, which iterates and loads every account in the message (accumulating true sizes into `loaded_tx_data_size`) and only checks program ownership/existence in a final loop over `program_instructions_iter()` [3](#0-2) . This means all writable/readonly accounts — including arbitrarily large ones — are fully loaded and their sizes accumulated into `loaded_tx_data_size` before any `ProgramAccountNotFound`/`InvalidProgramForExecution` error is raised.

Back in `load_transaction`, on this `Err`, the reported `loaded_accounts_data_size` for the `FeesOnlyTransaction` is chosen based on the feature flag: [4](#0-3) 
- If `define_ltds_fee_only_semantics` is active, it correctly uses the accumulated real size (`loaded_transaction_data_size`).
- If not active (legacy semantics), it uses `tx_details.rollback_accounts.data_size()`, which only sums nonce + fee-payer byte lengths [5](#0-4) , ignoring every other loaded account's size.

The code's own comment acknowledges this is a known deficiency slated for removal by the SIMD-186 fee-payer data-size amendment [6](#0-5) . Since this data size feeds directly into `CostModel::calculate_cost_for_executed_transaction` / `calculate_loaded_accounts_data_size_cost` for cost-tracker/block-cost accounting [7](#0-6) [8](#0-7) , an attacker can cause the validator to perform full-size account reads while the cost model only bills for the tiny nonce/fee-payer footprint, as long as this legacy (non-SIMD-186) code path is exercised (i.e., before/where `define_ltds_fee_only_semantics` is inactive).

### Impact Explanation
This is a materially underpriced-execution / resource-exhaustion issue: an unprivileged sender can submit ordinary transactions (distinct durable-nonce and fee-payer accounts, large read/write account lists, and a final instruction targeting a nonexistent or non-executable program) that force the validator to load large account data sets while the compute/loaded-accounts-data-size cost billed and tracked against block limits reflects only the small nonce+fee-payer size. Repeated at scale this lets an attacker under-pay for loaded-account-data-size limits and consume disproportionate I/O/CPU relative to what the cost tracker records, falling into the "underpriced compute/storage work, resource exhaustion at near-zero cost" bounty category.

### Likelihood Explanation
This requires only unprivileged transaction construction: a `SeparateNonceAndFeePayer` transaction (nonce address ≠ fee-payer address), a set of large pre-funded accounts referenced in the message, and one instruction whose program id does not exist or is not owned by a recognized loader, guaranteeing failure in the final ownership-check loop of `load_transaction_accounts` after all accounts have already been loaded. The condition is entirely gated by whether `define_ltds_fee_only_semantics` (SIMD-186 amendment) has been activated on the target cluster; where it is inactive, the bug is fully and repeatably triggerable with a single crafted transaction, no special privileges needed.

### Recommendation
Remove the legacy fallback branch (or force it to always use `loaded_transaction_data_size` regardless of the feature flag) so `FeesOnlyTransaction::loaded_accounts_data_size` always reflects the real bytes touched during `load_transaction_accounts`, matching the invariant that declared loaded-accounts-data-size must upper-bound actual work performed, independent of feature-activation status.

    // loaded transaction data size for the cost model. This function will be removed by
    // the fee-payer data size amendment to SIMD-186.
    pub(crate) fn data_size(&self) -> usize {
        let mut total_size: usize = 0;
        for (_, account) in self.iter() {
            total_size = total_size.saturating_add(account.data().len());
        }
        total_size
    }
