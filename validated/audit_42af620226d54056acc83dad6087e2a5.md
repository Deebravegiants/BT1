### Title
Permanent loss of pre-seed/donation LT residue via unchecked `owner()` sweep in `_sweepLTToOwner` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._sweepLTToOwner`, invoked unconditionally at the end of the permissionless `finalizeGraduation`, transfers "rebalance residue" LT to `owner()` with no check that `owner()` is non-zero. `Bonding` is `Ownable2StepUpgradeable`, whose standard, un-overridden `renounceOwnership()` can set `owner()` to `address(0)`. If that ever happens (intentionally or by admin mistake), every subsequent hostile-pre-seed / donation-residue sweep silently burns real LT to the zero address instead of reverting, exactly mirroring the reported `CvgSDT.mint` pattern where `sdt.transferFrom(msg.sender, veSdtMultisig, amount)` is executed without checking `veSdtMultisig != address(0)`.

### Finding Description
`finalizeGraduation` always ends with: [1](#0-0) 

```solidity
function _sweepLTToOwner(address lt, uint256 keep) internal {
    uint256 bal = IERC20(lt).balanceOf(address(this));
    if (bal <= keep) return;
    uint256 amount = bal - keep;
    address recipient = owner();
    IERC20(lt).safeTransfer(recipient, amount);
    emit LTRescued(lt, recipient, amount);
}
```

`recipient = owner()` is read and used directly, with no `ZeroAddress` guard — unlike almost every other admin-address consumer in this codebase (`FeeVault.initialize`/`setFeeTo`, `Zap.initialize`, `Bonding.transferCreator`), which explicitly reject `address(0)`.

`Bonding` inherits `Ownable2StepUpgradeable` and never overrides `renounceOwnership()`: [2](#0-1) 

Once the owner calls the standard OZ `renounceOwnership()` (a legitimate, documented path for "decentralizing" a protocol, and something teams do at end-of-life or by mistake), `owner()` permanently returns `address(0)`. From that point on, any hostile-pre-seed/donation graduation (`_seedUniswapV2Direct`/`_seedRebalancing`, as documented in the natspec above `_sweepLTToOwner`'s caller): [3](#0-2) 

produces non-zero "rebalance residue" or donated LT that `_sweepLTToOwner` will `safeTransfer` to `address(0)` inside the fully permissionless `finalizeGraduation(tokenAddress)` call: [4](#0-3) 

Since `finalizeGraduation` is callable by anyone (`test_phase2_anyone_can_finalize`), any unrelated wallet can trigger this residue-sweep-to-zero path once the owner-zero precondition exists, permanently destroying the reserve-asset LT that would otherwise have been recovered to the protocol.

### Impact Explanation
Real, transferable LT (the external BounceTech reserve asset that trader funds are denominated in) is sent to `address(0)` and is unrecoverable — a permanent, protocol-level loss of funds identical in kind to the reported issue (irrecoverable loss of a valuable ERC20 due to an unchecked zero-address destination). Because `finalizeGraduation` runs this on every hostile-pre-seed/donation graduation once triggered, the loss recurs for every subsequent graduation of this shape, compounding over time.

### Likelihood Explanation
The precondition (owner renouncing ownership) is not something an unprivileged attacker can force, but it is a standard, always-available OZ function (`renounceOwnership`) that is never disabled or guarded here, unlike the deliberate design choices elsewhere in the codebase (e.g., choosing `Ownable2StepUpgradeable` specifically "so a bad `transferOwnership` can be cancelled ... before it takes effect" — the same design intent is completely undermined for `renounceOwnership`, which has no two-step protection and directly zeroes `owner()`). Once that state exists, triggering the loss requires nothing more than a normal hostile-pre-seed graduation and a permissionless `finalizeGraduation` call — reachable by any wallet, with no special privileges. This is analogous to the original report, where the precondition is also an admin-set zero address (`veSdtMultisig == address(0)`), not a permissionless-only bug — the loss vector on the unprivileged side (`mint`/`finalizeGraduation`) is what actually executes the fund destruction.

### Recommendation
Add a zero-address guard in `_sweepLTToOwner` (and/or cache `owner()` defensively) so a would-be sweep to `address(0)` reverts or is skipped/held rather than executed:

```solidity
function _sweepLTToOwner(address lt, uint256 keep) internal {
    uint256 bal = IERC20(lt).balanceOf(address(this));
    if (bal <= keep) return;
    address recipient = owner();
    if (recipient == address(0)) revert ZeroAddress();
    uint256 amount = bal - keep;
    IERC20(lt).safeTransfer(recipient, amount);
    emit LTRescued(lt, recipient, amount);
}
```
Additionally consider overriding `renounceOwnership()` in `Bonding` (and any other UUPS contract relying on `owner()` as a live fund-recipient) to revert, consistent with the existing rationale for choosing `Ownable2StepUpgradeable` to avoid an irreversible bad owner-address state.

### Proof of Concept
1. Protocol owner calls the un-overridden `Ownable2StepUpgradeable.renounceOwnership()` on `Bonding` (a standard, always-exposed function) → `owner() == address(0)`.
2. An attacker (or any actor) hostile-pre-seeds the HyperSwap V2 TOKEN/LT pair for a curve token approaching graduation, as in `test_brick_resistance_frontRun_dust_seed` / `test_syncDust_preseed_opensAtCurveRatio` in `TwoPhaseGraduation.t.sol`.
3. Trading continues until `Bonding.triggerGraduation(tokenAddress)` fires phase 1 (permissionless).
4. Any wallet calls `Bonding.finalizeGraduation(tokenAddress)` (permissionless) — the rebalance path leaves non-zero LT residue in `Bonding`, and `_sweepLTToOwner` executes `IERC20(lt).safeTransfer(address(0), amount)`, permanently destroying that LT. [1](#0-0)
