Based on my investigation, the strongest analog for this Apache Tika resource-consumption bug class (attacker-controlled length field driving oversized allocation during untrusted-input parsing) is the digest-count field in `Codec.DecodeHeader` in the Solidity consensus verifier.

### Title
Unbounded attacker-controlled digest count causes unbounded memory allocation in `Codec.DecodeHeader` - (File: evm/src/consensus/Codec.sol)

### Summary
`Codec.DecodeHeader` reads a SCALE compact-encoded `length` field directly from an untrusted, relayer-submitted parachain header and immediately allocates `Digest[] memory digests = new Digest[](length)` before any bound is validated against the remaining bytes in the header buffer.

### Finding Description
`DecodeHeader` decodes the digest count via `ScaleCodec.decodeUintCompact(slice)`, which for compact-encoding mode 3 can represent values up to `2^53` (`decodeUint256(read(data, l))` with `l` up to 8 bytes), and immediately calls `new Digest[](length)` with no sanity check against the actual size of `encoded` or any protocol-level maximum digest count. [1](#0-0) 
Only the subsequent per-item reads (`Bytes.readByte`, `Bytes.read`) enforce `require(self.offset + len <= self.data.length)` bounds — but that check happens per loop iteration, after the full array is already allocated up front. [2](#0-1) 

This function is reachable from a single relayed consensus proof: `EcdsaBeefy.verifyParachainHeaderProof` calls `Codec.DecodeHeader(para.header)` for every parachain header supplied in an `ParachainProof`, which is fully attacker/relayer-controlled input submitted as part of `handleConsensus`. [3](#0-2) [4](#0-3) 

The SP1-based BEEFY path decodes headers similarly via ABI-decoded `ParachainHeader[]` inputs that flow into hashing/verification without the codebase visibly bounding header/digest sizes at the entry point. [5](#0-4) 

### Impact Explanation
Because Solidity's `new T[](n)` triggers immediate memory expansion proportional to `n`, and EVM memory-expansion gas cost is quadratic, an attacker-crafted header with an inflated digest-count field forces the EVM to attempt a very large memory allocation. In practice EVM gas metering bounds the worst case to "revert on out-of-gas," so the primary victim is the caller's own gas (this differs from Tika, which has no execution-cost metering and can genuinely exhaust host memory). This limits the severity: it does not on its own achieve theft/freezing of funds or forged message delivery, and does not appear to make a route permanently unable to deliver messages, since it is a per-transaction revert, not a stored/poisoned state. I could not find evidence that this decoding path is also used off-chain (in an unmetered relayer/indexer context) where it would have unmetered memory-exhaustion impact analogous to CVE-2020-1950 — my searches for a corresponding unbounded Rust-side header/digest decoder did not surface one within the scope investigated.

### Likelihood Explanation
Uncertain/low-to-unproven: reaching this path requires a relayer to submit a `handleConsensus` proof with a crafted parachain header; the codebase's Rust-side proof/consensus clients that build `ParachainProof`/`ParachainHeader` structs are not the attack path, since an attacker can submit raw calldata directly to `handleConsensus`/`SP1Beefy` proof verification without going through the honest relayer tooling.

### Recommendation
Add an explicit upper bound check on the decoded `length` in `Codec.DecodeHeader` (and in `decodeDigestItem`'s inner `length`) against a sane maximum (e.g., derived from `encoded.length` or a fixed protocol constant) before calling `new Digest[](length)`, mirroring the `MAX_VALIDATORS` / `MAX_PROOF_DEPTH` bound patterns already used elsewhere in the codebase (e.g. `modules/consensus/pharos/verifier/src/state_proof.rs` and `modules/consensus/pharos/primitives/src/spv.rs`).

### Proof of Concept
Not independently verified against a running EVM instance; conceptually: submit a `handleConsensus` call whose `ParachainProof.parachains[i].header` bytes begin with a valid 32-byte parentHash, a valid compact blockNumber, 32-byte stateRoot, 32-byte extrinsicsRoot, followed by a SCALE compact-encoded digest count using mode-3 encoding set to a very large value (e.g., near `2^32`), with no further bytes. `Codec.DecodeHeader` will attempt `new Digest[](that large value)` before the loop's `readByte`/`read` bound checks can reject the malformed short buffer, consuming disproportionate gas relative to the tiny calldata submitted.

**Uncertainty note:** I was not able to fully confirm the actual on-chain gas/revert behavior of `new Digest[](length)` for very large `length` values in this specific Solidity version/compiler configuration, nor find a corresponding unmetered off-chain parser reachable from the same untrusted input — both would materially affect the true severity of this finding. Given the constraints of the scan (Medium/High/Critical only, and rejection of "resource-only" analogs without concrete fund/route impact), this finding is borderline and its qualification under the given severity bar is uncertain.

    /// @dev Reads `len` bytes from the slice at the current offset and advances the cursor.
    function read(ByteSlice memory self, uint256 len) internal pure returns (bytes memory) {
        require(self.offset + len <= self.data.length);
        if (len == 0) {
            return "";
        }
        uint256 addr = Memory.dataPtr(self.data);
        bytes memory slice = Memory.toBytes(addr + self.offset, len);
        self.offset += len;
        return slice;
    }
