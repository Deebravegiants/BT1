### Title
Webhook shop/topic/id fields are not covered by the HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the webhook are read straight from unauthenticated HTTP headers. Because the app's `client_secret` (used to compute/verify webhook HMACs) is shared across every shop that installs the app, any merchant can capture a validly-signed webhook body from their own store and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled data under a different shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are parsed from the request headers and are never part of the signed string: [3](#0-2) 

`HmacValidator.validate` only proves that `@raw_body` was signed with the app's `api_secret_key`; it says nothing about which shop, topic, or webhook id the caller claims the body belongs to: [4](#0-3) 

`Registry.process` validates only this body-HMAC, then immediately trusts the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` and dispatch to the app's handler: [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Because the HMAC covers only `raw_body`, this equality does not hold — `shop` is fully attacker-controlled at the HTTP layer while the "authentication" only proves the body bytes came from an entity possessing `Context.api_secret_key`. Since `api_secret_key`/`client_secret` is a single value shared by the app across *all* installing shops (it is not shop-specific), any merchant who installs the app can:
1. Trigger/capture any legitimate webhook delivery to their own shop (a validly HMAC-signed body + real headers).
2. Replay that exact body to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because the body bytes are unchanged and were legitimately signed by Shopify with the shared secret; `Registry.process` then hands `WebhookMetadata` claiming `shop: <victim-shop>` to the host app's handler.

Any host application that uses `WebhookMetadata#shop` to look up/scope tenant data, sessions, or trigger per-shop side effects (the intended and documented usage) will act on forged data believing it originates from the victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged merchant with their own legitimate app installation can cause the app to process attacker-supplied webhook payloads under another merchant's shop identity. Depending on how the host app uses the `shop` field from `WebhookMetadata` (e.g., to write data, invalidate caches, or trigger business logic scoped to that shop), this can lead to cross-tenant data corruption or forged events attributed to a victim's store, satisfying the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
The prerequisite is only that the attacker be a legitimate (unprivileged) user of the app on their own shop — no access to the app's `client_secret`, tokens, or victim credentials is required. Capturing a valid signed webhook body from one's own store and replaying it with modified headers is trivial (webhook signing secret is shared across all shops of a given app), making this readily exploitable by any installing merchant.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signed payload, or otherwise cryptographically bind them to the signed body (e.g., verify `shop` against a known/authorized session store keyed by the topic+webhook_id from a prior registration, rather than trusting the header value verbatim). At minimum, document that `Request#shop`/`topic` are unauthenticated header values and must not be used by host apps as trusted tenant identifiers without independent verification (e.g., cross-check against an actively registered webhook subscription for that shop).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the same app `client_secret`.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own shop and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
3. Attacker POSTs the identical body/HMAC to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (topic/webhook-id headers can also be altered to fit an existing registration).
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com`; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the shared secret: [6](#0-5) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, processing it as if Shopify itself confirmed this data belongs to the victim shop.
