## Title
Uniswap V4 venue pricing guard bounds only *reference deviation*, not execution cost — an order placer can move the underlying pool within the configured band to repeatedly siphon LP-backed inventory from the intent-fill venue - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
Hyperbridge's Simplex intent solver can price and fund cross-chain/same-chain `IntentGatewayV2`/`IntentGatewayV3` fills directly from a Uniswap V4 concentrated-liquidity position instead of a static curve. The only defense against a manipulated pool is `checkPriceGuard`, a **deviation-from-a-static-reference** check bounded by `maxDeviationBps` [1](#0-0) . Exactly like the reported OHM report — where a `THRESHOLD` bounded the allowed price move but repeated in-band trades still let a user siphon minted `OHM` — this guard bounds *how far* the quote can drift, but never checks execution cost/impact, letting an attacker move the pool within the tolerated band and repeatedly extract value from the solver's LP-backed inventory through ordinary intent fills.

### Finding Description
When a pair has no static bid/ask curve, `resolveLegRates` reads the live Uniswap V4 pool mid-price via `computeDirectPoolPriceUsd` and uses it, unmodified, as the fill rate [2](#0-1) . The venue-pricing flow doc confirms this is the *only* check on the path and explicitly notes it does not account for real execution cost: `computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96` with no size/impact term, and "the pool's fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price" [3](#0-2) .

`checkPriceGuard` only rejects a quote when it deviates from a fixed `referencePrice` by more than `maxDeviationBps` [4](#0-3) . This is the direct analog of the OHM report's `THRESHOLD`: it defines a tolerated band the attacker can move the market within, not a bound on how much value an in-band move can extract. The same guard also feeds `referenceRate`, which sizes confirmation depth from the same manipulable venue quote [5](#0-4) .

When the wallet lacks enough output token, the solver withdraws the deficit straight from the LP position via `UniswapV4FundingPlanner.planWithdrawalForToken`, which decreases liquidity and credits the fill from the pool's *current* state, priced at the same manipulable mid [6](#0-5) . Documentation for this feature explicitly acknowledges the trust assumption: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote" [7](#0-6) .

The attack shape mirrors the OHM report precisely:
1. Move the pool price via ordinary trades on the underlying Uniswap V4 pool, staying within `maxDeviationBps` of the configured `referencePrice` so `checkPriceGuard` still passes.
2. Submit an `IntentGatewayV2`/`V3` order (or bid as a favorable counterparty) that the solver fills at the now-skewed but still "in-band" venue rate, drawing the payout from the solver's LP position (`planWithdrawalForToken`) at that skewed price.
3. Trade back to restore the pool close to its original price (still within the band) to reset for the next round, repeating the extraction every block/cycle, exactly as the OHM PoC alternates `deposit → swap → withdraw → swap back`.

### Impact Explanation
Repeated in-band manipulation lets an attacker extract value from the solver's Uniswap V4-backed inventory on every cycle at low cost, bounded only by gas and pool depth — a direct, repeatable drain of protocol/solver-held funds through the intent-fill mechanism, matching "Medium" severity in the original report (bounded but real, recurring siphon of funds via a threshold-gated economic design).

### Likelihood Explanation
The guard is optional (`referencePrice`/`maxDeviationBps` can be left unset, "leaving the chain unguarded" [8](#0-7) ) and, even when configured, only bounds deviation, not cost — so any operator running venue-priced pairs against a manipulable pool is exposed. Anyone able to trade on the referenced Uniswap V4 pool and place/win intent orders (both unprivileged, permissionless actions) can execute the cycle; no special privilege is required, matching the original report's finding that the attack "can go on" as long as it stays inside the tolerated band.

### Recommendation
Apply the same mitigation direction the original report suggests: tighten `maxDeviationBps` and/or require the guard to account for execution cost (pool fee tier, size/impact), not just static deviation, before pricing a fill or withdrawing from the LP position. Consider adding a minimum time-weighted price check (TWAP) instead of a single-block mid, and factor the position's fee tier into `computeDirectPoolPriceUsd` as flagged in the venue-pricing flow notes.

### Proof of Concept
Conceptually mirrors the OHM PoC's `deposit → swap → withdraw → swap back` loop:
1. Configure `[vault.uniswapV4]` with `referencePrice`/`maxDeviationBps` for a venue-priced pair (as in `docs/content/developers/evm/simplex/pricing.mdx`).
2. Attacker trades against the underlying Uniswap V4 pool to push `sqrtPriceX96` to the edge of the `maxDeviationBps` band (still passing `checkPriceGuard`).
3. Attacker places/wins an intent order priced off the skewed venue quote; `resolveLegRates`/`referenceRate` accept it since deviation is within band [2](#0-1) ; the solver funds the payout by draining the LP position via `planWithdrawalForToken` at the skewed price [9](#0-8) .
4. Attacker trades back toward the reference price (still within band) and repeats the cycle each block/window, extracting value each time at the cost of pool trading fees only.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
