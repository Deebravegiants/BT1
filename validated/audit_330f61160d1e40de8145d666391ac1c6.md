The `shop` value passed into `WebhookMetadata` (line 198) comes from `request.shop`, which reads the `shop-domain`/`x-shopify-shop-domain` HTTP header (`lib/shopify_api/webhooks/request.rb:20-23`) — a value that is never included in the HMAC-signed payload.

### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is derived from the `shop-domain` HTTP header. `Registry.process` validates the HMAC over the body only, then trusts `request.shop` to build the `WebhookMetadata` passed to the app's `WebhookHandler`. Because the header is not part of the signed material, the equality `shop-domain header == shop bound by HMAC` does not hold: the HMAC binds the body to the app's `client_secret`, but says nothing about which shop the header claims.

### Finding Description
`Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac-sha256` header. For webhook requests, `to_signable_string` is: [1](#0-0) 
i.e., only `@raw_body`. Meanwhile `shop` is read straight from a header with no cryptographic binding: [2](#0-1) 
`Registry.process` performs the HMAC check and then immediately trusts `request.shop` for tenant attribution: [3](#0-2) 

Because every shop that installs the app is delivered webhooks signed with the same app-level `client_secret` (not a per-shop secret), an attacker who controls any shop installation of the target app can capture one of their own legitimately-signed webhook deliveries (valid body + valid HMAC) and resend it to the app's webhook endpoint with the `shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. The HMAC still validates because it is computed only over the untouched raw body, yet the host application's `WebhookHandler#handle` receives `WebhookMetadata` claiming to be from the victim shop, breaking the identity binding: "shop authenticated (HMAC over body) vs. shop asserted for tenant routing (header)."

### Impact Explanation
This crosses a tenant boundary: an attacker with access to only their own shop's webhook traffic can make the host app process attacker-controlled but "HMAC-verified" data under a victim shop's identity. Depending on how the host application's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up/store per-tenant records, update inventory, or trigger a redact/data flow), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/merchant who has installed the app on even one shop can generate a validly-HMAC'd webhook payload for that shop and simply replay it with a modified header value; no access to `api_secret_key` or any victim credential is required, only observation of one's own legitimate webhook delivery. This makes the analog directly and cheaply reachable through the gem's documented API surface (`Registry.process`).

### Recommendation
Bind the shop identity into the signed material, or otherwise reject any webhook where the header-asserted `shop` cannot be cryptographically tied to the payload. Concretely, include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in `Request#to_signable_string`, or validate that the `shop-domain` header matches a shop value embedded in the verified body/metadata before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and capture a legitimate webhook delivery (raw body `B`, header `hmac-sha256: H`, header `shop-domain: attacker.myshopify.com`).
2. Replay the same body `B` and same `H` to the app's registered webhook endpoint, but set `shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B` [4](#0-3) .
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"`, even though the body content and signature only prove authenticity for `attacker.myshopify.com` [3](#0-2) .
