### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant shop-header forgery - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)`, which verifies `request.hmac` against `request.to_signable_string`, and `Request#to_signable_string` returns solely `@raw_body` — never the `shop-domain` header. `Request#shop` (used as `WebhookMetadata#shop`) is read straight from the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header, so the shop identity handed to the host app's handler is not cryptographically bound to the signature that authenticated the payload.

### Finding Description
Binding claimed by the invariant: `shop authenticated by signature == shop delivered to handler`. Tracing the code:

- `Request#shop` reads directly from the header with no signing: [1](#0-0) 
- `Request#to_signable_string` is only the raw body, excluding all headers including `shop-domain`: [2](#0-1) 
- `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares to the received `hmac`, so it only proves "this body was signed with the app secret", not "this body belongs to this shop": [3](#0-2) 
- `Registry.process` validates only the HMAC, then immediately trusts `request.shop` when building `WebhookMetadata`, which is handed to the app's handler as the tenant identity: [4](#0-3) 
- The documented usage pattern explicitly tells developers to key their persistence/business logic off `data.shop`:  (`docs/usage/webhooks.md`, lines 24-26, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

Because the app's `client_secret` (`Context.api_secret_key`) is the same for every shop that installs the app, an attacker who controls their own development shop can legitimately install the app, receive a real webhook (real body + valid HMAC signed with the shared secret), and then replay that same untouched `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop. `HmacValidator.validate` still succeeds because it never looks at the shop header, and `Registry.process` passes `WebhookMetadata#shop` = attacker-chosen victim shop to the handler. Nothing in `HmacValidator`, `Request`, or `Registry` re-derives or checks the shop from a trusted, signed source (there is no equivalent of `ShopValidator.sanitize!`/JWT `aud`/`dest` check for webhooks).

### Impact Explanation
If the host app follows the gem's documented pattern (using `data.shop` to select which tenant's records to update, e.g., background job routing, data deletion for `customers/redact`/`shop/redact`, or state changes tied to `app/uninstalled`), an attacker can trigger tenant-scoped side effects attributed to a shop they do not control. This is a cross-tenant integrity/confidentiality issue: one shop's (attacker's own) validly-signed webhook body can be attributed to another, arbitrary merchant. It is repeatable indefinitely against any victim shop domain the attacker chooses, for every webhook topic the app has registered.

### Likelihood Explanation
Preconditions: the attacker needs their own dev/test shop with the target app installed (freely obtainable, matches the assumed unprivileged-attacker capabilities), the app must expose its webhook callback route publicly (standard deployment, as shown in `docs/usage/webhooks.md`), and the app must act on `WebhookMetadata#shop` without independent shop verification (the gem's own documentation encourages exactly this). No secrets are needed by the attacker; they only replay their own legitimately-received `(body, hmac)` pair with a substituted header. Cost is a single HTTP request per forged event.

### Recommendation
Bind the trusted shop to the payload rather than to an unsigned header: include the shop domain (and topic/webhook-id) in the signable string used for HMAC verification (matching what is actually authenticated), or require the host app to reconcile `request.shop` against a shop-domain value that was independently established via OAuth/session rather than trusting the header value as-is. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used alone to select which tenant's data to mutate without additional verification.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistrySpoofTest < Minitest::Test
      def setup
        super
        ShopifyAPI::Webhooks::Registry.clear
        @topic = "orders/create"
        @real_shop = "attacker-shop.myshopify.com"
        @victim_shop = "victim-shop.myshopify.com"
        @body = '{"id":1}'
        @hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @body),
        )
      end

      def test_shop_header_not_bound_to_signature
        received_shop = nil
        handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })

        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: @topic, path: "path", delivery_method: :http, handler: handler,
        )

        # Attacker takes a validly-signed (body, hmac) pair from their own shop's
        # webhook and swaps only the shop-domain header to a victim shop.
        forged_headers = {
          "x-shopify-topic" => @topic,
          "x-shopify-hmac-sha256" => @hmac,
          "x-shopify-shop-domain" => @victim_shop, # attacker-controlled, unsigned
        }

        request = ShopifyAPI::Webhooks::Request.new(raw_body: @body, headers: forged_headers)

        # Invariant under test: shop authenticated by signature (@real_shop, since the
        # HMAC was generated for a body originating from the attacker's own shop)
        # should equal the shop delivered to the handler. It does not.
        ShopifyAPI::Webhooks::Registry.process(request)

        assert_equal(@victim_shop, received_shop) # forged shop accepted
        refute_equal(@real_shop, received_shop)   # signature says nothing about shop identity
      end
    end
  end
end
```
This demonstrates that `Utils::HmacValidator.validate` accepts the forged request (the signature never covered the shop header), and `WebhookMetadata#shop` ends up equal to the attacker-supplied victim shop rather than any shop actually authenticated by the signature, breaking the claimed SHOP BINDING invariant.
