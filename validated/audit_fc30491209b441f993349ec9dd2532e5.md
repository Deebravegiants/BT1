### Title
Webhook Shop Attribution Bypass via HMAC That Only Covers the Request Body, Not the `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` value used to attribute that webhook to a tenant is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. Because the same app-level `api_secret_key` signs every shop's webhooks and the signature never binds the shop identifier, an attacker who can obtain any one valid `(body, hmac)` pair for the app (e.g., from their own store's legitimate webhook traffic) can replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook for a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is computed from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. The `shop` accessor is a separate, independent reader for the `shop-domain` header that is never mixed into `to_signable_string`.

`Utils::HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` uses this same validator, and then immediately builds `WebhookMetadata` using `request.shop`, which is the raw, HMAC-unprotected header value: [3](#0-2) 

The identity equality that should hold is:
`shop attributed to webhook data (request.shop)` == `shop that actually authored/owns the signed body`.

This equality is broken: the HMAC only proves "this body was signed with the app's secret" — it proves nothing about which shop the body belongs to. Since one `api_secret_key` is shared across every shop installation of the app, any attacker with a store that has the app installed can capture a legitimate `(raw_body, hmac)` pair emitted for their own shop (e.g., an `orders/create` payload) and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the payload to the registered handler tagged as coming from the victim shop.

### Impact Explanation
This is a cross-tenant attribution/authentication bypass: the receiving application's webhook handler (which typically uses `data.shop` to look up the tenant's session/access token, update tenant-scoped records, or trigger tenant-scoped side effects) can be tricked into believing attacker-controlled data originated from a shop the attacker does not own. Depending on the handler's logic this enables cross-tenant data injection (e.g., forging `orders/create`, `app/uninstalled`, `shop/redact` mandatory compliance events) attributed to an arbitrary victim shop, which the gem's documentation explicitly tells integrators to trust once `Registry.process` succeeds.

### Likelihood Explanation
Requires only that the attacker control (or have observed traffic from) one shop where the target app is installed — an "unprivileged internet user" relative to the victim shop, satisfying the low-privilege bar. No access to `api_secret_key`, access tokens, or the victim's credentials is needed; only a replay of previously-observed, validly-signed body bytes with a swapped header value.

### Recommendation
Bind the shop identifier into the signed/verified material, or otherwise cryptographically/contextually tie `request.shop` to the specific webhook delivery instead of trusting the header verbatim:
- Reject/flag any webhook whose `shop-domain` does not match a shop for which the receiving app currently holds an active session/installation record before dispatching to handlers, and document this requirement prominently since the gem itself cannot enforce it without app-level state.
- Where feasible, incorporate the `webhook_id` (topic + id is unique per delivery) checked against a per-shop dedupe/allow-list keyed by installed shops, so a replayed payload from Shop A can't be accepted under Shop B's identity.
- At minimum, update documentation/handler contract to explicitly warn implementers that `data.shop` is not authenticated by the HMAC and must be independently validated against the app's known/installed shop list before being trusted for tenant attribution.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid_hmac_for_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical raw body and identical HMAC header to the app's webhook endpoint, but swaps `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` runs:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
# passes, because HmacValidator only checks @raw_body, unaffected by the shop header

handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
# request.shop == "victim-shop.myshopify.com", trusted by the handler
```
4. The application's handler processes the attacker-controlled body as if it were authentic data from `victim-shop.myshopify.com`, since the library provided no way to detect the mismatch. This is confirmed by the test suite, which shows `request.shop` is populated purely from the header and separately from HMAC validation: [4](#0-3)

          received_signature = verifiable_query.hmac
