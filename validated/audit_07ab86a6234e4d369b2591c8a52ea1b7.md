## Title
Unrestricted `CallDispatcher.dispatch()` lets anyone mint tokens through any minter-privileged contract that trusts the dispatcher's identity - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` has no access control - it is a plain `external` function callable by any address, not just by the `HyperFungibleToken`/`IntentGatewayV2` apps that are supposed to route calldata through it after an ISMP delivery. Because the same `CallDispatcher` instance is granted `MINTER_ROLE` on `HyperFungibleTokenImpl`-based tokens to support the documented "transfer-and-act" calldata flow, any unprivileged caller can invoke `dispatch()` directly with a `Call[]` that targets `token.mint(attacker, amount)`. Since the token's role check only validates `msg.sender` (which becomes the dispatcher's address via `to.call(...)`), the mint succeeds with no ISMP proof, no host involvement, and no source-chain verification at all - functionally identical to the MTDAO incident where an unopened auxiliary contract holding minter permission was invoked directly to mint tokens for profit.

### Finding Description
`CallDispatcher.dispatch()` decodes a `Call[]` and executes each entry as a low-level `.call`, with the only check being that the target has code: [1](#0-0) 

There is no `onlyHost`, `onlyApp`, or caller allow-list on this function - unlike every `IApp` callback (`onAccept`, `onPostRequestTimeout`) which is gated by `onlyHost`. The intended flow is that `HyperFungibleToken.onAccept` mints tokens to a beneficiary/dispatcher first, and only afterward forwards attacker-supplied `message.data` to `ICallDispatcher(_dispatcher).dispatch(message.data)`: [2](#0-1) 

`HyperFungibleTokenImpl`, the role-based multi-minter token variant explicitly built "for scenarios where multiple contracts need minting capabilities," exposes `mint()` gated solely on `MINTER_ROLE`, checked against `msg.sender`: [3](#0-2) 

The project's own test fixture confirms that in practice the `CallDispatcher` address is granted `MINTER_ROLE` directly on a token so that calldata-driven post-mint actions work: [4](#0-3) 

Given that setup, `token.mint(attacker, amount)` executed via `CallDispatcher` sees `msg.sender == address(CallDispatcher)`, which holds `MINTER_ROLE` - it does not matter whether the call originated from a legitimate `onAccept` calldata payload or from an attacker calling `CallDispatcher.dispatch()` directly, because `dispatch()` itself performs no authentication of its caller. The `CallDispatcher` is also documented as a shared, cross-application deployment ("Existing CallDispatcher deployments are listed on the contract addresses page"), so any token or app that grants it a privileged role for legitimate calldata composability simultaneously exposes that privilege to every external account.

### Impact Explanation
An attacker calling `CallDispatcher.dispatch()` with a `Call` targeting a token that has granted the dispatcher `MINTER_ROLE` (or any other privileged role/function keyed off `msg.sender`) can mint unlimited unbacked tokens or trigger any other privileged action gated on the dispatcher's identity, without any ISMP message, proof, relayer, or host interaction. This is an unbacked-mint / concrete theft primitive directly analogous to the MTDAO loss, and it also undermines the security assumption documented for the calldata-execution feature ("If any call in the array reverts, the entire `onAccept` handler reverts") because the attack path bypasses `onAccept` entirely.

### Likelihood Explanation
This does not require any privileged role, admin key, or governance action - only knowledge of the shared `CallDispatcher` address (which is publicly documented) and any token/contract that has granted it a role for the intended composability flow, which the project's own test setup demonstrates is a supported and expected configuration. This is trivially reachable from a single unprivileged transaction.

### Recommendation
Restrict `CallDispatcher.dispatch()` so that privileged calls cannot be triggered by arbitrary EOAs impersonating the dispatcher's identity. Options: (1) make `dispatch()` `onlyHost`/caller-restricted so only registered `IApp` contracts (or the ISMP host mid-delivery) can invoke it, (2) never grant the shared `CallDispatcher` any token-level privileged role (`MINTER_ROLE`/`BURNER_ROLE`) directly - instead route mints through the app contract's own identity, not the dispatcher's, or (3) deploy per-app dispatcher instances so a privileged role granted for one app's calldata flow cannot be exploited generically by any caller.

### Proof of Concept
1. Identify a token `T` (e.g., a `HyperFungibleTokenImpl`-based deployment) that has called `T.grantMinterRole(address(callDispatcher))` to support calldata-driven flows, as shown in the project's own fixture: `feeToken.grantMinterRole(address(callDispatcher))` [4](#0-3) .
2. Attacker builds `Call[] calls = [Call({ to: address(T), value: 0, data: abi.encodeWithSelector(T.mint.selector, attacker, hugeAmount) })]`.
3. Attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly - no `onlyHost` check exists on `dispatch` [1](#0-0) .
4. `CallDispatcher` executes `T.mint(attacker, hugeAmount)` with `msg.sender == address(CallDispatcher)`, which passes `T`'s `onlyRole(MINTER_ROLE)` check [3](#0-2) , minting arbitrary tokens to the attacker with no ISMP proof or host involvement.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```
