Found the true analog: `_sendValue` in `IntentsBase.sol` — used to release escrowed native-ETH tokens to a beneficiary via `_withdraw` (which runs from `onGetResponse` and `onAccept`/`RedeemEscrow`/`RefundEscrow`).

### Title
Malicious ETH beneficiary can permanently block escrow release/refund on native-token orders - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_withdraw()` releases escrowed native ETH to `beneficiary` via `_sendValue()`, which performs a raw `.call{value: amount}("")` and reverts the *entire* transaction with `InsufficientNativeToken` if the recipient's fallback fails. Because `beneficiary` is `order.user` or `order.output.beneficiary` (attacker-controlled at order-placement time), and because `_withdraw` is invoked from within `onGetResponse`/`onAccept`, a beneficiary contract that deliberately reverts on receiving ETH permanently blocks the cross-chain settlement callback that would otherwise finalize the order, mirroring the Cooler `onRepay()` pattern where a counterparty makes its own inbound callback fail to force an unfavorable, permanent outcome for the other party.

### Finding Description
`_withdraw()` unconditionally attempts to push native ETH to `beneficiary`: [1](#0-0) 
`_sendValue` reverts hard on failed transfer: [2](#0-1) 

This is called from `onGetResponse` (source-side cancel path, invoked by the ISMP host with `onlyHost` after Hyperbridge delivers a GET response) and from `onAccept` for `RedeemEscrow`/`RefundEscrow` (destination→source settlement/refund messages): [3](#0-2) 

Unlike `EvmHost.dispatchIncoming`, which wraps module calls in a low-level `.call()` and deletes the receipt on failure so the message can be retried indefinitely without side effects [4](#0-3) , `onGetResponse`/`onAccept` here have already mutated protocol state (or are about to) as part of the same call that performs the ETH push. If `beneficiary` (set by the order creator at placement time, fully attacker-controlled) is a contract whose `receive()`/fallback always reverts, `_sendValue` reverts, and the entire `onAccept`/`onGetResponse` call reverts. Just like the Cooler `Lender._onRepay()` which always reverts to force a loan default and seize collateral, the order creator here can set a beneficiary contract designed to always reject ETH, causing every attempt to release/refund escrow to that beneficiary to fail. Because the underlying commitment `_filled[commitment]` is never set to a non-zero value when `_withdraw` reverts (the assignment happens before the loop, but the whole call reverts atomically since Solidity storage writes are rolled back on revert), the order is permanently stuck: neither a solver's fill settlement (`RedeemEscrow`) nor a legitimate cancellation (`RefundEscrow`, or the source-side `onGetResponse` refund) can ever complete for that beneficiary/order.

### Impact Explanation
This freezes the escrowed native-ETH input tokens permanently for that order commitment — no cancellation path or fill-settlement path can succeed since every one of them funnels through `_withdraw`→`_sendValue` for a beneficiary that always reverts. Funds become irrecoverably locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract, meeting the "permanent freezing of funds" bar. It could also be weaponized by a solver: if `order.user`/`beneficiary` is malicious, the solver who already delivered output tokens on the destination chain for a `fillOrder` can never have the input escrow released to them via `RedeemEscrow`, since that message routes to the same `_withdraw` and reverts if the fee-forwarding beneficiary (also the same malicious address, since transaction fees route to `beneficiary` too) rejects ETH — causing loss to solvers as well.

### Likelihood Explanation
Any user can place an order with `order.user`/`session`/beneficiary set to a contract they control that always reverts on receiving ETH; this requires no special privilege and is directly reachable by placing a native-ETH order and then triggering the standard cancel/fill/refund flow (`cancelOrder`, `fillOrder` cross-chain settlement) — all permissionless, single-transaction-triggerable paths.

### Recommendation
Do not let a failed ETH push to `beneficiary` revert the entire settlement/cancellation callback. Wrap `_sendValue` in a try/catch (or use a non-reverting `.call` with a fallback such as crediting an internal, separately-withdrawable balance for that beneficiary/token) so that `_filled`/escrow bookkeeping updates and the ISMP callback complete successfully regardless of whether the beneficiary can receive ETH, consistent with the isolation pattern already used in `HyperbridgeLzEndpoint.onAccept` (see the documented rationale about not letting a deterministic revert brick a channel) [5](#0-4) .

### Proof of Concept
1. Attacker deploys a `RejectETH` contract with a `receive()` that always reverts.
2. Attacker calls `placeOrder` with a native-ETH input and `order.user = address(RejectETH)` (cross-chain order, destination chain X).
3. After the deadline, attacker calls `cancelOrder` from the source chain (`_cancelFromSource`), which dispatches a GET request; Hyperbridge delivers the response and the host calls `onGetResponse` → `_withdraw` → `_sendValue(address(RejectETH), amount)`, which reverts every time it is resubmitted.
4. The escrowed ETH can never be refunded to the attacker's own contract, or — in the solver-griefing variant — a solver who filled the order can never receive their `RedeemEscrow` payout because the same beneficiary/fee-forwarding path reverts, permanently locking funds in the gateway contract.
