### Title
Fee-on-transfer tokens over-credit escrow in Tron `IntentGatewayV2.placeOrder` (uses requested amount instead of actual received amount) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` credits escrow with `reducedInputs[i].amount` — computed from the caller-specified `order.inputs[i].amount` minus the protocol fee — rather than the amount the contract actually received via `safeTransferFrom`. For any ERC20/TRC20 with a fee-on-transfer, the gateway's real token balance increase is smaller than the amount it records as escrowed, mirroring exactly the SimplePlugin/StakingModule bug class in the referenced report (assuming transferred amount == requested amount).

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally increments `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the pre-transfer `order.inputs[i].amount` (see the fee computation loop at lines 359-385: `originalAmount = order.inputs[i].amount; ... reducedAmount = originalAmount - protocolFee;`) [2](#0-1) 
There is no balance-before/balance-after measurement anywhere in this path, unlike the corresponding non-Tron `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots `balBefore`/`balancesBefore` and sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing the commitment and escrow: [3](#0-2) 
The Tron variant was evidently ported without this fee-on-transfer fix, so for a fee-on-transfer input token the escrow ledger (`_orders[commitment][token]`) records more tokens than the gateway actually holds.

### Impact Explanation
Because `_orders[commitment][token]` (escrow accounting) becomes inflated relative to the gateway's real TRC20 balance, subsequent flows that pay out based on this accounting — solver settlement/fill payouts and `cancelOrder` → `withdraw` refunds — can attempt to transfer more tokens than the contract holds. In a multi-order/multi-user contract, this is not merely a self-inflicted revert for the depositor: because escrowed balances are pooled per-token across all orders, the shortfall from one fee-on-transfer order depletes the shared token balance, causing insolvency that can cause other, unrelated orders' rightful withdrawals/fills to fail or be shortchanged (last-user-can't-withdraw / permanent partial freezing of funds). This satisfies the "concrete... permanent freezing of funds" bar via unbacked escrow credit.

### Likelihood Explanation
Any TRC20/ERC20 token with a transfer fee (a known, common token category) supplied as an `order.inputs` token in a non-predispatch `placeOrder` call on the Tron deployment triggers this immediately and deterministically — no special privileges or timing needed, just a single `placeOrder` transaction from an ordinary user/solver using such a token.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the gateway's token balance before `safeTransferFrom`, compute `received = balanceAfter - balanceBefore`, and use `received` (not `order.inputs[i].amount`) both for computing the protocol fee/`reducedInputs` and for the amount credited to `_orders[commitment][token]`. Apply the same balance-diff approach to the predispatch/dispatcher-sweep branch's dust/escrow accounting for consistency with the corrected non-Tron implementation.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with a TRC20 token `FOT` that charges e.g. 1% fee on `transfer`/`transferFrom` (same as the `FeeOnTransferToken` test helper used to validate the fix on the non-Tron contract): [4](#0-3) 
2. User approves the Tron gateway for `inputAmount = 1000e18` of `FOT` and calls `placeOrder` with `order.inputs = [{token: FOT, amount: 1000e18}]` and no predispatch.
3. `safeTransferFrom` moves only `990e18` into the gateway (1% fee burned/retained by token), but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount = 1000e18` (or `1000e18` minus protocol fee if configured) — i.e., 10e18 more than the gateway actually holds for this order.
4. When the order is filled/cancelled and `withdraw`/settlement logic pays out based on `_orders[commitment][FOT]`, the shortfall is drawn from the shared `FOT` balance backing other orders, causing later withdrawals for unrelated orders in the same token to fail or be short — a direct token-balance insolvency introduced by a single `placeOrder` call.

        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
