### Title
Webhook Shop-Domain and Topic Headers Are Not Bound by the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers and passed straight to the registered handler by `Registry.process`. The identity binding that should hold — "shop verified by HMAC" == "shop acted upon by the handler" — does not hold, because the HMAC never covers the shop-domain header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) that are never included in the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only, per `to_signable_string`) and then, if valid, forwards `request.shop`, `request.topic`, and the parsed body directly to the app's registered handler as the tenant/topic identity for that webhook: [3](#0-2) 

The HMAC validator itself only ever checks `to_signable_string` against the secret: [4](#0-3) 

Equality that should be enforced: `hmac == HMAC(secret, raw_body || shop || topic)`, but the actual implementation is `hmac == HMAC(secret, raw_body)` while `shop` and `topic` are trusted unconditionally from headers. Since many webhook topics (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`) carry bodies with little or no shop-identifying content of their own, a valid HMAC computed for a webhook delivered to one shop can be replayed against a different `x-shopify-shop-domain` (and even a different `x-shopify-topic`) header value without invalidating the signature, since the gem never binds those headers into the signed content.

### Impact Explanation
The consuming application's `WebhookHandler` receives `WebhookMetadata` whose `shop` field is derived from the unauthenticated header, not from anything verified by the HMAC. If the handler uses this `shop` value to look up sessions, revoke access, delete data, or otherwise act with the app's stored per-shop credentials, an attacker who owns a legitimately-installed test/free copy of the app can capture a validly-signed webhook and replay it with a forged shop-domain header to make the host application act on a different tenant's data — i.e., cross-tenant access — using the gem's own "verified" `Request` object as the trust anchor.

### Likelihood Explanation
Exploitation requires only an installed instance of the target app (attacker's own store) capable of receiving any webhook whose HMAC does not depend on shop-specific body content, and network-level ability to replay/modify the header before it reaches the host app's webhook endpoint (e.g., proxy, custom infra, or a host app that reads the header from a source outside TLS-terminated origin verification). This is a design gap in the gem's `HmacValidator`/`Request` binding rather than a one-off implementation bug, so any application that trusts `request.shop`/`WebhookMetadata#shop` as authenticated (which the gem's own API implies, since `Registry.process` performs the HMAC check right before dispatching that value) inherits the exposure.

### Recommendation
Bind the shop domain (and topic) into the HMAC-signable content, or otherwise require `Registry.process` to independently verify that the `shop-domain` header corresponds to a value cryptographically tied to the signed request (e.g., include it in `to_signable_string`, matching how `Oauth::AuthQuery#to_signable_string` already binds `shop` and `host` into its signature). Document clearly that `Request#shop` is not currently covered by the signature so host applications are not misled into treating it as verified.

### Proof of Concept
1. Register a webhook handler for a topic whose payload body is shop-agnostic (e.g., `app/uninstalled`).
2. Using the attacker's own store, receive a legitimately signed webhook delivery; note `x-shopify-hmac-sha256` is computed over the raw body only, per `Request#to_signable_string`.
3. Replay the identical raw body and HMAC header to the host app's webhook endpoint, but substitute `x-shopify-shop-domain` with a victim store's domain.
4. `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC; `Registry.process` proceeds to invoke the handler with `WebhookMetadata#shop` set to the victim's domain, causing the host app to perform shop-scoped actions (e.g., token/session invalidation, data deletion) against the wrong tenant.
