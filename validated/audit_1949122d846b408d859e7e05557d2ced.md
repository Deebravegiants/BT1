### Title
Webhook HMAC Does Not Bind `shop-domain`/`topic`/`webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC computation. `Utils::HmacValidator` therefore only proves that the body bytes were signed by the app's secret — it proves nothing about which shop, topic, or webhook the body belongs to. A merchant who has installed the app (an unprivileged tenant from the perspective of any other tenant) legitimately receives real webhooks signed with the same shared `api_secret_key` used for every shop on the app. That merchant can replay the exact `(body, hmac)` pair they received, while forging the `shopify-shop-domain` header to name a different, victim shop. `Registry.process` accepts this as valid and dispatches the handler with the attacker-chosen `shop`, breaking the binding between "HMAC verified" and "which shop this event is for."

### Finding Description
The identity binding that should hold is:
`hmac_valid(request) == true` should imply `request.shop == the shop Shopify actually generated this exact webhook for`.

In practice the binding that holds is only:
`hmac_valid(request) == true` implies `request.raw_body was signed by Context.api_secret_key at some point`,

because the signable string used for verification is body-only: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated, attacker-controllable HTTP headers: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` trusts this result and forwards `request.shop`, `request.topic`, and `request.webhook_id` straight into the handler without any additional check that they correspond to the shop/topic the signature was actually generated for: [4](#0-3) 

Because the `api_secret_key` (the app's client secret) is shared across every shop that installs the app, any installed merchant — an ordinary unprivileged user of the app, not a privileged account — can capture one genuine `(body, hmac)` pair delivered to their own endpoint, then resend it with the `shopify-shop-domain` header changed to a different shop's domain (and optionally a different `shopify-topic`/`shopify-webhook-id`, since none of these are covered by the signature). The gem will report the request as HMAC-valid and hand the handler a `WebhookMetadata` object whose `shop` field is fully attacker-controlled.

### Impact Explanation
This is a cross-tenant confused-deputy vulnerability: it lets one tenant of a multi-tenant app forge webhook events that appear to originate from — and are attributed to — a different, victim tenant. Any host application that uses `request.shop`/`WebhookMetadata#shop` to select which merchant's data to update (a documented and expected usage pattern of this gem's webhook dispatch API) can be tricked into applying webhook side effects to the wrong tenant's records, which is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app with more than one installed shop: the only prerequisite is being any ordinary installed merchant capable of receiving one legitimate webhook (freely available to every installer), and the header spoofing itself requires no cryptographic knowledge — just resending a captured request with modified headers, since none of `shop-domain`, `topic`, or `webhook-id` participate in the signature.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the request (e.g., verify that these header values match values embedded in/derivable from the signed body), so that a valid signature can only ever be attributed to the exact shop/topic/webhook it was issued for.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify sends a genuine webhook to the attacker's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body B>`
   - Body: `B`
3. Attacker computes nothing new — they simply replay the same body `B` and the same `hmac-sha256` value to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (per `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`) and it matches, since the header change did not alter the signed bytes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though this event never originated for that shop.
