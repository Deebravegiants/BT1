### Title
Shared Emporium custody lets any caller sweep externally-held positions opened by a different `emporiumMessage` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s only anti-replay guard, `EmporiumStorageVars.usedMessages`, is a flat boolean keyed solely by `circomData.emporiumMessage` and has no relationship to which assets or external-protocol positions were created by that message. Because "stateless" ops execute with `msg.sender == address(EmporiumUpgradeable)` for every caller, and `runAction` attributes any balance increase measured during the *current* call to the *current* caller regardless of who actually funded/opened that position, an unrelated, independently-valid `emporiumMessage` from a different account can redeem/withdraw a position left at Emporium by a previous victim's message and have the proceeds credited to the attacker's own output UTXO.

### Finding Description
The claimed equality — "assets Emporium holds after victim's tx == assets attributable only to victim's `emporiumMessage`" — is false. `verifyWallet` only records that a given `emporiumMessage` value has been consumed: [1](#0-0) 

This gives zero information about which on-chain assets or external protocol positions the message's ops created; there is no analogous per-message asset-ownership mapping.

`runAction` diffs Emporium's own token balances only across the span of the *current* atomic call: [2](#0-1) [3](#0-2) 

and credits any positive delta to whoever is currently executing, via `handleOut` sending to `msg.sender` (Hinkal core, which then mints the UTXO for the current transactor): [4](#0-3) 

For "Case 2: Stateless Interaction," the op is executed directly by the Emporium contract itself: [5](#0-4) 

so from any external protocol's perspective `msg.sender == address(EmporiumUpgradeable)` regardless of which user's `transact()` triggered the call. Any staking/lending/LP position opened this way is recorded by the external protocol against the single shared Emporium address, not against the depositor's message or commitment. `onlyAllowedRecipient` only checks that the caller is the registered Hinkal core contract, not that it corresponds to a particular prior message or asset owner: [6](#0-5) 

**Exploit flow:** Victim A calls `Hinkal.transact()` with a valid, self-consistent proof whose Emporium op deposits an ERC20 into an external protocol (`ExternalProtocol.deposit()`), executed as Case 2 so the resulting position/receipt token is held by Emporium, not converted into A's `erc20TokenAddresses`/output UTXO in the same call (e.g., A only declared the deposited token, not the receipt token, intending to withdraw later). Attacker B — an unrelated, unprivileged EOA — crafts their own valid proof and `CircomData` with a fresh, unrelated `emporiumMessage`, whose Case-2 op calls `ExternalProtocol.withdraw()`/`redeem()` against the same protocol (again executed with `msg.sender == Emporium`), converting A's parked position back into a raw token balance increase visible during B's own atomic call. `runAction`'s before/after balance diff captures this increase as belonging to B and mints it into B's own output UTXO. `verifyWallet` happily accepts B's message since it was never used before, `insertNullifiers`/`rootHashExists`/the circuit constraints only check internal arithmetic consistency of each prover's own inputs — none of them constrain that externally-created state must remain exclusive to the message/commitment that created it.

Note: Case 1 ("Stateful Interaction") is not vulnerable this way, because it routes through a per-signer `HinkalWallet` contract (`IHinkalWallet(stack.signerAddress).callHinkalWallet`) which is EIP-712-signature-gated to the wallet owner, isolating positions per wallet address. The vulnerability is specific to Case 2, where Emporium's own address is the shared custodian for every user.

### Impact Explanation
Critical: this allows direct theft of user funds that were routed into any stateful external protocol via Emporium's stateless call path. The victim's shielded UTXO/commitment record still implies the value (deposited/staked) is theirs, but the underlying collateral/position can be redeemed and stolen by any other unprivileged party, permanently depriving the victim. This matches "direct theft of shielded or in-flight user funds" / "executing calls or moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Requires only that: (1) some user routes an Emporium Case-2 op into a stateful external protocol without immediately withdrawing/capturing the resulting position value within the same atomic call (a legitimate, expected usage pattern for staking/lending/LP use cases via Emporium), and (2) the attacker can determine the external protocol/endpoint and calldata needed to redeem that position (often public/inferable, e.g., calling a known `withdraw()`/`redeem()` function). No privileged role, no victim key, no relayer collusion needed — attacker only needs their own valid proof/UTXOs and knowledge of the target protocol's withdraw interface. Fully repeatable against any external protocol integrated this way.

### Recommendation
Track per-position ownership at the Emporium layer instead of a flat message-replay boolean: e.g., record which `emporiumMessage`/committer opened a given external position (by endpoint + selector + relevant identifying params, or by requiring stateful protocol interactions to always route through a dedicated per-user `HinkalWallet` proxy rather than Emporium's own shared address), and require withdrawal ops to prove authorization tied to the original depositing message/signer before crediting proceeds to a different caller's output UTXO. At minimum, disallow Case-2 "stateless" ops from being used with any protocol that leaves a redeemable position at `msg.sender` (i.e., mandate Case-1 wallet-scoped execution for any stateful integration).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock `ExternalProtocol` with `deposit(uint256)` (mints/tracks shares keyed by `msg.sender`) and `withdraw()` (burns caller's shares, returns underlying to caller).
2. Victim A calls `Hinkal.transact()` with a valid proof whose `CircomData.externalActionData` targets Emporium with a Case-2 op = `ExternalProtocol.deposit(amount)`, `erc20TokenAddresses` = [depositToken] only. Assert `EmporiumStorageVars.usedMessages[A.emporiumMessage] == true` and assert `ExternalProtocol` records the position under `address(EmporiumUpgradeable)`.
3. Attacker B (different EOA, own funds/UTXOs, unrelated `emporiumMessage`) calls `Hinkal.transact()` with a valid proof whose Case-2 op = `ExternalProtocol.withdraw()`, `erc20TokenAddresses` = [underlyingToken].
4. Assert `EmporiumStorageVars.usedMessages[B.emporiumMessage] == true` and `usedMessages[A.emporiumMessage]` unaffected (proving no cross-message linkage exists).
5. Assert B's resulting UTXO/output commitment amount equals A's originally deposited value (or its yield), demonstrating value that should be attributable only to A's `emporiumMessage`/commitment was captured by B — i.e., `assets attributable to victim's emporiumMessage` (nonzero, held externally) != `0` while B walks away with it, breaking the claimed equality.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],

            uint256(balanceChange),

            circomData.stealthAddressStructure,
            circomData.timeStamp
