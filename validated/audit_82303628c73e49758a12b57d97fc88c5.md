### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the binding: `hmac == HMAC(secret, body)` should imply `shop == the shop that legitimately produced this exact body+hmac pair`, but no such binding exists in the gem.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `shop`, `topic`, `webhook_id`, `api_version` are all read straight from HTTP headers via `shopify_header` without any cryptographic tie to the HMAC [4](#0-3) .

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare` [5](#0-4) . Since `to_signable_string` for webhooks is the body alone, the same `(body, hmac)` pair validates successfully for `Registry.process` regardless of what `shop`, `topic` or `webhook_id` headers accompany it: `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching the handler with `request.shop` as the tenant identity [6](#0-5) .

Because the app's HMAC secret (`api_secret_key`) is shared across all shops/tenants installed on the app (it is the app's `client_secret`, not a per-shop secret — see `HmacValidator.validate` using `Context.api_secret_key` globally, and `Oauth.validate_auth_callback` reusing the same secret for every shop's OAuth exchange) [7](#0-6) , any `(body, hmac)` pair that is valid for one tenant is valid for every tenant. An unprivileged user who operates their own shop installed on the target app can legitimately trigger a webhook for their own shop (e.g. `orders/create` with attacker-controlled body content such as customer name/email fields), capture the resulting `raw_body` + `x-shopify-hmac-sha256` value, and then directly POST that same body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will accept it as HMAC-valid and hand the handler a `WebhookMetadata` claiming `shop: <victim shop>` with attacker-chosen body content [8](#0-7) .

### Impact Explanation
Any host application that scopes data writes/reads by `data.shop` from the webhook handler (the intended and documented use of `WebhookMetadata`) can be made to apply attacker-supplied webhook content to a victim tenant's records, i.e. cross-tenant access/data corruption — matching the Critical "cross-tenant access" category, since the tenant-binding field (`shop`) is never covered by the HMAC that is supposed to authenticate the whole webhook message.

### Likelihood Explanation
The webhook receiving endpoint is by design internet-reachable (Shopify posts to it over the public internet), so no privileged access, TLS interception, or leaked secret is required. The only prerequisite is that the attacker controls at least one shop installed on the same app (a normal, low-privilege merchant), which is a realistic scenario for public/multi-tenant Shopify apps.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable content used for HMAC verification (or otherwise cryptographically bind them, e.g. re-deriving/validating them against a value embedded in the signed body), so a valid `(body, hmac)` pair cannot be replayed under a different shop/topic/webhook_id. At minimum, document that `request.shop` is unauthenticated and must not be trusted as a tenant boundary by host applications without additional verification (e.g. confirming the shop has an active session/installation matching this exact webhook_id via Shopify's Admin API).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers `orders/create` with an order note containing attacker-chosen data.
2. Attacker's app receives the legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for `HMAC(secret, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker directly POSTs to the app's webhook endpoint: body `B`, `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: orders/create`.
4. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers/body [9](#0-8) ; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` (`B`) and `hmac` (`H`) still match [7](#0-6) .
5. `Registry.process` dispatches the registered handler with `shop: "victim.myshopify.com"` and the attacker-controlled body content, even though the victim shop never sent this webhook [6](#0-5) .
