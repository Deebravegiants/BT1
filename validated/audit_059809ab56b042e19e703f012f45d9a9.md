### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant shop-identity spoofing in `Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then trusts the `shop-domain` header — a field never included in the signed bytes — to identify which tenant/shop the event belongs to. This breaks the intended binding `shop authenticated by HMAC == shop used to process/attribute the event`, mirroring the reported bug class of "a field acted on but not covered by the authentication check."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cryptographic binding to the HMAC-covered body: [3](#0-2) 

`Registry.process` validates the HMAC and, upon success, immediately dispatches the handler using this unauthenticated `shop` value together with the (authenticated) body: [4](#0-3) 

The resulting `WebhookMetadata.shop` field — which host applications use to key sessions, database records, or app-level actions — is thus attacker-controllable even though the request "passes" HMAC verification: [5](#0-4) 

Because a single app's `api_secret_key` (used to sign webhooks) is shared across every shop that installs the app, any unprivileged merchant who installs the app on their own store can trigger a real, correctly-signed webhook (e.g., `orders/create`) for their own shop, capture the exact `raw_body` + `hmac` pair (e.g. by proxying their own webhook endpoint), and then replay that same body/HMAC pair to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` will still succeed (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop — an equality of `HMAC-authenticated origin == asserted tenant identity` that does not actually hold.

### Impact Explanation
This is a cross-tenant confusion vulnerability: a malicious but otherwise unprivileged app installer can make the host application believe an event (and its body/payload) originates from a shop they do not control. Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up a session/access token, write order data, or trigger side effects keyed by shop), this can lead to cross-tenant data corruption, unauthorized actions attributed to a different merchant's store, or processing of attacker-supplied body content under a victim's identity — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitability requires no leaked or privileged credentials: the attacker only needs to be a legitimate installer/merchant of the app (a normal, unprivileged action), able to trigger and observe one authentic webhook delivery to their own endpoint, and able to POST a crafted HTTP request (with a modified `shop-domain` header) to the app's shared webhook processing endpoint. No knowledge of `api_secret_key` is needed since the attacker reuses a genuinely signed body/HMAC pair rather than forging one.

### Recommendation
Bind the `shop-domain` (and other identity-relevant headers such as `topic`/`webhook-id`) into the HMAC-signed material, or otherwise cryptographically verify that the `shop` header matches an expected/whitelisted value tied to the session under which the webhook was registered, before using it to key any tenant-scoped action. At minimum, `Registry.process` should not treat HMAC success over the body alone as validating the `shop` header value used downstream.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) which Shopify signs with the app's shared `api_secret_key` and delivers with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac>`, and some `raw_body`.
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value (e.g., via a proxy in front of their own webhook receiver).
3. Attacker sends a new POST directly to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [2](#0-1) .
5. `Registry.process` calls `handler.handle` with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's raw_body parsed>, ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's identity.
