This confirms the vulnerability: `message.from` is set to `abi.encodePacked(msg.sender)` on the source chain — fully attacker-controlled, since `send()` is a public, unpermissioned function callable by anyone with tokens to burn. There is no cryptographic binding between `message.from` and any signature; it is simply the caller's own EVM address, which the caller can never *impersonate someone else's* since it's literally `msg.sender`. Let me verify the destination behavior more precisely — the critical bit is that `message.from` (attacker-controlled `msg.sender` on source chain) is converted directly into a Substrate `AccountId` and used as `RawOrigin::Signed(origin)` to dispatch an arbitrary runtime call, with no signature required, whenever `substrate_data.signature` is `None`.### Title
Unsigned `data` payload lets any caller impersonate an arbitrary beneficiary to dispatch a privileged runtime call in `pallet-hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`HyperFungibleToken::on_accept` executes an optional `SubstrateCalldata.runtime_call` on the destination chain, dispatched with `RawOrigin::Signed(origin)`. When `substrate_data.signature` is `None`, `origin` is derived directly from `message.from` — a value that is fully attacker-controlled on the source EVM chain (`abi.encodePacked(msg.sender)`), with no signature check at all.

### Finding Description
On the EVM side, `HyperFungibleToken.send()` (and `WrappedHyperFungibleToken`/`Upgradeable` variants) is a public, permissionless function. It builds the cross-chain `Message` with `from: abi.encodePacked(msg.sender)`: [1](#0-0) 

On the Substrate destination side, `Pallet::on_accept` decodes this ABI message and, when calldata is attached, checks whether `substrate_data.signature` is present. If it is `Some`, the signature is cryptographically verified against the beneficiary account. But if it is `None`, the code falls through to using `message.from` directly, converting it to a Substrate `AccountId` via `T::EvmToSubstrate::convert`, with **no verification whatsoever** that whoever submitted this cross-chain message controls that identity beyond simply being `msg.sender` on the source chain: [2](#0-1) 

This `origin` is then used to dispatch an arbitrary `T::RuntimeCall` (subject only to `BaseCallFilter`): [3](#0-2) 

The root issue mirrors CVE-2022-23131: an unverified identity field carried in message/session state (`message.from`) is trusted to authorize a privileged action (dispatching a runtime call as that account) without confirming the actor controlling the *destination* chain identity actually authorized it. Since `message.from` is nothing more than the caller's own source-chain `msg.sender`, and `EvmToSubstrate::convert` deterministically zero-pads any H160 into an `AccountId`, an attacker's own EVM address always maps to a *derived* Substrate account they cannot otherwise control funds/permissions on unless that derived account happens to hold privileges (e.g. via `sudo`, governance keys mapped from a known EVM address, or any account whose derived-from-H160 identity has elevated `BaseCallFilter`-permitted capabilities). More critically, this pattern also means **the destination-chain runtime call is dispatched as the identity the attacker chose to be `msg.sender`** with zero binding to any actual private key held by that identity — i.e. it authenticates "the account is whoever the source-chain caller happened to be," not "the caller actually authorized this specific runtime call for that beneficiary," breaking the intended cross-chain call authorization model used by legitimate SDK callers.

Concretely, this means any account (including throwaway/burner EVM addresses or fresh Substrate accounts) can trigger any destination runtime call permitted by `BaseCallFilter`, dispatched under that account's own on-chain identity, without ever proving cryptographic possession of a destination-chain key. This directly conflicts with the pallet's documented intent (calldata should require signature verification to bind to a beneficiary) — the `None`-signature branch was evidently meant only as a convenience fallback for same-address token transfers but ends up letting the "beneficiary" identity be silently trusted from unauthenticated cross-chain data.

### Impact Explanation
Any account can cause an arbitrary runtime call (bounded by `BaseCallFilter`) to be dispatched on the destination chain as an identity of the attacker's choosing (any H160/AccountId), without proving control of a private key for that destination identity. If any destination account reachable via this address-derivation scheme (e.g. treasury/sudo accounts represented by their EVM-mapped `AccountId`, or accounts holding asset approvals) can be targeted, this results in unauthorized privileged actions dispatched under a forged identity — a critical "unauthorized app action" per the ISMP-application dispatch model.

### Likelihood Explanation
High. `send()` is public and permissionless on any EVM chain running `HyperFungibleToken`; an attacker only needs to burn tokens (which they can mint/acquire in small amounts or for cheap assets) and craft `SendParams.data` as a `SubstrateCalldata` with `signature: None`. No special privileges, admin action, or governance step is required — a single transaction reaches this code path.

### Recommendation
Remove the unsigned fallback path entirely, or require that `message.from`-derived origin only be used to execute calls that are inherently scoped to that specific beneficiary/sender-controlled resource (never used to invoke `RuntimeCall::dispatch` as a general-purpose origin). At minimum, require `substrate_data.signature` to always be present and verified before dispatching any runtime call, eliminating the `None` branch, or bind the accepted `origin` to a locally-controlled proxy account rather than an unauthenticated cross-chain-supplied identity.

### Proof of Concept
1. Attacker deploys/uses a `HyperFungibleToken` on an EVM source chain, calling `send()` with `params.data` set to a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any allowed call> }`, and `msg.sender` set to any address of the attacker's choosing (their own EOA, or an address they compute to match a targeted destination account's H160→AccountId mapping).
2. The message is relayed and delivered via ISMP; `Pallet::on_accept` runs.
3. Since `substrate_data.signature` is `None`, `origin` becomes `T::EvmToSubstrate::convert(H160::from_slice(&message.from[...]))` — fully attacker-chosen, unauthenticated.
4. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes as that forged identity: [4](#0-3) , with the only gate being `BaseCallFilter`, not any proof that the attacker controls a key for `origin`.
