Based on the investigation, this gem's webhook processing path exhibits exactly the "field acted on but not covered by the HMAC" pattern described in the report's bug class.

### Title
Webhook `shop` domain is not covered by HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `x-shopify-shop-domain` header — which is never part of the signed material — as the authoritative tenant identifier passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the HMAC-covered bytes: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, i.e. over `to_signable_string` (the body), and then immediately forwards `request.shop` to the app's handler as `WebhookMetadata#shop`: [3](#0-2) [4](#0-3) 

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [5](#0-4) 

This breaks the intended binding `HMAC(body, api_secret_key) == authenticates(shop, topic, body)`. In reality it only proves `HMAC(body, api_secret_key) == authenticates(body)`. The `shop` (and `topic`/`webhook_id`) headers are unauthenticated metadata riding alongside an authenticated body.

The gem's own documentation and example code treat `data.shop` as a trusted per-tenant identifier to key application logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that downstream apps are expected to rely on this field as if it were authenticated: [6](#0-5) 

### Impact Explanation
A merchant who has installed the app on their own store (an unprivileged, non-credentialed party from the app's perspective — they hold no access token, `api_secret_key`, or admin credentials of the app) legitimately receives real, correctly-HMAC-signed webhooks from Shopify for their own shop (same body + valid signature, since the app's `api_secret_key` is shared across all merchants of the app). Because the signature covers only the body and not the shop-domain header, that merchant can replay the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `x-shopify-shop-domain` header. `Registry.process` will accept it (HMAC still validates against the unmodified body) and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. Any app that uses `data.shop` to look up/update per-tenant records (session storage, order sync, uninstall handling, billing state, etc.) can be tricked into cross-tenant data corruption or injection — attacker-controlled webhook content attributed to a victim tenant. This matches the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs (a) the ability to install the target app on a shop they control to receive genuine signed webhooks, and (b) knowledge/derivation of a body payload whose forged interpretation is useful against a chosen victim shop (e.g., a generic `app/uninstalled` or `orders/create` payload). No secrets, tokens, or privileged access are required — only normal, unauthenticated merchant-level interaction with the app (installing it), which fits the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the authenticated material instead of trusting an unsigned header:
- Extract the shop from the signed webhook body (Shopify always includes shop-level fields, and for topics without one, register/verify against the shop the webhook subscription was created for) rather than the `x-shopify-shop-domain` header, or
- Include the `shop`, `topic`, and `webhook-id` headers in the HMAC-signable string (requires coordinating with Shopify's signing scheme) so the values processed by `WebhookMetadata` can no longer be swapped independently of the signature, or
- At minimum, document in `WebhookMetadata`/`Registry.process` that `shop` is unauthenticated and require app developers to cross-check it against a shop known to have valid registrations for that specific webhook/topic before trusting it for tenant-keyed operations.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook (e.g. `orders/create`) — Shopify delivers a POST with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(B, api_secret_key)`, plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture `(B, H)` and resend the same request to the app's webhook endpoint, replacing only the header:
   `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(B, api_secret_key)` — identical to `H` since `B` is unchanged — and accepts the request.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, and any tenant-keyed logic in the host app now processes attacker-supplied content attributed to `victim.myshopify.com`.
