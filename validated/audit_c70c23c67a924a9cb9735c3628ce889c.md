### Title
Webhook Shop/Topic Identity Spoofing — HMAC Covers Only the Body, Not the Shop or Topic Headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies solely that the body was HMAC-signed with the app's secret. The `shop-domain`, `topic`, and `webhook-id` headers used downstream to identify the tenant are never part of the signed material, letting anyone who legitimately receives a valid signed webhook (i.e., any Shopify merchant) re-label it as coming from a different shop.

### Finding Description
`lib/shopify_api/webhooks/request.rb` builds the object consumed by `Utils::HmacValidator`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors are populated straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` (and `request.topic`) as the tenant identity for dispatch immediately after this body-only HMAC check passes, with no separate validation that the shop header is authentic: [4](#0-3) 

The broken identity binding, stated as an equality that the code should enforce but does not:

`HMAC_verified(raw_body) == raw_body` holds, but the code implicitly also relies on `HMAC_verified(shop_header) == shop_header_used_for_dispatch`, which is false — `shop_header` is never part of the signed bytes.

### Impact Explanation
Any unprivileged internet user who operates (or creates a free/dev) Shopify store can install any third-party app that consumes webhooks through this gem. Shopify will deliver a legitimately signed webhook (valid body + `X-Shopify-Hmac-Sha256`) to that app for the attacker's own shop. Because the shop/topic/webhook-id headers are outside the signed payload, the attacker can replay the exact same body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` still returns true (it only checks the body), and `Registry.process` hands the payload to the app's handler tagged with the attacker-chosen `shop`. Any application logic that uses `WebhookMetadata#shop` to scope per-tenant storage, trigger tenant-specific side effects, or make trust decisions is now cross-tenant confusable/poisonable by an attacker with no access token, no `client_secret`, and no special privileges — this is a cross-tenant access issue, matching the Critical impact bucket.

### Likelihood Explanation
Likelihood is high for any consumer of this gem's default webhook flow: becoming a Shopify merchant able to receive genuine signed webhooks is trivial (free dev stores), header manipulation on an HTTP request is trivial, and no knowledge of the target app's `api_secret_key` or any credential is required — only knowledge of the target app's public webhook URL, which is typically documented/discoverable.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., validate them against a signed session/registration record) rather than trusting header values that ride alongside a body-only signature. At minimum, document and/or enforce that host applications must independently authenticate/authorize the `shop` value before using it for any tenant-scoped action.

### Proof of Concept
1. Attacker registers a free Shopify development store and installs the target app, allowing Shopify to send a legitimate webhook (e.g., `orders/create`) to the app's public webhook endpoint. Attacker captures the raw HTTP request: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's secret), plus headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256: H` to the same endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Webhook-Id`/`X-Shopify-Topic` to whatever suits the target logic).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `B`, matching `H` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim-shop.myshopify.com"` — a shop the attacker does not control — even though the HMAC only ever proved authenticity of `B`, not of the shop association.
