### Title
Webhook `shop` (tenant) header is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable content solely from the raw HTTP body [1](#0-0) , while the shop identity used by the application (`request.shop`) is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in that signable string [2](#0-1) . `Registry.process` validates the HMAC over the body only, then unconditionally trusts `request.shop` and forwards it to the merchant's webhook handler as the tenant identity [3](#0-2) .

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhooks that string is exactly `@raw_body` [1](#0-0) [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled from HTTP headers that are outside the signed material [5](#0-4) .

The binding that should hold is: `shop reported in the request == shop covered by the HMAC`. Because only the body is signed, this equality does not hold — an attacker who can obtain any single validly-signed webhook body for the app (e.g. by installing the app on their own store and receiving a real webhook, since the HMAC secret is the app's shared `client_secret`, identical for every shop using this app) can replay that exact body to the app's webhook endpoint while substituting an arbitrary value for `x-shopify-shop-domain`. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will dispatch `WebhookMetadata.new(... shop: request.shop ...)` with the attacker-chosen shop to the handler [6](#0-5) .

The gem's own documentation instructs app authors to treat `data.shop` as the authoritative shop identity for dispatching background work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , so this is not merely a host-app misuse issue — the gem's documented contract is to hand back an unverified tenant label as if it were verified.

### Impact Explanation
This breaks the tenant boundary (cross-tenant access): an app that keys per-shop side effects (e.g., storing webhook payloads, updating cached shop state, triggering shop-scoped jobs) off `data.shop` as returned by this gem can be made to attribute or apply attacker-supplied (but validly-Shopify-signed) webhook payloads to a victim shop of the attacker's choosing, since the shop value carries no cryptographic binding to the signed payload.

### Likelihood Explanation
Any merchant/developer who can install the app on their own store (an unprivileged, non-credentialed actor from the gem's perspective) can obtain a validly HMAC-signed webhook body, because the same `client_secret` is used to sign webhooks for every shop on the app. Forging the header afterward requires only a direct HTTP request to the app's public webhook endpoint — no access token, secret, or privileged account is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is handed to `WebhookMetadata`/handlers — e.g., verify `shop` against a value carried inside the signed JSON body, or require the host application to independently confirm the shop has an active, previously-established session/installation before trusting `data.shop`. At minimum, document prominently that `shop` is unauthenticated header data and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; capture a genuine webhook delivery, which includes a body `B` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `client_secret` over `B`.
2. Replay an HTTP POST to the app's webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256` header, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only hashes `@raw_body` [1](#0-0) .
4. `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"` [3](#0-2) , causing the host application to process attacker-controlled data under the victim shop's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. - `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
