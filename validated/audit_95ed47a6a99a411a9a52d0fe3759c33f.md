## Title
Cross-tenant webhook spoofing — webhook `shop`, `topic`, `webhook_id`, `api_version` headers are not covered by the HMAC signature - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request **body**. The `shop`, `topic`, `webhook-id`, and `api-version` values, which are taken from HTTP headers, are never part of the signed data and are handed to the app's handler as trusted metadata. Because the webhook signing secret (`Context.api_secret_key`) is a single per-app secret shared across every shop that installs the app (not per-shop), any merchant who has installed the app can capture a validly-signed webhook body sent to their own shop and replay it against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop. The signature still validates because it never covered the shop header, and the app's webhook handler receives `WebhookMetadata` claiming the body belongs to the victim shop.

### Finding Description
The webhook HMAC check is performed by `Utils::HmacValidator.validate`, which validates `verifiable_query.to_signable_string` against `Context.api_secret_key`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled straight from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` raises only if the body's HMAC is invalid, then immediately trusts `request.shop`/`request.topic`/etc. to build the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop value cryptographically bound by the HMAC == shop value the handler uses to select the tenant`

In reality:
`HMAC covers raw_body only` ≠ `shop (and topic/webhook_id/api_version) sourced from unauthenticated headers`

Since `Context.api_secret_key` used for HMAC validation is a single value shared by the app across **all** installed shops (it is the app's secret, not a per-shop secret — confirmed by `HmacValidator.validate` always calling `Context.api_secret_key`, and by `Context.setup` storing one global `api_secret_key`), any tenant of a multi-tenant app can obtain a body+hmac pair that is valid for the shared secret (e.g., from a webhook legitimately delivered to their own shop) and reuse that exact body/hmac pair while substituting the `shop-domain` header value. `Registry.process` will accept it as authentic and hand the attacker-chosen `shop` value straight to the handler.

### Impact Explanation
This breaks the tenant isolation the library is documented to provide via `WebhookMetadata#shop`; host applications are expected to use `data.shop` from `WebhookMetadata` as the tenant key to route webhook side-effects (e.g., load the shop's session/access token, update shop-scoped records). A malicious merchant can trick a multi-tenant app into applying webhook data (and, in apps that trigger reactive writes/reads keyed by `webhook.shop`) under a victim shop's identity — a cross-tenant access impact, without needing the victim's access token, `api_secret_key`, or any privileged account beyond a normal app installation.

### Likelihood Explanation
Any merchant that installs the app already has a legitimate channel to obtain a body+hmac pair signed with the app's shared secret (their own webhooks are delivered to their configured endpoint, or an attacker acting as their own tenant can trigger webhook deliveries and capture the exact bytes and signature). Forging the `shop-domain` header on replay requires no cryptographic material and no interaction with Shopify's platform — only sending an HTTP request to the app's public webhook endpoint. This is a highly reachable "unprivileged internet user" analog to the reported fee-inclusivity bug: a field (`shop`) is *acted on* by the app but not *covered* by the same authenticity check (`HMAC`) that gates processing.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (or at minimum `shop` and `topic`) in the signable string alongside the raw body, or independently verify that these header values are consistent with values embedded in the (still-HMAC-covered) body/context before trusting them for tenant routing. Alternatively, document/require host applications to cross-check `WebhookMetadata#shop` against session data obtained through another authenticated channel before treating it as the tenant identifier.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and configures/observes a webhook (e.g. `orders/create`) delivered to the app's public endpoint; captures the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify computed with the app's shared `api_secret_key`.
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same app endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the (shared) secret — see: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` from the forged header and invokes the app's handler, which believes the (attacker-authored) body pertains to the victim shop.
