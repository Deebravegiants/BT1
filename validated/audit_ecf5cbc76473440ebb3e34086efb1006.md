Audit Report

## Title
Incorrect local credit-balance decrement on capability overspend allows workflow quota bypass - ([File: core/services/workflows/metering/metering.go])

## Summary
`Report.Settle` computes the difference between what was earmarked (`step.Deduction`) and the actual measured spend (`spentCredits`) and passes it directly to `balanceStore.Add` [1](#0-0) . `Add` explicitly rejects any negative amount via `ErrInvalidAmount` and performs no balance mutation in that case [2](#0-1) , so whenever actual spend exceeds the earmarked deduction, the local balance is never decremented for the overage — only a log line is emitted.

## Finding Description
The refund/overage logic in `Settle` is a single call: `r.balance.Add(step.Deduction.Sub(spentCredits))`. When `spentCredits <= step.Deduction` (spend under or equal to budget), the difference is non-negative and `Add` correctly credits back the unused earmark. When `spentCredits > step.Deduction` (spend exceeds the pre-execution reservation), the difference is negative, `Add` returns `ErrInvalidAmount` without touching `bs.balance`, and the code merely logs `"invariant: spend exceeded reserve"` [1](#0-0) . There is no corresponding call to `Minus`/`MinusAs` to actually apply the overage to the local balance.

Meanwhile, `AddSpent(spentCredits)` unconditionally records the true spend for billing/reporting purposes [3](#0-2) , and `bs.spent` is what is later reported via `SubmitWorkflowReceipt`'s `CreditsConsumed` field [4](#0-3) . But `bs.balance` — the value read by `getMaxSpendForInvocation` to gate how much can still be spent within the current execution — was only ever reduced by the original (smaller) `Deduction` amount at `Deduct` time, and is never further reduced for the overage [5](#0-4) . This leaves the tracked local balance higher than the true remaining reserve, letting subsequent `Deduct` calls within the same execution authorize more capability spend than the reservation should permit.

## Impact Explanation
This is an in-execution spend-quota accounting bug: the local balance tracker used to gate remaining capability calls in a workflow execution is not decremented correctly on overspend, violating the invariant the code itself documents ("capability should not let spend exceed reserve"). It allows a workflow execution to authorize more capability invocations than its credit reservation should allow within that single execution. It does not, however, change what is ultimately billed — `AddSpent` still records the true spend, which flows into `CreditsConsumed` on the receipt — so the final accounting/billing to the customer is not corrupted; the bug's effect is confined to the in-memory gating check (`getMaxSpendForInvocation`) during a single execution.

## Likelihood Explanation
Triggering this requires only that a capability's actual reported spend, after conversion, exceeds the amount earmarked via `Deduct` before execution — a realistic and plausible scenario whenever spend is estimated ahead of time (e.g., `ByDerivedAvailability`) and real usage (gas price, compute cost) varies. No elevated privilege is needed; any workflow execution that experiences this condition naturally triggers the under-decrement, making it a genuine, reproducible bug in normal (non-adversarial) operation of the metering code, confirmed directly in the checked-in source.

## Recommendation
`Settle` should branch explicitly on the sign of `step.Deduction.Sub(spentCredits)`: call `Add` for the refund case (spend under budget) and call `Minus`/`MinusAs` for the overage case (spend over budget) so `bs.balance` is correctly decremented by the true overspend rather than silently left unchanged when `Add` rejects the negative amount.

## Proof of Concept
1. A workflow step calls `Deduct(ref, ByDerivedAvailability(...))`, earmarking `Deduction = 10` credits, reducing `bs.balance` by 10 via `Minus`.
2. The capability's reported spend, once converted, yields `spentCredits = 15` (exceeds the earmark).
3. `Settle` computes `10 - 15 = -5` and calls `r.balance.Add(-5)`, which returns `ErrInvalidAmount` per `core/services/workflows/metering/balance_store.go` lines 176-178 and performs no mutation; only an info log is emitted.
4. `r.balance.AddSpent(15)` records the full 15 into `bs.spent` (used for billing), but `bs.balance` was only ever reduced by 10 at `Deduct` time — leaving 5 credits of extra, unaccounted headroom available for further `Deduct` calls (via `getMaxSpendForInvocation`) within the same workflow execution.

A Go unit test on `balanceStore`/`Report.Settle` asserting `bs.balance` after a `Deduct(10)` followed by a `Settle` reporting `spentCredits=15` should show the balance is unchanged from post-`Deduct` (i.e., still reflects only a 10-credit reduction) instead of reflecting the true 15-credit spend, confirming the accounting drift.

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
