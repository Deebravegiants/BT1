### Title
Webhook HMAC only signs the raw body, so the `shop-domain` and `topic` headers used to route/attribute the webhook are unauthenticated, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)` against the raw request body, but then dispatches the handler using `request.topic` and `request.shop`, both of which are taken verbatim from HTTP headers that are never part of the signed material. This breaks the intended identity binding: `shop == shop that produced this HMAC-signed payload`. Because the app's `client_secret` (`Context.api_secret_key`) is shared across all shops that install the app, an attacker who legitimately installs the app on their own shop can capture one of their own valid, signed webhook deliveries and replay it to the same endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header changed to point at a victim shop. The HMAC will still validate because it never covered those headers.

### Finding Description
- `Request#hmac` and `#to_signable_string` are only derived from `@raw_body`: [1](#0-0) 
- `Request#topic` and `Request#shop` are read straight from unauthenticated headers: [2](#0-1) 
- `HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e. the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 
- `Registry.process` validates only the body HMAC, then dispatches strictly on the unauthenticated `topic`/`shop` header values and forwards `request.shop` into the handler's `WebhookMetadata`: [4](#0-3) 

The intended equality the gem should enforce is: *"the shop/topic the handler acts on" == "the shop/topic that authored the HMAC-signed bytes."* Instead, the gem enforces only *"the body bytes were HMAC-signed by some shop using this app's secret,"* and lets `shop`/`topic` come from an unrelated, unauthenticated channel (HTTP headers). This is exactly the "bytes verified vs. bytes parsed" / "field acted on but not covered by the HMAC" class of bug called out for `retain()`'s missing `checkpointNominee` binding: the code checks one thing (raw body signature) but acts on a different, un-bound value (headers).

### Impact Explanation
Because the `client_secret` used to sign webhooks is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any merchant who has legitimately installed the app can generate their own validly-signed webhook (e.g. by triggering `orders/create`, `app/uninstalled`, GDPR data-request webhooks, etc. on their own store) and then replay that exact signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Registry.process` will accept it (HMAC over the body still matches) and hand the attacker-controlled body to the handler tagged as having come from the victim shop, per `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`. Depending on how the host application's handler trusts `shop`, this enables cross-tenant data injection/confusion (e.g. forging an `app/uninstalled` event for a victim shop to trigger deprovisioning, or injecting forged order/customer data attributed to a shop the attacker does not control) — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate to high: the attacker only needs to be a normal, legitimate (unprivileged) installer of the app on their own store — no leaked secrets, no privileged account, and no interaction with the app's `api_secret_key` are required, since they can generate a validly-signed webhook for their own tenant and simply relabel the routing headers before replay.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`) into the signed material that `HmacValidator` verifies, or otherwise cryptographically/contextually confirm that the `shop-domain` header matches the shop the webhook was actually delivered for (e.g., by validating it against a known/registered shop list per delivery, or including it in the signable string) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` to the app's webhook endpoint.
2. Capture `B` and its valid HMAC from this delivery (attacker fully controls their own shop's traffic to their own configured endpoint, or can simply log it in their own receiving code).
3. Replay a POST to the same webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks the body bytes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `shop: "victim.myshopify.com"` and the attacker's chosen body, even though that body was never actually sent by/for the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
