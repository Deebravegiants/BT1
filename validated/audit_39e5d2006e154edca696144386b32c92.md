### Title
Webhook shop-domain header is not covered by the HMAC, allowing shop spoofing / cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw body only, but the `shop` field that the gem hands to the app's handler (and that the docs instruct developers to use as the tenant key) is taken from an HTTP header that is never included in the signed bytes. This is the same class of bug as the reported VaultV2 issue: a value that is *acted on* (used to identify the tenant/shop) is not *covered by the authenticity check* (the HMAC), so the two can be made to diverge.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is *not* part of that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body/secret pair, then immediately trusts `request.shop` when constructing the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the `hmac` header — again, this only binds the *body*, never the shop header: [4](#0-3) 

Crucially, `api_secret_key` is a single, app-wide secret shared across *every* installed shop (it is the app's client secret, not a per-shop secret) — see its use in OAuth and elsewhere as a global `Context` value, e.g. in `Oauth.validate_auth_callback`: [5](#0-4) 

Because the HMAC secret is identical for all shops of the app, any merchant who has installed the app can capture a legitimate webhook delivered to their own store (a valid `raw_body` + valid `hmac`), and then simply replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `shopify-shop-domain` header value naming a victim shop that also uses the same app. `HmacValidator.validate` still returns `true` (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the attacker-chosen victim domain.

The binding that is broken is:
```
verified(hmac) over body  !=  identity(shop) acted upon by handler
```
i.e. the equality `shop_that_signed_the_payload == shop_the_handler_believes_sent_it` is never enforced.

### Impact Explanation
The documented usage pattern explicitly routes on `data.shop` as the tenant key (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and the library's own webhook doc states `shop` is "The shop domain of the webhook." Any host application that follows this documented pattern (looking up per-shop sessions/state keyed by `data.shop`, e.g., to schedule work, delete data on `app/uninstalled`, update inventory on `orders/create`, etc.) can be made to attribute one shop's payload to a different, victim shop. This is a cross-tenant data/action injection: an unprivileged (but genuinely installed) merchant can inject forged, shop-mislabeled webhook events for another tenant of the same app, corrupting or manipulating that victim's app state without any credential belonging to the victim.

This matches the Critical "cross-tenant access" impact category: the vulnerability lets one tenant affect data/state attributed to another tenant purely by controlling an unauthenticated header, exploitable by any user who can install the app (no `api_secret_key`, access token, or victim credentials required).

### Likelihood Explanation
Exploitation only requires:
1. Installing the target app on an attacker-controlled shop (a normal, unprivileged action any Shopify merchant can take for any public app).
2. Capturing one legitimate webhook delivery (raw body + `x-shopify-hmac-sha256`) sent to the attacker's own shop — trivial, since the attacker owns that endpoint's traffic.
3. Replaying the identical body/HMAC to the app's webhook endpoint with a forged `shop-domain` header pointing at a known victim shop domain (shop domains are public/guessable, e.g., from the storefront URL).

No brute forcing of the HMAC, no access to `api_secret_key`, and no interaction with the victim is required. The only prerequisite is that the target app is multi-tenant (serves more than one shop), which is the normal deployment model for this gem.

### Recommendation
- Do not treat the `shop` header as trusted tenant identity on its own. Either:
  - Include the shop-domain (and topic/webhook-id) header values in the signable string that is HMAC-verified, so that any header tampering invalidates the signature, or
  - Independently verify that the shop named in the header actually has webhooks registered/an active session for this topic/handler before dispatching, and reject/flag mismatches.
- Document prominently that `data.shop` in `WebhookMetadata` is unauthenticated header data with respect to the HMAC check, and that host apps must correlate it against known installed-shop records (not just presence in the events they registered) before performing any tenant-scoped action.
- Consider deriving the shop identity from data embedded in the signed body when the topic payload contains it, rather than solely from headers.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and has installed the target app.
# Shopify legitimately delivers a webhook to the attacker's own endpoint:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the exact same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop that also installed the app.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",  # attacker-controlled value
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate(request) => true, because only raw_body is checked.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com",  # forged
#                                              body: {...}, ...))
```
`lib/shopify_api/webhooks/request.rb` lines 20-23 and 35-38, together with `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 and `lib/shopify_api/webhooks/registry.rb` lines 188-200, confirm the header is read and forwarded without ever being part of the verified bytes.
