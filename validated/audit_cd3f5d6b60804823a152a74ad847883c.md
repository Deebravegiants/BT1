I found the key finding: `ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all taken from unauthenticated HTTP headers — are passed downstream as trusted identity/routing data without being covered by the signature.Confirmed. This is the vulnerability.

### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted by `ShopifyAPI::Webhooks::Registry.process` without being covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only authenticates the bytes of the body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers [2](#0-1) . Those header-derived values are nonetheless taken at face value and handed to the app's webhook handler as trusted `WebhookMetadata` (in particular `shop`, which the gem's own documentation instructs apps to use as the tenant identifier, e.g. `data.shop`) [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes == bytes that determine the shop/topic used for authorization and side effects`

Here it is broken: `hmac` is computed from `shopify-hmac-sha256` header, decoded and compared against `HMAC(body)` [5](#0-4) , but `shop`, `topic`, `webhook_id`, and `api_version` are read straight from separate, unauthenticated headers [6](#0-5) . `Registry.process` validates only the body-based HMAC and then unconditionally trusts `request.shop`/`request.topic` to build `WebhookMetadata`, which is passed to the app's handler as the tenant/routing context [2](#0-1) .

Because Shopify's genuine HMAC signature never covers these headers (confirmed by the test fixtures, which build the HMAC only from the JSON body and set `shop-domain`/`topic` headers independently) [7](#0-6) , any `(body, hmac)` pair that was legitimately produced by Shopify for one shop/topic remains cryptographically valid when replayed to the same endpoint with a different `shop-domain` or `topic` header. `HmacValidator.validate` will still return `true` because it only recomputes the digest over the untouched body [8](#0-7) . The gem gives apps no way to detect this: `Request` exposes `shop` as a plain, unauthenticated accessor with no cross-check against the signed content, and the documented handler contract explicitly relies on `data.shop` as the authoritative tenant identifier [9](#0-8) .

### Impact Explanation
An attacker who can capture (or generate, e.g. via a webhook they control on their own installed shop) one genuine `(raw_body, hmac)` pair from Shopify can replay it to the victim app's public webhook endpoint while substituting the `shop-domain` header for a different, victim merchant's domain. Since the gem's own `process` method treats the header-derived `shop` as authoritative and never checks it against anything covered by the HMAC, the app's handler will process attacker-controlled webhook content under the identity of a shop the attacker does not control — a cross-tenant data/action injection that can lead to unauthorized writes, notifications, job triggering, or data disclosure scoped to the spoofed shop. This satisfies the "cross-tenant access" High/Critical impact category since the tenant-binding field (`shop`) is not bound to the signature that is supposed to authenticate the whole webhook.

### Likelihood Explanation
The precondition — obtaining at least one legitimately signed `(body, hmac)` pair — is trivially satisfiable by any developer/attacker who installs the target app on their own store (a normal, unprivileged action) and receives one real webhook, no `api_secret_key` or stolen credentials required. From there, forging the header value is a simple unauthenticated HTTP replay against the app's public webhook callback URL. Because `Request`/`Registry.process` provide no per-shop content binding, the exploit path is entirely within this gem's control flow rather than depending on the host app deviating from the documented API — the documented API itself (`data.shop`) is the thing being spoofed.

### Recommendation
Bind the shop/topic identity to the authenticated content: include the `shop-domain`, `topic`, and `webhook-id` header values in the `to_signable_string` computation (mirroring the `AuthQuery#to_signable_string` pattern which folds `shop`, `state`, `host`, etc. into the signed string [10](#0-9) ), or otherwise cryptographically bind the shop identity before exposing it via `WebhookMetadata`. At minimum, document that `data.shop` is unauthenticated and must be cross-verified by the host app against a known registered shop before being trusted for tenant-scoped actions.

### Proof of Concept
```ruby
# Step 1: attacker installs target app on their own shop "attacker.myshopify.com"
# and receives one real Shopify webhook, e.g. orders/create, capturing:
raw_body = '{"id":1,"note":"hello"}'
real_hmac_header = "<base64 hmac shopify sent, valid because it is HMAC(raw_body, api_secret_key)>"

# Step 2: attacker replays the same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_header,   # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (HMAC(raw_body) matches)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-controlled content under victim-shop's identity.
```
