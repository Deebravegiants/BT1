### Title
Unchecked U128 → u64 truncation in `swap_base_out` lets an attacker drain a pool for near-zero input - ([File: program/src/processor.rs])

### Summary
`process_swap_base_out` / `process_swap_base_out_v2` compute the required input amount (`swap_in_after_add_fee`) as a `U128` value and then narrow it to `u64` with `.as_u64()`, which — like the kernel's `io_estimate_bvec_size()` — silently truncates instead of checking that the value fits. An attacker who chooses `amount_out` close to the pool's total reserve can drive the internal `U128` computation far above `u64::MAX`, causing the truncated `deduct_in`/`swap_in_after_add_fee` to wrap around to an attacker-controllable tiny value, while the actual `amount_out` transferred out of the vault remains untouched and large.

### Finding Description
`swap_token_amount_base_out` computes the swap input amount before fees: [1](#0-0) 

For `SwapDirection::Coin2PC`, `amount_in = coin * amount_out / (pc - amount_out)`. Both `coin`/`pc` and `amount_out` are attacker-influenced through `swap.amount_out` (a user-controlled `u64` field), and the division uses `checked_ceil_div` on `U128` values, so there is no overflow protection against the *result* growing arbitrarily large — only the internal `U128` arithmetic is checked, not the final size.

In `process_swap_base_out_v2`, this result is then multiplied by `swap_fee_denominator` and divided again, still in `U128`, and finally truncated to `u64` via `.as_u64()`: [2](#0-1) 

The `uint` crate's `construct_uint!`-generated `as_u64()` (used to build `U128`/`U256` in this codebase) simply returns the low 64 bits of the integer — it does not panic or error if the value does not fit, unlike `Calculator::to_u64` which uses `try_into` and correctly rejects overflow: [3](#0-2) [4](#0-3) 

After truncation, the code only validates the *truncated* value against the user's balance and `max_amount_in`, and separately validates only that `amount_out < total_..._without_take_pnl`: [5](#0-4) [6](#0-5) 

Finally, the transfer into the pool uses the truncated `swap_in_after_add_fee`, while the transfer out of the pool uses the untouched, attacker-chosen `swap.amount_out`: [7](#0-6) 

The identical pattern (same truncating `.as_u64()` on the computed input amount) exists in the non-v2 handler: [8](#0-7) 

### Impact Explanation
By choosing `amount_out` such that the pool reserve minus `amount_out` is very small (e.g., `pc - amount_out = 1`), the pre-fee input `coin * amount_out / (pc - amount_out)` can be pushed to a value on the order of `coin * amount_out`, which for realistic vault balances easily exceeds `u64::MAX` (~1.8e19). After further multiplication by `swap_fee_denominator`, the value is truncated by `.as_u64()` to an attacker-chosen low-64-bit remainder — the attacker can iterate `amount_out` values to find one where the truncated remainder is arbitrarily small (even zero, aside from the `== 0` check which only rejects the exact zero case). The attacker then supplies a matching tiny `max_amount_in` and drains nearly the entire opposite-side vault (`swap.amount_out`, capped only by `>= total_..._without_take_pnl`) for a negligible real deposit. This is direct, permanent theft of LP/pool funds and insolvent pool accounting, reachable from a single `SwapBaseOut`/`process_swap_base_out_v2` instruction with attacker-chosen data — no privileged signer or off-chain access required.

### Likelihood Explanation
High. Both `SwapInstructionBaseOut.amount_out` and `max_amount_in` are fully attacker-controlled instruction data; the swap instructions are reachable by any unprivileged swapper against any live pool with normal-sized reserves. No special account permissions, validator behavior, or non-default build is needed — only careful selection of `amount_out` near the pool reserve to trigger the truncation-friendly modulus.

### Recommendation
Replace the truncating `.as_u64()` calls in `swap_in_after_add_fee`/`deduct_in` computations (and any other size-carrying `U128`→`u64` narrowing in the swap-out paths) with a checked conversion (e.g., `Calculator::to_u64` which uses `try_into` and returns `AmmError::ConversionFailure` on overflow) so that any value not representable in `u64` aborts the instruction instead of silently wrapping.

### Proof of Concept
1. Attacker identifies a pool with `total_coin_without_take_pnl = C` and `total_pc_without_take_pnl = P` (Coin2PC direction).
2. Attacker crafts `SwapBaseOut`/`SwapBaseOutV2` with `amount_out = P - 1` (satisfies `amount_out < total_pc_without_take_pnl`).
3. `swap_in_before_add_fee ≈ C * (P-1) / 1 = C*(P-1)`, a `U128` value far exceeding `u64::MAX` for realistic `C`, `P`.
4. `swap_in_after_add_fee = (swap_in_before_add_fee * fee_denominator).checked_ceil_div(fee_denominator - fee_numerator).as_u64()` truncates to `(true_value) mod 2^64`; attacker can brute-force nearby `amount_out` values off-chain to land on a small truncated remainder (e.g., a few lamports).
5. Attacker sets `max_amount_in` to match this tiny truncated value; the balance/slippage checks pass trivially.
6. Program transfers the tiny `swap_in_after_add_fee` from attacker to the coin vault, then transfers the full `amount_out = P - 1` (nearly the entire pc vault) to the attacker, draining the pool for negligible cost. [9](#0-8)

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
