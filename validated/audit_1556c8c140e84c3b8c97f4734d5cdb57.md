### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant identity spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken from unauthenticated HTTP headers and hands them to the app's handler as `WebhookMetadata`. Since the HMAC signature never covers these header values, an attacker who possesses a validly-signed body (e.g., from their own installed instance of the app) can replay it with an arbitrary `x-shopify-shop-domain` header, and the gem will report it to the handler as authentic data for a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled directly from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC (which — per `to_signable_string` — covers exclusively the body bytes) and then immediately constructs `WebhookMetadata` from the request's header-derived, unauthenticated `shop`, `topic`, `webhook_id`, and `api_version`: [3](#0-2) 

`HmacValidator.validate` confirms the signature is computed purely over `verifiable_query.to_signable_string` (the body), with no shop/topic binding: [4](#0-3) 

This breaks the identity binding: `shop authenticated == shop stored/used by the handler` does not hold, because the equality actually enforced is `HMAC(raw_body) == valid`, independent of which shop header accompanies that body. An attacker who legitimately installs the app on their own shop (or otherwise obtains one validly-signed webhook body/HMAC pair for topic X) can capture that `(raw_body, hmac)` pair and replay it against the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. Because Shopify's HMAC secret (`api_secret_key`) is shared across all shops installed on the app (it is per-app, not per-shop), the same HMAC value validates successfully regardless of which `shop` header is attached, since that header plays no part in the signature computation.

The `WebhookMetadata` struct passed to the app's `WebhookHandler#handle` therefore carries an attacker-controlled `shop` field that the host application will typically treat as authoritative for looking up that shop's session/access token or for writing shop-scoped data: [5](#0-4) 

This is the same class of flaw as the reported "field acted on but not covered by the HMAC" — analogous to the metaTx flow trusting fields (`relayerFee`, contract target) that were never validated against the signed/authoritative source before being acted upon.

### Impact Explanation
This enables cross-tenant confusion: a malicious merchant/attacker can cause an app to process webhook data (order data, GDPR/mandatory topics, product data, etc.) under a victim shop's identity, since the `shop` value used by the downstream handler to select the tenant/session is not authenticated. Depending on how the host app uses `WebhookMetadata.shop` (e.g., to look up the merchant's stored access token and act on their behalf, or to write/merge data into the victim's tenant record), this can lead to cross-tenant data corruption or actions being attributed to/performed against the wrong shop. This falls under the Critical "cross-tenant access" category since the trust boundary between shops sharing the same app installation is broken by the gem's own verification logic.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker who can install the app on their own shop (a normal, unprivileged action for public/embedded apps) and capture one raw webhook body plus its valid HMAC for a topic of interest. Because the signature never binds to the `shop-domain` header, the replay requires no cryptographic secret knowledge — only crafting the raw HTTP request with a different `shop-domain` header value and the pre-captured valid `(body, hmac)` pair.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) as part of the signed/verifiable content, or cross-check the header-provided `shop` against an independent, trusted source (e.g., require the caller to additionally prove shop ownership, or validate that the shop domain is one for which the app holds an active session before dispatching to `handle`). At minimum, document that host applications must not trust `WebhookMetadata.shop` without separately verifying it against a known/installed shop list, and consider incorporating the shop domain into the signable string used by `HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install) and configures a webhook handler, causing Shopify to send a real webhook with a validly-signed body B and `x-shopify-hmac-sha256` header H (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker captures `(B, H)` and crafts a POST to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: <same or different registered topic>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body: `B`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) using the shared `api_secret_key` and finds it matches `H` — validation succeeds: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process (or act upon) data under the victim's shop identity despite the payload never having been sent by Shopify for that shop.
