### Title
Missing "already-delivered" guard in `EvmHost.dispatchIncoming` allows a reentrant `onAccept`/`onGetResponse` callback to trigger unbacked double-minting - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` and `EvmHost.dispatchIncoming(GetResponse, address)` unconditionally overwrite `_requestReceipts[commitment]` / `_responseReceipts[commitment]` and then perform the external call to the destination module's `onAccept`/`onGetResponse`, without first checking whether a receipt already exists for that commitment. This mirrors the exact bug class in the ImageMagick MSL advisory: a resource is destroyed/finalized twice because a guard that should reject a second invocation on an already-processed object is missing. The Rust ISMP core (`modules/ismp/core/src/handlers/request.rs`, `modules/ismp/core/src/handlers/response.rs`) explicitly re-checks the receipt immediately before invoking the module callback for exactly this reason — the EVM host does not.

### Finding Description
`dispatchIncoming` for a `PostRequest` is:
```solidity
function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
    ...
    bytes32 commitment = request.hash();
    _requestReceipts[commitment] = relayer;               // <-- no prior "already set?" check
    (bool success,) = address(destination).call(abi.encodeWithSelector(IApp.onAccept.selector, ...));
    if (!success) {
        delete _requestReceipts[commitment];
        return;
    }
    emit PostRequestHandled(...);
}
``` [1](#0-0) 

The GET-response path has the identical pattern:
```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({...});   // <-- no prior "already set?" check
    (bool success,) = _bytesToAddress(response.request.from).call(...onGetResponse...);
    ...
}
``` [2](#0-1) 

Contrast this with the equivalent Substrate/Rust `ismp-core` request handler, which contains an explicit second check placed immediately before the module callback for exactly this scenario — a callback invoked earlier in the same batch (directly, or by re-entering the handler) could have already stored a receipt for the *same* request, and the up-front proof-verification pass cannot catch that because it runs before any callback executes:
```rust
// Re-check the receipt right before dispatch. ... a prior request's on_accept in
// this same batch could have stored a receipt for this request
// (directly or by re-entering the handler), and we must not invoke
// on_accept a second time.
if host.request_receipt(&wrapped_req).is_some() {
    Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
}
let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
``` [3](#0-2) 

The same defensive re-check exists in the response handler:
```rust
// Re-check the receipt right before dispatch. ... a prior response's on_response in
// this same batch could have stored a receipt for this response
// (directly or by re-entering the handler), and we must not invoke
// on_response a second time.
if host.response_receipt(&response).is_some() {
    Err(Error::DuplicateResponse { meta: (&response).into() })?
}
``` [4](#0-3) 

`EvmHost.dispatchIncoming` has no analogous check. Since `IApp.onAccept` is an arbitrary external call to whatever contract the request's `to` field resolves to, a malicious or compromised destination module can, from inside its own `onAccept`, re-enter the handler with a fresh call that resolves to the same commitment's `PostRequest` (e.g., by re-triggering `HandlerV2` processing of a proof for the same already-verified leaf, since the ISMP state/dispatch-root membership proof for a request remains valid for as long as the corresponding state commitment is retained) and cause `dispatchIncoming` to run a second time for that commitment before the first call unwinds. Because the write to `_requestReceipts[commitment]` is not gated on the previous value, the second `onAccept` invocation proceeds exactly as the first did.

### Impact Explanation
For any `IApp` whose `onAccept` performs a state-changing, non-idempotent action keyed only on message content rather than on an internal one-time-use flag (e.g. `HyperFungibleToken.onAccept` / `BridgeToken.onAccept`, which unconditionally call `_mint(beneficiary, message.amount)` on every invocation), a second `dispatchIncoming` call for the same commitment mints the bridged amount a second time with no corresponding burn/lock on the source chain — an unbacked mint of bridged tokens. This is the CWE-416-adjacent "process the same resource twice" bug class from the advisory, here manifesting as a double state-transition rather than a memory free, but with the same root cause: absence of a guard against re-invoking a destructive/finalizing operation on an object (the commitment/receipt) that has already been finalized once. [5](#0-4) 

### Likelihood Explanation
Exploitation requires the attacker to control (or compromise) a destination `IApp` contract that Hyperbridge is configured to deliver to, and to have that contract's `onAccept` re-enter the message-processing pipeline before the outer call returns. `restrict(_hostParams.handler)` limits direct calls to `HandlerV2`, so the attacker cannot call `dispatchIncoming` directly; the practical path is convincing `HandlerV2` to process a second membership-proof batch for the same already-known request/response leaf from within the reentrant callback. I was not able to fully inspect `HandlerV2.sol`'s batch-processing logic (its own possible in-batch duplicate filtering) within the available tool budget, so I cannot confirm whether `HandlerV2` independently deduplicates commitments across separate top-level `handlePostRequests`/`handleGetResponses` invocations that occur via reentrancy. This uncertainty affects likelihood but not the underlying root-cause gap in `EvmHost.dispatchIncoming`, which — unlike its Rust counterpart — has no independent, host-level protection against a second invocation.

### Recommendation
Add an explicit check in both `dispatchIncoming` overloads (mirroring the Rust `ismp-core` pattern) that reverts if `_requestReceipts[commitment] != address(0)` (respectively `_responseReceipts[commitment].relayer != address(0)`) before writing the receipt and making the external call, rather than relying solely on `HandlerV2`'s upstream proof-batch deduplication.

### Proof of Concept
1. Deploy a malicious `IApp` as the `to` address of a `PostRequest` routed by `EvmHost`.
2. Have a relayer submit a valid membership-proof batch containing this request; `HandlerV2` invokes `EvmHost.dispatchIncoming(request, relayer)`, which sets `_requestReceipts[commitment] = relayer` and calls the malicious app's `onAccept`.
3. Inside `onAccept`, before returning, re-enter `HandlerV2` with the same (still valid) membership proof for the identical leaf/commitment, causing `dispatchIncoming` to run again for the same `commitment`.
4. Because `_requestReceipts[commitment]` is overwritten unconditionally rather than checked, the second `onAccept` executes successfully; for a token-mint `IApp` such as `HyperFungibleToken`/`BridgeToken`, this results in `_mint` being called twice for the single source-chain transfer, i.e., an unbacked double mint.     function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
