The `Webhooks::Request` class computes its HMAC signature using only the raw request body via `to_signable_string`, defined at [1](#0-0) , while the `shop` (tenant identity) is read from a separate unsigned header, defined at [2](#0-1) . `Utils::HmacValidator.validate` only checks that the HMAC matches `to_signable_string`, i.e., the body, at [3](#0-2) . `Registry.process` then trusts `request.shop` for tenant attribution after this HMAC check passes, at [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook attribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and the `shopify-shop-domain` header used as the tenant identity is read separately, without being included in the HMAC-signed content [2](#0-1) . `Utils::HmacValidator.validate` only verifies the body signature [5](#0-4) , so the equality the app relies on — "shop the HMAC authenticates" == "shop the handler receives" — does not hold, because the shop header is completely outside the authenticated bytes.

### Finding Description
`Registry.process` validates the webhook by calling `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` (the raw body only) and compares it to the `hmac-sha256` header [4](#0-3) . Once that check passes, `request.shop`, sourced directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) , is passed straight into `WebhookMetadata` and handed to the app's webhook handler as the shop the event belongs to.

Because the `shop-domain` header is never part of the signed content, any request whose body+HMAC pair is valid for the shared `api_secret_key` will pass validation regardless of which shop-domain header accompanies it. Since the `api_secret_key` is shared across all shops that install the same app (it is not shop-specific), any installed merchant — an unprivileged actor with respect to other tenants of the same app — legitimately receives real webhooks for their own shop, each with a valid HMAC computed over a body they can fully observe. That merchant can resend/replay that exact body and HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still accept it because it only checks the body bytes, and `Registry.process` will attribute the (attacker-controlled-content) event to the spoofed shop.

### Impact Explanation
This breaks the identity binding between the value the HMAC authenticates (the body) and the value the app trusts for tenant routing (the shop-domain header), enabling cross-tenant event injection/attribution: an app's webhook handler that keys any per-shop record lookup, mutation, or side effect using `WebhookMetadata#shop` can be made to act on behalf of a different merchant's shop than the one whose secret actually produced the signature. Depending on the handler (e.g., updating shop-level settings, revoking access, processing `shop/redact`/`customers/redact` compliance webhooks with attacker-chosen shop targets), this can lead to cross-tenant data corruption or spoofed compliance actions — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker to be a merchant who has installed the app (no special privilege beyond normal app installation) so they can observe at least one valid body+HMAC pair from their own real webhook traffic, and (2) the ability to POST arbitrary HTTP headers to the app's public webhook endpoint, which is inherent to any HTTP client. No access token, `client_secret`, or leaked credential is needed — the merchant only ever sees their own legitimately-issued webhook. This is a straightforward replay with header substitution, well within reach of a single unprivileged app-installer.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value inside the HMAC-signed content, or otherwise cryptographically bind the shop domain to the signed payload, so `HmacValidator.validate` fails whenever the shop header is altered relative to what was actually signed by Shopify for that specific shop/body pair. At minimum, `Request#to_signable_string` should incorporate `shop` so verification and the value acted upon by `Registry.process` refer to the same authenticated bytes.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same app, same shared `api_secret_key`).
2. The attacker (installer of `shop-a`) receives a genuine webhook from Shopify: body `B`, header `x-shopify-shop-domain: shop-a.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)` per `Request#to_signable_string`/`HmacValidator` [1](#0-0) .
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and matches `H` — validation succeeds [3](#0-2) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` [6](#0-5) , causing the app to process an event as belonging to `shop-b`, even though it was never actually signed/sent by Shopify for `shop-b`.
