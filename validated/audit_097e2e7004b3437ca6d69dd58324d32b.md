## Title
Webhook Shop Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC verification in this gem authenticates only the raw request body, while the `shop` value used to identify the tenant for the webhook (taken from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) is never included in the signed bytes. This breaks the intended binding: `HMAC-verified bytes == raw_body` vs. `tenant-identifying bytes == shop-domain header`, which is never authenticated at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `shop` accessor reads directly from an unauthenticated header: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` to build `WebhookMetadata` that is handed to the app's business logic as the tenant identifier: [3](#0-2) 

Contrast this with the OAuth callback path, where the equivalent `shop` field is explicitly included in the signed content (`AuthQuery#to_signable_string`), correctly binding shop to the signature: [4](#0-3) 

For webhooks, no such binding exists. Because the app's `client_secret`/`api_secret_key` is a single shared value used to sign webhooks for *every* shop that has installed the app, any shop that installs the app can capture a `(raw_body, hmac)` pair that Shopify legitimately signed for its own webhook delivery, and replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. The HMAC check passes (it only checks the body bytes), and `Registry.process` dispatches to the app's handler with `data.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who merely installs the app on their own shop (an unprivileged actor from the perspective of any other merchant) can forge webhook deliveries that the host application will attribute to a different merchant's shop, since `shop` is never cryptographically bound to the authenticated payload. Depending on how the host app consumes `WebhookMetadata#shop` (e.g., to look up sessions, trigger `app/uninstalled` cleanup, GDPR redaction flows, or other tenant-scoped side effects), this enables cross-tenant data manipulation/corruption using only a valid signature obtained from the attacker's own shop.

### Likelihood Explanation
Exploitation requires only that the attacker (or any other party who can observe a shared webhook payload/signature, since the same `client_secret` signs all shops' webhooks for a given app) install the target app on any shop they control, capture one legitimate `(body, hmac)` pair from a webhook topic with body content they don't need to control precisely (e.g., a topic with an empty or predictable body), and replay it directly to the app's public webhook endpoint with a forged shop header. No access token, session, or `api_secret_key` knowledge is required — only the gem's own documented header/body contract.

### Recommendation
Include the shop identity in the material used to compute/verify the webhook signature — e.g. Shopify's own signature semantics only cover the body, so the gem should instead bind `shop-domain` (and ideally `topic`/`webhook-id`) to the trusted context by deriving/validating it against known installed-shop state, or by requiring the host application to cross-check `request.shop` against a shop for which a stored session/webhook registration exists, before trusting it as the tenant key. At minimum, document loudly that `request.shop` is not authenticated by the HMAC and must not be used as a sole tenant-binding key without additional verification (e.g., against active sessions).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining valid webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures a delivered webhook with raw body `B` and its valid header `x-shopify-hmac-sha256: H` (any topic with a body they can obtain, e.g. `app/uninstalled` with body `{}`).
3. Attacker POSTs to the victim app's webhook endpoint with:
   - body: `B`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`: original topic
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only hashes `B`: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, believing the event genuinely originated from the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
