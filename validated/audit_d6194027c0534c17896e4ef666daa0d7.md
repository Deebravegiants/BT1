### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook data forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` field used to attribute the webhook to a tenant is read from an unauthenticated header. The gem's own documentation instructs consumers to trust `data.shop` as the tenant identifier after `Registry.process` verifies the HMAC, but the signature never binds `shop` to the payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding [2](#0-1) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which signs/verifies `to_signable_string` (i.e., only the body) against `Context.api_secret_key` [3](#0-2) [4](#0-3) . After this check passes, `request.shop` (the unauthenticated header) is forwarded directly into `WebhookMetadata` and handed to the app's handler as the tenant identifier [5](#0-4) .

The gem's documentation explicitly tells integrators to key their business logic off `data.shop` as "The shop domain of the webhook" [6](#0-5)  and describes `Registry.process` as verifying "the request did indeed come from Shopify" before invoking the handler [7](#0-6)  — but the verification only proves the body was signed by holder of `api_secret_key`; it proves nothing about which shop the body is attributed to.

This breaks the intended identity binding: `shop header value == tenant the payload is attributed to` should equal `shop covered by HMAC`, but instead `shop` is entirely outside the signed material.

### Impact Explanation
Because Shopify signs webhooks using a single `client_secret` shared across all shops that have installed a given app (not a per-shop secret), any legitimate merchant/tenant of the app can obtain a validly HMAC-signed `(body, hmac)` pair by triggering an event on their own store (e.g., editing their own product/order data to attacker-chosen content). That attacker-controlled `(body, hmac)` pair remains valid regardless of which `shop-domain` header accompanies it, since `shop` is not part of the signed string. By replaying the same body+hmac to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain, an attacker can make the app process attacker-chosen webhook data as if it originated from the victim's store — a cross-tenant data-integrity/confusion issue whose severity depends on how the host app uses `data.shop` (e.g., to look up/update per-tenant records), potentially leading to state corruption or cross-tenant data injection in the merchant's own store.

### Likelihood Explanation
Exploitation requires: (1) the attacker to be an installer/merchant of the target app (to legitimately trigger Shopify-signed webhooks with attacker-chosen body content), and (2) the ability to intercept/replay/craft the raw HTTP request to the app's webhook endpoint with a modified `shop-domain` header (webhook endpoints are typically unauthenticated public URLs, so this is a network-reachable, unprivileged action once a valid signed body/hmac pair is obtained). No access token, `client_secret`, or privileged credential is required — only interaction reachable by an ordinary merchant using the gem's documented API as designed.

### Recommendation
Bind the shop identity into the webhook signature verification path: either require verification that `request.shop` matches an expected/registered shop for the session performing the lookup, or extend `to_signable_string`/verification to incorporate the shop domain (and other trust-relevant headers) so that the header cannot be swapped independently of the signed body. At minimum, update documentation to explicitly warn that `data.shop` is not authenticated by the HMAC check and must be independently validated (e.g., against a known list of installed shops) before being used as a tenant key.

### Proof of Concept
1. App has webhooks registered; endpoint receives `POST /callback/orders/create`.
2. Attacker (merchant of shop `attacker.myshopify.com`) edits an order on their own store so Shopify sends a genuine webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, valid `x-shopify-hmac-sha256: H` computed by Shopify using the app's shared `client_secret` over `B`.
3. Attacker captures `(B, H)` and resends the identical POST to the app's webhook endpoint, replacing only the header: `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [8](#0-7) .
5. The handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, and the host app processes attacker-controlled data attributed to `victim.myshopify.com` [5](#0-4) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
