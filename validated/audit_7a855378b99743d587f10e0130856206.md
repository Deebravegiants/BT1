### Title
Local success determination bypasses backend duplicate/fraud registration for user-centric signups - (File: `src/plans/mod.rs`)

### Summary
`do_signup` in `MasterPlan` (`src/plans/mod.rs`) determines signup success in two different ways depending on the `user_centric_signup` flag. For the normal path it calls `enroll_user::Plan::run`, which performs the authoritative backend registration/duplicate-check round-trip (`signup_post::request` + polling `signup_poll::request`). For the `user_centric_signup` path, this authoritative call is skipped entirely, and success is derived purely from the locally-computed `signup_reason` (built from a pipeline result and a local `detect_fraud` call). This mirrors the `TopUpActionLibrary.lockFunds` bug class: a critical state-mutating/verifying call (`stakerVault.increaseActionLockedBalance` / here, the backend `signup_post`/`signup_poll` registration) is omitted on one path, letting a downstream trust decision (`success`) be computed from stale/never-updated authoritative state.

### Finding Description
In `do_signup`: [1](#0-0) 
when `user_centric_signup` is true and the backend hasn't set `ignore_user_centric_signups`, `success` is computed directly from `signup_reason` without ever invoking `self.enroll_user(...)`, which is the only code path that talks to the backend's `signup_post`/`signup_poll` endpoints: [2](#0-1) 
Those backend endpoints are explicitly documented as the mechanism that detects "Backend duplicates", "Backend inflight matches", and "Backend detected fraud" (see the comment block in `enroll_user.rs`). Skipping this call means the backend's authoritative uniqueness/duplicate ledger is never consulted or updated for this signup path.

The local fallback decision instead relies on `detect_fraud`: [3](#0-2) 
which in this repository always returns `false` ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS"), meaning `signup_reason` will be `Normal` for any signup where the biometric pipeline produced output, regardless of prior enrollments.

### Impact Explanation
Because the backend's duplicate/fraud-registration round trip is never invoked on the `user_centric_signup` path, a signup can be marked `Success` (`debug_report.signup_successful()`, `enroll_user::Status::Success`) locally without the backend's authoritative signup/duplicate ledger ever being updated or consulted for that identity. This is the same class of impact as the original report: a security-relevant counter/state (here, backend-side signup registration/duplicate tracking) is not updated on one code path, allowing that path's checks (which depend on the up-to-date state) to be silently bypassed, enabling unauthorized/duplicate signup success and cross-signup state bleed between the local success determination and backend truth.

### Likelihood Explanation
Reachability depends on the backend granting `user_centric_signup = true` for a given user QR/session (via `orb_qr_link::UserData`), which is outside the orb's control, but once granted, the orb-side code executes this bypass unconditionally for any completed biometric pipeline, with no additional backend confirmation step. Given that `detect_fraud` is a stub that always returns `false` in this codebase, the "safety net" of local fraud detection provides no compensating control, making the missing backend call the sole gate for correctness on this path.

### Recommendation
Do not fully bypass the backend registration/duplicate-check flow for `user_centric_signup`. At minimum, still invoke a backend call equivalent to `signup_post`/`signup_poll` (or an explicit lightweight duplicate-check endpoint) to update/verify the authoritative signup state before marking `success = true`, mirroring the fix in the referenced report (calling the missing state-update function after the state-changing operation).

### Proof of Concept
1. Backend returns user data with `user_centric_signup = true` for a session (`src/backend/user_status.rs` lines 203-244).
2. `do_signup` executes biometric capture/pipeline; `detect_fraud` returns `false` unconditionally (`src/plans/mod.rs` lines 1392-1406).
3. `signup_reason` becomes `SignupReason::Normal`.
4. The `user_centric_signup` branch sets `success = true` and `debug_report.enrollment_status(enroll_user::Status::Success)` without ever calling `enroll_user::Plan::run` / `signup_post::request` / `signup_poll::request` (`src/plans/mod.rs` lines 639-656).
5. The backend's duplicate/fraud ledger (normally updated/consulted via `enroll_user.rs` lines 90-176) is never contacted, so this signup completes as "Success" while the backend-side uniqueness state remains unaware of it.
