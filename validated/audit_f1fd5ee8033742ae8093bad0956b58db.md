### Title
Webhook shop/topic attribution not covered by HMAC signature enables cross‑tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature computed by `HmacValidator` only covers the raw request body [1](#0-0) . Since `Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop` header value to the app's handler, an attacker can take any single legitimately-signed webhook body (obtained by installing the app on their own store) and replay it with a forged `shop-domain` header pointing at a victim shop, breaking the binding between the HMAC-verified payload and the shop it is attributed to.

### Finding Description
`HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string`, and for webhook requests this method returns only `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then trusts `request.shop` when constructing the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The gem's own documentation instructs host applications to treat `data.shop` as the authoritative shop for the verified webhook and to key downstream work off of it (e.g. `shop_domain: data.shop`): [5](#0-4) 

Because the shop attribution is not part of the signed payload, "HMAC passed" only proves the body came from Shopify for *some* shop that has the app installed — not that it came for the specific shop named in the `shop-domain` header. Any unprivileged actor who installs the app on their own store (a normal, unprivileged action) will receive genuinely-signed webhook bodies for that store, and can then replay the exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain`/`x-shopify-shop-domain` header value. The signature check still succeeds, and the host app processes attacker-supplied body content as if it belonged to the victim tenant.

This is the same class of bug flagged in the analog report: a value that participates in trust decisions (shop identity) is not covered by the same authentication check as the payload it accompanies (`checkPermission`-style binding break), i.e. `hmac_valid(body) == true` does not imply `shop_header == shop_that_produced(body)`.

### Impact Explanation
This crosses a tenant boundary: an attacker with no privileges on the victim's shop can cause an app built on this gem to process attacker-chosen webhook bodies (subject/order/customer data, etc.) under the identity of the victim shop, since the handler is only ever given the header-derived `shop` value and the documented contract tells integrators to trust it. Depending on how the host app uses `data.shop` (e.g., to look up the victim's stored session/access token, enqueue background jobs keyed by shop, or write records against the victim's tenant), this enables cross-tenant data injection/confusion — matching the High-severity "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: the only prerequisite is the ability to install the target app on any shop (including the attacker's own, a completely unprivileged action available to any Shopify merchant/developer), which yields a valid `(body, hmac)` pair. Forging the `shop-domain` header on a raw HTTP request to the app's public webhook endpoint requires no additional secret material. No access token, `api_secret_key`, or privileged account on the victim tenant is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the specific webhook subscription/secret used to sign the body, so that a valid signature for one shop's payload cannot be replayed while claiming a different shop identity. At minimum, document/require host apps to cross-check `data.shop` against the shop associated with the specific webhook subscription (e.g. via `webhook_id` lookup) rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker sends this exact `(raw_body, hmac_header)` pair to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the signature over `raw_body` only and it matches, so `Registry.process` proceeds.
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-originated body, and — per the gem's documented usage pattern — processes/enqueues work attributed to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
