### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by verifying an HMAC over the raw request body only, but hands the app's `handle` callback a `shop` value taken from an unauthenticated header. Since the app-level `api_secret_key` is shared across every shop that installs the app, any tenant can obtain a validly-signed webhook body (by triggering an event on their own store) and replay it with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, breaking the binding "shop that produced the HMAC-signed bytes == shop attributed to the event."

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before invoking the handler: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` returns only `@raw_body`, and `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never mixed into the signable string: [3](#0-2) [4](#0-3) 

The verified `shop` value is then propagated as the tenant identifier into `WebhookMetadata`, which the host app's `WebhookHandler#handle` implementation uses to scope side effects (e.g., persisting data, billing, deletion) per shop: [5](#0-4) [6](#0-5) 

By contrast, the OAuth callback signing (`Auth::Oauth::AuthQuery`) correctly binds `shop` into the signed string used for HMAC verification: [7](#0-6) 

Because `api_secret_key` (the app's client secret) is identical for every shop installing the same app, HMAC validity on a webhook body proves only "this body+signature pair was produced by Shopify for *some* shop running this app" — not "this body belongs to the shop named in this header." An attacker who runs their own store on the target app can capture one of their own legitimately-signed webhook deliveries (valid `hmac` + `raw_body`) and re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it never looks at the header), so `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the equality "shop bound by the cryptographic signature == shop the application attributes the event to," which is exactly the tenant-isolation guarantee webhook processing is supposed to provide. Any app that uses the `shop` field from `WebhookMetadata` to scope data writes, deletions, or entitlement changes (the intended and documented usage pattern) can have those actions misattributed to an arbitrary tenant chosen by any other tenant of the same app — a cross-tenant access/write vulnerability reachable by an unprivileged merchant who has simply installed the app on their own store (no special credentials needed beyond normal app installation, which any user can do).

### Likelihood Explanation
Moderate-to-high: exploitation only requires installing the target app on an attacker-controlled shop (freely available to any Shopify user), triggering any webhook event to capture a valid `(raw_body, hmac)` pair, and replaying it against the shared webhook endpoint with a modified shop-domain header. No access to `api_secret_key`, access tokens, or victim credentials is required.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the claimed shop to the signed payload, e.g.:
- Include the shop domain (and ideally topic/webhook-id) in the string used for `to_signable_string`, matching the pattern already used in `Auth::Oauth::AuthQuery`, or
- Cross-check the header-derived shop against an independent, previously-established record for that installation (e.g., verify the shop is registered/known and that the specific webhook subscription id belongs to that shop) before trusting `request.shop` for tenant-scoped actions, or
- Document prominently (and enforce in `Registry.process`) that `request.shop` must not be trusted for tenant attribution unless corroborated by a per-shop webhook secret or additional binding, since Shopify's default HMAC scheme signs the body with the app-wide secret, not a per-shop secret.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test shop `attacker.myshopify.com` (using this gem's OAuth flow).
2. Attacker triggers a webhook event on their own shop (e.g., updates a product), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: HMAC(app_secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com` to the app's webhook endpoint.
3. Attacker captures `B` and the valid HMAC, then re-sends the same `B` and HMAC to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(app_secret, B)` (per `lib/shopify_api/webhooks/request.rb` line 36-38 and `lib/shopify_api/utils/hmac_validator.rb` line 26-31), independent of the shop header.
5. The app's handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` and performs shop-scoped side effects attributed to `victim.myshopify.com`, even though the event actually originated from the attacker's own shop.
