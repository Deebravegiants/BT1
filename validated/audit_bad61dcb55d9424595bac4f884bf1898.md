### Title
`fund_message` allows funding an already-completed (delivered or timed-out) ISMP request/response, permanently burning the caller's funds - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
Pallet-ismp exposes a signed, unprivileged extrinsic `fund_message` that lets any user top up the relayer fee for a pending cross-chain request or response, keyed only by its `MessageCommitment`. The pallet's own documentation states the call "should not be called on a message that has been completed (delivered or timed-out) as those funds will be lost forever," which is the same root cause as the referenced Sublime finding: a state-changing, fund-moving entrypoint that does not verify the target's lifecycle status before accepting value, so a mistaken or racing call permanently destroys the caller's tokens. [1](#0-0) 

### Finding Description
`fund_message` is a `Signed`-origin call taking `FundMessageParams { commitment, amount }` and increasing the escrowed relayer fee tied to that commitment. [2](#0-1)  The documented call table explicitly flags the danger: calling it on a request/response that has already been delivered or timed out destroys the additional fee, because completed messages no longer have a live path that would refund or forward the extra fee back to the payer — the escrow bookkeeping for that commitment has already been settled/removed by the delivery or timeout handler. [3](#0-2) 

This mirrors the Sublime `depositCollateral` bug class precisely: a fund-accepting function (`fundRequest`/`fund_message`) that does not gate on the commitment's lifecycle state (pending vs. delivered/timed-out) before pulling in value from an unprivileged caller. The EVM-side analog, `IDispatcher.fundRequest`, appears to have mitigated this by donating funds to the protocol when the request is already delivered rather than losing them, per its documented behavior. [4](#0-3)  The Substrate-side `fund_message`, however, is documented only as "should not be called" on a completed message, with no stated fallback or safety net for that case, indicating the enforcement is left to the caller rather than the pallet.

### Impact Explanation
A relayer, dApp, or end-user who calls `fund_message` slightly too late — a common race given that delivery/timeout can land in the same or an adjacent block as the funding transaction — has their `amount` permanently and unrecoverably lost, since the underlying request/response commitment record it was meant to top up no longer exists in a "pending" state to receive or refund it. This is a direct, permanent loss of user funds through a normal, expected interaction with the protocol, reachable by any signed account with no privileged access required.

### Likelihood Explanation
Likelihood is realistic rather than purely theoretical: `fund_message` is intended for exactly the scenario where delivery is slow or uncertain (to "incentivize faster delivery"), which is also the scenario most likely to race against delivery/timeout finalizing in parallel. Automated fee-bumping bots or manual users reacting to a stalled request are the primary callers, and they cannot atomically guarantee the message is still pending at the moment their transaction executes.

### Recommendation
Add an explicit check in `fund_message` (or the corresponding `IsmpDispatcher` fee-escrow update path in `modules/pallets/ismp/src/lib.rs` / `modules/pallets/ismp/src/utils.rs`) that the target commitment still has a live, pending `RequestCommitments`/`ResponseCommitments` entry before accepting and escrowing `amount`; reject with an error (e.g., `MessageAlreadyCompleted`) otherwise, so the extrinsic can never silently burn a user's tokens. This mirrors the recommended fix for the original Sublime issue: require the resource to be in an active/collectable state before accepting a deposit.

### Proof of Concept
1. Alice dispatches a `Get`/`Post` request via `dispatch_request`, producing `commitment`. [5](#0-4) 
2. A relayer delivers the response (or the timeout window elapses and the timeout handler runs), which removes/settles the commitment's fee-tracking state for that request.
3. Concurrently, or just after, Alice (unaware of step 2) submits `fund_message` with `MessageCommitment::Request(commitment)` and `amount = 10 * UNIT`, mirroring the pallet's own test flow. [6](#0-5) 
4. Per the pallet's documented behavior, because the message is now completed, the `amount` transferred is lost forever with no recovery path — the same "user error, but the protocol enables it and loses the funds silently" outcome the original C4 report flagged, and Sublime chose to add a check for despite disagreeing on severity. [7](#0-6)

### fundRequest()

Increases the relayer fee for a pending request to incentivize faster delivery.

```solidity lineNumbers
function fundRequest(bytes32 commitment, uint256 amount) external payable
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `commitment` | `bytes32` | The request commitment hash |
| `amount` | `uint256` | Additional relayer fee in fee token |

**Payment:**
- **Native token** (`msg.value`): Automatically swapped to fee token via Uniswap
- **Fee token**: Transferred from caller (requires prior approval)

**Behavior:**
- Additional fee refunded to `payer` if request times out
- Can be called multiple times for incremental increases
- If request already delivered, funds donated to protocol
