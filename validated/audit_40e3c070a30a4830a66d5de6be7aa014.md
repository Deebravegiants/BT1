## Finding: PoA Bridge withdrawal status/txHash can be misattributed across concurrent same-asset withdrawals

### Title
PoA Bridge `describeWithdrawal()` matches withdrawal status by `assetId` only, misreporting status/txHash for concurrent same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` looks up the on-chain outcome for a specific withdrawal by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely on `assetId` rather than on a unique identifier tied to that particular withdrawal (destination address, amount, or PoA bridge withdrawal id/index). [1](#0-0) 

### Finding Description
The comment directly above the lookup states: *"Response list is unsorted, so we match by assetId instead of index"* [2](#0-1) . The CHANGELOG confirms this was a deliberate change from index-based matching to assetId-based matching (`8bbd5c6: Fix POA bridge withdrawal matching to use assetId instead of index.`) [3](#0-2) .

If a caller has more than one PoA withdrawal outstanding for the same `assetId` (same token, e.g. two USDT-on-Ethereum withdrawals to different destination addresses, or a retried withdrawal for the same user), the underlying PoA bridge status API returns a list of withdrawals for the account, and `findMatchingWithdrawal` picks based on `assetId` alone. This breaks the equality "status/txHash reported for withdrawal A must be the on-chain outcome for withdrawal A" - the SDK can return withdrawal B's `COMPLETED` status and `transfer_tx_hash` when the caller asked about withdrawal A (or vice versa), since both share the same `assetId`.

I was not able to view the full body of `findMatchingWithdrawal` (defined in `poa-bridge-utils.ts`, referenced from `poa-bridge.ts`) in this session to confirm whether it applies any additional disambiguating filter beyond `assetId` (e.g., matching also on destination address or amount). The comment and changelog entry strongly suggest `assetId` is the sole matching key, but this should be verified directly against the `findMatchingWithdrawal` implementation before treating this as confirmed.

### Impact Explanation
Per the scoring rubric, "a status or hash misreport making an integrator credit or refund twice" is a High-severity outcome. An integrator (exchange, wallet, custodial service) that calls `sdk.processWithdrawal` / `waitForWithdrawalCompletion` for multiple same-asset withdrawals concurrently and relies on the returned `status`/`txHash` to mark a specific withdrawal as settled could:
- Mark withdrawal A as completed using withdrawal B's destination tx hash, causing the integrator to release funds or clear an internal ledger entry for A while A is still pending/unconfirmed on-chain (or never happened), or
- Attribute the wrong `transfer_tx_hash` to a customer support/reconciliation record, causing a double-credit or a wrongly-cleared liability.

### Likelihood Explanation
This does not require a malicious actor — any normal user or service issuing two or more concurrent withdrawals of the same PoA-bridged token (a very common pattern for a custodial withdrawal queue) can trigger the ambiguity. Whether it is exploitable in practice depends on the exact match rule inside `findMatchingWithdrawal`, which I could not confirm within this session — this is the key remaining uncertainty.

### Recommendation
- Have `findMatchingWithdrawal` disambiguate by more than `assetId`, e.g. by destination address, amount, and/or a unique withdrawal identifier/near-tx-hash+index tuple that the PoA API exposes, so that `describeWithdrawal` for withdrawal A can never return withdrawal B's `transfer_tx_hash`.
- If the PoA bridge status API does not expose a reliable unique key per near-tx-hash+index, consider having `IntentsSDK` refuse to disambiguate and instead surface an explicit ambiguity error rather than silently returning a status that might belong to a different withdrawal.

### Proof of Concept
Not independently verified (would require confirming `findMatchingWithdrawal`'s matching predicate and PoA bridge API response shape for a NEAR account with two outstanding withdrawals of the same `assetId`). 	async describeWithdrawal(
```typescript
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```
