### Title
Emporium acts as unauthenticated pooled custody: CASE 2 stateless ops let any caller sweep another user's uncounted vault-share position - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
A victim's `transact` call routes through `EmporiumUpgradeable.runAction` to deposit into an ERC4626 vault, minting vault shares to Emporium's own address. Because `circomData.erc20TokenAddresses` for that call only lists the underlying asset, no balance check or UTXO is ever produced for the shares, leaving them as an untracked, unowned ERC20 balance sitting at the Emporium contract. A second, unrelated attacker can later submit their own `transact` call whose `erc20TokenAddresses` lists only the underlying asset and whose CASE 2 (`signerAddress == address(0)`, no signature check) op calls `vault.redeem(shares, receiver=Emporium, owner=Emporium)` — a call that succeeds because `msg.sender == owner == Emporium` — recovering the underlying assets into Emporium's balance, which `handleOut` then sweeps into a UTXO owned by the attacker.

### Finding Description
The broken equality is the balance-conservation check in `Hinkal.transact`:
`balanceDif == amountChanges[i] + utxoAmount` for each `circomData.erc20TokenAddresses[i]` [1](#0-0) .

This check is only ever evaluated over the token addresses that the *current* caller chooses to include in their own `circomData.erc20TokenAddresses`. Nothing forces every asset that a prior call left at Emporium (e.g., minted vault shares) to be included in that same call's array, so the victim's deposit never produces a UTXO for the shares:
- Victim's op: `endpoint=vault`, `callData=deposit(assets, receiver=Emporium)`. Shares are minted to Emporium's address, but `circomData.erc20TokenAddresses` only lists the underlying asset, so `EmporiumUpgradeable.runAction`'s `balancesBefore/balancesAfter` diff loop and `handleOut` never observe or move the share balance [2](#0-1) . The shares remain sitting at Emporium, uncounted and unlinked to any UTXO.

The root cause enabling theft is that CASE 2 stateless ops execute **arbitrary attacker-controlled calls** from Emporium's own address with no authentication when `signerAddress == address(0)`:
```
else {
    bytes4 selector = bytes4(op.callData);
    if (selector == callHinkalWallet.selector || selector == doSendToRelay.selector) revert UnauthorizedWalletCall();
    (success, err) = op.endpoint.call{value: op.value}(op.callData);

``` [3](#0-2) 
And `verifyWallet` explicitly skips signature verification entirely when `stack.signerAddress == address(0)`:
```
if (stack.signerAddress == address(0)) { return; }
``` [4](#0-3) 

Attacker's exploit call: their own `transact` with `erc20TokenAddresses = [underlyingAsset]`, `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one CASE 2 op: `endpoint = vault`, `callData = redeem(sharesAmount, receiver = Emporium, owner = Emporium)`. Since the low-level `.call` is made from Emporium's own address, `msg.sender == owner` inside the vault's `redeem`, so OpenZeppelin ERC4626's allowance check is trivially satisfied without the attacker owning any shares. The redeem burns Emporium's (victim-derived) shares and sends the underlying assets back to Emporium. `EmporiumUpgradeable.runAction`'s balance diff then sees `balancesAfter[underlying] - balancesBefore[underlying] > 0`, and `handleOut` transfers that increase to `msg.sender` (Hinkal) and creates a UTXO encrypted for the **attacker's** own stealth address [5](#0-4) . The `require(balanceChange < 0)` guard, `Hinkal.transact`'s slippage/balance checks, `performHinkalChecks`, `dimensionsCheck`, and the circuit's `inTotal + amountChanges === outTotal` constraint all evaluate correctly for the attacker's *own* declared token set — none of them can detect that the redeemed shares were never the attacker's, because that fact lives entirely outside the tracked `erc20TokenAddresses` array and outside any UTXO or nullifier.

### Impact Explanation
This is direct, unauthenticated theft of a victim's shielded vault position: the attacker drains the underlying value of vault shares that were minted to Emporium on the victim's behalf, converting them into a UTXO owned by the attacker. This matches Critical severity ("direct theft of shielded or in-flight user funds"). The attack is repeatable against any Hinkal user who performs an Emporium-mediated interaction with an external contract that mints/leaves value (shares, LP tokens, rewards, etc.) in a token not included in that call's `erc20TokenAddresses`.

### Likelihood Explanation
Preconditions: (1) some prior call through Emporium leaves a fungible ERC20 position (e.g., ERC4626 shares) sitting at Emporium's address that was not included in that call's `erc20TokenAddresses`; (2) the position's redeeming interface allows the holder (Emporium) to redeem/withdraw to an arbitrary receiver with `msg.sender == owner`. Both are common patterns (any vault/staking/LP integration where Emporium is the position holder). The attacker needs no special role — any EOA can submit a `transact` call with a self-crafted CASE 2 `EmporiumStack` (no signature required when `signerAddress == 0`), and only needs to know/observe that Emporium is holding an uncaptured position (observable on-chain via the vault's share balance). Cost is a single transaction with a valid proof for the attacker's own (even zero-value) UTXO set.

### Recommendation
- Require that any token balance change occurring on Emporium during an op be attributable to the same call's declared `erc20TokenAddresses`/UTXO set — e.g., track Emporium's exact set of held tokens per position and require it to be closed out (converted to a UTXO or explicitly re-deposited) in the same transaction that creates it, rather than allowing leftover balances to persist.
- Disallow or tightly scope CASE 2 stateless calls when `signerAddress == address(0)`; at minimum, restrict the endpoints/selectors callable in this unauthenticated mode, or require an allowlist tying `op.endpoint` to declared `erc20TokenAddresses` so redemption targets can't be freely chosen by an unrelated caller.
- Alternatively, force all value-bearing external interactions (vault deposits/withdraws) to go through `IHinkalWallet.callHinkalWallet` (CASE 1, per-user signed wallet) rather than Emporium's shared address, so shares are never custodied by a shared contract reachable by arbitrary third parties.

### Proof of Concept
Foundry test plan:
1. Deploy a mock ERC4626 vault over a mock ERC20 underlying, `EmporiumUpgradeable`, `Hinkal`, and required helper/verifier mocks.
2. Victim performs `transact` with `externalActionId` = Emporium, `erc20TokenAddresses = [underlying]`, CASE 2 op `endpoint=vault, callData=deposit(assets, receiver=Emporium)`. Assert vault shares are minted to Emporium and that no UTXO/commitment for the share token was created (only the underlying-asset balance equation `balanceDif == amountChanges[i] + utxoAmount` is checked and satisfied).
3. Attacker (unrelated, funds their own dummy UTXO) submits `transact` with `erc20TokenAddresses = [underlying]`, CASE 2 op `endpoint=vault, callData=redeem(victimShares, receiver=Emporium, owner=Emporium), signerAddress=address(0)`.
4. Assert the call succeeds without any signature from the victim, that Emporium's underlying balance increases, and that a UTXO for that increase is created with the attacker's `stealthAddressStructure`.
5. Assert attacker's redeemed value exceeds anything the attacker deposited themselves, proving the underlying assets recovered belong to the victim's original deposit.
