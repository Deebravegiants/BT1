Audit Report

## Title
Concurrent map read/write in `WorkflowMetadataHandler.Authorize` causes remote unauthenticated Gateway crash - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` without acquiring `h.mu.RLock()`, while the periodic `syncMetadata` background goroutine replaces the entire `authorizedKeys` map (along with `workflowRefToID`, `workflowIDToRef`, `workflowShards`) under `h.mu.Lock()`. Since `Authorize` sits on the hot path of every incoming HTTP trigger request (`HandleUserTriggerRequest` → `authorizeRequest` → `Authorize`), an attacker who floods the Gateway with concurrent trigger requests can race an unlocked read against the periodic locked write and trigger Go's unrecoverable `fatal error: concurrent map read and map write`, crashing the entire Gateway process.

## Finding Description
`WorkflowMetadataHandler` guards its shared maps with `h.mu sync.RWMutex`, and this pattern is followed correctly everywhere else in the file: `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference` all acquire `h.mu.RLock()`/`RUnlock()` before touching `workflowShards`, `workflowRefToID`, or `workflowIDToRef`. `Authorize`, however, reads `h.authorizedKeys[workflowID]` and iterates the returned inner map with zero locking. Concurrently, `syncMetadata` — scheduled via `runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)` in `Start` — builds fresh maps and swaps them into `h.authorizedKeys`, `h.workflowRefToID`, `h.workflowIDToRef`, `h.workflowShards` while holding `h.mu.Lock()`. `Authorize` is reachable via `httpTriggerHandler.authorizeRequest`, called from `HandleUserTriggerRequest`, the entry point for external/unauthenticated-at-that-point HTTP trigger submissions to the Gateway. This is a genuine violation of Go's map concurrency contract: an unlocked read racing a locked full-map reassignment satisfies the conditions for the runtime's fatal (non-recoverable) concurrent map access detector.

## Impact Explanation
This is a full denial-of-service against the Gateway process: a crash here takes down JSON-RPC handling for every DON, shard, and workflow served by that Gateway instance, not just the targeted workflow, and is triggerable by an external caller with only a valid/guessable `workflowID` and no valid JWT (the crash occurs in/around the map lookup itself). This maps to an in-scope Chainlink impact class (gateway request handling / availability of node-facing services).

## Likelihood Explanation
The race window depends on hitting the periodic `syncMetadata` write (default interval `MetadataAggregationIntervalMs`, e.g., 60s), but since `syncMetadata` unconditionally reassigns the maps every cycle regardless of change, an attacker can trivially increase likelihood by sending sustained high-concurrency trigger requests, similar to typical concurrent-map-access race PoCs. No special privileges or credentials are required to reach `Authorize` — it is exercised before JWT validity is meaningfully required to succeed (JWT is verified first, but the vulnerable unlocked read happens right after, on every request with a syntactically valid JWT and any/guessable workflowID).

## Recommendation
Acquire `h.mu.RLock()`/`h.mu.RUnlock()` around the read of `h.authorizedKeys[workflowID]` (and the inner-map lookup) in `Authorize`, consistent with the locking pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Also audit `aggForNode`'s unguarded reads of `h.nodeAddrToShard` and `h.aggs` for the same class of bug, since these maps are not reassigned under lock elsewhere in the shown code but should still be reviewed for consistency.

## Proof of Concept
1. Run the Gateway with `-race` and an active DON registration so `syncMetadata` periodically executes.
2. From an external client, continuously send high-concurrency `HandleUserTriggerRequest` JSON-RPC calls (`gateway_common.MethodWorkflowExecute`) with a valid `workflowID`.
3. Under `-race`, this deterministically reports a `DATA RACE` between the read at `workflow_metadata_handler.go:92` and the write at `workflow_metadata_handler.go:178`; in production (without `-race`), sustained concurrent load will eventually align a read with `syncMetadata`'s map-swap, producing `fatal error: concurrent map read and map write` and crashing the process. A Go unit test spinning up goroutines calling `Authorize` concurrently with direct invocations of `syncMetadata` (or a scaled-down `MetadataAggregationIntervalMs`) under `-race` is sufficient to demonstrate the bug without needing the full aggregation pipeline populated.
