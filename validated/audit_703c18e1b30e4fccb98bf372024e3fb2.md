## Title
Uniform-priority permissionless `handle_unsigned` extrinsic enables free transaction-relay jamming of time-sensitive cross-chain messages - (File: `modules/pallets/ismp/src/lib.rs`)

## Summary
`pallet-ismp`'s `handle_unsigned` call is a permissionless, fee-free unsigned extrinsic that any actor can submit to deliver ISMP request/response/timeout batches [1](#0-0) . `ValidateUnsigned::validate_unsigned` assigns every request/response/timeout batch the *same* flat `priority: 100`, regardless of the message's urgency, size, or relayer fee, while only consensus updates get a higher priority tied to block height [2](#0-1) . Because `GetRequest` timeouts require no proof at all — only that the host's timestamp has elapsed — an attacker can manufacture an unbounded stream of cheap, valid, free, unsigned "filler" transactions at the same priority tier as a legitimate, fee-paying, deadline-sensitive delivery, congesting block space and mempool slots and delaying or starving the legitimate message until it exceeds its `timeout_timestamp`. This is the same bug class as CVE-2024-55563: flooding the relay/mempool layer with valid low-value traffic to prevent timely propagation of a specific transaction, thereby altering the outcome of a time-boxed off-chain-coordinated protocol (an HTLC in Bitcoin's case; an ISMP request/order deadline here).

## Finding Description
`pallet-ismp::Call::handle_unsigned` accepts arbitrary batches of `Message`s from an unsigned origin and is fully validated (including full protocol execution) inside `validate_unsigned`, which is designed to keep invalid or already-processed messages out of the pool [3](#0-2) . However, "valid" does not mean "useful" — the docs even acknowledge that all cross-chain messages are executed "for free" and rely solely on proof/duplicate validity to filter spam [4](#0-3) .

The transaction-pool priority computed for every request/response/timeout batch is a hardcoded constant, independent of relayer fee or urgency:
```rust
priority: if has_consensus { 200 } else { 100 },
``` [5](#0-4) 

`GetRequest` timeouts specifically need no state proof to be valid — only that `host.timestamp()` has advanced past the request's `timeout_timestamp` and that the request is known:
```rust
/// There are no proofs for Get timeouts, we only need to
/// ensure that the timeout timestamp has elapsed on the host
Get {
    requests: Vec<GetRequest>,
},
``` [6](#0-5)  and the handler enforces exactly that with no proof step [7](#0-6) .

An attacker can therefore:
1. Dispatch a cheap `GetRequest` (fee can legally be zero — `dispatch_request` only transfers a fee if `fee.fee != Zero::zero()` [8](#0-7) ) with a very short `timeout` from any account (this costs only a normal, cheap signed extrinsic).
2. Once the timeout elapses, repeatedly craft new, distinct, fully valid `handle_unsigned` timeout batches (each with a unique `provides` tag derived from the batch content, so they are not deduped) and submit them as free unsigned extrinsics.
3. Because every such batch is assigned the same flat `priority: 100` as a legitimate fee-paying relayer's time-critical `PostRequest`/`GetResponse` delivery batch, the attacker's flood competes on equal footing (or with more submission bandwidth, since it's free and infinitely repeatable) for the same limited block weight/pool slots.
4. This delays inclusion of the legitimate, deadline-sensitive delivery until it passes its own `timeout_timestamp`, at which point the request times out instead of being delivered.

This is structurally analogous to CVE-2024-55563: the ability to flood a permissionless relay/mempool layer with valid but low-value traffic (no signature/fee cost gate proportional to value) to prevent timely propagation of a specific, deadline-bound transaction, thereby forcing an unwanted "timeout" outcome instead of the intended settlement — exactly the "outcome of an HTLC changed because a flood of transaction traffic prevents propagation" pattern described in the advisory.

## Impact Explanation
A successfully jammed delivery causes a legitimate cross-chain message to time out instead of being delivered. Downstream this can:
- Cause a relayer's fee-paying delivery to be timed out and refunded to the payer instead of collected by the relayer, denying honest relayers their reward and undermining the delivery incentive market described in `docs/content/protocol/ismp/relayers.mdx`.
- Force an IntentGateway cross-chain fill message or `RedeemEscrow`/`RefundEscrow` settlement past its window, changing which cancellation/refund path becomes available (analogous to an HTLC timing out to the wrong party) — this is the same "off-chain protocol outcome changed by relay jamming" class flagged in the advisory.
- Generally degrade the liveness guarantee that ISMP's timeout mechanism was designed to provide only for genuine liveness failures, not for adversarially induced ones caused by free-to-produce filler traffic.

This is a medium-severity availability/timing-integrity issue reachable by any unprivileged actor without needing governance, admin, or protocol secrets — it only requires the ability to submit ordinary signed transactions plus unsigned extrinsics, both permissionless entry points.

## Likelihood Explanation
The `handle_unsigned` extrinsic is explicitly permissionless and fee-free by design [9](#0-8) , and `GetRequest` timeouts require no proof, only elapsed time [7](#0-6) . The priority scheme uniformly assigns `100` to every request-carrying batch regardless of fee or urgency [5](#0-4) . No mechanism in the reviewed code ties transaction pool priority, inclusion ordering, or per-account throttling to the economic value of the batch being relayed, making the attack straightforward to mount with modest sustained cost (one cheap signed dispatch per filler request, plus ongoing free unsigned resubmissions).

## Recommendation
- Scale unsigned-extrinsic priority by the economic value/urgency of the batch (e.g., attached relayer fee, remaining time-to-timeout) rather than a flat constant, so genuinely time-critical, fee-paying deliveries always outrank filler timeout batches.
- Consider rate-limiting or requiring a minimal bond/fee for `GetRequest` dispatch and/or for submitting timeout batches, closing the "dispatch cheap request → free-timeout-spam forever" loop.
- Consider giving timeout messages (which benefit only the request's own payer, per `docs/content/protocol/ismp/relayers.mdx`) a distinctly lower priority tier than delivery messages, since they compete for the same block space but serve non-time-critical, single-beneficiary purposes.

## Proof of Concept
1. Attacker account `A` dispatches a `DispatchGet` (or `DispatchPost`) request through any ISMP-dispatching pallet/module with `fee = 0` and a minimal `timeout` (e.g., 1 second) via a normal signed extrinsic — cheap and repeatable.
2. Once `host.timestamp()` passes the resulting `timeout_timestamp`, `A` submits `pallet_ismp::Call::handle_unsigned { messages: [Message::Timeout(TimeoutMessage::Get { requests: [get] })] }` as an unsigned extrinsic. `validate_unsigned` executes it successfully (no proof required for Get timeouts) and returns `priority: 100`, `longevity: 25` [2](#0-1) .
3. `A` repeats step 1–2 continuously with fresh nonces/requests, each producing a unique `provides` tag so none are deduplicated, saturating the transaction pool and block weight budget at the same `priority: 100` used by a legitimate relayer's fee-paying `PostRequest`/`GetResponse` delivery batch.
4. The legitimate batch is starved of inclusion until its own `timeout_timestamp` elapses, at which point the intended delivery becomes impossible and the request times out instead — the analog of the CVE-2024-55563 outcome-manipulation-via-relay-jamming.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
