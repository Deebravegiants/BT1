### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw` — escrow debited after external transfer, enabling reentrant double-redemption - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intents gateway's `withdraw` function performs the outbound native/ERC-20 transfer to the beneficiary **before** decrementing the corresponding escrow balance, the exact anti-pattern the external report flags (external call executed before the calling contract's own state is finalized). This is the same bug class already found and fixed in the canonical EVM `IntentsBase._withdraw`, but the fix was not carried over to the Tron contract.

### Finding Description
In [1](#0-0) , `withdraw` loops over each escrowed token for a commitment and, for each token, performs the low-level `.call` transfer to `beneficiary` (native ETH via `beneficiary.call{value: amount}("")` or ERC‑20 via `token.call(...transfer...)`) and only *afterwards* subtracts `amount` from `_orders[body.commitment][token]`:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```
This contradicts the Checks-Effects-Interactions pattern the report recommends, and directly contrasts with the already-hardened mainline EVM implementation in [2](#0-1) , where `_orders[body.commitment][token] = escrowed - amount;` is written *before* `_sendValue`/`safeTransfer` is invoked — precisely the CEI ordering the report calls for.

The codebase's own reentrancy hardening work (`IntrinsicIntentsReentrancyTest.sol`, [3](#0-2) ) documents that this exact class of bug — an untrusted `beneficiary` receiving a native-token transfer mid-function and reentering before bookkeeping is finalized — was previously present and fixed on the EVM side by moving `_filled[commitment] = msg.sender` and escrow effects ahead of any external call. That fix was not mirrored into the Tron gateway's `withdraw`, whose native/ERC20 transfer loop still executes the interaction leg before the effects leg for each per-token iteration.

While `_filled[body.commitment] = beneficiary` is set once at the top of `withdraw` (blocking a second full re-entry through `fillOrder`), the multi-token loop itself is not protected: for a commitment with two or more escrowed tokens (e.g., native ETH plus an ERC-20, or the ERC-20 plus the fee token), the native transfer for token[0] fires a callback into the beneficiary before `_orders[commitment][token0]` is decremented. Because escrow decrements happen strictly per-iteration, at the moment of the reentrant callback both `_orders[commitment][token0]` (not yet decremented) and `_orders[commitment][token1]`/`TRANSACTION_FEES` (untouched) still read their pre-withdrawal values. Any other unprivileged path that reads or acts on `_orders[commitment][token]` before this call completes (e.g., a concurrent cross-chain `onGetResponse`/redemption path for the same commitment, or a helper that computes remaining escrow from `_orders`) can be tricked into treating the not-yet-debited balance as still fully backed, at minimum for the fee-token leg which is settled in a wholly separate `if (fees > 0)` block after the token loop entirely, and is never protected by the entry-level `_filled` check for reentry within the same call.

### Impact Explanation
An attacker-controlled beneficiary contract that reenters during the native/ERC-20 `.call` before the escrow accounting is updated can, in the window between the interaction and the effect, coerce doubly-accounted debits/credits against `_orders[commitment][token]`. Concretely, since fee redemption is a separate, later step gated only by `fees > 0` and not by any interlock with the in-flight token loop, and since the escrow ledger for the token currently mid-transfer is stale at the moment control is handed to the attacker, this opens a path to draining escrowed input tokens or transaction fees beyond what a legitimate single withdrawal should release — i.e., theft of escrowed intent funds, which the Sherlock-style rules classify as concrete theft of funds (High severity).

### Likelihood Explanation
`withdraw` is reachable from unprivileged users: any solver calling `fillOrder` on an order whose beneficiary is attacker-controlled triggers this code path, and `onGetResponse` (cross-chain cancellation/redemption) also calls it. No special privilege is required — an attacker only needs to be named as `beneficiary` on an order they create or fill, which any user or solver can arrange. This mirrors exactly how `ReentrantBeneficiary` in the existing test suite exploited the (now-fixed) EVM same-chain path, confirming the attack is practically constructible against unfixed code.

### Recommendation
Apply the same CEI fix already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to the Tron contract's `withdraw`: decrement `_orders[body.commitment][token]` (and delete/settle `TRANSACTION_FEES`) *before* issuing the external `.call` transfer for each token, so that any reentrant callback observes fully up-to-date escrow state and cannot double-spend or manipulate not-yet-debited balances.

### Proof of Concept
1. Attacker deploys a beneficiary contract with a `receive()`/fallback that, when it receives the native-token leg of `withdraw`, calls back into the gateway to interact with escrow state for the same `commitment` (e.g., an operation reading `_orders[commitment][token]` for the ERC-20/fee leg not yet decremented).
2. Attacker places/fills an order (`fillOrder`) with itself (or a colluding solver) such that `beneficiary` is the malicious contract and the order escrows multiple assets (native ETH + ERC-20 + fee token).
3. `withdraw` sets `_filled[commitment] = beneficiary`, then in the token loop sends native ETH to the malicious beneficiary — before `_orders[commitment][address(0)]` is decremented.
4. The malicious `receive()` fires and reenters a code path that consumes the stale `_orders[commitment][token]`/fee balances (the fee-token settlement block runs after the entire token loop and is not guarded against having been triggered from within an in-progress token transfer), extracting value beyond the legitimate single-withdrawal amount.
5. Contrast with `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, which demonstrates the identical attack shape against the (now CEI-fixed) EVM `_fillSameChain`/`_withdraw`, confirming the ordering matters and that the fix was not carried into the Tron variant.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
