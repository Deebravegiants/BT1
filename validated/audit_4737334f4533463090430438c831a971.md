## Title
Webhook HMAC verification only covers the raw body, allowing the `shop-domain` header to be forged for cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking that the HMAC recomputed over the raw request body matches the `X-Shopify-Hmac-Sha256` header. The shop identity (`X-Shopify-Shop-Domain` header) that the handler receives and trusts as the tenant for the event is never included in the signed data, so it can be swapped for any value without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Registry.process` validates only that string against the HMAC header, then hands `request.shop` straight to the app's handler as the trusted tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the supplied `hmac`: [4](#0-3) [5](#0-4) 

Since `shop` is read from a header (`shop-domain`) that is not part of `to_signable_string`, the equality the library implicitly claims to the app — "the shop reported to the handler is the shop that produced this signed payload" — does not actually hold. The gem's own documentation instructs apps to treat `data.shop` as the authenticated shop for the event: [6](#0-5) [7](#0-6) 

Because Shopify's webhook HMAC uses the app's single shared `client_secret` (not a per-shop secret), any merchant who has installed the app can capture a legitimate `(raw_body, hmac)` pair delivered to the app's own webhook endpoint for their own store, then replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` calls the handler with `shop: request.shop` equal to the attacker-chosen value, spoofing the webhook as belonging to a different tenant.

### Impact Explanation
This breaks the identity binding `shop-domain header == shop that produced this signed body`. Any host application that keys per-tenant state (webhook idempotency stores, order/customer sync, GDPR redact handling for `shop/redact`/`customers/redact`, billing, provisioning) off `data.shop` as returned by this gem can be made to process forged data under another merchant's identity — a cross-tenant data-integrity/confusion issue reachable by any unprivileged merchant who has installed the app (no access token or `client_secret` required, only a valid webhook body+HMAC pair they legitimately received for their own shop).

### Likelihood Explanation
Any app installer can trivially capture a real webhook payload+HMAC delivered to their own endpoint (or forge a payload with a compliant JSON body while replaying an unrelated hmac pair as long as the body they resend is byte-identical to what was signed) and replay it to the public webhook endpoint with a different `shop-domain` header value. This requires no credentials beyond installing the app once, and the library provides no facility to bind shop to the HMAC — this is a structural gap, not a host-app misuse.

### Recommendation
Bind the shop identity into the verified signable data (or otherwise cryptographically tie `shop` to the payload before trusting it), e.g., by requiring/validating that the shop reported in the webhook belongs to a store from which the app has an active, previously-established session/installation, and by treating the `shop-domain` header as untrusted metadata rather than an authenticated field until it is cross-checked against known installed shops.

### Proof of Concept
1. App "Foo" is installed on `attacker.myshopify.com` and on `victim.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to Foo's endpoint for `attacker.myshopify.com`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC(client_secret, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. The attacker, who legitimately received this request as their own store's webhook delivery, replays the identical raw body `B` and header `H` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com"})` is constructed and passed to `Registry.process`.
5. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `B` against `H`.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from `victim.myshopify.com`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
