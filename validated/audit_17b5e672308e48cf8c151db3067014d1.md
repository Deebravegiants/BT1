### Title
Missing zero-address validation on order beneficiary causes permanent loss of escrowed/output funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` accepts a user-supplied `order.output.beneficiary` (and, on settlement, a `WithdrawalRequest.beneficiary`) with no validation against `address(0)`. When escrow is finally released via `_withdraw`, a native-token payout to `address(0)` silently succeeds instead of reverting, permanently destroying the funds — the same "no zero-address check → stuck/lost user funds" root cause as the original Symmetrical `depositFor` finding.

### Finding Description
`_withdraw` in `IntentsBase.sol` converts the `bytes32` beneficiary field straight into an `address` with no validation, then transfers escrowed tokens to it: [1](#0-0) 

For the native-token branch, the payout uses a raw low-level call via `_sendValue`: [2](#0-1) 

`address(0).call{value: amount}("")` returns `sent == true` (an EOA/empty account accepts value transfers), so `_sendValue(address(0), amount)` does **not** revert — unlike OpenZeppelin's `_mint`/`_transfer`, which explicitly reject `address(0)`. This means the "safety net" that made the original zero-address-mint bug at least detectable (a revert) is absent here for native token flows: the ETH is unrecoverably locked at `address(0)`.

The beneficiary value ultimately traces back to user input at order-placement time (`order.output.beneficiary`, part of the `PaymentInfo` struct), and `placeOrder` performs no zero-address check on it before it becomes part of the order commitment: [3](#0-2) 

`_validateParams`, the only input-sanitizing routine visible in the base contract, validates only gateway configuration (`host`, `dispatcher`, fee bps, `priceOracle`) — never order-level beneficiary fields: [4](#0-3) 

Because the order commitment is a hash over the entire `Order` struct (including `output.beneficiary`), an order placed with a zero beneficiary is fully valid and fillable/refundable on-chain — there is no on-chain rejection anywhere in the placement, fill, cancel, or cross-chain settlement (`RedeemEscrow`/`RefundEscrow`) paths that would catch this before funds move.

### Impact Explanation
A user who mistakenly (or a solver acting on a malformed/malicious order) leaves `beneficiary = bytes32(0)` triggers a native-token transfer to `address(0)` during escrow release (`_withdraw`), which succeeds silently rather than reverting. This is a direct, permanent loss of user-escrowed funds with no recovery path — the same class of impact ("High") as the original report: user funds become permanently stuck/unretrievable due to an unchecked zero address.

### Likelihood Explanation
Reachable by any unprivileged user calling the public `placeOrder` entry point with attacker/user-supplied order data; no special privileges are required. The bug is a straightforward missing input-validation gap that is triggered by ordinary usage (a typo/mistake or malformed integration on the `beneficiary` field), matching the "user deposited for zero address by mistake" scenario from the source report.

### Recommendation
Add explicit zero-address checks:
1. In `placeOrder` (and any order-cancellation/select paths), reject orders where `order.output.beneficiary == bytes32(0)`.
2. In `_withdraw` and `_sweepDust`, revert if the decoded `beneficiary` resolves to `address(0)` before performing `_sendValue` or `safeTransfer`.
3. Consider hardening `_sendValue` itself to reject `to == address(0)` regardless of caller, mirroring OpenZeppelin's `_mint`/`_transfer` zero-address guard, since raw `.call` transfers do not naturally provide this safety.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.output.beneficiary = bytes32(0)` and `order.output.assets` containing the native-token sentinel (`address(0)` as `TokenInfo.token`) — no revert occurs since neither `placeOrder` nor `_validateParams` checks this field.
2. A solver fills the order (same-chain) or the cross-chain settlement message is delivered and `onAccept` invokes `_withdraw` with the corresponding `WithdrawalRequest.beneficiary = bytes32(0)`.
3. Inside `_withdraw`, `beneficiary = address(uint160(uint256(0))) = address(0)`; for the native-token branch, `_sendValue(address(0), amount)` executes `address(0).call{value: amount}("")`, which returns `true`, so the function does not revert and the escrowed ETH is sent to `address(0)` — permanently lost, with `_orders[commitment][token]` already decremented so there is no residual claim.
