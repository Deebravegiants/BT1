### Title
Simplex FXFiller sizes Uniswap V4 venue-priced fills off a raw, unguarded pool spot price, allowing flash-loan price manipulation to steal solver funds - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
When a Simplex `[vault.uniswapV4]` pair has no bid/ask curves, `FXFiller` prices and sizes fills directly off the live Uniswap V4 pool's spot price (`sqrtPriceX96`), the same class of bug as the Predy `Trade.sol`/`UniHelper.getSqrtPrice()` finding (using `slot0` instead of a TWAP). The only defense is an **optional** static-reference deviation guard that is disabled by default, so an attacker can flash-loan-manipulate the pool immediately before an intent fill to make the solver deliver output tokens at a manipulated rate.

### Finding Description
`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` derives the exotic token's USD price directly from the pool's current mid: `sdkPool.token0Price` / `token1Price`, which is built from the live `sqrtPriceX96`/`tick` read via `getSlot0` in `UniswapV4LiquidityState.refresh`: [1](#0-0) 

This raw spot price feeds `FXFiller.getVenueUsdPrice` → `resolveLegRates`, which uses it, inverted, as the leg's execution rate with **no size or price-impact term** — the mid is extended linearly across the whole priced quantity: [2](#0-1) 

The only mitigation is `checkPriceGuard`, which compares the live quote against a **static** `referencePrice`/`maxDeviationBps` pair — and this is explicitly optional and unguarded when omitted: [3](#0-2) [4](#0-3) 

The project's own internal documentation confirms this is a recognized, unresolved gap: "`computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96`... there is no size or impact term... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [5](#0-4) 

This is structurally identical to the Predy M-01 report: `Trade::getSqrtPrice()` → `UniHelper::getSqrtPrice()` reads `slot0` with no TWAP and no manipulation check, letting a flash-loan attacker move the spot price to distort trade sizing. Here, an unprivileged intent placer (or any third party observing a pending fill in the mempool) can flash-loan swap against the same Uniswap V4 pool the solver is about to source/price from, pushing `sqrtPriceX96` away from fair value immediately before the solver's fill transaction lands, then reverse the swap after. If `[vault.uniswapV4]` price guard is left unconfigured for that chain/position (which the docs treat as a normal, supported configuration — "omit both to leave the chain unguarded"), the solver computes and delivers an incorrect output amount based entirely on the manipulated spot price.

### Impact Explanation
A successful attack causes the Simplex solver to either:
- Deliver more exotic/stable tokens than the fair-value trade warrants (direct theft of solver/vault funds), or
- Under-deliver to the user relative to fair value (user loss), depending on the manipulation direction, since the mid price is used with no size/impact correction and no time-weighting.

Because this directly produces a concrete, uncompensated transfer of value out of the solver's LP-backed vault (funded from real Uniswap V4 positions), this constitutes theft of funds analogous to the original Predy finding, just relocated from a lending/perp trade context to an intents-fulfillment pricing context.

### Likelihood Explanation
Likelihood is Medium: the price guard, when configured, meaningfully bounds the blast radius, and Uniswap V4 pools typically require material capital to move meaningfully within a single block/flash-loan window depending on pool depth. However, the guard is optional, off by default in example config, and per-chain (a solver could have it configured on some chains/positions and not others), and the linear, no-impact pricing formula makes even a modest price shift translate directly into filler loss without any slippage/impact safeguard. An attacker only needs a flash loan and the ability to observe a pending intent order (or generically batch-attack a set of curveless venue-priced pairs) to exploit this.

### Recommendation
- Replace or supplement the raw spot-price read (`getSlot0`) with a TWAP/observation-based price (or require a minimum trailing observation window) before using it to size fills.
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory for any curveless, venue-priced pair rather than optional, and/or add a hard-coded sanity ceiling so a chain can never be silently "unguarded".
- Add a size/impact-aware pricing function (e.g., quote via a simulated swap through the position's own liquidity/fee tier) instead of linearly extending the raw mid across the whole leg notional, mirroring the recommendation to use TWAP over spot price in the original finding.

### Proof of Concept
1. Configure a curveless, USD-stable/token0 pair funded via `[vault.uniswapV4]` with no `referencePrice`/`maxDeviationBps` set (a supported, documented configuration — "omit both to leave the chain unguarded").
2. An attacker takes a flash loan and swaps heavily against the configured Uniswap V4 position's pool, moving `sqrtPriceX96` far from fair value.
3. The attacker (or an unrelated user, since the order need not be attacker-controlled) submits or already has a pending intent order for that pair.
4. `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the manipulated pool state and returns a distorted price, which is used directly (linearly, unguarded) to size the fill.
5. The attacker reverses the pool swap and repays the flash loan, retaining the value siphoned from the solver's fill at the distorted rate.

Note: full exploitability (exact magnitude vs. pool depth, gas/flash-loan economics) would require deploying and running this against a forked mainnet Uniswap V4 pool and a live Simplex filler instance, which was not executed as part of this static analysis — the code path and missing invariant are confirmed by direct code and by the project's own internal documentation acknowledging the gap.

```typescript
	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
