This is the key vulnerability: in `lib/shopify_api/webhooks/request.rb`, the HMAC's `to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop` (tenant identity) used by `Registry.process` to dispatch the webhook to the handler comes from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely outside the HMAC-signed bytes [2](#0-1) . `Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header [3](#0-2) ; it never binds the `shop` header into the signature. `Registry#process` then trusts `request.shop` as the tenant identity and passes it straight to the handler as `WebhookMetadata` without any further cross-check [4](#0-3) .

### Title
Webhook `shop` (tenant) identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, not the `shop-domain` header, so an attacker who replays or forges a webhook payload for their own shop (a valid HMAC over a body they control) can freely alter the `shop-domain` header to any other shop domain, and `Registry.process` will hand the handler webhook data claiming to be for that other, victim shop.

### Finding Description
`HmacValidator.validate` proves only that the caller possesses a valid signature over `request.to_signable_string`, which is defined as `@raw_body` alone [1](#0-0) . The `shop` accessor used everywhere downstream as the tenant identifier is read from an HTTP header that is never included in that signable string [2](#0-1) . `Registry#process` validates the HMAC and then unconditionally trusts `request.shop` to build `WebhookMetadata`, which is delivered to the app-registered handler [4](#0-3) .

Because a merchant/attacker who owns a real (possibly free/trial) Shopify shop can trigger a legitimate webhook delivery to the app's own endpoint (i.e. obtain a valid HMAC computed by Shopify over a body of their choosing, for a real topic), they possess a body+HMAC pair that is valid under the app's `api_secret_key`. Since the `shop-domain` header carrying tenant identity is not part of the signed bytes, that same valid `(raw_body, hmac)` pair can be resubmitted to the app's webhook endpoint with the `shop-domain` header rewritten to reference a different, victim shop the attacker does not control. `HmacValidator.validate` will still accept it because it only checks the body/HMAC pair, not the header [5](#0-4) .

The broken identity binding, stated as an equality that should hold but does not:
`shop_header_used_by_handler == shop_bound_inside_HMAC_signed_bytes`
Here the left side is attacker-controlled (any header value) while the right side doesn't exist at all — the signed bytes never include a shop identifier.

### Impact Explanation
This crosses a tenant boundary: an app handler that keys any per-shop logic (state updates, entitlement changes, data lookups, cache invalidation, order/inventory sync, deletion of local records on `shop/redact` or `app/uninstalled`, etc.) off `WebhookMetadata#shop` can be made to act on a shop it has no relationship with, using data supplied by the attacker's own shop. This is a cross-tenant access vector matching the Critical bar for cross-tenant access in the rules, since a request whose credentials are only valid for tenant A can be made to affect tenant B's data/state in a host application that reasonably relies on the gem's `shop` accessor as the authenticated tenant.

### Likelihood Explanation
An attacker only needs a genuine, low-privilege Shopify development/trial store (unprivileged internet user, no special access to the target app or its secrets) to obtain a validly-signed webhook body/HMAC pair from Shopify, then replay it to the same app endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only network access to the app's public webhook endpoint, which is by definition unauthenticated aside from the HMAC.

### Recommendation
Include the `shop-domain` header (and ideally `webhook-id`/`topic`) in the HMAC-covered signable string, or otherwise cryptographically bind the `shop` value to the payload/signature (e.g., verify a nonce/shop record tied to prior webhook registration) before trusting `WebhookMetadata#shop` in `Registry#process`. Short term, document that consuming apps must not rely on the `shop-domain` header alone and should cross-reference it against the shop that actually registered/owns the webhook subscription.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and has installed the app so it can trigger a real webhook delivery (e.g., a product update) to the app's webhook endpoint. Shopify signs the body with the app's `api_secret_key`, producing `hmac`.
2. Attacker intercepts/replays this POST to the app's webhook endpoint but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, leaving `raw_body` and `X-Shopify-Hmac-Sha256` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `raw_body` [1](#0-0)  and succeeds because the body was untouched.
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [6](#0-5)  and performs whatever per-shop action it implements, believing it originated from `victim-shop`, even though `victim-shop` never sent this webhook and the payload content actually belongs to `attacker-shop`.
