### Title
`hinkalFee` is stranded in `ExternalActionSwap` when `circomData.relay == address(0)`, breaking value conservation on swap output - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
In `ExternalActionSwap.swap`, `hinkalFee` is computed from the real `swappedAmount` returned by `callRouter` and is subtracted from the amount credited to the user's UTXO via `totalFee`, but `sendToRelay` silently no-ops when `circomData.relay == address(0)`. As a result the fee amount is deducted from the user's output UTXO yet never transferred anywhere, leaving it permanently stuck in the action contract's `outputToken` balance.

### Finding Description
The equality that should hold is:
`swappedAmount == amountToSendToHinkal + amountActuallySentToRelay`

Tracing `swap()` in [1](#0-0) :
1. `swappedAmount` is the real output amount from `callRouter`.
2. `hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, circomData.feeStructure.variableRate)` is computed strictly after the swap, using the real `swappedAmount`.
3. `sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken)` (or the split-token branch) is called, but `sendToRelay` in [2](#0-1)  only performs a transfer `if (relay != address(0) && actualAmount > 0)`. When the attacker sets `circomData.relay = address(0)`, this transfer is skipped entirely — no tokens leave the contract for the relay.
4. Regardless of whether the relay transfer happened, `totalFee = hinkalFee + (feeToken==outputToken ? relayFee : 0)` is computed and `amountToSendToHinkal = swappedAmount - totalFee` is what actually gets transferred to `msg.sender` (the Hinkal core) via `transferERC20TokenOrETH` and credited into the output UTXO.

So when `relay == address(0)`: `amountToSendToHinkal = swappedAmount - totalFee`, but `0` tokens were sent to any relay. The `hinkalFee` (and `relayFee` if same token as output) portion is subtracted from the value credited to the UTXO, yet it is never transferred out of the contract to `msg.sender`, to a relay, or anywhere else. It simply remains as an ERC20 balance sitting in the `ExternalActionSwap` implementation contract, with no `nullifier`/proof commitment tracking it and no on-chain accounting referencing it going forward.

I found no `withdraw`/`rescue`/sweep function in `ExternalActionBaseV2` [3](#0-2)  or in `ExternalActionSwap.sol` that would let the owner or anyone recover this stranded balance, so the value is permanently locked in the contract rather than credited to the user, a relay, or the protocol.

None of the existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, slippage checks) prevent this: the circuit only constrains `inTotal + amountChanges === outTotal` for the UTXO commitments that are actually created; it has no visibility into `swappedAmount` (a runtime value from an external router call) nor into whether `sendToRelay` actually executed a transfer. The proof only commits to `amountToSendToHinkal` as the new UTXO's amount — the discrepancy between the router's real output and the credited UTXO amount is an off-circuit runtime bug in fee routing, not something the ZK constraints can catch.

### Impact Explanation
The `hinkalFee`-equivalent value (and possibly `relayFee` too, in the same-token branch) is permanently frozen inside the `ExternalActionSwap`/`LifiExternalAction` contract's token balance — it is not credited to the user's shielded UTXO, not paid to a relay, and not recoverable by any admin function found in the codebase. This matches the High-severity category "permanent freezing of protocol/relay fees." I was unable to verify the claim in the question that a "next caller" can harvest this stranded balance as own value — I found no code path where a subsequent `swap()` call would read or redistribute the contract's pre-existing residual token balance into its own UTXO output; each call's `amountToSendToHinkal` is derived purely from that call's own `swappedAmount`, not from `getERC20OrETHBalance`. So the "harvestable by next caller" portion of the finding is unconfirmed/likely incorrect, but the core freezing defect is confirmed.

### Likelihood Explanation
Trivial to trigger: an unprivileged user simply constructs `CircomData` with `feeStructure.variableRate > 0` and `relay = address(0)` when calling the swap action (a normal, unprivileged, self-service call), which is an explicitly supported code path (`sendToRelay` intentionally no-ops for `relay == address(0)`). Every such call permanently strands `hinkalFee` (and `relayFee` for matching fee/output tokens). This is fully repeatable per-transaction and requires no special preconditions beyond a nonzero `variableRate` fee structure.

### Recommendation
When `circomData.relay == address(0)`, either (a) skip charging `hinkalFee`/`relayFee` entirely and set `totalFee = 0` so the full `swappedAmount` is credited to the user's UTXO, or (b) redirect the fee to a fixed protocol treasury/fee-collector address instead of `circomData.relay`, ensuring `sendToRelay`'s no-op path can never cause fee funds to be both deducted from the UTXO and left untransferred. Add an invariant check `require(swappedAmount == amountToSendToHinkal + amountSentToRelay)` before finalizing the UTXO.

### Proof of Concept
Hardhat test:
1. Deploy `ExternalActionSwap` (or its concrete subclass, e.g. `LifiExternalAction`) with a mock router that returns a known `swappedAmount` for a given `inputAmount`.
2. Craft `circomData` with `feeStructure.variableRate > 0`, `feeStructure.feeToken == outputToken`, and `relay = address(0)`.
3. Call `swap()` (via `runAction` from an allowed recipient).
4. Assert `swappedAmount - amountToSendToHinkal == totalFee > 0` (read from emitted UTXO amount vs. mocked router return value).
5. Assert the action contract's `outputToken.balanceOf(actionContract) == totalFee` after the call (no relay ever received it, no extra amount went to `msg.sender`).
6. (Optional, unverified) Attempt a second `swap()` or a direct token-balance check to see if this residual is ever swept elsewhere in this contract — based on code inspection, it stays stuck indefinitely with no sweep path found in the codebase.

        require(

            "ExternalActionBase: sender not allowed"
        );
        _;

    constructor(address[] memory _allowedRecipients) {
        for (uint i = 0; i < _allowedRecipients.length; i++) {
            isAllowedRecipient[_allowedRecipients[i]] = true;
        }

    function setAllowedRecipients(
        address[] calldata recipients
    ) external onlyOwner {
        for (uint i = 0; i < recipients.length; i++) {
            require(recipients[i] != address(0), "zero address!");
            isAllowedRecipient[recipients[i]] = true;
        }
    }
