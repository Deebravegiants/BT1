### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate`, but the `shop`, `topic`, `api_version`, and `webhook_id` values — all taken directly from unauthenticated HTTP headers — are never included in the signed material and are handed to the application's webhook handler unverified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single client secret, shared across every merchant/shop that has installed the app — it is not shop-specific: [4](#0-3) 

This breaks the intended identity binding: `hmac(raw_body, app_secret) == valid` is treated as proof that `shop-domain header == the shop that generated raw_body`, but the header is never part of the signed content, so that equality does not actually hold.

### Impact Explanation
Because the api_secret_key is shared across all shops that install the same app, any shop that installs the app (including one controlled by an attacker) can legitimately receive Shopify-signed webhooks with a valid HMAC over some `raw_body`. An attacker can capture such a legitimately-signed `(raw_body, hmac)` pair from their own shop's installation and replay it to the same app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop (and/or a forged `x-shopify-topic`/`x-shopify-webhook-id`). Since `Registry.process` never checks that the header-derived `shop`/`topic` are consistent with the HMAC-covered body, the forged request passes validation and the handler executes with `WebhookMetadata.shop` set to the victim shop. Any host application logic that keys tenant-scoped actions (e.g., uninstall handling, subscription/billing state, data deletion, session invalidation) off `data.shop` from the SDK is misled into acting on the wrong tenant — a cross-tenant confusion condition rooted in this gem's own validation logic, not merely a host misuse.

### Likelihood Explanation
Exploitation requires the attacker to install the target app on at least one shop they control (a normal, unprivileged action available to any Shopify merchant/developer for public apps) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint — both are low-privilege, internet-reachable capabilities. No access token, `api_secret_key`, or the victim's credentials are required.

### Recommendation
Bind the identity fields to the signed payload: include `shop`, `topic`, `api_version`, and `webhook_id` in the value passed to `to_signable_string` (mirroring what `AuthQuery#to_signable_string` already does for OAuth), or otherwise validate that the header-derived `shop`/`topic` match values embedded in and covered by the signed body before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, so the app's shared `api_secret_key` is now usable by the attacker to obtain validly-signed webhook deliveries for their own shop.
2. Shopify delivers a real webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host app to perform uninstall/tenant-scoped cleanup for a shop that never actually uninstalled the app.
