## Front-runnable pool-address squatting permanently blocks bonding-curve graduation and freezes FA custody - (File: aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move)

### Summary
The bonding-curve `graduate()` flow (triggered automatically inside `swap_apt_to_fa` once the APT reserve threshold is crossed) unconditionally calls the permissionless `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)` to create a brand-new DEX pool at a deterministic address, then immediately seeds it via `add_liquidity_coin_entry_transfer_ref` with `amount_1_min = 0, amount_2_min = 0` — the same "no slippage floor" pattern flagged in the external report, but taken to zero instead of `1`. Because `router::create_pool_coin` / `liquidity_pool::create` is a public entry function open to anyone and unconditionally does `move_to` at a deterministic, precomputable address without checking for prior existence, any unprivileged attacker can pre-create that exact pool ahead of time. When graduation later fires, `liquidity_pool::create`'s `move_to` collides with the pre-existing resource and aborts, which aborts the entire enclosing `swap_apt_to_fa` transaction — permanently preventing that FA from ever graduating.

### Finding Description
`graduate()` is only reachable through `swap_apt_to_fa`, and it is the *only* code path that flips `liquidity_pair.is_frozen = false` [1](#0-0) , which the module's own comment states is what unlocks the custom `withdraw` for holders ("From here, participants are free to use their FA as they'd like, because the custom `withdraw` function is no longer frozen for `transfer`") [2](#0-1) .

`graduate()` calls `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)` unconditionally, with no existence check, and immediately follows with a liquidity seeding call that has zero slippage protection: [3](#0-2) 

`router::create_pool_coin` / `liquidity_pool::create` is a fully public, permissionless entry point [4](#0-3) . `liquidity_pool::create` derives the pool's object address deterministically from the sorted token pair and stability flag (`liquidity_pool_address` = `object::create_object_address(&@swap, get_pool_seeds(...))`) and unconditionally does `move_to` of `LiquidityPool`/`FeesAccounting` resources at that address with no prior-existence guard: [5](#0-4) 

Because the pool address is fully predictable from `(coin_wrapper::get_wrapper<AptosCoin>(), fa_object_metadata, false)`, any external, unprivileged account can call `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)` (or `swap::liquidity_pool::create`) for any bonding-curve FA at any time — well before the bonding curve's APT reserves reach `APT_LIQUIDITY_THRESHOLD`. Once that pool object exists, the *second* creation attempt inside `graduate()` will hit `move_to` on an address that already holds `LiquidityPool`, which the Move VM aborts (resource already exists at address). Since this call happens synchronously inside `swap_apt_to_fa`, the abort propagates and reverts the entire swap transaction, including the state flip that would have cleared `is_frozen`.

Because `graduate()` is the *only* code path capable of clearing `is_frozen`, and it will now deterministically abort every single time the threshold is crossed, the FA becomes permanently stuck in its frozen/bonding-curve-only state — a durable custody lock affecting every holder of that fungible asset, imposed by a completely unprivileged third party who never even needs to hold the FA itself.

### Impact Explanation
This breaks the custody invariant that ownership/transfer authority over the FA's fungible store (the frozen/custom-withdraw gate) must remain under legitimate protocol control and must eventually be releasable to holders as designed. An unprivileged attacker can permanently and irrevocably lock every holder's FA inside the bonding-curve-only transfer regime, with no admin recovery path shown in this module (there is no re-attempt/alternate-pool-address logic, and `is_frozen` can only be cleared inside the now-permanently-failing `graduate()`). This is a "permanent lock or non-recoverable loss of object-held ... value" as defined by the custody impact gate, and it is triggerable by anyone at zero cost relative to the value locked (a single `create_pool_coin` call), for any/all bonding-curve tokens deployed through this module.

### Likelihood Explanation
High likelihood: `router::create_pool_coin` is public, requires no special permission, and the target pool address is fully computable off-chain from public token metadata before the bonding curve ever approaches its graduation threshold. An attacker only needs to submit one cheap transaction per FA they want to permanently sabotage, and can do so proactively for many/most actively-trading bonding-curve tokens.

### Recommendation
- In `graduate()`, check whether the pool already exists (e.g., via `liquidity_pool::liquidity_pool_address_safe`) before calling `router::create_pool_coin`, and if it already exists, treat that as the target pool instead of attempting to recreate it.
- Alternatively/also, make pool creation for the graduation flow use a protocol-controlled/friend-gated function rather than the fully public `router::create_pool_coin`, so third parties cannot pre-empt the deterministic address.
- Separately (independent of this specific bug), replace `amount_1_min = 0, amount_2_min = 0` in `add_liquidity_coin_entry_transfer_ref`'s call inside `graduate()` with real slippage bounds derived from expected/desired amounts, consistent with the external report's original recommendation, since an attacker who does become the first LP of a pre-existing pool controls the price at which the graduation deposit is valued.

### Proof of Concept
1. Observe a bonding-curve FA (`name`, `symbol`) approaching `APT_LIQUIDITY_THRESHOLD` in `liquidity_pairs::LiquidityPair`.
2. Before it crosses the threshold, call the public entry function `router::create_pool_coin<AptosCoin>(fa_object_metadata, /*is_stable=*/false)` (any account, no FA holdings required) — this creates a `LiquidityPool` object at the deterministic address `liquidity_pool::liquidity_pool_address(coin_wrapper::get_wrapper<AptosCoin>(), fa_object_metadata, false)`.
3. Wait for/trigger a swap that pushes `apt_updated_reserves` above `APT_LIQUIDITY_THRESHOLD`, invoking `swap_apt_to_fa` → `graduate()`.
4. Inside `graduate()`, `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)` is called again and tries `move_to` on the same deterministic address, which now already has `LiquidityPool`/`FeesAccounting` resources from step 2 — the Move runtime aborts with a resource-already-exists error, aborting the whole `swap_apt_to_fa` transaction.
5. `liquidity_pair.is_frozen` is never cleared (still `true`), and every future crossing of the threshold repeats the same abort, so the FA can never graduate and remains permanently frozen for all holders.

Note: I was not able to fully inspect `bonding_curve_launchpad.move` (the friend module that registers this FA's custom `withdraw`/dispatch hooks and interprets `is_frozen`) or the internal `create_lp_token`/`get_pool_seeds` implementation within the tool-call budget available, so the exact mechanics of how `is_frozen` gates transfers, and full confirmation that `create_lp_token`'s object address exactly matches `liquidity_pool_address`'s deterministic derivation, should be verified directly in those files before remediation.

    /// Creates a new liquidity pool.
    public fun create(
        token_1: Object<Metadata>,
        token_2: Object<Metadata>,
        is_stable: bool,
    ): Object<LiquidityPool> acquires LiquidityPoolConfigs {
        if (!is_sorted(token_1, token_2)) {
            return create(token_2, token_1, is_stable)
        };
        let configs = unchecked_mut_liquidity_pool_configs();

        // The liquidity pool will serve 3 separate roles:
        // 1. Represent the liquidity pool that LPs and users interact with to add/remove liquidity and swap tokens.
        // 2. Represent the metadata of the LP token.
        // 3. Store the min liquidity that will be locked into the pool when initial liquidity is added.
        let pool_constructor_ref = create_lp_token(token_1, token_2, is_stable);
        let pool_signer = &object::generate_signer(pool_constructor_ref);
        let lp_token = object::object_from_constructor_ref<Metadata>(pool_constructor_ref);
        fungible_asset::create_store(pool_constructor_ref, lp_token);
        move_to(pool_signer, LiquidityPool {
            token_store_1: create_token_store(pool_signer, token_1),
            token_store_2: create_token_store(pool_signer, token_2),
            fees_store_1: create_token_store(pool_signer, token_1),
            fees_store_2: create_token_store(pool_signer, token_2),
            lp_token_refs: create_lp_token_refs(pool_constructor_ref),
            swap_fee_bps: if (is_stable) { configs.stable_fee_bps } else { configs.volatile_fee_bps },
            is_stable,
        });
        move_to(pool_signer, FeesAccounting {
            total_fees_1: 0,
            total_fees_2: 0,
            total_fees_at_last_claim_1: smart_table::new(),
            total_fees_at_last_claim_2: smart_table::new(),
            claimable_1: smart_table::new(),
            claimable_2: smart_table::new(),
        });
        let pool = object::convert(lp_token);
        smart_vector::push_back(&mut configs.all_pools, pool);

        event::emit(CreatePool { pool, token_1, token_2, is_stable });
        pool
    }
