Confirmed. The `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` only checks `verifiable_query.to_signable_string` against the HMAC, and for webhooks that signable string is exclusively the raw HTTP body [1](#0-0) , while `shop`, `topic`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers [2](#0-1)  and passed through to the handler untouched [3](#0-2) .

### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying that the HMAC-SHA256 signature matches the raw request body [4](#0-3) . The `shop` field that is subsequently handed to the app's handler as the tenant identifier for the event is read from the `X-Shopify-Shop-Domain` HTTP header, a value that is never part of the signed bytes [5](#0-4) [1](#0-0) . This breaks the intended identity binding: `shop authenticated by HMAC` ≠ `shop used to key/attribute the event`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes the HMAC over exactly that signable string with the app's `api_secret_key` [6](#0-5) . None of the headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed data — they are parsed independently from `@headers` [7](#0-6) .

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` (the header value) without any additional check that it matches the tenant whose body/HMAC pair was actually verified: [3](#0-2) .

Because the `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app receives legitimate, correctly-signed webhooks for their own shop. Such a merchant (an unprivileged internet user relative to other tenants of the same app) can capture one of these real `(body, X-Shopify-Hmac-Sha256)` pairs and replay it to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value naming a victim shop. `HmacValidator.validate` still succeeds because it only checks the untouched body against the untouched HMAC, and `request.shop` now returns the attacker-chosen victim domain, which flows straight into the handler as the authenticated tenant for the event.

### Impact Explanation
This is a cross-tenant boundary violation: an app using this gem's documented webhook-processing API to key tenant data by `WebhookMetadata#shop` can be made to attribute or act on webhook data under the wrong shop's identity, since `shop` is treated as authenticated (it survived `HmacValidator.validate`) when it is not. Depending on the handler's logic (e.g., processing `app/uninstalled`, `shop/update`, `customers/redact`, or order/customer data keyed by shop), this can lead to cross-tenant data corruption or disclosure driven entirely by attacker-controlled, unauthenticated header bytes.

### Likelihood Explanation
Any developer who has installed the app on their own shop obtains real, validly-signed webhook bodies for arbitrary topics they can trigger (e.g. by editing a product, updating shop settings) at will, then only needs to change one HTTP header when replaying the request to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or any other credential is required — only the ability to send an HTTP request, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification, or otherwise refuse to trust `request.shop` as an authenticated tenant identifier. Concretely, `HmacValidator`/`VerifiableQuery.to_signable_string` for webhook `Request` objects should incorporate the shop-domain header (and other identifying headers) into the string that is HMAC-verified, so a valid signature can only be produced by Shopify for the exact `(shop, body)` pair it actually sent, not for a `body` replayed with an attacker-substituted `shop-domain` header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, and it is granted the `orders/create` webhook.
2. Attacker triggers an order creation, capturing the legitimate webhook HTTP request: headers include `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and a JSON body.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) and succeeds [4](#0-3) .
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's order JSON>, ...)` [8](#0-7)  and processes attacker-controlled order data as if it belonged to `victim.myshopify.com`.
