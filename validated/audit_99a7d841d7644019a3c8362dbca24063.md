### Title
Webhook tenant identity (`shop`) is taken from an unauthenticated header, not bound to the HMAC signature, enabling cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies nothing except the raw body bytes. The `shop` value used as the tenant/session key that is handed to every app's webhook handler comes straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is completely outside the HMAC-covered bytes. This breaks the identity binding `shop_authenticated_by_hmac == shop_used_as_tenant_key`.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the signature purely over `verifiable_query.to_signable_string`: [2](#0-1) 

`Request#shop` is read from the `shop-domain` header, which is never part of `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC (of the body only) and then forwards `request.shop` — the unauthenticated header value — directly into `WebhookMetadata`, which the host app's handler uses as the tenant key to look up/act on shop-specific data: [4](#0-3) 

The documented handler contract explicitly treats `data.shop` as the trustworthy tenant identifier for looking up shop-specific session/data: [5](#0-4) 

Since the HMAC only binds the body, any actor who can obtain one legitimate `(raw_body, hmac)` pair for a topic they control (e.g. by installing the app on their own store and triggering a webhook event for a topic like `orders/create`, `products/update`, etc., where they control much of the body content) can replay that exact body + signature to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g. a victim shop). `Utils::HmacValidator.validate` will still pass because the signature check never inspects the header, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain and `body` containing attacker-influenced content, which the app will process as if it legitimately originated from the victim's store.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the gem provides no mechanism to bind the `shop-domain` header to the cryptographic signature, so a host application that follows the gem's own documented handler contract (using `data.shop` from `WebhookMetadata` as the tenant key) can be made to attribute attacker-controlled webhook data to an arbitrary victim shop. Depending on how the host processes topics such as `orders/create`, `customers/update`, `app/uninstalled`, etc., this can corrupt or poison another tenant's stored data, trigger unauthorized side effects scoped to the victim tenant, or facilitate further cross-tenant actions — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Exploitation requires no credentials belonging to the app or the victim shop. An unprivileged internet user can install the target app on their own (free/dev) Shopify store, capture one legitimate, correctly-signed webhook delivery for a topic whose body they can influence, and replay it to the app's known/public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or privileged account is needed — only a normal HTTP client and control of a single, unprivileged shop.

### Recommendation
Include the tenant-identifying fields (at minimum the shop domain, and ideally the webhook id/topic) inside the HMAC-signed payload derivation, or otherwise cryptographically bind the `shop-domain` header value into `Request#to_signable_string` / a header-aware verification step in `Utils::HmacValidator`, so that the verified signature actually attests to the shop the webhook claims to be from before that value is trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic they can influence content of (e.g. `products/update`).
2. Attacker triggers the event in their own store and captures the raw POST Shopify sends to the app's webhook URL, including `x-shopify-hmac-sha256: <valid_hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, plus the raw JSON body.
3. Attacker resends the exact same request to the app's public webhook endpoint, but changes only the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (leaving body and HMAC header untouched).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the untouched HMAC.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, and any host logic keyed on `data.shop` now processes attacker data under the victim's tenant identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
