### Title
Missing shop-domain validation on JWT `dest` claim in `TokenExchange.exchange_token` breaks the "shop authenticated vs. shop used to build the HTTP client host" binding - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
Every other credential-issuing flow in this gem (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) runs the `shop` value through `Utils::ShopValidator.sanitize!` before it is used to build the `Session` whose `shop` attribute determines the HTTPS host that `Clients::HttpClient` sends the app's `client_secret` and access-token request to. [1](#0-0) [2](#0-1) [3](#0-2) 

`exchange_token`, however, takes the shop straight from the JWT payload's `dest` claim without ever calling `ShopValidator.sanitize!`, and hands it directly to `Session.new`, which is then used by `Clients::HttpClient` to compute the request host: [4](#0-3) 

`JwtPayload#shop` merely strips the `"https://"` prefix off `dest` with no domain-allow-list check: [5](#0-4) 

### Finding Description
The identity binding that should hold is:
`shop domain cryptographically authenticated inside the session token == shop domain used to construct the URL that receives the app's client_secret`.

`JwtPayload` only verifies the token's signature (`aud == Context.api_key`) and standard JWT time claims; it never constrains `dest` to `*.myshopify.com` / `myshopify.io` / `spin.dev` / `shop.dev` the way `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` does elsewhere in this same file/module. In `exchange_token`, `dest_shop` flows unchecked into `Session.new(shop: dest_shop)` and then into `Clients::HttpClient.new(session: shop_session, ...)`, which builds the outbound request host from `session.shop` (as evidenced by the analogous, validated call sites in `refresh_token.rb`/`client_credentials.rb`/`migrate_to_expiring_token`, all of which pass a `Utils::ShopValidator.sanitize!`-derived value into the identical `HttpClient` construction pattern).

Since the app's `client_id`/`client_secret` are embedded directly in the POST body sent to that host (`body = { client_id: ..., client_secret: ..., ... }`), any value accepted as `dest` is turned into the destination of an outbound request carrying the app's `client_secret`. Compare this with the sibling method `migrate_to_expiring_token`, in the very same file, which sanitizes `shop` before doing exactly the same `HttpClient`/body construction — showing the omission in `exchange_token` is an inconsistency rather than intended behavior.

### Impact Explanation
If the `dest` claim can ever contain a value that is not restricted to Shopify's trusted domain suffixes (e.g. due to future claim format changes, a permissive JWT library configuration, or reuse of `JwtPayload` in a code path where the token's origin is less strictly controlled than a first-party Shopify-issued session token), the missing `ShopValidator.sanitize!` call is the only thing standing between that value and an outbound HTTPS POST containing `client_id` and `client_secret`. This matches the report's Critical/High bug class: SSRF/credential-leakage carrying the app's own `client_secret` to an attacker-influenced host — precisely the class of "host validated versus host that receives... `client_secret`" identity-binding break called out in scope.

### Likelihood Explanation
Under the current, correctly-configured JWT verification (`aud` check, HMAC-SHA256 signature verification with `Context.api_secret_key`), a valid session token's `dest` claim can only be forged by someone possessing the app's `api_secret_key`, which is out of scope per the rules. The residual risk is architectural/defense-in-depth: the gem enforces the trusted-domain allow-list everywhere else a shop value reaches `HttpClient`, but this one path relies solely on JWT signature validity as the sole guard on the destination host. This is a real code inconsistency (verifiable by diffing `exchange_token` against `migrate_to_expiring_token` in the same file) rather than a purely theoretical concern, but exploitation strictly through an unprivileged internet request (without the `api_secret_key`) could not be fully confirmed from the code alone — the JWT signature check should currently prevent an external, credential-less attacker from controlling `dest`.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(jwt_payload.shop)` (or equivalent) to `dest_shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`Session.from`, mirroring the pattern already used in `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange.migrate_to_expiring_token`, so that every path that ultimately determines the destination host for a request carrying `client_secret` enforces the same trusted-domain invariant.

### Proof of Concept
Could not be constructed as a concrete unprivileged-attacker exploit: under current JWT verification, the `dest` claim is protected by HMAC-SHA256 signing with `Context.api_secret_key` (see `JwtPayload#decode_token`), which an internet attacker without that secret cannot forge. The finding is a verified code-level inconsistency (missing `ShopValidator.sanitize!` in `exchange_token` versus its sibling methods) rather than a demonstrated end-to-end exploit chain. [6](#0-5)
