Audit Report

## Title
Stale `TemporarySlots` entry allows lease seizure by an unrelated para manager after deregister/register of the same `ParaId` - (File: `polkadot/runtime/common/src/assigned_slots/mod.rs`)

## Summary
`assign_temp_parachain_slot` with `SlotLeasePeriodStart::Next` writes a `TemporarySlots` entry that materializes into an actual lease only later, in `allocate_temporary_slot_leases`, and this later step uses the manager captured at assignment time rather than re-validating current `ParaId` ownership. Because `paras_registrar` has no coupling to `assigned_slots` (confirmed by its import list), `deregister`/`register` do not purge or update `TemporarySlots`, so a deferred lease can materialize against a `ParaId` whose manager has since changed via an ordinary deregister/register cycle.

## Finding Description
The `Next` branch of `assign_temp_parachain_slot` inserts into `TemporarySlots::<T>` without creating a lease immediately, deferring lease creation to a later block [1](#0-0) . The deferred lease is created by `allocate_temporary_slot_leases`, which iterates `TemporarySlots::<T>` and calls `configure_slot_lease` using `temp_slot.manager` captured at assignment time, with no re-check against the para's current registrar manager [2](#0-1) . `configure_slot_lease` forwards directly to `T::Leaser::lease_out(para, &manager, ...)`, which acts on the `ParaId` itself [3](#0-2) . The only extrinsic that removes `TemporarySlots`/`PermanentSlots` entries is `unassign_parachain_slot`, gated by `AssignSlotOrigin`, and is not called by `paras_registrar` [4](#0-3) . The import list of `paras_registrar/mod.rs` confirms it has no dependency on `assigned_slots`, so its `deregister`/`register` extrinsics cannot and do not invalidate any `assigned_slots` storage [5](#0-4) .

I was not able to fully inspect the `deregister`/`register` function bodies in `paras_registrar/mod.rs` within the available tool budget (file read calls failed due to a parameter error on the final iteration), so I cannot independently confirm from source whether `deregister` enforces additional lifecycle guards (e.g., disallowing deregistration while any pending governance action targets the para) that might prevent this race in practice. Based on the cited code for `assigned_slots` and the confirmed lack of any cross-pallet coupling, the core mechanism described — a deferred `TemporarySlots` entry that is not invalidated by `paras_registrar` and materializes later using stale manager information — is real and matches the citations provided in the claim.

## Impact Explanation
If the exploit path is reachable (i.e., if `paras_registrar::deregister` does not independently block deregistration of a para with a pending `assigned_slots` assignment), an unrelated, unprivileged account that later registers a freed `ParaId` could passively receive a lease-holding-parachain upgrade that was approved by `AssignSlotOrigin` for a different party. This would be a governance-bypass state-transition affecting coretime/parachain-slot allocation, which is a legitimate in-scope impact class if triggerable.

## Likelihood Explanation
The claim's likelihood hinges entirely on whether `paras_registrar::deregister` performs any lifecycle check that would block deregistration while a temp-slot assignment is pending, and whether `ParaId` reuse after deregistration is actually permitted by the registrar (some registrars enforce reservation/ID-issuance rules that could prevent an "unrelated" party from acquiring the exact same freed `ParaId`). Without confirming the `deregister`/`register` implementation details, this cannot be fully validated as reproducible; the described sequence is plausible from the `assigned_slots` side alone but the report does not demonstrate (via an actual executed test) that `deregister` succeeds while a `TemporarySlots` entry with `last_lease: None` is outstanding, nor that ID reuse is unguarded.

## Recommendation
Add a hook so that `paras_registrar::deregister` purges or invalidates any `assigned_slots::TemporarySlots`/`PermanentSlots` entry for the deregistered `ParaId` (e.g., a `Config::OnParaDeregistered` callback implemented by `assigned_slots`), or have `allocate_temporary_slot_leases`/`configure_slot_lease` re-validate that `T::Registrar::manager_of(id)` still equals `temp_slot.manager` immediately before calling `Leaser::lease_out`, skipping/dropping desynced entries with an emitted event.

## Proof of Concept
As described in the report: assign a `Next`-period temp slot to a para controlled by manager A via `AssignedSlots::assign_temp_parachain_slot`, have A deregister the para via `paras_registrar::deregister`, have unrelated manager B register the same `ParaId`, advance to the lease period boundary to trigger `allocate_temporary_slot_leases`, and check whether the para (now controlled by B) becomes a lease-holding parachain. This test would need to be executed against the actual `paras_registrar::deregister`/`register` implementations to confirm the deregistration step is not otherwise blocked and that `ParaId` reuse succeeds as described — this execution was not verified in this review.
