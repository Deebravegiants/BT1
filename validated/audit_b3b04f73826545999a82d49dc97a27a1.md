### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but `Utils::HmacValidator` only verifies the raw request **body**. Because the signature never covers the `shop` header, any actor who already possesses one valid `(body, hmac)` pair for their own shop can attach that same valid HMAC to a request with a different `shop` header value, and the gem will treat the forged tenant identity as authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` is read directly from an unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` only checks this body HMAC before forwarding the (unauthenticated) `request.shop` straight to the application's webhook handler as the tenant identifier: [4](#0-3) 

The broken identity binding is:
`shop header value used by handler.handle(shop:)` ≠ `shop value covered by the verified HMAC (none)`.

Since the `hmac-sha256` header authenticates only the byte content of the body, and the `shop-domain` header travels outside the signed envelope, the gem cannot distinguish "this body was signed for shop A" from "this body plus arbitrary shop header." A holder of one legitimate webhook delivery for their own store (attacker owns/operates Shop A, and Shopify legitimately signs and delivers a webhook to them, e.g. via a public app that is also installed by the attacker) can capture that `(raw_body, hmac)` pair and replay it against the same endpoint while substituting a different `shop-domain` header value belonging to a victim tenant (Shop B). `HmacValidator.validate` will still pass because it only re-hashes the untouched raw body, and `Registry.process` will hand the handler `shop: "shop-b.myshopify.com"` with attacker-controlled body content.

### Impact Explanation
This breaks the tenant/authentication boundary between merchants: an unprivileged actor (any merchant who has the app installed on their own store, i.e., no `api_secret_key`, access token, or other elevated credential needed) can inject webhook events that the host application will process as if they originated from a different, victim shop. Depending on how the host app's webhook handler uses `shop` (order/customer syncing, provisioning, uninstall/GDPR handling, billing state changes), this is a cross-tenant data-integrity/confidentiality issue satisfying the "cross-tenant access" Critical-impact category defined for this scan.

### Likelihood Explanation
Exploitation requires only (1) the attacker's own legitimately-installed instance of the app so they can capture one valid `(raw_body, hmac)` pair delivered to their own shop, and (2) the ability to replay an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — no secrets, tokens, or privileged access are required. This is a `lib/shopify_api/webhooks/**` code-path issue, not a host-application misuse, since the verification logic itself never covers the `shop` field.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook-id`) in the data that is HMAC-verified, or otherwise cryptographically bind the header values to the signed payload before they are trusted. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should compute the signature over a canonical string containing `shop`, `topic`, and the body, matching Shopify's authenticated envelope, so a valid HMAC for one shop/body pair cannot be replayed with a substituted `shop` header.

### Proof of Concept
1. Attacker installs the target public app on their own development shop `attacker.myshopify.com`.
2. Shopify legitimately delivers a webhook (e.g. `orders/create`) to the app's endpoint, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>` and body `B`.
3. Attacker intercepts and replays this exact request to the same endpoint, only changing the header to `x-shopify-shop-domain: victim.myshopify.com` (raw body `B` and HMAC value are left untouched).
4. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` (`B`) only — [3](#0-2)  — the signature still matches.
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...))` — [5](#0-4)  — the host application processes attacker-supplied data as if it belonged to `victim.myshopify.com`.
