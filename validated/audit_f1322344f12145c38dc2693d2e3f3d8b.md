## Analog Found

### Title
Solver Payout Burned With No Refund When the Cross-Chain `RedeemEscrow` Settlement Message Cannot Be Delivered - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
In `IntentGatewayV2`'s cross-chain fill path, a solver pays out real value to the order beneficiary on the destination chain synchronously and atomically, and only *afterwards* dispatches a `RedeemEscrow` message that must be validated and processed on the source chain to release the matching escrow back to the solver. If that validation fails (e.g. the settlement message doesn't match a live escrow entry), the source-side `onAccept` reverts and the solver's payment is never refunded — mirroring the tgUSD/stgUSD pattern where an irreversible action (burn) is committed before a downstream validation step that can permanently fail without a refund path.

### Finding Description
`_fillCrossChain` immediately transfers real output tokens to `beneficiary` [1](#0-0) , then dispatches a `RedeemEscrow` post request to the order's source chain to claim the matching escrowed inputs for the solver [2](#0-1) .

On the source chain, `onAccept` authenticates the message and calls `_withdraw` for `RedeemEscrow`/`RefundEscrow` kinds [3](#0-2) . `_withdraw` reverts with `UnknownOrder()` if the referenced `(commitment, token)` has no live escrow balance [4](#0-3) . This happens whenever the message body doesn't correspond exactly to an order still escrowed on the source (already settled/refunded commitment, any mismatch between the fill-side order encoding and what was actually placed/escrowed on the source, or an order the solver reconstructed incorrectly).

Unlike `HyperFungibleToken`'s design, where a failed/undelivered message can always be recovered via `onPostRequestTimeout` which re-mints the burned amount back to the sender [5](#0-4) , the Intent Gateway's own project documentation explicitly notes that it dispatches escrow-settlement messages with no timeout and does not implement timeout handling, relying on `HyperApp`'s default (revert) behavior: "Timeouts mint a refund to the original sender, so a forged timeout proof mints. The intent gateway does not gate its timeout callbacks because `HyperApp`'s defaults revert and it dispatches with no timeout." [6](#0-5) 

Because there is no timeout, a `RedeemEscrow` message that fails validation on the source chain can never trigger a refund flow to the solver — it either stays permanently undeliverable (retried forever by relayers, always reverting) or is simply never redeemed. The only recovery mechanism present for the contract is `SweepDust`, which is scoped to protocol fee dust accumulated from surplus, not to a specific solver's unredeemed settlement amount [7](#0-6) . There is no admin operation to force-credit a specific solver for a failed `RedeemEscrow` claim, analogous to the tgUSD-engine's lack of a `refundByMint()` fallback.

### Impact Explanation
The solver has already delivered real, irreversible value to the beneficiary on the destination chain within the same atomic transaction as the `RedeemEscrow` dispatch. If the settlement message subsequently fails validation on the source chain (mismatched/invalid order encoding, stale/already-settled commitment, or any other condition that makes `_orders[commitment][token] == 0`), the solver's payout is unrecoverable: no timeout exists to trigger a refund, and there is no privileged operation capable of crediting the solver for the specific unredeemed amount without arbitrarily minting/transferring protocol funds. This is a permanent loss of solver funds — a concrete instance of "permanent freezing/loss of funds" comparable to the tgUSD/stgUSD burn-without-refund bug class.

### Likelihood Explanation
Likelihood is moderate: a solver (an unprivileged intent filler) reachable via the standard `fillOrder`/`fillOrder`-equivalent path can trigger this simply by supplying an `Order` struct or fill data that doesn't exactly match what is escrowed on the source chain (e.g., stale order snapshot, off-by-one field mismatch producing a different `keccak256` commitment, or racing a cancellation/refund that consumes the escrow before the `RedeemEscrow` message lands). Because commitments are exact ABI-encoded hashes of the full order, any accidental divergence between the solver's reconstructed order and the canonical order stored on the source chain silently causes this failure mode, and it requires no malicious admin, governance, or privileged actor — only a single fill transaction from an ordinary solver.

### Recommendation
Adopt the same mitigation pattern used by `HyperFungibleToken`/`WrappedHyperFungibleToken`: dispatch the `RedeemEscrow` (and `RefundEscrow`) settlement messages with a real timeout, and implement `onPostRequestTimeout` on the `IntentGatewayV2`/`ExtrinsicIntents` contracts to refund the solver (or otherwise make them whole) if the settlement message cannot be delivered before expiry. Alternatively, track failed/unredeemable `RedeemEscrow` claims in a dedicated per-solver ledger (similar to the tgUSD report's Recommendation 2) and expose a permissionless or admin-gated claim function so solvers are not permanently penalized for message-delivery or order-formatting failures outside their control.

### Proof of Concept
1. User places a cross-chain order on chain A, escrowing input tokens under commitment `C = keccak256(abi.encode(order))`.
2. A solver observes the order (e.g., via an off-chain indexer) but reconstructs the `Order` struct with any field divergence from the canonical placed order (or acts on a stale snapshot where the order was already cancelled/refunded/filled on chain A).
3. The solver calls `fillOrder` on chain B (`_fillCrossChain`), which immediately transfers real output tokens to `beneficiary` [1](#0-0)  and dispatches a `RedeemEscrow` message with the solver's (mismatched) commitment `C'` and no timeout.
4. On chain A, `onAccept` → `_withdraw` looks up `_orders[C'][token]`, finds it `== 0`, and reverts with `UnknownOrder()` [8](#0-7) .
5. Because the message was dispatched without a timeout, there is no `onPostRequestTimeout` refund path available for the solver; the message can only be retried indefinitely by relayers, always reverting, and the solver's payment made in step 3 is permanently lost with no recovery mechanism beyond an unrelated `SweepDust` operation scoped to protocol fees.
