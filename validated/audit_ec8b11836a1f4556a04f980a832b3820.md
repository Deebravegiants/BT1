## Analysis: Unbounded loop DoS in GRANDPA ancestry verification

The MySQL CVE describes an availability-only, network-reachable bug: crafted input causes the server to hang or crash. The closest reachable analog in Hyperbridge is an **unbounded loop in `AncestryChain::ancestry`** in the GRANDPA consensus verifier, reachable by any relayer submitting a `Message::Consensus` update — and, critically, triggered *before* any signature verification occurs.

### Title
Unbounded ancestry-walk loop in GRANDPA finality verification allows an unauthenticated consensus update to hang the runtime - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks parent-hash pointers taken directly from attacker-supplied `unknown_headers` with no depth bound and no cycle detection. `verify_grandpa_finality_proof` invokes this walk **twice before verifying the justification's signatures**, so a relayer can submit a crafted `Message::Consensus` whose `unknown_headers` contain a self-referencing or cyclic parent-hash chain and hang block execution indefinitely, without needing any valid GRANDPA authority signature.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

The loop terminates only when `current_hash == base` or when a hash is missing from the map; there is no bound on iteration count and no cycle check. If the untrusted header set contains two (or more) headers whose `parent_hash` fields reference each other (e.g. `H1.parent_hash == H2.hash()` and `H2.parent_hash == H1.hash()`), the loop never reaches `base` and never hits a missing hash — it spins forever, continually pushing hashes onto `route`, which also grows unbounded (memory exhaustion in addition to the CPU hang).

`verify_grandpa_finality_proof` calls this function twice, and both calls occur **before** `justification.verify(...)`: [2](#0-1) 

- `headers` is built entirely from `finality_proof.unknown_headers` — fully attacker-controlled.
- The first `headers.ancestry(base.hash(), consensus_state.latest_hash)` call (conditional) and the second, unconditional `headers.ancestry(from, target.hash())` call both execute before any cryptographic check that the submitted justification/authority signatures are genuine.
- Since only `target.hash() == finality_proof.block` and `justification.commit.target_hash == finality_proof.block` are checked beforehand — both trivially satisfiable by the attacker since they control the whole `FinalityProof` structure — the ancestry walk over attacker-crafted, cyclic `unknown_headers` executes with no prior authentication.

This function is reached from the standard consensus-update dispatch path: [3](#0-2) 

`Message::Consensus` is processed by any relayer submitting a client update; `verify_consensus` for the GRANDPA client decodes the message and calls into `verify_grandpa_finality_proof`.

### Impact Explanation
An unprivileged relayer can submit a single `Message::Consensus` extrinsic with a maliciously crafted `unknown_headers` cycle to hang the runtime's execution of that message indefinitely (bounded only by the block's gas/weight budget being exhausted repeatedly, or by node-level resource exhaustion if weight metering doesn't preempt busy-loops mid-execution). This matches the CVE's impact class exactly: "ability to cause a hang or frequently repeatable crash (complete DOS)" reachable via network access, without needing any privileged key material — worse than the original CVE, since here it requires **no signature at all**, only a well-formed but unauthenticated proof structure.

### Likelihood Explanation
High. Constructing two headers with mutually referencing `parent_hash` fields is trivial and requires no cryptographic material. The only preconditions are that `target.hash()` matches `finality_proof.block` and `justification.commit.target_hash` matches it too — both are fields the attacker fully controls in the submitted message, and `GrandpaJustification::decode` only requires successful SCALE decoding, not valid signatures. This is directly reachable from a single relayed extrinsic with no privileges.

### Recommendation
- Bound the ancestry walk by a maximum number of iterations tied to `finality_proof.unknown_headers.len()` (e.g., the walk can visit at most `unknown_headers.len()` distinct hashes before it must fail), and detect revisits via a `visited` set to reject cycles deterministically instead of looping.
- Alternatively, restructure `verify_grandpa_finality_proof` so that `justification.verify(...)` (which validates authority signatures) runs strictly before any ancestry walk over attacker-supplied headers.

### Proof of Concept
1. Craft two headers `H1`, `H2` such that `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()`; include both in `unknown_headers` in a `FinalityProof` with `block = H_max.hash()` where `H_max` is the header with the greatest block number in the set (satisfying the `target.hash() == finality_proof.block` check).
2. Set `justification.commit.target_hash = finality_proof.block` (no valid signature required to reach the vulnerable call, since `verify()` runs after the ancestry walk).
3. Submit as `Message::Consensus(consensus_message)` via the standard ISMP consensus-update path (`handle_incoming_message` → GRANDPA client `verify_consensus` → `verify_grandpa_finality_proof`).
4. Execution enters `headers.ancestry(from, target.hash())` (or the earlier conditional call) and loops forever because `current_hash` cycles between `H1.hash()` and `H2.hash()`, never equaling `base`/`from`, and never hitting a missing map entry.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
