### Title
Missing Arbitrum Sequencer uptime check allows stale/manipulated Chainlink prices to be used for fee pricing - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments and fee-recycling swaps using Chainlink `AggregatorV3Interface.latestRoundData()` feeds for both the native asset and each registered token, and is deployed to Arbitrum mainnet [1](#0-0) . Like the GMX Synthetics `Oracle._setPricesFromPriceFeeds` issue referenced in the report, the contract only checks `answer <= 0` and staleness against `block.timestamp - updatedAt`, but never checks whether the Arbitrum Sequencer is up via a Chainlink L2 sequencer-uptime feed.

### Finding Description
`_getOraclePrice` reads `latestRoundData()` from the configured `AggregatorV3Interface` and validates only positivity and freshness relative to `maxOracleAge`: [2](#0-1) 

This is used both for the per-UserOp token price used to size the amount pulled from the user in `_tokenPrice`, and for the swap `amountOutMin` guard in `swapAndDeposit`: [3](#0-2) [4](#0-3) 

When the Arbitrum Sequencer goes down, L2-submitted transactions (including the aggregator nodes that update Chainlink feeds on L2) stop being processed, so the on-chain `latestRoundData()` value can be frozen at its last value while `updatedAt` also freezes — however, once the sequencer comes back online, there is a known window where the feed catches up and reports stale/incorrect data before `updatedAt` reflects it, or a malicious/compromised sequencer batch could apply transactions using the frozen price against current chain state. Because the maximum staleness bound (`maxOracleAge`, capped at `MAX_ORACLE_AGE = 7 days`) is configured generously enough to tolerate normal update latency, a sequencer outage of hours can still pass the staleness check while the feed is not truly current, since `updatedAt` may simply be stale relative to the true off-chain price rather than reverting.

Unlike the referenced GMX report (index price staleness affecting order execution price), here the impact is that a user's gas-fee token debit (`_erc20Cost`/`getTokenPrice`) and the treasury's fee-recycling swap price (`swapAndDeposit`) can be computed from a price that does not reflect the current market — during a sequencer outage a user could submit a UserOp (or the treasury an autonomous swap) at a favorable stale rate the moment the sequencer resumes, before feeds have converged, extracting value from either the paymaster's stablecoin reserves or the treasury's recycling swap.

### Impact Explanation
This is a Medium severity issue: it does not permit outright forging of messages or minting, but it can lead to economic loss for the paymaster contract (mispriced gas-token debits) or unfavorable swap execution during a chainlink-side/L2 sequencer disruption on Arbitrum, one of the paymaster's supported deployment chains. The paymaster's own stablecoin/token reserves and its treasury-controlled `swapAndDeposit` flow are both gated exclusively by the `StaleOraclePrice`/`InvalidOraclePrice` checks, with no sequencer-liveness gate to prevent using a technically-fresh-looking but market-incorrect price during/just after an outage.

### Likelihood Explanation
Likelihood is Low-to-Medium: Arbitrum Sequencer downtime events are infrequent but have occurred historically, and the attack window (immediately following sequencer recovery, before feeds fully catch up) is narrow but real and has been exploited in comparable DeFi protocols. The contract is unprivileged for `getTokenPrice`/`estimateTokenCost` reads and for any UserOp using the mode-1/mode-2 paymaster paths, so any user (not just a privileged actor) can trigger a mispriced fee debit during this window, satisfying the "unprivileged message dispatcher" reachability requirement.

### Recommendation
Add a Chainlink L2 Sequencer Uptime feed check (e.g. `0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum) to `_getOraclePrice`, reverting or applying a grace period (Chainlink recommends ~1 hour) after the sequencer comes back online before trusting `latestRoundData()` results, consistent with Chainlink's documented guidance for L2 price-feed consumers.

### Proof of Concept
1. Arbitrum Sequencer halts; Chainlink price feeds on Arbitrum stop updating but remain within `maxOracleAge` (up to 7 days per `MAX_ORACLE_AGE`) [5](#0-4) .
2. Sequencer resumes; a burst of transactions is processed, including a delayed oracle update that has not yet converged to the true off-chain price.
3. An attacker submits a UserOp with mode-1/mode-2 paymasterData referencing a token whose price is still favorably stale, calling `getTokenPrice`/triggering `_tokenPrice` in the paymaster's validation, obtaining an under-priced gas debit relative to the token's true value.
4. Alternatively, the treasury (or anyone able to trigger `swapAndDeposit` timing, since it's treasury-gated but time-of-call determines the price snapshot) executes `swapAndDeposit` at the stale rate, producing a worse-than-market `amountOutMin` bound and effectively locking in value loss for the protocol.
5. No sequencer-uptime check exists anywhere in the repository (`grep` for `SequencerUptime`/`isSequencerUp` returns no results), confirming the gap.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
