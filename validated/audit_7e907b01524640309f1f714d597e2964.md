### Title
`describeWithdrawal()` in `PoaBridge` matches status by `assetId` only, causing wrong withdrawal status/txHash to be reported for batched withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
Similar to the `safeTransferMany()` bug (a function whose implementation does not actually perform the check its name/contract implies), `PoaBridge.describeWithdrawal()` claims to correctly resolve the status of *a specific* withdrawal identified by a `WithdrawalIdentifier`, but its matching logic only keys on `assetId`, not on the specific withdrawal instance (amount, destination address, or index). This breaks the equality "status/txHash reported for withdrawal N" == "actual on-chain outcome of withdrawal N" when multiple withdrawals of the same asset are in flight for the same account.

### Finding Description
`describeWithdrawal()` fetches the account's PoA withdrawal statuses and then resolves the specific record via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [1](#0-0) 

The comment explicitly states the rationale: *"Response list is unsorted, so we match by assetId instead of index."* This means the correlation key used to disambiguate between multiple pending/completed withdrawal records returned by the POA bridge API is the `assetId` alone — not the `index` field that is otherwise used throughout the SDK to disambiguate multiple withdrawals of the same route/asset (see `createWithdrawalIdentifiers` which explicitly maintains per-route index counters): [2](#0-1) 

and the `WithdrawalIdentifier.index` field, which is designed to distinguish concurrent withdrawals of the same route: [3](#0-2) 

If a user (or an integrator batching multiple withdrawals on the caller's behalf) submits two or more PoA withdrawals of the **same** `assetId` (e.g., two separate BTC withdrawals with different amounts/destination addresses) within a time window where the bridge has not yet fully indexed/sorted them, `findMatchingWithdrawal` can return the wrong underlying withdrawal record for a given `WithdrawalIdentifier`. The caller (`sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) then reports the `status`/`txHash` of a *different* withdrawal instance as if it belonged to the one being tracked.

### Impact Explanation
This maps to the "status reported that is not the on-chain outcome" class explicitly called out in scope: an integrator polling withdrawal N's status via the SDK can be told withdrawal N is `completed` with a specific `txHash` when that `txHash`/completion actually belongs to a sibling withdrawal N' of the same asset. This can cause an integrator to:
- Credit/mark withdrawal N as completed based on a transaction that settles withdrawal N' instead (potential double-credit or premature release of custody/liability on the integrator's side).
- Conversely, report the wrong withdrawal as still pending/failed while the actual one already completed, or attribute the wrong destination tx hash to the wrong recipient in downstream bookkeeping.

This satisfies the High severity bar: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Likelihood is moderate: it requires the same account to have ≥2 in-flight withdrawals of the identical `assetId` (not uncommon for batch/repeated withdrawal use cases, which the SDK explicitly supports via `withdrawalParams: WithdrawalParams[]` in `waitForWithdrawalCompletion`/`estimateWithdrawalFee`) combined with the PoA bridge API returning an unsorted list where amount/destination based disambiguation is not performed by the SDK. The code comment itself acknowledges the list is unsorted, and no additional field (amount, destination address, or an explicit withdrawal id) is used to disambiguate — only `assetId`, which is shared across all such batched withdrawals.

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than just `assetId` — additionally match on `amount`, `destinationAddress` (and `destinationMemo` if present), or, if the PoA API round-trips a client-supplied identifier/index, propagate and match on that unique identifier instead of relying on `assetId` alone.

### Proof of Concept
Not independently reproduced against a live PoA API in this pass (would require constructing two concurrent same-asset withdrawals and an unsorted mocked response with swapped amounts/destinations to observe `describeWithdrawal` returning the wrong `txHash` for the wrong `WithdrawalIdentifier`); this is inferred directly from the matching implementation's documented behavior (comment: "match by assetId instead of index") and the absence of amount/destinationAddress checks in the call signature `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`. I was not able to view the full body of `findMatchingWithdrawal` before running out of tool iterations, so the exact matching logic (e.g., whether it additionally inspects `amount`/`address` internally) is not fully confirmed — this should be verified by reading `findMatchingWithdrawal`'s implementation in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts` (or wherever it is defined) before treating this as conclusively exploitable.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

async function findBridgeForWithdrawal(
	bridges: Bridge[],
	params: WithdrawalParams,
): Promise<Bridge | undefined> {
	for (const bridge of bridges) {
		if (await bridge.supports(params)) {
			return bridge;
		}
	}
	return undefined;
}
