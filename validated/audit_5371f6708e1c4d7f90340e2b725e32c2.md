### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw request body, never the `shopify-shop-domain` / `x-shopify-shop-domain` header. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's webhook handler as the authoritative tenant identifier, without that value ever being covered by the cryptographic check.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — the `shop` accessor, which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, is never included: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches `request.shop` (unverified) directly into `WebhookMetadata`, which is the tenant-identifying value the app-level handler acts on: [4](#0-3) 

This breaks the intended identity binding: `hmac-verified-bytes == tenant-authenticated-request`. The HMAC only proves "this body was produced with our `api_secret_key`" — it does not prove "this body originated from shop X." Because the same `api_secret_key` is shared across every shop installed on a multi-tenant app, a party that legitimately receives one valid signed webhook (e.g., a merchant who installed the app on their own shop and can view Shopify's webhook deliveries, or anyone able to capture one genuine webhook POST) can replay the identical body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature will still validate (`OpenSSL.secure_compare` only checks body-derived bytes) while `request.shop` — the value the app trusts to select which tenant's data/session to touch — is fully attacker-controlled.

This matches the report's bug class: a field the code treats as authenticated (`shop`) is not actually bound by the cryptographic check (`hmac` covers `raw_body` only), i.e. `verified_bytes ⊆ signed_content` but `shop ∉ signed_content`.

Compare with the OAuth callback path, where the analogous field IS correctly protected: `AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter set, so `Oauth.validate_auth_callback` can safely trust `auth_query.shop` after HMAC validation: [5](#0-4) [6](#0-5) 

No equivalent protection exists for the webhook `shop` field.

### Impact Explanation
Host applications built on this gem are documented to key their session/tenant lookup off `WebhookMetadata#shop` (e.g., to load the correct shop's session/access token, or to route webhook data into the correct tenant's records). Since `shop` is unauthenticated relative to the HMAC, an attacker can forge which tenant a webhook payload is attributed to while still passing HMAC validation, enabling **cross-tenant data injection/access** — writing or triggering side effects (order/webhook-driven business logic) against a victim shop's tenant context using a signature that was only ever valid for the attacker's own shop's payload. This satisfies the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Requires only: (1) the app be multi-tenant and share one `api_secret_key` across shops (standard Shopify app model), and (2) the attacker be able to observe at least one genuine webhook delivery for a shop they control (trivial — merchants can inspect their own app's webhook traffic, or run the app themselves) and replay it with a modified shop header to the shared public webhook endpoint. No access token, `api_secret_key`, or privileged account is needed — this is exploitable by any unprivileged internet user who can install/operate the target app on a shop they control.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise validate `request.shop` against an authenticated source (e.g., cross-check against the shop recorded when the specific `webhook-id` was registered, or validate the shop domain via `ShopValidator` before trusting it) instead of trusting the raw header as-is once body HMAC succeeds.

### Proof of Concept
1. App installs webhooks for Shop A (attacker's own shop) and Shop B (victim) on the same multi-tenant deployment sharing one `api_secret_key`.
2. Attacker triggers an event on Shop A, capturing the genuine POST: body `B`, header `shopify-hmac-sha256: H = HMAC(secret, B)`, `shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker resends the identical request to the app's webhook endpoint, replacing only the header: `shopify-shop-domain: shop-b.myshopify.com` (HMAC `H` and body `B` unchanged).
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body` [2](#0-1) .
5. `Registry.process` calls the app handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com", body: <attacker-controlled parsed JSON from Shop A's event> ...)` [7](#0-6) , causing the app to process attacker-controlled webhook content under Shop B's tenant identity.
