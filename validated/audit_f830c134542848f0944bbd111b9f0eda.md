### Title
Non-standard ERC20 transfer return value not validated in `IntentGatewayV2.withdraw` and `onAccept` (SweepDust) causes escrow funds to be lost/permanently stuck - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` uses low-level `.call` with `IERC20.transfer.selector` to move escrowed input tokens, protocol fees, and swept dust to beneficiaries, but only checks that the low-level call did not revert (`success`). It never decodes and validates the ERC20 boolean return value. Tokens that follow the (common, non-reverting) pattern of returning `false` on a failed transfer instead of reverting will cause this contract to treat the transfer as successful, even though no tokens were actually moved.

### Finding Description
`withdraw()` releases escrowed tokens to the settling solver/beneficiary and finalizes the order: [1](#0-0) 

For every escrowed token, it performs:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and unconditionally decrements `_orders[body.commitment][token] -= amount;` and, for the finalizing call, sets `_filled[body.commitment] = beneficiary;` and clears `_orders[body.commitment][TRANSACTION_FEES]`, **before or regardless of** whether the ERC20 actually transferred value. The same unchecked pattern is used for dust sweeping in `onAccept`'s `SweepDust` branch: [2](#0-1) 

The contract already imports and uses `SafeERC20` elsewhere (`using SafeERC20 for IERC20;`, and `safeTransferFrom` is used consistently in `placeOrder`/`fillOrder`), which shows the intended pattern was to always validate the ERC20 return value — but `withdraw()` and the `SweepDust` handler in `onAccept` bypass `SafeERC20` and use raw `.call` checking only the outer call success, not the ABI-decoded boolean return data. Per the ERC20 standard many tokens (and any misbehaving/blacklist-style token, e.g. one that returns `false` when the beneficiary is blacklisted or paused) return `false` on failure rather than reverting, which this code will treat as a successful transfer.

`onAccept` is called by the `IsmpHost`/`HandlerV2` message-delivery path when a relayer submits a cross-chain settlement proof (`RequestKind.RedeemEscrow`/`RefundEscrow`/`SweepDust`), making this reachable by any unprivileged relayer delivering an otherwise-valid, authenticated cross-chain message — no special privilege beyond normal message delivery is required to trigger the vulnerable code path.

### Impact Explanation
Because escrow accounting (`_orders[...]`) is decremented and the order is marked `_filled` regardless of whether the token transfer actually succeeded, a failed-but-non-reverting transfer results in:
- The solver/beneficiary never receiving the tokens they are owed for filling the order.
- The order being irreversibly marked as filled/settled (`_filled[commitment] = beneficiary`), so the escrowed tokens can never be re-claimed through the normal withdrawal path (`_orders[commitment][token]` is reduced/zeroed and a repeat call reverts with `UnknownOrder`).
- Tokens remaining physically locked in the `IntentGatewayV2` contract, unbacked by any correct accounting entry — a permanent freezing/loss of user/solver funds.

This satisfies the "concrete theft or permanent freezing of funds" bar: user-escrowed funds and protocol fee balances can become permanently stuck while the protocol state records them as already disbursed.

### Likelihood Explanation
Likelihood is Medium-High: it requires an ERC20 token used as an order input/fee/dust token that returns `false` on failure instead of reverting (a well-documented common ERC20 non-compliance pattern, and also achievable adversarially with blacklist/pausable tokens where a `transfer` to a blacklisted/paused address returns `false`). The delivery path itself (an authenticated cross-chain settlement message reaching `onAccept`) is routine and triggered by any relayer completing normal protocol operation, so no additional privilege is needed to reach the vulnerable code — only control over, or use of, a non-standard-return-value token is needed to realize the loss.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with the rest of the contract (`placeOrder`/`fillOrder` already use `safeTransferFrom`). `SafeERC20` correctly reverts both on call failure and on a decoded `false` return value, preventing state (`_orders`, `_filled`) from being updated as if a transfer succeeded when it did not.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer` implementation returns `false` (rather than reverting) when the transfer cannot be completed (e.g., recipient blacklisted, paused, or insufficient allowance-style internal check) — a pattern several real-world tokens implement.
2. A user places an order in `IntentGatewayV2` escrowing this token via `placeOrder` (uses `safeTransferFrom`, succeeds normally on deposit).
3. A solver fills the order on the destination chain; the settlement path dispatches a `RedeemEscrow`/`RefundEscrow` request back to the source chain.
4. A relayer delivers this request; `IsmpHost` calls `onAccept` → `withdraw(body, ...)`.
5. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (call didn't revert) but the ABI-decoded boolean payload is `false` — the beneficiary receives nothing.
6. `_orders[body.commitment][token] -= amount` still executes and `_filled[body.commitment] = beneficiary` is set, finalizing the order.
7. The escrowed tokens remain in the `IntentGatewayV2` contract, but there is no longer any valid accounting path to redeem them — the beneficiary lost funds permanently while the protocol registers the order as fulfilled.
