### Title
Webhook shop-domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the identity binding `hmac-authenticated content == shop attributed to the event`, letting an unprivileged user who has captured any one valid `(body, hmac)` pair from a webhook delivered to their own shop replay it with an arbitrary `shop-domain` header, causing the gem to dispatch a validly-authenticated webhook under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers, completely outside the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the signature purely against `verifiable_query.to_signable_string`, i.e., only the body: [3](#0-2) 

`Webhooks::Registry.process` performs this HMAC check and then, on success, builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no further validation performed by the gem: [5](#0-4) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, Shopify legitimately signs a valid `(body, hmac)` pair whenever any webhook is delivered for any shop that has the app installed — including a shop the attacker themselves controls (e.g., a free trial store). The equality that should hold is:
`shop bound by the authenticated signature == shop the handler acts on`
Here it instead holds only:
`bytes verified by HMAC (body) != shop attributed to the event (header)`
An attacker who intercepts/replays their own legitimately-signed webhook can swap the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header to any other shop domain string, and `Registry.process` will still accept it (`HmacValidator.validate` only re-checks the body) and forward the forged shop identity to the app's handler.

### Impact Explanation
This is a cross-tenant identity spoofing vector: any actor who can obtain one valid signed webhook (trivially achievable by installing the app on a shop they control, since the secret is app-wide, not shop-specific) can forge webhook events that the consuming application will treat as authentic events for an arbitrary victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to locate/mutate a merchant's stored session, to process `app/uninstalled`, `shop/redact`, `customers/data_request`, or other GDPR/compliance topics, or to gate business logic per-tenant), this can be leveraged to trigger destructive or data-exposing actions against a shop the attacker does not control and has no legitimate credentials for — a cross-tenant access violation stemming entirely from this gem's own webhook-verification design, not from host-app misuse of a documented API.

### Likelihood Explanation
Exploitability requires only: (1) the app's webhook endpoint be reachable over the internet, which is a standard, documented requirement of any Shopify app; and (2) the attacker be able to obtain at least one legitimately-signed `(body, hmac)` pair, which any developer/user who can install the app on a shop they control automatically receives from Shopify. No secrets, tokens, or elevated privileges are needed — the header can simply be modified before replay. This makes the attack straightforward for any unprivileged internet user with the ability to install trial/dev stores of the target app.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value verified by HMAC rather than trusting an unauthenticated header. Since Shopify's HMAC only signs the body by protocol design, the gem should not treat `request.shop` as an authenticated identity on its own; at minimum, document this and require/encourage callers to cross-check `request.shop` against a shop known to have installed the app (e.g., an existing stored session) before acting on webhook data, or extend verification to reject shops with no corresponding stored session prior to invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a free/dev store they control) and triggers any webhook topic (e.g. `orders/create`) that is registered for the app.
2. Shopify delivers a webhook POST to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(client_secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then replays it to the same endpoint unmodified except changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (unchanged) — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which now processes an authenticated-looking event under the victim's shop identity despite the attacker having no relationship to that shop. [6](#0-5)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
