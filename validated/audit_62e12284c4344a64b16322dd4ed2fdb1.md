## Analysis

The BNO exploit's root cause is a **check-then-act state desynchronization**: `emergencyWithdraw()` mutates the pledge/stake bookkeeping without properly clearing the "staked" flag that `unstakeNft()` relies on, so both exit paths can succeed for the same underlying position, letting the attacker collect value twice from what should be a single-use state transition.

The closest analog I can find in-scope (internet-facing gateway request authentication) is the JWT replay-protection cache in `WorkflowMetadataHandler.Authorize`, which performs its "already used?" check and its "mark as used" write as two **separate, non-atomic critical sections**, creating the same class of check-then-act race that let the BNO attacker reuse an already-consumed state twice.

### Title
JWT replay-guard TOCTOU race allows a single signed trigger token to authorize concurrent duplicate workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` checks whether a JWT's `jti` has already been used via `jwtCache.isReplay(claims.ID)` and, only after the signer/authorization checks pass, calls `jwtCache.recordUsage(claims.ID)` to mark it consumed. These are two separate lock acquisitions rather than one atomic check-and-set operation, so two concurrent requests bearing the same valid signed JWT can both observe "not yet used" before either records usage.

### Finding Description
`isReplay` takes an `RLock`, reads the map, and releases the lock [1](#0-0) . Only later, after signer/authorization validation succeeds, does `Authorize` call `recordUsage`, which takes a separate `Lock` to write the entry [2](#0-1) , with the actual write happening here [3](#0-2) . Between the `isReplay` read and the `recordUsage` write there is no lock held across the whole "check + record" sequence, so two goroutines invoking `Authorize` concurrently with the identical `jti` can both pass the replay check before either one records the token as used — exactly the same decoupled check-then-act state bug pattern as the BNO `emergencyWithdraw`/`unstakeNft` desync, where two independent exit paths were allowed to both succeed against a single logical state.

The `HandleUserTriggerRequest` -> `authorizeRequest` -> `WorkflowMetadataHandler.Authorize` call path is reachable directly from an unprivileged client's gateway request (the `MethodWorkflowExecute` JSON-RPC message) before any per-`requestID` in-flight dedup happens in `setupCallback`, and `setupCallback`'s dedup key is the outer envelope `requestID`, not the JWT `jti` [4](#0-3) . There is no requirement that the envelope `requestID` be tied 1:1 to the JWT, so nothing before the vulnerable check-then-act sequence serializes concurrent `Authorize` calls for the same `jti`.

### Impact Explanation
If exploitable, this breaks the stated security guarantee "JWT token has already been used. Please generate a new one with new id (jti)" — the intended one-shot replay protection for signed workflow-trigger tokens [5](#0-4) . An attacker capable of firing two near-simultaneous requests with a single valid signed JWT could trigger the associated workflow execution twice from one token, which is a concrete replay/duplicate-execution bypass of the authentication/replay guard the code explicitly tries to enforce.

### Likelihood Explanation
Exploitation requires only client-side concurrency (no privileged access) and a narrow but realistic race window between the `RLock` read in `isReplay` and the `Lock` write in `recordUsage`, during which signer/authorization validation for both goroutines executes. This is a genuine race condition rather than a purely theoretical one, but its window is narrow and timing-dependent, so reliability of triggering it depends on network/goroutine scheduling — likelihood is plausible but not guaranteed on every attempt.

### Recommendation
Make the check-and-record operation atomic: hold a single lock (or use `sync.Map`/`LoadOrStore`-style semantics) across both the "is this `jti` already present" check and the "insert this `jti`" write, so no other goroutine can observe the pre-insertion state, consistent with how `RequestReplayGuard.CheckAndRecord` in the Vault package already does it correctly under one lock [6](#0-5) .

### Proof of Concept
Not independently verified with a live race-reproduction harness; the concurrency window is inferred directly from the code structure (separate `RLock`/`Lock` sections in `isReplay` and `recordUsage`, called from two different points in `Authorize` with unrelated validation logic in between) [2](#0-1) .

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
