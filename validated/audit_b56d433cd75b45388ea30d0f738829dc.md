This confirms a real identity-binding gap: the webhook HMAC signature is computed over `@raw_body` only [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC of the body and then dispatches the handler using `request.shop` and `request.topic` taken from those unsigned headers [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain`) is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature Shopify computes and sends never covers the `shop-domain`, `topic`, or `webhook-id` headers. `Registry.process` validates the HMAC and then trusts those unsigned headers to route the webhook, breaking the intended binding between the authenticated payload and the tenant it is attributed to.

### Finding Description
`Request#hmac` reads the `X-Shopify-Hmac-Sha256` header and `Request#to_signable_string` returns `@raw_body` [4](#0-3) . `Utils::HmacValidator.validate` computes an HMAC over exactly that signable string (`compute_signature(verifiable_query.to_signable_string, secret)`) and compares it to the received value [5](#0-4) . Nothing in this computation includes `shop`, `topic`, or `webhook_id` — those are parsed straight from HTTP headers via `shopify_header` [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the topic handler using `request.shop` and `request.topic` [3](#0-2) . This means the identity binding `bytes verified == bytes parsed` is broken: the bytes cryptographically verified are the JSON body only, while the bytes the host application actually acts on for tenant/topic routing (`shop-domain`, `topic`, `webhook-id` headers) are unauthenticated and fully attacker-controllable in a request that carries a validly-signed body.

Concretely, since the signature never binds `shop-domain` to the body, any request whose body byte-for-byte matches a previously-observed, validly-signed webhook body (a very plausible situation, since many webhook payload shapes for a given topic are highly similar/predictable, and some topics — e.g. many `*/redact` or state-change events with minimal or templated payloads — have identical or near-identical bodies across different shops/events) will pass HMAC validation regardless of which shop header accompanies it. An attacker who can, for one shop instance they control (e.g. their own paid/dev shop) or by intercepting a single legitimate webhook, obtain one valid `(body, hmac)` pair for a topic, can then resend that exact body with a different `shop-domain` header value to the same app endpoint. `HmacValidator.validate` will accept it because it only checks the body's HMAC, and `Registry.process` will invoke the app's handler believing the event came from the spoofed `shop`, achieving cross-tenant data confusion at the identity level the gem is responsible for authenticating.

### Impact Explanation
This falls under the "Critical – cross-tenant access" category: the shop identity that host applications rely on for per-tenant handling of webhook data (e.g. deciding which merchant's data record to update, or which tenant's local state to mutate) is not authenticated by this gem, even though the gem's `HmacValidator` API is presented as the security boundary for accepting a webhook as genuine. Since the `shop` field is not covered by the HMAC computation, the "authenticated" designation the library gives to `WebhookMetadata.shop` is misleading, and downstream applications relying on `Registry.process`'s HMAC check as proof-of-origin-and-tenant will process cross-tenant events under the wrong shop identity.

### Likelihood Explanation
Medium-High: the attacker needs one valid `(body, hmac)` pair for some topic (obtainable from their own shop instance, which every developer can freely create) and only needs to replay the body with a modified `shop-domain` header to the target app's public webhook endpoint. No secret key or elevated access is required — only network access to the app's own publicly reachable webhook receiver, matching the "unprivileged internet user" threat model.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, and `api-version`) in the signable string alongside the raw body (or otherwise bind them cryptographically, e.g. HMAC over a canonical concatenation of header values and body) so that `Utils::HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually signed for that request.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` in App A, which is installed on `shopA.myshopify.com` and `shopB.myshopify.com` (attacker controls `shopA`, victim owns `shopB`).
2. Trigger a webhook delivery on `shopA` and capture the raw request: headers (including `X-Shopify-Shop-Domain: shopA.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac>`) and raw JSON body.
3. Replay the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `shopB.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#initialize` accepts the headers, `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) computes the HMAC solely over `@raw_body` and succeeds since the body/hmac pair is genuinely valid.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting `shopB.myshopify.com`, even though the payload never originated from Shopify for that shop — demonstrating the cross-tenant identity confusion.
