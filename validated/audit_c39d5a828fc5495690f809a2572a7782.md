### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` recomputes/compares the HMAC over that body alone. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and passed unchanged into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle`. Because the app's single `api_secret_key` is shared across every shop that installs the app, any shop owner (an unprivileged internet user with respect to other tenants) can capture a legitimate webhook (body + valid HMAC) delivered to their own store and replay it against the same endpoint while substituting a different `shop-domain` header. The HMAC still validates, because it never covered the shop identity, and the handler receives `WebhookMetadata` claiming the forged shop.

### Finding Description
- `Request#hmac` and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:10-13, 35-38`) bind the signature only to `@raw_body`.
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` (`lib/shopify_api/webhooks/request.rb:15-33`) are derived purely from headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in `to_signable_string`.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only `Utils::HmacValidator.validate(request)` — i.e., body-only — and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to build `WebhookMetadata`, which is delivered to the host app's handler.
- `Utils::HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) performs `OpenSSL.secure_compare` against `compute_signature(verifiable_query.to_signable_string, secret)` — confirming the signed content is exactly the body, nothing else.

This breaks the intended identity binding: `shop_claimed_in_header == shop_the_HMAC_actually_authenticates`. The HMAC only proves "Shopify's app secret produced this body"; it proves nothing about which shop the body belongs to. Since `api_secret_key` is the app-level (not shop-level) secret, every installing shop can independently produce HMAC-valid bodies. An attacker who is a legitimate (if unprivileged) tenant of the app can therefore forge the shop-attribution of any webhook delivery.

### Impact Explanation
This crosses a tenant boundary: an attacker who merely installs the app on their own store (no access token theft, no `client_secret` leakage, no privileged account) can cause the app to process a webhook body it validly received while asserting it originated from a different (victim) shop. If the host application uses `WebhookMetadata#shop` (as documented/intended, `lib/shopify_api/webhooks/webhook_handler.rb:6-11`) to route data — e.g., to look up/update records, trigger side effects, or store data keyed by shop — the attacker can inject data attributed to, or trigger actions against, a shop they do not control. That is a cross-tenant integrity/confidentiality impact consistent with the "cross-tenant access" Critical impact category in scope.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-controlled shop (which is by design open to any merchant), (2) capturing one legitimate webhook (body + `x-shopify-hmac-sha256`) sent to that shop, and (3) replaying it to the app's public webhook endpoint with a modified `shop-domain` header (topic/webhook-id/api-version could also be altered to select a different registered handler). No cryptographic secret needs to be recovered — the attacker already legitimately possesses a valid `(body, hmac)` pair. This is straightforward for anyone who can install the app, which is the intended experience of any public app.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed content, or otherwise cryptographically tie the header-derived shop domain to the specific installation/session before trusting `WebhookMetadata#shop`. At minimum, cross-check the incoming `shop-domain` header against a shop known to be currently subscribed/registered for that specific `webhook_id`/topic combination (per-shop webhook subscription IDs returned by Shopify are unique), rather than trusting the header value directly for attribution.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger a webhook event (e.g., `orders/create`) so Shopify delivers a POST to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Capture the raw body and the `x-shopify-hmac-sha256` header value from that legitimate delivery.
3. Replay a POST to the same webhook endpoint with the identical body and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over the body — validation succeeds.
5. `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))` is invoked, and the host app processes/persists the attacker's data as if it belonged to `victim-shop.myshopify.com`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
