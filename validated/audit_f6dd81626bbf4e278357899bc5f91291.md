### Title
Permanent freezing of escrowed user funds when cancelling a same-chain order with active protocol fees, due to mismatched escrow accounting in `cancelOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.cancelOrder()` (Tron fork) builds the same-chain refund `WithdrawalRequest` using the order's original, un-reduced `order.inputs` amounts, while `placeOrder()` escrows the fee-**reduced** amounts (`reducedInputs`) whenever a protocol fee is configured. `withdraw()` then attempts to transfer the larger, unreduced amount and subtract it from the smaller escrowed balance, causing an arithmetic underflow revert on every same-chain cancellation once `protocolFeeBps > 0`, permanently locking the user's escrowed tokens.

### Finding Description
In `placeOrder`, when a non-zero protocol fee applies, the escrow ledger is populated with the *reduced* amount: [1](#0-0) [2](#0-1) 

`reducedInputs[i].amount = originalAmount - protocolFee`, so `_orders[commitment][token]` holds the discounted amount, not `order.inputs[i].amount`.

When the order owner cancels a same-chain order, `cancelOrder` builds the `WithdrawalRequest` from `order.inputs` directly (the full, unreduced amount), not from the actual escrowed balance: [3](#0-2) 

`withdraw()` then transfers this larger `amount` and subtracts it from the smaller ledger entry: [4](#0-3) 

Since `amount` (`order.inputs[i].amount`, unreduced) is strictly greater than `_orders[body.commitment][token]` (the reduced escrow) whenever `protocolFee > 0`, the checked subtraction `_orders[body.commitment][token] -= amount;` always underflows and reverts (Solidity ≥0.8 panics on arithmetic underflow), rolling back the entire cancellation transaction — including the token transfer that was attempted just before it.

By contrast, the reference EVM implementation avoids this entirely by reading the *actual* escrowed balance for the withdrawal amount instead of the original order amount: [5](#0-4) 

The Tron port diverges from this correct pattern, reintroducing the mismatch.

### Impact Explanation
Whenever the gateway's protocol fee is non-zero (`_params.protocolFeeBps` or a destination-specific override, both settable by governance/admin via `setParams`/`UpdateParams`), *every* same-chain order placed through this Tron deployment becomes uncancellable: the sole same-chain cancel path (`cancelOrder` → `withdraw`) will always revert with an underflow. Since this contract's `withdraw` is the only mechanism to release escrowed inputs back to the user pre-fill, and no `fillOrder` function exists in this contract to otherwise release the escrow, user funds placed in an order that is never picked up by a solver become permanently stuck in the contract. This matches the "permanent freezing of funds" impact class.

### Likelihood Explanation
This is trivially and deterministically triggered by any unprivileged user in a single transaction sequence: `placeOrder` (escrowing any token, with a non-zero protocol fee already configured), followed by `cancelOrder` for the same, same-chain order. No attacker collusion, timing, or race condition is required — it happens on every attempt whenever the fee configuration is non-zero, which is the normal expected operating condition for a fee-charging deployment.

### Recommendation
In `cancelOrder`'s same-chain branch, build the `WithdrawalRequest.tokens` from the actual escrowed balances (`_orders[commitment][token]`) rather than from `order.inputs[i].amount`, mirroring the pattern used in `IntrinsicIntents._cancelSameChain`:
```solidity
for (uint256 i; i < inputsLen; i++) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    uint256 escrowed = _orders[commitment][token];
    remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
}
```
This ensures the amount passed to `withdraw()` never exceeds the ledger balance, regardless of protocol-fee configuration.

### Proof of Concept
1. Admin/governance sets `_params.protocolFeeBps = 100` (1%) via `setParams`/`UpdateParams`.
2. User calls `placeOrder(order, graffiti)` escrowing `order.inputs[0].amount = 1000` of `TokenA`.
   - `reducedInputs[0].amount = 990` is computed and `_orders[commitment][TokenA] += 990`.
3. Before any solver fills the order, the user calls `cancelOrder(order, options)` on the same chain (`orderSource == orderDest == currentChain`).
   - `withdraw` is invoked with `body.tokens[0].amount = order.inputs[0].amount = 1000`.
   - `_orders[commitment][TokenA]` (990) `== 0`? No, so the zero-check passes.
   - `token.call(transfer(beneficiary, 1000))` is attempted (draining more than what was actually escrowed for this order from the pool's shared balance) then `_orders[commitment][TokenA] -= 1000` underflows (990 - 1000), causing a panic revert.
4. The entire `cancelOrder` transaction reverts every time it is retried; the user's 990 `TokenA` remains locked in the contract with no other means of retrieval.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
