## Title
Fee-on-transfer tokens cause escrow under-collateralization in the Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the escrow mapping `_orders[commitment][token]` with the user-requested (fee-adjusted-by-protocol-only) amount instead of the amount actually received by the contract after the `safeTransferFrom` call. For fee-on-transfer (FOT) ERC20 tokens, this causes the on-chain escrow bookkeeping to overstate the tokens the contract actually holds, unlike the main EVM `IntentGatewayV2.sol`, which was specifically hardened against this by measuring `balanceOf` before/after every transfer.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

the contract does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is simply `order.inputs[i].amount` minus the protocol fee bps [2](#0-1) , it is never derived from an actual balance check. If `token` charges a transfer fee, the contract receives strictly less than `order.inputs[i].amount`, yet the escrow ledger is still incremented as if the full (minus-protocol-fee) amount arrived.

The same pattern occurs in the predispatch branch: [3](#0-2) 
Here a "dust" event is emitted only for `balance - requiredAmount` (surplus over the required amount), but there is no protection against `balance < requiredAmount` reducing the actual sweep below what the escrow subsequently credits (`reducedInputs[i].amount`).

By contrast, the primary EVM `IntentGatewayV2.sol` explicitly measures the balance delta and mutates `order.inputs[i].amount` to the actual received amount before computing escrow and commitment, exactly to avoid this fee-on-transfer inconsistency: [4](#0-3) 
and this behavior is explicitly validated by dedicated fee-on-transfer tests in the test suite: [5](#0-4) 

The Tron contract lacks this correction entirely, meaning `_orders[commitment][token]` (the value later used to authorize withdrawals/refunds via `withdraw()` in `cancelOrder`/`onAccept`) can exceed the token balance the gateway actually holds for that commitment.

### Impact Explanation
Because `cancelOrder` (same-chain and cross-chain refund/redeem paths) and `onAccept`'s `RedeemEscrow`/`RefundEscrow` handling rely on the `_orders` mapping to authorize and size outbound transfers: [6](#0-5) [7](#0-6) 
an order placed with a fee-on-transfer input token will have an escrow record larger than the contract's actual token balance attributable to that commitment. When the beneficiary/solver later attempts to withdraw (cancel/refund or redeem after fill), the outbound transfer for the FOT token can revert due to insufficient balance, permanently freezing the escrowed principal for that order, or, if the shortfall is silently drawn from other orders' balances (since `_orders` is a per-token, not a strictly separated vault), it can cause insolvency that leaves a later, unrelated order's legitimate withdrawal unable to be satisfied — a shared-pool under-collateralization across all orders using that token.

### Likelihood Explanation
Any unprivileged user can trigger this by simply calling `placeOrder` with a fee-on-transfer token as an input asset — no special privileges or preconditions are required beyond the token being accepted by the gateway (fee-on-transfer tokens are explicitly an in-scope compatibility concern per the analog report, and the main EVM contract's own test suite proves the protocol intends to support them).

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` (or the dispatcher's balance, for the predispatch path) before and after each `safeTransferFrom`/sweep, and use the *actual delta* — not the caller-declared `order.inputs[i].amount` — as the basis for `reducedInputs[i].amount` and the resulting `_orders[commitment][token]` credit, mutating `order.inputs` in place so the commitment hash stays consistent with what is actually escrowed.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 token (e.g., 1% fee) as done in `FeeOnTransferToken` test helper: [8](#0-7) 
2. User calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}`, no protocol fee configured. `safeTransferFrom(user, gateway, 1000e18)` executes; gateway actually receives `990e18` due to the 1% fee, but `_orders[commitment][FOT]` is incremented by `reducedInputs[0].amount == 1000e18` (since `protocolFeeBps == 0`, `reducedInputs == order.inputs`).
3. Gateway's actual `FOT.balanceOf(gateway)` is `990e18`, but its internal escrow ledger for this commitment records `1000e18`.
4. User calls `cancelOrder` before fill; `withdraw()` attempts to transfer `_orders[commitment][FOT] == 1000e18` back to the user, but the contract only holds `990e18` — the transfer reverts, permanently freezing the user's `990e18` in the contract (or, in a shared-balance scenario across multiple orders of the same FOT token, draining balance needed for other legitimate withdrawals).

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
