Based on this analysis, the documentation explicitly confirms the gem's own contract: `docs/usage/webhooks.md` lines 12-17 state that after `Registry.process` verifies the request "did indeed come from Shopify" (line 125), the handler receives `shop` as an authenticated field of `WebhookMetadata`. This is the binding this gem breaks.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted by `Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then hands the caller-supplied `shop` header value as an authenticated tenant identifier, even though that value was never part of the signed content.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` as legitimate: [1](#0-0) 

The HMAC validation itself only signs the raw request body, never the headers: [2](#0-1) 

`HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` (the raw body, for webhooks) and compares it against the received HMAC: [3](#0-2) 

Because the app's `client_secret` (and therefore the HMAC key) is shared across every shop that has installed the app — it is not shop-specific — any legitimate merchant who has installed the app can trigger a webhook event in their own store, capture the resulting genuinely-signed body+HMAC pair from Shopify, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to name a different, victim shop that also has the app installed. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and `Registry.process` will then dispatch to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain: [4](#0-3) 

This is precisely the "field acted on but not covered by the HMAC" pattern: the equality the gem should enforce — `authenticated_shop == shop_used_by_handler` — is never checked; only `HMAC(body)` is checked, and `shop` is orthogonal to that signature.

The gem's own documentation instructs handler authors to trust `data.shop` as the authenticated shop domain of the webhook once `Registry.process` has validated it: [5](#0-4)  and states that `process` "will verify the request did indeed come from Shopify": [6](#0-5) . The verification performed does not actually bind the shop identity, contradicting this documented guarantee.

### Impact Explanation
Any app storing/updating per-tenant data keyed by `WebhookMetadata.shop` (e.g., orders, inventory, customer PII, redact/GDPR topics) can be made to attribute an attacker-controlled payload to a victim shop, producing cross-tenant data corruption or disclosure inside the host application, driven entirely by data the attacker's own store legitimately produced. This matches the "cross-tenant access" Critical-impact category, since the identity boundary between tenants (shops) is broken using only an attacker-controlled, otherwise-legitimate installation.

### Likelihood Explanation
The attacker only needs to be a legitimate merchant who installs the target app in their own store (a low bar — most Shopify apps are installable by any merchant) and to trigger any webhook topic the app is registered for. No possession of `api_secret_key` or another merchant's token is required, since the HMAC secret is shared per-app across every installer and the vulnerable check never binds `shop` to that signature.

### Recommendation
Have `Registry.process` (or `HmacValidator`) incorporate the `shop` domain (and ideally `topic`/`webhook_id`) into the value verified against the HMAC, or independently cross-check the header-provided `shop` against a list of shop domains that are known to have legitimately installed the app (e.g., via a stored offline session) before dispatching to the handler, rather than passing the raw header value through as an authenticated identifier.

### Proof of Concept
1. App has one shared `api_secret_key` for all installations; shops A (attacker-controlled) and B (victim) both install the app and register the same webhook topic.
2. Attacker triggers the event in shop A, causing Shopify to POST a body `B` with headers `shopify-shop-domain: shop-a.myshopify.com`, `shopify-hmac-sha256: HMAC(secret, B)` to the app's endpoint.
3. Attacker intercepts/replays this exact request to the same endpoint but rewrites the header to `shopify-shop-domain: shop-b.myshopify.com`, leaving body `B` and the HMAC unchanged.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still matches, per [7](#0-6) .
5. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "shop-b.myshopify.com"` and body `B`, per [8](#0-7) , causing the host app to process attacker-controlled data as if it originated from victim shop B.
