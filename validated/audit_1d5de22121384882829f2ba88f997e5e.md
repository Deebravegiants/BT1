The documentation explicitly claims `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and hands the resulting `data.shop` to the app as an authenticated shop identity [2](#0-1) . This is enough to finalize the analog.

### Title
Webhook `shop` header is trusted and dispatched to handlers without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)` and then immediately builds a `WebhookMetadata` object using `request.shop`, which is taken verbatim from the `x-shopify-shop-domain` HTTP header. The HMAC, however, is computed only over the raw request body, never the shop header, so nothing binds the verified body to the shop value that is handed to the application.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to that body [4](#0-3) . `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it against the `hmac-sha256` header using the shared `api_secret_key` [5](#0-4) . `Registry.process` then trusts this unverified header directly: it raises only if the HMAC over the body fails, and otherwise constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and passes it straight to the app's handler [6](#0-5) .

Because the `api_secret_key` used for HMAC verification is the app's single shared secret — not a per-shop secret — any merchant who has installed the app can receive their own legitimately-signed webhook body from Shopify for their own store, then replay that HTTP request to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The body-only HMAC still validates (it was genuinely signed by Shopify's shared secret for the attacker's own webhook), so `Registry.process` accepts the request and calls the handler with `data.shop` equal to the spoofed victim domain and `data.body` equal to the attacker-controlled body content. The binding that should hold — `authenticated body == data claimed to belong to shop X` — is broken: the equality actually enforced is only `HMAC(body, secret) == received_hmac`, with no assertion that `shop_header` was ever part of what Shopify signed.

### Impact Explanation
This lets an unprivileged attacker who merely installs the app on their own store impersonate any other tenant's webhook traffic toward the host application, since the gem asserts the request "did indeed come from Shopify" (per its own documentation) while allowing the tenant-identifying field to be freely spoofed. Depending on how the host app models `data.shop` (e.g., looking up an existing session/store by that domain and writing incoming webhook payloads under it), this enables cross-tenant data injection/corruption under another merchant's identity — a cross-tenant boundary violation.

### Likelihood Explanation
Any actor able to install the app on a shop they control (a standard, low-privilege action for any merchant) can trigger a real, correctly-HMAC'd webhook delivery for their own store, capture it, and resend it to the app's public webhook endpoint with a modified shop header. No access token, `client_secret`, or elevated privilege is required — only the ability to receive one legitimate webhook.

### Recommendation
Bind the shop identity to the verified payload instead of trusting the header value alone: include the shop domain in the signable string used for HMAC verification (mirroring what is actually authenticated), or cross-check `request.shop` against the `shop`/`domain` field embedded in the webhook's parsed body where Shopify includes it, rejecting the request if they disagree. At minimum, document that `data.shop` from `Registry.process` is not itself HMAC-verified and must be independently checked against a known/installed shop before being trusted as an identity for downstream operations.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`, causing Shopify to deliver a legitimately-signed webhook (e.g. `orders/create`) to the app's endpoint with headers `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, and some JSON body `B`.
2. Capture this request, then resend it (or a modified body `B'` matching an already-known valid HMAC scenario is not required — the same `B`/HMAC pair is reused) to the same endpoint, replacing only the `x-shopify-shop-domain` header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers [7](#0-6) ; `Utils::HmacValidator.validate` recomputes the HMAC over body `B` only and it still matches, since the header was never part of the signed string [8](#0-7) .
4. `Registry.process` passes validation and invokes the app's handler with `WebhookMetadata` where `shop == "victim.myshopify.com"` but `body == B` (attacker-controlled), achieving cross-tenant impersonation [6](#0-5) .

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
