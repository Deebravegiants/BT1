Audit Report

## Title
JWT Replay Guard Uses Non-Atomic Check-Then-Record, Allowing Concurrent Replay of a Single JWT in HTTP Trigger Workflow Authorization - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` performs JWT replay protection by calling `h.jwtCache.isReplay(claims.ID)` and, later, `h.jwtCache.recordUsage(claims.ID)` as two separately-locked operations rather than one atomic check-and-set. [1](#0-0)  Because `isReplay` takes an `RLock` and releases it, and `recordUsage` later takes a separate `Lock`, concurrent calls carrying the identical JWT can both pass the replay check before either records usage. [2](#0-1) 

## Finding Description
`Authorize` validates the JWT signature, calls `h.jwtCache.isReplay(claims.ID)` to check for prior use, performs signer/authorized-key validation, and only afterward calls `h.jwtCache.recordUsage(claims.ID)` to mark the JWT as spent. [3](#0-2)  The `jwtReplayCache` type implements `isReplay` (RLock, read, release) and `recordUsage` (separate Lock, write, release) as independent critical sections rather than a single atomic operation. [2](#0-1)  By contrast, the Vault capability's `RequestReplayGuard.CheckAndRecord` performs the existence check and insertion under one lock, demonstrating the codebase's own correct pattern for this exact class of problem. [4](#0-3)  The gap between the two independently-locked calls in `Authorize` is a genuine TOCTOU (time-of-check-to-time-of-use) window: two concurrent calls with the same `jti` can each observe "not yet seen" in `isReplay` before either executes `recordUsage`.

## Impact Explanation
An unprivileged external caller holding one valid signed JWT for an HTTP-trigger request can send concurrent duplicate requests to the gateway; due to the non-atomic check/record gap, more than one can bypass the "each JWT usable exactly once" guarantee and be authorized, each dispatching the trigger request onward to the DON. This defeats the anti-replay control that is specifically meant to enforce single-use JWTs, enabling duplicate/unauthorized triggering of workflow executions from a single captured token — mapping to the "unauthorized job run" impact category.

## Likelihood Explanation
Exploitation only requires an unprivileged actor to fire two (or more) concurrent HTTP requests to the internet-facing trigger endpoint (`HandleUserTriggerRequest` → `Authorize`) using the same JWT — no elevated privileges, network position, or special access are needed. The race window is narrow (bounded by two mutex acquisitions in rapid succession), so exploitation is timing-dependent but realistically achievable by any remote client issuing simultaneous requests.

## Recommendation
Introduce a single atomic `CheckAndRecord(jti)` method on `jwtReplayCache` that acquires the write lock once, checks for existence, and inserts if absent — mirroring `RequestReplayGuard.CheckAndRecord`. Update `Authorize` to call this atomic method in place of the separate `isReplay`/`recordUsage` calls, eliminating the check-then-act race.

## Proof of Concept
1. Obtain one valid signed JWT for a given `req` (`jti = X`).
2. Fire two concurrent goroutines/HTTP requests calling `handler.Authorize(workflowID, tokenString, req)` with the identical token, timed so both reach the `isReplay` check before either reaches `recordUsage`.
3. Both goroutines observe `isReplay(claims.ID) == false` since neither has recorded usage yet, both pass signer/authorized-key validation, and both return successful `*gateway.AuthorizedKey` results — i.e., the same JWT is accepted twice. This can be demonstrated as a Go unit test using two goroutines invoking `Authorize` concurrently with a synchronization barrier placed to widen the window between `isReplay` and `recordUsage` (e.g., via a test-only hook or by running with `-race` and high iteration count), contrasting with the existing sequential-only "JWT replay protection" test in `workflow_metadata_handler_test.go` which does not exercise concurrency. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
