## Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant) identity that is handed to the app's webhook handler is read from an HTTP header that is never included in the signed payload. This breaks the equality that should hold between "bytes verified by HMAC" and "identity used to route/process the event," allowing a webhook legitimately received for one shop to be replayed with a forged shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header, a value that is completely separate from `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) — it never touches header fields such as shop-domain: [3](#0-2) 

`Registry.process` uses this same unauthenticated `shop` value as the tenant identity forwarded to the app's handler: [4](#0-3) 

The binding the gem should enforce is:
`bytes_covered_by_HMAC (raw_body) == bytes_that_determine_tenant_identity (shop header)`

In reality: `bytes_covered_by_HMAC (raw_body) ≠ shop header` — the header is fully attacker-controllable and unauthenticated. Any entity that has legitimately received one valid `(raw_body, hmac)` pair for their own shop (e.g., a merchant who has installed the app, and thus genuinely receives HMAC-signed webhooks for their own store) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `Utils::HmacValidator.validate` will still report the request as valid, because it only re-derives the signature from the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `shop: <victim-shop>` while it actually is a replay of the attacker's own shop's event.

### Impact Explanation
This is a cross-tenant identity-confusion vector: a party that only controls their own (unprivileged, merchant-level) tenant can cause the host application to process webhook data under a different shop's identity, without needing the app's `api_secret_key`, an access token, or any credential belonging to the victim tenant. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., for `app/uninstalled`, `shop/redact`, `customers/data_request`, or generic data-sync handlers), this can lead to state corruption, unauthorized data access, or actions being taken against the wrong tenant's account — i.e., cross-tenant access driven entirely by an unauthenticated header field.

### Likelihood Explanation
Likelihood is moderate: the attacker must be able to obtain at least one genuine `(raw_body, hmac)` pair, which any merchant using the app can obtain for their own store's webhook traffic, and must be able to submit HTTP requests to the app's public webhook endpoint with custom headers (trivial, since these are ordinary HTTP headers, not TLS-bound or otherwise protected).

### Recommendation
Include the identity-bearing header (`shop-domain`, and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before it is trusted and forwarded to the handler. At minimum, `Utils::HmacValidator` should validate a canonicalized string that incorporates the shop-domain header rather than the raw body alone, and `Webhooks::Registry.process` should reject requests where the authenticated shop cannot be established.

### Proof of Concept
1. Attacker (merchant M) installs the app and legitimately receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: m.myshopify.com` — `H` is a valid HMAC of `B` under the app's shared secret, computed by Shopify and sent to M's own endpoint (M does not need to know the secret).
2. Attacker replays the exact same body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (see `to_signable_string`), matches `H`, and returns `true`.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to treat attacker-supplied data as belonging to the victim shop.

          received_signature = verifiable_query.hmac

        end
