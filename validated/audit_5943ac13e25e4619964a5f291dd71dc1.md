### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the nominal input amount instead of the actual tokens received, causing fee-on-transfer collateral to be either stuck or to drain other users' escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` does not measure the gateway's actual token balance before/after `safeTransferFrom`. It credits `_orders[commitment][token]` with an amount derived purely from the user-supplied `order.inputs[i].amount`, unlike the canonical EVM implementation which explicitly snapshots balances to compute the amount actually received. For a fee-on-transfer (or any deflationary) ERC20 used as an order input, the gateway will record more tokens in escrow than it physically holds, exactly the same root cause reported for Teller's `CollateralManager`.

### Finding Description
In the canonical `evm/src/apps/IntentGatewayV2.sol::placeOrder`, the non-predispatch branch protects against fee-on-transfer tokens by comparing balances before and after the transfer and mutating `order.inputs[i].amount` to the actual delta: [1](#0-0) 

The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, omits this balance check entirely. It pulls tokens with `safeTransferFrom` using the caller-specified `order.inputs[i].amount`, and then credits escrow with `reducedInputs[i].amount`, which is derived only from that same nominal amount (minus protocol fee), never from the gateway's actual balance: [2](#0-1) 

The `reducedInputs` amounts used for both the commitment hash and the escrow credit are computed earlier from `order.inputs[i].amount` (the pre-transfer, nominal value) with no adjustment for a possible transfer fee: [3](#0-2) 

The identical unguarded pattern also exists in the predispatch branch, where `_orders[commitment][token] += reducedInputs[i].amount` is credited from the nominal `reducedInputs` value while `balance`/`dust` are only used to detect *excess*, not shortfall, from a fee-on-transfer skim: [4](#0-3) 

Consequently, for a token that takes a cut on transfer, the Tron gateway will hold strictly less of that token than the amount recorded in `_orders[commitment][token]`.

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow ledger consumed later during settlement/withdrawal (`withdraw()`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and from `cancelOrder`). Because the ledger overstates the gateway's real token balance for any fee-on-transfer input:
- A solver who fills the order and triggers `withdraw()` for the recorded (inflated) amount can, depending on `withdraw()`'s implementation, either revert (permanently freezing that order's funds — the order is marked filled but escrow release fails) or successfully withdraw the recorded amount by drawing down the token balance belonging to other users' outstanding orders that share the same token, since `_orders` per-commitment is only an accounting entry and the contract-wide `IERC20` balance is shared across all orders.
- This matches the reported class of bug: an inconsistency between an internal escrow accounting value and the real on-chain balance, leading to permanent freezing of funds for the affected order and/or cross-order fund shortfall/insolvency for the token's other escrowed orders.

This satisfies the "permanent freezing of funds" / unsound accounting bar for Medium/High severity, reachable by any unprivileged user calling `placeOrder` with a fee-on-transfer token.

### Likelihood Explanation
Any user can call `placeOrder` with an arbitrary ERC20 `token` address in `order.inputs`; no permissions are required and no allowlist filters transferable tokens are shown in this contract. Fee-on-transfer tokens are common in the wild, and the surrounding test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) explicitly demonstrates the project is aware of and tests for this exact scenario on the canonical EVM contract, confirming it is an anticipated, in-scope attack surface, while the Tron fork was not updated to match the fix.

### Recommendation
Apply the same balance-snapshot pattern used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: record `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` (both in the non-predispatch and predispatch branches), and use the actual delta — not the nominal `order.inputs[i].amount` — as the basis for `reducedInputs`, the commitment hash, and the `_orders[commitment][token]` credit.

### Proof of Concept
1. Deploy a 1%-fee ERC20 (`FeeOnTransferToken`, as already used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) and mint 10,000 tokens to a user on a Tron-deployed `IntentGatewayV2`.
2. User approves the gateway for `inputAmount = 1000e18` and calls `placeOrder` with that token as `order.inputs[0]`.
3. `safeTransferFrom` moves only `990e18` tokens into the gateway (1% fee lost), but because there is no balance check, `_orders[commitment][token]` is credited with `990e18` reduced only by protocol fee from the nominal `1000e18`, not from the actual `990e18` received — i.e., escrow-recorded amount exceeds the gateway's real token balance for this order once other orders in the same token also exist, or in isolation the escrow simply equals the true balance by coincidence for a single order but the accounting invariant (`sum of _orders[*][token] == balanceOf(gateway)`) is broken.
4. When a solver fills and the settlement `withdraw()` path attempts to transfer the recorded escrow amount to the solver/beneficiary, insufficient contract balance (due to the accumulated shortfall across multiple fee-on-transfer orders) causes the transfer to revert, freezing legitimately filled orders, or succeeds by consuming token balance escrowed for a different order's commitment.
