## Title
Stale operator authorization/location data reused for up to 23 hours without re-validating against the backend before authorizing user signups - (File: src/plans/mod.rs)

### Summary
The reported bug class is: a critical authorization decision (`exchangeFei`, `reweight`) reads a cached "oracle" value (price) that is never refreshed before being used to gate the operation, so the decision can be based on stale data. The same pattern exists in `orb-core`'s signup flow: once an operator QR-code is validated against the backend (`backend::operator_status::request`), the resulting `OperatorData` (including `valid`/`location_data`) is cached with a timestamp and reused for every subsequent user signup as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` — a window that defaults to **23 hours** — without ever re-querying the backend to confirm the operator is still authorized or still at the claimed location.

### Finding Description
`MasterPlan::scan_remaining_qr_codes` decides whether to reuse the previously captured `OperatorData` purely based on an elapsed-time check, never re-verifying operator status: [1](#0-0) 

The reused, unrefreshed `operator_data` (containing `location_data` fetched once by `backend::operator_status::request`) is then fed straight into `verify_user_qr_code`, which uses it — including `session_coordinates`/`stationary_location_coordinates` — to authorize the *user's* QR code against the backend, when `user_qr_validation_use_only_operator_location` is enabled (the default): [2](#0-1) [3](#0-2) 

The freshness window itself is configured by `operator_qr_expiration_time`, which defaults to 23 hours: [4](#0-3) 

This mirrors the Fei report exactly: there *is* a "staleness" check (the `elapsed() < expiration_time` comparison, analogous to the reweight fix's price-freshness gate), but the value being checked for staleness (`operator_data.valid`/`location_data`) is never actually re-fetched from the source of truth (the backend "oracle") — only the local clock is consulted. If the operator's authorization is revoked, or the operator's registered location changes, on the backend during that window, `orb-core` will continue to treat the operator (and therefore any user signups routed through `use_only_operator_location` checks) as valid for up to 23 hours, exactly as `TribeReserveStabilizer.exchangeFei` continues to use a stale FEI price until someone else happens to update the oracle.

### Impact Explanation
Because the location/validity data is not re-verified, a since-revoked or relocated operator identity can continue to be used by `orb-core` to authorize a large volume of user signups within the 23-hour cache window, i.e. misattributed/unauthorized signup authorization tied to an operator credential that the backend no longer considers valid or correctly located. This directly affects the unprivileged end-user signup flow (not an operator/malicious-node scenario), since the consequence is that ordinary users get enrolled under stale/incorrect operator attribution.

### Likelihood Explanation
The condition is triggered automatically by the normal control flow (no attacker action needed beyond continuing to run signups on the same orb session) whenever more than one user signup occurs within the `operator_qr_expiration_time` window, which is the intended common case (operator QR is meant to be scanned once and reused for many users). The only mitigating factor is that in practice the backend infrequently revokes operator status mid-session, similar to how price oracles infrequently diverge sharply in a short window — the same "partial-fix, accepted-risk" reasoning the Fei team used to justify not fixing `exchangeFei`.

### Recommendation
Re-validate the operator's status/location periodically (or before each user QR-code authorization that depends on `use_only_operator_location`) by calling `backend::operator_status::request` again instead of relying solely on the locally cached `OperatorData` and an elapsed-time check, or substantially shorten `operator_qr_expiration_time` and treat it as a hard cache-invalidation boundary rather than the sole trust anchor.

### Proof of Concept
1. Operator scans an operator QR-code; `scan_remaining_qr_codes` populates `OperatorData` from a single `backend::operator_status::request` call at time T0 (`src/plans/mod.rs:836-853`).
2. Backend operator status is revoked, or the operator's real location changes, at T0+1h.
3. Because `operator_data.timestamp.elapsed() < operator_qr_expiration_time` (up to 23h) still holds, subsequent calls to `scan_remaining_qr_codes` skip re-verification (`src/plans/mod.rs:794-820`) and reuse the stale `operator_data`.
4. `verify_user_qr_code` uses this stale `location_data` to authorize new users' QR codes against the backend (`src/plans/mod.rs:1580-1598`, `src/backend/user_status.rs:112-134`), resulting in signups being processed under operator authorization/location data that is no longer valid on the backend.

async fn do_request(
    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));
