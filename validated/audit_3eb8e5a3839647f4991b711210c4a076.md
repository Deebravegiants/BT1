### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate(request)` only proves the body's integrity, not the `shop-domain` or `topic` HTTP headers that `Registry.process` trusts to route and tenant-scope the webhook.

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over whatever `to_signable_string` returns and compares it to the `hmac` accessor on the `VerifiableQuery` object [2](#0-1) . For `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body or to each other [3](#0-2) .

`Registry.process` validates only the HMAC and then immediately trusts `request.topic` (for handler dispatch) and `request.shop` (passed straight into `WebhookMetadata` as the tenant identifier) without any secondary check that ties these header values to the signed body: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This is the exact analog class called out in scope: *"a field acted on but not covered by the HMAC."* The HMAC proves "Shopify (holder of `api_secret_key`) produced this exact body," but `Registry.process`/`WebhookMetadata` use the header-derived `shop` as if the HMAC also proved "and this body belongs to shop X." Those are two different equalities:
- What is actually verified: `HMAC(secret, raw_body) == received_hmac`
- What the app implicitly trusts: `request.shop == <shop that produced raw_body>`

Because the `shop-domain` header is outside the signed material, any party capable of relaying a previously valid `(raw_body, hmac)` pair for one shop (e.g., through webhook-forwarding infrastructure, proxies, logs, or a host application that fans a single physical HTTP endpoint out across multiple tenants using the header value to select the tenant) can substitute a different `shop-domain` header while the HMAC still validates successfully, because the signature never covered that header.

### Impact Explanation
If a host application relies on `Webhooks::Request#shop` returned by this gem as the tenant key (which is precisely what `WebhookMetadata` and the documented `WebhookHandler#handle` contract expose to consuming apps), then whoever can supply/alter the `shop-domain` header on an otherwise-valid signed webhook payload can make the app process, store, or act on data under an attacker-chosen tenant identity while HMAC validation reports success. In a multi-tenant SaaS app this is a cross-tenant data confusion/write primitive — data intended for shop A gets attributed to and merged into shop B's records, or a request that only legitimately exists for one shop is replayed to trigger side effects (e.g., `customers/redact`, `shop/redact` handlers) against an unrelated shop. This matches the Critical "cross-tenant access" impact category, since the boundary broken is exactly the shop/tenant identity binding the HMAC is supposed to protect.

### Likelihood Explanation
Exploitation does not require the `api_secret_key` or any access token — it only requires the ability to submit an HTTP request to the app's public webhook endpoint with a header value the gem does not authenticate, paired with any HMAC-valid body the attacker can obtain (e.g., a body/hmac pair from a genuine webhook delivery that was observed, replayed, or forwarded through shared infrastructure). This is a realistic condition for apps that serve many shops behind one endpoint and dispatch based on the header field this gem exposes, since the gem itself provides no protection binding header to body.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signed/verified material used by `Utils::HmacValidator`, or otherwise cryptographically bind the header-derived identifiers to the HMAC-covered body (e.g., verify a nonce/shop value embedded in the payload against the header) before `Registry.process` uses `request.shop`/`request.topic` for dispatch. At minimum, document clearly that `request.shop` and `request.topic` are unauthenticated header values and that consuming applications must independently verify shop identity (e.g., against a known/registered shop list) before trusting them for tenant-scoped operations.

### Proof of Concept
1. Attacker observes/obtains any single legitimate webhook delivery `(raw_body, shopify-hmac-sha256, shopify-shop-domain: "victim-shop.myshopify.com")` — e.g., via shared logging/proxy infrastructure that fronts a multi-tenant webhook endpoint.
2. Attacker resends the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but with `shopify-shop-domain` changed to `attacker-shop.myshopify.com` (a shop the attacker controls or wants to attribute data to).
3. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `raw_body`, which is unchanged [1](#0-0) [2](#0-1) .
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop` value, which the app treats as authenticated [4](#0-3) .
