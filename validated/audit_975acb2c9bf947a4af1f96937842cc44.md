## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` — the value that `Utils::HmacValidator` verifies against the `X-Shopify-Hmac-Sha256` header — is defined as the raw body alone. The `shop`, `topic`, `webhook_id`, and `api_version` values, all taken directly from unauthenticated HTTP headers, are never part of the signed material, yet the gem hands `request.shop` straight to the app's webhook handler as if it were an authenticated tenant identifier.

### Finding Description
`Request#to_signable_string` is implemented as: [1](#0-0) 

and `request.shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authorization to dispatch the request, and forwards the unauthenticated `request.shop` header value into `WebhookMetadata`, which is what app code is instructed to trust: [4](#0-3) 

The documented usage pattern explicitly tells integrators to key their tenant-scoped work off `data.shop`: [5](#0-4) 

Because the app's `api_secret_key` (the `client_secret`) is a single value shared across every shop that installs the app, a party who controls one legitimate install of the target app can obtain a real, validly-signed webhook (correct body + correct `hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still passes, because the shop header was never part of the signed input — breaking the identity binding: shop-header-value == shop-that-actually-authorized-this-payload.

### Impact Explanation
This is a cross-tenant data/identity confusion: an attacker-controlled shop can cause the merchant app to process webhook data under the identity of a different (victim) shop, since the gem's own `WebhookMetadata.shop` — the only tenant identifier surfaced by this library for webhook processing — is unauthenticated. Any app that follows the documented pattern (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`) will misattribute the replayed payload to the wrong tenant, enabling cross-tenant record creation/overwrite scoped by `shop`.

### Likelihood Explanation
Requires only that the attacker operate one legitimate (possibly free/dev) install of the target app to harvest a validly-signed body/HMAC pair, then send a forged HTTP request with a different shop header to the app's public webhook endpoint — no access to `api_secret_key`, tokens, or the victim's infrastructure needed.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified material for webhooks, or otherwise cryptographically bind the shop domain to the payload before it is exposed via `WebhookMetadata`, so a replayed valid HMAC cannot be reattributed to a different shop by simply changing headers.

### Proof of Concept
1. Attacker installs the target Shopify app on an attacker-owned store `attacker.myshopify.com`.
2. Attacker triggers/receives a real webhook, capturing `raw_body` and `X-Shopify-Hmac-Sha256` (valid since HMAC is computed with the app-wide `api_secret_key`, per `lib/shopify_api/utils/hmac_validator.rb`).
3. Attacker POSTs the same `raw_body`/HMAC to the app's webhook route, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC successfully (body unchanged) and calls the app handler with `shop: "victim-shop.myshopify.com"`, even though `victim-shop` never sent this webhook.

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
