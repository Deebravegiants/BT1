### Title
Fee-on-transfer tokens desync escrow accounting from actual balances in Tron IntentGatewayV2 - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits escrow (`_orders[commitment][token]`) using the user-declared `order.inputs[i].amount` (reduced only by the protocol fee), without verifying that this amount actually landed in the contract. For fee-on-transfer ERC20 tokens, the contract will record more escrow than it actually holds, causing later `withdraw()` calls to attempt transferring out amounts the contract does not have — either reverting (freezing funds/orders) or, in a multi-order scenario, draining the token balance backing other users' unrelated escrowed orders (fund theft from other order holders sharing the same token pool).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()`'s non-predispatch branch does: [1](#0-0) 
```
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            ...
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
    }
}
```
`safeTransferFrom` only guarantees the call succeeded, not that `address(this)` received exactly `order.inputs[i].amount` — for fee-on-transfer tokens (e.g. STA, PAXG, and potentially future USDC/USDT fee modes), the actual balance received will be less than requested. `reducedInputs[i].amount` is derived purely from `originalAmount = order.inputs[i].amount` minus the protocol fee percentage [2](#0-1) , with no reconciliation against actual token balance. The predispatch branch has the same flaw: it credits `_orders[commitment][token] += reducedInputs[i].amount` based on the pre-fee `requiredAmount`/`reducedInputs`, not the measured `balance` swept from the dispatcher [3](#0-2) .

This is in stark contrast to the primary EVM contract `evm/src/apps/IntentGatewayV2.sol`, which explicitly measures balance-before/balance-after around every token transfer specifically to handle fee-on-transfer tokens, and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and crediting escrow: [4](#0-3) . This fix is confirmed by dedicated fee-on-transfer tests in the test suite [5](#0-4) . The Tron variant lacks this balance-diffing logic entirely, reintroducing the exact bug class the main contract was hardened against.

When `withdraw()` is later invoked (via `fillOrder`/cross-chain settlement or cancellation), it transfers `body.tokens[i].amount` — sourced from the (over-)recorded escrow — to the beneficiary and decrements `_orders[body.commitment][token]` by that same amount: [6](#0-5) . If the contract's actual token balance is less than the sum of all outstanding escrow records (because fee-on-transfer shortfalls accumulated), a `withdraw()` for one order can consume token balance that was actually escrowed for a different order, or fail entirely, depending on withdrawal ordering.

### Impact Explanation
- **Insolvency / fund theft across orders**: Since the escrowed amount recorded for an under-collateralized order is fictitiously high, when that order is filled/cancelled and withdrawn, `token.transfer(beneficiary, amount)` pulls from the shared contract balance, which may include tokens that rightfully back other users' still-outstanding orders. Whichever `withdraw()` executes first drains real tokens that other legitimate depositors are still owed, resulting in the later depositors being unable to withdraw their entitled escrow (their transfer will fail, freezing/losing their funds) — a form of fund theft/permanent freezing traceable to a single `placeOrder()` call with a fee-on-transfer token.
- This is reachable by any unprivileged user submitting an order with a fee-on-transfer token via `placeOrder`, satisfying the "unpermissioned token bridger/intent solver" reachability requirement.

### Likelihood Explanation
Likelihood is Medium: it requires the deployment to accept an ERC20 not on an allowlist that charges a transfer fee (STA, PAXG-style, or a fee-enabled stablecoin variant). If `_params`/deployment configuration allows arbitrary ERC20 tokens as `order.inputs[i].token` without restricting to known non-fee-on-transfer tokens, any user can trigger this by simply placing an order with such a token — no special privileges needed, and the main EVM contract's own comments/tests demonstrate that fee-on-transfer tokens are an anticipated use case for this system, making the Tron variant's omission a genuine regression risk rather than a theoretical edge case.

### Recommendation
Apply the same balance-before/after reconciliation used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` (and after the predispatch sweep), and compute the protocol fee / `reducedInputs[i].amount` / escrow credit from the actually-received amount rather than the user-declared `order.inputs[i].amount`. Alternatively, maintain a token allowlist that excludes fee-on-transfer/rebasing tokens if balance reconciliation cannot be added to this variant.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 5% fee on transfer) and register it as a valid input token for the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000}`. The contract only receives 950 tokens (5% fee burned/redirected), but `reducedInputs[0].amount` is computed from `1000` (minus protocol fee), and `_orders[commitmentA][FOT] += reducedInputs[0].amount` records ~995 (assuming near-zero protocol fee) even though the contract holds only 950.
3. User B places a normal (non-fee) order with the same FOT token, contributing e.g. 500 tokens, recorded correctly as 500. Contract balance is now 950 + 500 = 1450, while total recorded escrow is 995 + 500 = 1495 — a 45-token shortfall against User A's order.
4. Order A gets filled/cancelled first and `withdraw()` transfers 995 FOT to its beneficiary, leaving the contract holding only 455 FOT.
5. Order B's `withdraw()` then attempts to transfer the recorded 500 FOT to its beneficiary but the contract only holds 455 — the transfer either reverts (permanently freezing User B's legitimate escrow) or, if executed earlier, would have succeeded at the expense of a later Order A withdrawal, demonstrating that whichever order withdraws first extracts value backed by another user's deposit.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
