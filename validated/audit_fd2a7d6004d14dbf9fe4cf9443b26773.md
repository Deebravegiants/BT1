## Title
Withdrawals can permanently revert for small residual LP balances due to floor-rounding to zero, mirroring the "stuck sub-minimum balance" bug class - (File: `program/src/processor.rs`)

## Summary
`process_withdraw` computes the coin/pc amounts a user receives for burning LP tokens using floor-rounded proportional math, and then unconditionally rejects the withdrawal if either computed output is zero. There is no fallback path (no ability to accept a smaller-than-proportional output, and no way to withdraw "everything remaining"), so a user whose residual LP balance rounds down to a zero payout for either token is permanently unable to redeem that balance — the same "trapped below an implicit minimum" pattern described in the referenced report, except here the effective minimum arises from integer rounding rather than an explicit hard-coded floor.

if a user's remaining LP balance (e.g., dust left after a partial withdrawal, or a naturally small position relative to a large/skewed pool) is small enough that `total_coin_without_take_pnl * withdraw.amount / amm.lp_amount` or the pc-side equivalent floors to `0`, then **every possible withdrawal amount up to and including their full remaining balance will always revert** with `AmmError::InvalidInput`. There is no mechanism in the contract to let the user redeem that residual balance at all — the LP tokens are functionally stuck, exactly like the `InstantManager` case where a balance below the minimum redemption threshold becomes permanently locked (absent depositing new funds to dilute the proportion problem, which forces the user to bring in unrelated capital just to unlock what is already theirs, incurring pool fee exposure in the process).

## Impact Explanation
This is a real availability/freezing issue for LP funds: a legitimate liquidity provider can end up with an LP balance they are contractually entitled to redeem for underlying coin/pc tokens, but for which `process_withdraw` will never succeed, because the payout math floors one side of the pair to zero and the processor treats that as an unconditional `InvalidInput` error. The user's only workaround is to deposit additional coin/pc into the pool to grow their LP share above the rounding threshold, which is directly analogous to the report's "deposit more to unlock the stuck balance" mitigation path, incurring extra swap/deposit fee exposure and requiring capital the user may not want to commit.

## Likelihood Explanation
This can occur naturally without any privileged action: any unprivileged liquidity provider can trigger it simply by (a) doing a partial withdrawal that leaves a small residual LP balance, or (b) depositing a very small amount relative to a large/imbalanced pool. Both are ordinary user actions reachable from a single submitted `Withdraw` transaction with attacker-chosen (their own) LP amount and standard accounts — no special build, validator behavior, or off-chain component is required.

## Recommendation
Instead of rejecting the withdrawal outright when `coin_amount == 0 || pc_amount == 0`, allow the withdrawal to still burn the LP tokens and transfer whatever non-zero side is computed (or apply ceiling rounding for the side being redeemed by the user rather than floor), or explicitly support a "close position" style instruction that lets users redeem their full remaining LP balance even when normal proportional rounding would floor to zero, similar to how the report recommends letting users withdraw balances that fall below the minimum redemption threshold.

## Proof of Concept
1. Pool has `amm.lp_amount = 10_000_000_000` and large `total_coin_without_take_pnl` / `total_pc_without_take_pnl`.
2. Alice deposits and receives a small LP balance, e.g. `user_source_lp.amount = 50` (either from a tiny deposit or as dust after a large partial withdrawal).
3. Alice calls `Withdraw` with `withdraw.amount = 50` (her entire balance).
4. `InvariantPool::exchange_pool_to_token` computes `coin_amount = total_coin_without_take_pnl * 50 / amm.lp_amount`, which floors to `0` if `total_coin_without_take_pnl < amm.lp_amount / 50`.
5. `process_withdraw` hits `if withdraw.amount == 0 || coin_amount == 0 || pc_amount == 0 { return Err(AmmError::InvalidInput.into()); }` and reverts [3](#0-2) .
6. Any `withdraw.amount` Alice picks between `1` and `50` produces the same zero-floor result, so the transaction always reverts — her 50 LP tokens are permanently unredeemable unless she deposits substantially more capital to shift the ratio.

    pub fn exchange_pool_to_token(
        &self,
        token_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())

                .unwrap()
                .as_u64()
        })
