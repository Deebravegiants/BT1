### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop` domain (and topic, webhook id, api version) come from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts `request.shop` as the tenant identity handed to the app's webhook handler once the body HMAC passes, without that identity ever being bound to the signature. An attacker who can obtain one valid `(body, hmac)` pair — e.g., by installing the app on their own shop and capturing a webhook Shopify sent to them — can replay that exact body/HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header, and the registry will process it as if it came from the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from request headers, never mixed into the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately treats `request.shop` as the authoritative tenant identity, forwarding it to the handler: [3](#0-2) 

The equality the HMAC is supposed to enforce is:
`hmac_signed(shop_claimed_in_request) == shop_acted_on_by_handler`

But the signature only binds the body bytes; it says nothing about which shop the body was delivered for. So the binding actually enforced is:
`hmac_signed(raw_body) == raw_body_received`, while `shop` is taken from an out-of-band, unsigned header and trusted anyway.

This matches the "field acted on but not covered by the HMAC" class: the `shop` value is acted on (used as the tenant key passed into `WebhookMetadata`) but is not part of the signed payload.

### Impact Explanation
Because the app-level webhook secret (`client_secret`) is shared across all shops that install the app, any attacker who is a merchant of one shop (or otherwise obtains one legitimate `(body, hmac)` pair for a topic they can trigger, such as `orders/create` or `app/uninstalled`) can forge a webhook request for a different, targeted shop by keeping the body/HMAC and swapping the `shopify-shop-domain` header. If the host application uses `WebhookMetadata#shop` to select which merchant's data/session to mutate (a documented, expected usage of this field), this allows cross-tenant data injection/manipulation without ever possessing the victim shop's access token — a cross-tenant impact.

### Likelihood Explanation
Exploitation requires only: (1) the ability to trigger a real webhook containing attacker-controlled or generic body content (trivial for topics like `app/uninstalled`, `orders/create` on the attacker's own store), and (2) sending a raw POST to the target app's public webhook endpoint with a forged shop header — no access token, no TLS interception, and no privileged access needed. This is fully reachable through the gem's documented `Webhooks::Registry.process` / `Webhooks::Request` API.

### Recommendation
Bind the tenant identity to the signed material, or otherwise re-verify it out of band: e.g., include `shop`/`topic`/`webhook_id` in the signable string in a way that mirrors Shopify's actual signing behavior, or require the host application to cross-check `request.shop` against an existing, previously-established session/installation record before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated header data and must not be trusted for authorization decisions without independent verification.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; attacker triggers a webhook (e.g. `app/uninstalled`) and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`, independent of shop).
2. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`: [4](#0-3) 
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` and performs the topic's action (e.g., wiping victim's local app data on a forged `app/uninstalled`) attributed to the victim shop, even though the request never touched Shopify's servers for that shop.
