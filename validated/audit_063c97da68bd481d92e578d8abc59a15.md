### Title
Uniswap V4 venue-pricing has no execution-cost/impact term, letting a flash-loan pool manipulation set the fill price for Simplex intent orders - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
Simplex's FX filler prices "venue-priced" pairs (curveless pairs where `token0` is a USD stablecoin) directly off the raw mid-price of a configured Uniswap V4 pool via `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, and the only defense is a static-reference deviation guard (`checkPriceGuard`/`maxDeviationBps`) in `sdk/packages/simplex/src/strategies/fx.ts`. Neither the price source nor the guard accounts for trade size, pool depth, or the actual execution cost the filler will pay to source inventory from the same pool. This mirrors the reported Slurpycoin bug class: an attacker manipulates an on-chain price source (there, a buyback mechanism; here, a Uniswap V4 pool) within tolerance and profits from the resulting mispriced trade at the counterparty's expense — sandwich/flash-loan style.

### Finding Description
`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` (lines 246-275) reads the pool's `token0Price`/`token1Price` straight from `sqrtPriceX96` with no size or slippage adjustment: [1](#0-0) 

This price feeds `resolveLegRates` in the filler strategy, which is documented as trusting the live pool with only a static-reference deviation check as protection: [2](#0-1) 

The docs explicitly state the guard "checks deviation from a static reference, not execution cost," and that "there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the whole priced quantity," and that "a venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against." The pricing docs (`pricing.mdx`) confirm the guard is optional (`referencePrice`/`maxDeviationBps` must be configured together, "omit both to leave the chain unguarded") and even when configured only rejects deviations beyond a basis-point threshold, not manipulation within that threshold: [3](#0-2) 

An attacker who places an order against a venue-priced pair can, in the same transaction bundle (flash loan), push the configured Uniswap V4 pool's price toward the edge of the allowed `maxDeviationBps` band, submit the order to be quoted/filled by the solver at that skewed price, then reverse the pool trade — extracting the difference from the solver's inventory, exactly as Slurpycoin's attacker manipulated its buyback-driven price to profit from sandwich arbitrage.

### Impact Explanation
This causes concrete value extraction from the solver (LP)'s escrowed/funded inventory on a single order: the solver fills at an attacker-favorable exchange rate it did not actually clear at, losing the spread (and potentially more) to the manipulator. Since venue-priced pairs are directly reachable by any unprivileged order placer submitting an intent through the IntentGateway/phantom order flow, and the loss is a direct, quantifiable transfer of value from LP to attacker, this qualifies as Medium severity (bounded by `maxDeviationBps` and pool liquidity/available capital for the flash loan, but real and repeatable).

### Likelihood Explanation
Exploitability requires: (1) a venue-priced pair configured without bid/ask curves (an operator choice, but explicitly supported and documented as a normal configuration), (2) a Uniswap V4 pool with liquidity thin enough to move within `maxDeviationBps` via a flash-loanable amount, and (3) the attacker being the order placer or colluding with one. Given flash loans make capital effectively free and the guard only bounds deviation from a stale reference (not real-time execution cost), this is realistically repeatable against any thin/venue-priced pair, similar to the low-cost ($3K) Slurpycoin exploit.

### Recommendation
- Price venue-priced legs using a depth-aware/impact-adjusted quote (e.g., simulate the actual swap size against the pool, or use a TWAP) rather than the instantaneous mid from `sqrtPriceX96`.
- Make `checkPriceGuard`'s reference price dynamic (e.g., a recent TWAP or external oracle) instead of a static operator-set value, and consider tightening `maxDeviationBps` or basing it on order size.
- Account for the pool's own fee tier when the solver must source inventory by swapping through the same pool, so the guard reflects the LP's real economics rather than a manipulation-agnostic mid.

### Proof of Concept
1. Solver configures a venue-priced pair (e.g., `[[pairs]] token0=USDC, token1=EXOTIC`) with `[vault.uniswapV4]` position(s) and no bid/ask curves, with `referencePrice`/`maxDeviationBps` set per docs.
2. Attacker takes a flash loan and swaps a large amount through the configured Uniswap V4 pool, moving `sqrtPriceX96` so `computeDirectPoolPriceUsd` reports a price skewed to just within `maxDeviationBps` of the operator's static `referencePrice`.
3. Attacker (or a colluding party) submits an intent order against that pair; `resolveLegRates` → `getExoticTokenPrice` reads the manipulated pool price, passes `checkPriceGuard`, and the solver fills at the skewed rate — `computeLegPolicyOutput` linearly extends the manipulated mid across the whole order size with no impact discount.
4. Attacker reverses the initial pool swap and repays the flash loan, net-profiting from the spread between the manipulated fill price and the pool's true price — analogous to the Slurpycoin buyback-manipulation sandwich attack.

Note: I could not fully trace `checkPriceGuard`'s exact implementation (its body wasn't returned before the tool budget ran out), so the exact bound/rounding behavior of the deviation check is based on the docstring/flow-doc description rather than direct code inspection; a full review of `sdk/packages/simplex/src/strategies/fx.ts`'s `checkPriceGuard` function is recommended to confirm precise guard semantics.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
