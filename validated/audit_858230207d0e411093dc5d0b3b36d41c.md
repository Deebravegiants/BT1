### Title
`request.topic`/`request.shop` drive dispatch and handler data while being absent from `to_signable_string`, so the HMAC never covers them - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, never including the `topic`, `shop-domain`, `api-version`, or `webhook-id` headers. [1](#0-0)  `Registry.process` validates the HMAC over that signable string, but then dispatches the handler and builds `WebhookMetadata` using `request.topic` and `request.shop`, both pulled straight from unauthenticated headers. [2](#0-1)  The base64-padding leniency of `Base64.decode64` in `#hmac` is not itself exploitable, since `OpenSSL.secure_compare` still requires the decoded bytes to match a correctly HMAC'd value. [3](#0-2) [4](#0-3) 

### Finding Description
The binding the invariant claims should hold is: `signed_bytes(hmac) == f(topic, shop, api_version, webhook_id, raw_body)`. In fact `to_signable_string` returns `@raw_body` alone: [1](#0-0) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`, i.e. it authenticates `raw_body` only. [4](#0-3)  `Registry.process` then uses `request.topic` (unauthenticated) to select the handler from `@registry`, and passes `request.shop`, `request.topic`, `request.api_version`, `request.webhook_id` (all unauthenticated) into `WebhookMetadata` handed to the app's handler. [2](#0-1) 

Given the stated threat model — the attacker can register their own dev shop, receive a legitimately signed webhook (a valid `raw_body` + correctly computed `hmac`), and fully controls headers/body/ordering of the request they send to the app's public webhook endpoint — they can take that one genuine `(raw_body, hmac)` pair and replay it to the same endpoint with a different `x-shopify-shop-domain` and/or `x-shopify-topic` header. Because the HMAC only covers `raw_body`, `HmacValidator.validate` still returns `true` for the replayed request, and `Registry.process` will dispatch to whatever handler is registered for the forged `topic`, and hand the handler a forged `shop` value in `WebhookMetadata`. Nothing in `Request#initialize` (header presence check only, no header authentication) or `Registry.process` (HMAC check happens before dispatch, but the check itself never covers the dispatch key) closes this gap. [5](#0-4) 

This matches the existing test setup, which builds the HMAC only over the raw body (`"{}"`) while independently setting `x-shopify-topic`/`x-shopify-shop-domain` in the headers hash and asserting the handler receives those header values — i.e., the test suite itself demonstrates that topic/shop are trusted independent of the signature. [6](#0-5) [7](#0-6) 

### Impact Explanation
An app that relies on `WebhookMetadata#shop`/`#topic` to route data or associate it with a merchant (a documented and expected usage pattern) can be handed a forged shop identity or forged topic while the request still "passes" HMAC validation, because that validation never covered those fields. This is a cross-tenant confusion primitive: one shop's genuinely-signed webhook body can be replayed and relabeled as belonging to another shop or another topic. The severity depends on what the app does with `shop`/`topic` downstream (e.g., writing data keyed by `shop`, or invoking a different, more sensitive handler such as `customers/data_request` or `shop/redact`), which is outside this gem, but the gem provides no barrier to it.

### Likelihood Explanation
Requires only that the attacker (a) has one legitimately signed webhook (achievable via a self-owned development shop) and (b) can POST directly to the app's public webhook endpoint with arbitrary headers, both of which are within the stated threat model. No secret key is ever needed. Repeatable indefinitely, and against any shop/topic combination the attacker chooses, as long as the app's endpoint doesn't perform its own independent shop/topic authentication (which this gem does not provide and does not document as necessary).

### Recommendation
Include `topic`, `shop`, `api_version`, and `webhook_id` (all values later trusted by `Registry.process`/`WebhookMetadata`) in the string passed to `HmacValidator`, or otherwise bind the HMAC check to the specific dispatch key before trusting it — e.g. change `to_signable_string` to canonicalize and include these headers, or have `Registry.process` independently verify `request.shop` against session/tenant data before dispatch.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb style addition
def test_process_replay_with_forged_shop_and_topic_passes_hmac
  raw_body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
  signed_hmac_header = Base64.encode64(hmac)

  handler_shops = []
  handler = TestHelpers::FakeWebhookHandler.new(
    lambda { |data| handler_shops << data.shop },
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
  )

  # Same raw_body + same valid hmac, two different (attacker-supplied) shop headers
  req1 = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => signed_hmac_header,
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
    },
  )
  req2 = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => signed_hmac_header,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    },
  )

  ShopifyAPI::Webhooks::Registry.process(req1)
  ShopifyAPI::Webhooks::Registry.process(req2)

  # Both requests pass HMAC validation and reach the handler with two different,
  # unauthenticated "shop" values for the exact same signed body/hmac pair.
  assert_equal(["victim-shop.myshopify.com", "attacker-shop.myshopify.com"], handler_shops)
end
```
This demonstrates that `HmacValidator.validate` (via `to_signable_string` returning only `@raw_body`) is satisfied for both requests despite the `shop` (and equivalently `topic`) header differing and being fully attacker-controlled, confirming the signature-coverage gap.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
