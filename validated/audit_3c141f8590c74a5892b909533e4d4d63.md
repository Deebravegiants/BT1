Confirmed: `WebhookMetadata.shop` (used by every app's `WebhookHandler#handle`) is populated directly from `request.shop`, which reads the raw `shopify-shop-domain` / `x-shopify-shop-domain` header, and `Registry.process` only validates the HMAC before dispatching this metadata to the handler.### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then dispatches to the app's handler a `WebhookMetadata` struct whose `shop` field is taken verbatim from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header. That header is never included in the signed bytes, so the binding "HMAC-verified bytes == the shop this webhook is attributed to" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight out of unauthenticated headers: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes and compares the HMAC only against `verifiable_query.to_signable_string` (i.e., the raw body): [4](#0-3) 

`Registry.process` performs exactly this HMAC check and then immediately builds `WebhookMetadata` using `request.shop` (the header) as the tenant identifier passed to the app's `WebhookHandler#handle`: [5](#0-4) [6](#0-5) 

The identity binding that breaks: `hmac-verified byte-range == "shop" field the application trusts and acts on`. In fact only the request body is inside the verified byte-range; the `shop` field consumed by every host application's handler comes from a header that sits entirely outside it.

Because the HMAC is a pure function of `(secret, raw_body)`, any `(raw_body, hmac)` pair that was legitimately generated by Shopify for **one** shop remains a valid signature for that same body no matter what `shop-domain` header accompanies it. A user who is a legitimate (unprivileged) merchant/tenant on Shop A can trigger events in their own store to produce webhook deliveries with attacker-influenced body content and a Shopify-computed, valid HMAC. That exact `(body, hmac)` pair can then be POSTed directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to Shop B (a different, victim tenant of the same app). `Registry.process` will accept it — HMAC checks out — and hand the handler a `WebhookMetadata` claiming the data belongs to Shop B, even though it never came from Shopify for Shop B.

### Impact Explanation
This is a cross-tenant data/identity confusion: an app built on this gem, following its documented API (`Registry.process`), cannot distinguish a genuine webhook for Shop B from a replayed, validly-signed webhook for Shop A with a forged shop-domain header. Any handler that uses `data.shop` to select which tenant's records to create/update/delete (a standard and expected use of `WebhookMetadata.shop` per this gem's own documented contract) can be made to write attacker-influenced webhook payloads into another merchant's tenant context. This matches the "cross-tenant access" Critical-impact category, since the compromise crosses a tenant boundary the gem is expected to enforce as part of its webhook-authentication API.

### Likelihood Explanation
Requires only: (1) being an unprivileged merchant who has the app installed on any shop (standard onboarding, no elevated privilege), (2) triggering a webhook-eligible action in one's own store to obtain a valid `(body, hmac)` pair, and (3) sending a direct HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or TLS interception is needed — the header is simply never covered by the signature the gem itself computes.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`api-version`) header bytes in the signable payload used for HMAC verification, or otherwise cryptographically bind the shop the webhook is attributed to (e.g., have `Registry.process` require the caller to supply/verify the expected shop out-of-band, or reconstruct the signable string as `shop-domain header + raw_body` matching Shopify's actual signing contract if this differs from official documentation). At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated and must not be used as a tenant-routing key without additional verification.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant of shop-a.myshopify.com with the app installed.
# They perform an action that fires a real webhook, capturing the exact raw body
# Shopify sent and its accompanying x-shopify-hmac-sha256 value (both are visible
# to them since it's their own shop's webhook delivery, or they can predict/control
# `raw_body` if their store data ends up in it, e.g. product titles).

raw_body = captured_raw_body        # legitimately delivered for shop-a.myshopify.com
valid_hmac_b64 = captured_hmac_header

# Attacker POSTs directly to the app's public webhook endpoint,
# reusing the valid (body, hmac) pair but claiming a different shop:
headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "shop-b.myshopify.com",  # victim tenant, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (Utils::HmacValidator.validate only checks raw_body).
# => The registered handler receives WebhookMetadata(shop: "shop-b.myshopify.com", ...)
#    even though the payload never originated from shop-b.
```
