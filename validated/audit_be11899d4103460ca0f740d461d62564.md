### Title
Panic-inducing unchecked subtraction in `calc_take_pnl`'s stale PnL cache can permanently freeze LP funds - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` relies on a persisted "last-k" cache (`TargetOrders.calc_pnl_x` / `calc_pnl_y`) that is compared against live vault balances only via a *product* (`x*y`) invariant check, then subjected to unconditional per-component `checked_sub().unwrap()` operations. This is directly analogous to the MariaDB `used_tables_and_const_cache` class of bug: a cached/derived value is trusted to stay consistent with live state across statements, and when a crafted sequence of inputs desynchronizes the cache from reality, the unguarded assumption trips an unrecoverable panic instead of a graceful error, causing a denial of service that this codebase's persistence model turns into a *permanent* freeze rather than a one-shot crash.

### Finding Description
`Processor::calc_take_pnl` [1](#0-0)  is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all reachable by unprivileged users with attacker-chosen amounts [2](#0-1) [3](#0-2) [4](#0-3) .

The function loads the persisted "cache" values `target.calc_pnl_x` / `target.calc_pnl_y` from the `TargetOrders` account [5](#0-4)  and validates only that the *product* of the current vault totals is `>=` the product of the cached values: [6](#0-5) 

If that aggregate check passes, it proceeds to compute `x2` via integer square root and `y2` via `x2 * y1 / x1`, then performs **unconditional, per-component** subtractions with `.unwrap()`: [7](#0-6) 

The guard only bounds the *product* `x1*y1` against `calc_pnl_x*calc_pnl_y`; it does not independently guarantee `x2 <= x1` and `y2 <= y1`. Because `x2` is derived through `integer_sqrt()` and `y2` through a `checked_div`, and because the cache (`calc_pnl_x`/`calc_pnl_y`) is itself repeatedly updated by chained `checked_add`/`checked_sub().unwrap()` arithmetic on every Deposit and Withdraw call [8](#0-7) [9](#0-8) [10](#0-9) , rounding drift accumulates across attacker-controlled sequences of small/large deposits and withdrawals. A crafted sequence can push the cached `calc_pnl_x`/`calc_pnl_y` state into a configuration where the product-level check still passes but the per-axis subtraction underflows, triggering the `.unwrap()` panic.

Unlike a single failed transaction, this panic is a permanent bug for the pool: `calc_take_pnl` is called unconditionally on **every** subsequent Deposit, most Withdraw calls (unless status is `WithdrawOnly`), and every `WithdrawPnl` for that same `AmmInfo`/`TargetOrders` pair, using the exact same persisted, unrecoverable cache state [11](#0-10) . Once the corrupted state is reached, every subsequent call into this code path panics deterministically, since there is no instruction to reset or repair `calc_pnl_x`/`calc_pnl_y` independent of this same vulnerable arithmetic.

### Impact Explanation
Once the divergence condition is reached, all Deposit, Withdraw (outside `WithdrawOnly`), and WithdrawPnl instructions for the affected pool deterministically panic and abort. This permanently freezes LP funds in the vaults and freezes protocol PnL funds, since there is no other instruction path that bypasses `calc_take_pnl` to recover the pool to a working state. This matches the required "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
The path is reachable by any unprivileged user through the ordinary Deposit/Withdraw instructions with attacker-chosen deposit/withdraw amounts, executed in a chosen sequence to accumulate rounding drift between the persisted `calc_pnl_x`/`calc_pnl_y` cache and the true vault ratio. No privileged signer, leaked key, or off-chain component is required — only ordinary transactions with attacker-controlled instruction data. Because the guard in `calc_take_pnl` checks only the aggregate product and not the per-axis relationship, exploitability depends on finding vault-ratio/deposit-amount combinations where sqrt/division rounding causes `x2 > x1` or `y2 > y1`; this is a real, but data-dependent, precondition, so likelihood is assessed as Medium rather than trivially deterministic on the first transaction.

### Recommendation
Replace the unconditional `.unwrap()` subtractions in `calc_take_pnl` for `diff_x`/`diff_y` with `checked_sub` that returns a program error (e.g. `AmmError::CalcPnlError`) instead of panicking, and add an explicit invariant check that `x2 <= x1` and `y2 <= y1` before computing `diff_x`/`diff_y`, in addition to the existing product check. This converts a panic-based permanent DoS into a graceful, recoverable error path.

### Proof of Concept
1. Create a pool via `Initialize2` with two token mints, establishing an initial `calc_pnl_x` / `calc_pnl_y` cache in `TargetOrders` equal to the initial normalized vault reserves.
2. Perform a sequence of `Deposit` and `Withdraw` calls with attacker-chosen `amount`/`min` values chosen to skew the ratio of `total_pc_without_take_pnl` : `total_coin_without_take_pnl` relative to `calc_pnl_x` : `calc_pnl_y`, while keeping the aggregate product check `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` satisfied (verifiable off-chain by simulating `Calculator::calc_x_power`/`integer_sqrt`/`checked_div` with the exact fixed-point arithmetic used in `program/src/math.rs`).
3. Once a combination is found where the per-axis check `x1.checked_sub(x2)` or `y1.checked_sub(y2)` underflows, submit the triggering Deposit/Withdraw transaction; the program panics inside `calc_take_pnl`.
4. Observe that all further Deposit/Withdraw/WithdrawPnl transactions against the same `AmmInfo`/`TargetOrders` pair panic identically, since the corrupted cache state persists on-chain and is re-used by `calc_take_pnl` on every call.
