### Title
Webhook `shop` field is trusted from an HTTP header but is not covered by the HMAC signature, breaking the tenant-binding invariant - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `X-Shopify-Shop-Domain` HTTP header, but `to_signable_string` (the data over which the HMAC is verified) only returns the raw request body. `shop` never enters the signature computation, so `Registry.process` accepts the header-supplied `shop` value as authentic tenant identity as long as the body's HMAC checks out, even though the header itself carries no cryptographic binding to that body.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against `verifiable_query.hmac` [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `Request#shop` is parsed straight out of the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed payload [3](#0-2) .

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` to build `WebhookMetadata` that is handed to the app's `WebhookHandler#handle` as the tenant identity for this event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This is the same bug class as the referenced report: a field that is *acted on* (here, `shop`, used to route/attribute the webhook to a tenant) is not *covered by the HMAC* that's supposed to authenticate the whole request. The equality that should hold is:

`shop_bound_by_signature == shop_used_by_handler`

but in this implementation:

`shop_bound_by_signature (∅, not signed) ≠ shop_used_by_handler (header value)`

Because HMAC only covers the raw body, an attacker who can replay or forge a genuine, previously-observed valid `(body, hmac)` pair (e.g. captured from their own store's legitimate webhook, or any publicly-observable webhook payload/HMAC pairing) can resubmit it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still pass because it only checks the body against the HMAC — it never checks that the `shop` header matches the tenant the HMAC was actually generated for.

### Impact Explanation
If an application's `WebhookHandler#handle` implementation uses `data.shop` (as documented/intended by the gem's `WebhookMetadata`) to determine which merchant/tenant record to update, delete, or read (a very common integration pattern, e.g. `customers/redact`, `shop/redact`, `orders/*`), an attacker who can obtain any one valid `(raw_body, hmac)` pair can relabel it to point at a different shop domain and have the host application act on/against that shop's tenant data — a cross-tenant access condition. This matches the Critical bucket: "cross-tenant access" caused entirely by this gem's own trust boundary (the gem hands the header-derived `shop` to the handler as if it were authenticated, when only the body was authenticated).

### Likelihood Explanation
Exploitability requires only the ability to send an HTTP POST to the app's webhook endpoint (no access token, no `api_secret_key`, no privileged account) plus knowledge of one valid `(body, hmac)` pair for the target's app — which is often obtainable by an attacker who owns/controls their own installed shop (a legitimate merchant of the app) and simply captures their own outbound webhook traffic, then replays it against the same endpoint with a spoofed `shop` header to impersonate a different tenant. This requires no interception of TLS and no secret material.

### Recommendation
- **Short term:** Include the `shop` domain (and ideally `topic`, `webhook_id`, `api_version`) explicitly in `to_signable_string`, or independently verify that the header `shop` matches an app-tracked shop that legitimately corresponds to this HMAC/webhook subscription before constructing `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be used to resolve tenant scope without additional verification (e.g., cross-checking against the shop associated with the offline access token/session on file).
- **Long term:** Add regression tests asserting that tampering with the `shop`, `topic`, or `webhook_id` header while keeping the body/HMAC valid causes `Registry.process` to fail (mirrors the "regression bug... should have been caught by a comprehensive test suite" lesson from the referenced report).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and configure a webhook subscription (e.g., `customers/redact`) via the gem.
2. Capture one legitimate delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), plus header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only hashes `B` [2](#0-1) ; `Registry.process` proceeds and calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) .
5. If the host app's handler trusts `data.shop` to select which tenant's data to modify (the documented purpose of `WebhookMetadata#shop`), the attacker has caused a cross-tenant write/deletion using only their own webhook traffic.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
