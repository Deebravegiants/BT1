Audit Report

## Title
Post-expiry state corruption permanently locks staked funds in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`update_pool_rewards` unconditionally sets `last_update_block` to `T::BlockNumberProvider::current_block_number()` instead of the capped value `last_block_reward_applicable(pool_info.expiry_block)` that was actually used to compute `reward_per_token`. Once a pool's expiry has passed and any staker interacts with it (via `stake`, `unstake`, or `harvest_rewards`), `last_update_block` becomes greater than `expiry_block`, permanently poisoning the pool state.

## Finding Description
`reward_per_token` bounds reward accrual using `Self::last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?`. [1](#0-0) 
`last_block_reward_applicable` returns `min(now, expiry_block)`. [2](#0-1) 
However, `update_pool_rewards`, which persists the state consumed by the next call to `reward_per_token`, writes the raw current block number rather than this capped value: [3](#0-2) 

Both `unstake` and `harvest_rewards` explicitly permit calls after expiry (`ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin)`), and both invoke `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`. [4](#0-3) [5](#0-4) 

Once one such call succeeds post-expiry, `last_update_block` is set to `now > expiry_block`. On the next call, if `total_tokens_staked` is still non-zero, `reward_per_token` computes `last_block_reward_applicable(expiry_block) = expiry_block`, and `expiry_block.ensure_sub(last_update_block)` underflows (since `last_update_block > expiry_block`), returning an `Err` propagated via `?`. This causes `stake`, `unstake`, and `harvest_rewards` to fail deterministically for any staker until the admin extends the expiry via `set_pool_expiry_block`, which is the only path that re-derives and re-caps `last_update_block` correctly (since it also calls `update_pool_rewards`, but at that point `now < new_expiry_block`, so `current_block_number()` happens to equal the capped value again — this masks the bug only when an extension is made). [6](#0-5) 

The only guard here is the early return in `reward_per_token` for `total_tokens_staked.is_zero()`, which skips the subtraction entirely — but this only avoids the bug if the pool has been fully emptied, not for any pool that still has staked tokens after the first post-expiry interaction. [7](#0-6) 

## Impact Explanation
This is a genuine, unprivileged, permissionless-reachable accounting/state-transition bug. Staked assets remain frozen under `FreezeReason::Staked` and become unrecoverable through the pallet's normal `unstake` path for any staker who is not first to interact with the pool after expiry, and the pool becomes permanently stuck unless the admin proactively extends `expiry_block`. This matches a genuine fund-freeze/DoS impact class, not merely a cosmetic or gas issue, and does not require any privileged or malicious actor — only two ordinary, unprivileged users interacting with a normally-expiring pool (the pallet's expected end-of-life scenario, given `cleanup_pool` exists specifically for pools that have concluded).

## Likelihood Explanation
High. Any pool that is allowed to reach genuine expiry (not perpetually extended by an admin) and has more than one staker (or a staker performing multiple partial unstakes) will hit this deterministically: the first post-expiry `unstake`/`harvest_rewards`/`stake` call succeeds and poisons `last_update_block`; every subsequent call to `stake`, `unstake`, or `harvest_rewards` on that pool fails with an arithmetic underflow via `ensure_sub` in `reward_per_token`. No special timing, front-running, or governance/mocked path is required.

## Recommendation
In `update_pool_rewards`, set `last_update_block` to `Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the unconditional current block number, keeping it consistent with the value used in the reward computation:
```rust
new_pool_info.last_update_block = Self::last_block_reward_applicable(pool_info.expiry_block);
```

## Proof of Concept
1. Create a pool with `expiry_block = 25`, non-zero `reward_rate_per_block`.
2. Two stakers stake into the pool before expiry (`total_tokens_staked > 0`).
3. Advance to a block number well past expiry (e.g., block 200), with no admin call to `set_pool_expiry_block`.
4. Staker 1 calls `unstake` (or `harvest_rewards`) for a partial amount, leaving `total_tokens_staked > 0`. This call succeeds, and `update_pool_rewards` sets `Pools::<T>::get(pool_id).last_update_block = 200` (`> expiry_block = 25`).
5. Advance a few more blocks (e.g., block 210). Staker 1 or Staker 2 calls `unstake`/`harvest_rewards`/`stake` again on the same pool.
6. `reward_per_token` computes `last_block_reward_applicable(25) = 25`, then `25.ensure_sub(200)` underflows, returning `ArithmeticError::Underflow`, propagated via `?` through `update_pool_and_staker_rewards`, causing the extrinsic to fail with a `DispatchError`. This traps the remaining staked funds behind a permanently-failing call path until the admin extends `expiry_block`.

	fn set_pool_expiry_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_expiry: DispatchTime<BlockNumberFor<T>>,
	) -> DispatchResult {
		let now = T::BlockNumberProvider::current_block_number();
		let new_expiry_block = new_expiry.evaluate(now);
		ensure!(new_expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(new_expiry_block > pool_info.expiry_block, Error::<T>::ExpiryCut);

		// Always start by updating the pool rewards.
		let reward_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, reward_per_token)?;

		pool_info.expiry_block = new_expiry_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolExpiryBlockModified { pool_id, new_expiry_block });

		Ok(())
	}
