No dedicated tests exist for `CallDispatcher.sol` covering reentrancy or allowance persistence — confirming this is unguarded. I have sufficient evidence to produce the finding.

### Title
Shared, unauthenticated `CallDispatcher` allows any order/message to steal ERC-20 tokens left approved or transiently held by unrelated orders - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a public, access-control-free function on a single shared contract instance used by every `IntentGatewayV2`/`IntentsBase` order (predispatch and postdispatch calldata) and by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment (calldata execution after mint/unlock) on a chain. Because the dispatcher is a stateless pass-through executed with no scoping to a specific order, commitment, or caller, any user-supplied `Call[]` (fully attacker-controlled, since it is part of an order's `predispatch.call`/`output.call` or an HFT message's `data` field) can leave a persistent ERC-20 `approve()` from the dispatcher to an attacker-controlled spender. Any later, unrelated order or bridge transfer that temporarily routes the same token through the shared dispatcher (a normal, documented usage pattern) will have its funds pulled out via that dangling allowance before the legitimate sweep/transfer-back step runs. This mirrors the reported Vault.sol issue: a broadly-scoped permission (there, `userApprovedContracts`; here, ERC-20 allowances granted from the dispatcher's own address) is not scoped to the specific interaction that justified it, so any "malicious pair" (order) sharing the same trusted intermediary can steal another party's temporarily-custodied tokens.

### Finding Description
`CallDispatcher` has no caller restriction at all: [1](#0-0) 

It is invoked from multiple, mutually-untrusted call sites that route real user funds through it. `IntentGatewayV2`/`IntentsBase` transfer predispatch input assets into the dispatcher, run the order-creator-supplied `order.predispatch.call`, then sweep whatever balance the dispatcher now holds back to the gateway: [2](#0-1) [3](#0-2) 

Postdispatch calldata execution follows the same pattern — the dispatcher's calls are executed, then residual token balances of the dispatcher are swept as "dust": [4](#0-3) 

`HyperFungibleToken`/`WrappedHyperFungibleToken` mint or unlock tokens directly to the dispatcher and then forward arbitrary sender-supplied calldata to it for execution, explicitly to let that calldata spend the just-delivered tokens (e.g. approve + swap): [5](#0-4) 

Because `dispatch()` performs a raw `to.call(call.data)` from the dispatcher's own address with no allowance-cleanup, no nonce, and no restriction on `to`, any user's calldata can call `SomeToken.approve(attackerSpender, type(uint256).max)` on behalf of the dispatcher. That approval is written into `SomeToken`'s persistent storage keyed by `(dispatcher, attackerSpender)` and survives after this dispatch call returns — it is not undone by the later "sweep the current balance" step, because a sweep only moves balance, it does not revoke allowances. The protocol's own documentation acknowledges the resulting risk without any code-level mitigation: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." [6](#0-5) 

Since the same `CallDispatcher` instance is shared across every `IntentGatewayV2` order, every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment, and any third-party app that also references the published dispatcher address, the dangling allowance is not scoped to the order/message that created it. Any subsequent, unrelated interaction that transiently sends the same ERC-20 token into the dispatcher — a normal predispatch step of some other user's order, or a normal HFT mint-to-dispatcher for calldata execution — briefly gives the dispatcher a nonzero balance of that token while the attacker's spender already holds an unlimited allowance over it. The attacker's spender contract can then call `transferFrom(dispatcher, attacker, amount)` at any point after that balance appears (even outside the victim's transaction, since the allowance is durable state, not a transient one) and drain it before the victim's own sweep/transfer-back call executes, or immediately after it, whenever the dispatcher next holds that token.

### Impact Explanation
This allows outright theft of ERC-20 tokens that legitimately, if only temporarily, pass through the shared `CallDispatcher` — including a victim's escrowed order inputs (`predispatch.assets`), fill outputs routed through post-fill calldata, and freshly minted/unlocked cross-chain-bridged tokens awaiting calldata execution. Because the dispatcher is reused indefinitely across all orders and all HFT deployments on a chain, a single malicious order placed once is enough to plant a durable, unlimited allowance that can later be exploited against many unrelated victims whose transactions happen to route the same token through the dispatcher. This is a concrete theft-of-funds vulnerability, not merely a griefing or resource issue.

### Likelihood Explanation
The attack requires only placing a single, ordinary Intent Gateway order (or triggering any HFT bridge message) with a `predispatch.call`/`output.call`/`data` field that includes one extra `approve()` call targeting a token the attacker wants to farm — no privileged access, no governance, and no protocol bug beyond the missing allowance hygiene is needed. `CallDispatcher.dispatch` has no caller check, so the attacker's spender contract can call `transferFrom` at will once a target token transiently lands in the dispatcher. The likelihood is elevated by the fact that this is a documented, known risk pattern (per the HFT docs' explicit warning) that the code does nothing to prevent, and stablecoins/common tokens routed through predispatch/postdispatch swaps are exactly the assets most likely to be shared across many orders on the same dispatcher.

### Recommendation
- **Short term:** Warn integrators/users prominently (beyond the current HFT-only note) that any `Call[]` submitted to `IntentGatewayV2` (`predispatch.call`, `output.call`) or to any HFT `data` field must never leave a non-zero allowance from the `CallDispatcher` address, and recommend `approve(spender, 0)` cleanup calls appended to every batch that grants an allowance.
- **Long term:** Enforce allowance hygiene at the protocol level — e.g., have `CallDispatcher.dispatch` snapshot and revoke (`approve(_, 0)`) any allowance it granted to a target during the same call before returning, or deploy per-order/per-message ephemeral dispatcher instances (via `CREATE2`/minimal proxy, self-destructing or otherwise unusable after one dispatch) so no allowance state can outlive the transaction that created it.

### Proof of Concept
1. Attacker deploys `EvilSpender`, a contract with a function `drain(address token, address dispatcher)` that calls `IERC20(token).transferFrom(dispatcher, attacker, IERC20(token).balanceOf(dispatcher))`.
2. Attacker places an `IntentGatewayV2` order whose `predispatch.assets` is empty/minimal but whose `predispatch.call` is `abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, address(EvilSpender), type(uint256).max)})])`. `placeOrder` executes this via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, leaving `USDC.allowance(dispatcher, EvilSpender) == type(uint256).max` permanently, per [7](#0-6) .
3. At any later time, a victim places an unrelated order with USDC as a `predispatch.assets` input; `placeOrder` transfers the victim's USDC into the shared `dispatcher` before running the victim's own `predispatch.call` and before sweeping it back to the gateway, per [3](#0-2) .
4. Attacker calls `EvilSpender.drain(USDC, dispatcher)` (front-running or simply racing the victim's sweep-back transaction, or targeting any brief window where the dispatcher holds a USDC balance from any HFT/IntentGateway flow), pulling the victim's escrowed USDC to the attacker's address via the still-outstanding allowance from step 2.
5. The victim's `placeOrder`/sweep subsequently reverts or under-escrows, and the funds are irretrievably in the attacker's control.

                revert NotContract(to);
            }

        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
