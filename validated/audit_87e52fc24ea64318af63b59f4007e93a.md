### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` used to dispatch a webhook handler purely from unauthenticated HTTP headers, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Any actor who can produce one genuine `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own free/dev store — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, and the signature will still validate.

### Finding Description
`Registry.process` authenticates a webhook solely via the body HMAC: [1](#0-0) 

`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string`, which for a webhook request is only the raw JSON body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from attacker-controllable headers and are never part of the signed material: [3](#0-2) 

The binding that should hold is: `HMAC(raw_body, api_secret_key) valid` ⇒ `shop header == shop that actually produced raw_body`. Because `to_signable_string` only returns `@raw_body`, this equality is never enforced — the HMAC only proves "some request was produced with the correct secret for this body," not "this body belongs to this shop." `Registry.process` then forwards the untrusted `request.shop` straight into `WebhookMetadata`, which the host application's webhook handler treats as the identity of the tenant the event belongs to: [1](#0-0) 

### Impact Explanation
An attacker who has ever received one legitimate webhook for their own (attacker-owned) shop — trivially achieved by installing the app on a free development store and triggering any webhook topic — can capture that exact `(raw_body, x-shopify-hmac-sha256)` pair. They can then POST it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop's domain. `HmacValidator.validate` will accept it because the HMAC never covered the shop field, and the host application's handler will process the payload as an authentic event for the victim shop. Depending on what the app does with webhook data (e.g. `app/uninstalled`, GDPR, `shop/update`, order/customer webhooks), this enables cross-tenant data corruption or spoofed business events attributed to a shop the attacker never controls.

### Likelihood Explanation
Webhook endpoints must be publicly reachable HTTP(S) URLs by design, so no credential, access token, or `api_secret_key` is needed to reach them. The only prerequisite is possession of one authentic `(body, hmac)` pair, which any developer can obtain for free by installing the app themselves. This is a low-effort, self-service attack path.

### Recommendation
Bind the tenant identity into the verified signable material, or otherwise cryptographically tie the `shop-domain` header to the specific webhook subscription/body being validated (e.g., look up the webhook by `webhook_id` and compare against a shop recorded when the webhook was registered, or include `shop`/`topic` in the value that is HMAC-verified) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; trigger any webhook (e.g. `app/uninstalled`) to capture a genuine `raw_body` and its `x-shopify-hmac-sha256` value.
2. POST that exact `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and the desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks the body against the secret; the handler executes with `shop == "victim-shop.myshopify.com"`, spoofing a webhook for a shop the attacker does not own. [1](#0-0)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
