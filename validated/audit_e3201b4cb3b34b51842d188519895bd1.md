### Title
Batch withdrawals of the same asset via PoA Bridge report the wrong destination tx hash/status - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the shared `waitForWithdrawalCompletion()` helper resolve the status of a specific withdrawal (identified by `index` within a batch) using `findMatchingWithdrawal()`, which matches only on `assetId`/`near_token_id`, ignoring `index`, `amount`, and `destinationAddress`. When a single NEAR transaction contains two or more withdrawals of the same token (a supported "Batch Withdrawals" use case per the SDK's own README), the function will return the *first* withdrawal in an admittedly unsorted API response array that matches the asset — which may not be the withdrawal the caller actually asked about.

### Finding Description
`createWithdrawalIdentifier()` builds a `WithdrawalIdentifier` that carries `index`, but `describeWithdrawal()` never uses `index` to disambiguate between multiple withdrawals of the same asset in one tx: [1](#0-0) 

The matching function's own docstring acknowledges the gap: [2](#0-1) 

The same limitation exists in the sibling implementation used by `waitForWithdrawalCompletion()`: [3](#0-2) 

This breaks the equality "status/hash reported == actual on-chain outcome for *that specific* withdrawal instance." If a batch contains two withdrawals of the same `nep141` asset (e.g., two different destination addresses, or two different amounts of `usdc.omft.near`), calling `describeWithdrawal({ index: 0, ... })` and `describeWithdrawal({ index: 1, ... })` both invoke `findMatchingWithdrawal` with only `assetId`, and both will resolve to the same (first found) entry in the unsorted `withdrawals` array — even though the underlying `withdrawal.data.address`/`amount` may not correspond to `index: 1`'s actual `destinationAddress`/`amount`.

The batch withdrawal feature is explicitly documented and supported by the SDK's higher-level APIs (`sdk.processWithdrawal`, `sdk.waitForWithdrawalCompletion`, `sdk.createWithdrawalCompletionPromises`), which loop over `withdrawalParams` by index and call each bridge's `describeWithdrawal` per index: [4](#0-3) [5](#0-4) 

### Impact Explanation
An integrator using batch withdrawals with two or more legs of the same PoA-bridged asset (e.g., splitting a withdrawal across two destination addresses, or a withdrawal + fee-refund pattern of the same token) can receive a **status/txHash misreport**: the SDK reports index 1's withdrawal as `completed` with a destination tx hash that actually belongs to index 0's withdrawal (or vice versa). If the integrator credits users/marks the withdrawal fulfilled based on this signal, this is a status misreport that can cause an integrator to believe a specific leg (to a specific address/amount) has completed when it has not, or to associate the wrong destination tx hash with a database record — leading to double crediting/refunding or crediting the wrong recipient's flow as complete. This matches the "status or hash misreport making an integrator credit or refund twice" impact class.

### Likelihood Explanation
This requires no malicious action from the relayer/bridge/RPC — it is triggered purely by legitimate use of the SDK's own advertised "Batch Withdrawals" feature (packages/intents-sdk/README.md) with two withdrawals of the same underlying PoA asset in one intent. The code path is reachable by any consumer of `processWithdrawal`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` with such parameters, and the bug is explicitly acknowledged (not hypothetical) in the source comments, though the team apparently considers same-asset batches an unsupported edge case rather than a fixed scenario.

### Recommendation
Disambiguate withdrawals within `findMatchingWithdrawal` by also validating `amount` and `destinationAddress` (and ideally sorting both the API results and `withdrawalParams` by amount as the code comment itself suggests) instead of matching by `assetId` alone. Until the POA API supports precise correlation (e.g., a per-leg withdrawal id), `PoaBridge.supports()`/`createWithdrawalIdentifier()` should reject or explicitly flag batches containing more than one withdrawal of the same asset to prevent silent misreporting.

### Proof of Concept
1. Build a batch withdrawal intent with two `ft_withdraw` intents for the same PoA asset (e.g., `nep141:usdc.omft.near`), one to `destinationAddress = A, amount = 100`, another to `destinationAddress = B, amount = 200`, in a single NEAR tx.
2. After settlement, call `sdk.waitForWithdrawalCompletion` (or directly `PoaBridge.describeWithdrawal`) with `index: 0` and separately `index: 1`, both referencing `withdrawalParams` for the same `assetId`.
3. Mock/observe the POA bridge withdrawal-status API returning an unsorted array containing two `COMPLETED` withdrawal records for that asset (as in the existing test at `poa-bridge.test.ts:1054-1111`, "matches withdrawal by assetId, not by index" — which demonstrates the exact matching behavior, though there it is presented as intended for a *single* logical withdrawal spread across chains rather than as a bug in a *same-asset multi-leg batch*).
4. Both `describeWithdrawal` calls resolve using `findMatchingWithdrawal`, which returns `withdrawals.find(w => nep141:w.data.near_token_id === assetId)` — the same first match for both index 0 and index 1 — reporting the same `transfer_tx_hash`/status for both legs regardless of which one actually corresponds to `destinationAddress A` vs `B`.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
