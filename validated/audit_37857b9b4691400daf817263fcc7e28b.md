### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC, allowing cross-tenant impersonation via header substitution - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string solely from the raw HTTP body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers without any cryptographic binding to that signature [2](#0-1) . `Registry.process` validates only the HMAC of the body and then trusts the header-derived `shop` value to build `WebhookMetadata`, which is handed to the host application's handler as the authoritative tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`hmac_valid(raw_body) == true` should imply `shop header == shop that actually generated raw_body`.

In this gem, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the signature purely from that string and the app's `client_secret` [4](#0-3) . The `shop` accessor is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header [5](#0-4) , and is never checked against the body content or bound into the signed bytes.

Because every shop that installs the app shares the same app `client_secret`, any shop for which the app is installed can legitimately receive a real webhook delivery with a valid HMAC over some raw body. An attacker who controls such a shop (an ordinary, unprivileged merchant — no `api_secret_key` knowledge required) can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body bytes and hmac), and `Registry.process` forwards the forged `shop` value straight into `WebhookMetadata` and into the handler [3](#0-2) . Any host application that uses `data.shop` from the webhook to select which merchant record/session/data to act on (a documented, intended usage pattern) will attribute the attacker-controlled body to the victim's tenant.

### Impact Explanation
This breaks a tenant/identity boundary: the field ("shop") that host applications use to decide *whose* data the webhook body applies to is not covered by the HMAC that is supposed to authenticate the request as coming from Shopify for that specific shop. An attacker who merely installs the app on any shop they control can forge webhook deliveries that appear to originate from a different, victim shop, enabling cross-tenant data confusion/injection in any app that trusts `WebhookMetadata#shop` for authorization or record lookup — this matches the Critical "cross-tenant access" impact category, since no `api_secret_key` or leaked credential is required, only ordinary use of the app as an unprivileged merchant.

### Likelihood Explanation
Likelihood is high for any app builder following the documented `WebhookHandler`/`WebhookMetadata` API, since `shop` is exposed as a first-class trusted field of the metadata struct and the gem provides no warning or mechanism binding it to the signed payload. The only prerequisite is the ability to install the app on a shop (or observe a webhook delivery for a shop the attacker controls), which is trivially available to any unprivileged internet user in the Shopify app-store/dev ecosystem.

### Recommendation
Include the identity-carrying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string (or otherwise cryptographically bind them, e.g., by validating them against a signed value delivered out-of-band by Shopify), so that `HmacValidator.validate` fails if any of these fields are altered independently of the body. At minimum, document clearly that `shop` from `WebhookMetadata` is unauthenticated and must not be used for authorization decisions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`. The app subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's `client_secret`, and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(raw_body, hmac)` from this delivery (e.g., by proxying their own endpoint or intercepting logs).
4. Attacker replays the exact same `raw_body` and `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` [1](#0-0)  — validation succeeds despite the shop header being forged.
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [6](#0-5)  and, if it uses `data.shop` to select/update the victim's tenant record, processes attacker-controlled data under the victim shop's identity.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
