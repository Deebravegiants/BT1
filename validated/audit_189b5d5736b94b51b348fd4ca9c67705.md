### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating an HMAC computed only over the raw request body, but the `shop` (tenant identifier) that gets forwarded to the app's webhook handler is read straight from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. This breaks the equality `hmac_signed_bytes == bytes_used_for_tenant_identification`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor used for tenant identification, however, is pulled unauthenticated from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only) and compares it against a single, app-wide `Context.api_secret_key` — not a per-shop secret: [3](#0-2) [4](#0-3) 

Because the same `api_secret_key` is used to sign webhooks for every shop that has installed the app, and the HMAC covers only the body (never the `shop-domain` header), a valid HMAC only proves "this body was signed with this app's secret" — it says nothing about which shop the header claims. `request.shop` is then passed straight into `WebhookMetadata`, which the host application uses to identify the tenant the webhook belongs to: [5](#0-4) 

Equality that should hold but doesn't: `bytes_covered_by_hmac == bytes_used_to_select_the_tenant`. Here `bytes_covered_by_hmac = raw_body` while `bytes_used_to_select_the_tenant = header["shop-domain"]`, which is disjoint from the signed data.

### Impact Explanation
An attacker who controls a shop that has installed the app (a routine, unprivileged action) can capture a legitimate webhook delivery (raw body + its valid HMAC) sent to their own endpoint, then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` forwards the forged `shop` value to the handler as if it were authentic. Any host application relying on `WebhookMetadata#shop` for tenant scoping (the documented, intended use per `docs/usage/webhooks.md`) can be tricked into applying webhook data (e.g. `app/uninstalled`, `shop/redact`, or other body-light topics) against the wrong tenant, producing cross-tenant data corruption/confusion. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (standard, unprivileged) and be able to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — both trivially available to any internet user targeting a public app. No secrets, tokens, or elevated access are required.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) into the HMAC-verified material, e.g. include the `X-Shopify-Shop-Domain` header value in `to_signable_string`, or require the host application to independently confirm the shop against a value it already trusts (e.g. a shop record keyed by a value obtained during OAuth) before treating the header-derived `shop` as authentic tenant context. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant-scoping key.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers a webhook (e.g. `app/uninstalled`) pointing at the app's public endpoint.
2. Shopify delivers the webhook with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` and re-sends a POST to the same endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it matches `H` — validation passes.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled webhook data under the victim shop's tenant context.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
