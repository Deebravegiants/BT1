This confirms the finding: `ShopifyAPI::Webhooks::Request#hmac` is computed over `@raw_body` only via `to_signable_string` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the signed payload [2](#0-1) . `Registry.process` validates only the HMAC over the body, then trusts `request.shop`/`request.topic` to build `WebhookMetadata` passed to the app's handler [3](#0-2) . This matches the explicitly in-scope bug class "a field acted on but not covered by the HMAC."

### Title
Webhook tenant identity (`shop-domain`) header is not covered by HMAC verification, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC signature over the raw JSON body only, but hands the app's webhook handler a `shop` value taken from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. Since the header is not part of the signed data, any request whose body+HMAC pair was legitimately produced by Shopify for shop A can be replayed with the `shop-domain` header rewritten to shop B, and `Utils::HmacValidator.validate` will still accept it, causing the host app's handler to process/attribute the payload to the wrong tenant.

### Finding Description
`Registry.process` is the sole authorization gate for inbound webhooks:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`Utils::HmacValidator.validate` verifies the HMAC against `verifiable_query.to_signable_string`, and `Request#to_signable_string` returns only `@raw_body`:

```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers, none of which are covered by that signature:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

The binding the gem is supposed to enforce is:
`hmac_valid(raw_body) == true` implies `shop header == shop that actually produced raw_body`.

That equality does not hold: `hmac_valid` only certifies the body bytes came from Shopify with the app's secret; it says nothing about which shop the accompanying `shop-domain` header refers to. An attacker who can obtain one legitimately-signed `(raw_body, hmac)` pair for any shop (e.g. a webhook payload delivered to a multi-tenant endpoint, or one they can trigger themselves as a merchant/dev-store owner of shop A) can resend the exact same body and HMAC to the app's callback URL while substituting `shop-domain: shop-b.myshopify.com`. `Utils::HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` calls the handler with `WebhookMetadata#shop == "shop-b.myshopify.com"` even though the signed bytes were never produced for shop B.

### Impact Explanation
Apps built on this gem's documented webhook API (`docs/usage/webhooks.md`) are told to use `data.shop` to scope local persistence/authorization ("perform_later(topic: data.topic, shop_domain: data.shop, ...)") [6](#0-5) . Because the gem itself never binds `shop` to the signed payload, any consumer following this documented pattern inherits cross-tenant data confusion: an attacker who has captured or can generate one valid signed webhook can cause data belonging to shop A to be recorded/acted on as if it belonged to shop B (or vice versa), corrupting per-tenant state without possessing shop B's credentials.

### Likelihood Explanation
Requires the attacker to possess at least one valid `(raw_body, hmac)` pair, which is achievable by any developer with their own (attacker-controlled) Shopify dev/trial store subscribed to the target app, or by intercepting/observing one delivery (webhooks are delivered over plain HTTPS POST to a public callback URL, so a legitimate webhook for shop A is fully in the attacker's hands once received by their own shop). No access token, `client_secret`, or privileged account for the victim tenant is needed — only the app's already-public callback endpoint and the attacker's own tenant relationship, satisfying the "cross-tenant access" criterion without crossing a credential/authentication boundary the app controls.

### Recommendation
Bind the tenant-identifying header into the signed material verified by `HmacValidator`, e.g. include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that `request.shop` matches the shop associated with the webhook subscription/session before invoking the handler, rather than trusting an unauthenticated header.

### Proof of Concept
1. Attacker registers a webhook on their own shop `attacker-shop.myshopify.com` for a topic handled by the target app.
2. Shopify delivers a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical `B` and `hmac` to the app's callback URL, replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only [7](#0-6)  and it matches, so `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , despite `B` never having been produced for `victim-shop.myshopify.com`.
