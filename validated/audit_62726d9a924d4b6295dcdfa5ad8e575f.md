Confirmed and important: the documentation states `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and instructs handlers to trust `data.shop` as "The shop domain of the webhook" [2](#0-1) . That is exactly the identity-binding gap that matters here: the gem's own documented contract implies the shop identity is verified, but the code never binds the shop header to the HMAC.

### Title
Webhook shop-domain identity spoofing via HMAC/tenant-binding mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body [3](#0-2) , while the tenant-identifying `shop` value is read directly from an unauthenticated header [4](#0-3) . `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally forwards `request.shop` to the app's handler as the authoritative tenant identity [5](#0-4) . Because the HMAC never covers the shop domain, any actor who can produce one valid `(body, hmac)` pair (e.g., from webhooks delivered to their own installed shop) can resubmit that exact pair with an arbitrary `shopify-shop-domain` header and it will pass `HmacValidator.validate` unchanged.

### Finding Description
The identity binding that should hold is:
`shop_header == shop_that_produced(body, hmac)`

`HmacValidator.validate` only checks `computed_signature(verifiable_query.to_signable_string) == received_signature` [6](#0-5) , and for webhook requests `to_signable_string` is defined as the raw body alone [3](#0-2) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors all read straight from client-supplied headers with no cryptographic tie to the HMAC [7](#0-6) . Since the API key/secret (`Context.api_secret_key`) is a single per-app secret shared across every shop that installs the app (not a per-shop secret), the signature `HMAC(secret, body)` is byte-for-byte identical no matter which shop the body is claimed to originate from. `Registry.process` trusts `request.shop` as-is when building `WebhookMetadata` for the handler [5](#0-4) , and the documented contract tells integrators that `data.shop` is "the shop domain of the webhook" without any caveat that it is unauthenticated [2](#0-1) , and that `process` "will verify the request did indeed come from Shopify" [1](#0-0)  — implying the whole request, including its shop attribution, is verified.

Before the attack: shop A (attacker-controlled, legitimately installed) receives a real webhook with body `B` and valid `hmac = HMAC(secret, B)`.
After the attack: attacker POSTs the same `(B, hmac)` to the app's webhook endpoint with header `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` returns `true` (it never looked at the shop header), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"`, `body: B` — data the attacker controls, now falsely attributed to the victim tenant.

### Impact Explanation
This breaks the tenant boundary the whole HMAC check exists to enforce: the app is led to believe attacker-crafted webhook content originated from a different (victim) shop. Depending on how the host app's handler uses `data.shop` (e.g., to key database writes, trigger emails/actions, sync inventory, issue refunds, or gate access to per-tenant data), this enables cross-tenant data injection/corruption or unauthorized actions performed under another merchant's identity — matching the Critical "cross-tenant access" impact category. It requires no access token, no `api_secret_key`, and no privileged account — only the ability to install the app on an attacker's own (free/trial) shop to legitimately obtain one valid `(body, hmac)` sample, or simply to craft any body and predict/observe an hmac pairing from any webhook the attacker's shop naturally receives.

### Likelihood Explanation
Likelihood is high for any app relying on the documented `Registry.process` / `WebhookHandler` flow to attribute webhook data to shops, since nothing in the public API signals that `shop` needs independent verification against a known-installed-shop list — the docs state the opposite, that `process` verifies the request "did indeed come from Shopify." Any developer using this gem exactly as documented inherits the flaw. The only prerequisite is discovering/guessing the app's webhook endpoint path, which is typically a fixed, low-entropy route (e.g., `/webhooks/orders_create`).

### Recommendation
Bind the shop domain (and other headers acted upon, like `topic`/`webhook_id`) into the value verified by the HMAC, or explicitly document/require that consumers cross-check `data.shop` against their own store of shops that have valid, currently-installed sessions/access tokens before trusting it. Concretely: extend `VerifiableQuery`/`to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop header into what gets checked, or add a mandatory secondary check in `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) that rejects webhooks whose `shop` isn't in the caller-registered set of active sessions, and update `docs/usage/webhooks.md` to make clear that `data.shop` is not itself HMAC-authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B = '{"id":1}'`, header `x-shopify-hmac-sha256: HMAC_B64(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, changing only:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `hmac` and `to_signable_string` are unaffected by the shop header change [8](#0-7) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body [5](#0-4) .
5. The registered handler executes with `data.shop == "victim-shop.myshopify.com"` and attacker-controlled `data.body`, exactly as documented for legitimate webhooks [9](#0-8) .
