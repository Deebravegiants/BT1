## Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC over the raw request body only, but the `shop` value used to attribute the webhook to a specific merchant is read from an unsigned HTTP header. An attacker who can obtain one legitimately-signed webhook body (e.g. from their own shop where they installed the app) can replay it to the host application's webhook endpoint with a forged `shop-domain` header naming a different (victim) shop. `Utils::HmacValidator.validate` still reports success because it never inspects the header, so the gem hands the handler a `WebhookMetadata` object whose `shop` field is attacker-controlled while claiming HMAC-verified authenticity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC of the request (i.e. of `raw_body` only) and, on success, immediately trusts `request.shop` as the tenant identifier passed to the merchant's handler: [3](#0-2) 

The identity binding that should hold is:

`shop authenticated by HMAC == shop value acted upon by the handler`

Because the HMAC only binds the body bytes, this equality never holds for the `shop` field: any body/HMAC pair that was legitimately produced by Shopify for shop A remains cryptographically valid when replayed with an attacker-chosen `shop-domain` header claiming shop B. The gem cannot detect this substitution because the header simply isn't part of the material it verifies.

### Impact Explanation
An unprivileged attacker who has (or creates) their own development/trial shop with the app installed will legitimately receive real, validly-signed webhook deliveries for that shop. By capturing one such delivery and re-sending it to the app's public webhook endpoint with a different `shop-domain` header, the attacker gets `ShopifyAPI::Webhooks::Registry.process` to report a verified webhook whose `WebhookMetadata#shop` names an arbitrary victim shop. Any host application that trusts `data.shop` from a "verified" webhook (as the gem's own API implies it should, since it only exposes `shop` after successful HMAC validation) will process attacker-supplied body content under the wrong tenant's identity — a cross-tenant data/event injection primitive that crosses the shop-identity boundary the HMAC is supposed to enforce.

### Likelihood Explanation
Exploitation only requires an internet-reachable webhook endpoint and the ability to install the app on any shop (including a free/dev shop the attacker controls) to harvest one valid `(body, hmac)` pair; no access to `client_secret`, tokens, or the victim shop is needed. The replay itself is a single crafted HTTP request with a substituted header.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC computation, or independently verify the header-derived `shop` against a value obtained from the same trust boundary as the signature — e.g. cross-check `webhook_id`/`shop` via the Admin API using a session already known to belong to that shop, or require applications to correlate against a shop known from OAuth-derived state, rather than exposing `shop` as an implicitly-trusted field on a "validated" webhook request.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1}` with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the exact same body and `hmac-sha256` header to the host app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` using only `request.to_signable_string` (== `raw_body`), which still matches, so validation succeeds: [3](#0-2) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the payload never having been produced by/for that shop, demonstrating the broken `shop`-to-HMAC binding.
