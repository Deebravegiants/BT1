## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop-domain` header (which is *not* part of the signed material) to identify which tenant the webhook belongs to when dispatching to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the HMAC computation: [2](#0-1) 

`Registry.process` verifies the HMAC over the body only and then immediately builds the tenant-identifying metadata from the unauthenticated `shop` header, passing it to the app's handler as the source of truth for the shop: [3](#0-2) 

The library's own documentation instructs app authors to trust `data.shop` as "The shop domain of the webhook" and to use it directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), i.e., as the tenant key for downstream processing: [4](#0-3) 

This breaks the identity binding: **shop authenticated by the HMAC (none — only the body is signed) ≠ shop used as the tenant key handed to the app** (`request.shop`, an unauthenticated header value). Because the signature is computed with `HMAC(api_secret_key, raw_body)` and depends on neither the `shop-domain` nor `topic`/`webhook-id` headers, the exact same `(raw_body, hmac)` pair is valid for **any** value of the `shop-domain` header.

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook delivery for a shop they control (trivial — install the app on their own store, or any low-privilege merchant account, and capture the resulting webhook POST) can replay that same body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `Utils::HmacValidator.validate` will still succeed (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Since apps are documented to trust `data.shop` for tenant dispatch/storage, this allows cross-tenant data injection/corruption (e.g., writing another merchant's shop-scoped records with attacker-controlled webhook body content), which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High: no access to `api_secret_key` or any Shopify credential is required — only a single real, previously-delivered webhook (with its original raw body and HMAC) from any shop, including one the attacker legitimately controls. The webhook endpoint is a public HTTP route by design, and replay only requires resending the same bytes with a different header value.

### Recommendation
Bind the shop identity to the verified signature material instead of trusting an unauthenticated header:
- Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed input verified in `HmacValidator.validate`, or
- Require and cross-check the `shop` header against session/registration state known to the app (e.g., that a webhook was actually registered for that shop) before dispatching, or
- At minimum, document and enforce that `data.shop` must never be trusted as an authenticated value derived from the HMAC, and require app authors to independently verify shop ownership before using it as a tenant key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g., `orders/create`), receiving a legitimate webhook POST with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the exact same request to the app's public webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` (using `to_signable_string` = `B`) and it matches `H`, so validation succeeds.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, causing the app to process attacker-controlled data under the victim shop's tenant context.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
