## Analysis

The reported Astaria bug is a **missing-origin-validation on a privileged callback**: `ClearingHouse`'s fallback trusts *any* Seaport settlement call touching its `collateralId`, without checking that the call is tied to the genuine auction/session it claims to settle. The reachable analog in `orb-core` is in the Orb-Relay client's message dispatcher.

In `orb-relay-client/src/client.rs`, the `main_loop` receives multiplexed messages for a signup session and is supposed to reject anything not originating from the expected session peer: [1](#0-0) 

but the `RequestState` branch is checked *before* the source-identity check and unconditionally echoes `self.last_message` (the last payload this client sent — e.g. `AnnounceOrbId`, `SignupEnded`, or other self-serve session state) back to the caller, with no verification that the request actually comes from `self.config.dst_id` (the counterpart bound to the current session): [2](#0-1) 

The code even documents the multiplexing risk as an open TODO: [3](#0-2) 

`last_message` is only ever set from this client's own outgoing sends tied to the current signup/session: [4](#0-3) 

and this session state is used to drive real signup lifecycle behavior (`SignupEnded`, `AnnounceOrbId`) in `src/plans/mod.rs`: [5](#0-4) [6](#0-5) 

### Title
Unauthenticated `RequestState` handling bypasses source verification and leaks session state - (File: `orb-relay-client/src/client.rs`)

### Summary
The Orb-Relay client's response loop special-cases the `self_serve::app::v1::RequestState` payload and responds with the last session message **before** performing the `src.id != self.config.dst_id` check that gates every other message type. As a result, any entity able to reach the multiplexed relay stream can obtain a copy of another session's most recent signup-relevant payload without proving it is the genuine counterpart for that session — the same "callback trusted without proof of genuineness" root cause as the ClearingHouse/Seaport report, applied to a session/state-disclosure path instead of a fund/asset path.

### Finding Description
`PollerAgent::main_loop` processes incoming `RelayPayload`s from the backend. For all message types except `RequestState`, it enforces `src.id == self.config.dst_id` before calling `handle_message`, i.e., before trusting the payload as belonging to the current session's counterpart (`orb-relay-client/src/client.rs:441-452`). However, the `RequestState` branch (`client.rs:436-440`) executes unconditionally on `src`, sending `self.last_message` — the last payload this client actually transmitted for the active signup session — back over `sender_tx` with no check that the requester is the legitimate `dst_id` for that session. This mirrors the reported class of bug precisely: a state-mutating/disclosing operation is triggered by an unauthenticated caller because the code assumes any message reaching the handler is "genuine," instead of validating the caller against the expected session context, exactly as `ClearingHouse`'s fallback assumed any Seaport settlement touching its `collateralId` was genuine.

### Impact Explanation
`last_message` carries session-bound content (e.g., `AnnounceOrbId`, `SignupEnded` outcome/failure feedback) tied to a specific signup. An entity that is not the legitimate session peer (mismatched `dst_id`/`session_id`) can still trigger disclosure of this state by sending `RequestState`, since the check that would normally reject it is skipped for this payload type. This is a concrete cross-signup state disclosure: session metadata intended for one app/orb pairing can be obtained by another party on the shared relay transport, which the code itself acknowledges as a known multiplexing risk in the adjacent TODO comment.

### Likelihood Explanation
Likelihood is moderate to high in the reachable path: any client capable of authenticating to the relay backend (as an app or orb, per `Client::new_as_app`/`new_as_orb`) and reaching the same multiplexed stream can send a `RequestState` payload; no additional privilege beyond basic relay auth is required to hit the branch that skips the source check, since the check is skipped by construction rather than by a hard-to-reach edge case.

### Recommendation
Move the `RequestState` handling after (or make it subject to) the same `src.id == self.config.dst_id` validation applied to all other payloads, so the client only replays session state to the verified session counterpart, analogous to Astaria's fix of requiring `ClearingHouse` to verify sufficient/matching payment context before treating a Seaport callback as genuine.

### Proof of Concept
1. Start an Orb-Relay client pairing for session A (`orb_id`, `session_id_A`) and have the Orb side send a session-bound message (e.g., `SignupEnded`), setting `last_message` accordingly (`client.rs:498-500`).
2. From a separate, differently-authenticated client (session B, or any entity whose `src.id` does not equal the Orb's configured `dst_id` for session A) send a `self_serve::app::v1::RequestState` payload routed to the Orb's stream.
3. Observe that the Orb's `main_loop` responds with `self.last_message` (session A's state) without ever evaluating `src.id != self.config.dst_id`, because the `RequestState` branch (`client.rs:436-440`) is checked first and unconditionally.
