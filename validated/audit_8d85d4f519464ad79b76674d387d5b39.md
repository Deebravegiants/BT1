There's a `shop_validator.rb`. Let me check it and how/where it's used relative to `Oauth.validate_auth_callback`.### Title
OAuth callback flow sends `client_secret` to an unvalidated `shop` domain, unlike every other credential-exchange entry point - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the token-exchange URL from `auth_query.shop` and POSTs the app's `client_id`/`client_secret` to it, without ever running that `shop` value through `Utils::ShopValidator.sanitize!`. Every other credential-exchange code path in this gem (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, `TokenExchange.exchange_token`) explicitly calls `ShopValidator.sanitize!` before constructing the session/URL used to send the secret. `Oauth.validate_auth_callback` is the outlier that skips this check.

### Finding Description
`validate_auth_callback` only verifies the HMAC over the query string (`code`, `host`, `shop`, `state`, `timestamp`) via `Utils::HmacValidator.validate(auth_query)`: [1](#0-0) 

That HMAC check proves the query bytes weren't tampered with by a third party in transit, but it says nothing about whether `shop` is a legitimate `*.myshopify.com`/trusted Shopify domain — it is signed by whoever holds `api_secret_key`, using whatever `shop` string was supplied to `begin_auth`, which itself takes an unvalidated caller-supplied `shop:` argument: [2](#0-1) 

After the HMAC check passes, `shop` is used directly to build the base URI and the request that carries `client_secret`: [3](#0-2) [4](#0-3) 

Compare this to the sibling flows, all of which sanitize `shop` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is used to build the target host that receives `client_secret`: [5](#0-4) [6](#0-5) [7](#0-6) 

The identity binding that should hold is: `shop` used to construct `auth_base_uri(shop)` (the host that receives `client_secret`) == a validated Shopify-owned host, exactly as enforced by `ShopValidator.sanitize!` elsewhere in the gem. In `oauth.rb`, "HMAC-verified" is silently substituted for "domain-validated," and those are not the same guarantee — HMAC integrity protects the bytes of the query string, it does not constrain the semantic value of `shop` to a Shopify-controlled host. `ShopValidator.sanitize!` exists specifically to reject values like `"attacker.example"` or `"myshopify.com.evil.com"`, per its own test suite: [8](#0-7) 

but `oauth.rb` never calls it.

### Impact Explanation
This maps to the accepted High-impact category "SSRF with the app's credentials." If an application built on this gem passes an attacker-influenced `shop` value into `begin_auth`/`AuthQuery` (e.g., a multi-tenant or embedded scenario where the host app reflects a `shop` query parameter without its own domain check, trusting the gem to enforce this — which every sibling method in this same gem does), the resulting callback, even with a technically valid HMAC for that exact string, will cause `validate_auth_callback` to POST the app's `client_id` and `client_secret` to `https://#{shop}/admin/oauth/access_token` for whatever host `shop` resolves to. This is a genuine inconsistency in the gem's own trust boundary, not merely "the host app misusing the API": the gem asserts a security invariant (shop-domain validation before sending secrets) in three call sites and omits it in the fourth, functionally identical, call site.

### Likelihood Explanation
Moderate. Exploitability depends on whether the host application forwards an untrusted `shop` string into `AuthQuery`/`begin_auth` without independently validating it — which is a realistic integration pattern given the docs show `AuthQuery.new(request.parameters.symbolize_keys...)` built straight from request params. Because the gem itself performs this exact validation in `RefreshToken`, `ClientCredentials`, and `TokenExchange`, but omits it in `Oauth.validate_auth_callback`/`begin_auth`, this is squarely an internal inconsistency in the gem rather than a host-application misuse issue.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `shop` (and the `AuthQuery.shop` value) through `Utils::ShopValidator.sanitize!` in both `begin_auth` and `validate_auth_callback`, before it is used to construct `auth_base_uri(shop)`, mirroring the pattern already used in `RefreshToken`, `ClientCredentials`, and `TokenExchange`.

### Proof of Concept
1. A host app collects `shop` from an OAuth-initiation request and calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: attacker_supplied_shop, redirect_path: "/callback")` without its own domain check (trusting the gem, consistent with how the gem validates `shop` elsewhere).
2. The subsequent callback arrives at the app's callback route with `shop=attacker_supplied_shop` and a valid `hmac` for that exact query string (computed by whoever controls the callback delivery with knowledge of `api_secret_key`, e.g. a compromised or attacker-directed redirect chain that still round-trips through a component holding the secret, or a host app that itself re-signs/forwards the parameters).
3. `ShopifyAPI::Auth::Oauth.validate_auth_callback` passes the HMAC check (`Utils::HmacValidator.validate(auth_query)` at `lib/shopify_api/auth/oauth.rb:64`) and then calls `auth_base_uri(shop)` → `"https://#{attacker_supplied_shop}/admin/oauth/access_token"` (`lib/shopify_api/auth/oauth.rb:118`), POSTing `client_id` and `client_secret` (`lib/shopify_api/auth/oauth.rb:74-79`) to that attacker-controlled host.
4. Contrast with `ShopifyAPI::Auth::RefreshToken.refresh_access_token`, which would reject the same `shop` value via `Utils::ShopValidator.sanitize!` at `lib/shopify_api/auth/refresh_token.rb:24`, raising `ShopifyAPI::Errors::InvalidShopError` before any secret is transmitted.

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
