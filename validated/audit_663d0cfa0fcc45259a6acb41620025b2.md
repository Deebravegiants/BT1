### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying that the HMAC of the **raw body** matches the app's shared `api_secret_key` [2](#0-1) . The `shop` value used to identify which tenant the webhook belongs to is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) . The `shop` accessor is derived independently from an unauthenticated header: [4](#0-3) . `HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the shared `Context.api_secret_key` (or `old_api_secret_key`) — it never binds the signature to the shop header [5](#0-4) . `Registry.process` then forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which the host app's handler is documented to trust as the tenant identity: [2](#0-1) .

Because `api_secret_key` (the app's `client_secret`) is a single value shared across **every shop** that has installed the app, any merchant who has installed the app receives genuine, correctly-signed webhooks for their own shop. That merchant is an "unprivileged internet user" with respect to any other shop's data. They can replay the exact `raw_body` + `hmac-sha256` header pair they legitimately received, while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is valid for the shared secret), so `Registry.process` calls `handler.handle` with `WebhookMetadata#shop` set to the attacker-chosen victim domain, even though the body content belongs to the attacker's own shop.

The identity binding broken is: `hmac == HMAC(secret, shop ++ body)` is expected by the host application (since `shop` is used for tenant routing) but the gem only enforces `hmac == HMAC(secret, body)`, i.e., `shop` is a field acted on (used for tenant identification/routing) but not covered by the HMAC.

### Impact Explanation
This breaks the tenant/shop authentication boundary of the webhook subsystem: a party who is legitimately authenticated for shop A can inject attacker-controlled data labeled as originating from shop B into any host application that follows this gem's documented pattern of trusting `WebhookMetadata#shop` (as shown in the gem's own `docs/usage/webhooks.md` example, which enqueues jobs keyed on `data.shop`). This is a cross-tenant data injection primitive that satisfies the "Critical - cross-tenant access" impact criteria, since the host app has no way, using only this gem's API, to detect that the shop label is unauthenticated.

### Likelihood Explanation
Requires only that the attacker be a legitimate installer of the target app (any shop owner can install most public/embedded apps) and have network tooling to replay an HTTP POST with a modified header — no access to `api_secret_key`, access tokens, or privileged accounts is needed, and no host-application misconfiguration beyond following the gem's documented usage is required.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie `request.shop` to the verified body before constructing `WebhookMetadata`, e.g. by validating that the shop domain matches the shop that actually owns the specific `webhook_id`/subscription, or by documenting/enforcing that consumers must independently verify the shop is one they have an active session for before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's shared `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` computes `HMAC(secret, B)`, which still equals `H`, so validation passes [6](#0-5) .
4. `Registry.process` invokes the host's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [7](#0-6) , causing the host app to act on attacker data under the victim's tenant identity.
