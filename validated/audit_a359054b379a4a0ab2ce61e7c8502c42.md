Audit Report

## Title
Verifier signature replay across crowdloan fund lifecycles due to missing `fund_index` in signed payload - (File: `polkadot/runtime/common/src/crowdloan/mod.rs`)

## Summary
`Pallet::do_contribute` verifies KYC/whitelist signatures against the payload `(index, &who, old_balance, value)`, where `index` is the `ParaId` and `old_balance` is read from the *current* fund's child-trie via `fund.fund_index`. Because `fund_index` itself is never part of the signed payload, and a freshly created fund's child-trie always starts each contributor's balance at `0`, a signature issued for a contributor's first contribution to one fund is byte-for-byte valid again for the same contributor's first contribution to a later fund created for the same `ParaId` after the original fund is dissolved.

## Finding Description
The verifier check in `do_contribute` is: [1](#0-0) 

`old_balance` is fetched via `contribution_get(fund.fund_index, &who)`, which reads from a child-trie keyed by `id_from_index(fund.fund_index)`: [2](#0-1) 

`fund_index` is assigned monotonically at `create` time and stored in `FundInfo`, but is never included in the signed payload: [3](#0-2) 

`dissolve` removes the `Funds` entry for a `ParaId` once `raised` is zero, which permits `create` to be called again for the *same* `ParaId` (the `ensure!(!Funds::<T>::contains_key(index), ...)` guard in `create` only checks for an existing live fund, not fund_index reuse): [4](#0-3) 

Since the new fund gets a fresh child-trie keyed by the new `fund_index`, any contributor's `old_balance` there starts at `0` — identical to the `old_balance` that was signed for their first contribution to the previous, now-dissolved fund for the same `ParaId`. Because the signed tuple `(index, who, old_balance, value)` is unchanged (same `ParaId`, same account, same `0` balance, same contribution amount), the same `MultiSignature` verifies successfully against the new fund, provided the new fund reuses the same verifier key — a realistic scenario since crowdloan organizers commonly reuse the same KYC/verifier provider across re-attempted crowdloans for the same parachain. None of the other checks in `do_contribute` (cap, period, VRF delay, auctioneer status) reference `fund_index` or otherwise distinguish which fund lifecycle a signature was issued for, so none of them prevent this replay.

## Impact Explanation
This breaks the intended security property that a verifier signature authorizes exactly one contribution event tied to a specific fund. A contributor can bypass the KYC/whitelist gate on a newly created fund by resubmitting a previously broadcast, publicly visible extrinsic and its embedded signature, undermining jurisdictional/accredited-investor restrictions that crowdloan organizers rely on the verifier mechanism to enforce.

## Likelihood Explanation
The preconditions are realistic and require no privileged access: create a verified fund, have a contributor make a first contribution (`old_balance == 0`, making the signature/extrinsic public on-chain), dissolve the fund once `raised` returns to zero (a routine outcome after refund on a failed/expired crowdloan), and create a new fund for the same `ParaId` reusing the same verifier key. The "attacker" is simply the original contributor replaying their own old signed extrinsic — no cryptographic forgery required, and the scenario (re-running a crowdloan for the same parachain) is a plausible real-world occurrence.

## Recommendation
Bind the signed payload to the specific fund instance, e.g., include `fund.fund_index` in the payload: `(fund.fund_index, index, &who, old_balance, value)`, so a signature cannot be validated against a different fund lifecycle even when `old_balance` and `ParaId` coincide.

## Proof of Concept
1. `create` fund `F1` for `ParaId(1)` with `verifier = Some(pubkey)`.
2. Sign payload `(ParaId(1), who=1, old_balance=0, value=100)` with the verifier's private key → `sig`.
3. Call `contribute(who=1, index=1, value=100, Some(sig))` → succeeds, `Contributed` event emitted.
4. `refund` fund `F1` (contribution removed, `raised` returns to 0), then `dissolve` fund `F1` (`Funds` entry removed).
5. `create` a new fund `F2` for the same `ParaId(1)` reusing the same `verifier` pubkey.
6. Call `contribute(who=1, index=1, value=100, Some(sig))` reusing the same `sig` from step 2 without any new signing.
7. Observe the call succeeds (rather than returning `Error::<T>::InvalidSignature`), proving the old signature is replayable across the fund lifecycle boundary via `polkadot/runtime/common/src/crowdloan/mod.rs` lines 782-791.

			let who = ensure_signed(origin)?;

			let fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let pot = Self::fund_account_id(fund.fund_index);

			// Only allow dissolution when the raised funds goes to zero,

			let permitted = who == fund.depositor || now >= fund.end;
			let can_dissolve = permitted && fund.raised.is_zero();
