### Title
Case-insensitive Bech32 addresses bypass the "withdraw to token's own address" equality check - ([File: packages/intents-sdk/src/lib/compareAddresses.ts])

### Summary
`compareAddresses` is the SDK's canonical-equality function, used by every bridge (`direct-bridge`, `hot-bridge`, `omni-bridge`, `poa-bridge`) to block a withdrawal whose `destinationAddress` equals the token's own on-chain address. For Bitcoin, Litecoin and other Bech32/Bech32m-based chains it falls through to a byte-level `a === b` comparison [1](#0-0) , while the address-acceptance gate (`validateAddress`) normalizes case before decoding and therefore accepts both the lower-case and the all-upper-case spelling of the same Bech32 address as valid [2](#0-1) . This is the same class of bug as the Deno advisory: the "deny" check compares raw bytes while the underlying encoding treats differently-cased spellings as equivalent, so a denied value can be reached through an alternate spelling.

### Finding Description
`validateBtcBech32Address` lower-cases only the human-readable part for the prefix check, but hands the address (in whatever case it was submitted) straight to `bech32`/`bech32m` decode, and the existing test suite proves a fully upper-cased Bech32 address decodes successfully and represents the exact same witness program as its lower-case form: [3](#0-2) 

`compareAddresses`, however, treats Bitcoin (and Litecoin, Dogecoin, etc. that share the same `a === b` branch) as an exact string match with no case normalization: [4](#0-3) 

Every bridge's `validateWithdrawal` uses exactly this function to enforce the invariant "destination address must not equal the token's own chain address": [5](#0-4) [6](#0-5) [7](#0-6) 

Because `validateAddress` (the acceptance gate) recognizes an all-uppercase Bech32 spelling of an address as valid, but `compareAddresses` (the denial gate) does not fold case before comparing, a caller can supply the token's own Bitcoin/Litecoin Bech32 deposit address in a different case than the one stored in configuration (`tokenInfo.origin_chain_address`, always lower-case per typical config/API convention) and the equality check silently returns `false`, letting the withdrawal through.

### Impact Explanation
This defeats the SDK's own self-transfer guard (`DestinationAddressMatchesTokenAddressError`) that exists specifically to prevent funds from being withdrawn back into the bridge/token's own custody address on the destination chain — an action from which, per the code's own comments and error naming, recovery requires manual intervention. This matches the "withdrawal stuck until manual intervention" High-impact category: the SDK reports the withdrawal as valid/succeeds, but the underlying on-chain address is the same one the bridge treats as its own token address, not a genuinely different, user-controlled destination.

### Likelihood Explanation
Any caller of `validateWithdrawal` for a Bech32-chain asset (BTC being the most prominent, given production configs reference `nep141:btc.omft.near` with a lower-case `origin_chain_address`) can trigger this simply by upper-casing the address string before calling the SDK — no privileged access, RPC manipulation, or bridge/relayer cooperation required.

### Recommendation
Normalize Bech32-family addresses (Bitcoin, Litecoin, and any other chain compared via the plain `a === b` branch that uses Bech32/Bech32m encoding) to their canonical lower-case form (or fully decode to the witness program bytes, as already done for Aptos/Sui/Starknet/TON/Tron) inside `compareAddresses` before comparing, instead of relying on raw string equality.

### Proof of Concept
1. Configure a BTC withdrawal where `tokenInfo.origin_chain_address` is `"bc1q973xrrgje6etkkn9q9azzsgpxeddats8ckvp5s"`.
2. Call `bridge.validateWithdrawal({ assetId: "nep141:btc.omft.near", amount, destinationAddress: "BC1Q973XRRGJE6ETKKN9Q9AZZSGPXEDDATS8CKVP5S" })`.
3. `validateAddress` accepts the upper-case address (per `validateAddress.spec.ts` fixture) so the format check passes.
4. `compareAddresses(tokenInfo.origin_chain_address, "BC1Q973...", Chains.Bitcoin)` executes `a === b` on differently-cased strings and returns `false`, even though both decode to the identical witness program/address.
5. `DestinationAddressMatchesTokenAddressError` is never thrown, and the withdrawal proceeds to send funds to the bridge's own BTC deposit address.

function validateBtcBech32Address(address: string): boolean {
	let decoded: { prefix: string; words: number[] };
	let isBech32m = false;

	try {
		decoded = bech32.decode(address as `${string}1${string}`);
	} catch {
		try {
			decoded = bech32m.decode(address as `${string}1${string}`);
			isBech32m = true;
		} catch {
			return false;
		}
	}

	if (decoded.prefix.toLowerCase() !== "bc") return false;
