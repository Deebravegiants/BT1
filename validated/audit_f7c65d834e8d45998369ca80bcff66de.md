### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator.validate` checks is computed only over the raw request body. The shop domain, topic, and webhook id headers are never bound into the signed payload, so an attacker who captures one legitimately-signed webhook (e.g. delivered to their own shop) can replay the exact same body/HMAC pair while substituting a different `shop-domain` header, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` (the value used downstream to attribute the webhook to a tenant) is read straight from an attacker-controllable HTTP header with no cryptographic binding to that header: [2](#0-1) 

`Registry.process` gates handling solely on the body HMAC and then forwards the unauthenticated `shop` header value straight to the app's webhook handler: [3](#0-2) 

The identity binding that should hold is: `shop-domain header == shop bound inside the HMAC-verified payload`. Here, the verified bytes (`raw_body`) and the bytes acted upon for tenant attribution (`shop-domain` header) are disjoint — exactly the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" pattern.

### Impact Explanation
Any user who can legitimately install the app on their own store (an unprivileged action available to any Shopify merchant) can capture a genuinely Shopify-signed webhook delivery to their own shop, then replay the identical body and HMAC header to the app's webhook endpoint while swapping only the `shop-domain` header to a victim shop's domain. Because the signature check never touches that header, the forged request passes `Utils::HmacValidator.validate` and the app's handler receives `WebhookMetadata` attributing attacker-chosen (but validly-signed) body content to a shop the attacker does not control. Depending on how the host app's registered handler uses `data.shop` (e.g., updating per-tenant records, honoring mandatory `customers/redact`/`shop/redact` requests), this is a cross-tenant confusion primitive: attacker-controlled webhook effects get attributed to and executed against a shop that never sent them.

### Likelihood Explanation
The attacker only needs to install the app on their own shop and be able to trigger any webhook topic (or wait for a routine one like `orders/create`), which are standard, unprivileged capabilities for any merchant using the app. No access to the app's `client_secret` or another shop's credentials is required — only capture-and-replay of one legitimately delivered webhook with a header substitution.

### Recommendation
Bind the shop domain (and ideally the topic/webhook id) into the signed material, or otherwise cryptographically tie the `shop-domain` header to the payload before trusting it — e.g., require the host application to cross-check `request.shop` against the shop associated with a stored, previously-registered webhook subscription rather than trusting the header outright, or extend `to_signable_string` to canonically include the relevant headers if Shopify's delivery signs them elsewhere. At minimum, document prominently that `request.shop` is unauthenticated and must not be used for tenant attribution without an independent binding.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and register a webhook (e.g., `orders/create`).
2. Capture a real webhook delivery at the attacker's endpoint: raw body `B`, and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`, computed by Shopify).
3. Re-send a new HTTP request to the app's webhook endpoint with the same body `B` and same `shopify-hmac-sha256: H`, but replace `shopify-shop-domain: attacker-shop.myshopify.com` with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and matches `H` — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to process attacker-supplied webhook content as if it originated from `victim-shop.myshopify.com`.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
