## Analysis

Mapping the report's bug class ("field acted on but not covered by the cryptographic verification") to this gem's webhook processing path reveals a real identity-binding gap.

### The binding that should hold
`HMAC(raw_body, api_secret_key)` is meant to authenticate **the entire webhook request**, including which shop it is `for`. In practice, `ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the raw body) against the shared, per-app `Context.api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC passes, and then forwards the **unauthenticated** `request.shop` header straight into the handler's `WebhookMetadata`: [4](#0-3) 

### Why this breaks the binding
`api_secret_key` is a single value shared by the app across **all** installed shops (it's the app's `client_secret`, not a per-shop secret) — see its use in the OAuth token exchange body: [5](#0-4) 

Because the HMAC only binds `raw_body`, and `api_secret_key` is identical for every tenant of the app, a merchant who has the app installed on their **own** shop can trigger a real webhook (a genuine, validly-signed HMAC for that body), capture it, then replay the exact same body to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) for a victim shop. `HmacValidator.validate` still passes (body unchanged, same shared secret), but `WebhookMetadata#shop` now falsely claims to be the victim's shop. If the host application uses `data.shop` from `Registry.process`'s handler callback to key merchant records (which is the documented and intended usage pattern, per `docs/usage/webhooks.md`), this is a cross-tenant data-integrity break: attacker-controlled webhook data gets attributed and applied to a shop the attacker does not control.

This is a genuine equality mismatch: **the shop the HMAC verifies against (none — HMAC verifies only the body) ≠ the shop the handler acts on (the unauthenticated header value)**.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted for tenant attribution but excluded from the HMAC signature - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, not the `shop`, `topic`, `webhook_id`, or `api_version` headers. `Registry.process` validates that body-only HMAC and then forwards the unauthenticated `shop` header to application handlers as ground truth for tenant identity.

### Finding Description
`HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) is the sole authenticity check performed before a webhook is dispatched to application code (`lib/shopify_api/webhooks/registry.rb:189-200`). It calls `verifiable_query.to_signable_string`, which for webhook requests returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from caller-supplied HTTP headers with no cryptographic binding (`lib/shopify_api/webhooks/request.rb:15-33`). `Context.api_secret_key` used for the HMAC is the app's single shared `client_secret`, identical for every shop that installs the app (`lib/shopify_api/auth/oauth.rb:74-79`). Consequently, any body+HMAC pair that is valid for shop A's webhook remains a valid HMAC pair no matter what `shop` header accompanies it, since the header plays no role in the signature computation.

### Impact Explanation
An attacker who installs the app on a shop they control can legitimately trigger any webhook topic (e.g., `orders/create`) to obtain a genuinely-signed `(raw_body, hmac)` pair. By resending that exact body to the app's public webhook endpoint with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header naming a different, victim shop, the request still passes `HmacValidator.validate`. The handler then receives `WebhookMetadata` claiming the data belongs to the victim shop (`registry.rb:198-199`), enabling cross-tenant data injection into whatever store/logic keys off `data.shop`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/merchant who can install the app (a normal, unprivileged action) can obtain a validly-signed webhook body for their own shop and replay it against the app's internet-facing webhook endpoint with a different shop header — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the payload before trusting it, and cross-check `request.shop` against a known/installed shop record before invoking handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. create an order) so Shopify sends a real webhook with a valid `x-shopify-hmac-sha256` for the resulting `raw_body`.
2. Capture that request (`raw_body`, `x-shopify-hmac-sha256`, `x-shopify-topic`).
3. Replay the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate` (`registry.rb:190`), which passes because it only checks `raw_body` against the shared `api_secret_key`.
5. The handler executes with `WebhookMetadata#shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's shop.
