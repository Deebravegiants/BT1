### Title
Session ID exposed as an unsigned, predictable session cookie value enabling cross-tenant session hijacking - (File: `lib/shopify_api/auth/oauth/session_cookie.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's value directly to the plaintext, predictable session id (`"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions) with no HMAC or signature protecting that value. [1](#0-0)  `SessionUtils.cookie_session_id` and `current_session_id` then read this raw cookie value straight from the unauthenticated cookie jar and hand it back to the host app as "the" session id to use for session lookup, with no verification step at all. [2](#0-1) [3](#0-2)  `SessionCookie` itself is a plain struct with no signing/verification logic. [4](#0-3) 

### Finding Description
The identity binding that should hold is: **cookie bytes the browser presents == an id cryptographically bound to the specific OAuth session that this gem created for this specific shop/user**. Instead, the binding that actually holds is: **cookie bytes the browser presents == raw string echoed back by `cookie_session_id`, with zero integrity check**.

- Session ids are deterministic and computed purely from public information: `offline_#{shop}` [5](#0-4)  and `#{shop}_#{user_id}` [6](#0-5) , both used verbatim as the `Session#id` in `Session.from`. [7](#0-6) 
- `validate_auth_callback` puts this predictable id directly into the cookie `value` for non-embedded apps: `SessionCookie.new(value: session.id, expires: ...)`. [1](#0-0) 
- `SessionUtils.current_session_id` for a non-embedded app (or embedded app falling back to cookies) just returns `cookies[SESSION_COOKIE_NAME]` unchanged — there is no HMAC, signature, or any cryptographic binding checked against this value before it is used as the session lookup key. [2](#0-1) 

Because the id format is public and derivable from a known/guessable shop domain (`{shop}.myshopify.com` domains are enumerable/guessable, and Shopify user ids are small sequential integers), any unprivileged internet user who can set an arbitrary cookie value on a request to the host application (trivial — cookies are entirely client-controlled) can construct `offline_victim-shop.myshopify.com` or `victim-shop.myshopify.com_1` and present it as their session cookie. If the host application follows this gem's documented, intended usage — using `SessionUtils.current_session_id` to fetch the id and then loading the corresponding stored `Session` (with its access token) by that id, exactly as shown in the gem's own docs (`docs/getting_started.md`) — the gem hands back an id belonging to a different tenant with no verification that the requester ever completed OAuth for that shop.

This is a direct instance of the flagged bug class: **"a session id derived from unauthenticated bytes"** — `cookie_session_id`/`current_session_id` treat raw, attacker-controlled cookie bytes as an authenticated identity token, when nothing in this gem cryptographically binds that value to the OAuth flow that produced it.

### Impact Explanation
If the host app follows the gem's documented pattern (load session by the id `current_session_id` returns, then use that `Session`'s access token for API calls), an attacker who merely sets a guessed/forged cookie value can cause the app to resolve and act under a foreign shop's `Session`, i.e. **cross-tenant access** — one of the explicitly qualifying Critical impacts. No credentials, TLS interception, or privileged account are required; only knowledge of a target shop's domain (public) and, for online sessions, a plausible Shopify user id.

### Likelihood Explanation
Likelihood is high in any deployment that follows the gem's own documented session-id-from-cookie flow verbatim, since:
- The gem provides no signing/verification primitive for the cookie value at all (`SessionCookie` is a bare struct). [4](#0-3) 
- `current_session_id` performs a straight cookie read with no defense. [2](#0-1) 
- Offline session ids need only a shop domain to guess; online session ids need only a shop domain plus a small integer user id, both of which are frequently observable/enumerable.

### Recommendation
Do not use the raw, predictable session id as the cookie's bare value. Either (a) sign/HMAC the cookie value with `api_secret_key` (or a separate server secret) and verify that signature in `cookie_session_id`/`current_session_id` before trusting it, or (b) store an unguessable random token in the cookie that maps to the session id server-side instead of embedding the deterministic `shop`/`user_id`-derived id directly in client-visible, unauthenticated storage.

### Proof of Concept
1. App follows the documented flow: on request, calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for a non-embedded/offline flow, per `docs/getting_started.md`.
2. Attacker (any unprivileged internet user), knowing (or guessing) a victim shop domain `victim-shop.myshopify.com`, sends a request to the app with cookie: `shopify_app_session=offline_victim-shop.myshopify.com`.
3. `cookie_session_id` returns this raw string unchanged: `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` → `"offline_victim-shop.myshopify.com"`. [3](#0-2) 
4. This exactly matches the id that `Session.from` would have generated for the real victim session (`"offline_#{shop}"`). [8](#0-7) 
5. The host app looks up its session store using this id (as shown in the gem's own documented usage pattern) and retrieves the victim shop's real `Session`/access token, granting the attacker cross-tenant access — without ever completing OAuth for that shop.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end

        def from(shop:, access_token_response:)
          is_online = access_token_response.online_token?

          if is_online
            associated_user = T.must(access_token_response.associated_user)
            associated_user_scope = access_token_response.associated_user_scope
            id = "#{shop}_#{associated_user.id}"
          else
            id = "offline_#{shop}"
          end

          if access_token_response.expires_in
            expires = Time.now + access_token_response.expires_in.to_i
          end

          if access_token_response.refresh_token_expires_in
            refresh_token_expires = Time.now + access_token_response.refresh_token_expires_in.to_i
          end

          new(
            id: id,
            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,
            is_online: is_online,
            associated_user_scope: associated_user_scope,
            associated_user: associated_user,
            expires: expires,
            shopify_session_id: access_token_response.session,
            refresh_token: access_token_response.refresh_token,
            refresh_token_expires: refresh_token_expires,
          )
        end
