In `exchange_token` (`lib/shopify_api/auth/token_exchange.rb`), the shop used to build the HTTP client's base host — which receives `client_secret` and `subject_token` — comes directly from `jwt_payload.shop` (the `dest` claim), with no format/allowlist validation (unlike `migrate_to_expiring_token`, which calls `Utils::ShopValidator.sanitize!(shop)` on line 103). This differs from the `validate_auth_callback` OAuth flow where `auth_query.shop` is a field explicitly covered by `to_signable_string` in `lib/shopify_api/auth/oauth/auth_query.rb:34-43`, and is HMAC-verified as a whole unit against `Context.api_secret_key`. However, `dest` in the JWT is verified only via the JWT's own HS256 signature (`lib/shopify_api/auth/jwt_payload.rb:76-81`), and this only proves the token was signed by someone possessing `Context.api_secret_key` — the app's own secret — not that `dest` is a legitimate `*.myshopify.com` domain.

### Title
Missing shop-domain validation on JWT `dest` claim before Token Exchange host binding - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` builds the HTTP client used to POST the app's `client_secret` and `subject_token` using `dest_shop = jwt_payload.shop`, taken unsanitized from the JWT `dest` claim, unlike its sibling method `migrate_to_expiring_token`, which sanitizes the shop via `Utils::ShopValidator.sanitize!(shop)`.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#shop` simply strips `"https://"` from the `dest` claim [1](#0-0) , with no validation that the value is a `*.myshopify.com` (or otherwise Shopify-controlled) hostname. `exchange_token` then uses this value directly as `dest_shop`, builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, and passes it to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [2](#0-1) . The `HttpClient` derives its request host from `session.shop`, meaning `client_id`, `client_secret`, and `subject_token` in the POST body are sent to a host derived from an attacker-controllable claim. By contrast, `migrate_to_expiring_token` (same file) validates the `shop` parameter with `Utils::ShopValidator.sanitize!(shop)` before constructing the session [3](#0-2) , confirming that shop-domain sanitization is the library's own expected control for this exact host-binding operation — and it is absent in `exchange_token`.

This is the exact bug class from the report: an identity binding (host that receives the app's credentials) is enforced in one code path (`migrate_to_expiring_token`) but not in the structurally identical sibling path (`exchange_token`), analogous to `service.head` being read under lock in most places but not others.

### Impact Explanation
If the JWT's `dest` claim can be influenced to a non-Shopify host while still passing `aud == Context.api_key` and HS256 signature verification (i.e., signed by the app's own secret, which the app controls, or via any component that mints/relays session tokens without independently constraining `dest`), the app would emit its `client_secret` to that host — Critical-level `client_secret` exfiltration/SSRF with the app's credentials. Even absent an external forgery path, this is a High-severity SSRF-with-credentials risk class: the destination host for `client_secret` disclosure is bound only to `dest`, not to any allowlist of Shopify domains, breaking the "host validated == host that receives client_secret" identity binding called out in the rules.

### Likelihood Explanation
Exploitability depends on whether an attacker can supply or influence a JWT `dest` value that still verifies under HS256 with the app's `api_secret_key` — this requires either knowledge of the secret (out of scope per the rules) or a token-issuance path that doesn't itself constrain `dest`. I could not find, within the in-scope files, any additional caller that validates `dest`/`jwt_payload.shop` before invoking `exchange_token`, nor a shop domain constraint enforced by `JwtPayload` itself. This uncertainty limits confidence that a fully unprivileged path exists purely within this gem; the missing validation is a latent gap consistent with the report's "identity binding not enforced everywhere" pattern, but the concrete privilege-free trigger from this gem's code alone is not fully demonstrated.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) in `exchange_token`, mirroring `migrate_to_expiring_token`, before constructing `shop_session` and issuing the token-exchange request, so the host that receives `client_id`/`client_secret`/`subject_token` is always constrained to a valid Shopify domain regardless of the `dest` claim's raw value.

### Proof of Concept
Not independently reproducible from this gem alone — the exploit requires either a JWT signed with the app's own `api_secret_key` containing a non-Shopify `dest` (e.g., `"https://attacker.example.com"`), or an upstream token-issuance flaw. Given a valid such token: `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)` would compute `dest_shop = "attacker.example.com"` [4](#0-3)  and issue the POST containing `client_secret` to that host via `Clients::HttpClient.new(session: shop_session, ...)` [5](#0-4) .
