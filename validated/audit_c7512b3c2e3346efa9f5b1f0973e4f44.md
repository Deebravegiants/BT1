### Title
Stable-pool reserve skew deflates `AquariusStableLp` collateral price to force unfair liquidations - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The price aggregator prices `AquariusStableLp` collateral from the pool's *live* reserves (`get_reserves`) at read time. The fair-value formula `D * min(price_a, price_b) / shares` is strictly decreasing in reserve imbalance, so an unprivileged trader can skew the pool's reserves in the same transaction as a `liquidate` call, push a victim's health factor below 1 WAD, and seize their collateral at a liquidation bonus — then unwind the skew atomically. This mirrors the reported class: a permissionless entrypoint gated on a spot-manipulable valuation, with the manipulated state read fresh inside the triggering call.

### Finding Description
`read()` resolves both leg prices from external feeds but reads `reserve_a`/`reserve_b` and `total_shares` directly from the live Aquarius pool at the moment of the call: [1](#0-0) 

For stable pools the fair price is `solve_stable_d(x_wad, y_wad, amp) * min(price_a, price_b) / share_supply_wad`: [2](#0-1) 

`D ≤ x + y` and decreases monotonically as the reserves move away from balance, so `price_wad` can only be pushed *down* by skewing — exactly what an attacker needs against borrowers. Note the constant-product variant (`fair_lp_price_wad`, `2*sqrt(v_a*v_b)/shares`) is resistant because `v_a*v_b` is invariant under the constant-product constraint; the stable variant is not, because `D` is not invariant under reserve skew.

Liquidation eligibility is computed from this price inside the same transaction: `build_liquidation_plan` requires `totals.health_factor < Wad::ONE`, where the totals come from `calculate_account_risk_totals` using Context-resolved (strict) prices. [3](#0-2) 

`liquidate` is permissionless (the liquidator authenticates but need not own the target, per INV-LIQ-01), and seizure pays the liquidator collateral at a bonus (`SeizeMode::Transfer` pays underlying; `SeizeMode::Credit` credits supply shares). There is no TWAP, no smoothing, and no check that the pool reserves are near a historical state — the only bounds are the static `min_sanity_price_wad`/`max_sanity_price_wad` band, which leaves room for several-percent deflation on LP tokens whose fair price drifts anyway (mainnet config contains `AquariusStableLp` sources with wide sanity bands, e.g. ±10–20%).

### Impact Explanation
Forced liquidation of otherwise-healthy borrowers: the liquidator seizes victim collateral at the protocol liquidation bonus (plus the excess value in whole-unit/sub-3-decimal full closes). This is theft of user funds — value is transferred from the borrower to the attacker purely because of the transient price distortion. In the worst case a skew that drives the pool invariant solver to fail returns `NoLastPrice`/`InvalidPrice`, which fail-closes the oracle; the profitable regime is a moderate skew that keeps the derived price inside the sanity band but below the victim's liquidation boundary.

### Likelihood Explanation
- No privileged access required: the attacker swaps on the Aquarius stable pool with their own funds (or a `flash_loan` on flashloanable debt markets to fund the skew), calls `controller.liquidate`, and swaps back — all atomic within one Soroban transaction via a receiver contract, so the skew never needs to persist.
- Cost is the pool swap fee plus temporary slippage, recovered by the liquidation bonus; stable-swap curves make large notional skews cheap near balance.
- Constraint: the deflated price must remain ≥ `min_sanity_price_wad` and the pool must keep `D` solvable; this bounds the achievable deflation, so the attack only works on accounts near the liquidation threshold — which is the common case for levered LP collateral.

### Recommendation
Do not derive collateral value from spot pool reserves alone. Options: (a) price the stable LP share from a manipulation-resistant lower bound such as `min(v_a, v_b) * 2 / shares` style virtual reserves or an off-chain-attested LP NAV feed (`Feed`/`Scaled` source) instead of live reserves; (b) require a TWAP/historical reserve observation; (c) at minimum, add an on-chain check comparing current reserves against a stored/attested snapshot and reject large deviations.

### Proof of Concept
Conceptual transaction (single Soroban tx from an attacker contract):

1. Ensure victim account holds `AquariusStableLp` collateral with debt such that `HF = 1 + ε`.
2. In the attacker contract's entrypoint:
   a. `pool.swap(attacker, token_in=A, large_amount_in)` → reserves become `(x + Δ, y − δ)`; `solve_stable_d` yields `D' < D`, so `price_wad' < price_wad`.
   b. `controller.liquidate(attacker, victim_id, debt_payments, SeizeMode::Transfer)` → `calculate_account_risk_totals` resolves the LP price through `providers::aquarius::read`, which calls `get_reserves` and returns the deflated `price_wad'` → `weighted_collateral` drops → `HF < 1 WAD` → plan builds, attacker repays part of the debt and seizes collateral worth `repay * (1 + bonus)`.
   c. `pool.swap(attacker, reverse direction)` → restores reserves, recovering the skewed funds minus fees.
3. Attacker nets `bonus + recovered skew − fees`; victim loses collateral above what their true health justified.

Uncertainties: the precise deflation obtainable within `min_sanity_price_wad` for each configured stable market was not numerically verified; if bands are tighter than a few percent on every stable LP market, the feasible impact shrinks to near-threshold accounts only.
