### Title
`Webhooks::Registry.process` trusts unsigned `x-shopify-shop-domain` header as authenticated shop identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` covers exclusively the request body — never the `shop-domain` header. `WebhookMetadata#shop`, which host apps are documented to use as the key for loading a stored `Auth::Session` and its access token, is populated straight from that unsigned header, so it can diverge from the shop that actually produced/signed the body.

### Finding Description
The claimed binding is: `hmac_valid(raw_body, secret) == true` implies `request.shop == the_shop_that_produced(raw_body)`. Tracing the code shows this equality is never enforced:

- `Webhooks::Request#shop` reads `shopify_header("shop-domain")` directly with no cryptographic tie to the body: [1](#0-0) 
- `Webhooks::Request#to_signable_string` returns `@raw_body` only — headers, including the shop domain, are excluded from what is signed: [2](#0-1) 
- `Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it has no knowledge of, and does not check, `shop`: [3](#0-2) 
- `Registry.process` gates only on this body-HMAC check, then builds `WebhookMetadata` directly from `request.shop`: [4](#0-3) 

Because the header is excluded from the signable string, an attacker who legitimately receives one valid `(raw_body, hmac)` pair from Shopify (e.g., via their own dev shop and their own registered webhook endpoint) can replay that exact body and HMAC directly to the victim host app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value — `victim_shop.myshopify.com`. `HmacValidator.validate` still returns `true` because the body and HMAC are unchanged and match the shared `api_secret_key`; `Registry.process` then hands the handler a `WebhookMetadata` whose `shop` is `victim_shop.myshopify.com`. If the host app follows the documented pattern of "look up session by webhook shop → call Admin API with that session's token" (as shown in `docs/usage/webhooks.md`), it will authenticate an outbound Admin API call as the victim using a session the attacker never touched. None of `ShopValidator.sanitize!`, `state` comparisons, or `JwtPayload` checks apply here — those guard OAuth/App-Bridge session-token flows, not the webhook HMAC path, and `Context.setup?/private?/embedded?` play no role in `Registry.process`.

### Impact Explanation
An attacker can make an installed host app perform a real, authenticated Admin API call against any shop domain string of their choosing, provided the host app resolves sessions/tokens by the webhook's `shop` value (the pattern this gem's own docs recommend). This is a cross-tenant access issue: the attacker never sees or exfiltrates the victim's access token, but they can cause the host app to use it on their behalf, which matches the "Critical - cross-tenant access" / "forged webhook accepted" category. It is repeatable against any victim shop domain the attacker knows or guesses, at will, for as long as the attacker retains one valid `(raw_body, hmac)` pair from their own shop.

### Likelihood Explanation
Preconditions: (1) attacker has a working dev shop with the app installed, so they can receive at least one genuinely Shopify-signed webhook (any topic); (2) the host app's webhook controller is reachable over the internet (true by design, since Shopify itself must reach it); (3) the host app implements the documented "load session by `WebhookMetadata#shop`, then call Admin API" pattern, which is exactly what `docs/usage/webhooks.md` shows. No secrets, no TLS interception, and no privileged access are required — only capturing one's own legitimately-received webhook body+HMAC and re-POSTing it with a different `shop-domain` header. This is cheap and fully repeatable per victim shop domain.

### Recommendation
Bind the shop identity into the verified signature space, or otherwise stop treating the `shop-domain` header as trusted, authenticated data:
- Include the shop domain (and ideally topic/webhook-id) inside the signable string used by `HmacValidator`, or
- Require `Registry.process` callers/handlers to cross-check `WebhookMetadata#shop` against a shop that is otherwise known to be legitimately installed (e.g., verify it corresponds to a session that was created through a verified OAuth callback), and document clearly that `WebhookMetadata#shop` is not itself an authenticated value.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryShopSpoofTest < Test::Unit::TestCase
      def setup
        super
        @topic = "orders/create"
        @raw_body = '{"id":1}'
        @valid_hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @raw_body)
        )
      end

      def test_hmac_valid_but_shop_domain_is_attacker_controlled
        attacker_headers = {
          "x-shopify-topic" => @topic,
          "x-shopify-hmac-sha256" => @valid_hmac, # captured from attacker's own legitimate webhook
          "x-shopify-shop-domain" => "victim_shop.myshopify.com", # spoofed, not covered by HMAC
        }

        request = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: attacker_headers)

        # Equality check BEFORE: hmac validity vs claimed shop
        assert(ShopifyAPI::Utils::HmacValidator.validate(request), "hmac should validate: it only signs raw_body")
        assert_equal("victim_shop.myshopify.com", request.shop)

        handler_data = nil
        handler = TestHelpers::FakeWebhookHandler.new(->(data) { handler_data = data })
        ShopifyAPI::Webhooks::Registry.add_registration(topic: @topic, path: "path",
          delivery_method: :http, handler: handler)

        ShopifyAPI::Webhooks::Registry.process(request)

        # Equality check AFTER: Registry.process happily forwards the spoofed shop
        assert_equal("victim_shop.myshopify.com", handler_data.shop)
      end
    end
  end
end
```
This demonstrates that `Utils::HmacValidator.validate` and `Registry.process` never bind `request.shop` to the signed body, so a handler (and, per the docs' recommended pattern, any session lookup keyed on `WebhookMetadata#shop`) receives an attacker-chosen shop string despite a fully valid HMAC.
