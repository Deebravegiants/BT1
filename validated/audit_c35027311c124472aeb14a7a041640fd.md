### Title
Webhook shop-domain header used for tenant attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler [1](#0-0) . In reality, the HMAC signature only covers the raw request body, while the `shop` value handed to the handler for tenant attribution is taken from an unsigned HTTP header, breaking the binding `shop authenticated == shop used to route/attribute the webhook data`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`: [3](#0-2) 

`Registry.process` uses only this body-only HMAC check, then trusts the `shop` accessor (sourced from the `x-shopify-shop-domain` / `shopify-shop-domain` header, never from the signed bytes) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) [6](#0-5) 

`WebhookMetadata#shop` is the field the gem's own documentation instructs developers to use for tenant identification (`data.shop`) inside the handler, with no caveat that it is unauthenticated: [7](#0-6) [8](#0-7) 

Because the client secret used to compute the HMAC is shared by the app across every shop that has installed it (not per-tenant), any merchant who has installed the app can legitimately receive a webhook to their own endpoint with a valid `(raw_body, hmac)` pair, then replay that same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The HMAC check passes (it never inspects the header), and the handler is invoked believing the data originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an app installer for shop A can cause the app to process (and typically persist/act on) attacker-supplied webhook data under the identity of shop B. Depending on the handler's use of `data.shop` (e.g., looking up shop B's session/token to act on shop B's store, or writing data keyed by shop B), this can lead to cross-tenant data corruption or actions taken with another merchant's stored access token — matching the "Critical - cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (unprivileged) installer of the app on their own shop — no access to the app's `client_secret`, no privileged account, and no host/TLS manipulation. They can trivially capture a valid `raw_body`/`hmac` pair from their own real webhook deliveries and replay it with a forged `shop-domain` header value, since nothing in this gem binds that header to the signed bytes.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed input, or otherwise separately verify that the shop claimed in the header corresponds to a shop with an active, previously-established session/installation known to the app before invoking the handler. At minimum, update `VerifiableQuery`/`Request#to_signable_string` so the signature binds the shop identity, and document this requirement clearly since `Registry.process`'s current claim of verifying "the request did indeed come from Shopify" is misleading with respect to the `shop` field.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the attacker's server with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(client_secret, B)` — a valid, legitimately-issued pair.
3. Attacker sends a forged HTTP POST to the same app's webhook endpoint with the identical `raw_body = B` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `B` against the HMAC [9](#0-8) .
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged header value and invokes the app's handler, which treats the payload `B` as authentic data for `victim-shop.myshopify.com` [10](#0-9) .
