### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body when validating a webhook's authenticity, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the handler are taken from unauthenticated HTTP headers. This breaks the identity binding `verified_bytes == bytes_the_application_acts_on`, allowing a party who legitimately receives one valid `(body, hmac)` pair (e.g., a malicious merchant who installs the app on their own store) to replay that pair with a forged `shop` header and impersonate a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. However, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are never included in the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `to_signable_string` (the body) against the computed HMAC, and gives no signal about the header values: [3](#0-2) 

`Registry.process` calls this validator and, once it passes, unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata handed to the app's own webhook handler: [4](#0-3) 

Critically, the HMAC secret used to sign Shopify webhooks is the app's single `api_secret_key`, shared across every shop that installs the app — it is not shop-specific. Combined with the fact that `shop` is excluded from the signed content, any actor who can install the app on a shop they control (an "unprivileged internet user" from Shopify's perspective) can capture a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair from their own store's webhook delivery, then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` will still succeed because the signature only ever covers the body, and `Registry.process` will happily dispatch the forged event with `shop: <victim-shop>` to the app's handler.

This directly matches the documented usage contract: the gem's own docs claim `Registry.process` "will verify the request did indeed come from Shopify," implying full authenticity of the delivered fields, when in fact only the body bytes are verified: [5](#0-4) 

and instruct app authors to key their business logic directly off `data.shop`: [6](#0-5) 

The equality that should hold is:
`bytes_verified_by_HMAC (raw_body) == bytes_the_application_trusts_for_tenant_identity (shop header)`
This equality is false — `shop` is acted upon (used as the tenant key passed to the handler) but is entirely outside the HMAC-protected payload.

### Impact Explanation
This is a cross-tenant confusion vulnerability reachable by any unprivileged actor able to install the app on a shop they control (a normal, credential-free interaction for a public app). By replaying a self-obtained valid `(body, hmac)` pair with a spoofed `shop` header, they can make the host application process arbitrary webhook events (e.g., `app/uninstalled`, `customers/data_request`, `orders/create`) as if they originated from any other merchant using the app, since nothing in the verified payload ties the HMAC to the claimed shop. Depending on how the host app uses `data.shop` (e.g., to look up/delete a shop's session, to trigger data exports, or to update per-shop state) this can lead to cross-tenant data corruption, unauthorized data disclosure, or forced deauthorization of a victim shop — satisfying the "cross-tenant access" criterion for a Critical finding.

### Likelihood Explanation
Likelihood is high for any app that publicly allows installs: an attacker only needs to install the target app on their own store (a normal, unauthenticated onboarding flow from the attacker's perspective) to obtain a valid signed webhook body/HMAC pair, then can freely relabel the `shop`/`topic`/`webhook_id` headers when replaying it to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required — only the ability to receive a webhook on a self-owned shop, which is the normal installation flow the gem is designed to support.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content used by `to_signable_string`, or otherwise cryptographically bind them to the payload (e.g., verify them against a `webhook_id`/subscription record known to belong to the claiming shop) before passing `WebhookMetadata` to the handler. At minimum, document clearly that `Registry.process` only authenticates the raw body and that host applications must independently corroborate the `shop` header via their own subscription/session records before trusting it for tenant-scoped operations.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook delivery (e.g., `products/update`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — this HMAC is valid because it's computed with the app's single shared `api_secret_key`.
3. Replay the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the (unchanged) body, so `HmacValidator.validate` returns `true`.
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, `topic`, and `webhook_id` fully attacker-controlled, despite HMAC validation having "passed." [7](#0-6) [4](#0-3)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
