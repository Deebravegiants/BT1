### Title
Webhook `shop` (and topic/webhook_id/api_version) fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream by `Registry.process` and passed to the host application's webhook handler are taken directly from HTTP headers that are never included in the signed data. An attacker who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, causing the app to process attacker-controlled webhook data attributed to a victim shop.

### Finding Description
The binding that should hold is: `shop asserted to the handler == shop cryptographically bound by the signature`. In this gem that equality is broken.

`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from request headers with no cryptographic binding to the signature [2](#0-1) .

`Utils::HmacValidator.validate` only checks that the computed HMAC of `to_signable_string` (i.e., the raw body) matches the supplied `hmac` header, using the app's shared `api_secret_key` [4](#0-3) . It never inspects `shop`, `topic`, or any header field.

`Registry.process` uses this validation result as the sole authenticity gate, then immediately trusts `request.shop` (a bare header value) as the tenant identity forwarded to the app's handler via `WebhookMetadata` [3](#0-2) .

Because the `api_secret_key` used for the HMAC is a single app-wide secret (not per-shop), any shop that has installed the app can generate a validly-signed webhook body. That valid `(raw_body, hmac)` pair remains valid for **any** `shop-domain` header value, since the header is outside the signed data. Replaying it against another shop's identity constitutes a break of the shop-identity binding purely from the app's public webhook endpoint, with no access token, `api_secret_key`, or privileged account needed beyond installing the app on an attacker-controlled store to harvest a valid signature.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled shop can cause the host application (built on top of this gem's `Webhooks::Registry.process`/`WebhookMetadata`) to process forged webhook data while believing it originates from a different, victim shop — i.e., cross-tenant data injection/confusion, matching the Critical "cross-tenant access" category, since the gem's API offers no way for a correctly-integrated consumer to distinguish this forged event from a genuine one.

### Likelihood Explanation
Requires only that the attacker can install the app on a shop they control (a normal, unprivileged onboarding flow) to harvest one valid `(raw_body, hmac)` pair for a chosen topic, then POST it to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No secrets, tokens, or elevated access are required.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` fields in `Request#to_signable_string` (or otherwise cryptographically bind them, e.g., derive/verify the shop domain from a separate signed channel) so the HMAC check fails when any of these header-derived identity fields are altered relative to what was originally signed.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering a legitimate webhook, e.g., `orders/create`, delivered with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some `raw_body`.
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker POSTs the same `raw_body` and same `x-shopify-hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object with `shop == "victim.myshopify.com"` [5](#0-4) .
5. `Utils::HmacValidator.validate(request)` succeeds because it only hashes `raw_body` [4](#0-3) .
6. `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, delivering attacker-controlled data under the victim's tenant identity [6](#0-5) .
