### Title
`hostnameFromString` mis-parses URLs with a colon in the path/query, dropping exodus.io-scoped headers - ([File: adapters/fetch-factory/src/hostname.js])

### Finding Description
`hostnameFromString` checks for a port separator (`:`) before checking for the path (`/`) or query (`?`) separators: [1](#0-0) 
For a URL like `https://api.exodus.io/v1/prices?ids=btc:usd`, after stripping the `://` prefix, `hostname` becomes `api.exodus.io/v1/prices?ids=btc:usd`. `hostname.indexOf(':')` finds the colon inside `btc:usd`, which occurs *after* the `/`. Because the port check runs first, the code slices at that colon, producing `api.exodus.io/v1/prices?ids=btc` — a string that still contains a `/`. This fails `isValidHostname` (which uses `domainPattern`, disallowing slashes), so the function returns `null` instead of the correct hostname `api.exodus.io`.

This function is invoked from `getUrlHostname`, which is called by `FetchFactory#buildHeaders`: [2](#0-1) 
When `getUrlHostname` returns `null`, the `if (hostname)` branch is skipped, so no per-host header config (e.g. one registered for `exodus.io` via `setDefaultExodusIdentifierHeaders`, which sets `x-exodus-app-id`, `x-exodus-version`, `x-requested-with`) is merged into the outgoing request headers: [3](#0-2) 

The attacker-controlled input here is the URL/query string that gets fetched (e.g. price API queries with `ids=btc:usd`-like parameters, or other remote/dApp-influenced URLs containing a colon anywhere before the actual host-terminating `/` or `?`... more precisely, any colon anywhere in the path/query before the true delimiter). Since pricing/remote-config/NFT endpoints often accept caller/remote-supplied query parameters, a URL shaped to include a colon in its path or query value will silently defeat host-scoped header attachment.

### Impact Explanation
The scoped impact is limited to authentication/identification headers being **dropped**, not misdirected to a different attacker-controlled host — the fallback is `null`, not a substitute hostname, and `isValidHostname` rejects the malformed slice in this specific case, so it fails closed rather than fails open to a wrong host. This means requests to `exodus.io` may go out without `x-exodus-app-id`/`x-api-key` headers when the URL contains a colon in its path/query, which can break backend request identification/rate-limiting expectations, but does not itself leak secrets, misroute credentials to an attacker's origin, or enable unauthorized signing. There's no direct wallet-compromise path (no key material, no signing, no auth bypass into privileged state) — it is a header/availability correctness bug rather than an origin-binding security bypass to a malicious host.

### Likelihood Explanation
Triggerable whenever any fetch call is routed through a `FetchFactory` instance with a URL string containing a colon inside the path or query before the actual `/` (path) or `?` (query) delimiter — e.g., query parameter values containing `:` such as pair IDs (`btc:usd`), timestamps, or other colon-containing tokens. Reachable via any feature that lets user/remote data influence request URLs to `exodus.io`-hosted endpoints (pricing, NFTs, remote-config).

### Recommendation
Reorder the checks in `hostnameFromString` so the `/` and `?` delimiters are checked first (they always terminate the authority component before any port), and only treat a `:` as a port separator if it appears before the first `/` or `?`. Simplest fix: replace the custom parser with the native `URL`/`URL.parse` API, or compute `Math.min` of the first `/`, `?`, and `:` (port) indices to find the true end of the host component before slicing.

### Proof of Concept
Unit test in `adapters/fetch-factory/src/hostname.js` (or its test suite):
```js
import { hostnameFromString } from './hostname.js' // or getUrlHostname

test('hostname parsing matches native URL for colon-in-path/query', () => {
  const urls = [
    'https://api.exodus.io/v1/prices?ids=btc:usd',
    'https://api.exodus.io/path:with:colons/more',
    'https://api.exodus.io/v1/prices?a=1&b=x:y',
  ]
  for (const url of urls) {
    const expected = new URL(url).hostname
    expect(hostnameFromString(url)).toBe(expected) // currently fails, returns null
  }
})
```
Expected: `hostnameFromString` should return `api.exodus.io` for all cases; currently it returns `null`, demonstrating the header-dropping bug reachable from `FetchFactory#buildHeaders`.
