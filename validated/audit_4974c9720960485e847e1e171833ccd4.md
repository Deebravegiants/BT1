## Title
Webhook HMAC validation does not cover the `shop-domain` (or `topic`/`webhook-id`) header, allowing cross-tenant shop-identity spoofing in webhook processing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `Registry.process` binds solely to the payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values used by the host application to identify *which merchant* the webhook is for come from unauthenticated HTTP headers that are never included in the signed data.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received HMAC. [1](#0-0) 

For webhooks, `to_signable_string` is defined as just `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC over the body, then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler, which acts on that shop's behalf: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on (request.shop)`

Because `shop` is not part of `to_signable_string`, this equality never actually holds — the HMAC only proves "this body was signed with our `api_secret_key`" (a secret shared across *all* shops using this app), not "this body belongs to shop X." An unprivileged internet user who can obtain any one genuine `(raw_body, hmac)` pair for the app — trivially done by installing the app on their own store (or any store) and receiving one legitimate webhook delivery — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. The signature still validates because the HMAC never covered those headers, and the handler is invoked believing the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker can make the host application process attacker-controlled webhook content while asserting it came from an arbitrary target shop, since `WebhookMetadata.shop` (used by handlers to scope database writes, cache invalidation, credential lookups, redaction flows, etc.) is derived from an unauthenticated header. Depending on how the host app's handler uses `shop`, this enables cross-tenant data confusion/access (e.g., mandatory `shop/redact`, `customers/redact`, or `customers/data_request` handlers acting on the wrong tenant, or app data keyed by `shop` being corrupted/read across tenants).

### Likelihood Explanation
Medium-High: exploitation only requires the ability to (1) obtain one legitimate webhook body+HMAC pair for the app (achievable by any developer who installs the app on a store they control) and (2) send an HTTP request to the app's public webhook endpoint with forged headers — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or otherwise cryptographically bind them to the body before trusting them — e.g., verify the HMAC using a canonical string that concatenates the raw body with the shop-domain/topic headers, or require the host application to cross-check `request.shop` against an out-of-band known list of installed shops before acting on the payload. At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Install the app on an attacker-controlled store `attacker.myshopify.com` and trigger any subscribed webhook topic, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC(api_secret_key, B)`).
2. Send a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - `X-Shopify-Topic`: optionally forged to another registered topic
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`. [4](#0-3) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` and performs its action believing it is legitimately processing `victim.myshopify.com`'s data, even though the content and trigger originated entirely from the attacker's own store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
