Found it: the Tron version of `IntentGatewayV2` reimplements the entire gateway logic and its `onAccept`/`withdraw` path is missing the `_checkRelayer` gate that the canonical EVM version (`ExtrinsicIntents.sol`) enforces on every privileged delivery path.

### Title
Tron `IntentGatewayV2.onAccept`/`onGetResponse` lack the relayer authorization gate present in the canonical EVM implementation - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2` composes `ExtrinsicIntents`, whose `onAccept` and `onGetResponse` call `_checkRelayer(incoming.relayer)` as the very first statement before any request body is decoded [1](#0-0) , and again in `onGetResponse` [2](#0-1) . This gate restricts which relayer's delivered proof is honored once one has been configured (`setRelayer`), consistent with the documented delivery-authorization model [3](#0-2) .

The Tron port of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is a separate, hand-duplicated implementation (not inheriting `ExtrinsicIntents`) that has no `_relayer` state, no `setRelayer`, and no relayer check anywhere in its `onAccept` or `onGetResponse`: [4](#0-3) [5](#0-4) .

### Finding Description
This mirrors the OpenClaw root cause precisely: "owner-only enforcement depended on tool-name checks and was not consistently metadata-driven across all call paths" — here, the relayer-restriction check is applied per-call-path in one implementation and simply absent from a duplicated call path (the Tron contract) that reaches the exact same privileged actions (`NewDeployment`, `UpdateParams`, `SweepDust`, `RedeemEscrow`, `RefundEscrow`).

Both contracts gate `onAccept` with `onlyHost`, so `msg.sender` must be the local Hyperbridge host [6](#0-5) , and both additionally check `incoming.request.source == hyperbridge()` before applying `NewDeployment`/`UpdateParams`/`SweepDust` [7](#0-6) . That part is present and correct in the Tron version. What is missing is the second layer of the model used everywhere else in the codebase: once a message is authenticated as coming from Hyperbridge through the host, the EVM implementation additionally restricts which *relayer* (the address that physically submitted the proof to `HandlerV2`) is trusted to deliver it, via `_checkRelayer`. The Tron implementation has no such concept at all — any relayer (not just the intended authorized one) can deliver `RedeemEscrow`/`RefundEscrow` withdrawal messages and any of the governance-restricted actions once they pass host+Hyperbridge-source checks.

### Impact Explanation
Because the relayer restriction is a defense-in-depth control specifically intended to let governance restrict which relayer address may deliver messages to a given gateway deployment (per the documented flow: "Only then is the first body byte read... A gateway whose `_relayer` is zero accepts every relayer"), its complete absence in the Tron gateway means that contract can never be locked down to an authorized relayer set. On the EVM gateway this is an explicit governance control (`setRelayer`, reachable via the `Execute` discriminator) used to prevent unauthorized parties who might obtain forged, malformed, or front-run proof submissions from being the first to deliver sensitive messages (dust sweeps, param updates, deployment registration, escrow releases) to the gateway. The Tron deployment permanently lacks this control, silently diverging from the security model documented and tested for the EVM implementation, and cannot be remediated at runtime (no `setRelayer`/`_relayer` state exists to add without a contract upgrade). This is an authorization completeness gap consistent with CWE-863 (incorrect authorization) reachable by any relayer able to submit a valid Hyperbridge-verified proof — i.e., an unprivileged message dispatcher/relayer path.

### Likelihood Explanation
Any relayer that can successfully deliver a Hyperbridge-verified message to the Tron `IntentGatewayV2` (a normal, permissionless relaying operation) automatically reaches every `onAccept`/`onGetResponse` action without the extra relayer-authorization check that exists on all other chains' gateway. No special privilege beyond being any relayer is required, exactly matching the "authenticated non-owner ... reach broader-than-intended owner-only actions" pattern in the referenced advisory, translated to "any relayer reaches privileged-relayer-only delivery paths."

### Recommendation
Bring `evm/tron/contracts/apps/IntentGatewayV2.sol` in line with the canonical implementation: add `_relayer` storage, a `setRelayer` function reachable only via the host (mirroring `ExtrinsicIntents._checkRelayer`/`setRelayer`), and call the same check as the first statement in both `onAccept` and `onGetResponse`, exactly as done in `ExtrinsicIntents.sol`. Longer term, refactor the Tron contract to inherit from the shared `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` composition (as the canonical EVM `IntentGatewayV2.sol` does) instead of maintaining a hand-duplicated copy, so that authorization logic is centralized and cannot drift out of sync across chain-specific ports.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` contract and note it has no `_relayer` variable, `setRelayer` function, or any relayer-identity check in `onAccept`/`onGetResponse`.
2. Compare against `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, which calls `_checkRelayer(incoming.relayer)` unconditionally at the top of both callbacks before any body decoding.
3. On the EVM gateway, once governance calls `setRelayer(authorizedRelayer)` (via the host-only `Execute` path), any delivery submitted by a different relayer reverts with `Unauthorized` and is retryable only by the authorized relayer.
4. On the Tron gateway, no equivalent mechanism exists — an identical Hyperbridge-verified message routed through any relayer is accepted by `onAccept`/`onGetResponse` regardless of which account submitted the proof, since the only checks present are `onlyHost` and (for governance actions) the Hyperbridge-source check, neither of which restricts relayer identity.

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
