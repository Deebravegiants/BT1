Based on my investigation, I found a strong Aptos-native custody analog to the reported fee-evasion bug class, rooted in `aptos-framework/sources/fungible_asset.move`. I was unable to fully re-verify `object.move`'s `transfer`/`allow_ungated_transfer` implementation details in this session (ran out of tool calls), so I note that caveat below, but the core evidence comes directly from the framework's own documented design intent.

### Title
Fungible-asset custody/compliance hooks (denylist, pause, fees) can be bypassed via raw object-layer store transfer unless the issuer explicitly opts into `Untransferable` - (File: `aptos-move/framework/aptos-framework/sources/fungible_asset.move`)

### Summary
The Aptos `dispatchable_fungible_asset` framework lets an FA issuer override `withdraw`/`deposit` semantics (pause, denylist, fees, deflation) by registering dispatch hook functions on the FA's `Metadata` object. However, a `FungibleStore` is itself a normal Aptos `Object`. Unless the issuer explicitly calls the object-layer protection (`Untransferable`, applied at `create_store` time only if `is_untransferable(metadata)` is already true), the store object can be moved to a different owner using the generic object-transfer path, which changes the store's owner/balance holder without ever invoking `withdraw_sanity_check`, `deposit_sanity_check`, or the registered withdraw/deposit dispatch hooks.

### Finding Description
`fungible_asset.move` defines: [1](#0-0) 

and `create_store` only marks a store untransferable if the metadata object already carries the `Untransferable` marker resource: [2](#0-1) 

All of the compliance/economic logic (pause flags, denylists, per-transfer fees, deflation) that issuers build via `dispatchable_fungible_asset::register_dispatch_functions` is enforced only inside the `withdraw`/`deposit` dispatch path: [3](#0-2) 

and the sanity checks that gate this path (`withdraw_sanity_check_impl` / `deposit_sanity_check`) only check store ownership and the `frozen` flag on the `FungibleStore` — they say nothing about, and cannot prevent, a transfer of the underlying `FungibleStore` object itself: [4](#0-3) 

Because `FungibleStore` is `has key` and behaves as a standard Aptos object (unless explicitly marked `Untransferable`), its owner can call the generic object-transfer entry point to reassign the object's owner to any address. This moves the entire balance held in that store to the new owner without going through `fungible_asset::withdraw`/`deposit`, so none of the pause check, denylist check, or fee logic implemented in the issuer's custom `withdraw`/`deposit` functions (as demonstrated by the `fa_coin` and `usdk` patterns that only guard the dispatch path) ever executes.

This is structurally identical to the reported `TokenFactory` bug: fee/compliance logic is enforced only on one designated transfer path (bonding-curve buy/sell there; dispatchable `withdraw`/`deposit` here), while an alternate custody-transfer path (open-market DEX trade there; raw object ownership transfer here) moves the same value without triggering that logic.

### Impact Explanation
For any live, mainnet fungible asset that relies on dispatchable hooks for regulatory/compliance controls (denylist, pause, transfer allowlist) or for economic controls (fees, deflation) — and that does not additionally opt into `Untransferable` — an unprivileged holder can:
- Move funds to a denylisted/sanctioned address, defeating the denylist invariant.
- Continue transferring value while the asset is "paused," defeating the pause invariant.
- Evade any deposit/withdraw fee or deflation logic entirely.

This directly corrupts the custody invariant "fungible asset metadata, dispatchable hooks, and freeze state must preserve supply and holder identity" for any deployed asset depending on the hook mechanism as its sole enforcement point, moving value to an unintended/unauthorized holder.

### Likelihood Explanation
Medium-to-High: any account with a non-frozen secondary or primary `FungibleStore` object it owns can trigger this by using the ordinary object-transfer flow instead of the FA transfer flow. The precondition — the issuer not calling the `Untransferable` opt-in when registering dispatch hooks — is easy to miss because the framework does not enforce or default to it when `register_dispatch_functions` is called; nothing in `dispatchable_fungible_asset::register_dispatch_functions` couples hook registration to `Untransferable`.

### Recommendation
- Have `fungible_asset::register_dispatch_functions` (or `dispatchable_fungible_asset::register_dispatch_functions`) automatically set the metadata's `Untransferable` marker (or otherwise force `disable_ungated_transfer` on every store created for that metadata) whenever withdraw/deposit dispatch functions are registered, so compliance/fee-bearing FAs cannot have their stores moved outside the hook path.
- Alternatively, make `create_store` unconditionally check for the presence of dispatch functions on the metadata (not just `Untransferable`) and disable ungated transfer in that case.
- Document/require issuers of denylist, pause, or fee-charging FAs to call the untransferable/ungated-transfer-disabling API, and add a Move verification/lint rule flagging dispatch-hook registration without corresponding untransferability.

### Proof of Concept
1. Issuer deploys an FA (e.g., following the `fa_coin`/`usdk` pattern) and calls `dispatchable_fungible_asset::register_dispatch_functions` to enforce `assert_not_paused()` / `assert_not_denylisted()` on every `withdraw`/`deposit`, but does **not** call anything that sets the `Untransferable` marker on the metadata.
2. Governance calls `set_paused(true)` (or denylists address `B`).
3. Holder `A`, who owns a secondary `FungibleStore` object for this FA with a nonzero balance, calls the generic object transfer entry function on that `FungibleStore` object, changing its owner to `B`.
4. Because this path never calls `fungible_asset::withdraw`/`deposit`, `assert_not_paused()`/`assert_not_denylisted()` never execute; `B` now controls the full balance held in that store despite the pause/denylist state, and no fee/deflation logic in the dispatch hooks ever ran.

**Note on verification limits:** I confirmed the framework's own `Untransferable` doc comment and the `create_store` logic proving stores are transferable-by-default at the object layer, and confirmed the dispatch/sanity-check code path only guards `withdraw`/`deposit`, not object ownership transfer. I was not able, within this session's remaining tool budget, to re-read `object.move`'s `transfer`/`disable_ungated_transfer` implementation in full to double-check whether some other mainnet-wide default (e.g., a global gating condition applied to all objects, or a primary-store-specific restriction) independently blocks this path for all FA stores. If such a global restriction exists and applies uniformly to every `FungibleStore`, this finding would be mitigated to the extent that already-issued primary stores are covered, but it would not explain why the framework ships an explicit opt-in `Untransferable` mechanism specifically for FA stores if ungated transfer were already disabled by default.

    /// Allow an object to hold a store for fungible assets.
    /// Applications can use this to create multiple stores for isolating fungible assets for different purposes.
    public fun create_store<T: key>(
        constructor_ref: &ConstructorRef, metadata: Object<T>
    ): Object<FungibleStore> {
        let store_obj = &constructor_ref.generate_signer();
        move_to(
            store_obj,
            FungibleStore { metadata: metadata.convert(), balance: 0, frozen: false }
        );

        if (is_untransferable(metadata)) {
            constructor_ref.set_untransferable();
        };

        if (default_to_concurrent_fungible_balance()) {
            move_to(
                store_obj,
                ConcurrentFungibleBalance {
                    balance: aggregator_v2::create_unbounded_aggregator()
                }
            );
        };

        constructor_ref.object_from_constructor_ref<FungibleStore>()
    }

            if (features::is_function_value_dispatch_enabled()) {

                dispatchable_withdraw(

                    borrow_transfer_ref(store),
                    func,

        } else {
            fungible_asset::unchecked_withdraw(store.object_address(), amount)
        }
    }
