### Title
Webhook shop-domain identity not bound by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, never the shop-domain header. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body+HMAC pair is valid and then hands the handler a `WebhookMetadata` object built from the *unauthenticated* `shop` header, breaking the identity binding `HMAC-verified bytes == data acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic coverage [2](#0-1) . `HmacValidator.validate_signature` computes the signature purely from `to_signable_string` (i.e., the body) and compares it against the received `hmac` header [3](#0-2) . `Registry.process` performs exactly this HMAC check and then immediately trusts `request.shop` to build the payload dispatched to the app's handler [4](#0-3) .

Because the same `api_secret_key` is shared across every shop installation of the app, a body+hmac pair generated for one shop's webhook remains a *valid* signature no matter which value is placed in the `shop-domain` header — the header is never part of the signed material. This is structurally identical to the reported bug class: a value that is *acted upon* (the recipient/target identity) is not covered by the authentication check that gates the action, so the check answers permissively for an attacker-chosen identity.

Equality that should hold but doesn't:
`shop used by handler.handle(...)` == `shop bound inside the HMAC-verified payload`
In reality: `shop used by handler.handle(...)` == `attacker-controlled request header`, while the HMAC only proves: `body used by handler.handle(...)` == `body signed by Shopify`.

### Impact Explanation
An attacker who can obtain one genuine webhook delivery for the app (e.g., by installing the app on a shop they control, or replaying a previously captured legitimate webhook) can resend the identical body and HMAC signature while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim tenant. Any host application that follows the gem's documented flow — calling `ShopifyAPI::Webhooks::Registry.process` and keying its own storage/business logic off `WebhookMetadata#shop` — will process the forged event as if it originated from the victim shop, leading to cross-tenant data corruption or unauthorized state changes keyed on shop domain. This lines up with the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid webhook body/HMAC pair for the shared `api_secret_key`, which is trivially obtainable by any merchant who installs the app on their own store (an "unprivileged internet user" relative to other tenants of the same app) and captures the raw webhook request. No access token, `client_secret`, or privileged credential is required. The replay only needs a header rewrite, no cryptographic work.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting an unauthenticated header:
- Include the shop domain (and/or a per-shop secret/lookup) in the HMAC-signable material, or
- After HMAC validation, require the caller to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation for this app before dispatching to handlers, and document this requirement prominently since `Registry.process` currently gives no such guarantee.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering topic `X` and capturing the resulting webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and header `H` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (no header integrity check) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` and `H` [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [7](#0-6)  and performs the app's business logic against the victim shop's stored data, even though the payload actually originated from the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
