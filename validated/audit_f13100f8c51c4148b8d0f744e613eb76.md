I found a real, injected custody bug in the timelock feature bolted onto `multisig_account.move` in this fork. It reduces to the same class as the reported "predecessor" bug: a control-flow check (here, the timelock/override-approval gate) can be satisfied using votes that are not actually authoritative for the timelock bypass, allowing a transaction against multisig-held funds to execute earlier than the invariant intends.

### Title
Timelock override bypass via implicit/self-approval inflation in `multisig_account::can_execute_with_timelock` - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The multisig timelock feature is meant to force a mandatory waiting period (`timelock_period`) before a transaction can execute, unless a higher `override_threshold` of approvals is reached. However, `num_approvals` used to check the override threshold is the same value computed for the ordinary quorum check, which includes an "implicit approval" from the executing owner even if that owner never explicitly voted [1](#0-0) . This lets the timelock override threshold be reached with fewer genuine, recorded votes than intended, undermining the timelock's purpose of giving owners a delay window to detect and cancel malicious/compromised proposals before funds move.

### Finding Description
`can_execute_with_timelock` decides whether a pending multisig transaction can bypass the timelock: `(override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock` [2](#0-1) .

The `num_approvals` value fed into this check is computed in `validate_multisig_transaction` (the VM prologue) as follows: it first counts recorded votes via `num_approvals_and_rejections`, then — critically — adds one more implicit approval for the *executing* owner if that owner hasn't explicitly voted yet [3](#0-2) . This same inflated `num_approvals` is then reused for the timelock override check [4](#0-3) .

The identical pattern exists in `can_execute` (the view-function analog), which likewise adds an implicit approval for the queried owner before evaluating `can_execute_with_timelock` [5](#0-4) .

This means: if `num_signatures_required = k` and `override_threshold = k+1` (the minimum legal value per the stated invariant "must be greater than num_signatures_required" [6](#0-5) ), then a transaction with only `k` genuine recorded approvals can be executed immediately, bypassing the timelock entirely, because the executing owner's implicit approval pushes the count to `k+1` — satisfying `override_threshold` — even though that owner cast no explicit, auditable vote for override.

This breaks the intended custody invariant: the timelock is supposed to require `override_threshold` *distinct, explicit* approvals (a strictly higher bar than ordinary quorum) before allowing early execution of a transaction that can move the multisig-controlled resource account's assets (APT, coins, or any object/FA the multisig owns/controls). Instead, the bar collapses to functionally the same threshold as ordinary quorum plus one non-recorded, automatic vote, effectively making `override_threshold = k+1` no stronger a guarantee than plain quorum `k` in the "last approver executes" pattern.

### Impact Explanation
Multisig accounts on Aptos are resource accounts that routinely hold APT and other assets and can also govern object/code-object ownership. The timelock/override design signals to owners that a proposal needs a delay window (for detection/veto of compromised-owner or malicious proposals) unless a supermajority explicitly overrides it. Because the "supermajority" can be silently satisfied with one phantom implicit vote, an attacker who compromises or colludes with `k` owners (the ordinary quorum) — not `k+1` — can execute a fund-draining or ownership-reassignment transaction immediately, defeating the entire purpose of the timelock safety control and enabling premature/unauthorized movement of custodied value. This is a High severity custody-control-bypass: it doesn't corrupt raw balances directly, but it removes the intended additional-authorization gate protecting fund/ownership-changing transactions.

### Likelihood Explanation
Likelihood is high wherever a timelock is configured with `override_threshold == num_signatures_required + 1` (the minimum allowed per the input validation, presumably the common/default configuration), and the last approver is also the executor (a normal, expected usage pattern where whichever owner satisfies quorum then calls execute). This requires no external exploit tooling — it's an inherent property of the current implicit-approval accounting reused for the override check.

### Recommendation
Compute a separate, strict approval count for the override-threshold check that only counts *explicit* recorded votes (`num_approvals_and_rejections` without the implicit executor bump), so `override_threshold` genuinely requires that many distinct owners to have proactively voted "approve," not merely reached ordinary quorum via the auto-added executor vote. Alternatively, explicitly document/enforce that `override_threshold` be validated against `num_signatures_required + 2` at minimum to compensate — but the cleaner fix is separating the two counts in `validate_multisig_transaction` and `can_execute`.

### Proof of Concept
1. Create a multisig account with `num_signatures_required = 2`, 3 owners (A, B, C), and enable timelock with `override_threshold = 3` disabled... actually use minimum legal value `override_threshold = 3` requires all 3; instead configure `override_threshold = 3` is the max-strict case. Use `num_signatures_required = 1`, owners {A, B}, `override_threshold = 2` (the minimum legal value, `> num_signatures_required`).
2. Owner A creates a transaction (no one votes explicitly besides A's implicit creation vote, if any).
3. Owner B calls execute directly without ever explicitly voting to approve.
4. In `validate_multisig_transaction`, recorded explicit approvals = 1 (A, if creation counts) or 0; the implicit-approval bump for B (the executor) adds +1, making `num_approvals = 2`, meeting `override_threshold = 2`.
5. `can_execute_with_timelock` returns `true` via the override branch even though `elapsed < timelock`, and the transaction executes immediately, moving the multisig's assets — with only 1 genuinely recorded vote plus B's non-explicit implicit approval, rather than 2 distinct explicit override votes.

Due to index size limits, I was not able to pull the full contiguous listing of `approve_transaction`/`vote_transaction`/`create_transaction` to verify whether the creator's vote is explicit or also implicit — a Devin session with full repo access would be needed to confirm the exact minimal owner-collusion count and finalize the PoC with concrete test code.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
