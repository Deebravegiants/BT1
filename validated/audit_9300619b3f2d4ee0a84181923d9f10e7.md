Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers via `shopify_header` [2](#0-1) . `Registry.process` only validates the HMAC over that signable string (the body) and then hands `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler without any of them being covered by the signature [3](#0-2) .

### Title
Webhook shop-domain (and topic/webhook-id) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body. The `shop-domain`, `topic`, and `webhook-id` HTTP headers — which the gem passes on to the app's handler as the authoritative identity of the event — are never included in the HMAC-signed content, so their values are effectively unauthenticated attacker-controlled input once a valid `(body, hmac)` pair is obtained for any tenant.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the HMAC using `verifiable_query.to_signable_string` [4](#0-3) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . This means the equality the code implicitly relies on — "the shop/topic/webhook-id the handler acts on == the shop/topic/webhook-id Shopify actually signed" — does not hold, because Shopify's HMAC (`X-Shopify-Hmac-Sha256`) is computed purely over the JSON body, and the gem never binds the `shop-domain` header (or `topic`/`webhook-id`) into that signature check itself.

Any party that legitimately receives a real webhook for shop A (e.g., a merchant who has installed the same multi-tenant app on their own store, or anyone able to observe the delivery) can replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint while substituting a different `shop-domain` header value (shop B). Since `HmacValidator.validate` only checks the body/hmac pair, `Registry.process` will accept the request as valid and invoke the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-chosen `shop` value [5](#0-4) .

### Impact Explanation
This breaks the identity binding between "the tenant Shopify authenticated this webhook for" and "the tenant the app processes the webhook as." Any host application that trusts `WebhookMetadata#shop` returned by this gem to select which merchant/session/tenant record to update (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into writing or acting on data under the wrong shop, i.e., cross-tenant access/confusion, using only a legitimately-received webhook payload as raw material and no privileged credentials.

### Likelihood Explanation
Exploitability requires the attacker to obtain one genuine `(raw_body, hmac)` pair from Shopify for a topic/body they control (trivial for any merchant with the app installed, since they receive real webhooks for their own shop) and then send it to the app's public webhook endpoint with a forged `shop-domain` header. `Registry.process` performs no additional check that the signed body's shop matches the declared shop header, so the forged request passes verification unconditionally [3](#0-2) .

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable content computed by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them (e.g., verify the shop domain against Shopify's `X-Shopify-Shop-Domain` value combined into the HMAC input, matching Shopify's documented webhook verification which signs the body — if headers can't be added to the signature per Shopify's spec, at minimum require the host app to cross-check `request.shop` against a known/allow-listed installed-shop list before trusting it, and document this requirement prominently since the gem currently implies the value is already verified).

### Proof of Concept
1. Attacker installs the multi-tenant app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) — Shopify delivers a POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays this request to the app's public webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed [6](#0-5) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because `to_signable_string` returns `B`, unaffected by the header tampering [7](#0-6) .
5. The handler is invoked with `WebhookMetadata` reporting `shop: "victim.myshopify.com"` even though Shopify never generated this event for that shop [5](#0-4) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
