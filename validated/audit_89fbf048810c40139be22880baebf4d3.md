### Title
Bandwidth tier revocation after purchase-time check permanently strands buyer funds with no refund path - ([File: evm/src/apps/BandwidthManager.sol], [File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`BandwidthManager.purchase()` validates the tier against a locally cached `tierPrice` on the source chain and immediately pulls the fee token from the buyer, then fires an ISMP POST with `timeout: 0` to `pallet-bandwidth` on Hyperbridge. The pallet is the sole source of truth for whether a tier is actually purchasable (`Tiers` storage, mutated by the admin-only `set_tier` call). If governance revokes the tier (`set_tier(tier, None)`) in the window between the buyer's on-chain payment and relayer delivery of the purchase message, the pallet-side credit fails with `UnknownTier`, the buyer's funds are never refunded, and because the dispatch carries `timeout: 0` there is no timeout-based recovery path either. This is directly analogous to the reported Vault issue: a legitimate parameter change made by the protocol operator (lowering max leverage / revoking a tier) retroactively invalidates an already-committed user action (an open leveraged position / an already-paid purchase), unfairly harming the user who acted correctly under the parameters in effect at submission time.

### Finding Description
- `BandwidthManager.purchase()` on the EVM side reads `tierPrice[tier]` — a locally-cached copy of pricing pushed by governance via `SetTiers` — and if non-zero, pulls `amount` of fee token from `msg.sender` immediately: [1](#0-0) 
- It then dispatches a `BandwidthPurchaseMsg` to `pallet-bandwidth` on Hyperbridge: [2](#0-1) 
- The pallet is the only party with authoritative knowledge of whether the tier is actually valid, via `Tiers<T>` storage, and any `AdminOrigin` account can revoke a tier at any time by calling `set_tier(tier, None)`: [3](#0-2) 
- The pallet's own error enum documents that a purchase referencing a tier without a `TierConfig` is rejected as `UnknownTier`: [4](#0-3) 
- There is no synchronization mechanism between the EVM-side `tierPrice` cache used at purchase-time and the pallet-side `Tiers` map that ultimately gates the credit; a revocation dispatched by governance (`set_tier`) can land on Hyperbridge before the buyer's already-signed, already-paid purchase message is delivered by a relayer.
- Once the buyer has paid (fee token pulled into the `BandwidthManager` contract) and the corresponding purchase message fails to credit on the pallet side (because the tier no longer exists), there is no code path in `BandwidthManager.sol` that returns the payer's funds: the only fund-movement action reachable via governance is `Withdraw`, which sends to an arbitrary `beneficiary` chosen by governance, not automatically back to the original buyer.
- The purchase dispatch is fire-and-forget with `timeout: 0`, so there is also no ISMP timeout callback that could trigger an automatic on-chain refund once the message becomes permanently undeliverable.

### Impact Explanation
A buyer's fee-token payment can become permanently and irrecoverably stuck in the `BandwidthManager` contract whenever governance revokes a tier between the buyer's payment and message delivery — an ordinary, non-malicious governance action (adjusting product configuration) that unfairly strands legitimate user funds, exactly mirroring the reported class of bug (a parameter change retroactively invalidating an already-committed user action, to that user's detriment, with no recovery mechanism). This is a permanent freezing-of-funds condition for the affected buyer(s), satisfying the Medium-severity bar for unbacked/irrecoverable loss of escrowed value.

### Likelihood Explanation
This requires no attacker and no malicious governance intent — it is a natural race between routine tier configuration updates (which the pallet explicitly supports via `set_tier`) and normal relayer delivery latency of an ordinary purchase message. Any tier price change, deprecation, or migration performed by the protocol operator while purchases are in flight triggers this condition for any buyer whose message has not yet been delivered, making it a realistic operational hazard rather than a contrived edge case.

### Recommendation
Add a refund path for undeliverable/rejected purchase messages: either (a) have the pallet dispatch a compensating `Refund` message back to the `BandwidthManager` when it rejects a purchase (`UnknownTier`, `InvalidPurchaseBody`, etc.) so the contract can return funds to the original payer, or (b) set a non-zero `timeout` on the purchase dispatch and implement an `onPostRequestTimeout` handler in `BandwidthManager.sol` that refunds the payer automatically when the message times out unprocessed. Additionally, consider a grace period on `set_tier` revocation (e.g., mark tiers deprecated rather than immediately removing `TierConfig`) so in-flight purchases against a soon-to-be-revoked tier can still be honored.

### Proof of Concept
1. Governance configures `TierOne` on the pallet and pushes its price to `BandwidthManager` via `SetTiers`.
2. Buyer calls `purchase(app, TierOne, months, chain)` on `BandwidthManager`; the contract validates `tierPrice[TierOne] != 0`, pulls the fee token, and dispatches the `BandwidthPurchaseMsg` with `timeout: 0` (see [5](#0-4) ).
3. Before a relayer delivers the message, governance calls `set_tier(TierOne, None)` on Hyperbridge, removing the `TierConfig` (see [6](#0-5) ).
4. The relayer delivers the purchase message; the pallet's purchase handling rejects it with `UnknownTier` because `Tiers::<T>::get(TierOne)` is now `None`.
5. No credit is issued to `(app_chain, app)`, and because the dispatch had `timeout: 0` and there is no refund action in `BandwidthManager.sol`'s `onAccept`/action set (only `SetTiers` and `Withdraw`, see [7](#0-6) ), the buyer's fee-token payment remains permanently locked in the `BandwidthManager` contract with no recovery mechanism available to them.

		#[pallet::call_index(3)]
		#[pallet::weight(T::DbWeight::get().writes(1))]
		pub fn set_tier(
			origin: OriginFor<T>,
			tier: TierIndex,
			config: Option<TierConfig>,
		) -> DispatchResult {
			<T as pallet_ismp::Config>::AdminOrigin::ensure_origin(origin)?;
			match config {
				None => Tiers::<T>::remove(tier),
				Some(cfg) => {
					ensure!(cfg.bytes > 0 && cfg.duration_secs > 0, Error::<T>::InvalidTierConfig);
					Tiers::<T>::insert(tier, cfg);
				},
			}
			Self::deposit_event(Event::TierSet { tier, config });
			Ok(())
		}
