### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` uses to identify which tenant/handler an event belongs to are taken from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `to_signable_string` (the raw body) matches the `hmac` header using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts any request that passes this body-only check and then dispatches to the handler using the *unverified* `shop`, `topic`, and `webhook_id` header values: [4](#0-3) 

This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop delivered to the handler`. The signature proves "this exact body was signed with our secret at some point," not "this shop-domain/topic/webhook-id header is genuine for this body." Any party who can obtain one valid `(raw_body, hmac)` pair — trivially achievable by installing the app on their own store and capturing a legitimate webhook — can replay that exact body to the app's public webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers to point at a different shop, topic, or webhook id. `Registry.process` will accept it as valid and hand the forged identity straight to the registered handler.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler will act as if the payload originated from and pertains to a shop/topic it never actually did. Depending on what handlers do with `WebhookMetadata#shop` and `#topic` (e.g., look up a shop's session, trigger app/uninstalled cleanup, process GDPR data-request/erasure logic, or update shop-scoped records), an attacker-controlled replay can cause the app to perform tenant-scoped actions attributed to a victim shop that never sent that event — data corruption, incorrect session/session-data deletion, or misclassification of webhook payloads under the wrong shop/topic. This falls under cross-tenant access.

### Likelihood Explanation
Moderate. The attacker needs one legitimately signed `(body, hmac)` pair, which is easy to obtain by installing the target app on an attacker-controlled test shop (any unprivileged merchant can do this) or by observing one webhook delivery. No access to `api_secret_key` or any privileged credential is required to perform the replay itself — only the ability to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable/verified material (or otherwise cryptographically bind them to the payload) before dispatching to handlers, or have the gem explicitly document/enforce that these header values must not be trusted for tenant identification without an additional authenticated lookup (e.g., cross-checking against a known/expected shop for the webhook subscription). At minimum, `HmacValidator.validate` should not be presented as validating "the request," only the raw body.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com` and capture one legitimate webhook POST, e.g. body `{"id":123}` with headers `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the exact same body and `hmac` header to the app's public webhook route, but change `x-shopify-shop-domain` to `victim.myshopify.com` (and/or change `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Utils::HmacValidator.validate` succeeds because it only checks the raw body against the secret-derived signature: [5](#0-4)  — headers are never part of `to_signable_string`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...)`, causing the app to process a forged event as if it came from the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
