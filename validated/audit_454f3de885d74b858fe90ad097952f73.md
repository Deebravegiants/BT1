### Title
Simplex solver prices intent fills off an unmitigated Uniswap V4 spot price, letting a single-transaction pool manipulation drain solver funds via phantom/real bids — ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Simplex intent-filler strategy (`FXFiller.resolveLegRates` in `sdk/packages/simplex/src/strategies/fx.ts`) prices "venue" cross-asset legs directly from a Uniswap V4 pool's current `sqrtPriceX96`/tick, read on demand via `UniswapV4FundingPlanner.getExoticTokenPrice` → `UniswapV4LiquidityState.refresh` → `StateView.getSlot0`. This is a raw instantaneous spot price with no TWAP, no size/impact adjustment, and no fee-tier correction. The only defense is an optional `checkPriceGuard` (`referencePrice`/`maxDeviationBps`) which the documentation explicitly states is unguarded when omitted, and even when configured only bounds deviation from a static reference rather than execution cost.

### Finding Description
Any unprivileged actor who can move the price of a thin/low-liquidity Uniswap V4 pool that Simplex references for venue pricing (e.g. via a flash-loan-funded swap within the same block/transaction context, or simply trading against a thin pool) can cause `getExoticTokenPrice`/`resolveLegRates` to return a manipulated mid-price. `computeDirectPoolPriceUsd` returns this raw pool mid derived from `sqrtPriceX96` [5](#0-4) , and `computeLegPolicyOutput` extends that mid linearly across the whole priced quantity with no execution-cost or slippage term of its own. `resolveLegRates` invokes `checkPriceGuard` only when the leg is curveless and token0 is a USD stable [2](#0-1) , and the operator-level documentation says plainly that "referencePrice and maxDeviationBps must be set together; omit both to leave the chain unguarded" [6](#0-5) . Where `resolveLegRates`'s guard is configured, it only checks deviation from a static number, not the actual cost of sourcing inventory through the same pool the fill will trade against, which itself carries a fee tier "it never quoted against" [5](#0-4) .

This is directly analogous to the reported bug class: Tulip Protocol suffered losses because collateral/asset values it relied on were derived from Mango's manipulable oracle price, and an attacker who moved that price in a single set of transactions caused the protocol to misprice value and lose funds. Here, an unprivileged intent placer/bidder reachable path (submitting an intent order that the solver prices and fills, or a phantom-order bid the solver quotes against) similarly lets the pool-derived price feed the fill/withdrawal math the solver commits capital against.

### Impact Explanation
A manipulated pool price causes the Simplex solver to either (a) under-price the exotic-token leg it delivers (giving away more value than it should for the stablecoin it receives), or (b) mis-value its Uniswap V4 LP inventory used to fund a withdrawal-based fill (`UniswapV4FundingPlanner.planWithdrawalForToken`), both of which directly drain solver-held funds to the manipulating counterparty — concrete theft of solver capital, reachable from a single attacker-controlled sequence of transactions against a thin pool, with no protocol-level halt beyond an optional and imperfect guard.

### Likelihood Explanation
Likelihood is Medium-High for any pair configured for "Pool-Based Pricing" without both `referencePrice` and `maxDeviationBps` set, or for pairs on thin pools where the guard's static deviation band is wide enough (or absent) to still allow a profitable attack window. Since the documentation itself flags this as a known, accepted risk category ("Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool") [7](#0-6) , deployments that omit the optional guard (the documented default state) are directly exploitable by any actor able to move the referenced pool.

### Recommendation
Make the price guard mandatory (not optional) for every venue-priced pair, replace/augment the static-reference deviation check with a TWAP-based sanity check over multiple blocks, and incorporate the pool's fee tier and a size/impact-aware quote (rather than linear extension of the spot mid) into `computeLegPolicyOutput` so that the price used for fills reflects actual execution cost through the same pool.

### Proof of Concept
1. Operator configures a `[vault.uniswapV4]` pair with no `referencePrice`/`maxDeviationBps` (the documented default of "leave the chain unguarded").
2. Attacker executes a large swap against the thin Uniswap V4 pool backing that pair in one transaction, moving `sqrtPriceX96` far from fair value.
3. Attacker (or an accomplice) immediately submits/bids on an intent order priced against that pair; `FXFiller.resolveLegRates` → `getVenueUsdPrice` reads the now-manipulated `getSlot0` price with no guard rejecting it [2](#0-1) .
4. The solver fills at the manipulated rate, transferring value to the attacker; attacker reverses the pool manipulation (e.g. closes out the swap), realizing profit at the solver's expense.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
