### Title
`exchange_token` trusts a Shopify JWT's `dest` claim without binding it to the `iss` (issuer) claim, allowing non-admin session tokens to be exchanged for a full merchant access token - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` accepts any `session_token` whose JWT signature validates and whose `aud` claim matches the app's `client_id`, then uses the token's `dest` claim as the shop to request an online/offline admin access token from Shopify's `/admin/oauth/access_token` token-exchange endpoint. It never checks the token's `iss` claim to confirm the token was actually issued for the Admin embedded-app context (as `JwtPayload#shopify_user_id` does internally via `admin_session_token?`). Any Shopify-issued, correctly-signed session token sharing the same `client_id`/`aud` (e.g. a checkout UI extension or other non-admin extension token, which is exposed to lower-privileged front-end contexts) will pass validation and be exchanged for a merchant access token, even though it was never an admin session token.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#initialize` only validates the JWT signature and the `aud` claim: [1](#0-0) 

The `admin_session_token?` predicate (checking `iss.end_with?("/admin")`) exists but is only used internally to gate `shopify_user_id`, not to gate whether `shop`/`dest` may be trusted for other purposes: [2](#0-1) [3](#0-2) 

`TokenExchange.exchange_token` decodes the incoming token, takes `dest_shop = jwt_payload.shop` directly, and immediately uses it to build a session and send the app's `client_id`/`client_secret` to that shop's OAuth endpoint requesting an access token — with no `iss` check: [4](#0-3) 

By contrast, `migrate_to_expiring_token` (a sibling method in the same module) sanitizes its shop input with `Utils::ShopValidator.sanitize!` before use, showing the codebase is aware that unauthenticated shop-derived values need vetting — yet `exchange_token`'s `dest_shop`, sourced from a JWT the caller supplies, receives no equivalent context binding: [5](#0-4) 

The broken identity binding is: `token.iss == "https://{shop}/admin"` is never checked to equal the context `exchange_token` assumes (an Admin session). The method only enforces `token.aud == Context.api_key`, treating any correctly-signed, correctly-audienced JWT as equivalent to an admin session token regardless of the actual issuing surface (`iss`), even though non-admin surfaces (e.g., checkout/POS UI extensions) can produce and expose valid tokens to less-privileged parties (customers, extension code running in less-trusted contexts) that share the same `client_id`.

### Impact Explanation
If Shopify's token-exchange endpoint itself does not independently re-validate that the subject token is an admin-context ID token (the gem provides no such guarantee and forwards whatever token it is given), an unprivileged party who can obtain a valid non-admin session token for the shop (for example, via a checkout UI extension context, which is exposed to the customer's browser) could call `exchange_token` and have this gem exchange it for a genuine merchant online/offline access token — a scope/context check that answers permissively. This matches the Critical impact bucket: theft/escalation to a merchant access token beyond the privilege level the token was actually issued for.

### Likelihood Explanation
Exploitability depends on: (1) an attacker/lower-privileged actor being able to obtain a validly-signed, non-admin-context session token sharing the same `aud` for the target shop, and (2) Shopify's server-side token-exchange endpoint not independently enforcing that the subject token is an admin session token. Because the gem's own local validation (`JwtPayload`) provides no defense-in-depth for this binding — despite already possessing the `admin_session_token?` check needed to enforce it — the client library itself does not prevent misuse if such a token is obtained. This is a real gap in the code path, even though full exploitability also relies on server-side behavior outside this gem.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, require that the decoded `jwt_payload` be an admin session token before using its `dest` claim to request a merchant access token — e.g., expose and check `jwt_payload.admin_session_token?` (or equivalently validate `iss.end_with?("/admin")`) and raise `Errors::InvalidJwtTokenError` otherwise, mirroring the binding already enforced for `shopify_user_id`.

### Proof of Concept
1. Obtain (or have surfaced to a lower-privileged context) a Shopify-issued JWT for the target shop that has `aud == app.client_id` but `iss` not ending in `/admin` (e.g., a non-admin extension session token).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: RequestedTokenType::OFFLINE_ACCESS_TOKEN)`.
3. `JwtPayload.new(token)` succeeds (signature and `aud` both valid); `dest_shop = jwt_payload.shop` is used unchecked.
4. The gem POSTs `client_id`/`client_secret`/`subject_token` to `https://{dest_shop}/admin/oauth/access_token` and returns whatever `Session` Shopify's endpoint grants — with no local enforcement that the original token was ever an admin session token. [6](#0-5)

        def exchange_token(session_token:, requested_token_type:, shop: nil)
          unless ShopifyAPI::Context.setup?
            raise ShopifyAPI::Errors::ContextNotSetupError,
              "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for private apps." if ShopifyAPI::Context.private?
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
            requested_token_type: requested_token_type.serialize,
          }

          if requested_token_type == RequestedTokenType::OFFLINE_ACCESS_TOKEN
            body.merge!({ expiring: ShopifyAPI::Context.expiring_offline_access_tokens ? 1 : 0 })
          end

          client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
