### Title
Destination-side order cancellation irreversibly commits `_filled[commitment]` before the cross-chain `RefundEscrow` message is guaranteed to be delivered, leaving no retry path if delivery stalls - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` marks the order commitment as settled on the destination chain and dispatches a `RefundEscrow` POST request to the source chain with an unbounded timeout (`timeout: 0`). Unlike the source-side cancellation path, which does not mutate `_filled` until the cross-chain response is actually processed (and can therefore be safely retried), the destination-side path commits state immediately and offers no mechanism to re-dispatch or recover if the `RefundEscrow` message is never delivered/accepted on the source chain.

### Finding Description
`cancelOrder` in `IntentGatewayV2.sol` routes destination-side cancellations to `_cancelFromDest`: [1](#0-0) 

This function sets `_filled[commitment] = order.user` *before* the cross-chain message is confirmed delivered, permanently blocking any future fill of the order on the destination chain. It then calls `_post`, which builds a `DispatchPost` with `timeout: 0`: [2](#0-1) 

A `timeout` of `0` means the request never expires on the ISMP host, so there is no timeout-driven recovery path either. Delivery of `onAccept` on the source chain is additionally gated by `_checkRelayer`, which restricts acceptance to a single authorised relayer address once one is configured: [3](#0-2) 

By contrast, the source-side cancellation route (`_cancelFromSource`) does not touch `_filled` until the GET response is actually processed by `onGetResponse`, so if that round trip stalls, the user can simply call `cancelOrder` again with a fresh proof height: [4](#0-3) 

The destination-side route has no equivalent retry: once `_filled[commitment]` is set, `cancelOrder` reverts with `Filled()` on any subsequent call (both `fillOrder` and `cancelOrder` check `_filled[commitment] != address(0)`), so the user cannot re-dispatch the `RefundEscrow` message if the first one is dropped, censored, or otherwise fails to reach `onAccept` on the source chain.

### Impact Explanation
If the single `RefundEscrow` POST request is not accepted on the source chain (e.g., the message is lost, the source gateway/host pauses, the source chain's registered gateway instance changes, or the whitelisted relayer becomes unavailable/rotated before delivering this particular message), the user's escrowed input tokens on the source chain remain locked in the `IntentGatewayV2` contract indefinitely. Because the destination order is already irreversibly marked as settled and the request never times out, there is no unprivileged path (no re-cancel, no re-dispatch, no alternative claim function) for the user to recover the escrowed collateral. This is a permanent freezing of user funds, directly analogous to the reported class of bug (a withdrawal request that cannot be "accepted" by the counterpart leaves the user's collateral irrecoverable).

### Likelihood Explanation
This is reachable by any regular user simply calling `cancelOrder` from the destination chain on their own order — no privileged role or malicious actor is required to trigger the initial commit. The likelihood of the message actually failing to deliver depends on operational conditions (relayer availability, host state, chain reorgs) rather than a guaranteed bug, but the code path provides no compensating control (no timeout, no retry, no fallback claim) once the irreversible commit happens, so any transient delivery failure becomes a permanent loss rather than a delayed one.

### Recommendation
Do not set `_filled[commitment]` until the `RefundEscrow` message is confirmed dispatched/finalized, or provide an explicit retry/resend function that allows the user (or the destination gateway) to re-dispatch the `RefundEscrow` POST request for an already-cancelled-but-unrefunded commitment. Alternatively, give the `DispatchPost` for `RefundEscrow` a bounded timeout and implement an `onPostTimeout`/`onPostRequestTimeoutHandled` handler on the destination chain that reverses the local `_filled` mark, restoring the order to a fillable/cancellable state so the user is not permanently locked out of both filling and refund paths.

### Proof of Concept
1. User places a cross-chain order and it is not filled before `order.deadline`.
2. User (or anyone, post-deadline) calls `cancelOrder(order, options)` on the destination chain, which is routed to `_cancelFromDest`.
3. `_filled[commitment]` is immediately set to `order.user`, and a `RefundEscrow` `DispatchPost` with `timeout: 0` is sent.
4. Assume the authorised relayer set via `setRelayer` fails to deliver this specific message to `onAccept` on the source chain (e.g., relayer downtime, message dropped, relayer rotated mid-flight).
5. The user calls `cancelOrder` again to retry: it reverts with `Filled()` because `_filled[commitment] != address(0)` (see check in `cancelOrder`, `evm/src/apps/IntentGatewayV2.sol:508`).
6. No other function exists to re-trigger the `RefundEscrow` message or reclaim the escrow on the source chain; the input tokens escrowed at `evm/src/apps/intentsv2/IntrinsicIntents.sol` remain stuck in the source-chain `IntentGatewayV2` contract permanently.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
