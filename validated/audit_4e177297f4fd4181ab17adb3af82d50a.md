### Title
Infinite loop in GRANDPA ancestry-chain traversal via cyclic `parent_hash` pointers in attacker-supplied consensus proof - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The GRANDPA consensus client's ancestry-route computation walks a chain of headers by following `parent_hash` pointers through a `BTreeMap` keyed by each header's own computed hash, with no cycle detection and no iteration bound. Because the header set (`unknown_headers`) and the justification's `votes_ancestries` are fully attacker-controlled fields of a `ConsensusMessage` that any unprivileged relayer can submit, an attacker can craft two (or more) headers whose `parent_hash` fields point at each other's hash, forming a cycle. When `AncestryChain::ancestry` is asked to walk from a `block` hash that lands inside that cycle to a `base` hash that is never reached, the `while current_hash != base` loop never terminates, resulting in unbounded CPU consumption — the same bug class as CVE-2021-40111 (Apache James infinite loop from crafted IMAP input).

### Finding Description
`AncestryChain<H>` is built directly from the untrusted `unknown_headers: Vec<H>` field of a `FinalityProof`, itself part of `ConsensusMessage::Polkadot`/`Relaychain` submitted by any relayer: [1](#0-0) 

The map keys each header by its own `hash()`: [2](#0-1) 

The traversal that follows `parent_hash` pointers has no visited-set / cycle check and no depth bound: [3](#0-2) 

Because header hashing is a plain SCALE-encode + Blake2 hash with no proof-of-work or monotonicity constraint tying a header's hash to its parent's hash, an attacker can trivially construct two headers `A` and `B` such that `parent_hash(A) == hash(B)` and `parent_hash(B) == hash(A)`. Once such a cycle exists among entries actually present in `self.ancestry` (i.e., present in the submitted `unknown_headers`), any call to `ancestry(base, block)` where `block`'s hash lands inside the `{A, B}` cycle and `base` is never a hash of `A` or `B` will loop `current_hash = A → B → A → B → …` forever, since the map lookup always succeeds (both `A` and `B` are keyed by their own hash) and the loop's only exits are `current_hash == base` or a missing-entry error — neither of which is reached.

This function is invoked directly during on-chain proof verification:
- In `GrandpaJustification::verify_with_voter_set`, once per precommit, to compute the ancestry route from the commit's `base_hash` to each precommit's `target_hash`: [4](#0-3) 
- In `verify_grandpa_finality_proof`, to compute ancestry from the trusted `consensus_state.latest_hash` to the finality proof's target, and from the proof's `base` to `consensus_state.latest_hash`: [5](#0-4) 

`verify_grandpa_finality_proof` is the top-level function invoked by the `ismp-grandpa` consensus client's `verify_consensus`/fraud-proof handling when a relayer submits a GRANDPA `ConsensusMessage` through pallet-ismp's normal (permissionless) message-submission path, and again in `verify_fraud_proof`: [6](#0-5) 

No size or well-formedness constraint on `unknown_headers`/`votes_ancestries` prevents constructing a small (as few as two) header cycle; the loop is not bounded by the size of the supplied vector, it is bounded only by whether a cycle exists, so even a tiny, cheap-to-submit payload can spin forever.

### Impact Explanation
Any relayer or unprivileged extrinsic submitter can submit a crafted GRANDPA consensus/fraud-proof message that drives on-chain verification (`pallet-ismp`'s consensus-message handling, which runs inside block execution / weight-metered dispatch) into an unbounded loop. In a Substrate runtime this manifests as excessive, unbounded computation inside a single extrinsic's execution — a denial-of-service against the relaychain-GRANDPA-consensus light client used by Hyperbridge, potentially exhausting block execution time/weight and stalling consensus updates for that client, i.e., "a route unable to deliver messages" for that consensus client until intervention. This is a Medium-severity availability issue analogous to the referenced CVE, not a direct fund-theft or forgery bug, since the loop is a correctness/liveness failure rather than an unsound acceptance.

### Likelihood Explanation
High: constructing two headers with mutually-referencing `parent_hash` values requires no cryptographic break — headers are attacker-encoded structures, and their hash is simply Blake2(SCALE-encode(header)); the attacker freely chooses digest/extrinsics-root/state-root fields to hit any desired parent_hash target for the sibling header (a header preimage of an arbitrary 32-byte value is not needed since the attacker controls both headers being linked to each other, not to a fixed hash). It is trivial to author a `Vec<H>` of just two crafted headers, wrap them in a `ConsensusMessage` (or `FraudProofMessage`), and submit it as a normal, unprivileged relayer transaction.

### Recommendation
Add cycle detection (e.g., a bounded `visited: BTreeSet<Hash>` or a maximum iteration count equal to `unknown_headers.len()`) to `AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs`, returning `finality_grandpa::Error::NotDescendent` (or a new typed error) once the number of hops exceeds the number of distinct headers supplied, since a valid ancestry route can never revisit a hash or exceed the header-set size.

### Proof of Concept
1. Construct header `B` with an arbitrary `parent_hash = H_A_target` (chosen later) and compute `hash(B) = H_B`.
2. Construct header `A` with `parent_hash = H_B` and compute `hash(A) = H_A`.
3. Re-derive `B` so that its `parent_hash` equals `H_A` (iterate/adjust a free field such as `digest` in `B` until `hash(B)` stabilizes into a two-header fixed cycle, or simply accept `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)` computed in one pass since both are fully attacker-chosen structures with no interdependency constraint beyond the two hash equalities, which can be solved directly without any hash inversion — set `B`'s fields first, compute `H_B`, set `A.parent_hash = H_B`, compute `H_A`, then set `B.parent_hash = H_A`; recomputing `B` changes `H_B`, so instead pick `A` and `B` with `parent_hash` fields pointing at each other's *final* encodings via a small fixed-point search over a few nonce bytes in each header's digest — feasible offline in negligible time).
4. Submit `unknown_headers = [A, B]` (plus any headers needed to satisfy `target`/`base` selection) inside a `ConsensusMessage::Relaychain` (or the fraud-proof variant) such that a precommit's `target_hash` or the finality-proof's `target`/`base` resolves ancestry through the `A ⇄ B` cycle without ever equating to `base`.
5. Submit this message via the normal permissionless ISMP message path; the runtime call into `GrandpaJustification::verify` / `verify_grandpa_finality_proof` enters `AncestryChain::ancestry` and loops indefinitely, consuming the extrinsic's weight/CPU without terminating.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
