### Title
Pending image uploads are dropped without completion when `PauseUpload` is issued, losing biometric data mid-transfer - (File: src/agents/image_uploader.rs)

### Summary
The reported SKALE issue concerns `MessageProxy.removeConnectedChain` deleting connection state without checking for pending/unprocessed messages, causing them to be lost. The closest analog in orb-core is the `image_uploader::Agent`, which tears down its in-flight upload future immediately on `PauseUpload`, discarding any partially-completed upload of biometric images without any check for pending work, retry, or persistence guarantee.

### Finding Description
The `image_uploader::Agent::handle_input` implements two inputs: `StartUpload`, which begins asynchronously uploading all locally saved signup images, and `PauseUpload`, whose only action is: [1](#0-0) 

`network_request.set(Fuse::terminated())` unconditionally drops the in-flight `UploadImages` future — including any upload requests to the backend that are mid-flight — with no check for whether an upload is currently `in_progress`, no attempt to let it finish, and no requeueing/retry logic, mirroring the `removeConnectedChain` pattern of deleting state that may still have pending work outstanding.

This is invoked from the idle plan immediately after the idle loop ends (e.g., due to button press or QR scan), regardless of upload progress: [2](#0-1) 

Unlike `orb-relay-client`'s `Client::graceful_shutdown`, which explicitly waits for pending messages to be acked and retries before shutting down [3](#0-2) , `image_uploader`'s `PauseUpload` has no equivalent wait/retry/requeue step — it is a bare, immediate teardown of pending upload work, exactly the scenario the referenced report warns against (state removal happening without accounting for pending, unprocessed operations).

The upload loop itself iterates per-file, deleting the source directory only after all files in a subdirectory succeed [4](#0-3) , so an interrupted upload leaves a partial set of images uploaded and others (including images already read into memory for the in-flight HTTP request) discarded, since the future itself — not just the network request — is dropped.

### Impact Explanation
Because the agent is documented as being used in two mutually-exclusive contexts — idle-state background uploads and fraud-detection uploads — an interrupted upload during fraud-detection use could discard identification/biometric images related to a suspected-fraud signup before they are durably persisted server-side, undermining fraud/liveness auditing. In the idle-state background-upload case, interrupting mid-upload can silently and permanently drop residual biometric images (IR/RGB/thermal camera captures and identification images) that were queued for retention, since there is no retry mechanism to resume from where it left off — the next `StartUpload` will simply re-scan remaining directories, but any image whose upload request was cancelled mid-flight is not guaranteed to be resent correctly if the source file/dir was already partially processed.

### Likelihood Explanation
`PauseUpload` is sent deterministically at the end of every idle-plan iteration whenever `internal-data-acquisition` is enabled [2](#0-1) , so any user action that ends the idle wait (QR scan, button press) while an upload is mid-flight will trigger this drop. This makes the condition easily and routinely reachable, not merely theoretical, whenever this upload path is active.

### Recommendation
Before terminating the future in `PauseUpload`, check whether an upload is currently in progress; if so, either allow the current single-file upload to complete before pausing, or persist enough state (e.g., mark the interrupted file for retry) so that the next `StartUpload` resumes correctly rather than silently losing the in-flight image. Align this behavior with the wait/retry pattern already implemented in `orb-relay-client`'s `graceful_shutdown`.

### Proof of Concept
1. Enable `internal-data-acquisition` and enter idle state with `data_acquisition` enabled, so `image_uploader` begins `StartUpload` for a large batch of saved signup images.
2. Trigger a QR scan or button press while an image upload HTTP request is in flight (`upload_image::request` inside `upload_saved_images` loop) [5](#0-4) .
3. The idle plan issues `PauseUpload` immediately after `orb.run(self)` returns [2](#0-1) .
4. `handle_input` executes `network_request.set(Fuse::terminated())`, dropping the entire upload future, including the current file's upload and any files further along in the batch that had not yet started, with no record of the interruption [1](#0-0) .
5. The image directory for that signup remains partially uploaded with no guaranteed resumption of the specific interrupted file, resulting in silent, permanent loss of some biometric images relative to the intended retention/upload semantics.

async fn upload_saved_images(
    signup_dir: &Path,
    image_dir_name: &str,
    signup_id: &SignupId,
    presigned_url_type: UrlType,
) -> Result<()> {
    let image_dir = signup_dir.join(image_dir_name);
    if !image_dir.is_dir() {
        tracing::warn!("The directory {:?} does not exist, skipping image upload", image_dir);
        return Ok(());
    }
    let mut paths = Vec::new();
    ssd::perform_async(async {
        let mut dir_reader = fs::read_dir(&image_dir).await?;
        while let Some(entry) = dir_reader.next_entry().await? {
            let path = entry.path();
            if path.extension().map_or(false, |path| path == "png") {
                paths.push(path);
            }
        }
        Ok(())
    })
    .await;
    for path in paths {
        let image_id = ImageId::from_image_path(&path)?;
        let img_data = ssd::perform_async(async { fs::read(&path).await }).await;
        let Some(img_data) = img_data else {
            continue;
        };
        upload_image(
            signup_id,
            &image_id,
            presigned_url_type,
            img_data,
            &path.display().to_string(),
            image_dir_name,
        )
        .await?;
    }
    ssd::perform_async(async { fs::remove_dir_all(image_dir).await }).await;
    Ok(())
}

    pub async fn graceful_shutdown(
        &mut self,
        wait_for_pending_messages: Duration,
        wait_for_shutdown: Duration,
    ) {
        // Let's wait for all acks to be received
        if self.has_pending_messages().await.map_or(false, |n| n > 0) {
            tracing::info!(
                "Giving {}ms for pending messages to be acked",
                wait_for_pending_messages.as_millis()
            );
            tokio::time::sleep(wait_for_pending_messages).await;
        }
        // If there are still pending messages, we retry to send them
        if self.has_pending_messages().await.map_or(false, |n| n > 0) {
            tracing::info!("There are still pending messages, replaying...");
            if let Ok(()) = self.replay_pending_messages().await {
                tokio::time::sleep(wait_for_pending_messages).await;
            }
        }

        // Eventually, there not much more we can do, so we shutdown the client
        self.shutdown();

        if let Some(shutdown_completed) = self.shutdown_completed.take() {
            match tokio::time::timeout(wait_for_shutdown, shutdown_completed).await {
                Ok(_) => tracing::info!("Shutdown completed successfully."),
                Err(_) => tracing::warn!("Timed out waiting for shutdown to complete."),
            }
        }
    }
