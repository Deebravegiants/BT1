### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `HmacValidator` verifies only covers the raw request body, never the shop header. Any actor capable of producing (or replaying) a validly-signed webhook body — most simply, any legitimate merchant of the host app receiving their own genuine webhooks — can resend that same signed body while substituting an arbitrary `X-Shopify-Shop-Domain` value. `Webhooks::Registry.process` accepts the HMAC as proof of authenticity and then attributes the payload to the attacker-chosen shop, breaking the binding between "the tenant the event is verified for" and "the tenant the event is attributed to."

### Finding Description
The signable content used for verification is defined here: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body` — the `shop` value (line 20-23, sourced from the `shop-domain` header) is not part of the signed content at all.

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. only the body) and compares it to the received HMAC: [2](#0-1) 

`Webhooks::Registry.process` treats a passing HMAC check as full authentication of the request, then immediately uses the unauthenticated `request.shop` to build the metadata handed to the app's webhook handler: [3](#0-2) 

The identity binding that should hold is:
`shop attributed to the event by the handler == shop cryptographically bound by the HMAC`

In reality, `to_signable_string == raw_body` only, so:
`shop attributed to the event == header value (attacker-controlled)` while `HMAC-verified content == raw_body only`.

Because the body and shop are signed/verified independently of each other, a valid HMAC for a given body says nothing about which shop it belongs to. Anyone who can obtain one validly-signed webhook body (e.g., a legitimate merchant installed on the same multi-tenant app, replaying their own real webhook traffic) can re-POST that exact body with a forged `X-Shopify-Shop-Domain` header naming a different (victim) shop. `Registry.process` will pass HMAC validation and dispatch the payload to the app's handler tagged as belonging to the victim tenant, since `data.shop` in `WebhookMetadata` is taken straight from the unverified header.

This is directly analogous to the reported bug class: a field that is *acted upon* (the disable/whitelist status in the Alchemix report; here, the tenant/shop attribution) is not covered by the security check that is supposed to gate it (the whitelist membership check there; the HMAC signature here).

### Impact Explanation
This allows cross-tenant event injection: an attacker who is a legitimate tenant of a multi-tenant Shopify app can cause the app to process arbitrary (but real, previously-observed) webhook payloads as if they originated from a different merchant's shop. Any host application that uses `WebhookMetadata#shop` to select the tenant's data/session to act on (a common and expected pattern, since the gem explicitly exposes `shop` for that purpose) can be tricked into performing tenant-scoped writes/reads against the wrong shop's data — i.e., cross-tenant access, which the program's scope explicitly lists as a Critical impact.

### Likelihood Explanation
Likelihood is meaningful in any deployment that has more than one installed merchant, since exploitation only requires network access to the app's public webhook endpoint plus one legitimately-signed webhook body (trivial for an attacker to obtain by simply installing the app themselves and capturing their own webhook traffic). No access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Bind the shop to the same trust boundary as the HMAC: include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed/verified content of `to_signable_string`, or otherwise cryptographically bind the reported shop to the signature computation, so that a body can only validate for the specific shop it was actually generated for.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant of the host app and captures one of their own
# real, validly-signed webhooks (raw_body + hmac), e.g. from their own shop "attacker.myshopify.com".

captured_raw_body = '{"id": 123, "note": "legit order payload"}'
captured_hmac = OpenSSL::Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, captured_raw_body)
)

# Attacker replays the identical body/hmac but swaps the shop-domain header to a victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,     # still valid: HMAC never covered "shop"
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: forged_headers)

# Passes HMAC validation because to_signable_string == raw_body only.
ShopifyAPI::Webhooks::Registry.process(forged_request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now believes this event belongs to "victim-shop.myshopify.com".
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
