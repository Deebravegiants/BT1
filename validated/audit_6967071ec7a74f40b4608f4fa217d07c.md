### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` checks the HMAC exclusively against that raw body. The `shop`, `topic`, and `webhook_id` values that `ShopifyAPI::Webhooks::Registry.process` extracts and hands to the app's webhook handler come from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) that are never included in the signed payload. Any party capable of triggering a legitimate webhook for one shop (e.g. an app's own merchant/test store) can capture a body+HMAC pair and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a different, victim shop, and the HMAC check still passes because the signature never covered the header.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the value returned by `verifiable_query.hmac`: [3](#0-2) 

For webhook requests, `to_signable_string` returns just `@raw_body`, and `hmac` is decoded from the `x-shopify-hmac-sha256` header: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are all read straight from headers with no cryptographic binding to the body or to each other: [4](#0-3) 

`Registry.process` only asserts that the HMAC over the body validates, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` object dispatched to the application's handler: [5](#0-4) 

Because the shop identity is carried in a header rather than inside the HMAC-covered content, the equality the code implicitly relies on — "the shop whose secret validated this HMAC" == "the shop named in the `shop-domain` header" — does not actually hold. The HMAC only proves "this body byte sequence was produced/known by someone with the app's `client_secret`"; it says nothing about which shop the header claims the event originates from. Since every shop installing the same app shares the same `client_secret` for webhook signing, a request captured from shop A's webhook delivery remains fully valid (same body, same HMAC) if resent with shop B's domain in the header.

### Impact Explanation
An attacker who controls (or has installed the app on) any shop can receive genuine webhook deliveries addressed to their own store, each with a valid HMAC over the body. By replaying that exact body/HMAC pair while substituting a different shop's domain in `x-shopify-shop-domain` (and optionally a different `webhook_id`/`topic` combination the app also handles), the attacker can make the app process a fabricated event "as if" it originated from a shop they do not own. If the app's handler uses `WebhookMetadata#shop` to select which tenant's data to update, delete, or act upon (a common pattern, e.g. `customers/redact`, `shop/redact`, inventory sync, order fulfillment webhooks), this results in cross-tenant data manipulation performed under an attacker-chosen victim shop identity — without needing that victim's access token or credentials.

### Likelihood Explanation
Likelihood is moderate-to-high: any developer or test-store owner with an app installed can trivially capture a legitimate `(body, hmac)` pair from their own webhook deliveries (webhooks are delivered to the app's own public endpoint), and replaying an HTTP POST with a modified header value is a straightforward action requiring no special tooling, no leaked secrets, and no privileged access to Shopify internals.

### Recommendation
Bind the shop (and ideally the topic/webhook id) into the value that is HMAC-verified rather than trusting header values that sit outside the signed payload. Options include: incorporate the `shop-domain` (and `webhook_id`) header into the string that is HMAC-verified (many Shopify webhook payloads already carry the shop domain in the JSON body itself — cross-check `parsed_body`'s shop-identifying field against the header and reject mismatches), or otherwise ensure that any per-tenant dispatch decision is only made using data that was part of the HMAC-covered content.

### Proof of Concept
1. App merchant M installs the app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body B>`, and body `B`.
2. Attacker captures the full request (headers + body `B`) from their own delivery.
3. Attacker resends an identical HTTP POST to the app's webhook endpoint, keeping body `B` and the `x-shopify-hmac-sha256` value unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the new headers; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — unchanged — and it matches the unchanged header value, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ..., body: parsed_body)`, i.e., a webhook event now attributed to a shop the attacker does not own, verified as "authentic" by the gem's HMAC check.
