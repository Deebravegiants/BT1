### Title
Webhook shop-tenant identity (`x-shopify-shop-domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` so that `Registry.process` can authenticate an inbound webhook via HMAC before dispatching it to the app's handler. However, the HMAC signature only covers the raw request body — it never covers the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is the field the gem hands to the handler as the tenant identifier. Any party that can obtain one valid `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body/hmac pair while substituting an arbitrary shop domain in the header, and `HmacValidator.validate` will still report the request as authentic.

### Finding Description
`Registry.process` authenticates a webhook exclusively through `HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — the tenant-identifying `shop` field (sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is completely outside the signed material: [3](#0-2) 

Yet that same unauthenticated `shop` accessor is exactly what `Registry.process` forwards to the app's handler as the tenant identity for the event: [4](#0-3) 

This breaks the identity binding: `hmac_valid(body) == true` is treated by the gem as equivalent to `shop_header == actual_source_shop`, but the two are independent. The equality that should hold — `shop bound in signature == shop acted upon` — does not: the signature binds only `body`, while the dispatch binds tenant identity to `header["shop-domain"]`.

### Impact Explanation
This is a cross-tenant identity confusion at the library's webhook-authentication boundary. An attacker who is a legitimate merchant of the multi-tenant app (an "unprivileged internet user" with respect to any *other* tenant) can:
1. Install the app on their own store and capture a real webhook delivery, which comes with a genuine `(raw_body, hmac)` pair computed by Shopify using the app's `api_secret_key`.
2. Replay that captured request to the app's webhook endpoint, but swap the `x-shopify-shop-domain` header to a victim shop's domain.
3. `HmacValidator.validate` still returns `true` because it never inspected the header, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` even though the body content is fully attacker-controlled.

Any host application that uses `data.shop` from `Registry.process`'s handler dispatch to determine which tenant's data to update (a documented, intended use of this API) will apply attacker-controlled webhook content under another merchant's identity — a cross-tenant write/spoofing primitive purely through the gem's own validation contract.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a store they control (a normal, unprivileged action for any multi-tenant Shopify app) and be able to POST arbitrary HTTP headers to the app's public webhook endpoint — no access token, secret key, or privileged account is required. The HMAC check gives host developers false confidence that `request.shop` is authenticated, when it is not.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise cryptographically tie the header-derived shop to the signed body, before exposing `Request#shop` as a trusted tenant identifier. At minimum, `to_signable_string` should incorporate `shop` (and other headers relied upon for tenant dispatch) so that tampering with the shop header invalidates the HMAC:

```diff
- def to_signable_string
-   @raw_body
- end
+ def to_signable_string
+   "#{shop}\n#{@raw_body}"
+ end
```
and document clearly to consumers that `WebhookMetadata#shop` is only as trustworthy as this binding.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop and captures a genuine webhook:
real_body = '{"id": 1, "note": "attacker-controlled content"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)

# Attacker replays the exact same body/hmac, only forging the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, despite forged shop

ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's real_body)
```
