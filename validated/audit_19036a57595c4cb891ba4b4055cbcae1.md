### Title
Webhook Shop/Topic Identity Spoofing via HMAC Signing Only the Raw Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an inbound webhook solely by HMAC-verifying the raw JSON body, while the `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers that the gem hands to the application's handler as the authoritative tenant identity are never included in the signed content. This breaks the equality that should hold: `hmac_signed_bytes == bytes_the_handler_trusts_for_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (the raw body only) and compares it against `verifiable_query.hmac` (the header-provided signature). Once that body-only check passes, the code immediately trusts `request.shop` and `request.topic` — values that were never part of the signed material — and dispatches them straight to the application's webhook handler as `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` confirms the check is body/secret only: [4](#0-3) 

Because the app's `api_secret_key` is a single shared secret across every shop that installs the app (not a per-shop key), any tenant that has installed the app can legitimately trigger a real Shopify webhook delivery whose raw body they substantially control (e.g., an `orders/create` payload containing attacker-chosen line-item titles, customer fields, etc.) and whose `hmac-sha256` header is a valid signature over that exact raw body. Since `Request.new` and `Registry.process` accept `shop-domain`/`topic`/`webhook-id` from any header value the caller supplies, and never bind those values into the HMAC check, a request replayed straight to the app's public webhook endpoint with the untouched `raw_body`/`hmac-sha256` pair but a substituted `x-shopify-shop-domain` header (pointing at a victim tenant) still passes `Utils::HmacValidator.validate` unmodified. The application's handler receives `WebhookMetadata.shop == "victim-shop.myshopify.com"` for data that was never associated with that tenant, i.e. the equality `authenticated_shop == shop_used_for_tenant_routing` is broken.

This is the direct Ruby-gem analog of the report's root cause: a value that is acted upon by downstream logic (the Bitcoin address / here the Shopify shop identity) is not itself covered by the cryptographic check (`isOnCurve` validation / here the HMAC signature), letting an attacker substitute an unverified value while keeping the verified portion valid.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to key per-tenant storage, trigger tenant-specific side effects, or attribute webhook events to a specific merchant is exposed to cross-tenant data injection: an attacker who controls one (even trial/free) installed shop can cause the app to process attacker-controlled webhook content as if it originated from an arbitrary victim shop domain string, without any credential belonging to the victim. This matches the Critical "cross-tenant access" impact category, since tenant isolation — the central trust boundary the gem is meant to enforce for merchants — is defeated using only the attacker's own low-privilege shop installation and a forged HTTP header.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own shop to have the target app installed (unprivileged, self-service action any internet user can perform for a public app), (2) the ability to trigger a webhook whose body they can shape (standard Shopify resource webhooks like `orders/create` embed many attacker-controlled string fields), and (3) sending an HTTP POST directly to the app's public webhook endpoint with the captured `raw_body`/`hmac-sha256` unchanged but the `x-shopify-shop-domain` header replaced. No TLS interception, no leaked secret, and no privileged account are required — only reuse of a value the attacker legitimately received for their own tenant.

### Recommendation
Bind the routing/identity headers into the authenticated payload before trusting them: include `topic`, `shop-domain`, and `webhook-id` in `to_signable_string` (or otherwise incorporate them into the HMAC computation) so that `Utils::HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually signed. Alternatively/additionally, cross-check the `shop-domain` header against a known/allow-listed set of shops that have active sessions with this app before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., creates an order with an attacker-chosen body) so Shopify sends a real webhook POST to the app's webhook endpoint containing:
   - `raw_body`: attacker-controlled JSON
   - `x-shopify-hmac-sha256`: valid signature of `raw_body` using the app's `api_secret_key`
   - `x-shopify-shop-domain`: `attacker-shop.myshopify.com`
2. Attacker captures this exact `raw_body` + `x-shopify-hmac-sha256` pair (e.g., via a request-inspection proxy they control in front of their own test endpoint, or by configuring the webhook to point at a URL they log).
3. Attacker replays an HTTP POST directly to the app's public webhook controller URL using the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — unchanged — so validation succeeds: [5](#0-4) 
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, and any tenant-scoped logic in the host app acts on attacker data under the victim shop's identity.
