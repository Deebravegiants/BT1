## Title
Webhook Shop/Topic Identity Spoofing via HMAC Scope Gap — Signature Covers Only Raw Body, Not Shop/Topic Headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop, topic, and webhook-id used for downstream processing are taken directly from unauthenticated HTTP headers. The identity binding that `Registry.process` relies on — "the HMAC-verified bytes authorize the shop/topic this webhook is attributed to" — does not hold, because the header values are never part of what the HMAC covers.

### Finding Description
`to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC (over the body alone) and then unconditionally trusts `request.shop` / `request.topic` to construct the `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks that `computed_signature(hmac(secret, raw_body))` matches the supplied HMAC; it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

Because Shopify signs webhooks with the app's single, shared `client_secret` (the same key for every shop that installs the app), any party who legitimately receives one webhook for *any* shop (e.g., an attacker who installs the app on their own store) obtains a `(raw_body, valid_hmac)` pair. That pair remains valid regardless of which `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` headers accompany it, because those headers are excluded from the signed content. Replaying the same body+HMAC while substituting a victim shop's domain into the header breaks the intended identity equality:

`verified(hmac) == "this body originated from and is attributable to shop X"`

versus the actual guarantee provided:

`verified(hmac) == "this body was signed with the app's shared secret"`

### Impact Explanation
This directly maps to the "cross-tenant access" impact category: an attacker with a legitimate install of the app on one shop can forge webhook deliveries that the app processes as if they came from a different, victim shop, because the shop attribution is never authenticated. Depending on the handler implementation (order/customer/product data ingestion keyed by `request.shop`), this can inject attacker-controlled data into another merchant's per-tenant records/data store, or trigger shop-scoped side effects (e.g., billing, inventory sync, notifications) under a victim shop's identity — a cross-tenant confusion/injection vulnerability rooted entirely in this gem's `Webhooks::Request`/`Registry` design.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker run the target app on a shop they control (no special privilege, no access to `api_secret_key` needed) and the ability to send arbitrary HTTP requests with attacker-chosen headers to the app's public webhook endpoint, which is inherent to how webhook delivery endpoints work.

### Recommendation
Bind the shop/topic/webhook-id identity to the signed content — e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the request), rather than trusting header-only values once the raw-body HMAC succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (valid because `H = HMAC(app_secret, B)`), and header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `shopify-topic`/`shopify-webhook-id`).
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes the HMAC over `B` only and it matches `H`, so the request passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, and the app's handler processes it as authentic data from `victim-shop.myshopify.com`.
