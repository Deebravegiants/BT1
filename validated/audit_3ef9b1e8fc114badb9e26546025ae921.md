### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are not covered by the HMAC signature, allowing cross-tenant metadata spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its `hmac`-verified signable string solely from the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by handlers come from unauthenticated HTTP headers. `Registry.process` validates only the body against the HMAC and then passes the header-derived `shop` straight to `WebhookMetadata`, breaking the intended binding: `HMAC-covered bytes == bytes trusted for tenant identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the HMAC over exactly that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates the HMAC (over the body only) and then constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values, handing them to the app's registered handler as trusted identifiers: [4](#0-3) . The `WebhookMetadata` struct simply stores whatever `shop` string it's given, with no independent verification [5](#0-4) .

This is the same bug class as the report: an action is taken based on a field (rewards/balance) that is not re-synchronized/re-verified at the point of the effectful operation. Here, the identity-binding equality that should hold is:
`HMAC(secret, signable_string)` should cover `shop` ⇒ but in fact `signable_string == raw_body` only, so `shop ⊄ HMAC-covered bytes`.

Because the `shop-domain`, `topic`, and `webhook-id` headers sit entirely outside the HMAC's scope, anyone who has ever obtained one genuine, validly-signed webhook body+HMAC pair for a given topic and payload shape (e.g. by running their own installed instance of the app on their own shop, which Shopify itself will happily send them) can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (since it only checks the body), and the app-provided `WebhookHandler#handle` receives a `WebhookMetadata` claiming the payload belongs to a shop the attacker does not control.

### Impact Explanation
This crosses a tenant boundary: an app's webhook handler is a merchant-facing trust boundary keyed by `shop`, and if that handler uses `data.shop` (as most Shopify apps do, e.g. to look up the target merchant's session/store record and apply the webhook's contents), an attacker can inject a legitimately-signed payload under a victim shop's identity. Depending on what the host app does with mandatory-compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) or business webhooks (orders, app-uninstalled, etc.), this enables cross-tenant data confusion/corruption without ever needing the target's access token or `client_secret`—only the app's own `api_secret_key`-signed traffic that the attacker can generate against their own shop.

### Likelihood Explanation
Requires only that the attacker (or their own genuinely-installed copy of the app) receive one legitimate webhook, which is trivial to obtain — install the app on an attacker-controlled shop, trigger the relevant webhook event, capture the raw body and HMAC header, then resend it with a modified `X-Shopify-Shop-Domain` header. No secrets or privileged access are needed. The main mitigating factor is that impact is entirely dependent on how the host application's `WebhookHandler#handle` implementation uses the `shop` field — this is a library-level gap, not a full end-to-end exploit on its own.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before trusting them in `WebhookMetadata`. At minimum, document that consumers of `WebhookHandler#handle` must not treat `data.shop`/`data.topic`/`data.webhook_id` as authenticated unless the gem itself binds them into the signature.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — both are valid and pass `HmacValidator.validate` because the app's `api_secret_key` signs exactly `raw_body`, per `Request#to_signable_string` [1](#0-0) .
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [4](#0-3) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` even though the payload was never generated by or for that shop, since `request.shop` reads the unauthenticated header value [6](#0-5) .
