Confirmed: `EvmHost.dispatchIncoming(PostRequest)` at [1](#0-0)  catches a revert in `onAccept` and deletes the request receipt "so that it can be retried" — it does not permanently brick the message, it just leaves it undeliverable until it succeeds or times out. This changes the analysis: the escrow/withdraw revert on `IntentGatewayV2`/`IntentsBase` doesn't corrupt protocol state, but as long as the blacklisted beneficiary address remains blacklisted, the message can never be delivered, and once `timeoutTimestamp` passes, no timeout handler exists for `RedeemEscrow`/`RefundEscrow` POST requests to unwind the escrow to a different address — so the escrowed input tokens are permanently stuck in the `IntentGatewayV2` contract for that commitment.

### Title
Escrowed input tokens can be permanently frozen if the withdrawal beneficiary is blacklisted by the input token (e.g. USDC) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` (used by both `IntrinsicIntents` same-chain fills/cancels and `ExtrinsicIntents`'s `onAccept`/`onGetResponse` cross-chain settlement) pushes escrowed ERC-20 tokens directly to a `beneficiary` address via `IERC20(token).safeTransfer(beneficiary, amount)` [2](#0-1) . If that token enforces an admin-controlled blacklist (USDC, USDT, etc.) and the beneficiary is blacklisted, the transfer reverts and the entire settlement call reverts, with no pull-based fallback to recover the escrow.

### Finding Description
For cross-chain orders, `ExtrinsicIntents.onAccept` decodes a `WithdrawalRequest` from an incoming Hyperbridge POST request and calls `_withdraw(body, ..., true)`, which iterates the order's input tokens and does a direct push transfer to `beneficiary` — the solver's address for `RedeemEscrow`, or the original user's address for `RefundEscrow` [3](#0-2) [2](#0-1) . The same pattern exists in the GET-response cancellation path (`onGetResponse` → `_withdraw`) and same-chain cancellation (`_cancelSameChain`) [4](#0-3) . The Tron variant of `IntentGatewayV2` has an equivalent `withdraw()` function with the same push-only design [5](#0-4) .

If any of these beneficiaries (a solver who filled the order, or the order's original user) is later blacklisted by the escrowed ERC-20 (e.g. USDC), the `safeTransfer` call reverts. Because `EvmHost.dispatchIncoming` deletes the receipt on failure to allow a retry [1](#0-0) , the message stays perpetually retryable but can never succeed while the beneficiary is blacklisted. There is no mechanism in `IntentsBase`/`IntentGatewayV2` to redirect the withdrawal to an alternate address, and once the request's `timeoutTimestamp` is exceeded there's no timeout handler defined for the `RedeemEscrow`/`RefundEscrow` message kind to release the escrow to anyone else. The tokens escrowed under `_orders[commitment][token]` therefore remain locked in the `IntentGatewayV2` contract indefinitely.

### Impact Explanation
Medium: user or solver funds already escrowed in the contract become permanently unrecoverable once the token issuer blacklists the relevant beneficiary address, which the protocol cannot prevent or route around. This is a real freezing-of-funds scenario reachable purely by normal usage (placing/filling/cancelling an intent order) combined with an external, out-of-protocol event (blacklisting), matching the analog's "stuck funds" class.

### Likelihood Explanation
Requires the input/escrowed token to implement an admin blacklist (USDC and several other major stablecoins do) and requires the specific beneficiary address (solver or user) to become blacklisted between order placement/fill and settlement. This is a plausible, externally-triggerable condition rather than a contrived edge case, though it depends on real-world compliance actions outside the protocol's control.

### Recommendation
Add a pull-based fallback: if the push transfer to `beneficiary` fails, credit the amount to an internal claimable balance for that beneficiary (or an owner-updatable rescue address) rather than reverting the whole settlement, and let the beneficiary (or a re-specified address) withdraw later via a separate `claim()` call. Alternatively, wrap the token transfer in a try/catch and on failure escrow the funds under the beneficiary key for a delayed, governance-assisted redirect.

### Proof of Concept
1. User places a cross-chain order via `placeOrder`, escrowing USDC as `order.inputs` [6](#0-5) .
2. A solver fills the order on the destination chain; the source-chain settlement dispatches a `RedeemEscrow` POST request with `beneficiary = solver` [7](#0-6) .
3. Before the message is delivered, Circle blacklists the solver's address on USDC.
4. The relayer delivers the message; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which calls `IERC20(usdc).safeTransfer(solver, amount)`; USDC's `transfer` reverts because `solver` is blacklisted [8](#0-7) .
5. `dispatchIncoming` catches the revert and deletes the receipt, allowing indefinite retries, but every retry fails identically while the blacklist is in effect; the escrowed USDC remains stuck in the `IntentGatewayV2` contract with no path to recovery (test scaffolding for the normal, non-blacklisted flow is at [9](#0-8) , which would fail to complete under this condition).

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
