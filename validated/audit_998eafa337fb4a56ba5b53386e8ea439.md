### Title
Sybil delivery of self-dispatched ISMP messages lets a relayer mint unlimited `ReputationAsset` and buy collator-selection power - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
`pallet-messaging-incentives` mints a `ReputationAsset` to whichever account signed as `relayer` on every executed ISMP `Request`/`Response` message, scaled purely by payload byte-size (`bytes × MintPerByte`), with no cap, no requirement that a real fee was paid, and no check that the message reflects genuine third-party demand. `pallet-collator-manager` then uses that same `ReputationAsset` balance to rank and select collators every session. This reproduces the "sponsor vault sybil" pattern from the external report: an actor that controls both ends of a message flow (source dispatcher and destination "relayer") can generate arbitrarily many self-serving deliveries to drain/inflate an incentive pool that has no sybil-resistance, at no economic cost beyond ordinary transaction fees.

### Finding Description
`FeeHandler::on_executed` in `modules/pallets/messaging-incentives/src/lib.rs` (lines 156-187) runs for every batch of ISMP messages `pallet-ismp` executes: [1](#0-0) 

For each `Message::Request`/`Message::Response`, it computes `bytes = max(body_len, 32)` per request [2](#0-1) , recovers a `relayer` account purely from the sr25519 signature embedded in the message's own `signer` field [3](#0-2) , and unconditionally mints `bytes × MintPerByte` of `ReputationAsset` to that account via `T::ReputationAsset::mint_into`.

Nothing in this flow:
- Requires that the message carried a real fee (`RequestPayments`/fee metadata is irrelevant here — minting is keyed only to byte size).
- Requires that source and destination are distinct, unrelated parties.
- Caps how many messages, or how large the aggregate mint, a single account can produce.
- Distinguishes a message delivered on behalf of a genuine third-party application from a message an attacker dispatched to itself and then delivered/signed itself.

Because dispatching an ISMP request on the source chain and later submitting/"delivering" it as the signing relayer on the destination side (Hyperbridge) are both actions available to any unprivileged account, an attacker can act as both the source application and the delivering relayer, repeatedly dispatching padded-body requests between accounts it controls and self-signing the delivery. Each round mints new `ReputationAsset` with no offsetting value flowing anywhere — this is the same "no mechanism to detect sybil attacks" defect the report describes for Connext's sponsor vault, just against a mint-based incentive rather than a funded vault.

The consequence is compounded because `ReputationAsset` is not a purely cosmetic score: `pallet-collator-manager::new_session` (modules/pallets/collator-manager/src/lib.rs, lines 503-571) ranks and selects the parachain's collator set strictly by each candidate's `ReputationAsset` balance: [4](#0-3) 

So unbounded self-minting is not merely inflating an inert counter — it is a direct lever on who becomes a block-producing collator for the chain.

### Impact Explanation
This is an unbacked-mint plus unauthorized-app-action class issue:
- **Unbacked mint**: `ReputationAsset` supply increases with no corresponding economic contribution, purely from an attacker relaying its own self-dispatched traffic — directly analogous to the sponsor-vault sybil drain, except the "funds" being extracted are freshly minted tokens rather than a pre-funded pool.
- **Unauthorized consensus/app influence**: because `pallet-collator-manager` uses this same balance to pick collators, an attacker with enough capital to pay ordinary dispatch gas costs can out-mint legitimate relayers and force its own controller account into (or ahead of) the collator set, undermining the intended "select collators based on real bandwidth delivered" design goal stated in the pallet's own README.

Severity is High if `MintPerByte` is set to a non-zero value on any runtime and the `ReputationAsset` genuinely feeds `pallet-collator-manager`'s session selection (as it does in `parachain/runtimes/gargantua` and `parachain/runtimes/nexus`, both of which reference `ReputationAsset`) — this converts a spam-cost budget into leverage over network consensus composition.

### Likelihood Explanation
Likelihood is High once minting is enabled with a non-trivial rate: the attacker only needs (a) an account that can dispatch ISMP requests on some source chain, and (b) the ability to sign/submit the corresponding delivery on Hyperbridge as the "relayer" — both are ordinary, unprivileged, permissionless capabilities in the protocol's design (self-relay is explicitly supported: "Apps that prefer to self-relay can leave the fee at zero"). No proof forgery, governance compromise, or privileged role is required — only repeated self-dealing traffic, whose only real cost is normal transaction/storage fees on the source chain, which are unrelated to and can be far smaller than the `MintPerByte` reward if governance sets the rate generously.

### Recommendation
- Do not mint reputation based purely on byte count of self-controlled traffic; tie the mint to genuine, fee-backed deliveries (e.g., only mint when `RequestPayments`/fee metadata shows a real, non-self-paid fee was collected from a source distinct from the relayer/destination beneficiary).
- Introduce a per-account (or per-source-destination-pair) cap or decay on `ReputationAsset` accrual per session, mirroring the recommendation in the referenced report to "cap" sybil-exploitable incentive flows rather than relying on economic disincentive alone.
- Consider requiring that the message's source application/account differ from the relayer/signer account, or otherwise detect same-controller round-tripping, before minting.
- If reputation must remain purely byte-based, decouple it from collator-selection weight, or apply a governance-tunable ceiling on the influence a single account's `ReputationAsset` balance can have on `new_session` selection.

### Proof of Concept
1. Governance sets `MintPerByte::<T>` to a non-zero value via `set_mint_per_byte` (as intended for normal operation).
2. Attacker controls account `A` on some connected source chain and account `A'` (same key material, or associated) as the Hyperbridge relayer.
3. Attacker dispatches an ISMP `PostRequest` from `A` to a destination it also controls, with `body` padded to a large size (e.g. several KB), attaching zero or minimal fee (self-relay is explicitly supported with zero fee per the fee docs).
4. Attacker (as the relayer) submits/signs the delivery `Message::Request` themselves so that `Pallet::relayer_for` recovers `A'` as the reward recipient (`modules/pallets/messaging-incentives/src/lib.rs:140-153`).
5. `pallet-ismp` invokes `FeeHandler::on_executed`, and `messaging-incentives` mints `bytes × MintPerByte` of `ReputationAsset` into `A'` with no check on the relationship between the message's origin and its relayer (`modules/pallets/messaging-incentives/src/lib.rs:160-186`).
6. Attacker repeats steps 3-5 arbitrarily many times, each round only bounded by normal source-chain transaction/storage fees, accumulating an unbounded `ReputationAsset` balance in `A'`.
7. At the next session boundary, `pallet-collator-manager::new_session` ranks candidates by `ReputationAsset` balance (`modules/pallets/collator-manager/src/lib.rs:511-530`), letting the attacker's inflated balance push `A'`'s controller into the collator set ahead of legitimate participants.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
