### Title
Webhook shop identity not bound to HMAC-verified payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`) values used by `ShopifyAPI::Webhooks::Registry.process` to dispatch and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC strictly over `verifiable_query.to_signable_string` (i.e., the raw body) using the app's `api_secret_key`, and compares it to the `hmac` header: [2](#0-1) 

Meanwhile, `Request#shop` and `Request#topic` are read directly from the (unsigned) `x-shopify-shop-domain` / `shopify-shop-domain` and `x-shopify-topic` headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to dispatch to a handler, constructing `WebhookMetadata` with the unauthenticated shop value: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, bytes-that-determine-the-processed-shop)`. Instead, `hmac == HMAC(secret, raw_body)` while `shop-used-by-handler == unauthenticated-header`. Because the same `api_secret_key` is shared across every shop that has installed the app, any actor who legitimately controls one installation of the app (e.g., installs it on their own test/free development store) can capture a genuinely-signed `(raw_body, hmac)` pair for a webhook triggered on their own store, then resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header (e.g., a victim merchant's domain). `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source of that (attacker-supplied) event data.

### Impact Explanation
This breaks the shop/tenant identity binding at the core of the webhook trust model: the cryptographic guarantee ("this HMAC was produced by Shopify for api_secret_key X") no longer implies "for shop Y." An app relying on `data.shop` from `WebhookMetadata` to select which merchant's session/data record to act on (a standard, encouraged pattern — see `WebhookMetadata` fields consumed by handlers) can be made to apply attacker-controlled webhook content under an arbitrary victim shop's identity, which is a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Any actor able to install the target app on at least one shop (a very low bar — free development stores are trivially obtainable) can generate valid `(body, hmac)` pairs at will and replay them with a forged shop header directly to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or any privileged account is required.

### Recommendation
Bind the values used for dispatch/authorization to the signed content: require applications (and provide gem-level enforcement) to validate that the shop header claimed by the webhook matches a shop that is both installed and expected to have triggered that specific event, or include the shop/topic identity as part of what is validated before trusting it (e.g., cross-check `request.shop` against a table of active installations rather than trusting the header verbatim), and document this gap prominently in `Registry.process`/`WebhookMetadata` usage guidance.

### Proof of Concept
1. Install the app (as an ordinary merchant) on `attacker-shop.myshopify.com`, and receive a legitimate webhook: Shopify sends `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Capture `B` and the valid HMAC value.
3. Send a new POST to the same app endpoint with the identical body `B` and HMAC header, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) passes because it only checks `B` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
