This confirms the root cause. The `@exodus/browser-extension-adapters/seco-storage` implementation (which is the concrete `seedStorage` used for encrypting the mnemonic seed) explicitly falls back to plaintext storage whenever no `passphrase` is supplied: `if (!passphrase) return storage.set(key, value)` [1](#0-0) . The `@exodus/wallet` module's `#setSeed` is the code path that decides whether a `passphrase` gets forwarded to `seedStorage.set`, and it only forwards one if the caller explicitly provided a passphrase, or if `useAutoGeneratedPassword` is enabled (which auto-generates one) [2](#0-1) . When a consuming app configures the wallet feature with `usePassword: true` but `useAutoGeneratedPassword: false` (or `usePassword: false` entirely) and the user calls `wallet.create()`/`wallet.import()` without a `passphrase`, the mnemonic seed is persisted through `seedStorage.set(SEED_KEY, seed, { passphrase: undefined })`, which the seco-storage adapter stores completely unencrypted on disk [3](#0-2) . This is exactly the bug class from the report — the wallet layer permits creating a wallet backup/storage entry with no encryption at all, silently, with no error or warning surfaced from this layer (any warning would have to be added by a UI layer not present in this SDK).

### Title
Wallet module persists the mnemonic seed completely unencrypted when no passphrase is supplied - (File: features/wallet/module/wallet.js)

### Summary
The `@exodus/wallet` feature's `#setSeed` method only forwards a `passphrase` to the underlying `seedStorage.set()` call when the caller explicitly supplies one or when `useAutoGeneratedPassword` is enabled. If a consuming app configures the wallet with `usePassword: true`/`useAutoGeneratedPassword: false` (or disables `usePassword` altogether) and a user calls `wallet.create()`/`wallet.import()` without providing a passphrase, the seed is stored via `seedStorage.set(SEED_KEY, seed, { passphrase: undefined })`. The concrete `seedStorage` adapter shipped in this monorepo, `@exodus/browser-extension-adapters/seco-storage`, treats a missing `passphrase` as an explicit signal to skip encryption entirely and writes the raw mnemonic/seed object to the underlying unsafe storage.

### Finding Description
`Wallet#setSeed` in `features/wallet/module/wallet.js` decides encryption purely based on whether a `passphrase` string ends up populated:
```
#setSeed = async ({ seed, passphrase }) => {
  if (this.#usePassword) {
    if (passphrase) { ... mark hasUserSetPassphrase ... }
    else {
      if (this.#useAutoGeneratedPassword) { passphrase = genPassphrase(); ... }
      await this.walletStorage.set(HAS_USER_SET_PASSPHRASE_KEY, false)
    }
  }
  await this.walletStorage.set(SEED_KEY, seed, { passphrase })
  ...
}
``` [2](#0-1) 

If `usePassword` is `false`, or `usePassword` is `true` but `useAutoGeneratedPassword` is `false` and the caller passes no passphrase, `passphrase` remains `undefined` and gets forwarded as `{ passphrase: undefined }` into `seedStorage.set`.

The actual `seco-storage` adapter (a `seedStorage` implementation shipped for browser-extension consumers) implements this contract literally:
```
const _set = async (key, value, opts = {}) => {
  const { passphrase } = opts
  if (!passphrase) return storage.set(key, value)   // <-- plaintext write, no encryption
  ...
  data = await seco.encryptString({ data, key: passphrase, encoding, appVersion })
  return storage.set(key, data)
}
``` [4](#0-3) 

The `@exodus/wallet` README explicitly documents that "encryption is the responsibility of `seedStorage`" and that the wallet module simply forwards whatever `passphrase` it receives [5](#0-4) . The wallet feature configuration allows `usePassword` and `useAutoGeneratedPassword` to both be disabled by config [3](#0-2) , and even with `usePassword: true`/`useAutoGeneratedPassword: false`, a plain `wallet.create()` call with no passphrase silently produces an unencrypted, plaintext mnemonic at rest — mirroring the reported bug class of allowing users (or an integrating app on the user's behalf) to persist an unencrypted backup of the wallet's secret key material with no forced minimum protection.

### Impact Explanation
If the raw storage backing `seedStorage` (e.g., `chrome.storage.local`, or any persistent/sync-capable store an integrator plugs in) is later synced, backed up, or otherwise exfiltrated, the attacker obtains the plaintext BIP-39 mnemonic directly — full compromise of every asset derived from that seed, no decryption needed. This matches the core impact concern in the report: full custody compromise once the backup medium is compromised, since there is no forced encryption floor.

### Likelihood Explanation
Reachable purely through the documented, unprivileged SDK API: `wallet.create({ mnemonic })` / `wallet.import({ mnemonic })` with no `passphrase` argument, combined with a wallet feature configuration where `useAutoGeneratedPassword` is disabled (a supported, documented configuration flag) [6](#0-5) . No privileged/administrative access or malicious peer is required — any consumer of the SDK/browser extension calling the ordinary onboarding flow without passing a passphrase triggers plaintext storage.

### Recommendation
- Short term: In `Wallet#setSeed`/`#getSeed`, when `usePassword` is enabled, refuse to persist the seed unless a passphrase is present (either user-supplied or auto-generated) rather than silently falling through to `{ passphrase: undefined }`. Likewise, harden `seco-storage`'s `_set`/`_get` to throw rather than silently write plaintext when `passphrase` is missing, forcing callers to opt in to unencrypted storage explicitly instead of by omission.
- Long term: Require callers to declare an explicit `allowUnencrypted` flag before `seedStorage` will ever accept a missing passphrase, and audit all `seedStorage`/`seco-storage` consumers in the monorepo to ensure they always supply a passphrase for the primary seed.
