### Title
Unbounded-length attacker-controlled `from` address panics `HyperFungibleToken::on_accept` via `H160::from_slice`/`copy_from_slice` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The CVE-2017-7854 bug class is a crafted-input parser that reads/derefs attacker-controlled bytes without validating length, causing a crash (heap over-read/DoS) in `consume_init_expr`. The closest reachable analog in this codebase is `HyperFungibleToken`'s ISMP `on_accept` handler in `modules/pallets/hyper-fungible-token/src/module.rs`, which derives the beneficiary/origin account from `message.from` without checking that the byte length matches the expected 20 (EVM) or 32 (Substrate) bytes before slicing/copying.

### Finding Description
In the calldata-execution branch of message handling: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

`message.from` originates from the ISMP `Post` request's `from` field, which is set by the *source* chain's dispatching contract/pallet address. Because Hyperbridge is a permissionless cross-chain messaging protocol, an unprivileged actor can deploy an arbitrary contract/pallet on the source state machine and dispatch an ISMP `Post` request whose `from` field is any byte sequence of the sender's choosing — it is not constrained to 20 or 32 bytes by the ISMP request format itself. This request, once relayed with a valid state/consensus proof, is fully attested at the protocol layer (the proof only certifies that this exact byte sequence was committed on the source chain — not that it has a particular length).

When such a message reaches `on_accept` and takes the `substrate_data.signature.is_none()` path (i.e., no signature attached, from-address path taken):
- If `source.is_evm()` is true but `from_bytes.len() < 20`, the expression `from_bytes.len() - 20` underflows `usize`, causing an arithmetic-overflow panic in debug builds, or (in release builds with wrapping/overflow-checks off) a massive index that panics on the subsequent slice bounds check — either way, a runtime panic.
- If `source.is_evm()` is false, `account.copy_from_slice(from_bytes)` panics whenever `from_bytes.len() != 32` (the standard `copy_from_slice` behavior on mismatched length), which is entirely plausible for a substrate-labeled source chain whose dispatching pallet id/account representation the attacker controls in a crafted proof.

This exactly mirrors the `consume_init_expr`-style bug class: parsing/consuming attacker-supplied bytes with an implicit fixed-length assumption and no defensive length check before indexing, leading to a crash.

### Impact Explanation
A panic inside `on_accept`, invoked from the pallet-ismp message-handling dispatch path, halts extrinsic execution for that call. Because this can be triggered by any unprivileged party who can dispatch a cross-chain `Post` request to the `HyperFungibleToken` module (via a properly proven, but content-arbitrary, request), it is a remotely triggerable denial-of-service against message processing for this module — consistent with a Medium-severity “crash / DoS” finding, matching the reference CVE’s CVSS profile (`AV:L`-like reachability translated to “reachable via a relayed, proof-verified message” in this system, `C:N/I:N/A:H`).

### Likelihood Explanation
Likelihood is high for any party willing to deploy a throwaway contract/pallet on a supported source chain and dispatch one non-standard-length `from` message through the bridge with a valid delivery proof — no privileged role, governance, or malicious relayer/validator collusion is required. The trigger condition (short or oversized `from`) is trivial to construct.

### Recommendation
Validate `from_bytes.len()` against the expected 20/32-byte length before slicing or copying, and return an explicit `HftError` (e.g., `InvalidFromAddressLength`) instead of panicking, mirroring the defensive length checks already applied elsewhere in the codebase (e.g., the Pharos SPV proof `nibble_at_depth`/`ProofTooDeep` guards, the BEEFY `leaf_indices.len() != 1` guard, and the RLP `decode_plan` empty-HP-prefix guard).

### Proof of Concept
1. On an EVM source chain, deploy a minimal contract that calls the local `IIsmpDispatcher` to dispatch a `Post` request to the `HyperFungibleToken` module id on the destination chain, but craft the request manually via a relayer/off-chain script so the `from` field is fewer than 20 bytes (e.g. 1 byte) while `source.is_evm()` still resolves true on the destination side, and `data` is a valid encoded `SubstrateCalldata` with `signature: None`.
2. Have any relayer submit the request together with a valid state/consensus proof from the source chain (proving inclusion of exactly this short `from` value — no consensus-layer validation constrains its length).
3. On delivery, `pallet-ismp`’s `handle_incoming_message`/dispatcher invokes `HyperFungibleToken::on_accept`, which executes `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() < 20`, causing an underflow/index panic and reverting/halting that message's processing — a remotely triggerable crash requiring only a normal cross-chain dispatch and a relayer, no special privileges.
