### Title
`migrate_from_blend` pre-authorizes token pulls to a caller-supplied `blend_pool`, letting a fake Blend pool drain controller-held tokens — (File: contracts/controller/src/external/blend.rs)

### Summary
The OpenClaw advisory describes credentials (an `Authorization` header) being forwarded across a cross-origin redirect to a party that was never meant to receive them. The analog in XOXNO Lending is invoker-contract auth forwarded to an attacker-chosen contract: `blend_repay_all` builds exact-amount `token.transfer(controller → blend_pool, cap)` authorization entries **before** calling `blend_pool.submit(...)`, and `blend_pool` is supplied through `migrate_from_blend` rather than loaded from controller config. An unprivileged caller can pass a malicious contract as `blend_pool`; that contract directly invokes the pre-authorized `transfer` calls and pockets the controller's tokens — the "redirect" keeps the authorization intact while changing the effective recipient of the value.

### Finding Description
`authorize_repay_pulls` registers one `InvokerContractAuthEntry` per `(debt_asset, max)` pair, each authorizing `transfer(controller, blend_pool, max)` on the token contract, then `guarded_submit` calls `BlendPoolClient::submit(from, controller, controller, requests)` on the same `blend_pool` address [1](#0-0) . Because the auth entries are bound to the *token contract and the `blend_pool` recipient address* — not to any behavior inside `submit` — a hostile `blend_pool` contract can simply ignore the `submit` request semantics and call each authorized `token.transfer(controller → itself, max)` directly from within the `submit` invocation. The authorization "follows the redirect": it was intended to fund a real Blend repayment, but is redeemable by whatever contract sits at the supplied address.

The same shape exists in `swap_tokens`: `authorize_transfer_as_current(env, token_in, controller, router_addr, amount_in)` pre-authorizes a pull by the router before `execute_strategy` runs [2](#0-1) . There the recipient is config-bound (`storage::get_swap_aggregator`), so it is safe; the Blend path differs precisely because `blend_pool` comes in through the migration entrypoint arguments rather than trusted storage, which is what makes this exploitable. In the router case the balance-delta checks (`RouterOverspend`) would also catch a router that over-pulls [3](#0-2) ; `guarded_submit` has no post-call balance verification for the repay pulls [4](#0-3) .

### Impact Explanation
Every authorized leg is an unconditional `transfer` from the controller's own balance to the attacker contract, up to each supplied `max`. Any tokens custodied at the controller address — flash-position proceeds in flight, excess-payment refunds pending, residual swap input, or stranded balances — can be pulled by the malicious `blend_pool` in a single `migrate_from_blend` call. That is theft of funds belonging to the protocol/users at the controller address, matching the credential-forwarding class (the auth grant is consumed by an unintended party).

### Likelihood Explanation
The path is reachable by any unprivileged address able to call `migrate_from_blend` with attacker-controlled `blend_pool` and `debt_caps` arguments; no signature, allowlist, or privileged role is required on the Blend submission itself. Exploit value is bounded by (a) how much debt-cap value the entrypoint lets the caller claim and (b) the controller's live token balances, which are typically transient — consistent with a Medium. A caveat on full verification: I did not read `contracts/controller/src/strategies/migrate_blend.rs` and `lib.rs` in this pass, so the exact validation applied to `blend_pool`/`debt_caps` (e.g., whether caps are clamped to positions read from a real Blend pool, or whether `blend_pool` is checked against a registered hub) is unconfirmed; if the entrypoint already binds `blend_pool` to on-chain-registered state, this finding is mitigated.

### Recommendation
- Source `blend_pool` from controller storage/config (a registered Blend pool per hub), not from caller arguments, mirroring how `storage::get_swap_aggregator` pins the router in `swap_tokens`.
- If dynamic pools must be supported, bind each authorized `transfer` to the *real* repaid amount measured after `submit` (balance-delta accounting like `RouterOverspend`), and revert if the pool pulled more than the position's actual repaid debt.
- Add post-`submit` verification in `guarded_submit` that the controller's token balances decreased by no more than the legitimately repaid amounts reported by the returned `BlendPositions`.

```rust
fn authorize_repay_pulls(env: &Env, blend_pool: &Address, debt_caps: &Vec<(Address, i128)>) {
    if debt_caps.is_empty() {
        return;
    }
    let controller = env.current_contract_address();
    let mut entries: Vec<InvokerContractAuthEntry> = Vec::new(env);
    for (debt_asset, max) in debt_caps.iter() {
        entries.push_back(InvokerContractAuthEntry::Contract(SubContractInvocation {
            context: ContractContext {
                contract: debt_asset,
                fn_name: symbol_short!("transfer"),
                args: (controller.clone(), blend_pool.clone(), max).into_val(env),
            },
            sub_invocations: Vec::new(env),
        }));
    }
    env.authorize_as_current_contract(entries);
```
