### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to attribute that body to a tenant. Because the shop identity is never part of the signed content, a party that legitimately receives one valid signed webhook (for their own shop) can replay the same body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` header to any other shop, causing the app to process attacker-controlled webhook data as if it belonged to a victim tenant.

### Finding Description
`Registry.process` validates authenticity like this: [1](#0-0) 

`Utils::HmacValidator.validate(request)` computes the HMAC using `request.to_signable_string`, which for webhook requests is defined as only the raw body: [2](#0-1) 

The `shop` value used to build `WebhookMetadata` (the tenant identity passed to the app's handler) is read directly from the `shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed bytes: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the app attributes the payload to`

Here that equality does not hold: the HMAC only binds `raw_body`, not `shop`. Since all shops that install the same app share a single `client_secret` (`Context.api_secret_key`), an HMAC computed by Shopify for shop A's webhook body is numerically identical to a valid HMAC for the same bytes delivered under any other shop header — the signature carries no shop-specific binding. `HmacValidator.validate` is generic and simply calls `compute_signature(verifiable_query.to_signable_string, secret)`; nothing in the webhook path ties the signature to `shop`: [4](#0-3) 

### Impact Explanation
Any application that uses `request.shop` inside its `WebhookHandler#handle` implementation (a pattern explicitly enabled by the gem, since `WebhookMetadata#shop` is a first-class field handed to every handler) to decide which tenant's data/session/store record to update will accept attacker-forged data under a victim's identity. This is a cross-tenant access primitive: an attacker who operates or compromises a single shop that has installed the app can capture a real signed webhook delivered to them, then re-POST the identical body+HMAC to the app's public webhook endpoint with the `shop-domain` header changed to any other installed shop, and the gem will treat it as validly authenticated data for that other shop.

### Likelihood Explanation
High. Webhook endpoints are public HTTP endpoints by necessity (Shopify posts to them over the internet), so nothing prevents an attacker from POSTing directly to them with arbitrary headers. Becoming a "shop" that installs the app is typically self-service/free for many app listings, so obtaining at least one legitimately-signed webhook body is trivial. The only requirement is a topic whose body content the attacker doesn't need to control precisely (they only need the header field, not the body, to point at the victim), which is satisfied for many webhook topics (e.g., `app/uninstalled`, generic topics with static or attacker-influenced bodies).

### Recommendation
Bind the shop (and ideally topic) into the material that is HMAC-verified, or otherwise cryptographically/contractually tie the `shop-domain` header to the request before trusting it. Concretely:
- Include the `shop-domain` header value in `Request#to_signable_string` (or require callers to separately verify that the `shop` in the payload/registered installation record matches the header) before constructing `WebhookMetadata`.
- At minimum, document/enforce that the resolved `shop` must be cross-checked against a known-installed-shop store keyed by something not attacker-suppliable, before webhook data is applied.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook they control the topic for (e.g. by performing the action that fires it).
2. Shopify posts the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `hmac-sha256` header value.
4. Attacker POSTs the same `raw_body` and `hmac-sha256` value to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object whose `hmac` still matches (`Utils::HmacValidator.validate` only checks `raw_body`), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to act on attacker-controlled body content attributed to the victim's tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
