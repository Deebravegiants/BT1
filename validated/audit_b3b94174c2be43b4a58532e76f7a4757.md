### Title
Relayer fee amounts are redeemed against the *current* `feeToken` instead of the token they were actually accrued in - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
Hyperbridge's relayer fee pallet accumulates a relayer's earned fees as a bare `U256` amount keyed only by `(dest_chain, address)`, with no record of which ERC-20 token that amount was denominated in at accrual time. When the relayer later withdraws, the pallet looks up whatever fee token is *currently* configured for that destination chain and pays out the stored numeric amount in that token. If governance rotates the destination chain's `feeToken` between accrual and withdrawal, a relayer who delays their claim receives the same face-value amount but in a different (potentially far more valuable) asset — the same "amount tracked without pinning the underlying asset" bug class described in the external StabilityPool report.

### Finding Description
Fees accrue in `Fees::<T>` via the accumulation pipeline in `modules/pallets/relayer/src/accumulate.rs`, which credits a relayer's balance for a given destination `StateMachine` based on proofs of message delivery [1](#0-0) . This balance is a plain amount with no token identity attached — it is not "100 units of token A," it is just "100."

When the relayer withdraws, `Pallet::withdraw` reads `available_amount` from `Fees::<T>::get(dest_chain, address)` and then, for EVM destinations, fetches the **current** host params for that chain to determine the token to pay out: [2](#0-1) 

Note specifically:
```
let HostParam::EvmHostParam(params) = HostParams::<T>::get(withdrawal_data.dest_chain)...
let body = WithdrawalParams { beneficiary_address, amount: available_amount.into(), token: params.fee_token }
```
`params.fee_token` is resolved at withdrawal time, not at the time the fee was earned. There is no per-token bucketing of `Fees`, analogous to the vulnerable `collateralGainsByDepositor` array indexed by collateral slot rather than by collateral identity in the external report.

The destination-side `feeToken` can change: EvmHost's `updateHostParamsInternal` allows swapping `feeToken` as long as the *EvmHost contract's own* balance of the old token is zero: [3](#0-2) 

This guard only protects protocol-owned revenue held directly by the host contract. It has no visibility into, and does nothing to reconcile, outstanding relayer balances sitting in `pallet-relayer::Fees` on the Hyperbridge chain — the exact same disconnect as the original bug, where `_overwriteCollateral` only checked collateral-slot invariants and never accounted for stale, unclaimed `collateralGainsByDepositor` entries pointing at that slot. Likewise, `pallet-hyperbridge-host-executive::update_evm_hosts`/host param updates for a state machine can change `EvmHostParam.fee_token` for any destination with no cross-chain check that all relayers with pending `Fees` balances for that chain have withdrawn first.

### Impact Explanation
Any relayer permissionlessly earning fees through the normal (unsigned, spam-protected) `accumulate_fees`/`withdraw` flow can strategically delay their withdrawal. If governance later changes the fee token for that destination — a legitimate, expected operational action, comparable to sunsetting/re-adding collateral — the relayer's stored numeric balance gets paid out in the new token at 1:1 face value, regardless of the new token's actual worth. This can result in disproportionate, unbacked payouts from the destination host's fee-token balance, i.e. theft of protocol/relayer-fee funds relative to what was actually earned, or (if the new token is worth less) the opposite unfairness to the relayer — either way an unsound accounting/settlement issue reachable without any special privilege beyond being a relayer that delivers messages.

### Likelihood Explanation
Fee-token rotation is a documented, intended admin capability (`updateHostParams`/`update_evm_hosts`), and relayer withdrawal timing is entirely relayer-controlled — a relayer incurs no cost or risk by delaying a withdrawal while watching for a fee-token change, mirroring the "attacker incurs no losses" likelihood argument in the source report.

### Recommendation
Denominate and store `Fees` per `(dest_chain, token)` rather than per `dest_chain` alone (e.g. `Fees: StorageMap<_, _, (StateMachine, Vec<u8> /* token */), Balance>`), so a relayer's withdrawal always resolves against the fee token that was actually in effect when the fee was accrued. Alternatively, require full settlement/draining of all outstanding `Fees` for a state machine as a precondition before its `fee_token` param can be rotated, mirroring — and closing the same gap left open by — the existing (but insufficient) `CannotChangeFeeToken` check in `EvmHost.sol`.

### Proof of Concept
1. Relayer R delivers messages to destination chain D whose current `feeToken` is Token A; `accumulate_fees` credits `Fees::<T>::get(D, R)` with amount `X` (see `modules/pallets/relayer/src/accumulate.rs`).
2. R does not call `withdraw`.
3. Governance (via `pallet-hyperbridge-host-executive::update_evm_hosts` or `EvmHost.updateHostParams`) rotates D's `fee_token` from Token A to Token B, a materially more valuable ERC-20, after first draining the EvmHost's own Token A balance to satisfy `CannotChangeFeeToken` (`evm/src/core/EvmHost.sol:617-621`).
4. R calls `Pallet::withdraw` for chain D; `withdrawal.rs:145-158` reads the *current* `HostParams::<T>::get(D)` and builds `WithdrawalParams{ amount: X, token: TokenB }`, dispatching a POST that instructs D's host manager to pay `X` units of Token B to R.
5. R receives `X` units of Token B, worth far more than the `X` units of Token A actually earned.
