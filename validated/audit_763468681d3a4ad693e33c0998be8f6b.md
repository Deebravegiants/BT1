## Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed payload — to identify which merchant the webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from an unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC only against `verifiable_query.to_signable_string`, i.e. the raw body, using the app-wide `Context.api_secret_key` (shared by every shop that installs the app, not per-tenant): [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the whole request, then forwards the never-verified `request.shop` straight into the handler-facing `WebhookMetadata`: [4](#0-3) 

The binding that should hold is:
`hmac_valid(raw_body, api_secret_key) == true` should imply `shop == the tenant that actually generated raw_body`.

In reality the equality that is enforced is only `hmac_valid(raw_body) == true`; `shop` is never part of what is authenticated. Because `api_secret_key` is the same for every installation of the app (it's the app's client secret, not a per-shop secret), any party who runs the app on their own store receives genuinely-signed webhook deliveries (valid `raw_body` + valid HMAC) for their own shop. That signed `(raw_body, hmac)` pair remains valid for any `shop` header value, since `shop` never entered the HMAC computation. Replaying the captured `raw_body`/HMAC pair against the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header causes `Registry.process` to accept the request and dispatch it to the app's handler labeled as belonging to a different (victim) shop.

The gem's own documentation encourages exactly this trust pattern, using `data.shop` directly for tenant-scoped dispatch without any extra verification step: [5](#0-4) 

### Impact Explanation
An app built per the gem's documented usage (dispatching by `data.shop`) can be made to process attacker-controlled but validly-HMAC'd webhook content as if it originated from an arbitrary victim shop. This is a tenant-identity confusion / cross-tenant access issue: the attacker (who only needs to install the app on their own shop — an unprivileged action requiring no credentials or access tokens belonging to the victim) can inject data attributed to another merchant's shop into the host app's business logic (e.g., triggering shop-scoped background jobs, cache writes, or webhook-driven state changes keyed by `shop`).

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on their own (attacker-controlled) Shopify store — a normal, unprivileged, self-service action — and then replay a captured, genuinely-signed webhook body against the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain`/`shopify-shop-domain` header. No secrets, tokens, or victim credentials are required, and the vulnerable code path (`Registry.process` / `HmacValidator.validate` / `Request#shop`) is exercised on every documented webhook integration.

### Recommendation
Do not treat `request.shop` as authenticated data derived purely from HMAC validation. At minimum:
- Document prominently that `shop` in `WebhookMetadata` is unauthenticated and must be cross-checked by the host application against a known/installed shop before being used for tenant-scoped actions.
- Where feasible, have `Registry.process` require the caller to supply the expected/authorized shop (e.g., from an existing session lookup) and verify it matches `request.shop` before invoking the handler, rather than passing the raw header value straight through.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`) via the app's normal registration flow.
2. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint: raw body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, and `X-Shopify-Hmac-SHA256: HMAC(api_secret_key, B)`.
3. Attacker captures this request and replays it to the same endpoint, changing only the header to `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and the HMAC value identical.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still matches (`lib/shopify_api/utils/hmac_validator.rb:26-31`), so `Registry.process` accepts the request and calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload never originated from `victim.myshopify.com`.
