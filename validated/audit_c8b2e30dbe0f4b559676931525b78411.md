### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read straight from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, and `ShopifyAPI::Webhooks::Registry.process` forwards this value unmodified into `WebhookMetadata#shop`, which host apps use to attribute the webhook body to a tenant (session lookup, GDPR redaction, uninstall handling, etc.). However, the HMAC signature that `Registry.process` verifies via `Utils::HmacValidator.validate` is computed only over the raw body, never over the shop-domain header. This breaks the intended identity binding `authenticated_bytes == shop_used_for_tenant_routing`.

### Finding Description
`Registry.process` is documented as verifying "the request did indeed come from Shopify" before dispatching to a handler: [1](#0-0) 

The verification call is: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [3](#0-2) 

For webhooks, `to_signable_string` is defined as just the raw body — no headers are included in the signed content: [4](#0-3) 

Meanwhile, `shop` is read directly from an attacker-controllable header with no cryptographic tie to the HMAC: [5](#0-4) 

This `shop` value is what gets handed to the app's handler as the trusted tenant identity: [6](#0-5) [7](#0-6) 

The library even singles out three mandatory GDPR topics (`shop/redact`, `customers/redact`, `customers/data_request`) that every app must implement: [8](#0-7) 

This mirrors the reported bug class exactly: a field that is acted upon (here, the shop the webhook body is attributed to) is not covered by the same authentication primitive (HMAC) that gates whether the request is trusted at all. `Utils::HmacValidator.validate` only proves "this body+HMAC pair was produced with the app's `api_secret_key` for *some* shop"; it proves nothing about *which* shop the accompanying `shop-domain` header claims.

### Impact Explanation
Because the shop identity is decoupled from the signed content, once an attacker obtains any one genuine `(raw_body, hmac)` pair produced by Shopify for the app (for example, by triggering an event on a store they legitimately control and viewing the delivery details/HMAC through the app's own webhook logging, retry/replay UI, or their own request logging on a proxy they control before it reaches the app — none of which requires the app's `api_secret_key`, TLS interception, or privileged access), they can resend that exact body and HMAC directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` will accept it as valid (HMAC still matches, since the header isn't part of the signed content) and dispatch it to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that uses `data.shop` to key off session storage, trigger data-redaction, mark the app uninstalled, or otherwise perform tenant-scoped side effects is silently attributed to the wrong tenant — a cross-tenant identity-binding break.

### Likelihood Explanation
Exploitation only requires: (1) any store the attacker controls or has otherwise observed a webhook delivery from (no `api_secret_key`, no access token, no TLS interception needed), and (2) the ability to send a normal HTTP POST to the app's public webhook endpoint, which is by design internet-reachable. The gem's own documentation actively encourages developers to trust `data.shop` as the verified tenant identity once `Registry.process` returns without raising, reinforcing that this is a library-level trust boundary problem rather than host-app misuse.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header value as part of the HMAC-signed content used in `Utils::VerifiableQuery#to_signable_string` for webhook requests, or otherwise cryptographically bind the claimed shop to the verified payload before constructing `WebhookMetadata`. At minimum, document prominently that `data.shop` is not authenticated by the HMAC check and must not be used for tenant-scoped authorization decisions without independent verification (e.g., cross-checking against a shop known from an active, previously-established session).

```ruby
# 2. Attacker triggers a webhook (e.g. "orders/create") and captures the exact
#    raw_body + X-Shopify-Hmac-Sha256 that Shopify sent to the app's endpoint
#    (via the app's own webhook delivery logs/retry tooling, or a proxy the
#    attacker controls in front of their own test infrastructure).
raw_body = '{"id":1,...}'          # captured genuine body
hmac     = "captured-valid-hmac"   # captured genuine HMAC for that body

# 3. Attacker replays the same body/HMAC pair directly to the app's public
#    webhook endpoint, but swaps the shop-domain header to the victim's shop.
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,          # still matches raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "attacker-controlled-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (Utils::HmacValidator.validate only checks raw_body),
#    handler.handle is invoked with WebhookMetadata#shop == "victim-shop.myshopify.com",
#    even though the payload never originated from that shop.
```
