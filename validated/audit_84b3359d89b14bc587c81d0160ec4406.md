This confirms my analysis: `signer_id` for the newly-signed payload flows only from `IntentPayloadBuilder`/`intentParams`/`intentPayloadFactory` values that the calling application itself controls, never from `signedIntents.before`/`.after`.

### Analysis

The claimed equality is: `signed.signer_id (of the newly created MultiPayload) == the signer_id value the caller intended when constructing the new intent`.

Tracing `IntentExecuter.signAndSendIntent` [1](#0-0) :

1. `intentPayload` (including `signer_id`) is built purely from `defaultIntentPayloadFactory(salt, {verifying_contract, ...intentParams})` and optionally merged with `this.intentPayloadFactory` via `mergeIntentPayloads` — neither of these ever reads from `signedIntents`. [2](#0-1) 
2. `this.intentSigner.signIntent(intentPayload)` (e.g. `IntentSignerViem.signIntent`) then serializes exactly this `signer_id`/`verifying_contract`/`deadline`/`nonce`/`intents` into the JSON `payload` string and signs it with the local key. [3](#0-2) 
3. Only *after* signing does `composeMultiPayloads(multiPayload, signedIntents)` run, and it merely concatenates the caller-supplied `before`/`after` arrays with the new `multiPayload` — it does not read, write, or merge any field from those payloads into the new one: `result.push(...before); result.push(newPayload); result.push(...after)`. [4](#0-3) 

So the pre-signed `MultiPayload`s in `signedIntents.before/.after` are opaque, already-signed, independent payloads (each already containing its own `signer_id`, and already having been produced by `signIntent`/`signRaw` under some other key). There is no code path where their content is copied, merged, or otherwise mixed into the currently-being-signed `intentPayload`. Tests confirm this behavior explicitly — the composed array is exactly `[before..., newPayload(as its own object), after...]` with no field bleed. [5](#0-4) 

Furthermore, `intents.near` verifies each `MultiPayload` entry in a batch independently against its own embedded `signer_id`/`verifying_contract` and its own signature (ERC-191 hash is `keccak256` over the exact JSON `payload` string of that single entry, per `computeSignedErc191Hash`) [6](#0-5) . An attacker cannot alter a byte of an already-signed `payload` (including its `signer_id`) without invalidating that entry's own signature — the signature covers the *entire* payload string, not just `intents`.

To place a foreign `signer_id` into `before`/`after`, the caller (an "unprivileged" SDK user) would need to already possess a validly-signed `MultiPayload` from that other signer — i.e. they'd need the victim's private key or the victim's own cooperation (e.g., a counterparty forwarding a legitimately quote-signed payload for atomic settlement, which is the documented, intended use of `signedIntents`). This is not a forgery — it's presenting a payload that party already authorized under their own signature, for their own `signer_id`, with their own intents, exactly as they signed it. There is no mechanism by which an attacker can make `intents.near` accept a `native_withdraw` intent debiting `wrap.near` from a `signer_id` who never signed it.

`signedIntents.before`/`.after` is explicitly documented as an intentional atomic-composition feature for the SDK ("Useful for dependencies that must be executed first" / "cleanup or follow-up actions") [7](#0-6) , which per the rules of this audit is an "documented escape hatch," out of scope unless it's misused to alter fields of *another* signer's payload — which, as shown, it structurally cannot do.

function composeMultiPayloads(
	newPayload: MultiPayload,
	signedIntents?: SignedIntentsComposition,
): MultiPayload[] {
	if (!signedIntents) {
		return [newPayload];
	}

	const result: MultiPayload[] = [];

	// Add "before" intents first
	if (signedIntents.before && signedIntents.before.length > 0) {
		result.push(...signedIntents.before);
	}

	// Add the new payload
	result.push(newPayload);

	// Add "after" intents last
	if (signedIntents.after && signedIntents.after.length > 0) {
		result.push(...signedIntents.after);
	}

	return result;
}
