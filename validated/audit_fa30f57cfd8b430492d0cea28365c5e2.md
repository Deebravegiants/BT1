### Title
Webhook `shop` (tenant) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to route and attribute the webhook to a tenant are read from HTTP headers that are never included in the signed data. `Registry.process` validates only the body HMAC and then hands the unauthenticated `shop` header straight to the app's handler, breaking the binding `shop_authenticated == shop_acted_on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled from HTTP headers that are outside of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `to_signable_string`, i.e. the raw body bytes, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly that check and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity passed to the app's handler: [4](#0-3) 

Because the `api_secret_key` is a single per-app secret shared across every shop that installs the app, any merchant that installs the app can obtain a body + HMAC pair that Shopify signs as genuine (e.g. by triggering a real event on their own store and capturing the raw POST that Shopify sends to their app's public webhook endpoint). That same `(raw_body, hmac)` pair remains valid forever for that body, regardless of which `shop-domain` header is sent alongside it, because the header is never part of the signed content. An attacker can therefore resubmit the untouched, validly-signed body to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and even `x-shopify-topic`) for a victim shop. `HmacValidator.validate` still returns `true`, and `WebhookMetadata.shop` ends up holding the attacker-chosen victim domain: [5](#0-4) 

This is the direct analog of the reported bug class: a value that is *acted on* (here, tenant attribution via `shop`) is not covered by the binding check (the HMAC) that is supposed to authenticate the whole request.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to decide which tenant's records to create/update/delete (the documented and expected usage pattern for `Registry.process`) can be made to apply attacker-supplied webhook data to a different shop's records purely because the shop identity is not part of what is cryptographically verified. This is a cross-tenant integrity/data-confusion issue reachable by any unprivileged actor who can install the app on their own store (a normal, unprivileged action) and send one HTTP request to the app's public webhook endpoint — no leaked credentials, access tokens, or `api_secret_key` are needed.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires only (1) installing the target app on an attacker-controlled shop (self-service, no special privilege), (2) capturing one legitimately signed webhook body/HMAC pair from that shop, and (3) replaying it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. All of the gem's own validation logic (`HmacValidator.validate`) passes unchanged because it never inspects headers.

### Recommendation
Bind the tenant-identifying header(s) into the value that is HMAC-verified, or perform a secondary authenticated check that the `shop` header matches a shop this app instance actually has an active session/installation for before invoking the handler. At minimum, `Request#to_signable_string` (or a new signable representation used specifically for header validation) should incorporate `shop`, `topic`, and `webhook_id` so that tampering with those headers invalidates the HMAC, mirroring how `AuthQuery#to_signable_string` correctly includes every field it later relies on (`code`, `host`, `shop`, `state`, `timestamp`).

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed event (e.g. `orders/create`) so Shopify sends a webhook POST to the app's public endpoint, capturing:
   - `raw_body` (JSON payload)
   - `x-shopify-hmac-sha256` header (valid HMAC over `raw_body` using the app's shared `api_secret_key`)
2. Resend an HTTP POST to the same public webhook endpoint with:
   - Same `raw_body` and same `x-shopify-hmac-sha256` (unchanged, still valid)
   - `x-shopify-shop-domain` header rewritten to `victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation succeeds: [6](#0-5) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload/event actually originated from the attacker's own shop, allowing data to be misattributed/cross-applied to the victim tenant.
