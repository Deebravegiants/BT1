### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop`, `topic`, and `webhook_id` fields are read from HTTP headers that are never covered by that HMAC computation.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate_signature` computes/compares the signature exclusively against that signable string using the app-wide `Context.api_secret_key` [2](#0-1) . Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are all derived from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no cryptographic binding to the HMAC at all [3](#0-2) .

`Registry.process` raises only if the HMAC check on the body fails, then immediately constructs `WebhookMetadata` from the unauthenticated header values and forwards it to the app's handler: [4](#0-3) . The `WebhookMetadata` struct that the handler receives and is expected to trust for tenant-scoping is `const :shop, String` populated straight from `request.shop` [5](#0-4) .

Because `Context.api_secret_key` is a single, app-wide secret shared across every merchant/shop that has installed the app (it is not scoped per-shop), the "binding" the code implicitly relies on is:
`HMAC(body, api_secret_key) valid` ⟺ `body legitimately originated from shop X`

but the actual equality that must hold and does not is:
`shop used by handler (from unauthenticated header)` == `shop that the HMAC-verified body actually belongs to`.

An attacker who legitimately installs the app on their own shop (an "unprivileged" tenant relative to any other merchant) receives real webhooks for their own shop with a valid `(body, hmac)` pair. Nothing in `HmacValidator.validate` or `Request` binds that pair to the `shop-domain` header. If the attacker can deliver a request to the app's public webhook endpoint with the same body/HMAC but a different `shopify-shop-domain` header, `Registry.process` will pass the HMAC check (same body, same app secret) and dispatch `WebhookMetadata` with the attacker-chosen `shop` value to the handler, which typically uses `data.shop` to select the tenant's database/session/tokens to update.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem verifies only the body's integrity/authenticity, not the shop attribution that host applications rely on to route webhook data to the correct tenant record. A successful attack lets one merchant's webhook traffic be attributed to (and processed as belonging to) a different merchant, i.e., cross-tenant data/state confusion mediated entirely by this gem's `HmacValidator`/`Request`/`Registry` code path.

### Likelihood Explanation
Exploitability depends on whether an unprivileged internet user can reach the app's webhook HTTP endpoint directly (bypassing Shopify's own delivery infrastructure) and control the `shop-domain` header value on that request — which is generally possible for any application whose webhook endpoint is a normal public HTTP route, since HTTP headers are attacker-controlled unless the host framework independently restricts them. The gem itself provides no mechanism to prevent this because it never binds `shop`/`topic`/`webhook_id` into the HMAC.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the authenticated signable content, or otherwise cryptographically tie the header-derived `shop` to the verified request, e.g., by requiring callers to pass the expected shop and comparing it against a value that is itself covered by the HMAC (or by validating against Shopify's IP allowlist/mTLS at the transport layer, which is outside this gem's scope). At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are NOT covered by `HmacValidator.validate` and must not be trusted for tenant identification without additional verification, or rename/restructure `Registry.process` so it is explicit that only the body—not the shop attribution—is authenticated.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a forged POST directly to the app's public webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `H` against `HMAC(B, api_secret_key)` [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes `handler.handle(data: ...)` [4](#0-3) , causing the host app to apply the attacker's webhook payload under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
