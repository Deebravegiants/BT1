## Analysis: Webhook `shop`/`topic` headers not covered by HMAC (Cross-tenant/topic confusion)

The GearToken `signatory` bug class ("a value is used for authorization/attribution decisions without verifying it was actually produced/bound by the trusted signer") maps directly onto how this gem validates inbound Shopify webhooks.

### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` are not covered by the HMAC signature, allowing tenant/topic spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers when dispatching to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then immediately trusts these header-derived fields to route/attribute the webhook to a handler and to a specific shop: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body), never incorporating `shop`, `topic`, `webhook_id`, or `api_version`: [4](#0-3) 

The identity binding that should hold is: `shop attributed to webhook == shop that produced the HMAC-signed body`. Because the header values aren't part of the signed content, this binding is broken — HMAC validity proves only "some request with `api_secret_key` produced this body," not "this body belongs to this shop/topic."

### Impact Explanation
Any entity capable of obtaining one genuine webhook body+HMAC pair (e.g., a merchant who legitimately installs the app on their own store and receives/triggers a real webhook, which is not a privileged action) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop, and/or substituting the `x-shopify-topic` header for a different topic. `Registry.process` will accept it (HMAC over body still matches) and hand the forged `shop`/`topic` straight to the app's handler via `WebhookMetadata`: [5](#0-4) 

If the host application uses `WebhookMetadata#shop` to determine whose data to update/delete (a documented, expected use of this field), this enables cross-tenant data manipulation — an attacker's own webhook payload can be attributed to a victim shop. This satisfies the "Critical - cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is moderate-to-high in typical multi-tenant app deployments: obtaining a valid body+HMAC pair requires only owning/controlling one shop that has the app installed and triggering a real event (an unprivileged, self-service action), and the replay itself requires no knowledge of `api_secret_key`.

### Recommendation
Include the shop domain, topic, webhook id, and api version in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed body), so `HmacValidator.validate` fails if any of these header-derived attribution fields are altered after signing.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook event, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Send a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim.myshopify.com"` even though `victim` never sent this webhook, demonstrating the broken shop-to-signature binding.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
