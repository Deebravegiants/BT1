### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop` (a shop identifier taken from an HTTP header) to the app's handler as trusted tenant identity. The HMAC, however, is computed only over the raw request body — never over the shop-domain header — so the "shop that produced a validly-signed payload" and "the shop the library reports to the handler" are not the same authenticated value.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```
`shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header, while `to_signable_string` (the value that gets HMAC-verified) is only the raw body. [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely from that signable string against `Context.api_secret_key`; it never touches headers: [2](#0-1) 

`Registry.process` uses this to authenticate the whole request, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity dispatched to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The gem's own documentation confirms this HMAC check is presented as full request authentication ("This will verify the request did indeed come from Shopify") [4](#0-3) , and that `data.shop` is meant to be relied upon by the handler as "The shop domain of the webhook" [5](#0-4) .

**Identity binding broken (as equality):** `shop_bound_by_signature == shop_delivered_to_handler` does not hold. The signature only proves `HMAC(raw_body, api_secret_key)` is correct; it proves nothing about which shop's header accompanied that body. Since the `api_secret_key` for a given app is the same across every shop that installs it, any unprivileged user who installs the app on their own store legitimately receives a genuinely signed `(raw_body, hmac)` pair. They can then POST that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for any victim shop that also uses the same app. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the library dispatches attacker-chosen body content under a victim shop's identity to the host application's webhook handler, which — per the gem's documented contract — is expected to trust `data.shop` as the authenticated origin of the event. Depending on the handler's logic (e.g., updating per-shop records, honoring `shop/redact` or `customers/data_request` GDPR webhooks, syncing inventory/orders), this allows an attacker to inject or manipulate another merchant's data under the guise of a validated Shopify webhook — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be able to install/operate the same third-party app on a shop they control (an unprivileged capability available to anyone using the app) and be able to reach the app's public webhook HTTP endpoint, both of which are standard, expected exposure of any Shopify app integrating this gem per its documented usage.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the string that is HMAC-verified (mirroring how OAuth's `AuthQuery#to_signable_string` includes `shop` in the signed payload [6](#0-5) ), or otherwise cryptographically bind headers to the payload before trusting `request.shop` as tenant identity in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a shop they legitimately control) and triggers a webhook (e.g., `orders/create`), receiving a normal delivery with body `B` and a valid `x-shopify-hmac-sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `B` (the same `to_signable_string`) — the substituted shop header is never part of the signed value. [7](#0-6) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled content as though it originated from `victim-shop.myshopify.com`. [8](#0-7)
