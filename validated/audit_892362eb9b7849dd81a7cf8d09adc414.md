### Title
Excess native token sent to `EvmHost::dispatch`/`fundRequest` is not refunded to the caller and is permanently trapped in the host - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's bug class is: a contract that receives native token to cover a fee, calls a downstream mechanism with that `msg.value`, and fails to return the unused/excess portion back to the original depositor. The Hyperbridge EVM host (`EvmHost`) exhibits the same structural flaw in its native-token payment path for `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`.

### Finding Description
When an application dispatches a request and pays with native token, `EvmHost` swaps the entire `msg.value` for the exact `fee` amount via Uniswap V2's `swapETHForExactTokens`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
```

The identical pattern exists in `dispatch(DispatchGet)` and `fundRequest`: [2](#0-1) [3](#0-2) 

Uniswap V2's `swapETHForExactTokens` refunds any unspent ETH to `msg.sender` of that call — but the caller of the router *is `EvmHost` itself*, not the original transaction sender who supplied `msg.value` to `dispatch()`/`fundRequest()`. This is exactly the behavior the caller comment in `HyperbridgeLzEndpoint`/`UniV3UniswapV2Wrapper` and `UniV4UniswapV2Wrapper` explicitly guards against elsewhere in this same codebase — those wrapper contracts capture the router's refund and forward it back to `msg.sender`: [4](#0-3) 

and the `UniV4UniswapV2Wrapper` test even documents the correct behavior explicitly: [5](#0-4) 

By contrast, `EvmHost.dispatch`/`fundRequest` never captures or forwards this refund to the original caller — the swap router refunds the dust ETH straight into `EvmHost`'s own balance, where it has no `receive()`/withdrawal path visible to return it. Meanwhile, every other native-token-accepting entrypoint in this repo (`IntentGatewayV2.placeOrder`, `ExtrinsicIntents._fillCrossChain`) explicitly refunds unspent `msg.value` to the caller: [6](#0-5) [7](#0-6) 

This confirms the codebase's own convention is "always refund unspent native token to the caller," and `EvmHost`'s dispatch/fund paths violate that convention. Any unprivileged caller — including apps like `HyperbridgeLzEndpoint.send()` which forwards its entire `msg.value` straight into `IDispatcher(_host).dispatch{value: msg.value}(request)` without any subsequent refund logic of its own — sending more native token than exactly required for the fee swap loses the excess permanently. [8](#0-7) 

### Impact Explanation
Users/apps overpaying native token for relayer fees on `dispatch()`/`fundRequest()` permanently lose the excess amount, which is silently absorbed by `EvmHost` with no accounting or recovery mechanism found. Any downstream integrator that estimates gas conservatively (e.g. `HyperbridgeLzEndpoint.quote()` applies a deliberate 2x buffer "to absorb legacy per-byte fees," expecting the excess to be refunded) will systematically lose roughly half of every native-fee payment. This is a direct, repeatable loss of user/protocol funds — matching the "ETH-Transfer" bug class of the analog report, downgraded from High to Medium in the original judgment because losses are capped to the fee/gas overpayment rather than a full drain.

### Likelihood Explanation
High likelihood of occurrence in normal operation: any caller who does not compute the *exact* Uniswap quote (which is subject to slippage/price movement between quote-time and dispatch-time) and instead sends a buffer — as `HyperbridgeLzEndpoint.quote()` explicitly instructs integrators to do via its 2x markup — will trigger this loss on every single native-paid dispatch. This is not an edge case; it is the expected steady-state usage pattern for any app avoiding revert-on-insufficient-fee.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the actual amount spent by the swap and refund the remainder of `msg.value` to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder` and the `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper` contracts, e.g.:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    (bool ok,) = _msgSender().call{value: msg.value - amounts[0]}("");
    require(ok, "refund failed");
}
```

### Proof of Concept
1. Application `A` calls `EvmHost.dispatch(DispatchPost{fee: 1e18, ...})` with `msg.value = 2 ether` (deliberate buffer to survive quote slippage, as recommended by `HyperbridgeLzEndpoint.quote()`'s 2x markup comment).
2. `EvmHost.dispatch` calls `IUniswapV2Router02.swapETHForExactTokens{value: 2 ether}(1e18, path, address(this), ...)`.
3. The router spends only the ETH needed to obtain `1e18` fee tokens (say 0.5 ether) and refunds the remaining 1.5 ether — but to `msg.sender` of the swap call, which is `EvmHost`, not application `A`.
4. `EvmHost`'s native balance increases by 1.5 ether; `A` never receives it back, and no function exists to reclaim it on `A`'s behalf. [1](#0-0)
