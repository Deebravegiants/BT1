## Finding: Multisig Timelock-Bypass Threshold Can Be Silently Downgraded by a Lower-Quorum Owner-Management Transaction

### Title
Multisig `override_threshold` (timelock bypass quorum) auto-clamped by owner removal approved with only `num_signatures_required` votes - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` implements an on-chain multisig with an optional `MultisigAccountTimeLock` that lets owners require a mandatory delay before a transaction executes, unless a higher-quorum `override_threshold` of approvals is reached (a deliberately stronger bar than the everyday `num_signatures_required`). [1](#0-0) 

The problem: routine owner-list changes (`add_owners`, `remove_owners`, `swap_owners`, etc.), which are only gated by the ordinary `num_signatures_required` quorum, silently shrink `override_threshold` down to the new owner count whenever it would otherwise exceed it — with no requirement that the higher-quorum bar be re-approved by anyone. [2](#0-1) 

### Finding Description
`update_owner_schema` is the single internal function backing `add_owners`, `remove_owners`, `swap_owner(s)`, `add_owners_and_update_signatures_required`, and `swap_owners_and_update_signatures_required`. Every one of these is an `entry fun` that can only be invoked by the multisig account's own signer — i.e., once a proposal has collected `num_signatures_required` approvals (the *normal*, lower quorum), per the module's documented flow. [3](#0-2) 

Inside `update_owner_schema`, after the owner list is mutated, the code checks whether a `MultisigAccountTimeLock` exists and, if the configured `override_threshold` now exceeds the (possibly smaller) owner count, it clamps `override_threshold` down to `num_owners` and emits `TimelockUpdated`:
```
if (exists<MultisigAccountTimeLock>(multisig_address)) {
    let timelock = &mut MultisigAccountTimeLock[multisig_address];
    if (timelock.override_threshold.is_some() && timelock.override_threshold.borrow() > &num_owners) {
        timelock.override_threshold = option::some(num_owners);
        emit(TimelockUpdated { ... });
    };
    assert!(
        timelock.override_threshold.is_none() || timelock.override_threshold.borrow() > &multisig_account_ref_mut.num_signatures_required,
        error::invalid_state(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
    );
}
``` [2](#0-1) 

`override_threshold` is documented as "the number of approvals required to bypass the timelock and execute immediately" and must stay "greater than the number of signatures required normally." It is a deliberate, higher security bar meant to protect assets custodied by the multisig's resource account from fast, low-quorum execution. [1](#0-0) 

The bug: nothing requires that a *change* to `override_threshold` itself be approved by anything close to the original override quorum. Any owner-removal transaction, approved by only `num_signatures_required` votes, can shrink the owner set enough to force `override_threshold` down to the new (smaller) owner count — as long as the post-clamp value still satisfies `override_threshold > num_signatures_required`. This is a strictly weaker requirement than "must be re-approved by the original override quorum." A colluding subset of owners equal to `num_signatures_required` can therefore:
1. Propose and pass `remove_owners` to shrink the owner list until `override_threshold` clamps down to a value the same coalition can also satisfy (e.g., `num_owners = num_signatures_required + 1`).
2. Immediately propose a malicious transaction (e.g., draining APT/fungible-asset balances held by the multisig resource account) and gather approvals equal to the now-deflated `override_threshold`, bypassing the timelock delay that the account's owners originally configured specifically to prevent fast execution by anything less than a supermajority.

This is the same bug class as the referenced auction report: a security-critical economic/authorization parameter (there, the platform fee; here, the timelock-bypass quorum) can be altered mid-flight by an operation that itself required far less authority than what the parameter was meant to protect, defeating the purpose of setting it in the first place.

### Impact Explanation
The multisig account is a resource account that can directly custody APT and fungible assets (`coin` import, `SignerCapability`) and control code-object/upgrade authority for anything owned by the multisig. The `MultisigAccountTimeLock.override_threshold` exists precisely to prevent a minority/lower-quorum coalition from fast-tracking a fund-draining or authority-changing transaction. Silently downgrading this threshold via ordinary, lower-quorum owner-management operations lets that same lower-quorum coalition subsequently bypass the timelock and execute an unauthorized transaction (theft/drain of custodied assets, or transfer of upgrade/control authority) with fewer approvals than the multisig owners originally mandated. This is a custody-grade authority break tied to live, multisig-held value.

### Likelihood Explanation
Exploitation requires only that (a) the multisig has a timelock configured with `override_threshold` set higher than the current owner count would otherwise allow, and (b) an owner-removal/swap transaction reaches the normal `num_signatures_required` quorum — both are standard, expected multisig operations, not privileged/administrative edge cases. No external precondition beyond normal multisig usage is needed, making this a realistically likely misconfiguration path rather than a purely theoretical one.

### Recommendation
Do not silently auto-clamp `override_threshold` as a side effect of `update_owner_schema`. Instead:
- Abort the owner-removal/swap transaction if it would violate the timelock invariant (`override_threshold > num_signatures_required` and `override_threshold <= num_owners`), forcing owners to explicitly and separately update the timelock configuration through a dedicated, equally (or more) strongly gated call.
- Alternatively, require that any transaction which would alter `override_threshold` (directly or as a side effect) itself be approved by at least the *current* `override_threshold`, not just `num_signatures_required`.

### Proof of Concept
1. Create a multisig account with owners `{A, B, C, D, E}`, `num_signatures_required = 2`, and a `MultisigAccountTimeLock` with `override_threshold = 5` (i.e., only unanimous approval can bypass the delay).
2. `A` and `B` (2 of 5, meeting `num_signatures_required`) propose and execute `remove_owners([C, D])`, shrinking owners to `{A, B, E}`.
3. Inside `update_owner_schema`, since `override_threshold (5) > num_owners (3)`, it is silently clamped to `3`; the assert `3 > num_signatures_required (2)` passes, so the transaction succeeds.
4. `A` and `B` now propose a malicious transaction (e.g., transferring all APT/FA out of the multisig's resource account) and gather approval from `A`, `B`, and `E` (3 approvals) — now equal to the deflated `override_threshold`, letting them bypass the timelock delay entirely, despite the original configuration intending that only a full 5-of-5 could do so. [2](#0-1) 

**Caveat:** I was not able to view the full transaction-execution/validation logic (`can_be_executed`, `validate_multisig_transaction`, and the specific timelock-bypass check) in this pass due to tool-call limits, so I cannot 100% confirm the exact mechanics of how `override_threshold` is consumed at execution time beyond what the module's own comments and `update_owner_schema` describe. The core defect — that a security parameter meant to require a high quorum can be silently weakened by a much lower-quorum operation — is confirmed directly in the code shown above. Further verification of the execution-time check against `override_threshold` is recommended before treating this as fully proven end-to-end.

    /// `drop` is safe here because this resource holds only primitives (no capabilities, no
    /// event handles). It's used so that `remove_timelock` can `move_from` without destructuring.
    /// Note that because on-chain transactions cannot realistically be executed in less than a
    /// second, the resolution of `creation_time_secs` is at-second granularity — setting/removing
    /// a timelock within the same on-chain second as a pending transaction's creation is not a
    /// concern in practice.
    enum MultisigAccountTimeLock has key, drop {
        V1 {
            /// The time lock period in seconds after the creation of the multisig transaction.
            timelock_period: u64,
            /// The number of approvals required to bypass the timelock and execute immediately.
            /// Must be greater than the number of signatures required normally and less than or equal to the number of owners.
            override_threshold: Option<u64>,
        }
    }
