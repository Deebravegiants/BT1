### Title
Third-party dust deposits overwrite a victim’s cached liquidation parameters - ([File: contracts/controller/src/positions/supply.rs](contracts/controller/src/positions/supply.rs))

### Summary
`supply` permits a caller that is not the account owner or delegate to add funds only to a `HubAssetKey` that already exists in the target account’s supply map. [1](#0-0)  However, the merge path unconditionally refreshes the entire stored risk tuple for that existing position using `RiskRefreshScope::FullTuple`. [2](#0-1)  A third party can therefore spend the minimum nonzero-share deposit to rewrite another account’s cached LTV, liquidation threshold, liquidation bonus and liquidation-fee fields to the current listing configuration, bypassing the safety floor applied by the dedicated threshold-update path.

### Finding Description
`process_supply` authenticates only `caller`, then loads the requested account and calls `require_third_party_existing_supply`. [3](#0-2)  For an existing account and non-owner/non-delegate caller, that check requires every submitted `HubAssetKey` to already be present in `account.supply_positions`; it does not prevent writes to the existing position or its cached risk parameters. [4](#0-3) 

The deposit is then processed through `process_deposit`, which transfers the caller’s tokens to the pool and merges the pool mutation. [5](#0-4)  `merge_supply_leg` loads the victim’s existing position, calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)`, and then persists the updated scaled balance and position. [6](#0-5)  Consequently, a dust-sized third-party top-up acts as a write primitive against the victim’s cached liquidation configuration even though the caller cannot otherwise act on that account.

### Impact Explanation
After governance legitimately tightens a market’s risk configuration, an attacker can selectively apply the new liquidation threshold, bonus and fee parameters to a chosen victim without waiting for the victim or a keeper-gated refresh. If the victim is near the boundary, the restamp can reduce the cached health factor below one and make the account liquidatable; if it is already liquidatable, applying a higher liquidation bonus or fee can increase the attacker’s seizure proceeds. The cost is only the minimum deposit that produces nonzero supply shares, and that deposit is credited to the victim rather than consumed as a fee. [7](#0-6) 

This can cause theft of user collateral through liquidation using only the unprivileged `supply` and `liquidate` entrypoints.

### Likelihood Explanation
The exploit requires a governance listing update that worsens at least one cached liquidation parameter and a victim whose existing supply position can be topped up. Both conditions are realistic during routine risk tightening or liquidation-incentive changes. The attacker needs no victim authorization, leaked key, malicious token, oracle manipulation or privileged role; Bob’s own authorization is sufficient for `supply`, and liquidation is permissionless once the cached health factor is below one. [8](#0-7) [9](#0-8) 

### Recommendation
Do not let a third-party top-up restamp an existing position’s liquidation tuple. For callers that fail `is_owner_or_delegate`, merge only the scaled supply increase and preserve the stored `loan_to_value`, `liquidation_threshold`, `liquidation_bonus` and `liquidation_fees`. Alternatively, gate a full risk refresh behind owner/delegate authority or require the same post-refresh health-factor floor used by the maintenance path before committing the state. Add a regression test in which governance tightens the listing, a stranger supplies dust to a victim’s existing slot, and the stored tuple and liquidation eligibility remain unchanged.

### Proof of Concept
1. Alice owns account `A` with an existing supply position in `hub_usdc` and enough debt that lowering its liquidation threshold can move its health factor below one.
2. Governance executes a valid listing update that lowers `liquidation_threshold` and/or raises `liquidation_bonus` or `liquidation_fees` for `hub_usdc`.
3. Attacker Bob calls:
   `controller.supply(caller=Bob, account_id=A, spoke_id=A.spoke_id, assets=[(hub_usdc, minimum_nonzero_share_amount)])`.
4. The third-party check passes because `A.supply_positions` already contains `hub_usdc`. [9](#0-8) 
5. `merge_supply_leg` refreshes Alice’s existing position with `RiskRefreshScope::FullTuple`, replacing its cached liquidation parameters before `update_or_remove_supply_position` persists it. [10](#0-9) 
6. Alice’s health factor is now computed under the tightened cached parameters. If it is below one, Bob calls `liquidate` and seizes Alice’s collateral under the attacker-selected refreshed terms.

/// Supplies collateral, creating an account when `account_id` is zero.
/// Third parties may only add to existing supply positions. Returns the account id.
pub(crate) fn process_supply(
    env: &Env,
    caller: &Address,
    account_id: u64,
    spoke_id: u32,
    assets: &Vec<HubPayment>,
) -> u64 {
    validation::require_authorized_caller(env, caller);
    let aggregated = payments::aggregate_positive_payments(env, assets);
    let mut cache = Context::new(env);

    let (acct_id, mut account) = account::load_or_create_account(
        env,
        caller,
        account_id,
        spoke_id,
        PositionMode::Normal,
        account::AccountGuard::Supply,
        &mut cache,
    );

    require_third_party_existing_supply(env, account_id, acct_id, caller, &account, &aggregated);

    process_deposit(env, caller, &mut account, &aggregated, &mut cache);

/// Restricts third parties to existing supply positions. New accounts are
/// exempt because the caller becomes their owner.
fn require_third_party_existing_supply(
    env: &Env,
    account_id: u64,
    resolved_account_id: u64,
    caller: &Address,
    account: &Account,
    aggregated: &AggregatedPayments,
) {
    if account_id != 0
        && !account::is_owner_or_delegate(env, resolved_account_id, caller, &account.owner)
    {
        for (hub_asset, _) in aggregated.iter() {
            assert_with_error!(
                env,
                account.supply_positions.contains_key(hub_asset.clone()),
                GenericError::NotAuthorized
            );
        }
    }
}

/// Checks supply entry gates and credits measured pool receipts.
pub(crate) fn process_deposit(
    env: &Env,
    caller: &Address,
    account: &mut Account,
    aggregated: &AggregatedPayments,
    cache: &mut Context,
) {
    validate_position_entry_gates(
        env,
        account,
        aggregated,
        cache,
        AccountPositionType::Deposit,
    );
    let pool_addr = cache.cached_pool_address();
    let mut entries: Vec<PoolSupplyEntry> = Vec::new(env);
    for (hub_asset, amount_in) in aggregated.iter() {
        let asset_config: AssetConfig = cache.require_spoke_asset(account.spoke_id, &hub_asset);
        let received = payments::transfer_amount_measured(
            env,
            &hub_asset.asset,
            caller,
            &pool_addr,
            amount_in,
            GenericError::AmountMustBePositive,
        );
        let position = account.get_or_create_supply_position(&hub_asset, &asset_config);
        entries.push_back(PoolSupplyEntry {
            action: make_pool_action(&position, received, hub_asset.clone()),
        });
    }

    let results = pool_supply_call(env, &pool_addr, &entries);
    for_each_leg(env, &entries, &results, |entry, result| {
        merge_supply_leg(env, account, &entry.action, &result, cache);
    });

/// Merges a supply result, refreshing risk parameters and updating usage,
/// market index, and event state.
pub(crate) fn merge_supply_leg(
    env: &Env,
    account: &mut Account,
    action: &PoolAction,
    result: &PoolPositionMutation,
    cache: &mut Context,
) {
    let hub_asset = &action.hub_asset;
    let asset_config: AssetConfig = cache.require_spoke_asset(account.spoke_id, hub_asset);

    let mut position = account.get_or_create_supply_position(hub_asset, &asset_config);
    let old_scaled = position.scaled_amount;

    refresh_supply_risk_params(
        env,
        cache,
        account,
        hub_asset,
        &mut position,
        &asset_config,
        RiskRefreshScope::FullTuple,
    );

    let outcome = LegOutcome::from(result);
    position.scaled_amount = outcome.new_scaled;

    apply_leg_usage(
        env,
        cache,
        account.spoke_id,
        UsageSide::Supply,
        hub_asset,
        LegDirection::Entry {
            asset_decimals: result.asset_decimals,
        },
        old_scaled,
        &outcome,
    );

    cache.put_market_index(hub_asset, &outcome.market_index);
    cache.record_supply_position_update(
        events::PositionAction::Supply,
        hub_asset,
        outcome.market_index.supply_index,
        action.amount,
        &position,
    );

    update_or_remove_supply_position(account, hub_asset, &position);
