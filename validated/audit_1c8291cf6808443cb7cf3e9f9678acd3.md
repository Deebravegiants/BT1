### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then passes the unsigned `shop` value straight to the app's handler, so the identity binding "shop that produced the signed bytes" ≠ "shop the handler is told the webhook came from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` verify `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body) using `Context.api_secret_key` — the `shop` header plays no role in this computation: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` taken directly from the unsigned header, which is handed to the app's handler as the authoritative tenant identity: [4](#0-3) 

Because `hmac-sha256` only proves that the body bytes were produced by Shopify for *some* shop with knowledge of `api_secret_key`, but says nothing about which shop, an attacker who owns their own Shopify store can capture a legitimately-signed webhook delivered to their own app endpoint (a validly-signed body/HMAC pair for their own shop) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The signature remains valid (it never covered the header), so `Registry.process` accepts it and dispatches `data.shop == "victim-shop.myshopify.com"` to the handler, even though the signed body actually originated from the attacker's own shop.

Per the documented handler contract, `data.shop` is the trusted tenant identifier host apps use to route/act on data ("The shop domain of the webhook"), e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [5](#0-4) 

This breaks the identity binding: `shop authenticated by HMAC` should equal `shop attributed to the processed webhook`, but the gem lets the latter be attacker-controlled.

### Impact Explanation
This enables cross-tenant confusion: a malicious merchant/app installer can forge webhook deliveries that appear to originate from any other shop, causing the host application to create, update, or act on records under the wrong tenant using attacker-supplied (but validly-signed for a different shop) body content. This matches the Critical "cross-tenant access" impact category, since no access token or `api_secret_key` is required — only a legitimately-received webhook from the attacker's own store.

### Likelihood Explanation
Likelihood is high for any app that installs the gem's webhook processing as documented: any developer/merchant who can install the app on their own store automatically receives real, validly-signed webhooks and can trivially replay them with a modified shop-domain header to the same public endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or, at minimum, require and enforce that `Registry.process` cross-checks `request.shop` against an expected/allow-listed shop before invoking the handler. Since Shopify's own HMAC scheme only signs the body, the gem should document/require callers to independently verify the shop header corresponds to a known, installed shop before trusting `WebhookMetadata#shop`, or the library should expose a stronger verification API that ties the shop identity to the signed payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for topic `orders/create`.
2. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-for-body>`, and some JSON body.
3. Attacker captures this raw body + HMAC header, then replays it to the same endpoint, replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com` (any header, not just shop domain, since none but the body is signed).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because only `raw_body` is checked; `request.shop` now yields `"victim-shop.myshopify.com"`.
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, and performs tenant-scoped actions (e.g., `shop_domain: data.shop`) against the victim's tenant data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
