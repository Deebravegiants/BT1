### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body alone, then trusts `request.shop` (parsed from the `x-shopify-shop-domain` / `shopify-shop-domain` header) as the tenant identifier passed to the app's handler. The shop identity is never part of the signed bytes, so it is not cryptographically bound to the HMAC that authenticates the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using this signable string, and if it validates, unconditionally trusts `request.shop` when constructing the metadata handed to the app's webhook handler: [2](#0-1) 

The `shop` accessor is read directly from an HTTP header with no cross-check against the signed payload: [3](#0-2) 

This breaks the identity binding `shop_claimed_in_header == shop_that_produced_the_signed_bytes`. Because a public app's webhook HMAC is computed with the single app-wide `client_secret` (`Context.api_secret_key`) — the same secret used for every merchant/shop installation of the app — the signature is valid for any shop, not just the one that actually sent the body. Only the request `body` bytes are authenticated; the `shop-domain` header is not.

Concretely, any merchant/attacker who has legitimately installed the vulnerable app on their own store (an ordinary, unprivileged action requiring no special access) will receive genuine Shopify-generated webhook deliveries — bodies with a valid HMAC signed by the shared `client_secret`. Because that signature never incorporates the shop domain, the attacker can capture one such legitimately-signed `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's domain. `HmacValidator.validate` will still pass (it only checks body+secret), and `Registry.process` will hand the attacker-controlled body to the app's handler tagged as data belonging to the victim shop.

### Impact Explanation
This allows cross-tenant data injection/spoofing: an app built on this gem, following its documented API (`Registry.process`/`WebhookMetadata#shop`), will process attacker-supplied webhook content under a victim shop's tenant identity. Depending on how the host app uses `data.shop` (e.g., to look up the victim's session/access token and act on their store, or to write/merge data into the victim's tenant records), this can lead to cross-tenant access or corruption of another merchant's data — a Critical-class impact (cross-tenant access) per the boundary that the gem is expected to enforce via its own HMAC verification API.

### Likelihood Explanation
Moderate-to-high: the prerequisite (installing the app on one's own shop to obtain a legitimately-signed webhook body) is trivial for any unprivileged internet user for a public app, and no leaked credentials, TLS interception, or privileged access are required. The only work needed is replaying an HTTP POST with a modified header, which is well within reach of a normal user of the gem's documented webhook-processing surface.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the bytes that are HMAC-verified, or explicitly bind/validate `request.shop` against an independently trusted source (e.g., require the caller to supply the expected shop, or verify it against a previously known/authorized shop for that webhook subscription) before dispatching to the handler. At minimum, document and enforce that `WebhookMetadata#shop` must not be trusted as an authenticated tenant identifier unless corroborated elsewhere.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` (ordinary app install, no special privileges).
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(client_secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(client_secret, B)` from `to_signable_string` (body only) and it matches — validation passes. [4](#0-3) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_from_B, ...)`, causing the app to treat attacker-controlled content as authentic data for `victim.myshopify.com`. [2](#0-1)
