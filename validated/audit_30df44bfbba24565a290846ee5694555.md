### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value used downstream to identify *which tenant* the webhook belongs to is read from an unsigned HTTP header and is never included in the HMAC-covered data.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable payload as only the raw body: [1](#0-0) 

The `shop` accessor, however, is taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside that signed data: [2](#0-1) 

`Registry.process` validates authenticity using only `Utils::HmacValidator.validate(request)`, i.e. only `to_signable_string` (`@raw_body`) is checked against the HMAC, and then immediately trusts `request.shop` to build the metadata passed to the host application's handler: [3](#0-2) 

`HmacValidator.validate` confirms only that *some* valid `(body, hmac)` pair was produced with the app's `api_secret_key` — it says nothing about which shop that pair belongs to: [4](#0-3) 

Because `api_secret_key` is a single, per-app secret shared across every merchant that installs the app (not a per-shop secret), any merchant who has legitimately installed the app can capture a real, validly-signed `(raw_body, hmac)` pair delivered to their own webhook endpoint (e.g. by simply having their store trigger the relevant webhook topic). They can then replay that exact body+HMAC directly to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is genuinely valid for the shared secret), and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain:

The binding that should hold is:
`shop authenticated by HMAC == shop used to select/mutate tenant data`
but the actual code enforces only:
`body verified by HMAC ⊄ shop trusted for tenant identification`

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` to select which merchant's session/access token/data to read or write (the intended and documented use of webhook handlers) can be made to apply a spoofed webhook's payload to an arbitrary victim shop's tenant context. This is a cross-tenant access/data-integrity break driven entirely by a gap in this gem's authentication check, meeting the Critical bar ("cross-tenant access").

### Likelihood Explanation
Likelihood is high for any real-world integration: no special privilege beyond a normal, legitimate app install is required. Any of the app's own merchants can obtain a valid `(body, hmac)` pair from their own store's webhook delivery and replay it with a modified shop header directly against the app's public webhook endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable data, or otherwise cryptographically bind the shop identity to the signed payload (e.g., require the shop to also be present in the signed body/claims), so that `HmacValidator.validate` cannot succeed unless the shop header matches what was actually signed by Shopify for that specific delivery.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the vulnerable app and legitimately receives a webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` using the app's shared `api_secret_key`).
2. Attacker crafts a raw POST to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   shopify-topic: orders/create
   shopify-hmac-sha256: H
   shopify-shop-domain: victim-shop.myshopify.com
   shopify-webhook-id: <any>

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because `H` is a valid HMAC of `B` under the shared secret [5](#0-4) .
4. `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked, delivering attacker-controlled data tagged with the victim's shop identity [6](#0-5) .
