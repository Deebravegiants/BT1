Analog found. Raydium's LP withdraw path exhibits the same "dust rounding blocks full redemption" pattern seen in the Surge report, just applied to LP-token/vault-share accounting instead of debt-share accounting.

### Title
User with a small residual LP balance can be permanently unable to redeem it due to floor-division dust in `process_withdraw` - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` computes the coin/pc amounts owed for a given LP-token amount using floor division (`InvariantPool::exchange_pool_to_token`), then unconditionally rejects the whole instruction if either resulting amount is zero. This means any LP balance small enough that its floor-divided share of the vault rounds down to `0` coin or `0` pc can never be withdrawn — not even partially — permanently trapping that value in the pool for the holder, exactly the "dust remainder blocks full removal" pattern described in the report.

### Finding Description
In `process_withdraw`, the payout is computed via `InvariantPool` with `RoundDirection::Floor`: [1](#0-0) 

Right after logging, the code hard-fails if either computed amount is `0`, with no fallback path (no burn-only option, no "sweep leftover" logic): [2](#0-1) 

The floor-division helper is defined here, showing the rounding-down behavior that produces the dust: [3](#0-2) 

Because a user's LP balance can end up as an arbitrarily small residual (e.g., after a large partial withdrawal, after swaps skew the coin/pc ratio, or simply because their proportional share of `total_coin_without_take_pnl` / `total_pc_without_take_pnl` relative to `amm.lp_amount` is sub-unit for one side), `coin_amount` or `pc_amount` can floor to `0` for that entire remaining LP balance. Since `Withdraw` is the only instruction that redeems LP tokens for underlying assets, and it always reverts when either leg rounds to zero, there is no way to ever redeem that dust LP balance — it is neither large enough to withdraw successfully, nor is there a partial/burn-without-payout path.

This mirrors the reported Surge issue: a value derived from a floor-division/share calculation (there: debt shares vs. collateral; here: LP shares vs. vault balances) can leave a "dust" remainder that the same function's own zero-checks/`InvalidInput` guard makes permanently unresolvable through the intended user flow.

### Impact Explanation
Any liquidity provider whose LP balance decays to a dust amount (through normal partial withdrawals or ratio drift from swaps/fees) can lose access to that value permanently — it is stuck as an un-redeemable LP-token balance backed by real vault assets that can never be extracted by that user through `Withdraw`. This is a freezing-of-user-funds condition, matching the Medium-severity classification of the analog report (permanent, protocol-enforced lock of a portion of a legitimate user's funds, reachable with attacker/user-chosen withdraw amounts in an ordinary transaction).

### Likelihood Explanation
Reachable by any unprivileged LP holder simply by calling `Withdraw` (`AmmInstruction::Withdraw` / `process_withdraw`) with an amount that leaves them a small residual LP balance, or by anyone who ends up holding a small enough absolute LP amount relative to the pool's `total_coin_without_take_pnl`/`total_pc_without_take_pnl`. No privileged role, special build, or off-chain component is required — only ordinary deposit/withdraw/swap activity that shifts the coin:pc:lp ratios enough that a small LP balance's floor-divided share of one side of the pool is `< 1` token unit.

### Recommendation
Allow a minimum "sweep" path: if `coin_amount == 0` or `pc_amount == 0` but `withdraw.amount > 0` and it equals the caller's entire LP balance, either (a) round up (ceiling) instead of floor for the side that would otherwise be zero when the user is closing out their full position, or (b) permit burning the residual LP tokens with the honestly-owed (possibly zero) proportional payout rather than reverting outright, so dust LP balances are not permanently unredeemable.

### Proof of Concept
1. Pool has `amm.lp_amount = L`, `total_coin_without_take_pnl = C`, `total_pc_without_take_pnl = P`, with `C` and `L` such that some small residual `lp_dust` satisfies `lp_dust * C / L < 1` (floor to 0) — e.g., `C` small relative to `L` for the coin side (feasible because independent partial withdrawals and swaps continuously change `C`, `P`, and `L`, and a user's own final small remainder can land in this range).
2. Any prior `Withdraw` call leaves the user holding `lp_dust` LP tokens (e.g., they withdraw `withdraw.amount = balance - lp_dust`, a value they freely choose).
3. The user calls `Withdraw` again with `amount = lp_dust`.
4. `process_withdraw` computes `coin_amount = invariant.exchange_pool_to_token(C, Floor)` which floors to `0` given the above ratio (`program/src/processor.rs` lines 1756-1758).
5. The check at `program/src/processor.rs` lines 1775-1777 triggers `AmmError::InvalidInput`, and the instruction always reverts for any `amount <= lp_dust` for this user — the LP tokens (and the assets they represent) can never be redeemed.

    /// Exchange rate
    pub fn exchange_pool_to_token(
        &self,
        token_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
