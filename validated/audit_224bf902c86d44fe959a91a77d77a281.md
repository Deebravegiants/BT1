### Title
Beneficiary-controlled ETH push in `withdraw()` allows griefing of escrow settlement via message-delivery revert - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` pushes native ETH to an attacker-chosen `beneficiary` address using a raw `.call{value: amount}("")` and reverts the entire call if the transfer fails [1](#0-0) . This function is reached from `onAccept`, the unauthenticated ISMP delivery entrypoint invoked by any relayer that submits a valid Hyperbridge proof for a `RedeemEscrow`/`RefundEscrow` message [2](#0-1) . Because the `beneficiary` field of the `WithdrawalRequest` is taken directly from `order.user` (attacker-supplied when they placed/cancelled the order), an attacker can set it to a contract with a `receive()` that unconditionally reverts (or burns gas), permanently blocking delivery of that specific settlement message — the same bug class as the referenced Notional report where a user-controlled ETH recipient can revert a permissionless settlement call.

### Finding Description
`withdraw()` is invoked for both `RedeemEscrow` (solver claiming filled-order proceeds) and `RefundEscrow` (order cancellation) request kinds inside `onAccept`, which is restricted only to `onlyHost` — i.e., it is triggered by any relayer submitting a correctly proven cross-chain message, not by the beneficiary or order owner themselves [3](#0-2) . Inside `withdraw()`, for every native-token (`token == address(0)`) leg, the code does:

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [1](#0-0) 

`beneficiary` is decoded from `body.beneficiary`, which for `RefundEscrow` is set to `order.user` at cancellation time (attacker-controlled, since the attacker is the order creator) [4](#0-3) . Because the low-level call reverts the whole `onAccept` transaction on failure, and `_filled[body.commitment]` and `_orders[...]` state changes are unwound with it, the message can never be successfully delivered by any relayer, since the same `beneficiary` value is embedded immutably in the request body/commitment that was already hashed and dispatched from the source chain.

The equivalent `IntentsBase._sendValue`/`_withdraw` path used by the non-Tron `IntentGatewayV2`/`ExtrinsicIntents` contracts has the same raw-ETH-push behavior for the `beneficiary` [5](#0-4) , though I was not able to fully inspect `_sendValue`'s implementation (whether it wraps to WETH on failure) within the available context, so it's unclear whether the primary EVM package has the identical fix applied that the Tron variant lacks.

### Impact Explanation
An attacker who places a same-chain-source/cross-chain-destination order and sets themselves (`order.user`) to a hostile contract that always reverts on `receive()` can permanently prevent the `RefundEscrow`/`RedeemEscrow` message for their own commitment from ever being delivered. This:
- Permanently locks the escrowed input tokens for that commitment on the source chain (the funds sit unrecoverable in the gateway since `withdraw()` can never succeed), a permanent freezing-of-funds outcome.
- Wastes relayer gas on every delivery attempt (a relayer must submit a full proof, which is non-trivial gas, only to have `onAccept` revert), degrading relayer economics and creating a denial-of-service vector against a specific commitment.
- Because the same commitment/message is fixed once dispatched from the source (its hash includes `beneficiary`), no relayer or admin can route around the malicious beneficiary — this matches the "route unable to deliver messages" criterion.

This is a self-inflicted freeze for the attacker's own funds in the simplest form, but it also permanently poisons the specific request commitment so it can never be settled, and burns relayer fees/gas repeatedly if relayers keep retrying, satisfying the "permanent freezing of funds" / "unable to deliver messages" bar for a Medium/High-severity analog.

### Likelihood Explanation
Trivial to trigger: any account can deploy a `receive() external payable { revert(); }` contract, place/cancel a cross-chain order naming that contract as `order.user`/beneficiary, and the resulting `WithdrawalRequest.beneficiary` will always cause `withdraw()`'s ETH branch to revert on delivery. No special privileges, front-running, or race conditions are required — it is fully within the attacker's control at order-placement time.

### Recommendation
Do not let a failed native-ETH push abort the entire settlement. Mirror the pattern already used elsewhere in the codebase for `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which falls back to delivering wrapped WETH via ERC-20 transfer if the native push fails [6](#0-5) : in `IntentGatewayV2.withdraw()` (and the analogous `IntentsBase._withdraw`/`_sendValue`), attempt the raw ETH transfer, and on failure wrap the amount into WETH and deliver it as an ERC-20 `safeTransfer` to the beneficiary instead of reverting the whole message. This guarantees the escrow can always be settled/refunded regardless of the beneficiary's ability to receive native ETH.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary` with `receive() external payable { revert(); }`.
2. Attacker places a cross-chain order on the source chain with `order.user = address(MaliciousBeneficiary)` and a native-ETH output/input leg, per the order-placement flow described in `docs/content/developers/evm/intent-gateway/placing-orders.mdx`.
3. Attacker (as order owner) calls `cancelOrder`/triggers `_cancelFromDest`-equivalent path so a `RefundEscrow` `WithdrawalRequest{ beneficiary: order.user, tokens: order.inputs }` is dispatched to the source-chain gateway, per [4](#0-3) .
4. Any relayer submits the proof; `HandlerV2` verifies it and calls `IntentGatewayV2.onAccept`, which dispatches to `withdraw(body, isRefund=true)` [2](#0-1) .
5. `withdraw()` attempts `beneficiary.call{value: amount}("")`; `MaliciousBeneficiary.receive()` reverts, `sent == false`, and `withdraw()` reverts with `InsufficientNativeToken()` [1](#0-0) , rolling back the entire `onAccept` call.
6. Because the commitment and beneficiary are fixed in the already-dispatched message, every subsequent relayer delivery attempt fails identically — the escrow is permanently stuck and undeliverable.
