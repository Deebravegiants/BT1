### Title
Webhook `shop` domain is not covered by HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes/verifies the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; the `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [2](#0-1) 
and `shop` is read from a separate, unsigned header: [3](#0-2) 

`HmacValidator.validate` only checks that the HMAC of `to_signable_string` (i.e., the raw body) matches, using the app's shared `api_secret_key`: [4](#0-3) 

`Registry.process` treats a passing HMAC check as proof the whole request (including `shop`) "did indeed come from Shopify" and passes `request.shop` straight into `WebhookMetadata`, which the docs tell app developers to trust for tenant identification (e.g., `shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body ‖ shop)`, but the gem instead only enforces `hmac == HMAC(secret, raw_body)`. Because the same `api_secret_key` is used for every shop that installs the app, any body+HMAC pair legitimately produced by Shopify for one tenant (shop A) remains valid when replayed with the `shop-domain` header rewritten to a different tenant (shop B) — the signature check still passes, since it never inspected the header. An unprivileged attacker who controls (or has access to) delivery of a webhook to their own shop (e.g., by installing the target app on their own store, or intercepting/replaying a webhook they legitimately receive) can capture a valid `(raw_body, hmac)` pair and re-POST it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value, causing the app to process the payload under a victim shop's identity.

### Impact Explanation
This breaks the shop/tenant identity binding at the core of webhook trust and enables cross-tenant confusion: an app relying on `WebhookMetadata#shop` (as the gem's own documentation instructs) to select the tenant record/session for which to act (e.g., "cancel this order for shop X", "update inventory for shop X") can be tricked into applying attacker-controlled webhook payloads to a different, victim shop, since the gem does not bind the shop to the cryptographic signature it verifies. This matches the Critical/High class of cross-tenant access via an identity check that verifies one artifact (body bytes) while trusting an unrelated, unverified field (shop) for authorization decisions.

### Likelihood Explanation
Any entity able to install the vulnerable app on their own store (a basic unprivileged action any merchant/developer can perform) can obtain a validly-signed `(raw_body, hmac)` webhook pair for a topic of their choosing, then replay it against the app's public webhook endpoint with a forged `shop-domain` header pointing at any other install. No secrets, tokens, or elevated access are required — only network access to the app's webhook route and a self-service app install.

### Recommendation
Include the `shop` domain (and ideally other header fields the application depends on for authorization, such as `topic`) in the signed/verified material, or independently verify that the `shop` header value corresponds to a shop actually known to have an active installation/session before trusting it in `WebhookMetadata`. At minimum, update `Webhooks::Request#to_signable_string`/`HmacValidator` so the HMAC check is bound to the shop the payload claims to originate from, and document to integrators that `data.shop` must be cross-checked against the app's own installation records rather than trusted outright.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`, registers a webhook (e.g., `orders/create`), and triggers an order creation, causing Shopify to POST a legitimately-signed webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, plus `raw_body`.
2. Attacker captures this `(raw_body, hmac)` pair.
3. Attacker resends the identical `raw_body` and `hmac` to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new` accepts the forged headers (only checks presence, not shop/HMAC linkage): [7](#0-6) 
5. `HmacValidator.validate` recomputes HMAC over `raw_body` only and it matches, so `Registry.process` proceeds and dispatches `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)` to the app's handler, which acts on `victim.myshopify.com` using attacker-supplied data.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
