### Title
Webhook `shop-domain` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop` is read directly from the unauthenticated `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then hands the header-derived `shop` value straight to the app's handler as trusted webhook metadata.

### Finding Description
The identity binding that should hold is:
`HMAC_valid(secret, body) == true` should imply `(topic, shop, body)` were all authored by Shopify for that specific tenant.

In practice only `body` is covered by the signature: [1](#0-0) 

`Registry.process` accepts the request purely on that body-only HMAC check and then forwards the unauthenticated `shop` header value to the registered handler: [2](#0-1) 

`HmacValidator.validate` simply recomputes the HMAC over whatever `to_signable_string` returns and compares it — it has no knowledge of, or binding to, the `shop-domain` header: [3](#0-2) 

Because the app's `client_secret` (and thus the HMAC) is the same across every shop that has the app installed, any shop that has legitimately installed the app can capture one of its own genuine webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different, victim shop's domain. `Registry.process` will still report `Utils::HmacValidator.validate(request)` as `true` (the body and HMAC are untouched and correctly signed with the shared secret), and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

The gem's own documentation presents `data.shop` to app authors as reliable identity information for the webhook, with no caveat that it is unauthenticated: [4](#0-3) 

This is exactly the class of bug flagged in the reference report: a value that is *acted upon* (voting power tied to `totalContributions`) is inconsistent with the value that was actually *verified* (contribution amount after fees). Here, the value acted upon (`shop`, used to attribute/act on the event) is disjoint from what the cryptographic check actually verifies (only `body`).

### Impact Explanation
Any unprivileged internet user who can install the app on a shop they control (which for most public/free apps requires no privilege beyond having a Shopify account) can cause the app's webhook processing pipeline to attribute a validly-signed payload to an arbitrary victim shop domain of their choosing. Applications that key shop-scoped side effects (access-token lookups, data writes, entitlement checks) off `WebhookMetadata#shop` as delivered by this gem can be tricked into acting against another tenant's identity — a cross-tenant confusion enabled entirely by this gem's trust model, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled shop (ordinary, unprivileged action for public apps), (2) capturing one legitimate webhook delivery (headers + body are visible to the receiving server/attacker since it's their own installation), and (3) resending the identical body/HMAC pair to the app's webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, tokens, or any Shopify-side credential is needed beyond what a normal app installation already grants.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually authenticated before trusting it, e.g.:
- Require the host app to independently confirm that the resolved `shop` in `WebhookMetadata` corresponds to an actually installed/known shop for this app (cross-check against stored sessions) before use, and document this requirement prominently, or
- Extend `Request#to_signable_string` / `HmacValidator` usage so that verification incorporates the shop domain the caller intends to act on (e.g., compare the header-derived shop against a shop resolved independently from stored session state) rather than trusting the header value implicitly once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify sends a genuine webhook: body `B`, headers including `X-Shopify-Hmac-Sha256: valid_for(B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures this request (it's sent to their own server).
3. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `to_signable_string` is unchanged (`B`), so `Utils::HmacValidator.validate(request)` in `Registry.process` returns `true`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — data the app believes came from, and pertains to, `victim-shop.myshopify.com`, though it never sent any such webhook.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          received_signature = verifiable_query.hmac

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
