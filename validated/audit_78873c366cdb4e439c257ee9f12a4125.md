## Title
Attacker-controlled `Call[]` payloads routed through the shared `CallDispatcher` singleton can plant unlimited ERC20 approvals to itself, permanently draining any token balance that later transits the dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes an attacker- or user-supplied `Call[]` array against arbitrary targets with no whitelist, exactly mirroring the H-1 root cause ("unsafe call...allowing the contract to call the token contracts directly"). Unlike the JOJO helper contracts, the immediate caller here (`IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken*`) is trusted, but the *contents* of the calldata it forwards (`order.predispatch.call`, `order.output.call`, cross-chain `message.data`) are fully controlled by an unprivileged order-placer or solver. Because `CallDispatcher` is one shared, address-stable contract reused across every order and every app, a malicious `Call` that sets `token.approve(attacker, type(uint256).max)` leaves a standing allowance on the dispatcher that outlives the single transaction and lets the attacker drain any token balance any other legitimate order later routes through the same dispatcher.

### Finding Description
`CallDispatcher.dispatch()` only checks that the target has code, then blindly executes each `Call{to, value, data}`: [1](#0-0) 

The calldata forwarded to `dispatch()` originates from unprivileged inputs:
- `order.predispatch.call` — set by the user placing the order.
- `order.output.call` — set by the beneficiary/solver via `PaymentInfo.call`.
- `message.data` on `HyperFungibleToken`/`WrappedHyperFungibleToken` — set by the sender on the source chain.

`IntentGatewayV2` transfers order assets to the dispatcher and then blindly forwards this attacker-controlled payload: [2](#0-1) 

Likewise for post-fill calldata: [3](#0-2) 

The dispatcher address (`_params.dispatcher`) is a single, persistent, well-known contract shared by every order and every app instance that uses it. The documentation itself acknowledges that `Call[]` entries are expected to `approve()` spenders *from* the dispatcher, and explicitly warns that unlimited allowances are dangerous *because the dispatcher holds tokens temporarily*: [4](#0-3) 

Nothing in `CallDispatcher.dispatch()` restricts which addresses can be `approve`d, nor resets/revokes approvals after use. A test in the repo already demonstrates the pattern of granting `type(uint256).max` approval from the dispatcher to a router as part of ordinary calldata: [5](#0-4) 

If an attacker (an ordinary order-placer or a solver providing `output.call`) substitutes their own address for the router in such a `Call`, e.g. `Call({to: USDC, value: 0, data: approve(attacker, type(uint256).max)})`, this executes successfully (dispatch has no allowlist) and leaves `USDC.allowance(dispatcher, attacker) = type(uint256).max` permanently, since nothing ever revokes it.

Because every subsequent order that uses USDC as a predispatch/output asset (from any other, unrelated user) necessarily moves USDC through this same `dispatcher` address before the internal sweep call runs, the attacker can call `USDC.transferFrom(dispatcher, attacker, amount)` directly on the ERC20 contract at any point the dispatcher holds a nonzero USDC balance (front-running the sweep, or exploiting fee-on-transfer/dust remnants), stealing tokens that belong to other users' in-flight orders.

### Impact Explanation
This is a direct theft-of-funds vector against any user or solver whose order routes the approved token through the shared `CallDispatcher`. Since the dispatcher is reused across `IntentGatewayV2`, `IntentsBase`-derived apps, and the `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution path, a single malicious order or malicious bridge message poisons the shared contract for all future users of that token, matching the High severity bar from the original report (all funds transiting the contract can be stolen).

### Likelihood Explanation
Any unprivileged actor can place an order (or act as a solver supplying `output.call`, or send a bridged message with `data`) — no special privilege is required to reach `CallDispatcher.dispatch()` with attacker-chosen calldata. The only requirement is that some future, unrelated flow uses the same dispatcher and the same token, which is the normal, expected operating mode of the contract (it is explicitly a shared singleton). This makes exploitation straightforward and realistic, not merely theoretical.

### Recommendation
Enforce a whitelist of allowed `to` targets (and/or disallow `approve`/`increaseAllowance`-style selectors) in `CallDispatcher.dispatch()`, mirroring the fix applied to the original JOJO report. Alternatively, deploy an ephemeral (per-call or per-order) dispatcher instance instead of one persistent shared contract, and/or have the dispatcher revoke any approvals it granted immediately after each `dispatch()` batch completes, so no standing allowance survives past the single transaction.

### Proof of Concept
1. Attacker places an order (or supplies solver `output.call`) whose `predispatch.call`/`output.call` decodes to `Call[]` containing `Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})`.
2. `IntentGatewayV2`/`IntentsBase` forwards this to `ICallDispatcher(dispatcher).dispatch(...)`; it executes successfully since `dispatch()` has no target/selector restriction (`CallDispatcher.sol` L44-62).
3. `USDC.allowance(dispatcher, attacker)` is now `type(uint256).max` and persists indefinitely.
4. Any later, unrelated order that uses USDC as a predispatch asset or output asset transfers USDC into `dispatcher` before the internal sweep (`IntentGatewayV2.sol` L230-260, `IntentsBase.sol` L498-533).
5. Attacker calls `USDC.transferFrom(dispatcher, attacker, amount)` directly, draining the victim's in-transit funds using the standing approval from step 3.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
