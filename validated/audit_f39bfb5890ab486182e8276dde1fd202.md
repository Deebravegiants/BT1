## Title
Webhook shop-domain identity spoofing — HMAC signs only the raw body, letting an attacker replay a validly-signed payload under a forged tenant identity - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

## Summary

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Registry.process` accepts the request once `Utils::HmacValidator.validate(request)` succeeds against that body-only signable string [2](#0-1) . The `shop` identity used downstream, however, is read straight from the `shop-domain`/`x-shopify-shop-domain` header, which is never part of the HMAC-signed material [3](#0-2) . After a successful HMAC check, `Registry.process` builds `WebhookMetadata` directly from this unauthenticated header and dispatches it to the app's handler as the tenant identity for the event [4](#0-3) .

`Context.api_secret_key`, the HMAC key, is a single value shared by the app across *all* installed shops [5](#0-4)  — it is not shop-specific. This breaks the intended binding: `shop header == tenant that the HMAC-signed bytes belong to`. Concretely: bytes verified (body only) ≠ bytes acted on for tenant routing (body + unsigned shop header).

An attacker who owns/controls their own shop installation of the app can trigger a legitimate webhook delivery with attacker-chosen body content (e.g. via `products/create`, `orders/create`, etc. with attacker-controlled resource fields), capturing a validly-signed `(body, hmac)` pair from Shopify. Because the shop identity is not covered by the signature, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks body+secret), and `Registry.process` will dispatch the handler with `shop: <victim-domain>`, causing the host application to believe attacker-controlled data originated from the victim tenant.

## Impact Explanation
This is a cross-tenant identity-binding break: the same shared app secret validates a payload whose recorded tenant (`shop`) is fully attacker-controlled and unauthenticated. Any host application that uses `WebhookMetadata#shop` to route storage, trigger tenant-scoped side effects, or otherwise trust the identity of the acting shop (which is the gem's documented usage pattern, as shown in `test/webhooks/registry_test.rb`) can be made to process forged data attributed to a shop the attacker does not control — a cross-tenant data-integrity/confusion vector.

## Likelihood Explanation
The prerequisite is only that the attacker control one legitimate installation of the target app (any shop owner can install a public app or already has an install), which is an "unprivileged internet user" relative to any *other* merchant's tenant. Capturing a valid `(body, hmac)` for attacker-chosen webhook content and replaying it with a different `shop-domain` header requires no secrets, tokens, or privileged access to the victim.

## Recommendation
Bind the shop identity into the HMAC-signed material, or otherwise cryptographically tie the `shop-domain` header to the signature — e.g., have `VerifiableQuery`/`to_signable_string` for webhooks include the shop domain (and ideally topic/webhook-id) in the signed input, matching how Shopify's own webhook signature is verified per-topic, or require a separate mechanism to associate each installed shop with its own registered webhook endpoint/secret so cross-shop replays fail validation.

## Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g. `products/create`) with an attacker-chosen JSON body; capture the raw `x-shopify-hmac-sha256` header and raw body from the legitimate delivery.
3. Replay a POST to the app's webhook endpoint using the identical body and HMAC header, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `body` + shared `api_secret_key`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `shop: "victim.myshopify.com"`, even though the payload never touched the victim shop.
