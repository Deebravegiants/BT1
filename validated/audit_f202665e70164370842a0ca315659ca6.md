### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then trusts the `shop` value taken from an HTTP header that is never included in that signature. Any party capable of obtaining one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store and receiving a legitimate webhook, since the app's `client_secret` is shared across every shop that installs the app) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, and the gem will accept it as an authentic webhook for the spoofed shop.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` compute/verify the signature using only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no role in the signable string at all: [3](#0-2) 

`Registry.process` validates the HMAC and then, without any further binding check, forwards `request.shop` straight to the handler as the tenant identifier: [4](#0-3) 

The binding that is broken is:
`shop authenticated (bytes actually covered by HMAC = raw_body only) ≠ shop used as tenant/session key (header value delivered in WebhookMetadata#shop)`

Because Shopify apps use a single `client_secret` for all shops that install the app, an attacker who installs the app on their own store legitimately receives webhooks (body + valid HMAC) signed with that same secret. Since the shop header is outside the signed payload, the attacker can resend the identical body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop's domain. The gem's `HmacValidator.validate` call succeeds because it only checks the byte-for-byte body against the secret, not the shop-body binding, and `Registry.process` dispatches to the handler with `shop` set to whatever the attacker chose.

### Impact Explanation
Host applications built on this gem rely on `WebhookMetadata#shop` as the trusted tenant key to look up the merchant session, update per-shop data, or take shop-scoped actions — the gem's documented webhook handling flow provides no other verified tenant boundary. An attacker can therefore inject attacker-controlled webhook payloads that are processed under a victim shop's identity, resulting in cross-tenant data confusion/access within the app (e.g., data intended for one merchant being written into or triggering actions for another merchant's record). This satisfies the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Likelihood is high: any user can install the app for free on their own development/test store (a normal, unprivileged flow for any Shopify app), capture one legitimate webhook delivery for a topic they control, and then replay it against the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only participation as a normal merchant installing the app, which is the baseline threat model for this class of finding.

### Recommendation
Bind the shop identity into the authenticated payload before trusting it: include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, or cross-check `request.shop` against an independently verified value (e.g., the shop associated with the session/store record the app expects for that webhook subscription) before invoking the handler in `Registry.process`. At minimum, document that consumers must not treat `WebhookMetadata#shop` as authenticated without additional verification, and update `HmacValidator`/`Request#to_signable_string` so the shop domain participates in the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because it is computed with the app's shared `client_secret`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - body `B` (unchanged)
3. `Webhooks::Request.new` parses these headers/body, `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `B`: [5](#0-4) 
4. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, even though the payload actually originated from and reflects the attacker's own shop, achieving cross-tenant webhook injection.

**Uncertainty note:** I could not fully trace how downstream host applications typically consume `WebhookMetadata#shop` (that logic lives outside this gem), so the concrete downstream damage depends on the integrating app's use of that field; the vulnerability described here is confined to the trust gap within this gem's own webhook verification code path.
