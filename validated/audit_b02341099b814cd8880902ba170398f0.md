### Title
`TokenFaucet.drip` per-address daily cap can be bypassed via disposable contracts, permitting unlimited unbacked minting of the fee token - (File: `evm/src/utils/TokenFaucet.sol`)

### Summary
`TokenFaucet` is granted `MINTER_ROLE` on the `HyperFungibleTokenImpl` fee token deployed on every non-mainnet Hyperbridge chain, and its only guard against unlimited minting is a `mapping(address => uint256) consumers` cooldown keyed on `msg.sender`. Exactly like the referenced `MeritDutchAuction.CAP_PER_ADDRESS` bug, this per-address gate is trivially defeated by calling `drip()` from freshly deployed helper contracts (or any number of distinct addresses) within a single transaction/script, since nothing ties the cap to a real, resource-constrained identity.

### Finding Description
`TokenFaucet.drip` is unauthenticated and open to any caller: [1](#0-0) 

It mints `1000 * 1e18` of the target `HyperFungibleTokenImpl` token to `msg.sender`, gated only by `consumers[msg.sender]` being older than 1 day. `HyperFungibleTokenImpl.mint` itself has no supply cap and is fully permissioned to whoever holds `MINTER_ROLE`: [2](#0-1) 

The faucet is deployed and granted `MINTER_ROLE` on the token in the standard, non-mainnet deployment path: [3](#0-2) 

Because the cooldown is keyed purely on `msg.sender` and not on any Sybil-resistant identity (`tx.origin`, a stake, a KYC gate, etc.), an attacker can deploy an arbitrary number of throwaway contracts (or fund an arbitrary number of EOAs) that each call `drip(token)` once. Each new contract address has a `consumers[...]` value of `0`, so the `delay < 1 days` check always passes for a fresh address — the exact bypass technique used against `MeritDutchAuction.CAP_PER_ADDRESS` in the referenced report, where `Buyer1`/`Buyer2` helper contracts each minted up to the "per-address" cap and then consolidated to a single beneficiary. Here the same technique lets one entity mint unbounded amounts of the fee token to a single address in one transaction, with no aggregation limit at all.

### Impact Explanation
The fee token minted by `TokenFaucet` (`USD.h`/equivalent) is the token used to pay dispatch/relayer fees across the Hyperbridge ISMP protocol on every affected chain, and it is also used in integration/e2e flows (e.g., Simplex solver funding, bandwidth purchases priced in the fee token) as documented in the testnet faucet flow: [4](#0-3) 

Since `mint` has no total-supply ceiling and the per-address cooldown is the only bound, an attacker can mint an effectively unlimited amount of this fee token by fanning out `drip()` calls across disposable contract addresses in one transaction, producing unbacked inflation of the protocol's fee token supply on that chain. This directly satisfies the "unbacked mint" impact criterion: an attacker gains free, uncapped fee-token balance they can use to pay for message dispatch, drain liquidity pools pairing this token, or otherwise distort any economic mechanism (fee markets, Simplex pricing, bandwidth purchases) that treats the fee token as scarce/valuable.

### Likelihood Explanation
The attack requires no privileges: `drip()` is a public, unauthenticated function, and deploying helper contracts that each call it once is a standard, cheap, single-transaction technique (identical in spirit to the referenced Sherlock finding). The only friction is gas cost per helper contract, which does not meaningfully rate-limit an attacker willing to mint a large supply. This is realistically exploitable on every chain where this faucet/token pattern is deployed (documented for BSC Testnet, Polygon Amoy, Sepolia, etc., per `docs/content/developers/evm/contract-addresses/testnet.mdx` and the faucet deployment in `DeployIsmp.s.sol`).

### Recommendation
- Do not rely solely on `msg.sender` for the rate limit; either restrict `drip()` to EOAs (`require(msg.sender == tx.origin)`, understanding this blocks legitimate smart-account use) or require a Sybil-resistant precondition (e.g., a minimum native-token balance/age, a signed allowlist, or a captcha/off-chain gate before minting).
- Add a global (not just per-address) rate limit or hard supply cap to the faucet/token pair so that even with many addresses, total mintable amount per epoch is bounded.
- Consider moving the cooldown enforcement to `tx.origin` combined with a per-block or per-transaction cap on total `drip()` calls, and/or requiring the caller to burn/lock a small amount of gas token or previously-acquired token as a Sybil cost.

### Proof of Concept
Analogous to the reference report's `Buyer1`/`Buyer2` pattern:
```solidity
contract DripHelper {
    TokenFaucet public immutable faucet;
    address public immutable token;
    address public immutable beneficiary;

    constructor(address _faucet, address _token, address _beneficiary) {
        faucet = TokenFaucet(_faucet);
        token = _token;
        beneficiary = _beneficiary;
        faucet.drip(token);
        // forward minted balance to beneficiary
        IERC20(token).transfer(beneficiary, IERC20(token).balanceOf(address(this)));
    }
}

contract SybilFaucetDrain {
    function drainMany(address faucet, address token, uint256 n) external {
        for (uint256 i = 0; i < n; i++) {
            new DripHelper(faucet, token, msg.sender);
        }
    }
}
```
Calling `drainMany(faucet, usdH, N)` in one transaction deploys `N` fresh `DripHelper` contracts, each with `consumers[address(this)] == 0`, each successfully calling `drip()` and minting `1000e18` tokens to `msg.sender` — bypassing the "once per address per day" limit entirely and scaling only with gas/block-gas-limit, not with any protocol-enforced cap.

```text
contract TokenFaucet {
    mapping(address => uint256) private consumers;

    // @dev Will only drip tokens, once per day
    function drip(address token) public {
        uint256 lastDrip = consumers[msg.sender];
        uint256 delay = block.timestamp - lastDrip;

        if (delay < 1 days) {
            revert("Can only request tokens once daily");
        }

        consumers[msg.sender] = block.timestamp;
        HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18);
    }
```
