### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Request#shop` is read from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header [1](#0-0) . `Webhooks::Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then hands `request.shop` straight to the app's handler as the tenant identifier [2](#0-1) . This is the same bug class as the external report: an identifier that the code *acts on* (`shop`) is not part of what is cryptographically *verified* (the HMAC covers `@raw_body` only).

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac` [3](#0-2) . For webhooks, `to_signable_string` is defined as just `@raw_body` [4](#0-3) , so the signature only proves "this body was produced by an app-secret holder (Shopify) for *some* shop," not "this body belongs to shop X." The value of `shop` is taken verbatim from a header that is never mixed into the signed content [5](#0-4) .

`Registry.process` passes this unauthenticated `shop` value directly into `WebhookMetadata`, which is the only tenant-binding information delivered to the host application's handler [2](#0-1) .

Binding that should hold but doesn't:
`shop_bound_by_HMAC == shop_used_by_handler`
Before the attack: both sides refer to the attacker's own shop (the legitimate webhook they received). After the attack: the HMAC-covered side (body) still corresponds to the attacker's shop, but `request.shop` (header, unauthenticated) has been rewritten to a victim shop domain — the equality is broken, yet `Utils::HmacValidator.validate` still returns `true` because it never inspects `shop`.

### Impact Explanation
An unprivileged internet user who is merely a merchant that installs the target app on their own store (no special access, no leaked secrets) can:
1. Trigger any webhook topic the app subscribes to on their own store (e.g., `orders/create`) and capture the raw POST body + its valid `x-shopify-hmac-sha256` value (both are delivered to the app's public webhook endpoint, which the attacker can front with their own reverse proxy/logger since it's their own installation).
2. Replay the identical body and HMAC to the app's webhook endpoint, only changing the `x-shopify-shop-domain` header to a victim shop's domain.
3. `Utils::HmacValidator.validate` still succeeds because it only checks the body's HMAC, not the shop header [6](#0-5) .
4. The host application's registered handler receives `WebhookMetadata` claiming the payload is for the victim's shop and shop-scoped data [7](#0-6) .

This crosses a tenant boundary: data or events belonging to the attacker's shop are attributed to, and processed under, a different merchant's tenant context — a cross-tenant access condition per the impact criteria (Critical).

### Likelihood Explanation
Likely reachable by any app merchant/installer without credentials beyond normal use of the app (installing it on their own store to obtain one legitimately-signed webhook). No `api_secret_key`, access token, or TLS interception is required — only the ability to observe traffic to an endpoint the attacker controls (their own store's webhook delivery target is the app's public endpoint, reachable from the internet by definition of webhooks).

### Recommendation
Bind the tenant identity into what is cryptographically verified, or add an independent authorization check before trusting `request.shop`:
- Verify that the `shop-domain` header corresponds to a shop the app has recorded as legitimately installed (e.g., cross-check against stored sessions/access tokens) before invoking the handler, rather than trusting the header at face value.
- Alternatively, since Shopify's HMAC over the raw body is shared across all shops the app is installed on, document and enforce in `Webhooks::Registry.process` / `WebhookMetadata` that `shop` must be validated by the host application against a known/installed shop list, and reject processing for shops the app cannot corroborate independently (e.g., via `webhook_id` uniqueness checks against the Admin API), rather than presenting `request.shop` as a trusted, HMAC-covered field.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app.
# Attacker triggers e.g. orders/create on their own shop and captures:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
)

# Attacker replays the exact same body+hmac but spoofs the shop header:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac,          # still valid, HMAC only covers raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # spoofed, not covered by HMAC
  "x-shopify-webhook-id"   => "any-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# -> Utils::HmacValidator.validate(request) returns true (body-only check)
# -> handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed_body, ...)
