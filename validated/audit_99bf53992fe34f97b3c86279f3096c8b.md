### Title
Webhook shop-tenant confusion via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body against the app's `client_secret`. The `shop` attribute that the gem hands to the developer's handler as the tenant identifier is read straight from an HTTP header and is never included in the signed material, so it can be swapped for any value without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identifier directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

The HMAC that authenticates the request is computed only over `to_signable_string`, which returns the raw body and nothing else: [1](#0-0) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` object handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC using `OpenSSL.secure_compare` [4](#0-3)  — the `shop` header plays no role in this computation at all.

The equality the gem's own security boundary should enforce is:
`shop authenticated by HMAC == shop the handler acts on`

but the actual behavior is:
`shop authenticated by HMAC (none) != shop the handler acts on (request.shop, attacker-controlled header)`

Since `client_secret` is fixed per app (not per shop), any legitimate merchant of the same app can capture one authentic webhook delivery (body + valid `hmac-sha256` header) for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will dispatch to the handler with `data.shop` set to the attacker-chosen domain. The docs explicitly tell integrators to use `data.shop` as the shop-scoping key for follow-up work (`perform_later(topic:, shop_domain: data.shop, ...)`), so this directly produces cross-tenant data association in the host app's records, all through a mechanism entirely inside this gem's own verification code.

### Impact Explanation
This breaks the tenant-isolation boundary that the gem's webhook HMAC check is supposed to provide. A merchant who legitimately receives webhooks for their own shop (an "unprivileged" actor relative to other tenants of the same app) can cause the app to attribute arbitrary webhook payloads to a shop domain of their choosing, resulting in cross-tenant data confusion/injection in any app that follows the gem's documented `data.shop` usage. This matches the Critical "cross-tenant access" impact category since it crosses the tenant boundary that the gem is meant to enforce.

### Likelihood Explanation
Any customer/merchant who has installed the app and can observe webhook traffic to their own endpoint (e.g., via a proxy/logging capture) has everything needed: a valid `(raw_body, hmac-sha256)` pair, obtainable without any special privilege beyond normal app installation. Forging the `shop-domain` header requires only a raw HTTP request to the app's public webhook endpoint — no access to `api_secret_key`, tokens, or TLS interception is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified against Shopify, or require the caller to cross-check `request.shop` against an out-of-band expected value (e.g., a shop registered for that specific webhook subscription/topic pairing) before trusting it, rather than exposing an unauthenticated `shop` accessor that flows directly into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw request body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify to the app's webhook endpoint.
2. Attacker sends a new POST to the same endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `hmac` returns the decoded `H` and `shop` returns `"victim-shop.myshopify.com"` [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to record/act on attacker-controlled data under the victim shop's identity.
