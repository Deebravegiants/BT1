### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are all read from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies the HMAC over the body, so it never binds these headers to the signature. This breaks the identity binding `HMAC-verified bytes == shop-attributed bytes`: an attacker who legitimately receives one valid webhook (with a valid HMAC over its body) for their own shop can replay the identical body while substituting an arbitrary `x-shopify-shop-domain` header, and the library will accept it and hand the (unrelated) body off to the app's handler tagged with the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived purely from headers: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop` (a header-derived, unsigned value) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across every install of an app, the *shape* of a valid signed payload is not shop-specific — only the body content is bound to the signature, not the header that names which shop it belongs to. Any party who has legitimately received one valid signed webhook (e.g., by installing the app on their own store) can capture the raw body and its valid HMAC, then resend that exact `(body, hmac)` pair to the app's webhook endpoint with a different `shop-domain` header value. `HmacValidator.validate` will still pass because it only checks the body against the HMAC, and the library will label the delivered data with whatever `shop` the attacker put in the header.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in scope: the equality that should hold is `hmac_signed_bytes == (body, shop)`, but the actual implementation only enforces `hmac_signed_bytes == body`, leaving `shop` completely unauthenticated.

### Impact Explanation
This crosses a tenant boundary: an application that uses `request.shop` from `ShopifyAPI::Webhooks::Registry.process` (a documented, intended API of this gem) to select which merchant's records to update, would process attacker-supplied webhook data under a victim shop's identity — a cross-tenant access/data-injection primitive, which is classified as Critical (cross-tenant access) per the impact rubric. The severity depends on what the app does with `data.shop`, but the gem itself provides no assurance that `shop` is bound to the signed payload, when a reasonable consumer would assume the HMAC check covers the full identifying triple (topic/shop/body).

### Likelihood Explanation
Exploitation requires only: (1) the attacker to be able to install (or otherwise legitimately trigger) the target app on any shop they control to obtain one valid signed webhook, and (2) the ability to POST an HTTP request with custom headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — this is reachable by any unprivileged internet user who can install the app on a shop they control (a normal, permitted action), making likelihood high in any deployment relying on `request.shop`/`data.shop` for tenant isolation.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable material verified by the HMAC, or otherwise cryptographically bind them to the body before trusting `request.shop`/`data.shop`. At minimum, `Utils::HmacValidator.validate` should be changed so `to_signable_string` incorporates the shop domain (and topic), not just the raw body, so that tampering with those headers invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, with body `B` and a valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `api_secret_key`).
2. Attacker captures `(B, H)` from the request sent to their own endpoint (or a logging proxy they control).
3. Attacker crafts a new HTTP POST to the app's real webhook endpoint with:
   - Body: the exact same `B`
   - Header `x-shopify-hmac-sha256`: the exact same `H`
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (any shop that has the app installed)
   - Header `x-shopify-topic`: unchanged (`orders/create`)
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is `B`; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and matches `H`, so `Registry.process` proceeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — the attacker's order data is now processed as if it belonged to `victim-shop.myshopify.com`.
