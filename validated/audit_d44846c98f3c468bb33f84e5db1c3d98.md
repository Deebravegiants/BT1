I found a concrete match. The webhook signature verification in this gem covers only the raw JSON body, but the `shop` (and `topic`/`webhook_id`) values used to route and process the webhook are taken from unauthenticated HTTP headers.This confirms the root cause: `Utils::VerifiableQuery` is a generic interface with `hmac` and `to_signable_string`, and `Webhooks::Request#to_signable_string` (returning only `@raw_body`) is the sole implementation used by `HmacValidator.validate`/`Registry.process`. None of the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of the signed material.

### Title
Webhook HMAC only signs the request body, letting an attacker rebind a validly-signed webhook payload to any victim shop - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the `X-Shopify-Hmac-SHA256` signature exclusively against that string. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated headers and are never included in the signed bytes. Any body+HMAC pair that was legitimately produced by Shopify for one shop (e.g., the attacker's own shop, which is a genuine merchant install of the app) can be replayed verbatim to the app's webhook endpoint with a different `shop-domain` header, and `Registry.process` will still accept it as valid.

### Finding Description
The library's webhook verification binds the HMAC to the request body only: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, and `webhook_id` are pulled from headers that are not part of that signed string: [2](#0-1) 

`Registry.process` verifies the HMAC and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler, without any additional check that the `shop-domain` header is bound to the signed body: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

Contrast this with the OAuth flow, where `AuthQuery#to_signable_string` deliberately folds `shop` into the signed string so the shop identity is cryptographically bound to the HMAC: [4](#0-3) 

The webhook path breaks the exact same binding pattern that the referenced report's `belowMaintenanceThreshold` bug illustrates: an equality/inequality (here, "HMAC valid ⟺ this exact shop sent this body") that is supposed to hold is not actually enforced. The equality that should hold is:
`HMAC_valid(body) AND shop-domain header == shop that Shopify actually generated this HMAC for`
but the code only checks the first half, so:
`HMAC_valid(body) ⇏ shop-domain header is authentic`

### Impact Explanation
An unprivileged internet user who is a genuine merchant with the app installed on their own shop (call it `attacker.myshopify.com`) legitimately receives real webhooks from Shopify signed with the app's real `api_secret_key`. Because the signature covers only the body, the attacker can capture any `(raw_body, X-Shopify-Hmac-SHA256)` pair from their own shop and resend it to the app's public webhook endpoint with `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) rewritten to a victim shop, e.g. `victim.myshopify.com`. `HmacValidator.validate` still returns `true` because it never looks at the shop header, and `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` and the attacker's chosen body content. Any app whose webhook handler uses `data.shop` to decide which tenant's records to create/update/delete (the documented and expected usage pattern, e.g. mandatory `customers/redact`, `shop/redact`, `orders/create`, etc.) will perform that action against the wrong tenant using attacker-supplied body content — a cross-tenant integrity/confidentiality breach performed with valid Shopify-issued cryptographic material and no credential of the victim's needed.

### Likelihood Explanation
Any app builder using this gem's webhook `Registry` gets this behavior by default; nothing in the public API surface lets them include shop identity in the HMAC check. The attacker only needs one installed shop of their own (any developer/partner store) to obtain a valid signed webhook body/HMAC pair for the exact topic they want to spoof, then a single HTTP replay with a modified header. No secrets, tokens, or elevated privileges of the victim are required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity into the signed material verified for webhooks, or explicitly documented/enforced constraint that the verified `shop-domain` header must match a shop the app expects to receive webhooks for. Concretely, change `Webhooks::Request#to_signable_string` (or `HmacValidator`) so verification fails unless the `shop-domain` header is cryptographically tied to the payload — e.g., have `HmacValidator.validate` also assert that the header-derived `shop` corresponds to the actual signed payload before `Registry.process` invokes the handler, mirroring the approach used in `Auth::Oauth::AuthQuery#to_signable_string`, which folds `shop` into the signed string.

### Proof of Concept
1. App has webhook registered for topic `orders/create` and a handler that trusts `data.shop`.
2. Attacker owns/installs the app on `attacker.myshopify.com`. Shopify sends a real webhook:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: attacker crafts/controls order content on their own shop before the webhook fires.
3. Attacker captures the raw body and the valid HMAC value.
4. Attacker POSTs the same raw body and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb:13-22`) validates successfully because it only recomputes HMAC over `request.to_signable_string` (`@raw_body`), which is unchanged.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body, causing the app to act on `victim`'s tenant data using forged content.
