### Title
Incorrect decimal-scaling conversion in `convert_to_erc20` enables unbacked minting across the HFT bridge - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers use `u8::saturating_sub` to compute a scaling exponent between the local asset's decimals and the destination chain's registered ERC20 decimals. `saturating_sub` silently clamps to `0` whenever the local asset has *more* decimals than the destination's ERC20 token, turning what should be a scale-down division into a no-op. This is exactly the "incorrect data conversion" bug class from the report (JSON→YAML mis-conversion enabling unintended trust): here a numeric unit conversion silently degenerates into an identity transform whenever the subtraction direction is reversed, and the un-scaled raw value is then dispatched cross-chain and minted as-is on the destination.

### Finding Description
`convert_to_erc20` in [1](#0-0)  computes:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

`erc_decimals.saturating_sub(local_decimals)` is only correct when `erc_decimals >= local_decimals` (scale up). When the local asset's decimals exceed the destination chain's registered ERC20 decimals (`local_decimals > erc_decimals` — an entirely ordinary configuration, e.g. a locally-registered 18-decimal asset bridging to a 6-decimal USDC-style ERC20 on the destination), the subtraction saturates to `0`, so the multiplier becomes `10^0 = 1`. The function returns `value` completely unscaled instead of dividing by `10^(local_decimals - erc_decimals)`.

This function is invoked directly from the unprivileged, user-callable `send` extrinsic: [2](#0-1) 

```rust
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
let token_message = Message {
    from: sender.to_vec().into(),
    to: params.recipient.to_vec().into(),
    amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()),
    data: params.call_data.unwrap_or_default().into(),
};
```

The mis-scaled `amount` is placed directly into the ISMP `Message.amount` field dispatched to the destination chain. On the receiving `HyperFungibleToken.sol` / `WrappedHyperFungibleToken.sol` contract, `onAccept` performs **no decimal conversion at all** and mints the raw value verbatim: [3](#0-2) 

So any raw-unit inflation introduced on the Substrate side is minted 1:1 on the EVM side.

The mirrored helper `convert_to_balance`, used in `on_accept`/`on_timeout`, has the same flaw in the opposite direction (dividing by `10^erc_decimals.saturating_sub(local_decimals)`), which under-mints (loses value) instead of over-minting when `local_decimals > erc_decimals`: [4](#0-3) [5](#0-4) 

### Impact Explanation
Any unprivileged user calling `send()` on an asset whose registered local decimals exceed the destination chain's registered `erc_decimals` (`ChainConfig.decimals`, set at token registration and entirely plausible for standard token pairs such as an 18-decimal local asset bridged to a 6-decimal stablecoin representation) causes the dispatched cross-chain `Message.amount` to be `10^(local_decimals - erc_decimals)` times larger than intended. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints or unlocks that inflated amount to the beneficiary with no additional checks, producing an unbacked mint — the attacker escrows/burns a small real amount on the source chain and receives a vastly larger amount on the destination, directly draining the destination's backing liquidity (for the "Wrapped" lock/unlock variant) or arbitrarily inflating token supply (for the mint/burn variant). This matches the "unbacked mint" / concrete theft criteria required for validity.

### Likelihood Explanation
This is not an edge case requiring attacker-crafted malformed input — it triggers deterministically for any token/chain pair where `local_decimals > erc_decimals`, a very common real-world configuration (e.g., bridging an 18-decimal governance/native asset to a 6-decimal USDC-style ERC20 peer). Once such a pair is registered (a routine administrative action, not a "malicious admin" scenario — the bug is in the arithmetic itself, not in trusting a bad actor), every ordinary `send()` call by any user is affected and profitable to exploit.

### Recommendation
Replace the `saturating_sub`-based single-direction scaling with an explicit bidirectional conversion that branches on which decimal count is larger and applies multiplication or division accordingly (using `checked_pow`/`checked_mul`/`checked_div` to avoid silent saturation), e.g.:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Apply the symmetric fix to `convert_to_balance`, and add regression tests covering both `local_decimals > erc_decimals` and `erc_decimals > local_decimals` configurations.

### Proof of Concept
1. Register a local asset with `local_decimals = 18` (e.g. via `register_token`), and configure a destination chain's `ChainConfig.decimals = 6` (representing a 6-decimal ERC20 peer, e.g. USDC-style) via `Precisions`/`ChainConfig`.
2. A user calls `HyperFungibleToken::send` with `amount = 1_000_000_000_000_000_000` (1.0 token at 18 decimals), escrowing/burning exactly 1 token locally.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1e18` unscaled instead of the correct `1e18 / 10^12 = 1_000_000` (1.0 token at 6 decimals).
4. The dispatched `Message.amount` field carries `1_000_000_000_000_000_000`.
5. On the destination `HyperFungibleToken.sol`, `onAccept` executes `_mint(beneficiary, message.amount)` — minting `1e18` raw units, which at 6-decimal precision equals `1,000,000,000,000` tokens (1 trillion), a 10^12x over-mint relative to the 1 token that was actually escrowed on the source chain.
