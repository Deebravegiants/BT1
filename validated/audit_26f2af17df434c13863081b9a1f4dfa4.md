### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies is computed only over the raw request body. The `shop` field is never bound to the signature, so any unauthenticated caller who can obtain one valid `(raw_body, hmac)` pair for the app's client secret can replay it to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the request still validates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is taken straight from an attacker-controllable header and is never part of that signable string: [2](#0-1) 

`Registry.process` validates the request using only this body-bound HMAC and then dispatches the handler using the *unverified* `request.shop`: [3](#0-2) 

`Utils::HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac` header — it has no notion of `shop` at all: [4](#0-3) 

The identity binding that should hold is:
`HMAC_sha256(client_secret, raw_body) == received_hmac` **and** `shop == the tenant that this body actually belongs to`

But the code only enforces the first equality. Because `client_secret` is a single per-app secret shared across every shop that installs the app, any merchant who has legitimately installed the app (i.e., an unprivileged party with respect to *other* tenants of the same app) can capture a valid `(raw_body, hmac)` pair from a real webhook Shopify sent to their own store, then POST that same body/hmac to the app's public webhook route while forging the `shopify-shop-domain` header to name a victim shop. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` hands the forged `shop` straight to the app's handler via `WebhookMetadata`.

The library's own documentation reinforces the false assumption that `process` fully authenticates the request ("This will verify the request did indeed come from Shopify"), so integrators reasonably trust `data.shop` as an authenticated tenant identifier.

### Impact Explanation
This is a cross-tenant identity-binding break: a party who is unprivileged relative to other tenants can make the host application process webhook data under a victim shop's identity while only possessing valid credentials for their own shop's webhook traffic (via the shared app secret). Downstream host applications built per the gem's documented pattern (`data.shop`) will store/act on data keyed to the wrong tenant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation does not require the app's `client_secret`, an access token, or TLS interception — the attacker only needs to be an app-installing merchant capable of triggering at least one webhook delivery for their own store (trivial, e.g. via `app/uninstalled`, or a resource whose JSON body content they can fully control/predict) and the ability to POST directly to the app's public webhook endpoint with a crafted `shopify-shop-domain` header, which requires no special access.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or require the host application to cross-check `request.shop` against an independently known/authorized shop before trusting it. At minimum, `Utils::HmacValidator`/`Webhooks::Registry.process` should fail closed if the `shop` header cannot be tied to the signature, rather than passing an unauthenticated `shop` value into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `app/uninstalled`) to the app's public endpoint, capturing the raw body and the `x-shopify-hmac-sha256` header value.
2. Attacker sends a forged HTTP POST directly to the same app endpoint with:
   - the identical `raw_body` and `hmac` header captured in step 1,
   - `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` → `Utils::HmacValidator.validate(request)` succeeds (body/hmac match).
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes the payload as if it belonged to `victim-shop.myshopify.com`, even though Shopify never sent this data for that shop.
