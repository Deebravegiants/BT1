### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) header values are trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the tenant-identifying `shop-domain` header (along with `topic`, `api-version`, `webhook-id`) is read directly from unauthenticated HTTP headers and passed downstream as the merchant identity for webhook processing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled straight from HTTP headers with no cryptographic binding to that signature: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts any request whose body/HMAC pair validates, then forwards `request.shop` — taken from the unauthenticated header — as the tenant identity to the app's `WebhookHandler`: [4](#0-3) 

This breaks the intended identity binding: `shop authenticated (bound to the signed bytes) == shop acted on (used to select/attribute tenant data)`. Here, the left side of that equality is empty — nothing about `shop` (or `topic`/`webhook_id`) is bound to the HMAC — while the right side is exactly the value handed to the host application's handler as the source-of-truth tenant identifier.

### Impact Explanation
Anyone who can produce one valid `(body, HMAC)` pair for the app's webhook endpoint — e.g. the operator of their own shop installed on the same app, who legitimately receives real webhooks with a correctly computed HMAC for their own shop's payloads — can replay that exact body/HMAC pair while substituting the `shop-domain` (and/or `topic`, `webhook-id`) header to point at a different merchant. `HmacValidator.validate` will still succeed because it never inspects those headers, and `Registry.process` will hand the spoofed `shop` value to the app's handler as if the event genuinely belonged to that other tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the target merchant's session/data to act upon), this is a cross-tenant data confusion vector: an attacker-controlled body gets attributed to, and processed against, a victim shop.

### Likelihood Explanation
Exploitation requires the attacker to already be able to generate at least one valid HMAC over content they choose — achievable by any merchant who has the app installed on their own shop and can trigger/replay a webhook body-and-signature pair they legitimately received, then resend it with a modified `shop-domain` (or `topic`) header value. No possession of the app's `client_secret` is required beyond what a normal, low-privilege merchant already receives via legitimate webhook deliveries. The request path (`Registry.process` → `HmacValidator.validate` → handler dispatch) is squarely in-scope, non-test library code.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers into the signed content used for HMAC verification, or otherwise cryptographically tie them to the payload (e.g., include them in `to_signable_string`, or require the host app to cross-check `shop` against a known/expected value before trusting it), so that the verified HMAC actually authenticates the tenant-identifying metadata, not just the raw body bytes.

### Proof of Concept
1. App operator/attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook for topic `X` with body `B`; Shopify computes `hmac = HMAC-SHA256(secret, B)` and sends headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: hmac`.
2. Attacker replays the exact same `B` and `hmac` to the app's webhook endpoint but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` — unaffected by the header change — and passes.
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked, causing the app to process attacker-controlled body content as if it originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
