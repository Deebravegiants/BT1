Webhook shop-domain trusted for tenant routing without HMAC coverage - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw HTTP body against the app's `client_secret`, then forwards the unauthenticated `X-Shopify-Shop-Domain` header value to the host app's handler as the tenant identifier, with no binding between the two.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the HMAC solely against that signable string via `Utils::HmacValidator.validate(request)` [2](#0-1) . The `shop` value is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2)  and is never part of the HMAC-covered bytes. After HMAC validation succeeds, `Registry.process` immediately hands this unauthenticated `request.shop` to the developer's handler as the tenant key: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) . The gem's own documentation reinforces that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` simply as "The shop domain of the webhook," giving no indication to integrators that this field is unauthenticated and must be independently cross-checked against the shop that actually owns the installation before it is used for tenant-scoped lookups.

Because the HMAC secret (`api_secret_key`) is a single value shared by the app across every merchant that installs it, any unprivileged internet user can install the app on their own (attacker-controlled) store, receive genuinely Shopify-signed webhook deliveries for that store, and then replay the exact same raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. Since only the body is covered by the signature, this forged request passes `HmacValidator.validate` unchanged, and the host app's handler will process data under the victim's tenant identity.

### Impact Explanation
This breaks the identity binding `shop authenticated by the gem == shop used as the tenant/session key by the host application`. An attacker-installed instance of the app can inject data attributed to an arbitrary victim shop domain into any tenant-keyed processing path (queues, DB writes, webhook idempotency keys) that trusts `data.shop`, since the gem hands this value to the handler as if it had been authenticated together with the payload. This is a cross-tenant confusion vector reachable by any user capable of installing the app on their own store, without needing the app's `client_secret`, an access token, or any privileged access.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action for any public Shopify app) and that they can predict or reuse a raw body value shared across shops (e.g., topics whose body content is static, empty, or attacker-influenced, such as `shop/redact`, or any topic where the body is not shop-specific). This is a moderate-likelihood scenario limited to apps that use `request.shop` for tenant-critical decisions without independent verification.

### Recommendation
Do not treat `request.shop` as authenticated. Either (a) include the `shop-domain` header bytes in the HMAC-signable string so header tampering invalidates the signature, or (b) explicitly document and enforce in `Registry.process`/`WebhookMetadata` that the shop domain must be cross-checked by the host application against the shop that registered the specific `webhook_id`/topic before use, and surface this as a required validation step rather than an implicit assumption.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. App registers a webhook (e.g., `shop/redact`, whose body content is fixed and attacker-observable) for the attacker's shop.
3. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint with `X-Shopify-Shop-Domain: attacker.myshopify.com` and body `B`.
4. Attacker captures this exact request, then re-sends the same raw body `B` and its valid `X-Shopify-Hmac-Sha256` value to the same endpoint, replacing the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` [2](#0-1) , which only recomputes the HMAC over `@raw_body` [1](#0-0)  — validation succeeds despite the spoofed shop header.
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [5](#0-4) , causing the host app to act on behalf of the victim tenant using attacker-supplied data.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
