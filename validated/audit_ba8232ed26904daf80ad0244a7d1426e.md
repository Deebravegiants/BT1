### Title
Sustained accrual overflows `scaled_to_original` before the index cap engages, permanently freezing all market operations — (File: contracts/pool/src/cache/scale.rs)

### Summary
CVE-2023-37765 is a crash-class bug: reachable code dereferences/overflows and the process dies. In XOXNO Lending the analogous shape is a panic reachable by any unprivileged caller that bricks a market forever. RAY-scaled borrow indexes grow with compounding interest, but `borrowed_scaled * borrow_index` in `scaled_to_original` hits the `i128` ceiling and panics with `MathOverflow` **before** the stored index reaches its `MAX_BORROW_INDEX_RAY` clamp. Because every pool verb accrues first, the panic wedges the entire market: no supply, withdraw, repay, borrow, or liquidation ever succeeds again.

### Finding Description
Every controller verb (`supply`/`withdraw`/`borrow`/`repay`/`liquidate`/etc.) loads a `Cache` that runs `global_sync`, which chunks elapsed time and applies `accrue_step` to grow `borrow_index`/`supply_index` [1](#0-0) . Utilization — recomputed on essentially every op — unscales book totals via `scaled_to_original(self.borrowed, self.borrow_index)` [2](#0-1) , which bottoms out in `mul_div_*` primitives that panic with `GenericError::MathOverflow` when `scaled * index` exceeds `i128` [3](#0-2) . The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the ordering bug directly: on a large 18-decimal market at ~98% utilization on a steep rate curve, `try_update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — i.e., the protective index cap never engages because the *product* overflows first — and subsequent `withdraw` and `repay` calls fail identically since accrual precedes them [4](#0-3) . The test itself notes the documented bound in `docs/reference/formulas.md` is wrong.

### Impact Explanation
Permanent freezing of funds. Once `borrowed_scaled * borrow_index` crosses the `i128` boundary, every entrypoint that touches the market panics during accrual before any state transition or guard can run. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and `recapitalize`/`clean_bad_debt` accrue through the same path, so there is no in-protocol recovery — all user funds in that market book are locked indefinitely.

### Likelihood Explanation
No privileged action is required: `update_indexes` is permissionless and utilization is driven entirely by ordinary `supply`/`borrow` calls. The trigger needs a high-decimal market holding whale-scale value (on the order of `i128`-adjacent scaled books, e.g. ~1e9 whole units at 18 decimals) held at high utilization on a steep curve for a sustained accrual horizon, plus caps/max-utilization raised enough to permit it — conditions governance-approved caps may constrain but do not forbid. Like the CVE (a reachable crash, not a crafted exploit), it is a deterministic arithmetic cliff that honest usage can walk into. Medium severity: permanent fund freeze contingent on market scale and time.

### Recommendation
Bound the product, not just the index: derive per-market index caps as `i128::MAX / max_scaled_book` (or clamp `borrowed`/`supplied` scaled totals) so `scaled_to_original` can never overflow before `MAX_BORROW_INDEX_RAY` engages, and enforce it inside `accrue_step`. Alternatively, saturate `scaled_to_original` (or the index update) instead of panicking, and fix the incorrect bound documented in `docs/reference/formulas.md` [5](#0-4) .

### Proof of Concept
The in-repo test demonstrates the full path:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let principal = BILLION * 10i128.pow(18);          // whale 18-decimal market
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
loop { t.advance_time(YEAR_SECS); t.try_update_indexes_for(&["BIG18"])?; }
// -> Err(MATH_OVERFLOW) while borrow_index < MAX_BORROW_INDEX_RAY
// market frozen: withdraw and repay both fail with MATH_OVERFLOW
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause: `calculate_utilization` (and every other unscale) computes `borrowed * borrow_index` in `i128`; the product overflows while `borrow_index` is still below its configured cap, so the intended ceiling never fires [6](#0-5) [7](#0-6) .

*Caveat: I was unable to read `common/src/rates/index.rs` to confirm the exact cap-check ordering inside `accrue_step`; the claim that the cap "never engages" rests on the harness test's assertion and may warrant verifying that file directly.*

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
```

        "mul_div_half_up: non-negative x, y and positive d"

#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
