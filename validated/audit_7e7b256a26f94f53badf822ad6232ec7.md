This confirms the vulnerability: the webhook's HMAC only signs `@raw_body` (`to_signable_string` returns `@raw_body`, `lib/shopify_api/webhooks/request.rb:36-38`), while the `shop` field consumed by the application (`lib/shopify_api/webhooks/request.rb:20-23`) comes from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed payload. `Registry.process` validates only the HMAC of the body (`lib/shopify_api/webhooks/registry.rb:189-199`) and then forwards `request.shop` straight into `WebhookMetadata` to the app's handler, with no cross-check that the header-derived shop matches the shop the HMAC was actually generated for.

### Title
Webhook shop-domain header is not covered by HMAC, allowing shop/tenant spoofing on valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), but the `shop` attribute the gem hands to application webhook handlers is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is completely outside the HMAC's signed content.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header value [1](#0-0) . For webhooks, `to_signable_string` is defined to return only `@raw_body` [2](#0-1) , while `shop` is derived independently from a header that carries no cryptographic binding to that signature [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body's HMAC is valid for *some* legitimate webhook signed with the app's secret), then immediately builds `WebhookMetadata` using `request.shop` unchecked and dispatches it to the registered handler [4](#0-3) .

The identity binding that should hold is: `shop_the_HMAC_was_computed_for == shop_the_handler_receives`. Because the header is unauthenticated, an attacker who owns/controls one shop (or who has captured a single genuine webhook delivery for any shop, e.g. their own store) can replay that exact `raw_body` + valid `hmac` header pair to the app's webhook endpoint while substituting an arbitrary value for `x-shopify-shop-domain`. The HMAC still validates (it only checks the body), yet the app-level handler is told the event belongs to a different, attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: `Registry.process` (and the `WebhookMetadata.shop` value it produces) is the only tenant-identifying signal host applications are expected to trust when persisting webhook data or triggering per-shop side effects (data deletion, redaction, order/customer updates, etc.). An attacker can cause the application to process a validly-HMAC'd payload attributed to an arbitrary victim shop domain, i.e. cross-tenant confusion/write using data that was never actually sent by or intended for that shop. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint and possession of one legitimately-signed webhook body (which any merchant using the app already receives for their own shop, or which can be observed since delivery endpoints are typically public URLs receiving unauthenticated POSTs). No access to `api_secret_key`, access tokens, or any privileged credential is required — the attacker never needs to compute a valid HMAC themselves, only to reuse one that was legitimately produced, while swapping the unauthenticated `shop` header.

### Recommendation
Bind the shop (and, ideally, topic/webhook-id) into the value that is actually verified, e.g. include `shop-domain` in `to_signable_string`, or independently verify that the header-derived shop matches a shop the app expects/has an active registration/session for before dispatching to handlers. At minimum, document and enforce that `request.shop` must never be trusted as an authenticated value derived from the HMAC.

### Proof of Concept
1. Attacker's own store legitimately receives a real webhook: `POST /webhooks` with body `{"id": 123}`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed by Shopify over that body with the app's shared secret.
2. Attacker resends the identical body and HMAC header to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the (unchanged) HMAC [5](#0-4) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the application to process attacker-controlled data as if it originated from the victim's shop.
