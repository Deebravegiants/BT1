### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, allowing tenant/topic spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable string solely from the raw body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used to identify which merchant and event the payload belongs to come from HTTP headers that are never included in the signature. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then forwards the untrusted header-derived `shop`/`topic` to the app's `WebhookHandler`.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the received signature: [3](#0-2) 

`Registry.process` treats a valid body HMAC as sufficient proof of authenticity for the whole request, then builds `WebhookMetadata` directly from the unauthenticated `shop`/`topic`/`api_version`/`webhook_id` header values and hands it to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header == shop the HMAC secret proves the payload originated from`. In reality, the HMAC only proves `raw_body == HMAC(secret, raw_body)`; it says nothing about which shop or topic that body belongs to. An unprivileged attacker who legitimately installs the app on their own store can obtain any number of genuine `(raw_body, hmac)` pairs (since Shopify signs webhooks with the app's own `api_secret_key`, and the attacker is a legitimate merchant of their own shop receiving those webhooks). The attacker can then POST that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain/topic. `HmacValidator.validate` still succeeds because it never looks at the headers, so `Registry.process` calls the handler with `shop: <victim shop>` and a body the attacker fully controls.

### Impact Explanation
This breaks the shop-authenticity binding this gem exists to provide. Applications rely on `Registry.process`/`WebhookMetadata#shop` to identify which merchant a webhook event applies to (e.g., to look up that merchant's session/access token or to update per-tenant state). Because the shop identity is not covered by the signature, an attacker can force webhook side effects to be attributed to an arbitrary victim shop with attacker-chosen body content, which is a cross-tenant confusion/impersonation at the authentication boundary this gem enforces.

### Likelihood Explanation
Requires no secret, no credential theft, and no privileged access - only the ability to install the app on an attacker-owned shop (to harvest one valid `(body, hmac)` pair) and to send a crafted HTTP POST with modified headers to the app's public webhook endpoint. This is directly reachable by any unprivileged internet user.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string, or otherwise cryptographically bind them to the body before comparing against the HMAC, so that tampering with any of these headers invalidates the signature rather than only tampering with the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw request body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` with the app's `api_secret_key`.
2. Attacker sends `POST <app-webhook-endpoint>` with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes.
4. `Registry.process` looks up the handler for the (possibly attacker-chosen) topic and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
