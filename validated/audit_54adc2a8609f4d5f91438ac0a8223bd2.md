### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) are unauthenticated header values not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), event `topic`, `webhook_id`, and `api_version` from HTTP headers that are never included in the value used to compute/verify the webhook HMAC. `Utils::HmacValidator.validate` only authenticates the raw request body via `to_signable_string`, which returns `@raw_body` alone. This breaks the equality `shop authenticated by HMAC == shop delivered to the handler`, letting anyone in possession of one valid (body, HMAC) pair from Shopify — trivially obtainable by installing the app on their own low-privilege test store — replay that same body/HMAC pair while swapping the `x-shopify-shop-domain` header to a victim merchant's domain and have it pass validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding to that same request: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`) straight into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header — it never touches `shop`: [4](#0-3) 

The gem's own documentation instructs developers to treat `data.shop` from `WebhookMetadata` as the authoritative tenant identifier for downstream per-shop actions (e.g., enqueuing jobs keyed by shop): [5](#0-4) 

This is the direct analog of the reported bug class: an identity-relevant field (`shop`) is *acted upon* by the library's documented API but is *not covered* by the same cryptographic check (`HMAC`) that is supposed to authenticate the request, exactly mirroring "a field acted on but not covered by the HMAC."

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled, unprivileged) shop receives legitimate webhook deliveries for that shop, each with a valid `(raw_body, hmac-sha256)` pair signed with the app's real `api_secret_key`. Because `shop`, `topic`, and `webhook_id` are not part of the signed payload, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with any other real merchant's `myshopify.com` domain. `Utils::HmacValidator.validate` will still succeed (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any app that uses `data.shop` to select which merchant's session/access token to act on, or that writes/deletes data keyed by `data.shop` (per the gem's own documented usage pattern), will perform tenant-scoped operations attributed to the wrong shop — a cross-tenant access/data-integrity break driven entirely by this gem's identity binding gap.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker: no credentials, access tokens, or `api_secret_key` are required — only a free/trial installation of the target app on an attacker-controlled store to harvest one valid signed webhook, then a single replayed HTTP request with a modified header. The gem provides no defense (e.g., binding `shop`/`topic`/`webhook_id` into the signed value, or verifying the header shop matches a shop associated with the delivered `webhook_id`) that would prevent this.

### Recommendation
Bind the identity-relevant header fields (`shop`, `topic`, `webhook_id`, `api_version`) into the value used for HMAC verification (analogous to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed string), or otherwise require the consuming application to independently verify that `webhook_id`/`shop` correspond to a subscription the app actually registered for that shop before trusting `WebhookMetadata#shop` for tenant-scoped actions. At minimum, update `Utils::VerifiableQuery`/`HmacValidator` usage in `Webhooks::Request` so the signable string incorporates the header fields that are subsequently treated as trusted identity data.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook delivery:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body) # computed by Shopify, unknown secret to attacker but delivered on the wire

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "attacker.myshopify.com", # <- attacker swaps this
  "x-shopify-webhook-id" => "any-id",
}

# 2. Attacker replays the exact same body + hmac header, but with the shop domain
#    changed to the victim's shop:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation still succeeds because it only checks raw_body,
#    which the attacker did not modify:
ShopifyAPI::Webhooks::Registry.process(request)
# => Handler invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though Shopify never sent this webhook for victim-shop.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
