### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop/tenant spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request **body**. The `shop` value that is handed to the app's webhook handler — and that a host application uses to select the tenant/session the webhook applies to — comes from an HTTP header that is **not** included in the signed material. This breaks the identity binding `shop verified by HMAC == shop acted upon by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside of what gets signed: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, i.e. the body only, and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts the request purely based on this body-only HMAC check, then dispatches to the handler using `request.shop` — the unauthenticated header value — as the tenant identifier delivered to the app: [4](#0-3) 

Because `hmac-sha256` is computed by Shopify over the JSON body only (this is standard Shopify webhook behavior and matches this gem's own signable-string implementation), an attacker who legitimately receives webhooks for a shop they control can capture a `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to an arbitrary victim shop domain. The signature still validates (it never covered the shop header), so `Registry.process` calls the handler with `WebhookMetadata#shop` equal to the attacker-chosen victim shop while the body content is whatever the attacker originally received.

This is exactly the bug class described in the report: a field that is *acted upon* (`shop`, used by the host app to pick the tenant/session the webhook data is attributed to) is not covered by the cryptographic check that is supposed to authenticate the whole request (`shop authenticated != shop used to route/act`).

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata#shop` (as documented/intended for building the session/tenant context for the webhook, e.g. via `ShopifyAPI::Utils::SessionUtils.offline_session_id(shop)`) can be tricked into applying attacker-supplied webhook data to a different merchant's tenant context. This is a cross-tenant boundary break driven entirely by data this gem itself failed to authenticate, meeting the Critical "cross-tenant access" impact bar defined in scope.

### Likelihood Explanation
The prerequisite is only that the attacker has installed the app on any shop they control (an ordinary, unprivileged action) so that they legitimately receive at least one valid `(body, hmac)` webhook pair; no access to `api_secret_key`, tokens, or privileged accounts is required, and no interception of Shopify traffic is needed. This is a self-service, unprivileged-internet-user attack against the gem's own validation logic.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) as part of the data verified against the HMAC, or independently bind/verify the header-derived `shop` against a value the app has already established (e.g., only accept webhooks for shops with an existing session, and don't let the header alone determine trust). At minimum, `Utils::HmacValidator.validate` should be changed so `Webhooks::Request#to_signable_string`/the verification path incorporates the shop-domain header, closing the gap between what is signed and what is trusted for tenant routing.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers/receives one legitimate webhook, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's real `client_secret` — the attacker never needs to know the secret, only to observe `H`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same header `H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B) == H` — this passes.
4. The handler executes with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, i.e., attacker-controlled body content is processed as if it belongs to the victim shop.

        end
