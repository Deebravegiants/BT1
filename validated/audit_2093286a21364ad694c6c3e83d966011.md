## Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler actually acts on are taken from unauthenticated HTTP headers and are never included in the signed content, so they can be freely substituted in a replayed request without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` verifies the request only via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (i.e. checks only the body), and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute `compute_signature(verifiable_query.to_signable_string, secret)` and compare it to the received HMAC — for a `Webhooks::Request`, `to_signable_string` is just `@raw_body`, so the header values are entirely outside the authenticated boundary: [4](#0-3) 

This breaks the identity binding `shop-domain header == shop that produced the signed body`. An unprivileged actor who is a legitimate merchant/installer of the app (i.e., can trigger any genuine webhook delivery for their own shop, which Shopify signs with the app's real `api_secret_key` on Shopify's side — the merchant never needs to know the secret to receive it) can capture one valid `(raw_body, hmac)` pair, then replay that exact body/HMAC to the app's webhook endpoint while altering the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers. The signature still validates because those headers were never part of the signed string, so `Registry.process` will invoke the handler believing the event legitimately originated from an arbitrary shop and/or topic of the attacker's choosing.

### Impact Explanation
This allows cross-tenant webhook forgery: an attacker-controlled event (with attacker-controlled body content, since they trigger the original webhook) can be attributed to a victim shop by simply replacing the `shop-domain` header, or reinterpreted under a different topic by replacing the `topic` header, while still passing HMAC validation. Any host application logic that trusts `WebhookMetadata#shop` or `#topic` for tenant-scoped actions (e.g., updating per-shop data, revoking access, triggering fulfillment/order side effects) can be manipulated cross-tenant. This falls under the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a normal, unprivileged app user capable of triggering at least one genuine webhook for their own shop (e.g., installing the app to a store they control and generating any subscribed event) — no access to `api_secret_key`, access tokens, or any privileged account is needed. Capturing and replaying the HTTP request with modified headers is trivial once the attacker has one valid `(body, hmac)` pair.

### Recommendation
Include the authenticated identity fields (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed content used for HMAC verification, or otherwise cryptographically bind them (e.g., verify `shop` against the session/shop the app expects for that webhook subscription) rather than trusting header values that fall outside the HMAC-covered bytes.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g. `orders/create`) so Shopify delivers a body `B` with header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Capture the raw HTTP request (`B`, headers).
3. Replay the exact same `B` and `H` to the app's webhook endpoint, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com` (and/or change `x-shopify-topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` [5](#0-4) , and `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the app to process an attacker-crafted body as an authentic event from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
