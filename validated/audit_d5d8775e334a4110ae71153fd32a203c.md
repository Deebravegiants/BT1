### Title
`socialize-debt` can drive `assets` to `u0` while `zft` total-supply stays unaffected, breaking the shares-backing invariant - (`mainnet/contracts/vault/v0-vault-ststx.clar`)

### Summary
`socialize-debt` writes down `principal-scaled`, `total-borrowed` and `assets` independently of the `zft` token supply. When a liquidation shortfall is large enough to zero out `principal-scaled`, the code also drives `assets` to exactly `u0` [1](#0-0) , while `total-supply` (the outstanding `zft` shares) is never touched by this function. This produces a state where `total-assets-preview() = u0` but `total-supply > u0`, which is exactly the "empty pool, nonzero shares" edge case that ERC-4626-style share-math implementations must special-case.

### Finding Description
Identity claimed to hold: `total-assets-preview() > u0` whenever `total-supply() > u0` (shares must remain backed by a positive asset value). `socialize-debt` breaks this:

- `principal-reduction = scaled-amount * borrowed / scaled-principal` and `assets' = if current-assets > principal-reduction then current-assets - principal-reduction else u0` [2](#0-1) .
- With `scaled-amount == principal-scaled` (full write-off) and `principal-reduction >= current-assets` (i.e. the bad debt equals or exceeds the recorded pool value — plausible since `assets` also contains idle liquidity plus other borrowers' outstanding balances, and a single large defaulted position can exceed it if it was under-collateralized enough), `var-set assets ... u0` fires, zeroing the pool's backing value.
- `socialize-debt` never reads or writes the `zft` fungible-token supply, so `total-supply()` is completely unaffected by this call. There is also no check inside `socialize-debt` that `assets` staying `> u0` is required, nor any assertion tying the write-down to `total-supply`.
- `socialize-debt` is reachable from an unprivileged caller through the public `liquidate` entrypoint in `market.clar`, which on a large-enough shortfall calls `socialize-debt-asset` → `vault-socialize-debt` → `socialize-debt` [3](#0-2) . `check-caller-auth` inside `socialize-debt` only restricts the *direct* caller to be an authorized contract (the market), not the ultimate liquidator, so any unprivileged principal that calls `liquidate` on an under-collateralized position it controls (or that it engineered via price movement/borrow-to-cap) can trigger this write-down.
- After this state is reached, a subsequent `deposit(amount, u0, recipient)` computes `inkind = (convert-to-shares-preview amount)` [4](#0-3) . Whatever the exact zero-denominator handling in `convert-to-shares-preview` (not retrievable in this pass — it is either a `mul-div-down` against a zero `total-assets-preview()` denominator, which Clarity aborts on, or an explicit `total-assets == u0` branch that mints 1:1/zero shares), the underlying protocol state fed into it (`total-assets-preview() = u0`, `total-supply() > u0`) is a genuinely broken invariant that the deposit path was never designed to handle safely. If the branch mints `u0` shares for a nonzero deposit (matching the question's proof idea), the deposit's `min-out = u0` passes the slippage check trivially and the depositor's underlying is pulled in and added to `assets` with zero `zft` minted — a direct loss of the depositor's funds absorbed by existing shareholders.

I was not able to retrieve the exact source of `convert-to-shares-preview` in this session, so I cannot confirm with certainty whether the resulting deposit call reverts (division-by-zero abort, which would neutralize the theft but still leave deposits permanently frozen) or silently mints zero shares (direct theft as hypothesized). Either outcome is a Critical-severity failure mode stemming from the same root cause: `socialize-debt` is allowed to zero `assets` without any corresponding constraint on `total-supply`, `zft` burn, or a guard preventing further deposits/redeems while the pool is insolvent.

### Impact Explanation
- If `convert-to-shares-preview` mints zero shares: every subsequent deposit while `assets == u0` and `total-supply > u0` is a full loss of the depositor's principal, repeatable for every future depositor until the pool state is corrected — protocol insolvency directly monetized against unsuspecting depositors (Critical: direct theft of user funds).
- If it instead reverts, deposits are permanently frozen once this state is reached, and existing shareholders' shares are irrecoverably worthless (Critical: protocol insolvency / permanent freezing of funds), since `redeem` also depends on `assets` and `convert-to-assets-preview` and would return `u0` for any withdrawal.
- Either way, the loss is deterministic and reproducible: whoever triggers the socialize-debt write-off need only ensure `principal-reduction >= current-assets` in a single call.

### Likelihood Explanation
Reaching `scaled-amount == principal-scaled` and `principal-reduction >= current-assets` requires a liquidation-driven shortfall large relative to the vault's recorded `assets`, which is more feasible in a young/thin vault (e.g., right after deployment or with a small deposit base) than in a fully utilized mature vault. An attacker who is also the borrower can deliberately under-collateralize and default to engineer this, at the cost of losing their own collateral. This makes it a plausible, low-capital attack in low-liquidity vault conditions rather than a purely theoretical one.

### Recommendation
`socialize-debt` should never be able to reduce `assets` (or `total-assets`) to a value that leaves `total-supply() > u0` with zero backing. Enforce an invariant check (e.g., `asserts! (or (is-eq (total-supply) u0) (> (var-get assets) u0)) ERR-INSOLVENT`) after the write-down, or pause `deposit`/`redeem` automatically once `assets` reaches `u0` while shares remain outstanding, and/or make `convert-to-shares-preview`/`convert-to-assets-preview` explicitly revert (rather than mint/redeem zero) whenever `total-supply() > u0` and `total-assets-preview() == u0`, so insolvency is surfaced as a halt rather than silently absorbed by new depositors.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Initialize `v0-vault-ststx`, deposit a small amount `D` from LP1 so `assets == D`, `total-supply == D` shares (1:1 bootstrap).
2. Have `market.clar` `system-borrow` most of `D` against a position, then force `socialize-debt(scaled-amount)` (via the authorized market call path) with `scaled-amount == principal-scaled` such that `principal-reduction >= D`.
3. Assert `(var-get assets) == u0` and `(var-get principal-scaled) == u0` while `(total-supply) == D` (unchanged) — this is the identity break: `total-assets-preview() = u0`, `total-supply() = D > u0`.
4. Call `deposit(amount2, u0, attacker)` from an unprivileged attacker principal.
5. Assert on the resulting `inkind` value returned/`ft-mint?` amount and on `(var-get assets)` before/after to determine which failure mode occurs (zero-mint theft vs. runtime abort/freeze), and record the exact numeric divergence for the report.
