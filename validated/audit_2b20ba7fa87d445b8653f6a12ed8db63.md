### Title
Unbounded gas forwarded to attacker-controlled destination modules in `EvmHost.dispatchIncoming`/`dispatchTimeOut` enables gas-griefing and return-bomb DoS against relayers - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)`, `dispatchIncoming(GetResponse, address)`, and both `dispatchTimeOut` overloads deliver cross-chain messages to destination applications via raw, gas-unbounded `.call` invocations to an address that is fully attacker-controlled (`request.to` / `timeout.request.from`, decoded directly from message bytes). This is the same bug class as the Sablier report: calling out to an untrusted contract without limiting forwarded gas lets the callee inflate gas usage (or force expensive `returndata` copying) at the caller's expense — here the caller is the relayer submitting the delivery transaction. [1](#0-0) 

### Finding Description
`dispatchIncoming(PostRequest memory request, address relayer)` resolves the destination purely from message data (`_bytesToAddress(request.to)`) and then performs:

```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [2](#0-1) 

No gas stipend is supplied, so Solidity forwards essentially all remaining gas (63/64 rule) to `destination`. Because `request.to` is chosen by whoever dispatched the original cross-chain request on the source chain, an attacker can deploy a contract implementing `IApp.onAccept` that either:
- burns gas in a loop up to (near) the entire forwarded amount ("gas bomb"), or
- reverts (or returns) with an enormous `bytes` payload, forcing the caller's implicit ABI-decode of the `(bool, bytes)` tuple to copy huge return data into memory ("return-data bomb"), which scales quadratically with memory expansion cost.

The exact same unbounded-forwarding pattern is repeated for:
- `dispatchIncoming(GetResponse memory response, address relayer)` calling `onGetResponse` [3](#0-2) 
- `dispatchTimeOut(GetRequestTimeout, ...)` calling `onGetTimeout` [4](#0-3) 
- `dispatchTimeOut(PostRequestTimeout, ...)` calling `onPostRequestTimeout` [5](#0-4) 

All four are `restrict(_hostParams.handler)`, i.e. reachable only from `HandlerV2`'s batch delivery functions, which are themselves invoked permissionlessly by any relayer submitting a valid proof for a batch of requests/responses/timeouts. The docs explicitly acknowledge apps are expected to "keep gas costs reasonable" and use try/catch [6](#0-5)  — but this is only advisory for honest app authors; nothing in `EvmHost` enforces a gas cap on the callee, and the destination module is not vetted or restricted by the protocol (any deployed contract can be a target since `request.to`/`from` is attacker-supplied).

### Impact Explanation
Because a single relayer-submitted transaction (`HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handlers) processes a batch of deliveries and calls into `EvmHost.dispatchIncoming`/`dispatchTimeOut` per item, one attacker-planted malicious destination module can:
1. Consume most of the relayer's supplied gas via a gas bomb or return-data bomb, starving gas available to process the remaining items in the same batch — causing otherwise-valid, honest requests/responses to fail delivery (marked non-relayed / retryable) purely due to gas exhaustion caused by an unrelated malicious entry.
2. Impose disproportionate real-money gas costs on relayers relative to the relayer fee actually paid for that message, since the fee is fixed/estimated ahead of time and cannot account for adversarial gas consumption by the callee.
3. At scale, this can make relaying to affected destinations economically unattractive, degrading or halting message delivery on a route — one of the explicitly in-scope impacts ("a route unable to deliver messages").

This does not directly cause fund loss to the relayer beyond gas paid, but it is a reliable, cheaply-triggerable griefing/DoS vector on the message-delivery path with no gas ceiling or per-call gas cap protecting the host or relayer, matching Medium severity for availability degradation of the messaging layer.

### Likelihood Explanation
Any actor can dispatch a POST request (or a GET request that will produce a response/timeout) whose `to`/`from` field points at a contract they control containing a malicious `onAccept`/`onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` implementation. No special privilege, whitelisting, or high cost is required beyond normal dispatch fees, and the message will unconditionally reach `dispatchIncoming`/`dispatchTimeOut` once proofs verify, since `EvmHost` performs no bytecode/behavior vetting of the destination before making the unbounded `.call`. This makes the attack straightforward and repeatable by any user of the protocol.

### Recommendation
Cap the gas forwarded to `IApp` callbacks in `EvmHost.dispatchIncoming`/`dispatchTimeOut` (e.g. `destination.call{gas: GAS_CAP}(...)`), and avoid implicit copying of arbitrary-length return data — use a low-level call plus `returndatacopy` bounded to a fixed maximum, or a `try/catch` pattern with an explicit gas stipend, so a single malicious module cannot consume more than a bounded, predictable amount of the relayer's gas regardless of its own logic.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp` where `onAccept` (or `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout`) either loops until near-`gasleft()` exhaustion, or `revert(hugePayload)`/`return(hugePayload)` with e.g. a multi-MB byte array.
2. Attacker dispatches a POST request from a source chain module with `to = address(EvilApp)` (or arranges a GET request whose `from` is `EvilApp` so the response/timeout targets it), batched alongside other legitimate pending messages destined for the same relayer batch.
3. A relayer submits `HandlerV2.handlePostRequests` (or the GET-response/timeout equivalent) covering the batch; internally this calls `EvmHost.dispatchIncoming`/`dispatchTimeOut` for each item including the attacker's entry.
4. The `.call` to `EvilApp` forwards ~63/64 of remaining gas and either burns it or forces an oversized `returndatacopy`, consuming a large, disproportionate share of the transaction's gas budget.
5. Result: the relayer either runs out of gas processing the remainder of the batch (other honest deliveries fail/are left retryable) or pays far more gas than the relayer fee compensates for, at the attacker's near-zero cost — demonstrating the griefing/DoS vector described in the report, applied to Hyperbridge's `EvmHost` message-delivery callbacks.

```text
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
```
