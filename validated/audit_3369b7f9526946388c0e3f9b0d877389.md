Found it. In `Webhooks::Registry.process`, the request's `to_signable_string` returns only `@raw_body` [1](#0-0) , i.e. the HMAC (`hmac-sha256` header) authenticates only the body bytes. The `shop` field used by the library and forwarded to the handler is read straight from the `shop-domain` header, which is never part of the signed data [2](#0-1) . `Registry.process` validates the HMAC over the request and then passes `request.shop` (from the unauthenticated header) directly into `WebhookMetadata` given to the app's handler [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw body only, never to the `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` accepts any request whose `hmac-sha256` header matches `HMAC(secret, raw_body)`, then reads the tenant identity (`shop`) from the unauthenticated header and hands it to the app's webhook handler as trusted data.

### Finding Description
The bug-class hint (key/identity mismatch between what is bound and what is used to look things up) maps here to a genuine binding break: the equality the code needs to hold is `shop_header == shop_that_produced(hmac, raw_body)`, but the code only ever checks `hmac == HMAC(secret, raw_body)` and never ties `shop-domain` into that computation [4](#0-3) . Because Shopify computes and includes the HMAC over the body for every webhook it sends, and because a merchant/admin of *any* store subscribed to the same topic can capture (or replay from their own logs) a validly-signed webhook payload for their own shop, they can resend that exact valid `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `Registry.process` will pass HMAC validation (it only checks the body/hmac pair) and will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen value [5](#0-4) .

Host applications are documented/expected to use `WebhookMetadata#shop` as the tenant key for locating the shop's session/access token and applying the payload (this is the only shop identifier the library exposes from a webhook request). Since this field is not authenticated, any host app that trusts it for tenant routing can be tricked into attributing a valid, HMAC-verified payload to the wrong shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: a request with a cryptographically valid signature can carry an attacker-chosen shop identity. Depending on how the host application uses `WebhookMetadata.shop` (e.g., to select which merchant's data to update, or to fetch that merchant's access token from its session store to act on the webhook), this enables cross-tenant data confusion/write using an authenticated (from the app's perspective) webhook delivery. This aligns with the "cross-tenant access" criterion in the Critical impact bucket, since it stems directly from the library failing to bind the `shop-domain` field into the signature it verifies.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs a validly-signed `(body, hmac)` pair for the topic they want to spoof — obtainable only by controlling a shop that legitimately receives such webhooks (e.g., their own development store subscribed to the same app) and replaying its own genuine webhook to the app's endpoint with a modified `shop-domain` header. No secret key or Shopify credentials are required — only network access to the app's public webhook endpoint and one's own store's valid webhook traffic, which fits the "unprivileged internet user" analog (no `api_secret_key`, access token, or privileged account needed).

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the request before trusting them, e.g. by having `to_signable_string` return a canonical concatenation of the raw body with the shop-domain header, and require the caller to independently verify that the resulting `request.shop` matches an actively-registered, expected shop before acting on the payload.

### Proof of Concept
1. Register the app’s webhook handler for topic `orders/create` and subscribe both "shop-a.myshopify.com" (attacker's own dev store) and "shop-b.myshopify.com" (victim) to it.
2. Attacker triggers an event in their own store "shop-a.myshopify.com"; Shopify POSTs the webhook to the app with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC of body using app secret>`
   - `x-shopify-shop-domain: shop-a.myshopify.com`
   - body: `{...order json...}`
3. Attacker captures this request and replays it to the same endpoint, changing only:
   - `x-shopify-shop-domain: shop-b.myshopify.com`
   (body and hmac header left untouched)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and compares to the header — it still matches, since the body is unchanged [6](#0-5) .
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: <shop-a's order data>, ...)` [7](#0-6) , causing the app to process shop-a's data under shop-b's identity if the app trusts `shop` for routing/session lookup.
