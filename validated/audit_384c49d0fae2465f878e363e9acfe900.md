### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the `shop` value taken from an unauthenticated HTTP header to the application's webhook handler. Because the `shop-domain` header is not part of the signed payload, an unprivileged attacker who can produce (or replay/capture) any valid `(body, hmac)` pair for the configured `api_secret_key` can attach an arbitrary `shop-domain` header and have the library report that event as originating from any shop of the attacker's choosing.

### Finding Description
The binding that should hold is: `shop reported to handler == shop that produced the HMAC`. In this gem that equality is never enforced.

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: `@raw_body`. [1](#0-0) 

- `ShopifyAPI::Webhooks::Request#shop` reads the `shop-domain` header, completely independent of the signed content: [2](#0-1) 

- `Utils::HmacValidator.validate` computes/compares the signature strictly against `to_signable_string` (the body), never touching headers: [3](#0-2) 

- `Webhooks::Registry.process` treats a passing HMAC check as authentication for the *entire request*, then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata`, which the host application uses to attribute the event to a merchant: [4](#0-3) 

Because `shop` never enters `to_signable_string`, the HMAC only proves "this body was signed with our secret for *some* shop" — it does not prove which shop. An attacker who can obtain any single valid `(body, hmac)` pair (e.g. by capturing a real webhook delivery, which travels over plain HTTP webhook endpoints and is not itself secret) can resend that exact body/HMAC with a different `x-shopify-shop-domain` header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming an attacker-chosen shop, even though the signature was never computed over that shop value.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended) to look up the merchant's session/access token or to scope a database write, an attacker can cause the app to process a webhook under an incorrect shop identity — effectively cross-tenant data confusion/attribution. This matches the Critical "cross-tenant access" impact category: the shop-identity binding that host applications rely on from this library is not actually authenticated.

### Likelihood Explanation
Exploitation requires only a single previously-observed valid `(body, hmac)` pair for the target app (webhook deliveries are not confidential and pass through externally reachable endpoints), plus the ability to send an HTTP request with a custom header — no access token, `client_secret`, or privileged account is needed. This is a realistic unprivileged-network-attacker scenario.

### Recommendation
Bind the shop (and other routing metadata such as topic/api-version/webhook-id) into the signed material, or otherwise cryptographically verify that the `shop-domain` header matches data actually covered by the HMAC (e.g. by including it in `to_signable_string`, or by requiring the host application to independently confirm the shop via a value present in the signed body). At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker captures one legitimate webhook delivery to the app's public endpoint: body `{}` with header `x-shopify-hmac-sha256: <valid-hmac-for-empty-body>` and `x-shopify-shop-domain: victim-shop.myshopify.com`.
2. Attacker resends the identical body and HMAC header, but sets `x-shopify-shop-domain: attacker-shop.myshopify.com` (or any other tenant's domain).
3. `Utils::HmacValidator.validate` succeeds because it only checks the body [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `shop` is `"attacker-shop.myshopify.com"` [6](#0-5) , even though the HMAC never certified that shop value.
