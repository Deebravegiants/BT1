### Title
`Oauth.validate_auth_callback` builds `Session` from unsanitized `auth_query.shop`, allowing shop-identity divergence from `ShopValidator`-canonicalized lookups - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` never calls `Utils::ShopValidator.sanitize!` on `auth_query.shop`; it passes the raw callback `shop` value straight into `Session.from`, which derives `session.id`/`session.shop` directly from that string. Other OAuth entry points in this gem (`ClientCredentials.client_credentials`, `TokenExchange`, `RefreshToken`) do call `ShopValidator.sanitize!` before constructing sessions, but `Oauth.validate_auth_callback` does not, creating an inconsistency in shop-identity canonicalization across the gem's own OAuth code paths.

### Finding Description
The claimed binding is:
`session.shop == ShopifyAPI::Utils::ShopValidator.sanitize!(auth_query.shop)`.

In [1](#0-0) , `validate_auth_callback` validates the HMAC via `Utils::HmacValidator.validate(auth_query)` and the `state` cookie, then builds `null_session = Auth::Session.new(shop: auth_query.shop)` and finally `session = Session.from(shop: auth_query.shop, access_token_response: ...)` — using the raw `auth_query.shop` string with no call to `Utils::ShopValidator.sanitize!` anywhere in this method.

`Session.from` in [2](#0-1)  builds `id = "offline_#{shop}"` (or `"#{shop}_#{associated_user.id}"` for online tokens) directly from the passed-in `shop` string, with no canonicalization.

By contrast, `ClientCredentials.client_credentials` explicitly does `validated_shop = Utils::ShopValidator.sanitize!(shop)` before calling `Session.from` [3](#0-2) , and `ShopValidator.sanitize!` itself implements unified-admin normalization via `myshopify_domain_from_unified_admin`, converting `admin.shopify.com/store/<shop>` into `<shop>.myshopify.com` [4](#0-3) [5](#0-4) .

The HMAC check in `Utils::HmacValidator.validate` only verifies that `auth_query.to_signable_string` (built from `code`, `host`, `shop`, `state`, `timestamp` fields, verbatim, via `URI.encode_www_form`) matches a signature computed with the app's secret [6](#0-5) [7](#0-6) . It authenticates that Shopify signed those exact bytes; it says nothing about the semantic form of `shop` and provides no canonicalization guard. Given the stated precondition — that Shopify itself can, on some surfaces, present `shop` in the unified-admin form (`admin.shopify.com/store/<shop>`) for a legitimately signed callback — the HMAC check passes for that literal string, and nothing downstream in `validate_auth_callback` normalizes it before it becomes `session.id`/`session.shop`.

Therefore, if a host app elsewhere in its own code canonicalizes shop identifiers via `ShopValidator.sanitize!` (as this gem's own other OAuth flows do) for session storage keys or lookups, a session produced by `validate_auth_callback` from a unified-admin-form `shop` would be keyed differently (`offline_admin.shopify.com/store/attacker-shop`) than the app's canonical key (`attacker-shop.myshopify.com`), producing the identity divergence described.

### Impact Explanation
If exploitable, this affects tenant-identity consistency: a session object returned by `validate_auth_callback` would carry a `shop`/`id` value that does not match the canonical `*.myshopify.com` form used by `ShopValidator.sanitize!` elsewhere in the gem (and presumably by the host app for storage/lookup keys). This could cause a host app that mixes raw OAuth-callback shop values with `ShopValidator`-sanitized values (e.g., in different parts of its session storage layer) to store or retrieve tokens under mismatched keys — a tenant-identity confusion bug. This matches the "cross-tenant access" category only if a concrete host-app-facing exploit (not just an internal inconsistency) can be demonstrated; the gem itself does not perform any cross-tenant lookup with this value, so the impact is real but contingent on how a host app uses the returned `session.shop`/`session.id`.

### Likelihood Explanation
The exploit depends entirely on the unverified precondition that Shopify's own signed OAuth callback can present `shop` in the `admin.shopify.com/store/<name>` form for a request to a dev/app install flow. This gem's `AuthQuery`/`HmacValidator` do not restrict the format of `shop`; they only check byte-for-byte HMAC integrity. No credential or secret is required by the attacker beyond triggering their own OAuth callback (installing their own app on their own dev shop), which is within the stated attacker capabilities. Feasibility of getting Shopify to emit this callback format is a Shopify-platform behavior question, not something this gem's code enforces one way or the other.

### Recommendation
In `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`), canonicalize `auth_query.shop` through `Utils::ShopValidator.sanitize!` immediately after the HMAC/state checks, and use the sanitized value consistently for `null_session`, the HTTP client's base URI, and the final `Session.from(shop: ..., ...)` call — mirroring the pattern already used in `ClientCredentials.client_credentials`, `TokenExchange`, and `RefreshToken`.

```ruby
def test_validate_auth_callback_does_not_canonicalize_unified_admin_shop
  unified_admin_shop = "admin.shopify.com/store/attacker-shop"
  canonical_shop = ShopifyAPI::Utils::ShopValidator.sanitize!(unified_admin_shop)
  # canonical_shop == "attacker-shop.myshopify.com"

  auth_query = ShopifyAPI::Auth::Oauth::AuthQuery.new(
    code: @callback_code,
    shop: unified_admin_shop,
    timestamp: @callback_timestamp,
    state: @callback_state,
    host: ShopifyAPI::Context.host_name,
    hmac: compute_valid_hmac_for(shop: unified_admin_shop, ...), # signed over the literal string
  )

  stub_request(:post, "https://#{unified_admin_shop}/admin/oauth/access_token")
    .to_return(body: @offline_token_response.to_json, headers: { content_type: "application/json" })

  result = ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: @cookies, auth_query: auth_query)

  refute_equal(canonical_shop, result[:session].shop)
  # demonstrates session.shop (== unified_admin_shop) != ShopValidator.sanitize!(unified_admin_shop)
end
```
Note: this PoC demonstrates the internal code-path divergence within the gem (no sanitize! call in `validate_auth_callback`); it does **not** by itself prove that Shopify's real OAuth server would ever sign a callback with `shop` in that literal form — that premise is asserted as a precondition in the question and could not be verified against this repository's code, since it is a Shopify-platform behavior, not something enforced or contradicted by this gem.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```

```ruby
        def validate(verifiable_query)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```
