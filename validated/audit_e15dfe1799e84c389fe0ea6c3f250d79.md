### Title
Arbitrary `originalSender` in `DepositOnChainUtxosExternalAction.runAction` allows draining any address's stale ERC20 allowance to the action contract - ([File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol])

### Summary
`DepositOnChainUtxosExternalAction.runAction` reads `userAddress` directly from the attacker-supplied `circomData.originalSender` field and calls `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` with no check that `userAddress == msg.sender` (the actual transaction submitter) and no cryptographic binding of `originalSender` to the caller. Any address that has ever granted an ERC20 allowance to this specific action contract (e.g. via a prior legitimate `approveUnlimited`-style deposit) can have that allowance drained by an unrelated attacker who names it as `originalSender` and directs the resulting on-chain UTXOs to their own `stealthAddressStructure`.

### Finding Description
Tracing the call: `Hinkal.transact` → `_externalTransact` → `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` [1](#0-0) . Inside `runAction`, `userAddress = circomData.originalSender` is used as the `_from` parameter of `transferERC20TokenFrom`, with only a non-zero-address check — there is no assertion that `userAddress == msg.sender` (the account that actually submitted the `transact` call) [2](#0-1) [3](#0-2) . Unlike `_internalTransact`, which explicitly requires `circomData.externalActionData.externalAddress == msg.sender` before pulling a deposit [4](#0-3) , no analogous check exists for `originalSender` in this external-action path.

Regarding the specific "proof coverage" framing in the question: the claim that minted UTXOs are "unbacked by any proof-verified deposit" is not accurate as stated, because `Hinkal.transact` independently enforces a Solidity-level balance-diff equation for `onChainCreation` tokens — `balanceDif == 0 + utxoAmount` — which forces the actual token amount pulled into the contract to equal the sum of UTXO amounts minted for that token [5](#0-4) . So `tokenTotal` cannot diverge from `utxoAmount`; no value is minted "from nothing." The real, exploitable defect is a different one: which address is debited is unauthenticated, letting an attacker impersonate `originalSender` = any address holding a stale allowance to this contract, and steal exactly that amount of real tokens while directing the resulting UTXOs to themselves.

### Impact Explanation
An attacker can direct-theft any user's ERC20 tokens that remain approved to the `DepositOnChainUtxosExternalAction` contract from an earlier, unrelated legitimate deposit, by naming that user as `originalSender` and setting their own address in `stealthAddressStructure`. This is direct theft of user funds and matches the Critical severity category. It is repeatable against every address that has left a non-zero allowance to this action contract, up to the full approved amount, until the allowance is revoked or exhausted.

### Likelihood Explanation
Feasibility depends entirely on whether any legitimate user has left a residual (especially unlimited/`approveUnlimited`-style) ERC20 allowance to this specific action contract — a common pattern to avoid repeated approval transactions. The attacker needs no special privileges: they can call `transact` themselves, craft `circomData` with `deltaAmounts[i] == 0` and arbitrary `originalSender`/`utxoAmounts`, and generate a valid proof for their own (unrelated) UTXO state since `originalSender` and `externalActionMetadata` are not shown to be bound into the circuit's public inputs. This significantly raises exploitability versus a scenario requiring privileged access, but full confirmation would require verifying `HinkalHelper.performHinkalChecks` to confirm `originalSender`/`externalActionMetadata` are not otherwise constrained against `msg.sender` — this could not be fully verified from the available index contents.

### Recommendation
Require `circomData.originalSender == msg.sender` in `DepositOnChainUtxosExternalAction.runAction` (mirroring the check already present in `Hinkal._internalTransact`), or otherwise cryptographically bind `originalSender` to the transaction submitter (e.g., via a signature check or by making the field always equal `tx.origin`/`msg.sender` from `Hinkal.transact`, not attacker-suppliable calldata).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `DepositOnChainUtxosExternalAction`, and a mock ERC20.
2. Have `victim` legitimately call the deposit flow once and leave a large/unlimited allowance to the `DepositOnChainUtxosExternalAction` contract (simulating a stale `approveUnlimited` residual approval).
3. As `attacker` (unrelated EOA, no special role), craft `CircomData` with `originalSender = victim`, `deltaAmounts[i] == 0`, `stealthAddressStructure` pointing to attacker's keys, and `externalActionMetadata` encoding `utxoAmounts` summing to `tokenTotal <= victim's remaining allowance`.
4. Generate a valid Groth16 proof for attacker's own unrelated UTXO state (proof does not need to reference `originalSender` or `externalActionMetadata`).
5. Call `Hinkal.transact` as attacker.
6. Assert: `victim`'s ERC20 balance decreases by `tokenTotal`; `attacker` gains a spendable on-chain UTXO commitment for `tokenTotal` under their own stealth address; equality check: `victim_balance_before - victim_balance_after == tokenTotal == sum(utxoAmounts minted to attacker)`, with `deltaAmounts[i] == 0` throughout, proving the debited party (`victim`) was never a signer or participant of this transaction.
