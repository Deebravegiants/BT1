### Title
Unprotected `initialize` allows re-initialization and ownership takeover - (File: contracts/controller/src/governance.rs)

### Summary
The controller's initialization routine `governance::init` writes the owner, position limits, borrow floor, app version, and pause state unconditionally, with no "already initialized" lock check before or inside it. Because `init` calls `ownable::set_owner(env, admin)` directly — a low-level setter that overwrites `OwnableStorageKey::Owner` rather than an enforced-once constructor — any caller who reaches the `initialize` entrypoint can reset the owner to an address of their choosing, even after legitimate deployment.

### Finding Description
The bug class from the external report (initializers missing a lock mechanism) maps directly onto the controller. `init` at `contracts/controller/src/governance.rs:14-33` performs five privileged writes with no guard:

- `ownable::set_owner(env, admin)` — overwrites the owner with the caller-supplied `admin` argument. The two-step transfer path (`transfer_ownership`/`accept_ownership` at lines 81–99) shows the codebase distinguishes the safe setter (`role_transfer::transfer_role`, which requires auth) from raw `set_owner`, which authenticates nothing — the comment at line 82 explicitly states "low-level role transfer does not" authenticate.
- `set_position_limits`, `set_min_borrow_collateral_usd`, `AppVersion`, and `pausable::pause` are all rewritten unconditionally.

There is no `initialized` flag, no `instance().has(&OwnableStorageKey::Owner)` check, and no panic on re-entry anywhere in `init`. The governance contract uses `has_controller`/`has_price_aggregator` existence checks (`contracts/governance/src/storage.rs:70-95`) and the pool uses `market_exists` (`contracts/pool/src/storage.rs:16-20`) for the same purpose, but the controller's init path has no equivalent guard.

### Impact Explanation
An unprivileged address calling the `initialize` entrypoint with their own address as `admin` becomes controller owner. Ownership in this contract gates the entire admin surface: `set_pool`, `set_swap_aggregator`, `set_price_aggregator`, `set_accumulator`, `unpause`, `upgrade`, and market/risk configuration. Concretely, the attacker can point `SwapAggregator` at a malicious contract so that `swap_debt`/`swap_collateral`/`repay_debt_with_collateral`/`multiply` route user collateral through attacker-controlled venues, or `upgrade` the contract Wasm outright. This is theft of user funds and potential protocol insolvency — a Critical/High impact, not a best-practice nit.

### Likelihood Explanation
A single unprivileged address submits one call: `Controller::initialize(attacker_addr)`. The exploit requires no timing advantage beyond the initializer being callable after deployment — it is reachable at any time if the entrypoint lacks an on-chain guard, since `init` itself performs no validation. The only mitigating factor is if the public entrypoint in `contracts/controller/src/lib.rs` performs an existence check before delegating to `init` (I could not confirm the entrypoint's body within the indexed code — the `pub fn` entrypoints appear to live in `lib.rs`/`contractimpl` blocks whose full contents were partially indexed); `init` itself provably contains no lock.

### Recommendation
Add a once-only guard at the top of `init` (or the `initialize` entrypoint), e.g. panic with `GenericError::AlreadyInitialized` if `env.storage().instance().has(&OwnableStorageKey::Owner)`. Prefer deploying with the Soroban `__constructor`, which the runtime guarantees executes exactly once, eliminating the class entirely. Apply the same pattern to any `initialize` on position-nft, pool, and price-aggregator if they use regular entrypoints rather than constructors.

### Proof of Concept
1. Deploy `Controller`; legitimate admin calls `initialize(admin)`. Contract is paused, owner = `admin`.
2. Attacker EOA calls `Controller::initialize(attacker)`. `init` runs `ownable::set_owner(env, attacker)` with no prior-owner check — owner is now `attacker`, and the contract is re-paused.
3. Attacker calls `set_swap_aggregator(malicious)` then `unpause`, or directly `upgrade(malicious_wasm_hash)`, gaining full control of routing/execution for all subsequent `swap_*`/`multiply`/`flash_position` flows and draining user collateral. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

pub(crate) fn init(env: &Env, admin: &Address) {
    ownable::set_owner(env, admin);
    ownable::emit_ownership_transfer_completed(env, admin);

    config::registry::set_position_limits(
        env,

            max_borrow_positions: POSITION_LIMIT_MAX,

    env.storage()
        .instance()
        .set(&ControllerKey::AppVersion, &INITIAL_APP_VERSION);

    pausable::pause(env);
}

pub(crate) fn transfer_ownership(env: &Env, new_owner: &Address, live_until_ledger: u32) {
    // The entrypoint authenticates the owner; low-level role transfer does not.
    let current_owner = ownable::get_owner(env)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::OwnerNotSet));

    role_transfer::transfer_role(
        env,
        new_owner,
        &ownable::OwnableStorageKey::PendingOwner,
        live_until_ledger,
    );
    ownable::emit_ownership_transfer(env, &current_owner, new_owner, live_until_ledger);
}

/// Renews instance TTL and completes transfer with pending-owner authorization.
pub(crate) fn accept_ownership(env: &Env) {

    ownable::accept_ownership(env);
}
