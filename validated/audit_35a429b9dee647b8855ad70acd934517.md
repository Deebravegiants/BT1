### Title
Missing sender-module authorization on `HYPR-FEE` relayer-fee withdrawal lets any pallet on the coprocessor forge fund withdrawals - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`HyperbridgeWithdrawalModule::on_accept`, the built-in ISMP module that pays relayer-fee withdrawals on behalf of Hyperbridge, authorizes an incoming `WithdrawRelayerFees` message solely by checking the **chain-level** `request.source` against the configured `Coprocessor`. It never checks `request.from` — the specific module/pallet on that coprocessor chain that actually dispatched the message. Any pallet capable of dispatching an arbitrary ISMP POST request from the coprocessor chain and addressing it to the well-known module id `b"HYPR-FEE"` can therefore trigger a transfer from `RELAYER_FEE_ACCOUNT` to any `AccountId` of its choosing, exactly mirroring the Snipe-IT bug class: an endpoint that authenticates the caller/source but omits the authorization check on *who* within that trusted boundary is allowed to perform the privileged action.

### Finding Description
`IsmpHostRouter::module_for_id` intercepts the reserved id `HYPERBRIDGE_MODULE_ID = b"HYPR-FEE"` and always routes it to `HyperbridgeWithdrawalModule`, regardless of which pallet on the coprocessor originated the request: [1](#0-0) 

`on_accept` then performs exactly one authorization check — that `request.source` equals the configured `Coprocessor` state machine — before decoding the body and executing the transfer: [2](#0-1) 

Unlike every other privileged cross-chain action in the codebase (e.g. `IntentGatewayV2.onAccept`'s `NewDeployment`/`UpdateParams`/`SweepDust`/`Execute` branches, which are additionally checked against `IDispatcher.hyperbridge()` *and* only decoded after that check, or the destination-side `HostManager.onAccept` fix documented for the same class of bug — see `sdk/packages/core/docs/ai/decisions/2026-09-03-hostmanager-deliveries-are-gated-too...`), the `HYPR-FEE` handler has no check that `request.from` is the specific pallet/component on Hyperbridge that is meant to authorize withdrawals (e.g. `pallet-ismp-relayer`'s `withdraw`/`accumulate` logic). It trusts *any* module id on the coprocessor chain that can get an ISMP POST dispatched with `dest = <this chain>`, `to = HYPR-FEE`.

On the coprocessor (nexus) side, ordinary user-facing pallets can freely choose `to` and `body` for outgoing dispatches — for example `pallet-hyper-fungible-token::send` lets a signed user pick the `to` field (normally the paired token contract) and fully controls the encoded body sent to the destination chain: [3](#0-2) 

Because the destination-side authorization check in `HyperbridgeWithdrawalModule::on_accept` never inspects `request.from`, a message whose `to` is coerced to `HYPR-FEE` and whose body is a valid `Message::WithdrawRelayerFees` SCALE encoding will be accepted as if it came from Hyperbridge's own relayer-payout logic, as long as it structurally originates from the coprocessor chain. This is the same "authenticated but not authorized" gap as the Snipe-IT `POST /hardware/history` bug: the check that exists (source chain == coprocessor) is necessary but not sufficient, and the missing check (which specific module on that chain is allowed to speak for the protocol) allows an unprivileged actor to reassign funds ( `RELAYER_FEE_ACCOUNT` → arbitrary `account` ) and forge protocol-level audit events (`RelayerFeeWithdrawn`), just as the CVE allowed reassigning assets and injecting fraudulent audit-log entries via a batch import path that checked authentication but not the caller's authorization to perform that specific action.

### Impact Explanation
Successful exploitation drains `RELAYER_FEE_ACCOUNT` — the pooled escrow funding all relayer-fee payouts across every connected chain — to an attacker-chosen account, for an attacker-chosen `amount`, on any destination chain running `pallet-ismp` with `HYPR-FEE` wired in. This is concrete theft of protocol funds (VC:N/VI:H in the source CVSS vector maps to a comparable "unauthorized value transfer" primitive here) and simultaneously forges a `RelayerFeeWithdrawn` audit event, corrupting the protocol's on-chain accounting of relayer payouts — directly analogous to Snipe-IT's audit-log injection via unauthorized asset reassignment.

### Likelihood Explanation
Exploitability hinges on whether any deployed coprocessor-side pallet lets an unprivileged, signed account fully control both the `to` (destination module id) and `body` fields of an outgoing ISMP POST dispatched to a given destination chain (as `pallet-hyper-fungible-token::send` structurally permits for its own `to`/`body` construction, and more generally as `IsmpDispatcher::dispatch_request` accepts a caller-supplied `DispatchPost{to, body}` with no restriction tying `to` to the calling module's own identity). If the coprocessor's own dispatch surface constrains `to` (e.g., always the registered token contract) this specific vector may be blocked in practice, but the underlying flaw — that `HyperbridgeWithdrawalModule::on_accept` authorizes on chain-source alone — remains a design gap that any future or misconfigured coprocessor-side pallet capable of free-form dispatch would immediately weaponize. I was not able to fully enumerate every pallet integrated on the live `nexus` runtime's `Router`/`ProxyModule` dispatch path within the available context to conclusively prove an existing unconstrained dispatch caller; this should be verified against the full `nexus` runtime's set of pallets with dispatcher access before triage.

### Recommendation
Add a `request.from` (sending module/pallet identity) check to `HyperbridgeWithdrawalModule::on_accept`, restricting accepted `HYPR-FEE` messages to the specific well-known module id used by Hyperbridge's own relayer-payout logic (mirroring how `IntentGatewayV2.onAccept` restricts `NewDeployment`/`UpdateParams`/`SweepDust`/`Execute` to `source == hyperbridge` *before* trusting the decoded body, and how `HostManager.onAccept` was hardened to check the specific authorized relayer/module rather than just the chain). Audit all pallets wired into the coprocessor-side `IsmpDispatcher` to ensure none allow a signed user to set an arbitrary `to` module id when dispatching to a destination chain, or otherwise scope `dispatch_request` callers so `from` cannot be spoofed to impersonate the protocol's fee-withdrawal origin.

### Proof of Concept

On the coprocessor chain (nexus), find or craft a signed extrinsic path that calls `IsmpDispatcher::dispatch_request` with a caller-controlled `DispatchPost { dest: <victim_chain>, to: b"HYPR-FEE".to_vec(), body: Message::WithdrawRelayerFees(WithdrawalRequest { account: <attacker_account>, amount: <X> }).encode(), .. }` (e.g. by driving `pallet-hyper-fungible-token::send`'s `token_contract`/body construction toward this shape, or any other pallet exposing free-form `to`/`body` dispatch).
2. Relay the resulting ISMP POST request to `<victim_chain>`; the request's `source` correctly resolves to the coprocessor state machine.
3. `IsmpHostRouter::module_for_id` routes it to `HyperbridgeWithdrawalModule` because `to == HYPR-FEE`.
4. `on_accept` checks only `source == Coprocessor` (true), decodes the forged `WithdrawRelayerFees` message, and transfers `amount` from `RELAYER_FEE_ACCOUNT` to `attacker_account`, emitting `RelayerFeeWithdrawn` as if this were a legitimate protocol payout. [2](#0-1)

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
