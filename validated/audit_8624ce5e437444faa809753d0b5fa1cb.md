### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop` (and `topic`, `api_version`, `webhook_id`) attributes are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body-derived HMAC and then forwards the header-derived `shop` value to the application's webhook handler as the tenant identifier, breaking the intended binding between "the shop the HMAC proves the request is authentic for" and "the shop the handler is told this event belongs to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate_signature` verifies `computed_signature` (over `to_signable_string`, i.e. body only) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then hands the *unauthenticated* `request.shop` straight to the app's handler as the tenant context: [4](#0-3) 

The binding that should hold is:
`shop authenticated by HMAC == shop delivered to handler as WebhookMetadata.shop`

In this implementation that equality does not hold: the HMAC only authenticates the byte content of the body against the app's shared `client_secret` (the same secret is valid for every shop that has installed the app), while the `shop` field consumed by `handler.handle(...)` is taken verbatim from an attacker-controllable header. An attacker who controls any shop that has the target app installed can capture a body+HMAC pair that is valid under the shared secret (e.g., by triggering a real webhook to their own store) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to name a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects the header, and the handler will process the payload believing it pertains to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an actor who is a legitimate but low-privileged Shopify merchant with the same app installed (an "unprivileged internet user" relative to other tenants of the app) can make the app attribute webhook data/actions to an arbitrary other shop identifier, without ever having credentials for that shop. Depending on how the hosting application uses `WebhookMetadata#shop` (e.g., to look up/create records, invalidate caches, or select the session/access token to act with), this enables cross-tenant data corruption or cross-tenant action — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to control one shop where the target app is installed (to obtain a legitimately-HMAC-signed body) and the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a forged header — no access token, `client_secret`, or privileged account is needed. The gem provides no header-binding safeguard, so any host application that trusts `request.shop`/`WebhookMetadata.shop` as an authenticated tenant key (a natural and encouraged use, since the gem exposes it as if it were verified) is exposed.

### Recommendation
Include `shop` (and ideally `topic`/`api_version`/`webhook_id`) in the signed content verified against the HMAC, or otherwise cryptographically bind the header-derived shop to the signature (e.g., require the caller to independently confirm the shop via a signed session/token rather than trusting the raw header). At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`) so Shopify sends a body `B` with a valid `x-shopify-hmac-sha256` signature `H` computed with the app's shared `client_secret`.
2. Attacker captures `B` and `H` from the request to their own endpoint (or via a proxy/logging on their own infra).
3. Attacker sends a POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` [5](#0-4)  — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the app to process attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.
