This confirms the vulnerability. The docs explicitly instruct app developers to use `data.shop` as the tenant identifier (`perform_later(topic: data.topic, shop_domain: data.shop, ...)` in `docs/usage/webhooks.md:26`), and `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header — a value that is never included in the HMAC computation, since `Request#to_signable_string` returns only `@raw_body`.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using only the HMAC over the raw request body, but the `shop` value it hands to app handlers is read from an HTTP header that is never part of the signed payload. Any party who possesses one valid `(body, HMAC)` pair for the shared app secret (e.g., a genuine webhook delivered to their own installed shop) can replay that exact body/HMAC while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will report the forged shop as authentic to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac`/`Request#shop` are both derived independently from HTTP headers [2](#0-1) . Thus the identity binding the code implicitly relies on — `hmac == HMAC(secret, body) AND shop_header == shop_of(body)` — is never actually enforced by the gem; only `hmac == HMAC(secret, body)` is checked.

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app-supplied handler: [3](#0-2) . The `WebhookMetadata` struct exposes `shop` as a plain, unauthenticated string field [4](#0-3) , and the gem's own documentation instructs app developers to key their tenant-scoped processing directly off this value: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) .

Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app, a malicious merchant who has the app installed on their own store legitimately receives real `(body, HMAC)` pairs signed with that shared secret. They can capture one, and resend it directly to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds because the body and secret are unchanged, and `Registry.process` will forward the victim's shop identifier paired with attacker-controlled body content to the app's handler.

### Impact Explanation
This breaks the tenant identity binding relied upon by every downstream consumer of this gem: the recorded `shop` for a webhook event no longer corresponds to the shop that actually authored the payload. Depending on how the host application persists/acts on webhook data (as documented and recommended by this gem), this enables cross-tenant data injection — e.g., an attacker's order/product/customer payload being attributed to and processed under a different merchant's tenant record, or a `shop/redact`/`customers/redact` GDPR-style payload being falsely attributed to trigger tenant-scoped side effects for a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the identity that is supposed to gate per-tenant data processing is forgeable by any user who can install the app on one shop and reach the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is High: no access token, `client_secret`, or privileged account is required beyond the ability to install the app on an attacker-controlled shop (the normal, unprivileged path for any Shopify merchant) and to send a raw HTTP request to the app's public webhook receiver — both are within reach of an "unprivileged internet user" per the scope of this analysis. The only additional requirement is capturing one legitimate webhook body/HMAC pair from the attacker's own store, which is trivial since Shopify delivers those to the app automatically once installed.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) header values into the HMAC-signed material, not just the raw body — e.g., compute the signature over a canonicalized string that includes these header values, or otherwise cryptographically bind the shop header to the payload before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should refuse to process a webhook whose `shop` header cannot be independently corroborated (e.g., cross-checked against a shop already known to have a stored session for the topic/webhook_id), rather than passing an unauthenticated header value straight into tenant-scoped application logic.

### Proof of Concept
```ruby
# Attacker has the app installed on their own shop "attacker.myshopify.com"
# and captures a real webhook Shopify sent them:
body = '{"id": 1, "note": "hi"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, body)

# Attacker now POSTs the exact same body+HMAC to the app's public webhook
# endpoint, but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (body/secret unchanged); handler receives
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's body, ...)
```
