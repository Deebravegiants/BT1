Based on the investigation, I found a strong structural analog to the `airdropUpdateLastClaimTime` bug class in the market's same-block liquidation guard, though I was unable to fully verify the exact borrow-path code in the remaining iteration budget.

### Title
Same-block liquidation guard is bypassed because `last-borrow-block` is never refreshed on borrow, defeating the oracle-frontrunning protection - (File: `mainnet/contracts/market/v0-market-vault.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `liquidate` function in `v0-4-market.clar` relies on the per-position field `last-borrow-block` to block liquidations that occur in the same block as a borrow, protecting a borrower from a flashloan-funded price manipulation followed by an instant liquidation. This mirrors the reported `airdropUpdateLastClaimTime` bug: a state field that a guard depends on is declared and read, but the write path that is supposed to refresh it on the relevant action (`borrow`, analogous to `airdropUserClaimPlx`) does not actually update it, so the guard becomes permanently trivially satisfied.

### Finding Description
`create` initializes a position with `last-borrow-block: u0` [1](#0-0) . The only mutator observed for refreshing a position's mask/timestamp on subsequent actions is `refresh`, which returns a partial merge object containing only `{ mask: mask, last-update: stacks-block-time }` — it does **not** include `last-borrow-block` [2](#0-1) . `insert`, by contrast, takes the *full* params struct including `last-borrow-block` [3](#0-2) .

`liquidate` explicitly depends on `last-borrow-block` for its "prevent same-block liquidation" oracle-frontrunning protection: `(same-block-check (asserts! (not (is-eq last-borrow-block stacks-block-height)) ERR-LIQUIDATION-BORROW-SAME-BLOCK))` [4](#0-3) . If the borrow path only ever merges through `refresh` (which omits `last-borrow-block`) rather than a full `insert` that sets `last-borrow-block` to the current `stacks-block-height`, the field would remain stuck at its initialization value (`u0`) forever, making the `is-eq last-borrow-block stacks-block-height` check effectively always `false` — i.e., the guard never blocks any liquidation, regardless of whether the borrow and liquidation occur in the same block.

This is structurally identical to the reported bug class: a guard variable (`airdropUpdateLastClaimTime` / `last-borrow-block`) that is checked against a live value but whose write side is disconnected from the action that is supposed to refresh it, causing the check to be permanently in the "unprotected" state.

**Uncertainty:** I could not confirm within the available tool budget whether the `borrow` function in `v0-4-market.clar` calls `insert` (which would correctly set `last-borrow-block`) or `refresh` (which would not) when updating an existing position's registry entry. This is the deciding fact for whether the vulnerability is real, and I was not able to locate/read the body of `borrow` before running out of iterations.

### Impact Explanation
If `last-borrow-block` is indeed never updated on borrow, the same-block liquidation protection is permanently disabled. An attacker could use a flashloan (as capital, not as the exploited logic itself) to manipulate an oracle price within a single block, borrow against or push a victim's position into apparent unhealthiness, and immediately liquidate it in the same block — extracting collateral at a favorable liquidation penalty that the guard was designed to prevent. This would constitute theft of a borrower's collateral (funds at rest), which is Critical severity under the given rubric.

### Likelihood Explanation
Likelihood is contingent on the unresolved code path (whether `borrow` uses `refresh` or `insert`/an equivalent full update). If confirmed, likelihood is high since the guard is a core, permissionless liquidation-path check that any external actor with oracle-manipulation capability (via flashloan capital) and access to the `liquidate` function could exploit repeatedly.

### Recommendation
Verify the `borrow` function's registry-update call. If it merges through `refresh` (or any path that omits `last-borrow-block`), change it to also set `last-borrow-block: stacks-block-height` on every borrow, either by extending `refresh` to include this field or by calling `insert` with the full updated params (mirroring the reported fix pattern of referencing the correct per-position field instead of a stale/unwritten one).

### Proof of Concept
1. Attacker (or victim, self-attack for demonstration) opens a borrow position; `last-borrow-block` is set/remains `u0` due to the suspected `refresh`-only update path.
2. In the same block, attacker manipulates the oracle price feed (potentially using flashloaned capital to move markets) to push the position's LTV above `ltv-liq-partial`.
3. Attacker calls `liquidate` in the same block. The check `(not (is-eq last-borrow-block stacks-block-height))` evaluates `(not (is-eq u0 <current-block>))`, which is `true`, so the assertion passes — the same-block guard fails to block the liquidation it was designed to block.
4. Attacker completes the liquidation and extracts collateral with the liquidation penalty before the price/position reverts to its true healthy state.

Given that I could not directly confirm the borrow-side registry update call within the tool budget, this finding should be treated as **unconfirmed pending verification of the `borrow` function body** in `v0-4-market.clar`/`v0-market-vault.clar`.
