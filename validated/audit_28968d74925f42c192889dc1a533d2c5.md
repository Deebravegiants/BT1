### Title
`findMatchingWithdrawal` matches same-token withdrawals by `assetId` only, causing status/txHash cross-attribution across `WithdrawalIdentifier`s in the same batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves a `WithdrawalIdentifier` to a specific PoA withdrawal record solely via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`. When a single NEAR transaction batches two or more withdrawals of the same token (same `assetId`, different `destinationAddress`/`amount`), every `WithdrawalIdentifier` sharing that `assetId` and `tx.hash` will resolve to the exact same (first) matching entry in `response.withdrawals`, regardless of which destination/amount it actually corresponds to.

### Finding Description
The broken equality: `describeWithdrawal(identifier_i).status/txHash` should equal the on-chain status/txHash of the specific withdrawal whose destination address and amount match `identifier_i.withdrawalParams`. Instead, it equals the status/txHash of `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` — i.e., the first entry in the API response array with a matching token, independent of destination or amount.

Code path: `IntentsSDK.waitForWithdrawalCompletion` → per-identifier `Bridge.describeWithdrawal` → `PoaBridge.describeWithdrawal` (poa-bridge.ts:313-343) → `getWithdrawalStatusWithRetry` (poa-bridge.ts:345-372), which calls `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })`. This call returns *all* withdrawals produced by that NEAR transaction hash (`response.withdrawals`), because a single NEAR tx can carry multiple `ft_withdraw`-style intents (a batch). `findMatchingWithdrawal` (poa-bridge.ts:418-427) then filters this array down using only `assetId` (`nep141:<near_token_id>`), with no comparison against `withdrawalParams.destinationAddress` or `amount`. The function's own docstring (poa-bridge.ts:409-417) explicitly states: "multiple withdrawals of the same token in a single transaction are not supported" and that matching would need to be redone by sorting by amount when that's fixed — confirming the code authors are aware the current implementation is unsound for this case, yet `IntentsSDK`/`PoaBridge.createWithdrawalIntents` and `supports()` place no guard preventing a caller from constructing and submitting such a batch.

Attacker/caller input: an integrator (or the SDK caller, who forwards user-supplied withdrawal requests) builds a batch with two withdrawal legs for `nep141:movement.omft.near` (e.g., different `destinationAddress`, potentially different `amount`) and submits it as one transaction. Nothing in `PoaBridge.supports`, `validateWithdrawal`, or `createWithdrawalIntents` rejects duplicate `assetId` legs in a batch — those functions validate each request independently, not batch composition. No batch dedup or per-leg amount/address matching exists in `poa-bridge.ts`.

Exploit flow: Two withdrawal intents for the same token are submitted in one tx, producing `WithdrawalIdentifier` at `index: 0` (destination A) and `index: 1` (destination B). After the transaction lands, `withdrawal_status` returns two entries for `near_token_id = movement`, one `COMPLETED` (for A, with its `transfer_tx_hash`) and one still `PENDING`/`SIGNED` (for B). When the integrator calls `describeWithdrawal` for identifier index 1 (destination B), `findMatchingWithdrawal` still returns the *first* array element matching the token — which, depending on API ordering, may be A's completed entry — reporting `{status: "completed", txHash: A's hash}` for a payout that actually went to destination A, not B. Existing guards (`validateAddress`, `compareAddresses`, `assert` checks) operate at withdrawal-creation time on a single leg and do not inspect batch siblings; they cannot catch this cross-attribution because it happens purely in the status-lookup/matching logic after submission.

### Impact Explanation
An integrator relying on `IntentsSDK.waitForWithdrawalCompletion`/`describeWithdrawal` for a specific `WithdrawalIdentifier` can be told that identifier B (its own leg, destined for address B) is `completed` with a `txHash`, when in fact that `txHash`/completion belongs to a different leg (destination A). This is a status/hash misreport: the integrator may release custody, credit a user, or mark a payout resolved based on the wrong leg's confirmation, matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. It affects any caller of the SDK that batches ≥2 withdrawals of the same PoA token in one transaction; it is repeatable for every such batch.

### Likelihood Explanation
Preconditions: the caller (an ordinary SDK user/integrator) must construct a batch containing two or more withdrawal legs for the same `nep141:*` PoA asset within a single NEAR transaction — a scenario the code's own comment says is unsupported but does not prevent. This costs the attacker/integrator nothing beyond forming such a batch (no privileged access needed) and requires only that the PoA relayer processes the legs at different times (near-certain in practice, since relayer settlement timing varies per leg). Feasibility is high given no validation blocks duplicate-`assetId` batches at `createWithdrawalIntents`/`supports()` time.

### Recommendation
In `findMatchingWithdrawal`, disambiguate among same-`assetId` candidates using additional fields available in the PoA status response (e.g., destination address and amount) rather than `assetId` alone; if the PoA API cannot yet distinguish them, `PoaBridge` should explicitly reject/throw when constructing a batch (`createWithdrawalIntents`/`supports`) that contains more than one withdrawal for the same `assetId` in the same transaction, so callers cannot silently rely on incorrect status reporting.

### Proof of Concept
Vitest plan (mock HTTP only, per `poa-bridge.test.ts` conventions):
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to return `{ withdrawals: [ { data: { near_token_id: "movement.omft.near", transfer_tx_hash: "0xA" }, status: "COMPLETED" }, { data: { near_token_id: "movement.omft.near", transfer_tx_hash: null }, status: "PENDING" } ] }` for `withdrawal_hash` matching a shared `tx.hash`.
2. Construct two `WithdrawalIdentifier`s sharing `tx.hash` and `assetId: "nep141:movement.omft.near"`, but with `withdrawalParams.destinationAddress`/`amount` set to "A" and "B" respectively (matching the two entries).
3. Call `poaBridge.describeWithdrawal(identifierA)` and `poaBridge.describeWithdrawal(identifierB)`.
4. Assert the equality that should hold: `describeWithdrawal(identifierB).status !== "completed"` (since B's real record is `PENDING`) and `describeWithdrawal(identifierA).txHash === "0xA"` while `describeWithdrawal(identifierB).txHash !== "0xA"`.
5. Current implementation fails this assertion: both calls return `{status: "completed", txHash: "0xA"}` because `findMatchingWithdrawal` ignores destination/amount and always returns the first `COMPLETED` entry matching the shared `assetId`.
