### Title
Relayer fee redirect/withdrawal signatures and balances bind only to `StateMachine`, omitting `consensus_state_id`, enabling cross-consensus-client replay/fund confusion - (File: modules/pallets/relayer/src/accumulate.rs, modules/pallets/relayer/src/withdrawal.rs)

### Summary
The relayer-fee pallet signs and stores nonces/fees keyed by the bare `StateMachine` enum (e.g. `Kusama(2000)`), never the full `StateMachineId` that additionally carries `consensus_state_id`. Hyperbridge's own core type explicitly documents that `consensus_state_id` exists "to prevent name clashes" between distinct consensus-client instances that otherwise report the same nominal `StateMachine` value. Because the signed payloads and the storage that tracks nonces/fees drop that disambiguating field, a signature or accrued balance that is only meaningful in the context of one consensus-client instance is fungible across any other consensus client configured to track the same `StateMachine` value — the exact bug class from CVE-2023-42806, where Hydra's snapshot signature omitted the head/instance identifier (`cid`) and thus could be replayed across different head instances sharing the same participant keys.

### Finding Description
`StateMachineId` is the canonical instance identifier in the ISMP core: it pairs a `StateMachine` with a `consensus_state_id` precisely because the same `StateMachine` value can be legitimately tracked by more than one consensus client instance: [1](#0-0) 

`StateMachineId`'s two fields are both required to uniquely identify a tracked chain instance: [2](#0-1) 

However, the relayer fee-accumulation and withdrawal flows drop the `consensus_state_id` component when constructing the signed message and when indexing on-chain state. `beneficiary_message` hashes only `(nonce, state_machine, beneficiary)`, where `state_machine` is `withdrawal_proof.source_proof.height.id.state_id` (the bare `StateMachine`, not the `StateMachineId`): [3](#0-2) [4](#0-3) 

The `Nonce` map that is supposed to make each redirect signature single-use is likewise keyed only by `(address, state_machine)`: [5](#0-4) 

The standalone `withdraw` flow has the same shape: the signed payload is `(nonce, dest_chain, beneficiary)` where `dest_chain` is a `StateMachine`, and `Nonce`/`Fees` are both keyed by `(address, StateMachine)`: [6](#0-5) [7](#0-6) 

This is structurally identical to the Hydra flaw: the signed authorization for moving value is scoped to an identifier that is *narrower* than the actual protocol instance identifier (`cid`/head-id in Hydra vs. `consensus_state_id` in Hyperbridge), while the thing that actually determines fund custody (participant set / trie root being proven against) can vary independently of that narrower identifier. Any host configuration where a `StateMachine` value (e.g. `Kusama(2000)`) is tracked by two different consensus clients/`consensus_state_id`s — which the protocol's own `StateMachineId` design anticipates as a normal occurrence requiring disambiguation, e.g. during consensus-client rotation/migration or coexistence of two clients for the same chain — causes `Fees[StateMachine][address]` to silently aggregate balances proven under either consensus client, and a `beneficiary_message`/`message` signature (and its single-use nonce) produced in the context of one `consensus_state_id` to be verifiable and spendable against a state-proof submitted under a different `consensus_state_id`.

### Impact Explanation
An attacker who is a legitimate relayer under one consensus-client instance for a `StateMachine` value, but who can also get a delivery attributed to them (or exploit a fee balance already accrued) under a second consensus client instance tracking the identical `StateMachine` value, can have their redirect/withdrawal signature or accumulated fee balance validated using the "wrong" instance's state root. This can cause fee funds credited under one consensus instance's provenance to be redirected/withdrawn using a signature or nonce state that was never actually bound to that instance, i.e. unauthorized redirection/draining of the treasury-held relayer fee balance — a concrete theft-of-funds path, matching the "Medium" severity bar (value misattribution / unauthorized fund movement) of the source CVE.

### Likelihood Explanation
This requires the host to configure (or migrate to) more than one consensus client instance tracking the same `StateMachine` identifier — a scenario the protocol's own `StateMachineId` type is built to handle and disambiguate, indicating it's an anticipated operational situation (e.g., consensus-client rotation, redundant/failover clients, or migration periods) rather than a purely theoretical one. It does not require any single admin/governance action beyond normal consensus-client lifecycle management, and once such a configuration exists, exploitation only needs a relayer/attacker to submit an `accumulate_fees`/`withdraw_fees` extrinsic with a proof drawn from the "other" consensus client.

### Recommendation
Bind the signed payloads in `beneficiary_message` and `withdrawal::message`, as well as the `Nonce` and `Fees` storage keys, to the full `StateMachineId` (including `consensus_state_id`) rather than the bare `StateMachine`, so that fee balances and redirect/withdrawal authorizations are scoped to the exact consensus-client instance whose state proof produced them.

### Proof of Concept
1. Host configures/migrates so that `StateMachine::Kusama(2000)` is trackable via two consensus clients with distinct `consensus_state_id` values `A` and `B` (a scenario `StateMachineId` is explicitly designed to disambiguate).
2. Relayer R delivers messages proven under consensus instance `A`, accruing `Fees[Kusama(2000)][R]` and obtaining nonce `n` at `Nonce[R][Kusama(2000)]`.
3. R signs `beneficiary_message(n, StateMachine::Kusama(2000), beneficiary)` intending it to be used together with a state proof from instance `A`.
4. Attacker (or R acting maliciously) submits `accumulate_fees`/`withdraw_fees` using a state proof drawn from instance `B` instead — verification succeeds because `verify_withdrawal_proof`/`Nonce`/`beneficiary_message` never check or embed `consensus_state_id`, only `StateMachine`, so the same signature and nonce validate against `B`'s data as well as `A`'s, and the shared `Fees[Kusama(2000)][*]` balance is redirected/withdrawn using authorization that was only ever intended for a proof rooted in instance `A`.

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
