### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the shop identity (`shop`), `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts `request.shop` as the tenant key for the handler without that value ever being covered by the HMAC check.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over that signable string and compares it to the `hmac` field: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from request headers with no cryptographic binding to the body/HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the tenant/routing identity handed to the app's webhook handler: [4](#0-3) 

This breaks the intended identity binding: **shop value authenticated by HMAC** should equal **shop value used as tenant key by the handler**. In this implementation, the HMAC authenticates only the byte content of the body — it says nothing about which shop the payload came from. Any header value, including `X-Shopify-Shop-Domain`, can be swapped without invalidating the signature, because it was never part of `to_signable_string`.

### Impact Explanation
An unprivileged internet user who has observed or captured one legitimate webhook delivery (body + valid HMAC) for any shop/topic combination — e.g., from a shop they control, or one leaked via logs/network capture — can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. Because `Registry.process` only checks the HMAC of the body and then passes the attacker-controlled `shop` header straight through to `WebhookMetadata`/the handler, the app's webhook handler will process (and likely persist/act on) attacker-supplied data under the identity of a different tenant. If the host application uses `data.shop` to look up sessions, scope database writes, or otherwise segment tenants (the documented and expected usage of `WebhookMetadata#shop`), this results in cross-tenant data confusion/injection — data attributed to shop B is actually attacker-controlled content that was only ever validated against shop A's (or the attacker's own) secret-derived HMAC of the body.

### Likelihood Explanation
The attacker only needs one legitimate webhook body+HMAC pair (trivially obtainable by installing the app on any shop they control, or observing any single delivery) and the ability to send an HTTP request with custom headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is required. The library itself performs no validation binding the header-derived `shop`/`topic`/`webhook_id` to the signed payload, so exploitation is a pure protocol-level replay/header-substitution, fully within reach of an unprivileged internet user.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the raw body before `Registry.process` trusts them for routing/tenant identification. At minimum, `to_signable_string` should not silently omit fields that are subsequently used as trust boundaries (tenant key) downstream.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B`, headers including `X-Shopify-Hmac-SHA256: H` (valid HMAC of `B` under the app's secret) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends a request to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `H` against `HMAC(secret, B)`; the shop header was never part of the signed content: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-supplied `victim-shop.myshopify.com` value and dispatches it to the registered handler as if it were an authentic webhook for the victim shop: [6](#0-5) 

*Note: I could not fully inspect `lib/shopify_api/utils/verifiable_query.rb` or `lib/shopify_api/webhooks/webhook_handler.rb` before tool access ended, so the exact downstream handling contract (`WebhookMetadata` field usage guarantees) is based on the constructor call shown in `registry.rb` rather than a full read of those files.*

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
