### Title
Attacker-controlled QR octal parameter can produce a value >7 and trigger an `assert_eq!` panic in `SweepConfiguration::parse_configuration_value` - ([File: src/plans/biometric_capture/focus_sweep.rs])

### Summary
The `From<biometric_capture::Plan> for Plan` conversion parses the QR-supplied `parameters` string with `u8::from_str_radix(parameter, 8)` [1](#0-0) , which happily accepts multi-digit octal strings (e.g. `"10"`, `"77"`, `"377"`) yielding `u8` values from 0–255, far beyond the 3-bit (0–7) contract implied by `WAVELENGTH_LUT`. `parse_configuration_value` then formats this value as binary and asserts the result is exactly 3 characters wide, which fails for any value ≥ 8 and panics [2](#0-1) .

### Finding Description
The QR user-data regex `QR_CODE_SIGNUP_EXTENSION` captures an arbitrary `parameters` group matching `[a-z0-9:]+` with no length or numeric-range restriction [3](#0-2) . This string is stored verbatim in `SignupExtensionConfig::parameters` [4](#0-3)  and flows unchanged into `biometric_capture::Plan::signup_extension_config`.

When the focus-sweep extension plan is constructed via `From<biometric_capture::Plan> for Plan`, the parameter is parsed as octal and defaulted to `1` only on outright parse failure (`unwrap_or(1)`); a successful octal parse of e.g. `"10"` (=8 decimal) or `"377"` (=255 decimal) passes through untouched [1](#0-0) . `SweepConfiguration::new` immediately calls `parse_configuration_value`, which formats the value with `format!("{configuration_value:0>3b}")` — for values ≥8 this produces 4+ binary characters, causing `assert_eq!(binary_repr.chars().count(), 3, ...)` to panic [2](#0-1) . `WAVELENGTH_LUT` itself is only defined for exactly 3 bit positions [5](#0-4) , confirming the 3-bit contract is violated by the octal parsing which permits an 8-bit range.

The same unchecked pattern exists in `mirror_sweep.rs`'s identical `From` impl [6](#0-5)  (verify path/line — mirrors the focus_sweep code exactly), while `overcapture.rs` guards this with an explicit `parse_u8_octal` helper that presumably bounds the value (not fully verified here) [7](#0-6) .

No validation exists at the QR-parsing layer (`user.rs`) or at the `biometric_capture::Plan` construction boundary to reject out-of-range parameters before they reach the panicking assertion — the code's own `TODO` comment acknowledges this gap ("Move parsing of configuration flag to QR code scanning phase -> Handle/Fail early") [8](#0-7) .

### Impact Explanation
A crafted QR parameter that is valid octal syntax but represents a decimal value ≥8 causes an unconditional Rust panic inside the signup extension setup path. Depending on how panics propagate in the async signup task (not fully confirmed from available code — no `catch_unwind` boundary was located around this call), this can abort the in-progress signup task or the whole `orb-core` process, denying service to the current signup. This matches a signup-availability / DoS-class impact.

### Likelihood Explanation
Reachability is gated: the QR regex that populates `parameters` (`QR_CODE_SIGNUP_EXTENSION`) is only compiled under `#[cfg(any(feature = "internal-data-acquisition", test))]` [9](#0-8) , and the extension config is only honored when **both** the operator QR and the user QR request a signup extension mode [10](#0-9) . This means exploitation requires the orb binary to be built with the `internal-data-acquisition` feature (used for internal data-collection/QA orbs, not the standard consumer build) and an operator-side QR that also opts into the extension. Under those preconditions, triggering the panic is trivial and fully deterministic (any octal string ≥ `"10"`), but the "unprivileged attacker with only QR control" threat model in the general/production build is not satisfied without operator/build cooperation.

### Recommendation
Validate and clamp `configuration_value` to the 0–7 range immediately after parsing (e.g., `.filter(|v| *v <= 7)` before `unwrap_or(1)`), and replace the `assert_eq!` in `parse_configuration_value` with a fallible check (`Result`/`Option`) that fails closed (defaults to a safe wavelength set or rejects the signup) instead of panicking. Apply the same fix to the identical pattern in `mirror_sweep.rs`.

### Proof of Concept
Unit test in `focus_sweep.rs`:
```rust
#[test]
fn parse_configuration_value_does_not_panic_on_out_of_range_octal() {
    for raw in ["10", "77", "377", "0", "7"] {
        let value = u8::from_str_radix(raw, 8).unwrap_or(1);
        let _ = SweepConfiguration::new(value); // should not panic; should fail closed for value > 7
    }
}
```
Expected (fixed) behavior: values decoding to >7 are rejected/clamped before reaching `parse_configuration_value`, so no `assert_eq!` panic occurs; a fuzz test feeding arbitrary QR `parameters` strings through the `From<biometric_capture::Plan> for Plan` path should assert no panic for any input string.
