This confirms the vulnerability in the Tron variant of `IntentGatewayV2.sol`. Both `withdraw()` and the `SweepDust` handler use raw low-level `.call()` with the `IERC20.transfer.selector` and only check the boolean `success` returned by the low-level call — they never decode/verify the ABI-encoded return data. The rest of the contract (and the escrow/deposit paths) consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which correctly validates both call success and, when present, a `false` return value.

### Title
Unsafe raw `IERC20.transfer` calls in `withdraw()`/`SweepDust` allow silent transfer failures to be treated as success, permanently freezing escrowed user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` escrows user input tokens via `SafeERC20.safeTransferFrom` throughout `placeOrder`/`fillOrder`, but the escrow-release path `withdraw()` and the governance `SweepDust` handler release tokens with a raw low-level `.call()` targeting `IERC20.transfer.selector`, checking only that the external call itself did not revert (`success`), never inspecting/decoding the return data as `SafeERC20` does. [1](#0-0) [2](#0-1) 

### Finding Description
On the Tron chain, TRC20 tokens are commonly non-standards-compliant in exactly the way described by the referenced report: some tokens' `transfer`/`transferFrom` return `false` on failure instead of reverting, and some return no data at all. A raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only reports `success = true` when the EVM call itself did not revert — it says nothing about whether the token's internal logic actually moved value or returned `false`. `SafeERC20.safeTransfer` protects against this by additionally requiring that, if return data is present, it decodes to `true`.

In `withdraw()`, this raw pattern is used to pay out escrowed input tokens and accumulated fee-token balances to the beneficiary (solver on `EscrowReleased`, or user on `EscrowRefunded`), and the escrow accounting `_orders[body.commitment][token] -= amount;` (and `delete _orders[body.commitment][TRANSACTION_FEES];` for fees) is unconditionally decremented/cleared immediately after the raw call, regardless of whether the token actually transferred value. [3](#0-2) 

The same unsafe pattern is used in the `SweepDust` governance-request handler that runs on `onAccept` when the message kind is `RequestKind.SweepDust`. [4](#0-3) 

This is inconsistent with every other transfer path in the same contract and in the non-Tron `IntentGatewayV2.sol`/`IntentsBase.sol`, which use `SafeERC20.safeTransferFrom`/`safeTransfer` for escrow deposits and releases. [5](#0-4) [6](#0-5) 

### Impact Explanation
If a token used as an order input on Tron returns `false` on a failed `transfer` (a well-documented non-conforming ERC20/TRC20 behavior), `withdraw()` will:
1. Report `success = true` from the low-level call (the call target executed without reverting).
2. Decrement the internal escrow accounting `_orders[body.commitment][token] -= amount` as though the beneficiary was paid.
3. Mark the order `_filled[body.commitment] = beneficiary` and emit `EscrowReleased`/`EscrowRefunded`.

The beneficiary (solver completing a cross-chain fill, or user receiving a refund) never actually receives the tokens, yet the protocol's internal state now reflects the escrow as spent. The tokens remain permanently stuck in the contract with no accounting entry pointing to them, and the intended recipient has no funds and no further recourse since the order is already marked filled/refunded. This is a direct, unauthorized loss/freezing of escrowed user funds — matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Reachable by any solver/user going through the ordinary cross-chain settlement or refund flow (`onAccept` → `withdraw`) or by governance dispatching a `SweepDust` request — no privileged or malicious actor is required beyond someone choosing (or being tricked into accepting) a non-standard TRC20 token as an order input, which is common on the Tron network the contract is specifically deployed for. Given the contract already anticipates fee-on-transfer and non-standard token behavior elsewhere (using `SafeERC20` and balance-delta accounting in `placeOrder`), the omission specifically in `withdraw()`/`SweepDust` is a straightforward oversight rather than a theoretical edge case.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (the contract already imports and uses `SafeERC20` elsewhere via `using SafeERC20 for IERC20;`), so that both call failure and non-standard `false`-return failures are treated as reverts, keeping escrow accounting consistent with actual token movement.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a TRC20-style token `T` whose `transfer(address,uint256)` returns `false` (does not revert) when the sender's balance check fails internally due to a bug, blacklist, or paused state, instead of reverting.
2. A user places a cross-chain order with `T` as an input; tokens are escrowed via `safeTransferFrom` (this succeeds normally on deposit).
3. A solver fills the order on the destination chain and the `RedeemEscrow` settlement message is delivered back to the source chain, invoking `onAccept` → `withdraw(body, false)`.
4. Suppose token `T` is later paused/blacklists the gateway contract (or hits an internal invariant) such that `transfer` now returns `false` without reverting. `withdraw()`'s raw `.call()` still reports `success = true` because the low-level call did not revert.
5. `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased` is emitted — but the solver's TRC20 balance never increased. The escrowed `T` tokens are now stranded in the gateway with no recorded claim, while the solver (or refunded user) receives nothing.
