## Title
Missing zero-address check in `WrappedHyperFungibleToken.onAccept` permanently burns native ETH when a bridged transfer's recipient is `address(0)` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.onAccept` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.onAccept`) decodes the destination-chain `beneficiary` from the cross-chain message and, when the wrapped underlying is WETH, unwraps it and pushes native ETH to that address via a raw low-level `call`. Unlike an ERC20 `transfer`, a low-level `call{value:}` to `address(0)` (or any account with no code) always returns `success = true`, so no zero-address validation ever triggers. If `beneficiary` decodes to `address(0)`, the contract unwraps the WETH and irrecoverably sends the native ETH to the zero address, with no fallback and no possibility of retrieval.

### Finding Description
`HyperFungibleToken.Message.to` (the destination recipient) is attacker/user-supplied on the source chain via `SendParams.to`, and is never validated against `address(0)` in `send()`/`_buildDispatchPost()`. [1](#0-0) 

On delivery, `onAccept` derives `beneficiary` via `_toAddr(message.to)`, which only checks the byte length (must be 20), not whether the resulting address is zero: [2](#0-1) 

When `_isWeth` is true, the contract unwraps WETH and attempts a native push before falling back to an ERC20 transfer: [3](#0-2) 

`beneficiary.call{value: message.amount}("")` to `address(0)` succeeds (returns `sent = true`) because calling a non-contract address with no bytecode is always successful at the EVM level, regardless of the target's ability to actually use the funds. Because `sent == true`, the `if (!sent)` re-wrap/ERC20-fallback branch (which would have reverted on `address(0)` via `IERC20.safeTransfer`'s standard OZ zero-address check) is never reached. The function proceeds to emit a `Received` event claiming successful delivery, while the ETH is permanently lost — nobody controls `address(0)`.

This mirrors the reported bug class: a bridge finalize/mint/unlock path fails to reject `address(0)` as early as possible, and the "transfer succeeds" path silently completes instead of reverting, resulting in loss of funds rather than a clean revert that would allow recovery (e.g. via the ISMP timeout mechanism, which cannot fire since the request is marked delivered, not timed out).

By contrast:
- The non-WETH ERC20 branch (`IERC20(_underlying).safeTransfer(beneficiary, ...)`) is safe because standard OpenZeppelin ERC20 `_transfer` reverts on `to == address(0)`.
- The burn/mint `HyperFungibleToken.onAccept` (`_mint(beneficiary, message.amount)`) is also safe because OZ `ERC20._mint` reverts on `address(0)`. [4](#0-3) 

Only the WETH-unwrap-and-push code path in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lacks any protection, because it relies on a raw `call` whose success semantics don't reflect fund deliverability.

### Impact Explanation
Native ETH bridged through a WETH-backed `WrappedHyperFungibleToken` deployment is permanently and irrecoverably lost if the destination `to` field resolves to `address(0)` — whether from a user/integrator error (e.g., a bug in a calling contract that leaves `to` unset/zero) or from a malformed/malicious relay of a message whose `to` field is attacker-influenced through composed calldata. Once delivered, the request is marked as fulfilled (no timeout path is triggered), so the standard ISMP refund-on-timeout safety net does not apply. This is a permanent freezing/loss-of-funds bug in the token bridge's unlock path.

### Likelihood Explanation
The relayer, `onAccept` caller, and message body only need to be a legitimately verified ISMP POST request from the registered peer contract — no privileged role is required to trigger this beyond the ordinary bridging flow (send → relay → onAccept). Any account (via its own `send()` call, or a composing contract with a bug that defaults `to` to `address(0)`) can cause funds routed through it to be destroyed. It requires `_isWeth == true` for the specific `WrappedHyperFungibleToken` deployment.

### Recommendation
Validate `beneficiary != address(0)` at the top of `onAccept` (and `refundee != address(0)` in `onPostRequestTimeout`) before attempting any transfer, reverting early with a dedicated error (e.g. `InvalidBeneficiary()`), consistent with how `HyperFungibleToken`'s `_mint` and the non-WETH ERC20 branch already behave. Alternatively, treat `call` success alone as insufficient and additionally require `beneficiary != address(0)` before the native-push branch.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_isWeth = true`, `_underlying = WETH`.
2. Register a valid peer chain/source module.
3. On the source chain, a user calls `send()` with `params.to = abi.encodePacked(address(0))` (20 zero bytes) and locks WETH/ETH.
4. The relayer delivers the resulting POST request to the destination chain's `onAccept`.
5. `_toAddr(message.to)` returns `address(0)`; `IWETH(_underlying).withdraw(message.amount)` unwraps WETH to native ETH held by the contract; `address(0).call{value: message.amount}("")` returns `success = true` (this is standard EVM behavior for a plain value transfer to any address, including ones with no code).
6. The `if (!sent)` fallback never executes; the WETH-backed ETH is now held by nobody (sent to `address(0)`), `Received` event fires as if delivery succeeded, and the funds cannot be recovered by any party.

    function _toAddr(bytes memory b) internal pure returns (address addr) {
        if (b.length != 20) revert InvalidAddress(b.length);
        // casting to 'bytes20' is safe because we already checked length
        // forge-lint: disable-next-line(unsafe-typecast)
        return address(bytes20(b));
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
