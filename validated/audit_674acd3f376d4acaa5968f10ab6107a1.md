### Title
Cross-tenant webhook spoofing via unauthenticated `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity (`shop-domain` header) used by `ShopifyAPI::Webhooks::Registry.process` to route/attribute the webhook payload is never covered by that signature. Any unprivileged party who can obtain one genuine, HMAC-valid webhook (e.g. by installing the app on their own store) can replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header, causing the host application to process the payload as if it belonged to a different (victim) tenant.

### Finding Description
`Request#hmac`/`#to_signable_string` binds the HMAC check exclusively to `@raw_body`: [1](#0-0) 

`#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC (`Utils::HmacValidator.validate(request)`, which itself only ever signs `to_signable_string` == the raw body) and then unconditionally forwards `request.shop` into `WebhookMetadata`, which the app's registered handler uses as the tenant/session key: [3](#0-2) 

Because the same `Context.api_secret_key` is shared across every shop that has installed the app, the HMAC computed over a given body is identical no matter which shop the body "belongs to." An attacker who installs the app on their own store can generate a genuine webhook (valid HMAC, since it's their own legitimate traffic), then simply swap the `shop-domain` header to a target/victim shop's domain before delivering it to the app's public webhook endpoint. `Utils::HmacValidator.validate` (which only ever checks `verifiable_query.to_signable_string`, i.e. the body) will still pass: [4](#0-3) 

The library provides no mechanism (and no documented recommendation in this gem) to bind the header-derived `shop` to the HMAC-authenticated bytes, so any host application that trusts `WebhookMetadata#shop` (as the gem's own docs/tests imply is the intended usage) is fed a shop identity that was never actually authenticated.

### Impact Explanation
This breaks the identity binding "shop authenticated (via HMAC) versus shop used as the session/tenant key." A host application that stores or routes webhook data keyed by `WebhookMetadata#shop` can be tricked into attributing another store's legitimately-signed-by-the-app-secret webhook body to an arbitrary victim shop domain, resulting in cross-tenant data confusion/injection — an unprivileged attacker (any merchant who installs the app) can inject data attributed to a shop they do not own.

### Likelihood Explanation
High for any host application built on this gem that uses `data.shop` from `WebhookMetadata` for tenant routing/storage (which is the pattern demonstrated in this gem's own tests, e.g. `handler.handle` asserting on `data.shop`). No secret, access token, or privileged access is required — only the ability to install the app on an attacker-controlled store and forge an HTTP request with a modified header value.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signable string that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the request body before it is handed to webhook handlers. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must be independently validated against a known/installed shop record before use.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, receiving a legitimate webhook: body `{"id":1}}`, with `x-shopify-hmac-sha256` computed by Shopify using the shared `api_secret_key`.
2. Attacker resends this exact body/HMAC pair to the app's webhook endpoint, replacing header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate` recomputes HMAC over the raw body only and it matches (same secret, same body) — see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:10-38`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the host app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though `victim-shop.myshopify.com` never actually sent this webhook.
