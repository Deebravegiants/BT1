### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the shop identity attribute (`shop-domain` header) that the gem hands to the webhook handler is never part of the signed material. An attacker who can produce (or replay) any validly-signed webhook body can attach an arbitrary `shop-domain` header and have `Registry.process` attribute the event to a shop it did not originate from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the raw body — it never touches `shop`: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` that is handed to the app's handler as the tenant identifier: [5](#0-4) 

The identity binding that should hold is:
`shop that produced/authorized this HMAC-signed body == shop attributed to WebhookMetadata.shop`

Because only the body bytes are verified and the `shop-domain` header is parsed independently and trusted, this equality is never enforced. A request whose HMAC was computed for shop A's body but whose `shop-domain` header is set to shop B still passes `Utils::HmacValidator.validate`, and the handler is invoked believing the event belongs to shop B. This is structurally the same class of bug as the report's "verify one thing, act on another, no equality check enforced" pattern: the report is about acting on an untrusted `transferOut()` return value; here the gem acts on an untrusted `shop` field that was never covered by the cryptographic check that is supposed to authenticate the whole request.

### Impact Explanation
Apps built on this gem rely on `WebhookMetadata#shop` (populated straight from the unsigned header) as the tenant key for storing/updating per-shop state (e.g., disabling a shop on `shop/redact`, updating shop-scoped records for `orders/updated`, etc.), because the gem's own `Registry.process` presents this field as already-authenticated (it runs only after `Utils::HmacValidator.validate` succeeds). Since `shop` isn't bound to the HMAC, an attacker who can obtain any one validly-signed webhook body (e.g. from their own shop, which they legitimately receive webhooks for) can relabel it to point at a victim shop domain, causing cross-tenant data confusion/corruption in any downstream handler that trusts `data.shop`. This matches the High-impact category of "scope or expiry check bypass" / identity-binding bypass across tenants.

### Likelihood Explanation
Likelihood is high for any actor who legitimately receives webhooks for at least one shop (e.g. operates their own dev store or a store where the app is installed) — no secret material (`api_secret_key`) is required to exploit this, only the ability to capture one legitimately-signed body and resend it with a modified header, since the header is completely outside the signed scope.

### Recommendation
Include the `shop-domain` header (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-covered material, or independently bind/validate that the `shop-domain` header matches an expected/authorized shop (e.g. compare against a `session`/registration record) before constructing `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop` as authenticated data derived from HMAC verification.

### Proof of Concept
1. Shop A's app receives a legitimate webhook: body `{}` with header `x-shopify-shop-domain: shop-a.myshopify.com` and a correctly computed `x-shopify-hmac-sha256` for that body.
2. Attacker resends the identical body and HMAC, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: tampered_headers)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because the signed material (`raw_body`) is unchanged.
4. `ShopifyAPI::Webhooks::Registry.process(request)` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act on victim-shop data/state using an attacker-controlled, unauthenticated shop identifier.
