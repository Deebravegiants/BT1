### Title
Cross-chain audience bypass in IntentGateway's peer authentication via `instance()` default fallback allows theft of escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The IntentGateway's `_authenticate()` / `authenticate()` peer-check (used to gate `RedeemEscrow` and `RefundEscrow` message processing in `onAccept`) validates the `PostRequest.from` field against `instance(request.source)`. When no explicit `Deployment` has been registered for a given source `StateMachine`, `instance()` falls back to returning `address(this)` instead of rejecting the lookup. Because IntentGateway is deployed deterministically (the same contract address across EVM chains), any state machine that Hyperbridge is configured to accept requests from — but for which governance has not yet called `NewDeployment` — is implicitly treated as an authenticated peer as long as the forged `from` field equals the local contract's own address. This mirrors the Keycloak audience-bypass bug class: a message whose "audience" (the registered peer gateway) was never explicitly established is nonetheless accepted as if it came from the trusted resource, letting an unprivileged actor exfiltrate/redirect funds meant only for the legitimate cross-chain flow.

### Finding Description
`authenticate()` (mirrored as `_authenticate()` in `ExtrinsicIntents.sol`) is the sole gate protecting `RedeemEscrow`/`RefundEscrow` processing in `onAccept`: [1](#0-0) [2](#0-1) 

The `instance()` lookup that backs this check defaults to `address(this)` whenever no `Deployment` has been registered for the claimed `request.source`: [3](#0-2) 

Because `authenticate()` only compares `request.from` (an arbitrary attacker-controlled 20 bytes taken from the incoming, otherwise-legitimately-verified `PostRequest`) against `instance(request.source)`, and `instance()` silently substitutes the local contract's own address for any state machine id that was never explicitly registered via `NewDeployment`, the check degrades to "is `from == address(this)`" for every unregistered chain — rather than rejecting the message outright. `NewDeployment` registration itself is gated only by requiring the request to originate from Hyperbridge (`request.source == hyperbridge()`), which does not retroactively lock down state machines that governance has not yet reached: [4](#0-3) 

Since IntentGateway deployments are performed deterministically (CREATE2) to be at identical addresses on every EVM chain, an attacker who deploys a look-alike (or any) contract at that same address on a still-unregistered chain — a chain Hyperbridge's consensus clients already support proving state for, but that the IntentGateway operator hasn't explicitly whitelisted with `NewDeployment` — can dispatch a real, provable ISMP `PostRequest` with `from = address(this)` from that chain. This satisfies `authenticate()`'s check on the destination chain by falling through the `address(this)` default, letting an unprivileged actor forge `RedeemEscrow`/`RefundEscrow` messages that are processed as if they came from the genuine peer gateway.

### Impact Explanation
A successful forgery lets the attacker call `_withdraw()` for arbitrary `WithdrawalRequest` commitments, releasing escrowed input tokens and fee-token balances that belong to legitimate solvers/users to an attacker-chosen address — direct theft of escrowed funds: [5](#0-4) 
This satisfies "concrete theft of funds" — the vulnerability is reachable by a single relayed/dispatched ISMP message from any unprivileged actor controlling a not-yet-registered source chain.

### Likelihood Explanation
Exploitability depends on the operational reality that governance registers IntentGateway peer deployments (`NewDeployment`) lazily/per-chain, while Hyperbridge's underlying consensus clients may already support many more chains than have registered gateways. Any gap between "chains Hyperbridge can verify state for" and "chains that have had `NewDeployment` called" is directly exploitable, and since the gateway's address is deterministic by design, the attacker does not need to compromise any existing deployment — only deploy on an unregistered but Hyperbridge-supported chain. This is a realistic, moderate-likelihood misconfiguration window rather than a purely theoretical one, matching the Medium severity of the analog.

### Recommendation
Change `instance()`'s default behavior so that an unregistered state machine causes `authenticate()` to revert (e.g., add an explicit "registered" flag/mapping separate from the zero-address sentinel, and have `authenticate()` treat "not registered" as `Unauthorized`/`UnknownInstance` rather than falling back to `address(this)`). Only self-referencing same-chain messages (where `request.source` genuinely equals the local chain id) should be allowed to match `address(this)`.

### Proof of Concept
1. Identify a state machine `X` supported by Hyperbridge's consensus clients on the destination chain, for which the deployed IntentGateway has not yet had `NewDeployment` called (`instance(X)` returns `address(this)`).
2. On chain `X`, deploy any contract at the IntentGateway's deterministic CREATE2 address (or otherwise obtain code at that exact address before the legitimate team does).
3. From that contract, dispatch a genuine ISMP `PostRequest` to the destination IntentGateway with `body = RequestKind.RedeemEscrow || WithdrawalRequest{...attacker-chosen commitment/beneficiary...}`, `source = X`, `from = <deterministic address>`.
4. Relay the request through Hyperbridge's normal handler (`HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IntentGatewayV2.onAccept`); the state/membership proof verifies because the request truly exists on chain `X`.
5. `authenticate()` computes `instance(X) == address(this)` (fallback) `== module` (the deterministic address used as `from`), passes, and `_withdraw()` releases escrowed tokens to the attacker.

     * @dev Authenticates an incoming cross-chain post request by verifying that the
     * sender module matches the registered gateway instance for the source chain.

     * @param request The incoming post request to authenticate.
     */
    function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }
