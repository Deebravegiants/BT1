### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant) value used by `Registry.process` to route and attribute the webhook is read from an HTTP header that is excluded from that signature. An attacker who can obtain one valid `(raw_body, hmac)` pair — e.g. by owning a shop that installs the app and observing its own webhook deliveries — can replay that exact body/HMAC pair while substituting a different `Shopify-Shop-Domain` header, and the request will still pass HMAC validation and be processed as if it belonged to the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it with the `hmac` value from the same object: [1](#0-0) 

For webhooks, `Webhooks::Request` implements `VerifiableQuery` such that the signable string is exactly the raw body, and nothing else: [2](#0-1) 

`shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a field that is never part of `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity when dispatching to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop)`, i.e. the authenticated bytes should cover the tenant claim that downstream code relies on. Instead the equality actually enforced is `hmac == HMAC(secret, body)` while `shop` is parsed independently and unauthenticated — the same "field acted on but not covered by the signature" pattern as the escrow-NFT report, where the guarding structure (buyPrice/auction) didn't cover the asset actually transferred.

### Impact Explanation
Because `shop` is excluded from the signed bytes, any holder of one valid `(raw_body, hmac)` pair for a given topic can present it to the app's webhook endpoint with an arbitrary `Shopify-Shop-Domain` header and have `Utils::HmacValidator.validate` accept it. `Registry.process` will then hand the handler a `WebhookMetadata` claiming a different shop than the one that actually produced/authorized the payload: [5](#0-4) 
Any app logic that uses `WebhookMetadata#shop` to select a tenant's session/access token, mutate tenant-scoped data, or fulfil GDPR "redact" requests would act on the wrong tenant — a cross-tenant data/action confusion crossing the multi-tenant boundary this gem is meant to enforce.

### Likelihood Explanation
The attacker only needs a valid `(body, hmac)` pair for any topic, which is trivial to obtain: install the app on a shop the attacker controls (or otherwise observe one legitimate webhook delivery, e.g., via logs), then replay that exact body with a forged shop header to the same public endpoint. No `api_secret_key`, access token, or privileged access is required — only the ability to send arbitrary HTTP requests to the app's already-public webhook route, which is squarely within an unprivileged internet user's reach.

### Recommendation
Bind the tenant identity into the signed material (or otherwise cryptographically tie `shop` to the verified payload), e.g. by including `shop-domain` in `to_signable_string`, or by requiring the app to cross-check `request.shop` against the shop embedded in the (already-signed) body/topic-specific resource before trusting it for tenant-scoped operations. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a tenant selector without additional verification (e.g., confirming the shop has an active, matching session and that the payload's own resource IDs belong to that shop).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — this still matches, since `raw_body` is unchanged: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload originated from `attacker-shop.myshopify.com`, causing any tenant-scoped logic keyed on `shop` to act on the wrong tenant.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
