### Title
Non-embedded apps trust an unsigned, predictable session cookie value as the identity key, allowing session-ID forgery and cross-tenant access - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `SessionUtils.current_session_id` accepts the raw `shopify_app_session` cookie value as the session identifier with **no cryptographic verification**, and that identifier is itself a deterministic, publicly-guessable string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`) derived only from the shop's `.myshopify.com` domain. [1](#0-0)  Because the attacker fully controls the `Cookie` header of their own requests, they can set this header to the predictable session key for any target merchant and have the host app resolve/load that merchant's stored offline session (and its access token) instead of their own.

### Finding Description
The claimed invariant is: `shop authenticated by signature/JWT == shop interpolated into session id == shop used as request host`. In the non-embedded branch of `current_session_id`, there is no signature or JWT step at all — the cookie is "the only accepted credential": [2](#0-1) 
`cookie_session_id` simply returns `cookies[SESSION_COOKIE_NAME]` verbatim as the session id, with zero validation that it corresponds to the requesting shop: [3](#0-2) 

The value stored in that cookie originates from `Oauth.validate_auth_callback`, which — after a successful HMAC-validated callback for shop A — sets the cookie to `session.id`: [4](#0-3) 
and `session.id` for offline sessions is computed by the fully deterministic, secret-free formula `offline_session_id(shop) = "offline_#{shop}"`, or for online sessions `jwt_session_id(shop, user_id) = "#{shop}_#{user_id}"`: [5](#0-4) 

Because the identifier contains no HMAC/signature and is a plain string concatenation of public information (the merchant's shop domain, which is exposed in URLs, webhooks, app listings, etc.), an attacker who knows or guesses a victim shop's `.myshopify.com` domain can compute `"offline_victim-shop.myshopify.com"` themselves and send it as their own `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` header. The gem hands this value straight back to the host app as "the current session id" with no check that it matches the shop actually making the request (there is no host/shop-vs-session-id cross-check anywhere in this file or in `Oauth`). If the host app then loads the session from its `SessionStorage` using this key — which is exactly the documented usage pattern for this utility — it retrieves the victim merchant's real `Session` object, including its `access_token`, and will proceed to serve the attacker's request as if it were an authenticated request from the victim shop.

None of the existing guards prevent this: `HmacValidator.validate` and the OAuth `state` check only protect the OAuth callback step, not this later cookie-based resumption path; `JwtPayload`'s `aud` check is irrelevant here since no JWT is presented for non-embedded flows (the `if Context.embedded?` branch is skipped entirely); and `Context.embedded?` merely selects the branch that has no signature check at all.

### Impact Explanation
An attacker who knows a target merchant's shop domain (public, guessable, enumerable) can construct the exact session key for that merchant's offline session and, by supplying it as their own request cookie, get the host application to load and act on that merchant's stored `Session`/`access_token` on their behalf. This is a cross-tenant break: one shop's request (the attacker's) reads or mutates another merchant's data via the victim's access token. The blast radius is every non-embedded app instance built on this gem where the resolved `current_session_id` is used to look up sessions without an additional shop-vs-session cross-check, and it is repeatable against any victim shop whose domain is known.

### Likelihood Explanation
Preconditions: app configured `is_embedded: false` (explicitly required by the exploit scenario) and using cookie-based session resumption as documented. Attacker cost is trivial — no secrets, tokens, or prior access to the victim required; only the public shop domain name, which is either guessable (`{store-name}.myshopify.com`) or trivially discoverable. The attack requires no interaction with the victim and is fully repeatable against arbitrary shops known to the attacker, making this highly feasible for any internet attacker per the stated threat model.

### Recommendation
Do not use raw, unsigned, deterministically-derived strings as bearer session identifiers delivered via cookies. Either (a) sign/HMAC the cookie value with the app's `api_secret_key` and verify the signature in `cookie_session_id`/`current_session_id` before trusting it, or (b) after resolving the session id and loading the session from storage, verify that the loaded session's `shop` matches the shop of the actual current request (host/shop param) before using its credentials, rejecting mismatches.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (additional test)
def test_offline_session_id_is_predictable_and_accepted_without_verification
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  victim_shop = "victim-shop.myshopify.com"
  forged_cookie_value = "offline_#{victim_shop}" # attacker-computable, no secret needed
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  resolved_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # The gem returns the attacker-forged value verbatim, with no signature check,
  # matching exactly the key under which the victim's real offline session
  # (with its access_token) is stored by the host app.
  assert_equal(forged_cookie_value, resolved_id)
  assert_equal(ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop), resolved_id)
end
```
This demonstrates that `current_session_id`/`cookie_session_id` performs no verification binding the returned identity to the actual requesting shop, and that the identity string is fully attacker-computable from public information.
