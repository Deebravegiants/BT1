## Finding: `CallDispatcher.dispatch` performs privileged, unauthenticated calls against whatever balance is currently parked in the contract — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single, shared, permissionless contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute user-supplied calldata against tokens that are briefly parked in its balance during predispatch/postdispatch or calldata-execution flows. `dispatch()` has no caller restriction at all: it executes any `Call[]` with the dispatcher's own funds and code-execution rights, without checking who is calling it or whose funds are being moved. This mirrors the Dropbear class of bug — a privileged/shared forwarding operation is carried out on behalf of whoever asks, without checking that the caller is entitled to the resource being acted on (the functional equivalent of skipping the `SO_PEERCRED` check before forwarding to a root-owned socket).

### Finding Description
`CallDispatcher.dispatch` is declared with no modifier: [1](#0-0) 

It simply iterates the caller-supplied `Call[]` and executes each against `to` with the dispatcher's own native/ERC20 balance — there is no check that `msg.sender` is `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken`, and no tracking of which order/message a balance belongs to.

The dispatcher is used as a transient token holder across multiple apps:
- `HyperFungibleTokenUpgradeable.onAccept` mints tokens directly to a beneficiary (which the documented pattern sets to the `CallDispatcher` address itself, "so the swap can spend the tokens") and then invokes `ICallDispatcher(_dispatcher).dispatch(message.data)` with attacker/sender-controlled `data`: [2](#0-1) 
- `WrappedHyperFungibleTokenUpgradeable.onAccept` follows the identical unlock-then-dispatch pattern: [3](#0-2) 
- `IntentGatewayV2` transfers predispatch/order assets to the same shared `dispatcher` address and then calls `ICallDispatcher(dispatcher).dispatch(...)`, sweeping back only the tokens explicitly enumerated in `order.inputs`: [4](#0-3) 

The official documentation acknowledges that the dispatcher "holds tokens temporarily during execution" and specifically warns integrators to use exact-amount approvals rather than unlimited allowances "since the dispatcher contract holds tokens temporarily" — confirming the intended invariant that no value is meant to persist there: [5](#0-4) 

Because the mint-to-dispatcher/unlock-to-dispatcher, then call-execution flows are driven entirely by user-supplied `Call[]`/`data`, any of the following commonly occurring conditions leaves a nonzero balance sitting in the shared `CallDispatcher` after the triggering transaction completes:
- A cross-chain `send()` with `to = CallDispatcher` whose `data` swap consumes less than the full minted/unlocked amount (partial fill, slippage-bounded swap, fee-on-transfer token, or calldata that simply doesn't forward 100% of the balance).
- Multi-hop `predispatch`/`postdispatch` calls in `IntentGatewayV2` that produce an intermediate or byproduct token not listed in `order.inputs`/`order.output.assets`, so the sweep-back loop (which only iterates the declared token set) never reclaims it.
- Excess native ETH forwarded via `Call.value` that a downstream router doesn't fully consume, retained by the dispatcher's unconditional `receive()`.

Because `dispatch()` is unauthenticated and untied to any specific order/message, **any address** can call `CallDispatcher.dispatch()` directly, at any later block, with a `Call` that transfers out whatever balance is currently sitting in the shared contract — regardless of which user's operation left it there.

### Impact Explanation
This is concrete, permanent theft of funds belonging to a prior HFT/WHFT recipient or IntentGatewayV2 order participant. The dispatcher is a single shared instance across the deployment (used by every `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` on a chain), so any leftover balance — dust, unconsumed calldata-execution output, or excess native token — is globally exposed to whichever unprivileged account calls `dispatch()` first. Given the medium CVSS of the Dropbear analog (`AV:N/AC:L/PR:L/UI:N/C:L/I:L/A:N`), the same "any authenticated-but-unprivileged party can reach privileged, unchecked forwarding" pattern applies here: an unprivileged message dispatcher/relayer/user who observes a residual balance can extract it by simply invoking a public function with no other action required.

### Likelihood Explanation
Medium: it requires an execution path that leaves nonzero balance on the dispatcher (partial swap, fee-on-transfer token, unswept intermediate token, or slack native value), which is a realistic and even documented risk ("dispatcher contract holds tokens temporarily during execution"), combined with the fact that `dispatch()` itself is completely unauthenticated. No proof forgery, consensus compromise, or privileged role is needed — only a normal user's calldata that doesn't perfectly balance token flow, followed by any third-party call to `dispatch()`.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., `onlyCaller(address)` set at construction, or per-call authorization tied to the invoking app), so it cannot be invoked directly by arbitrary third parties.
- Alternatively, make the dispatcher session-scoped (e.g., deploy an ephemeral dispatcher per order/message, or require the caller to prove ownership of a specific pending execution) so no shared balance can ever be drained by an unrelated caller.
- Add invariant checks/asserts in `IntentGatewayV2`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleTokenUpgradeable` that the dispatcher's relevant token/native balance is zero (or reduced to an expected residual swept back to the app) immediately after each `dispatch()` call, reverting otherwise.

### Proof of Concept
1. A user calls `HyperFungibleToken.send()` cross-chain with `to = CallDispatcher` and `data` encoding a `Call[]` that swaps only part of the minted amount (e.g., due to slippage bounds), intentionally or not leaving a token remainder on the dispatcher after `onAccept` completes.
2. Any unrelated third party (no special role, no proof, no relayer credentials) calls `CallDispatcher.dispatch(encodedCalls)` directly with a `Call` such as `{to: token, value: 0, data: transfer(attacker, dispatcher.balanceOf(token))}`.
3. Because `dispatch()` performs no caller check and no ownership tracking, the call succeeds and the residual tokens — which belonged to the earlier HFT recipient/order — are transferred to the attacker.
