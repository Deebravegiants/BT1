Audit Report

## Title
Metering balance under-decrements when capability spend exceeds earmarked reserve, allowing quota/reserve bypass for subsequent workflow steps - ([File: core/services/workflows/metering/metering.go])

## Summary
In `Report.Settle`, the refund logic computes `step.Deduction.Sub(spentCredits)` and passes it to `balance.Add(...)` to true-up the local `balanceStore` after real node-reported spend is known. When `spentCredits` (actual spend) exceeds `step.Deduction` (the amount earmarked earlier in `Deduct`/`ByDerivedAvailability`), this delta is negative, `balanceStore.Add` rejects negative amounts via `ErrInvalidAmount`, and the code simply logs "invariant: spend exceeded reserve" without adjusting the balance at all [1](#0-0) . This leaves the local balance artificially inflated relative to true consumption.

## Finding Description
`ByDerivedAvailability` earmarks a limit up front by calling `r.balance.Minus(limit.Decimal)` based on `getMaxSpendForInvocation`, which splits the current balance across `openConcurrentCallSlots` [2](#0-1) . Later, `Settle` aggregates real node-reported `SpendValue`s into `spentCredits` via median aggregation and unit conversion [3](#0-2) , then attempts to true-up the balance by refunding `step.Deduction.Sub(spentCredits)`.

`balanceStore.Add` explicitly rejects negative amounts:
```go
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	...
	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}
	bs.balance = bs.balance.Add(amount)
	return nil
}
``` [4](#0-3) 

When `spentCredits > step.Deduction`, this delta is negative, `Add` returns `ErrInvalidAmount`, and `Settle` only logs the error via `r.lggr.Info("invariant: spend exceeded reserve")` without performing any compensating deduction from the local balance [1](#0-0) . Meanwhile, `r.balance.AddSpent(spentCredits)` unconditionally records the correct total spend for billing receipt purposes [5](#0-4) , but the *local* `bs.balance` value — used to gate subsequent `Deduct`/`ByDerivedAvailability` calls within the same execution via `getMaxSpendForInvocation` — remains higher than the true remaining reserve should allow [6](#0-5) .

This is a genuine "whole vs. delta" accounting bug: the code assumes `spentCredits <= step.Deduction` always holds, and when that assumption breaks, the correction is dropped entirely instead of being clamped.

## Impact Explanation
Because `getMaxSpendForInvocation` computes subsequent per-step spend limits directly from `r.balance.Get()`, an inflated local balance means later steps in the same workflow execution can be authorized to spend more credits than were actually reserved via `Reserve`/`ReserveCredits` from the billing service [7](#0-6) . This is a quota/reserve-bypass condition within a single execution: the on-chain/billing-service reservation is a fixed amount, but the local gating logic can permit spend beyond what that reservation should allow when node-reported spend legitimately exceeds a prior earmark. This maps to an in-scope "unauthorized fund/resource consumption beyond reservation" impact category.

## Likelihood Explanation
This does not require a malicious node. Any legitimate variance between the `Deduct`-time earmark (derived from `userSpendLimit`/`openConcurrentCallSlots` at the time the step starts) and the capability's later, node-reported actual spend at `Settle` time — due to normal gas price or compute-cost fluctuation — can cause `spentCredits` to exceed `step.Deduction`. This makes the bug reachable under ordinary operating conditions, not just adversarial ones, and it is deterministic once the precondition is hit (verified directly in the code: `balanceStore.Add` unconditionally rejects negative deltas).

## Recommendation
In `Settle`, when `step.Deduction.Sub(spentCredits)` is negative, explicitly subtract the excess (clamped to the local balance) rather than silently dropping the operation:
```go
diff := step.Deduction.Sub(spentCredits)
if diff.IsNegative() {
    _ = r.balance.Minus(diff.Abs())
    r.lggr.Warnw("spend exceeded reserve; deducting excess from local balance", "excess", diff.Abs())
} else if err := r.balance.Add(diff); err != nil {
    r.lggr.Info("invariant: spend exceeded reserve")
}
```
This ensures the local balance used to gate subsequent `Deduct`/`ByDerivedAvailability` calls accurately reflects true consumption.

## Proof of Concept
Go unit test plan targeting `core/services/workflows/metering/metering_test.go`:
1. Create a `Report` with a `balanceStore` seeded with a known starting balance (e.g., 100 credits) and call `Reserve`.
2. Call `Deduct` (or `ByDerivedAvailability`) for a step with `openConcurrentCallSlots=1` such that `step.Deduction` is earmarked at, e.g., 10 credits (balance now 90).
3. Call `Settle` with `CapabilityMetadata` containing node `SpendValue`s that, after conversion, aggregate to `spentCredits = 15` (greater than the 10-credit earmark).
4. Assert: `r.balance.Get()` is expected to be `90 - 5 = 85` (properly reflecting the 5-credit overage), but observed behavior leaves it at `90` because `balance.Add(10-15) = balance.Add(-5)` returns `ErrInvalidAmount` and is only logged, not applied.
5. Assert `getMaxSpendForInvocation` on the next step gates against the stale, inflated balance of `90` instead of the correct `85`, demonstrating the quota-bypass window.

func (r *Report) getMaxSpendForInvocation(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
) (decimal.NullDecimal, error) {
	nullCapSpendLimit := decimal.NewNullDecimal(decimal.Zero)
	nullCapSpendLimit.Valid = false

	if openConcurrentCallSlots == 0 {
		// invariant: this should be managed by the consumer (engine)
		return nullCapSpendLimit, ErrNoOpenCalls
	}

	if !r.reserved {
		return nullCapSpendLimit, ErrNoReserve
	}

	if r.meteringMode {
		return nullCapSpendLimit, nil
	}

	// Split the available local balance between the number of concurrent calls that can still be made
	spendLimit := r.balance.Get().Div(decimal.NewFromInt(int64(openConcurrentCallSlots)))

	if userSpendLimit.Valid {
		spendLimit = decimal.Min(spendLimit, userSpendLimit.Decimal)
	}

	return decimal.NewNullDecimal(spendLimit), nil
}
