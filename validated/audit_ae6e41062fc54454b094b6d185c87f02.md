## Title
Excess native-token payment in `EvmHost.dispatch()`/`fundRequest()` swaps is not refunded to the original caller, causing permanent loss of user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and, when `msg.value > 0`, swap the *entire* `msg.value` for an exact amount of fee tokens via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. Any user who over-pays `msg.value` (relative to the exact ETH needed to buy `fee`/`amount` of the fee token) never gets that unspent ETH back, because the swap router refunds unused ETH to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
```

The same pattern exists in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` (both the real UniswapV2 router and the project's own wrapper, e.g. `UniV3UniswapV2Wrapper`) only spends as much ETH as required to buy the exact output amount and refunds the difference to `msg.sender` of the swap call: [4](#0-3) 

```solidity
bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
uint256 spent = abi.decode(results[0], (uint256));

if (spent < msg.value) {
    uint256 refund = msg.value - spent;
    IWETH(weth).withdraw(refund);
    (bool success,) = msg.sender.call{value: refund}("");
    if (!success) revert RefundFailed();
}
```

Because `EvmHost` is the one calling `swapETHForExactTokens{value: msg.value}(...)`, the router/wrapper's `msg.sender` in this call is `EvmHost`, not the end user (`_msgSender()`/`tx.origin`). Any refunded/unspent ETH lands back inside `EvmHost`'s own balance. `EvmHost` never forwards this refund to the caller who originally sent the over-sized `msg.value`, nor does it validate `msg.value` against an expected/quoted amount before performing the swap (unlike the exact-amount check pattern the referenced DODO report recommends, i.e. `require(msg.value == amount, ...)`). The dispatch functions and `fundRequest()` simply consume `msg.value` in full for the swap call and silently retain whatever change the router hands back, with no accounting or return path to the payer.

This directly mirrors the DODO `_deposit()` finding: a function accepts `msg.value` for one specific purpose (swap to buy an exact `fee`/`amount` of fee token) but never checks/enforces that the provided value matches what's actually needed, and the leftover value is not returned to the sender — it becomes stuck/absorbed by the protocol contract.

### Impact Explanation
Any user (or any of Hyperbridge's own EVM `HyperApp`/`IntentGatewayV2` forwarding contracts) that calls `dispatch()` or `fundRequest()` with `msg.value` larger than the ETH cost of the requested `fee`/`amount` permanently loses the excess ETH: it is swapped into fee tokens (spending less than sent) and the change is retained by `EvmHost` with no mechanism to reclaim or credit it to the payer. Given the documentation explicitly instructs integrators to just estimate fees off-chain and send `msg.value` (see `docs/content/developers/evm/messaging/post-requests.mdx`), any imprecision in the front-end estimate, slippage, or race with price changes results in guaranteed fund loss for the caller with no recovery path — a concrete, permanent loss of user funds, satisfying the Medium/High bar for "concrete theft or permanent freezing of funds."

### Likelihood Explanation
High likelihood: this is the default, documented pattern for every native-token payment path into `EvmHost` (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest()`), and it is exercised on every single native-fee dispatch transaction, not an edge case requiring adversarial setup. Uniswap slippage and any mismatch between the client-side `quote()` estimate and the on-chain price at execution time (explicitly acknowledged as a sandwich-attack risk in the docs) makes exact `msg.value` matching essentially impossible in practice, so leftover ETH will regularly and unavoidably be produced.

### Recommendation
Track the actual ETH spent by the swap (`amounts[0]` returned by `swapETHForExactTokens`) and refund the difference (`msg.value - spent`) back to `_msgSender()` (or `post.payer`/`get.payer`) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the DODO-recommended fix of validating/handling unused `msg.value` rather than silently discarding it:

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    (bool sent, ) = _msgSender().call{value: msg.value - amounts[0]}("");
    require(sent, "REFUND_FAILED");
}
```

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `post.fee = 100` fee-token units and sends `msg.value = 1 ETH`, expecting the excess to be usable/refunded (as implied by "Will revert if enough native tokens are not provided" in the NatSpec, which only documents the underpayment case, not overpayment).
2. `swapETHForExactTokens{value: 1 ether}(100, path, address(this), block.timestamp)` only spends e.g. `0.05 ETH` to obtain the 100 fee-token units; the remaining `0.95 ETH` is refunded by the router/wrapper to `msg.sender`, which is `EvmHost`, not the user.
3. `EvmHost.dispatch()` returns the commitment; the transaction succeeds. The user's `0.95 ETH` remains locked in `EvmHost`'s balance with no state variable, event, or function exposing a way for the user to reclaim it.
4. Repeating this for `fundRequest()` and `dispatch(DispatchGet)` demonstrates the same loss on every native-token-funded call path.
