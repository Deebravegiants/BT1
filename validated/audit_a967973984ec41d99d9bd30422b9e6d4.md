Audit Report

## Title
User enumeration via distinct login error messages disclosed to unauthenticated clients - (File: core/sessions/localauth/orm.go)

## Summary
The unauthenticated `/sessions` login endpoint returns a different, attacker-observable error message ("Invalid email" vs "Invalid password") depending on whether the submitted email exists in the system, allowing account/user enumeration by any unauthenticated client.

## Finding Description
`SessionsController.Create` forwards the raw error returned by `AuthenticationProvider().CreateSession` verbatim to the client via `jsonAPIError(c, http.StatusUnauthorized, err)`, and `jsonAPIError` serializes `err.Error()` directly into the JSON response body when the error isn't a `*models.JSONAPIErrors`: [1](#0-0) [2](#0-1) 

`orm.CreateSession` distinguishes an unrecognized/mismatched email from a correct-email-wrong-password case with two distinct hardcoded strings, `"Invalid email"` and `"Invalid password"`: [3](#0-2) 

This endpoint is mounted without authentication under `unauth.POST("/sessions", sc.Create)`, protected only by a rate limiter, not by any mechanism that would obscure the distinguishing error content: [4](#0-3)  No existing sanitization/redaction layer normalizes the two error strings before they reach the HTTP response, confirming the claim as described.

## Impact Explanation
An unauthenticated attacker can distinguish "email not registered" from "email registered but wrong password" responses, enabling enumeration of valid usernames/emails on a Chainlink node's operator UI/API. This maps to CWE-209 (information exposure through error message) and could assist follow-on credential-stuffing or phishing against confirmed accounts. However, this does not by itself constitute authentication bypass, key/secret exfiltration, unauthorized job execution, fund movement, gateway impersonation, or cross-user response corruption — the categories explicitly enumerated as in-scope high-impact classes for this program. The impact is limited to a low-severity information disclosure that requires substantial additional attacker effort (credential stuffing/brute force against a rate-limited endpoint) to translate into concrete compromise, and on a typical Chainlink node deployment the pool of registered emails is very small (often a single admin account), further limiting real-world impact.

## Likelihood Explanation
Reachable by any unauthenticated network client with a single POST to `/sessions`; feasibility is real, though the presence of `rateLimiter` (`UnauthenticatedPeriod`/`Unauthenticated` limits) throttles rapid mass enumeration attempts.

## Recommendation
Return a single generic error (e.g., "invalid credentials") from `orm.CreateSession` for both the unknown-email and wrong-password branches, keeping the differentiated `AuthLoginFailedEmail` / `AuthLoginFailedPassword` audit events internal only, and ensure `SessionsController.Create` surfaces a constant generic message rather than the raw provider error for 401 responses.

## Proof of Concept
```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"realuser@example.com","password":"wrongpassword"}
```
Response body: `"Invalid password"`

```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"nonexistent@example.com","password":"wrongpassword"}
```
Response body: `"Invalid email"`

Comparing the two responses lets an unauthenticated client determine which email addresses are registered users on the node.

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
