### Title
Webhook shop/topic identity not covered by HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and the library verifies) only the raw HTTP body via HMAC, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used downstream by `ShopifyAPI::Webhooks::Registry.process` are taken directly from unauthenticated request headers. Because the app's `api_secret_key` is shared across every shop that installs the app, any tenant that legitimately receives one valid `(body, hmac)` pair can replay that exact body/HMAC to the app's webhook endpoint while substituting a different shop's domain in the `X-Shopify-Shop-Domain` header, and the library will accept it as authentic for the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string` (i.e., the raw body), never the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using the unauthenticated header-derived `request.shop` and `request.topic`: [4](#0-3) 

Because `Context.api_secret_key` is a single app-wide secret (not per-shop), this breaks the intended identity binding: `shop_the_handler_believes == shop_that_actually_produced_the_signed_bytes`. Any tenant that has legitimately received a webhook to their own endpoint has, by definition, observed a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the shared app secret. That tenant can re-POST the identical body and HMAC to the app's webhook endpoint while swapping `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to a different, victim shop. `HmacValidator.validate` will report the request as valid (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` even though the payload was never produced for that shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged tenant of a multi-tenant app built on this gem can cause the host application to process webhook data as though it originated from an arbitrary other shop, without possessing that shop's credentials or the app's `client_secret`. Depending on how the host app's webhook handlers use `data.shop` (e.g., to look up/update per-shop records, toggle subscription/billing state, or trigger app-uninstall cleanup for `app/uninstalled`), this can lead to cross-tenant data corruption or state manipulation attributed to a victim tenant — squarely in the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker must be an existing (even free/unprivileged) tenant of the target app to have observed one legitimate `(body, hmac)` pair from their own webhook deliveries, and must find or construct a webhook body that is shop-agnostic (many topics, e.g. `app/uninstalled`, have empty or near-empty bodies) so the replayed payload doesn't leak attacker-shop-specific data into the impersonated victim context. No secret material, TLS interception, or social engineering is required — only crafting an HTTP request with substituted headers, which any internet-reachable client can do against the app's public webhook endpoint.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified payload, or otherwise cryptographically bind them to the HMAC (e.g., verify them against a Shopify GraphQL lookup or bind them into `to_signable_string`) before dispatching to handlers, and document that consuming applications must not trust the shop header for tenant-sensitive operations without this validation.

### Proof of Concept
1. App tenant "Shop A" installs the app; the app registers webhook handlers via `ShopifyAPI::Webhooks::Registry`.
2. Shopify delivers a legitimate webhook to the app's endpoint for Shop A, e.g. topic `app/uninstalled` with body `{}` and headers:
   - `X-Shopify-Topic: app/uninstalled`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of "{}">`
   - `X-Shopify-Shop-Domain: shop-a.myshopify.com`
3. Because the request hits the tenant's own infrastructure/logs (or the attacker runs their own thin relay in front of the app endpoint), the attacker records the exact `(raw_body="{}", hmac)` pair.
4. The attacker crafts a new POST to the same app webhook endpoint with the identical body `{}` and HMAC header, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `"{}"` using the shared `Context.api_secret_key` and it matches, so validation succeeds: [5](#0-4) 
6. `Registry.process` invokes the `app/uninstalled` handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "shop-victim.myshopify.com", ...)`: [6](#0-5) 
7. The host application performs uninstall cleanup (or whatever business logic is bound to that topic) for `shop-victim.myshopify.com`, even though Shop A — not Shop Victim — actually triggered the underlying event.
