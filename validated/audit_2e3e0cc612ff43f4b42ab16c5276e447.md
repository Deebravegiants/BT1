Based on the Zest vault accrual logic, I've identified a valid analog to the reported issue.### Title
Protocol Treasury Can Be Permanently Denied Its Reserve-Factor Share of Interest via Rounding in `accrue()` - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vaults)

### Summary
Every Zest vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes the protocol's reserve-factor share of newly accrued interest (`reserve-inc`) using integer division with no minimum-threshold enforcement, mirroring the reported `GluexRouter` flaw where `protocolShare` can be driven to zero despite a real surplus. Because `accrue()` is a public, unprivileged, freely-callable function, an attacker can force many small accrual increments (small `debt-delta` per call) so that `reserve-inc` rounds down to `0` on every single call, while the borrow index (`idx`) and liquidity index (`lindex`) still advance and compound normally for borrowers/suppliers. The truncated reserve amount is never retained or carried forward — it is permanently lost.

### Finding Description
In the shared `accrue` logic (identical across all six vaults, e.g. `mainnet/contracts/vault/v0-vault-stx.clar:841-865`): [1](#0-0) 

```clarity
(let ((next (next-index))
      (nliq (next-liquidity-index))
      (scaled-principal (var-get principal-scaled))
      (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
      (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
      (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
      (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
      (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
  ...
  (if (> treasury-lp u0)
      (try! (ft-mint? zft treasury-lp .dao-treasury))
      false)
  ...
  (var-set last-update stacks-block-time)
  ...)
```

`reserve-inc = debt-delta * fee-reserve / BPS` uses `mul-div-down` (rounds toward zero). `BPS` is `10000` [2](#0-1) . For a typical reserve factor of 1000 bps (10%), any `debt-delta` such that `debt-delta * 1000 < 10000` (i.e. `debt-delta < 10` base units of the underlying) makes `reserve-inc = 0`, and the `(if (> reserve-inc u0) ... u0)` guard then skips minting treasury shares entirely.

Critically, `accrue()` is `define-public` and callable by any principal with no cooldown, and `last-update` is reset to `stacks-block-time` on every call that changes `idx`/`lindex` [3](#0-2) . This means an attacker can call `accrue()` on a vault every block, artificially minimizing `time-delta` and therefore `debt-delta` on each call (`calc-multiplier-delta` scales the rate by `time-delta`, so a smaller `time-delta` yields a proportionally smaller multiplier and thus a smaller `debt-delta` per call) [4](#0-3) . Each call's fractional reserve contribution is computed independently from the current state and is not accumulated as a remainder for the next call — once rounded to zero and `last-update` advanced, that slice of interest's protocol share is gone forever, even though:
- The borrow index `idx` still increases, so borrowers still owe (and eventually pay) the full economic interest.
- The liquidity index `lindex` still increases via `calc-liquidity-rate`, so depositors still receive their portion of interest.

Only the treasury's cut is dropped. This exactly matches the reported bug class: "no enforcement of a minimum threshold for [the protocol share] allowing it to be zero or arbitrarily small... resulting in the protocol receiving negligible or no compensation from a transaction that generates a valid surplus."

### Impact Explanation
This breaks the value identity that the protocol's reserve-factor share of interest generated (`interest created`) should equal `interest distributed to the treasury` over time. By spamming the unprivileged `accrue()` entry point, an attacker permanently and systematically deprives the DAO treasury of its due reserve-factor share of interest across all vaults, while suppliers/borrowers are unaffected. This is a theft/permanent freezing of unclaimed protocol yield — the treasury's `dao-treasury` account never accumulates the `zft` shares it is economically entitled to for the affected accrual windows, and this loss cannot be recovered retroactively since `last-update` has already advanced past the affected interval.

### Likelihood Explanation
Likelihood is high: `accrue()` requires no special permission, capital, or fees to call, and the attack only requires repeatedly invoking a single public function once per block (or whenever a new block/timestamp is available) instead of allowing interest to accrue over longer natural intervals. No flashloan, oracle manipulation, or DAO compromise is needed — it is a pure integer-rounding griefing/theft vector reachable by any address.

### Recommendation
Enforce a minimum accrual interval or minimum `debt-delta`/`reserve-inc` threshold before allowing `last-update` to advance and the interest to be "consumed," or accumulate rounding remainders (e.g., track a running remainder in a persistent variable and carry it into the next accrual calculation) so that repeated small calls cannot systematically zero out the protocol's reserve share. Alternatively, compute `reserve-inc` with round-up (`mul-div-up`) semantics or require `reserve-inc > 0` as a precondition to updating `last-update`, so partial accrual periods are not lost/finalized before the protocol's share becomes non-negligible.

### Proof of Concept
1. Attacker (unprivileged) observes a Zest vault (e.g. `v0-vault-stx`) with `fee-reserve = 1000` (10%) and a normal utilization/borrow rate.
2. Attacker calls `(contract-call? .v0-vault-stx accrue)` in block N. This sets `last-update` to block N's timestamp and updates `idx`/`lindex` slightly; `debt-delta` is tiny since only one block has elapsed since the last legitimate accrual, so `reserve-inc = debt-delta * 1000 / 10000` rounds to `0`; no treasury mint occurs.
3. Attacker repeats step 2 every subsequent block (or every time a new `stacks-block-time` is available), always keeping `time-delta` since `last-update` minimal.
4. Over many blocks, the cumulative sum of "true" interest (reflected in `idx`/`lindex` growth, and thus in borrower debt and supplier redemption value) is substantial, but the treasury's minted `treasury-lp` remains `0` for every single call because each individual slice's `reserve-inc` rounds down to zero.
5. Result: the DAO treasury permanently receives none of its 10% reserve factor for the entire period the attacker keeps forcing frequent small accruals, even though real interest was generated and distributed to lenders/borrowers — an unprivileged, cost-free denial of protocol revenue.
