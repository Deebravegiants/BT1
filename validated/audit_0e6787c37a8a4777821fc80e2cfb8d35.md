Audit Report

## Title
Cross-workflow HTTP action response cache confusion due to `OutboundHTTPRequest.Hash()` omitting `WorkflowID` - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

## Summary
The gateway's outbound HTTP action response cache (`responseCache`) keys cache entries solely on `gateway_common.OutboundHTTPRequest.Hash()`, which incorporates method, URL, headers, body, and `WorkflowOwner` but not `WorkflowID`. Two different workflows registered under the same `WorkflowOwner` that issue an identical outbound HTTP action (same method/URL/headers/body) will read and write the same cache slot, so one workflow can receive another workflow's cached HTTP response, in direct contradiction to the package's own documented "Workflow Isolation" guarantee.

## Finding Description
The `core/services/gateway/handlers/capabilities/v2/README.md` explicitly documents that the cache key is "Generated from workflow ID and request hash" and that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) .

The actual implementation in `responseCache.Fetch` and `responseCache.Set` uses only `req.Hash()` as the map key, with no `WorkflowID` component [2](#0-1) [3](#0-2) .

The gateway's `makeOutgoingRequest` (invoked from `HandleNodeMessage` when a DON node reports an HTTP action for the gateway to execute) unmarshals the untrusted `OutboundHTTPRequest` sent by the node and, based on `CacheSettings`, calls `Fetch` or `Set` keyed purely on this hash [4](#0-3) .

The project's own unit tests confirm the gap: `TestRequestHash`'s "having different workflowID results in same Hash" case asserts two requests differing only by `WorkflowID` produce an identical hash, while differing `WorkflowOwner` correctly produces different hashes [5](#0-4) .

The code comment at `http_handler.go` line ~327-329 acknowledges that fields on `OutboundHTTPRequest`, including presumably `WorkflowOwner`/`WorkflowID`, "come from untrusted nodes," confirming these are node-supplied fields, not independently verified against the workflow registry at this layer [6](#0-5) .

There is no existing mitigation: `Hash()` differentiates by `WorkflowOwner` but not `WorkflowID`, so the isolation the README promises at the workflow level is not actually enforced by the cache implementation.

## Impact Explanation
Because `WorkflowID` is absent from the cache key, cached HTTP action responses (which can contain workflow-specific data returned by an external endpoint, e.g., session tokens or state tied to a particular workflow's prior calls) can be served to a different workflow that happens to share the same `WorkflowOwner` and issues a request with an identical method/URL/headers/body. This breaks the documented per-workflow isolation guarantee and constitutes cross-workflow response/data confusion within the gateway's response cache, falling under the "cross-user response corruption" class of in-scope impact. Note that since `WorkflowOwner` is still part of the hash, this leakage is bounded to workflows sharing the same owner — it is not a cross-owner/cross-tenant disclosure across different customers, which somewhat limits the severity compared to a strict cross-tenant breach.

## Likelihood Explanation
Triggering this does not require any malicious or Byzantine node behavior — it is a natural consequence of two legitimate workflows deployed under the same owner making outbound HTTP action calls with `CacheSettings.Store`/`MaxAgeMs` set and identical request shape (e.g., both hitting the same public API endpoint with the same headers), which is realistic for routine workflow usage. The unit test `TestRequestHash` demonstrates this collision deterministically, without any adversarial input crafting.

## Recommendation
Include `WorkflowID` in the value hashed by `OutboundHTTPRequest.Hash()`, or namespace the `responseCache` map by `(WorkflowID, req.Hash())` in addition to the existing components, so that cached responses are strictly scoped per-workflow as documented. Add a regression test asserting that identical requests from different `WorkflowID`s under the same `WorkflowOwner` produce distinct cache entries.

## Proof of Concept
1. Workflow A (`WorkflowID = "wf-A"`, `WorkflowOwner = "0xOwner"`) issues an HTTP action with `CacheSettings.Store = true`, causing `responseCache.Set` to cache the response under `req.Hash()` (method+url+headers+body+owner, no workflow ID) [3](#0-2) .
2. Workflow B (`WorkflowID = "wf-B"`, same `WorkflowOwner = "0xOwner"`) issues an outbound HTTP action with identical method/URL/headers/body and `CacheSettings.MaxAgeMs > 0`.
3. `makeOutgoingRequest` calls `responseCache.Fetch`, which computes the same `req.Hash()` (WorkflowID excluded) and returns Workflow A's cached response to Workflow B's node [7](#0-6) .
4. This is directly demonstrated by the existing `TestRequestHash` "having different workflowID results in same Hash" sub-test [8](#0-7) .

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
