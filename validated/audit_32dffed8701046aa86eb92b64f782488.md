### Title
Empty-body PostRequest causes unconditional revert (out-of-bounds array access) in cross-chain `onAccept` handlers before source authentication - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
Several `onAccept` callbacks that receive incoming ISMP `PostRequest`s decode the leading dispatch-kind byte via `uint8(incoming.request.body[0])` before validating that the request actually originates from an authorized source or has any authenticated content. If `body` has zero length, this indexing operation reverts (Solidity `Panic(0x32)`, array out-of-bounds), and — because the read happens before the source/authentication check — it is reachable by any account able to dispatch an ISMP `PostRequest` to the target contract, not only by Hyperbridge governance.

### Finding Description
`ExtrinsicIntents.onAccept` reads the discriminator byte unconditionally: [1](#0-0) 
before the `incoming.request.source == hyperbridge` check that happens later: [2](#0-1) 

The same pattern exists in `IntentGatewayV2.onAccept`: [3](#0-2) 

and in `SimplexPaymaster.onAccept` / `HostManager.onAccept`, though in those two the source/relayer authorization check happens first, which limits the practical reach (analogous to CVE-2016-4343's root cause — an attacker-controlled, zero-size field is dereferenced/indexed without a length guard before any other validation, producing undefined behavior on the decoder path): [4](#0-3) [5](#0-4) 

Any user can dispatch an arbitrary `PostRequest` destined for one of these contracts via `IDispatcher.dispatch`, and a relayer will later present a state proof through `HandlerV2`/`EvmHost` delivery to `onAccept`. If the dispatched request's `body` is empty, `ExtrinsicIntents`/`IntentGatewayV2`'s `onAccept` reverts at `body[0]` **before** `_checkRelayer`/`_authenticate`/source checks would otherwise reject it, so the crafted message needs no special privilege to reach the faulting line.

### Impact Explanation
I was not able to fully verify, within the available tooling, whether the on-chain delivery path (`HandlerV2`/`EvmHost` `handlePostRequests`) wraps each per-request `onAccept` call in a try/catch that isolates the revert to that single request (in which case the impact is limited to that message being dropped/retried, a low-severity issue), or whether the revert propagates and reverts the entire relayer-submitted batch transaction (in which case a single crafted zero-body request could be used to grief/DoS batched delivery of otherwise-legitimate requests in the same transaction, forcing relayers to always deliver this contract's messages individually and burning relayer gas on reverted batches). I could not locate and read the `handlePostRequests`/`dispatchToModule` implementation in `evm/src/core/HandlerV2.sol` or `EvmHost` to confirm this before running out of tool calls — this is the key unresolved question for scoring this as Medium vs. informational.

Unlike the CVE, Solidity's checked array access reverts cleanly rather than dereferencing an uninitialized pointer, so there is no memory-corruption or fund-theft primitive here directly. The realistic impact is denial-of-service / delivery-disruption of the affected app's cross-chain message channel, not unbacked mint or forged delivery.

### Likelihood Explanation
Likelihood is high for triggering the revert: dispatching a `PostRequest` with an empty body to `ExtrinsicIntents`/`IntentGatewayV2` requires only a normal permissionless `dispatch` call and a relayer to deliver it — no privileged role, governance, or malicious validator is needed. Whether this constitutes a *meaningful* exploit depends entirely on the unverified batching/try-catch behavior noted above.

### Recommendation
Add an explicit `if (incoming.request.body.length == 0) revert InvalidBody();` (or equivalent minimum-length check) at the top of `onAccept` in `ExtrinsicIntents.sol` and `IntentGatewayV2.sol`, before indexing `body[0]`, and move the discriminator read to occur only after any partial length validation. Confirm (or add) per-request isolation in the batch-delivery path (`HandlerV2`/`EvmHost`) so a revert in one module's `onAccept` cannot abort delivery of unrelated requests in the same relayer batch — mirroring the try/catch pattern already used in `HyperbridgeLzEndpoint.onAccept`.

### Proof of Concept
1. Attacker calls `IDispatcher(host).dispatch(DispatchPost{ dest: <ExtrinsicIntents chain>, to: abi.encodePacked(extrinsicIntentsAddress), body: "", timeout: 0, fee: 0, payer: attacker })` on any source chain — no authorization required, standard permissionless dispatch.
2. A relayer, following normal incentives, delivers this request with a valid state/consensus proof via the destination `HandlerV2`/`EvmHost`, which invokes `ExtrinsicIntents.onAccept(incoming)`.
3. Execution reaches `RequestKind kind = RequestKind(uint8(incoming.request.body[0]));` with `incoming.request.body.length == 0`, causing a `Panic(0x32)` revert — before `_checkRelayer` or the Hyperbridge-source check are evaluated for the non-escrow branches.
4. Whether this reverts only the single request or the whole relayer batch transaction determines the blast radius; this could not be confirmed against `HandlerV2.sol`'s delivery loop within the available investigation.
