## Analog Found

### Title
Signed calldata payload for HFT's `on_accept` omits any chain/consensus binding, allowing cross-chain signature replay across multiple `hyper-fungible-token` deployments - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `hyper-fungible-token` pallet lets an incoming ISMP token-transfer message carry optional `SubstrateCalldata` (a `runtime_call` plus an optional `signature`) that is executed with `RawOrigin::Signed(beneficiary)` once the signature is verified. The message signed off-chain by the beneficiary is only `(nonce, runtime_call)` — it contains no state-machine/chain identifier, unlike every other signed-message construction in this codebase (`pallet-ismp-relayer`'s `message()`/`beneficiary_message()` both explicitly bind to `StateMachine`/`dest_chain`).

### Finding Description
In `on_accept`, when the incoming `PostRequest.body` decodes to a `Message` with non-empty `data`, the pallet decodes `SubstrateCalldata` and, if a signature is present, reconstructs the signed payload purely from the beneficiary's local nonce and the call bytes: [1](#0-0) 

For each signature scheme the preimage is built the same way:
```
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
```
— see the Ed25519/Sr25519/Ecdsa arms: [2](#0-1) 

`nonce` is read live from `frame_system::Pallet::<T>::account_nonce(beneficiary)` on the destination chain — it is **not** part of the attacker-controlled payload, but it is chain-local state that trivially collides across deployments (e.g., both start at `0` for any fresh account, or can otherwise coincide across two separate `hyper-fungible-token` deployments on different destination chains/consensus systems). Nothing in the signed preimage — no `StateMachine`, no genesis hash, no consensus/chain id — ties the signature to a specific destination deployment.

This contrasts directly with the rest of the codebase's signed-message conventions, which explicitly guard against exactly this bug class: [3](#0-2) [4](#0-3) 
and is even unit-tested for rejection of exactly this cross-chain reuse pattern: [5](#0-4) 

Since `hyper-fungible-token` is registered per (asset, destination `StateMachine`) via `TokenRegistration.chains: BTreeMap<StateMachine, ChainConfig>`, the same asset/pallet can legitimately be bridged to and deployed as multiple destination consensus systems from a single source contract: [6](#0-5) 

An unprivileged relayer or message dispatcher who observes a legitimately signed `PostRequest` body (containing `Message{..., data: SubstrateCalldata{signature, runtime_call}}`) destined for chain A can re-dispatch the identical body/message to chain B's HFT deployment (any destination whose local `ContractToAsset` mapping accepts the same `source`/`from` pair and whose beneficiary account happens to share the same nonce, most commonly nonce `0` for a not-yet-active account). Because the ISMP delivery layer's own replay protection (`_requestReceipts`/commitment) is keyed by the full request tuple (source, dest, nonce, body, etc.), a request re-encoded for a different `dest` produces a different top-level ISMP commitment and is *not* blocked by ISMP's own replay guard — only the pallet's own signature check stands in the way, and that check does not bind to the destination chain at all.

### Impact Explanation
A successful replay lets an attacker execute an arbitrary `runtime_call` (dispatched with `RawOrigin::Signed(beneficiary)`, subject only to `BaseCallFilter`) on a second `hyper-fungible-token` deployment the user never intended to authorize. Because the origin is the real beneficiary's account, this is not a bounded "spend the tokens twice" bug — it is an unauthorized dispatch of an arbitrary signed call on the user's behalf on a chain outside the scope the user agreed to when signing, which can range from unwanted transfers to invoking arbitrary dispatchables filtered only by the destination runtime's base call filter. This matches the report's core concern ("permit is valid on any chain the contract/pallet is deployed to") and is a concrete "unauthorized app action" per the validation criteria.

### Likelihood Explanation
Exploitability requires: (1) the same `hyper-fungible-token` pallet/asset deployed on ≥2 destination chains reachable from a common source `ContractToAsset` mapping (an intended, documented multichain deployment pattern for this pallet), (2) a beneficiary account whose local nonce on the second chain coincidentally equals the nonce used in the signed payload — most trivially true for the very common case of a beneficiary's first-ever signed calldata transfer (nonce `0`) on a freshly used account on each chain. No governance or validator collusion is needed; a normal relayer or any party who can read the source chain's emitted `PostRequestEvent` (public data) and redispatch/re-submit it against a different destination client can trigger this. This is a realistically reachable, medium-likelihood but high-impact path.

### Recommendation
Bind the signed preimage to the destination chain, mirroring the pattern already used in `pallet-ismp-relayer`:
```rust
let payload = (nonce, T::StateMachineId::get() /* or the local StateMachine constant */, substrate_data.runtime_call.clone()).encode();
```
Alternatively include `frame_system::Pallet::<T>::block_hash(0)` (genesis hash) or a config-provided consensus/state-machine identifier in the signed tuple for all three signature branches (Ed25519, Sr25519, Ecdsa) in `on_accept`.

### Proof of Concept
1. Deploy `hyper-fungible-token` (or `WrappedHyperFungibleToken`) with the same source EVM contract registered as a valid `ContractToAsset` source on two destination chains, A and B (a supported, documented configuration per `TokenRegistration.chains`).
2. A user Bob (fresh account, nonce `0` on both A and B) signs `keccak256/blake preimage of (0u64, runtime_call_bytes)` intending to authorize `runtime_call` only on chain A, attaching it as `SubstrateCalldata` in the `data` field of a cross-chain transfer `Message` sent from the source EVM contract to chain A.
3. The relayer (or any observer of the source chain's `PostRequestEvent`) copies the identical `body` (containing the same `Message`/`SubstrateCalldata`) and submits/dispatches an equivalent `PostRequest` targeted at chain B's HFT deployment instead (or in addition).
4. On chain B, `on_accept` reads Bob's nonce (`0`, since Bob has never transacted there), reconstructs the same `(0, runtime_call)` preimage, and successfully verifies the signature — dispatching `runtime_call` as `RawOrigin::Signed(Bob)` on chain B, which Bob never authorized for that chain.

*Note: full exploitation depends on operational specifics (which destination chains/registrations are live, and coincidental nonce matching) that could not be independently confirmed beyond the code paths cited above; a Devin session with repo/test execution access would be needed to build and run a concrete end-to-end PoC test.*

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
