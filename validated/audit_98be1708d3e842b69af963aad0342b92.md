### Title
Missing zero/empty-address sanity check in `register_token`/`update_token` lets `CreateOrigin` (and any relayer submitting the resulting peer address) create a token route that burns/escrows user funds against an unreachable peer contract - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`register_token` and `update_token` in `pallet-hyper-fungible-token` insert an operator-supplied `token_contract: H160` byte string directly into `TokenContracts` and `ContractToAsset` storage with no validation that the address is non-zero or otherwise well-formed, mirroring the `UXDRouter.registerDepository` pattern in the referenced report (registering a zero-address depository silently accepted, later routing real user funds to it).

### Finding Description
`register_token` copies `config.token_contract.0.to_vec()` straight into `TokenContracts::<T>::insert` and `ContractToAsset::<T>::insert` for each configured chain, with checks only for `NonEvmPeerChain` and `ErcDecimalsBelowLocal` — there is no `ensure!(token_contract != H160::zero(), ...)`: [1](#0-0) 
`update_token` has the identical gap when adding chains: [2](#0-1) 

Once such a token is registered, `send()` looks up `TokenContracts` for the `to` field of the outgoing `DispatchPost` unconditionally — it only checks the map returns *some* value, not that the value is a meaningful address — then burns/escrows the caller's tokens and dispatches the ISMP request: [3](#0-2) 

If `token_contract` was registered as the zero address (or any address with no corresponding `HyperFungibleTokenUpgradeable` deployment), the destination-chain message is addressed to a contract that cannot process it (no code, or a contract lacking `onAccept`), so it can never mint/refund the counterpart tokens. Because tokens are already burned/escrowed on the source chain at dispatch time, this becomes a permanent freeze/loss of user funds for every `send()` call against that route, until the request times out and `on_timeout` is triggered to refund — and even that path only works if the request is provably undeliverable and a timeout proof is submitted.

### Impact Explanation
Unlike a purely malicious-admin scenario, this is an input-validation gap that converts an operator's one-time registration mistake into ongoing loss exposure for arbitrary unprivileged callers of `send()`. Every user who calls `send()` against a token/chain pair with a bad `token_contract` has their assets escrowed/burned into a route that cannot deliver, matching the "concrete... permanent freezing of funds" acceptance criterion. This matches the class of the referenced Sherlock finding (registering `address(0)` as a depository silently accepted, then routed real funds).

### Likelihood Explanation
Requires `CreateOrigin` to register/update a token chain config with a wrong/zero `token_contract` — a config-time human error, not requiring malicious intent, and nothing in `register_token`/`update_token` prevents or flags it. Given there is no automated verification that the address has been deployed and speaks the expected `onAccept` protocol, likelihood of an operational mistake reaching production is realistic across multi-chain, multi-asset registration.

### Recommendation
Add a sanity check on `config.token_contract` in both `register_token` and `update_token` (and analogous checks in `update_asset_precision`-type calls elsewhere if similar patterns exist), e.g. `ensure!(token_contract != H160::zero(), Error::<T>::InvalidTokenContract);`. Consider also validating uniqueness/no self-collision in `ContractToAsset` to avoid silently overwriting the reverse map for another asset.

### Proof of Concept
1. `CreateOrigin` calls `register_token` with `registration.chains = { StateMachine::Evm(1) => TokenConfig { token_contract: H160::zero(), decimals: 18 } }`.
2. Storage now maps `TokenContracts[(Evm(1), asset_id)] = 0x000...000` and `ContractToAsset[(Evm(1), 0x000...000)] = asset_id`, with no revert. [4](#0-3) 
3. Any signed user calls `send({ asset_id, destination: Evm(1), amount, recipient, ... })`.
4. `send()` succeeds: it fetches `token_contract` (the zero address) without validating it, burns/escrows the user's tokens, and dispatches a `DispatchPost` with `to: 0x000...000` on Ethereum. [5](#0-4) 
5. On Ethereum, no contract exists at the zero address (or the deployed contract there is not the intended `HyperFungibleTokenUpgradeable`), so the message cannot be delivered/accepted; the sender's tokens remain burned/escrowed with no automatic recovery path other than a timeout-triggered refund, which the pallet does support via `on_timeout`, but only if a relayer submits a timeout proof after `params.timeout` elapses — leaving funds frozen for the interim and dependent on manual/relayer action to recover.

**Uncertainty**: I was not able to fully verify whether `on_timeout`'s reliance on `ContractToAsset::get(dest, &to)` (keyed by the same bad `token_contract`) would still resolve correctly to allow the refund path, since that lookup uses the same corrupted mapping; if it does resolve, the funds are recoverable only via timeout, not immediately, which still constitutes a temporary freeze rather than outright permanent loss. This would need runtime-level testing on Devin to confirm end-to-end behavior with a zero/invalid `token_contract`.
