### Title
RAY index accrual overflows i128 and permanently freezes a market - (File: common/src/rates/scaling.rs)

### Summary
A sufficiently large market can reach an interest-index state where unscaling total debt or supply exceeds `i128::MAX`. `scaled_to_original` performs an unconditional RAY multiplication, so the next accrual panics before the borrow-index cap can protect the market. [1](#0-0)  Every pool operation loads the market through `synced_market`, which runs `global_sync` before executing the requested action. [2](#0-1)  Once this boundary is crossed, withdrawals, repayments, borrows, liquidations, and explicit index updates for that market all revert atomically. [3](#0-2) 

### Finding Description
`scaled_to_original` multiplies a scaled RAY position by the market index without saturating or reducing the intermediate value. [1](#0-0)  Interest accrual evaluates market totals while applying each time chunk, and `global_sync` repeatedly applies `accrue_chunk` until the elapsed interval is consumed. [4](#0-3)  The borrow-index update caps only the index returned by multiplication; it does not cap the separately computed `scaled * index` market value that accrual and subsequent operations require. [5](#0-4)  Consequently, a large 18-decimal market can cross the i128 value ceiling while its stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5) 

The vulnerable precondition can be created through ordinary `supply` and `borrow` calls when a listed market has enough decimals and permitted capacity. [7](#0-6)  The permissionless controller `update_indexes` entrypoint forwards the selected assets to the pool and requires only caller authorization. [8](#0-7) 

### Impact Explanation
The panic permanently freezes all user funds in the affected market because repayment and withdrawal both start by syncing the market and therefore hit the same overflowing unscaling operation. [9](#0-8) [10](#0-9)  Liquidation and bad-debt processing also use pool operations that load a synced market, so underwater positions cannot be repaired through the normal protocol paths. [11](#0-10)  Since `update_indexes` itself panics and every mutation accrues first, the condition is not recoverable through an in-scope user call. [12](#0-11) 

### Likelihood Explanation
The required market scale is extreme, but it can arise through normal protocol use in a high-decimal asset rather than through malformed input or privileged state corruption. [7](#0-6)  Time passage is the remaining trigger, and any authorized caller can then invoke `update_indexes` or trigger accrual through another market operation. [8](#0-7)  The repository’s regression case demonstrates the same sequence and observes `MathOverflow` before the borrow-index cap engages. [13](#0-12) 

### Recommendation
Make index accrual and market-value calculations ceiling-aware before multiplying scaled positions by indexes. Cap or clamp the borrow index based on the current scaled debt so `scaled * index` cannot exceed the representable RAY range, and use saturating or widened arithmetic for total-market calculations. [14](#0-13)  Add an explicit post-accrual bound to every chunk and a regression covering supply, debt, supply-index, and revenue-share products at the representable boundary. [15](#0-14) 

### Proof of Concept
1. On a listed 18-decimal market, a user calls controller `supply(caller, 0, spoke_id, supply_actions)` and deposits enough underlying to create approximately `1e36` raw RAY units of supply.
2. Another position posts sufficient collateral and calls `borrow(caller, account_id, borrow_actions, receiver)` to reach roughly 98% utilization. [16](#0-15) 
3. Time elapses while utilization remains high.
4. Any caller invokes `update_indexes(caller, vec![HubAssetKey { hub_id, asset }])`; accrual reaches `scaled_to_original(scaled, index)` and panics with `MathOverflow`. [2](#0-1) [1](#0-0) 
5. Subsequent `withdraw`, `repay`, `liquidate`, and `clean_bad_debt` paths involving that market all revert before performing their operation because they load the same synced market. [17](#0-16)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

pub(crate) fn apply(env: &Env, entry: &PoolSeizeEntry) -> MarketStateSnapshot {
    require_nonneg_amount(env, entry.position.scaled_amount);
    let mut cache = ops::synced_market(env, &entry.hub_asset);
    let position = Ray::from(entry.position.scaled_amount);

    match entry.side {
        AccountPositionType::Borrow => {
            let bad_debt = cache.unscale_borrow_ceil_ray(position);

            cache.burn_debt(position);
        }
        AccountPositionType::Deposit => {
            cache.absorb_supply_as_revenue(position);
        }
    }

    cache.commit()
