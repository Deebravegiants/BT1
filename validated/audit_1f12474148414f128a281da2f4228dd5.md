The docs explicitly document that `data.shop` is "The shop domain of the webhook" — a tenant identity binding that the host app (per the gem's own documented pattern) relies on to route/attribute webhook data, as shown in the `webhooks.md` example passing `shop_domain: data.shop`.

### Title
Webhook tenant identity (`shop` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator` verifies the HMAC exclusively over that body. The `shop` field, which is read from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header and is the value the gem exposes to host applications as the tenant identity for the webhook, is never included in the signed material. This breaks the identity binding: `HMAC-verified(body) == HMAC-valid` but `shop-used-for-tenant-routing != shop-covered-by-HMAC`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`shop` is read straight from headers with no cryptographic binding: [3](#0-2) 

`Registry.process` validates the HMAC and then passes the header-derived `request.shop` straight to the app's handler as the trusted tenant identifier: [4](#0-3) 

The gem's own documentation instructs apps to use `data.shop` as the tenant key for routing/storing webhook data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), confirming this is the intended and documented identity-binding use of the field: [5](#0-4) 

Because the api_secret_key is shared across all shops that install a given app, any merchant who has legitimately installed the app receives real, validly-signed webhooks for their own shop (body + HMAC). Since the HMAC covers only the body and not the shop header, that same (body, HMAC) pair remains valid when replayed to the app's webhook endpoint with an attacker-modified `x-shopify-shop-domain` header pointing at a different, victim shop. `Utils::HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:13-22` will still return `true` because it only recomputes and compares the HMAC of `@raw_body`.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem's documented pattern (using `data.shop` to select which merchant's session/data store to write to) can be made to process/store attacker-supplied webhook content under an arbitrary victim shop's identity, without needing that victim's credentials. This maps to the "Critical - cross-tenant access" category, since the tenant boundary (`shop`) that the host app relies on is not actually authenticated by this gem despite being presented as verified once `HmacValidator.validate` passes.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must be a legitimate installer of the target app (to obtain at least one genuine `(raw_body, hmac)` pair signed with the app's real `api_secret_key`), and the attacker can only control the header value, not the raw body content itself (so injected content is limited to whatever body they legitimately received). This still allows shop-identity spoofing/replay for any topic and is triggerable by any unprivileged app installer, with no access to `api_secret_key`, tokens, or victim credentials required.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable representation, or independently verify that the header-derived `shop` matches a shop actually associated with a currently valid session/installation for this app before trusting it as the tenant key, instead of relying on the raw-body-only HMAC to implicitly vouch for header values that are not part of the signed content.

### Proof of Concept
1. Attacker installs "Victim App" on their own store `attacker.myshopify.com`, and receives a real webhook: raw body `B` with header `x-shopify-hmac-sha256: HMAC_SECRET(B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the same app's webhook endpoint, but with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body unchanged; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SECRET(B)` (unchanged) and compares against the (unchanged) received signature — validation passes.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, so the app processes attacker-controlled content as if it originated from `victim.myshopify.com`.
