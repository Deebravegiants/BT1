### Title
PoA Bridge withdrawal status matched by `assetId` alone lets one withdrawal's completion misreport another's status/hash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a *specific* withdrawal (identified by `index` within a NEAR transaction) by calling `findMatchingWithdrawal`, which selects an entry from the POA bridge API response using only `assetId` equality, ignoring the withdrawal's `index`/amount. When a single intent transaction contains two or more withdrawals of the same token (e.g., `nep141:btc.omft.near` twice), each `describeWithdrawal({..., index: 0})` and `describeWithdrawal({..., index: 1})` call resolves to the *same* matched record, so the status/txHash reported for one withdrawal is actually the outcome of a different withdrawal in the same batch.

### Finding Description
`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that carries an `index` field meant to disambiguate multiple withdrawals of the same asset within one NEAR tx: [1](#0-0) 

However, `describeWithdrawal` never uses `args.index`; it fetches the full withdrawal list for the tx hash and delegates matching purely to `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [2](#0-1) 

The matcher itself explicitly documents (and accepts) this limitation: [3](#0-2) 

This breaks the equality "status/hash reported for withdrawal N == on-chain outcome of withdrawal N": with two same-asset withdrawals in one intent tx (index 0 and index 1), both calls to `describeWithdrawal` return the identical `withdrawal` object (typically the first match found by `Array.find`), so the second withdrawal is reported with the first withdrawal's `status`/`transfer_tx_hash`, or vice versa depending on API ordering (explicitly called out as "unsorted" in the code comment at `poa-bridge.ts:318`).

The polling/consumption path treats this reported status as ground truth for completion: [4](#0-3) 

`watchWithdrawal`/`waitForWithdrawalCompletion` resolve based solely on `status.status === "completed"` and the returned `txHash`, with no cross-check against `index`, amount, or destination for POA. An integrator relying on `sdk.waitForWithdrawalCompletion` (or `describeWithdrawal` directly) for each withdrawal identifier in a batch can therefore mark the wrong withdrawal as completed with the wrong destination tx hash — or mark a still-pending withdrawal as completed because the other (already completed) same-asset withdrawal's record was matched instead.

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice" (High). Concretely:
- If withdrawal #0 (small amount) completes before withdrawal #1 (large amount) in the same tx, an integrator polling for #1's completion via `describeWithdrawal`/`waitForWithdrawalCompletion` can receive `{status: "completed", txHash: <tx of #0>}` prematurely, causing it to treat a not-yet-executed transfer as settled and release downstream funds/credit based on a fabricated completion signal.
- Conversely, once withdrawal #0 fails or is still pending, `describeWithdrawal` for #1 could report `pending`/`failed` even though #1 already completed, or report the wrong `reason`.
The misreport is on the SDK's read-side status API used to drive integrator business logic (crediting, unlocking, releasing downstream transfers), not merely a display bug.

### Likelihood Explanation
Likelihood is moderate: it requires an intent to include ≥2 withdrawals of the exact same `assetId` routed through the PoA bridge in a single NEAR transaction — a scenario explicitly acknowledged as unsupported/broken in the code's own comment, meaning it's a known reachable edge case rather than a hypothetical one. Any integrator batching multiple same-token withdrawals to different destinations in one call (a supported SDK feature — see `Batch Processing` in the README) can trigger it without any malicious actor.

### Recommendation
Disambiguate matching by including the withdrawal's `index`/amount (or another unique field such as destination address/memo) in `findMatchingWithdrawal`, or request/track a per-withdrawal identifier from the POA API so `describeWithdrawal` binds strictly to the specific withdrawal instance rather than the first record matching `assetId`. At minimum, when multiple candidates match the same `assetId`, correlate by remaining unconsumed candidates (consume matched records) so repeated calls for different indexes don't return the same record.

### Proof of Concept
1. Submit one NEAR intent transaction containing two `ft_withdraw` intents for `nep141:btc.omft.near` — withdrawal A (amount 1000) to address X, withdrawal B (amount 2000) to address Y.
2. SDK creates two `WithdrawalIdentifier`s with `index: 0` and `index: 1`, same `tx.hash`, same `assetId` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:295-311`).
3. Once the POA bridge processes withdrawal A (destination X) and returns it as `COMPLETED` while B is still `PENDING`, call `describeWithdrawal` for identifier with `index: 1` (withdrawal B).
4. `findMatchingWithdrawal` searches `response.withdrawals` by `assetId` only (`poa-bridge.ts:418-427`) and returns the first entry matching `nep141:btc.omft.near`, which is A's `COMPLETED` record with `transfer_tx_hash` for the transfer to X.
5. `describeWithdrawal` returns `{status: "completed", txHash: <A's hash>}` for what the caller believes is withdrawal B (destined to Y) — an integrator using `waitForWithdrawalCompletion` for B would incorrectly conclude B is settled and reference the wrong destination transaction hash.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
