This confirms the vulnerability path: HMAC validation for webhooks only signs the raw request body via `to_signable_string`, and never binds the `shop`, `topic`, or `webhook_id` header values into the signed payload.### Title
Webhook shop/topic attribution is not covered by HMAC verification, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, and `webhook_id` values used to attribute and route the event are taken from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using this signable string and, if valid, immediately builds a `WebhookMetadata` from the same request's header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) without any additional binding check between those fields and the verified body: [2](#0-1) 

The `shop` and `topic` accessors read directly from attacker-controllable HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`), which are not part of the HMAC-signed content: [3](#0-2) 

The HMAC computation itself confirms only body integrity/authenticity against `Context.api_secret_key`, with no header binding: [4](#0-3) 

This is precisely the bug class described in the report analog: two fields that must match to preserve an identity/tenant binding — here, "the shop that Shopify actually signed this payload for" versus "the shop asserted by the `x-shopify-shop-domain` header" — are never checked against each other. The gem's own documentation instructs host applications to trust `data.shop` directly for shop attribution and downstream job dispatch, without any further verification, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [5](#0-4) 

### Impact Explanation
Because the shop/topic headers are not covered by the HMAC, any actor who can obtain one valid `(raw_body, hmac)` pair — trivially available to any merchant who has the app installed on their own store, since Shopify will deliver a legitimately signed webhook to that merchant's own account — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still return true (it only checks the body), and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` claiming to be the victim shop. Since the gem's documented usage pattern is for host apps to key job/session lookups off `data.shop`, this enables cross-tenant data confusion: attacker-originated webhook content gets attributed to and processed against a different tenant's shop context.

### Likelihood Explanation
Exploitation requires only: (1) any account with the app installed (to obtain one valid signed payload+HMAC), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook callback URL with forged headers — both are unprivileged-internet-user actions with no access token, `client_secret`, or other credential required. The webhook signature does not protect against this because it authenticates content, not the header-based sender/tenant claim that the library and its documented consumers rely upon.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified payload rather than trusting them as unauthenticated headers — e.g., include them in `to_signable_string`, or cross-validate the header-asserted shop against the shop associated with the webhook subscription/registration before constructing `WebhookMetadata`. At minimum, document prominently that `data.shop` must not be trusted as an authenticated tenant identifier by host applications without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST for `orders/create` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the same app endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `raw_body` (lib/shopify_api/webhooks/request.rb:35-38, lib/shopify_api/utils/hmac_validator.rb:26-31).
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`, and any host application following the documented pattern (lib docs/usage/webhooks.md:19-30) will process/attribute this attacker-controlled payload as belonging to `victim-shop.myshopify.com`.
