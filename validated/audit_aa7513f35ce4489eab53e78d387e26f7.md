### Title
Hostile HyperSwap V2 pre-seed bypasses the "dust-only" rebalance fallback and forces a full-ratio LP donation to the attacker in `finalizeGraduation` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._seedRebalancing` assumes that whenever `_pairRebalance` cannot execute a swap (`s == 0` or `expectedOut == 0`), the pre-existing HyperSwap V2 reserves must be "negligible" and therefore safe to overpower with a raw `_seedDirectMint` (`pair.mint(lpLock)`). That assumption is only checked for the small, symmetric case gated by `DIRECT_MINT_PRESEED_BPS`; the same fallback is silently reused on the asymmetric, large-reserve rebalance path where the "negligible reserves" precondition does not actually hold. This mirrors the `glance` advisory's root cause: a guard (`--nodot`) that is only enforced at the shallow/expected case (top-level dotfiles) is silently absent for a related, reachable case (files nested one level deeper), letting content that should be excluded slip through the same code path.

### Finding Description
`Bonding.finalizeGraduation` seeds HyperSwap V2 liquidity via `_seedUniswapV2Direct` → `_seedRebalancing`: [1](#0-0) 

The `DIRECT_MINT_PRESEED_BPS` band (1 bps) is the *only* explicit safety check that reserves are small enough that a direct `pair.mint(lpLock)` against a non-empty pool is an acceptable "negligible subsidy": [2](#0-1) 

If the pre-seed is not below that band on both sides, the code instead tries to rebalance the pool toward the curve-close ratio with a direct-to-pair swap capped at `_swapBudget` (99% of Bonding's *own* inventory of the relevant asset, i.e. bounded by `tokensForLP` ≤ `LP_RESERVE` or `ltFromPair`, not by the attacker's reserves): [3](#0-2) 

`_pairRebalance` computes the fee-aware output via `IUniswapV2Pair(pair).getAmountOut(s, tokenIn)` and returns `false` — triggering the very same `_seedDirectMint` fallback used for the dust case — whenever that quote rounds to zero: [4](#0-3) 

Because `s` is capped at Bonding's own bounded inventory (`maxSwap`) while `reserveIn`/`reserveOut` are entirely attacker-controlled (the attacker funds and `mint()`s the HyperSwap pair before graduation, at whatever size and skewed ratio they choose), an attacker can size the pre-existing reserves so that the standard V2 fee formula (`amountInWithFee*reserveOut/(reserveIn*1000+amountInWithFee)`) rounds `expectedOut` to `0` even though the reserves are not "negligible dust" relative to `tokensForLP`/`ltFromPair`. This is not gated by `DIRECT_MINT_PRESEED_BPS` at all — that check only fires when *both* sides are tiny, but `_pairRebalance` can return `false` for large, deliberately-skewed reserves too.

When that happens, `_seedRebalancing` falls through to `_seedDirectMint`, which unconditionally transfers Bonding's full `(tokensForLP, ltFromPair)` into the pair and calls `IUniswapV2Pair(pair).mint(lpLock)`: [5](#0-4) 

Standard UniswapV2 `mint()` computes `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)`. Because the attacker's pre-seeded reserves are deliberately off the curve-close ratio, the `min()` selects the smaller (attacker-favoring) side, so the *entire* excess of `tokensForLP`/`ltFromPair` on the larger side becomes bare reserves that inflate the pool's price against the LP-lock's minted share — effectively donating value to the attacker's pre-existing LP position, exactly the scenario the `_seedRebalancing`/`_pairRebalance` machinery exists to prevent, but which the fallback's implicit "reserves must be dust" assumption fails to actually enforce for this reachable branch.

### Impact Explanation
This breaks the protocol's explicit invariant that "the LP opens at the exact curve-close ratio" and that hostile pre-seeds cannot capture more than a `DIRECT_MINT_PRESEED_BPS`-bounded subsidy. A sufficiently large, ratio-skewed HyperSwap V2 pre-seed lets an attacker capture a share of the graduation's `tokensForLP`/`ltFromPair` deposit disproportionate to their own contribution — a permissionless, unprivileged-caller theft of value that would otherwise accrue to `LPLock` (and thus to the token's holders/creator) at graduation. This is a concrete instance of "an LP seeded away from the curve close price," which the report's validation criteria explicitly treats as in-scope Medium+ impact.

### Likelihood Explanation
Any unprivileged address can permissionlessly call `IUniswapV2Factory.createPair(token, lt)` and `pair.mint()` to pre-seed a token's future graduation pair before `Bonding.finalizeGraduation` ever runs (`_ensureUniswapV2Pair` merely fetches or lazily creates the pair — it does not restrict who may create/seed it first). Sizing the pre-seed reserves so that `getAmountOut` on Bonding's *bounded* rebalance budget rounds to zero is a straightforward, deterministic calculation from public pair math and known protocol constants (`LP_RESERVE`, `graduationThresholdUsd`, LT `exchangeRate`), making the attack reliably reproducible rather than probabilistic.

### Recommendation
Do not treat `_pairRebalance` returning `false` as universally implying "negligible reserves." Before falling back to `_seedDirectMint` on the rebalance path, independently re-verify that the pre-existing reserves are within an acceptable bound relative to `tokensForLP`/`ltFromPair` (i.e., apply the same or a comparable band check used for the direct dust case), and if they are not, choose a different remediation (e.g., increase precision of the swap, split into multiple swaps, or explicitly cap the LP-lock's exposure/require a minimum output share) rather than silently minting into a still-skewed pool.

### Proof of Concept
1. Attacker observes a `Curve`-stage token/LT pair in `Bonding` approaching graduation (or triggers it via `Bonding.triggerGraduation`).
2. Before `finalizeGraduation` runs, attacker calls `IUniswapV2Factory(uniswapV2Factory).createPair(token, lt)` and funds+`mint()`s the pair with a large, deliberately skewed `(token, lt)` ratio, sized so that for Bonding's known `tokensForLP`/`ltFromPair` budget, `IUniswapV2Pair(pair).getAmountOut(maxSwap, tokenIn)` rounds to `0` under the standard V2 fee formula.
3. Any address calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedUniswapV2Direct` sees `totalSupply != 0` → `_seedRebalancing`; the reserves are not below `DIRECT_MINT_PRESEED_BPS` on both sides, so it attempts `_pairRebalance`, which returns `false` (`expectedOut == 0`) due to the attacker-tuned reserve sizing rather than genuine dust.
4. `_seedRebalancing` falls back to `_seedDirectMint`, transferring the full `tokensForLP`/`ltFromPair` into the skewed pool and minting LP to `LPLock` at the attacker's ratio, donating the mismatched side to the attacker's pre-existing LP position instead of the curve-close price.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
