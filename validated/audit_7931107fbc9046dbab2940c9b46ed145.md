### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is covered by the HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` value taken directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` verifies covers only the raw request body, not this header. This lets the `shop` field handed to a host application's webhook handler diverge from the tenant that the signed body actually belongs to.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against `verifiable_query.to_signable_string` [2](#0-1) . Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC at all [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, and then forwards `request.shop` unmodified into `WebhookMetadata`, which is the only tenant-identifying field passed to the host application's handler [4](#0-3) [5](#0-4) .

The identity binding that should hold is: `shop header verified-by-HMAC == shop attributed to the webhook payload`. Because the header is never part of the signed bytes, this equality is not enforced by the gem — any request that reproduces a valid HMAC for a given body (e.g., a genuine webhook delivery captured and replayed, or any scenario where the raw body's HMAC can be reused) can be paired with an arbitrary `shop-domain` header and will still pass `HmacValidator.validate`, then be delivered to the handler tagged as coming from a different shop than the one whose secret/body actually produced the signature.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to provide to host applications: the `shop` value in `WebhookMetadata` is the field host apps use to scope database writes, look up sessions, or select per-shop lookup tokens. Because it is not authenticated, a party who can influence or capture one valid `(body, hmac)` pair for shop A can cause the library to hand that payload to the host app labeled as shop B, letting an attacker inject or misattribute webhook-driven data across tenants. Per the scope's Critical bucket ("cross-tenant access"), this qualifies as a cross-tenant confusion vector rooted entirely in this gem's `Webhooks::Request`/`Registry` code, independent of how the host app is implemented (the host only receives what `Request#shop` reports).

### Likelihood Explanation
Exploitation requires an attacker to control or replay the `shop-domain` header while keeping a body/HMAC pair valid — e.g., replaying a previously captured legitimate webhook delivery (bodies for events like `app/uninstalled` or `shop/redact` carry no shop-identifying content of their own) with a substituted `shop-domain` header, or any transport where headers can be set independently of the signed payload (this is standard for HTTP webhook delivery, where the app's webhook endpoint parses headers and body separately before calling `Registry.process`). Because Shopify's own webhook payloads frequently omit the shop domain from the JSON body, nothing in the signed bytes prevents the header from being swapped, making this a low-effort mismatch to trigger once a single valid signed body is obtained.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) inside the HMAC-covered signable string, or independently verify that the `shop-domain` header matches a shop identifier embedded in the verified body/session before constructing `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must not be trusted as a tenant boundary by host applications.

### Proof of Concept
```ruby
# Assume ATTACKER has captured one legitimate webhook delivery for shop "victim.myshopify.com":
raw_body = '{"id":1,"email":"a@b.com"}'
hmac_header = "<valid Shopify-computed HMAC over raw_body>"

# Attacker (or a misconfigured relay) redelivers the same body/HMAC but swaps the shop header:
headers = {
  "x-shopify-topic" => "customers/update",
  "x-shopify-hmac-sha256" => hmac_header,   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "attacker-controlled.myshopify.com", # swapped, not covered by HMAC
  "x-shopify-webhook-id" => "1",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body against hmac_header.
# The registered handler receives WebhookMetadata(shop: "attacker-controlled.myshopify.com", ...)
# even though the signed payload belonged to "victim.myshopify.com".
