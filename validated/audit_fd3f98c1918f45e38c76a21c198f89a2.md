### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. An attacker who legitimately receives one correctly-signed webhook for their own shop can replay the exact same body/HMAC pair while substituting an arbitrary victim shop domain in the header, and `Registry.process` will accept it and hand the victim's shop identity plus attacker-controlled body content to the app's webhook handler.

### Finding Description
`Request#shop` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop` comes from the `shopify-shop-domain` header, while `to_signable_string` returns only `@raw_body`. The HMAC validator computes the signature strictly over that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and dispatches it to the app's handler: [3](#0-2) 

The broken identity binding, stated as an equality that should hold but doesn't:

`shop_that_the_HMAC_secret_actually_authenticates == shop_value_passed_to_the_handler`

Before the attack (a genuine Shopify-delivered webhook), both sides are the shop that owns the webhook subscription, because Shopify itself sets both the body and the `shop-domain` header consistently. After the attack, an unprivileged user who owns a shop (and thus receives a validly-HMAC-signed webhook for their own body content) can keep the valid `(raw_body, hmac)` pair unchanged and swap only the `shop-domain` header to any other shop's domain when POSTing directly to the app's public webhook endpoint URL (this endpoint is a normal internet-reachable HTTP route, not restricted to Shopify's IPs by this gem). `HmacValidator.validate` still passes because it never inspects the header, so `Registry.process` calls the handler with `data.shop == victim_shop` and `data.body` fully attacker-controlled.

The documentation explicitly instructs apps to key their tenant-scoped work off `data.shop`: [4](#0-3) 

so any app following this documented pattern will process attacker-authored webhook content under another merchant's identity — a cross-tenant data-injection/confusion vector rooted entirely in this gem's failure to bind the `shop` field into the signed bytes.

### Impact Explanation
This breaks tenant isolation between unrelated Shopify merchants using the same installed app: an attacker who is a legitimate app installer/user on their own shop can cause the app to attribute attacker-chosen webhook payload content to a victim shop of the attacker's choosing, without ever needing that victim's credentials, access token, or `client_secret`. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any user able to install the app (a normal, unprivileged step for a public/embedded app) can trigger a webhook for their own shop, capture the raw body + HMAC signature Shopify sent, and replay it directly to the app's public webhook endpoint with a forged `shop-domain` header. No special network position, secret material, or race condition is required — this is a straightforward request-replay-with-header-substitution reachable from any client on the internet that knows the app's webhook URL (typically discoverable/guessable, e.g. `/callback/orders/create`).

### Recommendation
Bind the shop identity into the signed material, or at minimum verify that the shop the app resolves via `data.shop` actually owns a webhook subscription that would legitimately produce that specific body. Concretely: include the `shop-domain` (and ideally `topic`/`webhook-id`) header values as part of `to_signable_string` so a mismatch invalidates the HMAC, or independently verify in `Registry.process` that the shop's registered webhook secret/subscription corresponds to the claimed `shop-domain`. Track this together with `topic`/`webhook_id` uniqueness checks apps are already advised to implement.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers `orders/create` (attacker can freely control fields such as line-item titles, notes, etc. in their own order).
2. Shopify sends the app a webhook to the registered callback URL with:
   - body: `{"id":123, "note": "<attacker-controlled>"}`
   - header `x-shopify-hmac-sha256`: valid HMAC of that exact body computed with `Context.api_secret_key`
   - header `x-shopify-shop-domain`: `attacker.myshopify.com`
3. Attacker captures this exact `(raw_body, hmac)` pair, then sends a new HTTP POST directly to the app's public webhook endpoint with the same body and same `x-shopify-hmac-sha256` value, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only, which still matches, so validation succeeds.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `data.shop == "victim.myshopify.com"` and `data.body` containing the attacker's content, even though `victim.myshopify.com` never sent this webhook.
