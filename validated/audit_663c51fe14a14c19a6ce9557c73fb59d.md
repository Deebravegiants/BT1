## Analysis Result

### Title
Webhook Shop/Topic/Webhook-ID Headers Are Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`) fields exclusively from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body. Any attacker who can obtain one authentically-signed webhook body/HMAC pair (e.g., by installing the app on their own store) can replay that exact body+HMAC while substituting the `shopify-shop-domain` header for a victim shop, and the request will pass HMAC validation and be dispatched to the app's handler as if it originated from the victim shop.

### Finding Description
The library's identity binding for webhooks is broken in the same way as the reported bug class: a field that is *acted upon* (`shop`, used to attribute the webhook data to a specific merchant) is not *covered by the cryptographic proof* (the HMAC).

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `Request#shop`, `#topic`, and `#webhook_id` are read straight from headers, with zero cryptographic binding to the body: [2](#0-1) 

- `Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler — the very fields excluded from the signed data: [3](#0-2) 

- `HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` (the raw body, for webhooks) and compares it to the received HMAC; it has no notion of shop/topic binding: [4](#0-3) 

Equality that should hold but doesn't: `shop_used_by_handler == shop_that_the_HMAC_actually_authenticates`. Before the attack, both are the attacker's own shop (legitimately signed). After the attack, the handler receives `shop = victim-shop.myshopify.com` while the HMAC only ever authenticated the *body*, not that shop value — the two sides diverge, exactly mirroring the `permitSingle.details.token != order.inputToken` mismatch in the source report.

### Impact Explanation
This crosses a tenant boundary using data an unprivileged internet user can obtain unprivileged (any developer can install the app on a free/dev store and receive a real, validly-signed webhook for that store). By replaying the captured body and HMAC with a forged `shopify-shop-domain` header, the attacker causes the host app's webhook handler to process/store data under a different, arbitrary shop identity. Depending on how the host application's handler uses `WebhookMetadata#shop` (which is the gem's documented, intended way to identify the tenant for a webhook — see `handler.handle(data: WebhookMetadata.new(topic:, shop:, ...))`), this enables cross-tenant data injection/corruption, satisfying the "cross-tenant access" Critical-impact category, since the trust boundary violated is inherent to this gem's own webhook-verification API, not a misuse by the host app.

### Likelihood Explanation
Moderate-to-high: obtaining one authentic webhook only requires installing the app for free on a throwaway/dev store, which any internet user can do for a public embedded Shopify app. No access token, `client_secret`, or privileged account is required — only participation as a normal (if malicious) merchant, which matches the "unprivileged internet user" framing used for the analog.

### Recommendation
Bind the trust-sensitive identity fields into the signed payload validation, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified request instead of trusting raw headers post-hoc. Concretely: after validating the body HMAC, require the caller (host app) to also confirm `request.shop` matches an installed/known session for that shop before invoking the handler, or extend `to_signable_string`/validation to incorporate the header values that `WebhookMetadata` exposes as trusted identifiers, closing the gap between what is verified and what is acted upon.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook (e.g., `orders/create`) with a legitimate `shopify-hmac-sha256` computed by Shopify over the raw JSON body.
2. Attacker captures the raw body `B` and its valid HMAC `H = HMAC_SHA256(secret, B)`.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` and any desired `shopify-topic`/`shopify-webhook-id`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(secret, B)` — matches `H` — validation succeeds: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though the HMAC never authenticated that shop association.
