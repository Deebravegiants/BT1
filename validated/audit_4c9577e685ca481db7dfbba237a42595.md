### Title
Webhook HMAC signature does not bind `shop`/`topic` headers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator` verifies covers exclusively the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler are read straight from unauthenticated HTTP headers and are never included in the signed data, breaking the binding `hmac_is_valid(body) == (shop, topic) trusted by handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — the `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and `topic` (from the `shopify-topic` header) are parsed straight from request headers and are **not** part of the bytes that get HMAC'd.

`Utils::HmacValidator.validate` computes and compares the HMAC strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

`Webhooks::Registry.process` trusts `request.topic` and `request.shop` (unauthenticated header values) to dispatch the handler and build `WebhookMetadata`, using only the body-only HMAC check as its authentication gate: [3](#0-2) 

Because the signature never covers `shop` or `topic`, any request whose **body bytes** happen to match a body that was ever validly HMAC-signed by Shopify (e.g., one the attacker received for their own shop after installing the app) can be resubmitted with different `shopify-shop-domain` and `shopify-topic` header values, and it will still pass `HmacValidator.validate`. The handler then receives a `WebhookMetadata` claiming an arbitrary `shop`/`topic` of the attacker's choosing, e.g.: [4](#0-3) 

This breaks the identity binding: `computed_hmac(body) == valid` should imply `(shop, topic)` were the values Shopify actually signed for, but here `shop`/`topic` are independent of the signed bytes.

### Impact Explanation
This is a cross-tenant vulnerability: an unprivileged attacker who can install the public app on their own shop (or otherwise obtain one legitimately-signed webhook body/HMAC pair) can replay that exact `(raw_body, hmac)` pair while forging the `shop`/`topic` headers to any value. Downstream handler code built on top of this gem (which is documented to trust `WebhookMetadata#shop` and `#topic` as authenticated) will process the event as if it genuinely originated from the victim shop and/or under a different topic (e.g. compliance topics like `shop/redact`, `customers/redact`, `app/uninstalled`), potentially causing cross-tenant data corruption, unauthorized data deletion, or incorrect app-uninstall bookkeeping for a shop the attacker does not control.

### Likelihood Explanation
Exploitation only requires the attacker to have received at least one legitimately-signed webhook for a shop they control (trivial for any developer who installs the public app), and the ability to send an HTTP POST to the app's webhook endpoint with custom headers — no access token, no `api_secret_key`, and no privileged account is required. The library itself performs no additional binding between the signed bytes and the shop/topic, so every consumer of this gem's `Webhooks::Registry.process` inherits the gap.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) header values as part of the signable/verified data, or otherwise cryptographically bind them to the HMAC before dispatching to handlers, so that a valid signature for one shop/topic cannot be replayed with substituted `shop`/`topic` header values in `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `raw_body` with header `x-shopify-hmac-sha256: <valid_hmac_for(raw_body)>`.
2. Attacker resends the exact same request to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any topic registered by the app)
   - keeping `raw_body` and `x-shopify-hmac-sha256` unchanged.
3. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only (per `Request#to_signable_string`) and it matches, so `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", ...)`, causing the app to act on behalf of `victim-shop.myshopify.com` despite the request never being signed for that shop or topic.
