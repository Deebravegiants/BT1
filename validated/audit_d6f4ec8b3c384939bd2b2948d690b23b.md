### Title
Webhook shop identity not bound by HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) fields are read directly from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches to the app's handler using `request.shop` as the tenant identifier, without that value ever being cryptographically bound to the signature that was verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no relation to the HMAC computation: [2](#0-1) 

`HmacValidator.validate` verifies the signature by recomputing HMAC over `to_signable_string` only, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that has installed the app, and the identity binding the equality `verified_bytes == shop_claimed_by_handler` never holds — the HMAC only certifies `raw_body`, not `shop`. Any actor who can obtain one genuine `(raw_body, hmac)` pair from Shopify (e.g., by installing the app on a shop they control and receiving a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because the header is not part of the signed string, and the handler will process the payload believing it originated from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the webhook mechanism is supposed to guarantee: the app's business logic (order/customer/GDPR/app-uninstalled handlers, etc.) keys off `WebhookMetadata#shop`, which any minimally-privileged app installer can spoof to point at any other merchant's shop domain. Depending on how host applications use the `shop` field (e.g., to look up records, trigger data deletion, or mark uninstall state), this enables cross-tenant data corruption or disclosure — matching the "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (an ordinary, unprivileged action for any Shopify merchant/developer) to obtain a valid `(body, hmac)` pair, and then send a forged HTTP request with a different `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to receive one legitimate webhook from Shopify.

### Recommendation
Include the shop identity (and other trust-relevant headers like `topic`/`webhook_id`) in the value verified against the HMAC, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is exposed via `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must not be used as the sole tenant key without additional verification (e.g., cross-checking against a known/installed shop list) in `Registry.process`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com` and configure a webhook subscription (e.g., `orders/create`).
2. Trigger a real event, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it is computed only over the body with the app's shared `client_secret`.
3. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `raw_body`.
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the forged payload as if it came from the victim shop: [5](#0-4)
