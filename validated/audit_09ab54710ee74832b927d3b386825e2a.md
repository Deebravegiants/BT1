### Title
Accrual-time `i128` value overflow permanently freezes a market before the index cap engages - (File: common/src/rates/index.rs)

### Summary
Every controller verb accrues interest first, and accrual computes `borrowed.mul(env, new_borrow_index)` / `supplied.mul(env, old_index)` in `i128`. On a sufficiently large book, the RAY-scaled total value overflows `i128` while `borrow_index` is still well below `MAX_BORROW_INDEX_RAY`, so `update_indexes` panics with `GenericError::MathOverflow`. Since `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `flash_loan`, `claim_revenue`, and `recapitalize` all route through accrual, the entire market freezes permanently — suppliers cannot exit and borrowers cannot repay.

### Finding Description
`update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY`, and `update_supply_index` saturates the grown index at `MAX_SUPPLY_INDEX_RAY` via `mul_div_floor_saturating` [1](#0-0) . But before those caps can help, `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)` with the panicking (non-saturating) multiply [2](#0-1) , and `update_supply_index` computes `supplied.mul(env, old_index)` the same way [3](#0-2) . `Ray::mul` is `x * y / RAY` in `i128`/`I256` per `fp_core`, and panics when the result does not fit [4](#0-3) .

Caps only bound the *scaled* book: `max_cap_for_decimals` guarantees `cap * RAY` fits `i128`, i.e. value-at-index-1.0 fits — it does not account for index growth, so at index ~170x the value overflows regardless [5](#0-4) . Once the stored scaled book and the index jointly exceed the `i128` value ceiling, *every* call that accrues panics — there is no non-accruing escape hatch, making the freeze permanent rather than transient. The protocol's own threat model acknowledges the gap ("Finite RAY value capacity can be exhausted before the index ceiling. Synchronizing an overlarge book can then fail before an otherwise risk-reducing operation") [6](#0-5) .

### Impact Explanation
Permanent freezing of all user funds in the affected market: suppliers cannot `withdraw`, borrowers cannot `repay`, liquidators cannot `liquidate`, and `claim_revenue`/`recapitalize` cannot run, because each entrypoint performs index accrual first. The harness test demonstrates the terminal state concretely: after the overflow, `try_withdraw` and `try_repay` both fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — the cap never engaged [7](#0-6) . This is the direct analog of the CVE's "hang or frequently repeatable crash → complete DOS".

### Likelihood Explanation
Reachable entirely with unprivileged verbs: `supply`, `borrow`, and `update_indexes` (which only requires an authorized caller, not a role) [8](#0-7) . The attacker's cost is capital, not privilege: fill a market to its supply cap (up to `i128::MAX / 10^(RAY_DECIMALS - decimals)` base units — astronomically large for high-decimal tokens) and drive sustained high utilization so the index compounds. On a high-decimal (e.g. 18-decimal) market with a steep rate curve, the harness shows the cliff is reached in well under 40 years at ~98% utilization even with caps lifted to the representable domain; the window shrinks for markets governed near `max_cap_for_decimals` since caps are the only bound on scaled book size [9](#0-8) . Requirements (whale-scale deposits, multi-year high utilization, a steep-curve market) place this at Medium — plausible on real deployments for cap-poor configurations, and irreversible once crossed.

### Recommendation
Bound the *value* ceiling, not just the index ceiling:
- In `update_supply_index` and `calculate_supplier_rewards`, use `mul_div_floor_saturating`-style value computation or detect overflow and clamp `new_borrow_index` to `i128::MAX / borrowed` before multiplying, so accrual degrades to capped-index behavior instead of panicking.
- Alternatively enforce a dynamic supply cap of `max_cap_for_decimals(d) / current_index` at `supply`/`borrow`/`flash` time so no book can be pushed past the value ceiling.
- Add a non-accruing emergency path (e.g. `recapitalize` or `withdraw` variant that settles at the last stored index) so a market already past the cliff can still unwind.

### Proof of Concept
Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` [10](#0-9) :

1. Create an 18-decimal market on the XLM rate curve; set caps to the representable domain.
2. `supply(BOB, BIG18, 1e9 * 1e18)` — permissionless.
3. `supply(ALICE, COL, ...)` then `borrow(ALICE, BIG18, 0.98 * principal)` — drives 98% utilization, permissionless.
4. Advance ledger time; call `update_indexes(caller, [BIG18])` each period (any authorized caller).
5. Once `borrowed_scaled * new_borrow_index > i128::MAX`, `update_indexes` reverts with `GenericError::MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. From that point `withdraw`, `repay`, `liquidate`, `borrow`, `supply`, `claim_revenue`, and `recapitalize` on `BIG18` all panic with `MATH_OVERFLOW` — permanent market freeze.

```rust
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
```
