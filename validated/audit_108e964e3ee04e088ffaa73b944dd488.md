## Analysis

The reported bug class — governance splitting a *value pair* (token address + amount) across two independent transactions, letting an unprivileged actor act in the exploitable window between them — maps to Hyperbridge's `pallet-bandwidth` / `BandwidthManager` tier configuration, where the byte allowance and the price for the same tier live on two different chains and are updated by two independent, non-atomic governance calls.

### Title
Non-atomic cross-chain tier (bytes/duration, price) updates allow purchasers to buy mispriced bandwidth during the update window - (File: `modules/pallets/bandwidth/src/lib.rs`, `evm/src/apps/BandwidthManager.sol`)

### Summary
A bandwidth tier's value is defined by two coupled parameters that live on different chains: `(bytes, duration_secs)` on the Hyperbridge pallet, and `price18d` on the per-chain `BandwidthManager` contract. Governance updates them via two separate calls — `set_tier` (local, pallet-side) and `dispatch_set_tiers` (cross-chain, delivered asynchronously via a relayer to the EVM manager). Because these are independent transactions with no atomicity guarantee across them, and the cross-chain leg is delayed by relayer delivery time, any unprivileged buyer can call `BandwidthManager.purchase()` in the window where the byte/duration side has already changed on the pallet but the price side is still stale on the manager (or vice-versa), buying bandwidth at an unintended price/bytes ratio.

### Finding Description
`set_tier` writes `Tiers::<T>::insert(tier, cfg)` immediately and takes effect on the very next block on Hyperbridge: [1](#0-0) 

`dispatch_set_tiers` instead only *dispatches* a cross-chain `SetTiers` message; it does not update anything locally on the EVM manager — the price only lands once a relayer delivers the message and `onAccept` executes: [2](#0-1) [3](#0-2) 

The manager's `purchase()` is public and unprivileged — any buyer can call it at any time, pulling the fee token amount computed strictly from the manager's *currently stored* `tierPrice[tier]`: [4](#0-3) 

The pallet's `on_accept` (credit path) uses whatever `TierConfig` (`bytes`, `duration_secs`) is *currently* stored for that tier discriminant at the time the purchase message is processed — independent of what price was actually paid on the EVM side: [5](#0-4) 

The documentation itself acknowledges the two sides are updated separately and must be manually kept in sync, explicitly warning of exactly this hazard: [6](#0-5) [7](#0-6) 

This is structurally identical to the UMA bug: two governance calls that must land together (token+amount there; price+bytes here) but are executed as independent transactions, with an unprivileged third party (there: `proposeTransactions`; here: `purchase()`) able to act in the gap and realize an unintended value ratio. Here the gap is worse than a same-chain front-run window — it spans an entire cross-chain relay delay, since `dispatch_set_tiers`'s effect on the EVM side only lands after relayer delivery, while `set_tier`'s effect on the pallet side is instantaneous.

### Impact Explanation
Whenever governance rebalances a tier's $/byte rate (increasing `bytes`/`duration_secs` alongside a price change, or the reverse), a purchaser monitoring the pallet's `TierSet` event / mempool can call `purchase()` on the EVM manager while it still charges the stale price, then have the credit computed against the already-updated (more generous) `TierConfig` on the pallet — receiving materially more bandwidth than the intended price should have bought. This is an economic exploit against protocol revenue: bandwidth subscriptions are effectively "minted" at an unintended, under-collateralized rate relative to what governance intended, analogous to an unbacked-mint condition on the credited asset (bandwidth allowance).

### Likelihood Explanation
Reachable by any unprivileged bandwidth purchaser with no special permissions — just calling the public `purchase()` function. It requires governance to perform a coordinated tier-value rebalance (changing bytes/duration and price together), which per the docs is an expected/likely maintenance operation ("Update a tier's byte budget or duration" in the Upgrades table), and the cross-chain delivery delay for `dispatch_set_tiers` provides a comfortably large and externally observable window (via `TierSet`/`TiersDispatched` events) for an opportunistic purchaser to act in.

### Recommendation
Treat a tier-value rebalance as a single atomic operation from the purchaser's perspective: either (a) have the pallet stage the new `TierConfig` without activating it until the corresponding price update is confirmed delivered to the target manager (e.g., gate activation behind an ack/commitment check), or (b) have `BandwidthManager.purchase()` pin the byte/duration terms into the dispatched message itself (fetched via a prior cross-chain read, or embedded at price-set time) so the pallet credits exactly the tier terms that were in effect when the price was last synced, rather than whatever `TierConfig` happens to be live at credit time.

### Proof of Concept
1. Governance calls `dispatch_set_tiers(target, [(TierOne, new_higher_price)])` intending to also increase `TierOne`'s bytes — the message is dispatched but not yet delivered/executed by `onAccept` on `target`'s `BandwidthManager`.
2. Before the relayer delivers it, governance calls `set_tier(TierOne, Some(TierConfig{bytes: much_larger, duration_secs: ...}))` on the pallet — this is a local write, effective immediately: [8](#0-7) .
3. A purchaser observes `TierSet` and, in the window before the relayer delivers the `SetTiers` message, calls `BandwidthManager.purchase(app, TierOne, 1, chain)` — this charges the *old, lower* `tierPrice[TierOne]` still stored on the manager: [9](#0-8) .
4. The dispatched purchase message reaches `pallet-bandwidth`'s `on_accept`, which computes the credited allowance using the *already-updated, much larger* `TierConfig` for `TierOne` — the purchaser receives the new large byte allowance while having paid only the old low price.

			tier: TierIndex,
			config: Option<TierConfig>,
		) -> DispatchResult {
			<T as pallet_ismp::Config>::AdminOrigin::ensure_origin(origin)?;
			match config {
				None => Tiers::<T>::remove(tier),
				Some(cfg) => {
					ensure!(cfg.bytes > 0 && cfg.duration_secs > 0, Error::<T>::InvalidTierConfig);
					Tiers::<T>::insert(tier, cfg);
				},
			}
			Self::deposit_event(Event::TierSet { tier, config });
			Ok(())
		}

		/// Push tier prices to a remote `BandwidthManager` (the EVM
		/// side holds prices; this pallet holds bytes/duration).
		/// `updates` is `(tier, price18d)` pairs.
		#[pallet::call_index(4)]
		#[pallet::weight(T::DbWeight::get().writes(1))]
		pub fn dispatch_set_tiers(
			origin: OriginFor<T>,
			target: StateMachine,
			updates: Vec<(TierIndex, U256)>,
		) -> DispatchResult {
			<T as pallet_ismp::Config>::AdminOrigin::ensure_origin(origin)?;
			ensure!(!updates.is_empty(), Error::<T>::EmptyTierBatch);
			let manager = BandwidthManager::<T>::get(&target).ok_or(Error::<T>::UnknownManager)?;

			let count = updates.len() as u32;
			let rows: Vec<Tier> = updates
				.into_iter()
				.map(|(t, p)| {
					let id_u32: u32 = t.into();
					Tier { tier: to_alloy_u256(U256::from(id_u32)), price: to_alloy_u256(p) }
				})
				.collect();

			let mut body = vec![ACTION_SET_TIERS];
			body.extend(rows.abi_encode_params());

			let commitment = Self::dispatch_governance(target, manager, body)?;
			Self::deposit_event(Event::TiersDispatched { target, count, commitment });
			Ok(())
		}

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

        emit BandwidthPurchased({
            payer: msg.sender,
            feeToken: feeToken,
            tier: tier,
            months: months,
            amountPaid: amount,
            app: app,
            chain: chain,
            commitment: commitment
        });
    }
