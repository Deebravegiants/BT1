This confirms the vulnerability: the HMAC only binds `@raw_body`, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — including the tenant identifier `shop` — are read straight from unauthenticated headers and passed to the handler.

### Title
Webhook `shop` (tenant) identity is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC computation [2](#0-1) . `Registry.process` validates only this body-only HMAC and then forwards the unauthenticated `request.shop` value straight into the handler as the tenant identifier [3](#0-2) .

### Finding Description
The equality the gem is supposed to guarantee is: `shop_used_by_handler == shop_that_actually_produced_the_signed_bytes`. Because `HmacValidator.validate` (via `VerifiableQuery#to_signable_string`) only signs `@raw_body` [1](#0-0) [4](#0-3) , the `x-shopify-shop-domain` header is free for an attacker to set independently of the HMAC signature that Shopify computed for the original event. Since the HMAC secret (`Context.api_secret_key`, the app's shared `client_secret`) is identical for every shop that installs the app — not per-shop — any unprivileged user who legitimately installs the public app on a shop they control receives real webhook deliveries with a body+HMAC pair that is valid under the app's shared secret. That user can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` (it only checks the body bytes), so `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with the attacker-chosen victim shop [3](#0-2) . Any host application that uses `data.shop` to key merchant records, look up the shop's offline token, or otherwise scope actions per tenant (the documented/intended use of `WebhookMetadata#shop`) will act on attacker-controlled data under a victim shop's identity.

### Impact Explanation
This breaks tenant isolation: an attacker with only an install on their own (attacker-controlled) shop can make the app process arbitrary attacker-chosen webhook payloads as if they belonged to a different, victim shop. This falls under "cross-tenant access," since the identity binding the gem is expected to enforce (HMAC covers only what the app is allowed to trust as originating from that shop) does not include the shop identifier itself.

### Likelihood Explanation
Any user who can install the public app on a shop they control (a normal, unprivileged action for a public/embedded Shopify app) can capture a real `(body, hmac)` pair from their own legitimate webhook deliveries and replay it with a forged `shop-domain` header directly against the app's public webhook endpoint. No access to `api_secret_key`, tokens, or Shopify infrastructure is required — only network access to the app's webhook receiver.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the value that is HMAC-verified, or otherwise independently authenticate the shop before trusting `request.shop`/`WebhookMetadata#shop` for tenant-scoped actions — e.g., verify the header value against the shop stored in the session that was used to register that specific webhook subscription, rather than trusting the header on its own.

### Proof of Concept
1. Install the target public app on an attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook POST, e.g. `raw_body = '{"id":1}'` with header `x-shopify-hmac-sha256: <valid_hmac>` (valid under the app's shared `api_secret_key`).
2. Send a new HTTP request to the same webhook endpoint with the identical `raw_body` and identical `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC [5](#0-4) ; `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` [6](#0-5) , causing the host application to act on attacker-supplied data attributed to the victim shop.
