### Title
Webhook HMAC only signs the raw body, not the `shop-domain` header, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks binds *only* the JSON body to the app's `client_secret`. The `shop-domain`, `topic`, `api-version`, and `webhook-id` HTTP headers are read directly from attacker-controlled request headers and are never part of the signed material, yet `Registry.process` trusts `request.shop` as the tenant identity handed to the app's handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers via `shopify_header`, which reads directly from the HTTP request headers supplied by whoever calls the route: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the raw body) and compares it with the supplied `hmac` header: [4](#0-3) 

`Registry.process` treats a passing HMAC check as sufficient authorization to hand `request.shop` (and `request.topic`, `request.webhook_id`) straight to the registered handler as the trusted tenant identity: [5](#0-4) 

The identity binding that should hold is: `shop header == shop the HMAC authenticates`. In reality the HMAC authenticates nothing but the byte-identical body; the `shop-domain` header is unauthenticated. Any entity that can obtain **one** genuine `(raw_body, hmac)` pair signed with the app's `client_secret` — trivially done by installing the app on their own free/dev store and capturing any webhook Shopify sends them — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shop-domain` (and, since `topic` is also unauthenticated, an arbitrary registered `topic`) header value naming a different, victim merchant. `HmacValidator.validate` still returns `true` because it only re-hashes the raw body, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: the "authenticated shop" and "the shop passed to application logic" are not the same value. Depending on how the host app's handler uses `shop`/`topic` (session lookup, data deletion, state changes keyed by shop, e.g. an `app/uninstalled` handler that revokes/erases stored access tokens for `data.shop`), an attacker can trigger actions attributed to a shop they have no relationship with — a cross-tenant action performed under the guise of a validated Shopify webhook. This matches the Critical bucket ("cross-tenant access") in scope.

### Likelihood Explanation
Likelihood is moderate-to-high for any app: obtaining one genuine signed payload only requires installing the target app on any store the attacker controls (a normal, unprivileged action for any developer using the public app), and no secret, token, or privileged access is ever needed to forge the header fields, since the HTTP headers of the replayed request are entirely attacker-controlled. The only limiting factor is that the replayed body content is fixed to whatever the attacker's own store's webhook contained, but for topics whose body doesn't matter for the action taken (e.g., `app/uninstalled`, `shop/redact`) this is a full spoof.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value(s) in the signed/verified material, or otherwise cryptographically bind the shop identity to the signature (e.g., verify the header-derived shop against a value that is itself covered by the HMAC, or require the caller to additionally verify the shop against session/store state before trusting `request.shop`). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant-scoped side effects without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `app/uninstalled`, capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers as-is: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H`, so validation passes: [7](#0-6) 
5. The registered handler for `app/uninstalled` is invoked with `WebhookMetadata#shop == "victim.myshopify.com"`, even though nothing about that request was ever authenticated for `victim.myshopify.com` — only the body bytes originally issued for the attacker's own store were verified.

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
