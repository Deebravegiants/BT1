### Title
Governance cannot rotate the price-aggregator admin/ownership: admin-restricted ownership functions are unreachable through `AdminOperation` — (File: contracts/governance/src/op.rs)

### Summary
The bug class is "an admin-only setter exists, but the admin (governance) has no way to invoke it, so a critical protocol address is permanently frozen." In XOXNO Lending, governance is not a generic timelock executor: `propose()` only schedules operations produced by `resolve_op()`, which pattern-matches on the closed `AdminOperation` enum in `contracts/governance/src/op.rs` (lines 124–431). Every cross-contract call governance can ever make must appear as a variant there. The enum routes exactly three calls to the price aggregator — `set_oracle`, `set_tolerance`, and `upgrade` (`price_aggregator_operation` / `sensitive_price_aggregator_operation`, lines 82–102, 353–360, 389–405) — while `contracts/price-aggregator/src/admin.rs` implements the aggregator's admin/ownership surface (admin setters and ownership functions, per the admin module). There is no `TransferAggregatorOwnership`, `SetAggregatorAdmin`, or equivalent variant, so the aggregator's privileged admin/ownership functions can never be invoked by their own authorized caller — the exact `changeDAO()` analog.

### Finding Description
`resolve_op()` is the only path from a governance proposal to an executable `ResolvedOperation`; `propose()` in `contracts/governance/src/timelock/lifecycle.rs` (lines 72–78) schedules only what `operation_for_admin_op` produces from that enum, and `execute()` requires the operation id to have been scheduled that way (lines 99–110). There is no arbitrary-call escape hatch. Auditing the full `AdminOperation` match shows aggregator-targeted operations limited to `ConfigureAssetOracle` → `set_oracle`, `EditOracleTolerance` → `set_tolerance`, `UpgradePriceAggregator` → `upgrade`, plus `SetPriceAggregator` which only repoints the controller/governance storage at a new aggregator address. The aggregator's own `src/admin.rs` entrypoints (admin transfer/rotation) have no corresponding variant. Any governance attempt to rotate the aggregator admin reverts during `propose()`, since no `AdminOperation` encodes it.

### Impact Explanation
The aggregator's privileged role becomes immutable. If the aggregator admin is the governance contract (as implied by `sensitive_price_aggregator_operation` routing `upgrade` through the timelock), then any admin-gated functionality that cannot be expressed as one of the three whitelisted calls is permanently dead code, and ownership can never be transferred to a successor governance contract — a protocol-migration or admin-key-compromise scenario would strand the aggregator forever. This mirrors the Vader `changeDAO()` finding: a setter exists and is correctly authorized, but the authorized caller structurally cannot reach it. If the aggregator admin is instead an EOA, the same conclusion holds with the roles reversed (governance cannot take over, and any aggregator function gated on "caller is governance" beyond the three variants is frozen).

### Likelihood Explanation
The gap is deterministic, not conditional: it exists in the deployed enum today. Its impact materializes the moment admin rotation or an unlisted admin call is needed (key rotation, governance migration, incident response). No unprivileged call is required — the vulnerability is that the privileged path is unreachable by construction.

### Recommendation
Add an `AdminOperation` variant covering the aggregator's admin/ownership surface (e.g., `TransferAggregatorOwnership`/`SetAggregatorAdmin` resolving via `sensitive_price_aggregator_operation` to the corresponding `admin.rs` entrypoint), and audit every admin-gated function in `contracts/price-aggregator/src/admin.rs`, `contracts/xoxno-oracle/src/admin.rs`, `contracts/controller/src/lib.rs`, and `contracts/pool/src/lib.rs` against `resolve_op()` so each authorized setter has a reachable governance route.
