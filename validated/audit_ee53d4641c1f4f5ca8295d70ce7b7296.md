### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the "trusted" `shop` identifier that is handed to the application's webhook handler is read from an unauthenticated HTTP header. Any party able to obtain one validly-signed webhook (e.g. by installing the app on their own shop) can rewrite the `shop-domain` header to any other value and replay the same body, producing a request that still passes `HmacValidator.validate` but is now attributed to an arbitrary shop in `WebhookMetadata`.

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop` accessor, however, is taken straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content: [2](#0-1) 

`HmacValidator.validate` verifies exactly (and only) `to_signable_string` against the received `hmac`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the *entire* request, including the header-derived `shop`, and forwards it unchanged into `WebhookMetadata` given to the app's handler: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs developers to key subsequent tenant-scoped work (e.g. enqueuing jobs, looking up sessions) directly off `data.shop`, treating it as authoritative: [6](#0-5) 

This is the same class of defect as the reported "lax boundary" issue: a value that is acted upon (`shop`, used analogous to the `isOwnerRegister` bucket decision) is not bound by the integrity check that is supposed to authenticate the whole message (HMAC, analogous to the owner-only `registerToken` guard). Equality that should hold — `shop header value == shop that produced the signed body` — is never verified.

### Impact Explanation
Because the HMAC only binds the body, an attacker who obtains any single genuine, validly-signed webhook delivery (trivially available to anyone who installs/trials the app on their own store — no privileged Shopify or app-owner credentials are required) can resend that exact body to the app's webhook endpoint with a forged `shop-domain` header naming a different merchant. The library will report the HMAC as valid and hand the handler a `WebhookMetadata` claiming the event came from the victim shop. If the host application follows the gem's documented pattern and uses `data.shop` to select the merchant's session/access token or to route/attribute data, this results in cross-tenant data confusion — e.g., a job processed under the wrong shop's session/access token, or data written to the wrong tenant's store.

### Likelihood Explanation
Moderate: exploitation requires the attacker to obtain at least one legitimately-signed webhook body of a topic the app subscribes to (achievable via a free trial/dev store install) and to replay it with a modified header to the same publicly reachable webhook endpoint. No secret material, TLS interception, or privileged account is required — only the ability to install the target app on an attacker-controlled store and issue an HTTP request, both of which are actions available to any unprivileged internet user/developer.

### Recommendation
**Short term:** Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or independently verify the header-derived `shop` against a value the app already trusts (e.g., an active session/known installed shop) before dispatching to the handler. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must not be used alone to select credentials or perform tenant-scoped actions.

**Long term:** Provide an API that lets consumers verify the webhook's shop against their own store of installed shops/subscriptions (e.g., cross-referencing `webhook_id` with a value returned at registration time) so that host applications aren't tempted to trust the raw header value.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store (`attacker-shop.myshopify.com`) and trigger a subscribed webhook topic (e.g. `orders/create`), capturing the genuine request: body `B`, and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's real secret).
2. Replay the request to the same app webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`: [7](#0-6) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [4](#0-3) 
5. Any handler logic that keys off `data.shop` (as shown in the gem's own docs) now operates under the wrong tenant context.
