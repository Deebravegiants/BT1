### Title
Webhook HMAC binds only the raw body, not the `shop`/`topic` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body. The `shop` (and `topic`) values that the handler subsequently trusts as the tenant identity are taken from unauthenticated HTTP headers and are never included in the signed content. Because the HMAC secret (`Context.api_secret_key`) is the *app's* client secret and is identical across every merchant installation, any attacker who controls one shop that has installed the app can capture a validly-signed webhook body and replay it to the app's webhook endpoint with a forged `shopify-shop-domain` (and/or `shopify-topic`) header pointing at a victim shop. The signature still validates, and the handler is invoked believing the event belongs to the victim tenant.

### Finding Description
The equality that should hold is:
`shop_bound_by_hmac == shop_acted_upon_by_handler`

In `ShopifyAPI::Webhooks::Request`, the value returned for the HMAC computation is only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (the raw body) and compares it against a signature computed with `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, the `shop` header value is forwarded unchecked into `WebhookMetadata`, which is what the app's handler code uses to identify which merchant the event belongs to: [5](#0-4) 

Because `Context.api_secret_key` is the same secret for every shop that installs the app (it's the app's client secret, not a per-shop key), a body+HMAC pair captured from a legitimate webhook delivered to an attacker-owned shop remains a valid signature no matter what `shopify-shop-domain` header accompanies it. The binding `hmac(body, api_secret_key)` never incorporates `shop`, so `shop` can be swapped freely post-signature without invalidating the check.

### Impact Explanation
This crosses a tenant boundary: an attacker with any shop that installs the vulnerable app can forge webhook events "from" a different, victim shop by replaying a validly-signed body with a modified `shop`/`topic` header. Any application logic that trusts `WebhookMetadata#shop` to select which merchant's data to update (e.g., order/fulfillment/app-uninstalled webhooks) can be manipulated into acting on behalf of the wrong tenant, i.e., cross-tenant access/manipulation using forged events. This matches the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Requires the attacker to control at least one shop where the target app is installed (a very low bar — installing a public app is unprivileged) and the ability to send raw HTTP requests to the app's public webhook endpoint with attacker-chosen headers. No access token, `client_secret`, or leaked credentials are needed — only observation of one legitimate webhook delivery to their own shop, which they can trigger themselves (e.g., updating an order in their own store). This makes exploitation practical for any unprivileged internet user who can install the app.

### Recommendation
Bind the tenant/topic identity into the authenticated content instead of trusting headers verbatim:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (e.g., verify over a canonical concatenation of header values + body, similar to how Shopify's own webhook signature is computed over the body but should additionally be cross-checked against an expected/registered shop for that webhook subscription), or
- After HMAC success, independently confirm that `request.shop` corresponds to a shop session/subscription that the app actually registered this specific webhook topic for, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives any webhook (e.g., `orders/create`) with a legitimate signed body `B` and HMAC `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - body: `B`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, api_secret_key) == H` — this succeeds because `B` and `H` are unchanged and the secret is shared across all shops.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, causing the app to process an attacker-controlled event as if it originated from the victim shop. [6](#0-5) [7](#0-6) [4](#0-3)
