## Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header from the HMAC-signed content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then trusts the unsigned `shop-domain` header as the tenant identifier passed to the app's webhook handler. This breaks the intended binding: `shop authenticated == shop the handler acts on`.

### Finding Description
The HMAC validation in this gem is: [1](#0-0) 

which verifies `verifiable_query.to_signable_string` against the received HMAC. For webhook requests, `to_signable_string` is defined as: [2](#0-1) 

Only the raw body (`@raw_body`) is included — the `shop` accessor, sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header, is never part of the signed data: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally forwards the unauthenticated `request.shop` value into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identifier: [4](#0-3) 

The library's own documentation confirms that `data.shop` is expected to be used by consuming apps to key work per-merchant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

Since the `api_secret_key` used for signing is shared across all merchants of the app (it is not per-shop), any legitimate merchant who installs the app can:
1. Receive a legitimately Shopify-signed webhook for their own shop (a valid `hmac-sha256` over some body `B`).
2. Replay that exact HTTP request to the app's webhook endpoint, but swap only the `shop-domain` header to a victim shop's domain, leaving body `B` untouched.
3. `HmacValidator.validate` still passes, because it only checks `B` against the shared secret — it never checks that `B` "belongs to" the claimed shop.
4. `Registry.process` then calls the app handler with `WebhookMetadata.shop == victim_shop` and `body == B`, causing the app to process attacker-controlled webhook content under the victim's tenant identity.

This is the same class of bug as the report's `MarketERC20::permit` issue: an action (processing webhook data as belonging to a shop) is performed based on a field (`shop`) that is not bound by the authentication mechanism (the HMAC) actually protecting the request.

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to key per-tenant side effects (queued jobs, database writes, cache invalidation, triggering actions "on behalf of" a shop, etc., as the docs themselves recommend) is exposed to cross-tenant data injection/confusion: an attacker-controlled shop can cause data to be attributed to and processed against a victim shop it doesn't own, without ever needing the app's `client_secret`, access tokens, or the victim's credentials — only its own legitimate (and often self-service) installation of the app.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app for their own shop (a normal, unprivileged action for any public/embedded app) and replay an HTTP request to the app's public webhook endpoint with one header modified — no cryptographic secret is needed since the shop identity is simply never covered by the signature. This is straightforward for anyone building or testing against the gem's documented webhook flow.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed content, or otherwise cryptographically bind the `shop` value to the signed body before exposing it via `WebhookMetadata`. At minimum, `Request#to_signable_string` should not allow the `shop` field to be trusted independently of what was actually signed; `Registry.process` should verify that the shop asserted by the header matches a shop that is expected/authorized to send the given payload (e.g., by requiring the caller to supply the shop being validated against, similar to how `MarketERC20::permit`'s fix requires `msg.sender == spender`).

### Proof of Concept
1. Attacker installs the app for `attacker-shop.myshopify.com`. Shopify sends a legitimately signed webhook: headers include `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
2. Attacker POSTs the same body `B` and same `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: attacker_headers)` is constructed; `to_signable_string` returns `B`, unaffected by the header change (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which (per the gem's own documented pattern) processes/queues work keyed to `victim-shop.myshopify.com` using attacker-supplied body content.
