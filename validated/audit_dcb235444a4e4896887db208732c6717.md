### Title
Webhook HMAC covers only the raw body, allowing forged `shop-domain` header to spoof tenant identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, not the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. `Utils::HmacValidator.validate` therefore only authenticates the body bytes, while `Webhooks::Registry.process` trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identity passed to the app's webhook handler.

### Finding Description
The binding that should hold is: `hmac_verified_bytes == bytes_used_to_derive_tenant_identity`. In this gem that equality is broken:

- `to_signable_string` returns `@raw_body` only [1](#0-0) .
- `shop` (and `topic`, `api_version`, `webhook_id`) are pulled from HTTP headers that are never part of the signed string [4](#0-3) .
- `HmacValidator.validate_signature` recomputes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header [5](#0-4) .
- `Registry.process` checks `Utils::HmacValidator.validate(request)` and, once that body-only check passes, dispatches to the handler using `request.shop` as the merchant/tenant identifier, with no cross-check against anything HMAC-covered [3](#0-2) .

Because the app's `client_secret`/HMAC key is shared across every shop that installs the app, any merchant who installs the app receives a legitimately-signed webhook (raw body + valid HMAC) for their own store. Since the signature is independent of the `shop-domain` header, that attacker can replay the exact same `raw_body`/`hmac-sha256` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it only re-derives the HMAC from the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop [6](#0-5) .

### Impact Explanation
This breaks the tenant boundary that `Webhooks::Registry.process` is supposed to enforce: an unprivileged attacker who is merely one (of potentially many) legitimate app installer can inject data that the host application will treat as authenticated on behalf of a different shop it never actually sent. Any app logic that keys per-tenant state off `WebhookMetadata#shop` (e.g., `shop/redact`, `customers/redact`, order/customer sync, entitlement changes) can be poisoned or manipulated for a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on the attacker's own store (or observing one webhook they legitimately receive) to obtain one valid `(raw_body, hmac)` pair, and (2) sending a direct HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is needed — this is well within "unprivileged internet user" capability and is fully reachable through the gem's own documented `Registry.process` API.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC verification, or otherwise cryptographically bind the verified header set to the body before trusting `request.shop` downstream, so `to_signable_string` covers every field the handler subsequently relies on for tenant identity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)`.
2. Attacker captures `B` and the HMAC value from that webhook delivery.
3. Attacker sends their own POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: the captured, still-valid HMAC
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: any registered topic
4. `HmacValidator.validate` returns `true` because it only re-derives the HMAC from `B` [7](#0-6) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though `B` was generated for `attacker-shop.myshopify.com` [6](#0-5) .
