### Title
Webhook `shop-domain` header is trusted for tenant identification but not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then hands the handler a `WebhookMetadata` object whose `shop` field is taken from the unauthenticated `shop-domain` HTTP header. Because the same `api_secret_key` is used to sign webhooks for every shop that installs the app, any merchant who can produce (or observe) one genuine, HMAC-valid webhook body for their own store can replay that body with a forged `shop-domain` header pointing at a different tenant, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) with `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` uses this HMAC check as its only authenticity gate, then forwards `request.shop` unchecked to the handler as the tenant identifier: [4](#0-3) 

The binding that should hold is: `hmac_signature == HMAC(api_secret_key, raw_body_and_shop)`, i.e. the `shop` identity should be cryptographically bound to the payload that is authenticated. Instead the binding actually enforced is `hmac_signature == HMAC(api_secret_key, raw_body)`, with `shop` supplied out-of-band and trusted implicitly. Since `api_secret_key` is a single secret shared across all shops that install the app (not a per-shop secret), a webhook payload/HMAC pair that is valid for shop A's `orders/create` event is also a valid HMAC for the identical body claiming to originate from shop B, because the signature never covered which shop sent it.

### Impact Explanation
This breaks the tenant boundary the library is expected to preserve for host applications: a party controlling one installed shop (or one captured/valid webhook delivery) can cause the app to process webhook data while asserting it belongs to a different merchant, by simply changing the `shop-domain` header on their own outbound POST to the app's webhook endpoint. If the host application uses `WebhookMetadata#shop` (as documented/tested behavior of this gem) to select which merchant's session/records to act on, this enables cross-tenant data application under an incorrect shop identity — e.g., updating or attributing another merchant's order/product/customer record with attacker-supplied body content, without holding that merchant's access token. This satisfies the "cross-tenant access" criterion because the gem provides no cryptographic binding of `shop` to the authenticated payload; the vulnerability is fully within this gem's `Webhooks::Request`/`Webhooks::Registry` code, requires no `api_secret_key`, no access token, and no TLS interception — only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers.

### Likelihood Explanation
Likelihood is constrained by two factors: (1) the attacker needs at least one genuine HMAC/body pair, which any shop that has *itself* installed the app can obtain by receiving its own real webhook (a normal, unprivileged action any merchant can do by installing the app and triggering an event); and (2) the attacker must know/guess a target shop's domain, which is public information (`{shop}.myshopify.com`). No secrets, tokens, or elevated access are required, and the webhook endpoint is by design internet-reachable. This makes the finding practically exploitable, not merely theoretical.

### Recommendation
Bind the shop identity into the authenticated material: include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in `Webhooks::Request#to_signable_string`, or otherwise verify, using the shop the app expects for the resolved session/store, that it matches the shop the app's records show issued that specific webhook subscription, before trusting `request.shop` in `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used by consuming apps to select tenant-scoped resources without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger a real event (e.g., create an order) so Shopify delivers a webhook with a body `B` and a valid `x-shopify-hmac-sha256` header `H = HMAC(api_secret_key, B)`.
2. Capture the raw request (`B`, `H`).
3. Replay the raw POST to the app's webhook endpoint, keeping `B` and `H` unchanged, but setting `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only hashes `B` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed_body(B) ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from `attacker-shop.myshopify.com`.
