### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, breaking `shop == HMAC-authenticated shop` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, and `webhook_id` fields it exposes to the host application are read from unauthenticated HTTP headers. This breaks the identity binding `shop attribute used by the app == shop authenticated by the HMAC`, mirroring the report's root cause of relying on state that is not actually covered by the same trust boundary as the state that is checked.

### Finding Description
`to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

`hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header and verified against that same raw body via `HmacValidator.validate`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received signature: [2](#0-1) 

However, `shop`, `topic`, and `webhook_id` — the fields the host application uses to attribute the webhook to a tenant and act on it — are pulled straight from headers that are never mixed into the signed content: [3](#0-2) 

So the equality the app implicitly relies on, `request.shop == shop that produced the valid HMAC`, does not hold: the HMAC only proves "this body was signed with the app's secret," not "this body was sent for this particular shop." Anyone who can obtain one genuine `(body, hmac)` pair — e.g., by installing the app on their own store and receiving a legitimate webhook delivery for that store — can replay the same body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value, since that header is not part of `to_signable_string` and the gem performs no cross-check between the header and the signed payload.

### Impact Explanation
If a host application trusts `ShopifyAPI::Webhooks::Request#shop` (as returned by this library) to determine which tenant's data/session a webhook payload applies to — which is exactly what the gem's own documented `shop` accessor is for — an attacker controlling their own installed shop can forge webhook deliveries that the verification layer accepts as authentic, but that misattribute the payload to a victim shop of the attacker's choosing. This is a cross-tenant data-integrity break rooted entirely in this gem's `Request` class not binding `shop` to the signature it verifies.

### Likelihood Explanation
The attacker needs no privileged credentials: any developer/merchant can install a public app themselves to receive one legitimately-signed webhook, then replay it with a substituted `shop-domain` header at the app's webhook endpoint. No `api_secret_key`, access token, or TLS interception is required — only the gem's own `HmacValidator`/`Request` behavior. This makes the underlying primitive (spoofable `shop`/`topic`/`webhook_id` under a valid signature) low-effort to exploit, though full impact severity depends on how the host app models "webhook belongs to shop X" without extra cross-checks.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content (`to_signable_string`) alongside the raw body, or at minimum document/enforce that consumers must independently verify `request.shop` corresponds to a shop that has an active, previously-established session/installation for the given `webhook_id`/`topic`, rather than trusting the header value once `hmac` validates. Mirroring the report's fix pattern, the values used to make trust decisions (shop identity) must be captured/verified from the same authenticated source as the check that gates on them, not read independently from unauthenticated input.

### Proof of Concept
```ruby
# Attacker installs the target app on their own store "attacker-shop.myshopify.com"
# and receives one legitimate webhook delivery, e.g.:
raw_body = '{"id": 1, "note": "legit payload from attacker-shop"}'
valid_hmac_header = "<hmac provided by real Shopify for attacker-shop's delivery>"

# Attacker now replays the same body/hmac but swaps the shop-domain header:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => valid_hmac_header,   # still valid, since HMAC only covers raw_body
  "shopify-shop-domain" => "victim-shop.myshopify.com",  # arbitrary, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true
request.shop # => "victim-shop.myshopify.com"  (fully attacker-controlled, HMAC never checked it)
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
