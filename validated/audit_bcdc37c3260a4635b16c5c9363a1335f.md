### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant identification but are not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the shop that a webhook is attributed to is read directly from an unauthenticated HTTP header. Anyone who can obtain one genuine `(body, hmac)` pair signed by the app's secret (e.g. a merchant who has the app installed on their own store) can replay that exact body/HMAC to the webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop. `HmacValidator` still validates because it only checks the body, so `Registry.process` will hand the attacker-chosen `shop` to the host application's handler as if it were verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` that is dispatched to the app's handler: [3](#0-2) 

The binding that should hold is: `hmac_valid(body) ⇒ shop_header == shop_that_Shopify_actually_sent_for`. In this implementation that implication does not hold — HMAC validity only proves the body byte-string was signed by Shopify at some point in time, for *some* shop; it says nothing about which shop-domain header accompanies it. Compare this to `Auth::Oauth::AuthQuery`, where `shop` and `host` are explicitly included in `to_signable_string` and therefore are bound by the HMAC: [4](#0-3) 

The webhook path lacks this equivalent binding for `shop`.

Attack sequence:
1. Attacker legitimately installs the multi-tenant app on Shop A (their own store) and receives a real Shopify webhook: body `B` with header `x-shopify-shop-domain: shop-a.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over `B` with the app's `api_secret_key`.
2. Attacker replays the identical body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim tenant).
3. `HmacValidator.validate` recomputes HMAC over `B` only and it matches, so `Utils::HmacValidator.validate(request)` passes.
4. `Registry.process` builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and dispatches `B`'s contents to the handler, which the host app will process as data belonging to Shop B.

### Impact Explanation
This breaks tenant isolation: an authenticated-looking, HMAC-"verified" webhook can be attributed to any shop the attacker chooses, independent of which shop actually generated the payload. Any app logic keyed off `WebhookMetadata#shop` for record lookups/updates (order sync, inventory, GDPR/mandatory topics, uninstall handling, etc.) can be made to write attacker-supplied Shopify-originated data into a different tenant's context — a cross-tenant access/data-confusion issue.

### Likelihood Explanation
Requires an attacker to already be a bona fide merchant/tenant of the app (to obtain one legitimately signed body+HMAC pair) and to know or guess a victim shop domain — no `api_secret_key` or access token needed. This is realistic in any public multi-tenant Shopify app where installation is open and webhook endpoints are internet-reachable, which is normal for this library's intended usage.

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind the shop/topic to the payload before trusting them in `WebhookMetadata`. At minimum, `Registry.process`/`Request` should cross-validate that the `shop` header corresponds to a shop the app expects for that specific installation/session before dispatching, rather than trusting it solely because the body's HMAC matched.

### Proof of Concept
```ruby
# Attacker captures a genuine webhook they received for their own shop:
body = '{"id":1,"note":"legit order for shop-a"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
)

# Attacker replays it, only changing the shop-domain header:
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,          # unchanged, still matches body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body unchanged),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: body, ...)
``` [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
