## Finding: Webhook `shop` (and `topic`) identifiers are not covered by the HMAC signature

### Title
Webhook tenant identifier (`shop-domain` header) is not bound by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw HTTP body, while the `shop` (and `topic`) values used by host applications to attribute the webhook to a tenant are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

so `to_signable_string` — the bytes the HMAC actually covers — is only `@raw_body`. Meanwhile, the value that identifies *which shop* the webhook belongs to is pulled straight out of an HTTP header with zero cryptographic binding to that signed body: [2](#0-1) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all header-derived accessors, but `HmacValidator.validate` only proves that `@raw_body` was signed with the app's secret: [3](#0-2) [4](#0-3) 

The equality that should hold is:
`shop-domain header used by the host app to select a tenant/session == shop that the signed body actually originated from`

That equality is never checked anywhere in this class or in `HmacValidator`. Any bytes with a valid signature for the raw body pass `HmacValidator.validate`, regardless of what `shopify-shop-domain` header accompanies them.

### Impact Explanation
A webhook consumer built on top of this gem typically does: validate HMAC → read `request.shop` → look up/attribute the event to that shop's session or tenant data → process `request.parsed_body`. Because `shop` is not part of the signed bytes, an attacker who controls any shop with the target app installed (trivial — free/dev store) can capture one of their own genuinely-signed webhook deliveries (valid HMAC, since it really was signed by Shopify using the app's secret for the attacker's own shop) and resubmit that exact `raw_body` + `hmac` header pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it only checks `@raw_body`, and the host application will attribute the (attacker-controlled) body content to whatever shop the attacker put in the header — a cross-tenant data confusion/corruption primitive with no credential or network-position requirement beyond owning any shop where the app is installed.

### Likelihood Explanation
High reachability for an unprivileged internet user: obtaining a shop with the target app installed is normal usage, not a privilege escalation. No `api_secret_key`, access token, or interception is required — the attacker only replays a payload they legitimately received from Shopify for their own shop while altering an unauthenticated header.

### Recommendation
- **Short term:** Bind the shop identifier into the signed material, or independently verify that the `shop-domain` header value belongs to a shop associated with the specific webhook subscription/topic being delivered (e.g., cross-check against the known set of shops registered for that webhook via `Webhooks::Registry`) before it is handed to consumer code.
- **Long term:** Treat all `shopify-*` headers as untrusted input; do not expose `shop`/`topic` accessors as if they were verified by `HmacValidator.validate` — either document clearly that only the body is authenticated, or extend the signable string / verification routine to cover header values used for tenant routing.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (free dev store).
2. Attacker triggers a real event (e.g., updates a product) causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint, with headers `X-Shopify-Hmac-Sha256: <valid>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: products/update`.
3. Attacker captures this raw body + HMAC header, then resends the identical body/HMAC to the app's webhook endpoint but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Request.new(raw_body:, headers:)` is constructed; `HmacValidator.validate(request)` returns `true` (it only hashes `@raw_body`), while `request.shop` now returns `"victim.myshopify.com"`.
5. The host app's handler (typically invoked as `handler.handle(topic: request.topic, shop: request.shop, body: request.parsed_body)`) processes attacker-controlled content under `victim`'s tenant context.
