### Title
Webhook `shop` (and `topic`) Are Taken From Unauthenticated Headers, Not Covered by the HMAC Signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by validating only the raw request body against the `X-Shopify-Hmac-Sha256` header, then trusts the `shop` (and `topic`) values pulled from separate, unsigned HTTP headers to attribute and dispatch the webhook payload. Because `shop` is never included in the HMAC-signed material, an attacker who owns any valid `(raw_body, hmac)` pair for the shared app secret (e.g. from a webhook delivered to their own installation) can replay that exact body while substituting an arbitrary `x-shopify-shop-domain` header, causing the host application's webhook handler to process the payload as if it belonged to a different (victim) tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight out of HTTP headers that are entirely outside the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (which covers `raw_body` alone) and then forwards the unauthenticated `request.shop` value directly into `WebhookMetadata`, handing it to the host app's handler as if it were verified: [4](#0-3) 

The identity binding that should hold is:
`shop value cryptographically bound by HMAC == shop value the handler acts upon`

but the actual code enforces only:
`hmac(secret, raw_body) == received_hmac`

with `shop` (and `topic`) completely decoupled from that check. Any entity that can produce one genuine `(raw_body, hmac)` pair — which is trivial for a legitimate merchant installing the same public app on their own store, since Shopify signs and delivers real webhooks to every installer using the same `api_secret_key` — can replay that exact body/HMAC to the app's webhook endpoint while freely setting `x-shopify-shop-domain` (and `x-shopify-topic`) to any value, because those headers play no role in signature verification.

### Impact Explanation
This crosses a tenant boundary: the gem hands the host application a `shop` value that it implicitly presents as authenticated (it survived `HmacValidator.validate`), but that value is fully attacker-controlled independent of the signature check. Host applications relying on `WebhookMetadata#shop` to select/attribute per-tenant data (a documented and expected use of the field returned by this gem) can be made to associate a replayed payload with an arbitrary victim shop, i.e., cross-tenant access/data injection.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus possession of one valid `(body, hmac)` pair for that app's secret — obtainable by any user who installs the public app on their own store (a normal, unprivileged action) and captures a real webhook delivery. No credential leakage, TLS interception, or privileged access is needed; the header can be freely set on a direct HTTP request to the endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified material, or otherwise cryptographically tie the header values to the signed body, e.g. by including them in `to_signable_string`, or by requiring the host app to reconcile the header `shop` against a shop already known/authorized for the specific webhook subscription (subscription id) rather than trusting the header alone. At minimum, document clearly that `shop`/`topic` returned from `Request` are unauthenticated and must be independently verified by the host application before being used for tenant attribution.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker-shop.myshopify.com`, receiving a real webhook `orders/create` with raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST directly to the app's webhook endpoint with the identical body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — this matches, since `B` and `H` are unchanged (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using `request.shop`, which returns the attacker-supplied header `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`, `lib/shopify_api/webhooks/request.rb:21-23`).
5. The host app's handler processes order data intended for the attacker's own store as if it belonged to `victim-shop.myshopify.com`, breaking tenant isolation.
