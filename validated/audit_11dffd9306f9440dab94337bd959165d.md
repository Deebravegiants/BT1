### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request **body**, then unconditionally forwards the `shop`, `topic`, and `webhook_id` values taken from HTTP **headers** to the app's handler as trusted, verified data. Those header fields are never included in the HMAC-signed material, so they are "acted on but not covered by the HMAC" — the exact identity-binding break called out in the bug-class hint from the ETH-deposit-limit report (verifying one field while acting on another, unbound, field).

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` treats HMAC success as proof the whole request is authentic, then dispatches handler-selection (`@registry[request.topic]`) and constructs `WebhookMetadata` — including `shop: request.shop` — using these unauthenticated header values: [4](#0-3) 

The equality the code implicitly (and incorrectly) assumes is:
`bytes verified by HMAC (raw_body)` == `bytes acted on (shop header, topic header, webhook_id header)`

These are never the same bytes. Anyone who can submit an HTTP request with a body/HMAC pair that will validate (e.g., a previously observed legitimate delivery for shop A, or any body whose HMAC they can compute if they ever learn one valid pair for a fixed body) can pair that valid `(body, hmac)` with an arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header. `Registry.process` will accept it, route it to a handler keyed by the attacker-chosen `topic`, and hand the handler a `WebhookMetadata.shop` value that the app will treat as the authenticated tenant identity — even though it was never checked against the HMAC.

### Impact Explanation
Apps commonly use `WebhookMetadata#shop` to look up the tenant's stored access token/session or to write/update tenant-scoped data (this is the documented purpose of `shop` in `WebhookMetadata`, per `docs/usage/webhooks.md`). Because `shop` is unauthenticated with respect to the HMAC, an attacker with network reach to the app's public webhook endpoint and knowledge of one valid `(body, hmac)` pair can cause the app to process that payload under a different, attacker-chosen shop identity, or dispatch it to a handler for a different topic than the one Shopify actually signed for. This is a cross-tenant identity-binding break consistent with the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires an attacker to already possess at least one legitimate `(body, hmac)` pair (e.g., captured from a real delivery, or a body they fully control if the app ever echoes external input into webhook-like testing/replays) and the ability to POST to the app's public webhook endpoint with arbitrary headers — both are realistic for a public HTTPS endpoint with no other binding of headers to signature. No secret (`api_secret_key`) or credential is required, satisfying the unprivileged-internet-user constraint.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material (or otherwise cryptographically bind them to the body), matching the report's resolution pattern of verifying the same bytes that are acted upon. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain and topic, and `Registry.process` should reject requests where these headers were not covered by the validated signature.

### Proof of Concept
1. Capture (or otherwise obtain) one valid webhook delivery: raw body `B` and its `x-shopify-hmac-sha256` header `H`, originally sent for `shop-domain: shop-a.myshopify.com`, `topic: orders/create`.
2. POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: shop-b.myshopify.com` and/or `x-shopify-topic: customers/redact`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` routes to the handler for the attacker-supplied `topic` and passes `shop: "shop-b.myshopify.com"` in `WebhookMetadata`, even though the original signed delivery was for `shop-a.myshopify.com` and a different topic.
