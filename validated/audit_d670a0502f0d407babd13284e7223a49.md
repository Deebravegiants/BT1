### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` verifies the integrity of the request body only. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read straight from HTTP headers, are never part of the signed payload and are handed to the app's `WebhookHandler#handle` as trusted, verified data.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled unauthenticated from headers via `shopify_header`, independent of the signed body: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header — it never binds `shop` (or `topic`/`webhook_id`) into that signature: [3](#0-2) [4](#0-3) 

The unverified `shop` field is then passed straight into `WebhookMetadata`, which is delivered to the app's handler as authenticated data: [5](#0-4) 

This breaks the intended identity binding `hmac == HMAC(secret, body ∧ shop)` that a webhook consumer relies on; in reality the gem only enforces `hmac == HMAC(secret, body)`. All shops that use the same app share one `api_secret_key`, so any actor who can obtain one genuine `(raw_body, hmac)` pair signed by that shared secret (e.g. by installing the app on their own shop and observing a webhook delivery, which is not itself privileged access to Shopify's or the app's credentials) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a different shop. `Registry.process` will accept it as valid because the HMAC still matches, and will dispatch it to the app's handler labeled with the attacker-chosen `shop`.

By contrast, the OAuth `AuthQuery` in the same codebase does correctly bind `shop` into its `to_signable_string` and thus into the HMAC: [6](#0-5) 
This makes the omission of `shop` from the webhook signable string an inconsistency in the same trust model rather than a deliberate design choice.

### Impact Explanation
Because the shop-domain binding is missing from the webhook HMAC, a merchant who has installed the app on their own store (an unprivileged, non-credentialed actor with respect to any *other* tenant) can forge a webhook delivery that the receiving app will process as if it came from a different, arbitrary shop. Any per-shop logic keyed off `WebhookMetadata#shop` — looking up or mutating that shop's stored session/data, triggering GDPR flows (`shop/redact`, `customers/redact`, `customers/data_request`), or writing attacker-controlled body content under another tenant's identity — is exposed to cross-tenant data injection/confusion. This matches the "Critical - cross-tenant access" impact category, since the attacker crosses the tenant boundary that the HMAC is supposed to enforce.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate (even free/trial) user of the app on their own shop so they can capture one genuine `(raw_body, hmac)` pair from a real webhook delivery, and (2) network access to POST to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any other credential is needed — the shared app secret is never exposed to the attacker, only its signature output over attacker-visible data. This is a realistic, low-effort attack path for any host application that trusts `WebhookMetadata#shop` (which the gem's documented API explicitly encourages handlers to use).

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified for webhooks, mirroring how `AuthQuery#to_signable_string` binds `shop` for OAuth. Since Shopify's own webhook signature is computed over the raw body only, the gem should introduce an additional cryptographic binding — e.g., derive/require a per-request check that ties the header-derived `shop` to the caller-provided session/shop context before invoking the handler, or document/require that consuming apps independently re-validate `shop` against the shop that they expect to have registered the specific `webhook_id`/topic, rather than trusting `request.shop` as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook event (e.g. `orders/create`) that the app has registered for.
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header from that delivery — both are visible to them as the receiving party.
3. Attacker replays that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` recomputes the HMAC over `raw_body` only [7](#0-6)  and it matches, so `Registry.process` proceeds and calls `handler.handle` with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [3](#0-2)  — the app now processes attacker-controlled webhook content under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
