Confirmed: no rescue/emergency-cancel function exists anywhere in the intents contracts to recover escrow stuck behind a reverting transfer, unlike Bracket.sol's (also-vulnerable) `adminCancelOrder`.

### Title
Permanent Freezing of Escrowed Funds via Blacklisted `order.user` in IntentGatewayV2/IntentsBase Withdrawal Paths - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` uses `IERC20.safeTransfer` to send escrowed/refunded tokens directly to a beneficiary address taken from the order (`order.user` for refunds, or the filler for redemptions) with no check that the transfer can succeed. For blacklistable tokens (USDC, USDT, etc.), if that beneficiary address is or becomes blacklisted, every withdrawal path reverts permanently, and there is no admin/rescue function anywhere in the intents contracts to recover the escrow, unlike the analogous `adminCancelOrder` gap identified in the referenced Oku `Bracket.sol` report.

### Finding Description
`_withdraw` transfers to `beneficiary = address(uint160(uint256(body.beneficiary)))` without any preflight check: [1](#0-0) 

This function is reachable from three withdrawal routes, all deriving the beneficiary from `order.user` (stamped to the order creator at `placeOrder`):

1. **Same-chain cancel** — `_cancelSameChain` calls `_withdraw` synchronously in the same transaction as `cancelOrder`: [2](#0-1) 
If `order.user`'s token balance/receive path is blacklisted, `cancelOrder` reverts every time it is called — there is no alternate exit for the escrowed tokens.

2. **Cross-chain destination-side cancel** — `_cancelFromDest` immediately marks `_filled[commitment] = order.user` (blocking any future fill) and dispatches a `RefundEscrow` message to the source chain: [3](#0-2) 
On the source chain, `onAccept` decodes the body and calls `_withdraw`: [4](#0-3) 
Crucially, `EvmHost.dispatchIncoming` swallows a reverting `onAccept` by deleting the request receipt and returning without reverting the outer transaction, which makes the message indefinitely retryable but never delivers if the underlying transfer always reverts: [5](#0-4) 

3. **Cross-chain source-side cancel** — `onGetResponse` calls `_withdraw` after the non-membership proof confirms the order was never filled: [6](#0-5) 
The GET-response delivery path has the same non-reverting swallow behavior in `EvmHost.dispatchIncoming` for `GetResponse`.

Once path (2) executes, `_filled[commitment]` is already set on the destination chain, permanently preventing any future `fillOrder`, while the source-chain escrow can never be released because the refund transfer to the blacklisted `order.user` always reverts, and the failed delivery is silently retryable-but-never-successful rather than surfaced as a permanent failure with an alternate remedy. The identical raw-`.call` + explicit-revert pattern exists in the Tron variant's `withdraw`: [7](#0-6) 

No sweep/rescue mechanism exists for this stuck per-order escrow (the only sweep function, `SweepDust`, only moves protocol-fee dust, not user escrow), and `IntentsBase.sol` defines no admin override for `_withdraw`'s beneficiary.

### Impact Explanation
This results in **permanent freezing of user funds**: once an order's escrow beneficiary is a blacklisted address for the escrowed token, the tokens are locked in the `IntentGatewayV2` contract with no code path to release them — not by the user, not by a relayer, not by governance. For a token like USDC/USDT this is externally triggerable at any time after order placement (Circle/Tether can blacklist an address independently of the protocol), and for the same-chain path, is deterministic and immediate once the address is blacklisted, since `cancelOrder` unconditionally attempts the direct transfer.

### Likelihood Explanation
Likelihood is realistic for any deployment involving centrally-blacklistable stablecoins, which the docs explicitly target (USDC is used throughout the test suite and documentation examples, e.g. `docs/content/developers/evm/intent-gateway/placing-orders.mdx`). While `order.user` cannot be attacker-set to an arbitrary third party (it is always stamped to `msg.sender` at placement), a user's own address can be sanctioned/blacklisted after order placement but before cancellation/refund, which is a well-documented and previously-exploited pattern (see the cited Oku/Bracket.sol Sherlock finding). No special privilege is required to trigger it — merely placing an order and later being blacklisted, or a relayer/attacker racing to get the address blacklisted before cancellation completes.

### Recommendation
Add a pull-based withdrawal pattern or a fallback recovery mechanism in `_withdraw` (e.g., catch a failed `safeTransfer`/low-level call and credit an internal, separately-withdrawable balance instead of reverting the whole operation), and/or provide an admin/governance-gated escape hatch to redirect stuck escrow to a different address after a timeout, mirroring what is missing from the referenced Bracket.sol report. At minimum, wrap the token transfer in a try/catch so that a stuck transfer does not block `_filled` state transitions or leave the message permanently non-deliverable, and expose a way to re-route the withdrawal to a fresh address supplied by the original `order.user`.

### Proof of Concept
Conceptual PoC (same-chain path, deterministic and immediately provable):
1. Deploy `IntentGatewayV2` with a blacklistable ERC-20 (e.g., a mock USDC with `Blacklistable` semantics) as the input token.
2. `user` calls `placeOrder` with `inputs = [{token: mockUSDC, amount: X}]`; `order.user` is stamped to `user` by the contract (`evm/src/apps/IntentGatewayV2.sol` lines 224).
3. Token issuer (or test harness) blacklists `user`'s address on `mockUSDC`.
4. `user` calls `cancelOrder(order, cancelOpts)` for the same-chain path; `_cancelSameChain` → `_withdraw` attempts `IERC20(mockUSDC).safeTransfer(user, escrowed)`, which reverts due to the blacklist check inside the token, causing `cancelOrder` to revert unconditionally.
5. Escrowed `X` tokens remain locked in the gateway contract permanently — no other function exists to release them to `user` or any other address.

For the cross-chain variant, the same blacklist condition applied before the `RefundEscrow`/`onAccept` delivery on the source chain reproduces the freeze via `EvmHost.dispatchIncoming`'s non-reverting failure handling, as cited above; this path could not be fully traced end-to-end within the available tool budget (specifically, whether any timeout-based recovery exists for an undeliverable `RefundEscrow` message was not exhaustively verified beyond the `onPostRequestTimeout` mechanics documented for outbound dispatch, which apply to the *sender* side, not to a message that is deliverable-but-perpetually-reverting on accept).

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;

            unchecked {
                ++i;
            }

        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
