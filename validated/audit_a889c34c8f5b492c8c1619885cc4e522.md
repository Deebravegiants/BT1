### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that body via `Utils::HmacValidator.validate`. The `shop` field, read directly from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, is never included in the signed material, yet it is forwarded unchanged into `WebhookMetadata` and handed to the host application's webhook handler as the authoritative tenant identifier.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body + shop)` (or equivalent binding that ties the claimed shop to the signed payload). Instead, the gem computes and verifies:
`hmac == HMAC(secret, raw_body)` only [1](#0-0) , while `shop` is read straight from an attacker-controllable header with no cross-check against the signed body [2](#0-1) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is passed to the app's handler: [3](#0-2) 

Because any party who legitimately installs the app on their own shop (an unprivileged internet user, no special access needed) will receive real webhooks from Shopify with a valid HMAC computed only over the body, they can capture such a webhook and replay the exact same `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g., a victim shop). `HmacValidator.validate` will still succeed because the signable string used for verification never includes the shop header [4](#0-3) . The forged request is then dispatched to the handler labeled with the attacker-chosen `shop`, which the gem's own documentation instructs developers to treat as the shop-scoped tenant key for storing/queuing the payload [5](#0-4) .

### Impact Explanation
This breaks the equality `shop_claimed_in_metadata == shop_that_actually_produced_and_signed_the_payload`. Any application that uses `data.shop` (as explicitly recommended in the gem's own docs) to route, store, or scope webhook data per tenant will attribute another shop's identity to data that came from — or was replayed by — a different, attacker-controlled shop, since the gem provides no protection against this mismatch. This is a cross-tenant identity-binding failure entirely within the gem's webhook-processing surface.

### Likelihood Explanation
Likelihood is high for any app author following the documented `WebhookHandler` pattern: the only prerequisite is that the attacker operate their own installed shop (a normal, unprivileged action any merchant can take) to obtain one valid `(raw_body, hmac)` pair, then replay it with a spoofed `shop-domain` header — no secret key, access token, or privileged access is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value as part of the signed material verified by `HmacValidator`, or otherwise cryptographically bind the claimed shop to the verified payload before constructing `WebhookMetadata`, so `Request#to_signable_string` cannot be satisfied by a body-only signature while the shop is swapped out.

### Proof of Concept
1. Install the app normally on `attacker.myshopify.com`; capture a legitimate webhook POST, including its `x-shopify-hmac-sha256` header and raw body.
2. Resend the identical raw body and `x-shopify-hmac-sha256` header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) and finds it matches — validation passes [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` even though the payload was never produced or signed under that shop's context [7](#0-6) .
