## Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing shop-identity spoofing in delivered webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header without being part of the HMAC-signed material [2](#0-1) . `Registry.process` validates only the HMAC over the body, then forwards the unverified `shop` header value straight into the handler as trusted tenant identity [3](#0-2) .

### Finding Description
This is the same bug class as the reported Go `Root` issue: a value the protocol relies on being validated/bound is instead accepted without the expected check. Here, the "binding" the webhook protocol depends on is:

`HMAC-verified bytes == identity attributed to the event (shop)`

In reality:
- The HMAC signature is computed and verified only over `@raw_body` [1](#0-0)  via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` [4](#0-3) .
- `shop` is pulled directly from the `x-shopify-shop-domain` header [2](#0-1) , a value that is **not** included in `to_signable_string` and therefore **not covered by the HMAC**.
- `Registry.process` validates the HMAC (over the body only) and, having asserted "authenticity," immediately constructs a `WebhookMetadata` using the unverified `shop` header and hands it to the application's handler as the trusted tenant identifier [3](#0-2) .
- `WebhookMetadata.shop` is a plain `String` field with no further validation [5](#0-4) .

Because Shopify's real webhook HMAC (computed server-side from the shared `client_secret`) only covers the JSON body, and this gem never mixes the shop-domain header into the signed material, an attacker who can obtain any single valid `(body, hmac)` pair for a given payload for topic X (e.g., their own store's legitimate webhook, or any payload whose HMAC they can compute if they ever obtain the app's secret through another channel, or more realistically a replayed webhook capture) can resend that exact same body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` will report success because it only checks the body signature [6](#0-5) , and the handler will process the payload as if it belongs to the attacker-chosen shop.

Note the OAuth callback path in the same gem, by contrast, correctly binds the shop into the signed query string — `AuthQuery#to_signable_string` includes `shop` as part of the query, and `HmacValidator` verifies that whole query [7](#0-6) . The webhook `Request` class breaks this pattern by excluding `shop` (and `topic`, `webhook_id`) from the signable string, unlike the OAuth flow.

### Impact Explanation
This crosses a tenant boundary: the `shop` value is used by host applications (as documented in `docs/usage/webhooks.md`) to look up the merchant/session record and apply the webhook payload to that merchant's data. If the shop attribution can be forged while the HMAC still validates, an attacker can cause a webhook payload to be misattributed to a different, victim shop — i.e., **cross-tenant data confusion delivered through what the app believes is an authenticated Shopify-origin event**. This matches the High-severity category of a scope/identity check that "answers permissively" because it validates the payload's integrity but not the actor/tenant field the application relies on for authorization of the event.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair — trivially available for their own registered shop's webhooks, since HMAC-signed webhooks for the attacker's own store are legitimately delivered to them. The attacker only needs to relay that same body/HMAC to the target app's public webhook endpoint with a forged `shop-domain` header; no access token, secret, or privileged account is needed. This is a low-effort, network-reachable modification of a header field within the attacker's control.

### Recommendation
- Short term: Bind `shop` (and `topic`, `webhook_id`) into the HMAC-signed material for webhook verification, or, at minimum, require the host application to independently authenticate the `shop` field against a known/registered shop before trusting it — document that `WebhookMetadata#shop` is currently unauthenticated relative to the HMAC.
- Long term: Audit all `VerifiableQuery` implementations (`Auth::Oauth::AuthQuery`, `Webhooks::Request`) to ensure every field used downstream for authorization decisions is part of `to_signable_string`, and add tests asserting that tampering with `shop-domain`/similar identity headers while keeping the body and HMAC unchanged causes verification to fail.

### Proof of Concept
```ruby
# Attacker has legitimately received one webhook for their own shop:
raw_body = '{"id": 123, "note": "some order data"}'
valid_hmac_for_own_shop = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret_known_only_via_legit_delivery, raw_body)
)
# (app_secret is never known to attacker directly, but the *signed pair* they receive
#  for their own store is: raw_body + hmac header, both attacker-controlled/observable)

forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac_for_own_shop,   # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com" # forged - NOT covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (only checks raw_body)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-supplied body under the victim shop's identity.
