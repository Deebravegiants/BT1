### Title
Unrestricted flash-loan callbacks can smuggle caller-authorized wallet transfers into the signed authorization tree - (File: contracts/controller/src/lib.rs)

### Summary
`flash_loan` accepts an arbitrary `receiver` contract selected by the caller and invokes its callback while the caller’s authorization context is active. [1](#0-0)  A malicious receiver can make an unrelated token execute `transfer(victim, attacker, amount)`, causing transaction simulation to attach that transfer as a child of the victim’s `flash_loan` authorization; if a crafted application convinces the victim to sign the resulting tree, the transfer executes even though it is unrelated to the flash loan. [2](#0-1) [3](#0-2) 

### Finding Description
The public `flash_loan(caller, asset, amount, receiver, data)` interface gives the caller complete control over the callback contract and callback payload. [1](#0-0)  Soroban does not limit the caller’s authorization to operations initiated directly by the controller: arbitrary deeper contract code can request the caller’s token authorization, and simulation records the request beneath the signed controller invocation. [4](#0-3)  The repository’s authorization test demonstrates the policy boundary: an honest signed tree rejects the hidden transfer, while the poisoned simulated tree authorizes it. [5](#0-4) [6](#0-5) 

A malicious flash receiver can therefore perform two actions inside the callback: steal an unrelated wallet asset under the caller’s authorization and approve/retain enough of the borrowed asset for the pool’s required principal-plus-fee settlement. [7](#0-6)  Because the enclosing transaction succeeds after repayment, the unrelated transfer is not rolled back. [8](#0-7) 

### Impact Explanation
A crafted application can steal arbitrary token balances held by a user who signs the poisoned authorization tree; the stolen asset does not need to be listed by XOXNO or participate in the flash loan. [9](#0-8)  The demonstrated effect moves the victim’s complete unrelated wallet balance to the attacker while the requested protocol operation still completes normally. [10](#0-9)  This is theft of user funds and maps to Medium severity because it requires a victim-approved crafted transaction rather than unilateral on-chain execution. [11](#0-10) 

### Likelihood Explanation
The attacker needs to induce the victim to use a malicious application or transaction builder that supplies the rogue receiver and then sign the simulated authorization tree. [12](#0-11)  No privileged role, oracle manipulation, compromised key, protocol upgrade, or leaked parameter is required: the malicious callback address is an ordinary user-supplied argument to a permissionless entrypoint. [13](#0-12)  The exploit’s dependence on social engineering and wallet/auth-tree presentation lowers its likelihood, but it is the same crafted-application authorization-policy weakness described by the CVE. [14](#0-13) 

### Recommendation
Do not invoke arbitrary user-selected contracts while an account’s authorization context can be extended with unrelated token transfers. [1](#0-0)  Prefer a contract-level boundary that only invokes governance-approved receiver/pool contracts, or redesign flash execution so untrusted callbacks cannot run beneath the caller’s signed authorization context. [5](#0-4)  If arbitrary receivers remain supported, wallets and transaction builders must decode the simulated authorization tree and reject any caller child invocation beyond the expected controller operation—an honest account-signed `flash_loan` should not contain an unrelated `token.transfer(caller, attacker, amount)` child. [6](#0-5) 

### Proof of Concept
1. Deploy `RogueReceiver`, configured with `victim`, `unrelated_token`, `attacker`, and `steal_amount`; its `execute_flash_loan` callback calls `token.transfer(victim, attacker, steal_amount)` and then leaves or approves enough borrowed asset for `amount + fee`. [15](#0-14) 
2. Have the victim hold a balance in `unrelated_token`, which need not be a protocol market asset. [16](#0-15) 
3. Through a crafted application, simulate `Controller::flash_loan(caller=victim, asset=<liquid market>, amount=<loan>, receiver=RogueReceiver, data=<opaque bytes>)`. [1](#0-0) 
4. During simulation, the malicious callback’s token call is recorded as a child of the victim’s controller authorization. [17](#0-16) 
5. If the victim signs only the honest root without the hidden child, enforcement rejects the rogue transfer and the transaction reverts. [5](#0-4) 
6. If the crafted application obtains a signature for the poisoned tree containing the unrelated child transfer, the same transaction succeeds, drains `steal_amount` to the attacker, and settles the flash loan normally. [18](#0-17)
