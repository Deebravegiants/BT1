### Title
Webhook shop-domain, topic, and webhook-id are not covered by the HMAC signature, allowing signed body replay across shops/topics - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` identifiers used by the app's webhook handler are taken from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that the HMAC matches `to_signable_string` (i.e., the raw body) against the shared `client_secret`: [3](#0-2) 

`Registry.process` accepts any request whose HMAC validates against the body, then hands the *header-derived* `shop`/`topic`/`webhook_id` straight to the app's handler without any additional cross-check that those headers correspond to the body that was actually signed: [4](#0-3) 

`WebhookMetadata` is the struct the host application's `WebhookHandler#handle` receives and is expected to trust for identifying which merchant/tenant and which event the payload belongs to: [5](#0-4) 

The identity binding this breaks (mapping the report's mint-award manipulation, i.e., "an action credited to an identity that wasn't actually verified for that action," onto this gem) is:

`shop_header_used_by_handler == shop_actually_signed_by_the_HMAC`

This equality does not hold: the HMAC secret (`client_secret`) is shared across every shop that has installed the app, and only the raw body is signed. Any party who can obtain one validly-signed webhook body for their own shop (which they can trivially generate themselves — e.g., by placing an order in their own shop or triggering `app/uninstalled`) can resend that exact same signed body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers rewritten to any value they choose. Because those fields are outside `to_signable_string`, `HmacValidator.validate` still returns `true`, and `Registry.process` forwards the forged `shop`/`topic` to the handler as if they were authenticated.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended) to key database writes for a specific merchant, this allows a person with their own store to make the app associate their own genuine order/customer/webhook payload with an arbitrary victim shop domain string, or to relabel benign topics as sensitive ones (e.g., `shop/redact`, `customers/data_request`) that trigger data deletion or export flows scoped by header-supplied `shop`. This crosses the app's tenant boundary using only a signature the attacker legitimately obtained for their own account, which matches the Critical "cross-tenant access" impact category, since no leaked secret, TLS interception, or privileged account is required — only a standard merchant installation of the app.

### Likelihood Explanation
Exploitability requires only that the attacker (i) install the app on a shop they control (a normal, unprivileged action) and (ii) intercept/capture one webhook their own shop legitimately receives — which is a routine capability for any merchant configuring their own server or a debugging proxy for their own webhook endpoint, not privileged access to Shopify's infrastructure or the app's `client_secret`. The replay itself is a trivial HTTP POST with rewritten headers and an unchanged, still-validly-signed body.

### Recommendation
Include the shop domain, topic, webhook id, and API version in the HMAC-signable string (or otherwise bind them cryptographically to the payload) so `HmacValidator.validate` fails if any of these header values are altered after the payload was signed by Shopify. At minimum, `Request#to_signable_string` should incorporate the header values that `WebhookMetadata` exposes to handlers, mirroring how `Oauth::AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Attacker triggers a legitimate webhook event on their own store (e.g., updates an order), and captures the resulting raw POST body plus the valid `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's webhook endpoint (they control the receiving server/proxy for their own store's webhook subscription).
3. Attacker resends that exact same body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` and/or `X-Shopify-Topic` with a different topic string.
4. `Request.new` accepts the forged headers (only presence, not authenticity, is checked): [6](#0-5) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the secret: [7](#0-6) 
6. The handler receives `WebhookMetadata.new(topic: <forged>, shop: "victim-shop.myshopify.com", body: <attacker's own payload>, ...)` and processes it as if Shopify itself vouched for that shop/topic combination.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
