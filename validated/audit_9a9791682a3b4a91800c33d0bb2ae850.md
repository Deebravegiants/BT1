### Title
Untyped, domain-unseparated challenge signing in `@exodus/auth-client-base` enables cross-service signature replay - (File: `libraries/auth-client-base/client.js`)

### Summary
`@exodus/auth-client-base` implements a pseudonymous, signature-based REST authentication flow: the client fetches a raw base64 "challenge" from a server and signs it directly with the wallet/device `keyPair`, submitting the signature to obtain a bearer token. Domain separation (binding the signature to a specific server/service) is only applied when the consuming service explicitly supplies a `serverId` string, which is prepended to the raw challenge bytes before signing. If `serverId` is omitted (it's `typeforce.maybe(typeforce.String)`, i.e. optional) — or if two different services happen to reuse the same `serverId` — the exact same key material can produce a signature over indistinguishable, untyped byte payloads. This is architecturally the same root cause as the "untyped data signing" report: no mandatory, structured domain separator (service identity, purpose, expiry) baked into what is signed.

### Finding Description
In `_authenticate()` [1](#0-0) , the client:
1. Requests a `challenge` (raw base64 bytes) from `authChallengeUrl`, keyed only by the client's public key.
2. Optionally concatenates a `serverId` string in front of the raw challenge bytes.
3. Signs the resulting untyped byte blob (`keyPair.sign(encodedChallenge)`), with no type tag, version, expiry, or purpose field encoded in the signed payload.
4. Submits `publicKey` + `signedChallenge` to obtain a bearer token.

The `serverId` binding is the *only* domain-separation mechanism, and it is opt-in via config [2](#0-1) . There is no enforcement in this library that `serverId` must be set, must be unique per consuming backend, or must be validated against `authChallengeUrl`/`baseUrl`. A consuming application that forgets to set `serverId` (or that reuses the same wallet keypair across multiple backend integrations with the same or no `serverId`) produces signatures that are valid, generic proofs-of-possession of the public key with no cryptographic binding to *which* service requested them — directly mirroring the Rigor report's "signature reuse across different projects/functions" pattern, but at the wallet's authentication layer rather than a smart contract.

Because the code lives in a shared library reused across "your auth scenario" (per the README, it's designed as a generic drop-in client), any Exodus-side or third-party backend that instantiates this client without a `serverId`, or that shares a keypair/backend identity with another instance, inherits the vulnerability.

### Impact Explanation
If exploited, a malicious or compromised server that legitimately issues one of these challenges (or an attacker who can observe a challenge response, e.g. via MITM on an insecure integration, or a second party server also using this client library against the same keypair) could:
- Replay a previously obtained `signedChallenge` against a different server instance that trusts the same public key and does not enforce a distinguishing `serverId`, effectively impersonating the user/device and obtaining a valid bearer token for a different service (cross-service auth bypass).
- If `serverId` is used inconsistently by different callers of this shared library, the isolation guarantee it's meant to provide silently degrades to none.

This could lead to unauthorized issuance of an auth token bound to the user's device/wallet identity on a service the user never intended to authenticate with, i.e., an account/session privilege bleed across services sharing this signing scheme.

### Likelihood Explanation
Likelihood depends entirely on how consuming services configure this shared library:
- If every current internal Exodus consumer of `@exodus/auth-client-base` reliably sets a unique, non-guessable `serverId`, the practical exploitability is low today.
- However, since `serverId` is optional at the type level and there is no runtime enforcement, guard, or documentation requirement making it mandatory, this is a latent design flaw that a future or third-party integration (or a misconfiguration) could trivially trigger. The lack of any structured/typed challenge format (analogous to EIP-712) means the security property rests entirely on every caller manually doing the right thing, rather than being guaranteed by the library.

### Recommendation
- Make `serverId` (or an equivalent audience/domain identifier) a required, validated configuration field rather than optional (`typeforce.String` instead of `typeforce.maybe(typeforce.String)`).
- Replace the ad-hoc `serverId + challenge` byte concatenation with a structured, typed signing payload (e.g., a versioned struct containing `{ purpose: "auth", serverId, audience/baseUrl, challenge, issuedAt }`), hashed with a fixed, unambiguous encoding — analogous in spirit to EIP-712's domain separator — so that signatures cannot be reinterpreted or replayed across contexts.
- Have the server-side challenge/verification also bind and check the audience/serverId server-side, not just rely on the client including it.

### Proof of Concept
Conceptual replay scenario (cannot be executed without the corresponding server-side verification code, which is not present in this repository):
1. Service A and Service B both integrate `@exodus/auth-client-base` against the same user keypair, and neither sets `config.serverId` (both `undefined`).
2. User's client signs `encodedChallenge = Buffer.from(challengeA, 'base64')` for Service A's `authChallengeUrl`, producing `signedChallengeA`.
3. If Service B's challenge-generation happens to issue an identical or predictable challenge value (or an attacker controlling Service A's challenge endpoint issues a challenge equal to one Service B would accept), `signedChallengeA` submitted to Service B's `authTokenUrl` with the same `publicKey` is a valid, unauthorized proof-of-possession, since the signed bytes carry no indication of which service they were intended for. [3](#0-2) 

Note: the server-side challenge generation/validation logic is not present in this repository (index limitation for this specific area was not hit, but the backend service is simply out of scope/not part of this codebase), so full exploitability (e.g., whether challenges are single-use/short-lived and whether backends currently always pass distinct `serverId`s) could not be independently confirmed from the client library alone.

```javascript
  _authenticate() {
    const { keyPair, authChallengeUrl, authTokenUrl, serverId } = this._config
    this._authPromise = (async () => {
      if (!keyPair) {
        return
      }

      const { challenge } = await this._request('POST', authChallengeUrl, {
        auth: false,
        data: {
          publicKey: keyPair.publicKey.toString('hex'),
        },
      })

      let encodedChallenge = Buffer.from(challenge, 'base64')

      if (serverId) {
        encodedChallenge = Buffer.concat([Buffer.from(serverId), encodedChallenge])
      }

      const signedChallenge = await keyPair.sign(encodedChallenge)
      const { token } = await this._request('POST', authTokenUrl, {
        auth: false,
        data: {
          publicKey: keyPair.publicKey.toString('hex'),
          signedChallenge: signedChallenge.toString('base64'),
        },
      })

      this._token = token
    })()

    return this._authPromise
  }
```
