### Title
Permanent market freeze via i128 value overflow in index accrual (`scaled_to_original`) before the index cap engages - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
An integer-overflow analog of the TensorFlow report: XOXNO Lending's accrual step multiplies scaled shares by a RAY index with a result that must fit `i128`. Once a market's scaled `supplied`/`borrowed` balances are large enough that `scaled * index / RAY` exceeds `i128::MAX`, `accrue_step` panics with `MathOverflow`. Since every user-facing verb accrues first via `global_sync`, and the panic is state-dependent and irreversible, the market freezes permanently — no supply, borrow, withdraw, repay, liquidation, or bad-debt cleanup can ever execute again. The pool keeps holding supplier and collateral funds that can never move.

### Finding Description
`accrue_step` unconditionally rescales the running totals before computing utilization:

- `common/src/rates/simulate.rs:60-61` — `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)`.
- `common/src/rates/scaling.rs:14-16` — `scaled_to_original` is `scaled.mul(env, index)`, i.e. `mul_div_half_up(scaled, index, RAY)` (`common/src/math/fp.rs:50-52`), which computes the product in `I256` but panics with `GenericError::MathOverflow` when the final `i128` result does not fit (`common/src/rates/compound.rs:40-41` shows the same panic convention; `common/tests/math/fp.rs:367-371` asserts overflow panics).

The panic happens for `scaled * index / RAY > i128::MAX` (~`1.7e38`). A market that admits ~`i128::MAX / 10^(27-d)` base units mints scaled shares up to ~`1e29-1e36`. The borrow and supply indexes are only capped at `MAX_BORROW_INDEX_RAY`/`10^36` (1000x or 1e9× initial), so the value ceiling is reached far earlier — the in-repo harness test confirms the index cap "never engages" and that a whale market at sustained high utilization hits `MATH_OVERFLOW` inside `scaled_to_original`, after which `withdraw` and `repay` both revert because every verb calls `global_sync` → `accrue_step` first (`contracts/pool/src/interest.rs:20-48`; `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`).

Reachable path (all unprivileged):
1. `controller.supply` / direct pool supply to build a large market near the admitted cap (cap checks use `calculate_scaled_cap`, which *saturates* rather than reverting — `common/src/rates/scaling.rs:26-33` — so caps do not prevent reaching the domain edge).
2. `controller.borrow` to drive utilization high so the borrow index compounds toward the cliff.
3. `controller.update_indexes` (permissionless) advances accrual; once `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` crosses `i128::MAX`, every subsequent accrual panics.

Because `accrue_step` fails before writing anything and there is no admin path to roll the index back or skip accrual, the panic is a permanent state: `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `flash_position`, `multiply`, `swap_*`, `claim_revenue`, and `recapitalize` all accrue first and all revert.

### Impact Explanation
Permanent freezing of all funds in the affected (hub, token) book: suppliers' deposits, borrowers' collateral backing the position, and unclaimed protocol revenue in that market become unrecoverable. This matches the "permanent freezing of funds" / "contract unable to operate" impact class directly.

### Likelihood Explanation
Medium-low. It requires (a) a market whose scaled totals approach the RAY-domain ceiling (hundreds of billions of units of a low-decimals, high-value asset, or a very large 18-decimal book) and (b) sustained index growth — the harness reaches the cliff only after years at ~98% utilization on the steepest curve segment. No privileged action is needed; caps fail open via `calculate_scaled_cap`'s saturation, and an attacker can accelerate the condition simply by supplying and borrowing at scale and letting compounding run. The condition is monotone — once crossed, it cannot uncross.

### Recommendation
Make the unscale path in `accrue_step` saturating (e.g. a `mul_div_*_saturating` variant like the one already used in `calculate_scaled_cap` and `Wad::div_floor_saturating`, `common/src/math/fp.rs:207-209`), or clamp `borrowed`/`supplied` scaled totals and indexes so that `scaled * index / RAY` provably stays in `i128` — e.g. enforce an entry cap of `i128::MAX * RAY / MAX_INDEX` scaled shares per market rather than relying on `calculate_scaled_cap`'s open-ended saturation. At minimum, gate `update_borrow_index`/`update_supply_index` growth so index accrual stops before the value ceiling, mirroring the existing `MAX_BORROW_INDEX_RAY` cap which currently engages too late.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`):

```rust
// market BIG18 (18 decimals), caps lifted; principal = 10^9 * 10^18 base units
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// -> GenericError::MathOverflow inside scaled_to_original; borrow_index < cap
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The overflow fires in `accrue_step` at `scaled_to_original` (`common/src/rates/simulate.rs:60-61` → `common/src/rates/scaling.rs:14-16` → `Ray::mul` at `common/src/math/fp.rs:50-52`), and because `global_sync` (`contracts/pool/src/interest.rs:20-33`) runs before every state transition, the market is bricked thereafter.
