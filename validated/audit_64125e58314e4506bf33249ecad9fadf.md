### Title
Route-supplied pool contracts execute under the caller's `require_auth` tree and can drain the caller's unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
CVE-2022-39201's class — a trusted proxy endpoint forwarding the user's ambient credential to a caller/attacker-chosen destination — maps directly onto the lending protocol's router-strategy path. `swap_collateral`, `multiply`, `swap_debt`, `repay_debt_with_collateral` (and any strategy calling `swap_tokens`) run under the user's `require_auth()` at the controller entrypoint, then pass a user-supplied `swap_xdr` route into the swap aggregator. The aggregator keeps **no allowlist of pool or token addresses** — hop instructions name arbitrary `pool`/`token` addresses that get invoked. Any contract reached inside the route executes *below the user's authorization*, so it can call `token.transfer(user, attacker, amount)` on any token the user holds; Soroban's host records that transfer as a sub-invocation of the user's auth entry, and a wallet that signs the simulated tree authorizes the theft — exactly the "cookie forwarded to a destination plugin" shape.

### Finding Description
- The controller authenticates the caller at the strategy entrypoint and then forwards the raw route to the configured router: `router.execute_strategy(&controller, &amount_in, swap)` inside `swap_tokens` (contracts/controller/src/strategies/swap.rs:36-38). The controller only authorizes its *own* input transfer via `authorize_transfer_as_current` (line 34); it places no constraint on which addresses the route invokes.
- The aggregator dispatches hop `pool` addresses straight from the decoded payload (`dispatch_hop`, contracts/swap-aggregator/src/venues/mod.rs:23-40) and venue adapters invoke the pool contract by address (e.g., `env.invoke_contract(&ctx.hop.pool, ...)` in comet.rs:30-34). There is no venue/pool registry — the skills doc confirms "None of these appear in the sender's auth tree," i.e., router self-auth covers only its own pulls; anything a pool does under the *user's* auth is unbounded.
- The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the behavior end-to-end: a `RogueHopPool` named by the route calls `token.transfer(alice, attacker, WALLET_BALANCE)` during `swap_collateral`; simulation records it as a child of Alice's `swap_collateral` auth entry, and signing that tree moves her entire unrelated wallet token balance (lines 194-269).

### Impact Explanation
Theft of user funds. An attacker who supplies a malicious route (or a compromised/malicious route source) can name a pool contract that transfers *any* token from the swapper's wallet to the attacker — not just the routed `amount_in`, which is the only quantity the controller bounds (`actual_spent <= amount_in`, swap.rs:44-48). Neither the payload `min_out` nor the final health-factor gate constrains this loss, because the stolen transfer is orthogonal to the swap accounting.

### Likelihood Explanation
Reachable by any unprivileged address crafting a `swap_xdr` (the format is public and attacker-controlled by design). Exploitation requires the victim to sign a simulated auth tree containing the extra `transfer` child — the same trust assumption the Grafana bug relied on (user authorizes a proxy call without inspecting what the destination does with their credential). The threat model itself acknowledges the exposure: "a route can put third-party code on the call stack below the caller's authorization ... The loss is then the caller's wallet" (docs/explanation/threat-model.md:154-160), mitigated only by off-chain client diligence, which is not enforced on-chain.

### Recommendation
Constrain what can ride on the user's authorization: (a) maintain an on-chain allowlist of pool contracts per venue in the aggregator so payload-named destinations are restricted to known DEX pools; and/or (b) have the controller invoke the router such that user-facing strategy entrypoints do not expose the caller's `require_auth` subtree to route-named code — e.g., perform the swap in a separate invocation where the user authorizes only the exact token transfers. At minimum, document and enforce that clients must reject any auth tree containing children beyond the single input transfer.

### Proof of Concept
Already demonstrated by the in-repo test:

1. Alice supplies USDC; attacker deploys `RogueHopPool` storing `(victim=alice, wallet_token, to=attacker, amount=alice's full balance)` and crafts a route naming it as a hop pool.
2. Alice calls `controller.swap_collateral(alice, account, USDC, amount, ETH, route)`. `simulateTransaction` records the auth tree; it contains Alice's `swap_collateral` root with a child `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` (test lines 206-222).
3. If Alice's wallet signs the returned tree (the default flow — wallets auto-sign simulated auth), the pool's `swap` executes `token::Client::transfer(&victim, &to, &amount)` under her authorization and her `WALLET_BALANCE` of the unrelated token moves to the attacker, while the swap itself settles "fairly" and passes all controller risk gates (test lines 224-227, 259-268).
