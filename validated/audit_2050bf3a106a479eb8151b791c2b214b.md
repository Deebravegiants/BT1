### Title
`EvmHost.dispatch()` swaps native ETH for fee tokens using `block.timestamp` as the Uniswap deadline, providing no actual deadline protection - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` allow any unprivileged caller to pay the relayer fee in native ETH. When `msg.value > 0`, the contract swaps ETH for the exact fee-token amount via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the `deadline` parameter [1](#0-0) , and identically for the GET-request path [2](#0-1) . This mirrors the reported bug class exactly (`UniV3SwapInput` / Uniswap deadline misuse): supplying `block.timestamp` as the deadline is equivalent to having no deadline at all, since Uniswap's deadline check (`require(deadline >= block.timestamp)`) is evaluated against the timestamp of the block the transaction is actually mined in — which will always equal whatever value is passed at execution, trivially satisfying the check regardless of how long the transaction has sat in the mempool.

### Finding Description
Uniswap V2/V3 router deadlines exist to bound how long a signed transaction remains executable against quoted market conditions. The correct pattern is to compute the deadline off-chain (or as `block.timestamp + N`) at the time the transaction is *submitted*, so that if the transaction is delayed in the mempool past that point, it reverts rather than executing at a stale price.

`EvmHost.dispatch()` instead computes `block.timestamp` at *execution* time and passes it directly as the swap deadline [3](#0-2) . This means the deadline check inside the router is always satisfied trivially — there is no window enforcement whatsoever. A transaction can sit in the mempool indefinitely (e.g., held by a searcher/validator, delayed due to gas pricing, or intentionally sandwiched) and will still execute the swap at whatever price exists at the moment it's finally included, with the caller having no on-chain guarantee the fee-token price matches expectations at submission time.

The `dispatch()` functions are `external payable` with no access control (`notFrozen` modifier only) [4](#0-3) , making this reachable by any unprivileged caller/application dispatching a POST or GET request and choosing to pay fees in native token.

### Impact Explanation
Because the deadline provides zero protection, callers who pay relayer fees in native ETH are fully exposed to price manipulation via sandwich attacks or delayed inclusion: an attacker can manipulate the ETH/feeToken pool price immediately before the swap executes (front-run) since there is no time bound forcing the swap to revert if conditions have shifted. Since `swapETHForExactTokens` pulls an *exact* output amount (`post.fee`/`get.fee`) but has no `amountInMaximum`-equivalent guard here (the router will consume up to `msg.value`), a caller could be forced to spend meaningfully more ETH than intended to acquire the same fee-token amount, or an MEV actor could profit by sandwiching each dispatch call. This constitutes a fund-loss vector for any protocol/application dispatching cross-chain messages and paying fees natively — a core, frequently-used code path in the protocol (every POST/GET dispatch with native payment).

### Likelihood Explanation
High likelihood: `dispatch()` is a primary, frequently-invoked entry point for any application sending cross-chain messages through Hyperbridge, and paying in native token is an explicitly supported, documented payment path [5](#0-4) . No special privileges or unusual conditions are required to trigger the vulnerable code path — simply calling `dispatch()` with `msg.value > 0` executes the flawed swap every time.

### Recommendation
Do not use `block.timestamp` as the deadline argument to Uniswap functions. Accept a caller-supplied deadline parameter (validated to be reasonable) in `DispatchPost`/`DispatchGet`, or compute `block.timestamp + hostParams.maxSwapDelay` at call time so a genuine expiry window is enforced, causing the swap to revert if the transaction is not included promptly.

### Proof of Concept
1. Application `A` calls `EvmHost.dispatch(DispatchPost{...})` with `msg.value = X` intending to swap ETH for `post.fee` amount of fee token at the current pool price.
2. The transaction sits in the mempool (network congestion, low gas price, or is deliberately held/observed by a searcher).
3. Because `deadline = block.timestamp` is evaluated only once the transaction is finally mined, the deadline check trivially passes no matter how much time has elapsed or how much the price has moved.
4. A searcher front-runs the transaction, shifting the ETH/feeToken pool price unfavorably, then lets `A`'s transaction execute — `A` pays more ETH than expected for the same `post.fee` output, with the difference captured by the searcher via the price impact/back-run.
5. Because the check offers no protection, this can be repeated on every `dispatch()` call that pays with native ETH. [1](#0-0) [2](#0-1)

```text
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
```
