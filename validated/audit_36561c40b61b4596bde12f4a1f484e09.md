### Title
Accrual-time `i128` overflow permanently freezes a market — all exit verbs panic in `global_sync` before the borrow-index cap engages - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
The analog to CVE-2017-6441 is a crash-class defect: an arithmetic trap (here a typed `MathOverflow` panic, the Soroban equivalent of a null-pointer abort) is reachable on a path every user-facing verb must traverse. In `accrue_step`, `scaled_to_original(env, borrowed, borrow_index)` multiplies the scaled debt by the borrow index inside `i128`. On a large high-decimals market at sustained high utilization, the debt *value* outgrows `i128` while the borrow index is still far below `MAX_BORROW_INDEX_RAY`, so the cap that is supposed to bound index growth never engages. Because `interest::global_sync` runs this step before every mutation (`Cache::load` → `global_sync` → mutate), once the market crosses that boundary every subsequent call — `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `claim_revenue`, `recapitalize`, `update_indexes` — panics in the accrual prologue. Nothing can ever move again.

### Finding Description
`common/src/rates/simulate.rs::accrue_step` (lines 60–61) computes `borrowed_original = scaled_to_original(borrowed, borrow_index)` and `supplied_original` the same way. `scaled_to_original` is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), a `mul_div_half_up` that panics with `GenericError::MathOverflow` when `scaled * index / RAY` exceeds `i128` (`common/src/math/fp_core.rs:108-118`). `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`), but the overflow is in the *product* `borrowed_scaled × index`, which hits `i128::MAX` while the index is only ~170× — orders of magnitude below the 10⁹·RAY cap. The cap therefore cannot prevent it.

`contracts/pool/src/interest.rs::global_sync` (lines 20–33) invokes `accrue_chunk` → `accrue_step` unconditionally whenever time elapsed, and the pool README's documented flow (`Cache::load → interest::global_sync → mutate → guards → commit`) shows accrual precedes every market mutation (`contracts/pool/README.md:159-168`). The controller's `update_indexes` path and every account action reach the same step via `Context::cached_market_index`.

The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) demonstrates exactly this end-to-end: after enough years at 98% utilization on the steep XLM-curve segment, `update_indexes` fails with `MathOverflow`, `last.borrow_index < MAX_BORROW_INDEX_RAY` (cap never engaged), and both `withdraw` and `repay` then fail with `MathOverflow` — the market is permanently frozen.

### Impact Explanation
Permanent freezing of funds. All supplier principal, borrower collateral routed through the market, and unclaimed revenue in that hub market become irrevocably locked: repayment is impossible (so borrowers cannot free collateral on other markets either, where positions span the frozen book), withdrawal is impossible, liquidation is impossible, and `recapitalize` — which would be the governance recovery lever — also accrues first and panics. There is no admin escape hatch short of a contract upgrade, which is out of scope.

### Likelihood Explanation
Requires three conjunctive conditions, all reachable by unprivileged actions but demanding scale and time: (1) a market whose asset decimals are high (the test uses 18) and whose supply/borrow caps sit near `max_cap_for_decimals` — note that for an 18-decimal asset the maximum expressible cap (`i128::MAX / 10⁹`) is only ~2× below the ray-value overflow boundary, so the unsafe region overlaps the legitimate cap domain rather than sitting beyond it; (2) debt near the borrow cap at sustained high utilization on a steep rate curve; (3) enough elapsed accrual time for the index to multiply the scaled debt past `i128::MAX` (the test crosses the cliff in under 40 years; at ~1.7× index per the test comment, meaningfully less on steeper utilization). No privileged call is needed to *trigger* the freeze once the state exists — any `update_indexes` call detonates it — but the state itself requires whale-scale capital and a long horizon, so likelihood is low-to-moderate. Severity of impact is critical if it materializes; overall severity is bounded by the setup cost. Medium.

### Recommendation
Bound the product, not just the index. Either (a) detect overflow in `scaled_to_original` inside `accrue_step` and clamp the borrow index to the largest value where `borrowed_scaled × index` still fits `i128` (a "value cap" companion to `MAX_BORROW_INDEX_RAY`), so accrual saturates instead of trapping; or (b) enforce a dynamic borrow cap `debt_scaled ≤ i128::MAX / index` at borrow-entry time so the market can never cross the cliff. Option (a) is preferable since it also unsticks a market that is already near the boundary, whereas (b) only prevents new entries. Whichever is chosen, `docs/reference/formulas.md`'s stated bound must be corrected — the harness test already flags it as wrong.

### Proof of Concept
The committed harness test is the PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`):

```rust
let principal = BILLION * 10i128.pow(18);        // 18-decimals market
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // MathOverflow
}
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Mechanism per chunk in `accrue_step`:
- `borrowed_scaled` (RAY) stays fixed; `borrow_index` grows ~e^(rate·Δt) each chunk.
- `borrowed_scaled × borrow_index` crosses `i128::MAX` while `borrow_index ≈ 170·RAY ≪ MAX_BORROW_INDEX_RAY`.
- `mul_div_half_up` inside `Ray::mul` overflows → `panic_with_error!(MathOverflow)` → the entire transaction reverts, and since `global_sync` is the first step of every verb, no subsequent transaction can touch the market.
