### Title
Webhook `shop-domain` header is trusted as tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` only proves the body bytes match a signature computed with the app's shared `client_secret`. The `shop` (and `topic`/`webhook_id`/`api_version`) values are read straight from unauthenticated HTTP headers and are never included in the signed payload, yet `Registry.process` forwards `request.shop` to the app's handler as trusted tenant identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed from HTTP headers, and none of them are part of `to_signable_string` — only `@raw_body` is: [2](#0-1) 

`Registry.process` validates the HMAC only against this body-only signable string, then uses the unauthenticated `request.shop` value as the tenant identity handed to the app's handler: [3](#0-2) 

Shopify signs webhooks per-app (using the single `client_secret` shared across every shop that has the app installed), not per-shop. Because `shop-domain`, `topic`, and `webhook_id` are excluded from the signed bytes, `HmacValidator.validate` only proves "this body was signed by someone holding this app's `client_secret`" — it says nothing about which shop the body actually belongs to. The binding that should hold is:

`shop asserted in header == shop that produced the signed body`

but the code only checks:

`hmac(header) == hmac(compute(body, secret))`

with `shop` entirely outside the equality. This is exactly the "field acted on but not covered by the HMAC" class from the report: `coreId`/`parentId`/`datasetId` were unauthenticated fields consumed downstream in the Solidity example; here `shop` is the unauthenticated field consumed downstream by `WebhookMetadata`/handler logic across all apps built on this gem.

### Impact Explanation
Any tenant (shop) that has the target app installed receives correctly-signed webhooks for its own events. Since the HMAC secret is shared across all shops using that app installation, and the shop identity is never bound into the signature, a malicious/compromised shop can capture one of its own valid `(body, hmac)` pairs and replay it to the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to name a victim shop. `Registry.process` will pass validation and dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop. Any host application that uses this gem's `shop` value to look up/mutate per-tenant state (installation status, subscription status, GDPR `shop/redact`, `customers/data_request`, `app/uninstalled` cleanup, etc.) can be tricked into acting on the wrong tenant's data — a cross-tenant identity confusion originating from this gem's own validation contract.

### Likelihood Explanation
Exploitation only requires installing the app on any shop (the normal, unprivileged path for any merchant) and capturing one legitimate webhook delivery, then replaying it with a modified header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required beyond what any regular merchant tenant already has.

### Recommendation
Bind the tenant/topic identity into the verified signature, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the validated body — e.g., include them in `to_signable_string`, or require the host app to independently confirm the shop via a value that Shopify itself signs (not simply trusting a raw header). At minimum, document that `request.shop`/`topic` are unauthenticated and must be re-validated against known/registered shops before being used for any tenant-scoped action, and consider failing closed if the gem cannot make this guarantee itself.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, receiving legitimately signed webhooks (shared app `client_secret`).
2. Attacker records a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair from one such webhook.
3. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret: [4](#0-3) 
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, `topic`, and `webhook_id` all taken from attacker-controlled headers: [5](#0-4) 
6. The host application acts on `victim.myshopify.com` using attacker-supplied body content, achieving cross-tenant impact.
