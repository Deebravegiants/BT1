This confirms the documented contract: `ShopifyAPI::Webhooks::Registry.process` is expected to "verify the request did indeed come from Shopify" and the handler trusts `data.shop` as the tenant identifier for downstream actions (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)` as shown in the doc's own example).

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` (tenant identity) field that host applications are told to trust is taken from an HTTP header that is never included in the HMAC-signed material. This breaks the identity binding `HMAC(raw_body) valid ⇒ shop header is authentic`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against anything cryptographically bound to the request: [2](#0-1) 

`Registry.process` validates only the HMAC of the raw body via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the raw body) and `verifiable_query.hmac` — never the shop header: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is forwarded unchanged into `WebhookMetadata` and handed to the host application's handler as the trusted tenant identifier: [5](#0-4) 

The gem's own documentation instructs developers to trust `data.shop` as "the shop domain of the webhook" and to use it directly to scope work per-tenant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and states that `Registry.process` "will verify the request did indeed come from Shopify" — implying the shop identity itself is authenticated, which it is not.

This is the same bug class as the reported Argo issue: an enforcement mechanism (HMAC / collateral-ratio check) is applied, but a field that is actually acted upon (the shop header / vault's real debt) is not covered by that mechanism, letting an attacker manipulate the uncovered field while keeping the check passing.

### Impact Explanation
Any entity that can obtain one genuine `(raw_body, HMAC)` pair signed with the app's `api_secret_key` — trivially available to any developer/attacker who installs the target app on their own Shopify store, since Shopify sends them real signed webhooks for their own shop — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim merchant's domain). The HMAC validation still succeeds because the header is not part of the signed content, so `Registry.process` invokes the handler with `data.shop` set to the attacker-chosen victim shop. Any host application that uses `data.shop` to select the tenant/session/database record to update (the exact pattern shown in this gem's own documentation) can be made to write, delete, or process data under a victim shop's identity — a cross-tenant access primitive.

### Likelihood Explanation
High likelihood: the only requirement is the ability to register the target app on any single shop (including the attacker's own store, which typically requires no special privilege for public apps) to legitimately receive at least one signed webhook, and then a trivial HTTP replay with a modified header — no access to `api_secret_key`, access tokens, or any other credential is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the verified payload before it is trusted (e.g., derive/validate the shop against a value obtained from a previously established, per-shop authenticated session rather than trusting the unauthenticated header verbatim). At minimum, `VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the shop domain header so `HmacValidator.validate` fails if that header is tampered with.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) for their own store, capturing the raw body `B` and the genuine `X-Shopify-Hmac-Sha256` header `H` computed by Shopify over `B` with the app's `api_secret_key`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H` — validation succeeds. [3](#0-2) 
4. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the request never involved the victim shop, letting the attacker-controlled body `B` be processed as if it originated from the victim.
