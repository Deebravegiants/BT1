This confirms the vulnerability: the Tron-specific `IntentGatewayV2.sol` contract uses raw low-level `.call()` with the `IERC20.transfer` selector and only checks the boolean `success` returned by the low-level call (i.e., whether the call reverted), but never decodes/validates the ABI-encoded `bool` return value that `transfer()` itself returns. Tokens that return `false` on failure instead of reverting (the classic non-compliant/legacy ERC20 pattern, e.g. some deployed on Tron/TRC20 tokens) will make `success == true` even though the transfer silently failed, while escrow accounting (`_orders[...] -= amount`) still decrements as if the transfer succeeded — permanently losing beneficiary funds without ever delivering them.

### Title
Unchecked ERC20 boolean return value in `withdraw()`/`onAccept()` (`SweepDust`) permits silent transfer failure and permanent loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron deployment of the IntentGateway release escrowed ERC20 tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the low-level `success` boolean, never decoding the actual `bool` returned by `transfer()`. This differs from the main EVM `IntentGatewayV2.sol`/`IntentsBase.sol`, which correctly use OpenZeppelin's `SafeERC20.safeTransfer` [1](#0-0) .

### Finding Description
`withdraw()` is invoked from `onAccept()` when an incoming ISMP POST request carries `RequestKind.RedeemEscrow` or `RequestKind.RefundEscrow`, after authentication of the request source/proof [2](#0-1) . Inside `withdraw()`, for every non-native token in `body.tokens`, the contract does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

`success` here only reflects whether the external call reverted, not the boolean payload the ERC20 standard requires `transfer()` to return. Any ERC20 (or TRC20, since this contract targets Tron) that returns `false` on failure rather than reverting — a well-known non-standard-but-common behavior — will cause `success` to be `true` even though no tokens moved. The function then unconditionally decrements the escrow accounting `_orders[body.commitment][token] -= amount`, and marks the order filled/refunded via `_filled[body.commitment] = beneficiary`, permanently losing the ability to redeem those funds: the beneficiary never receives the tokens, and the internal accounting believes they were already paid out. The same pattern recurs for the transaction-fee payout in the same function [4](#0-3)  and in the `SweepDust` branch of `onAccept()` [5](#0-4) .

### Impact Explanation
This results in permanent freezing/loss of escrowed intent funds: tokens remain locked in the `IntentGateway` contract's balance (since they were never actually transferred out), while the protocol's internal bookkeeping (`_orders` mapping and `_filled` marker) treats the order as settled, so there is no legitimate path left to retry or reclaim the withdrawal for that commitment. This is reachable by any relayer delivering a valid cross-chain `RedeemEscrow`/`RefundEscrow` message once the corresponding order was filled/refunded on the source chain — an ordinary, unprivileged part of the intents flow.

### Likelihood Explanation
Likelihood is moderate-to-high in practice for a Tron deployment: TRC20 tokens (Tron's ERC20 equivalent) are historically inconsistent in complying with strict revert-on-failure semantics, and some popular tokens return `false` instead of reverting on insufficient balance/blacklist/pause conditions. Since this code path executes on every escrow redemption/refund and every dust sweep, a single incompatible token configured as an intent input/output token is enough to trigger fund loss on that specific withdrawal.

### Recommendation
Replace the raw `.call` + `success`-only checks with OpenZeppelin's `SafeERC20.safeTransfer` (as already done correctly in the main EVM contracts, e.g. `IntentsBase._withdraw` [1](#0-0) ), which decodes and validates the returned boolean (or accepts tokens with no return data) and reverts on failure. Apply this consistently in `withdraw()` (both the token loop and the fee payout) and in the `SweepDust` branch of `onAccept()`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., insufficient contract balance due to a race, or a paused/blacklisted-recipient TRC20).
2. Create and fill an order that escrows this token; on fill/refund, Hyperbridge relays a `RedeemEscrow`/`RefundEscrow` request to `onAccept()`, invoking `withdraw()` [6](#0-5) .
3. If the token's `transfer()` call returns `false` (without reverting) for the given amount/recipient at execution time, `success` is `true`, `TransferFailed` is not raised, `_orders[commitment][token]` is decremented, and `_filled[commitment]` is set.
4. The beneficiary never received the tokens; the escrowed balance sitting in the contract for that commitment is now unreachable through any subsequent redeem/refund call, permanently freezing those funds in the contract.
