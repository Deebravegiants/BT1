Confirmed root cause: the webhook `hmac` signature only covers `to_signable_string` = `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers (`lib/shopify_api/webhooks/request.rb:20-33`) and are never included in the signed bytes. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) only proves that `@raw_body` was signed by `Context.api_secret_key`; it says nothing about which shop or topic header accompanied that body. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) then trusts `request.shop` as the tenant identity and hands it straight to the host app's handler via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` without any re-binding to the signed payload.

### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, so the HMAC that `Utils::HmacValidator` checks proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers carried alongside that body.

### Finding Description
`Request#hmac` is read from the `X-Shopify-Hmac-Sha256` header and validated via `OpenSSL.secure_compare(computed_signature, received_signature)` in `lib/shopify_api/utils/hmac_validator.rb#L26-L31`, where `computed_signature` is `HMAC(api_secret_key, verifiable_query.to_signable_string)`. For `Request`, `to_signable_string` is defined as simply `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers (`lib/shopify_api/webhooks/request.rb:20-33`), which are never mixed into the signed bytes. `Registry.process` validates only the body's HMAC (`lib/shopify_api/webhooks/registry.rb:190`) and then uses `request.shop` to build `WebhookMetadata` passed to the app's handler (`lib/shopify_api/webhooks/registry.rb:198-199`), effectively trusting the header as the source-of-truth tenant identity.

Because a single app-level `client_secret` (`Context.api_secret_key`) is shared across every merchant install, any body+HMAC pair that is valid for one shop's webhook delivery is also a valid HMAC for the *identical* body claimed to originate from a different `shop-domain` header. The binding that should hold is:
`shop_authenticated == shop_the_signed_bytes_actually_came_from`
but because `shop` is outside `to_signable_string`, this becomes:
`shop_authenticated == shop header value (attacker-controlled, unauthenticated)`.

### Impact Explanation
An unprivileged internet user who can observe or replay one legitimately-HMAC'd webhook body for the target app (e.g., from their own store's install, or a captured/leaked delivery) can resend it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` will accept the HMAC (since it only checks the body) and dispatch the handler believing the payload belongs to the spoofed victim shop, causing cross-tenant data confusion in whatever business logic the host app performs keyed off `WebhookMetadata#shop` (e.g., updating the wrong merchant's records, triggering redaction/GDPR flows for the wrong shop, or unlocking shop-scoped features). This crosses a tenant boundary using only a body/HMAC pair the attacker can legitimately obtain from their own shop.

### Likelihood Explanation
Requires the attacker to possess at least one valid `(body, hmac)` pair for the target app (trivially available to any merchant/developer who has installed the app on their own store, since every legitimate webhook delivery is signed with the same shared `client_secret`) and the ability to POST to the app's public webhook endpoint with a modified header — both are unprivileged actions requiring no leaked secrets.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content evaluated by `Request#to_signable_string`, or otherwise cryptographically bind the header-derived tenant identity to the verified payload before it is handed to `Registry.process`/`WebhookMetadata`, so an attacker cannot decouple a validly-signed body from an arbitrary shop/topic claim.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker replays the same `B`/`H` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) and `Utils::HmacValidator.validate(request)` returns `true`, since it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` invokes the host app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on attacker-supplied order data as if it belonged to `victim.myshopify.com`. [1](#0-0) [2](#0-1) [3](#0-2)
