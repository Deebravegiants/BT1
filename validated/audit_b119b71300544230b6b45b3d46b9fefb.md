### Title
Webhook shop/topic/webhook_id identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the app relies on to route/attribute the webhook are read straight from unauthenticated HTTP headers. `Registry.process` verifies the body's HMAC but then forwards these unauthenticated header values to the app's handler as trusted metadata, breaking the binding between "bytes verified" (the body) and "bytes acted on" (the shop identity).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all parsed directly from the `x-shopify-*`/`shopify-*` headers, which are never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` (none of which are covered by the signature) and hands them to the app's handler as authoritative metadata: [4](#0-3) 

This is the exact identity-binding gap called out in the report class: a field (`shop`) that is acted upon (used to attribute/route webhook data, as shown in the gem's own documented handler example that keys work off `data.shop`) but is not covered by the HMAC that is supposed to authenticate the request.

Because the HMAC is computed purely over the body with the app's shared `client_secret`, any body/HMAC pair legitimately generated for one shop (e.g. an attacker's own test/dev store, which they fully control and can trigger webhooks on) remains a valid HMAC for that exact same body regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it. An attacker who controls a store with the app installed can capture one genuine webhook delivery (valid body + valid HMAC) and then POST that same body/HMAC pair directly to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop. `Registry.process` will validate successfully (HMAC only checks the body) and dispatch to the handler with `shop: "<victim-shop>"`, `topic`, and `webhook_id` all attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: `HMAC-verified-body == HMAC-verified-body-for-shop-X` does not imply `request.shop == shop-X`. Any host application that follows the gem's documented pattern (using `data.shop` to select which tenant's records to create/update, as shown in `docs/usage/webhooks.md`) can be made to ingest attacker-chosen webhook content attributed to an arbitrary victim shop, without the attacker ever having access to that shop — a cross-tenant data injection/confusion issue.

### Likelihood Explanation
Requires only: (1) the app's webhook endpoint reachable over the internet (which is required for Shopify webhooks by design, per the gem's own docs) and (2) attacker control of any shop where the app is installed (e.g. a free/dev store) to obtain one legitimately-signed body+HMAC pair. No access token, `client_secret`, or privileged account is needed — this is reachable by any unprivileged internet user who can install the app on a store they control.

### Recommendation
Bind the identity fields to the signature instead of trusting raw headers post-HMAC-check:
- Either include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC computation (this would require coordinating with Shopify's actual webhook signing format), or
- At minimum, cross-check the `shop-domain` header against a known/expected set of shops with active registrations for that `topic`/`webhook_id` before dispatching to the handler, and document clearly that `data.shop`/`data.topic` are unauthenticated header values that must not be used as the sole tenant-selection key without additional verification (e.g. looking up the webhook subscription by `webhook_id` via the Admin API to confirm the shop association).

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled store `attacker.myshopify.com`, subscribed to some webhook topic (e.g. `orders/create`).
2. Trigger the webhook so Shopify delivers a POST to the app's public webhook URL with a genuine body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture `B` and `H`.
4. Send a new POST directly to the same public webhook endpoint with body `B`, `x-shopify-hmac-sha256: H` (unchanged, still valid since HMAC only covers `B`), but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(client_secret, B) == H`: [4](#0-3) 
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes/attributes the attacker's payload `B` as if it originated from the victim shop.
