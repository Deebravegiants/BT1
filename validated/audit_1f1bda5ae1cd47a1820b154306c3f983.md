### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header identity is trusted without being bound to the HMAC-verified payload, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by verifying the HMAC over the raw request body only, but the tenant-identifying `shop` value (and `topic`/`webhook_id`/`api_version`) is read from an unauthenticated HTTP header and handed to the handler as trusted. Any actor who can obtain one genuine, signature-valid webhook delivery (e.g. by installing the app on their own store) can replay that exact body+HMAC while swapping the `Shopify-Shop-Domain` header to a victim shop, producing a webhook the app will process as if it originated from the victim.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers that are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature exclusively against `verifiable_query.to_signable_string`, i.e. the body, never the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the metadata delivered to application code: [4](#0-3) 

The gem's own documentation instructs developers to use `data.shop` as the tenant identifier for downstream processing (e.g. enqueuing jobs keyed by shop), reinforcing that this field is expected to be trustworthy: [5](#0-4) 

This breaks the identity binding: **shop header value == shop that produced the HMAC-signed body** is never enforced. The HMAC only proves "this body was signed by our shared secret for *some* delivery," not "this body was signed *for this shop*."

### Impact Explanation
Because `topic`, `shop`, `webhook_id`, and `api_version` are excluded from the signed payload, an attacker who controls any shop with the app installed can capture one legitimate webhook delivery from Shopify (valid body + valid HMAC for that body), then resend the identical body/HMAC to the app's webhook endpoint with a forged `Shopify-Shop-Domain` header naming a different, victim shop. `Registry.process` will accept it (HMAC check only covers the body) and dispatch it to the handler tagged as belonging to the victim shop. Any application logic that keys storage, job queues, authorization, or state transitions off `WebhookMetadata#shop` (exactly as the documented example does) will attribute attacker-controlled webhook data to another tenant — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
Exploitation requires only: (1) the attacker have a shop where the target app is installed (a normal, unprivileged self-service action — installing a public/free app), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers, which is trivial. No access token, `client_secret`, or privileged account is required — the attacker reuses their own genuinely-issued webhook payload/HMAC pair. This is a realistic, low-effort attack path.

### Recommendation
Bind the shop (and topic/webhook_id) into the HMAC-verified material, or otherwise cryptographically tie the header-derived identity to the signed body — e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` before computing/verifying the signature, so a mismatch between the claimed shop and the shop the signature was actually issued for is detected. At minimum, document prominently that `data.shop`/`data.topic`/`data.webhook_id` are NOT covered by the HMAC and must not be used as a sole tenant/authorization key without additional server-side shop verification (e.g. cross-checking against a known/registered shop list per session).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's endpoint. Attacker captures the raw request: body `B`, and header `Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), along with `Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends an HTTP POST to the same webhook endpoint with:
   - Body: unchanged `B`
   - `Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`)
   - `Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `Shopify-Topic`, `Shopify-Webhook-Id` optionally forged too
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (`lib/shopify_api/webhooks/request.rb:45-63`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though Shopify never sent this webhook for that shop, and the app processes/stores it as victim-shop data per the documented handler pattern (`docs/usage/webhooks.md:25-26`).

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
