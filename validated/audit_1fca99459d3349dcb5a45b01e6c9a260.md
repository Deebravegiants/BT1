### Title
Arbitrary `op.endpoint.call` in `EmporiumUpgradeable.runAction` bypasses the token balance invariant for any ERC20/ETH not listed in `circomData.erc20TokenAddresses` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only measures balance changes for the tokens present in `circomData.erc20TokenAddresses`, exactly like the `ConvexTradeExecutor.totalFunds()` accounting gap described in the external report (a token held by the contract that is excluded from the accounting sum). Because Emporium operations can call **arbitrary** endpoints with **arbitrary** calldata (`op.endpoint.call{value: op.value}(op.callData)`), any token balance the shared `Emporium` contract holds that is not part of the caller-supplied `erc20TokenAddresses` array is completely invisible to the balance-diff checks in both `runAction` and the outer `Hinkal.transact` settlement loop, and can therefore be swept out by an unrelated, unprivileged caller.

### Finding Description
`runAction` snapshots balances only for the declared token list, executes the caller-supplied operations, and re-snapshots the same list: [1](#0-0) [2](#0-1) [3](#0-2) 

In the "stateless" branch (`invokeWallet == false` or `signerAddress == address(0)`), the call executes directly from the shared, singleton `Emporium` contract (`msg.sender == Emporium` on the target token), and the only restrictions are on two specific selectors targeting the `HinkalWallet` interface: [4](#0-3) 

Any ERC20/ETH balance that ends up on this shared `Emporium` contract but is **not** included in `erc20TokenAddresses` (e.g. dust/rewards returned by a router call in a token the caller didn't declare, or residual amounts left from a previous user's transaction) is never inspected by the `balancesBefore`/`balancesAfter` loop, and is never swept out via `handleOut`, which only iterates the same declared list: [5](#0-4) 

The same gap exists one layer up in `Hinkal.transact`, whose balance-equation invariant ("change in balance == change in UTXOs") is likewise scoped only to `circomData.erc20TokenAddresses`: [6](#0-5) 

Because `op.endpoint.call` is otherwise unrestricted, any caller can submit an `EmporiumOperation` whose `endpoint` is the residual/untracked token contract and whose `callData` is `transfer(attacker, amount)`, while declaring an unrelated `erc20TokenAddresses` set (e.g., a token they legitimately control) so that neither `runAction`'s nor `Hinkal.transact`'s balance checks ever look at the stolen token. This transfers value out of the shared Emporium contract with no corresponding nullifier spend, UTXO burn, or `calldataHash`/public-input coverage of the stolen token — breaking the fundamental "shielded balance in == balance out" equality without any check catching it.

### Impact Explanation
Any ERC20/ETH balance sitting on the shared `Emporium` contract but not covered by the current transaction's `erc20TokenAddresses` can be directly siphoned by any unprivileged caller via a crafted `EmporiumOperation`, with the protocol's own balance invariant (in both `runAction` and `Hinkal.transact`) blind to the movement. This is direct theft of protocol/other-users' funds held by the Emporium contract, matching the "Critical - direct theft of shielded or in-flight user funds" / "High - theft ... of protocol/relay fees" categories, since such residual balances (dust from swaps, unclaimed reward tokens returned by an integrated protocol, rounding remainders, etc.) are a normal byproduct of arbitrary external-call execution and are never proactively withdrawn for tokens outside the declared set.

### Likelihood Explanation
Likelihood is moderate-to-high: any user of the Emporium (via legitimate multi-hop swaps/interactions with external protocols) can inadvertently leave behind a token balance not declared in `erc20TokenAddresses` for that transaction (the circuit only needs to declare the tokens relevant to that user's own inputs/outputs, not every token an external call might touch/return). Once such a balance exists, exploitation requires nothing more than an unprivileged caller submitting a normal Hinkal transaction with a `EmporiumOperation` performing `token.transfer(attacker, amount)` — no admin, relay, or signature bypass is needed for the stateless (`signerAddress == address(0)`) path.

### Recommendation
Extend the balance-invariant checks in both `EmporiumUpgradeable.runAction` and `Hinkal.transact` to cover every token actually touched during external-call execution, not just the caller-declared `erc20TokenAddresses`. At minimum, restrict `op.endpoint.call` targets/selectors to a vetted allowlist, or require any token balance change on the Emporium/Wallet contracts (regardless of whether it's in `erc20TokenAddresses`) to be accounted for and either swept to the correct owner's UTXO or reverted if unaccounted-for value appears.

### Proof of Concept
1. User A performs a legitimate Emporium swap through an external router; the router unexpectedly returns a small amount of a bonus/reward token `X` not included in that transaction's `erc20TokenAddresses`. This `X` balance is stranded on the shared `Emporium` contract (not withdrawn by `handleOut`, since it only iterates the declared token list).
2. Attacker B calls `Hinkal.transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = [Y]` (an unrelated token they legitimately own a UTXO for, possibly with zero amount change), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, B, balanceOf(Emporium, X))}]`.
3. `runAction` executes the operation (`X.transfer(B, amount)`, `msg.sender == Emporium`), succeeding since `X` is a plain ERC20 and Emporium holds the balance; `payRelayFees` and the before/after balance loop only look at `Y`, so the transfer of `X` is never checked.
4. `Hinkal.transact`'s outer balance-diff loop also only iterates `erc20TokenAddresses = [Y]`, so it never notices `X` left the contract.
5. Attacker B has stolen token `X` from the shared Emporium contract with no nullifier spent and no UTXO created for it.
