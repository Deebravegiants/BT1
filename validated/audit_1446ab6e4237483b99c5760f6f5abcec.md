### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are never included in the signed material. `Registry.process` validates the HMAC against the body and then trusts the header-derived `shop` value when dispatching to the app's handler, breaking the binding between "what was cryptographically verified" and "what is acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` recomputes the signature purely from `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before trusting `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The expected identity binding should be: `HMAC-verified(shop, topic, body) == acted-upon(shop, topic, body)`. In this implementation it is actually: `HMAC-verified(body) == acted-upon(shop, topic, body)`. Since a Shopify app's `api_secret_key` is a single shared secret used to sign webhooks for *every* shop that has installed the app (not per-tenant), any attacker who controls one installed shop (including their own free/dev store) can obtain a genuinely-signed `(body, hmac)` pair. They can then replay that exact body+hmac pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it never examined the header, and `Registry.process` dispatches the forged event to the handler labeled with the victim's shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): an attacker with a single legitimate install can inject fabricated webhook events that the host application will process as if they originated from an arbitrary victim shop chosen by the attacker (not limited to the attacker's own store). Any application logic keyed off `WebhookMetadata#shop` (e.g., updating the victim merchant's local records, triggering side effects like inventory sync, fulfillment, or billing events "for" the victim shop) can be manipulated by an unrelated, unprivileged attacker, without needing the victim's session or access token.

### Likelihood Explanation
Any developer/attacker can install the app on their own store (a normal, unprivileged, unauthenticated action from Shopify's perspective) and thereby legitimately receive at least one webhook with a valid HMAC over an attacker-influenced body (e.g., an `app/uninstalled` or product-update webhook where the attacker controls some body content). Replaying it directly to the app's public webhook endpoint with a modified `shop-domain` header requires only a single crafted HTTP request — no secrets, no cryptography to break.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header value as part of the signable content that is authenticated, or independently authenticate the shop asserted in the header against a value derived from data that is protected by the HMAC (e.g., cross-check against the currently-registered webhook subscription for that shop/topic before trusting `request.shop`). At minimum, document and enforce that host applications must not treat the `shop-domain` header as trusted for tenant separation purposes without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-SHA256: H` (where `H = HMAC_SHA256(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint but replaces the header with `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and `X-Shopify-Hmac-SHA256: H` unchanged.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only (`lib/shopify_api/utils/hmac_validator.rb` line 29 via `to_signable_string`), which matches `H`, so the check passes.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) dispatches the handler with `shop: "victim.myshopify.com"`, even though the request never touched Shopify's servers on behalf of that victim shop.
