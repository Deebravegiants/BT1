## Analysis

The audit report describes a bug class where an identity-binding check (a validation fix) was applied to one code path (`CurveSpell`) but missed in an analogous code path (`ConvexSpell`) that shares the same vulnerable pattern. Searching `lib/shopify_api/**` for the equivalent pattern — a `shop` value used to build the OAuth host that receives the app's `client_id`/`client_secret`, validated in some flows but not others — surfaces exactly this inconsistency between `ShopifyAPI::Auth::Oauth.begin_auth` and the sibling OAuth-token flows (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`).

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` enables forced-OAuth / session-fixation via attacker-controlled authorize host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth "authorize" redirect URL directly from the caller-supplied `shop` value, with no domain validation. Every sibling method in the gem that turns an untrusted `shop:` argument into a request host explicitly calls `Utils::ShopValidator.sanitize!` first — except `begin_auth` (and its counterpart `validate_auth_callback`, which relies solely on `HmacValidator`).

### Finding Description
`ShopifyAPI::Auth::Oauth.begin_auth` takes a `shop:` argument and calls the private helper `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` with no domain restriction, then appends `/oauth/authorize?client_id=...&redirect_uri=...&state=...`: [1](#0-0) [2](#0-1) 

Compare this to the other three places in the gem where a caller-supplied `shop` is turned into a request host: [3](#0-2) [4](#0-3) [5](#0-4) 

In all three, `Utils::ShopValidator.sanitize!(shop)` is called before the value is used to construct the `Session`/request host — enforcing the binding `{shop host used to reach the OAuth endpoint} == {a domain in ShopValidator::TRUSTED_SHOPIFY_DOMAINS}`: [6](#0-5) [7](#0-6) 

`begin_auth` is the one OAuth-related function that has no other identity check available (no HMAC exists yet at this stage of the flow — the query is unsigned), yet it is exactly the entry point where `shop` most plausibly comes straight from an unauthenticated request parameter (e.g., a `/login?shop=` install link), matching the gem's own documented usage: [8](#0-7) 

Because the fix (`ShopValidator.sanitize!`) exists elsewhere in the same module family but was not carried over to `begin_auth`, an attacker can supply an arbitrary `shop` value (e.g. `evil.attacker.com`) that is not a `myshopify.com`/trusted domain, and the library will construct and return a redirect URL pointing at that attacker-controlled host, carrying the real app's `client_id`, `redirect_uri`, and — critically — the freshly generated OAuth `state` nonce, while also setting that same `state` value into a cookie on the victim's browser (`SessionCookie`): [9](#0-8) 

### Impact Explanation
This breaks the binding `{state value known only to app + victim browser} == {state value used by whoever completes OAuth}`. Since the attacker's own server is the redirect target, the attacker directly observes the `state` nonce placed in the authorize-URL (rather than needing to guess or leak it), while that same nonce has already been written into the victim's browser cookie via `SessionCookie`. The attacker can then complete a legitimate OAuth authorization on their own Shopify store (obtaining a Shopify-signed `code`/`hmac`/`state`-matching callback) and lure the victim into visiting the app's real callback URL with the attacker's `code`/`shop`/`state`. Because `validate_auth_callback` only checks `state == auth_query.state` against the cookie and a valid `HmacValidator` signature (both satisfiable using the attacker's own genuine store), the app will bind the attacker's shop/access token into the victim's session — a forced OAuth completion / session-fixation attack. This matches the "High - session fixation or forced OAuth completion" impact category. [10](#0-9) 

### Likelihood Explanation
Exploitability requires only that a host application pass a request-derived `shop` value into `begin_auth` without its own extra validation — which is exactly the pattern shown in the gem's own usage documentation (`request.parameters` / `shop` query param), and is the same class of trust the gem itself defends against in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token` via `ShopValidator.sanitize!`. No credentials, tokens, or privileged access are required by the attacker — only the ability to send the victim a crafted install link, matching an "unprivileged internet user" threat model.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `ShopifyAPI::Auth::Oauth.begin_auth`, mirroring `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, and use the sanitized value when building `auth_base_uri`. Consider also sanitizing `auth_query.shop` in `validate_auth_callback` for defense in depth, even though it is HMAC-covered.

### Proof of Concept
1. Host app exposes `GET /login?shop=<param>` and calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` per the documented pattern.
2. Attacker sends victim a link: `https://victim-app.example.com/login?shop=evil.attacker.com`.
3. `begin_auth` computes `auth_base_uri("evil.attacker.com")` → `"https://evil.attacker.com/admin"`, and returns `auth_route = "https://evil.attacker.com/admin/oauth/authorize?client_id=<real client_id>&redirect_uri=https://victim-app.example.com/auth/callback&state=<nonce>"`, plus sets a `SessionCookie` containing `<nonce>` on the victim's browser.
4. Victim's browser is redirected to `evil.attacker.com`, which now knows `<nonce>`, `client_id`, and `redirect_uri`.
5. Attacker separately performs real OAuth on their own Shopify store to obtain a Shopify-signed `code`/`hmac` for their store, then lures the victim (whose browser still carries the `<nonce>` cookie) to visit `https://victim-app.example.com/auth/callback?code=<attacker code>&shop=<attacker shop>&state=<nonce>&hmac=<valid hmac>`.
6. `validate_auth_callback` passes (`HmacValidator.validate` succeeds since it's a genuine Shopify signature; `state == auth_query.state` succeeds since the cookie holds the attacker-observed nonce), and the victim's session becomes bound to the attacker's shop/access token.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
