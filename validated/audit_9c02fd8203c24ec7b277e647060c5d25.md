### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` never checks the `shop-domain` header against the HMAC. Any attacker who obtains one valid `(body, hmac)` pair for the app (e.g., from their own free/trial store that has the app installed) can replay that exact pair to the webhook endpoint while swapping in a victim shop's domain, and the signature will still validate. The handler then dispatches to app logic using the attacker-chosen `shop` value, breaking the tenant binding between HMAC and shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`, while `shop` is read from a separate, unsigned header: [2](#0-1) 

`HmacValidator.validate` computes the HMAC solely from `verifiable_query.to_signable_string` and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` relies exclusively on this HMAC check before trusting `request.shop` for dispatch: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the same across every shop that has the app installed, a body+HMAC pair legitimately generated for one shop (e.g., an attacker's own dev/trial store) remains a valid signature for that exact body no matter which shop-domain header accompanies it. The identity binding that should hold — `shop-header == shop-covered-by-HMAC` — does not exist; `shop` is acted upon (`WebhookMetadata.new(... shop: request.shop ...)`) but never covered by the signature.

### Impact Explanation
This breaks the shop/tenant identity binding for a Critical/High-impact category (cross-tenant access): an attacker with any working installation of the app on a store they control can capture a legitimate `(raw_body, hmac)` pair for a webhook topic of their choosing, then replay it against the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header set to an arbitrary victim shop that also has the app installed. The receiving application (using this gem's `Registry.process`/`WebhookMetadata`) will treat the forged event as authentic for the victim shop, since the only verification performed — the HMAC — never covered the shop field. Depending on which webhook topic's body the attacker replays, this can trigger tenant-scoped side effects (e.g., data deletion/redaction flows, uninstall handling, order/customer processing) attributed to the wrong shop.

### Likelihood Explanation
Likelihood is realistic: creating a store with the app installed to harvest a valid `(body, hmac)` pair requires no privileged access to the target — any internet user can sign up for a free/trial Shopify store, install the target app, trigger a webhook event, and capture the body/HMAC from their own webhook delivery. Replaying it against the shared webhook endpoint with a different shop header requires only a normal unauthenticated HTTP POST.

### Recommendation
Include the shop identifier (and ideally the topic) in the signable payload, or otherwise cryptographically bind the `shop-domain` header to the signature verification — e.g., compute/verify the HMAC over `shop + topic + raw_body` (matching how the header is trusted), or independently verify that the shop asserted in the header matches a shop-scoped secret/session already known to the app before dispatching. At minimum, document that consuming apps must not treat the `shop-domain` header as trusted without additional shop-existence/session checks, and add a check in `HmacValidator`/`Registry.process` that ties the verified signature to the specific shop header value.

### Proof of Concept
1. Install the app on an attacker-controlled store `attacker.myshopify.com` and trigger any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (a store that also has the app installed).
3. Because `Request#to_signable_string` only hashes the body: [1](#0-0) 
`HmacValidator.validate` returns `true`, and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` even though Shopify never actually sent this event for that shop: [4](#0-3)
