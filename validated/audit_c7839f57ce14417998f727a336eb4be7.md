### Title
Webhook shop, topic and webhook-id are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` by reading them directly from HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. `Registry.process` validates the HMAC and then forwards the *unauthenticated* header-derived `shop`/`topic`/`webhook_id` straight to the app's webhook handler as trusted tenant/context metadata.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature check exclusively to `@raw_body`: [1](#0-0) [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are pulled from HTTP headers that are never part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body bytes are untampered / genuinely produced with the shared secret at some point) and then trusts the header-sourced `shop`, `topic`, and `webhook_id` when constructing the metadata handed to the app's handler: [4](#0-3) 

The broken identity binding is: **`shop` authenticated by the HMAC (none) ≠ `shop` acted upon by the handler (the `X-Shopify-Shop-Domain` header value)**. The HMAC only proves "this body was signed with the app's secret for *some* webhook, at some point," not "this body/topic/webhook-id came attached to *this* shop." Since `HmacValidator.validate` (shared with OAuth) only checks `to_signable_string` against `hmac`, and `to_signable_string` for `Request` is just `@raw_body`, an attacker who possesses one validly-signed webhook body (e.g., from a webhook delivered to their own shop/app installation, which is not a privileged secret) can replay that identical body with the `hmac-sha256` header unchanged while substituting the `shop-domain`, `topic`, and `webhook-id` headers for a victim's values. The signature will still validate because the body bytes are untouched, yet the app receives forged tenant/topic/webhook-id context.

### Impact Explanation
This directly matches "cross-tenant access": a host application that trusts `WebhookMetadata#shop` (constructed from `request.shop`) to select or scope tenant data — the documented, intended use of this API — can be made to apply a webhook payload under a different shop's identity, or process a replayed payload under a spoofed topic/webhook id. Any actor who can obtain a single legitimately-signed webhook body (an unprivileged event, not requiring the app's `api_secret_key`) can forge the tenant-identifying headers on replay, since the gem's own verification only proves body integrity and never binds `shop`/`topic`/`webhook_id` into the HMAC.

### Likelihood Explanation
High: no secret, token, or privileged access is needed beyond intercepting or generating one valid webhook delivery for any shop app instance (or via a shared/multi-tenant app where an attacker controls one shop and can trigger identical body content, e.g., an `app/uninstalled` or `shop/update` event carrying attacker-controlled fields). Swapping headers on replay is trivial HTTP tampering.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material, or independently verify them (Shopify's real HMAC only covers the body per its documented behavior, but the gem should treat the header-derived shop as untrusted and require the caller to cross-check it against a known/registered shop before acting, similar to how `JwtPayload` binds `aud` to `Context.api_key`). At minimum, document and/or enforce that `WebhookMetadata.shop` must be validated against an existing session/tenant record before any tenant-scoped action is taken, and consider incorporating shop/topic into `to_signable_string` if Shopify's signature scheme supports it.

### Proof of Concept
1. Attacker (an unprivileged Shopify merchant/dev running their own app instance, or anyone who captured one webhook delivery) receives a legitimately Shopify-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same `B`/`H` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes unchanged. [5](#0-4) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the attacker-controlled headers and handed to the app's registered handler, which believes the event came from `victim-shop.myshopify.com`. [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
