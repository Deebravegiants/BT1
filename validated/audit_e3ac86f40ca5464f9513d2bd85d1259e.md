Based on my research, I found a relevant analog in nearcore's `action_delete_account` handling, though I was unable to fully verify the exact behavior of refund receipts landing on non-existent accounts (the search results didn't surface the receiving-side logic in time).

### Title
Self-beneficiary `DeleteAccount` sends refund via a receipt that cannot recreate the deleted account, permanently burning the account's balance - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` pays out the deleted account's remaining balance to `beneficiary_id` via an asynchronous `Receipt::new_balance_refund`, not a synchronous in-place credit. If `beneficiary_id == account_id` (the account deletes itself and names itself as beneficiary — a common no-op-looking usage pattern, analogous to the Unlock `transferFrom(_from == _recipient)` case), the account is fully removed from state (`*account = None`) before the refund receipt is delivered. The explicit code comment states "Refunds don't automatically create accounts, because refunds are free" — meaning when the refund receipt for the now-deleted account arrives, it cannot recreate the account.

### Finding Description
In `action_delete_account` [1](#0-0) , the remaining balance is paid out as a new outgoing refund receipt rather than being merged into an existing account balance synchronously, and then the account record is deleted [2](#0-1) . The code's own comment documents that refund receipts are deliberately barred from triggering implicit account creation: "Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse. Account deletion with beneficiary creates a refund, so it'll not create a new account." [3](#0-2) . This mirrors the Unlock `transferFrom(_from == _recipient)` bug class: an operation that is superficially a "transfer to self" ends up destroying value because of an ordering/identity assumption (delete-then-recreate, or fee-then-expire) that breaks when source and destination coincide.

Existing integration tests exercise the "delete account, beneficiary = self" pattern only for a *named* account being deleted with itself as beneficiary [4](#0-3) , and the `delete_account` helper in the test-user API defaults the beneficiary to the signer/receiver itself [5](#0-4) , showing this is an expected/idiomatic call pattern in the codebase, not just a theoretical edge case a user might stumble into.

### Impact Explanation
If delivering a `Receipt::new_balance_refund` to a self-beneficiary account that was just deleted does not recreate the account (consistent with the code comment that refunds cannot create accounts), the refunded NEAR balance would be permanently lost/burned rather than returned to the user, unless the runtime special-cases this by, e.g., detecting the beneficiary equals the deleting account and crediting synchronously instead of via receipt. I was not able to conclusively trace the receiving-side code path that processes an incoming balance-refund receipt targeting a non-existent account within the available search iterations, so I cannot confirm with certainty whether the funds are actually burned, refunded elsewhere (e.g., to a protocol treasury / `tokens_burnt`), or handled by some other mitigation not surfaced in my searches.

### Likelihood Explanation
Self-beneficiary account deletion (`delete_account(signer_id, signer_id)`) is a directly reachable, unprivileged action from any transaction signer with a `DeleteAccountAction` — no special privileges are required, and it is explicitly exercised as a default pattern in nearcore's own test helpers [5](#0-4) , suggesting this is a realistic, easily-triggered user flow rather than a contrived edge case.

### Recommendation
Verify (and if necessary fix) the handling of `Receipt::new_balance_refund` when the target account was deleted in the same or a related receipt with itself as beneficiary. Confirm whether the refund is silently dropped/burned when it cannot recreate the account. If so, either (a) synchronously credit the beneficiary before finalizing account removal when `beneficiary_id == account_id`, or (b) special-case self-beneficiary deletion to reject it or fold the balance into a transfer that is exempt from the "no implicit account creation on refund" restriction, ensuring users cannot lose funds by naming themselves as the beneficiary of their own account deletion.

### Proof of Concept
1. Create an account `alice.near` with a non-zero balance.
2. Submit `DeleteAccountAction { beneficiary_id: "alice.near" }` signed by `alice.near` (self-beneficiary), exactly as `delete_account(signer_id, signer_id)` does in the test helper [5](#0-4) .
3. `action_delete_account` computes `account_balance = account_ref.amount()`, pushes `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, and then sets `*account = None`, fully removing `alice.near` from state [6](#0-5) .
4. When the refund receipt for `alice.near` is later processed, per the code's own documented invariant that refunds cannot trigger implicit account creation [7](#0-6) , the account cannot be recreated to receive the funds — requiring further verification of exactly where/whether the balance is burned versus recovered by some unseen mechanism.
