### Title
`user_centric_signup` path marks a signup as successfully enrolled without enforcing backend confirmation (duplicate/fraud check) - (File: `src/plans/mod.rs`)

### Summary
Similar to the Connext AAVE-portal finding — where the protocol credits a router's balance immediately and then merely *hopes* the router will complete the out-of-band repayment, without any enforced mechanism tying the credit to the obligation — `MasterPlan::do_signup` in orb-core grants a locally-determined "signup success" state whenever the QR-scanned user data carries `user_centric_signup == true`, without ever enforcing the backend's authoritative confirmation step that the classic path relies on.

### Finding Description
In the normal ("orb-centric") signup path, `do_signup` calls `Self::enroll_user`, which runs `enroll_user::Plan::run` (`src/plans/enroll_user.rs`). That function POSTs the signup to the backend (`signup_post::request`) and then polls `signup_poll::request` in a loop, waiting for the backend to authoritatively confirm the signup — a check that explicitly covers "Backend duplicates," "Backend inflight matches," and "Backend detected fraud" [1](#0-0) .

However, when the user data flags `user_centric_signup = true` (and the orb hasn't been configured to `ignore_user_centric_signups`), `do_signup` skips this entire backend-enforced verification step and instead sets the enrollment status to `Success` purely based on the orb's own local `signup_reason` (i.e., whether the local biometric pipeline ran and whether the orb's local, no-op fraud check flagged anything): [2](#0-1) 

This local `signup_reason` is derived only from whether the pipeline produced output and whether `detect_fraud` returned true — and in this codebase `detect_fraud` is a stub that always returns `false` ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS"): [3](#0-2) 

Crucially, the PCP tier0/tier1/tier2 packages (containing the encrypted iris/face biometric bundle and the identity commitment) are already uploaded to the backend *before* this success/failure branch is evaluated [4](#0-3) , and the resulting `success` flag directly drives `debug_report.signup_successful()`/`signup_server_failure()`, the UI's `signup_success()` feedback, the `dbus::Signup::signup_finished` signal, and (in self-serve mode) the `SignupEnded { success, .. }` message relayed to the user's app [5](#0-4) .

In other words: exactly like the AAVE-portal case where Connext credits the router's balance immediately and trusts the router to later perform the actual out-of-band repayment, orb-core here credits the signup as "Success" to the local state/UI/app immediately and trusts that the app-centric flow will later perform the actual backend-side uniqueness/duplicate/fraud enforcement out-of-band, elsewhere, off the orb's code path. There is no mechanism in this code that ties the "Success" state to a confirmed backend decision for `user_centric_signup` signups.

### Impact Explanation
If the "app-centric" backend-side duplicate/fraud verification that `user_centric_signup` is meant to defer to is not actually completed, delayed, or bypassable, the orb has already reported a definitive local "signup success" and released the associated feedback/state (UI success, dbus signal, relay `SignupEnded(success=true)`) based solely on local pipeline output. This can result in an unauthorized or misattributed signup being reported as successful — e.g., a duplicate person being told/treated as successfully enrolled — even though the authoritative uniqueness/fraud decision was never enforced by this code path, since the orb's own fraud detection is a permanent no-op in this build.

### Likelihood Explanation
This path is reachable whenever the backend-provided `authenticated_app_data.user_centric_signup` flag is `true` for a given signup (default backend/app behavior for "user-centric"/app-centric signups), and `ignore_user_centric_signups` is not set by orb configuration. No malicious operator or hardware access is required — it is a standard code path triggered by ordinary backend-issued user data during normal signup flow.

### Recommendation
Do not locally derive `enrollment_status::Success` for `user_centric_signup` signups from orb-local `signup_reason` alone. Instead, require an explicit, verifiable backend confirmation (analogous to the `signup_post`/`signup_poll` round trip used in the orb-centric path, or a signed acknowledgment scoped to this specific `signup_id`) before setting `debug_report.enrollment_status` to `Success` and before emitting `signup_success()` UI feedback, the `signup_finished` dbus signal, or the `SignupEnded{success:true}` relay message.

### Proof of Concept
1. Backend returns `authenticated_app_data.user_centric_signup = true` for a scanned user QR code (`src/backend/user_status.rs:203-244`).
2. `do_signup` runs the biometric pipeline; `detect_fraud` always returns `false` (`src/plans/mod.rs:1390-1406`), so `signup_reason = SignupReason::Normal` as long as the pipeline produced any output.
3. PCP packages are uploaded to the backend (`src/plans/mod.rs:599-636`).
4. Because `user_centric_signup` is true and `ignore_user_centric_signups` is false, `do_signup` sets `enrollment_status = Success` directly, with no backend confirmation call at all (`src/plans/mod.rs:639-645`).
5. `after_signup` reports this as a successful signup to the UI, dbus, and (if self-serve) the app via relay (`src/plans/mod.rs:1481-1495`) — all before any backend-enforced duplicate/fraud decision has been confirmed by this code path.
