### Title
Webhook Shop Identity Not Bound to HMAC Signature — Cross-Tenant Webhook Forgery via Replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook exclusively by checking the HMAC signature over the raw request body. The `shop` value that the handler ultimately trusts to identify the tenant is read from an HTTP header that is never included in the HMAC-signed bytes. An attacker who obtains one validly-signed webhook (trivially available by installing the app on their own shop) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the host application to process the payload as if it originated from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (computed only over the body) and then hands `request.shop` straight to the handler as the trusted tenant identifier, with no additional check that this header is consistent with the signed payload: [3](#0-2) 

The `HmacValidator.validate` call underneath only ever compares `verifiable_query.to_signable_string` (the raw body) against the HMAC secret: [4](#0-3) 

This breaks the identity binding: `bytes verified (raw_body) != bytes that determine the tenant (shop-domain header)`. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and exposes `data.shop` to the handler as the authoritative shop identity, encouraging apps to key their persistence/business logic directly off `data.shop`: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged internet user can become a valid, uninstalled merchant of the target app (e.g. via a free Shopify development/trial store) and obtain one legitimately-signed webhook payload for their own shop (HMAC computed with the app's shared secret over the raw body). They can then replay this exact body and HMAC to the app's public webhook endpoint while forging the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name any other installed shop. Because the shop identity is not covered by the signature, the host application will process the forged event believing it originated from the victim shop — a direct cross-tenant identity confusion. Depending on the topic registered (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, or any business-critical topic the host handles), this can be used to trigger tenant-scoped side effects (data deletion, state changes, notification spam) attributed to a shop the attacker does not control or own.

### Likelihood Explanation
High. No credentials, access tokens, or `client_secret` are required — only the ability to install the target app on an attacker-controlled shop (a normal, unprivileged onboarding action) and the ability to send an arbitrary HTTP request with the captured body/HMAC and a modified header, both trivially available to any internet client.

### Recommendation
Bind the shop identity to the signed payload. Either:
- Include the `shop-domain` header (and other webhook headers used for routing/dispatch such as `topic`, `webhook-id`) in the HMAC-signable string, or
- Require the host application to independently verify that `data.shop` corresponds to a shop with an active session/installation before trusting it, and document this explicitly as mandatory rather than implying `process` fully "verifies the request."

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and registers for topic `orders/create` (or any topic the app handles).
2. Shopify sends a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H` (e.g., via their own reverse proxy/logging on the webhook endpoint they control).
4. Attacker sends a new POST to the app's webhook URL with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the host app processes attacker-controlled data as an event from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
