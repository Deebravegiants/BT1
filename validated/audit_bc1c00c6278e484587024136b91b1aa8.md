### Title
Webhook shop-domain header is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` verifies binds nothing but the JSON payload bytes. The `shop` (and `topic`/`api_version`/`webhook_id`) values that `Webhooks::Registry.process` treats as the authoritative tenant identity are taken from unauthenticated headers.

### Finding Description
The intended binding should be: `hmac == HMAC(secret, shop || raw_body)` (or some construction that ties the claimed shop to the signed bytes). Instead the actual binding is `hmac == HMAC(secret, raw_body)` while `shop = header["shopify-shop-domain"]`, which is never part of the signed material [5](#0-4) .

`Registry.process` validates the HMAC and, if it passes, immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — none of which were checked against the signed bytes — and hands them to the app's registered handler as trusted values [3](#0-2) .

Because a Shopify app has a single `client_secret`/`api_secret_key` shared across every merchant that installs it, and `HmacValidator` always signs/verifies using that one global secret (`Context.api_secret_key`) regardless of which shop's webhook is being processed [4](#0-3) , a completely unprivileged user can:
1. Install the target app on their own (e.g. free development) store — no special privilege required.
2. Receive a legitimately Shopify-signed webhook for their own store (a valid `raw_body` + `hmac-sha256` header pair, signed with the app's real `api_secret_key`).
3. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but with the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header rewritten to point at a victim shop.
4. `Utils::HmacValidator.validate` still succeeds because it only re-computes `HMAC(secret, raw_body)`, and `Registry.process` dispatches the handler believing the payload came from the victim shop.

This breaks the identity binding `shop authenticated == shop the app acts on`: the HMAC authenticates "this body was really signed by Shopify for *some* shop using this app's secret," but the app trusts it as "this body was signed *for shop X*."

### Impact Explanation
This is a cross-tenant confusion: an attacker who legitimately installs the app on their own shop can make the app process arbitrary attacker-chosen payloads (e.g. `app/uninstalled`, `orders/create`, `customers/data_request`/`customers/redact`/`shop/redact` GDPR topics, etc.) while the app believes they originated from a different merchant's shop. Depending on how the host application's handler uses `shop` (e.g. to look up per-shop session/access tokens, to trigger data deletion, to update per-tenant records), this can lead to cross-tenant data corruption, spoofed GDPR compliance actions against a victim shop, or triggering shop-scoped business logic (uninstall cleanup, resource deletion) against a tenant the attacker doesn't own — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
High feasibility: no secrets, tokens or privileged access are required beyond the trivial act of installing the app on an attacker-controlled shop (something any developer can do for free), which is exactly the class of "unprivileged internet user" scenario in scope. Capturing one's own valid webhook body/HMAC pair and replaying it with a modified header requires only a basic HTTP client.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the signed material verified against the HMAC, or otherwise cryptographically bind the header-derived `shop` value to the request before trusting it — e.g. have `Webhooks::Request#to_signable_string` incorporate `shop`/`topic` (matching Shopify's actual webhook signing scheme if it does so), or independently verify the shop against the session/access-token store for that specific shop before processing, rather than trusting an arbitrary header value once any valid body HMAC is present.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook, e.g.:
raw_body = '{"id":1,"note":"hi"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Attacker replays the same body/hmac but swaps the shop-domain header
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by the HMAC
  "shopify-webhook-id" => "attacker-chosen-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (Utils::HmacValidator only checks raw_body),
#    and the handler is invoked with shop: "victim-shop.myshopify.com"
