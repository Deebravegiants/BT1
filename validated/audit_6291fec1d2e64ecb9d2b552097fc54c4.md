### Title
Read-modify-write race in `ConnectedOrigins#untrust`/`#setAttributes` allows a racing `setAutoApprove` to resurrect a just-untrusted origin with auto-approve enabled - (File: `features/connected-origins/module/connections.js`)

### Summary
`untrust` and `#setAttributes` (used by `setAutoApprove`, `connect`, `disconnect`, `updateConnection`, `setFavorite`) each perform a non-atomic read-modify-write against `connectedOriginsAtom`: they call `#getOrigin`/`#getData` to snapshot the array, compute a new array in memory, then call `#setData` to write it back. There is no locking or compare-and-swap between the read and the write, so two concurrent calls for the same origin can both read the pre-mutation snapshot and then write back in an order where the second `set()` overwrites the first with stale data, silently reinstating a removed/untrusted origin with `autoApprove: true`.

### Finding Description
`untrust({origin})` reads the current list via `#getData()` (`connections.js:187-196`), filters out the target origin, and calls `#setData(newData)`. `setAutoApprove({origin, value})` calls `#setAttributes` (`connections.js:214-216`), which itself independently reads via `#getOrigin`/`#getData` (`connections.js:51-64`), maps the array applying `{ ...connection, autoApprove: value }`, and calls `#setData`. [1](#0-0) [2](#0-1) 

Both operations read `#connectedOriginsAtom.get()` independently rather than through any shared transaction. The underlying atom (`createStorageAtomFactory` wrapped in `enforceObservableRules`) only serializes the execution order of `.set()` calls via `makeConcurrent({ concurrency: 1 })`; it does not perform optimistic-lock/compare-and-swap, and `.get()` is explicitly configured non-concurrent (`makeGetNonConcurrent: true`) so it can run interleaved with any pending write, returning whatever the last completed write produced, not a value that accounts for as-yet-unstarted queued writes. [3](#0-2) [4](#0-3) 

Exploitable interleaving:
1. `untrust(origin)` reads the full array (origin present, trusted).
2. `setAutoApprove(origin, true)` (via `#setAttributes`) reads the same full array before either write has landed.
3. `untrust` calls `#setData(dataWithoutOrigin)` -> `connectedOriginsAtom.set(...)` executes first (queue empty).
4. `setAutoApprove`'s `#setData(dataWithOriginAutoApproveTrue)` -> `connectedOriginsAtom.set(...)` is queued next and executes after step 3, since it was computed from the pre-removal snapshot it still contains the origin entry, now with `autoApprove: true`, and overwrites the just-removed state.

Result: the origin that was supposedly untrusted (removed) reappears in storage with `autoApprove: true`, i.e. auto-approve signing privilege persists/is granted despite an intervening untrust. No check in `#setAttributes` (`if (!item) return`, line 54) protects against this, because at the time of the check the item still existed in the stale snapshot — the check only guards against acting on an origin that never existed, not against a concurrently-removed one. [5](#0-4) 

### Impact Explanation
If `setAutoApprove`/`connect`/`disconnect`/`updateConnection` calls can be driven back-to-back with an `untrust` call for the same origin (e.g. via rapid origin connect/disconnect/approve UI or extension messaging flows), the wallet can end up persisting an `autoApprove: true` record for an origin the user just revoked trust from. Since `isAutoApprove`/`isTrusted` are read directly from this persisted record and gate whether a dapp origin can sign without further user approval, this is a privilege-persistence bug: a supposedly disconnected/untrusted origin can retain (or regain) the ability to auto-sign transactions without explicit user consent, violating the stated invariant that "consent must be explicit and cannot be reinstated by a race."

### Likelihood Explanation
Exploitability requires triggering two of these module calls concurrently for the same origin so that both reads happen before either write completes — feasible because none of `untrust`, `#setAttributes`, `#getOrigin`, `#getData` introduce any locking, and the write queue (`makeConcurrent`) only affects execution order of `set()`, not consistency of the data being set. This is a genuine unguarded TOCTOU window purely from ordinary application logic (no privileged access required); the practical trigger depends on the host app's UI/message-handling actually invoking two such operations concurrently for the same origin (e.g. rapid successive dapp requests/UI actions), which is plausible in an event-driven extension/background-script architecture but not proven end-to-end from a remote dapp message handler in the code inspected.

### Recommendation
Serialize all read-modify-write sequences per origin (or globally) through the same concurrency primitive already used for atom writes — e.g., wrap `#getOrigin` -> mutate -> `#setData` in a single `makeConcurrent` critical section keyed on the module instance (or origin), or switch `#setAttributes`/`untrust` to use an atomic "setter" style (`connectedOriginsAtom.set((current) => ...)`) so the read and the corresponding write are guaranteed to operate on the same/latest snapshot, similar to the setter pattern already supported by `enforceObservableRules`'s `set` (`isSetter` handling, `enforce-rules.ts:96-105`). Reject stale writes (e.g., via version/CAS check) if full serialization is not desired for performance.

### Proof of Concept
Integration test using the in-memory atom test harness already present in `features/connected-origins/module/__tests__/connections.test.js`:
1. Seed `connectedOriginsAtom` with one trusted origin, `autoApprove: false`.
2. Stub/spy `#getData`/`connectedOriginsAtom.get` (or use `pDefer` to control resolution order, as done in `libraries/atoms/__tests__/index.test.ts`) so that:
   - `untrust({origin})`'s internal read resolves first (data with origin present).
   - `setAutoApprove({origin, value:true})`'s internal read is deferred to also resolve on the stale snapshot.
3. Call `connectedOrigins.untrust({origin})` and `connectedOrigins.setAutoApprove({origin, value:true})` without awaiting either individually; control resolution so `untrust`'s `#setData` write completes before `setAutoApprove`'s write is invoked.
4. `await Promise.all([...])`.
5. Assert final state: `await connectedOrigins.isTrusted({origin})` should be `false` and the origin should be absent from `connectedOriginsAtom.get()`; if the race is exploitable, the test instead observes the origin reinstated with `autoApprove: true` — this failing assertion is the proof of the race.
