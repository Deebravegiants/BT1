### Title
Global `challengePeriod` reduction via `updateHostParams` retroactively shrinks the fraud-proof/veto window for already-pending state commitments - ([File: evm/src/core/EvmHost.sol])

### Summary
The reported Perennial bug is that a vault upgrade can change `targetLeverage`/`maxCollateral` to values inconsistent with already-open positions created under the old parameters, with no check that the new values remain compatible with existing state, causing a mass liquidation. The structural analog in Hyperbridge is `EvmHost.updateHostParams`, which lets governance change `_hostParams.challengePeriod` at any time with no check against state commitments that are already stored and mid-flight in their (old) challenge/veto window. Because `HandlerV2` always reads the *current* `challengePeriod()` rather than the period that was in effect when a given state commitment was received, lowering the parameter retroactively shrinks (or eliminates) the safety window fishermen rely on to veto a fraudulent/erroneous state commitment that was submitted moments before the parameter change.

### Finding Description
`EvmHost.updateHostParams` / `updateHostParamsInternal` validates only structural invariants (non-zero addresses, correct interfaces, non-empty hyperbridge id, `unStakingPeriod >= 1 day`, fee-token balance draining) before overwriting `_hostParams.challengePeriod` unconditionally: [1](#0-0) 

`challengePeriod()` simply returns the current live value: [2](#0-1) 

State commitments are stored with only an update timestamp, independent of whatever challenge period applied at the time they were written: [3](#0-2) 

All of the delivery entrypoints in `HandlerV2` gate on `delay > challengePeriod`, where `delay = block.timestamp - stateMachineCommitmentUpdateTime(height)` and `challengePeriod` is fetched live at call time, not the value that was active when the commitment landed: [4](#0-3) [5](#0-4) 

The fisherman veto mechanism (`deleteStateMachineCommitmentInternal`) is the only defense against a bad/fraudulent state commitment during its challenge window, and it depends on fishermen having time — bounded by `challengePeriod` — to observe and veto before a relayer can act on it: [6](#0-5) 

Because the parameter change is not scoped to newly-created commitments, any commitment already stored under the old (longer) challenge period has its remaining safety margin retroactively recomputed against the new (shorter) value the instant `updateHostParams` executes. There is no analog of the Perennial fix's "must not regress below previous value / must remain consistent with existing open state" check — `challengePeriod` (and other host params like `unStakingPeriod`, which gates staking/unbonding rather than the challenge window) can move from any value to any smaller value in one governance call, exactly mirroring `targetLeverage`/`maxCollateral` being lowered under already-open Perennial vault positions.

### Impact Explanation
If a state commitment submitted by a compromised/malicious consensus-proof relayer is sitting in its challenge window (already accepted by `storeStateMachineCommitment` but not yet vetoed), a subsequent, otherwise-legitimate `updateHostParams` call that lowers `challengePeriod` immediately makes that commitment deliverable via `handlePostRequests`/`handleGetResponses`/timeout handlers before fishermen who were relying on the old, longer window have had the chance to detect and veto it. This can result in forged/fraudulent message delivery being processed and dispatched to destination `IsmpModule`s (unauthorized app actions, unbacked mint on token-bridge style receivers, or other state corruption) — a concrete instance of "forged message delivery" and "unsound state commitment" acceptance, the exact class the audit rules call out as valid impact.

### Likelihood Explanation
`updateHostParams` is routine, expected governance functionality (parameter tuning is a normal operational action, not solely a malicious-governance scenario — analogous to the Perennial vault owner performing a routine upgrade). The vulnerability requires no attacker privilege beyond normal relaying: an attacker only needs to get a state commitment accepted (e.g., during a period where a compromised committee member/relayer is submitting consensus proofs) and then have any parameter-tuning `updateHostParams` call land while that commitment is still within its original challenge window. Because the check compares against the *current* global value rather than a per-commitment snapshot, this is a structural gap that fires on any legitimate reduction of `challengePeriod`, not only an intentionally malicious one.

### Recommendation
Snapshot the challenge period applicable to each state commitment at the time it is stored (e.g., record `challengePeriodAtUpdate` alongside `_stateCommitmentsUpdateTime`), and have `HandlerV2` compare `delay` against that stored value rather than the live `hostParams.challengePeriod()`. Alternatively, disallow reducing `challengePeriod` for a state machine while any of its stored-but-not-yet-elapsed commitments would be affected, or require that any reduction only apply to commitments stored after the update — mirroring the recommended fix in the source report of validating new parameters against the currently live/open state rather than accepting an unconstrained overwrite.

### Proof of Concept
1. Governance/relayer submits a consensus proof accepted by `ConsensusRouter`/`HandlerV2.handleConsensus`, which calls `host.storeStateMachineCommitment(height, commitment)`, recording `_stateCommitmentsUpdateTime[stateMachineId][height] = block.timestamp` under the currently configured `challengePeriod = T1` (e.g., 24 hours) — [3](#0-2) .
2. Before `T1` elapses and before any fisherman calls `deleteStateMachineCommitment` to veto it, a `SetHostParam` governance action is delivered through `HostManager.onAccept` → `EvmHost.updateHostParams`, setting `challengePeriod = T2` where `T2 << T1` (e.g., 1 minute) — [7](#0-6)  and [8](#0-7) .
3. A relayer immediately calls `handlePostRequests` (or `handleGetResponses`) with a proof against that same `height`. `delay = block.timestamp - stateMachineCommitmentUpdateTime(height)` now only needs to exceed `T2`, which it already does, so `challengePeriod > delay` is false and the check passes — [9](#0-8) .
4. The request/response is dispatched to the destination module via `host.dispatchIncoming` before any fisherman veto (which was still expected to have up to `T1` to occur) can be exercised, permanently accepting state that was never fully vetted within its originally-promised safety window.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
