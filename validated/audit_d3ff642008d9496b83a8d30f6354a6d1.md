### Title
Borrower plants an unpriceable Aquarius-LP dust collateral leg and drains the LP pool below `min_pool_value_wad` to permanently block liquidation and bad-debt cleanup of their underwater account - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
`supply` accepts a new collateral leg without requiring a valid price, while `liquidate` and `clean_bad_debt` re-price *every* supply leg of the target account. A borrower can supply a dust amount of a listed Aquarius LP share token as collateral, then withdraw their own liquidity from that Aquarius pool so its value falls below `min_pool_value_wad`. From that point the LP price read fails with `InsufficientAquariusLiquidity`, and every liquidation and every permissionless bad-debt cleanup of the account reverts — the attacker can keep their underwater debt accruing interest indefinitely, turning the account into unremovable bad debt.

### Finding Description
The root cause is an asymmetry between entry and exit pricing:

- `process_supply` (`contracts/controller/src/positions/supply.rs:40-74`) deposits collateral and calls `finalize_position_flow` without requiring a fresh price for the supplied asset — confirmed by the harness test where supplying WBTC succeeds while its feed is deliberately stale (`tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs:26-30`).
- `socialize_bad_debt` (`contracts/controller/src/positions/liquidation/mod.rs:212-238`) calls `risk::calculate_account_risk_totals` over `account.supply_positions`, and liquidation planning does the same — a single leg whose price read errors aborts the whole call. The test proves both `liquidate` and `clean_bad_debt` revert with `PRICE_FEED_STALE`/`InsufficientAquariusLiquidity` while one leg is unpriceable, and succeed again once it recovers (`audit_liquidate_and_clean_stale_leg.rs:36-47`).
- For `PriceSource::AquariusLp`/`AquariusStableLp` collateral, the read in `aquarius::read` returns `Err(OracleError::InsufficientAquariusLiquidity)` whenever `pool_value_wad < lp.min_pool_value_wad` (`contracts/price-aggregator/src/providers/aquarius.rs:118-122`). Pool value is computed from live reserves and total shares (`aquarius.rs:90-119`), so any liquidity provider of that pool — including the attacker — can force the error by withdrawing their liquidity, no oracle compromise needed.
- `require_third_party_existing_supply` restricts third parties to topping up existing positions, so this cannot be used to brick a *victim's* account — but the borrower plants the leg on their own account, which is all that is needed to shield their own debt.

### Impact Explanation
Temporary freezing of funds trending toward protocol insolvency. While the shield is active:

1. No liquidator can touch the account regardless of how deep below HF = 1 it falls — interest keeps accruing at up to the borrow-index cap while collateral stays frozen.
2. `clean_bad_debt` reverts on the same price read, so even once the account is insolvent and under the $5-equivalent dust gate it cannot be socialized permissionlessly.
3. `force_socialize_bad_debt` also runs `calculate_account_risk_totals`, so the governance runbook path is blocked too until the pool is refilled — which the attacker controls (they can even re-add liquidity to momentarily unblock, withdraw again, repeatedly).

The debt is never collectible while shielded, and the accrued interest is real loss socialized onto suppliers via the supply-index write-down when the account is eventually cleaned. Cost to the attacker is only a dust LP position plus temporarily parking liquidity out of one pool.

### Likelihood Explanation
High reachability, moderate precondition. All steps are unprivileged entrypoints in scope: `supply` (own account, any listed asset, no price needed), Aquarius pool `withdraw_liquidity` (own LP position), and the attacker merely needs to have borrowed before going underwater — which happens naturally in any price drawdown or can be engineered. The constraint is that at least one listed collateral must be an Aquarius LP token whose pool the attacker can drain below `min_pool_value_wad`; thin pools with a meaningful `min_pool_value_wad` make this cheap. The threat model explicitly acknowledges the primitive (`DoS.1`: "an indebted borrower can add a dust leg … liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`"), so this is a real acknowledged shape rather than a hypothetical — it is reported here because the attacker-induced LP drain variant is an active, unprivileged action rather than passive oracle downtime.

### Recommendation
- Make risk-total computation tolerant of unpriceable supply legs: treat a leg whose oracle read fails as zero-value collateral for liquidation/cleanup gating (it contributes nothing to the borrower's health anyway), rather than aborting the entire call. Alternatively compute risk per leg and skip legs with `Err` reads.
- Alternatively, require a valid fresh price at `supply` time for any new supply position (not just top-ups), so a fragile leg cannot be planted for free.
- For Aquarius LP sources, consider pricing via the deeper of the configured sources or caching the last good LP fair value with a decay bound, so a transient liquidity dip cannot unilaterally mute the leg.
- At minimum, make `clean_bad_debt` skip unpriceable collateral legs (seize only what can be valued) so the permissionless insolvency path is never hostage to one feed.

### Proof of Concept
1. Deploy markets with an Aquarius LP token `LPX` listed as collateral, priced by `PriceSource::AquariusLp` with `min_pool_value_wad = V`. Attacker holds LPX liquidity in that pool.
2. Attacker calls `supply(attacker, 0, spoke, [USDC])` creating an account, then `borrow(attacker, id, [ETH])` near max LTV.
3. Attacker calls `supply(attacker, id, spoke, [LPX: dust_amount])` — succeeds despite anything, since supply needs no price.
4. Attacker withdraws their liquidity from the Aquarius pool so `fair_lp_price * total_shares / 10^dec < V`. `aquarius::read` now returns `InsufficientAquariusLiquidity` for LPX.
5. Price moves / accrual push the account below HF = 1. Any liquidator calling `liquidate` reverts (risk totals hit the failed LPX read); any caller of `clean_bad_debt` reverts identically.
6. Debt accrues unbounded; eventual cleanup (if ever unblocked) writes a larger loss down against supplier indexes.

The existing test `audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg` (`tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs`) reproduces steps 3–5 mechanically with a stale feed; substituting the Aquarius `min_pool_value_wad` drain makes the outage attacker-controlled rather than exogenous.
