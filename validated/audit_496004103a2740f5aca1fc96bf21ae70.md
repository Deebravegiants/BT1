The reported issue is fundamentally an EVM concept: Solidity's `msg.value` and Uniswap V2's separate `swapExactETHForTokens`/`swapExactTokensForTokens` code paths depending on whether native ETH or an ERC20 is being swapped. Solana programs have no analogous concept — there is no `msg.value` and no implicit native-currency call path that a program must branch on.

In this codebase, all swaps (`process_swap_base_in`, `process_swap_base_out`, `process_swap_base_in_v2`, `process_swap_base_out_v2`) operate exclusively through explicit SPL token accounts passed in the instruction, with transfers executed via `Invokers::token_transfer` / `Invokers::token_transfer_with_authority` CPIs to the SPL Token program [1](#0-0) . Native SOL support is handled uniformly by using a wrapped-SOL (WSOL) SPL token account like any other mint — the same instruction and account layout is used regardless of whether the underlying asset is native SOL or another token, and there is no separate "value" field or alternate call path that could be bypassed or mismatched [2](#0-1) .

The only place native lamports are handled specially is `withdraw_excess_lamports_from_token`, which uses `sync_native`/`UnwrapLamports` to reconcile WSOL token account lamports with their token amount — this is unrelated to swap routing or msgValue-style decisions and is not reachable by an unprivileged swapper as part of a swap instruction [3](#0-2) .

Since Solana's account-based, explicit-CPI model has no equivalent "native value vs. token routing" ambiguity that this bug class exploits, there is no valid analog reachable via `Initialize2`, `Deposit`, `Withdraw`, or the swap instructions in this program.
