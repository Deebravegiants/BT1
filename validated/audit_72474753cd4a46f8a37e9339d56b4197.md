## Analog Found [1](#0-0) 

### Title
BSC light client accepts finality votes one validator short of the true 2/3+1 BFT supermajority, enabling forged state commitments - (File: modules/consensus/bsc/verifier/src/lib.rs)

### Summary
The `verify_bsc_header` function in the BSC (Parlia) consensus verifier checks vote-set participation with `participant_count < ((2 * current_validators.len()) / 3)` as the *rejection* condition, meaning it *accepts* any `participant_count >= (2*n)/3` (integer floor division). This is off by one vote relative to BSC's actual BEP-126 fast-finality rule and relative to every other quorum check in the same codebase, which all require `>= ((2*n)/3) + 1`.

### Finding Description
The function documents itself as needing "the same threshold specified in the bsc parlia consensus which is 2/3" [2](#0-1)  and implements:

```
if participant_count < ((2 * current_validators.len()) / 3) {
    Err(Error::NotEnoughParticipants)?
}
``` [3](#0-2) 

For `n = 21` validators (the BSC testnet shape used in this repo's own tests), `(2*21)/3 = 14`, so the check accepts `participant_count >= 14`. The project's own test explicitly documents this as the intended behavior: "10 of 21 bits set (threshold is 14)" [4](#0-3) .

This contradicts:
1. The project's own documentation of Parlia/BEP-126, which states the requirement is "more than two-thirds ... Additionally, at least one more unique validator needs to participate to reach the required threshold of (2/3 * N) + 1 votes" [5](#0-4) .
2. Every other supermajority check implemented elsewhere in this same codebase for other consensus clients, all of which correctly require `>= (2*total)/3 + 1`:
   - BEEFY: `len >= ((2 * total) / 3) + 1` [6](#0-5) 
   - Sync-committee: `sync_aggregate_participants < ((2 * committee_size as u64) / 3) + 1` (rejected below this) [7](#0-6) 
   - Pharos: `required = (total_stake * 2 / 3) + 1` [8](#0-7) 

For a true BFT quorum with `n=21` and fault tolerance `f = floor((n-1)/3) = 6`, the honest-majority quorum is `n - f = 15`, not `14`. The current check therefore under-counts the required quorum by exactly one validator, mirroring the Lido `MAX_MEMBERS` off-by-one class of bug: the threshold check accepts one fewer participant than the protocol actually requires.

### Impact Explanation
An attacker (or colluding minority) controlling only `14` of `21` BSC validators — a set that does **not** meet BSC's own consensus-defined "more than 2/3" supermajority — can produce a `BscClientUpdate` that passes `verify_bsc_header` in the `ismp-bsc` client. Since this verifier finalizes `source_header`'s state commitment (`VerificationResult.finalized_header`) which is subsequently trusted by Hyperbridge for cross-chain state and event proofs, an attacker meeting only the weaker 14/21 threshold could get an unsound state commitment accepted by the light client, enabling forged message delivery / unauthorized state proofs for cross-chain messages routed through the BSC state machine. This is an unsound state commitment vulnerability reachable purely by submitting a relayed consensus proof — no privileged role required.

### Likelihood Explanation
Reaching this code path only requires submitting a `BscClientUpdate` via the standard consensus update path exposed to any relayer of BSC consensus messages; no admin or governance privilege is needed. The gap between the required "true" quorum (15/21) and the accepted quorum (14/21) is narrow but concrete and exactly reproducible per the project's own test comments.

### Recommendation
Correct the check to match BSC's actual quorum requirement and the pattern used by every other consensus verifier in this codebase:
```rust
if participant_count < ((2 * current_validators.len()) / 3) + 1 {
    Err(Error::NotEnoughParticipants)?
}
```

### Proof of Concept
Using the repo's own test harness (`dummy_validators(21)`), construct a vote bit-set with exactly 14 of 21 bits set (`mask: u64 = (1u64 << 14) - 1`). Per the current code, `verify_bsc_header` passes the participation check (`14 >= (2*21)/3 = 14`), even though BSC's actual quorum for `n=21` is `15`. This is directly analogous to the existing `rejects_too_few_in_range_participants` test [9](#0-8) , except with `14` bits instead of `10`, demonstrating the verifier lets a sub-quorum set of validators pass the supermajority gate.
