### Title
Unauthenticated `CallDispatcher.dispatch` allows anyone to drain any native ETH/ERC20 balance held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch` is the direct analog of the reported `SbFunction.forward` bug: it performs an external, low-level `.call{value: call.value}(call.data)` to a caller-controlled `to` address using a caller-controlled `value`, with **no access control whatsoever** on the entry point and no check that the funds being forwarded actually belong to, or were intended for, the caller.

### Finding Description
`CallDispatcher.dispatch` decodes an arbitrary `Call[]` array and executes each entry with `to.call{value: call.value}(call.data)`: [1](#0-0) 

There is no `onlyOwner`, `onlyGateway`, or `msg.sender` check of any kind — the function is `external` with zero modifiers, exactly like the vulnerable `SbFunction.forward` which allowed `transaction.value` to be forwarded to an arbitrary `transaction.to` without validating that the caller was entitled to spend that value. The `ICallDispatcher` interface confirms the entry point takes only opaque encoded bytes with no authorization parameter: [2](#0-1) 

The `CallDispatcher` is a **shared, reusable singleton** wired into multiple production apps as `_params.dispatcher` / `_dispatcher`: `IntentGatewayV2` (predispatch/postdispatch swap flows), `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken` (`onAccept` calldata execution), and `BridgeToken`. In all of these flows, the pattern is: (1) transfer native ETH or ERC20 tokens into the dispatcher, (2) call `ICallDispatcher(dispatcher).dispatch(...)` to run the batch, (3) sweep the resulting balance back out.

Example from `IntentGatewayV2.placeOrder`, native tokens are pushed to the dispatcher before `dispatch` is invoked: [3](#0-2) 

And from `HyperFungibleTokenUpgradeable.onAccept`, arbitrary attacker/message-controlled calldata is routed straight through the dispatcher: [4](#0-3) 

Because `dispatch()` itself is completely unauthenticated, **any unprivileged actor can call `CallDispatcher.dispatch` directly**, independent of the orchestrating app (`IntentGatewayV2`, HFT, WHFT, BridgeToken). Whatever native ETH or ERC20 balance the dispatcher happens to be holding at that moment — even momentarily, e.g., ETH sent via its permissive `receive()` — can be redirected to an arbitrary `to`/`value` chosen by the attacker: [5](#0-4) 

This mirrors the root cause described in the report: an externally reachable function performs a value-carrying external call using caller-supplied parameters without verifying the caller's entitlement to those funds, and the fix pattern described (zero out/guard the call value / gate the caller) is exactly what is missing here.

### Impact Explanation
Since the same `CallDispatcher` instance is deployed once and shared across every app that needs "swap-then-escrow" / "fill-then-act" composability (`IntentGatewayV2`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, `BridgeToken`), any native token or ERC20 balance that transiently sits in the dispatcher — whether from a legitimate in-flight order, a stuck/partial sweep, or funds mistakenly sent to its permissive `receive()` — is fully and immediately stealable by any address on-chain, with no relationship to the app that deposited the funds. This is a concrete theft-of-funds vector reachable from a single unprivileged transaction, consistent with the "Unchecked Fund Provision" bug class in the reference report.

### Likelihood Explanation
Likelihood is high in principle because the vulnerable function is public, requires no privilege, and no proof/signature/ownership check gates it — any address can call it in any block. The practical exploitability depends on whether the dispatcher's balance is reliably zero between the deposit step and the `dispatch()` call within the same transaction across all call sites (the code I reviewed shows deposit-then-dispatch-then-sweep occurring within single transactions in the flows examined, e.g. `IntentGatewayV2.placeOrder`/`IntentsBase._execute`). I was not able to fully verify, given tool-call limits, whether every code path (in particular `IntrinsicIntents.sol`/`fillOrder`, and `BridgeToken`) guarantees strict atomicity between funding the dispatcher and invoking `dispatch`, or whether any path leaves a non-atomic window (e.g., cross-transaction dust, a reentrant callback within `order.predispatch.call`/`order.output.call`, or a failed sweep) during which the dispatcher holds a drainable balance. That gap is exactly what an unrestricted `dispatch()` turns into a theft primitive regardless of how the balance got there — the missing access control is the root cause, independent of which specific call site creates the exposure window.

### Recommendation
Restrict `CallDispatcher.dispatch` to be callable only by an authorized/registered caller (e.g., an allow-listed set of app contracts configured at deploy/registration time), analogous to the `SbFunction.forward` fix pattern of removing the ability for unauthorized parties to direct value transfers. At minimum, add an `onlyAuthorized`/`onlyOwner`-style modifier so arbitrary external accounts cannot invoke `dispatch()` directly, and consider adding a reentrancy guard and/or ensuring the dispatcher never holds a non-zero balance outside of a single atomic call sequence.

### Proof of Concept
1. Observe/wait for any transaction where `CallDispatcher` transiently holds native ETH or ERC20 tokens (e.g., mid-`placeOrder`/`fillOrder` predispatch/postdispatch flow, or ETH sent directly via its permissive `receive()`).
2. As any unprivileged address, call `CallDispatcher.dispatch(encodedCalls)` directly (not through `IntentGatewayV2`/HFT/BridgeToken), with `encodedCalls` decoding to a `Call[]` where `to = attacker-controlled-contract` (must have code, per `extcodesize` check) and `value = address(callDispatcher).balance`.
3. The `to.call{value: call.value}(call.data)` in `CallDispatcher.dispatch` (evm/src/utils/CallDispatcher.sol:59) unconditionally forwards the dispatcher's balance to the attacker's contract, with no check that the caller is `IntentGatewayV2`, the HFT contracts, or `BridgeToken`, and no check that the value being sent was ever earmarked for this caller.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```
