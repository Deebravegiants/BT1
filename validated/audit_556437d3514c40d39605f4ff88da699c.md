### Title
Permanent freezing of relayer fees and timeout-callback state when a request's `payer` is blacklisted on the `feeToken` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchTimeOut()` (both the `GetRequestTimeout` and `PostRequestTimeout` variants) refunds the relayer fee to `meta.sender` — the arbitrary `payer` address recorded at dispatch time — via an unguarded `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`. If `feeToken()` is a blacklist-capable stablecoin (e.g. USDC) and `meta.sender` is later blacklisted, this transfer reverts unconditionally and permanently, exactly as in the reported Blueberry `doRefund()`/`bank.EXECUTOR()` pattern where a fixed, unprivileged recipient address becoming blacklisted freezes an entire flow.

### Finding Description
`dispatchTimeOut` first calls the source module's `onGetTimeout`/`onPostRequestTimeout` callback, and only after that succeeds does it perform the fee refund: [1](#0-0) 

```solidity
function dispatchTimeOut(GetRequestTimeout memory timeout, FeeMetadata memory meta, bytes32 commitment)
    external restrict(_hostParams.handler)
{
    delete _requestCommitments[commitment];
    (bool success,) = _bytesToAddress(timeout.request.from)
        .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));
    if (!success) { _requestCommitments[commitment] = meta; return; }
    if (meta.fee != 0) {
        IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
    }
    ...
}
```

The same pattern applies to the `PostRequestTimeout` overload: [2](#0-1) 

`meta.sender` is the `payer` address that any unprivileged dispatcher supplies when calling `dispatch()` on the source chain — it is fully attacker/user controlled and not validated: [3](#0-2) 

`HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` invoke `host.dispatchTimeOut(...)` directly inside a loop, with no `try/catch`, so any revert propagates and aborts the whole batch: [4](#0-3) 

The same unguarded-transfer-to-arbitrary-address pattern also exists in `dispatchIncoming(GetResponse, address relayer)`, which pays the relayer fee to `relayer` (the caller of `handleGetResponses`, itself permissionless) with no try/catch: [5](#0-4) 

If `meta.sender` (the payer) or `relayer` becomes blacklisted on `feeToken()`, every future attempt to process that timeout/response reverts, because:
1. The successful module callback and the fee transfer happen in the same atomic call — there's no way to separate them.
2. `HandlerV2` calls `dispatchIncoming`/`dispatchTimeOut` without a try/catch, so a revert in the fee transfer reverts the entire batched `handlePostRequestTimeouts`/`handleGetRequestTimeouts`/`handleGetResponses` transaction, including the state changes and callback execution for that item (and, when batched, for every other unrelated item in the same call).
3. Retrying the same message will hit the identical revert forever, since the blacklist status doesn't change — the request/response can never be finalized.

### Impact Explanation
This permanently freezes the relayer's earned fee (for `dispatchIncoming(GetResponse,...)`) or the payer's refunded relayer fee (for both `dispatchTimeOut` variants) in the `EvmHost` contract with no recovery path. Worse, because the module callback (`onGetTimeout`/`onPostRequestTimeout`/`onGetResponse`) is bundled atomically with the transfer, the destination application's corresponding state transition (e.g., releasing escrow, unlocking user funds, cleaning up dependent state) can never be delivered either — the message becomes permanently stuck and undeliverable. This satisfies the "permanent freezing of funds" / "route unable to deliver messages" bar, since a single unprivileged party (dispatcher choosing their own `payer`, or a relayer who happens to submit the proof) can be blacklisted by the stablecoin issuer for unrelated reasons and this then blocks/freezes funds and message delivery that other, unrelated users depend on when batched together.

### Likelihood Explanation
`feeToken()` is documented as "usually a stablecoin" like USDC/DAI, which are known to implement issuer-controlled blacklists. `meta.sender`/`relayer` are unprivileged, freely chosen addresses (any dispatcher sets their own `payer`; any address can become the relaying `_msgSender()`). No governance action or malicious insider is required — an address simply needs to be sanctioned/blacklisted by the token issuer at any point after dispatch, which is a realistic real-world event (as already demonstrated on USDC).

### Recommendation
Decouple the module callback from the fee transfer failure: wrap `IERC20(feeToken()).safeTransfer(...)` in a try/catch (or use a pull-based accounting model where fees are credited to an internal balance mapping and withdrawn separately) so that a reverting transfer to a blacklisted `meta.sender`/`relayer` cannot block delivery of the callback or of other batched messages. At minimum, execute `dispatchIncoming`/`dispatchTimeOut` calls inside `HandlerV2`'s loops via low-level `call` wrapped so a single item's failure doesn't revert the whole batch, matching the pattern already used for `dispatchIncoming(PostRequest,...)`.

### Proof of Concept
1. User A dispatches a `PostRequest`/`GetRequest` from chain X with `payer = A` and a non-zero relayer `fee` paid in `feeToken()` (e.g. USDC).
2. Some time later, `A`'s address is added to the USDC blacklist (independently of this protocol).
3. The request times out; a relayer submits a valid timeout proof via `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts`.
4. `EvmHost.dispatchTimeOut` executes the module callback successfully, then calls `IERC20(feeToken()).safeTransfer(A, meta.fee)`, which reverts because `A` is blacklisted.
5. The entire `handlePostRequestTimeouts` transaction reverts, including the callback's side effects and any other timeouts batched in the same call.
6. Every subsequent retry hits the same revert — `A`'s relayer fee is permanently frozen in `EvmHost`, and the destination application never receives the timeout notification, permanently freezing any funds/state gated on that callback.
