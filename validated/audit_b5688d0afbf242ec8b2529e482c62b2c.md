This confirms the vulnerability: the documentation explicitly states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and the handler is told it can trust `data.shop` as "The shop domain of the webhook" [2](#0-1) . This is the gem's own documented guarantee, which the implementation breaks.

### Title
Webhook HMAC signature does not cover the `shop-domain` header, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers [4](#0-3) . `Registry.process` validates the HMAC over that signable string only [5](#0-4) , then passes `request.shop` straight into `WebhookMetadata` as the tenant identifier used by the app's handler [6](#0-5) . This exactly matches the report's bug class: a field (`shop`) is acted upon but is not covered by the cryptographic binding (the HMAC) that is supposed to authenticate the request.

### Finding Description
The identity binding that should hold is:
`shop asserted by request.shop` == `shop that produced the signed body via Context.api_secret_key`

This equality is never checked. `HmacValidator.validate` only proves that `Context.api_secret_key` (or `old_api_secret_key`) was used to sign `@raw_body` [7](#0-6) . Since every shop that installs the app uses the *same* app-wide `api_secret_key` (this is a single-tenant secret per app, shared across all merchant shops that install it), any user who installs the app on their own (even free/dev) shop will receive genuine webhooks with valid HMACs computed over bodies they fully control the timing/format of. Because the HMAC signable string never includes the `shop-domain` header, that exact `(raw_body, hmac)` pair remains valid no matter what `shop-domain` header value is sent alongside it.

An attacker who has installed the app on Shop A can:
1. Trigger a webhook (e.g. `orders/create`) to be delivered to the app's public webhook endpoint with attacker-controlled body content, and capture the resulting `(raw_body, hmac)` pair (both attacker-visible, since it's their own shop/webhook).
2. Replay the same `raw_body` + `hmac` to the app's shared webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop B's domain.
3. `HmacValidator.validate` still succeeds (it only checks body vs. secret) [5](#0-4) , and `Registry.process` calls the handler with `shop: request.shop` == shop B, `body: request.parsed_body` == attacker's chosen content [6](#0-5) .

The app's handler, per the gem's own documented contract, has no way to know this is spoofed — it is told the request is verified to "have indeed come from Shopify" for the given `shop` [1](#0-0) .

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a user who legitimately controls their own shop's install can inject attacker-controlled webhook bodies attributed to any other merchant shop that also uses the app, as long as they can guess/know that shop's `myshopify` domain (which is often public/guessable, e.g. via storefront). Depending on what the handler does with `data.shop` + `data.body` (e.g., updating cached order/customer data keyed by shop, triggering per-shop side effects, invalidating sessions, syncing inventory), this allows one merchant to inject falsified data into another merchant's tenant context — a cross-tenant integrity/confidentiality violation, matching the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is bounded by the fact that the app's own webhook secret (`api_secret_key`) is shared across all installs of the app, and any unprivileged internet user can install the app on their own shop to legitimately obtain valid `(body, hmac)` pairs, then replay them with a forged `shop-domain` header value to the shared endpoint — no interception, credentials, or privileged access to the victim's data is required. The only extra requirement is knowledge of the target shop's `.myshopify.com` domain, which is commonly public.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values inside the string that is HMAC-verified, or otherwise cryptographically bind them (e.g., derive a canonical string from all headers + body before computing/verifying the HMAC), matching what `AuthQuery#to_signable_string` already does for OAuth callbacks [8](#0-7) . At minimum, document prominently that `data.shop` is not authenticated by the HMAC and that consuming applications must independently verify it belongs to a shop with an active installation before trusting it.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and triggers/receives a genuine webhook, capturing:
raw_body = '{"id":123,"note":"hello"}'
hmac     = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body))
# (api_secret_key is shared for the whole app across all installs)

# Attacker replays it against the app's public webhook endpoint,
# forging the shop-domain header to point at a victim shop:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, unverified
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (body+secret matched);
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...}))
# The app now believes attacker-controlled data came authentically from victim-shop.
