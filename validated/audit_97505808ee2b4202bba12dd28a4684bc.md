Audit Report

## Title
Improper suffix-only wildcard host matching in gateway CORS `Origin` allowlist enables cross-origin bypass - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway's CORS wildcard origin match (`*.example.com`) uses `strings.HasSuffix` without verifying a preceding `.` (domain-label boundary), so any attacker-controlled domain ending in the same characters (e.g. `evilremix.com` vs. an allowlisted `*.remix.com`) is incorrectly treated as a trusted subdomain.

## Finding Description
`isAllowedOrigin` parses the client-supplied `Origin` header and each configured allowlist entry via `splitURL` (`url.Parse` + `net.SplitHostPort`), then for wildcard entries strips the `*.` prefix and checks `strings.HasSuffix(originHost, allowedHost)`. This check has no requirement that the match start at a `.`-delimited label boundary, so `evilremix.com` satisfies `*.remix.com` just as much as `foo.remix.com` would. `handleRequest` calls `isAllowedOrigin` directly on the unauthenticated, attacker-controlled `Origin` header before any other validation, and there is no additional check anywhere in the codebase that re-validates domain-label boundaries — the existing wildcard test suite in `httpserver_test.go` only exercises legitimate subdomains and disjoint non-matching domains, never a suffix-collision case, confirming the gap is real and untested.

## Impact Explanation
On any deployment with `CORSEnabled: true` and a wildcard `CORSAllowedOrigins` entry (a normal, supported configuration documented in `core/scripts/gateway/sample_config.toml`), an attacker who registers a domain sharing the configured suffix (e.g. `evilremix.com` against `*.remix.com`) has their `Origin` accepted, and the server reflects it back verbatim as `Access-Control-Allow-Origin`. This lets an attacker-controlled webpage make cross-origin authenticated requests to the gateway's workflow-trigger JSON-RPC HTTP endpoint and read the responses — an allowlist bypass leading to cross-origin response disclosure.

## Likelihood Explanation
Exploitation requires no privileged access: only that the operator use the documented wildcard CORS feature and that the attacker register/control a domain with a matching suffix and get a victim's browser to visit it. This is a low-effort, repeatable attack path fully triggerable by an unprivileged network client.

## Recommendation
Require a `.` boundary before the matched suffix, e.g. `strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost`, or split hostnames into DNS labels and compare the trailing labels for exact equality instead of raw string suffix comparison.

## Proof of Concept
1. Configure `CORSAllowedOrigins = ["https://*.remix.com"]` and `CORSEnabled = true`.
2. Send an HTTP request to the gateway's configured `Path` with header `Origin: https://evilremix.com`.
3. Observe `isAllowedOrigin` returns `true` and the response includes `Access-Control-Allow-Origin: https://evilremix.com`, despite `evilremix.com` not being a subdomain of `remix.com`. This can be verified as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `httpserver_test.go`, but asserting the origin `https://evilremix.com` against allowlist `https://*.remix.com` is (incorrectly) accepted.
