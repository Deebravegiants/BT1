Based on the library code inspection, I found a valid analog: the webhook HMAC in this gem signs only the raw body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which the app trusts as the tenant identity to act on — are taken from unauthenticated HTTP headers that are not covered by that signature.

### Title
Webhook shop/topic/webhook_id identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` authenticates the body bytes only. The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` uses to identify *which tenant* the webhook belongs to are read straight from HTTP headers that are never included in the signed content.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and the identity fields are pulled from raw headers: [2](#0-1) 

`HmacValidator.validate_signature` computes the expected signature exclusively from `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` directly, without any cross-check against the signed payload, and forwards them to the app's handler as the record of which tenant/topic the event belongs to: [4](#0-3) 

Because the signature covers only the body, the binding the app relies on — "the shop/topic in this event equals the shop/topic verified by the HMAC" — does not hold: `signed(body) == shop-header` is never true; the header is fully independent of the signature. An unprivileged actor who has ever received one legitimate webhook delivery for their own shop (which is trivial to obtain as a normal merchant/installer of the app, requiring no `api_secret_key` or privileged access) can capture that valid `raw_body` + `hmac` header pair and resend it to the same public webhook endpoint with the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers swapped to arbitrary values. The HMAC check still passes (it only validates the untouched body bytes), and the handler will process the event believing it originates from a different shop/topic/webhook id.

### Impact Explanation
This breaks the tenant isolation the HMAC is supposed to guarantee: the app processes attacker-chosen `shop` identity together with a body from a different, legitimate delivery, i.e. cross-tenant data confusion/injection without needing any secret. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up which merchant's session/data to update), this can let one merchant poison, spoof, or trigger event handling under another shop's identity — a cross-tenant access impact.

### Likelihood Explanation
Any merchant that installs the app and has webhooks enabled can capture one legitimate `(raw_body, hmac)` pair from their own shop (e.g., via a webhook subscribed to a benign, frequent topic) and replay it against the app's public webhook endpoint with modified `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers. No credentials, secrets, or privileged access are required — only network access to the app's public webhook route, which is inherently internet-reachable.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content used for HMAC verification (or otherwise cryptographically bind them, e.g. by validating `webhook_id` uniqueness/replay and re-deriving `shop` from an authenticated source such as a stored per-webhook mapping), rather than trusting header values that fall outside the HMAC's coverage.

### Proof of Concept
1. As a legitimate merchant, install the app and let it receive one real webhook for shop `a.myshopify.com`, topic `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Capture `B` and `H`.
3. POST to the app's webhook endpoint with headers:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-webhook-id: <any-id>`
   - `x-shopify-hmac-sha256: H`
   - body: `B`
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, which is still true.
5. `Registry.process` invokes the topic handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as though the event came from `victim-shop.myshopify.com`.
