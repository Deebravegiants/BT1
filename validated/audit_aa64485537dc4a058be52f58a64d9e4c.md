### Title
`EvmHost.dispatch()` / `dispatch(DispatchGet)` / `fundRequest()` permanently strand excess native-token payments instead of refunding them - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and swap it via `swapETHForExactTokens` for an exact amount of fee token, but never capture the router's return value or refund the unspent ETH back to the caller. The Uniswap V2 router refunds any leftover ETH to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender — so any overpayment is stuck in the host contract with no code path returning it to the user.

### Finding Description
In `dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The identical pattern is repeated in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

`swapETHForExactTokens` on UniswapV2Router02 spends only as much ETH as required to buy the exact `amountOut` and refunds the remainder to `msg.sender` of that call. Here the caller of the router is `EvmHost` (not the user), so any `msg.value` sent above the exact amount needed for the fee-token swap is refunded to `EvmHost` and silently absorbed into its balance — it is never sent back to the dispatching user, nor is it credited to that request's fee metadata.

This is the same root cause as the reported analog: no cap/equality check on the value supplied, and (worse than the reference bug) not even an attempt to return the excess to the payer.

Critically, the codebase elsewhere demonstrates the correct fix pattern is known and used: `IntentGatewayV2.placeOrder()` captures `amounts[0]` from `swapETHForExactTokens` and explicitly refunds `msgValue - amounts[0]` to `msg.sender` via `_sendValue` [4](#0-3) , and `IntentGatewayV2SameChainTest.sol` / `IntentGatewayV2Test.sol` explicitly assert this refund behavior [5](#0-4) . `EvmHost.dispatch`/`dispatch(Get)`/`fundRequest` do not apply this same refund pattern, so this is an inconsistency/gap rather than an inherent limitation of the design.

There is no `receive()`/sweep mechanism visible in `EvmHost.sol` that would let the overpaying user reclaim these stuck funds; the only privileged party able to move host balance is the governance-controlled `hostManager` (via `HostParams.hostManager`) [6](#0-5) , which is not the paying user.

### Impact Explanation
Any unprivileged user or app contract calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native token payment and sending more ETH than the swap actually requires permanently loses the difference — it accrues to the `EvmHost` contract's balance rather than being refunded. Since fee estimation off-chain (`quote()`) can easily diverge from the on-chain AMM price at execution time (slippage, front-running, price movement), overpayment is a normal, expected occurrence, not just user error — making this a realistic and recurring fund-loss vector for every dispatching user/app on every EVM deployment of Hyperbridge. This satisfies the "concrete theft or permanent freezing of funds" bar, since the difference is neither refunded nor recoverable by the original payer.

### Likelihood Explanation
High likelihood: any user/app dispatching a POST or GET request with native-token payment, or funding a pending request via `fundRequest`, is exposed on every call, since exact fee-token pricing via AMM cannot be perfectly predicted client-side and the contract makes no attempt to cap or refund the difference.

### Recommendation
Capture the actual amount spent from `swapETHForExactTokens` (its returned `amounts[0]`) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amountSpent` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2._placeOrder`/`ExtrinsicIntents`/`IntrinsicIntents` (`_sendValue(msg.sender, msgValue)`).

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `post.fee = 100` fee-token units and sends `msg.value = 2 ether`, expecting the swap to cost roughly 1 ETH based on an off-chain quote.
2. `swapETHForExactTokens{value: 2 ether}(100, path, address(this), ...)` executes, spending e.g. only `0.9 ether` to acquire the 100 fee-token units, and the router refunds the remaining `1.1 ether` to `msg.sender` of the call — `EvmHost`.
3. `EvmHost.dispatch` continues without ever inspecting the swap's return value or transferring anything back to the user; the `1.1 ether` remains in `EvmHost`'s balance permanently, with no user-facing withdrawal path.
4. Compare to `IntentGatewayV2.placeOrder`, tested in `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` [5](#0-4) , where the equivalent excess is refunded to the user — demonstrating `EvmHost` diverges from the intended/expected safe behavior.
