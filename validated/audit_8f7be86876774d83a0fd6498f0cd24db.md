**Analysis:**

The `check_struct_def_instantiation` check in `struct_api_checker.rs` reads the `StructDefInstantiation` pool entry directly from the module (`self.module.struct_instantiation_at(sdi_idx)`) and validates its actual contents (`sdi.def` and `sdi.type_parameters`) at the exact call site being processed [1](#0-0) . Because this reads the pool entry's live data rather than any cached/aliased state, "reusing" a pool entry across multiple `PackGeneric` sites cannot desynchronize the check from the real data — whatever content sits at `sdi_idx` is what gets validated, every time it's referenced, in every function that uses it.

`check_pack_pattern` only inspects the single second-to-last bytecode instruction of the specific wrapper function's fixed-shape code unit (`MoveLoc*, PackGeneric, Ret`), and calls `check_struct_def_instantiation` on that instruction's own `sdi_idx` [2](#0-1) . There is no cross-function memoization, "pre-validation" cache, or trust propagation from one call site to another — each occurrence of `PackGeneric` in each function's bytecode triggers its own independent lookup and check of `sdi.def == self.struct_def_idx` plus canonical `TypeParameter(0..n-1)` args.

If two `PackGeneric` sites shared one pool entry, both would necessarily be checked against the same `sdi.def`, so they could only "alias" validly if they belong to the exact same struct definition index with the same number of type parameters — in which case canonical-or-not is a single, unambiguous property of that one pool entry, not something that can diverge between sites. There is no code path where a canonical check at one site causes a non-canonical entry to be silently accepted at another site.

Additionally, this checker only governs the compiler-generated struct-API wrapper functions (`pack$S`-style names); it is not the general type-safety verification for arbitrary `PackGeneric` usage in normal module code, which is independently enforced by `type_safety.rs` for every instruction occurrence regardless of pool sharing [3](#0-2) .

Since the premise (that pool-entry reuse can bypass or corrupt independent per-site canonical checks) does not hold given the code's direct-read, per-occurrence validation design, there is no path from unprivileged bytecode/module input to a mistyped generic `Object<T>`/`Coin<T>` wrapper or any custody-relevant state corruption.
