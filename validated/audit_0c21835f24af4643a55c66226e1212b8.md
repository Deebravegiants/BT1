## Title
Webhook shop/topic/metadata headers are not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the signed material [2](#0-1) . `Registry.process` verifies only the body's HMAC and then trusts these header-derived values, including `shop`, to build `WebhookMetadata` for the handler [3](#0-2) .

### Finding Description
The equality that should hold is: `shop_bound_by_signature == shop_acted_on_by_handler`. In `Registry.process`, `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string`, which is exclusively the raw body [4](#0-3) . The `shop` value comes from `shopify_header("shop-domain")`, a plain HTTP header with no cryptographic binding to the signature [5](#0-4) . As a result, `shop_bound_by_signature` (nothing — the signature only proves the body's integrity) is not equal to `shop_acted_on_by_handler` (the header value blindly forwarded into `WebhookMetadata`) [3](#0-2) .

Any party who can obtain one genuine, validly-signed `(body, hmac)` pair for their own shop (e.g., a merchant who installs the app on their own store and receives a webhook delivery to their own endpoint) can resend that exact same `body`+`shopify-hmac-sha256` pair while substituting `shopify-shop-domain` (and optionally `shopify-webhook-id`/`shopify-topic`) to any value. `HmacValidator.validate` still succeeds because it only checks the body/secret pair via `OpenSSL.secure_compare` [6](#0-5) , and `Registry.process` proceeds to invoke the handler believing the event originated from the spoofed shop.

### Impact Explanation
This breaks the tenant-identity binding that consuming applications rely on: the gem's own `WebhookMetadata.shop` is presented to the handler as an authenticated fact, but it is not bound by the signature at all. Any host application that keys shop-scoped state (e.g. upserting store data, revoking access, updating billing/subscription status) off `WebhookMetadata.shop` without independently re-verifying shop identity can be made to apply another tenant's webhook payload to an arbitrary shop record — a cross-tenant data-integrity issue.

### Likelihood Explanation
Requires only application-level access (installing/using the app on one's own shop to legitimately receive one webhook), no secret leakage, no TLS interception, and no privileged account — squarely an "unprivileged internet user" analog. It is reliable and repeatable once a single valid (body, hmac) sample is captured.

### Recommendation
Have `Utils::HmacValidator`/`Webhooks::Request` bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material used for verification, or otherwise require the `Registry` to reject/flag when acting on `shop` unless it's independently corroborated (e.g., cross-checked against the session/store the request line/route was addressed to), rather than trusting headers wholesale after a body-only HMAC check.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a real webhook delivery with headers `shopify-hmac-sha256: <valid>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, and some JSON body `B`.
2. Attacker resends the exact same body `B` and `shopify-hmac-sha256` value to the app's webhook endpoint but sets `shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body [7](#0-6) ; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because only `B` and the secret are checked [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)` [9](#0-8) , causing the host application to process attacker-controlled data under the victim shop's identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
