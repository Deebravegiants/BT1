### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller and becomes stuck in the contract - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are `payable` and accept native ETH as an alternative fee-payment rail, swapping it to the protocol `feeToken` via Uniswap V2. None of these three functions capture or forward back any ETH left over after the swap, so any overpayment is silently absorbed by the `EvmHost` contract itself instead of being returned to the caller.

### Finding Description
In all three functions, when `msg.value > 0` the code does: [1](#0-0) 

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

The standard `UniswapV2Router02.swapETHForExactTokens` implementation refunds any unspent ETH (`msg.value - amounts[0]`) via `safeTransferETH(msg.sender, dust)`, where `msg.sender` from the router's perspective is `EvmHost` (the direct caller of the router), **not** `_msgSender()` of the original `dispatch`/`fundRequest` call. This refund lands back in `EvmHost`'s own balance rather than being routed to the address that actually paid the excess ETH.

The same pattern repeats in `dispatch(DispatchGet)` [2](#0-1) 

and in `fundRequest` [3](#0-2) 

No code after the swap in any of these three functions checks the remaining/leftover native balance and sends it back to `_msgSender()`. This is in direct contrast to `IntentGatewayV2.placeOrder` and `IntentGatewayV2.fillOrder`/`IntrinsicIntents`/`ExtrinsicIntents`, which each explicitly track the residual `msgValue` after every native operation and refund it at the end via `_sendValue(msg.sender, msgValue)`: [4](#0-3) [5](#0-4) 

This shows the codebase is aware of the "excess ETH must be refunded" invariant and implements it consistently elsewhere, but omits it specifically in `EvmHost`'s three native-payment entry points — the exact bug class described in the external report (payable batch/dispatch function that accepts `msg.value` for a computed cost without returning the difference).

### Impact Explanation
Any application, relayer, or end user that calls `EvmHost.dispatch{value: X}(...)` or `EvmHost.fundRequest{value: X}(...)` with `X` greater than the exact amount required to buy `post.fee`/`get.fee`/`amount` worth of `feeToken` permanently loses the difference — it becomes native ETH balance sitting in `EvmHost` with no tracked owner and no exposed withdrawal path for native ETH (only `feeToken`-denominated `withdrawFees`-style functions exist for the ERC20 revenue). Because exact-quoting native fee amounts client-side is inherently imprecise (AMM price can move between quote and execution, and callers commonly overprovision `msg.value` as a safety margin, as shown in the SDK/docs guidance to send `nativeValue` which "the gateway swaps ... (unused native is refunded)"), overpayment is a normal, expected occurrence in production usage, not an edge case. Every overpaid dispatch/fundRequest permanently locks user funds — a direct loss of funds for callers and an unbacked freeze of ETH inside the host contract.

### Likelihood Explanation
High likelihood: `dispatch()` and `fundRequest()` are the primary, unprivileged, externally reachable entry points for any application dispatching cross-chain messages or topping up relayer fees using the native-token payment rail (as documented in `docs/content/developers/evm/api/idispatcher.mdx` and `docs/content/developers/evm/messaging/post-requests.mdx`). Any caller who does not send the exact wei amount required by the current AMM price (which is the common case, since users/apps typically send a margin above the estimated quote to avoid reverts from price movement) will lose the excess with no recovery mechanism.

### Recommendation
Track the ETH balance before/after the `swapETHForExactTokens` call (or capture `amounts[0]` returned by the swap) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and forward the unspent remainder back to `_msgSender()` at the end of each function, mirroring the refund pattern already used in `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.1 ETH worth of `feeToken` at current market price (analogous to the existing test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` in `evm/tests/foundry/IntentGatewayV2Test.sol:3714-3752`, which validates the refund behavior exists in `IntentGatewayV2` but has no counterpart test for `EvmHost.dispatch`/`fundRequest` refunding excess ETH).
2. Internally, `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` spends only the required ~0.1 ETH and refunds the remaining ~4.9 ETH to `msg.sender`, i.e., `EvmHost` itself, via the router's internal `safeTransferETH(msg.sender, dust)`.
3. `dispatch()` returns without ever inspecting `address(this).balance` or forwarding the 4.9 ETH back to the caller.
4. The caller's transaction succeeds, `post` is recorded and emitted normally, but ~4.9 ETH remains trapped in the `EvmHost` contract with no code path to recover it back to that caller.
