### Title
Webhook HMAC Validation Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop-domain` header — which is handed to the app's webhook handler as the authenticated tenant identifier — is never included in the signed material, so it can be swapped freely while the HMAC still validates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers and are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery` — only checks `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` (taken from the unauthenticated `shop-domain` header) is forwarded verbatim to the host application's handler as the tenant identity for the event: [5](#0-4) 

**Binding broken (as an equality):**
`shop_bound_by_HMAC == shop_delivered_to_handler` is **false**. The gem's contract implies the header set (including `shop-domain`) is authenticated once the HMAC check passes, but the HMAC only covers `raw_body`. `shop-domain` is bytes-parsed, not bytes-verified.

**Concrete break:** the app's `api_secret_key` is a single, shared secret across every merchant that installs a multi-tenant app. Any installed merchant (an "unprivileged internet user" relative to other tenants of the same app) legitimately receives a validly-signed webhook for their own shop, i.e. a `(body, HMAC(secret, body))` pair. Because `shop-domain` is excluded from the signable string, that same merchant can replay the identical `(body, HMAC)` pair directly to the app's webhook endpoint while substituting a different `shop-domain` header (a victim tenant's domain). `Registry.process` still validates the HMAC (it only checks the body) and dispatches the event to the handler tagged with the victim's shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: a malicious or curious merchant can cause the host application to process attacker-supplied webhook content (e.g., `orders/create`, `products/update`, GDPR-style topics, etc., shaped from data the attacker controls on their own store) under another tenant's identity. Depending on what the host app's webhook handlers do with `data.shop` (e.g., writing to that shop's records, triggering shop-scoped side effects, updating cached state keyed by shop), this can lead to cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not own. This matches the "cross-tenant access" impact bucket.

### Likelihood Explanation
High likelihood of reachability: the webhook endpoint is deliberately public-facing (Shopify posts to it directly), the attacker only needs to be an installed merchant of the same app to legitimately obtain one valid `(body, HMAC)` pair from their own store's webhook deliveries, and then simply POST that same payload with a forged `shop-domain` header to the app's exposed webhook route. No access token, `api_secret_key`, or privileged account is required — only ordinary use of the app as any tenant.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, ideally `topic` and `webhook-id`) in the signed material verified against the HMAC, or otherwise cryptographically bind the shop identifier to the request before handing it to `handler.handle`. Concretely, extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to incorporate `shop`, and/or require callers to have a whitelist of known-installed shop domains that is only trusted after webhook body integrity is confirmed to originate for that specific shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over BODY, computed by Shopify with the app's shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...
   Body: BODY  (JSON content the attacker controls, e.g., order details)
   ```
2. Attacker replays the exact same `x-shopify-hmac-sha256` and `BODY`, but changes the domain header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same HMAC as step 1, unchanged>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: ...
   Body: BODY  (same bytes as step 1)
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, BODY)` — identical to step 1 — so validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: BODY, ...)`, causing the host app to process attacker-controlled content as if it originated from `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
