### Title
Permissionless HyperSwap V2 pre-seed can force `LPLock.recordLock` to revert forever, permanently freezing curve-raised LT and the 250M LP token reserve in `Bonding.finalizeGraduation` - (File: `packages/contracts/src/Bonding.sol`, `packages/contracts/src/LPLock.sol`)

### Summary
The external report's root cause is that a value treated as "required" (non-nil/non-zero) is only enforced by a downstream hard-fail check, while the upstream code path can still legitimately produce the invalid value and has no recovery. The same shape exists in alt.fun's graduation flow: `LPLock.recordLock` unconditionally reverts if the LP amount is zero [1](#0-0) , but `Bonding.finalizeGraduation`'s deposit math, when facing an attacker-seeded HyperSwap pool, can deterministically compute zero liquidity — creating an unrecoverable revert loop that permanently strands the curve's raised reserve and LP-bound token supply.

### Finding Description
Graduation is split into two phases. Phase 1 (`_enterGraduating` → `_prepareGraduationLiquidity`) permanently freezes `tokensForLP` and `ltFromPair` at the curve-close price and immediately moves the real raised LT out of the curve into `Bonding` via `router.graduate` [2](#0-1) . Phase 2 (`finalizeGraduation`) is permissionless and must deposit exactly that cached `(tokensForLP, ltFromPair)` pair into the HyperSwap V2 TOKEN/LT pool, then call `LPLock.recordLock` with the resulting `liquidity` [3](#0-2) .

Because pair creation and seeding are permissionless, an attacker can pre-create the HyperSwap TOKEN/LT pair and seed it with reserves that are (a) already very close to alt.fun's eventual curve-close ratio and (b) enormous relative to the fixed `tokensForLP`/`ltFromPair` amounts that will later be deposited. When phase 2 runs, `_seedUniswapV2Direct` sees `totalSupply() != 0` and enters `_seedRebalancing` [4](#0-3) . Because the pool is already close to the target ratio, `_noFeeSwapInput`/`_pairRebalance` compute a swap input whose fee-charging quote rounds to zero, so `_pairRebalance` returns `false` and the code falls back to `_seedDirectMint`, which calls the raw HyperSwap `pair.mint(lpLock)` with the fixed graduation amounts [5](#0-4) . Standard UniswapV2 mint math computes `liquidity = min(amountA*totalSupply/reserveA, amountB*totalSupply/reserveB)`; against an attacker's vastly larger pre-existing reserves/totalSupply, the fixed graduation deposit can truncate to `liquidity == 0`.

Whether the external HyperSwap pair itself reverts on a zero-liquidity mint or returns `0`, the failure surfaces (directly, or via `finalizeGraduation`'s own call) at `LPLock.recordLock(tokenAddress, lpPair, 0)`, which explicitly reverts with `ZeroAmount()` [6](#0-5) . Since the whole `finalizeGraduation` transaction reverts, no state changes persist — including the `pendingGraduation` cache, which remains byte-identical for every retry (the natspec on `finalizeGraduation` explicitly notes it recomputes nothing and never re-reads live price/ratio state) [7](#0-6) . As long as the attacker's oversized pool reserves remain in place (which they will, since a reverted tx changes nothing), every future call to `finalizeGraduation` reproduces the exact same zero-liquidity outcome, forever.

### Impact Explanation
The token is permanently stuck in `Lifecycle.Graduating`: `Zap.buy`/`Zap.sell` both revert with `TokenIsGraduating` for any token in this state [8](#0-7) [9](#0-8) , so all trading permanently freezes. The curve's entire real raised LT reserve was already transferred out of the curve to `Bonding` via `router.graduate` in phase 1 and is unrecoverable (no owner rescue function exists for LT belonging to a stuck `Graduating` token — `_sweepLTToOwner` only runs inside a successful `finalizeGraduation`). The 250M `LP_RESERVE` tokens reserved for the LP are similarly stranded inside `Bonding`. This is a permanent freeze of trader and LP funds with no on-chain recovery path (`LPLock`'s `isLocker` set is add-only and `Bonding` has no admin override to abort/retry graduation with different parameters), qualifying as Critical.

### Likelihood Explanation
Both HyperSwap pair pre-creation/seeding and driving a token's curve to graduate are explicitly reachable by any unprivileged address. The attack requires the attacker to (1) predict/observe the token's curve-close ratio (derivable from public curve state before the threshold is crossed) and (2) seed the not-yet-existing HyperSwap pair with a large, closely-matched-ratio liquidity position ahead of graduation — a straightforward, permissionless, pre-plannable griefing action requiring only capital, not any special privilege or timing race against the protocol.

### Recommendation
Do not let `finalizeGraduation` silently fall back to a raw `pair.mint`/zero-liquidity outcome when a hostile pre-seed makes the deposit round to zero. Either (a) revert `_enterGraduating`/`finalizeGraduation` with a clear, retriable error when the projected LP mint would be zero and provide an owner/keeper path to re-derive fresh `tokensForLP`/`ltFromPair` targets or route to a fresh pair, or (b) enforce a minimum-liquidity floor check before attempting `_seedDirectMint`/`pair.mint` (analogous to validating a "required" field before use) so the failure mode is a recoverable revert rather than a deterministic infinite loop, and add an owner-only escape hatch to migrate a permanently stuck `Graduating` token's escrowed LT/tokens to a new pair or back to claimable state.

### Proof of Concept
1. Attacker observes token `T` trading on its bonding curve nearing the graduation threshold and estimates the eventual curve-close `tokensForLP`/`ltFromPair` ratio from public `Pair.getReserves()`/`Pair.k()` state.
2. Attacker calls `IUniswapV2Factory.createPair(T, LT)` and seeds it directly (`transfer` + `mint`) with a very large TOKEN/LT liquidity position at (or extremely close to) that predicted ratio, becoming sole LP holder with a huge `totalSupply()`.
3. Normal trading pushes `T` past `canGraduate` (USD threshold or sellout); `_enterGraduating` caches the fixed `(tokensForLP, ltFromPair)` and moves the real raised LT into `Bonding` via `router.graduate` [10](#0-9) .
4. Anyone calls `finalizeGraduation(T)`. `_seedRebalancing` computes a near-zero rebalance swap (rounds to zero output against the already-matched large reserves), falls back to `_seedDirectMint`, and `pair.mint(lpLock)` yields `liquidity == 0` because the fixed deposit is negligible against the attacker's huge reserves/totalSupply [11](#0-10) .
5. `LPLock.recordLock(T, pair, 0)` reverts with `ZeroAmount()` [1](#0-0) , reverting the entire `finalizeGraduation` transaction.
6. Every subsequent call to `finalizeGraduation(T)` re-reads the identical cached `pendingGraduation` values against the still-unchanged hostile pool and fails identically — `T` is permanently stuck in `Lifecycle.Graduating`, with its raised LT and 250M LP-reserved tokens frozen inside `Bonding` and all trading disabled.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }

    /// @dev Transfer the full `(tokensForLP, ltFromPair)` to the pair and
    ///      `mint` the LP to `LPLock`, opening at the exact cached
    ///      curve-close ratio. Used by the empty-pair regime and as the
    ///      dust-pre-seed fallback in `_seedRebalancing` — against dust
    ///      reserves the V2 `min()` formula's donation to any pre-existing
    ///      LP is negligible (see `_seedUniswapV2Direct` natspec). Any TOKEN
    ///      remainder (a skimmed pure-donation pre-seed) is burned; the LT
    ///      remainder is left for `finalizeGraduation`'s `_sweepLTToOwner`
    ///      post-bookend.
    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
        liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
    }
