### Title
Donated / excess LT sent directly to a curve `Pair` is permanently locked with no recovery path - ([File: packages/contracts/src/Bonding.sol], [File: packages/contracts/src/Pair.sol])

### Summary
The original Ajna report is that a rebasing collateral token's rebase, or any direct donation, becomes untracked and permanently stuck inside the pool because the pool only accounts for reserves it explicitly tracked, and there's no mechanism to sweep the untracked surplus. alt.fun has the same structural gap: LT (the reserve asset, itself an externally rebasing/appreciating BounceTech leveraged token) sent directly to a `Pair` via `ERC20.transfer` rather than through the curve is never drained back out, before or after graduation, because only `Router` (holding `BONDING_ROLE`) can move a `Pair`'s asset balance, and `Router.graduate` only ever pulls the curve-computed `ltFromPair` amount, not the pair's full balance.

### Finding Description
`Bonding._graduate()` computes the real LT raised by the curve as `ltFromPair = reserve1 - virtualLtReserve`, deliberately excluding any LT that was donated directly to the pair via a raw ERC20 transfer, and drains only that amount through `Router.graduate(token, ltFromPair)`: [1](#0-0) 

The docs explicitly acknowledge that "Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`," and this is codified as an invariant tested in `GraduationInvariants.t.sol` ("Donation resistance ... donated LT stays locked in the curve pair"): [2](#0-1) 

Similarly, real token donations to the pair (before graduation) are unconditionally burned by `_prepareGraduationLiquidity` rather than credited to anyone, and the "supply trigger" in `canGraduate` cannot be satisfied while donated tokens inflate `tokenBalance()`: [3](#0-2) 

Because `Pair`'s asset/token balances can only ever be moved by the `Router` under `BONDING_ROLE`, and `Bonding`/`Router` expose no function that sweeps a pair's *excess* balance above its accounted `reserve0`/`reserve1` (either pre- or post-graduation), any LT or Token transferred directly into a `Pair` — whether from a stray donation, an accidental transfer, or the appreciation dynamics of the rebasing/exchange-rate-bearing LT being deposited outside the mint/curve path — is permanently stranded. Once the token graduates, the curve `Pair` becomes economically dead (all trading moves to the HyperSwap V2 TOKEN/LT pool), so the locked LT/Token in the old `Pair` can never be retrieved by anyone, including the protocol.

This is the direct on-chain analog of the reported bug class: the pool (Pair) is not the tracked accounting object for everything transferred into it, and there is no `reserveAuction()`-style or `sweepDonations()`-style recovery mechanism for the curve `Pair`, unlike `FeeVault`, which does implement exactly such a sweep (`FeeVault.sweepDonations()`): [4](#0-3) 

The asymmetry (FeeVault sweeps donated USDC to `feeTo`, but `Pair` has no equivalent for donated LT/Token) confirms the team addressed this bug class for `FeeVault` but left the `Pair` contract's untracked-balance exposure unmitigated.

### Impact Explanation
Any LT (or launched Token) transferred directly to a `Pair` outside of the `Zap`/`Bonding` flow is permanently and irrecoverably locked — a genuine, unbounded loss of funds for whoever sent them, with no path for the protocol, the sender, or any other party to reclaim the value, satisfying the "permanent freezing of trader, creator or LP funds" bar. Because LT is a leveraged, appreciating asset (its `exchangeRate()` grows over time), any LT that lands in a `Pair` this way is value that is permanently removed from circulation with no offsetting mechanism, mirroring the original report's "rebase is lost forever" framing.

### Likelihood Explanation
Reachable by any unrelated wallet with a single unprivileged `IERC20.transfer(pairAddress, amount)` call — no special role or permission is required, matching the "direct ERC20 transfers of ... an LT into Pair" path explicitly called out as in-scope. The likelihood of accidental donations (e.g., users mistaking the `Pair` address for the `Zap`/`Bonding` entrypoint, or wallets/bridges auto-forwarding LT) is realistic given LT is the reserve asset users regularly hold and transact with.

### Recommendation
Add a permissionless sweep on `Pair`/`Bonding`, gated to only move the *excess* over the tracked `(reserve0, reserve1)` — analogous to `FeeVault.sweepDonations()` — that forwards untracked LT/Token surplus to a safe destination (e.g., `FeeVault`, the token's creator, or burns it), both pre- and post-graduation, so no value transferred into a `Pair` outside the curve flow is permanently unrecoverable.

### Proof of Concept
1. A token is launched via `Bonding.launch`, creating a `Pair` for `token`/`lt`.
2. Any wallet calls `IBounceLeveragedToken(lt).transfer(pairAddress, X)` directly (a plain ERC20 transfer, not via `Zap.buy`).
3. `Pair`'s real LT balance now exceeds `reserve1`, but `Bonding.canGraduate`'s USD leg only reads `assetReserve` from `getReserves()` (the stored reserve, not the live balance) — see the `realLtRaised = assetReserve - _launchTimeVirtualLtReserve` computation in `canGraduate`: [5](#0-4) 
4. When the token later graduates, `_graduate()` drains only `ltFromPair = reserve1 - virtualLtReserve` via `Router.graduate`, per `docs/contracts-scope.md` lines 89-92 above; the donated `X` LT is never withdrawn.
5. The curve `Pair` is now dead (all liquidity/trading has moved to HyperSwap V2); the donated `X` LT sits in the `Pair` contract forever, with no function on `Bonding`, `Router`, or `Pair` able to move it out (movement is gated to `Router`'s `BONDING_ROLE`, and `Router.graduate` was already called with the fixed `ltFromPair` amount).

    ///         Supply trigger: uses live `IPair.tokenBalance()`. This IS an
    ///         `IERC20.balanceOf` read but is donation-resistant in the
    ///         opposite direction — token donations can only INCREASE the
    ///         balance, never satisfy "== 0", and the only path that drains
    ///         tokens out of the pair is the curve buy flow. Donated tokens
    ///         are unconditionally burned by `_prepareGraduationLiquidity`.
    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
