### Title
`onPostRequestTimeout()` incorrectly gated by `whenNotPaused`, blocking refunds for already-locked/burned funds during pause - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.onPostRequestTimeout()` (and its counterpart in `WrappedHyperFungibleToken.sol`) is gated by the `whenNotPaused` modifier, the same modifier used to guard `send()`. Pausing is meant to stop *new* outbound transfers, but it also blocks completion of transfers that were already initiated (burned/locked) before the pause and later time out — exactly the "queued/in-flight work should still complete" pattern described in the external report for `MarginDex.execute_limit_order()`.

### Finding Description
`send()` burns the caller's tokens and dispatches an ISMP POST request, guarded by `whenNotPaused`: [1](#0-0) 

If that request times out (destination never delivered it before the timeout), anyone can permissionlessly submit a timeout proof through `HandlerV2.handlePostRequestTimeouts()`, which calls into the host and ultimately invokes the app's `onPostRequestTimeout()` to refund the sender by re-minting the burned amount: [2](#0-1) 

That refund path is also gated by `whenNotPaused`: [3](#0-2) 

This mirrors the `MarginDex` bug class exactly: `is_accepting_new_orders` (here, `paused`) is correctly checked at the point a *new* action is initiated (`post_limit_order` / `send`), but is then re-checked on the *completion* of an action that was already committed before the pause took effect (`execute_limit_order` / `onPostRequestTimeout`). The `HandlerV2.handlePostRequestTimeouts()` dispatcher itself only checks `notFrozen(host)` at the host level, not app-level pause state, confirming that app-level pausing of the timeout-refund path is a design decision specific to `HyperFungibleToken`, not a protocol invariant: [4](#0-3) 

The same pattern exists in the wrapped variant, which underlies/locks an external ERC20 rather than burning a native supply, making the frozen-funds impact identical: [5](#0-4) 

### Impact Explanation
While a `HyperFungibleToken` deployment is paused (e.g., admin puts it into defensive/incident mode), any user whose earlier `send()` transaction subsequently times out cannot be refunded: their tokens remain burned (or locked, for the wrapped token) with no way to reclaim them until the owner unpauses the contract. This is a freezing-of-funds condition for the token bridger persona reachable purely by submitting a normal `send()` and then a permissionless timeout-proof relay — no privileged action required to trigger the loss condition, only to resolve it (unpause). During an incident, this is precisely the scenario where a pause is most likely to be active and prolonged, compounding user fund lock-up at the worst time.

### Likelihood Explanation
Likelihood is moderate-to-high: pausing a bridge app is a normal admin-mitigation action during incidents, and cross-chain message timeouts are a routine occurrence (network delays, destination chain issues, relayer inactivity). Any user who sent tokens shortly before a pause was activated, and whose message later times out, is affected without any special conditions.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout()` (and, if similarly present in `WrappedHyperFungibleToken.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`, and `HyperFungibleTokenUpgradeable.sol`), since refunding an already-initiated, already-debited transfer does not create new bridge exposure and should not be blocked by the guard intended to stop *new* sends. Retain `whenNotPaused` on `send()` and `onAccept()` (which does create new exposure by minting from an incoming, unverified-during-pause path), but let timeout-driven refunds always be completable.

### Proof of Concept
1. User calls `HyperFungibleToken.send(...)` while unpaused; the contract burns `params.amount` from the user and dispatches a POST request (`HyperFungibleToken.sol:264-266`).
2. Before the destination processes the request, the owner calls `pause()` (`HyperFungibleToken.sol:213-215`) due to an unrelated incident.
3. The request's timeout elapses without delivery. Any relayer permissionlessly submits a timeout proof via `HandlerV2.handlePostRequestTimeouts()` (`HandlerV2.sol:254-286`), which invokes `onPostRequestTimeout()` on the token.
4. `onPostRequestTimeout()` reverts due to `whenNotPaused` (`HyperFungibleToken.sol:321`), so the user's burned tokens are not refunded and remain unrecoverable until the owner unpauses — even though the underlying event (transfer never delivered) is unrelated to why the contract was paused.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
