### Title
Unauthenticated `superApprove()` in `HyperFungibleTokenImpl` lets any address grant itself unlimited allowance over any token holder's balance - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.sol`, deployed as the protocol's testnet/faucet fee token via `evm/script/DeployIsmp.s.sol` and paired with the public `TokenFaucet.drip()` entrypoint, exposes a `public` function `superApprove(address owner, address spender)` that calls `_approve(owner, spender, type(uint256).max)` with **no access control whatsoever** [1](#0-0) . This is a more severe variant of the referenced WatchPug finding on `L1Escrow.approve()`: instead of requiring `DEFAULT_ADMIN_ROLE`, this function can be called by **any unprivileged address**, for **any owner**, to grant unlimited ERC-20 allowance to **any spender**.

### Finding Description
`HyperFungibleTokenImpl` is an ERC-20 with role-gated `mint`/`burn` and `grantMinterRole`/`grantBurnerRole` all correctly protected with `onlyRole(DEFAULT_ADMIN_ROLE)` or `onlyRole(MINTER_ROLE)` [2](#0-1) . However, the last function, `superApprove`, is declared `public` and takes an arbitrary `owner` parameter, directly setting that owner's allowance for an arbitrary `spender` to `type(uint256).max` via the internal `_approve` [3](#0-2) . There is no `msg.sender == owner` check, no role check, and no signature/permit verification — the function is reachable by literally anyone.

This token contract is not a test-only artifact: it is deployed by the production deployment script `evm/script/DeployIsmp.s.sol` and is the token minted by the permissionless `TokenFaucet.drip()` function, which any address can call once daily to receive tokens and interact with the deployed instance [4](#0-3) . Any holder of this token (e.g., a relayer, message dispatcher, or intent solver funding gas/fees with it) is exposed: an attacker can call `superApprove(victim, attacker)` for any victim address that holds a balance, then immediately call `transferFrom(victim, attacker, balance)` to drain the victim's full balance of the token.

### Impact Explanation
Unlike the original L1Escrow finding — which required a compromised/malicious `DEFAULT_ADMIN_ROLE` holder to cause harm — this bug requires **no privilege at all**. Any single unprivileged transaction from any external account can grant itself (or any address) unlimited spending rights over any other holder's balance of this token, enabling immediate, permanent theft of funds from every holder of the token deployed from this contract, including relayers/dispatchers who fund operations with this fee token via the faucet.

### Likelihood Explanation
High. The function is public, requires no special role or approval, costs a single gas-only transaction, and directly targets `_approve` without any authentication of `owner`. Given `TokenFaucet.drip()` publicly mints and distributes this exact token to any caller, an attacker can trivially identify holders (and the faucet itself, plus any consumer contracts) as targets and drain them with a single `superApprove` + `transferFrom` pair.

### Recommendation
Remove `superApprove` from production code entirely, or, at minimum, restrict it so it can only be called by `owner == msg.sender` (making it a redundant, no-op relative to the standard `approve`), or gate it behind an explicit role intended only for test/deployment tooling and never deploy such a build to any live or public-facing environment (including public testnets, since the faucet distributes real value/usage credit).

### Proof of Concept
1. Protocol deploys `HyperFungibleTokenImpl` as configured in `evm/script/DeployIsmp.s.sol`, paired with `TokenFaucet`.
2. Victim calls `TokenFaucet.drip(token)` and receives `1000e18` tokens [5](#0-4) .
3. Attacker calls `HyperFungibleTokenImpl(token).superApprove(victim, attacker)`, which succeeds unconditionally and sets `allowance[victim][attacker] = type(uint256).max` [3](#0-2) .
4. Attacker calls `transferFrom(victim, attacker, 1000e18)` (inherited standard ERC-20 `transferFrom` from OpenZeppelin's `ERC20`), draining the victim's entire balance.

contract TokenFaucet {
    mapping(address => uint256) private consumers;

    // @dev Will only drip tokens, once per day
    function drip(address token) public {
        uint256 lastDrip = consumers[msg.sender];
        uint256 delay = block.timestamp - lastDrip;

        if (delay < 1 days) {
            revert("Can only request tokens once daily");
        }

        consumers[msg.sender] = block.timestamp;
        HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18);
    }
