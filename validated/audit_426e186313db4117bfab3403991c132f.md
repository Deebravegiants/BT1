### Title
Interest accrual overflows debt valuation and permanently freezes a large market - (File: common/src/rates/scaling.rs)

### Summary
An unprivileged account can leave a sufficiently large borrowed market in a state where the next accrual panics while calculating `borrowed * borrow_index`. Because every pool mutation accrues before performing its operation, the market then rejects repayments, withdrawals, liquidations, bad-debt cleanup, parameter updates, and further index updates, permanently freezing the funds held in that market. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes` accepts an authorized caller and forwards arbitrary `HubAssetKey` entries to `pool_update_indexes_call`; authorization here means the caller signs its own invocation rather than holding a privileged role. [3](#0-2) [4](#0-3) 

The pool's `accrue` path loads each selected market and calls `interest::global_sync`. [5](#0-4)  `global_sync` processes elapsed time in bounded chunks and calls `accrue_step` for each chunk. [6](#0-5) [7](#0-6) 

`accrue_step` converts the stored scaled debt into its current RAY-denominated value with `scaled_to_original(borrowed, borrow_index)` before calculating utilization and updating the index. [8](#0-7)  `scaled_to_original` is a checked `Ray::mul`, whose result must fit in `i128`; once the scaled-debt/index product exceeds `i128::MAX`, accrual panics with `MathOverflow`. [2](#0-1) [9](#0-8) [10](#0-9) 

The borrow-index ceiling does not prevent this condition: `update_borrow_index` caps the index only after multiplying by the interest factor, while debt valuation occurs before that update and has no corresponding ceiling on the resulting debt value. [11](#0-10) [12](#0-11) 

An attacker can establish the precondition through ordinary `supply` and `borrow` calls on their own account, then let sustained high utilization grow `borrow_index` until the next permissionless `update_indexes(caller, vec![hub_asset])` invocation crosses the representable-value boundary. [13](#0-12) [3](#0-2) 

### Impact Explanation
This is a permanent freezing of user funds and a market-level denial of service. All pool-side mutations use `synced_market` or `renewed_market`, which run the same failing accrual before supply, borrow, withdraw, repay, net settlement, seizure, flash operations, strategy creation, recapitalization, or revenue claims can proceed. [14](#0-13) [15](#0-14) 

The existing regression test demonstrates that after the overflow both `withdraw` and `repay` continue to fail with `MathOverflow`, and comments note that liquidation is blocked for the same reason. [16](#0-15)  Even an administrative rate-model replacement accrues under the old model before writing new parameters, so lowering the interest rate cannot bypass the panic without an implementation change or upgrade. [17](#0-16) [18](#0-17) 

### Likelihood Explanation
Triggering the condition requires an unusually large market and enough elapsed time at high utilization for the debt value—not merely the index—to exceed the `i128` range. The in-repository reproduction uses one billion whole 18-decimal tokens at 98% utilization and repeatedly advances time until accrual fails. [19](#0-18) 

Nevertheless, the path uses only normal account authorization and a permissionless index update once market configuration, caps, liquidity, and collateral allow the position. The resulting state is not a transient rejected transaction or a fail-closed input check: no subsequent user operation can move that market's funds because accrual itself can no longer complete. [1](#0-0) [20](#0-19) 

### Recommendation
Do not let debt valuation overflow make accrual permanently impossible. Representative mitigations include:

1. Track or cap market debt in a wider representation, such as `I256`, until it is converted back to an asset amount that must fit `i128`.
2. Bound admitted scaled debt so `scaled_debt * MAX_BORROW_INDEX_RAY` remains representable, and enforce that bound on every borrow/strategy debt-mint path.
3. Add a pre-overflow debt-value ceiling analogous to `MAX_BORROW_INDEX_RAY`, and define deterministic accrual, repayment, liquidation, and socialization behavior at that ceiling.
4. If a saturated state is chosen deliberately, make subsequent accrual a no-op rather than panicking, while preserving conservative debt valuation for risk and repayment calculations.
5. Add invariants tying maximum accepted borrow amounts to asset decimals and `MAX_BORROW_INDEX_RAY`, rather than testing only the index bound.

### Proof of Concept
The repository already contains a reproduction in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

1. Create an 18-decimal market and a collateral market.
2. Supply `1_000_000_000 * 10^18` units of the debt asset.
3. Supply sufficient collateral and borrow 98% of that liquidity.
4. Advance ledger time and call `update_indexes` until `scaled_to_original` fails.
5. The call returns `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`; subsequent `withdraw` and `repay` calls fail with the same error. [16](#0-15) 

The minimal production call that triggers the already-created condition is:

```rust
controller.update_indexes(
    attacker,
    vec![&env, HubAssetKey {
        hub_id,
        asset: debt_asset,
    }],
);
```

`markets::update_indexes` forwards that asset to the pool, whose `accrue` loop invokes `global_sync`, then `accrue_step`, then the overflowing `scaled_to_original` calculation. [3](#0-2) [5](#0-4) [12](#0-11)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
