### Title
Local `signup_reason` fully substitutes for backend uniqueness/fraud enforcement in the `user_centric_signup` path, allowing a signup to be counted as successful without the biometric-dedup check that the standard path performs - ([File: src/plans/mod.rs])

### Summary
The referenced Sherlock finding is a fee-bypass bug where a two-step operation (asymmetric deposit + withdraw) reaches the effect of a "taker" swap while only ever passing through the code path that enforces the cheaper "LP/swap fee" check, never the path that enforces the "taker fee." The structural root cause is that an economically equivalent alternate path exists which omits an enforcement step that the canonical path always performs. `orb-core` has a directly analogous structural pattern in `do_signup`.

### Finding Description
In the canonical signup flow, `do_signup` computes `signup_reason` from the (now no-op) local `detect_fraud` check [1](#0-0)  and then calls `enroll_user`, which performs the mandatory backend round-trip (`signup_post`/`signup_poll`) — this backend call is the actual place where the server performs biometric uniqueness/dedup checks, in-flight match detection, and backend-side fraud detection, as documented directly in the code comments ("Backend duplicates", "Backend inflight matches", "Backend detected fraud") [2](#0-1) .

However, `do_signup` has a second branch, gated on `user_centric_signup`, that completely bypasses this backend enrollment/dedup call: [3](#0-2) 

When `user_centric_signup` is `true` and the orb's `ignore_user_centric_signups` config flag is `false` (the default, per `Config::default()` [4](#0-3) ), signup "success" is derived purely from the local `signup_reason == SignupReason::Normal` check — i.e., purely from the on-orb pipeline result and the currently-no-op `detect_fraud` — and the network call to `enroll_user` (the only place that performs backend-side uniqueness/dedup/fraud enforcement) is never made [5](#0-4) .

The `user_centric_signup` flag itself originates from `authenticated_app_data` returned by the backend `user_status` endpoint and is nominally protected by a signature/hash check (`user_data.verify(user_data_hash)`) [6](#0-5) . This mirrors the DEX bug's structure precisely: two logically-equivalent flows exist for reaching "signup success," but only one of them performs the enforcement step (backend dedup/fraud, analogous to the "taker fee") that the design intends to always apply; the other flow ("user-centric," analogous to "asymmetric deposit + withdraw") skips it while still producing the same externally-visible effect (a recorded successful/enrolled signup with locally-derived status).

### Impact Explanation
If the `user_centric_signup` flag can be forced to `true` for a given signup (either through a compromised/malicious client-side app value that still carries a validly-signed but attacker-influenced `user_data`, or through any backend/app inconsistency that marks a signup as app-centric), the signup completes and is reported as successful (`result.success = true` via `debug_report.enrollment_status`) without ever exercising the backend's biometric uniqueness/dedup and fraud-detection logic that `enroll_user`/`signup_post`/`signup_poll` are responsible for. This is a cross-signup state bleed / unauthorized-signup risk: a person already enrolled (or otherwise disqualified server-side) could be locally reported as a fresh, successful, non-duplicate signup, since the only component capable of catching "Backend duplicates" and "Backend inflight matches" is skipped entirely in this branch.

### Likelihood Explanation
Reachability depends on how much control an unprivileged app/user has over the `user_centric_signup` bit and the surrounding authenticated payload. Because the field passes through `user_data.verify(user_data_hash)`, the code intends this to be backend-signed/authenticated, but I could not fully verify the verification scope or whether `user_centric_signup` is bound to the specific hash the way biometric/keys fields are — this is a limitation of what's indexed/available for review. The `ignore_user_centric_signups` config flag exists specifically as an operator-side override to force the fallback to the checked path, which itself suggests this branch was recognized as needing a "kill switch," consistent with it being a weaker enforcement path.

### Recommendation
Do not treat `user_centric_signup` as a sufficient condition to skip the backend `enroll_user` dedup/fraud round trip. At minimum, always call `enroll_user` (or an equivalent backend check) regardless of `user_centric_signup`, and only skip the *UI-facing* differences (not the enforcement call) for the app-centric flow. If skipping the round trip is intentional for latency/UX reasons, ensure the backend has already performed and cryptographically attested the uniqueness/fraud check *before* issuing the `user_centric_signup: true` flag, and bind that attestation, with an expiry, directly to the specific `signup_id`/capture being processed rather than trusting a general per-user flag.

Not applicable — this is a structural code-path analysis of `do_signup` in `src/plans/mod.rs`; a concrete PoC would require reproducing the backend's `authenticated_app_data`/`user_data_hash` signing scheme, which is external to this repository and not verifiable from the indexed code alone.
