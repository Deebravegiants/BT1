## Root Cause

The developer's own comment at `Bonding._deployAndSeed` proves this bug class is understood and *intentionally mitigated only at launch time*, not at graduation: [1](#0-0) 

```
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
// The raised LT reserve peaks at `3 * virtualLtReserve` (curve sell-out)
// and is later deposited into a HyperSwap V2 pair, whose reserves are
// `uint112`. Bound it at launch (4x headroom) so graduation can never
// exceed that slot.
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
```

This is exactly CVE-2018-5709's bug class: the code stores a value in a wider variable (`ltFromPair`/`tokensForLP`, `uint256`) that is *knowingly* going to be truncated when it lands in a narrower field downstream (`uint112` inside the HyperSwap V2 pair's `getReserves()`/`_reserve0`/`_reserve1`, see `IUniswapV2Pair.sol:14` and the mock's `_reserve0`/`_reserve1` state at `MockHyperswapRouter.sol:15-16,69-70,112-113,163-164`), and the guard against that truncation is applied to the wrong quantity/time.

The `uint112.max/4` check at launch bounds only the **launch-time virtual seed** derived from the exchange rate at the moment of deployment. It assumes "the raised LT reserve peaks at `3 * virtualLtReserve`" — i.e., it assumes the *real* LT raised through curve trading can never exceed 3x the initial virtual seed. But `ltFromPair`, the actual amount later transferred into the HyperSwap V2 pair, is computed at graduation time from the pair's live stored reserves and the exchange rate *at that time*: [2](#0-1) 

The code's own `PendingGraduation` struct doc explicitly acknowledges `ltFromPair` can exceed the 3x/4x assumption baked into the launch-time guard: [3](#0-2) 

```
/// @dev `ltFromPair` is held as `uint256` (not narrower) because token
///      creation is permissionless and a malicious LT returning a tiny
///      `exchangeRate` could legitimately push it past 2^128 — a
///      narrowing cast would strand real LT in phase 2.
struct PendingGraduation {
    uint256 tokensForLP;
    uint256 ltFromPair;
    ...
}
```

The team widened the *internal* struct to `uint256` specifically to avoid Bonding's own bookkeeping stranding value — but that only postpones the truncation. `ltFromPair` is still transferred whole into the real HyperSwap V2 pair in `_seedDirectMint`/`_seedRebalancing`: [4](#0-3) 

and the pair's own `mint()` truncates the deposited balance into `uint112` on write (mirrored faithfully by the mock, matching real `UniswapV2Pair` semantics): [5](#0-4) 

If `ltFromPair` (or, in principle, `tokensForLP`, though the parabola cap at `LP_RESERVE` keeps the token side safely bounded) exceeds `type(uint112).max` (~5.19e33), `uint112(balance0)`/`uint112(balance1)` silently wraps, storing a corrupted, much-smaller reserve while the pair's real token balance holds the full amount. Every subsequent `getAmountOut`, `swap`, and price calculation reads the wrapped, wrong reserve — the AMM's price/liquidity accounting is permanently corrupted, exactly like the Kerberos dump file corrupting "other artifacts of the database" once a wrongly-sized field truncates trusted data.

## Reachability

This is reachable from unprivileged transactions: the exchange rate of the paired LT is a live, externally-read value (`exchangeRate()` on the BounceTech leveraged token) that legitimately drifts with the leveraged asset's price — the whole graduation design depends on this drift ("HYPE pumps raise the USD value of already-raised LT above the threshold" per `docs/contracts-scope.md:70`). A severe depreciation of the LT's exchange rate after launch (a leveraged token trading toward zero is a normal, expected market outcome for leverage, not "malicious LT" off-scope behavior) means far more raw LT units are needed to cross the fixed USD graduation threshold via ordinary `Zap.buy`/`Bonding.buy` calls from any trader. This inflates `ltFromPair` computed in `_prepareGraduationLiquidity`, with **no re-check against `type(uint112).max`** at graduation time — unlike the launch-time check. `finalizeGraduation` is permissionless (any address can call it) and unconditionally proceeds to `_seedUniswapV2Direct` → `_seedDirectMint`/`_seedRebalancing`, transferring the full `ltFromPair` into the pair.

## Impact

Once the HyperSwap V2 pair's `uint112` reserve wraps, the pool's stored price is permanently disconnected from its true token balances. This is concrete freezing/loss of value: LPLock's locked LP position (`LPLock.recordLock`, a one-shot, non-skippable call per the repo's own AGENTS.md) is minted against corrupted reserves, traders on the graduated pool get mispriced swaps forever, and real LT that should back the pool becomes partially "invisible" to the AMM's own accounting — unbacked/frozen relative to the wrapped reserve value. There's no post-graduation remediation path since `Pair`/HyperSwap reserves aren't owner-adjustable.

## Uncertainty

I could not fully verify, without deploying or fuzzing, the exact numeric threshold of LT exchange-rate depreciation required to push `ltFromPair` past `type(uint112).max` in a realistic BounceTech leveraged-token scenario (this depends on the LT's actual price dynamics, which are out of scope per the rules), so I cannot state a concrete, guaranteed-reachable numeric PoC — only that the code contains no graduation-time bound mirroring the launch-time one, which the developers' own comments show they considered necessary.

### Title
Unbounded `ltFromPair` transferred into HyperSwap V2's `uint112` reserve slots can silently truncate/corrupt the graduated pool's AMM state - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._deployAndSeed` bounds the launch-time virtual LT reserve to `type(uint112).max / 4` specifically because the eventual real LT raised is later written into a HyperSwap V2 pair's `uint112` reserve slots. That bound is never re-applied to `ltFromPair` at graduation time, even though the codebase's own comments acknowledge `ltFromPair` can legitimately exceed the assumed 3x/4x multiple if the paired LT's exchange rate falls sufficiently.

### Finding Description
`_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` from the pair's live stored reserves with no upper bound check [6](#0-5) . This value is transferred in full to the HyperSwap V2 pair inside `_seedDirectMint` [7](#0-6) , whose `mint()` casts the post-transfer balance down to `uint112` [8](#0-7) . Unlike the launch-time seeding, which explicitly checks `virtualLtReserve > type(uint112).max / 4` [9](#0-8) , no equivalent check guards `ltFromPair` before this transfer.

### Impact Explanation
A `uint112` truncation on the pair's reserve write corrupts the AMM's price/liquidity bookkeeping permanently — this is a Medium/High-severity theft/freezing analog: post-graduation trades are mispriced against wrapped reserves, and the locked LP (`LPLock.recordLock`, one-shot and irreversible) is minted against corrupted state, with no on-chain remedy.

### Likelihood Explanation
Requires the paired LT's `exchangeRate()` to depreciate severely enough, over the life of a curve, that the real LT raised to cross the fixed USD graduation threshold grows past `type(uint112).max`. This is an extreme but not implausible outcome for a leveraged token tracking a volatile underlying, and the codebase's own documentation treats it as a real (if "malicious-LT"-labeled) scenario worth widening `PendingGraduation.ltFromPair` to `uint256` for — yet stops short of preventing the truncation at its actual point of consequence (the HyperSwap pair write).

### Recommendation
Re-check `ltFromPair` (and defensively `tokensForLP`) against `type(uint112).max` inside `_prepareGraduationLiquidity` or immediately before `_seedUniswapV2Direct`, and revert or cap gracefully (documenting the resulting behavior for stuck tokens) rather than relying solely on the launch-time bound that does not account for post-launch exchange-rate drift.

### Proof of Concept
1. Launch a token against an LT whose `exchangeRate()` is just under the launch-time cap (`virtualLtReserve` close to `type(uint112).max / 4`).
2. Have the LT's `exchangeRate()` fall substantially over time (legitimate leverage decay), requiring correspondingly more raw LT to hit `graduationThresholdUsd()`.
3. Multiple unprivileged `Zap.buy` calls raise `ltFromPair` (the pair's real stored LT reserve) past `type(uint112).max`.
4. Any address calls `Bonding.triggerGraduation` then `Bonding.finalizeGraduation` (both permissionless), driving `_seedDirectMint`'s `IUniswapV2Pair(pair).mint(...)`, which truncates `_reserve0`/`_reserve1` via `uint112(balance)`, corrupting the pool's stored reserves relative to its actual token balances.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
