### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` uses to attribute and dispatch the event are read directly from unauthenticated HTTP headers. This breaks the intended binding of "who signed this payload" = "which shop this payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` (and equivalents) HTTP headers, which are not part of the signed material at all: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then immediately trusts `request.shop` and forwards it, unauthenticated, straight into the merchant-facing handler call: [3](#0-2) 

The equality that should hold is: **shop whose secret validated the HMAC == shop attributed to the event data passed to the handler**. Because the signature covers only the body bytes and not the shop header, an attacker who possesses any one legitimately-signed `(raw_body, hmac)` pair for their own shop (trivial to obtain — install the app on their own store and capture one incoming webhook) can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting a victim's `shop-domain` header value. `Utils::HmacValidator.validate` will still succeed, since it only recomputes the HMAC over `@raw_body`, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim's shop — with attacker-controlled body content now falsely attributed to the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem lets an unprivileged (but app-installing) internet user forge which shop a validly-HMAC'd webhook event is attributed to, without ever needing the app's `client_secret`, TLS interception, or any privileged access. Depending on how the host application's webhook handlers act on `data.shop` (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or handlers that create/update/delete per-shop records keyed by `shop`), this can cause the app to execute actions against, or leak data about, a shop the attacker does not control — a cross-tenant access/integrity violation.

### Likelihood Explanation
Moderate-to-high. No secret material, MITM, or privileged credentials are required — only: (1) install the target app on any store the attacker controls (a normal unprivileged action available to any merchant/developer), (2) capture one legitimately delivered webhook (body + `hmac-sha256` header) for a topic of interest, and (3) replay it to the app's public webhook endpoint with the `shop-domain` header changed to the victim's domain. The webhook endpoint is, by design, unauthenticated apart from the HMAC check, so nothing else stops the forged header from reaching `Registry.process`.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or otherwise cross-check the header-derived `shop` against an independently trusted source (e.g., look up the shop by the resolved offline session/access token rather than trusting the header verbatim) before passing it to `WebhookMetadata`. At minimum, document prominently that `request.shop`/`request.topic`/`request.webhook_id` are not covered by the signature and must not be trusted for authorization decisions without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives a webhook (e.g. `app/uninstalled`) sent to the app's public callback URL. They capture the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` from that legitimate delivery.
2. Attacker crafts a new HTTP POST to the same app webhook endpoint with:
   - Body: the identical bytes `B`
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`: unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only [4](#0-3)  — validation succeeds because the shop header was never part of the signed content.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the host application to process attacker-controlled webhook content as if it originated from the victim shop.
