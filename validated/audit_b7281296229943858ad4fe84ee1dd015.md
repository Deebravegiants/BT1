Based on the investigation, the strongest reachable analog to the "unbounded loop" bug class in nearcore is the account-deletion path, where `remove_account` performs unbounded trie iteration over an account's access keys, gas-key nonces, and contract-data entries, while the `DeleteAccount` action is charged a single fixed `ActionCosts::delete_account` execution fee that does not scale with the amount of state actually being removed.

### Title
Unbounded trie iteration in `remove_account` performs unpriced work relative to the fixed `DeleteAccount` action fee - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (invoked from `action_delete_account` in `runtime/runtime/src/actions.rs`) iterates over *every* access key, gas-key nonce entry, and contract-data entry belonging to an account with no cap on the number of items processed, deleting them one by one.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs` performs two unbounded loops over trie ranges owned by the target account: one over all access-key/gas-key-nonce rows (`state_update.locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)`) and one over all contract-data rows (`get_raw_prefix_for_contract_data`). [1](#0-0)  The loops parse and individually collect every key before removing them one at a time, with no limit on how many access keys, gas-key nonce slots, or contract-data entries an account can accumulate. [2](#0-1)  This is called from `action_delete_account` in `runtime/runtime/src/actions.rs`, imported as `remove_account`, which is dispatched for the `DeleteAccount` action during ordinary receipt execution. [3](#0-2)  Unlike other loop-bearing code paths found in this codebase (e.g. `apply_action_receipt`'s per-action loop, `view_access_keys`'s paginated iterator with an `access_keys_limit`, or `promise_and`'s in-loop dependency-count check against `max_number_input_data_dependencies`), this deletion path has no analogous cap on iteration count, and no evidence was found that the `DeleteAccount` action's `exec_fee`/`send_fee` scale with the number of keys or data entries actually removed — the fee model in `core/parameters/src/cost.rs`/`runtime/runtime/src/config.rs` (referenced via `ActionCosts::delete_account`) applies as a flat per-action cost, not a per-item one. I was not able to fully confirm the exact numeric fee formula within the available iterations, so this specific point (whether the fee is entirely flat vs. partially scaled) should be verified directly in `core/parameters/src/cost.rs` and `RuntimeFeesConfig` before treating this as conclusively proven.

### Impact Explanation
If the per-action fee for `DeleteAccount` is fixed regardless of the number of access keys/gas-key nonces/contract-data rows under the account, a user can accumulate a very large number of such entries (each individually paid for via storage staking) and then submit a single `DeleteAccount` action that forces the runtime to perform O(n) trie reads/removals for a flat, cheap gas charge. This is the same "unbounded loop vs. flat cost" shape flagged in the source report. The practical impact is underpriced computation for a single receipt, which can slow chunk application and, in the worst case with many such accounts, contribute to degraded chunk-processing performance (resource-use amplification) rather than direct token theft.

### Likelihood Explanation
Reaching this path only requires a normal user to (a) legitimately add many access keys / gas keys / contract-data entries to their own account (each backed by storage staking, so it costs NEAR to grow), and (b) then submit one ordinary `DeleteAccount` transaction. No validator or node-operator privilege is needed. However, because growing the account's key/data set is not free (it requires paying storage staking proportional to bytes stored, per `check_storage_stake` in `verifier.rs`), the practical degree of amplification an attacker can achieve is bounded by how much NEAR they're willing to lock up beforehand — this is analogous to the "governable/economically-bounded" loops that celo's own team argued were not real vulnerabilities in the source report. This substantially reduces the severity/novelty of the finding.

### Recommendation
Verify whether `ActionCosts::delete_account`'s exec/send fees already account for the number of access keys, gas-key nonces, and contract-data entries removed (e.g., via `storage_removes_compute` referenced in `actions.rs` imports). If they do not, charge gas/compute proportional to the number of trie entries actually iterated and removed in `remove_account`, or impose a hard cap on the number of access keys / contract-data entries an account may hold (independent of storage-staking cost), so that a single `DeleteAccount` receipt cannot perform unbounded work for a fixed fee.

### Proof of Concept
Not independently reproduced; based on static analysis of `remove_account` (`core/store/src/utils/mod.rs:505-575`) and its caller `action_delete_account` (`runtime/runtime/src/actions.rs`). A concrete PoC would: (1) create an account, (2) add a large number of `AddKey` / `TransferToGasKey`(with many nonces) / contract-data-writing `FunctionCall` actions to inflate the access-key and contract-data ranges, funding enough balance to cover storage staking, then (3) submit a single `DeleteAccount` action and measure actual wall-clock/trie-IO cost versus the gas charged for that action.
