### Title
Native-fee swaps in `EvmHost.dispatch`/`fundRequest` use `block.timestamp` as a no-op deadline and never refund unspent ETH, permanently losing user funds to sandwich attacks - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all let a caller pay the Hyperbridge relayer fee in native token by forwarding `msg.value` into `IUniswapV2Router02.swapETHForExactTokens`. All three call sites pass `block.timestamp` as the Uniswap `deadline` argument and discard the function's return value, unlike `IntentGatewayV2.placeOrder`, which captures the `amounts` array and refunds unspent native token to the caller. Compare to the correct pattern used in `IntentGatewayV2.placeOrder`, which captures `amounts[0]` and refunds the excess `msgValue` back to `msg.sender`: [4](#0-3) 

### Finding Description
`swapETHForExactTokens(amountOut, path, to, deadline)` guarantees only that the *tokens out* is fixed (`post.fee`/`get.fee`/`amount`); the *ETH in* is bounded solely by `msg.value` (the implicit `amountInMax`), and any leftover ETH is refunded by the router to whoever called the router — which here is `EvmHost` itself (`to = address(this)`), not the end user.

Two distinct problems follow from this, both stemming from the same "deadline provides no real protection" root cause the external report describes:

1. **`deadline = block.timestamp` is a no-op.** Passing the current block's timestamp as the deadline can never cause the swap to revert on staleness — it always equals "now" at the moment of execution, regardless of how long the transaction sat in the mempool. This is functionally identical to omitting the deadline check entirely, exactly the anti-pattern flagged in the referenced Uniswap V2 Router audit issue.

2. **No slippage/refund handling for the caller.** Because `amounts` (the actual ETH spent) is never read, and because the Uniswap router's leftover-ETH refund lands on `EvmHost`, not on `_msgSender()`, any native token sent above what the swap actually consumes is stuck in the `EvmHost` contract. Combined with (1), an attacker can sandwich the swap: front-run to push the WETH→feeToken price up (increasing the ETH required to satisfy `swapETHForExactTokens`'s fixed `amountOut`), let the victim's `dispatch()`/`fundRequest()` transaction execute (consuming close to the victim's full `msg.value` since there is no protective minimum-out/maximum-in bound the caller controls beyond raw `msg.value`), then back-run to restore the price and extract the difference. Whatever ETH the victim overpaid beyond fair value is not recoverable by them — the router's refund path returns it to `EvmHost`, where it is not credited back to `_msgSender()` anywhere in the function.

This is directly reachable by any unprivileged party dispatching a POST/GET request or funding an existing request with a native-token fee payment — the exact class of "place order"-style, fee-paying transaction the external report is concerned with.

### Impact Explanation
Any unprivileged user who dispatches a POST/GET request or calls `fundRequest` with a native token payment is exposed to value extraction via sandwich attack, and any ETH sent above what the manipulated swap actually consumes is permanently unrecoverable by the user (it accrues silently to the `EvmHost` contract balance rather than being refunded). This is a direct, protocol-level loss of user funds on a maximally exposed, single-transaction, unprivileged code path — the core dispatch entrypoint of Hyperbridge messaging.

### Likelihood Explanation
Every `dispatch()`/`fundRequest()` call that pays fees in native token on any EVM chain with a Uniswap V2-style pool goes through this path. Sandwiching a public mempool transaction against a known AMM pool is a well-established, low-cost, and commonly automated MEV strategy, making exploitation straightforward and not reliant on any privileged position.

### Recommendation
- Accept a caller-supplied `deadline` (or a bounded max staleness window) instead of hardcoding `block.timestamp`, so the Uniswap call can actually revert for stale/delayed execution.
- Capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.
- Consider adding an explicit `amountInMax` parameter (rather than relying on raw `msg.value`) so callers can bound their worst-case slippage precisely, consistent with the documentation's own warning that on-chain use of Uniswap quoting is "vulnerable to sandwich attacks."

### Proof of Concept
1. Attacker monitors the mempool for a `dispatch(DispatchPost)`/`dispatch(DispatchGet)`/`fundRequest` call with `msg.value > 0` on a chain where `_hostParams.uniswapV2` points to a low-liquidity WETH/feeToken pool.
2. Attacker front-runs with a large WETH→feeToken (or opposite direction) swap to shift the pool price so that acquiring `post.fee` feeTokens now requires close to the victim's entire `msg.value`.
3. Victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` — the `block.timestamp` deadline never blocks this execution regardless of the price manipulation, and the call still succeeds because `msg.value` still covers the (now inflated) input requirement.
4. Attacker back-runs to restore the pool price, pocketing the price impact. Any ETH `EvmHost` didn't need for the swap is refunded to `EvmHost` itself by the router (since it is `to`/caller in the swap), not to the victim, so the victim cannot reclaim the difference either way. [1](#0-0)
