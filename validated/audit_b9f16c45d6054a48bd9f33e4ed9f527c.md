### Title
Webhook shop/topic headers not covered by HMAC allow cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw webhook body, while the shop domain, topic, and webhook id used to route and attribute the webhook are taken from unauthenticated HTTP headers. An attacker who legitimately receives one genuine webhook (e.g., by installing the app on their own store) can replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`) headers, and the request will still pass HMAC validation but be attributed to an arbitrary victim shop.

### Finding Description
`Webhooks::Request` extracts the HMAC purely from the `hmac-sha256` header and exposes `to_signable_string` as the raw body only: [1](#0-0) [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no relation to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` and `request.topic` to build the dispatched metadata, without any cross-check that those header values are bound to the signed body: [4](#0-3) 

The equality being broken is: `shop-used-to-verify-HMAC` should equal `shop-attributed-to-the-processed-event`, but the HMAC only binds `raw_body`, so `shop header` and `topic header` can be freely substituted after capturing any one valid `(raw_body, hmac)` pair produced with the same `api_secret_key`. Because every install of a given app shares the same `client_secret`/`api_secret_key`, a webhook that Shopify legitimately sent for attacker's own shop is HMAC-valid for **any** shop value the attacker chooses to put in the `x-shopify-shop-domain` header — the signature says nothing about which shop it belongs to.

### Impact Explanation
This breaks the tenant isolation the app relies on: the webhook handler receives `WebhookMetadata` with a shop identifier that is not actually cryptographically bound to the signed payload. If the host application uses `request.shop` to key data storage/lookups (as documented usage strongly implies, e.g. `ShopifyAPI::Webhooks::Registry.register(session: shop_session)` per-shop model), an attacker who has installed the app on their own store (an ordinary unprivileged action available to any Internet user) can inject attacker-chosen webhook body content while making it appear associated with an arbitrary victim shop, resulting in cross-tenant data corruption/injection — a Critical-class outcome under this program's classification (cross-tenant access).

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged flow for any public app) and be able to send a raw HTTP POST to the app's publicly reachable webhook endpoint — both trivially available to an unprivileged internet user. No access to `api_secret_key`, access tokens, or the victim's data is needed.

### Recommendation
Bind the shop (and ideally topic) to the HMAC-verified content: e.g., include `shop`/`topic` in the signable string that is HMAC-verified, or independently verify the `x-shopify-shop-domain` header against the shop associated with the currently active session/registration before dispatching to the handler, rather than trusting the header value as-is once only the body HMAC has passed.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event on their store (e.g., `orders/create`), and captures the genuine POST Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and raw body `B`.
3. Attacker replays a POST to the same webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the handler with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body `B`, even though this data never came from Shopify for that shop.
