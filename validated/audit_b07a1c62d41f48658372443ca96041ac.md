### Title
Unrestricted `op.endpoint.call` in `EmporiumUpgradeable.runAction`'s stateless branch allows arbitrary calls (e.g., `approve`) that bypass Hinkal's `externalActionMap` and the post-call balance guard - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`Hinkal._externalTransact` only validates that the *outer* action address (`circomData.externalActionData.externalAddress`) matches `externalActionMap[externalActionId]`, but the *inner* `op.endpoint` used inside `EmporiumUpgradeable.runAction`'s "Stateless Interaction" branch is read straight from attacker-supplied `externalActionMetadata` with no allowlist check at all. Because the only post-call safety net (`balanceChange >= 0`) only inspects the ERC-20 balances listed in `circomData.erc20TokenAddresses`, an attacker can point `op.endpoint` at any ERC-20 token and call `approve(attacker, type(uint256).max)` on it - an operation that doesn't move any balance and therefore is invisible to that check - granting themselves unlimited allowance over any token balance Emporium happens to hold.

### Finding Description
The claimed broken equality is: every call executed *as* an external action contract should be constrained to Hinkal's registered `externalActionMap[externalActionId] == externalAddress`, but the nested `op.endpoint.call` inside `EmporiumUpgradeable.runAction` is never checked against any such registry.

Trace:
- `Hinkal._externalTransact` enforces `externalActionMap[circomData.externalActionData.externalActionId] == circomData.externalActionData.externalAddress` [1](#0-0)  and then calls `IExternalActionV2(externalAddress).runAction(...)` [2](#0-1) . This check only binds which top-level action contract Hinkal invokes (e.g., Emporium).
- Once inside `EmporiumUpgradeable.runAction`, the entire `EmporiumStack`/`EmporiumOperation[]` (including each `op.endpoint` and `op.callData`) is decoded directly from `circomData.externalActionData.externalActionMetadata`, a field the attacker fully controls [3](#0-2) .
- For the "Stateless Interaction" branch (`op.invokeWallet == false` or no signer), the only checks are that `op.callData`'s selector isn't `callHinkalWallet`/`doSendToRelay`; `op.endpoint` itself is never checked against `externalActionMap`, `isAllowedRecipient`, or any allowlist before `op.endpoint.call{value: op.value}(op.callData)` is executed with `msg.sender == Emporium` [4](#0-3) .
- The proof/circuit only commits to the fact that `calldataHash == keccak256(...circomData.externalActionData...)` [5](#0-4)  and that this equals the value checked in `performHinkalChecks` [6](#0-5) . This binds the proof to whatever metadata the attacker chose - it does not restrict the *content* of that metadata, since the attacker crafts and proves their own transaction.
- The only safety net after the loop of ops is: `balanceChange = balancesAfter[i] - balancesBefore[i]` (adjusted for the deposit) must be `>= 0`, iterated only over `circomData.erc20TokenAddresses` [7](#0-6) . This check only detects balance *decreases* of listed tokens; it cannot detect an `approve()` call on any token (listed or not), since `approve` does not change `balanceOf`.
- The code's own comment ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") confirms Emporium is expected to be able to hold residual balances across calls [8](#0-7) .

Exploit flow: the attacker crafts `circomData` with `externalActionData.externalActionId` = Emporium's registered id (passes the outer check), and `externalActionMetadata` encoding an `EmporiumStack` whose `ops[0]` is `{endpoint: someERC20Token, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)}`. The attacker generates their own valid proof for this self-crafted data (nothing here requires third-party cooperation), submits the transaction through `Hinkal.transact`. `_externalTransact`'s registry check passes (Emporium is legitimately registered), `runAction` executes the attacker's arbitrary `approve` call as `msg.sender == Emporium`, and the balance check trivially passes since `approve` doesn't move funds. The attacker now holds unlimited `transferFrom` rights over Emporium's balance of that token and can drain any current or future balance Emporium holds for that token in a separate, proof-free transaction.

The originally proposed attacker action of pointing `op.endpoint` at `DepositOnChainUtxosExternalAction` specifically would revert, because that contract's `runAction` is gated by `onlyAllowedRecipient`, which checks `msg.sender` against its own allowlist; `msg.sender` there would be Emporium (not Hinkal), and Emporium is not normally registered as an allowed recipient of that action [9](#0-8) [10](#0-9) . So that exact reproduction fails, but the underlying root cause it identifies (no allowlist on `op.endpoint`) is real and independently exploitable via arbitrary `approve` calls as shown above.

### Impact Explanation
This lets an unprivileged attacker obtain unlimited ERC-20 `transferFrom` allowance over any token balance the Emporium contract holds, and later drain it in a follow-up transaction. This is theft of protocol/Emporium-held funds (dust, fees, or any residual token balances not swept in the same transaction), matching the Critical/High impact categories (theft of funds not authorized by their owner). It is repeatable for every token the Emporium contract ever custodies balance of, at zero cost beyond gas and one attacker-generated proof.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs Emporium to be a registered external action in `Hinkal.externalActionMap` (already the case for a functioning protocol) and needs to craft `externalActionMetadata` themselves, which is explicitly within the threat model (attacker can craft every field of `CircomData`). No privileged role, victim cooperation, or special tree state is required to perform the `approve` call itself. The actual monetary extraction depends on Emporium holding a non-zero balance of the targeted token at the time of `transferFrom` (e.g., protocol fee dust, rounding remainders, or funds left by another user's transaction that hasn't yet completed its final sweep) - this makes realized theft dependent on Emporium's balance conditions, but the approval-planting step itself is always executable regardless.

### Recommendation
Constrain `op.endpoint` in `EmporiumUpgradeable.runAction`'s stateless branch to a maintained allowlist of permitted call targets (e.g., router/hook contracts explicitly approved by governance), reusing or extending the existing `isAllowedRecipient`/allowlist pattern already used for `onlyAllowedRecipient`. Additionally, block dangerous selectors such as `approve`/`increaseAllowance`/`setApprovalForAll` from being invoked on arbitrary ERC-20/721/1155 endpoints unless the endpoint is a pre-approved router, and/or require any allowance granted during `runAction` to be reset to zero before returning.

### Proof of Concept
Foundry plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered under `HINKAL_EMPORIUM_ACTION_ID` in `externalActionMap`), and a mock ERC-20 token; fund Emporium with some balance of that token, or simply let the attacker's own deposit be transferred into Emporium as part of `_externalTransact`'s deposit path (`contracts/Hinkal.sol:250-255`).
2. As the attacker, build an `EmporiumStack` with a single stateless `EmporiumOperation{endpoint: address(mockToken), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)}`.
3. Generate a valid proof for `circomData` using the attacker's own keys/UTXOs, with `externalActionData = {externalAddress: emporiumAddress, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(stack)}`.
4. Call `Hinkal.transact(...)` and assert it succeeds.
5. Assert `mockToken.allowance(emporiumAddress, attacker) == type(uint256).max` even though `attacker` (as `op.endpoint`'s implicit target of approval) was never checked against `externalActionMap` and `op.endpoint` (`mockToken`) is not a registered external action address.
6. In a second, proof-free transaction, call `mockToken.transferFrom(emporiumAddress, attacker, mockToken.balanceOf(emporiumAddress))` and assert it succeeds, demonstrating extraction of funds Emporium held, bypassing the `balanceChange >= 0` guard entirely (since `approve` never altered `balancesBefore`/`balancesAfter`).
