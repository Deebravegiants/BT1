I have sufficient evidence to confirm the vulnerability. The webhook signing scheme in `ShopifyAPI::Webhooks::Request` only covers the raw body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route/attribute the webhook come from unauthenticated HTTP headers.

### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the HMAC-SHA256 signature validated by `Utils::HmacValidator.validate` binds solely to the JSON body of a webhook call. The `shop`, `topic`, `webhook_id`, and `api_version` fields — all of which come from `x-shopify-*`/`shopify-*` HTTP headers — are never included in the signed content, yet `Registry.process` trusts them unconditionally and hands them straight to the app's handler as `WebhookMetadata`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#1-0) 
which returns only the raw body. `shop`, `topic`, `webhook_id`, and `api_version` are all read from headers via `shopify_header`: [2](#1-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which, per `HmacValidator#validate_signature`, only ever verifies `verifiable_query.to_signable_string` (the raw body) against the secret — and then immediately constructs `WebhookMetadata` from the *unverified* header-derived `shop`, `topic`, `webhook_id`, and `api_version`: [3](#1-2) [4](#1-3) 

The identity binding that should hold is: `shop asserted to the handler == shop cryptographically verified by the HMAC`. In reality, only `body == HMAC(body)` is verified; `shop` (and `topic`/`webhook_id`) are asserted bytes that never enter the signature computation. Any party that can produce one valid `(body, hmac)` pair for the app's secret — trivially available to any merchant who has installed the app and received even a single real webhook, since the body for many topics (e.g. `app/uninstalled`, `shop/redact`, or filtered webhooks with only `fields`/`metafieldNamespaces` selected) is fixed or attacker-influenceable — can replay that exact `(raw_body, hmac)` pair while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will accept it as valid and dispatch the handler believing the event originated from the spoofed shop.

### Impact Explanation
This breaks the shop-identity binding documented for webhook handlers: apps are told to trust `data.shop` from `WebhookMetadata` as the authenticated tenant identifier (see `docs/usage/webhooks.md` example using `data.shop` directly for `shop_domain`). Because that value is unauthenticated, a malicious or compromised merchant can forge webhooks attributed to a different shop, achieving cross-tenant confusion in any app logic keyed off `data.shop` (e.g. selecting which tenant's records to update/delete based on the spoofed shop, or bypassing per-shop authorization checks downstream). This lands in the "High" impact bucket for identity-binding breaks (cross-tenant access via an unauthenticated field trusted post-HMAC-check).

### Likelihood Explanation
Likelihood is contingent on an attacker being able to obtain at least one legitimately signed `(body, hmac)` pair — achievable by any developer/merchant who installs the target app on their own store and observes a webhook delivery (or by intercepting their own webhook traffic, which they legitimately receive). No possession of `api_secret_key` or the access token is required; only replay of previously observed signed bytes with a substituted header.

### Recommendation
Bind the shop identity to the cryptographic check: either include `shop`, `topic`, and `webhook_id` in `to_signable_string` so they're covered by the HMAC (matching Shopify's own header-plus-body verification recommendations), or require host applications to independently verify `request.shop` against a known/installed shop list before dispatching to handlers, and document this requirement prominently in `docs/usage/webhooks.md`. At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as trusted solely because the body's HMAC validated.

### Proof of Concept
1. App installs webhook handler trusting `data.shop` (per documented usage in `docs/usage/webhooks.md` lines 19-29).
2. Attacker installs the app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `app/uninstalled` with body `{}` and a valid `x-shopify-hmac-sha256` header computed over `{}`.
3. Attacker replays the exact same raw body `{}` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body/HMAC pair is valid for the shared secret) — see `lib/shopify_api/utils/hmac_validator.rb` lines 13-22 — and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to act on data.shop as if the event genuinely came from the victim shop.
