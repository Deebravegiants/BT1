### Title
Webhook `shop-domain` and `topic` identifiers are not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity by HMAC-verifying only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — read from HTTP headers — are excluded from the signed content and are trusted as-is when dispatched to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Request#hmac` decodes the `hmac-sha256` header [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (the body only) against the app's `api_secret_key`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from unsigned headers — to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . The `shop` accessor is a plain header read with no cryptographic binding to the body or the HMAC [4](#0-3) .

Because a Shopify app's webhook HMAC key (`api_secret_key`) is the same across every shop that installs the app (it is not shop-specific), any merchant who has installed the app can obtain a body+HMAC pair that is valid for the app's secret (e.g., from a webhook triggered by an action on their own store). That merchant can then replay the exact same raw body and HMAC to the app's webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header to name a different, victim shop. `HmacValidator.validate` only checks `hmac == HMAC(secret, raw_body)`, which still succeeds since the body/HMAC pair was never altered — only the unauthenticated header claiming the shop identity was changed. `Registry.process` then dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop [5](#0-4) , even though the signed bytes never bound that shop identity.

This is the identity-binding break called out in scope: "a field acted on but not covered by the HMAC." The equality that should hold — `HMAC-authenticated shop == shop the handler acts on` — is broken because `shop` is parsed from a header entirely outside the signed payload.

### Impact Explanation
Downstream host applications commonly key their session/token lookup and side effects (order sync, inventory updates, fulfillment triggers, data writes) off `WebhookMetadata.shop`. An attacker who is a legitimate merchant on the app can force the app to process a forged event under a different (victim) shop's identity, causing cross-tenant action/data confusion — data written or state changed for a shop that never actually sent that webhook. This matches the "cross-tenant access" Critical impact category, since the tenant boundary (shop identity) that the app relies on this gem to authenticate is not actually authenticated.

### Likelihood Explanation
Exploitation only requires the attacker to be any merchant who has installed the target app (a normal, unprivileged relationship for this threat model) and the ability to send an HTTP POST with modified headers to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or TLS interception is needed, and no host-application misuse of the documented API is required: the gem's own `Registry.process`/`Request` design is what leaves `shop` unauthenticated.

### Recommendation
Include the delivering shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., cross-check against a shop value embedded in the signed body, or require verification through a channel where the shop identity is authenticated, not just header-supplied). At minimum, document that `request.shop` must not be trusted for tenant-authorization decisions without additional verification, and consider incorporating header values into `to_signable_string`.

### Proof of Concept
1. App is installed on Shop A (attacker-controlled) and Shop B (victim), sharing one `api_secret_key`.
2. Attacker triggers a benign event on Shop A that causes Shopify to send a webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)` and `x-shopify-shop-domain: shopA.myshopify.com`.
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: shopB.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers/body [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equals `H`, so validation **passes** [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "shopB.myshopify.com", body: parsed(B), ...)`, causing the app to act on Shop B's tenant context using attacker-supplied content, despite Shop B never sending this webhook.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
