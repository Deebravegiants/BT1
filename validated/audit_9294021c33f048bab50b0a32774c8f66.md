### Title
Access-key allowance refund is credited to any FunctionCall key that reuses a deleted key's public key, silently overriding the account owner's intended spending limit - ([File: runtime/runtime/src/actions.rs])

### Summary
`DirectBuyIssuer`'s bug is that a secondary accounting record (`getOrderEscrow`) is not invalidated when the primary state it depends on (the order) is cancelled/cleared, so a stale, in-flight operation (`takeEscrow`) can later act on the orphaned record and move funds it should no longer be entitled to. The nearcore analog is the `FunctionCallPermission.allowance` refund path: `try_refund_allowance` (`runtime/runtime/src/actions.rs:134-158`) restores allowance to whatever `AccessKey` currently sits at `(account_id, public_key)`, without any check that this is the *same* logical key that earned the refund. If the original key is deleted and a new, more-restricted `FunctionCall` key is added re-using the same public key before the in-flight gas refund lands, the refund silently inflates the *new* key's allowance beyond the limit the account owner just set.

### Finding Description
When a transaction signed with a `FunctionCallPermission` access key finishes executing, `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1230-1365`) emits a gas-refund receipt keyed only by `signer_id` and `signer_public_key` (`runtime/runtime/src/lib.rs:1354-1362`, `Receipt::new_gas_refund`). This refund receipt is delivered later, possibly after several other receipts/blocks, and is applied in `action_transfer_or_implicit_account_creation` (`runtime/runtime/src/lib.rs:2910-2957`), which calls `try_refund_allowance` for gas refunds (`:2936-2943`).

`try_refund_allowance` (`runtime/runtime/src/actions.rs:134-158`) does the following and nothing else:
```
if let Some(mut access_key) = get_access_key(state_update, account_id, public_key)? {
    ... if permission is FunctionCall && allowance.is_some() {
        allowance = allowance.saturating_add(deposit);
    }
}
```
It only checks that *some* access key currently exists at that `(account_id, public_key)` pair and that it has a `FunctionCall` permission with a limited allowance. It performs no check that this is the same `AccessKey` instance (e.g., same `nonce`/generation) that generated the refund. The protocol's own documentation acknowledges the key can be deleted between issuance and refund and calls this "best effort" (`docs/RuntimeSpec/Refunds.md:57-60`), but it never considers the case where the *same public key is subsequently reused* by a brand-new, intentionally more restricted key — this is exactly the "escrow record not cleared on cancellation" pattern: the accounting artifact (pending allowance credit) is not tied to, or invalidated together with, the account-state object (the specific access key) that authorized it.

Sequence mirroring the Sherlock report:
1. Account owner adds `FunctionCall` key `K` with a large allowance and grants it to an app/relayer.
2. The owner submits a large `FunctionCall` transaction with `K`; the transaction consumes a large prepaid-gas amount and the corresponding gas-refund receipt is generated but not yet delivered (it can be delayed by congestion, cross-shard forwarding, or simply queued behind other receipts within the same or later blocks).
3. Before the refund lands, the owner (in good faith) revokes trust from the app: `DeleteKey(K)` then `AddKey` re-adding a **new** `FunctionCall` key with the **same public key** `K` but a small allowance (the owner intends to give the app minimal spending capability going forward).
4. The stale gas-refund for the *old* `K` now arrives and is applied via `try_refund_allowance`, crediting the *new* restricted key's allowance with however much gas was unused/refunded from the old key's transaction — inflating the new key's allowance beyond what the owner explicitly configured.
5. The app, now holding a `FunctionCall` key intentionally capped at a small allowance, can spend well beyond that cap using the injected refund.

### Impact Explanation
This breaks the access-key allowance guarantee described in `core/primitives-core/src/account.rs:889-896`: allowance is supposed to be a hard balance/gas ceiling an account owner sets for a specific, restricted signer. The bug allows a decoupled refund path — analogous to the un-cleared escrow record — to bypass an owner's freshly configured spending limit, letting a third-party/low-trust key holder consume more of the account balance for gas/fees than authorized. This is an "unauthorized balance/gas accounting" issue on the owner's own account: value that should have been inaccessible to the restricted key becomes spendable through it. It does not mint tokens or cross account boundaries, but it does violate the access-control invariant central to `FunctionCallPermission`, which nearcore explicitly treats as a security boundary between an account owner and less-trusted relayers/apps.

### Likelihood Explanation
This requires: (a) a `FunctionCall` access key executing a transaction that leaves unused prepaid gas (extremely common — almost every function call under-uses its gas budget), (b) the account owner deleting and immediately re-adding a key with the same public key but a different (lower) allowance before the refund receipt is delivered. Refund delivery is not instant — it is a new receipt subject to normal receipt-processing ordering, congestion, and cross-shard forwarding delays (`docs/RuntimeSpec/Refunds.md:10`, `protocol-model/spec/runtime-execution.md:96-100`), so there is a real window in which this key-rotation race can occur, especially under network congestion. However, exploiting it for concrete gain requires the account owner (or a colluding party controlling both the old and new key material with intent to under-fund an app) to specifically perform this delete/re-add rotation, which is a narrower scenario than a fully passive attack. This keeps likelihood at low-to-medium rather than trivial/ubiquitous.

### Recommendation
Tie the allowance refund to the specific access-key instance that earned it rather than to the bare `(account_id, public_key)` pair — e.g., include the access key's `nonce` (or a generation counter) in the refund receipt/committed metadata, and in `try_refund_allowance` (`runtime/runtime/src/actions.rs:134-158`) verify the currently stored key's nonce matches before crediting allowance. If it doesn't match (key was deleted/recreated), the refund should be dropped/burnt rather than silently applied to an unrelated key, exactly as the Sherlock fix cleared the escrow record instead of letting a stale reference persist across a state transition.

### Proof of Concept
Conceptual reproduction using existing test infrastructure (`integration-tests/src/tests/standard_cases/mod.rs:1258-1326`, `runtime/runtime/src/actions.rs:134-158`, `runtime/runtime/src/lib.rs:1354-1362`):
1. Create account `alice`; add `FunctionCall` key `K` (public key `pk`) with allowance `1000 NEAR`, `receiver_id = "app.near"`.
2. From `alice`, sign and send a large-prepaid-gas `FunctionCall` transaction to `app.near` using `K`; do not let its gas-refund receipt apply yet (in a real chain this is naturally delayed by receipt processing order/congestion; in a unit test, hold the refund receipt aside instead of feeding it to `apply` immediately).
3. Before applying the refund receipt, submit and apply `DeleteKey(pk)` then `AddKey(pk, FunctionCallPermission{ allowance: Some(1 NEAR), receiver_id: "app.near" })` — the owner's intent is to cap the app to `1 NEAR` going forward.
4. Now apply the previously-held gas-refund receipt (`Receipt::new_gas_refund` targeting `alice`/`pk`) via `try_refund_allowance`.
5. Assert: the new key's allowance is now `1 NEAR + refunded_amount`, exceeding the `1 NEAR` cap the owner explicitly set in step 3 — demonstrating the un-invalidated "escrow" (allowance credit) crossing the state boundary the owner tried to enforce by deleting/recreating the key.
