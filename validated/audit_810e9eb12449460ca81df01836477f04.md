Audit Report

## Title
Unauthenticated `/sessions` login endpoint leaks account-existence via differential error messages - (File: core/sessions/localauth/orm.go)

## Summary
`SessionsController.Create` forwards the raw error from `AuthenticationProvider().CreateSession` verbatim into the HTTP response body via `jsonAPIError`, which calls `err.Error()` when the error is not a `*models.JSONAPIErrors`. The local-auth `CreateSession` implementation returns the raw SQL error (`sql: no rows in result set`) when the email does not exist in the `users` table, but returns the distinct string `"Invalid password"` when the email exists but the password is wrong, letting an unauthenticated caller distinguish valid from invalid emails.

## Finding Description
`SessionsController.Create` binds the request, then calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`; any returned error is passed straight to `jsonAPIError(c, http.StatusUnauthorized, err)`: [1](#0-0) 

`jsonAPIError` serializes `err.Error()` into the JSON body unless the error is already a `*models.JSONAPIErrors`: [2](#0-1) 

In `localauth.orm.CreateSession`, the first step is `FindUser`, which internally runs `SELECT * FROM users WHERE lower(email) = lower($1)` via `sqlx`'s `GetContext` and returns whatever `GetContext` returns — for no matching row this is the underlying `sql.ErrNoRows`-derived error, returned unwrapped: [3](#0-2) [4](#0-3) 

If the user is found, the subsequent password check produces a distinctly worded error instead: [5](#0-4) 

I additionally checked the WebAuthn pre-check in `SessionsController.Create` (`GetUserWebAuthn`), which does not leak — it treats "no rows" as an empty, non-error result — so that call path does not add to the discrepancy, but it does not neutralize the discrepancy present in the subsequent `CreateSession` call. No normalization, generic-error wrapping, or constant-response-shape logic exists between `CreateSession`'s two failure branches and the point where `jsonAPIError` serializes the string, so the two failure modes ("no such user" → raw SQL error text vs. "wrong password" → `"Invalid password"`) produce genuinely different JSON bodies for the same `401` status code.

## Impact Explanation
This produces an account/email-enumeration oracle on the unauthenticated node login endpoint (`POST /sessions`). An attacker with only network access to the node's Operator API can distinguish "email not registered" from "email registered, wrong password" purely from response body content, which aids targeted credential-stuffing, phishing, or brute-force attacks against confirmed real accounts. This maps to CWE-204 (Observable Response Discrepancy) and is a legitimate, if lower-severity, information-disclosure finding — it does not itself grant authentication bypass, secret exfiltration, or fund movement.

## Likelihood Explanation
The endpoint is reachable by any unauthenticated network client without credentials, since `/sessions` is registered outside the authenticated route group and requires no prior access. The discrepancy is present on every single request (not requiring statistical/timing analysis), though per-IP rate limiting (5 requests before a 429) somewhat slows a full enumeration campaign without eliminating it.

## Recommendation
Normalize all `CreateSession` failure paths in `core/sessions/localauth/orm.go` (user-not-found from `FindUser`, email-mismatch, and wrong-password) into a single generic error (e.g., `"invalid credentials"`) before returning to `SessionsController.Create`, and apply the same treatment in the OIDC/LDAP local-login fallback authenticators (`core/sessions/oidcauth/oidc.go`, `core/sessions/ldapauth/ldap.go`) to avoid the same distinguishable-error pattern. Consider also equalizing timing between the two paths if feasible.

## Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@example.com","password":"x"}` on a fresh node — the local-auth `FindUser` query returns no row, `CreateSession` returns that raw SQL error, and the client receives a JSON body containing the raw SQL "no rows" error text via `jsonAPIError`.
2. `POST /sessions` with `{"email":"<real-registered-email>","password":"wrongpassword"}` — `FindUser` succeeds, the password check fails, and the client instead receives a JSON body containing `"Invalid password"`.
3. Comparing the two distinct response bodies (both `401 Unauthorized`) lets an unauthenticated attacker confirm whether `<real-registered-email>` is a registered node user account. This can be verified with a Go integration test against `web.Router` similar to `TestSessions_RateLimited` in `core/web/router_test.go`, asserting the differing `detail` field content between the two request cases.

```go
// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
