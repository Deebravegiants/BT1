### Title
Unbounded interest accrual permanently freezes oversized markets - (File: contracts/pool/src/interest.rs)

### Summary
The pool accrues interest before every market operation but does not cap the resulting indexed value within the `i128` domain. At sufficiently large scaled balances, ordinary compounding eventually causes `scaled_to_original` to return `MathOverflow`; because the same accrual is repeated before recovery operations, the market can never progress again. [1](#0-0) 

### Finding Description
`global_sync` iteratively applies `accrue_chunk` for all elapsed time and each chunk derives the updated utilization and indexes from the live `borrowed`, `supplied`, `borrow_index`, and `supply_index` state. [2](#0-1)  `Cache::calculate_utilization` converts both scaled balances back to original RAY values with `scaled_to_original`, whose multiplication can exceed `i128::MAX`. [3](#0-2) 

An unprivileged market participant can construct the prerequisite state through the controller: supply liquidity with `supply`, post collateral, and borrow at sustained high utilization with `borrow`. [4](#0-3)  After enough elapsed time, a permissionless controller `update_indexes` call reaches `pool_update_indexes_call`, which invokes the pool's `update_indexes`. [5](#0-4) 

The pool endpoint then loads the market and calls `interest::global_sync` before committing. [6](#0-5)  Once the overflow boundary is crossed, this call fails before `last_timestamp` is updated, so subsequent calls retry the same overflowing accrual rather than making progress. [7](#0-6) 

The issue is not limited to `update_indexes`: borrow accounting calls `ops::load_leg` before minting debt, repay accounting calls `ops::load_leg` before resolving repayment, and withdraw accounting does the same before resolving the withdrawal. [8](#0-7) [9](#0-8) [10](#0-9)  Consequently, repayment, withdrawal, liquidation-related settlement, and further index synchronization all hit the same permanent overflow.

### Impact Explanation
All funds and debt positions tied to the affected `(hub_id, asset)` market become permanently frozen. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot restore solvency, and the protocol cannot accrue or settle the market's revenue.

This is stronger than an ordinary fail-closed input rejection: the protocol first accepts the large, valid supply and borrow positions, then deterministic interest accumulation creates an unreachable domain boundary. The existing regression test explicitly observes that the index cap does not engage first and that both withdrawal and repayment subsequently fail with `MathOverflow`. [11](#0-10) 

### Likelihood Explanation
Exploitation requires a very large market balance and enough time for the borrow index to push the scaled value beyond the `i128` ceiling. Those requirements reduce practical likelihood, but no privileged access, malformed input, third-party oracle manipulation, or implementation-dependent token behavior is needed.

Once caps admit a sufficiently large market, the transition is deterministic and cannot be interrupted by recapitalization or repayment because those paths also accrue first. The existing test demonstrates a reachable configuration at 98% utilization and confirms the market freezes before `MAX_BORROW_INDEX_RAY` is reached. [12](#0-11) 

### Recommendation
Enforce an explicit value-domain invariant below the overflow point instead of relying on the borrow-index cap:

- Bound admitted market size so `borrowed * borrow_index` and `supplied * supply_index` cannot reach `i128::MAX` at the maximum permitted index.
- During supply and borrow, check the projected accrual ceiling, not merely the current indexed value and market cap.
- During accrual, clamp or reject before calculating utilization when a scaled total multiplied by its index would exceed the representable domain.
- Prefer an explicit market halt or index saturation state that still permits repayments, withdrawals, liquidation, and bad-debt settlement.
- Add a regression test asserting that crossing the projected value ceiling cannot disable all recovery paths.

### Proof of Concept
The repository already contains a deterministic proof in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

1. Create an 18-decimal market and supply `1_000_000_000 * 10^18` base units.
2. Supply sufficient separate collateral.
3. Borrow 98% of the market.
4. Advance ledger time and repeatedly call `update_indexes`.
5. The accrual eventually fails with `MathOverflow` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`.
6. A subsequent withdrawal and repayment both fail with the same `MathOverflow`, demonstrating that the overflowed accrual permanently blocks recovery. [12](#0-11)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
