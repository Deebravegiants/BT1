## Analysis Summary

The strongest reachable analog is in Shopify's webhook processing pipeline: the HMAC signature only binds the request **body**, while `shop`, `topic`, `webhook_id`, and `api_version` are read from **unauthenticated HTTP headers** and passed straight to application webhook handlers without being covered by the same signature.

### Title
Webhook shop/topic/metadata fields are trusted from unsigned headers while only the body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC computed by `Utils::HmacValidator` binds solely to the payload bytes. However, `Registry.process` forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all parsed from headers outside the signed material — directly into the handler's `WebhookMetadata`, which the merchant-facing application uses as the tenant/topic identity for the event.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac-sha256` header value. [1](#0-0) 
For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 
Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never part of the signed string: [3](#0-2) 
`Registry.process` validates only the body/HMAC pairing, then uses the unauthenticated `shop` header to build the metadata object handed to the app's business logic: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, but the gem only enforces `hmac == HMAC(secret, body)`. Because `Context.api_secret_key` is a single, app-wide secret shared across every merchant install (not per-shop), any unprivileged internet user who installs the app on their own (even free/dev) store legitimately receives real webhook deliveries with valid HMACs for bodies they fully control. They can then replay that exact `body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop, and `Registry.process` will accept it as authentic — because the header content is never checked against the signature.

### Impact Explanation
This breaks the tenant-authentication boundary: an attacker-controlled webhook body gets attributed to another merchant's shop and processed by the app's handler as if Shopify sent it for that shop. Depending on how the host app uses `WebhookMetadata#shop`/`#body` (e.g., updating shop-scoped records, triggering shop-scoped side effects, or feeding into further Admin API calls using the victim's stored session), this can lead to cross-tenant data corruption or unauthorized actions performed under another merchant's identity — a cross-tenant access impact.

### Likelihood Explanation
Moderate-to-high: no special privileges beyond a free Shopify partner/dev store are needed to obtain a genuinely valid (body, HMAC) pair, and the webhook endpoint is typically a public, internet-reachable URL. The only skill required is scripting an HTTP replay with a modified `shop-domain` header, which is unauthenticated header data by design.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material actually verified, or otherwise cryptographically tie the `shop-domain` header to a value the app already trusts for that delivery (e.g., cross-check `request.shop` against the shop stored for the session/webhook subscription owning `webhook_id`, verified via a signed Admin API lookup) rather than trusting it as attacker-supplied header data merely because the body happened to carry a valid HMAC from the shared app secret.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app registers for (e.g., `orders/create`) to receive a real Shopify-delivered request with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Replay this exact request to the app's public webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as an authentic event from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
