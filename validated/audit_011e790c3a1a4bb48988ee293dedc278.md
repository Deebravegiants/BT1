### Title
Blacklist/pausable-token beneficiary permanently DoSes multi-token escrow withdrawal in IntentGateway `_withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The Lavarage finding centers on failing to consider that an accepted collateral token can have an authority (SPL freeze authority) that renders an account holding that token permanently unusable, deadlocking funds that a protocol otherwise assumes are always transferable. `IntentGateway`/`IntentsBase` in this repo accepts **arbitrary, user-specified ERC20 tokens** as order inputs/outputs with no allow-list or check on token behavior, and its escrow-release path performs a direct, unguarded `safeTransfer` to the beneficiary for every token in the order inside a single loop.

### Finding Description
`_withdraw` iterates over all tokens tied to an order commitment and unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one: [1](#0-0) 

ERC20 tokens commonly used as collateral/escrow assets (USDC, USDT, and many other compliance-gated or pausable tokens) can place any address — including the escrow beneficiary — on a blacklist, or can be globally paused by their issuer. This is functionally identical to the SPL "freeze authority" described in the referenced report: an authority external to the protocol can render a specific account's transfers permanently reverting, with no way for the protocol to work around it. Nothing in `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` validates or restricts which ERC20 addresses can be used as `Order.inputs`/`Order.output.assets`, and there is no per-token try/catch or partial-success handling in `_withdraw`.

Because the loop is a single all-or-nothing transaction, if *any one* of the multiple escrowed tokens in an order reverts on transfer to the beneficiary (frozen/blacklisted/paused), the entire `_withdraw` call reverts — including the `_filled[commitment]` finalize write, the fee release, and event emission. The failure is not confined to the problematic token; it blocks release of *every other, otherwise-transferable token* in the same order as well, and since `_filled`/escrow accounting for that commitment is never advanced, the order can never be finalized as long as the blacklist condition persists (which, per SPL/ERC20 compliance semantics, can be indefinite).

This is reachable directly by an unprivileged user: any user can call `placeOrder` with a token in `inputs`/`output.assets` chosen so that the beneficiary (which the user or a malicious counterpart controls/knows) is later blacklisted by the token issuer, or by simply using a token whose issuer subsequently blacklists the beneficiary address for unrelated reasons. A malicious solver could also intentionally craft output using a token, expecting the fill to complete, then have the beneficiary blacklisted (or self-blacklist as a griefing vector against the counterpart) to strand escrow.

### Impact Explanation
Permanent freezing of escrowed user/solver funds: if a beneficiary of a `RedeemEscrow`/`RefundEscrow`/fill withdrawal becomes blacklisted for one of the tokens in the order, the entire withdrawal path becomes permanently un-executable, and all escrowed tokens for that commitment (not just the frozen one) become stuck in the `IntentGateway` contract. This matches the judge's assessment in the referenced report: rare but avoidable, and causes real fund loss/lockup for a specific order/beneficiary combination, with a blast radius that can include otherwise-healthy tokens bundled in the same order.

### Likelihood Explanation
Low-to-moderate likelihood but fully attacker/beneficiary-independent — it does not require any privileged role, malicious admin, or off-chain compromise. Widely used stablecoins (USDC, USDT) implement blacklisting, and pausable ERC20s are common; a beneficiary address ending up blacklisted (compliance action, sanctions, prior unrelated activity) is a realistic real-world event, and a solver picking a beneficiary address that later gets blacklisted is entirely plausible in a live cross-chain intents market. The report's own precedent (confirmed Medium severity by Lavarage/C4 judge) supports treating this class as Medium given "avoidable" per-token isolation is missing.

### Recommendation
- In `_withdraw`, isolate each token transfer so a single reverting/blacklisted token cannot block release of the others: use a low-level `call` with try/catch semantics per token (or a pull-based claim pattern), and if a transfer fails, leave that specific token's balance escrowed/claimable later instead of reverting the whole finalize step.
- Decouple `_filled`/fee-release finalization from the per-token transfer loop so bookkeeping updates (marking the order filled, releasing fees) are not blocked by an individual stuck transfer.
- Consider an explicit "stuck funds" recovery path (e.g., a separate `claim(token, commitment)` function) so a beneficiary who becomes unblacklisted later, or an alternate recipient, can still retrieve escrowed balances without needing all other tokens in the order to also succeed.
- Document/consider an allow-list or risk assessment for tokens accepted into intents orders, similar to the SPL recommendation of rejecting tokens with active freeze/blacklist authority, if full permissionless token support is not required.

### Proof of Concept
1. User places a same-chain order via `placeOrder` (or cross-chain via `IntrinsicIntents`) with `Order.inputs` containing two tokens: `TokenA` (blacklist-capable, e.g., mock USDC-style token) and `TokenB` (plain ERC20).
2. A solver fills the order; `_withdraw` is invoked (directly for same-chain, or via `onAccept`/`RedeemEscrow` for cross-chain) with `beneficiary` = solver address.
3. Before withdrawal executes, `TokenA`'s issuer blacklists the solver's beneficiary address (simulate with a mock token whose `transfer`/`transferFrom` reverts for a blacklisted address, mirroring real USDC-style blacklist behavior).
4. Call `_withdraw`: the loop reaches `TokenA` and `safeTransfer` reverts due to the blacklist check, reverting the entire transaction.
5. Result: `TokenB`, which had no issue, is also never delivered to the beneficiary, `_filled[commitment]` is never set, and the accumulated transaction fee is never released — all escrow for this commitment is permanently stuck as long as the beneficiary remains blacklisted for `TokenA`, exactly mirroring the freeze-authority DoS pattern described in the referenced report.     /**
     * @dev Releases escrowed tokens to a beneficiary. Iterates over the withdrawal request's
     * token list, decrements the escrow balance for each, and transfers tokens out.
     *
     * When `finalize` is true, the order is marked as filled in the `_filled` mapping,
     * any accumulated transaction fees (in the protocol fee token) are forwarded to the
     * beneficiary, and the appropriate event (EscrowReleased or EscrowRefunded) is emitted.
     *
     * When `finalize` is false (partial fills), only the proportional token amounts are
     * released without finalizing the order.
     *
     * @param body The withdrawal request containing the commitment, token amounts, and beneficiary.
     * @param isRefund If true, emits EscrowRefunded instead of EscrowReleased on finalization.
     * @param finalize If true, marks the order as complete and releases accumulated fees.
     */
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
