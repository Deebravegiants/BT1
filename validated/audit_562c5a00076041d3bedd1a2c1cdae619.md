### Title
Webhook shop/topic/version identity headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's handler as trusted identity/routing data are read straight from HTTP headers that are excluded from the signed material. This breaks the identity binding `HMAC(body) verified == shop/topic that the app acts on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are parsed directly from headers, independent of the HMAC: [2](#0-1) 

`Registry.process` verifies the HMAC and, if it passes, immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler — none of these fields are cross-checked against anything bound to the HMAC: [3](#0-2) 

The underlying `HmacValidator.validate` call only ever operates on `verifiable_query.to_signable_string`, i.e. the body bytes: [4](#0-3) 

Because the signature only binds the body, any two webhook deliveries carrying the same body (e.g., an empty-body test webhook, or two shops that happen to receive structurally identical payloads for the same topic) produce interchangeable, mutually valid `(body, hmac)` pairs. An attacker who legitimately receives a genuine Shopify webhook delivery (for example, by installing the app on a shop they control) can capture that valid `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it to the same endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header for a different, victim shop domain. `Registry.process` still finds the HMAC valid (it only checks the body) and forwards a `WebhookMetadata` claiming the event came from the victim shop, breaking the equality `shop authenticated by HMAC == shop delivered to the handler`.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem lets the caller's webhook handler act on a `shop` value that was never actually authenticated by the signature, only the body bytes were. A host application that (reasonably, given the gem's API) trusts `WebhookMetadata#shop` to scope side effects (writing shop-scoped data, invalidating shop-scoped caches, triggering shop-scoped billing/notification logic, etc.) can be made to attribute attacker-controlled webhook bodies to an arbitrary victim shop domain, i.e., cross-tenant confusion/injection of forged events under another merchant's identity.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one genuine `(body, hmac)` pair, which is straightforward for any actor who can install the app on a shop they control (or trigger any webhook whose body content they can predict/control, e.g., certain low-entropy or app-uninstalled-style payloads). No access to `api_secret_key` or any merchant credential is needed to perform the replay — only header manipulation on the HTTP request to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material, or otherwise verify them out-of-band (e.g., look up the expected shop for the topic and require it to match the shop that installed the corresponding webhook subscription) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. App installs webhook subscriptions and receives a genuine delivery for shop `attacker.myshopify.com`, topic `app/uninstalled`, body `{}` (a body shape common enough to be predictable), with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-"{}">`.
2. Attacker replays a POST to the app's webhook endpoint with the same raw body `{}` and the same valid `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body` per `request.rb:35-38` / `hmac_validator.rb:26-31`.
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(... shop: "victim.myshopify.com" ...))`, per `registry.rb:198-199`, causing the app to process a forged event as if it originated from `victim.myshopify.com`.
