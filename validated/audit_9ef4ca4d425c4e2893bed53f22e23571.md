### Title
Cross-tenant webhook forgery: `shop-domain` header is not covered by the HMAC in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only after `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature it checks covers only the raw request body — never the `shop-domain` (tenant) header that the same request carries and that gets handed to the app's webhook handler as the authenticated shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`#hmac` is read from the `hmac-sha256` header and `#shop` is read independently from the `shop-domain` header, with no cryptographic relationship between the two: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header — it never touches `shop`: [3](#0-2) 

`Registry.process` treats a valid HMAC as sufficient authentication for the whole request, then forwards the **unauthenticated** `request.shop` value straight into the tenant-scoped `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's `client_secret` (`Context.api_secret_key`) is shared across **every** shop that installs the app, any unprivileged user who installs the same (possibly free/public) app on their own store legitimately receives webhook deliveries with a valid `(raw_body, hmac)` pair signed with that same shared secret. That attacker can then POST the app's public webhook endpoint directly (bypassing Shopify's delivery infra entirely — nothing about this gem restricts the HTTP source of the request) reusing their own legitimate `raw_body`/`hmac-sha256` pair, but substituting an arbitrary `shop-domain` header value (e.g., a victim's shop). `HmacValidator.validate` still passes, because it never checked `shop`, and `Registry.process` will invoke the handler with `data.shop == "victim-shop.myshopify.com"` even though the signed bytes never attested to that shop.

This breaks the identity binding: `shop asserted by HMAC (∅, not included in signable string) ≠ shop used to select tenant context (Request#shop, from an unauthenticated header)`.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` (the officially exposed, documented field for handlers, per `lib/shopify_api/webhooks/webhook_handler.rb`) to select or scope tenant data will process attacker-controlled payloads under a victim shop's identity. Depending on the handler this enables cross-tenant data corruption/injection (e.g., writing forged order/product/customer updates against a shop that never sent them), which matches the "cross-tenant access" Critical impact category, without requiring any credential, token or `api_secret_key` knowledge beyond an app the attacker is legitimately allowed to install for themselves.

### Likelihood Explanation
Any internet user can install a public/free app on their own development or trial store to obtain legitimate `(raw_body, hmac)` pairs, then send raw HTTP POSTs directly to the app's exposed webhook endpoint (webhook endpoints are ordinary public HTTP routes, not restricted to Shopify's IP ranges by this gem). No secrets, tokens, or privileged access are required — only the ability to become an installer of the target app, which is the baseline "unprivileged internet user" capability for public apps.

### Recommendation
Bind the shop identity into the verified material instead of trusting it as a bare header:
- Do not treat `Request#shop` as authenticated by `HmacValidator.validate` alone; require the host application to independently confirm the shop is a known/installed tenant (e.g., look up a stored session/offline token for that shop) before acting on webhook data — the docs should call this out explicitly as a required step.
- Alternatively, when feasible, incorporate the `shop-domain` (and `topic`/`webhook-id`) header values into the signable string validated in `Utils::HmacValidator`/`VerifiableQuery`, or provide a variant of `HmacValidator.validate` that also demands the shop belongs to a set of authenticated shops known to the app before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving genuine webhook deliveries signed with the app's shared `client_secret`, e.g. body `raw_body` and header `shopify-hmac-sha256: <valid hmac>`.
2. Attacker replays this exact `raw_body` and `hmac-sha256` value directly to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` instead of their own shop.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which succeeds because it only checks the raw body against the shared secret.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [6](#0-5) , causing the app to process attacker-supplied data under the victim's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
