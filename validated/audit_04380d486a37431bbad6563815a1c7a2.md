Webhook `shop`/`topic` values are trusted from unauthenticated HTTP headers while HMAC only covers the raw body — ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the webhook's raw request body via `Utils::HmacValidator.validate(request)`, but the `shop` and `topic` values used to route and label the event are read directly from HTTP headers that are never included in that HMAC computation.

### Finding Description
`Webhooks::Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` are pulled from the `shopify-shop-domain` / `shopify-topic` (or `x-shopify-*`) headers, which are completely separate from the signed body: [2](#0-1) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) 

The identity binding that should hold is: `hmac_signed_bytes == bytes_the_application_acts_on`. Here, the bytes verified (raw JSON body only) are not equal to the bytes acted on for tenant attribution (`shop` header) and event routing (`topic` header). This is the same class of bug as the report's disparity between the bytes verified and the shop/session key actually acted on — a field (`shop`, `topic`) that is used to make security-relevant decisions but is not covered by the same authentication check that gates the request.

Because the header values are attacker-controllable independent of the HMAC-protected body, an attacker who can replay or relay a single previously-observed legitimate webhook body/HMAC pair (e.g., captured from network logs, a shared proxy, a leaky log, or a webhook the attacker's own shop received, since HMAC key is the app's global `client_secret`, identical for every shop) can resubmit that body with the `shop`/`topic` headers rewritten to a different value. `Registry.process` will still consider the HMAC valid (body unchanged) and will hand the modified `shop`/`topic` metadata to the handler, causing the application to attribute the webhook payload to the wrong shop/topic combination.

### Impact Explanation
This does not, by itself, leak an access token or bypass OAuth — access tokens are never present in the webhook payload. However, it breaks a tenant-identity binding relied upon by every consuming application: the `shop` field in `WebhookMetadata` is documented as trustworthy and typically used to look up the merchant's stored session/access token to act on their behalf (`docs/usage/webhooks.md` shows apps dispatching background jobs keyed on `data.shop`). If a host app uses this unauthenticated `shop` value to select which merchant's session/access token to load and act with, this bug allows cross-tenant confusion — data intended for shop A being applied under shop B's identity — which is a cross-tenant boundary violation stemming directly from a gap in this gem's own signature coverage, not from host-app misuse of a documented contract.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one valid `(raw_body, hmac)` pair for the shared `client_secret` (e.g. their own shop's or an intercepted webhook), and to be able to POST to the app's public webhook endpoint with modified headers. Because `client_secret` is per-app (not per-shop), an attacker with a developer/test store connected to the same app can legitimately obtain valid signed bodies and then replay them with a forged `shop` header pointed at another tenant. This is a realistic, unprivileged-attacker scenario that does not require compromising the app's secret.

### Recommendation
Include the shop domain and topic (and ideally webhook id / timestamp) in the HMAC-signed payload verification, or otherwise cryptographically bind these header values to the signed body before trusting them for routing/attribution. At minimum, the gem should document and/or enforce that `shop`/`topic` headers cannot be trusted independently of the body HMAC, and should provide a signable representation of `Request` that incorporates these values so `HmacValidator.validate` protects the full set of security-relevant fields, not just the JSON body.

### Proof of Concept
1. Attacker's own store (or any store connected to the target app) triggers a legitimate webhook, e.g. `orders/create`, and the attacker captures the raw POST: body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`, and `client_secret` is shared across all shops of the app).
2. Attacker replays this exact request to the app's webhook endpoint, keeping `B` and `H` unchanged but replacing the `shopify-shop-domain` header with `victim-shop.myshopify.com` (and/or the `shopify-topic` header with a different topic the app handles).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `to_signable_string` still returns `B`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and finds it equal to `H` — validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: forged_topic, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's handler with this attacker-controlled shop attribution, even though the payload never actually originated from `victim-shop`. [3](#0-2)
