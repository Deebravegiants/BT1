**Analysis:**

The mempool's `get_batch` function tracks selected transactions in a `HashSet<(AccountAddress, ReplayProtector)>` and separately in an `exclude_transactions: BTreeMap<TransactionSummary, TransactionInProgress>` keyed by `TransactionSummary` (which embeds the full `ReplayProtector` enum, not just a bare number). Since `ReplayProtector::SequenceNumber(n)` and `ReplayProtector::Nonce(n)` are distinct enum variants, they never collide as map/set keys, even with the same numeric value [1](#0-0) .

The premise of "one logical transaction" being double-counted across variants doesn't hold: a `SequenceNumber` transaction and a `Nonce` transaction for the same sender are two genuinely distinct `SignedTransaction` objects, each independently signed by the account owner. Nothing in `get_batch` or `add_txn` allows an unprivileged third party to cause one payload to be counted twice under two different replay-protector identities — the sender must sign each transaction separately, and the signature commits to the specific `ReplayProtector` value embedded in the raw transaction [2](#0-1) .

The existing test `test_transaction_ordering_seqnos_and_nonces` confirms the intended/expected behavior: an account can have both sequence-number and nonce transactions coexist in mempool and be selected into the same block, because Aptos supports "orderless" (nonce-based) transactions alongside legacy sequence-number transactions as two independently valid submission mechanisms for the same account, not as aliases for a single logical transaction [3](#0-2) .

Since both transactions require the account owner's own valid signature to enter mempool in the first place, this scenario needs the pre-existing authority of the account owner (or someone who already compromised their key) — it does not let an unprivileged attacker cross a custody boundary to move, mint, burn, or freeze another party's assets. The two transactions executing in the same block is by design (a normal case of a user submitting two independent transfers), not corruption of the batch result.

fn test_transaction_ordering_seqnos_and_nonces() {
