### Title
Infinite-loop denial of service in GRANDPA ancestry-chain traversal via attacker-crafted circular header set - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks backwards from a target header to a base header purely by following each header's self-declared `parent_hash` field, with no cycle detection. The header set it walks (`finality_proof.unknown_headers` / `votes_ancestries`) is attacker-supplied data submitted as part of a GRANDPA consensus update, and the walk executes *before* the GRANDPA justification signatures are verified. A relayer can therefore submit two or more crafted headers whose `parent_hash` fields point at each other, forming a cycle that never reaches the required `base`/`from` hash, causing the traversal to loop forever (or until node resources are exhausted) without ever needing a valid signature.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

The loop condition is only `current_hash != base`; there is no visited-set / cycle check, so if the header map contains a cycle that does not pass through `base`, `current_hash` oscillates among the cycle members forever, and `route` (a `Vec`) grows without bound.

This function is invoked by `verify_grandpa_finality_proof`, which builds the `AncestryChain` directly from attacker-supplied `finality_proof.unknown_headers` and calls `.ancestry()` **before** the justification is cryptographically verified: [2](#0-1) 

Specifically, `headers.ancestry(from, target.hash())` at line 88 runs prior to `justification.verify(...)` at line 91-93. Since `target` and `base` are picked by `max_by_key`/`min_by_key` over the attacker-controlled `unknown_headers` list, and each header's hash is simply the hash of its self-declared contents (`h.hash()`), an attacker can construct two headers H1/H2 where `H1.parent_hash = hash(H2)` and `H2.parent_hash = hash(H1)`, forming a genuine cycle keyed correctly in the `BTreeMap`. As long as this cycle does not include `from` (the trusted `consensus_state.latest_hash`), the ancestry walk never terminates.

This is reached through the permissionless consensus-update path: `GrandpaConsensusClient::verify_consensus` decodes the submitted `ConsensusMessage` and calls `verify_parachain_headers_with_grandpa_finality_proof` → `verify_grandpa_finality_proof`, without any prior structural/cycle validation of `unknown_headers`: [3](#0-2) 

Consensus updates in `pallet-ismp` are dispatched as unsigned extrinsics (`handle_unsigned`), whose `ValidateUnsigned` implementation performs only structural/priority checks, not cryptographic verification of the payload before it reaches `verify_consensus`: [4](#0-3) 

This is directly analogous to CVE-2023-35933 (OpenFGA): in both cases, a graph/ancestry traversal that walks a relationship structure supplied by an untrusted caller has no cycle protection, and a circular definition drives the traversal into an unbounded loop, producing a denial of service.

### Impact Explanation
A single relayer, without needing any valid GRANDPA signatures, can submit a consensus update containing a crafted circular header ancestry. The affected node (light client / parachain runtime / full node executing `handle_unsigned`) will hang in an unbounded loop while executing `headers.ancestry(...)`, consuming CPU and unboundedly growing memory (`route: Vec<H::Hash>`) until the process stalls or is OOM-killed. Because this runs inside block execution (via the unsigned extrinsic dispatch), it can stall consensus-update processing for the affected client/state machine, effectively freezing the relevant Hyperbridge route until the runtime/node is patched or restarted — a route-unable-to-deliver-messages condition, which is one of the accepted high/medium-severity outcomes.

### Likelihood Explanation
The header hash is self-computed from attacker-supplied header contents, so constructing a two-header (or larger) cycle is trivial and requires no privileged access — only the ability to submit an ISMP consensus-update message, which any relayer/permissionless actor can do. The vulnerable ancestry walk executes before signature verification, so the attack requires no valid GRANDPA authority signatures at all, making exploitation straightforward and reachable from a single submitted message.

### Recommendation
Add cycle detection to `AncestryChain::ancestry` (e.g., track visited hashes in a `BTreeSet` and bound the number of steps to `unknown_headers.len()`), returning an error such as `NotDescendent`/a new `CyclicAncestry` error once a hash is revisited or the step count exceeds the header-set size. Additionally, validate that `unknown_headers` forms a well-formed, acyclic chain (each header's computed hash used at most once as a `parent_hash` target) before performing any traversal, and consider moving justification signature verification ahead of ancestry computation where feasible.

### Proof of Concept
1. Craft two `SubstrateHeader` values H1 and H2 (arbitrary but well-formed) such that `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()`.
2. Set `H1.number` to be the maximum, `H2.number` to be the minimum, so they are selected as `target` and `base` respectively by `verify_grandpa_finality_proof` (or, similarly, use `votes_ancestries` for `GrandpaJustification::verify_with_voter_set`).
3. Build a `FinalityProof { block: H1.hash(), justification: <any bytes decodable as a GrandpaJustification, need not be valid>, unknown_headers: vec![H1, H2] }`.
4. Submit this as the proof payload to `GrandpaConsensusClient::verify_consensus` via the ISMP unsigned consensus-update extrinsic, with `consensus_state.latest_hash` set to any hash other than `H1.hash()`/`H2.hash()`.
5. Execution enters `headers.ancestry(from, target.hash())`, which loops indefinitely between H1 and H2 since neither equals `from`, hanging the executing node/runtime — reproducible with the existing `AncestryChain` unit-test harness (`modules/consensus/grandpa/primitives/src/justification.rs` test module) by constructing this cyclic header pair instead of the acyclic chain used in `test_ancestry_route`.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
