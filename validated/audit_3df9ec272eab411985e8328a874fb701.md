This confirms the vulnerability: `HmacValidator.validate` only ever signs/verifies `to_signable_string`, and for `Webhooks::Request` that method returns solely `@raw_body` [1](#0-0) , while `shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate_signature` computes the signature only over `verifiable_query.to_signable_string` [3](#0-2) , so the shop-domain header is never bound to the HMAC. `Registry.process` then forwards this unauthenticated `request.shop` value straight into `WebhookMetadata` used by the app's handler for tenant identification [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant identification from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The shop-domain header is never part of the signed bytes, so it can be modified without invalidating the HMAC.

### Finding Description
The intended identity binding is: `shop asserted in webhook == shop whose secret produced the HMAC`. In practice:
- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the body) [5](#0-4) .
- `Request#shop` is read straight from the header with no cryptographic binding to the HMAC [2](#0-1) .
- `Registry.process` validates only the HMAC, then immediately trusts `request.shop` for dispatch to the app's handler as the tenant identifier [4](#0-3) .

Because the HMAC is computed over the body only, an attacker who owns any legitimate Shopify store can capture a real webhook delivery (valid body + valid HMAC, both generated by Shopify using the app's real secret for the attacker's own shop) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, yet `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-chosen) body belongs to the victim shop.

### Impact Explanation
This breaks the binding "shop verified by HMAC" == "shop acted upon by the handler," enabling cross-tenant data injection: an app's webhook handler will process attacker-controlled body content as if it originated from the victim's shop (e.g., updating records, triggering side effects, or writing to the wrong tenant's session/store keyed by `shop`). This matches the Critical "cross-tenant access" impact category, since tenant isolation guaranteed by webhook authenticity is bypassed.

### Likelihood Explanation
Likelihood is high for any attacker who is themselves a legitimate, unprivileged merchant/app installer: they can generate arbitrary webhook bodies with genuine Shopify-issued HMACs for their own shop (by performing normal store actions), then replay the request to the target app's public webhook endpoint with a forged `shopify-shop-domain` header. No access token, `client_secret`, or privileged access is required — only the ability to receive one's own webhooks and replay HTTP requests.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or otherwise cryptographically bind the asserted `shop` header to the HMAC-covered body before trusting it for tenant routing. At minimum, `Registry.process`/`WebhookMetadata` should not treat the header-derived `shop` as authenticated unless it is cross-checked against a value that was actually covered by the HMAC.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and installs the target app, so Shopify legitimately sends webhooks to the app's endpoint signed with the app's real secret for the attacker's shop, e.g. `POST /webhooks` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body the attacker controls (e.g. via editing a product they own).
2. Attacker captures this request and resends it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= raw_body`) only — validation passes because the body was not modified.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the forged `shop` value and dispatches it to the app's handler, which now processes attacker-chosen content under `victim-shop.myshopify.com`'s identity [4](#0-3) .
