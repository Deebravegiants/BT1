### Title
Cost model under-accounts allocated-accounts-data-size for CPI-based `CreateAccount`/`Allocate`, allowing `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` to be bypassed - (File: cost-model/src/cost_model.rs)

### Summary
`CostModel::calculate_allocated_accounts_data_size` only walks top-level instructions via `transaction.program_instructions_iter()` / `SVMStaticMessage` iteration and pattern-matches on `SystemInstruction` variants encoded directly in those top-level instructions. A transaction whose top-level instruction invokes a custom program that internally CPIs into `system_instruction::create_account`/`allocate` is not inspected, so the declared allocation is `0` even though real account data growth occurs during execution.

### Finding Description
`CostModel::calculate_transaction_cost` computes `allocated_accounts_data_size` by calling `Self::calculate_allocated_accounts_data_size(instructions, feature_set)` where `instructions` is `transaction.program_instructions_iter()` [1](#0-0) . This is used both for the pre-execution estimate path (`calculate_cost`/`estimate_cost`) and for the **post-execution** path `calculate_cost_for_executed_transaction`, which is invoked from `get_transaction_costs` in `runtime/src/transaction_execution.rs` after the transaction has actually run, feeding `check_block_cost_limits` which enforces `CostTracker::try_add` and the `allocated_data_size` limit (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) [2](#0-1) [3](#0-2) .

Critically, even though `calculate_cost_for_executed_transaction` receives real post-execution values for `actual_programs_execution_cost` and `actual_loaded_accounts_data_size_bytes`, it still recomputes `allocated_accounts_data_size` by re-scanning only the static top-level `program_instructions_iter()` [4](#0-3) . The instruction inspection function `calculate_account_data_size_on_deserialized_system_instruction` only recognizes `SystemInstruction` variants when the top-level instruction's program id is the system program and its data deserializes to one of `CreateAccount`, `CreateAccountWithSeed`, `Allocate`, `AllocateWithSeed`, or (feature-gated) `CreateAccountAllowPrefund` [5](#0-4) . There is no traversal into inner/CPI instructions recorded by the SVM invocation stack, so any account allocation performed by a custom BPF program that CPIs into the System Program is invisible to this accounting, both pre- and post-execution.

This confirms the cost-tracker's `allocated_data_size` limit (default `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000` bytes, `cost-model/src/block_cost_limits.rs:37`) can be systematically under-counted: an attacker submits a top-level instruction to a wrapper BPF program (no ComputeBudget allocation instruction needed to trigger this specific gap) that CPIs `CreateAccount`/`Allocate` with large `space`. The declared `allocated_accounts_data_size` for that instruction is `0`, while the real allocation happens during CPI execution inside the SVM and is charged nowhere in this specific metric.

### Impact Explanation
This allows an attacker to grow account data within a block beyond the `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` accounting ceiling that the cost tracker is meant to enforce, since the tracker's admission check (`CostTracker::try_add`, `cost-model/src/cost_tracker.rs:188-193`) relies entirely on the declared/estimated value which the CPI path evades. This matches the stated bounty category: compute-budget/cost-model accounting charging materially less than real resource consumption, potentially exhausting block/account-data capacity without being reflected in the cost/fee accounting used for block admission.

### Likelihood Explanation
This requires no privileged access — any user can deploy or use an existing BPF program that CPIs `system_instruction::create_account`/`allocate`, and submit a top-level transaction invoking it via a public RPC/TPU endpoint. It is fully repeatable per transaction and does not require staked/leader/gossip control, matching the "unprivileged attacker" threat model. Feasibility is high because CPI-based account creation is an extremely common Solana pattern (e.g., PDA creation via `invoke_signed` wrapping `create_account`), so this is not an obscure edge case.

However, whether this constitutes a *practically exploitable* denial-of-capacity or merely a mis-accounted metric depends on whether `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` is the only enforcement point for total accounts-data growth, or whether the bank additionally enforces a hard cap using actual `accounts_data_len_delta` computed from `accounts_resize_delta` after commit (as seen updating `update_accounts_data_size_delta_on_chain` in `runtime/src/bank.rs:4419-4430`). That mechanism tracks the *global* accounts data size (a separate, real, post-execution-derived accounting), and it is unclear from what was inspected whether it also enforces a hard per-block delta cap independent of the cost-tracker's `allocated_data_size` limit. If it does, the actual security impact of bypassing `CostTracker`'s pre-admission estimate may be limited to scheduling/prioritization effects rather than an unbounded real-resource bypass, and further investigation of `update_accounts_data_size_delta_on_chain` and any associated global limit check would be needed to fully confirm severity.

### Recommendation
Extend `CostModel::calculate_account_data_size_on_instruction` (or its post-execution counterpart) to account for accounts allocated via CPI by using the actual `accounts_resize_delta` / accounts-data-size delta recorded by the SVM during transaction execution (already computed and available via `processed_tx.execution_details().accounts_deltas` in `runtime/src/bank.rs:4419-4429`) instead of, or in addition to, static top-level instruction inspection, at least for the post-execution `calculate_cost_for_executed_transaction` path that feeds the cost tracker's block-level `allocated_data_size` enforcement.

### Proof of Concept
Rust integration test plan (in `cost-model/src/cost_model.rs` or a bank-integration test crate):
1. Deploy a minimal BPF program `wrapper_program` whose instruction handler performs `invoke_signed`/`invoke` of `system_instruction::create_account` with a large `space` (e.g., near `MAX_PERMITTED_DATA_LENGTH`) for a PDA it controls.
2. Build a transaction with a single top-level instruction invoking `wrapper_program`, no ComputeBudget allocation instruction.
3. Call `CostModel::calculate_allocated_accounts_data_size(sanitized_tx.program_instructions_iter(), &FeatureSet::all_enabled())` and assert it returns `0`.
4. Execute the transaction against a `Bank` (via `bank.process_transaction` or SVM batch processor), then read the actual account data size created (e.g., via `bank.get_account(&pda).unwrap().data().len()` or `accounts_resize_delta` in the commit result execution details).
5. Assert: `real_allocated_bytes > 0` while `CostModel`-declared `allocated_accounts_data_size == 0`, demonstrating `COST_UPPER_BOUND` (declared ≥ actual) invariant failure.

    fn calculate_account_data_size_on_deserialized_system_instruction(
        instruction: SystemInstruction,
        feature_set: &FeatureSet,
    ) -> SystemProgramAccountAllocation {
        let validate_space = |space: u64| {
            if space > MAX_PERMITTED_DATA_LENGTH {
                SystemProgramAccountAllocation::Failed
            } else {
                SystemProgramAccountAllocation::Some(space)
            }
        };

        match instruction {
            SystemInstruction::CreateAccount { space, .. }
            | SystemInstruction::CreateAccountWithSeed { space, .. }
            | SystemInstruction::Allocate { space }
            | SystemInstruction::AllocateWithSeed { space, .. } => validate_space(space),
            SystemInstruction::CreateAccountAllowPrefund { space, .. } => {
                if !feature_set.snapshot().create_account_allow_prefund {
                    return SystemProgramAccountAllocation::Failed;
                }
                validate_space(space)
            }
            // DEVELOPER WARNING: New allocating instructions MUST return `Failed`
            // until activated by a feature gate
            SystemInstruction::Assign { .. }
            | SystemInstruction::Transfer { .. }
            | SystemInstruction::AdvanceNonceAccount
            | SystemInstruction::WithdrawNonceAccount(..)
            | SystemInstruction::InitializeNonceAccount(..)
            | SystemInstruction::AuthorizeNonceAccount(..)
            | SystemInstruction::UpgradeNonceAccount
            | SystemInstruction::AssignWithSeed { .. }
            | SystemInstruction::TransferWithSeed { .. } => SystemProgramAccountAllocation::None,
            // DEVELOPER WARNING: New non-allocating instructions MUST return `Failed`
            // until activated by a feature gate
        } // Do not add wildcard pattern (_)
    }

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
