### Title
Unchecked ERC20 `transfer` Return Value in Intent Gateway Dust-Sweep Leads to Incorrectly Emitted `DustCollected` Accounting - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._execute()` sweeps residual output-token balances from the `CallDispatcher` back to the gateway using a raw, low-level `IERC20.transfer.selector` call routed through `ICallDispatcher.dispatch()`, without ever checking the boolean return value of `transfer()`. The `DustCollected` event is emitted with the pre-transfer `balanceOf(dispatcher)` value *before* the transfer is confirmed to have actually moved funds, and no post-transfer balance verification exists (unlike the analogous `placeOrder`/predispatch-sweep code paths in `IntentGatewayV2.sol`, which explicitly measure `balanceOf` deltas after the sweep).

### Finding Description
In `_execute()` [1](#0-0) , for each non-native output token the code builds a `Call` with `data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` and emits `DustCollected(token, balance)` immediately, then batches all these calls through `CallDispatcher.dispatch()`.

`CallDispatcher.dispatch()` only checks that the low-level `.call` did not revert; it never inspects/decodes the returned `bool` from an ERC20 `transfer()` [2](#0-1) . Per the report's bug class, ERC20 implementations that return `false` on failure (rather than reverting) will make the `.call` "succeed" at the low level while the actual token transfer silently fails.

This is functionally the same unchecked-return-value pattern from the referenced Footium audit finding: the code assumes a non-reverting call implies a successful transfer, and neither `_execute()` nor `CallDispatcher.dispatch()` validates the actual boolean result.

By contrast, the sibling code path in `IntentGatewayV2.placeOrder()` (predispatch sweep) is careful to snapshot balances before dispatch and compute `received = balanceOf(address(this)) - balancesBefore[i]` afterward [3](#0-2) , so a silently-failing `transfer()` there only zeroes out the credited amount — it does not falsely report dust collection. `_execute()`'s sweep has no equivalent post-check: it emits `DustCollected` using the pre-sweep `balanceOf(dispatcher)` snapshot and never re-verifies that the gateway's own balance increased by that amount.

### Impact Explanation
If a non-standard/malicious output token used as an order's output asset returns `false` on `transfer()` failure instead of reverting (e.g., paused token, blacklist-style token, or one with insufficient allowance/balance edge cases triggered via reentrant calldata), the `DustCollected` event would report an amount that was never actually swept to the gateway, while the tokens remain stuck in the `CallDispatcher`. This produces an accounting/state inconsistency (misleading dust-collection records and stranded balances in the `CallDispatcher`) rather than a direct fund-theft path, since the gateway's escrow accounting (`_orders[commitment][token]`) is not driven by this emitted value.

### Likelihood Explanation
Likelihood is limited by two factors: (1) it requires an order to specify `output.call` (postdispatch calldata) with a non-standard, silently-failing ERC20 as an output asset, and (2) exploitation depends on token behavior outside the protocol's control (most major ERC20s revert on failure per EIP-20 convention; only edge-case tokens like some deflationary/blacklist tokens return `false`). This is a moderate-likelihood, protocol-hygiene issue rather than a readily-triggerable exploit against standard tokens.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used elsewhere in this codebase, e.g. `IntrinsicIntents.sol`) instead of raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` inside `_execute()`'s sweep-call construction, or add an explicit post-dispatch balance check (mirroring `IntentGatewayV2.placeOrder()`'s pattern) before emitting `DustCollected`, so the event and internal accounting only reflect tokens actually received.

### Proof of Concept
1. Deploy an order whose `output.assets` includes a custom ERC20 token `T` that returns `false` from `transfer()` under some triggerable condition (e.g., token paused mid-transaction via reentrant logic in `order.output.call`, or a blacklist rule against the `CallDispatcher` address) instead of reverting.
2. Solver fills a cross-chain or same-chain order with `output.call` set, causing `_execute()` to run: `ICallDispatcher(dispatcher).dispatch(order.output.call)` executes the postdispatch calldata that triggers the failure condition on `T`.
3. `_execute()` observes `balance = IERC20(T).balanceOf(dispatcher) > 0`, builds the sweep `Call` with a raw `transfer` selector, and emits `DustCollected(T, balance)`.
4. `ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls))` executes; the low-level `.call` to `T.transfer(...)` does not revert (returns `false`) so `CallDispatcher` treats it as `success`.
5. Result: `DustCollected` event falsely reports `balance` tokens collected, but `T`'s balance remains stuck on the `CallDispatcher` contract — no on-chain re-verification catches the discrepancy.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
