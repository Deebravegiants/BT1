### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop-domain` header verbatim when building the `WebhookMetadata` passed to the app's handler. The `shop` value is never included in the signed payload, so the identity of the shop a webhook is attributed to is not cryptographically bound to the signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read directly from the (attacker-suppliable, unauthenticated) HTTP header, entirely outside the signed material: [2](#0-1) 

`Registry.process` verifies only that the body's HMAC is valid, then immediately forwards `request.shop` to the handler with no additional check that this shop is the one whose secret actually produced the signature: [3](#0-2) 

Because a single app-wide `client_secret`/`api_secret_key` is used to sign webhooks for *every* installed shop (multi-tenant secret), any unprivileged internet user who has installed the app on their own shop can obtain a legitimately-signed `(raw_body, hmac)` pair from their own tenant's webhook traffic. Since the shop header is excluded from the signed string, that same `(raw_body, hmac)` pair remains valid when replayed with the `shop-domain`/`x-shopify-shop-domain` header swapped to an arbitrary victim shop domain. `HmacValidator.validate` will still return `true`: [4](#0-3) 

The binding that is broken, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC` (secret-holder that produced the signature, tied only to body bytes) `≠` `shop the gem attributes the webhook to in WebhookMetadata.shop` (taken from an unsigned header).

### Impact Explanation
This is a cross-tenant identity-binding failure: a webhook whose body was legitimately generated for shop A can be replayed and falsely attributed to shop B while still passing HMAC validation. Any handler logic that trusts `WebhookMetadata#shop` to route data updates, deletions, deprovisioning (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`), or billing state to the correct tenant record can be tricked into applying attacker-controlled webhook content against a victim shop's tenant data. This matches the Critical bucket ("cross-tenant access") since it lets one tenant impersonate a webhook event for another tenant without holding the victim's credentials.

### Likelihood Explanation
Requires only: (1) attacker installs the app on their own (attacker-controlled) shop — a normal, unprivileged action for any public app; (2) attacker captures one legitimately-signed webhook request from their own shop (trivial, they control the endpoint or can sniff their own traffic); (3) attacker replays that exact body+hmac to the app's webhook endpoint with a different `shop-domain` header. No access token, `api_secret_key`, or victim credentials are needed. This is straightforward to execute against any app built on this gem's `Webhooks::Registry`.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unauthenticated header:
- Cross-check `request.shop` against the shop of an already-known/authenticated session (e.g., the offline session for that shop) before invoking the handler, rejecting the webhook if no matching installed session exists for that shop.
- Alternatively/additionally, include `shop` (and `topic`, `webhook_id`) in the signable string used for HMAC verification so that tampering with those headers invalidates the signature, matching how `AuthQuery#to_signable_string` binds `shop`, `code`, `host`, `state`, and `timestamp` together for OAuth callbacks: [5](#0-4) 

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining the app's usual webhook traffic for that shop (e.g., an `orders/create` webhook with body `{"id":123, ...}` and header `X-Shopify-Hmac-Sha256: <valid hmac of body>`).
2. Attacker constructs a raw POST request reusing the exact same body and `X-Shopify-Hmac-Sha256` value, but sets:
   - `X-Shopify-Topic: app/uninstalled` (or whichever registered topic they want, as long as it is a topic registered by the app and the body was originally emitted for that topic/shape) 
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. Sends this request to the app's public webhook endpoint.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`: [6](#0-5) 
   This computes HMAC over `to_signable_string` = `@raw_body` only, so it validates successfully regardless of the `shop-domain` header value.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`: [7](#0-6) 
   and acts on `victim-shop.myshopify.com` using attacker-supplied body content, even though the signature only proves the body was signed by the shared app secret — not that it was ever generated for or by the victim shop.
