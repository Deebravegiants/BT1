### Title
Deposit function mints zero shares for rounded-down deposit amounts, causing silent loss of user principal - ([File: mainnet/contracts/vault/v0-vault-usdc.clar], and identical pattern in v0-vault-stx.clar, v0-vault-sbtc.clar, v0-vault-ststx.clar, v0-vault-usdh.clar, v0-vault-ststxbtc.clar)

### Summary
The `deposit` function in all Zest v2 vault contracts computes `inkind` (shares to mint) via `convert-to-shares-preview`, which can round down to `0` for small deposit amounts when the vault has accrued interest (share price > 1). Unlike `redeem`, which explicitly asserts `(> inkind u0) ERR-OUTPUT-ZERO`, `deposit` has no equivalent check on the minted-share output. This lets a user transfer real underlying tokens into the vault while receiving `0` vault shares (`zft`) in return.

### Finding Description
`convert-to-shares-preview` computes shares as `mul-div-down amount ts ta` [1](#0-0) . When `ta` (total-assets, inflated by accrued interest) is greater than `ts` (total-supply), the share price exceeds 1:1, so `amount * ts / ta` can round down to `0` for sufficiently small `amount`.

In `deposit`, the only zero-guards are on the input `amount` (`(asserts! (> amount u0) ERR-AMOUNT-ZERO)`) and on the slippage bound `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`, which trivially passes when `min-out` is `0` (or is left at the default/unspecified value by a naive caller) and `inkind` is also `0`. The function then proceeds to pull the user's underlying tokens (`receive-underlying`) and mint `inkind` (i.e., `0`) shares to the recipient [2](#0-1) .

By contrast, `redeem` explicitly guards against this exact failure mode with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` [3](#0-2) , showing the vault's authors were aware of this rounding-to-zero issue but only mitigated it on the withdrawal side, not the deposit side. This is the same root cause pattern as the external GLM report: a value-conversion helper that legitimately returns `0` for small inputs, paired with a caller that fails to reject a `0` result before transferring the user's principal.

The identity broken is:
```
assets_transferred_in(amount) > 0  ⇒  shares_minted(inkind) should be > 0
```
but the code allows:
```
amount > 0  AND  inkind == 0  →  deposit succeeds, user's tokens are custodied, zft supply/backing unaffected
```
This is confirmed identical across `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`, all sharing the same `deposit`/`convert-to-shares-preview` structure [4](#0-3) [5](#0-4) .

### Impact Explanation
A user (or anyone integrating with the vault, e.g. via a bot/contract that doesn't set a nonzero `min-out`) who deposits a sufficiently small `amount` when `total-assets/total-supply` ratio is high enough will have their underlying tokens transferred into the vault and permanently receive zero vault shares. Their principal is irrecoverably lost — it becomes undifferentiated vault backing with no corresponding claim, effectively donated to existing shareholders. This is a permanent freezing/theft of the depositor's principal, fitting the "High" impact tier (theft/permanent freezing of funds for that specific depositor), though each individual loss is bounded by how small a deposit rounds to zero shares (bounded by `ta/ts` ratio).

### Likelihood Explanation
Occurs whenever `ta > ts` (any vault that has accrued any interest so share price > 1) and a depositor supplies a raw `amount` small enough that `amount * ts / ta < 1`, with `min-out` set to `0` (the natural default for a "no slippage protection" caller) so the `ERR-SLIPPAGE` check does not trigger. This requires no privileged access and can be triggered by any unprivileged depositor, intentionally or accidentally (e.g., a naive integration/dust deposit).

### Recommendation
Add an explicit output check to `deposit`, mirroring the existing `redeem` guard, e.g.:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other `asserts!` calls in `deposit`, before `receive-underlying`/`ft-mint?` are executed, across all vault contracts (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Vault accrues interest over time such that `total-assets-preview() = ta` grows larger than `total-supply-preview() = ts` (e.g., `ta = 2 * ts`).
2. A user calls `deposit(amount=1, min-out=0, recipient=user)`.
3. `convert-to-shares-preview(1)` computes `mul-div-down(1, ts, ta)` = `1 * ts / ta` = `0` (integer division rounds down) [1](#0-0) .
4. All `asserts!` in `deposit` pass: `amount(1) > 0` ✓, `inkind(0) >= min-out(0)` ✓, cap check ✓.
5. `receive-underlying(1, account)` pulls the user's 1 unit of underlying token into the vault.
6. `ft-mint? zft 0 recipient` mints zero shares.
7. User has permanently lost their 1 unit of underlying with no corresponding `zft` balance to redeem it back.

```text
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

```text
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))

    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))
```
