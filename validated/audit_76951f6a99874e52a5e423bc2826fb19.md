This confirms the exact analog. This is exactly the same bug class as the Backed Protocol report: an exact-output quote is pre-computed off-chain (`amountIn`) by grossing up a net amount using the **currently observed** `protocolFeeBps`, but the actual protocol fee applied to that same `amountIn` on-chain, at `placeOrder` execution, is read live from `_destinationProtocolFees`/`_params.protocolFeeBps` at whatever value it holds at that later block. If governance increases the fee between the SDK's `quoteIntent()` call and the `placeOrder` transaction landing on-chain, the escrowed `reducedAmount` (and thus the `output.assets` amount the solver is asked to match, and the value actually available to the user) will be smaller than the value the exact-output quote guaranteed — mirroring the original `minLoanAmount` vs. post-fee-received mismatch.

### Title
Exact-output intent quotes gross up input using a stale `protocolFeeBps`, so a governance fee increase between quoting and `placeOrder` under-funds the escrowed order - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`quoteIntent()` in the SDK computes an exact-output order's `amountIn` by grossing up the desired net input with the `protocolFeeBps` read live from the gateway at quote time (`grossUpForProtocolFee`, `readProtocolFeeBps`). The user later submits `placeOrder(order)` with that pre-computed `order.inputs[i].amount`. `IntentGatewayV2.placeOrder` re-reads `protocolFeeBps` (or a destination-specific override) **at execution time** and deducts it from the submitted gross amount to derive `reducedAmount`, which becomes both the escrowed balance and the amount baked into the order commitment that solvers must match.

### Finding Description
The fee used to gross up the quote and the fee used to reduce the escrow are read at two different points in time from the same governance-controlled storage (`_params.protocolFeeBps` / `_destinationProtocolFees`), updated via the `UpdateParams` cross-chain governance message. [1](#0-0)  There is no mechanism to lock the fee rate that was used to build the order, analogous to the original finding's observation that "the only true mitigation... would be to store originationFeeRate in the Loan struct at the time of origination." Here too, the fee rate is not committed to the order at quote/authoring time; it is applied fresh at placement.

The SDK explicitly documents that `amountIn`/`amountOut` from `quoteIntent()` "already account for the IntentGateway protocol fee," and instructs integrators to "use the returned amounts directly... no further fee or slippage adjustment is required." [2](#0-1)  For an exact-output quote, `grossUpForProtocolFee` computes `amountIn` from the desired net amount and the fee rate observed at quote time. [3](#0-2)  The same helper is used across quote strategies (Uniswap V4, Phantom snapshot, indexed rates) to gross up `amountIn` before the order is authored. [2](#0-1) [4](#0-3) 

When `placeOrder` finally executes, it recomputes `protocolFeeBps` from current contract state and derives `reducedAmount = originalAmount - protocolFee`, which is written into escrow and folded into the order commitment that solvers see. [1](#0-0)  If governance raises `protocolFeeBps` (or sets/raises a destination-specific override) between the moment `quoteIntent()`/`grossUpForProtocolFee` executed and the moment `placeOrder` is mined — a normal, non-malicious governance update delivered via the standard `UpdateParams` cross-chain message — the resulting `reducedAmount` will be strictly less than the net amount the exact-output quote promised. The docs' own protocol-fee section reinforces that the escrowed/reduced amount, not the gross input, is "the amount actually escrowed and offered to solvers." [5](#0-4) 

### Impact Explanation
For an exact-output order, the user transfers the full gross `amountIn` computed at quote time, but ends up escrowing (and thus offering solvers, and thus receiving from a solver, since solvers only need to match the escrowed/reduced amount encoded in the commitment) less than the intended net value once a fee increase lands before `placeOrder` executes. This can:
- Silently under-deliver value relative to the quoted/expected `amountOut` for exact-output swaps, since the order's `output.assets` amount is fixed by the user off-chain independent of the actual on-chain fee deduction, while `order.inputs` (from which solvers profit) shrinks — making the order relatively less attractive/profitable for solvers to fill, or in the worst case unprofitable, causing it to go unfilled or expire, permanently costing the user the (non-refundable) protocol fee dust with no swap executed.
- For exact-input orders the effect is smaller (output naturally shrinks proportionally), but the SDK's guarantee that "no further fee or slippage adjustment is required" is invalidated whenever this race occurs, which the Medium-severity original report treated as harmful reliance on a stale rate.

### Likelihood Explanation
This requires no attacker action — any legitimate `UpdateParams` (or per-destination fee override) governance action that happens to land in the window between a client's `quoteIntent()` call and the corresponding `placeOrder` transaction inclusion triggers the mismatch. Given block confirmation delays, mempool latency, and the fact that fee updates are ordinary governance operations (not attacks), this window is realistically reachable in production without any privileged or malicious behavior.

### Recommendation
Bind the order's protocol-fee assumption at authoring time rather than re-deriving it purely from live storage at `placeOrder`. Options include: allow the caller to pass an expected/maximum `protocolFeeBps` (or minimum `reducedAmount`) with `placeOrder` and revert if the live fee exceeds it (an explicit slippage-style guard analogous to `amountOutMin`), or expose a short-lived fee-rate commitment/timelock so quotes remain valid for a bounded window. This mirrors the recommendation from the original report to make the fee-affected amount deterministic and protected against fee changes between the two relevant points in time.

### Proof of Concept
1. Off-chain: call `quoteIntent({ tokenIn, tokenOut, amountOut })`; the SDK reads `protocolFeeBps = X` via `readProtocolFeeBps`/`params()` and returns `amountIn = grossUpForProtocolFee(netAmountFor(amountOut), X)`. [2](#0-1) 
2. User builds `order.inputs[0].amount = amountIn` and submits the `placeOrder` transaction, but it sits in the mempool.
3. Before it is mined, governance dispatches `UpdateParams` raising `protocolFeeBps` to `Y > X` (or sets a destination-specific `destinationFeeBps` override for `order.destination`). [6](#0-5) 
4. `placeOrder` executes: `protocolFee = amountIn * Y / 10_000` (using `Y`, not `X`), so `reducedAmount = amountIn - protocolFee` is smaller than the `netAmountFor(amountOut)` value the quote guaranteed. [7](#0-6) 
5. The order commitment and escrow now reflect the smaller `reducedAmount`; a solver filling per the commitment gives the user only the originally-specified `output.assets` amount regardless (since output is independent), but the order is less profitable for solvers than priced, at the cost of the (non-refundable) extra protocol fee taken from the user's escrowed input — a direct, non-malicious-admin-caused value mismatch matching the reported bug class.

/** Conservatively grosses a net amount up so protocol-fee deduction cannot leave it short. */
export function grossUpForProtocolFee(netAmount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return netAmount
	if (protocolFeeBps >= BPS_DENOMINATOR) throw new Error("protocolFeeBps must be less than 10,000")
	return divCeil(netAmount * BPS_DENOMINATOR, BPS_DENOMINATOR - protocolFeeBps)
}

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
