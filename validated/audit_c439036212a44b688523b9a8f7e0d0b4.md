### Title
Unbounded rounding-loss accumulation via `Pair.swap`'s `+1` K-slack permanently bricks curve trading with an arithmetic-underflow DoS - ([File: packages/contracts/src/Pair.sol])

### Summary
NanoMQ's CVE-2024-42650 is a crash triggered by feeding a malformed but protocol-legal PUBLISH message through code that assumes well-formed inputs, causing an unhandled fault that permanently denies service. The structural analog in alt.fun is a sequence of fully protocol-legal, unprivileged buy/sell calls that exploit the permissive `+1` slack in `Pair.swap`'s K-invariant check to erode the pair's *real* `tokenReserve * assetReserve` product below the frozen `k` with zero trading fee to offset the loss, until a later legitimate `Router._computeBuy`/`_computeSell` call underflows and reverts unconditionally — permanently bricking that token's bonding-curve pair.

### Finding Description
`Router` explicitly documents itself as fee-free: *"AMM math for bonding-curve pairs. No fees here — Zap handles fees."* [1](#0-0) . Every buy/sell quote is computed via floor division against the immutable `k` set once at `Pair.mint`:

```
newReserveAsset = reserveAsset + amountInUsed;
tokensOut = reserveToken - (k / newReserveAsset);
``` [2](#0-1) 

and symmetrically for sells:
```
newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [3](#0-2) 

Because `k / x` is floor division, setting `newTokenReserve = floor(k / newReserveAsset)` makes the *actual* post-trade product `newTokenReserve * newReserveAsset <= k`, i.e. every single trade can shave real backing off the pool. `Pair.swap`'s invariant check only enforces the padded bound, not the true product:

```
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
``` [4](#0-3) 

The `+1` padding on both sides is exactly large enough to always absorb the floor-rounding loss from `_computeBuy`/`_computeSell` (`floor(k/x)*x >= k - x + 1`, so `(floor(k/x)+1)*x > k`), so the check never blocks a rounding-losing trade. With no trading fee to replenish the lost value (explicitly a design choice per the `Router` NatSpec), each round-trip buy+sell by any unprivileged trader permanently erodes the pair's true `tokenReserve * assetReserve` below `k`. `Pair`'s stored `_pool.tokenReserve`/`_pool.assetReserve` (read via `getReserves()`) drift accordingly [5](#0-4) .

Once the drift is large enough, a later legitimate call to `_computeSell` (or `_computeBuy`) computes `k / newReserveToken` (or `k / newReserveAsset`) larger than the now-eroded `reserveAsset`/`reserveToken`, and the subtraction underflows, causing an unconditional arithmetic-panic revert. Since `buy`/`sell`/`getAmountOut` in `Router` and `Bonding.buy`/`Bonding.sell` all route through these same two internal functions, this bricks the curve entirely for that token: no one can buy, no one can sell, and `canGraduate`/`triggerGraduation` (which also reads `getReserves()`) can be pushed into the same broken arithmetic path, permanently trapping the LT and tokens already inside the curve `Pair` — funds belonging to every trader still holding a position in that launched token.

### Impact Explanation
This is a permanent freezing of trader/curve funds: once the underflow condition is reached, `Router.buy`/`Router.sell` (and therefore `Bonding.buy`/`Bonding.sell`/`Zap.buy`/`Zap.sell`) revert unconditionally for that pair, with no admin recovery path (`Router` has no repair function, and `graduate()` is gated behind `Bonding`'s own lifecycle logic which reads the same broken reserves). Tokens and LT already committed to the curve become permanently unreachable — a concrete, permanent freezing of funds, matching the required impact bar.

### Likelihood Explanation
Every action needed is a fully permissionless, protocol-legal call: `Zap.buy`/`Zap.sell` (which wrap `Bonding.buy`/`Bonding.sell` → `Router._computeBuy`/`_computeSell`) [6](#0-5) . No special privileges, timing, or oracle manipulation is required — only a sustained sequence of small round-trip trades against a single token's curve, well within reach of any unrelated wallet, particularly against a low-liquidity long-tail launch where `k` is small and rounding loss is proportionally larger per trade.

### Recommendation
Charge a curve-side trading fee (or otherwise round in the protocol's favor on every trade) so the real `tokenReserve * assetReserve` product can never fall below `k`, and/or clamp `_computeBuy`/`_computeSell` to saturate (rather than underflow-revert) when `k / x` would exceed the counterpart reserve, returning a `0`/capped quote instead of reverting. Additionally, tighten `Pair.swap`'s invariant check to bound the true (unpadded) product against `k`, not just the `+1`-padded one, or track drift explicitly and reject swaps that would push the real product further below `k`.

### Proof of Concept
1. Launch a token via `Zap.createToken`, establishing a `Pair` with `_pool.k = totalSupply * virtualLtReserve` [7](#0-6) .
2. Repeatedly call `Zap.buy` followed by `Zap.sell` (any unprivileged wallet) with small amounts. Each round trip: `Router._computeBuy` sets `newTokenReserve = floor(k/newReserveAsset)` [8](#0-7) , losing up to `newReserveAsset - 1` units of real product versus `k`; `Pair.swap`'s `+1` check always passes [4](#0-3) .
3. After enough rounds, query `Pair.getReserves()`/`Pair.k()` and observe `reserveToken * reserveAsset` has drifted meaningfully below `k`.
4. Submit one more `Zap.sell`/`Zap.buy`: `Router._computeSell`/`_computeBuy`'s subtraction (`reserveAsset - k/newReserveToken` or `reserveToken - k/newReserveAsset`) underflows and reverts with an arithmetic panic, and every subsequent buy/sell against that pair reverts identically — the curve is permanently bricked.
