### Title
Webhook shop-domain and topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body (`to_signable_string` returns `@raw_body`), but the `shop`, `topic`, `webhook_id`, and `api_version` fields that `Registry.process` acts on are read directly from unauthenticated HTTP headers. Any attacker who can obtain one genuine `(body, hmac)` pair — trivially possible since anyone can install a public Shopify app on their own store and receive real webhook calls — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain`, `topic`, or `webhook-id` header. `Utils::HmacValidator.validate` will report the signature as valid because it only re-hashes the body, and `Registry.process` will then dispatch the (attacker-controlled) topic/shop combination to the registered handler as if Shopify itself sent it for that shop.

### Finding Description
`lib/shopify_api/utils/hmac_validator.rb`'s `validate` calls `verifiable_query.to_signable_string` and HMACs that string with `Context.api_secret_key`, then does a constant-time compare against the presented `hmac`. For webhooks, `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) is defined as simply:
```ruby
def to_signable_string
  @raw_body
end
```
Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the body or HMAC:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only the HMAC-over-body, then dispatches based on the unauthenticated `request.topic`, and forwards `request.shop` into `WebhookMetadata`, which is the exact identity binding host apps rely on to know which merchant tenant a webhook is for (per `docs/usage/webhooks.md` and `WebhookMetadata` struct in `lib/shopify_api/webhooks/webhook_handler.rb`).

This is the direct analog of the referenced report: a check function (`HmacValidator.validate`) is presented as validating the whole webhook request's authenticity, but the actual bytes it verifies (`raw_body`) do not cover the bytes the application acts on (`shop`, `topic`, `webhook_id`). The binding that should hold — `hmac_signed_fields == fields_used_for_dispatch/tenant_attribution` — is broken.

### Impact Explanation
This allows cross-tenant confusion: an attacker who legitimately installs the target app on their own store (a normal, unprivileged action) can capture one valid `(raw_body, hmac)` pair from a real webhook Shopify sends them, then replay it against the app's public webhook endpoint with a forged `shopify-shop-domain` header naming a victim shop and/or a forged `shopify-topic` header naming a more sensitive topic (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`) than the one the body was actually generated for. Since the HMAC never covered these fields, the request passes validation, and the app's handler executes business logic attributing the (attacker's own, but replayable) body content to the victim shop. This meets the High-severity bar (scope/expiry-style check bypass across tenant boundaries) because the shop/topic identity check is answered permissively relative to what's actually authenticated.

### Likelihood Explanation
Any developer using this gem's public webhook API (`ShopifyAPI::Webhooks::Registry.process`) as documented is affected; there is no non-default mitigation applied automatically by the gem. The prerequisite (obtaining one legitimate signed webhook body) is trivial for anyone who can install the target app on a store they control, which is inherent to how Shopify apps work and requires no privileged credentials, TLS interception, or social engineering.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so `Registry.process` cannot be made to attribute a validly-signed body to an arbitrary shop or topic. At minimum, apps should be prevented from trusting `request.shop`/`request.topic` unless they are covered by the same signature that authenticates the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's real `client_secret`.
2. Attacker sends a new POST request to the app's public webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: customers/data_request`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true`, because it only recomputes HMAC over `@raw_body`, which is unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` dispatches to the handler registered for the forged topic, passing `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` — data the app's handler will act on as if Shopify itself attested this webhook belongs to the victim shop.
