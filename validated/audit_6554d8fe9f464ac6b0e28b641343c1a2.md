### Title
Webhook processing trusts unauthenticated `shop-domain`/`topic`/`webhook_id` headers that are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then forwards the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are included in the signed content — to the app's webhook handler as trusted, tenant-identifying data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` gates on this body-only HMAC and then immediately trusts the header-derived `shop`, `topic`, `webhook_id`, and `api_version` to build the metadata passed to the app's handler: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers, with no cross-check against the signed body or any other value: [4](#0-3) 

The `api_secret_key` used to compute this HMAC is the app's single `client_secret`, shared across every shop that has the app installed — it is not shop-specific. Consequently `HMAC(secret, raw_body)` only proves "this body was signed by an entity that possesses the app's client secret" (i.e., Shopify, on behalf of *any* shop with the app installed); it proves nothing about *which* shop the webhook is for. The identity binding the gem should enforce is:

`shop header used by the handler to attribute/act on the payload == shop that actually produced the signed body`

but the gem only enforces `HMAC(secret, body) == received_hmac`, leaving `shop` (and `topic`/`webhook_id`) completely unauthenticated. An unprivileged party who legitimately installs the same public app on their own shop can capture a validly-signed `(raw_body, hmac-sha256)` pair from a real webhook Shopify sends them, then replay that exact body/HMAC to the victim app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim shop. `Utils::HmacValidator.validate` still passes (it never looks at headers), and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant boundary violation: the host application's webhook handler (built on the documented `data.shop` field) will process attacker-supplied body content while believing it is scoped to a different, victim tenant. Depending on the handler's use of `data.shop` (looking up the shop's stored access token, updating shop-scoped records, etc.), this enables cross-tenant data corruption/confusion or misuse of another merchant's stored credentials/session, which falls under the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any actor who can install the target app on a shop they control (a normal, unprivileged flow for public apps) can trigger a genuine webhook delivery for themselves, capture the resulting `(body, hmac)` pair, and replay it with forged shop/topic headers to the shared webhook endpoint. No access to the app's `client_secret`, an access token, or a privileged account is required — only the ability to receive one legitimately signed webhook from their own store, which is inherent to installing any public app.

### Recommendation
Bind the header-derived `shop` (and ideally `topic`/`webhook_id`) into the authenticated content, or otherwise cryptographically tie them to the signed body, before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, cross-check the header `shop` against an independently verified value (e.g., look up the shop by installed session/access token rather than trusting the header verbatim) before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged onboarding).
2. Shopify sends the attacker a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC-SHA256(client_secret, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays `B`/`H` unmodified to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC-SHA256(client_secret, B)`, which still equals `H` since only the body is signed, so validation succeeds.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act on attacker-controlled data as if it originated from the victim shop.
