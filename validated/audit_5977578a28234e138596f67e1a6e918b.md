### Title
Cross-tenant webhook confusion via unauthenticated `shop-domain` header replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using `Utils::HmacValidator.validate(request)`, but the HMAC only covers the raw request body — never the `shop` identity that the handler ultimately trusts and acts on. This mirrors the report's bug class: a field acted upon (`shop`) is not bound by the same integrity check that authenticates the request (HMAC), so the two "sides" (verified bytes vs. trusted identity) can be made to disagree, exactly like the vesting contract checking one state while acting on another.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 
`hmac` is derived from the `X-Shopify-Hmac-Sha256` header, and `to_signable_string` returns only `@raw_body`: [2](#0-1) 
Meanwhile `shop` is read straight from the `X-Shopify-Shop-Domain` header, a field that is never included in the signable string: [3](#0-2) 

`Registry.process` validates the HMAC and then hands `request.shop` directly to the handler as the tenant identifier, with no separate check binding it to the signed payload: [4](#0-3) 

The identity-binding equality this breaks is:
`hmac-authenticated bytes (raw_body) == identity acted upon (shop header)` — the check authenticates the former but the latter is what host apps use to resolve per-tenant sessions/access tokens (as documented and expected in `docs/usage/webhooks.md`): [5](#0-4) 

Because a merchant that has installed the app is an unprivileged party with respect to *other* merchants of the same app, they can capture one of their own legitimate webhook deliveries (raw body + valid `X-Shopify-Hmac-Sha256`, computed with the app's shared `client_secret` that the merchant never sees but that Shopify attaches identically regardless of which shop the app instance serves) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still succeed, since it only checks the body signature, and `Registry.process` will invoke the handler with an attacker-chosen `shop`.

### Impact Explanation
Because `WebhookMetadata.shop` is the sole tenant-identity signal passed to host application handlers (per the gem's documented contract) and it is not covered by the HMAC, a request with a genuinely valid signature can be attributed to a shop the attacker does not own. Any host application that uses `data.shop` to key its per-tenant lookups (session/access-token retrieval, background job dispatch keyed by shop, etc.) — the exact pattern the gem's own docs recommend — will process the payload for the spoofed shop. Since webhook payloads (e.g. `orders/create`, `customers/update`) can carry data influenced by the sender, this enables cross-tenant data injection/attribution: an attacker's own webhook content is processed as if it originated from a victim shop, corrupting per-tenant state or triggering privileged per-tenant actions (e.g., a job that fetches the victim's stored access token and acts using their credentials) under attacker control. This matches the "cross-tenant access" impact bucket.

### Likelihood Explanation
Any actor who can get any real webhook delivered to their own installed app instance (e.g. simply performing an action in their own store that triggers a subscribed topic) obtains a valid `(raw_body, hmac)` pair. Replaying it with a modified `X-Shopify-Shop-Domain` header requires no secrets, no privileged access, and no cryptographic break — only a plain HTTP POST to the app's public webhook endpoint. The gem provides no mechanism (and the docs show no guidance) to cross-check the header-derived `shop` against anything cryptographically bound to the request.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or require the host application to independently corroborate the `shop-domain` header against an out-of-band trusted source (e.g. cross-check against the shop associated with the webhook subscription that was registered, since Shopify does not sign this header). At minimum, document prominently that `data.shop` is unauthenticated and must not be used alone to key per-tenant secrets/actions without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and registers for `orders/create`.
2. Attacker triggers an order creation, causing Shopify to POST a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` over the raw JSON body and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures the exact raw body bytes and the `X-Shopify-Hmac-Sha256` value.
4. Attacker replays the identical body and HMAC header to the app's public webhook URL, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC key — see `lib/shopify_api/webhooks/request.rb` line 36-38 (`to_signable_string` returns `@raw_body` only, no `shop`).
6. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"` even though the payload originated from the attacker's own store, at `lib/shopify_api/webhooks/registry.rb` lines 198-199.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
