## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` for webhook HMAC validation, but its `to_signable_string` returns only the raw request body, not the headers. The `shop` (and `topic`, `webhook_id`, `api_version`) values used downstream to attribute the webhook to a tenant are read directly from HTTP headers that are never included in the signed material.

### Finding Description
`Registry.process` validates a webhook solely via: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is just `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never fed into `to_signable_string` and thus are not covered by the HMAC signature at all: [4](#0-3) 

The identity binding this breaks is: `HMAC-verified content == content acted upon`. Here, `bytes verified` (the raw body) ≠ `bytes parsed for tenant attribution` (the `x-shopify-shop-domain` header). `process` trusts `request.shop` to attribute the payload to a specific merchant/tenant when dispatching to the registered handler, even though that field carries zero cryptographic binding to the signed body: [5](#0-4) 

### Impact Explanation
An attacker who can obtain one valid `(raw_body, hmac)` pair signed by Shopify for the app's `client_secret` (e.g., by triggering an event on a shop they control that has this app installed, or otherwise causing/observing a legitimate webhook delivery for any shop) can replay that exact `raw_body`+`hmac-sha256` header pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different, victim tenant. `HmacValidator.validate` will pass because the body and HMAC are untouched, and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop`, causing the host application's handler to process/store attacker-supplied data as if it belonged to the victim tenant. This is a cross-tenant identity confusion at the gem's own validation boundary, directly analogous to the reported bug class (a field acted upon — tenant/shop binding — that is not covered by the verification the code relies on).

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain one valid signed webhook body for the target app (trivial for any developer/merchant with the app installed on their own store, since webhook topics like `orders/create`, `app/uninstalled`, etc. are attacker-triggerable), and being able to replay/craft the HTTP request to the app's public webhook endpoint with a modified header — no `client_secret`, access token, or TLS interception is required. This only requires normal internet-reachable POST access to the app's webhook route plus a self-triggered legitimate webhook, which is a realistic unprivileged-attacker scenario.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise verify the header-provided `shop` against a trusted, out-of-band source before using it. Concretely, `Webhooks::Request#to_signable_string` should not be the sole trust anchor for `shop`/`topic`; the gem should document/require verifying `shop` returned from `process`/`WebhookMetadata` against the session/store the app expects for that endpoint, or Shopify's HMAC computation should be extended (as Shopify's own webhook verification recommends) to only trust `shop` after confirming it corresponds to a shop with an active, previously-established app installation/session — never solely from the unauthenticated header.

### Proof of Concept
1. App has a legitimate shop, `attacker-shop.myshopify.com`, install the app there.
2. Trigger any webhook event (e.g., update a product) so Shopify sends a legitimately HMAC-signed webhook: `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Capture this request, then POST the same `raw_body = B` and same `x-shopify-hmac-sha256` header to the app's webhook endpoint again, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and any topic string for a handler that identifies data by `shop`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since it only checks `B` against the unchanged HMAC: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled `B` as if it originated from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
