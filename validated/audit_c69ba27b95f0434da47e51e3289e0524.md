### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the body bytes, never the `shop` (i.e. `X-Shopify-Shop-Domain` / `shopify-shop-domain`) header that `Registry.process` later trusts and hands to the app's webhook handler as an authenticated tenant identifier.

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [2](#0-1) . For webhook requests, `to_signable_string` is defined to be just `@raw_body` [1](#0-0) , while `shop` is read straight from an HTTP header with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` validates only that the HMAC over the body is valid, then forwards `request.shop` unchanged into `WebhookMetadata`, which is passed to the app-supplied handler as the identified tenant for that event [4](#0-3) . `WebhookMetadata#shop` is documented as "The shop domain of the webhook" and is the field host apps use to route/attribute the webhook payload to a specific merchant [5](#0-4) , and the docs explicitly tell integrators to key their processing off `data.shop` [6](#0-5) .

The broken identity binding, as an equality: `shop authenticated (bytes covered by HMAC) == shop acted upon (header trusted by Registry.process)` is false — the HMAC only binds the raw body, not the header.

Because the app's `api_secret_key` is shared across every shop that installs the app (it is the app's client secret, not a per-shop secret), any shop that has legitimately installed the app receives real webhooks whose HMAC is computed with that same shared secret over the body only. An attacker who controls one legitimate/free shop installation of the app can capture one of their own genuine webhook deliveries (valid `raw_body` + valid `hmac`), then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (body/HMAC pair is untouched), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain instead of the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce: an attacker with a legitimate (their own) installation can make the app believe body content (e.g., an `orders/create` or `customers/data_request` payload under their control) belongs to a different merchant's store. Any host app that follows the documented pattern of using `data.shop` to select the tenant's DB/record to update (as directly encouraged in `docs/usage/webhooks.md`) can be tricked into writing, deleting, or otherwise processing data under a victim shop's identity — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Requires only: (1) the attacker have their own real installation of the target app (unprivileged, self-service, not requiring `api_secret_key`, tokens, or any credential theft), and (2) capture one legitimate webhook delivery to their own endpoint (trivial, since it is delivered to infrastructure they control). No secrets need to be known or brute-forced, since the HMAC/body pair is reused verbatim; only the header is altered. This is the same bug class as the referenced report — a value used to make a security-relevant decision (there: goroutine channel state; here: tenant identity) that isn't actually protected/consistent with the check that gates the action (there: length check race; here: HMAC signature scope).

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC signable string for webhooks, the same way `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signature [7](#0-6) , or otherwise cryptographically bind the `shop` header to the signed payload before trusting it in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body B, computed with the app's shared api_secret_key>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: B
   ```
2. Attacker replays the identical body `B` and identical `X-Shopify-Hmac-Sha256` value, but changes only the header:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...X-Shopify-Shop-Domain: "victim.myshopify.com"...})` is constructed by the host app and passed to `Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `B`, unaffected by the header change [8](#0-7) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`, so any handler logic keyed on `data.shop` operates as if this attacker-controlled payload belongs to `victim.myshopify.com` [4](#0-3) .

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
