### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the tenant identity, with no cryptographic binding between the two.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate`/`validate_signature` compute and compare the signature strictly against `verifiable_query.to_signable_string`, i.e. the body only: [2](#0-1) . The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a completely separate, unsigned channel: [3](#0-2) .

`Registry.process` checks `Utils::HmacValidator.validate(request)` (body-only check) and, once it passes, forwards `request.shop` unchanged into `WebhookMetadata` that is delivered to the app's handler: [4](#0-3) .

The identity binding that should hold is:
`shop value the HMAC authenticates == shop value the handler treats as the tenant`

But because the HMAC covers only `@raw_body` and the `shop` field is taken from an unauthenticated header, the equality is broken: **HMAC-authenticated bytes (body) ≠ bytes used to select tenant (header)**. Any request whose body/HMAC pair is valid for the app's secret — regardless of which shop that pair originally belonged to — passes `HmacValidator.validate` unconditionally of the `shop-domain` header value, since that header plays no role in the signature computation.

### Impact Explanation
This breaks tenant isolation: a request carrying a body+HMAC pair that is authentic for shop A can be replayed to the same webhook endpoint with the `shop-domain` header rewritten to shop B. `Registry.process` will still pass HMAC validation (it never inspects the header) and will invoke the handler with `shop: "B"`, causing the app to process attacker-influenced webhook data under a victim tenant's identity — a cross-tenant access condition. This maps to the Critical "cross-tenant access" impact category, since the gem's own validation logic is the root cause of the missing binding, not a host-application decision.

### Likelihood Explanation
Any unprivileged internet user can install the target app on their own development/test store and thereby legitimately trigger the app to receive at least one genuinely Shopify-signed webhook (body + HMAC) for a topic the app has registered. That signed pair can then be replayed directly to the app's public webhook HTTP endpoint with an arbitrary `shop-domain` header, since nothing in `ShopifyAPI::Webhooks::Request` or `HmacValidator` ties the header to the signed body. No access token, `api_secret_key`, TLS interception, or privileged account is required — only network access to the webhook endpoint and a single legitimately obtained signed payload.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the signable content, or otherwise cryptographically verify that the claimed `shop-domain` corresponds to the shop the HMAC was actually generated for (e.g., look up the expected shop from stored webhook/session state rather than trusting the header), before invoking the registered handler.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Install the target app on attacker-owned store `attacker.myshopify.com`, trigger an `orders/create` event, and capture the resulting raw body and its genuine `x-shopify-hmac-sha256` value (this is a legitimately signed pair, since the attacker is a real merchant of their own store).
3. Send a forged HTTP POST directly to the app's webhook endpoint:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <hmac captured from attacker's own store>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: forged-id

<raw body captured from attacker's own store>
```
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `@raw_body` (matches the captured HMAC).
5. The handler executes with `data.shop == "victim-shop.myshopify.com"`, even though the payload and signature actually originated from the attacker's own store, demonstrating the cross-tenant identity binding failure.
