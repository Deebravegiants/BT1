Based on my research, I found a genuine analog vulnerability in the graduation LP-seeding path that has not been defended against — unlike the extensively-tested hostile-mint-pre-seed (Regime 3), the honest "empty-pair" happy path (Regime 1, ~99% of graduations) has **no floor guard** against a dust-sized `(tokensForLP, ltFromPair)` pair, which is exactly the shape the CVE's "hang or crash / complete DOS" class maps onto here: a permanently unrecoverable, brickable state.

### Title
Dust-sized graduation LP mint can permanently brick `finalizeGraduation` via HyperSwap V2's `MINIMUM_LIQUIDITY` floor - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._seedDirectMint` (the Regime-1 happy path used by ~99% of graduations, per `packages/contracts/AGENTS.md`) transfers `tokensForLP` and `ltFromPair` straight to a fresh HyperSwap V2 pair and calls `IUniswapV2Pair(pair).mint(lpLock)` [1](#0-0) . Standard UniswapV2 `mint()` computes `liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` and reverts with `INSUFFICIENT_LIQUIDITY_MINTED` when this underflows/equals zero. Unlike Regime 3 (the hostile-mint-pre-seed path), which was hardened with a `_swapBudget` 1%-reserve guarantee specifically because a zero-liquidity mint would brick `LPLock.recordLock` forever, Regime 1 has no such floor check on `(tokensForLP, ltFromPair)` themselves.

### Finding Description
Graduation can be reached with an arbitrarily small `ltFromPair` because the USD trigger fires as soon as `realLtRaised × exchangeRate() ≥ graduationThresholdUsd` [2](#0-1) . If `exchangeRate()` is large relative to the threshold (e.g. a high-leverage/high-price LT, or one whose rate has appreciated significantly since launch), a trivially small `realLtRaised` — down to a handful of wei of LT — can satisfy the USD leg. `_prepareGraduationLiquidity` then derives `tokensForLP = (ltFromPair × tokenReserve) / assetReserve` [3](#0-2) , which scales down proportionally with `ltFromPair`. Both `tokensForLP` and `ltFromPair` can therefore be pinned to values whose product's square root is at or below UniswapV2's fixed `MINIMUM_LIQUIDITY` (1000), on any LT whose native decimals/scale make this reachable.

Once `_enterGraduating` caches these dust values in `pendingGraduation[token]` and flips `lifecycle` to `Graduating` [4](#0-3) , they are frozen — `finalizeGraduation` reuses the cached values verbatim and there is no re-pricing/recompute path [5](#0-4) . `finalizeGraduation` is permissionless and callable by anyone, including a stranger [6](#0-5) , but every call routes through `_seedDirectMint` on a fresh pair, which will always attempt the same dust `pair.mint(lpLock)` and always revert `INSUFFICIENT_LIQUIDITY_MINTED`. Because `pendingGraduation[token]` is only deleted on a *successful* `finalizeGraduation` [7](#0-6) , the token is stuck in `Lifecycle.Graduating` forever — `Bonding.buy`/`sell` are already gated off in this lifecycle, and `LPLock.recordLock` (a one-shot, no-rescue contract per its own natspec) is never reached to unstick it [8](#0-7) .

This is the direct architectural counterpart to the "hang or frequently repeatable crash (complete DOS)" class in CVE-2020-14786: an unprivileged party (a trader executing the threshold-crossing buy, or simply market conditions moving `exchangeRate()`) can drive a code path into a permanent revert loop with no recovery, exactly the failure mode the protocol's own `AGENTS.md` calls "the load-bearing security property" for Regime 3 but never extended to Regime 1.

### Impact Explanation
All LT already raised by the curve (`ltFromPair`, moved into `Bonding` via `Router.graduate` during phase 1) and the 250M-token `LP_RESERVE` allocation for that token are permanently frozen in `Bonding` with no code path to release them — the token can never graduate, its curve is permanently frozen (trading is disabled once `Lifecycle.Graduating` is set), and holders can never exit via either the curve (frozen) or a HyperSwap pool (never created). This is a permanent freezing of trader/creator funds tied to that specific token, satisfying the "Validate" bar (permanent freezing of trader or LP funds).

### Likelihood Explanation
Reachable via a single unprivileged transaction: any trader's ordinary `Zap.buy` that crosses the USD graduation threshold on a token paired with a high-rate/high-decimals LT can trigger phase 1 with dust-sized cached amounts; no privileged role or LT-side bug is required, only the natural combination of the threshold math and a small enough LT unit relative to `graduationThresholdUsd`. Because the vulnerable values are computed and frozen entirely from stored pair state (independent of any external manipulation of HyperSwap), this is deterministic once the triggering conditions are met, not merely probabilistic.

### Recommendation
Add the same floor protection to `_seedDirectMint`/`_prepareGraduationLiquidity` that Regime 3 already has for its swap budget: before caching `(tokensForLP, ltFromPair)` in `_enterGraduating`, verify `sqrt(tokensForLP * ltFromPair) > MINIMUM_LIQUIDITY` (1000) for the target HyperSwap pair, and if not, either scale up the effective raise required to graduate (delay phase 1) or route the dust case through an alternate seeding mechanism that doesn't depend on UniswapV2's `MINIMUM_LIQUIDITY` burn. Alternatively, add a recovery path (e.g., an admin/permissionless function that can adjust `pendingGraduation` amounts within the already-verified zero-gap price ratio, scaled up, when the raw amounts fall below the LP-mint floor) so a stuck token is not unrecoverable.

### Proof of Concept
1. Launch a token paired against an LT with a very high `exchangeRate()` relative to `graduationThresholdUsd` (e.g. exchangeRate scaled such that `graduationThresholdUsd / exchangeRate()` is on the order of a few thousand wei of LT).
2. Seed-buy and then execute a normal `Zap.buy` that pushes `realLtRaised × exchangeRate() ≥ graduationThresholdUsd` while `realLtRaised` itself is on the order of a few thousand wei — this fires `_enterGraduating` inline (`Bonding._executeBuy`'s post-buy `canGraduate` check) [4](#0-3) .
3. Observe `pendingGraduation[token].tokensForLP` and `.ltFromPair` are both small enough that `sqrt(tokensForLP * ltFromPair) <= 1000` (UniswapV2 `MINIMUM_LIQUIDITY`).
4. Call `finalizeGraduation(token)` (permissionless, callable by any address) — it reverts in `_seedDirectMint`'s `IUniswapV2Pair(pair).mint(lpLock)` with `INSUFFICIENT_LIQUIDITY_MINTED`.
5. Repeat step 4 from any address — it reverts identically every time; `pendingGraduation[token]` is never cleared and `lifecycle` never leaves `Graduating`, permanently freezing the token's curve-raised LT and 250M token reserve.

Note: I was unable to fully verify the exact numeric feasibility of driving `sqrt(tokensForLP * ltFromPair)` below 1000 given the specific `graduationThresholdUsd` and LT decimal conventions used in production deployment, since those config values live outside the indexed contract snippets I could retrieve. A background Devin session with access to `DeployHelper.sol`/deployment config and the BounceTech LT's real decimal/rate ranges would be needed to confirm concrete reachability bounds before treating this as fully proven rather than a structural gap.

    ///         keeper drives the happy path; anyone can rescue a stuck token.
    /// @dev Bypasses the V2 router and calls `pair.mint(lpLock)`
    ///      directly. This is brick-proof against a front-runner pre-creating
    ///      the pair and dust-seeding it between phases.
    /// @dev Exchange-rate drift between phase 1 and phase 2 is accepted by
    ///      design. The cached `(tokensForLP, ltFromPair)` are pure pair-
    ///      state arithmetic — see `_prepareGraduationLiquidity`, which
    ///      never reads `exchangeRate()` — so the LP opens at the exact
    ///      LT-per-token ratio the curve closed at, regardless of how long
    ///      phase 2 takes. What drifts is only the USD denomination of the
    ///      LT side, which is inherent to using a leveraged token as the
    ///      curve reserve: holders accept that exposure when they buy in.
    ///      A keeper Worker drives finalize within ~60s of `TokenGraduating`,
    ///      so the practical drift window is single-digit seconds. No
    ///      freshness timestamp / staleness gate: a recompute would return
    ///      byte-identical values (inputs are frozen while
    ///      `Lifecycle.Graduating`), and re-pricing the LP at the live
    ///      `exchangeRate()` would break the zero-gap-in-LT-units invariant.
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        address tokenAddress,
