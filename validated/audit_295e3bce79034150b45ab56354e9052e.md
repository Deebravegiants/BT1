This confirms the vulnerability. The `Registry.process` method at `lib/shopify_api/webhooks/registry.rb:189-199` calls `Utils::HmacValidator.validate(request)` which, per `Request#to_signable_string`, only signs the raw body bytes.### Title
Webhook shop-domain and topic identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that raw body string. However, `Registry.process` uses `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all read from unauthenticated HTTP headers — to build the `WebhookMetadata` handed to the app's handler, without those fields ever being covered by the signature.

### Finding Description
The bug-class hint ("a field acted on but not covered by the HMAC") maps directly onto this code:

- `Request#hmac` decodes `shopify-hmac-sha256`/`x-shopify-hmac-sha256`. [1](#0-0) 
- `Request#to_signable_string` signs *only* the raw body bytes: [2](#0-1) 
- `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled from HTTP headers that are never part of `to_signable_string`: [3](#0-2) 
- `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac`; the identity fields are simply not part of this equality: [4](#0-3) 
- `Registry.process` trusts `Utils::HmacValidator.validate(request)` as proof of authenticity for the *whole request*, then builds `WebhookMetadata` from the unauthenticated header fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`) and dispatches it to the app's handler: [5](#0-4) 
- The documented usage pattern feeds `request.headers.to_h` directly into `Request.new`, so any caller of this public HTTP endpoint controls those headers verbatim: [6](#0-5) 
- `WebhookMetadata.shop` is a plain `String` constant with no further validation (no `ShopValidator.sanitize!` call, no cross-check against a session): [7](#0-6) 

**Identity binding broken (as an equality):**
`HMAC_valid(raw_body) == true` is treated by `Registry.process` as if it meant `shop-domain header == the tenant that produced this raw_body`. In reality `HMAC_valid` only proves `raw_body` bytes are unmodified relative to *some* valid HMAC computed with the app's secret — it says nothing about which shop (or even which topic) that HMAC was originally computed for, because `shop`, `topic`, `api_version`, and `webhook_id` are excluded from `to_signable_string`.

**Concrete exploitation path (unprivileged internet user, no leaked credentials needed):**
1. An attacker installs the same app on their own (attacker-controlled) shop — a legitimate, unprivileged action available to anyone who can install a Shopify app.
2. Shopify sends the attacker's shop a genuinely signed webhook: `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`, `x-shopify-topic = T`.
3. The attacker replays this exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain` with a victim shop domain (and/or a different `x-shopify-topic` value, if the target app registers handlers per topic that trust `data.shop`/`data.topic` for tenant-scoped side effects, e.g. writing/deleting data keyed by `shop`).
4. `Utils::HmacValidator.validate` still returns `true`, because the signature only covers `B`, which is unchanged.
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: T, body: B, ...)`, and the host application — following this gem's own documented pattern of trusting `data.shop`/`data.topic` (`docs/usage/webhooks.md` lines 24-26) — will process/store the attacker's payload as if it originated from the victim shop.

This is a genuine flaw in the gem's own `HmacValidator`/`Request` design (not merely "the host app ignoring documented API") because the gem explicitly hands the host app an object (`WebhookMetadata`) that bundles unauthenticated header data next to a validated-body flag, without disclosing that `shop`/`topic`/`webhook_id`/`api_version` are unauthenticated.

### Impact Explanation
This breaks the shop-identity binding used for webhook tenant routing, enabling an attacker who legitimately owns *any* shop with the target app installed to inject data attributed to an arbitrary victim shop into the host app's webhook processing pipeline — a cross-tenant data injection / cross-tenant access primitive (Critical, per the rules' "cross-tenant access" bucket), achieved purely by replaying an unauthenticated header on top of one legitimately obtained signed body.

### Likelihood Explanation
High. Obtaining one genuinely signed `(body, hmac)` pair only requires installing the app on any shop (or waiting for any webhook event), which is trivial for any developer/merchant. Sending a forged HTTP request with an altered `shop-domain` header to the app's public webhook URL requires no special access, no secrets, and no privileged account.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (e.g., sign a canonical concatenation of these headers plus the raw body), or at minimum document/enforce that host applications must independently verify `data.shop` and `data.topic` against a session/registration record before trusting them, and add that verification inside `Registry.process` itself so the guarantee is enforced by the gem rather than left to the integrator.

### Proof of Concept
```ruby
# Attacker legitimately receives one signed webhook for their own shop:
raw_body = '{"id":1}'
secret   = ShopifyAPI::Context.api_secret_key
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)

# Attacker replays it to the app's public webhook endpoint with a spoofed shop header:
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # still valid! body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (signs raw_body only)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {...}))
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.     )
    render json: {success: true}.to_json
  end
end
