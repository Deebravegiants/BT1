Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the request body, enabling cross-tenant webhook relabeling - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw body [1](#0-0) , then passes `request.shop` — read straight from the `shop-domain` header — into `WebhookMetadata` as the trusted tenant identifier [2](#0-1) . The `Request#to_signable_string` used for HMAC verification is defined as only `@raw_body`, never including `shop`, `topic`, `webhook_id`, or `api_version` [3](#0-2) . This breaks the binding: `hmac-verified(body) == shop-attributed(header)` — the HMAC never authenticates which shop the body belongs to.

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` header value [4](#0-3) . For webhook requests, `to_signable_string` returns only the raw JSON body [5](#0-4) , so the cryptographic guarantee is "this body byte-string was HMAC'd with the app's `client_secret`" — it says nothing about which shop sent it. `Registry.process` nonetheless forwards the header-derived `shop` value unchanged into the handler as ground truth: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [2](#0-1) .

This gem's own documentation instructs app developers to treat `data.shop` as the authenticated shop for the event and use it directly for tenant-scoped side effects, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [6](#0-5) . Because `shop-domain` is not part of the signed content, any party who can obtain one valid `(raw_body, hmac)` pair for *any* shop that has this app installed — e.g., by installing the app on their own store, which is not a privileged action — can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a different, victim shop domain. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop, while carrying attacker-controlled JSON content in `body`.

### Impact Explanation
This is a cross-tenant identity-binding failure: the HMAC authenticates the payload bytes but not the shop attribution used by every downstream consumer of the webhook. An unprivileged attacker (any merchant who installs the app on a store they control) can forge events that this library reports as originating from a shop they do not own, injecting attacker-chosen JSON bodies attributed to the victim tenant into whatever business logic the app built on top of `WebhookMetadata#shop` (e.g., data writes keyed by shop, cache invalidation, `app/uninstalled` cleanup, order/customer record confusion). This matches the "cross-tenant access" criterion.

### Likelihood Explanation
Moderate-to-high for an app that has any publicly installable listing or free/dev-store install flow: the attacker only needs to install the target app once on any shop under their control to obtain a valid `(body, hmac)` pair signed with the app's real `client_secret`, then replay the HTTP POST to the app's webhook endpoint with a different `shop-domain` header. No access token, `client_secret`, or victim credentials are required — only the ability to trigger one legitimate webhook delivery to themselves and then re-send the raw bytes with a modified header, which is achievable by any internet user who can install the app.

### Recommendation
Bind the shop attribution to the same authenticated context as the payload:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) header value in the signable string that `HmacValidator` verifies, so any header tampering invalidates the HMAC, or
- Independently verify that the `shop-domain` header corresponds to a shop with a known/active installation (session) for this app before dispatching to the handler, rejecting webhooks for shops that have no such session, and
- Document this gap prominently so app authors do not treat `WebhookMetadata#shop` as authenticated on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a real webhook (e.g., `orders/create`) delivered by Shopify with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real `client_secret`.
2. Attacker captures the raw POST: headers `x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, and the raw JSON body.
3. Attacker resends the identical raw body and `hmac-sha256` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`@raw_body` only) [5](#0-4)  and it matches, since the body is unchanged; validation succeeds.
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` [2](#0-1) , which the app treats as a legitimate event for the victim tenant.
