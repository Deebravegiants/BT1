## Title
Overpaid native-token dispatch fees are permanently confiscated as "dust" instead of refunded to the caller — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap the *entire* amount through `swapETHForExactTokens` for only the exact `fee`/`amount` needed in `feeToken`. Any native-token overpayment refunded by the Uniswap router lands back in `EvmHost` itself (via its `receive()`), and there is no logic returning that excess to the original caller — it is retained by the contract as "dust," recoverable only by privileged cross-chain governance via `withdraw()`, never by the depositor.

### Finding Description
`dispatch(DispatchPost)` swaps the full `msg.value` for an exact output amount of `feeToken`: [1](#0-0) 

The same unconditional full-value swap pattern is repeated in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

Uniswap V2's `swapETHForExactTokens` only spends as much ETH as required to receive the exact output `fee`/`amount`; any unspent ETH is refunded by the router directly to its caller — which is `EvmHost`, not the original `_msgSender()`. This refund is explicitly acknowledged in the contract itself via a dedicated `receive()` function whose comment states it exists purely to sweep this leftover value: [4](#0-3) 

None of the three `payable` entry points (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) contains any code path that forwards this leftover ETH back to `_msgSender()`. The only way that ETH can leave the contract is through the privileged, cross-chain-governance-gated `withdraw()` function, restricted to `_hostParams.hostManager`, which pays out to an arbitrary `beneficiary` chosen by governance — not the original depositor: [5](#0-4) 

This is a direct functional analog to the Opyn `Controller` bug: a `payable` function accepts and spends more ETH than strictly required for the requested action, and the excess remains trapped in the contract with no self-service recovery path for the sender — recoverable only by an admin/governance-style withdrawal, exactly the pattern the original report flags as a bug. Notably, the same codebase demonstrates the correct pattern elsewhere: `IntentGatewayV2.placeOrder`/`fillOrder` explicitly refund unspent `msg.value` to the caller after a fee-token swap: [6](#0-5) 

This confirms the protocol's own design intent is that overpaid native-token amounts used for AMM-fee swaps should be refunded to the sender — an intent that `EvmHost`'s three payable dispatch/fund entry points fail to implement.

### Impact Explanation
Any application contract or relayer-forwarded transaction that calls `dispatch()`/`fundRequest()` with `msg.value` even slightly above the exact amount needed for the Uniswap swap (which is common, since callers must estimate slippage/price-impact in advance to guarantee the swap succeeds and typically pad the value) permanently loses that excess ETH. It becomes indistinguishable protocol-owned "dust," extractable only by governance to a beneficiary of governance's choosing — never returned to the depositor. Since `dispatch` is the primary, unprivileged, permissionless path used by every `IApp` on the chain (POST/GET dispatch) and is reachable from a single transaction, this is a realistic and repeatable loss-of-funds vector for ordinary users/integrators, not a privileged-actor issue.

### Likelihood Explanation
High likelihood of triggering unintentionally: because `swapETHForExactTokens` requires knowing the exact ETH needed up front (dependent on live AMM price), any caller who is not perfectly precise — or who intentionally overpays for slippage safety — will lose the difference. This applies to every dispatch call using native-token payment across all EVM-hosted chains running `EvmHost`.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, snapshot `address(this).balance` before the `swapETHForExactTokens` call and refund the delta (i.e., unspent `msg.value`) to `_msgSender()` after the swap, mirroring the pattern already used in `IntentGatewayV2._sendValue(msg.sender, msgValue)` at `evm/src/apps/IntentGatewayV2.sol:394-397`. Alternatively, compute the required native-token input via `getAmountsIn` before swapping and only pull that exact amount, refunding the remainder immediately.

### Proof of Concept
1. An `IApp` contract calls `IDispatcher(host).dispatch{value: X}(post)` where `X` is intentionally larger than the current spot-price ETH cost of `post.fee` feeToken (to tolerate slippage).
2. `EvmHost.dispatch` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. The router spends `Y < X` ETH and refunds `X - Y` ETH back to `EvmHost` (the swap's caller), landing in `EvmHost.receive()`.
4. `dispatch` returns without ever moving `X - Y` back to the original caller; the app/user's overpaid ETH is now permanently part of `EvmHost`'s balance.
5. The only recovery path is `EvmHost.withdraw()`, callable exclusively by `_hostParams.hostManager` through governance, which can only send the funds to a beneficiary chosen by governance — never automatically back to the original depositor.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
