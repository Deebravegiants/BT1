### Title
Unallowlisted route venue can attach wallet-draining token transfers to the caller's `require_auth` tree - (File: contracts/controller/src/strategies/swap_collateral.rs, contracts/swap-aggregator/src/venues/auth.rs)

### Summary
The external report describes a relayer losing its own funds because untrusted receiver code executes under the relayer's transaction authority (`tx.origin`). Soroban has no `tx.origin`, but it has the direct equivalent: a single `require_auth` at the entrypoint covers the whole recorded sub-invocation tree. XOXNO's swap strategies execute arbitrary, non-allowlisted "venue" contracts named inside the route payload while the caller's authorization is still active, so attacker-supplied venue code can issue `token.transfer(victim, attacker, …)` calls that are recorded as children of the victim's signed authorization tree and drain the victim's wallet — exactly the reported bug class. This is confirmed by an in-repo test, `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` (swap and `convert_swap` legs) all take a `swap: Bytes` route payload and forward it to the configured swap-aggregator. The router resolves venue and pool addresses from the payload itself; the threat model states the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization."

The in-repo test deploys a `RogueHopPool` whose `swap()` function executes `token::Client::transfer(victim, attacker, amount)` against a token the victim holds unrelated to the swap. A router double (`UnlistedPoolRouter`) calls `env.invoke_contract(&route.hop_pool, "swap")` while Alice's `sender.require_auth()` is on the stack. Simulation records the rogue transfer as a `sub_invocation` of Alice's `swap_collateral` root authorization, the signed tree is accepted, Alice's full wallet balance moves to the attacker, and the swap itself still settles correctly (`supply_balance_raw` shows the fair output credited), so nothing in the protocol reverts.

The controller only authorizes one exact input-token transfer to the router and measures the output delta; neither the controller's measured output check, the router's `min_out` check, nor the post-swap account risk gate bounds the extra transfers the rogue venue performs under the caller's auth.

### Impact Explanation
Theft of user funds. A single unprivileged attacker deploys a malicious venue contract and gets a victim to route through it; every token transfer the venue issues against the victim's address executes once the victim signs the simulation-recorded auth tree. The loss is the victim's entire wallet balance in any token, unbounded by the swap amount. A `swap_collateral` caller loses funds held completely outside the protocol while receiving a "correct" swap result.

### Likelihood Explanation
Medium. Execution requires the victim to sign an authorization tree containing the malicious transfer, which honest simulation records faithfully — an attentive client that diffs the tree would refuse. However, this is the same trust model as the reported `tx.origin` issue: the executor/relayer is unaware of what the foreign code does, and wallets/clients commonly sign recorded trees as-is. The project itself documents this exposure in `docs/explanation/threat-model.md` ("the loss is then the caller's wallet, not the routed amount") while keeping venues deliberately unallowlisted, so the attack surface is live for any route naming an attacker-controlled address.

### Recommendation
- Enforce a governance-controlled allowlist of venue/pool addresses the router will call, or at minimum restrict `hop_pool`-style generic invocations to vetted venues.
- On the controller side, prefer pulling the input via `transfer_from` into the controller and authorizing only the router's exact input transfer, and document that clients must reject any auth tree containing child invocations beyond the single expected input transfer.
- Surface the full recorded auth tree to users before signing (e.g., in SDK helpers) and warn on token-transfer children targeting the caller.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the attack end-to-end:

- `RogueHopPool::swap` reads a `(victim, wallet_token, to, amount)` plan from storage and calls `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` — no authorization of its own is needed because the call rides under the victim's active auth.
- `UnlistedPoolRouter::execute_strategy` does `sender.require_auth()`, pulls `total_in`, then `env.invoke_contract(&route.hop_pool, "swap")` on the attacker-named pool before paying out `min_out`.
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` asserts the recorded auth tree is exactly `{ alice -> controller.swap_collateral(args) -> [token.transfer(alice, attacker, WALLET_BALANCE)] }`, and after execution `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while Alice's ETH supply position receives the fair output — the swap succeeds and the theft is invisible to every protocol-level check.

Attack path: attacker deploys `RogueHopPool` configured with `(victim, wallet_token, attacker, balance)`, crafts a `RoutedSwap` whose `hop_pool` names it, and the victim submits `controller.swap_collateral(caller=victim, account_id, current, amount, new, swap=route)` and signs the simulated tree. The venue's `transfer` executes as an authorized child, draining the victim's wallet-token balance.
