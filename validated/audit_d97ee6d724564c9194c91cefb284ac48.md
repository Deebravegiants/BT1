### Title
Webhook Shop-Domain Spoofing — HMAC Covers Only the Raw Body, Not the `shop`/`topic` Headers Trusted by the Handler - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic — and hands the handler an authoritative `shop` value — as soon as `Utils::HmacValidator.validate(request)` passes. But the HMAC is computed only over the raw request body, never over the `shop-domain` (or `topic`/`webhook-id`) header. Any bytes that produce a valid HMAC for *some* installed shop can be replayed with a forged `shop-domain` header pointing at a different tenant, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`hmac` is parsed from the `hmac-sha256` header, and `shop` is parsed from the separate `shop-domain` header — neither is bound to the other: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` computes/compares the signature strictly over `verifiable_query.to_signable_string` (i.e., the raw body), with no reference to the shop, topic, or any other header: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that has the app installed, an unprivileged merchant who has the app installed on their own store can trigger a genuine webhook (e.g. by creating an order), capture the resulting `(raw_body, hmac)` pair that Shopify legitimately signs with the app's shared secret, and replay it to the app's public webhook endpoint after only changing the `x-shopify-shop-domain` header to a victim shop's domain. The HMAC check still succeeds because it never examined the header, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain — a shop-identity binding that was never actually verified.

The gem's own documentation reinforces the false sense of assurance: it states that `Registry.process` "will verify the request did indeed come from Shopify" and lists `data.shop` simply as "The shop domain of the webhook," with no caveat that the shop value itself is unauthenticated: [5](#0-4) [6](#0-5) 

This is exactly the reward-duration bug's root-cause pattern applied to authentication: the value the code *acts on* (`shop`, used to key the handler's business logic, analogous to "the balance actually available") is not the same as the value that was *cryptographically verified* (the raw body's HMAC, analogous to "rewards actually owed"), so the two silently diverge whenever an attacker controls the unverified field while keeping the verified one valid.

### Impact Explanation
This breaks the identity binding `shop authenticated == shop acted upon`. A single unprivileged merchant with app access (no `api_secret_key`, no access token, no leaked credentials required) can make the host application record/process webhook events under any other tenant's shop domain of their choosing, causing cross-tenant data corruption/confusion in every application built on this gem's documented webhook API (e.g. wrong shop's records updated, uninstall/redact webhooks misattributed, orders/customers data written under the wrong tenant). This matches the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
High for any application that trusts `WebhookMetadata#shop` as authenticated (which the gem's own documentation encourages by asserting the request "did indeed come from Shopify"). No secret material, TLS interception, or social engineering is needed — only capturing one's own genuine webhook traffic (trivial for any merchant/developer with the app installed) and replaying it with one header changed.

### Recommendation
Extend the HMAC-covered signable string (or add a separate binding step) so the `shop-domain` (and `topic`) header is cryptographically tied to the payload, or require `Registry.process`/host applications to cross-check `request.shop` against the shop associated with the session/registration state (not just header). At minimum, document in `docs/usage/webhooks.md` that `data.shop` is unauthenticated header data and must be independently validated against known installed shops before being trusted.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a genuinely-signed webhook by, e.g., creating an order and letting Shopify POST to the app's `orders/create` endpoint. Attacker captures the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's shared `api_secret_key` over `B`).
2. Attacker replays the exact same request to the app's public webhook endpoint but replaces `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`, keeping body `B` and hmac `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation passes.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, so the host application processes attacker-supplied order/customer data as if it belongs to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
