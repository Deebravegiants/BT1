### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop-domain`, `topic`, and `webhook-id` HTTP headers — which are used unauthenticated to attribute the webhook to a tenant and to select a handler — are never included in the signed material, breaking the binding: `shop authenticated by HMAC == shop attributed to the processed event`.

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body, while `shop`, `topic`, and `webhook_id` are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` verifies only the body HMAC and then dispatches using the header-derived (unsigned) `shop`, `topic`, and `webhook_id`, constructing `WebhookMetadata` that the app's handler trusts as the tenant identity of the event: [3](#0-2) 

Because the signature only binds the body bytes, any request with a body+HMAC pair that was legitimately produced by Shopify for *some* shop/topic remains valid even if the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers are swapped for different values. The equality the code implicitly assumes — `hmac verifies body` implies `hmac verifies (shop, topic, webhook_id, body)` — does not hold, since headers are excluded from `to_signable_string`.

### Impact Explanation
An attacker who controls (or receives legitimate webhooks for) one shop can capture a valid `(raw_body, hmac)` pair from their own tenant's webhook delivery, then resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop (and/or the `shopify-topic`/`shopify-webhook-id` headers altered). `HmacValidator.validate` will still pass because it never inspects those headers, and `Registry.process` will hand the forged `shop`/`topic`/`webhook_id` to the app's handler as if they were authentic. If the host application persists or acts on webhook data keyed by `shop` (as recommended by Shopify's own webhook docs), this results in cross-tenant data injection/confusion — data belonging to the attacker's shop gets attributed to another merchant's tenant. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged actor who can install the app on any shop (including their own) to receive at least one legitimate webhook, then replay the body/HMAC to the same public webhook endpoint with modified headers — no access token, `client_secret`, or privileged credentials are needed, and the request travels over the app's normal, internet-reachable webhook route. This is a realistic starting point for an "unprivileged internet user" per the rules, and directly mirrors the reported bug class: a field (`shop`/`topic`/`webhook_id`) that is acted upon by the code but not covered by the cryptographic signature, letting the attacker tamper with it after a valid signature already exists.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the material that is HMAC-verified, or otherwise cryptographically bind them to the body (e.g., verify them against a separate signed channel, or require the host application to cross-check `shop` against the caller's registered webhook endpoint/session before trusting it). At minimum, document prominently that `shop`/`topic`/`webhook_id` are not authenticated by `Registry.process` and must not be trusted as tenant identifiers without additional verification by the consuming application.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and let it receive a legitimate webhook, capturing the raw request body `B` and header `shopify-hmac-sha256: H` (valid for `B` under the app's real `api_secret_key`).
2. Resend a request to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but with `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `HmacValidator.validate` succeeds because `to_signable_string` only checks `B` against `H`: [4](#0-3) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-supplied data as if it came from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
