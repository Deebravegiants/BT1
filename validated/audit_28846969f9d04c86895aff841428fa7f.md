### Title
Missing parameter validation in Tron `IntentGatewayV2.onAccept`/`UpdateParams` and `setParams` allows a forged/erroneous governance message to permanently brick order settlement - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` applies `Params`/`ParamsUpdate` supplied via `setParams()` and the cross-chain `RequestKind.UpdateParams` branch of `onAccept()` with **no validation whatsoever**, unlike the canonical EVM implementation which routes every params write through `IntentsBase._validateParams`, rejecting zero/non-contract `host`, zero/non-contract `dispatcher`, `surplusShareBps > 10_000`, `protocolFeeBps >= 10_000`, and a non-contract `priceOracle`. [1](#0-0) 

### Finding Description
In the Tron contract, `setParams` only checks the caller is `_admin` and then blindly overwrites `_params`: [2](#0-1) 

The cross-chain governance path is worse: `onAccept`'s `RequestKind.UpdateParams` branch decodes an arbitrary `ParamsUpdate` from a relayed Hyperbridge message and applies it directly to `_params` and `_destinationProtocolFees`, with **no bounds check on `protocolFeeBps`, `surplusShareBps`, `destinationFeeBps`, and no zero-address/code-length check on `host`, `dispatcher`, or `priceOracle`**: [3](#0-2) 

Compare this to the EVM/mainline `IntentsBase._updateParams`, which validates `p.host`, `p.dispatcher`, `surplusShareBps`, `protocolFeeBps`, and `priceOracle` before applying, and separately bounds every `destinationFeeBps < 10_000`: [4](#0-3) 

Concretely, on the Tron gateway a governance/relayer-delivered `UpdateParams` message with `protocolFeeBps >= 10_000` causes `placeOrder`'s fee arithmetic (`reducedAmount = originalAmount - protocolFee`) to underflow and revert for every order with a nonzero input, permanently freezing new order placement on that chain (a route unable to deliver/process value going forward). A `host` or `dispatcher` set to `address(0)` or a non-contract similarly bricks `host()`, fee-token lookups, and dispatch, since every escrow/dispatch/fee call in `placeOrder`/`fillOrder`/`withdraw` depends on `IDispatcher(host())` succeeding.

### Impact Explanation
This is directly reachable by a single delivered cross-chain governance-labeled message (`RequestKind.UpdateParams`) processed through `onAccept`, which any relayer can deliver once the Hyperbridge-sourced request passes the (source == hyperbridge) check — the check gates *origin*, not the *content* of the update. Because no bounds/zero checks exist, a malformed/mis-encoded, buggy, or protocol-drifted `ParamsUpdate` (not necessarily malicious governance — any inconsistency between the source-chain encoder and this contract's expectations) permanently breaks `placeOrder` for every user via arithmetic underflow/revert, or breaks all interactions with the host/dispatcher. This matches "a route unable to deliver messages"/"permanent freezing of funds" — Medium/High severity, since escrowed funds already in-flight during the bad update could also become unroutable if `host`/`dispatcher` becomes a non-contract.

### Likelihood Explanation
Likelihood is elevated relative to the EVM contract because the safety net (`_validateParams`) that the rest of the codebase consistently applies to this exact same `Params`/`ParamsUpdate` structure is simply absent from the Tron file — this is a straightforward divergence/regression between the two near-identical contracts (the EVM version was clearly hardened after finding this exact bug class, as evidenced by its explicit `InvalidInput` checks and dedicated tests `testRevert_UpdateParams_DestinationFeeBpsTooHigh`, `testRevert_SetParams_ProtocolFeeBpsTooHigh`, etc.), while the Tron port never received the same fix. [5](#0-4) 

### Recommendation
Port `IntentsBase._validateParams`'s checks into the Tron `IntentGatewayV2` before assigning `_params` in both `setParams` and the `RequestKind.UpdateParams` branch of `onAccept`, and bound each `destinationFees[i].destinationFeeBps < 10_000` before writing to `_destinationProtocolFees`, exactly mirroring: [4](#0-3) 

### Proof of Concept
1. Hyperbridge governance (or a relayer submitting a proof for a message whose encoding was produced incorrectly/without the same guard used on EVM) dispatches a `PostRequest` to the Tron `IntentGatewayV2` with body `[RequestKind.UpdateParams, abi.encode(ParamsUpdate{params: Params{..., protocolFeeBps: 10_000, ...}, destinationFees: []})]`.
2. `onAccept` decodes it, and since `source == hyperbridge()`, applies it directly: `_params = update.params;` with no bound check. [6](#0-5) 
3. Any subsequent `placeOrder` computes `protocolFee = (originalAmount * 10_000) / 10_000 = originalAmount` and `reducedAmount = originalAmount - protocolFee = 0`, or with `protocolFeeBps > 10_000` the subtraction underflows and reverts, freezing all order placement on the chain until a further correcting governance message (itself equally unguarded) is delivered.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
