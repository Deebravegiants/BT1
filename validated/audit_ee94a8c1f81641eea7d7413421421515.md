This confirms `ValidatedRequestFromMessage` performs no allowlist or sender-authorization check whatsoever — it only requires `MessageID` and `Method` to be non-empty. `Message.Validate()` at [1](#0-0)  only checks field lengths and extracts a signer address from a signature that any attacker can self-generate with their own ECDSA key; it never checks that the sender is an allowlisted/registered node or user. Combined with the confirmed absence of any duplicate-ID rejection in `HandleLegacyUserMessage`'s callback registration at [2](#0-1) , and the lookup-and-delete-by-`MessageID`-only logic in `handleWebAPITriggerMessage` at [3](#0-2) , the claim's exploit chain is verified against the actual code.

The `ProcessRequest` flow in `gateway.go` at [4](#0-3)  shows the `MessageID` originates directly from the client-supplied JSON-RPC `id` field and flows unmodified into `HandleLegacyUserMessage`, with the only gatekeeping being a length check and a valid-but-arbitrary self-signature — no binding to caller identity or session exists anywhere in this path.

Audit Report

## Title
Unauthenticated Cross-User Response Hijacking via MessageID Collision in Gateway WebAPI Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The Gateway's user-facing HTTP endpoint accepts JSON-RPC requests whose `id` field becomes the `MessageID` used to route asynchronous DON node responses back to the originating HTTP caller. This `MessageID` is fully attacker-controlled, requires only a self-generated ECDSA signature (no allowlist/registration check), and is stored in `savedCallbacks` with no duplicate-ID rejection and no binding to caller identity, session, or IP. Any unprivileged client can therefore register the same `MessageID` as a concurrent legitimate in-flight request, silently overwrite the stored callback, and receive the DON node's response intended for the victim.

## Finding Description
`ProcessRequest` decodes the raw JSON-RPC request and assigns `msg.Body.MessageID = request.ID` directly from client-supplied JSON. For legacy requests, `msg.Validate()` is called, which only checks field lengths/format and extracts a signer address from the attacker's own signature — it does not check that the signer/sender is registered, known, or previously associated with this `MessageID`. `HandleLegacyUserMessage` then stores the callback keyed only by `msg.Body.MessageID`:
```go
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
```
with no existence check before the write, unlike the sibling `responses.new()` in `outgoing_connector_handler.go`, which explicitly rejects a duplicate ID (`already have response for id`). When a DON node later responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up `savedCallbacks[msg.Body.MessageID]`, deletes it, and forwards the result to whichever callback is currently registered under that key — with no verification that the response belongs to the original requester.

## Impact Explanation
An unauthenticated client reaching the gateway's public `/user` HTTP endpoint can overwrite another concurrent, legitimate requester's pending callback by reusing the same `MessageID`, causing: (1) the DON node's response intended for the victim to be delivered to the attacker (cross-user response confusion/information disclosure), and (2) the victim's original request to be starved of its response (denial of service). This maps to the in-scope "cross-user response corruption" impact class for the Chainlink gateway.

## Likelihood Explanation
The `/user` endpoint is explicitly internet-facing. No authentication ties a `MessageID` to a calling identity — a self-generated, unregistered ECDSA key is sufficient to pass `Validate()`. The explicit `// TODO: apply allowlist and rate-limiting here` comment at line 384 confirms no additional gatekeeping exists on this path today. Exploitation only requires matching a `MessageID` of an in-flight request, which is feasible when IDs are predictable, sequential, or reused by client tooling (as shown in the sample script using a static `"12345"` default).

## Recommendation
- Bind pending callbacks to a unique, gateway-generated correlation key, or at minimum a `(Sender, MessageID)` tuple, instead of trusting the client-supplied `MessageID` alone.
- Reject requests attempting to reuse an already-pending `MessageID`, mirroring the duplicate check in `responses.new()`.
- Implement the allowlist/rate-limiting noted as a TODO in `HandleLegacyUserMessage`.

## Proof of Concept
1. Victim sends a legitimate `web_api_trigger` request to `POST /user` with `id: "X"`, self-signed with victim's key.
2. Before the DON node responds, attacker sends a request to `POST /user` with the same `id: "X"`, self-signed with attacker's own (unregistered) key — `Validate()` accepts it since no allowlist check occurs.
3. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with the attacker's callback.
4. The DON node's response for message `"X"` arrives at `handleWebAPITriggerMessage`, which looks up `savedCallbacks["X"]` (now the attacker's entry) and delivers the victim's intended response to the attacker's HTTP connection; the victim's `callback.Wait` times out. // ValidatedRequestFromMessage converts a legacy Gateway Message to a JSON-RPC request
func ValidatedRequestFromMessage(msg *api.Message) (*jsonrpc.Request[json.RawMessage], error) {
	if msg == nil {
		return nil, errors.New("nil message")
	}
	if msg.Body.MessageID == "" {
		return nil, errors.New("message ID is empty")
	}
	if msg.Body.Method == "" {
		return nil, errors.New("method is empty")
	}
	params, err := json.Marshal(msg)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal message: %w", err)
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageID,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	return req, nil
}
