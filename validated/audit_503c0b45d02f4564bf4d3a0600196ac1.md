Confirmed: `WrappedHyperFungibleToken.send()` at line 272 does a raw `safeTransferFrom(msg.sender, address(this), params.amount)` with no balance-before/after reconciliation, then encodes the *requested* `params.amount` (not actual received) into the dispatched `Message` via `_buildDispatchPost` (line 241). On the peer chain, `onAccept()` unconditionally releases/unlocks `message.amount` of the underlying to the beneficiary (lines 316-323). If `_underlying` is a fee-on-transfer (or rebasing/deflationary) token, this creates a permanent solvency gap between what's locked in the contract and what's promised across the bridge — analogous to the BendDAO finding but here it's an unchecked-received amount rather than an unchecked-required-amount revert, and it's worse because it doesn't even revert; it silently under-collateralizes the bridge and drains the pool for other legitimate users. This checked pattern is exactly what `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol` lines 320-322) already does correctly by comparing balances before/after and mutating the escrowed amount — `WrappedHyperFungibleToken` and its upgradeable twin lack this fix.

I also verified `WrappedHyperFungibleTokenUpgradeable.sol` has the identical unguarded pattern.

### Title
Fee-on-transfer/deflationary underlying tokens cause `WrappedHyperFungibleToken` to under-collateralize cross-chain transfers, draining the locked pool - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via a plain `safeTransferFrom` and then dispatches a cross-chain message encoding the caller-requested `params.amount`, without ever measuring how many tokens the contract actually received. If `_underlying` is a fee-on-transfer, deflationary, or rebasing token, the contract receives less than `params.amount` but still instructs the peer-chain deployment to release the full `params.amount` in `onAccept()`.

### Finding Description
In `send()`: [1](#0-0) 
the ERC20 is pulled with no balance check, unlike the pattern used elsewhere in the same repo (`IntentGatewayV2.placeOrder`) which snapshots `balanceOf` before/after `safeTransferFrom` and reduces the escrowed amount to the actual delta: [2](#0-1) 
The unadjusted `params.amount` then flows straight into the dispatched message body via `_buildDispatchPost`: [3](#0-2) 
On the destination-chain instance of `WrappedHyperFungibleToken` (or the mirrored deployment on the source chain acting as `onAccept` receiver for a return trip), `onAccept()` releases `message.amount` from that chain's locked pool unconditionally: [4](#0-3) 
Because this is a lock/unlock bridge (not mint/burn) for wrapped underlyings, every `send()` on a fee-on-transfer asset locks `amount - fee` but commits the network to release the full `amount` somewhere else, permanently depleting the reserve backing all other users' locked balances. The identical unguarded logic exists in the upgradeable variant, `WrappedHyperFungibleTokenUpgradeable.sol` (lines 294-301, 320-336).

### Impact Explanation
This is a direct, unbacked-mint/insolvency-style bug: each transfer of a fee-on-transfer underlying token permanently shrinks the pool of tokens actually held versus the amount owed to users across the bridge. Given enough volume, later legitimate redemptions/`onAccept` calls or timeout refunds will fail due to insufficient underlying balance (`safeTransfer` reverting) — freezing funds for those users — while earlier users effectively receive value siphoned from later depositors' collateral. This satisfies the "unbacked mint" / "permanent freezing of funds" impact bar for a Medium/High finding.

### Likelihood Explanation
Likelihood depends on whether a fee-on-transfer/deflationary token is ever configured as `_underlying` via `configure()`. Since `configure()` is owner-gated but the vulnerability is triggered purely by any unprivileged user calling `send()` with such a token already configured, and the codebase explicitly acknowledges and defends against this exact bug class elsewhere (`IntentGatewayV2`'s fee-on-transfer test suite), the omission here appears to be an inconsistency/oversight rather than an intentional restriction, making it a realistic risk if such a token is ever supported.

### Recommendation
In `send()`, measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and encode the actual received delta (not `params.amount`) into the dispatched `Message`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`. Alternatively, explicitly document that fee-on-transfer/deflationary/rebasing tokens are unsupported as `_underlying` and add an owner-side guard/check to prevent misconfiguration.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a 1% fee-on-transfer token, mirrored on chain B.
2. Alice on chain A calls `send({amount: 1000, ...})`. `safeTransferFrom` pulls 1000 from Alice but the contract balance only increases by 990 (10 tokens burned as fee). The dispatched `Message.amount` is still `1000`.
3. On chain B, `onAccept()` releases `1000` of the (mirrored) underlying to Alice's recipient — 10 more than chain A actually escrowed.
4. Repeat across multiple `send()` calls: chain A's real locked balance falls further behind the cumulative amount promised/released on chain B.
5. Eventually a legitimate `onAccept()` or `onPostRequestTimeout()` call on chain A (for a different user's inbound transfer/refund) reverts with insufficient balance in `safeTransfer`, freezing that user's funds — demonstrated conceptually by the already-existing `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` test pattern in `IntentGatewayV2SameChainTest.sol` (lines 2441-2494), which shows the correct balance-delta approach that `WrappedHyperFungibleToken` fails to apply.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
