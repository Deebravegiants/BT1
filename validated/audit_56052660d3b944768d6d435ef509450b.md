### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating the HMAC over the request body only, then hands the handler a `shop` value that is read straight from an HTTP header that is *not* included in the signed content. Because the app's `client_secret` (`Context.api_secret_key`) is shared across every shop that has installed the app, any tenant that receives a legitimately-signed webhook for its own shop can reuse that valid `(body, hmac)` pair while substituting a different `shop-domain` header, causing the handler to process the payload as if it belongs to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over exactly that signable string and secure-compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates on this HMAC check and then constructs `WebhookMetadata` using `request.shop`, which is read from the `shop-domain` header — a field with no cryptographic binding to the HMAC: [3](#0-2) [4](#0-3) 

The identity binding the gem is supposed to enforce is: *shop that authorized/produced this signed payload == shop the handler is told to act on*. Because only the body is signed, this equality does not hold — the `shop` field is "acted on but not covered by the HMAC," exactly the class of bug illustrated by the analog report (using the wrong/uncovered checkpoint value for an identity-bearing computation instead of the one that is actually tied to the authenticated entity).

Since `Context.api_secret_key` is the app's single `client_secret`, shared by all shops that install the app (it is not shop-specific), a merchant who has installed the app receives real webhook deliveries for their own shop with valid HMACs computed over their own body. That merchant fully controls a request with: a body of their choosing (as long as it's from a delivery they legitimately received, so the HMAC is valid) and, since headers aren't signed, an arbitrary `shop-domain` header. Sending this crafted request to the app's webhook endpoint passes `HmacValidator.validate` and is dispatched to the handler tagged with an attacker-chosen `shop`.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to select a tenant's session/store record (the documented, expected usage pattern — see `WebhookRequestTest`/`RegistryTest` which pass `shop-domain` straight through to `data.shop`), an attacker who is a legitimate but malicious merchant can cause the app to write or interpret webhook data under a different, victim tenant's identity. This is a cross-tenant boundary break rooted entirely in this gem's authentication primitive (`HmacValidator`/`Webhooks::Request`), not in host misuse of an undocumented API — the gem itself hands out an unauthenticated `shop` value as if it were verified.

### Likelihood Explanation
Exploitation requires only: (1) being an app-installing merchant (no privileged internal access, no leaked secrets — any store owner who installs a public app qualifies as an "unprivileged internet user" relative to other tenants), and (2) the ability to POST arbitrary headers to the app's public webhook endpoint, which by design must be internet-reachable to receive Shopify webhooks. No knowledge of `api_secret_key` is needed since the attacker reuses a genuinely valid `(body, hmac)` pair issued to them for their own shop.

### Recommendation
Bind the shop identity into the signed material, or otherwise cross-check it against an authenticated source, e.g.:
- Include `shop` (and `topic`, `webhook_id`) in the HMAC-signed content, or
- Require the caller to separately verify `request.shop` against the shop associated with the session/店 that the raw body's HMAC was computed for (not just presence of a valid HMAC), or
- At minimum, prominently document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant selection without an additional check (e.g., confirming the shop has an active session before trusting the payload).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `client_secret`), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends this exact request to the app's public webhook endpoint but replaces the `x-shopify-shop-domain` header with `victim.myshopify.com`, keeping body `B` and hmac `H` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes because `B` and `H` are unmodified. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, i.e., the app now processes attacker-controlled data as though it originated from `victim.myshopify.com`. [6](#0-5)
