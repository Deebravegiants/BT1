### Title
Unrefunded/unswept native TRX permanently locked in `IntentGatewayV2.placeOrder` (Tron variant) when order inputs are all ERC20 - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` on the Tron `IntentGatewayV2` is `payable` and accepts `msg.value`, but only consumes it when an order input or predispatch asset explicitly has `token == address(0)` (native TRX). If a user places an order whose `order.inputs` are entirely ERC20 tokens but mistakenly attaches native TRX via `msg.value` (e.g., wallet/dApp bug, or copy-pasting mainline EVM interaction code that sends `value:` for fees), that TRX is never validated against zero, never fully accounted for, and — critically — is never refunded to the sender at the end of the function.

### Finding Description
In the ERC20-only branch of `placeOrder`, `msgValue` is left completely untouched for non-native tokens: [1](#0-0) 

In the fee section, if `order.fees > 0` and `msgValue > 0`, the leftover value is swapped via `swapETHForExactTokens{value: msgValue}` but the actual amount spent (`amounts[0]` from the swap) is never subtracted from `msgValue`, and no refund of the remainder is performed: [2](#0-1) 

The function then immediately emits `OrderPlaced` and returns — there is no `_sendValue(msg.sender, msgValue)` (or equivalent) refund step: [3](#0-2) 

Compare this to the mainline EVM `IntentGatewayV2.sol::placeOrder`, which correctly tracks `msgValue` through the fee-swap path (`msgValue -= amounts[0]`) and explicitly refunds any leftover native value to `msg.sender` before emitting the event: [4](#0-3) 

There is no `receive()`/`fallback()` or admin sweep-native function found in the Tron `IntentGatewayV2.sol` that would let the contract or the user later reclaim this stranded native balance — the file only imports `SweepDust`, which is a token-dust mechanism, not a native-TRX recovery path.

### Impact Explanation
Any user who mistakenly sends native TRX with `msg.value` while calling `placeOrder` with an all-ERC20 `order.inputs` array on the Tron deployment will have that TRX permanently stuck in the `IntentGatewayV2` contract, with no code path to recover it (unless it happens to be entirely consumed by the fee-swap, in which case any excess above the exact swap cost is likewise lost). This is a direct, unrecoverable loss of user funds reachable by a single unprivileged `placeOrder` transaction — exactly the bug class described in the source report (ensure `msg.value == 0` when the input token is not the native asset), but here manifesting as a genuine asymmetry/regression between the Tron port and the audited mainline EVM contract.

### Likelihood Explanation
Likelihood is moderate-to-high: users interacting with Tron dApps/SDKs often reuse patterns from the mainline EVM `IntentGatewayV2` (which supports paying `order.fees` with attached native value) or wallet UIs that default to sending gas/value with contract calls. Since `placeOrder` is `payable` with no revert-on-nonzero-value guard for ERC20-only orders, this can be triggered unintentionally by ordinary users, not just adversaries.

### Recommendation
Port the same accounting/refund logic used in the mainline EVM contract to the Tron variant: track `amounts[0]` spent during the fee swap and subtract it from `msgValue`, then after all escrow/fee logic, if `msgValue > 0`, refund it to `msg.sender` via a native transfer (or revert if no native input/fee path expects it, i.e., `require(msg.value == 0)` when not needed).

### Proof of Concept
1. Deploy/target the Tron `IntentGatewayV2` contract.
2. Construct an `Order` with `order.inputs` containing only ERC20 `TokenInfo` entries (no `token == address(0)` entry), and `order.predispatch.assets` empty, and `order.fees == 0`.
3. Call `placeOrder(order, graffiti)` with `msg.value = 1 TRX` (or any nonzero value) alongside proper ERC20 approvals.
4. Observe: the ERC20 tokens are escrowed normally, `OrderPlaced` is emitted, but the 1 TRX sent as `msg.value` remains in the contract's balance — no revert, no refund event, and no function exists to retrieve it back to the sender.
