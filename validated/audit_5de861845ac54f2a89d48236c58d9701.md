Based on the code I read directly, the claim's core technical assertion is confirmed:

`jwtReplayCache.isReplay` takes an `RLock` and only reads, while `recordUsage` takes a separate `Lock` and writes, with no shared lock spanning the two calls: [1](#0-0) 

`Authorize` calls `isReplay` first, then performs an authorized-key map lookup, then calls `recordUsage` — two non-atomic operations with intervening work in between: [2](#0-1) 

This is a genuine, unmitigated check-then-act (TOCTOU) race: two goroutines processing the same JWT concurrently can both observe `isReplay(jti) == false` before either calls `recordUsage(jti)`, since `isReplay` releases its `RLock` immediately and does not hold any lock across to the `recordUsage` call. This contrasts with the vault capability's `replayGuard.CheckAndRecord`, which the report correctly cites as the atomic pattern used elsewhere in the codebase: [3](#0-2) 

Downstream, the only de-duplication is keyed on the JSON-RPC request `ID`, in `setupCallback`: [4](#0-3) 

and `VerifyRequestJWT` binds the JWT to a `Digest` computed from `req.Digest()`, checked against `verifiedClaims.Digest`, independent of `req.ID`: [5](#0-4) 

I was not able to fully confirm within available iterations whether `jsonrpc.Request.Digest()` is computed strictly over `Method`/`Params` and excludes `ID` (which would allow two distinct `req.ID`s to carry an identical digest and thus both validate against the same JWT), since the `Digest()` implementation itself is defined in the external `chainlink-common` module, outside this repo's indexed contents. This is the one piece of the report's reasoning I could not verify directly, but the report's own citations (the "JWT digest mismatch" test checking only params) are consistent with typical JSON-RPC digest schemes that hash `Method`+`Params` and not the envelope `ID`. Given the codebase confirms the two-call, non-atomic replay guard with no intervening lock, and the exploit path through `HandleUserTriggerRequest`/`setupCallback` deduplicating only on `req.ID` (not `jti`), the overall finding holds as described.

Audit Report

## Title
JWT Replay Guard TOCTOU Race in `WorkflowMetadataHandler.Authorize` Allows Same Token to Authorize Multiple Concurrent HTTP Trigger Requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtReplayCache.isReplay` and records usage via `jwtReplayCache.recordUsage` as two separate, non-atomic calls, with JWT signature verification and an authorized-key map lookup performed in between. Concurrent requests carrying the identical JWT `jti` can both pass the `isReplay` check before either reaches `recordUsage`, allowing a single one-time-use signed HTTP-trigger token to authorize and dispatch more than one workflow execution.

## Finding Description
`Authorize` performs `VerifyRequestJWT` → `h.jwtCache.isReplay(claims.ID)` → authorized-key lookup → `h.jwtCache.recordUsage(claims.ID)` as sequential, independently-locked steps rather than a single atomic check-and-set. `isReplay` acquires an `RLock`, reads, and releases before `Authorize` continues; `recordUsage` acquires a separate `Lock` later. No lock is held across the whole `Authorize` invocation, so two goroutines racing on the same `jti` can both observe `isReplay == false` and both subsequently call `recordUsage`, both succeeding. This mirrors the atomic `CheckAndRecord` pattern used by the vault capability's `replayGuard`, which `Authorize` does not replicate. Downstream, `HandleUserTriggerRequest` only de-duplicates in-flight requests by JSON-RPC `req.ID` in `setupCallback`, not by `jti`, so two requests bearing distinct `req.ID`s but the same underlying JWT are not blocked by that mechanism.

## Impact Explanation
A caller in legitimate possession of one valid signed HTTP-trigger JWT can, by racing two requests, cause the associated workflow to be dispatched twice instead of the intended single execution. Depending on the workflow's side effects (on-chain transactions, external calls, capability invocations), this could produce duplicate fund movement or duplicate job/workflow runs — an in-scope "unauthorized job run" / duplicated execution impact for the gateway trigger path.

## Likelihood Explanation
Exploitation requires only sending two near-simultaneous HTTP requests to the gateway's public trigger endpoint using a JWT the caller already legitimately holds — no privileged or operator access is needed. The race window, while narrow (bounded by JWT verification and a map lookup), is real because no lock spans the check-then-act sequence.

## Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic check-and-set operation on `jwtReplayCache` (e.g., an `Add`-style method that inserts the `jti` under one lock and returns whether it was already present), rejecting the request if the `jti` was already recorded. This mirrors the existing atomic `replayGuard.CheckAndRecord` pattern used by the vault authorizer.

## Proof of Concept
1. Sign one JSON-RPC HTTP-trigger request with JWT `jti = "abc"` for workflow `W`.
2. Fire two concurrent HTTP POSTs to the gateway's trigger endpoint carrying the same JWT, using distinct outer `jsonrpc.Request.ID` values.
3. Add a Go test that calls `WorkflowMetadataHandler.Authorize` concurrently from two goroutines with the same `claims.ID`/token and asserts that at most one call succeeds — under the current implementation both can succeed, demonstrating the race (this can be shown deterministically by inserting a small sleep/synchronization point between `isReplay` and `recordUsage` to widen the window for the test, or via Go's `-race` detector combined with repeated iterations).
