## Title
Webhook `shop` (tenant) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully "verified" once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature only covers the raw request body — it never binds the `shopify-shop-domain` header that the handler receives as the trusted tenant identifier (`data.shop`). Any party who can obtain one genuinely-signed webhook payload for the app's `api_secret_key` (e.g., by installing the app on their own store) can replay that exact body+signature to the app's webhook endpoint while substituting an arbitrary `shop` header, and the gem will report the request as verified.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

while `shop` is read directly and unauthenticated from the HTTP header: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature purely against `to_signable_string` (the body), independent of any header value: [3](#0-2) 

`Registry.process` uses this same validator as its sole authenticity check, then forwards the caller-supplied `request.shop` straight into `WebhookMetadata` given to the app's handler as trusted tenant context: [4](#0-3) 

The documentation explicitly tells integrators that `process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop it is attributed to — is authenticated: [5](#0-4) 

Because the signing secret (`Context.api_secret_key`) is the app's single client secret shared across every merchant/tenant that installs the app, and the signature never incorporates the shop domain, the identity binding `shop_header == shop_that_produced(hmac, body)` does not hold. Before the request: the attacker holds a legitimate `(raw_body, hmac)` pair issued by Shopify for their own store. After the request: they submit that unmodified pair with a forged `shopify-shop-domain` header naming a victim shop; `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant boundary that host applications rely on: `WebhookMetadata#shop`/`data.shop` is the gem's documented way to determine which merchant's session/data the webhook applies to before doing scoped work (updating records, triggering per-shop side effects). By spoofing this field while retaining a valid signature, an unprivileged user who can install the app on any store (including a fresh throwaway/development store) can inject payloads that any consuming application will treat as originating from a different, targeted shop — a cross-tenant access primitive rooted entirely in this gem's `process`/`HmacValidator` verification logic, not in host-application misuse.

### Likelihood Explanation
Exploitation requires only: (1) install the target app on any store the attacker controls (a normal, unprivileged action available to any merchant/developer), (2) capture one legitimately delivered webhook body and its `x-shopify-hmac-sha256` value, and (3) POST that identical body/signature to the app's public webhook endpoint with a different `shopify-shop-domain` header. No secrets, tokens, or privileged access to the victim's store are needed, making this readily reachable by an unprivileged internet-facing attacker.

### Recommendation
Include the shop domain (and ideally topic) as part of the value that is verified/bound to the HMAC, or require the caller to supply an out-of-band expected shop (e.g., resolved from an authenticated session/webhook subscription record) and assert `request.shop == expected_shop` before dispatching to handlers, rather than trusting the header solely because the body's HMAC checks out.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggers any subscribed webhook topic, and captures the delivered `raw_body` and `x-shopify-hmac-sha256` header — both valid under the app's shared `api_secret_key`.
2. Attacker POSTs to the app's webhook route with the same `raw_body`/HMAC but headers rewritten:
```
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <captured, unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, letting the attacker inject data attributed to the victim tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
