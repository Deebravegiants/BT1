### Title
Webhook `X-Shopify-Shop-Domain` header is trusted for tenant identification despite not being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the `hmac-sha256` header, then hands the `shop` value — read from an unauthenticated header — to the app's handler as the tenant identifier. This is the same class of bug as the reported `TwabLib::getTwabBetween` finding: a value is trusted and acted upon as if it were bound to the verification that was performed, when in fact the verification covers a different, narrower set of bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication step, then constructs `WebhookMetadata` using `request.shop`, which is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the HMAC-covered bytes: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header value == shop whose secret produced this HMAC`. Because the HMAC only signs `raw_body`, that equality is never checked — `shop` and `hmac` are independent, unbound fields. Since the same `api_secret_key` is used to validate webhook HMACs for every shop that has installed the app (there is one shared client secret per app, not per shop), any tenant that has legitimately installed the app can capture one of its own genuinely-signed webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `shop` header rewritten to a different, victim shop's domain. The HMAC check still passes (same body bytes, same signature), but `WebhookMetadata#shop` — the value the host application is documented to use for tenant lookup/dispatch — now names the victim tenant.

This exactly mirrors the report's bug class: a piece of data ("shop") is acted upon by downstream logic without being provably bound to the data that was actually verified ("raw_body" via HMAC), enabling a caller to present a self-consistent-looking but semantically wrong context, just as `getTwabBetween` could return balances not bound to the safe time window that had actually been observed.

### Impact Explanation
The library's own documentation instructs host apps to treat `data.shop` as the authoritative shop identifier from a verified webhook and dispatch business logic keyed on it (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

An attacker who is a legitimate (potentially free/low-trust) merchant on the app can therefore forge webhook events that the host application will process as if they originated from an arbitrary other shop that also uses the app, because `Registry.process` provides no cryptographic assurance that `request.shop` matches the tenant whose secret validated the HMAC. Depending on how the host app uses `data.shop` (e.g. `shop/redact`, `customers/redact`, inventory/order mutations, app-uninstall handling), this enables cross-tenant data corruption or triggering of privileged per-tenant actions under another merchant's identity — this is a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires only that the attacker control one shop that has installed the app (no leaked secrets, no privileged account, no TLS interception) — well within the "unprivileged internet user" threat model. The attacker needs one genuine webhook delivery for their own shop (freely obtainable by triggering any registered topic, e.g. `orders/create`) and the ability to POST an HTTP request with a modified header to the app's public webhook endpoint. This is a realistic, low-effort attack path, though its ultimate severity is host-app dependent (this issue lies in the gem providing no protection against it, not in a proof that every hosting app is exploitable).

### Recommendation
Do not treat `shop` (or `topic`, `webhook_id`, `api_version`) as authenticated data derived solely from the HMAC check over the body. Either:
1. Compute the webhook HMAC over a canonical string that includes the shop domain (and topic) in addition to the body, or
2. Require the host application to independently verify that `request.shop` corresponds to a shop with a currently valid, stored session/installation before dispatching to the handler, and document this requirement prominently, or
3. Cross-check `request.shop` against a per-shop webhook secret/signing context if Shopify's webhook delivery model supports it, instead of relying on one shared `api_secret_key` for HMAC validation across all tenants.

### Proof of Concept
1. As attacker, install the app on `attacker-shop.myshopify.com` and trigger a registered webhook topic (e.g. update a product) to receive a genuine webhook POST from Shopify: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `api_secret_key`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Replay this exact request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (leaving body `B` and `X-Shopify-Hmac-Sha256: H` untouched).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` (`B`) only and succeeds, since `B` and `H` are unchanged: [6](#0-5) 
4. `WebhookMetadata` is built with `shop: request.shop`, now `"victim-shop.myshopify.com"`, and passed to the host app's handler, which acts on behalf of the victim shop despite the request never being signed with anything tied to that shop.
