Confirmed: `message.from` is an `alloy_primitives::Bytes` field decoded via ABI from attacker-controlled `PostRequest.body` (an ISMP message dispatched from a source chain's contract), with no length validation before being used, unlike the `to`/recipient field which is explicitly checked for 32 or 20 bytes.

### Title
Panic-induced Denial of Service via unchecked `message.from` length in `on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` decodes the ABI-encoded `Message` from an untrusted ISMP `PostRequest.body`. When the message carries optional calldata (`message.data` non-empty) with no `signature`, the code derives the calldata-dispatch origin straight from `message.from` without validating its length, unlike the `to`/beneficiary field a few lines above which is explicitly checked for 32 or 20 bytes.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, lines 176-186:

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],
        ))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
``` [1](#0-0) 

`message.from` is an `alloy_primitives::Bytes` field of the ABI-decoded `Message` struct, sourced entirely from the ISMP request body which is attacker-controlled (any relayer can submit any bytes as the ABI-encoded payload, only the top-level `PostRequest.from`/`source` contract mapping is checked via `ContractToAsset`, not the length of the inner `Message.from` field): [2](#0-1) 

Two distinct panics are reachable:
- `if source.is_evm()`: `from_bytes.len() - 20` is an unchecked `usize` subtraction; if `from_bytes.len() < 20`, this either panics with subtraction overflow (debug builds) or wraps to a huge value causing a slice-index-out-of-bounds panic (release builds) when used as a range start.
- `else` branch (non-EVM source): `account.copy_from_slice(from_bytes)` panics unless `from_bytes.len()` is exactly 32 (`copy_from_slice` requires equal lengths).

By contrast, the `to`/beneficiary field a few lines earlier explicitly validates length and returns a typed error (`HftError::InvalidRecipientLength`) instead of panicking: [3](#0-2) 

This is directly analogous to the CVE-2023-43279 bug class: a crafted, low-privilege input (crafted CLI/cidr argument in Tcpreplay; here, a crafted cross-chain ISMP message body) reaches an arithmetic/length-assumption that is not validated, causing an unhandled panic instead of an error path.

### Impact Explanation
A panic inside `on_accept`, which is invoked from the pallet-ismp message-handling dispatch path for incoming ISMP `PostRequest`s, aborts execution of that extrinsic/transaction. Depending on how `IsmpModule::on_accept` is invoked by the runtime's handler (typically within a dispatchable that is expected to not panic), this can crash block execution for that transaction, causing the relayer/message-dispatch pipeline for HyperFungibleToken messages to fail. Any account holding a registered `ContractToAsset` mapping (i.e., any deployed HFT token contract) can trigger this by crafting a message body with `data` non-empty, no `signature`, and a `from` value whose length is neither 20 nor 32 bytes as required by the corresponding source-chain branch. This is a message/route availability issue reachable by any relayer delivering a message from a registered source contract — matching the "route unable to deliver messages" impact category.

### Likelihood Explanation
High for an attacker who controls (or can spoof, via a malicious/compromised source-chain contract already registered in `ContractToAsset`) the encoded `Message.data`/`from` fields of a cross-chain post request targeting the HFT pallet. No signature or special privilege is needed beyond being a known source contract for a registered asset — an attacker can craft the ABI payload itself, since only `body` decoding via `Message::abi_decode` is required to succeed, and `from` accepts arbitrary-length `Bytes` at the ABI level.

### Recommendation
Validate `message.from`'s length before use, matching the existing pattern used for `message.to`/`beneficiary_bytes` (return `HftError::InvalidRecipientLength`-style typed error instead of panicking) for both the EVM (`from_bytes.len() == 20`) and non-EVM (`from_bytes.len() == 32`) branches, and avoid unchecked `usize` subtraction from `.len()`.

### Proof of Concept
Construct a `PostRequest` where the source contract is registered via `ContractToAsset`, with body encoding a `Message` such that:
- `data` is non-empty and decodes to a valid `SubstrateCalldata` with `signature: None`.
- `from` is set to a `Bytes` of length e.g. 5 bytes (neither 20 nor 32).

Calling `module.on_accept(post)` for an EVM source will attempt `from_bytes.len() - 20` = `5usize - 20`, which panics with subtraction overflow; for a non-EVM source it will panic in `copy_from_slice` due to a length mismatch. This is a direct extension of the existing regression test pattern in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs` (e.g. `should_receive_asset_with_calldata`), replacing the well-formed 20-byte `from` with a malformed length.
