### Title
Object ownership cycles create permanently-locked custody with no bounded recovery path - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::transfer_raw` (and therefore the public `transfer`/`transfer_call`/`transfer_to_object` entry points) only validates that the **object being moved** is currently owned (directly or indirectly) by the calling signer. It never validates anything about the **destination** address. This allows any unprivileged owner of two objects to construct a 2-object ownership cycle (`A.owner == B`, `B.owner == A`) using only the standard public `transfer` entry function. Once the cycle exists, no account can ever again satisfy `verify_ungated_and_descendant`'s walk-to-signer check for either object, so the standard transfer path permanently reverts, and any Fungible-Asset stores, Token objects, or other resources held at those two addresses become unrecoverable.

### Finding Description
`transfer_raw` calls `verify_ungated_and_descendant(owner_address, object)` where `object` is the address being moved, not `to`: [1](#0-0) 

`verify_ungated_and_descendant` only walks the ownership chain starting at the moved object up to the transaction signer; it never inspects the destination chain at all: [2](#0-1) 

Because of this, a user `U` who owns two ordinary objects `A` and `B` can:
1. `object::transfer(U, B, address_of(A))` — legal, since `B` is currently owned directly by `U` (chain match is instant), regardless of the fact that the destination `A` is also owned by `U`. Result: `B.owner == A`.
2. `object::transfer(U, A, address_of(B))` — legal, since `A` is still currently owned directly by `U` (the check only inspects `A`'s own chain, not `B`'s). Result: `A.owner == B`.

After step 2, `A.owner == B` and `B.owner == A`: a two-node cycle with no path back to any account-controlled address.

Any subsequent attempt to move `A` or `B` via the normal `transfer`/`transfer_call`/`transfer_to_object` API re-invokes `verify_ungated_and_descendant`, whose `while` loop is bounded by `MAXIMUM_OBJECT_NESTING`, and since the signer's address is never encountered while alternating between `A` and `B`, the call deterministically aborts with `EMAXIMUM_NESTING`: [3](#0-2) 

This closely mirrors the bounded/unbounded asymmetry in the source report: `owns` and `verify_ungated_and_descendant` are gas-bounded via `MAXIMUM_OBJECT_NESTING`, but `root_owner` walks the same kind of chain with **no bound at all**: [4](#0-3) 

confirming that the framework itself assumes ownership graphs are acyclic DAGs terminating at an account — an invariant that `transfer_raw`/`verify_ungated_and_descendant` fails to enforce because it never checks the destination side of a transfer.

### Impact Explanation
Once the cycle is formed, any `FungibleStore`, `Token`/`AmbassadorToken`-style resource, or other object-held value living at address `A` or `B` becomes permanently unreachable through the standard, non-privileged `object::transfer` family of functions — the only transfer mechanism most objects expose (objects typically do not retain a `TransferRef`/`ExtendRef` after creation). This is a direct match to the required custody impact: "Permanent lock or non-recoverable loss of object-held ... value," since ordinary primary-fungible-store balances, tokens, or nested objects placed under `A`/`B` can no longer be moved out through any code path that depends on `verify_ungated_and_descendant` succeeding. It also creates an unbounded-gas condition on any code that calls `root_owner` for such objects, echoing the exact bug class in the seed report (compute exhaustion via an unbounded ownership walk), but with the more severe consequence of asset lock rather than mere query slowdown.

### Likelihood Explanation
No privileged capability, `TransferRef`, or admin action is required — only two ordinary objects owned by the same account and two calls to the public `object::transfer` entry function. This can happen accidentally in composable protocols that programmatically re-parent objects (e.g., wrapping/rebalancing logic that nests objects into each other), or be intentionally triggered by an attacker who tricks a victim contract/flow into performing the two transfers (e.g., via a malicious dispatch hook, or a vault/aggregator that blindly executes user-supplied transfer instructions on objects it manages).

### Recommendation
`verify_ungated_and_descendant` (or `transfer_raw`) should also validate the destination side, e.g., reject transfers where `to` is (or transitively becomes) a descendant of the object being moved, preventing cycle formation. At minimum, before mutating `object_core.owner`, walk `to`'s ownership chain and abort if it ever reaches `object` (the object being moved), enforcing the DAG invariant that the framework's comments and `root_owner` implicitly assume.

### Proof of Concept
```move
// U owns objects A and B (e.g., via object::create_object(&U))
object::transfer(&U, B, object::address_from_constructor_ref(&a_ref)); // B.owner = A
object::transfer(&U, A, object::address_from_constructor_ref(&b_ref)); // A.owner = B

// Now A.owner == B, B.owner == A. Any further transfer aborts:
object::transfer(&U, A, signer::address_of(&U)); // aborts with EMAXIMUM_NESTING
// Any FungibleStore/Token resource stored at A or B's address is now permanently stuck.
```

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
