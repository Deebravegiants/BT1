### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` binds only the JSON payload bytes to the app's `client_secret`. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken directly from unauthenticated HTTP headers — are never included in the signed material, yet they are trusted and forwarded verbatim to the app's webhook handler as the tenant/routing identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the shop domain, topic, webhook id, and API version straight from HTTP headers: [1](#0-0) 

but the value that actually gets HMAC-verified is only the raw body: [2](#0-1) 

`Registry.process` accepts the request once `Utils::HmacValidator.validate(request)` succeeds, and then hands the (unauthenticated) `shop`, `topic`, and `webhook_id` values straight to the registered handler as `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate_signature` computes `HMAC(client_secret, to_signable_string)` and compares it to the `hmac-sha256` header — it never mixes in the shop, topic, or webhook id: [4](#0-3) 

Because a single app-level `client_secret` (`Context.api_secret_key`) is shared across every shop that has installed the app, any shop that has installed the app can obtain a validly-HMAC-signed `(raw_body, hmac)` pair by triggering a real webhook to itself (e.g. `orders/create`). Since `shop`, `topic`, and `webhook_id` are not part of the signed material, that same `(raw_body, hmac)` pair remains valid when replayed with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a different shop that also uses the app. `Registry.process` will pass HMAC validation and invoke the handler with `WebhookMetadata.shop` set to the victim shop while the body content is entirely attacker-controlled.

### Impact Explanation
This breaks the identity binding "shop that produced/authenticated the HMAC" vs. "shop the application attributes and stores the payload under." An unprivileged app user (any shop that installs the app) can inject attacker-controlled webhook data attributed to a different tenant (victim shop) of the same app, since the tenant identifier is never covered by the HMAC. Depending on how the host application keys its data store off `data.shop`, this is a cross-tenant data injection/confusion vulnerability.

### Likelihood Explanation
Any shop that installs the app can generate a legitimately-signed webhook body via their own store's webhook delivery (no special privilege required beyond installing the app, which is the "unprivileged" actor model here). Forging headers on a replayed HTTP request to the app's own webhook endpoint requires no cryptographic secret, only knowledge that `shop`/`topic`/`webhook_id` aren't bound to the signature — which is a property of this gem's implementation, not something the host app can compensate for since the gem itself performs the HMAC check and packages `WebhookMetadata` from the unauthenticated headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material — e.g., verify against `"#{shop}\n#{topic}\n#{raw_body}"` rather than just `@raw_body` — or otherwise cryptographically bind the header-derived routing fields to the signature so a payload signed for one shop cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` (which has the target app installed) receives a genuine webhook from Shopify: raw body `B`, header `x-shopify-hmac-sha256: H` (H = HMAC-SHA256(client_secret, B)), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com` (a shop that also has the app installed).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and matches `H` — validation succeeds because `to_signable_string` never included the shop header.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the attacker's crafted body to be processed/stored under the victim shop's identity.
