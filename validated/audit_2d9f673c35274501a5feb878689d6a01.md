### Title
Webhook shop identity spoofing via HMAC-unbound `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The `ShopifyAPI::Webhooks::Request` class exposes a `shop` attribute that is trusted by `Webhooks::Registry.process` as the identity of the tenant a webhook belongs to, but this value is never included in the HMAC signature that authenticates the webhook payload.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`) as authenticated tenant metadata passed to the app's handler: [1](#0-0) 

However, `Webhooks::Request#to_signable_string` — the data actually covered by the HMAC — is only the raw request body: [2](#0-1) 

While `shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is completely outside the signed data: [3](#0-2) 

Contrast this with the OAuth callback path, `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` into the signed string so that the HMAC cryptographically binds the shop identity to the payload: [4](#0-3) 

No equivalent binding exists for webhooks. The identity equality the system implicitly relies on — `hmac_signed_shop == header_shop` — never holds, because `hmac_signed_shop` isn't a value that exists at all (only the body is signed). This is exactly the "field acted on but not covered by the HMAC" bug class: the HMAC proves the *body* bytes were produced with the app's secret, but proves nothing about which shop that body pertains to. An attacker who can obtain any single valid `(raw_body, hmac)` pair signed by Shopify for the app (e.g., by triggering a webhook event on their own installed/development shop, which they fully control) can replay that exact body+HMAC pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` will pass (it never inspects the header), and `Registry.process` will hand the handler a `WebhookMetadata` object asserting `shop: "victim-shop.myshopify.com"` with attacker-controlled body content.

### Impact Explanation
Applications built on this gem are expected to use `WebhookMetadata#shop` to resolve which tenant's session/data store to act on (this is the documented purpose of the field, and it's the only shop identifier provided by the library for webhook processing). Since the shop value is unauthenticated relative to the signed payload, an attacker can inject falsified data (product/order/customer-redact payloads, GDPR requests, etc.) attributed to an arbitrary victim shop — this is a cross-tenant integrity/confidentiality break entirely within the trust boundary this gem is responsible for (HMAC verification of webhooks). It satisfies the "cross-tenant access" Critical impact category, since the library's own verification primitive is what host applications rely on to establish per-tenant trust for webhook data.

### Likelihood Explanation
The attacker only needs to be an unprivileged party capable of installing/operating their own shop against the app (any normal merchant), which lets them generate legitimate `(body, HMAC)` pairs signed with the app's secret without ever learning the secret itself. No access token, `client_secret`, or privileged access is required — only the ability to trigger any webhook-eligible event on their own store and replay the resulting request with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated data before trusting it: either (a) require host applications to independently verify `request.shop` against an already-established session/install record before acting on webhook data (document this requirement clearly), or (b) have `HmacValidator`/`Webhooks::Request` incorporate the `shop-domain` (and `topic`) header into the signable string context validated per-tenant, or (c) cross check `request.shop` against a list of shops for which the webhook `topic` registration/subscription is known to exist for that specific installation before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/allows a webhook topic (e.g., `products/update`).
2. Attacker triggers the event on their own shop, capturing the legitimate webhook HTTP request Shopify sends to the app's endpoint — headers include `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`, with a body fully controlled by the attacker (e.g., editing product title/description to arbitrary attacker-chosen text).
3. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replaces the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` succeeds because it only checks `Digest.hexencode(...)` against the raw body [5](#0-4)  using `Utils::HmacValidator.validate_signature` [6](#0-5) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)` [7](#0-6) , causing the host application to act on attacker-controlled data as if it originated from the victim shop.
