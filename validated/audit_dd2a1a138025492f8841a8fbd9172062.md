### Title
Disabled unfreeze/refreeze in the Sequential submission path leaves EvmHost's mandatory-consensus freeze window permanently unenforced - (File: tesseract/consensus/admin-relayer/src/batch.rs)

### Summary
The `tesseract-admin-relayer` protects `EvmHost` mandatory authority-set-handover consensus updates by bracketing `handleConsensus` inside an unfreeze → update → refreeze sequence, exactly like Docker recreates iptables isolation rules around a privileged network event. In `submit_mandatory_sequential`, both the unfreeze and refreeze transactions are commented out, so for every chain configured with `submission_mode = "sequential"` the bracket is never applied even though the surrounding documentation and code comments still assert it is.

### Finding Description
`tesseract-admin-relayer` documents two submission paths for a mandatory BEEFY consensus update: `Batched` — a single ERC-7821 batch `[unfreeze, handleConsensus, freeze]` — and `Sequential` — three plain EOA transactions `setFrozenState(None) → handleConsensus → setFrozenState(All)` [1](#0-0) . The `lib.rs` module doc reiterates that "Each consensus update is submitted as an ERC-7821 batch that atomically unfreezes the ISMP host, applies the update, and re-freezes it" [2](#0-1) , and the `run_mandatory_task` module diagram states the flow as `unfreeze → handleConsensus → freeze` [3](#0-2) .

In practice, `submit_mandatory_sequential` computes the unfreeze/freeze calldata but never sends them — both transmission calls are commented out, leaving only `handleConsensus` executed: [4](#0-3) 

The doc comment directly above this function still claims "The refreeze step is always attempted, even if the consensus step fails, to avoid leaving the host unfrozen" — the exact opposite of what the code does [5](#0-4) .

`EvmHost.setFrozenState` is the on-chain gate this bracket is supposed to toggle, restricted to admin or handler [6](#0-5) , and `HandlerV2`'s `notFrozen` modifier reads that same state to decide whether `handleConsensus` (and other handler entry points) may proceed [7](#0-6) . `SubmissionMode::Sequential` is explicitly intended for production chains that don't yet support EIP-7702 (the config names Soneium as an example) [8](#0-7) , so this is not a dead/test-only path — it is the live path for a subset of real deployed chains.

This is a direct structural analog of the Moby/firewalld bug: a protective gate (iptables isolation rules / EvmHost frozen state) is meant to be re-established immediately after a privileged, narrow-window operation (firewalld reload / mandatory consensus handover), but the re-establishment step is silently missing, leaving the resource in an open/exposed state indefinitely rather than only for the intended brief window.

### Impact Explanation
For every EVM chain configured with `submission_mode = "sequential"`, the freeze bracket around mandatory authority-set handovers never executes. Concretely:
- The host is never re-armed to `FrozenStatus.All` after a mandatory update lands, so whatever protection the freeze window is meant to provide against processing based on the authority set mid-handover is permanently absent for these chains, not just skipped for one update.
- Because the unfreeze call is also skipped, `handleConsensus` will only ever succeed on a Sequential-mode chain if the host is already unfrozen through some other means — meaning in steady state the host must be left in `FrozenStatus.None` for this relayer to function at all, which is precisely the exposed condition the batched path is designed to avoid outside the update window.
- This silently defeats a documented security control across an entire class of production chains (those without EIP-7702 support) without any error, alert, or on-chain signal — the relayer logs proceed as if the bracket succeeded.

Given CWE-909 (Missing Initialization of Resource) framing from the source report, this is a Medium-severity finding: it is a systemic control-plane weakening reachable by the natural operation of the mandatory consensus relayer, not requiring any additional attacker action to trigger — every authority-set handover on a Sequential-mode chain reproduces it.

### Likelihood Explanation
This triggers automatically and unconditionally on any `EpochChanged` notification for a chain configured with `submission_mode = "sequential"` — no attacker interaction is required to reach the disabled code path; it fires as part of normal relayer operation. Any deployment that enables `Sequential` mode (the documented fallback for non-EIP-7702 chains) is affected on every mandatory update cycle.

### Recommendation
Re-enable the commented-out `send_and_await_receipt` calls for both `_unfreeze_cd` and `_freeze_cd` in `submit_mandatory_sequential`, preserving the stated invariant that the refreeze is attempted even if the consensus step fails (e.g., wrap consensus submission so the freeze step runs in all code paths, matching the doc comment). Add a runtime assertion or test verifying `EvmHost.frozen()` returns to `FrozenStatus.All` after `submit_mandatory_sequential` returns, and add CI coverage exercising `SubmissionMode::Sequential` end-to-end so this regression cannot silently reoccur.

### Proof of Concept
1. Configure `tesseract-admin-relayer` for a chain with `submission_mode = "sequential"` (as documented for chains like Soneium) [9](#0-8) .
2. Trigger an `EpochChanged` notification so `run_mandatory_task` calls `submit_mandatory(&client, proof.message, SubmissionMode::Sequential)` [10](#0-9) .
3. Observe that `submit_mandatory_sequential` only sends the `handleConsensus` transaction; the `setFrozenState(None)` and `setFrozenState(All)` calls are commented out and never submitted [11](#0-10) .
4. Query `EvmHost.frozen()` before and after the run: it is unchanged by this call regardless of outcome, contradicting the doc-comment guarantee that the host is always left refrozen.
