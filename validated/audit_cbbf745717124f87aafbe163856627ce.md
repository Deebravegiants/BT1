Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the signed material. `HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (`lib/shopify_api/utils/hmac_validator.rb:27-31`), so `Registry.process` only proves the body's authenticity, then trusts the unauthenticated `request.shop` header to build `WebhookMetadata` passed to the app's handler (`lib/shopify_api/webhooks/registry.rb:188-199`).

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw body via HMAC but reads the `shop` (and `topic`/`api_version`/`webhook_id`) from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to attribute the payload to a tenant, breaking the binding `shop authenticated == shop whose bytes were signed`.

### Finding Description
`Registry.process` is the single trust boundary for inbound webhooks in this gem: [1](#0-0) 
It calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 
For `Webhooks::Request`, `to_signable_string` is hard-coded to the raw body only: [3](#0-2) 
Meanwhile `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the HMAC: [4](#0-3) 
Because the `shop` header sits outside the signed material, an attacker who controls (or has previously received, e.g. by installing the app on their own store) a validly-signed `raw_body`/HMAC pair for shop A can resend the identical body/HMAC pair while substituting the `shopify-shop-domain` header with victim shop B's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` forwards `request.shop` (now shop B) into `WebhookMetadata` given to the host application's handler: [5](#0-4) 
This is the same class of bug as the referenced report: a value that is *acted upon* (the tenant/shop identity used to key data in the host app) is not covered by the integrity check (the HMAC), so the two can be desynchronized by an attacker-controlled input.

### Impact Explanation
This crosses a tenant boundary: a webhook payload cryptographically proven only to have originated from *some* authentic Shopify-signed source can be relabeled to any arbitrary shop domain chosen by the attacker, without possessing that shop's secret. Any host application that uses `WebhookMetadata#shop` (as documented/recommended in `docs/usage/webhooks.md`) to select which tenant's data to update, delete, or redact — including the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics — can be tricked into applying webhook payloads under a victim's tenant identity. This matches the "cross-tenant access" class of Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to be able to generate at least one validly-HMAC-signed webhook body under the app's `client_secret` — achievable simply by installing the app on their own development/trial store (a normal, unprivileged action) and capturing the webhook Shopify sends them. They then replay that exact body/HMAC with a forged `shop-domain` header pointing at any target shop. No access token, leaked credential, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified for webhooks, or otherwise cryptographically bind the `shop` header to the payload before it is trusted (e.g., verify it out-of-band against a known, previously-registered shop record rather than passing it through unchecked to the handler). At minimum, document that `WebhookMetadata#shop` is not authenticated and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any registered webhook topic (e.g. `orders/create`) and capture the raw POST body plus the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it is computed by Shopify itself over that exact body with the app's real secret.
2. Replay that identical raw body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. In `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`), `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) only checks the raw body, which is unmodified.
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"`, even though the body actually originated from the attacker's shop — demonstrating the host app receives attacker-controlled, unauthenticated tenant attribution for authentically-signed data.
