### Title
Session ID derivation trusts JWT `sub` claim without enforcing the admin-session binding check applied elsewhere in the same class - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token` derives an online session id as `"#{shop}_#{sub}"` directly from the decoded JWT's `sub` claim [1](#0-0) , but `ShopifyAPI::Auth::JwtPayload` itself defines a stricter accessor, `shopify_user_id`, which only trusts `sub` as a user id when `admin_session_token?` (i.e. `iss.end_with?("/admin")`) is also true [2](#0-1) [3](#0-2) . The primary session-id derivation path used by embedded-app request authentication (`SessionUtils.current_session_id` → `session_id_from_shopify_id_token` → `jwt_session_id`) never performs this `admin_session_token?` check, so any correctly-signed-for-this-app JWT whose `aud` matches `Context.api_key` — regardless of what context/`iss` it was actually issued for — is accepted to compute an "online admin session id."

### Finding Description
`JwtPayload#initialize` only validates the `aud` claim against `Context.api_key` [4](#0-3) ; it does not validate that `iss` corresponds to an admin/embedded-app session token as part of construction. That extra binding (`admin_session_token?`) is applied only inside the `shopify_user_id` accessor [2](#0-1) [3](#0-2) , which nothing else in the gem calls.

`SessionUtils.session_id_from_shopify_id_token` bypasses this accessor entirely and instead reads `payload.sub` directly, feeding it into `jwt_session_id(shop, user_id)`, which just concatenates `"#{shop}_#{user_id}"` with no further checks [1](#0-0) . This is the exact function documented and used to compute the current session id for embedded-app requests [5](#0-4) , feeding `SessionUtils.current_session_id`, which host apps use to look up a previously stored `Session`/access token in their session store [6](#0-5) .

The equality that should hold but doesn't: `session_id computed from token == session_id only if token.iss indicates an admin/embedded session token`. Instead the code enforces: `session_id computed from token == "#{dest}_#{sub}" for ANY token with aud == api_key`, dropping the `iss`-based binding that the library itself defines as necessary elsewhere.

### Impact Explanation
If Shopify issues any other JWT sharing the same `aud` (app client id) but a different `iss` (i.e., not ending in `/admin` — e.g. a token scoped to a different embedded surface/extension context for the same app and shop), an unprivileged party in possession of such a token can compute the identical `"#{shop}_#{sub}"` session id used to key the host application's online-session store for a genuine admin user. If the host app's session storage (e.g. the companion `shopify_app` gem, explicitly recommended by this gem's docs for persistence [7](#0-6) ) is looked up by this id, the mismatch lets a non-admin-context token retrieve or collide with another identity's stored access token — an authentication/session-identity-boundary bypass with no need for a merchant access token, refresh token, or `client_secret`.

### Likelihood Explanation
Requires only a validly-signed-for-this-app JWT (any `aud`-matching token) that an unprivileged party can otherwise obtain through non-admin surfaces of the same app; no leaked credentials, TLS interception, or privileged account access are needed to trigger the identifier collision, since the check that would prevent it (`admin_session_token?`) exists in the codebase but is simply never invoked on this path.

### Recommendation
Have `SessionUtils.session_id_from_shopify_id_token` (and `jwt_session_id`) require `payload.admin_session_token?` (or equivalently use `payload.shopify_user_id` instead of raw `payload.sub`) before deriving an online session id, so the same `iss`-binding enforced in `JwtPayload#shopify_user_id` is consistently applied wherever a session id is derived from a JWT.

### Proof of Concept
1. Obtain any JWT valid for the target app (`aud == Context.api_key`) whose `iss` does not end in `/admin` (a non-admin-session-token context for the same app/shop).
2. Call `ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token(id_token: token, online: true)`.
3. Observe it returns `"#{shop}_#{sub}"` exactly as it would for a genuine admin session token, because `admin_session_token?` is never checked in this call path [1](#0-0) , unlike the `shopify_user_id` accessor which does gate on it [2](#0-1) .

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

### Sessions

Sessions are required to make requests with the REST or GraphQL clients. This Library provides helpers for creating sessions via OAuth. Helpers are provided to retrieve session ID from a HTTP request from an embedded Shopify app or cookies from non-embedded apps.

For *embedded* apps:

If you have an `HTTP_AUTHORIZATION` header or `id_token` from the request URL params , you can pass that as `shopify_id_token` into:
- `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, nil, true)` for online (user) sessions or
- `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, nil, false)` for offline (store) sessions.

`current_session_id` accepts shopify_id_token in the format of `Bearer this_token` or just `this_token`.

You can also use this method to get session ID:
- `ShopifyAPI::Utils::SessionUtils::session_id_from_shopify_id_token(id_token: id_token, online: true)` for online (user) sessions or
- `ShopifyAPI::Utils::SessionUtils::session_id_from_shopify_id_token(id_token: id_token, online: false)` for offline (store) sessions.
