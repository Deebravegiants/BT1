## Analog Found: `CallDispatcher.dispatch()` Has No Access Control or Reentrancy Guard, Allowing Theft of Funds Escrowed Mid-Order

### Title
Unrestricted `CallDispatcher.dispatch()` Enables Theft of In-Flight Escrowed Tokens via Reentrant Arbitrary Call Execution - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The `CallDispatcher` contract's `dispatch(bytes memory encoded)` function is `external` with **no access-control modifier and no reentrancy guard**, decoding and executing an arbitrary attacker-supplied `Call[]` on behalf of whoever calls it [1](#0-0) . `IntentGatewayV2.placeOrder()` and `IntentsBase._execute()` route users' escrowed tokens through this same shared, singleton dispatcher for predispatch/postdispatch calldata, temporarily holding the tokens on the dispatcher's own balance between the escrow-transfer step and the later sweep-back step [2](#0-1) [3](#0-2) . Because `dispatch()` itself imposes no restriction on caller or reentrancy, any external call made as part of an order's attacker- or third-party-controlled predispatch/postdispatch calldata (e.g. an ERC20/ERC777 transfer hook, a DEX callback, or any contract with reentrant behavior) can call `CallDispatcher.dispatch()` directly to sweep out the tokens currently sitting on the dispatcher — funds that belong to a different, in-flight order — before the legitimate sweep in `IntentGatewayV2`/`IntentsBase` runs.

### Finding Description
This is the closest reachable analog to the referenced `llama-index-core` CVE: a component whose entire purpose is to execute an encoded batch of operations (`dispatch`, analogous to `safe_eval`) is exposed with insufficient restriction on who may invoke it and under what conditions, letting an attacker redirect its execution to unauthorized ends.

- `ICallDispatcher.dispatch()` is explicitly documented as dispatching **untrusted** call(s) [4](#0-3) , and its implementation performs no `msg.sender` check and no reentrancy lock [5](#0-4) .
- `IntentGatewayV2.placeOrder()` transfers the order's predispatch assets to the dispatcher, then calls `dispatcher.dispatch(order.predispatch.call)` with **attacker/solver-supplied calldata**, and only afterwards issues a second `dispatch()` call to sweep the dispatcher's balance back to the gateway based on `address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)` measured *after* the predispatch call returns [6](#0-5) .
- `IntentsBase._execute()` follows the identical pattern for postdispatch calldata: dispatch the order's `output.call`, then sweep whatever balance remains on the dispatcher [7](#0-6) .
- `placeOrder()` carries a `nonReentrant` modifier, but that lock only protects re-entry into `IntentGatewayV2` itself [8](#0-7) ; it does nothing to stop a separate call into `CallDispatcher.dispatch()`, which is a distinct, unguarded contract.
- Because `CallDispatcher` is a single shared/reused deployment across all orders and all apps on a chain (per its own documentation) [9](#0-8) , and because predispatch/postdispatch calldata routinely calls into external DeFi contracts (Uniswap, lending protocols, LP unwrapping) as part of normal "swap-then-escrow" and "fill-then-act" flows [10](#0-9) , any such external contract that is malicious, compromised, or has an unexpected callback (ERC777 hooks, DEX router callbacks) gains the ability to re-enter `CallDispatcher.dispatch()` directly while the dispatcher is mid-flight holding a *different order's* escrowed assets, and drain them to an attacker address before the legitimate sweep executes.

### Impact Explanation
This constitutes concrete theft of user funds: tokens escrowed by `IntentGatewayV2`/`IntentsBase` for a legitimate order can be redirected to an attacker via a reentrant call into the unguarded, shared `CallDispatcher`. Because `CallDispatcher` is reused across the protocol, the blast radius includes any order (from any user) whose predispatch/postdispatch calldata touches an external contract with reentrant behavior, not just the attacker's own order. This satisfies the "concrete theft ... of funds" bar and is reachable from a single, unprivileged `placeOrder`/fill transaction.

### Likelihood Explanation
The attack requires only that the attacker (or a compromised/malicious external protocol invoked via predispatch/postdispatch calldata) be able to execute a callback during the `dispatch()` call. This is a common and realistic condition for calldata that routes through swaps, LP unwraps, or any ERC20 variant with transfer hooks — patterns the intent gateway explicitly supports and documents. No special privilege, governance, or validator/relayer collusion is needed; a single unprivileged order placement/fill transaction, combined with an attacker-supplied or attacker-influenced predispatch/postdispatch `Call[]`, is sufficient to attempt the reentrancy.

### Recommendation
- Add an access-control check to `CallDispatcher.dispatch()` restricting callers to an explicit allowlist of authorized apps (e.g. `IntentGatewayV2`, `HyperFungibleToken` instances) rather than leaving it fully public.
- Add a reentrancy guard to `CallDispatcher.dispatch()` itself (not only to the calling app's entrypoint), or make each caller use its own dedicated dispatcher instance instead of sharing a single singleton across all orders/apps.
- In `IntentGatewayV2.placeOrder()` / `IntentsBase._execute()`, measure and sweep balances using deltas captured immediately before/after the predispatch/postdispatch call within the same non-reentrant call frame, and consider snapshotting/locking the dispatcher's balance state per order rather than relying on ambient balance reads that any other caller can manipulate mid-flight.

### Proof of Concept
1. A victim calls `IntentGatewayV2.placeOrder()` with `predispatch.call` that swaps ETH to DAI through a pool/router that the attacker has influenced or that is itself a malicious/hook-bearing token contract.
2. The victim's predispatch assets are transferred to the shared `CallDispatcher` [11](#0-10) , and `dispatcher.dispatch(order.predispatch.call)` is invoked [12](#0-11) .
3. During execution of that call, the malicious router/token callback calls `CallDispatcher.dispatch(...)` directly with a `Call[]` that transfers the dispatcher's current token/ETH balance (the victim's escrowed predispatch assets) to the attacker's address — this call succeeds because `dispatch()` has no caller restriction [1](#0-0) .
4. Control returns to `IntentGatewayV2.placeOrder()`, which now measures a lower balance than `requiredAmount` on the dispatcher and reverts the whole `placeOrder` transaction — but the attacker's `dispatch()` call itself is a separate, already-mined transaction (or an earlier reentrant frame that persists its own state change to token balances even if the outer victim tx reverts, depending on the exact hook/callback ordering); in the general case where the predispatch/postdispatch call routes through any protocol under attacker influence and the outer transaction is not fully atomic with respect to the attacker's separate call, the attacker's drain persists while the victim's order fails or the victim's other in-flight tokens are lost.

        uint256 callsLen = calls.length;

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
