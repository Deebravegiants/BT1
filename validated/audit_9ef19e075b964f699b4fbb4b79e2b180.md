### Title
Stale `TombStone` from a prior soft-burn lets an unrelated past owner reclaim an object legitimately sent to the burn address by a later owner - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::burn` attaches a `TombStone{original_owner}` to an object without changing its `owner` field or restricting further transfers. Ordinary ownership transfers (`transfer`, `transfer_raw`, `transfer_to_object`) never clear this `TombStone`. Only the ref-based `transfer_with_ref` path explicitly purges it. Consequently, if account A soft-burns an object and later legitimately transfers it away (via ordinary transfer), the stale `TombStone{original_owner: A}` persists. If any subsequent, unrelated owner B later moves the object to `BURN_ADDRESS` (the documented, ordinary way to permanently give up an object), A can call `unburn` and reclaim the object from `BURN_ADDRESS`, seizing custody of an object it no longer legitimately owns.

### Finding Description
`object::burn` ( [1](#0-0) ) only requires the caller to be the current owner, then does `move_to(&create_signer(object_addr), TombStone { original_owner })`. It does not disable ungated transfer and does not alter `ObjectCore.owner`, so the "burnt" object is still fully transferable by its owner via the ordinary transfer API.

`unburn` ( [2](#0-1) ) supports two reclaim paths:
- if the *current* owner equals the caller, it simply clears the `TombStone` (soft-burn undo).
- if the *current* owner is `BURN_ADDRESS` ("old functionality"), it checks only that `TombStone.original_owner == caller`, then force-transfers the object back to that caller via `transfer_raw_inner`.

The ordinary transfer path, `transfer_raw_inner` ( [3](#0-2) ), only updates `object_core.owner` and emits a `Transfer` event — it never checks for or removes an existing `TombStone`. In contrast, `transfer_with_ref` for `LinearTransferRef` explicitly does: "Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later" ( [4](#0-3) ). This comment shows the developers were aware of exactly this hazard, but the fix was applied only to the ref-based transfer function, not to the plain `transfer`/`transfer_raw`/`transfer_to_object` entry points that ordinary users actually call.

Because `to` in `transfer_raw` is an arbitrary address with no requirement that it be an `ObjectCore` ( [5](#0-4) ), any current owner can send an object straight to `BURN_ADDRESS` using the normal `object::transfer` entry function — this is the documented purpose of `BURN_ADDRESS` ("Address where unwanted objects can be forcefully transferred to", [6](#0-5) ).

Exploit sequence:
1. Account A owns object O and calls `object::burn(A, O)`. This attaches `TombStone{original_owner: A}` to O; `O.owner` remains `A`.
2. A calls ordinary `object::transfer(A, O, B)`. Ownership legitimately moves to B. The `TombStone` is *not* cleared because `transfer_raw_inner` never checks for it.
3. B, wanting to permanently dispose of O (a documented use of `BURN_ADDRESS`), calls `object::transfer(B, O, BURN_ADDRESS)`.
4. A (who has no relationship to B and no current ownership) calls `object::unburn(A, O)`. Since `O.owner == BURN_ADDRESS` and the stale `TombStone.original_owner == A`, the check passes and `transfer_raw_inner(O, A)` executes, reassigning `ObjectCore.owner` to A.

A has thereby seized custody of an object it sold/transferred away, diverting it from wherever B intended it to go (or from anyone else who might legitimately expect burnt objects to stay unowned/irrecoverable).

### Impact Explanation
This is an unprivileged ownership-reassignment / theft primitive on the core Aptos object model, which underlies fungible asset stores, token objects, and any object-held value. Any object that has ever been soft-burned by a past owner and later legitimately transferred carries a hidden, permanent "landmine": whoever holds the `TombStone.original_owner` slot can, at any future point, reclaim the object the instant any current owner sends it to `BURN_ADDRESS` — a common, protocol-sanctioned disposal action. This directly breaks the "Object creation, transfer, burn ... ownership refs must preserve the intended controller" custody invariant, causing unauthorized owner reassignment of object-held value (e.g., an object holding a `FungibleStore`, token, or other asset).

### Likelihood Explanation
Likelihood is high in any workflow where objects are soft-burned and later re-transferred through the ordinary transfer path (a fully supported, un-gated operation), and where any current owner subsequently transfers the object to `BURN_ADDRESS` (the documented mechanism for voluntarily giving up an object). No special privilege is required by the attacker (A) — only that A was a prior owner who once called `burn`. The bug requires no race condition or unusual gas/timing assumptions, only ordinary sequential transactions.

### Recommendation
Clear any existing `TombStone` for the object whenever ownership changes via the ordinary transfer paths (`transfer_raw_inner`), exactly as is already done for `transfer_with_ref`'s `LinearTransferRef` path. Alternatively, `unburn`'s `BURN_ADDRESS` branch should validate that the `TombStone.original_owner` is still the address that *most recently* sent the object to `BURN_ADDRESS` (e.g., by re-deriving/refreshing `original_owner` on every ordinary transfer rather than only checking it once at burn time), or the legacy `BURN_ADDRESS` reclaim path should be removed for objects that have undergone any ordinary (non-ref) transfer since the `TombStone` was created.

### Proof of Concept
```move
#[test(a = @0x123, b = @0x456)]
fun test_stale_tombstone_theft(a: &signer, b: &signer) {
    let (_, hero) = create_hero(a);          // A owns `hero`
    burn(a, hero);                           // A soft-burns; TombStone{original_owner: A} attached, owner stays A
    transfer(a, hero, signer::address_of(b)); // ordinary transfer A -> B; TombStone NOT cleared
    // B now legitimately owns `hero` and later disposes of it as documented:
    transfer(b, hero, BURN_ADDRESS);          // ordinary transfer B -> BURN_ADDRESS
    // A, unrelated to B's disposal, reclaims the object using the stale TombStone:
    unburn(a, hero);
    assert!(hero.owner() == signer::address_of(a), 0); // A now owns an object it previously gave up
}
```
This mirrors the existing test `test_cannot_unburn_after_transfer_with_ref` ( [7](#0-6) ), which proves the ref-based path is protected, but no equivalent test exists — and none passes — for the ordinary `transfer` path, confirming the gap.

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
