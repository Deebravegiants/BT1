### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from an unauthenticated HTTP header while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but then trusts the `shop` (tenant) identifier from an HTTP header that is never covered by that HMAC. Anyone who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — e.g. by installing the app on their own store and capturing a genuine webhook delivery — can replay that exact body to the app's public webhook endpoint while freely setting the `X-Shopify-Shop-Domain` header to an arbitrary victim shop. The HMAC check still passes (it only verifies the body/secret pair), and the forged `shop` value is handed straight to the application's webhook handler as the authoritative tenant, producing cross-tenant data confusion/injection.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as just the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from a caller-supplied header with no binding to the signature: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` field — it has no knowledge of `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` performs exactly this check and then immediately forwards the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`) to the application handler as the trusted tenant/event identity, with no cross-check that this shop is a session/tenant known to the app: [4](#0-3) 

The binding that should hold is:
`HMAC-verified(raw_body) == identity(shop, topic, webhook_id)` used by the handler.

In this implementation, only `raw_body` is bound to the HMAC; `shop` (and other headers) are independent, attacker-settable inputs. Because `api_secret_key` is the same shared "client secret" across every shop that installs the app (it is not per-shop), a merchant who installs the app on their own store obtains at least one legitimately Shopify-signed `(raw_body, hmac)` pair. That pair remains cryptographically valid for the exact same `raw_body` regardless of which `X-Shopify-Shop-Domain` header accompanies it, since the header is outside the signed content.

### Impact Explanation
An attacker (any merchant who can install the app, i.e. an "unprivileged" party with respect to other tenants) can:
1. Install the target app on their own store and capture a genuine webhook delivery (`raw_body`, `x-shopify-hmac-sha256`).
2. Replay that exact `raw_body` + `hmac` to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` header for a victim shop.
3. `Registry.process` validates the HMAC successfully (it only checks the body) and dispatches to the handler with `shop: <victim-shop>`, `topic`, and `webhook_id` all attacker-chosen.

Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop records, triggering side effects, canceling/refunding, disabling features, writing audit logs attributed to a shop) can be forced to act on/for a shop the attacker does not control — a cross-tenant confusion/injection primitive. This satisfies the "Critical - cross-tenant access" bar since it lets a single-tenant attacker inject data that the app processes as if it belonged to a different tenant.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to have (or create) an installation of the target app somewhere (trivial for public apps, and the shared `api_secret_key` design means the captured signature is valid across all shops of that app), and to be able to reach the app's webhook endpoint directly with custom headers (standard for any public HTTPS endpoint; the gem does not restrict by source IP or any Shopify-specific transport guarantee). This exactly mirrors Shopify's documented HMAC scheme (sign body only), so the exposure is inherent to how `Registry.process`/`Request` are wired in this gem, not a host-app misuse of a documented API.

### Recommendation
- Do not treat `request.shop` (or `topic`/`webhook_id`) as authoritative purely because the body HMAC validated. At minimum, require the application to supply/verify a shop it already has an active session for before invoking the handler, or
- Extend the signable content / verification step to also bind `shop`, `topic`, and `webhook_id` (e.g., by requiring the caller to pass the expected shop and comparing it against a stored, previously-authenticated value, or by only accepting webhooks for shops with an existing offline session), and
- Document explicitly in `Webhooks::Registry` that `WebhookMetadata#shop` is not cryptographically authenticated and must be independently verified by the host application before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally (uses the app's public/shareable installation flow, no special privilege needed).
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - body: `{"id":1,...}`
3. Attacker captures the exact raw body bytes and the `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new HTTP POST directly to the same webhook endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Webhooks::Request.new` parses this into a `Request` whose `hmac` matches (`Utils::HmacValidator.validate` only checks body+secret) — see [5](#0-4) .
6. `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop — see [6](#0-5) .
