### Title
Webhook HMAC only signs the request body, not the `shop-domain` header used for tenant attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` verifies the HMAC over the body only, yet `Registry.process` trusts `request.shop` (from the header) as the authoritative tenant identity when constructing `WebhookMetadata` passed to the app's handler.

### Finding Description
The identity binding that should hold is:
`hmac_valid(raw_body)` should imply `shop == origin_shop_that_produced(raw_body)`.

In practice the library breaks this equality:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#shop` (and `topic`, `webhook_id`, `api_version`) are parsed straight from headers with no cryptographic binding [2](#0-1) .
- `HmacValidator.validate`/`validate_signature` compute and compare the signature using only `verifiable_query.to_signable_string` (the body) [3](#0-2) .
- `Registry.process` checks only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (and the other unauthenticated headers) into `WebhookMetadata`, which is delivered to the app's handler as the trusted shop/tenant identity for this event [4](#0-3) .

Because the HMAC never covers `shop-domain`, an attacker who legitimately installs the target app on their own store (an ordinary unprivileged action) will receive genuine, validly-signed webhook deliveries (body + HMAC computed with the app's `client_secret`, which the attacker never sees but Shopify computes for them). That attacker can capture any such `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` hands the forged `shop` value straight to the handler as `WebhookMetadata#shop` — the very field the library exposes to callers specifically so they can attribute the event to a tenant.

### Impact Explanation
This crosses a tenant boundary without any credential, access token, or `client_secret` in the attacker's possession: the attacker only needs their own legitimate installation and network access to the app's public webhook URL. The library's own parsed, "verified" metadata (`data.shop`) can be made to point at any other merchant, satisfying the Critical "cross-tenant access" bar. This is a library-level defect, not a case of the host ignoring documented behavior — the library computes and exposes `shop` as if it were validated by the same HMAC check that gates `process`.

### Likelihood Explanation
Moderately likely to be exploitable in practice: it requires the attacker to have their own store with the app installed (trivial, self-service) and to be able to trigger at least one webhook delivery with a body they can predict or capture (many webhook bodies, e.g., `app/uninstalled`, are deterministic or attacker-influenced). No secret material is required, only observation of one's own legitimate webhook traffic.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document clearly that `shop` on `WebhookMetadata` is unauthenticated and must not be used for tenant routing without an independent check (e.g., cross-referencing against a known, previously-established session/shop record).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC over `B` using the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same body `B` and the same `H` to the app's webhook endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true` [5](#0-4) .
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the app to process/attribute the event under the victim's tenant even though it never originated from Shopify for that shop.
