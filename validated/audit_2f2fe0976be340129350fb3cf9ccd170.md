### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are trusted despite being outside the HMAC signature scope, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, but that validator only signs `Request#to_signable_string`, which is the raw request **body**. The `shop`, `topic`, `webhook_id`, and `api_version` values - all read from HTTP headers - are never part of the signed payload, yet they are used unchecked to select the handler and to populate `WebhookMetadata` passed to the host application.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers, unrelated to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e., only the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` then trusts `request.topic` to select the handler and forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` into `WebhookMetadata` handed to the app's handler, with no verification that these header values were ever covered by the signature: [4](#0-3) 

The binding this breaks: `hmac(body)` should equal an identity-bound tuple of `(shop, topic, body)`, but instead the library verifies only `hmac(body) == hmac_header`, while `shop` and `topic` are read independently and un-authenticated. Anyone who can obtain one legitimate `(body, hmac)` pair — trivially available to any unprivileged internet user by installing the target app on their own free development/trial shop and triggering a webhook event with attacker-controlled body content (e.g., a product or order they created) — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain and/or the `x-shopify-topic` header to route to a different handler. `HmacValidator.validate` still succeeds because the body (and therefore the HMAC) is untouched; only the uncovered header fields changed.

### Impact Explanation
This allows an unprivileged internet user to make the host application process attacker-chosen webhook body content under the identity of an arbitrary victim shop (`WebhookMetadata#shop`) or under an arbitrary topic (`WebhookMetadata#topic`), without possessing the app's `client_secret`/`api_secret_key`. If the host application uses `data.shop` to look up stored access tokens, update per-tenant records, or gate business logic (the intended purpose of this field), this is a cross-tenant access vector: attacker-supplied data is committed against another merchant's tenant context. This satisfies the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is Medium: the attacker needs at least one genuine `(body, hmac)` pair, which they can freely generate by installing the app on their own shop (installing an app requires no special privilege and is available to any internet user with a Shopify dev/partner account) and then triggering any webhook topic the app subscribes to with content they control. Webhook endpoints are, by design, public unauthenticated HTTP endpoints, so replaying with modified headers requires no additional access.

### Recommendation
Bind the identity fields into the signed payload verification, e.g., include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (matching what Shopify's HMAC actually authenticates for the specific delivery), or independently corroborate `shop`/`topic` against the registration/subscription that was expected for that HMAC, rather than trusting header values that fall entirely outside the HMAC's signed scope.

### Proof of Concept
1. Install the target app (built on this gem) onto an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook topic the app subscribes to (e.g., `orders/create`) with attacker-controlled body content.
3. Capture the genuine POST request Shopify sends to the app's webhook endpoint, including `x-shopify-hmac-sha256` and the raw body.
4. Replay the exact same body/HMAC to the same endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally `x-shopify-topic` with another subscribed topic).
5. `Registry.process` calls `HmacValidator.validate(request)` — this still passes because it only hashes the untouched body.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, despite the request never having been authenticated for that shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
