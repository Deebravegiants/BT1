### Title
Webhook `shop`/`topic` identity is trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — returns only the raw HTTP body. `Registry.process` accepts the request once the body's HMAC checks out and then dispatches to the app's handler using the header-derived, unauthenticated `shop` and `topic` values.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` only checks this body-HMAC, then immediately trusts `request.shop` and `request.topic` to route and construct the metadata handed to the app's handler: [4](#0-3) 

The intended binding, expressed as an equality, should be:
`shop_covered_by_hmac == shop_used_by_handler`

What is actually enforced is:
`hmac == HMAC(secret, raw_body)` — a statement about *bytes verified* (body only) — while `shop_used_by_handler == header["shopify-shop-domain"]` — a statement about *bytes parsed* (headers), which are never included in the signed material. The `shop` field is therefore "acted on but not covered by the HMAC," exactly the binding-break class this analysis targets.

Since `HMAC(secret, body)` is a deterministic function of `body` and the shared `api_secret_key` (no nonce, timestamp, or shop identifier is mixed into the signed string), a valid `(raw_body, hmac)` pair generated for one shop remains valid forever for that identical body regardless of which `shopify-shop-domain` header accompanies it.

### Impact Explanation
An unprivileged internet user who is themselves a merchant/tenant of the app (i.e., can install the app on their own store and trigger webhooks addressed to the app's public webhook endpoint) can:
1. Trigger any webhook topic on their own shop, capturing the resulting `raw_body` and its corresponding `shopify-hmac-sha256` value.
2. Replay that exact `(raw_body, hmac)` pair against the app's public webhook endpoint with the `shopify-shop-domain` (and `shopify-topic`, `shopify-webhook-id`) headers rewritten to name a victim shop.
3. `HmacValidator.validate` still succeeds (it only checks `raw_body`), so `Registry.process` treats the forged request as authentic and calls `handler.handle` with `shop: <victim shop>`, `topic: <attacker-chosen topic>`.

If the host app's handler uses `data.shop` to identify which tenant's records to update/query/delete (a normal and expected usage pattern for multi-tenant Shopify apps), this breaks tenant isolation: mandatory compliance topics such as `shop/redact` or `customers/data_request` could be spoofed against a shop the attacker does not own, or ordinary topics (`orders/create`, etc.) could pollute another tenant's data — a cross-tenant action/data-integrity break rooted entirely in this gem's webhook verification code, not in host-app misuse of an undocumented API.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free-trial) installer of the target app on their own store — no leaked secrets, no privileged Shopify Partner access, and no interception of TLS is needed. Any app that exposes a public webhook receiver (a requirement of Shopify's webhook delivery model) is affected.

### Recommendation
Bind the identity fields into the signed material, or verify them out-of-band against a trusted source (e.g., the session's stored shop) before dispatch:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string`, matching them against values already known to the app for that specific installation, or
- After body-HMAC validation succeeds, cross-check `request.shop` against the shop associated with the session/webhook subscription that the app itself registered, rejecting any mismatch, rather than trusting the header value unconditionally in `Registry.process`.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger a webhook (e.g. `customers/data_request`) so Shopify POSTs a valid `raw_body` with header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, raw_body)`.
2. Capture `raw_body` and `H`.
3. Send a new POST to the same app webhook endpoint with identical `raw_body` and `shopify-hmac-sha256: H`, but headers rewritten:
   - `shopify-shop-domain: victim.myshopify.com`
   - `shopify-topic: customers/data_request` (or `shop/redact`)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since it only checks `raw_body` against `H`.
5. `handler.handle(data: WebhookMetadata.new(topic: "customers/data_request", shop: "victim.myshopify.com", ...))` fires, causing the app to act as though Shopify requested data redaction/export for `victim.myshopify.com`, even though the attacker never controls that shop.
