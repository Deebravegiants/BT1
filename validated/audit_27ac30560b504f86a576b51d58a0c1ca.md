### Title
PoA bridge writes case-preserved mixed-case bech32 BTC address into withdrawal memo despite case-insensitive address validation - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts])

### Summary
`validateBtcBech32Address` in `validateAddress.ts` accepts mixed-case/uppercase bech32 BTC addresses (via `bech32.decode`, which is case-insensitive per BIP173), so `PoaBridge.validateWithdrawal` lets a mixed-case `bc1...` address like `BC1QSFQ3EAT543RZZWARGVNJEQJZGL4TATSE3MR3LU` pass. However, `createWithdrawIntentPrimitive`/`createWithdrawMemo` in `poa-bridge-utils.ts` writes the destination address into the `WITHDRAW_TO:` memo exactly as received, without lowercasing, unlike the Omni route's `deriveOmniWithdrawIntentParams` which explicitly lowercases `bc1` addresses (`omni-withdraw-params.ts:118-124`) specifically because "the contract accepts only lowercase bech32" (CHANGELOG `95eca42`).

### Finding Description
The broken equality is: **address accepted by validation** (`validateAddress(address, Chains.Bitcoin)` → case-insensitive, confirmed by `validateAddress.spec.ts:85-86` accepting `"BC1Q973XRRGJE6ETKKN9Q9AZZSGPXEDDATS8CKVP5S"`) should equal **address encoded into the executable payload** (the `WITHDRAW_TO:<address>` memo the PoA relayer parses). For the asset `nep141:btc.omft.near`, `contractIdToCaip2` (`poa-bridge-utils.ts:106-117`) resolves this to `Chains.Bitcoin`, so this asset is routed through `PoaBridge`, not `OmniBridge`.

Path: `PoaBridge.createWithdrawalIntents` (`poa-bridge.ts:142-162`) → `createWithdrawIntentPrimitive` (`poa-bridge-utils.ts:6-26`) → `createWithdrawMemo` (`poa-bridge-utils.ts:28-49`). `createWithdrawMemo` only strips a `bitcoincash:` prefix (case-insensitively checked but the *replacement* value is the original-case `receiverAddress` when no prefix is present); it never lowercases BTC bech32 addresses. So `memo = "WITHDRAW_TO:BC1QSFQ3EAT543RZZWARGVNJEQJZGL4TATSE3MR3LU"` verbatim.

Contrast with `deriveOmniWithdrawIntentParams` (`omni-withdraw-params.ts:118-124`), which explicitly lowercases any `bc1`-prefixed address before building the `recipient`/memo, with a code comment stating: *"Omni contract only accepts lowercase bech32 addresses; uppercase/mixed-case bech32 is spec-valid but rejected on-chain."* The CHANGELOG entry `95eca42: "To lower case bech32 btc addresses, as contract accepts only lowercase bech32"` documents this was a known, previously-fixed class of bug — but the fix landed only in the Omni path, not the PoA path.

Root cause: `PoaBridge.validateWithdrawal` (`poa-bridge.ts:181-188`) calls the same case-insensitive `validateAddress`, giving integrators/users false confidence that any bech32 casing is safe, while `createWithdrawIntentPrimitive` downstream does not normalize case before it becomes the literal memo string the off-chain PoA relayer parses to determine payout destination.

No existing guard catches this: `supports()`, `compareAddresses` (used only to compare against the token's own origin address, not to normalize casing), and `assert` sanity checks in `poa-bridge.ts` do not touch address casing.

### Impact Explanation
An ordinary user calling `sdk.createWithdrawalIntents` with `assetId: "nep141:btc.omft.near"` and a mixed-case `bc1` `destinationAddress` gets an intent whose signed memo contains the mixed-case string. If the PoA relayer's bech32 parser is strict/lowercase-only (as the CHANGELOG states for the contract-side acceptance), the relayer either rejects the withdrawal (funds get stuck in the PoA bridge contract pending manual/support intervention) or mis-parses it. This matches the High severity category: "a withdrawal stuck until manual intervention." It is repeatable per call and requires no privilege beyond being a normal user choosing to type/paste a mixed-case address (which is a valid, spec-compliant BTC address form).

### Likelihood Explanation
Preconditions: withdrawal must use the PoA route (default route for `*.omft.near` BTC assets) and the caller must supply a `bc1` address with any character in a non-lowercase form (e.g., copy-pasted from a QR/wallet display that renders bech32 uppercase, which is common and spec-valid per BIP173). No special privilege or cost is required — this is a normal, attacker-free usage pattern that any legitimate withdrawal request could accidentally trigger, and it is fully repeatable on every PoA BTC withdrawal call with a non-lowercase address.

### Recommendation
In `createWithdrawMemo` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts`), normalize BTC/bech32-form addresses to lowercase (mirroring the `bc1`-detection and `.toLowerCase()` logic already present in `omni-withdraw-params.ts:118-124`) before building the `WITHDRAW_TO` memo, for any PoA-bridged chain that uses bech32 addressing (BTC, and potentially Litecoin `ltc1` given `validateLitecoinAddress` also accepts case-insensitively per its bech32 decode).

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}
