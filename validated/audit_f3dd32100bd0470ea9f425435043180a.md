## Finding

### Title
Relayer's accumulated fee balance is zeroed before the cross-chain withdrawal is confirmed, risking permanent loss if the destination `EvmHost` lacks sufficient fee-token balance - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
The Sherlock report describes `OngoingBountyV1` promising a fixed payout to a claimant who has already performed the work, without guaranteeing the contract actually holds enough funds at claim time — the claim reverts and the claimant's completed work goes uncompensated. The same "accounting says paid, but destination balance is not guaranteed" pattern exists in Hyperbridge's relayer fee withdrawal path.

### Finding Description
A relayer earns fees by delivering cross-chain messages and proving delivery via `accumulate_fees`, which credits `Fees::<T>::insert`/`try_mutate` on Hyperbridge [1](#0-0) . To realize this balance, the relayer calls `Pallet::withdraw`, which dispatches a fire-and-forget ISMP POST request to the destination chain's `HostManager`/`EvmHost.withdraw()`, and — critically — zeroes the `Fees` entry on Hyperbridge immediately after the dispatch call succeeds, without waiting for confirmation that the destination payout actually happened: [2](#0-1) 

On the destination side, `EvmHost.withdraw()` performs a plain `IERC20.safeTransfer`/native transfer out of the host contract's own balance, with no reservation or escrow mechanism ensuring the funds are actually available for this specific relayer claim: [3](#0-2) 

If the `EvmHost` contract's fee-token balance is insufficient when the withdrawal message is delivered, `IHostManager.withdraw` (and therefore `HostManager.onAccept`) reverts, confirmed by the existing test `test_host_manager_insufficient_balance` [4](#0-3) . `EvmHost.dispatchIncoming` catches this failure by deleting the request receipt so it "can be retried" [5](#0-4) , but the withdrawal request is dispatched with zero relayer fee (`FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` [6](#0-5) ), so there is no independent economic incentive for anyone to keep re-delivering a failing withdrawal. Meanwhile the relayer's `Fees` accounting entry on Hyperbridge has already been zeroed — the relayer has no further on-chain claim to reissue if the destination host's balance never recovers.

### Impact Explanation
Analogous to the OngoingBounty scenario: the relayer has already performed the incentivized work (submitting valid delivery/consensus proofs, verified and credited on Hyperbridge), but payout correctness at the destination depends on an unenforced invariant — that the destination `EvmHost`'s fee-token balance covers every relayer's accumulated claim. If that invariant is violated (e.g., balance is drawn down by other withdrawals, governance sweeps, or slow fee accrual relative to claims), the relayer's already-credited-and-zeroed reward can become permanently unrecoverable, since the crediting bookkeeping (`Fees` zeroing) happens optimistically before final settlement is confirmed.

### Likelihood Explanation
This requires the destination `EvmHost`'s fee-token balance to be lower than an individual withdrawal amount at the time of delivery, which can occur under normal operation (e.g., many relayers converging on withdrawals, uneven fee accrual across chains, or governance withdrawals of "bridge revenue" via the same `withdraw()` function competing for the same balance pool) without any malicious actor being required.

### Recommendation
Do not zero the relayer's `Fees` entry until destination-side settlement is confirmed (e.g., via a settlement acknowledgment/timeout callback), or reserve/escrow the fee-token amount at accrual time so that a relayer's earned balance is backed by segregated funds rather than the host contract's general balance, mirroring the "check funds are available before finalizing the payout accounting" recommendation from the referenced report.

### Proof of Concept
1. Multiple relayers accumulate fees for chain `X` via `accumulate_fees`, crediting `Fees::<T>` beyond what `EvmHost` on chain `X` currently holds in its fee token.
2. Relayer A calls `withdraw`; `Fees` is zeroed and a POST is dispatched to `X`'s `HostManager`.
3. When delivered, `EvmHost.withdraw()` reverts because the contract balance is insufficient (as in `test_host_manager_insufficient_balance`) [4](#0-3) .
4. `dispatchIncoming` deletes the receipt for a retry, but with zero attached fee there's no incentive to retry, and relayer A's `Fees` entry on Hyperbridge is already zero — their earned reward is effectively stuck/lost until someone alters the balance situation.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

#[test]
fn test_host_manager_insufficient_balance() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
	assert!(!err.is_empty(), "expected non-empty revert data");
}
