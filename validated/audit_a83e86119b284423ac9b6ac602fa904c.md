Audit Report

## Title
Same-call-stack `charge_deposit` + `terminate()` ordering in `try_into_deposit`'s refund-before-charge processing can strand storage-deposit funds - (File: substrate/frame/contracts/src/storage/meter.rs)

## Summary
`RawMeter::terminate` computes the termination refund as `Deposit::Refund(info.total_deposit())` [1](#0-0) , where `info.total_deposit()` already reflects in-memory increases to `ContractInfo` from a preceding `charge_deposit` call (e.g. from `set_code_hash`) that has not yet been transferred/held on the contract's account [2](#0-1) . Because `try_into_deposit` executes all queued `Refund`s before any queued `Charge`s [3](#0-2) , the refund under-transfers via `Precision::BestEffort`, and the later `Charge` deposits and holds fresh balance on the already-terminated, swept contract account, which can never be released.

## Finding Description
`RawMeter::charge_deposit` pushes a `Charge` entry with `state: ContractState::Alive` directly into the nested meter's `charges` vec, separate from `own_contribution` [4](#0-3) . `set_code_hash` calls `info.update_base_deposit(...)` (mutating `ContractInfo` in-memory) and then `frame.nested_storage.charge_deposit(...)` with the incremental amount, in the same call frame's meter [2](#0-1) .

If the same contract execution subsequently calls `terminate`, `Ext::terminate` in `exec.rs` extracts `info` (which already reflects the increased `storage_base_deposit`) and calls `frame.nested_storage.terminate(&info, beneficiary)` [5](#0-4) , which sets `own_contribution = Contribution::Terminated { deposit: Deposit::Refund(info.total_deposit()), beneficiary }` — an amount that includes the not-yet-held increment [1](#0-0) .

Both entries — the `Charge(X)` from `charge_deposit` and the `Refund(total_including_X)` from `terminate` — end up in the same `charges` vector, either directly (same nested meter) or via `absorb` up the call stack [6](#0-5) . `try_into_deposit` processes all `Refund`s first, then all `Charge`s [3](#0-2) .

In `ReservingExt::charge`, the `Refund` branch calls `transfer_on_hold` with `Precision::BestEffort`; if the contract's actual hold is smaller than `amount` (since `X` was never placed on hold), the transfer silently returns a partial amount, logging only an error [7](#0-6) . Immediately after, because `state` is `Terminated`, the contract's consumer ref is decremented and its remaining reducible balance is swept to the beneficiary [8](#0-7) . Only afterward does the second pass execute the `Charge(X)` entry via `transfer_and_hold`, moving fresh balance from `origin` into the now-dead, already-swept contract account and placing a new hold there under `HoldReason::StorageDepositReserve` [9](#0-8) . Since the contract's `ContractInfoOf` entry was already removed and no future execution can occur against this dead account [10](#0-9) , this hold has no code path to ever be released.

The design comment's assumption that refund-before-charge ordering makes "the order of storage changes irrelevant with regard to the deposit system" [11](#0-10)  holds only for netting against the origin's balance sufficiency, not for the per-account hold accounting used by `transfer_on_hold`/`transfer_and_hold`.

## Impact Explanation
Storage-deposit balance becomes permanently stuck under `HoldReason::StorageDepositReserve` on a terminated contract's account with no remaining code path to release it — a concrete stuck/lost-funds condition rather than theft. The amount at risk is bounded by the size of the same-frame deposit increment preceding self-termination (e.g., from `set_code_hash`'s base-deposit delta).

## Likelihood Explanation
The sequence requires an unprivileged contract to call `seal_set_code_hash` (or an equivalent deposit-increasing host function using `charge_deposit`) followed by `seal_terminate` within the same call execution — both are ordinary, unprivileged host functions reachable from any contract's `call` export, with no observed guard preventing this ordering in `exec.rs`. This is fully attacker-controlled and repeatable by any contract deployer, requiring no privileged access, governance, or victim mistake.

## Recommendation
Compute the termination refund only against the amount actually charged/held (not the in-memory `ContractInfo` total which may include unheld pending increments), or process `Charge`/`Refund` entries per-contract in causal order (net before executing transfers) rather than as two global passes across all `charges`. Alternatively, disallow further deposit-increasing operations after a contract's termination is queued in the same frame, or coalesce a contract's `Charge` and `Refund` entries before executing any transfer.

## Proof of Concept
Extend `substrate/frame/contracts/src/storage/meter.rs`'s test module (near `termination_works`): within one nested meter, call `charge_deposit(contract, Deposit::Charge(X))` to simulate a `set_code_hash` base-deposit increase applied to `info` first, then call `terminate(&info, beneficiary)` where `info.total_deposit()` already includes `X`. Absorb into root and call `try_into_deposit`; assert the mock `Ext::charge` invocation order is `Refund(total_including_X)` before `Charge(X)`. For an integration-level PoC using `ReservingExt`, deploy a contract, have it call `set_code_hash` then `terminate` in one call, and assert: (1) the `transferred < amount` branch is hit in `ReservingExt::charge`'s refund path, and (2) after execution, `origin`'s free balance plus the residual hold on the contract's now-dead account is less than `origin`'s pre-call balance, demonstrating stuck value.

	fn terminate(&mut self, beneficiary: &AccountIdOf<Self::T>) -> DispatchResult {
		if self.is_recursive() {
			return Err(Error::<T>::TerminatedWhileReentrant.into());
		}
		let frame = self.top_frame_mut();
		let info = frame.terminate();
		frame.nested_storage.terminate(&info, beneficiary.clone());

		info.queue_trie_for_deletion();
		ContractInfoOf::<T>::remove(&frame.account_id);
		Self::decrement_refcount(info.code_hash);

		for (code_hash, deposit) in info.delegate_dependencies() {
			Self::decrement_refcount(*code_hash);
			frame
				.nested_storage
				.charge_deposit(frame.account_id.clone(), StorageDeposit::Refund(*deposit));
		}

		Contracts::<T>::deposit_event(Event::Terminated {
			contract: frame.account_id.clone(),
			beneficiary: beneficiary.clone(),
		});
		Ok(())
	}

	fn set_code_hash(&mut self, hash: CodeHash<Self::T>) -> DispatchResult {
		let frame = top_frame_mut!(self);
		if !E::from_storage(hash, &mut frame.nested_gas)?.is_deterministic() {
			return Err(<Error<T>>::Indeterministic.into());
		}

		let info = frame.contract_info();

		let prev_hash = info.code_hash;
		info.code_hash = hash;

		let code_info = CodeInfoOf::<T>::get(hash).ok_or(Error::<T>::CodeNotFound)?;

		let old_base_deposit = info.storage_base_deposit();
		let new_base_deposit = info.update_base_deposit(&code_info);
		let deposit = StorageDeposit::Charge(new_base_deposit)
			.saturating_sub(&StorageDeposit::Charge(old_base_deposit));

		frame.nested_storage.charge_deposit(frame.account_id.clone(), deposit);

		Self::increment_refcount(hash)?;
		Self::decrement_refcount(prev_hash);
		Contracts::<Self::T>::deposit_event(Event::ContractCodeUpdated {
			contract: frame.account_id.clone(),
			new_code_hash: hash,
			old_code_hash: prev_hash,
		});
		Ok(())
	}
