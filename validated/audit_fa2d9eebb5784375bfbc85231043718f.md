### Title
Public `accrue()` lets any caller shrink each debt-delta increment, rounding the DAO treasury's reserve fee to zero on every call - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every vault contract exposes an unauthenticated, public `accrue()` function that recomputes the borrow/liquidity indexes and mints the protocol's `fee-reserve` cut of newly accrued interest to `.dao-treasury`. The reserve cut is computed as `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)`, which truncates to `0` whenever `debt-delta * fee-reserve < BPS`. Because `accrue()` has no access control and resets `last-update` to the current block on every successful call, any address can call it every block (or repeatedly within short intervals) to keep `debt-delta` tiny, permanently forcing `reserve-inc` to `0` and starving the DAO treasury of its fee share while depositors still receive the full underlying interest.

### Finding Description
`accrue()` is `define-public` with no `check-caller-auth` or similar guard: [1](#0-0) 

Inside it, the fee (reserve) skimmed from interest for the DAO treasury is computed via floor-division: [2](#0-1) 

`debt-delta` is the change in `total-debt` (itself derived from `principal-scaled` and the borrow `index`) since the *last* accrual. Because `last-update` is refreshed to the current block time on every successful `accrue()` call: [3](#0-2) 

...an attacker can call `accrue()` as often as possible (every block, or back-to-back within the same short interval across many transactions) so that `time-delta` — and thus `debt-delta` — stays very small on each call. With `fee-reserve` set at typical values such as 1000 bps (10%) per the sBTC configuration proposal: [4](#0-3) 

`reserve-inc = mul-div-down(debt-delta, 1000, 10000)` truncates to `0` whenever `debt-delta < 10` (in the underlying's smallest units). By fragmenting the natural interest accrual into many tiny `accrue()` calls instead of allowing it to accumulate into a single larger delta, the truncation-to-zero happens on essentially every call, so `treasury-lp` (the vault shares minted to `.dao-treasury` representing the fee) never gets minted: [5](#0-4) [6](#0-5) 

Meanwhile the vault's `index`/`lindex` are still advanced each call (interest is not lost from the borrower's debt or the supplier's share value — `calc-cumulative-debt` uses `mul-div-up` and `total-assets` picks up the full interest delta), so the *entire* interest amount still flows to `total-assets` / suppliers via `zft` share appreciation, while the treasury's cut, which should equal `fee-reserve × total-interest / BPS`, is diverted to zero. This breaks the identity:

`Fees Owed to Treasury (Σ fee-reserve% × Δdebt_i over a real period) == Fees Actually Minted to .dao-treasury (Σ mul-div-down(Δdebt_i, fee-reserve, BPS))`

by making the attacker choose the granularity of `Δdebt_i` (via call frequency) so the right-hand side sums to `0` while the left-hand side (and the value that ends up backing `zft` for depositors) is unaffected.

This same pattern (`accrue`, `calc-treasury-lp-preview`, `mul-div-down` fee-reserve calc) is repeated identically across all vaults: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
This is a permanent loss of the DAO treasury's unclaimed yield/fee income across every vault in the protocol. The fee-reserve mechanism exists specifically to fund protocol reserves via minted `zft` shares to `.dao-treasury` on each accrual, per design documentation: [12](#0-11) 

By calling `accrue()` frequently and gratuitously, any unprivileged address can suppress this minting essentially indefinitely, redirecting what should be the treasury's yield share to depositors instead, at no cost to the attacker beyond transaction fees. This qualifies as theft/permanent loss of unclaimed yield belonging to the protocol.

### Likelihood Explanation
`accrue()` is public, requires no special permission, no minimum call interval, and is inexpensive to call. It can be invoked directly by any address as its own function or triggered incidentally through other public vault/market operations that call `accrue` internally (e.g. `system-borrow` calls `accrue` at its start). Any actor motivated to grief the treasury's fee income (or simply an automated MEV/keeper-style bot maximizing LP yield) could call this repeatedly at low cost, making this readily exploitable.

### Recommendation
- Accumulate un-minted "dust" from `reserve-inc` truncation in a persistent variable and mint it once it exceeds a minimum unit, instead of discarding it on each call.
- Alternatively, round `reserve-inc` up (`mul-div-up`) in the protocol's favor, consistent with the rounding-direction principle recommended in the source report, and/or impose a minimum time-delta before `accrue()` is allowed to actually update state (rather than being callable with negligible `time-delta` repeatedly).
- Consider restricting `accrue()`'s state-mutating path to be triggered only alongside real user actions (deposit/borrow/repay/redeem) with a meaningfully bounded minimum interval, so an attacker cannot artificially fragment interest accrual into many truncation-favorable calls.

### Proof of Concept
1. Vault `vault-stx` has `fee-reserve = 1000` (10%) and a nonzero `principal-scaled` (i.e., outstanding borrows), so interest is naturally accruing.
2. Attacker (any address, no special permission) calls `accrue()` in vault-stx every block.
3. Each call: `time-delta` is minimal (one block), so `debt-delta` (the interest accrued since the last call) is a very small number of micro-units.
4. `reserve-inc = mul-div-down(debt-delta, 1000, 10000)`. As long as `debt-delta < 10`, `reserve-inc = 0`, so no `zft` is minted to `.dao-treasury` — see: [13](#0-12) 
5. `index`/`lindex` still update each call (so the full interest is reflected in `total-assets`/`total-debt`), meaning suppliers' redemption value grows by the full interest amount while the treasury's `fee-reserve` share is permanently forfeited call after call.
6. Repeating this every block over the vault's lifetime results in the treasury receiving near-zero of its intended reserve-factor fee income, while under normal (infrequent) accrual the same total interest would produce nonzero `reserve-inc` and treasury minting.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))

### Protocol Reserves & DAO Treasury

A portion of interest earned goes to protocol reserves, which are minted directly as vault shares to the DAO treasury contract. This follows the AAVE model where treasury minting occurs on each vault state update.

**Reserve Factor:** Percentage of interest allocated to protocol (e.g., 10%)

**Treasury Minting Process:**
```clarity
;; In vault contracts (e.g., vault-stx.clar)
;; On each accrue operation:
;; 1. Calculate total interest earned
;; 2. Reserve factor determines protocol share (e.g., 10%)
;; 3. Mint vault shares directly to dao-treasury
;; 4. Remaining interest goes to suppliers
```

**Reference:** Similar to [AAVE's ReserveLogic](https://github.com/aave-dao/aave-v3-origin/blob/8a43339b6f93ea0a2f4d8e1ef3b9494c9d206a64/src/contracts/protocol/libraries/logic/ReserveLogic.sol#L85-L101) where treasury minting happens on status updates.

**Example:** 
- 10 USDC interest earned
- 10% reserve factor
- 1 USDC equivalent in zUSDC shares → dao-treasury
- 9 USDC equivalent in value → suppliers
```
