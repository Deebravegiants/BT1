## Analog Found: Unchecked `uint256`→`int256` casts in `VWAPOracle.recordSpread` mirror the reported overflow/casting bug class

### Title
Unsafe `uint256`-to-`int256` casts in `VWAPOracle.recordSpread` can silently corrupt or unpredictably revert same-token spread accounting - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
The external report's root cause is a Solidity type-cast into `int256` performed on a value that has not been range-checked, so a value larger than `type(int256).max` reinterprets its top bit as the sign bit instead of reverting, corrupting downstream logic that assumes the cast is faithful. The same anti-pattern exists in `VWAPOracle.recordSpread`, which is the `IIntentPriceOracle` implementation invoked by the `IntentGateway` during same-token cross-chain intent fills.

### Finding Description
`recordSpread` normalizes solver-supplied `inputs`/`outputs` amounts to 18 decimals and then casts the resulting `uint256` values straight into `int256` with no bounds check: [1](#0-0) 

- `_normalizeAmount` multiplies raw token amounts by `10 ** (18 - decimals)` for any token with fewer than 18 decimals: [2](#0-1) 
- The normalized `uint256` is then cast with `int256(outputAmountNormalized)` / `int256(inputAmountNormalized)` and used in signed arithmetic (`amountDiff`, `spreadBps`, `weightedSpread`): [3](#0-2) 

Solidity 0.8's overflow checks apply to `+ - * /` operators but **not** to explicit type conversions — `int256(x)` for `x > type(int256).max` (~5.79e76) does not revert; it reinterprets the bit pattern as a negative number. This is the exact class of bug in the report: a value that "can still silently overflow" during a cast, corrupting the signed value used afterward, or — because the *subsequent* signed multiplications and additions **are** checked — causing the whole call to unconditionally revert once the corrupted/oversized operand is used in `amountDiff * int256(BPS_DENOMINATOR)` or `spreadBps * int256(inputAmountNormalized)`.

Any token with fewer than 18 decimals (e.g. 0- or 6-decimal tokens, which are common and do not require an attacker-deployed contract) can reach normalized amounts near or above `type(int256).max` for sufficiently large — but otherwise legitimate — transferred amounts, since `_normalizeAmount` performs an unchecked `uint256` multiplication that only reverts if it exceeds `type(uint256).max`, far above `type(int256).max`.

### Impact Explanation
`recordSpread` is called from the `IntentGateway`'s same-token fill path (restricted via `restrict(_intentGateway)`), so it executes inside the solver's fill transaction: [4](#0-3) 
If the casts silently wrap, the oracle's cumulative state (`weightedSpreadSum`, which is checked-added in `_updateCumulativeSpread`) is permanently poisoned with a corrupted sign/magnitude, since `totalVolume`/`weightedSpreadSum` never get corrected and there is no way to unwind a bad update: [5](#0-4) 
Alternatively, if the corrupted value feeds a checked signed multiplication that itself overflows `int256`, the entire `recordSpread` call reverts, which — since it executes inside the solver's fill transaction — causes every future fill of that (chain, token) pair to revert deterministically, permanently blocking legitimate same-token intent fills for that pair (denial of service on the fill path, analogous to the reported "getPrice ... will revert all the time").

### Likelihood Explanation
Reaching the vulnerable path requires no privileged access: any solver filling a same-token cross-chain intent for a token with fewer than 18 decimals and a large-enough (but realistic, e.g. billions of units of a 0- or 2-decimal token) amount triggers the unchecked cast. No malicious token deployment is strictly required, only a token/amount combination that is otherwise valid input to the intent-fill flow.

### Recommendation
Bound-check normalized amounts before casting to `int256` (e.g. `require(outputAmountNormalized <= uint256(type(int256).max))`), or use a safe-cast library (OpenZeppelin's `SafeCast.toInt256`) throughout `recordSpread`, so an out-of-range amount reverts explicitly and predictably instead of silently corrupting signed accounting or non-deterministically reverting the fill.

### Proof of Concept
1. Configure/accept a token with `decimals = 0` (or any value `< 18`) as a source-chain asset via `_processTokenDecimalsUpdates`.
2. Fill a same-token cross-chain order whose `inputs[i].amount` (raw, pre-normalization) is `> type(int256).max / 10**18` (~5.79e58) — well within `uint256` range and plausible for a 0-decimal token with large integer supply.
3. `_normalizeAmount` computes `amount * 10**18`, which now exceeds `type(int256).max` but is still `< type(uint256).max`, so it does not revert.
4. `int256(outputAmountNormalized)` (or `inputAmountNormalized`) silently reinterprets the value as negative.
5. Either: (a) `weightedSpreadSum` is now corrupted with an incorrect sign/magnitude that persists forever in storage, poisoning all future `spread()` reads for that token, or (b) the subsequent checked multiplication (`amountDiff * int256(BPS_DENOMINATOR)` or `spreadBps * int256(inputAmountNormalized)`) itself overflows `int256` and reverts, causing the solver's `fillOrder` transaction — and every subsequent fill of that pair — to revert.

**Uncertainty note:** I could not fully verify within the available tool budget (a) the exact call site inside `IntentGateway`/`IntentsBase.sol` that invokes `recordSpread` during a fill (grep showed matches in `IntentsBase.sol` but I did not read the surrounding context), nor (b) whether `spread()`'s corrupted output is consumed anywhere else on-chain to gate fund-moving decisions beyond the DoS-on-fill scenario described above. The DoS/state-corruption impact on the fill path itself is directly supported by the cited code.

```text
    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
```
