### Title
Webhook `shop` (and `topic`) header fields are trusted for tenant routing but are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but `to_signable_string` — the value the HMAC is computed and verified over — is only the raw request body [1](#0-0) . `Registry.process` accepts the request once `Utils::HmacValidator.validate(request)` succeeds, then blindly forwards `request.shop` and `request.topic` (unauthenticated header values) to the app's handler as trusted tenant identity [2](#0-1) .

### Finding Description
The identity binding broken here is: **shop authenticated by the HMAC ≠ shop delivered to the handler**. `HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` only [3](#0-2) , and compares it against the HMAC header using `OpenSSL.secure_compare` [4](#0-3) . The `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers are never part of the signed material [5](#0-4) .

Crucially, the `api_secret_key` used to compute this HMAC is a single per-app secret shared across every shop that installs the app — it is not shop-specific. Any merchant who installs the app (an unprivileged internet user relative to other tenants of the same app) legitimately receives real webhook deliveries containing a valid `(body, hmac)` pair signed with that shared secret. Because `shop`/`topic` are outside the signed scope, that same valid `(raw_body, hmac)` pair can be resent to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header, and `Registry.process` will still accept it as authentic — attributing the payload to a victim shop chosen by the attacker [6](#0-5) .

The `WebhookMetadata` passed to the handler exposes exactly these unauthenticated fields as if verified, per the gem's own documentation instructing handler authors to trust `data.shop` and `data.topic` [7](#0-6) .

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker with a legitimate (but unprivileged, merchant-level) install of the app can forge webhook events that the app attributes to a different, victim shop. Since apps commonly use `data.shop`/`data.topic` to select which tenant's records to create, update, or delete (e.g., `app/uninstalled`, `shop/update`, `orders/create` handlers keyed by shop), this can be leveraged for cross-tenant data corruption or unauthorized actions performed under another merchant's identity — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability only requires the attacker to install the target app on their own shop (a normal, unprivileged action) and capture one legitimate webhook delivery for a topic/body they can predict or control (many topics have static or near-static bodies, e.g. `app/uninstalled` is frequently `{}`), then replay the same body+HMAC with a forged `shop`/`topic` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged credentials are needed beyond the attacker's own valid installation.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic` to the verified body:
- Have `Webhooks::Request#to_signable_string` include `shop`, `topic`, and `webhook_id` alongside the body (this requires a corresponding change to how Shopify signs webhooks, so at minimum the gem should not present `request.shop`/`request.topic` as verified facts), or
- Require host applications to cross-check `request.shop` against a known/installed shop list (session store) before acting on the payload, and clearly document that `shop`/`topic` are unauthenticated header values not covered by the HMAC, and
- Consider deduplicating/binding via `webhook_id` plus a server-side registration table `(shop, topic, webhook_id)` recorded at registration time via `Registry.register`, rejecting any inbound webhook whose `(shop, topic)` pair was not registered by that specific shop's session.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's single `api_secret_key`.
2. Attacker captures one delivery for a topic with body `"{}"` (many mandatory topics, e.g. `app/uninstalled`), noting `x-shopify-hmac-sha256` is valid for body `"{}"`.
3. Attacker sends a POST to the app's webhook endpoint with the exact same body `"{}"` and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the headers [8](#0-7) ; `Utils::HmacValidator.validate` returns `true` because it only checks the body [9](#0-8) ; `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [10](#0-9) , exactly as demonstrated by the gem's own test fixture pattern of computing HMAC over `"{}"` independent of the shop header [11](#0-10) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
