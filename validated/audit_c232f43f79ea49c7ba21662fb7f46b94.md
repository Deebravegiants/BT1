### Title
Non-embedded `current_session_id` trusts the raw, unsigned `shopify_app_session` cookie value as an authenticated session lookup key, enabling cross-tenant session/access-token theft - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `SessionUtils.current_session_id` returns `cookies["shopify_app_session"]` verbatim as the session id used to fetch a `Session` (and its `access_token`) from the app's session storage, without ever invoking `Auth::HmacValidator` or any other cryptographic check that the value actually originated from this gem's OAuth callback. Because offline session ids are deterministically constructed as `"offline_#{shop}"` [1](#0-0) , and online ones as `"#{shop}_#{user_id}"` [2](#0-1) , an attacker who knows (or guesses) a target shop's `.myshopify.com` domain can forge that cookie value and have it accepted verbatim.

### Finding Description
The claimed binding is: `session_id_returned_by(current_session_id) == session_id_that_HmacValidator/OAuth_actually_issued_to_this_requester`. Tracing the non-embedded branch:

```
current_session_id(shopify_id_token, cookies, online)
  else
    raise ... unless cookies && cookies[SESSION_COOKIE_NAME]
    cookie_session_id(cookies)   # => cookies[SESSION_COOKIE_NAME], returned unmodified
``` [3](#0-2) [4](#0-3) 

No `Auth::HmacValidator.validate` call, no signature check, no comparison against any server-side nonce/MAC exists on this path — the entire trust decision is `cookies[SESSION_COOKIE_NAME].present?`. The only place `Auth::HmacValidator` is invoked in this gem is in `Oauth.validate_auth_callback`, which runs once during the OAuth callback exchange, not on every subsequent request that resolves the current session [5](#0-4) .

The cookie value that legitimately gets set into `shopify_app_session` is simply `session.id` in plaintext, with no MAC/signature attached by this gem:
```
cookie = ... SessionCookie.new(value: session.id, expires: ...)
``` [6](#0-5) 

`SessionCookie` itself carries only `name`, `value`, `expires` — no MAC field [7](#0-6) . Since `session.id` for offline sessions is exactly `"offline_#{shop}"` and shop domains are public/enumerable, the cookie's entire value space is guessable without ever completing OAuth or possessing `api_secret_key`.

Attacker request: send any HTTP request to a non-embedded app endpoint with header `Cookie: shopify_app_session=offline_target-shop.myshopify.com` and no id token, no HMAC query params, nothing else. `current_session_id` returns `"offline_target-shop.myshopify.com"` unconditionally as long as the target merchant has an existing stored session under that id (i.e., previously installed the app) [3](#0-2) . The host app then loads that `Session` from its session storage and uses its `access_token` for subsequent `Clients::HttpClient` calls performed on the attacker's behalf, exposing another merchant's access token/cross-tenant data.

None of the existing guards intervene: `HmacValidator.validate` is not on this call path at all; `ShopValidator.sanitize!` is not invoked here; there is no `state` comparison (that only happens once, during the original `validate_auth_callback`); `JwtPayload`'s checks are irrelevant to the non-embedded cookie branch since no JWT is presented; `Context.embedded?` merely selects this vulnerable branch, it doesn't add protection.

### Impact Explanation
Any unprivileged attacker who knows or guesses a victim shop's myshopify domain (and offline sessions were previously created, which is the default persistent post-install state) can obtain that merchant's `access_token` and issue authenticated Admin API calls as that merchant via `Clients::HttpClient`. This is cross-tenant access and access-token theft, matching the Critical severity category. It is fully repeatable against any victim shop whose domain is known/guessable and who has installed the app, with no rate limiting on cookie guesses in-scope of this analysis.

### Likelihood Explanation
Preconditions: the app must be configured as non-embedded (`Context.embedded? == false`), and the target merchant must have completed OAuth previously so that a `Session` exists in storage under the deterministic id `offline_#{shop}`. Attacker cost is a single HTTP request with a forged `Cookie` header — no secrets, no valid OAuth flow, no signed request. Shop domains are typically discoverable (public storefront, `X-Shopify-*` headers, app listing, etc.), making the offline session id trivial to construct. This is a very low-cost, high-repeatability attack against any deployment that follows the documented flow of feeding raw `Cookie` header values into `current_session_id` for non-embedded apps.

### Recommendation
Do not use the raw session id as the entire trust anchor for a bearer cookie. Either (a) require the host application to store this cookie via a cryptographically signed/encrypted cookie jar (e.g., Rails `cookies.signed`/`cookies.encrypted`) and document/enforce that `cookies` passed into `SessionUtils.current_session_id` must have already been verified, or (b) have this gem itself embed and verify a MAC (HMAC with `Context.api_secret_key`) over the cookie value inside `SessionCookie`/`current_session_id`, rejecting any cookie whose value doesn't carry a valid signature, independent of the underlying session id's predictability.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_non_embedded_cookie_is_trusted_without_hmac_validation
  ShopifyAPI::Context.stubs(:embedded?).returns(false)
  Utils::HmacValidator.expects(:validate).never

  forged_cookie = { "shopify_app_session" => "offline_target-shop.myshopify.com" }
  session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookie, false)

  assert_equal("offline_target-shop.myshopify.com", session_id)

  # Simulate host app's session store lookup using the returned id verbatim
  victim_session = ShopifyAPI::Auth::Session.new(
    id: session_id,
    shop: "target-shop.myshopify.com",
    access_token: "victim-secret-token",
  )
  fake_store = { session_id => victim_session }

  assert_equal("victim-secret-token", fake_store[session_id].access_token)
end
```
This demonstrates that `current_session_id` returns the attacker-forged cookie value unmodified, `Auth::HmacValidator.validate` is never called on this path, and the returned id is sufficient to retrieve another merchant's `access_token` from a session store keyed by that id.
