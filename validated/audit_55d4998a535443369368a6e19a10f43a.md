Based on my analysis of the in-scope library code (excluding machine-generated REST resources, tests, and docs), I found a genuine identity-binding gap in the webhook processing path that matches the "field acted on but not covered by the HMAC" bug class from the rules.

### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and validates only the raw JSON body via HMAC, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed downstream to the handler unverified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` is derived purely from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Registry.process` validates only this body-bound HMAC, then reads `request.topic` and `request.shop` — both sourced from headers that are excluded from the signed content — and forwards them unverified to the app's handler: [3](#0-2) 

The binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` implies `signed_bytes == (topic, shop, body)`. In this implementation the equality only holds for `signed_bytes == body`; `topic` and `shop` are parsed from the request but never part of `signed_bytes`, so they are not bound to the signature at all.

### Impact Explanation
Any user who can obtain one genuinely-signed webhook delivery from Shopify for the app (e.g., by installing a public app on their own store, which requires no special privilege) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers with a victim shop/topic of their choosing. The HMAC check still passes because it only ever validated the body. `Registry.process` then dispatches to the registered handler with `WebhookMetadata.shop` and `topic` set to the attacker-chosen values, so the host app performs the corresponding logic (e.g., session/token revocation on `app/uninstalled`, data handling on `shop/redact`/`customers/redact`) as if it originated from the victim shop. This is a cross-tenant action, matching the Critical impact bar in the rules ("cross-tenant access").

### Likelihood Explanation
Exploitation requires only: (1) obtaining at least one genuine webhook (any topic) from the target app for a shop the attacker controls (a normal, unprivileged action for public apps), and (2) sending a forged HTTP POST with modified `shop-domain`/`topic` headers reusing that body+hmac pair. No access token, `client_secret`, or leaked credential is required, and no TLS interception is needed since the attacker is the direct sender of the forged request.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them to the body), so `HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually sent.

### Proof of Concept
1. Install the vulnerable app on an attacker-owned development store; trigger any webhook topic to receive a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's real secret.
2. Replay an HTTP POST to the app's webhook endpoint using the captured `raw_body` and `hmac` header unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled` (or another sensitive topic).
3. `ShopifyAPI::Webhooks::Registry.process` at [4](#0-3)  validates the HMAC successfully (it only checks the body) and invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on behalf of a shop the attacker does not control.
