### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) values from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies covers only the raw request body. This breaks the identity binding `shop authenticated == shop acted upon`, allowing a party who can obtain any single genuine `(raw_body, hmac)` pair issued for the app (signed with the app's shared `client_secret`) to relabel it as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` field, never incorporating the shop header: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` gates handler dispatch solely on this body-only HMAC check, then forwards the unauthenticated `request.shop` value into `WebhookMetadata` given to the host app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain, unguarded `String` field that host applications are expected to trust as the tenant identifier for the event: [5](#0-4) 

Because Shopify apps use one shared `client_secret` (hence one HMAC key via `Context.api_secret_key`) across every shop that has installed the app, a valid `(raw_body, hmac)` pair obtained from any single installed shop remains cryptographically valid for that body forever, regardless of which shop's domain header accompanies it. The gem's own verification logic therefore cannot distinguish "this body was really sent for shop X" from "this body was sent for shop X but relabeled as shop Y."

### Impact Explanation
This is a cross-tenant confusion vulnerability rooted in this gem's webhook verification implementation: `ShopifyAPI::Webhooks::Registry.process` and `Utils::HmacValidator` together authenticate the body but not the shop identity that the host application's `WebhookHandler#handle` implementation relies on via `WebhookMetadata#shop`. Any host app that (as documented/intended) uses `data.shop` to select which tenant record/session to update will process the replayed event under the attacker-chosen shop, producing cross-tenant data corruption or privilege confusion — squarely within the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Exploitation requires the attacker to have legitimately triggered at least one real webhook delivery for a shop that has the same app installed (e.g., an app that anyone can install on their own store, or any shop where the attacker has an ordinary account able to trigger a webhook topic such as `orders/create`, `app/uninstalled`, etc.). No `api_secret_key`, access token, or privileged account is needed — just capture of one's own genuine webhook delivery, which is straightforward since the attacker controls the shop generating it. The replay only requires resending that exact body with a forged shop-domain header to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered material, or otherwise cryptographically bind the shop identity to the signed payload — for example, by having `to_signable_string` incorporate the normalized header set, or by requiring host apps to independently verify that `request.shop` corresponds to an active, previously-established session before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated with respect to the HMAC check and must not be trusted for tenant-scoping decisions without an additional lookup against known installed shops/sessions.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the exact raw request body and the `x-shopify-hmac-sha256` header value sent by Shopify — both are valid under the app's single shared `client_secret`.
2. Attacker (or a component in the request path they influence) resends this exact body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — it validates successfully because the body and secret are unchanged. [6](#0-5) 
4. The registered `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, i.e., the attacker's own event data now impersonates the victim shop from the host application's point of view.
