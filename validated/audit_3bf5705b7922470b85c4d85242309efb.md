## Custody Analog Found: Multisig Timelock Override-Threshold Downgrade via Ordinary Owner-Removal Governance

### Title
Owner removal via normal (weak) quorum silently downgrades the timelock's override-approval quorum, letting stale approvals on a pending transaction retroactively satisfy the override and bypass the timelock delay - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
The custody invariant from the seed bug is "a value used to gate an economically sensitive action must not be silently substituted for a weaker one." In `multisig_account.move`'s timelock feature, `override_threshold` is meant to be a strong, independently-configured quorum (`> num_signatures_required`, up to `owners.length()`) required to bypass a time-delay before executing a multisig transaction. `update_owner_schema` — invoked via `remove_owner`/`remove_owners`, which only require the *normal* (weaker) `num_signatures_required` quorum — silently reclamps `override_threshold` down whenever an owner is removed [1](#0-0) . Because the override check is evaluated lazily at execution time against the *current* `override_threshold` and *current* votes on a still-pending transaction [2](#0-1) , votes cast under a stronger policy can retroactively satisfy a weakened override, letting the timelock delay be bypassed without any new approvals for the pending high-risk transaction itself.

### Finding Description
The `MultisigAccountTimeLock` resource stores `override_threshold: Option<u64>`, documented as "the number of approvals required to bypass the timelock and execute immediately," constrained to be strictly greater than `num_signatures_required` and at most `owners.length()` [3](#0-2) .

`can_execute_with_timelock` allows immediate execution of a *pending* transaction whenever its currently-recorded `num_approvals` meets or exceeds `override_threshold`, computed fresh from `pending_transaction.creation_time_secs` and the live vote/threshold state — not fixed at the moment the transaction was created or last voted on [4](#0-3) .

`update_owner_schema` (reached via the routine, weak-quorum entry functions `remove_owner`/`remove_owners`, which are governed only by `num_signatures_required`) clamps `override_threshold` down to the new (smaller) owner count whenever owners are removed, and only re-validates that it still exceeds `num_signatures_required` — it never re-validates the override quorum against any *pending* transaction's existing vote count [1](#0-0) . The project's own test `test_owner_removal_clamps_override_threshold` confirms this exact mutation path: an override of 3-of-3 is silently reduced to 2-of-2 the moment one owner is removed [5](#0-4) .

This breaks the custody invariant that the override quorum is a fixed, strong security control independent of routine (weaker) governance actions: a set of owners that only satisfies `num_signatures_required` can indirectly downgrade `override_threshold` for a transaction they already approved under the stronger policy, without casting any new approval on that transaction.

### Impact Explanation
Concrete scenario:
1. Multisig has owners `{A, B, C}`, `num_signatures_required = 2`, timelock configured with `override_threshold = 3` (unanimous approval needed to skip the delay).
2. `A` creates a high-value transaction (e.g., transferring the multisig's `AptosCoin`/fungible-asset holdings, rotating a resource account's auth key, or publishing a code-object upgrade). Creation implicitly counts as `A`'s approval.
3. `B` approves — 2/3 approvals. This is below `override_threshold (3)`, so `can_execute_with_timelock` forces the transaction to wait out the full delay, which is the entire point of the security control (giving owners/observers a window to detect and react to a malicious payload).
4. Before the timelock elapses, `A` and `B` — who already meet the *ordinary* 2-of-3 quorum — execute `remove_owner(C)` through the normal proposal flow. This is a routine action gated only by `num_signatures_required`, not by `override_threshold`.
5. `update_owner_schema` clamps `override_threshold` from 3 to 2 (owners.length() is now 2) [6](#0-5) .
6. The still-pending high-value transaction from step 2/3 already has 2 approvals (`A`, `B`). `can_execute_with_timelock` now finds `num_approvals (2) >= override_threshold (2)` and allows immediate execution — bypassing the timelock delay entirely, with zero new approvals cast on the sensitive transaction.

Impact is custody-grade and high: the timelock's entire purpose — protecting APT/fungible-asset transfers, resource-account signer-capability operations, or code-object upgrade transactions held by the multisig from being executed too quickly by a bare majority — is defeated by an unrelated, lower-bar governance action. This directly maps to the "Custody invariants should hold across... transfer" and "must not leak upgrade, freeze, or transfer authority to unprivileged callers" pivots: here the caller set is nominally privileged (owners), but is strictly weaker than the quorum the timelock was configured to require for that specific bypass, and the downgrade happens as a side effect rather than through the intended override path.

### Likelihood Explanation
Likelihood is Medium: it requires collusion or coincidence of exactly the ordinary quorum of owners (not necessarily malicious individually — could also occur accidentally, e.g., legitimate offboarding of a departing owner while a security-sensitive transaction is mid-flight). No external/unprivileged attacker is needed, but the scenario is a realistic operational sequence (owner departs/needs removal while a large pending transaction is queued), and the framework's own test suite demonstrates the clamp behavior is a known, intentional design choice rather than a random edge case — meaning it is easy to trigger deliberately by two of three owners with no additional friction.

### Recommendation
When clamping `override_threshold` down due to an owner-count change, re-validate all currently pending transactions (or at minimum, disallow immediate override-bypass for transactions whose approvals were locked in prior to the clamp), e.g. by tracking the `override_threshold` value effective at each transaction's `creation_time_secs` and requiring approvals to be re-collected under a changed threshold, or by forcing any owner-schema change that would reduce `override_threshold` for a transaction with already-satisfying-under-old / not-satisfying-under-new-but-now-satisfying approvals to require re-voting before it can execute early.

### Proof of Concept
```
setup_timelock_multisig(A, B, C);                    // owners = {A,B,C}, num_sig_required = 2
upsert_timelock(multisig_signer, 3600, option::some(3)); // override 3-of-3

create_transaction(A, multisig, PAYLOAD);             // seq 1, implicit approval from A
approve_transaction(B, multisig, 1);                  // 2/3 approvals -> below override(3), timelock enforced
assert!(!can_execute(A_addr, multisig, 1));           // blocked, must wait 3600s

// A and B use the ordinary 2-of-3 quorum to remove C via the normal proposal flow
remove_owner(multisig_signer, C_addr);
// update_owner_schema clamps override_threshold 3 -> 2 (owners.length() == 2)
assert!(timelock_override_threshold(multisig) == option::some(2));

// seq 1 transaction still has 2 approvals recorded from step above
assert!(can_execute(A_addr, multisig, 1));            // now TRUE — timelock bypassed with zero new votes
successful_transaction_execution_cleanup(A_addr, multisig, vector[]); // executes immediately, months early
```

**Note on coverage:** The full behavior of `create_with_owners_and_timelock` and every call site of `update_owner_schema` (e.g., `swap_owners`) was reviewed via search snippets and the generated documentation rather than a complete line-by-line read of the entire `multisig_account.move` file; if a Devin session is available, it would be worth confirming there are no additional guards elsewhere (e.g., in VM prologue/cleanup) that re-check `override_threshold` against a snapshot taken at approval time before treating this as fully unmitigated in production.

    /// `drop` is safe here because this resource holds only primitives (no capabilities, no
    /// event handles). It's used so that `remove_timelock` can `move_from` without destructuring.
    /// Note that because on-chain transactions cannot realistically be executed in less than a
    /// second, the resolution of `creation_time_secs` is at-second granularity — setting/removing
    /// a timelock within the same on-chain second as a pending transaction's creation is not a
    /// concern in practice.
    enum MultisigAccountTimeLock has key, drop {
        V1 {
            /// The time lock period in seconds after the creation of the multisig transaction.
            timelock_period: u64,
            /// The number of approvals required to bypass the timelock and execute immediately.
            /// Must be greater than the number of signatures required normally and less than or equal to the number of owners.
            override_threshold: Option<u64>,
        }
    }

    #[view]
    /// Return true if the owner can execute the transaction with given transaction id now.
    public fun can_execute(owner: address, multisig_account: address, sequence_number: u64): bool {
        assert_valid_sequence_number(multisig_account, sequence_number);
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, owner)) {
            num_approvals += 1;
        };

        is_owner(owner, multisig_account) &&
            sequence_number == last_resolved_sequence_number(multisig_account) + 1 &&
            num_approvals >= num_signatures_required(multisig_account) && can_execute_with_timelock(multisig_account, sequence_number, num_approvals)
    }

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
