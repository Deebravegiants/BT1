Audit Report

## Title
CORS wildcard-origin allowlist uses unanchored suffix matching, letting attacker-registered domains bypass host validation - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin()` in `core/services/gateway/network/httpserver.go` strips the `*.` prefix from a configured wildcard host and then checks `strings.HasSuffix(originHost, allowedHost)` with no dot-boundary enforcement, so a domain like `evilremix.com` passes the check configured for `*.remix.com`. [1](#0-0)  This is invoked directly from `handleRequest` using the caller-supplied `Origin` header whenever `CORSEnabled` is true. [2](#0-1) 

## Finding Description
The root cause is confirmed in the code: after stripping `*.`, the remaining suffix comparison has no check that the preceding character in `originHost` is a `.` or that the match aligns to a label boundary. [1](#0-0)  The exact-match branch above it is correct, but the wildcard branch is not boundary-aware. [3](#0-2)  `handleRequest` reflects the attacker-controlled `Origin` header back in `Access-Control-Allow-Origin` once `isAllowedOrigin` returns true, with no additional validation layer. [4](#0-3) 

## Impact Explanation
This is a legitimate origin-validation bypass. If an operator configures a wildcard entry in `CORSAllowedOrigins` (an explicitly supported configuration feature, not a misconfiguration), any attacker who registers a domain that merely ends with the configured suffix as a raw substring (e.g., `evilremix.com` for `*.remix.com`) is granted the same CORS trust as legitimate subdomains, allowing cross-origin JavaScript to read gateway responses. This maps to a genuine origin/allowlist-bypass integrity issue in the gateway's CORS handling, consistent with the "allowlist bypass" category referenced in the validation rules.

## Likelihood Explanation
No credentials, roles, or privileged access are required — only a normal browser request from an attacker-controlled domain sharing the vulnerable suffix, and only reachable if the operator opts into wildcard `CORSAllowedOrigins` entries. This is directly triggerable by an unprivileged external actor and is fully reproducible.

## Recommendation
Replace the raw `strings.HasSuffix` check with a boundary-aware comparison, e.g. `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` after stripping the `*.` prefix, so `evilremix.com` no longer matches `*.remix.com`.

## Proof of Concept
1. Configure gateway with `CORSAllowedOrigins: ["https://*.remix.com"]` and `CORSEnabled: true`.
2. Send `GET /<path>` with header `Origin: https://evilremix.com`.
3. `splitURL` yields `originHost = "evilremix.com"`; wildcard entry yields `allowedHost = "remix.com"`. [5](#0-4) 
4. `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, so the gateway responds with `Access-Control-Allow-Origin: https://evilremix.com`, wrongly trusting the attacker's origin. [6](#0-5) 
5. A Go unit test calling `isAllowedOrigin("https://evilremix.com")` against config `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it returns `true` (incorrectly) confirms the bug.

func (s *httpServer) splitURL(rawURL string) (string, string, string, error) {
	// lowercase the URL to avoid case sensitivity issues
	parsedURL, err := url.Parse(strings.ToLower(rawURL))
	if err != nil {
		return "", "", "", fmt.Errorf("error parsing URL: %w", err)
	}

	host, port, err := net.SplitHostPort(parsedURL.Host)
	if err != nil {
		// if there's no port, the host itself is returned
		if parsedURL.Host != "" {
			return parsedURL.Scheme, parsedURL.Host, "", nil
		}
		return "", "", "", fmt.Errorf("error splitting host and port: %w", err)
	}

	return parsedURL.Scheme, host, port, nil
}
