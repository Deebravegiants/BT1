### Title
Unsanitized swap routes can invoke attacker-controlled code and steal unrelated wallet tokens through `swap_collateral` - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts opaque user-supplied `swap` bytes and forwards them to the configured router without decoding the route or constraining the contracts it reaches. A malicious route can therefore place attacker-controlled code beneath the caller's `swap_collateral` authorization and add an unrelated token transfer to the authorization tree recorded by simulation. If that tree is signed, the transaction both settles as a valid collateral swap and transfers arbitrary tokens from the victim's wallet to the attacker.

### Finding Description
`swap_collateral` accepts `swap: Bytes` and requires only that the caller owns or delegates the account and that the destination can be supplied [1](#0-0) . The implementation never interprets those bytes: `swap_tokens` requires only that they are non-empty, snapshots input/output balances, authorizes exactly one controller-token transfer, and passes the payload to `router.execute_strategy` [2](#0-1) .

The measured controller balances constrain only the declared input and output tokens. They do not prevent route-selected third-party code from asking for an additional authorization from the original account owner. The repository's auth-tree proof uses a route-selected hop contract whose `swap` invokes `wallet_token.transfer(victim, attacker, amount)`; simulation records that transfer as a child of the victim's `swap_collateral` authorization, and enforcing mode executes it when the recorded tree is signed [3](#0-2) . The same test shows that signing the benign root-only tree rejects the rogue transfer, while signing the simulated poisoned tree moves the entire unrelated wallet balance [4](#0-3) .

This is the contract-level analogue of unsanitized branch/path input reaching command execution: untrusted bytes select executable external code, and the outer protocol's balance checks validate only the economic legs they measure, not the complete authorization side effects of that code.

### Impact Explanation
A victim can lose tokens that were never supplied to XOXNO and are unrelated to the swap, in addition to completing the intended collateral conversion. The test moves `77_770_000_000` units of an unlisted wallet token from the victim to the attacker while crediting the victim's expected `ETH` collateral [5](#0-4) . This satisfies theft of user funds.

The same untrusted `swap` argument is exposed by `multiply`, `swap_debt`, and `repay_debt_with_collateral`, so the issue is not confined to `swap_collateral`; that entrypoint is simply the demonstrated path.

### Likelihood Explanation
An unprivileged attacker can deploy the malicious hop contract and construct the malicious route bytes. The victim must submit or sign a transaction containing that route, but ordinary composition explicitly accepts route bytes generated off-chain, and simulation naturally surfaces the malicious child invocation inside the authorization tree rather than as a separate obvious approval [6](#0-5) . Wallet/software that does not inspect the full simulated auth tree can therefore turn an apparently valid strategy transaction into an unrelated-token transfer.

### Recommendation
Do not treat `swap` as opaque executable data at the controller boundary. Decode the route, or require the router to present a machine-checkable route manifest, and reject any route whose hop pools, token addresses, venues, or invoked functions are not on a governance-approved allowlist and do not match the requested `token_in`/`token_out`. Independently, expose or enforce an authorization-tree policy that permits exactly the expected input pull and no other caller-authorized child invocation.

### Proof of Concept
1. Deploy a malicious contract exposing a `swap()` function that calls `unrelated_token.transfer(victim, attacker, victim_balance)`.
2. Create `swap` bytes whose route executes that contract as a hop, while still returning enough `new` collateral for the controller's positive-output and final-risk checks.
3. Have the victim call:

```rust
controller.swap_collateral(
    victim,
    account_id,
    current_usdc,
    amount,
    new_eth,
    malicious_swap,
);
```

4. Simulate the transaction. The recorded auth tree contains a child `unrelated_token.transfer(victim, attacker, victim_balance)` under the victim's `swap_collateral` root [7](#0-6) .
5. Submit the simulated authorization tree. The swap succeeds and the unrelated wallet token is transferred to the attacker [8](#0-7) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
