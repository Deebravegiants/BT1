This confirms `jsonAPIError` writes `err.Error()` directly into the JSON response body via `models.NewJSONAPIErrorsWith(err.Error())` [1](#0-0) , and `SessionsController.Create` passes the raw error from `CreateSession` straight into `jsonAPIError` at the unauthenticated `/sessions` endpoint [2](#0-1) . The `orm.CreateSession` implementation does produce two distinct string errors — `"Invalid email"` when the email fails `constantTimeEmailCompare`, and `"Invalid password"` when the password hash check fails — each behind a distinguishable code path [3](#0-2) .

Audit Report

## Title
User enumeration via distinct login error messages disclosed to unauthenticated clients - (File: core/sessions/localauth/orm.go)

## Summary
The unauthenticated `/sessions` login endpoint returns different, attacker-observable error strings ("Invalid email" vs "Invalid password") depending on whether the submitted email matches an existing user, allowing an unauthenticated caller to enumerate registered user emails on a Chainlink node.

## Finding Description
`SessionsController.Create`, mounted unauthenticated at `/sessions` via `unauth.POST("/sessions", sc.Create)`, forwards whatever error `AuthenticationProvider().CreateSession` returns directly into `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) . `jsonAPIError` places `err.Error()` verbatim into the JSON response body when the error isn't a `*models.JSONAPIErrors` [1](#0-0) . In `localauth.orm.CreateSession`, after `FindUser` succeeds, the code performs a distinct check for email match versus password match, returning `pkgerrors.New("Invalid email")` or `pkgerrors.New("Invalid password")` respectively, each firing a different audit event (`AuthLoginFailedEmail` vs `AuthLoginFailedPassword`) [4](#0-3) . There is no generic/constant error normalization in `SessionsController.Create` before the response is emitted, so the distinguishing string is exposed unauthenticated over HTTP.

## Impact Explanation
This maps to CWE-209 (information exposure through error messages) and enables unauthenticated account/user enumeration, which is a legitimate, if lower-severity, information-disclosure class relevant to node operator security posture (aids credential stuffing/phishing against known valid accounts on the node's admin API). It does not by itself grant authentication bypass, key exfiltration, unauthorized job execution, or fund movement.

## Likelihood Explanation
The `/sessions` endpoint is public by design for login and only rate-limited, not blocked, per `sessionRoutes` in `core/web/router.go` [5](#0-4) , so an attacker can iterate over candidate emails without any credential or role and reliably distinguish account existence from the response body. This is a single, ordinary unauthenticated POST request — no special setup required.

## Recommendation
Normalize both the "unknown email" and "wrong password" cases in `orm.CreateSession` to a single generic error message (e.g., "invalid credentials"), keeping the differentiated `AuthLoginFailedEmail`/`AuthLoginFailedPassword` audit events for internal logging only, and/or have `SessionsController.Create` substitute a constant generic message for all `CreateSession` 401 failures rather than propagating `err.Error()` to the client.

## Proof of Concept
```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"realuser@example.com","password":"wrongpassword"}
```
Response body contains `"Invalid password"`.

```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"nonexistent@example.com","password":"wrongpassword"}
```
Response body contains a different message (either "Invalid email" or the underlying `FindUser` not-found error), confirming the distinguishable behavior described in `core/sessions/localauth/orm_test.go` and `core/web/sessions_controller_test.go` test cases for "incorrect pwd" vs "incorrect email" scenarios [6](#0-5) .

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
