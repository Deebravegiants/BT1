### Title
Signup signature omits `signup_id`, allowing the same signed iris payload to be replayed/re-attributed across a different signup session - (File: `src/plans/enroll_user.rs`)

### Summary
`make_signature` builds the domain-separated signature that is submitted to the backend as proof that a given orb signed a specific iris capture for a specific `userId`. Unlike the `signup_id`-scoped multipart request that carries it, the signed payload itself never binds to the `signup_id`, mirroring the reported class of bug where a state/authorization structure omits an identifier (there: destination chain ID in PDA seeds; here: session/signup identifier in the signed digest) that is required to scope the cryptographic artifact to the intended execution context.

### Finding Description
`make_signature` hashes `ORB_ID`, the target `user_qr_code.user_id`, and the iris/pipeline output, then signs it with the secure element: [1](#0-0) 

This signature is sent to the backend alongside a *separate*, unsigned `signup_id` field, and the backend signup endpoint is addressed by that same `signup_id` in the URL path: [2](#0-1) 

Because `signup_id` (an `orb_wld_data_id::SignupId`, generated per attempt in `Plan`) is not part of the hashed context in `make_signature`, the cryptographic signature over the iris data is not bound to the specific signup session it is meant to authorize: [3](#0-2) [4](#0-3) 

This is structurally analogous to the reported Solana bug: a signed/derived artifact (there, a PDA; here, a secure-element signature) omits a context identifier (destination chain ID / `signup_id`) that should scope it to one specific execution instance, letting the same artifact be presented for a different instance than the one intended.

### Impact Explanation
If the backend relies on the orb-signed signature purely as proof of "this iris data came from this orb, tied to this signup," but does not itself independently re-derive or cross-check that the signature is unique to the `signup_id` path it was submitted under (this repo cannot show backend-side verification logic, since it is out of scope), a captured `(signature, userId, codes)` tuple from one signup attempt could be replayed against a different `signup_id` for the same `userId`/iris output — e.g. a retried or duplicate signup created by the same physical scan — producing signup state bleed between sessions rather than a fresh, uniquely-authorized signup. This does not, on its own, forge a signature for a different iris/user (those are hashed), but it removes the guarantee that the signature is unique per signup session.

### Likelihood Explanation
This requires the backend to have a security-relevant expectation that the signature is single-use / scoped to one `signup_id`, and for an unprivileged party (or a retried orb-core flow) to be able to submit the same signature under a different `signup_id`. Whether the backend actually depends on per-session uniqueness of this signature (versus merely using `signup_id` for idempotency/HTTP addressing unrelated to the signature's authorization) could not be verified from the orb-core codebase alone, since `signup_post`/`signup_poll` backend-side verification logic lives outside this repository.

### Recommendation
Include `signup_id` in the hashed context passed to `secure_element::sign` in `make_signature`, so the resulting signature is cryptographically bound to the specific signup session, consistent with how the analogous Solana fix added the destination chain ID into the seeds used to derive/authorize the `SwiftSourceSolanaState` account.

### Proof of Concept
Not independently reproducible from this repository alone: reproducing the impact requires backend-side signup verification behavior (whether/how the backend checks that a signature is unique to a `signup_id`), which is not present in `orb-core`. The root-cause code path (signature construction omitting `signup_id`) is shown above at [1](#0-0) ; confirming exploitability would require inspecting the backend `/api/v2/signups/{signup_id}` handler referenced in [5](#0-4) .

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
