## Finding

### Title
Panic-inducing unchecked length slicing on attacker-controlled `message.from` bytes in cross-chain calldata delivery — ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`HyperFungibleToken`'s ISMP `on_accept` handler decodes an ABI-encoded `Message` from an incoming POST request and, when the message carries optional calldata with no attached signature, derives the dispatch origin from `message.from` using unchecked slice arithmetic and `copy_from_slice`. If the byte length of `message.from` does not match the length the code assumes (20 bytes for EVM sources, 32 bytes for non-EVM sources), the runtime panics instead of returning a typed error — the same bug class as CVE-2024-41437 (an unchecked length assumption in a byte-buffer decoder leading to an out-of-bounds/invalid-length access and a crash on crafted input).

### Finding Description
In `on_accept`, once the token mint/transfer succeeds and `message.data` is non-empty, the code branches on whether a signature was provided: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

- `from_bytes.len() - 20`: if `from_bytes.len() < 20`, this `usize` subtraction underflows. In a debug/overflow-checked build this panics immediately (`attempt to subtract with overflow`); in a release build without overflow checks it wraps to a huge index, and the subsequent slice indexing panics with an out-of-bounds access — either way, a crash.
- `account.copy_from_slice(from_bytes)`: `copy_from_slice` panics unconditionally unless `from_bytes.len() == 32` exactly.

`message.from` originates from `Message::abi_decode(&body)` — an ABI-decoded `bytes` field from the ISMP `PostRequest.body` — and is never length-validated before this point, unlike `message.to`, which the Solidity side gates with an explicit length check (`_toAddr` reverts unless the address field is exactly 20 bytes): [2](#0-1) 

By contrast, the Rust decoder performs no equivalent length validation on `from` before slicing/copying it. This mirrors the exact defect pattern seen and already fixed elsewhere in this codebase for the same class of bug — e.g. `StateMachine::from_str` and `consensus_state_id_from_str` were hardened specifically because unchecked `copy_from_slice` on attacker-influenced byte lengths panics and crashes the runtime/RPC worker: [3](#0-2) [4](#0-3) 

The `on_accept` path in `hyper-fungible-token` has no such guard.

### Impact Explanation
A panic inside `on_accept`, which executes during ISMP message delivery (reachable through `pallet_ismp::Pallet::<T>::execute`/`handle_unsigned` when a relayer submits a delivery proof for a POST request), aborts the dispatchable/extrinsic executing the delivery. Depending on how the ISMP host's dispatch loop handles a panicking module callback, this can abort the whole extrinsic or block-import path processing that batch of messages, denying delivery of that message (and potentially co-batched messages) — a Denial-of-Service against the token bridge's message-delivery route, matching the "Medium" severity and availability-only (`C:N/I:N/A:H`) profile of the referenced CVE.

### Likelihood Explanation
Reachability depends on whether the paired dispatch-side contract(s) that originate these `PostRequest`s always fix `message.from`'s encoded length (e.g., to `msg.sender`, always 20 bytes on EVM, or a fixed-size AccountId on Substrate). I was not able to fully verify the construction of `message.from` on the dispatch side within the available tool budget — only the receive/decode side (`module.rs`) and the emitted event assignment (`from: msg.sender`) were confirmed. If the length is always fixed by the trusted counterpart contract, exploitation requires either a bug in that contract or control over a governance-registered source contract, lowering the likelihood. If any dispatch path allows the sender to influence the encoded length of the `from` field (e.g., through a custom or upgraded implementation, or a non-standard companion pallet), the DoS is trivially triggerable by any account with access to that bridge's public dispatch entrypoint.

### Recommendation
Validate the length of `message.from` before slicing or copying it, returning a typed `HftError` (mirroring the existing `HftError::InvalidRecipientLength` used for `message.to`) instead of relying on `copy_from_slice`/subtraction to fail safely:

```rust
let from_bytes = message.from.as_ref();
let origin_bytes = if source.is_evm() {
    if from_bytes.len() < 20 {
        return Err(HftError::InvalidSenderLength(from_bytes.len()).into());
    }
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    if from_bytes.len() != 32 {
        return Err(HftError::InvalidSenderLength(from_bytes.len()).into());
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```

### Proof of Concept
1. An account with access to submit a cross-chain POST request through the registered HFT bridge contract (or, if reachable, any account able to influence the raw ABI-encoded `body`) constructs a `Message` whose `from` field is fewer than 20 bytes (e.g., 0 bytes) while `data` is non-empty and `signature` is `None`.
2. A relayer delivers the request with a valid proof; `pallet_ismp` invokes `HyperFungibleToken::on_accept`.
3. Execution reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 0`, causing a `usize` underflow / out-of-bounds panic instead of a decoding error, aborting the message-delivery extrinsic.

**Caveat:** This finding's practical reachability hinges on whether the trusted dispatch-side contract(s) ever allow `message.from`'s encoded byte length to vary from the fixed 20/32-byte assumption; I could not fully confirm this within the tool budget, so treat the reachability claim as unverified pending inspection of the dispatch-side `Message` construction code (both the EVM `HyperFungibleToken.sol`/`HyperFungibleTokenUpgradeable.sol` dispatch functions and any Substrate-side companion pallet).

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
