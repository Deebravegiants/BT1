### Title
Placeholder sentinel collision in `withFilesystemFallback.get()` causes legitimate short values equal to `'~'` to be treated as filesystem-fallback markers - ([File: adapters/storage-mobile/src/helpers/with-filesystem-fallback.ts])

### Summary
`withFilesystemFallback` uses the literal string `'~'` as an out-of-band sentinel to mark "large value spilled to filesystem." Because the sentinel is compared against the *parsed* value returned by the underlying `storage.get()`, any legitimately stored value that JSON-round-trips to the exact string `'~'` collides with the sentinel, causing `get()` to incorrectly redirect to `filesystemStorage.get(key)`, which was never populated for that key.

### Finding Description
`set()` decides how to persist a value based on payload size: [1](#0-0) 

For payloads under `threshold`, it calls `storage.setString(key, stringifiedPayload)`, where `stringifiedPayload = JSON.stringify(value)`. If `value` is the plain string `"~"`, `JSON.stringify("~")` produces `'"~"'`, which `StorageMobile.setString` writes verbatim to `AsyncStorage`: [2](#0-1) 

On read, `get()` calls `storage.get(key)`, which internally calls `batchGet`, which does `JSON.parse(value)` on the raw stored string: [3](#0-2) 

`JSON.parse('"~"')` yields the string `"~"` — bare, unquoted, identical to the sentinel constant. `withFilesystemFallback.get()` then performs a strict equality check against the placeholder: [4](#0-3) 

Since the parsed real value (`"~"`) strictly equals `placeholder` (`"~"`), the check `value !== (placeholder as never)` is `false`, and `get()` incorrectly falls through to `filesystemStorage.get(key)`. Because the real value was written via `setString` (small-value path), the filesystem copy for that key was **never written** (`filesystemStorage.setString` is only called in the large-value branch), so `filesystemStorage.get(key)` fails to read the file and returns `undefined` (its `get()` swallows all errors): [5](#0-4) 

No validation anywhere rejects or escapes values equal to the sentinel string before persisting them through the small-value path, so any code path that stores an attacker-influenced literal string `"~"` under a tracked key (e.g., a generic settings/config store backed by this adapter, populated by remote-config values, imported backup fields, or RPC-driven state) will silently lose that value on the next read, being replaced by `undefined`. The identical flaw also exists in `batchGet`: [6](#0-5) 

### Impact Explanation
If a security-relevant flag or marker (e.g., a lock state, migration/version marker, or feature toggle) is ever stored as a raw string value through this generic storage layer and that value happens to be (or is coerced/attacker-influenced to be) exactly `"~"`, subsequent reads return `undefined` instead of the true value. Depending on how the caller interprets `undefined` (commonly treated as "unset"/default), this can cause the wallet to fall back to default/unlocked/unmigrated state, matching the "wrong/absent security state" impact described. The blast radius is limited strictly to keys whose value can literally equal the single-character string `'~'`.

### Likelihood Explanation
The bug is 100% deterministic and requires no privilege beyond causing a normal `set(key, "~")` call through this storage instance's public API — i.e., any component/flow that persists an attacker-influenced string value via this adapter with content equal to `"~"`. It does not depend on race conditions, timing, or environment. Likelihood of actually reaching a security-relevant key depends on whether any such flag/marker is stored as a bare string susceptible to attacker control equalling `"~"`, which is plausible but not universally confirmed across all call sites in the index.

### Recommendation
Do not use a plain-data value as the sentinel. Use an out-of-band marker that cannot collide with legitimate payloads, e.g.:
- Store the placeholder as a value with a distinguishing wrapper/tag that cannot be produced by `JSON.stringify` of user data (e.g., `{ __fsFallback: true }` compared with a dedicated type-check, or prefix the sentinel with a non-JSON-parseable marker written via a separate `setString` call rather than through `JSON.stringify`).
- Alternatively, track the "spilled to filesystem" bit in a separate namespaced key/index rather than overloading the value slot with a sentinel string.

### Proof of Concept
```ts
// pseudo unit test against withFilesystemFallback
const storage = withFilesystemFallback({
  storage: mockStorageMobile, // uses real JSON.stringify/JSON.parse round trip like StorageMobile
  filesystem: mockFilesystem,
  hashString: (s) => s,
  rootDir: '/tmp/test',
  threshold: 1024 * 1024,
  placeholder: '~',
})

await storage.set('lockFlag', '~') // legitimate small value, real data
const result = await storage.get('lockFlag')

// Expected (bug): result === undefined, because get() treats stored '~' as sentinel
// and redirects to filesystemStorage.get('lockFlag'), which was never written.
expect(result).toBeUndefined() // demonstrates loss/corruption of real value
// Whereas correct behavior should be:
// expect(result).toBe('~')
```
This reproduces the sentinel collision purely through the module's public `set`/`get` API with no test/mock hacks beyond the standard `AsyncStorage` mock already used elsewhere in the adapter's test suite.
