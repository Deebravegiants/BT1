### Title
Webhook shop/topic/webhook-id identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body bytes, while `shop`, `topic`, `webhook_id`, and `api_version` are taken from HTTP headers that are never included in the HMAC computation. `Registry.process` trusts these unverified header values to build `WebhookMetadata`, which the host app's handler uses to identify which shop/tenant the webhook belongs to.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from request headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler, then forwards the unverified `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight into `WebhookMetadata` [4](#0-3) . `WebhookMetadata.shop` is a plain `String` field with no independent verification [5](#0-4) .

Because the HMAC secret (`Context.api_secret_key`/`client_secret`) is shared across every shop that has the app installed rather than being shop-specific, any shop that installs the app receives its own genuinely-signed webhook deliveries. The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop_header == shop_that_actually_sent_body`.
In this implementation that equality does not hold — `hmac_valid(body)` only proves the body bytes were signed by the app's shared secret, not which shop the header claims to be from.

### Impact Explanation
An unprivileged holder of one shop's genuine webhook delivery (any merchant/user who has installed the multi-tenant app on their own store, an "unprivileged internet user" with respect to other tenants) can capture a legitimately-signed webhook (raw body + HMAC) that Shopify sent to the app for their own shop, then replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any host application that uses `data.shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern) will process the attacker's payload as though it originated from the victim shop, resulting in cross-tenant data corruption/injection — a cross-tenant boundary violation.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must control an app installation (a normal, unprivileged capability for any merchant who can install a public/custom app) and must have received at least one webhook delivery to capture a valid body+HMAC pair. No access token, `api_secret_key`, or privileged credential is required — only observation of one's own inbound webhook traffic and the ability to send an HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed content used for HMAC verification, or independently validate `request.shop` against a shop known to be registered with a value bound into the signature (e.g., verify that the body itself, or a signed claim, matches the header-derived shop) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated and that host applications must cross-check it against tenant records derived from authenticated data, and consider making the header validation mandatory in the gem itself so unmodified header trust cannot occur silently.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and receives a legitimate webhook:
body = '{"id":123,"note":"legit body from shop-a"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SHARED_SECRET, body) # captured from real Shopify delivery

# Attacker replays the same body/hmac but claims it is from shop-b (victim):
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body signature matches),
#    handler.handle receives WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)
#    even though shop-b never sent this webhook.
```
