## Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop domain, topic, and webhook id that drive the handler's business logic are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then forwards these header-derived, unauthenticated values straight to the app's webhook handler. This breaks the identity binding: **HMAC-covered bytes (body) ≠ bytes acted upon (headers: shop, topic, webhook-id)**.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 

Only `@raw_body` is included in `to_signable_string`, i.e. the value that is HMAC-verified. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from the request's HTTP headers, which are entirely outside the scope of the signature.

`Registry.process` validates the HMAC only over the body, then immediately trusts the header-derived `shop`/`topic`/`webhook_id` to dispatch the handler: [2](#0-1) 

Because Shopify signs webhooks using the app's single `client_secret` (the same secret for every shop that installs the app, not a per-shop secret), any shop that has legitimately installed the app receives webhooks whose `(raw_body, hmac)` pair is valid under that same shared secret. This means the HMAC only proves "this body was generated by Shopify for some install of this app" — it proves nothing about which shop the body concerns, since that information (`shopify-shop-domain` header) is unsigned.

An unprivileged holder of one valid `(raw_body, hmac)` pair (e.g., a merchant who installed the app and captured/replayed one of their own webhooks) can resend the exact same body/HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`). `Utils::HmacValidator.validate(request)` still succeeds because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as the origin: [3](#0-2) 

Any host application that keys its persistence, authorization, or state transitions off `WebhookMetadata#shop` (the documented, intended use of this field) will process attacker-supplied body content under an arbitrary victim shop identity.

### Impact Explanation
This is a cross-tenant confusion vector: a party with only their own shop's valid webhook material can cause the app to attribute body content to a different, unauthorized shop, since the shop identity is never cryptographically bound to the payload. Depending on the webhook topic and how the host app uses `WebhookMetadata#shop`/`#topic` (e.g., to select which merchant's records to mutate), this can lead to cross-tenant data corruption or unauthorized state changes attributed to a shop the caller does not control — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only one valid `(raw_body, hmac)` pair, which any shop that has installed the app naturally possesses from its own legitimate webhook traffic (since the signing secret is shared across all installs of the same app, not per-shop). No access to `api_secret_key`, access tokens, or the target shop's credentials is needed — only a replay/header-substitution against the app's public webhook endpoint.

### Recommendation
Bind the shop (and topic/webhook id, if they drive business logic) into the HMAC-covered material, or otherwise cryptographically tie the header values to the verified body (e.g., include them in `to_signable_string`, or cross-check them against an out-of-band trusted channel such as the session/shop the webhook subscription was registered for). At minimum, document and/or enforce that `WebhookMetadata#shop` must never be trusted as an authenticated tenant identifier by consumers of this gem without additional verification.

### Proof of Concept
1. Shop A installs the app and receives a legitimate webhook with body `{}` and header `shopify-hmac-sha256` computed over `{}` using the app's shared `client_secret`.
2. Attacker (controlling Shop A, or anyone who intercepted this pair) resends the identical raw body and HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` and any desired `shopify-topic`.
3. `Webhooks::Request.new(raw_body: "{}", headers: spoofed_headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `{}` against the shared secret: [4](#0-3) 
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the host app's handler to act as if the (empty/attacker-chosen) body genuinely originated from `victim-shop.myshopify.com`.
