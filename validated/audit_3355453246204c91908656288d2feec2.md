## Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers to route and attribute the webhook to a tenant. The HMAC binds only the body bytes; it never binds the header values that the rest of the pipeline treats as authenticated shop identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` (i.e., only the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` (an unauthenticated header) as the tenant identity passed to the app's handler: [4](#0-3) 

The equality that should hold is: `shop (bytes covered by HMAC) == shop (bytes acted on by the handler)`. In reality the HMAC only covers `raw_body`, so `shop`/`topic`/`webhook_id` can be swapped in transit or replayed with a different shop header while the HMAC remains valid, breaking that equality. This mirrors the report's root cause class: a value used for a security-relevant decision (fee attribution in the report; tenant attribution here) is derived from data that is not actually covered by the verification that is presented as proof of authenticity.

### Impact Explanation
Any request that reaches `Registry.process` with a previously-valid `(raw_body, hmac)` pair — but an attacker-chosen `shop-domain` header — passes signature validation and is routed to the handler as if it originated from the attacker-chosen shop. Because `WebhookMetadata.shop` is taken from the unauthenticated header, this is a cross-tenant identity confusion: data legitimately signed for tenant A can be delivered to the handler labeled as tenant B, letting an attacker with access to their own shop's genuine webhook traffic misattribute events to another merchant. This lands in the Critical "cross-tenant access" category since the app's handler code (which typically keys storage/session lookups off `data.shop`) has no way to detect the substitution.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(raw_body, hmac)` pair generated for their own shop (obtainable by installing the app and triggering an event that fires a webhook to the app's public endpoint, then resending that same body/HMAC directly to the endpoint with a modified `shopify-shop-domain` header). No knowledge of `api_secret_key` is needed because the original signature is reused verbatim — only the routing header is swapped. This requires only ordinary merchant/installer access, not a privileged credential.

### Recommendation
- Bind `shop`, `topic`, and `webhook_id` into the signed payload, or at minimum cross-check `request.shop` against the shop already known to be associated with the delivered `webhook_id`/subscription before invoking the handler.
- Short term: document/enforce that consuming apps must independently validate the `shop-domain` header against their own known/installed shop list rather than trusting it implicitly from `WebhookMetadata`.
- Long term: extend `Utils::HmacValidator`/`VerifiableQuery` so `to_signable_string` incorporates all header fields that downstream code treats as authenticated (shop, topic, webhook id), matching the invariant the report calls for ("send the exact... value", not an estimate/unverified proxy).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any event (e.g., create a product) so Shopify sends a real webhook POST to the app's public webhook endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over body B>`, and body `B`.
2. Capture `(B, valid HMAC)` (e.g., via a debug proxy the attacker controls in front of their own installation, or an app feature that echoes back webhook receipt).
3. Resend `B` with the same `shopify-hmac-sha256` value to the app's webhook endpoint, but set `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-31` succeeds because it only checks `B` against the HMAC. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-199` then calls the handler with `shop: "victim-shop.myshopify.com"`, `body: parsed(B)` — data now falsely attributed to the victim tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
