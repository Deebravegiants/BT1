Found it: the webhook `shop-domain` header is not covered by the HMAC.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `HmacValidator.validate` checks only binds the request body. The `shop-domain`, `topic`, `webhook-id` and `api-version` values are all read straight from unauthenticated HTTP headers and are never part of the signed material, yet `Registry.process` trusts `request.shop` to identify the tenant for the dispatched handler.

### Finding Description
`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`. [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body bytes: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are not part of that signed string: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` (and `request.topic`) as the trusted tenant identifier, without ever re-checking that this header was itself authenticated: [4](#0-3) 

This breaks the identity binding `shop_authenticated == shop_used_by_handler`. Because the HMAC only proves "Shopify sent *some* payload with this exact body", any unprivileged attacker who has previously received (or replays/observes) one valid webhook body+signature pair for shop A can resend that same signed body but with headers claiming a different `shop-domain` (shop B) or a different `topic`, and the library will still report `Utils::HmacValidator.validate(request)` as `true`, because the signature never covered the header values.

The host application's webhook handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` believing the shop label is authenticated, when in fact it is attacker-controlled and outside the HMAC's coverage: [5](#0-4) 

This exactly mirrors the H-1 bug class: a field (here, `shop`/`topic`) is *acted on* by the library (used as the tenant key dispatched to the handler) but is *not covered* by the cryptographic binding (HMAC) that the library itself performs and advertises as its authenticity guarantee.

### Impact Explanation
An attacker who can obtain any one legitimately-signed webhook body (e.g. from their own installed test shop, or via a lower-privilege webhook subscription they control) can relabel it as belonging to a different `shop-domain`/`topic` and have `ShopifyAPI::Webhooks::Registry.process` validate it as authentic and dispatch it to the merchant application's handler under the attacker's chosen shop identity. Any host application that relies on `WebhookMetadata#shop` to select which tenant's data to update (a documented, intended use of this field) is exposed to cross-tenant data corruption/injection using only this gem's own verification primitive, satisfying the "cross-tenant access" Critical impact category, since the trust boundary is crossed entirely within the shipped `HmacValidator`/`Webhooks::Request`/`Registry` code path.

### Likelihood Explanation
The attacker only needs unprivileged access to any one valid `(body, hmac)` pair signed by the app's own `client_secret` for any topic/shop (trivially obtainable by installing the app on an attacker-owned free development store and triggering any webhook) and the ability to POST to the app's public webhook endpoint with forged headers — no `client_secret`, access token, or privileged account is required, and it is fully reachable via documented gem usage (`Registry.process`).

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` header values in the `to_signable_string` used for HMAC verification, or otherwise reconstruct and verify the signature the same way Shopify computes it (Shopify itself signs only the raw body with `X-Shopify-Hmac-Sha256`, so the additional headers must be independently authenticated, e.g. by requiring `shop` to be looked up only from a session/registration store keyed by an already-authenticated relationship rather than trusted directly from the header). At minimum, `Registry.process` should not treat `request.shop`/`request.topic` from headers as authenticated identifiers when dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (an unprivileged action) and receives a legitimately Shopify-signed webhook, e.g. body `{"foo":"bar"}` with header `x-shopify-hmac-sha256: <valid mac for that body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker POSTs the identical raw body and identical `x-shopify-hmac-sha256` value to the merchant app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, raw_body)` — unchanged since only the body is signed — and returns `true`.
4. `Registry.process` proceeds to call the registered handler for the (possibly attacker-chosen) topic with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this data, demonstrating the cross-tenant identity confusion.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          received_signature = verifiable_query.hmac
