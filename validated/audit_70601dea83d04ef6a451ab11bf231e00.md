Silent ERC20 transfer failures in Tron `IntentGatewayV2.withdraw()` and predispatch sweep are not caught by return-value checks - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` checks only the boolean returned by the low-level `.call()` (i.e., whether the call reverted), never decoding/verifying the ERC20 function's own returned success flag. For "no revert on failure" ERC20 tokens (e.g. classic ZRX-style tokens that return `false` instead of reverting), the low-level call succeeds even though the token transfer itself failed, so the contract proceeds as if funds moved when they did not — exactly the bug class described in the reference report.

### Finding Description
In `withdraw()`, escrowed tokens are released with a raw low-level call instead of `SafeERC20.safeTransfer`: [1](#0-0) 

`success` here only reflects whether the target contract's code executed without reverting — it is `true` even if the ERC20 `transfer` function internally returns `false` on failure (no-revert-on-failure tokens). The code never inspects the ABI-decoded boolean return value, so `TransferFailed()` never fires for this class of token, `_orders[body.commitment][token]` is still decremented, and `_filled[body.commitment]` is marked filled/refunded as if the beneficiary was paid — even though no tokens moved.

The same unchecked pattern appears in `SweepDust` handling: [2](#0-1) 

and in the transaction-fee payout in the same function: [3](#0-2) 

Additionally, on the deposit/escrow side, `placeOrder`'s predispatch sweep (moving tokens from the `CallDispatcher` back into the gateway) credits escrow based on the *requested* amount rather than verifying the *actual* balance received by the gateway: [4](#0-3) 

The sweep itself is executed via `ICallDispatcher.dispatch`, whose only safety check is that the inner `.call()` did not revert: [5](#0-4) 

This mirrors the exact root cause in the referenced Footium report: return-value-based ERC20 failures are indistinguishable from success at every one of these call sites. Note this is specific to the Tron deployment — the primary EVM `IntentGatewayV2.sol`/`IntentsBase.sol` correctly use `SafeERC20.safeTransfer`/`safeTransferFrom` for withdrawals, e.g.: [6](#0-5) 

### Impact Explanation
For a no-revert-on-failure ERC20 used as an order's input or output token (a solver, filler, or user can freely choose any ERC20 address for `order.inputs`/`order.outputs`), a transfer failure during `withdraw()` — e.g. triggered by blacklist logic, a paused state, or any internal check returning `false` rather than reverting — is silently treated as success: the escrow accounting is decremented and the order is marked filled/refunded, but the beneficiary (solver or user) never receives the tokens. This is a direct loss of funds for the intended recipient, with no path to retry since the order is already marked as settled (`_filled`) and escrow already zeroed out. The same class of bug on the deposit side allows escrow bookkeeping to diverge from the gateway's real token holdings, which can allow legitimate escrow for other orders to be later drained since `_orders[commitment][token]` bookkeeping no longer reflects actual custodied balances.

### Likelihood Explanation
Reachable via the unprivileged, permissionless `placeOrder`/`fillOrder`/cross-chain `withdraw` (triggered by `onAccept`) paths using any attacker- or user-chosen ERC20 token address — no special privileges required. The only precondition is using (or being forced to interact with) a token that implements the no-revert-on-failure pattern, which is a well-known and still-deployed category of ERC20 tokens (ZRX and similar).

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `SweepDust` handling, and the predispatch/output sweep in `placeOrder`) with OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the ERC20 return value (or reverts on missing/invalid return data), consistent with the primary EVM contract's `IntentsBase._withdraw`. For deposit-side sweeps, verify actual received balance via `balanceOf` diffs (as done in `evm/src/apps/IntentGatewayV2.sol`) before crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy (or use) an ERC20 token that returns `false` on transfer failure instead of reverting (no-revert-on-failure pattern).
2. Place a cross-chain order on the Tron `IntentGatewayV2` with this token as an input, and have it filled normally so escrow is recorded in `_orders[commitment][token]`.
3. Arrange for the token's internal transfer check to fail at redemption time (e.g., token owner blacklists the beneficiary, or the token is paused) such that `transfer()` returns `false` without reverting.
4. Trigger settlement so `onAccept` calls `withdraw()`: the low-level `.call()` at line 706 returns `success = true` (since the call did not revert), bypassing the `TransferFailed()` check at line 707.
5. Observe that `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set (order marked as settled), while `beneficiary`'s token balance is unchanged — funds are permanently lost/unretrievable for that beneficiary.
