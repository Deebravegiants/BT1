The claim is confirmed by direct code inspection. `ProcessRequest` in `core/services/gateway/gateway.go:221-294` is the entry point invoked by the gateway's HTTP server for every incoming JSON-RPC request, requiring no authentication beyond the optional `auth` header passed to `jsonrpc2.DecodeRequest`, and it copies the caller-supplied `jsonRequest.ID` straight through to `msg.Body.MessageID` via `ValidatedMessageFromReq` [1](#0-0) , with only a length cap enforced [2](#0-1) . For legacy requests, `ProcessRequest` calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) , which for the `web_api_trigger` method reaches `capabilities.handler.HandleLegacyUserMessage`.

That function stores the per-request `callback` into the shared `h.savedCallbacks` map keyed purely by the attacker-controlled `msg.Body.MessageID`, with an explicit unconditional overwrite and no existence check (the code even leaves a `// TODO: apply allowlist and rate-limiting here` comment, confirming no authorization gate exists) [4](#0-3) . When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes whatever entry currently sits at that key and forwards the response to it, with no ownership/ownership-token check [5](#0-4) . This is a straightforward last-writer-wins race that any two independent callers with the same `MessageID` can trigger, exactly as described.

The comparison to `OutgoingConnectorHandler` also holds up: `responses.new(id)` explicitly checks for an existing channel and rejects duplicates before inserting [6](#0-5) , confirming that the missing guard in the Web API trigger path is an inconsistency relative to the sibling code, not an intentional design choice enforced elsewhere.

No authentication, allowlist, or per-caller binding is applied anywhere in this path before the map write — the request reaches the handler directly from the public gateway HTTP endpoint, and the `TODO` comment confirms allowlisting was never implemented for this method. This satisfies "unprivileged actor reachable" and "existing checks reviewed and shown insufficient" (there are none). The impact is legitimate cross-user response confusion / DoS against the gateway's public Web API trigger path, matching the claimed in-scope impact category.

Audit Report

## Title
Unprivileged clients can hijack another user's Web API trigger response via `MessageID` collision in the Gateway's `savedCallbacks` map - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` stores each pending Web API trigger request's response callback in a shared map keyed solely by the client-supplied JSON-RPC `ID` (`MessageID`), overwriting any existing entry for that key without checking for a collision. A second unprivileged caller who submits a request with the same `MessageID` while the first is still pending silently displaces the first caller's callback, so the eventual DON response is delivered to the second caller instead, while the first caller's request times out.

## Finding Description
The gateway's public HTTP endpoint routes every incoming JSON-RPC request through `ProcessRequest`, which copies the caller-controlled request `ID` into `msg.Body.MessageID` (via `ValidatedMessageFromReq`) with only a length check enforced, and then dispatches legacy requests to `h.HandleLegacyUserMessage(ctx, msg, callback)` with no authentication or allowlist applied. Inside `HandleLegacyUserMessage`, the handler unconditionally writes `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` before forwarding the request to all DON members — there is no check for an existing entry at that key (the code even contains a `// TODO: apply allowlist and rate-limiting here` comment confirming no additional gating exists). When a DON node later responds, `handleWebAPITriggerMessage` looks up `savedCallbacks[msg.Body.MessageID]`, deletes it, and forwards the response to whatever callback is currently registered — it performs no verification that the response belongs to the original requester. This directly contrasts with the sibling `OutgoingConnectorHandler`, whose `responses.new(messageID)` explicitly detects and rejects duplicate IDs before registering a new response channel, proving that the missing duplicate check in the Web API trigger path is an omission rather than a deliberate design decision enforced elsewhere in the codebase.

## Impact Explanation
An unauthenticated/unprivileged caller of the gateway's public HTTP JSON-RPC endpoint can cause cross-user response confusion: by submitting a `web_api_trigger` request with a `MessageID` matching a victim's in-flight request, the attacker's callback overwrites the victim's, causing the DON's eventual response to be delivered to the attacker instead of the victim, and the victim's request to time out (DoS). This maps to the in-scope "cross-user response corruption"/"gateway request impersonation" impact category.

## Likelihood Explanation
Exploitation requires only unprivileged HTTP access to the gateway's public endpoint, knowledge or guessability of the victim's `MessageID`, and timing the second request within the default 120-second callback lifetime (`defaultCallbackMaxAgeSec`). No credentials, node/operator access, or protocol bypass are required, making this readily reachable and repeatable by any external client.

## Recommendation
Mirror the existing protection in `OutgoingConnectorHandler.responses.new(messageID)`: before inserting into `savedCallbacks`, check for an existing entry keyed by `MessageID` and reject the new request if one is found, rather than silently overwriting it. Consider also deriving `MessageID` server-side or scoping it per-connection/per-DON instead of trusting the raw client-supplied JSON-RPC `ID`.

## Proof of Concept
1. Client A sends a `web_api_trigger` legacy gateway request with JSON-RPC `ID = "X"`. The gateway registers A's callback in `savedCallbacks["X"]` and forwards the request to all DON members (`handler.go:411-419`).
2. Before any DON node responds, Client B sends an unrelated `web_api_trigger` request also using `ID = "X"`. The gateway overwrites `savedCallbacks["X"]` with B's callback via the same code path (no duplicate check).
3. A DON node responds with `MethodWebAPITrigger` tagged `MessageID = "X"`. `handleWebAPITriggerMessage` (`handler.go:148-162`) looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers the response to B.
4. Client A's HTTP request times out with no response; Client B receives the DON response data associated with Client A's trigger request. This can be reproduced as a Go unit/integration test against `handler.HandleLegacyUserMessage` and `handleWebAPITriggerMessage` by issuing two concurrent calls with identical `MessageID` values and asserting which callback receives the response.
