## Analysis: CVE-2016-2788 analog in Hyperbridge

CVE-2016-2788 is a critical bug class where an **unauthenticated component that looks like a simple relay/ping utility actually allows execution of attacker-controlled payloads** (arbitrary code execution reachable by any unprivileged network participant, no access control on the dispatch path). The closest reachable analog in this codebase is `CallDispatcher.dispatch()` — a permissionless, unauthenticated arbitrary-call executor shared across every `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` deployment on a chain.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows any account to drain residual balances and plant persistent malicious approvals - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with **no caller restriction whatsoever** — it does not check `msg.sender` against the `HyperFungibleToken`, `WrappedHyperFungibleToken`, or `IntentGatewayV2` contracts that are supposed to be its only legitimate callers. [1](#0-0) 

This single `CallDispatcher` instance is deliberately deployed once per chain via CREATE2 and reused by all integrated apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`), transiently holding tokens/ETH mid-transaction for swap-then-escrow, fill-then-act, and calldata-after-mint patterns. [2](#0-1) [3](#0-2) 

### Finding Description
Any unprivileged EOA can call `CallDispatcher.dispatch()` directly with an arbitrary `Call[]` at any time — it is not gated to the intended callers:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [4](#0-3) 

Because the dispatcher is shared across all bridge/intent apps and holds tokens transiently in normal flows (predispatch/postdispatch swaps, calldata-after-mint), any dust or unswept balance left behind by a legitimate flow becomes drainable by anyone calling `dispatch()` with `Call({to: token, data: transfer(attacker, balance)})`. Worse, an attacker can **pre-emptively** call `dispatch()` to set `approve(attacker, type(uint256).max)` on any token from the `CallDispatcher`'s own context — a standing, cross-transaction approval that persists in dispatcher state regardless of which future transaction populates the dispatcher with that token. The docs explicitly acknowledge unlimited approvals are a real risk pattern used in this flow (e.g. `IERC20.approve(uniswapRouter, type(uint256).max)` in the documented/test calldata), and warn integrators to use exact amounts — but nothing in `CallDispatcher` itself prevents an attacker from installing the same kind of approval in the attacker's own favor first. [5](#0-4) [6](#0-5) 

The intended protection ("if any call fails, the whole `onAccept`/`fillOrder` reverts, so dust doesn't accumulate") only defends the atomic transaction that legitimately uses the dispatcher; it does nothing to stop an attacker from calling `dispatch()` in a completely separate, unrelated transaction to plant approvals or sweep any token/ETH that ends up sitting on the dispatcher (e.g., non-order tokens like referral/reward tokens sent by a predispatch swap that aren't part of the swept `order.inputs`/`order.output.assets` list, or ETH sent via `receive()`). [7](#0-6) 

### Impact Explanation
Any funds or standing approvals that ever reside on the singleton `CallDispatcher` — across every app integrated with it on that chain (HFT, WHFT, IntentGatewayV2, and any future `IApp` reusing the same shared dispatcher) — are permanently theft-able by any unprivileged caller, since `dispatch()` performs the exact "arbitrary call, no auth" primitive that CVE-2016-2788 exploited in `mco ping`. This is a direct path to theft of user/protocol funds without needing any proof, relayer role, or governance privilege.

### Likelihood Explanation
High: `dispatch()` requires zero setup cost or special privilege to call — any address can submit a transaction to it. The only requirement is that the dispatcher at some point holds a balance or that the attacker pre-installs an approval before a balance later appears, both of which are realistic given the documented predispatch/postdispatch/calldata-execution flows that intentionally route funds through this shared, unauthenticated contract.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a known, immutable, or governance-managed allowlist of caller contracts (e.g., `onlyAuthorizedCaller` mapping populated at deployment/governance time), or make the dispatcher single-use/ephemeral per call (e.g., deploy a fresh minimal-proxy dispatcher per transaction) so it never holds standing approvals or balances reachable by third parties between transactions.

### Proof of Concept
1. Attacker observes that `CallDispatcher` at a known CREATE2 address is used by `HyperFungibleToken`/`IntentGatewayV2` deployments on a chain.
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly — this succeeds because `dispatch()` has no caller check. [4](#0-3) 
3. At any later point where a legitimate order/bridge flow causes the dispatcher to (even transiently or via unswept dust) hold USDC, the attacker calls `USDC.transferFrom(dispatcher, attacker, amount)` directly from their own account — draining the balance using the approval planted in step 2, entirely outside of any legitimate transaction's atomic boundary.

**File:** docs/content/developers/evm/hyper-fungible-token/overview.mdx (L88-98)
```text
Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```

    /**
     * @dev Executes arbitrary calldata attached to an order's output via the CallDispatcher.
     * After dispatching the calls, any residual token balances left on the dispatcher
     * are swept back to this contract and accounted for as protocol dust.
     *
     * This enables composable order fulfillment — solvers can route through DEXes,
     * lending protocols, or other DeFi primitives as part of filling an order.
     *
     * @param order The order containing the output calldata to execute.
     * @param outputsLen The number of output assets to sweep after execution.
     */
    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }
