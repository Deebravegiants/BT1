## Analysis: Standing ERC20 approvals via the shared `CallDispatcher`

The Footium bug — an "owner" role granting itself an ERC20 approval on a shared/reused escrow contract, which persists and lets it steal tokens belonging to a *later, unrelated* owner of that same contract — has a direct structural analog in Hyperbridge's `CallDispatcher`.

`CallDispatcher` is a single, contract shared by every order placed through `IntentGatewayV2` (and other apps like `HyperFungibleToken`). It executes caller-supplied `Call[]` arrays via plain `.call` (not `delegatecall`), so any `approve()` issued inside that calldata is a real, persistent ERC20 allowance *from the dispatcher* to whatever spender the caller names [1](#0-0) .

`placeOrder`'s predispatch path moves `order.predispatch.assets` into the dispatcher, runs the attacker/user-supplied `order.predispatch.call`, and only afterward sweeps back the balance of the tokens listed in `order.inputs` [2](#0-1) . Any token that the predispatch call touches but that is *not* one of `order.inputs` (e.g. swap-path leftovers/dust, or reward tokens) is never swept and simply sits on the dispatcher indefinitely. The analogous postdispatch path (`_execute`) only sweeps `order.output.assets` tokens after running `order.output.call` [3](#0-2) .

Because the dispatcher is reused by every subsequent order from every user, an attacker can place one order whose predispatch calldata is simply `tokenX.approve(attacker, type(uint256).max)`. This grants `attacker` a standing allowance from the dispatcher for `tokenX` that never expires and is never revoked by the protocol. Any later, unrelated order (from any other user) whose predispatch/postdispatch execution leaves any balance of `tokenX` stranded on the dispatcher (because `tokenX` isn't in that order's tracked `inputs`/`output.assets` set) can then be drained by the attacker via `tokenX.transferFrom(dispatcher, attacker, amount)`, at any time, in a separate transaction — exactly the "approve now, steal later" pattern from the reported issue, except the "escrow" is the shared `CallDispatcher` and the "owner" is any unprivileged order-placer.

The project's own documentation for the sibling `HyperFungibleToken` app explicitly flags this exact class of risk: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [4](#0-3)  — this is advisory only; nothing in `CallDispatcher` or `IntentGatewayV2` enforces exact-amount approvals or resets/limits allowances the dispatcher grants to third parties.

### Title
Standing ERC20 approvals granted through `CallDispatcher`'s arbitrary calldata let an unprivileged caller steal tokens later routed through the same shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single contract reused across every `IntentGatewayV2` order's predispatch/postdispatch calldata. Because it executes calldata via `.call` (not `delegatecall`), any `approve()` embedded in one user's calldata creates a real, persistent ERC20 allowance from the dispatcher to an attacker-chosen spender. Since `placeOrder`/`fillOrder` only sweep back the specific tokens declared in `order.inputs`/`order.output.assets`, any other token balance left on the dispatcher by a later, unrelated order remains claimable by whoever previously obtained a standing approval.

### Finding Description
`CallDispatcher.dispatch` loops over an attacker/user-controlled `Call[]` and executes each entry with `to.call{value: call.value}(call.data)`, so the dispatcher itself is `msg.sender` for any ERC20 calls inside [1](#0-0) . Anyone can place an order whose `order.predispatch.call` is just `tokenX.approve(attacker, type(uint256).max)`, granting `attacker` an unlimited allowance from the dispatcher for `tokenX`.

`IntentGatewayV2.placeOrder`'s predispatch phase transfers `order.predispatch.assets` to the dispatcher, executes the (arbitrary) predispatch call, and then sweeps back only the balances of the tokens listed in `order.inputs` [2](#0-1) . Any token touched by the predispatch execution that is not part of `order.inputs` (dust from a swap route, reward tokens, partial-consumption leftovers) is never collected and stays on the dispatcher indefinitely. The postdispatch path in `_execute` has the same property with respect to `order.output.assets` [3](#0-2) .

Combining these two facts: an attacker who has pre-armed a standing approval for `tokenX` can later sweep any `tokenX` balance a *different, unrelated* user's order accidentally leaves on the shared dispatcher — with no relationship between the attacker's order and the victim's order other than both routing through the same singleton `CallDispatcher`.

### Impact Explanation
This allows unauthorized, permanent theft of ERC20 tokens that pass through, or are inadvertently stranded on, the shared `CallDispatcher` — funds that belong to unrelated users/orders, not the attacker's own order. Because the approval is a normal ERC20 allowance, it survives indefinitely and is redeemable at any time in the future, matching the "future tokens" theft pattern in the reference report.

### Likelihood Explanation
Reaching this requires only a single, unprivileged `placeOrder` call with attacker-chosen predispatch calldata — no special role, no governance, no relayer/consensus involvement. The likelihood of tokens actually being stranded depends on other orders' predispatch/postdispatch calldata leaving non-`inputs`/non-`output.assets` token residue on the dispatcher (e.g., multi-hop swap dust), which is a realistic and encouraged usage pattern per the documented "swap-then-escrow" and "fill-then-act" calldata features.

### Recommendation
- Reset/limit any allowance the dispatcher grants during a `dispatch()` call before returning control (e.g., force-approve back to zero for any token touched), or disallow `approve`-shaped calls to ERC20 targets entirely from within `CallDispatcher`.
- Sweep the *entire* balance of every token the dispatcher ends a call holding (not just the tokens named in `order.inputs`/`order.output.assets`) back to the gateway or to a designated dust-treasury at the end of each `placeOrder`/`fillOrder` invocation, so no token balance — and no exploitable window — persists across transactions.
- Consider deploying a fresh, ephemeral dispatcher (or a per-order proxy) instead of one long-lived singleton, so no allowance or balance state can carry over between unrelated orders.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.predispatch.call` encoding a single `Call` to `tokenX.approve(attacker, type(uint256).max)` (any minimal, otherwise-valid order). This executes through `CallDispatcher.dispatch`, and since the dispatcher is `msg.sender` of that call, `tokenX.allowance(dispatcher, attacker)` becomes `type(uint256).max` [1](#0-0) .
2. At any later time, an unrelated victim places an order whose `predispatch.call` performs a multi-hop swap that leaves a residual `tokenX` balance on the dispatcher (because `tokenX` is not one of that victim's `order.inputs` tokens, so the sweep in `placeOrder` never collects it) [5](#0-4) .
3. Attacker calls `tokenX.transferFrom(dispatcher, attacker, amount)` using the standing allowance from step 1, draining the victim's stranded funds from the shared dispatcher.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
