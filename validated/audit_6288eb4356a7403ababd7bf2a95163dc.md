### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the *unauthenticated* `shop`, `topic`, `api_version`, and `webhook_id` header values straight to the app's handler as the identity of the tenant/event. This breaks the equality "bytes verified by HMAC == bytes the handler trusts for shop identity."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id`, however, are all parsed directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then immediately trusts these header-derived values, passing `request.shop` as the tenant identity into the handler: [4](#0-3) 

The HMAC (`HmacValidator.validate`) computes `OpenSSL::HMAC.hexdigest(sha256, secret, signable_string)` where `signable_string` is exactly `@raw_body`: [5](#0-4) 

Because the same `api_secret_key` is shared across every shop that installs the app, any legitimately captured `(raw_body, hmac)` pair remains cryptographically valid no matter what `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` headers are attached to it. An attacker who can obtain one valid `(body, hmac)` pair for their own shop (or via network capture) can resend the identical body/hmac to the app's webhook endpoint while substituting a different `shop-domain` header. `Registry.process` will still pass HMAC validation and will invoke the handler with `shop:` set to the attacker-chosen (unverified) value — the equality "shop verified by HMAC" vs "shop used by the handler" does not hold.

### Impact Explanation
If a webhook handler uses `data.shop` to look up/update per-tenant records (a common integration pattern, e.g., syncing order/customer data keyed by shop), an attacker can cause the app to process data for or attribute an action to a different merchant's shop than the one which actually authenticated the request, i.e., cross-tenant confusion/access. This matches the Critical category "cross-tenant access."

### Likelihood Explanation
Medium: the attacker needs at least one valid `(raw_body, hmac)` pair, which is straightforward to obtain by triggering any webhook event on their own installed shop (they own the shop, so they can trigger events at will) and capturing the request the gem would accept. They then only need to replay it with a modified `shop-domain`/`topic`/`webhook_id` header to the exposed webhook endpoint — no possession of `api_secret_key` is required.

### Recommendation
Include `shop`, `topic`, and any other header fields used for routing/tenant identification in the HMAC-signed material (or otherwise cryptographically bind them to the body), or require correlating the `shop` header against an expected/registered shop for that webhook subscription before dispatching to handlers.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` with the target app installed; they trigger a webhook (e.g., `orders/create`) and capture the raw POST body and its `x-shopify-hmac-sha256` header — both are valid because Shopify itself signed them with the shared `api_secret_key`.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or the `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC — header changes are irrelevant to this check.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and describes `attacker-shop.myshopify.com`'s data — the app's handler now processes attacker-controlled data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)

            secret,

          )
        end
