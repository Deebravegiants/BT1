### Title
Missing enforced upper limit on solver payout price allows profit extraction via price manipulation - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
`FXFiller.evaluateOrder` (in `sdk/packages/simplex/src/strategies/fx.ts`) sizes the amount a filler (intent solver) will pay out on `IntentGatewayV2.fillOrder` using `policyMaxOutput`, a value derived from on-chain venue pricing (e.g. a Uniswap V4 pool). The code that used to clamp this payout to a caller-configured ceiling (`maxOverfillBps` above the user-requested amount) has been turned into a warning-only no-op, so there is no enforced upper bound on the amount the solver commits to pay, mirroring exactly the "Lack of user-controlled limits for input amount" pattern in the external report — except here the un-capped party is the solver paying out, not the liquidator's caller.

### Finding Description
The relevant code: [1](#0-0) 

```
// Overfill detection is warn-only: the clamp is DISABLED, so the filler
// fills the full computed amount even when it exceeds
// (1 + maxOverfillBps) × user-requested — including venue-priced legs
// (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that
// previously protected against a bug / stale cache / manipulated venue
// price. Output is no longer capped; we only emit a warning.
const overfillCeiling = (output.amount * (10000n + this.maxOverfillBps)) / 10000n
const policyMaxOutput = rawPolicyMaxOutput
if (rawPolicyMaxOutput > overfillCeiling) {
    this.logger.warn(...)
}
```

and then: [2](#0-1) 

`targetOutput = policyMaxOutput` is used unconditionally as the amount funded and eventually passed as `FillOptions.outputs` to `IntentGatewayV2.fillOrder` on-chain, per the design decision documented explicitly: [3](#0-2) 

The `maxOverfillBps` config knob is advertised to operators as "Bounds per-leg loss when internal pricing is wrong (bug, stale cache, manipulated venue)" and defaults to 5%: [4](#0-3) 

but the enforcement point is dead code — it only logs a warning and never actually reduces `targetOutput`. This is the same root-cause class as the ToB `liquidatePortion` finding: an amount computed from a price oracle/feed at execution time is used without any hard, enforced ceiling that the caller (here, the solver committing capital) can rely on.

### Impact Explanation
For venue-priced legs (Uniswap V4 pool positions used as the FX price source), an attacker can manipulate the pool's spot price immediately before the solver's `UserOperation` lands on-chain (the classic sandwich/price-manipulation setup: swap to move price, wait for the solver's signed bid/UserOp — which is valid until `FillOptions.validUntil` — to execute, then swap back). Because `policyMaxOutput` is derived from that manipulated price and the overfill ceiling is not enforced, the solver can be made to pay out an output amount far above `(1 + maxOverfillBps) × output.amount`, directly transferring solver funds to the attacker/user side of the order with no protocol-level or off-chain-code-level ceiling stopping it. This is a direct, unbounded loss-of-funds vector for the solver operating this filler.

### Likelihood Explanation
Likelihood is elevated relative to the original ToB report because: (1) the protection knob exists in config and is advertised as active but is silently disabled in code (a latent/regression bug), giving operators false confidence; (2) the price source (Uniswap V4 pool) is a venue an outside actor can manipulate within a single block or across the bid-validity window (`bidValiditySeconds`, default 300s / mapped to a block height), which is a realistic and well-known DeFi manipulation primitive; (3) exploitation only requires placing/observing an order that maps to a venue-priced pair and manipulating that venue's price before the signed bid executes.

### Recommendation
Restore the enforcement: clamp `policyMaxOutput` (and thus `targetOutput`) to `overfillCeiling = output.amount * (10000 + maxOverfillBps) / 10000` instead of only logging a warning, i.e. reintroduce `const policyMaxOutput = rawPolicyMaxOutput > overfillCeiling ? overfillCeiling : rawPolicyMaxOutput`. If unclamped overfill is intentionally desired as a competitive feature for offline/curve-priced legs, at minimum re-enable the clamp specifically for on-chain venue-priced legs (e.g. Uniswap V4), where the price is manipulable within the transaction/block window, and restore the `maxConsecutiveClamps` halt behavior (`recordOrderOutcome` is documented as always called with `false`, per the decision doc, meaning the halt subsystem is also dormant).

### Proof of Concept
1. Operator configures a cross-asset pair priced via a Uniswap V4 LP position (`fxPricing` = venue price), with `overfillProtection.maxOverfillBps` left at default (500 = 5%).
2. A user places an order whose leg resolves to this pair.
3. `FXFiller.evaluateOrder` computes `rawPolicyMaxOutput` from the current pool price via `resolveLegRates`/`computeLegPolicyOutput` at `sdk/packages/simplex/src/strategies/fx.ts:622-664`, and this is assigned unclamped to `policyMaxOutput`/`targetOutput` at lines 685 and 736.
4. Immediately before the solver's signed `UserOperation` (bid) executes, an attacker submits a swap against the Uniswap V4 position to move the pool price so that the true output value implied by the new price is, e.g., 50% above `output.amount` — far beyond the configured `500 bps` ceiling.
5. Because the clamp is a no-op (`const policyMaxOutput = rawPolicyMaxOutput`), the fill proceeds with the inflated `targetOutput`, and the solver's UserOp transfers the inflated amount via `fillOrder`, realizing an immediate loss equal to the price manipulation delta, with only a warning log recorded and no halt triggered.

the rate is applied, which is where the exposure actually is: a capped leg never pays out more than
