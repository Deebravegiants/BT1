### Title
Webhook HMAC only covers the request body, not the `shop-domain` header - allows cross-tenant webhook shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop` (from the `X-Shopify-Shop-Domain` header) that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the app's webhook handler is never part of the signed data. An attacker who can obtain one validly-signed webhook payload (e.g. by installing the app on their own shop and receiving a real webhook) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header, and the signature check still passes.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The equality the gem is implicitly relying on is:

`shop bound by HMAC == shop delivered to handler`

but in reality:

`shop bound by HMAC (∅, not signed) != shop delivered to handler (attacker-controlled header)`

Because `Utils::HmacValidator.validate` (shared with OAuth) only ever checks `verifiable_query.to_signable_string` against the secret, and for `Request` that string is exclusively `@raw_body`: [4](#0-3) 

any HTTP header, including `shop-domain`, `topic`, `webhook-id`, and `api-version`, can be freely modified by an attacker without invalidating the signature, as long as the body bytes and their HMAC remain paired as originally issued by Shopify.

### Impact Explanation
An app that installs this library and serves multiple shops uses `request.shop` (surfaced via `WebhookMetadata#shop`) to determine which tenant's data/session the webhook body applies to (e.g. to look up that shop's session/access token or to key stored data). Since the shop identity is not bound by the signature, an attacker who legitimately receives one signed webhook (by installing the app on a shop they control) can resend the identical body+signature pair while swapping the `shop-domain` header to point at a victim shop. The app will process attacker-supplied body content as if it came from the victim tenant — a cross-tenant data-integrity/impersonation issue, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint plus one legitimately obtained (topic, body, HMAC) triple from any shop that has installed the app — something any unprivileged internet user can obtain by installing a public app on their own free development store and capturing its own inbound webhook. No access token, `client_secret`, or privileged credential is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified for webhooks, or have `Registry.process` cross-check `request.shop` against an expected/allow-listed value tied to the delivery context before trusting it. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a tenant-identifying value without independent verification (e.g. matching against the shop stored for the session/webhook subscription being processed).

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Resend the exact same request to the app's webhook endpoint, unchanged body `B` and `H`, but replace the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` (see `to_signable_string`), regardless of the `shop-domain` header value: [3](#0-2) 
4. `Registry.process` calls the app's handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, causing the host application to process/store data under, or act on behalf of, the victim tenant.
