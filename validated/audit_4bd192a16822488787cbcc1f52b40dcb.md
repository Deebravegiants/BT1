Audit Report

## Title
Broad Role Disclosure of External Initiator Outgoing Webhook Credentials to Low-Privilege "view" Users - ([File: core/web/external_initiators_controller.go])

## Summary
`GET /v2/external_initiators` is registered with only generic authentication (no role wrapper), so any authenticated user with the lowest role (`view`) can list every configured external initiator, and the response includes the plaintext `OutgoingToken` secret for each one. This is inconsistent with `Create`/`Destroy` on the same resource, which require `edit`, creating a privilege-boundary mismatch where a weaker role can read a credential that only a stronger role is trusted to manage.

## Finding Description
The route registration confirms no role restriction is applied to the index endpoint, unlike its sibling write routes: [1](#0-0) 

`Index` fetches all `ExternalInitiator` rows from the ORM with no per-user scoping (external initiators are node-wide) and maps every row through `NewExternalInitiatorResource`, which includes `OutgoingToken`: [2](#0-1) [3](#0-2) 

`OutgoingToken` is a raw, unhashed secret (`utils.NewSecret`), stored in plaintext in the `external_initiators.outgoing_token` column, generated alongside `OutgoingSecret` at creation time: [4](#0-3) [5](#0-4) 

The RBAC test matrix explicitly documents and locks in `viewOnlyAllowed: true` for this exact route, confirming the behavior is intentional/tested current design rather than an accidental oversight: [6](#0-5) 

By contrast, `Create` and `Destroy` on the same resource require `edit`: [7](#0-6) 

This is a genuine, root-cause-identifiable inconsistency: a role weaker than the one required to create/rotate a secret can read that same secret indefinitely, with test-suite assertions confirming it as designed, reachable behavior on this fork.

However, I was unable to find, anywhere in the indexed codebase (including `core/services/webhook`, which does not exist as a directory here, and no `Authorization`/`Bearer` usage tied to `OutgoingToken`/`OutgoingSecret`), any code path that actually consumes `OutgoingToken`/`OutgoingSecret` as a bearer credential when calling back to an external initiator's registered `URL`. The only authentication code found for external initiators (`AuthenticateExternalInitiator`) uses the **inbound** `AccessKey`/`Secret` pair to authenticate *incoming* run-trigger requests from the initiator, not the outgoing pair: [8](#0-7) 

Additionally, the config documentation in this codebase marks the whole feature as legacy/vestigial: `ExternalInitiatorsEnabled` is annotated "Unused: used to enable the External Initiator feature for legacy webhook job runs via external initiators," suggesting the outbound-notification mechanism this token would protect may no longer be implemented or actively exercised in this version.

## Impact Explanation
If `OutgoingToken` were used as a bearer/authentication credential for outbound calls to an external initiator's endpoint, disclosure to a `view`-role user would allow that user to impersonate the node toward the initiator — a legitimate secret-exfiltration concern. This part of the claim is architecturally sound (the RBAC gap is real and confirmed by code and by test), but the report itself, and my own search, could not locate the runtime code path that actually uses `OutgoingToken`/`OutgoingSecret` as a credential in this codebase; no outbound HTTP call using these fields was found. Without confirming that this token is actually used as a live credential anywhere reachable in this fork, the concrete impact (impersonation of the node to an external system) remains unverified rather than demonstrated. It is also possible this functionality was removed/never fully ported in this fork, in which case the field is dead data with reduced practical exploit value beyond generic secret-hygiene concerns.

## Likelihood Explanation
Reachability is high and trivially exploitable by any `view`-role authenticated user via a single GET request, and this is corroborated by the codebase's own RBAC test suite treating it as expected/passing behavior — i.e., it is an intentional, already-tested design decision rather than an unnoticed bug, which weighs against this being an actionable, undisclosed vulnerability for a bounty submission.

## Recommendation
Regardless of confirmed runtime usage, since `OutgoingToken` is a persisted secret value, restrict `GET /v2/external_initiators` to at least `edit` role (matching `Create`/`Destroy`), or strip `OutgoingToken` from the `view`-accessible response and only return credential fields to `edit`/`admin` roles.

## Proof of Concept
1. As an `edit`/`admin` user, `POST /v2/external_initiators` with a name/URL to create an external initiator (generates `OutgoingToken`).
2. Create a second user with role `view`.
3. As the `view` user, call `GET /v2/external_initiators`.
4. Observe `outgoingToken` populated in the JSON response for the initiator created in step 1, as asserted in the existing test: [9](#0-8) 

This confirms the RBAC gap on disclosure of the `OutgoingToken` field, though the concrete downstream exploitability (using this token to impersonate the node against an external system) could not be confirmed in this codebase's indexed contents.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
```
