This confirms the documented contract: the gem explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md line 125) and that `data.shop` is "The shop domain of the webhook" (docs/usage/webhooks.md line 14) — an authoritative tenant identifier the host app is told it can trust after `process` succeeds. But the verification only covers the raw body.

### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which HMAC-signs only the raw request body. The `shop` value that is then handed to the app's `WebhookHandler` as the trusted tenant identifier comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is entirely outside the HMAC's signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#hmac` is derived purely from the `hmac-sha256` header [2](#0-1) . The `shop` accessor used downstream is read straight from the `shop-domain` header with no cryptographic binding to the signed body at all [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed into the app's handler: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) . `HmacValidator.validate` compares `compute_signature(verifiable_query.to_signable_string, secret)` against the header HMAC using `OpenSSL.secure_compare` [5](#0-4) ; since `to_signable_string` is only the body, the `shop-domain` header can be swapped to any value and the signature check still passes.

The binding that is broken, expressed as an equality that should hold but does not:
`shop authenticated by HMAC` ≠ `shop used as WebhookMetadata#shop (session/tenant key passed to handler)`.

Concretely: a party who controls (or has legitimate access to) one Shopify store with the app installed will, in the normal course of using the app, receive a genuinely-signed webhook delivery (valid `hmac-sha256` header + body) for their own shop. Because the HMAC never covers the `shop-domain` header, that same body+HMAC pair can be resent to the app's public webhook endpoint with the `shop-domain` header rewritten to any other installed shop domain. `HmacValidator.validate` still succeeds (it only checks the body against the secret), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, even though the payload was never produced by or for that shop.

### Impact Explanation
This is a cross-tenant boundary violation: the gem's own documentation instructs host apps that `process` "will verify the request did indeed come from Shopify" [6](#0-5)  and that `data.shop` is the (implicitly trustworthy) "shop domain of the webhook" [7](#0-6) . Handlers built on this API (as shown in the gem's own example, which uses `data.shop` directly to key work such as `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process forged data under an arbitrary victim shop's identity, without possessing that shop's installation, its access token, or the app's `client_secret`. This satisfies the "cross-tenant access" impact bar: an attacker who is merely a normal, unprivileged installer of the app on their own store can inject fabricated webhook events attributed to any other merchant of the same app.

### Likelihood Explanation
The only prerequisite is that the attacker's own shop has the app installed and subscribed to at least one webhook topic — a standard, unprivileged capability of any merchant. No access token, `api_secret_key`, or victim credentials are required; the attacker only needs to capture one legitimately delivered `(raw_body, hmac header)` pair from their own installation (trivially done by controlling the endpoint that receives it, or via a proxy they operate) and replay it with a different `shop-domain` header value to the target app's public webhook URL.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed payload verification, e.g. include the `shop-domain` header in `to_signable_string`, or independently verify that the shop asserted in the header corresponds to a shop for which this app has an active installation/session, before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Attacker triggers the event in their own store; Shopify delivers a webhook to the app with headers including a valid `x-shopify-hmac-sha256` and `x-shopify-shop-domain: attacker.myshopify.com`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (they control the receiving endpoint or a proxy in front of it).
4. Attacker sends a new POST to the app's public webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but with `x-shopify-shop-domain: victim.myshopify.com` (a shop known to have the app installed).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and it matches, so validation succeeds [8](#0-7) .
6. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [9](#0-8) , causing the app to process attacker-controlled data as if it originated from the victim shop.
