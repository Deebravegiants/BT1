### Title
Controller teardown/liquidation paths unconditionally dereference position‑NFT state that may be absent, permanently bricking a live account - (File: contracts/controller/src/storage/account.rs)

### Summary
The kernel bug class is "uninit/teardown dereferences a resource that init never completed" (`hw_intr == NULL`). The analog in this codebase: every account-resolving and account-removing path in the controller dereferences position‑NFT state (`account_owner` / `nft_burn_call`) while holding the invariant "live `AccountMeta` ⇒ live NFT". That invariant can be broken from outside the controller — the position‑NFT contract has its own storage/TTL lifecycle and its own `burn` entrypoint — so the NFT half can be missing while the controller account and its positions remain live. Once the NFT entry is gone, every flow that resolves ownership or removes the account (`withdraw`, `repay` as owner, `liquidate`, `clean_bad_debt`, `force_socialize_bad_debt`, `update_account_threshold`) reverts with `AccountNotFound`, leaving the account's collateral and debt permanently stranded.

### Finding Description
`remove_account_and_burn_nft` deletes the controller entries and then unconditionally calls `nft_burn_call` (`contracts/controller/src/account.rs:159-163`). `require_account_owner` and `get_account` resolve ownership through `storage::account_owner`, which reads the NFT contract (`account.rs:143-148`). The documented model confirms the NFT side is not renewed or proven by `account_exists` — the skill doc states `account_exists` "does not renew or prove the existence of ... NFT entries" (`skills/xoxno-lending-contracts/positions.md:11-13`), and the runbook admits "Ownership lookup and NFT burn both require readable NFT state" (`docs/reference/runbooks/force-socialize-bad-debt.md:39`).

The test `bad_debt_winddown_resolves_nft_ownership` demonstrates the broken state directly: it burns the position NFT while controller state stays live (`account_exists(id) == true`), after which both `clean_bad_debt` and `force_socialize_bad_debt` revert `AccountNotFound` (`tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:313-334`). There is no "null-guard" analog of the kernel fix anywhere in this direction: the code treats the NFT as always present for a live account instead of tolerating its absence on teardown, and `renew_user_account` renews only controller keys, never the NFT (`contracts/controller/src/storage/account.rs:259-272`).

### Impact Explanation
Once the NFT entry is absent (owner-initiated `burn` where the NFT contract permits holder burn, or persistent-entry archival of NFT state that nothing in the controller renews), the account becomes permanently ungovernable:

- Owner cannot `withdraw`, `repay`, `flash_position`, or transfer the account — every path reverts on the owner check.
- Liquidators cannot `liquidate`; `clean_bad_debt` fails; even the governance backstop `force_socialize_bad_debt` fails (`get_account` → `AccountNotFound`), per the cited test.
- Collateral is permanently frozen and the debt becomes unsocializable bad debt — the write-down machinery in `execute_bad_debt_cleanup` (`positions/liquidation/bad_debt.rs:14-61`) is unreachable, so the backing shortfall can never be booked, satisfying "permanent freezing of funds" and "protocol insolvency."

### Likelihood Explanation
Reachability depends on the position‑NFT contract's `burn` authorization (holder-burnable vs. controller-only), which I could not fully confirm within the iteration budget; the test invokes `PositionNftClient::burn` under `mock_all_auths` so it does not establish the auth model. Even if burn is controller-restricted, the same state is reachable non-maliciously through TTL archival of NFT entries — the codebase itself flags NFT state as independently expiring (runbook step 5; `positions.md` lifecycle note) — in which case the freeze lasts until the archived entry is restored, still satisfying "temporary freezing of funds" with zero attacker cost beyond letting TTL lapse on an underwater account the owner has no incentive to maintain. Severity: Medium.

### Recommendation
Mirror the kernel fix — guard the teardown on the possibly-absent resource:

1. In `remove_account_and_burn_nft`, only call `nft_burn_call` when the NFT token actually exists (a `try_owner_of`/`has` check), so a missing NFT does not abort account cleanup.
2. Make `account_owner` distinguish "NFT missing" from "wrong owner" and let cleanup paths (`execute_bad_debt_cleanup`, `cleanup_account_if_empty`) proceed on an explicit "NFT already gone" result instead of panicking.
3. Extend `renew_user_account` (or a dedicated keeper path) to renew the NFT token entry, closing the TTL-asymmetry that lets the NFT half disappear while `AccountMeta` stays live.

### Proof of Concept
1. Alice opens an account via `supply` (mints position NFT `id`) and `borrow`s against it.
2. The position NFT's persistent entry becomes unreadable — either Alice calls `burn` on the position‑NFT contract (if holder-authorized) or the entry archives via TTL, which nothing in `renew_user_account` or `account_exists` renews (`storage/account.rs:259-272`, `positions.md:11-13`). `account_exists(id)` still returns `true` because only `AccountMeta` is checked.
3. Collateral price crashes below the bad-debt threshold. Any liquidator calling `liquidate`, or any keeper calling `clean_bad_debt`, reverts with `AccountNotFound` inside `account_owner`; governance's `force_socialize_bad_debt` reverts identically — exactly the trace in `bad_debt_winddown_resolves_nft_ownership`.
4. Result: the collateral is frozen forever and the debt can never be socialized — the uninit path dereferenced `hw_intr` (the NFT) unconditionally, and the write-down/cleanup machinery is unreachable.

Note: this conclusion is based on indexed code; the position‑NFT `burn` authorization model could not be fully verified, which determines whether the missing-NFT state is attacker-triggerable or only TTL-reachable (permanent vs. temporary freeze).
