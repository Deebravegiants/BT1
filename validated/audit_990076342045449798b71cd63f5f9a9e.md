### Title
Face-detection identity check performed once at start of biometric capture is never re-validated against the actual frames selected for enrollment - ([File: src/plans/biometric_capture/mod.rs])

### Summary
The Orb's signup flow validates that "a face" is present via a single `detect_face` check before starting the multi-second biometric capture loop [1](#0-0) . The actual frames that end up enrolled (left iris, right iris, and the self-custody face candidate) are chosen later, independently, by a continuous best-score replacement process that runs across the whole capture session [2](#0-1) . Nothing re-verifies, at the end of capture, that the final winning frames correspond to the same person who passed the initial `detect_face` check. This is the same bug class as the report: an invariant ("this position/identity is valid") is checked once, up front, against expected/initial state, but the actual outcome is determined by a later, independent selection/matching process whose final result is never re-checked against that invariant.

### Finding Description
`detect_face` runs once, gating entry into the capture loop [3](#0-2) [4](#0-3) . After that single check passes, `biometric_capture::Plan::run` iterates over `objectives` (left-eye captures at several IR wavelengths, then right-eye captures) for the duration of the whole session [5](#0-4) [6](#0-5) .

During this loop:
- `left_ir`/`right_ir`/`left_rgb`/`right_rgb` slots are populated independently per objective, purely based on IR sharpness/score thresholds and side-matching, with no cross-check against the face that was originally detected [7](#0-6) .
- `self_custody_candidate_rgb` (the face frame that becomes the enrolled face identity) is continuously overwritten whenever a higher-scoring frame arrives, across the entire session, again with no continuity/identity check against the originally detected face [2](#0-1) .

The `run_check` function that decides when capture is "complete" only checks that both eyes' objectives have been achieved (`set_next_objective`) - it does not re-validate that the resulting `Capture` (left eye, right eye, self-custody face) is internally consistent with one identity [8](#0-7) . The resulting `Capture` is then passed straight into the biometric pipeline and enrollment with no further identity-consistency check [9](#0-8) . Downstream, `detect_fraud` in this build is fully neutralized (`// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`) [10](#0-9) , so no later stage compensates for this gap either.

This mirrors the reported bug precisely: the "small position" check in `ExitShortFacet` was only evaluated against the expected/requested `buyBackAmount`, not against the actual amount left after matching, letting an attacker exploit the divergence between what was validated and what actually happened. Here, the "face is present" check is only evaluated once at session start, not against the actual frames that are eventually selected by the continuous best-score replacement mechanism running for the rest of the session, letting the divergence between the initially validated identity and the finally selected identity go unchecked.

### Impact Explanation
Because the "best-score wins" frame-selection mechanism has no continuity constraint, a second person present during capture (deliberately, e.g., swapping in front of the Orb mid-session, or simply an occlusion/pass-by event with a higher instantaneous score) can have their eye/face frames overwrite the originally detected user's frames. The single up-front `detect_face` check gives false assurance that the enrolled biometric package corresponds to one physical individual, when the actual enrolled left iris, right iris, and self-custody face frame can be drawn from different points in time and, potentially, different individuals. This is a concrete identity-binding/cross-signup integrity break: the signup session's `user_id`/QR code binding (established at QR-scan time) can end up associated with biometric material that does not consistently correspond to the person who was originally validated, undermining the core "one iris code == one enrolled identity" guarantee the system is built to enforce.

### Likelihood Explanation
The precondition (a second face/eye appearing briefly in front of the Orb during the multi-second, multi-objective capture window, or coordinated behavior by an unprivileged user and an accomplice) is realistic and requires no privileged access - it is exactly the kind of "malicious normal user abusing valid product flow" scenario in scope. The capture loop explicitly runs for multiple seconds across several IR wavelengths and both eyes plus continuous RGB scoring, giving a wide window for such interference, and there is no code path that re-validates the final `Capture`'s cross-frame identity consistency before it flows into enrollment.

### Recommendation
Add an explicit identity-continuity check after the capture loop completes (in `run_check`/`run_post`/`into_capture` in `src/plans/biometric_capture/mod.rs`) that compares the finally selected `left_ir`/`right_ir`/`self_custody_candidate_rgb` frames (e.g., via face-embedding similarity, bounding-box/landmark continuity, or timestamp-window constraints) to ensure they all correspond to the same physical individual detected at capture start, and fail/retry the signup if that invariant does not hold - rather than relying solely on the one-time `detect_face` check performed before the loop begins.

### Proof of Concept
1. Start a signup; `detect_face` succeeds for user A, `biometric_capture::Plan::run_pre`/loop begins.
2. During the left-eye objective phase, user A's left iris scores above `IRIS_SCORE_MIN` and is captured into `left_ir`/`left_rgb`.
3. Shortly after, user B leans into frame with a higher-scoring right eye/face; `handle_ir_net`/`handle_rgb_net`/`handle_face_identifier` overwrite `right_ir`, `right_rgb`, and `self_custody_candidate_rgb` with user B's data because the code only compares scores, not identity continuity [11](#0-10) [12](#0-11) .
4. `run_check` returns `true` once both eye-objectives are satisfied, regardless of whose eye satisfied which side [13](#0-12) .
5. The resulting `Capture` (mixed identity) proceeds to the biometric pipeline and enrollment with no fraud check blocking it in this build [14](#0-13) , producing a signup enrolled under user A's QR-bound session but containing biometric material from two different people.

**Note on uncertainty**: I was unable to fully inspect `into_capture()` and `set_next_objective()` (both located in `src/plans/biometric_capture/mod.rs` but truncated by index size limits) to confirm there is absolutely no hidden identity-continuity check inside them. If a Devin session with full file access is available, I'd recommend reading those two functions in full to confirm this gap before treating the finding as fully confirmed.

    fn handle_ir_net(
        &mut self,
        orb: &mut Orb,
        output: port::Output<ir_net::Model>,
        frame: Option<camera::ir::Frame>,
    ) -> Result<BrokerFlow> {
        match output.value {
            ir_net::Output::Estimate(estimate) => {
                self.update_occlusion(orb, &estimate);
                if let Some(perceived_side) = estimate.perceived_side {
                    if perceived_side != i32::from(!self.target_left_eye) {
                        tracing::debug!("Skipping frame due to target and perceived side mismatch");
                        return Ok(BrokerFlow::Continue);
                    }
                } else {
                    tracing::debug!("IRNet perceived_side=None, skipping frame");
                    return Ok(BrokerFlow::Continue);
                }

                self.update_ux(orb, estimate.sharpness);

                let frame = frame.expect("frame must be set for an estimate output");
                let valid_capture = estimate.score >= IRIS_SCORE_MIN
                    && (!orb.ir_auto_exposure.is_enabled()
                        || IRIS_BRIGHTNESS_RANGE.contains(&frame.mean()))
                    && self.valid_capture_after <= Instant::now();

                if valid_capture {
                    let slot =
                        if self.target_left_eye { &mut self.left_ir } else { &mut self.right_ir };
                    if slot.is_none() {
                        dd_incr!(
                            "main.count.signup.during.biometric_capture.\
                             first_side_sharp_iris_detected",
                            &format!(
                                "side:{}",
                                if self.target_left_eye { "left" } else { "right" }
                            )
                        );
                    }
                    tracing::debug!("Found sharp iris: {}", estimate.score);
                    *slot = Some(FrameInfoIr::new(estimate, frame));
                }
            }
            ir_net::Output::Version(_) => {}
            ir_net::Output::Error => {
                tracing::error!("IR-Net failed during biometric capture phase");
            }
            ir_net::Output::Warmup => unreachable!("IR-Net::Warmup not part biometric capture"),
        }
        Ok(BrokerFlow::Continue)
    }
