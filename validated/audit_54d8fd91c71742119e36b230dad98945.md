This confirms the vulnerability: the gem's documentation explicitly instructs developers to use `data.shop` as the tenant identifier (`shop_domain: data.shop`) for downstream job dispatch, while the `Request#to_signable_string` only signs `@raw_body`, never the `shop-domain` header.

### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `to_signable_string` — the data that `Utils::HmacValidator` actually verifies — only returns `@raw_body`. The tenant-identifying `shop` field is never part of the HMAC-protected payload, so verifying the HMAC proves nothing about which shop the body belongs to.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares its HMAC-SHA256 against the `hmac` header: [1](#0-0) 

`to_signable_string` is defined to return only the raw JSON body: [2](#0-1) 

Meanwhile `shop` is read straight from an untrusted header with no cross-check against the signed content: [3](#0-2) 

The identity binding the gem should enforce is: `shop-domain header == shop that produced/authorized raw_body+hmac`. Because `shop-domain` is excluded from `to_signable_string`, that equality is never checked. `Registry.process` then forwards the *unverified* shop value directly into `WebhookMetadata`, which is exactly what the host app is documented to use as the tenant key: [4](#0-3) [5](#0-4) 

Any party that can obtain one validly-HMAC-signed `(raw_body, hmac)` pair for their **own** shop — e.g., a merchant/developer who installs the same app on their own store and captures a real webhook delivery — can replay that exact body/HMAC pair to the victim app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value for a different shop. `Utils::HmacValidator.validate` still passes because it only checks the body, and the host application (following this gem's own documented usage pattern) will process/enqueue that body under the attacker-chosen shop.

### Impact Explanation
This breaks the tenant/session boundary that the "shop" identity is supposed to enforce, i.e., cross-tenant data injection: an attacker-controlled webhook body (with valid HMAC from their own store) can be attributed to and processed under a different, victim shop's identity by any app that follows this gem's documented pattern of trusting `WebhookMetadata#shop`. Depending on what host apps do with that shop-scoped data (e.g., updating per-shop records, triggering per-shop side effects), this can lead to cross-tenant data corruption or injection — matching the Critical "cross-tenant access" impact category, since it originates purely from a signature/identity-binding gap in this gem's own webhook verification code, not from host-app misuse of an undocumented API.

### Likelihood Explanation
Likelihood is bounded by needing at least one legitimately-signed `(raw_body, hmac)` pair, but the gem's own threat model (a single shared `api_secret_key` across all shops using the app, per `HmacValidator.validate`) makes this trivial to obtain: any unprivileged merchant/developer who installs the target app on their own shop receives Shopify webhooks validly signed with that same `api_secret_key`. They can then replay the captured body+HMAC to the app's public webhook endpoint with a forged `shop-domain` header pointing at any other installed shop, since nothing in `Request`/`HmacValidator`/`Registry.process` binds the header to the signature.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed/verified content, or otherwise cryptographically bind them to the HMAC check — e.g., verify `shop` against a value derived from a per-shop secret/session lookup rather than trusting the header outright. At minimum, `Utils::HmacValidator` should be extended so `VerifiableQuery#to_signable_string` for webhook requests incorporates the shop-domain header, and `Registry.process` should reject requests where the header-derived shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev/test store (`attacker.myshopify.com`) and subscribes to a webhook topic the app handles (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker (or anyone, since no further secret is needed) sends a new HTTP POST to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC), `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, and the host app processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
