### Title
Stateless Emporium calls credit external protocol positions/rewards to the shared `EmporiumUpgradeable` contract instead of the individual user, allowing reward/position theft between users - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` executes user-supplied external calls either through a per-user `HinkalWallet` (Case 1, `invokeWallet == true`) or directly from the shared `EmporiumUpgradeable` singleton itself (Case 2, `invokeWallet == false`, plain `op.endpoint.call{value: op.value}(op.callData)`). [1](#0-0)  In Case 2 the external protocol sees `msg.sender == EmporiumUpgradeable`, which is a single contract shared by every Hinkal user routing through Emporium — exactly the pattern described in the report where `ConvexStakingWrapper`/`StakingRewards` call `masterChef.deposit()`/`withdraw()` using their own address instead of the actual depositor.

### Finding Description
Any external protocol integration that keeps its own per-depositor accounting (a staking pool, a lending market, a rewards-accruing vault, etc.) keyed by `msg.sender` will record all Case-2 Emporium interactions under the single `EmporiumUpgradeable` address, not under the individual Hinkal user who authorized the operation via `emporiumMessage`/signature. [2](#0-1) 

Hinkal's own balance-diff/UTXO equation in `Hinkal.sol` correctly captures the *immediate* ERC20 balance delta of the `EmporiumUpgradeable` contract around the call and mints/burns the correct amount of UTXO value for the calling user for that single transaction. [3](#0-2)  However, that equation only sees the token balance change *of this one call*; it has no visibility into off-chain, protocol-internal state such as an accrued-but-unclaimed reward balance or a staked position that persists at the external protocol keyed to `address(EmporiumUpgradeable)`.

Concretely:
1. User A stakes 1,000,000 tokens into an external `StakingRewards`-like contract by having Emporium call `stake(1000000)` in Case-2 mode. The external contract's internal ledger now shows `balanceOf(EmporiumUpgradeable) == 1,000,000`, not `balanceOf(userA)`.
2. Rewards accrue against `EmporiumUpgradeable`'s pooled position over time.
3. User B later triggers, via Emporium, any call on that same external contract that has a side effect of paying out/claiming rewards (e.g. `withdraw()`, `getReward()`, or `exit()`), even for a token amount B did not stake. Because the reward-accrual state is attributed to `EmporiumUpgradeable` as a whole rather than to individual Hinkal users, B's Case-2 call captures Emporium's entire pooled reward/position balance change and B's resulting `handleOut` UTXO absorbs value that rightfully belonged to A. [4](#0-3) 

The `CircomData`/signature scheme (`emporiumMessage`, `_hashEmporiumOps`, EIP-712 signature) only authenticates *which calls a given user asked Emporium to make*; it says nothing about, and cannot constrain, how a third-party external protocol attributes ongoing balances/rewards to the caller address. Since `EmporiumUpgradeable` is one shared address for all users, the accounting equality "external-protocol position of user X" == "external-protocol position attributed to `EmporiumUpgradeable`" is broken as soon as more than one user routes stateful positions through Case-2 calls.

### Impact Explanation
This is a "value moved by an external action but not counted in the balance equation" class issue. It allows theft of protocol/user funds: whichever user happens to trigger a payout-producing call on the externally-staked/pooled position captures value (staked principal or accrued rewards) that was contributed by other Hinkal users through the same Emporium contract. Depending on which external protocol is targeted this can mean loss of another user's rewards or even their staked principal, satisfying the High/Critical impact bar (theft of user funds / unauthorized asset movement a wallet owner never authorized for that reward/position).

### Likelihood Explanation
Likelihood depends on Emporium being used to call external protocols that keep `msg.sender`-keyed cumulative state (staking/rewards contracts, some lending markets) in Case-2 (`invokeWallet == false`) mode. Case 1 (`invokeWallet == true`) routes calls through a per-user `HinkalWallet`, so `msg.sender` at the external protocol is the user's own wallet and this issue does not apply there. [5](#0-4)  Because `EmporiumStack.ops[i].invokeWallet` is a value the caller (or the off-chain circuit-builder) chooses per operation, and nothing on-chain forces stateful, position-bearing calls to always go through the wallet path, an attacker or even an innocuous non-malicious relay/UI misconfiguration could route a staking-type call through Case 2 and open the door to this cross-user leakage.

### Recommendation
Force any operation whose target contract maintains its own per-caller state (stake positions, reward balances, etc.) to be executed through the caller's dedicated `HinkalWallet` (Case 1) rather than directly from the shared `EmporiumUpgradeable` address. Concretely: either (a) require `invokeWallet == true` whenever `stack.signerAddress != address(0)` for all ops (removing the Case-2 branch's ability to run against protocols with persistent state), or (b) explicitly document/allow-list which `endpoint`s are safe for stateless (Case-2) execution, restricting them to protocols with no persistent per-caller balance. Additionally consider disallowing selectors known to be "claim/reward/deposit/withdraw"-style state-mutating calls in Case 2, mirroring the existing selector-based restriction already applied to `callHinkalWallet`/`doSendToRelay`. [6](#0-5) 

### Proof of Concept
1. Deploy a toy `StakingRewards`-like contract that tracks `balanceOf[msg.sender]` and pays out accrued rewards to `msg.sender` on `withdraw()`/`getReward()`.
2. User A submits an Emporium operation with `invokeWallet = false` and `callData = stake(1_000_000)` on the toy contract, routed through `EmporiumUpgradeable.runAction` (Case 2 branch). The toy contract now shows `balanceOf[EmporiumUpgradeable] == 1_000_000`.
3. Time passes; rewards accrue to `EmporiumUpgradeable`'s position in the toy contract.
4. User B, who staked nothing (or staked a trivial amount) through the same Emporium contract, submits an Emporium operation with `invokeWallet = false` and `callData = getReward()` (or `withdraw(...)` with auto-claim) on the toy contract.
5. The toy contract pays out all accrued rewards to `msg.sender == EmporiumUpgradeable`; `EmporiumUpgradeable.handleOut()` then attributes the resulting balance increase to User B's UTXO output, because from Hinkal's perspective the balance change happened during B's transaction. [4](#0-3) 
6. User A's rewards (and, depending on the external contract's withdraw semantics, potentially staked principal) are stolen by User B, exactly mirroring the ConvexStakingWrapper/StakingRewards → MasterChef issue in the referenced report.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
