### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given shop as soon as `Utils::HmacValidator.validate` succeeds. However, the HMAC is computed only over the raw request body; the `shop`, `topic`, and `webhook_id` values used to build the `WebhookMetadata` passed to the app's handler come from HTTP headers that are entirely outside the signed data.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares an HMAC-SHA256 over that string against the `hmac` field [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, and `webhook_id` are read directly from the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` only checks the HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` delivered to the app's handler as the tenant/topic context: [4](#0-3) 

Because a Shopify app's webhook signing secret (`api_secret_key`/`client_secret`) is shared across every shop that installs the app — not scoped per-shop — any unprivileged internet user can install the target app on their own (attacker-controlled) development store, trigger any webhook topic they choose on that store, and capture a legitimately-signed `(raw_body, hmac)` pair straight from Shopify. Because `shop-domain`, `topic`, and `webhook-id` are not part of the signed payload, the attacker can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`). `HmacValidator.validate` still succeeds because it only checks the untouched raw body, and `Registry.process` hands the forged `shop` value straight to the handler as if it were an authenticated statement from Shopify about the victim shop.

This breaks the identity binding that `Registry.process` implicitly assumes: `shop_that_produced_a_valid_hmac == shop_asserted_in_the_shop-domain_header`. In reality the equality only holds for `secret_used_to_sign == app_client_secret`, which is common to all installs, not per-tenant.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (or `#webhook_id`/`#topic`) to select which merchant's records to create/update/delete, or to short-circuit further authorization, is vulnerable to cross-tenant data corruption/disclosure: an attacker-controlled shop can impersonate any other shop's webhook traffic without ever obtaining that victim's credentials. This matches the Critical "cross-tenant access" impact category, since one tenant (the attacker's own store) can inject data attributed to another tenant purely through this gem's webhook processing primitive.

### Likelihood Explanation
Likelihood is high for any app that lets outside parties install it (the normal Shopify app-store distribution model): installing the app on a free/dev store is trivial for any internet user, capturing a self-triggered, validly-signed webhook body+HMAC requires no special access, and replaying it with a modified header against a public webhook endpoint is a simple HTTP request.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material verified by `Registry.process` where possible, or, at minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated header values and that consuming applications must independently verify the shop is a legitimate, currently-installed tenant (e.g., cross-check against a stored, per-shop webhook subscription/`webhook_id` mapping) before trusting them for tenant-scoped operations. Consider exposing a stricter `process` variant that requires the caller to supply the expected shop/topic and rejects mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook, e.g. `orders/create`.
2. Attacker triggers an order on their own store; Shopify sends a webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` (they own the receiving endpoint/logs for their own store's webhook, or intercepts their own traffic).
4. Attacker sends a POST to the same app's webhook endpoint with:
   - body `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid since body unchanged)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only recomputes HMAC over `raw_body` [5](#0-4) .
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., webhook_id: ...)` [6](#0-5) , and any app logic keyed on `data.shop` now acts as though this event legitimately originated from `victim-shop.myshopify.com`.
