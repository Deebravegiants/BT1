## Analog Found

### Title
Direct ERC-20 donations to `StreamingYieldVault` bypass the vesting guard and let an attacker sandwich-steal yield instantly - (File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol)

### Summary
`StreamingYieldVault` is Hyperbridge's ERC-4626 primitive used to hold liquidity that backs solver/LP capital for the Intent Gateway (referenced by Simplex's `TokenSender`/`VaultFundingPlanner` flows) [1](#0-0) . Like the reported MetaMorpho VaultV2 issue, its exchange-rate accounting (`totalAssets`) is designed to only recognize deliberately-tracked inflows (owner `addYield` tranches, vested linearly) — but a plain, unprivileged ERC-20 `transfer()` of the underlying asset straight to the vault address is not tracked by that mechanism at all, and is instantly and fully folded into `totalAssets`, defeating the vault's own "no instant jump / no yield sniping" invariant.

### Finding Description
`totalAssets()` is defined as the raw asset balance of the contract minus the not-yet-vested portion of the current owner-funded tranche: [2](#0-1) 

`_lockedYield()` only masks out `_vestingAmount`/`_vestingStart`, which are exclusively updated by `addYield` (onlyOwner) or the ERC-1363 `onTransferReceived` hook (which itself requires `from == owner()`): [3](#0-2) 

Nothing prevents any unprivileged address from calling `IERC20(asset).transfer(vault, amount)` directly. Such a transfer raises `asset.balanceOf(vault)` immediately, and since it never touches `_vestingAmount`/`_vestingStart`, `_lockedYield()` does not mask any of it — `totalAssets()` (and therefore the ERC-4626 share price via `convertToAssets`/`convertToShares`) jumps in the very same block. This is exactly the "donation directly to the underlying" side-effect from the external report: an accounting variable meant to be updated only through a controlled path (`allocation[id]` / `_totalAssets` in VaultV2, `_vestingAmount` here) is instead moved by an arbitrary token donation, breaking the documented invariant ("no instant jump… no yield sniping") [4](#0-3) .

Because the jump is instantaneous and undated by `VEST`, it can be sandwiched: an attacker deposits `A` right before an incoming donation `D` (which can be their own or anyone else's), then redeems immediately in the same or a following block, capturing `A·D/(T+A)` of value from other, already-present shareholders, where `T` is the vault's pre-donation `totalAssets()`. This mirrors the report's core issue: funds not intended to instantly benefit "suppliers" (existing depositors) instead do — extracted by whoever times a deposit/redeem around the donation, at the expense of the depositors who were present before and after the attacker's round-trip.

### Impact Explanation
Any legitimate, incidental, or third-party ERC-20 transfer into the vault (partner-protocol rebates, MEV-bot dust, mis-routed sweeps, or an intentional "poison" donation by an attacker themselves) can be instantly and fully captured, in whole or in part, by a same-block deposit+redeem sandwich, directly transferring value away from genuine LPs/solvers who supplied capital to back Intent Gateway fills. This is a direct value-extraction/theft vector against vault depositors, undermining the exact "no yield sniping" guarantee the contract's own documentation claims to provide.

### Likelihood Explanation
No privileged role is required by the attacker — only the ability to call the vault's public `deposit`/`redeem` functions and to send (or observe someone else sending) a plain ERC-20 transfer to the vault address, both of which are unrestricted, single-transaction actions. The vault's only mitigations (decimals offset, seed-and-burn) target the classic first-depositor inflation attack on an *empty* vault; neither mitigates a sandwich around a raw donation into an already-seeded vault, so the attack is reliably exploitable whenever any non-`addYield` inflow occurs.

### Recommendation
Compute `totalAssets()` from an internally tracked balance (incremented only on `deposit`/`mint`/`addYield`/`onTransferReceived`) rather than the live `asset.balanceOf(this)`, or apply the same linear-vesting treatment to any balance surplus detected relative to the internally tracked accounting, so that unsolicited/direct donations are streamed in over `VEST` (or excluded entirely) instead of being recognized instantly.

### Proof of Concept
1. Vault is seeded (`_seedAndBurn`) with `totalAssets() = T`, `totalSupply() = S`.
2. Attacker calls `deposit(A, attacker)`, minting `s ≈ A·S/T` shares (no `VEST` restriction applies to deposits when not currently vesting).
3. In the same or next block, any account (attacker or a third party) sends `asset.transfer(vault, D)` directly — bypassing `addYield`/`onTransferReceived`.
4. `totalAssets()` at line 94-96 immediately reports `T + A + D` since `_lockedYield()` is unaffected.
5. Attacker calls `redeem(s, attacker, attacker)`, receiving `(T+A+D)·A/(T+A)`, i.e., a profit of `A·D/(T+A)` extracted from the pre-existing shareholders' claim on the donation, executed entirely within an attacker-controlled window with no owner or governance involvement.

    /// @inheritdoc ERC4626
    /// @notice Total assets backing shares, net of any not-yet-vested yield.
    function totalAssets() public view override returns (uint256) {
        return IERC20(asset()).balanceOf(address(this)) - _lockedYield();
    }

    function onTransferReceived(address, address from, uint256 value, bytes calldata)
        external
        override
        returns (bytes4)
    {
        if (msg.sender != asset()) revert CallerNotAsset(msg.sender);
        if (from != owner()) revert OwnableUnauthorizedAccount(from);

        _startVesting(value);

        return IERC1363Receiver.onTransferReceived.selector;
    }

    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
    
    /// @notice Add a new yield tranche, pulled from the caller. Reverts unless the previous
    ///         tranche has fully vested, which guarantees tranches never overlap and no yield
    ///         is ever left permanently locked.
    /// @param amount The amount of `asset` to stream in over `VEST`.
    function addYield(uint256 amount) external onlyOwner {
        // Pull the funds first so `balanceOf` already reflects `amount` before it is marked
        // locked; otherwise `totalAssets` would transiently underflow when a tranche exceeds
        // the current backing (e.g. the very first `addYield` on a near-empty vault).
        IERC20(asset()).safeTransferFrom(msg.sender, address(this), amount);

        _startVesting(amount);
    }

    /// @dev Arms a new tranche after validating the no-overlap / deposit-window guards. The caller
    ///      must have already moved `amount` of `asset` into the vault (so `balanceOf` reflects it
    ///      before `_vestingAmount` is set, avoiding a transient `totalAssets` underflow).
    function _startVesting(uint256 amount) private {
        if (amount == 0) revert ZeroAmount();

        uint256 start = _vestingStart;
        if (start != 0) {
            if (block.timestamp < start + VEST) revert YieldStillVesting(start + VEST);
            // Hold off until the guaranteed deposit window has elapsed, so new capital always has
            // a chance to enter between tranches regardless of how promptly the keeper runs.
            if (block.timestamp < start + VEST + MIN_WINDOW) revert DepositWindowOpen(start + VEST + MIN_WINDOW);
        }

        _vestingAmount = amount;
        _vestingStart = block.timestamp;

        emit YieldAdded(amount, block.timestamp);
    }
