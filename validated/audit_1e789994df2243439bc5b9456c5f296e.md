### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted from unauthenticated headers while the HMAC only signs the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, which computes an HMAC-SHA256 over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . However, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are never included in the signed payload [2](#0-1) . `Registry.process` uses these unauthenticated header values to build `WebhookMetadata` that is handed directly to the app's handler, including the `shop` identity: [3](#0-2) .

### Finding Description
The equality that should hold is: `shop_bound_by_hmac == shop_used_by_handler`. In this gem, the HMAC only binds the request body bytes; it never binds the `shop-domain` header. So the check `HmacValidator.validate(request)` only proves "this body was signed with `api_secret_key`" — it proves nothing about which shop the webhook is "for." Because the shared app secret (`api_secret_key`) is the same across all merchants/tenants of a multi-tenant app, any tenant that receives one legitimately-signed webhook (body + valid `hmac-sha256` header) — including a tenant who is the attacker's own shop — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass because it only recomputes the HMAC over the untouched raw body [4](#0-3) , yet `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the attacker-chosen `shop` [5](#0-4) . The gem's own documentation instructs apps to trust `data.shop` as the shop identity for routing/storage of webhook data [6](#0-5) , so this unauthenticated field is exactly the kind of identity binding this class of bug targets.

### Impact Explanation
This breaks tenant isolation: a malicious app-installing merchant can cause the app to process webhook data under a different, victim shop's identity (cross-tenant confusion). Depending on how the host app uses `data.shop` (e.g., as a lookup/write key into per-shop storage, or to select which shop's access token to use for follow-up API calls), this can lead to cross-tenant data corruption or leakage — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker must control (or observe traffic for) at least one legitimate shop that has the app installed and can receive one authentic webhook, which is a low bar for an "unprivileged" but real tenant of a multi-tenant Shopify app (self-installation is standard for embedded apps). No access to `api_secret_key` or any access token is required — only replaying a previously-received, validly-signed body with a forged shop header.

### Recommendation
Bind the tenant identity into the HMAC-verified surface: either compute the webhook HMAC over a signable string that includes `shop`, `topic`, and `webhook_id` (mirroring how `Auth::Oauth::AuthQuery`/`VerifiableQuery` binds multiple fields for OAuth callbacks, e.g. `lib/shopify_api/auth/oauth/auth_query.rb`), or explicitly document/require that consuming apps cross-check `data.shop` against an independently-established session/shop record (e.g., a shop known to have an active offline session) before trusting it, rather than treating the header value as authenticated by the HMAC check alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged tenant) and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker replays the identical body + `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [7](#0-6) ; `Utils::HmacValidator.validate(request)` succeeds because it only checks the unchanged raw body against the shared `api_secret_key` [8](#0-7) .
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the body content actually belongs to `attacker-shop.myshopify.com` [5](#0-4) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
