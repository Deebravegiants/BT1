This confirms the intended, documented usage: apps construct `ShopifyAPI::Webhooks::Request` from raw headers/body and pass it to `ShopifyAPI::Webhooks::Registry.process`, which the docs claim "will verify the request did indeed come from Shopify." This is exactly the code path where the identity-binding gap exists.

### Title
Webhook shop-domain, topic, and webhook-id are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` proves nothing more than "this body was HMAC'd with the app's secret." The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` come straight from HTTP headers that are never included in the signed bytes, so any party who can obtain one valid `(body, hmac)` pair can relabel it to any shop domain and have it accepted as authentic for that shop.

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are part of the signed string: [4](#0-3) 

The `shop` value is then trusted directly and forwarded to the app's handler as the tenant identifier: [5](#0-4) 

The identity binding that should hold is: `HMAC-verified bytes == bytes that determine tenant (shop)`. Here, the verified bytes are `raw_body` only, while the tenant-determining byte is the unauthenticated `shopify-shop-domain` header — exactly the same class of bug as the reported `Karma.sol` issue, where the value used to construct/verify an identity domain (EIP-712 `name`/`version`) was not the value actually bound into the cryptographic check.

### Impact Explanation
An unprivileged attacker who can install the target app on any shop they control (e.g., a free Shopify dev/partner store) will legitimately receive real webhook deliveries from Shopify — each with a valid `x-shopify-hmac-sha256` computed by Shopify using the app's shared secret over that specific body. The attacker captures one such `(body, hmac)` pair for their own shop, then replays it to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` header to name a **different, victim shop**. Because the HMAC never covered the shop header, `HmacValidator.validate` still passes, and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and body content chosen/controlled by the attacker (from their own shop's event). This is cross-tenant: an attacker-controlled event is processed by the app under a victim tenant's identity, potentially triggering data mutation, deletion (e.g. spoofed `shop/redact`, `customers/redact`), session/token cleanup (e.g. spoofed `app/uninstalled`), or other tenant-scoped side effects the host app performs keyed on `data.shop`. This matches the Critical bucket for cross-tenant access.

### Likelihood Explanation
The attack requires no privileged credentials, no access token, and no knowledge of `api_secret_key` — only the ability to install the target app on any shop (trivial for any internet user with a Partner/dev store) and to intercept/replay their own webhook HTTP request, which is standard for any app owner debugging their own webhook endpoint. The victim shop domain is guessable/enumerable (`*.myshopify.com`), so likelihood is high for any app whose webhook handlers key business logic off `data.shop` as the sole tenant identifier, exactly as the gem's own documentation instructs apps to do.

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified bytes before trusting them:
```diff
 sig { override.returns(String) }
 def to_signable_string
-  @raw_body
+  "#{shop}\n#{topic}\n#{webhook_id}\n#{@raw_body}"
 end
```
This requires computing the comparison HMAC the same way at generation time, or — since Shopify does not sign headers itself — the mitigation must instead be documented/enforced at the point of trust: `Registry.process` (or the host app) should treat `shop` as untrusted unless corroborated against a known/registered shop for that webhook subscription (e.g., cross-check against the shop that owns the session used to register that specific `webhook_id`), rather than accepting the header value as-is once body HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any free dev store) and registers a webhook (e.g. `orders/create`) pointing at the app's public callback URL.
2. Shopify sends a real webhook POST to the app with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request (e.g., via their own logging/proxy) and replays it to the same endpoint, changing only the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping `B` and `H` unchanged.
4. The app builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` and calls `Registry.process`.
5. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes.
6. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body `B`, causing the app to act on victim-shop's tenant data/state using attacker-controlled webhook content.
