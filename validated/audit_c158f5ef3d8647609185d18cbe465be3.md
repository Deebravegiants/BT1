### Title
Double-entry token aliasing allows minting 2x shielded UTXO value from a single real deposit via `DepositOnChainUtxosExternalAction` - (File: `contracts/Hinkal.sol`, `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`Hinkal.transact` verifies solvency per index of `circomData.erc20TokenAddresses` by comparing `balanceOf` snapshots before/after the action to the UTXO amount minted for that index, but it never verifies that the `erc20TokenAddresses` entries correspond to economically independent balances — only that they are pairwise unequal as raw addresses (enforced in the circuit). An attacker can deploy two distinct contract addresses that expose (read) the *same* underlying balance while one of them makes its `transferFrom` a no-op, causing a single real transfer to be counted as backing for two separate on-chain UTXOs.

### Finding Description
The claimed equality that should hold per token index `i` is:
`balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]`, and in aggregate: real tokens entering the vault == `sum(amountChanges) + sum(minted on-chain UTXO amounts)`. [1](#0-0) 

`getBalancesForArray` just calls `balanceOf`/ETH balance independently for each address in `erc20TokenAddresses`: [2](#0-1) 

The only uniqueness guarantee for `erc20TokenAddresses` comes from the circuit, which checks pairwise address *inequality*, not balance independence: [3](#0-2) 

Neither `dimensionsCheck` nor `checkOnchainCreation` in `HinkalHelper.sol` impose any token whitelist or "these addresses must be economically distinct assets" constraint: [4](#0-3) 

`DepositOnChainUtxosExternalAction.runAction` (registered as an `externalActionId != 0` action, invoked from `_externalTransact`) requires `deltaAmounts[i] == 0` for every token, then for each index whose `tokenTotal > 0` calls `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` and mints an on-chain UTXO of `tokenTotal` for that token index: [5](#0-4) 

`transferERC20TokenFrom` is just `IERC20(_erc20TokenAddress).safeTransferFrom(_from, _to, _value)` — it trusts the token contract's return value and does not independently verify that the vault's real balance for that specific address actually increased by `_value`: [6](#0-5) 

Exploit flow:
1. Attacker deploys `tokenA` (a normal ERC-20 with real backing) and `tokenB`, a distinct contract address whose `balanceOf(addr)` simply proxies/reads `tokenA.balanceOf(addr)` (or shares the same underlying storage), and whose `transferFrom(...)` is implemented as a no-op that returns `true` without moving any value. `tokenA != tokenB` as raw addresses, satisfying `distinctErc20AddressChecks`.
2. Attacker calls `Hinkal.transact` with `erc20TokenAddresses = [tokenA, tokenB]`, `externalActionData.externalActionId` pointing at `DepositOnChainUtxosExternalAction`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]` (required by `checkOnchainCreation`), and `externalActionMetadata` encoding `utxoAmounts = [[X], [X]]`.
3. `_externalTransact` computes `deltaAmountChanges = [0, 0]` (satisfies the `deltaAmounts[i]==0` requirement inside the external action) and calls `runAction`.
4. Inside `runAction`: for index 0 (`tokenA`), it calls `transferERC20TokenFrom(tokenA, user, Hinkal, X)` — a real transfer of `X` tokens into the vault, which also increases the shared/proxied balance that `tokenB.balanceOf(Hinkal)` reports. For index 1 (`tokenB`), it calls `transferERC20TokenFrom(tokenB, user, Hinkal, X)` — attacker's no-op, moving zero real value but returning success. Two on-chain UTXOs of amount `X` each are queued (one tagged `tokenA`, one tagged `tokenB`).
5. Back in `Hinkal.transact`, `oldBalances`/`newBalances` are snapshotted via `getBalancesForArray([tokenA, tokenB])`. Because `tokenB.balanceOf` mirrors `tokenA`'s real balance, `balanceDif[0] == X` and `balanceDif[1] == X` both hold, exactly matching `utxoAmount[0] == X` and `utxoAmount[1] == X`. Both `require` checks pass.
6. Net result: only `X` real tokens entered the vault, but `2X` of shielded value was minted (`X` under `tokenA`, `X` under `tokenB`), which the attacker can later redeem from the shielded pool as if backed 1:1.

Using `circomData.relay == address(0)` (self-relay) or a whitelisted relay with `feeStructure.flatFee = 0` and `variableRate = 0` keeps the flow free of any relay-fee-driven balance adjustments, since `DepositOnChainUtxosExternalAction` performs no relay-fee logic of its own, so the exploit math above is exact and unaffected by fee splitting.

None of the existing guards catch this: `verifyProof`/circuit constraints only check `inTotal + amountChanges === outTotal` per index and address pairwise-inequality, not real-world balance independence; `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, `nonReentrant` are all satisfied normally; the per-index `balanceDif == amountChanges/onchain + utxoAmount` check is defeated because the two indices' `balanceOf` reads are not independent measurements of distinct value.

### Impact Explanation
The attacker mints shielded on-chain UTXOs (spendable via the normal shielded-pool withdrawal path) worth more than the real tokens deposited into the vault — a direct case of "minting shielded value without backing," i.e., protocol insolvency. This is repeatable for any amount `X` and any number of aliased token pairs the attacker cares to deploy, and scales with the number of `erc20TokenAddresses` entries allowed per transaction (bounded only by `MAX_LEAVES_PD`/dimension limits). This matches the Critical severity category (minting shielded value without backing).

### Likelihood Explanation
No privileged role is required. The attacker only needs to: deploy two ordinary-looking contracts (one "real" ERC-20, one balance-aliasing/no-op contract), obtain a normal deposit-side proof for `DepositOnChainUtxosExternalAction` (fully within their own UTXO control, no need to forge others' proofs), and submit `transact` directly (or via any whitelisted relay with zero fee — no special relay cooperation needed since the relay just executes the transaction, it doesn't validate token semantics). Feasibility is high; cost is limited to deploying two contracts and gas for one `transact` call.

### Recommendation
Do not rely solely on raw `balanceOf` deltas per user-supplied address as the sole solvency proof. Options: (a) maintain and require registration of `erc20TokenAddresses` against a protocol-controlled allowlist so arbitrary attacker-deployed contracts cannot be used as `erc20TokenAddresses`; (b) after computing `oldBalances`/`newBalances`, additionally verify token contract code/behavior invariants (e.g., re-check that a `transferFrom` call attributed to token `i` actually reduces `balanceOf(user)` for that same token by the claimed amount, rather than trusting a separate `balanceOf(vault)` read that can be aliased); (c) require that `DepositOnChainUtxosExternalAction` (and other external actions) validate `balanceOf(msg.sender's own deposit source)` deltas per-token in addition to vault-side deltas, so that aliasing/proxy tokens cannot inflate credited value beyond what was actually debited from the depositor for that specific token address.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with a minimal `HinkalHelper`/verifier mock that accepts a crafted proof (or use the project's existing test harness/verifier mock) and register `DepositOnChainUtxosExternalAction` as an external action.
2. Deploy `TokenA` (standard ERC-20, mintable to test user, `X = 1000` minted and approved to `Hinkal`/action contract).
3. Deploy `TokenB` with `balanceOf(addr) = TokenA(tokenA).balanceOf(addr)` and `transferFrom(...) returns (bool) { return true; }` (no state change).
4. Build `circomData` with `erc20TokenAddresses = [tokenA, tokenB]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, `slippageValues = [0, 0]`, `externalActionData.externalActionMetadata = abi.encode([[1000],[1000]])`, valid nullifier/commitment set for the depositor's own UTXOs (empty inputs), `relay = address(0)`.
5. Record `vaultTokenABalanceBefore = TokenA.balanceOf(Hinkal)` and `userTokenABalanceBefore = TokenA.balanceOf(user)`.
6. Call `Hinkal.transact(...)`.
7. Assert: `TokenA.balanceOf(Hinkal) - vaultTokenABalanceBefore == 1000` (only 1000 real tokens moved) and `userTokenABalanceBefore - TokenA.balanceOf(user) == 1000`.
8. Assert: two on-chain UTXO commitments were inserted with total credited value `2000` (1000 tagged `tokenA`, 1000 tagged `tokenB`) — i.e. `sum(minted UTXO amounts) (2000) > real tokens received by vault (1000)`, proving the equality `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)` is violated (`1000 != 0 + 2000`).

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }
