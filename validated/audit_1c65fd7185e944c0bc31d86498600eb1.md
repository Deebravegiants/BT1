### Title
Non-constant-time PIN comparison in `isCorrectPin` enables timing side-channel PIN brute force - (File: `features/auth-mobile/module/auth.js`)

### Summary
`Auth.isCorrectPin` in `features/auth-mobile/module/auth.js` verifies the user-supplied PIN against the PIN stored in the keystore using JavaScript's native `===` string comparison, which is a variable-time (short-circuiting) comparison rather than a constant-time one. This mirrors the reported HMAC-comparison timing-attack bug class: any secret comparison performed with `==`/`===`/`!=` leaks information about how many leading bytes/characters matched through execution-time differences, which is the exact vulnerability class described in the report.

### Finding Description
The `isCorrectPin` method retrieves the stored PIN from secure storage and compares it to caller-controlled input using plain equality: [1](#0-0) 

```js
isCorrectPin = async (input) => {
  const pin = await this.#keystore.getSecret(this.#key(AUTH_KEYSTORE_PIN_KEY))
  return !!pin && pin === input
}
```

JavaScript engines compare strings character-by-character and return as soon as a mismatch is found, so `pin === input` takes measurably longer when more leading characters of `input` match `pin`. This is architecturally identical to the `mac != self.mac` pattern flagged in the report: a secret value (the PIN) is compared to attacker-influenced input using a non-constant-time operator, exposing a timing side channel. `isCorrectPin` is exposed to the UI/API layer through `features/auth-mobile/api/index.js`, meaning any caller across that boundary can invoke it repeatedly with crafted inputs and measure response latency to incrementally recover the correct PIN, byte by byte (this is the classic timing-oracle exploitation strategy described in the original report's exploit scenario).

### Impact Explanation
The 6-digit PIN gates a "should authenticate" state used to restrict access to protect-worthy resources such as the mnemonic phrase, per the feature's own documentation: [2](#0-1) 

If an attacker (e.g., malicious/compromised UI code, a rogue app on the device, or any caller reachable across the `api` boundary) can repeatedly invoke `isCorrectPin`, they can leverage statistical timing analysis to substantially reduce the PIN search space or fully recover it faster than pure brute force, undermining the authentication gate protecting sensitive wallet operations. This is a real auth-bypass-adjacent primitive, though its practical severity is bounded by two factors I could not fully verify from the index: (1) whether any rate-limiting/lockout wraps PIN attempts elsewhere in the stack, and (2) how precisely timing can be measured across the actual process/IPC boundary in production builds.

### Likelihood Explanation
Likelihood is moderate: exploiting sub-millisecond timing differences over an IPC/bridge boundary (rather than a local process) is harder than a pure in-process attack and requires many samples plus statistical averaging, consistent with the original report's own exploit scenario (repeated triggering + statistical analysis). No throttling/backoff logic is visible in `auth.js` itself, which would otherwise mitigate repeated-attempt timing attacks.

### Recommendation
Replace the direct `===` comparison with a constant-time comparison primitive (e.g., `crypto.timingSafeEqual` after encoding both PIN and input to fixed-length buffers, or an existing constant-time compare utility already used elsewhere in the crypto libraries in this repo, such as `libraries/sodium-crypto`). Additionally, ensure PIN length is validated/normalized before the constant-time compare so length itself doesn't leak, and consider adding attempt throttling/lockout as defense in depth.

### Proof of Concept
Conceptual PoC (not executed, derived from code reading):
1. Attacker gains ability to call `auth.isCorrectPin(candidate)` repeatedly (e.g., via the `api/index.js` binding exposed to UI/less-trusted code).
2. For each position in the 6-digit PIN, attacker submits candidates varying only in that digit and measures round-trip latency over many trials.
3. Because `pin === input` short-circuits on first mismatch, correct-prefix candidates take marginally longer on average.
4. Attacker iteratively fixes each correct digit based on timing signal, reducing the PIN search space from 10^6 brute-force attempts to a much smaller number of statistical trials per digit, eventually recovering the full PIN and unlocking protected wallet resources gated by `hasPin`/`shouldAuthenticate`.
