This confirms the asymmetry: in the OAuth flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-signed parameter set [1](#0-0) , binding the shop identity to the HMAC. In contrast, the webhook `Request#to_signable_string` returns only the raw body, and `shop` is read from a separate, unsigned header [2](#0-1) [3](#0-2) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [4](#0-3) , so for webhooks it never covers the shop-domain header. `Registry.process` validates the HMAC and then dispatches the handler using `request.shop` taken straight from that unverified header [5](#0-4) .

### Title
Webhook shop identity is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken from separate, unsigned HTTP headers. `Registry.process` validates the HMAC and then trusts `request.shop` when building `WebhookMetadata` for the handler, without any cryptographic binding between the verified body and the claimed shop.

### Finding Description
The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. For OAuth callbacks, the library correctly enforces this equality — `AuthQuery#to_signable_string` includes `shop` inside the signed parameter set, so `Utils::HmacValidator.validate` cryptographically binds the shop to the signature [1](#0-0) .

For webhooks, this equality is broken. `Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside that signed string [2](#0-1) . `HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) using the app's single global `Context.api_secret_key` (or `old_api_secret_key`), and does not consider the shop header at all [6](#0-5) .

Because the `client_secret`-derived HMAC key is the same for every shop that installs the app, any `(raw_body, hmac)` pair that is valid for one shop's webhook delivery is also a cryptographically valid `(raw_body, hmac)` pair when replayed with a different `shop-domain` header — the signature computation is shop-agnostic. `Registry.process` raises only if the HMAC itself is invalid, then immediately calls the topic handler with `request.shop` taken from the unverified header [5](#0-4) . Nothing re-derives or cross-checks the shop against the signed content.

An attacker who is a legitimate (even free-tier) installer of the app receives real webhook deliveries for their own shop, giving them valid `(body, hmac)` pairs for known/predictable payload shapes (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or any webhook whose body content the attacker fully controls or can predict, such as one triggered by their own store actions). By replaying that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain, the request passes `HmacValidator.validate` and is dispatched to the handler as if it genuinely originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate but unprivileged user of the app (any shop owner installing the app) can cause the app to process a forged webhook attributed to a shop they do not control. Depending on which handler is registered, this can trigger cross-tenant effects — e.g., forging an `app/uninstalled` webhook to make the app delete or invalidate a victim shop's stored session/access token, or forging GDPR redaction webhooks (`shop/redact`, `customers/redact`) to cause deletion of another merchant's data. This matches the Critical category of cross-tenant access via an identity-binding break, since it does not require possession of the victim's access token, `client_secret`, or any privileged credential.

### Likelihood Explanation
Likelihood is bounded by the attacker needing a valid `(body, hmac)` pair, which is realistically obtainable by installing the app on their own shop (a normal, unprivileged action) and capturing any webhook delivery whose body they can also reproduce or predict for the victim scenario (many webhook topics have fixed/near-empty bodies, e.g. `app/uninstalled` typically sends minimal or predictable JSON). No interception of Shopify-to-app traffic or secret material is required — only header manipulation on a replayed HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop to the signed content for webhook verification, mirroring the OAuth `AuthQuery` design: include the shop-domain header (and/or webhook id) inside the HMAC-signable string, or independently authenticate the shop (e.g., by validating that the shop-domain header matches a shop with an active, previously-established session/subscription for that specific webhook topic/id before invoking the handler), rather than trusting an unsigned header once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers/receives a webhook (e.g. `app/uninstalled`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing the exact captured `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this matches the captured signature since the body and app secret are unchanged [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata` built from `request.shop` = `victim.myshopify.com`, `request.topic` = `app/uninstalled`, even though the request never actually came from Shopify about that shop [9](#0-8) .
