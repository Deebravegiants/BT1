### Title
`EvmHost.dispatch`/`fundRequest` swap `msg.value` for fee tokens but never refund leftover ETH to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native ETH via `msg.value` and swap it through `IUniswapV2Router02.swapETHForExactTokens` to obtain an exact amount of `feeToken()`. Unlike `IntentGatewayV2` and `ExtrinsicIntents`, which explicitly capture the swap's spent amount and call `_sendValue(msg.sender, msgValue)` to refund any unspent native token, `EvmHost` discards the router's return value and performs no refund at all.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the function calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` and ignores its return value. Because `recipient` is `address(this)` (the `EvmHost` contract) rather than the caller, the standard `UniswapV2Router02.swapETHForExactTokens` implementation refunds any unspent ETH to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender (`_msgSender()`). The same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

By contrast, `IntentGatewayV2._createOrder` (called by `placeOrder`) performs the analogous swap and explicitly refunds the leftover native token to the original caller: [4](#0-3) 
The same explicit-refund pattern is present in `ExtrinsicIntents.sol`'s fill logic: [5](#0-4) 

`EvmHost` has no equivalent refund step. Any dApp/relayer/user that overestimates the native-ETH amount needed to cover `post.fee`/`get.fee`/`amount` when calling `dispatch(...)` or `fundRequest(...)` on `EvmHost` permanently loses the excess ETH into the `EvmHost` contract, which — per the code exposed here — has no ETH withdrawal path (only `feeToken` revenue withdrawal via the `hostManager`).

### Impact Explanation
This is directly reachable by any unprivileged message dispatcher: any app contract or user calling `IDispatcher(hostAddr).dispatch(...)` (POST or GET) with native ETH, or calling `fundRequest` to top up a relayer fee, will have excess ETH silently swallowed by `EvmHost` rather than refunded. Since Uniswap swap output is variable (slippage/price movement) and callers must supply `msg.value` upfront without knowing the exact router execution price, overpayment is a normal, expected occurrence — not an edge case. This results in permanent freezing/loss of user funds inside the `EvmHost` contract with no recovery mechanism for the ETH portion, satisfying a "permanent freezing of funds" impact.

### Likelihood Explanation
High likelihood: every dispatch of a POST/GET request or `fundRequest` call paid in native ETH is affected, since the router's exact-output swap virtually never consumes 100% of the supplied ETH exactly. This is the default/expected code path for native-fee payments across `EvmHost`, not a rare edge case, and requires no special conditions beyond a normal dispatch call with `msg.value` slightly exceeding the swap's exact cost.

### Recommendation
Capture the `amounts` array returned by `IUniswapV2Router02.swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compute `msg.value - amounts[0]` as leftover ETH, and refund it to `_msgSender()` (mirroring the `_sendValue(msg.sender, msgValue)` pattern already used in `IntentGatewayV2` and `ExtrinsicIntents`).

### Proof of Concept
1. A dApp calls `EvmHost.dispatch(DispatchPost{..., fee: X})` with `msg.value = X + Δ` ETH (a reasonable buffer to account for router price movement, as `IntentGatewayV2`'s own documentation/tests recommend for fee swaps, e.g. `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` sending `5 ether` for a swap that costs a fraction of that: [6](#0-5) ).
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
3. The router swaps only enough ETH to buy `X` feeToken and refunds the remaining `Δ` ETH to `msg.sender` of the swap call, i.e., to `EvmHost`'s own address (not the caller).
4. `EvmHost.dispatch` never checks or forwards this refunded `Δ` ETH; it remains stuck in the `EvmHost` contract balance with no function to withdraw stray ETH, permanently freezing the caller's `Δ` ETH.
