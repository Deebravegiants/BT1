## Analysis

The CVE describes a bug class where malicious, attacker-controlled input traps a message-processing loop in an endless busy-loop with no way to exit except killing the process. The Hyperbridge codebase has a directly analogous defect in the GRANDPA consensus verifier's ancestry-walking routine.

### Title
Unbounded busy-loop DoS via cyclic header ancestry in GRANDPA `AncestryChain::ancestry` - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks parent-hash pointers collected entirely from attacker-supplied `unknown_headers`/`votes_ancestries` in a submitted GRANDPA consensus proof, with no cycle detection or iteration bound. A relayer can submit a consensus message whose header set contains a parent-hash cycle, causing the walk to loop forever, exactly mirroring the curl WebSocket bug class (endless busy-loop triggerable by crafted, unprivileged input, exitable only by killing the process/thread).

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

The `ancestry` map it walks is built directly from the untrusted `unknown_headers` field of the submitted `FinalityProof`: [2](#0-1) 

This function is invoked from `verify_grandpa_finality_proof`, which is the entry point reached by an unsigned/relayed `ConsensusMessage::StandaloneChain` (or via `verify_parachain_headers_with_grandpa_finality_proof` for the Polkadot/Relaychain variants) inside `GrandpaConsensusClient::verify_consensus`: [3](#0-2) [4](#0-3) 

The same unbounded-walk primitive is also used inside `GrandpaJustification::verify` on `votes_ancestries`, so both the `verify_grandpa_finality_proof` call at line 88 and the per-precommit ancestry lookups at line 125-127 are exposed to the same attacker-controlled header set: [5](#0-4) 

Because `unknown_headers` is decoded straight from the wire (`ConsensusMessage`) with no validation that the parent-hash chain forms an acyclic, terminating path back to `base`/`from`, an attacker can construct two (or more) headers `A`, `B` where `A.parent_hash == hash(B)` and `B.parent_hash == hash(A)`. When `ancestry(base, block)` is invoked with `base` not equal to `A` or `B`, the `while current_hash != base` loop finds every visited hash present in the map (so the `_ => return Err(NotDescendent)` arm is never hit) and never reaches `base`, spinning forever exactly like the curl WebSocket loop that "has no other way to escape or exit... other than killing the thread/process."

### Impact Explanation
Since consensus verification runs synchronously inside on-chain runtime execution (`verify_consensus` is called from pallet-ismp during message handling), a single crafted consensus-update submission can hang the executing node/collator indefinitely, halting block production/consensus-state advancement for that state machine — a Medium/High-severity denial-of-service that prevents the route from delivering any further messages, satisfying the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Any unprivileged relayer can submit a `ConsensusMessage` containing a `FinalityProof` with a crafted `unknown_headers`/`votes_ancestries` set. Constructing two headers whose parent hashes point at each other only requires computing SCALE-encoded header hashes offline — no signing authority or special privilege is needed, since the cyclic headers themselves are never required to be justified/signed; they merely need to be present in the `ancestry` map that seeds the walk.

### Recommendation
Bound `AncestryChain::ancestry` with either (a) a maximum iteration count derived from the number of supplied headers (since a valid ancestry route can never revisit a header, `route.len()` should never exceed `ancestry.len()`), or (b) explicit cycle detection via a `visited` set that aborts with an error once a hash is seen twice. Apply the same bound to the parallel logic in `GrandpaJustification::verify`.

### Proof of Concept
1. Craft headers `A` and `B` (arbitrary block numbers/state roots) such that `A.parent_hash = Blake2Hash(B)` and `B.parent_hash = Blake2Hash(A)`.
2. Build a `FinalityProof` whose `unknown_headers` includes `A`, `B`, and a genuine `target`/`base` header pair such that the finality-grandpa commit validation passes (or reach the `ancestry` call before/independent of that check, depending on which invocation path is targeted).
3. Submit the resulting `ConsensusMessage::StandaloneChain` via the GRANDPA consensus client's `verify_consensus` entry point.
4. Observe that `AncestryChain::ancestry` enters the `A → B → A → B → ...` cycle and never returns, hanging the executing node.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
