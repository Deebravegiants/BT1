This confirms the finding. Note that for the OAuth `AuthQuery`, `shop` **is** included in `to_signable_string` (line 38 of `lib/shopify_api/auth/oauth/auth_query.rb`), so the OAuth callback binds `shop` to the HMAC correctly. But for webhooks, `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `request.shop` is read directly from an unauthenticated header [2](#0-1)  and is trusted downstream by `Registry.process` to build `WebhookMetadata` dispatched to the handler [3](#0-2) .

### Title
Webhook `shop` identity is not bound by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw body [4](#0-3) , computed via `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` and compares it against the app's `api_secret_key` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include the `shop-domain` header at all [1](#0-0) . The `shop` field consumed elsewhere in the same request object is read straight from the (unauthenticated) `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . After the HMAC check passes, `Registry.process` builds a `WebhookMetadata` object using this unauthenticated `request.shop` and hands it to the app's registered handler [6](#0-5) .

### Finding Description
This breaks the identity-binding equality that the bug-class hint targets: **the field acted upon (`shop`) is not covered by the HMAC that is verified**. The HMAC only proves that the request *body* was signed with the app's `api_secret_key` — a secret shared across *every* shop that has the app installed (public apps use one `client_secret`/`api_secret_key` for all tenants). It proves nothing about which shop the event pertains to, because `shop` is excluded from `to_signable_string`.

Contrast this with the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameter set [7](#0-6) , correctly binding `shop == shop_signed`. The webhook path has no equivalent binding: `shop_verified (∅, not in signable string) ≠ shop_acted_on (header value trusted by handler)`.

Any attacker who has legitimately received one valid `(raw_body, hmac)` pair from Shopify for their *own* shop (trivial — they can install the app on a store they control, or replay a previously captured legitimate webhook for a generic/predictable topic and body) can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a *different* merchant's shop domain. `Utils::HmacValidator.validate` will accept it because the signature only ever covered `raw_body` [8](#0-7) , and the handler will process the event believing it originated from the spoofed shop.

### Impact Explanation
This is a cross-tenant confusion vector at the library's authentication boundary: the gem hands the host application a `shop` value it advertises as authenticated (it survived HMAC verification) but that is in fact attacker-controlled. Any host application that uses `WebhookMetadata#shop` as a trusted tenant key (e.g., to select which merchant's stored session/data to update, per the documented usage pattern in `docs/usage/webhooks.md`) can be tricked into performing actions against the wrong tenant's data using an attacker-supplied body, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request with a valid `(raw_body, hmac)` pair and a forged `shop-domain` header — no access token, `client_secret`, or privileged account is needed. An attacker can trivially generate their own valid pair by installing the app on a shop they control (or waiting for one benign webhook) and mandatory webhook topics (`shop/redact`, `customers/redact`, `customers/data_request`) even have fixed/predictable bodies in some cases, lowering the bar further [9](#0-8) .

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed payload before trusting it. Short term: `Webhooks::Request#to_signable_string` should incorporate the shop (and ideally topic) into the signed string, or the library should document/require host applications to independently verify that the `shop` on file for a given topic/subscription matches, rather than trusting the header value as authenticated. Long term: add integration tests asserting that tampering with `shop-domain` (while keeping `raw_body`/`hmac` fixed) causes verification to fail.

### Proof of Concept
```ruby
# Attacker has a valid (raw_body, hmac) pair from their own shop's webhook
# (or a replayed mandatory webhook body), e.g.:
raw_body = '{"id":123}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)
hmac_b64 = Base64.encode64(hmac)

# Attacker forges the shop-domain header to a victim's shop
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because to_signable_string == raw_body only.
# Handler receives WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)
# even though the signature never authenticated that shop value.
```
