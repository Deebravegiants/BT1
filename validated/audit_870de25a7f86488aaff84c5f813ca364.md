### Title
Webhook `Request` HMAC only authenticates the raw body — `shop`, `topic`, and `webhook_id` headers are unauthenticated and can be forged for cross-tenant confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof that the entire webhook request — including which shop it came from and which topic/webhook it represents — is authentic. In reality, the HMAC only covers the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values, which are read straight from HTTP headers, are never bound into the signed material, so any party who can produce one valid `(body, hmac)` pair for the app's secret can freely relabel that payload as belonging to any shop/topic/webhook id.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates only that signable string against the secret, then unconditionally trusts the header-derived `shop`/`topic`/`webhook_id` to build `WebhookMetadata` and dispatch it to the registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the received signature — it never incorporates the shop/topic/id headers: [4](#0-3) 

This breaks the identity binding `authenticated_shop == request.shop`: passing HMAC validation only proves "this body was produced/known by someone holding `api_secret_key`" — a much weaker guarantee than "this event legitimately originated from shop `request.shop` for topic `request.topic`." Because the shop-domain and topic headers are outside the signed scope, they can be swapped independently of the body while the signature remains valid.

### Impact Explanation
Any unprivileged party who has legitimately observed one valid `(raw_body, x-shopify-hmac-sha256)` pair for the target app (e.g., from their own store's webhook deliveries, which they can view/capture on their own tunnel/endpoint) can replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` for a different (victim) shop, and/or a different `x-shopify-topic` / `x-shopify-webhook-id`. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the forged metadata to the handler as if it were an authentic event for the victim shop/topic. Depending on the host app's handler logic (e.g., updating shop-specific state, deleting data, syncing orders), this enables cross-tenant data corruption/injection into a shop the attacker does not control — a direct violation of the tenant-isolation guarantee the HMAC check is meant to provide.

### Likelihood Explanation
Exploitability only requires the ability to send arbitrary HTTP requests to the app's public webhook endpoint plus one legitimately-signed `(body, hmac)` sample, which any merchant installing the same app on their own store can trivially obtain from their own webhook traffic. No `api_secret_key`, access token, or privileged access is required — this fits the "unprivileged internet user" threat model.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the payload (e.g., verify a canonical string containing shop+topic+body against the HMAC) before constructing `WebhookMetadata` and dispatching to handlers, so that a valid signature can only be replayed for the exact shop/topic it was issued for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and observes a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid signature of `B` with the app's `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(secret, B) == H` — this passes.
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B, ...)`, i.e., attacker-controlled body content is processed as if it legitimately originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
