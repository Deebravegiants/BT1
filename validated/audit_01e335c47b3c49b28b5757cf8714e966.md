Audit Report

## Title
Double-application of the same storage `Diff` to `ContractInfo` inflates storage-deposit refunds - ([File: substrate/frame/revive/src/metering/storage.rs])

## Summary
`RawMeter::apply_pending_changes_to_contract` calls `diff.update_contract::<T>(Some(info))`, which mutates `info.storage_bytes`, `info.storage_items`, `info.storage_byte_deposit`, and `info.storage_item_deposit` in place, but the function leaves `own_contribution` as `Contribution::Alive(diff)` unchanged. [1](#0-0)  If `apply_pending_storage_changes` (its wrapper in `mod.rs`) is invoked more than once for the same frame before the diff is finally reset via `bank_pending_changes` or `finalize_own_contributions`, the same accumulated diff gets applied to the already-mutated `ContractInfo` again, producing a second, spurious `Deposit::Refund`/charge and further mutating the info fields. [2](#0-1) 

## Finding Description
`Diff::update_contract` is not idempotent: it computes a `Deposit::Charge`/`Deposit::Refund` from `self` (the diff) and `info`'s *current* byte/item counts, and then permanently updates `info.storage_bytes`, `info.storage_items`, `info.storage_byte_deposit`, and `info.storage_item_deposit` accordingly. [3](#0-2) 

`apply_pending_changes_to_contract` was explicitly added (per its doc comment, referencing contract-issues#213) to let a child frame see a parent's not-yet-finalized diff before creating a nested call. [4](#0-3)  Unlike `finalize_own_contributions`, which converts `own_contribution` from `Contribution::Alive(diff)` to `Contribution::Checked(deposit)` after applying it once, [5](#0-4)  and unlike `bank_pending_changes`, which resets `own_contribution` to `Contribution::Alive(Default::default())` right after applying the diff, [6](#0-5)  `apply_pending_changes_to_contract` neither resets nor checkpoints the diff. `charge()` keeps accumulating onto the same `own_contribution` diff via `own.saturating_add(diff)`. [7](#0-6) 

Consequently, if `FrameMeter::apply_pending_storage_changes` (the `mod.rs` wrapper) [8](#0-7)  is invoked more than once for a frame before that frame's diff is finally consumed by `finalize`/`bank_pending_storage_changes`, the *entire accumulated diff* (unchanged between the two calls, unless new storage changes were recorded in between) is applied a second time to the already-mutated `info`. Because the refund ratio in `update_contract` is computed from `info.storage_bytes`/`info.storage_items` *at call time*, and these were already reduced by the first application, the second application computes a refund/charge based on stale-but-nonzero removed/added counts against the newly-reduced base, producing an additional non-zero `Deposit` and additional mutation of `info`'s deposit fields, when logically no new storage change occurred between the two calls.

`charge_contract_deposit_and_transfer` and `record_contract_storage_changes` only guard against exceeding the deposit *limit* via `adjust_effective_weight_limit`/`deposit_left().is_none()`; they impose no constraint preventing a diff from being applied to `ContractInfo` more than once. [9](#0-8) 

## Impact Explanation
This is a real, reproducible logic bug in the storage-metering code: `apply_pending_changes_to_contract`/`apply_pending_storage_changes` mutate `ContractInfo`'s deposit fields without consuming or resetting the diff that was applied, breaking the invariant that a given `Diff` should affect `ContractInfo`'s persistent deposit counters exactly once. This matches the code-level root cause described in the claim, verified directly from the referenced source. Whether this manifests as an exploitable "inflated refund stealing funds" depends on how many times `apply_pending_storage_changes` is actually invoked per frame lifetime in `exec.rs` (i.e., whether the call-frame machinery calls it more than once for the same still-`Alive` diff before finalization/banking) — I was unable to fully confirm the call sites and invocation cadence in `exec.rs` within the available tool budget, so I cannot conclusively verify whether a normal nested-call/delegate-call sequence actually triggers a second invocation of `apply_pending_storage_changes` against an unreset diff versus only being called once per nested-call boundary in a way that's naturally bounded.

## Likelihood Explanation
The root-cause mutation-without-reset bug is confirmed in the code. The claim's exploit scenario (a contract issuing multiple nested calls in one frame) is plausible as a trigger path since nested calls are entirely permissionless and controllable by any contract author, but confirming the exact reachability (i.e., that `exec.rs`'s frame-lifecycle logic calls `apply_pending_storage_changes` multiple times for the same un-banked/un-finalized diff during a single frame, rather than once per nested-call entry with intervening resets elsewhere) requires deeper tracing of `exec.rs` that could not be completed.

## Recommendation
Ensure `apply_pending_changes_to_contract` does not permit re-application of the same diff to `ContractInfo`. Either (1) checkpoint the diff already exposed to children and only apply the delta since the last exposure, or (2) compute a non-mutating preview of `info` for child visibility, deferring all real, permanent mutation of `ContractInfo`'s deposit fields to `finalize_own_contributions`/`bank_pending_changes`, which are the only functions that should mutate `info` and which already correctly convert/reset `own_contribution` after doing so.

## Proof of Concept
Add a unit test in `substrate/frame/revive/src/metering/storage/tests.rs` that: (1) creates a `ContractInfo` with known `storage_bytes`/`storage_byte_deposit`; (2) calls `meter.charge(&diff)` with a `Diff` containing `bytes_removed`/`items_removed`; (3) calls `apply_pending_changes_to_contract(&mut info)` once and records `info.storage_byte_deposit`; (4) calls `apply_pending_changes_to_contract(&mut info)` again with no intervening `charge` call; (5) assert the deposit field is unchanged between the two calls. Under the current code, the second call further reduces `info.storage_byte_deposit`/`storage_item_deposit`, demonstrating the same diff is reapplied.

	pub fn update_contract<T: Config>(&self, info: Option<&mut ContractInfo<T>>) -> DepositOf<T> {
		let per_byte = T::DepositPerByte::get();
		let per_item = T::DepositPerChildTrieItem::get();
		let bytes_added = self.bytes_added.saturating_sub(self.bytes_removed);
		let items_added = self.items_added.saturating_sub(self.items_removed);
		let mut bytes_deposit = Deposit::Charge(per_byte.saturating_mul((bytes_added).into()));
		let mut items_deposit = Deposit::Charge(per_item.saturating_mul((items_added).into()));

		// Without any contract info we can only calculate diffs which add storage
		let info = if let Some(info) = info {
			info
		} else {
			return bytes_deposit.saturating_add(&items_deposit);
		};

		// Refunds are calculated pro rata based on the accumulated storage within the contract
		let bytes_removed = self.bytes_removed.saturating_sub(self.bytes_added);
		let items_removed = self.items_removed.saturating_sub(self.items_added);
		let ratio = FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		bytes_deposit = bytes_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_byte_deposit)));
		let ratio = FixedU128::checked_from_rational(items_removed, info.storage_items)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		items_deposit = items_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_item_deposit)));

		// We need to update the contract info structure with the new deposits
		info.storage_bytes =
			info.storage_bytes.saturating_add(bytes_added).saturating_sub(bytes_removed);
		info.storage_items =
			info.storage_items.saturating_add(items_added).saturating_sub(items_removed);
		match &bytes_deposit {
			Deposit::Charge(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_sub(*amount)
			},
		}
		match &items_deposit {
			Deposit::Charge(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_sub(*amount)
			},
		}

		bytes_deposit.saturating_add(&items_deposit)
	}

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}

		&mut self,
		contract: T::AccountId,
		amount: DepositOf<T>,

			self.deposit.max_charged(),
		);

		self.deposit.charge_deposit(contract, amount);
		self.adjust_effective_weight_limit()
	}

	/// Record storage changes of a contract.
	pub fn record_contract_storage_changes(&mut self, diff: &Diff) -> DispatchResult {
		log::trace!(
			target: LOG_TARGET,
			"Charge contract storage: \
				diff={:?}, \
				deposit_left={:?}, \
				deposit_consumed={:?}, \
				max_charged={:?}",
			diff,
			self.deposit_left(),
			self.deposit_consumed(),
			self.deposit.max_charged(),
		);

		self.deposit.charge(diff);
		self.adjust_effective_weight_limit()
	}

	/// [`Self::charge_contract_deposit_and_transfer`] and [`Self::record_contract_storage_changes`]
	/// does not enforce the storage limit since we want to do this check as late as possible to
	/// allow later refunds to offset earlier charges.
	pub fn finalize(&mut self, info: Option<&mut ContractInfo<T>>) -> DispatchResult {
		self.deposit.finalize_own_contributions(info);

		if self.deposit_left().is_none() {
			return Err(<Error<T>>::StorageDepositLimitExhausted.into());
		}

		Ok(())
	}
