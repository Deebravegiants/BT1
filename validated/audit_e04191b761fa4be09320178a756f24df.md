### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop` value used downstream as the tenant identifier comes from an unsigned header. Since Shopify webhook HMACs are computed with the app-wide `api_secret_key` (shared across every shop that has the app installed) rather than a per-shop secret, any merchant who has received one legitimate, signed webhook can replay that same body+HMAC pair while substituting a different `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` accepts this forged tenant identity without any additional binding check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (unsigned) `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` verify the HMAC strictly against `verifiable_query.to_signable_string` (i.e. the body only), never incorporating `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the handler as the trusted tenant identity, with no additional check that this value was covered by the signature: [4](#0-3) 

This is the same bug class as the referenced report: a field that is acted upon (`shop`, used as the tenant/session key for the handler) is not covered by the authentication primitive (the HMAC) that is supposed to bind the whole request. The equality that should hold is `shop_verified_by_hmac == shop_used_for_tenant_routing`, but the code only guarantees `hmac_of(body) == received_hmac`; `shop` is never part of that equation.

Because Shopify computes webhook HMACs using the app's single `api_secret_key`, not a per-shop key, any shop that installs the app and receives one legitimate webhook obtains a valid `(body, hmac)` pair that will validate successfully for that app regardless of which shop header accompanies it. A malicious merchant can therefore capture their own legitimate webhook delivery and resend the identical body/HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop.

### Impact Explanation
This crosses a tenant boundary: `WebhookMetadata.shop` is used by consuming apps to determine which merchant/tenant record a webhook body applies to. An attacker-controlled `shop` value passing HMAC validation lets an unprivileged app-installer inject data (order/product/customer payloads they crafted or replay) attributed to an arbitrary other shop, i.e. cross-tenant access/confusion, which meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is realistic: no `api_secret_key`, access token, or elevated privileges are required — only that the attacker's own shop installed the app and received at least one real webhook, which happens naturally on any subscribed topic. Rewriting one HTTP header on a replayed request is trivial.

### Recommendation
Include the shop domain (and other tenant/topic-identifying headers) inside the HMAC signable string, e.g. concatenate `shop-domain` (and `topic`) with the body before computing/verifying the HMAC, or otherwise cryptographically bind the header value used for tenant routing to the value that was actually delivered by Shopify for that specific webhook subscription.

### Proof of Concept
1. App has webhook topic `orders/create` registered; Shop A (attacker-controlled) installs the app and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `api_secret_key`), header `X-Shopify-Shop-Domain: shopA.myshopify.com`.
2. Attacker resends the exact same `(B, H)` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only and it matches `H`, so validation passes at `lib/shopify_api/webhooks/registry.rb:190`.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"`, even though that value was never covered by the HMAC — the host application's handler now processes attacker-supplied `orders/create` data as if it originated from the victim shop.
