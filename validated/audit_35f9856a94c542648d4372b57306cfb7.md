### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header values are trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but then hands the caller-supplied `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers straight to the handler as trusted, shop-scoped metadata. None of these header values are included in the HMAC signature, so the binding "HMAC-authenticated request == data attributed to `shop`" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from HTTP headers and are never mixed into the signed payload: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` when constructing the metadata passed to the app's handler: [3](#0-2) 

The identity binding the gem is supposed to enforce is: `shop_that_HMAC_authenticated_the_request == shop_attributed_to_the_delivered_data`. Because the HMAC only covers `@raw_body`, that equality is never actually checked — only the byte-for-byte legitimacy of the body is proven, not which shop it came from. Any bytes (headers) not covered by `to_signable_string` are attacker-controllable while the HMAC still validates as long as the (unmodified) body is reused.

### Impact Explanation
A merchant who has installed the app receives real webhook deliveries at the app's public endpoint (that is a documented, unprivileged capability of any tenant of a multi-tenant Shopify app — no `api_secret_key`, access token, or admin privilege is required). Because the header fields are outside the signed data, that same merchant can replay a webhook payload they legitimately received while swapping only the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header to point at a different tenant's shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), and `Registry.process` will call the host application's handler with `shop: <attacker-chosen shop>` alongside the original victim shop's body data. If the host application uses this `shop` value (as `docs/usage/webhooks.md` and `WebhookMetadata` construction suggest it is meant to be used) to select which tenant record/session/database row to write order, customer, or inventory data into, this yields cross-tenant data confusion/injection — one merchant's webhook can be attributed to and written into another merchant's data store. This satisfies the "Critical – cross-tenant access" impact bar in the rules.

### Likelihood Explanation
Likelihood is high for any app built on this gem that trusts `WebhookMetadata#shop` (i.e., what `Registry.process` passes as `shop:`) for tenant routing, which is the documented and expected usage pattern (`docs/usage/webhooks.md` shows building the `Request` straight from framework headers and calling `Registry.process`, and the value is surfaced through the handler's `data.shop` field as shown in the test suite). Any existing merchant of a multi-tenant app already has all the material needed (their own legitimately-signed webhook body/HMAC) to mount the attack; no secret material or elevated privilege is required, only the ability to send an HTTP request with attacker-chosen headers to the app's own webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is cryptographically verified before it is trusted:
- Have `Registry.process` cross-check the header-derived `shop` against something authenticated (e.g., require the caller to supply/verify an expected shop, or fetch/validate shop identity via a signed channel rather than a bare header), or
- At minimum, document loudly that `request.shop`/`request.topic`/`request.webhook_id` are NOT covered by the HMAC and must not be used by host applications for authorization/tenant-routing decisions without additional verification (e.g., confirming the shop is one that currently has this webhook topic registered, or validating it against the session store keyed by a value that *is* HMAC-protected).
- Consider extending `to_signable_string` (or a companion check) to incorporate the `shop-domain` header when validating, if backward compatibility with Shopify's actual webhook signing scheme allows it, or clearly gate `Registry.process` behind an explicit shop-allowlist check supplied by the host app.

### Proof of Concept
1. App merchant "shop-a.myshopify.com" installs the app and receives a legitimate webhook POST at the app's webhook endpoint with headers:
   `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: shop-a.myshopify.com`, body `{"id":123,...}`.
2. Attacker (merchant "shop-a" itself, or anyone who can capture this request, e.g. via a browser dev proxy on their own tunnel/ngrok endpoint they control for testing) resends the exact same body and HMAC header to the app's webhook endpoint, but changes only `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as before; `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only — unchanged — and returns `true` [4](#0-3) .
4. `Registry.process` proceeds and invokes the handler with `shop: "shop-b.myshopify.com"` and the order data that actually belongs to shop-a [3](#0-2) .
5. If the host app trusts `data.shop` for tenant routing (as documented usage implies), shop-a's order data is now written/attributed under shop-b's tenant context.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
