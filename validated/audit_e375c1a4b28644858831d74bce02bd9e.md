### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` verifies solely the request body against the app's `client_secret`. The `shop` value, read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, is passed straight into `WebhookMetadata` and handed to the app's handler as the authoritative tenant identifier, without being bound by the signature.

### Finding Description
`to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38` signs only `@raw_body`: [1](#0-0) 

`shop` is read from a header that plays no part in that signable string: [2](#0-1) 

`Registry.process` validates only this body-only HMAC before dispatching to the handler with `request.shop` as the trusted tenant: [3](#0-2) 

The binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. Because the shared secret (`Context.api_secret_key`) is the same app-wide `client_secret` for every merchant using the app (not a per-shop secret), any merchant who has the app installed on their own shop can capture one legitimately signed webhook delivery (valid `raw_body` + valid `hmac`) and resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to any other shop's domain. `HmacValidator.validate` still succeeds because it only checks the body/secret, so `Registry.process` accepts the forged request and invokes the handler believing it is a genuine webhook for the victim shop, per the documented contract in `docs/usage/webhooks.md:12-30` that `data.shop` is "the shop domain of the webhook."

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: a request nominally scoped to shop A is delivered to app logic as if it belongs to shop B, with attacker-chosen `topic`, `shop`, and `webhook_id` metadata combined with attacker-controlled-but-signed `body` content from their own store. Any host app that (as documented) trusts `data.shop` to look up per-shop state, enqueue per-shop jobs, or attribute data will process a payload under the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be an unprivileged merchant who has installed the target app on their own shop (no special privileges, no access token, no admin access to the victim). They passively capture one webhook delivery Shopify sends them, then replay the same signed body with a modified `shop-domain` header to the app's public webhook endpoint. No secret material needs to be obtained.

### Recommendation
Bind the shop domain (and other metadata like `topic`/`webhook_id`) into the signed content, or otherwise verify that `request.shop` matches a shop expected to be delivering that specific request (e.g., cross-check against the endpoint or a per-shop lookup) before trusting it in `WebhookMetadata`. At minimum, document prominently that `data.shop` is not part of the HMAC-protected payload and must be independently corroborated by the host application before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid hmac of raw_body>`, and some `raw_body`.
3. Attacker resends the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` check in `Registry.process` (`Utils::HmacValidator.validate(request)`) passes, because validation only hashes `raw_body` — see: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, so app logic keyed on `data.shop` now operates against `victim.myshopify.com` using attacker-supplied body content.
