## Finding

Hyperbridge's `HandlerV2.sol` batches multiple independent POST requests / GET responses into a single delivery transaction, and — just like the referenced Mycelium `Vault.sol` plugin loop — a single bad element anywhere in that batch causes the *entire* transaction to revert, blocking delivery of every other valid message bundled alongside it.

### Title
One bad leaf in a batched `handlePostRequests`/`handleGetResponses` call reverts the whole batch, blocking delivery of all other valid requests/responses — (File: evm/src/core/HandlerV2.sol)

### Summary
`handlePostRequests` and `handleGetResponses` iterate over an array of MMR leaves representing independent cross-chain messages destined for potentially different application modules. Any single leaf that fails a per-item check (`InvalidMessageDestination`, `MessageTimedOut`, `DuplicateMessage`) causes an unconditional `revert`, aborting the whole call and every other leaf in the batch, even though those other leaves are individually valid and deliverable.

### Finding Description
In `handlePostRequests`, the first loop validates each leaf independently and `revert`s on the first failure: [1](#0-0) 

The second loop then checks for duplicates and dispatches, again reverting the whole call if any single leaf was already delivered: [2](#0-1) 

The same pattern exists in `handleGetResponses`, where an `UnknownMessage`/`DuplicateMessage` on any one leaf reverts the batch of GET responses: [3](#0-2) 

This mirrors the reported issue precisely: in Mycelium's `Vault.sol`, iterating over independent plugins and reverting the whole `deposit`/`_ensureLinkAmount` call on the first plugin failure blocks unrelated, otherwise-successful plugins. Here, iterating over independent requests/responses in one MMR proof and reverting on the first bad leaf blocks unrelated, otherwise-deliverable messages bound for different destination modules.

This is compounded by `IHandlerV2.batchCall`, which is explicitly documented and tested as atomic — any single inner call failing reverts the entire multi-message batch: [4](#0-3) [5](#0-4) 

Both the tesseract relayer and SDK deliberately batch multiple messages into single `handlePostRequests`/`batchCall` transactions for gas efficiency: [6](#0-5) [7](#0-6) 

Because delivery is permissionless, an attacker (or even an innocent third party) can pre-deliver a single leaf of a pending batch (e.g. front-run one POST request from the same MMR proof with a separate `handlePostRequests` call), which flips that leaf's state to `DuplicateMessage` for any subsequent inclusion. When the relayer's already-built batch transaction lands, the whole batch reverts — including all unrelated, still-valid requests bundled with it.

### Impact Explanation
Requests/responses have explicit `timeoutTimestamp`s. If a griefer can repeatedly force reverts of a relayer's batched delivery transaction (by pre-delivering one leaf, or by waiting for one leaf in the batch to expire), the relayer must re-derive and resubmit smaller batches, burning gas and time. If the relayer cannot get all messages delivered before their timeouts elapse, those requests time out and go through the refund/timeout path instead of successful delivery — this is a concrete "route unable to deliver messages" condition, and for time-sensitive cross-chain flows (e.g. token-gateway teleports, intents, LayerZero-style endpoints riding on top of ISMP `PostRequest`s) it can force fallback-to-timeout behavior or repeated re-delivery attempts, degrading availability of an otherwise-permissionless, unprivileged delivery path.

### Likelihood Explanation
Likelihood is meaningful but not high: it requires an attacker to identify a pending batch's leaf set (observable, since messages/proofs and MMR indices are public) and race a single-leaf `handlePostRequests` call ahead of the relayer's bundled transaction, or rely on natural races between relayers/self-relayers bundling overlapping leaves. Given `handlePostRequests` is fully permissionless and the SDK/relayer code explicitly supports self-relay and third-party relay of the same underlying MMR-proven requests, such races are plausible in practice, especially under gas-price competition or malicious griefing.

### Recommendation
Process each leaf/response in the batch independently with try/catch (or a low-level call to an isolated dispatch function) so a single leaf's `DuplicateMessage`/`MessageTimedOut`/`InvalidMessageDestination`/module-callback failure only skips that leaf (emitting a per-leaf failure event) instead of reverting the whole `handlePostRequests`/`handleGetResponses`/`batchCall` transaction. This preserves atomicity guarantees only where genuinely required (e.g., consensus updates) while making per-message delivery within a batch fault-isolated, consistent with the intended "permissionless, independent request delivery" model of ISMP.

### Proof of Concept
1. Relayer/self-relayer builds a `PostRequestMessage` containing leaves `[A, B, C]` from a single MMR proof, targeting three different destination modules, via `handlePostRequests`: [8](#0-7) .
2. Before this transaction lands, an attacker submits a separate `handlePostRequests` call containing only leaf `A` (using the same MMR proof/leaf data), successfully delivering `A` and setting `host.requestReceipts(A.hash())` to a non-zero relayer address.
3. The original transaction with `[A, B, C]` now hits `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` on leaf `A`: [2](#0-1) , reverting the whole call and preventing delivery of `B` and `C`, even though both remain valid and undelivered.
4. If `B` or `C`'s `timeoutTimestamp` elapses before a retry succeeds, they become permanently undeliverable via `handlePostRequests` and must be timed out instead — the message never reaches its destination module.

     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
