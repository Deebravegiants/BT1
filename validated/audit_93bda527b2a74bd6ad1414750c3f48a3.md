Audit Report

## Title
Unbounded in-memory `activeRequests` map in Gateway `confidentialrelay` handler allows attacker-driven memory exhaustion DoS - (File: `core/services/gateway/handlers/confidentialrelay/handler.go`)

## Summary
`HandleJSONRPCUserMessage` in the `confidentialrelay` handler creates an entry in `h.activeRequests` keyed by the caller-supplied `req.ID` with no authorization step and no bound on map size, only a duplicate-ID check. Combined with a periodic sweep that only reclaims entries after `requestTimeout` (default 30s), a caller who can reach this endpoint can grow the map without bound by sending unique IDs faster than the cleanup interval, unlike the codebase's own `RequestCache`, which enforces `maxCacheSize`.

## Finding Description
`HandleJSONRPCUserMessage` validates only that `req.ID` is non-empty and ≤200 chars, then immediately calls `h.newActiveRequest(req, labels, callback)` before any authorization or DON-facing validation: [1](#0-0) . `newActiveRequest` only rejects a duplicate `req.ID`; it has no cap on `len(h.activeRequests)`: [2](#0-1) . There is no `AuthorizeRequest`/allowlist/JWT check anywhere in this file — a grep of the handler for authorization-related identifiers returned no matches, confirming the map is populated purely from the caller-supplied `req.ID` with no gating logic in this handler. The only reclamation path is the periodic sweep bounded by `defaultCleanUpPeriod` (1s) and `h.requestTimeout` (default 30s): [3](#0-2) [4](#0-3) . This is in clear contrast to `RequestCache`, which enforces a configured `maxCacheSize` and rejects further inserts once full: [5](#0-4) .

I could not confirm from the code explored whether there is upstream authentication (JWT, mTLS, allowlist) gating access to the confidential-relay method at the gateway HTTP layer before `ProcessRequest` dispatches to `HandleJSONRPCUserMessage` — the gateway's `ProcessRequest` dispatcher itself performs no authorization, only ID-length and DON/service-name lookup, before calling the handler: [6](#0-5) . Regardless, within the `confidentialrelay` handler package itself, there is no authorization gate comparable to the vault handler's `requestProcessor.ProcessRequest` (allowlist/JWT check), which in the `vault` handler runs *before* `newActiveRequest` is called for the secrets methods: [7](#0-6) . Note this means the claim's assertion that "the identical pattern... exists in the vault handler" is only partially accurate: the vault handler's `MethodPublicKeyGet` path (cached aggressively, explicitly called out in the code comment as low-risk) can call `newActiveRequest` without authorization, but the higher-value secrets methods (`SecretsCreate/Update/Delete/List`) require successful `AuthorizeRequest` via allowlist or JWT before an `activeRequest` is created, meaning the vault handler is materially less exposed to this specific unauthenticated flooding vector than `confidentialrelay`.

## Impact Explanation
Growth of `h.activeRequests` is bounded only by the 30-second timeout sweep in the `confidentialrelay` handler, and each entry retains a copy of the request, a responses map, and metadata until swept, so a sustained flood of unique-ID requests can drive unbounded memory growth and lock contention on `h.mu`, degrading the shared Gateway process serving all DON workflows relying on confidential relay. This maps to a resource-exhaustion/availability impact against shared gateway infrastructure, which is a legitimate class of finding if the endpoint is reachable without meaningful cost to the attacker (i.e., unauthenticated or authenticated-but-uncostly).

## Likelihood Explanation
Likelihood depends critically on whether the confidential-relay JSON-RPC endpoint requires prior authentication/authorization at the gateway or connector layer — this could not be conclusively confirmed from the code explored (no `SECURITY.md`/`Researcher.md` scope details were reviewed, and the upstream HTTP/WS layer's auth wiring for this specific service was not fully traced). If the endpoint is reachable by any authenticated-but-otherwise-low-privilege caller (e.g., any onboarded workflow/DON member) without per-request cost, exploitation is straightforward: crafting unique `req.ID` values requires no proof-of-work or heavy computation. If instead the endpoint requires signed/authorized envelopes validated before reaching this handler, the practical exploitability is reduced to authenticated actors only.

## Recommendation
Add a configurable bound on `h.activeRequests` in the `confidentialrelay` handler (mirroring `RequestCache.maxCacheSize`), rejecting or backpressuring new request creation once the cap is reached, and consider applying a per-sender/global rate limiter on the user-facing request path (analogous to the existing `perNodeRateLimiters`/`globalNodeRateLimiter` used for node responses) so that request *creation*, not just node-response processing, is throttled. Clarify and, if absent, add explicit authentication/authorization gating for `HandleJSONRPCUserMessage` in this handler prior to any state allocation.

## Proof of Concept
1. Obtain access to send requests to the Gateway's confidential-relay JSON-RPC user endpoint (`MethodCapabilityExec`/`MethodSecretsGet`), per whatever preconditions the deployment's connector/HTTP layer imposes.
2. Send a high-rate stream of such requests, each with a freshly generated unique `req.ID` (≤200 chars), never consuming the response.
3. Observe `h.activeRequests` grow via `HandleJSONRPCUserMessage` → `newActiveRequest` (`core/services/gateway/handlers/confidentialrelay/handler.go:394-430`) faster than the 1-second sweep (`removeExpiredRequests`) can reclaim entries older than the 30-second `requestTimeout`, causing sustained memory growth — verifiable with a Go test exercising `handler.HandleJSONRPCUserMessage` in a loop with unique IDs and asserting `len(h.activeRequests)` grows unbounded before the timeout elapses.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalID]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalID{request.Body.Sender, request.Body.MessageID}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
	codec := api.JSONRPCCodec{}
	timer := time.AfterFunc(c.timeout, func() {
		err := c.deleteAndSendOnce(key, handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(request), ErrorCode: api.RequestTimeoutError})
		if err != nil {
			lggr.Errorw("failed to send timeout response", "error", err)
		}
	})
	c.cache[key] = &pendingRequest[T]{Callback: callback, responseData: responseData, timeoutTimer: timer}
	return nil
}
