Audit Report

## Title
Deferred termination-sweep in `RawMeter::try_into_deposit`/`Ext::charge` can drain a redeployed contract's balance to a stale termination beneficiary - (File: substrate/frame/contracts/src/storage/meter.rs)

## Summary
In classic `pallet-contracts`, terminating a contract removes its `ContractInfoOf` entry immediately (`substrate/frame/contracts/src/exec.rs:1363-1387`), but the actual balance sweep to the termination beneficiary and the `dec_consumers` call are deferred to the very end of the whole call stack via `RawMeter::try_into_deposit` (`meter.rs:395-408`) and `Ext::charge` (`meter.rs:540-607`). Because contract addresses are a deterministic function of `(deployer, code_hash, input_data, salt)` and independent of nonce (`substrate/frame/contracts/src/address.rs:55-67`), a new contract can be instantiated at the same address within the same call stack before the deferred sweep executes, causing the new contract's endowment/value to be swept to the old contract's beneficiary.

## Finding Description
`Frame::terminate` synchronously removes `ContractInfoOf` for the terminated account (`substrate/frame/contracts/src/exec.rs:1363-1387`), so a subsequent `instantiate` call within the same call stack passes the `DuplicateContract` guard in `ContractInfo::new` (which only checks `ContractInfoOf::<T>::contains_key`). `NestedMeter::terminate` (`meter.rs:465-476`) only records `own_contribution = Contribution::Terminated{ deposit: Refund(total_deposit), beneficiary }` — no balance moves at this point.

When a nested meter absorbs into its parent, this becomes a `Charge{contract, amount: Refund(...), state: Terminated{beneficiary}}` entry appended to `self.charges` (`meter.rs:325-344`). All such entries across the entire call stack are only executed once, at the very end, by `RawMeter::try_into_deposit` (`meter.rs:395-408`), which runs all `Refund` charges first and then all `Charge` charges — regardless of the chronological/nesting order in which they were recorded.

Meanwhile, `NestedMeter::charge_instantiate` (`meter.rs:436-463`) performs an **immediate**, non-deferred `T::Currency::transfer(origin, contract, ed, ...)` and `System::inc_consumers(contract)` when a new contract is instantiated — this happens synchronously during execution, not through the deferred `charges` list.

Consequently, if within one call stack a contract at address `A` is terminated (recording a deferred `Terminated{beneficiary}` refund) and then a new contract is instantiated at the same address `A` (same deployer/code_hash/input_data/salt), the new contract's ED and any subsequently transferred value land in account `A` before `try_into_deposit` runs. When the deferred `Refund`/`Terminated` branch of `Ext::charge` finally executes (`meter.rs:592-606`), it calls `System::dec_consumers(&contract)` and sweeps `T::Currency::reducible_balance(&contract, Preservation::Expendable, Polite)` — i.e., whatever is currently in the account, including the new contract's funds — to the stale `beneficiary`. This also erroneously decrements the consumer count that the new contract's `charge_instantiate` had just incremented.

No check exists in `try_into_deposit`, `absorb`, or `Ext::charge` to confirm that a `Terminated` charge's target account still refers to the same contract instance it was recorded for, nor is the beneficiary sweep scoped to the specific balance of that terminated instance.

## Impact Explanation
This allows fund extraction: the endowment/value sent to a freshly (re)instantiated contract at a reused address can be diverted to an attacker-chosen beneficiary set during an earlier termination in the same call stack, and the consumer-reference bookkeeping becomes inconsistent (a live contract's consumer count decremented). This breaks the accounting invariant that a live contract's balance corresponds to its own endowment/deposits, and matches an in-scope fund-loss impact for `pallet-contracts`.

## Likelihood Explanation
The exploit only requires ordinary, unprivileged contract-call primitives: a driver contract can (1) instantiate contract A with a chosen salt, (2) call A to invoke `seal_terminate(beneficiary)`, then (3) — still within the same call stack — instantiate a new contract with the identical `code_hash`/`input_data`/`salt` so the deterministic address matches A's former address, sending value/ED into it. The `ContractInfoOf::remove` happening synchronously at termination time, combined with address determinism independent of nonce, and the deferred refund/charge batching in `try_into_deposit`, make this concretely reachable and repeatable.

## Recommendation
Do not defer the termination beneficiary sweep or the `dec_consumers` call past the point where the same account id could be reused for a new live contract instance within the same call stack. Perform the sweep and consumer decrement synchronously at `seal_terminate` time (mirroring how `ContractInfoOf` removal is already synchronous), or otherwise prevent instantiation at an address that was terminated earlier in the same call stack until all deferred charges tied to that address have been fully settled.

## Proof of Concept
1. Deploy a "driver" contract `D` that: instantiates contract `A` via `instantiate_v2`/`seal_instantiate` with a fixed `code_hash`, `input_data`, and `salt`.
2. From `D`, call `A`, which invokes `seal_terminate(beneficiary)` with an attacker-controlled beneficiary.
3. Immediately afterward, still in `D`'s execution (same call stack), call `seal_instantiate` again with the identical `code_hash`/`input_data`/`salt`, transferring `value > existential_deposit` to the new contract `B`, which resolves to the same address as `A` (per `address.rs` formula, independent of nonce).
4. Let the extrinsic complete.
5. Assert: the resulting contract `B`'s free balance is less than `value + min_balance` (having been swept to the stale beneficiary from step 2), and/or the beneficiary's balance increased by more than `A`'s balance at termination time, demonstrating fund diversion from `B`.
