### Title
Webhook Shop Identity Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook HMAC verification only authenticates the raw HTTP body of an incoming webhook request. The `shop` (and `topic`/`api_version`/`webhook_id`) values are taken from unauthenticated HTTP headers and are never bound to the HMAC signature. This breaks the identity equation `shop authenticated == shop acted upon`: the HMAC proves "this body was signed by the app's secret," but the code trusts a completely separate, unsigned header to decide *which tenant* the body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only compares the HMAC against `to_signable_string`, i.e. the body — it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately forwards the unauthenticated `request.shop` value to the app's handler as the tenant identifier, alongside the (correctly authenticated) body: [4](#0-3) 

Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any shop's genuine webhook delivery (valid body + valid HMAC, generated legitimately by Shopify for that installer's own store) can be replayed by that same low-privilege merchant/attacker directly to the app's public webhook endpoint with only the `x-shopify-shop-domain` header changed to an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it never looked at the header), so `Registry.process` invokes the handler with `WebhookMetadata#shop` pointing at the victim tenant while `body` is attacker-controlled content from the attacker's own store's event. Any handler that uses `shop` to select the tenant record to create/update (a standard pattern for webhook consumers) will write or act on data under the victim's identity using attacker-supplied content — a cross-tenant identity confusion rooted entirely in this gem's verification logic, not a documented API misuse.

### Impact Explanation
This breaks the tenant boundary: the app-secret HMAC only proves "signed by this app," not "this data belongs to this shop." An unprivileged user who can install the app on their own shop (a low-privilege, self-service action) obtains a stream of validly-signed webhook bodies and can freely relabel which merchant they are attributed to when replayed to the app's endpoint. This is a cross-tenant access primitive against any app whose webhook handlers key state by `shop`, satisfying the Critical severity bar (cross-tenant access) defined for this assessment.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs to be able to install the target app on a shop they control (typical for public/self-serve apps) and send one HTTP POST to the app's known webhook URL with a modified header — no access to the app's `client_secret`, no TLS interception, and no privileged account is required.

### Recommendation
Bind the shop (and topic/webhook id) into the authenticated material, e.g. include the relevant header values in `to_signable_string`/the HMAC computation, or independently verify that the `shop` header corresponds to a shop with an active session/installation known to the app before trusting it, and never rely on unauthenticated headers to establish tenant identity for HMAC-"verified" requests.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a genuine webhook (e.g., `orders/create`) delivered to the app's public webhook endpoint with headers:
   `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker replays the exact same body/HMAC to the same endpoint, changing only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) passes because it only checks the untouched body.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, causing the app to act as if the victim shop produced that event.
