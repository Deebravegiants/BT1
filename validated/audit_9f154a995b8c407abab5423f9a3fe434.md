### Title
Unbounded `keys` array in `GetRequest` allows a single dispatched message to permanently block relayer delivery of the corresponding `GetResponse` - ([File: modules/ismp/core/src/handlers/response.rs], [File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchGet)` and the pallet-ismp `dispatch_request` path accept a `GetRequest` with an attacker-controlled, unbounded `keys: bytes[]` / `Vec<Vec<u8>>` array, with no cap enforced anywhere in the dispatch path. Responding to that request forces the relayer/coprocessor to run an unbounded per-key loop (`verify_state_proof`) to build the `GetResponse`, mirroring the reported "long for-loop -> DOS" pattern from DODORouteProxy, but here the loop length is chosen by the message's original sender rather than by whoever pays for the resulting computation.

### Finding Description
`EvmHost.dispatch(DispatchGet)` builds a `GetRequest` and simply forwards the caller-supplied `keys` array unchanged into the request commitment and event, with no length check: [1](#0-0) 

The same is true on the Substrate dispatcher, `dispatch_request`, which copies `dispatch_get.keys` verbatim into the `GetRequest` with no bound: [2](#0-1) 

When the response is eventually processed, `handlers/response.rs::handle` loops per Get request and, for each one, calls `state_machine.verify_state_proof(host, keys, ...)` with the full `keys` vector for that single request: [3](#0-2) 

The EVM state-machine's `verify_state_proof` implementation performs per-key work (grouping by contract, hashing each slot, proving each contract's account and every slot within it) with a cost that scales linearly (or worse, given the per-contract trie build) in the number of keys supplied — again with no cap on `keys.len()`: [4](#0-3) 

Grep of the codebase found no `MaxKeys`/`MaxStorageKeys`-style bound enforced at dispatch time for `GetRequest.keys` in either the EVM or Substrate dispatch paths, and the `#[pallet::weight(weight())]` annotation on `handle_unsigned` is a benchmark-derived declared weight, not a runtime-enforced cap tied to the actual number of keys embedded in a `GetRequest` that a relayer must re-submit as a `ResponseMessage`.

This is structurally the same bug class as the reported `mixSwap`/`_multiSwap` DOS: an attacker-controlled array length drives an unbounded loop of per-item work (decode, hash, verify-proof) inside a message-delivery/handler function. The key difference from the original report — and the reason this is weaker than a High/Critical — is that in DODORouteProxy the caller who pays gas is the same party forced to eat the unbounded loop, whereas here the party who *creates* the oversized request (the dispatching app/user) is not the party who must pay to *deliver* the response (the relayer, and ultimately the Hyperbridge chain's block-weight budget, since `handle_unsigned` executes the message during `validate_unsigned`).

### Impact Explanation
A GET request with an excessively large `keys` array can be dispatched cheaply from a source chain (the sender pays only for encoding the array, not for the destination-side proof verification cost). No relayer can ever build/submit a valid `ResponseMessage` for it if the required state proof (covering every requested key across every implicated contract) grows large enough to exceed:
- the EVM handler's practical gas budget (`handleGetResponses`/`verify_state_proof` cost on the Substrate side building the response), or
- the parachain's per-block weight limit for `handle_unsigned` (an unsigned, free extrinsic that executes messages inside `validate_unsigned`).

If the response can never be delivered, the outstanding `GetRequest` is stuck: it cannot time out cleanly if timeout processing itself also requires walking the same unbounded key set, and legitimate applications relying on that pending request are permanently blocked, matching the "route unable to deliver messages" impact category.

### Likelihood Explanation
Likelihood is Medium: the only prerequisite is that an unprivileged app/user dispatches a `DispatchGet` with a very large `keys` array (or an attacker abuses an app that forwards user-supplied keys, e.g., an intents/read-based integration). No governance or privileged role is required. It does require the attacker to pick a `keys.len()` large enough to exceed practical delivery limits, which is a straightforward, deterministic griefing action rather than a probabilistic exploit.

### Recommendation
- Enforce a maximum number of keys per `GetRequest` (and/or a maximum aggregate key-bytes size) at dispatch time in both `EvmHost.dispatch(DispatchGet)` and `pallet_ismp::dispatcher::dispatch_request`, rejecting requests above the bound before a commitment is stored.
- Alternatively/also, scale the relayer fee and/or bandwidth-gate cost charged at dispatch time proportionally to `keys.len()` so an attacker cannot externalize the response-side verification cost onto relayers/block-weight for a flat fee.
- Ensure `handle_unsigned`'s declared weight is derived from the actual message content (number of keys/requests) rather than a fixed benchmark, so oversized batches are rejected by `CheckWeight`/`validate_unsigned` rather than silently attempted.

### Proof of Concept
1. Deploy/target an app on chain A that calls `IDispatcher(host).dispatch(DispatchGet)` (e.g. the reference test contracts `TestDispatcher.sol` / `HyperGet.sol`) with a `keys` array containing N (e.g. 50,000) valid 52-byte storage keys pointing at many distinct contracts on destination chain B.
2. The dispatch succeeds and a commitment is stored on chain A's `EvmHost` with no rejection, per `EvmHost.dispatch(DispatchGet)`.
3. A relayer attempting to fulfill the request must, on Hyperbridge, run `handlers/response.rs::handle`, which calls `dest_state_machine.verify_state_proof` with all N keys grouped per contract — this either exceeds practical gas/weight to construct and submit the `ResponseMessage`, or the resulting `handle_unsigned` extrinsic exceeds the parachain block weight limit and is rejected/never includable.
4. The `GetRequest` remains permanently pending: relayers cannot deliver a response, and (depending on timeout-handling implementation) may be unable to cleanly time it out either, leaving the requester's escrowed fee and any dependent application logic stuck indefinitely.

pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	// Reject repeats before doing any work at all. They are already an error — repeats collapse
	// in the map returned below, so the caller's key-count check fails — but reaching that
	// check means every repeat has been verified first, and for account queries that is a
	// clone of the whole contract proof each time.
	let mut seen_keys = BTreeSet::new();
	for key in &keys {
		if !seen_keys.insert(key.as_slice()) {
			return Err(EvmStateMachineError::DuplicateKey.into());
		}
	}

	let evm_state_proof = decode_evm_state_proof(proof)?;
	let mut map = BTreeMap::new();
	let mut contract_to_keys = BTreeMap::new();
	let mut contract_account_queries = Vec::new();

	// Group keys by the contract address they belong to
	for key in keys {
		// For keys that are 52 bytes we expect the first 20 bytes to be the contract address and
		// the last 32 bytes the slot hash.
		// For keys that are 20 bytes we expect that to the
		// contract or account address.
		// For keys that are 32 bytes we expect that to be a slothash in
		// the Ismp EVM host
		let contract_address = if key.len() == 52 {
			H160::from_slice(&key[..20])
		} else if key.len() == 32 {
			ismp_address
		} else if key.len() == 20 {
			contract_account_queries.push(H160::from_slice(&key));
			continue;
		} else {
			return Err(EvmStateMachineError::UnsupportedKeyLength.into());
		};
		let entry = contract_to_keys.entry(contract_address.0.to_vec()).or_insert(vec![]);

		let slot_hash = if key.len() == 52 {
			H::keccak256(&key[20..]).0.to_vec()
		} else {
			H::keccak256(&key).0.to_vec()
		};

		entry.push((key, slot_hash));
	}

	// The storage proof must correspond exactly to the contracts a key was requested from:
	// every one covered, and nothing else. Both directions are settled here, before a single
	// entry is resolved — resolving one clones the whole contract proof and rebuilds its trie,
	// so checking as we go would let a proof padded with unrequested accounts do that work
	// before being rejected, and would make which error surfaces depend on map ordering.
	// The honest prover already emits exactly this set, deriving its map from the requested
	// keys, so nothing legitimate is turned away.
	let result = contract_to_keys
		.clone()
		.into_keys()
		.all(|contract| evm_state_proof.storage_proof.contains_key(&contract));
	if !result {
		return Err(EvmStateMachineError::IncompleteStorageProof.into());
	}

	if evm_state_proof
		.storage_proof
		.keys()
		.any(|contract| !contract_to_keys.contains_key(contract))
	{
		return Err(EvmStateMachineError::UnrequestedContractProof.into());
	}

	for (contract_address, storage_proof) in evm_state_proof.storage_proof {
		// Unreachable: the correspondence check above already rejected any entry without a
		// requested key. Kept as a hard error rather than a skip so the invariant survives if
		// that check is ever moved or relaxed.
		let Some(keys) = contract_to_keys.remove(&contract_address) else {
			return Err(EvmStateMachineError::UnrequestedContractProof.into());
		};

		let contract_root = get_contract_account::<H>(
			evm_state_proof.contract_proof.clone(),
			&contract_address,
			root,
		)?
		.storage_root
		.0
		.into();

		let slot_hashes = keys.iter().map(|(_, slot_hash)| slot_hash.clone()).collect();
		let values = get_values_from_proof::<H>(slot_hashes, contract_root, storage_proof)?;
		keys.into_iter().zip(values).for_each(|((key, _), value)| {
			map.insert(key, value);
		});
	}
