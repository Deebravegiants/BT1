### Title
Incomplete secret redaction allows sensitive request-body fields (tokens, keys, secrets) to be written to Debug logs - (File: core/web/router.go)

### Summary
The Chainlink node's HTTP request logging middleware (`loggerFunc` in `core/web/router.go`) logs the full JSON body of every incoming API request at Debug level, applying only a narrow redaction filter (`isBlacklisted`) that matches on the substring `"password"`. Any other sensitive field name in a request body — e.g. `secret`, `token`, `apiSecret`, `keyJSON`, `privateKey` — is not redacted and will be written verbatim into node logs whenever Debug logging is enabled, mirroring the CWE-532 "improper log output" class described in the Spinnaker advisory (full/verbose logging unintentionally capturing credentials).

### Finding Description
`loggerFunc` reads and buffers the entire request body, then calls `readBody`/`readSanitizedJSON` to produce a log-safe representation before emitting it via `lggr.Debugw(...)`: [1](#0-0) 

`readSanitizedJSON` only redacts top-level JSON keys matched by `isBlacklisted`, and `isBlacklisted` only matches `"password"`-related key names: [2](#0-1) 

Because the blacklist is a hardcoded, narrow list (`password`, `newpassword`, `oldpassword`, `current_password`, `new_account_password`) and only inspects the top level of the JSON object (nested objects/arrays are copied through unfiltered), any other credential-bearing field sent in a request body — such as encrypted keystore blobs (`keyJSON`) submitted when importing ETH/CSA keys, API secrets, bearer tokens embedded in JSON payloads, or any future endpoint field not named literally "password" — is logged in full whenever the Debug log level is active. This is structurally the same root cause as the Spinnaker advisory: logging infrastructure that unconditionally captures full request content without a comprehensive secret-redaction scheme, so any sensitive field not explicitly enumerated leaks into log storage/log-forwarding systems (including the optional `AuditLogger` HTTP forwarder, which also has no additional filtering and forwards logged data externally).

### Impact Explanation
An operator who enables Debug logging (a normal operational action, exposed via the `/v2/log` `LogController.Patch` endpoint) will have sensitive request-body content persisted to disk/log aggregation for every subsequent API call, including any secret material submitted by any authenticated user (not just admins) whose field name doesn't happen to be "password". This can expose encrypted key material, tokens, or other credentials to anyone with log access (ops teams, log-forwarding third parties, or a compromised log pipeline), consistent with the "confidentiality: low" impact rated in the reference CVE.

### Likelihood Explanation
Likelihood is moderate: it requires Debug-level logging to be enabled (a supported, documented configuration/runtime option, not a rare edge case) and a request containing a non-"password"-named secret field. Since redaction logic is a static, incomplete allowlist-by-exclusion, it will silently fail to protect any new or existing endpoint field that carries sensitive data but isn't named "password", making this a systemic gap rather than a one-off.

### Recommendation
- Replace the substring/exact-match "password" blacklist with a broader, explicit deny-list (or better, an allow-list) covering common secret-bearing field names (`secret`, `token`, `apiSecret`, `apiKey`, `keyJSON`, `privateKey`, `mnemonic`, etc.).
- Recursively sanitize nested JSON objects/arrays, not just top-level keys.
- Consider disabling full-body request logging by default, or gating it behind an explicit, clearly-documented opt-in separate from generic Debug logging, given the risk of forwarding logs to external audit sinks (`AuditLogger.ForwardToUrl`).

### Proof of Concept
1. Enable Debug logging via `PATCH /v2/log` with `{"level":"debug"}` (see `LogController.Patch`): [3](#0-2) 
2. Submit any authenticated POST/PUT/PATCH request whose JSON body contains a sensitive field not named "password", e.g. importing an encrypted key with `{"keyJSON": "<encrypted-private-key-blob>"}`.
3. Observe that `loggerFunc` logs the request body field verbatim (only `password`-named keys are replaced with `*REDACTED*`), persisting the sensitive value into node logs and, if `AuditLogger.ForwardToUrl` / log shipping is configured, into external log storage.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
