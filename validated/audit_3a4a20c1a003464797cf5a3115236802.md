### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that gets attributed to an inbound webhook from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header, while the HMAC signature that `Registry.process` validates only covers the raw request body. This breaks the binding: `hmac_verified_bytes == raw_body` but `tenant_identity_used_by_handler == request.shop`, and `shop` is never included in the signable string.

### Finding Description
`Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body** (`@raw_body`) — the `shop`, `topic`, `api_version`, and `webhook_id` header values are excluded from what is signed: [3](#0-2) 

Yet immediately after the HMAC check passes, `Registry.process` uses `request.shop` (parsed from the unauthenticated header) as the tenant identity handed to the app's webhook handler: [1](#0-0) 

This is the exact bug class from the report generalized to this gem: a field (`shop`) is *acted on* (used to route/attribute webhook data to a tenant) but is *not covered by the HMAC* that authenticates the request — analogous to the AmAmm bug where a state transition path skipped a check that other paths enforced. Here, the body-authenticity check is enforced, but the tenant-binding check is silently absent, so `hmac_valid(body) == true` does not imply `shop_header_authentic == true`.

**Exploit path (unprivileged internet user):** An attacker who legitimately installs the target app on their own shop (ordinary, unprivileged action — any Shopify Partner/dev store) will receive real webhook deliveries from Shopify with a valid `X-Shopify-Hmac-Sha256` computed over the body using the app's shared `client_secret`. The attacker captures one such delivery (body + valid HMAC) and replays it to the app's webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. Because the HMAC only signs the body (unchanged), `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain.

### Impact Explanation
This crosses a tenant boundary using only an unprivileged capability (installing/using the app on one's own shop) to forge webhook events "from" a different, victim shop. Any host application that uses `data.shop` from `WebhookMetadata` to select the tenant record to update (a documented, expected usage pattern of this gem, not a misuse) can be made to attribute attacker-controlled payload data to a different merchant's account — e.g., writing/replacing data keyed by victim's shop, or triggering shop-scoped side effects (like `shop/redact`, order/customer updates) against the wrong tenant. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High. It requires no secrets, tokens, or privileged access — only the ability to install the target app once (a normal, often self-serve action for public/dev-store testing) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-controlled headers, which is trivial for any internet-reachable webhook route.

### Recommendation
Include `shop` (and ideally `topic`) as part of the HMAC-covered signable content, or independently verify that the `shop` header corresponds to a shop the app has installed/expects for this delivery before trusting it for tenant routing, mirroring how `AuthQuery#to_signable_string` correctly folds `shop` into its signed payload: [4](#0-3) 

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop and captures a legitimate webhook delivery.
captured_body = '{"id": 123, "note": "legit order"}'
captured_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, captured_body)
)

# Step 2: Attacker replays the exact same body+HMAC but swaps the shop-domain header to the victim.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,      # still valid: HMAC only covers the body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# HMAC validation succeeds because it only checks captured_body against captured_hmac.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle called with data.shop == "victim-shop.myshopify.com",
#    even though this payload never originated from that shop.
```
