Webhook tenant identity (`shop`) is derived from an unauthenticated header, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying an HMAC over the raw request body, then trusts the `shop` value taken from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header — a value that is never included in the HMAC-signed content — and passes it downstream to the host application's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, and then, having authenticated *only the body*, forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` for the handler to use as the tenant/shop identity: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unvalidated `String` field, and the documented usage pattern shows apps using `data.shop` directly to key their per-tenant data (e.g., enqueuing background jobs keyed by `shop_domain: data.shop`): [4](#0-3) [5](#0-4) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` should imply `shop == the actual originating shop`, but the equality the gem actually enforces is only `hmac == HMAC(secret, body)`; `shop` is fully attacker-controllable independent of that check, because `VerifiableQuery#to_signable_string` for this request type only commits to `@raw_body`: [6](#0-5) 

Since a single app-wide `api_secret_key` signs webhooks for every shop that installs the app, an attacker who controls (or has previously installed) one shop on the same app can capture (or construct, if the body content is attacker-influenceable, e.g., via a webhook topic whose payload the attacker can shape) a validly HMAC-signed body from *their own* shop, then replay that raw body with a forged `shopify-shop-domain` / `x-shopify-shop-domain` header pointing at a *victim* shop. `Registry.process` will pass HMAC validation (since it only checks the body) and hand the handler `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with a legitimate (even free/trial) installation of the app can cause the host application to process an attacker-supplied event under a victim shop's identity. Depending on how the host app's handler uses `data.shop` (e.g., to look up the corresponding session/access token and act on the victim's store, or to write attacker-controlled body content into per-shop records keyed by `data.shop`), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant's data — satisfying the "cross-tenant access" criterion, since the tenant boundary (`shop`) is not actually bound to the authenticated bytes.

### Likelihood Explanation
Reachability is high for any app using this gem's documented `Registry.process` / `WebhookHandler` pattern exactly as shown in `docs/usage/webhooks.md`. The only requirement is that the attacker be able to install the app on at least one shop (a standard, low-privilege action for any Shopify merchant/developer) and be able to submit an HTTP request to the app's webhook endpoint with a forged shop header — no access token, `client_secret`, or elevated privilege is required.

### Recommendation
Include the shop domain (and topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the verified payload before trusting it — e.g., have `to_signable_string` incorporate the shop header value, or independently verify that the shop claimed in the header matches a shop that Shopify's signature actually vouches for. At minimum, document prominently that `data.shop` must not be trusted as authenticated tenant identity without additional verification, since today the gem effectively presents it as verified (it's returned only after `Utils::HmacValidator.validate(request)` succeeds).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a valid webhook for a topic they control the payload of (or simply captures any legitimate webhook body/HMAC pair sent to their own shop's endpoint).
2. Attacker sends a POST to the app's registered webhook endpoint with:
   - `raw_body` = the exact bytes from the captured legitimate webhook (so the HMAC still validates).
   - `X-Shopify-Hmac-Sha256` = the original valid signature for that body.
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (forged).
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version` = arbitrary/original values.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`: [7](#0-6) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-influenced body>, ...)` and processes it as if it were a genuine event from the victim shop.

**Note on scope/verification limits:** I was not able to inspect the entirety of `Utils::HmacValidator` beyond the code already shown (its `validate`/`validate_signature` methods, confirmed to hash only `to_signable_string`), nor any host-app-side mitigations that might exist outside this gem. The severity in practice depends on what the specific webhook topic payload contains and whether the host app treats `data.shop` as authenticated — but the gem itself provides no protection against this header/body decoupling, which is the root cause identified here.
