## Title
Unchecked ERC-20 return value in `withdraw()`/`SweepDust` allows silent transfer failures to permanently freeze escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (Tron variant) settles cross-chain `RedeemEscrow`/`RefundEscrow` requests by moving tokens out of escrow with a raw low-level `.call` to `IERC20.transfer`, checking only that the call itself did not revert — not that the ABI-decoded boolean return value is `true`. The same pattern is used in the `SweepDust` handler. This mirrors the reported bug class (ERC-20 boolean return values not checked after a token operation), but here it applies to `transfer` rather than `approve`.

### Finding Description

and in the `SweepDust` branch of `onAccept`: [2](#0-1) 

Both only check `success` from the low-level `.call`, which is `true` as long as the callee didn't revert — it does not verify the decoded `bool` return data. Any ERC-20/TRC-20 token that returns `false` on failure instead of reverting (a common non-standard but legal implementation, and notably common among Tron TRC20 tokens, which is presumably why this file avoids `SafeERC20`/`safeTransfer` used elsewhere) will pass this check even though no tokens were actually moved.

Critically, in `withdraw()`, `_orders[body.commitment][token] -= amount;` runs unconditionally right after the "successful" transfer attempt, so escrow accounting is decremented regardless of whether the beneficiary actually received the tokens. This is invoked from `onAccept` for `RequestKind.RedeemEscrow`/`RefundEscrow`, which is the code path that processes an incoming, authenticated Hyperbridge message settling a cross-chain intent — i.e., it is reachable via the normal relayed-message delivery flow, not an admin-only path.

### Impact Explanation
If the escrowed token silently fails a transfer (returns `false`), the beneficiary never receives their funds, yet the contract's internal accounting (`_orders`) is decremented as though the withdrawal succeeded. The tokens remain locked in the `IntentGatewayV2` contract with no accounting entry pointing to them and no way to re-trigger `withdraw` for that commitment (guarded by `_filled`/`_orders == 0` checks), resulting in a permanent freezing/loss of user or solver funds. This directly matches the "permanent freezing of funds" impact category.

### Likelihood Explanation
Exploitation does not require attacker privilege beyond using or influencing which token is escrowed for an order — since intents on this gateway can involve arbitrary ERC-20 tokens configured by users/solvers, encountering (or intentionally choosing) a non-reverting-on-failure token, or one that returns `false` under specific conditions (e.g., blacklist/pausable tokens), is realistic and does not require any special access, only a normal order placement/fill/redeem flow through the existing dispatch/authenticate machinery.

### Recommendation
Decode and require the boolean return value (or adopt OpenZeppelin's `SafeERC20.safeTransfer`, already imported and used elsewhere in this file via `using SafeERC20 for IERC20;`) for both the `withdraw()` and `SweepDust` transfer paths, so a token that returns `false` reverts the whole request instead of silently succeeding and desynchronizing internal accounting from actual token balances.

### Proof of Concept
1. A user places an order whose input/output token is an ERC-20 that returns `false` (rather than reverting) when a `transfer` call fails (e.g., due to a paused/blacklisted state at settlement time).
2. The order proceeds through Hyperbridge; a valid `RedeemEscrow`/`RefundEscrow` request is delivered and authenticated, calling `withdraw()`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (external call did not revert) but the decoded boolean payload is `false`, meaning the beneficiary's balance is unchanged.
4. The check `if (!success) revert TransferFailed();` passes, and `_orders[body.commitment][token] -= amount;` executes, permanently zeroing out the escrow record for those tokens while the tokens remain stuck in the contract and unrecoverable by the beneficiary.
