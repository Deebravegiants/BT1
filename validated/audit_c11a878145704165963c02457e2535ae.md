This confirms the identity binding break: `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns only `@raw_body`, and `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) verifies the HMAC exclusively over that raw body. The `shop-domain` header, exposed via `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`), is never part of the signed content. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) validates the HMAC and then forwards `request.shop` — sourced from this unauthenticated header — directly into `WebhookMetadata` as the tenant identifier used by the host app's handler.

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw JSON body; the `shop-domain`, `topic`, and `webhook-id` headers are excluded from the HMAC computation, yet `shop-domain` is trusted as the authoritative tenant identifier passed to the app's webhook handler.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `OpenSSL::HMAC.hexdigest` over `request.to_signable_string` — i.e., `@raw_body` only [1](#0-0) . Meanwhile `request.shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header verbatim, with no cryptographic binding to that value [2](#0-1) . After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and dispatches it to the registered handler [3](#0-2) .

The binding that should hold is: `shop_that_HMAC_authenticates == shop_the_handler_acts_on`. Because the signature only covers the body bytes, and the shop identity is read from a separate, unsigned header, these two values are not bound together. Any request whose body byte-for-byte matches a previously HMAC'd payload (from any topic/shop this gem's consumer has ever received, since HMAC is computed with the same shared `api_secret_key` for the whole app across all shops) will pass `HmacValidator.validate` regardless of what `shop-domain` header accompanies it.

### Impact Explanation
An attacker who can capture one valid `(raw_body, hmac)` pair delivered by Shopify to the app (e.g., by installing the app on their own shop and observing/replaying their own legitimately-received webhook) can resend that exact body with the `hmac-sha256` header intact but an arbitrary `shop-domain` header substituted. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming a different shop than the one the payload actually originated from. Host applications that use `WebhookMetadata#shop` to select which tenant's data store to write to (a documented, expected usage pattern) will attribute/act on the payload under the wrong tenant, producing cross-tenant data leakage or corruption — the request crosses a tenant boundary despite technically passing this gem's own signature check.

### Likelihood Explanation
Any merchant who installs the target app can trivially obtain their own legitimately-signed webhook body/HMAC pair (since Shopify sends real webhooks to every installed shop), then replay it toward the endpoint with a forged `shop-domain` header — no access to `api_secret_key`, access tokens, or privileged accounts is required, only the ability to send an arbitrary HTTP POST to the app's public webhook endpoint, which this gem does not otherwise restrict by source IP or mutual TLS.

### Recommendation
Include the tenant-identifying header (`shop-domain`) and other security-relevant headers (`topic`, `webhook-id`) in the signed content, or otherwise cryptographically bind them to the HMAC'd body before trusting `request.shop` in `Registry.process`, so that the shop the signature authenticates is provably the same shop the handler acts upon.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook Shopify sends: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) ; since validation only checks `B` against `H`, it succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` [5](#0-4)  even though the payload actually originated from `attacker.myshopify.com`, and the handler processes it as if it belongs to the victim tenant.
