### Title
Browser-side `describeWithdrawal` reports `completed` with BTC `pending_sign_id` that can diverge from the true final tx hash - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
For UTXO (BTC) landing chains, `OmniBridge.describeWithdrawal` returns `{status: "completed", txHash: transfer.utxo_meta?.pending_sign_id}` when running in a browser environment, instead of waiting for `transfer.finalised?.transaction_hash`. Since `watchWithdrawal`'s poll loop terminates as soon as `status === "completed"`, an integrator polling from the browser can be handed a `pending_sign_id` that the code's own comment says "may change if the BTC transfer fails to be submitted," with no subsequent re-check against the real finalized hash.

### Finding Description
The broken equality: reported `txHash` for a BTC withdrawal must equal the eventual on-chain finalized BTC transaction hash (`transfer.finalised.transaction_hash`). In the browser branch, `describeWithdrawal` (packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:714-721) instead returns `transfer.utxo_meta?.pending_sign_id`, which the adjacent comment explicitly documents as *not* the finalized hash and subject to change on resubmission.

`watchWithdrawal` (packages/intents-sdk/src/core/withdrawal-watcher.ts:43-47) treats any `status === "completed"` response as terminal and returns `{hash: status.txHash}` to the caller, ending the poll loop. There is no mechanism causing the SDK to later re-poll and reconcile `pending_sign_id` against `finalised.transaction_hash` for a call that already returned `"completed"`. This is a genuine status/hash misreport: a "completed" status is returned before actual finality is confirmed, and the reported identifier can silently become stale/wrong with no correction path through this SDK call.

No guard in the codebase (`validateAddress`, `compareAddresses`, `assert` checks, etc.) addresses this — it's purely a status-semantics issue in `describeWithdrawal`'s branch selection, not an address/amount/signature validation gap.

### Impact Explanation
An integrator (unprivileged, using the SDK exactly as documented, in a browser context) that credits/reconciles a withdrawal based on the SDK's reported "completed" `txHash` may end up tracking a BTC hash (`pending_sign_id`) that never confirms on-chain, while the real settled transaction has a different hash (`finalised.transaction_hash`). This matches the "High" category: "a status or hash misreport making an integrator credit or refund twice" / "a withdrawal stuck until manual intervention" — reconciliation against the real chain would require manual intervention since the SDK's own polling already terminated.

### Likelihood Explanation
Preconditions: BTC/UTXO landing chain, code executing in a browser (`typeof window !== "undefined"`), and the rare-but-documented case where the initial BTC broadcast fails and a new transaction/`pending_sign_id` is created. This is explicitly called out in the source comment as a known, real (if rare) occurrence — not a theoretical edge case. No attacker action is required at all; this triggers from the bridge/relayer's own resubmission behavior on an ordinary withdrawal, and any browser-based integrator polling `watchWithdrawal` for a BTC withdrawal is exposed every time this resubmission occurs.

### Recommendation
In the browser branch, do not report `status: "completed"` based solely on `pending_sign_id`. Either: (a) always use `transfer.finalised?.transaction_hash` for the terminal "completed" status regardless of environment, returning `"pending"` until finality is available, or (b) introduce a distinct intermediate status (e.g., `"pending_broadcast"` with the tentative hash) that `watchWithdrawal` does not treat as terminal, so polling continues until `finalised.transaction_hash` is available and only that value is ever returned as the final, authoritative hash.

// vitest, mocking only HTTP (omniBridgeAPI.getTransfer)
it("browser path reports pending_sign_id as completed even though finalised hash differs", async () => {
  vi.stubGlobal("window", {}); // simulate browser env

  const bridge = new OmniBridge(/* ...deps with mocked omniBridgeAPI */);
  bridge.omniBridgeAPI.getTransfer = vi.fn().mockResolvedValue([
    {
      recipient: "btc:some-btc-address",
      utxo_meta: { pending_sign_id: "A" },
      finalised: { transaction_hash: "B" }, // simulates resubmission producing a different final hash
    },
  ]);

  const result = await bridge.describeWithdrawal({
    landingChain: ChainKind.Btc,
    index: 0,
    withdrawalParams: {/* ... */},
    tx: { hash: "near-tx-hash" },
  });

  // Broken equality check:
  expect(result.status).toBe("completed");
  expect(result.txHash).toBe("A");       // what SDK reports (pending_sign_id)
  expect(result.txHash).not.toBe("B");   // true finalised.transaction_hash never surfaced
});
