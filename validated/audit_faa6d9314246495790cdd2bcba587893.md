Because Shopify webhook HMACs are computed with the app's single shared `client_secret` (identical for every shop that installs the app, confirmed by `Context.api_secret_key` usage) rather than a per-shop secret, any merchant who installs the app can capture one of their own legitimately-signed webhook deliveries and replay it with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain — the HMAC over the untouched raw body still validates, and the handler executes believing it is processing data for the victim shop.

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw body via `to_signable_string`, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used to route and attribute the webhook are taken from unauthenticated headers and never enter the HMAC computation.

### Finding Description
`Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` [5](#0-4) , which recomputes an HMAC over `verifiable_query.to_signable_string` — for `Webhooks::Request` this is defined as just `@raw_body` [1](#0-0) . The `shop` accessor, however, is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header with no cryptographic binding to the body or the signature [6](#0-5) . After validation succeeds, `Registry.process` builds `WebhookMetadata` directly from this unauthenticated `request.shop` and hands it to the app's handler [7](#0-6) . This breaks the equality that should hold: `shop authenticated by HMAC == shop the handler acts on`. Since the HMAC secret is the app's single `client_secret` (`Context.api_secret_key`), the same secret is used to sign webhooks for every shop that installs the app, so a valid signature from one tenant's webhook delivery is equally valid when the `shop-domain` header is swapped for a different tenant's domain.

### Impact Explanation
This is a cross-tenant data integrity issue: an unprivileged existing merchant of a multi-tenant app can trick the app's webhook handler into processing attacker-controlled payloads as if they originated from a different (victim) shop, because the shop identity is never bound by the HMAC that the library considers sufficient proof of authenticity.

### Likelihood Explanation
Any user who can install the app on a shop (i.e., any Shopify merchant) can obtain a validly-signed webhook body/HMAC pair and replay it with a modified `shop-domain` header value; no special privileges, secrets, or access tokens beyond normal app installation are required.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) into the signed material, or otherwise cross-check the header-derived `shop` in `Webhooks::Request` against a shop known/expected by the application (e.g., via a registered session) before dispatching to the handler, rather than trusting header values that are outside the HMAC's coverage in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw HTTP request, including its valid `X-Shopify-Hmac-Sha256` header and raw body.
2. Replay the exact same request to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
3. `HmacValidator.validate` still succeeds because it only checks the raw body [3](#0-2) , and `Registry.process` invokes the handler with `WebhookMetadata` claiming `shop: "victim.myshopify.com"` [7](#0-6) , causing the app to act on attacker-supplied data under the victim tenant's identity.
