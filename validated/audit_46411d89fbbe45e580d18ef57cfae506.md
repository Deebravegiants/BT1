### Title
`createWithdrawalIntents` skips the fee-exceeds-amount check that `estimateWithdrawalFee` performs, allowing a negative/underflowed withdrawal amount to be signed - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK._estimateWithdrawalFee` validates that a `feeInclusive` withdrawal amount is greater than the estimated fee before calling `bridge.validateWithdrawal`, throwing `FeeExceedsAmountError` otherwise. `IntentsSDK.createWithdrawalIntents`, which is a separately callable public method that also computes `actualAmount = amount - feeEstimation.amount` for `feeInclusive` withdrawals, does not perform this same check before handing the amount to `bridge.validateWithdrawal` / `bridge.createWithdrawalIntents`.

### Finding Description
In `_estimateWithdrawalFee`, the SDK explicitly guards against the fee exceeding the withdrawal amount: [1](#0-0) 

However `createWithdrawalIntents` performs the identical subtraction without any equivalent guard: [2](#0-1) 

`createWithdrawalIntents` is a public SDK method that accepts an arbitrary `feeEstimation` object supplied by the caller (not necessarily the one just returned by `estimateWithdrawalFee` for the current `amount`). If a caller supplies (or a stale/cached) `feeEstimation.amount` that is greater than or equal to `withdrawalParams.amount` while `feeInclusive` is `true`, `actualAmount` becomes zero or negative (as a `bigint`, this is a genuine negative value, not a wrapped/overflowed unsigned integer). This value is then passed into `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`, which construct and sign intent primitives such as `ft_withdraw`/`mt_withdraw` using `amount.toString()`, e.g. in `omni-bridge-utils.ts`: [3](#0-2) 
and the analogous HOT bridge path: [4](#0-3) 

This breaks the intended equality that the signed withdrawal amount must equal `requested amount - fee` and be non-negative/sane. Because none of the bridge-level `validateWithdrawal` implementations I could inspect (`omni-bridge.ts`, `poa-bridge.ts`) re-derive or re-check `amount > 0` against the fee prior to constructing the intent (they check destination-address/min-amount rules, not the fee-vs-amount relationship), a negative `actualAmount` is not caught before an intent payload is built.

### Impact Explanation
If reachable with a genuinely stale or attacker-influenced `feeEstimation` (e.g., a caller/integrator reusing an old fee quote against a smaller amount, or race conditions between quote and submission), the resulting signed intent could carry an amount inconsistent with what the user actually intended to withdraw net of fees — either producing an invalid on-chain call that reverts, or in the worst case an underflowed/negative amount that is serialized incorrectly, causing an overcharge or a malformed withdrawal. This matches the "fee error draining a material share of the amount" / "fee overcharge" class of High/Critical impact called out in the rules, since the very check meant to prevent exactly this exists in the sibling method (`_estimateWithdrawalFee`) but is missing here.

### Likelihood Explanation
Likelihood depends on whether SDK consumers are expected to always pass a freshly computed `feeEstimation` from `estimateWithdrawalFee` into `createWithdrawalIntents` for the same `amount`. I could not find in-repo documentation strictly enforcing this pairing, and `createWithdrawalIntents` is exported as an independent public API taking `feeEstimation` as a caller-supplied argument, so the missing validation is directly reachable by any integrator/caller without needing a malicious relayer, bridge, or admin.

### Recommendation
Add the same `FeeExceedsAmountError` guard in `createWithdrawalIntents` that exists in `_estimateWithdrawalFee`:
```ts
if (args.withdrawalParams.feeInclusive) {
  if (args.withdrawalParams.amount <= args.feeEstimation.amount) {
    throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
  }
}
```
placed before computing `actualAmount` in `packages/intents-sdk/src/sdk.ts`'s `createWithdrawalIntents`.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents({ withdrawalParams: { amount: 100n, feeInclusive: true, ... }, feeEstimation: { amount: 150n, ... } })` directly (skipping/bypassing a fresh `estimateWithdrawalFee` call, or using a stale fee estimation object).
2. Observe `actualAmount = 100n - 150n = -50n` computed at `packages/intents-sdk/src/sdk.ts:342-344`, with no throw.
3. This negative `actualAmount` flows into `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`, producing a malformed/negative amount in the constructed intent (e.g., `amount.toString()` in `omni-bridge-utils.ts:68` or `hot-bridge.ts:230`), whereas the equivalent path through `estimateWithdrawalFee` (`sdk.ts:421-428`) would have thrown `FeeExceedsAmountError` for the same inputs.
