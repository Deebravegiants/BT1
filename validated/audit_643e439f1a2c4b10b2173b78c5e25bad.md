### Title
Pool repay accepts unfunded repayment messages and refunds the declared overpayment out of real token custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The wolfSSL bug class is a component accepting a message that should only ever arrive from the other role, after a precondition that never occurred. The pool's repay op has the same shape: it trusts that the caller already delivered `action.amount` tokens, resolves any excess over outstanding debt as an "overpayment", and transfers that excess back to the `payer` — without checking that any tokens were actually received and without debiting `cash` or passing `require_reserves`. When the market has no (or little) debt, the entire declared amount becomes a refund paid from pool custody. The codebase's own test documents this: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` shows a repay with nothing transferred in drains `custody_before` to the payer with the book untouched (contracts/pool/tests/flows.rs:3578-3611).

### Finding Description
`ops::repay::apply` runs `accounting`, which calls `cache.resolve_repay(amount, position)` and then unconditionally executes `outcome.cache.transfer_out(payer, outcome.overpayment)` (contracts/pool/src/ops/repay.rs:25-34). The refund is derived purely from the *declared* `action.amount`, not from a measured balance delta of the pool's token account. The accompanying test comment states the refund "neither debits `cash` nor passes `require_reserves`" and that a repay against a zero-debt market makes the whole declared amount an overpayment, refunded "out of real custody with the book untouched" (contracts/pool/tests/flows.rs:3578-3588).

The controller-side callers (`settle_repay` in contracts/controller/src/positions/debt.rs:126-162 and `apply_liquidation_repayments` in contracts/controller/src/positions/liquidation/apply.rs:34-87) do fund the pool with `transfer_amount_measured` before calling `pool_repay_call`, so the protocol path is safe. The defect is that the pool — a contract holding one physical token balance across all hub/spoke books — performs a token outflow on an unauthenticated precondition ("the repayer has already paid"). Any direct invocation of `Pool::repay` that is not preceded by a matching inbound transfer mints value for the caller: declaring `amount = X` on a market whose `current_debt_ceil` is 0 produces `overpayment = X` sent to `payer` from supplier funds.

### Impact Explanation
Theft of user funds / protocol insolvency. Each invocation with a declared amount up to the pool's token balance pays that amount to an arbitrary `payer` while `cash` and `borrowed` books are unchanged — the fixture test asserts `credited == 0` and the full custody balance leaving the pool. Supplied and revenue tokens backing RAY supply shares are drained with no debt retired, so suppliers' scaled positions become unbacked.

### Likelihood Explanation
Exploitation requires only an unprivileged address submitting `repay(payer, actions)` directly to the pool contract (or reaching the same path through any component that does not pre-fund). No price manipulation, no capital, and no privileged role is needed; a single call on an idle market returns the entire custody balance. The only residual uncertainty is whether deployment configuration restricts the pool's `repay` entrypoint to the controller via auth — nothing in `ops::repay::apply` itself performs such a check, and the codebase's own test harness invokes it with only a `payer` address.

### Recommendation
Measure the inbound receipt before refunding: snapshot the pool's token balance at the start of the repay batch (or accept the measured transferred-in amount as a parameter from the funding caller), and cap `overpayment` at the measured receipt rather than the declared `action.amount`. Additionally, gate refund transfers behind `require_reserves`/`cash` accounting so refunds can never pay out funds that were never received, and enforce that `Pool::repay` is only invocable by the configured controller.

### Proof of Concept
Reproduced by the existing test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590-3611): with `borrowed == 0` and custody `C`, call `pool.repay(payer, [(action{amount: C, ...})])`. `resolve_repay` takes the full-close branch, `net_repay = 0`, `RepayRoundsToZeroShares` passes on its `net_repay == 0` disjunct, and `transfer_out(payer, C)` moves the entire custody to `payer`. For partial theft on an active market, declare `amount = outstanding_debt + X`; the `X` excess is refunded out of custody regardless of what was transferred in.
