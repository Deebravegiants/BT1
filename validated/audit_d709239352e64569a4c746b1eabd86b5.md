### Title
Borrow-index accrual overflows i128 before the index cap engages, permanently freezing the market - (File: contracts/pool/src/interest.rs)

### Summary
The bug class in CVE-2018-10776 is an unchecked arithmetic/input path that crashes the process (segfault). In XOXNO Lending the analog is an unbounded fixed-point multiplication inside interest accrual: `scaled_to_original` panics with `MathOverflow` when `borrow_index * borrowed` exceeds the i128 RAY domain. Because every state-changing pool verb accrues first, once the RAY value ceiling is crossed the entire market is permanently frozen — no repay, withdraw, borrow, seize, or liquidation can ever execute again.

### Finding Description
`global_sync` runs at the top of every pool op and calls `accrue_chunk`, which delegates to `accrue_step` in `common::rates`. [1](#0-0)  `accrue_step` internally computes scaled-to-original values (`scaled_to_original`, invoked via `Cache::calculate_utilization` and the index update math) that multiply `borrowed` (scaled shares) by `borrow_index`. [2](#0-1)  There is a documented cap `MAX_BORROW_INDEX_RAY`, but a pinned regression test proves the raw value ceiling is reached *before* the cap can engage: on a whale-scale market at ~98% utilization on the steep XLM rate curve, accrual panics with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. [3](#0-2) 

Because the panic happens inside `global_sync`, it precedes all checks and all recovery paths — including `seize_positions`/bad-debt cleanup and `recapitalize`, which also accrue. The test explicitly verifies `withdraw` and `repay` revert after the cliff. The test comment notes "the bound in docs/reference/formulas.md is wrong," confirming this is a real arithmetic gap, not a documented design choice.

### Impact Explanation
Permanent freezing of funds and a market unable to operate. Once the overflow state is reached, all supplier principal in that (hub, token) book is locked forever: `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` all hit the same accrual panic. This satisfies the "permanent freezing of funds" / "contract unable to operate" acceptance criteria. Debtors also escape their obligations since repayment and liquidation both revert.

### Likelihood Explanation
Fully reachable by a single unprivileged address through `controller.supply` and `controller.borrow`: an attacker supplies a large amount of an 18-decimal market token, pushes utilization to the steep segment of the interest curve (~98%), and lets time-based accrual do the rest. No governance action, no leaked keys, no privileged params — only capital and time. The pinned harness test reproduces the freeze deterministically, confirming the state is attainable through ordinary user flows. The cost is high (whale-scale liquidity and a long accrual horizon), which is the main mitigating factor, placing this at Medium/High rather than Critical.

### Recommendation
Clamp inside `accrue_step` rather than letting the value multiply overflow:
- Cap `borrow_index` at `MAX_BORROW_INDEX_RAY` *before* `scaled_to_original` is evaluated, or detect the would-be overflow in `accrue_chunk` and pin the index at the cap, then stop accruing (mark the market as index-saturated).
- Alternatively, compute accrual in a way that never materializes `borrowed * borrow_index` as a single i128 (e.g., chunked index growth bounded so the product stays in domain, or early-exit accrual when the product saturates).
- Fix the documented bound in `docs/reference/formulas.md`, which the test shows is incorrect.

### Proof of Concept
The repo already contains a deterministic PoC at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`:

1. Create an 18-decimal market (`BIG18`) on the XLM rate curve with caps lifted, plus a collateral market.
2. Attacker supplies `BILLION * 10^18` of BIG18 and borrows 98% of it (`borrow` → high utilization on the steep curve segment).
3. Advance ledger time in one-year steps and call `update_indexes`. Before reaching `MAX_BORROW_INDEX_RAY`, `accrue_step` panics with `MathOverflow` (`scaled_to_original` overflow).
4. Every subsequent op on the market reverts: the test asserts `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW`. The market — and all supplier cash in it — is frozen permanently. [4](#0-3) [2](#0-1) [5](#0-4) 

Uncertainty note: I could not inspect `common::rates::accrue_step`/`scaled_to_original` internals within the iteration budget, but the test's assertion (`borrow_index < MAX_BORROW_INDEX_RAY` at failure) confirms the overflow occurs in the value multiply rather than an index bound check. Whether the intended `MAX_BORROW_INDEX_RAY` guard exists but is checked in the wrong order is the exact detail a fix session should verify in `common/src/rates`.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
