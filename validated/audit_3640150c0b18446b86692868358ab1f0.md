### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing tenant-spoofed webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by HMAC-validating only the raw request body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler as the tenant/event identity come from unauthenticated HTTP headers [2](#0-1) . The binding the gem is supposed to guarantee — "the `shop` passed to the handler == the shop that Shopify authenticated this delivery for" — is broken because the HMAC only signs `@raw_body`.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header: [4](#0-3) 

`Registry.process` uses this body-only check as the sole authentication gate, then forwards the *header-derived* `shop`, `topic`, `webhook_id`, and `api_version` fields — none of which participated in the signature — directly into `WebhookMetadata` given to the app's handler: [5](#0-4) 

Because the app-wide `Context.api_secret_key` is shared across every shop that installs the app (it is not a per-shop secret), a valid `(raw_body, hmac)` pair obtained from any one legitimately-installed shop (e.g. the attacker's own store, which can freely install the target app and observe/capture Shopify's real webhook deliveries to a listener they control) remains a *cryptographically valid* pair no matter which `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` header values are attached to it, since those headers are not covered by the signature. Replaying that captured body+HMAC to the app's public webhook endpoint with a different, victim shop's domain in the `x-shopify-shop-domain` header still passes `Utils::HmacValidator.validate`, because validation never inspects the headers.

This breaks the equality the gem's own documented `WebhookMetadata` API implies to consumers — that `data.shop` is the HMAC-authenticated identity of the sender [6](#0-5) . Apps built on this gem are expected (and documented) to use `data.shop` to select which tenant/session/access-token the webhook applies to; the gem provides no protection against a forged `shop` value riding on a validly-signed (but unrelated) body.

### Impact Explanation
An app that follows the gem's documented handler contract (using `data.shop` from `WebhookMetadata` to route webhook effects to the correct tenant) can be made to apply one merchant's webhook data under a different merchant's `shop` identity, since the mapping `data.shop -> HMAC-authenticated shop` is not actually enforced by the gem. This is a cross-tenant identity-binding break reachable by any unprivileged internet user who can install the target app on a shop they control (a normal, low-privilege interaction) and can send arbitrary HTTP requests with attacker-chosen headers to the app's public webhook endpoint.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated-at-transport-layer HTTP endpoint reachable by anyone; `x-shopify-*` headers are ordinary request headers fully controllable by whoever sends the POST. Obtaining one valid `(body, hmac)` pair only requires installing the target app on any shop (including a free/dev shop the attacker controls) and capturing a real webhook delivery — no access to `api_secret_key`, access tokens, or privileged accounts is needed. The gem performs no header-to-signature binding whatsoever, so exploitation is purely a request-crafting exercise.

### Recommendation
Extend `Utils::VerifiableQuery`/`Webhooks::Request` so the values used for tenant/event identity (`shop`, `topic`, `webhook_id`) are cryptographically bound to the authenticated delivery — e.g., include the relevant `x-shopify-*` header values in the signable string used for HMAC comparison (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `host`, `code`, `state`, `timestamp` together [7](#0-6) ), or otherwise document/enforce that `data.shop` must never be trusted for tenant selection without an independent, per-shop verification step.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on `attacker-shop.myshopify.com` and configures a webhook receiver they control.
2. Shopify delivers a real webhook to the attacker's listener with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the target app's public webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com` (and any desired `x-shopify-topic` / `x-shopify-webhook-id`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [4](#0-3)  — validation succeeds.
5. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: <attacker's own shop's data>, ...)` [8](#0-7)  and, if it uses `data.shop` for tenant routing (per the documented contract), processes attacker-controlled data under the victim shop's identity.
