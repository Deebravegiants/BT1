### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop-domain` (as well as `topic`, `webhook-id`, and `api-version`) values are read directly from HTTP headers and are never included in the signed payload, so the app's webhook handler receives a `shop` claim that is completely unauthenticated even though the request as a whole passes signature validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` and compares it against the HMAC secret: [3](#0-2) 

```ruby
sig { params(request: Request).void }
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

And `HmacValidator` only checks `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`: [4](#0-3) 

The binding the gem is supposed to guarantee is:
`shop header value used by handler == shop that Shopify's HMAC actually authenticates`

But because `to_signable_string` is `@raw_body` alone, the equality actually enforced is only:
`HMAC(secret, raw_body) == received_hmac`

with **no cryptographic tie between that HMAC and the `shop-domain`/`topic`/`webhook-id` headers**. Any request bearing a *previously observed* `(raw_body, hmac)` pair (e.g., captured from a legitimate webhook delivery, from logs, from a shared reverse proxy, or from any multi-tenant deployment where the webhook endpoint is shared across shops) can be replayed with an arbitrary `x-shopify-shop-domain` header substituted, and `Utils::HmacValidator.validate` will still return `true`, since the header is never part of the signed material.

### Impact Explanation
This breaks the shop/tenant identity binding: the app's webhook handler (`handler.handle`) is invoked with a `shop` value from `WebhookMetadata` that has never been authenticated. In a multi-tenant app that persists or dispatches data keyed by `data.shop` (which is the documented and intended use, per `docs/usage/webhooks.md`), an attacker who can obtain one valid `(body, hmac)` pair for any shop can forge a request that is processed for a different shop, causing cross-tenant data injection/impersonation — data intended for shop A is written into shop B's record after the header is altered, since the shop binding is never checked cryptographically. This matches the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires the attacker to have captured a legitimate `(raw_body, hmac)` pair once (e.g., via a shared/misconfigured multi-tenant endpoint, browser/proxy logs, or a compromised low-privilege observer of webhook traffic) — it does not require the `api_secret_key` or any credential. Once captured, the pair can be replayed indefinitely against the same endpoint with an arbitrary spoofed `shop-domain` header, since neither the header nor its binding to the signed body is checked. This is a design gap in the gem's `Request`/`Registry` classes rather than a host-application misuse, since the gem's own `to_signable_string` implementation is what omits the header from the signed material.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the raw body before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document and/or enforce that consumers must independently verify `request.shop` against a known/authorized shop for the endpoint before processing, since the library-level guarantee currently only covers the body bytes.

### Proof of Concept
1. Legitimate webhook for `shop-a.myshopify.com` is delivered with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker (who has visibility into `B`/`H`, e.g., via a shared endpoint serving multiple shops, or captured traffic) constructs a new request:
   - `raw_body: B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: shop-b.myshopify.com` (attacker-controlled)
   - `x-shopify-topic`, `x-shopify-webhook-id` (optionally also altered)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC(secret, B)`, which still matches `H`.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed_body_of_B, ...)`, causing shop A's webhook payload to be processed under shop B's tenant context.
