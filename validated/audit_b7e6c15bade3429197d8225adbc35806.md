### Title
Unbounded computational cost in `pallet-ismp::handle_unsigned` charged a fixed, size-independent weight — permissionless CPU-exhaustion DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is the on-chain analog of the reachable, unprivileged "message dispatch" path described in scope (any relayer/dispatcher can call it for free). Its declared `#[pallet::weight]` is a fixed constant (`weight()` → `Weight::from_parts(300_000_000, 0)`), completely independent of the size of the `messages: Vec<Message>` argument the caller controls. Because the call is `ensure_none`-gated (unsigned, feeless) and its real execution cost (membership/non-membership proof verification, per-item hashing, router dispatch, storage reads/writes across every `PostRequest`/`GetRequest`/`GetResponse` in the batch) scales with the attacker-controlled batch size and proof size — not with the declared weight — this is directly analogous to CVE-2005-3510's "cheap request forces disproportionate CPU work" DoS pattern.

`execute` fans out to `handlers::request::handle`, `handlers::response::handle`, and `handlers::timeout::handle`, each of which performs, per item in the caller-supplied `Vec`:
- a merkle multiproof/non-membership verification over `msg.requests`/`msg.timeouts` (cost scales with batch length),
- a `hash_request` per item,
- a router lookup + `on_accept`/`on_response`/`on_timeout` callback with storage reads/writes per item.

See the per-item iteration and membership check in the POST-request handler: [5](#0-4) 

None of these costs are reflected in the constant 300_000_000 weight units (≈0.3ms of ref-time) declared for the call — that constant does not vary with `messages.len()`, the number of `requests`/`timeouts` inside each `Message`, or proof size. Substrate's `CheckWeight` signed extension (applied to unsigned extrinsics too) only checks the *declared* pre-dispatch weight against the remaining block weight budget before allowing the extrinsic to execute; the real cost is only known after execution (`PostDispatchInfo::actual_weight`), by which point the CPU time has already been spent both by the block author (execution) and by every full node in the network (both `validate_unsigned` during pool gossip revalidation and the actual `on_finalize`/apply-extrinsic execution).

Because the call is unsigned (feeless, no nonce, no account-based rate limiting), an attacker can:
1. Craft a `handle_unsigned` call whose `Vec<Message>` contains a large `RequestMessage`/`ResponseMessage`/`TimeoutMessage` batch (thousands of `PostRequest`/`GetRequest` entries, bounded only by the generic block-length/extrinsic-size limit, not by any per-call cap tied to `messages.len()`),
2. Submit many such transactions concurrently/in parallel (no account, no fee, no nonce needed) to many nodes simultaneously,
3. Each node must run the full `execute()` (proof verification + per-item hashing/dispatch) during transaction-pool validation for every submission, and the block author must run it again at inclusion time, while the on-chain weight accounting only "sees" 300_000_000 units — i.e. the fixed cost of a trivial call — letting many such calls be packed into the same block without tripping the weight limit that is supposed to bound per-block execution time.

This mirrors the Tomcat DoS bug class exactly: an unauthenticated party issues a small number of requests whose *declared* cost (page load / here, extrinsic weight) is trivial, but whose *actual* server-side/node-side CPU cost (listing a huge directory / here, verifying and dispatching a huge batch) is unbounded relative to what the resource-accounting system charges for it.

### Impact Explanation
This is a genuine chain-level resource-exhaustion vector reachable by any unprivileged party able to submit an unsigned extrinsic (the same "message dispatcher/relayer" surface named in scope). Its impact is:
- Block-production stalls / missed block deadlines as block authors spend far more wall-clock time executing `handle_unsigned` extrinsics than the declared weight accounts for, potentially causing the parachain to miss its slot.
- Transaction-pool/node CPU exhaustion across the network as every node revalidates the same oversized calls during gossip, independent of whether they are ever included.
- A resulting "route unable to deliver messages" condition: if block production degrades or nodes fall behind due to CPU starvation, legitimate relayed messages (POST requests, GET responses, timeouts) cannot be delivered/confirmed in a timely manner, which is one of the impact classes explicitly in scope.

Given the free/unsigned nature of the call and lack of any per-message-count or per-batch-size weight scaling, this is High severity rather than Medium.

### Likelihood Explanation
Likelihood is high: the call is fully permissionless (`ensure_none`), requires no fee, no stake, and no prior setup beyond constructing a large but otherwise-syntactically-valid `Message` batch (the proofs inside can be malformed/rejected — the expensive work of hashing/verifying still happens before that rejection is returned). An attacker only needs network access to submit extrinsics to the parachain, which is the same reachability level already granted to any relayer in the system's design.

### Recommendation
- Make the declared weight for `handle_unsigned` (and the analogous `pallet-state-coprocessor::handle_unsigned`) a function of the actual input size: charge weight proportional to `messages.len()`, the number of requests/responses/timeouts nested in each message, and proof length, using benchmarked per-item weights (similar to how `frame_support` benchmarks size-dependent calls), rather than a single constant.
- Enforce an explicit maximum on the number of items processed per `handle_unsigned` call (e.g. a `MaxMessagesPerBatch`/`MaxRequestsPerMessage` bound checked at the very start of `execute`/`validate_unsigned`, before any hashing or proof verification is attempted), independent of the generic block-length limit.
- Consider charging a deposit/fee for unsigned `handle_unsigned` calls that scales with batch size, or introduce a lightweight, cheap pre-check (e.g. a cap on total encoded proof bytes) before running the expensive `execute` path in `validate_unsigned`.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` extrinsic with `messages = vec![Message::Request(RequestMessage { requests: <N thousand PostRequest entries, sized to approach the runtime's max extrinsic/block length>, proof, signer })]`.
2. Submit this extrinsic (unsigned, no fee) to the network. Because `weight()` returns a constant regardless of `N`, the `CheckWeight` pre-dispatch check passes as if this were a trivial call.
3. Observe that every node's `validate_unsigned` runs `Self::execute(messages.clone())`, which iterates `N` requests, hashing each (`hash_request`), verifying a merkle multiproof over all `N` leaves, and dispatching each to its module callback — CPU cost scaling with `N`, not reflected anywhere in the 300_000_000 declared weight.
4. Repeat with multiple such extrinsics submitted concurrently by different (still unsigned/feeless) submitters; because there is no per-account/nonce constraint, arbitrarily many can be in flight, and the block author can be forced to spend execution time far exceeding what the block's declared weight budget assumed for these extrinsics.

*(Note: I could not fully confirm the exact `BlockWeights`/`NORMAL_DISPATCH_RATIO` values configured in `parachain/runtimes/gargantua/src/lib.rs` and `nexus/src/lib.rs` due to running out of tool iterations before reading that file's content — those values would let one compute a precise "N transactions of size N overrun the block time budget by X%" number, but the fixed-weight-vs-scaling-cost mismatch itself is directly confirmed from `modules/pallets/ismp/src/lib.rs` and `modules/ismp/core/src/handlers/request.rs`.)*
