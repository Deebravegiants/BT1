## Title
Mismatched coin/pc mint decimals cause `calc_x_power` to overflow `U256` in `calc_take_pnl`, permanently locking pool funds - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`AmmInfo::initialize` derives a single `sys_decimal_value = 10^max(pc_decimals, coin_decimals)` that is used to normalize both coin and pc amounts into a common decimal scale for PnL accounting [1](#0-0) . When the two mints have very different decimals (e.g. one mint uses `0` decimals and the other uses `19`, the maximum value that does not panic at pool creation), the normalization of the low-decimal side amplifies its value by up to `10^19`, while the other side stays essentially unscaled. This asymmetry, combined with the unchecked-but-`unwrap()`ed `U256` multiplication chain in `Calculator::calc_x_power`, can overflow `U256` on any subsequent call to `calc_take_pnl` (invoked from `Deposit`, `Withdraw`, and `WithdrawPnl`), permanently reverting every future interaction with the pool and freezing all deposited liquidity.

### Finding Description
`Calculator::normalize_decimal_v2` scales a raw token amount into "system decimal" units: [2](#0-1) 

Because `sys_decimal_value` is fixed to `10^max(pc_decimals, coin_decimals)` for the life of the pool, a pool with `pc_decimals = 0` and `coin_decimals = 19` (both are legal — `AmmInfo::initialize` only panics if `10^decimals` overflows `u64`, i.e. for `decimals >= 20`) produces: [3](#0-2) 

- `x (normalized pc)` ≈ `pc_amount * 10^19` (amplified, up to ~1.84e38 for `pc_amount` near `u64::MAX`)
- `y (normalized coin)` ≈ `coin_amount` (unscaled, up to ~1.84e19)

These normalized values `x1`, `y1` are stored across calls in `TargetOrders.calc_pnl_x` / `calc_pnl_y`, and fed straight into `Calculator::calc_x_power` on every subsequent `Deposit`/`Withdraw`/`WithdrawPnl`: [4](#0-3) 

`calc_x_power` computes `last_x * last_y * current_x / current_y` fully in `U256`, but performs both multiplications **before** the division: [5](#0-4) 

With `last_x ≈ current_x ≈ 1.84e38` and `last_y ≈ 1.84e19`, the intermediate product `last_x * last_y * current_x` reaches roughly `6.3e95`, which vastly exceeds `U256::MAX` (~1.16e77). `checked_mul` returns `None`, and the `.unwrap()` panics, aborting the transaction.

### Impact Explanation
Once a pool is initialized with such a decimal mismatch and receives large enough deposits (near `u64::MAX` scale on the low-decimal side), `TargetOrders.calc_pnl_x`/`calc_pnl_y` permanently hold the amplified value. Every future call into `process_deposit`, `process_withdraw`, or `process_withdrawpnl` re-executes `calc_take_pnl` → `calc_x_power` with these stale, large values and will panic identically, since there is no code path to reset `calc_pnl_x`/`calc_pnl_y` without going through the same overflow. This permanently freezes all coin/pc tokens already held in the pool's vaults — a concrete, permanent loss of access to user/LP funds, not merely a failed single transaction.

### Likelihood Explanation
Pool creation via `Initialize2` and deposits are fully permissionless — any user can create a pool, choose the coin/pc mints (including a self-created SPL mint with `decimals = 19`), and deposit large amounts. No privileged role is required. The only constraint is achieving sufficiently large normalized values; because `sys_decimal_value` scales with mint decimals which the attacker/pool-creator fully controls, and deposits can reach `u64::MAX`-scale raw token amounts, the overflow is practically reachable via two ordinary transactions (create pool + deposit).

### Recommendation
- Perform the `calc_x_power` computation using a wider intermediate type (e.g. reorder division before the second multiplication, or use `U512`), or clamp/validate `pc_decimals`/`coin_decimals` disparity at pool initialization to a safe bound that guarantees `sys_decimal_value`-scaled amounts cannot overflow `U256` in the PnL formula.
- Alternatively, restructure `calc_x_power` to divide early: `last_x.checked_mul(last_y)?.checked_div(current_y)?.checked_mul(current_x)?` (reduces magnitude before the second multiplication) while preserving acceptable precision loss, and add proper error propagation instead of `.unwrap()` so a bad state degrades gracefully rather than permanently bricking the pool.

### Proof of Concept
1. Create two SPL mints: `mintA` with `decimals = 0`, `mintB` with `decimals = 19` (both accepted by `spl_token::instruction::initialize_mint`, and by `AmmInfo::initialize` since `10^19` fits in `u64`).
2. Call `Initialize2` with `init_pc_amount` on `mintA` (0-decimal side) close to `u64::MAX`, and `init_coin_amount` on `mintB` similarly large — this sets `TargetOrders.calc_pnl_x ≈ init_pc_amount * 10^19`, `calc_pnl_y ≈ init_coin_amount` via `check_init`.
3. Call `Deposit` again with any additional amount to trigger `calc_take_pnl` → `calc_x_power(last_x≈1.8e38, last_y≈1.8e19, current_x≈1.8e38, current_y≈1.8e19)`.
4. The intermediate `last_x.checked_mul(last_y).unwrap().checked_mul(current_x)` exceeds `U256::MAX`, `checked_mul` returns `None`, and `.unwrap()` panics, reverting the transaction.
5. Every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` on this pool repeats the same panic, permanently locking the vault balances deposited in step 2.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
