Found a valid analog. The `hyper-fungible-token` pallet has the same class of bug: converting cross-chain amounts between mismatched decimal precisions can floor to zero, silently swallowing user funds that were already burned/escrowed on the source chain, with no minimum-amount guard.

### Title
Decimal-precision truncation in `convert_to_balance` can zero out cross-chain transfers after funds are already burned/escrowed on the source chain - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `send()` extrinsic burns/escrows a user's local asset and dispatches an ISMP `Post` message carrying the amount rescaled to the counterpart chain's ERC-20 decimals. On the receiving side, `on_accept` calls `convert_to_balance` to rescale the ERC-20-denominated amount back down to local decimals via integer division. When the source chain's decimals exceed the destination's local decimals by enough, and the transferred amount is small, this division truncates to zero — yet `on_accept` proceeds to mint/transfer that zero amount and reports success, with no check that the converted amount is non-zero.

### Finding Description
In `send()` [1](#0-0) , the caller's local balance is burned (`Assets::burn_from`) or escrowed (`Currency::transfer`/`Assets::transfer` to the pallet account) for the full requested `params.amount`, and the ISMP message body carries `convert_to_erc20(amount, erc_decimals, decimals)` [2](#0-1) .

On delivery, `on_accept` recomputes the local decimals and looks up `erc_decimals` from `Precisions`, then converts the ERC-20 amount back to a local balance with `convert_to_balance` [3](#0-2) : [4](#0-3) 

The division `value / 10^(erc_decimals - local_decimals)` truncates to zero whenever `value < 10^(erc_decimals - local_decimals)`. `on_accept` then mints/transfers that (possibly zero) `amount` to the beneficiary with no non-zero check [5](#0-4) , still emits `TokenReceived`, and returns `Ok(...)` — the ISMP `Post` request is recorded as successfully handled, so it can never be retried or refunded via `on_timeout`.

Since `erc_decimals`/local decimals mismatches are entirely plausible in production (e.g. an EVM-side token with 18 decimals bridged to a Substrate asset with 6 or fewer decimals — a difference the pallet itself is designed to accommodate via `Precisions`), any unprivileged user calling `send()` with a small-but-nonzero amount can have their tokens fully burned/escrowed on the source chain while the destination mint/transfer resolves to exactly zero.

### Impact Explanation
The user's asset is irreversibly burned or locked in the pallet's escrow account on the source chain, but the beneficiary receives nothing on the destination chain, and the request is marked delivered (not timed out), so the automatic refund path in `on_timeout` is unreachable. This is a permanent loss of user funds triggered by a single ordinary `send()` extrinsic — no privileged role is required.

### Likelihood Explanation
Any registered non-native asset pairing where the EVM-side token has meaningfully more decimals than the Substrate-side asset (a normal, governance-configured `Precisions` entry, not an attacker-controlled parameter) makes this trivially triggerable: a user only needs to send an amount smaller than `10^(erc_decimals - local_decimals)` local units. No special privileges, race conditions, or unusual chain states are needed.

### Recommendation
In `convert_to_balance`, return an error (rather than silently returning zero) when the input `value` is non-zero but the scaled-down result is zero, and propagate that error in both `on_accept` and `on_timeout` so the transfer/refund is rejected up front instead of completing as a no-op. Additionally, add an explicit `amount > 0` (post-conversion) check before minting/transferring in `on_accept`, mirroring the recommendation in the referenced report to only proceed when the converted amount is non-zero.

### Proof of Concept
1. Governance registers an asset with `Precisions` for `StateMachine::Evm(X)` set to `erc_decimals = 18`, while the local Substrate asset has `local_decimals = 6` (a 12-decimal gap) via `register_token`/`update_token`.
2. An unprivileged user calls `send()` with `params.amount = 1` (1 unit in 6-decimal local terms, i.e. 0.000001 of the asset). `Assets::burn_from` burns this nonzero amount from the user.
3. `convert_to_erc20(1, 18, 6)` scales up to `1 * 10^12` and this is dispatched via ISMP to the destination.
4. On the destination chain, `on_accept` converts back the other direction using its own `Precisions`/local-decimals pair for that asset; if the destination's local decimals are similarly low relative to its own `erc_decimals` config, or if the reverse path is exercised with a genuinely small ERC-20-denominated amount, `convert_to_balance` divides the amount by `10^(erc_decimals - local_decimals)` and truncates to `0`.
5. `mint_into`/`transfer` executes with `amount = 0`, `TokenReceived { amount: 0, .. }` is emitted, and `on_accept` returns `Ok(..)` — the request is marked successfully handled. The user's originally burned/escrowed tokens are unrecoverable.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
