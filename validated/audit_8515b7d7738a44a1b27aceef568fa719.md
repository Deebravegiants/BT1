### Title
Unvalidated route bytes let attacker-named venue contracts execute under the caller's authorization and drain the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The XXE class — parsing attacker-controlled external data that dereferences outside entities inside a privileged context — maps directly onto how the controller forwards opaque route bytes to the swap router. `swap_tokens` (contracts/controller/src/strategies/swap.rs:13-55) authorizes one exact input transfer, then invokes `router.execute_strategy(controller, amount_in, swap)` where `swap` is caller-supplied XDR. The router keeps no allowlist of the pool/token addresses the payload names, so the attacker places arbitrary contract code on the call stack *below the caller's signed authorization*. A rogue "pool" invoked in a hop can call `token.transfer(victim, attacker, x)` on any token the victim holds; the Soroban host records that transfer as a child of the victim's `swap_collateral`/`multiply`/etc. auth entry, and it executes if signed. The threat model itself documents this (docs/explanation/threat-model.md:154-165), and a harness test demonstrates a wallet drain inside `swap_collateral` (tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227).

### Finding Description
Analog of XXE: the `swap`/`data` bytes are the "external entity." The controller and router resolve entities (pool/token addresses) named inside attacker-supplied serialized input without binding them to any allowlist, and the dereferenced code runs while the victim's `require_auth` tree is open. Concrete paths an unprivileged caller reaches:

- `multiply` (`PositionMode::Long`/`Short` require distinct tokens, so a non-empty route is mandatory)
- `swap_collateral`, `swap_debt`, `repay_debt_with_collateral` — each takes a `swap: Bytes` argument forwarded verbatim (contracts/controller/src/lib.rs:255-303)
- Direct `execute_strategy(sender, total_in, swap_xdr)` on the router

The venue call chain is `env.invoke_contract(ctx.hop.pool, ...)` where `hop.pool` comes from the payload's address registry (contracts/swap-aggregator/src/venues/comet.rs:30-34, and ADR-0018 "Registries need not be unique" in docs/explanation/decisions.md:221-228). The malicious pool executes, ignores the swap semantics, and issues `token.transfer(victim, attacker, amount)` for any victim-held token. In recording/simulation mode this transfer is attached to the victim's authorization entry; the test asserts the recorded tree contains `transfer(alice, attacker, WALLET_BALANCE)` as a child of the `swap_collateral` root and that Alice's wallet balance goes to zero while the attacker receives it.

### Impact Explanation
Theft of user funds beyond the routed amount. The loss is the victim's whole wallet balance of any token the malicious hop targets — unbounded by `total_in`, the route `min_out`, or the controller's `RouterOverspend`/`NoSwapOutput` checks, since the stolen transfer is orthogonal to the swap's measured deltas and the swap itself can still return a positive output. This matches the XXE original (SSRF/secret exfiltration via parsed entities) in shape: untrusted serialized input resolves an external entity that performs actions inside the requester's trust boundary.

### Likelihood Explanation
Exploitation requires the victim to sign a transaction whose auth tree contains the rogue child transfer. An honest client that decodes the route and refuses unexpected auth children (as the threat model instructs) prevents it. However: route bytes are produced by an off-chain quote service and are opaque to most signers; wallet UIs display the root invocation, not necessarily every nested child; and nothing on-chain rejects the extra child — the host accepts any subtree the victim signed. A single unprivileged attacker can stand up the malicious pool contract and craft the route at will; delivery is via the same channel routes already come from. This is materially weaker than a pure on-chain theft (it needs a signed poisoned tree), which argues Medium rather than High.

### Recommendation
- On-chain: the router should constrain each hop's `pool` to implement a venue adapter interface check, or the controller should enforce a venue/pool allowlist for strategy swaps rather than accepting fully arbitrary registries (currently only the fee whitelist exists, which "does not restrict permitted tokens" — docs/reference/endpoints.md:263).
- Alternatively, run each venue call in a context that cannot require_auth the sender (impossible on Soroban today), so the practical fix is the allowlist plus mandatory client-side decoding of `routeXdr` and rejection of any auth tree child beyond the single input `transfer` (already documented as required client behavior; enforce it in the SDK's `verifyRouteBytes`).

### Proof of Concept
Existing harness proof: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs):

1. Attacker deploys a pool contract that, when its swap entry is invoked, calls `wallet_token.transfer(victim, attacker, balance)`.
2. Attacker crafts route bytes whose `assets` registry names that contract as a hop pool.
3. Victim calls `swap_collateral(caller=victim, account_id, current=ETH, amount, new=USDC, swap=route)` and signs the simulated auth tree.
4. Recorded tree contains `transfer(alice → attacker, 77_770_000_000)` as a child of the swap root; Alice's wallet token balance becomes 0, the attacker holds it, and the swap itself still credits a fair ETH output — so no protocol-side check (`RouterOverspend`, `NoSwapOutput`, final HF gate) detects the theft.
