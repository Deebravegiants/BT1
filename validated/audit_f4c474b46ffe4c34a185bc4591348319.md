### Title
`authHandleToIntentsUserId` maps NEAR implicit accounts and TON identifiers to the same `IntentsUserId` for any 64-hex string - ([File: packages/internal-utils/src/utils/authIdentity.ts])

### Summary
`authHandleToIntentsUserId` produces identical output for the `"near"` and `"ton"` auth methods whenever the identifier is a 64-character hex string, because both branches simply lowercase the raw identifier with no chain-specific tag or prefix. This collapses two distinct-chain identities into a single `intents.near` user id.

### Finding Description
The claimed broken equality is: `authHandleToIntentsUserId(x, "near") == authHandleToIntentsUserId(x, "ton")` for `x = "a".repeat(64)`.

- `case "near"` (and `"evm"`) at [1](#0-0) : returns `authHandle.identifier.toLowerCase()` verbatim — a 64-hex-char NEAR implicit account id passes through unchanged (lowercased).
- `case "ton"` at [2](#0-1) : asserts length 64, hex-decodes for validation only, then also returns `authHandle.identifier.toLowerCase()` verbatim, with no `ton:` prefix or other chain tag.

Since NEAR implicit account ids are exactly 64 lowercase hex characters (ed25519 public key hex) and the `ton` branch requires the exact same shape (64 hex chars) and applies the exact same transform (lowercase, no prefix), any 64-hex string `x` produces the same `IntentsUserId` for both methods: `x.toLowerCase() === x.toLowerCase()`. This is confirmed by comparing this behavior against the other chains in the same function, all of which are either format-incompatible with 64-hex (evm requires `0x` + 40 hex, solana/stellar/tron/webauthn re-encode into a different byte layout) — `near` and `ton` are the only two branches that (a) accept the identical 64-hex-char shape and (b) apply the identical no-op lowercase transform, with no distinguishing prefix such as `ton:` that other systems typically use to namespace chain-specific ids [3](#0-2) .

This `IntentsUserId` is used directly as the `signer_id` in signed intent payloads (NEP-413 message and ERC-191 message), e.g. `intent.signer_id ?? this.accountId` in `IntentSignerNEP413.signIntent` [4](#0-3) , and via `utils.authHandleToIntentsUserId({ identifier: ..., method: "evm" })` fallback in `IntentSignerViem.signIntent` [5](#0-4) . The `signer_id` is the account identity that the intents.near contract credits/debits balances against.

### Impact Explanation
Because the `IntentsUserId` string is the sole key used to identify and route balances for a user inside intents.near (it appears as `signer_id` in `Nep413DefuseMessageFor_DefuseIntents` / `DefusePayloadFor_DefuseIntents`) [6](#0-5) [7](#0-6) , a collision in this id derivation means funds/deposits attributed to a NEAR implicit account `x` and funds/deposits attributed to a TON identifier `x` (same 64-hex string) would be tracked under the identical on-chain account bucket. However, whether this is *actually exploitable* by an unprivileged attacker depends on facts outside this repo's reach from static analysis alone:
1. Whether the TON authentication/deposit flow in this SDK ever actually produces or accepts a raw 64-hex identifier equal to some existing NEAR implicit account's public key (i.e., whether TON auth identifiers as used elsewhere in the SDK are raw ed25519 public keys, or wallet addresses derived differently) — I could not find any caller in this repo that invokes `authHandleToIntentsUserId` with `method: "ton"` (no matches for `"ton"` combined with this function), nor a TON intent-signer implementation, so I cannot confirm the actual TON identifier format fed into this path from a real TON wallet flow.
2. Whether intents.near's own signature verification (Rust contract, outside this repo) additionally binds the signature scheme to the claimed identity type, which would prevent an attacker who only controls a TON key from producing a valid NEP-413 signature for the colliding NEAR-style `signer_id`, and vice versa.

Given these two open, repo-external unknowns, I cannot state with confidence that a real dual-chain fund-movement exploit is reachable purely from code in this repository. The `authIdentity.ts` collision itself is real and reproducible in isolation, but the rule "trust assumptions about external RPCs... or defects inside intents.near... with no path through this repo" excludes findings whose exploitability hinges on the external contract's verification behavior, which is unverified here.

### Likelihood Explanation
No caller in this repository is found invoking `authHandleToIntentsUserId` with `"ton"` from an actual TON wallet integration, so there's no evidence within the SDK today that a real TON login/deposit flow would produce a colliding identifier without user or integrator action deliberately crafting one. The collision is a code-level defect (missing chain-specific namespacing in the `ton`/`near` branches), but reachability of the "steal funds" scenario described in the question requires additional unverified conditions (matching key material across chains and no additional binding checks by intents.near).

### Recommendation
Add a chain-specific prefix/tag to the `ton` branch's output distinct from the `near`/`evm` branches (e.g. `ton:` + hex, mirroring how `tron` and `webauthn` already produce distinguishable, re-encoded outputs) so that `authHandleToIntentsUserId(x, "near")` can never equal `authHandleToIntentsUserId(x, "ton")` for any input `x`.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { authHandleToIntentsUserId } from "./authIdentity";

it("near and ton identifiers collide for the same 64-hex string", () => {
  const x = "a".repeat(64);
  const nearId = authHandleToIntentsUserId(x, "near");
  const tonId = authHandleToIntentsUserId(x, "ton");
  expect(nearId).toBe(tonId); // demonstrates broken chain-distinctness invariant
});
```

I flag this finding as **inconclusive for Critical/High severity as scoped**, because I could not verify within this repo (a) any actual TON auth-identifier producer/consumer that would feed a colliding value into this function under realistic conditions, or (b) that intents.near's contract-side signature verification does not already separate signer identity by method/signature-scheme, which the audit rules explicitly place out of scope ("defects inside intents.near... with no path through this repo", "trust assumptions about... the relayer, bridge APIs"). The code-level equality collision itself is real and reproducible as shown above, but I recommend a maintainer/Devin session verify the TON identifier production path and the contract's signature/method binding before treating this as a confirmed fund-movement vulnerability.

/**
 * Converts a blockchain address to a standardized Defuse user ID.
 *
 * The conversion follows these rules:
 * 1. NEAR addresses: Used as-is (lowercased)
 *   - Explicit: "bob.near"
 *   - Implicit: "17208628f84f5d6ad33f0da3bbbeb27ffcb398eac501a31bd6ad2011e36133a1"
 *
 * 2. EVM addresses: Used as-is (lowercased)
 *   - Format: "0xc0ffee254729296a45a3885639ac7e10f9d54979"
 *
 * 3. Solana addresses: Converted from base58 to hex
 *   - Input: base58 public key
 *   - Output: hex-encoded string
 *
 * 4. WebAuthn credentials: Converted based on curve type
 *   - P-256: Keccak256(prefix + pubkey) -> last 20 bytes -> hex with 0x prefix
 *   - Ed25519: Raw public key -> hex encoding
 *
 * @param authIdentifier - The user's identifier (blockchain address or WebAuthn public key)
 * @param authMethod - The type of credential ("evm", "near", "solana", "webauthn")
 * @returns A standardized Defuse user ID
 */
