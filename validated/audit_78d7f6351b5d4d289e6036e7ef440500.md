## Title
Webhook shop attribution not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the unauthenticated `x-shopify-shop-domain` header. Because the signature never binds the shop identity, a valid `(body, hmac)` pair obtained for one shop can be replayed with a different `shop-domain` header and will still pass verification, letting an attacker attribute forged/replayed webhook data to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is computed purely from the `hmac-sha256` header value: [2](#0-1) 

`Registry.process` verifies only this body-derived HMAC, then immediately trusts `request.shop` (sourced from the `shop-domain` header, which is not part of the signed payload) to build the dispatched `WebhookMetadata`: [3](#0-2) 

`request.shop` is read straight from headers with no cross-check against the HMAC-covered content: [4](#0-3) 

The identity binding broken is: `HMAC-covered bytes (raw_body) ≠ bytes acted upon for tenant attribution (shop-domain header)`. Since Shopify signs webhooks for an app with the app's single shared `client_secret` across *all* shops that installed the app, any shop that can install the app (including an attacker's own store) can obtain a genuinely-signed `(body, hmac)` pair. Because the header is excluded from the signed content, replaying that exact body/hmac pair while substituting a victim shop's domain in `x-shopify-shop-domain` produces a request that still passes `Utils::HmacValidator.validate`, yet is processed as if it originated from the victim shop.

### Impact Explanation
This is a cross-tenant integrity issue: an unprivileged internet user who controls any shop where the target app is installed can forge the shop attribution of an otherwise-valid, correctly-signed webhook payload and have the host application process it under a different merchant's identity. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to update per-tenant data, trigger fulfilment, disable/uninstall handling, or write audit logs keyed by shop), this can lead to cross-tenant data corruption or unauthorized actions performed against a merchant the attacker does not control — matching the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint plus the ability to trigger at least one genuine webhook delivery (trivially available to anyone who installs the app in a shop, even a free/dev store), and then replaying the same body/HMAC pair with a modified `shop-domain` header. No access to `api_secret_key` or any merchant's access token is needed.

### Recommendation
Include the shop domain (and ideally other routing headers such as `topic`) in the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the verified payload before dispatch, e.g., require the host application/Registry to validate that the `shop` header matches shop data embedded in the verified body, or sign a canonical string of `shop + topic + raw_body` instead of `raw_body` alone.

### Proof of Concept
1. Install the target app on an attacker-controlled shop, `attacker-shop.myshopify.com`.
2. Capture a genuine webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — valid because it was actually sent by Shopify for the attacker's own install.
3. Replay the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (only `B` and `H` are checked): [5](#0-4) 
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though the payload/body actually originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
