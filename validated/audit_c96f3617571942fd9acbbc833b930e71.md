### Title
Host freeze checked with a single overloaded `notFrozen` gate blocks the escape-hatch timeout path exactly when it is needed - ([File: evm/src/core/HandlerV2.sol])

### Summary
`EvmHost` exposes a single `FrozenStatus` (`None`/`Incoming`/`Outgoing`/`All`) used to halt bridge operations when a fault is suspected. `HandlerV2` gates every relayer-submitted message — including `handlePostRequestTimeouts` and `handleGetRequestTimeouts`, the recovery/refund path for requests that were dispatched (and paid a fee) but never delivered — behind the same `notFrozen(host)` modifier that also blocks accepting new incoming requests/responses/consensus updates. This mirrors the Morpho finding: a status flag meant to stop one class of risky action (`isBorrowPaused`/incoming acceptance) was not decoupled from the flag/path that lets users recover funds (`isLiquidateBorrowPaused`/timeout processing), so setting the "safety" flag simultaneously disables the safety valve.

### Finding Description
`EvmHost.sol` defines the `notFrozen` modifier used for dispatch (outgoing) and `HandlerV2.sol` defines an equivalent `notFrozen(IHost host)` modifier used for all incoming datagram processing: [1](#0-0) 

This single modifier is applied uniformly to `handleConsensus`, `handlePostRequests`, `handleGetResponses`, and — critically — to the timeout-handling entry points: [2](#0-1) [3](#0-2) 

`handlePostRequestTimeouts`/`handleGetRequestTimeouts` do not deliver untrusted foreign-chain data into an `IsmpModule`; they verify a **non-membership** proof against an already-anchored `StateCommitment` to prove a request was never processed, and then release the escrowed fee/funds back to the payer: [4](#0-3) 

Because `Incoming` (and `All`) freeze both the acceptance of new untrusted requests/responses *and* this refund/timeout path, freezing the host for a legitimate reason (e.g. a suspected consensus fault, an operational pause during a consensus client update — the admin-relayer tooling literally toggles `FROZEN_ALL`/`FROZEN_NONE` around `handleConsensus` submissions) simultaneously removes the only way users can reclaim funds locked in in-flight `PostRequest`/`GetRequest`s that time out while the freeze is active: [5](#0-4) [6](#0-5) 

`EvmHost.dispatch` escrows the payer's fee in `requestCommitments` at dispatch time, and that fee/escrow is only released via `dispatchTimeOut` inside the very functions gated by `notFrozen`: [7](#0-6) 

This is the same root-cause pattern as the Morpho audit finding: a single flag/gate is reused to protect two conceptually distinct operations — "don't trust new incoming data" vs. "let users exit/refund a stuck position" — without carving out the exit path, so activating the protective flag also freezes the recovery mechanism it should have left open.

### Impact Explanation
While the host is frozen for `Incoming` or `All`:
- Any `PostRequest`/`GetRequest` (including token-bridge transfers via `IntentGatewayV2`/`HyperFungibleToken`/token-gateway apps) that times out during the freeze window cannot be timed out and refunded — the fee/escrow stays locked in the host/app until the freeze is lifted.
- If the freeze persists (e.g. the underlying consensus fault is never resolved, or governance is slow to unfreeze), this is an indefinite, protocol-level freezing of user funds with no workaround, since the only code path that releases escrowed request fees is itself blocked.
- This affects any unprivileged user/relayer who dispatched a request before the freeze and is now unable to submit the corresponding timeout message — a direct, permanent loss-of-access to escrowed funds, not merely a delay, if the freeze period exceeds the request's practical patience/urgency (e.g., time-sensitive intents).

### Likelihood Explanation
`setFrozenState` is restricted to `admin` or `handler`, so triggering the freeze itself requires a privileged actor, but this is not a "malicious admin" bug — it is a **design consistency defect**: legitimate, expected freeze usage (as evidenced by the admin-relayer tooling wrapping consensus submissions in `FROZEN_ALL`/`FROZEN_NONE` toggles) has the unintended side effect of blocking the timeout/refund path for any user with an in-flight request, through no fault of the admin's intent. The reachable, unprivileged trigger is simply: dispatch a request, have it time out while the host happens to be frozen for `Incoming`/`All` for any operational reason, and be unable to reclaim funds via `handlePostRequestTimeouts`/`handleGetRequestTimeouts` until unfreeze.

### Recommendation
Split the `notFrozen` check so that `Incoming`/`All` freeze only blocks acceptance of new, untrusted incoming requests/responses/consensus updates, and introduce either a dedicated status (or explicit carve-out) that always permits `handlePostRequestTimeouts`/`handleGetRequestTimeouts` to proceed, since they rely on non-membership proofs against already-finalized state and are the sole mechanism for releasing escrowed fees back to users. This mirrors the audit's recommendation to decouple the deprecation/pause flags so the recovery action (liquidation there, timeout here) is never blocked by the safety flag meant for a different concern.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost{...})`, paying a fee that is recorded in `requestCommitments` (see `evm/tests/foundry/EvmHostTest.sol:158-171` `testFundRequest`).
2. Admin/handler calls `setFrozenState(FrozenStatus.Incoming)` (or `.All`) for an unrelated operational reason (e.g. mid consensus-client update, mirroring `tesseract/consensus/admin-relayer/src/batch.rs:117-123`).
3. The dispatched request times out (`request.timeout()` elapses) while the freeze is still active.
4. User/relayer submits `handlePostRequestTimeouts(host, message)` with a valid non-membership proof; the call reverts with `HostFrozen()` due to the `notFrozen(host)` modifier at `evm/src/core/HandlerV2.sol:254-260`, even though the proof itself is valid and unrelated to any live consensus risk.
5. The escrowed fee (and, for token-bridge/intents apps built on top, the escrowed principal) stays locked until an admin/handler eventually calls `setFrozenState(FrozenStatus.None)` — demonstrated as achievable in `evm/tests/foundry/EvmHostTest.sol:118-142` (`testCannotDispatchWithFrozenHost`), which shows dispatch/timeout functions reverting identically under freeze, with no separate path to force a timeout during that window.
