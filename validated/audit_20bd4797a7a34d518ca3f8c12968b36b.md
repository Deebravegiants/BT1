### Title
Webhook HMAC only covers the raw body, allowing shop/topic header spoofing for cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC exclusively against that string. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read straight from HTTP headers and forwarded into `WebhookMetadata` for the host app's handler to act on, are never part of the signed material.

### Finding Description
`Webhooks::Registry.process` is the sole authenticity gate for inbound webhooks: it raises `Errors::InvalidWebhookError` unless `Utils::HmacValidator.validate(request)` succeeds, then immediately builds a `WebhookMetadata` struct using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` and hands it to the registered `handler.handle`. [3](#0-2) 

However, `Webhooks::Request#to_signable_string` — the value the HMAC is actually computed over — is defined as just `@raw_body`, with no inclusion of the `shop`, `topic`, `webhook_id`, or `api_version` headers. [4](#0-3) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received `hmac`. Because `to_signable_string` excludes the header fields, the equality that the code effectively enforces is:

`HMAC(secret, raw_body) == received_hmac`

not

`HMAC(secret, raw_body + shop + topic) == received_hmac`.

This breaks the intended binding between "the shop the app authenticates the request as belonging to" (`request.shop`, used as the tenant key passed to `handler.handle`) and "the bytes actually verified by the HMAC" (`request.to_signable_string`, i.e., only the body). [2](#0-1) 

An attacker who legitimately controls their own shop with the app installed will receive genuine Shopify webhooks (valid body + valid HMAC) addressed to their own shop. Since the HMAC never covers the `shop-domain`/`topic`/`webhook-id` headers, the attacker can resend that exact `raw_body`+`hmac` pair to the app's webhook endpoint while substituting a victim's shop domain (and/or a different topic) in the headers. `HmacValidator.validate` still returns `true` because the body bytes and secret are unchanged, and `Registry.process` forwards `shop: <victim-domain>` to the app's handler as if Shopify itself had asserted that binding.

### Impact Explanation
This is a cross-tenant authentication/binding bypass: the app's own webhook-processing code (`Registry.process`) trusts `request.shop` as the authenticated tenant identifier post-HMAC-check, but that field carries no cryptographic binding to the signed payload. A malicious tenant can inject data (or trigger handler side effects, e.g. mandatory `customers/redact`, `shop/redact` handling, order/customer state changes, uninstall handling) attributed to a different, victim shop, without ever needing the app's `client_secret`. This matches the "Critical — cross-tenant access" impact bucket via a genuine identity-binding break (shop authenticated vs. bytes actually verified by HMAC).

### Likelihood Explanation
Likelihood is realistic for any unprivileged internet user who can install the app on a shop they control: they only need to capture one legitimate webhook delivery (body + `hmac-sha256` header) that Shopify sends them, then replay it with altered `shop-domain`/`topic` headers to the app's public webhook endpoint. No secret, token, or privileged access is required — only observation of traffic Shopify already legitimately sent to the attacker's own store.

### Recommendation
Include the tenant/topic-identifying fields in the signed material, or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the HMAC check — e.g., have `to_signable_string` incorporate the normalized headers alongside the body, or have `HmacValidator`/`Registry.process` independently verify that the `shop` header matches a shop already known to be associated with this app installation (e.g., via session/offline-token lookup) before dispatching to `handler.handle`, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app registers for (e.g., `orders/create`).
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header from that legitimate delivery — both are valid because `Webhooks::Request#to_signable_string` only signs `@raw_body`. [5](#0-4) 
3. Resend the identical body and `hmac-sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `HmacValidator.validate` returns `true` (body/secret unchanged), so `Registry.process` does not raise `Errors::InvalidWebhookError` and calls `handler.handle` with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...)`, causing the host app to act as if Shopify verified that this data belongs to the victim shop. [6](#0-5)
