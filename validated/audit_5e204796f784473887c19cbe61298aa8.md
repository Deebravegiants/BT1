### Title
Secondary `FungibleStore` objects remain ungated-transferable by default, letting holders bypass dispatchable withdraw/deposit custody hooks via `object::transfer` - (File: `aptos-move/framework/aptos-framework/sources/fungible_asset.move`)

### Summary
The custody invariant the external report reduces to is: *a security-critical guard/authority check must be evaluated on every path that can mutate the protected state; if any code path exists that changes the protected state without triggering the guard's tracked accounting, the guard's protections are silently bypassed.* In the HSG bug, the Safe's guard tracked module count and could be defeated because another privileged code path (a different module) mutated the enabled-modules set without updating the guard's bookkeeping.

The Aptos-native analog exists in the fungible asset / dispatchable fungible asset design. `dispatchable_fungible_asset` exists specifically so issuers can enforce custody rules — denylists, KYC allowlists, deflation, predicated transfers — on every withdraw/deposit [1](#0-0) . However, a `FungibleStore` is also an ordinary Aptos `Object`, and `fungible_asset::create_store` only disables ungated object transfer when the *metadata* itself is marked `Untransferable`; otherwise the store keeps `allow_ungated_transfer = true` by default: [2](#0-1) .

Because `allow_ungated_transfer` stays `true`, any holder of a non-primary store can call the generic object-transfer entrypoints `object::transfer`/`object::transfer_call`/`object::transfer_raw`, which move the whole `FungibleStore` object (and therefore its entire balance) to any address by mutating `ObjectCore.owner` directly: [3](#0-2) . This path never calls `fungible_asset::withdraw`/`deposit`, `dispatchable_fungible_asset::withdraw`/`deposit`, or any dispatch hook (`dispatch_withdraw_hook`/`dispatch_deposit_hook`) that an issuer registered via `register_dispatch_functions` [4](#0-3) [5](#0-4) .

By contrast, Aptos explicitly recognized this exact risk for primary stores and hard-coded a fix there: `create_primary_store` always calls `transfer_ref.disable_ungated_transfer()` with the comment "Disable ungated transfer as deterministic stores shouldn't be transferrable" [6](#0-5) . No equivalent protection exists for secondary stores created directly via `fungible_asset::create_store`, which is a public API intended for "applications ... to create multiple stores for isolating fungible assets for different purposes" [7](#0-6) .

### Finding Description
1. An issuer creates a fungible asset and registers dispatch functions to enforce a custody-relevant rule at the withdraw/deposit layer (e.g., a denylist, a KYC allowlist, a "predicated transfer" gate, or a deflation/fee mechanism) via `dispatchable_fungible_asset::register_dispatch_functions`, without separately marking the metadata `Untransferable`.
2. A holder creates or receives a secondary (non-primary) `FungibleStore` object for that asset via `fungible_asset::create_store`. Because `is_untransferable(metadata)` is false (the issuer only gated transfers at the withdraw/deposit layer, not via the object-level `Untransferable` marker), the resulting store object has `allow_ungated_transfer = true` (`fungible_asset.move` lines 894-917).
3. Instead of calling `dispatchable_fungible_asset::transfer` (which would invoke `withdraw`/`deposit` and thus the issuer's dispatch hooks — the denylist/allowlist/predicate check), the holder calls `object::transfer`/`object::transfer_call` directly on the store's object address.
4. `object::transfer_raw` only checks `verify_ungated_and_descendant`, which merely checks `allow_ungated_transfer` and object nesting depth — it has no knowledge of, and never calls, the fungible-asset dispatch machinery (`object.move` lines 572-594, 605-639).
5. `transfer_raw_inner` unconditionally reassigns `ObjectCore.owner` to the new address, moving custody of the entire store balance with it, with none of the issuer's withdraw/deposit invariants (denylist checks, freeze-on-transfer semantics tied to the hook, deflation) ever evaluated.

The corrupted state is `ObjectCore.owner` for the `FungibleStore` object: it is changed to an unauthorized recipient chosen by the current holder, completely outside of the custody-control path (`dispatchable_fungible_asset::withdraw`/`deposit`) that the asset issuer relied on to gate exactly this kind of transfer. The `frozen` boolean on `FungibleStore` and the FA `Supply` accounting are untouched by this path — the FA's dispatch-based transfer-authorization layer is bypassed entirely, silently defeating any denylist/allowlist/predicated-transfer/deflation control that is only enforced in the dispatch hooks rather than as an object-level `Untransferable` restriction.

### Impact Explanation
This breaks the confidentiality/authority model that `dispatchable_fungible_asset` (AIP-73) is designed to provide: issuers relying on dispatch hooks for denylist/KYC gating, predicated transfers, or fee/deflation enforcement can have their entire economic model bypassed for any non-primary store, because holders can move full balances to arbitrary addresses without ever calling `withdraw`/`deposit`. This is a supply/custody accounting corruption that moves value to the wrong holder — assets end up in a wallet the issuer's rules were specifically designed to prevent (e.g., a denylisted or non-KYC'd address), and any fee/deflation the protocol depends on for solvency is skipped. Because this affects any fungible asset issuer that uses dispatch hooks without independently marking their metadata `Untransferable`, and multiple real modules in this codebase build custody logic on top of dispatch hooks (deflation token, allowlist examples, `fa_coin`/`FACoin.move` pause+denylist pattern using deposit/withdraw overrides), the impact is high: unauthorized asset movement and bypass of built-in custody controls at the object layer for any non-primary-store deployment.

### Likelihood Explanation
Likelihood is high because:
- No special permission is required — any owner of a secondary `FungibleStore` object can invoke the fully public `object::transfer_call`/`object::transfer`/`object::transfer_raw` entry functions.
- The bypass requires no interaction with the fungible-asset module at all — it operates purely at the generic `object` layer, which has no notion of fungible-asset dispatch semantics.
- The documented examples of dispatch usage (denylist, predicated transfer, deflation, loyalty token) in `dispatchable_fungible_asset.move`'s own module doc do not, by themselves, imply `Untransferable` metadata; nothing in the framework enforces that issuers who register dispatch hooks must also mark their metadata untransferable, so this misconfiguration is easy to fall into and not flagged anywhere in the API.

### Recommendation
When `fungible_asset::create_store` creates a store for a metadata that has dispatch functions registered (`is_store_dispatchable`/`is_asset_type_dispatchable`), disable `allow_ungated_transfer` on the new store's `ConstructorRef` by default (mirroring what `primary_fungible_store::create_primary_store` already does), forcing all balance movement to go through `dispatchable_fungible_asset::withdraw`/`deposit` (and thus through the issuer's dispatch hooks). Alternatively, document loudly and enforce at registration time (`register_dispatch_functions`) that any dispatchable asset's metadata must also be `Untransferable`, and add an explicit check/abort in `register_dispatch_functions` if it is not.

### Proof of Concept
1. Issuer publishes a fungible asset and calls `dispatchable_fungible_asset::register_dispatch_functions` with a custom `withdraw`/`deposit` pair that enforces a denylist (reject transfers to a blocked address) — but does **not** call `object::set_untransferable`/mark the metadata `Untransferable`.
2. Alice creates (or is given) a secondary `FungibleStore` for that asset via `fungible_asset::create_store` and receives a deposit of 1,000 units through the normal dispatched `deposit` path (denylist enforced).
3. Alice wants to send funds to `Bob`, an address on the denylist. Calling `dispatchable_fungible_asset::transfer(alice, alice_store, bob_store, 1000)` would correctly abort in the custom `withdraw`/`deposit` hook.
4. Instead, Alice calls `object::transfer_call(alice_signer, alice_store_address, bob_address)` (or `object::transfer<FungibleStore>(alice, alice_store_object, bob_address)`).
5. `object::transfer_raw` checks only `allow_ungated_transfer` (true, since `create_store` never disabled it) and reassigns `ObjectCore.owner` of the `FungibleStore` to `bob_address` — moving the full 1,000-unit balance to Bob without ever invoking the denylist-enforcing `withdraw`/`deposit` dispatch hooks.
6. Bob (a denylisted address) now fully owns the `FungibleStore` object and can withdraw/spend the 1,000 units normally, with the issuer's custody control permanently and silently defeated for that store.

**Note on confidence**: I was not able to directly execute this scenario in a live Move test environment (no code execution tools available in this ask-only session); the finding is based on static analysis of the cited source showing (a) `create_store` does not disable ungated transfer unless the metadata is separately marked `Untransferable`, (b) `object::transfer_raw`/`transfer_call` are unauthenticated-by-dispatch generic entrypoints that mutate `ObjectCore.owner` directly, and (c) `primary_fungible_store` explicitly works around this exact risk for primary stores only. A Devin session with Move-test execution would be needed to confirm the exact abort/success behavior end-to-end.

    /// Allow an object to hold a store for fungible assets.
    /// Applications can use this to create multiple stores for isolating fungible assets for different purposes.
    public fun create_store<T: key>(
        constructor_ref: &ConstructorRef, metadata: Object<T>
    ): Object<FungibleStore> {
        let store_obj = &constructor_ref.generate_signer();
        move_to(
            store_obj,
            FungibleStore { metadata: metadata.convert(), balance: 0, frozen: false }
        );

        if (is_untransferable(metadata)) {
            constructor_ref.set_untransferable();
        };

        if (default_to_concurrent_fungible_balance()) {
            move_to(
                store_obj,
                ConcurrentFungibleBalance {
                    balance: aggregator_v2::create_unbounded_aggregator()
                }
            );
        };

        constructor_ref.object_from_constructor_ref<FungibleStore>()
    }

    /// Transfers ownership of the object (and all associated resources) at the specified address

    public entry fun transfer<T: key>(
        owner: &signer,
        object: Object<T>,
        to: address,
    ) {
        transfer_raw(owner, object.inner, to)
    }

    /// Attempts to transfer using addresses only. Transfers the given object if
    /// allow_ungated_transfer is set true. Note, that this allows the owner of a nested object to
    /// transfer that object, so long as allow_ungated_transfer is enabled at each stage in the
    /// hierarchy.
    public fun transfer_raw(
        owner: &signer,
        object: address,
        to: address,
    ) {
        let owner_address = signer::address_of(owner);
        verify_ungated_and_descendant(owner_address, object);
        transfer_raw_inner(object, to);
    }

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };
    }
