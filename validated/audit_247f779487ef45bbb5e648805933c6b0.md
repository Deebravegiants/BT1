### Title
Status/hash misreport for batched same-asset withdrawals due to index-blind matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the status of a specific withdrawal by calling `findMatchingWithdrawal()`, which matches purely on `assetId` and ignores the `index` that uniquely identifies which withdrawal within a batched NEAR transaction is being queried. When a single NEAR transaction contains two or more withdrawals of the same token (a supported batch pattern, e.g. via `sdk.createWithdrawalIntents`/`estimateWithdrawalFee` batch APIs), every `describeWithdrawal({ index })` call returns the same first-matching record from the POA indexer response regardless of the requested index.

`findMatchingWithdrawal` uses `Array.prototype.find` keyed solely on `nep141:${w.data.near_token_id} === assetId`, with no use of `args.index` and no disambiguation by destination address or amount. The function's own docstring acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" — but this is only a documentation comment, not an enforced guard; callers can still create two withdrawal intents for the same asset in one NEAR transaction (the `Bridge` interface's `createWithdrawalIdentifier` explicitly takes an `index` for exactly this scenario, and the SDK supports batching, as shown by `sdk.estimateWithdrawalFee`/`createWithdrawalIntents` accepting arrays of `withdrawalParams`).

When two withdrawals of the same `assetId` (but different destination addresses/amounts) are included in one NEAR transaction, calling `describeWithdrawal({ index: 0, ... })` and `describeWithdrawal({ index: 1, ... })` both resolve to the same POA API record (the first one matching the assetId in the unsorted `withdrawals` array), because `index` is never consulted. This breaks the equality "status/txHash reported for withdrawal N == the on-chain outcome for withdrawal N": both index-0 and index-1 queries can report the same `status: "completed"` and the same `txHash`, even though only one of the two on-chain destination transfers may have actually completed.

### Impact Explanation
An integrator that submits a batched withdrawal of the same POA-bridged asset to two different destinations, and then polls `describeWithdrawal` per index to decide when to credit/settle each leg, can be told that the second withdrawal is `"completed"` with a specific `txHash` while that withdrawal has not actually reached the destination chain (or while that hash belongs to the first withdrawal's transfer). This is a status/hash misreport that can cause an integrator to credit or settle a withdrawal that has not actually landed — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category in scope.

### Likelihood Explanation
Requires no privileged access and no malicious relayer/bridge/RPC behavior — only that a legitimate, unprivileged caller submits a batch of withdrawals for the same POA-bridged asset within a single NEAR transaction (a pattern the SDK's public API supports, since `WithdrawalParams` can be an array and `index` exists specifically to disambiguate multiple withdrawals from one transaction). The condition is a same-asset, same-transaction batch, which is a realistic usage pattern rather than a contrived edge case, though it does require the integrator to actually batch multiple withdrawals of the identical token.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` by also comparing destination address (and/or amount) in addition to `assetId`, or fail loudly (throw) when more than one withdrawal record matches the same `assetId` and the caller cannot be safely disambiguated, instead of silently returning the first match for every index. At minimum, `describeWithdrawal` should refuse to resolve (return `pending`/throw) rather than return a possibly-wrong `completed` status/txHash when multiple same-asset withdrawals exist in one transaction.

### Proof of Concept
1. Build one NEAR transaction with two `ft_withdraw` intents for `nep141:btc.omft.near`: one to address `A`, one to address `B` (both same asset, one tx hash `TX`).
2. Call `sdk`'s POA-bridge path: `bridge.createWithdrawalIdentifier({ withdrawalParams: paramsA, index: 0, tx: { hash: TX } })` and `bridge.createWithdrawalIdentifier({ withdrawalParams: paramsB, index: 1, tx: { hash: TX } })`.
3. Suppose the POA indexer's `getWithdrawalStatus({ withdrawal_hash: TX })` returns `withdrawals: [{ status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "hashA", address: A, ... } }]` (only the first leg indexed/completed so far).
4. Call `bridge.describeWithdrawal(widIndex0)` → returns `{ status: "completed", txHash: "hashA" }` (correct).
5. Call `bridge.describeWithdrawal(widIndex1)` → because `findMatchingWithdrawal` ignores `index` and matches only by `assetId`, it also returns `{ status: "completed", txHash: "hashA" }` — misreporting withdrawal #1 (to address `B`) as completed with a tx hash that actually belongs to withdrawal #0 (to address `A`), even though no on-chain transfer to `B` has happened yet. 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
