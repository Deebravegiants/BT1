## Analysis

The Sherlock report's bug class—**a status/permission gate that blocks legitimate fund withdrawal even for users who deposited before the gate was flipped**—has a direct analog in the Raydium AMM program's `AmmStatus` permission model.

### Title
Pool `Disabled` status permanently blocks LP withdrawal, freezing user/LP funds with no redemption path - (`program/src/processor.rs`, `program/src/state.rs`)

### Summary
`process_withdraw` gates all withdrawals behind `AmmStatus::withdraw_permission()`. For every status except `Uninitialized` and `Disabled`, withdrawal is permitted. However, when the pool owner sets the status to `Disabled` via `process_set_params`, `withdraw_permission()` returns `false`, and any subsequent `Withdraw` instruction reverts with `AmmError::InvalidStatus`, exactly mirroring the reported pattern where a legitimate exit path reverts once an admin-controlled flag changes state.

### Finding Description
`AmmStatus::withdraw_permission()` explicitly returns `false` for both `Uninitialized` and `Disabled`, while all other statuses (`WithdrawOnly`, `LiquidityOnly`, `OrderBookOnly`, `SwapOnly`, `WaitingTrade`) return `true`: [1](#0-0) 

`process_withdraw` enforces this permission unconditionally before any transfer logic runs: [2](#0-1) 

The status is set by the pool owner through `process_set_params` (`AmmParams::Status`), which accepts any value passing `AmmStatus::valid_status`, including `Disabled` (`2u64`): [3](#0-2) [4](#0-3) 

Unlike `process_withdrawpnl`, which only disallows the `Uninitialized` status ("withdrawpnl in all status except Uninitialized"), the LP-owner-facing `process_withdraw` path additionally disallows `Disabled`: [5](#0-4) 

There is no alternate instruction in the program that lets an LP holder burn LP tokens and redeem the underlying `coin`/`pc` vault balances while the pool is `Disabled`. Once the owner (a one-time, prior, privileged action — analogous to de-whitelisting an asset) flips the pool to `Disabled`, every unprivileged LP holder's outstanding LP position becomes permanently unredeemable through the program's normal withdrawal instruction.

### Impact Explanation
Any LP already holding pool LP tokens at the time the owner sets `Disabled` loses the ability to redeem their share of the `coin_vault`/`pc_vault` for as long as (or permanently, if) the status remains `Disabled`. This is a permanent freezing of LP funds via the standard exit path, matching the medium-severity impact class described in the reference report (users unable to redeem their position due to a status/whitelist gate).

### Likelihood Explanation
The path is trivially reachable: any account holding LP tokens for the pool can submit a normal `Withdraw` instruction with correctly matched accounts once the pool owner has (at some earlier point) called `SetParams` with `AmmParams::Status = Disabled`. No exotic accounts or race conditions are needed — the only precondition is the owner-controlled status flag, which is a normal operational lever already exposed by the program (e.g., for incident response), making the freeze scenario realistically reachable.

### Recommendation
Allow `Disabled` status to retain `withdraw_permission() == true` (similar to how `withdrawpnl` only blocks `Uninitialized`), so LP holders can always redeem their share of vault assets regardless of whether swaps/deposits are paused. If `Disabled` is meant strictly as a "kill switch" that should still allow orderly exit, decouple the withdraw gate from the general status enum, or add an explicit emergency-withdraw path that bypasses `Disabled` while still enforcing all other safety checks (vault/mint/authority validation).

### Proof of Concept
1. Pool owner calls `SetParams` with `param = AmmParams::Status`, `value = Some(2)` (`Disabled`) via `process_set_params`.
2. An LP holder who deposited before this call attempts `Withdraw` with a valid `WithdrawInstruction { amount, .. }` and all correct accounts.
3. `process_withdraw` calls `AmmStatus::from_u64(amm.status).withdraw_permission()`, which returns `false` for `Disabled`, and the instruction reverts with `AmmError::InvalidStatus` before any token transfer occurs.
4. The LP's tokens remain locked in the vault with no instruction in the program capable of redeeming them while the pool stays `Disabled`.
