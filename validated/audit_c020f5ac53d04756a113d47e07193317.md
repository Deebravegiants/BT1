### Title
Webhook shop/topic/webhook-id headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which the gem hands to app-registered handlers as the trusted identity of the webhook — are read directly from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#hmac` decodes the `hmac-sha256` header value to compare against a signature computed purely from that body: [2](#0-1) 

`HmacValidator.validate` performs a constant-time comparison of `compute_signature(verifiable_query.to_signable_string, secret)` against the received signature — i.e. it authenticates `@raw_body` and nothing else: [3](#0-2) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from request headers, none of which participate in `to_signable_string`: [4](#0-3) 

The identity binding that should hold is:
`bytes verified by HMAC == bytes the app treats as authenticated (body + shop + topic + webhook_id)`

but the actual binding is only:
`bytes verified by HMAC == raw_body`

Since a single app-level `client_secret` (`Context.api_secret_key`) signs webhooks for *every* shop that installs the app, an attacker who has installed the app on their own (low-privilege) shop can legitimately receive a correctly-signed webhook (`raw_body`, `hmac`) for their own tenant. They can then replay that same `raw_body`/`hmac` pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers to any value they choose — the HMAC check in `Registry.process` will still pass because it only ever re-validates `raw_body`, and the resulting `Request#shop`/`#topic`/`#webhook_id` values handed to the app's handler are attacker-controlled and unauthenticated.

### Impact Explanation
This breaks the shop/tenant identity binding that consuming applications rely on when they call `ShopifyAPI::Webhooks::Registry.process(request)` and dispatch based on `request.shop`. An attacker who legitimately controls one shop can forge webhook events attributed to a different (victim) shop domain, since the shop identity is never cryptographically bound to the signed payload. This is a cross-tenant confusion vector at the gem level (High/Critical class per the rubric: cross-tenant access), because the gem's own webhook-verification primitive fails to bind the field it exposes as the tenant identifier (`shop`) to the authenticated bytes.

### Likelihood Explanation
Likelihood is moderate-to-high: the only capability required is the ability to install the app on any shop (an ordinary, low-privilege action for any merchant/developer), capture one legitimately signed webhook delivered to that shop, and replay it to the app's public webhook endpoint with modified headers. No access to `client_secret`, tokens, or the victim shop is needed — only observation of a header format that is publicly documented by Shopify.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them (e.g., require the app to independently confirm the `shop` against a value obtained through an authenticated channel, such as the corresponding stored session, before trusting `Request#shop` for tenant routing). At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be used as the sole tenant-routing key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged onboarding flow).
2. Shopify delivers a legitimately-signed webhook to the app for that shop: `raw_body = "{...}"`, header `X-Shopify-Hmac-Sha256 = Base64(HMAC-SHA256(client_secret, raw_body))`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is built; `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC — as verified in the test's expected flow, e.g. `assert_equal(@shop, data.shop)` derived purely from the header: [5](#0-4) 
5. The app's registered handler receives `data.shop == "victim-shop.myshopify.com"` and `data.body` equal to the attacker's payload, processing it as if it originated from the victim's shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
