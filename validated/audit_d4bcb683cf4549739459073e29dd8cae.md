Good — the AuthQuery case actually confirms `shop` and `host` ARE covered by the HMAC in `to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), so OAuth callback is solid: the `shop` used to build the session is part of the signed payload validated in `HmacValidator.validate` [1](#0-0) . The webhook path is different: `Request#to_signable_string` returns only `@raw_body`, while `shop` comes from the `shopify-shop-domain` header, entirely outside the signed content, and is passed straight into `WebhookMetadata.shop` used by the host app's handler.### Title
Webhook shop identity (`X-Shopify-Shop-Domain`) is not covered by the HMAC signature, allowing cross-tenant data injection via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC using only the raw request body, but hands the caller-supplied `shop` header value — which is completely outside the signed content — to the app's handler as the tenant identity. This breaks the intended binding: `HMAC(secret, verified_bytes) == received_hmac` should imply that every field the app trusts (including which shop the payload belongs to) was authenticated, but here `shop` is parsed and trusted without being covered by the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [2](#0-1) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [3](#0-2) , while `Request#shop` is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [4](#0-3) .

`Registry.process` validates the HMAC and, on success, immediately builds `WebhookMetadata` using `request.shop` (the header) alongside `request.parsed_body`, and dispatches it to the app's handler as the authoritative tenant for the payload: [5](#0-4) .

This is the exact bug class from the analog report: a field the application acts on (`shop`, used to attribute/scope the webhook body) is not covered by the cryptographic check that is supposed to authenticate the whole request. The gem's own documentation instructs handler implementations to treat `data.shop` as the trusted shop domain of the webhook and use it to scope work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), confirming this is the gem's documented, intended trust boundary rather than a host-app misuse: [6](#0-5) .

Concretely:
- Before request: `computed_hmac(raw_body) == received_hmac` is the only check performed; `shop` is unconstrained.
- After request: the handler receives `WebhookMetadata{shop: <attacker-controlled header>, body: <raw_body-derived, HMAC-verified>}` and typically persists/acts on `body` under the identity of `shop`.

An attacker who is an unprivileged internet user with a legitimate install of the app on their own store receives real, validly-HMAC'd webhooks from Shopify for their own shop (this requires no privileged credential — merely installing a public/free app is normal unprivileged access). Because only `raw_body` is signed, the attacker can resend that exact validly-signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The signature still validates (it never inspected the header), and the handler executes attacker-controlled webhook data attributed to the victim's tenant — a cross-tenant data-integrity breach at the trust boundary the gem is supposed to enforce.

This mirrors the report's pattern precisely: the report showed `amountOutMinimum` decoupled from the actual claimed reward balance, breaking the intended `swap-output == committed-minimum` invariant; here, `shop` is decoupled from the HMAC-verified `raw_body`, breaking the intended `verified-body == verified-tenant` invariant.

### Impact Explanation
This qualifies as **Critical - cross-tenant access**: a request whose body is verified as genuinely originating from Shopify (for the attacker's own shop) can be relabeled to another merchant's shop identity and processed by the host application as if it belonged to that other tenant, without needing the app's `client_secret`, without TLS interception, and without a privileged account (only a self-service app installation is required to obtain a genuine signed body/HMAC pair).

### Likelihood Explanation
Medium-High. It requires the attacker to (1) install/interact with the app on a shop they control to obtain at least one legitimately signed webhook body/HMAC pair, and (2) resend it to the same public webhook endpoint with a modified `shop-domain` header — both trivially achievable by any unprivileged internet user, using only documented, unauthenticated HTTP headers. No brute-forcing of the HMAC secret is needed.

### Recommendation
Bind the `shop` domain (and ideally `topic`/`webhook_id`) into the signed content, or otherwise authenticate the header out-of-band (e.g., cross-check against the shop recorded for the corresponding registered webhook/subscription, or require the app to independently verify `shop` against session/install records before trusting it) rather than deriving the trusted tenant purely from an unsigned header. At minimum, update `Request#to_signable_string` (or `Registry.process`) to include the `shop` header value in what is verified, and document that `WebhookMetadata.shop` must not be treated as authenticated by the HMAC check alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a POST with body `B` and a valid `x-shopify-hmac-sha256` computed as `HMAC(secret, B)`.
2. Attacker resends the identical POST to the app's webhook route, keeping `raw_body = B` and the original valid HMAC header, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == received_hmac` [7](#0-6)  — this passes because `B` and the HMAC are unchanged.
4. `WebhookMetadata.new(shop: request.shop, ...)` now carries `shop = "victim-shop.myshopify.com"` [8](#0-7) , and the handler processes attacker-controlled `body` data as if it belongs to the victim's shop, per the gem's documented handler contract [6](#0-5) .
