### Title
Unbounded-depth SCALE decode of attacker-controlled cross-chain calldata enables stack-overflow DoS of the destination chain in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an attacker-supplied, arbitrary-length byte blob into `T::RuntimeCall` using plain `Decode::decode`, with no recursion-depth limit, before dispatching it. The sibling pallet `pallet-call-decompressor` in the same repository handles the structurally identical problem (decoding an untrusted, attacker-supplied `RuntimeCall`) correctly by using `decode_all_with_depth_limit` bounded to `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT`, showing the maintainers are aware of this class of bug elsewhere but did not apply the same mitigation here.

### Finding Description
In `on_accept`, after crediting the beneficiary, optional calldata is processed: [1](#0-0) 

The `runtime_call` field of `SubstrateCalldata` is a raw `Vec<u8>` fully controlled by whoever sends the cross-chain message on the source chain (via the `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract's `data` field, or `SendParams.call_data` on a peer substrate chain): [2](#0-1) 

It is decoded with an unbounded `Decode::decode` call: [3](#0-2) 

SCALE's derive-based `Decode` implementation recurses through nested types (e.g. `RuntimeCall` variants such as `Utility::batch(Vec<RuntimeCall>)`, `Proxy`, nested `Option`/`Box` wrappers, etc.). Without a bound on nesting depth, an attacker can craft a small but deeply-nested encoded call that drives the decoder's call stack to exhaustion, causing a stack overflow / process abort during block execution.

This is exactly the failure mode `pallet-call-decompressor` guards against explicitly: [4](#0-3) [5](#0-4) [6](#0-5) 

`pallet-hyper-fungible-token` never calls `decode_all_with_depth_limit` anywhere in the codebase — it is the only pallet in the repo that decodes an attacker-controlled `RuntimeCall`-shaped payload without this guard.

### Impact Explanation
`on_accept` runs during ISMP message execution, i.e. inside `pallet_ismp::Pallet::<T>::handle_unsigned` / `execute`, which every full node and collator must run identically to reach consensus on the same block. A crafted deeply-nested `runtime_call` blob that overflows the stack during decode would abort the process on every node processing that block, halting block production/finalization for the entire parachain — a chain-wide denial of service triggered by a single cross-chain message from an unprivileged sender (anyone who can call the peer `HyperFungibleToken` contract on the source chain with a non-empty `data` field, no special privilege required). This is reachable purely through the intended "token bridger" cross-chain calldata-execution feature described in the pallet's own documentation, not through any admin/governance/privileged path.

### Likelihood Explanation
The attack requires no privileged access, no proof forgery, and no capital: any account able to submit a source-chain transfer through the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` contract can set an arbitrary `data` payload. Once the cross-chain message is relayed and delivered via `handle_unsigned`, `on_accept` will attempt the vulnerable decode unconditionally whenever `message.data` is non-empty, with the only pre-condition being an amount transfer to a registered asset (a normal, permissionless flow per the pallet's documentation).

### Recommendation
Replace the unbounded `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` call in `on_accept` (and the analogous decode in `on_timeout`/refund paths, if present) with `T::RuntimeCall::decode_all_with_depth_limit(MAX_DECODE_DEPTH_LIMIT, &mut &*substrate_data.runtime_call)`, mirroring the mitigation already present in `pallet-call-decompressor::decode_and_execute`. Also bound `substrate_data.runtime_call`'s byte length before decode to avoid unrelated resource exhaustion.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send(...)` (or the peer substrate `send` extrinsic) targeting the vulnerable chain, setting `data` to a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <deeply nested RuntimeCall, e.g. thousands of nested Utility::batch(vec![Utility::batch(vec![...])]) encodings> }`.
2. A relayer submits the resulting ISMP `PostRequest` via `pallet_ismp::Pallet::<T>::handle_unsigned`.
3. `pallet-hyper-fungible-token::on_accept` is invoked by the ISMP router, reaches line 189, and calls the unbounded `T::RuntimeCall::decode`, which recurses to the configured nesting depth of the payload and overflows the stack on every node executing the block, since the same decode occurs identically during block import.

Note: I could not find or verify a concrete maximum SCALE recursion depth constant/config that would already bound this in this repo outside of `pallet-call-decompressor`'s pallet-local constant, so the exact byte size required to trigger a stack overflow in this specific runtime build is unconfirmed without running the actual binary — this would need to be validated experimentally in a Devin session with access to build/test tooling.
