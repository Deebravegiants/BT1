### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but then trusts the unauthenticated `shop-domain` HTTP header when constructing the `WebhookMetadata` passed to the host application's handler. This mirrors the FUEL1-16 bug class: a field that is *acted upon* by downstream logic is not actually *covered* by the cryptographic integrity check, breaking the intended binding `verified_bytes == interpreted_bytes` (here, `hmac_covers(body) != identity_used_for(shop)`).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately builds `WebhookMetadata` using `request.shop` (along with `topic`, `api_version`, `webhook_id`, all likewise header-derived and unsigned) and hands it to the app-provided handler as though it were verified data: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no additional validation performed anywhere in the library: [4](#0-3) 

Because Shopify's HMAC signature (`X-Shopify-Hmac-SHA256`) is computed over the JSON body only, an attacker who is a legitimate merchant on their own store can capture a genuinely-signed `(body, hmac)` pair delivered to their own webhook subscription, then replay that exact `(body, hmac)` pair directly to the same app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `topic`/`webhook-id`) with a victim shop's domain. `Registry.process` will accept it: `Utils::HmacValidator.validate` succeeds (body/HMAC pair is authentic), and the handler receives `data.shop` pointing at the victim tenant while `data.body` actually contains attacker-controlled content from the attacker's own store event. No `api_secret_key`, access token, or TLS interception is required — the attacker only needs their own valid app installation and the ability to POST to the webhook endpoint.

### Impact Explanation
If the host application uses `WebhookMetadata.shop` as the tenant key to write, update, or invalidate data (a very common pattern — e.g., updating order/customer/inventory records keyed by shop), this allows a cross-tenant write/confusion: attacker-controlled data attributed to and processed under a different shop's identity, without ever compromising that shop's credentials. This satisfies the "Critical - cross-tenant access" impact bar, since the identity binding between HMAC-verified bytes and the shop identifier the library exposes as authenticated is broken.

### Likelihood Explanation
Likelihood is realistic: it only requires the attacker to install the target app on any shop they control (a normal, unprivileged action), capture one legitimate webhook delivery for that shop, and replay it with a modified header to the same public endpoint. No secrets, tokens, or network interception are needed.

### Recommendation
Either (a) reject or ignore `shop`/`topic`/`webhook-id`/`api-version` values that are not independently verified, or (b) incorporate these header values into the HMAC-signed material check (or cross-check them against a registered webhook_id → shop mapping fetched from Shopify), so that `Registry.process` cannot be tricked into associating attacker-controlled but genuinely-HMAC'd bodies with an arbitrary shop. At minimum, documentation should explicitly warn implementers that `WebhookMetadata.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., matching against the shop associated with the given `webhook_id` via a stored subscription record).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`).
2. Shopify delivers: body `B`, header `X-Shopify-Hmac-SHA256: H = HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and sends a new POST directly to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` — this only checks `HMAC(secret, request.to_signable_string) == H`, i.e., `HMAC(secret, B) == H`, which is true.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and calls the host app's handler, which now processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
