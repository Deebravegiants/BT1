Confirmed: `WebhookMetadata` carries `shop` directly from the unauthenticated header value passed into every handler, and the HMAC only covers the raw body.### Title
Webhook `shop` identity not covered by HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body [1](#0-0) , while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers that are never part of the signed data [2](#0-1) . `Registry.process` validates only that HMAC before dispatching to the app's handler [3](#0-2) , and the unauthenticated `shop` header is forwarded verbatim into `WebhookMetadata`, the struct the host app relies on to know which tenant a webhook belongs to [4](#0-3) .

### Finding Description
The binding that should hold is: **shop attributed to a webhook == shop whose data actually produced the signed body**. Instead, the gem verifies only `HMAC(secret, raw_body) == received_signature` via `Utils::HmacValidator.validate` [5](#0-4) , and the `shop` field is taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header outside the signed scope [2](#0-1) .

Because the app's `api_secret_key` is shared across all shops that install the app (it's a per-app secret, not per-shop), any unprivileged user who installs the app on their own store receives genuine, validly-signed webhooks for their own shop. Nothing in this gem prevents that same person from replaying the identical `raw_body` + `x-shopify-hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop's domain). `Utils::HmacValidator.validate` will still return `true`, because the shop header is never part of `to_signable_string` [1](#0-0) . `Registry.process` then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and hands it to the handler as if it were authentic data for that shop [3](#0-2) .

Any host application that follows the gem's documented pattern — trusting `WebhookMetadata#shop` to look up/update per-tenant records (sessions, orders, GDPR data, etc.), exactly as shown in the gem's own usage docs — will process attacker-supplied (but real-body) events under the wrong tenant identity.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: an attacker with no privileges beyond installing the app on any shop can cause the app to process webhook data attributed to a shop they don't control, i.e., cross-tenant data injection through a component whose only reason for existing is to prove genuineness *and* origin of a webhook. Depending on how the host app keys logic off `WebhookMetadata#shop` (e.g. `app/uninstalled`, `customers/redact`, subscription billing events), this can lead to unauthorized state changes, forced data deletion, or record confusion for a shop the attacker never authenticated against.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on some shop the attacker controls (typical of any public/free Shopify app), and (2) direct HTTP access to the app's webhook endpoint (which is by definition internet-reachable). No access token, `client_secret`, or privileged account is needed — only a replay of a legitimately-received webhook body/HMAC pair with a substituted `shop-domain` header, which this gem's own `Request` parser and `HmacValidator` will accept.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signable content, or otherwise cryptographically tie the shop identity to the signature verification step — e.g., include the shop domain in the HMAC computation, or require the caller to supply/verify the expected shop out-of-band before trusting `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must not be used as a sole tenant identifier without additional verification (e.g., cross-checking against a known/installed-shop list).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any unprivileged self-serve install).
2. Shopify sends a legitimately signed webhook to the app, e.g. body `{"id":123}` with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of body with shared api_secret_key>`
3. Attacker captures this raw body + HMAC header and replays it directly to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request#hmac` still decodes the same valid signature, and `Utils::HmacValidator.validate` compares it against `HMAC(secret, raw_body)` — unaffected by the header change — so `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`.
