### Title
Unvalidated `shop` Parameter in `Oauth.begin_auth` Enables Forced OAuth Completion / Session Fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization redirect URL directly from the caller-supplied `shop` string without validating it against the gem's own trusted-domain allowlist (`Utils::ShopValidator`), even though every sibling authentication entry point in the same library (`ClientCredentials`, `RefreshToken`, `TokenExchange`) enforces that check before using `shop` to construct a request destination.

### Finding Description
`begin_auth` takes `shop:` as a raw parameter and passes it straight into `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` with no sanitization: [1](#0-0) [2](#0-1) 

The resulting `auth_route` (containing the app's `client_id`, requested `scope`, `redirect_uri` pointing at the real app's callback, and a freshly generated `state` nonce) is handed back to the host application to redirect the end user's browser to:
```ruby
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
{ auth_route: auth_route, cookie: cookie }
``` [3](#0-2) 

Nothing in `begin_auth` calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, unlike the client-credential/refresh-token/token-exchange flows in the same library, which explicitly gate the `shop` argument through `ShopValidator` before using it to construct a request target: [4](#0-3) 

The `docs/usage/oauth.md` example shows the typical (and expected) usage pattern: the host app reads `shop` straight from the request/query string and passes it to `begin_auth` before any HMAC has been verified (HMAC validation only happens later, in `validate_auth_callback`, on the *callback* leg, not on the *begin* leg): [5](#0-4) 

Because the `shop` value used to compute `auth_route` at this stage is unauthenticated (no HMAC or trusted-domain check protects it), an unprivileged attacker who can influence the `shop` query parameter (e.g. by sending a victim a link to the app's own login route with `?shop=attacker.example`) can make `begin_auth` return an authorization URL whose host is entirely attacker-controlled: `https://attacker.example/admin/oauth/authorize?client_id=...&redirect_uri=<real-app-callback>&state=<nonce>...`. The victim's browser is redirected there, carrying the app's `client_id`, the intended `redirect_uri` for the legitimate app, and the `state` nonce — all attacker-observable. The attacker's server can then drive its own interaction with the real Shopify `/oauth/authorize` endpoint using that harvested `redirect_uri`/`client_id`, and redirect the victim onward with an authorization `code`/`state` pair of the attacker's choosing, completing an OAuth flow against the victim's real app session (forced OAuth completion / state/session fixation), because the app's `validate_auth_callback` only checks that the callback `state` equals whatever value was placed in the victim's cookie by the very `begin_auth` call the attacker triggered — it never independently confirms that the *destination* the authorization request was actually sent to was a genuine Shopify domain.

This is the direct analog of the reported bug class: an identity-binding field (`shop`, which determines the trusted counterparty that will receive OAuth `state`/`client_id` and eventually issue an authorization `code`) is trusted and acted upon by `begin_auth` without being checked against the same allowlist that protects the equivalent field everywhere else in the library, breaking the equality `shop used to pick destination == shop verified as a genuine myshopify.com/trusted domain`.

### Impact Explanation
This matches the High-impact category "session fixation or forced OAuth completion": an unauthenticated attacker can redirect a victim's OAuth flow to an attacker-influenced host while carrying the legitimate app's `client_id` and callback URL, and control the `state`/nonce cookie set on the victim, undermining the CSRF/state protection that `validate_auth_callback` relies on. It does not expose `api_secret_key` (that is only sent later, in `validate_auth_callback`, over a call whose target session is built from `auth_query.shop`, which by that stage *is* HMAC-covered), so the worst-case blast radius here is state/session fixation on the begin-auth leg rather than secret exfiltration.

### Likelihood Explanation
High likelihood: `shop` is a standard, attacker-visible query parameter in every real-world Shopify app install/login flow (`?shop=...`), and the gem's own documentation instructs host apps to read it directly from the request and pass it, unsanitized, into `begin_auth`. No special access, credentials, or privileged account is required — any internet user who can get a victim to click a crafted link to the app's login route can trigger this path.

### Recommendation
Validate `shop` in `Oauth.begin_auth` against `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) before using it in `auth_base_uri`, exactly as is already done in `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/auth/token_exchange.rb`, raising `Errors::InvalidShopError` for any domain outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Host app exposes `GET /login?shop=<shop>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`, mirroring the documented usage.
2. Attacker sends victim a link: `https://victim-app.example/login?shop=attacker.example`.
3. `begin_auth` executes `auth_base_uri("attacker.example")` → `"https://attacker.example/admin"`, producing `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=<real client_id>&scope=...&redirect_uri=https://victim-app.example/auth/callback&state=<nonce>&grant_options[]=..."`, and a `state` cookie is set on the victim's browser.
4. Victim's browser is redirected to `attacker.example`, leaking `client_id`, `redirect_uri`, and `state` to the attacker, who now controls/observes the values needed to script a forced completion of the OAuth flow back at `https://victim-app.example/auth/callback`, whose only server-side check is `state == cookie_state` from step 3 — a value the attacker already influenced.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

```markdown
An example is shown below in a Rails app but these steps could be applied in any framework:

```ruby
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
