### Title
Webhook shop-domain header trusted for tenant identification but not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant identification directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as `WebhookMetadata#shop`, so the value an app uses to decide *which tenant* a webhook belongs to is never bound to the cryptographic proof that the request is authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from a header, never included in `to_signable_string`, and never re-checked against anything else: [3](#0-2) 

`Registry.process` only verifies the HMAC (over the body) and then forwards `request.shop` to the app's handler unchanged: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`bytes_verified_by_hmac == bytes_used_to_identify_the_tenant`

but the actual relationship is:
`bytes_verified_by_hmac (raw_body) != bytes_used_to_identify_the_tenant (shop-domain header)`

Any party that can obtain one valid `(raw_body, hmac)` pair — trivially available to any developer who installs the app on their own store (an "unprivileged internet user" with respect to other merchants' data) — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will call the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain. The library's own documentation confirms apps are expected to key their persistence/business logic off `data.shop` (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`), so this un-bound field is exactly the value host apps rely on to scope webhook processing to the correct tenant.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-used-as-identifier binding called out in the analog rules. An attacker who legitimately installs the target app on their own Shopify store can capture a real webhook (raw body + valid HMAC signed with the shared `api_secret_key`), then replay that body/HMAC pair against the app's webhook endpoint with the `shop-domain` header set to a victim shop's domain. Because the gem validates only body authenticity and passes the header-derived shop through untouched, the app will process cross-tenant events under the wrong tenant identity — e.g. updating another merchant's local records, triggering data sync/exfiltration keyed to the wrong shop, or performing unauthorized state changes attributed to a shop the attacker doesn't control. This is a cross-tenant access issue as defined by the Critical impact bucket.

### Likelihood Explanation
Likelihood is high for any app that (a) receives webhooks for multiple shops on a shared endpoint (the common single-endpoint webhook pattern shown in this gem's own docs) and (b) trusts `WebhookMetadata#shop` for tenant scoping, which is the documented/intended usage pattern. The attacker needs no special privileges beyond being able to install the app on any shop (including their own, low-cost/free), capture one webhook payload+signature, and replay it with a forged header — all doable with basic HTTP tooling, no access to `api_secret_key`, access tokens, or TLS interception required.

### Recommendation
Bind the shop identity into what is being verified: either (1) include the shop-domain header value in the signable string used for HMAC computation, matching against Shopify's authenticated delivery, or (2) require callers to independently corroborate `request.shop` against a shop already authenticated for that specific webhook subscription (e.g., compare against a stored mapping of subscription-id → shop, not a bare header), and document clearly that the shop header is unauthenticated and must not be used alone as a tenant key. Fail closed if the header-provided shop cannot be corroborated against an authenticated source.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new HTTP request to the app's public webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...spoofed shop...})` builds successfully (only header presence is checked, not header authenticity) — [6](#0-5) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds since `H` is a valid signature of `B` — [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled webhook content under the victim shop's identity — [8](#0-7) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
