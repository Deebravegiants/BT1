### Title
Webhook shop/topic identity trusted from unauthenticated headers while only the body is HMAC-covered, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are never included in the HMAC signature. Only the raw request body is signed. The gem verifies the body's HMAC and then unconditionally trusts the header-derived `shop` value when dispatching to the app's webhook handler, exactly the "field acted on but not covered by the HMAC" pattern described in the source report (there, a contract's existence check and its use were split across different code paths; here, the *authenticated* part of the webhook (body) and the *acted-upon* identity field (`shop` header) are similarly decoupled).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac` header — it never touches `shop`: [3](#0-2) 

`Registry.process` validates only that body-HMAC, then immediately forwards the unauthenticated `request.shop` (and other header fields) to the app-supplied handler: [4](#0-3) 

The gem's own documentation tells integrators that `data.shop` is "The shop domain of the webhook," presenting it as a trustworthy, verified identity field for tenant routing/lookup: [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is shared across every shop that has installed the app, any tenant that has legitimately installed the app can capture one of their own genuine webhook deliveries (valid body + valid `X-Shopify-Hmac-Sha256`, computed by Shopify itself — the attacker never needs to know the secret) and replay the identical bytes to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to name a different, victim tenant. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

Binding broken: `shop` claimed by header ≠ `shop` bound by the HMAC-signed bytes.

### Impact Explanation
This enables cross-tenant data injection: an app that follows the gem's documented pattern of using `data.shop` to look up the appropriate merchant/session record will process attacker-controlled body content under the identity of a different, victim merchant. This matches the "cross-tenant access" Critical-impact category, since one tenant's traffic can be attributed to and processed against another tenant's data/session without any credential of the victim being required.

### Likelihood Explanation
Any attacker who can install the target app on a shop they control (including a free Shopify dev/partner store) can trigger webhook events, capture the resulting HTTP request, and replay it with a forged shop header to the same publicly reachable webhook endpoint — no access to `api_secret_key`, access tokens, or the victim's credentials is required. Likelihood is Medium-High given how trivial the replay is once an attacker has any working install of the app.

### Recommendation
Bind tenant identity to the signed payload instead of trusting unauthenticated headers:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (e.g., sign a canonical string combining headers + body, similar to how `AuthQuery#to_signable_string` binds `shop`/`state`/`code` together), or
- At minimum, document and/or enforce that host applications must cross-check the header-derived `shop` against a shop known to have this specific `webhook_id`/subscription registered before trusting it, and consider rejecting replays via `webhook_id` de-duplication tied to the originating shop.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they legitimately control).
2. Attacker performs an action that triggers a subscribed webhook (e.g. `products/create`) and captures the raw HTTP request Shopify sends to the app's callback URL, including the body and the genuine `X-Shopify-Hmac-Sha256` header.
3. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (a shop that also has the app installed).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)`.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker-supplied data as though it originated from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
