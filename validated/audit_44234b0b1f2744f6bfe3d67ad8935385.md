### Title
Unprivileged whale-scale supply + 98% borrow permanently freezes a market via `i128` RAY-value overflow in accrual - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
The ChakraCore report is a memory-corruption class bug; in this Soroban codebase the analog is a checked-arithmetic overflow that corrupts liveness rather than memory. Every pool mutation first runs `interest::global_sync`, which computes market values as `scaled * index` in RAY via `scaled_to_original` / `Ray::mul` (`mul_div_half_up`). When `supplied * supply_index` (or `borrowed * borrow_index`) exceeds `i128::MAX ≈ 1.7e38`, `mul_div_*` panics with `MathOverflow`. Because accrual runs before every verb — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `claim_revenue` — a market pushed past this ceiling can never be touched again. The index cap `MAX_BORROW_INDEX_RAY = 1e36` does not save it: the value ceiling is hit at roughly `i128::MAX / borrowed`, i.e. an index of only ~170× for a large market, far below 1e36.

### Finding Description
- `contracts/pool/src/ops/mod.rs:30-34` — `synced_market` calls `interest::global_sync` before any mutation.
- `contracts/pool/src/interest.rs:39-53` — `accrue_chunk` calls `accrue_step`, which internally computes utilization and supplier rewards via `scaled_to_original(borrowed, borrow_index)` and `supplied.mul(old_index)` (`common/src/rates/index.rs:34`).
- `common/src/math/fp_core.rs:108-118` — `mul_div_half_up` panics with `MathOverflow` when the RAY product exceeds `i128`.
- `common/src/constants` caps the *index* at `MAX_BORROW_INDEX_RAY = 1e36`, but nothing caps the *value* `shares × index`; `docs/reference/invariants.md` (INV-IDX-01) concedes "debt-value overflow can still revert accrual before that ceiling," and `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` demonstrates the freeze end-to-end: after the cliff, both `withdraw` and `repay` fail with `MATH_OVERFLOW`.

Reachability for a single unprivileged address: supply a large quantity of a high-decimals, near-zero-price listed asset (decimals up to 18 are admitted), then borrow back ~98% of it using trivial collateral (the USD debt value is ~0, so `min_borrow_collateral_usd` and the health factor pass with dust). Supply caps can be saturated anyway (`calculate_scaled_cap` fails open at low supply index, INV-HALT-03), and `max_utilization` is a parameter, not a per-market hard bound; borrowing at the top of the curve maximizes the borrow rate (up to `MAX_BORROW_RATE_RAY = 2×RAY`), compounding the borrow index ~7.4× per untouched year. Once `borrowed × borrow_index` crosses `i128::MAX`, the next accrual panics and the market is bricked forever — all other suppliers' deposits are permanently frozen.

### Impact Explanation
Permanent freezing of user funds. Every entrypoint that touches the market accrues first, so `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` all revert with `MathOverflow`. Suppliers' principal and accrued interest are unrecoverable; even bad-debt socialization cannot run because it is also gated behind accrual. This is irreversible on Soroban — there is no admin path in the in-scope surface that mutates `borrow_index`/`borrowed` without accrual.

### Likelihood Explanation
The attacker controls the two driver variables: total supplied/borrowed shares (by choosing an asset with high decimals and low unit price, quantities near `i128::MAX / RAY` are cheap in USD terms) and utilization (borrowing 98% of their own supply requires only dust collateral since the debt's USD value is negligible). The remaining ingredient is time for the index to compound ~170× at the steep part of the curve; the attacker can keep utilization pinned by repaying/re-borrowing is unnecessary — doing nothing suffices since unpaid debt only grows the index. No privileged role, leaked key, or oracle manipulation is required; prices within their sanity bands suffice.

### Recommendation
Cap the market's RAY *value* rather than only the index: in `accrue_step`/`update_supply_index`, clamp `supplied` and `borrowed` (or the computed `new_index`) so that `shares × index` never exceeds a safe bound below `i128::MAX`, e.g. refuse accrual-driven growth past `MAX_RAY_VALUE` and treat further accrual as a no-op, mirroring how `update_supply_index` already clamps to `MAX_SUPPLY_INDEX_RAY` via `mul_div_floor_saturating`. Alternatively, bound `create_market`/listing parameters and supply caps so `total_supplied × MAX_BORROW_INDEX_RAY` provably fits `i128` for every admitted decimal count, and make `accrue_chunk` degrade gracefully (clamp index at the value ceiling) instead of panicking.

### Proof of Concept
Mirrored by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
let principal = BILLION * 10i128.pow(18);          // 1e9 whole tokens, 18 dp
t.supply_raw(BOB, "BIG18", principal);             // attacker supply
let debt = principal / 100 * 98;                   // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);                // attacker borrow-back
loop { t.advance_time(YEAR_SECS);                  // compound at steep curve
       if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } }
// update_indexes, withdraw, repay all revert with MATH_OVERFLOW (33)
// book.borrow_index < MAX_BORROW_INDEX_RAY: the index cap never engaged
```

The only change needed for a realistic attacker is financing: `BOB`/`ALICE` are the same unprivileged address, and the asset can be a cheap high-decimal listing so `principal`'s USD cost is small while its RAY share count is enormous.
