### Title
POA Bridge withdrawal status is matched only by `assetId`, causing wrong destination tx hash / status to be reported for one of two same-token withdrawals batched in the same transaction - ([File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts])

### Summary
`WithdrawalIdentifier.index` exists specifically to disambiguate multiple withdrawals created in the same NEAR transaction [1](#0-0) , and `describeWithdrawal` receives that index [2](#0-1) . The POA Bridge implementation, however, ignores the index entirely and resolves status/tx-hash purely by matching `assetId` against the API response, returning the **first** entry found.

### Finding Description
`findMatchingWithdrawal` in `waitForWithdrawalCompletion.ts` looks up a withdrawal by `assetId` only: [3](#0-2) 

The same pattern is duplicated in the SDK's `PoaBridge.describeWithdrawal`, which also matches by `assetId` and ignores `index`: [4](#0-3) 

The code comment explicitly acknowledges the gap: "multiple withdrawals of the same token in a single transaction are not supported" [5](#0-4) .

`WithdrawalIdentifier` was designed with an `index` field precisely for this scenario (distinguishing multiple withdrawals from the same `tx`) [1](#0-0) , and the SDK's own test explicitly documents that matching is "by assetId, not by index" [6](#0-5) , but that test only exercises the case where the two withdrawals use *different* assetIds — it never verifies the case the comment above admits is broken: two withdrawals of the *same* asset in the same tx.

Because `Array.prototype.find` returns the first match, when a caller creates two POA withdrawals of the same token in one NEAR transaction (e.g. `ft_withdraw` to two different destination addresses/amounts, both routed through PoaBridge), `describeWithdrawal({ index: 0, ... })` and `describeWithdrawal({ index: 1, ... })` will both resolve against the *same* underlying withdrawal record — reporting the same `status` and the same `transfer_tx_hash` for both, regardless of which one it actually corresponds to.

### Impact Explanation
This breaks the equality "status/txHash reported for withdrawal N corresponds to the on-chain outcome of withdrawal N." An integrator polling both withdrawal identifiers (via `watchWithdrawal`/`waitForWithdrawalCompletion`) sees "completed" with the same destination `txHash` for both entries, even though on-chain only one of the two transfers actually completed to that hash. This can lead an integrator to:
- Credit/refund the second withdrawal based on the first withdrawal's completion evidence (double credit), or
- Falsely mark a withdrawal as completed to a destination it never actually reached.

This matches the High-impact bucket: "a status or hash misreport making an integrator credit or refund twice." [7](#0-6) 

### Likelihood Explanation
No malicious actor is required — this is triggered by ordinary use of the SDK's multi-intent withdrawal capability (`createWithdrawalIntents` can emit multiple `ft_withdraw` intents in one call/tx) when two withdrawals of the same underlying token are batched together and both route through PoaBridge. The bug is self-acknowledged in the code comment as an unhandled case, confirming it is reachable, not merely theoretical.

### Recommendation
Extend `findMatchingWithdrawal` (both in `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` and the duplicated logic in `intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`) to disambiguate by more than `assetId` when multiple withdrawals of the same asset exist in the response — e.g., match remaining unmatched entries by `destinationAddress`/`amount`/ordinal position consistent with `index`, or track already-consumed entries so a second `describeWithdrawal` call for the same tx does not reuse the first match. At minimum, until POA's API supports disambiguation, the SDK should refuse to report `completed` for a duplicate-asset batch (fail closed) rather than silently returning another withdrawal's result.

### Proof of Concept
1. Build a NEAR transaction containing two `ft_withdraw` intents for the same `assetId` (e.g., `nep141:btc.omft.near`) to two different destination addresses/amounts, both routed via PoaBridge, at indices 0 and 1 in the same `tx.hash`.
2. Call `bridge.describeWithdrawal({ landingChain, index: 0, withdrawalParams: {assetId, destinationAddress: A, amount: X}, tx })` and `bridge.describeWithdrawal({ landingChain, index: 1, withdrawalParams: {assetId, destinationAddress: B, amount: Y}, tx })`.
3. Once the POA API completes only withdrawal for address `A`, both calls return `{ status: "completed", txHash: <A's transfer_tx_hash> }` because `findMatchingWithdrawal` returns the same first matching entry for the shared `assetId`, as shown by the matching logic [8](#0-7) .
4. An integrator relying on `watchWithdrawal`'s resolved `txHash` per index [9](#0-8)  would incorrectly treat withdrawal index 1 (to address B) as completed with a transaction hash that actually paid address A.

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
