Confirmed: `Session#id` for offline sessions is deterministically `"offline_#{shop}"` [1](#0-0)  and for online sessions `"#{shop}_#{associated_user.id}"` [2](#0-1) , both fully derivable from public information (the shop's `.myshopify.com` domain, which is not secret). This exact string is placed as the raw, unsigned value of the `shopify_app_session` cookie [3](#0-2)  and the OAuth flow's `validate_auth_callback` sets `cookie: SessionCookie.new(value: session.id, ...)` for non-embedded apps [4](#0-3) . For non-embedded (and JWT-less embedded fallback) requests, `SessionUtils.current_session_id` simply echoes back whatever value is present in that cookie with **no cryptographic verification whatsoever** — it neither checks a MAC/signature nor cross-checks it against any authenticated claim: [5](#0-4)  and [6](#0-5) . The gem's own docs instruct developers to set this as a plain (not `cookies.signed[]`) cookie: `cookies[auth_result[:cookie].name] = {expires:, secure: true, http_only: true, value: ...}` [7](#0-6) .

### Title
Predictable, Unsigned Session ID Enables Cross-Tenant Session Hijacking - (File: `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth/session_cookie.rb`)

### Summary
The gem's session-lookup helper `ShopifyAPI::Utils::SessionUtils.current_session_id` treats the raw bytes of the `shopify_app_session` cookie as an authenticated session identifier, but that value is never bound to any credential, signature, or secret — it is a deterministic string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`) computed solely from the merchant's public shop domain. Because the cookie carries no HMAC/signature and the gem performs no additional verification before returning it as the trusted `current_session_id`, any client can substitute their own cookie value to name a *different* shop's session identifier and, if the host app's session store is keyed by this identifier (as the gem's own docs instruct), retrieve and operate under another merchant's stored access token.

### Finding Description
The identity binding that should hold is:
`session_id_returned_by_gem == session_id_that_was_authenticated_for_this_client`

Instead, the gem computes:
- `equality broken`: `session_id_returned_by_gem == raw_unauthenticated_cookie_bytes_supplied_by_the_client`

Walking the flow:
1. During legitimate OAuth completion, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a `Session` whose `id` is fully deterministic given only the `shop` — `"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online sessions [8](#0-7) .
2. This deterministic value is placed as the literal cookie *value* — not signed, not encrypted, not MACed — in a `SessionCookie` struct that only stores `name`, `value`, `expires` [3](#0-2) .
3. Later, when the (non-embedded, or JWT-less embedded) app needs to identify "the current session," it calls `SessionUtils.current_session_id`, which does nothing but read `cookies[SESSION_COOKIE_NAME]` and hand it back verbatim as the session id to look up: `cookie_session_id(cookies)` returns `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` directly, with no cryptographic check [5](#0-4) .
4. There is no code anywhere in `current_session_id`, `cookie_session_id`, or `Session` that verifies the returned id actually corresponds to the presenting client's prior, authenticated OAuth transaction (unlike the embedded JWT path, which cryptographically derives the id from a `JwtPayload` verified against `Context.api_secret_key` at [9](#0-8) ).

Consequently, since the session identifier's entire content space is `{"offline_" + <public shop domain>}` or `{"<public shop domain>" + "_" + <user id>}`, and `<shop domain>` is not a secret (it's the merchant's storefront URL, e.g. `victim-store.myshopify.com`), an attacker who has ever been a legitimate user of the app (e.g., installed it on their own test store as any unprivileged internet user can) can trivially compute another merchant's exact session-id string and present it as their own cookie value.

### Impact Explanation
If the host application follows the gem's own documented pattern of storing/looking up sessions keyed by this `id` (as shown in `docs/usage/oauth.md`, "Store the Session object ... to be used later" [10](#0-9) ), an attacker who swaps in a guessed/known victim shop's session id gains the victim shop's stored `access_token` for making Admin API calls on the attacker's behalf — this is cross-tenant access to another merchant's access token and data, one of the explicitly listed Critical impacts (cross-tenant access / theft of a merchant access token). It also matches the High-impact category of session fixation, since the "session identifier" the gem asks the host app to trust is not actually proof of authentication — it's a guessable label.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented, non-embedded cookie flow literally (plain, non-signed cookie assignment as shown in the docs) combined with a session store keyed by `Session#id`. No secret material, API key, or leaked token is required — only knowledge of the target shop's domain, which is public by design (it is the merchant's storefront URL).

### Recommendation
Do not use a deterministic, publicly-derivable string as the trusted session identifier for cookie-based (non-JWT) session lookups. Either (a) sign/MAC the cookie value (e.g., via `cookies.signed[]` or an explicit HMAC over the id using `Context.api_secret_key`) and verify that MAC inside `SessionUtils.cookie_session_id`/`current_session_id` before trusting it, or (b) generate a cryptographically random, unguessable session identifier (as is already done for the `Session#id` default when no id is passed, via `SecureRandom.uuid` at [11](#0-10) ) and use that random value — not the deterministic `"offline_#{shop}"`/`"#{shop}_#{user_id}"` string — as the cookie's contents.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally and receiving a `shopify_app_session` cookie with value `offline_attacker.myshopify.com`.
2. Attacker (in their own browser/HTTP client) rewrites the `shopify_app_session` cookie value to `offline_victim-store.myshopify.com` — a value it can compute purely from the victim's public storefront domain, with no secret knowledge.
3. Attacker sends a request to the app's server; the server calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-store.myshopify.com"` unchanged and unverified [12](#0-11) .
4. The host app's session store (keyed by this id, per the gem's documented pattern) returns the victim's stored `Session`, including its real Admin API `access_token`, and the app proceeds to act on Shopify's API using the victim's credentials on the attacker's behalf.
