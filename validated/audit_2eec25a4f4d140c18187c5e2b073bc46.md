Confirmed: for the OAuth `AuthQuery`, the `shop` field IS included in `to_signable_string` (so it's HMAC-bound), but for `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of `shop`, `topic`, `webhook_id`, or `api_version` (all read from HTTP headers) are covered by the HMAC at all.

### Title
Webhook shop/topic/webhook_id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the app's business logic actually acts on are taken from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with the app's `client_secret` — it proves nothing about which shop or topic the webhook is claimed to belong to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`: [3](#0-2) 

Contrast this with the OAuth callback path, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed string, so `shop` is cryptographically bound to the HMAC: [4](#0-3) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality the library implicitly relies on is `hmac_valid(body) == hmac_valid(body, shop, topic)`, which is false. Because a single app has one `client_secret` shared across every shop that installs it, any unprivileged actor who installs the app on their own store (or otherwise obtains one genuinely Shopify-signed webhook delivery, e.g. by triggering `orders/create` on their own shop) possesses a `(raw_body, hmac)` pair that is valid for *any* `shop-domain`/`topic`/`webhook-id` header combination, because those headers are never hashed. The attacker can replay that body with a forged `x-shopify-shop-domain` header naming a different, victim tenant, and `HmacValidator.validate` will still return `true`, since it only recomputes the HMAC over `@raw_body`.

### Impact Explanation
Downstream host applications (per this gem's own documented pattern, `WebhookMetadata#shop` and `#topic`) use `request.shop` to look up/attribute the delivery to a specific merchant/tenant record and `request.topic` to select the handler and, through it, the tenant-scoped `body`. Since neither is authenticated, an app user for shop A can forge webhook deliveries that the host app will attribute to shop B, achieving cross-tenant data injection/impersonation without ever needing shop B's or the app's `client_secret`. This satisfies the Critical "cross-tenant access" impact bar defined for this analog set.

### Likelihood Explanation
Any developer/merchant who can install the target app on a shop they control can trivially trigger a real webhook delivery from Shopify to obtain a legitimately signed `(body, hmac)` pair, then replay it to the app's public webhook endpoint with a modified `shop-domain`/`topic`/`webhook-id` header — no secret material, privileged account, or TLS interception is required, matching the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (in addition to the body) in the value that `HmacValidator` verifies for webhook requests — e.g., bind them into `to_signable_string`, or independently verify that the delivering shop matches an installation record before trusting `request.shop`/`request.topic` in `Registry.process`.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; attacker triggers `orders/create` there and captures the raw POST body plus the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is computed by Shopify with the same `client_secret` used for every shop on this app.
2. Attacker replays the identical body/HMAC to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   which recomputes the HMAC only over `request.to_signable_string` (`@raw_body`) — identical to step 1 — so validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim.myshopify.com"`, even though Shopify never signed anything asserting that claim; the host application processes the forged delivery as if it genuinely originated from the victim shop.
