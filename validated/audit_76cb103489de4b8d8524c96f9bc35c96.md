## Finding

### Title
Escrow release in Tron `IntentGatewayV2.withdraw()` does not check ERC20 return value, only call success - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent tokens and protocol fees via a raw low-level `.call` to the ERC20 `transfer` selector, checking only that the call did not revert (`success`). It never inspects the ABI-decoded boolean return value of `transfer()`. Non-compliant/legacy ERC20 tokens — most notably Tron's TRC20 `USDT`, the canonical example of a token that returns `false` on failure instead of reverting — will make `success == true` even when the token balance was never actually moved.

### Finding Description
In `withdraw()`, both the per-token escrow redemption and the transaction-fee redemption use a manual low-level call instead of `SafeERC20.safeTransfer`, even though the contract already declares `using SafeERC20 for IERC20;` and uses `safeTransferFrom`/`safeTransfer` everywhere else in the file (e.g. `placeOrder`): [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
...
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```

`success` here reflects only whether the external call itself reverted, not whether the token's `transfer()` logic succeeded. For a token that returns `false` on failure (rather than reverting) — exactly the class described in the referenced report and exactly how Tron's widely-used TRC20 `USDT` behaves — `success` is `true` and `TransferFailed()` never fires, even though `beneficiary`/`fees` recipient received nothing.

`withdraw()` is invoked from the core settlement paths reachable by any solver or user: `onAccept` (cross-chain redeem/refund) and `onGetResponse` (cancel-from-source), i.e. it's on the path any unprivileged solver/relayer/user triggers by filling or cancelling an intent order: [2](#0-1) 

By contrast, the primary EVM `IntentGatewayV2.sol` in `evm/src/apps/` uses `safeTransferFrom`/checked patterns consistently and does not exhibit this raw-call pattern in its escrow release path — this defect is specific to the Tron variant.

### Impact Explanation
When the escrowed input token or the fee token is a non-reverting, false-returning ERC20 (the norm for TRC20 tokens on Tron, including `USDT`), the contract will:
1. Mark the order as filled/withdrawn (`_filled[commitment] = beneficiary`, `_orders[...] -= amount`, deleting fee escrow) as if funds were paid out, and
2. Emit `EscrowReleased`/`EscrowRefunded` as a success signal,

while the beneficiary/solver actually receives zero tokens. The escrowed tokens remain permanently trapped in the `IntentGatewayV2` contract (no other function can re-release them for that commitment since state has already been mutated to reflect a completed withdrawal), resulting in a permanent freezing/loss of user or solver funds.

### Likelihood Explanation
High on Tron specifically, because TRC20 `USDT` — the dominant stablecoin used for intents/liquidity on Tron — is well known to return `false` (not revert) on failed transfers (e.g., due to blacklist, paused state, or insufficient allowance edge cases handled by that particular implementation). Any order using such a token as input or as the `feeToken` will silently fail its final settlement leg under those conditions, requiring no special privilege — just a normal fill/cancel flow interacting with an affected token.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` with `IERC20(token).safeTransfer(beneficiary, amount)` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in the file), which reverts on both call failure and a `false` return value, keeping the escrow state and actual token movement in sync.

### Proof of Concept
1. Deploy a mock ERC20 that mimics TRC20 `USDT` semantics: `transfer()` returns `false` (does not revert) when, e.g., the recipient is blacklisted or a global pause flag is set, instead of reverting.
2. `placeOrder()` an intent escrowing this token as input.
3. Toggle the mock token into its "fail silently" mode.
4. Have a solver fill the order cross-chain; on settlement, `onAccept` calls `withdraw()`.
5. Observe: `token.call(...)` returns `(true, data)` where `data` decodes to `false`; `success` is `true`, so `TransferFailed()` does not revert; `_orders[commitment][token]` is decremented and `EscrowReleased` is emitted, yet `beneficiary`'s token balance is unchanged — the escrowed tokens are now unrecoverable.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
