### Title
Front-runnable, deterministic lockup account derivation lets an unprivileged user permanently hijack a victim's lockup address with attacker-chosen vesting/whitelist parameters - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` derives the new lockup contract's account ID solely and deterministically from the attacker-controlled `owner_account_id` argument, with no binding to the caller (`predecessor_account_id`) and no reservation/authorization check. Any unprivileged account can observe a pending, legitimate `create` transaction in the mempool (or simply predict the deterministic address for a known target `owner_account_id`) and front-run it with their own `create` call for the same `owner_account_id`, but with attacker-chosen `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id`. Because NEAR account creation is atomic and unique, whichever transaction lands first wins that account name permanently.

### Finding Description [1](#0-0) 
computes:
```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```
This mirrors the root cause pattern in the external report: a public, unauthenticated entry point accepts attacker-supplied configuration (`vesting_schedule`, `release_duration`, `staking_pool_whitelist_account_id`, `foundation_account_id` derivation) that determines security-critical parameters of the resulting contract, while the "identity" binding the transaction to a specific intended party (`owner_account_id` → deterministic address) is public and reused without any signature, nonce, or predecessor check tying the call to an authorized submitter.

Exploit flow:
1. The foundation (or any funder) submits `create(owner_account_id=victim, vesting_schedule=Some(...), ...)` with the intended real deposit, to grant `victim` a vesting lockup.
2. Because `lockup_account_id` is fully deterministic from `owner_account_id` (a public value, often known in advance since it identifies the employee/grantee), an attacker (which can even be the intended `owner`/employee themselves — an unprivileged actor with no special access) front-runs by calling `create(owner_account_id=victim, vesting_schedule=None, release_duration=None, ...)` themselves, paying only the `MIN_ATTACHED_BALANCE` (3.5 NEAR) — [2](#0-1) .
3. Since `vesting_schedule.is_some()` is false in the attacker's transaction, `foundation_account_id` is set to `None` [3](#0-2) , meaning the resulting lockup will have no vesting and no ability for the foundation to terminate/claw back anything. The attacker can also point `staking_pool_whitelist_account_id` to a whitelist contract they control [4](#0-3) , which would later let a delegating owner be tricked into delegating to unvetted/malicious staking pools (bypassing the safety guarantee described in `whitelist/README.md`, since `select_staking_pool` in the lockup contract itself just asks whichever whitelist account is configured — [5](#0-4) ).
4. Attacker's `create_account()` on `lockup_account_id` succeeds first (NEAR guarantees account-creation uniqueness).
5. The legitimate foundation transaction subsequently executes; its `create_account()` action fails because the account already exists. Because all actions (`create_account`, `deploy_contract`, `transfer`, `function_call`) are batched into one atomic NEAR receipt, the whole receipt fails, and `on_lockup_create` refunds the deposit to the original predecessor [6](#0-5) .
6. Result: the deterministic account name for that `owner_account_id` is now permanently occupied by an attacker-controlled lockup contract configured with no vesting restriction / no foundation termination right / a malicious staking-pool whitelist — and the foundation can never create the intended, correctly-configured vesting lockup at that address again.

### Impact Explanation
This is a state-transition / account-binding failure reachable by a fully unprivileged caller (the factory's `create` is a public, payable method with no access control), matching the in-scope impact category: "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release, vesting termination... flows" and "State-transition bypass ... that lets an unprivileged user perform actions beyond intended authority." Specifically:
- The foundation permanently loses the ability to issue the intended vesting/lockup contract for that specific grantee account, since the deterministic address is squatted.
- If the "attacker" is the intended grantee (owner) themselves, they can strip away the foundation's vesting-termination authority entirely by preemptively creating their own lockup with `vesting_schedule = None`/`foundation_account_id = None`, permanently defeating the vesting/clawback guarantee the lockup contract is designed to provide — this is unprivileged-user overreach beyond intended authority, not mere self-harm, because it defeats the *foundation's* enforcement rights, a protocol guarantee explicitly documented in `lockup/README.md` ("Guarantees" section, e.g. "The owner can not prevent the foundation from withdrawing the unvested balance in case of termination").
- An attacker could also seed a malicious `staking_pool_whitelist_account_id`, undermining the delegation-safety guarantee that the whitelist contract is supposed to provide (protecting delegated tokens from loss).

Actual attached deposits from the legitimate/foundation transaction are not stolen (the NEAR receipt is atomic, so the funder's deposit is refunded), so this does not directly move value out of the protocol, but it does permanently and irrecoverably corrupt the intended vesting/lockup issuance flow for the targeted account — a real reachable High-severity griefing/authority-bypass vulnerability analogous in root cause to the reported "front-run and rebind attacker-chosen config to a public, unauthenticated creation call" pattern.

### Likelihood Explanation
High feasibility: the entry point `create()` is public and payable, requires only `MIN_ATTACHED_BALANCE` (3.5 NEAR) from the attacker, and the target `lockup_account_id` is fully computable off-chain from `owner_account_id` (`sha256(owner_account_id)[..20]`), which is typically known in advance (e.g., an employee's own account ID, or public HR/onboarding communications). No privileged role, secret, or validator access is needed — this is a pure "observe a known/expected owner_account_id and race a create-account transaction" attack, feasible by any NEAR account holder.

### Recommendation
- Bind `create()` (or, better, the resulting lockup account derivation) to the caller: e.g. require `env::predecessor_account_id()` to be the foundation/authorized funder, or include the funder's account and/or a factory-issued nonce in the derivation/salt so the account name cannot be pre-computed and squatted by an unrelated third party.
- Alternatively, require the `owner_account_id` grantee (or an authorized foundation signer) to explicitly opt in (e.g. via a two-step commit-reveal, or requiring the `create` call's predecessor to equal `owner_account_id` or the configured `foundation_account_id`), rather than allowing any unprivileged caller to instantiate a lockup for an arbitrary owner with self-chosen vesting parameters.
- Consider restricting `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id` parameters to only be settable by the `foundation_account_id`, defaulting untrusted callers to conservative/no-op behavior (e.g., reject if `predecessor_account_id() != foundation_account_id` when a vesting schedule is being configured).

### Proof of Concept
1. Foundation account `near` prepares to grant employee `alice.near` a vesting lockup and broadcasts:
   `create({owner_account_id: "alice.near", vesting_schedule: Some(schedule), ...})` with deposit `X` NEAR, attached to `lockup.near` factory (deploying to deterministic address `sha256("alice.near")[..20].lockup.near`).
2. Attacker (or `alice.near` herself) observes this in the mempool (or simply predicts the address ahead of time), and submits her own transaction first:
   `create({owner_account_id: "alice.near", vesting_schedule: None, release_duration: None, whitelist_account_id: Some("attacker-whitelist.near")})` with `MIN_ATTACHED_BALANCE` (3.5 NEAR), from any account.
3. Attacker's `create_account()` for `sha256("alice.near")[..20].lockup.near` lands first and succeeds; `foundation_account_id` is `None` because `vesting_schedule` was `None` (`lockup-factory/src/lib.rs:123-126`), and the whitelist is attacker-controlled.
4. Foundation's `create` transaction later fails at `create_account()` (account already exists); the whole batched receipt fails; `on_lockup_create` refunds foundation's deposit (`lockup-factory/src/lib.rs:171-198`).
5. Result: `alice.near`'s deterministic lockup address is permanently occupied by a lockup contract with no vesting/foundation-termination right and an attacker-chosen whitelist — the foundation can never issue the intended vesting-restricted lockup at that address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
