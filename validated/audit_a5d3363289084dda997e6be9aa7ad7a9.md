## Title
Webhook Shop/Topic Identity Not Bound to HMAC, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` verifies solely that HMAC before dispatching to the registered handler. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that determine *which tenant and event* the payload is treated as are read straight from unauthenticated HTTP headers and are never covered by the signature check. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for a webhook `Request` that string is just `@raw_body`: [4](#0-3) 

`shop`, `topic`, and `webhook_id` are parsed from headers with no cryptographic tie to the signature: [5](#0-4) 

`Registry.process` checks only that this body-only HMAC is valid, then immediately trusts `request.shop` and `request.topic` to build the dispatched metadata: [3](#0-2) 

Because the same app-wide `api_secret_key` is used to sign every shop's webhooks, and the signature is a function of body content alone, the equality actually enforced is:

`HMAC(secret, raw_body)_received == HMAC(secret, raw_body)_computed`

whereas the equality the handler *needs* in order to trust `shop`/`topic` as identity fields is:

`shop_header_used_for_dispatch == shop_that_the_secret-holder_actually_signed_for`

That second equality is never checked — `shop` is a field "acted on" (used to build `WebhookMetadata` and dispatched to the app's per-tenant handler logic) but not covered by the HMAC, which is exactly the class of bug in the reference finding (state fields that are overwritten/trusted outside what the signature actually protects).

### Impact Explanation
An attacker who is themselves a legitimate (even free/unprivileged) merchant with the app installed receives genuine Shopify webhooks at their own endpoint, each with a valid `(raw_body, hmac)` pair signed by the app's single shared secret. Because the signature only binds the body, the attacker can resend that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`) with a victim shop's domain or a different registered topic. `Registry.process` accepts the request as authentic and calls the handler with attacker-chosen `shop`/`topic`/`body`, letting the attacker inject cross-tenant webhook events (e.g., forged `app/uninstalled`, `orders/create`, or other lifecycle events) for a shop they do not control. This is a cross-tenant integrity/authentication issue, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any user of the app who has installed it on a shop they control can capture legitimate `(body, hmac)` pairs from webhooks they legitimately receive, then replay them against the shared endpoint with spoofed shop/topic headers — no access to `api_secret_key`, access tokens, or TLS interception is required, only the ability to receive one webhook and issue an HTTP POST.

### Recommendation
Bind the identity-critical fields into what is verified: either include `shop-domain`, `topic`, and `webhook-id` in the signable string (if Shopify's HMAC scheme supported it), or — since Shopify's documented scheme only signs the body — have `Registry.process`/`WebhookMetadata` require the caller to independently confirm that `request.shop` corresponds to a shop with an active, stored session/installation before acting on the payload, rather than trusting the header value as an authenticated tenant identifier.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com` and lets it register webhooks normally.
2. Shopify delivers a legitimate webhook to the attacker's endpoint: `raw_body = B`, header `x-shopify-hmac-sha256 = H = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker crafts a new request to the same app endpoint with the identical `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes `HMAC(secret, B)` and compares to `H` — it passes.
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process an event as though it originated from `victim.myshopify.com`.
