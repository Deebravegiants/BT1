### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` validation only authenticates the raw request body. The `shop` (and `topic`, `webhook_id`) values are read straight from HTTP headers that are never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair is valid and then trusts the header-derived `shop` value as the tenant identity handed to the application's webhook handler. Any user who can obtain one legitimately-signed `(body, hmac)` pair — trivially available to any internet user who installs the app on their own free Shopify store — can replay that pair to the app's public webhook endpoint with the `shop-domain` header swapped to a victim shop, causing the handler to execute tenant-scoped logic under the wrong shop's identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are parsed straight from headers that are not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (i.e., "this body was really signed by our client secret") but then unconditionally trusts `request.shop` — an unauthenticated header — as the tenant identity forwarded to the handler: [3](#0-2) 

The broken identity binding is:
`shop authenticated by HMAC` (∅, since `shop` is never included in `to_signable_string`) ≠ `shop used as tenant key by the handler` (`request.shop`, an arbitrary attacker-controlled header).

Because Shopify signs *all* webhooks for an app with the same app-wide `client_secret` (not a per-shop secret), any shop that has installed the app — including a shop an unprivileged attacker sets up for free — receives genuinely signed `(body, hmac)` pairs. Since the HMAC never covers the `shop-domain` header, the attacker can replay that exact body+HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain`/`shopify-shop-domain` with a victim shop's domain. `Registry.process` will accept it (HMAC of the body still checks out) and invoke the handler with `shop: <victim shop>`, causing the application to perform shop-scoped side effects (e.g. data updates, uninstall handling, entitlement changes) attributed to the wrong tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with no privileged credentials, no access token, and no knowledge of `api_secret_key` can make the app process a webhook under an arbitrary victim shop's identity, driving whatever tenant-scoped business logic the host app's handler performs (data mutation, resource deletion, uninstall/reinstall bookkeeping, billing state changes, etc.) against a shop they do not control. This matches the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app on a free/attacker-controlled Shopify dev store — a normal unprivileged action — and triggering any subscribed webhook topic (e.g. an easily reproducible event). The victim shop domain is plaintext and predictable/guessable/harvestable (shop domains are commonly public). No TLS interception, secret exfiltration, or social engineering is required, since the exploit relies purely on the header/body verification asymmetry in this gem's `Request`/`Registry` code.

### Recommendation
Bind the trusted identity to the signed payload instead of trusting header values independently. Options:
- Include the `shop`, `topic`, and `webhook_id` header values in the signed material used for HMAC verification (this would require Shopify platform changes, so more practically:)
- Have `Registry.process` cross-check `request.shop` against an application-provided allow-list/registered-shop lookup (e.g., verify the shop has an active, stored session/installation) before invoking the handler, rather than trusting the header value implicitly.
- At minimum, document/enforce that consumers of `Registry.process` must independently authenticate `shop` (e.g., via a stored session check) before acting on webhook data, and make this a required step in this gem rather than leaving it fully to the host app.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker.myshopify.com` (a free, unprivileged action) and triggers a webhook subscription, e.g. `orders/create`.
2. Shopify sends the app a legitimate webhook request:
   - Body: `{"id":1,...}` (attacker fully controls the content by creating the order on their own store).
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker captures this raw body + HMAC (both are visible to them, since it's their own store/traffic).
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the *same* body and HMAC, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` only checks the HMAC against the raw body, which still matches, so validation passes: [4](#0-3) 
6. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the application to perform its `orders/create` handling logic scoped to the victim shop, even though the event never actually originated from that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
