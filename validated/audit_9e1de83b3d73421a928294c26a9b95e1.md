### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body [1](#0-0) , while the `shop`, `topic`, and `webhook_id` values used by the app to attribute and process the webhook are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only this body-only HMAC and then forwards `request.shop` as the tenant identity to the app's handler [3](#0-2) .

### Finding Description
The binding that should hold is: **shop claimed in the request == shop covered by the verified signature**. In `ShopifyAPI::Webhooks::Request`, `hmac` is computed from `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header and validated against `to_signable_string`, which returns `@raw_body` only [1](#0-0) . The `shop` accessor instead reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content [4](#0-3) [5](#0-4) .

Contrast this with the OAuth callback path, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter set together with `code`, `host`, `state`, and `timestamp` [6](#0-5) , correctly binding the shop identity to the signature. The webhook path breaks this same binding: `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only verifies the body bytes, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` handed to the app's handler [3](#0-2) .

An unprivileged internet user who has legitimately installed the app on their own store receives real, validly-signed webhooks from Shopify for their own shop (a normal, permitted action — no privileged credentials required). Because the HMAC covers only the body, that attacker can replay the exact same body + HMAC value to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop domain. `HmacValidator.validate` will still pass, since `compute_signature` never saw the shop header [7](#0-6) , and the app's handler will process the (attacker-controlled) body content as if it authentically originated for the victim shop.

### Impact Explanation
This breaks the identity binding between the cryptographically verified sender and the tenant the app attributes the payload to, enabling cross-tenant data injection: an app that persists webhook body content keyed by `data.shop` (the normal integration pattern, per `WebhookMetadata`) can be made to associate attacker-controlled order/customer/product data with a shop the attacker does not own. This matches the Critical impact category of cross-tenant access via an authentication/identity-binding bypass.

### Likelihood Explanation
Likelihood is high for any unprivileged actor: obtaining a validly HMAC-signed body only requires installing the app on any store (a normal, permitted action) and capturing one real webhook delivery. No access to `api_secret_key`, tokens, or any privileged account is required to mount the replay against the public webhook endpoint with a forged shop header.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signable content for webhooks, e.g. by validating the header values against a per-shop secret/HMAC scheme, or by requiring the app to independently confirm the shop the payload claims to be from (e.g., cross-check against an existing installed session for that shop) before trusting `request.shop`, rather than trusting it purely from an unauthenticated header sibling to a body-only signature.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a real webhook delivery — headers include `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, with some `raw_body`.
2. Resend an HTTP POST to the app's webhook endpoint with the identical `raw_body` and identical `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers and body as usual [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches, since the shop header was never part of the signed content [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, despite the signature never having authenticated that shop value [10](#0-9) .
