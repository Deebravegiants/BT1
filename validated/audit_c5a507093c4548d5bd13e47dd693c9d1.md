### Title
Unconditional `--operator-qr-code`/`--user-qr-code` CLI override bypasses backend QR verification on all build flavors, including production - (File: src/cli.rs, src/plans/mod.rs)

### Summary
The Sherlock report's root cause is a *compile-time constant that is applied identically across environments regardless of context*, silently disabling correct behavior where the assumption doesn't hold (mainnet WETH baked into non-mainnet builds). The orb-core analog is `Cli::operator_qr_code` / `Cli::user_qr_code`, defined in `src/cli.rs` without any `#[cfg(feature = ...)]` gate, unlike every other debug/testing knob in the same struct (`skip_pipeline`, `skip_fraud_checks`, `biometric_input`, `ci_hacks`, `data_acquisition`), all of which are gated behind `allow-plan-mods`, `integration_testing`, or `internal-data-acquisition`. [1](#0-0) [2](#0-1) 

### Finding Description
In `src/bin/orb-core.rs`, these CLI values are wired unconditionally into `MasterPlan::builder()`, with no feature gate around the call: [3](#0-2) 

`MasterPlan::operator_qr_code`/`user_qr_code` store the parsed override, falling back to the compile-time constants `DUMMY_OPERATOR_QR_CODE`/`DUMMY_USER_QR_CODE` when an empty string is passed: [4](#0-3) [5](#0-4) 

Crucially, `verify_operator_qr_code` treats any override as pre-verified and fabricates a trusted `LocationData` result, skipping the real backend call to `backend::operator_status::request` entirely: [6](#0-5) 

Because none of this is behind `#[cfg(feature = "allow-plan-mods")]` or `#[cfg(feature = "stage")]` (unlike the sibling flags in the same CLI struct), the exact same compiled production binary that ships to orbs in the field accepts `--operator-qr-code`/`--user-qr-code` and will locally fabricate a "valid" operator/location result and accept an arbitrary attacker-chosen or dummy user QR code string, without ever consulting the backend authorization service — mirroring how the hardcoded mainnet WETH constant silently breaks the intended chain-specific behavior because the code never conditions on the actual deployment context.

### Impact Explanation
An operator (or anyone with shell/CLI access to the orb binary) can start a signup while forging the operator's identity/location and injecting an arbitrary "operator QR" string that is never checked against `backend::operator_status::request`, and/or force a fixed dummy/attacker user QR-code to be treated as scanned. This can result in unauthorized or misattributed signups being started under falsified operator identity/location data (`team_operating_country: "DEV"`, coordinates `0.0,0.0`), directly matching the "unauthorized or misattributed signup" and "cross-signup state bleed" impact classes called out in the validation rules, since the backend never validates that this operator/location is legitimate for this signup session.

### Likelihood Explanation
Likelihood is medium: exploitation requires local execution access to the orb-core binary with custom CLI arguments (an "unprivileged local operator/CLI user" analog, not a remote attacker), but critically the flags are present and functional in the production build flavor (`flavours.prod = ["v2_x_x"]` in `flake.nix` does not include `allow-plan-mods`), so no special debug feature needs to be enabled — the vulnerable code path ships as-is in production, just as the mainnet-WETH constant shipped as-is to L2 deployments without any deployment-specific gating. [7](#0-6) 

### Recommendation
Gate `operator_qr_code` and `user_qr_code` in `src/cli.rs` behind the same feature flag used for other test/debug overrides (e.g. `allow-plan-mods`), so production builds cannot accept these overrides at all, analogous to making the WETH address an explicit, environment-scoped constructor argument instead of a universal compile-time constant. Additionally, `verify_operator_qr_code` in `src/plans/mod.rs` should not fabricate a trusted `LocationData` for override QR-codes in non-test builds; the bypass path should itself be compiled out via `#[cfg(feature = "allow-plan-mods")]`.

### Proof of Concept
1. Build orb-core with the `prod` flavor (no `allow-plan-mods`).
2. Run the binary with `orb-core --operator-qr-code=<attacker-string> --user-qr-code=<attacker-string>`.
3. Observe in `MasterPlan::scan_remaining_qr_codes` → `verify_operator_qr_code` (`src/plans/mod.rs:1543-1557`) that because `self.operator_qr_code_override.is_some()`, the function immediately returns `Ok(Some((0, LocationData{team_operating_country:"DEV", ...})))` without calling `backend::operator_status::request`, i.e., without ever validating the operator QR code or its location against the backend, letting the signup flow proceed under fabricated operator/location data.

    /// Sets the default operator QR-code value instead of asking the user.
    pub fn operator_qr_code(mut self, qr_code: Option<Option<&str>>) -> Result<Self> {
        self.operator_qr_code_override = qr_code
            .map(|qr_code| qr_code.unwrap_or(DUMMY_OPERATOR_QR_CODE))
            .map(|qr_code| {
                qr_scan::operator::Data::try_parse(qr_code)
                    .ok_or_else(|| eyre!("provide a valid operator QR code"))
            })
            .transpose()?;
        Ok(self)
    }

    /// Sets the default user QR-code value instead of asking the user.
    pub fn user_qr_code(mut self, qr_code: Option<Option<&str>>) -> Result<Self> {
        self.user_qr_code_override = qr_code
            .map(|qr_code| qr_code.unwrap_or(DUMMY_USER_QR_CODE))
            .map(|qr_code| {
                qr_scan::user::Data::try_parse(qr_code)
                    .ok_or_else(|| eyre!("provide a valid user QR code. We got {:?}", qr_code))
                    .map(|x| (x, qr_code.to_string()))
            })
            .transpose()?;
        Ok(self)
    }
