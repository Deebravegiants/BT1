### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shopify-shop-domain` header as the tenant identity passed to the app's webhook handler. Because the app's `client_secret` (the HMAC key) is identical for every merchant that has installed the app, anyone who has legitimately received one valid `(body, hmac)` pair from their own shop can replay it against the app's webhook endpoint while substituting a different `shop-domain` header, and the request will still pass verification — but be processed as if it came from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read from headers that are **not part of the signed payload**: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (the raw body) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly this check and then forwards the unauthenticated `request.shop` directly into `WebhookMetadata`, which is handed to the app's registered handler as the tenant identity for the event: [4](#0-3) 

The equality that should hold is:
`hmac_secret_owner(client_secret) == shop_that_the_event_is_attributed_to`

What is actually enforced is only:
`hmac_secret_owner(client_secret) == raw_body`

Since the same `client_secret` is shared by the app across **every** merchant installation, any user who installs the app on their own store legitimately receives real webhooks (e.g. `app/uninstalled`, whose body is `{}`) with a valid HMAC computed over that body using the app's shared secret. That attacker can capture this `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `shopify-shop-domain` header changed to any victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the app's handler believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding for webhook processing — a cross-tenant access primitive. Depending on the webhook topic an app has registered (e.g. `app/uninstalled`, `shop/update`, `customers/redact`, etc.), a malicious but otherwise unprivileged merchant can force the host application to execute shop-scoped business logic (deleting/deactivating a victim's stored session/access token, triggering GDPR redaction flows, corrupting per-shop cached state, etc.) attributed to a shop they do not control, purely because the body content is attacker-known/reusable and the shop identity is never bound to the signature. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
High. Any user can install the target app on their own (even free/dev) store to legitimately obtain a valid `(raw_body, hmac)` pair for predictable/empty-body topics such as `app/uninstalled`. No access token, `client_secret`, or privileged access is required — only the ability to send an HTTP POST to the app's public webhook endpoint with a forged `shopify-shop-domain` header.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is cryptographically verified, or otherwise cross-check the header-derived shop against an independently trusted source before dispatching to handlers. Concretely: include the `shop-domain` header (and other identity-bearing headers currently trusted unauthenticated) in the signed material used by `to_signable_string`, or require the host application to verify `request.shop` against a shop that is already known to have a valid session/webhook subscription before acting on the event.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers/uninstalls the app to receive a legitimate `app/uninstalled` webhook: body `"{}"`, headers include `shopify-hmac-sha256: <valid-hmac-of-"{}">` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body and `hmac-sha256` header to the app's webhook endpoint, but replaces `shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb`, only `@raw_body` is checked) and `ShopifyAPI::Webhooks::Registry.process` invokes the registered `app/uninstalled` handler with `shop: "victim-shop.myshopify.com"` (per `lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the host app to process an uninstall/cleanup event for a shop that never actually uninstalled or sent the webhook.
