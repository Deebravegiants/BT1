### Title
Independent rounding in `do_remove_liquidity` can drain a pool asset reserve below `minimum_balance` and trigger dust removal of the pool account - (File: substrate/frame/asset-conversion/src/lib.rs)

### Summary
`Pallet::do_remove_liquidity` computes `amount1`/`amount2` from `lp_token_burn` via independent `mul_div` operations against each asset's reserve, then checks the resulting `reserve1_left`/`reserve2_left` against `T::MintMinLiquidity` rather than each asset's actual existential deposit (`T::Assets::minimum_balance`). Because the two assets in a pool can have different, runtime-configured minimum balances that are unrelated to the LP-token-denominated `MintMinLiquidity` constant, a caller can pick `lp_token_burn` so that the invariant check passes while one asset's reserve in `pool_account` drops below its real `minimum_balance`, causing `pallet-assets`/`pallet-balances` to reap that asset account on the next `Assets::transfer`/`unreserve` operation performed inside the pallet or immediately after.

### Finding Description
`do_remove_liquidity` derives `amount1` and `amount2` as separate `mul_div(lp_token_burn, reserveN, total_supply)` computations, meaning the two withdrawal amounts round independently rather than being derived from a single shared invariant. The pallet's safety check on the resulting reserves compares `reserve1_left`/`reserve2_left` to `T::MintMinLiquidity::get()`, a constant meant to protect against the classic "first LP mints dust shares" attack on the *LP token* supply — it is not tied to, and can be numerically smaller than, the *asset-side* existential deposit returned by `T::Assets::minimum_balance(asset)`/`T::Assets::minimum_balance(asset2)`. Since assets registered in `Pools::<T>` can be arbitrary `T::AssetKind`s (including ones from `pallet-assets` with configured minimum balances well above whatever `MintMinLiquidity` is set to), an attacker who is the sole or a large LP holder can:

1. Create/join a pool near-minimal reserves via `add_liquidity`.
2. Call `remove_liquidity` with an `lp_token_burn` value engineered (via the deterministic `mul_div` rounding) so that `amount1`/`amount2` leave `reserve2_left` at, say, `minimum_balance(asset2) - 1` while the `MintMinLiquidity` check still passes (because that constant is independent of asset2's ED).
3. The subsequent `T::Assets::transfer` moving `amount2` out of `pool_account` leaves `pool_account`'s asset2 balance below the existential deposit for a non-sufficient asset, and `pallet-assets` dust-removes/kills that asset account.
4. `Pools::<T>` storage entry and outstanding LP token supply for other holders still exist, but the pool's asset2 account is gone, so any subsequent `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` referencing that pool will fail (balance reads return zero/`NoFunds`), permanently trapping remaining LPs' backing funds for asset1.

The existing check only guards the LP-token economic invariant (`MintMinLiquidity`), not the physical existential-deposit requirement of each underlying asset, so it does not stop this path.

### Impact Explanation
This breaks the core invariant that "the pool account must never be reaped while `Pools::<T>` and outstanding LP token supply still exist." Once one leg of the pool's asset account is dusted, the pool becomes permanently unusable for swaps, and any remaining LP holders' claim on the surviving asset becomes effectively unredeemable through the normal AMM path (their `remove_liquidity` calls will also then read a zero/missing balance for the reaped asset and fail or return incorrect proportional amounts), amounting to a permanent freeze of user funds — a direct violation of the "user-controlled assets must remain fully backed and cannot be permanently frozen" invariant.

### Likelihood Explanation
This requires: (a) the pool's two assets to have different, non-trivial existential deposits configured independently of `T::MintMinLiquidity`; (b) the pool to be near-minimal reserves (easily engineered by the attacker themselves, e.g., a pool the attacker created or is the majority LP in); and (c) the attacker to choose an `lp_token_burn` value that satisfies the `MintMinLiquidity` check but crosses the real ED threshold for one asset — a deterministic computation given public on-chain reserve/supply state, requiring no special privileges, only ordinary `remove_liquidity` extrinsic calls from a signed account. This is fully reproducible and repeatable by any unprivileged LP.

### Recommendation
Replace/augment the `MintMinLiquidity`-based check in `do_remove_liquidity` with explicit checks that `reserve1_left == 0 || reserve1_left >= T::Assets::minimum_balance(asset1)` and the same for asset2 (i.e., either fully drain the reserve to zero, killing the account intentionally and consistently, or keep it above the asset's actual existential deposit), and ensure this holds atomically before performing the outbound transfers, returning `Error::<T>::ReserveLeftLessThanMinimal` otherwise.

### Proof of Concept
Integration test in `substrate/frame/asset-conversion/src/tests.rs`:
1. Configure two assets with distinct existential deposits (e.g., asset1 ED = 1, asset2 ED = 100) via `pallet-assets` `force_create`/`set_metadata`.
2. `create_pool(asset1, asset2)` then `add_liquidity` with near-minimal amounts so `pool_account` holds just above asset2's ED.
3. Compute `lp_token_burn` such that `mul_div` rounding leaves `reserve2_left = ED(asset2) - 1` while the current `MintMinLiquidity` check still passes; call `AssetConversion::remove_liquidity` from the LP account.
4. Assert: the extrinsic succeeds, `pallet_assets::Account::<T>::get(asset2, pool_account)` is `None` (account reaped), `Pools::<T>::get(pool_id)` still exists, and a subsequent `swap_exact_tokens_for_tokens` on that pool fails — demonstrating the pool is permanently broken while LP tokens/storage still reference it.
