### Title
Attacker-supplied route payload executes arbitrary contract code beneath the signer's auth tree, draining the caller's wallet beyond the routed amount - ([File: contracts/swap-aggregator/src/execute/mod.rs](contracts/swap-aggregator/src/execute/mod.rs))

### Summary
`execute_strategy` decodes a fully caller-supplied `StrategyPayload` (`swap_xdr`) whose `assets` registry names the pool address every hop invokes. The venue adapters then `invoke_contract` on that payload-chosen address with no allowlist — an arbitrary-code-execution primitive equivalent to the gridx `$query` sink. Because the rogue pool executes below the caller's authorization, any `token.transfer(caller, attacker, x)` it performs is recorded by `simulateTransaction` as a child of the caller's own auth entry; once signed, the host enforces it. The measured balance-delta checks only bound the routed funds, so the loss is the signer's entire wallet of any token, and the swap can still return a fair output so nothing on-chain reverts.

### Finding Description
The analog of "crafted `$query` reaches code execution" is "crafted `swap_xdr` reaches `invoke_contract` on an attacker-chosen address":

1. `execute::run` auths only `sender`, decodes `ops`, and loops `execute_op` over attacker-built instructions [1](#0-0) .
2. Each `Opcode::Swap` builds `SwapHop { pool: ctx.assets.get_unchecked(op.idx_a), .. }` — the pool address comes straight from the payload's `assets` registry, with no allowlist of pools or tokens [2](#0-1) .
3. Adapters invoke that address directly, e.g. Soroswap calls `get_reserves` and `swap` on `ctx.hop.pool` via `env.invoke_contract` [3](#0-2) [4](#0-3) .
4. `dispatch_hop` only checks that the router's own `token_in`/`token_out` deltas match `amount_in`/positive output [5](#0-4) . A malicious pool can pay a fair output while also calling `token::Client::transfer(victim, attacker, x)` on any token the victim holds.
5. The host records that transfer as a sub-invocation of the caller's root auth entry (`swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral`, or a direct `execute_strategy`), so the simulated transaction the wallet asks the user to sign already contains the theft; enforcing mode then executes it [6](#0-5) .

Reachability for an unprivileged attacker: publish a malicious route (or inject it anywhere a `routeXdr` is consumed) that a victim embeds in `swap_collateral(caller, account_id, asset_in, amount, asset_out, swap_xdr)` or calls `execute_strategy(sender, total_in, swap_xdr)` with; the poisoned `hop_pool` contract — deployed by the attacker — runs inside the call. The dedicated harness test proves the theft executes end-to-end through `swap_collateral` when the simulated tree is signed [7](#0-6) . The threat model confirms no allowlist exists and the bound "covers the controller's own grant only" [8](#0-7) .

### Impact Explanation
Theft of user funds. The rogue hop can transfer any token the signer holds — including assets the protocol never listed — up to the wallet's full balance, while the swap itself returns a compliant output and passes `min_out` and the controller's post-swap risk checks. Neither the payload minimum, the measured-delta checks, nor `ExcessiveResidual` bound the stolen amount. Impact scales with the signer's total wallet, not the routed `total_in`. Severity: High (Critical is tempered by the signing requirement below).

### Likelihood Explanation
The exploit needs the victim to sign a transaction containing the malicious route. That is the normal flow: users sign whatever `routeXdr` a quote or counterparty hands them, and `simulateTransaction` produces the auth tree they approve. The theft appears as an extra `transfer` child in the simulated tree — nothing fails on-chain, and the router's own checks all pass. The harness test demonstrates that recording mode silently attaches the rogue transfer under the `swap_collateral` entry and that signing that tree moves the funds [9](#0-8) . Likelihood rests on wallet/client UX not decoding the route — a realistic assumption, though it does require the user to sign, which keeps this at High rather than Critical.

### Recommendation
Whitelist venue contracts on-chain: maintain an owner-governed registry of approved pool addresses (or venue+pool pairs) and reject `Swap`/`Mint`/`Burn` instructions whose `assets[idx_a]` is not registered. As a defense-in-depth, record and cap the expected shape of the authorization the route produces (e.g., verify post-simulation that the only caller-side transfer is the single input pull), and document that clients must refuse any signed tree with extra child invocations. Until a whitelist exists, the SDK should decode `swap_xdr` and reject pools outside the known venue set.

### Proof of Concept
1. Attacker deploys `RogueHopPool`, whose `swap()` pays the expected output tokens to the router and additionally calls `wallet_token.transfer(victim, attacker, victim_balance)` (`tests/test-harness/.../rogue_hop_pool_transfer_joins_caller_auth_tree.rs:51-72`).
2. Attacker hands the victim a `swap_xdr` whose `assets` registry lists `RogueHopPool` as the hop pool for a Soroswap-opcode instruction, with `min_out` at the fair output.
3. Victim submits `controller.swap_collateral(alice, account_id, USDC, amount, ETH, swap_xdr)` (or a direct `execute_strategy`). The router pulls `total_in`, calls `invoke_contract(rogue_pool, "swap", ...)`; the rogue contract pays out and performs the wallet transfer inside the call stack [10](#0-9) .
4. `simulateTransaction` returns the auth tree with `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` nested under the `swap_collateral` root; the victim signs it [11](#0-10) .
5. Enforcing mode executes: Alice's 10 000 USDC swap still yields 2.5 ETH, but her entire `WALLET_BALANCE` of the unrelated token is transferred to the attacker — `assert_eq!(wallet(alice), 0); assert_eq!(wallet(attacker), WALLET_BALANCE)` [12](#0-11) .

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
