### Title
Circular header ancestry in GRANDPA's `AncestryChain::ancestry` causes an unbounded loop, permanently halting consensus-update processing - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The GRANDPA consensus client walks a relayer-supplied set of headers backward via `parent_hash()` pointers to reconstruct an ancestry route, exactly like SPDK's vhost descriptor-chain walk in CVE-2019-9547. Neither implementation detects a circular chain among the untrusted, attacker-constructed nodes, so a crafted proof causes the walk to loop forever instead of terminating with an error.

### Finding Description
`AncestryChain::ancestry` walks backward from `block` to `base` purely by following `parent_hash()` values taken from a `BTreeMap` built directly from the untrusted, submitted `unknown_headers`: [1](#0-0) 

The loop terminates only when `current_hash == base` or when a hash is missing from the map. It never records visited hashes, so if the submitted header set contains a cycle (header A's `parent_hash` = hash(B), header B's `parent_hash` = hash(A)), the map lookup always succeeds for both A and B, `current_hash` never equals `base`, and the loop runs forever.

An attacker fully controls the content of every header in `finality_proof.unknown_headers` (this is exactly what a relayer submits as a GRANDPA consensus proof). Because a header's hash is simply the hash of its own content, the attacker can freely choose the `parent_hash` field of each header independently of any real chain relationship — nothing enforces that `parent_hash` corresponds to an actually-existing ancestor, and nothing enforces strictly decreasing block numbers along the parent-hash chain. A 2-node cycle (A → B → A) is trivial to construct.

This function is called from the on-chain verifier that a relayer's consensus proof reaches directly: [2](#0-1) 

and [3](#0-2) 

`verify_grandpa_finality_proof` is invoked directly inside `verify_consensus`, the entry point the ISMP GRANDPA client exposes to the runtime for every submitted consensus message (`ConsensusMessage::Polkadot`, `::Relaychain`, `::StandaloneChain`): [4](#0-3) [5](#0-4) 

The `target`/`base` selection (`max_by_key`/`min_by_key` on `.number()`) does not validate that the `parent_hash` chain between them is acyclic before `ancestry()` is invoked, and `ancestry()` itself performs no visited-set/cycle check — the exact bug class described in CVE-2019-9547, where a vhost target failed to detect a circular virtqueue descriptor chain constructed by an untrusted VM.

### Impact Explanation
Any relayer can submit a GRANDPA consensus update (`ConsensusMessage`) containing a crafted `unknown_headers` set with a circular `parent_hash` reference. When the runtime processes this message through `GrandpaConsensusClient::verify_consensus`, execution enters `AncestryChain::ancestry` and never returns — the loop spins indefinitely inside the same call that updates consensus state for the affected route. Because this runs as part of on-chain extrinsic/message-handling execution, an unbounded loop here stalls block execution for as long as the runtime allows the call to run, effectively making the affected consensus client (and therefore every state machine/route relying on it for message delivery, including HandlerV2 dispatch that depends on state commitments produced by this consensus client) unable to make progress — "a route unable to deliver messages," which matches the accepted impact categories. This is reachable from a single relayed proof with no privileged access required.

### Likelihood Explanation
High. Constructing two headers whose `parent_hash` fields point at each other requires no special access — headers in `unknown_headers` are attacker-supplied SCALE-encoded data with no on-chain constraint tying `parent_hash` to any genuine ancestor. The consensus-update path is explicitly permissionless (any relayer submits it), and no validation in `verify_grandpa_finality_proof` or `AncestryChain::ancestry` rejects such a proof before the unbounded walk begins.

### Recommendation
Add cycle detection to `AncestryChain::ancestry` (e.g., track visited hashes in a `BTreeSet`/`HashSet` and bound the number of iterations by `ancestry.len() + 1`, returning `Error::NotDescendent` once exceeded). Additionally, validate during header-set construction that headers form a strictly decreasing chain by block number along `parent_hash` links, rejecting any proof where the `parent_hash` walk revisits a previously-seen hash or exceeds the header-set cardinality.

### Proof of Concept
1. Craft header `A` with an arbitrary body and `parent_hash = hash(B)` (chosen ahead of time), and header `B` with `parent_hash = hash(A)`.
2. Set `A.number()` to the maximum among a submitted `unknown_headers` set (so `A` becomes `target`), and craft the remaining headers/justification so `verify_grandpa_finality_proof`'s early checks (`target.hash() == finality_proof.block`, justification decode, `justification.commit.target_hash == finality_proof.block`) pass.
3. Submit this as `ConsensusMessage::StandaloneChain`/`::Relaychain` via `GrandpaConsensusClient::verify_consensus`. Execution reaches `headers.ancestry(from, target.hash())`, which walks `A → B → A → B → ...` forever since neither hash equals `from` and both remain present in the `BTreeMap`, matching the assertion `verify_proof_walk`/`ancestry` never performs cycle detection as shown in `modules/consensus/grandpa/primitives/src/justification.rs:180-198`.

Note: I was not able to confirm from the indexed excerpts whether the justification signature check (`justification.verify(...)`, executed after the vulnerable `ancestry` calls) is reordered ahead of the ancestry walk in some code path, which could reduce reachability if signatures are checked first; based on the code shown, the ancestry calls (`headers.ancestry(...)`) execute before `justification.verify(...)`, so the loop is reached before any cryptographic check on the justification itself. This ordering should be verified directly in the repository if further confirmation is needed.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
