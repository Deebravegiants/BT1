### Title
RAY debt-value overflow during accrual permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
A market can grow to a state in which `borrowed * borrow_index` no longer fits the protocol's `i128` RAY-value domain before `MAX_BORROW_INDEX_RAY` is reached. The next accrual reverts with `MathOverflow`, and because every pool market mutation accrues first, suppliers cannot withdraw, borrowers or third parties cannot repay, and liquidations touching that market cannot settle. The regression test demonstrates this end state by having both `withdraw` and `repay` fail after `update_indexes` fails. [1](#0-0) 

### Finding Description
`controller.update_indexes(caller, assets)` is permissionless and forwards the requested markets to `pool.update_indexes`. [2](#0-1) [3](#0-2) 

Pool accrual loads each market and executes `interest::global_sync`, which calls `accrue_step` for each elapsed chunk. [4](#0-3) [5](#0-4) 

`accrue_step` computes the current debt value before calculating the new index:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
```

This executes `scaled.mul(env, index)`, ultimately `mul_div_half_up(borrowed, index, RAY)`. [6](#0-5) [7](#0-6) [8](#0-7) 

Although intermediate multiplication is widened to `I256`, the resulting quotient must still fit `i128`; otherwise `mul_div_half_up` panics with `MathOverflow`. [9](#0-8) 

The borrow-index cap is applied only after multiplying the old index by the new interest factor, and it caps the index—not the represented `borrowed * index` value. [10](#0-9)  Therefore a sufficiently large scaled-debt book can cross the representable debt-value boundary while its index remains below `MAX_BORROW_INDEX_RAY`; the repository's regression test asserts that exact ordering. [11](#0-10) 

### Impact Explanation
Once the next accrual crosses the boundary, the market's stored `borrowed` and `borrow_index` make `scaled_to_original` overflow. The failing call does not advance `last_timestamp`, so every later invocation encounters the same product.

This permanently freezes all flows that must synchronize the affected market:

- `update_indexes` cannot commit accrual;
- `withdraw` cannot pay suppliers;
- `repay` cannot reduce debt;
- `borrow` and market parameter updates cannot proceed;
- liquidation settlement cannot mutate the frozen market.

The test explicitly demonstrates `update_indexes`, `withdraw`, and `repay` reverting with `MathOverflow`. [12](#0-11) 

The result is permanent freezing of user funds unless a privileged contract upgrade changes the arithmetic or state. That satisfies the accepted impact class even though no funds are directly stolen.

### Likelihood Explanation
The condition requires an exceptionally large market whose debt remains outstanding while the borrow index grows. The harness scenario uses an 18-decimal market, a 1-billion-token supply, 98% utilization, elevated caps, and repeated accrual until the RAY-value boundary is crossed. [13](#0-12) 

No privileged call is required to trigger the failure once such a market state exists: any authorized caller can submit `controller.update_indexes(caller, assets)`, and ordinary users hit the same failure through `withdraw`, `repay`, or liquidation. The size requirement is the main limiting factor and makes this Medium rather than High.

### Recommendation
Do not let a market enter a state whose persisted scaled balances and indexes imply an unrepresentable RAY value.

At minimum:

1. Before borrowing or minting debt shares, enforce a dynamic cap based on the largest `borrow_index` that keeps `borrowed * borrow_index / RAY` below `i128::MAX`.
2. Apply the same representability bound to `supplied * supply_index / RAY`, since `accrue_step` also computes that product.
3. In `accrue_step`, detect an out-of-range current value before performing the conversion and clamp index growth, rather than reverting after the state has become unreachable.
4. Prefer an explicit market state such as interest suspension at the numeric boundary over an always-reverting accrual.
5. Add a regression assertion that recovery paths—`repay`, `withdraw`, liquidation, and `update_indexes`—remain executable immediately below and at the numeric ceiling.

### Proof of Concept
For a market whose configured caps admit the required size:

1. Supply `1_000_000_000 * 10^18` units of an 18-decimal asset to the market.
2. Supply enough collateral to borrow `980_000_000 * 10^18` units, producing approximately 98% utilization.
3. Allow accrual to advance until `borrowed * borrow_index / RAY` exceeds `i128::MAX`, while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. Any caller submits:

```text
controller.update_indexes(
    caller,
    vec![HubAssetKey { hub_id, asset }]
)
```

5. The call reaches `pool.update_indexes → ops::market::accrue → global_sync → accrue_step → scaled_to_original` and reverts with `MathOverflow`.
6. Subsequent `controller.withdraw` and `controller.repay` calls on the same market also revert before their requested operation executes.

The repository's `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` test implements this scenario and confirms that the index cap never engages before the market freezes. [14](#0-13)

```rust
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

        assert!(
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```
