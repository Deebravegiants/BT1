### Title
Creator's accrued FeeVault balance becomes permanently frozen if their claiming address can never receive USDC, and `Bonding.transferCreator` cannot rescue it - ([File: packages/contracts/src/FeeVault.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
`FeeVault` credits creator fees under `creatorBalance[creator]` and only ever pays them out via `claim()`, which force-sends the funds to `msg.sender` itself. `Bonding.transferCreator` looks like the designed escape hatch for a broken/rotated creator address, but it only updates `TokenInfo.creator` for future fee *attribution* — it never migrates the already-accrued balance sitting in `FeeVault.creatorBalance[oldCreator]`. If a creator's address becomes permanently unable to receive the fee-token (the canonical real case: Circle blacklists the address, which reverts `safeTransfer`), every dollar already accrued to that address is frozen forever, with no on-chain path to redirect it — the exact "store the broken recipient, no way to swap it for a live recipient" bug class described in the report.

### Finding Description
`FeeVault.claim()` is hard-coded to pay `msg.sender`: [1](#0-0) 

The balance is keyed purely by the creator address recorded at accrual time: [2](#0-1) 

`FeeVault` exposes no owner or creator function to move a balance from one address to another — the full contract (initialize, accrue, claim, claimProtocol, sweepDonations, admin setters) contains nothing that touches `creatorBalance[creator]` except `accrue` (increment) and `claim` (zero-out-and-pay-self). There is no `migrateBalance`/`setClaimant`/`rescue` path.

`Bonding.transferCreator` is the only creator-identity-changing function in the protocol, and it is scoped to `TokenInfo.creator` only: [3](#0-2) 

Per the fee-flow spec, `Zap` reads `Bonding.tokenInfo(token).creator` at accrual time and forwards that address into `FeeVault.accrue`; `transferCreator` therefore redirects only *future* accruals: [4](#0-3) 

So the sequence: (1) address `C` creates a token and earns fees, which pile up in `FeeVault.creatorBalance[C]`; (2) `C` becomes unable to receive the fee token at that exact address (USDC blacklist is the concrete, permissionless-to-trigger-against-yourself-unintentionally case — e.g. sanctioned-adjacent activity, an exchange deposit address flagged by Circle, or simply losing the key and having to rotate via `transferCreator` for *future* fees while the *past* balance stays trapped under the now-unusable `C`); (3) `C` calls `transferCreator(token, newAddr)` believing this "fixes" their claim path — it does not, because `creatorBalance[C]` in `FeeVault` is untouched; (4) `claim()` from `C` reverts forever (blacklisted transfer), and `claim()` from `newAddr` pays out `creatorBalance[newAddr]` (zero), never `creatorBalance[C]`. The funds sit in `FeeVault`, fully backed (they pass the `accrue` underfund check and are excluded from `sweepDonations`'s surplus calculation since `totalAccruedCreator` still counts them), but unclaimable by anyone, forever.

### Impact Explanation
This is a permanent freeze of legitimately-earned creator funds held in `FeeVault`, with no on-chain recovery — matching the "permanent freezing of trader, creator or LP funds" acceptance criterion. Because `totalAccruedCreator` keeps counting the frozen balance, it also permanently reduces the pool that `sweepDonations` can ever recover, so the value doesn't return to the protocol either — it is simply gone.

### Likelihood Explanation
Reaching this state requires no privileged action: any creator can launch a token via `Bonding.launch`/`Zap.createToken`, accrue creator fees through ordinary `Zap.buy`/`Zap.sell` traffic, and then become claim-blocked at that address for reasons entirely outside the protocol's control (most concretely, USDC issuer blacklisting — a real, historically-exercised power over ordinary addresses). The creator's own natural remedy, `Bonding.transferCreator`, is reachable by exactly the same unprivileged actor and is the function most likely to be called in response, yet it silently fails to solve the problem, which increases the chance the frozen balance is never noticed/rescued in time.

### Recommendation
Give `FeeVault` a way to move an existing `creatorBalance` entry to a new claimant, gated on the same authority that already controls fee attribution. Concretely:
- Add a `FeeVault.migrateCreatorBalance(address oldCreator, address newCreator)` (or an `onlyDepositor`/owner-gated variant) that moves `creatorBalance[oldCreator]` to `creatorBalance[newCreator]` (summing if `newCreator` already has a balance), leaving `totalAccruedCreator` and `lifetimeCreatorEarned` semantics intact.
- Wire `Bonding.transferCreator` to call this migration (via the depositor-privileged `Zap`/router path, or by having `Bonding` itself be an allowlisted depositor) so that transferring creator identity also moves the already-accrued, not-yet-claimed balance — making `transferCreator` the complete recovery path the design already implies it should be.

### Proof of Concept
1. Creator `C` launches a token through `Bonding.launch` + `Zap.createToken` and trades accrue fees, crediting `FeeVault.creatorBalance[C] = X` via `Zap` → `FeeVault.accrue(token, C, creatorAmount, protocolAmount, isBuy)` (`FeeVault.sol:101-123`).
2. `C`'s address is blacklisted by the USDC issuer (or otherwise permanently loses the ability to receive the fee token) — any `IERC20(usdc).transfer(C, ...)` now reverts.
3. `C` calls `Bonding.transferCreator(token, newAddr)` (`Bonding.sol:738-748`) to move ownership going forward.
4. `C` calls `FeeVault.claim()` from `C` — reverts (blacklisted recipient in `safeTransfer`).
5. `newAddr` calls `FeeVault.claim()` — succeeds but pays out `creatorBalance[newAddr]`, which is `0`; `creatorBalance[C] = X` is untouched.
6. `X` is now permanently unclaimable by any address, and remains counted in `totalAccruedCreator` so it can never be swept via `sweepDonations` either — confirmed by the full absence of any balance-migration function in `FeeVault.sol` (`FeeVault.sol:1-240`).

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
