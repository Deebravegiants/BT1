### Title
Full-fill escrow release drains a token's *entire* shared escrow bucket instead of the specific leg's share, enabling over-withdrawal on multi-input orders with repeated input tokens - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` releases escrow per output leg by indexing into `order.inputs[i]`, but the underlying escrow ledger (`_orders[commitment][token]` in `IntentsBase.sol`) is keyed only by `(commitment, token address)`, not by leg index. When a leg is fully filled, the code releases the *entire remaining balance* recorded for that token rather than the amount specifically backing that leg. This mirrors the Cypher incident's root cause: a shared collateral/margin value that multiple sub-accounts draw against, where finalizing one sub-account's position lets it claim funds actually backing another, producing over-withdrawal / bad debt.

### Finding Description
The escrow ledger is declared as a flat per-token mapping, not per input-index: [1](#0-0) 

In `_fillSameChain`, when a given output leg `i` reaches `amountFilled == totalRequired`, the code does **not** compute the leg-specific input amount; instead it reads whatever is currently left in the shared per-token bucket and treats that as the amount to release: [2](#0-1) 

For any *other* leg (or subsequent partial fill) that also happens to reference the same input token address (`order.inputs[j].token == order.inputs[i].token`, `j != i`), its escrow was accounted for in that very same `_orders[commitment][token]` slot at order placement. Nothing in `_fillSameChain` or the surrounding validation rejects orders whose `inputs[]` array contains duplicate token addresses across indices — `InvalidInput` is only checked for output-token mismatches (`options.outputs[i].token != outputToken`), not for input duplication.

`_withdraw` then unconditionally transfers whatever `escrowedAmount` it was given and decrements the shared bucket by that same amount: [3](#0-2) 

Because Solidity 0.8's checked arithmetic only guards against `amount > escrowed`, and the amount passed in the full-fill branch is *by construction* set equal to the full remaining balance, the first leg to complete captures value that was placed in escrow to also back a sibling leg, zeroing the shared bucket and causing the second leg's fill/withdraw to revert with `UnknownOrder` — a straightforward escrow accounting break, structurally identical to Cypher's sub-account/margin mechanism where completing one path against a shared balance improperly drew funds meant to also cover a different position.

### Impact Explanation
This is a fund-safety break in the escrow accounting of `IntentGatewayV2`'s same-chain intents path, reachable by any unprivileged solver submitting a `fillOrder` transaction against an order it (or a colluding order creator) constructs with repeated input token addresses across legs. The result is: (a) a solver over-collects escrow relative to the specific leg it filled, and (b) the remaining legs referencing the same token become permanently unfulfillable (their escrow evaporates), denying the honest counterparties their expected output/refund — concrete theft or permanent freezing of funds as required by the validation criteria.

### Likelihood Explanation
Reachable from a single `fillOrder` call with no special privileges — only requires an order with ≥2 inputs sharing a token address feeding independent output legs, which nothing in `placeOrder`/`_fillSameChain` currently rejects.

### Recommendation
Track escrow per `(commitment, input index)` rather than per `(commitment, token)`, or explicitly reject orders whose `inputs[]` contains duplicate token addresses at `placeOrder` time. In `_fillSameChain`, always compute the leg's release amount from the pro-rata formula `(order.inputs[i].amount * fillAmount) / totalRequired` (or the leg's own remaining ledger entry) rather than reading the shared per-token bucket on full-fill.

### Proof of Concept
1. User places a same-chain order with two inputs of the same ERC-20 token `T`: `inputs[0] = {T, 600}` backing `output[0]`, `inputs[1] = {T, 400}` backing `output[1]`. At placement, `_orders[commitment][T] = 1000`.
2. Solver calls `fillOrder` and fully satisfies `output[0]` in one call. In `_fillSameChain`, since `amountFilled == totalRequired` for leg 0, `escrowedAmount = _orders[commitment][T]` = 1000 (the full bucket), not 600.
3. `_withdraw` transfers 1000 `T` to the solver and sets `_orders[commitment][T] = 0`, even though only 600 was owed for leg 0.
4. A subsequent fill attempt for `output[1]` reads `_orders[commitment][T] == 0` and reverts with `UnknownOrder`, permanently stranding the user's expectation for leg 1 while the solver walked away with 400 extra tokens that belonged to leg 1's escrow. [4](#0-3) [5](#0-4)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
