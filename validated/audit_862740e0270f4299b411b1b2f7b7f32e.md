### Title
Webhook shop identity is never bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Registry.process` treats `Utils::HmacValidator.validate(request)` as proof that the *entire* webhook — including the `shop-domain` header — is authentic, but `Webhooks::Request#to_signable_string` only returns `@raw_body`. Because the app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, an attacker who owns a legitimate dev-shop installation can capture one of their own validly-signed webhook deliveries and replay the identical `raw_body`/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and `Registry.process` will accept it and hand the forged `shop` value straight to the handler.

### Finding Description
The binding that should hold is:

`request.shop` (the value dispatched to the handler as the tenant identifier) `==` `shop that the received signature was computed over`

Tracing the code:
- `Webhooks::Request#shop` reads the unauthenticated header `shopify-shop-domain`/`x-shopify-shop-domain` [1](#0-0) .
- `Webhooks::Request#to_signable_string` returns only `@raw_body` — headers, including the shop header, are never part of the signed material [2](#0-1) .
- `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it to the received HMAC — again, only body bytes, never the shop header, feed the computation [3](#0-2) .
- `Registry.process` gates only on that boolean, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the handler, with no independent check that this shop was the one Shopify actually addressed the signature to [4](#0-3) .

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` *is* included in `to_signable_string`, showing the library elsewhere treats shop-binding as a first-class part of the signed payload [5](#0-4) . No such binding exists in the webhook path.

`Context.api_secret_key` is the app's single `client_secret`, shared by every shop that installs the app — it is not a per-shop secret. An attacker who legitimately installs the target app on their own dev shop will receive genuinely-signed webhook deliveries (valid `raw_body` + HMAC pair, computed with that shared secret). Because the shop header is outside the signed bytes, the attacker can:
1. Capture one of their own legitimate webhook deliveries (`raw_body`, `X-Shopify-Hmac-Sha256`).
2. Replay that exact `raw_body`/HMAC pair to the app's webhook receiver endpoint, substituting `X-Shopify-Shop-Domain` with the victim's shop domain.
3. `HmacValidator.validate` still returns `true` (the body and secret are unchanged), so `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` even though that shop never signed or sent anything.

No other guard in this file (or reachable from it) re-derives or checks `request.shop` against the signed bytes — `ShopValidator.sanitize!`, `state` comparisons, and `JwtPayload`'s `aud` check belong to OAuth/session-token flows, not `Registry.process`, and are not invoked here.

### Impact Explanation
The app's webhook handler is invoked with an attacker-chosen `shop` value and attacker-originated body content that passes HMAC verification, letting one tenant's traffic be attributed to another tenant. Any host-app logic that keys persistence, GDPR (`customers/redact`, `shop/redact`, `customers/data_request`), inventory, or order-processing side effects off `WebhookMetadata#shop` can be made to write/act on behalf of a victim shop it never received input from — this is cross-tenant data injection/contamination, repeatable against any victim shop that has installed the same app, at will and indefinitely, since the attacker only needs one legitimately-signed payload template to replay with arbitrary shop headers.

### Likelihood Explanation
Preconditions are minimal and match the stated attacker model exactly: attacker installs the app on their own dev shop (no special privilege), captures one genuine webhook delivery, and replays it against the shared webhook endpoint with a modified `shop-domain` header. No secret, token, or credential is required — only observation of traffic the attacker legitimately receives for their own shop. This is fully repeatable and costs nothing beyond one webhook subscription and one HTTP replay per exploit attempt.

### Recommendation
Bind the shop identity to the verified bytes before dispatch in `Registry.process`: either (a) include the shop domain in the signable string used by `HmacValidator`, or (b) require the host app / gem to cross-check `request.shop` against a separately-authenticated source of truth (e.g., the shop associated with the specific webhook subscription/session) rather than trusting the header outright, rejecting the request if they diverge.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_binding_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryShopBindingTest < Minitest::Test
      def setup
        ShopifyAPI::Context.setup(
          api_key: "key", api_secret_key: "secret", api_version: "2024-01",
          host_name: "app.com", scope: "read_products", is_embedded: false,
          is_private: false,
        )
        ShopifyAPI::Webhooks::Registry.clear
        @received_shops = []
        handler = Class.new do
          define_method(:handle) { |data:| ShopifyAPITest::Webhooks::RegistryShopBindingTest.record(data.shop) }
        end.new
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: handler,
        )
      end

      def self.record(shop)
        (@@shops ||= []) << shop
      end

      def self.shops
        @@shops ||= []
      end

      def build_request(shop_domain)
        raw_body = '{"id":1}'
        hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
        headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => Base64.encode64(hmac),
          "x-shopify-shop-domain" => shop_domain,
        }
        ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
      end

      def test_hmac_validity_is_independent_of_shop_header
        victim_request = build_request("victim-shop.myshopify.com")
        attacker_request = build_request("attacker-shop.myshopify.com")

        # Same raw_body/hmac, different shop headers: both pass validation identically.
        ShopifyAPI::Webhooks::Registry.process(victim_request)
        ShopifyAPI::Webhooks::Registry.process(attacker_request)

        assert_includes(self.class.shops, "victim-shop.myshopify.com")
        assert_includes(self.class.shops, "attacker-shop.myshopify.com")
        # Both succeeded with the SAME raw_body + hmac pair, proving shop is unauthenticated.
      end
    end
  end
end
```
This demonstrates that `Registry.process` accepts the identical signed payload regardless of the asserted `shop` header, confirming the shop field is never bound to the validated bytes.
