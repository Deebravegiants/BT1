### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop-domain` header — which `Registry.process` passes on to the host application's handler as the authoritative tenant identifier — is read directly from an unauthenticated HTTP header and never bound into the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` verifies a webhook by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only the raw JSON body, and `hmac` is decoded from the `hmac-sha256`/`x-shopify-hmac-sha256` header — but `shop` is read from a completely separate header (`shop-domain`) that is not part of the signable string at all: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., that the *body* came from Shopify with the app's secret), and then unconditionally forwards `request.shop` — the unauthenticated header value — to the handler as the tenant identifier: [3](#0-2) 

Because `shop` is never bound into the HMAC, the equality the gem implicitly relies on — "the shop the HMAC authorizes" == "the shop the handler is told to act on" — does not hold. A holder of any genuine webhook delivery for their *own* shop (a legitimate, unprivileged merchant/tenant of the host app) possesses a body + valid HMAC pair that is valid for that exact body regardless of which `shop-domain` header accompanies it, since the header is outside the signed bytes. That merchant can resubmit the identical body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a different tenant's shop domain. `Utils::HmacValidator.validate` still returns `true` (only the body+secret are checked), and `Registry.process` will call the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, ...)`, causing the host application to attribute Shopify-authenticated event data to a tenant that never sent it.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to enforce: an attacker who is a legitimate merchant of the app can inject fabricated events under another merchant's shop identity. Depending on how the host application's handler uses `WebhookMetadata#shop` (e.g., to select which merchant's data store, session, or credentials to update), this constitutes cross-tenant access/data injection — writing or triggering actions against another tenant's account using data attributed to that tenant without their involvement.

### Likelihood Explanation
Likelihood is realistic for any actor who is themselves onboarded to the app (their own shop generates real, validly-signed webhook deliveries), since the only requirement is capturing one legitimate body+HMAC pair and replaying it with a modified `shop-domain` header value — no knowledge of `api_secret_key` or another tenant's credentials is required. The delivery must reach the app's webhook endpoint directly (bypassing Shopify's normal per-shop dispatch), which is a plausible unprivileged-internet-user path since HTTP endpoints handling webhooks are typically public.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `topic`, `api-version`, `webhook-id`) in the signable payload verified by the HMAC, or otherwise cryptographically bind the `shop-domain` header to the signature before trusting it as the tenant identifier passed to `WebhookHandler#handle`.

### Proof of Concept
1. As a legitimate merchant "shop-a.myshopify.com" installed on the app, trigger any webhook (e.g. `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay the exact same request to the app's webhook endpoint, but change the header `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` still decodes `H`; `#to_signable_string` still returns `B`; `Utils::HmacValidator.validate` recomputes the same HMAC over `B` and it matches, so validation succeeds: [4](#0-3) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: <B's parsed contents>, ...)`, even though `shop-b` never sent this event — demonstrating the handler receiving Shopify-authenticated body content falsely attributed to a different tenant.
