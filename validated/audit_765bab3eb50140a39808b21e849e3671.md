### Title
Webhook `shop-domain` header is trusted and delivered to app handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC against the raw request body only. The `shop` value that is subsequently handed to the app's `WebhookHandler` (the tenant identifier the host app will act on) is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) accessors instead read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` verifies the HMAC via `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (i.e., the raw body) against the computed signature, and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` from the headers when building `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

This is the same bug class as the referenced ERC5095 finding: a value that is *acted upon* (here, the `shop` field used to attribute the webhook to a tenant) is disjoint from the value that is *actually covered by the integrity check* (here, only the raw body bytes). The equality that should hold — `hmac_signed_bytes == bytes_that_determine(shop)` — does not, because `shop` is derived purely from an attacker-controllable header while the HMAC only binds the body.

Because the HMAC signing key (`client_secret`) is the same for every shop installing a given app, any merchant who installs the app on their own shop can obtain a genuinely-signed webhook request (valid HMAC for some body) from Shopify. That merchant/attacker can then replay the identical raw body and HMAC header to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop's domain) and/or a different `shopify-topic` / `shopify-webhook-id` header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards `request.shop` (attacker-controlled) straight into `WebhookMetadata`, which the host application uses to decide which tenant's data to update.

### Impact Explanation
This breaks the tenant-identity binding a host application relies on (`WebhookMetadata#shop`) despite the code path being labeled as "verified" (`Invalid webhook HMAC.` is only raised when the body-only check fails). An attacker who controls their own installation of the app can cause the webhook handler to process fabricated data under another shop's identity, i.e., cross-tenant confusion/cross-tenant access to whatever side effects the handler performs keyed on `data.shop` (e.g., writing "orders/create" data, revoking access, updating billing state, etc., for a shop the attacker doesn't control).

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) and be able to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is needed — only observing one legitimate webhook delivery to their own shop to obtain a body + HMAC pair, which they can then replay with a forged `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified payload rather than trusting the unauthenticated header value. At minimum, `to_signable_string` should incorporate a canonicalized combination of the header fields the application depends on (or, more robustly, host applications should be told/enforced to cross-check `request.shop` against the currently-authenticated session/shop making the callback registration, not just trust the header). If Shopify's real webhook protocol truly only signs the body, the gem should not silently expose `shop` as if it were verified data — the API/docs should clearly flag that the shop-domain header is unauthenticated and must be independently corroborated (e.g., matched against a known/stored shop) before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining a legitimate webhook delivery, e.g. for `orders/create`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body signed with app's client_secret>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate(request)` still returns `true` because it only hashes `raw_body`.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, causing the host application to attribute/act on attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
