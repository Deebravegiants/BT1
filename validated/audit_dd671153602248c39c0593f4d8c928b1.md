Confirmed: `Webhooks::Request#hmac` signs only `to_signable_string` (the raw body), while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the signed payload.### Title
Webhook `shop-domain` header is trusted as tenant identity while only the request body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content as the raw body only, and `Registry.process` uses `Utils::HmacValidator.validate(request)` to authenticate the webhook. The `shop` value that is handed to the app's `WebhookHandler` (and used by apps as the tenant key to look up sessions/data) is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is **not** part of the HMAC-signed payload.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC and then builds `WebhookMetadata` using `request.shop`, which is pulled straight from the (unsigned) header: [2](#0-1) [3](#0-2) 

`WebhookMetadata.shop` is then handed directly to the host application's `handle` method as the authoritative tenant identity: [4](#0-3) 

By contrast, `Auth::Oauth::AuthQuery` (used for the OAuth callback) does include `shop` inside `to_signable_string`, so it is properly bound to the HMAC: [5](#0-4) 

This creates the exact identity-binding gap called out in the analog rules: **the field acted on (`shop`) is not covered by the HMAC that is verified.** The equality that should hold is:
`shop used to authorize/attribute the webhook == shop bound inside the HMAC-signed payload`
but in this gem it is actually:
`shop used to attribute the webhook == shop taken from an unauthenticated header`, while only the JSON body is bound by the signature.

Because Shopify's webhook HMAC secret (the app's `client_secret`) is shared across every shop that installs the same app, any shop that has legitimately installed the app can obtain a real, validly-signed webhook body+HMAC pair for its own store (e.g., by triggering an `orders/create` webhook on its own shop). That merchant — an "unprivileged" actor relative to any other tenant of the same multi-tenant app — can then replay that same body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks the body against the same shared secret, and the forged `shop` value will flow unmodified into `WebhookMetadata.shop`, which is exactly what host apps are documented and expected to trust as the shop that produced the event.

### Impact Explanation
This matches "Critical - cross-tenant access": a webhook payload can be attributed to an arbitrary shop merely by manipulating an unauthenticated header, letting a low-privileged tenant of the app inject data or trigger side effects (order/webhook processing, data writes, cache/session updates keyed by shop) under another merchant's identity, without ever needing that other merchant's credentials.

### Likelihood Explanation
Exploitation only requires: (1) the attacker to be any merchant who has installed the same Shopify app (no elevated privilege, no access to the app's `client_secret`, no compromise of Shopify's infrastructure), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — both of which are trivially available to any internet client. The gem provides no mechanism to bind `shop` to the signature, so every app built on `Webhooks::Registry.process` inherits this gap by design, making this a systemic library-level issue rather than a host-app misconfiguration.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) as part of the value verified by `Utils::HmacValidator`, e.g., by extending `Request#to_signable_string` to bind `shop` (and other trust-critical headers) into the signed content, or by having `Registry.process` independently cross-check `request.shop` against an out-of-band trusted source (such as the session store keyed by the webhook subscription) before invoking the handler. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be used by host apps as a tenant key without independent verification.

### Proof of Concept
1. App A has two installs: Shop X (attacker) and Shop Y (victim), both webhooks routed to the same app endpoint, both signed with the same `client_secret`.
2. Attacker triggers a real webhook event on Shop X, capturing the raw JSON body and the resulting `X-Shopify-Hmac-Sha256` header (both valid, since Shopify computed them with the shared secret).
3. Attacker replays this exact body + HMAC header to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-y.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against the shared secret: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata` with `shop: "shop-y.myshopify.com"` and dispatches it to the host app's handler as if the event genuinely originated from Shop Y: [2](#0-1)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
