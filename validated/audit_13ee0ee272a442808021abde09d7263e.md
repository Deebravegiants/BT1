## Analysis

The external Solmate finding centers on a common bug class: **updating internal accounting state to reflect a successful transfer without actually confirming that the transfer succeeded**. While NEAR core-contracts don't use ERC20 `safeTransfer`/`safeTransferFrom`, the same root-cause pattern (unconditional balance deduction paired with an unchecked/uncallback'd fund-movement primitive) is reachable in `staking-pool`.

### Title
Unstaked balance and `last_total_balance` are permanently decremented before the NEAR transfer promise is confirmed successful in `internal_withdraw` - (`staking-pool/src/internal.rs`)

### Summary
`internal_withdraw` deducts the caller's `unstaked` balance and the contract's `last_total_balance`, then fires a `Promise::new(account_id).transfer(amount)` with no `.then()` callback to verify the transfer's outcome, unlike the equivalent flow in `lockup`.

### Finding Description
In `staking-pool/src/internal.rs`, `internal_withdraw` synchronously mutates state — decrementing `account.unstaked`, persisting it via `internal_save_account`, and decrementing `self.last_total_balance` — and only afterward schedules the native transfer, without checking or reacting to its result: [1](#0-0) 

This function is invoked by both `withdraw` and `withdraw_all`, both public/unprivileged entrypoints: [2](#0-1) 

Compare this to the parallel flow in `lockup`, where a staking-pool withdrawal is only reflected in contract state inside the async callback, guarded by `is_promise_success()`: [3](#0-2) 
and the calling code explicitly schedules that callback via `.then(ext_self_owner::on_staking_pool_withdraw(...))`: [4](#0-3) 

`staking-pool::internal_withdraw` has no equivalent callback/rollback mechanism. If the outbound transfer receipt fails for any reason after the calling receipt has already committed the state mutation (e.g., the contract's actual liquid NEAR balance is insufficient to cover the transfer at execution time — which can diverge from the internal `unstaked`/`last_total_balance` accounting due to rounding in `STAKE_SHARE_PRICE_GUARANTEE_FUND` handling, concurrent unstake/withdraw races, or restaking/locking interactions with `internal_restake`), the deduction from the user's `unstaked` balance and from `last_total_balance` is not reverted. The user's on-chain accounting entry has already been consumed with no compensating error handling, no retry path, and no way to reclaim the un-delivered funds through the contract's own public interface.

### Impact Explanation
This maps to "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... unstake-withdraw ... flows" — an unprivileged staking-pool depositor calling the public `withdraw`/`withdraw_all` methods can have their internal `unstaked` balance and the contract's `last_total_balance` permanently decremented while the corresponding NEAR transfer receipt fails, leaving them with no accounted balance and no delivered funds, and no code path to recover it since `internal_save_account` already persisted the decremented account and there's no failure branch.

### Likelihood Explanation
Likelihood depends on the transfer receipt actually failing after the state-mutating receipt has committed — a scenario made plausible by the fact that `last_total_balance`/`unstaked` accounting is separate bookkeeping from the contract's real NEAR balance (reconciled only in `internal_ping`), so any divergence (rounding drift from the guarantee fund, reentrant/overlapping unstake-then-withdraw sequences, or an owner reducing balance via other paths) can cause the promised transfer to be short of actual liquid balance at execution time, while the deduction has already been made irrevocably in the calling receipt.

### Recommendation
Move the `account.unstaked -= amount` and `self.last_total_balance -= amount` state updates into a `.then()` callback that checks `is_promise_success()` on the `Promise::new(account_id).transfer(amount)` result — mirroring the pattern already used for `on_staking_pool_withdraw` in `lockup/src/owner_callbacks.rs` — so state is only finalized once the transfer is confirmed to have succeeded.

### Proof of Concept
1. An unprivileged user calls `withdraw`/`withdraw_all` on the staking pool with a valid `unstaked` balance.
2. `internal_withdraw` immediately zeroes/decrements `account.unstaked` and `self.last_total_balance`, and only then issues `Promise::new(account_id).transfer(amount)` with no callback. [5](#0-4) 
3. If the transfer receipt subsequently fails (contract's actual liquid balance insufficient relative to the divergent internal accounting), the user's balance reduction is never reverted, and the funds are unrecoverable through any public method.

```rust
    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
```

```rust
    /// Withdraws the entire unstaked balance from the predecessor account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw_all(&mut self) {
        let need_to_restake = self.internal_ping();

        let account_id = env::predecessor_account_id();
        let account = self.internal_get_account(&account_id);
        self.internal_withdraw(account.unstaked);

        if need_to_restake {
            self.internal_restake();
        }
    }

    /// Withdraws the non staked balance for given account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw(&mut self, amount: U128) {
        let need_to_restake = self.internal_ping();

        let amount: Balance = amount.into();
        self.internal_withdraw(amount);

        if need_to_restake {
            self.internal_restake();
        }
    }
```

```rust
    pub fn on_staking_pool_withdraw(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if withdraw_succeeded {
            {
                let staking_information = self.staking_information.as_mut().unwrap();
                // Due to staking rewards the deposit amount can become negative.
                staking_information.deposit_amount.0 = staking_information
                    .deposit_amount
                    .0
                    .saturating_sub(amount.0);
            }
            env::log(
                format!(
                    "The withdrawal of {} from @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {
            env::log(
                format!(
                    "The withdrawal of {} from @{} failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        }
        withdraw_succeeded
    }
```
