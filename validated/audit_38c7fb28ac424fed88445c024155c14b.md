### Title
Webhook `shop` identity is taken from an unauthenticated header, not from the HMAC-covered body, enabling cross-tenant confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request **body**, but the tenant identity (`shop`) that gets handed to the app's `WebhookHandler` is read from an HTTP **header** that is never covered by that HMAC. This is the same class of bug as the reported `LevelMinting` issue: a value that downstream code treats as authoritative (`_supportedAssets` membership / here, the `shop` field) is not actually bound by the check that is supposed to guarantee its integrity (the redeemable-set check / here, the HMAC signature).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled straight from HTTP headers (`shopify-shop-domain`, etc.), which are not part of the signed payload: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., HMAC over `to_signable_string` == `@raw_body`) and then forwards `request.shop` — the unauthenticated header value — directly into `WebhookMetadata`, which is passed to the app's handler as the tenant identifier: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` computes the HMAC using `Context.api_secret_key`, which is the same shared secret for **every shop** that installs the app — it is not a per-shop secret: [5](#0-4) 

Because the secret is shared across all tenants of the app and the signature covers only the JSON body (not headers), a `(body, hmac)` pair that is valid for shop A's webhook is also a cryptographically valid `(body, hmac)` pair when replayed with a different `shopify-shop-domain` header claiming to be shop B. `Registry.process` has no way to detect this substitution because it never checks that the header-derived `shop` is consistent with anything inside the signed body.

This directly parallels the report's hint: "a field acted on but not covered by the HMAC" — here the acted-upon field is `shop`, and the documented tenant-safety guarantee (`shop == the tenant this event actually happened to`) is broken because `shop` is outside the integrity boundary.

### Impact Explanation
Docs and tests show `WebhookHandler` implementations are expected to use `data.shop` as the tenant key to persist/process data (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

Any host application following this documented pattern — which is the gem's own recommended usage — will attribute an arbitrary, attacker-chosen shop domain to webhook body content that only the gem certified as "authentically from Shopify" via HMAC. An attacker who is a legitimate (but unprivileged relative to other tenants) merchant installer of a multi-tenant app can trigger an event on their own store to obtain one valid `(body, hmac)` pair from Shopify, then resend that exact body/hmac to the app's public webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop. The gem will report this as a validly-authenticated webhook for the victim shop, causing cross-tenant data confusion (e.g., writing attacker-controlled data into another tenant's record, or triggering shop-scoped side effects like `shop/redact` for a shop the attacker doesn't own). This matches the "Critical - cross-tenant access" impact category, since no `access_token`, `api_secret_key`, or privileged credential beyond ordinary app installation is required.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated HTTP endpoint (that is the entire point of webhooks), so no network position or special access is needed. Getting one legitimately signed webhook body is trivial for any merchant who installs the app (e.g., by triggering `orders/create` on their own shop). Forging the `shop`-domain header on the replayed request requires only standard HTTP client control, which any internet-connected caller has. The only friction is that the attacker must guess/know the victim's `.myshopify.com` domain, which is generally public/discoverable information (shop domains are not secrets).

### Recommendation
Do not treat the header-derived `shop` (or `topic`/`webhook_id`) as trusted on its own. At minimum:
- Bind `shop` to the signed payload, e.g. require/verify that the `shop` conveyed in headers matches a `shop`/`myshopify_domain` field present in the webhook body itself (Shopify includes shop-identifying data in most payloads), or
- Include the relevant headers (`shop-domain`, `topic`, `webhook-id`) in the HMAC-signable string rather than only the raw body, if compatible with Shopify's signing scheme, or
- Require host applications to cross-check `data.shop` against an existing, already-authenticated session/install record for that shop before trusting the payload, and document this requirement prominently since the current docs imply `data.shop` can be used directly.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com` (a multi-tenant SaaS app using this gem).
2. Attacker triggers an event on their own store (e.g., updates a product) causing Shopify to send a legitimately HMAC-signed webhook to the app:
   - Headers: `x-shopify-topic: products/update`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 123, "title": "Malicious Payload"}`
3. Attacker captures this raw `(body, hmac)` pair (they own the shop, so they can log network traffic reaching their own server-side callback, or use any request-inspection tool on their own webhook subscription).
4. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(api_secret_key, raw_body)`, which is unchanged and still valid: [7](#0-6) 
6. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id": 123, "title": "Malicious Payload"}, ...)`, and the host application — following the gem's documented pattern — processes/stores this payload under the victim shop's tenant record.
