### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from an HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. This breaks the intended binding: `hmac == HMAC(secret, body)` should imply `(body, shop) == (body, shop)` as delivered by Shopify, but the `shop` field used by the application to attribute the webhook to a tenant is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, so for a `Request` object it verifies the body signature and nothing about the shop header: [3](#0-2) 

`Registry.process` gates on this same HMAC check and then forwards `request.shop` (the unauthenticated header) directly into `WebhookMetadata` for the handler to act on: [4](#0-3) 

Because the HMAC only binds the raw body, any request with a *previously valid* `(raw_body, hmac)` pair — for example a webhook payload the attacker's own shop legitimately received from Shopify — remains HMAC-valid even if the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header is swapped for a different, victim shop's domain. `HmacValidator.validate` returns `true` because it never inspects the shop header at all, and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged operator of Shop A (who legitimately receives real, validly-signed webhooks for their own shop) can replay one of those bodies to the app's webhook endpoint with the shop header rewritten to Shop B's domain. The app's webhook handler — which trusts `data.shop` from `WebhookMetadata` (built straight off `request.shop`) to decide which tenant's session/data/access token to look up or update — will process attacker-supplied data under Shop B's identity, without ever validating that the header matches the shop the HMAC was actually generated for. Any app that keys per-tenant state, triggers tenant-scoped side effects, or authorizes actions based on `WebhookMetadata#shop` is exposed to cross-tenant data injection or unauthorized cross-tenant actions, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is bounded by the attacker needing a genuine `(raw_body, hmac)` pair, which they can obtain from any webhook legitimately delivered to their own store (they are a legitimate merchant/app-installer, i.e., an "unprivileged" party relative to other tenants). No access to the app's `client_secret` or another tenant's credentials is required — only replay of a header value that the gem never authenticates. This is analogous to the reported "first deposit" class bug in that a value the code trusts and acts on (the shop identity) is not actually bound by the mechanism (HMAC) meant to guarantee its authenticity.

### Recommendation
Bind the shop identity into the signed material, or independently verify it: e.g., include the shop domain in `to_signable_string` for webhook requests (if Shopify's webhook signing scheme supports it) or cross-check `request.shop` against a shop the app has an active, previously-registered webhook/session for before invoking any tenant-scoped handler logic. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and receives a legitimate webhook:
#   headers: { "x-shopify-topic" => "orders/create",
#              "x-shopify-hmac-sha256" => "<valid_b64_hmac_of_body>",
#              "x-shopify-shop-domain" => "shop-a.myshopify.com" }
#   raw_body: '{"id":123, ...}'

# Attacker replays the SAME raw_body/hmac but swaps the shop header:
tampered_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<same_valid_b64_hmac_of_body>", # body unchanged, so still valid
  "x-shopify-shop-domain" => "shop-b.myshopify.com",          # victim tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: tampered_headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "shop-b.myshopify.com", ...))
# The app now processes attacker-controlled webhook data attributed to shop-b.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
