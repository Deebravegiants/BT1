## Finding

### Title
Single failing token transfer in a multi-token escrow release permanently blocks fund recovery for all tokens in the order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` releases every escrowed token for an order in one loop with `safeTransfer`/native calls, and reverts the entire function if any single transfer fails. Because this function backs order settlement, refund, and cancellation, one problematic token (paused, blacklisted beneficiary, etc.) blocks recovery of *all* other, unrelated escrowed tokens belonging to the same order, mirroring the reported Sentiment `sweepTo` bug class where an all-or-nothing sweep loop turns one bad asset into a total liquidation failure.

### Finding Description
`_withdraw` iterates `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` (or a native `_sendValue`) for each token, with no isolation between iterations: [1](#0-0) 

If `beneficiary` is blacklisted for one of the escrowed ERC-20s (e.g., a frozen USDC/USDT address) or that token contract is paused, `safeTransfer` reverts and the whole `_withdraw` call reverts — including the release of every *other* token in `body.tokens`, and (when `finalize` is true) the `_filled` update and fee payout.

This function is reached from multiple unprivileged/relayer-triggered paths:
- Cross-chain settlement/refund via ISMP delivery: `ExtrinsicIntents.onAccept` decodes `RedeemEscrow`/`RefundEscrow` and calls `_withdraw`. [2](#0-1) 
- Cross-chain cancel-from-source GET response handling: `onGetResponse` calls `_withdraw` after verifying the destination fill slot is empty. [3](#0-2) 
- Same-chain cancellation, directly callable by the order owner: `_cancelSameChain` collects all remaining escrow across `order.inputs` and calls `_withdraw` unconditionally. [4](#0-3) 
- Same-chain (partial) fill settlement also routes through `_withdraw`. [5](#0-4) 

For the cross-chain `onAccept` path, `EvmHost.dispatchIncoming` does delete the request receipt and allow retries when `onAccept` reverts: [6](#0-5) 

but this retry mechanism only helps for *transient* failures. If the underlying cause is persistent (a permanently blacklisted beneficiary address, or a token contract that stays paused/deprecated), every retry of the same `WithdrawalRequest` fails identically forever, because `_withdraw` has no way to skip the offending token and still release the rest. The same-chain cancel path (`_cancelSameChain`) has no retry/receipt-deletion safety net at all — it is a direct external call that simply reverts, with no alternate function to recover only the healthy tokens.

### Impact Explanation
An order with multiple escrowed input tokens (e.g., USDC + DAI) becomes permanently unrecoverable in its entirety if just one of those tokens can no longer be transferred to the designated beneficiary/user — even though the other tokens are perfectly transferable. This is a permanent freezing of funds for the unaffected tokens, since there is no per-token settlement or sweep-to-alternate-address fallback, matching the reported "liquidation can fail" bug class (an all-or-nothing loop over heterogeneous assets that a single bad asset can jam).

### Likelihood Explanation
Multi-input orders are a normal, expected usage pattern of the Intent Gateway (the code explicitly iterates `body.tokens`/`order.inputs` arrays). Stablecoins such as USDC/USDT support address freezing by their issuers, and any ERC-20 pausable implementation is a realistic token to escrow. An attacker/griefer, or simply real-world compliance action against a beneficiary/user address, is a plausible, low-cost trigger — no special privilege is required to place or fill an order containing such a token.

### Recommendation
Make `_withdraw` resilient to individual token transfer failures:
- Wrap each token transfer in a try/catch (or low-level `call`) so a failure for one token does not prevent release of the others, and account for/emit any tokens that could not be delivered (e.g., leave them escrowed and expose a separate, permissionless retry/sweep-to-address function per token), instead of reverting the entire batch.
- Ensure `_filled`/finalize bookkeeping is not gated behind the success of every token transfer, or split "mark filled" from "transfer assets" the same way the original report recommends splitting liquidation from sweeping.

### Proof of Concept
1. User places a same-chain (or cross-chain) order with two inputs: `USDC` and `DAI`.
2. `USDC` issuer blacklists the order's beneficiary/user address (or, for a cross-chain settlement, the solver/user address becomes blacklisted before the redeem/refund message is delivered).
3. Cancellation (`_cancelSameChain`) or settlement delivery (`onAccept` → `_withdraw`) is attempted: the loop reaches the USDC transfer, `safeTransfer` reverts due to the blacklist, and the whole `_withdraw` call reverts.
4. The DAI escrow, which has no delivery obstacle, remains permanently locked in the contract alongside the USDC, because there is no code path that releases DAI independently of USDC's failure.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
