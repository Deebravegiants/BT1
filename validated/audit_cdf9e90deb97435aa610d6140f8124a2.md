## CallDispatcher.dispatch() has no access control or reentrancy guard, allowing theft of funds it transiently holds - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated, unguarded external function that executes attacker-suppliable low-level calls with arbitrary `value`. Multiple bridge apps (`IntentGatewayV2`/`IntentsBase`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) route native ETH and ERC20 tokens *through* a shared `CallDispatcher` instance as a transient custody point between two separate `dispatch()` invocations in the same flow. Because `dispatch()` checks neither `msg.sender` nor re-entrancy, any call target reachable from attacker/solver-supplied calldata (`order.predispatch.call`, `order.output.call`, or a token's `data` field) can re-enter the very same `CallDispatcher` and redirect its transiently-held balance to an attacker address before the legitimate second `dispatch()` call sweeps it back.

### Finding Description
`CallDispatcher.dispatch()` decodes a `Call[]` and blindly forwards `value`/`data` to any address with code, with zero access control: [1](#0-0) 

The contract is explicitly designed to hold ETH/ERC20 balances between calls — the docs confirm this is intentional ("the `CallDispatcher` can hold and forward native tokens") [2](#0-1) 

In `IntentsBase._execute`, user/solver-supplied `order.output.call` is executed by the dispatcher while it is holding output assets, and only afterward are the residual balances swept back with a *second*, separate call to `dispatch()`: [3](#0-2) 

The same two-call pattern exists in `IntentGatewayV2.placeOrder` for `order.predispatch.call` (assets are pushed to the dispatcher, `dispatch(order.predispatch.call)` runs attacker-controlled calldata, and only then is a sweep `dispatch(transferCalls)` issued to pull the balance back): [4](#0-3) 

`IntentGatewayV2.placeOrder` itself carries `nonReentrant`, but that guard only protects re-entry into `IntentGatewayV2`'s own functions — it does not, and cannot, protect the shared `CallDispatcher` contract, which has no reentrancy guard of its own: [5](#0-4) 

Because `order.predispatch.call`/`order.output.call` are attacker/solver-supplied `Call[]` entries whose `to`/`data` are fully controlled, one of those calls can target an attacker-owned contract; that contract, invoked *as* the low-level call target from inside `CallDispatcher.dispatch()`, can call back into `CallDispatcher.dispatch()` on the same instance (it is a plain external function, not `onlyOwner`/`onlyApp`, not `nonReentrant`) and instruct it to forward its *current* balance — the assets just deposited by the legitimate flow — to an address of the attacker's choosing.

The cross-chain token apps follow an identical two-step "unlock to dispatcher, then dispatch" pattern, so the same shared-dispatcher trust model applies to `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken.onAccept` whenever tokens are unlocked directly to the `CallDispatcher` address before `dispatch(message.data)` is invoked: [6](#0-5) 

### Impact Explanation
This is a concrete theft-of-funds primitive reachable from a single unprivileged transaction (a submitted intent order or a bridged token delivery whose calldata is attacker-controlled) — no admin, governance, relayer, or off-chain compromise required. Any value the shared `CallDispatcher` is holding at the moment an attacker-controlled call executes (escrowed order inputs/outputs, unlocked/minted bridge tokens, or residual dust from `receive()`/fee-on-transfer slippage) can be redirected to an attacker address instead of reaching its intended recipient (the order taker, the escrow, or the bridged-token beneficiary). Because `CallDispatcher` is a single shared, unauthenticated contract used by several apps (per the deploy scripts it is deployed once and configured into `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`), the blast radius is not limited to the flow that deposited the funds.

### Likelihood Explanation
High: `dispatch()` requires no privilege whatsoever to invoke, and the attacker-controlled call targets needed to trigger the reentrant drain are first-class, documented features of the intent/bridge flows (`predispatch.call`, `output.call`, HFT `message.data`) rather than an edge case. The only defenses on other contracts (`nonReentrant` on `placeOrder`, `onlyHost` on `onAccept`) do not extend to `CallDispatcher` itself, which has none.

### Recommendation
Add access control to `CallDispatcher.dispatch()` so only the configured caller contract(s) (the specific `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` instances that own that dispatcher) may invoke it, and/or add a reentrancy guard to `dispatch()` itself so a call executed inside one `dispatch()` invocation cannot recursively invoke `dispatch()` again on the same instance. Additionally, avoid the "transient custody in a shared, unauthenticated contract between two calls" pattern — prefer passing the balance/allowance atomically within a single `dispatch()` invocation, or use a per-call-scoped, freshly deployed dispatcher/ escrow rather than a long-lived shared singleton.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.predispatch.assets = [{token: X, amount: A}]` and `order.predispatch.call = [Call{ to: AttackerContract, value: 0, data: <exploit()> }]`.
2. `placeOrder` transfers `A` of token `X` to the configured `dispatcher` (`evm/src/apps/IntentGatewayV2.sol:244-251`), then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` (`evm/src/apps/IntentGatewayV2.sol:258`).
3. Inside that `dispatch()` call, `CallDispatcher` low-level-calls `AttackerContract.exploit()` (`evm/src/utils/CallDispatcher.sol:59`). `AttackerContract` re-enters `CallDispatcher.dispatch()` directly (unauthenticated, unguarded) with a `Call[]` transferring `X`'s full balance held by the dispatcher to an attacker-owned address.
4. Depending on how the surrounding flow validates post-dispatch balances (e.g., whether the follow-on sweep check reverts the whole transaction or is bypassable via zero/partial amounts, dust accounting, or a flow where the drained asset is not the one balance-checked afterward — such as the WETH/native `Call.value` forwarding path documented for `WrappedHyperFungibleToken`), the attacker can extract value that was meant for escrow/the order taker/the bridge beneficiary instead of it landing there.

Note: I was not able to fully trace the `fillOrder`/solver-funding path (who ultimately supplies `order.output.call` and the exact balance-check ordering at fill time) within the available iterations, so the fill-side variant of this primitive is plausible but not independently confirmed here — the `placeOrder`/`predispatch.call` variant above is directly supported by the read code. The core, fully-verified root cause is the complete absence of access control and reentrancy protection on `CallDispatcher.dispatch()` itself.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

            from: message.from,
            to: beneficiary,
            source: string(request.source),
