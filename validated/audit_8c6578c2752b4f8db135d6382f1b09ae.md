### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook delivery by validating an HMAC over the raw request body only. The `shop` (tenant) attribute that handlers use to know which merchant the event belongs to is read from the `x-shopify-shop-domain` header, which is completely outside the HMAC-protected content. Because the underlying HMAC secret (`api_secret_key`) is shared across all shops that install the app rather than being shop-specific, an attacker who controls one legitimate installation can forge webhook deliveries falsely attributed to a different shop.

### Finding Description
`Request#to_signable_string` returns `@raw_body` and nothing else [1](#0-0) . `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is attacker-controlled input on any HTTP request reaching the webhook endpoint [2](#0-1) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only proves the body bytes were signed with `Context.api_secret_key`, and then immediately builds `WebhookMetadata` using `request.shop`, an unauthenticated field, and dispatches it to the app's handler [3](#0-2) .

The identity binding that should hold is: `shop attributed to the event == shop cryptographically bound by the HMAC`. In this gem that equality is never enforced — the HMAC binds only `body`, not `(body, shop)`. Since `HmacValidator` uses the single app-wide `Context.api_secret_key` for every shop [5](#0-4) , a signature valid for shop A's webhook is equally "valid" (in the sense the gem checks) no matter which `shop` header accompanies it, because that header is never part of what's hashed.

### Impact Explanation
This crosses the cross-tenant boundary explicitly called out as Critical impact: an attacker who legitimately installs the app on their own store (unprivileged action, no special credentials needed) can capture one webhook delivery and replay its exact bytes to the same endpoint while substituting the `shop` header value of a victim merchant. The host application, trusting `WebhookMetadata#shop` as it's handed by this gem's own `Registry.process`/`Request` API, will process/store data as if it came from the victim shop — e.g. triggering shop-scoped data mutations, `shop/redact` or `customers/redact` handling, or webhook-driven session/data updates for a shop the attacker does not control.

### Likelihood Explanation
Likelihood is realistic: obtaining one authentic signed webhook body only requires installing the target app on any store (which is typically open to any Shopify merchant), then replaying the captured POST with a modified `shop` header — no access to `api_secret_key`, access tokens, or the victim's credentials is needed, satisfying the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-verified signable content, or independently verify that `request.shop` matches an expected/known shop for the delivery (e.g., cross-check against the shop that owns the corresponding `webhook_id`/registration) before dispatching to handlers. At minimum, document that `Request#shop` is unauthenticated and must not be trusted as a tenant identifier without additional verification by the host application.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) to capture a real request with its raw body and valid `x-shopify-hmac-sha256` header.
2. Replay the identical HTTP POST (same raw body, same valid HMAC header) to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (headers present) [6](#0-5) ; `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body against the shared `api_secret_key` [4](#0-3) .
4. `Registry.process` dispatches to the registered handler with `shop: "victim.myshopify.com"` [7](#0-6) , causing the host application to act on attacker-supplied data as if it originated from the victim shop.
