### Title
Webhook Shop Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` only verifies that body against the app's shared `api_secret_key`. The `shopify-shop-domain` (and `topic`/`webhook-id`) headers are never included in the signed content, yet `Registry.process` trusts `request.shop` as the tenant identity passed to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely over that signable string: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then hands `request.shop` (read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) to the handler as the tenant identity: [3](#0-2) 

The `shop` accessor is derived purely from headers with no cryptographic binding: [4](#0-3) 

Since the app's `api_secret_key` is a single shared secret across every shop that installs the app (not a per-shop secret), a merchant using the app receives genuine `(raw_body, hmac)` pairs for their own webhooks. That merchant can replay the exact same body/HMAC pair to the app's public webhook endpoint while swapping the `shopify-shop-domain` header to a different, victim shop's domain. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and `Registry.process` passes the attacker-chosen shop through to the handler via `WebhookMetadata`, breaking the identity binding: `shop authenticated by HMAC` ≠ `shop acted upon by the handler`.

### Impact Explanation
This crosses a tenant boundary: an app that persists or acts on webhook data keyed by `WebhookMetadata#shop` (the gem's documented, sole means of tenant attribution for webhooks) will attribute attacker-supplied/replayed data to a shop the attacker does not own. This satisfies the Critical "cross-tenant access" criterion — a merchant that only controls their own shop's legitimate webhook traffic can inject data attributed to another merchant's tenant.

### Likelihood Explanation
Any shop that installs the app is, by definition, an "unprivileged internet user" relative to other tenants of the same app, and can capture their own legitimately-signed webhook deliveries (e.g., via browser devtools/network capture, or a proxy) without needing the app's secret. Replaying the request to the app's public webhook URL with a modified shop header is trivial and requires no credentials beyond having installed the app once.

### Recommendation
Bind the shop identity to the HMAC-verified payload rather than trusting an unauthenticated header:
- Include the `shopify-shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signed content, or
- Require host applications to cross-check the header-derived shop against an authenticated, per-installation secret/session record before trusting `WebhookMetadata#shop`, and document this requirement clearly, or
- Have `Registry.process` reject requests where the shop header cannot be corroborated against known-registered subscriptions for that specific shop/session.

### Proof of Concept
1. Shop A installs the app and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared `api_secret_key`), plus `shopify-shop-domain: shop-a.myshopify.com`.
2. The operator of Shop A captures `(B, H)` from the delivered request.
3. Shop A's operator sends a new HTTP POST directly to the app's webhook endpoint with body `B`, header `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: shop-b.myshopify.com` (a victim tenant).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "shop-b.myshopify.com"` (from `request.shop`), causing the host app to process/store Shop A's replayed data as belonging to Shop B.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
