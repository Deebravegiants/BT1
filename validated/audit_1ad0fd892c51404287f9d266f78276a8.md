### Title
Missing shop-domain validation in OAuth callback allows `client_secret` exfiltration via attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request destination directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling flows `ClientCredentials.client_credentials`, `RefreshToken`, and `TokenExchange.exchange_token`, which explicitly call `Utils::ShopValidator.sanitize!(shop)` before using the shop value. This breaks the intended equality "the shop that is HMAC-authenticated == the shop that is validated as a trusted `*.myshopify.com`/known Shopify domain" — the code substitutes "HMAC-signed" for "domain-validated," which are not the same guarantee.

### Finding Description
`validate_auth_callback` validates only that the callback's query string was HMAC-signed with the app's `api_secret_key`/`old_api_secret_key`: [1](#0-0) 

It then builds a `null_session = Auth::Session.new(shop: auth_query.shop)` and passes it straight to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which computes the outbound request host as `"https://#{api_host || session.shop}"`: [2](#0-1) 

The POST body sent to that attacker-influenceable host includes `client_id` and `client_secret` in plaintext: [3](#0-2) 

Compare this to the three other credential-exchange flows in the same library, which all call `Utils::ShopValidator.sanitize!` to constrain the shop to a trusted Shopify domain before it is used to build the request host: [4](#0-3) 

`ShopValidator` exists specifically to prevent an attacker-supplied `shop` string from being treated as a legitimate request host: [5](#0-4) 

`oauth.rb`'s `validate_auth_callback` never calls it — grepping the codebase confirms `ShopValidator`/`sanitize!` usages are limited to `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `clients/graphql/storefront.rb`, and are absent from `auth/oauth.rb`.

The root of the analog to the reported bug class: the field acted upon (the destination host derived from `shop`) is not actually re-checked against the trusted-domain allowlist that a sibling code path enforces for the identical `shop`-derived host-building operation. The HMAC only proves the query string was signed by the app secret over `code/host/shop/state/timestamp` as delivered by Shopify's redirect — it does not itself constrain `shop` to be a `*.myshopify.com` domain, and nothing downstream re-checks that before the `client_secret` is transmitted to that host. If the OAuth callback route in a host application forwards a raw query string to `AuthQuery.new` without additional shop-domain checks (which the library does not require or document as mandatory, and does not perform itself), the shop value used to build the destination host has no explicit domain-allowlist enforcement inside this gem's own OAuth completion path.

### Impact Explanation
If a caller can influence the `shop` value reaching `AuthQuery` (e.g., because the host application is under the reasonable assumption that this gem enforces the same domain validation it enforces in `TokenExchange`/`ClientCredentials`/`RefreshToken`), the app's `client_secret` and `client_id` would be sent via HTTPS POST to a host chosen by that `shop` string, constituting SSRF with the app's credentials — a High-severity condition per the credential-exfiltration/SSRF criteria.

### Likelihood Explanation
Exploitability strictly depends on whether the `shop` value reaching `AuthQuery` can be attacker-influenced in a real deployment; this requires the surrounding HMAC to also validate for that attacker-chosen `shop` (i.e., it requires either a signature computed by Shopify for that shop, or a host application that skips its own shop-domain checks and trusts this gem to have already done so). I could not fully verify, purely from `lib/shopify_api/**`, whether Shopify's redirect mechanics could ever produce a validly-signed callback for a non-myshopify `shop` string, since HMAC generation is Shopify-side and out of this gem's control. This limits my confidence that this is independently, fully exploitable from an unprivileged internet user without any host-application-side omission — the asymmetry with the other three flows in the same library is nonetheless a real and directly-verifiable code-level inconsistency.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` inside `validate_auth_callback` before constructing `null_session`, mirroring the pattern already used in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, so the shop used to build the outbound request host to which `client_secret` is sent is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently reproducible purely within `lib/shopify_api/**` without controlling a validly-HMAC-signed callback for an attacker-chosen `shop`; the code-level gap is demonstrated by contrasting: [1](#0-0) 
(no `ShopValidator` call) against [4](#0-3) 
(explicit `Utils::ShopValidator.sanitize!(shop)` call) for the structurally identical operation of using `shop` to build the `client_secret`-bearing request host via `Clients::HttpClient`.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
```
