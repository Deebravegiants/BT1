### Title
Webhook Shop Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC that `Utils::HmacValidator` verifies authenticates *body integrity* only. The `shop` (and `topic`, `webhook_id`, `api_version`) values are taken straight from unauthenticated HTTP headers and are handed to the application's handler unchecked, allowing an attacker who possesses one valid `(raw_body, hmac)` pair to relabel it as originating from an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the body (`@raw_body`) is fed into the HMAC computation. `HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it with the `hmac-sha256` header value: [2](#0-1) 

Meanwhile `request.shop` is read directly from the unauthenticated `shopify-shop-domain` header: [3](#0-2) 

`Registry.process` verifies only the HMAC, then forwards `request.shop` (and `request.topic`, `request.webhook_id`) straight into `WebhookMetadata` passed to the app's handler, without any check binding the shop header to the signed body: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(raw_body) == true` should imply `shop_header == shop_that_produced(raw_body)`.

In this implementation that equality does not hold — `shop_header` is never part of the signed material, so it can be swapped for any value while the HMAC over the (unchanged) body remains valid.

### Impact Explanation
Any party capable of obtaining one legitimate `(raw_body, hmac)` pair sent to the app's public webhook endpoint (e.g., a shop owner who has installed the app themselves and can observe webhooks Shopify sends them, since HTTP webhook endpoints are internet-reachable) can replay that exact body+HMAC to the same endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different, victim shop's domain. Because `HmacValidator.validate` never inspects the shop header, the forged request passes verification and the handler executes business logic believing the event belongs to the victim shop — i.e., cross-tenant data confusion/injection using only body content the attacker was already legitimately entitled to generate. This satisfies the "cross-tenant access" high-impact criterion, since no `api_secret_key`, access token, or other credential the attacker shouldn't have is required — only replay of previously-observed bytes.

### Likelihood Explanation
The webhook endpoint is intentionally public (Shopify posts to it over the internet), so anyone can send arbitrary POSTs to it. Producing a *valid* HMAC without the secret is infeasible, but *reusing* a genuinely-issued HMAC/body pair from a webhook the attacker legitimately received (e.g. from their own shop install) requires no secret knowledge — only knowledge of the gem's documented behavior (shop identity comes from an unsigned header). This makes the attack straightforward for any developer/tenant using the same multi-tenant app.

### Recommendation
Include the shop domain (and ideally topic / webhook id) in the signed material, or independently verify that the `shop-domain` header corresponds to a shop the app has a stored session/installation for and that has actually been sent this exact webhook (e.g., via a webhook_id de-duplication/replay cache scoped to shop). At minimum, document and enforce that `WebhookMetadata#shop` must not be trusted for authorization decisions unless cross-checked against the app's own installation state.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: headers include `x-shopify-hmac-sha256: <H>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `B`.
2. Attacker replays the identical body `B` and header `x-shopify-hmac-sha256: <H>` to the same public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it came from the victim shop.
