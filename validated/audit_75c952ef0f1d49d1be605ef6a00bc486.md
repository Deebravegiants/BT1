## Analysis Result

The `instantUnstake` fee-rounding bug class maps directly onto the treasury reserve-fee minting logic in Zest's lending vaults (`vault-stx.clar`, `vault-usdc.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`, `vault-usdh.clar`, and their `mainnet/contracts/vault/v0-vault-*.clar` counterparts). The public, unprivileged `accrue` function computes the DAO's protocol-fee share of newly accrued interest via a floor-rounding `mul-div-down`, and that fee can be driven to zero by fragmenting accrual into many small calls — exactly the "loop small amounts to avoid the fee" pattern from the report.

### Title
DAO reserve-fee minting rounds down to zero when `accrue` is split into many small calls, letting suppliers capture protocol yield - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
The permissionless `accrue` function computes the DAO treasury's protocol fee (`reserve-inc`) as `mul-div-down(debt-delta, fee-reserve, BPS)` and only mints treasury shares (`treasury-lp`) when `reserve-inc > 0`. Because this rounds the fee down instead of rounding the fee up (or the net amount down), an attacker can call `accrue` repeatedly with very short time deltas so each `debt-delta` is small enough that `reserve-inc` floors to `0`, permanently skipping the treasury mint while the full interest still flows into `total-assets`, inflating the value of existing zToken holders' shares at the DAO's expense.

but the borrow-side `total-assets` (which determines the zToken share price for `deposit`/`redeem`) uses the *full, un-reduced* debt growth: [5](#0-4) 

The only mechanism that claws back the DAO's fee-reserve share from that full `total-assets` growth is the `treasury-lp` mint in `accrue`. Because `reserve-inc` is `mul-div-down`'d (floored) instead of rounded up, when `debt-delta * fee-reserve < BPS`, `reserve-inc` is exactly `0` and no treasury shares are minted for that call — yet `total-assets` (and thus `total-supply-preview`/`convert-to-assets-preview` share pricing) has already fully absorbed that interest. An attacker calling `accrue` every block instead of allowing interest to compound over a longer natural interval can keep each `debt-delta` under the rounding threshold indefinitely, systematically suppressing DAO treasury minting while share price for existing zToken holders appreciates by the full (undiscounted) interest amount.

This is functionally identical to the reported bug: `amount - fee` semantics (here, "grow total-assets fully, then try to subtract the DAO's cut via a separately floored calculation") let an attacker fragment a value transfer into pieces small enough that the fee rounds to zero on each piece, while the underlying value transfer (interest accrual into `total-assets`) still occurs in full.

### Impact Explanation
This breaks the identity: `DAO treasury fee = fee-reserve × (interest accrued into total-assets)`. By spamming `accrue()` with short intervals, an attacker (or even an economically-incentivized bot, since it strictly benefits existing zToken/LP holders and thus arbitrageurs holding those tokens) permanently zeroes or greatly reduces the DAO's cut of interest revenue for as long as the attack is sustained, while suppliers receive 100% of the yield. This is theft of unclaimed yield/royalties belonging to the DAO Treasury — a High severity impact per the given classification.

### Likelihood Explanation
`accrue` is a public function with no access control, callable by anyone at any time, and it is also invoked as part of every `deposit`/`redeem`/`borrow`/`repay` call, so simply performing many rapid low-value operations (or calling `accrue` directly in a loop) achieves the fragmentation with no special privileges, no flashloan, and no DAO compromise required. The magnitude of loss depends on `fee-reserve`, per-block interest rate, and token decimals — smaller-decimal or lower-utilization vaults are more susceptible, mirroring the report's observation that low-cost chains / low-decimal tokens make the exploit more practical.

### Recommendation
Avoid floor-rounding the reserve fee out of a monotonically growing debt-delta. Round the reserve fee up (`mul-div-up`) so it can only be zero when `fee-reserve` itself is zero, or accumulate a running remainder across `accrue` calls so fractional fee dust is never permanently lost (carry-forward pattern), analogous to the recommended `amountMinusFee = amount * (BASIS_POINTS - fee) / BASIS_POINTS` fix in the report.

### Proof of Concept
1. Vault has `fee-reserve = 1000` (10%), `BPS = 10000`. Assume current borrow rate implies interest accrues at a rate such that letting one hour pass yields `debt-delta = 1000` base units, giving `reserve-inc = mul-div-down(1000, 1000, 10000) = 100` (correctly minted to treasury).
2. Instead, attacker calls `accrue()` (directly, or indirectly by calling `deposit`/`redeem` with `min-out`/`amount` values chosen to satisfy preconditions) once per Stacks block over the same hour (e.g., 60 times), so each call's `time-delta` yields `debt-delta ≈ 16` per call.
3. Each call computes `reserve-inc = mul-div-down(16, 1000, 10000) = 1` — actually check smaller windows: for sub-second/short blocks or lower utilization, `debt-delta` per call can easily fall under `10` (the threshold below which `mul-div-down(debt-delta, 1000, 10000)` floors to `0`), e.g., `debt-delta = 9` gives `reserve-inc = 0`.
4. Over 60 such calls with `debt-delta = 9` each (total interest = `540`), total treasury minting = `0`, whereas a single `accrue()` over the same period with `debt-delta = 540` would have minted `reserve-inc = 54`.
5. `total-assets` still increases by the full `540` across all calls (via `idx`/`total-borrowed`), so that value is captured entirely by existing zToken holders through share-price appreciation in `convert-to-assets-preview`, while DAO treasury receives nothing for the corresponding period.
