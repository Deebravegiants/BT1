### Title
Missing freeze-authority check on coin/pc mints in `Initialize2` allows a malicious pool creator to permanently freeze the AMM vaults - ([File: program/src/processor.rs])

### Summary
`process_initialize2` validates that the LP mint has no freeze authority, but never performs the same check on the coin mint or pc mint that the attacker supplies as the pool's trading pair. Anyone can create a pool (permissionless `Initialize2`), so an attacker can mint a token with a live `freeze_authority`, use it as `coin_mint`/`pc_mint`, seed the pool, and later freeze the AMM's own vault token account, permanently locking all liquidity ever deposited into that pool.

### Finding Description
In `process_initialize2`, the coin and pc mints are unpacked via `Self::unpack_mint(...)`, which only checks the token-program owner and successfully deserializes the mint — it performs no validation on `freeze_authority`: [1](#0-0) 

Compare this to the LP mint, which is explicitly required to have no freeze authority before the pool is allowed to mint initial liquidity: [2](#0-1) 

The coin/pc mints, however, are unpacked and used to build the AMM's vault accounts (`amm_coin_vault_info`, `amm_pc_vault_info`) with no equivalent guard: [3](#0-2) 

Because vault accounts owned by the AMM authority PDA are ordinary SPL Token accounts for whatever mint the creator supplied, if that mint still has an active `freeze_authority`, the mint's admin (i.e., the pool creator, who controls the mint) can call SPL Token's `FreezeAccount` on the vault at any time after `Initialize2` completes. Once the vault is frozen, every subsequent SPL Token CPI transfer out of (or into) that vault fails, because `spl_token::instruction::transfer`/`mint_to` on a frozen account errors out inside the token program. This breaks:
- `Deposit`, which calls `Invokers::token_transfer` against the coin/pc vaults, e.g. the analogous transfer pattern used throughout the swap/deposit code: [4](#0-3) 
- `Withdraw`, which transfers user LP tokens for a share of the frozen vault
- All four swap instructions (base-in/base-out coin↔pc), which both deposit into and withdraw from the vaults via `Invokers::token_transfer`/`token_transfer_with_authority`: [5](#0-4) 

Since the vault is a PDA-owned account and the AMM program has no path to change or clear an externally-set freeze on the mint, once frozen, the funds are permanently locked with no on-chain recovery.

### Impact Explanation
Any liquidity contributed to the pool by unrelated, honest LPs (in addition to the attacker's own seed liquidity) becomes permanently frozen the moment the attacker calls `FreezeAccount` on the vault. This is a permanent freezing of user/LP funds, matching High severity: no swap, deposit, or withdrawal against that pool can ever succeed again, and there is no unfreeze mechanism available to the program or its users.

### Likelihood Explanation
The attack requires only a single permissionless `Initialize2` transaction using a token mint the attacker fully controls (mint authority + freeze authority retained), which is trivial and low-cost to create on Solana. No privileged Raydium signer, validator behavior, or off-chain component is needed — the attacker supplies their own accounts and data end-to-end.

### Recommendation
In `process_initialize2`, after unpacking `coin_mint`/`pc_mint`, reject pool creation if either mint's `freeze_authority` is `Some`, mirroring the existing check already applied to `lp_mint`:
```rust
if coin_mint.freeze_authority.is_some() || pc_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
```

### Proof of Concept
1. Attacker creates an SPL mint `M` with `freeze_authority = attacker_key` and mints supply to themselves.
2. Attacker calls `Initialize2` using `M` as `amm_coin_mint`/`amm_pc_mint` (and a normal token, e.g. USDC, as the other side), seeding `amm_coin_vault`/`amm_pc_vault` — `unpack_mint` passes because it never checks `freeze_authority` [6](#0-5) .
3. Other users deposit liquidity via `Deposit`, adding `M` and USDC to the vaults.
4. Attacker submits an SPL Token `FreezeAccount` instruction against `amm_coin_vault_info` using their retained freeze authority over mint `M`.
5. All subsequent `Deposit`, `Withdraw`, and swap instructions touching that vault fail at the `Invokers::token_transfer*` CPI calls (e.g. [7](#0-6) ), permanently locking all deposited funds in the pool.

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
    ) -> Result<(), ProgramError> {
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }

    /// Issue a spl_token `Transfer` instruction.

        authority: AccountInfo<'a>,

            destination.key,

            amount,
        )?;

            &ix,

        )
    }
