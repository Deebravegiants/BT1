### Title
Webhook shop identity spoofing via header field excluded from HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` header — which is *not* covered by that HMAC — to attribute the webhook to a tenant. An attacker who possesses one genuinely-signed `(raw_body, hmac)` pair for their own shop (trivially obtainable, since they are a real merchant who installed the app and legitimately receives Shopify webhooks) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature still validates (it only checks body bytes), so the handler executes with `WebhookMetadata#shop` pointing at a victim shop the attacker never controls.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature exclusively over `to_signable_string`: [3](#0-2) 

`Registry.process` performs that single check and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional verification that the header shop matches the body's true origin: [4](#0-3) 

The gem's own documentation instructs developers to construct the `Request` directly from the raw incoming HTTP request/headers (i.e., attacker-controlled input on a publicly reachable route), reinforcing that this is the intended, documented call path rather than a misuse of the API: [5](#0-4) 

This is the same bug class as the report: an identity-relevant field (`shop`) is acted upon downstream while a different, narrower set of bytes (`raw_body` only) is the one actually covered by the cryptographic check. The broken equality is:
`shop_bound_by_hmac (∅, not signed) ≠ shop_used_for_tenant_attribution (request.shop header, attacker-settable)`.

### Impact Explanation
Any internet-reachable actor who is a legitimate (unprivileged) merchant of the app can capture one authentic `(raw_body, hmac)` webhook pair for their own store — including for mandatory GDPR topics such as `customers/redact`, `customers/data_request`, or `shop/redact`, or for `app/uninstalled` — and replay it against the same public endpoint with a forged `shop-domain` header naming a different, victim tenant. Because `Registry.process` never ties `request.shop` to the signed bytes, the handler executes believing the event genuinely originated from and pertains to the victim shop. Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (exactly as documented, e.g., `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data corruption/spoofing — e.g., triggering a GDPR redact/uninstall workflow against a shop the attacker does not own, or injecting the attacker's own webhook payload under another tenant's identity.

### Likelihood Explanation
The attack requires no `api_secret_key`, no access token, and no privileged account — only that the attacker be an ordinary merchant who has installed the app (satisfying the "unprivileged internet user" threshold), plus the ability to POST directly to the app's public webhook route with custom headers, both of which are trivial and match the gem's documented integration pattern exactly.

### Recommendation
Bind the shop (and other identity-critical headers such as `topic`/`webhook-id`) into the signed material, or otherwise cross-check `request.shop` against an independently-verified source of truth (e.g., the session/store record the app already has for that shop) before invoking the handler, rather than trusting the unauthenticated header value alongside a body-only HMAC.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate Shopify webhook, e.g. `customers/redact`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because Shopify signed `B` with the shared `api_secret_key`).
2. Attacker POSTs to the app's public webhook route (`/callback/customers/redact` in the docs example) with the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this passes.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to perform the redact/uninstall/data-request workflow against `victim.myshopify.com` on the attacker's behalf, even though Shopify never issued this webhook for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
