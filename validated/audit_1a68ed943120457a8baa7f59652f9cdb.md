### Title
Unbounded-depth SCALE decode of attacker-controlled `RuntimeCall` bytes in `hyper-fungible-token`'s `on_accept` enables stack-overflow DoS - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The XStream advisory is a stack-overflow DoS caused by deserializing an attacker-manipulated binary stream with unbounded/self-referential recursion. Hyperbridge has the exact same bug class in its `pallet_ismp` `RuntimeCall` decoding pipeline, and the codebase itself already fixed one instance of it (`pallet_call_decompressor`) with `decode_all_with_depth_limit` and an explicit `decompress_stack_exhaustion_poc` regression test [1](#0-0) . However, `hyper-fungible-token`'s `IsmpModule::on_accept` decodes an embedded, cross-chain-delivered `RuntimeCall` with plain, depth-unlimited `Decode::decode`, so the same fix was not applied there.

### Finding Description
In `Pallet::<T> as IsmpModule>::on_accept`, when an incoming token-transfer `PostRequest` carries non-empty `message.data`, the pallet decodes `SubstrateCalldata` and then decodes the embedded call bytes directly into the runtime's `RuntimeCall` type using unlimited-depth SCALE decoding: [2](#0-1) [3](#0-2) 

`RuntimeCall` is a recursive enum (it can contain `pallet_sudo::Call::sudo { call: Box<RuntimeCall> }`, `pallet_utility` batches, and other pallets' calls that box a nested `RuntimeCall`). SCALE's default `Decode` implementation recurses once per nesting level with no depth cap, so an input encoding thousands of nested call variants drives the decoder's call stack to overflow — precisely the class of bug XStream's binary-stream `Decode` path exhibited (CWE-121, stack-based buffer/recursion overflow via deserialization). The codebase's own test suite demonstrates that an encoded chain of ~1000 nested `Sudo(sudo(Box<...>))` calls is enough to exhaust the stack when decoded without a depth limit: [4](#0-3) 

That test only proves the attack works against `pallet_call_decompressor`'s decoder before the depth-limit fix was applied there; `hyper-fungible-token`'s `on_accept` uses the exact same unguarded pattern that the fix protects against and has no analogous protection or test.

Reachability: `on_accept` is invoked by `pallet-ismp`'s message-handling pipeline (`handle_unsigned`) whenever a `Post` request destined for a registered HFT contract is delivered with a valid consensus/state proof [5](#0-4) . Any account holding the corresponding `ContractToAsset` mapping's source contract, i.e., any user who can call the paired EVM token-bridge contract to send tokens with an accompanying calldata payload, can populate `message.data` (and therefore `substrate_data.runtime_call`) with an arbitrary attacker-chosen byte string, since the token amount/recipient fields are ABI-decoded from user input and the optional calldata is a free-form byte blob [6](#0-5) . No signature is required to reach the vulnerable decode call — the signature check (lines 124–172) only gates which *origin* the eventual dispatch uses, not whether decoding happens; decoding of `substrate_data.runtime_call` occurs unconditionally once `message.data` is non-empty.

### Impact Explanation
A crafted incoming token-transfer message that is otherwise valid (correct proof, registered source contract, valid amount) but carries a deeply nested `RuntimeCall` blob in its optional calldata field will overflow the decoding thread's stack during `handle_unsigned` execution. Because `handle_unsigned` is validated and executed by every collator/validator processing the block (and by the transaction pool during `validate_unsigned`), this can crash or panic the node process executing/validating the extrinsic — a remotely triggerable Denial of Service against block production/validation for any chain running `pallet-hyper-fungible-token`, matching the "High" severity of the original XStream advisory (network-wide service disruption via a single malicious message).

### Likelihood Explanation
Likelihood is high: constructing a deeply nested `RuntimeCall` SCALE encoding is trivial and does not require any cryptographic breaks, admin privileges, or race conditions — only a legitimate (attacker-owned) token transfer through the paired bridge contract with an oversized calldata payload. The `MaxCallSize`-style guard that exists in `pallet_call_decompressor` for exactly this attack does not exist in the HFT calldata-execution path, and there is no size/depth check before `SubstrateCalldata::decode` or `T::RuntimeCall::decode` in `on_accept`.

### Recommendation
Replace the plain `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` call in `modules/pallets/hyper-fungible-token/src/module.rs` with a depth-limited decode (e.g. `Decode::decode_all_with_depth_limit` from `codec::DecodeLimit`, mirroring `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` used in `pallet_call_decompressor`), and additionally bound `message.data`'s total length before attempting to decode `SubstrateCalldata`/`RuntimeCall`. Add a regression test analogous to `decompress_stack_exhaustion_poc` that submits a deeply nested `RuntimeCall` as calldata through `on_accept` and asserts a clean decode error rather than a stack overflow.

### Proof of Concept
1. Build a `RuntimeCall` value nesting `pallet_sudo::Call::sudo { call: Box<...> }` (or any other pallet call that boxes a `RuntimeCall`) several thousand levels deep, as done in the existing test: [7](#0-6) 
2. SCALE-encode this call and wrap it as `SubstrateCalldata { signature: None, runtime_call: <encoded bytes> }`, then encode that as `message.data`.
3. ABI-encode a `Message` with valid `to`, `amount`, `from`, and this `data` field, and submit it (via the token bridge’s existing send path, or directly as a crafted `Post` request body plus a valid state/consensus proof) as an ISMP `Post` request targeting the HFT module's registered contract.
4. Submit as `pallet_ismp::Call::handle_unsigned { messages: [Message::Request(...)] }`. When `on_accept` reaches `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)`, the unbounded recursive decode overflows the executing thread's stack, crashing/aborting the node processing (or validating) the extrinsic.
