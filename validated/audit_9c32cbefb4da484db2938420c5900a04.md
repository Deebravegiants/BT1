### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `shop` value taken from the `X-Shopify-Shop-Domain` header as an authenticated tenant identifier, but the gem's HMAC check only authenticates the raw request body, never the header. This breaks the equality "HMAC-authenticated bytes == identity used for tenant attribution," letting a party who can obtain one legitimately-signed webhook (e.g. from their own store) replay it with a forged `shop` header attributed to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (unauthenticated) HTTP header, entirely independent of the body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received HMAC only against `to_signable_string` (the raw body): [3](#0-2) 

`Registry.process` performs that body-only HMAC check, then unconditionally trusts `request.shop` as the source-of-truth tenant identity and hands it to the application's webhook handler: [4](#0-3) 

Because the signature covers only the body, two requests with the identical body but different `shop`/`webhook-id`/`api-version` headers produce the identical, valid HMAC. Any party who can obtain one genuine, signed webhook delivery from Shopify to the app (which requires nothing more than installing/using the app on their own store — no `api_secret_key`, access token, or other privileged credential) can capture that raw body + HMAC pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and `webhook-id`) header rewritten to name an arbitrary victim shop. `HmacValidator.validate` will accept it, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

This is the same bug class as the report's `op::execute`/balance-sync issue: an operation (here, tenant attribution of a webhook event) is driven by data that is not covered by the integrity/authentication check that gates the trusted operation.

### Impact Explanation
An app that keys any per-tenant side effect (e.g., updating billing state, disabling a plan, marking uninstalled, refreshing subscription status, invalidating sessions) off `WebhookMetadata#shop` can have that state changed for a shop the attacker does not own — a cross-tenant access/write primitive achieved purely by forging an HTTP header, without needing the app's `client_secret` or any merchant credential.

### Likelihood Explanation
Low-medium effort, no special access required: an attacker with any account that can trigger a webhook to the app (e.g., installing a public app on their own dev store, or subscribing to a webhook topic whose body content is generic/does not itself carry shop-identifying data) can capture a valid signed request and replay it with a different `shop` header value.

### Recommendation
Bind the shop identity into the material that is actually authenticated, e.g., verify the delivered `X-Shopify-Shop-Domain` header against the shop associated with the stored session/subscription for that `webhook-id`/topic before trusting it, or require host apps to cross-check `request.shop` against their own installed-shop registry rather than treating it as authenticated by the HMAC. At minimum, document explicitly in this gem that `Webhooks::Request#shop` is unauthenticated and must be independently verified by the host application before use.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook whose topic/body content contains no shop-identifying data (e.g., `app/uninstalled` with an empty or generic body).
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` value Shopify sent for that delivery.
3. Attacker POSTs the same body/HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and any desired `X-Shopify-Webhook-Id`).
4. `HmacValidator.validate` passes because it only checks `raw_body` against the HMAC [5](#0-4) .
5. `Registry.process` invokes the handler with `WebhookMetadata` claiming `shop: "victim.myshopify.com"` [6](#0-5) , causing any handler logic keyed on `shop` to act on the victim tenant.
