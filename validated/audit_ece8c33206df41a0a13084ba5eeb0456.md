### Title
Duplicate `erc20TokenAddresses` entries break the balance equation, enabling unbacked minting of shielded UTXOs - (File: `contracts/Hinkal.sol`, `contracts/HinkalHelper.sol`)

### Summary
`Hinkal.transact` validates, for every index `i` of `circomData.erc20TokenAddresses`, that the *whole-transaction* balance change for that token equals `amountChanges[i] + utxoAmount(i)`. Neither the circuit nor `dimensionsCheck` (`contracts/HinkalHelper.sol`) forbids the same ERC20 address from appearing more than once in the array. Because the balance snapshot is taken once for the entire call, the same true balance delta `D` is checked against every duplicated index independently rather than being split across them, letting a caller mint shielded output value that exceeds what was actually deposited.

### Finding Description
`transact` takes one `oldBalances`/`newBalances` snapshot for the whole `erc20TokenAddresses` array, then loops per index to enforce the balance equation: [1](#0-0) 

For a given token address, `balanceDif` is the *aggregate* real change in contract balance for that token over the whole call — identical for every array index holding that same address. `_internalTransact` performs a real transfer per index based on `amountChanges[i]`: [2](#0-1) 

`dimensionsCheck` in `HinkalHelper.sol` validates array lengths but never checks that `erc20TokenAddresses` entries are unique: [3](#0-2) 

If the same token address is placed at `n` indices with deposit amounts `a_1..a_n` (so the true aggregate deposit is `D = a_1+...+a_n`), the per-index check requires, for every `j`:
`D == amountChanges[j] + utxoAmount(j)` ⇒ `utxoAmount(j) = D - a_j`.

Summing over all `n` positions: `Σ utxoAmount(j) = n·D − D = (n−1)·D`. With `n = 3` duplicated indices, the attacker can create shielded output commitments totaling `2D` while only depositing `D` tokens — i.e. `D` worth of shielded value is minted with no backing (drawn from the shared pool's existing reserves). This breaks the core equality the report's bug class targets: "value moved by Hinkal ... but not counted in the balance equation" — here the same movement is *double-counted* across duplicate slots instead of being properly partitioned.

Nothing in `MainEVMCircuit.circom` enforces distinctness of `erc20TokenAddresses` either; each token slot is processed independently with its own inputs/outputs/nullifiers, so the ZK proof for such a crafted transaction is satisfiable.

### Impact Explanation
This is Critical: it allows minting shielded value without backing, directly draining the shared pool of legitimately deposited funds of other users. Once inserted, the extra unbacked commitments are ordinary leaves in the Merkle tree and are fully spendable later via normal `transact` calls, resulting in permanent theft of protocol funds.

### Likelihood Explanation
Any unprivileged EOA capable of constructing a valid proof (a normal Hinkal user/relay) can supply a `circomData.erc20TokenAddresses` array with repeated entries for the same token, since neither `dimensionsCheck` nor the circuit rejects duplicates. The only requirement is producing a valid witness for the repeated-slot arithmetic, which the circuit performs per slot with no cross-slot uniqueness constraint — no privileged role, admin, or relayer collusion is needed.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` in `dimensionsCheck` (or in `performHinkalChecks`), rejecting any transaction whose array contains a repeated token address. Alternatively, restructure the balance-equation check to aggregate `amountChanges[i] + utxoAmount(i)` across all indices sharing the same address and compare the aggregate against `balanceDif` once per distinct address, rather than checking the same `balanceDif` against each duplicated index independently.

### Proof of Concept
1. Attacker calls `Hinkal.transact` with `circomData.erc20TokenAddresses = [TKN, TKN, TKN]` (3 duplicate slots for the same ERC20).
2. Sets `amountChanges = [a1, a2, a3]` (all positive deposits), with `externalActionData.externalAddress == msg.sender`, causing `_internalTransact` to call `transferERC20TokenFromOrCheckETH` three times, pulling `a1+a2+a3 = D` tokens total from the attacker into the contract (see `contracts/Hinkal.sol` lines 172–187).
3. Crafts a valid proof/`circomData` such that for slot 0 the created on-chain/off-chain UTXO total is `u1 = a2+a3`, for slot 1 `u2 = a1+a3`, for slot 2 `u3 = a1+a2` — each individually satisfies `balanceDif (=D) == amountChanges[i] + utxoAmount(i)` at `contracts/Hinkal.sol` lines 137–146.
4. Total shielded UTXO value created: `u1+u2+u3 = 2D`, while only `D` was actually deposited — `D` of unbacked shielded value has been minted and is later withdrawable from the pool.
