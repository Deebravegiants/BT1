Interestingly, `DepositOnChainUtxosExternalAction.sol` explicitly guards against this by adding `+ utxoIndex` per output, which the code comment itself acknowledges: `"commitments are fully determined by the caller, because their timestamps come from circomData.timeStamp rather than from the block"` [1](#0-0) [2](#0-1) . `EmporiumUpgradeable.handleOut` has no such de-duplication and stamps every output UTXO in a call with the caller-supplied `circomData.timeStamp` unmodified [3](#0-2) .

### Title
Deterministic commitment/nullifier collision lets an attacker permanently freeze a self-created Emporium UTXO by duplicating (amount, token, stealthAddress, timeStamp) — (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.handleOut` stamps output UTXOs with a caller-controlled `circomData.timeStamp` that is never checked against `block.timestamp`, and both the on-chain commitment (`hash4`) and the in-circuit commitment/nullifier derivation are fully deterministic functions of `(amount, token, stealthAddress, timeStamp)` plus the owner's private key, with no leaf-index or randomizing salt. Two Emporium calls that produce identical `(balanceChange, token, stealthAddressStructure, timeStamp)` create two Merkle leaves with the identical commitment value, and — critically — spending either one computes the exact same nullifier, so once the first is spent the second becomes permanently unspendable.

### Finding Description
The broken equality is: **leaf_1 (commitment at tree index N) ≠ leaf_2 (commitment at tree index N+1)** is expected, but under this exploit **leaf_1 == leaf_2** as values, and worse, **nullifier(leaf_1, ownerKey) == nullifier(leaf_2, ownerKey)**.

Trace:
- `EmporiumUpgradeable.handleOut(balanceChange, circomData, i)` builds `outUtxo = UTXO(balanceChange, token, circomData.stealthAddressStructure, circomData.timeStamp)` directly from caller-supplied `circomData` fields, with no monotonic/unique salt added [3](#0-2) .
- `Hinkal.transact` → `createOnchainCommitment` computes `commitment = hash4(amount, token, stealthAddress, timeStamp)` [4](#0-3) , and `insertCommitments`/`insertMany` push this raw value as a Merkle leaf regardless of whether an identical value already exists in the tree [5](#0-4) .
- `circomData.timeStamp` is only integrity-checked via inclusion in `calldataHash`/`signedMessageHash` (`getSignedMessageHash`, `getHashedCalldata`) [6](#0-5) , and `performHinkalChecks` never compares it to `block.timestamp` [7](#0-6) . This is unlike `DepositOnChainUtxosExternalAction`, whose own code comment flags this exact pattern and which mitigates it by adding `+ utxoIndex` to every output's timestamp [1](#0-0) .
- When the attacker later spends one of these two identical-valued UTXOs, `MainEVMCircuit` recomputes `commitment = OriginalCommitmentCalculator(amount, token, publicKey, timeStamp)` [8](#0-7) , then `Signature.circom` computes `signature = Poseidon(nullifyingPrivateKey, commitment)` — fully deterministic, no random nonce [9](#0-8) , and `NullifierCalculator.circom` computes `nullifier = Poseidon(commitment, signature)` [10](#0-9) . Since `commitment` is identical for both UTXOs and the owner's `nullifyingPrivateKey` is the same, **both UTXOs map to the exact same nullifier value**, regardless of which Merkle leaf position (siblings/path) is used to prove inclusion — `MerkleRootCalculator` only requires the leaf *value* to hash up to a valid historical root, not a unique position [11](#0-10) .
- `HinkalBase.insertNullifiers` enforces global uniqueness on the nullifier value via `mapping(uint256=>bool) nullifiers` [12](#0-11) . Once the first identical leaf is spent, its nullifier is marked used; any later attempt to spend the second, value-identical leaf reverts with `"Nullifier cannot be reused"`, even though that leaf's own Merkle inclusion proof is perfectly valid and unspent.

None of the existing guards prevent this: `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `rootHashExists`, and the circuit's `ForceEqualIfEnabled`/`OverflowPreventer`/`BabyJubjubSubgroupCheck` constraints all validate proof/structural correctness, but none of them enforce leaf-value uniqueness or bind `timeStamp` to `block.timestamp` or to a per-output unique counter in the Emporium path.

### Impact Explanation
The attacker permanently strands their own funds represented by the second (later, colliding) UTXO — after the first colliding leaf is spent, the second's shared nullifier is already burned, so it can never be spent. This matches the "Critical — permanent freezing of user funds" category, though the direct victim is the attacker themselves, since triggering it against a real victim's future deposit would require predicting/controlling that victim's exact `stealthAddressStructure` and `timeStamp`, which the attacker cannot do without collusion. The attack is repeatable at will against the attacker's own funds, but has no clear path to steal or freeze a third party's assets without the victim voluntarily reusing the same `timeStamp`/`stealthAddress` pairing, which is not attacker-controllable in practice.

### Likelihood Explanation
Preconditions: attacker must craft two Emporium `runAction` calls with an `endpoint`/`callData` pair that produces identical `balanceChange` on identical token, use the identical `circomData.stealthAddressStructure`, and identical `circomData.timeStamp` in both — all fully within attacker control since they own the endpoint and can freely choose calldata/timestamp per the "Rules" (attacker can craft every field of `CircomData`). No relay privilege or victim cooperation is required to reproduce the self-inflicted freeze. Cost is only gas for two Emporium transactions plus proof generation. It is trivially repeatable by the attacker against their own funds.

### Recommendation
Bind output UTXO commitments to a value that is guaranteed unique per Merkle insertion instead of a fully caller-controlled `timeStamp`. Options: (a) require `circomData.timeStamp == block.timestamp` (or a tight window) in `performHinkalChecks`/`handleOut`, and additionally salt each output's timestamp with its position within the batch (as `DepositOnChainUtxosExternalAction` already does with `+ utxoIndex`) so that multiple outputs in the same block/tx cannot collide; or (b) include the Merkle leaf's insertion index (or a fresh random nonce, "rho") as an explicit additional input to the commitment/nullifier derivation so that two UTXOs with identical (amount, token, owner, timestamp) still yield distinct nullifiers.

### Proof of Concept
Foundry test plan (`EmporiumUpgradeable` + `Hinkal.transact`):
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a trivial `endpoint` contract that accepts arbitrary calldata and returns a fixed token amount to `msg.sender` (simulate `deltaAmountChanges`/`balancesAfter`).
2. Generate two Emporium `transact` calls (locally computed Groth16 proofs) with: same `erc20TokenAddresses[i]`, same `stealthAddressStructure`, same `circomData.timeStamp`, and endpoint calldata engineered so both produce the same `balanceChange` in `handleOut`.
3. Assert both calls' `NewCommitment` events emit the identical `commitment` value (`leaf_1 == leaf_2`), inserted at two different Merkle indices.
4. Spend the first UTXO with a valid proof; assert `Nullified(nullifier_1)` is emitted and `nullifiers[nullifier_1] == true`.
5. Attempt to spend the second UTXO (different Merkle path/siblings, same underlying commitment value) with a valid proof for its own inclusion; assert the transaction reverts with `"Nullifier cannot be reused"`, and that `nullifier_2 == nullifier_1` was computed by the circuit/off-chain nullifier calculator — proving the second leaf is permanently dead despite never being spent.
