### Title
Duplicate mnemonic check in `addSeed` compares raw strings, not seedId, allowing seedId-aliased entries in `extraSeeds` storage - (File: features/wallet/module/wallet.js)

### Summary
`Wallet#addSeed` computes `seedId` from `mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })`, but its duplicate-prevention check only compares raw mnemonic strings (`seeds.some((seed) => seed.mnemonic === mnemonic)`) instead of comparing `seedId`s. Because `validate: false` skips BIP39 wordlist/checksum validation, an attacker-supplied mnemonic can be an arbitrary string, and two distinct JS strings that are Unicode-canonically-equivalent (e.g., a precomposed character vs. its NFKD-decomposed form) normalize to the identical string inside `mnemonicToSeed`'s `nfkd()` call, yielding identical seed bytes and thus identical `seedId`, while still comparing as unequal strings.

### Finding Description
In `libraries/bip39/src/index.js`, `mnemonicToSeed` does:
```js
const salt = `mnemonic${nfkd(password)}`
return pbkdf2('sha512', nfkd(mnemonic), salt, { iterations: 2048, dkLen: 64 }, format)
``` [1](#0-0) 
The seed is derived from `nfkd(mnemonic)` alone; if `validate` is `false`, `mnemonicAssertValid` (which enforces wordlist membership and checksum) is skipped entirely, so any string is accepted as a "mnemonic" [2](#0-1) .

In `features/wallet/module/wallet.js`, `addSeed` calls `mnemonicToSeed` with `validate: false`, derives `seedId`, and only checks uniqueness of `seedId` against the primary seed — never against existing extra seeds:
```js
const seed = await mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })
const seedId = await getSeedId(seed)
if (seedId === (await this.#primarySeedIdAtom.get())) {
  throw new Error('Seed already present')
}
...
if (seeds.some((seed) => seed.mnemonic === mnemonic)) {
  throw new Error('Seed already present')
}
seeds.push(data)
await this.#setExtraSeeds(seeds)
await this.#seedMetadataAtom.set((previous) => ({ ...previous, [seedId]: { dateCreated, label, compatibilityMode } }))
return this.#keychain.addSeed(data.seed)
``` [3](#0-2) 

Because the duplicate check compares `seed.mnemonic === mnemonic` (raw string equality) rather than `seedId` equality, an attacker can submit `m1` and `m2` such that `m1 !== m2` as JS strings but `nfkd(m1) === nfkd(m2)` (e.g., a mnemonic word containing `"é"` U+00E9 vs. the canonically-equivalent decomposed form `"e"` + combining acute accent U+0301). Both calls to `addSeed` will:
- Pass the primary-seed check (same `seedId`, but not equal to primary).
- Pass the raw-string duplicate check (`m1 !== m2`).
- Push two distinct entries into the persisted `extraSeeds` array (`walletStorage[EXTRA_SEEDS_KEY]`) that both resolve to the identical `seedId`.
- Call `#keychain.addSeed(data.seed)` twice with identical seed bytes — a no-op collision in `Keychain#addSeed` since it simply re-derives the same `masters[seedId]`, but the persisted `extraSeeds` array now has two aliased records for one seedId [4](#0-3) .
- `seedMetadataAtom` itself is keyed by `seedId` and is overwritten, not duplicated — the metadata object won't contain two separate keys for the same seedId, but the `extraSeeds` storage array will contain aliased/duplicated records that map to a single `seedId`.

The `seeds.length >= this.#maxExtraSeeds` check counts array length, not unique `seedId`s, so an attacker can effectively exhaust the `maxExtraSeeds` quota using seedId-aliased mnemonics that all resolve to the same underlying key material, without ever adding a functionally distinct seed [5](#0-4) .

`removeManySeeds` recomputes `seedId` from each stored seed's bytes when filtering (`extraSeeds.map(async (seed) => [seed, await getSeedId(seed.seed)])`), so removing by `seedId` would actually remove all aliased records correctly (both objects resolve to the same seedId and get filtered together) [6](#0-5) . This limits (but does not eliminate) the "desync" impact hypothesized in the question — the primary concrete, provable impact is the persisted `extraSeeds` array containing seedId-duplicate/aliased entries and quota-exhaustion, not necessarily an unrecoverable removeSeed desync.

### Impact Explanation
The concrete, provable impact is: (1) storage-integrity corruption — `extraSeeds` can hold multiple records that alias the same `seedId`, violating the intended one-record-per-seed invariant; and (2) quota exhaustion — an attacker can consume all `maxExtraSeeds` slots with aliased mnemonics for what is cryptographically a single seed, denying the ability to add genuinely distinct seeds. This does not directly leak keys or bypass signing/authorization, so it falls under state/accounting integrity impact rather than direct fund loss.

### Likelihood Explanation
Requires only an unlocked wallet with multi-seed support enabled (`maxExtraSeeds > 0`) and attacker-controlled mnemonic input via the `addSeed`/import RPC — both are explicitly permitted preconditions. Crafting two Unicode-canonically-equivalent but string-unequal mnemonics is straightforward and repeatable (well-documented normalization behavior), and is trivially achievable because `validate: false` skips wordlist/checksum enforcement, so the attacker is not constrained to real BIP39 words.

### Recommendation
In `addSeed`, compute uniqueness by comparing derived `seedId`s (or the NFKD-normalized mnemonic) against all existing extra seeds' `seedId`s, not raw mnemonic string equality, e.g.:
```js
const existingSeedIds = await Promise.all(seeds.map((s) => getSeedId(s.seed)))
if (existingSeedIds.includes(seedId)) {
  throw new Error('Seed already present')
}
```
Also enforce the `maxExtraSeeds` cap against the count of unique `seedId`s rather than raw array length.

### Proof of Concept
Unit test (to be added under `features/wallet/module/__tests__/index.test.js`):
```js
const m1 = 'cousin access oak tragic entire dynamic marine expand govern enjoy honey tissu\u00E9' // é precomposed
const m2 = 'cousin access oak tragic entire dynamic marine expand govern enjoy honey tissue\u0301' // e + combining acute

const seedA = await mnemonicToSeed({ mnemonic: m1, format: 'buffer', validate: false })
const seedB = await mnemonicToSeed({ mnemonic: m2, format: 'buffer', validate: false })
assert(seedA.equals(seedB)) // same seed bytes / same seedId despite m1 !== m2

await wallet.addSeed({ mnemonic: m1 })
await wallet.addSeed({ mnemonic: m2 }) // currently succeeds — should throw or be a no-op

const extraSeeds = await wallet.getExtraSeedIds()
assert.strictEqual(new Set(extraSeeds).size, extraSeeds.length) // FAILS: duplicate seedId present in extraSeeds
```
Expected (fixed) behavior: the second `addSeed` call throws `'Seed already present'`, and `extraSeeds`/`seedMetadataAtom` remain seedId-unique.

export async function mnemonicToSeed({
  mnemonic,
  password = '',
  validate = true,
  wordlist = english,
  format = 'uint8',
}) {
  assert(typeof mnemonic === 'string' && mnemonic.length > 0, 'mnemonic must be a non-empty string')
  assert(typeof password === 'string', 'password should be a string')
  if (validate) await mnemonicAssertValid({ mnemonic, wordlist })
  const salt = `mnemonic${nfkd(password)}`
  return pbkdf2('sha512', nfkd(mnemonic), salt, { iterations: 2048, dkLen: 64 }, format)
}
