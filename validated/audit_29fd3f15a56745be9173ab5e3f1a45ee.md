### Title
First authority-set rotation (epoch 0) can never be recorded or rewarded due to zero-default sentinel collision - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.recordEpoch` uses `_currentEpoch == 0` (the storage default) as the "no epoch recorded yet" sentinel, exactly like `MainVault`'s `withdrawalRequestPeriod == 0` bug. Because `epoch 0` is also a *legitimate* value (`nextAuthoritySetId - 1` when the very first rotation brings in authority set `1`), the guard `authoritySetId <= _currentEpoch` collapses `0 <= 0` to true and silently no-ops, so the genuine first rotation is never attributed to any relayer.

### Finding Description
`HandlerV2.handleConsensus` computes the just-ended epoch as `nextAuthoritySetId - 1` and only calls `host.recordEpoch(epoch, _msgSender())` when `epoch > host.currentEpoch()`: [1](#0-0) 

`EvmHost.recordEpoch` repeats the same zero-based guard and writes `_epochs[authoritySetId] = relayer` only if it passes: [2](#0-1) 

`_currentEpoch` is a `uint256` storage variable that defaults to `0` — indistinguishable from "epoch 0 already recorded". When the very first mandatory consensus proof rotates the authority set from the genesis set to set `1` (`nextAuthoritySetId = 1`), the "just-ended" epoch computed by `HandlerV2` is `0`. Both `HandlerV2`'s `epoch > host.currentEpoch()` (`0 > 0`) and `EvmHost`'s `authoritySetId <= _currentEpoch` (`0 <= 0`) evaluate such that the write is skipped — `_epochs[0]` is never populated and `_currentEpoch` never advances off its default. This is structurally identical to the `MainVault.withdrawalRequestPeriod == 0` bug: a monotonic counter that legitimately starts at `0` is used as its own "not yet set" sentinel.

### Impact Explanation
`modules/pallets/relayer/src/outbound_consensus.rs::process_outbound_consensus_delivery_claim` pays the `OutboundConsensusDeliveryReward` to whichever relayer's signature matches the address stored at `EvmHost._epochs[set_id]`, proven via a destination state proof: [3](#0-2) 

An unset/zero-address slot is explicitly treated as `OutboundDeliveryNotProven` — "logically equivalent to 'no delivery proven yet'" — per the comment at lines 159-165. Because `_epochs[0]` can never be written on any `EvmHost` deployment, the relayer who performs the genuine first authority-set rotation delivery to that destination can never prove or claim `OutboundConsensusDeliveryReward` for `set_id = 0`. This is a permanent, unrecoverable loss of relayer-reward attribution for a specific, deterministic, always-occurring event (every fresh `EvmHost` deployment's first rotation), falling under in-scope "relayer fee and reward accounting."

### Likelihood Explanation
High likelihood of occurrence: this is not an edge case requiring attacker action — it triggers automatically and deterministically on the first authority-set rotation delivered to *every* `EvmHost` deployment (mainnet or new destination onboarding), with no way to reset `_currentEpoch` after the fact. Any relayer that is first to deliver that rotation is silently denied a reward it otherwise earned, with no error surfaced on the delivery transaction itself (the consensus message still processes/succeeds; only the epoch bookkeeping/reward-eligibility silently fails).

### Recommendation
Use an explicit "has an epoch been recorded" sentinel instead of overloading `0`, mirroring the suggested fix pattern in the source report (replace the ambiguous default-based check with an unambiguous one). For example, initialize `_currentEpoch` to `type(uint256).max` at deployment/construction (or track a separate `bool _epochRecorded` flag / start authority-set ids at 1 so `0` never occurs), and use that as the sentinel:

```solidity
// EvmHost.sol
uint256 private constant NO_EPOCH = type(uint256).max;
uint256 private _currentEpoch = NO_EPOCH; // set in constructor/initializer

function recordEpoch(uint256 authoritySetId, address relayer) external restrict(_hostParams.handler) {
    if (_currentEpoch != NO_EPOCH && authoritySetId <= _currentEpoch) return;
    _currentEpoch = authoritySetId;
    _epochs[authoritySetId] = relayer;
    emit NewEpoch({authoritySetId: authoritySetId, relayer: relayer});
}
```
and update `currentEpoch()`'s external consumers (e.g. `HandlerV2.handleConsensus`'s `epoch > host.currentEpoch()` gate) accordingly so epoch `0` is always recordable exactly once.

### Proof of Concept
1. Deploy a fresh `EvmHost` (as in `evm/tests/foundry/HandlerV2Test.sol` setup) — `_currentEpoch` defaults to `0`.
2. Submit a consensus proof via `HandlerV2.handleConsensus(host, proof)` where the decoded `nextAuthoritySetId = 1` (the first-ever rotation, i.e., ending epoch `0`), analogous to `_makeConsensusProof(paraId, height, 1)` used in `testHandleConsensusV2RecordsRelayerOnEpochChange` (which instead tests `nextAuthoritySetId = 2` and asserts `host.relayerOf(1) == tx.origin`): [4](#0-3) 
3. Observe that `epoch = nextAuthoritySetId - 1 = 0`, and `host.currentEpoch()` is `0` by default, so `epoch > host.currentEpoch()` is false — `recordEpoch` is never invoked and `host.relayerOf(0)` remains `address(0)` (compare with `testHandleConsensusV2NoEpochChange`, which asserts exactly `relayerOf(0) == address(0)` for the *no-rotation* case, showing the code cannot distinguish "no rotation happened" from "epoch 0 rotation happened but wasn't recorded"): [5](#0-4) 
4. Any relayer attempting `claim_outbound_consensus_delivery_reward` with `set_id = 0` for that destination will fail at the state-proof read of `_epochs[0]`, which is permanently the zero address, yielding `Error::OutboundDeliveryNotProven` forever — the reward for that legitimate delivery can never be claimed by anyone.
