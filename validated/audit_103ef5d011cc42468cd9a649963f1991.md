## Title
Webhook `shop-domain` header is trusted for tenant identity despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating the HMAC over the raw request body only, then hands the caller-supplied `shop-domain` header — a field the HMAC never covers — to the application as the trusted tenant identifier for that payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors simply read raw HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only that the body's HMAC is correct, then immediately trusts `request.shop`/`request.topic` (header values) to route and label the payload for the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

but in reality the HMAC only authenticates `(secret, raw_body)`; the `shop-domain` header is not part of the signable string, so:
`HMAC-covered bytes (body) != identity bytes used by handler (shop-domain header)`

Because Shopify signs webhooks per-app (not per-shop) using the app's single `client_secret`/`api_secret_key`, a valid `(body, hmac)` pair generated for one installation of the app is cryptographically valid for *any* shop using that same app. An attacker who installs the app on their own store (an ordinary, unprivileged action) receives real webhooks with a genuine `(body, hmac)` pair. They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain. `Utils::HmacValidator.validate` will report success because it only checks the body: [4](#0-3) 

`Registry.process` then calls the registered handler with `shop: request.shop` set to the victim's domain while `body: request.parsed_body` is the attacker's own (or arbitrary reused) payload: [5](#0-4) 

An app built on this gem's documented `WebhookMetadata` (keyed by `shop`) will therefore process attacker-controlled webhook content under a different tenant's identity — e.g. triggering GDPR `shop/redact`/`customers/redact` handling, `app/uninstalled` cleanup, or order/customer data writes attributed to a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: the `shop` value the app is told to trust after "successful" HMAC verification is not actually bound to that verification. This enables cross-tenant confusion/cross-tenant action — an unprivileged holder of a legitimate app installation (their own shop) can cause the app to process or misattribute events for a shop they do not own, purely by capturing one authentic webhook and re-sending it with a different `shop-domain` header. No access token, `api_secret_key`, or privileged account is required.

### Likelihood Explanation
Likelihood is high for any app that installs the gem's webhook registry as documented: the attacker only needs to be a legitimate installer of the target app on their own store (a normal, unprivileged flow) to obtain one valid `(body, hmac)` pair, and headers on an inbound HTTP request are trivially attacker-controlled unless the host framework independently re-verifies them (which the gem's own API gives it no way to do, since `shop`/`topic` are never included in the HMAC input).

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the shop/topic to the signed payload, so that the HMAC check fails if any of these identity-bearing headers are altered independently of the body.

### Proof of Concept
1. Install the target app (using this gem) on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw request: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`, and `client_secret` is shared across all installs of the app).
2. Replay a POST to the app's webhook endpoint using the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the body content actually originated from the attacker's own shop, so the app processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
