### Title
Missing minAnswer/maxAnswer check on Chainlink price feeds in `SimplexPaymaster._getOraclePrice` allows mispriced gas payments and treasury draining - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` only checks that the Chainlink `answer` is positive and not stale; it never validates the answer against the underlying aggregator's `minAnswer`/`maxAnswer` bounds [1](#0-0) . If either the `nativeOracle` or a registered token's `tokenOracle` hits its aggregator floor/ceiling during a market crash or de-peg event, the feed keeps reporting the clamped `minAnswer`/`maxAnswer` instead of the true price, and this contract has no mechanism to detect or reject it.

### Finding Description
`_getOraclePrice` is the sole price-validation function used across the whole pricing surface of `SimplexPaymaster`: `_tokenPrice` (used by `_fetchDetails` to price every gas-paying UserOp) and `swapAndDeposit` (used to compute `amountOutMin` for the treasury's fee-recycling swap) both call it for both the native/USD and token/USD feeds [2](#0-1) [3](#0-2) .

Any unprivileged sender who submits an ERC-4337 UserOp targeting this paymaster reaches this code path with no permission check: `_fetchDetails` is invoked during `PaymasterERC20`'s cost calculation and simply trusts `_tokenPrice(cfg)` as the exchange rate [4](#0-3) . The only sanity checks performed are:
```solidity
if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
if (block.timestamp - updatedAt > maxOracleAge) {
    revert StaleOraclePrice(address(oracle), updatedAt);
}
```
There is no comparison against the aggregator's configured `minAnswer`/`maxAnswer`, so a clamped answer (which is always positive and can be freshly "updated" by the aggregator's keeper even while economically stale/wrong) passes both checks silently.

### Impact Explanation
- If the `nativeOracle` (e.g. BNB/USD or ETH/USD) or a `tokenOracle` (e.g. a stablecoin/USD feed) is clamped at `minAnswer` during a crash, or at `maxAnswer` during a spike, `_tokenPrice` computes a wrong `tokenPrice = nativeUsd * 10^tokenDecimals * (1+markup) / tokenUsd` used directly to charge gas-paying users [2](#0-1) . Depending on which side is clamped, users can be systematically overcharged (loss of user funds via `_erc20Cost`/prefund) or the paymaster can be systematically undercharged, silently draining the treasury's stablecoin/native reserves over many UserOps.
- The same stale/clamped price feeds into `swapAndDeposit`'s `amountOutMin` calculation, which is meant to protect the treasury-controlled swap from bad execution prices; if the oracle itself is wrong, the "slippage protection" is anchored to the wrong reference price and can be gamed via a manipulated pool, directly costing the protocol swapped funds [5](#0-4) .
This is a Medium-severity fund-loss issue: it does not require any privileged actor, just a live market event pushing one of the configured feeds to its bound, combined with ordinary unprivileged UserOp submission.

### Likelihood Explanation
Chainlink aggregators for volatile assets (native gas tokens, and even some stablecoins during de-peg events) do have configured `minAnswer`/`maxAnswer` bounds, and hitting them during high volatility is a documented, recurring real-world occurrence (as referenced in the original report). Because `SimplexPaymaster` is explicitly designed to support arbitrary governance-registered ERC-20/oracle pairs (`RegisterToken`) [6](#0-5) , and every gas payment through the paymaster is priced via this unguarded call, the exposure grows with the number of supported tokens/chains and is triggered purely by external market conditions, not any special attacker capability.

### Recommendation
Fetch and cache each aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV2V3Interface.aggregator()` -> `minAnswer()`/`maxAnswer()`, or by having governance supply them at `RegisterToken`/`UpdateParams` time) and enforce them in `_getOraclePrice`:
```solidity
if (answer <= 0 || answer <= minAnswer || answer >= maxAnswer) {
    revert InvalidOraclePrice(address(oracle), answer);
}
```
This should be applied to both the `nativeOracle` and every `tokenOracle` used by `_tokenPrice` and `swapAndDeposit`.

### Proof of Concept
1. Governance registers a token whose `tokenOracle` is a Chainlink aggregator with `minAnswer = X`.
2. The underlying asset's market price drops below `X`; the aggregator's off-chain reporters keep pushing rounds, but `latestRoundData()` continues to return `answer == X` (clamped), with a fresh `updatedAt`.
3. Any user submits a UserOp paying gas with this token. `_fetchDetails` -> `_tokenPrice` -> `_getOraclePrice` accepts the clamped `X` because it is positive and fresh [7](#0-6) .
4. The computed `tokenPrice` misrepresents the true exchange rate, so `_erc20Cost` (called from `_prefund`) charges the wrong token amount, either overcharging the user or undercharging relative to true gas value, repeatable across every subsequent UserOp until governance intervenes with `UpdateParams`/`RegisterToken`.

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
