Audit Report

## Title
Missing future-timestamp validation in `HandleLegacyUserMessage` allows indefinite replay of signed Web API trigger messages - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` in the Gateway's legacy Web API trigger handler only rejects messages whose `TriggerRequestPayload.Timestamp` is too old, via `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`, and never checks that the timestamp is not in the future. Since `Timestamp` is fully client-controlled and signed, a message crafted with a far-future timestamp can be replayed indefinitely without ever failing this staleness check.

## Finding Description
The only freshness check performed on the incoming payload is the one-sided staleness comparison at [1](#0-0) . There is no corresponding upper bound comparing `payload.Timestamp` against `time.Now()`. The rest of the handler applies the sender's rate limiter and forwards the request unconditionally to every DON member via `don.SendToNode` [2](#0-1) , with no per-message replay/nonce tracking at this layer.

Downstream, `triggerConnectorHandler.processTrigger` in the workflow's web-api-trigger capability checks `allowedSenders`, `allowedTopics`, and the sender's rate limiter, then unconditionally forwards the event to the registered workflow channel for every topic match [3](#0-2) . There is no deduplication keyed on `TriggerEventId`/timestamp that would prevent the same signed message from firing the workflow again on each resend — `TriggerEventID` is only used to generate an execution ID for logging, not to block reprocessing [4](#0-3) .

This confirms the root cause: the freshness window is enforced only from one side (rejecting messages that are too old), while a future-dated, signed message can be resent by anyone holding it (including the original authorized sender or an interceptor) for as long as `payload.Timestamp` remains ahead of `now - MaxAllowedMessageAgeSec`, with each replay causing another workflow trigger.

## Impact Explanation
An authorized `allowedSender` (or anyone who captures a valid signed trigger message) can craft or reuse a message with `Timestamp` set arbitrarily far in the future, then resend the identical signed payload repeatedly to the gateway. Each resend passes the sole staleness check and is forwarded to all DON nodes and into the registered workflow's trigger channel, causing repeated/duplicate workflow executions ("unauthorized job run") well beyond the intended single-fire or freshness-bounded semantics of the trigger. This is a concrete, in-scope impact (unauthorized job run via gateway request replay).

## Likelihood Explanation
Likelihood is moderate: exploitation requires no privilege beyond being a configured `allowedSender` for the target workflow's `web_api_trigger` topic (or capturing one such sender's signed message), and the flaw is a straightforward, deterministic input-validation gap rather than requiring a cryptographic break or race condition. The per-sender rate limiter in `webapiTrigger.rateLimiter` throttles but does not eliminate the ability to repeatedly retrigger the workflow over time.

## Recommendation
Add a symmetric upper-bound check rejecting messages whose `payload.Timestamp` is ahead of `time.Now()` (allowing a small clock-skew tolerance) in `HandleLegacyUserMessage`, alongside the existing staleness check. Additionally, consider adding explicit per-sender/per-`TriggerEventId` replay tracking (similar to `RequestReplayGuard` or `jwtReplayCache` used elsewhere in the gateway) in either the gateway handler or `triggerConnectorHandler.processTrigger` so message freshness is not the sole replay defense for this legacy trigger path.

## Proof of Concept
1. As an address listed in `allowedSenders` for a workflow's `web-api-trigger@1.0.0` topic, construct a `webapicap.TriggerRequestPayload` with `Timestamp` set to `time.Now().Unix() + 10_000_000` and a fixed `TriggerEventId`.
2. Sign it with `msg.Sign(key)` (as done in `core/services/gateway/handlers/capabilities/handler_test.go`'s `triggerRequest` helper) and submit it as a `MethodWebAPITrigger` message; observe `HandleLegacyUserMessage` accepts it because `now - MaxAllowedMessageAgeSec` never exceeds the future timestamp, and it is forwarded to all DON members.
3. Resend the identical signed message at a later time (still within rate-limiter allowance); observe it is accepted again and forwarded again, since no nonce/replay cache exists in `HandleLegacyUserMessage` or `processTrigger`, each resend re-triggering the workflow.
