### Title
Webhook `shop` domain (and topic/webhook_id/api_version) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` domain, `topic`, `webhook_id`, and `api_version` are all parsed from separate, unsigned HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` only checks that the HMAC matches the body bytes, so any of these header-derived fields can be freely tampered with by an attacker without invalidating the signature. Since `ShopifyAPI::Webhooks::Registry.process` forwards `request.shop` directly into `WebhookMetadata` as the trusted tenant identifier — and the gem's own documentation instructs handlers to key business logic off `data.shop` — an attacker who can obtain one validly-signed webhook body (e.g., from their own shop's install) can replay it with a forged `x-shopify-shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
The identity binding that should hold is:
```
bytes_verified_by_HMAC == bytes_the_application_treats_as_authenticated(shop, topic, webhook_id, api_version)
```

In this gem, that equality is broken:
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight from HTTP headers with no cross-check against the signed body: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` only recomputes and compares the HMAC over `to_signable_string` (i.e. the body), never incorporating the headers: [3](#0-2) 
- `Registry.process` validates the HMAC and then unconditionally forwards the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` into the handler: [4](#0-3) 
- The `WebhookMetadata` struct exposes `shop` as a plain field with no indication it is unauthenticated: [5](#0-4) 
- The gem's own documentation tells integrators to treat `data.shop` as the tenant key for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that host apps will rely on it as an authenticated identity field.

Because `shop` (and the other headers) sit outside the HMAC-covered byte range, they satisfy the report's "field acted on but not covered by the HMAC" analog directly.

### Impact Explanation
An attacker who legitimately installs the target app on their own Shopify store will receive real webhooks for that store with a body and HMAC computed by Shopify using the app's `client_secret` — this is a completely valid signature the attacker can capture without needing the secret itself. Since the signature only binds the body, the attacker can resend the exact same request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a *different* (victim) shop. `HmacValidator.validate` will still pass because it only checks the (unmodified) body against the (unmodified) signature. The application, following the documented pattern, will process this as authentic data belonging to the victim tenant — a cross-tenant data-confusion/injection primitive (e.g., fabricated "orders/create" or "customers/redact" events attributed to a shop the attacker does not control), which can corrupt per-tenant state, trigger unauthorized side effects keyed by shop, or be used to inject spoofed compliance/redaction events against an unrelated merchant.

### Likelihood Explanation
Likelihood is high in relative terms: no leaked secret, no privileged account, and no TLS interception is required — only the ability to become a normal app installer (which is the ordinary, unprivileged onboarding flow for any public Shopify app), replay a captured legitimate request, and edit one HTTP header. The only friction is that the attacker must have a webhook topic in common between their own shop and the target processing logic, and the app must key sensitive behavior off `data.shop` (as the docs recommend) rather than performing an independent server-side lookup.

### Recommendation
Bind the identity fields into the signed content instead of trusting the raw headers verbatim:
- Preserve compatibility with Shopify's real signing scheme (which also only signs the body) but stop treating header-derived `shop`/`topic`/`webhook_id` as authenticated inside this gem — clearly document in `WebhookMetadata` that `shop` is unauthenticated header data and that host applications MUST independently verify the shop has a known, registered session/webhook subscription before trusting the payload for tenant-scoped actions.
- Optionally, have `Registry.process` cross-check `request.shop`/`request.topic` against the currently registered subscription/session for that shop (e.g., verify a session exists for `request.shop` and that `request.topic` was actually registered) before invoking the handler, rather than passing the raw header values through unchecked.
- At minimum, add a loud warning in `docs/usage/webhooks.md` and in `WebhookMetadata`'s type documentation that `shop`, `topic`, `webhook_id`, and `api_version` are NOT covered by the HMAC and must not be used as the sole authorization/tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store (`attacker.myshopify.com`) and subscribes to a webhook topic the app also processes for other merchants (e.g. `customers/redact` or `orders/create`).
2. Shopify sends a legitimate webhook POST to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request and replays it to the same endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (topic/webhook_id can also be altered if desired), leaving the body `B` and its HMAC unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — unchanged — and succeeds: [6](#0-5) 
5. `request.shop` returns the attacker-forged `"victim-shop.myshopify.com"`, and this is what gets handed to the app's handler as `data.shop`: [7](#0-6) 
6. The host app, following the documented usage pattern of trusting `data.shop`, processes attacker-controlled body content as though it originated from `victim-shop.myshopify.com`.
