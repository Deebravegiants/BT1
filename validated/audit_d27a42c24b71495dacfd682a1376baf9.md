### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the pre-transfer amount instead of the tokens actually received, causing under-collateralized escrow for fee-on-transfer tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` escrows tokens by transferring `order.inputs[i].amount` via `safeTransferFrom`/sweep calls, but credits `_orders[commitment][token]` with `reducedInputs[i].amount`, a value derived purely from the user-declared `order.inputs[i].amount` minus the protocol fee — never from the balance the gateway actually received. The main EVM `IntentGatewayV2.sol` (non-Tron) fixed this exact issue by measuring `balanceOf` before and after each transfer/sweep and mutating `order.inputs[i].amount` to the real received amount before computing the commitment/escrow, but the Tron contract still uses the unadjusted, pre-fee-deduction value.

### Finding Description
In `placeOrder`, `reducedInputs` and the commitment hash are computed directly from `order.inputs[i].amount` (the user-specified amount) before any token movement occurs: [1](#0-0) 

Later, tokens are actually escrowed via `safeTransferFrom` (non-predispatch path) or swept from a call dispatcher (predispatch path), but in both branches the contract still credits `_orders[commitment][token]` with the pre-computed `reducedInputs[i].amount`, without checking what the gateway actually received: [2](#0-1) [3](#0-2) 

For any fee-on-transfer ERC-20 used as an input token, the gateway's actual token balance increase is strictly less than `order.inputs[i].amount` (and less than `reducedInputs[i].amount`), yet the escrow ledger `_orders[commitment][token]` is inflated to the pre-fee value. This is the exact class of bug the sibling `evm/src/apps/IntentGatewayV2.sol` was hardened against — that contract snapshots balances before/after each transfer and mutates `order.inputs[i].amount` to the actually-received amount prior to computing `reducedInputs`/commitment: [4](#0-3) 

That fix and its accompanying Foundry test suite explicitly validate this scenario is a real, exploitable risk class for this codebase: [5](#0-4) 

The Tron contract's `withdraw` function later pays out exactly the ledgered `_orders[body.commitment][token]` amount to the beneficiary (solver on fill, or user on refund) via `token.call(transfer(...))`, without any real-time balance check against actual contract holdings: [6](#0-5) 

### Impact Explanation
Because the escrow ledger is credited above the true token balance held by the gateway for every order using a fee-on-transfer input token, the sum of all `_orders[commitment][token]` claims across active orders can exceed the gateway's actual token balance. When solvers/users later redeem via `RedeemEscrow`/`RefundEscrow` (`onAccept` → `withdraw`), transfers can fail for later claimants once the shortfall is exhausted, permanently freezing funds for the affected orders, or — depending on transfer ordering — allow one over-credited withdrawal to drain balance that rightfully belongs to other orders' escrow, effectively stealing from other depositors' locked funds. This satisfies the "permanent freezing of funds" / unauthorized value transfer criteria for a Medium/High severity finding in Hyperbridge's IntentGatewayV2 escrow accounting.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` with a fee-on-transfer (or any deflationary/rebasing-on-transfer) ERC-20 as an input token — a single transaction is sufficient to create a permanently mismatched escrow entry. No special privileges, governance, or multi-step setup are required, and the codebase's own test suite for the sibling EVM contract demonstrates this token category is explicitly anticipated to occur in production usage.

### Recommendation
Apply the same fix already implemented in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot `IERC20(token).balanceOf(address(this))` (and dispatcher balances in the predispatch sweep) before and after each transfer, use the actually-received delta as `order.inputs[i].amount` before computing `reducedInputs`/the commitment hash, and credit `_orders[commitment][token]` with that reconciled, actually-received value rather than the user-declared pre-fee amount.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC-20 (e.g., 1% transfer fee) as a supported input token.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no protocol fee configured.
3. `reducedInputs[0].amount` = 1000e18 (since `protocolFeeBps == 0`, `reducedInputs = order.inputs` unchanged) and commitment is computed from this value.
4. `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but due to the 1% fee, the gateway's balance only increases by 990e18.
5. `_orders[commitment][token] += reducedInputs[0].amount` credits 1000e18, i.e., 10e18 more than what the contract actually holds for this order.
6. When the order is filled/refunded, `withdraw` transfers `amount = 1000e18` to the beneficiary based on the ledger — over-crediting relative to actual contract balance, which either reverts (freezing other users' escrow) or succeeds by drawing down tokens escrowed for unrelated orders.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
