This confirms the vulnerability. The gem's documented, intended usage flow is exactly `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))` as shown in `docs/usage/webhooks.md`, and internally `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` and `request.topic` taken straight from HTTP headers.

### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` HMACs that body against `Context.api_secret_key`. The `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and label the webhook are read directly from HTTP headers, which are never part of the signed material.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body`: [1](#0-0)  while `shop`, `topic`, and `webhook_id` are pulled from headers with no cryptographic binding to the body: [2](#0-1) . `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value [3](#0-2) , so the signature only attests to body integrity, never to which shop or topic the body belongs to. `Registry.process` accepts the request purely on `HmacValidator.validate(request)` succeeding, then forwards the header-derived `shop`/`topic` straight to the app's handler: [4](#0-3) .

The equality this breaks is: `shop bound by HMAC == shop acted on by handler`. In reality, `shop (and topic) authenticated by HMAC == ∅`; only the raw body bytes are authenticated. This is the same class of defect as the reported bug (a value used by downstream logic that is not the value actually covered by the cryptographic check) — except here the unauthenticated value is a tenant-identifying field (`shop`) and a routing field (`topic`), not a price/exchange-rate value.

### Impact Explanation
An unprivileged internet user who legitimately operates their own Shopify shop and installs the target app receives genuine webhooks from Shopify — full HTTP requests including a body and a valid `hmac-sha256` header computed with the app's real `client_secret`. Because the signature covers only the body, the attacker can capture such a genuine request and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain, and/or the `X-Shopify-Topic` header changed to a different registered topic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`), while the HMAC remains valid since the body is untouched. The app's handler will process this as an authentic event for the victim shop/topic. Depending on what the handler does with `data.shop` (e.g. `shopify_app`'s reference handlers delete shop data, revoke tokens, or write records keyed by shop on `shop/redact`/`app/uninstalled`), this is a cross-tenant integrity/availability attack triggered purely with credentials the attacker legitimately possesses for their own shop.

### Likelihood Explanation
Medium-High: no secret, token, or privileged account for the victim is required — only a legitimate but attacker-controlled shop installation of the target app (which any internet user can create) is needed to harvest one validly-signed webhook body/HMAC pair, plus a body that some registered topic will accept without content-based validation (e.g. GDPR compliance topics have minimal/empty bodies as shown in the test fixtures using `"{}"` bodies [5](#0-4) ). The gem's own documented processing path performs no additional binding between the signed body and the headers.

### Recommendation
Include the identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., have `to_signable_string` concatenate a canonical form of these header values with the body) so the signature attests to the full tuple `(shop, topic, body)` rather than the body alone. At minimum, document that consuming apps must independently verify `data.shop` against a known/subscribed shop and must not trust `data.topic` for authorization-sensitive routing without additional validation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, gets a real webhook fired by Shopify for topic `orders/create`, and captures the raw POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B)`), `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256: H` header to the same public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or `X-Shopify-Topic: app/uninstalled` if body `B` is compatible/empty, as GDPR/compliance topics accept trivial bodies).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `to_signable_string` is still `B`, so `Utils::HmacValidator.validate(request)` returns `true` [1](#0-0) .
4. `Registry.process` looks up the handler for the forged topic and invokes it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop`/`topic` values, causing the app to act as though this event legitimately originated from `victim.myshopify.com` [4](#0-3) .
