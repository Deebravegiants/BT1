### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing shop attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator.validate` authenticates the body bytes but never binds the `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) that `Registry.process` hands to the webhook handler. An attacker who can obtain any single valid `(raw_body, hmac)` pair (e.g. by installing the app on their own store) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`Registry.process` validates the webhook purely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC check computes the signature over `request.to_signable_string`, which is defined as just the raw body: [2](#0-1) 

`request.shop`, which is passed into `WebhookMetadata` and given to the app's handler for tenant-scoped processing, is read straight from an attacker-controlled HTTP header and is never part of the signed material: [3](#0-2) 

`Utils::HmacValidator.validate` only compares the HMAC over `to_signable_string` (the body) against the secret-derived signature — it has no way to know about, let alone validate, the `shop` header: [4](#0-3) 

This is the same root-cause pattern as the referenced report: an identity/attribution field (`shop`) that is *acted on* by the consuming code (handler dispatch keyed by shop) is disjoint from the field set that is actually *covered by the signature* (only the raw body). The equality that should hold — `shop authenticated by HMAC == shop used by handler` — does not, because `shop` is outside the HMAC's scope entirely.

### Impact Explanation
Because the signature only certifies the body bytes, any attacker who has legitimately received one authentic webhook delivery (trivial: install the target app on the attacker's own free/dev myshopify store and wait for/trigger a webhook, e.g. `app/uninstalled` or another topic whose body is fixed or attacker-controlled/predictable) possesses a valid `(body, hmac)` pair for that exact body. The attacker can then POST that identical body and hmac to the app's webhook endpoint while setting `x-shopify-shop-domain` to a victim shop's domain. `HmacValidator.validate` will succeed (it never looks at the shop header), and `Registry.process` will call the handler with `data.shop == "victim-shop.myshopify.com"`. Any host application that uses `data.shop` to select which tenant's records to update/delete/redact (the gem's own docs instruct exactly this pattern) will act on the wrong tenant, i.e. this is a **cross-tenant** confusion driven entirely by an unauthenticated field — data intended for/about the attacker's shop gets attributed to and processed against a different shop.

### Likelihood Explanation
No credentials, access tokens, or `client_secret` knowledge are required. The only prerequisite is that the attacker can obtain one legitimate `(body, hmac)` pair, which any unprivileged internet user can do by installing the target app on a shop they control. Replaying it with a different `shop-domain` header is a single unauthenticated HTTP request to the app's public webhook route.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header value in the HMAC-signable material, or otherwise cryptographically bind the shop attribution to the request (e.g., verify the shop against a value derived from a per-shop secret/session rather than trusting the raw header), so `to_signable_string` cannot be satisfied while the shop is altered. At minimum, document that host applications must independently verify webhook delivery came from a shop that has an active app installation before trusting `data.shop`, and consider failing closed if the shop for the topic can't be corroborated elsewhere.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's real secret).
2. Attacker sends a POST to the app's webhook endpoint with:
   - body: exactly `B`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`, `x-shopify-webhook-id` as needed
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over `B` only and matches `H` — validation passes.
4. `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))` is invoked; any handler logic keyed on `data.shop` now operates as if the event genuinely originated from the victim shop.
