I found strong analog candidates. Let me verify the price-fetch path that turns a stale leg into a liquidation revert.### Title
Borrower can plant a dust supply leg in an asset with a stale oracle feed, disabling liquidation, bad-debt cleanup, and withdrawals on their own account - (File: contracts/controller/src/risk/totals.rs)

### Summary

`calculate_account_risk_totals` fetches a fresh price for **every** supply and borrow asset in the account (`cache.load_markets(portfolio_hub_keys(...))` then `cache.cached_price`), and a stale feed fails closed with `PriceFeedStale`. However, `supply` accepts a **new** dust position in an asset whose feed is already stale, because no price of that asset is needed to admit it. A borrower can therefore add a sub-unit "poison" leg in an asset whose oracle is currently stale, after which `liquidate`, `clean_bad_debt`, `withdraw`, and `update_account_threshold(has_risks=true)` all revert for that account — mirroring the Arcadia pattern where an account owner's own action flips the account into a fail-closed state that stalls liquidation.

### Finding Description

In Arcadia, switching to a creditor with a shorter grace period made `_isSequencerDown` return true, reverting all Registry valuation functions and hence liquidations. In XOXNO Lending the equivalent "per-position freshness budget" is `oracle.max_price_stale_seconds` in the price aggregator, enforced in `is_stale` and propagated as `OracleError::PriceFeedStale` through `engine::resolve`/`force`.

The risk engine iterates every leg:

- `calculate_account_risk_totals_body` calls `cache.load_markets(&portfolio_hub_keys(supply_positions.keys(), &borrow_positions.keys()))` and then `cache.cached_price(&hub_asset.asset)` per supply leg (`contracts/controller/src/risk/totals.rs:163-173`). Missing or stale cached prices fail closed.
- `account_price_assets` (`totals.rs:22-38`) likewise enumerates all supply and borrow keys, so any path that prices the account pulls in the poisoned leg.

The entry point that plants the leg is `supply` → `process_supply` → `process_deposit` (`contracts/controller/src/positions/supply.rs:40-136`). For a *new* supply leg:

- `validate_position_entry_gates` does not need the new asset's price to admit it; `merge_supply_leg` calls `refresh_supply_risk_params`, but the `FullTuple` gate `apply_gated_liquidation_params` only computes HF (which would read all prices) when the new tuple `favors_liquidator` (`contracts/controller/src/risk/params.rs:68-99`). A fresh position stamped with the listing's own config does not favor the liquidator, so no price of the stale asset is read at supply time.

This is exactly what the existing harness tests demonstrate:

- `audit_supply_setup_blocks_liquidation_via_stale_dust_leg` (`tests/test-harness/tests/controller/audit_supply_stale_shield.rs`): supplying `0.001` WBTC with a feed 3,600 s stale succeeds; afterward `liquidate`, `clean_bad_debt`, and even the owner's own `withdraw` of the dust leg all revert with `PRICE_FEED_STALE`.
- `audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg` (`tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs`): same bricking against `clean_bad_debt` on an underwater account.

Attack flow (single unprivileged address):

1. Observe an asset listed in the borrower's spoke whose feed is stale (e.g., a low-cadence NAV/RWA feed past `max_price_stale_seconds`, or one that simply stops updating).
2. Call `supply(caller=borrower, account_id, spoke_id, [(hub_asset, dust_amount)])` — succeeds despite the stale feed.
3. The account is now unliquidatable and uncleanable while the feed stays stale: `liquidate` reverts in `calculate_account_risk_totals` before the HF check; `clean_bad_debt` reverts identically; the owner cannot even withdraw the leg to self-heal (`withdraw` runs `enforce_post_pool_solvency` which reads all prices).
4. If the market later drops the account below HF 1 while the feed is still dead, liquidation stalls — the borrower hopes for recovery, exactly the Arcadia motive.

### Impact Explanation

Temporary freezing of funds / temporary DoS of liquidation and bad-debt cleanup on the attacker's account. While the stale leg persists, liquidators cannot de-risk the position and `clean_bad_debt` cannot write it down, increasing the chance the account accrues bad debt socialized to the hub's suppliers. Unlike a passive staleness outage, here the borrower *opts in* to the fail-closed state at will by planting a dust leg — the same "user-controlled switch into a disabled-features state" class as the Arcadia creditor swap.

### Likelihood Explanation

Medium-low. The attacker must find a listed asset whose feed is stale at plant time (or that goes stale while held). The DoS lasts only until the feed refreshes, and it only shields the attacker's own account. However, planting is cheap (dust amount), requires no privilege, works on any spoke asset the account can supply, and the harness confirms the revert propagates to `liquidate`, `clean_bad_debt`, and `withdraw`.

### Recommendation

- Allow removing/closing a supply leg without repricing the whole account, e.g. a `withdraw`-all of a single leg that skips `enforce_post_pool_solvency` when the account stays debt-covered, or a dedicated "remove dust leg" path gated on zero balance.
- Alternatively, price stale legs conservatively (value = 0) inside `calculate_account_risk_totals` for collateral purposes instead of reverting, so a dead feed lowers HF rather than bricking liquidation — combined with rejecting borrows while any held feed is stale.
- Or reject `supply` of a new leg whose oracle cannot currently price it (probe the feed in `validate_position_entry_gates` for newly created positions), matching Arcadia's recommended "check the new creditor's sequencer is up before switching".

### Proof of Concept

See `tests/test-harness/tests/controller/audit_supply_stale_shield.rs` (`audit_supply_setup_blocks_liquidation_via_stale_dust_leg`) and `tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs`:

```rust
t.set_oracle_single_spot("WBTC");
t.supply(ALICE, "USDC", 10_000.0);
t.borrow(ALICE, "ETH", 3.0);

// WBTC feed is 3,600 s stale at plant time
t.mock_reflector_client()
    .set_price_at(&wbtc, &usd(60_000), &(now - 3_600));

// Supplying the poisoned dust leg SUCCEEDS
let plant = t.try_supply(ALICE, "WBTC", 0.001);
assert!(plant.is_ok());

// Crash USDC so the account is underwater
t.set_price("USDC", usd_cents(50));

// All of these revert with PRICE_FEED_STALE while WBTC stays stale
test_harness::assert_contract_error(
    t.try_liquidate(LIQUIDATOR, ALICE, "ETH", 1.0), errors::PRICE_FEED_STALE);
test_harness::assert_contract_error(
    t.try_clean_bad_debt_by_id(alice_id),         errors::PRICE_FEED_STALE);
test_harness::assert_contract_error(
    t.try_withdraw(ALICE, "WBTC", 0.0001),        errors::PRICE_FEED_STALE);
```

Root cause: `calculate_account_risk_totals_body` loads and prices every supply key (`contracts/controller/src/risk/totals.rs:163-173`) and missing/stale prices fail closed, while `process_deposit`/`merge_supply_leg` (`contracts/controller/src/positions/supply.rs:100-136,275-296`) admit a new leg without ever pricing it when the tuple does not favor the liquidator (`contracts/controller/src/risk/params.rs:76-88`).
