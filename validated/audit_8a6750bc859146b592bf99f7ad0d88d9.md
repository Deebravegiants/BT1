### Title
Fee-only `MaxLoadedAccountsDataSizeExceeded` transactions report `min(actual_bytes_loaded, requested_limit)` instead of real bytes loaded, under-charging cost-model accounting for account-load I/O work - ([File: svm/src/account_loader.rs])

### Summary
When a transaction fails during account loading with `TransactionError::MaxLoadedAccountsDataSizeExceeded` and is committed as `ProcessedTransaction::FeesOnly`, the `loaded_accounts_data_size` recorded for cost-model purposes is clamped to `min(actual_accumulated_size, requested_loaded_accounts_data_size_limit)` rather than the real number of bytes the validator actually read from accounts-db before the limit check tripped. An attacker can set a low `set_loaded_accounts_data_size_limit` and reference one or more large accounts so that the limit is exceeded only after a large account has already been fully loaded, causing the leader/replaying validators to perform real I/O/deserialization work that the cost tracker never accounts for.

### Finding Description
`load_transaction_accounts` (`svm/src/account_loader.rs:522-620`) iterates transaction accounts and, for each one, calls `account_loader.load_account(...)`/`load_transaction_account` to actually read the account from accounts-db, then calls `loaded_tx_data_size.increase_calculated_data_size(loaded_size, ...)` (`svm/src/account_loader.rs:549`). This function (`svm/src/account_loader.rs:488-511`) adds the just-loaded account's size to a running total and only *after* the add checks `if self.loaded_accounts_data_size > self.requested_loaded_accounts_data_size_limit` to return `Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)`. Because the check happens after the account is already fully loaded, the accumulated `loaded_accounts_data_size` at the moment of failure reflects the true bytes read and can exceed the limit by up to the size of the single account that tripped it.

When `load_transaction` (`svm/src/account_loader.rs:423-472`) turns this error into `TransactionLoadResult::FeesOnly(FeesOnlyTransaction { ... })`, it sets `loaded_accounts_data_size: loaded_transaction_data_size.into()` (feature-gated by `define_ltds_fee_only_semantics`). The `Into<u32>` conversion (`svm/src/account_loader.rs:514-520`) is:
```rust
impl From<LoadedTransactionDataSize> for u32 {
    fn from(value: LoadedTransactionDataSize) -> Self {
        value.loaded_accounts_data_size.min(value.requested_loaded_accounts_data_size_limit)
    }
}
```
This clamps the reported value down to the attacker's own requested (and thus attacker-controlled) limit, discarding the true amount of data that was actually loaded.

This clamped value is exactly what downstream cost accounting consumes: `Bank::create_commit_results` (`runtime/src/bank.rs:4451-4526`) stores it in `TransactionLoadedAccountsStats.loaded_accounts_data_size`, and `runtime/src/transaction_execution.rs:171-195` (`get_transaction_costs`) feeds `committed_tx.loaded_account_stats.loaded_accounts_data_size` into `CostModel::calculate_cost_for_executed_transaction`, whose result is then checked against block/account limits in `cost_tracker.try_add()` (`cost-model/src/cost_tracker.rs:172-238`), including the `WouldExceedAccountDataBlockLimit` check on `allocated_accounts_data_size`.

The repository's own test `fee_only_loaded_transaction_data_size` (`svm/tests/integration_test.rs:3624-3769`) confirms this exact behavior: with `define_ltds_fee_only_semantics` enabled, `fail_limit_loaded_size` is asserted to equal `size_limit` (the attacker-chosen limit) rather than the real accumulated size of the accounts referenced, even though those accounts were already loaded from state before the limit check fired.

Because fee calculation (`fee_details`) for the failed transaction is computed from the *requested* limit during pre-execution validation, not from actual bytes read, the fee paid tracks the declared limit — but the *cost-model accounting* used for block-level resource limiting also only tracks the declared limit, not the real I/O work performed. An attacker can therefore force real account-loading I/O (up to the max permitted account size, ~10 MiB, per offending account) while the block cost tracker "sees" only the tiny declared limit.

### Impact Explanation
This is a materially underpriced-execution / cost-model-bypass bug: the leader (and every validator replaying the block deterministically re-derives the same clamped value, so there is no consensus divergence) performs real disk/cache I/O and deserialization work to load large accounts, but the cost tracker's `allocated_accounts_data_size` and block-cost accounting undercount that work by up to the size of one attacker-chosen large account per transaction. Repeating this across many fee-only transactions in rapid succession lets an attacker force more real account-loading work onto the leader than the cost model permits within the block's declared data-size and cost budget, an underpriced-work / resource-exhaustion condition consistent with Agave's availability/DoS bounty category. It does not create value, double-spend, or cause cross-node state divergence, since the computation is deterministic and reproduced identically by every replaying node.

### Likelihood Explanation
Highly feasible and fully reachable by an unprivileged attacker: they need only submit an ordinary signed transaction containing a `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` instruction with a small value and account references to one or more large, pre-existing accounts (any account they can read, no special permission needed), followed by any instruction referencing a program (to guarantee a load failure and hence the fee-only path, or simply relying on hitting the limit itself which already returns `MaxLoadedAccountsDataSizeExceeded`). This can be repeated arbitrarily by broadcasting many such transactions to the public TPU, each independently costing the attacker only the base signature fee while causing the leader to load large account data uncredited to the cost tracker.

### Recommendation
Track and report the true accumulated `loaded_accounts_data_size` at the point of failure (i.e., remove the `.min(requested_loaded_accounts_data_size_limit)` clamp in `impl From<LoadedTransactionDataSize> for u32`, or add a separate uncapped field used specifically for cost-tracker/cost-model accounting) so that fee-only transactions that exceed the loaded-accounts-data-size limit are charged/cost-tracked based on the real bytes loaded rather than the attacker's declared limit. Alternatively, perform the size check before loading each account's full data (e.g., using account metadata size lookups) so no account is ever fully loaded past the requested limit.

### Proof of Concept
Extend the existing test `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` (around line 3624) with an additional assertion using account-loader instrumentation (or a mock `TransactionProcessingCallback` that records real bytes read per `load_account` call):

```rust
#[test_case(true; "simd186_fee_only")]
fn fee_only_loaded_transaction_data_size_underaccounted(define_ltds_fee_only_semantics: bool) {
    // ... reuse setup from fee_only_loaded_transaction_data_size, but:
    // 1. Instrument TestCallbacks::load_account to accumulate `real_bytes_loaded`.
    // 2. Build a transaction referencing ONE large account (e.g. 8192 bytes)
    //    with set_loaded_accounts_data_size_limit set to loaded_fee_payer_size + 1
    //    (i.e., smaller than the large account, guaranteeing the limit trips
    //    only after the large account is fully loaded).
    // 3. Execute and read reported loaded_accounts_data_size from the FeesOnly result.
    //
    // Expected (bug): reported loaded_accounts_data_size == the tiny requested limit,
    // while real_bytes_loaded (instrumented) >= loaded_fee_payer_size + 8192 + TRANSACTION_ACCOUNT_BASE_SIZE.
    assert!(real_bytes_loaded > reported_loaded_accounts_data_size);
}
```
This demonstrates that `real_bytes_loaded` (actual I/O/account-loader work) materially exceeds the `loaded_accounts_data_size` value fed into `CostModel::calculate_cost_for_executed_transaction` and `cost_tracker.try_add`, confirming the cost-model under-accounting.
