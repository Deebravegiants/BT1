## Title
Webhook `shop-domain` (and topic/webhook-id/api-version) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `Registry.process` trusts the unauthenticated `shop-domain` header to identify which merchant a webhook belongs to. Because a single app-wide `api_secret_key` is used to sign every webhook for every shop that installs the app, any shop that legitimately receives a genuinely-signed webhook can replay the identical `(body, hmac)` pair to the same endpoint while substituting a different `shop-domain` header, and the signature will still validate. This breaks the binding `hmac-authenticated origin == shop header`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no cryptographic linkage to the signed body: [2](#0-1) 

`HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e., the body) against the shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC, then blindly forwards the unauthenticated `request.shop` value to the app's handler as the tenant identity for this webhook: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret (not per-shop), any merchant who installs the app is a valid holder of `(body, hmac)` pairs that are indistinguishable, from the gem's perspective, from ones destined for any other merchant. An attacker who installs the app on their own store (an ordinary, unprivileged action available to any internet user via the Shopify app install flow) receives real webhooks with a valid HMAC for their own shop. They can then POST that exact same body + HMAC to the app's webhook endpoint again, this time with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` hands the handler `shop: "victim-shop.myshopify.com"` alongside attacker-controlled body content.

### Impact Explanation
This breaks the multi-tenant isolation the gem is expected to provide to host applications: `shop-domain` is the field host apps rely on to select the correct per-shop session/data before acting on the (verified-looking) payload. An attacker can inject spoofed data (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request` payloads) attributed to any other shop that uses the same app installation, without ever needing the app's `api_secret_key`. Depending on how the host app consumes `WebhookMetadata#shop`, this enables cross-tenant data corruption/injection — a Critical-class cross-tenant access issue.

### Likelihood Explanation
Exploitation only requires installing the target Shopify app on an attacker-controlled development/test store (a normal, unauthenticated action any internet user can take against a public app), capturing one legitimate webhook delivery, and replaying it against the same public webhook endpoint with a different `shop-domain` header. No access to `api_secret_key`, access tokens, or the victim shop is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or independently verify that the `shop-domain` header corresponds to a shop actually known/installed for this app before trusting it, e.g. by cross-checking against the app's own session/shop store, and reject webhooks whose header-derived shop cannot be corroborated. At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are NOT authenticated by the HMAC and must not be used as a sole tenant-selection key by host applications.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal app install, no secret/tokens needed).
2. Shopify sends a real webhook, e.g. `orders/create`, to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical request to the same endpoint, only changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-chosen body `B`, even though this data never originated from that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
