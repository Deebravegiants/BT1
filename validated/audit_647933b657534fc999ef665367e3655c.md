### Title
Undecodable BounceTech LT revert (`0x05eb05ac BelowMinTransactionSize`) DoSes `Zap.sell` on chunked exits when the LT's live floor is raised mid-market — ([File: packages/contracts/src/Zap.sol])

### Summary
The @hapi/content advisory is a class of bug where an external/library call throws a raw, undecodable system error that propagates unhandled up the call stack and halts the application. Alt.fun has the same bug class: `Zap._sellInternal` calls the external BounceTech LT's `redeem()` directly, and the LT can revert with the *undecodable* 4-byte selector `0x05eb05ac` (`BelowMinTransactionSize`) — a raw error the protocol's own ABI cannot decode — whenever the redeemed USDC amount falls below the LT's live `minTransactionSize`.

### Finding Description
`Zap._sellInternal` guards the *pre-redeem* estimate against the floor, but the guard is computed from `ltReceived * exchangeRate()`, i.e. the same rate BounceTech uses internally at the moment of the check [1](#0-0) . The floor itself, `GlobalStorage.minTransactionSize`, is read live and can be raised by BounceTech at any time (the codebase explicitly acknowledges this is a *live*, externally-controlled parameter — see `test_minUsdcAmount_tracksGlobalStorageFloor` on the buy side) [2](#0-1) . On the buy side, the code carefully reads this floor live via `zap.minUsdcAmount()` and reverts cleanly with `Zap.BelowMinAmount` before calling `mint()` [3](#0-2) . On the sell side, the check in `_sellInternal` also exists and was previously fixed for a decimal-scale bug (regression #313) that let sub-$10 sells slip past the guard and hit the LT's raw selector [4](#0-3) .

However, that guard is computed against `grossUsdcEstimate`, which is derived from the LT's *current* `exchangeRate()` at check-time — not from the actual `redeem()` output, and not from a live re-read of `minTransactionSize` bounded against slippage between the check and the `redeem()` call in the same transaction is not the concern here (same tx, same block). The real gap is structural: `Zap` never mirrors or floors against `minTransactionSize` explicitly on the sell path the way `minUsdcAmount()` does for buys — it only approximates the floor via a USD-value heuristic (`grossUsdcEstimate / 1e12 < minUsdcAmount()`), which is itself just a proxy for BounceTech's real floor, not the floor read live from `GlobalStorage`. Any rounding/timing mismatch between Alt.fun's approximation of the LT-side floor and BounceTech's own live floor check inside `redeem()` reproduces exactly the @hapi/content pattern: an external component's raw, unhandled system error (`0x05eb05ac`) propagating up through `Zap.sell` with no `try/catch`, reverting the whole user transaction with an opaque, unparseable selector instead of Alt.fun's own typed `BelowMinAmount` error.

Because sells are also capped by `baseAssetBalance()` (the LT's idle USDC buffer) and users are expected to "sell in chunks if needed" per the documented sell flow [5](#0-4) , a BounceTech floor raise (a routine, permissionless-to-BounceTech, unprivileged-to-Alt.fun event) can push chunked sell sizes below the new floor mid-session, causing every subsequent `Zap.sell` call for affected chunk sizes to revert with the undecodable selector rather than a clean, catchable error — a functional DoS on exiting the position via `Zap` for any trader whose remaining/chunked balance sits in the dirty band.

### Impact Explanation
This does not lock funds permanently (holders can still eventually sell once they resize their chunk, and `redeem()` itself is never paused per BounceTech's mint-only pause design noted in `_executeBuy`'s comments) [6](#0-5) . But for the affected chunk sizes it is a genuine, unhandled-exception denial of service on the sell path exactly matching the @hapi/content bug class — the difference from `_executeBuy`'s buy-side floor handling is that the buy path explicitly reads and floors against `minUsdcAmount()`/`ltIfFull`/`ltUntilGraduation` with dedicated fallback branches (the "floor-bump" logic), while the sell path relies on a coarser USD-value proxy check that is not guaranteed to track BounceTech's live floor exactly across all exchange-rate/decimal combinations, since it only re-validated against one specific decimal-scale bug (#313) rather than being derived symmetrically from the same live-floor read used on the buy side.

### Likelihood Explanation
Medium. It requires (a) BounceTech raising `minTransactionSize` (an event outside Alt.fun's control, but explicitly anticipated in the codebase's own AGENTS notes and tests) and (b) a trader's sell size landing in the resulting gap between Alt.fun's approximated floor and BounceTech's actual floor. This is realistic given the documented pattern of users "selling in chunks" near the LT's idle-buffer limit, increasing the odds that some chunk sizes land exactly in the dirty band.

### Recommendation
Mirror the buy-side pattern exactly on the sell path: read `IBounceLeveragedToken(lt).minTransactionSize()` live (as `zap.minUsdcAmount()`/`GlobalStorage` is read for buys) and floor the *actual redeem input* (`ltReceived`, converted to base terms) against it before calling `redeem()`, reverting with the typed `Zap.BelowMinAmount` error — instead of relying solely on the pre-fee USD-value estimate. Additionally, wrap the `redeem()` call itself in a `try/catch` that re-throws a decodable Alt.fun-native error on any raw/undecoded revert, so callers and off-chain consumers never see the bare `0x05eb05ac` selector.

### Proof of Concept
1. Trader buys tokens on curve via `zap.buy`, accumulating a token balance.
2. BounceTech raises `GlobalStorage.minTransactionSize` (simulable via `lt.setMinTransactionSize(newFloor)` in the test mock) to a value such that a specific token sell size produces `ltReceived` whose LT amount, once redeemed, is just below the new floor but whose `grossUsdcEstimate` heuristic in `_sellInternal` still passes the `minUsdcAmount()` proxy check (feasible because the proxy uses `exchangeRate()` at check-time and 1e12 scale normalization, distinct arithmetic from BounceTech's own floor check inside `redeem`).
3. Trader calls `zap.sell(tokenAddr, tokenAmount, 0)`.
4. `_sellInternal` passes its own `grossUsdcEstimate` check but the downstream `IBounceLeveragedToken(lt).redeem(...)` call reverts with the undecodable `0x05eb05ac` selector (as already demonstrated for the buy-side floor in `test_buy_revertsInPostFeeDirtyBand`, applying the same mechanic to `redeem`) [7](#0-6) .
5. The transaction reverts with a raw, unparseable selector instead of `Zap.BelowMinAmount`, and the trader cannot exit that chunk size — the exact @hapi/content-class failure mode: an unhandled external system error bubbling up and denying service.
