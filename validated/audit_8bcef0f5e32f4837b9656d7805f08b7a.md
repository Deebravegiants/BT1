### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC over the raw JSON body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are read straight from HTTP headers and never included in the signed bytes — are handed to the app's handler as trusted identity data (`WebhookMetadata#shop`, `#topic`).

### Finding Description
The HMAC validation in `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` [6](#0-5) . For a webhook `Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) . Because Shopify signs webhooks by HMAC-ing the raw body with the app's shared `client_secret`, that same HMAC value is valid for *any* shop or topic that happens to send an identical body — the signature is completely independent of the `shop`, `topic`, or `webhook-id` headers.

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — before dispatching to the handler with `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` taken directly from headers [1](#0-0) . These fields are never re-derived from or cross-checked against the signed payload.

The identity binding that should hold is:
```
shop authenticated by HMAC == shop delivered to the handler
```
but the gem only guarantees:
```
body authenticated by HMAC == body delivered to the handler
```
`shop`, `topic`, and `webhook_id` are fields acted on (used to route/attribute the event) but not covered by the HMAC — exactly the identity-binding gap described in the bug-class hint.

### Impact Explanation
An attacker who controls (or has previously received, e.g. as their own trial/dev store) one genuine Shopify webhook delivery for a given app — body + valid `X-Shopify-Hmac-Sha256` — can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`). `Registry.process` will accept it as valid (the HMAC check passes because only the body matters) and invoke the registered handler with `WebhookMetadata.shop` set to the attacker-chosen shop. Any host application that trusts `data.shop` to select which merchant's data to update, delete, or act upon (a normal and expected usage pattern, e.g. `customers/redact`, `shop/redact`, order-update handlers) will perform that action against the wrong (attacker-chosen) tenant — a cross-tenant action forged by an unprivileged internet user, without ever needing the app's `client_secret` or any merchant credential.

### Likelihood Explanation
Any endpoint that exposes `ShopifyAPI::Webhooks::Registry.process` publicly (as documented and shown in `docs/usage/webhooks.md`) is reachable by an unauthenticated internet user. Obtaining one valid signed body is trivial (install the app on any store, even the attacker's own, or observe/capture one legitimate delivery), and replaying it with a modified header requires no special access, timing, or bypass beyond a normal HTTP POST.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material verified by the gem (or, since Shopify's actual signature only covers the body, have `Registry.process` require the caller to independently confirm that the resolved `shop` corresponds to a session/store the app actually expects for that specific delivery — e.g. compare against a `webhook_id`-keyed record of registrations, or document explicitly that host apps MUST NOT trust `WebhookMetadata.shop`/`topic` without independent verification). At minimum, `HmacValidator`/`Request#to_signable_string` should not be a static claim of security when in fact only the body is authenticated — expose a documented way to bind headers to the verified payload.

### Proof of Concept
```ruby
# 1. Attacker captures one legitimate webhook delivery to their own store's endpoint:
#    raw_body = '{"id":123,"note":"hi"}'
#    valid_hmac = Base64 of HMAC-SHA256(app_client_secret, raw_body)   # attacker doesn't need the secret,
#                                                                       # Shopify computed and sent it
#
# 2. Attacker replays the SAME body+hmac to the app's public webhook endpoint,
#    but swaps the shop-domain header to a victim shop that also installed the app:
headers = {
  "x-shopify-topic"       => "customers/redact",   # or any topic they captured a body for
  "x-shopify-hmac-sha256" => valid_hmac,            # unchanged, still verifies against raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled
  "x-shopify-webhook-id"  => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (only raw_body is verified, see request.rb#to_signable_string)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/redact", ...))
# The host app's handler now performs an action attributed to "victim-shop.myshopify.com"
# even though that shop never sent this webhook.
```
