### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `HmacValidator.validate` in `Registry.process` covers the body but not the `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers, yet `Registry.process` trusts `request.shop` and forwards it unverified to the app's webhook handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all derived purely from HTTP headers that are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which only checks the HMAC over `to_signable_string` (i.e., the body): [3](#0-2) 
and `HmacValidator` computes/compares the signature purely against `to_signable_string`: [4](#0-3) 

After a successful HMAC check, `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata`, which app handlers use as the tenant identifier: [5](#0-4) [6](#0-5) 

Critically, Shopify webhooks are signed with the app's single `client_secret`/`api_secret_key`, which is shared across **every shop** that installs the app — it is not a per-shop secret. This means a valid `(raw_body, hmac)` pair generated from an event on the attacker's own (unprivileged) shop is a valid signature for the *same body* regardless of which `shop-domain` header accompanies it, because the header is never part of the signed content.

The binding that is broken as an equality:
`shop-domain header used by the app (request.shop passed to WebhookMetadata) != shop bound inside the HMAC-covered bytes (to_signable_string, which contains only the body)`

The gem's own documentation asserts a guarantee that is not actually met: "This will verify the request did indeed come from Shopify" — but it only proves the body wasn't tampered with; it proves nothing about which shop the body is attributed to.

### Impact Explanation
An attacker who has installed the target app on their own (unprivileged) shop can trigger a webhook event in their own shop, capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair that Shopify sends (which is valid because it's signed with the app-wide `client_secret`), then directly POST that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain`/`x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will pass (body/HMAC match), and `Registry.process` will invoke the handler with `shop: <victim-shop>`, causing the app to process attacker-controlled webhook data as if it originated from the victim tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up the victim's session/store data and write/update records), this results in cross-tenant data injection/corruption attributed to a shop the attacker does not own — a tenant-isolation break reachable by any unprivileged user who can install the app on their own store.

### Likelihood Explanation
High likelihood for any multi-tenant deployment: no secrets are required beyond what any installing merchant already legitimately receives (their own valid webhook deliveries), and the webhook endpoint is by design internet-reachable. The only extra step is crafting a raw HTTP POST with a different `shop-domain` header, which requires no special privilege.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) header values into the HMAC-signable content, or otherwise verify that the shop asserted in the webhook headers has an active registration/session correlated independently of the header itself, before trusting `request.shop` in `Registry.process`. At minimum, update `Request#to_signable_string` to incorporate the shop domain so a captured body/HMAC pair cannot be replayed under a different tenant's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers `orders/create` in their shop, causing Shopify to send a webhook to the app's public endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `client_secret` (shared across all installs).
3. Attacker intercepts/replicates this `(raw_body, hmac)` pair (e.g., via their own server logs, a proxy, or by simply reusing values they can generate/observe from their own installation).
4. Attacker sends a new POST directly to the app's webhook route with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [3](#0-2) 
6. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and processes it as legitimate data for the victim tenant.
