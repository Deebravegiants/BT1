### Title
POA Bridge `describeWithdrawal` Matches Withdrawals by `assetId` Instead of Index, Causing Wrong Destination-Hash Reporting for Batched Same-Asset Withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` deliberately ignores the `index` of the withdrawal it is asked to describe and instead resolves the withdrawal purely by matching `assetId` against the (unsorted) list returned by the POA indexer. When a caller batches multiple withdrawals of the same asset in a single NEAR intents transaction, each `describeWithdrawal(index=i)` call resolves to the same ambiguous match, so a completion status/destination tx hash belonging to one withdrawal in the batch can be reported for a different withdrawal in the same batch.

### Finding Description
`describeWithdrawal` is documented as matching by `assetId` "because the response list is unsorted": [1](#0-0) 

`findMatchingWithdrawal` is used to pick the withdrawal item purely from `args.withdrawalParams.assetId`, with no correlation to `args.index`, `args.withdrawalParams.amount`, or `args.withdrawalParams.destinationAddress`: [2](#0-1) 

This is also confirmed by the test suite, which explicitly notes matching is done "by near_token_id, not defuse_asset_identifier" and by assetId, with no index/amount disambiguation exercised for the multi-withdrawal-of-same-asset case: [3](#0-2) 

The withdrawal watcher relies on `describeWithdrawal`'s `{status, txHash}` result as the on-chain source of truth per withdrawal index, without any additional cross-check: [4](#0-3) 

When a single NEAR transaction contains two or more withdrawal intents for the *same* `assetId` (e.g., a batch withdrawal splitting one payout into multiple destination addresses of the same token, or paying two recipients the same token), `findMatchingWithdrawal(response.withdrawals, assetId)` cannot distinguish between them by index. The equality that should hold — "the status/txHash reported for withdrawal index `i` equals the actual on-chain outcome of withdrawal index `i`" — can break: `describeWithdrawal({index: 0, assetId: X})` and `describeWithdrawal({index: 1, assetId: X})` can both resolve to the same underlying POA record (or the wrong one), yielding an incorrect `transfer_tx_hash` being attributed to the wrong logical withdrawal.

### Impact Explanation
This maps to "a status or hash misreport making an integrator credit or refund twice" (High). An integrator/consumer of `IntentsSDK.waitForWithdrawalCompletion` (which iterates per-index withdrawal identifiers) could mark withdrawal #1 "completed" using the destination tx hash that actually corresponds to withdrawal #0 (or vice versa), causing double-crediting of one leg and no confirmation (or a wrong confirmation) for the other — with no way for the caller to detect the mismatch because both share the same `assetId`.

### Likelihood Explanation
Likelihood is moderate: it requires the caller to withdraw the *same asset* more than once in a single intents transaction via the POA route (a legitimate, unprivileged usage pattern already supported by the SDK's batch/index-based withdrawal APIs), not any malicious or privileged action. Given the SDK explicitly supports multiple `withdrawalParams` per intent and tracks them by `index`, this is a realistic call pattern for any integrator that programmatically batches withdrawals.

### Recommendation
Change `findMatchingWithdrawal` in `poa-bridge.ts` to disambiguate not only by `assetId` but also by additional withdrawal-specific fields available in the response (e.g., `amount`, `address`/`destinationAddress`, and ideally the withdrawal's `index`/order among same-asset entries in the response, mirroring how `omni-bridge.ts` uses the `index` positionally). If the POA indexer cannot guarantee positional stability, at minimum consume `amount` and `destinationAddress` as part of the match key so that two same-asset withdrawals in one batch cannot be conflated.

### Proof of Concept
1. Submit one NEAR intents transaction containing two `withdraw` intents for the same `assetId` (e.g., `nep141:usdc.token.near`) to two different destination addresses (index 0 and index 1).
2. Call `PoaBridge.describeWithdrawal({ ..., index: 0, withdrawalParams: { assetId: "nep141:usdc.token.near", ... } })` and `describeWithdrawal({ ..., index: 1, withdrawalParams: { assetId: "nep141:usdc.token.near", ... } })`.
3. Because `findMatchingWithdrawal` (per `poa-bridge.ts` lines 318-322) selects strictly by `assetId` from an "unsorted" list with no positional/amount/address correlation, both calls can resolve to the same POA record, or the wrong one, returning the completed status and `transfer_tx_hash` of the wrong logical withdrawal to at least one of the two indices.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
