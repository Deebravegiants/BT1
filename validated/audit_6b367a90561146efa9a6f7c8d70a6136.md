## Title
Webhook shop/topic/webhook-id are trusted for tenant attribution but are not covered by the HMAC signature, allowing cross-tenant webhook forgery — (`lib/shopify_api/webhooks/request.rb`)

### Summary
The Cap Protocol report describes a broken binding: funds are moved based on one piece of state (a Delegation transfer) while a later authorization check (`coverage(_agent) == 0`) is evaluated against a *different, unrelated* state, letting an unauthorized party redirect value meant for one entity to another. The structural analog in this gem is in `ShopifyAPI::Webhooks::Request`: the HMAC signature only binds the *body* of a webhook request, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to attribute and act on the webhook are taken from unauthenticated headers and are never covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which — per `HmacValidator.validate_signature` — only compares the received HMAC against a signature computed over `to_signable_string` (i.e., the body): [3](#0-2) 

Once that body-only check passes, `Registry.process` immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` handed to the app's business logic, with no further check that the shop header is consistent with the signed payload's origin: [4](#0-3) 

The broken identity binding, stated as an equality that the code fails to enforce:
`shop_header_used_for_tenant_attribution == shop_that_actually_produced_the_signed_body`

Because only the body is signed, an attacker who has legitimate, unprivileged access to their own shop's webhook stream (any merchant installing the app receives real webhooks signed with the app's shared `client_secret`) can capture a genuine `(body, hmac-sha256)` pair, then replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body against the signature, and `Registry.process` will hand the forged shop identity straight to the host app's handler.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: the host application's webhook handler is invoked believing the event genuinely originated from shop B, when it was in fact forged by an unprivileged user of shop A. Depending on what the host app does in its handler (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`), this enables cross-tenant data injection or state mutation attributed to a shop the attacker does not control — a cross-tenant access issue.

### Likelihood Explanation
Any merchant who installs the app can trivially obtain real, validly-signed webhook bodies for topics they control (e.g., by creating a product/order in their own store to trigger a webhook, or intercepting their own traffic to the public endpoint). No access to `api_secret_key`, access tokens, or the app owner's credentials is required — only the ability to send an HTTP POST to the app's public webhook URL with modified headers, which is inherent to how webhook endpoints must remain publicly reachable.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the signed body), or require the host application to independently verify that the shop domain in the webhook headers matches a shop for which the app currently holds a valid, previously-issued access token/session before acting on the payload.

### Proof of Concept
1. Attacker installs the app on their own shop, `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. creates a product) and captures the resulting `POST` — raw body `B`, and header `X-Shopify-Hmac-Sha256: H` (validly signed with the app's shared `client_secret`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker sends a new request to the same public webhook endpoint using the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the signature over `B` only, which still matches `H`, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the payload never originated from that shop.
