This confirms the finding: the gem's own documentation explicitly tells host apps to trust `data.shop` as the authenticated tenant identifier (`docs/usage/webhooks.md` lines 12-14, 25-26), and `ShopifyAPI::Webhooks::Registry.process` documentation states it will "verify the request did indeed come from Shopify" (line 125) — but the verification only covers the raw body, not the shop identity.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `Request#shop` is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body alone and then forwards `request.shop` into `WebhookMetadata` for the host app's handler, breaking the intended binding: `HMAC-authenticated bytes == shop identity trusted by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed from the `shop-domain` header with no cryptographic binding to the body or HMAC: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string`, i.e. only the body for webhook requests: [3](#0-2) 

`Registry.process` validates this body-only HMAC, then passes the unauthenticated `request.shop` straight to the handler as tenant identity: [4](#0-3) 

The gem's documentation instructs host apps to trust `data.shop` as "The shop domain of the webhook" and to key subsequent business logic (e.g. job enqueueing) on it: [5](#0-4) [6](#0-5) 

and states that `Registry.process` "will verify the request did indeed come from Shopify": [7](#0-6) 

That verification claim is false for the `shop` field: any attacker holding a genuine `(body, hmac)` pair for one shop — trivially obtainable by installing the public app on their own store and capturing their own webhook deliveries — can replay the exact same body and HMAC to the victim app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because the signature never covered the shop header, so `Registry.process` calls the handler with `WebhookMetadata(shop: <attacker-chosen shop>, body: <attacker's own shop data>)`.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts to the integrating app (via documentation and API contract) that `data.shop` is the Shopify-authenticated origin of the webhook, but that field carries no cryptographic guarantee. A host application that (as documented) uses `data.shop` to select which tenant's records to update/enqueue work for can be made to apply attacker-supplied webhook content under an arbitrary victim shop's identity — i.e., cross-tenant access/data corruption within the app, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on a shop they control (the normal, unprivileged installation flow for a public Shopify app) can capture a legitimate `(body, x-shopify-hmac-sha256)` pair from their own store's webhook deliveries and replay it directly to the victim app's public webhook endpoint with a forged `x-shopify-shop-domain` header — no access token, `client_secret`, TLS interception, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload that `to_signable_string` protects, or otherwise cryptographically bind `request.shop` to the verified body (e.g., require the handler-visible `shop` to be independently confirmed, such as by verifying it matches a shop with an active, previously-established session/registration) before trusting it as tenant identity in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a genuine webhook to the app's registered endpoint: `POST /callback/orders/create` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(app_secret, B)`, plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` from their own delivery logs/network.
4. Attacker sends `POST /callback/orders/create` to the same public endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true`.
6. `ShopifyAPI::Webhooks::Registry.process` invokes the host handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's own order data>)`, causing the app to act on victim tenant data with attacker-controlled content. [4](#0-3)
