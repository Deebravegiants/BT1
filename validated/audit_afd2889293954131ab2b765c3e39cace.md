### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that raw body. The `shop-domain`, `topic`, and `webhook-id` values, which are used by `Registry.process` to build the `WebhookMetadata` object handed to the app's handler, come from HTTP headers that are never part of the HMAC-signed material.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. `HmacValidator.validate`/`validate_signature` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` accepts a `Request`, validates only the body HMAC, and then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id`, none of which participated in the HMAC computation: [3](#0-2) 
`shop`, `topic`, and `webhook_id` are read straight from the corresponding `x-shopify-*`/`shopify-*` headers with no cryptographic binding to the body: [4](#0-3) 

This breaks the equality that should hold: `shop attributed to processed webhook == shop that produced the signed body`. Because the same `client_secret`/HMAC key is used for every shop installed on a given app, an unprivileged party who can obtain any one genuine `(raw_body, hmac)` pair signed for their own store (e.g., by installing the app on their own trial/development shop and triggering an event) can replay that exact body and HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header value pointing at a victim shop. `HmacValidator.validate` will still succeed because it only checks the untouched body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim's shop domain.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler acts on data it believes originates from shop B while the payload was actually produced (and legitimately signed) for shop A, an unprivileged attacker's own store. For mandatory privacy topics such as `shop/redact` or `customers/redact` (whose bodies are simple, attacker-controllable-content JSON largely independent of which shop is named in the header), or for any handler that keys persistence/authorization decisions off `data.shop` from `WebhookMetadata`, this enables cross-tenant data manipulation using only a validly-signed payload obtained from the attacker's own installation. This matches the "cross-tenant access" criterion.

### Likelihood Explanation
Any developer or trial user who can install the app on a shop they control can generate an arbitrary number of genuinely-signed `(body, hmac)` pairs for chosen topics, then relay them to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `api_secret_key`, or privileged access is required — only the ability to receive one's own app webhooks and forge HTTP headers on a subsequent unauthenticated request to the app's endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in `to_signable_string`'s signed material, or otherwise cryptographically bind the shop attribution to the HMAC (e.g., by validating that the message body/topic is internally consistent with the claimed shop) instead of trusting the header value directly in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a `shop/redact` (or other mandatory) webhook, capturing the raw body and the `x-shopify-hmac-sha256` header Shopify sent — both valid under the app's real `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with the exact same body and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the unmodified HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on victim-shop data/state using attacker-controlled, but validly-signed, content.
