## Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook exclusively by HMAC-validating the raw request body, while the `shop-domain` header — the value used to attribute the payload to a specific merchant/tenant — is read directly from unauthenticated headers and is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight out of HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC solely against `verifiable_query.to_signable_string` (i.e., the raw body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop` (from the unauthenticated header) as the tenant identity handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop value cryptographically bound in signed payload == shop value the handler treats as the tenant`. Here, the left side does not exist — the HMAC only proves "this body was produced with my app's secret," not "this body belongs to shop X." Any entity that possesses one valid `(raw_body, hmac)` pair for their own shop — which they legitimately receive as the owner of any store that installs the app — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still passes because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` into `WebhookMetadata`, which the host application uses to route/attribute the event to a tenant.

### Impact Explanation
This crosses the Critical bar of "cross-tenant access": an unprivileged actor who merely installs the app on their own shop (a normal, unprivileged flow) can generate valid HMAC-signed bodies, then replay them under a spoofed `shop-domain` claiming to be a different, victim merchant. Any downstream logic that keys per-tenant state, session lookup, or business actions off `WebhookMetadata#shop` (as documented for consumers of this gem) can be tricked into attributing attacker-controlled webhook data to another tenant.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the normal case for a public Shopify app): obtaining a valid `(body, hmac)` pair only requires being a legitimate, unprivileged merchant of the app, and forging the header requires nothing more than an HTTP client capable of setting request headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header value to the verified body (e.g., verify that the shop associated with the accepted body via body content matches the header, or require callers to look up/validate the shop against a known, previously-established per-shop secret/session rather than trusting the header value once HMAC on the body succeeds).

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the resulting `raw_body` and `x-shopify-hmac-sha256` header — both valid and correctly signed by the app's real `api_secret_key`.
2. Replay a POST to the app's webhook endpoint using the identical `raw_body` and `hmac` header, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — line [5](#0-4)  — which passes because only the body is checked.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` — line [6](#0-5)  — even though the payload was never produced for that shop, demonstrating the cross-tenant identity spoof.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
