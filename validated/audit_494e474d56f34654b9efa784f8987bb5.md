### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only the HMAC over the raw request body, but derives the trusted `shop` identity from an unauthenticated HTTP header. This breaks the intended binding: `hmac_verifies(bytes) == identity_trusted(bytes)`. In reality, `hmac_verifies(raw_body)` while `identity_trusted(header["shopify-shop-domain"])` — two disjoint byte ranges.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [4](#0-3) , and `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature [5](#0-4) . `HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string` (i.e., the body) [6](#0-5) . `Registry.process` raises only if that body HMAC fails, then immediately forwards `request.shop` — the unauthenticated header — into `WebhookMetadata` passed to the app's handler [7](#0-6) .

Because the app's `api_secret_key` is one shared secret across every shop that installs the app, any shop that can trigger a webhook with attacker-influenced body content (e.g. `orders/create`, `products/update` fields the merchant controls) receives from Shopify a genuine `(raw_body, hmac)` pair signed with that shared secret. Since the HMAC covers only the body and not the `shop` header, that same `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain — `HmacValidator.validate` will still return `true`, and `Registry.process` will invoke the handler with `data.shop` set to the victim's domain.

### Impact Explanation
This is a cross-tenant identity binding failure exactly analogous to the reward-accounting rounding bug's root cause of "the value verified is not the value used": here, the value verified (raw body under HMAC) and the value trusted downstream (shop domain header) are different pieces of data. Any host app that follows this gem's documented pattern (`data.shop` as the tenant key, as shown in the gem's own docs) can be made to attribute attacker-forged webhook payloads to a victim shop — a cross-tenant access/data-integrity violation, without needing the `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Moderate-to-high: any unprivileged internet user who can install the app on a shop they control (common for public apps) can harvest genuine `(body, hmac)` pairs for webhook topics whose body content they influence, then replay them against the app's public webhook endpoint with a forged `shop` header. No secret material or session is required — only network access to the app's webhook route, which by design is public and unauthenticated.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified: either require the app to independently confirm that the claimed `shop` corresponds to a shop with an active, previously-established session/installation for this app before trusting `WebhookMetadata#shop`, or extend `Request#to_signable_string` (and validation) to incorporate the shop-domain header (or otherwise correlate it with a corresponding subscription/session record) so that spoofing the header alone can no longer pass HMAC validation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers for `orders/create`.
2. Attacker creates an order whose fields end up in the webhook body (fully or partially attacker-controlled JSON body).
3. Shopify delivers the webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over that raw body using the app's shared `api_secret_key`, and header `x-shopify-shop-domain: attacker.myshopify.com`.
4. Attacker captures `(raw_body, hmac)` (e.g., via a proxy they control between Shopify and their own server, or by controlling the endpoint themselves) and replays an HTTP POST to the same app webhook route, keeping `raw_body` and `x-shopify-hmac-sha256` identical but changing `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body signature [8](#0-7) .
6. `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"` [9](#0-8) , causing the app to act on attacker-supplied data as if it originated from the victim's shop.
