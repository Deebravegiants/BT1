### Title
`_noFeeSwapInput`'s unguarded `Math.mulDiv` can be forced to overflow-revert by an attacker-seeded HyperSwap pre-seed pair, permanently bricking `finalizeGraduation` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` (phase 2 of the permissionless two-phase graduation) seeds the HyperSwap V2 TOKEN/LT pair via `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`. `_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` where `reserveIn`/`reserveOut` are read live from the HyperSwap pair's stored reserves [1](#0-0) . Because the V2 pair can be pre-created and pre-seeded by anyone before `finalizeGraduation` runs (the whole reason the "hostile-pre-seed defense" exists), `reserveIn`/`reserveOut` are attacker-influenceable up to the `uint112` reserve ceiling. `Math.mulDiv`'s 512-bit intermediate lets the multiplication itself never overflow, but it still reverts if the *final quotient* exceeds `type(uint256).max` [2](#0-1) . The protocol's own natspec on `_noFeeSwapInput` explicitly acknowledges this: "Constructed adversarial inputs that violate this would `revert` rather than silently truncate, which is the correct failure mode" [3](#0-2) . That revert is **not** caught anywhere — `_pairRebalance` and `_seedRebalancing` call it directly with no try/catch [4](#0-3) , and `finalizeGraduation` itself has no fallback path if `_seedUniswapV2Direct` reverts [5](#0-4) .

### Finding Description
The rebalance-regime dispatch in `_seedRebalancing` only skips the swap math (falling to a safe direct mint) when **both** the token side and the LT side of the pre-existing pool are below `DIRECT_MINT_PRESEED_BPS` relative to `(tokensForLP, ltFromPair)` [6](#0-5) . An attacker can pre-seed the pool with one side deliberately large (well above the band) so the rebalance path is taken instead of the safe fallback, while choosing the ratio so that `reserveIn`, `reserveOut` (uint112-bounded pair reserves) combined with the protocol's own `targetN = ltFromPair`, `targetD = tokensForLP` push `reserveIn * reserveOut * targetN / targetD` above `2^256`.

`ltFromPair` and `tokensForLP` are cached at phase-1 time from the curve's own state, and — critically — the USD graduation trigger is denominated in USD via `exchangeRate()`, not in raw LT amount: `(storedAssetReserve − virtualLtReserve) × exchangeRate ≥ $9K` [7](#0-6) . A token whose paired LT has an inflated `exchangeRate()` can graduate with an arbitrarily small real `ltFromPair` (and a correspondingly small `tokensForLP`, since `tokensForLP = ltFromPair × tokenReserve / assetReserve`) [8](#0-7) . A very small `tokensForLP` (the divisor `targetD`) combined with an attacker-chosen large `reserveIn`/`reserveOut` in the pre-seeded HyperSwap pair is exactly the shape that maximizes the discriminant and can drive `Math.mulDiv`'s quotient past `2^256`, causing a Solidity Panic revert inside `_noFeeSwapInput`.

Once that revert fires, every call to `finalizeGraduation(tokenAddress)` for that token reverts unconditionally — there is no retry-with-different-parameters path, no admin override, and no way to re-run phase 1 (the lifecycle is already `Graduating`) [9](#0-8) . The token is permanently stuck in `Lifecycle.Graduating`: all curve-raised LT drained into `Bonding` by `Router.graduate` in phase 1 and the 250M `LP_RESERVE` tokens reserved for LP are frozen forever, and every holder who bought on the curve loses the ability to ever sell (holders can never reach the post-graduation HyperSwap venue, and curve trading is already frozen at phase 1).

This directly contradicts the protocol's own stated invariant that "`_seedUniswapV2Direct` MUST never revert under any pre-seed shape" and that "a hostile pre-seed of any shape cannot DoS `finalizeGraduation`" [10](#0-9) [11](#0-10) . The `_noFeeSwapInput` natspec's overflow-safety comment shows the authors reasoned about V2's `uint112` cap and the *token supply* bound on `targetN`/`targetD`, but did not account for `targetD` being made arbitrarily small by a rate-pumped-LT USD-trigger graduation combined with an attacker-controlled large-reserve V2 pre-seed on the *opposite* side from the band-skip check.

This maps onto the CVE-2018-3145 bug class (a crafted, low-privilege, network-reachable input causing a parser/engine component to crash/hang, denying service) — here the "parser" is the closed-form swap-input math (`_noFeeSwapInput`), the "network input" is a permissionlessly pre-seeded HyperSwap pool ratio plus the graduation's own reserve state, and the "crash" is an unrecoverable EVM Panic that bricks a state machine with no escape hatch.

### Impact Explanation
Permanent freezing of funds: all real LT raised by the curve for the affected token (moved into `Bonding` via `Router.graduate` at phase 1) and the 250M-token `LP_RESERVE` become permanently unreachable, since `finalizeGraduation` can never complete and there is no alternate exit function once `Lifecycle.Graduating` is set. Every trader holding the token is also permanently locked out of exit liquidity (curve trading is frozen; the graduated pool never opens). This satisfies "concrete... permanent freezing of trader, creator or LP funds."

### Likelihood Explanation
Reachable entirely by unprivileged addresses using only in-scope entry points: `factory.createPair(token, lt)` is permissionless on HyperSwap, and anyone can `transfer` TOKEN/LT to the pair and call `pair.mint(attacker)` to set an arbitrary reserve ratio before `finalizeGraduation` runs — this is precisely the "hostile pre-seed" attack surface the protocol already defends against for other regimes. Constructing the specific numeric shape that pushes `Math.mulDiv`'s quotient past `2^256` requires the attacker to control real V2-pair reserves at a scale on the order of the `uint112` ceiling and/or to coordinate with a graduation that closes with a very small `tokensForLP`/`ltFromPair` (achievable via a large `exchangeRate()` pump on the paired LT, which the design explicitly allows to trigger graduation off a near-zero real LT raise). This makes the attack capital-intensive and requires some precision, which is why it is assessed as Medium rather than High/Critical, but it is a genuine, code-supported failure mode that the authors themselves flagged as an accepted "revert rather than truncate" outcome without providing any fallback.

### Recommendation
Wrap the `_noFeeSwapInput` closed-form computation (or the call in `_pairRebalance`) in a bounds pre-check that safely detects when `reserveIn * reserveOut * targetN / targetD` would exceed `type(uint256).max` (e.g., via a pre-division ordering or a `try/catch`-style guarded path) and fall back to `_seedDirectMint` in that case, the same way the existing `s == 0` / `getAmountOut(s) == 0` fallback already works. This preserves the "must never revert" invariant across every reachable pre-seed shape and closes the last unguarded arithmetic path in the graduation seeding pipeline.

### Proof of Concept
1. Creator launches a token paired to LT `L`; the curve later graduates via the USD trigger after `L.exchangeRate()` is pumped so that `ltFromPair` (real LT raised) and thus `tokensForLP` are both very small — phase 1 (`_enterGraduating`) caches these tiny `(tokensForLP, ltFromPair)` values in `pendingGraduation[token]` [12](#0-11) .
2. Before anyone calls `finalizeGraduation`, the attacker calls the permissionless `factory.createPair(token, L)` on HyperSwap, transfers a very large amount of TOKEN (bounded by curve supply, up to ~750M·1e18) and a very large amount of `L` LT to the pair, then calls `pair.mint(attacker)` — setting `reserve0`/`reserve1` to values that put one side well above `DIRECT_MINT_PRESEED_BPS` relative to `(tokensForLP, ltFromPair)`, forcing `_seedRebalancing` into the rebalance branch instead of the safe direct-mint fallback [13](#0-12) .
3. Anyone calls `bonding.finalizeGraduation(token)`. Inside `_pairRebalance` → `_noFeeSwapInput`, `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` computes a quotient exceeding `2^256` (large attacker-set `reserveIn`/`reserveOut` divided by the tiny cached `targetD = tokensForLP`), and `Math.mulDiv` reverts with an EVM Panic [2](#0-1) .
4. `finalizeGraduation` reverts every time it is called for this token from then on — the token is permanently stuck in `Lifecycle.Graduating`, and the LT/tokens already escrowed in `Bonding` are unrecoverable.

Note: precisely reproducing the numeric threshold (exact `reserveIn`/`reserveOut`/`targetN`/`targetD` magnitudes needed to cross `2^256`) requires running the arithmetic/fuzzing in Foundry against the real `uint112` and token-supply bounds; this was not executed here and should be validated with a concrete Foundry PoC (extending `test/NoFeeSwapInput.t.sol`'s existing overflow-safety fuzz harness) before treating the magnitude as fully proven.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. In either case `_pairRebalance` returns `false`, and `_seedRebalancing` overpowers the dust with a direct `transfer + pair.mint` at the cached `tokensForLP / ltFromPair` ratio (`_seedDirectMint`), opening the pool on-ratio. This is safe specifically because the swap only rounds to zero when the reserves are negligible against this graduation's inventory: the V2 `min()` donation to the attacker's pre-existing LP is then bounded by `max(reserveToken/tokensForLP, reserveLT/ltFromPair)`, which vanishe ... (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
- **No external dependency on the router slot being correct post-deploy.** `uniswapV2Router` is set at `initialize` time alongside `uniswapV2Factory` and is rejected if zero. There's no live setter — rotation requires a UUPS upgrade so the change is visible on-chain ahead of any in-flight graduation.
