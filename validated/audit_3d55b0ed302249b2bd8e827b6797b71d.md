### Title
POA bridge `describeWithdrawal` misattributes withdrawal status/tx hash between concurrent same-asset withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches the on-chain/API withdrawal record to a caller-specified `WithdrawalIdentifier` using only `assetId`, not amount, destination address, or index, via `findMatchingWithdrawal`. When a batch of intents contains more than one withdrawal of the same asset (e.g., two different destination addresses withdrawing the same `nep141:` token in one transaction), the matching is ambiguous and the SDK can report the wrong `txHash`/status for a given withdrawal identifier.

### Finding Description
`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns each withdrawal an `index` per bridge route based on ordering, and later `PoaBridge.describeWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, lines 313-343) ignores that `index` entirely and instead calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which: [1](#0-0) 
selects the first API record whose `near_token_id` matches the `assetId` — with no disambiguation by amount, destination address, or the created index. The code comment openly acknowledges the limitation: [2](#0-1) 

The equality that should hold is: *the status/txHash reported for withdrawal at index N must correspond to the on-chain transfer for that exact withdrawal record (same recipient/amount)*. Because matching is done only by `assetId`, if a single NEAR transaction contains two `ft_withdraw` intents for the same token to different destinations, `describeWithdrawal` for withdrawal #1 can return the API record that actually belongs to withdrawal #2 (and vice versa), since `response.withdrawals` is explicitly documented as unsorted.

### Impact Explanation
This breaks the "status reported is not the on-chain outcome" class described in the prompt. An integrator that watches multiple same-token withdrawals in one batch (via `watchWithdrawal`/`createWithdrawalCompletionPromises` in `sdk.ts`, which iterate withdrawal identifiers and call `bridge.describeWithdrawal`) could:
- Report withdrawal A as "completed" with a `txHash` that actually completed withdrawal B, causing the integrator to credit/mark-complete the wrong leg while the real destination for A remains unconfirmed.
- Conversely, a completed withdrawal's `txHash` could be attributed to a still-pending withdrawal, potentially causing duplicate settlement action by the integrator for a withdrawal that already completed under another identifier's status.

This matches the required High-impact pattern: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no privileged action or trust in the relayer/PoA API beyond what integrators already extend by design. Any regular user (or the integrator's own batching logic) triggering a batch of `ft_withdraw` intents for the same `.omft.near` asset to two different destinations in a single intent settlement transaction reaches this path deterministically, since `createWithdrawalIntents` and multi-withdrawal orchestration explicitly support arrays of `WithdrawalParams`. The maintainers' own comment confirms this is a known, currently-unhandled edge case rather than a defended invariant.

### Recommendation
Extend `findMatchingWithdrawal` (or the POA bridge withdrawal-status API usage) to disambiguate by more than `assetId` — e.g., additionally matching on destination address and amount (net of fee), or by consuming a per-token ordinal/index consistent with `createWithdrawalIdentifier`'s `index` so that concurrent same-asset withdrawals in one transaction are correctly distinguished. Until fixed, `createWithdrawalIdentifiers`/orchestration code should reject or serialize batches containing multiple withdrawals of the same asset routed through the POA bridge, since status matching cannot currently guarantee correctness for that case.

### Proof of Concept
1. Construct a single `signAndSendIntent`/withdrawal batch containing two `ft_withdraw` intents for the same POA-bridge asset (e.g., `nep141:usdt.omft.near`), one to `destinationAddress = X` and one to `destinationAddress = Y`.
2. `createWithdrawalIdentifiers` assigns index 0 and 1 respectively for the `poa_bridge` route (`packages/intents-sdk/src/core/withdrawal-watcher.ts` lines 80-107).
3. After the NEAR tx settles, call `bridge.describeWithdrawal` for each `WithdrawalIdentifier`. Both calls hit `getWithdrawalStatusWithRetry` → same `response.withdrawals` list, and `findMatchingWithdrawal` returns the first entry matching `assetId` for *both* identifiers if the underlying API return order does not align with submission order (explicitly called out as unsorted in the source comment) — resulting in identifier #0 and #1 both resolving to the same (or swapped) `txHash`/status, misreporting completion for the wrong leg of the batch.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
