### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking the HMAC over the raw request body, then forwards the **unauthenticated** `shop` (and `topic`/`webhook-id`) header values straight to the app's handler. The identity binding that should hold is `HMAC(secret, body ‖ shop) == received_hmac`, but the actual check only verifies `HMAC(secret, body) == received_hmac`. This mirrors the reported bug class: a field that is *acted on* (`shop`, used as the tenant identity) is not *covered* by the integrity check (the HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the *entire request*, including `request.shop`, is authentic, and immediately hands that value to the app's handler as the tenant identifier: [3](#0-2) 

`request.shop` itself is read directly from the `X-Shopify-Shop-Domain` header with no cryptographic binding to the body or the HMAC: [4](#0-3) 

Because the webhook HMAC key (`api_secret_key`) is the app's single shared secret — identical for every shop that installs the app — any merchant who installs the app on their own store receives real webhook deliveries with a valid `(body, hmac)` pair signed with that same shared secret. An attacker (an "unprivileged internet user" from the perspective of any other tenant, i.e., a legitimately-onboarded merchant with no special access to other tenants' data) can capture one such valid `(body, hmac)` pair from their own store's webhook delivery, then replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. The HMAC check still passes because it only validates the body, not the shop header, so the forged shop value flows unchecked into `WebhookMetadata` and the app-supplied handler.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: an app built on this library, following its documented API (`Registry.process` → handler receives `data.shop`), will process attacker-controlled webhook content under an arbitrary victim shop's identity. Depending on how the app trusts `data.shop` (e.g., to look up or attribute data, trigger shop-scoped side effects, or key storage), this enables cross-tenant data injection/corruption — a High/Critical-adjacent cross-tenant access issue, since it directly violates the equality `authenticated_shop == acted_on_shop` that the HMAC is supposed to guarantee.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be able to install the target app on any shop they control (a normal, unprivileged action available to any merchant/developer on the Shopify platform), (2) capture one legitimate webhook body+HMAC pair from their own shop, and (3) replay it to the same app's public webhook endpoint with a different `shop` header. No access to `api_secret_key`, access tokens, or any other tenant's credentials is required — only the gem's own documented `Registry.process`/`Request` flow is used. This is a realistic and low-effort attack path.

### Recommendation
Bind the shop identity to the HMAC-verified payload instead of trusting an unauthenticated header:
- Do not treat `request.shop` (or `topic`/`webhook-id` header values) as authenticated merely because the body HMAC validated.
- Include the shop domain (and topic) in the signable string used for HMAC computation, or otherwise cross-check the header-provided `shop` against a value obtained through an authenticated channel (e.g., the shop associated with the webhook subscription registered via the Admin API, or the resource owner encoded in the payload) before passing it to `WebhookMetadata`.
- Document/enforce in `Registry.process` that consumers must independently verify `data.shop` against their own known/authorized shop list rather than trusting it implicitly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body, keyed with the app's shared api_secret_key>`
   - body: `{"id": 1, ...attacker-controlled order data...}`
3. Attacker captures this exact `(raw_body, hmac)` pair (they legitimately received it).
4. Attacker replays an HTTP POST to the app's webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see [5](#0-4) .
6. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` using the attacker-forged `victim-shop.myshopify.com` value and invokes the app's handler with it, as shown at [6](#0-5) , causing the app to process attacker-controlled content as if it originated from the victim shop.
