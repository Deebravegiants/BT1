## Analysis Result

I reviewed the orb-core codebase for the reported bug class ("sensitive data logged/emitted in production"). Most candidate logging (iris codes, normalized iris images, PCP credentials) is gated behind opt-in, non-default Cargo features (`log-iris-data`, `internal-data-acquisition`) and is therefore not part of the default production build.

However, one unconditional, always-compiled logging statement is a legitimate analog: the full backend-authenticated user data — including the user's `identity_commitment` (a persistent, biometrically-derived identifier used to prevent duplicate signups) — is logged at `info` level with no feature gate. [1](#0-0) 

### Title
Biometric Identity Commitment Disclosed via Unconditional Info-Level Logging - (File: src/backend/user_status.rs)

### Summary
`user_status::request` logs the entire `authenticated_app_data` (`orb_qr_link::UserData`) structure at `tracing::info!` level immediately after receiving it from the backend, before it is destructured. This structure contains `identity_commitment`, the user's persistent biometric-derived identity commitment, along with `self_custody_public_key`, `pcp_version`, `user_centric_signup`, and `orb_relay_app_id`.

### Finding Description
In `request()` in `src/backend/user_status.rs`, once the backend returns `authenticated_app_data`, the code immediately logs it in full:

```rust
if let (Some(backend_keys), Some(user_data)) = (backend_keys, authenticated_app_data) {
    tracing::info!("User QR-data: {user_data:?}");
``` [1](#0-0) 

This call is not gated by any Cargo feature flag (unlike iris-code logging, which requires the non-default `log-iris-data` feature [2](#0-1) , or normalized-image persistence, which requires `internal-data-acquisition`). The struct being logged, `orb_qr_link::UserData`, is subsequently destructured into fields the app treats as sensitive/durable — most notably `identity_commitment`, which is derived from the user's iris and used as the durable cross-signup identity anchor [3](#0-2) . It also includes `self_custody_public_key` and `orb_relay_app_id`, both persistent per-user identifiers.

Because this is an `info!`-level log with no feature gate, it is emitted on every device in production, on every successful signup validation, and is captured by the standard log pipeline the same way any other operational log is.

### Impact Explanation
`identity_commitment` is the durable value used across the whole system to correlate/deduplicate a user's biometric identity across signups. Persisting it in plaintext application logs (which are typically retained, shipped off-device, and accessible to a broader set of operators/support/debugging tooling than the signup pipeline itself) creates unnecessary exposure of a value that is meant to be treated as a sensitive, identity-linking biometric derivative. Combined with the same log's `orb_relay_app_id` and `self_custody_public_key`, this enables tracking/correlating a specific individual's signup sessions and iris-identity across time from log data alone — a cross-signup identity-linkage disclosure, consistent with the reported bug class (sensitive user data logged inappropriately).

This does not expose raw biometric imagery or private keys (those remain feature-gated or encrypted), so the impact is a privacy/correlation disclosure rather than direct account takeover.

### Likelihood Explanation
This code path executes unconditionally on every successful user QR-code validation during normal signup flow — no special feature flag, debug build, or attacker action is required to trigger the log line. Any party with read access to the Orb's/operator's logs (log aggregation, on-device debug logs, support tooling) is exposed to this data automatically.

### Recommendation
Remove or redact the `tracing::info!("User QR-data: {user_data:?}")` line, or downgrade it to a `trace!`/`debug!` level line that only logs non-sensitive fields (e.g., `pcp_version`, `user_centric_signup`) explicitly, rather than the whole `Debug`-derived struct. Consider implementing a custom `Debug` impl on `orb_qr_link::UserData` that redacts `identity_commitment` and `self_custody_public_key`, similar to the existing `Password` redaction pattern used elsewhere in the codebase. [4](#0-3) 

### Proof of Concept
1. Run the orb-core signup flow with a valid user QR code that the backend accepts (`valid: true`, non-empty `authenticated_app_data`).
2. Observe application logs at `info` level (default production log level).
3. The log line `User QR-data: UserData { identity_commitment: "...", self_custody_public_key: "...", ... }` appears, exposing the user's biometric identity commitment and other persistent identifiers in plaintext in the log stream.
