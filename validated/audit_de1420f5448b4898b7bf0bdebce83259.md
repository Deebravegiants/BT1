### Title
Missing L2 Sequencer Uptime Check in `SimplexPaymaster` Chainlink Price Consumption - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using raw Chainlink `latestRoundData()` calls with only a staleness bound (`maxOracleAge`), but never verifies that the L2 sequencer is up, as Chainlink officially requires for any L2 deployment of its price feeds.

### Finding Description
`_getOraclePrice` fetches `answer`/`updatedAt` from an `AggregatorV3Interface` and reverts only on non-positive answers or staleness beyond `maxOracleAge`: [1](#0-0) 

This is invoked from `_tokenPrice`, which is called both from the ERC-4337 validation path (`_fetchDetails`, used to determine what the sender is charged) and from the treasury-only `swapAndDeposit`: [2](#0-1) [3](#0-2) 

The `Params` struct and deploy script confirm this paymaster is intended for L2/L1 multi-chain deployment (Base, Ethereum, BSC referenced directly in comments), where Chainlink documents that during an L2 sequencer outage a feed can keep serving its last pushed answer — which remains "fresh" under a naive `updatedAt` staleness check even though the sequencer (and thus true price discovery) is halted: [4](#0-3) [5](#0-4) 

`_fetchDetails` is reached for every `UserOperation` a bundler submits naming this paymaster — a fully permissionless, unprivileged entry point (any wallet paying gas in a supported stablecoin is a "bandwidth purchaser" of this paymaster's gas sponsorship): [6](#0-5) 

Nowhere in the contract — `_setParams`, `_getOraclePrice`, `_tokenPrice`, `swapAndDeposit` — is there any reference to a Chainlink `Sequencer Uptime Feed` (e.g. `0xBCF85224fc0756B9Fa45aA7892530B47e10b6433` on Arbitrum, or the Optimism/Base equivalents) or a grace-period check after a sequencer restart.

### Impact Explanation
During an L2 sequencer outage, `nativeOracle`/token oracles keep returning their last on-chain answer, which stays within `maxOracleAge` (documented as up to 24h for Base/Ethereum stablecoin feeds) even though the true native-asset/token exchange rate may have since diverged sharply once trading resumes off-chain/on other venues. Any unprivileged party can submit a `UserOperation` during this window and be charged (or, symmetrically, cause the paymaster treasury to be shorted) based on the stale price rather than the real one, directly draining paymaster-held stablecoin/native reserves — a concrete transfer-of-value bug reachable by an ordinary gas-paying sender, not an admin or governance actor.

### Likelihood Explanation
L2 sequencer downtime is an operationally observed event (Arbitrum, Optimism, and Base have each experienced multi-minute-to-hour outages), and exploitation requires no special privilege — only submitting an ordinary `UserOperation` with paymaster data naming a token during (or immediately after) the outage while the last-good Chainlink answer is still inside `maxOracleAge`. No governance, admin, or relayer action is needed to reach `_fetchDetails`/`_getOraclePrice`.

### Recommendation
Wire a Chainlink `Sequencer Uptime Feed` into `_getOraclePrice` (or a dedicated check invoked from `_fetchDetails`/`_tokenPrice`/`swapAndDeposit`): revert if the feed reports the sequencer down, and enforce a grace period (e.g. Chainlink's recommended pattern of ~1 hour) after it comes back up before trusting price answers again, mirroring the `sequencerNotDown` pattern referenced in the analogous Arcadia finding.

### Proof of Concept
1. L2 sequencer (e.g. Base) goes down while `nativeOracle`/`tokenOracle` last reported ETH/USD = $X.
2. Off-sequencer, ETH price moves materially (up or down) due to broader market activity, but the Chainlink feed on the halted L2 cannot update.
3. Once the sequencer resumes (or via any RPC still serving the paused chain's last state during downtime, depending on infra), a searcher/bundler submits a `UserOperation` with `paymasterData` naming a registered stablecoin; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` reads the stale-but-not-yet-`maxOracleAge`-expired answer and computes `tokenPrice` off the outdated rate.
4. The sender's ERC-20 prefund is computed and pulled using the stale conversion rate, letting them systematically underpay (or the paymaster systematically overpay refunds) relative to the true market price, draining `treasury`/EntryPoint-backed reserves over repeated submissions until the feed catches up.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
