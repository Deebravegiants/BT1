### Title
Duplicate `input_data_ids` in an `ActionReceipt` can permanently stall a receipt (analogous to unchecked duplicate transaction inputs) - (File: `runtime/near-vm-runner/src/logic/logic.rs`)

### Summary
Dogecoin/Bitcoin's fix addressed a crash caused by never rejecting duplicate inputs within a single transaction. nearcore has a structurally similar gap: `promise_and` builds a receipt's list of "input dependencies" without deduplicating repeated `ReceiptIndex`/data-id entries, and receipt validation never rejects duplicates in `input_data_ids`.

### Finding Description
`promise_and` (`runtime/near-vm-runner/src/logic/logic.rs:2346-2399`) accepts an arbitrary array of previously created promise indices and folds their receipt dependencies into one `Vec<ReceiptIndex>` via `receipt_dependencies.extend(...)` [1](#0-0) . Nothing deduplicates this list, so a contract can trivially produce a `Promise::NotReceipt` whose dependency vector contains the same `ReceiptIndex` more than once (directly, or indirectly by joining a `promise_and` result with one of its own inputs).

This vector eventually becomes `ActionReceipt.input_data_ids` (`core/primitives/src/receipt.rs:599-604`). Receipt validation, `validate_action_receipt` (`runtime/runtime/src/verifier.rs:588-616`), only bounds the length against `max_number_input_data_dependencies` [2](#0-1)  — it never checks for duplicate ids.

On the receiving shard, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) iterates `input_data_ids` and, for each **not yet received** id, increments `pending_data_count` and writes a `PostponedReceiptId` link keyed by `(receiver_id, data_id)` [3](#0-2) . If the same `data_id` appears twice in the list, `pending_data_count` is incremented twice for what is really only one underlying `DataReceipt` that will ever be produced (each `data_id` is unique per originating receipt and delivered exactly once). When that single `DataReceipt` eventually arrives, `process_receipt`'s `Data` branch decrements `pending_data_count` only once (the `PostponedReceiptId` entry for that `data_id` is looked up and removed a single time) [4](#0-3) . The counter therefore never reaches zero, and the postponed receipt is stuck permanently — it never executes, since there is no other pending mechanism that will decrement it again.

### Impact Explanation
This is a chain/contract-execution liveness bug, not simple crash-on-invalid-input like the Dogecoin bug, but it fits the "node panic or unbounded resource use / chain stall" category the analysis is scoped to accept: a permanently orphaned postponed receipt occupies state forever (state bloat) and the intended callback/continuation of the DAG constructed with `promise_and` never fires, silently breaking the caller's cross-contract callback logic. Because it is triggerable purely from a `FunctionCall` action originated by any unprivileged account, it is reachable via ordinary transactions/receipts.

### Likelihood Explanation
Any contract can call `promise_and` with a manually crafted duplicate index array (or construct a diamond dependency graph that ends up joining the same underlying receipt twice), so the trigger requires only a `FunctionCall` deployed by any account — no validator or node-level privilege needed.

### Recommendation
Deduplicate `receipt_dependencies` in `promise_and` (`runtime/near-vm-runner/src/logic/logic.rs:2373-2386` and the wasmtime counterpart) before building `Promise::NotReceipt`, and/or add an explicit duplicate check for `input_data_ids` in `validate_action_receipt` (`runtime/runtime/src/verifier.rs`) so a receipt with a duplicated `input_data_ids` entry is rejected as invalid rather than silently stalling.

### Proof of Concept
1. Deploy a contract that calls `promise_create`/`promise_batch_create` to obtain two independent promise indices, `p1` and `p2`, each targeting some account.
2. Call `promise_and([p1, p1])` (duplicate index) or construct a diamond via nested `promise_and` calls that end up including the same underlying `ReceiptIndex` twice.
3. Call `promise_then`/`promise_batch_then` on the resulting joined promise index to create a callback `ActionReceipt` whose `input_data_ids` field now contains the same `data_id` twice.
4. Observe that once the single corresponding `DataReceipt` for that `data_id` is delivered, `process_action_receipt`'s `pending_data_count` (initialized to 2 for the duplicated id) is only decremented once in `process_receipt`, so the callback receipt remains permanently postponed in state and its `promise_then` callback never executes.

I was not able to trace an end-to-end integration test exercising this exact duplicate-`promise_and` scenario in the indexed code (only single-occurrence `promise_and` tests were found, e.g. `runtime/near-vm-runner/src/logic/tests/miscs.rs:391-455`), so the exact runtime behavior on duplicate joins should be confirmed with a live reproduction; a Devin session with full repo/test access would be needed to write and run this PoC end-to-end.
