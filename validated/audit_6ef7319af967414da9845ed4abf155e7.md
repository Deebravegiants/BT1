### Title
Withdrawal status matched only by asset ID causes cross-withdrawal transaction-hash misattribution in batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`, `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary

### Finding Description
When the PoA bridge resolves the completion status of a withdrawal, it looks up the matching entry in the bridge's withdrawal list using `findMatchingWithdrawal`, which matches **solely by `assetId` (derived from `near_token_id`)**, ignoring `index`, `amount`, and `destinationAddress`: [1](#0-0) 

The same pattern exists in the internal-utils PoA client used by `waitForWithdrawalCompletion`: [2](#0-1) 

The comment explicitly acknowledges: *"This means multiple withdrawals of the same token in a single transaction are not supported."* However, the SDK's newer batch-withdrawal API (`createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` with an array) is specifically designed to let integrators process **each withdrawal of a batch independently by index**: [3](#0-2) 

Nothing in `WithdrawalParams`, `createWithdrawalIdentifier`, or `processWithdrawal` prevents a caller from submitting a batch with two or more withdrawal entries that share the same `assetId` but differ in `amount` and/or `destinationAddress` (e.g., an exchange/integrator batching several users' USDC withdrawals into a single NEAR intent). `describeWithdrawal` is called independently per index (`entry.wid`) — see `withdrawalParams.map((_, index) => ...)` in `createWithdrawalCompletionPromises` — but the underlying `PoaBridge.describeWithdrawal` / `findMatchingWithdrawal` call: [4](#0-3) 

performs `.find()` over the *same* full `withdrawals` list every single call, keyed only by `assetId`. Because `.find()` always returns the first element in the array matching the asset id, **every index in the batch that shares the asset id resolves against the identical, first-matching backend withdrawal record** — regardless of which physical on-chain transfer actually corresponds to that index's `destinationAddress`/`amount`.

### Impact Explanation
For a batch of `N` withdrawals of the same asset to different destination addresses, `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` (and so on) can both report `status: "completed"` with the **same `txHash`**, even though only one physical destination-chain transaction corresponds to that hash. An integrator relying on `createWithdrawalCompletionPromises`'s per-index promises (exactly the granular-per-user tracking use case documented in `packages/intents-sdk/README.md` and the design RFC) to mark individual users' withdrawals as settled would attribute the wrong destination transaction hash to the wrong user/index — reporting a completed status/hash for a withdrawal to address B using the txHash that actually paid address A. This is a status/hash misreport that can make an integrator credit or reconcile a withdrawal that never happened at that hash, or fail to detect that a distinct on-chain payment is still pending, i.e., a double-credit/misreport condition on the integrator side.

### Likelihood Explanation
This requires no malicious actor: any legitimate caller batching multiple withdrawals of the same NEP-141 asset to different destinations in one intent (an anticipated and directly-supported feature per the batch-withdrawal RFC and README, `packages/intents-sdk/README.md` "Batch Withdrawals" section) triggers it deterministically once more than one same-asset withdrawal is indexed by the PoA bridge API.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate among multiple same-asset withdrawals — e.g., by additionally matching on `destinationAddress`/`amount`, or by consuming matched entries so repeat calls for the same intent do not return an already-attributed record, as suggested in the existing code comment ("matching could be done by sorting both API results and withdrawal params by amount").

### Proof of Concept
1. Submit a batch withdrawal intent with two `WithdrawalParams` entries, both `assetId: "nep141:usdc.omft.near"`, but `destinationAddress` A (amount 100) and `destinationAddress` B (amount 200).
2. After the intent settles, both destination transfers complete on the PoA side, producing two entries in `getWithdrawalStatus().withdrawals`, one for A and one for B.
3. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [paramsA, paramsB], intentTx })`.
4. Both `promises[0]` and `promises[1]` resolve via `PoaBridge.describeWithdrawal` → `findMatchingWithdrawal`, which `.find()`s the withdrawals array by `assetId` alone — both index calls return the identical first-matching entry's `transfer_tx_hash`, even though index 1 should report B's own distinct hash.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
