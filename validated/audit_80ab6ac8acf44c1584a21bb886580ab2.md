### Title
Unprotected `CallDispatcher.dispatch()` allows anyone to drain any funds transiently or permanently held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared, singleton, unowned contract used by `IntentGatewayV2`/`ExtrinsicIntents` (predispatch/postdispatch order execution) and by `HyperFungibleToken`/`WrappedHyperFungibleToken` (cross-chain calldata execution) to run arbitrary `Call[]` batches on behalf of these apps while holding tokens/ETH mid-flight. Its `dispatch(bytes memory encoded)` function is `external` with **no caller restriction whatsoever** — unlike every other privileged entry point in the codebase (`onlyHost`, `onlyOwner`, treasury-gating, etc. as seen throughout `HyperApp.sol`, `BridgeToken.sol`, `SimplexPaymaster.sol`), there is no `onlyGateway`/`onlyOwner`/allow-list check on who may invoke it.

### Finding Description [1](#0-0) 

The `dispatch` function decodes an arbitrary `Call[]` from caller-supplied bytes and executes each call from the `CallDispatcher`'s own address/context/balance, with zero access control. Multiple critical flows route tokens through this single shared contract and depend on it holding a **zero balance at rest**, sweeping any residual balance back to the gateway only at the end of the same transaction:

- `IntentGatewayV2.placeOrder`'s predispatch flow transfers `order.predispatch.assets` to the dispatcher, calls `dispatch(order.predispatch.call)`, then sweeps the resulting balance back via a second `dispatch(...)` call: [2](#0-1) 
- `IntentsBase._execute` sends solver output tokens directly to the dispatcher-as-beneficiary, then runs `order.output.call` via `dispatch`, then sweeps: [3](#0-2) 
- HyperFungibleToken cross-chain messages mint/unlock tokens directly `to` the `CallDispatcher` address so that bridged funds can be spent by embedded calldata: [4](#0-3) 

Because `dispatch()` is callable by anyone, an attacker who observes (or times) a moment where the `CallDispatcher` holds a nonzero token/ETH balance — for example, any token left over from a swap that isn't in the tracked `order.inputs`/`order.output.assets` list (so it is never swept), a lingering unlimited `approve()` granted to a router during a previous postdispatch swap (the docs explicitly warn "approvals... should use exact amounts... since the dispatcher contract holds tokens temporarily during execution" [5](#0-4) ), or any stray token/ETH sent to the well-known, CREATE2-deterministic `CallDispatcher` address across chains — can call `dispatch()` directly with a `Call[]` transferring that balance to themselves, or spending any outstanding allowance the dispatcher granted to a DEX router. This mirrors the `98Token` bug class exactly: a public function with no access control that lets any address invoke privileged token-moving logic on funds sitting in the contract.

### Impact Explanation
Any tokens or native currency that end up resting in the shared `CallDispatcher` — whether from an untracked side-token produced by postdispatch DeFi composability, a stray/accidental transfer, or a stale allowance to a router — are permissionlessly stealable by any address, since there is no restriction on who can call `dispatch()`. This constitutes concrete theft of funds routed through the intents and HyperFungibleToken bridging flows, both of which are core, unprivileged, user/solver-reachable paths in Hyperbridge.

### Likelihood Explanation
The `CallDispatcher` is intentionally shared across multiple apps and chains (same CREATE2 address), and its documentation itself flags the risk of it holding non-zero balances mid-execution and warns against unlimited approvals precisely because of this exposure. Any solver constructing postdispatch calldata that swaps through a DEX with slippage, or any cross-chain HFT message that mints to the dispatcher for a swap, can leave a nonzero balance or approval that any third party can then race to claim by directly invoking the unprotected `dispatch()` function — no proof, relayer, or governance action is required.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an allow-listed set of gateway/token contracts (e.g., an `onlyAuthorizedCaller` modifier configured by the deployer, or by deploying a dedicated, non-shared dispatcher instance per calling app), and/or ensure any residual approvals granted during a `Call[]` batch are revoked (`forceApprove(target, 0)`) at the end of execution so a shared dispatcher can never carry a persistent allowance or balance between unrelated calls.

### Proof of Concept
1. A solver fills an `IntentGatewayV2` order whose `output.call` performs `approve(uniswapRouter, type(uint256).max)` then `swapTokensForExactTokens(...)` (as shown in the existing test `testPostdispatchTokenSweep` [6](#0-5) ), leaving a large residual allowance on the shared `CallDispatcher` to the router that the `_execute` sweep does not revoke.
2. Separately, a HyperFungibleToken bridge message mints a small side-reward token directly to the `CallDispatcher` as part of an unrelated cross-chain swap-and-forward operation; this token is not part of any `order.inputs`/`order.output.assets` list and is therefore never swept.
3. An attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly (no relationship to any gateway) with `calls = [{to: sideToken, data: transfer(attacker, dispatcher.balanceOf)}]`, or `{to: uniswapRouter, data: swapExactTokensForTokens(..., recipient: attacker, ...)}` exploiting the residual allowance, and receives the funds — exactly analogous to the `98Token_exp.sol` PoC calling the unprotected `swapTokensForTokens` on the victim `swapContract`.

```text
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];

                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
