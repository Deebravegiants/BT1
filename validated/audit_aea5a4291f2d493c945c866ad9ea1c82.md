## Finding

### Title
Partial-fill escrow release rounds down to zero, letting a solver deliver real output and receive no escrowed input in return - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrowed input released to a solver on a partial fill with floor (round-down) integer division. When the fill is small relative to the total required output, this division can truncate to zero, so a solver transfers real output tokens to the beneficiary but is released zero input tokens from escrow — the exact "burn without return" bug class from the referenced report, applied to the intent solver instead of a vault depositor.

### Finding Description
In `_fillSameChain`, for a partial (non-completing) fill, the escrowed amount to release to the solver is: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

Only the completing fill (`amountFilled == totalRequired`) reads the actual remaining escrow balance (avoiding rounding loss for the *last* solver — this is the fix already validated by `testPartialFill_RoundingDustReleasedToFinalSolver`, see [2](#0-1) ). Every non-completing partial fill still uses floor division: `order.inputs[i].amount * fillAmount / totalRequired`.

Before this line, the solver has already unconditionally paid `fillAmount` (+ any surplus/protocol share) of output tokens to the beneficiary: [3](#0-2) 

If `order.inputs[i].amount * fillAmount < totalRequired`, `escrowedAmount` floors to `0`. `_partialFills[commitment][outputToken]` is still incremented by the full `fillAmount`, permanently consuming that portion of the order's remaining fillable amount, and the `WithdrawalRequest` is built with `escrowedInputs[i].amount == 0` and dispatched via `_withdraw`: [4](#0-3) 

The solver has transferred real value (output tokens) to the beneficiary but is entitled to and receives zero escrowed input tokens for that fill — a direct, permanent loss of the value delivered in that transaction. Unlike the completing fill, there is no later step that reimburses this solver for the rounded-away dust; the dust is simply absorbed by whichever solver happens to complete the order later (or left to the protocol if cancelled), not the solver who paid for it.

This is reachable by any unprivileged solver calling the public `fillOrder`/`_fillSameChain` path with a `solverAmount` that is small relative to `totalRequired` (e.g., low-decimal input token vs. high-decimal output token, or simply a tiny partial fill), without any minimum-fill-amount guard in the contract.

### Impact Explanation
A solver that submits a small, legitimate partial fill can pay real output tokens to the order's beneficiary and receive `0` input tokens from escrow in return. This is a direct loss of funds for the solver triggered by ordinary, permitted use of `fillOrder` — no malicious counterparty or governance action is required, only an unfavorable ratio between `order.inputs[i].amount`, `fillAmount`, and `totalRequired`. Repeated or larger-scale small fills compound the loss and correspondingly leave escrow trapped in the gateway beyond what any later solver's completing fill will recover for them.

### Likelihood Explanation
Likelihood is meaningful whenever input/output token decimals differ significantly (e.g., 6-decimal input vs 18-decimal output, as already exercised by the repo's own rounding tests) or a solver intentionally/accidentally fills a very small `solverAmount`. The existing test suite already demonstrates non-trivial truncation magnitudes (e.g., `33333333` units truncated per fill in `testPartialFill_RoundingDustReleasedToFinalSolver`); the same arithmetic can floor fully to zero for smaller `fillAmount`/`order.inputs[i].amount` combinations, and there is no code path preventing a solver from choosing such a fill.

### Recommendation
Require `escrowedAmount > 0` for non-completing partial fills (revert or reject fills that would round to zero), and/or use a rounding mode/guard that never releases less value than the solver is due, e.g.:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
if (escrowedAmount == 0) revert FillTooSmall();
```
Alternatively, enforce a minimum fill amount per output asset sufficient to guarantee `escrowedAmount >= 1` given the input/output amount ratio, so solvers cannot submit fills that structurally round their compensation to zero.

### Proof of Concept
Given an order with `order.inputs[i].amount = 1` (1 base unit) and `totalRequired = order.output.assets[i].amount = 1_000_000` (any output token with that much required):
1. Solver calls `fillOrder` with `solverAmount = 999_999` (a legitimate partial fill, `remaining = 1_000_000`, so `fillAmount = 999_999`).
2. Solver's output tokens (`beneficiaryTotal = fillAmount = 999_999`) are transferred to the beneficiary via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` (or ETH sent).
3. `escrowedAmount = (1 * 999_999) / 1_000_000 = 0` (floor division).
4. `_withdraw` is invoked with `escrowedInputs[i].amount = 0`; the solver receives no input token.
5. `_partialFills[commitment][outputToken]` is now `999_999`, so a later solver can only ever claim the remaining `1` unit of output and whatever escrow remains — the first solver's paid `999_999` output tokens are uncompensated.

    /*//////////////////////////////////////////////////////////////
                    ROUNDING DUST IN PARTIAL FILLS (Finding #4)
    //////////////////////////////////////////////////////////////*/

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeCleanAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeCleanAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeCleanAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
