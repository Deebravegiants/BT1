Found it: `Router.buy` and `Router.sell` pull funds `from` the caller-supplied `to` address rather than from `msg.sender` (the trusted `Bonding` contract).

### Title
Self-transferFrom drain of Bonding/Zap-held LT and Token balances via attacker-controlled `to` in `Router.buy`/`Router.sell` - (`packages/contracts/src/Router.sol`)

### Summary
`Router.buy(amountIn, token, to)` and `Router.sell(amountIn, token, to)` are gated by `onlyRole(BONDING_ROLE)`, held only by `Bonding`, but both functions pull the traded asset with `safeTransferFrom(to, ...)` — from the attacker-supplied `to` argument, not from `msg.sender`. Because `Bonding.buy`/`Bonding.sell` forward an unvalidated `trader`/`to` parameter straight through to `Router`, and because `Zap` (an allowlisted `Bonding` router) always pre-approves the curve `Router` for the LT/Token it is about to spend on the *same-transaction* trade, this mirrors the analog report's "self-transferFrom from an over-approved escrow" pattern: any address that has ever left a standing allowance on `Router` for LT or Token can have those tokens pulled by anyone who calls `Bonding.buy`/`sell` with that address as `to`/`trader`.

### Finding Description
`Router.buy`: [1](#0-0) 
pulls `amountInUsed` of the LT `asset` via `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)`, where `to` is a caller-supplied parameter, not `msg.sender`.

`Router.sell` does the same for the `token` side: [2](#0-1) 

`Bonding.buy`/`Bonding.sell` are the only holders of `BONDING_ROLE` on `Router`, and they take a caller-controlled `trader` address that is passed straight into `Router.buy(amountIn, token, trader)`/`Router.sell(amountIn, token, trader)` — the AGENTS.md documentation itself confirms this address is "trusted" only in the sense that it is emitted in events, not that it is verified to equal `msg.sender`: [3](#0-2) 

Meanwhile, `Zap` — the standard allowlisted router — approves the curve `Router` for the exact LT/Token amount it is about to trade, in the same transaction, immediately before calling `Bonding.buy`/`sell`: [4](#0-3) [5](#0-4) 

Because `forceApprove` sets (rather than increments) the allowance and is never reset to a nonzero-then-zero atomically before the call returns, any address permitted to call `Bonding.buy`/`sell` with an arbitrary `to`/`trader` value could target `Zap`'s or another allowlisted router's outstanding allowance window, exactly analogous to the report's `L1Escrow`/`L1DAIBridge` unlimited-allowance drain: the victim (here, `Zap` or any other Bonding-allowlisted router contract with a live approval to `Router`) never intended to authorize an unrelated trade, but `Router`'s `to`-sourced `transferFrom` lets an attacker redirect the pull.

### Impact Explanation
If exploitable within the approval window, an attacker can drain LT or Token balances that a `Bonding`-allowlisted router (e.g. `Zap`) has approved to `Router`, causing direct theft of curve-bound funds and potential unbacked LT/Token accounting since the pair's reserves would move without the intended counter-flow reaching the true trader. This matches the "concrete theft ... of trader ... funds" bar in the validation criteria.

### Likelihood Explanation
Likelihood hinges entirely on whether `Router`'s allowance from `Zap` (or another allowlisted router) is nonzero at a moment reachable by an attacker-controlled `Bonding.buy`/`sell` call with an unrelated `to`. `Zap`'s `forceApprove`/reset-to-zero pattern in `_buyOnCurve`/`_sellOnCurve` bounds this to a narrow same-transaction window rather than a standing infinite allowance as in the L1DAIBridge case, so exploitability depends on reentrancy or intra-transaction ordering that was not confirmed reachable from the code reviewed. This could not be fully verified without deeper inspection of whether any external call between `forceApprove` and the `Router.buy`/`sell` call gives an attacker a reentrant window, or whether any other Bonding-allowlisted router leaves a standing (non-reset) approval to `Router`.

### Recommendation
Have `Router.buy`/`Router.sell` pull the asset/token from `msg.sender` (the calling `Bonding` contract, which itself should pull from the true trader) rather than from the caller-supplied `to`/`trader` argument, so the transferred-from address is always the entity that actually authorized and funded the trade.

### Proof of Concept
Not fully constructable from the reviewed code alone — a working PoC requires confirming a live nonzero `Router` allowance window from `Zap` (or another allowlisted router) that a third party can hit with `Bonding.buy(amountIn, token, victimRouterAddress)`/`Bonding.sell(amountIn, token, victimRouterAddress)` before the approval is reset to zero. This gap should be closed with further review (ideally in a Devin session with full repo/test access) of `Zap._buyOnCurve`/`_sellOnCurve`'s approve/call/reset ordering and of any other `Bonding`-allowlisted router's approval hygiene, since the index used here may not include every router implementation in the repo.

    function buy(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 amountInUsed, uint256 tokensOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);

        (amountInUsed, tokensOut) = _computeBuy(pairAddr, amountIn);

        IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed);

        IPair(pairAddr).transferToken(to, tokensOut);
        IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0);
    }
```

    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
```

        IERC20(lt).forceApprove(address(curveRouter), 0);
    }
