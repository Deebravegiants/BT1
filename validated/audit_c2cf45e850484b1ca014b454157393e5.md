### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) are trusted for tenant dispatch but are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and are then used by `Registry.process` to route/dispatch the payload as if it came from that shop. This breaks the identity binding `shop authenticated by HMAC == shop the handler acts on`, exactly the report's bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are not part of the signed content: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` then trusts the unsigned `request.shop` header directly for dispatch to the app's handler, once the (headers-independent) body HMAC passes: [4](#0-3) 

Because the app's `client_secret` (and therefore the webhook HMAC key) is shared across every shop that has installed the app, any merchant who installs the app can generate a legitimate webhook (valid body + valid HMAC) from their own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header. `Registry.process` will pass HMAC validation (since only the body is checked) and hand the handler a `WebhookMetadata` claiming the payload came from the victim's shop.

Equality that should hold but doesn't: `shop bound into the HMAC computation == shop the handler treats as the event's tenant`. Here the left side is never established (no shop material is in `to_signable_string`), so the right side is fully attacker-controlled.

### Impact Explanation
This allows cross-tenant data injection: an attacker with a legitimate, unprivileged installation of the app on their own shop can forge webhook events that the app processes under a victim shop's identity, e.g. writing/updating tenant-keyed records, revoking data, or triggering `shop/redact`-like side effects for a shop the attacker does not control. This matches the accepted "cross-tenant access" impact category.

### Likelihood Explanation
Any user who can install the target app on a shop they control (a normal, unprivileged action) can capture a genuine `(body, hmac)` pair for a webhook topic the app registered, and then send an unauthenticated HTTP POST to the app's public webhook endpoint with the same body/hmac but a different `shop-domain` header. No access token, `client_secret`, or privileged access is required — only the ability to trigger a webhook on one's own store and to make one arbitrary HTTP POST.

### Recommendation
Include the identity/routing fields that the application will act on inside the signed payload, or otherwise cryptographically bind them to a value only Shopify controls per-shop. Concretely, verify the `shop-domain` header against an out-of-band trusted source (e.g. an active session/access token already known for that shop) before dispatching, rather than trusting the header as-is once the body-only HMAC passes. At minimum, document/require that consuming applications re-validate `WebhookMetadata#shop` against their own shop records before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a registered webhook topic (e.g. update a product) and captures the resulting POST: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` per `HmacValidator.compute_signature` / `Request#to_signable_string`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and the same `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation passes because the signature never covered the `shop-domain` header.
5. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the handler believes the event originated from the victim shop.
