### Title
Unauthenticated `origin` Parameter in `ConnectedOrigins` Module Allows Cross-Origin Privilege Bleed - (File: `features/connected-origins/module/connections.js`)

### Summary
The `ConnectedOrigins` module manages dApp connection trust state (`trusted`, `autoApprove`, `activeConnections`) keyed purely by an `origin` string supplied as a plain function argument, with no binding to the actual caller identity/context. This is exposed directly as a public SDK API surface in `features/connected-origins/api/index.js`, analogous to the reported `LendingMarket.cleanUpOrders()` issue: a state-mutating function that lacks any check tying the caller to the entity whose state is being mutated, relying entirely on the invoker to supply correct/trusted parameters.

### Finding Description
`ConnectedOrigins.connect`, `.disconnect`, `.setAutoApprove`, `.setFavorite`, `.updateConnection`, and `.add` all accept an arbitrary `origin` string and directly look up/mutate the origin's stored record with `#getOrigin`/`#setAttributes`, with no verification that the request actually originates from that origin: [1](#0-0) 

These module methods are re-exported verbatim as a public API surface: [2](#0-1) 

Just as `LendingMarket.cleanUpOrders()` mutates `activeLendOrderIds`/`activeBorrowOrderIds` for a `user` argument without restricting the caller to the legitimate `LendingMarketController` flow — trusting the caller to supply correct bookkeeping — here `connect`/`disconnect`/`setAutoApprove` mutate per-origin trust and connection state for an `origin` argument without restricting the caller to a flow that has cryptographically/structurally verified the request came from that origin (e.g., the browser extension's content-script/background message sender). The RPC transport used for the injected web3 provider (`libraries/browser-extension-rpc/content.js`, `libraries/browser-extension-channels/channel.js`) tracks `sender`/`tabId` metadata at the channel level, but I could not find, within indexed files, code in the RPC method dispatch that cross-checks the `origin` argument passed into `connectedOrigins.*` calls against `sender.tab.url`/`sender.origin`. If such enforcement is missing or bypassable at the dispatch layer, a malicious page could invoke these methods with an arbitrary `origin` string (e.g. a known trusted site) rather than its own.

### Impact Explanation
If the RPC dispatch layer does not enforce that the `origin` argument matches the real sender origin, a malicious website could:
- Call `setAutoApprove({ origin: '<trusted-site>', value: true })` to force auto-approval of connection requests for a different, already-trusted origin, weakening user confirmation flows for that origin.
- Call `connect`/`disconnect` with an arbitrary `origin` to forge or tear down another site's active connection state, and `getConnectedAccounts`/`isTrusted` are gated on `trusted`, so forging `add({ origin, trusted: true, ... })` could expose wallet addresses to an unrelated `origin` value, causing account/address disclosure across origin boundaries — a direct account/origin isolation bleed similar in class to the "unaccounted funds" problem (mutating protected state via an unauthenticated actor supplying the key).

### Likelihood Explanation
Uncertain/Medium. This depends entirely on whether the transport layer between the injected page and the extension background (which brokers `connectedOrigins.*` calls) independently pins the `origin` to `sender.tab`/`sender.url` before invoking the module method, discarding or overriding any page-supplied `origin`. I was not able to locate, within the indexed portion of the repo, the exact glue code that maps an incoming provider RPC request to the `connectedOrigins` API call with origin injection/validation. Given the indexing size limits mentioned for this codebase, this enforcement may exist in files not surfaced by search (e.g., in a provider/background module not indexed). This should be verified directly against the full source, ideally in a Devin session, before treating this as confirmed rather than a plausible analog.

### Recommendation
1. In the code path that dispatches incoming `connectedOrigins.*` calls from injected page/content scripts, ignore any `origin` value supplied by the caller and always derive it from the authenticated message sender (`sender.tab.url` / `sender.origin` from the browser messaging API), never from caller-supplied RPC parameters.
2. Add explicit assertions/tests in `features/connected-origins/module/connections.js` and its API wiring confirming that `origin` cannot be spoofed by the calling page, mirroring how `LendingMarket.cleanUpOrders()` was fixed by adding `onlyLendingMarketController` — i.e., restrict `connectedOrigins.connect/disconnect/setAutoApprove/add` to only be reachable through a controller/mediator that has already verified the true origin.
3. Audit all other public "module"/"api" definitions marked `public: true` that take identity-like parameters (`origin`, `walletAccount`, `id`) as plain arguments to confirm they aren't reachable directly from untrusted RPC callers without server-side (background) verification of the caller's real identity.

### Proof of Concept
Not able to construct a concrete, runnable PoC from the indexed files alone, because the exact RPC dispatch/glue code that would let an untrusted page invoke `connectedOrigins.setAutoApprove`/`connect`/`disconnect` with an arbitrary `origin` argument was not located in the available index (only the module implementation, its unit tests using the module directly, and the generic RPC transport primitives were found). A background Devin session with full repository access is needed to trace the exact request path from `window.exodus`/injected provider → `libraries/browser-extension-rpc` → `connectedOriginsApi` to confirm whether `origin` is trusted from the page or re-derived from `sender` metadata, and to build a concrete exploit script if unverified.

  setAutoApprove = async ({ origin, value }) => {
    return this.#setAttributes({ origin, attributes: { autoApprove: value } })
  }

  setFavorite = async ({ origin, value, assetNames = [] }) => {
    return this.#setAttributes({ origin, attributes: { favorite: value, assetNames } })
  }

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  disconnect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnections = activeConnections.filter((connection) => connection.id !== id)

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }
