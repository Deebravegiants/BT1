## Title
Unlimited replay of a single signed `transfer_from` approval drains the `usdk` stablecoin owner's balance - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

## Summary
The `usdk` stablecoin's `transfer_from` reimplements the ERC20 `approve`/`transferFrom` delegation pattern using a signed off-chain `Approval` message instead of an on-chain allowance mapping. The message's replay-protection field is `nonce: account::get_sequence_number(from)` [1](#0-0) , but `transfer_from` is submitted by `spender`, not by `from`, so calling it never advances `from`'s on-chain sequence number. Consequently the identical signature/proof remains valid and can be resubmitted an unbounded number of times, each call moving another `amount` out of the owner's primary store — a materially worse variant of the reported ERC20 race, since here it's unlimited replay rather than a narrow front-running window.

## Finding Description
`transfer_from` builds an `Approval` struct locally at call time using the owner's *current* sequence number as the anti-replay nonce, then verifies the caller-supplied `proof` against that freshly-constructed message: [2](#0-1) 

The critical assumption baked into this design is that `nonce` changes after each use so a previously valid signature becomes stale. But nothing in `transfer_from` consumes or increments `from`'s sequence number — the transaction sender/signer of this call is `spender`, and Aptos's transaction prologue only bumps the sequence number of the account that actually authorizes (signs) the top-level transaction, i.e. `spender`'s account, not `from`'s. `from`'s `Account.sequence_number` only advances when `from` itself submits a transaction. `account::get_sequence_number` simply reads that stored counter without mutating any state tied to this delegated-transfer flow.

Because of this, once Alice signs one `Approval{owner: from=Alice, spender: Bob, amount: 1000, nonce: N}` message and hands it to Bob (the intended off-chain "permit" use case), Bob can call `transfer_from` repeatedly: each call recomputes `nonce = account::get_sequence_number(Alice)`, which is still `N` since Alice hasn't transacted, so `verify_signed_message` succeeds every time and `primary_fungible_store::transfer_with_ref` executes again, each time withdrawing another `amount` from Alice's store via the module's own `Management.transfer_ref` (bypassing normal owner-authorization and frozen/denylist bypass only being blocked by pause/denylist checks, not by allowance exhaustion). This can be done in a single PTB (looped calls) or across many separate transactions, continuing until Alice's balance is exhausted or she submits any transaction (which finally advances her sequence number).

This breaks the custody invariant that a single owner-signed transfer authorization should permit at most one transfer of the specified `amount`; instead it permits `balance / amount` transfers of the owner's fungible-asset store to an address of the spender's choosing.

## Impact Explanation
This is a direct custody violation: unauthorized, repeated withdrawal of FA-held value (the `usdk` stablecoin) from the owner's primary fungible store to an arbitrary `to` address chosen by the spender, using only a single signature the owner believed authorized one bounded transfer. Because `usdk` stores are set `Untransferable` and rely solely on this signed-approval path (plus admin mint/burn/freeze) for peer-to-peer movement, this is the primary custody control for end-user funds in this module. An attacker (any spender who obtains one valid signed approval, e.g. for a legitimate one-time payment) can drain the full balance of the signer's `usdk` store, not just the approved `amount`. This is a high-severity theft/custody-accounting-corruption issue for any deployment of this stablecoin example pattern.

## Likelihood Explanation
Likelihood is high wherever this pattern is used: it requires no privileged role and no race/timing luck (unlike the classical ERC20 issue). Any party who legitimately receives one signed `Approval` (e.g., a merchant paid once via a gasless transfer) can trivially replay it in a loop to steal the owner's entire balance, as long as the owner does not submit an unrelated transaction in between. This is well within normal usage patterns of a "permit"-style delegated transfer and requires no special preconditions beyond possessing one valid signature.

## Recommendation
Bind the approval to a nonce/allowance that is actually consumed on use, not to the account's global transaction sequence number (which this flow never advances):
- Maintain an explicit per-`(owner, spender)` on-chain nonce or one-time-use allowance counter in the `usdk` module (e.g., a `Table<address, u64> approval_nonce` incremented inside `transfer_from` after successful verification), and require the signed message to include that module-local nonce instead of `account::get_sequence_number(from)`.
- Alternatively, mark the specific `(owner, to, spender, amount, nonce)` tuple (or a hash of it) as consumed in a resource so the exact same signature cannot be replayed, mirroring EIP-2612-style `permit` implementations that use a dedicated incrementing nonce mutated during `permit`/`transferFrom`, not the account's transaction sequence number.

## Proof of Concept
1. Alice's `usdk` primary store holds 1000 units; her account sequence number is `N` (unaffected by anything below).
2. Alice signs `Approval{owner: Alice, to: Bob, nonce: N, chain_id, spender: Bob, amount: 100}` and gives Bob the `proof` to pay for one $100 invoice.
3. Bob calls `usdk::transfer_from(bob_signer, proof, Alice, scheme, pubkey, Bob, 100)`. `transfer_from` computes `nonce = account::get_sequence_number(Alice) == N`, verification passes, 100 units move to Bob. Alice's sequence number is still `N` (only Bob's account's sequence number advanced from submitting the tx).
4. Bob calls the exact same `transfer_from(bob_signer, proof, Alice, scheme, pubkey, Bob, 100)` again (same `proof`, same parameters). `nonce` recomputed is still `N` since Alice performed no transaction; verification succeeds again; another 100 units move to Bob.
5. Repeat step 4 up to 10 times total (or bundle in one PTB loop) to drain Alice's entire 1000-unit balance from a single authorization intended for a 100-unit payment. [3](#0-2)

    /// Allow a spender to transfer tokens from the owner's account given their signed approval.
    /// Caller needs to provide the from account's scheme and public key which can be gotten via the Aptos SDK.
    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
