### Title
Unchecked subtraction in `canGraduate`'s USD-graduation leg lets rounding drift from `Pair.swap`'s `+1` K-slack permanently brick a curve's buy/sell/graduation path - ([File: packages/contracts/src/Bonding.sol])

### Summary
The Envoy CVE-2019-18838 root cause is a shared code path that dereferences a field ("Host header") that is not guaranteed to be present in every state the path can be reached from, crashing the process. The structural analog in alt.fun is `Bonding.canGraduate`'s `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` [1](#0-0) , an unchecked subtraction that assumes `assetReserve` (the `Pair`'s stored LT reserve) can never fall below the launch-time virtual reserve baked into `k()`. `canGraduate` is called on the hot path of *every* `Bonding.buy` and `Bonding.sell` [2](#0-1) [3](#0-2) , so a revert inside it doesn't just fail one transaction — it permanently freezes trading and graduation for that token.

### Finding Description
`Pair.swap` enforces the constant-product invariant with an off-by-one slack: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts, rather than requiring the exact product to hold [4](#0-3) . This slack exists *because* `Router._computeBuy` and `Router._computeSell` round every trade in the trader's favor via floor division:

- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` — `k / newReserveAsset` floors, so `tokensOut` is rounded up (more tokens out than the exact curve value) [5](#0-4) .
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` — same floor-division bias, rounding `assetOut` up [6](#0-5) .

Both directions systematically hand the trader slightly more than the exact K-preserving amount, so the resulting post-trade product is strictly below `k` — which is exactly what the `+1` slack in `Pair.swap` is there to tolerate. Because the curve charges **no fee** at the `Router`/`Pair` layer (fees only exist in `Zap`, skimmed from the gross USDC before it's ever converted to LT/curve units) [7](#0-6) , nothing at the AMM-math layer claws back the rounding leakage. Repeated round-trip buy+sell cycles on the same token can therefore drift the stored `assetReserve` down relative to the immutable `virtualLtReserve` baseline recovered via `_launchTimeVirtualLtReserve` (`k() / TOTAL_SUPPLY()`) [8](#0-7) .

Once enough drift accumulates that `assetReserve` dips below the recovered virtual baseline, `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts with a `Panic(0x11)`. Because `canGraduate` is invoked unconditionally inside `Bonding.buy` → `_executeBuy` and inside `Bonding.sell` [9](#0-8) [10](#0-9) , and also inside `triggerGraduation` [11](#0-10) , every subsequent buy, sell, and even the permissionless graduation trigger for that token reverts forever. The token is left permanently stuck in `Lifecycle.Curve` with its curve-raised LT and the creator's/traders' positions locked inside the `Pair`, unreachable by any of the three exits (buy, sell, graduate).

### Impact Explanation
This is a permanent freeze of funds, not a mere revert: the affected token can never trade again on the curve and can never reach graduation (both of `Bonding.buy`/`sell`/`triggerGraduation` are unconditionally gated by the now-reverting `canGraduate`). All LT previously raised into that `Pair`, and all tokens/LT held by traders who bought in, become permanently inaccessible through the protocol's own exits. This satisfies the "permanent freezing of trader, creator or LP funds" bar.

### Likelihood Explanation
The precondition — the whole trade path routes exclusively through `Zap.buy`/`Zap.sell`, which charge bps fees on every leg (`buyFeeBps`, `sellFeeBps`, capped at `MAX_FEE_BPS = 200`) [12](#0-11)  — means the wei-level rounding gain per round trip is dwarfed by the fee cost of each cycle, so this is not a profit-motivated attack; it is a griefing/DoS vector requiring an attacker to fund many round trips purely to force the drift. I was not able to fully quantify, within this pass, whether realistic reserve magnitudes (18-dp LT amounts, `VIRTUAL_LIQUIDITY_USD = 3000 ether` seed) allow the floor-rounding drift to cross the full-reserve threshold within an economically tolerable number of transactions, or whether it is bounded to sub-wei noise that never crosses zero. This needs an on-chain/Foundry simulation of repeated `buy`+`sell` cycles at the minimum `minTransactionSize()` granularity to confirm reachability before treating this as confirmed-exploitable rather than a plausible rounding-hardening gap.

### Recommendation
- Make the `canGraduate` / `previewLtUntilGraduation` subtraction saturating (as `finalizeGraduation` already does for its own `ltBalance - p.ltFromPair` computation [13](#0-12) ), so a reserve dipping at or below the virtual baseline degrades to "not yet graduatable" rather than reverting.
- Alternatively/additionally, tighten `Pair.swap`'s invariant check so it cannot be crossed by rounding-favorable trades over many iterations (e.g., charge a minimal curve-level fee, or round in the protocol's favor instead of the trader's in `_computeBuy`/`_computeSell`).

### Proof of Concept
1. Attacker acquires a small amount of USDC and calls `Zap.buy` then `Zap.sell` (or vice versa) on a freshly launched, thinly-traded token repeatedly, at the smallest amount permitted by `minUsdcAmount()`.
2. Each round trip nets the attacker a rounding-favorable output on both legs via `Router._computeBuy`/`_computeSell`, which `Pair.swap`'s `+1`-slack K-check permits.
3. Over sufficiently many cycles, the stored `assetReserve` in `Pair` drifts down relative to the immutable virtual baseline recoverable from `k()/TOTAL_SUPPLY()`.
4. Once `assetReserve` falls at/below that baseline, the next call to `Bonding.buy`, `Bonding.sell`, or `Bonding.triggerGraduation` for that token reverts inside `canGraduate`'s unchecked subtraction, permanently bricking the token's curve and graduation path with LT and tokens locked inside `Pair`.

(Note: step 3's practical iteration count to reach the underflow boundary was not numerically verified in this pass and should be confirmed with a Foundry fuzz/invariant test before treating severity as fully confirmed.)

        uint256 assetIn,

    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.assetReserve = newAssetReserve;
