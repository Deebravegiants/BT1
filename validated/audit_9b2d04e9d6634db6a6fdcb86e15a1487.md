### Title
Webhook HMAC signs only the request body, not the `shop-domain` header — allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook is genuinely from Shopify by validating an HMAC, but the HMAC is computed only over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — all taken from HTTP headers — are never part of the signed material, yet they are trusted and forwarded unchanged into the handler as the tenant-identifying `WebhookMetadata`. This breaks the equality `shop authenticated by HMAC == shop acted on by handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the signature exclusively against `verifiable_query.to_signable_string`, i.e. the body: [2](#0-1) 

`Registry.process` gates on this HMAC check and then builds `WebhookMetadata` directly from unauthenticated header-derived accessors (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`): [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [4](#0-3) 

Because the HMAC is computed with the app's single `client_secret` (shared across every shop that installs the app) and covers only the body, any entity that installs the app on their own shop legitimately receives correctly-signed webhook deliveries from Shopify for their own shop's events. That entity can capture such a request and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header rewritten to a victim shop domain, while keeping the original body and its still-valid HMAC signature untouched. `Utils::HmacValidator.validate` will accept it because it only re-derives the signature from the untouched body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop, carrying attacker-chosen body data.

### Impact Explanation
This is a cross-tenant confused-deputy condition: the library exposes header-derived `shop` to application handlers as if it were authenticated, when in fact only the body bytes are authenticated. Any host application that uses `data.shop` (per `WebhookMetadata`) to select the tenant/session/record to act on — the intended and documented usage pattern — can be made to apply attacker-supplied webhook payloads (e.g. `app/uninstalled`, `shop/redact`, `orders/create`, etc.) to a different merchant's tenant, with a signature that legitimately validates. This crosses the tenant boundary that the HMAC check is supposed to enforce, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged user can install the target app on a shop they control (a normal, unprivileged action for public apps), which causes Shopify to deliver a genuinely-signed webhook to the app for their own shop. Capturing and replaying that request with a modified `shop-domain` header requires no secrets, tokens, or elevated access — only the ability to make an HTTP request to the app's public webhook endpoint, which is the exact threat model of an "unprivileged internet user."

### Recommendation
Bind the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material, or otherwise verify that the `shop-domain` header corresponds to the shop the webhook was actually registered/delivered for (e.g. cross-check against an installed/known shop list or session store) before constructing `WebhookMetadata`. At minimum, document prominently that `data.shop` is not itself covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over BODY, using app's client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, "attacker-controlled": "data"}
   ```
3. Attacker resends the identical body/HMAC to the same endpoint, only changing the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `hmac` validates successfully via `Utils::HmacValidator.validate`, because validation only checks `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"attacker-controlled" => "data"}, ...)`, causing the host application to apply attacker data under the victim shop's tenant context.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
