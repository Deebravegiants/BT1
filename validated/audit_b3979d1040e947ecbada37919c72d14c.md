### Title
`Webhooks::Request#shop`/`#topic` are read from unsigned headers while HMAC only covers the raw body, allowing header-spoofed cross-tenant webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Utils::HmacValidator.validate` verifies only `Request#to_signable_string` (the raw HTTP body) against `hmac`, but `Registry.process` independently trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`, which are parsed from unauthenticated headers (`shopify-shop-domain`/`x-shopify-shop-domain`, `shopify-topic`, `shopify-api-version`). Because none of these headers are part of the signed content, a valid `(body, hmac)` pair for one shop/topic can be replayed with different header values and still pass validation, letting `WebhookMetadata#shop`/`#topic` diverge from what was actually signed.

### Finding Description
The claimed binding is: `bytes_signed == bytes_acted_on`, i.e. the shop/topic that the HMAC verifies for must equal the shop/topic the handler acts on.

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only to `verifiable_query.hmac` [2](#0-1) . The shop, topic, api-version and webhook-id headers are never included in the signable string or the comparison.
- `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled straight from the (attacker-writable, unsigned) HTTP headers via `shopify_header`, with no cross-check against the body or HMAC [3](#0-2) [4](#0-3) .
- `Registry.process` validates the HMAC once, then immediately trusts these unsigned fields to build `WebhookMetadata` and dispatches to the host app's handler: `Utils::HmacValidator.validate(request)` ... `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [5](#0-4) .
- `WebhookMetadata` is a plain `T::Struct` that stores exactly the raw `shop` string handed to it — there is no re-derivation or re-verification of shop identity anywhere downstream [6](#0-5) .

Exploit flow: an attacker installs the target app on their own development shop and, using their own legitimate Admin API access, registers an HTTP webhook subscription pointing at a server they control. Shopify delivers a genuinely signed webhook (`raw_body` + `X-Shopify-Hmac-Sha256` computed with the app's real `api_secret_key`) to that attacker-controlled endpoint. Because the HMAC never covers `shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, or `shopify-webhook-id`, the attacker can now forward that exact `(body, hmac)` pair to the app's real public webhook route while substituting `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`, e.g. `customers/redact` or `shop/redact`). `HmacValidator.validate` still returns `true` because it only checks the body bytes against the HMAC, and `Registry.process` then builds `WebhookMetadata` carrying the victim's shop domain and dispatches it to the host app's handler as if it were an authentic webhook for that shop.

None of the existing guards catch this: `HmacValidator.validate` only authenticates body bytes, not headers [7](#0-6) ; there is no `ShopValidator.sanitize!` call, no session/state comparison, no JWT check, and no Sorbet runtime check that ties `shop` to the signed payload — Sorbet only enforces that `shop` is a `String`, not that it is authentic.

### Impact Explanation
The host app's webhook handler receives `WebhookMetadata#shop` fully attacker-controlled while believing it has been authenticated by the HMAC check that just passed. Any host app that uses `data.shop` to decide which merchant's records to read, write, or delete (a documented, intended use of this field) can be made to act against an arbitrary victim shop domain using attacker-supplied body content and topic. This satisfies "Critical - cross-tenant access: one shop's request reads or mutates another merchant's data," including the worst case of triggering mandatory compliance topics (`customers/redact`, `shop/redact`) against a shop the attacker does not own. The attack is repeatable against any victim shop domain known to the attacker (shop domains are not secret) and any topic, for every request.

### Likelihood Explanation
Preconditions are modest and within the declared attacker capability set: the attacker only needs their own development shop, the ability to install the target app, and the ability to register a webhook to a server they control (all explicitly permitted). No `api_secret_key`, access token, or victim credentials are required — the only "secret" needed (a valid HMAC over an attacker-chosen body) is obtained legitimately from Shopify's own delivery to the attacker's own endpoint. Forging the replayed HTTP request (arbitrary headers) is trivial and requires no TLS interception. This is directly reachable through the gem's documented API (`ShopifyAPI::Webhooks::Registry.process`), so likelihood is high.

### Recommendation
Do not trust unsigned headers for tenant-identifying fields. Either (a) include `shop-domain`, `topic`, `api-version`, and `webhook-id` in the signable string that is HMAC-verified (matching what Shopify actually signs, if that's supported), or (b) require host apps to independently verify `WebhookMetadata#shop` against a known/installed-shop list (e.g., cross-check against `Auth::Session` state) before using it to select data, and document that the header-derived `shop`/`topic` fields are not authenticated by the HMAC check alone.

### Proof of Concept
```ruby
# test/webhooks/request_spoof_test.rb
require "test_helper"

class RequestSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @raw_body = '{"id":123,"note":"attacker-controlled"}'
    @hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body)
    )
  end

  def test_hmac_ignores_shop_header
    headers_shop_a = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => @hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2024-01",
      "x-shopify-webhook-id" => "1",
    }
    headers_shop_b = headers_shop_a.merge(
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      "x-shopify-topic" => "customers/redact",
    )

    req_a = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_shop_a)
    req_b = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_shop_b)

    # BYTE IDENTITY: same body/hmac bytes verified in both cases
    assert_equal req_a.hmac, req_b.hmac
    assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_b)

    # Divergence: shop/topic acted upon differ despite identical signed bytes
    assert_equal "attacker-shop.myshopify.com", req_a.shop
    assert_equal "victim-shop.myshopify.com", req_b.shop
    assert_equal "orders/create", req_a.topic
    assert_equal "customers/redact", req_b.topic
  end
end
```
This demonstrates that identical signed bytes (`raw_body` + `hmac`) validate successfully under two different `shop-domain`/`topic` header combinations, proving the HMAC-verified content and the shop/topic later used to build `WebhookMetadata` and dispatch to the handler are not bound to each other.
