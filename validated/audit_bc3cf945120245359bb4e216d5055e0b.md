### Title
Double-entry token aliasing lets a single real ERC20 transfer satisfy two independent `balanceDif` checks, minting shielded UTXOs without full backing - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` snapshots `getBalancesForArray(circomData.erc20TokenAddresses)` once before and once after `_internalTransact`, then validates `balanceDif[i] == amountChanges[i] + utxoAmount` **independently per array index**. Because the check never verifies that each `erc20TokenAddresses[i]` corresponds to a distinct underlying balance, an attacker who deploys a token where two different addresses read/write the same storage (a "double-entry" token) can make one real transfer of `X` satisfy the equality for two separate entries, letting the SNARK-verified off-chain UTXO set mint `2X` of shielded value while the vault only received `X`.

### Finding Description
The invariant claimed to hold is:
`newBalances[i] - oldBalances[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` for every `i` [1](#0-0) 

Both `oldBalances` and `newBalances` are produced by `getBalancesForArray`, which simply calls `balanceOf`/`address(this).balance` for each entry of `circomData.erc20TokenAddresses`, with no deduplication or aliasing check [2](#0-1) .

For `externalActionId == 0`, `_internalTransact` iterates the same array and, for each index with a positive `deltaAmountChange`, performs a real `transferFrom` pulling `amountChanges[i]` tokens into the vault; for negative deltas it pushes tokens out (net of relay fee) [3](#0-2) . Critically, `utxoSet` stays an empty array for the internal path (`UTXO[] memory utxoSet;` is never assigned in the `externalActionId == 0` branch) [4](#0-3) , so `utxoAmount` is always `0` and the check collapses to `balanceDif[i] == amountChanges[i]` per index for internal transacts.

Attack: the attacker deploys a malicious "twin" ERC20 where address `A` is the real token (implements a genuine `transferFrom` that moves value and updates a shared storage slot) and address `B` is a second contract instance whose `balanceOf()` reads that same shared storage slot but whose `transferFrom()`/`transfer()` is a no-op (attacker fully controls the token code, which is permitted — the attacker deposits/withdraws their own funds through their own deployed token). The attacker then calls `transact` with `erc20TokenAddresses = [A, B]` and `amountChanges = [X, X]` (both interpreted as deposits by `_calculateDeltaAmount`) [5](#0-4) .

During `_internalTransact`, index 0 (`A`) executes a real `transferFrom` moving `X` real tokens into the vault, which increases the *shared* underlying storage by `X`. Index 1 (`B`) also has `deltaAmountChange > 0`, so `transferERC20TokenFromOrCheckETH(B, ...)` is called, but `B.transferFrom` is a no-op — no additional real value moves. Because `A` and `B` alias the same storage, `getERC20OrETHBalance(A)` and `getERC20OrETHBalance(B)` both now read `oldBalance + X`. Back in `transact`, `balanceDif[0] = X` and `balanceDif[1] = X` are computed independently from the global before/after snapshot, satisfying `balanceDif[i] == amountChanges[i]` for **both** indices [1](#0-0) , even though only `X` of real value ever entered the vault.

Since the SNARK circuit treats `A` and `B` as two distinct field-element token identifiers with independent `inTotal + amountChanges == outTotal` constraints per token, the attacker's proof mints off-chain UTXOs worth `X` for token `A` and `X` for token `B` — `2X` of shielded value credited to the pool, backed by only `X` of real assets. `verifyProof`, `rootHashExists`, `dimensionsCheck`, and `insertNullifiers`/`insertCommitments` never cross-check that two distinct `erc20TokenAddresses` entries do not alias the same real balance, so none of the existing guards catch this.

When `circomData.feeStructure.feeToken` equals the token used for a withdrawal leg that is also aliased with a deposit leg elsewhere in the array, the flat/variable relay fee is computed from `sumAbs` derived purely from `amountChanges[i]` at that index [6](#0-5) , completely decoupled from the aliasing-inflated balance snapshot at the other index — the fee logic offers no additional protection and can be manipulated in the same transaction to also under-pay the relay while the double-entry mint occurs.

### Impact Explanation
The attacker mints shielded UTXOs (real, spendable, transferable Hinkal balance) worth up to `2X` (scales with the number of aliased duplicate entries) while only depositing `X` of real tokens into the vault, i.e., minting shielded value without backing / protocol insolvency — a direct Critical impact per the rules. This is fully repeatable: the attacker can redeploy new twin-token contracts and repeat the exact same call pattern to keep inflating the shielded pool, and later redeem the excess shielded balance for real assets belonging to other users, draining the vault.

### Likelihood Explanation
Preconditions are entirely within attacker's control: they need to deploy one malicious ERC20 contract (unprivileged, permitted per the rules) and construct a valid proof for their own UTXOs using `externalActionId == 0` (internal transact, no whitelisting/registration required, unlike external actions which require `externalActionMap` registration). No special protocol state, admin role, or victim interaction is required — cost is just gas plus proof generation for the attacker's own deposit. This is a low-cost, highly repeatable attack.

### Recommendation
Do not compute `balanceDif` per array index against independent `balanceOf` snapshots. Instead:
- Deduplicate `circomData.erc20TokenAddresses` and aggregate all `amountChanges`/`utxoAmount` per unique address before comparing to a single balance delta for that unique address, rejecting transactions where a token address repeats with inconsistent totals, or
- Explicitly reject duplicate entries in `erc20TokenAddresses` (enforce strict uniqueness) at the `performHinkalChecks`/`dimensionsCheck` stage, since the aliasing exploit fundamentally relies on being able to list the "same" real balance under two different addresses/indices.
- Additionally, consider validating balances via `transferFrom`-return deltas measured immediately around each individual transfer rather than one aggregate before/after snapshot for the whole batch, closing off other same-index reentrancy-style balance manipulation.

### Proof of Concept
Foundry test plan:
1. Deploy `TwinToken` pair: `TokenA` (real ERC20 with `transferFrom` moving value into a shared `uint256 sharedBalance[holder]` mapping) and `TokenB` (exposes `balanceOf` reading the same `sharedBalance` mapping, but `transferFrom`/`transfer` are no-ops returning `true`).
2. Fund attacker with `X` `TokenA`/shared balance; approve `Hinkal`.
3. Generate a valid proof (locally, using the repo's circuits) for an internal transact (`externalActionId == 0`) with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, producing two off-chain UTXOs each worth `X` for `TokenA` and `TokenB` respectively that satisfy the circuit's `inTotal + amountChanges === outTotal` per-token constraint.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. Assert: `IERC20(TokenA).balanceOf(hinkal) - oldBalanceA == X` (only `X` real value entered the vault) while `balanceDif` computed by the contract for BOTH indices equals `X`, and the transaction succeeds (does not revert on "Balance Diff Should be equal to sum..."), demonstrating that the two shielded UTXOs totaling `2X` were credited to the pool.
6. Assert the broken equality directly: `sum(amountChanges) + sum(onchain UTXO amounts minted) == 2X`, while `net real tokens entering Hinkal == X` — confirming `2X != X`, i.e. insolvency introduced in a single transaction.

```text
    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
```
