I have enough context now to finalize the analysis. The `process_deposit` function (`program/src/processor.rs`) reads vault balances once via `unpack_token_account` before the transfer, calculates `mint_lp_amount` from the nominal `deduct_coin_amount`/`deduct_pc_amount`, and only afterward calls `Invokers::token_transfer` for the actual CPI — with no post-transfer balance verification.

### Title
Deposit does not verify actual vault balance increase before minting LP tokens, allowing dilution/insolvency with fee-on-transfer (deflationary) mints - (File: program/src/processor.rs)

### Summary
`Processor::process_deposit` computes the LP tokens to mint based on the *nominal* `deduct_coin_amount`/`deduct_pc_amount` values, then transfers that nominal amount from the user to the AMM vaults via `Invokers::token_transfer`, without re-reading the vault's SPL token balance after the transfer to confirm the amount actually received. If the pool's coin or PC mint is a fee-on-transfer / deflationary token, the vault receives strictly less than `deduct_coin_amount`/`deduct_pc_amount`, yet `mint_lp_amount` is still minted as if the full nominal amount arrived.

### Finding Description
In `process_deposit`, vault balances are unpacked once at the top of the function via `Self::unpack_token_account` [1](#0-0) , and used to build the pre-deposit pool invariant. Based on this invariant and the user-supplied `deposit.max_coin_amount`/`deposit.max_pc_amount`, `deduct_coin_amount`, `deduct_pc_amount`, and `mint_lp_amount` are derived [2](#0-1) .

After only checking that the user's token account has sufficient nominal balance (`deduct_coin_amount > user_source_coin.amount`), the program performs the SPL transfers and mints LP tokens for the *nominal* deduced amount, with no subsequent check of the vaults' actual post-transfer balances: [3](#0-2) .

The transfer itself is a plain `spl_token::instruction::transfer` CPI in `Invokers::token_transfer` [4](#0-3) , which for a fee-on-transfer/rebasing mint credits the destination vault with less than the debited amount. Since `amm.lp_amount` is incremented by the full `mint_lp_amount` computed from the nominal deposit rather than the actual tokens received [5](#0-4) , the LP supply becomes over-minted relative to the real assets backing the pool.

### Impact Explanation
Because `mint_lp_amount` is derived from the intended transfer amount rather than the verified post-transfer vault delta, any pool created with a fee-on-transfer or otherwise balance-mutating token mint will systematically mint more LP tokens than the value actually deposited. This dilutes all existing LP holders' redeemable share of the coin/pc vaults on every subsequent deposit, and on `Withdraw` this under-collateralization becomes realized as insolvency once cumulative minted LP exceeds the real backing — an unbacked LP minting / insolvent pool accounting condition affecting all LPs, not just the depositor.

### Likelihood Explanation
`Initialize2` is permissionless and lets any user create a pool for an arbitrary coin/pc mint pair (subject only to it being a valid OpenBook market), so an attacker can trivially create a pool using a fee-on-transfer or rebasing SPL token as coin or pc mint, then repeatedly call `Deposit` to mint inflated LP tokens for themselves before withdrawing against the (higher-than-actual) backing, at the expense of any other LP who deposits a "clean" paired asset. No privileged signer or off-chain component is required — a single `Deposit` instruction with attacker-chosen accounts on a self-created pool is sufficient to reach the vulnerable code path.

### Recommendation
Before minting LP tokens (and before computing swap-adjacent PnL bookkeeping in `Deposit`), re-read the actual vault token account balances after the SPL transfer completes and use the observed delta (post-balance minus pre-balance) rather than the nominal `deduct_coin_amount`/`deduct_pc_amount` when computing `mint_lp_amount`. Equivalently, disallow pools whose coin/pc mint has a non-zero `TransferFeeConfig` extension (Token-2022) or is otherwise known to be rebasing/deflationary, by validating the mint at `Initialize2` time.

### Proof of Concept
1. Attacker calls `Initialize2` to create a new AMM pool with `pc_mint` set to a fee-on-transfer SPL token (e.g., a Token-2022 mint with `TransferFeeConfig`) and a normal `coin_mint`.
2. Attacker calls `Deposit` with `max_pc_amount = X`. `process_deposit` computes `deduct_pc_amount ≈ X` and a corresponding `mint_lp_amount` from the pre-deposit pool ratio [6](#0-5) .
3. `Invokers::token_transfer` debits `X` from the attacker's source PC account, but due to the transfer fee the vault only receives `X * (1 - fee_bps)`.
4. `amm.lp_amount` is nonetheless incremented by the full `mint_lp_amount` computed for `X` [5](#0-4) , so the attacker (or any depositor) receives LP tokens representing more value than was actually transferred into the vault, diluting all other LP holders proportionally.
