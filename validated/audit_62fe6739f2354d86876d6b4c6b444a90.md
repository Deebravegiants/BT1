## Title
Checks-Effects-Interactions violation in `withdraw()` allows reentrant double-redemption of escrow and fee token via a malicious "token" contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The Tron deployment of `IntentGatewayV2` performs the low-level, arbitrary-token external call (`token.call(transfer(...))`) *before* decrementing the corresponding `_orders[commitment][token]` escrow accounting and *before* deleting the `TRANSACTION_FEES` entry, inside `withdraw()`. Because the escrowed `token` address is fully attacker-controlled (set by the user at `placeOrder` time), an attacker can register a malicious "token" contract as an order input, whose `transfer` implementation reenters the surrounding protocol before the storage is updated, exactly mirroring the Panoptic SFPM bug where the external liquidity/token operation preceded the `feesBase`/accounting update.

## Finding Description
`withdraw()` is the internal function invoked by `onAccept` (for `RedeemEscrow`/`RefundEscrow`) and `onGetResponse` (for source-chain cancellation) to release escrowed order inputs and transaction fees to a beneficiary: [1](#0-0) 

The order of operations in the loop is:
1. `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — only checks non-zero, not full balance.
2. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` — **external interaction**, control can pass to attacker code if `token` is a malicious contract.
3. `_orders[body.commitment][token] -= amount;` — **effect applied only after the interaction**.

Likewise, the `TRANSACTION_FEES` release performs `feeToken.call(transfer(...))` and only deletes `_orders[body.commitment][TRANSACTION_FEES]` afterward.

The escrowed `token` addresses in `body.tokens` originate directly from `order.inputs`, which are supplied by the user at `placeOrder()` time — i.e., fully attacker-controlled, exactly as in the referenced report where the attacker chose an ERC777 token to obtain a reentrancy callback during a Uniswap/SFPM operation. This is structurally identical to the H-01 root cause: **an externally-controlled token/liquidity operation is sequenced before the corresponding internal accounting update**, allowing a reentrant call to observe stale (non-decremented) escrow state.

Neither `onAccept` nor `onGetResponse` nor `withdraw()` carries any reentrancy guard (`nonReentrant`/`ReentrancyLock`), unlike the CEI hardening already applied elsewhere in the codebase for `IntrinsicIntents._fillSameChain` (which sets `_filled[commitment] = msg.sender` before any external call specifically to prevent this class of bug, as documented in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`).

## Impact Explanation
If the attacker's malicious token reenters into any function that reads `_orders[body.commitment][token]` (still un-decremented at that point) or `_orders[body.commitment][TRANSACTION_FEES]` (not yet deleted), the attacker can cause a double-payout of the same escrowed funds or transaction fee to the beneficiary from the gateway's real balances (transaction fees are paid in a shared `feeToken()` pool funded by all users' orders, per `IDispatcher(host()).feeToken()`), resulting in direct theft of funds belonging to other users/the protocol. This matches the "concrete theft of funds" bar required for High severity.

## Likelihood Explanation
The main blocking factor is whether a re-entrant call path back into `withdraw()`/`onAccept`/`onGetResponse` is reachable from within the token's `transfer` callback in a single transaction (these entry points are `onlyHost`-gated, and I could not fully confirm within the available tool budget whether `EvmHost`/`HandlerV2`'s message-delivery replay protection is itself reentrancy-safe on this specific Tron variant, or whether a single relayer-submitted batch could deliver two proofs for the same commitment before the first `_orders` write completes). Regardless of the exact re-entry route, the ordering itself is a clear CEI violation on attacker-controlled external calls, matching the analog bug class precisely, and the main EVM (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) already fixes this exact issue by decrementing `_orders` before the transfer — confirming the team recognizes this pattern as unsafe and has already patched it elsewhere, but the Tron contract was left with the vulnerable ordering.

## Recommendation
Apply the same Checks-Effects-Interactions fix already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to the Tron `IntentGatewayV2.sol::withdraw()`:
- Decrement `_orders[body.commitment][token]` and `delete _orders[body.commitment][TRANSACTION_FEES]` **before** performing the external `token.call`/`feeToken.call` transfers.
- Add a reentrancy guard on `onAccept`/`onGetResponse` (or the `withdraw` internal function) for defense in depth, consistent with the `ReentrancyLock` recommendation in the referenced report.

## Proof of Concept
Conceptual PoC (cannot be executed without deploying the Tron contracts and a mock ISMP host, but the mechanics are directly analogous to the original report's `AttackImp`):
1. Attacker deploys `MaliciousToken` with a fake `transfer(address,uint256)` that (a) always returns `true`-encoded data, and (b) inside its execution, attempts to trigger a second delivery/processing of the same `WithdrawalRequest` commitment (e.g., by having a colluding/duplicate relayer submission processed in the same transaction, or via any other function that reads `_orders[commitment][token]` before it is decremented).
2. Attacker calls `placeOrder()` using `MaliciousToken` as one of `order.inputs`, escrowing `_orders[commitment][MaliciousToken] = amount`.
3. When settlement/cancellation triggers `withdraw()`, the `token.call(transfer(...))` for `MaliciousToken` executes attacker code before `_orders[commitment][MaliciousToken] -= amount` runs.
4. If any reachable path re-invokes `withdraw()` (or reads/pays out based on) the same un-decremented `_orders` entry or the un-deleted `TRANSACTION_FEES` entry, the attacker receives duplicate payouts, draining protocol/other-users' escrow or fee-token balances. [1](#0-0) [2](#0-1)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
