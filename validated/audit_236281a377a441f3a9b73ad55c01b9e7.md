This is exactly the analog the report class predicts, and it is real: in `ShopifyAPI::Webhooks::Request`, the HMAC only signs the raw HTTP body (`to_signable_string` returns `@raw_body`) [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are never included in the signed bytes [2](#0-1) . `Registry.process` validates only that HMAC over the body via `Utils::HmacValidator.validate(request)` and then trusts `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` to dispatch to the handler and build `WebhookMetadata` [3](#0-2) . `HmacValidator.validate_signature` compares `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` against the received signature [4](#0-3) , so it only proves the body bytes are authentic, not the tenant-identifying header (`shop`).

### Title
Webhook `shop` header not covered by HMAC allows cross-tenant handler dispatch with valid signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `hmac_validator.rb` verifies the HMAC exclusively against that body. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values are pulled straight from unauthenticated HTTP headers and are never part of the signed payload.

### Finding Description
The equality the gem should enforce is: `shop` field trusted by `Registry.process` == `shop` value that was cryptographically bound by the HMAC. In this codebase that equality does not hold — the HMAC binds only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`), a value entirely outside the signed bytes. Any party capable of replaying (or lightly modifying headers of) a previously-observed, validly-signed webhook body for one shop can attach a different `shop-domain` header, and `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret. `Registry.process` then trusts the forged `shop` to construct `WebhookMetadata` handed to the app's own handler (`lib/shopify_api/webhooks/registry.rb:190-199`), so the app-level handler — which typically keys tenant data/session lookups off `data.shop` — can be made to act as if the event came from a different merchant than the one whose bytes were actually signed.

### Impact Explanation
This breaks the tenant-identity binding for a "Critical - cross-tenant access" scenario: a handler that looks up a merchant record, session, or access token using `WebhookMetadata#shop` can be pointed at another tenant's data using a signature that was never computed over that shop value. This is the direct structural analog to the reported bug class (a value acted upon that is not covered by the cryptographic proof), even though the specific field here is `shop`/`topic`/`webhook_id` rather than a block hash.

### Likelihood Explanation
Requires the attacker to have captured (or be replaying) one legitimately HMAC-signed webhook body — e.g., from a public endpoint log, an SSRF-adjacent leak, or their own shop's webhook traffic reused against another shop's identifier — and to control the HTTP headers of the request reaching the app's webhook endpoint (a realistic unprivileged capability for anyone who can send arbitrary HTTP requests to the app's public webhook route). No `api_secret_key`, access token, or privileged account is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them, e.g., via a canonicalized string built from headers + body) instead of relying on the header values being implicitly trustworthy just because the body HMAC matches.

### Proof of Concept
1. Attacker observes/captures a legitimately-signed webhook request for `shop-a.myshopify.com` with body `B` and valid `x-shopify-hmac-sha256` header `H = HMAC(secret, B)`.
2. Attacker resends the exact same body `B` and HMAC header `H`, but replaces `x-shopify-shop-domain` with `shop-b.myshopify.com` (a different tenant) and, if desired, a different `webhook-id`/`topic` combination that still parses against `B`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and it matches `H`, so validation passes [4](#0-3) .
4. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"shop-b.myshopify.com"` despite the body never having been signed in association with that shop [5](#0-4) .
5. Any app logic keyed off `data.shop` (e.g., loading `shop-b`'s stored access token/session to act on the webhook payload) now operates cross-tenant using data that was authenticated for `shop-a`.
