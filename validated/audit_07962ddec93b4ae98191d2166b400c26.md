### Title
Webhook `shop`, `topic`, `api-version` and `webhook-id` fields are not covered by the HMAC signature, allowing tenant-identity spoofing in otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version` and `webhook_id` values used by app webhook handlers entirely from unauthenticated HTTP headers, while `to_signable_string` (used by `HmacValidator.validate`) signs only the raw JSON body. This breaks the identity binding `HMAC(secret, bytes_verified) == bytes_the_handler_acts_on`: the bytes that are cryptographically verified (`raw_body`) are not the bytes that determine which shop/tenant the webhook is attributed to (`shop-domain` header).

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via: [1](#0-0) 

This call delegates to `Utils::HmacValidator.validate`, which computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `api_version`, and `webhook_id` — the values that get forwarded to the app's `WebhookHandler#handle` as `WebhookMetadata` — are read straight from HTTP headers that are never included in the signed bytes: [4](#0-3) [5](#0-4) [6](#0-5) 

The equality that should hold is: `bytes_verified_by_HMAC == bytes_that_determine_the_tenant (shop)`. In this implementation, `bytes_verified_by_HMAC = raw_body` while `tenant_identity = header["shopify-shop-domain"]`, an entirely disjoint, unauthenticated value.

### Impact Explanation
An attacker who legitimately receives real Shopify webhooks for their own store (any developer can install any public/dev app on their own trial shop and receive genuine, correctly-HMAC-signed webhook deliveries for that shop) can capture one such delivery and replay it to the app's webhook endpoint with the `shop-domain` (and optionally `topic`/`api-version`/`webhook-id`) header rewritten to point at a victim shop. Because the HMAC only covers the raw body, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the merchant's webhook handler with `WebhookMetadata#shop` set to the victim's domain while the handler code — following the gem's documented contract — trusts `data.shop` as the authenticated tenant identifier. Any host application that uses `data.shop` to look up/update per-tenant state (which is the gem's own recommended usage pattern) can be made to process attacker-supplied data under the wrong tenant's identity, i.e., cross-tenant data injection/confusion, without the app ever needing the victim's access token or secrets.

### Likelihood Explanation
Reasonably likely: the prerequisite (owning/controlling a real Shopify shop capable of receiving a genuinely-signed webhook from the target app) is available to any unprivileged internet user who can install a public app or set up a development store, requiring no leaked credentials, no `api_secret_key`, and no privileged account on the target tenant. Only standard HTTP header manipulation on replay is needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., concatenate headers + body before computing/verifying the digest), so that `to_signable_string` reflects everything the handler will act on. At minimum, document/require host apps to independently re-verify `shop` against a known/installed-shop list rather than trusting the header value as authenticated.

### Proof of Concept
1. Install the target app (or any app using this gem) on an attacker-controlled trial shop `attacker.myshopify.com`; trigger a webhook event so Shopify sends a legitimately HMAC-signed webhook POST with body `B` and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture the raw request (`B`, headers, HMAC signature `H`).
3. Replay the exact same POST to the app's webhook endpoint but change only the `x-shopify-shop-domain` header to `victim.myshopify.com` (leave `B` and `H` untouched).
4. `ShopifyAPI::Webhooks::Request#hmac` / `Utils::HmacValidator.validate` recompute the HMAC over `B` only, which still matches `H`, so `Registry.process` succeeds and calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, confirming that the tenant identity used by the handler was not covered by the HMAC that gated processing.
