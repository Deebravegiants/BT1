## Finding

### Title
Webhook HMAC only signs the request body, allowing shop/topic identity spoofing via header replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw request body only, while `Registry.process` trusts the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers to build the `WebhookMetadata` handed to the app's handler. The HMAC verifies "did this body come from someone who knows the API secret," not "does this shop/topic header match what Shopify actually signed for," breaking the intended identity binding between the verified payload and the shop/topic the handler acts on.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read directly from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.hmac` against a signature computed over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` performs that body-only HMAC check, then immediately trusts the header-derived `request.shop`/`request.topic`/etc. to dispatch to the registered handler: [4](#0-3) 

Because the HMAC signature is a function of the body alone, any `(body, hmac)` pair the attacker can obtain from a genuine Shopify webhook — e.g., a webhook fired for a shop the attacker controls (their own dev/trial store, which every unprivileged internet user can create) — remains valid for that same body regardless of which `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` headers accompany it. The attacker can replay the captured body+hmac to the app's public webhook endpoint while substituting the `shop-domain` header (and/or `topic`) for a victim shop. `HmacValidator.validate` still returns `true` (body untouched), and `Registry.process` will invoke the handler believing the data originated from the victim shop.

This is the same class of defect as the reported EIP-1155 issue: a check (`supportsInterface`/HMAC) is performed over one representation of the object while a different, unguarded field (`interfaceId` union / `shop` header) is what the caller actually relies on for identity — the two are not bound to each other.

### Impact Explanation
Handlers built on this library key their business logic off `WebhookMetadata#shop` (e.g., looking up the merchant's session/access token, updating per-shop state, billing, etc.), trusting it as authenticated because `Registry.process` gated it behind an HMAC check. Since the `shop` value is not actually covered by that HMAC, an attacker can make the host application process webhook data under an arbitrary victim shop identity — a cross-tenant confusion inside the app's webhook-handling code, satisfying the Critical "cross-tenant access" bar. It also allows spoofing `topic`, which can route a captured legitimate payload into a different (attacker-chosen) handler than Shopify intended.

### Likelihood Explanation
Exploitability only requires: (1) the ability to trigger a real webhook for a shop the attacker controls (trivial — any developer can install the app on their own store to receive a genuinely signed webhook), and (2) the ability to POST to the app's public webhook endpoint with modified headers (also trivial, since webhook endpoints are internet-reachable by design). No secret key, access token, or privileged account is required, matching the "unprivileged internet user" threat model.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, at minimum) in the signed content that `HmacValidator` verifies, or otherwise cryptographically bind them to the body/HMAC (e.g., verify the `shop` against a separate trusted channel, or require the webhook registration confirm the topic/shop combination server-side via a follow-up API call) rather than trusting header values that sit entirely outside the HMAC's scope. At minimum, document/require that consuming apps must independently validate `data.shop` against their own known-installed-shops list before acting on webhook data, since this gem does not bind it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook topic they can also observe on `victim-shop.myshopify.com` deployments (e.g., a common topic like `app/uninstalled` or any topic registered by the app).
2. Attacker captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)` — valid because it was genuinely computed by Shopify for the attacker's own installation.
3. Attacker replays the exact `(B, H)` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` recomputes the signature over `B` alone and it matches `H`, so `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` — the app now processes attacker-supplied data attributed to `victim-shop.myshopify.com`.
