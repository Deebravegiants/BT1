### Title
Interest accrual panics with `MathOverflow` once `borrowed × borrow_index` exceeds `i128`, permanently freezing a large high-utilization market - ([File: common/src/rates/simulate.rs])

### Summary
The analog to the go-ipfs "malformed input crashes the node" class is an arithmetic trap inside the mandatory interest-accrual path. Every mutating verb on a market (supply, borrow, withdraw, repay, liquidate, seize) first runs `global_sync` → `accrue_step`, which computes the original (unscaled) debt value via `scaled_to_original(env, borrowed, borrow_index)`. That is a `mul_div` of two RAY-scaled `i128` values; once the product `borrowed_scaled × borrow_index / RAY` leaves the `i128` domain it panics with `GenericError::MathOverflow`. Because the panic happens *before* any state is written, `last_timestamp` never advances, so every subsequent call fails the same way — the market is permanently bricked: no repayment, no withdrawal, no liquidation.

### Finding Description
- `common/src/rates/simulate.rs:60` — `accrue_step` calls `scaled_to_original(env, borrowed, borrow_index)` unconditionally on every compounding chunk. This is the panic site.
- `contracts/pool/src/interest.rs:20-33` — `global_sync` runs `accrue_chunk` in a loop before any market mutation; there is no way to skip accrual.
- `common/src/math/fp_core.rs:108-118` — `mul_div_half_up` widens to `I256` but panics with `MathOverflow` when the *result* doesn't fit `i128`; the borrow index cap `MAX_BORROW_INDEX_RAY = 10^36` is applied *after* the value multiplication (`update_borrow_index` clamps the index, not the `borrowed × index` product), so the value overflow fires first.
- `docs/reference/formulas.md:432-437` explicitly documents the gap: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."
- `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` demonstrates it end-to-end: a ~170-billion-whole-token market at 98% utilization on the XLM curve reaches the RAY-value cliff (borrow index ~x170, below the 10^9 cap), after which `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` — permanently.

An unprivileged user reaches this through the permissionless `update_indexes` entrypoint (or any supply/borrow/withdraw/repay/liquidate call) once the market's `borrowed × borrow_index` crosses the boundary.

### Impact Explanation
Permanent freezing of funds: once the overflow threshold is crossed, all suppliers' deposits and all borrowers' collateral in that market are locked forever, and bad debt can never be liquidated or cleaned. Unlike the IPFS crash (recoverable by restart/upgrade), there is no remediation path short of a contract upgrade — and `recapitalize`/`clean_bad_debt` also accrue first, so they are bricked too.

### Likelihood Explanation
Low-to-moderate. The attacker cannot accelerate ledger time; the freeze requires a very large market (order of 10^11 whole tokens near the token-to-RAY bound) sustained at high utilization for years while the borrow index compounds ~170×. However, it is a deterministic cliff: any market that grows large enough eventually hits it, the protocol emits no ceiling alarm, and governance cannot defuse it after the fact because `update_params` and every rescue verb accrue first.

### Recommendation
Bound the value computation rather than letting it trap: compute `borrowed_original`/`supplied_original` with a saturating or `I256`-checked variant, or clamp `borrowed` to `i128::MAX / borrow_index × RAY` before the multiply so accrual degrades gracefully (index cap engages, interest stops growing) instead of poisoning the market. Alternatively, make `global_sync` tolerate a `MathOverflow` step by advancing `last_timestamp` and pinning the indexes at their caps, keeping exits and liquidations live.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`: supply ~10^29 base units of an 18-decimal asset, borrow 98% of it against collateral, advance ledger time year-by-year calling `update_indexes` until `try_update_indexes` returns `MathOverflow` (borrow index ≈ x170, below `MAX_BORROW_INDEX_RAY`); then `try_withdraw(1)` and `try_repay` both fail with `MathOverflow`, confirming the freeze is permanent and reachable by an unprivileged caller.
