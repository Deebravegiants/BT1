### Title
Native-token overpayment on `EvmHost.dispatch`/`fundRequest` gets permanently stranded in the Host contract with no sweep path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)` and `fundRequest` are `payable` functions that forward the caller's entire `msg.value` into `IUniswapV2Router02.swapETHForExactTokens`, requesting an *exact* token output (`post.fee`/`get.fee`/`amount`). [1](#0-0) [2](#0-1)  The standard `swapETHForExactTokens` implementation only spends `amounts[0] <= msg.value` and refunds the unspent difference to its immediate caller — here that caller is `EvmHost` itself, not the original transaction sender. `EvmHost` has no logic that forwards this refunded ETH back to the user, and no admin/governance function exists to sweep stray native balance out of the contract (governance withdrawal via `IHostManager` only covers the ERC-20 `feeToken`, never native currency). Any excess native value sent to `dispatch`/`fundRequest` beyond the exact swap input becomes permanently locked in `EvmHost`, mirroring the RCOrderbook analog of a payable function with no corresponding withdraw path.

### Finding Description
- `dispatch(DispatchPost)` (called by any unprivileged `HyperApp`/user who wants to pay in native token) does: `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. [1](#0-0) 
- `fundRequest` follows the identical pattern for topping up relayer fees. [2](#0-1) 
- `dispatch(DispatchGet)` repeats the same pattern. [3](#0-2) 
- In UniswapV2Router02's canonical `swapETHForExactTokens`, only the exact input amount required for `amountOut` is consumed; any `msg.value` surplus is refunded via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Because `EvmHost` is the direct caller of the router (not the end user), this refund lands on `EvmHost`'s own balance, not the original sender's wallet.
- `EvmHost` defines a `receive`/`fallback` (confirmed present via grep, two matches) so the refund does not revert the whole dispatch transaction — it silently accumulates as stray native balance.
- Nowhere in `EvmHost.sol` or the governance-facing `IHostManager` interface is there a function to withdraw native ETH/xDAI/MATIC balance; `IHostManager.updateHostParams`/withdrawal flows operate on the `feeToken` ERC-20 only. [4](#0-3) 

This is functionally identical to the referenced report's bug class: a `payable` function (`dispatch`/`fundRequest`) can receive/retain native currency with no corresponding withdraw function, so value gets locked in the contract permanently.

### Impact Explanation
Any user or integrating `HyperApp` who overestimates the native-token amount needed to cover a swap into `feeToken` (common given Uniswap price movement, MEV/sandwiching, or simply passing a generous `msg.value` buffer) has the excess silently swallowed by the Host contract with no recovery mechanism — not for the user, not even for protocol governance. Given this path is reachable by every unprivileged dispatcher of POST/GET requests and every fee-request funder, the aggregate value at risk grows continuously and is unrecoverable, constituting a permanent freezing-of-funds condition.

### Likelihood Explanation
High reachability: `dispatch`/`fundRequest` are the primary, unprivileged entry points used by every message-dispatching integrator paying with native token; the developer docs explicitly recommend sending `msg.value` for native payments and instruct callers to estimate fees off-chain via a `quote()` helper that itself is documented as being imprecise/sandwichable, making overpayment a realistic and recurring occurrence rather than a contrived edge case. [5](#0-4) 

### Recommendation
Have `EvmHost.dispatch`/`dispatch(DispatchGet)`/`fundRequest` capture the actual amounts spent (`swapETHForExactTokens` returns `amounts[0]`) and explicitly forward any leftover native balance back to `_msgSender()` after the swap, rather than relying on the router to refund the immediate caller. As defense in depth, add a governance-gated sweep function for stray native balance on `EvmHost`, analogous to the fix applied elsewhere in this codebase for `SimplexPaymaster`'s stake-lock issue (`RequestKind.WithdrawAssets`/`_withdrawAssets` pattern). [6](#0-5) 

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: X}(post)` where `post.fee = F` and `X > amountIn required for F` (e.g., sends `2 ether` intending to cover a `1 ether`-equivalent fee, or simply overestimates due to price movement between quoting and execution).
2. Inside `dispatch`, `IUniswapV2Router02.swapETHForExactTokens{value: X}(F, path, address(this), ...)` consumes only `amountIn <= X` computed from pool reserves at execution time. [7](#0-6) 
3. The router refunds `X - amountIn` in native ETH to `msg.sender`, i.e., to `EvmHost`'s own address (since `EvmHost` is the router's caller), not to the original transaction sender.
4. `EvmHost` accepts the ETH (has `receive`/`fallback`) but never forwards it onward, and no function exists anywhere in `EvmHost.sol`/`IHostManager` to withdraw native balance.
5. The refunded `X - amountIn` is permanently locked in the `EvmHost` contract, repeatable by any caller, growing the stranded balance over time with no recovery path.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
