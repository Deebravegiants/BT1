### Title
Hostile pre-seed rebalance swap is budget-capped, letting an attacker permanently open the graduated HyperSwap LP away from the curve close price - (`packages/contracts/src/Bonding.sol`)

### Summary
The CVE analog is a bug class where an untrusted party creates a crafted object inside a *shared* resource that a trusted, privileged process later consumes without fully validating/repairing it — the guest plants a device file in the shared virtio-fs directory and the trusted host daemon later services it with elevated rights it should not extend. In alt.fun, the shared resource is the HyperSwap V2 `TOKEN/LT` pair, which is permissionlessly creatable and depositable by *anyone* before `Bonding.finalizeGraduation` runs. `finalizeGraduation`/`_seedUniswapV2Direct` is the trusted process that is supposed to "sanitize" that shared object (rebalance it back to the curve-close ratio) before permanently locking LP into it via `LPLock`. The rebalance step is bounded by an inventory cap that an attacker can exceed, so the sanitization is incomplete and the trusted process locks LP at a price the attacker chose rather than the price the curve actually closed at.

### Finding Description
`Bonding.triggerGraduation` / the threshold-crossing buy calls `_enterGraduating`, which caches `tokensForLP` and `ltFromPair` at the curve close price [1](#0-0) . `finalizeGraduation` is fully permissionless and calls `_seedUniswapV2Direct` to seed the HyperSwap pair with those cached amounts [2](#0-1) .

Before phase 2 runs, any unprivileged address can pre-create the `TOKEN/LT` pair and call `pair.mint(attacker)` against a self-funded hostile ratio, per the protocol's own documented exploit ("Regime 3 — mint pre-seed") [3](#0-2) . `_seedRebalancing` attempts to correct this by computing a no-fee swap `s` that would drive the pool back to the curve-close ratio via `_noFeeSwapInput`, then executing it directly on the pair via `_pairRebalance` [4](#0-3) .

The swap input is explicitly capped by `_swapBudget`, at 99% of `Bonding`'s own available inventory on the swap-in side (`_ltSwapInventory(lt, protectedLT)` or `Token` balance) — *not* by however much correction the attacker's pre-seed actually requires [5](#0-4) . Inside `_noFeeSwapInput`, the ideal correction `s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn` is silently truncated to `maxSwap` whenever the ideal value exceeds it [6](#0-5) . After this capped swap, `_routerDepositAndDispose` deposits the remaining inventory into the pool at whatever ratio the pool is *actually* at post-swap (the router's `quote()`-based split matches the *current*, still-skewed, pool ratio — it does not restore the curve-close ratio) [7](#0-6) . The resulting LP is then permanently locked by `LPLock.recordLock`, a one-shot call that `finalizeGraduation` cannot skip or retry [8](#0-7) .

The protocol's own documentation concedes the residual risk is unbounded for large enough pre-seeds: "for catastrophic pre-seeds beyond our budget capacity ... the alternative is bricking" [5](#0-4) , and separately states the ~50 bps open-price ceiling only holds for the "meaningful-reserve swap path" under normal conditions, while the dedicated end-to-end hostile-pre-seed test suite asserting attacker-no-profit / wrong-opening-price bounds was removed and "is no longer enforced by automated tests" [9](#0-8) . Since `tokensForLP` is capped at ≤250M tokens and `ltFromPair` is capped at whatever LT the curve raised (bounded by the $9K graduation threshold at launch-time exchange rate), `Bonding`'s own swap-side inventory is a small, predictable, on-chain-readable number. An attacker can size a `pair.mint` pre-seed with reserves large relative to that inventory (e.g. several times `tokensForLP`/`ltFromPair`) so that even a 99%-of-inventory rebalance swap cannot restore the target ratio, guaranteeing the graduated pool opens materially away from the curve's actual close price — a permanently mispriced pool that the attacker's own pre-existing LP position is calibrated to profit from via arbitrage, at the expense of every trader who buys/sells post-graduation through `Zap` at the skewed price.

### Impact Explanation
This meets the "LP seeded away from the curve close price" impact criterion explicitly listed as acceptable. Because `LPLock.recordLock` is one-shot and `finalizeGraduation` cannot be re-run once `Lifecycle.Graduated` is set, the mispriced pool state is permanent — there is no remediation path other than off-chain arbitrage closing the gap over time (during which the attacker's LP and any front-running arbitrageur profit at graduated-token holders' expense, and any trader whose swap executes before the price closes suffers a real economic loss). This is a High-severity issue: it requires no privileged role, is reachable by any address that can call `factory.createPair` / `transfer` / `pair.mint` against the not-yet-created HyperSwap pair, and directly and permanently damages the price integrity of every post-graduation trade routed through `Zap`.

### Likelihood Explanation
Moderate-to-high likelihood. The exact `tokensForLP`/`ltFromPair` values are only finalized during phase 1 (`_enterGraduating`), but they are readable on-chain the moment `TokenGraduating` is emitted and before `finalizeGraduation` (permissionless, no time bound, keeper-driven at "~60s") lands. An attacker monitoring for `TokenGraduating` events has a window to front-run `finalizeGraduation` with a hostile `pair.mint` sized specifically to exceed the 99%-of-inventory swap cap for that token. The attack requires capital proportional to the token's own curve-raised inventory (bounded, but for smaller/earlier-launched tokens with modest `ltFromPair` this capital requirement is low), and the protocol's own docs concede this exact scenario is real ("catastrophic pre-seeds beyond our budget capacity") and no longer covered by regression tests.

### Recommendation
- Size the rebalance swap budget relative to the required correction magnitude (or the pre-seed's own reserves), not solely to `Bonding`'s available inventory, so the pool ratio can always be fully restored regardless of how large a hostile pre-seed is, even if that means proportionally scaling down `tokensForLP`/`ltFromPair` deposited that round.
- Alternatively, cap the *acceptable pre-seed skew* itself: if `_pairRebalance`'s capped swap cannot bring the post-swap ratio within a strict bps tolerance of the cached curve-close ratio, abort the deposit into the existing pair and instead deploy a fresh pair (or queue for a keeper-assisted remediation) rather than silently locking LP at an arbitrarily skewed price.
- Restore and re-enable the removed `test/HostilePreSeed.t.sol` wrong-opening-price / attacker-no-profit / leftover-recovery assertions as CI-blocking regression tests, since the AGENTS.md documentation itself flags these properties as currently unverified.

### Proof of Concept
1. Creator launches `TOKEN` via `Zap.createToken`; trading proceeds until the curve crosses the graduation trigger and `Bonding._enterGraduating` fires, caching `tokensForLP`/`ltFromPair` and emitting `TokenGraduating` (state: `Lifecycle.Graduating`).
2. Before any keeper/rando calls `finalizeGraduation`, attacker (unprivileged EOA) calls `hyperSwapFactory.createPair(TOKEN, LT)`, transfers a large, deliberately skewed amount of `LT`/`TOKEN` dust-far-exceeding `Bonding`'s cached `ltFromPair`/`tokensForLP` inventory (e.g. 50–100x), and calls `pair.mint(attacker)` to receive LP at that hostile ratio.
3. Any address (e.g. a keeper, or the attacker themselves) calls `Bonding.finalizeGraduation(TOKEN)`. Inside `_seedRebalancing`, `_pairRebalance`'s swap is capped at `_swapBudget(inventory)` (99% of `Bonding`'s own `ltFromPair`/`tokensForLP`), which is far smaller than what's needed to correct a 50–100x skew; the post-swap pool ratio remains materially away from the curve-close ratio.
4. `_routerDepositAndDispose` deposits the remaining balanced-subset inventory at this still-skewed ratio via `router.addLiquidity(..., 1, 1, lpLock, ...)`; `LPLock.recordLock` permanently locks this mispriced LP.
5. Post-graduation, any trader calling `Zap.buy`/`Zap.sell` (routed through `_swapOnUniswapV2`) executes against the mispriced pool until arbitrage (largely captured by the attacker's own pre-existing LP position) closes the gap, realizing a permanent value transfer from traders/creator to the attacker.

Note: I was unable to execute this scenario against the Foundry test suite (e.g. `test/TwoPhaseGraduation.t.sol`'s `test_hostilePreSeed_*` tests) to empirically confirm the exact bps deviation for a pre-seed sized several multiples beyond `_swapBudget`'s cap, since I only have read access to the indexed codebase and not a live execution environment. The root-cause code paths (`_swapBudget`, `_noFeeSwapInput`'s truncation, `_routerDepositAndDispose`'s post-swap-ratio deposit) are directly cited above and confirm the mechanism exists; a Devin session with repo/test execution access would be needed to produce concrete numeric PoC output.

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
```

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```markdown
#### Regime 3 — mint pre-seed (the actual exploit)

Attacker called `pair.mint(attacker)` against a self-funded dust seed. Reserves are non-zero at a hostile ratio. We:

1. **Compute the swap input** that would drive the pool ratio back to the curve-close ratio under the no-fee constant-product model: `s = sqrt(reserveIn · reserveOut · targetN / targetD) − reserveIn`, capped at our per-side budget. Implementation in `_noFeeSwapInput`. Closed-form via OZ `Math.sqrt + Math.mulDiv`; no binary search, no convergence loop.
2. **Execute the swap directly on the pair** via `pair.swap(amount0Out, amount1Out, address(this), "")`. We read the output from the pair's own fee-aware `getAmountOut` quote and pass it as the output. **Bypasses the router** — HyperSwap's V2 router has no canonical `swapExactTokensForTokens` (see "HyperSwap Router non-standard ABI" above). Same direct-to-pair pattern Zap uses for post-grad user swaps. Implementation in `_pairRebalance`.
3. **Deposit the remaining inventory** via `router.addLiquidity(rest, 1, 1, lpLock, ...)`. The router's `quote()`-based optimal split deposits only the matched-ratio subset; neither side becomes a `min()` donation. Off-ratio remainder stays in `Bonding`. The router's `addLiquidity` IS canonical V2 on HyperSwap (verified selector `0xe8e33700`), so this leg is safe to keep on the router and gets the `quote()` math for free.
4. **Dispose the off-ratio remainder.** TOKEN side burned (`Bonding` is the Token owner). LT side auto-swept to the protocol owner by `finalizeGraduation`'s post-sweep — emits `LTRescued(lt, owner, amount)` for observability. See "Per-graduation LT isolation" below.

Why the **asymmetric router usage** (pair for swap, router for addLiquidity): the swap is unsafe to send through the router because HyperSwap's swap ABI is non-standard; the deposit IS safe because HyperSwap's `addLiquidity` ABI is canonical AND the `quote()`-based optimal-split logic is the part that defuses the LP-capture attack. We get the best of both — no HyperSwap-specific footgun on the swap, no reimplementation burden on the deposit.

Why the fourth step matters: **mass conservation prevents fixing both the price and the deposit.** If the pool starts off-target and our inventory is on-target, we cannot end with both at-target reserves AND a fully-deposited inventory — something has to absorb the imbalance. Step 4 is where it goes.
```
