Confirmed: `Bonding.transferCreator` (packages/contracts/src/Bonding.sol:738-748) only reassigns `info.creator` for *future* fee attribution — it does not, and cannot, move an already-accrued `creatorBalance[oldCreator]` in `FeeVault`. Combined with `FeeVault.claim()` (packages/contracts/src/FeeVault.sol:127-135), which pays out strictly to `msg.sender` with no destination-address parameter, this gives the exact reachable analog.

### Title
Creator's already-accrued fees are permanently frozen in FeeVault if their address is blacklisted by USDC, since `claim()` has no destination parameter and `transferCreator` cannot move past balances - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` pays out `creatorBalance[msg.sender]` exclusively to `msg.sender`, with no way to specify an alternate recipient address. USDC (the sole fee asset in this system) implements an address blacklist. If a token creator's wallet is ever blacklisted by USDC — for any reason, on-chain or off — that creator can never again call `claim()` successfully, because the final `safeTransfer(msg.sender, amount)` will revert every time regardless of retries, gas, or time elapsed (short of USDC unbanning the address).

### Finding Description
`FeeVault.claim()`: [1](#0-0) 
zeroes `creatorBalance[msg.sender]` only after transferring, and the transfer target is hard-coded to `msg.sender`. There is no `claim(address to)` variant and no owner/creator-controlled override for the destination of an individual creator's pooled balance.

The only mechanism that could conceivably let a creator redirect their earnings to a fresh address is `Bonding.transferCreator`: [2](#0-1) 
but this only updates `info.creator` for a specific token, which changes *future* fee attribution in `FeeVault.accrue` (keyed by `Bonding.tokenInfo(token).creator`). It does nothing to the creator's existing `creatorBalance[oldCreator]` entry in `FeeVault`, which remains permanently tied to the old (now-blacklisted) address and is only claimable by that same address calling `claim()`.

This is a direct structural analog of the reported bug class: `withdraw()`/`removeCollateral()` in the referenced report hard-code the recipient to the caller with no override, so a blacklisted caller can never retrieve funds that are otherwise fully solvent and sitting in the contract. Here, `FeeVault.claim()` has the identical shape — no destination parameter — while the sibling function `claimProtocol()` is explicitly protected against this exact class of bug because it always pays the admin-settable `feeTo`, which the owner can update away from a blacklisted address: [3](#0-2) 
No equivalent recovery path exists for `creatorBalance`.

### Impact Explanation
A creator's earned 0.25% share of every buy/sell fee on their launched token(s), tracked in `creatorBalance[creator]` and backed 1:1 by USDC actually held in `FeeVault` (enforced by the `UnderfundedAccrual` check in `accrue`), becomes permanently unclaimable the moment that creator's address is blacklisted by USDC. This is a genuine, solvent balance that is otherwise fully backed — the funds sit in the vault forever, unable to be swept (they are correctly counted as "backed" by `totalAccruedCreator`, so `sweepDonations` cannot touch them either), constituting a permanent freeze of creator funds.

### Likelihood Explanation
USDC blacklisting is a real, externally-triggerable event (OFAC sanctions, exchange/compliance flags, court orders) entirely outside the creator's or protocol's control, and this is the sole settlement asset for all fees in the system. Any creator who accrues fees and is later blacklisted — or whose wallet happens to already be on a blacklist by the time they try to claim — hits this permanently, with no admin remediation path (the owner cannot re-route `creatorBalance[creator]`, unlike `feeTo`).

### Recommendation
Add a destination parameter to the creator claim path, e.g. `claim(address to)` (or an owner/self-service `reassignCreatorBalance(address oldCreator, address newCreator)` gated appropriately), so a creator — or in emergencies, governance — can redirect a stuck `creatorBalance` to a non-blacklisted address, mirroring the flexibility already given to `claimProtocol()` via the admin-settable `feeTo`.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`; trading accrues fees, and `FeeVault.accrue` credits `creatorBalance[C] += X` USDC, fully backed per the `UnderfundedAccrual` check.
2. Circle blacklists `C`'s address in USDC (a real-world, protocol-external event).
3. `C` calls `FeeVault.claim()`. `amount = creatorBalance[C]` succeeds, `creatorBalance[C]` is zeroed, but `$.usdc.safeTransfer(msg.sender, amount)` reverts because USDC's `transfer` reverts for a blacklisted recipient — reverting the whole transaction, so `creatorBalance[C]` remains `X` (Solidity state rollback), but is now permanently unreachable since every future `claim()` call fails identically.
4. `C` calls `Bonding.transferCreator(token, newAddress)` — this only changes attribution for *future* accruals; `creatorBalance[C] == X` is untouched and remains locked forever in `FeeVault`, with no function anywhere in the codebase capable of moving it to `newAddress`.

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```
