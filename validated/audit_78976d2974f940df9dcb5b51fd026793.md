### Title
Missing storage gap in upgradeable cross-chain token bridge base contracts risks storage collision on upgrade - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol], [File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable` are the SDK's base contracts for deploying cross-chain, mint/burn (or lock/unlock) token bridge applications behind upgradeable proxies. Neither declares a storage gap (`uint256[N] private __gap;`) at the end of its state-variable layout, unlike the repo's other upgradeable proxy contract, `SimplexPaymaster`, which does reserve one.

### Finding Description
Both contracts follow the standard OpenZeppelin upgradeable pattern: they use `Initializable`, disable initializers in the constructor, and are meant to be deployed behind a proxy (UUPS/Transparent), as confirmed by the documented migration flows for `OFTUpgradeable`/`OApp` deployments in `docs/content/developers/evm/lz-endpoint.mdx`.

`HyperFungibleTokenUpgradeable` declares its own storage after inheriting `ERC20Upgradeable`, `ERC165Upgradeable`, `HyperApp`, `OwnableUpgradeable`, and `PausableUpgradeable`: [1](#0-0) 

`WrappedHyperFungibleTokenUpgradeable` similarly declares its own state (`_host`, `_dispatcher`, `_underlying`, `_isWeth`, `_supportedChains`) directly after its inherited upgradeable bases, with no gap reserved: [2](#0-1) 

Neither contract ends with a `__gap` array, in contrast to `SimplexPaymaster`, which explicitly reserves one for exactly this reason: [3](#0-2) 

Because these two contracts are explicitly designed to be extended (each token deployment is "its own bridge application", per the contract's own NatSpec) and deployed behind an upgradeable proxy, any future upgrade to the base contract that appends new state variables (e.g. new bridge configuration, fee accounting, or additional chain metadata) will silently write into the storage slots that a derived/extended token contract, or a later-appended variable in `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` itself, already occupies. This is the classic Solidity upgradeable-storage-collision hazard the OpenZeppelin `__gap` convention exists to prevent.

### Impact Explanation
A storage collision in these contracts corrupts the accounting for a live cross-chain token bridge: `_supportedChains` (which peer module a given `dest` chain routes to), `_host`/`_dispatcher` (the trusted ISMP host and call dispatcher addresses used to authorize `onAccept` message delivery and dispatch mint/burn requests), or the ERC20 balance/allowance storage inherited via `ERC20Upgradeable`, could be overwritten by a subsequent implementation upgrade. Depending on which slot is clobbered, this can permanently freeze cross-chain transfers (peer/host pointers zeroed out), redirect a `send`/mint to an attacker-controlled destination, or corrupt token balance accounting on a token that burns on the source chain and mints on the destination chain — a direct unbacked-mint / fund-freezing class of impact for a token bridge application.

### Likelihood Explanation
Likelihood depends on Polytope Labs (or any third party who deploys these SDK templates as their own upgradeable token bridge) shipping a future implementation upgrade that adds new state variables to the base contract. Given the contracts are actively documented as an SDK for third parties to build "their own bridge application" and the sibling `SimplexPaymaster` contract in the same repo already anticipates this need with an explicit `__gap`, it is reasonably likely that these two token contracts will also receive appended state in a future release, at which point any proxy already deployed on top of the current layout is at risk.

### Recommendation
Add a storage gap array (e.g. `uint256[50] private __gap;`) at the end of the declared state variables in both `HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable`, sized to leave room for anticipated future fields, matching the pattern already used in `SimplexPaymaster`. Any already-deployed proxies without this gap should have their next upgrade carefully checked with a storage-layout diff tool before adding new state.

### Proof of Concept
1. Polytope Labs (or a downstream integrator) deploys a `HyperFungibleTokenUpgradeable` proxy and configures `_host`, `_dispatcher`, and several `_supportedChains` entries.
2. A future release of the base contract adds a new state variable, e.g. `uint256 public bridgeFeeBps;`, appended immediately after `_supportedChains` because there is no `__gap` to consume first.
3. The proxy is upgraded to the new implementation via the documented `upgradeTo`/`upgradeToAndCall` flow.
4. The new `bridgeFeeBps` slot lands on top of whatever the next contract-specific storage slot held before (in a derived/extended token, or in future fields the maintainers add to the mapping's continuation slots), corrupting `_supportedChains` routing data or any subsequently-appended derived-contract state, without any explicit incompatibility being flagged at compile time.
