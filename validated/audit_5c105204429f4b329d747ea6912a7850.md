### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC signature it validates only covers the raw request body — not the `x-shopify-shop-domain` (or `shopify-shop-domain`) header that is later trusted as the tenant identity for the webhook.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC over that signable string and, if valid, dispatches to the registered handler using `request.shop`, which is read directly from the unauthenticated `shop-domain` header: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it with `secure_compare`: [4](#0-3) 

Because the `shop` header is never part of the signed content, the identity binding the gem's own documentation promises — "verify the request did indeed come from Shopify" — does not actually hold for the `shop` field: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" analog class: the equality that should hold is `hmac == HMAC(secret, raw_body ++ shop)`, but the gem only enforces `hmac == HMAC(secret, raw_body)`, leaving `shop` fully attacker-controlled at the HTTP layer.

### Impact Explanation
An unprivileged internet user who has ever received one legitimate Shopify webhook for their own store (a valid `raw_body` + `hmac-sha256` pair, trivially obtainable by installing the target app on their own shop) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `Registry.process` will validate successfully and hand the handler a `WebhookMetadata` whose `shop` is attacker-chosen, e.g.: [6](#0-5) 

Any host application that uses `data.shop` from `WebhookMetadata` to key a lookup, update tenant-scoped records, or route further authenticated API calls (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into acting on another merchant's data using attacker-supplied but "verified" webhook content — a cross-tenant confusion/injection primitive rooted entirely in this gem's incomplete verification.

### Likelihood Explanation
High for any consumer of the documented `Registry.process` API: the attacker needs no secrets, only a free trial/dev shop to obtain one legitimate signed webhook, and standard HTTP tooling to replay it with a modified header. The vulnerable code path is the exact one the docs instruct developers to use.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the signed payload used for verification, or independently confirm that the `shop-domain` header matches a shop the app is actually registered/installed for before trusting it, rather than relying solely on the raw-body HMAC.

### Proof of Concept
1. Install the app on attacker-owned shop `evil.myshopify.com`; Shopify sends a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S`).
2. Attacker POSTs to the app's public webhook route with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` over `to_signable_string` (`= B`), which matches `H`, so validation succeeds: [7](#0-6) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though nothing about that value was ever verified against Shopify, and processes it as if it were a genuine event for the victim's store.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
