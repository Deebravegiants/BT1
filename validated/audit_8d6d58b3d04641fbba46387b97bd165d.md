### Title
Emporium confused-deputy ETH drain via unconstrained `op.value` when ETH is omitted from `erc20TokenAddresses` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation[]` (including `op.value`, drawn from Emporium's own ETH balance) with no signature check when `stack.signerAddress == address(0)`, and only reconciles ETH balance changes for token indices present in `circomData.erc20TokenAddresses`. Because `dimensions.tokenNumber`/`erc20TokenAddresses`/`amountChanges` are fully attacker-chosen (including the degenerate zero-length case used for the "Emporium Min" proof path), an attacker can omit `address(0)` (ETH) from the array entirely, letting `op.value` siphon Emporium's existing ETH balance to an attacker-controlled endpoint with zero proof or Solidity-level accounting of that ETH movement.

### Finding Description
Broken equality: **ETH leaving Emporium via `op.value` (in `op.endpoint.call{value: op.value}(op.callData)`) != any entry of the attacker's own `circomData.amountChanges` constrained by their ZK proof.**

Trace:
- `EmporiumUpgradeable.runAction` decodes `stack` (including `ops[]`) from `circomData.externalActionData.externalActionMetadata` [1](#0-0) .
- `verifyWallet` marks the message used and, when `stack.signerAddress == address(0)`, returns immediately **without validating `stack.ops` at all** (no EIP-712 signature check on endpoint/callData/value) [2](#0-1) .
- In the "Stateless Interaction" branch, `op.endpoint.call{value: op.value}(op.callData)` is executed directly from Emporium's own balance — `op.value` is fully attacker-controlled (subject only to the self-consistency `calldataHash` check, not to any ownership/proof constraint on ETH) [3](#0-2) .
- After the ops loop, the only reconciliation is a per-token loop over `circomData.erc20TokenAddresses` comparing `balancesBefore`/`balancesAfter` adjusted by `deltaAmountChanges[i]` [4](#0-3) . If `address(0)` (ETH) is not present in that attacker-supplied array, no check on ETH ever runs.
- The same array (`circomData.erc20TokenAddresses`) is what Hinkal's top-level `transact` uses for its own balance-conservation check (`balanceDif == amountChanges[i] + utxoAmount`) — again, skipped entirely for indices/tokens not listed [5](#0-4) .
- `dimensionsCheck` only requires `erc20TokenAddresses.length == dimensions.tokenNumber` — it does not force ETH (`address(0)`) to be included, and `dimensions.tokenNumber` (hence array length) is entirely attacker-chosen, including `0` [6](#0-5) .
- `CircomDataBuilder.formInputForCircom` explicitly special-cases `erc20TokenAddresses.length == 0` for the Emporium action, switching to `formInputEmporiumMin`, which produces a minimal public-input set (`emporiumMessage`, `timeStamp`, `calldataHash`) with **no token/amount constraints whatsoever** [7](#0-6) . The corresponding `MainEVMCircuitMin` circuit only computes `message <== Poseidon(1)([messageSeed])` — it proves nothing about ownership of funds or amount conservation [8](#0-7) .

Exploit flow: attacker (any EOA) crafts `circomData` with `erc20TokenAddresses = []` (triggering the Min proof path), `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one stateless `op` whose `endpoint` is the attacker's own contract, `op.value = <Emporium's current ETH balance>`, `op.callData` any 4-byte selector that isn't `callHinkalWallet`/`doSendToRelay`. The attacker generates the trivial `MainEVMCircuitMin` proof (no real UTXO ownership needed) and calls `Hinkal.transact`. `performHinkalChecks` and `verifyProof` pass since no token/amount constraints exist for this path. Inside `runAction`, `verifyWallet` skips ops validation (`signerAddress == 0`), and `op.endpoint.call{value: op.value}(...)` drains Emporium's ETH balance to the attacker's contract. No balance/slippage check anywhere catches this because the token array is empty.

Existing guards that fail to prevent this: `performHinkalChecks`'s `calldataHash` check only verifies self-consistency of the submitted data, not that `op.value` corresponds to any deposited/withdrawn amount; `dimensionsCheck` never mandates ETH's presence in `erc20TokenAddresses`; `verifyWallet` explicitly bypasses signature/ops validation for `signerAddress == address(0)`; the balance-reconciliation loops in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` only iterate over the attacker-chosen (possibly empty) token array.

### Impact Explanation
Direct theft of Emporium's held native ETH balance (accumulated relay-fee dust, rounding remainders, or any ETH sent to Emporium's `receive()`), stolen by an unprivileged attacker with no real fund ownership required (Min-path proof requires no UTXOs). This is repeatable any time Emporium holds a non-zero ETH balance and matches the "theft of protocol/relay fees" High/Critical impact category — actual severity depends on how much ETH accumulates in Emporium, but the mechanism itself constitutes an unauthorized, proof-unconstrained movement of protocol-held native funds.

### Likelihood Explanation
Preconditions: Emporium must hold some ETH balance (plausible via relay-fee remainders, rounding, or direct `receive()` deposits since `receive() external payable {}` accepts unsolicited ETH from anyone) [9](#0-8) . Attacker cost is minimal — a single transaction with a self-generated trivial proof (Min circuit) and no capital requirement beyond gas. It is fully repeatable each time Emporium's ETH balance is replenished.

### Recommendation
Enforce that `address(0)` (native ETH) is always included and constrained in `circomData.erc20TokenAddresses`/`amountChanges`/`dimensions.tokenNumber` whenever any `EmporiumOperation.value > 0` is used, or reconcile ETH balance changes unconditionally (not only for tokens present in the caller-supplied array) inside `EmporiumUpgradeable.runAction`. Additionally, require `stack.ops` (including `op.value`) to always be signature-verified/hash-committed against the ZK-checked `amountChanges`/`erc20TokenAddresses`, even when `stack.signerAddress == address(0)`, so stateless ops cannot move value outside what the proof accounts for.

### Proof of Concept
Foundry fork test plan:
1. Deploy Hinkal + EmporiumUpgradeable; fund Emporium with ETH directly (`vm.deal(emporium, 5 ether)` or via a legitimate relay-fee flow) to simulate accumulated balance.
2. Deploy an attacker "sink" contract with a `receive()` that just accepts ETH.
3. Construct `circomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: sink, invokeWallet: false, value: 5 ether, callData: "0x" }], ... }`.
4. Generate a locally-produced `MainEVMCircuitMin` proof for the resulting minimal public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`), with correctly computed `calldataHash` per `CircomDataBuilder.getHashedCalldata`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `sink.balance` increased by `5 ether`, `emporium.balance` decreased by `5 ether`, while `sum(circomData.amountChanges) == 0` (trivially true since the array is empty) — demonstrating ETH left Emporium with zero corresponding proof-constrained `amountChanges` entry.

pragma circom 2.1.6;

include "../../node_modules/circomlib/circuits/poseidon.circom";

template MainEVMCircuitMin() {
  // Public inputs:
  signal input outTimeStamp;
  signal input calldataHash;

  // Private inputs:
  signal input messageSeed;

  // outputs:
  signal output message;

  message <== Poseidon(1)([messageSeed]);
}
