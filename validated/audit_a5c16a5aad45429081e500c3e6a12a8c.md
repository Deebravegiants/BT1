### Title
SimplexPaymaster's Chainlink price-feed reads lack L2 sequencer-uptime/grace-period validation - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` reads Chainlink `latestRoundData()` for both the native-asset oracle and each registered token oracle, checking only that the answer is positive and that `updatedAt` is within `maxOracleAge`. It never verifies an L2 sequencer-uptime feed or a `GRACE_PERIOD_TIME`, even though the paymaster is deployed across multiple Chainlink-supported L2s that use sequencers (Arbitrum, Optimism, Base per the mainnet chain list used elsewhere in the repo).

Only `answer <= 0` and `block.timestamp - updatedAt > maxOracleAge` are checked; there is no `sequencerUptimeFeed.latestRoundData()` call and no `GRACE_PERIOD_TIME` guard. Per Chainlink's documented L2 pattern (cited in the original report), consumers on Arbitrum/Optimism/Base must check that the sequencer has been up for at least the grace period before trusting a feed answer, because during a sequencer outage and the subsequent recovery window, feed updates can be stale or manipulable (e.g., transactions queued and replayed once the sequencer resumes, allowing outdated round data to be reported as fresh once the sequencer restarts and updates flush through).

This function is used to price every sponsored `UserOperation` — both for prefund validation (`_tokenPrice` in `validatePaymasterUserOp`) and for swap-slippage bounds — meaning any bundler/user submitting a UserOp during a sequencer outage/recovery window reaches this unguarded pricing path with no privileged access required.

### Impact Explanation
If an L2 sequencer this paymaster is deployed behind (per `tesseract/consensus/beefy/tests/mainnet_rotation.rs` the mainnet deployment set includes Arbitrum, Optimism, Base and Soneium) goes down and later recovers, Chainlink price feeds on that L2 can report values that predate the outage or are otherwise inconsistent with the true market price, yet still pass the `maxOracleAge` staleness check because `updatedAt` may be recent (the feed updates once the sequencer resumes, but the underlying price data reflects a window during which the true price could have diverged). Because `_tokenPrice`/`_getOraclePrice` directly drives how much ERC-20 (via `_prefund`/Permit2) is pulled from a user to cover native gas costs, an attacker (or an ordinary user acting opportunistically) submitting UserOperations during this window can cause the paymaster to under-charge for gas (draining paymaster treasury/token surplus) or over-charge users, i.e., a concrete funds-loss vector for the paymaster's treasury.

### Likelihood Explanation
Sequencer outages and subsequent grace-period windows are a documented, recurring operational event on Arbitrum/Optimism/Base, and this paymaster is designed to be fully permissionless — any bundler can submit a UserOperation during that window, with no special privileges needed to trigger `_getOraclePrice`. The vulnerability is passive (no attacker action required beyond normal usage timing), making exploitation likelihood non-trivial whenever a sequencer incident occurs on a chain where the paymaster is deployed.

### Recommendation
Add a Chainlink L2 sequencer-uptime feed check (per-chain, since only L2s with sequencers need it) in `_getOraclePrice` (or a wrapper called before it), reverting if the sequencer is down or if `block.timestamp - startedAt <= GRACE_PERIOD_TIME`, mirroring Chainlink's documented pattern, before trusting `latestRoundData()` from the native/token price oracles in `evm/src/utils/SimplexPaymaster.sol`.

### Proof of Concept
1. Deploy `SimplexPaymaster` behind an Arbitrum/Optimism/Base sequencer with a registered token oracle.
2. Simulate a sequencer outage followed by recovery (as documented by Chainlink, feeds served through the sequencer can report stale/inconsistent data during the recovery window while still satisfying `block.timestamp - updatedAt <= maxOracleAge`).
3. Submit a `UserOperation` with `paymasterData` selecting the affected token; `validatePaymasterUserOp` → `_tokenPrice` → `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:662-676`) accepts the stale price without any sequencer check.
4. The resulting `prefundAmount`/`tokenPrice` diverges from the true market price, allowing the submitter to pay less ERC-20 than the gas actually costs the paymaster (or the reverse, overcharging users), demonstrating fund loss driven purely by the missing sequencer/grace-period validation.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
