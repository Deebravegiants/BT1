### Title
Webhook HMAC only covers the request body, letting a captured webhook be replayed with a forged `shop`/`topic` header to impersonate another tenant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature Shopify computes over a webhook covers exclusively the payload bytes — it never binds the `shop`, `topic`, `webhook-id`, or `api-version` values that `Registry.process` extracts from unauthenticated HTTP headers and hands to the app's webhook handler.

### Finding Description
`Request#hmac` reads `shopify-hmac-sha256`/`x-shopify-hmac-sha256` and `Request#to_signable_string` returns `@raw_body` verbatim: [1](#0-0) 

`Registry.process` validates that HMAC against the body, then immediately trusts `request.shop` and `request.topic` (both read straight from headers, not signed) to build the `WebhookMetadata` that is dispatched to the app's handler: [2](#0-1) 

`Request#shop`/`#topic` come from `shopify_header`, which only reads whatever header value was supplied — there is no cryptographic tie between these values and the signature: [3](#0-2) 

Binding that is broken (as an equality that should hold but doesn't):
`shop_bound_by_hmac == shop_used_by_handler`
In reality: `shop_bound_by_hmac = ∅` (nothing) while `shop_used_by_handler = header["shopify-shop-domain"]` (attacker-controlled, unauthenticated).

Attack sequence:
1. An app installed on shop A sends webhooks to the app's public webhook endpoint. The receiving party for shop A (e.g., the merchant who installed the app, or anyone with read access to that endpoint's traffic) can observe a legitimate `(raw_body, hmac)` pair — this is a valid signature produced by Shopify using the app's `client_secret`, but the attacker doesn't need the secret, only a captured valid pair.
2. The attacker resends the exact same `raw_body` (and therefore the same valid `hmac`) to the app's webhook endpoint, but replaces the `shopify-shop-domain` and/or `shopify-topic` headers to claim it originates from shop B (or a different topic).
3. `HmacValidator.validate` succeeds because it only checks the body bytes against the secret — nothing about the headers is verified.
4. `Registry.process` builds `WebhookMetadata` using the forged `shop`/`topic` and invokes the app's handler, which will typically use `metadata.shop` to scope database writes/tenant state.

### Impact Explanation
This breaks the tenant boundary the app relies on: the HMAC is meant to prove "this webhook genuinely came from Shopify for this shop/topic," but it only proves the body bytes are unmodified. Any party who can observe one valid `(body, hmac)` pair (which is unavoidably visible to the shop that owns the webhook, or to anyone with visibility into the app's inbound traffic) can replay it while relabeling the `shop`/`topic`, causing the host application to process/store data under the wrong tenant. This is a cross-tenant data-integrity/impersonation issue in a security-critical primitive (webhook authenticity), qualifying as Critical severity (cross-tenant access) per the rules.

### Likelihood Explanation
Requires only a previously-observed legitimate webhook to the same app and the ability to send a crafted HTTP request to the app's public webhook endpoint — no access token, `client_secret`, or privileged credential is needed. The library provides no facility, and gives the host app no signal, to detect that headers are unauthenticated, so any host app that (reasonably) trusts `WebhookMetadata#shop`/`#topic` as authenticated is exposed by design of this gem's `Request`/`Registry` classes.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., by having `to_signable_string` concatenate the canonicalized headers with the body before hashing), so that `HmacValidator.validate` fails if any of these values are altered independently of the body.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` that writes to storage keyed by `data.shop`.
2. Capture one legitimate delivery: `raw_body = '{"id":1}'`, `x-shopify-hmac-sha256 = <valid HMAC over raw_body>`, `x-shopify-shop-domain = shopA.myshopify.com`, `x-shopify-topic = orders/create`.
3. Resend the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain = shopB.myshopify.com`.
4. Observe `ShopifyAPI::Webhooks::Registry.process` accepts the request (HMAC check passes since only body is signed) and invokes the handler with `shop: "shopB.myshopify.com"`, even though the payload was never issued for shop B.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
