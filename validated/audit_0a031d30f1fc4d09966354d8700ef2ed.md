### Title
Webhook `shop`, `topic`, and other identifying headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values purely from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. An attacker who controls (or has captured) one legitimately-signed webhook body/HMAC pair can retransmit it to the app's webhook endpoint with a forged `shop-domain` (and/or `topic`) header, and the gem will report it as an authenticated webhook for an arbitrary shop/topic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received `hmac` against `to_signable_string` (i.e. the raw body only) using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then dispatches to the handler using the **unverified** `request.shop` and `request.topic`: [4](#0-3) 

This is exactly the bug class of "a field acted on but not covered by the HMAC": the authentication boundary (HMAC over body, proving the payload originated from Shopify for this app's secret) does not bind to the tenant-identifying `shop` field that the host application/handler relies on to know *which* merchant the event belongs to.

### Impact Explanation
Because the `api_secret_key` is shared by a single app across all of its installed shops, any shop that installs the app receives correctly HMAC-signed webhooks for its own events. Such a shop owner (an "unprivileged" party relative to other tenants of the same app) can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop/topic. If the host application trusts the `shop` value returned by this gem to select the tenant record to update (a common pattern, since the gem's own webhook flow is the trust boundary offered to callers), this results in cross-tenant data confusion/injection — data or actions intended for the attacker's shop get attributed to (and can corrupt) a different merchant's records.

### Likelihood Explanation
Any merchant/developer who has installed the target app on their own shop can trivially capture a valid signed webhook (e.g., via any webhook debugging proxy) and replay it with a modified header using a simple HTTP client — no access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Bind the shop/topic identity to the signature verification, e.g., include the `shop`, `topic`, and `webhook_id` header values in the signable string that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `request.shop`/`request.topic` are not authenticated by the HMAC check and must be cross-checked by the caller against a known/expected shop before being used to select tenant state.

### Proof of Concept
1. Shop A installs the app; app sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC over `B` with the app's secret) and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker (owner of Shop A) captures `(B, H)`.
3. Attacker POSTs the same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different, victim shop that also uses the same app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `to_signable_string` (`B` only) — this succeeds since `B`/`H` are unmodified and valid. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, even though the payload actually originated from Shop A — a cross-tenant spoof accepted as authentic by this gem's own verification logic.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
