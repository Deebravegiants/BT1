### Title
Missing sender-binding check for `RequestState` messages allows any relayed peer to trigger orb state disclosure - (File: `orb-relay-client/src/client.rs`)

### Summary
The `PollerAgent::main_loop` dispatches incoming relay messages by first checking payload *type* (`RequestState`) before checking the message's declared sender (`src.id`) against the bound peer (`self.config.dst_id`). Every other message type is gated by an explicit `src.id != self.config.dst_id` check, but `RequestState` bypasses it entirely — directly analogous to `takeMultipleOneOrders` skipping the Complication-specific authorization check while applying the generic checks to everything else.

### Finding Description
In `orb-relay-client/src/client.rs:425-452`, incoming messages are matched like this: [1](#0-0) 

```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```
For every message type except `RequestState`, the code enforces that `src.id == self.config.dst_id` — i.e., the message must originate from the specific bound peer (the specific app session or specific orb) established at `connect()`. The `RequestState` branch, however, is evaluated first and unconditionally re-sends `self.last_message` (the last outgoing `RelayConnectRequest`, which can carry sensitive session state such as `AnnounceOrbId`, `SignupEnded`, capture-trigger state, etc.) regardless of `src.id`. This mirrors the root cause in the external report: a per-type dispatch path was added without applying the authorization/binding check that is enforced elsewhere.

Additionally, the code's own inline TODO at `orb-relay-client/src/client.rs:389-391` [2](#0-1)  confirms that a single relay connection can carry multiplexed messages from different sources ("avoid multiplexing messages from different sources"), which is the exact precondition required to exploit the missing check: an unrelated relayed peer can inject a `RequestState` payload with an arbitrary `src.id` and receive the orb's cached last message.

### Impact Explanation
The `last_message` re-sent on `RequestState` can be state normally scoped to a specific app-orb session pairing (`session_id`/`orb_id`), including signup lifecycle state (`AnnounceOrbId` with hardware/mode type, `SignupEnded`, capture trigger events). Because the check that would restrict this to the legitimate bound peer (`src.id == self.config.dst_id`) is skipped for this message type, any entity able to relay a `RequestState` payload through the shared connection can retrieve this session state without being the authorized counterpart — a cross-session state disclosure comparable in class (missing per-message-type authorization check) to the original Complication-check omission, though the concretely leaked data here is signup/session status metadata rather than biometric data itself.

### Likelihood Explanation
Exploitability depends on the relay server's routing behavior — whether it can deliver payloads to a client with `src.id` values other than the expected `dst_id` over the same stream, which the code's own TODO comment indicates is an open/known risk ("avoid multiplexing messages from different sources"). Given this is explicitly called out as unresolved in the code, the precondition is plausible under the current implementation, though full confirmation would require server-side relay routing behavior which is outside this repository.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState::matches` branch so that *all* incoming payload types — including `RequestState` — are validated against the bound peer identity before being processed, mirroring the fix pattern in the original report (apply the authorization check uniformly regardless of message/order type).

### Proof of Concept
1. Establish an orb-relay session between orb A and app session S (`Client::new_as_orb`/`new_as_app`), where `dst_id` on each side is bound to the other's id.
2. From an unrelated relayed peer with a different `src.id` (not equal to the orb's configured `dst_id`), send a `self_serve::app::v1::RequestState` payload through the relay to the orb.
3. Per `orb-relay-client/src/client.rs:436-440`, because the type check for `RequestState` occurs before the `src.id != self.config.dst_id` check, the orb responds with `self.last_message` (its last cached `RelayConnectRequest`) to the requester — a peer not bound to the session — regardless of `src.id`.
