### Title
Excess native token supplied to `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller and is permanently lost - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native-token payment for dispatch fees by calling `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` and forwarding the *entire* `msg.value`, but never capture the router's returned "amount spent" nor refund the unspent remainder back to the caller. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the reported `wfCashLogic.mintViaUnderlying` issue: a function accepts more native/underlying value than it actually consumes, and fails to correctly account for and return the residual to the payer, resulting in silent loss of user funds.

The standard `UniswapV2Router02.swapETHForExactTokens` implementation only spends up to `amountOut`'s equivalent input and refunds any unused ETH to `msg.sender` of that call — via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. When `EvmHost` calls this router, `msg.sender` from the router's perspective is `EvmHost` itself, not the original transaction sender (`_msgSender()`/`msg.sender` of `dispatch`/`fundRequest`). Consequently, any refund the router issues lands back in `EvmHost`'s own balance rather than being returned to the user who overpaid.

`EvmHost` never captures `amounts[0]` (actual ETH spent) from the swap call, nor does it compute `msg.value - spent` and forward it back to the caller. Contrast this with the sibling contract `IntentGatewayV2.placeOrder`, which performs the identical pattern correctly by capturing `amounts[0]`, decrementing `msgValue`, and explicitly refunding any leftover with `_sendValue(msg.sender, msgValue)`: [4](#0-3) 

`EvmHost.dispatch`/`fundRequest` lack this final refund step entirely — the swap call is fire-and-forget with the full `msg.value`, and any ETH not consumed by the swap simply accumulates as stray native balance on `EvmHost` with no path back to the user, and (based on the code inspected) no admin sweep/withdraw function was found for the accumulated native balance in `EvmHost.sol`.

### Impact Explanation
`dispatch()` (both POST and GET variants) is the core, permissionless, unprivileged entry point used by every single app/user/relayer-fee-payer sending a cross-chain message through Hyperbridge (reachable directly by any EOA or by any `HyperApp`/`IntentGateway`/bridge app that dispatches on a user's behalf with `msg.value`). Any caller who does not send the *exact* wei amount required for the fee-token swap (which is generically hard to predict precisely due to AMM price movement, since callers typically pad `msg.value` for slippage, exactly as the intended pattern in `IntentGatewayV2.placeOrder` anticipates and refunds) will have the unspent portion permanently stuck in the `EvmHost` contract. Because there is no accounting keyed to the depositor for that stray balance, this constitutes a permanent freezing/loss of user funds on every native-fee dispatch that overpays — a systemic, high-frequency loss vector at the very center of the protocol's dispatch path.

### Likelihood Explanation
This triggers on the ordinary, expected usage path: any caller quoting the fee client-side, adding slippage buffer (a standard practice to guard against AMM price movement between quote and execution, as documented and tested elsewhere in this exact codebase for `IntentGatewayV2.placeOrder`), and calling `dispatch{value: paddedFee}(...)` will overpay and lose the difference. No adversarial conditions are required; it manifests under completely normal operation whenever `msg.value` isn't the exact minimal amount the AMM consumes.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: capture the `amounts` array returned by `swapETHForExactTokens`, compute `refund = msg.value - amounts[0]`, and explicitly transfer `refund` back to `_msgSender()` (or `post.payer`/`get`'s payer) at the end of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. Caller A calls `EvmHost.dispatch{value: X}(post)` where `post.fee = F` (in fee-token units) and `X` is deliberately padded above the current market-rate ETH cost of `F` fee tokens (standard slippage protection, as advised in the project's own documentation for `placeOrder`'s `nativeValue`). [5](#0-4) 
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(F, path, address(this), block.timestamp)` executes; the router spends only `spent <= X` ETH to buy `F` fee tokens for `address(this)` (EvmHost), and refunds `X - spent` ETH to `msg.sender` of that call, i.e., to `EvmHost` itself. [1](#0-0) 
3. `dispatch()` proceeds to build/emit the `PostRequest` and returns, never inspecting the swap's return value or `address(this).balance`; `X - spent` wei of ETH is now permanently held by `EvmHost` with no accounting entry crediting Caller A and no sweep mechanism found in the contract.
4. Caller A has irrecoverably lost `X - spent` wei, repeatable on every dispatch call that isn't a perfectly exact-priced payment.
