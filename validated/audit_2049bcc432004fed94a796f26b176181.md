### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking that `Utils::HmacValidator.validate(request)` returns `true`. That validation is computed exclusively over the raw request body (`to_signable_string` returns `@raw_body` only), while the `shop` value that the handler receives and treats as the tenant identifier is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header. The HMAC therefore never binds "this body" to "this shop", breaking the equality `shop authenticated == shop acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so the computed HMAC covers nothing but the body bytes. `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers with no cryptographic tie to the signature: [3](#0-2) 

`HmacValidator.validate` computes `HMAC-SHA256(client_secret, verifiable_query.to_signable_string)` and compares it to the header-supplied `hmac`: [4](#0-3) 

`Registry.process` gates entirely on this body-only HMAC check, then forwards the header-derived, unauthenticated `shop` value straight to the app's webhook handler as the tenant identifier: [5](#0-4) 

Because `client_secret` (the HMAC key) is shared across **every** shop that has the app installed, any actor who can obtain one valid `(raw_body, hmac)` pair — e.g., by installing the app on their own store and capturing a real webhook delivery, since nothing in the raw body or signature restricts it to their shop — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because the header is not part of the signed material, and `Registry.process` will hand the handler `WebhookMetadata` claiming the spoofed shop: [6](#0-5) 

This is exactly the identity-binding class described in the report: a field acted upon (`shop`, used by the handler for tenant-scoped side effects such as data updates, un-installs, GDPR redaction, etc.) that is not covered by the authentication primitive (HMAC), so the "shop authenticated" and "shop the handler acts on" values can diverge under attacker control.

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata#shop` to select which tenant's data/session to mutate (a documented and expected usage pattern of this gem's webhook API) can be tricked into performing that mutation against a different, unrelated shop by an attacker who merely has legitimate install access to their own store. This is a cross-tenant integrity/confidentiality boundary break enabled purely by this gem's signature-verification implementation, meeting the "Critical - cross-tenant access" bar, since it requires no access token, no `client_secret`, and no privileged account beyond a normal app installation.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate installation of the target app (a standard unprivileged action), (2) capturing one raw webhook body + its HMAC (trivially obtainable by the attacker's own server, which already receives these deliveries), and (3) resending that body with a different `shop-domain` header value to the app's public webhook endpoint. No secret material or elevated privileges are needed, making this readily reachable by an ordinary internet-connected app installer.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is verified, not merely into fields read off unauthenticated headers:
- Include the `shop-domain` (and `topic`) header value in `to_signable_string`/the HMAC computation, or
- Independently verify the `shop-domain` header against a shop the app has actually installed/authorized before dispatching to the handler, or
- Document and enforce that webhook handlers must not use `WebhookMetadata#shop` as a trusted tenant key unless it has been independently corroborated (e.g., against session storage) before performing tenant-scoped writes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (fully legitimate, unprivileged action).
2. Shopify delivers a real webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac>`, and some raw body `B`.
3. Attacker replays the exact same request to the same endpoint, unchanged except the header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replay_headers)` is constructed; `hmac` is unchanged, `to_signable_string` (`= B`) is unchanged.
5. `Utils::HmacValidator.validate(request)` recomputes `HMAC(client_secret, B)` — identical to the original, unaffected by the header change — and returns `true`.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, i.e., the handler believes this data legitimately originated from `victim-shop`, even though it was fabricated by the attacker.         def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
