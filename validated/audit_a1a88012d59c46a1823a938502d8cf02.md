### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant spoofing of `WebhookMetadata#shop` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw JSON body (`to_signable_string` returns `@raw_body`), while `shop` is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` validates the HMAC and then forwards `request.shop` unmodified to the host app's handler via `WebhookMetadata#shop`, so the tenant identity delivered to the app is never covered by the cryptographic signature.

### Finding Description
The equality this code is supposed to guarantee is: `HmacValidator.validate(request) == true` implies `request.shop == the shop the signed body actually originated from`. In reality only the body is authenticated: [1](#0-0) 

- `hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header.
- `shop` is derived from the `shop-domain`/`x-shopify-shop-domain` header.
- `to_signable_string` returns only `@raw_body` — the exact bytes that were HMAC'd. [2](#0-1) 

`Registry.process` validates the HMAC over the body and then hands `request.shop` straight to the app's `WebhookHandler#handle`, with no binding check between the two: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app — it is not shop-specific. Because of this, `HmacValidator.validate` proves only "this body was HMAC'd with this app's secret," never "this body belongs to shop X." An attacker who legitimately installs the app on their own store (an ordinary, unprivileged action any internet user can perform) will receive genuinely-signed webhook deliveries for their own shop. That attacker can then replay the identical raw body to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) will still pass, because it only recomputes the HMAC over `@raw_body`, which is unchanged, and the forged `shop` header is not part of the signed material.

### Impact Explanation
This crosses a tenant boundary: the app receives a webhook it will process as belonging to shop B while the payload actually originated from shop A's install. Any host application logic that trusts `WebhookMetadata#shop` to select which tenant's session/access token/database record to act on (the documented and expected usage pattern, per `WebhookMetadata`'s `shop` field being the sole tenant identifier passed to handlers) can be tricked into writing attacker-controlled data into another shop's record, or misattributing events cross-tenant. This matches the Critical "cross-tenant access" category, since the vulnerability lets one shop's authenticated webhook traffic be re-labeled as another shop's traffic without possessing any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker: obtaining a valid `(raw_body, hmac)` pair requires nothing more than installing the target app on a store the attacker controls (a normal, permitted operation) and capturing one webhook delivery. Replaying that body with a modified `shop-domain` header requires only an HTTP client. No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Bind the shop identity to the signed content instead of trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string used for HMAC computation in `Request#to_signable_string`, or
- Require host applications to independently verify that `WebhookMetadata#shop` matches a shop with an active, previously-established session/install record before processing, and document this requirement clearly.
- At minimum, cross-check that the `shop` header value in a replayed request has not been reused across different registered webhook deliveries (e.g., dedupe by `webhook_id`), to reduce replay-based tenant confusion.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com`.
2. Shopify delivers a webhook (e.g. `orders/create`) to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body computed with the app's api_secret_key>`, and some JSON `raw_body`.
3. Attacker captures this raw body and HMAC header value.
4. Attacker sends a new HTTP request to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — it matches, since the body/HMAC pair is untouched — so validation passes: [4](#0-3) 
6. The host app's `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's JSON>, ...)`, causing the application to process attacker-controlled data under the victim shop's tenant identity.
