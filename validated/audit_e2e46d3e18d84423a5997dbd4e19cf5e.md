Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match in gateway HTTP server - (File: `core/services/gateway/network/httpserver.go`)

## Summary
`isAllowedOrigin` strips the `*.` prefix from a configured wildcard allowed-origin entry and then checks `strings.HasSuffix(originHost, allowedHost)` without verifying that a literal `.` immediately precedes the matched suffix. This lets an attacker-controlled hostname that merely ends with the allowed domain string (e.g. `evilexample.com` vs. allowed `*.example.com`) be treated as a legitimate subdomain, bypassing the intended origin restriction.

## Finding Description
`isAllowedOrigin` (lines 157–193) parses the request's `Origin` and each configured `CORSAllowedOrigins` entry, matches scheme and port exactly, then for wildcard entries strips `*.` and does a raw suffix check: [1](#0-0) 
`strings.HasSuffix("evilexample.com", "example.com")` returns `true` even though `evilexample.com` is not a subdomain of `example.com` (no dot boundary). This value flows directly into `handleRequest`, which reflects the raw `Origin` header into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true: [2](#0-1) 
`handleRequest` is registered as the handler for the gateway's externally-reachable JSON-RPC path and requires no authentication to reach this CORS check, so any client can set an arbitrary `Origin` header. There is no existing test covering the sibling-domain case; the test suite in `core/services/gateway/network/httpserver_test.go` only exercises true subdomains (`remix.ethereum.org` vs `*.ethereum.org`) and non-matching unrelated domains (`ethereum.remix.org`), not the `evilexample.com`-style suffix-only collision, confirming the gap is unaddressed. [3](#0-2) 

## Impact Explanation
This is a concrete allowlist-bypass in the gateway's internet-facing HTTP server. An operator who configures `CORSAllowedOrigins: ["*.trusted-domain.com"]` intends to scope cross-origin browser access to that domain and genuine subdomains. Due to the unanchored suffix comparison, a domain merely ending in the same characters (e.g., `evil-trusted-domain.com`) receives the same CORS trust, allowing a malicious site's JavaScript to read gateway responses and issue custom-header cross-origin requests that should have been blocked. This falls under the in-scope "allowlist bypass" impact category for the gateway.

## Likelihood Explanation
Exploitation requires only that the attacker control a domain string ending in the configured suffix and have it send a request with that `Origin` header — no authentication, credentials, or elevated role needed. The bug is a deterministic string-matching flaw, triggered on every CORS-enabled request that uses a wildcard entry, making it reliably reproducible.

## Recommendation
Replace the raw suffix check with a proper domain-boundary comparison: after stripping `*.`, only match if `originHost == allowedHost` or `originHost` ends with `"."+allowedHost` (i.e., require the dot separator). Add regression tests for sibling-domain collisions (e.g., `evilexample.com` vs `*.example.com`) in addition to the existing true-subdomain and unrelated-domain tests.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.example.com"]` (as done via `startNewServer` in `httpserver_test.go`).
2. Send a POST request to the server's configured path with header `Origin: https://evilexample.com`.
3. Observe the response contains `Access-Control-Allow-Origin: https://evilexample.com`, proving `isAllowedOrigin` incorrectly returned `true` for a non-subdomain that merely shares the suffix `example.com`.
4. This can be added as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, but asserting the header IS set (bug) versus the expected behavior (should be empty).

	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
