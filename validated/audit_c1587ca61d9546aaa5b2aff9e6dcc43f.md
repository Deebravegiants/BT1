### Title
Unvalidated `chain` field in `BandwidthPurchaseMsg` is parsed via naive delimiter-splitting `StateMachine::from_str`, letting an attacker-controlled string smuggle multi-part input into another chain's credit ledger key - (File: `modules/pallets/bandwidth/src/abi.rs`)

### Summary
`PurchaseMessage::try_from` (`modules/pallets/bandwidth/src/abi.rs:60-63`) takes the raw `chain` bytes out of an ISMP `PostRequest` body dispatched by a `BandwidthManager` contract, decodes it as UTF-8, and passes it straight into `StateMachine::from_str` (`modules/ismp/core/src/host.rs:344-426`) without any additional validation of its shape. `from_str` recognizes prefixes (`"EVM-"`, `"POLKADOT-"`, `"KUSAMA-"`, `"SUBSTRATE-"`, `"RELAY-"`, `"TNDRMINT-"`) and then does `name.split('-').last()`/`.get(1)` to recover numeric or 4-byte identifiers — a purely delimiter-based parse of a field the caller fully controls, structurally the same bug class as CVE-2017-9801 (an unsanitized, delimiter-bearing user field being interpreted by a downstream parser as multiple structured fields instead of an opaque value).

### Finding Description
`BandwidthManager.purchase()` on any source chain lets any caller supply `chain` as an arbitrary string (docs: `docs/content/developers/evm/bandwidth/overview.mdx:110` — "chain = 'EVM-8453'"), encoded into `BandwidthPurchaseMsg.chain` and dispatched cross-chain. On the pallet side (`modules/pallets/bandwidth/src/abi.rs:60-63`) this byte string is decoded as UTF-8 and handed to `StateMachine::from_str`.

`from_str`'s `RELAY-` arm is the most exposed: `let values = name.split('-').collect::<Vec<_>>(); ... let relay = values.get(1)...` (`modules/ismp/core/src/host.rs:366-386`). Because the split has no bound on the number of `'-'`-delimited segments and no validation that the whole string only contains exactly the expected number of segments, a `chain` string such as `"RELAY-CENJ-extra-1000"` or one engineered so `values.get(1)` and `values.last()` land on attacker-chosen bytes independent of what the human-readable name suggests, lets the caller pick the resulting `StateMachine::Relay { relay, para_id }` value largely freely, decoupled from the visually apparent chain name. The same applies to `SUBSTRATE-`/`TNDRMINT-` arms, which take `name.split('-').last()` — a string with an embedded extra `'-'` (e.g. `"SUBSTRATE-AB-CD"`) still parses (as long as the last segment is 4 bytes), silently discarding the attacker's own leading segment rather than rejecting the malformed shape.

The resulting `StateMachine` value becomes `PurchaseMessage.chain`, which the pallet then uses directly as the storage key for crediting a bandwidth subscription: `Self::push_subscription(&params.app_chain, ...)` / the analogous purchase-credit path keys `(app_chain, app)` from this parsed value (per `docs/content/developers/evm/bandwidth/overview.mdx:112`: "The pallet keys allowance storage by `(app_chain, app)` taken from the message body"). An attacker who can craft an arbitrary delimiter-laden byte string can therefore cause the parser to resolve to a `StateMachine` identity that does not match the intended, displayed chain — e.g., colliding with an existing registered `(chain, app)` bucket the attacker does not otherwise control, or producing malformed/unexpected relay identifiers that downstream systems must treat opaquely.

### Impact Explanation
Impact is bounded by what `BandwidthManager → pallet-bandwidth` interaction is trusted to do: credit `(app_chain, app)` byte allowances. Because `chain` selects the storage key with no cross-check against `request.source` or any registered mapping, and the parser's delimiter-splitting is not strict about the number/shape of segments, an attacker can construct payloads whose *effective* parsed `StateMachine` diverges from a naive reading of the string, enabling ledger-key confusion across unrelated `(chain, app)` buckets in the bandwidth-gate accounting (a `pallet-ismp` unauthenticated-mint-style data-integrity issue for bandwidth credits, not a direct fund theft). This is Medium severity: it corrupts application-level accounting/routing state reachable from a single unprivileged cross-chain message, but does not directly move tokens.

### Likelihood Explanation
High likelihood of reachability: any address that can call `BandwidthManager.purchase()` on a registered source-chain manager (an intentionally permissionless, fee-gated entry point) fully controls the `chain` byte string that flows unvalidated into `StateMachine::from_str`. No additional validation constrains the number of `'-'`-delimited segments before parsing.

### Recommendation
Validate `chain` strictly before use: require an exact, closed-form grammar (e.g., exactly one `'-'` for numeric variants, exactly two segments with fixed lengths for `RELAY-`), rejecting any string with unexpected extra delimiters rather than using `.last()`/`.get(1)` on an unbounded `split('-')` iterator. Consider replacing the free-text `chain` encoding with the same strict ABI-typed `StateMachine` representation used elsewhere (e.g., an explicit tagged enum/struct) instead of a Display-string round trip through untrusted bytes.

### Proof of Concept
1. Deploy/registration state: `pallet-bandwidth::set_manager(EVM-X, managerAddr)` is configured normally.
2. Attacker calls `BandwidthManager.purchase()` on chain `EVM-X`, supplying `chain = "RELAY-CENJ-1000-9999"` (or any string engineered with extra `'-'` segments) instead of a well-formed single relay id.
3. The dispatched `BandwidthPurchaseMsg.chain` bytes reach `PurchaseMessage::try_from` (`modules/pallets/bandwidth/src/abi.rs:60-63`), which calls `StateMachine::from_str` (`modules/ismp/core/src/host.rs:366-386`); `values.get(1)` and `values.last()` resolve to attacker-chosen segments of the crafted string rather than a clean, expected two-part identifier.
4. The resulting `StateMachine::Relay { relay, para_id }` is used as the `(app_chain, app)` storage key for the credited subscription, potentially colliding with or diverging from the identifier an observer of the raw string would expect.
