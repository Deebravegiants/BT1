### Title
`EngineMeter::charge_ref_time` never persists the fuel decrement, letting host-function costs be silently "refunded" to the wasmi engine's fuel counter - (File: substrate/frame/contracts/src/gas.rs)

### Summary
`EngineMeter::charge_ref_time` (called from `GasMeter::sync_to_executor`, itself invoked by the `sync_gas_after` code generated in `substrate/frame/contracts/proc-macro/src/lib.rs`) computes whether a fuel subtraction would underflow via `self.fuel.checked_sub(amount)` but discards the `Some(value)` result instead of writing it back to `self.fuel`. As a result, every time a contract calls a chargeable host function, wasmi's actual `Store` fuel is reset (via the generated `__caller__.set_fuel(fuel.into())` call) to the pre-call fuel value instead of a properly decremented one, effectively crediting the host function's weight cost back into the executor's instruction budget.

### Finding Description
The gas-sync protocol between wasmi and `GasMeter<T>` works as follows for every host-function call, generated by `sync_gas_before`/`sync_gas_after` in `substrate/frame/contracts/proc-macro/src/lib.rs` (lines 710-751):

1. On entry: `sync_from_executor(engine_fuel)` reads wasmi's current fuel, computes bytecode-consumed weight via `EngineMeter::set_fuel`, correctly persists the new fuel value (`self.fuel = fuel;`), and deducts the bytecode cost from `gas_left`. [1](#0-0) 
2. The host function body then charges its own weight cost (e.g. `HostFn` base cost plus operation-specific cost such as a storage write) directly against `gas_left` via `charge_gas`/`GasMeter::charge`.
3. On exit: `sync_to_executor(before)` computes `ref_time_consumed = before.0.saturating_sub(gas_left)` (the host-function-specific cost) and calls `EngineMeter::charge_ref_time(ref_time_consumed)` to translate that into fuel units and subtract it from the engine's fuel budget before writing it back into wasmi. [2](#0-1) 

The bug is in step 3's implementation: `self.fuel.checked_sub(amount)` is called only to detect underflow (`.ok_or_else(...)?`), but its `Some(new_value)` is dropped — `self.fuel` is never reassigned. [3](#0-2)  The function then returns `Syncable(self.fuel)` — the *unchanged*, pre-host-call fuel value — which the generated code writes straight back into the wasmi `Store` via `__caller__.set_fuel(fuel.into())`. [4](#0-3) 

Because wasmi's fuel was already at exactly that value when the host call started (having just been synced in step 1), this write-back is a no-op: the cost of every host-function call (`HostFn` overhead plus its specific weight, e.g. `seal_set_storage`'s storage-write cost) is deducted from `gas_left` (correct for fee/weight accounting) but is never subtracted from wasmi's own fuel counter that gates how much raw bytecode it is willing to execute before self-trapping with `OutOfFuel`. Each host call therefore effectively "refunds" its own weight cost back into the engine's execution budget. This deficit accumulates linearly with the number of host-function calls the contract makes; it is only caught when `gas_left` finally goes negative in a *future* `sync_from_executor` call (`checked_reduce` returning `None` → `Error::<T>::OutOfGas`) or in `WasmBlob::process_result` at call termination. [5](#0-4)  By the time that check fires, wasmi has already executed the extra bytecode instructions that the over-credited fuel permitted — this is genuine, already-spent CPU/wall-clock work that occurred beyond what the charged `gas_limit` should have allowed.

`set_fuel` (used for the executor→meter direction) is implemented correctly for comparison, confirming `charge_ref_time` is the outlier and the omission is a real defect rather than intentional design. [6](#0-5) 

### Impact Explanation
An attacker who deploys and calls an ordinary contract (fully permitted, unprivileged extrinsic path via `pallet_contracts::Call::call`/`instantiate`) can author Wasm bytecode that repeatedly invokes any chargeable host function (e.g. `seal_set_storage`) interleaved with compute-heavy loops. Each host call effectively "tops up" wasmi's remaining instruction fuel back to its pre-call level regardless of that call's real weight cost, letting the contract execute materially more Wasm instructions per extrinsic than its declared/charged `gas_limit` should permit before `OutOfGas` is finally raised (at the next host call or at the very end via `process_result`). The scoped impact is unauthorized extra Wasm execution steps beyond the charged gas limit — real CPU/wall-clock consumption not backed by the weight fee paid, i.e. a resource-accounting/DoS-adjacent bug, without affecting balances directly.

### Likelihood Explanation
Fully reachable by any unprivileged signed account through the standard `pallet_contracts` call/instantiate extrinsics — no special origin, proxy, or governance access required. The only precondition is authoring a Wasm module that calls a chargeable host function in a loop, which is trivial and requires no privileged capability. The bug is deterministic (not a race condition) — it triggers on every single host-function invocation, so the effect is easily repeatable and scales with the number of host calls made.

### Recommendation
Fix `EngineMeter::charge_ref_time` in `substrate/frame/contracts/src/gas.rs` to persist the decremented fuel value:
```rust
fn charge_ref_time(&mut self, ref_time: u64) -> Result<Syncable, DispatchError> {
    let amount = ref_time
        .checked_div(T::Schedule::get().ref_time_by_fuel())
        .ok_or(Error::<T>::InvalidSchedule)?;
    self.fuel = self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
    Ok(Syncable(self.fuel))
}
```

1. Construct a `GasMeter::<Test>::new(gas_limit)` with a known `gas_limit`/`ref_time_by_fuel`.
2. Call `sync_from_executor(engine_fuel)` simulating bytecode consumption, then simulate a host-function charge via `charge(...)` for some `HostFn`-equivalent token, then call `sync_to_executor(before)`.
3. Assert that the fuel value returned by `sync_to_executor` (the `Syncable` converted to `u64`) is strictly less than the fuel value passed into the preceding `sync_from_executor` call by an amount corresponding to the host-function charge, i.e. `new_fuel == old_engine_fuel - (host_cost / ref_time_by_fuel)`. Currently this assertion fails because `new_fuel == old_engine_fuel` unconditionally.
4. As an integration/fuzz-style test, deploy a fixture contract that loops calling `seal_set_storage` N times interleaved with a busy-loop, submit it with a fixed `gas_limit`, and measure actual wasmi instructions executed (e.g. via a wasmi fuel-consumption counter or wall-clock) versus the theoretical bound implied by `gas_limit`; assert total executed wasm fuel does not exceed `gas_limit / ref_time_by_fuel` — this assertion should fail on the current code and pass after the fix.
