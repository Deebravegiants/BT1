### Title
Webhook shop attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`/`webhook_id`/`api_version`) used to route and attribute an incoming webhook from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This breaks the binding `verified_bytes == bytes_used_to_identify_the_tenant`.

### Finding Description
`Registry.process` validates a webhook purely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`: [1](#0-0) 

`to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in the signed payload: [3](#0-2) 

`HmacValidator.validate_signature` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (i.e., the body only) using the app-level `Context.api_secret_key` — the same secret is valid for every shop that has installed the app, since webhook HMACs are not per-shop-keyed: [4](#0-3) 

After the HMAC check passes, `request.shop` is forwarded unauthenticated into `WebhookMetadata`, which is what host applications use to attribute the event to a specific merchant/tenant: [5](#0-4) 

Because the `shop` header is never part of the HMAC-verified bytes, any request bearing a body+HMAC pair that is valid for *some* shop (e.g., the attacker's own store, which they legitimately control and can freely receive real webhooks from) can be replayed to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body signature, and `Registry.process` will hand the forged `shop` value to the host application's handler as if it were authentic.

### Impact Explanation
This is a cross-tenant identity-binding break: the value used to route/attribute a webhook to a merchant tenant is not covered by the same signature that authenticates the payload. An attacker who owns one shop that has the app installed can forge webhook events (of any topic they can legitimately trigger in their own store, e.g. `app/uninstalled`, `orders/create`, `customers/data_request`, etc.) and relabel them as belonging to any other shop by simply changing the `shop-domain` header, since that header is not bound to the HMAC. Downstream host applications that key session/tenant lookups off `WebhookMetadata#shop` (the intended and documented usage pattern) can be tricked into processing attacker-controlled data under a victim shop's identity — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to have their own shop with the app installed (a normal unprivileged app install, not a privileged account or leaked secret) and the ability to intercept/replay their own outbound webhook HTTP request to the app's public webhook endpoint. No `api_secret_key`, access token, or other privileged credential of the target shop is needed — only observation of one's own legitimately-signed traffic and header manipulation.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values in the signable payload that `Utils::HmacValidator` verifies, or otherwise cryptographically bind the shop domain to the HMAC before it is trusted for routing/attribution in `Webhooks::Registry.process`. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be used by host apps without independent shop verification — but the safer fix is to make `to_signable_string` incorporate the shop/topic headers so `HmacValidator.validate` actually authenticates them.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` calls `to_signable_string` → returns `B` only, computes the same `H`, and `OpenSSL.secure_compare` succeeds: [2](#0-1) 
4. `Registry.process` proceeds and invokes the host app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)`: [5](#0-4) 
5. The host application, following the documented pattern of trusting `data.shop`, processes the attacker-supplied payload as an event belonging to `victim.myshopify.com`, achieving cross-tenant data injection/spoofing.
