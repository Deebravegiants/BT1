### Title
Webhook shop identity is trusted from an unsigned header while only the raw body is HMAC-covered - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that *the body bytes* were signed with the app's secret [2](#0-1) . The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signed material [3](#0-2) . `Registry.process` only checks the HMAC before dispatching, then forwards `request.shop` verbatim to the handler as the tenant identity in `WebhookMetadata` [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes_verified)` implies `shop == bytes_verified.shop`. In this gem that equality does not hold: `bytes_verified` is only the JSON body, while `shop` is taken from a header that is completely outside the signed scope. Any user who can capture one legitimate webhook delivery for their own shop (e.g., a merchant who has installed the app, or anyone able to observe/replay the raw POST from the network path to the app's public webhook endpoint) possesses a body + HMAC pair that will validate successfully regardless of which `shop-domain` header value accompanies it, because the header is not part of `to_signable_string`. Re-submitting the exact same body/HMAC with a different `x-shopify-shop-domain` header value passes `HmacValidator.validate` and is delivered to the handler tagged with the attacker-chosen shop. Since the app's `api_secret_key` is shared across every shop/tenant that installs the app, this is not merely a replay of one's own data — it is a means of impersonating an arbitrary victim tenant's webhook stream using data the attacker never needed elevated privileges to obtain.

### Impact Explanation
If the host application (as documented and intended by this gem's `WebhookMetadata`/`Registry` API) uses `data.shop` to select the tenant record to update (e.g., mark an order paid, deactivate a subscription, update inventory, disable a customer), an attacker can attribute genuine-looking, HMAC-valid webhook events to a shop they do not own. This is a cross-tenant data integrity/authenticity break rooted entirely in this gem's webhook verification contract (`Request`/`HmacValidator`), matching the "cross-tenant access" impact category, since the shop-identity claim carried in `WebhookMetadata` is not bound by the cryptographic check the gem performs.

### Likelihood Explanation
Exploitation requires only: (1) knowledge of one valid `(body, hmac)` pair for any topic the app handles (trivially available to any merchant with the app installed, since Shopify sends real webhooks to installed apps), and (2) the ability to POST to the app's public webhook endpoint with a forged `shop-domain` header, which is a normal HTTP client capability requiring no secret material, access token, or privileged account. No TLS interception or social engineering is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the signable material verified by `HmacValidator`, or have `Registry.process` independently authenticate the shop claim (e.g., cross-check it against a previously established, HMAC-verified per-shop secret/session rather than trusting the header outright). At minimum, document/require that consuming applications not treat `WebhookMetadata#shop` as authenticated unless additional binding is added, since today the identity used for tenant dispatch is not the identity covered by the cryptographic check in `lib/shopify_api/utils/hmac_validator.rb`.

### Proof of Concept
1. As a merchant with the app installed, trigger any webhook event (e.g., `orders/create`) and capture the raw request: `raw_body`, and the `x-shopify-hmac-sha256` header value.
2. Replay a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) [5](#0-4) [1](#0-0)  — validation succeeds because the body/HMAC pair is unchanged.
4. `handler.handle` receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to attribute the attacker's own event data to the victim tenant.
