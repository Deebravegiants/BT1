### Title
Escrow settlement in `IntentGatewayV2`/`ExtrinsicIntents` permanently freezes funds when the beneficiary is blacklisted by the escrowed token, with no pull-based recovery path - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_withdraw()` in `IntentsBase.sol` (and the equivalent `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) unconditionally pushes escrowed input tokens to a `beneficiary` address baked into the cross-chain settlement message via `safeTransfer`/`transfer`. If that token implements an address blacklist (e.g. USDC/USDT-style tokens) and the beneficiary becomes blacklisted, the transfer reverts every time the message is delivered or retried, and the escrow can never be released — a direct structural analog of the Cooler `repayLoan()` griefing bug, where a blacklistable-token push-transfer to an attacker-influenced or externally-blacklistable address permanently blocks fund release.

### Finding Description
`_withdraw()` iterates the `WithdrawalRequest.tokens` and does a direct push transfer to `beneficiary`: [1](#0-0) 

`beneficiary` is fixed inside the ISMP message body at the time the order is filled or cancelled, and cannot be changed afterwards:
- On a cross-chain fill, `beneficiary = msg.sender` (the filler/solver) is embedded in the `RedeemEscrow` message dispatched back to the source chain: [2](#0-1) 
- On a destination-side cancellation, `beneficiary = order.user` is embedded in the `RefundEscrow` message: [3](#0-2) 

Both message kinds are delivered via `onAccept()`, which calls `_withdraw(..., true)` unconditionally: [4](#0-3) 

`EvmHost.dispatchIncoming(PostRequest, ...)` invokes `onAccept` via a low-level `.call`; if it fails the receipt is deleted "so that it can be retried": [5](#0-4) 

This retry mechanism assumes transient failures. But if the escrowed input token is a blacklistable stablecoin (USDC/USDT) and `beneficiary` (the filler or the user) has been placed on that token's blacklist — whether through unrelated compliance action, sanctions, or the address itself becoming flagged after order placement — every retry of the identical message replays the same `safeTransfer(beneficiary, amount)` call and reverts identically forever. There is no alternate path to change the beneficiary, pull the funds, or reroute them: `SweepDust` only sweeps unrelated protocol-dust balances via `_params`/Hyperbridge governance, not the per-commitment `_orders[commitment][token]` escrow tied to a specific `WithdrawalRequest`.

The Tron variant has the identical push-and-revert pattern: [6](#0-5) 

### Impact Explanation
This results in a guaranteed, permanent freeze of the escrowed input tokens for that order:
- **RedeemEscrow case**: the solver already delivered the output tokens to the user on the destination chain (fulfilling their obligation), but if the solver's own address is later blacklisted on the input token, the solver can never redeem the escrowed input tokens — total, irrecoverable loss of the filled order's funds to the protocol/user, permanently locked in the gateway contract.
- **RefundEscrow case**: if `order.user` is blacklisted on the escrow token (or becomes blacklisted between order placement and cancellation settlement), the refund can never complete, permanently locking the user's own escrowed collateral in the contract with no recovery mechanism.

Either way this satisfies "permanent freezing of funds" — the escrow can never be released to anyone once the beneficiary's blacklist status is triggered, and no governance/admin function exists to redirect the specific commitment's held tokens.

### Likelihood Explanation
Any order that escrows a blacklist-capable stablecoin (USDC, USDT, and similar tokens are explicitly supported and tested throughout the intents test suite) is exposed. A malicious filler could deliberately self-blacklist (or use a disposable address they know is likely to be blacklisted) after collecting the output side of a trade, guaranteeing their own input-side payout is frozen purely to grief the escrow balance/protocol accounting, or an already-blacklisted/soon-to-be-sanctioned address could simply be the natural recipient without any malicious intent, freezing user funds through no fault of the protocol. This requires no privileged access — any user/filler dispatching a normal fill or cancellation reaches this code path.

### Recommendation
Replace the direct push-transfer in `_withdraw()`/`withdraw()` with a pull-based claim pattern: on settlement, credit an internal balance mapping `claimable[beneficiary][token] += amount` instead of transferring immediately, and expose a separate `claim(token)` function the beneficiary calls themselves. This isolates a blacklisted recipient's failure to their own claim call rather than blocking the entire cross-chain settlement message and permanently freezing the escrow, mirroring the standard mitigation for this bug class (as recommended in the referenced Cooler audit finding).

        address beneficiary = address(uint160(uint256(body.beneficiary)));

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
