## Title
`Oauth.validate_auth_callback` sends `client_secret` to a `shop` host that skips `ShopValidator` domain sanitization applied everywhere else in the OAuth family - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` and `begin_auth` build the OAuth admin URL directly from the caller-supplied/query-supplied `shop` string via `auth_base_uri(shop)` and then POST the app's `client_id`/`client_secret` to `https://#{shop}/admin/oauth/access_token`. Unlike the other credential-issuing flows in the same gem (`ClientCredentials.client_credentials`, and `TokenExchange`/`RefreshToken` via `Utils::ShopValidator`), the `shop` value here is never passed through `Utils::ShopValidator.sanitize!`, so the "host that receives the `client_secret`" is not bound to the "host validated as a trusted Shopify domain."

### Finding Description
The binding that should hold is:
`host_validated_as_trusted_shopify_domain == host_that_receives(client_id, client_secret)`

In `lib/shopify_api/auth/client_credentials.rb:25-33`, this binding is enforced: `shop` is run through `Utils::ShopValidator.sanitize!(shop)` (which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` such as `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) *before* it is used to build the session/base URI that the client secret is sent to.

In `lib/shopify_api/auth/oauth.rb:60-128`, the same binding is absent:
- `validate_auth_callback` takes `auth_query.shop` directly from the caller-constructed `AuthQuery` (built, per the gem's own docs, from raw `request.parameters`, see `docs/usage/oauth.md:246-251`) and uses it unsanitized: `Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` → `auth_base_uri(shop)` returns `"https://#{shop}/admin"` [1](#0-0) .
- `auth_base_uri` performs no domain allow-listing at all [2](#0-1) .
- The only check on `auth_query` before this point is `Utils::HmacValidator.validate(auth_query)`, which verifies that `code, host, shop, state, timestamp` were HMAC-signed with `Context.api_secret_key` [3](#0-2) [4](#0-3) . This HMAC check verifies *integrity/authenticity of the field values relative to the signing secret*, but it does not constrain `shop` to be a `*.myshopify.com`-style host — it will happily validate as long as whoever produced the query string held the `api_secret_key` (or `old_api_secret_key`).

By contrast, `Utils::ShopValidator` exists specifically to prevent an arbitrary attacker-controlled `shop` string from being turned into a URL that receives the app's credentials — and the gem itself applies it consistently in `client_credentials.rb`, `token_exchange.rb`, and `refresh_token.rb`, but omits it in `oauth.rb`'s Authorization Code Grant flow.

### Impact Explanation
If `Context.api_secret_key`/`old_api_secret_key` is ever the *old* (rotated-out) secret, or if a consuming application relaxes the HMAC precondition in a subclassed/customized flow, or in any scenario where `shop` is not perfectly constrained to `*.myshopify.com` by upstream Shopify request validation, `auth_base_uri(shop)` will send the app's `client_id`/`client_secret` in a JSON POST body to whatever host is present in `shop`. This is exactly the "host validated vs. host that receives client_secret" identity-binding break called out as in-scope, and mirrors why `ShopValidator` was introduced for the other OAuth code paths in this gem. Given the impact category is "SSRF with the app's credentials," this maps to a High-severity issue.

### Likelihood Explanation
Likelihood is constrained: in the intended, documented usage (`docs/usage/oauth.md:242-251`), `shop` only reaches `validate_auth_callback` after having been HMAC-verified end-to-end by Shopify's callback signature, which in the common case does force `shop` to be a legitimate Shopify domain because only Shopify holds the current `api_secret_key`. This is why I cannot construct a working end-to-end unprivileged-attacker PoC purely from this gem's code: I could not find another point within `lib/shopify_api/**` where an unauthenticated caller can supply an arbitrary `shop` value that reaches this code path without a corresponding valid HMAC. The gap is real (missing defense-in-depth relative to the pattern established by `ShopValidator` elsewhere in this gem), but on its own it is not a demonstrable authentication bypass, credential exfiltration, or SSRF chain triggerable by an unprivileged internet user against this library alone — it depends on the `old_api_secret_key` rotation window or a host application misusing the API (which is out of scope per the rules).

### Recommendation
Apply `Utils::ShopValidator.sanitize!(shop)` to `auth_query.shop` (and to `begin_auth`'s `shop` parameter) in `lib/shopify_api/auth/oauth.rb` before it is used to build `auth_base_uri`, matching the pattern already used in `ClientCredentials.client_credentials` [5](#0-4) , so that the host that receives `client_id`/`client_secret` is always constrained to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, independent of what the HMAC check alone guarantees.

### Proof of Concept
Not constructible as a self-contained unprivileged-attacker exploit within this gem: the missing `ShopValidator.sanitize!` call is a defense-in-depth gap only, since under documented normal use `auth_query.shop` cannot be attacker-controlled without a currently-valid HMAC signature (which requires knowledge of `api_secret_key`/`old_api_secret_key`), and exploiting the `old_api_secret_key` rotation window or a host-app misuse scenario is outside the stated scope of this analysis.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
