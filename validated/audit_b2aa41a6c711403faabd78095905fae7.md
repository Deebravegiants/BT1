### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while `ShopifyAPI::Utils::HmacValidator` (invoked from `ShopifyAPI::Webhooks::Registry.process`) only computes the HMAC over the raw request body via `to_signable_string`. The `shop` value that the app's webhook handler uses to identify the tenant is never bound to the cryptographic signature, breaking the equality `shop authenticated == shop the handler acts on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no signature coverage: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `request.shop` value as the tenant identity: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the signature purely from `verifiable_query.to_signable_string` (the body) and the app's shared `api_secret_key`: [4](#0-3) 

Because the `api_secret_key` is the same for every shop that installs the app, and the signature only covers the body, any actor who can legitimately install the app on their own store (an unprivileged action any internet user can perform) can capture a validly-signed `(body, hmac)` pair from their own shop's webhook delivery, then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because it never inspects the `shop` header, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming the data belongs to the victim shop: [5](#0-4) 

This is the same identity-binding class as the referenced report: a field that is acted upon (here, the tenant-identifying `shop`) is not covered by the authentication primitive (the HMAC), so its value can be swapped independently of the signed payload.

### Impact Explanation
Any app that keys per-shop data storage, redaction, or business logic off `WebhookMetadata#shop` (the documented and expected use of the webhook handler interface) can have that data attributed to, or mutated for, an arbitrary victim shop, without the attacker ever possessing that shop's credentials. Because the attacker only needs their own shop's HMAC secret validation to pass (using the shared app secret), this crosses a tenant boundary — satisfying the "cross-tenant access" criterion for a Critical/High finding.

### Likelihood Explanation
Any developer/merchant can install a public app on their own store to legitimately receive a signed webhook, then replay it toward the app's public webhook URL with a modified `shop-domain` header (and other headers such as `topic`/`webhook-id` if desired). No secret material, no privileged account, and no interception of legitimate traffic is required — only capturing one's own inbound webhook and reissuing it.

### Recommendation
Bind the shop, topic, and webhook_id to the signature verification, not just the body — e.g., include `shop-domain` (and ideally `topic`/`webhook_id`) in the signed material `Request#to_signable_string` returns, or independently verify that the shop asserted in headers corresponds to a shop session/tenant already known to be associated with this app installation before dispatching to handlers. At minimum, document that consumers must not trust `WebhookMetadata#shop` unless they cross-check it against their own installed-shop records.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; the app registers webhooks for topics such as `orders/create`.
2. Attacker's shop triggers the webhook; Shopify sends a POST with a body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and resends the same POST to the app's public webhook endpoint, but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` and matches `H` — validation succeeds because only `B` is signed.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process/store attacker-controlled webhook content under the victim shop's identity.
