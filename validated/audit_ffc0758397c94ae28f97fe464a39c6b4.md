### Title
Unrestricted destination/payload in cross-chain `CallDispatcher.dispatch` allows arbitrary calls on delivery (SSRF-analog) - (File: `evm/src/utils/CallDispatcher.sol`, `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` lets any unprivileged caller attach an arbitrary `data` payload to a cross-chain transfer. On delivery, `onAccept` forwards that attacker-controlled payload verbatim to the shared `CallDispatcher.dispatch()`, which blindly `.call{value}(...)`'s any `to` address the attacker names, with any calldata and any value, subject only to an `extcodesize>0` check. There is no allow-list/deny-list of destination contracts and no restriction on what the forwarded call can target — structurally identical to the reported dApp-authentication SSRF, where a fully attacker-controlled destination (`req.callback` / `galleon://...`) is blindly requested by a trusted actor without validation.

### Finding Description
- `HyperFungibleToken.SendParams.data` is user-supplied and unchecked: [1](#0-0) 
- `send()` packages `params.data` into the outbound ISMP message body without any validation: [2](#0-1) 
- On the destination chain, `onAccept` (reachable by any relayer submitting a valid ISMP proof for the message — a normal, unprivileged path) decodes the message and, if `data` is non-empty, forwards it unmodified to the dispatcher: [3](#0-2) 
- `CallDispatcher.dispatch` decodes an arbitrary `Call[]` (`to`, `value`, `data`) and executes a raw low-level call to each entry, gated only by `extcodesize(to) != 0`: [4](#0-3) 
- `CallDispatcher` also accepts arbitrary native-token deposits via a public `receive()`: [5](#0-4) 

The dispatcher is shared infrastructure — the same `CallDispatcher` instance is wired into multiple bridge apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`, etc.) per chain, as configured via `ConfigOptions.dispatcher`. This means:
1. Any account on any *configured/whitelisted* source-chain deployment of `HyperFungibleToken` can originate a `send()` with `data` that is 100% attacker-controlled — no on-chain check ever validates `call.to`, `call.value`, or `call.data` before they are forwarded and executed on the destination chain.
2. Because `CallDispatcher` is a shared contract with its own address/identity and can hold a native-token balance (via `receive()`), the attacker effectively gets a trusted, funded contract to originate calls "as," to any address of their choosing — this is functionally the SSRF pattern: a trusted intermediary is coerced into contacting/interacting with an attacker-chosen destination it never validated, purely because the attacker controlled the "callback"/target field of an authenticated request.

The `onAccept` source check (`expectedSource`) only verifies the message *originated from a trusted HyperFungibleToken deployment on a configured chain* — it does nothing to constrain what `data` (i.e., the `Call[]` destination/payload) that trusted-but-permissionless deployment is allowed to carry, since `send()` itself imposes no restriction on `data`.

### Impact Explanation
- **Arbitrary call forwarding / unauthorized app action:** Any address that can call `send()` on a supported-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment can force `CallDispatcher` on the destination chain to execute a call to any contract with any calldata and any `msg.value` up to `CallDispatcher`'s balance. Since `CallDispatcher` is shared across bridge apps on a chain, this is a confused-deputy: the dispatcher's identity/authorization (as `msg.sender`) can be pointed at any destination contract that trusts calls only by `msg.sender == CallDispatcher` (or that assumes such calls are benign), enabling unauthorized app actions in other integrations built on top of it.
- **Native-token drain:** Because `receive()` accepts unconditional ETH deposits, any native token balance accrued in `CallDispatcher` (accidental transfers, dust, or refunds from partially-successful `Call.value` sends) can be swept to an attacker-chosen address by crafting a `Call{to: attacker, value: balance, data: ""}` and delivering it through a legitimate, permissionless `send()` — this is a direct theft-of-funds vector, not merely a griefing one.
- **No destination allow-list, mirroring the reported SSRF root cause:** exactly as the report recommends allow/deny-listing destinations before honoring an attacker-supplied callback address, `CallDispatcher.dispatch` has no equivalent control — every `Call.to` is honored as long as it has code.

### Likelihood Explanation
High reachability: triggering this requires only a single unprivileged `send()` transaction on a supported source chain plus normal relayer delivery — no governance, admin, or privileged role is needed. `data` is fully attacker-supplied with zero on-chain validation at any hop (`send()` → ISMP dispatch → `onAccept` → `CallDispatcher.dispatch`). The only friction is that the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment for the pair of chains must be configured (`_supportedChains`), which is a normal, expected deployment state, not a barrier for an attacker who simply uses an existing supported lane.

### Recommendation
- Short term: constrain what `Call[]` entries `CallDispatcher.dispatch` may execute — e.g., restrict `to` to an application-specific allow-list configured by governance, or scope `CallDispatcher` instances per-application (non-shared) so a compromised/abused call cannot pivot into unrelated contracts holding shared trust in the dispatcher's address.
- Remove or gate the unconditional `receive()` so `CallDispatcher` never accrues a spendable native-token balance that an attacker-controlled `Call.value` could exfiltrate.
- Long term: apply the same SSRF-style destination validation recommended in the source report — require applications embedding cross-chain calldata (`HyperFungibleToken.data`, intents calldata, etc.) to explicitly declare/whitelist acceptable destination contracts, and reject calls to addresses outside that scope at `onAccept`/dispatch time rather than trusting the payload blindly.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send()` on a supported source chain with:
   - `params.to` = attacker-controlled recipient (mint destination, can be trivial amount)
   - `params.data` = `abi.encode([Call({to: <victim-or-drain-target>, value: <CallDispatcher balance>, data: <arbitrary calldata>})])`
2. A relayer (unprivileged, economically incentivized) delivers the ISMP POST request to the destination chain as normal — no special privilege required, this is the standard delivery path (`RequestMessage` handling in `modules/ismp/core/src/handlers/request.rs`, then `EvmHost.dispatchIncoming` → `HyperFungibleToken.onAccept`).
3. `onAccept` mints the attacker's tokens, decodes `message.data`, and calls `ICallDispatcher(_dispatcher).dispatch(message.data)`.
4. `CallDispatcher.dispatch` executes `to.call{value: call.value}(call.data)` for the attacker-chosen `to`, draining any native balance held by `CallDispatcher` and/or invoking arbitrary functionality on `to` as `msg.sender == CallDispatcher`, with no validation ever performed against the attacker-supplied destination — the cross-chain analog of the reported `galleon://` callback SSRF.

            to: dest,

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
