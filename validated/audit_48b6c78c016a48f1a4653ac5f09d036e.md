### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, then forwards `request.shop` to the app's handler as the trusted tenant identifier. The HMAC, however, is computed only over the raw request body (`Request#to_signable_string` returns `@raw_body`), never over the `shop-domain`/`x-shopify-shop-domain` header. This is the same bug class as the referenced report: a field that is acted upon (the shop identity used downstream) is not actually covered by the cryptographic check that is assumed to bind it.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed payload: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `verifiable_query.to_signable_string`, using the app's single, per-app `client_secret` (`Context.api_secret_key`): [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication, and then passes the *unverified* `request.shop` straight to the app-supplied handler as the identified tenant: [4](#0-3) 

Because `Context.api_secret_key` (the app's `client_secret`) is the same for every shop that has installed the app, and the HMAC signature is a function only of the raw JSON body plus that shared secret, the signature is independent of which shop the webhook is claimed to originate from. Concretely: `hmac = HMAC(client_secret, raw_body)` — no `shop` term is included, so `hmac` is valid for a given `raw_body` regardless of the value placed in the `shop-domain` header. The equality the code implicitly assumes — "the shop that produced a body with a valid HMAC == the shop named in the `shop-domain` header" — does not hold, because `shop-domain` is never an input to the signature.

An attacker who legitimately installs the vulnerable app on their own store (a normal, unprivileged action) receives real webhooks that are validly signed with the app's shared `client_secret`. They can then replay/craft an HTTP POST to the app's webhook endpoint using that same signed body (or any body of their choosing that they can get signed via their own installation's real webhook traffic) while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `shop` is now the attacker-chosen victim domain.

### Impact Explanation
If the host application uses the `shop` field from `WebhookMetadata` to select which merchant's session/data to update (a very common and encouraged pattern per `docs/usage/webhooks.md`), an attacker can inject attacker-controlled webhook payloads that are processed under another merchant's identity — e.g. triggering `shop/redact` or `customers/data_request`/`customers/redact` handling, or any custom topic handler, against a shop the attacker does not control. This is a cross-tenant integrity/authentication issue: the gem presents a spoofable identity (`shop`) as if it had been verified by the same mechanism (HMAC) that verified the body, when it was not.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on an attacker-owned development/test store — a normal, unprivileged action available to any developer — and the ability to send a crafted HTTP request to the app's public webhook endpoint with attacker-controlled headers. No access to the app's `client_secret`, no leaked credentials, and no privileged account are required; the attacker only needs their own valid signed webhook traffic and control over HTTP headers on their own outbound (spoofed) request, both trivially available to any unprivileged internet user who is themselves an app installer.

### Recommendation
Bind the claimed `shop` (and other routing headers like `topic`) into the value that is actually authenticated, or otherwise cryptographically tie them to the verified body — e.g., include `shop-domain` in the signable string used for HMAC computation, or require the caller to additionally verify `shop` against the set of shops known to have installed the app (a shop registered via OAuth) before trusting it as a tenant identifier. At minimum, `Request#to_signable_string` should incorporate the shop-domain header, matching the "shop authenticated == shop the credential is bound to" invariant, rather than validating body integrity alone and letting an unrelated header dictate tenant identity.

### Proof of Concept
1. Register/own an app with `client_secret = S`. Install it on attacker's own store `attacker.myshopify.com`; Shopify sends a real webhook: `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: HMAC(S, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker intercepts/reuses `(B, HMAC(S,B))` and issues their own POST to the app's webhook endpoint, replacing only the header `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(S, B)` from `request.to_signable_string` (== `B`) — this matches the supplied `hmac`, so validation passes: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...)`: [6](#0-5) 
5. Any host-app logic keyed off `data.shop` now operates as if the request genuinely originated from `victim.myshopify.com`, even though the body and topic were entirely attacker-controlled and the shop identity was never part of the signed material.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
