### Title
LP-seeding rebalance defense has a budget-capped residual that opens graduated pools materially off curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
The permissionless two-phase graduation flow (`triggerGraduation` / `finalizeGraduation`) parks all curve-raised LT and the LP-reserve tokens on `Bonding` between phases, then seeds a HyperSwap V2 pair that anyone can pre-create and pre-fund before phase 2 runs. [1](#0-0)  `_seedUniswapV2Direct`'s Regime 3 defends against a hostile `pair.mint` pre-seed by swapping the pool back toward the curve-close ratio via `_pairRebalance`, but that rebalance swap is intentionally capped at a fixed per-side budget rather than being allowed to fully correct the ratio. [2](#0-1) [3](#0-2)  When an attacker pre-seeds the pair with a sufficiently lopsided ratio (verified in-repo at ~200x LT-rich), the optimal corrective swap exceeds this budget, the cap binds, and the pool is deposited while still materially off the curve's closing price — a state the protocol's own regression suite explicitly measures and accepts (`test_hostilePreSeed_budgetCappedSwap_isNotProfitable`, tagged "M-02"). [4](#0-3) 

This is a structural analog of the CVE-2022-2625 bug class: a routine, trust-boundary-crossing action (`CREATE OR REPLACE`/extension update in Postgres; here, the keeper's permissionless `finalizeGraduation` call which mints LP and hands it to `LPLock`) operates over an object (the schema/function; here, the HyperSwap pair) that an unprivileged attacker was able to pre-position ("lure") before the trusted action executes, and the defense that exists is bounded rather than complete — so the final state committed on behalf of the protocol/holders can still be corrupted relative to the correct/intended one.

### Finding Description
`_seedUniswapV2Direct` branches into three regimes depending on the state an attacker left the HyperSwap pair in before `finalizeGraduation` runs. [5](#0-4)  Regime 3 (a hostile `pair.mint` pre-seed) is the only regime where the attacker actually holds LP against a non-empty pool, and it is handled by:
1. Computing a no-fee rebalancing swap size via `_noFeeSwapInput`'s closed-form `sqrt` formula, "capped at our per-side budget." [6](#0-5) 
2. Executing that swap directly against the pair (`pair.swap`). [7](#0-6) 
3. Depositing the remaining balanced inventory via `router.addLiquidity(rest, 1, 1, lpLock, ...)`.
4. Burning/sweeping the off-ratio remainder.

Because step 1's swap input is budget-capped (not sized to fully correct any arbitrary pre-seed ratio), an attacker who funds the pair with a large enough imbalance (e.g., LT reserve at 200× the target ratio versus TOKEN at 1% of target) can force the optimal corrective swap to exceed the cap. The rebalance then only partially corrects the ratio, and `finalizeGraduation` proceeds to lock LP into `LPLock` at a price that is "materially off curve-close" — the repository's own test asserts the resulting price is more than 20% away from the true curve-close ratio in this scenario. [8](#0-7) 

The protocol's mitigating claim is that the pre-seeder cannot profit from this (their residual LP claim, valued at the fair curve-close price, is asserted to be ≤ their deposit), and the over-funded side is confiscated to the owner. [9](#0-8)  However, "attacker doesn't profit" is a separate property from "the LP that ends up permanently locked for the protocol/token holders opens at the correct price." The task's own validation criteria treat "an LP seeded away from the curve close price" as a standalone, sufficient impact independent of attacker profitability, and this residual is a first-party-acknowledged, directly reachable consequence of `finalizeGraduation`/`_seedUniswapV2Direct`/`_pairRebalance`'s budget cap.

### Impact Explanation
Any unprivileged address can pre-create the HyperSwap pair via `factory.createPair(token, lt)` and pre-fund/`mint` it at an extreme ratio before a keeper (or anyone, since `finalizeGraduation` is permissionless) calls `finalizeGraduation`. [10](#0-9)  This is reachable by a single attacker transaction sequence requiring only ERC20 transfers and pair calls, no privileged role. The resulting permanently-locked LP (held by `LPLock`, which "has no rescue path in v1") [11](#0-10)  opens the post-graduation trading venue at a price divorced from the curve's actual close, mispricing the asset for every subsequent trader and creating an immediate, un-arbitraged wealth transfer opportunity against the LP itself (and by extension the token/LT holders whose economic backing the LP represents) at the moment of graduation.

### Likelihood Explanation
Moderate-to-high. The precondition (a sufficiently extreme mint-pre-seed ratio) is explicitly demonstrated as achievable and is directly parameterized/tested in the repository (`reserveToken = tokensForLP/100`, `reserveLt = ltFromPair*200`), meaning the budget cap is not a purely theoretical edge — it is a concrete, quantified boundary the code accepts as a known residual rather than eliminates. [12](#0-11)  Any actor observing a token approach `canGraduate` can front-run phase 2 with a self-funded pre-seed of this shape.

### Recommendation
Either (a) remove the fixed per-side swap budget and size the rebalance to fully correct the ratio (subject only to brick-resistance safeguards already in place for the zero-output case), or (b) if the budget must remain bounded for gas/brick reasons, add a secondary defense for the budget-exceeded case — such as routing the excess-imbalance shape through the Regime-1/2 style disposal (fully skim/burn/sweep and re-mint fresh) instead of depositing LP at a materially-off price — so that no code path can lock LP for token holders at a price that diverges materially (e.g., beyond a few bps, consistent with the ~50 bps ceiling already targeted for the in-budget case) from curve-close.

### Proof of Concept
Based on `packages/contracts/test/TwoPhaseGraduation.t.sol::test_hostilePreSeed_budgetCappedSwap_isNotProfitable`: [13](#0-12) 
1. Launch and drive a token into `Lifecycle.Graduating` via the normal curve buy flow (`_enterGraduating`), caching `(tokensForLP, ltFromPair)`.
2. As an unprivileged attacker (`griefer`), call `hsFactory.createPair(tokenAddr, lt)`, then `transfer` `reserveToken = tokensForLP/100` TOKEN and `reserveLt = ltFromPair*200` LT into the pair, and call `pair.mint(griefer)` — this is `_grieferMintPreSeed`.
3. Anyone calls `bonding.finalizeGraduation(tokenAddr)`.
4. Observe: the call does not revert (brick-resistant), but the resulting pool price (`_poolPriceLtPerToken`) is more than 1.2× the true curve-close price (`ltFromPair/tokensForLP`), confirming the LP is permanently locked at a price materially away from curve-close.

    function triggerGraduation(
        address tokenAddress
    ) external nonReentrant {
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        if (!canGraduate(tokenAddress)) revert NotGraduatable();
        _enterGraduating(tokenAddress);

    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );

        // The over-funded LT side is arbed out by the rebalance swap and swept
        // to the owner — the pre-seeder cannot recover it.
        assertGt(
            lt.balanceOf(bonding.owner()) - ownerLtBefore,
            reserveLt / 2,
            "the over-funded LT side must be confiscated to the owner"
        );

        // P&L: the pre-seeder's residual LP, valued at the fair (curve-close)
        // price, is worth a fraction of what they deposited — the attack is
        // cost-negative.
        uint256 claimValue = _lpValueAtCurveClose(hyperPair, tokenAddr, grieferLp, tokensForLP, ltFromPair);
        uint256 depositValue = _depositValueAtCurveClose(reserveToken, reserveLt, tokensForLP, ltFromPair);
        assertLe(claimValue, depositValue, "pre-seeder must not profit (P&L <= 0)");
        assertLt(claimValue * 2, depositValue, "pre-seeder must lose materially, not merely break even");
    }
