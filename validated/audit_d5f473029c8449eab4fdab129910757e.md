### Title
Webhook `shop` identifier is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by checking only the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the trusted tenant identifier. Because the shop identifier is never part of the signed material, an attacker who can obtain one validly-signed webhook body (e.g. from their own shop, since the app's `api_secret_key` used to sign every merchant's webhooks is the single, shop-independent secret for the whole app) can replay that body to the app's webhook endpoint while forging the `x-shopify-shop-domain`/`shopify-shop-domain` header to name a victim shop. The library reports this as a validated, Shopify-originated event for the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` is computed from headers, but the value that is actually verified against it is `to_signable_string`, which returns only the raw body bytes: [1](#0-0) 

The `shop` accessor is read straight from an unauthenticated header with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body only for webhooks: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and, immediately after it passes, forwards `request.shop` — the unverified header — into `WebhookMetadata` given to the app-level handler, without any comparison to a known/authenticated shop, session, or subscription record: [4](#0-3) 

The gem's own documentation states that calling `Registry.process` "will verify the request did indeed come from Shopify," implying the entire `WebhookMetadata` (including `shop`) is trustworthy, which is the guidance the app author is expected to rely on: [5](#0-4) 

The identity binding that should hold is: `shop used to key/act on tenant data == shop bound by the HMAC-covered signature`. Here the left side is `request.shop` (arbitrary attacker-controlled header) and the right side is nothing — the signature covers only body bytes, not shop. Since `api_secret_key` is the app's single, shop-independent signing secret (the same secret authenticates webhooks for every merchant that installs the app), any attacker who runs the app on their own store can legitimately receive an HMAC-valid `(body, hmac)` pair for their own account, then POST that exact pair directly to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim's `myshopify.com` domain.

### Impact Explanation
Because host applications key session lookup, tenant-scoped data writes, and business logic (order creation, inventory changes, GDPR data, background jobs, etc.) by `data.shop` as documented, this allows an attacker to have their own attacker-crafted webhook payload processed by the app under a victim shop's identity — a cross-tenant access/injection scenario reaching a Critical-tier impact category (cross-tenant access) without needing the app's `client_secret`, an access token, or any leaked credential; only a working installation of the app on a shop the attacker controls is required.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair only requires installing the app on any shop (including a free/dev store) and triggering an event that fires a subscribed webhook topic; the header carrying `shop-domain` is fully attacker-controlled in the raw HTTP request and is never cross-checked by the library.

### Recommendation
Bind the shop identity into the verified material, or explicitly require host apps to validate `data.shop` against a known/authenticated session/shop record before trusting it. Concretely, `Registry.process` should either (a) reject webhooks whose `shop` does not match a shop with an active, previously-established session/subscription for that specific `topic`/`webhook_id`, or (b) document and enforce that `shop` is untrusted metadata that callers must independently verify — and stop implying via docs/method naming that `process` fully "verifies the request came from Shopify" for the shop attribute as well as the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) they registered for, capturing the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` per [1](#0-0) .
2. Attacker crafts an arbitrary malicious `B` is not required — they can even use the identical, unmodified `B`/`H` pair, since only `B` is signed.
3. Attacker sends a POST directly to the app's public webhook endpoint with headers `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, and `x-shopify-shop-domain: victim.myshopify.com`, and body `B`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` per [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's data>, ...)` per [7](#0-6) , causing the host app to process attacker-controlled webhook content as an authentic event for the victim's tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
