### Title
Unbounded cycle in GRANDPA `AncestryChain::ancestry` causes infinite loop on attacker-crafted `unknown_headers` - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`GrandpaConsensusClient::verify_consensus` decodes a relayer-submitted `ConsensusMessage` and calls `verify_grandpa_finality_proof`, which walks parent-hash pointers over a relayer-supplied `Vec<H>` of `unknown_headers` via `AncestryChain::ancestry`. That walk has no cycle detection and no bound on the number of hops, so a relayer can submit two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that the walk enters and never exits — an infinite loop, directly analogous to CVE-2016-7122's infinite loop from a crafted structure with no forward-progress guarantee.

### Finding Description
`AncestryChain::ancestry` walks from `block` back to `base` by repeatedly following `parent_hash`, terminating only when `current_hash == base` or when a hash is missing from the map: [1](#0-0) 

The `ancestry` map itself is built directly from the untrusted `finality_proof.unknown_headers` supplied inside the consensus proof bytes: [2](#0-1) 

`verify_grandpa_finality_proof` invokes this walk with `from = consensus_state.latest_hash` (trusted) and `target.hash()` (attacker-controlled, taken as the header with the highest declared `number()` among `unknown_headers`): [3](#0-2) 

`Header::number()` is an attacker-set field with no cryptographic tie to the actual parent chain beyond the header's own hash. Nothing prevents a relayer from crafting two headers `A` and `B` where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`, both included in `unknown_headers`, with `target`'s parent pointer routed into that cycle instead of toward `from`. Because both hashes exist in the `ancestry` `BTreeMap`, every lookup in the `while current_hash != base` loop succeeds, `current_hash` bounces between `A` and `B` forever, and the loop never returns `Err(NotDescendent)` nor reaches `base`. There is no depth counter, no bound tied to `unknown_headers.len()`, and no visited-set check to detect revisiting a hash.

This is reachable from an unsigned, permissionless consensus-update dispatch path: `GrandpaConsensusClient::verify_consensus` decodes the relayer-supplied proof and calls straight into `verify_grandpa_finality_proof` / `verify_parachain_headers_with_grandpa_finality_proof`: [4](#0-3) 

The same unbounded, un-deduplicated ancestry walk is reused for parachain-header verification as well.

### Impact Explanation
This is a route-unable-to-deliver-messages / permanent-DoS class bug: a single relayer-submitted GRANDPA consensus message can drive block execution into an infinite loop inside `verify_consensus`, which runs during on-chain extrinsic/message execution. Because BEEFY/GRANDPA consensus updates are processed via unsigned or otherwise low-cost dispatch (any relayer can submit a consensus proof), an attacker needs no privileged role — only the ability to submit a consensus update — to hang block execution for the state machine relying on this consensus client, halting all further state and message verification through it (freezing all pending cross-chain messages/funds routed through that consensus client).

### Likelihood Explanation
Likelihood is high for any attacker capable of submitting a `ConsensusMessage` for the GRANDPA client: crafting two headers with mutually-referencing `parent_hash` values requires no cryptographic break — headers are attacker-constructed byte blobs whose `hash()` is simply BLAKE2b of their own encoded contents, and nothing constrains a header's declared `parent_hash` to match a real, previously-existing block. Submitting such a proof is a normal, permissionless relayer action.

### Recommendation
- Bound `AncestryChain::ancestry`'s traversal by the number of entries in the ancestry map (`self.ancestry.len()`), returning `Err(NotDescendent)` once that bound is exceeded, since any valid acyclic route can visit at most `unknown_headers.len()` distinct hashes.
- Alternatively/additionally, maintain a visited-hash set during the walk and fail immediately if a hash is revisited.
- Reject `unknown_headers` sets containing more than one header with hash appearing as another header's parent in a way that would create a cycle, or otherwise validate that all headers form a strictly single, non-branching, non-cyclic chain before running the ancestry walk.

### Proof of Concept
1. Craft header `B` with an arbitrary `number` field and `parent_hash = H(A)` (computed after `A` is finalized below).
2. Craft header `A` with `parent_hash = H(B)`.
3. Craft header `TARGET` with `number()` higher than `A`/`B`, `parent_hash = H(A)`, whose hash equals `finality_proof.block`.
4. Submit `unknown_headers = [A, B, TARGET]` (plus any headers needed so `min_by_key` picks a `base` distinct from the trusted `from`) inside a `FinalityProof`, along with a syntactically-valid (but not necessarily super-majority-verified, since the ancestry walk is invoked before/independent of signature verification succeeding) `GrandpaJustification` targeting `TARGET.hash()`.
5. Call `GrandpaConsensusClient::verify_consensus` (or directly `verify_grandpa_finality_proof`) with this proof; `headers.ancestry(from, target.hash())` walks `TARGET -> A -> B -> A -> B -> ...` indefinitely, hanging the calling extrinsic/message execution.

Note: exact enforcement order (whether justification/signature checks occur before the `ancestry` call in all code paths) should be confirmed against the full runtime dispatch flow; the `verify_grandpa_finality_proof` function as read calls `headers.ancestry(from, target.hash())` before `justification.verify(...)`, so the infinite loop is hit prior to any cryptographic authority-set check.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
