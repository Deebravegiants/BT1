## Title
Webhook shop-domain spoofing due to HMAC covering only the raw body, not the `shop`/`topic`/`webhook_id` headers — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the webhook HMAC exclusively against that body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all taken from unauthenticated HTTP headers — are handed to the merchant's webhook handler as trusted tenant-identifying metadata, even though none of them are covered by the signature.

### Finding Description
`Request#to_signable_string` is defined as just the raw body: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (and the other header-derived fields) to the application's handler as authoritative tenant data: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e., the body, using the app's shared `api_secret_key` (the same secret is reused for every shop that installs the app): [4](#0-3) 

Because the HMAC is a function of body bytes only, the equality the gem should enforce — *the shop the HMAC was computed for* == *the shop delivered to the handler* — never actually holds. An attacker who installs the app on their own (legitimately owned) shop receives real webhook deliveries whose `x-shopify-hmac-sha256` is computed with the app's single shared secret over that specific body. The attacker can then replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`webhook-id`) header value. `HmacValidator.validate` still succeeds because the header changes never touch the signed bytes, and `Registry.process` passes the attacker-chosen `shop` through to the handler as `WebhookMetadata#shop` unchanged.

### Impact Explanation
This lets an unprivileged internet user (anyone who can install the app on any shop, including a free/dev store they control) inject attacker-controlled webhook payloads that the host application will process under the identity of a victim shop of the attacker's choosing. Any host application logic that uses the delivered `shop` value to select which tenant's session/data to update (a documented, expected pattern per `WebhookMetadata#shop`) can be tricked into cross-tenant data corruption/injection — e.g., writing attacker-supplied order/product/customer data into a victim's tenant record, or triggering app-side actions (uninstall processing, GDPR data-request handling, etc.) attributed to the wrong shop. This is a cross-tenant integrity break rooted entirely in the gem's webhook verification, matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is High: no privileged credentials, leaked secrets, or social engineering are required. The attacker only needs to install the app on any shop they control (a normal, permission-less action for public apps) to obtain a valid `(body, hmac)` pair signed with the app's shared secret, then replay it with a forged `shop-domain` header to the app's own publicly reachable webhook endpoint.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the `shop` value to the HMAC, rather than trusting it purely from a header alongside a body-only HMAC:
- Include the `shop` (and ideally `topic`/`webhook_id`) in `to_signable_string`, or
- Cross-check `request.shop` against a shop value independently bound to the delivery (e.g., verify the webhook against a known, previously-registered shop/session rather than trusting the header verbatim), and document that consumers must not treat `WebhookMetadata#shop` as authenticated unless the gem enforces this binding.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, completing OAuth normally.
2. Attacker triggers an event (e.g., `orders/create`) on their own shop, causing Shopify to POST a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` and replays it directly to the same public webhook endpoint, replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` (body unchanged) and it matches `H`, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`.
5. Any handler logic keyed on `shop` now operates as if attacker-controlled body `B` legitimately originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          received_signature = verifiable_query.hmac
