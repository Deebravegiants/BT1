### Title
Swap-base-out instructions panic on attacker-controlled `amount_out` due to unchecked subtraction before bounds validation - (File: program/src/processor.rs, program/src/math.rs)

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` call `Calculator::swap_token_amount_base_out` with the caller-supplied `amount_out` before validating that `amount_out` is smaller than the pool's available reserve. `swap_token_amount_base_out` performs `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin equivalent), which panics when `amount_out` is greater than or equal to the reserve — a state fully reachable from a single unprivileged swap transaction with attacker-chosen instruction data.

### Finding Description
Both swap-base-out entry points compute the swap math before the sufficiency check that would normally reject an oversized `amount_out`:
- `process_swap_base_out`: `swap_token_amount_base_out` is called at [1](#0-0) , while the check `if swap.amount_out >= total_pc_without_take_pnl { return Err(...) }` only happens later at [7](#0-6) .
- `process_swap_base_out_v2` has the identical ordering: math call at [2](#0-1) , bounds check at [8](#0-7) .

Inside `Calculator::swap_token_amount_base_out` (program/src/math.rs), both branches subtract `amount_out` from the relevant pool reserve using `.checked_sub(amount_out).unwrap()`: [5](#0-4) [6](#0-5) 

If `amount_out >= total_pc_without_take_pnl` (Coin2PC direction) or `amount_out >= total_coin_without_take_pnl` (PC2Coin direction), the `checked_sub` returns `None`, and the subsequent `.unwrap()` panics. This is directly analogous to the Apollo Router CWE-703/754 class of bug in the report: an externally-controlled input reaches a code path that terminates the process via an unhandled exceptional condition (a panic) instead of gracefully returning an error, even though a correct bounds check exists elsewhere in the function but is ordered too late.

### Impact Explanation
A Solana BPF program panic aborts the transaction with a runtime panic rather than a controlled program error. While this does not directly drain funds (the transaction fails and is rolled back), it is a reliable, unauthenticated Denial-of-Service vector: any swapper can force `process_swap_base_out`/`process_swap_base_out_v2` to panic by choosing `amount_out` at or beyond the pool's reserve, at zero cost beyond a failed transaction fee. Because this is deterministic and requires no special privileges, it can be used to grief front-running bots, integrators, or off-chain simulators that treat a panic differently from a normal program error (e.g., certain client SDKs/relayers), and reduces the reliability guarantee that all failure modes are structured `ProgramError`s.

### Likelihood Explanation
Trivial to trigger — it only requires submitting a `SwapBaseOut`/`SwapBaseOutV2` instruction with `amount_out` set to or above the current on-chain reserve amount for the relevant vault, both of which are publicly readable on-chain. No special account permissions, signer keys, or pool state manipulation are required beyond the pool being in a swap-permitted status.

### Recommendation
Reorder the checks so the sufficiency check (`amount_out < total_{pc,coin}_without_take_pnl`) happens *before* calling `Calculator::swap_token_amount_base_out`, or replace the `.unwrap()` calls in `swap_token_amount_base_out` with proper error propagation (e.g., return `Result<U128, AmmError>` and map `None` to `AmmError::InsufficientFunds`/`CalculationExRateFailure`), consistent with the pattern already used elsewhere in the codebase (e.g., `.ok_or(AmmError::CalculationExRateFailure)?` in the deposit path at [9](#0-8) ).

### Proof of Concept
1. Read the current `amm_pc_vault`/`amm_coin_vault` token account balances for a target pool (public on-chain data).
2. Submit a `SwapBaseOut` (or `SwapBaseOutV2`) instruction where `swap.amount_out` is set equal to (or greater than) `total_pc_without_take_pnl` (for `Coin2PC` direction, i.e., user_source mint = coin, user_destination mint = pc) or `total_coin_without_take_pnl` (for `PC2Coin` direction).
3. During execution, `Calculator::swap_token_amount_base_out` is invoked at [1](#0-0)  before the sufficiency check, causing `total_pc_without_take_pnl.checked_sub(amount_out)` (or coin equivalent) to return `None` inside [5](#0-4) , and the subsequent `.unwrap()` panics, aborting the transaction with a runtime panic rather than a clean `AmmError`.
