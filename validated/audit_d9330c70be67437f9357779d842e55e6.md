### Title
Emporium Min-proof path lets attacker drain arbitrary Emporium-held funds via unaccounted self-executed ops - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol :: runAction, contracts/CircomDataBuilder.sol :: formInputForCircom/formInputEmporiumMin)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only forces the circuit to prove `message == Poseidon(messageSeed)` [1](#0-0) . This bypasses all nullifier/root/amount accounting, yet `EmporiumUpgradeable.runAction` still executes an attacker-supplied `EmporiumStack.ops` array whose length is completely independent of `erc20TokenAddresses.length`, so any assets moved by those ops are never captured by the `balancesBefore`/`balancesAfter` accounting loop.

### Finding Description
The broken equality: **assets Emporium can move in a tx == assets accounted in `balancesBefore`/`balancesAfter`**.

- `formInputForCircom` selects the Min path solely based on `erc20TokenAddresses.length == 0` [2](#0-1) . In this path the only public constraint proven by `MainEVMCircuitMin` is `message <== Poseidon(1)([messageSeed])` [3](#0-2)  — no nullifiers, no root usage, no amounts are constrained.
- `dimensionsCheck` only forces `erc20TokenAddresses.length`, `amountChanges.length`, `inputNullifiers.length`, `outCommitments.length`, etc. to equal `dimensions.tokenNumber`; setting `tokenNumber = 0` makes all of these trivially empty and self-consistent [4](#0-3) .
- `rootHashExists` accepts any historical root within `[MINIMUM_INDEX, m_index)` with no recency window [5](#0-4) ; since no nullifier/input UTXO is actually proven in the Min path, a stale root is functionally irrelevant — the root check is decoupled from any spend logic in this path.
- In `EmporiumUpgradeable.runAction`, `EmporiumStack` is decoded straight from attacker-controlled `externalActionData.externalActionMetadata` (not proof-constrained) [6](#0-5) . When `stack.signerAddress == address(0)`, `verifyWallet` skips the EIP-712 signature check entirely and only marks `emporiumMessage` used [7](#0-6) .
- The ops loop iterates `stack.ops.length` (attacker-chosen, arbitrary length) and directly calls `op.endpoint.call{value: op.value}(op.callData)` as Emporium itself (`msg.sender == Emporium`) [8](#0-7) .
- The only accounting/guard (`balanceChange < 0` revert, `handleOut`) is bounded by `circomData.erc20TokenAddresses.length`, which is forced to 0 in this exact path [9](#0-8) . With zero iterations, no check fires no matter what the ops did.

Exploit flow: attacker crafts `CircomData` with `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalAddress = Emporium`, and `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [op1, op2, ...]})` where each `op.endpoint` is an ERC20 token Emporium holds a balance of and `op.callData = transfer(attacker, balance)` (or any endpoint/token the attacker wants Emporium to act on, chained arbitrarily, since ops length is unbounded). Attacker generates a trivial `MainEVMCircuitMin` proof for a self-chosen `messageSeed`, submits any valid historical `rootHashHinkal`/index, and calls `Hinkal.transact`. `performHinkalChecks` and `verifyProof` pass because nothing meaningful is proven; `_externalTransact` calls `runAction`, which executes every op as Emporium's own call, draining any ERC20/ETH balance parked in the Emporium contract, with zero balance/slippage guard triggered because `erc20TokenAddresses` is empty.

Existing guards fail because: (1) `performHinkalChecks`/`dimensionsCheck` only validate internal array-length consistency, not that Emporium's actual asset movement is bounded; (2) `rootHashExists` and the proof itself constrain nothing about the actual funds touched in the Min path; (3) `runAction`'s balance-accounting loop bound (`erc20TokenAddresses.length`) is decoupled from the actual op-execution loop bound (`stack.ops.length`).

### Impact Explanation
Any funds sitting in the Emporium contract's balance (parked/in-flight deposits, un-swept balances between operations, fee balances) for ERC20 tokens or ETH can be stolen by an unprivileged attacker in a single transaction with a trivial, self-generated Min proof. This is direct theft of shielded/in-flight user funds — Critical severity — and is fully repeatable against every token balance Emporium ever holds.

### Likelihood Explanation
Preconditions are minimal and attacker-achievable: Emporium must be a registered `externalActionMap` entry (already the case for the protocol's Emporium feature) and must hold a non-zero balance of some asset at call time (which happens naturally whenever users route funds through Emporium ops). The attacker needs no special role, no valid Merkle leaf, and no real spending proof — only a self-chosen `messageSeed` and arbitrary `externalActionMetadata`. Cost is a single transaction; the finding is deterministic and repeatable for as long as Emporium holds a drainable balance.

### Recommendation
Do not allow the Emporium Min proof path to bypass the balance/accounting loop. Specifically: reject `runAction` execution unless `stack.ops.length == 0` when `erc20TokenAddresses.length == 0`, or better, remove the Min-path special case entirely for stateless op execution and require `erc20TokenAddresses` to enumerate every token/ETH balance that any `op` in `stack.ops` can affect, with the existing `balancesBefore`/`balancesAfter` accounting scoped to cover them. Additionally, require `stack.signerAddress != address(0)` (mandatory signature verification) whenever `stack.ops` contains any stateless call to an arbitrary `endpoint`, or restrict stateless-mode endpoints to a strict allow-list unrelated to Emporium's own held balances.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal, HinkalHelper, EmporiumUpgradeable (register in `externalActionMap`), and a mock ERC20.
2. Fund Emporium directly with `mockToken.mint(emporium, 1000e18)` to simulate parked balance.
3. As attacker EOA, build `CircomData` with `dimensions.tokenNumber = 0`, all length-0 arrays, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalAddress = emporium`, `externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(mockToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))})], maxFee: 0, deadline: 0}))`.
4. Generate a real snarkJS proof for `MainEVMCircuitMin` with attacker-chosen `messageSeed`; set `circomData.emporiumMessage = Poseidon(messageSeed)`.
5. Use any existing valid `(rootHashHinkal, rootHashHinkalIndex)` pair, including one from many batches ago.
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
7. Assert: before tx `mockToken.balanceOf(emporium) == 1000e18` and `mockToken.balanceOf(attacker) == 0`; after tx `mockToken.balanceOf(emporium) == 0` and `mockToken.balanceOf(attacker) == 1000e18`, while `circomData.erc20TokenAddresses.length == 0` and no `require` in `runAction`'s balance-accounting loop ever executed (confirmed via loop bound == 0), proving assets moved (1000e18) != assets accounted (0).
