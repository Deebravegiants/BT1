### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value exclusively from the unauthenticated `shopify-shop-domain` HTTP header, while `HmacValidator` only verifies the HMAC over the raw request body. Because the tenant identifier (`shop`) is never part of the signed material, an attacker who has captured one legitimate, validly-signed webhook can replay it while swapping the `shop-domain` header to any value, and the signature check will still pass.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value returned by the query object: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` such that `to_signable_string` returns **only** `@raw_body`, and `hmac` comes from the `hmac-sha256` header — but `shop` is read from a completely separate, un-signed header: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

This is structurally the same class of bug as the reported `merkleRoot == 0` issue: a value that is *acted upon* as an authenticated/trusted identifier (`merkleRoot` in the report; `shop` here) is never actually validated/bound by the mechanism meant to guarantee its integrity (a root-existence check in the report; the HMAC signature here). The equality that should hold — `shop authenticated by HMAC == shop delivered to the handler` — does not hold, because the HMAC computation never includes `shop`.

Concretely: `sign(secret, body) == hmac` is verified, but `shop` is not part of `body`'s signed representation, so `shop` can be swapped freely by anyone who can present *any* previously-observed valid `(body, hmac)` pair for the same secret (e.g. an attacker's own store, since every merchant's webhook uses the same app `client_secret`/`api_secret_key`).

### Impact Explanation
Any user who runs their own Shopify store using the same app (a completely unprivileged, legitimate installer) receives real, validly-HMAC-signed webhooks from Shopify for their own store. They can then replay that exact `(raw_body, hmac-sha256 header)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` will still succeed because the signature only covers the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop: [4](#0-3) 

Any host application that uses `data.shop` to select per-tenant state, storage keys, or triggers (exactly as the gem's own documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) is thus exposed to cross-tenant data injection/corruption driven entirely by an unprivileged attacker who only needs an app installation on their own store.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant with the app installed on their own shop — no leaked secrets, no privileged access, and no TLS interception are required. They passively observe webhooks sent to their own registered endpoint (which they control) and replay the byte-identical body/HMAC pair with a forged `shop-domain` header to the target endpoint. This is fully within the "unprivileged internet user" threat model and requires no cooperation from Shopify or the victim.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is actually verified by the HMAC, or otherwise cryptographically tie the shop domain to the signed payload before trusting it as a tenant identifier. At minimum, `VerifiableQuery#to_signable_string` for webhook requests should incorporate the shop-domain header (and other identity-bearing headers) so that a signature computed for one shop cannot be replayed for another. Documentation and examples that pass `data.shop` directly into tenant-keyed operations should be updated once this binding is fixed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the attacker's own endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — this is fully attacker-observable since it's their own store's traffic.
3. Attacker crafts a new HTTP POST to the app's webhook callback URL:
   - Body: exactly `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: exactly `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`, `x-shopify-webhook-id`: reused/forged as needed
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` only and successfully matches `H`: [5](#0-4) 
5. The handler executes with `data.shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and pertains to, the attacker's own store — demonstrating the cross-tenant identity spoof.
