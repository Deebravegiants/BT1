### Title
`Oauth.begin_auth` fails to validate `shop`, allowing the CSRF `state` nonce to be leaked to an attacker-controlled domain, enabling forced OAuth completion - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` parameter without ever validating that it is a genuine Shopify domain, unlike every other entry point in the gem that accepts a `shop` string.

### Finding Description
`begin_auth` generates a random CSRF nonce (`state`), stores it in a cookie on the user's browser, and then redirects the browser to `auth_base_uri(shop) + "/oauth/authorize?..."`, embedding that same `state` value in the URL query string: [1](#0-0) 

`auth_base_uri` performs no domain validation at all — it simply interpolates the raw `shop` string into `https://#{shop}/admin`: [2](#0-1) 

Every other place in the gem that accepts an untrusted `shop` value runs it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [3](#0-2) 

For example, `TokenExchange.migrate_to_expiring_token` and `ClientCredentials` both call `sanitize!(shop)` before using the value to build a request host: [4](#0-3) 

`begin_auth` is the one OAuth entry point that omits this check. Because of this, the equality that should hold — *the domain the browser is redirected to* == *a domain trusted to legitimately participate in Shopify OAuth* — is not enforced. Only `validate_auth_callback` (the callback side) binds `shop` cryptographically, via the HMAC computed over `code/host/shop/state/timestamp`: [5](#0-4) [6](#0-5) 

But that check only happens *after* the state nonce has already been exposed to whatever host `begin_auth` redirected to.

### Impact Explanation
If a host application passes an unsanitized, request-controlled `shop` value into `begin_auth` (which is exactly the pattern shown in this gem's own documentation, `shop = request.headers["Shop"]`), an attacker can supply an attacker-controlled hostname as `shop`. The victim's browser is redirected to the attacker's page carrying the freshly minted, cookie-bound CSRF `state` value in the URL. The attacker's page can read that `state` from the query string (it's their own server/page receiving the request) and then separately perform a legitimate OAuth authorization with Shopify for **their own shop**, obtaining a valid `code`/`hmac` pair for that shop. The attacker then forces the victim (whose browser still holds the original `state` cookie) to visit the legitimate app's callback URL with `shop=<attacker's shop>&code=<attacker's code>&hmac=<valid>&state=<leaked nonce>`. `validate_auth_callback` will accept this, because the HMAC and the state match — resulting in the victim's browser session/cookie being bound to a session for the **attacker's** shop. This is a forced OAuth completion / session fixation, matching the High-impact category for this class of gem.

### Likelihood Explanation
Exploitation requires no privileged access, no leaked secrets, and no code beyond producing a crafted link/redirect — only that a host application pass a browser/request-derived `shop` value straight to `begin_auth`, which is precisely the pattern shown in this gem's own `docs/usage/oauth.md` example (`shop = request.headers["Shop"]` then `Oauth.begin_auth(shop: domain, ...)`), and the inconsistency with `ShopValidator` usage elsewhere in the same file/gem suggests this was simply missed rather than intentionally left to callers.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `begin_auth`, exactly as is already done in `ClientCredentials.client_credentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, so that only a domain within `TRUSTED_SHOPIFY_DOMAINS` can ever be used to build the `auth_route`.

### Proof of Concept
1. Host application implements the login route exactly per this gem's documented example:
```ruby
def login
  shop = request.headers["Shop"] # or params[:shop]
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
  cookies[auth_response[:cookie].name] = { value: auth_response[:cookie].value, ... }
  redirect_to auth_response[:auth_route]
end
```
2. Attacker sends victim a link to `https://legitapp.com/login?shop=attacker-controlled.example`.
3. `begin_auth` sets the victim's `state` cookie and redirects the victim's browser to `https://attacker-controlled.example/admin/oauth/authorize?client_id=...&state=<NONCE>&redirect_uri=https://legitapp.com/auth/callback&...`.
4. Attacker's server, receiving this request, records `<NONCE>`.
5. Attacker independently performs a real OAuth authorization for their own Shopify store, obtaining a valid `code`/`hmac` for `attacker-shop.myshopify.com`.
6. Attacker forces the victim's browser (still holding the `state=<NONCE>` cookie) to `https://legitapp.com/auth/callback?shop=attacker-shop.myshopify.com&code=<attacker_code>&state=<NONCE>&hmac=<valid_hmac>&timestamp=...`.
7. `validate_auth_callback` passes HMAC and state checks and creates a session bound to `attacker-shop.myshopify.com` in the victim's browser context — a forced OAuth completion.
