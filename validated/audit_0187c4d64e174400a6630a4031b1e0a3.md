## Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers. `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body string, then `Webhooks::Registry.process` trusts `request.shop` to hand off tenant identity to the app's webhook handler. This breaks the identity binding `shop authenticated == shop used to key data`, enabling one tenant to replay another tenant's legitimate webhook body under a forged `shop-domain` header and have it accepted as valid for an arbitrary shop.

### Finding Description

and the shop identifier is pulled straight from a header, entirely outside that signed content: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC secret — it never incorporates `shop`, `topic`, or any header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then forwards `request.shop` directly to the handler as the authenticated tenant identity: [4](#0-3) 

Because Shopify signs app webhooks with the app's single `client_secret` shared across every installed shop (not a per-shop secret), any merchant that has installed the app receives legitimate `(body, hmac)` pairs for their own store through normal, unprivileged use of the app. That merchant can capture one such pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` passes the forged `shop` value straight through to `WebhookMetadata`, so the host app's handler processes attacker-controlled webhook content as if it originated from the victim tenant.

### Impact Explanation
This breaks tenant isolation: a malicious (but otherwise unprivileged) merchant can make the application process orders/customers/fulfillment/GDPR-type payloads it fully controls (the body from their own legitimate deliveries) while impersonating a different shop's identity in `WebhookMetadata#shop`. Any host application logic that keys persistence, side effects, or authorization decisions off `data.shop` (the documented, intended usage per the webhook doc) is exposed to cross-tenant data corruption or injection — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Medium-to-high: no `api_secret_key`, access token, or privileged account is required — only that the attacker themselves runs a shop that has installed the target app (the normal, unprivileged path any internet user can take), then replays one of their own captured webhook deliveries with a modified `shop-domain` header against the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic) into the authenticated content, e.g., include a canonicalized `shop-domain`/`topic` value in `to_signable_string`'s HMAC computation, or otherwise cross-check that the shop asserted in the header corresponds to a session/tenant record the app already trusts for that specific `webhook_id`/HMAC value, before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker POSTs the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only (`to_signable_string`), matches `H`, and validation passes.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, causing the app to act on attacker-controlled data under the victim's tenant identity.
