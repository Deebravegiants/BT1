Audit Report

## Title
LDAP DN Injection via unescaped bind-DN construction in login flow - (File: core/sessions/ldapauth/ldap.go)

## Summary
`CreateSession` and `TestPassword` in `core/sessions/ldapauth/ldap.go` build the LDAP bind DN by concatenating attacker-controlled email input sanitized only with `ldap.EscapeFilter`, which escapes LDAP *search-filter* metacharacters (`\`, `*`, `(`, `)`, NUL) but not LDAP *DN* metacharacters (`,`, `+`, `"`, `<`, `>`, `;`, leading `#`/space). This allows an unauthenticated caller submitting a crafted `email` to inject additional RDN components into the DN string passed to `conn.Bind()`.

## Finding Description
`CreateSession`, reachable from the unauthenticated `POST /sessions` endpoint via `SessionsController.Create` → `AuthenticationProvider().CreateSession`, constructs: [1](#0-0) 

```go
escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
```

`TestPassword` has the identical pattern: [2](#0-1) 

`sr.Email` originates directly from an unauthenticated JSON POST body with no validation beyond JSON binding: [3](#0-2) 

`ldap.EscapeFilter` is the wrong sanitizer for a value embedded in a DN string — it does not escape `,`, `+`, `"`, `<`, `>`, or `;`, all of which are structurally significant in RFC 4514 DN syntax. This is a genuine mismatch between the sanitization applied and the context (DN vs. filter) in which the value is used, confirmed by direct code inspection; no other validation or escaping is applied to `sr.Email`/`email` before DN construction in either function.

Note on practical exploitation: because the code always appends `,%s,%s` (UsersDN, BaseDN) after the injected value, an attacker's injected RDN components are inserted *before* the fixed suffix rather than replacing it. This constrains — but does not eliminate — exploitation: an attacker can still alter which RDN component(s) are targeted within the constructed DN (e.g., inserting extra RDNs or multi-valued RDNs via `+` ahead of the intended `UsersDN`/`BaseDN` suffix), changing the identity actually presented to `conn.Bind()` from what the application intends to enforce.

## Impact Explanation
This is a legitimate broken-security-assumption bug: the code assumes `ldap.EscapeFilter` neutralizes DN-significant input, which is false. An unauthenticated caller can alter the structure of the bind DN sent to the upstream directory, which maps to the "authentication/role bypass" and "request impersonation" impact categories, since role assignment downstream depends on `FindUser` being called with the same manipulated `escapedEmail`. The severity is tempered by the fact that the fixed `,UsersDN,BaseDN` suffix is always appended, limiting (but not eliminating) how far outside the intended subtree an attacker can steer the bind target.

## Likelihood Explanation
Reachable directly from an unauthenticated `POST /sessions` request, with the only precondition being that the node is configured with `AuthenticationMethod = 'ldap'` — a supported, documented authentication mode rather than an insecure misconfiguration. Crafting an email value containing DN metacharacters is trivial for a remote, unauthenticated attacker, making this a practical and repeatable defect once LDAP auth is enabled.

## Recommendation
Replace `ldap.EscapeFilter` with a DN-specific escaping routine (e.g., `ldap.EscapeDN` in `github.com/go-ldap/ldap/v3`, or manual RFC 4514-compliant escaping) for the value embedded in `searchBaseDN` in both `CreateSession` and `TestPassword`. Reserve `ldap.EscapeFilter` for values embedded in filter expressions only (as already done correctly in `FindUser`). Additionally, validate/normalize the email format before DN construction (e.g., reject characters outside the expected `uid`/email charset) as defense in depth.

## Proof of Concept
1. Configure the node with `WebServer.AuthenticationMethod = 'ldap'` against a test LDAP backend.
2. Send `POST /sessions` with body `{"email": "victim,ou=admins", "password": "attacker-known-password"}`.
3. Observe `searchBaseDN` in `CreateSession` (`core/sessions/ldapauth/ldap.go:407`) resolves to `uid=victim,ou=admins,ou=users,dc=example,dc=com` instead of the intended `uid=victim\2cou\3dadmins,ou=users,dc=example,dc=com`, demonstrating that unescaped DN metacharacters from unauthenticated input are structurally interpreted by `conn.Bind()` rather than treated as a literal value — confirming the sanitization mismatch and its exploitability, subject to the fixed-suffix constraint described above.
