### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches to the app's handler using a `shop` (and `topic`) value that is read from unauthenticated HTTP headers and never bound into that HMAC computation.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` accepts the webhook as authentic solely based on this signature: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute `HMAC(raw_body, api_secret_key)` and compare it to the `hmac-sha256` header — never touching `shop`, `topic`, or `webhook-id`: [3](#0-2) 

However, `request.shop` and `request.topic` are read straight from HTTP headers, which are entirely separate from `raw_body` and are not part of the signable string: [4](#0-3) 

The resulting, ostensibly "verified", `shop` value is then handed to the app's handler as trusted metadata: [5](#0-4) 

The identity binding that should hold is: `hmac == HMAC(shop ‖ topic ‖ raw_body, api_secret_key)`. What the gem actually verifies is `hmac == HMAC(raw_body, api_secret_key)`. Because a single app's `api_secret_key` is shared across every shop that has the app installed, this signature is shop-agnostic: any request body that legitimately produces a valid HMAC for one shop produces an identical, still-valid HMAC when replayed with a different `x-shopify-shop-domain` (or `shopify-shop-domain`) header pointing at a different shop. `Registry.process` has no mechanism to detect this substitution — it treats `Utils::HmacValidator.validate(request)` succeeding as proof the whole `WebhookMetadata` (including `shop`) is genuine, mirroring the report's core pattern of "a field acted on but not covered by the HMAC."

### Impact Explanation
An unprivileged attacker who merely has an app installed on their own Shopify store can legitimately trigger a webhook delivery to the app's endpoint (e.g., by creating an order, updating a product, or uninstalling the app) and capture the resulting `raw_body` + `hmac-sha256` header — both are visible to them since it's their own shop's traffic. Because the HMAC never binds to the shop, they can resend that exact `raw_body`/`hmac` pair while overwriting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the spoofed victim domain. Any host application logic keyed off `data.shop` (e.g., looking up/loading the victim's stored session or access token, updating per-shop billing/state, or triggering side effects scoped "by shop") will act as if the event came from the victim tenant — a cross-tenant confusion condition rooted entirely in this gem's webhook verification primitive.

### Likelihood Explanation
Requires only an app-installed, unprivileged Shopify merchant account (no special credentials, no access to the app's `api_secret_key` beyond what's naturally exposed via their own webhook deliveries) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a forged header — no TLS interception, no leaked secrets, no social engineering.

### Recommendation
Include `shop` (and ideally `topic`/`webhook-id`) in the signable material verified against the HMAC, or otherwise cryptographically bind the header-derived shop domain to the signed payload before it is trusted and forwarded to `WebhookMetadata`. At minimum, document and enforce that `WebhookMetadata#shop` is unauthenticated header data that must be independently cross-checked (e.g., against a shop known to have this webhook/topic registered) by consumers before using it to key any tenant-scoped state.

### Proof of Concept
1. Attacker owns Shop A with the target app installed; triggers an event (e.g. `app/uninstalled`) producing `raw_body = B` and a legitimate `x-shopify-hmac-sha256: H = HMAC_SHA256(api_secret_key, B)` header from Shopify.
2. Attacker replays a POST to the app's webhook endpoint with the same `B` and `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to a topic the attacker wants processed for the victim.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (headers only checked for presence, not authenticity) — see `lib/shopify_api/webhooks/request.rb` lines 45-63.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and compares to `H` — matches, since only `B` was signed.
5. The handler is invoked with `WebhookMetadata.new(topic: forged_topic, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on victim-shop-scoped data/state despite the event actually originating from the attacker's own shop.
