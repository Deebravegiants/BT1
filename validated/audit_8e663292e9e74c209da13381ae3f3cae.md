### Title
JWT rotation fallback treats an empty-string `old_api_secret_key` as a valid signing key, allowing session-token forgery - ([File: lib/shopify_api/auth/jwt_payload.rb](lib/shopify_api/auth/jwt_payload.rb))

### Summary
`ShopifyAPI::Auth::JwtPayload#initialize` verifies an incoming session token (JWT) first against `Context.api_secret_key`, and on failure falls back to `Context.old_api_secret_key` for key-rotation support. The fallback guard only checks for `nil`, not for an empty string, unlike the equivalent guard in `HmacValidator`.

### Finding Description
In `lib/shopify_api/auth/jwt_payload.rb`:
```ruby
payload_hash = begin
  decode_token(token, Context.api_secret_key)
rescue ShopifyAPI::Errors::InvalidJwtTokenError
  raise unless Context.old_api_secret_key

  decode_token(token, T.must(Context.old_api_secret_key))
end
``` [1](#0-0) 

`raise unless Context.old_api_secret_key` only treats `nil` as "no fallback key configured." In Ruby, an empty string `""` is truthy, so if `Context.old_api_secret_key` is set to `""` (e.g. during a key-rotation window where an operator blanks the old key rather than removing the parameter, or a misconfigured environment variable resolves to an empty string), the code proceeds to `decode_token(token, "")`, which calls `JWT.decode(token, "", true, algorithm: "HS256")`. This validates the signature using HMAC-SHA256 with an **empty key**, a key trivially known/guessable by anyone.

Contrast this with `lib/shopify_api/utils/hmac_validator.rb`, which explicitly guards against both `nil` and empty:
```ruby
if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
  result
else
  validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
end
``` [2](#0-1) 

This is the exact bug class from the report: a "lock"/identity-binding mechanism (here, the HMAC signature that binds a session token's claims — `dest` (shop), `sub` (user), `aud` (api key) — to the app's shared secret) silently becomes a no-op when the guarding value is an empty string instead of a properly-absent value.

If this path is reachable (i.e. an app operator has `old_api_secret_key: ""` configured), an unauthenticated attacker can:
1. Construct any JWT payload with `aud` set to the victim app's known `api_key` (public), `dest` set to any victim shop domain, and `sub` set to any user id.
2. Sign it with HMAC-SHA256 using the empty string as the key.
3. Submit it as a session token (e.g. via `SessionUtils.session_id_from_shopify_id_token` or `Auth::TokenExchange.exchange_token`) — the token passes `decode_token(token, Context.old_api_secret_key)` because the fallback check doesn't reject empty keys.
4. In `TokenExchange.exchange_token`, the forged token's `dest` claim becomes the shop used to request a real Shopify access token via token exchange, and `JwtPayload#shop`/`#shopify_user_id` derived from attacker-controlled claims are trusted directly. [3](#0-2) [4](#0-3) 

The identity binding broken: `shop (claimed in forged dest) == shop (session/token actually authorized for)` — this equality is supposed to be enforced by the HMAC signature over the JWT, but with an empty key it enforces nothing.

### Impact Explanation
If reachable, this is a full authentication bypass / cross-tenant impersonation: an attacker can mint session tokens for arbitrary shops and drive `TokenExchange` to obtain real offline/online access tokens for shops they don't control, meeting the "Critical" bar (authentication bypass, cross-tenant access, token theft path).

### Likelihood Explanation
Likelihood is low-to-moderate and conditional: it requires the host application to have explicitly configured `old_api_secret_key` as an empty string (rather than leaving it `nil`), which is a plausible but non-default misconfiguration during secret-rotation workflows (analogous to `@nonreentrant("")` being set instead of omitted). The default value of `old_api_secret_key` is `nil`, so out-of-the-box installations are not affected. I could not find any additional validation in `Context.setup` (`lib/shopify_api/context.rb`, lines 54-99) that rejects an empty-string `old_api_secret_key`, so nothing in the gem prevents this misconfiguration from being effective.

### Recommendation
In `lib/shopify_api/auth/jwt_payload.rb`, change the fallback guard to match `HmacValidator`'s pattern, rejecting both `nil` and empty-string old keys:
```ruby
raise if Context.old_api_secret_key.nil? || Context.old_api_secret_key.empty?
```

### Proof of Concept
Conceptual PoC (requires the app to be misconfigured with `old_api_secret_key: ""`):
```ruby
ShopifyAPI::Context.setup(
  api_key: "known_public_api_key",
  api_secret_key: "real_secret_key",
  old_api_secret_key: "",   # misconfiguration mirroring nonreentrant("")
  ...
)

forged_payload = {
  iss: "https://victim-shop.myshopify.com/admin",
  dest: "https://victim-shop.myshopify.com",
  aud: "known_public_api_key",
  sub: "1",
  exp: Time.now.to_i + 60,
  nbf: Time.now.to_i,
  iat: Time.now.to_i,
  jti: SecureRandom.hex,
}
forged_token = JWT.encode(forged_payload, "", "HS256")

# Passes because Context.old_api_secret_key ("") is truthy and used as the HMAC key
payload = ShopifyAPI::Auth::JwtPayload.new(forged_token)
payload.shop # => "victim-shop.myshopify.com", fully attacker-controlled
```
