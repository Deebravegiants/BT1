This confirms the vulnerability: `Webhooks::Request#to_signable_string` (in `lib/shopify_api/webhooks/request.rb`) returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unsigned HTTP headers via `shopify_header`. `Webhooks::Registry.process` validates only this body-based HMAC, then forwards the header-derived `shop` straight into `WebhookMetadata` passed to the app's handler.

### Title
Webhook shop identity not covered by HMAC allows any app-installing shop to forge webhooks impersonating another shop - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw request body only, never to the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `ShopifyAPI::Webhooks::Registry.process` validates that body-only HMAC and then trusts the unauthenticated `shop` header value when constructing `WebhookMetadata` for the app's handler, breaking the binding `shop-that-produced-the-HMAC == shop-attributed-to-the-request`.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` exclusively — no header is included in the signable material. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight off the (attacker-controllable, unauthenticated) HTTP headers: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, on success, immediately builds `WebhookMetadata` using `request.shop` from the header, without any cross-check that the header value matches the shop that actually produced the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` (and `validate_signature`) only ever operate on `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

Because a Shopify app uses a single, global `api_secret_key` shared across every shop that installs it (not a per-shop secret), any unprivileged merchant who has installed the app can:
1. Install the app on their own shop and receive a legitimate webhook — a `(raw_body, HMAC)` pair valid under the app's shared `client_secret`.
2. Replay that exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain (and optionally swap `x-shopify-topic`/`x-shopify-webhook-id`).
3. `HmacValidator.validate` recomputes the HMAC over `raw_body` alone, using the app's single shared secret — the signature still matches, because it never depended on the header values.
4. `Registry.process` calls the registered `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))` with the forged `shop` value, so the app processes attacker-controlled body content while believing it originates from the victim shop.

The equality this breaks is: `shop asserted by the HMAC's signer == shop attributed to this request by the gem`. Before the attack, both sides equal the shop that produced the HMAC. After the attacker's forged request, the left side is still "any shop holding the shared secret" but the right side becomes an arbitrary victim shop domain chosen by the attacker — the gem never re-derives or checks the shop from signed material.

### Impact Explanation
This crosses a tenant boundary: any unprivileged merchant with a legitimate app installation (no special privilege, no leaked credentials, no access token needed) can make the app attribute attacker-chosen webhook payloads to an arbitrary victim `shop` value. Depending on how the host application keys its per-shop data/session lookups off `WebhookMetadata#shop` (which is the gem's documented/intended field for that purpose), this enables cross-tenant data corruption or state confusion — e.g., an app that updates victim-shop records, revokes/synchronizes settings, or triggers side effects keyed only by this unauthenticated `shop` field.

### Likelihood Explanation
Any user who can install the app on their own store obtains a valid `(body, HMAC)` pair effortlessly (every webhook Shopify sends them is a valid pair), and only needs to change one HTTP header before replaying it. No brute force, no secret leakage, and no privileged access are required — only the ability to install the app, which is the baseline unprivileged capability for any Shopify merchant.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the header claims to the verified body — e.g., include the `shop-domain` header in `to_signable_string`, or require callers to independently verify `request.shop` against a per-shop secret/session record before trusting it, rather than relying solely on the shared `api_secret_key`-based body HMAC to authenticate shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook: body `{"id":123}"` with header `x-shopify-hmac-sha256: <HMAC computed with the app's shared client_secret over the body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` matches (body unchanged) and whose `shop` now returns `"victim-shop.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)` → `true` (body-only check passes), then dispatches `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: {"id"=>123}, ...))`, exactly as demonstrated by the test harness's own webhook construction pattern (only headers vary, body/HMAC computed once): [5](#0-4) 
The app's handler now processes attacker-controlled data attributed to the victim shop.
