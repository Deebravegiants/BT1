Confirmed. `Utils::VerifiableQuery#to_signable_string` is the only thing fed into the HMAC digest, and for `Webhooks::Request` (`lib/shopify_api/webhooks/request.rb:36-38`) that returns only `@raw_body`. ### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body via `Utils::HmacValidator.validate` [1](#0-0) . The signable string used for that HMAC is defined by `Webhooks::Request#to_signable_string`, which returns only `@raw_body` [2](#0-1) . The `shop` (and `topic`/`webhook_id`/`api_version`) values consumed by the handler come from HTTP headers that are read independently of the HMAC-covered bytes [3](#0-2) . Because the shop identity is never part of the signed material, a valid HMAC for one shop's body does not bind to that shop.

### Finding Description
Any merchant can install the app on their own store and receive genuine, correctly-signed webhooks for topics that they can trigger themselves (e.g. `orders/create`, `carts/update`, `customers/create`, depending on what the host app registers). Because the HMAC only covers `raw_body` [4](#0-3) , this attacker-merchant can capture one such legitimately-signed `(raw_body, hmac)` pair and then POST it directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with an arbitrary victim shop's domain. `HmacValidator.validate` recomputes `HMAC(secret, raw_body)` and compares it with `OpenSSL.secure_compare` [5](#0-4) ; since `raw_body` is untouched, validation succeeds regardless of which shop header is attached. `Registry.process` then invokes the registered handler with `shop: request.shop` set to the attacker-chosen victim domain and `body: request.parsed_body` set to the attacker's own crafted payload [6](#0-5) .

The identity binding that should hold is: `shop cryptographically authenticated by HMAC == shop the handler attributes the data to`. Before the request: the real webhook for the attacker's own store has `(shop = attacker.myshopify.com, hmac = HMAC(secret, body))`. After the attacker's crafted request: `(shop header = victim.myshopify.com, hmac = HMAC(secret, body))` — the same HMAC now accompanies a different claimed shop, and the check passes because the shop was never part of what the HMAC certifies.

### Impact Explanation
Any app whose webhook handlers use `data.shop` to select tenant-scoped storage, state transitions, or side effects (the documented, intended use of `WebhookMetadata#shop`) can be made to act on/associate attacker-supplied data with a victim shop it has never interacted with — a cross-tenant data injection/attribution vulnerability triggered by an unprivileged internet user who merely needs their own (unprivileged) shop installation to mint a validly-signed payload.

### Likelihood Explanation
High. No secret material is required by the attacker; they only need to be a legitimate merchant of some shop where the app is installed (which is the normal, unprivileged way to use the app) to obtain a real `(body, hmac)` pair, and then replay it with a rewritten header via any HTTP client. `Registry.process` performs no additional check that the header-derived shop matches any authenticated claim.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) inside the HMAC-covered signable string, or otherwise cryptographically bind the `shopify-shop-domain` header to the signed body before trusting it as the tenant identity passed to webhook handlers.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` and trigger a webhook topic the app has registered (e.g. create an order), capturing the real `X-Shopify-Hmac-Sha256` header and raw body Shopify sent to the app's webhook endpoint.
2. Replay that exact raw body and HMAC header to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate` which passes (body unchanged), then invokes the handler with `shop: "victim.myshopify.com"` and the attacker's chosen body content [7](#0-6) .
