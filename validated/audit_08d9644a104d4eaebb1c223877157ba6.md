### Title
Missing re-initialization guard in `LockupContract::new()` allows an unprivileged caller to hijack contract ownership - (File: `lockup/src/lib.rs`)

### Summary
Every other production contract in the audited set (`lockup-factory`, `multisig`, `staking-pool`, `staking-pool-factory`, `whitelist`) protects its `#[init]` constructor with an explicit `assert!(!env::state_exists(), "Already initialized")` guard. `lockup/src/lib.rs`'s `LockupContract::new()` does not contain this guard, so `new()` can be invoked again after the contract has already been deployed and initialized.

### Finding Description
The Note.sol bug (H-11) is fundamentally an authorization-check placed on the wrong branch of an "is this the first call?" condition, letting an unprivileged caller win a race to become the privileged party. The `lockup` contract exhibits the analogous root cause in the initialization flow itself: near-sdk 3.1.0's `#[init]` macro does not implicitly enforce a single-initialization invariant — each contract must add its own `assert!(!env::state_exists(), ...)` check. [1](#0-0) , [2](#0-1) , and [3](#0-2)  all explicitly assert `!env::state_exists()` before initializing.

`lockup/src/lib.rs`'s `new()` has no such assertion: [4](#0-3) 

Because the lockup account is a "key-less" account (per design, it should have no access keys so only the contract logic can move funds), anyone can still submit a `FunctionCall` transaction targeting the deployed lockup contract's `new` method (function calls don't require the *target* account to hold a key, only the caller's own signing key to pay gas). Since `new()` unconditionally overwrites `owner_account_id`, `foundation_account_id`, `vesting_information`, `staking_information`, and `lockup_information` without checking whether the contract has already been initialized, an attacker can call `new()` on an already-initialized, funded lockup contract and set themselves as `owner_account_id` (and/or `foundation_account_id`).

### Impact Explanation
Once the attacker becomes `owner_account_id`, they gain full access to all owner-only methods in `lockup/src/owner.rs`, gated only by `assert_owner()`: [5](#0-4) . This includes selecting a malicious staking pool, withdrawing available balance, and ultimately directing the locked NEAR tokens to accounts of the attacker's choosing — an unauthorized transfer/withdrawal of locked funds reachable by an unprivileged user via a public-call state-transition bypass. This matches the Critical/High impact classes for unauthorized transfer/withdrawal and state-transition bypass in the lockup flow.

### Likelihood Explanation
The likelihood is high once discovered: the attack requires only submitting a single `FunctionCall` transaction with attacker-chosen arguments to the already-deployed lockup contract's `new` method, no special privileges, keys, or races against a legitimate first call are needed (unlike the Note.sol front-run scenario, here the contract is *already* initialized and funded, so the attacker can strike at any time after deployment, not just at deployment race time).

### Recommendation
Add the same reinitialization guard used in all sibling contracts to `LockupContract::new()`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
This should be inserted at the very top of the `new()` function in `lockup/src/lib.rs`, before any other logic, mirroring the pattern in `lockup-factory`, `multisig`, `staking-pool`, `staking-pool-factory`, and `whitelist`.

### Proof of Concept
1. Deploy and initialize `lockup1` via `lockup-factory` normally (owner = `owner1`, funded with locked NEAR).
2. As an unprivileged attacker account `evil`, submit:
```bash
near call lockup1 new '{"owner_account_id": "evil", "lockup_duration": "0", "lockup_timestamp": "0", "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}}, "vesting_schedule": null, "release_duration": null, "staking_pool_whitelist_account_id": "staking-pool-whitelist", "foundation_account_id": null}' --accountId=evil --gas=25000000000000
```
3. Because `new()` never checks `env::state_exists()`, this call succeeds and overwrites `owner_account_id` to `evil`.
4. `evil` now calls owner-only methods (e.g. `select_staking_pool`, withdraw flows) since `assert_owner()` now passes for `evil`, allowing extraction of the locked NEAR balance.

**Note on verification limits:** I was not able to execute the contract to confirm runtime behavior (no sandbox/terminal access in this mode), and I could not fully inspect the near-sdk 3.1.0 macro-expansion source to rule out any implicit re-init protection at the SDK level beyond what is documented/observed by comparison with sibling contracts in this same codebase. The consistent presence of the explicit guard in every other `#[init]` constructor in this repo, and its absence specifically in `lockup/src/lib.rs`, is the strongest evidence of a genuine, codebase-specific gap.     #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
