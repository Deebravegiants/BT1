Front-runnable pool creation lets an attacker squat the deterministic PDA seeds and hijack `Initialize2` before the intended creator - (File: program/src/processor.rs)

### Summary
`process_initialize2` derives all of a pool's core accounts (target orders, lp mint, coin vault, pc vault, amm info) as deterministic PDAs seeded only by `market_info.key` and fixed suffix constants, and `market_info` itself is explicitly unchecked/unvalidated ("can be any account"). Because these PDAs are fully predictable from public inputs, and the instruction can be invoked by any unprivileged signer with attacker-chosen `init_pc_amount`/`init_coin_amount`, an attacker can race ahead of the intended pool creator and consume these PDAs first, establishing an attacker-controlled initial price ratio and minimal liquidity, then permanently blocking the legitimate creator's `Initialize2` call for that same market/mint pair. This mirrors the reported bug class: a value/condition that is supposed to reflect the intended actor's own state is instead derived from and can be pre-empted by an unrelated third party manipulating an address ahead of time.

### Finding Description
`process_initialize2` computes the coin vault, pc vault, lp mint, target-orders and amm-info addresses via `get_associated_address_and_bump_seed`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`/`generate_amm_associated_account`, all seeded by `[program_id, market_account.key, associated_seed]`: [1](#0-0) 

These helper functions only check that the target address matches the derived PDA and that it is *currently* owned by the system program; if it is already owned by another program (i.e., already created), they simply fail with `RepeatCreateAmm` rather than verifying the caller has any right to that market: [2](#0-1) [3](#0-2) 

Crucially, the instruction documentation itself states `market_info` is "Just a seed for AMM account. Can be any account", and the code performs no signer check, no ownership check tying it to a real market/creator, and no check that the caller has any special permission over it: [4](#0-3) [5](#0-4) 

Because `market_info.key` is the only unique input tying a set of vault/mint/target-orders PDAs to a pool, and it is unauthenticated, anyone can pick the same `market_info`/mint pair that a legitimate creator intends to use, and submit their own `Initialize2` transaction with attacker-chosen `init_pc_amount`/`init_coin_amount` (even as low as the smallest representable unit of each mint) before the legitimate creator's transaction lands. The attacker's transaction creates the PDAs first via `generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`/`generate_amm_associated_account`, transfers only the attacker's own chosen (tiny/skewed) amounts into the coin/pc vaults, and computes the pool's exact initial invariant, LP amount, and price purely from those attacker-controlled vault balances: [6](#0-5) [7](#0-6) 

Once the attacker's `Initialize2` succeeds, the AMM account's `status` moves from `Uninitialized`, so the legitimate creator's subsequent `Initialize2` call for that exact market/mint pair now fails at the `AlreadyInUse` check: [8](#0-7) 

This is directly analogous to the reported vulnerability class: a critical operation's outcome is gated on/derived from state at an address that is not exclusively controlled by the intended caller, and that address can be manipulated/occupied by a front-running third party, permanently interfering with the intended actor's ability to complete the operation as designed.

### Impact Explanation
An attacker can permanently seize the canonical pool for any given coin/pc mint pair before the legitimate team/LP does, setting whatever initial coin/pc ratio and (near-zero) liquidity they choose. Because the resulting `amm_coin_vault`/`amm_pc_vault` balances directly determine `liquidity`/`user_lp_amount` (and thus the pool's starting price and LP supply), the attacker fully controls the economic parameters of "the" pool for that mint pair, can immediately manipulate price via `SwapBaseIn`/`SwapBaseOut` against the minimal liquidity, and denies the legitimate creator the ability to ever initialize a pool at that market key (permanent `AlreadyInUse`/`RepeatCreateAmm` denial of service combined with economic hijacking of subsequent depositors/swappers who interact with the attacker's pool believing it to be the legitimate one).

### Likelihood Explanation
Exploitation requires only observing or predicting an upcoming pool-creation transaction (e.g., via mempool/simulation, or simply choosing to create a pool for a popular new token pair before the legitimate team) and submitting a single ordinary `Initialize2` transaction with attacker-chosen accounts/data ahead of it — no privileged signer, no validator collusion, and no off-chain dependency beyond normal transaction ordering/racing. This is reachable by any unprivileged user in a single transaction, matching the in-scope threat model.

### Recommendation
Tie pool creation to a verifiable, creator-exclusive input rather than an arbitrary, attacker-guessable `market_info` account — e.g., require `market_info` to be a genuine, validated market account (as the deprecated `Initialize` path implies) or bind the derived PDAs to the creator's own signer key / a nonce reserved in advance, and add an explicit check that the intended coin/pc mint pair for a given market has not already been claimed by a different, unauthenticated party before allowing funds to be committed based on the resulting vault balances.

### Proof of Concept
1. Attacker observes (or anticipates) that a creator intends to call `Initialize2` for mint pair `(coin_mint, pc_mint)` using some `market_info` key `M`.
2. Attacker computes the same PDAs `get_associated_address_and_bump_seed(program_id, M, COIN_VAULT_ASSOCIATED_SEED/PC_VAULT_ASSOCIATED_SEED/LP_MINT_ASSOCIATED_SEED/TARGET_ASSOCIATED_SEED/AMM_ASSOCIATED_SEED, program_id)` themselves (all inputs are public).
3. Attacker submits their own `Initialize2` transaction using `M`, `coin_mint`, `pc_mint`, and attacker-chosen `init_coin_amount`/`init_pc_amount` (e.g., minimal amounts skewing the price), landing before the legitimate creator's transaction.
4. `process_initialize2` succeeds for the attacker: it creates the PDAs at lines 748-814, transfers only the attacker's funds at lines 827-841, and sets `amm.status` away from `Uninitialized`.
5. The legitimate creator's `Initialize2` transaction for the same `M`/mint pair now fails at the `AlreadyInUse` check (line 845-847), permanently denying them the canonical pool while the attacker's manipulated pool remains live for third parties to swap/deposit into.
