### Title
Unchecked `U128::as_u64()` truncation in swap fee calculation allows pool drain via integer wraparound - (File: program/src/processor.rs, program/src/math.rs)

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` compute the amount a swapper must pay (`swap_in_after_add_fee`) as a `U128` value and then narrow it to `u64` using the unchecked `.as_u64()` conversion method from the `uint` crate's `U128` type [1](#0-0) . Unlike `Calculator::to_u64()`, which uses `try_into()` and returns `AmmError::ConversionFailure` on overflow [2](#0-1) , `.as_u64()` silently truncates to the low 64 bits with no overflow check. If the pre-truncation value exceeds `u64::MAX`, the resulting charge amount wraps to an arbitrarily small number while the full `swap.amount_out` is still paid out to the attacker.

### Finding Description
In `process_swap_base_out`, the amount the user must deposit is computed entirely in `U128` arithmetic and only converted to `u64` at the very last step via `.as_u64()`: [3](#0-2) 

The same unchecked pattern exists in the `_v2` variant of the instruction: [4](#0-3) 

`total_pc_without_take_pnl` / `total_coin_without_take_pnl` are derived directly from the actual SPL token vault balances, which are attacker-controllable because pool creation (`Initialize2`) and the associated mints/vaults are permissionless and unprivileged — any user can create a pool with a custom SPL mint holding a total supply near `u64::MAX` and deposit it into the pool's coin/pc vaults. `swap_token_amount_base_out` then computes `swap_in_before_add_fee` as a function of these huge reserves [5](#0-4) , and `swap_in_after_add_fee = swap_in_before_add_fee * fee_denominator / (fee_denominator - fee_numerator)` inflates that value by roughly 0.25% before truncating with `.as_u64()`. If `swap_in_before_add_fee` is crafted (via `swap.amount_out`) to sit just under `u64::MAX / 1.0025`, the fee-inflated value crosses `u64::MAX` and wraps to a small residual value. This mirrors the reported root cause pattern exactly: an unchecked narrowing numeric conversion (`int k` in the CVE vs. `U128::as_u64()` here) causes a value used to drive a memory/fund operation to be computed from stale or wrapped data instead of the true magnitude.

### Impact Explanation
Because the wrapped `swap_in_after_add_fee` is used both for the "sufficient funds" check and the actual SPL token transfer amount taken from the user: [6](#0-5) 

the attacker deposits only the truncated (small) amount into the vault while receiving `swap.amount_out` — up to nearly the entire opposing-side reserve — via `Invokers::token_transfer_with_authority`. This is concrete theft of pool/LP funds and results in immediate insolvent pool accounting (assets drained without matching consideration).

### Likelihood Explanation
Exploitation requires the attacker to control the pool's reserve magnitude, which is achievable because pool creation and both token mints in `Initialize2` are fully attacker-chosen and unprivileged. The attacker can mint an SPL token with supply near `u64::MAX`, create a new Raydium pool with that mint as one side, seed the reserves via `Initialize2`/`Deposit`, then invoke `SwapBaseOut`/`SwapBaseOut2` with an `amount_out` engineered to push `swap_in_after_add_fee` just past `u64::MAX`. This is executable in a single transaction with attacker-supplied accounts and instruction data, matching the "single submitted transaction, attacker-chosen accounts/data" reachability bar.

### Recommendation
Replace `.as_u64()` in the `swap_in_after_add_fee` computations of `process_swap_base_out` and `process_swap_base_out_v2` with `Calculator::to_u64()` (or an equivalent checked conversion) so overflow triggers `AmmError::ConversionFailure` instead of silently wrapping. Audit all other `.as_u64()`/`.as_u128()` call sites in `program/src/processor.rs` and `program/src/math.rs` that feed directly into token-transfer amounts for the same unchecked-narrowing pattern.

### Proof of Concept
1. Attacker mints a custom SPL token `X` with total supply close to `u64::MAX` and controls both the coin and pc mints for a new pool.
2. Attacker calls `Initialize2` to create a Raydium pool seeded with large `init_coin_amount`/`init_pc_amount` (near `u64::MAX`), making `total_pc_without_take_pnl`/`total_coin_without_take_pnl` similarly large.
3. Attacker calls `SwapBaseOut` (or `SwapBaseOut2`) with `swap.amount_out` chosen such that `swap_token_amount_base_out(...)` yields `swap_in_before_add_fee` just below `u64::MAX / (denominator/(denominator-numerator))`, so that after the fee inflation and `.as_u64()` truncation at [7](#0-6)  the resulting `swap_in_after_add_fee` wraps to a small value (e.g., near 0).
4. The `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` checks trivially pass with a near-empty attacker wallet.
5. The program transfers the small wrapped amount from the attacker to the vault, then transfers the full (huge) `swap.amount_out` from the vault to the attacker — draining the pool.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
```
