### Title
Unsafe cache key concatenation in `getCachedStorageDepositValue` can collide across distinct `(contractId, accountId)` pairs, returning stale storage-deposit state - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key as `` `${contractId}${accountId}` `` with no separator, so two different `(contractId, accountId)` pairs can produce the identical key string. `estimateWithdrawalFee` trusts this cache to decide whether `storageDepositFee` is `0n`, so a collision can cause the fee estimator to report `0n` for a token/destination pair that actually requires a nonzero storage deposit.

### Finding Description
The broken equality: the cache lookup for `(contractId, accountId)` must return the storage-balance tuple `[minStorageBalance, userStorageBalance]` that corresponds *exactly* to that `(contractId, accountId)` pair. Instead, the key is computed as plain string concatenation without a delimiter [1](#0-0) , so `contractId="a", accountId="bc"` and `contractId="ab", accountId="c"` (or any pair where one contract id is a prefix of the other and the account-id suffixes complement each other) both hash to key `"abc"`.

Exploit flow:
1. Attacker calls `estimateWithdrawalFee` for `assetId` whose parsed `tokenAccountId` is `contractId1`, and a `destinationAddress = accountId1` where they already control storage registration (`userStorageBalance >= minStorageBalance`). Because `result[1] >= result[0]`, the tuple is cached under key `contractId1+accountId1` [2](#0-1) .
2. Attacker later calls `estimateWithdrawalFee` for a different `assetId`/`contractId2` and `destinationAddress = accountId2`, chosen so that `contractId2+accountId2 === contractId1+accountId1` (string collision). The cache lookup at line 278 returns the *stale* tuple from step 1 instead of querying real RPC state for `(contractId2, accountId2)`.
3. `minStorageBalance <= userStorageBalance` short-circuits to `feeAmount = 0n` [3](#0-2) , even though the real destination has no storage registered on `contractId2`.
4. `createWithdrawalIntents` then sets `storageDeposit: getUnderlyingFee(..., "storageDepositFee")` to `0n` in the withdraw intent [4](#0-3) .

Existing guards do not prevent this: `validateWithdrawal` checks address format/existence but not storage balance [5](#0-4) , and there is no per-pair uniqueness assertion on the cache key itself.

However, exploitability is tightly constrained by NEAR's account-naming rules: `contractId1`/`contractId2` must both be real, deployed NEP-141-compatible contracts that respond successfully to `storage_balance_bounds`/`storage_balance_of` RPC calls, and the two contract ids must be in a prefix/suffix relationship with the chosen account ids to produce an exact string collision. Constructing such a collision requires either (a) finding two already-deployed tokens whose account ids happen to satisfy this relationship, or (b) the attacker registering/deploying their own NEAR account+contract with a name precisely matching `contractId1 + accountId1[0..k]`, which is permissionless on NEAR but still a nontrivial, deliberate setup step, not an incidental one.

### Impact Explanation
If exploited, the withdrawal intent's `storage_deposit` field is signed as `0` for a destination that actually needs a deposit, meaning the on-chain `ft_transfer`/`ft_transfer_call` to an unregistered receiver will fail per NEP-141 semantics, leaving the withdrawal stuck in the bridge/intents contract until manual recovery (relayer/support must diagnose and reissue with a correct deposit) rather than funds being irrecoverably lost or redirected. This matches the **High** category ("a withdrawal stuck until manual intervention") rather than Critical, since NEP-141 transfers to unregistered accounts revert atomically rather than draining funds. If the `DirectBridge`/cache instance is shared across multiple end users by an integrator (a single long-lived SDK instance serving a hosted service), a successfully engineered collision could also silently poison another user's fee estimate for an unrelated withdrawal.

### Likelihood Explanation
Low-to-moderate. The attacker fully controls `assetId` and `destinationAddress` inputs to `estimateWithdrawalFee` (an ordinary SDK caller), and NEAR account registration/contract deployment is permissionless, so constructing a colliding pair is theoretically achievable at attacker's own cost (registering/deploying a contract account whose name satisfies the prefix condition, and ensuring it implements the NEP-141 storage interface). But it requires deliberate, nontrivial setup (a real deployed second token contract with a specific literal account-id relationship to the first), not something that happens by accident on typical inputs. It is repeatable once a colliding pair is established (cache TTL is 1 hour, `max: 100`).

### Recommendation
Use a delimiter/hash that cannot produce collisions when building the cache key, e.g. `` `${contractId}::${accountId}` `` (with a character disallowed in NEAR account ids) or a structured key such as `JSON.stringify([contractId, accountId])`, in `getCachedStorageDepositValue`.

### Proof of Concept
```ts
// vitest, mocking only the NEAR RPC (nearProvider.query) used by
// getNearNep141MinStorageBalance / getNearNep141StorageBalance
it("cache key collision returns stale storage state for a different (contractId, accountId) pair", async () => {
  const bridge = new DirectBridge({ envConfig, nearProvider, solverRelayApiKey: undefined });

  // Pair 1: contractId="a", accountId="bc" -> already registered (bal >= min)
  mockRpc({ contractId: "a", accountId: "bc", min: 1250000000000000000000n, bal: 1250000000000000000000n });
  const fee1 = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:a", destinationAddress: "bc", routeConfig: undefined },
  });
  expect(fee1.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(0n);

  // Pair 2: contractId="ab", accountId="c" -> NOT registered (bal < min), distinct real state
  mockRpc({ contractId: "ab", accountId: "c", min: 1250000000000000000000n, bal: 0n });
  const fee2 = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:ab", destinationAddress: "c", routeConfig: undefined },
  });

  // Broken equality: fee2.storageDepositFee should equal (min - bal) = 1250000000000000000000n
  // but the collided cache key "abc" makes it incorrectly return the pair-1 cached tuple.
  expect(fee2.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(
    1250000000000000000000n, // expected real value
  ); // actual observed value will be 0n due to the collision, demonstrating the bug
});
```
