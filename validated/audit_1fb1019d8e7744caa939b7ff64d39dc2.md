## Title
Malformed cross-chain `from` field in `HyperFungibleToken::on_accept` calldata path causes runtime panic / message-delivery DoS - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `IsmpModule::on_accept` handler decodes an ABI-encoded `Message` from an incoming ISMP `PostRequest` and, when `message.data` is non-empty and carries no signature, derives a dispatch origin directly from the attacker-controlled `message.from` bytes without validating their length before indexing/copying into a fixed-size buffer.

### Finding Description
In the unsigned-calldata branch of `on_accept`: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

`message.from` is fully attacker-controlled: it is a field of the ABI-decoded `Message` struct taken straight from the ISMP request body relayed from the source chain. [2](#0-1) 

Unlike the sibling `to`/`from` length checks used elsewhere in the same function and in `on_timeout` (which explicitly validate for 32 or 20 bytes and return a typed error otherwise): [3](#0-2) [4](#0-3) 

the branch at lines 177-186 performs no such validation:
- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing either an immediate arithmetic-overflow panic (debug/overflow-checks builds) or a huge wrapped start index that then panics on the out-of-range slice.
- On the non-EVM branch, `account.copy_from_slice(from_bytes)` panics unless `from_bytes.len()` is exactly 32 — any other length (which is entirely plausible/unenforced for the `from` field emitted by a Substrate `HyperFungibleToken` counterpart or a hand-crafted malicious message) triggers `panic!("source slice length ... does not match destination slice length")`.

This mirrors the CVE-2016-7044 bug class: a parser reads a field assuming a well-formed/complete length and performs unchecked pointer/slice arithmetic on it, and a truncated/malformed input drives that arithmetic out of bounds, crashing the process instead of returning a typed error — exactly the pattern this codebase's own regression tests elsewhere explicitly guard against (e.g. `empty_hp_prefix_returns_error_not_panic`, `nibble_at_depth` bounds checks, BOHR-fork extra-data length checks).

### Impact Explanation
`on_accept` is invoked by `pallet-ismp`'s message-handling path (`handle_unsigned`) when any relayer delivers a valid ISMP POST proof destined for the `hyper-fungible-token` pallet with non-empty `data` and no `substrate_data.signature`. A single malicious or malformed cross-chain message (with a `from` field shorter than 20/32 bytes as appropriate) causes a Rust panic during WASM execution of the extrinsic. Since this occurs inside on-chain state-transition logic (whether via signed dispatch, the free "handle_unsigned" unsigned extrinsic path, or block-import re-execution by every node), the panic traps the WASM runtime for that block, halting import for all nodes that receive/execute the block — a chain-halting Denial of Service and a route rendered unable to deliver any further token-bridge messages until fixed, satisfying the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Reachability is high: any relayer/attacker can submit a message from a *counterparty* HFT contract/pallet address that has been registered via `ContractToAsset` (a normal, expected registration, not requiring privileged access on this chain), with `data` containing a `SubstrateCalldata` whose `signature` field is `None` and whose `from`/`message.from` bytes are simply not 20/32 bytes. No governance or admin compromise is needed — only a standard relayed proof/message delivery, matching the required "single relayed proof / dispatched request" threat model.

### Recommendation
Validate `from_bytes.len()` before use in both branches, mirroring the existing `to_bytes`/`InvalidRecipientLength` and `on_timeout`'s `InvalidSenderLength` checks:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    if from_bytes.len() != 20 { Err(HftError::InvalidSenderLength(from_bytes.len()))? }
    T::EvmToSubstrate::convert(H160::from_slice(from_bytes))
} else {
    if from_bytes.len() != 32 { Err(HftError::InvalidSenderLength(from_bytes.len()))? }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```
Add a regression test analogous to the repo's existing "Regression: ... must now return an Err cleanly" pattern for a truncated/oversized `message.from`.

### Proof of Concept
1. Register a counterparty EVM `HyperFungibleToken` contract address for `source` via the normal `ContractToAsset` registration flow (standard integration step, not privileged in the sense of requiring a governance compromise to exploit once a token is live).
2. Craft an ISMP `PostRequest` whose ABI-encoded `Message.data` decodes to a `SubstrateCalldata` with `signature: None` and any non-empty `runtime_call`.
3. Craft `Message.from` to be any byte length other than 20 (source is EVM) — e.g. 5 bytes.
4. Relay this request with a valid state/consensus proof through `handle_unsigned`; when `on_accept` executes the unsigned-calldata branch, `from_bytes.len() - 20` underflows / the subsequent slice indexing panics, aborting block execution.

*(Note: I was not able to independently verify whether `overflow-checks` are enabled in the runtime's release WASM build config, which determines whether the subtraction panics immediately versus wrapping into an out-of-range slice that panics — either way a panic results, so the DoS outcome holds in both cases. A Devin session with full build access would be needed to confirm the exact panic message/config.)*
