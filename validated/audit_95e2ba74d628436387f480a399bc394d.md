### Title
Gateway HTTP trigger response handler always reports `NoError`/success even when all nodes agree on a JSON-RPC error, masking failed workflow executions - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.HandleNodeTriggerResponse` aggregates identical node responses via `IdenticalNodeResponseAggregator` and forwards the aggregated payload to the external caller, but it hardcodes `ErrorCode: api.NoError` regardless of whether the aggregated JSON-RPC response actually contains a `jsonrpc.WireError`. This is the same bug class as the reported `settlement.cairo` issue: the outer/transport-level status is unconditionally marked SUCCESS even though the underlying result may indicate FAILED.

### Finding Description
`IdenticalNodeResponseAggregator.CollectAndAggregate` matches responses purely by content digest — it has no concept of success/failure and will happily reach quorum on an *error* response (confirmed by the aggregator's own test `"error responses are handled correctly"` in `response_aggregator_test.go`, which shows `CollectAndAggregate` returning a response whose `Error` field is populated). [1](#0-0) 

In `HandleNodeTriggerResponse`, once `agg.CollectAndAggregate` returns a non-nil aggregated response (`aggResp`), the handler marshals it and sends it to the user with `ErrorCode: api.NoError` unconditionally — it never inspects `aggResp.Error`: [2](#0-1) 

Immediately after, the handler unconditionally increments the success metric: [3](#0-2) 

This is inconsistent with how other gateway handlers correctly propagate node error status to the outer response. For example, `vault/handler.go`'s `sendSuccessResponse` explicitly checks `resp.Error != nil` before choosing an `ErrorCode`: [4](#0-3) 

The `ErrorCode` returned in `UserCallbackPayload` is not just a metrics label — it directly drives the HTTP status code returned to the unprivileged caller who initiated the HTTP trigger, via `gateway.ProcessRequest`: [5](#0-4) 

Because `HandleNodeTriggerResponse` always passes `api.NoError`, `api.ToHTTPErrorCode` always maps to a success HTTP status code, even when the DON-agreed JSON-RPC payload embeds a `WireError` (e.g., a capability/workflow execution failure that all nodes deterministically returned).

### Impact Explanation
An unprivileged external client invoking an HTTP-triggered workflow (via the internet-facing gateway) receives an HTTP success status code for a request whose workflow execution actually failed (JSON-RPC `error` object present in the body). Callers that gate business logic on HTTP status (a very common integration pattern) will treat a failed workflow run as successful, potentially causing downstream systems to proceed as if an action completed when it did not — directly mirroring the "failed transaction marked as successful" impact from the reported analog. It also pollutes the `IncrementRequestSuccess` metric, undermining failure-rate observability/alerting for this gateway.

### Likelihood Explanation
This triggers any time all responding nodes deterministically agree on an error result (e.g., a workflow that always fails validation, hits a capability error, or intentionally returns a JSON-RPC error) — a normal occurrence, not an attack-dependent edge case. No malicious actor is required; a legitimate unprivileged HTTP caller triggering a workflow that errors out consistently across the DON will observe this.

### Recommendation
In `HandleNodeTriggerResponse`, inspect `aggResp.Error` (mirroring the pattern already used in `vault/handler.go`'s `sendSuccessResponse`) and set `ErrorCode` accordingly (e.g., map to an appropriate error code such as `api.HandlerError`) before calling `SendResponse`, and only increment `IncrementRequestSuccess` when the aggregated response carries no error.

### Proof of Concept
1. Register an HTTP-triggered workflow assigned to a DON/shard.
2. Have the unprivileged caller send an HTTP trigger request via the gateway (`HandleUserTriggerRequest`).
3. Have `2f+1` (threshold) nodes for the shard deterministically return the same JSON-RPC error response (e.g., simulate a workflow that fails validation and every node returns identical `WireError`) to `HandleNodeTriggerResponse`.
4. Observe: `agg.CollectAndAggregate` reaches threshold and returns the error-bearing response; `HandleNodeTriggerResponse` sends it with `ErrorCode: api.NoError`; `gateway.ProcessRequest` returns `api.ToHTTPErrorCode(api.NoError)` (a success HTTP status) to the caller alongside a JSON-RPC body that contains `"error": {...}`.
