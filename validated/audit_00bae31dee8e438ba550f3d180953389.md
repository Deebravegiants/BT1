### Title
Webhook `shop` domain is not covered by HMAC verification, allowing tenant spoofing in `ShopifyAPI::Webhooks::Request` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable signable string solely from the raw request body (`to_signable_string` returns `@raw_body`) [1](#0-0) . The `shop` value that the app relies on to identify which merchant/tenant sent the webhook is read from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header [2](#0-1) , a field that is never included in the HMAC-signed content. `Utils::HmacValidator.validate` recomputes the signature purely from `to_signable_string` (the body) and the app's secret, then compares it to the `hmac-sha256` header [4](#0-3) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` [3](#0-2) .

### Finding Description
The binding that should hold is: **HMAC-verified bytes == bytes the app trusts for tenant identity**. Here it doesn't: the HMAC only authenticates `raw_body`, but `shop` (the tenant identity used to route/attribute the webhook) comes from an unauthenticated header. Since Shopify's genuine webhook HMAC is computed over the body only (this matches Shopify's real webhook signing scheme, so this isn't itself a deviation from spec), the header value is inherently attacker-controllable if an attacker can replay or forge a request with a valid HMAC for *some* shop's secret combined with an arbitrary `shop-domain` header — e.g., an attacker who owns/operates their own Shopify shop (using the same app) can capture a legitimately HMAC-signed webhook body for their own shop and re-send it with the `shop-domain` header rewritten to a victim shop, since the body-only signature remains valid for the same `client_secret`.

### Impact Explanation
This crosses a tenant boundary: `WebhookMetadata#shop` [5](#0-4)  is handed to the app's handler as ground truth for which merchant the event belongs to. Apps commonly use this value to look up the shop's stored access token/session and perform actions on that shop's behalf, or to write data keyed by shop. Spoofing it enables cross-tenant data injection or triggering shop-scoped business logic (e.g., `shop/redact`, `customers/redact` flows) attributed to a different shop than actually sent the webhook.

### Likelihood Explanation
Requires only that the attacker installs (or already runs) the same app on their own shop (any unprivileged merchant can do this for public apps) — no privileged access to the target shop or its secrets is needed. They intercept/replay one legitimately signed webhook and swap the header.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) as part of the signable string used for HMAC verification, or otherwise independently bind/derive the shop identity from an HMAC-covered value rather than trusting the raw header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and legitimately receives a webhook with a valid `x-shopify-hmac-sha256` for body `B`.
2. Attacker resends the same raw body `B` and the same valid HMAC header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` passes because it only checks `HMAC(secret, B)` [6](#0-5) .
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to process/act on data attributed to the victim shop it never actually sent.
