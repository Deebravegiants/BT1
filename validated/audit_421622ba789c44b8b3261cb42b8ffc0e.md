### Title
Webhook `shop` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` never verifies the `shop-domain`, `topic`, or `webhook-id` headers. `Registry.process` uses `request.shop` (an unauthenticated header value) to build the `WebhookMetadata` that host applications use to route per-tenant side effects, so an attacker who can obtain any one valid `(body, hmac)` pair can relabel it to any target shop.

### Finding Description
`HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` header: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, while `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` only validates the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) to dispatch tenant-scoped work to the registered handler: [3](#0-2) 

The binding that should hold is:
`shop_that_produced_the_valid_HMAC == shop_the_handler_believes_it_is_processing_for`

But the gem only proves `body == body_that_was_HMAC-signed_with_api_secret_key`; the `shop-domain` header is never part of that proof. Because a single app-level `api_secret_key` is shared across every shop that installs the app, any legitimately-signed `(body, hmac)` pair obtained from *any* shop (including one the attacker fully controls, e.g., their own free/dev store) remains a valid signature for that same body no matter which `shop-domain` header is attached to the replayed request. An unprivileged internet user can therefore:
1. Install the target app on a shop they control (a normal, unprivileged action).
2. Trigger any webhook topic that is also relevant to another shop's data (e.g., `app/uninstalled`, `customers/redact`, `orders/cancelled`) and capture the genuine `(raw_body, x-shopify-hmac-sha256)` pair Shopify sent them.
3. Replay that exact body and HMAC directly to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
4. `HmacValidator.validate` succeeds because it never inspected the shop header, and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant-isolation binding "shop authenticated via signature vs. shop the handler acts on," letting an attacker cause the host application to perform shop-scoped actions (data deletion/redaction, uninstall cleanup, order state changes, etc.) attributed to a shop the attacker does not control. This is a cross-tenant access vulnerability.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the app on any shop they control (an ordinary, unprivileged capability for any Shopify developer/merchant) and to send arbitrary HTTP requests to the app's public webhook endpoint — no leaked credentials, access tokens, or `api_secret_key` knowledge are required, since the HMAC is computed by Shopify itself on the attacker's own legitimate webhook delivery and is merely replayed with a different header.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) headers in the signable payload used for HMAC verification (e.g., authenticate a canonical string of `shop-domain + raw_body`, or additionally verify that the shop encoded in the body/topic matches the header before dispatch), so the shop attribute cannot be swapped independently of the signed body.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook call from Shopify:
raw_body = '{"id":123,"note":"legit payload from attacker-owned shop"}'
hmac_header = "<value Shopify computed with the shared api_secret_key>"

# 2. Attacker replays the exact same body/hmac to the app's public
#    webhook endpoint, but swaps the shop header to the victim:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => hmac_header,       # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (only checks raw_body),
# handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...)) is invoked.
``` [4](#0-3)

          received_signature = verifiable_query.hmac
