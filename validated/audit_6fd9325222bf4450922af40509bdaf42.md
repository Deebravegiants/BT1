### Title
Unnecessary `receive()` on `HostManager` needlessly exposes native funds to being trapped - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager` accepts arbitrary native-token transfers via an unconditional `receive() external payable {}`, even though the contract's own comment states funds should not be sent to it directly, and it has no function to move out any accidentally-received native balance.

### Finding Description
`HostManager` is a governance-relay contract whose sole job is to receive cross-chain governance instructions from Hyperbridge via `onAccept` and forward them to `EvmHost` (e.g., `Withdraw`, `SetHostParam`, `SetAdmin`). It holds a `receive()` function annotated with a comment that explicitly says this is only for tests and that users should not send tokens here directly: [1](#0-0) 

Unlike `EvmHost.receive()`, which is functionally required to collect dust returned by the UniswapV2 router during fee-token swaps, `HostManager` performs no swap and never expects to hold native ETH — all its logic (`Withdraw`, `SetHostParam`, `SetAdmin`) operates on `EvmHost`'s balances via `IHostManager(_params.host).withdraw(...)`, not on funds held by `HostManager` itself: [2](#0-1) 

Nothing in the contract — `init`, `onAccept`, or any other function — ever reads or moves `address(this).balance`. Any native token sent to `HostManager` (whether by user mistake, a wallet's default-recipient behavior, `selfdestruct` forcing, or a misconfigured integration) becomes permanently stuck, since there is no `withdraw`/`sweep`/`rescue` function scoped to `HostManager`'s own balance.

### Impact Explanation
Funds mistakenly sent as native ETH to `HostManager` are permanently locked (no rescue path exists in this contract), matching the "concrete... permanent freezing of funds" criterion. Because `HostManager` addresses are published/discoverable (it's the governance executive endpoint per-chain, referenced by `HostExecutive`/`update_host_params` on the Nexus chain), it's plausible for third parties (users, other contracts, or automation) to send funds there by mistake, especially since block explorers and address books don't distinguish it from `EvmHost`, which *does* legitimately receive ETH.

### Likelihood Explanation
Likelihood is low-to-medium: `HostManager` is not a common user-facing destination for token transfers and requires an explicit mistaken transfer (e.g., copy-paste of a wrong contract address, a `selfdestruct`-based forced send, or a misdirected refund). However, since the contract's own comment acknowledges this risk ("Do not send any tokens directly to this contract"), it demonstrates the team is aware ETH can land there without any corresponding recovery mechanism.

### Recommendation
Either remove the `receive()` function entirely (causing any accidental native transfer to `HostManager` to revert, protecting user funds), or, if a payable fallback is retained for compatibility, add an admin-gated sweep/rescue function so any ETH balance can be recovered rather than being permanently trapped, mirroring the referenced pattern in the DODO `MarginTrading` finding.

### Proof of Concept
1. Any externally-owned account or contract sends native ETH directly to the deployed `HostManager` address (e.g., `hostManager.call{value: 1 ether}("")`).
2. `receive() external payable {}` accepts the transfer unconditionally with no validation of sender or purpose.
3. No function in `HostManager.sol` (`init`, `onAccept`, `params`, `host`, `relayer`) ever reads or transfers `address(this).balance`.
4. The ETH remains permanently locked in the contract; only a contract upgrade (which is not exposed by `HostManager` — this is not a proxy) could recover it. [3](#0-2)

contract HostManager is HyperApp, ERC165 {
    using Bytes for bytes;

    enum OnAcceptActions {
        Withdraw,
        SetHostParam,
        SetAdmin
    }

    HostManagerParams private _params;

    // @dev Action is unauthorized
    error UnauthorizedAction();

    // @dev The host is already bound
    error AlreadyInitialized();

    // @dev The admin may not be zero. It is the only account able to deliver governance here, so
    // a zero admin would leave no way to reach this contract again, rotation included.
    error InvalidAdmin();

    /**
     * @dev Emitted when a `SetAdmin` request replaces the admin
     * @param previous The admin before this change
     * @param current The admin from now on
     */
    event AdminUpdated(address previous, address current);

    // @dev restricts call to the provided `caller`
    modifier restrict(address who, address caller) {
        if (who != caller) revert UnauthorizedAction();
        _;
    }

    constructor(HostManagerParams memory managerParams) {
        if (managerParams.admin == address(0)) revert InvalidAdmin();
        _params = managerParams;
    }

    /*
     * @dev fallback function for tests. Do not send any tokens directly to this contract.
     */
    receive() external payable {}

    /**
     * @dev See {IERC165-supportsInterface}.
     */

        return interfaceId == type(IApp).interfaceId || super.supportsInterface(interfaceId);
