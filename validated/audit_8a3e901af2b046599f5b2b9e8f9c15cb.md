## Title
Unchecked `body[0]` index panics on empty POST request bodies, permanently DoS-ing message delivery to intent gateways - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`ExtrinsicIntents.onAccept` (and the equivalent Tron `IntentGatewayV2.onAccept`) decode the leading byte of an incoming ISMP POST request body to select a `RequestKind` without first checking that the body is non-empty: [1](#0-0) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    _checkRelayer(incoming.relayer);
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```

The Tron copy has the identical pattern: [2](#0-1) 

This mirrors the Rosenpass bug class exactly: the decoder indexes into an attacker-controlled buffer without validating its length first.

### Finding Description
`onAccept` is the `IIsmpModule` callback invoked by the host (`onlyHost`) once a relayer submits a valid `HandlerV2.handlePostRequests` proof for a POST request destined to this contract. The source chain and `from` address that produce this request are cross-chain — for `ExtrinsicIntents`/`IntentGatewayV2` a POST arrives from the registered gateway instance on the source chain, or (unauthenticated at this point) from any origin claiming to be Hyperbridge before the `keccak256(source) == hyperbridge()` check further down. Because `RequestKind(uint8(incoming.request.body[0]))` is evaluated **before** any length check, a POST request whose `body` is the empty byte string causes calldata array indexing on a 0-length array, which in Solidity 0.8+ reverts with `Panic(0x32)` (array out-of-bounds access).

The impact of this differs from ordinary "app reverts" documented as an operational hazard in `HandlerV2`, because `handlePostRequests` processes an entire *batch* of requests in a single transaction (`evm/src/core/HandlerV2.sol:181-210`), verifying the MMR multiproof for all leaves before dispatching them one by one via `host.dispatchIncoming`. If `dispatchIncoming` does not wrap the module callback in a try/catch (verification of this was not possible for `EvmHost.sol` due to file-content indexing limits in this session), a single crafted zero-length-body request can cause the whole batch's transaction to revert, meaning every other legitimate request bundled in that relay transaction fails to be delivered, and — because ISMP’s host state has already accepted the proof/consensus update path independently — the same message can be repeatedly resubmitted by any attacker to force reverts on every relayer attempting to include it in a batch alongside other pending requests, degrading the general POST-request delivery route to any application via that relayer strategy.

### Impact Explanation
An unbacked, permissionless input (any state machine capable of dispatching a POST request to the `IntentGatewayV2`/`ExtrinsicIntents` address, or the coprocessor path) can craft a zero-length body. This is reachable purely from a dispatched cross-chain request — no privileged or malicious-admin action is required. Per the scope rules, this is a "route unable to deliver messages" class finding: legitimate intent-fill/redeem/refund messages sharing a relay batch with the malformed request cannot be delivered until a relayer isolates and skips the malformed one, and the malformed request itself can never succeed (revert is deterministic on `body.length == 0`), producing a permanently un-deliverable message occupying a slot in the pending queue.

### Likelihood Explanation
High: sending a zero-length body POST request costs the attacker nothing beyond ordinary dispatch fees on the origin chain (or none, if the attacker's origin state machine dispatch is fee-less), and the destination-side effect (panic) is deterministic and always reachable — no consensus forgery, timing, or race condition is needed.

### Recommendation
Add an explicit length guard before indexing, e.g.:
```solidity
if (incoming.request.body.length == 0) revert InvalidRequestBody();
RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```
in both `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`. Additionally, confirm (and if absent, add) that `EvmHost.dispatchIncoming` isolates each module's `onAccept` call in a try/catch so that one malformed/reverting request cannot block delivery of the other requests verified in the same MMR-proof batch — this would also contain the blast radius of any future callback-side revert bug, not just this one.

### Proof of Concept
1. On the source chain, dispatch (or have the coprocessor relay) an ISMP `PostRequest` targeting the `IntentGatewayV2`/`ExtrinsicIntents` contract address as `dest`/`to`, with `body = ""` (zero bytes).
2. A relayer collects this request together with other pending, legitimate intent-fill requests into one `HandlerV2.handlePostRequests` call and submits the batch with a valid MMR multiproof.
3. During the per-leaf dispatch loop, `host.dispatchIncoming` invokes `onAccept` on the target contract for the malformed leaf; `RequestKind(uint8(incoming.request.body[0]))` executes `body[0]` on a 0-length calldata bytes array, triggering `Panic(0x32)`.
4. If the host does not catch this panic per-leaf, the entire `handlePostRequests` transaction reverts, so none of the batched requests (including the legitimate ones) are delivered in that transaction, and the malformed request remains pending to be re-batched and re-attempted indefinitely.

**Note on unverified assumption:** whether `EvmHost.dispatchIncoming` wraps the `onAccept` call in a try/catch (which would limit the blast radius to only the single malformed request rather than the whole batch) could not be confirmed in this session — the `evm/src/core/EvmHost.sol` file contents were not available through the indexed codebase search (only line 1 returned). This should be verified directly in the repository before relying on the "whole batch fails" severity claim; even if `dispatchIncoming` isolates failures per-leaf, the underlying panic still permanently and deterministically blocks delivery of that specific message to `IntentGatewayV2`.
