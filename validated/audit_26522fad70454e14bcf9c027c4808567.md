### Title
Webhook HMAC Only Covers Request Body, Not the `shop-domain` Header Trusted as Tenant Identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature verified by `Utils::HmacValidator` proves nothing about the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `Registry.process` nonetheless passes `request.shop` — taken straight from that unauthenticated header — into `WebhookMetadata` and the app's handler as the tenant identity, breaking the equality "shop bytes verified by HMAC == shop bytes trusted for tenant scoping."

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the app-provided handler: [1](#0-0) 

That check calls `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers that are never included in the signed string: [4](#0-3) 

After a successful HMAC check, `Registry.process` builds `WebhookMetadata` using `request.shop` (the unauthenticated header value) and hands it to the app's handler: [5](#0-4) 

The identity binding that should hold is: *the shop whose HMAC key validated the payload == the shop the handler is told the payload came from*. Because the signature covers only `@raw_body`, that equality does not hold — the header can be swapped freely without invalidating the signature, since the app's HMAC secret (`api_secret_key`) is a single per-app secret shared across every shop that has the app installed. Any merchant who has installed the app receives genuine, correctly-signed webhook deliveries for their own shop. Because the signature is computed only over the body (not shop, topic, or webhook id), that same merchant can replay the exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. `HmacValidator.validate` still succeeds — it only re-derives the same signature over the same body — so `Registry.process` proceeds and invokes the handler with `WebhookMetadata#shop` set to the victim's domain instead of the attacker's own.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select which merchant's session/access token/database record to load or mutate (the officially documented usage pattern in `docs/usage/webhooks.md`) is exposed to cross-tenant action: an authenticated attacker (any merchant with the app installed) can cause the handler to run business logic against another merchant's `shop` identifier while presenting a validly-HMAC'd request. Depending on what the handler does with `data.shop` (e.g. looking up and updating that shop's stored access token, deleting that shop's data, or triggering shop-scoped side effects), this crosses the tenant boundary defined in scope ("cross-tenant access"). No `api_secret_key`, access token, or victim credential is required — only having one's own app installation, which is the unprivileged-attacker starting point.

### Likelihood Explanation
The attack requires only: (1) the attacker be a legitimate but malicious merchant with the target app installed (readily obtainable for any public/embedded app), and (2) capturing one real webhook delivery's raw body (trivial, since it's delivered straight to their own endpoint or observable via any proxy they control), then replaying the HTTP POST to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No cryptographic material needs to be forged since the HMAC does not cover the header at all. This is a low-effort, high-reliability attack against any app that trusts `WebhookMetadata#shop` for tenant scoping, which is the pattern this gem's own documentation recommends.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signable string used for webhook HMAC verification, or independently bind the header-derived shop to a value cryptographically tied to the signature (e.g., verify that `shop` matches an expected/known installed shop before dispatch, in addition to body HMAC verification). At minimum, document loudly that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a sole tenant-scoping key without additional verification (e.g., cross-checking against the shop stored for the given `webhook_id`/registration).

### Proof of Concept
1. App installs itself on `attacker-shop.myshopify.com`; attacker's own webhook endpoint (or an attacker-controlled proxy in front of it) receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-signature-over-raw-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: ...
   Body: {"id": 1, ...}
   ```
2. Attacker replays the identical raw body and `X-Shopify-Hmac-Sha256` value to the same app endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`) — it matches, since the body and hmac are unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds and calls `handler.handle(data: WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...))`, causing the app's business logic to run scoped to the victim shop using attacker-supplied data, despite the attacker never having any credential for that victim shop.
