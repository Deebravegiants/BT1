### Title
Webhook shop/tenant identity is taken from an unauthenticated header, not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC matches the **raw request body**, but the `shop`, `topic`, `api_version`, and `webhook_id` fields that the handler actually acts on are read straight from unauthenticated HTTP headers and are never part of the signed material. An attacker who can obtain one valid `(raw_body, hmac)` pair for a shop they control can replay that exact body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop, and the library will report it as an authenticated webhook "from" the victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body — none of the Shopify headers are included in the signable material: [2](#0-1) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` — the values used to route and attribute the event — are parsed directly from unauthenticated headers with no cryptographic binding to the body that was actually signed: [3](#0-2) [4](#0-3) 

`Registry.process` only re-verifies the HMAC against the body, then immediately hands the unauthenticated header-derived fields to the app's handler as if they were verified: [5](#0-4) 

The `WebhookMetadata` struct passed to every handler carries `shop` and `topic` straight from these headers: [6](#0-5) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop covered by HMAC (∅, since HMAC only signs raw_body) ≠ shop delivered to handler (request.shop, from the "shopify-shop-domain" header)`.

Because the app's `api_secret_key` is the same for every installation of the app (it's a per-app secret, not a per-shop secret), a valid `(raw_body, hmac)` pair generated for **any** shop that has installed the app is a valid pair for **every** shop from the HMAC validator's point of view — the validator has no way to bind a signature to a specific tenant. Only the header (which is not signed) distinguishes which shop the payload is supposed to belong to.

### Impact Explanation
This is a cross-tenant confusion vulnerability (Critical, per the "cross-tenant access" criterion). Any merchant that has legitimately installed the app can:
1. Trigger a real webhook event on their own store (e.g. `orders/create`) to obtain a body + a valid `x-shopify-hmac-sha256` value signed with the app's secret.
2. Replay that exact HTTP request to the app's webhook endpoint, but with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header changed to point at a different, victim shop that also uses the app.

`Registry.process` will accept this as a legitimate webhook "from" the victim shop (HMAC checks out because it only covers the body), and will invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that uses `data.shop` to look up per-tenant state (e.g., to select which merchant's access token/session/database row to update, per the very purpose these webhooks exist for) will now operate on the victim tenant using attacker-supplied body content, i.e., forged cross-tenant webhook injection.

### Likelihood Explanation
High/likely to be reachable: any app built with this gem processes webhooks through `Registry.process`, and every documented integration path (`ShopifyAPI::Webhooks::Request.new` + `Registry.process`) exhibits this behavior — there is no optional "strict" mode that binds the header fields into the signed payload. The only prerequisite for an attacker is the ability to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer), which is a far lower bar than needing `api_secret_key`, an access token, or any other privileged credential.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or independently authenticate it:
- Include `shop`, `topic`, and `webhook_id` header values in `to_signable_string` so the HMAC covers the full set of fields the handler will trust, or
- Cross-check the header-derived `shop` against an out-of-band trusted source (e.g., the session/shop record associated with the webhook subscription that was registered via `Registry.register`) before dispatching to the handler, rejecting the webhook if they don't match.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both subscribed to `orders/create`.
2. Attacker places an order on `attacker-shop`, capturing the webhook POST Shopify sends: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`).
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and same header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks `B` against `H`), see `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: B, ...)`, `lib/shopify_api/webhooks/registry.rb:188-200`, causing the app to process attacker-controlled order data as if it belonged to the victim tenant.

          received_signature = verifiable_query.hmac

        end
