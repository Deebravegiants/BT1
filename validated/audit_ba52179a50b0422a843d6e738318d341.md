### Title
Non-UTF8 `dest`/`source` bytes in `EvmHost.dispatch()` produce a `PostRequestEvent`/`GetRequestEvent` whose commitment can never be reconstructed off-chain, permanently orphaning the request - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` build the on-chain `PostRequest`/`GetRequest` struct with an attacker-supplied `dest` field of type `bytes`, hash it with `keccak256(abi.encode(request))`, and then re-cast that same raw `bytes` value to Solidity `string` when emitting `PostRequestEvent`/`GetRequestEvent`. Solidity's `string(bytes)` cast performs no UTF-8 validation — it just reinterprets the raw bytes. Any off-chain consumer that decodes the emitted event through an ABI stack that *does* enforce UTF-8 (viem/ethers in the indexer/SDK, or Rust's `String`/alloy decoding in the relayer and `abi.rs`) will either throw on decode or silently replace invalid byte sequences (U+FFFD), producing a string that no longer round-trips to the original bytes used to compute the on-chain commitment.

### Finding Description
`dispatch(DispatchPost)` builds the commitment directly from the raw `post.dest` bytes chosen by the caller: [1](#0-0) 

Nothing in this path validates that `post.dest` is a recognized/well-formed state machine identifier or valid UTF-8 — it is copied verbatim into `PostRequest.dest` and hashed: [2](#0-1) 

Then the exact same raw bytes are re-emitted with a `string` type in the event: [3](#0-2) 

Every downstream commitment reconstruction depends on decoding this event field back to bytes and re-encoding with `abi.encode`:

- Indexer (TypeScript/ethers, `RequestService.computeRequestCommitment`) takes the decoded `dest` string, converts it with `ethers.utils.toUtf8Bytes(dest)`, and hashes it to reproduce the commitment: [4](#0-3) 
called directly from the event handler on every `PostRequestEvent`: [5](#0-4) 

- Relayer-side Rust decode (`modules/ismp/core/src/abi.rs`) parses the event's `source`/`dest` strings via `StateMachine::from_str`, which itself operates on a `String` that the ABI layer already had to successfully build from the raw bytes: [6](#0-5) 

If `post.dest` (or `post.source`, though `source` is fixed to `host()`) contains a byte sequence that is not valid UTF-8, the JS/TS ABI decoders (viem/ethers) and the Rust `String`-typed ABI decoders used by `PostRequestEvent::decode_log_data` do not agree with Solidity's "no validation" semantics for `bytes`→`string` casts:
- Some decoders throw on invalid UTF-8, causing the event to be undecodable entirely.
- Others (e.g., a `TextDecoder`-style lossy decode) substitute the replacement character `U+FFFD` for invalid byte sequences, silently changing the string's byte representation.

Either way, re-encoding the decoded string with `toUtf8Bytes`/`String::as_bytes` no longer reproduces the original `post.dest` bytes that the contract used when computing `commitment = request.hash()`. The indexer/relayer therefore either (a) crashes/skips indexing this event, or (b) computes a *different* commitment than the one actually stored in `_requestCommitments` on-chain.

This is a direct structural analog of CVE-2023-27488: an attacker-controlled field that is not required to be valid UTF-8 is transported through a "string"-typed channel (gRPC message field in Envoy; Solidity event `string` field here) to a downstream consumer that assumes UTF-8 validity for further processing (protobuf decode → downstream service in Envoy; commitment re-derivation → relayer delivery pipeline here). In Envoy, the outcome was a policy/logging bypass; here, the outcome is silent loss of message deliverability.

### Impact Explanation
The dispatcher already collects the caller's fee (`IERC20(feeToken()).safeTransferFrom(...)` or the native-token swap) and commits `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` before the event is emitted — the request is fully and successfully dispatched on-chain regardless of what `dest` bytes were chosen. If `dest` is crafted with invalid UTF-8 bytes:

- The relayer network's event-decoding pipeline (`abi.rs` / tesseract messaging) and/or the indexer's commitment-recomputation pipeline either fail to decode the log or recompute a commitment that does not match the one actually stored on `EvmHost`. In both cases, the relayer/indexer never correctly associates a deliverable pending request with the correct commitment, so the message is never picked up and delivered to Hyperbridge.
- The relayer fee paid by the caller (`post.fee`, collected up front) becomes effectively unrecoverable in the normal flow, since delivery never happens and the indexer that tracks the request lifecycle for refund/timeout handling never registers it correctly.

This matches the "route unable to deliver messages" and "permanent freezing of funds" (locked relayer fee) impact bars from the validation criteria, reachable by any unprivileged caller of `IDispatcher.dispatch()`.

### Likelihood Explanation
Any address can call `dispatch(DispatchPost)` or `dispatch(DispatchGet)` with an arbitrary `dest` byte string — there is no restriction to a known/allow-listed state machine identifier or UTF-8-validity check in the dispatch path. Constructing a non-UTF-8 `dest` (e.g., a single `0xC0` continuation-less lead byte, or an overlong/surrogate sequence, as already characterized as invalid by the SDK's own hand-rolled UTF-8 validator used elsewhere in the codebase) is trivial and costs only the normal dispatch fee. The bug is triggered by a single transaction with no special privileges.

### Recommendation
- Validate that `post.dest`/`get.dest` (and any other byte field cast to `string` for event emission) is well-formed UTF-8 before accepting the dispatch, reverting otherwise — mirroring the strict validation already implemented for chain-id strings elsewhere in the codebase (e.g., the hand-rolled UTF-8 decoder in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts` and `isValidUTF8` in `sdk/packages/sdk/src/utils.ts`).
- Alternatively/additionally, restrict `dest` to the enumerated set of supported `StateMachine` identifiers at dispatch time (all of which are ASCII/UTF-8 by construction), rejecting anything that doesn't parse.
- Ensure every off-chain consumer (indexer, relayer, SDK) that recomputes the commitment from decoded event data uses the exact same bytes that were ABI-encoded on-chain, not a UTF-8-decoded/re-encoded round trip, to avoid any decoder-dependent divergence even for otherwise-valid inputs.

### Proof of Concept
1. Call `EvmHost.dispatch(DispatchPost)` with `post.dest = hex"c0"` (a single invalid UTF-8 lead byte with no continuation) and any valid `to`/`body`/`fee`.
2. `EvmHost.sol` computes `commitment = request.hash()` over the raw bytes and stores `_requestCommitments[commitment]`, emitting `PostRequestEvent{ dest: string(hex"c0"), ... }`.
3. Off-chain, the indexer's event handler decodes `args.dest` from the log; depending on the ABI decoder, this either throws (log/event silently dropped from the try/catch-wrapped code path in `handlePostRequestEvent`) or yields a string containing `U+FFFD`.
4. `RequestService.computeRequestCommitment(source, dest, ...)` re-encodes `dest` via `ethers.utils.toUtf8Bytes(dest)`; for the `U+FFFD` case this produces bytes `ef bf bd`, not the original `c0` byte, so `keccak256(abi.encode(...))` differs from the on-chain `commitment`.
5. The indexed `Request` entity's derived commitment never matches the actual on-chain commitment key under which the fee/metadata was stored, so downstream relaying/status-tracking logic that keys off the indexer's computed commitment can never locate and deliver the real pending request.
