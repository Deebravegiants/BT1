### Title
Stale stored `Account.owner` grants the prior NFT holder full control after `position-nft` transfer — (`contracts/controller/src/account.rs`)

### Summary
The kernel bug class is "a resource's readers keep operating on a stale reference after ownership/release semantics changed" (key slot released via kref while lockless readers still see it). The analog here is account ownership: the controller stores `owner` inside the `Account` struct at creation, but the *live* owner is the position-NFT holder, and the NFT is freely transferable via the OZ `NonFungibleToken::transfer`/`transfer_from` interface with no callback into the controller. The two ownership sources diverge after any transfer: `require_account_owner` reads the live NFT owner via `storage::account_owner`, while `require_owner_or_delegate`/`is_owner_or_delegate` compare `caller` against the stale `account.owner` field — which is written exactly once, in `create_account_with` (`contracts/controller/src/account.rs:64-70`), and never restamped.

### Finding Description
`create_account_with` snapshots the minter as `account.owner` at mint time (`contracts/controller/src/account.rs:63-70`). Owner-gated flows — `AccountGuard::Migrate` and `AccountGuard::Multiply` in `load_or_create_account`, plus every path calling `require_owner_or_delegate` (`contracts/controller/src/account.rs:101-140`) — authorize `caller` by `caller == account.owner` or by looking up delegates keyed under `account.owner` (`storage::get_delegates(env, account_id, owner)` at `account.rs:126`). Separately, `require_account_owner` (`account.rs:143-148`) and `renew_account`/`add_delegate`/`remove_delegate` authenticate against the live NFT owner (`storage::account_owner`, `account.rs:145`). The NFT contract's `transfer`/`transfer_from` are stock OZ entrypoints (`contracts/position-nft/src/contract.rs:131-173`); they require only token-owner auth and invoke no controller hook, so nothing updates `account.owner` on transfer. Like the kernel freeing the AEAD transform in a context where a lockless reader could still hold a reference, the controller "frees" ownership (NFT moves) while privileged readers still consult the stale stored owner.

### Impact Explanation
- Theft of user funds: after selling/transferring the position NFT, the old owner still satisfies `caller == account.owner` on every `require_owner_or_delegate` path (withdraw, borrow-side strategies such as `multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `migrate_from_blend`). They can withdraw the new owner's collateral and run debt-altering strategies on an account they no longer own.
- Permanent/temporary freezing: conversely, the *new* NFT owner fails `require_owner_or_delegate` (they are not `account.owner` and hold no delegate slot under the old owner's key), so they cannot operate or exit the account they just bought — collateral is stranded until the old owner cooperates.
- Delegate leakage: delegates registered under the previous owner (`add_delegate`) remain authoritative because `get_delegates` is keyed by `account.owner`, so a prior owner's manager retains power post-transfer.

### Likelihood Explanation
The trigger is a single unprivileged action — `transfer`/`transfer_from`/`approve`+`transfer_from` on the position NFT — reachable by any account holder, with no protocol gate, pause, or flag blocking it (INV-HALT-01 pauses controller entrypoints, not the NFT contract). Any secondary-market sale, OTC deal, or wallet migration exercises the divergence. Whether this is exploitable in a given deployment depends only on whether any frontend ever transfers position NFTs, which the interface explicitly supports.

### Recommendation
Restamp `account.owner` (and re-key or clear the delegate list) whenever ownership is exercised — i.e., load the live owner via `storage::account_owner` at the top of every `require_owner_or_delegate` call site and compare `caller` against that, not against the stored field; or have all owner checks route through `require_account_owner`'s live-NFT lookup and persist the refreshed owner before delegate-keyed lookups. Alternatively, restrict NFT transfers while the account is non-empty. A storage migration is needed for already-transferred accounts.

### Proof of Concept
1. Alice calls `supply` with `account_id = 0`; `create_account_with` mints NFT `N` to Alice and stores `account.owner = ALICE` (`account.rs:63-70`). Alice supplies 10,000 USDC.
2. Alice transfers NFT `N` to Bob via `position-nft.transfer(alice, bob, N)` — stock OZ path, no controller notification (`contract.rs:131-173`).
3. Alice calls `withdraw` (or `multiply`/`migrate_from_blend`) for account `N` signed by Alice. `load_or_create_account`/`require_owner_or_delegate` loads the stored `Account`, sees `caller == account.owner == ALICE`, and authorizes (`account.rs:106,136`). Alice withdraws collateral that now economically belongs to Bob.
4. Symmetrically, Bob calling `withdraw` fails `is_owner_or_delegate` since `caller != account.owner` and Bob holds no delegate slot under `add_delegate`'s `owner` key — Bob's purchased collateral is frozen.

Caveat: I verified `account.owner` is assigned only at creation and that no transfer hook exists in the position-NFT contract, but iteration limits prevented enumerating every call site of `require_owner_or_delegate`; if a wrapper already restamps `account.owner` from `account_owner` on every entry, this reduces to a documentation issue — that should be confirmed before final severity.
