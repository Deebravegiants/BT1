That `VMRunnerError::LoadingError` then propagates up to `execute_function_call` in `runtime/runtime/src/function_call.rs`, which explicitly maps it to `VMOutcome::nop_outcome(...)` — a zero-gas, zero-burnt outcome [1](#0-0) . This confirms the audit's premise: under the legacy code path, a deserialization failure at call time is metered as a free nop rather than charging the contract-loading fee (`contract_loading_base` + `contract_loading_bytes * len`), even though the node has already spent CPU time compiling/attempting to load the module.

This is also directly validated by the repo's own regression test, `test_max_core_instance_size_breached` in `runtime/near-vm-runner/src/tests/runtime_errors.rs:29-93`, whose comment states "Pre-fix: zero-gas nop, loading work uncharged" and asserts the pre-fix path returns `Err(VMRunnerError::LoadingError(_))` while the post-fix path (`fix_contract_loading_error: true`) charges `expected_gas > 0` and finalizes as a committed `LoadingError` abort [3](#0-2) .

The protocol feature `ProtocolFeature::FixContractLoadingError` exists specifically to close this gap ("Charge the contract-loading fee ... rather than a zero-gas nop when a compiled module fails to load at `Module::deserialize`") [4](#0-3) , confirming this is a known, named issue the codebase is actively guarding against/fixing via a protocol upgrade, not a hypothetical.

However, the exploitability at present depends on whether `FixContractLoadingError` is already active on mainnet/stable. Based on the code and comments found, this feature is gated in `version.rs` similarly to the related `FixContractLoadingCost`/nightly features, and I could not fully confirm from the available index whether it is stabilized on the version currently deployed to mainnet. If it is still nightly-only/not yet activated, the vulnerability window is real for the current stable protocol version; once activated it is closed.

### Impact Explanation
This is a gas-metering-completeness bypass: CPU work (module deserialization attempt, which for a large/complex corrupted module can be non-trivial) is performed by every validator/chunk-producer applying the receipt, but the resulting outcome is a `nop_outcome` with `burnt_gas = 0`, `used_gas = 0`. An attacker can deploy a contract whose compiled artifact deserializes-fails (e.g., crafted to pass `DeployContract`/`prepare` validation but fail at the `Module::deserialize` stage due to cached-artifact/version confusion) and then repeatedly call it at minimal attached gas, forcing validators to redo the failing deserialization attempt on each call for free. This matches the "gas or storage metering bypass" / "free or underpriced execution" impact class, with potential network-wide throughput degradation from repeated cheap invocations.

### Likelihood Explanation
Exploitability is gated entirely on protocol-version activation of `FixContractLoadingError`. Constructing a module that passes `prepare`/validation but fails `Module::deserialize` specifically (as opposed to failing earlier at compile or preparation) is a narrow target — normally a contract that fails preparation is rejected before compilation succeeds, and a contract that compiles successfully via `compile_and_cache` should deserialize successfully from its own freshly-produced cache entry within the same node/version. The realistic trigger vectors are cache/version-skew scenarios called out in the code's own comment ("if one forgot to change the cache key when upgrading the near_vm library, or the database had data corrupted at rest") — i.e., an operational/versioning edge case rather than something an ordinary attacker can trivially and reliably trigger purely via a crafted Wasm binary through normal `DeployContract` validation. This significantly lowers likelihood versus the theoretical framing in the question.

### Recommendation
Ensure `FixContractLoadingError` (and the analogous `FixContractLoadingCost`) is activated for the current stable protocol version so that all `Module::deserialize` failures are always charged via `before_loading_executable`/`after_loading_executable` before finalizing as a committed abort, and remove/deprecate the legacy `VMRunnerError::LoadingError` → `nop_outcome` mapping in `runtime/runtime/src/function_call.rs` once the fix is unconditionally active.

### Proof of Concept
The repo already contains the exact PoC pattern requested: `runtime/near-vm-runner/src/tests/runtime_errors.rs::test_max_core_instance_size_breached` (lines 29-93) toggles `fix_contract_loading_error` and asserts:
- `false`: `Err(VMRunnerError::LoadingError(_))` (which the runtime maps to a zero-gas `nop_outcome`).
- `true`: `outcome.used_gas == expected_gas` (`contract_loading_base + contract_loading_bytes * len`), with `expected_gas > 0`, and the outcome is a committed `LoadingError` abort.

To adapt this into a direct measurement of "gas charged vs CPU time spent," extend the test to wrap the `run(...)` calls with `std::time::Instant` timing around the deserialization-failure path, asserting non-negligible wall-clock time is spent while `burnt_gas == 0` under the `false` configuration, and repeat the call N times to demonstrate the cost accumulates for free.

                let after =

                let loading_base = after.ext_costs.gas_cost(ExtCosts::contract_loading_base);
                let loading_byte = after.ext_costs.gas_cost(ExtCosts::contract_loading_bytes);
                let expected_gas = loading_base
