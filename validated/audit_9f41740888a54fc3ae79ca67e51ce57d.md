### Title
Withdrawal status/tx-hash misreported for batched same-asset POA withdrawals due to assetId-only matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by NEAR tx hash + `index`) by matching the bridge indexer's unsorted withdrawal list using only `assetId`, ignoring `index`. When a single NEAR transaction batches two or more withdrawal intents of the *same* token to *different* destinations, this method reports the wrong withdrawal's status and `transfer_tx_hash` for at least one of them — the equivalent of Grafana returning a value that does not correspond to the entity the caller actually asked about.

### Finding Description
`describeWithdrawal` explicitly disregards the withdrawal `index` and matches purely by `assetId`: [1](#0-0) 

The code comment even documents the design choice: *"Response list is unsorted, so we match by assetId instead of index"* [2](#0-1) . This is safe only when a single NEAR transaction contains at most one withdrawal per `assetId`. The existing regression test confirms the matching strategy operates purely on `assetId`, with no additional discriminator such as `destinationAddress` or amount: [3](#0-2) .

If a user (via `sendSignedIntents`/batched intents) submits a single NEAR transaction with two `withdraw` intents for the *same* `assetId` but different `destinationAddress`/amount (e.g., splitting a withdrawal to two recipients), each withdrawal gets its own `WithdrawalIdentifier` differentiated only by `index`: [4](#0-3) . When `describeWithdrawal` is later polled for `index: 1`, `findMatchingWithdrawal` still filters the API response solely by `assetId` and can return the entry that actually corresponds to `index: 0` (or vice versa), because the bridge indexer response contains multiple entries for the same `assetId` and there is no tie-breaker matching to the specific intent index.

This breaks the equality that the report and rules are concerned with: **a status reported that is not the actual on-chain outcome of the specific withdrawal being queried.** The caller (an integrator polling withdrawal state via `watchWithdrawal`/`waitForWithdrawalCompletion`) receives a `completed` status with a `transfer_tx_hash` that belongs to a *different* withdrawal instance than the one requested.

### Impact Explanation
An integrator relying on `describeWithdrawal`/`watchWithdrawal` to confirm a specific withdrawal's completion (and its destination) could be told withdrawal #1 is `completed` with a tx hash that actually belongs to withdrawal #0 (or is still `pending` while it was actually completed under the other entry). This falls into the "status or hash misreport making an integrator credit or refund twice" impact category — an integrator could release funds/credit a user for a withdrawal that has not actually landed at that specific destination, or fail to detect that a withdrawal genuinely completed, since the wrong record was consumed. Because `withdrawal-watcher.ts` treats `status: "completed"` as a terminal signal to resolve the poll [5](#0-4) , the misreport directly and silently propagates to any downstream consumer.

### Likelihood Explanation
Likelihood is moderate: it requires no privileged access — any unprivileged user of the SDK who batches ≥2 withdraw intents of the same `assetId` (different destinations) within one NEAR transaction (a normal usage pattern for batched intents) triggers the ambiguous match. No malicious intent by a relayer/operator is needed; the bug is purely in the client-side matching logic that ignores `index`.

### Recommendation
`findMatchingWithdrawal` should disambiguate withdrawals sharing the same `assetId` within the same `tx_hash` by also comparing `destinationAddress` (and/or `amount`) from `withdrawalParams` against `withdrawal.data.address`/`amount`, or by tracking a stable per-intent ordering key from the indexer response rather than relying on `assetId` alone.

### Proof of Concept
1. Construct one NEAR transaction with two intents: `withdraw(assetId=X, destination=A, amount=100)` at index 0 and `withdraw(assetId=X, destination=B, amount=200)` at index 1.
2. The POA bridge indexer returns both entries for `withdrawal_hash = tx.hash`, tagged only with `defuse_asset_identifier = X` (same for both) and differing `address`/`amount`.
3. Call `bridge.describeWithdrawal({ tx, index: 1, withdrawalParams: { assetId: X, destinationAddress: B, ... } })`.
4. `findMatchingWithdrawal(response.withdrawals, "X")` returns the first entry matching `assetId === X` — which may be the entry for index 0 (destination A) — causing `describeWithdrawal` to report `{ status: "completed", txHash: <hash for A's transfer> }` for what is actually withdrawal to B, per the matching logic shown at [6](#0-5) .

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
