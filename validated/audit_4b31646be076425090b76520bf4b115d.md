### Title
Webhook `shop` identity not bound to HMAC signature, allowing cross-tenant attribution of forged webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `Utils::HmacValidator` authenticate a webhook exclusively by the HMAC over the raw request body. The `shop` field, extracted from the unauthenticated `X-Shopify-Shop-Domain` header, is never included in the signed material yet is trusted downstream as the tenant identifier passed to the app's webhook handler. This breaks the intended binding `HMAC-verified bytes == bytes acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string` (i.e., raw body only) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` validates the request via this HMAC check and then immediately forwards the *unauthenticated* `request.shop` value into `WebhookMetadata`, which is handed to the app's handler as trusted, verified tenant identity: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant that has installed the app already possesses at least one legitimately-signed `(raw_body, hmac)` pair for their own shop — delivered to their own registered webhook endpoint, which they fully control and can read. That merchant can then replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a different (victim) shop's domain. `Utils::HmacValidator.validate` still returns `true`, because the HMAC only ever covered the body, not the shop header. The `Registry.process` API — which is this gem's own documented processing entry point, not something the host app must additionally guard — then hands the handler a `WebhookMetadata` claiming the payload is `shop: "victim-shop.myshopify.com"` while the actual signed content originated from the attacker's own shop.

This is the direct analog of the reported bug class: a field (`shop`) is acted upon and trusted as part of the "verified" webhook contract, but it is not covered by the cryptographic check (HMAC) that supposedly grants that trust — mirroring the original report's core pattern of an identity/quantity used downstream without being bound to the value that was actually validated.

### Impact Explanation
This crosses a tenant boundary: an app built directly on this gem's documented `Registry.process` / `WebhookMetadata` API will process attacker-controlled webhook payloads (their own shop's genuine data/events) as if they belonged to an arbitrary victim shop of the same app. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select which tenant's database record to update, which access token/session to look up, or which customer/order to mutate), this enables cross-tenant data corruption or disclosure using only a standard merchant-level webhook subscription that any app installer already has — no `api_secret_key`, no stolen tokens, and no privileged account required beyond installing the app once as a normal merchant.

### Likelihood Explanation
Any shop that installs the app receives legitimately HMAC-signed webhooks at their own configured callback URL and can trivially capture `(raw_body, hmac)` pairs from their own traffic. Replaying that pair with a modified shop-domain header against the app's webhook endpoint requires no cryptographic material beyond what a normal, unprivileged app-installing merchant already has access to, and no special network position. The only variable is whether the host application relies on `WebhookMetadata#shop` for tenant-sensitive decisions — a usage explicitly enabled and encouraged by this gem's own API (`WebhookMetadata.new(topic:, shop:, body:, ...)`), not a misuse of it.

### Recommendation
Bind the shop identity into the authenticated material before it is trusted, e.g.:
- Include the `shop`/`x-shopify-shop-domain` value inside the signable string used by `Request#to_signable_string` (Shopify's HMAC is computed over the body only server-side, so this specific fix isn't directly available), or
- Cross-check `request.shop` against an out-of-band trusted source (e.g., the `shop` associated with the specific webhook subscription/`webhook_id`, or a known active session for that shop) before dispatching to the handler, and document to consumers that `WebhookMetadata#shop` must not be treated as cryptographically verified on its own.
- At minimum, update documentation to explicitly warn that `shop` in `WebhookMetadata` is not covered by the HMAC and must be independently validated against expected tenant records by the host application before being used for any privileged, tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures/observes a webhook (e.g., `orders/create`) delivered to their own controlled endpoint.
2. Attacker captures the legitimate raw body `B` and header `X-Shopify-Hmac-Sha256: H` from this delivery (both valid, since Shopify signed `B` with the shared `client_secret`).
3. Attacker sends a new POST to the target app's real webhook processing endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, etc. adjusted as desired.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` derived from the attacker's own data, and processes it as belonging to the victim tenant.
