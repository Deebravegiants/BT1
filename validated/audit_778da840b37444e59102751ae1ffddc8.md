## Analysis

The equality claimed to be violated is:

`sum(real tokens that entered the Hinkal vault) == sum(amountChanges credited) + sum(on-chain UTXO amounts minted)`

Tracing `Hinkal.transact`, this is checked **per index of `circomData.erc20TokenAddresses`**, not per real underlying asset:

```
oldBalances = getBalancesForArray(erc20TokenAddresses)   // balanceOf() snapshot, per-index
... run internal/external action ...
newBalances = getBalancesForArray(erc20TokenAddresses)   // balanceOf() snapshot, per-index
balanceDif[i] = newBalances[i] - oldBalances[i]
require(balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i])
``` [1](#0-0) 

The only guard against using the same underlying balance twice is the circuit's pairwise `IsEqual` check on the raw `erc20TokenAddresses[i]` field values: [2](#0-1) 

That check only rejects literally identical addresses — it cannot detect two **distinct** contract addresses whose `balanceOf(hinkal)` reads reflect the same underlying reserve (a known "multiple token addresses" pattern in real-world ERC20s, e.g. legacy/new proxy pairs that both remain live, transferable, and economically fungible). Neither `HinkalHelper.dimensionsCheck`/`checkOnchainCreation` nor any token allowlist filters this: I found no token registry enforcement in `Hinkal.sol`/`HinkalBase.sol` — `erc20TokenRegistryAddress` only appears in an unused interface struct field, `IHinkal.ConstructorArgs`, and is never referenced in checks. [3](#0-2) 

So if such a token exists and both of its live addresses carry real market value, an attacker can list both as separate entries in `erc20TokenAddresses`. A single real transfer of `X` tokens into Hinkal (via address A) causes `balanceOf` at address B to also rise by `X` (same storage). The attacker satisfies the per-index equation twice for that single physical event — e.g. `amountChanges[iA] = X` (normal deposit accounting) **and** `onChainCreation[iB] = true` with a freshly minted on-chain UTXO of `X` for address B via `DepositOnChainUtxosExternalAction`/`EmporiumUpgradeable.handleOut`. [4](#0-3)  Both checks pass independently, yet the vault only ever received `X` real tokens while the ledger now recognizes `2X` of credited/minted value. Redeeming the minted UTXO later via address B's real `transfer()` call genuinely drains reserve backing other users' balances.

However, this requires such a **real, dual-address, equally-valuable token to exist and to be usable through Hinkal** — Hinkal itself imposes no token allowlist, so any ERC20 (including such tokens) can be passed as `erc20TokenAddresses`. That precondition (a genuinely fungible/real-value double-entry-point token) is what the question requires and is outside "price-oracle/depeg" or "attacker's own worthless fake token" concerns — it exploits a legitimate accounting gap in `Hinkal.transact`'s per-index balance snapshotting rather than a token's economic assumption.

### Title
Per-index `balanceOf` snapshotting in `Hinkal.transact` lets a double-entry-point token back two credited/minted values with one real transfer - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` validates `balanceDif == amountChanges[i] + utxoAmount[i]` independently for each entry of `circomData.erc20TokenAddresses`, relying only on `balanceOf()` snapshots and the circuit's raw-address-inequality check. Neither guards against two distinct, legitimate token addresses that alias the same underlying reserve (a documented "multiple token addresses" ERC20 pattern), allowing a single real transfer to satisfy the balance equation twice.

### Finding Description
Equality claimed: real tokens entering Hinkal == `sum(amountChanges)` + `sum(minted on-chain UTXO amounts)`. `Hinkal.transact` computes `oldBalances`/`newBalances` via `getBalancesForArray` (`balanceOf`) once per index in `erc20TokenAddresses`, then checks the equation per index in the same loop. [1](#0-0)  If `erc20TokenAddresses[i]=A` and `erc20TokenAddresses[j]=B` are distinct addresses of a token that shares its balance storage across both (both real and transferable, e.g. a legacy/new address pair), a single real transfer of `X` into Hinkal via A also raises B's reported balance by `X`. The circuit only enforces `A != B` as raw field values via `distinctErc20AddressChecks`, never that they represent independent reserves. [2](#0-1)  The attacker sets index A's `amountChanges[iA]=X` (normal deposit credit) and index B's `onChainCreation[iB]=true` with a minted on-chain UTXO of amount `X` (via `DepositOnChainUtxosExternalAction` or `EmporiumUpgradeable.handleOut`, both of which independently call `getBalancesForArray`/`transferERC20TokenOrETH` per index without cross-checking aliasing). [5](#0-4)  Both per-index checks pass, crediting `2X` worth of value for one real `X` deposit. No existing guard (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, slippage checks, or the circuit's `inTotal+amountChanges===outTotal`) checks cross-index reserve independence — they all operate per declared address.

### Impact Explanation
Critical: minting shielded/on-chain value without backing, since the attacker can later redeem the extra minted UTXO for real tokens via address B's genuine `transfer()`, draining reserve that should back other users' UTXOs — causing protocol insolvency for that token. Repeatable per double-entry-point token instance the attacker can source/use.

### Likelihood Explanation
Requires a genuinely dual-address, equally-valuable ERC20 (a known but uncommon "weird ERC20" category) to be usable through Hinkal; Hinkal enforces no token allowlist (the `erc20TokenRegistryAddress` field is present in `IHinkal.ConstructorArgs` but unused/unenforced anywhere in `Hinkal.sol`/`HinkalBase.sol`), so any attacker-selected pair of addresses can be supplied. [3](#0-2)  Attacker cost is limited to gas plus locating/using such a token; no privileged role needed.

### Recommendation
Do not trust `erc20TokenAddresses[i]` uniqueness by raw address alone. Either (a) enforce a governance-curated token allowlist/registry actually wired into `performHinkalChecks`/`transact` that vets tokens for storage independence, or (b) compute a single aggregate `balanceOf`-based accounting keyed by a canonical token identity rather than per supplied address, or (c) require and verify (e.g., via `codehash`/registry mapping) that no two allowed token addresses can alias the same reserve.

### Proof of Concept
Foundry plan: deploy a mock "dual-address" ERC20 whose two proxy addresses (A, B) forward `balanceOf`/`transfer` to one shared storage; whitelist/register both as usable Hinkal tokens (since no registry restriction exists); build `CircomData` with `erc20TokenAddresses=[A,B]`, deposit `X` real tokens via A in the same `transact` call while setting `onChainCreation[iB]=true` and using `DepositOnChainUtxosExternalAction` to mint a UTXO of `X` for B; assert `transact` succeeds; then redeem the minted UTXO via B's `transfer`; assert `IERC20(A).balanceOf(hinkal)` (== B's, since shared storage) has dropped below the amount required to still back the UTXO/credit created from the original deposit — i.e., total credited (`amountChanges[iA] + utxoAmount[iB] = 2X`) exceeds the single real inflow (`X`).
