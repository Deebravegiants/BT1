### Title
Unchecked subtraction/slice on attacker-controlled `message.from` length causes panic-based DoS in `on_accept` - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `IsmpModule::on_accept` handler decodes a cross-chain ABI-encoded `Message` from an incoming `PostRequest` body and, when no signature is supplied and the source chain is EVM, slices the last 20 bytes off `message.from` with `&from_bytes[from_bytes.len() - 20..]` without first validating that `from_bytes.len() >= 20`. [1](#0-0) 

### Finding Description
`message.from` is decoded via `Message::abi_decode(&body)` where `body` comes directly from a relayed `PostRequest` — an ABI `bytes` field whose length is fully attacker-controlled by whoever crafts the source-chain message (or, since this is a cross-chain token module, potentially forged/short data on non-EVM sources routed as `source.is_evm()`). [2](#0-1) 

Unlike the sibling handling of `message.to`, which explicitly validates the length is either 32 or 20 bytes before use (`to_bytes.len() == 32` / `== 20`, else `Err(HftError::InvalidRecipientLength)`), the `message.from` path taken when `substrate_data.signature` is `None` performs no equivalent length check before computing `from_bytes.len() - 20`: [3](#0-2) [4](#0-3) 

If `from_bytes.len() < 20`, the `usize` subtraction `from_bytes.len() - 20` underflows. In a debug/overflow-checked build this panics immediately; in a release build without overflow checks it wraps to a huge value, and the subsequent slice `from_bytes[huge_value..]` panics with an out-of-bounds index. This is directly analogous to the CVE-2018-8001 root cause: `UnescapeName()` in PoDoFo read past the buffer bounds because it advanced/consumed indices from attacker-controlled input without checking remaining length before dereferencing — here the code advances an index (`len() - 20`) derived from attacker-controlled input without checking that the buffer is long enough, leading to an out-of-bounds access.

### Impact Explanation
A malicious or malformed relayed message with optional calldata (`message.data` non-empty, `substrate_data.signature == None`, `source.is_evm() == true`, and `message.from` shorter than 20 bytes) causes the runtime to panic while executing `on_accept`, which is invoked from ISMP message dispatch/handling (`HandlerV2`-style delivery). A panic inside pallet dispatch logic executed during block processing halts/reverts the transaction and, depending on how panics propagate through the runtime's `dispatch` wrapping, can degrade availability of the token-bridge message-handling pipeline for a route — a denial-of-service against message delivery for this pallet, reachable by any party able to submit or relay a PostRequest destined for the HFT module.

### Likelihood Explanation
The path is reachable by a single relayed `PostRequest` — no privileged role is required, only that the request is deliverable to this module (arbitrary `from`/`to`/`body` fields are attacker-supplied on the source chain and merely need to pass the module's `ContractToAsset` source-authentication check, which authenticates the source contract address, not the encoded `from` bytes' length). Crafting a `message.from` of fewer than 20 bytes with non-empty `message.data` and no signature is trivial for anyone controlling the source-chain sender contract or message encoding.

### Recommendation
Validate `from_bytes.len()` (accepting only 20 or 32 bytes, matching the `to_bytes` handling) before performing the `len() - 20` slice, returning an `HftError::InvalidSenderLength`-style error instead of panicking, mirroring the check already present in `on_timeout`'s handling of `message.from`: [5](#0-4) 

### Proof of Concept
1. Register a source EVM contract mapped in `ContractToAsset` for some asset.
2. Relay a `PostRequest` from that EVM `source`/`from` address whose ABI-encoded `Message.from` field is set to fewer than 20 bytes (e.g., 5 bytes) and `Message.data` non-empty with `SubstrateCalldata { signature: None, runtime_call: <any valid encoded call> }`.
3. Hyperbridge's `on_accept` decodes the message, reaches the `else` branch at line 176 (`from_bytes = message.from.as_ref()`), computes `from_bytes.len() - 20` which underflows since `from_bytes.len() == 5`, and the subsequent slice indexing panics. [1](#0-0)
