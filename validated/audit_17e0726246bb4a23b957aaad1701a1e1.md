## Analysis

I mapped the reported bug class ("field acted upon but not covered by the integrity check") onto this gem's webhook‑processing path. The concrete analog is in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Registry.process` validates the HMAC over that body alone. However, the `shop` (`shopify-shop-domain` header) that is subsequently used to identify which tenant a webhook event belongs to is read straight from an unauthenticated header and passed to the app's handler without being bound to the signature.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the signature only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` (parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is *not* part of the signed content) to build the `WebhookMetadata` delivered to the app's handler: [3](#0-2) 

Because a single app typically has one shared `client_secret` used to compute HMACs for **every** shop that installs the app, and the callback endpoint is shared across all tenants, the binding that should hold is:
`shop authenticated by signature == shop acted upon by the handler`

This binding is broken: the signature only proves "this body was HMAC'd with the app's secret" — it proves nothing about which shop the body belongs to. Any user who can install the app on their own store (an unprivileged action) receives genuine `(body, hmac)` pairs signed with the app's shared secret for their own shop's events. That same valid `(body, hmac)` pair can be replayed to the shared webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain, and `Utils::HmacValidator.validate` will still succeed since the header is never included in `to_signable_string`.

### Impact Explanation
This lets a low-privilege user (merely installs the app on their own store) forge events attributed to another tenant, achieving cross-tenant data injection into the host application via `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`. If the host app trusts `shop` from webhook metadata to look up/update per-tenant records (a documented, expected usage pattern of this gem), an attacker can inject or corrupt data under an arbitrary victim's tenant identity.

### Likelihood Explanation
Exploitation only requires (a) installing the target app on an attacker-controlled store to obtain one genuine `(body, hmac)` pair, and (b) sending a crafted HTTP request to the app's public webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header. No access to `api_secret_key`, tokens, or any privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is verified, or require the caller to explicitly confirm that the `shop` extracted from headers matches an already-known/allow-listed shop before trusting it in `WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant identification without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, triggers an event, and captures the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair sent to the app's webhook endpoint.
2. Attacker resends the identical body and HMAC header to the same endpoint, replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body's HMAC.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, believing it originated from the victim's store.
