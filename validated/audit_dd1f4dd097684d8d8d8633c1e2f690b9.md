### Title
Cross-chain governance can flip `solverSelection` mid-flight, letting any solver front-run a session-authorized fill and drain escrow before the intended solver — `ExtrinsicIntents.sol` / `IntentGatewayV2.sol`

### Summary
Hyperbridge's `IntentGatewayV2` intent-auction flow enforces "solver selection" (only the session-key-authorized solver may fill an order) by re-reading the *global*, governance-mutable `_params.solverSelection` flag at `fillOrder()` time, rather than snapshotting it into the order at `placeOrder()` time. Governance (via `onAccept` → `UpdateParams`) can change this flag instantly, with no timelock, while orders placed under the old assumption are still pending in escrow — exactly the "mutable auction/rebalance parameter changes mid-flight" bug class from the referenced report.

### Finding Description
The order-auction flow: a user calls `placeOrder()`, sets `order.session` (a disposable session key), and solvers bid off-chain via Hyperbridge. The user picks a winner and calls `select()` to authorize exactly one solver (stored via `tstore`), and `fillOrder()` enforces that only the selected solver may claim the escrow when `_params.solverSelection` is `true`: [1](#0-0) 

This check is entirely gated on the **live, current value** of `_params.solverSelection`, not a value captured when the order was placed. `_params` is a single global struct shared by every pending order, and it can be replaced wholesale by cross-chain governance at any time via `_updateParams`, which performs no invariant checking on `solverSelection` and applies the change immediately (no timelock, no delay): [2](#0-1) 

The governance path reaching this is the `UpdateParams` request kind handled through the gateway's `onAccept`, delivered from Hyperbridge exactly like the other governance actions (`SetHostParam`, `SetAdmin`, `Withdraw`) documented for the host: a single relayed message swaps out the entire params struct instantly.

Because the enforcement condition (`_params.solverSelection`) is evaluated at `fillOrder()`/settlement time rather than being pinned to the order at `placeOrder()` time, this is structurally identical to the `auctionMultiplier`/`auctionDecrement` bug: mutable protocol-wide parameters that govern in-flight commitments can be changed after escrow has been locked but before settlement, altering the guarantees the depositor relied on. If governance (malicious, compromised, or simply mis-configured) flips `solverSelection` from `true` to `false` while a solver-selection order sits in escrow with `order.session` set and a winning bid already signed off-chain, the `if (_params.solverSelection)` branch is skipped entirely for every pending order — the transient-storage selection check never runs — and **any address** can call `fillOrder()` directly, supplying only the bare minimum required outputs (no `select()` call needed), and claim the escrowed inputs ahead of the user-selected solver.

### Impact Explanation
- Escrowed input tokens for any order relying on solver-selection protection become claimable by an arbitrary front-runner the instant the flag flips, bypassing the entire auction/selection mechanism the user opted into.
- Because `_filled[commitment]` is a first-write-wins gate, the attacker (or any bot watching the mempool/governance mempool for the parameter change) can race and win the fill with the minimum acceptable output, denying the user the benefit of the competitive auction and denying the legitimately selected solver its fill (its signed bid/UserOp becomes worthless, wasting gas/fees already committed).
- Unlike a purely "malicious relayer" bug, the actor able to trigger this is cross-chain *governance* — the same class of privileged-but-not-instantly-catastrophic actor the underlying report is about (the judge in the referenced report classified analogous governance-controlled-parameter rug vectors as Medium precisely because it requires a malicious/compromised governance actor and can be timed with a proof/relay race).

### Likelihood Explanation
Requires cross-chain governance to dispatch an `UpdateParams` message (a single relayed post request, no timelock gating `solverSelection` specifically, unlike `EvmHost`'s `minIbRatio`-style protections mentioned in the reference report). Any governance key compromise, misconfiguration, or intentional malicious action can trigger it, and the race to front-run a specific in-flight order additionally requires watching the mempool/coprocessor for a live order — feasible for a sophisticated actor but adding some execution complexity. This lands at Medium severity, consistent with the judge's downgrade rationale in the referenced report (malicious/compromised privileged actor required, but concrete fund-diversion is possible and not contingent on any other bug).

### Recommendation
Snapshot `solverSelection` (and any other order-critical, currently-global parameter such as `surplusShareBps` handling of calldata) into the `Order` struct or a per-commitment record at `placeOrder()` time, and enforce the snapshotted value in `fillOrder()` instead of re-reading the live `_params`. Alternatively, gate `UpdateParams` changes to `solverSelection` behind a timelock long enough to exceed the maximum order lifetime (`order.deadline`), so no order placed under one policy can be settled under another.

### Proof of Concept
1. User calls `placeOrder()` with `order.session = sessionKeyAddress` while `_params.solverSelection == true`. Inputs are escrowed and `OrderPlaced` is emitted.
2. Off-chain, solvers bid; user signs a `SelectOptions` authorizing the winning solver via `select()` (in the same tx that would normally batch with `fillOrder()`).
3. Before the winning solver's transaction lands, Hyperbridge governance dispatches `UpdateParams` (via `onAccept`, `RequestKind.UpdateParams`) setting `solverSelection = false`, exercised in-repo by `testOnAcceptUpdateParamsWithDestinationFees`/`testOnAcceptUpdateParams`-style flows: [3](#0-2) .
4. `_params.solverSelection` is now `false` globally, including for the already-escrowed order from step 1.
5. Any address (not the selected solver) calls `IntentGatewayV2.fillOrder(order, options)` directly — no `select()` needed — with `options.outputs` set to exactly `order.output.assets`; the `if (_params.solverSelection)` branch at `evm/src/apps/IntentGatewayV2.sol:464-472` is skipped, `_filled[commitment]` is set, and the escrowed inputs are transferred to the front-running caller instead of the user-selected solver.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
