## Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body [1](#0-0) . However, the `shop` (and `topic`/`webhook_id`/`api_version`) values that are subsequently trusted and forwarded to the app's webhook handler are read directly from HTTP headers that are **not** part of the signed material [2](#0-1) . This breaks the identity binding between "bytes verified" (the body) and "shop acted on" (the header), letting any user who controls one legitimately-signed webhook payload re-attribute it to an arbitrary other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly over that signable string [4](#0-3) . Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all parsed straight from headers with no cryptographic protection:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` only checks the HMAC and then hands the unauthenticated `shop` value straight to the handler as trusted tenant identity:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [6](#0-5) 

This is the same bug class as the reported `CraftingSystem` issue: an item (there, the ERC721 token; here, the `shop` field) is *acted on* — used to identify and route data for a tenant — without being covered by the check that is supposed to authenticate the whole operation (there, the ownership check; here, the HMAC). Notably, this codebase demonstrates it knows how to bind `shop` into a signature correctly elsewhere: `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters [7](#0-6) , but the equivalent binding is missing for webhook requests.

Because the HMAC is body-only, any user who is a merchant (fully unprivileged w.r.t. other tenants) and has the app installed on their own shop can capture one legitimately Shopify-signed webhook payload delivered to the app's public webhook endpoint, then directly POST that exact same body/HMAC to the same endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header for a victim shop. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` pointing at the victim tenant.

### Impact Explanation
This crosses the identity boundary between tenants (shops) using only artifacts an unprivileged internet user (any merchant who installed the app) can obtain. A downstream application that persists/reacts to webhook data keyed by `WebhookMetadata#shop` (e.g., updating orders, inventory, or app state "for shop X") can be tricked into attributing attacker-controlled events to a different shop, i.e., cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-owned shop to receive one genuinely signed webhook, and (2) sending an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header while reusing the untouched body/HMAC. No access to `api_secret_key`, tokens, or the target's credentials is needed, making this readily reachable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the value that is HMAC-verified, or otherwise cryptographically tie them to the verified body (e.g., include them in the signable string similar to `AuthQuery#to_signable_string`, or require the host app to cross-check `shop` against an independently known, already-authenticated session/shop before trusting `WebhookMetadata#shop`). At minimum, document and enforce that `Registry.process` must not treat header-derived `shop` as authenticated purely on the basis of `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a real webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker crafts a raw HTTP POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC_SHA256(client_secret, B) == H`, as shown in [8](#0-7)  and [3](#0-2) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [9](#0-8)  and processes/stores data as if it legitimately originated from the victim shop.
