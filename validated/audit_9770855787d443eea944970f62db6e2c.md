## #Vulnerability found for this question.

### Title
`process_withdraw` can permanently revert due to double-rounded PnL/decimal-normalization arithmetic underflowing `target_orders.calc_pnl_x`/`calc_pnl_y` - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` recomputes the pool's PnL baseline (`target_orders.calc_pnl_x`/`calc_pnl_y`) by combining two independently-rounded quantities: the withdrawn amount re-normalized from native decimals, and `delta_x`/`delta_y` (the PnL amount computed directly in normalized units). Because these two values are rounded down through different code paths, their sum can exceed the pre-computed baseline `x1`/`y1`, causing the `checked_sub(...).unwrap()` calls to panic and the whole withdraw transaction to revert.

### Finding Description
In `process_withdraw` (`program/src/processor.rs:1726-1841`), the pool baseline is updated as: [1](#0-0) 

```rust
target_orders.calc_pnl_x = x1
    .checked_sub(Calculator::normalize_decimal_v2(pc_amount, amm.pc_decimals, amm.sys_decimal_value))
    .unwrap()
    .checked_sub(U128::from(delta_x))
    .unwrap()
    .as_u128();
```

`x1` is `normalize_decimal_v2(total_pc_without_take_pnl, ...)` computed **before** PnL is taken. `delta_x` is produced by `calc_take_pnl` (`program/src/processor.rs:167-281`), which computes the PnL to subtract via two separately-rounded paths: [2](#0-1) 

- `delta_x` is computed directly in normalized (`sys_decimal_value`) units: `floor(diff_x * pnl_numerator / pnl_denominator)`.
- The amount actually deducted from `total_pc_without_take_pnl` (used afterward to compute `pc_amount`) is computed by first restoring `diff_x` to native decimals via `restore_decimal` (a floor division) and then applying the PnL fraction again (`pc_pnl_amount`), i.e. a floor-then-scale-then-floor sequence.

Because `floor(a) * f` and `floor(a * f)` differ by rounding error, the amount actually subtracted from `total_pc_without_take_pnl` (in native units, later re-normalized as `normalize_decimal_v2(pc_amount, ...)`) can end up **larger relative to `x1 - delta_x`** than intended — i.e., `normalize_decimal_v2(pc_amount, ...) + delta_x` can exceed `x1`. This mirrors exactly the reported bug class: two independently-rounded-down quantities summed can exceed a value that was expected to bound them, causing an unconditional-looking subtraction to underflow.

`normalize_decimal_v2` and `restore_decimal` are the underlying decimal-normalization primitives responsible for this rounding behavior: [3](#0-2) 

The identical unsafe pattern (`checked_sub(...).unwrap()` chained twice) is repeated in `process_deposit` (`program/src/processor.rs:1352-1371`) and `process_withdrawpnl` (`program/src/processor.rs:1531-1532`), but `process_withdraw` is the highest-risk instance because it is reachable by any unprivileged LP holder in a single transaction, and the risk is maximized for large/near-full withdrawals (`withdraw.amount` close to `amm.lp_amount - 1`, which is the maximum allowed per the check at `program/src/processor.rs:1716`), where `pc_amount`/`coin_amount` approach the entire post-PnL pool balance.

### Impact Explanation
When the underflow occurs, the Rust panic aborts the transaction, so `Withdraw` reverts for the affected LP position/amount. Because the discrepancy is a function of the pool's accumulated PnL state (`target_orders.calc_pnl_x`/`calc_pnl_y`, `need_take_pnl_pc/coin`) and the size of the withdrawal relative to the pool, an LP attempting to withdraw a large or full position can be persistently unable to withdraw — even though the token transfers/burn for that instruction would otherwise succeed — since every retry recomputes the same rounding relationship from the same on-chain state. This constitutes a freezing-of-funds risk for LPs, matching the severity class of the original report (DoS reverting a critical unstake/withdraw path due to rounding-down arithmetic).

### Likelihood Explanation
This requires no attacker privilege and no malicious input beyond calling `Withdraw` with a legitimate LP amount; the trigger condition depends only on organically accumulated `calc_pnl_x`/`calc_pnl_y` drift and the ratio of the requested withdrawal to the pool's remaining balance, both of which occur naturally over the pool's lifetime as swaps and multiple withdrawals accumulate rounding error. It is most likely to manifest for large or full withdrawals, a routine and expected LP action.

### Recommendation
Avoid summing independently-rounded quantities as if they were derived from a single consistent decomposition. Compute the post-withdrawal, post-PnL normalized baseline directly from the reduced `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (which already reflects both the PnL deduction and the withdrawal) via a single `normalize_decimal_v2` call, rather than reconstructing it by subtracting two separately-floored deltas from `x1`/`y1`. Alternatively, replace the `.unwrap()` calls with saturating subtraction (clamping to zero) so that rounding dust cannot cause a hard revert of user-facing fund-moving instructions.

### Proof of Concept
1. Set up a pool where `target_orders.calc_pnl_x`/`calc_pnl_y` and vault balances have diverged over time such that `calc_take_pnl`'s two rounding paths for `diff_x`/`pc_pnl_amount` differ by at least 1 unit in normalized terms (readily achievable given arbitrary `pc_decimals`/`sys_decimal_value`/`pnl_numerator`/`pnl_denominator` combinations, as demonstrated by the existing repo test `test_calc_pnl_precision` in `program/src/processor.rs:3090-3213`, which already exercises multi-step PnL/withdraw precision).
2. Call `Withdraw` with `withdraw.amount` close to `amm.lp_amount - 1` (the maximum permitted, per `program/src/processor.rs:1716`), so `pc_amount`/`coin_amount` approach the full post-PnL pool balance.
3. Observe that `Calculator::normalize_decimal_v2(pc_amount, ...) + delta_x > x1` (or the analogous coin-side condition), causing `x1.checked_sub(...).unwrap()` at `program/src/processor.rs:1819-1828` to panic, aborting the transaction after the token transfers/burn logic would otherwise have succeeded — i.e., the withdraw instruction is unusable for that amount/pool state.
