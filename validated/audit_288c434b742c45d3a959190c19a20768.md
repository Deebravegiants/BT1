### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop spoofing via replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` value that is handed to the app's webhook handler and used as the tenant identifier is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed material. Because the signature only binds the body, not the shop, a valid `(body, hmac)` pair generated by Shopify for one shop can be replayed with a different, attacker-chosen `shop` header value and will still pass validation — breaking the binding `hmac_signed_shop == header_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from an unauthenticated header: [2](#0-1) 

Validation in the registry only checks the HMAC over that signable string (the body) and, if it passes, immediately trusts `request.shop` when constructing the metadata passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, with no reference to `shop`: [4](#0-3) 

The identity binding that should hold is:
`hmac(body, api_secret_key) valid` **⇒** `shop header == shop that Shopify actually generated this webhook for`

That binding does not hold in this code, because the shop header is never mixed into the signed content. Any party who legitimately receives a genuinely-signed webhook for their own shop (e.g., an unprivileged merchant who installed the app on their own store) possesses a valid `(raw_body, hmac)` pair. They can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value pointing at a victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and will dispatch `WebhookMetadata.new(shop: request.shop, ...)` — with `shop` fully attacker-controlled — to the host application's handler.

The impact is amplified for topics where the body is largely static or attacker-influenced (e.g., `app/uninstalled`, or any topic where the attacker's own store data is echoed back in the payload), since the attacker only needs one legitimately-signed payload from their own store to replay against arbitrary victim shop identifiers.

### Impact Explanation
This crosses a tenant boundary: the gem hands the host application webhook data tagged with a `shop` value that was never authenticated by Shopify's HMAC, only by an unauthenticated header. Any host application that trusts `WebhookMetadata#shop` (as documented and recommended, e.g. to look up/act on a specific tenant's session or record) can be made to attribute a replayed, attacker-obtained payload to a different shop than the one it was actually issued for. Depending on the topic, this enables cross-tenant data injection/confusion (e.g., causing the app to believe shop B sent an uninstall, order, or other webhook that really came from shop A), which falls under cross-tenant access.

### Likelihood Explanation
The attacker does not need the app's `api_secret_key` or `client_secret`, an access token, or any privileged credential — they only need to be a legitimate (unprivileged) end-user of the app on their own store, which is enough to receive real Shopify-signed webhook payloads (from Shopify's servers) for their own shop. Replaying that payload against the app's public webhook endpoint with a different shop header is trivial and requires no TLS interception or social engineering.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material verified against the HMAC, or otherwise ensure the shop identity cannot be altered independently of the signed body — e.g., verify `shop` against a known/expected value tied to the webhook subscription, or refuse to trust the header-derived `shop` unless it is cryptographically tied to the signed payload. At minimum, document prominently that `data.shop` is not authenticated by the HMAC and must not be trusted as a tenant identifier without additional verification by the host application.

### Proof of Concept
1. Attacker installs the app on their own store (`attacker-shop.myshopify.com`) and legitimately receives a real webhook, e.g. body `raw_body` with header `X-Shopify-Hmac-Sha256: <valid hmac for raw_body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` (see `to_signable_string`) — it matches, since the body is unchanged. [5](#0-4) 
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though Shopify never generated this webhook for that shop. [6](#0-5)
