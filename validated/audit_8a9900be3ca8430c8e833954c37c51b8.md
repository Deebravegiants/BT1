### Title
Unchecked low-level ERC20 `transfer` return value in Tron `IntentGatewayV2` withdraw/sweep paths permanently freezes escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` escrows ERC20/TRC20 tokens on `placeOrder` and later pays them out via `withdraw()` (fill/refund settlement) and via the `SweepDust` handler. Both paths release tokens using a raw low-level `.call()` to the `transfer` selector and only check that the call itself did not revert, never decoding/verifying the boolean return value that a compliant ERC20 must return on success.

### Finding Description
In `withdraw()`, both the per-token payout loop and the fee-token payout use:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

The same pattern is used in the `SweepDust` incoming-request handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the external call reverted or not; it does not decode the ABI-encoded `bool` payload that ERC20's `transfer` is supposed to return. Any token that returns `false` on a failed transfer instead of reverting (a widely known non-compliance pattern, exemplified by USDT, and also present among TRC20 tokens on Tron) will make this call return `success = true` even though no tokens moved.

Despite the transfer silently failing, `withdraw()` unconditionally updates internal escrow accounting immediately afterward:
```solidity
_filled[body.commitment] = beneficiary;
...
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

Because `_filled` is marked and `_orders[...]` is decremented as if the payout succeeded, the escrowed tokens remain stuck in the `IntentGatewayV2` contract while the protocol's bookkeeping shows the order as already settled (filled or refunded). There is no retry path since `_orders[body.commitment][token]` is now zero and `_filled[body.commitment]` is set, so the beneficiary can never reclaim the escrowed balance.

Note that elsewhere in the same file, deposits correctly use `safeTransferFrom` (`IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` at line 405 and 459), confirming the codebase is aware of SafeERC20 but the payout/withdraw and dust-sweep paths on the Tron gateway were left using unchecked low-level calls. [4](#0-3) 

### Impact Explanation
This is a reachable path for any relayer or filler that triggers order settlement (fill/refund) or the governance-driven dust sweep for a non-standard-compliant token escrowed via `placeOrder`/predispatch flows on the Tron `IntentGatewayV2`. Funds legitimately owed to the order's beneficiary become permanently frozen in the contract because escrow accounting is finalized regardless of whether the transfer actually delivered tokens — a concrete permanent loss/freezing of user funds, matching the Medium bug class in the referenced report.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the Tron ecosystem includes tokens (including popular TRC20 stablecoins) known to follow the same non-standard "return false instead of revert" behavior that motivated the original Sherlock report for USDT on EVM. Any order using such a token as an input/output/fee asset will trigger this on settlement, with no special attacker privileges required — it can be hit organically by ordinary intent fills/refunds or by the permissioned `SweepDust` governance action.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee-token payout) and in the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which already is used for `safeTransferFrom` in this same file, so all transfer calls consistently revert on failed/non-compliant token returns before accounting state (`_orders`, `_filled`) is mutated.

### Proof of Concept
1. An intent order escrows a non-standard-compliant TRC20 token (one that returns `false` on failed `transfer` instead of reverting) as an input/output token via `placeOrder`.
2. When the order is later settled, `withdraw()` is invoked (e.g., via a fill or refund incoming request), reaching:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
3. Suppose the token transfer internally fails (e.g., due to a blacklist, paused state, or insufficient balance edge case handled without revert) and returns `false`. The low-level `call` still succeeds (`success == true`) because the call did not revert.
4. `withdraw()` proceeds to zero out `_orders[body.commitment][token]` and mark `_filled[body.commitment] = beneficiary`, treating the order as fully settled.
5. The beneficiary never received the tokens, and the escrowed balance sits in the `IntentGatewayV2` contract with no accounting path left to reclaim it — funds are permanently frozen.
