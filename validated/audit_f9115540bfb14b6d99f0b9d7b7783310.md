Audit Report

## Title
Header blocklist bypass via underscore-variant header names in Gateway outbound HTTP client - (core/services/gateway/network/httpclient.go)

## Summary
`validateHeaderNames` in `core/services/gateway/network/httpclient.go` only lower-cases header names before checking them against `defaultBlockedHeaders`, without normalizing `_` to `-`. Since Go's header canonicalization (`textproto.CanonicalMIMEHeaderKey`, used internally by `http.Header.Add`) does not treat `_` as a word separator either, underscore variants of blocked headers (e.g. `X_Forwarded_For`, `X_Real_Ip`, `Transfer_Encoding`) bypass the blocklist and are forwarded verbatim to the destination server.

## Finding Description
`validateHeaderNames` builds `blockedSet` from `strings.ToLower(b)` for each entry in `c.config.BlockedHeaders` and checks incoming header names with `strings.ToLower(name)` only, at `core/services/gateway/network/httpclient.go:411-423`. The blocklist (`defaultBlockedHeaders`, lines 116-131) is dash-delimited (`x-forwarded-for`, `x-real-ip`, `transfer-encoding`, `connection`, etc.), each entry documented with a specific spoofing/protocol-abuse rationale. Because there is no `_`↔`-` normalization step anywhere in this file or elsewhere in the codebase (confirmed via search for underscore-normalization helpers — none exist for this purpose), a header name like `X_Forwarded_For` lower-cases to `x_forwarded_for`, which is absent from `blockedSet`, so `validateHeaders`/`validateMultiHeaders` (lines 425-431) pass it through.

The passed header then flows into `requestToNetHeader` (lines 203-218) and is added via `r.Header.Add(k, v)` (lines 466-475). Go's canonicalization only capitalizes letters following `-`, not `_`, so `X_Forwarded_For` becomes the literal wire key `X_forwarded_for`, distinct from the canonical `X-Forwarded-For`, and is sent unmodified to the destination.

Reachability is confirmed: `makeOutgoingRequest` in `core/services/gateway/handlers/capabilities/v2/http_handler.go:404-421` takes the workflow-supplied `OutboundHTTPRequest.Headers`/`MultiHeaders` and passes them directly into `network.HTTPRequest` without any additional underscore-aware filtering, then calls `httpClient.Send`, which performs only the flawed check described above.

## Impact Explanation
This is a concrete allowlist/blocklist bypass in the Gateway's HTTP Action egress path. A workflow can smuggle `X-Forwarded-For`/`X-Real-Ip`/`X-Forwarded-Host`/`X-Forwarded-Proto` equivalents (with underscores) to any external endpoint the Gateway calls, potentially spoofing trust context on destination servers that normalize underscores (many CGI/WSGI-style backends do), and can smuggle protocol-sensitive headers like `Transfer-Encoding`/`Connection` in underscore form. This maps to the gateway request impersonation impact category: the Gateway itself (an operator-run, internet-facing egress component) fails to enforce its own documented security-relevant header blocklist against a workflow-controlled input, and the workaround requires no special privilege beyond authoring a normal HTTP Action workflow.

## Likelihood Explanation
High reachability and low complexity. Any party able to have a workflow's HTTP Action capability executed by a DON/Gateway node can set arbitrary `Headers`/`MultiHeaders`, including underscore variants, with zero additional privilege. The bypass is a single, deterministic string transformation, fully repeatable, and does not depend on race conditions, timing, or any other node/operator-level assumption.

## Recommendation
Normalize header names in `validateHeaderNames` by replacing `_` with `-` (in addition to lower-casing) before comparing against `blockedSet`, applied consistently to both `validateHeaders` and `validateMultiHeaders`. Alternatively/additionally, reject any header name containing an underscore outright for the outbound HTTP Action client, consistent with common "disallow underscores in headers" mitigations used against this defect class.

## Proof of Concept
1. Configure or use default `HTTPClientConfig.BlockedHeaders` (defaults from `defaultBlockedHeaders`).
2. Call `httpClient.Send(ctx, HTTPRequest{Method: "GET", URL: "http://example.com", MultiHeaders: map[string][]string{"X_Forwarded_For": {"10.0.0.1"}}})` directly, or simulate via `makeOutgoingRequest` with an `OutboundHTTPRequest{MultiHeaders: {"X_Forwarded_For": ["10.0.0.1"]}}`.
3. Observe `validateMultiHeaders` → `validateHeaderNames` does not return `ErrBlockedRequest` (lower-cased `"x_forwarded_for"` is not in `blockedSet`).
4. Inspect the outgoing `http.Request.Header` (or run against a local `httptest.Server` capturing raw headers) and confirm the literal key `X_forwarded_for: 10.0.0.1` is present on the wire, whereas `X-Forwarded-For` would have been rejected.
5. A Go unit test added to `core/services/gateway/network/httpclient_test.go` asserting `validateHeaderNames([]string{"X_Forwarded_For"})` returns `nil` (bypass) versus `validateHeaderNames([]string{"X-Forwarded-For"})` returns `ErrBlockedRequest` (correctly blocked) demonstrates the inconsistency directly.

// requestToNetHeader builds net/http.Header from req. Uses MultiHeaders when set, otherwise Headers.
func requestToNetHeader(req HTTPRequest) http.Header {
	out := make(http.Header)
	if len(req.MultiHeaders) > 0 {
		for k, values := range req.MultiHeaders {
			for _, v := range values {
				out.Add(k, v)
			}
		}
		return out
	}
	for k, v := range req.Headers {
		out.Add(k, v)
	}
	return out
}

// validateHeaderNames checks that none of the given header names are in the blocked list (case-insensitive).
func (c *httpClient) validateHeaderNames(names []string) error {
	blockedSet := make(map[string]struct{}, len(c.config.BlockedHeaders))
	for _, b := range c.config.BlockedHeaders {
		blockedSet[strings.ToLower(b)] = struct{}{}
	}
	for _, name := range names {
		if _, blocked := blockedSet[strings.ToLower(name)]; blocked {
			return fmt.Errorf("%w: HTTP header not allowed: %s", ErrBlockedRequest, name)
		}
	}
	return nil
}
