This confirms the vulnerability. The gem's own documentation (`docs/usage/webhooks.md:125`) explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" — implying `data.shop` is trustworthy — but the `shop` field is never covered by the HMAC that the gem itself computes and validates.

### Title
Webhook shop-domain identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks that the body's HMAC matches, then unconditionally trusts `request.shop` and hands it to the app's handler as the authenticated tenant identifier.

### Finding Description
The binding that should hold is: `shop value used to select/attribute tenant data == shop value cryptographically bound into the HMAC-signed payload`. In this gem that equality does not hold. [1](#0-0) 

`shop` is read purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header`, and `to_signable_string` (the data that is actually HMAC-verified) is just `@raw_body` — it never incorporates the shop header. [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` — which only proves the raw body was signed with the app's `api_secret_key` — and then immediately builds `WebhookMetadata.new(topic: request.shop == ...)` using the unverified `shop` header, passing it to the app's `WebhookHandler#handle` as if it were an authenticated tenant identifier. [3](#0-2) 

The `api_secret_key` used for the HMAC is a single, app-wide secret (not per-shop), as also seen in `Oauth.validate_auth_callback`'s use of `Context.api_secret_key`. Consequently, any two webhook deliveries to the same app — regardless of shop — are signed with the identical secret and validate as long as the body bytes match, since the shop identity itself is never part of the signed material. [4](#0-3) 

The gem's own documentation states processing "will verify the request did indeed come from Shopify," which promises a stronger authentication guarantee than what is actually enforced — the shop identity is not cryptographically attested at all.

### Impact Explanation
An unprivileged internet user who operates their own Shopify store (a merchant with the target app installed on their own shop, i.e., no special access to the victim shop) can:
1. Trigger a legitimate webhook delivery to the app for their own shop (e.g. by creating an order), capturing the valid raw body and its valid `x-shopify-hmac-sha256` signature.
2. Replay that exact body/signature pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain.

Because `to_signable_string` never includes the shop header, the HMAC still validates, and `Registry.process` forwards `WebhookMetadata` with `shop` set to the victim's domain to the app's handler. Any app logic that uses `data.shop` to select/attribute the tenant record (a pattern the gem's own docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-controlled data under a victim tenant's identity — a cross-tenant data-integrity/confidentiality violation reachable purely over the internet with no credentials beyond installing the app on one's own store.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented pattern: the vulnerable code path (`Request` + `Registry.process`) is the only documented mechanism for verifying and dispatching webhooks, and the flaw is entirely inside the gem — it is not a case of the host app ignoring documented behavior. The only precondition is the ability to install the app on an attacker-controlled shop (which is the normal, unprivileged way any user interacts with a public Shopify app) to obtain one valid signed payload to replay.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed/verified material, or independently bind the `shop-domain` header to a value the gem controls before trusting it — for example, by having `HmacValidator`/`VerifiableQuery` incorporate a canonicalized header set (topic + shop + webhook-id + body) into `to_signable_string` rather than the raw body alone, or by requiring/validating that the `shop` field for a given webhook_id matches records already known to the app (e.g., an existing session for that shop) before dispatching to the handler.

### Proof of Concept
1. Register an `orders/create` HTTP webhook handler as documented in `docs/usage/webhooks.md:19-30`, and install the app on attacker-owned shop `attacker.myshopify.com`.
2. Create an order on `attacker.myshopify.com` to trigger Shopify to POST a webhook to the app's endpoint; capture the raw body `B` and header `x-shopify-hmac-sha256: H`.
3. Replay the request to the same endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds (per [3](#0-2) ) because it only checks `to_signable_string` (`B`) against `H`.
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)` to the app handler, which processes attacker-supplied order data as belonging to the victim shop.
