## Analysis

I found a valid analog in `EvmHost.sol`. This is the same bug class as the BlueBerry finding: a `payable` entry point accepts `msg.value` of native token to cover a fee, forwards the *entire* `msg.value` to an external call, and never reclaims/forwards back any leftover native token to the original caller.

### Title
Excess native token sent to `dispatch()`/`fundRequest()` is refunded by the Uniswap router to `EvmHost` instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment and swap it for `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, but pass the *full* `msg.value` as the swap's `amountInMax` while only needing `post.fee`/`get.fee`/`amount` of output tokens. None of these functions capture the `amounts[0]` returned by the router or forward the leftover ETH back to the caller.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

In `dispatch(DispatchGet)`: [2](#0-1) 

In `fundRequest`: [3](#0-2) 

`swapETHForExactTokens(amountOut, path, to, deadline)` is a standard Uniswap V2 router function that only requires the caller to send *at least* `amountIn` (the amount needed to receive exactly `amountOut`); the router's own implementation refunds `msg.value - amountIn` back to its immediate caller — which here is `EvmHost` itself (since `EvmHost` calls the router with `{value: msg.value}`), not the original transaction sender. Because `EvmHost` discards the return value (`amounts[0]`) and has no logic to forward the difference back to `_msgSender()`, any native token sent above the exact amount required for the fee swap is refunded into `EvmHost`'s own balance and becomes permanently unaccounted for/stuck.

This is the exact bug class from the reported analog: a `payable` function that forwards `msg.value` to a sub-call which may return excess funds, with no refund path back to the caller.

Notably, the codebase's own newer intents contracts (`IntentGatewayV2.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`) correctly capture the swap's return value and refund the caller: [4](#0-3) 

This demonstrates the fix pattern exists elsewhere in the codebase but was not applied to the core `EvmHost.sol` dispatch/fund paths.

### Impact Explanation
Any user (or any `HyperApp`-based contract on behalf of a user, e.g. via `dispatchWithNative`-style helpers documented for `IDispatcher(_host).dispatch{value: msg.value}(...)`) who overestimates the native token amount needed to cover a relayer fee — which is expected in practice since exact `feeToken` output pricing via AMM slippage is hard to predict client-side — permanently loses the excess to `EvmHost`, with no recovery mechanism exposed to the caller. This is a direct loss of funds for any unprivileged caller dispatching POST/GET requests or funding a request with native token, which is one of the most common interaction paths in Hyperbridge (documented as the primary way to pay for cross-chain messages with native token). [5](#0-4) 

### Likelihood Explanation
High. This is triggered by ordinary use of the documented "Native Token Payment" flow (`dispatch{value: msg.value}(post)`), which explicitly instructs integrators to just forward `msg.value`. Since it is generally not possible to compute the exact optimal `amountIn` client-side without racing on-chain reserves, users routinely send some safety margin of native token, guaranteeing this leftover-refund issue occurs on a large fraction of native-token-funded dispatches.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or `payable(msg.sender)`), mirroring the pattern already used in `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`.

### Proof of Concept
1. User calls `IDispatcher(host).dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.1 ether` worth of ETH to swap into `feeToken`.
2. `EvmHost.dispatch` calls `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)`.
3. The router deposits only the needed `amountIn` (~0.1 ether) into WETH/swap, and refunds the remaining ~0.9 ether to `msg.sender` of the router call, which is `EvmHost`.
4. `EvmHost` never reads this refund nor forwards it to the user; the ~0.9 ether sits in `EvmHost`'s balance, unrecoverable by the user.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
