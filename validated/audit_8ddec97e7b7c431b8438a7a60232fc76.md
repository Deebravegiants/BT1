### Title
Predictable, non-random session identifiers enable session fixation / session hijacking - (File: `lib/shopify_api/auth/session.rb`)

### Summary
`ShopifyAPI::Auth::Session.from` derives the session's `id` — the value that is later stored as the `shopify_app_session` cookie and used verbatim as the lookup key for the stored access token — from fully public, guessable inputs (`shop` domain and, for online tokens, the merchant's numeric `associated_user.id`), rather than from a cryptographically random value or a value bound by any signature. Because the gem's own cookie helper (`SessionUtils.cookie_session_id`) blindly trusts whatever value comes back in the cookie as the session key, an attacker who can place or predict this deterministic value in a victim's cookie jar can have their browser treated as an authenticated session for that shop.

### Finding Description
When OAuth completes, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session and, for non-embedded apps, sets the browser cookie value to `session.id`: [1](#0-0) 

That `id` is computed in `Session.from` as a simple deterministic string with no random component: [2](#0-1) 

- Offline sessions: `id = "offline_#{shop}"` — fully derivable from the public `*.myshopify.com` domain.
- Online sessions: `id = "#{shop}_#{associated_user.id}"` — derivable from the shop domain plus a small, often-enumerable numeric user id.

This value is round-tripped as the entire content of the `shopify_app_session` cookie: [3](#0-2) 

and on every subsequent request, `SessionUtils.cookie_session_id` reads that cookie value back out and hands it straight to the host application as "the session id" with no verification that the caller ever legitimately obtained it: [4](#0-3) [5](#0-4) 

The identity binding this breaks is:

`cookie value presented by the browser` **should equal** `a secret, unguessable token proving prior successful OAuth for that shop/user`

but instead it equals:

`a string an attacker can compute offline from public data (shop domain, small numeric user id)`

Unlike the OAuth callback's `AuthQuery`/webhook `Request`, which are protected by an HMAC computed with `Context.api_secret_key` (see `Utils::HmacValidator.validate`), the session cookie itself carries no HMAC or signature — the "authentication" for the non-embedded/cookie fallback path is nothing more than knowledge of the shop's domain (and possibly a small integer).

### Impact Explanation
This matches the High-severity "session fixation" bucket in scope. Because the id is fully predictable, an attacker does not need to intercept anything: they can pre-compute `offline_victim-shop.myshopify.com` (or `victim-shop.myshopify.com_<n>` for a range of small user ids) and inject it as the `shopify_app_session` cookie value into their own browser, or fixate it into a victim's browser before/during the victim's OAuth flow. If the host application's session store (which the gem's documented pattern explicitly drives via this cookie value, see `docs/usage/oauth.md`) later persists or already contains a session keyed by that same predictable id — which is the expected outcome after the legitimate merchant completes install — the attacker's browser is treated as the authenticated merchant session, exposing the stored access token/API access for that shop (cross-tenant access to a merchant's data).

### Likelihood Explanation
Likelihood is elevated because:
- Shop domains (`*.myshopify.com`) are public/guessable.
- Online session user ids are small sequential integers, making brute force/enumeration feasible.
- The vulnerable code path (`cookie_session_id`) is the gem's documented, first-class mechanism for non-embedded apps and as a fallback for embedded apps without a JWT, so any app following the published `docs/usage/oauth.md` guidance inherits this weakness without any extra misconfiguration.

### Recommendation
Do not use a deterministic, guessable string as the bearer session identifier stored in a cookie. Generate a cryptographically random session id (e.g. `SecureRandom` as already used for the default `Session#id` when none is supplied, see `lib/shopify_api/auth/session.rb` line 72) and use the deterministic `shop`/`shop_user` string only as an internal lookup key inside the host application's storage, never as the value exposed to the browser. Alternatively, sign/HMAC the cookie value so that its authenticity, not just its knowledge, can be verified server-side before trusting it as a session key.

### Proof of Concept
1. Attacker learns (or guesses) a target shop's domain, e.g. `victim-shop.myshopify.com` (public/enumerable).
2. Attacker computes the offline session id exactly as the gem does: `offline_victim-shop.myshopify.com` (`lib/shopify_api/auth/session.rb:116`).
3. Attacker sets their browser's `shopify_app_session` cookie to this value and issues a request to the host app.
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the raw cookie value unchanged (`lib/shopify_api/utils/session_utils.rb:29-35, 69-71`) and looks up the corresponding stored session/access token — if that shop has already completed OAuth (the normal case for an installed app), the attacker's request is now treated as belonging to that shop's session.
