### Title
`connectedOriginsApi`'s trust/auto-approve reads and writes are backed by `unsafeStorage` with no lock gating, unlike comparable APIs - ([File: features/connected-origins/module/connections.js])

### Summary
The `connectedOrigins` feature explicitly aliases its storage to `unsafeStorage` [1](#0-0) , and its `isTrusted`, `isAutoApprove`, `setAutoApprove`, `setFavorite`, `add`, and `untrust` methods perform no lock check before reading/writing that storage [2](#0-1) . These methods are exposed verbatim through `connectedOriginsApi` [3](#0-2) , in contrast to `addressProviderApi`, which explicitly gates equivalent calls behind `lockedAtom.get()` [4](#0-3) .

### Finding Description
`StorageMobile` has no `isLocked()`/`unlock()` gating concept — it reads/writes plaintext JSON immediately via AsyncStorage [5](#0-4) [6](#0-5) . This contrasts with `createStorageEncrypted`, which defers all `get`/`batchGet` calls until `cryptoFunctionsPromise` resolves at unlock [7](#0-6) .

The `connectedOrigins` module deliberately binds its `connectedOriginsAtom` (holding `trusted`, `autoApprove`, `favorite`, `activeConnections` fields per origin) to `unsafeStorage` rather than encrypted storage [8](#0-7) . The `ConnectedOrigins` class methods `isTrusted`, `isAutoApprove`, `setAutoApprove`, `setFavorite`, `add`, `untrust` read/write this atom directly with no lock check anywhere in the class [9](#0-8) . These are then re-exported as-is by `connectedOriginsApi` for consumption by RPC/dapp-facing layers [10](#0-9) .

By comparison, `addressProviderApi` explicitly wraps each sensitive call with `withWalletAccountInstance`, which throws `'address-provider: wallet should be unlocked'` if `lockedAtom.get()` is true [4](#0-3) , demonstrating that the codebase's established pattern for wallet-lock-sensitive APIs is to gate access at the API layer — a pattern absent from `connectedOriginsApi`.

I was unable to fully verify, within the available search budget, whether there is an outer origin/RPC bridge (e.g., the provider/content-script bridge that dispatches dapp-originated calls to `connectedOriginsApi`) that globally enforces a lock check before dispatching to *any* public API method regardless of the API's own gating. No such global lock-gating middleware was found in `libraries/json-rpc` or `sdks/headless/src/features/wallet-rpc` [11](#0-10) [12](#0-11) , and the `connectedOriginsPlugin`'s `onLoad`/`onUnlock` hooks only gate the atom *observer* (event pushes), not direct RPC calls to `isTrusted`/`isAutoApprove`/`setAutoApprove` [13](#0-12) . Given the index's scope is limited to what's indexed, this could not be conclusively ruled out, but no such gating was found in the codebase for this specific API.

### Impact Explanation
If reachable pre-unlock via an RPC surface (consistent with the described precondition), an unprivileged dapp could: (1) read `isTrusted`/`isAutoApprove` state for its own or other known origins while the wallet is locked, and (2) call `setAutoApprove`/`setFavorite`/`add` to pre-seed `autoApprove: true` or `trusted: true` flags for its origin before authentication completes, so that immediately after the user unlocks, subsequent origin-approval prompts are silently bypassed via `getConnectedAccounts`'s `isTrusted` check [14](#0-13) . This matches "privilege persistence" / bypassing origin-approval gating, since trust state set while locked persists and is honored post-unlock without a fresh consent prompt.

### Likelihood Explanation
Preconditions per the prompt are that some RPC method forwards dapp calls to `connectedOriginsApi` without an explicit lock check — this codebase confirms `connectedOriginsApi`/`ConnectedOrigins` class itself performs no such check, unlike the sibling `addressProviderApi`, which does. The `add`/`setAutoApprove` methods have no argument validation tying them to an authenticated/consented flow (no caller/permission check), so exploitability hinges entirely on whether the outer transport layer gates it — which I could not fully confirm or refute from the index.

### Recommendation
Add lock gating to `connectedOriginsApi` (or the `ConnectedOrigins` module) mirroring `addressProviderApi`'s `withWalletAccountInstance` pattern: inject a `lockedAtom` dependency and reject `isTrusted`, `isAutoApprove`, `setAutoApprove`, `setFavorite`, `add`, `untrust`, `connect`, `disconnect` calls with an explicit error when `lockedAtom.get()` is true, or migrate `connectedOriginsAtom`'s storage from `unsafeStorage` to an encrypted/lock-gated storage backend so plaintext trust flags are inaccessible pre-unlock by construction.

### Proof of Concept
Integration test plan (extending `sdks/headless/__tests__/connected-origins.test.js`):
1. Start the app and call `application.create({ passphrase })` but do **not** call `application.unlock`.
2. Assert `exodus.application.isLocked()` (or equivalent) is `true`.
3. Call `exodus.connectedOrigins.add({ origin: 'evil.com', trusted: true, autoApprove: true })` — expect it to currently **succeed** (bug), then after fix expect it to reject with a lock error.
4. Call `exodus.connectedOrigins.isTrusted({ origin: 'evil.com' })` and `isAutoApprove({ origin: 'evil.com' })` while still locked — expect them to currently return `true` (bug), then after fix expect a lock error/rejection.
5. Unlock the wallet and call `exodus.connectedOrigins.getConnectedAccounts({ origin: 'evil.com' })` — currently returns connected accounts immediately (proving pre-seeded trust persisted through unlock without consent); after fix, expect trust state to have been rejected pre-unlock so no accounts are returned without a fresh approval flow.

    if (!isTrusted) return

  async _processCallMethod(request) {
    const { method: methodName, params = [], id } = request
    const methodImplementation = this._methods.get(methodName)
    if (!methodImplementation) {
      this._sendError(
        {
          ...errors.METHOD_NOT_FOUND,
          methodName,
        },
        id
      )
    } else if (typeof methodImplementation === 'function') {
      // JSON-RPC allows to send "named parameters", where params is an object
      // In case params is not an array we pass it as a first parameter to method
      const paramsArray = Array.isArray(params) ? params : [params]

      try {
        const result = await Promise.resolve(methodImplementation.apply(this._methods, paramsArray))
        this._sendSuccess({
          result,
          id,
        })
      } catch (error) {
        this._sendError(error, id)
      }
    } else {
      this._sendError(errors.INTERNAL_ERROR, id)
    }
  }

import { createInMemoryAtom } from '@exodus/atoms'

const walletRpc = (api) => {
  const id = 'wallet'

  const createSeedIngestingProxy = (primarySeedIdAtom) =>
    new Proxy(api, {
      get(target, prop) {
        if (prop === 'unlock') {
          return async (...args) => {
            const { primarySeedId } = await target[prop](...args)
            await primarySeedIdAtom.set(primarySeedId)
            return primarySeedId
          }
        }

        return target[prop]
      },
    })

  return {
    id,
    definitions: [
      {
        definition: {
          id: 'primarySeedIdAtom',
          type: 'atom',
          factory: () => createInMemoryAtom(), // eslint-disable-line @exodus/hydra/in-memory-atom-default-value
          public: true,
        },
      },
      {
        definition: {
          id,
          type: 'module',
          public: true,
          factory: ({ primarySeedIdAtom }) => createSeedIngestingProxy(primarySeedIdAtom),
          dependencies: ['primarySeedIdAtom'],
        },
      },
      {
        definition: {
          id: `${id}Api`,
          type: 'api',
          factory: ({ primarySeedIdAtom }) => ({
            [id]: createSeedIngestingProxy(primarySeedIdAtom),
          }),
          dependencies: ['primarySeedIdAtom'],
        },
      },
    ],
  }
}

export default walletRpc
