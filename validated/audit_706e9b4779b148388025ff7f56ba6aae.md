### Title
Webhook shop-domain is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and later verifies) only the raw request body via HMAC, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC of the *body* and then dispatches the handler using the *header-derived* `shop`, which is never bound to the signature. An attacker who can reach the host application's webhook endpoint (no Shopify credentials required) can replay any previously-observed, validly-signed webhook body while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the handler to process legitimate, signature-valid data under a victim/attacker-chosen tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is a plain header lookup, not part of the signed data: [2](#0-1) 

`Registry.process` validates the HMAC (of the body only) and then hands `request.shop` straight to the handler as the tenant identity for the event, with no cross-check that the shop is the one the payload was actually generated for: [3](#0-2) 

By contrast, `HmacValidator.validate` uses `OpenSSL.secure_compare` against a `computed_signature` derived purely from `to_signable_string`: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop used for tenant dispatch`. Here, `shop` used for dispatch is sourced from `X-Shopify-Shop-Domain`, a header entirely outside the HMAC's signed bytes, so the equality is not enforced — the gem verifies "these bytes (body) are authentic" but then trusts an unrelated, unauthenticated header as the tenant identifier for the same event.

### Impact Explanation
This breaks the tenant (shop) binding that host applications rely on when this gem's `Registry.process`/`WebhookMetadata` is used to route webhook data per-merchant. An attacker who obtains one genuine (previously delivered, or GDPR-mandatory-topic) webhook body/signature pair for their own shop, or intercepts/replays a body whose HMAC remains valid, can resend it with a different `shop-domain` header and have the host application process/store that event as if it belonged to another tenant — a cross-tenant data-confusion condition. This matches the "Critical - cross-tenant access" impact category, since the tenant boundary (`shop`) that the rest of the SDK (session storage keyed by shop, `WebhookMetadata.shop`) depends on is not authenticated.

### Likelihood Explanation
Exploitability requires only network access to the host app's public webhook receiver endpoint and one legitimately-signed webhook body for the same API secret (attacker's own shop is sufficient, since `hmac-sha256` is a function of the app's shared secret, not the shop). No access token, `client_secret`, or privileged account is needed — only the ability to send an HTTP POST with attacker-controlled headers, which is the definition of an unprivileged internet user in this rule set.

### Recommendation
Include `shop` (and ideally `topic`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the payload before trusting it for dispatch — e.g. have `Webhooks::Request#to_signable_string` incorporate the shop domain header alongside the raw body, or require the host application to independently verify that `request.shop` matches a shop it has an active, established session/webhook subscription for before invoking the handler.

### Proof of Concept

# Attacker has a valid webhook delivery for their own shop "attacker-shop.myshopify.com"
# (any genuine webhook received from Shopify with a correct X-Shopify-Hmac-Sha256 for `raw_body`)

raw_body = '{"id":123,"note":"legit payload"}'
valid_hmac_b64 = "<captured from the real Shopify delivery, valid for raw_body + app secret>"

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unauthenticated
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HMAC validation succeeds because it only checks raw_body against the shared secret,
# not the shop header, so the host app's handler is invoked believing this event
# belongs to "victim-shop.myshopify.com".
