### Title
Emporium's stateless call path allows any prover to move NFTs/ERC1155 held by Emporium that were never scoped in `circomData.erc20TokenAddresses` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`Transferer.onERC721Received`/`onERC1155Received` unconditionally accept any NFT sent to the Emporium contract, and `EmporiumUpgradeable.runAction`'s CASE 2 "stateless" branch executes an arbitrary `op.endpoint.call(op.callData)` from `address(Emporium)` with no signature requirement when `signerAddress == address(0)`, and with no check tying `op.endpoint`/`op.callData` to `circomData.erc20TokenAddresses`. Since Hinkal's only value-conservation equality (`balanceDif == amountChanges[i] + utxoAmount`) iterates strictly over `circomData.erc20TokenAddresses`, any asset outside that array (NFTs, ERC1155, or any ERC20 not listed) held by Emporium can be redirected by anyone holding a valid but otherwise unrelated Hinkal proof.

### Finding Description
The claimed broken equality: `sum(assets held by Emporium before tx) == sum(assets held by Emporium after tx)` restricted to the identity of whoever is "authorized" to move them. In practice, no such per-owner equality exists for anything outside `erc20TokenAddresses`, so this holds vacuously true/false regardless of who moves it.

Path:
1. `nft.safeTransferFrom(attacker, address(Emporium), tokenId)` succeeds unconditionally via [1](#0-0) .
2. Attacker calls `Hinkal.transact` with a proof for their own ERC20/ETH UTXOs and `externalActionData.externalAddress = Emporium`, going through `performHinkalChecks`/`verifyProof`/`rootHashExists` (all satisfied normally, since the proof is legitimately generated for the attacker's own funds) [2](#0-1) .
3. `_externalTransact` calls `EmporiumUpgradeable.runAction` with `circomData` and `deltaAmountChanges` derived solely from `erc20TokenAddresses` [3](#0-2) .
4. Inside `runAction`, `verifyWallet` short-circuits with no signature check at all when `stack.signerAddress == address(0)` [4](#0-3) .
5. CASE 2 then executes `op.endpoint.call{value: op.value}(op.callData)` with only `callHinkalWallet`/`doSendToRelay` selectors blocked - any other target/selector, including `IERC721.transferFrom(Emporium, attacker, tokenId)`, is permitted [5](#0-4) .
6. Because the call originates from `address(Emporium)` (msg.sender as seen by the NFT contract), and Emporium is the current token owner, `transferFrom`'s `_isApprovedOrOwner` check trivially passes.
7. The post-loop balance-conservation logic in `runAction` and in `Hinkal.transact` only ever reads `circomData.erc20TokenAddresses`/`getBalancesForArray(circomData.erc20TokenAddresses)` [6](#0-5)  and [7](#0-6) , so the NFT movement is never observed, checked, or constrained by any part of the accounting.

None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, or `dimensionsCheck` reference or constrain assets outside `erc20TokenAddresses`, so this path is fully reachable by an unprivileged attacker with an otherwise ordinary, self-funded Hinkal transaction.

### Impact Explanation
Any NFT/ERC1155 (or any asset type never enumerated in `erc20TokenAddresses`) that ends up held by the Emporium contract - whether by mistake, by a legitimate but incomplete swap flow, or by direct external transfer - can be moved out by **any** party who submits a valid but otherwise unrelated Hinkal proof, since Emporium's arbitrary "stateless" call is gated by nothing tied to asset ownership or depositor identity. This is "executing calls or moving assets a wallet owner or prover never authorised," which the given rubric classifies as **High** (not Critical, since NFTs held by Emporium are not part of Hinkal's shielded UTXO/ERC20 value-conservation system, so no shielded-fund theft, minting-without-backing, double-spend, or proof/nullifier bypass occurs). The exploit is repeatable for every asset that lands at Emporium outside the tracked token array.

### Likelihood Explanation
No privileged role is required. The attacker only needs: (a) to get any NFT/ERC1155 onto the Emporium contract (trivially satisfiable since `onERC721Received`/`onERC1155Received` accept unconditionally), and (b) their own normal, legitimately provable Hinkal transaction targeting Emporium with `EmporiumStack.signerAddress = address(0)` and one stateless `EmporiumOperation` pointing at the NFT contract's `transferFrom`. Both are fully within an unprivileged attacker's control, no relayer/oracle/social-engineering assumptions needed, and the attack is repeatable for any such stranded asset.

### Recommendation
- Require that CASE 2 stateless `op.endpoint` calls are restricted to addresses in `circomData.erc20TokenAddresses` (or an explicit allowlist of swap-router/DEX endpoints), rather than any arbitrary address.
- Alternatively, enforce that Emporium never holds non-enumerated assets across transactions (sweep/reject any asset not present in `erc20TokenAddresses` for the current call), or require signature verification (non-zero `signerAddress`) for every operation, including stateless ones, so that arbitrary calls cannot be authorized purely by an unrelated ERC20 proof.
- Disable/guard `onERC721Received`/`onERC1155Received` on Emporium if NFTs/ERC1155 are not an intended asset class for this contract.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as an external action), and a mock ERC721.
2. Mint `tokenId` to `attacker`; `attacker` calls `nft.safeTransferFrom(attacker, address(Emporium), tokenId)` directly (no Hinkal involvement) - assert `nft.ownerOf(tokenId) == address(Emporium)`.
3. `attacker` deposits some ERC20/ETH into Hinkal normally and generates a locally-produced valid proof for a `transact` call with `externalActionData.externalAddress = Emporium`, `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: address(nft), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC721.transferFrom.selector, address(Emporium), attacker, tokenId)}]}`.
4. Call `Hinkal.transact(...)`.
5. Assert `nft.ownerOf(tokenId) == attacker` after the call.
6. Assert that all `require`/equality checks in `Hinkal.transact` (`balanceDif == amountChanges[i] + utxoAmount` for each `i` in `erc20TokenAddresses`) passed without ever referencing `tokenId` or `nft`, proving the NFT transfer was completely outside Hinkal's value-conservation logic.
