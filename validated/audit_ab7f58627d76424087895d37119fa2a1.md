### Title
Self-signup filter bypass due to mismatched string representations of the same user identity in QR code parsing - (File: `src/plans/qr_scan/user.rs`, `src/plans/mod.rs`)

### Summary
The check meant to prevent an operator from signing themselves up (using their own operator QR code as the user QR code) relies on a raw string equality comparison of `user_id` fields that can be produced by two structurally different parsing paths yielding different string representations of what can be the same underlying identity, exactly analogous to the Notional `ETH_ADDRESS` vs `ALT_ETH_ADDRESS` confusion where two different representations of the same value defeat an equality-based guard.

### Finding Description
`qr_scan::user::Data::try_parse` in [1](#0-0)  produces the `user_id` field through two entirely different code paths depending on the QR-code format that was scanned:

1. Via `decode_qr(code)`, which yields a `Uuid` normalized to its canonical hyphenated lowercase 36-character string form: `user_id.hyphenated().to_string()` [2](#0-1) .
2. Via the `QR_CODE_V2` regex, which captures the `user_id` group *verbatim from the scanned text*, including a documented "shortened" form that omits the last two UUID groups entirely (as shown by `test_v2_shortened`, which parses `"3bcf883d-ce22-4a03"` as a valid, complete `user_id`) [3](#0-2) [4](#0-3) .

Downstream, `handle_user_qr_code` in `MasterPlan` uses a plain string equality check between the freshly scanned user QR code and the previously scanned operator QR code to filter out the case where the same QR code (i.e., same identity) is presented for both roles:

```
if user_qr_code.user_id == operator_data.qr_code.user_id {
    ...
    tracing::info!("User QR-code is the same as the operator QR-code, retrying");
    return Ok(None);
}
``` [5](#0-4) 

Because `user_id` is a bare `String` and not a normalized/canonical identity type, this comparison is only reliable if the two QR codes were parsed via identical code paths, producing identical string representations. Since the "V2" legacy scheme (used by `operator::Data`) accepts a shortened/truncated user-id string that omits UUID suffix groups, while the `decode_qr` path always yields the fully-qualified, hyphenated 36-character UUID, the same underlying identity can be represented as two different strings depending on which QR format the operator or user code was generated from. The equality check compares raw strings without any canonicalization, so it does not reliably catch the case where the operator's own identity — encoded once via the truncated V2 format and once via the full `decode_qr` UUID format — is used for both the operator and the "user" QR scans.

### Impact Explanation
If the self-signup guard can be defeated because the same identity is represented differently across the operator and user QR-code parsing paths, an operator could scan a QR code representing themselves as the "user" and proceed through the signup flow that the check at [5](#0-4)  was specifically designed to block. This directly maps to the "unauthorized or misattributed signup" impact category: an operator-controlled identity value could bypass the intended safeguard preventing operators from enrolling themselves through the operator flow, given the correct crafted/shortened QR-code representation.

### Likelihood Explanation
Exploiting this requires the attacker (an operator with access to the Orb) to control or influence which QR-code format encodes their identity for the "user" role versus the "operator" role — feasible since both the V2 shortened text format and the `decode_qr` link format are accepted inputs for user/operator QR scanning, and the shortened form is explicitly supported and tested (`test_v2_shortened`). No cryptographic or hardware-level exploit is needed; it is purely a string-representation mismatch in application logic, similar in nature and low complexity to the referenced bug class.

### Recommendation
Do not compare raw, differently-sourced string forms of `user_id` for identity equality. Normalize both operator and user identifiers to a canonical form (e.g., parse both as UUIDs and compare byte/canonical hyphenated forms, rejecting any shortened/partial representation) before performing the self-signup equality check in `handle_user_qr_code`. Reject QR codes whose `user_id` cannot be normalized to a complete UUID rather than allowing shortened forms to pass through unchanged.

### Proof of Concept
1. An operator generates two QR codes referencing the same identity: one in the legacy `userid:<uuid>:<policy>` V2 text format using the "shortened" UUID variant (e.g. `userid:3bcf883d-ce22-4a03:1`, valid per `test_v2_shortened`) used as the **operator** QR code, and one via the `decode_qr`-compatible encoded format (which always resolves to the full hyphenated UUID `3bcf883d-ce22-4a03-xxxx-xxxxxxxxxxxx`) used as the **user** QR code.
2. `scan_operator_qr_code` parses the operator code into `operator_data.qr_code.user_id == "3bcf883d-ce22-4a03"` [3](#0-2) .
3. `scan_user_qr_code` → `handle_user_qr_code` parses the user code via `decode_qr` into `user_qr_code.user_id == "3bcf883d-ce22-4a03-xxxx-xxxxxxxxxxxx"` (full hyphenated form) [2](#0-1) .
4. The equality check `user_qr_code.user_id == operator_data.qr_code.user_id` at [5](#0-4)  evaluates to `false` even though both QR codes represent the same identity, allowing the flow to continue and treat the operator's own identity as a distinct "user" for signup purposes.
