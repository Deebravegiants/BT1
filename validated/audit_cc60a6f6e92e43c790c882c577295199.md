### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates incoming webhooks solely by computing an HMAC over the raw request body and comparing it to the `hmac-sha256`/`x-shopify-hmac-sha256` header, using the app's `api_secret_key`, which is a single secret shared across **all** shops that install the app. The `shop` field returned by `Request#shop`, however, is taken directly from an unauthenticated header (`shopify-shop-domain`/`x-shopify-shop-domain`) and is **not** included in the signed bytes. `Registry.process` trusts this unauthenticated `shop` value and hands it straight to the app's `WebhookHandler` as the tenant identity for the event.

### Finding Description
The binding that should hold is:
`shop value trusted by the handler == shop that produced the HMAC-covered bytes`

In this gem it does not:

- `HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against `Context.api_secret_key`: [1](#0-0) 

- `Webhooks::Request#to_signable_string` returns only the raw body — no shop, topic, or webhook-id is included in the signable bytes: [2](#0-1) 

- `Webhooks::Request#shop` is read straight from an attacker-controllable header, entirely independent of the HMAC: [3](#0-2) 

- `Registry.process` validates only the HMAC (i.e., only the body), then immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata`, which is passed to the app-supplied handler as the trusted tenant identifier: [4](#0-3) 

Critically, `api_secret_key` is the app's single OAuth `client_secret` — the same value is used to sign/verify webhooks for *every* merchant shop that has installed the app, not a per-shop secret: [5](#0-4) [6](#0-5) 

Because the shared secret is the same for every shop, an unprivileged attacker who has installed the app for their own shop (or otherwise gets one valid HMAC-signed webhook body destined for their shop) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a **victim** shop's domain. `HmacValidator.validate` still succeeds because the shop header is outside the signed data, and `Registry.process` will pass the forged `shop` value on to the application handler as if the event genuinely originated from the victim shop.

Documentation and the reference handler pattern confirm the handler is expected to use `data.shop` as the authoritative tenant identity to route/process work (e.g., look up the shop's session, enqueue jobs "for the shop", etc.): [7](#0-6) [8](#0-7) 

This is the "field acted on but not covered by the HMAC" bug class: the `shop` field is consumed as trusted identity data by downstream handler logic, but it is never authenticated by the HMAC that is supposed to prove the request originated from Shopify for that particular shop.

### Impact Explanation
This is a **cross-tenant** issue (Critical bucket): an attacker with a legitimate but low-privilege trust relationship with the app (their own installed shop, which is enough to receive at least one real, validly-signed webhook body) can impersonate another merchant's shop identity toward the app's own webhook processing pipeline. Depending on what the app's handler does with `data.shop` (a very common pattern per the gem's own documentation example — looking up sessions/store records keyed by shop, enqueuing background jobs scoped to that shop, or triggering mutating GraphQL/REST calls using the session tied to that shop), this can lead to processing of forged data under another tenant's identity, corrupting or acting on another merchant's store record with attacker-supplied body content. This breaks the identity boundary that HMAC verification is meant to enforce between tenants of the same app.

### Likelihood Explanation
Any external, unprivileged party who can install the app once (a normal marketing/self-serve app install, not requiring `api_secret_key`, TLS interception, or privileged access) obtains a legitimately signed webhook body/HMAC pair for at least one topic. Forging the HTTP header on the replayed request requires no cryptographic secret — the shop header is plain text and the HMAC never covers it. The only constraint is that the attacker must supply a body whose content they don't fully control (it's the real event body Shopify sent them), but topics such as `app/uninstalled`, `shop/update`, or any of the many low-value-content topics still carry a `shop` field the handler will trust — and for handlers keying purely off the `shop` header (e.g., "refresh shop record for `data.shop`", "invalidate cache for `data.shop`", "requeue mandatory GDPR job for `data.shop`") this is directly exploitable with attacker-controlled timing and repetition.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) inside the HMAC-covered bytes, or otherwise cryptographically bind the shop header to the signed body, e.g.:
- Change `Webhooks::Request#to_signable_string` to incorporate the shop-domain header (and topic) alongside the raw body, and have `HmacValidator` (or a webhook-specific validator) verify that combined string.
- Alternatively, cross-check `request.shop` against a shop that the app has an active, previously-established session/webhook-registration for, before trusting it, rather than trusting the header value implicitly.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed over `B` using the app's single shared `client_secret`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` (they control the endpoint/network path to their own installed app instance, or otherwise observes it as the shop owner).
3. Attacker crafts a new HTTP POST to the same webhook endpoint with the *same* body `B` and *same* `X-Shopify-Hmac-Sha256: H` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. Server code constructs:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)
)
```
5. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B` (`to_signable_string`), matching `H` — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`.
6. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` and invokes the app's handler — see `lib/shopify_api/webhooks/registry.rb:188-199` — causing the handler to act as though the event genuinely came from `victim-shop.myshopify.com`.
