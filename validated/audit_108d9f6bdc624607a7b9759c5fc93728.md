### Title
`describeWithdrawal` in Omni Bridge reports `completed` for destination chains that are neither EVM/Sol/Fogo/Strk/Aptos nor UTXO, without checking any on-chain outcome - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal` branches on the destination chain kind to decide how to fetch the finalized transaction hash. Any chain that doesn't match the explicitly enumerated `isEvmChain`, `ChainKind.Sol`, `ChainKind.Fogo`, `ChainKind.Strk`, `ChainKind.Aptos`, or `isUtxoChain` falls into an `else` branch that unconditionally returns `{ status: "completed", txHash: null }`, even though the Omni Bridge API response (`transfer`) may not indicate the transfer actually finalized on the destination chain.

### Finding Description [1](#0-0) 

```
async describeWithdrawal(...) {
    const transfer = (await this.omniBridgeAPI.getTransfer(...))[args.index];
    if (transfer == null || transfer.recipient == null) {
        return { status: "pending" };
    }
    const destinationChain = getChain(transfer.recipient as OmniAddress);
    let txHash = null;
    if (isEvmChain(destinationChain) || destinationChain === ChainKind.Sol || ... ) {
        txHash = transfer.finalised?.transaction_hash;
    } else if (isUtxoChain(destinationChain)) {
        txHash = ...;
    } else {
        return { status: "completed", txHash: null };
    }
    if (!txHash) { return { status: "pending" }; }
    return { status: "completed", txHash };
}
```

For chains handled in the first two branches, `completed` is only returned once `transfer.finalised?.transaction_hash` (or the UTXO equivalent) is actually present - i.e., the status genuinely reflects an on-chain, finalized outcome. The `else` branch skips this check entirely: as soon as the Omni Bridge API returns any transfer record with a non-null `recipient` for one of these "other" chains, the SDK reports `completed`, regardless of whether the transfer has actually landed on the destination chain. This breaks the equality "status reported == on-chain outcome" that the interface contract explicitly promises: the `Bridge.describeWithdrawal` doc states it "Returns the current status without polling" implying it should reflect the true on-chain state [2](#0-1) .

### Impact Explanation
An integrator (wallet, backend, or other consumer of this SDK) that uses `describeWithdrawal`/`waitForWithdrawalCompletion` to decide when to credit a user's balance, mark an order as complete, or release funds could act on a `completed` status that does not correspond to an actual on-chain completion for these non-enumerated chains. This matches the High-severity impact category: "a status or hash misreport making an integrator credit or refund twice" — if the withdrawal is prematurely marked complete but has not landed, and the integrator's off-chain bookkeeping credits the user based on this false-positive status, double crediting or crediting against a stuck/failed withdrawal becomes possible.

### Likelihood Explanation
The likelihood depends entirely on which `ChainKind` values exist in `@omni-bridge/core` beyond the ones explicitly checked (EVM chains, Sol, Fogo, Strk, Aptos, and UTXO chains). I was not able to fully enumerate `ChainKind` in the available context (attempts to open `omni-bridge-utils.ts` and the full `omni-bridge.ts` header failed due to a tool error at the end of the investigation), so I cannot confirm with certainty whether any chain currently supported by Omni Bridge for withdrawal actually falls into this catch-all branch. Given that the Omni Bridge route also targets NEAR itself and possibly other non-EVM chain kinds tracked by `@omni-bridge/core`, this branch is reachable in principle, but I could not verify the exact current enum members before running out of tool budget.

### Recommendation
Replace the blanket `else { return { status: "completed", txHash: null } }` with a status derived from an actual verifiable field, or explicitly enumerate every supported `ChainKind` in the `if`/`else if` chain so that unknown/future chain kinds fail closed (`pending` or an explicit error) rather than fail open to `completed`. At minimum, assert on the possible `ChainKind` values so any newly added chain kind requires an explicit finalization check before it can report `completed`.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
