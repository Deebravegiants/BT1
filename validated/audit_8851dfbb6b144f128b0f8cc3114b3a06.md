### Title
Global mutable `challengePeriod` retroactively applies to already-stored state commitments, letting governance shrink the fishermen fraud-detection window after consensus proofs are already pending - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
`EvmHost` stores a single, global `challengePeriod` value that is used to gate the processing of *every* pending state commitment, regardless of what the challenge period was when that commitment was actually stored. `updateHostParams`/`updateHostParamsInternal` can change `challengePeriod` at any time without any validation and without snapshotting the old value against already-recorded `StateMachineHeight`s. This is the same root-cause pattern as the referenced Arcadia report: a risk/safety parameter is changed for the whole system, and state that was previously created under the old parameter is silently re-evaluated under the new one, without any check that the change doesn't compromise already-committed state.

### Finding Description
`HostParams.challengePeriod` is documented as the "Minimum challenge period for state commitments in seconds" and is stored as a single scalar in `_hostParams`: [1](#0-0) 

`updateHostParamsInternal` validates several fields (`hostManager`, `handler`, `consensusClient`, `hyperbridge`, `stateMachines.length`, `unStakingPeriod >= 1 days`, fee token immutability) but performs **no validation whatsoever** on `challengePeriod`, and immediately overwrites the live value used by the handler: [2](#0-1) 

Every message-processing entrypoint in `HandlerV2` computes the elapsed delay from the commitment's stored `stateMachineCommitmentUpdateTime` and compares it against the **current** `host.challengePeriod()`, not the value that was configured when that specific commitment was written: [3](#0-2) 

The same pattern repeats for GET responses, POST timeouts, and GET timeouts: [4](#0-3) [5](#0-4) 

Per Hyperbridge's own design docs, the challenge period exists specifically to give "fishermen" a promised time window to detect byzantine consensus updates and submit fraud proofs before any request/response proven against that state commitment can be processed: [6](#0-5) 

Because `challengePeriod` is a single mutable global rather than a value captured per `StateMachineHeight` at the time the commitment was stored, a legitimate, properly-authorized governance update to `challengePeriod` (e.g., lowering it for latency reasons, or even setting it to `0`) instantly and retroactively shortens (or removes) the review window for **every state commitment already stored under the previous, longer challenge period** — including commitments from consensus updates submitted moments earlier that fishermen have not yet had the originally-promised time to review. This is functionally identical to the Arcadia bug class: a parameter change made through a normal, permitted update path (`upgradeAccount` / `updateHostParams`) is applied globally without any invariant/health check that the previously-established state (an account's positions / an already-stored, not-yet-fully-challenged state commitment) remains safe under the new parameter.

### Impact Explanation
If `challengePeriod` is reduced (down to and including `0`) while a just-submitted, potentially fraudulent consensus/state update is still within its originally-promised challenge window, relayers can immediately call `handlePostRequests`/`handleGetResponses`/timeout handlers against that state commitment before fishermen have had the time they were guaranteed to submit a fraud proof and veto it. This directly undermines the optimistic-bridging security model that gives Hyperbridge's economic-security guarantee against byzantine/eclipsed consensus updates, and can lead to forged message delivery / dispatch based on an unsound, not-yet-fully-vetted state commitment — a High-severity outcome (forged message delivery / unsound state commitment acceptance).

### Likelihood Explanation
`updateHostParams` is reachable only through the authorized `hostManager` (cross-chain governance) or, on `TestnetHost`, the admin — so this is not exploitable by an arbitrary unprivileged party. However, unlike the other fields in `HostParams` (unstaking period has an explicit `1 days` floor, fee-token change is guarded, handler/consensus client/host manager addresses are interface-checked), `challengePeriod` has **no lower bound or sanity check at all**, and no mechanism exists to apply the change only prospectively to future commitments. Any routine parameter update (not necessarily malicious) that lowers `challengePeriod` will silently and immediately weaken the security of commitments already in-flight, which is a realistic operational scenario (e.g., governance tuning parameters for cost/latency) rather than a purely adversarial one.

### Recommendation
Snapshot the challenge period that was in effect at the time each `StateMachineHeight` commitment is stored (e.g., store it alongside `_stateCommitmentsUpdateTime`), and use that snapshotted value — not the live `_hostParams.challengePeriod` — when checking `ChallengePeriodNotElapsed` in `HandlerV2`. Alternatively, enforce that `updateHostParams` cannot decrease `challengePeriod` for already-recorded, still-pending commitments (only apply reductions to commitments recorded after the update), analogous to adding a post-upgrade invariant check as recommended in the referenced report.

### Proof of Concept
1. Governance/hostManager submits a consensus update for a byzantine/forked chain state; `EvmHost` stores the new `StateMachineHeight` commitment with `_stateCommitmentsUpdateTime = T0` and current `challengePeriod = C` (e.g., 1 hour).
2. Before `T0 + C` elapses (i.e., while fishermen still have time to submit a fraud proof), a legitimate governance action calls `updateHostParams` with a new `HostParams.challengePeriod = 0` (no validation prevents this, see `EvmHost.sol` lines 581-637).
3. A relayer immediately calls `HandlerV2.handlePostRequests` (or `handleGetResponses`/timeout handlers) for a request proven against the commitment from step 1. Since `host.challengePeriod()` now returns `0`, the check `challengePeriod != 0 && challengePeriod > delay` is bypassed regardless of how little time has actually elapsed since `T0`.
4. The request is dispatched to its destination module before fishermen had the originally-promised window to veto the (potentially fraudulent) state commitment, defeating the challenge-period security guarantee.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

The `update_client` method is responsible for advancing the state of the consensus client.
