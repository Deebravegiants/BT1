### Title
Webhook shop identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook only by checking the HMAC over the raw request body. The `shop` identity that is then handed to the app's handler is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC computation. This breaks the identity binding `hmac_valid(bytes) == shop_authenticated`, since the verified bytes (body) and the trusted identity (shop header) are disjoint.

### Finding Description
`Registry.process` performs exactly one check before dispatching to the app-provided handler: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC using `request.to_signable_string`, which for `Webhooks::Request` is only the raw body: [2](#0-1) 

The `shop` value used to build `WebhookMetadata` (and passed to the app's handler) is read straight from the `shop-domain` header, with no cryptographic tie to the verified body: [3](#0-2) 

Because the HMAC covers only `@raw_body` and not the `shop-domain` header, `hmac_valid(body) == true` proves only "this body was produced/authorized with the app's shared `api_secret_key`" — it says nothing about which shop it belongs to. The equality the code implicitly relies on, `verified_bytes.shop == claimed_header.shop`, does not hold: the verified bytes are the body, and the claimed shop identity is an independent, unauthenticated header.

An attacker who owns/operates their own shop with the app installed will legitimately receive Shopify-signed webhook deliveries (valid `X-Shopify-Hmac-Sha256` computed over the body with the real, shared `api_secret_key` — the same secret is used for every shop using this app, per the standard Shopify HMAC-validation model implemented here). Since the shop header is not part of the signed payload, that attacker can replay the exact same body/HMAC pair directly to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` for any other (victim) shop's domain. `Registry.process` will accept it as valid (the HMAC check passes) and invoke the handler with `shop: <victim-shop>` and attacker-chosen `body`.

### Impact Explanation
This is a cross-tenant identity confusion: data that the attacker fully controls (their own legitimately-obtained webhook body) can be attributed to an arbitrary victim shop inside the app's business logic, purely because the shop identifier is unauthenticated relative to the verified payload. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the victim's session/access token and acting on the victim's store data, writing records keyed by shop, or triggering internal automation scoped "per shop"), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's install — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker has (or creates) their own shop with the app installed — a normal, unprivileged capability for any internet user who can install a public Shopify app — and knowledge of the app's public webhook endpoint URL (typically discoverable/predictable). No possession of the `api_secret_key`, no TLS interception, and no privileged account is needed. The only extra step is a direct HTTP POST to the app's own endpoint with a spoofed header, which is trivial.

### Recommendation
Bind the shop identity to the verified bytes instead of trusting an unauthenticated header:
- Include the shop domain (and ideally topic/webhook id) inside the HMAC-signable content, or
- After HMAC validation, independently verify that the `shop-domain` header corresponds to a shop that is actually installed/known to the app (cross-check against stored sessions) before invoking any handler, and reject/flag mismatches, and
- Document clearly in `lib/shopify_api/webhooks/registry.rb` / `request.rb` that consuming apps must not trust `WebhookMetadata#shop` without independently confirming it against their own shop/session store, since it is not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and subscribes to a topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value (both fully attacker-visible, since it's their own webhook).
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the same body `B` and the same valid HMAC header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body [4](#0-3) , `Registry.process` validates HMAC successfully (since it only checks the body) [5](#0-4) , and the handler is invoked with `shop: "victim.myshopify.com"` and attacker-controlled `body`, despite the request never actually originating from or being authorized by the victim shop.

        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
      end
