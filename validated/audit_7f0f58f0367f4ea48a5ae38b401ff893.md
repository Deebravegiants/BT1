## Analog Found: CEI Violation in `IntentGatewayV2.withdraw()` (Tron variant)

### Title
State Variable (`_orders` escrow accounting) Updated After Token Transfer in `withdraw()` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` decrements the escrow-accounting mapping `_orders[commitment][token]` *after* the external token transfer call, exactly mirroring the reported bug class (state variable updated after `safeTransfer`/token movement). This is the same code that was already identified and fixed in the main EVM `IntentsBase.sol` contract, but the fix was not carried over to the Tron copy.

### Finding Description
In `withdraw()` [1](#0-0) , each token in `body.tokens` is paid out via a raw low-level `.call` to the token's `transfer` selector (or a native ETH `.call`), and only *after* that external call does the code update the escrow bookkeeping:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
...
_orders[body.commitment][token] -= amount;
```

The transaction-fee payout has the identical ordering — transfer first, `delete _orders[...][TRANSACTION_FEES]` second [2](#0-1) . This is a textbook Checks-Effects-Interactions violation, and `withdraw` carries no `nonReentrant` guard.

By contrast, the main EVM `IntentsBase.sol._withdraw` already applies the fix — it decrements `_orders[body.commitment][token]` *before* the transfer [3](#0-2) , and the accompanying reentrancy test explicitly documents this as an intentional CEI fix for the same class of bug ("Before the fix... a malicious beneficiary could re-enter and steal the escrowed tx fees. After the fix: `_filled[commitment] = msg.sender` is set at the top... before the output loop") [4](#0-3) .

The Tron contract does set `_filled[body.commitment] = beneficiary` before the token loop [5](#0-4) , which blocks the most direct re-entry vector (re-invoking `cancelOrder`/`fillOrder` for the same commitment during the reentrant callback, since those check `_filled[commitment] != address(0)`). However, `withdraw` itself uses raw `.call()` rather than `SafeERC20.safeTransfer`, has no reentrancy guard, and is reachable whenever an order escrows an attacker-chosen (potentially malicious) token — the escrowed token is fully user-controlled at `placeOrder` time. This leaves the contract exposed to any interaction added later (or any call path not yet covered by the `_filled` check) that reads or mutates `_orders[commitment][token]`/`TRANSACTION_FEES` during the external-call window.

### Impact Explanation
If any external-call re-entrant window into `_orders[commitment][*]` exists (now or introduced by future changes, since this function is not defended by a reentrancy guard, only by the `_filled` mapping written just-in-time), an attacker-controlled token used as order input could be leveraged to double-spend escrowed funds or drain protocol-fee dust before the accounting is finalized. Even absent a fully demonstrated double-withdrawal today, this is a structural fund-safety defect inconsistent with the already-hardened main EVM implementation of the same logic.

### Likelihood Explanation
Likelihood is constrained by the `_filled[commitment]` write occurring before the loop, which currently blocks the most obvious re-entrant paths (`cancelOrder`, `fillOrder` for the same commitment). I could not construct a fully concrete fund-draining PoC within the current call graph — `withdraw` is only reachable via `onAccept`/`onGetResponse`, both gated `onlyHost`, and ISMP request/response delivery is itself replay-protected, so a second, unauthorized invocation of `withdraw` for the same commitment is not directly triggerable by an external attacker under the current code. This differs materially from the original Union report, where `withdrawRewards` was a directly, repeatedly callable external function.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to update `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) before performing the external transfer, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol._withdraw`. Additionally, replace the raw `token.call(...)` transfer pattern with `SafeERC20.safeTransfer` (as the main EVM contract does) and add a `nonReentrant` guard for defense in depth, since the token used for escrow is attacker-controllable at order-placement time.

### Proof of Concept
A full step-by-step fund-drain PoC could not be constructed with confidence given the current call graph (the `_filled` guard and `onlyHost` gating on `withdraw`'s only two callers). The code-level PoC is the CEI ordering itself: place an order using a malicious ERC20 as input, have it filled/cancelled so a cross-chain `RedeemEscrow`/`RefundEscrow` message reaches `onAccept` → `withdraw`; the malicious token's `transfer()` implementation executes arbitrary attacker code before `_orders[body.commitment][token] -= amount` runs, at which point escrow accounting for that commitment/token is stale relative to actual token balance moved.
