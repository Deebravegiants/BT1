## Analysis

The reported glib bug class — an **integer overflow in a length computation while processing untrusted string data**, leading to under-allocation and a heap/DoS condition — has a concrete analog in Hyperbridge's Pharos consensus verifier.

### Title
Integer overflow in Pharos BLS-key string-length computation allows a permissionless consensus update to trigger unbounded allocation / DoS — (File: `modules/consensus/pharos/verifier/src/state_proof.rs`)

### Summary
`decode_bls_key_from_string_slot` computes a Solidity "long string" byte length from an attacker-supplied storage value and derives `slots_needed = (str_len + 31) / 32` before validating that enough storage slots were actually supplied. `str_len` itself is taken unmodified from `(header_val - 1) / 2` truncated via `low_u64()`, so it can be driven arbitrarily close to `u64::MAX` by the caller of `verify_consensus`.

### Finding Description
`PharosClient::verify_consensus` [1](#0-0)  decodes a fully attacker-controlled `proof: Vec<u8>` into a `VerifierStateUpdate` and calls `verify_pharos_block`. Inside `verify_pharos_block`, on an epoch-transition path, `state_proof::verify_validator_set_proof` is invoked **using `update.header.state_root` before `verify_block_signature` is called**: [2](#0-1) 

Because the header's `state_root` has not yet been attested by the trusted validator set's BLS signature at the point `verify_validator_set_proof` runs, the attacker can pick a self-consistent `state_root` and storage proof (Pharos uses a flat trie, verified directly against `state_root`) that carries arbitrary `storage_values`, including a crafted BLS-key "string header" slot.

`bls_data_slots_from_header` / `decode_bls_key_from_string_slot` then decode the long-string length as:
```
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
...
let slots_needed = (str_len + 31) / 32;
if data_slots.len() < slots_needed { return Err(...); }
let mut string_data = Vec::with_capacity(str_len);
``` [3](#0-2) 

`str_len` can be set close to `u64::MAX` by the attacker. The addition `str_len + 31` can overflow, which either panics (if overflow checks are enabled for the executing profile) or silently wraps to a tiny `slots_needed`, letting the bound-check `data_slots.len() < slots_needed` pass with only a handful of cheaply-supplied storage entries. Execution then reaches `Vec::with_capacity(str_len)` with the original, unmodified huge `str_len`, attempting a multi-exabyte allocation.

### Impact Explanation
This is reachable from a single unsigned/unprivileged consensus-update message relayed through `pallet-ismp`'s consensus client dispatch for the Pharos client — no governance, admin, or validator collusion needed, since the vulnerable code path executes before the block's BLS signature (i.e., before the state root's authenticity is actually established). The result is either a node/runtime panic (transaction-execution trap) or a memory-exhaustion abort, denying availability of the Pharos consensus client and thus blocking message delivery for that route — matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Any relayer/attacker can submit a `VerifierStateUpdate` proof; constructing a self-consistent flat-trie proof for a `state_root` never validated before this stage requires no special access — this makes the path trivially reachable, though whether the overflow panics or wraps (and thus whether it aborts immediately at the arithmetic or later at allocation) depends on the compiled profile's overflow-check setting.

### Recommendation
- Reorder `verify_pharos_block` so `verify_block_signature` (or at minimum, authentication of `header.state_root`) happens before `verify_validator_set_proof` is invoked, ensuring untrusted storage-derived values are never processed against an unauthenticated state root.
- Use checked/saturating arithmetic for `str_len + 31` and bound `str_len` to a sane maximum (e.g., 128 bytes, matching the expected 96/98-char BLS-key hex string) before calling `Vec::with_capacity`.

### Proof of Concept
1. Attacker crafts a `VerifierStateUpdate` whose `header.state_root` and `validator_set_proof.storage_proof/storage_values` are self-consistent under Pharos's flat-trie proof rules, with the BLS "string header" storage value set to a `U256` such that `(header_val - 1) / 2` truncates (via `low_u64`) to a value near `u64::MAX`.
2. Submit this as the consensus-update proof to `PharosClient::verify_consensus`.
3. Execution reaches `decode_bls_key_from_string_slot` before the block's BLS signature is ever checked, computes an overflowing/wrapping `slots_needed`, passes the (now trivially small) `data_slots.len() < slots_needed` check with minimal supplied slots, and then calls `Vec::with_capacity(str_len)` with the original huge `str_len`, aborting the process or panicking the runtime. fn decode_bls_key_from_string_slot(
	header_value: &Option<Vec<u8>>,
	data_slots: Option<&[Option<Vec<u8>>]>,
) -> Result<pharos_primitives::BlsPublicKey, Error> {
	use alloc::string::String;

	let header = header_value.as_ref().ok_or(Error::MissingBlsKeySlot)?;

	if header.is_empty() {
		return Err(Error::EmptyBlsKeySlot);
	}

	let header_val = decode_u256_from_storage(header)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	let bls_hex: String = if lowest_byte & 1 == 0 {
		// Short string: data is in the slot, length = lowest_byte / 2
		let len = (lowest_byte / 2) as usize;
		if len > 31 {
			return Err(Error::InvalidBlsStringLength);
		}
		// String data is stored in the high bytes of the slot
		String::from_utf8(header_bytes[..len].to_vec()).map_err(|_| Error::InvalidBlsKeyUtf8)?
	} else {
		// Long string: header contains (length * 2 + 1)
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;

		// For BLS keys, we expect a 96 or 98 character hex string
		// This requires 3 data slots (ceil(96/32) = 3)
		let data_slots = data_slots.ok_or(Error::LongStringBlsKeyUnsupported)?;

		let slots_needed = (str_len + 31) / 32;
		if data_slots.len() < slots_needed {
			return Err(Error::InsufficientStorageValues {
				expected: slots_needed,
				got: data_slots.len(),
			});
		}

		let mut string_data = Vec::with_capacity(str_len);
		for (i, slot_value) in data_slots.iter().take(slots_needed).enumerate() {
			let slot_data = slot_value.as_ref().ok_or(Error::MissingBlsKeySlot)?;
			let decoded = decode_u256_from_storage(slot_data)?;
			let bytes = decoded.to_big_endian();

			let remaining = str_len - (i * 32);
			let take = remaining.min(32);
			string_data.extend_from_slice(&bytes[..take]);
		}

		String::from_utf8(string_data).map_err(|_| Error::InvalidBlsKeyUtf8)?
	};
