### Title
NFT operator can grant a per-token approval that outlives its own operator grant, letting a third party steal the whole lending account after revocation - (File: contracts/position-nft/src/contract.rs)

### Summary
`PositionNft` exports the stock OpenZeppelin `NonFungibleToken` implementation unchanged (only `token_uri` is overridden, `contract.rs:139`). In the OZ model, `approve(approver, approved, token_id, live_until_ledger)` requires `approver` to be the owner **or an operator**, and stores an independent `Approval(token_id)` entry with its own `live_until_ledger` expiry. Nothing ties that per-token approval's lifetime to the operator's `ApprovalForAll(owner, operator)` grant. An operator whose grant is about to expire or be revoked can, while still authorized, `approve` a confederate with a far-future `live_until_ledger`. After the owner revokes the operator via `approve_for_all(owner, operator, 0)`, the per-token approval remains live, and the confederate calls `transfer_from` to seize the token — and with it the entire lending account's collateral and debt, since `account_id == token_id` (`README.md:33`, `:39-41`).

This mirrors the Frappe DocShare bug class: a user shares a permission (approval over the token) whose scope exceeds what they themselves hold — the operator's authority is bounded by `live_until_ledger` and revocability, but the approval it mints is bounded by neither.

### Finding Description
- `approve` and `approve_for_all` are the inherited OZ methods; `contract.rs:132-133` (`type ContractType = Enumerable`) pulls in `Base::approve`, which checks owner-or-operator at grant time only and writes `NFTStorageKey::Approval(token_id)` with a caller-chosen `live_until_ledger` (`README.md:95`).
- `approve_for_all(owner, operator, 0)` revokes only the `ApprovalForAll(owner, operator)` key (`README.md:96`, `:65`); it does not enumerate or clear per-token `Approval` entries the operator created.
- `transfer_from` admits a spender that is "the token's live approved address" independently of operator status (`README.md:63`), and the transfer moves the whole account: collateral and debt (`README.md:39-41`, `:168-172`).
- Owner revocation of the operator is documented as the remedy ("`0` revokes", `README.md:65`), but it cannot reach the sub-approval, so revocation is incomplete — the exact escalation the CVE describes (sharing a permission the sharer no longer has).

### Impact Explanation
Theft of user funds. Any operator (e.g., a marketplace or manager the owner temporarily approved via `approve_for_all`) can persist transfer authority over a specific position NFT to an accomplice address with `live_until_ledger` set to `u32::MAX`. When the owner later revokes the operator — the expected way to cut off its power — the pre-seeded approval survives, and the accomplice calls `transfer_from(spender=accomplice, from=owner, to=accomplice, token_id)` to take the account. The accomplice then withdraws all collateral via controller `withdraw` up to solvency limits, or takes max borrows against it. Loss is bounded only by the account's net collateral value.

### Likelihood Explanation
Requires the victim to grant `approve_for_all` to a malicious or compromised operator — a routine flow for NFT-integrated managers — and the operator to pre-seed the approval before revocation. No privileged role, no oracle manipulation, no race: two ordinary calls. The only mitigation is that approvals are per-token, so the operator must guess or front-run which token ids matter; for a known position id this is trivial.

### Recommendation
Override `approve` in `impl NonFungibleToken for PositionNft` (or wrap the base) so that when `approver` is an operator rather than the owner, the stored approval's `live_until_ledger` is clamped to the operator's own `ApprovalForAll` expiry — or simpler, restrict `approve` to the owner only, since an operator can already move the token directly and has no legitimate need to sub-delegate transfer rights. Alternatively, clear `Approval(token_id)` entries when `approve_for_all` is revoked.

### Proof of Concept
1. Alice owns position token `T` (a funded lending account).
2. Alice calls `approve_for_all(owner=Alice, operator=Mallory, live_until_ledger=L)`.
3. Mallory calls `approve(approver=Mallory, approved=Confederate, token_id=T, live_until_ledger=u32::MAX)` — passes the owner-or-operator check because the grant is live.
4. Alice revokes: `approve_for_all(Alice, Mallory, 0)`. `is_approved_for_all` is now false.
5. `get_approved(T)` still returns `Confederate`. Confederate calls `transfer_from(Confederate, Alice, Confederate, T)` — succeeds.
6. Confederate calls controller `withdraw`/`borrow` on `account_id = T` as the new owner and drains the collateral.

Owner-side revocation (`approve_for_all(..., 0)`) is documented as the fix for operator risk, but it does not reach the permission Mallory shared onward — matching the missing validation in the Frappe share path.
