Audit Report

## Title
Unbounded growth of in-memory `activeRequests` map allows unprivileged-client memory exhaustion DoS in `ConfidentialRelayHandler` - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

## Summary
`HandleJSONRPCUserMessage` accepts any caller-supplied JSON-RPC request whose `req.ID` is non-empty and ≤200 characters, then unconditionally creates and stores a new `activeRequest` entry keyed by that ID, with no authentication check, no cap on total concurrent entries, and no per-caller quota. Cleanup only happens on a 1-second ticker that reaps entries older than `requestTimeout` (default 30s), so an attacker who submits unique-ID requests faster than they expire can grow the map, its per-request response maps, and associated fan-out goroutines without bound.

## Finding Description
`HandleJSONRPCUserMessage` validates only `req.ID` length/non-emptiness and then calls `newActiveRequest`, which takes `h.mu.Lock()` and unconditionally inserts a new `*activeRequest` into `h.activeRequests` keyed by the caller-supplied `req.ID`: [1](#0-0) 

Unlike the sibling vault handler (`core/services/gateway/handlers/vault/handler.go`), which routes non-public-key methods through `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` for authorization before creating any active-request state, `ConfidentialRelayHandler.HandleJSONRPCUserMessage` performs no authorization/auth check at all before allocating the `activeRequest` and fanning out to the whole DON: [2](#0-1) [3](#0-2) 

The gateway's HTTP server (`core/services/gateway/network/httpserver.go`) forwards any POST body plus an optional bearer token straight to `ProcessRequest`; the JWT/auth header is optional (`jwtToken` defaults to `""` if absent), confirming reachability by an unauthenticated caller for handlers that don't themselves enforce auth: [4](#0-3) 

The `handler` struct holds `activeRequests` as a plain map guarded only by a mutex, with no maximum-size cap: [5](#0-4) 

Each `activeRequest` buffers a per-node `responses` map plus its own mutex and grace-window state: [6](#0-5) 

Cleanup is purely time-based, sweeping once per second and evicting only entries whose age exceeds `requestTimeout` (default 30 seconds): [7](#0-6) [8](#0-7) 

The only rate limiters configured (`globalNodeRateLimiter`, `perNodeRateLimiters`) are checked exclusively in `HandleNodeMessage`, which handles *node-originated* responses, not the user-request creation path: [9](#0-8)  There is no equivalent limiter gating `HandleJSONRPCUserMessage`/`newActiveRequest`. Additionally, every accepted request triggers an `errgroup`-based fan-out send to every DON member: [10](#0-9) 

## Impact Explanation
An unauthenticated caller reaching the gateway's user-facing JSON-RPC endpoint can sustain a flood of `MethodCapabilityExec`/`MethodSecretsGet` requests with unique, valid IDs. Each request allocates a new map entry, mutex, and per-node response map that persists for up to `requestTimeout` (30s default), and each spawns a goroutine per DON member for the send fan-out. Because entries are only evicted once per second and only past the timeout, the number of concurrently live entries scales with `attack_rate × requestTimeout`, unbounded by anything in this code path — degrading or crashing the gateway process (memory/goroutine exhaustion), a Denial of Service affecting legitimate workflow/vault traffic served by the same gateway process.

## Likelihood Explanation
The confidential relay handler's `HandleJSONRPCUserMessage` performs no authentication/authorization check itself (in contrast to the vault handler in the same package, which gates non-public-key methods through `requestProcessor.ProcessRequest`), and the underlying HTTP server treats the bearer token as optional. Absent an external layer that caps the number of *distinct concurrent* request IDs per caller (only payload-size and read/write timeouts are visible at the HTTP layer), the described accumulation is straightforward and repeatable for any party able to send POST requests to the gateway's user port.

## Recommendation
Add an explicit cap on the number of concurrently outstanding `activeRequests` (global and/or per-sender/IP), reject or backpressure new requests once the cap is reached, and/or require authentication before allocating request state for `HandleJSONRPCUserMessage`. Consider shrinking the cleanup interval relative to `requestTimeout`, or reserving map capacity/limiting growth so outstanding state cannot scale linearly with an attacker's request rate.

## Proof of Concept
1. Stand up (or point at) a gateway instance with a confidential-relay DON configured, without additional external per-caller concurrency limiting on the user HTTP port.
2. Script a client that POSTs to the gateway's user endpoint (`ProcessRequest` → `HandleJSONRPCUserMessage`) a `MethodCapabilityExec` (or `MethodSecretsGet`) JSON-RPC request with a fresh, valid (≤200-char) `req.ID` on every call, with no `Authorization` header, at a rate exceeding what `removeExpiredRequests` can reap within `requestTimeout` (30s default).
3. Observe/verify (e.g., via added instrumentation or `pprof`) that `h.activeRequests` size and total goroutine/memory usage grow roughly proportional to `attack_rate × requestTimeout` and do not shrink until the flood stops, demonstrating unbounded memory growth driven purely by an unauthenticated caller.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}

	_ = group.Wait()
