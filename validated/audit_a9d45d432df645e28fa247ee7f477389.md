### Title
Non-reentrant `placeOrder` on Tron `IntentGatewayV2` allows out-of-order nonce assignment via `predispatch` callback re-entrancy - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` assigns a monotonically-increasing `_nonce` to each order and computes the order commitment hash before making an external call to `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, but unlike the canonical EVM `IntentGatewayV2.sol`, it carries no `nonReentrant` guard. [1](#0-0)  This mirrors the Kairos root cause: an ordering/uniqueness invariant (`order.nonce = _nonce++`, consumed sequentially and assumed to correspond 1:1 with escrow/commitment bookkeeping and with off-chain indexers/relayers that key state by nonce order) can be violated by a reentrant call into `placeOrder` from the external `dispatch` callback.

### Finding Description
`placeOrder` in the Tron contract does the following, in order: stamps `order.user`, `order.source`, and `order.nonce = _nonce++`; computes the commitment (possibly with fee-reduced inputs); and — if `predispatch.call.length > 0` — calls out to an external, attacker/user-supplied dispatcher via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` before finishing escrow bookkeeping in `_orders[commitment][token]`. [1](#0-0) [2](#0-1) 

The canonical EVM version of the same function is protected with `nonReentrant`: [3](#0-2)  The Tron version has no such guard (`grep` for `nonReentrant`/`ReentrancyGuard` across `evm/tron/**` returns no matches), so `dispatch()` can re-enter `placeOrder` (or other state-mutating entry points) before the outer call finishes writing its own escrow/commitment state.

Because `predispatch.call` is attacker-controlled calldata routed through the `CallDispatcher` contract, a malicious caller can arm a target contract in that call sequence to synchronously call back into `placeOrder` (or `fillOrder`) mid-execution. This breaks the invariant that `_nonce` is consumed in the same order that `_orders[commitment][...]` escrow entries and `OrderPlaced` events are finalized/emitted — exactly analogous to the Kairos bug where reentrancy during `safeMint` let a receiver interleave loan issuance, breaking the assumption that a loan's NFT `tokenId`s are consecutive. Here, a reentrant `placeOrder` call can complete (assigning and consuming a nonce, escrowing tokens, emitting `OrderPlaced`) while the outer, first-dispatched order's escrow/commitment finalization is still pending, so the nonce sequence no longer matches the order in which orders are economically committed/escrowed. Any off-chain component (solver auction, indexer, or relayer) that assumes nonce order == escrow/commitment finalization order can be misled about which order is genuinely escrowed at a given point, misattribute solver fills, or, more seriously, interleave partial state so that escrow accounting for one order is manipulated while another order's escrow write is still outstanding in the call stack.

### Impact Explanation
This is a Medium-severity finding: it does not directly enable outright fund theft in the paths reviewed, but it breaks a state-integrity invariant (sequential/ordered nonce-to-commitment mapping) relied upon by off-chain indexers, relayers, and solver-selection logic that track intents by nonce and by the `OrderPlaced` event stream. Confusion between interleaved orders can cause incorrect escrow attribution, incorrect fill matching, or a solver filling the wrong order due to reentrant reordering — a state-consistency violation of the same class as the referenced Kairos issue, reachable by any user submitting a single `placeOrder` transaction with malicious `predispatch` calldata.

### Likelihood Explanation
Likelihood is Medium-to-High for the Tron deployment specifically: `predispatch.call` and `predispatch.assets` are fully attacker-controlled, `dispatch()` is public and unrestricted on the `CallDispatcher`, and the target of `predispatch.call` inside that dispatch can be any attacker-deployed contract that re-enters `placeOrder`. No `nonReentrant`/`ReentrancyGuard` blocks this on the Tron variant, unlike the primary EVM implementation which does guard `placeOrder`.

### Recommendation
Apply the same `nonReentrant` protection used in `evm/src/apps/IntentGatewayV2.sol`'s `placeOrder` to the Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol`, or otherwise adopt checks-effects-interactions ordering so that `_nonce` increment, commitment computation, and escrow bookkeeping are all finalized (and emitted) atomically before any external call to `ICallDispatcher.dispatch` is made.

### Proof of Concept
1. Attacker constructs an `Order` with `predispatch.call` encoding a `CallDispatcher.dispatch` payload whose target is an attacker contract `Reenterer`.
2. Attacker calls `placeOrder(order, graffiti)` on the Tron `IntentGatewayV2`. Execution reaches the line `order.nonce = _nonce++;`, computes the commitment, then invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`. [4](#0-3) 
3. `Reenterer`, invoked synchronously from inside `dispatch`, calls back into `placeOrder` with a second `order2`. Because there is no reentrancy guard, this nested call succeeds fully: it consumes `_nonce++` (now nonce N+1), computes its commitment, escrows its own tokens, and emits its `OrderPlaced` event — all before the outer call finishes escrowing tokens for the original order (nonce N).
4. Off-chain observers relying on nonce ordering to reconstruct escrow state (e.g., assuming `OrderPlaced(nonce=N)` implies order N's escrow is fully settled before nonce N+1's order begins) observe an inconsistent interleaving: order N+1 is fully escrowed and emitted before order N's escrow write completes, breaking the sequential invariant analogous to the non-consecutive `tokenId` issue in the referenced report.
