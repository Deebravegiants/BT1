### Title
Webhook HMAC signature does not cover the `shop-domain`, `topic`, `webhook-id` or `api-version` headers, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw HTTP body only, while the shop, topic, webhook id and API version used to route and process the webhook are read directly from unauthenticated headers. `Utils::HmacValidator` only proves that the body bytes were produced with the app's `client_secret`; it says nothing about which shop the request actually originated from. An attacker who can obtain any one validly-signed webhook delivery for the app (e.g. by installing the app on their own store and triggering an event) can replay that exact body with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header pointing at a different merchant, and the signature check will still pass.

### Finding Description
The HMAC binding is defined in `to_signable_string`: [1](#0-0) 

Only `@raw_body` is hashed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors, however, are read straight from attacker-visible/attacker-forgeable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust every field of the `request`, including `request.shop`, and hands it straight to the app's webhook handler: [4](#0-3) 

The equality the code implicitly relies on is:

`hmac_valid(body) == true` ⟹ `(shop_header, topic_header, webhook_id_header) are authentic for this body`

but the actual guarantee provided by the HMAC is only:

`hmac_valid(body) == true` ⟹ `body was produced by holder of api_secret_key`

Because `api_secret_key` is shared by the app across *all* installing shops (it is the app's client secret, not a per-shop secret), any merchant who installs the app can legitimately obtain a validly-signed webhook body for their own shop, then re-send that same body to the app's webhook endpoint with the `x-shopify-shop-domain` header (and/or topic/webhook-id headers) swapped to name a different, victim shop. The signature verification in `HmacValidator.validate` cannot detect this tampering because it never examines those headers.

### Impact Explanation
This breaks the tenant identity binding between the cryptographically-verified payload and the shop it is attributed to. A downstream webhook handler that uses `WebhookMetadata#shop` (built from `request.shop`) to look up a session/tenant and act on that tenant's data (e.g., update local records, revoke access, process an "app/uninstalled" cleanup, etc.) can be tricked into performing that action against an arbitrary victim shop chosen by the attacker, using only a signature the attacker rightfully obtained for their own shop. This is a cross-tenant access primitive: an unauthenticated caller with no relationship to the victim shop can cause the app to treat a forged request as authentic webhook traffic "from" that victim shop.

### Likelihood Explanation
Any user who can install the app being tested on a shop they control (which is normal, unprivileged usage of a Shopify app) can trigger any of the app's subscribed webhook topics for their own store and capture the resulting signed body/HMAC. Swapping the `x-shopify-shop-domain` (or other Shopify headers) on replay is a trivial HTTP-header edit; no secret, token, or privileged access is required to construct the attack payload. The only constraint is that the swapped webhook's body must be acceptable to the topic handler's business logic (many topics have shop-independent or minimal bodies), which is a realistic condition for several webhook topics.

### Recommendation
Bind the routing headers into the HMAC-covered material, or otherwise cryptographically tie the claimed `shop`, `topic`, and `webhook_id` to the verified body — e.g., include them in `to_signable_string`, or independently re-verify that the shop named in the header matches a shop the app is currently installed on/expects for that specific webhook subscription before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the target app (using this gem) on attacker-controlled shop `attacker.myshopify.com` and subscribe to a webhook topic (e.g., `app/uninstalled`) whose payload body does not depend on shop-specific content that would give away the mismatch.
2. Trigger the event so Shopify sends a legitimately HMAC-signed webhook request to the app's webhook endpoint, with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid signature over raw body>`
3. Capture the raw body and signature, then re-send the identical body/signature to the same endpoint but replace the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Utils::HmacValidator.validate` (called from `ShopifyAPI::Webhooks::Registry.process`) succeeds because `to_signable_string` returns only the untouched raw body — the modified `shop-domain` header is never checked.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the registered handler, which now believes it received a genuine webhook from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
