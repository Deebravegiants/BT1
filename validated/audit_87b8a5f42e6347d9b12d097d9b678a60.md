### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then dispatches to the app's handler using the `shop` value taken from an unauthenticated HTTP header. Because the tenant identifier (`shop`) is not part of the signed material, any unprivileged actor who can obtain one valid `(body, HMAC)` pair signed with the app's `client_secret` (trivially done by installing the app on their own store and capturing a real webhook delivery) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim shop's domain in the `shopify-shop-domain` / `x-shopify-shop-domain` header. The library will accept the forged request as authentic and dispatch it to the host application's handler tagged with the attacker-chosen victim shop, breaking the shop-to-payload identity binding.

### Finding Description
`Registry.process` verifies authenticity with: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` returns only the raw HTTP body — none of the Shopify-supplied headers (topic, shop-domain, webhook-id, api-version) are included in the signed content: [3](#0-2) 

Yet `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from those unauthenticated headers: [4](#0-3) 

and are passed directly into the metadata dispatched to the host application's handler without any additional binding check against the body or a known shop/session record: [5](#0-4) [6](#0-5) 

This is the exact bug class in the analog rule: "a field acted on but not covered by the HMAC" — here, `shop` is the field acted on (used to build `WebhookMetadata.shop`, which host apps use to attribute the payload to a tenant/session), while the HMAC covers only `@raw_body`. The equality that should hold is `shop-in-verified-material == shop-acted-on`, but instead `shop-acted-on` comes from a completely separate, unauthenticated channel (an HTTP header) than the one the HMAC verifies (the body).

### Impact Explanation
Because the app's `client_secret` is shared across every shop that installs the app, any unprivileged internet user can become a legitimate tenant by installing the app for free on their own development/test store, thereby obtaining real `(raw_body, HMAC)` pairs signed by the app's secret. They can then send a forged POST to the app's public webhook endpoint with the same body/HMAC but an arbitrary `shopify-shop-domain` header set to a victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) and invoke the host app's `WebhookHandler#handle` with `shop` equal to the attacker-chosen victim domain. If the host application (as documented/intended by this gem, e.g. `docs/usage/webhooks.md`) uses `data.shop` to select which merchant's records to update, this results in cross-tenant data corruption/injection — an app processing, say, an `orders/create` or `customers/update` webhook believing it originated from the victim shop when it did not. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for an attacker who is willing to install the target app on their own shop (a normal, unprivileged, self-service action requiring no special access, credentials, or social engineering) and then replay a single captured webhook request with a modified header to the app's public endpoint. No `api_secret_key`, access token, or privileged account is required — only the ability to (a) install the app as any regular merchant and (b) send arbitrary HTTP requests to the app's public webhook URL.

### Recommendation
Bind the tenant identity to the authenticated payload instead of trusting an unauthenticated header:
- Include the `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the body) so a captured `(body, HMAC)` pair cannot be replayed under a different shop's identity, or
- Have `Registry.process` cross-check the header-provided `shop` against an application-level, already-authenticated session/webhook record before dispatching to `WebhookHandler#handle`, and reject requests where no such binding exists.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering the app to receive a legitimate webhook, e.g. `orders/create`, with body `B` and a valid header `x-shopify-hmac-sha256: H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the captured request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` — it matches because the signature never depended on the shop header (`lib/shopify_api/webhooks/request.rb` line 36-38, `lib/shopify_api/utils/hmac_validator.rb` line 27-31).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host application to process attacker-controlled data as though it came from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
