### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by the application to route and attribute the webhook are pulled straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts these header-derived values to build `WebhookMetadata`, breaking the intended binding between "HMAC validated" and "shop identity trusted."

### Finding Description
`to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), which are not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The `HmacValidator` itself only computes a keyed signature over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) using the app's shared `api_secret_key`: [4](#0-3) 

The broken identity binding, expressed as an equality that the code assumes but does not enforce:
`HMAC-valid(body) == shop-header-is-authentic`

Because the app's `client_secret`/`api_secret_key` is shared across every merchant that installs the app (it is not per-install), any merchant who has installed the app can trigger events in their own store to obtain a body/HMAC pair that is genuinely valid for the app's secret (e.g., by creating an order or updating a product with attacker-chosen field values). They can then replay that exact signed body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-chosen) body belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery. A malicious but otherwise legitimate installer of the app can inject arbitrary attacker-controlled webhook payloads that are processed by the host application as if they originated from a different, victim tenant (shop). Any host application logic that uses `WebhookMetadata#shop` to look up/scope storage, session, or business data for a shop (which is the documented usage pattern of this library) can be poisoned with attacker data attributed to another merchant — this is a cross-tenant access/data-injection vector, one of the Critical impact categories in scope.

### Likelihood Explanation
Any merchant that has installed the app already possesses the ability to generate an event in their own shop, and can capture the raw request the app's webhook endpoint would receive (or simply craft a body themselves as long as it produces a body-only HMAC using the shared secret — note the attacker cannot forge new secret-authenticated bodies for arbitrary content unless it comes from a real Shopify-triggered delivery for their own shop, but they fully control the header fields on replay). This requires no privileged credentials or knowledge of `api_secret_key`, only that the attacker is a merchant/tenant of the app — an "unprivileged internet user" relative to other tenants.

### Recommendation
Include the tenant-identifying headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them downstream (e.g., verify shop domain against Shopify's servers, or require mutual TLS / IP allowlisting from Shopify's known webhook infrastructure in addition to HMAC). At minimum, document that `request.shop` is not authenticated by the HMAC and must be re-verified by the host app against the session/shop actually associated with the webhook subscription (e.g., cross-checking against a stored per-shop webhook secret or registered webhook id owner) before using it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g., updates a product with a malicious title/description) causing Shopify to send a legitimately signed webhook to the app, e.g.:
```
POST /webhooks
X-Shopify-Topic: products/update
X-Shopify-Hmac-Sha256: <valid-signature-over-body>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
Body: {"title": "<malicious-payload>"}
```
3. Attacker replays this exact request to the app's webhook endpoint, changing only:
```
X-Shopify-Shop-Domain: victim-shop.myshopify.com
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) raw body only — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", body: {"title": "<malicious-payload>"}, ...)`, causing the host app to process attacker-controlled data as belonging to `victim-shop.myshopify.com`.
