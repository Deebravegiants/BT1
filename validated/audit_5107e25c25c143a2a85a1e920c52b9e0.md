## Custody Invariant Reduction

The Solidity bug reduces to one custody invariant: **when a contract must push funds to N recipients in a single atomic loop, one malicious/uncooperative recipient must not be able to cause the whole distribution to fail and permanently deny funds to all other honest recipients.**

## Candidate Paths Considered

1. `aptos_account::batch_transfer` / `batch_transfer_coins` / `batch_transfer_fungible_assets` — caller-initiated batches, caller can just retry excluding the bad recipient; not custody-locked value, discarded.
2. `dispatchable_fungible_asset` withdraw/deposit hooks — a malicious FA issuer can revert its own hook, but this only affects that FA's transfers, not a shared multi-party pool; weaker "custody-grade" story, discarded in favor of the pool case.
3. `staking_contract::distribute_internal` — loops shareholders and calls `aptos_account::deposit_coins`; same root cause as (4) below but distribution pool membership for staking contracts is narrower (staker/operator/beneficiary).
4. `vesting::distribute` — loops an arbitrary, admin-configured set of `shareholders` (up to `MAXIMUM_SHAREHOLDERS`) and pushes `Coin<AptosCoin>` to each via `aptos_account::deposit_coins`. **Kept as strongest candidate** — matches the external bug's "push to N parties in one atomic call" pattern exactly, with a real framework-level abort condition on a per-recipient opt-out flag.

### Title
Malicious vesting shareholder can permanently block `vesting::distribute()` for all co-shareholders via `DirectTransferConfig` opt-out - (File: aptos-move/framework/aptos-framework/sources/vesting.move)

### Summary
`vesting::distribute()` pushes withdrawn stake rewards to every shareholder in the vesting contract's `grant_pool` in a single loop, using `aptos_account::deposit_coins`. That function aborts the entire transaction if a recipient has (a) not registered a `CoinStore<AptosCoin>` and (b) has explicitly disabled `allow_arbitrary_coin_transfers` via `set_allow_direct_coin_transfers(false)`. Any single shareholder can trigger this condition, permanently blocking reward distribution to every other shareholder of that vesting contract.

### Finding Description
`vesting::distribute()` iterates `grant_pool.shareholders()` and, for each one, extracts their share and calls `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` is the push-strategy sink used here: [2](#0-1) 

The abort condition is `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, gated by `can_receive_direct_coin_transfers`, which is `false` only when the account has explicitly called `set_allow_direct_coin_transfers(account, false)`: [3](#0-2) 

Crucially, account creation only registers the APT *primary fungible store*, not the legacy `CoinStore<AptosCoin>`: [4](#0-3) 

This means `coin::is_account_registered<AptosCoin>(to)` is false by default for ordinary accounts (they only have a primary fungible store, not a legacy `CoinStore`), so the `can_receive_direct_coin_transfers` check is live for virtually every recipient unless they've previously received/registered legacy `Coin<AptosCoin>`. A shareholder who calls `set_allow_direct_coin_transfers(false)` (a normal, permissionless, unprivileged self-call) and never registers a `CoinStore<AptosCoin>` will cause `deposit_coins` to abort every single time `distribute()` reaches their turn in the loop — reverting the entire transaction, including the `withdraw_stake` that already pulled funds out of the underlying stake pool for this distribution round.

Because the loop is all-or-nothing and there is no pull-based/per-shareholder claim function, no admin override to skip a malicious/uncooperative shareholder, and `distribute()` will be retried with the exact same shareholder set and exact same failure every time, this permanently blocks distribution of vested/unlocked rewards to **all** shareholders of that vesting contract (not just the attacker), for as long as the attacker maintains this opt-out state.

`staking_contract::distribute_internal` has the identical root cause (same `aptos_account::deposit_coins` sink, same loop-until-abort pattern) for its distribution pool of staker/operator/beneficiary: [5](#0-4) 

### Impact Explanation
This breaks the same invariant flagged in the external report: **all participants sharing a distribution must receive their funds; one participant must not be able to indefinitely deny funds to the rest.** Here:
- All co-shareholders' vested/unlocked APT rewards become permanently non-distributable through `distribute()`/`distribute_many()` as long as the malicious shareholder is a member of the `grant_pool` and keeps `allow_arbitrary_coin_transfers = false` while unregistered for `CoinStore<AptosCoin>`.
- `terminate_vesting_contract()` also calls `distribute()` first, so termination and final withdrawal (`admin_withdraw`) can be blocked too, since `distribute` is called unconditionally before termination proceeds: [6](#0-5) 
- This is custody-grade: it is a permanent, non-recoverable lock of already-unlocked APT value shared among multiple honest shareholders, caused by a single unprivileged, malicious actor.

### Likelihood Explanation
Likelihood is high for any vesting/staking-contract with more than one shareholder and an adversarial or simply uncooperative participant: `set_allow_direct_coin_transfers(false)` is a normal, permissionless entry function, and not registering a legacy `CoinStore<AptosCoin>` is the default state for modern accounts (APT now flows through primary fungible stores). No special privilege or race condition is required — a shareholder can set this up before or any time after being added to the vesting contract, and grief every subsequent distribution.

### Recommendation
Replace the push-loop with a pull-based claim pattern: instead of `distribute()` iterating and depositing to every shareholder atomically, credit each shareholder's redeemable share to an on-chain accounting structure and let each shareholder (or beneficiary) call a separate `claim()` entry function to withdraw their own share. Alternatively, wrap each per-recipient deposit in the loop with `deposit_coins`'s failure isolated (e.g., via a fallback that force-registers/holds undeliverable funds in an escrow keyed by recipient) so a single recipient's opt-out cannot abort the whole distribution.

### Proof of Concept
1. Admin creates a `vesting::VestingContract` with shareholders `[Alice, Bob]` via `create_vesting_contract`.
2. Bob calls `aptos_account::set_allow_direct_coin_transfers(bob_signer, false)` and never registers `CoinStore<AptosCoin>` (default state for a fresh account).
3. Time passes; `vest()` unlocks rewards; stake lockup expires so funds become withdrawable.
4. Anyone calls `vesting::distribute(contract_address)`.
5. `distribute` withdraws the pool's coins via `withdraw_stake`, then loops shareholders: Alice's `deposit_coins` succeeds (or fails depending on order), but when Bob's turn comes, `aptos_account::deposit_coins` hits `!coin::is_account_registered<AptosCoin>(bob)` and `!can_receive_direct_coin_transfers(bob)`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire transaction reverts, including the stake withdrawal — Alice receives nothing, and every future call to `distribute()`/`distribute_many()` on this contract fails identically, permanently blocking distribution to Alice (and any other shareholders) as long as Bob keeps this state.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
    }
