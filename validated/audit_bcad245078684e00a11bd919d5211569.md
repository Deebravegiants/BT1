### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body when computing the value that `Utils::HmacValidator.validate` checks against the `X-Shopify-Hmac-Sha256` header. None of the other headers — most importantly `shop` (the `x-shopify-shop-domain` / `shopify-shop-domain` header) — are included in the signed material, yet `request.shop` is the value trusted as the tenant identity when the webhook is dispatched to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. `HmacValidator.validate` computes the signature purely from this signable string: [2](#0-1) 
Meanwhile, `Registry.process` uses `request.shop` — read straight from an attacker-controllable header — as the tenant identity handed to the app's webhook handler, with no cross-check that this shop actually corresponds to the HMAC that was validated: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || ...)` so that the `shop` value delivered to the handler is provably the one the request originated for. Instead the binding actually enforced is only `hmac == HMAC(secret, body)`, with `shop` parsed from an unauthenticated header and never bound into the signed bytes. This is exactly the "bytes verified versus bytes parsed" mismatch: the bytes cryptographically verified (`raw_body`) are not the bytes acted upon for tenant identification (`shop` header).

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any merchant who has legitimately installed the app receives real webhooks with valid HMACs computed over a body that says nothing about which shop it's for. Such a merchant (an "unprivileged" actor with respect to other tenants of the same app) can capture one of their own legitimate webhook deliveries (valid body + valid hmac) and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because the shop header was never part of what it checks, and `Registry.process` will dispatch the payload to the app's handler tagged with the victim's `shop`, crossing the tenant boundary.

### Impact Explanation
This meets the Critical bar of cross-tenant access: an app built on top of `ShopifyAPI::Webhooks::Registry.process` cannot distinguish "this body was signed by our secret" from "this body was signed by our secret for shop X." A malicious but legitimately-onboarded merchant can inject arbitrary attacker-chosen webhook bodies (subject to whatever body they already received, or any topic/body combination if they can get the app to send them any webhook once) into another tenant's data stream, e.g. forging `orders/create`, `customers/data_request`, or app-uninstall/GDPR webhooks attributed to a victim shop, corrupting per-tenant state that the host app keys off `WebhookMetadata#shop`.

### Likelihood Explanation
Requires only that the attacker be a legitimate merchant with the app installed on their own store (no special privilege, no access to `api_secret_key`) — they can passively receive one legitimate signed webhook and replay it with a modified header value over the public internet to the app's public webhook endpoint. No credential theft, TLS interception, or code execution is needed.

### Recommendation
Bind the `shop` domain (and ideally `topic`/`webhook_id`) into the HMAC-covered signable string, or otherwise cryptographically authenticate the shop association (e.g., only trust `request.shop` after confirming the webhook body content is intrinsically about that shop, or require callers to compare `request.shop` against the shop tied to the API credentials used to compute the HMAC). At minimum, update `to_signable_string` to be `"#{shop}\n#{topic}\n#{raw_body}"`-style so replays across shops fail validation.

### Proof of Concept
1. App has one client secret shared by shop `attacker.myshopify.com` and shop `victim.myshopify.com`.
2. Attacker (merchant on `attacker.myshopify.com`) receives a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, valid `x-shopify-hmac-sha256` for `B`.
3. Attacker resends the same body `B` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Request.new` builds successfully (all headers present); `HmacValidator.validate(request)` in `Registry.process` passes because `to_signable_string` only checks `B`. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes body `B` as if it were sent by the victim shop.
