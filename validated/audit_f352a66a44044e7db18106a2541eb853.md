### Title
Swap "hinkalFee" is deducted from the user's output but permanently stuck in `ExternalActionSwap` when no relay is used - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`ExternalActionSwap.swap()` computes a variable-rate protocol/"hinkal" fee on every swap and subtracts it from the amount ultimately forwarded to the user, but the actual on-chain transfer of that fee only happens through `sendToRelay`, which is a silent no-op whenever `circomData.relay == address(0)`. Since `relay` is an optional, user-supplied field elsewhere in the protocol (self-relayed transactions are explicitly supported in `Hinkal._internalTransact`), any swap executed without a relay address permanently locks the "hinkalFee" portion inside the `ExternalActionSwap` contract with no code path to retrieve it. This is the same bug class as the reported `ClaggBaseAdapter._handleFee()` issue: a fee is subtracted from the equality the user/protocol expects to hold, but never actually routed to any recipient, remaining stuck in the contract forever.

### Finding Description
In `swap()`:
```solidity
uint256 relayFee = circomData.feeStructure.flatFee;
uint256 hinkalFee = hinkalHelper.calculateRelayFee(
    swappedAmount,
    0,
    circomData.feeStructure.variableRate
);

if (circomData.feeStructure.feeToken == outputToken) {
    sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
} else {
    sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken);
    sendToRelay(circomData.relay, hinkalFee, outputToken);
}

uint256 totalFee = hinkalFee +
    (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
uint256 amountToSendToHinkal = swappedAmount - totalFee;
``` [1](#0-0) 

`totalFee` (including `hinkalFee`) is always deducted from `amountToSendToHinkal`, which is what gets sent back to Hinkal/the user's shielded balance. The only attempted payout of that fee is via `sendToRelay`:
```solidity
function sendToRelay(
    address relay,
    uint256 actualAmount,
    address erc20TokenAddress
) internal {
    if (relay != address(0) && actualAmount > 0) {
        transferERC20TokenOrETH(erc20TokenAddress, relay, uint256(actualAmount));
    }
}
``` [2](#0-1) 

`sendToRelay` is a deliberate no-op when `relay == address(0)`. Elsewhere in the protocol, `relay == address(0)` is an explicitly supported "no relay" path — e.g. `Hinkal._internalTransact` only requires payment to a relay `if (circomData.relay != address(0))`, and enforces `circomData.relay == address(0) || hasPaidToRelay` [3](#0-2) , confirming self-submitted/relay-less transactions are a normal, expected mode of operation.

For an external-action swap, nothing in `ExternalActionSwap.swap()` requires `circomData.relay != address(0)`. Consequently, when a user (or a self-relaying caller) sets `circomData.relay = address(0)`:
- `hinkalFee` (the protocol's variable-rate cut) is still computed and subtracted from `amountToSendToHinkal`.
- `sendToRelay(address(0), hinkalFee, outputToken)` silently does nothing — the tokens are never moved anywhere.
- The tokens remain in the `ExternalActionSwap` contract's balance indefinitely, since there is no other function in this contract (no rescue/treasury sweep) to retrieve them.

This breaks the value-conservation expectation for the balance equation enforced upstream: the amount `Hinkal.sol` records via `utxoAmount`/`amountChanges` for the user is `swappedAmount - totalFee`, so the "missing" `totalFee` value is implicitly promised to be collected as a protocol/relay fee, yet no destination address ever actually receives it — it is silently absorbed by the adapter contract with no owner-level recovery path in scope.

### Impact Explanation
This causes permanent freezing of protocol fees (the "hinkalFee") for every relay-less swap executed through `ExternalActionSwap`. Per the rules, permanent freezing of protocol/relay fees is a **High** impact finding. The loss compounds with usage volume: every self-relayed swap silently donates its variable-rate fee to a contract that has no mechanism (within the audited scope) to release it.

### Likelihood Explanation
Likelihood is high because `relay == address(0)` is not a rare edge case — it is the documented, supported "no relay used" configuration elsewhere in the protocol (`Hinkal._internalTransact`), and nothing in `ExternalActionSwap` prevents or discourages users/integrators from using this same configuration for swaps. Any ordinary user submitting their own proof without going through a third-party relay would trigger this loss on every swap.

### Recommendation
In `ExternalActionSwap.swap()`, do not route the protocol's `hinkalFee` exclusively through `sendToRelay(circomData.relay, ...)`. Either:
1. Require `circomData.relay != address(0)` before attempting to collect `hinkalFee` in this path, or
2. Introduce a dedicated protocol fee recipient (treasury) address that `hinkalFee` is always transferred to via `transferERC20TokenOrETH`, independent of whether a relay is used, so the fee is never silently retained by the adapter contract.

### Proof of Concept
1. User builds a valid swap transaction through `ExternalActionSwap.runAction` with `circomData.relay = address(0)` (a valid, protocol-supported configuration for self-relayed transactions).
2. `swap()` executes the router call and computes `hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, feeStructure.variableRate)` [4](#0-3) .
3. `sendToRelay(address(0), hinkalFee, outputToken)` is called and returns immediately without transferring any tokens, because `relay != address(0)` fails [2](#0-1) .
4. `amountToSendToHinkal = swappedAmount - totalFee` is transferred to `msg.sender` (Hinkal contract), which is `swappedAmount` minus the never-paid `hinkalFee`.
5. The `hinkalFee` amount of `outputToken` remains permanently in `ExternalActionSwap`'s token balance; repeating the swap accumulates further stuck fees with no function in scope able to retrieve them.
