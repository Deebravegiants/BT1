Audit Report

## Title
Silent loss of HRMP channel notifications when destination para's DMQ is full - (File: polkadot/runtime/parachains/src/hrmp.rs)

## Summary
`Pallet::<T>::send_to_para` at [1](#0-0)  only inspects `dmp::QueueDownwardMessageError::ExceedsMaxMessageSize` from `dmp::Pallet::<T>::queue_downward_message`, leaving `ExceedsMaxQueueSize` (and `Unroutable`) completely unhandled — no log, no assert, no error propagation. Since the function returns `()` and is called after HRMP channel storage (`HrmpChannels`, `HrmpIngressChannelsIndex`, open-channel requests, etc.) has already been mutated, a full destination DMQ causes the relay-chain-side channel state transition to be committed while the corresponding DMP notification to the parachain is silently dropped.

## Finding Description
The code exactly matches the claim: the `if let Err(dmp::QueueDownwardMessageError::ExceedsMaxMessageSize) = ...` pattern in `send_to_para` [2](#0-1)  only matches one of three `QueueDownwardMessageError` variants defined in `dmp.rs`: `ExceedsMaxMessageSize`, `ExceedsMaxQueueSize`, and `Unroutable` [3](#0-2) . The module-level doc comment confirms `ExceedsMaxQueueSize` is a real, reachable outcome when a para's DMQ hits its hard `max_messages` cap, derived from `MAX_POSSIBLE_ALLOCATION / max_downward_message_size` [4](#0-3) . Since `send_to_para` returns `()`, callers such as the channel open/accept/close logic have no way to detect or react to a dropped notification, and the preceding storage writes to the HRMP channel state are not rolled back.

This is a genuine gap in the error-handling logic, not a misreading of the code — the fallthrough for `ExceedsMaxQueueSize` is silent by construction.

## Impact Explanation
The concrete impact is a notification-only desync: the destination parachain may not learn (via DMP) that a channel was opened, accepted, or closed, while the relay-chain-side storage already reflects the change. This does not cause direct loss of funds and does not corrupt consensus-critical state — HRMP channel status remains correctly recorded on the relay chain and is queryable through normal parachain-inherent/runtime-API paths independent of the dropped DMP message, so the failure mode is degraded XCM/collator awareness rather than an accounting or safety violation. The `DeliveryFeeFactor` mechanism in `dmp.rs` is specifically designed to make sustained DMQ growth exponentially expensive as a defense against exactly this kind of queue-exhaustion scenario [5](#0-4) , which meaningfully limits the practical impact.

## Likelihood Explanation
Filling a target para's DMQ up to its hard `max_messages` bound requires sending enough downward messages to overcome the exponentially increasing `DeliveryFeeFactor`, making this economically expensive and increasingly so the closer the queue gets to the cap. The attack window (multiple blocks before a session-boundary channel commit) increases feasibility somewhat, but the cost scaling specifically targets this abuse vector, making the attack impractical for anything but extremely well-funded, sustained flooding against a specific low-`max_downward_message_size` target, and the payoff (a dropped informational notification, recoverable via on-chain state queries) is disproportionately low relative to the cost.

## Recommendation
Handle `ExceedsMaxQueueSize` and `Unroutable` explicitly in `send_to_para` (e.g., with logging and metrics) even though channel storage should still commit, so operators have observability into dropped notifications. Consider exposing HRMP channel status via a mechanism parachains can poll independently of DMP delivery, if not already relied upon, to reduce dependence on notification delivery for consistency.

## Proof of Concept
Unit test plan in `polkadot/runtime/parachains/src/hrmp/tests.rs`: configure a mock `HostConfiguration` with a small `max_downward_message_size` for para B, flood B's DMQ via repeated `dmp::Pallet::<Test>::queue_downward_message` calls until it reaches `max_messages`, then trigger a channel action (e.g. `accept_open_channel`) that calls `send_to_para` targeting B, and assert that `queue_downward_message` returns `ExceedsMaxQueueSize` with no corresponding log/error emitted, while `HrmpChannels` storage still reflects the committed channel state.

//! To prevent Out of Memory errors on the `DownwardMessageQueue`, an
//! exponential fee factor (`DeliveryFeeFactor`) is set. The fee factor
//! increments exponentially after the number of messages in the
//! `DownwardMessageQueue` passes a threshold. This threshold is set as:
//!
//! ```ignore
//! // Maximum max sized messages that can be send to
//! // the DownwardMessageQueue before it runs out of memory
//! max_messages = MAX_POSSIBLE_ALLOCATION / max_downward_message_size
//! threshold = max_messages / THRESHOLD_FACTOR
//! ```
//! Based on the THRESHOLD_FACTOR, the threshold is set as a fraction of the
//! total messages. The `DeliveryFeeFactor` increases for a message over the
//! threshold by:
//!
//! `DeliveryFeeFactor = DeliveryFeeFactor *
//! (EXPONENTIAL_FEE_BASE + MESSAGE_SIZE_FEE_BASE * encoded_message_size_in_KB)`
//!
//! And decreases when the number of messages in the `DownwardMessageQueue` fall
//! below the threshold by:
//!
//! `DeliveryFeeFactor = DeliveryFeeFactor / EXPONENTIAL_FEE_BASE`
//!
//! As an extra defensive measure, a `max_messages` hard
//! limit is set to the number of messages in the DownwardMessageQueue. Messages
