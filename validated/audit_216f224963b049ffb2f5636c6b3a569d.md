### Title
Unrestricted `CallDispatcher.dispatch()` allows direct theft of funds held by the shared intents dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated "arbitrary call" primitive — the on-chain analog of Ghostscript's `superexec` operator sitting in the interpreter's internal dictionary, reachable by any unprivileged caller despite the sandboxing (`-dSAFER`) the rest of the system relies on. `IntentGatewayV2`/`IntentsBase` treat this contract as an internal-only helper that transiently custodies tokens/ETH during order predispatch and output execution, but nothing in `CallDispatcher` itself restricts who may invoke `dispatch()`, and the reentrancy guard applied to `IntentGatewayV2` does not extend to this separate contract.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded) external` decodes an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry, with no `onlyGateway`/`onlyOwner`/caller check of any kind: [1](#0-0) 

Its own interface documents it as dispatching *untrusted* calls, implying the contract itself is meant to be the trust boundary, not an authenticated component: [2](#0-1) 

`IntentsBase._execute()` and the predispatch flow in `IntentGatewayV2.sol` route ordinary intent funds through this same shared `CallDispatcher` instance (`_params.dispatcher`): tokens are transferred into the dispatcher, an order-supplied call is executed there, and only afterward are the dispatcher's *current* balances swept back to the gateway: [3](#0-2) [4](#0-3) 

Because the sweep-back step reads `dispatcher.balance` / `IERC20(token).balanceOf(dispatcher)` at sweep time rather than tracking exactly what this order deposited, any balance sitting in `CallDispatcher` — whether from the current order's in-flight funds, dust from a prior order, or ETH sent via its `receive()` — is up for grabs to whoever calls `dispatch()` first.

`IntentGatewayV2` wraps its own entry points in `ReentrancyGuardTransient`, but that guard only protects `IntentGatewayV2`'s own functions, not `CallDispatcher`, which has no guard of its own: [5](#0-4) 

Since `order.output.call` / `order.predispatch.call` (attacker/order-controlled calldata) is executed by `CallDispatcher` while it is holding the order's funds, a call target invoked from within that calldata can reenter `CallDispatcher.dispatch()` directly — bypassing `IntentGatewayV2`'s reentrancy guard entirely — and drain whatever balance the dispatcher currently holds to an address of the attacker's choosing, before the legitimate gateway sweep executes.

### Impact Explanation
This is a concrete theft-of-funds primitive: an intent solver or order creator can craft calldata that, when executed by the shared `CallDispatcher`, calls back into `CallDispatcher.dispatch()` to redirect escrowed/predispatch tokens (or ETH/ERC20 dust left over from unrelated orders) away from the intended recipient. Because `CallDispatcher` is a single shared instance referenced by `_params.dispatcher` across all orders, funds belonging to any order being processed at the time — not just the attacker's own — are exposed while they transiently sit in this contract.

### Likelihood Explanation
Medium-High: exploitation requires only placing/filling an order whose `predispatch.call` or `output.call` targets an attacker-controlled contract, something any unprivileged user or solver can already do as part of normal composable order fulfillment. No special privileges, governance access, or consensus manipulation is needed — only a single crafted transaction through the existing intents flow.

### Recommendation
Add caller authentication to `CallDispatcher.dispatch()` (e.g., an immutable `authorized` gateway address set in the constructor, or a per-deployment allowlist), and/or add a reentrancy guard to `CallDispatcher` itself so it cannot be re-entered while a sweep is pending. Additionally, make the sweep step in `IntentsBase._execute()` / predispatch handling account for exactly the amount deposited for the current order rather than sweeping the dispatcher's entire current balance, so residual/in-flight funds from other operations cannot be captured.

### Proof of Concept
1. Attacker places (or fills) an order whose `output.call` / `predispatch.call` targets `AttackerContract`.
2. `IntentsBase._execute()` transfers the order's tokens/ETH into the shared `CallDispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`.
3. `CallDispatcher.dispatch()` executes the call to `AttackerContract`, which, from inside that call, invokes `CallDispatcher.dispatch()` again directly (not through `IntentGatewayV2`, so `ReentrancyGuardTransient` does not trigger) with a `Call[]` that transfers the dispatcher's *entire current* token/ETH balance to the attacker's address.
4. Control returns to `IntentsBase._execute()`, which reads `dispatcher.balance` / `balanceOf(dispatcher)` — now zero or reduced — and sweeps only what remains, resulting in a loss of the order's/other users' funds to the attacker.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
