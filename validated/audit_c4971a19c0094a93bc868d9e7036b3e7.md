### Title
Webhook shop/topic identity spoofing via unauthenticated headers — HMAC only covers raw body, not `shop-domain`/`topic` — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed on to the registered handler as trusted values. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches the app's shared secret, then unconditionally trusts the header-derived `shop` and `topic` fields. Since the signing secret is shared across every shop that has installed the app, any shop can capture one legitimate `(raw_body, hmac)` pair from its own genuine webhook deliveries and replay it while forging the `shop-domain`/`topic` headers to impersonate another tenant.

### Finding Description
The intended binding is:
```
shop_header == shop_of_the_tenant_that_the_signed_body_belongs_to
```
but the code only checks:
```
hmac_header == HMAC(api_secret_key, raw_body)
```

`Request#hmac` and `Request#to_signable_string` show that only `@raw_body` participates in the signature: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic relationship to the signature: [2](#0-1) 

`HmacValidator.validate` (and `validate_signature`) only ever hash `verifiable_query.to_signable_string`, i.e. the body — never the shop/topic headers: [3](#0-2) 

`Registry.process` raises only on HMAC failure, then immediately constructs `WebhookMetadata` from the unauthenticated `request.shop` / `request.topic` and dispatches to the handler as if these were verified: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is shared across all shops that installed the app (it is not per-shop), any merchant/tenant using the app can legitimately receive a real webhook (any topic) for their own shop, giving them a valid `(raw_body, hmac)` pair. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic` header) with a victim shop's domain / a different topic of their choosing. `Registry.process` will pass HMAC validation (body unchanged) and will invoke the handler believing the event originated from, and is scoped to, the victim shop.

### Impact Explanation
This breaks the shop-to-signature identity binding and enables cross-tenant impersonation: an unprivileged tenant of a multi-tenant app can cause the app to process an event attributed to another shop it does not control. Depending on how the host app's handlers use `data.shop` (which is the documented and expected trust boundary per `docs/usage/webhooks.md`), this can be leveraged to:
- Trigger mandatory GDPR/lifecycle webhooks (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`) against a victim shop, causing deletion of the victim's stored session/access token or customer data.
- Feed forged data into any handler keyed by `shop`, corrupting or leaking data associated with another tenant.

This satisfies the Critical bar of cross-tenant access, since it lets one tenant act on another tenant's identity purely through the gem's own trust logic, requiring no possession of the victim's or the app's credentials.

### Likelihood Explanation
Any single legitimate installer of a multi-tenant app already possesses everything needed: a genuine `(raw_body, hmac)` pair from their own webhook deliveries (which they can capture by simply operating their own store and observing/logging inbound webhook requests before their app processes them, or from their own test/dev shop). No `api_secret_key`, no access token, and no TLS interception is required — only a standard, unprivileged internet-facing HTTP request to the app's webhook endpoint with modified headers. This is straightforward to exploit for anyone who can install the target app on their own shop.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity into the verified signature material, or otherwise independently verify the `shop-domain` header against the shop the app expects to be receiving the webhook for (e.g. cross-check against an active installation/session record) before trusting it in `WebhookMetadata`. At minimum, document that `request.shop`/`request.topic` are NOT cryptographically authenticated by `HmacValidator.validate` and that host applications must independently verify shop identity (e.g. against their own installed-shops table) before acting on webhook data.

### Proof of Concept
1. App `X` is installed on attacker's own shop `attacker.myshopify.com` and on victim's shop `victim.myshopify.com`.
2. Attacker's shop receives a legitimate webhook delivery, e.g. topic `app/uninstalled`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`. Attacker records `(B, H)`.
3. Attacker sends a POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since only body is signed)
   - header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - header `X-Shopify-Topic: app/uninstalled` (forged/unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `B`.
5. `Registry.process` dispatches `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` to the app's handler, which now processes an uninstall/redact event as if it came from the victim shop, even though the victim never sent this webhook.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
