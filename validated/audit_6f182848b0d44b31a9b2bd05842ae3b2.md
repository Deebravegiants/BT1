### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from an HTTP header, while the HMAC signature validated by `HmacValidator` only covers the raw request body. This breaks the identity binding `shop == HMAC-authenticated shop`, allowing anyone in possession of one valid `(raw_body, hmac)` pair for the app's shared secret (e.g., a merchant running their own store that has this app installed and receiving genuine webhooks) to relabel that payload as belonging to a different, arbitrary shop and have it processed by the app's webhook handler as if it came from that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field with a constant-time comparison: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns **only the raw body**:
```ruby
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

But `shop` (as well as `topic`, `webhook_id`, `api_version`) is read straight from an HTTP header that is never mixed into the signed content:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

This `shop` value is then handed, unauthenticated, to the app's webhook handler as the tenant identity for the event:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, used in the OAuth callback, where `shop` **is** part of the signed string (`to_signable_string` includes `shop`) [6](#0-5) , showing this is a deliberate design elsewhere in the same gem, just missing for webhooks.

**Broken binding (equality that should hold but doesn't):**
`shop_used_by_handler == shop_authenticated_by_hmac`

Before attack: legitimate webhook for `attacker-shop.myshopify.com` arrives with `raw_body B`, header `shop-domain: attacker-shop.myshopify.com`, and `hmac = HMAC(secret, B)`. Both sides agree.

After attack: attacker resubmits the same `(B, hmac)` pair to the app's webhook endpoint but with header `shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds because the signed content (`B`) is unchanged; `Request#shop` now returns `victim-shop.myshopify.com`. The gem passes `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` [5](#0-4)  to the app handler, which will typically look up/act on the victim's tenant record using data that never originated from the victim's shop.

Any actor who can obtain one valid `(body, hmac)` pair for the app's `client_secret` — e.g., a customer of the app running their own store and simply capturing/replaying their own genuine webhook deliveries — can forge webhooks that HMAC-validate as coming from a different, arbitrary shop domain, because the shop identity is never part of what the app's HMAC actually authenticates.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the library's own HMAC-validation API tells the app "this webhook is authentic," while the tenant-identifying `shop` field it hands back is fully attacker-controlled. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., to select which merchant's record to update/delete, revoke access, mark subscription state, etc.), this enables cross-tenant data corruption/access using another shop's identity, satisfying the "cross-tenant access" criterion. It does not require the attacker to know the `client_secret` or possess anyone else's access token — only a legitimately delivered webhook of their own.

### Likelihood Explanation
Moderate-to-high: any developer/merchant who has installed the app on any shop can trivially capture a valid `(raw_body, hmac)` pair from their own legitimately received webhook (webhooks are delivered to the app's public callback URL, so no privileged access is needed to observe the values sent to their own endpoint), then replay it with a modified `shop-domain` header. The `topic`, `webhook_id`, and `api_version` headers are equally unauthenticated, increasing the range of forgeable metadata (e.g. spoofing `topic` to route a body to the wrong handler).

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body before exposing `Request#shop`/`#topic` to consumers — mirroring how `AuthQuery#to_signable_string` binds `shop` into the OAuth HMAC. At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a shop already known to have registered that specific `webhook_id`).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers an event on their own store, causing Shopify to deliver a webhook to the app's callback with:
   - body `B`
   - headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(client_secret, B))`.
3. Attacker captures `(B, H)` from their own delivered request (they own this endpoint's traffic).
4. Attacker re-POSTs to the same app endpoint with identical body `B` and identical `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [7](#0-6) , which recomputes `HMAC(client_secret, B)` and matches `H` — validation succeeds because `shop` is not part of `to_signable_string` [3](#0-2) .
6. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the app to process attacker-controlled data under the victim shop's identity.
