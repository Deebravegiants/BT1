## Decimals Mismatch Between WrappedHyperFungibleToken's Underlying Token and HyperFungibleToken's Fixed 18-Decimal Representation Enables Escrow Drain - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol / HyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` (deployed on the token's home chain, e.g. locking USDC with 6 decimals) and `HyperFungibleToken` (deployed on remote chains, always inheriting the ERC20 default of **18 decimals**) exchange a single `uint256 amount` field with **no decimal scaling whatsoever**. Any unprivileged token bridger can exploit the resulting precision mismatch to unlock a vastly inflated amount of the underlying escrowed token, draining `WrappedHyperFungibleToken`'s reserves — the exact bug class described in the external DODO report (fee/amount fields with mismatched decimals leading to gross balance miscalculation and asset loss), but here applied to the core bridge accounting instead of a fee.

### Finding Description
The shared cross-chain message format is:
```solidity
struct Message {
    bytes from;
    bytes to;
    uint256 amount; // token amount
    bytes data;
}
``` [1](#0-0) 

`WrappedHyperFungibleToken.send()` locks `params.amount` raw units of the configured `_underlying` ERC20 (e.g. USDC, 6 decimals) and encodes that same raw number into `Message.amount` without any decimal conversion: [2](#0-1) [3](#0-2) 

On the remote chain, `HyperFungibleToken` is a plain OpenZeppelin `ERC20` that never overrides `decimals()`, so it always reports **18 decimals** — this is explicitly documented for the `BridgeToken` deployment ("`decimals()` is the inherited ERC20 default of 18 while BRIDGE is 12 decimals on nexus, so the pallet scales by 10^6 in both directions"): [4](#0-3) 

Critically, that scaling only exists for the **Substrate pallet ↔ EVM** path (`pallet-hyper-fungible-token`'s `Precisions` storage and `convert_to_erc20`/`convert_to_balance`): [5](#0-4) 

For the **EVM ↔ EVM** `WrappedHyperFungibleToken` ↔ `HyperFungibleToken` path, no equivalent precision configuration or scaling exists anywhere in `HyperFungibleToken.sol` or `WrappedHyperFungibleToken.sol`. `onAccept` on the remote `HyperFungibleToken` mints `message.amount` 1:1 as if it were already expressed in the local (18-decimal) unit: [6](#0-5) 

And when sending back, `HyperFungibleToken.send()` burns `params.amount` (in its own 18-decimal terms) and forwards that raw number to the home chain, where `WrappedHyperFungibleToken.onAccept()` unlocks that same raw number of units of the **6-decimal** underlying token: [7](#0-6) 

Because 1 USDC = `1e6` units but 1 "display unit" of the remote `HyperFungibleToken` = `1e18` units, locking 1 USDC (`1e6`) mints a negligible `1e6`-unit balance on the remote HFT (worth `0.000000000001` tokens by its own 18-decimal accounting). Conversely — and this is the exploitable direction — a user who acquires (via normal `send()`/`onAccept()` mint) any nonzero balance on the remote HFT and burns an amount expressed in 18-decimal terms (e.g. `1e18`, "1 token" per wallets/UIs) causes `WrappedHyperFungibleToken.onAccept()` to attempt to unlock `1e18` raw units of the 6-decimal underlying — twelve orders of magnitude more than was ever locked. Given enough aggregate USDC locked in the wrapper (from other users' legitimate `send()` calls), an attacker only needs to accumulate a comparatively tiny remote-chain HFT balance to unlock/drain the entire home-chain escrow.

### Impact Explanation
This directly matches "concrete theft ... of funds": the home chain's `WrappedHyperFungibleToken` escrow, funded by all users who bridged the underlying stablecoin/token out, can be drained by any holder of the remote-chain burn/mint `HyperFungibleToken` due to the 10^12 (18 vs 6 decimals) scaling error. This is reachable by a single unprivileged `send()` transaction/message delivery — no privileged role required.

### Likelihood Explanation
High. Any token pairing where the underlying ERC20 on the home chain has fewer than 18 decimals (USDC, USDT — both 6 decimals, exactly as flagged in the reference report, and the documented example deployment target) hits this by default, since `HyperFungibleToken` never customizes `decimals()` away from the ERC20 default of 18. No special conditions or governance error are needed; it is a structural property of the deployed contracts as documented in `docs/content/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token.mdx` (USDC given as the canonical underlying example).

### Recommendation
Add explicit per-chain decimals configuration (mirroring `pallet-hyper-fungible-token`'s `Precisions` storage and `convert_to_erc20`/`convert_to_balance` helpers) to `HyperFungibleToken`/`WrappedHyperFungibleToken`, scaling `Message.amount` by the ratio between the underlying token's `decimals()` and each peer chain's registered decimals before dispatch, and inversely on receipt, so amounts represent the same real-world value on both sides of the bridge.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on Ethereum with `underlying = USDC` (6 decimals).
2. Deploy `HyperFungibleToken` on Arbitrum (18-decimal ERC20 by default), register as peers.
3. Alice bridges 100 USDC: `WrappedHyperFungibleToken.send({amount: 100_000_000, ...})` locks `100_000_000` USDC units and dispatches `Message.amount = 100_000_000`.
4. On Arbitrum, `onAccept` mints Alice `100_000_000` wei of the 18-decimal HFT token (`0.0000000001` displayed tokens) — already a broken accounting, but not yet exploitable by itself.
5. Suppose over time `$1,000,000` of USDC accumulates in the Ethereum `WrappedHyperFungibleToken` escrow from many users' `send()` calls.
6. Any attacker who has accrued even a trivial mint balance (e.g., a few wei from step 4 across multiple small sends, or from being routed calldata) calls `HyperFungibleToken.send({amount: X, dest: Ethereum, ...})` on Arbitrum, burning `X` wei of the 18-decimal token.
7. On Ethereum, `WrappedHyperFungibleToken.onAccept()` executes `IERC20(_underlying).safeTransfer(beneficiary, X)`, attempting to unlock `X` raw units of 6-decimal USDC — for any `X ≥ 1e6` this unlocks USDC amounts up to `10^12` times larger than what was ever locked against that attacker's mint, up to the full escrow balance, at which point `safeTransfer` succeeds until the escrow is emptied, draining honest users' bridged funds.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
