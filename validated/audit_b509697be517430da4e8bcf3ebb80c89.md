### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body via `Utils::HmacValidator.validate(request)`. The `shop` (tenant) identifier that is handed to the app's handler and — per the gem's own documentation — used to route/attribute the webhook to a specific merchant, is read straight from the `X-Shopify-Shop-Domain` header, a field that is **not** included in the signable string used to compute/verify the HMAC. This mirrors the AngstromL2 bug class: a value that governs downstream, tenant-scoped state changes is not bound by the same authentication check that gates the operation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unauthenticated header: [2](#0-1) 

`Registry.process` verifies only the body HMAC, then forwards `request.shop` unchanged to the handler as trusted tenant context: [3](#0-2) 

The gem's documentation explicitly instructs developers to treat `data.shop` as the authoritative shop identity for the webhook and to key downstream work (e.g., background jobs) by it: [4](#0-3) 

The identity binding that should hold is:
`hmac_verified(body) == true` should imply `shop header == shop that produced body`.
In reality, the gem only verifies `hmac_verified(body)`; the `shop` header is fully decoupled from that check. Since the HMAC secret (`api_secret_key`) is shared across **all** shops that install a given app, any unprivileged user who installs the app on a shop they control can obtain a body+valid-HMAC pair (either by triggering a real webhook to their own endpoint, or, since HMAC is a keyed hash of the body only, by replaying any body they choose along with the resulting valid HMAC — no shop-specific secret is required). They can then POST that same `raw_body`/`X-Shopify-Hmac-Sha256` pair to the target app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain, causing the app to attribute/act on attacker-supplied webhook data under the victim tenant's identity.

### Impact Explanation
This breaks the tenant identity binding for the entire HTTP webhook processing path in the gem. Any downstream logic that keys off `data.shop` (looking up a `Session`, updating shop-scoped records, enqueueing jobs "for" that shop, as literally shown in the gem's own docs) can be made to act against a shop the attacker does not control, using attacker-chosen body contents. This is a cross-tenant access primitive achievable by any unprivileged internet user who can install the target app on any shop (including a free/dev store) — no `api_secret_key`, access token, or privileged account is required.

### Likelihood Explanation
High. Exploitation only requires: (1) installing the target Shopify app on an attacker-controlled shop (a normal, unprivileged capability), (2) capturing or generating a body+HMAC pair, and (3) issuing a plain HTTP POST to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No cryptographic secret needs to be recovered because the header used to select the tenant is simply outside the authenticated data.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the HMAC-covered signable string, or otherwise cryptographically bind the shop identity to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that consuming applications must independently verify `data.shop` corresponds to a shop with an active, expected app installation before using it to key any state-changing operation, and update `Registry.process` to reject requests whose shop cannot be corroborated against a known session/installation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; the app registers webhooks with topic `orders/create`.
2. Shopify (or the attacker directly, since the check is body-only) sends `POST /callback/orders/create` with:
   - body: `{"id": 1, "note": "pwned"}`
   - header `X-Shopify-Hmac-Sha256: <valid HMAC of body computed with the app's shared api_secret_key>`
   - header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `Utils::HmacValidator.validate(request)` succeeds because it only checks `Digest.hexencode(...)` against `HMAC(raw_body)`: [5](#0-4) 
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"pwned"}, ...)`, causing the app to process attacker-controlled data under the victim shop's tenant context.
