### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then forwards the **unauthenticated** `shop-domain` header value to the app's handler as the tenant identifier. Because the HMAC secret (`Context.api_secret_key`) is shared by the app across every installed shop, any unprivileged merchant who has installed the app can capture one of their own genuine `(body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The signature still validates (it never covered `shop`), so the app processes attacker-controlled webhook content under a victim shop's identity — a direct violation of the intended binding `verified_bytes == acted_on_identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; none of `shop`, `topic`, `api_version`, or `webhook_id` — all parsed straight from attacker-controllable HTTP headers — are part of the signed material.

`HmacValidator.validate` only checks that the received `hmac` matches `HMAC(secret, verifiable_query.to_signable_string)`: [2](#0-1) 

`Registry.process` uses this single check as the sole gate before dispatching to the handler, and it passes the **unverified** `request.shop` header straight into the tenant-identifying `WebhookMetadata`: [3](#0-2) 

Because `client_secret`/`api_secret_key` is one value per app (not per shop), the same secret signs every shop's webhook traffic. An attacker who installs the app on their own store (a normal, unprivileged action any internet user can perform via a Shopify dev/trial store) legitimately receives real webhooks with valid `(raw_body, hmac)` pairs computed by Shopify. Nothing in this gem's verification path binds that HMAC to the `shop` header, so the attacker can resend the identical body/hmac to the app's public webhook receiver endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `shop: <victim-shop>` while the body content is fully attacker-influenced (from their own store's genuine event, e.g. `orders/create`, `app/uninstalled`, `customers/data_request`, etc.).

This is precisely the "field acted on but not covered by the HMAC" class described in the rules: the identity binding `hmac-authenticated bytes == shop the event is attributed to` is broken, because the signed bytes are only the body, while the acted-upon shop identity comes from an unauthenticated header.

### Impact Explanation
This allows cross-tenant confusion/injection: an app whose webhook handlers key off `WebhookMetadata#shop` (e.g., to look up/update the correct merchant's data, deprovision/enable features, or trigger side effects) can be tricked into performing that logic against a shop the attacker does not own. Depending on the handler's semantics (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or custom order-processing webhooks), this enables cross-tenant state corruption or data exposure without requiring the victim's access token, credentials, or any privileged access — only the ability to install the app on an unrelated shop and send a crafted HTTP request to the app's public webhook endpoint.

### Likelihood Explanation
High reachability: installing an app on a throwaway/trial Shopify store to obtain a valid `(body, hmac)` pair is trivial and requires no special privilege; the webhook receiver endpoint is by definition internet-reachable (Shopify itself must be able to POST to it). No secret material or victim credentials are needed — only header manipulation, which is possible from any HTTP client.

### Recommendation
Bind the shop identity into the authenticated material before trusting it:
- Do not include the unauthenticated `shop` header as untrusted routing/tenant data downstream; instead resolve the shop through a value that is cryptographically tied to the request, e.g. verify the webhook is expected for that specific shop via a stored, shop-scoped session/webhook registration lookup (confirm the shop actually has this webhook topic registered) before dispatching, and/or
- Where possible, include the shop domain in the material used to compute/verify the signature (Shopify's own guidance to consumers is to use `X-Shopify-Shop-Domain` only after confirming this domain is a known, currently-installed shop for the app) rather than trusting it implicitly inside `Registry.process`.
- At minimum, document in this gem that `WebhookMetadata#shop` is unauthenticated and that consuming applications MUST independently verify the shop is an existing/authorized installation before using it to key any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/unprivileged action).
2. Attacker triggers a real event (e.g., updates an order) and captures the legitimate webhook POST Shopify sends to the app, including `x-shopify-hmac-sha256: <valid_hmac>` and body `raw_body`.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only (per `to_signable_string`) using the app's single `api_secret_key` — this matches the replayed `hmac`, so validation passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the app to process attacker-influenced data under the victim shop's tenant context.
