### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identifier that is handed to the app's webhook handler from the `shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates is computed only over the raw request body. The tenant-identifying field (`shop`) is therefore never cryptographically bound to the signature that "proves" the request is authentic, breaking the equality that should hold: `shop authenticated by HMAC == shop acted on by the handler`.

### Finding Description
`Registry.process` gates webhook handling on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the signature using `verifiable_query.to_signable_string` and compares it against the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) and are never part of the signed payload: [4](#0-3) 

These unauthenticated values are then passed straight into the handler as the tenant identity for the webhook event: [5](#0-4) 

Crucially, the HMAC secret (`Context.api_secret_key`) is the **app's** client secret — the same value is used to sign webhooks for *every* shop that has installed the app, not a per-shop secret. As a result:
- `HMAC(body) == HMAC(api_secret_key, body)` is valid for any request whose body was legitimately signed for **any** shop using this app.
- A holder of a valid `(body, hmac)` pair for their own shop can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop.
- `HmacValidator.validate` still returns `true`, because `shop` is not part of `to_signable_string`.
- The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's forged/replayed body>, ...)` and, per the documented usage pattern, acts on data on behalf of the victim shop: [6](#0-5) 

The documentation and example handler give no indication that `data.shop` requires any additional verification — it is presented as the trusted shop identifier for the event.

### Impact Explanation
This breaks the tenant isolation boundary: an entity who has ever received (or otherwise obtained) one validly-signed webhook body for the shared app secret can inject that body into a different tenant's data pipeline by only forging an HTTP header, without possessing that tenant's session, access token, or any Shopify-side credential. This is cross-tenant access/injection — one merchant/attacker causing another merchant's app instance to process attacker-controlled data as if it originated from Shopify for that shop (e.g., triggering `orders/create`/`app/uninstalled`-style side effects, corrupting stored data keyed by `shop`, or triggering business logic scoped to the victim's shop).

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the attacker needs at least one legitimately-signed webhook body (trivial — install the app on any shop, including a free/trial shop, and capture an incoming webhook), and (2) the app's webhook endpoint must be reachable and must not perform its own independent verification that the `shop` header corresponds to a shop it actually has an active session/installation record for. Since this gem's own webhook-processing path (`Registry.process`) performs no such secondary check and its documentation does not instruct developers to add one, any app that follows the documented pattern verbatim is exposed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`/`api_version`) into the signed material, or otherwise cryptographically tie the header values to the verified body — e.g., include them in `to_signable_string`, or require the caller to independently confirm the `shop` header corresponds to a shop with an active session/installation before invoking the handler. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the HMAC and must be cross-checked against known installed shops before being trusted.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action available to any Shopify user).
2. Shopify sends a webhook to the app for `attacker-shop.myshopify.com`; attacker captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (both signed using the app's single, shared `api_secret_key`).
3. Attacker sends a new POST request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <parsed B>, ...)`, causing the app to process attacker-supplied data under the victim shop's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
