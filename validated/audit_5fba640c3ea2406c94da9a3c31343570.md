### Title
Webhook `shop` (and `topic`) fields are not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by checking only the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, but `Webhooks::Request#to_signable_string` returns solely `@raw_body`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and are never included in the signed content. The host application's handler is then invoked with this unauthenticated `shop` value as the tenant identifier, breaking the binding `hmac_verified(body) == fields_trusted_for_dispatch`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` as just the raw body: [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from headers: [5](#0-4) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body only) and secure-compares it to the `hmac-sha256` header — then immediately dispatches to the handler using `request.topic` and `request.shop`, neither of which participated in the HMAC computation: [2](#0-1) .

Because the signature only covers the body, any request carrying a body+HMAC pair that is valid for the app's `client_secret` (which is shared across every shop/tenant using this app, not per-shop) will pass validation regardless of what `shop-domain` or `topic` header accompanies it. This is the direct analog of the report's core defect: a value ("shop") that is acted upon by the receiving logic (tenant attribution/dispatch) is not covered by the same integrity check ("HMAC") that is supposed to authenticate the request.

### Impact Explanation
An attacker who can obtain one valid `(body, hmac)` pair for the app — for example by triggering a webhook-eligible event on their own store/tenant that also has the app installed, and capturing the resulting webhook delivery — can replay that same body and HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. Because `Registry.process` never checks that the `shop` header is consistent with anything cryptographically bound to the payload, the host application's webhook handler receives `WebhookMetadata` attributing that (attacker-controlled) body to a shop the attacker does not control. Depending on how the host app persists or acts on webhook data (order/customer/product updates, GDPR redact triggers, etc.), this enables cross-tenant data injection/corruption keyed off a shop identity that was never authenticated for this specific payload — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to have legitimate access to at least one shop where the app is installed (to obtain a valid body/HMAC pair) or to otherwise capture one, plus network access to POST to the app's public webhook endpoint. It does not require `api_secret_key`, an access token, or any credential theft, and is fully triggerable by an unprivileged app-installing user — consistent with the "unprivileged internet user" scope for this analysis.

### Recommendation
Bind the identity fields to the signed content: either require the host application to source `shop` from a trusted, separately-verified channel rather than the raw header, or change `to_signable_string`/`HmacValidator` usage so that `topic`, `shop-domain`, and `webhook-id` are included in what is verified before being trusted for dispatch, matching how Shopify's own HMAC construction is documented to be used for header-derived identity fields.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers an event (e.g., `orders/create`) causing Shopify to send a webhook to the app with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures this `(B, H)` pair (they control the shop that received the payload).
3. Attacker (or any client with network access to the app) sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `Webhooks::Request.new` parses these headers: [6](#0-5) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [7](#0-6) .
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, causing the host app to process forged data under the victim tenant's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
