### Title
Webhook shop identity not bound by HMAC, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC signature and then unconditionally trusts the `shop` (and `topic`) values taken from unauthenticated HTTP headers when dispatching to the app's handler. The signature computed by `HmacValidator` only covers the raw request body, not the `shop-domain`/`x-shopify-shop-domain` header, so the shop identity handed to the handler is never actually authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from the `shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that header value: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then raises `InvalidWebhookError` only if that body-only HMAC fails, and afterwards forwards `request.shop` and `request.topic` — both unauthenticated header values — directly into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the intended identity binding: the equality that should hold is `shop authenticated by HMAC == shop delivered to handler`, but in fact `shop delivered to handler` is read from a header that is completely outside the signed bytes. Any request whose **body** carries a valid HMAC (e.g. a genuine webhook payload the attacker legitimately received for their own shop, since they are a merchant with the app installed) can be replayed with an arbitrary `shop-domain` header value, and `Registry.process` will still accept it and hand the (attacker-supplied) shop identity to the handler as if it were authenticated.

### Impact Explanation
An unprivileged merchant who has the target app installed on their own shop receives real, validly-signed webhooks for their own shop. By capturing one such request and re-sending it to the app's webhook endpoint with the `shop-domain` header changed to a different (victim) shop that also has the app installed, the gem's own `Registry.process` will still pass HMAC validation (since the signature never covered the shop header) and will invoke the app's handler with `WebhookMetadata#shop` set to the victim shop. If the host app uses this `shop` value to look up per-tenant data/sessions (the documented purpose of `WebhookMetadata#shop` per `docs/usage/webhooks.md`), this allows cross-tenant data injection/processing under another merchant's identity — a cross-tenant access impact rooted entirely in this gem's own verification logic, not requiring any secret, token, or host-application misuse.

### Likelihood Explanation
Any actor who can get the app installed on a shop they control (the normal, unprivileged path for any Shopify merchant installing a public app) can capture a legitimately-signed webhook body and hmac for their own shop, then replay it with a forged `shop-domain` header. No `api_secret_key`, access token, or privileged access is required — only observation of one's own inbound webhook traffic and the ability to send an HTTP request to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and topic, if it drives handler dispatch/authorization) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the validated payload before it is passed to `WebhookMetadata`/the handler, rather than trusting `shop-domain`/`x-shopify-shop-domain` headers verbatim once only the body's HMAC has been checked.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook, e.g. via `ShopifyAPI::Webhooks::Registry`.
2. Shopify delivers a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a correct `x-shopify-hmac-sha256` computed as `HMAC_SHA256(api_secret_key, B)` (per `HmacValidator.compute_signature`, `lib/shopify_api/utils/hmac_validator.rb:34-40`, which never includes the shop header).
3. Attacker replays this exact body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop that also has the app installed).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `Utils::HmacValidator.validate(request)`, which passes because the signature only ever covered `B`.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled content under the victim shop's identity — a cross-tenant identity binding failure entirely within this gem's own webhook verification path.
