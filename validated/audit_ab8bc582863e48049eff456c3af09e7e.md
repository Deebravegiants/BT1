## Finding

### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated ("verify the request did indeed come from Shopify") once `Utils::HmacValidator.validate(request)` passes, and then forwards `request.shop` to the app's handler as the trusted tenant identifier. However, the HMAC signature only covers the raw request body, not the `shop-domain` header that identifies which merchant/tenant the webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read directly and unverified from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` uses that single check as its full authenticity gate, then passes the unauthenticated `request.shop` value straight into `WebhookMetadata` for the app's handler: [4](#0-3) 

The documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," and that `data.shop` is "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

This is the classic "field acted on but not covered by the HMAC" binding break: the gem asserts `shop = authenticated tenant`, but in reality `shop = value of an attacker-controllable header`, since `shop ∉ HMAC(body)`.

Crucially, a Shopify app's `api_secret_key`/`client_secret` is the **same shared secret for every shop that installs the app** — it is not per-tenant. Any unprivileged internet user can become a legitimate tenant simply by installing the target app on their own store, and will then receive genuine Shopify webhooks (real body + valid HMAC computed with the app's shared secret).

### Impact Explanation
Because the shop identity is not bound to the signature, an attacker who legitimately installs the app on their own shop can capture a real Shopify webhook (valid body/HMAC pair for their own tenant) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `data.shop` equal to the victim's domain while `data.body` is fully attacker-influenced content from the attacker's own shop. Any host application that uses `data.shop` to route/attribute webhook data to a tenant record (exactly as shown in the gem's own documented handler example, `shop_domain: data.shop`) will attribute the attacker's forged event to the victim tenant — a cross-tenant data injection.

### Likelihood Explanation
Likelihood is high for any app: no special credentials beyond a routine self-installation are needed, the HMAC over the body remains genuinely valid (computed by Shopify itself using the shared client secret), and the only manipulation required is rewriting a single, unauthenticated request header before forwarding it to the app's already-public webhook endpoint.

### Recommendation
Bind the `shop` field to the signed payload, or otherwise independently authenticate it. Options:
- Include `shop-domain` (and `topic`, `webhook_id`) as part of the signable/verifiable material for webhook requests instead of relying purely on the raw body signature.
- After HMAC validation, cross-check `request.shop` against the set of shops the app has valid, stored sessions/installations for, rejecting webhooks for shops with no known relationship to this particular signed payload.
- Update the documentation so it does not claim the webhook `shop` value is verified when it is not, to avoid host apps trusting it as an authenticated tenant key.

### Proof of Concept
```ruby
# Step 1: Attacker installs the target Shopify app on their own store,
# attacker-shop.myshopify.com, and receives a genuine "orders/create" webhook:
raw_body = '{"id": 1, "note": "attacker-controlled order data"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# (This HMAC is computed by Shopify itself and delivered to the attacker's endpoint.)

# Step 2: Attacker relays the exact same body+hmac to the app's webhook
# controller, but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # still valid! HMAC never covered shop
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body signature matches)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_data, ...))
```
The handler receives attacker-supplied `body` tagged with the victim's `shop`, exactly matching the documented handler pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` from `docs/usage/webhooks.md`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
