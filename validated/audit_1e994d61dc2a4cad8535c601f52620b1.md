### Title
Webhook Shop/Topic Identity Not Bound by HMAC in `Webhooks::Request` — Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop`/`topic` values taken from HTTP headers — which are never covered by that HMAC — to decide which tenant and handler the payload belongs to. This breaks the intended identity binding: `hmac(raw_body) valid` ⇏ `shop header == shop that actually generated the body`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight out of unauthenticated HTTP headers with no cryptographic tie to the signed bytes: [2](#0-1) 

`Registry.process` validates only the body HMAC and then forwards the header-derived `shop`/`topic` straight to the app's webhook handler as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's single, shop-independent `client_secret`: [4](#0-3) 

Because the same `client_secret` is used to sign every shop's webhooks, and the signature covers only the body (not the shop/topic headers), the equality the gem implicitly relies on — `hmac_valid(body) == body originated from the shop named in the shop-domain header` — does not hold. Any tenant that has legitimately installed the app can capture a webhook delivered to their own installation (valid body + valid HMAC for that body, since they own that store and control what data goes into the body, e.g. order notes, product titles, customer fields), then resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with another tenant's shop domain. `HmacValidator.validate` still succeeds because it never looked at those headers, and `WebhookMetadata.shop` is populated from the forged header, so the host application processes attacker-controlled data as though it came from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure inside the gem's own webhook-processing path (not a host-application misuse of the API): the gem's documented `Request`/`Registry.process` contract presents `shop` as an authenticated field once `HmacValidator.validate` passes, but it is not actually bound to the signature. A malicious merchant/tenant can inject forged, attacker-controlled webhook payloads attributed to a victim shop, corrupting per-tenant state, session data, or business logic keyed on `shop` (e.g., `shop/redact`, `app/uninstalled`, `orders/create` handling) in the host application — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own legitimately installed instance of the target app (a normal, unprivileged merchant/tenant relationship, not a leaked secret or TLS interception) and be able to capture/replay a webhook they legitimately received to the app's own public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any other tenant's credentials is required.

### Recommendation
Include `shop`, `topic`, and other security-relevant identifiers in the HMAC-signed material (or otherwise cryptographically bind them, e.g., by deriving/validating the shop against a per-shop secret or session record) instead of trusting header values that are outside the signature's scope, mirroring how `Auth::Oauth::AuthQuery`'s HMAC covers `shop`, `state`, `code`, etc. At minimum, `Registry.process` should cross-check `request.shop` against an independently trusted source (e.g., the session store) before dispatching to a handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., `orders/create`) with attacker-chosen body content, capturing the raw request Shopify sends to the app's webhook endpoint, including the valid `X-Shopify-Hmac-Sha256` header (computed over that exact body with the app's shared `client_secret`).
3. Attacker resends the identical `(raw_body, X-Shopify-Hmac-Sha256)` pair to the same public webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `Registry.process` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/registry.rb:190`).
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, causing the host app to process forged data as belonging to the victim tenant.
