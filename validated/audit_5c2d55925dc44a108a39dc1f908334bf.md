### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)` before dispatching to the app's handler with `request.shop` (read from the `X-Shopify-Shop-Domain` header) as the tenant identity, without that header ever being part of the HMAC-verified bytes.

### Finding Description
The identity binding that should hold is: `hmac_verified_bytes == tenant_identity_used_downstream`. In this gem it does not:

- `Request#to_signable_string` is defined as just the raw body: [1](#0-0) 
- `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, none of which are included in the signable string: [2](#0-1) 
- `Registry.process` verifies only the HMAC over the body, then immediately trusts `request.topic` (to select the handler) and `request.shop` (as the tenant identity passed to the app's business logic) without any cryptographic binding between those header values and the HMAC-covered body: [3](#0-2) 
- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header — again, only the body is authenticated: [4](#0-3) 

Because `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) are not part of the signed payload, any party who can produce one valid `(body, hmac)` pair for the shared `client_secret` (e.g., a merchant installing the app who receives real webhooks for their own shop, or anyone able to replay a previously-observed legitimate webhook body/HMAC pair) can resubmit that same body with a different `shop-domain` header value and the signature will still validate. The gem exposes no API to detect or reject this — `Registry.process` accepts it as authentic and hands `WebhookMetadata` with the attacker-chosen `shop` to the host application's `WebhookHandler#handle` implementation.

This matches the reported bug class exactly: a field acted on (the `shop` field used as the tenant key) but not covered by the HMAC.

### Impact Explanation
Any application that uses `request.shop`/`WebhookMetadata#shop` returned by this gem as the tenant key to look up per-shop data/tokens (the intended and documented use of this field) can be made to process a validly-HMAC'd payload under an attacker-chosen shop identity. Since webhook handlers commonly perform side effects keyed by `shop` (e.g., updating per-tenant records, revoking data, redacting customer data for `shop/redact`), this can result in cross-tenant data corruption/exfiltration — one tenant's legitimately-signed webhook body being attributed to and applied against a different tenant. This satisfies the "cross-tenant access" criterion for a Critical/High-severity finding as scoped by this analysis.

### Likelihood Explanation
Exploitation requires only network-level access to the app's public webhook endpoint plus possession of one valid `(body, hmac)` pair signed with the shared app secret for any shop — something any shop that has installed the app can obtain simply by triggering an event that fires a real webhook to itself, since the webhook body/HMAC do not vary per-recipient shop in this validation scheme. No access to `api_secret_key`, access tokens, or privileged accounts is needed beyond being any installed-and-authenticated merchant of the app, and the header can be freely modified in transit by anyone controlling the HTTP request to the app's endpoint (the gem never inspects TLS-level origin).

### Recommendation
Bind the tenant/topic identity into the authenticated payload before dispatch: verify that `request.shop` corresponds to a shop for which the app already holds a stored session/access token (as Shopify's official approach expects), or require the host application to independently validate `shop` against known/registered shops rather than trusting the unauthenticated header value returned by `Request#shop`. At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is **not** authenticated by the HMAC and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against the shop stored for the session that originally registered the webhook).

### Proof of Concept
1. App registers webhooks for shop `victim.myshopify.com` and shop `attacker.myshopify.com` (attacker legitimately installs the app).
2. Shopify sends the attacker a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the same body `B` and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)`, which matches — validation passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to apply `attacker`-originated webhook content under `victim`'s tenant identity.
