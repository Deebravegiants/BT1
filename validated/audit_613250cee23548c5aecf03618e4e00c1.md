### Title
Unsanitized JWT `dest` claim used as OAuth token-exchange host, breaking the host==credential-recipient binding - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token` derives the request host solely from the JWT's `dest` claim (`jwt_payload.shop`) and never runs it through `Utils::ShopValidator.sanitize!`, unlike every other credential-sending flow in the gem (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`).

### Finding Description
`JwtPayload#initialize` only validates the `aud` claim against `Context.api_key` — it never validates or normalizes the `dest` claim: [1](#0-0) 

`TokenExchange.exchange_token` takes `dest_shop = jwt_payload.shop` and directly constructs a `Session` with it, then builds an `HttpClient` whose base URI is `"https://#{session.shop}"`, sending `client_id`/`client_secret` in the POST body to that host: [2](#0-1) 

Compare this to `TokenExchange.migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used to send the same credentials: [3](#0-2) [4](#0-3) [5](#0-4) 

`HttpClient` builds its request URL directly from `session.shop` with no additional validation: [6](#0-5) 

The binding that should hold is: `host that receives client_secret == host validated as a trusted Shopify domain`. In `exchange_token` this becomes `host that receives client_secret == raw dest claim value`, with no equality enforced against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Impact Explanation
If the `dest` claim value can be anything other than a genuine `*.myshopify.com`/trusted Shopify host (e.g., if the host application passes through a session token whose `dest` was not strictly validated to be one of Shopify's trusted domains, or a future/alternate token issuer with a different validation posture), this code will silently POST the app's `client_id` and `client_secret` to that host — an SSRF that exfiltrates the app's OAuth credentials. This matches the "Critical" bucket of theft of the app's `client_secret` / SSRF with the app's credentials.

### Likelihood Explanation
Exploitation depends on getting the gem to process a JWT whose `dest` is attacker-controlled while still passing the `aud == Context.api_key` check — this requires either a signature under the app's own secret (out of scope per rules) or a host/issuer that doesn't itself validate `dest` before invoking this gem. Given the JWT is HS256-signed with `Context.api_secret_key`, a token with a forged `dest` cannot be produced by an unprivileged internet user without the secret. This significantly limits standalone exploitability from this gem's own code alone, and I cannot fully verify a credential-free path to controlling `dest` without the secret.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop, myshopify_domain: ...)` in `TokenExchange.exchange_token` before constructing `shop_session`, mirroring the other three OAuth credential flows, so the destination host is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not concretely demonstrable without a valid signature over an attacker-chosen `dest`, since `JwtPayload` requires HS256 verification against `Context.api_secret_key` (or `old_api_secret_key`). This is the missing link that keeps this from being a directly provable end-to-end exploit in the current analysis; a session token with a non-Shopify `dest` value that nonetheless verifies would need to originate from a signing-secret compromise or an alternate/non-Shopify token issuer trusted by the host app — both outside pure code-review confirmation here.
