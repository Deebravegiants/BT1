**Why the claim fails:**

1. **Gas is charged atomically, not incrementally per validation branch.** In the native implementation, `context.charge(STRING_CHECK_UTF8_BASE + STRING_CHECK_UTF8_PER_BYTE * len)` is called **before** `std::str::from_utf8` runs, using only the byte length as input [1](#0-0) . The native function is not interruptible mid-loop — either the gas meter has enough balance and the whole `from_utf8` validation completes, or the charge itself fails and the native call never begins. There is no code path where the byte-scan runs "mid-way" and then aborts due to gas exhaustion inside the loop.

2. **Even if the per-byte price under-estimates actual CPU branch cost, this is a pricing/DoS concern, not a custody-boundary violation.** The gas parameters in question [2](#0-1)  only affect how much gas is deducted for a given input size — they do not affect what state is written.

3. **Aptos transactions are atomic — an abort (whether from insufficient gas or a Move `assert!` failure) reverts all session writes.** Per the AptosVM execution model, a failed/aborted execution discards the temporary change set produced during **Execution** and only the epilogue's gas-charging writes are kept; no application-level writes (like object creation via `move_to`) survive an abort [3](#0-2) . The `failed_transaction_cleanup`/`on_user_transaction_execution_failure` path constructs a fresh `EpilogueSession` on top of the *prologue* change set specifically to exclude aborted execution's writes [4](#0-3) . This means `string::utf8()`'s `assert!(internal_check_utf8(&bytes), EINVALID_UTF8)` [5](#0-4)  failing, or the whole transaction running out of gas, both result in the entire transaction's writes (including any partially-constructed FA metadata object) being rolled back — never committed to storage.

4. Consequently, there is no way for a crafted UTF-8 byte string to leave a "partially-initialized FA metadata object" claimable by another address. Move/Aptos has no notion of partial commit within a single transaction; the described "abort mid-way through primary-store metadata initialization" scenario doesn't correspond to any real execution semantics in this VM.

This does not cross a real custody boundary — it is at most a gas-pricing accuracy concern (worth flagging as a benchmarking/DoS-cost issue), not an ownership/authority confusion bug.
