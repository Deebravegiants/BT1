### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity (`shop-domain` header) and event `topic`/`webhook-id`/`api-version` headers are read directly from unauthenticated HTTP headers and are never included in the HMAC computation. `Registry.process` validates the HMAC against the body only and then hands the attacker-controlled `shop`/`topic` values straight to the app's webhook handler, breaking the binding between "payload the app's shared secret actually authenticated" and "shop the app believes the payload is for."

### Finding Description
The HMAC validation for webhooks is delegated to `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` to get the bytes that are HMAC'd: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never part of the signed bytes: [3](#0-2) 

`Registry.process` validates only the body-derived HMAC, then dispatches based on the unauthenticated `topic` header and forwards the unauthenticated `shop` header straight into `WebhookMetadata` for the app's handler: [4](#0-3) 

Since Shopify signs webhooks with the app's single shared `client_secret` (the same secret is valid for every shop that has installed the app, mirrored by `HmacValidator` checking `Context.api_secret_key`/`old_api_secret_key`), a valid HMAC only proves "this body was produced for *some* shop using this app," not "this body belongs to the shop named in the `shop-domain` header." This is exactly analogous to the report's core issue — a value used to determine identity/value (there: the strategy's `currentBalance`; here: the `shop` used to attribute the webhook) is decoupled from the value that was actually integrity-checked (there: real underlying share accounting; here: the HMAC-covered body).

The gem's own documented usage pattern explicitly trusts `data.shop` as the tenant identifier for routing/storage: [5](#0-4) 

### Impact Explanation
Any merchant who has installed the app (an unprivileged, ordinary user of the app — no special access needed) receives real webhooks with a valid body+HMAC pair for their own shop. Because the HMAC never binds the `shop-domain`/`topic` headers, that same attacker can capture one legitimate `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim shop) and/or a different `topic` header (e.g. changing a benign topic to a mandatory compliance topic like `customers/redact` or `shop/redact`). `Utils::HmacValidator.validate` still returns `true` because it only checks the untouched body bytes, and `Registry.process` will run the handler registered for the attacker-chosen topic with `WebhookMetadata.shop` set to the attacker-chosen shop. This crosses the tenant boundary: the app is fooled into attributing/acting on data for a shop that did not actually send it, satisfying the "cross-tenant access" impact category (data corruption/injection into another tenant's context, forged mandatory-webhook triggers, etc.).

### Likelihood Explanation
Likelihood is high for any app built on this gem that follows its documented pattern (using `data.shop`/`data.topic` for tenant/topic routing, as shown in the gem's own `docs/usage/webhooks.md` example). The attacker only needs to be a legitimate, unprivileged installer of the target app to obtain one valid `(body, hmac)` pair, which is trivial (install the app on a test/dev store and capture the delivered webhook, or use Shopify's "send test notification" feature).

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the payload), so that `Utils::HmacValidator.validate` fails if any of these header values are altered from what Shopify actually sent. At minimum, `Webhooks::Request#to_signable_string` should incorporate these headers rather than only `@raw_body`.

### Proof of Concept
1. Install the target app on shop `attacker-shop.myshopify.com` and register a webhook handler for topic `orders/create`.
2. Capture a real delivered webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid hmac of body>`, plus the raw JSON body.
3. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally change `x-shopify-topic` to a different registered topic, e.g. `customers/redact`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, which is unchanged, so validation passes: [6](#0-5) 
5. The handler for the (possibly attacker-chosen) topic is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though Shopify never sent anything to/for that shop — demonstrating cross-tenant webhook spoofing purely from a valid webhook the attacker legitimately received for their own shop.
