### Title
Suspicious guarded condition on genesis state-machine commitment storage - ([File: evm/src/core/HandlerV2.sol])

### Summary
`handleConsensus` in `evm/src/core/HandlerV2.sol` stores each newly finalized `IntermediateState` returned by the consensus client only if `latestHeight != 0 && intermediate.height > latestHeight` [1](#0-0)  where `latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId)`. If a state machine has never had a commitment stored (i.e., `latestStateMachineHeight` returns the Solidity default of `0`), the `latestHeight != 0` clause is false, and the branch that calls `host.storeStateMachineCommitment(...)` is skipped entirely — meaning the very first commitment for that state machine could never be persisted through this path, unless a separate genesis-seeding mechanism initializes `latestStateMachineHeight` to a non-zero value elsewhere in `EvmHost.sol`.

### Finding Description
This mirrors the reported bug class in that a numeric "progress pointer" (`latestStateMachineHeight`) is used as a proxy for "have I already accounted for this update," and the boundary/comparison logic around that pointer silently drops updates instead of processing them. In the original Sherlock report, `assetsAtEpoch` only accounted for `version` and `version + 1`, silently skipping any additional advanced versions when two related markets' oracles updated at different cadences. Here, the analogous risk is that `latestHeight == 0` is used both as "genuinely at height 0" and as "sentinel for never set," causing the store branch to be skipped for what may be a legitimately new state machine's first commitment.

I could not confirm from the available index whether `EvmHost.sol` has a separate initialization path (analogous to Substrate's `create_client`, which seeds `store_latest_commitment_height` explicitly, see `modules/ismp/core/src/handlers/consensus.rs` lines 108-114) that sets `latestStateMachineHeight` to a non-zero baseline before `handleConsensus` is ever called for a given state machine. If such seeding exists, this is not exploitable. If it does not exist, the first-ever consensus update for a newly added state machine would be silently dropped, which could delay or permanently block that route's ability to have any state committed, until a state machine reaches a height that happens not to be preceded by a genuine "0" state.

### Impact Explanation
If unmitigated by a genesis-seeding path, this could cause a route to be permanently unable to deliver messages (no state commitment ever recorded for that destination), which matches the "route unable to deliver messages" acceptance criterion. This would be a Medium/High severity availability/freezing issue rather than a fund-theft issue.

### Likelihood Explanation
Low-to-Medium confidence — I was not able to verify the counterpart initialization logic in `EvmHost.sol` due to running out of tool-call budget. This significantly limits certainty about exploitability.

### Recommendation
Verify in `EvmHost.sol` whether `latestStateMachineHeight` for a state machine is ever initialized without going through `HandlerV2.handleConsensus`'s guarded branch. If not, change the guard to distinguish "never set" from "set to height 0" (e.g., using a separate existence flag/mapping) rather than overloading the zero value, and ensure the first commitment for any state machine is always stored.
