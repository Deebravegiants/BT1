### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively over that body. The `shop-domain` header, which `ShopifyAPI::Webhooks::Registry.process` uses to identify the tenant for the handler, is never part of the signed material. Because the same `client_secret` is shared across every store that installs a given app, any store owner receiving genuine webhooks for their own shop can capture a validly-signed webhook and replay it with a forged `shop-domain` header pointing at a different (victim) shop, and the gem will accept it as authentic.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`, never including `shop`, `topic`, or any header value.

`HmacValidator.validate` computes and compares the HMAC strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` only checks this body-only HMAC before immediately trusting `request.shop` (parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) to build the tenant context handed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`shop_bytes_authenticated_by_HMAC == shop_bytes_used_for_tenant_dispatch`

In this code, the left side is undefined — the HMAC never covers the shop field at all — so the equality trivially fails to be enforced. `shop` is a "field acted on but not covered by the HMAC," matching the report's underlying bug class of an identity binding that isn't actually checked at the point of use.

Because Shopify signs every merchant's webhooks with the single, shared `client_secret` belonging to the *app* (not a per-shop secret), any unprivileged user who installs the app on their own store legitimately receives webhooks with valid HMACs computed over bodies they fully control the shape/timing of. That same signature remains valid regardless of which `shop-domain` header accompanies the request, since the header is excluded from the signed string.

### Impact Explanation
An attacker who has installed the target app on their own shop can:
1. Trigger/receive a legitimate webhook for their own shop (valid HMAC over a chosen/anticipated body, e.g., `orders/create`, `app/uninstalled`, etc.).
2. Replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes because it never checked the shop header.
4. `Registry.process` builds `WebhookMetadata` with `shop: <victim shop>` and hands the attacker-authored body to the host app's handler as if Shopify had authoritatively confirmed this event belongs to the victim tenant.

If the host application relies on the gem's stated HMAC verification to authenticate `shop`/`body` pairing (a reasonable assumption, given the gem exposes a single `validate`/`process` API for this purpose), this enables cross-tenant data injection/spoofing — e.g., forging `app/uninstalled` for a victim shop to deregister/disable it, or forging order/customer payloads attributed to a shop the attacker doesn't own. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user who can install the app on any shop (a normal, permitted action for any merchant) and knowledge of the victim's `myshopify.com` domain (public information, discoverable via the storefront). No access token, `client_secret`, or privileged account is needed — only the ability to receive one's own webhook and replay it to the shared webhook endpoint with a modified header. This is straightforward and repeatable.

### Recommendation
Include the authenticated shop identity in the signed material verified by this gem, or otherwise cryptographically bind the `shop-domain` header to the signature before it is trusted for dispatch. Concretely:
- Extend `Request#to_signable_string` (or add a separate check in `Registry.process`) to incorporate `shop` (and ideally `topic`, `webhook_id`) into the value verified against the HMAC, if Shopify's webhook signing scheme supports it, or
- Cross-validate `request.shop` against a known/expected set of shops (e.g., shops with an active session/installation) before dispatching to the handler, rather than trusting the header verbatim.
- At minimum, document explicitly that `shop-domain` is unauthenticated and must be independently verified by the host application before being used as a tenant key, since currently the gem's public API (`Registry.process`) implicitly presents `data.shop` as verified when it is not covered by the HMAC check it performs.

### Proof of Concept
```ruby
# Attacker's own shop legitimately triggers a webhook, e.g. app/uninstalled,
# and captures the raw body + valid X-Shopify-Hmac-Sha256 for it.
raw_body = '{"id":123,"malicious":"payload"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same body/HMAC but swaps the shop-domain header
# to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not attacker's own shop
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because shop-domain is never part of the signed string.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Handler receives attacker-controlled body attributed to the victim's shop.
ShopifyAPI::Webhooks::Registry.process(request)
```
This demonstrates that `HmacValidator.validate` and `Registry.process` accept a body/shop pairing that Shopify never actually issued together, because the `shop` field is a value acted upon (tenant dispatch) but not covered by the HMAC. [1](#0-0) [5](#0-4) [3](#0-2)
