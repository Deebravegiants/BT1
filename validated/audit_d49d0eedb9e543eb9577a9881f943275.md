Confirmed: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) validates the request via `Utils::HmacValidator.validate(request)`, but `Request#hmac`/`to_signable_string` only sign `@raw_body` while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes, and that unauthenticated `shop` value is what gets forwarded into `WebhookMetadata` and handed to the app's `WebhookHandler#handle`.### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the tenant identity (`shop`) that the gem hands to the app's handler is read directly from an HTTP header that is never included in the signed bytes. This breaks the binding "HMAC-verified bytes == identity used by the handler."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request using only that signable string via `Utils::HmacValidator.validate(request)`: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [4](#0-3) 

That unauthenticated `shop` value is forwarded verbatim into `WebhookMetadata` and passed to the app's `WebhookHandler#handle`, which multi-tenant apps use to look up/update per-shop records: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `signed_bytes ⊇ {shop, body}`, i.e. the tenant identifier must be covered by the same HMAC that authenticates the payload. Instead, `signed_bytes = {body}` and `shop` is taken from `headers`, an entirely separate, unauthenticated channel. This is directly analogous to the referenced report's root cause pattern — a value acted upon (here, tenant identity) that is not covered by the cryptographic check that is supposed to authenticate the whole message.

### Impact Explanation
A merchant who legitimately installs the app (an "unprivileged" party relative to other tenants of the same multi-tenant app) receives genuine, correctly-HMAC-signed webhook deliveries for their own shop whenever they perform ordinary actions in their own store (e.g., create a product/order with attacker-chosen field values). Because the HMAC only covers the JSON body and not the shop header, that merchant can capture one such valid `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to any other shop the app serves. `Registry.process` will accept it as valid (the HMAC check passes because the body is unchanged) and will dispatch it to the app's handler tagged with the victim's shop domain. Depending on how the host app trusts `WebhookMetadata#shop` (a documented, intended use per this gem's design), this allows cross-tenant data injection/corruption — e.g., forging `orders/create`, `app/uninstalled`, or `shop/redact` events attributed to a shop the attacker does not control. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem in a straightforward, documented way: the attacker needs only their own legitimate (and cheap/free) shop install to generate a genuinely-signed webhook, requires no access to `api_secret_key`, no leaked credentials, and no privileged account — only the ability to trigger a webhook-eligible action in a store they already control and then replay the HTTP request with one header value changed.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) inside the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is unauthenticated relative to the HMAC check, and require host apps to independently corroborate shop identity from a source that is covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g.:
   - Headers: `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over body>`
   - Body: `{"id": 1, "title": "arbitrary-attacker-controlled-content"}`
2. Attacker captures this HTTP request and resends it to the same app endpoint, only replacing the header:
   - `shopify-shop-domain: victim.myshopify.com`
   - Body and `shopify-hmac-sha256` left untouched.
3. In `Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (the untouched body) and it matches, so validation passes: [7](#0-6) 
4. `request.shop` now returns `"victim.myshopify.com"` and is delivered to the app's handler as the shop context: [8](#0-7) 
5. The app processes attacker-supplied body content under the victim tenant's identity.
