Audit Report

## Title
Unauthenticated MessageID collision in Gateway Web API handler causes cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` stores each caller's response `callback` in the shared `h.savedCallbacks` map keyed only by the client-supplied `msg.Body.MessageID`, with no existence check before the write [1](#0-0) . Since `MessageID` is fully attacker-controlled and only validated for length/null-suffix in `Message.Validate()` [2](#0-1) , a second caller reusing an in-flight ID silently overwrites the first caller's callback, and the eventual node response is delivered to whichever callback is currently stored for that ID in `handleWebAPITriggerMessage` [3](#0-2) .

## Finding Description
The gateway's user-facing entry point `ProcessRequest` treats any message with a non-empty `Body.DonID` as a "legacy request," validates only the signature/format via `msg.Validate()` (no per-caller or per-ID uniqueness/allowlist check — explicitly marked as a TODO in the handler), and dispatches it to `HandleLegacyUserMessage` [4](#0-3) . This is reachable by any unauthenticated external HTTP client hitting the gateway's user port; there is no operator/admin gate at this stage [5](#0-4) .

Inside `HandleLegacyUserMessage`, after payload/method validation, the callback is unconditionally written into the shared map keyed by `MessageID` with no check for a pre-existing entry [1](#0-0) . When a DON node later responds, `HandleNodeMessage` only checks that the responding node's address matches the message's `Sender` field — i.e., it authenticates the node, not that the `MessageID` still belongs to the original requester [6](#0-5) . The response is then routed purely by `MessageID` lookup in `handleWebAPITriggerMessage`, delivering it to whatever callback is currently stored [3](#0-2) .

This is a materially different design from the two sibling implementations in the same handlers package, both of which explicitly reject duplicate/in-flight IDs: `requestcache.go`'s `NewRequest` [7](#0-6)  and `http_trigger_handler.go`'s `setupCallback` [8](#0-7) . The legacy `handler.go` path lacks this guard, confirming it is a genuine gap rather than an intentional design choice.

## Impact Explanation
If a second, unrelated client submits a request reusing an in-flight `MessageID`, its callback overwrites the original requester's callback in `savedCallbacks`. The subsequent node response — semantically bound to the original request — is delivered to the second client instead, while the original requester silently times out with no response. This is a cross-user response confusion / information-disclosure issue triggerable purely through unprivileged, internet-facing gateway traffic, and maps to the "cross-user response corruption" impact class called out in the scope rules.

## Likelihood Explanation
Exploitability requires only that an attacker submit a request with a `MessageID` value matching another in-flight request's ID; `MessageID` is entirely client-chosen and only constrained by length/null-suffix rules, not uniqueness or unpredictability. Any external, unprivileged caller of the gateway's legacy Web API trigger endpoint can attempt this without any special credentials, and the flaw is reachable via normal HTTP requests to the gateway's user port as shown by `ProcessRequest`'s dispatch logic.

## Recommendation
In `HandleLegacyUserMessage`, check whether `h.savedCallbacks[msg.Body.MessageID]` already exists before storing a new entry and reject the request if so (mirroring `requestcache.go`'s `NewRequest` and `http_trigger_handler.go`'s `setupCallback`). Additionally, key the callback map by `(Sender, MessageID)` rather than `MessageID` alone so that even accidental cross-client collisions cannot cause response misdelivery, since `Sender` is a server-verified value set during `Message.Validate()` via `ExtractSigner()`.

## Proof of Concept
1. User A signs and POSTs a legacy Web API trigger message with `MessageID = "X"` to the gateway's user-facing endpoint; `ProcessRequest` validates it and calls `HandleLegacyUserMessage`, which stores `savedCallbacks["X"] = callbackA` (`core/services/gateway/handlers/capabilities/handler.go:411-414`) and forwards the request to DON nodes.
2. Before any node responds, User B signs and POSTs a different message body but with the same `MessageID = "X"`; `HandleLegacyUserMessage` overwrites the entry: `savedCallbacks["X"] = callbackB`.
3. A DON node responds for `MessageID = "X"`. `HandleNodeMessage` validates only `msg.Body.Sender == nodeAddr` (`handler.go:253-255`), then `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, and delivers User A's intended response data to User B (`handler.go:148-161`).
4. Verify via integration test against `gateway.go`'s `ProcessRequest`/`HandleLegacyUserMessage` path (or a Go unit test directly against `handler.go`) that User B's HTTP response contains User A's trigger payload, and that User A's request eventually errors out with `RequestTimeoutError`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
