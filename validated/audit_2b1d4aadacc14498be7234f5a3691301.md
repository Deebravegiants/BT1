Found it: in `TokenExchange.exchange_token`, `dest_shop = jwt_payload.shop` is used directly to build the session and select the HTTPS host that receives `Context.api_secret_key`, **without** ever passing through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing path (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before using it as the request host.

### Title
Unsanitized `dest` claim used as request host in `TokenExchange.exchange_token` risks SSRF with the app's `client_secret` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Finding Description
`exchange_token` decodes the session token with `ShopifyAPI::Auth::JwtPayload.new(session_token)` [1](#0-0) . `JwtPayload` verifies the HS256 signature and the `aud` claim against `Context.api_key` [2](#0-1) , but it never validates that the `dest`/`iss` claim is a legitimate `*.myshopify.com` (or otherwise trusted) domain — it just strips `https://` and returns it as `shop` [3](#0-2) .

`exchange_token` then builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` and issues the token-exchange POST — which carries `Context.api_secret_key` in the body — to that session's host via `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [4](#0-3) . Every sibling credential-issuing method sanitizes the shop first: `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` [5](#0-4) , `RefreshToken.refresh_access_token` does the same [6](#0-5) , and `TokenExchange.migrate_to_expiring_token` does the same [7](#0-6) . `exchange_token` is the one path that skips `ShopValidator` entirely, breaking the intended equality: "host that receives `client_secret`" should equal "a `ShopValidator`-sanitized trusted Shopify domain," but here it equals "whatever string the `dest` claim contains."

### Impact Explanation
This matters only if the `dest`/`iss` value in the signed JWT is attacker-influenceable, or if a signature-check bypass (e.g., a bug in the `jwt` gem, or leeway/alg confusion) could let a token with an arbitrary `dest` pass verification. If that occurs, the app would POST its `client_secret` (its long-lived, cross-tenant secret) to a host chosen by the token's `dest` value, which is a High-severity SSRF-with-credentials scenario per the target impact list.

### Likelihood Explanation
Likelihood is low-to-uncertain under this gem's own code: `JwtPayload#initialize` does enforce HS256 verification with `Context.api_secret_key` and checks `aud == Context.api_key` before `dest` is trusted, so as long as `JWT.decode`'s signature check is sound, `dest` cannot be forged by an unprivileged caller [2](#0-1) . I could not find, within `lib/shopify_api/**` (excluding generated REST resources), a way for an unprivileged internet user to produce a `dest` value the verifier accepts without already possessing the app's secret. I was not able to fully audit the `jwt` gem's decoding internals (out of scope per the rules), so I cannot rule out a signature-bypass precondition, but no such bypass is demonstrated here.

### Recommendation
Sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` in `exchange_token` before constructing `shop_session`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, so the host receiving `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not demonstrable purely within this gem's code: exploitation requires a `dest` claim value outside the trusted domain set to pass `JwtPayload`'s HS256/`aud` verification, which requires either possession of `Context.api_secret_key` (out of scope) or a flaw in the underlying JWT verification library (unverified, out of scope for this gem). No concrete unprivileged trigger was found; this is reported as a defense-in-depth gap/inconsistency rather than a proven exploitable path.
