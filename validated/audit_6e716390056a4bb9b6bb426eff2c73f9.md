## Analog Found

### Title
Single global `maxOracleAge` staleness bound applied to Chainlink feeds with materially different heartbeats causes either undetected stale pricing or a fully bricked paymaster - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` uses one governance-configured value, `maxOracleAge`, to bound the staleness of *every* Chainlink feed it reads — the shared `nativeOracle` and every registered `TokenConfig.tokenOracle` — even though the contract's own comments acknowledge these feeds have very different real-world heartbeats (e.g. "BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"). This is the same bug class as the external report: a single heartbeat/staleness threshold cannot correctly bound two oracles whose actual update cadences differ by orders of magnitude.

### Finding Description
`_getOraclePrice` checks every oracle read (native and per-token) against the same `maxOracleAge`: [1](#0-0) 

`maxOracleAge` is a single contract-wide field set via governance `UpdateParams`, capped only by `MAX_ORACLE_AGE = 7 days`: [2](#0-1) [3](#0-2) [4](#0-3) 

The contract's own docstrings explicitly document the heartbeat mismatch this creates: [5](#0-4) 

and the deployment script picks a value tuned to the *slowest* feed (stablecoin 24h heartbeats), explicitly to avoid false-positive staleness reverts, without any accounting for faster native-asset feeds such as BNB/USD (~27s heartbeat per the contract's own comment): [6](#0-5) 

`_tokenPrice` — reachable from every priced UserOperation and from the permissionless `swapAndDeposit`/`estimateTokenCost`/`getTokenPrice` paths — calls `_getOraclePrice` for both the native oracle and the token oracle using this one shared bound: [7](#0-6) 

`_tokenPrice` (and thus `_getOraclePrice`/`maxOracleAge`) is invoked from `_fetchDetails`, which every ERC-4337 UserOperation using this paymaster passes through during validation: [8](#0-7) 

Since a single `maxOracleAge` cannot simultaneously be tight enough to catch staleness on a fast feed (e.g. BNB/USD ~27s) and loose enough to tolerate the legitimate 24h cadence of a stablecoin feed:
- If governance sets `maxOracleAge` loose enough for the 24h stablecoin feeds (as the deploy script does, ~90,000s), the staleness check on the fast native-asset feed becomes ineffective — a stalled or manipulated native oracle can go undetected for up to a day, letting `_tokenPrice` compute a materially wrong `nativeUsd/tokenUsd` ratio.
- If governance instead tightens `maxOracleAge` to match the fast feed, every call touching a slow (24h-heartbeat) stablecoin oracle — `_fetchDetails` (hence `_validatePaymasterUserOp`), `getTokenPrice`, `estimateTokenCost`, and `swapAndDeposit` — reverts with `StaleOraclePrice` almost immediately after each stablecoin update, permanently breaking gas sponsorship and fee recycling for that token.

### Impact Explanation
This is a permissionless, unprivileged-reachable pricing path: any account submitting an ERC-4337 `UserOperation` through this "fully onchain, permissionless" paymaster triggers `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` with the shared `maxOracleAge`. Depending on how governance tunes the single knob:
- **Financial loss**: an undetected stale/incorrect native-asset price lets `_tokenPrice` misprice ERC-20 gas payment, letting users systematically underpay (draining paymaster surplus/treasury value) or overpay (loss to the user) relative to the true exchange rate — a concrete theft/mispricing vector reachable by any UserOperation submitter.
- **Freezing of functionality**: an overly tight bound makes `_getOraclePrice` revert deterministically on the slower-heartbeat feed, bricking `_validatePaymasterUserOp` (so the paymaster can no longer sponsor any UserOperation for that token) and `swapAndDeposit` (so accumulated fees can never be swapped/recycled into the EntryPoint deposit) — a route unable to deliver its core function to all users.

### Likelihood Explanation
This is not a hypothetical misconfiguration: the shipped `DeploySimplexPaymaster.s.sol` script already sets `maxOracleAge` (~90,000s) purely to accommodate 24h stablecoin heartbeats, with no separate bound for the native oracle, which the contract's own comments state can have a heartbeat as short as ~27 seconds on BSC. Any deployment mixing a fast native-asset feed with slow stablecoin feeds (explicitly the documented target use case: "BNB/USD on BSC" + "USDC, USDT... with a Chainlink feed") hits this exact mismatch by construction, with no code path to configure per-oracle bounds.

### Recommendation
Track a per-oracle (or at minimum native-vs-token) staleness bound instead of one contract-wide `maxOracleAge`, e.g. add a `maxOracleAge` field to `TokenConfig` (set at `RegisterToken` time) and a separate bound for `nativeOracle`, and validate `_getOraclePrice(oracle, decimals, maxAge)` against the bound appropriate to that specific feed's documented heartbeat.

### Proof of Concept
1. Governance calls `UpdateParams` with `nativeOracle = BNB/USD` (≈27s heartbeat) and registers `USDC` with `tokenOracle = USDC/USD` (24h heartbeat), setting `maxOracleAge = 90_000` (per `DeploySimplexPaymaster.s.sol`).
2. The BNB/USD feed stops updating (oracle outage or targeted manipulation) for, e.g., 12 hours — far beyond its real 27s heartbeat but still within `maxOracleAge`.
3. Any user submits a UserOperation paying gas in USDC; `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(nativeOracle, ...)` passes the staleness check (12h < 90,000s) despite the price being 12 hours stale relative to its true ~27s cadence, so the paymaster charges USDC based on a stale/incorrect BNB price.
4. Alternatively, governance tightens `maxOracleAge` to `60` (seconds, to properly bound BNB/USD): every USDC-paying UserOperation now reverts with `StaleOraclePrice` on the 24h-heartbeat USDC/USD feed almost immediately after each of its updates, permanently breaking gas sponsorship for USDC and freezing `swapAndDeposit` fee recycling.

```text
    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
