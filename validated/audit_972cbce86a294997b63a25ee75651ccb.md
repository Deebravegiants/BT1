### Title
`EmporiumUpgradeable.verifyWallet` fails to bind `feeStructure.feeToken`/`relay` in the EIP-712 signature, letting an unprivileged party who has seen a signed `EmporiumStack` redirect flat-fee collection to any ERC20 the wallet holds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EMPORIUM_SIGNATURE_TYPEHASH` only commits to `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline` [1](#0-0) . `verifyWallet` bounds only the numeric `flatFee` against `stack.maxFee` and never checks `feeStructure.feeToken` or `circomData.relay` against anything the signer authorized [2](#0-1) . Because the same wallet-owner signature (`v,r,s` over that typed data) can be embedded by anyone in a freshly self-generated proof with an independently chosen `feeStructure`/`relay`, the party who submits the transaction - not the signer - decides which ERC20 balance held by the persistent `HinkalWallet` gets drained and where it goes.

### Finding Description
Claimed equality that should hold: `feeToken actually debited from signerAddress's wallet == feeToken the signer's EIP-712 signature authorized`. This equality is broken because no such field exists in the signed payload.

- `runAction` decodes `EmporiumStack` from attacker-supplied `externalActionData.externalActionMetadata` and calls `verifyWallet(stack, circomData)` [3](#0-2) .
- `verifyWallet` recomputes the EIP-712 hash strictly from `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`, recovers the signer, and then only checks `circomData.feeStructure.flatFee > stack.maxFee` [2](#0-1) . `feeStructure.feeToken`, `feeStructure.variableRate`, `circomData.erc20TokenAddresses`, and `circomData.relay` are all outside the signed struct and outside this check.
- `payRelayFees` uses `circomData.feeStructure.feeToken` (attacker-chosen in the new tx) to decide which token to pull as the flat fee. If the attacker's `erc20TokenAddresses` doesn't even contain the fee token, the fallback branch still fires and pays `feeStructure.flatFee` in `feeStructure.feeToken` directly from the wallet as long as `signerAddress != address(0)` [4](#0-3) .
- `payRelay`/`sendToRelayFromWallet` then call `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`, which unconditionally executes `sendToRelay` on the persistent wallet contract for whatever `erc20TokenAddress` and `relay` were passed [5](#0-4) [6](#0-5) .
- `circomData.relay` is a free field on `CircomData` set by whoever submits the proof, not the signer, so the attacker can also redirect the fee payment to an address they control.

Exploit flow: an attacker who observes/harvests any legitimately signed `EmporiumStack` (v, r, s, ops, maxFee, deadline, emporiumMessage - none of this data is secret, it must be transmitted to whoever submits it on-chain) builds their own `CircomData`/proof for their own UTXOs, embeds the harvested stack unchanged (so `_hashEmporiumOps` and `maxFee`/`deadline` match and the signature verifies), but sets `feeStructure.feeToken` to any ERC20 the target wallet holds and `feeStructure.flatFee = stack.maxFee`, and sets `circomData.relay` to an address they control. The one call that gets accepted then drains `flatFee` units of the attacker-chosen token from the victim's `HinkalWallet` to the attacker-chosen relay.

Note: `verifyWallet` marks `$.usedMessages[circomData.emporiumMessage] = true` before the signature check, and this write is only durable if the enclosing transaction succeeds [7](#0-6) . This means only one submission using a given `emporiumMessage` can ultimately succeed - a failed attempt (e.g., bad ops hash) reverts and does not permanently consume the nonce, but a succeeding attempt does. So the specific PoC framing "two different proofs ... both succeed" is not literally achievable for the same `emporiumMessage`; however, the core break is that the attacker - not the signer - decides, in the one call that does succeed, which token and which relay gets paid, which is sufficient for theft.

None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, or `onlyAllowedRecipient` constrain `feeStructure.feeToken` or `circomData.relay` to anything the wallet signer committed to, since these fields are outside `EMPORIUM_SIGNATURE_TYPEHASH` entirely and are chosen by the same actor (any unprivileged caller with a valid, self-generated proof) who is submitting the transaction.

### Impact Explanation
An unprivileged attacker who has visibility into a signed `EmporiumStack` (which must, by construction, be transmitted off-chain to a submitter) can direct the flat fee debit from the victim's `HinkalWallet` in a token of their choosing (any ERC20 balance the wallet holds) and to a relay address of their choosing, rather than the token the wallet owner intended. This is unauthorized movement of wallet-held ERC20 balance that the signer never authorized for that specific asset - matching "executing calls or moving assets a wallet owner ... never authorised" (High), and if the attacker picks a valuable token while the signer intended a low-value one, this becomes effectively theft of wallet funds up to the numeric `flatFee` value in the attacker's chosen token (bordering on Critical depending on wallet holdings). It is a one-shot exploitation per harvested `emporiumMessage` due to the nonce, but repeatable across every signed stack an attacker can observe.

### Likelihood Explanation
Preconditions: attacker needs (1) access to a validly signed `EmporiumStack` before/concurrently with legitimate submission (plausible in any system relying on off-chain relay/broadcast of the signed payload), and (2) the ability to generate their own valid ZK proof for arbitrary UTXOs and metadata, which is explicitly within the attacker's normal capabilities. No privileged role, oracle assumption, or compromised dependency is required. The wallet must hold a non-zero balance of the chosen token. Cost is limited to gas and generating a proof, which any unprivileged user can do.

### Recommendation
Add `feeStructure` (at minimum `feeToken`) and `relay` (and ideally the full `erc20TokenAddresses`/`deltaAmountChanges` fee-relevant context) into `EMPORIUM_SIGNATURE_TYPEHASH` so the signer explicitly authorizes the exact fee token and recipient, or otherwise cryptographically bind `circomData.feeStructure.feeToken` and `circomData.relay` to the signed message before `verifyWallet` accepts it.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a `HinkalWallet` owned by `signer`, fund the wallet with `TokenA` and `TokenB`.
2. Have `signer` sign an `EmporiumStack` (`ops`, `maxFee = X`, `deadline`, `emporiumMessage = N`) intended to be paid in `TokenA`.
3. Attacker builds `circomData_1` with `feeStructure.feeToken = TokenA`, `flatFee = X`, submits via `runAction` - call succeeds, assert `TokenA` balance of wallet decreased by `X`, `$.usedMessages[N] == true`.
4. Attacker attempts a second submission `circomData_2` with `feeStructure.feeToken = TokenB`, same `emporiumMessage = N` - assert it reverts with `UsedMessage()`, confirming the nonce prevents double-spend but does not prevent token substitution on the first successful call.
5. Repeat steps 2-3 with a fresh `emporiumMessage = M` and `feeStructure.feeToken = TokenB` (a token the signer never intended to spend on fees) instead of `TokenA`, assert the call still succeeds and `TokenB` balance of the wallet decreases by `X`, and that `circomData.relay` (set to `attacker`) receives the funds - demonstrating the signer's asset-of-payment choice is not enforced by the signature.
