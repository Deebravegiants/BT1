### Title
`BandwidthManager._host` is settable only once and cannot follow a legitimate `EvmHost` migration, permanently freezing accumulated purchase revenue - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager` binds itself to a single, one-time-settable `EvmHost` address (`_host`) via `setHost`, which explicitly refuses to run a second time. Hyperbridge's own governance layer (`pallet-host-executive::update_evm_hosts`) is designed to update the recorded `EvmHost` address for a given `StateMachine`, i.e. `EvmHost` migrations are an expected, supported operation on the protocol side. `BandwidthManager` has no matching update path, so once an `EvmHost` migration happens, the contract is permanently orphaned: it can no longer receive the `onAccept` governance calls (gated by `onlyHost`, bound to the stale address) that are the only way to withdraw or reconfigure it, while the fee-token revenue it collects from `purchase()` sits in its own balance.

### Finding Description
`BandwidthManager.setHost` can only be called once: [1](#0-0) 

`host()` (required by `HyperApp`, and consumed by the `onlyHost` modifier that gates `onAccept`) simply returns this immutable-once `_host`: [2](#0-1) 

`purchase()` pulls the fee token from the caller into the contract's own balance and only then dispatches a zero-fee message to `pallet-bandwidth`; the collected revenue is not forwarded to the host, it stays custodied inside `BandwidthManager`: [3](#0-2) 

The only way to move that revenue out is the `Withdraw` action inside `onAccept`, which is reachable exclusively through an inbound `IApp.onAccept` call originating from the configured `_host`: [4](#0-3) 

Hyperbridge's Substrate side treats the `EvmHost` address per chain as mutable, updatable governance state, not a permanent constant: [5](#0-4) 

If the recorded `EvmHost` for a chain is ever updated via `update_evm_hosts` (e.g. due to a critical bug fix, a CREATE2 redeploy, or any other legitimate migration the pallet explicitly supports), any outgoing governance message (`SetTiers`, `Withdraw`) from `pallet-bandwidth` will now be dispatched to/through the new `EvmHost`. But `BandwidthManager._host` still points at the old, stale host address and can never be updated — `setHost` reverts unconditionally once `_host != address(0)`. `onlyHost` therefore forever rejects the delivery attempt from the new host, and there is no owner-level escape hatch (unlike `HostManager`, which supports `SetAdmin`/manager rotation, or `EvmHost` core params, which support `updateHostParams`). This is architecturally the same class of bug flagged in the external report: several core protocol addresses are baked in at construction/one-time-configuration with no update or migration mechanism, and if the surrounding system's addresses change, the dependent contract can no longer interact correctly — here concretely resulting in permanently stranded token balances.

### Impact Explanation
Any accumulated fee-token balance inside `BandwidthManager` (from every `purchase()` call across all buyers on that chain) becomes permanently unrecoverable the moment the chain's `EvmHost` is migrated, because:
- `onAccept`'s `Withdraw` action is the only code path capable of moving tokens/native currency out of the contract, and it is gated by `onlyHost` bound to the stale, unchangeable `_host`.
- There is no owner-only emergency withdrawal function, and `setHost` cannot be re-run.
- `purchase()` itself continues to accept payments (as long as the stale host is still live enough to answer `feeToken()`/`dispatch`), compounding the amount of value that becomes permanently locked.

This satisfies "permanent freezing of funds" for a real, reachable, unprivileged actor path (any buyer calling `purchase()`), triggered by an entirely legitimate, protocol-endorsed operation (`update_evm_hosts`).

### Likelihood Explanation
`EvmHost` per-chain address migration is not a hypothetical: the pallet exposes `update_evm_hosts` as a first-class governance call with dedicated events (`HostAddressSet`/`HostAddressUpdated`), meaning the protocol designers already anticipated needing to change a chain's `EvmHost` address post-deployment. `BandwidthManager` is deployed and listed as a production contract on every EVM chain in the mainnet contract-address registry, so it is exposed to this risk on every chain where it is deployed. The likelihood is tied entirely to whether/when Hyperbridge governance performs an `EvmHost` migration on a chain where `BandwidthManager` holds accrued balances — a foreseeable, non-adversarial event rather than a rare edge case.

### Recommendation
Add a governance-gated update path for `_host` in `BandwidthManager`, mirroring the pattern already used by `HostManager` (rotate via owner/governance action, or accept a `SetHost`-style `onAccept` action authenticated some other way, e.g. by contract owner rather than solely by the (now-stale) host). At minimum, add an owner-controlled emergency withdrawal function independent of `onlyHost`, so accrued balances can always be recovered even if the bound host becomes unreachable or is migrated.

### Proof of Concept
1. Deploy `BandwidthManager` with owner `O`; owner calls `setHost(hostA)`.
2. Multiple buyers call `purchase(...)`, each transferring fee-token amounts into `BandwidthManager`'s balance (funds accumulate in the contract per lines 153-189).
3. Hyperbridge governance calls `update_evm_hosts` to migrate the chain's registered `EvmHost` from `hostA` to `hostB` (a supported, documented governance call, `modules/pallets/host-executive/src/lib.rs` lines 244-268).
4. `pallet-bandwidth` later dispatches a `Withdraw` action addressed through the new `hostB`.
5. `hostB` attempts to deliver `onAccept` to `BandwidthManager`; `onlyHost` compares `msg.sender` against `_host` (still `hostA`) and reverts every delivery attempt.
6. Owner tries `setHost(hostB)` to fix it; call reverts (`UnauthorizedAction`) because `_host != address(0)`.
7. All fee-token balances accumulated in `BandwidthManager` are now permanently unrecoverable.

            revert InvalidPurchase();

        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();

        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })

    /// @notice Inbound governance from `pallet-bandwidth`. The first
    /// body byte selects `OnAcceptActions`; the remainder is the
    /// action's ABI-encoded payload.
    /// @dev Only the configured host may invoke (`onlyHost`); the
    /// request's `source` must additionally equal hyperbridge.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }

		/// Set or update the addresses for the specified evm hosts
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(2)]
		pub fn update_evm_hosts(
			origin: OriginFor<T>,
			params: BTreeMap<StateMachine, H160>,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			for (state_machine, address) in params {
				let old = EvmHosts::<T>::get(&state_machine);
				EvmHosts::<T>::insert(state_machine.clone(), address);
				if let Some(old_address) = old {
					Self::deposit_event(Event::<T>::HostAddressUpdated {
						state_machine,
						old_address,
						new_address: address,
					});
				} else {
					Self::deposit_event(Event::<T>::HostAddressSet { state_machine, address });
				}
			}

			Ok(())
		}
