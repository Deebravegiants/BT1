### Title
Missing origin-authenticity enforcement in `ConnectedOrigins` allows self-declared trust/auto-approve escalation - ([File: features/connected-origins/module/connections.js])

### Summary
The Perennial `MarketFactory.updateExtension()` bug is a case of a privileged trust-mapping being mutable by an unauthenticated caller, letting an attacker self-assign as a protocol-wide authorized operator. In this repo, the closest reachable analog is the `ConnectedOrigins` module (`features/connected-origins/module/connections.js`), which maintains the `trusted` / `autoApprove` flags that gate whether a website can silently act on wallet accounts (auto-connect, auto-approve signing) without a user prompt. As with `updateExtension()`, the methods that mutate this trust state (`add`, `setAutoApprove`, `connect`) take the `origin` identifier as a plain caller-supplied parameter and perform no independent verification that the caller actually is that origin.

### Finding Description
`ConnectedOrigins.add()` and `ConnectedOrigins.setAutoApprove()` write directly to the `connectedOriginsAtom` store, keyed by the `origin` string that is passed in as a function argument: [1](#0-0) [2](#0-1) 

These are exposed directly on the SDK's public API surface (`connectedOrigins.add`, `connectedOrigins.setAutoApprove`, `connectedOrigins.connect`) with no additional authorization/identity check layered on top: [3](#0-2) 

`isTrusted()` and `isAutoApprove()` are later relied on to decide whether a dApp's connection/signing request bypasses the user-approval popup ("eagerly connecting" / auto-approve, as documented for the Solana provider): [4](#0-3) [5](#0-4) 

The trust boundary that should prevent a malicious website from marking an arbitrary `origin` string as `trusted: true` / `autoApprove: true` (thereby causing future requests from that origin, or from itself impersonating a different origin string, to skip user confirmation) is not visible anywhere in the module itself — the class performs no comparison against a browser-verified sender identity (e.g., `sender.origin`/`sender.url` from `chrome.runtime`/`chrome.tabs` APIs). I searched for such a check (`sender.origin`, `sender.url`, `MessageSender`) across the whole indexed codebase and found no matches, and none of the RPC/transport layers (`libraries/browser-extension-rpc`, `libraries/json-rpc`, `libraries/sdk-rpc`) appear to bind or verify the `origin` parameter against the actual message sender before invoking `connectedOrigins.add`/`setAutoApprove`/`connect`.

I could not locate, within the indexed portions of the repository, the actual background-script handler that receives a "connect"/"enable" request from the injected in-page provider (`window.exodus.ethereum`/`window.exodus.solana`) and calls `connectedOrigins.add`/`connect` with an origin value taken from a trustworthy source (e.g. the extension's own `sender.origin`) versus a value taken from the postMessage payload originating in the untrusted page context. This is the critical missing piece to *prove* remote exploitability equivalent to the `updateExtension()` case, and due to index size limits some of that browser-extension wiring code may not be available to me.

### Impact Explanation
If the `origin` value used by `ConnectedOrigins.add`/`setAutoApprove`/`connect` is ever derived from data controllable by the requesting web page (rather than a browser-enforced sender origin), a malicious website could:
- Mark itself, or any other spoofed origin string, as `trusted`, bypassing the user-approval popup for account connection.
- Set `autoApprove: true` for an origin, causing subsequent signing/transaction requests from that origin to be approved without user interaction — directly analogous to the `extensions[sender] = true` self-assignment in `updateExtension()`, which allowed an attacker to act as an authorized protocol-wide operator and drain funds.

This would be a direct wallet-compromise / unauthorized-signing vector if provable, since auto-approve is documented to skip the user consent popup entirely.

### Likelihood Explanation
Uncertain / not confirmed. The vulnerability class (mutable trust flag with no ownership/authorization guard inside the function itself) is structurally identical to the Sherlock finding, but I was unable to confirm from the retrieved code whether the extension's message-passing layer independently binds the `origin` argument to a browser-verified sender identity before these methods are invoked. If such binding exists in the (unindexed) background-script glue code, this would not be exploitable by a untrusted webpage. Because this determination is essential and I cannot verify it with the tools available, I cannot assert this as a proven, exploitable analog with full confidence.

### Recommendation
- Verify (in a Devin session with full repository access) where `connectedOrigins.add`, `.connect`, and `.setAutoApprove` are invoked from the browser-extension background/content-script boundary, and confirm whether the `origin` argument is derived from a browser-enforced sender identity (e.g., `sender.origin` from `chrome.runtime.onConnect`/`onMessage`) rather than from data supplied by the requesting page.
- If the `origin` argument is attacker-influenceable, enforce that `ConnectedOrigins.add`/`connect`/`setAutoApprove` only ever operate on an origin value computed by the trusted background process, never one passed through from an untrusted RPC caller, mirroring the fix pattern from the source report (restrict privileged mutation to a trusted call path, analogous to adding `onlyOwner`).

### Proof of Concept
Not able to construct a concrete, working PoC with the retrieved code alone, since the actual message-origin binding point (background script handling of dApp `connect`/`enable` requests) was not found in the indexed files. A PoC would need to demonstrate that a webpage calling the injected provider's `connect()`/`enable()` can cause `connectedOrigins.add({ origin: <attacker-chosen>, trusted: true })` or `setAutoApprove({ origin: <attacker-chosen>, value: true })` to be invoked with an origin value it controls, rather than one enforced by the browser extension runtime.

    const value = await this.#getOrigin({ origin })

    if (!value) {
      return false
    }

    return value.trusted === undefined || value.trusted
  }

    const value = await this.#getOrigin({ origin })
    return value?.autoApprove || false
  }

#### Eagerly Connecting

After the user approves a Web3 site's connection to Exodus, the site becomes
trusted. This allows the site to automatically connect to Exodus on subsequent
visits or page refreshes. This is referred to as "eagerly connecting".

If you want to try to eagerly connect, you can pass the `onlyIfTrusted` option
to `connect()`.

```typescript
try {
  await window.exodus.solana.connect({ onlyIfTrusted: true })
} catch (err) {
  // { code: 4001, message: 'User rejected the request.' }
}
```

:::tip

When using this flag, Exodus will only connect if the site is trusted and won't
bother your users with a pop-up if they have not connected to Exodus before.

:::
