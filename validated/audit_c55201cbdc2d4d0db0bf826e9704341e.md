### Title
RAY debt-value overflow permanently freezes a large market before the borrow-index ceiling - (File: contracts/pool/src/interest.rs)

### Summary
A market whose scaled debt is large enough can reach a state where the next interest accrual overflows `i128` while calculating total debt, before `borrow_index` reaches its configured ceiling. Because every pool market mutation synchronizes interest before applying the requested operation, the failed accrual permanently blocks withdrawal, repayment, liquidation, bad-debt cleanup, recapitalization, parameter updates, and subsequent index updates for that market. [1](#0-0) [2](#0-1) 

### Finding Description
`global_sync` applies every elapsed accrual chunk before marking the market synchronized. [3](#0-2)  Each chunk calls `accrue_step`, which computes both the old and new aggregate debt as `borrowed * borrow_index`. [4](#0-3) [5](#0-4) 

Although `update_borrow_index` clamps the index to `MAX_BORROW_INDEX_RAY`, that clamp only bounds the index itself and does not ensure that `borrowed * index / RAY` remains representable in `i128`. [6](#0-5) [7](#0-6)  Once aggregate debt approaches the `i128` value boundary, increasing the index causes `new_total_debt` to panic with `MathOverflow`; subsequently, even the already accrued `old_total_debt` can overflow, leaving no successful accrual path. [8](#0-7) 

This is reachable through the permissionless controller maintenance path `update_indexes(caller, assets)`, which forwards caller-selected markets to the pool. [9](#0-8) [10](#0-9)  More importantly, the state can be created through ordinary user `supply` and `borrow` positions and then becomes unavoidable as time advances; no privileged call is required to trigger the accrual. [11](#0-10) 

### Impact Explanation
The affected market cannot process withdrawals or repayments because those paths load a synchronized market before mutating shares or cash. [1](#0-0)  Supplier funds and outstanding borrower collateral become permanently frozen at the contract level unless a contract upgrade introduces an overflow-safe accrual path, because `last_timestamp` is not advanced when the accrual panics. [3](#0-2) 

The repository’s long-horizon test demonstrates the failure mode: after a sufficiently large book accrues at high utilization, `update_indexes` returns `MathOverflow`, the borrow index remains below `MAX_BORROW_INDEX_RAY`, and subsequent withdrawal and repayment attempts fail with the same error. [12](#0-11) 

### Likelihood Explanation
The vulnerability requires a very large market and sustained interest accrual, so it is not triggerable at arbitrary scale on an ordinary small market. Nevertheless, admitted caps and index bounds do not jointly constrain `scaled_debt * borrow_index` to fit the `i128` result domain, and the documentation explicitly acknowledges that value overflow can occur before the index ceiling. [13](#0-12) 

Any caller may advance the market into the failing state by invoking `update_indexes`; an attacker does not need to own every supplied token because the calculation uses aggregate market debt rather than the attacker’s own position. [10](#0-9)  Once aggregate book size and elapsed time create the condition, the failed accrual is deterministic.

### Recommendation
Constrain scaled supply and debt such that the maximum possible index-scaled value remains representable for the whole configured index range, not merely at the current index. In particular, enforce market and position caps against a bound derived from `i128::MAX * RAY / MAX_*_INDEX_RAY`, or lower the index ceilings to match the maximum book sizes admitted by caps.

Additionally, make accrual fail safe before the computed debt value overflows: cap accrual to the largest representable index for the current aggregate scaled debt, emit a distinct state marker, and provide an owner-authorized recovery path that can settle or write down positions without first running the overflowing `calculate_supplier_rewards` calculation. Add a regression test asserting that every valid admitted market state can complete `update_indexes`, `repay`, `withdraw`, liquidation, and `update_params` through `MAX_BORROW_INDEX_RAY`.

### Proof of Concept
1. Configure or use a borrow-enabled market whose supply and borrow caps admit a very large aggregate book.
2. Call controller `supply(caller, account_id, spoke_id, [(BIG18, principal)])` to seed `principal` units of the market.
3. From a sufficiently collateralized account, call `borrow(caller, account_id, [(BIG18, debt)], None)` with `debt` near full utilization of that supply.
4. Allow enough ledger time to pass that `borrowed * next_borrow_index / RAY` exceeds `i128::MAX` while `next_borrow_index <= MAX_BORROW_INDEX_RAY`.
5. Call `update_indexes(caller, [BIG18])` from any authorized address. `global_sync` reaches `accrue_step`, and `calculate_supplier_rewards` panics in `borrowed.mul(env, new_borrow_index)` before the index clamp can provide a usable terminal state. [14](#0-13) [15](#0-14) 
6. Subsequent `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, and `update_indexes` attempts on that market all load through the same synchronization path and therefore fail before reaching their operation-specific guards. [1](#0-0) 
7. The existing regression test implements this scenario and observes `MathOverflow` on index update, withdrawal, and repayment while the borrow index remains below the configured ceiling. [12](#0-11)

```rust
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
```

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
