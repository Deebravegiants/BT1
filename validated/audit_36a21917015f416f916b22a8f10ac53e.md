Audit Report

## Title
Missing Allowlist/Rate-Limit Validation on Legacy Web API Gateway Trigger Messages Allows Unrestricted Fan-out to All DON Nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`handler.HandleLegacyUserMessage` in the Web API capabilities gateway handler is directly reachable from an unauthenticated-by-authorization HTTP client via `gateway.ProcessRequest`, and forwards the client-supplied request to every node in the DON without any sender/workflow allowlist check or per-caller rate limiting. The code contains an explicit unaddressed `// TODO: apply allowlist and rate-limiting here` comment immediately before the unconditional broadcast.

## Finding Description
`gateway.ProcessRequest` decodes an incoming JSON-RPC request and, for legacy requests carrying a `DonID`, only calls `msg.Validate()` before dispatching to `HandleLegacyUserMessage`: [1](#0-0) . `Message.Validate()` only checks field lengths/format and cryptographically recovers the signer address into `msg.Body.Sender` — it performs no authorization/allowlist lookup against that signer: [2](#0-1) .

Inside `HandleLegacyUserMessage`, the handler validates payload shape, timestamp/staleness, and method name, but the explicit TODO confirms the missing check, and the function proceeds to save a callback and unconditionally send the request to **every** DON member via `don.SendToNode`: [3](#0-2) .

The only rate limiter present in this handler (`h.nodeRateLimiter`) is applied exclusively to the reverse/outbound direction — messages initiated by DON nodes back out to external HTTP endpoints via `handleWebAPIOutgoingMessage` — not to this inbound user-triggered path: [4](#0-3) .

By contrast, the newer v2 HTTP trigger handler explicitly performs `authorizeRequest` and `checkRateLimit` before dispatch, confirming that these checks are considered a necessary security control for this class of request and are omitted only in the legacy path: [5](#0-4) .

## Impact Explanation
Any client able to produce a validly-signed (but otherwise unauthorized) message can submit a `web_api_trigger` legacy request targeting an arbitrary `DonID` and have it broadcast to all member nodes of that DON, with no check that the signer/workflow is entitled to trigger that DON. This enables unauthorized job/workflow triggering fan-out and creates a DoS vector against DON nodes, since the gateway does not throttle this inbound path at all. This maps to the in-scope "unauthorized job run" / "allowlist bypass" impact category for gateway request handling.

## Likelihood Explanation
The path is reachable directly through `gateway.ProcessRequest`, the top-level entrypoint for the gateway's HTTP server, requiring only a validly-formed signature (which any party with an ECDSA keypair can produce) and no confirmation that the specific signer is on any per-DON/per-workflow allowlist. The missing-check TODO in the source, combined with the demonstrably different (and more defensive) behavior in the v2 handler, indicates this is a genuine, currently-open gap in the legacy code path rather than an intentional design choice mitigated elsewhere in the reviewed code.

## Recommendation
Add caller/workflow authorization (allowlist check against `msg.Body.Sender`) and per-sender rate limiting inside `HandleLegacyUserMessage`, prior to storing the callback and calling `don.SendToNode`, mirroring the `authorizeRequest`/`checkRateLimit` pattern already implemented in `httpTriggerHandler.HandleUserTriggerRequest`. Reject unauthorized/non-allowlisted senders and enforce a quota before any fan-out to DON nodes.

## Proof of Concept
1. Craft a legacy JSON-RPC message with `Body.Method = "web_api_trigger"`, a valid `TriggerRequestPayload` (fresh `Timestamp`), and a target `DonID`, signed with an arbitrary/unauthorized keypair (satisfying only `Message.Validate()`'s format/signature-recoverability checks).
2. Submit it to the gateway's HTTP endpoint, which routes through `gateway.ProcessRequest` → `handler.HandleLegacyUserMessage` (exercised by the existing `TestHandlerReceiveHTTPMessageFromClient` test in `core/services/gateway/handlers/capabilities/handler_test.go`).
3. Observe the request passes payload/timestamp/method checks (no allowlist/rate-limit checks exist at the point marked by the `// TODO` comment at `handler.go:384`) and is forwarded via `don.SendToNode` to every entry in `h.donConfig.Members`, confirming any caller with a syntactically valid signature — authorized or not — can trigger fan-out to all DON nodes.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
