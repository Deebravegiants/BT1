### Title
Panic-based denial of service on the BEEFY SP1 consensus-update path via unchecked `try_into().expect(...)` conversions from attacker-controlled ABI proof fields - ([File: evm/rust/src/conversions.rs])

### Summary
`pallet-beefy-consensus-proofs::verify_and_apply` decodes a relayer-submitted `bytes` proof, ABI-decodes it into `ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof`, and converts it into the internal `Sp1BeefyProof` type via a `From` impl that uses `.try_into().expect("... out of bounds")` on several `U256`/large-integer commitment fields before any cryptographic (SP1 zkVM / signature) verification happens. Because these numeric fields are attacker-controlled ABI bytes, an out-of-range value causes a Rust panic instead of a typed error, aborting block execution/transaction validation — the same bug class as the reported GNU `patch` NULL-pointer/segfault issue (malformed input reaches unchecked code and crashes the process) but manifesting here as a `wasm`/runtime panic reachable through a single submitted proof.

### Finding Description
The call path is:

1. `Pallet::<T>::verify_and_apply(proof: &[u8])` — `modules/pallets/beefy-consensus-proofs/src/lib.rs:805-838` — decodes `proof_type` and ABI-decodes the payload:

2. The `.into()` call invokes `From<SP1BeefyProof> for Sp1BeefyProof`:
```rust

			mmr_leaf: value.mmrLeaf.into(),

``` [2](#0-1) 

`blockNumber` and `validatorSetId` are Solidity `uint256`/wide-integer ABI fields fully controlled by the submitter; converting them into a narrower type (`u32`/`u64`) with `.expect(...)` rather than a `map_err` produces a Rust panic on any out-of-range value (e.g., a value `> u32::MAX`). This happens *before* any SP1 zk-proof or authority-signature check, so it requires no valid consensus proof — only a syntactically valid ABI encoding with an oversized integer.

The same unchecked pattern recurs across the whole conversions module for the nested `mmrLeaf` (`From<BeefyMmrLeaf> for SpMmrLeaf`, `total_leaves`, `version`, `parentNumber`, authority-set `id`/`len`) and for `Commitment`/`Vote` used by the naive ECDSA BEEFY proof path as well (`From<Commitment> for SpCommitment`, `From<Vote> for SignatureWithAuthorityIndex`), all reached from the same `verify_and_apply` entrypoint via `From<BeefyConsensusProof> for ConsensusMessage`. [3](#0-2) 

This directly contradicts the pattern the rest of the codebase has been hardened to follow — e.g. GRANDPA's `RelayHeaderNotInUnknownHeaders` fix, the `as_utf8_string`/`StateMachine::from_str` fixes, and the BSC `parse_extra` BOHR-length fix all explicitly replaced `.expect`/panicking indexing on untrusted input with typed `Result` errors because such panics on the unsigned message-handling path can crash the node process. [4](#0-3) [5](#0-4) 

### Impact Explanation
`verify_and_apply` is invoked from the BEEFY consensus route which, per the runtime's `IsmpCallFilter`, is the mandated path for all BEEFY updates on Gargantua/Nexus (raw BEEFY updates through `pallet_ismp::handle_unsigned` are explicitly rejected in favor of this pallet). [6](#0-5) 
Any relayer/bridger — an unprivileged party — can submit a syntactically-valid but numerically out-of-range SP1 BEEFY proof and trigger a Rust panic mid-execution. Depending on where this executes (block-authoring runtime call vs. `validate_unsigned`/RPC dry-run), this is a wasm trap that aborts the extrinsic/host call, and in the worst case can be leveraged repeatedly to disrupt processing of the BEEFY consensus route that gates all cross-chain message delivery for that state machine — a denial-of-service against the primary bridging path (route unable to deliver messages), which the scan rules explicitly accept as in-scope impact.

### Likelihood Explanation
High: this requires only a single crafted transaction/extrinsic carrying an ABI-encoded `SP1BeefyProof` whose `commitment.blockNumber` or `commitment.validatorSetId` (or several other integer fields reachable via the same conversion chain) exceed the narrower target width. No signature, no valid SP1 proof, and no special privileges are needed to reach the panicking conversion, since the panics occur before verification.

### Recommendation
Replace every `.try_into().expect(...)` in `evm/rust/src/conversions.rs` (and any other `From`/`TryFrom` impl on this decode path) with fallible conversions that return a typed `ismp`/pallet error, mirroring the pattern already used elsewhere in the codebase (e.g. `map_err(|_| Error::<T>::AbiDecodeFailed)` or a dedicated `Error::IntegerOutOfBounds` variant), and propagate that error out of `verify_and_apply` instead of allowing a panic to unwind through pallet dispatch.

### Proof of Concept
1. Construct `SP1Beefy::SP1BeefyProof` ABI bytes where `commitment.blockNumber` (or `validatorSetId`) is set to a `U256` value `> u32::MAX` (or `> u64::MAX` as applicable to the target field width), with the remaining fields arbitrary/well-formed enough to pass ABI decoding.
2. Prefix with `types::PROOF_TYPE_SP1` and call the pallet's consensus-update extrinsic that ultimately calls `Pallet::<T>::verify_and_apply(&proof)` (as used in `modules/pallets/beefy-consensus-proofs/src/lib.rs`).
3. Observe that `abi_proof.into()` panics inside `From<SP1BeefyProof> for Sp1BeefyProof` at `evm/rust/src/conversions.rs:397-416` before any SP1/BLS verification is attempted, aborting the call instead of returning `Error::<T>::AbiDecodeFailed` or similar.

/// Gargantua routes all BEEFY consensus updates through `pallet-beefy-consensus-proofs`, which
/// requires each proof to pass SP1 zkVM verification before it can advance the BEEFY state.
/// Allowing raw updates through `handle_unsigned` would bypass that requirement entirely, so
/// any batch that carries a BEEFY consensus message is rejected here. `fund_message` is also
/// disabled because gargantua uses the bandwidth model for request fees; per-message top-ups
/// have no role in that accounting.
///
/// A consensus message only names the state it updates, so we ask the host which client owns
/// that state and compare against BEEFY. Reading from the host remains correct even as more
/// states (Polkadot, Paseo) are bound to the same client over time.
pub struct IsmpCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for IsmpCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		use ::ismp::{host::IsmpHost, messaging::Message};
		match call {
			RuntimeCall::Ismp(pallet_ismp::Call::fund_message { .. }) => false,
			RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages }) => {
				let host = Ismp::default();
				!messages.iter().any(|message| match message {
					Message::Consensus(consensus) =>
						host.consensus_client_id(consensus.consensus_state_id) ==
							Some(ismp_beefy::BEEFY_CONSENSUS_ID),
					_ => false,
				})
			},
			_ => true,
		}
	}
