## Analog Found

### Title
Permissionless native-fee swaps in `EvmHost.dispatch`/`fundRequest` and `IntentGatewayV2.placeOrder` execute Uniswap V2 swaps with no slippage bound, enabling MEV sandwich theft of the payer's native token - (File: `evm/src/core/EvmHost.sol`)

### Summary
Whenever a user pays Hyperbridge dispatch or intent-placement fees in native token, `EvmHost` and `IntentGatewayV2` route the payment through a live Uniswap V2 swap with a deadline of `block.timestamp` and no caller-supplied slippage/maximum-input bound. This is the same bug class as the referenced `FeePoolV0.distributeMochi` finding: a permissionless, unguarded AMM interaction that any address can trigger and that a searcher can sandwich to extract value from the transaction's own native-token payment.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all execute the identical pattern whenever `msg.value > 0`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    }
```

The same call shape recurs in `dispatch(DispatchGet)` and `fundRequest`: [2](#0-1) , and in `IntentGatewayV2.placeOrder`'s fee-escrow path: [3](#0-2)  (mirrored on the Tron variant at [4](#0-3) ).

These functions are the primary permissionless entry points into Hyperbridge messaging (`EvmHost.dispatch`) and the intent system (`IntentGatewayV2.placeOrder`) — reachable by any address that submits a transaction with `msg.value` set. Each call:
- Uses `block.timestamp` as the swap deadline, which offers zero protection: it is always satisfied at the moment of execution regardless of how long the transaction was delayed in the mempool.
- Places no bound on the effective price paid other than the caller's own `msg.value` cap. Since `swapETHForExactTokens` is an exact-output swap, the *output* (`post.fee` in feeToken) is fixed, but the *input* price the payer pays is fully exposed to the current pool state at execution time, with no explicit "maximum acceptable price" (i.e., no minimum-effective-price check) beyond the coincidental ceiling of whatever `msg.value` the caller happened to send.

The docs even acknowledge that Uniswap-derived pricing here is unsafe on-chain but only warn about the off-chain `quote()` helper, not about the on-chain swap itself: [5](#0-4) 

### Impact Explanation
A searcher observing a pending `dispatch`/`fundRequest`/`placeOrder` transaction with native-token payment can:
1. Front-run it with a large swap in the `WETH → feeToken` pool to spike the price.
2. Let the victim's `swapETHForExactTokens` execute — since it must still deliver the exact `post.fee` output, it consumes a disproportionately larger amount of the victim's `msg.value` in ETH at the manipulated price.
3. Back-run to reverse the price impact and realize the extracted ETH as profit.

The victim silently pays more native token than the fair market rate for the same fixed fee-token amount, transferring value directly to the attacker — the same theft-of-funds outcome described in the referenced `FeePoolV0.distributeMochi` report, just realized through an exact-output rather than exact-input AMM interaction. Because this pattern is embedded in the core dispatch path (`EvmHost.dispatch`, used by every app built on Hyperbridge) and in `IntentGatewayV2.placeOrder` (used by every intent order paying fees in native token), the blast radius covers essentially all native-token fee payments across the protocol.

### Likelihood Explanation
- The functions are fully permissionless and callable by any externally owned account or contract.
- No privileged role, governance action, or malicious insider is required — any ordinary user paying dispatch/order fees in native token is exposed purely by using the documented "Native Token Payment" flow.
- Sandwich/MEV extraction against unprotected Uniswap V2 interactions is a well-understood, automatable, and continuously profitable attack pattern for MEV searchers, making exploitation highly likely whenever meaningful native-token volume flows through these paths.

### Recommendation
Add an explicit maximum native-input bound (or equivalently, a caller-supplied acceptable price/slippage tolerance) to every on-chain swap invoked from `EvmHost.dispatch`, `EvmHost.fundRequest`, and `IntentGatewayV2.placeOrder`, so the transaction reverts rather than silently overpaying when the pool has been manipulated. Replace the `block.timestamp` deadline with a caller-supplied deadline that meaningfully bounds execution delay, and/or price the swap against a manipulation-resistant reference (e.g., a short TWAP or oracle price, as already done in `SimplexPaymaster.swapAndDeposit`'s oracle-derived `amountOutMin` check) before allowing the AMM swap to proceed. [6](#0-5) 

### Proof of Concept
1. Attacker monitors the mempool for a `EvmHost.dispatch(DispatchPost)` (or `fundRequest`/`IntentGatewayV2.placeOrder`) call with `msg.value > 0`.
2. Attacker front-runs with a large `WETH → feeToken` sell (or `feeToken → WETH` buy, depending on pool direction) to move the pool price against the victim.
3. Victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)` — since `block.timestamp` at execution always satisfies the deadline check, and there is no explicit `maxNativeIn` check beyond `msg.value`, the swap succeeds while consuming far more ETH than the pre-manipulation fair price for the same `post.fee` output.
4. Attacker back-runs to restore the pool price and unwind their position, capturing the ETH difference as profit — funds that should have remained with (or been refunded to) the original dispatcher/order-placer.

    function swapAndDeposit(address token, uint256 amountIn) external {
        if (msg.sender != treasury) revert UnauthorizedCall();
        address router = IDispatcher(host()).uniswapV2Router();
        if (router == address(0)) revert InvalidRouter(router);
        TokenConfig memory cfg = tokenConfigs[token];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(token);

        uint256 balance = IERC20(token).balanceOf(address(this));
