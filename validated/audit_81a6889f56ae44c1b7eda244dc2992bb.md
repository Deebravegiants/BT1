Audit Report

## Title
Unprivileged users can DOS the Gateway and DON nodes via unrestricted `web_api_trigger` legacy messages - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`gateway.ProcessRequest` routes any legacy JSON-RPC request carrying a `DonID` to `handler.HandleLegacyUserMessage` after only signature-format validation (no allowlist check) via `msg.Validate()`. Inside `HandleLegacyUserMessage`, the only checks are payload decode, non-zero timestamp, and staleness — the code explicitly marks the allowlist/rate-limit step as an unimplemented `// TODO` before fanning the message out to every DON member and storing a callback.

## Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:253-272`) calls `msg.Validate()` for legacy requests, which only checks field lengths/format and recovers a signer address from the ECDSA signature (`core/services/gateway/api/message.go:54-88`) — it does not check that the recovered signer is a member of any allowlist, permissioned workflow owner, or subscriber list. Since generating an ECDSA keypair and signing a message is free and instantaneous, this "signature" check provides no meaningful admission control against an unprivileged/anonymous attacker.

Inside `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-420`), after payload decode and staleness checks, the code contains an explicit `// TODO: apply allowlist and rate-limiting here` comment, and no allowlist or per-sender rate limiter is invoked before the message is forwarded via `don.SendToNode` to every DON member and a callback entry is stored in `h.savedCallbacks`, bounded only by `MaxSavedCallbacks`/pruning rather than by rejecting requests up front.

This asymmetry is corroborated by the node-message path `handleWebAPIOutgoingMessage`, which does call `h.nodeRateLimiter.Allow(nodeAddr)` before processing (`core/services/gateway/handlers/capabilities/handler.go:164-168`), and by the newer v2 HTTP trigger handler which enforces `authorizeRequest`/JWT and `checkRateLimit`. The gap is also acknowledged directly in the test suite via the comment `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` (`handler_test.go:365`). The HTTP server layer itself (`core/services/gateway/network/httpserver.go:211-218`) enforces only a max-request-size limit, with no per-client rate limiting, so no other layer compensates for this gap.

## Impact Explanation
An unprivileged, unauthenticated client (only needs to generate a throwaway ECDSA keypair, which is free) can generate unlimited well-formed `web_api_trigger` legacy requests and flood the gateway and every node in the targeted DON. This causes unbounded fan-out to `don.SendToNode` for every DON member per request, uncontrolled growth of the `savedCallbacks` map (up to `MaxSavedCallbacks`, default 20000), and consumption of DON node processing capacity — a legitimate availability/DOS impact on the gateway's internet-facing user endpoint, in the same spirit as unauthenticated resource-exhaustion bugs in scope for node/gateway availability.

## Likelihood Explanation
High. No credential, role, or prior relationship with the DON/gateway operator is required — an attacker only needs to construct a syntactically valid legacy message (any DonID that maps to a configured handler, `Method: "web_api_trigger"`, and a fresh `Timestamp`) and sign it with a self-generated key. This is fully repeatable and can be automated to produce sustained request volume with no built-in throttling in this code path.

## Recommendation
Implement the allowlist and rate-limiting logic referenced by the TODO in `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go`) prior to storing the callback and forwarding to `don.SendToNode`, mirroring the `authorizeRequest`/`checkRateLimit` pattern in the v2 HTTP trigger handler and the `nodeRateLimiter.Allow` pattern used for node-originated messages. At minimum, add per-sender and global rate limiting plus a sender/workflow-owner allowlist check before doing any DON fan-out.

## Proof of Concept
1. Generate an arbitrary ECDSA keypair (no privilege required).
2. Construct a legacy `api.Message` with a valid `DonID` (matching a configured handler), `Method: "web_api_trigger"`, a `TriggerRequestPayload` with a current `Timestamp`, and sign it with the generated key (as done in `newSignedLegacyRequest` in `gateway_test.go:440-458`).
3. POST the encoded request repeatedly to the gateway's user-facing HTTP endpoint (`ProcessRequest` → `HandleLegacyUserMessage`).
4. Observe requests pass validation and are forwarded to every DON member via `don.SendToNode` with no rejection, and callback entries accumulate in `h.savedCallbacks`, demonstrating unthrottled resource consumption. A Go integration/unit test extending `TestHandlerReceiveHTTPMessageFromClient` (`handler_test.go`) to send many distinct signed messages in a loop and assert no rejection/throttling occurs would concretely prove this.
