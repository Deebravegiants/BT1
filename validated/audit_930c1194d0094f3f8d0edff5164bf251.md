### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by the host application's handler come from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands the handler a `WebhookMetadata` object built with `shop: request.shop`, so any header value that survives HMAC validation is trusted as the tenant identifier even though it was never part of what the HMAC signed.

### Finding Description
`to_signable_string` in `Request` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e., against the body only) and then dispatches the handler using `request.shop` as the tenant identifier taken from the unauthenticated header: [3](#0-2) 

This is the same bug class as the Astaria `M-25` report: a value that is *acted on* (there, `duration`/`firstBidTime`; here, `shop`) is not actually covered by the mechanism meant to bind/authenticate it (there, the duration-extension arithmetic; here, the HMAC signature). The equality that should hold — "HMAC-verified bytes == bytes the app trusts for tenant identity" — is broken: HMAC verifies `raw_body` only, but the app trusts `shop` from a header outside that scope.

Because the app's `client_secret`/`api_secret_key` is shared across **all shops that installed the app**, not per-merchant, any merchant who has installed the app can legitimately receive a validly-signed webhook (valid HMAC over some body) for their own shop, then replay that same body with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header naming a different merchant. The HMAC check in `HmacValidator.validate` still passes because the header is not part of `to_signable_string`, and `Registry.process` forwards the attacker-chosen `shop` value to the handler unmodified.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to look up or scope tenant data (session/store lookup, feature-flags, order/customer records, billing, etc. — the intended and documented use of this field), an attacker who controls one legitimate shop installation can inject data attributed to a different, unrelated shop. This is a cross-tenant integrity issue: data meant for shop A can be forged and delivered as if it belonged to shop B, without any credentials beyond the attacker's own (legitimately obtained) webhook deliveries. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) installs on multiple shops (nearly all public/embedded apps), and (b) trusts `WebhookMetadata#shop` for tenant scoping, which is the documented, intended use of the field. No access token, api_secret_key leak, or privileged access is required — only that the attacker controls one shop's own installation and can send an HTTP request to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string (or otherwise cryptographically bind them, e.g., signing a canonical representation of headers + body), so any header tampering invalidates the HMAC. At minimum, `to_signable_string` should not silently exclude fields that downstream code treats as authenticated/trusted identity data.

### Proof of Concept
1. App is installed on Shop A and Shop B (attacker controls Shop A's admin/store, a legitimate action).
2. Shopify sends a real webhook to the app for Shop A, with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and body `B`.
3. Attacker intercepts/replays this request to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `shop-b.myshopify.com`, leaving body `B` and the HMAC header untouched.
4. `Utils::HmacValidator.validate` recomputes HMAC over `request.to_signable_string` (`@raw_body` only, per `lib/shopify_api/webhooks/request.rb:35-38`) — it matches, since the body wasn't changed.
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "shop-b.myshopify.com"` (per `lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the handler, which now processes attacker-supplied data under Shop B's identity.
