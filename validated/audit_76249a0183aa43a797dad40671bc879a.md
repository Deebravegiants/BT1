### Title
Cross-tenant webhook impersonation via unauthenticated `shop-domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never included in the signed payload. Because the signature only binds the body, an attacker who has ever received one legitimate, correctly-signed webhook for their own (attacker-owned) shop can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to name a victim shop. The signature still verifies, and the app's webhook handler is invoked believing the event belongs to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an untrusted header, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body), never over the shop header: [3](#0-2) 

`Registry.process` gates on that HMAC check and then dispatches the handler using `request.shop`, the unauthenticated header value: [4](#0-3) 

The identity binding that should hold is: `hmac-verified bytes == the shop attributed to those bytes`. Instead, the gem verifies "bytes = body" but acts on "shop = header," which are two independent channels. Anyone who has legitimately received a signed webhook for their own store (a normal, unprivileged app-installer) possesses a valid `(raw_body, hmac)` pair they can replay against the app's public webhook endpoint with an arbitrary `shop-domain` header, since nothing ties the header to the signature.

### Impact Explanation
This breaks the shop/tenant boundary the HMAC is supposed to enforce: an attacker can make the app believe a webhook event (order created, app uninstalled, customer data changed, etc.) originated from a shop they don't control. Any host application logic that trusts `WebhookMetadata#shop` to select the target tenant's session/data (e.g., to look up the shop's session, update tenant-scoped records, or trigger uninstall/cleanup flows) can be manipulated to act against a victim tenant using attacker-supplied (though structurally valid) body content. This is a cross-tenant access primitive achieved purely as an unprivileged internet user with no access to `api_secret_key`, satisfying the "Critical – cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high: no secret material is required. An attacker only needs to install the app on any shop they control (a normal, permitted, unprivileged action) to legitimately receive one signed webhook, then can replay it indefinitely against the same public callback URL with a forged `shop-domain` header for any target myshopify domain.

### Recommendation
Bind the shop identity to the signed payload before trusting it: either compute the HMAC over a signable string that includes the shop domain, or (matching Shopify's documented model) never trust the shop header alone — instead cross-check it against a shop identifier embedded in and covered by the signed body/topic, or resolve the shop from an app-owned session store keyed by data that is itself HMAC-covered. At minimum, the header-derived `shop` must never be treated as authenticated by `HmacValidator.validate`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture one legitimate delivered webhook, e.g. `orders/create`, with headers `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and raw body `B`.
2. Replay an HTTP POST to the app's webhook endpoint with the same raw body `B` and `X-Shopify-Hmac-Sha256: <H>`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over `B` only and succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though the payload content and hmac originated from the attacker's own store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
