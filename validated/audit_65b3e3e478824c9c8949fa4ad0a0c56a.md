### Title
Webhook tenant identity (`shop`) is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once the HMAC over the raw body validates, and then dispatches to the handler using the `shop` value read from an unauthenticated header. Because the HMAC signing key (the app's `client_secret`) is shared across every shop that installs the app, and the signature only covers the body — not the `shopify-shop-domain` header — a party that legitimately receives one valid signed webhook for their own shop can replay that exact `(body, hmac)` pair while substituting an arbitrary `shopify-shop-domain` value, and the gem will accept it as an authentic webhook for that other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body, and `hmac`, `topic`, `shop`, `api_version`, `webhook_id` are all parsed straight from HTTP headers outside of that signed value: [1](#0-0) [2](#0-1) 

`Registry.process` validates only that HMAC-over-body against the app's own `Context.api_secret_key`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the tenant identity handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`compute_signature` only ever hash `verifiable_query.to_signable_string` (the body) with the app-wide secret — nothing ties the signature to a specific shop: [4](#0-3) 

The documented integration pattern reinforces the false assumption that passing HMAC validation proves the request "did indeed come from Shopify" for the shop indicated in the headers: [5](#0-4) 

and the handler contract explicitly surfaces this unauthenticated `shop` field as the per-tenant identity for app logic to key on: [6](#0-5) 

Since the same `api_secret_key` is used to sign every shop's webhooks for a given app (it is the app's `client_secret`, not a per-shop secret), the binding the gem should enforce — *"the shop the HMAC was computed for" == "the shop attributed to the request by the gem"* — never actually holds. Anyone who can obtain one genuinely signed `(raw_body, hmac)` pair (e.g., their own shop installs the app and Shopify delivers a real webhook to them, or the raw body/hmac leak via logs/network capture) can POST that same body+hmac to the app's webhook endpoint with a forged `shopify-shop-domain` header for a victim shop. `Registry.process` will validate the HMAC successfully (it never looks at the shop header) and hand the attacker-chosen body to the handler labeled as coming from the victim's shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: it allows cross-tenant data injection, i.e., an unprivileged installer of the app can cause the app to process attacker-controlled webhook payloads under a different, arbitrary shop's identity. Any host application that stores/updates per-shop state (e.g., order/product data, revoking a shop, updating billing) driven directly by `WebhookMetadata#shop` inherits a cross-tenant write/reads primitive purely from data delivered through this gem's documented `Registry.process` flow.

### Likelihood Explanation
Exploitability requires only: (1) an attacker to install the target app on their own shop (a normal, unprivileged action available to anyone) to obtain a genuinely-signed webhook body/hmac pair for a topic they control (e.g., `app/uninstalled`, or any topic whose body content they can influence), and (2) the ability to POST to the target app's public webhook endpoint with a modified `shopify-shop-domain` header — no secrets, tokens or elevated privileges are needed. This is reachable purely through the gem's documented `Registry.process`/`HmacValidator` code path.

### Recommendation
Bind the shop identity into the value that is actually verified. Either:
- Include the `shopify-shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in `Webhooks::Request#to_signable_string` so they are covered by the HMAC, or
- Cross-check `request.shop` against a shop known to be associated with the currently configured `api_secret_key`/session before invoking the handler, or
- Document loudly, and enforce in `Registry.process`, that `shop` must be independently reconciled by the caller against a registered/installed shop list before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, causing Shopify to deliver a real webhook, e.g. topic `app/uninstalled`, with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `client_secret`.
2. Attacker captures the exact `raw_body` and `hmac` value from that delivery (via their own logs, or by controlling the webhook body content ahead of time for a topic they can trigger).
3. Attacker (or anyone with network access to the app's public webhook route) sends a POST to the app's webhook endpoint with the same `raw_body`/`X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` and matches — validation succeeds: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host application processes/attributes the forged payload as belonging to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
