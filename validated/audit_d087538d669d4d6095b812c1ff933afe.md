### Title
Gateway Re-registration via `NewDeployment` Permanently Strands In-Flight Escrow Settlement Messages - ([File: evm/src/apps/intentsv2/IntentsBase.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2` authenticates incoming `RedeemEscrow`/`RefundEscrow` settlement messages by checking that the message's sender (`request.from`) equals the single address currently stored in `_instances[keccak256(sourceChain)]` [1](#0-0) . When Hyperbridge governance dispatches a `NewDeployment` message to rebind that pointer to a new gateway address on the source chain, `_addDeployment` overwrites the mapping in place with no transition window [2](#0-1) . Any `RedeemEscrow`/`RefundEscrow` message that was already dispatched by the *old* gateway instance but has not yet been delivered/relayed at the moment of rebinding will permanently fail authentication once it finally arrives, because `_instance(request.source)` now resolves to the new address while `request.from` still carries the old one.

### Finding Description
This mirrors the "Owner-Controlled State Transitions Can Destroy Existing User Entitlements" bug class exactly: a single mutable authorization pointer (`raffleContract` in the external report, `_instances[stateMachine]` here) is rebound by a privileged, legitimate control-plane action, and any value tied to the pre-transition address (unfilled raffle rounds / in-flight escrow settlement messages) becomes permanently unauthorized and undeliverable.

Concretely:
1. A solver fills a cross-chain order on the destination chain, delivering output tokens to the beneficiary and dispatching a `RedeemEscrow` POST request back to the source chain via Hyperbridge [3](#0-2) . Prior to delivery, relayer/challenge-period latency is normal and unavoidable.
2. Before this message is relayed and accepted on the source chain, Hyperbridge governance issues a `NewDeployment` request updating `_instances[keccak256(sourceOrDestChain)]` to a new gateway address (e.g. after redeploying/migrating the destination gateway) [2](#0-1) .
3. When the relayer eventually delivers the pending `RedeemEscrow`/`RefundEscrow` message, `onAccept` calls `_authenticate`, which compares `request.from` (the *old* gateway address that actually dispatched it) against `_instance(request.source)` (now the *new* address) [4](#0-3) . The comparison fails and the call reverts with `Unauthorized`.
4. There is no fallback: the pointer holds exactly one address per state machine, there is no grace window allowing both old and new instances, and the message cannot be "re-dispatched" from a different `from` address since `from` is fixed to the sender contract at dispatch time. The escrowed input tokens on the source chain (for `RedeemEscrow`, owed to the solver; for `RefundEscrow`, owed to the user) become permanently unreachable through the only settlement path the contract exposes.

### Impact Explanation
This causes concrete, permanent loss of already-earned value for an unprivileged actor (the solver who filled the order, or the user awaiting a cancellation refund) whenever a legitimate/ordinary governance re-registration of a gateway instance races with in-flight settlement messages. The solver has already delivered real output tokens to the user in good faith and dispatched the settlement message; a subsequent, routine `NewDeployment` re-registration (not a malicious act) can strand that solver's entitled escrow release forever, since the message can never re-authenticate. This is a permanent freezing of funds tied to a single point-in-time authorization pointer, directly analogous to the raffle-rebinding path in the referenced report.

### Likelihood Explanation
Triggering requires an ordinary governance operation (`NewDeployment`, used whenever a gateway is redeployed/migrated for a state machine) to occur while at least one `RedeemEscrow`/`RefundEscrow` message dispatched by the outgoing instance is still in flight (dispatched but not yet delivered/finalized through the relayer/challenge-period pipeline). Given that cross-chain settlement already takes measurable time (consensus finality + challenge period + relayer delivery), and gateway migrations are an expected part of the protocol's operational lifecycle, this race is realistically triggerable without any malicious behavior — it is a routine deployment hazard rather than a contrived edge case.

### Recommendation
Do not overwrite the single `_instances[stateMachine]` pointer atomically. Instead:
- Maintain a set (or history) of previously valid gateway addresses for each state machine and authenticate `RedeemEscrow`/`RefundEscrow` against any address ever registered for that state machine, or
- Require a settlement-drain/quiescence period before finalizing a `NewDeployment` rebind — i.e., stage the new address and only retire the old one once all outstanding settlement messages dispatched under it have cleared, and
- Add regression tests that dispatch a `RedeemEscrow`/`RefundEscrow` from a since-rebound gateway address and assert it still settles rather than permanently reverting.

### Proof of Concept
1. Deploy `IntentGatewayV2` instance `A` on destination chain `D`, registered in `_instances` on source chain `S` at address `A`.
2. A solver fills a cross-chain order on `D`; `_fillCrossChain` dispatches a `RedeemEscrow` PostRequest with `from = A` targeting `S` [3](#0-2) .
3. Before the relayer delivers this message to `S`, Hyperbridge governance dispatches a `NewDeployment` message rebinding `S`'s view of `D`'s gateway to a new address `B` (e.g. after a gateway migration): `_addDeployment` sets `_instances[keccak256(D)] = B` [2](#0-1) .
4. The relayer now delivers the original `RedeemEscrow` message (`from = A`) to `S`. `onAccept` → `_authenticate` computes `_instance(D) == B`, compares against `module == A`, and reverts with `Unauthorized` [5](#0-4) [4](#0-3) .
5. The message can never be resubmitted with `from = B` (it was genuinely dispatched by `A`), so the escrowed input tokens on `S` for that order commitment remain locked with no valid redemption path — a permanent freeze of the solver's earned funds.

     * @dev Authenticates an incoming cross-chain post request by verifying that the
     * sender module matches the registered gateway instance for the source chain.
     * Reverts with InvalidInput if the sender address is malformed, or Unauthorized
     * if the sender is not the expected gateway.
     * @param request The incoming post request to authenticate.
     */
    function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }
