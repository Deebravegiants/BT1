### Title
Webhook shop identity not bound by HMAC, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate(request)` passes, then dispatches `request.shop` to the app's handler as the trusted tenant identifier. However, the HMAC only signs the raw request body; the `shop` value (and `topic`, `webhook_id`, `api_version`) are taken from HTTP headers that are completely outside the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes the HMAC exclusively over this signable string and compares it to the `hmac-sha256` header [4](#0-3) . Meanwhile `shop` is read from `shopify-shop-domain`/`x-shopify-shop-domain` [2](#0-1) , a plain header with no cryptographic tie to the HMAC.

`Registry.process` uses this unbound `shop` value directly to build `WebhookMetadata` passed to the app's handler once HMAC validation of the body succeeds [3](#0-2) . The library's contract for this method is that a caller can trust the metadata (including `shop`) once `process` doesn't raise. That is false: the equality the library should — but does not — enforce is `hmac_verified_shop == request.shop`. Instead it verifies `hmac_verified_bytes == raw_body` and separately trusts `request.shop`, an unauthenticated header, as if it were bound to the same signature.

Because `api_secret_key` is a single, app-wide secret (not per-shop) held in `Context`, any body/HMAC pair that is valid for one installed shop of the app is *also a valid HMAC for the same body regardless of which shop-domain header accompanies it* — the signature computation never consults `shop` at all. An entity that controls a shop where the app is installed (an unprivileged internet user, from the app's perspective, since app installation itself requires no special privilege) can trigger a webhook delivery for their own store, capture the resulting `(raw_body, hmac-sha256)` pair, and replay it to the same webhook endpoint with the `shop-domain` header rewritten to a victim shop that has also installed the app. `Registry.process` will accept the request as valid (the HMAC check only covers the untouched body) and hand the handler a `WebhookMetadata` claiming the data originated from the victim shop, even though it factually did not.

### Impact Explanation
This breaks the tenant-identity boundary the gem is supposed to provide for webhook processing: `hmac_valid(body) == true` is treated by callers as proof that `(body, shop)` jointly originated from Shopify for that shop, when in fact only `body` is proven. Any host application that persists webhook payloads keyed by `WebhookMetadata#shop` (the pattern documented and exercised in `lib/shopify_api/webhooks/webhook_handler.rb` and the webhook docs) can have data cross-attributed to the wrong merchant — a cross-tenant data integrity/confidentiality violation.

### Likelihood Explanation
Requires only that the attacker's own shop have the target app installed (a normal Shopify merchant relationship — no `client_secret`, access token, or privileged account needed) and the ability to submit an HTTP request with attacker-controlled headers to the app's known webhook endpoint. No cryptographic secret needs to be broken because the shop attribute was never signed in the first place.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, or otherwise cryptographically bind the shop-domain header to the verified body before it is exposed to consumers as `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a body they fully control.
2. Shopify delivers `POST /webhooks` with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
3. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks the body [5](#0-4) ; `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [3](#0-2) , causing the attacker-controlled payload to be processed/stored under the victim's tenant.
