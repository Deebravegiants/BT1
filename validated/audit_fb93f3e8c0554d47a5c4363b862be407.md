### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook exclusively by validating the HMAC of the **raw body**. The `shop-domain` header — which is handed to the app's webhook handler as the authoritative tenant identifier — is never included in the signed payload and is therefore never authenticated. Any party who can obtain one genuine, HMAC-signed webhook body for *any* shop on the same app can replay it with a forged `shop-domain` header, causing the app to process/attribute that payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, reads directly and unconditionally from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is attacker-controllable and not part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` performs exactly this HMAC check and then, without any further binding, hands `request.shop` to the registered handler as the trusted tenant identity for the webhook: [4](#0-3) 

This is the same bug class as the analog report: a field that is *acted on* by downstream logic (`shop`, used as the tenant/session key by the handler) is not covered by the integrity check (`HMAC` over `raw_body` only). The equality the code implicitly assumes —

`shop authenticated by HMAC == shop delivered to handler (WebhookMetadata#shop)`

— does not hold, because the left-hand side is empty (the HMAC says nothing about the shop) while the right-hand side is taken verbatim from an unauthenticated header.

### Impact Explanation
Because the app's HMAC secret (`api_secret_key`) is shared across every shop that has installed the app, a genuine webhook body/HMAC pair obtained for one shop is cryptographically valid material regardless of which shop it's replayed against — the signature never encodes shop identity. An attacker who legitimately installs the app on their own shop can:
1. Trigger a webhook (e.g., `products/update`) whose body content they control to some degree (title, note fields, etc.).
2. Capture the resulting `raw_body` and `x-shopify-hmac-sha256` value that Shopify sends to the app's own webhook endpoint.
3. Replay that exact body + HMAC to the app's webhook endpoint, but with the `x-shopify-shop-domain` header set to a victim shop.

`Registry.process` will accept this as valid (the HMAC check only validates the body) and dispatch it to the handler with `WebhookMetadata#shop` set to the victim shop's domain. If the host application (as most Shopify apps do) uses `data.shop` to look up per-tenant records, access tokens, or to persist data, this leads to cross-tenant data injection/corruption — data nominally belonging to shop A is written into or attributed to shop B's tenant space, entirely from the perspective of an unprivileged party who only controls their own shop.

### Likelihood Explanation
Any merchant who installs the app (no special privilege beyond ordinary app installation) can generate legitimate signed webhook payloads for their own shop and replay them with a modified header value; no access to `api_secret_key` or any Shopify credential belonging to the victim is required. The vulnerable code path (`Registry.process` → handler) is the exact, documented flow every consumer of this gem's webhook API is expected to use, so it is directly reachable rather than requiring the host app to deviate from documented usage.

### Recommendation
Bind the header-derived shop domain to something authenticated before it is trusted:
- Do not treat `request.shop` as authoritative. Where possible, cross-check it against the shop associated with the session/access-token context used to register the webhook subscription, or
- Extend `to_signable_string`/the HMAC computation to include the `shop-domain` (and `topic`/`webhook-id`) headers if Shopify's webhook contract supports it, or otherwise explicitly document that `WebhookMetadata#shop` is unauthenticated and must be independently verified by the host application before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a webhook receiver they control (e.g. a request-logging proxy) for `products/update`.
2. Attacker triggers a `products/update` event on their own shop, capturing the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify computed with the app's shared `api_secret_key`.
3. Attacker sends a POST request directly to the app's real webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured, still-valid HMAC
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - `x-shopify-topic`: `products/update`
   - body: the unmodified captured `raw_body`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body/HMAC pair.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes attacker-supplied data as though it originated from `victim-shop`, e.g. persisting or updating records under the victim's tenant key.
