### Title
Webhook `shop` Field Is Not Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Any party that possesses one valid `(raw_body, hmac)` pair for their own shop can replay it with an arbitrary `shop` header value and the request will still pass HMAC validation, letting them attribute a forged webhook to a different tenant.

### Finding Description
`Registry.process` authenticates a webhook solely via: [1](#0-0) 

which calls `HmacValidator.validate(request)`, and `HmacValidator` computes the signature only over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns nothing but the raw body: [3](#0-2) 

while `shop` is read straight from an attacker-controllable HTTP header, entirely outside the signed bytes: [4](#0-3) 

The verified equality the gem implicitly claims is "HMAC-authenticated bytes == the tenant (shop) the webhook is attributed to." In reality the HMAC only proves "the body bytes are unmodified"; it says nothing about the `shop` header. `Registry.process` nonetheless forwards this unauthenticated header value straight to the app's webhook handler as the trusted tenant identifier: [5](#0-4) 

This is exactly the documented, intended usage of the gem — the docs tell integrators to trust `data.shop` as "The shop domain of the webhook" and to key downstream processing on it (e.g. `shop_domain: data.shop`): [6](#0-5) 

By contrast, the OAuth callback binds `shop` into the signed content (`AuthQuery#to_signable_string` includes `shop`): [7](#0-6) 

showing the library is capable of, and elsewhere does, bind the shop identity into the signature — but omits this for webhooks.

### Impact Explanation
Any unprivileged user who legitimately installs the app on their own shop can capture one authentic `(raw_body, hmac)` pair generated by Shopify for their own tenant, then replay that exact body+signature to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still passes because it never inspects the header. The host application, following the gem's documented contract, then processes/persists that payload as belonging to the victim shop, i.e. a cross-tenant data-injection/cross-tenant access vulnerability — the strongest reachable, in-scope impact category for this bug class.

### Likelihood Explanation
Any app that lets an attacker install it on their own shop (a normal, self-service Shopify app installation, no special privilege needed) gives that attacker a valid signed payload for arbitrary bodies they control (they can trigger e.g. `orders/create` webhooks on their own store to get an HMAC over content of their choosing). Combined with the fact that only the body — never the shop header — is verified, exploitation only requires basic HTTP tooling and no credentials beyond normal self-service app installation.

### Recommendation
Bind the `shop` (and ideally `webhook_id`/`topic`) value into the signed content that `HmacValidator` verifies for webhook requests — e.g., include the shop domain header value in `Webhooks::Request#to_signable_string`, or independently verify `request.shop` against the shop associated with the offline/online session used to register the webhook subscription before invoking the handler.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com` and register a webhook (e.g. `orders/create`).
2. Trigger the webhook; capture the raw POST body `B` and the `shopify-hmac-sha256` header `H` that Shopify computed with the app's real `client_secret`.
3. Replay the exact same body `B` and header `H` to the app's webhook endpoint, but replace `shopify-shop-domain: attacker.myshopify.com` with `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and `Registry.process` accept the request because `HmacValidator.validate` only recomputes the HMAC over `B`, which is unchanged; the handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)` per [8](#0-7) , causing attacker-controlled data to be processed under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
