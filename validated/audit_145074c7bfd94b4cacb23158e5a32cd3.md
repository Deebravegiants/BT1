### Title
Webhook `Request` binds only the raw body to the HMAC while `shop`, `topic`, and `webhook-id` are trusted unsigned — cross-tenant webhook spoofing (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` verifies solely the request body, never the `shop`, `topic`, or `webhook-id` header values [1](#0-0) . `Registry.process` trusts `request.shop` as the tenant identity passed to the app's handler after only validating that HMAC [2](#0-1) . This breaks the identity binding `authenticated_body == (shop, topic, webhook_id)_used_downstream`.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the presented HMAC [3](#0-2) . For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body` [1](#0-0) , so the signature attests only to the body bytes. The `shop` (`shop-domain` header), `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers [4](#0-3) .

`Registry.process` validates the HMAC and then, without any further check that the `shop` header is bound to the signed content, dispatches the handler with `shop: request.shop` taken directly from that header [2](#0-1) .

Because webhook HMAC secrets for a multi-tenant app are the app's single `client_secret` (shared across every merchant install), any merchant who has installed the app can obtain a body+HMAC pair that Shopify legitimately signed for their own store's webhook event. That merchant can then replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks `@raw_body`, and `Registry.process` hands the handler `shop: <victim-shop>` together with the attacker-supplied body content, i.e. `authenticated_shop != shop_used_by_the_app`.

### Impact Explanation
This is a cross-tenant identity-binding break: the app's webhook handler is invoked believing the delivered data came from `victim-shop`, when the HMAC only ever authenticated a body an attacker-controlled merchant could legitimately generate for their own shop. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop billing/inventory/customer records, `shop/redact`-style GDPR flows, or shop-scoped audit trails) can be corrupted or targeted for a shop the attacker does not control, which constitutes cross-tenant access/data corruption through the gem's own trust boundary.

### Likelihood Explanation
The attacker needs no privileged credentials beyond installing the target app on their own store (a normal, unprivileged capability for any public app) and the ability to send an HTTP POST with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or other secret is required — the only "credential" needed (a valid HMAC over a chosen body) is obtained for free by being a legitimate, if malicious, install of the same app.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values inside the signed payload used for verification (or otherwise cryptographically bind them to the delivery, e.g. by requiring the app to look up/confirm the destination shop separately from the header), rather than trusting `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers that fall outside `to_signable_string`.

### Proof of Concept
1. Attacker installs the target multi-tenant app on their own store `attacker-shop.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures one such delivery: raw body `B` and header `x-shopify-hmac-sha256` = `H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the headers, `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`to_signable_string` returns `@raw_body`) and it matches `H`, so validation passes [1](#0-0) .
5. `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though the data never originated from `victim-shop` [5](#0-4) .
