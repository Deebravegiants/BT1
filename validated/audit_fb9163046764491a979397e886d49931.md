### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, and that validator computes the HMAC over `request.to_signable_string`, which is defined as just the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to application code as trusted identity come from HTTP headers that are never included in the signed bytes, so the HMAC "verifies the body" but the gem still treats the header-derived `shop` as if it had been "verified as coming from Shopify."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, which are outside the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then forwards `request.shop` straight into `WebhookMetadata`, which is passed to the app's handler as trusted, verified data: [3](#0-2) 

The `HmacValidator` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e. against the raw body, never the shop-domain header: [4](#0-3) 

The gem's own documentation asserts that calling `Registry.process` "will verify the request did indeed come from Shopify" and hands the app the `shop` field as part of that verified `WebhookMetadata`: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `bytes covered by HMAC (raw_body)` ≠ `bytes that determine tenant identity (shop-domain header)`. Because the shop-domain header is not part of the signable string, anyone who can obtain one valid `(raw_body, hmac)` pair for topic X (which does not require any secret — an attacker can receive this from their own trial/developer shop that has the app installed, since Shopify signs every webhook it sends to any installed shop with the app's own `client_secret`) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged attacker who legitimately receives one signed webhook for their own shop (which requires no secret, no privileged account, and no host application error — it is inherent to how the gem builds `WebhookMetadata`) can cause the host application to process/store webhook content while attributing it to a different, victim merchant's shop domain. Any downstream logic keyed off `data.shop` (e.g., looking up the victim's session/access token to act on their behalf, writing to per-tenant data using `data.shop` as the tenant key, or triggering merchant-specific side effects) is subject to cross-tenant confusion or injection, which matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants (including the attacker's own free/trial shop) and uses `data.shop` from the documented API as the trusted tenant identifier, exactly as shown in the gem's own usage example. No credentials, tokens, or `api_secret_key` need to be stolen — the attacker only needs a webhook payload/HMAC pair that Shopify sent to their own shop, and to replay it with a modified header to the app's public webhook endpoint.

### Recommendation
Include the shop-domain (and topic) header values in the bytes covered by the HMAC comparison — e.g., bind `request.shop` (and `topic`) into `to_signable_string`, or independently cross-check the header-derived `shop` against out-of-band trusted state (e.g., an active session/registration for that shop id and webhook id) before constructing `WebhookMetadata`, mirroring how upstream go-ethereum added a missing bounds/overflow check to close a gap between the value trusted and the value actually verified.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed; the app registers webhook topic `orders/create`.
2. Shopify sends: `POST /callback/orders/create` with body `B`, headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures this request (they control their own shop/network) and constructs a new request with the same body `B` and the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` → `to_signable_string` returns `B` unchanged → `HmacValidator.validate` succeeds because it only hashes `B`.
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled content as if it originated from the victim's shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
