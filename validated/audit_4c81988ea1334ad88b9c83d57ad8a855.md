### Title
Mid-signup config mutation lets a runtime-toggled flag bypass real user enrollment (`ignore_user_centric_signups`) - (File: `src/plans/mod.rs`)

### Summary
The reported bug class is: a privileged party can change a security-critical parameter at runtime, with no timelock/versioning/buffer, and that change is applied against state that is already "in flight" (an open position / an in-progress operation), producing an inconsistent and exploitable outcome. In orb-core, the analog is the backend-controlled `Config` object, which is refreshed in the background every `CONFIG_UPDATE_INTERVAL` and swapped wholesale into the shared `Arc<Mutex<Config>>` with no locking against in-progress signups, and whose fields are re-read at multiple disjoint points during a single signup.

### Finding Description
The orb polls the management backend for configuration and atomically replaces the shared config object without any regard for signups in progress: [1](#0-0) [2](#0-1) 

`CONFIG_UPDATE_INTERVAL` is 10 seconds: [3](#0-2) 

A single signup (`do_signup`) reads this shared config multiple separate times at different phases — at the very start, again for biometric capture, again for QR validation, and again after the biometric pipeline/PCP build finishes: [4](#0-3) [5](#0-4) 

Specifically, at line 639 the flag `ignore_user_centric_signups` is re-fetched from the (possibly already-mutated) shared config *after* the biometric pipeline and fraud-detection have already run, and it directly decides whether the code performs the real `enroll_user::Plan` (identity binding/enrollment call to backend) or instead short-circuits success purely based on the locally computed `signup_reason` from the pipeline, skipping the actual enrollment call entirely: [5](#0-4) 

Because the config can be overwritten by the background `config_update` task at any point during the multi-second/multi-minute signup flow (QR scan, capture, pipeline, PCP build), the value of `ignore_user_centric_signups` (and other flags such as `user_qr_validation_use_full_operator_qr`, `user_qr_validation_use_only_operator_location`, `self_serve`, used similarly at multiple separate read sites) observed at the start of `do_signup` is not guaranteed to be the same value observed at the enrollment decision point near the end. This is structurally identical to the reported bug class: a single logical operation (signup) spans a window during which a privileged, remotely-controlled parameter can change and be applied inconsistently against state that was already committed to a particular code path, with no snapshotting/timelock protecting the in-flight operation.

### Impact Explanation
If `ignore_user_centric_signups` flips from `true` to `false` mid-signup (or vice versa) due to a routine backend config push during the ~10 second polling window, a signup that a user believes will be verified through the normal `enroll_user` (identity binding / uniqueness / real backend enrollment) path can instead be routed through the "user-centric" shortcut that treats `signup_reason == Normal` as automatic success without ever calling the backend enrollment/identity-binding logic in `enroll_user::Plan`, or the reverse (a signup expected to be trusted locally instead gets forced through full enrollment unexpectedly). This creates inconsistent, config-race-dependent enrollment/identity-binding behavior for a signup that has already progressed through capture and biometric pipeline — the analog of a borrower's already-open position being evaluated under suddenly-changed collateral parameters.

### Likelihood Explanation
Config downloads happen automatically every 10 seconds via `DefaultPlan::config_update` with no coordination with the signup state machine (`signup_flag` is tracked, but `config_update` in `observer.rs` does not check it), and a signup routinely spans much longer than one polling interval (QR scan, 3s sound delay, biometric capture, biometric pipeline inference, PCP build/upload). This makes the race condition highly likely to occur naturally during normal backend configuration rollouts, not just via a targeted attack, since no code path pins/snapshots the config for the duration of a signup.

### Recommendation
Snapshot the entire `Config` once at the start of `do_signup` and thread that single snapshot through all phases of the signup (QR validation, capture, pipeline, fraud check, enrollment decision) instead of re-locking and re-reading the shared `Arc<Mutex<Config>>` at multiple independent points. Config updates delivered by the backend during an in-flight signup should only take effect for the next signup, not retroactively affect a signup whose earlier phases already executed under the old configuration.

### Proof of Concept
Not independently reproducible as a standalone PoC given the index's available context (this is a logic/race-condition analysis based on the read sites shown above, not a runtime test). A concrete PoC would require: (1) starting a signup with `ignore_user_centric_signups=false` and `user_centric_signup=true` in the QR data, (2) forcing/waiting for a backend config push that flips `ignore_user_centric_signups` to `true` while the signup is between `biometric_pipeline` completion and the check at `src/plans/mod.rs:639`, and (3) observing that the signup's success determination and whether `enroll_user::Plan` (identity binding) is invoked differs from what was true at signup start.

        if self.before_config_update()? {

                Some(None) => return Ok(()),
                Some(Some(result)) => result??,

                    config.lock().await.propagate_to_ui(ui.as_ref());

                Ok(())
            }));
        }
        Ok(())
    }
