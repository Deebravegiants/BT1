### Title
Webhook shop identity not covered by HMAC, allowing cross-tenant shop spoofing via payload replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by checking only that the HMAC of the raw request body matches, then constructs a `WebhookMetadata` object using the `shop` value read from the `x-shopify-shop-domain` header — a field that is never covered by the HMAC signature. Because the tenant identity (`shop`) is not cryptographically bound to the same signature used to authenticate the request, an attacker who can obtain any single valid `(raw_body, hmac)` pair can replay it with a different `shop-domain` header and cause the host app to process the payload as belonging to an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` calls this validator and, once it passes, immediately trusts `request.shop` to build the metadata handed to the app's business logic: [4](#0-3) 

The identity binding that should hold is:

`shop asserted in the header used by the handler == shop cryptographically bound to the HMAC-verified bytes`

In this code, the left side is attacker-controlled (arbitrary header) and the right side only covers the body — the two are never checked for equality. This is directly analogous to the reported bug class: a downstream authorization/attribution decision (`process_approve_account` trusting `mint_info.key` without checking it against `token_account.base.mint`) is made using a value (`mint`/`shop`) that is never validated against the value actually protected by the security mechanism (mint-account link / HMAC).

### Impact Explanation
Any component of the host application that uses `WebhookMetadata#shop` to scope data (e.g., "look up shop's session/store by `data.shop` and apply the update") can be made to attribute a valid, signature-verified payload to the wrong tenant. Because `shop` is not covered by the signature, an attacker who obtains one legitimate `(raw_body, hmac)` pair (from their own store's webhook deliveries, which they legitimately receive) can resend that exact body/HMAC combination with a forged `x-shopify-shop-domain` header pointing at a victim shop. This is a cross-tenant data/attribution confusion — the impact category explicitly listed as Critical ("cross-tenant access").

### Likelihood Explanation
Exploitability depends on the attacker having access to at least one legitimately signed `(raw_body, hmac)` pair, which any merchant installing the app already receives for their own store's webhooks (no special privilege beyond being an app user on any shop). Many webhook topics have static, minimal, or predictable bodies (e.g., `app/uninstalled`, `shop/redact`), making the replay straightforward once such a pair is captured. The request/response construction (`Registry.process` → `WebhookMetadata`) is entirely within this gem's code path, not reliant on the host ignoring documented behavior.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) claim to the signature verification, or require the host application to separately verify that the header-derived `shop` matches an expected/registered shop for that specific HMAC before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated relative to the HMAC and must be independently corroborated (e.g., against a known session for that shop) before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery for topic `app/uninstalled` with body `raw_body` and header `x-shopify-hmac-sha256: valid_hmac_for_raw_body`.
2. Attacker crafts a new HTTP request to the victim host app's webhook endpoint using the same `raw_body` and `valid_hmac_for_raw_body`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `raw_body` — it succeeds because the body is unchanged. [5](#0-4) 
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim-shop.myshopify.com"`, and the app's handler processes the (attacker-originated) event as if it came from the victim shop. [6](#0-5)
