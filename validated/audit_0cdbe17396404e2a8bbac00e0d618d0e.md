Audit Report

## Title
Missing rate-limiting/allowlist on legacy WebAPI user messages allows unmetered flooding of all DON nodes - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` accepts `web_api_trigger` messages from external clients, requiring only a valid ECDSA signature (checked by `msg.Validate()`/`ExtractSigner` before dispatch) plus a decodable payload and a non-stale timestamp, but performs no per-sender allowlist check and no rate limiting before fanning the message out to every member of `h.donConfig.Members` via `don.SendToNode` and registering it in the shared `h.savedCallbacks` map. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler.go" start="384-396" /> <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler.go" start="411-420" /> The gap is explicitly acknowledged by the code itself via `// TODO: apply allowlist and rate-limiting here` and by a matching `// TODO: Validate Senders and rate limit check` note in the handler's own test suite. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler_test.go" start="365-365" />

## Finding Description
The gateway's `ProcessRequest` routes any legacy (DON-ID-bearing) JSON-RPC message straight to `h.HandleLegacyUserMessage` after only calling `msg.Validate()`, which checks field lengths and verifies the ECDSA signature is well-formed/recoverable — it does not check the recovered signer against any allowlist. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/gateway.go" start="253-272" /> <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/api/message.go" start="54-88" /> Because `Sign`/`ExtractSigner` only require *a* valid ECDSA keypair — not a pre-registered or privileged one — any external caller can generate a keypair, sign an arbitrary message, and produce a request that passes `Validate()`. `HandleLegacyUserMessage` then does timestamp/payload checks and reaches the explicit `// TODO: apply allowlist and rate-limiting here` marker with no enforcement, before looping over all `h.donConfig.Members` to call `don.SendToNode` and inserting an entry into `h.savedCallbacks`. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler.go" start="341-420" /> This is asymmetric with the sibling node-facing path `handleWebAPIOutgoingMessage`, which does enforce `h.nodeRateLimiter.Allow(nodeAddr)` before doing work. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler.go" start="164-168" /> The only mitigation present is a periodic, size-bounded prune of `savedCallbacks` (age-based expiry plus eviction to `maxSize/2`), which limits unbounded memory growth but does not prevent per-request fan-out amplification. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler.go" start="299-338" />

## Impact Explanation
Each accepted `web_api_trigger` message multiplies into N node-directed `SendToNode` calls (one per DON member), so an unprivileged external caller can cheaply amplify a single HTTP request into N messages fanned out to the entire DON, and can also churn the shared `savedCallbacks` map. This is a plausible availability/DoS-class issue against the Gateway and its connected DON nodes, consistent with typical in-scope "node API" availability findings for Chainlink bounty scope.

## Likelihood Explanation
Exploitation only requires generating an ECDSA keypair and signing a well-formed `web_api_trigger` payload with a fresh timestamp — no privileged credential, allowlist membership, or prior registration is needed, since `Validate()` merely checks signature well-formedness, not signer identity. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/api/message.go" start="82-88" /> The absence of enforcement is not hypothetical — it is confirmed both by the explicit TODO in the production code path and by the corresponding acknowledgment in the handler's test file, indicating the maintainers are aware allowlist/rate-limit checks are not yet implemented here. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler.go" start="384-384" /> <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler_test.go" start="365-365" />

## Recommendation
Add a per-sender/global rate limiter (mirroring `h.nodeRateLimiter.Allow` used in `handleWebAPIOutgoingMessage`) and an allowlist check on `msg.Body.Sender` before the fan-out loop and `savedCallbacks` insertion in `HandleLegacyUserMessage`. Additionally consider rejecting duplicate in-flight `MessageID`s per sender, similar to the protections already present in `confidentialrelay.handler.newActiveRequest` and the v2 HTTP trigger handler's duplicate-request-ID check.

## Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration required).
2. Construct a `web_api_trigger` legacy `api.Message` with a unique `MessageID`, valid `TriggerRequestPayload` (including a current `Timestamp`), sign it with the generated key via `msg.Sign`.
3. POST repeated such messages to the Gateway's legacy JSON-RPC endpoint (`gateway.ProcessRequest`); each will pass `msg.Validate()`, pass the payload/timestamp checks in `HandleLegacyUserMessage`, hit the unenforced `TODO` marker, and be forwarded via `don.SendToNode` to every entry in `h.donConfig.Members`.
4. Repeating at high volume/rate demonstrates unmetered fan-out amplification with no throttling, reproducible via a Go test analogous to `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go` sending many distinct signed messages in a loop and asserting `don.SendToNode` is invoked without any rejection. <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/handler_test.go" start="236-265" />
