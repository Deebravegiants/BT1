## Title
Webhook `shop-domain` and `topic` Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers — which are entirely outside the signed payload — to decide which tenant and handler the data belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, never the headers: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `to_signable_string`, i.e., the raw body: [2](#0-1) 

`Registry.process` checks only this body-bound HMAC, and then unconditionally trusts `request.shop` and `request.topic` — both read straight from attacker-controllable headers — to route the payload to a handler and stamp the resulting `WebhookMetadata` with the shop identity the host application will act on: [3](#0-2) 

`Request#shop` and `Request#topic` are both simple header lookups with zero cryptographic binding to the signed body: [4](#0-3) 

**Binding that should hold:** `hmac(raw_body)` should equal `hmac(raw_body ‖ shop ‖ topic)` — i.e., the identity fields the application acts on (`shop`, `topic`) must be part of what the signature attests to. **Binding that actually holds:** `hmac` only attests to `raw_body`; `shop` and `topic` are accepted from unauthenticated header bytes never covered by the HMAC.

Because any legitimate webhook recipient (e.g., a merchant who has installed the host app on their own shop) can capture one genuine `(raw_body, hmac)` pair from their own shop's Shopify-delivered webhook, they can replay that exact body/HMAC pair to the host application's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will pass HMAC validation (it only checks the body) and will hand the forged shop identity straight to the host app's handler via `WebhookMetadata#shop`.

### Impact Explanation
This lets an unprivileged attacker who controls one shop inject webhook data that the host application will process as if it originated from a different, victim tenant — a cross-tenant data-integrity/authentication bypass. Depending on how the host app uses `data.shop` (e.g., to look up the tenant's session/access token and perform actions, update tenant records, or trigger tenant-scoped side effects), this can lead to cross-tenant state corruption or actions being taken against a merchant who never sent that webhook, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any user who can install the host app on a shop they control automatically becomes a legitimate webhook source and can capture a valid `(raw_body, hmac)` pair for at least one topic. Replaying it with a modified `shop-domain`/`topic` header requires no secret material and is trivially scriptable, so likelihood is high wherever the host app trusts `WebhookMetadata#shop`/`#topic` for tenant-specific logic.

### Recommendation
Bind the `shop-domain` (and ideally `topic`) header into the signed material that `to_signable_string` returns, or independently verify that the `shop` header matches an already-authenticated session/tenant context before dispatching to handlers, rather than trusting a header that sits outside the HMAC.

### Proof of Concept
1. Attacker installs the host app on their own shop `attacker.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker sends a new HTTP request to the host app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only recomputes/compares HMAC over `B` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), so the host application processes attacker-controlled webhook content as if it came from `victim.myshopify.com`.
