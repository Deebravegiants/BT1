### Title
Webhook `shop-domain` and `topic` headers are trusted and dispatched without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook to a specific merchant tenant are taken from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body/signature: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies the HMAC using exactly this `to_signable_string` value, so it authenticates the body bytes but says nothing about the header values: [4](#0-3) 

`Registry.process` accepts any request whose body HMAC validates, then forwards the *header-derived* `shop` (and `topic`) — not anything cryptographically tied to the signature — to the app's handler as the tenant identity for the event: [5](#0-4) 

The binding that should hold is:
`shop used to attribute/act on the webhook == shop covered by the verified HMAC`

but in this design it is actually:
`shop used to attribute/act on the webhook == shop header value (unauthenticated)`
`hmac covers == raw_body only`

Because the signature never binds `shop`, `topic`, or `webhook_id` to the body, any (body, hmac) pair that is valid for one shop/topic combination remains valid if replayed with different `shop-domain`/`topic` headers — the equality the app relies on (verified bytes == acted-upon identity) does not hold for the header fields.

### Impact Explanation
An unprivileged internet user who can obtain one genuine (raw_body, hmac) pair — trivially achievable by installing the (typically public/free) app on a shop they control and observing/capturing a legitimate webhook delivery to their own endpoint — can replay that exact body and HMAC to the host application's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will validate successfully (the HMAC check only looks at the body) and will hand the handler a `WebhookMetadata` claiming an arbitrary `shop`/`topic` of the attacker's choosing. If the host application uses `WebhookMetadata#shop` to look up per-tenant data, trigger tenant-scoped side effects (e.g., app/customer/shop data deletion, uninstall handling, order/customer record updates), this becomes a cross-tenant confusion vector — attacker-controlled data is attributed to a victim shop the attacker never proved control of. This satisfies the "cross-tenant access" impact criterion because tenant attribution is enforced only by an unauthenticated header, not by the cryptographic check that gates the endpoint.

### Likelihood Explanation
Requires no secrets, no session, no privileged account: only (1) capturing one valid HMAC+body pair, obtainable by installing the app on an attacker-owned store, and (2) sending a normal unauthenticated HTTP POST to the app's public webhook route with substituted headers. The library's `Request` constructor only checks header *presence*, not any relationship to the body, so nothing in this gem prevents such replay: [6](#0-5) . The actual severity depends on how the host app uses `shop`/`topic`, but the library provides no protection against header/body mismatch, and every consumer relying on `Registry.process` inherits this gap.

### Recommendation
Bind the identity fields the handler acts on to the verified signature: either (a) include `shop`, `topic`, and `webhook_id` in the signable string alongside the raw body, or (b) require callers to additionally verify the `shop` returned by `WebhookMetadata` against an expected/registered shop list before performing any tenant-scoped action, and document this requirement prominently. At minimum, `HmacValidator.validate` should be extended to take the full `Request` (headers + body) as signable material rather than body alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed for that body.
2. Attacker sends a POST to the app's public webhook endpoint reusing the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — the signature still matches because it never depended on the shop header: [7](#0-6) .
4. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act as if the (attacker-supplied) event genuinely originated from the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
