### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to attribute and route the webhook are taken from unauthenticated HTTP headers. This breaks the identity binding `shop-domain header == shop bound by the HMAC`, letting an unprivileged internet user who has captured any one validly-signed webhook body replay it with a forged `shop-domain` header and have the app process it as if it came from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to `verifiable_query.hmac` using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body` — none of the headers are part of the signed material: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are not authenticated by the HMAC at all: [3](#0-2) 

`Registry.process` validates only the body HMAC, then dispatches to the handler using the unauthenticated `request.shop` (and `request.topic`) values for tenant attribution: [4](#0-3) 

The equality that should hold is: `shop value the handler attributes data to == shop value bound by the HMAC`. In this implementation the left side comes from the `x-shopify-shop-domain`/`shopify-shop-domain` header while the right side (what the HMAC actually covers) is only the raw JSON body. These are never checked against each other, so the binding does not hold — mirroring the reported bug class of "a field acted on but not covered by the HMAC."

### Impact Explanation
Any entity that can install the target app on a shop it controls (i.e., any Shopify merchant/developer, which is an "unprivileged internet user" relative to the app's other tenants) will legitimately receive Shopify-signed webhooks for its own shop. Because the header carrying the shop identity is not part of the signed content, that captured `(raw_body, hmac)` pair remains valid when replayed with an arbitrary `shop-domain` header value. A host application that trusts `WebhookMetadata#shop` (as documented and exercised by this gem's own test suite) to key its per-tenant data store, dedupe webhooks, or authorize side effects can be made to process data under a different tenant's identity — a cross-tenant data-attribution bypass grounded entirely in this gem's `Request`/`Registry` code, not merely "the host app ignoring documented behavior," since the gem exposes `WebhookMetadata.shop` as an already-verified, trustworthy field once `Registry.process` succeeds.

### Likelihood Explanation
Requires only: (1) the attacker be a legitimate (even free-trial) installer of the target app on their own store to obtain one genuine `(body, hmac)` pair, and (2) the ability to POST an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no `api_secret_key`, access token, or privileged account is needed. This is realistically reachable by any developer/tester of the app.

### Recommendation
Bind the shop (and topic) identity into the signed material actually verified by this gem, e.g., require callers to supply the header value alongside the raw body and include it in `to_signable_string`, or — since Shopify's own signature does not cover headers — have `Registry.process` cross-check `request.shop` against a shop value obtained through an independently authenticated channel (e.g., the session/webhook subscription id previously registered for that shop) before dispatching to handlers, and clearly document that `WebhookMetadata#shop` is not itself HMAC-verified.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret `S`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's public webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim.myshopify.com` (topic/webhook-id can also be changed) while leaving body `B` and `hmac H` untouched.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only [5](#0-4)  — it matches `H`, so validation succeeds.
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` to the app's handler [4](#0-3) , causing the host application to process attacker-supplied data as belonging to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
