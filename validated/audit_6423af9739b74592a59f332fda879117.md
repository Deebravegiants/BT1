## Title
CORS wildcard-origin allowlist bypass via missing domain-boundary check - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway's `isAllowedOrigin` function matches wildcard CORS entries (e.g. `*.ethereum.org`) by stripping the `*.` prefix and calling `strings.HasSuffix(originHost, allowedHost)`, without requiring a `.` domain separator before the matched suffix. This allows an attacker who registers a domain like `evilethereum.org` to be treated as a trusted subdomain of `ethereum.org`, since the raw string comparison has no domain-boundary awareness.

## Finding Description
In `isAllowedOrigin`, the wildcard match branch is: [1](#0-0) . When `allowed` is configured as `https://*.ethereum.org`, `allowedHost` becomes `ethereum.org`, and any `originHost` for which `strings.HasSuffix(originHost, "ethereum.org")` holds is accepted — this is true for `evilethereum.org` just as much as for `remix.ethereum.org`, since `HasSuffix` performs a raw character-suffix comparison with no requirement that a `.` precede the match. This result is used directly to set the reflected CORS header in `handleRequest`: [2](#0-1) . No other check (scheme/port comparisons preceding it) constrains the host boundary, so the flaw is unmitigated. The existing test suite only exercises a differing-TLD negative case (`ethereum.remix.org` vs `*.ethereum.org`), which does not share a suffix and thus never exercises the actual boundary bug, leaving the gap unnoticed.

## Impact Explanation
This is a legitimate CORS allowlist bypass. If an operator uses the documented wildcard feature (`CORSAllowedOrigins = ["https://*.ethereum.org"]`, as demonstrated in `core/scripts/gateway/sample_config.toml`), an attacker who registers any domain ending in the same characters (e.g. `evilethereum.org`) can have the gateway reflect `Access-Control-Allow-Origin: https://evilethereum.org`. This lets a malicious webpage read cross-origin responses from the gateway API in a victim's browser, constituting gateway request/response impersonation and allowlist bypass, both in-scope impact classes.

## Likelihood Explanation
Exploitation requires only (1) an operator using the wildcard CORS feature as documented, and (2) an attacker registering an inexpensive, freely-available domain sharing the suffix. No node compromise, credentials, or elevated privileges are required — this is fully triggerable by an unprivileged remote actor purely through normal browser/HTTP requests to the gateway, and is deterministically reproducible.

## Recommendation
Require a domain-separator boundary when matching wildcard hosts, e.g. compare against `"." + allowedHost` (with the leading dot) instead of the bare suffix, so `evilethereum.org` no longer matches `*.ethereum.org` while `remix.ethereum.org` still does:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".ethereum.org"
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```

## Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the gateway endpoint with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the boundary-unaware `strings.HasSuffix` match in `isAllowedOrigin` at [1](#0-0)  incorrectly treats `evilethereum.org` as a subdomain of `ethereum.org`. This can be codified as a Go unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting `Access-Control-Allow-Origin` is set (bug present) for origin `https://evilethereum.org` against allowlist `https://*.ethereum.org`.
