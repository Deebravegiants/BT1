### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`, `api_version`) is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop/topic/webhook-id/api-version identifiers that the app's handler treats as authoritative are taken from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The tenant-identifying fields `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers via `shopify_header`, completely outside the HMAC's coverage: [2](#0-1) .

`Registry.process` validates the HMAC over the body only (`Utils::HmacValidator.validate(request)` → `to_signable_string` = raw body), and then, once that check passes, immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all header-derived, unauthenticated values — to build the `WebhookMetadata` that is handed to the app's registered handler: [3](#0-2) .

The equality this breaks is: `shop used to attribute/process a webhook payload` should equal `shop value covered by the cryptographic signature the app relies on to trust the request`. Here, `hmac = HMAC(raw_body)` but the tenant binding actually enforced by the handler is `shop = header("shopify-shop-domain")`, which is disjoint from the signed content. `HmacValidator.validate` (used identically for both OAuth callbacks and webhooks) only ever authenticates `verifiable_query.to_signable_string`: [4](#0-3) .

### Impact Explanation
If a valid `(raw_body, hmac)` pair for a given webhook delivery is ever replayed toward the app's public webhook endpoint with a different `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header, `Registry.process` will pass HMAC validation and dispatch the payload to the app's handler under the attacker-chosen shop identity, causing the app to process/store data under the wrong tenant — a cross-tenant data integrity issue in the app's webhook processing pipeline. This maps to the "field acted on but not covered by the HMAC" identity-binding class.

### Likelihood Explanation
Exploitation requires an attacker to obtain a legitimate `(raw_body, hmac)` pair from a genuine Shopify-issued webhook delivery and resend it with altered headers to the same endpoint; producing a valid HMAC for an arbitrary chosen body without the shared `api_secret_key` is infeasible. Obtaining a genuine pair typically requires visibility into a real delivery in transit (e.g. network-level observation) rather than a purely credential-free remote interaction, so likelihood is low without ancillary access; the underlying binding gap in the gem's code is nonetheless real and unconditional.

### Recommendation
Bind the header-derived identifiers into the signable content (e.g., include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC computation, or otherwise cryptographically bind them to the body) so that `HmacValidator.validate` fails if any of these fields are altered independently of the payload.

### Proof of Concept
1. Capture (via any means giving visibility into an in-flight webhook delivery, e.g., a proxy the attacker controls in front of their own store's webhook subscription) one legitimate webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC-SHA256(secret, B)` and compares to `H` — it succeeds because `B` is unchanged.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes the payload as though it originated from `victim-shop`, even though the shop header was never covered by the signature. [3](#0-2) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
