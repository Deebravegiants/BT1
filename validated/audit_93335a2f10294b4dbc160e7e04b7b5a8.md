**Reasoning:**

The premise—that skipping `validateOmniToken`/`parseOriginChain` when `targetChainSpecified` is true allows delivery of "a different asset"—doesn't hold up against the code.

When `routeConfig.chain` overrides the destination (e.g., Aptos), `supports()` and `makeAssetInfo()` call `getBridgedToken(nearProvider, omniAddress(ChainKind.Near, contractId), omniChainKind)`, which queries the Omni Bridge NEAR contract's own `get_bridged_token` registry [1](#0-0) . This is not an attacker-supplied or arbitrary mapping — it is the bridge protocol's canonical, on-chain record of the *same logical token's* deployed representation on the specified chain. If no such entry exists, `supports()` throws `TokenNotFoundInDestinationChainError` [2](#0-1) . There is no path for the caller to substitute a "different asset" or "wrapper" — only the address the bridge itself registered for that token on that chain is used.

Decimal normalization is explicitly handled for exactly this cross-chain scenario: `getCachedTokenDecimals` fetches `{decimals, origin_decimals}` for the destination-chain-specific token address, and `verifyTransferAmount` checks that `(amount - fee)` normalizes to a non-zero, valid amount under the target chain's decimal precision before allowing the withdrawal [3](#0-2) . This is standard cross-chain decimal handling (e.g., USDC 6 vs 18 decimals), not a value-leak bug — it's a safeguard against sending amounts that round to zero, not a mechanism that increases attacker gain.

`validateAddress(args.destinationAddress, assetInfo.blockchain)` validates the destination address against the *actual* target chain (Aptos, from `routeConfig.chain`), and `compareAddresses` checks the destination isn't accidentally the bridged token's own contract address on that same chain [4](#0-3) . Both operate on the correct, consistent chain context — there's no mismatch between the chain used for address rules and the chain used for the bridged-token lookup.

The chain-override feature (bridging a token to a non-origin chain it has been separately deployed to) is an intentional design of Omni Bridge, not a bypass of asset-identity checks. The equality "amount credited on the destination chain == signed amount − fees, same asset" is preserved through `verifyTransferAmount`'s decimal-normalization gate and the registry-backed `getBridgedToken` lookup, so the claimed divergence does not occur.
