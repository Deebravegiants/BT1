### Title
`calc_take_pnl` can hard-revert `Deposit`/`Withdraw`, permanently freezing LP funds once the stored-vs-actual reserve invariant is violated - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` enforces `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` and returns `AmmError::CalcPnlError` if this invariant does not hold [1](#0-0) . This function is called unconditionally (via `?`) from `process_deposit` and, whenever the pool is not in `WithdrawOnly` status, from `process_withdraw` [2](#0-1) [3](#0-2) . Just like the keep-tecdsa bug (where `freeBond`'s `lockedBonds[bondID] > 0` requirement can no longer be satisfied and blocks `closeKeep()`), a strict invariant check inside a helper used by the "exit" instruction (`Withdraw`) — and here also the "entry" instruction (`Deposit`) — can permanently revert once the recorded PnL state (`target.calc_pnl_x` / `target.calc_pnl_y`) and the live vault balances drift apart, with no fallback path for ordinary users to still withdraw or deposit.

### Finding Description
`target_orders.calc_pnl_x`/`calc_pnl_y` track the pool reserves (normalized to `sys_decimal_value`) as of the last deposit/withdraw/withdrawpnl call, and `calc_take_pnl` compares `restore_decimal(calc_pnl_x) * restore_decimal(calc_pnl_y)` (the "last k") against the currently observed native-decimal vault balances multiplied together (the "current k") [4](#0-3) . `normalize_decimal_v2`/`restore_decimal` truncate via integer division on every call [5](#0-4) , so the round-trip conversion is inherently lossy.

Under normal operation, swap fees should keep the pool's real product growing faster than this rounding noise, but for small-decimal tokens, low `sys_decimal_value`, or a sequence of very small-notional swaps, the accumulated truncation loss on the "last k" side can exceed the genuine fee-driven growth of "current k". When that happens, the `>=` check fails and `calc_take_pnl` returns `AmmError::CalcPnlError` [6](#0-5) .

Because `process_deposit` calls `calc_take_pnl` unconditionally and propagates the error with `?` [7](#0-6) , once this state is reached, every `Deposit` instruction on the pool fails. `process_withdraw` only skips the call when `amm.status == AmmStatus::WithdrawOnly` [8](#0-7) , a status that only a privileged config authority can set via `SetParams`/`UpdateConfigAccount`, and this exception is not available to `Deposit` at all. Any unprivileged LP or swapper transaction that pushes the pool into this state therefore leaves normal LPs unable to withdraw (unless/until a privileged admin flips the pool to `WithdrawOnly`) and permanently unable to deposit, exactly mirroring the reported bug class: a hard requirement inside an internal helper, invoked from the fund-exit/entry instruction, throws instead of degrading gracefully, blocking the legitimate operation entirely.

### Impact Explanation
If reached, this causes denial-of-service on core LP operations (`Deposit` always, `Withdraw` unless an admin intervenes) for the affected pool, which is a form of freezing of LP funds — LPs cannot add or remove liquidity, and ordinary users relying on deposits/withdrawals for that pool are blocked, until a privileged operator performs a `SetParams` status change (and even then, `Deposit` remains permanently broken since it has no bypass). This satisfies the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
This requires the reserve/PnL bookkeeping invariant to be violated by rounding drift accumulated over normal swap/deposit/withdraw activity — reachable purely through unprivileged transactions (repeated swaps and deposits/withdrawals with adversarial or naturally small amounts chosen to minimize fee growth relative to decimal-normalization truncation), with no special permissions needed. The precise amount/decimal combination needed to trigger the truncation-exceeds-growth condition is nontrivial to hit and is likely rare in practice for typical decimal configurations, so likelihood is best characterized as low-to-medium rather than trivially reproducible on every pool.

### Recommendation
Avoid hard-failing the fund-exit/entry path on this invariant violation. Options: (1) clamp/skip the PnL-taking step (treat delta as zero) instead of returning an error when `pool_pc*pool_coin < calc_pc*calc_coin`, similar to how `pc_pnl_amount != 0 && coin_pnl_amount != 0` already gracefully no-ops delta calculation [9](#0-8) ; (2) let `process_deposit` also bypass `calc_take_pnl` under the same conditions `process_withdraw` does; (3) increase internal precision (e.g., avoid double truncation via `normalize_decimal_v2`/`restore_decimal` round trips) so genuine fee growth cannot be masked by rounding noise.

### Proof of Concept
1. Initialize a pool with vault balances/decimals chosen so `sys_decimal_value` truncation is coarse relative to native decimals (e.g., low-decimal PC/coin mints).
2. Perform a sequence of very small-notional `SwapBaseIn`/`SwapBaseOut` calls (or `Deposit`/`Withdraw` cycles) whose fee-driven reserve growth is smaller than the truncation loss introduced by `normalize_decimal_v2`/`restore_decimal` round-tripping in `calc_take_pnl`.
3. Call `Deposit` or `Withdraw` (with `amm.status != WithdrawOnly`); `calc_take_pnl` computes `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount` and returns `AmmError::CalcPnlError`, aborting the transaction [1](#0-0) .
4. All subsequent `Deposit` calls on this pool fail identically; `Withdraw` remains blocked until a privileged `SetParams`/`UpdateConfigAccount` call sets `AmmStatus::WithdrawOnly`.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
