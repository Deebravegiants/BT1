Based on my investigation, I found a concrete analog to the M-6 bug class: a value that is moved by an external action (fee extraction from a user's `HinkalWallet`) but is not checked against the bound the user actually signed for, breaking an authorization equality.

### Title
Emporium relay fee charged to `HinkalWallet` is never checked against the EIP-712 signed `maxFee` bound - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet` has the wallet owner sign an EIP-712 message (`EMPORIUM_SIGNATURE_TYPEHASH`) that explicitly includes a `maxFee` field, and the contract even declares a `FeeExceedsSignedMax` error for this purpose [1](#0-0) . However, in the actual fee-charging path (`payRelayFees`/`payRelay`/`sendToRelayFromWallet`), the fee amount pulled directly from the wallet is never compared against `stack.maxFee`, and `FeeExceedsSignedMax` is never reverted with in this flow.

### Finding Description
When a signer (wallet) is used for an Emporium action (`stack.signerAddress != address(0)`), `payRelayFees` sets `relayFee = flatFee` directly from `circomData.feeStructure.flatFee` with no upper-bound check: [2](#0-1) 

That `relayFee` is then pulled straight from the wallet's own balance via `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`: [3](#0-2) , and the wallet itself performs no further validation - it just executes the transfer for any caller that is `emporium`: [4](#0-3) 

Meanwhile, `verifyWallet` is the only place `stack.maxFee` is referenced, and it is only included inside the hash that is signed - it is never read back and compared to the fee actually charged: [5](#0-4) 

`circomData.feeStructure` (which contains `flatFee`) is attacker/relay-controlled calldata - it is only checked for internal consistency via `calldataHash`/`signedMessageHash` [6](#0-5) , not bounded by anything the wallet owner signed. The wallet owner's EIP-712 signature over `maxFee` is therefore purely decorative in the code paths I could verify (lines 1–330 of the contract, covering `runAction`, `payRelayFees`, `payRelay`, and the start of `verifyWallet`) - the value actually debited from the wallet (`flatFee`) is never constrained to be `<= maxFee`.

This is a direct analog of M-6: just as Perp's debt calculation silently drops a term (`owedRealizedPnl`) that should be part of the value equation, here the fee-charging equality silently drops the bound (`maxFee`) that the signer explicitly authorized, so `actualFeeCharged` can exceed `signedMaxFee` without any revert.

### Impact Explanation
A malicious or compromised relay can set `circomData.feeStructure.flatFee` to any value and cause `doSendToRelay` to pull that amount directly from the user's `HinkalWallet` balance, exceeding the `maxFee` the wallet owner actually signed for. This is theft of user/protocol funds via a wallet operation the signer never authorized at that magnitude - matching the "High" impact bar (executing calls or moving assets a wallet owner or prover never authorised; theft of protocol/relay fees).

### Likelihood Explanation
Requires a malicious/compromised relay (the entity that assembles `circomData` and submits the transaction) but no admin/owner/upgrade key and no cooperation from the wallet owner - the wallet owner's only protection (the signed `maxFee`) is bypassed because the contract never checks it. Given relays are explicitly treated as semi-trusted-but-not-fully-trusted parties in this protocol's threat model (hence the `maxFee` signature mechanism existing at all), this is a realistically reachable path.

### Recommendation
In `payRelayFees` (or immediately before `sendToRelayFromWallet` is invoked with a signer), add an explicit check that the cumulative fee charged to the wallet does not exceed `stack.maxFee`, reverting with the already-declared `FeeExceedsSignedMax()` error if it does.

### Proof of Concept
1. Wallet owner signs an `EmporiumSignature` with `maxFee = X` for a batch of `ops`.
2. Relay submits the same signed `ops`/`emporiumMessage`/`deadline`, but crafts `circomData.feeStructure.flatFee = Y` where `Y >> X`.
3. `verifyWallet` only checks that the signature matches `emporiumMessage`, `_hashEmporiumOps(ops)`, `maxFee`, `deadline` — it does not check `flatFee` against `maxFee`, and passes.
4. `payRelayFees` computes `relayFee = flatFee = Y` and calls `sendToRelayFromWallet`, which calls `IHinkalWallet(signerAddress).doSendToRelay(relay, Y, feeToken)`.
5. `HinkalWallet.doSendToRelay` unconditionally transfers `Y` of `feeToken` from the wallet to `relay`, exceeding the signed `maxFee` bound with no revert anywhere in the call path.

**Uncertainty note**: I was not able to view the full body of `verifyWallet` past line 330 (only the signature-recovery call was visible) or any code beyond the contract sections returned by search. It is possible (though I found no evidence of it) that a `maxFee` check exists elsewhere in the contract that I could not retrieve. Given index size limits, I recommend confirming this by reading the complete `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` file directly (e.g., via a full Devin session) to rule out a check I may have missed further down in `verifyWallet` or in a modifier applied to `runAction`.
