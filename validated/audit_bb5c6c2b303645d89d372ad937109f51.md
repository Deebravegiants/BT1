## Analog Found

### Title
Silent u64 downcast overflow in `swap_in_after_add_fee` allows draining pool funds via `SwapBaseOut`/`SwapBaseOutV2` - (File: `program/src/processor.rs`)

### Summary
The base-out swap path computes the required input amount (`swap_in_after_add_fee`) in 128-bit precision and then truncates it to `u64` using the raw `.as_u64()` method on the `uint`-crate `U128` type, instead of the checked `Calculator::to_u64()` helper (which uses `try_into()` and returns `AmmError::ConversionFailure` on overflow) that is used everywhere else in the math module. If the true value exceeds `u64::MAX`, `.as_u64()` silently truncates to the low 64 bits rather than erroring, exactly mirroring the Notional `_fCashAmount` downcast bug class.

### Finding Description
In both `process_swap_base_out` and `process_swap_base_out_v2`, the amount the user must pay in is computed as: [1](#0-0) 

`swap_in_before_add_fee` is produced by `Calculator::swap_token_amount_base_out`, which computes `total_X * amount_out / (total_Y - amount_out)` entirely in `U128`: [2](#0-1) 

Because `amount_out` (attacker-controlled, up to `u64::MAX`) can be chosen arbitrarily close to `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (only checked to be strictly less than the pool total, later in the function), the denominator `total_Y - amount_out` can be made as small as `1`. This blows up `swap_in_before_add_fee`, and after multiplying by `swap_fee_denominator`, the resulting `U128` value can exceed `u64::MAX` while still fitting comfortably inside `U128`'s much larger range (so no `unwrap()` panics occur). The final `.as_u64()` call then silently truncates this oversized value to a small `u64`, unlike the checked conversions (`Calculator::to_u64`) used elsewhere in `math.rs`, e.g.: [3](#0-2) 

The truncated (small) `swap_in_after_add_fee` is what is subsequently validated and transferred from the user: [4](#0-3) [5](#0-4) 

Meanwhile, the amount paid *out* of the pool to the attacker is the full, non-truncated `swap.amount_out` value supplied directly in the instruction data. The only pre-transfer check on `amount_out` is `swap.amount_out >= total_pc_without_take_pnl` (or coin equivalent), which does not prevent `amount_out` from being chosen close enough to the pool total to trigger the overflow while still passing that check.

### Impact Explanation
An attacker calling `SwapBaseOut` or `SwapBaseOutV2` (unprivileged, single transaction, attacker-chosen accounts/data) can craft `amount_out` such that the true required input exceeds `u64::MAX`. The silent truncation causes `swap_in_after_add_fee` to wrap to an attacker-favorable small value, which then trivially satisfies both the `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` checks. The program then transfers only this tiny truncated amount from the user while paying out the full, large `swap.amount_out` from the AMM vault — directly draining pool/LP funds. This is concrete theft of pool funds, matching the "Impact" bar for this bug class.

### Likelihood Explanation
Reachable from a single transaction by any unprivileged user with normal swap accounts (no privileged signer, no off-chain component, no validator collusion needed) — only requires choosing `amount_out` close to the pool's total balance of the output token, which is public on-chain state readable before submitting the transaction. The identical vulnerable pattern exists in two entry points (`process_swap_base_out` and `process_swap_base_out_v2`), increasing exploitability.

### Recommendation
Replace the unchecked `.as_u64()` truncation on `swap_in_after_add_fee` (and any other direct `.as_u64()`/`.as_u128()` truncations on attacker-influenced `U128`/`U256` math results) with `Calculator::to_u64(...)`, which performs a checked `try_into()` and returns `AmmError::ConversionFailure` on overflow instead of silently wrapping.

### Proof of Concept
1. Attacker observes `total_pc_without_take_pnl` (call it `P`) and `total_coin_without_take_pnl` (call it `C`) from the AMM's vault balances.
2. Attacker submits `SwapBaseOutV2` with `swap.amount_out = P - 1` (Coin2PC direction), making the denominator in `swap_token_amount_base_out` equal to `1`.
3. `swap_in_before_add_fee` becomes `≈ C * (P - 1)`, which for realistic large vault balances exceeds `u64::MAX` once further multiplied by `swap_fee_denominator`.
4. `.as_u64()` truncates this to a small value `swap_in_after_add_fee` (e.g., near-zero modulo `2^64`).
5. `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` both trivially pass since the truncated value is tiny.
6. `Invokers::token_transfer` moves only the tiny truncated amount from the attacker into `amm_coin_vault`.
7. `Invokers::token_transfer_with_authority` pays out the full `swap.amount_out = P - 1` from `amm_pc_vault` to the attacker, draining almost the entire PC-side pool balance for a negligible cost. [6](#0-5)

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
