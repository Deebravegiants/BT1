### Title
Webhook shop/topic identity headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) purely from HTTP headers, while `#to_signable_string` — the value that `Utils::HmacValidator` actually authenticates — is only the raw body [4](#0-3) . This breaks the equality that the gem's webhook-processing security model implicitly assumes: `HMAC(raw_body, api_secret_key) valid ⇒ (shop, topic, webhook_id) are authentic`. In reality, HMAC validity only proves the body bytes are unmodified and were signed with the app's shared `api_secret_key`; it says nothing about which shop or topic the body was originally sent for.

### Finding Description
`Registry.process` performs exactly one authenticity check — `Utils::HmacValidator.validate(request)` — and then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` delivered to the app's handler [3](#0-2) . Because `api_secret_key` is a single shared secret per app (not per shop) [5](#0-4) , any real webhook body Shopify ever sent to the app for *any* installed shop carries a validly-computed HMAC for the app's secret. Since the header fields carrying `shop`, `topic`, and `webhook_id` are excluded from `to_signable_string`, an actor who has legitimately installed the app on their own store (a normal, unprivileged action requiring no leaked credentials) can capture one authentic `(raw_body, hmac)` pair from a real webhook delivery, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to point at a victim shop. `Registry.process` will validate the HMAC (it's still a correct signature over the unmodified body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop/topic [6](#0-5) .

### Impact Explanation
Any application built on this gem that uses `data.shop` from `WebhookHandler#handle` to key session/token storage or trigger tenant-scoped actions (as the gem's own documentation instructs: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) ) can be made to act on a shop it did not actually receive the event for. For example, spoofing the mandatory `app/uninstalled` topic against a victim's shop domain could cause the app to delete/revoke that victim's stored access token — cross-tenant impact triggered entirely by an unprivileged actor who only needed to install the app once on their own store.

### Likelihood Explanation
Requires no credentials beyond the ability to install the target app on any Shopify store (self-serve for public apps), and no access to `api_secret_key`. The attacker needs to capture one legitimate webhook body+HMAC pair and can then freely vary the shop/topic headers on replays to that same endpoint. This is a low-effort, header-substitution attack against a gem-supplied primitive (`Webhooks::Request` / `Webhooks::Registry`) rather than the host application.

### Recommendation
Bind the tenant-identifying headers into the signed payload before verifying, e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or verify them via a separate authenticated channel, such as looking up the expected shop for the given webhook subscription/session rather than trusting the header), so that `HmacValidator.validate` actually authenticates the fields the registry and handlers rely on.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; capture a real `app/uninstalled` webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's `api_secret_key`).
2. Send `POST <webhook_path>` to the target app with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
3. `Utils::HmacValidator.validate` computes `HMAC(B, api_secret_key)` which equals `H`, so the check passes [8](#0-7) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` [6](#0-5) , causing the app to treat this as an authentic event for the victim's shop.
