I have enough evidence to confirm the finding. The webhook HMAC signature only covers the raw body, not the `x-shopify-shop-domain` header, and `Registry.process` trusts that header when handing off to the host application's handler.### Title
Webhook shop identity is trusted from an unsigned header while HMAC only covers the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC signature only ever covers the raw request body. The `shop` value that is subsequently handed to the host application's handler as the tenant identity is read from an HTTP header that is never part of the signed material, so it can be swapped without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`HmacValidator.validate` computes the digest strictly over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` only checks that this body-only HMAC validates, then immediately trusts `request.shop` (the unsigned header) as the tenant identity passed to the app's handler: [4](#0-3) 

The identity binding the gem implicitly promises to the host app is: `shop that received/authorized this webhook == shop delivered to the handler`. In reality the binding enforced is only `hmac(body) == hmac(body)`; `shop-domain` is a field acted on (used to construct `WebhookMetadata` and passed to the handler for tenant-scoped business logic) but not covered by the HMAC. Because the signing secret (`api_secret_key`) is shared across all shops installing a given app, any merchant who has legitimately installed the app receives real, validly-signed webhooks for their own shop. That merchant can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata`, and thus into the host application's business logic keyed by shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: an authenticated-but-unprivileged merchant (one with any install of the same app) can make the app process webhook payloads under the identity of a different, arbitrary shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., looking up a session/access token for that shop, updating that shop's local records, redact/data-request handling for `shop/redact`/`customers/redact`/`customers/data_request` mandatory topics), this can result in cross-tenant data corruption or disclosure — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation only requires the attacker to control one shop that has the target app installed (a normal, unprivileged merchant capability) and to be able to POST an HTTP request with custom headers to the app's public webhook endpoint — no access token, `client_secret`, or `api_secret_key` needs to be known. The replay itself is trivial since the signed body is untouched.

### Recommendation
Bind the shop domain into the material that is verified before it is trusted: either require the host application to independently confirm the shop against a known/registered shop list before invoking the handler, or have `Request#to_signable_string`/`HmacValidator` cross-check the `shop` header against Shopify's guarantee (e.g., document that the header is untrusted, or provide a way to authenticate it, such as validating that the shop has an active webhook registration/session before dispatch).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `B`, headers `x-shopify-hmac-sha256: H(B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the identical request to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over body `B` only and matches `H(B)` — validation passes.
4. `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` is delivered to the app's registered handler, which now performs shop-scoped operations under the victim's identity despite the payload never having originated from Shopify for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
