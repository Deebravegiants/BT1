Confirmed root cause. The `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `HmacValidator.validate` in `Registry.process` covers exclusively the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers (`shopify_header`) that carry no cryptographic binding to that HMAC. ### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id` as the identity of the merchant/event that produced a webhook, yet only the raw JSON body is what the HMAC actually authenticates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [4](#0-3) 

`HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the value from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header: [5](#0-4) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from other headers that are never mixed into the signed string: [6](#0-5) 

`Registry.process` passes these unauthenticated header values on to the app's handler as the authoritative shop/topic identity: [7](#0-6) 

The binding the gem is supposed to enforce is:
`HMAC-authenticated bytes == (body, shop, topic, webhook_id)` for the event being dispatched to `WebhookMetadata`.

What actually holds is:
`HMAC-authenticated bytes == body only`, while `shop`, `topic`, and `webhook_id` are accepted from unauthenticated headers.

Any unprivileged internet user who can install the target app on a shop they control (a normal, free step of the OAuth flow) legitimately receives real Shopify webhooks with a valid `hmac-sha256` for their own shop's raw body. Because the signature never binds `shop-domain` or `topic`, the attacker can replay that same `(raw_body, hmac)` pair directly to the victim app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with the identifier of a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` forwards the attacker-chosen `shop` field to the app's `WebhookHandler` as `WebhookMetadata#shop`.

### Impact Explanation
This lets the attacker's own (attacker-controlled) event body be attributed to an arbitrary victim shop identifier inside the host application, since the gem itself vouches for `shop`/`topic` as verified once `HmacValidator.validate` returns true. Any app logic that keys tenant data or triggers tenant-scoped side effects (data deletion flows such as `shop/redact`, `customers/redact`, cache invalidation, billing state, resource sync, etc.) off `WebhookMetadata#shop`/`#topic` can be made to act on the wrong tenant — a cross-tenant confusion condition rooted entirely in this gem's failure to bind headers to the signed payload.

### Likelihood Explanation
High feasibility: no secrets, tokens, or privileged access are required. An attacker only needs to install the app on any shop (a normal unauthenticated onboarding action) to obtain one genuinely HMAC-signed webhook body, then can replay it with a forged `shop-domain`/`topic` header indefinitely, since neither is part of the signed content.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string that `HmacValidator` authenticates, or otherwise cryptographically bind them to the body before `Registry.process` trusts them and forwards them into `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; register a webhook (e.g. `orders/create`) via `Registry.add_registration`.
2. Trigger the event on the attacker shop; capture the resulting raw POST body `B` and its valid `x-shopify-hmac-sha256: H` header sent by Shopify (computed as `HMAC(api_secret_key, B)`, which is unknown to the attacker but still valid for `B`).
3. Replay the exact same `B`/`H` pair to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic` to any registered topic.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`to_signable_string`) — validation succeeds:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-forged `victim.myshopify.com` shop header, and dispatches it to the app's `WebhookHandler#handle`, which believes the (attacker-authored) body legitimately originated from the victim shop.
