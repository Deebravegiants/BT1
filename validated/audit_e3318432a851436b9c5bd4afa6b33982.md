### Title
Fee-on-Transfer tokens cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow using the nominal, pre-transfer input amount (minus protocol fee) instead of the amount actually received by the contract. Unlike the primary EVM `IntentGatewayV2.sol`, which was hardened to measure `balanceOf` before/after each `safeTransferFrom` and mutate `order.inputs[i].amount` to the actual received value [1](#0-0) , the Tron contract's direct-transfer path performs no such check.

### Finding Description
In the non-predispatch branch of `placeOrder`, the Tron contract calls `safeTransferFrom` for the nominal `order.inputs[i].amount`, then unconditionally credits the escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount`, which is derived from the nominal amount minus the protocol fee — not from the tokens the contract actually received: [2](#0-1) 

For any ERC20 with a transfer fee, `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` delivers strictly less than `order.inputs[i].amount` to the contract, yet `_orders[commitment][token]` is incremented by the full `reducedInputs[i].amount` (computed off the nominal amount). The predispatch branch has the analogous bug: it credits `reducedInputs[i].amount` regardless of the actual dispatcher/contract balance swept in, only checking `balance < requiredAmount` as a lower bound rather than reconciling actual receipt: [3](#0-2) 

This is the same root-cause pattern as the referenced BendDAO finding: balances are treated as invariant across a transfer, which fee-on-transfer tokens violate — except here the effect is not a revert but silent over-crediting of an internal accounting ledger.

### Impact Explanation
Every order placed with a fee-on-transfer token inflates the `_orders` escrow mapping beyond what the contract actually holds for that token. Since `_orders[commitment][token]` is a per-order-commitment tally that is later paid out via `_withdraw` (`IERC20(token).safeTransfer(beneficiary, amount)`) on fill/refund/redemption, the aggregate claims against that token can exceed the contract's real balance. This is a protocol-level insolvency: once enough fee-on-transfer deposits accumulate, some legitimate withdrawal (solver fill payout, refund, or redeem-escrow from a relayed cross-chain message) will fail or drain balance belonging to other users/orders of the same token, resulting in permanent freezing or loss of user/solver funds — reachable by any single unprivileged `placeOrder` call.

### Likelihood Explanation
Any user can trigger this deterministically by placing an order with an in-scope fee-on-transfer ERC20 as an input token — a single transaction, no special privileges required. The bug is unconditionally reachable whenever `predispatch.call.length == 0` (the common path) for non-native tokens; the affected asset just needs to charge a transfer fee.

### Recommendation
Match the fix already implemented in the main EVM `IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, compute the actual received amount as the post-transfer balance delta, and use that (rather than the nominal `order.inputs[i].amount`) as the basis for both the protocol-fee reduction and the escrow credit / commitment hash. Apply the same balance-delta reconciliation in the predispatch sweep branch instead of only checking `balance < requiredAmount`.

### Proof of Concept
1. Deploy a 1%-fee ERC20 token (as used in `FeeOnTransferToken` test helper [4](#0-3) ).
2. User approves and calls Tron `IntentGatewayV2.placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch call.
3. `safeTransferFrom` moves 1000e18 nominally but the contract only receives 990e18 (1% fee).
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits ~1000e18 (minus only the protocol fee, not the transfer fee) — exceeding the 990e18 actually held.
5. Repeat across multiple orders/users of the same FOT token; eventually a `_withdraw` call (via `fillOrder`, `RedeemEscrow`, or `RefundEscrow` incoming request) attempts to pay out more FOT than the contract holds, reverting or being satisfied at the expense of other users' escrowed balances.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
