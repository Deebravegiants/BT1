### Title
Unbounded octal-to-`u8` parsing causes reachable `assert_eq!` panic in `Configuration::parse_wavelength_configuration` - (File: src/plans/biometric_capture/overcapture.rs)

### Summary
`parse_u8_octal` only guarantees the source string is valid base-8 and that the resulting value fits in a `u8` (0–255); it does not guarantee the value fits in 3 bits (0–7) as required by `parse_wavelength_configuration`. Any octal string whose value is 8–255 (e.g. `"10"`..`"377"`) causes `format!("{:0>3b}", configuration_value)` to produce more than 3 characters, tripping the `assert_eq!` and panicking the biometric-capture task.

### Finding Description
The overcapture wavelength parameter is taken from the (colon-split) prefix of the `signup_extension_config.parameters` string and converted with: [1](#0-0) 
`from_str_radix(src, 8)` only rejects non-octal-digit characters or values that overflow `u8`; it happily returns values such as 8 (`"10"`), 63 (`"77"`), or 255 (`"377"`). That value is passed straight into `Configuration::new` → `parse_wavelength_configuration`: [2](#0-1) 
For any `configuration_value >= 8`, `format!("{configuration_value:0>3b}")` produces more than 3 binary digits, so `binary_repr.chars().count() != 3` and the `assert_eq!` panics with `"Overcapture wavelength parameter needs to be octal (<=3 bit)!"`. This is a live `assert!`/panic in production code (not test-only), reachable purely through the parsed configuration value — there is no upstream check that the parsed octal value is `<= 7` before calling `parse_wavelength_configuration`.

For the sub-range `0..=7`, the function behaves deterministically and consistently for both the actual IR wavelength sequencing (`extension_finished`) and the `Report` sent to the backend, since both are derived from the same `Configuration` instance built once and cloned into `Report`. The `push_front`-based reversal is therefore an internal, self-consistent encoding, not an attacker-triggerable mismatch between what is captured and what is reported — I could not identify a way for an attacker to desynchronize the report from the actual capture sequence given the current code structure.

### Impact Explanation
The verified exploitable defect is a **panic/crash** (denial of service) inside the biometric-capture task whenever the wavelength configuration value is in `8..=255`, rather than data corruption in `Report`. This matches an availability-impact bounty category (unhandled panic causing task/process crash during signup), not the "wrong LED attributed in Report" scenario hypothesized in the question, which I could not confirm as a real logic bug given the deterministic, self-consistent mapping used by both capture and reporting paths.

### Likelihood Explanation
Reachability depends entirely on whether the `wavelength_parameter` portion of `signup_extension_config.parameters` (consumed in `src/plans/biometric_capture/overcapture.rs` lines 107-132, sourced via `src/plans/qr_scan/user.rs`) can be influenced by an unprivileged attacker within their own signup session (e.g., via backend response content controllable by the attacker's session). I was not able to conclusively trace, within the available tool budget, whether this field's value is attacker-controllable end-to-end or is exclusively backend/operator-configured and not exposed to session-level attacker influence. This is the key unresolved precondition for exploitability under the stated threat model.

### Recommendation
Bound-check the parsed octal value before use: reject/clamp `wavelength_parameter` to `0..=7` in `parse_u8_octal` (or immediately after), and replace the `assert_eq!` in `parse_wavelength_configuration` with a graceful fallback (e.g., default configuration) instead of a panic, so no externally influenced value can ever reach an `assert!`/panic in production code.
