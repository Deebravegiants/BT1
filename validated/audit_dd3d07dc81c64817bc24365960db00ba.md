### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (tenant) identity is read from an unsigned HTTP header. `Webhooks::Registry.process` trusts that header value when dispatching the webhook to the app's handler, so an attacker who can obtain any single valid `(raw_body, hmac)` pair can replay it while swapping the `shop` header to any other shop domain, and the signature check will still pass.

### Finding Description
For OAuth callbacks, the gem correctly binds `shop` into the signed payload: `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` builds the HMAC-covered string from `code`, `host`, `shop`, `state`, `timestamp`: [1](#0-0) 

For webhooks, however, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body — `shop`, `topic`, and `webhook_id` are all read straight from unauthenticated headers and are never part of what gets HMAC-verified: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, so for a `Webhooks::Request` it only ever authenticates the body bytes: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the identity forwarded to the app's handler: [4](#0-3) 

The broken identity binding, expressed as an equality that the gem fails to enforce:
`shop_header_used_by_handler == shop_that_the_HMAC_actually_authenticates`
The left side comes from an attacker-controlled header; the right side does not exist at all, because the signable string never includes `shop`. Any request whose body+hmac pair is valid for the app's shared `client_secret` (the api secret key is one value shared by the app across all installed shops, per `Context.api_secret_key`/`HmacValidator.validate`) will pass verification regardless of which shop's domain is placed in the `shopify-shop-domain`/`x-shopify-shop-domain` header.

### Impact Explanation
This is a cross-tenant identity-binding failure. An attacker who controls (or has access to) any one legitimately-delivered webhook for the app — e.g., from their own shop's own installation, which is a normal, unprivileged merchant — can capture the exact `(raw_body, hmac)` pair Shopify sent them, then resend that identical body and signature to the app's webhook endpoint with the `shop` header rewritten to a different, victim shop's domain. Because `HmacValidator.validate` never binds `shop` into the signature, the forged request passes verification, and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload belongs to the victim shop: [5](#0-4) 
Any app that keys per-shop storage, GDPR/compliance actions (`shop/redact`, `customers/redact`, `customers/data_request`), or business logic off `WebhookMetadata#shop` can be tricked into applying another tenant's webhook body under an arbitrary shop identity, which is a cross-tenant integrity/data issue.

### Likelihood Explanation
Any developer/attacker who signs up their own shop for the app (unprivileged, no special credentials needed) automatically receives correctly HMAC-signed webhook deliveries for their own shop's events; capturing one such delivery is trivial (they operate the endpoint receiving it, or can proxy/log it). Replaying it with a modified `shop` header against the same public webhook endpoint requires no secret knowledge at all — only the mechanical omission of `shop` from `to_signable_string` needs to hold, which it does for every `Webhooks::Request`.

### Recommendation
Bind the tenant identity into the HMAC-covered material for webhooks the same way `AuthQuery` does for OAuth: either require verification that the signed body's declared `shop` (if present in `parsed_body`) matches the header-derived `shop`, or change `to_signable_string` to include the `shop`, `topic`, and `webhook_id` headers alongside the raw body so they are cryptographically bound to the signature that `Utils::HmacValidator.validate` checks.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` (fully unprivileged, self-service).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>` and some JSON `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker sends a new HTTP request to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Webhooks::Request#hmac`/`#to_signable_string` only exposes/signs `raw_body`, so `Utils::HmacValidator.validate` succeeds: [6](#0-5) 
6. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` even though the body actually originated from `attacker-shop.myshopify.com`: [7](#0-6) 
7. Any app logic keyed on `WebhookMetadata#shop` (data storage lookups, compliance actions, per-tenant business rules) now operates under the wrong, attacker-chosen tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
