### Title
Server-wide pipeline run history disclosure via `GET /v2/pipeline/runs` accessible to View-role users - (File: core/web/pipeline_runs_controller.go)

### Summary
The `PipelineRunsController.Index` handler, wired at `GET /v2/pipeline/runs` in [1](#0-0) , returns **every pipeline run on the node** when called without a job ID, exactly analogous to the Flowise `/api/v1/upsert-history` bug: an endpoint intended to show run history for a specific job instead dumps the entire server-wide history, unscoped by job, requester, or tenant, and is reachable by the lowest privileged authenticated role (`View`).

### Finding Description
In `PipelineRunsController.Index`, when the `ID` path parameter is empty, the controller calls `prc.App.JobORM().PipelineRuns(ctx, nil, offset, size)` with a `nil` job ID filter, which returns pipeline runs across **all jobs**, not scoped to the specific job the caller is inspecting: [2](#0-1) 

Notably, the handler also silently overrides the caller-provided page size to 1000 when none is specified ("Temporary: if no size is passed in, use a large page size"), maximizing the amount of data returned per request: [3](#0-2) 

This endpoint is registered under the authenticated `/v2` route group but requires only the `View` role (the lowest privilege tier) per the RBAC route map test, meaning any authenticated user — even one intended to only have read access — can retrieve the complete run history for the whole node: [1](#0-0) [4](#0-3) 

The returned `PipelineRunResource` includes `Inputs`, `Outputs`, and per-task `TaskRuns` output/error strings for every run, which can contain sensitive data flowing through bridge/HTTP tasks (e.g., external adapter URLs, request/response bodies, and other task-specific configuration parameters) — the same class of infrastructure/config leakage described in the Flowise advisory (Vector Store URLs, collection names, etc.): [5](#0-4) 

This mirrors the Flowise root cause precisely: an endpoint meant to be scoped to a specific resource (a job, in Chainlink's case; a user/tenant, in Flowise's) omits the scoping filter when no ID is supplied, and returns the full unbounded server-side dataset instead, with an oversized default page limit compounding the exposure.

### Impact Explanation
Any authenticated node API user, even one restricted to the `View` role for read-only dashboards, can enumerate the run history and task-level input/output data for **every job configured on the node**, not just jobs they are expected to observe. This can expose bridge/EA endpoint details, external adapter response bodies, and other operational configuration embedded in pipeline task outputs, enabling reconnaissance for further targeted attacks against the node's integrations — consistent with CWE-200 (Information Exposure) and CWE-862 (Missing Authorization) in the referenced advisory.

### Likelihood Explanation
High. The endpoint is reachable by any authenticated node API user with the lowest role (`View`), requires no special conditions, and is exercised simply by omitting the `ID` path parameter (`GET /v2/pipeline/runs`). No additional bypass is needed since scoping is missing by design in the handler logic, not merely misconfigured.

### Recommendation
- Require the `Index` handler to always scope results by job (or another explicit, authorized-for resource) instead of falling back to `nil`/all-jobs when no `ID` is provided; if a "list all jobs' runs" view is a genuine product requirement, gate it behind a stronger role (e.g., `Admin`) and apply strict pagination limits rather than defaulting to 1000.
- Remove the request-size override that silently substitutes a large page size (1000) when the caller does not specify one, and enforce a reasonable server-side maximum page size regardless of client input.
- Audit `PipelineRunResource`/`PipelineTaskRunResource` serialization to ensure sensitive task inputs/outputs (e.g., bridge/EA URLs, headers, secrets) are redacted before being returned via the API.

### Proof of Concept
1. Authenticate as a `View`-role API user (via session or API token) against the node's `/v2` API.
2. Issue `GET /v2/pipeline/runs` (no query parameters).
3. Observe that the response contains up to 1000 pipeline runs spanning **all jobs** on the node (verify via the `jobId`/`pipelineSpec` field in each returned `pipelineRun` resource differing across multiple unrelated jobs), rather than being scoped to a job the requester specifically queried, matching the unscoped, oversized response pattern described in the Flowise report.

```go
func (prc *PipelineRunsController) Index(c *gin.Context, size, page, offset int) {
	id := c.Param("ID")

	// Temporary: if no size is passed in, use a large page size. Remove once frontend can handle pagination
	if c.Query("size") == "" {
		size = 1000
	}

	var pipelineRuns []pipeline.Run
	var count int
	var err error

	ctx := c.Request.Context()
	if id == "" {
		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, nil, offset, size)
	} else {
		jobSpec := job.Job{}
		err = jobSpec.SetID(c.Param("ID"))
		if err != nil {
			jsonAPIError(c, http.StatusUnprocessableEntity, err)
			return
		}

		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)
	}

	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResources(pipelineRuns, prc.App.GetLogger())
	paginatedResponse(c, "pipelineRun", size, page, res, count, err)
```

```go
type PipelineRunResource struct {
	JAID
	Outputs []*string `json:"outputs"`
	// XXX: Here for backwards compatibility, can be removed later

	Errors       []*string                         `json:"errors"`
	AllErrors    []*string                         `json:"allErrors"`
	FatalErrors  []*string                         `json:"fatalErrors"`
	Inputs       jsonserializable.JSONSerializable `json:"inputs"`
	TaskRuns     []PipelineTaskRunResource         `json:"taskRuns"`
	CreatedAt    time.Time                         `json:"createdAt"`
	FinishedAt   null.Time                         `json:"finishedAt"`
	PipelineSpec PipelineSpec                      `json:"pipelineSpec"`
}

// GetName implements the api2go EntityNamer interface
func (r PipelineRunResource) GetName() string {
	return "pipelineRun"
}

func NewPipelineRunResource(pr pipeline.Run, lggr logger.Logger) PipelineRunResource {
	lggr = lggr.Named("PipelineRunResource")
	trs := make([]PipelineTaskRunResource, 0, len(pr.PipelineTaskRuns))
	for i := range pr.PipelineTaskRuns {
		trs = append(trs, NewPipelineTaskRunResource(pr.PipelineTaskRuns[i]))
	}

	outputs, err := pr.StringOutputs()
	if err != nil {
		lggr.Errorw(err.Error(), "out", pr.Outputs)
	}

	fatalErrors := pr.StringFatalErrors()

	return PipelineRunResource{
		JAID:         NewJAIDInt64(pr.ID),
		Outputs:      outputs,
		Errors:       fatalErrors,
		AllErrors:    pr.StringAllErrors(),
		FatalErrors:  fatalErrors,
		Inputs:       pr.Inputs,
		TaskRuns:     trs,
		CreatedAt:    pr.CreatedAt,
		FinishedAt:   pr.FinishedAt,
		PipelineSpec: NewPipelineSpec(&pr.PipelineSpec),
	}
}
```
