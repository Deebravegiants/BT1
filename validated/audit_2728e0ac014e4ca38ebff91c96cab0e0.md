### Title
Extreme market balances can permanently freeze interest accrual through an `i128` index-value overflow - (File: common/src/rates/simulate.rs)

### Summary
The accrual path computes `borrowed * borrow_index` and `supplied * supply_index` as `i128` RAY values before applying the configured borrow-index ceiling. A legally configured high-cap market can accumulate enough scaled supply and debt that ordinary index growth makes this product unrepresentable; the resulting `MathOverflow` permanently prevents subsequent accrual-dependent operations. [1](#0-0) 

### Finding Description
`accrue_step` first unscales total borrowed and supplied shares through `scaled_to_original`, which directly calls `scaled.mul(env, index)`. [2](#0-1) [3](#0-2) 

It then computes a new borrow index and calls `calculate_supplier_rewards`, which again multiplies the same scaled debt by both the old and new borrow indexes. [4](#0-3) [5](#0-4) 

The borrow-index ceiling is applied only after `old_index.mul(env, interest_factor)`, so it does not protect the earlier or later index-value products from overflowing `i128`. [6](#0-5)  The ceiling is `1e36` raw RAY, equivalent to a 1-billion-times multiplier because `RAY` is `1e27`. [7](#0-6) 

Market caps only ensure that an asset amount can be rescaled to RAY within `i128`; they do not ensure that the resulting scaled balance can be multiplied by the maximum permitted index. [8](#0-7) 

Once the stored totals and index reach the unrepresentable domain, `global_sync` panics during `accrue_step`, and every pool mutation that accrues before committing reaches the same panic. [9](#0-8) [10](#0-9) 

The controller exposes the affected operations to ordinary users: `withdraw` for owners or delegates, `repay` for anyone, and permissionless `liquidate` and `clean_bad_debt`. [11](#0-10)  These calls eventually invoke the owner-gated pool operations through the controller, including `withdraw`, `repay`, and `update_indexes`. [12](#0-11) [13](#0-12) 

The repository's stress test demonstrates the exact failure: a 1-billion-whole-token market at 98% utilization eventually returns `MathOverflow`, before `MAX_BORROW_INDEX_RAY` is reached, and subsequent withdraw and repay attempts fail with the same error. [14](#0-13) 

### Impact Explanation
This permanently freezes all funds and debt operations in the affected market because users cannot withdraw supplied assets, borrowers cannot repay, and liquidators cannot liquidate through accrual-dependent controller paths. [15](#0-14) 

Because pool mutations run `global_sync` before applying the operation, no ordinary state-changing recovery path exists that skips the overflowing total-value computation. [9](#0-8) [16](#0-15) 

### Likelihood Explanation
Triggering the condition requires an exceptionally large market balance, sustained borrowing, and enough elapsed accrual for the index-value product to cross the `i128` boundary, so it is not a low-capital immediate attack. [17](#0-16) 

The configuration used by the proof is nevertheless within the protocol's own validation domain: caps may be set as high as `max_cap_for_decimals`, utilization can reach the configured maximum, and `max_borrow_rate` may be as high as 200% APR. [18](#0-17) [19](#0-18) 

### Recommendation
Enforce a market-level scaled-share ceiling derived from `i128::MAX / MAX_*_INDEX_RAY`, rather than merely checking that the initial asset-to-RAY rescale fits. [20](#0-19) [7](#0-6) 

Alternatively, calculate aggregate supplied and debt values with a widened `I256` result and explicitly clamp or rebalance state before converting back to `i128`. [3](#0-2) [21](#0-20) 

A recovery path should also allow index state to be clamped or market totals to be reduced without first evaluating the overflowing aggregate-value expressions. [1](#0-0) 

### Proof of Concept
1. Configure an 18-decimal borrowable market with the steep valid XLM stress curve and set its spoke supply/borrow caps to `max_cap_for_decimals(18)`. [22](#0-21) [18](#0-17) 
2. Call `Controller::supply` for `BOB` with `BILLION * 10^18` base units of `BIG18`. [23](#0-22) [24](#0-23) 
3. Supply sufficient `COL` collateral and call `Controller::borrow` for `ALICE` with `98%` of the `BIG18` principal. [25](#0-24) [26](#0-25) 
4. Advance ledger time and repeatedly invoke index accrual until `accrue_step` panics with `MathOverflow`; the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [27](#0-26) 
5. Attempt `Controller::withdraw` for the supplier and `Controller::repay` for the borrower; both fail with `MathOverflow`, leaving user funds and debt operations frozen. [28](#0-27)

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;

    let mut remaining = cache.elapsed_ms();

        remaining = remaining.saturating_sub(chunk);
    }

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
