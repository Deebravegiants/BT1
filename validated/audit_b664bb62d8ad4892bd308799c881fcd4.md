Found a concrete analog: `SimplexPaymaster._getOraclePrice` at `evm/src/utils/SimplexPaymaster.sol:662-676` performs `block.timestamp - updatedAt` on a Chainlink `AggregatorV3Interface.latestRoundData()` return value, with no check that `updatedAt <= block.timestamp`. This is structurally the same class of bug as the Olympus finding: an unchecked-sign subtraction between "now" and an externally/administratively supplied timestamp field that is trusted to be in the past.

### Title
Chainlink `updatedAt` timestamp underflow can permanently DoS SimplexPaymaster's paymaster path - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`_getOraclePrice()` computes oracle staleness with `block.timestamp - updatedAt` where `updatedAt` comes directly from `oracle.latestRoundData()`. Solidity ^0.8 reverts on underflow. If `updatedAt` is ever equal to or greater than `block.timestamp` (a future/skewed round timestamp), every call to `_getOraclePrice` — and therefore every ERC-4337 UserOp using this paymaster for gas payment, plus `swapAndDeposit` fee recycling and `getTokenPrice`/`estimateTokenCost` views — reverts.

`_getOraclePrice` is called from `_tokenPrice` (used in `_fetchDetails`, the paymaster's validation-phase hook run on every incoming UserOp) and `swapAndDeposit`: [2](#0-1) [3](#0-2) 

There is no guard ensuring `updatedAt <= block.timestamp` before the subtraction. `latestRoundData()` is an external call to a Chainlink-compatible aggregator that governance registers via `RegisterToken`/`UpdateParams` governance messages, but the returned `updatedAt` value on any given call is not otherwise validated. Cross-chain block-timestamp skew, a misbehaving/compromised aggregator, a proxy/mock feed, or a chain reorg/clock adjustment producing a slightly-future `updatedAt` all make this reachable without needing a malicious admin — the report explicitly targets this bug class (an unchecked subtraction of a timestamp field that can legitimately or accidentally be ≥ `block.timestamp`), matching the root cause in the Olympus `SingleSidedLiquidityVault._accumulateInternalRewards` finding where `block.timestamp - rewardToken.lastRewardTime` underflows once `lastRewardTime` exceeds `block.timestamp`.

### Impact Explanation
Once triggered, `_getOraclePrice` reverts for that oracle on every call, and since `_tokenPrice` is invoked from `_fetchDetails` (the paymaster validation hook), **every UserOp attempting to pay gas through the affected registered token reverts** — a full denial-of-service on the paymaster's core function for that token, and by extension `swapAndDeposit` fee recycling for that token stops working too. Because `_relayer`/governance-only paths gate configuration changes, an app relying on this paymaster is effectively locked out of gas sponsorship until governance re-registers the token with a different oracle via a fresh cross-chain governance message (`RegisterToken`), which itself requires relayer delivery and a challenge-period wait — a nontrivial, delayed recovery. This satisfies the "route unable to deliver messages / permanent freezing of intended function" bar since the paymaster path becomes unusable for affected UserOps until a governance round-trip completes.

### Likelihood Explanation
Medium. It does not require a malicious admin — it can be triggered by any of: (1) a Chainlink-compatible feed returning a timestamp marginally ahead of the local `block.timestamp` due to clock/block skew (well documented on L2s with sequencer timestamp quirks), (2) a mock/incorrectly-integrated oracle for a newly registered token, or (3) a stale/compromised oracle emitting a bogus future `updatedAt`. Given the contract explicitly supports "any token with a Chainlink feed" and governance can register arbitrary oracle addresses across many chains, the surface for an oracle emitting an out-of-expectation `updatedAt` is non-trivial.

### Recommendation
Guard the subtraction, mirroring the recommended fix for the Olympus finding — skip/treat as fresh (or explicitly revert with a distinct, recoverable error) when `updatedAt > block.timestamp`, e.g.:
```solidity
uint256 age = block.timestamp > updatedAt ? block.timestamp - updatedAt : 0;
if (age > maxOracleAge) revert StaleOraclePrice(address(oracle), updatedAt);
```
This prevents the underflow revert path from permanently wedging the token's oracle price lookup and keeps `StaleOraclePrice`/silent-pass semantics well-defined for any `updatedAt` value the aggregator returns.

### Proof of Concept
1. Governance registers a token via `RegisterToken` with `oracle` pointing to a Chainlink-compatible aggregator.
2. At some point, `oracle.latestRoundData()` returns `updatedAt = block.timestamp + 1` (or any value `> block.timestamp`) — achievable via clock skew across chains, an L2 with drifting `block.timestamp`, or a misbehaving/mocked feed.
3. Any UserOp that pays gas with this token calls into `_fetchDetails` → `_tokenPrice` → `_getOraclePrice`, executing `block.timestamp - updatedAt`, which underflows and reverts under Solidity ^0.8 checked arithmetic.
4. Every subsequent UserOp for that token reverts at validation, and `swapAndDeposit(token, ...)` also reverts, until the aggregator's `updatedAt` falls back below `block.timestamp` or governance re-registers the token with a different oracle.
