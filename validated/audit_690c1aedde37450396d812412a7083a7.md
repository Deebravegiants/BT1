### Title
Webhook `shop-domain` (tenant identity) is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw HTTP body, but the `shop` (tenant identity) that is handed to the app's webhook handler is read from an HTTP header that is excluded from that signature. This breaks the intended binding `verified_bytes == acted_on_bytes`, analogous to the Timelock issue where the executed target/callData was not actually checked against what was verified.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC signature exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw request body (`@raw_body`): [2](#0-1) 

However, the `shop` (tenant identity), `topic`, `api_version`, and `webhook_id` fields that the registry uses to dispatch and identify the merchant are all parsed from HTTP headers, which are never part of the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then immediately trusts `request.shop` (from the unverified header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This means the equality the caller implicitly relies on — "the shop that was HMAC-verified" == "the shop the handler acts on" — does not hold. An attacker who has captured or replayed one legitimately-signed webhook body (bodies for many topics are near-identical/predictable or replayable, e.g. `customers/redact`, `shop/redact`) can resend that same signed body with a different `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. Because `Digest.hexencode(Base64.decode64(hmac_header))` is computed via `OpenSSL.secure_compare` against the body only, the signature still validates, yet `request.shop` — and therefore `data.shop` passed to the handler — reflects the attacker-controlled header, not the shop that actually produced the signed payload.

### Impact Explanation
This is a cross-tenant identity-binding break: a webhook body cryptographically bound to shop A can be relabeled as belonging to shop B (or vice versa) without invalidating the HMAC check, because the shop is not part of the signed material. Any app that keys tenant-scoped actions (record lookups, redaction, data deletion, billing side effects) off `WebhookMetadata#shop` as returned by this gem is exposed to cross-tenant data leakage or cross-tenant action execution triggered by an unprivileged internet user who can reach the app's webhook endpoint and has captured or replayed any one valid signed webhook body.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly-signed webhook body (obtainable via a public/test store the attacker controls, since webhook secrets are shared per app rather than per-shop, and via replay/relabeling of a captured request), then resend it with a forged `shop-domain` header pointing at a victim shop. No access token, `client_secret`, or `api_secret_key` is required — only network reachability to the app's webhook endpoint. This fits the "unprivileged internet user" threat model directly and does not depend on the host application ignoring documented behavior, since the gem itself performs the HMAC validation and dispatch and never authenticates the shop header.

### Recommendation
Include `shop` (and ideally `topic`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop-domain header to the signed body before it is used for dispatch/handler identification — e.g., require the caller to reconcile `request.shop` against an out-of-band trusted source (such as the registered app installation for that HMAC-verified payload) rather than trusting the raw header value once the body HMAC passes.

### Proof of Concept
1. Register a webhook handler for topic `customers/redact` that performs a shop-scoped action (e.g., deletes records for `data.shop`).
2. Obtain (or self-generate, using a store you control and the shared app secret) a validly HMAC-signed webhook body/HMAC pair for topic `customers/redact`.
3. Send a POST to the app's webhook endpoint with the original signed body and HMAC header, but replace `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body against the HMAC.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged header value `victim-shop.myshopify.com`, and the handler executes its shop-scoped logic against the victim shop despite the payload never having been signed in relation to that shop. [4](#0-3)
