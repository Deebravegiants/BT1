### Title
Excess native ETH sent to `EvmHost.dispatch()`/`dispatch(DispatchGet)`/`fundRequest()` is refunded to the host itself and permanently stranded, not returned to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` swap incoming `msg.value` for the exact fee amount via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard UniswapV2Router `swapETHForExactTokens` refunds any unspent ETH to its immediate caller (`msg.sender` of the swap call), which here is `EvmHost` itself — not the original transaction sender. Unlike the analogous fee-swap in `IntentGatewayV2.placeOrder`, which explicitly computes `msgValue -= amounts[0]` and calls `_sendValue(msg.sender, msgValue)` to return the unspent ETH, `EvmHost` never forwards this refund back out. This mirrors the `ArbitrumSwaps` bug pattern where a refund address of `address(this)` causes native value to accumulate on a "router-like" contract instead of the true payer.

### Finding Description
In `evm/src/core/EvmHost.sol`, all three fee-paying entry points follow the same pattern [1](#0-0) :

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

The same pattern repeats in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

`swapETHForExactTokens` on the standard UniswapV2 router only guarantees delivery of exactly `post.fee` output tokens to `address(this)` (the destination for `path[1]`); any *unspent* input ETH beyond what was needed is refunded to `msg.sender` of the swap call, i.e. `EvmHost` itself. None of these three functions computes or forwards the leftover ETH back to `_msgSender()` (the caller who actually funded the transaction). The compare point in this same codebase, `IntentGatewayV2.placeOrder`, does track and refund this delta correctly [4](#0-3)  using `msgValue -= amounts[0]` followed by `_sendValue(msg.sender, msgValue)` — a pattern conspicuously absent from `EvmHost`.

As a result, any caller who supplies `msg.value` greater than the exact ETH cost of the fee-token swap (which is normal, since callers must overestimate slippage/price when they cannot predict the exact swap output) leaves the unspent remainder permanently on `EvmHost`'s own native balance, unaccounted for and unreachable except by governance's own `withdraw()` (host revenue).

### Impact Explanation
Any unprivileged dispatcher, app, or end user calling `dispatch()`/`fundRequest()` with native ETH to pay protocol fees loses the unspent portion of `msg.value` with no path to reclaim it — this is a permanent freezing/loss of user funds, since only `IHostManager.withdraw()` (restricted to `_hostParams.hostManager`, itself only reachable via cross-chain governance) can move ETH out of `EvmHost` [5](#0-4) . Because pricing an exact `swapETHForExactTokens` amount in advance is inherently imprecise (AMM price movement between quote and execution), practically every native-fee payer will overpay by some margin, and that margin accrues indefinitely to the host contract rather than being returned. Over the volume of cross-chain dispatches this could represent a continuous, systemic loss of user value with no self-service recovery mechanism — a Medium-severity permanent-freezing-of-funds issue, directly reachable from a single `dispatch()`/`fundRequest()` call by any unprivileged caller.

### Likelihood Explanation
High. This triggers on the ordinary/expected native-fee-payment path of `EvmHost.dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` any time a caller doesn't supply the *exact* minimal wei amount for the swap — which is the normal case, since the exact swap cost cannot be known precisely ahead of time (front-running/slippage/price drift). No special conditions or malicious actors are required; this happens to well-intentioned integrators every time they slightly overpay.

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the returned `amounts[0]` (actual ETH spent) and refund the difference (`msg.value - amounts[0]`) to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` [6](#0-5) .

### Proof of Concept
1. Caller A invokes `EvmHost.dispatch(DispatchPost)` with `msg.value = 1 ether` while the required fee-token swap only actually costs `0.1 ether` worth of ETH.
2. Inside `dispatch`, `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes, delivering exactly `post.fee` feeTokens to `EvmHost`, and refunding the unspent `0.9 ether` to `msg.sender` of the swap call — which is `EvmHost` itself.
3. `dispatch()` returns without ever inspecting or forwarding this `0.9 ether`; it now sits in `address(EvmHost).balance`.
4. Caller A has no function to reclaim the `0.9 ether`; only cross-chain governance via `HostManager` → `EvmHost.withdraw()` can later move it, and typically to a protocol treasury, not back to Caller A.
5. Repeating this across every native-fee dispatch call permanently accumulates unreachable user ETH on `EvmHost`.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
