## Title
Webhook HMAC only covers the raw body, allowing shop/topic header spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` trusts and passes to the app's handler come from unauthenticated HTTP headers. This is the "field acted on but not covered by the HMAC" identity-binding break: the bytes cryptographically verified (`raw_body`) are not the same bytes the app relies on to identify which tenant (`shop`) the webhook belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC over exactly `to_signable_string` (i.e., the raw body) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates on this HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unsigned) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the signature only binds the body, any request whose body and `X-Shopify-Hmac-Sha256` header form a valid `(body, hmac)` pair — such as one legitimately obtained from a webhook sent to a shop the attacker controls (e.g., by installing their own app/dev store and capturing a genuine `app/uninstalled` or similar webhook, which commonly has a fixed/empty or attacker-influenced body) — remains valid when replayed with an arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header. `HmacValidator.validate` will return `true` because it never inspects the headers, and `Registry.process` will hand the attacker-chosen `shop`/`topic` values to the host application's webhook handler as if Shopify itself vouched for them.

### Impact Explanation
This breaks the equality `shop authenticated by HMAC == shop trusted by handler`. Because the host application relies on the gem's HMAC validation to establish authenticity of `WebhookMetadata#shop`, an attacker can cause the application to process actions attributed to a victim shop (e.g., mandatory compliance webhooks `shop/redact`, `customers/redact`, `customers/data_request`, or ordinary business webhooks) using a signature that was only ever valid for the attacker's own body/shop pairing. Depending on how the host app keys per-tenant state off `data.shop`, this enables cross-tenant confusion — the classic "Critical - cross-tenant access" impact category, since data intended for or attributed to one merchant can be forged to appear as belonging to another.

### Likelihood Explanation
An attacker only needs the ability to receive one legitimate, validly-signed webhook for a body they control or can predict (trivial for a person who installs the app on their own store, since Shopify signs any webhook body sent to any installed shop, including the attacker's own). No access to `api_secret_key`, tokens, or a privileged account of the victim is required — only network access to the app's public webhook endpoint and one captured signed request.

### Recommendation
Include the identity-defining headers (`shop-domain`, `topic`, `webhook_id`/`api_version` as applicable) in the signed material that `to_signable_string` returns (or otherwise incorporate them into an authenticated composite that is verified before trusting them), rather than signing only the raw body. At minimum, cryptographically bind `shop` to the signature so that `Registry.process` cannot be tricked into associating a valid signature with an unauthenticated shop domain.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`; Shopify sends a genuine webhook, e.g. `app/uninstalled` with body `{}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-of-{}>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends this exact `(body="{}", hmac=<valid-hmac-of-{}>)` pair to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com` and/or `X-Shopify-Topic` with a different registered topic.
3. `Webhooks::Request.new` parses these headers unchanged; `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only ("{}") and it matches, so validation succeeds: [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata` carrying the attacker-controlled `shop: "victim.myshopify.com"`, causing the host app to act as if Shopify authentically reported this event for the victim's tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
