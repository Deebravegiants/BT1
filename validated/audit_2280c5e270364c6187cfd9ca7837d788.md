## Title
Webhook HMAC does not bind the `shop` (or `topic`/`webhook-id`) header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then hands the unauthenticated `shop` value straight to the host application's handler. This lets any party who possesses one valid `(body, hmac)` pair — e.g., a merchant receiving genuine webhooks for their own store — replay that pair to the app's webhook endpoint with a forged `shop-domain` header, causing the app to process the payload as if it originated from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature using `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac` — it has no knowledge of, and cannot bind, the header fields: [3](#0-2) 

`Registry.process` only checks this body HMAC, then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, etc., and forwards it to the host app's registered handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain string field with no further validation (e.g. no `ShopValidator.sanitize!` call, unlike OAuth flows): [5](#0-4) 

This breaks the intended identity binding: `hmac_is_valid_for(body) == true` is treated by the gem as proof that `shop == request.shop`, when in fact the HMAC only proves `body` was produced by Shopify for *some* registered endpoint — it says nothing about which shop's header accompanied it. Formally, the gem conflates:
- `hmac_valid(body, api_secret_key)` (what is actually verified)
- `shop_header == originating_shop` (what the app implicitly trusts, unverified)

### Impact Explanation
An attacker who legitimately installs the target app on their own store (or otherwise obtains one valid `(raw_body, X-Shopify-Hmac-Sha256)` pair from any webhook delivery) can replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `Registry.process` will accept it as authentic and dispatch it to the app's handler labeled as coming from the victim shop. Since apps commonly key business logic, session/token lookups, and tenant-scoped data mutations off `WebhookMetadata#shop` (e.g. `app/uninstalled` to revoke tokens, `shop/redact` / `customers/redact` mandatory compliance topics, order/inventory sync), this enables cross-tenant data corruption, spoofed compliance actions against a shop the attacker doesn't control, or forced processing of attacker-chosen payload content attributed to another merchant. This is a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation requires no privileged credentials: any user able to install the app on a shop they control (or capture one delivered webhook) can obtain a valid signed body, then simply change the `shop-domain` header on replay, since headers are not included in the signable string. No knowledge of `api_secret_key` is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value verified by the HMAC, or independently verify that the `shop-domain` header corresponds to a shop with an actual registered relationship (e.g., cross-check against a known/allowed shop store) before constructing `WebhookMetadata`. At minimum, sanitize/validate `request.shop` via `ShopValidator` and document that host applications must not trust `WebhookMetadata#shop` as an authenticated value unless it's cross-checked against session/shop records maintained independently of the webhook headers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the app with body `B` and a valid `X-Shopify-Hmac-Sha256` header computed over `B` using the app's real `api_secret_key`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request and replays it to the same endpoint, keeping body `B` and the HMAC header identical, but changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC: [6](#0-5) 
5. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act as though `victim-shop` sent payload `B`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
