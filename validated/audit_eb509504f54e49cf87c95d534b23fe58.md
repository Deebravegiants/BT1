### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by the handler are read from unauthenticated HTTP headers. This breaks the identity binding `shop authenticated == shop acted upon`, allowing a request with a genuinely-signed body to be replayed with a forged `shop-domain` header pointing at a different (victim) tenant.

### Finding Description
`Registry.process` validates a webhook request purely with `Utils::HmacValidator.validate(request)` before invoking the handler: [1](#0-0) 

The HMAC validator computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only** the raw body — `@raw_body` — never any of the Shopify headers: [3](#0-2) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers with no cryptographic binding to the signed body: [4](#0-3) 

These unauthenticated values are then passed directly into the handler as the tenant identity for the webhook: [5](#0-4) 

Because the gem's app secret (`api_secret_key`) is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app can receive a legitimately-signed webhook for their own store — a valid `(raw_body, hmac)` pair. Since the HMAC never covers the `shop-domain` (or `topic`/`webhook_id`) header, that same `(raw_body, hmac)` pair remains valid if replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to point at a different, victim shop. `Utils::HmacValidator.validate` will still return `true` (it only checks the body), and `handler.handle` will be invoked believing the event originates from the victim shop.

This is the same root-cause pattern as the report: a value that is *acted upon* (the tenant/shop identity used to route/act on the webhook) is not the value that is *cryptographically verified* (only the body is verified). The equality that should hold — `hmac_verified_scope == identity_acted_upon` — is broken because the verified scope is `{body}` while the identity acted upon is `{shop, topic, webhook_id}` from unauthenticated headers.

### Impact Explanation
This enables **cross-tenant access**: an attacker who is merely a legitimate (unprivileged relative to any other tenant) installer of the app can forge webhook deliveries that the app will process as if they came from another merchant's shop. Depending on what the registered `WebhookHandler#handle` implementation does with `WebhookMetadata#shop` (e.g., looking up/mutating that shop's stored session, data, or triggering shop-scoped side effects), this can lead to cross-tenant data corruption, unauthorized actions performed against a victim shop's session, or information disclosure — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any actor able to install the app on at least one shop (a low bar, effectively an "unprivileged" party from the perspective of any other tenant) can obtain a genuinely HMAC-signed webhook body/HMAC pair addressed to their own shop, then replay it directly to the app's public webhook receiving endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. No secret material, TLS interception, or social engineering is required — only knowledge of the app's public webhook URL, which is typically documented/discoverable.

### Recommendation
Bind the shop/topic/webhook identity into the signed material, or otherwise cryptographically tie header claims to the verified body. Concretely, have `Webhooks::Request#to_signable_string` (or a wrapper the `HmacValidator` consumes) also verify that the `shop-domain`, `topic`, and `webhook-id` headers match values Shopify actually delivered for that specific webhook — e.g. by requiring callers to additionally validate the shop against a known/registered shop list, or by rejecting/flagging any mismatch between the header-derived shop and an out-of-band verified identity before invoking `handler.handle`. At minimum, document prominently that `request.shop` from `Webhooks::Request` is **not** authenticated by the HMAC and must not be trusted as a tenant identity without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Shopify delivers a legitimate webhook to the app for `attacker-shop.myshopify.com` with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared `api_secret_key`.
3. Attacker captures the exact `raw_body` and `hmac` value from that delivery.
4. Attacker POSTs the same `raw_body` and `hmac` directly to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally forges `topic`/`webhook-id`).
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (i.e., `raw_body`) — this still matches, so validation passes: [6](#0-5) 
6. `handler.handle` is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the event body and signature were never associated with that shop by Shopify — a cross-tenant identity spoof.
