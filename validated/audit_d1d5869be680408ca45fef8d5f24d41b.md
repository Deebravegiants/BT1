Audit Report

## Title
`ERC20Transactor` Credits Requested Amount Instead of Actually-Received Amount on Fee-on-Transfer ERC20 Tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the ERC-20 `transfer()` function on an arbitrary Solidity contract and, upon a `true` return value, unconditionally credit/move the caller-supplied `amount` into/out of XCM holding, without verifying the checking account's or beneficiary's actual balance delta. Because the `Matcher` (`ERC20Matcher`) used to gate which contract addresses are transactable is permissionless — any `AccountKey20` location matches, per `IsLocalAccountKey20` — an attacker can deploy their own fee-on-transfer ERC-20 contract and exploit this mismatch to bridge more asset value than is actually custodied in the `TransfersCheckingAccount`.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor sends an ERC-20 `transfer(checking_address, amount)` call and, if the call succeeds (`is_success == true`), creates `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the caller-supplied `amount`, not the actual balance increase of `TransfersCheckingAccount`: [1](#0-0) . The symmetrical `deposit_asset_with_surplus` has the same pattern, treating a `true` return from `transfer()` as full success without checking the beneficiary's actual receipt: [2](#0-1) .

Critically, the asset-matching gate is not a governance-curated allowlist. `ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [3](#0-2) , and `IsLocalAccountKey20` matches *any* location of the shape `(0, [AccountKey20 { .. }])` [4](#0-3) . `MatchedConvertedConcreteId::matches_fungibles` only checks `MatchAssetId::contains(id)` before converting [5](#0-4) , so any 20-byte address — including an attacker-deployed contract — is accepted as a valid transactable ERC-20 asset id. This resolves the "open question" the researcher raised: the matcher is permissionless, not governance-gated.

This confirms the exploit precondition is realistic: an unprivileged user can deploy an arbitrary fee-on-transfer ERC-20 contract via `pallet-revive` and immediately use it as an XCM asset through `ERC20Transactor` on Asset Hub Westend, where it is wired into `AssetTransactors` [6](#0-5) .

## Impact Explanation
When a fee-on-transfer ERC-20 is withdrawn, `TransfersCheckingAccount` receives less than `amount` (fee deducted), yet the XCM holding register is credited with the full `amount`. If this asset is used in a reserve-transfer flow (`WithdrawAsset` + `DepositReserveAsset`/`ReserveAssetDeposited` to a remote chain), the destination chain mints/represents the full requested `amount` as backed derivative value, while the actual custodied balance in the checking account is smaller. This produces a durable, uncorrectable accounting mismatch: unbacked derivative supply on the remote side that is never reconciled by a later failed `transfer()` call (since the mint on the remote chain is independent of the checking account's true balance). Each such transfer compounds the deficit, degrading solvency of the local asset backing over time. This is a genuine integrity/accounting defect at the bridge layer between XCM and EVM-style contracts, not a purely theoretical issue.

## Likelihood Explanation
The `Matcher` is confirmed permissionless — no governance/allowlist step restricts which ERC-20 contract addresses can be used, since `IsLocalAccountKey20` accepts any `AccountKey20` junction. Any user can deploy a fee-on-transfer contract via `pallet-revive` and immediately exploit the discrepancy through ordinary reserve-transfer XCM programs, requiring no elevated privileges, victim mistakes, or unrealistic assumptions. This makes the likelihood realistic and directly attacker-controlled.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the ERC-20 contract's `balanceOf` for the relevant account (checking account or beneficiary) immediately before and after the `transfer()` call, and use the observed delta — not the caller-specified `amount` — as the value credited into `AssetsInHolding` or transferred onward. Alternatively, restrict `ERC20Matcher`/asset registration to an explicitly governance-curated allowlist of audited, fee-free ERC-20 contracts, and document this as a hard security requirement.

## Proof of Concept
1. Deploy a Solidity ERC-20 contract via `pallet-revive` with a 1% transfer fee (deducted from recipient on every `transfer()`).
2. Reference this contract's address as an `AccountKey20` XCM asset id (matched automatically by `ERC20Matcher`/`IsLocalAccountKey20`), no registration/whitelisting required.
3. Submit an XCM program performing `WithdrawAsset` of `amount = 1_000_000` of this token followed by a reserve-transfer instruction targeting a remote chain.
4. `withdraw_asset_with_surplus` calls `transfer(checking_address, 1_000_000)`; `TransfersCheckingAccount` actually receives `990_000`, but `Erc20Credit(1_000_000)` is placed into XCM holding and reflected as `1_000_000` in the outgoing `ReserveAssetDeposited` message.
5. The remote chain mints/credits `1_000_000` of the derivative asset, while only `990_000` of real backing exists in the checking account — a permanent, compounding accounting deficit.
