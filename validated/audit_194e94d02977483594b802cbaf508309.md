Audit Report

## Title
Outbound HTTP response cache key omits WorkflowID, allowing cross-workflow response cache poisoning/leakage - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's `responseCache` for outbound HTTP actions keys cached responses solely by `req.Hash()` [1](#0-0) , and the handler's own test suite proves that two requests differing only by `WorkflowID` produce identical hashes [2](#0-1) , directly contradicting the documented design guarantee that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [3](#0-2) .

## Finding Description
`Fetch` and `Set` use `req.Hash()` as the sole cache-map key [4](#0-3) [5](#0-4) . The struct comment states the hash is derived from "method, URL, headers, body, workflowOwner" [6](#0-5) , and the test suite confirms `WorkflowOwner` changes the hash but `WorkflowID` does not [7](#0-6) . The `req` object used for hashing and caching comes from an `OutboundHTTPRequest` unmarshalled directly from a node-relayed message in `makeOutgoingRequest`, then passed unmodified into `Fetch`/`Set` [8](#0-7) . There is no additional namespacing by `WorkflowID` anywhere in the cache path — no wrapper, no key concatenation — so the only actual scoping applied is `WorkflowOwner`, not `WorkflowID` as documented. Note: `OutboundHTTPRequest.Hash()` itself is implemented in the external `chainlink-common` dependency, not in this repository, so I could not directly inspect its full implementation; the conclusion that `WorkflowID` is excluded is based entirely on this repo's own test assertions, which explicitly and unambiguously assert `hash1 == hash2` for differing `WorkflowID` values.

## Impact Explanation
Two different workflows belonging to the **same workflow owner** that issue outbound HTTP requests with identical method/URL/headers/body will collide on the same cache entry. This means Workflow B can receive Workflow A's cached HTTP response body/headers without making its own request — a concrete cross-workflow response cache confusion/leakage, matching the in-scope "cross-user response corruption" impact class. This is a real logic bug in the gateway's caching layer that undermines the isolation guarantee explicitly documented in the handler's README.

## Likelihood Explanation
Exploitation requires two workflows that share the same `WorkflowOwner` (a normal, unprivileged scenario — one owner/customer commonly deploys multiple workflows) issuing outbound HTTP requests with identical method/URL/headers/body while caching is enabled (`CacheSettings.Store`/`MaxAgeMs`). No operator, admin, or host access is needed — only normal workflow-node capability usage, so this is triggerable by an unprivileged actor within their own account across their own workflows. It does **not**, however, enable cross-*owner* leakage, since `WorkflowOwner` is still correctly included in the hash — this limits the severity somewhat compared to the report's framing, but the scoping failure relative to the documented (and presumably intended) per-workflow isolation is real and demonstrated by the repo's own tests.

## Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (in `chainlink-common`), or namespace the `responseCache` key by `WorkflowID` (e.g., `workflowID + ":" + req.Hash()`) before use in `Fetch`/`Set` in `core/services/gateway/handlers/capabilities/v2/response_cache.go`, so cached responses are only shared within the same workflow, matching the README's documented isolation guarantee.

## Proof of Concept
The existing test at `core/services/gateway/handlers/capabilities/v2/response_cache_test.go` lines 139-149 already demonstrates the root cause: `req1.WorkflowID = "workflow-123"`, `req2.WorkflowID = "workflow-456"` (same owner, same method/URL/headers/body) yield `hash1 == hash2`. An integration-level PoC would extend this to `responseCache.Set`/`Fetch`: populate the cache via `Set` with `req1` (WorkflowID A) and a distinguishable response, then call `Fetch` with `req2` (WorkflowID B, same owner, same method/URL/body/headers) and assert that `req1`'s cached response is returned to `req2` before its TTL/MaxAge expires, without a new outbound HTTP call being made.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
