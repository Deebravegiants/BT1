### Title
Relayer's cross-chain delivery decision is priced by a manipulable single-block Uniswap spot quote, enabling griefing/DoS of message delivery - (File: tesseract/messaging/evm/src/gas_oracle.rs)

### Summary
`get_price_from_uniswap_router` (`tesseract/messaging/evm/src/gas_oracle.rs:183-224`) prices the destination chain's native-token-to-USD rate with a single, un-averaged on-chain read: `router.getAmountsIn(amount_out, path).block(BlockId::latest())` [1](#0-0) . This value feeds `get_current_gas_cost_in_usd`'s `gas_price_cost`, which becomes `execution_cost` and, ultimately, `total_gas_to_be_expended_in_usd` in the delivery gate at `tesseract/messaging/messaging/src/events.rs:521-533` [2](#0-1) , where a request is only queued for relay ("`queries_to_be_relayed`") when the user-attached `fee_metadata >= fee_with_profit`.

### Finding Description
The router used here is whatever `HostParams.uniswapV2` points to on the destination host — either a canonical Uniswap V2 pool (spot reserves, trivially skewed within one block) or, on chains without a real V2 pool, `UniV3UniswapV2Wrapper`, whose `getAmountsIn` calls `IQuoterV2.quoteExactOutputSingle` against the *current* pool tick with no TWAP protection [3](#0-2) . Both are single-block/point-in-time reads, the same bug class as the Sherlock report's `slot0`/`observe`-derived price.

An attacker who can move the destination chain's WETH/feeToken pool price for one block (flash loan, large swap, or simply timing around thin liquidity) can inflate the reported native-token USD price right before/around the relayer's estimation call. This inflates `total_gas_to_be_expended_in_usd`/`fee_with_profit`, so the relayer's profitability check at `events.rs:530` fails even for requests whose real, honestly-attached fee is entirely sufficient — the request is pushed into `retriable_messages` instead of being relayed [4](#0-3) . Conversely, deflating the price could cause a relayer to under-price and deliver a request that is not actually profitable, or (more importantly for correctness) systematically mis-price which requests get through, degrading overall route liveness for a chain whose fee-oracle pool is thin.

The code's own comments acknowledge the router can revert or behave badly on thin-liquidity wrappers ("A reverting Uniswap pool... should not poison gas estimation" [5](#0-4) ) but only handle the *revert* case (defaulting `token_usd` to zero), not the *manipulated-but-successful* case, which silently produces a wrong-but-plausible price.

### Impact Explanation
This does not steal or freeze escrowed funds directly, but it lets an unprivileged actor (anyone able to move the destination pool for one block) make Hyperbridge's permissionless relayer network systematically refuse to deliver otherwise-profitable, correctly-fee-attached requests to a targeted destination chain — "a route unable to deliver messages," which is one of the explicitly accepted impact categories. Because delivery is the only path by which a dispatched POST/GET request reaches the destination `IHandlerV2`, sustained manipulation on a low-liquidity destination fee-oracle pool can indefinitely stall message delivery to that chain, and by extension any relayer-fee revenue tied to those deliveries (relayers never submit, so they never claim the fee either).

### Likelihood Explanation
Requires only a single-block price move on the specific WETH/feeToken pool configured as `HostParams.uniswapV2` for the targeted destination chain — no privileged access, no governance, and no protocol-level authorization needed. Feasibility scales inversely with that pool's liquidity; chains onboarded with thin liquidity or routed through the `UniV3UniswapV2Wrapper` (which reads live tick state, not TWAP) are the most exposed. This is lower severity than a direct fund-loss bug because it affects relayer decision-making/liveness rather than on-chain accounting, but it is reachable from a single transaction by any unprivileged party.

### Recommendation
- Replace the single-block `getAmountsIn`/`quoteExactOutputSingle` read in `get_price_from_uniswap_router` with a TWAP-based price (e.g., Uniswap V3 `observe` averaged over a meaningful window, or a Chainlink feed where available) for the purpose of gas-cost estimation.
- Clamp/sanity-check the derived `token_usd` against a bounded deviation from a recent moving average or governance-set reference price before using it to gate delivery, mirroring the `referencePrice`/`maxDeviationBps` guard pattern already used elsewhere in this codebase for Uniswap V4 venue pricing [6](#0-5) .
- Treat a suspicious/out-of-range quote the same as the existing revert-handling path (fail-safe default) rather than trusting whatever the pool currently reports.

### Proof of Concept
1. On the destination chain, identify `HostParams.uniswapV2` (or the deployed `UniV3UniswapV2Wrapper`) via `EvmHostInstance::hostParams()` [7](#0-6) .
2. Execute a large swap (optionally flash-loan funded) against that pool/pair in the block(s) during which a targeted request becomes eligible for relaying, skewing the WETH→feeToken price upward.
3. The next relayer call to `get_price_from_uniswap_router` reads the skewed `getAmountsIn`/`quoteExactOutputSingle` result at `BlockId::latest()`, inflating `token_usd` → `gas_price_cost` → `execution_cost`.
4. In `process_gas_estimates` (events.rs), `fee_with_profit` now exceeds the legitimately attached `fee_metadata`, so the request is logged as "Skipping unprofitable tx" and moved to `retriable_messages` instead of being relayed [8](#0-7) .
5. Repeat each retry cycle to keep the request permanently unprofitable-looking, stalling its delivery.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
