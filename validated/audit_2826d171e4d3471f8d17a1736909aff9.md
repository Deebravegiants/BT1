## Analog Found

### Title
Permissionless `CallDispatcher.dispatch()` Lets Any Unprivileged Caller Drain Funds Custodied by the Shared Dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is `external` with **no caller restriction whatsoever** — no `onlyHost`, no owner check, no allow-list of which app may invoke it [1](#0-0) . The interface itself is explicitly documented as dispatching "untrusted call(s)" [2](#0-1) , but "untrusted" is meant to describe the *target* of the forwarded call, not the caller of `dispatch()` itself. Because the same singleton `CallDispatcher` is shared across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` [3](#0-2) [4](#0-3) , any residual native ETH or ERC20 balance left sitting on the dispatcher between orchestrated calls is reachable by *any* external account — this is directly analogous to the MacVim bug class where a distributed-object service vends a privileged interface to any caller on the machine rather than only the intended trusted process.

### Finding Description
`CallDispatcher` is designed to be invoked exclusively by the orchestrating app contracts (`HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, `IntentGatewayV2.placeOrder`/`fillOrder`) as an intermediate execution sandbox that temporarily custodies funds while arbitrary calldata (Uniswap swaps, approvals, transfers) executes [5](#0-4) [6](#0-5) . However, the contract's only entry point, `dispatch(bytes memory encoded)`, has zero access control — any address on-chain can call it directly and force the dispatcher to execute arbitrary `Call[]` with `value` drawn from the dispatcher's own balance [7](#0-6) .

The documentation itself flags that the dispatcher holds funds only "temporarily during execution" [8](#0-7) , and the `IntentGatewayV2` sweep logic only recovers balances of tokens explicitly declared in `order.inputs`/`order.output.assets` [9](#0-8) . Any token accrued on the dispatcher that is *not* one of those declared assets (e.g., surplus from a swap that goes through an intermediate token, dust from `IERC20.approve(router, type(uint256).max)` calls documented as a supported pattern [10](#0-9) , or leftover ETH from `swapETHForExactTokens`) is never swept, and remains sitting at the `CallDispatcher` address across transaction boundaries. Because `dispatch()` has no caller check, that stranded balance is directly claimable by any unprivileged party who simply calls `CallDispatcher.dispatch()` with a `Call[]` that transfers the balance to themselves.

The `HyperFungibleToken`/`WrappedHyperFungibleToken` flow is even more exposed: `onAccept` mints/unlocks tokens directly to the `CallDispatcher` address, then invokes `dispatch(message.data)` — but there is **no sweep-back step at all** after this call [11](#0-10) . Any leftover balance from slippage, partial fills, or an incomplete swap therefore persists indefinitely on the dispatcher, fully claimable by anyone via a direct `dispatch()` call.

### Impact Explanation
Any unprivileged actor (no relayer role, no solver role, no admin role required) can permanently drain any native ETH or ERC20 balance that accumulates on the shared `CallDispatcher` from cross-chain token bridging or intent-fulfillment flows — this is direct, concrete theft of user/protocol funds without needing to forge any message, proof, or signature. Given the contract is reused by every `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` deployment on a chain [12](#0-11) , the blast radius spans the token bridge and intents surfaces simultaneously.

### Likelihood Explanation
High. No privileged role, proof, or timing race is needed — `dispatch()` is a plain public function with no modifier, so exploitation is a single unprivileged transaction as soon as any residual balance appears on the dispatcher, which the documentation itself acknowledges can happen (dust from swaps, unlimited approvals, unswept surplus tokens) [8](#0-7) .

### Recommendation
Restrict `CallDispatcher.dispatch()` to a known allow-list of trusted callers (the specific `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instances that are meant to use it), analogous to `onlyHost` gating elsewhere in the codebase [13](#0-12) , or make the dispatcher single-use/ephemeral per call so no balance can persist across transactions for an outside caller to claim.

### Proof of Concept
1. A user bridges tokens via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` containing a swap `Call[]`, as shown in the documented calldata-execution pattern [14](#0-13) .
2. On the destination chain, `WrappedHyperFungibleToken.onAccept` mints/unlocks the bridged amount to the `CallDispatcher` and calls `ICallDispatcher(_dispatcher).dispatch(message.data)` [11](#0-10) . Due to slippage or partial-fill behavior in the swap router, a residual token/ETH balance remains on the `CallDispatcher` after execution — no sweep-back exists in this code path.
3. Any unprivileged third party observes the `CallDispatcher`'s balance (e.g., via a block explorer or event) and submits a direct call to `CallDispatcher.dispatch(encoded)` with a `Call[]` transferring the leftover balance to their own address [7](#0-6) . The call succeeds because `dispatch()` performs no caller authentication.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as

            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)

            if (!sent) {

                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }

            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
```

```text
### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
