### Title
`describeWithdrawal` reports HOT-bridge withdrawal as "completed" without checking the `verified_withdraw` flag returned by the HOT API - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
The `HotBridge.fetchWithdrawalHashFromApi` method parses the HOT API withdrawal-status response using `HotApiWithdrawalSchema`, which explicitly includes a `verified_withdraw: boolean` field [1](#0-0) . However, when deciding whether a withdrawal is "completed" and returning a destination transaction hash, the code only checks that a `hash` is present and correctly hex-formatted — it never reads or checks `verified_withdraw` [2](#0-1) . This breaks the equality "status reported == on-chain outcome": the SDK can report `{ status: "completed", txHash }` for a withdrawal the HOT API itself has flagged as not (yet) verified.

### Finding Description
`describeWithdrawal` uses `fetchWithdrawalHashFromApi` as the fallback source of truth whenever the primary contract/bridge-indexer sources return nothing (`status === null`/pending) [3](#0-2) .

Inside `fetchWithdrawalHashFromApi`, the JSON response is validated against `HotApiWithdrawalResponseSchema`/`HotApiWithdrawalSchema`, which defines `verified_withdraw` as a required boolean field of each withdrawal record [4](#0-3) . This field exists precisely to indicate whether the bridge/relayer has cryptographically/on-chain verified the destination transaction, mirroring the semantics of a "signature present and verified" flag.

Despite parsing this field, the code path that decides completion status ignores it entirely:
```
const withdrawal = parseResult.output.withdrawals.find(
    (w) => w.nonce === nonce.toString(),
);

if (withdrawal?.hash) {
    const hash = withdrawal.hash.replace(/^0x/, "");
    if (isHex(hash)) {
        ...
        return hash;
    }
}
return null;
``` [2](#0-1) 

Any withdrawal record with a syntactically valid hash — regardless of `verified_withdraw` being `false` — causes `fetchWithdrawalHashFromApi` to return that hash, and `describeWithdrawal` immediately reports `{ status: "completed", txHash: formatTxHash(apiHash, ...) }` [3](#0-2) . This is structurally the same bug class as the gosaml2 report: a field meant to gate trust (`verified_withdraw` ≈ "signature present/valid") is parsed but the code falls through to treat the payload as authoritative anyway.

The existing test suite only exercises the case where `verified_withdraw: true` is returned [5](#0-4) ; there is no test covering `verified_withdraw: false` with a present hash, confirming this path was never validated to reject it.

### Impact Explanation
`describeWithdrawal`'s output is the primary signal consumed by `watchWithdrawal`/the withdrawal-completion-promise APIs to tell an integrator that funds have arrived on the destination chain [6](#0-5) . If the HOT API returns a withdrawal record with `verified_withdraw: false` (e.g., a pending/unconfirmed/rejected relay attempt) alongside a syntactically-plausible `hash`, the SDK will report `status: "completed"` to the caller even though the bridge itself has not verified funds landed. An integrator relying on this status to credit a user or release funds could credit/consider settled a withdrawal that never actually completed — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
This path is reached whenever the primary on-chain sources (contract view / bridge indexer) don't have data yet — a normal fallback state during withdrawal processing — and the HOT API is queried directly, which is entirely under the HOT relayer/API's control, not requiring any privileged local misconfiguration. Since the check is a straightforward missing-field validation (not requiring the caller to guess anything beyond a plausible hex hash + false flag from the upstream API), likelihood is moderate to high whenever the HOT API can be induced or observed to return `verified_withdraw: false` with a hash present.

### Recommendation
In `fetchWithdrawalHashFromApi`, require `withdrawal.verified_withdraw === true` before returning the hash as authoritative:
```ts
if (withdrawal?.hash && withdrawal.verified_withdraw) {
    const hash = withdrawal.hash.replace(/^0x/, "");
    if (isHex(hash)) {
        ...
        return hash;
    }
}
return null;
```
This mirrors the fix in the referenced advisory: reject/ignore the unverified record instead of silently treating it as trusted data.

### Proof of Concept
1. Mock `hotSdk.api.requestApi` (as done in existing tests) to return:
```json
{
  "hash": null, "nonce": "1", "near_trx": "txhash",
  "withdrawals": [
    { "hash": "0xDEADBEEF", "nonce": "1", "near_trx": "txhash", "verified_withdraw": false, "chain_id": 56 }
  ]
}
```
2. Call `bridge.describeWithdrawal(wid)` for a matching nonce with the contract/bridge-indexer returning no data (as in the existing "returns completed via API fallback" test setup) [7](#0-6) .
3. Observe the SDK still returns `{ status: "completed", txHash: "0xDEADBEEF" }` despite `verified_withdraw: false`, proving the flag is never checked.
