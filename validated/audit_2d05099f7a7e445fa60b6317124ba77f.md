This confirms the finding: `AuthQuery#to_signable_string` explicitly binds `shop` into the signed payload (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), so the OAuth callback path is a good analog to reject — `shop` is covered. But `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop` is read straight from an unsigned header (`lib/shopify_api/webhooks/request.rb:20-23`) and handed to the handler by `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) without ever being covered by the HMAC computed in `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`). This is the exact identity-binding gap the rules call out: "a field acted on but not covered by the HMAC."

### Title
Webhook `shop-domain` identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the trusted `shop` identity from the `x-shopify-shop-domain`/`shopify-shop-domain` header, but the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value is never part of the signed material, so the equality the app relies on — "the shop that signed this webhook == the shop attributed to this webhook" — is never actually checked.

### Finding Description
`Webhooks::Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

while `#shop` reads an unsigned header value: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string` (i.e. the body), never against `shop`: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` unconditionally once the body-only HMAC passes, and forwards it to the app's handler as authoritative tenant identity: [4](#0-3) 

Because an app's `api_secret_key` (client secret) is shared across every shop that installs the app, any merchant who legitimately installs the app receives real, validly-HMAC-signed webhooks for their own shop. Since `shop` is excluded from the signed material, that merchant (an unprivileged tenant relative to other tenants of the same multi-tenant app) can take a genuine `(raw_body, hmac)` pair issued for their own shop and resubmit it to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` still succeeds because the signature never covered `shop`, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source of that (attacker-chosen) body content.

This is directly analogous to the reported bug class: an identity field (shop) is acted upon (passed to the handler as the authoritative tenant) without being covered by the same integrity check (HMAC) that gates whether the request is trusted at all — mirroring "shop authenticated versus shop stored" and "field acted on but not covered by the HMAC" from the binding categories in scope.

Contrast with `Auth::Oauth::AuthQuery`, where the OAuth callback correctly folds `shop` into the signed string: [5](#0-4) 
No equivalent binding exists for `Webhooks::Request`.

### Impact Explanation
This breaks the tenant isolation guarantee (shop == HMAC-signer). A malicious/compromised merchant on a shared app installation can forge webhook events attributed to any other shop using the app, since the only per-request integrity check (HMAC) never covers `shop`. Depending on how the app's registered handler consumes `WebhookMetadata#shop` (e.g. to look up/replace per-tenant data, revoke access on `app/uninstalled`, or write attacker-controlled `body` under another tenant's record), this yields cross-tenant data corruption/injection — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to control (or previously capture) one legitimately-signed webhook payload for a shop they themselves installed the app on — a routine capability of any unprivileged merchant who installs a public/multi-tenant app. No access token, `api_secret_key`, or privileged account is needed; only the ability to POST an HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Bind `shop` (and other identity-relevant fields such as `topic`/`webhook_id` if used for authorization decisions) into the HMAC-signed material, or otherwise cryptographically tie the claimed shop to the signature — e.g., require the app to independently verify that `shop` matches a shop with an active, stored session/access token before trusting `WebhookMetadata#shop`, and document this requirement prominently since the gem itself cannot include `shop` in `to_signable_string` (Shopify signs only the body). At minimum, update `Webhooks::Registry.process`/docs so `shop` is treated as unauthenticated input that must be cross-checked against stored installation records before any tenant-scoped action is taken.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body with the app's api_secret_key>`
   - body: `{"id":1,...attacker-controlled fields...}`
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replaces the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Webhooks::Request.new(raw_body:, headers:)` builds successfully (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `raw_body`, which is unchanged (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Webhooks::Registry.process(request)` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on attacker-controlled data under the victim shop's identity.
