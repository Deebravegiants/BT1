## Analysis

**Equality claimed broken:** shares minted to `address(Emporium)` from victim's `vault.deposit()` should be redeemable only via the victim's own stealth-address-authorized `transact()` call, never via `deltaAmountChanges`/`handleOut` of an unrelated, later `transact()` call from a different user.

**Trace:**

`EmporiumUpgradeable.runAction` is only reachable via `onlyAllowedRecipient`, i.e. `msg.sender == Hinkal.sol`, which any unprivileged EOA can trigger simply by submitting their own valid `transact()` proof with an arbitrary `EmporiumStack` decoded from `circomData.externalActionData.externalActionMetadata` [1](#0-0) . In CASE 2 (`stack.signerAddress == address(0)` or `op.invokeWallet == false`), the operation is executed as `op.endpoint.call{value: op.value}(op.callData)` directly from `EmporiumUpgradeable`, so `msg.sender` seen by the target vault is `address(Emporium)` itself [2](#0-1) .

Accounting of what a given caller receives is purely a per-call delta: `balancesBefore`/`balancesAfter` are snapshotted only around that caller's own set of ops, and any positive delta is swept to `msg.sender` (the Hinkal contract, then re-shielded under whatever `stealthAddressStructure` that caller supplied) via `handleOut` [3](#0-2) . There is no on-chain bookkeeping anywhere in `EmporiumStorage`/`EmporiumUpgradeable` that ties a specific ERC20/vault-share balance sitting inside the Emporium contract to the specific stealth identity that produced it. The `BalanceChangeShouldBePositive` check and its accompanying comment ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") explicitly acknowledge that Emporium can carry an ERC20 balance across transactions [4](#0-3) .

Because CASE 2 calls run with `msg.sender == address(Emporium)` for *any* caller's arbitrary `endpoint`/`callData`, an attacker's own `transact()` proof can encode an `EmporiumOperation` calling `vault.redeem(shares, attackerRecipient, address(Emporium))`. ERC4626's `redeem` only requires `msg.sender == owner` to skip allowance checks — which holds here since the call itself originates from `Emporium` — and it pays the underlying assets directly to `receiver`. If `receiver` is set to `attackerRecipient` (an arbitrary externally owned address chosen by the attacker), the underlying assets leave the system entirely, bypassing `balancesBefore`/`balancesAfter` and `handleOut` altogether, since Emporium's own balance for that token never needs to change. Even if the attacker instead routes `receiver = address(Emporium)`, the resulting balance increase would still be swept out via `handleOut` into a UTXO owned by the attacker's own `stealthAddressStructure` — not the victim's.

None of `performHinkalChecks`, `verifyProof`/`buildVerifierId`, `rootHashExists`, `onlyAllowedRecipient`, `verifyWallet` (which only validates the EIP-712 signature when `signerAddress != address(0)`, and is a no-op for CASE 2 with `signerAddress == address(0)`), or the circuit's `inTotal + amountChanges === outTotal` constraint prevent this — those all validate the *caller's own* proof and UTXOs, not who is entitled to whatever ERC20 balance the shared `Emporium` contract happens to be holding at call time. The vulnerability is a design flaw: `Emporium` is a shared, pooled contract, and any position (vault shares, LP tokens, staking receipts) left resting in its balance between the "enter" and "exit" `transact()` calls of a DeFi workflow has zero owner-scoping and is drainable by any other unprivileged Emporium user.

### Title
Shared `Emporium` custody lets any unprivileged user drain another user's resting vault shares/position via `msg.sender == address(Emporium)` calls - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 path executes arbitrary `op.endpoint.call(op.callData)` with `msg.sender == address(Emporium)`, and any unprivileged EOA can trigger this by submitting their own valid `transact()` proof with a self-crafted `EmporiumStack`. Because Emporium is a shared pooled contract with no per-depositor ownership tracking of resting ERC20/vault-share balances, an attacker can call `vault.redeem(shares, attackerRecipient, address(Emporium))` (valid since `msg.sender == owner == Emporium`) to steal shares/underlying belonging to an unrelated victim who previously deposited via Emporium and left the resulting shares uncollected between two `transact()` calls.

### Finding Description
The broken equality: shares minted to `address(Emporium)` on the victim's `deposit()` call should only ever be redeemable by the victim's own subsequent authorized `transact()` call, never by a different `msg.sender` calling `Emporium.runAction` with an arbitrary op. In practice, `runAction`'s CASE 2 branch [2](#0-1)  lets any caller whose proof passes `onlyAllowedRecipient` (satisfied automatically by any user calling `Hinkal.transact()`) execute any `endpoint.call(callData)` with `Emporium` as the effective `msg.sender`/`owner` towards that endpoint. The accounting that follows (`balancesBefore`/`balancesAfter`, `handleOut`) only reasons about the delta produced during the *current* caller's own ops [3](#0-2) , and never verifies that the assets being moved actually originated from that same caller's earlier deposit. An attacker can therefore call `vault.redeem(shares, attackerRecipient, address(Emporium))`, which ERC4626 permits without allowance since the caller (`Emporium`) equals `owner`, and which sends underlying assets directly to `attackerRecipient`, bypassing Emporium's/Hinkal's balance-delta accounting entirely.

### Impact Explanation
Direct theft of another user's shielded value (their deposited principal represented as vault shares resting in `Emporium`), stealing funds that were never authorized to move to the attacker. This matches the Critical category: "direct theft of shielded or in-flight user funds." It is repeatable against any token/position left resting in Emporium by any user between two `transact()` calls (e.g., stake-then-unstake, deposit-then-later-withdraw flows), and costs the attacker only their own proof-generation and gas.

### Likelihood Explanation
Preconditions: a victim must have used Emporium's CASE 2 ("stateless", `signerAddress == address(0)`) path to interact with a vault/protocol where minted receipt tokens (shares) are left in `Emporium`'s balance rather than being fully swept out via `handleOut` in the same `transact()` call — e.g., because the receipt token wasn't included in that call's `circomData.erc20TokenAddresses`, or because the workflow intentionally spans multiple `transact()` calls (enter position, then exit position later). This is a realistic usage pattern for yield/staking-style DeFi integrations through Emporium. The attacker needs no privileges — just the ability to submit their own valid `transact()` proof with a crafted `EmporiumStack`, which is explicitly within the attacker capability model.

### Recommendation
Do not allow `Emporium` to persist ERC20/receipt-token balances across transactions in a way that any subsequent caller's arbitrary `op.endpoint.call` can act on. Options: (1) require every CASE 2 DeFi action to be fully atomic — deposit and withdrawal/redeem in the same `transact()` call, with a Hinkal-level invariant that Emporium's balance for every token in `erc20TokenAddresses` returns to (or below) its pre-call value net of `deltaAmountChanges`, rejecting any op sequence that leaves a net-positive residual balance not attributable to the current caller; (2) track per-stealth-identity ownership of any resting balances/positions on-chain (e.g., via a mapping from position/receipt-token amount to a specific stealth commitment) and enforce that only the recorded owner's proof can act on it; (3) require the `owner`/`msg.sender` parameter passed into third-party `redeem`/`withdraw`-style calls to be validated against a record of who deposited, not simply allowed because it equals `address(Emporium)`.
