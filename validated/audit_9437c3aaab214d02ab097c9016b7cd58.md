## Finding

### Title
Webhook shop-domain spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the **raw body**, then blindly trusts the `shop-domain` header (parsed from unauthenticated headers) as the tenant identity handed to the host application's webhook handler. Because the `shop` field is not covered by the HMAC, an attacker who can obtain any one validly-signed webhook (e.g., by installing the public app on their own store) can replay that exact body/HMAC pair while substituting a different shop's domain in the `X-Shopify-Shop-Domain` header, causing the host app to process/attribute the webhook payload as if it originated from an arbitrary victim shop.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` show that the signable content used for the HMAC check is only the raw JSON body: [1](#0-0) 

The `shop`, `topic`, `api-version`, and `webhook-id` values are all pulled directly from HTTP headers without ever being part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` against the secret-derived signature — it has no knowledge of, and does not bind, the `shop` header: [3](#0-2) 

`Webhooks::Registry.process` performs the HMAC check and then forwards `request.shop` (an unauthenticated field) straight into `WebhookMetadata`, which is the identity the host application's handler code uses to know which tenant/store the webhook is for: [4](#0-3) 

This is structurally the same class of bug as the reported Geth issue: a value that participates in downstream trust decisions (there, the EC public key used to derive a shared secret; here, the `shop` identity used to attribute webhook data) is not validated/bound by the cryptographic check that is supposed to establish authenticity (there, curve-membership validation; here, HMAC coverage). The equality that should hold — `shop asserted in the authenticated channel == shop the payload is attributed to` — is broken because `shop` sits entirely outside the HMAC's protected scope.

### Impact Explanation
An attacker who can obtain any single legitimately-signed webhook body (trivial for a public app — anyone can install it on their own store and receive real webhooks) can replay that same body+HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `Registry.process` will pass HMAC validation (since body is untouched) and hand `WebhookMetadata` with the attacker-chosen `shop` to the app's handler. Any host application that uses `shop` from `WebhookMetadata` to look up the tenant's session/store record and apply the webhook body's effects (the intended and documented usage pattern) will apply attacker-controlled data cross-tenant — i.e., cross-tenant data injection/corruption keyed off a forged shop identity. This matches the "cross-tenant access" high/critical impact category since the tenant boundary that webhooks are meant to preserve is not actually enforced by this gem's authentication primitive.

### Likelihood Explanation
Likelihood is high for any public/unlisted app: no privileged credentials, tokens, or the app's `client_secret` are required — an ordinary merchant can install the app to receive one authentic webhook, then replay it with a modified header at will since the header is not part of the signed content and there's no nonce/topic/shop binding or replay window enforced in `Registry.process` or `HmacValidator`.

### Recommendation
Bind the request-identifying headers (`shop`, `topic`, `webhook-id`, `api-version`) into the value that is HMAC-verified, or otherwise cryptographically bind `shop` before it is trusted — e.g., include the `shop` domain (and ideally topic/webhook-id) in `to_signable_string` for webhook requests, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop` in its signable content: [5](#0-4) 

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com`, triggers an event, and captures the resulting webhook POST — a legitimate `body` and its `X-Shopify-Hmac-Sha256` value signed with the app's real `api_secret_key`.
2. Attacker replays the exact same request to the app's webhook endpoint, unmodified except for `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — unchanged — and passes.
4. `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's payload>, ...)` is delivered to the host app's handler, which processes/attributes the payload against the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
