### Title
Same-asset collateral repayment is blocked by unnecessary oracle validation - ([File: contracts/controller/src/strategies/repay_debt_with_collateral.rs](contracts/controller/src/strategies/repay_debt_with_collateral.rs))

### Summary
`repay_debt_with_collateral` fetches strict prices for every account supply and debt asset before selecting its execution branch, including the same-asset path that only performs internal net settlement and transfers no tokens. As a result, an owner cannot use collateral to fully extinguish debt in that same asset while any fetched price is stale, deviates between configured sources, or violates its sanity band. This contradicts the protocol's otherwise risk-reducing exit behavior: ordinary debt-free withdrawals explicitly work with a broken oracle, and post-action risk gates are skipped once an account is debt-free. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The public `repay_debt_with_collateral` entrypoint accepts `caller`, `account_id`, `collateral`, `collateral_amount`, `debt`, `swap`, and `close_position`, and requires only owner or delegate authorization. [5](#0-4) [6](#0-5) 

Before checking whether `collateral == debt`, the implementation builds `extra_assets` from the two selected assets and calls `prefetch_strategy_prices`. [1](#0-0) 

`prefetch_strategy_prices` passes those extras through `account_price_assets`, which also collects every existing supply and debt token in the account, then calls the strict price-aggregator fetch. [7](#0-6) [2](#0-1) [8](#0-7) 

The same-market branch does not call an external router or transfer collateral; it only validates exit flags, obtains the supply and debt positions, calls `pool_net_settle_call`, and merges the resulting supply and debt reductions. [9](#0-8) [10](#0-9) [11](#0-10) 

The price fetch can therefore abort before a purely accounting operation that reduces both sides of the same market. [1](#0-0) [12](#0-11) 

Strict oracle outcomes reject stale readings, dual-source deviation, nonpositive prices, and sanity-band violations. [13](#0-12) 

The repository's own tests confirm that `SanityBoundViolated` or source deviation blocks valuation-dependent operations, while a full withdrawal by a debt-free account succeeds even after the oracle price is set to zero. [14](#0-13) [15](#0-14) [4](#0-3) 

### Impact Explanation
A borrower can be temporarily prevented from repaying debt with collateral in the same asset and then closing the position, even though the transaction reduces debt and can leave the account debt-free. [16](#0-15) [3](#0-2) 

Because the prefetch includes all account assets rather than only assets needed for a post-operation risk calculation, an invalid price for an unrelated collateral or debt can also block the same-asset settlement. [2](#0-1) [17](#0-16) 

The user can still make an ordinary `repay` if they independently hold the debt token, because `process_repay` only settles measured payments and persists the debt side, but users whose available repayment capital is represented by locked collateral lose that exit route until the oracle configuration is corrected. [18](#0-17) [19](#0-18) 

Correcting a sanity band generally requires a governance configuration operation and its scheduled delay; the repository's runbook describes band movement through `ConfigureAssetOracle`, while the narrower `set_sanity_band` path cannot move an excluded live price back into range. [20](#0-19) [21](#0-20) 

### Likelihood Explanation
This is reachable by any account owner or delegate holding both supply and debt in the same hub asset and calling `repay_debt_with_collateral` with `collateral == debt`. [5](#0-4) [22](#0-21) 

The triggering oracle state does not require privileged access from the borrower: strict reads fail on ordinary source staleness, disagreement, invalid values, or a live price outside configured sanity bounds. [13](#0-12) [23](#0-22) 

The likelihood is higher than necessary because every distinct token already present in the account is added to the strict fetch set, so a failure in an unrelated market is sufficient to revert the settlement attempt. [2](#0-1) [7](#0-6) 

### Recommendation
Move `prefetch_strategy_prices` below the `collateral == debt` branch selection and omit it for the pure net-settlement path, or prefetch only after determining that residual debt will remain and therefore a post-operation risk valuation is required. [24](#0-23) [3](#0-2) 

Keep strict prefetching for the cross-asset `repay_via_collateral_swap` path, since it performs an external conversion and needs valuation inputs, but do not let unrelated account prices or an invalid same-asset price block settlement that clears all debt. [25](#0-24) [26](#0-25) 

### Proof of Concept
1. An account holds supply and debt in the same `HubAssetKey`, with sufficient collateral to settle the entire debt.
2. Any price collected by `prefetch_strategy_prices` becomes invalid, such as the collateral/debt asset reporting outside its sanity band or an unrelated account asset having a stale or deviating dual-source price. [2](#0-1) [13](#0-12) 
3. The owner authorizes `repay_debt_with_collateral(caller, account_id, collateral, collateral_amount, debt, swap, close_position)` with `collateral == debt`, an empty `swap`, `collateral_amount` sufficient to extinguish the debt, and `close_position = true`. [5](#0-4) [27](#0-26) 
4. The call reverts inside `prefetch_strategy_prices` before reaching `net_settle_collateral_against_debt`, so neither the debt nor collateral position is reduced. [1](#0-0) [8](#0-7) 
5. Once the intended settlement would have emptied `borrow_positions`, `close_position` would pass the remaining-debt assertion and `require_post_pool_risk_gates` would skip its numerical checks for a debt-free account, so no strict price was needed for this full-exit shape. [28](#0-27) [3](#0-2)

/// Converts composed `Legs` into an `Outcome`. For two readings, marks the
/// outcome stale when either leg is individually stale, or when both legs
/// are market-nature feeds whose timestamps differ by more than
/// `MAX_LEG_AGE_SPREAD_SECONDS`. Takes the earlier of the two timestamps,
/// flags a deviation when the legs fall outside the oracle's tolerance band, and
/// sets the blended price to the midpoint of the two legs (zero if the
/// midpoint computation fails).
fn blend(env: &Env, oracle: &AssetOracle, legs: Legs) -> Outcome {
    match legs {
        Legs::Empty => Outcome::unreadable(),
        Legs::One(r) => Outcome::one(r),
        Legs::Partial { reading, slot } => Outcome::partial(reading, slot),
        Legs::Two { primary, anchor } => {
            let spread_bounded =
                primary.nature == FeedNature::Market && anchor.nature == FeedNature::Market;
            let age_spread = primary.timestamp.abs_diff(anchor.timestamp);
            let stale = primary.stale
                || anchor.stale
                || (spread_bounded && age_spread > MAX_LEG_AGE_SPREAD_SECONDS);
            let ts = primary.timestamp.min(anchor.timestamp);
            let deviation =
                !within_tolerance_band(env, anchor.price_wad, primary.price_wad, &oracle.tolerance);

            let price_wad = midpoint_price_or_zero(anchor.price_wad, primary.price_wad);
            Outcome {
                price_wad,
                timestamp: ts,
                first_wad: primary.price_wad,
                second_wad: anchor.price_wad,
                stale,
                deviation,
                err: None,
            }

fn settle_repay(
    env: &Env,

    payer: &Address,
    aggregated: &AggregatedPayments,
    cache: &mut Context,

        env,
        account,
        payer,
        events::PositionAction::Repay,

waits for the standard timelock delay. `configs/networks.json` sets 12
ledgers today; `TIMELOCK_MIN_DELAY_LEDGERS` suggests about 2 days. The ORACLE

| Posted NAV `p` | Step |
|---|---|
| `0.99 R <= p <= 1.015 R` | No step. |
| `1.015 R < p <= 1.03 R` | Propose a band around `p`: `R = p`. |
| `0.95 R <= p < 0.99 R` | Propose a band around `p`: `R = p`. |
| `0.849 R <= p < 0.95 R` | Freeze the listing (`tightenAssetFlags`, `frozen`). Propose a band around `p`. Clear the freeze (`relaxAssetFlags`) after the new band is live. |
| `p < 0.849 R` or `p > 1.03 R` | Prices fail closed. Freeze the listing. Make sure that the NAV is correct. Then propose a band around `p`. |
