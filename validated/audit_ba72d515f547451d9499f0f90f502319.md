## Title
Meta-transaction (`DelegateAction`) griefing via nonce front-running invalidates victim relayer's transaction - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's meta-transaction feature (NEP-366) lets a user sign a `DelegateAction` off-chain and hand it to a relayer, who wraps it in a `SignedTransaction` and pays for gas/execution on the user's behalf [1](#0-0) . This is structurally the same pattern as ERC20 `permit()`: an off-chain signature that authorizes an action and is redeemable by anyone who possesses it, gated only by a nonce. Because NEAR transactions (including the relayer's wrapping transaction that carries the `SignedDelegateAction`) are gossiped to peers/validators before being included in a chunk, an attacker can observe a pending `SignedDelegateAction`, extract it, and resubmit it themselves in a competing transaction with higher priority. The nonce check in `validate_delegate_action_key` only requires the delegate nonce to be strictly greater than the current access-key nonce, so whichever copy lands first consumes the nonce, and the legitimate relayer's original transaction is invalidated when it later attempts to execute (`DelegateActionInvalidNonce`), causing the relayer to lose the gas already spent to convert/process that transaction.

### Finding Description
A `SignedDelegateAction` is a payload signed by the sender that is bound to `(sender_id, receiver_id, actions, nonce, max_block_height, public_key)` [2](#0-1) . Any account can wrap this exact same signed payload inside its own outer `SignedTransaction` (as the "relayer") and submit it, since the signature only authenticates the inner delegate action content, not who relays it.

Validation of the delegate action's nonce happens in `validate_delegate_action_key`, which loads the current access-key nonce and rejects the delegate action only if `delegate_nonce <= current_nonce`; otherwise it accepts and later advances the nonce: [3](#0-2) 

Because NEAR transactions are broadcast/gossiped across the network before being committed to a chunk (any node that receives a transaction validates and gossips it to peers, and forwards it to upcoming chunk producers), an attacker can observe a `SignedDelegateAction` inside someone else's pending outer transaction before it is finalized: [4](#0-3) [5](#0-4) 

The attacker then re-wraps the identical `SignedDelegateAction` bytes in their own outer transaction (using themselves as the relayer/outer signer) and gets it included first (e.g., via a higher gas price / more favorable routing / lower height horizon). This causes the target access key's nonce to advance. When the original relayer's transaction is subsequently processed, `validate_delegate_action_key` will find `delegate_nonce <= current_nonce` and fail with `DelegateActionInvalidNonce`: [6](#0-5) 

Crucially, the outer transaction conversion (which charges the outer signer/relayer for the transaction's base gas cost) happens independently of whether the inner delegate action succeeds — the delegate action's actions and gas/balance costs "are subtracted from the relayer" once the receipt executes, so the relayer bears the cost of an action that is doomed to fail once front-run: [7](#0-6) 

This is a direct structural analog of the reported `supplyWithPermit`/`repayWithPermit` griefing bug class: a third party can consume a signature-bound nonce that was intended to be redeemed exactly once by the legitimate relayer, causing the victim's transaction to unavoidably fail and wasting their gas, with no requirement that the attacker hold any privileged role (they only need to observe gossiped transactions and submit their own ordinary transaction).

### Impact Explanation
This is a griefing vector: an unprivileged attacker can cause a relayer's (or self-relaying user's) meta-transaction to fail deterministically, wasting the gas paid to convert/process the doomed transaction and to route it through the network. Repeated abuse can be used to reliably block a specific `DelegateAction` from ever landing (since the attacker can keep watching the mempool and racing every retry with the same nonce, unless the victim re-signs with a new nonce each time), degrading the usability and reliability of the relayer/meta-transaction feature and harming the reputation of any dApp/relayer service built on top of NEP-366 meta-transactions. There is no direct token theft or inflation, matching a "Griefing" style impact rather than a fund-loss impact.

### Likelihood Explanation
Likelihood is limited by two factors: (1) it requires the attacker to observe the raw `SignedDelegateAction` bytes before the victim's outer transaction is finalized, which is plausible given NEAR's gossip-based transaction routing to upcoming chunk producers over a `tx_routing_height_horizon` window, and (2) it requires the attacker's copy to be committed to a chunk ahead of the victim's, which is a normal front-running race rather than requiring any privileged/validator role. Any account can submit the observed payload as an ordinary transaction, so this is reachable by any user, not just validators.

### Recommendation
Consider one or more of the following mitigations for the `DelegateAction`/meta-transaction path:
- Require (or at least recommend/support) that the relayer identity be committed into what the sender signs (e.g., binding the delegate action's validity to a specific relayer/`predecessor_id`), so a third party cannot redeem a signature intended for a specific relayer.
- Provide relayers with a way to check the current access-key nonce immediately before submission and to detect/react to `DelegateActionInvalidNonce` failures gracefully (e.g., re-signing flows), similar to the "check allowance before submitting permit" mitigation recommended in the source report.
- Document this front-running/nonce-griefing risk for meta-transaction relayer implementations so they can add their own protections (e.g., submitting through private/direct channels to a specific chunk producer rather than the public gossip path when possible).

### Proof of Concept
1. Sender (Alice) signs a `DelegateAction { sender_id: Alice, receiver_id: R, actions: [...], nonce: N, max_block_height: H, public_key: Alice_key }` and hands the `SignedDelegateAction` to Relayer B, who wraps it into `SignedTransaction { signer_id: B, actions: [Action::Delegate(signed_delegate_action)] }` and submits it via RPC.
2. Relayer B's transaction is gossiped to peers and forwarded toward upcoming chunk producers per the tx routing logic, before being included in a chunk (`chain/client/src/rpc_handler.rs::forward_tx`).
3. Attacker M observes the `SignedDelegateAction` (same bytes) in the gossiped/forwarded transaction, copies it, and submits their own transaction `SignedTransaction { signer_id: M, actions: [Action::Delegate(signed_delegate_action)] }` with better propagation/priority so it lands in an earlier chunk.
4. `validate_delegate_action_key` processes M's copy: `delegate_nonce (N) > current_nonce`, so it succeeds and advances Alice's access-key nonce to `N` (as shown by `test_validate_delegate_action_key_update_nonce`) [8](#0-7) .
5. Relayer B's original transaction is later processed. `validate_delegate_action_key` now finds `delegate_nonce (N) <= current_nonce (N)` and returns `DelegateActionInvalidNonce`, causing B's transaction/receipt to fail while B has already paid for its base transaction/gas cost — mirroring the reported ERC20 `permit()` griefing scenario, but with NEAR's access-key/delegate-action nonce.

    /// Signer of the delegated actions
    pub sender_id: AccountId,
    /// Receiver of the delegated actions.
    pub receiver_id: AccountId,
    /// List of actions to be executed.
    ///
    /// With the meta transactions MVP defined in NEP-366, nested

    /// relayer and should match for given account's `public_key`.

    /// The maximal height of the block in the blockchain below which the given DelegateAction is valid.

    /// Public key used to sign this delegated action.

}

            }
            (access_key.nonce, DelegateNonceUpdate::AccessKey)
        }
        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.
            let current_nonce =

                        StorageError::StorageInconsistentState(format!(
                            "gas key nonce row missing for {} {} at in-range index {nonce_index} (num_nonces {})",
                            sender_id, public_key, gas_key_info.num_nonces,
                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

    if delegate_nonce.nonce() <= current_nonce {
        result.result = Err(ActionErrorKind::DelegateActionInvalidNonce {
            delegate_nonce: delegate_nonce.nonce(),
            ak_nonce: current_nonce,
        }
        .into());
        return Ok(());

# Transactions in the Blockchain Layer

A client creates a transaction, computes the transaction hash and signs this hash to get a signed transaction.
Now this signed transaction can be sent to a node.

When a node receives a new signed transaction, it validates the transaction (if the node tracks the shard) and gossips about it to all its peers. Eventually, the valid transaction is added to a transaction pool.

Every validating node has its own transaction pool. The transaction pool maintains transactions that were either not yet discarded, or not yet included onto the chain.

Before producing a chunk, transactions are ordered and validated again. This is done to produce chunks with only valid transactions.

## Step 2: Inside the node

Our transaction has made it to a node in the system - but most of the nodes
are not validators - which means that they cannot mutate the chain.

That’s why the node has to forward it to someone who can - the upcoming
validator.

The node, roughly, does the following steps:

* verify transaction’s metadata - check signatures etc. (we want to make sure
  that we don’t forward bogus data)
* forward it to the ‘upcoming’ validator - currently we pick the validators that
  would be a chunk creator in +2, +3, +4 and +8 blocks (this is controlled by
  `TX_ROUTING_HEIGHT_HORIZON`) - and send the transaction to all of them.

## Step 3: En-route to validator/producer

Great, the node knows to send (forward) the transaction to the validator, but
how does the routing work? How do we know which peer is hosting a validator?

Each validator is regularly (every `config.ttl_account_id_router`/2 seconds == 30
minutes in production) broadcasting so called `AnnounceAccount`, which is
basically a pair of `(account_id, peer_id)`, to the whole network. This way each
node knows which `peer_id` to send the message to.

Then it asks the routing table about the shortest path to the peer, and sends
the `ForwardTx` message to the peer.
