## Analysis

The referenced Ambire finding is a gas-griefing bug class: a relayer can calibrate the transaction gas limit so that a low-level `call` used as a try/catch surrogate runs out of gas and fails, while the enclosing function still completes and treats the callback as "attempted." The equivalent pattern in Hyperbridge is the family of `dispatchIncoming`/`dispatchTimeOut` functions on `EvmHost`, which forward all remaining gas to application callbacks via a bare `.call(...)` with no gas floor, and are reachable from the fully permissionless `HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handler entry points.

### Title
Gas-griefing of `EvmHost.dispatchIncoming`/`dispatchTimeOut` callbacks allows a malicious relayer to cheaply and repeatedly block message delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` (for `PostRequest` and `GetResponse`) and `EvmHost.dispatchTimeOut` (for `GetRequestTimeout` and `PostRequestTimeout`) invoke the destination application's callback (`onAccept`, `onGetResponse`, `onGetTimeout`, `onPostRequestTimeout`) with a bare `.call(...)`, forwarding all remaining gas and only branching on `success`. These are reached from the permissionless `HandlerV2.handlePostRequests`, `handleGetResponses`, `handleGetRequestTimeouts`, and `handlePostRequestTimeouts` entry points, i.e. anyone acting as a "relayer" chooses the outer transaction's gas limit. ### Finding Description
Because the sub-call is not gas-limited, EIP-150's 63/64 rule means the callee gets ~63/64 of whatever gas remains at the call site. A caller who fully controls the top-level transaction's gas limit can pick that limit so that the amount forwarded to `onAccept`/`onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` is just barely insufficient to complete the callback's real work (causing an out-of-gas revert deep inside that sub-call), while the 1/64 gas retained by the outer `dispatchIncoming`/`dispatchTimeOut` call is enough to finish the `if (!success) { delete ...; return; }` branch without reverting the whole transaction.

The result: the top-level `handlePostRequests`/etc. transaction succeeds normally (no revert, so it looks like a legitimate delivery attempt), but the receipt/commitment is deleted "so it can be retried", and no event (`PostRequestHandled`, `GetRequestHandled`, etc.) is ever emitted: [4](#0-3) 

Because the destination module's `onAccept` (and equivalents) are arbitrary application logic (potentially gas-heavy, e.g. token bridge mint/burn, intent settlement), an attacker only needs to spend enough gas to reach the call site and let the callee run out partway through — cheaper than the gas an honest, fully-successful delivery would cost. This lets an attacker selectively and repeatedly grief delivery of a specific request/response/timeout by front-running every legitimate relayer's submission with a maliciously gas-capped call for the same commitment (paying only the reduced cost each time), since a failed attempt always resets state back to "undelivered" and is resubmittable, giving the attacker infinite retries at low marginal cost.

The same call-without-gas-floor pattern repeats for `GetResponse`, `GetRequestTimeout`, and `PostRequestTimeout` delivery: [5](#0-4) 

### Impact Explanation
This enables a "route unable to deliver messages" condition for targeted requests: a griefer can indefinitely suppress delivery of a chosen POST request, GET response, or timeout by continually forcing the application callback to run out of gas at low cost relative to a genuine delivery, denying the destination application (and its users/funds) the intended cross-chain effect. For time-sensitive messages (e.g. liquidations, price updates, bridged transfers with deadlines) this can effectively freeze funds or actions tied to that message, and blocks the fee-refund/reward flow for `dispatchTimeOut` (fees remain locked since `meta` is restored and the transfer branch never executes).

### Likelihood Explanation
The affected functions (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) are explicitly permissionless — "can be called by anyone" — so no privileged role is required. The attacker only needs to observe an in-flight request/response/timeout commitment (public on-chain) and submit a competing transaction with a calibrated gas limit; this requires some tuning of gas limits per target contract's callback cost but is a well-understood, repeatable technique (EIP-150 63/64 griefing), making it feasible for a motivated party willing to pay a fraction of normal delivery gas costs.

### Recommendation
Enforce an explicit minimum gas stipend before forwarding to application callbacks (e.g. `require(gasleft() >= MIN_CALLBACK_GAS + BUFFER)` prior to the `.call`, or use `.call{gas: fixedAmount}`) in `EvmHost.dispatchIncoming` and `EvmHost.dispatchTimeOut`, so the transaction reverts rather than silently discarding the delivery attempt when insufficient gas was supplied. This removes the attacker's ability to make a "just enough to fail cheaply" call succeed as a top-level transaction.

### Proof of Concept
1. A POST request commitment `C` is finalized on Hyperbridge and ready for delivery via `handlePostRequests`.
2. Attacker computes the gas cost of the destination module's `onAccept` for this specific payload (observable off-chain via simulation).
3. Attacker submits `handlePostRequests(host, msg)` with a total gas limit `G` chosen such that, after all the proof verification and loop overhead in `HandlerV2.handlePostRequests` (lines 181-210) plus `EvmHost.dispatchIncoming` bookkeeping (lines 794-808), the gas remaining at the `.call` site (line 809-810) is less than `onAccept`'s true gas requirement but where 1/64 of it still covers `delete _requestReceipts[commitment]; return;` (lines 812-816).
4. The outer transaction succeeds; `PostRequestHandled` is never emitted, and `_requestReceipts[commitment]` is cleared, so the request is reported as undelivered and can be resubmitted — repeat step 3 against every future honest resubmission.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
