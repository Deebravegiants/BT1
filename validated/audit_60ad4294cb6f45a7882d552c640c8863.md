## Title
Full JSON-RPC User Request (Including Auth Token) Logged at Debug Level in Vault Gateway Handler - ([File: core/services/gateway/handlers/vault/handler.go])

## Summary
`HandleJSONRPCUserMessage` in the Vault gateway handler logs the complete inbound `jsonrpc.Request[json.RawMessage]` object — including its `Auth` field and raw, unvalidated `Params` — at Debug level before any authorization or redaction occurs. Any operator who enables Debug logging (a routine, non-privileged operational toggle) will cause every vault request's auth token and raw parameters to be written to the log file in plaintext.

## Finding Description
At `core/services/gateway/handlers/vault/handler.go:403`:
```go
h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
```
`req` is the full `jsonrpc.Request[json.RawMessage]` struct passed into the handler, containing the `Auth` field used for authorization — confirmed later in the same function where `req.Auth != ""` is explicitly checked at line 432. This Debug log statement executes unconditionally for every method, including `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsList`, and executes *before* the authorization/validation call at line 427 (`h.requestProcessor.ProcessRequest`), meaning no redaction has been applied to `req.Auth` or `req.Params` at the point of logging.

The codebase itself acknowledges this gap: `TestVaultHandler_InvalidParamsDoesNotLogRawParams` in `core/services/gateway/handlers/vault/handler_test.go:1016-1058` explicitly sets the log observer to `zapcore.InfoLevel` with the comment "Observed at Info level so the pre-existing whole-request Debug log is excluded," and only asserts that the separate Error-level "invalid params" log path is redaction-safe. It does not test or sanitize the Debug-level whole-request log, confirming this is a known, unaddressed condition rather than a false claim. Similar unredacted logging of full request objects also appears at lines 333, 342, 347, and 357 for the public-key-fetch flow, though those requests carry synthetic (non-user) parameters and no `Auth` field, making them lower-impact but consistent with the same pattern.

## Impact Explanation
This falls into the CWE-532 (sensitive information in log file) category. If Debug logging is enabled, the gateway would persist the caller's `Auth` token/JWT and raw, pre-validation request parameters to disk for every vault request. This is a real, concrete disclosure of sensitive request-scoped data (auth material used for request authorization) that would not be exposed at default log levels. Anyone with read access to the resulting log file (e.g., via log aggregation, misconfigured log shipping, or local file access) could extract a valid `Auth` token and potentially replay/impersonate the original caller's vault request.

## Likelihood Explanation
Triggering the log line requires no attacker privilege escalation on the client side — an unprivileged client's normal vault request is unconditionally logged whenever Debug level is active. The precondition is that the node operator has set `Log.Level = debug`, which is a common, legitimate operational action for troubleshooting, not a security control bypass. This mirrors the referenced NiFi CWE-532 likelihood framing: the actual disclosure trigger is an admin-level log-level change, but the sensitive-data exposure itself is caused entirely by application code failing to redact request fields, and every subsequent unprivileged request is captured.

## Recommendation
- Remove `"request", req` from the Debug log at `core/services/gateway/handlers/vault/handler.go:403`, or replace it with a sanitized projection excluding `req.Auth` and raw `Params` (mirroring the redaction already used for the "invalid params" Error-level log).
- Apply the same treatment to the public-key-fetch Debug/Error logs at lines 333, 342, 347, 357.
- Extend `TestVaultHandler_InvalidParamsDoesNotLogRawParams` (or add a new test) to assert at Debug level that the "handling vault request" log entry does not contain `Auth` or raw `Params` values, rather than filtering the assertion to Info level to avoid the log line.

## Proof of Concept
1. Start a gateway node/test harness with `Log.Level = debug`.
2. Submit any vault JSON-RPC request via `HandleJSONRPCUserMessage` with a non-empty `Auth` field (e.g., a `MethodSecretsCreate` request with `req.Auth = "<jwt>"`).
3. Observe the log entry `"handling vault request" method=... requestID=... request={...Auth: "<jwt>", Params: {...}}"` emitted at `core/services/gateway/handlers/vault/handler.go:403`, containing the full `Auth` token and raw `Params` in plaintext — reproducible as a Go unit test using `logger.TestObserved(t, zapcore.DebugLevel)` and asserting the log entry's `ContextMap()["request"]` contains the auth token/marker.
