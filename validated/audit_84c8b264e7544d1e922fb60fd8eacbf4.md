This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over the body only, then dispatches the handler using `request.shop` taken from the header [3](#0-2) , so the shop identity is never bound by the signature that authenticates the request.

### Title
Webhook shop-domain (and topic/webhook-id) header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body alone, but `Registry.process` trusts the `shop`, `topic`, and `webhook_id` values taken from HTTP headers that are not included in that signable string. Since the HMAC secret (`client_secret`) is shared across every shop that has installed the app, any tenant that legitimately receives a webhook can replay the same body+HMAC pair to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header, and the gem will accept it as authentic and dispatch it as if it originated from the victim shop.

### Finding Description
`Registry.process` performs exactly one authenticity check:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` this method returns only `@raw_body`:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are parsed straight from attacker-controllable HTTP headers, with no cryptographic tie to the signed body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

The identity binding that should hold is: `hmac(body, client_secret) == received_hmac` should imply the `shop` header value is the shop for which that HMAC was actually generated by Shopify. Because the header is excluded from the signed content, this equality does not hold — `hmac` validity only proves "this body was signed once by the app's client_secret for some shop," not "for this particular shop." Since `client_secret` is identical for every store that installs the same app, any shop with the app installed can observe a legitimate webhook (body + valid HMAC) sent to it, then re-POST that exact body/HMAC pair to the app's public webhook endpoint while substituting a different shop's domain in the `X-Shopify-Shop-Domain` header (or `X-Shopify-Topic` / `X-Shopify-Webhook-Id`). `Registry.process` passes HMAC validation and calls the registered handler with `WebhookMetadata` built from these unverified header values:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

Host applications built on this gem (e.g. the common pattern documented in the gem's own README/webhooks doc) key their persistence and business logic off `WebhookMetadata#shop`, trusting it as the authenticated tenant identifier, exactly as they are expected to per this gem's documented contract.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls one shop that has the app installed can forge a webhook event attributed to a different (victim) shop, since the `shop` field consumed by application logic is not bound by the same HMAC that authenticates the request. This matches the "Critical - cross-tenant access" impact category, as it lets one tenant inject fabricated webhook data (e.g. `app/uninstalled`, `shop/redact`, `orders/create`) that the host app will process as belonging to another merchant's session/data.

### Likelihood Explanation
Exploitation requires only: (1) having the target app installed on any shop the attacker controls (a normal, unprivileged action any merchant can take by installing a public app), (2) observing one webhook delivery's body and its valid HMAC (trivial, since it's delivered to the attacker's own endpoint), and (3) POSTing that captured payload to the app's public webhook URL with a forged `X-Shopify-Shop-Domain` header. No access to `client_secret`, tokens, or the victim's infrastructure is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the payload/signature) in `Webhooks::Request#to_signable_string`, so that a signature is only valid for the specific shop/topic/webhook-id combination it was issued for. At minimum, document and/or enforce that host apps must independently verify `request.shop` against a shop known to have installed the app before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (their own store).
2. Shopify sends a legitimate webhook to the app's callback URL:
   - Body: `{"id": 1, ...}`
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`, `X-Shopify-Topic: orders/create`
3. Attacker captures this raw body and HMAC value (visible on their own endpoint).
4. Attacker re-sends an HTTP POST to the same app webhook endpoint with the identical body and HMAC, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the body only) — this matches, since the body is unchanged [6](#0-5) .
6. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this event for that shop [5](#0-4) .
