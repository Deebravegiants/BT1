### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used by webhook handlers from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` checks covers only the raw request body. Because the shop identity is not bound to the signed bytes, any party who can obtain one validly-signed webhook payload (e.g., a merchant installing the app receiving webhooks to their own endpoint) can replay that exact body+HMAC pair while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it and hand a spoofed shop identity to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies exactly `to_signable_string` (the body) against the HMAC, with no reference to any header including shop: [3](#0-2) 

`Registry.process` validates only the body HMAC and then dispatches to the handler using `request.shop` and `request.parsed_body` verbatim, with no cross-check that the shop header matches anything cryptographically tied to the signature: [4](#0-3) 

The broken identity binding is:
```
shop authenticated by HMAC (none — HMAC covers body only)
   !=
shop trusted by the handler (WebhookMetadata.shop, taken from an attacker-controllable header)
```

Attack sequence:
1. Attacker installs the target app on their own shop (or otherwise gets one legitimate webhook delivered to a reachable endpoint), capturing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared `api_secret_key`.
2. Attacker resends that exact body and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) to a victim shop's domain.
3. `HmacValidator.validate` succeeds because the body and HMAC are unchanged and match under the shared secret.
4. `Registry.process` calls `handler.handle` with `WebhookMetadata.shop` set to the victim's domain, `topic`, and `body` from the attacker's own event, so the app's business logic executes as if the event/action belongs to the victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged app-installer (any merchant, i.e., an "unprivileged internet user" relative to other tenants) can make the gem report a webhook as originating from a different shop than the one that actually produced it. If the host application uses `data.shop` from `WebhookMetadata` to select which merchant's session/access token/data record to update (a common, documented usage pattern for this gem's webhook API), the attacker can cause state changes attributed to, or scoped to, another merchant's tenant — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker has installed the app on some shop (normal customer capability) and can capture/replay one legitimate webhook body+HMAC pair to the app's public webhook endpoint with a forged header; no access token, secret key, or privileged role is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signable content verified by `HmacValidator`, or have `Registry.process`/`WebhookMetadata` independently verify that the shop header corresponds to a shop actually known/installed by the app before trusting it, rather than passing the raw header value straight into handler dispatch.

### Proof of Concept
```ruby
# 1. Attacker (an installed merchant) captures a real webhook delivery to their own
#    reachable endpoint: raw_body = '{"id":1}', hmac = <valid HMAC over raw_body only>.

# 2. Attacker resends the identical body/hmac to the app's webhook endpoint,
#    but swaps the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_valid_hmac, # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
}
req = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)

ShopifyAPI::Utils::HmacValidator.validate(req) # => true, because HMAC only covers raw_body
ShopifyAPI::Webhooks::Registry.process(req)
# handler.handle receives WebhookMetadata with shop == "victim-shop.myshopify.com"
# even though the payload/topic actually came from the attacker's own shop event.
``` [4](#0-3)
