### Title
Webhook `shop` (tenant) identity is read from an unauthenticated header not covered by the HMAC signature — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop/tenant identity for a webhook exclusively from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, while the HMAC that `Utils::HmacValidator.validate` checks is computed only over the raw request body. The header that identifies *which tenant* the webhook belongs to is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` reads directly from the header: [1](#0-0) 

`to_signable_string`, which is what `Utils::HmacValidator.validate_signature` HMACs, returns only `@raw_body`: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.shop` and forwards it to the handler as the tenant/shop identity, without any cryptographic binding between the body's signature and the shop-domain header: [3](#0-2) 

The identity equality that should hold is: `shop-domain header used for tenant dispatch == shop that produced/authorized the signed body`. Because the header is excluded from `to_signable_string`, this equality is never checked — only `hmac(raw_body) == hmac_received` is checked. This is the same bug class as the referenced report: a field that is acted upon (the balance/shop identity) is not covered by the check that's supposed to bind it (`_request.maxAmountsIn[i]` / the HMAC signature).

### Impact Explanation
Any party able to reach the app's public webhook endpoint with a body+HMAC pair that is valid for the shared `client_secret` (e.g., replaying/relaying a webhook originally delivered for their own shop, or any other means of obtaining a valid `(body, hmac)` pair) can freely set the `shopify-shop-domain` header to an arbitrary victim shop domain. The library will accept the request as authentic (HMAC checks out) and hand the host application a `WebhookMetadata`/dispatch keyed to the attacker-chosen shop, not the shop that actually authorized/produced the payload. If the host application uses this `shop` value to look up per-tenant state, credentials, or to write/attribute data (as the library's own docs direct apps to do), this enables cross-tenant data confusion/corruption — one tenant's webhook event being attributed to and processed against a different tenant's records.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — which any shop that has legitimately installed the app will naturally receive via ordinary webhook deliveries for its own events. No possession of the actual `client_secret` is required, and the webhook endpoint is a public HTTP endpoint reachable over the internet. The library performs no additional binding between the authenticated body and the shop header, so likelihood is limited only by the attacker's ability to intercept/replay/craft such requests to the public endpoint with a modified header — a capability squarely available to an unprivileged internet user who is a customer/tenant of the same multi-tenant app.

### Recommendation
Include the shop domain (and ideally the topic) in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the `shop-domain` header to the signed payload before trusting it for tenant dispatch. At minimum, document that host applications must independently verify `request.shop` corresponds to a shop with a legitimate, stored session/access token before processing webhook data, rather than trusting the header once HMAC-on-body passes.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed and legitimately receives (or can trigger, e.g. via `orders/create`) a webhook delivery to the app's public endpoint with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays a POST to the same public webhook endpoint with the identical body `B` and HMAC header `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) and `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(client_secret, B) == H`, per: [4](#0-3) 
4. `Registry.process` dispatches the handler with `shop: request.shop` = `"victim-shop.myshopify.com"`, per: [3](#0-2) 
5. Any host application logic keyed on `data.shop` now operates against the victim tenant using the attacker-controlled payload `B`, even though `B` was never produced by or authorized for that tenant.
