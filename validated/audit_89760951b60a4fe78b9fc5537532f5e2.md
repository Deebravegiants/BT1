Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` value taken from an HTTP header that is never part of the signed bytes. Anyone who can obtain one genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially available to any merchant who installs the app, since they will legitimately receive webhooks for their own shop — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes because it does not bind to the shop, letting the attacker impersonate a different (victim) shop in the data delivered to the app's `WebhookHandler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC purely over `verifiable_query.to_signable_string`: [2](#0-1) 

Meanwhile `Request#shop` is read straight from a header with no cryptographic binding to the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the app's handler as the authenticated tenant identifier: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field consumed by the app-defined `WebhookHandler#handle`, with no further validation available or performed by the gem: [5](#0-4) 

The identity binding that should hold is:
`shop_verified_by_HMAC == shop_acted_on_by_handler`

In this code, the left side is never computed — the HMAC only proves "this body/api_secret_key pair is authentic," not "this body belongs to shop X." Since the `api_secret_key` is a single app-level secret shared across all installations (not per-shop), a valid HMAC for shop A's traffic is equally valid when the shop header is swapped to shop B. This is the same "field acted upon but not covered by the HMAC" class as the redeem-example bug in the prompt: the router redeemed `mTokenRedeemAmount` while trusting stale state not verified by the failed call; here the app acts on `shop` while trusting a header not verified by the passing HMAC.

### Impact Explanation
Any actor who can install the app on their own shop (a normal, unprivileged action) legitimately receives real webhook deliveries (body + valid `hmac-sha256`) for their own shop. They can then replay that exact body and HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` will validate the HMAC successfully and hand the handler a `WebhookMetadata` claiming the event came from the victim shop. Any app logic that trusts `WebhookMetadata#shop` to look up sessions, write per-tenant data, or trigger shop-scoped side effects will process the forged data under the victim's tenant — a cross-tenant data-integrity/confusion issue reachable by an unprivileged internet user who only needs to be a legitimate merchant of their own store.

### Likelihood Explanation
Likelihood is high for any developer using this gem as documented: obtaining a genuine `(body, hmac)` pair requires nothing more than installing the app on any shop (which is the normal onboarding flow), and replaying an HTTP POST to a public webhook endpoint with a modified header requires no special access, credentials, or knowledge of `api_secret_key`. The gem provides no built-in defense (e.g., no per-shop secret, no shop binding in the signed content, no webhook_id de-duplication/shop cross-check), so the vulnerability is exploitable purely through the gem's documented webhook validation API.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, not just the raw body. Options:
- Have `Request#to_signable_string` (or a new signable representation) include the shop domain and topic instead of, or as well as, the raw body, so the HMAC cryptographically commits to which shop the payload is for.
- After Shopify's HMAC validation passes, cross-check `request.shop` against expected/registered shops for that call (e.g., require the shop to be resolvable in the app's own session store) before invoking the handler, and reject unknown/mismatched shops.
- Document clearly that `WebhookMetadata#shop` is unauthenticated by itself and must not be trusted without an independent shop lookup.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, completing OAuth normally (no special privileges).
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker intercepts/replays this exact POST to the same endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but rewrites `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes the HMAC over `B` using the app's single `api_secret_key` and finds it matches `H` — validation passes (see `hmac_validator.rb:12-31`).
5. `Registry.process` proceeds, builds `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (see `registry.rb:198-199`), and invokes the app's handler as if the (attacker-controlled) event body genuinely originated from `victim.myshopify.com`.
