### Title
Unchecked low-level ERC20 transfer in `IntentGatewayV2.withdraw` lets escrow accounting be decremented (and finalized) without funds actually reaching the beneficiary - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` decrements order-escrow accounting (`_orders[commitment][token]`) and marks the order as filled/refunded based solely on whether a raw `.call` to the token's `transfer` selector did not *revert*, without checking the ERC20 boolean return value. This mirrors the root cause of the H-04 finding: an accounting variable that represents custody of externally-held funds is mutated (and later relied upon) without confirming the corresponding value transfer actually happened, permanently losing/freezing funds owed to intent users and solvers.

### Finding Description
`IntentGatewayV2.withdraw` (Tron variant) redeems escrowed tokens for a `WithdrawalRequest` and finalizes the order: [1](#0-0) 

For every non-native token, it performs:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
and similarly for the transaction-fee redemption. `success` here only reflects whether the low-level `call` reverted; it does **not** decode/verify the `bool` return value that `transfer()` is supposed to return. Non-standard or degraded ERC20 tokens (a real risk on Tron, which is exactly why this file exists as a separate, non-`SafeERC20` implementation for some paths despite importing `SafeERC20`) can return `false` on failure instead of reverting — e.g. insufficient balance/allowance edge cases, paused/blacklist-style tokens, or tokens with non-conforming return data that get silently treated as `true`.

When that happens:
1. `success` is `true` (the call didn't revert), so execution proceeds.
2. `_orders[body.commitment][token]` is decremented as if the beneficiary was paid.
3. `_filled[body.commitment]` is set, finalizing/closing out the order.
4. The tokens never left the contract and the beneficiary never received them, but the escrow accounting that is the only mechanism for recovering those funds has already been reduced to zero (or otherwise cannot be re-claimed, exactly analogous to `KangarooVault.removeCollateral` decrementing `totalCollateral`/`usedFunds` without the exchange call that would have moved the actual collateral).

The correct EVM-side implementation in `IntentsBase._withdraw` avoids this class of bug entirely by using `SafeERC20.safeTransfer`, which reverts on both call failure and a falsy return value: [2](#0-1) 

The Tron `withdraw()` function, despite `using SafeERC20 for IERC20;` being declared at the contract level, deliberately bypasses `safeTransfer` in favor of a raw `.call` + `success`-only check, reintroducing the same "storage says paid, but funds were never actually moved" flaw that the KangarooVault report is about.

### Impact Explanation
This function is reachable by any relayer delivering a Hyperbridge `RedeemEscrow`/`RefundEscrow` POST request (solver redemption or user cancellation refund) or a GET response callback (`onGetResponse`) — i.e., it is on the core intent-settlement path, not an admin-only function. If the escrowed token misbehaves (returns `false` instead of reverting on transfer failure), the contract:
- permanently loses the user's/solver's ability to reclaim the escrowed tokens (the escrow slot is zeroed/decremented, and the order is marked `_filled`, so no retry path exists), while
- the tokens remain stuck in the `IntentGatewayV2` contract, unreachable by any other function (no sweep path covers "wrongly-retained escrow").

This is concrete permanent freezing/loss of user funds on a widely-reachable, unprivileged code path (solver fill/cancel flow), which matches the High-severity bar of the analog report.

### Likelihood Explanation
Likelihood depends on encountering a non-fully-ERC20-compliant token whose `transfer` can return `false` without reverting. This is a materially higher risk on Tron than on standard EVM chains — TRC-20 tokens have a documented history of divergent/non-standard return-value semantics, which is precisely the environment this dedicated Tron contract variant targets. Any order settled in such a token triggers the loss deterministically once a transfer legitimately fails (e.g., balance edge cases, blacklists, pausable transfers) rather than reverting.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` (and any other place in this file using the same pattern, e.g. the `SweepDust`/`placeOrder` paths) with `SafeERC20.safeTransfer`/`safeTransferFrom`, which already correctly decodes and enforces the ERC20 return value:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
so that only a genuinely realized transfer causes the down-stream escrow decrement/finalization to proceed; a token that returns `false` should revert the whole call, not silently succeed.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token contract that implements `transfer` to return `false` (rather than reverting) when, e.g., the sender is blacklisted or balance/allowance checks fail internally — a legal ERC20 implementation choice, and common among non-compliant/legacy tokens deployed on Tron.
2. A user places an order with escrow in that token; a solver fills it (or the user cancels it), producing a `WithdrawalRequest` routed to `onAccept`/`onGetResponse` → `withdraw(body, isRefund)`.
3. Have the token's internal state such that the `transfer` call to the beneficiary legitimately fails and returns `false` (call does not revert).
4. Observe: `withdraw()` does not revert (`success == true` from the low-level call), `_orders[commitment][token] -= amount` executes, `_filled[commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted.
5. Check the beneficiary's token balance: unchanged. Check the gateway contract's token balance: still holds `amount`. The escrow accounting no longer reflects any claim on those tokens, and the order is already finalized — the funds are permanently stuck/lost with no code path to recover them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;

            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;

                _sendValue(beneficiary, amount);

                IERC20(token).safeTransfer(beneficiary, amount);
