### Title
Webhook `shop` and `topic` are trusted from unauthenticated headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` and `topic` from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`) that are never included in the HMAC-signed payload. `Registry.process` validates only the HMAC over `raw_body` and then dispatches the handler using the unverified `shop`/`topic` values, breaking the binding: `shop_attributed_to_event == shop_covered_by_hmac`.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [2](#0-1) 

The `hmac` accessor reads `shopify-hmac-sha256` and is checked against a signature computed purely over the body: [4](#0-3) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic binding to the body or to each other: [5](#0-4) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to route/attribute the event to a tenant: [6](#0-5) 

Because the identifying headers are outside the signed scope, any request carrying a *previously valid* `(body, hmac)` pair (e.g., one the attacker legitimately received for their own shop) remains HMAC-valid no matter what `shop-domain`/`topic` headers are substituted in. This equality that should hold — "the shop attributed to the processed webhook" == "the shop whose secret produced the HMAC over that exact event" — is broken because the shop identity is never part of what the HMAC actually authenticates.

### Impact Explanation
An attacker who operates their own Shopify store (an ordinary, unprivileged merchant/internet user relative to the target app) can capture a legitimate, validly-signed webhook body+HMAC delivered to them by Shopify, then replay that same body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop and/or the `topic` header. `Registry.process` will accept it (HMAC checks out) and hand the handler data tagged with the attacker-chosen `shop`/`topic`/`webhook_id`, enabling cross-tenant data confusion in the host app (e.g., processing another shop's mandatory `customers/data_request`/`shop/redact` flows, or injecting fabricated events attributed to a victim shop) — a cross-tenant integrity violation.

### Likelihood Explanation
Moderate: it requires the attacker to install the app on a shop they control (to receive at least one genuine signed webhook) and to know/guess a victim shop domain, both of which are readily satisfiable by any unprivileged internet user; no leaked secrets or privileged access are needed.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signed string, or otherwise cryptographically bind them to the HMAC-covered payload, so that `to_signable_string` reflects everything the application trusts and dispatches on, not just the raw body.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because `to_signable_string` for `Webhooks::Request` is only `@raw_body`.
2. Attacker resends the identical body and HMAC to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`).
3. `Utils::HmacValidator.validate(request)` in `Registry.process` recomputes the signature over `@raw_body` only, which still matches, so validation passes.
4. `handler.handle` is invoked with `shop: "victim.myshopify.com"`, `topic:` attacker-chosen value, and the attacker-controlled body — the host app processes an event as if it legitimately originated for the victim shop.
