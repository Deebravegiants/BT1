Based on my research, the strongest analog to the WBGL-as-collateral issue exists in the Simplex filler's Uniswap V4 pool-based pricing path for "venue-priced" (curveless) pairs.

### Title
Thin-liquidity Uniswap V4 pool used as an unbounded exotic-token price oracle for Simplex fills - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
When a Simplex LP configures a cross-asset pair without static bid/ask curves, the filler derives the fill price directly from a live Uniswap V4 pool's `sqrtPriceX96` mid-price via `UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd`, exactly mirroring the WBGL report's pattern of trusting an easily-manipulated, thin on-chain price source for a financial decision (sizing/valuing a fill) without any depth- or impact-adjustment. [1](#0-0) 

### Finding Description
`resolveLegRates` in the filler's FX strategy picks the venue price for a curveless pair from `UniswapV4FundingPlanner.getExoticTokenPrice`, which selects "the position with the largest pool liquidity" and returns the *raw pool mid* computed from `sqrtPriceX96` — with no size or price-impact term applied. `computeLegPolicyOutput` then extends this mid linearly across the entire quantity being priced. [2](#0-1) 

The only mitigation is `checkPriceGuard`, which rejects a quote if it deviates more than `maxDeviationBps` from a static `referencePrice` configured by the LP operator — but this is optional ("omit both to leave the chain unguarded") and even when present it only bounds deviation from a stale reference, not execution cost or pool depth. [3](#0-2) 

This is structurally identical to the WBGL finding: a protocol-critical valuation is sourced from a single, potentially thin liquidity venue, with only an optional, coarse bound as protection, and no consideration of the manipulation cost relative to pool depth.

### Impact Explanation
An attacker (any unprivileged actor, since Uniswap V4 pools are public and swappable by anyone) can manipulate the referenced pool's price within the `maxDeviationBps` band (or entirely, if the LP left the guard unset per the docs' explicit callout) and then place/fill an intent order priced off that pool. Because `computeLegPolicyOutput` extends the manipulated mid linearly with no depth-awareness, the attacker can extract solver funds (the LP's escrowed/vault inventory) at a favorable rate — a direct theft-of-funds vector against the LP's treasury, analogous to draining the USSD protocol's collateral pool via a manipulated WBGL price.

### Likelihood Explanation
Likelihood is contingent on real-world configuration: it requires an LP to configure a curveless, venue-priced pair with a **thin** Uniswap V4 pool and either omit the guard or set a loose `maxDeviationBps`. This is an operator-choice/configuration risk rather than a protocol-level bug reachable purely by an unprivileged actor without any operator misconfiguration, and the guard mechanism (`referencePrice`/`maxDeviationBps`) already exists specifically to bound this attack — the docs explicitly flag the trust assumption ("Pool-based pricing trusts the live pool... exposed to a manipulated, stale, or thin pool"). This weakens confidence that it constitutes an unconditionally exploitable protocol vulnerability versus a documented, mitigable operational risk.

### Recommendation
- Make the `referencePrice`/`maxDeviationBps` guard mandatory for any venue-priced pair rather than optional.
- Incorporate pool depth/impact into `computeDirectPoolPriceUsd` (e.g., TWAP over a manipulation-resistant window, or size-aware quoting) rather than trusting the instantaneous `sqrtPriceX96` mid linearly extended across the full fill size.
- Cap per-order/per-fill notional relative to the referenced pool's available liquidity, similar to the WBGL report's recommendation of capping exposure to a fraction of the collateral asset's liquidity.

### Proof of Concept
Not independently verifiable from the indexed code alone (the exact `checkPriceGuard` deviation logic and `UniswapV4FundingPlanner.computeDirectPoolPriceUsd` implementation could not be fully read within tool limits — only doc-level and cross-referenced snippets were available). Conceptually: an attacker swaps against the configured thin V4 pool to move `sqrtPriceX96` within the allowed deviation band (or unboundedly, if the pool's guard fields are unset), places an intent order against the affected pair, and the filler's `resolveLegRates`/`computeLegPolicyOutput` values the fill at the manipulated mid, letting the attacker extract solver-held inventory at a favorable rate before the pool price reverts.

```

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
