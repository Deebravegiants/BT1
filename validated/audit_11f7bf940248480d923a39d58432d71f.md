Confirmed root cause. The `shop` identity field in `ShopifyAPI::Webhooks::Request` is populated from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header [1](#0-0) , but `to_signable_string`, which is what `HmacValidator` actually authenticates, only returns the raw request body [2](#0-1) . `HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it against the `hmac` header [3](#0-2) . `Registry.process` then trusts `request.shop` (and `request.topic`) unconditionally to build the `WebhookMetadata` passed to the app's handler once the body HMAC passes [4](#0-3) .

### Title
Webhook tenant identity (`shop`, `topic`) not bound by HMAC in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only covers the raw body, while `shop` and `topic` — the values used by `Registry.process` to route/tenant-scope webhook data — come from unauthenticated headers.

### Finding Description
`HmacValidator.validate` (used by `Registry.process`) proves only that *some* request with a given body was HMAC-signed with the app's shared `api_secret_key` [5](#0-4) . It never authenticates which shop or topic the payload is attributed to, because `Request#shop`/`Request#topic` are read straight from client-supplied headers and excluded from `to_signable_string` [6](#0-5) . Since `api_secret_key` is a single value shared across every shop that has installed the app (not per-tenant), any party who has legitimately received one valid `(body, hmac)` pair — e.g., a merchant using the app on their own store — can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards the forged `shop`/`topic` straight into `WebhookMetadata` for the handler [7](#0-6) . The binding that should hold — "shop credited by HMAC == shop the app acts on" — is broken: the HMAC only certifies `body`, not `(body, shop, topic)`.

### Impact Explanation
Applications built on this gem rely on `WebhookMetadata#shop` to determine which tenant's records to update/create in `handle(data:)`. Because that field isn't cryptographically bound to the signature, an attacker holding one valid signed payload for their own shop can inject fabricated webhook data attributed to any other shop, resulting in cross-tenant data corruption/injection in the host application — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Requires the attacker to already have obtained one legitimately-signed `(body, hmac)` pair, most trivially by installing the app themselves (any merchant can do this) and capturing a webhook Shopify sends them, then replaying it against the app's public webhook endpoint with a different shop header. No knowledge of `api_secret_key` is needed since the signature is replayed verbatim.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise validate that the `shop` header corresponds to an existing, expected session/tenant before dispatching to the handler, rather than trusting the header value that arrives alongside a body-only signature.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H`, computed as `HMAC-SHA256(api_secret_key, B)` — `H` does not depend on the shop header at all.
2. Capture `(B, H)`.
3. POST to the app's webhook endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only and matches `H` — passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the handler, which acts on the victim's tenant using attacker-controlled body content.
