Based on my investigation, this is a legitimate analog finding. The `shop` field is passed through to the handler in `WebhookMetadata` as an authoritative, trusted tenant identifier (per the documentation: `"shop", String` - "The shop domain of the webhook"), yet the `hmac` field in `ShopifyAPI::Webhooks::Request` covers only `@raw_body`, never the `shop-domain` header.

### Title
Webhook `shop` domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `topic`, `shop`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` returns only the raw body. `Utils::HmacValidator.validate` verifies the HMAC exclusively against that raw body, so the `shop` value delivered to the app's registered handler is never bound to the signature that authenticates the request as genuinely originating from Shopify for that shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` performs a single authenticity check: [1](#0-0) [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Request`, `to_signable_string` returns `@raw_body` only, while `shop`, `topic`, `api_version`, and `webhook_id` come from HTTP headers that are never included in the signed content: [3](#0-2) [4](#0-3) 

The equality that the gem's own naming and documentation implies but never enforces is: `hmac-verified-authenticity == shop-domain-header-value`. In reality only `hmac-verified-authenticity == raw_body content` holds. The `shop` field is passed straight through as authoritative tenant identity to the app's handler via `WebhookMetadata`, which the docs describe as "The shop domain of the webhook": [5](#0-4) 

Because a genuine, HMAC-valid webhook body received by shop A's app instance carries no cryptographic tie to the `shop-domain` header, an attacker who controls an installation of the app on their own shop (a legitimate, unprivileged capability of any Shopify merchant/developer) can capture one of their own valid webhook deliveries (valid `raw_body` + valid `hmac-sha256`) and replay it to the same app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to select which tenant's record to update (the pattern explicitly shown in the gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) is exposed to cross-tenant data corruption/injection: an attacker-controlled shop can inject webhook events that are processed as if they belonged to a shop the attacker does not control. This matches the "cross-tenant access" Critical-impact category, since the tenant boundary (`shop`) is not bound to the authenticity check (`hmac`).

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must control at least one shop with the target app installed (to obtain a validly-signed body/HMAC pair) and must be able to reach the app's public webhook HTTP endpoint directly (not through Shopify's delivery infrastructure) with a forged `shop-domain` header — both are realistic for any internet-reachable Rails/Sinatra endpoint built per the documented `ShopifyAPI::Webhooks::Registry.process` usage.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed content, or otherwise cryptographically or contractually bind the returned `shop` field to the verified payload, e.g., extend `Request#to_signable_string` to incorporate the shop-domain header, or have `HmacValidator`/`Registry.process` re-derive/validate `shop` from a source that is itself covered by the signature.

### Proof of Concept

# receives a genuine webhook from Shopify for their own shop:

# Attacker replays it directly to the app's public callback URL,

# => Utils::HmacValidator.validate(request) returns true (body matches signature)

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
