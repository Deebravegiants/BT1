### Title
Same-token withdrawals in one batch resolve to identical status/txHash regardless of destination - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal by `assetId` only via `findMatchingWithdrawal`, using `Array.find`, which returns the first entry in the (unsorted) POA API response whose `near_token_id` matches. When a single intent contains two withdrawals of the same PoA token (e.g. `nep141:adi.omft.near`) to different destinations/amounts, both resulting `WithdrawalIdentifier`s (index 0 and index 1) query the same `withdrawal_hash` and both get matched to the same (first) API entry, so one destination's actual completion/failure is misreported onto the other.

### Finding Description
The broken equality is: `describeWithdrawal(wid_i).status/txHash` should equal the status/txHash of the withdrawal actually delivered to `wid_i.withdrawalParams.destinationAddress`/`amount`, for each `i` in the batch.

Code path:
- `IntentsSDK.waitForWithdrawalCompletion` → `watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:36`) calls `bridge.describeWithdrawal({...args.wid, ...})` per `WithdrawalIdentifier`, with `wid.tx.hash` being the same NEAR transaction hash for all withdrawals created in one intent (see `createWithdrawalIdentifiers`, `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`, where the `index` is bridge-route-scoped but `tx` is shared).
- `describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry`, which fetches `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` — the SAME query for every withdrawal in the batch since they share the same NEAR tx hash.
- The response (`response.withdrawals`) is a list of ALL withdrawals in that transaction. `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — this ignores destination address, amount, and the `index`/ordering entirely.
- The code's own comment (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:409-417`) explicitly states: *"multiple withdrawals of the same token in a single transaction are not supported"* and that the API doesn't support disambiguation either — yet nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` rejects or blocks such a batch from being submitted and watched.

Because `.find()` always returns the first array element matching the token, both `WithdrawalIdentifier`s for index 0 and index 1 (same assetId, same tx hash, different destinations/amounts) resolve to the identical first-matching entry. If that first entry is `COMPLETED` while the second withdrawal is still `PENDING` or `FAILED` (or vice versa), the integrator watching the second `WithdrawalIdentifier` receives the wrong status and `txHash` — e.g., a `completed` status with a `transfer_tx_hash` that actually paid out to the *other* destination.

None of the listed guards prevent this: `validateAddress`/`compareAddresses` validate a single address in isolation and don't compare across batch entries; `supports()` only checks assetId/route type; there is no `matchesRequest`-style check tying the API withdrawal record's destination address/amount back to the specific `WithdrawalIdentifier.index`.

### Impact Explanation
An integrator polling withdrawal status for a batch with two `nep141:adi.omft.near` withdrawals to different addresses can be told withdrawal B is `completed` with a `txHash` that in reality corresponds to withdrawal A's payout (or vice-versa), even though B may still be pending or failed. This is a status/hash misreport that can cause an integrator to credit a user for a withdrawal that has not landed at their address, or to consider a withdrawal safe when a different one actually failed — matching the "High" impact category (status or hash misreport making an integrator credit or refund twice). This is fully repeatable by any user who deliberately constructs such a batch, and non-deterministic/order-dependent based on unsorted API results, making the exact effect on a per-run basis uncertain but the wrong-match structurally always present in a two-same-asset batch.

### Likelihood Explanation
Preconditions: the batch must contain ≥2 withdrawals of the exact same PoA `assetId` (e.g. `nep141:adi.omft.near`) with different destinations/amounts, submitted as one intent/one NEAR transaction. Nothing in `PoaBridge.supports`, `validateWithdrawal`, or the SDK's batch-construction code (`createWithdrawalIdentifiers`) blocks or disambiguates this case — it is explicitly documented as unhandled. Attacker cost is a single ordinary intent with normal funds; no privileged access, and it is repeatable at will.

### Recommendation
Either (a) reject batches containing multiple withdrawals of the same `assetId` in `createWithdrawalIdentifiers`/`supports`/`validateWithdrawal` until the POA bridge API supports disambiguation, or (b) implement the sorting-based matching the code comment suggests — sort both the API's returned withdrawals and the batch's same-asset withdrawal params by amount (since relayer fees are equal for same token) and match positionally, so each `WithdrawalIdentifier.index` binds to the correct destination/amount pair, rather than taking the first `.find()` match by assetId alone.

A correct implementation should assert `describeWithdrawal(widA)` returns `completed` and `describeWithdrawal(widB)` returns `pending`, distinguishing the two entries by destination/amount, not just assetId. 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
