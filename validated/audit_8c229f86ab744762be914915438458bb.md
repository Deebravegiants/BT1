### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` as trusted identity fields for a webhook delivery, but the HMAC signature that `Webhooks::Registry.process` verifies covers only the raw request body — never these header-derived fields. Any party who can obtain one validly-signed webhook body/HMAC pair for the app's shared `api_secret_key` (e.g. a merchant installing the app on their own store) can replay that body+HMAC pair while altering the `shop`, `topic`, or `webhook_id` headers, and the signature check will still pass.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet `shop`, `topic`, and `webhook_id` are all read directly from HTTP headers that are not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these unsigned fields to route and identify the webhook: [3](#0-2) 

The identity binding that should hold is:
`HMAC(secret, signed_bytes) == received_hmac` where `signed_bytes` should determine the *complete* semantic content the app acts on (topic + shop + body). Instead, `signed_bytes == raw_body` only, while `shop`/`topic`/`webhook_id` are taken from unauthenticated headers and handed to the app's handler as if they were verified (`WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)`), a mismatch between "bytes verified" and "bytes acted on" that is the same bug class as the `TapiocaOptionBroker` finding (state used to make a decision diverges from the state that was actually validated).

Because `api_secret_key` is shared by the app across every installed shop, any merchant that installs the app can capture one of their own genuinely-signed webhook deliveries (many topics, e.g. `app/uninstalled`, ship with a minimal/empty JSON body) and re-POST that exact body + HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop and/or the `x-shopify-topic` header for a different registered topic whose handler accepts that body shape. `Registry.process` will accept it as authentic for the victim shop/topic because the HMAC only ever validated the body bytes.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who controls one installed shop can cause the app to process a forged webhook "as" a different shop or under a different topic, without possessing that victim's session, access token, or the app's `client_secret`. Depending on what the handler does with `WebhookMetadata#shop`/`#topic` (e.g. deactivating/mutating per-shop stored state, treating `app/uninstalled` as a signal to wipe a victim's stored session), this can lead to cross-tenant state manipulation. This matches the Critical "cross-tenant access" impact category, since the boundary between one merchant's authenticated identity and another's is bridged purely by unauthenticated header values.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be able to install the app on at least one shop of their own (a normal, unprivileged action for any Shopify merchant) and to obtain a same/compatible-shaped body for the topic they want to spoof — several standard topics (e.g., `app/uninstalled`) commonly send an empty or near-static body, making this straightforward without any credential compromise.

### Recommendation
Bind the identity fields into the signed material instead of trusting header values. Since the app cannot control what Shopify signs, mitigation must happen on receipt: validate that `request.shop` corresponds to a shop with an active, known session/installation for this app before acting on the payload, reject topics that structurally conflict with the delivered body, and/or additionally verify `webhook_id` uniqueness/idempotency scoped per shop to prevent cross-shop replay. At minimum, `Webhooks::Registry.process` (and its documentation) should make clear that `shop`/`topic`/`webhook_id` are **not** HMAC-covered and must be independently authorized by the host application against its own shop/session store before being trusted.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook topic whose body is constant/empty, e.g. `app/uninstalled`, and capture the raw body (`{}`) plus the `x-shopify-hmac-sha256` header Shopify computed with the app's shared `api_secret_key`.
2. Replay a POST to the app's webhook endpoint using the captured body and HMAC header unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks the body bytes against the shared secret.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) dispatches the handler with `shop: "victim.myshopify.com"`, causing the host app to act on behalf of a shop the attacker never authenticated as.
