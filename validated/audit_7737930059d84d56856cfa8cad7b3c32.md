### Title
Stale `rpc.on('end')` listener from a superseded connection can delete the active RPC entry and permanently reset `#defer`, causing `callMethod`/`notify` to hang - (File: libraries/browser-extension-rpc/src/rpc-manager.js)

### Summary
`RPCManager.add(id, rpc)` overwrites `#instances.get(id)` without removing the previous rpc's `'end'` listener, so when two connections share the same `id` (which happens in practice because `id = port.sender.tab?.id || port.sender.documentId`, i.e. the browser tab id), the old connection's delayed `'end'` event deletes the entry that now belongs to the *new*, still-live rpc. If that was the only entry, `#instances` becomes empty while the new rpc is still connected, `#defer` is reset to a pending promise, and no subsequent `add()` is guaranteed to fire (the tab is already connected, so `chrome.runtime.onConnect` won't fire again). Any later `callMethod`/`callMethodWithRawResponse`/`notify` call then awaits `#defer.promise` forever.

### Finding Description
- `add()` does `this.#instances.set(id, rpc)` and attaches an `'end'` handler closed over `id`: [1](#0-0) .
- The `'end'` handler unconditionally does `this.#instances.delete(id)` and, if the map becomes empty, replaces `#defer` with a fresh pending deferred and emits `'end'`: [2](#0-1) .
- The `id` passed into `add()` in the real caller is `port.sender.tab?.id || port.sender.documentId` — i.e. the browser tab id (falling back to documentId only when no tab id exists): [3](#0-2) .
- Because the tab id is stable across reconnects of the same tab (e.g. UI popup/page reload, rapid open/close of the extension UI, or navigation events that re-create the port while the tab id stays constant), rapid churn produces two ports/rpcs registered under the *same* `id`. Sequence:
  1. `rpc1` connects → `add(id, rpc1)` → `#instances = {id: rpc1}`, `#defer` resolved.
  2. `rpc1` disconnects and `rpc2` (new connection, same tab id) connects quickly → `add(id, rpc2)` → `#instances.set(id, rpc2)` overwrites the map entry, but `rpc1`'s `'end'` listener (registered in step 1, closed over the same `id`) is never removed.
  3. `rpc1`'s underlying port `onDisconnect` fires asynchronously (browser event ordering is not guaranteed to be synchronous with the new connect) → `rpc1.on('end')` handler runs → `this.#instances.delete(id)` removes the entry that now holds `rpc2`, even though `rpc2` is alive and functioning.
  4. Since `#instances` is now empty, `exists()` returns false, so `#defer` is replaced with a new pending deferred.
  5. No further `chrome.runtime.onConnect` event will fire for the already-connected `rpc2` tab, so `#defer` never resolves again.
  6. Any subsequent `callMethod('getAccounts')`/`notify()` call does `await this.#defer.promise` and hangs indefinitely: [4](#0-3) .
- No guard exists that checks `this.#instances.get(id) === rpc` before deleting in the `'end'` handler, and `add()` does not detach the previous rpc's listener when overwriting an `id`. This is the root cause of the inconsistency between `#defer` state and `#instances` contents that the question's invariant targets.

### Impact Explanation
This produces a genuine denial of wallet operations: the background RPC manager can end up in a state where a live, connected UI/dapp-facing rpc exists but is invisible to `#instances`, and `#defer` never resolves again, so all wallet RPC calls (`getAccounts`, transaction signing requests routed through this channel, etc.) hang forever for that session until the extension/browser is restarted. This matches the "denial of legitimate wallet operations" impact class described in the question. It does not lead to secret disclosure, unauthorized signing, or routing to a truly stale/foreign rpc instance (the map only ever holds rpcs added via `add()`, and deleted entries are simply dropped, not misrouted to an attacker-controlled instance), so the impact is limited to availability/hang rather than compromise of key material or cross-origin/account confusion.

### Likelihood Explanation
Triggering requires only ordinary, unprivileged actions: rapid reconnect/reload of the same tab hosting the extension UI/dapp connection (same `tab.id`), which is a normal capability of any user or a malicious page that can force reloads/reconnects of itself. The race depends on browser event ordering (the old port's `onDisconnect` firing after the new port's connect has already been processed), which is plausible under load/high churn but not deterministic — making it a realistic but timing-dependent condition rather than a trivially always-reproducible bug.

### Recommendation
In `add()`, before overwriting, remove any existing rpc's `'end'` listener for that `id` (or check `this.#instances.get(id) === rpc` inside the `'end'` handler before deleting), so a stale connection's `end` event cannot delete a newer connection registered under the same `id`. Alternatively, use a unique/monotonic per-connection identifier instead of `tab.id`/`documentId` to avoid collisions entirely.

### Proof of Concept
Invariant/fuzz test for `rpc-manager.js`:
```js
import RPCManager from '../rpc-manager.js'
import EventEmitter from 'eventemitter3'

const makeRpc = () => {
  const ee = new EventEmitter()
  return {
    on: (e, l) => ee.on(e, l),
    emit: (e) => ee.emit(e),
    callMethod: async () => 'ok',
  }
}

test('stale end handler must not delete a live instance registered under same id', async () => {
  const manager = new RPCManager()
  const rpc1 = makeRpc()
  const rpc2 = makeRpc()

  manager.add('tab-1', rpc1)
  manager.add('tab-1', rpc2) // simulate reconnect with same tab id, overwrites map entry

  // stale rpc1 'end' fires after rpc2 already registered
  rpc1.emit('end')

  expect(manager.exists({ id: 'tab-1' })).toBe(true) // FAILS: entry was deleted

  const result = await Promise.race([
    manager.callMethod('getAccounts'),
    new Promise((_, reject) => setTimeout(() => reject(new Error('hang')), 200)),
  ])
  expect(result).toBe('ok') // FAILS: callMethod hangs, promise rejects with 'hang'
})
```
Expected (buggy) behavior: `manager.exists({ id: 'tab-1' })` is `false` after step 3, and `callMethod` hangs/times out because `#defer` was reset and never resolves again, demonstrating the `#defer`/`#instances` inconsistency and resulting denial of wallet operations.
