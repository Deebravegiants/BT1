### Title
Arbitrary user-token theft through a route-selected swap venue - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A malicious swap route can name an attacker-controlled venue contract. That venue runs inside a user-authorized strategy and can request unrelated token transfers from the victim; Soroban records those transfers as authorization children that a simulation/signing flow may include. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts caller-provided route bytes after authenticating the account owner or delegate. [3](#0-2) [4](#0-3) 

The controller authorizes only its own exact input transfer to the configured router, then invokes `router.execute_strategy`; its later checks only bound controller input spend and require positive output. [5](#0-4) 

Router instructions resolve the `pool`, `token_in`, and `token_out` addresses from the caller-supplied address registry and dispatch them to the selected venue. [6](#0-5) [1](#0-0) 

The venue adapters then invoke that supplied pool address; for example, the Soroswap adapter calls `get_reserves` and `swap` on `ctx.hop.pool`. [7](#0-6) [8](#0-7) 

There is no binding between route venues and a reviewed pool registry. A contract implementing the expected venue ABI can therefore execute arbitrary code during the hop, including `token.transfer(victim, attacker, amount)` for an unrelated token held by the victim. [9](#0-8) 

The focused test demonstrates the auth behavior: simulation records the rogue wallet transfer beneath the victim's `swap_collateral` authorization, and enforcing mode succeeds when the simulated tree containing that child is signed. [10](#0-9) [11](#0-10) 

### Impact Explanation
An attacker can drain arbitrary tokens from a victim's wallet, not merely obtain poor execution on the collateral being swapped. [12](#0-11) 

The malicious venue can also return the expected output token to the router, allowing the controller's positive-output measurement, final collateral accounting, and risk gates to pass while the unrelated wallet transfer remains part of the successful transaction. [13](#0-12) [14](#0-13) 

This is theft of user funds reachable through `swap_collateral`; the same externally supplied route mechanism also feeds `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [15](#0-14) [16](#0-15) 

### Likelihood Explanation
The attacker only needs to supply or arrange a route containing a malicious venue address and induce the victim to submit that route. [17](#0-16) 

The attack does not require a compromised router, leaked key, incorrect market parameter, oracle manipulation, or control of the victim's lending account; the attacker-controlled contract is reached through a syntactically valid swap hop. [18](#0-17) [19](#0-18) 

The remaining prerequisite is that the victim's simulation/signing flow accepts the additional child authorization. The regression test explicitly demonstrates that a signed poisoned tree executes the rogue transfer, while an unsigned child is rejected. [20](#0-19) 

### Recommendation
Do not allow route bytes to select arbitrary venue contracts. Governance should maintain an immutable, reviewed venue/pool registry, and route decoding or dispatch should reject any pool address absent from that registry. [1](#0-0) 

In addition, controller/router integrations should expose the complete expected authorization tree for client-side validation. Clients must reject any signed child authorization other than the exact protocol transfer or venue pull required by the route; documentation alone is not a protocol-level mitigation because the malicious child is valid once signed. [10](#0-9) 

### Proof of Concept
1. The victim owns a lending account with USDC collateral and separately holds an unlisted token `W`. [21](#0-20) 
2. The attacker deploys a contract implementing the selected venue's pool ABI. Inside its swap callback it calls `W.transfer(victim, attacker, victim_balance)`, consumes/pulls the routed input as required, and transfers a sufficient amount of `token_out` back to the router. [9](#0-8) 
3. The attacker constructs a `StrategyPayload` whose address registry contains the malicious pool, input token, and output token; its instruction selects the venue and indexes those registry entries. [6](#0-5) [22](#0-21) 
4. The victim invokes `swap_collateral(caller=victim, account_id, current=usdc_market, amount, new=eth_market, swap=payload)`. [3](#0-2) 
5. Simulation records `W.transfer(victim, attacker, victim_balance)` as a child of the victim's `swap_collateral` authorization. If that generated tree is signed, the malicious transfer and the economically valid swap execute atomically. [2](#0-1) 
6. The regression test verifies the result: the victim's unrelated wallet-token balance becomes zero, the attacker receives that balance, and the victim's account receives the expected swapped collateral. [14](#0-13) [11](#0-10)
