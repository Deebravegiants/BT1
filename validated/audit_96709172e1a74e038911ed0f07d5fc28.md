Based on my investigation, I found a strong analog to the JalaPair unbounded-accumulator overflow pattern in the `VWAPOracle` contract, which tracks cumulative fill spreads for the IntentGatewayV2 protocol.

### Title
Unbounded cumulative spread accumulator in `VWAPOracle` can be driven to overflow, permanently reverting `recordSpread` for a token pair - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle._updateCumulativeSpread` accumulates `weightedSpreadSum` (`int256`) and `totalVolume` (`uint256`) on every call to `recordSpread`, with no cap and no `unchecked` block, exactly mirroring the JalaPair `price0CumulativeLast`/`price1CumulativeLast` accumulator pattern flagged in the referenced Sherlock finding. Unlike JalaPair, where overflow only occurs after ~82–132 years of real elapsed time, this accumulator can be pushed toward `int256`/`uint256` limits by a small number of attacker-controlled fills, because the per-fill contribution (`spreadBps * inputAmountNormalized`) is unbounded by the caller.

### Finding Description
`recordSpread` is called (restricted to `_intentGateway`) once per token, per fill, from the `IntentGatewayV2` order-filling flow — a path reachable by any unprivileged solver who fills an order: [1](#0-0) 

The spread computation is unbounded: `spreadBps` is derived from `(outputAmountNormalized - inputAmountNormalized) * 10_000 / inputAmountNormalized` with no clamping, and `weightedSpread = spreadBps * inputAmountNormalized`: [2](#0-1) 

The accumulation itself uses plain (checked, Solidity ^0.8.24) arithmetic with no bounds: [3](#0-2) 

A solver fills its own order with a minimal input amount and a very large output amount (e.g., using a flash-loaned or self-supplied token balance for a single block) to produce an outsized `amountDiff`, and repeats this a handful of times for the same `(sourceChain, inputToken)` pair. Each repetition adds a large positive term to `weightedSpreadSum`/`totalVolume`. Once either accumulator approaches `type(int256).max` / `type(uint256).max`, the next `+=` reverts under Solidity 0.8's checked arithmetic — permanently reverting every future `recordSpread` call for that pair, exactly as JalaPair's `_update` permanently reverts once `timeElapsed`/cumulative price additions overflow.

### Impact Explanation
If the gateway's fill path does not tolerate a revert from the price-oracle call (the `IIntentPriceOracle` interface exposes no bounded/try-catch semantics visible in the codebase, and `recordSpread` has no return value to signal partial failure), a reverting `recordSpread` call would revert the entire `fillOrder` transaction for that token, permanently DoSing fills for that `(sourceChain, token)` pair. Orders already escrowed for that pair, and any new ones, would become unfillable, mirroring the JalaPair impact class of "core functionality broken, funds locked."

### Likelihood Explanation
This is more likely to be triggered than the original JalaPair bug, since the JalaPair overflow requires ~82+ years of real elapsed time regardless of user action, while here the overflow is a function of attacker-chosen fill amounts and can, in principle, be forced within a bounded number of transactions by an unprivileged filler. However, I was unable to confirm within the available tool calls whether `IntentGatewayV2`'s fill path wraps the `recordSpread` external call in a `try/catch` (which would downgrade this to a broken-oracle issue rather than a fill-blocking DoS) — the direct call site in `evm/src/apps/IntentGatewayV2.sol` was not retrieved before tool budget was exhausted. This is the key unresolved uncertainty for classifying this as Medium (oracle-only breakage) vs. higher severity (fill-path DoS/fund freeze).

### Recommendation
- Cap `spreadBps` (and thus `weightedSpread`) to a sane bound (e.g., ±10x BPS_DENOMINATOR) before accumulating.
- Periodically decay or reset `CumulativeSpreadData` (e.g., rolling window) instead of an unbounded lifetime accumulator.
- Wrap the `recordSpread` call site in `IntentGatewayV2` in a `try/catch` so a reverting price-oracle call never blocks `fillOrder`, consistent with the oracle being an auxiliary analytics component rather than a critical-path dependency.

### Proof of Concept
1. Attacker places an order with `inputToken = X`, `inputs[i].amount = 1` (minimal), and self-fills it (or colludes with the filler) providing `outputs[i].amount` as large as their (possibly flash-loaned) balance allows.
2. `recordSpread` is invoked with this input/output pair; `amountDiff` is huge, producing a large `spreadBps` and `weightedSpread`.
3. Repeat step 1–2 a bounded number of times for the same `(sourceChainHash, inputToken)` key until `data.weightedSpreadSum` or `data.totalVolume` is within one more accumulation of overflowing.
4. The next `recordSpread` call for that pair reverts on the `+=` in `_updateCumulativeSpread`, permanently breaking spread tracking (and potentially `fillOrder`, pending confirmation of call-site error handling) for that token pair. [4](#0-3)

```text
    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }
```

```text
    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;
        data.totalVolume += volume;
        data.fillCount += 1;
        data.lastUpdate = block.timestamp;
    }
```
