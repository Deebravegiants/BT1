## Title
Permissionless `Initialize2` Pool Creation Can Be Front-Run To Hijack Pool Seeding And Permanently DoS The Legitimate Creator - (File: `program/src/processor.rs`)

## Summary
`process_initialize2` derives every account that identifies a pool — `amm_info`, the LP mint, the coin/pc vaults, and `target_orders` — as PDAs seeded solely by the public `market_info.key` and fixed associated-seed constants, with no binding to `user_wallet_info` (the transaction submitter) or any other value the submitter controls. Because the OpenBook `market` account, `coin_mint`, and `pc_mint` for a given pool are public knowledge as soon as a `Initialize2` transaction appears in the mempool, an attacker can front-run it with their own `Initialize2` for the same market, seize the deterministic accounts first, dictate the initial coin/pc ratio (i.e., the initial pool price), and cause the legitimate creator's transaction to permanently revert.

## Finding Description
The accounts that make a pool unique are generated via `generate_amm_associated_account` / `generate_amm_associated_spl_token`, whose addresses are computed with `get_associated_address_and_bump_seed`: [1](#0-0) 

using `market_address` (i.e. `market_info.key`) plus a fixed constant such as `AMM_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED` — never `user_wallet_info.key`: [2](#0-1) 

`process_initialize2` calls these helpers in sequence for `target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, and the `amm_info` account itself, all keyed by the same `market_info`: [3](#0-2) 

Inside `generate_amm_associated_account`, if the derived address is already owned by something other than the system program, the call fails with `AmmError::RepeatCreateAmm` instead of allowing initialization to proceed: [4](#0-3) 

The instruction has no check restricting who may call `Initialize2` for a given market — any signer (`user_wallet_info.is_signer`) can supply `init_coin_amount`/`init_pc_amount` of their own choosing and become the account that funds the vaults and receives the initial LP tokens: [5](#0-4) [6](#0-5) 

This is the same bug class as the referenced report: a "salt" (here, the market pubkey) used to derive the unique deployment/init address is public and not bound to the submitter, so anyone can observe a pending `Initialize2` transaction in the mempool and resubmit an equivalent one with a higher fee, using their own `init_coin_amount`/`init_pc_amount` and `user_token_lp`. Because the accounts are PDAs (not fresh keypairs the original submitter controls exclusively), the attacker's transaction can land first, permanently claiming the pool's identity for that market. The legitimate creator's original transaction then reverts with `AmmError::RepeatCreateAmm` when it tries to re-create the same PDA accounts.

## Impact Explanation
Two consequences compound this into more than a pure griefing DoS:
1. **Denial of Service**: Once an attacker's `Initialize2` lands, the deterministic PDAs (`amm_info`, `lp_mint`, vaults, `target_orders`) for that specific market are permanently occupied, so the legitimate creator's transaction always fails and no alternate pool can ever be created for that market/program pair.
2. **Initial price/LP capture**: The attacker chooses `init_coin_amount` and `init_pc_amount`, which set the pool's starting price ratio, and receives the corresponding initial LP mint (`user_lp_amount`) themselves, effectively hijacking the pool creation intended by the legitimate party and controlling the pool's seeded state and initial liquidity ownership.

This qualifies as Medium severity: it does not directly drain existing user funds, but it permanently blocks legitimate pool creation for a targeted market and lets an attacker dictate a pool's initial economic parameters/liquidity ownership instead of the intended creator.

## Likelihood Explanation
`Initialize2` is a fully permissionless, unprivileged instruction reachable by any signer with a single transaction, and the market/mint public keys used as PDA seeds are visible in the mempool before confirmation, so the front-run only requires normal transaction replacement/priority-fee competition — no special access or off-chain secrets are needed.

## Recommendation
Bind the derived pool accounts (or at minimum an initialization nonce) to `user_wallet_info.key` (or another value the original submitter alone controls) rather than solely to the public `market_info.key`, e.g. by including `user_wallet_info.key` in the seed set passed to `get_associated_address_and_bump_seed`/`find_program_address`, or by requiring the AMM account to be a client-supplied keypair signer instead of a PDA derived from public market data. This prevents an observer from reproducing the exact account set needed to preempt a specific creator's `Initialize2` transaction.

## Proof of Concept
1. Alice broadcasts `Initialize2` for `market M`, `coin_mint C`, `pc_mint P`, intending a balanced initial price, with her wallet as `user_wallet_info`.
2. Mallory observes this pending transaction (or independently decides to front-run any pool creation for `M`), and computes the same PDAs via `find_program_address(&[program_id, M, <ASSOCIATED_SEED>])` for `amm_info`, `lp_mint`, `coin_vault`, `pc_vault`, `target_orders` — identical to what Alice's transaction will derive, per `get_associated_address_and_bump_seed` (`program/src/processor.rs:112-126`).
3. Mallory submits her own `Initialize2` for the same `market M` with a higher priority fee, using her own `user_wallet_info`, and arbitrary `init_coin_amount`/`init_pc_amount` skewed to a price favorable to her, and her own `user_token_lp` destination.
4. Mallory's transaction lands first: `generate_amm_associated_account`/`generate_amm_associated_spl_token` succeed (accounts previously owned by system program), vaults are funded from Mallory's tokens, and she receives the initial LP tokens (`program/src/processor.rs:747-841`, `897-929`).
5. Alice's transaction is then processed: `generate_amm_associated_account` now sees the target PDA owned by the AMM program (not system program) and returns `AmmError::RepeatCreateAmm` (`program/src/processor.rs:541-544`), permanently failing Alice's attempt to create a pool for market `M`.
