### Title
POA Bridge withdrawal status/hash misattribution across batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`describeWithdrawal`/`waitForWithdrawalCompletion` resolve the completion status and destination `txHash` for a specific withdrawal (identified by NEAR tx hash + `index`) by matching the POA Bridge API response purely on `assetId` (`near_token_id`), never on `index`, amount, or destination address. When a single NEAR transaction contains multiple withdrawal intents for the same underlying token (a supported batch-withdrawal pattern in this SDK), the lookup can return the wrong withdrawal record — reporting one withdrawal's `txHash`/status for a different one.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 409-427) and the duplicate implementation in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (lines 135-153) both select from the API's `withdrawals` array using only:
```
withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId)
```
`describeWithdrawal` (poa-bridge.ts, lines 313-343) calls this without ever using `args.index` to disambiguate, even though `WithdrawalIdentifier` carries an `index` field explicitly meant to distinguish multiple withdrawals originating from the same NEAR transaction (see `createWithdrawalIdentifier`, lines 295-311, and `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts`, lines 80-107, which assigns per-route indexes for exactly this purpose).

The code comment itself acknowledges the gap: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." That comment frames it as a known API limitation, but the SDK does not guard against or reject this case — it silently returns whatever same-asset withdrawal record the API lists first, for every index/consumer querying that NEAR tx hash. If a caller submits a batch withdrawal with two legs of the same POA-bridged asset (e.g., splitting a refund to two different destination addresses in one intent), both `describeWithdrawal(index: 0)` and `describeWithdrawal(index: 1)` resolve to the same matched record — whichever leg happens first in the API's array — so one leg's `completed`/`txHash` is reported for the other leg.

### Impact Explanation
This breaks the equality "status/hash reported == the on-chain outcome for *that* withdrawal leg." An integrator polling per-index withdrawal status (as the SDK's batch APIs `createWithdrawalCompletionPromises`/`describeWithdrawal` encourage, per `docs/design/rfc-batch-withdrawal-granular-control.md`) can be told leg B is `completed` with leg A's destination `txHash`, while leg B is actually still pending or went to a different destination address/amount. This matches the "status or hash misreport making an integrator credit or refund twice" impact class: an integrator could credit a user for a withdrawal that hasn't actually landed at the claimed destination, or double-credit two legs against a single on-chain transfer.

### Likelihood Explanation
Requires no privileged access — only that the SDK user (or any actor invoking `createWithdrawalIntents`/batch withdrawal flow) submits two POA-bridge withdrawals of the same underlying NEP-141 asset within a single NEAR transaction (e.g., two destination addresses receiving the same token). Both the SDK's bridge-selection code and RFC docs acknowledge batch/multi-leg withdrawals as a supported feature, and nothing in `validateWithdrawal` or the withdrawal-construction path rejects duplicate-asset legs in the same batch, so the precondition is realistically reachable through normal SDK usage, not through the POA Bridge operator or relayer acting maliciously.

### Recommendation
Disambiguate by more than `assetId`: use `index` together with amount/destination-address matching (or, as the existing code comment suggests, sort both the API results and the requested `withdrawalParams` by amount to preserve relative ordering) in `findMatchingWithdrawal` in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`. At minimum, until the POA Bridge API supports per-leg identifiers, the SDK should detect same-asset multi-leg batches at withdrawal-construction time and either reject them or clearly document/throw rather than silently risk cross-attributing status/hash between legs.

### Proof of Concept
1. Build and sign a single NEAR intents transaction containing two POA-bridge `ft_withdraw` legs for the same asset, e.g. `nep141:usdt.omft.near`, amount 100 to address `X`, and amount 200 to address `Y` (both valid POA destinations).
2. Call `bridge.createWithdrawalIdentifier` for each leg, giving `index: 0` and `index: 1` respectively, both referencing the same `tx.hash`.
3. After the POA relayer processes only leg 0 (to `X`), call `bridge.describeWithdrawal({ ...leg0Wid })` and `bridge.describeWithdrawal({ ...leg1Wid })`.
4. Because `findMatchingWithdrawal` matches solely on `nep141:usdt.omft.near`, both calls resolve to the same completed record for leg 0, so `describeWithdrawal` for `index: 1` (which is still unprocessed/going to `Y`) incorrectly reports `{ status: "completed", txHash: <leg-0's tx hash to X> }`. 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
