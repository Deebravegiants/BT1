This confirms the vulnerability class. The gem's own documentation explicitly states: "This will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`) and presents `data.shop` as a trusted field for the handler to act on [1](#0-0) , yet `shop` is derived from an unauthenticated HTTP header while the HMAC only covers the raw body.This confirms the design fully: `VerifiableQuery#to_signable_string` is the only value covered by HMAC comparison in `Utils::HmacValidator.validate_signature` [2](#0-1) , and for webhooks that signable string is exactly `@raw_body` [3](#0-2) . The `shop`, `topic`, and `webhook_id` fields are read straight from attacker-controllable HTTP headers [4](#0-3)  and are never included in the signed content, yet `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata` after only checking the body's HMAC [5](#0-4) . The docs explicitly promise the processed data—including `shop`—can be trusted as verified Shopify origin data [1](#0-0)  and demonstrate host apps keying business logic directly off `data.shop` [6](#0-5) .

### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are pulled from unsigned HTTP headers. `Utils::HmacValidator.validate` checks nothing but the body's HMAC. This breaks the equality the gem is supposed to guarantee: `shop authenticated by HMAC == shop delivered to the handler`. An attacker who can obtain one valid (body, HMAC) pair signed with the app's shared `client_secret` — e.g. by being a legitimately installed merchant on their own store, or by replaying/observing any previously delivered webhook for any shop using the app — can resend that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with any victim shop's domain. `HmacValidator.validate` still passes because it only recomputes the HMAC over the untouched body, and `Registry.process` hands the forged `shop` value straight to the app's `WebhookHandler` as `WebhookMetadata#shop`.

### Finding Description
- `Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC header [2](#0-1) .
- For webhook requests, `to_signable_string` returns `@raw_body` exclusively [3](#0-2) ; `shop`, `topic`, and `webhook_id` are read from headers that are never mixed into the signed string [4](#0-3) .
- `Registry.process` only calls `Utils::HmacValidator.validate(request)` before trusting `request.shop`, `request.topic`, and `request.webhook_id` and forwarding them into `WebhookMetadata` passed to the app's handler [5](#0-4) .
- Because the HMAC secret (`client_secret`) is shared across every shop that installs the app, any shop with a legitimate install can generate/observe a validly-signed `(body, hmac)` pair for its own webhooks, then reuse that pair against the same endpoint with a different `shop-domain` header, since nothing in the signed content depends on which shop the request claims to originate from.
- The gem's own documentation instructs app developers to trust `data.shop` for tenant-scoped decisions immediately after `Registry.process` runs [7](#0-6) , so this is not a case of the host app ignoring documented behavior — the gem's documented contract itself is the source of the trust that gets broken.

### Impact Explanation
This is a Critical cross-tenant access issue: an unprivileged attacker who merely has a legitimate installation of the target app on their own (attacker-controlled) shop can forge webhook deliveries that the app will process as belonging to any other shop using that same app, without ever needing the app's `client_secret`, an access token, or any other privileged credential. Depending on how the host application's handler uses `data.shop` (e.g. to look up which merchant record to update, which access token/session to use, or which tenant's data to write), this can lead to cross-tenant data corruption or unauthorized actions performed against a victim merchant's store record.

### Likelihood Explanation
Likelihood is elevated because: (1) the attacker only needs to be any merchant who has installed the target app (a normal, unprivileged action), (2) capturing a valid `(body, hmac)` pair requires no cryptographic attack — it's simply replaying an authentic delivery aimed at their own shop, and (3) the webhook processing endpoint is, by design, a public HTTP endpoint intended to receive unauthenticated internet traffic (from "Shopify"), so nothing prevents a direct forged POST from any client.

### Recommendation
Bind the shop, topic, and webhook id into the value that is HMAC-verified (or otherwise independently verify that the `shop-domain` header corresponds to a shop actually known/authorized to receive that specific `webhook_id`/body), rather than trusting header values verified by nothing but the raw body's HMAC. At minimum, document prominently that `data.shop`, `data.topic`, and `data.webhook_id` are NOT covered by the HMAC check and must be independently cross-checked (e.g. against the shop that legitimately owns the session/install) before being used for tenant-scoped decisions.

### Proof of Concept
1. App "Acme" is installed by attacker's shop `attacker.myshopify.com` and by victim's shop `victim.myshopify.com`, sharing the same `client_secret`.
2. Shopify delivers a legitimate webhook to Acme's endpoint for the attacker's shop:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>

   {"id": 1, "note": "malicious payload chosen by attacker via their own store actions"}
   ```
3. Attacker captures this exact `body` + `x-shopify-hmac-sha256` value (they control their own shop's webhook traffic/proxy).
4. Attacker sends a new POST to the same endpoint with the identical body and HMAC header, but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate(request)` recomputes the HMAC over the unchanged body and it matches, so validation passes [8](#0-7) .
6. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the app processes attacker-chosen data as though it came from the victim's store.
