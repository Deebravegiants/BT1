### Title
Missing Chainlink L2 sequencer-uptime check in SimplexPaymaster oracle pricing allows mispriced gas payments during/after sequencer downtime - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using raw Chainlink `latestRoundData()` answers with only a staleness (`maxOracleAge`) and positivity check, and no check of the Chainlink L2 sequencer-uptime feed. The paymaster is documented as "live on Ethereum, Arbitrum, Base, Polygon and BSC," so on the L2s (Arbitrum, Base) a sequencer outage can leave stale, out-of-market prices inside the `maxOracleAge` window (up to 24h per the code's own comment), letting any UserOp submitter (an unprivileged solver/user paying gas via the paymaster) prefund or get charged at a stale exchange rate.

### Finding Description
`_getOraclePrice` only rejects non-positive answers and answers older than `maxOracleAge`; it never queries a sequencer-uptime feed: [1](#0-0) 

This function backs both the per-UserOp pricing path (`_tokenPrice` → `_fetchDetails`, used in ERC-4337 validation on every sponsored UserOp) and the treasury's `swapAndDeposit` fee-recycling swap: [2](#0-1) [3](#0-2) 

`maxOracleAge` is governance-configured but permitted up to 7 days, and the code's own comment on `Params` says real-world heartbeats "vary per chain... up to 24h" for some stablecoin feeds: [4](#0-3) 

The contract is deployed on Arbitrum and Base per the project's own documentation, both of which use a centralized sequencer whose Chainlink feeds can return stale prices for an extended period during sequencer downtime (per Chainlink's L2-sequencer-feed guidance referenced in the source report): [5](#0-4) 

No `.sol` file in the repository references a sequencer-uptime feed or grace period at all, confirming the check is absent everywhere Chainlink is consumed on-chain.

### Impact Explanation
`_tokenPrice`/`_getOraclePrice` gate the exchange rate (native gas cost ⇄ ERC-20 token) charged to every sponsored UserOp. During a sequencer outage on Arbitrum/Base, or immediately after recovery, `latestRoundData()` can return an answer that is well within `maxOracleAge` but no longer reflects the real market price (Chainlink explicitly warns of this window). An unprivileged UserOp sender (any solver or user routed through the permissionless paymaster) can submit operations priced off that stale answer to:
- Pay the paymaster far less token value than the true gas cost, draining the paymaster's EntryPoint-staked native deposit and treasury-held tokens (theft of protocol funds), or
- Force `swapAndDeposit`'s oracle-derived `amountOutMin` calculation to also use the same stale price, degrading the treasury's fee-recycling swap execution price.

This is a direct, permissionless, financially exploitable mispricing of a governance-held treasury/paymaster balance — a concrete theft-of-funds vector, matching High severity.

### Likelihood Explanation
Likelihood depends on an L2 sequencer downtime event (Arbitrum/Base have each had multi-hour to multi-day outages historically) combined with price movement during that window, or exploitation of the recovery grace period Chainlink explicitly warns about. This is a known, recurring operational risk for L2-deployed price-consuming contracts, not a purely theoretical scenario, and requires no privileged access — only a normal UserOp submission through the already-permissionless paymaster.

### Recommendation
Add Chainlink's `SequencerUptimeFeed` check (per-chain, e.g. Arbitrum's `0xFdB631F5EE196F0ed6FAa767959853A9F219A63`, Base as applicable) in `_getOraclePrice`, reverting or falling back to a safe minimum/maximum price if the sequencer is currently down or within the recommended `GRACE_PERIOD_TIME` (e.g. 3600s) after it comes back up, following Chainlink's documented `L2-sequencer-feeds` example.

### Proof of Concept
1. On an L2 deployment of `SimplexPaymaster` (e.g. Arbitrum), the sequencer goes down for several hours while ETH/USD or the token/USD price moves materially on L1/other venues.
2. Chainlink's L2 aggregator continues to serve its last-cached `latestRoundData()`; `updatedAt` may lag but remain within `maxOracleAge` (configurable up to 7 days, with realistic heartbeats up to 24h per the code comment), so `_getOraclePrice` at `evm/src/utils/SimplexPaymaster.sol:662-676` does not revert.
3. Once the sequencer resumes accepting transactions (or during the outage if soft-forwarded), an attacker submits a UserOperation with `paymasterData` selecting a supported token, going through `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` at lines 524-556 and 653-676.
4. The paymaster charges/prefunds the attacker's token based on the stale price, letting them underpay for the native gas the paymaster fronts via the EntryPoint deposit, draining paymaster/treasury funds at the expense of correct pricing — with no check ever consulted for sequencer health.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
