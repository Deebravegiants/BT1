### Title
Fee-on-transfer tokens are not accounted for in `IntentGatewayV2.placeOrder()` on the Tron deployment, causing escrow insolvency - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits the escrow mapping `_orders[commitment][token]` with the nominal, fee-reduced input amount computed from the user-supplied `order.inputs[i].amount`, without ever verifying how many tokens the contract actually received via `safeTransferFrom`/sweep. For fee-on-transfer (or any deflationary/rebasing) ERC20 tokens, the contract's real balance will be lower than what is recorded in escrow, exactly the class of bug described in the Connext report where `dx` was overwritten with actual `balanceOf` deltas everywhere except in `swap()`.

### Finding Description
In the non-predispatch path of `placeOrder()`, the contract pulls tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally books `reducedInputs[i].amount` (derived from the pre-transfer `order.inputs[i].amount`) into escrow: [1](#0-0) 

In the predispatch path, dust accounting is based on the dispatcher's pre-sweep balance (`balance = IERC20(token).balanceOf(dispatcher)`), but the amount actually landing in `address(this)` after the sweep `transferCalls` execute is never measured; escrow is still credited with `reducedInputs[i].amount`: [2](#0-1) 

This is in stark contrast to the main EVM `IntentGatewayV2.sol`, which was hardened specifically against this bug class: it snapshots balances before/after every transfer and mutates `order.inputs[i].amount` to the *actually received* amount before computing the commitment and crediting escrow, for both the simple path: [3](#0-2) 

and the predispatch/sweep path: [4](#0-3) 

The dedicated fee-on-transfer regression tests in the foundry suite confirm this is a recognized and fixed bug class on the main EVM implementation, but the fix was not carried over to the Tron contract: [5](#0-4) 

### Impact Explanation
Any user placing an order with a fee-on-transfer token on the Tron `IntentGatewayV2` will cause the contract to record more tokens in `_orders[commitment][token]` than it actually holds. Since escrow balances are the accounting source of truth for `fillOrder`/withdrawal, this creates an under-collateralized state: the sum of recorded liabilities across orders exceeds the real token balance held by the contract. The first solver(s) to fill/withdraw against inflated escrow entries will succeed, draining real balance out of proportion, leaving later legitimate order fills or cancellations unable to be paid — a permanent freezing/loss of funds for other users of the same token, and a systemic insolvency of the escrow accounting for any fee-on-transfer or rebasing token routed through this deployment.

### Likelihood Explanation
Likelihood is high for any deployment configured with a fee-on-transfer token, since triggering the bug requires nothing more than a single unprivileged `placeOrder()` call with such a token — no special permissions, timing, or governance actions are needed. The bug is deterministic and reproducible on every order placed with a deflationary token.

### Recommendation
Apply the same fix used in the main EVM `IntentGatewayV2.placeOrder()`: measure the actual token balance delta on `address(this)` (and on the dispatcher for the predispatch sweep) before and after each transfer, and use that measured amount — not the nominal `order.inputs[i].amount` — both when computing the commitment hash and when crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a token that charges a 1% fee on transfer (e.g., the `FeeOnTransferToken` mock used in the EVM tests).
2. User calls `placeOrder()` with `order.inputs[0].amount = 1000e18`. The contract calls `safeTransferFrom(msg.sender, address(this), 1000e18)`, but due to the 1% fee only `990e18` actually lands in the contract.
3. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` computed from `1000e18` (e.g. `1000e18` minus protocol fee, but not minus the transfer fee) — i.e., escrow records ~1000e18-equivalent while the contract only holds `990e18`.
4. A solver fills the order and the withdrawal path pays out the escrowed amount recorded (~1000e18-equivalent) from the contract's real balance, which only has `990e18` for this token pool; the shortfall is either taken from other users' escrowed balances of the same token or causes reverts/freezing for subsequent legitimate withdrawals once the token balance is exhausted.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
