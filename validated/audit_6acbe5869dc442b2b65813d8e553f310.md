### Title
Webhook shop identity spoofing via unauthenticated `Shop-Domain` header not covered by HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `Request#shop` is read from an HTTP header that is never included in the signed material. `Registry.process` accepts the request once the body-only HMAC passes, then passes the untrusted header value as the shop identity to the host application's handler. This breaks the intended binding `hmac_verified_bytes == shop_used_for_dispatch`.

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; `shop` is read directly from the `shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string. `HmacValidator.validate` computes the HMAC purely over `to_signable_string`: [3](#0-2) 

`Registry.process` then trusts the unauthenticated `request.shop` and hands it straight to the app-supplied `WebhookHandler`: [4](#0-3) [5](#0-4) 

Because the HMAC only proves the integrity of the request body, not of the shop-domain header, a request with a *valid* HMAC (obtained from any real webhook the attacker legitimately received for their own shop) can have its `Shop-Domain` header value swapped to any other shop and will still pass `Registry.process`'s HMAC check. The equality that is supposed to hold — "the shop that produced HMAC-verifiable bytes" == "the shop attributed to the resulting `WebhookMetadata`" — does not, because the HMAC verifies bytes disjoint from the shop field. This is the exact bug class cited in the report: a field that is acted upon (`shop`, used for dispatch/tenant attribution) but not covered by the authenticity check (HMAC over `raw_body` only).

By contrast, the OAuth callback's `AuthQuery#to_signable_string` does include `shop` in the signed parameters, so that path is not affected: [6](#0-5) 

### Impact Explanation
Any unprivileged party who can install the app on a shop they control (a normal, unprivileged onboarding action) will legitimately receive real webhooks with a valid `x-shopify-hmac-sha256` value for their own shop's traffic. By replaying the identical raw body with the `Shop-Domain` header changed to a victim shop, the attacker can make the host application process (and dispatch to per-tenant business logic/storage) data while the gem reports it as belonging to a different, victim tenant — a cross-tenant identity-spoofing condition rooted in this gem's own `Request`/`Registry` code, independent of how carefully the host app implements its handler.

### Likelihood Explanation
Webhook endpoints are typically public HTTP endpoints, and obtaining at least one HMAC-body pair is trivial for anyone who installs the app on their own store (no `api_secret_key`, access token, or privileged access is required). Because the gem's own `Request#to_signable_string` never signs the shop-domain header, exploitation only requires standard HTTP tooling to alter one header while replaying the untouched body/HMAC pair.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the shop-domain header to the signed body before `Registry.process` uses `request.shop` for dispatch, so verified bytes and the shop identity used downstream cannot diverge.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook POST, including its raw body and the valid `x-shopify-hmac-sha256` value computed by Shopify for that body.
2. Replay the exact same raw body and HMAC header, but change `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-supplied header value `victim.myshopify.com`, and the app's handler executes tenant-scoped logic under the spoofed shop identity.
