### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery solely by validating the HMAC over the raw request body, but the `shop` value used to route and attribute the event to a specific merchant tenant is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed bytes. Anyone who can present a previously-observed valid `(raw_body, hmac)` pair to the app's public webhook endpoint can attach an arbitrary `shop-domain` header and have the payload processed as if it belongs to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is a separate accessor pulled straight from headers, entirely outside the HMAC-covered data: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` to build the `WebhookMetadata` that is handed to the application's handler: [4](#0-3) 

The identity binding that should hold is:
`hmac_verified_bytes == bytes_that_determine_the_tenant("shop")`

In this code the equality does not hold: `hmac_verified_bytes = raw_body` while `tenant = headers["shopify-shop-domain"]`. The `shop` field is "a field acted on but not covered by the HMAC" — the same bug class as the `toBlock` value in the referenced report being acted upon (`lastBlockRewarded = toBlock`) without being bound/checked against the value that was actually validated (`fromBlock`/sequence invariant).

### Impact Explanation
Because the shop header is unauthenticated, any request bearing a valid `(raw_body, hmac)` pair — regardless of where it originally came from — will be accepted and dispatched to the handler with an attacker-chosen `shop` value. Host applications built on this gem commonly key their tenant records (order records, inventory, install status, etc.) off `WebhookMetadata#shop`, so this allows cross-tenant event injection/attribution: data legitimately generated for shop A can be delivered to the application as though it belongs to shop B. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation does not require the app's `client_secret`/`api_secret_key`: the attacker only needs to obtain one legitimate `(raw_body, hmac)` pair that Shopify sent for any shop (e.g. from an app they install themselves and whose outgoing webhook traffic to the app's public endpoint they can observe/capture), then resend that exact body and HMAC value to the app's webhook endpoint with a different `shopify-shop-domain` header. No TLS interception, credential theft, or privileged account is required — this is achievable by any unprivileged internet user who is also a merchant/app-installer able to see their own webhook traffic to a shared public endpoint. Likelihood is Medium: it requires the attacker to capture at least one genuine webhook delivery, but nothing more privileged than that.

### Recommendation
Include the shop-identifying header (and other Shopify-sent identity headers used to route/attribute the event, e.g. `X-Shopify-Shop-Domain`, `X-Shopify-Webhook-Id`) in the HMAC-signed data, or otherwise cryptographically bind them (e.g. re-verify `shop` against a signed claim, or require applications to independently confirm the `shop` corresponds to a shop with an active token/installation) before trusting `request.shop`. At minimum, document and enforce that `shop` must be treated as untrusted unless separately corroborated (e.g. against known installed shops), and consider signing the header set explicitly as Shopify does elsewhere (e.g. JWT `aud`/`dest` claims, OAuth callback HMAC which does cover `shop`, see `lib/shopify_api/auth/oauth/auth_query.rb`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`. Shopify sends a legitimate webhook to the app's public endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over BODY>
   x-shopify-shop-domain: attacker.myshopify.com
   BODY: {"id": 1, ...}
   ```
2. Attacker captures this exact `BODY` and `x-shopify-hmac-sha256` value (they control network visibility into their own webhook delivery, e.g. via a shared multi-tenant webhook path or logging they can access).
3. Attacker replays the identical request to the same endpoint but swaps the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(..., @raw_body)` — see `lib/shopify_api/utils/hmac_validator.rb` and `Request#to_signable_string` above — so validation succeeds since `BODY` is unchanged.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process/attribute the order data under the wrong tenant.
