## Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, allowing a captured webhook to be replayed against a different tenant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable payload from the raw request body only. The `shop-domain`, `topic`, `webhook-id` and `api-version` HTTP headers are read directly from unauthenticated request headers and are never included in the signed material. `Registry.process` trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler, after validating only that the *body* bytes match the HMAC. This breaks the identity binding: `shop verified-by-HMAC` ≠ `shop used-by-handler`.

### Finding Description
`Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are parsed straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only verify the HMAC of `verifiable_query.to_signable_string` (i.e., the raw body) against the `hmac` header — it never checks `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` then constructs `WebhookMetadata` using `request.shop` and `request.topic` directly, right after the HMAC-only check, with no further validation that the shop header corresponds to the tenant that actually produced the signed body: [4](#0-3) 

Because the signature only proves "this exact body byte-string was HMAC'd with the app's secret at some point," and does not bind that body to a particular shop, topic, or webhook id, an unprivileged attacker who can obtain **any** one genuine `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and triggering a webhook, which requires no privileged secrets) can replay that exact body/HMAC pair to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to point at a different, victim shop. `HmacValidator.validate` will still pass (body bytes are unchanged), and the handler will receive `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: data that Shopify genuinely signed for tenant A can be attributed to tenant B purely by header manipulation, with no possession of the app's `client_secret`, access tokens, or any victim credentials. Depending on how the host application's webhook handler uses `shop` (e.g., keying customer/order records, triggering fulfillment, updating per-shop state, invoking authenticated API calls with a session looked up "by shop"), this allows an attacker to inject or spoof data into another merchant's tenant context — a cross-tenant access primitive.

### Likelihood Explanation
High. The only capability required is any interaction that causes the attacker's own store to fire one webhook to the app (installing the app on an attacker-owned store and performing an action like creating an order is normal, unprivileged behavior). No leaked secrets, tokens, or social engineering needed. The webhook endpoint is, by design, an internet-facing HTTP endpoint.

### Recommendation
Bind the identity fields to the signed payload, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified body — e.g., include them in the signable string computed for `Registry.process`, or require the host application to cross-check the header-derived `shop` against the shop associated with a session/webhook subscription that the app itself registered, rather than trusting unauthenticated headers as ground truth for `WebhookMetadata.shop`/`topic`.

### Proof of Concept
1. Attacker installs the app on their own test store `attacker.myshopify.com` and triggers a webhook subscription event (e.g., `orders/create`), capturing the resulting raw POST body and its genuine `X-Shopify-Hmac-Sha256` header — both are legitimately produced by Shopify using the real app secret.
2. Attacker replays the exact same request to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
3. `Registry.process` calls `HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` — unchanged — so validation succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the app's registered handler processes attacker-controlled data as if it came from the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
