## Title
Webhook HMAC covers only the raw body, not the `shop`/`topic`/`webhook_id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` is computed solely over the raw request body. Because the tenant-identifying `shop` field is never part of the signed bytes, an attacker who can obtain one validly-signed webhook (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while swapping the `shop-domain` header to point at a victim shop, causing the app to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from the (attacker-controlled, unauthenticated) HTTP headers via `shopify_header`: [2](#0-1) [3](#0-2) 

`Registry.process` only validates the HMAC (which, per above, covers just the body) and then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The HMAC computation itself only signs the signable string (the body), never any header: [5](#0-4) 

This is the same class of bug as the reported EIP-712 issue: a value that is *acted upon* (here, the `shop` used for tenant identification and dispatch) is not part of the data that is cryptographically bound by the signature. The equality that should hold — `shop-header == shop-bound-by-hmac` — does not, because the HMAC only binds the body bytes.

The gem's own documentation confirms host applications are expected to trust `data.shop` coming out of `Registry.process` as the authenticated tenant identifier: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who owns/operates any Shopify shop that has this app installed (no `api_secret_key` or privileged access needed) can trigger a real webhook event on their own store (e.g. `orders/create`), capture the genuine `raw_body` and the resulting valid HMAC that Shopify sends, and then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain (and optionally the topic/webhook-id headers). `HmacValidator.validate` will still succeed because it only checks the body bytes, and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the victim's domain. Any host application that uses `data.shop` to select the tenant record/session to update (exactly as recommended in the gem's own docs) will apply attacker-controlled data under a different tenant's identity — a cross-tenant confusion/data-injection primitive.

### Likelihood Explanation
Likely reachable in essentially every integration, since `docs/usage/webhooks.md` explicitly instructs developers to trust `data.shop` from `Registry.process` output, and the only gate (`HmacValidator.validate`) never considers the shop/topic/webhook-id headers. The only prerequisite is that the attacker can install the app on a shop they control (a normal, unprivileged flow) and can freely modify HTTP headers of their replayed request.

### Recommendation
Include the tenant-identifying and dispatch-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable bytes (or otherwise verify them independently, e.g. against a value embedded in the signed body, or against the shop associated with the webhook subscription), instead of trusting header values that sit entirely outside the HMAC signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. updates an order) so Shopify sends a legitimately signed webhook:
   - `raw_body = "{...attacker-controlled order json...}"`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
2. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — this still matches, so validation passes: [8](#0-7) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"` even though the body/HMAC pair actually came from the attacker's own shop: [9](#0-8) 
5. The app's handler processes attacker-supplied data as if it belonged to `victim-shop.myshopify.com`, per the documented pattern of trusting `data.shop`.
