### Title
Webhook shop identity not bound to HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, never from the `X-Shopify-Shop-Domain` header. Because the HMAC secret is the app's single `client_secret` (shared across all shops that installed the app), any shop that legitimately receives a validly-signed webhook can replay that exact body while substituting a different `shop-domain` header, and the gem's `HmacValidator` will still report the signature as valid.

### Finding Description
`Utils::HmacValidator.validate` computes `verifiable_query.to_signable_string` and HMAC-compares it against the `hmac` field using the app's `api_secret_key` [5](#0-4) . For webhooks, `to_signable_string` is defined as simply `@raw_body`, i.e. it signs only the JSON body, never any header [1](#0-0) . The `shop` accessor used downstream is taken straight from the `shop-domain` header without any cryptographic binding to the signature: `T.cast(shopify_header("shop-domain"), String)` [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates body-vs-secret, not shop-vs-signature) before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . Because the same `client_secret` is used to sign webhooks for every shop that has installed the app (not a per-shop secret), a webhook body that Shopify legitimately signed and delivered for Shop B's install can be re-POSTed to the app's webhook endpoint with the `shop-domain` header changed to Shop A — the HMAC check still passes because the header is outside the signed string, breaking the identity binding: `shop authenticated by HMAC` should equal `shop trusted for dispatch`, but here the former (body only) is disconnected from the latter (unauthenticated header).

### Impact Explanation
This breaks the cross-tenant boundary the gem is meant to enforce: `Registry.process`/`WebhookMetadata` and any host application logic keyed off `request.shop` (e.g., locating the tenant's stored session/access token, processing `app/uninstalled`, GDPR redaction topics, order/customer webhooks) can be made to act on the wrong shop's identity using a signature that was never issued for that shop-header pairing. Any merchant/shop that can trigger and observe its own legitimate webhook deliveries (trivial — install the app, cause any webhook event) obtains a validly-HMAC'd body they can replay against a different `shop` value, causing the host app to attribute/process the event under an arbitrary victim shop domain.

### Likelihood Explanation
Likelihood is meaningful wherever webhook bodies are generic or shop-domain-independent (many mandatory/GDPR topics and topics with minimal payloads), since the attacker fully controls both the replay and the header value, and needs no secret — only a previously legitimately-signed body for any shop. The main constraint is that the body content itself must not otherwise reveal/require matching shop context in the host app's own logic, which varies by integrator but is not enforced by the gem.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the signed data checked by `HmacValidator`, or require the host application to cross-check `request.shop` against the shop looked up via the resource identifiers embedded in the parsed body, before trusting `request.shop` for session/tenant resolution in `Registry.process`.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com`; the app receives a webhook (e.g., `orders/create`) with body `B` and header `x-shopify-shop-domain: shop-a.myshopify.com`, correctly HMAC-signed with the app's `client_secret`.
2. Attacker (owner of `shop-a`) captures `B` and its `x-shopify-hmac-sha256` value.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and signature, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only (matches, since body unchanged) and returns `true` [1](#0-0) .
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process/attribute the event as belonging to the victim tenant.
