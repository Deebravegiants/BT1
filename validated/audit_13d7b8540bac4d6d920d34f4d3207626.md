### Title
Unbounded `handle_unsigned` batch execution during unsigned mempool validation enables permissionless CPU-exhaustion DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is a permissionless, unsigned call: any network participant can submit an arbitrarily large `Vec<Message>` batch, each entry carrying a full consensus/state proof. Before the transaction is even accepted into the pool or gossiped, `ValidateUnsigned::validate_unsigned` fully executes the entire batch via `Self::execute(messages.clone())` — running every consensus/membership-proof verification in the batch — with no bound on the number of messages, no relation to the static per-call weight, and no charge to the submitter. Because this validation re-runs on every node that receives the transaction (and re-validates it on every new best block for its `longevity` window, with `propagate: true`), an attacker can craft one transaction whose validation cost is disproportionately large relative to its size and force every gossip-connected node to repeatedly perform that expensive verification, degrading or stalling block production and RPC responsiveness — the same "unauthenticated/low-cost request causes disproportionate backend work leading to unresponsiveness" bug class as CVE-2024-47217/CVE-2024-47214.

### Finding Description
`handle_unsigned` is dispatched with `ensure_none(origin)`, i.e. it requires no signature and no fee: [1](#0-0) 

Its declared weight is a flat constant, independent of how many messages the batch contains: [2](#0-1) 

Critically, the `ValidateUnsigned` implementation does not merely check basic shape — it calls the *same* `Self::execute(messages.clone())` that would run on-chain, fully verifying every message's consensus/state proof, during mempool validation (i.e., before the transaction is even included in a block): [3](#0-2) 

`execute()` iterates the whole message vector and, for each `Request`/`Response`, performs full state-machine membership-proof verification (Merkle/trie proofs, storage proofs, etc.) via `handle_incoming_message`: [4](#0-3) 

The pallet's own documentation confirms this design intent — “the transaction pool will check if the submitted extrinsics are valid before they are included... this validity check ensures that the transaction can be successfully executed and contains valid proofs” — but this validity check *is* the full-cost operation, and it is unbounded: [5](#0-4) 

Once validated, the transaction is marked `propagate: true` with `longevity: 25`, so it is gossiped to every peer (each of which independently re-runs the same expensive `validate_unsigned`) and is re-validated on each new best block for up to 25 blocks: [6](#0-5) 

There is no `BoundedVec` limit on `messages: Vec<Message>` size/count at the type level, no per-message proof-size cap enforced before verification begins, and no cost/fee charged for a failed or even a successful-but-unincluded transaction — only the block-inclusion path charges via `FeeHandler`. The only constraint is the runtime's generic max extrinsic/block-length limit, which is large enough to fit many proof-bearing `PostRequest`/`GetRequest` entries or several expensive consensus proofs (e.g. GRANDPA/BEEFY/sync-committee) in one transaction, each of which triggers full cryptographic verification during validation on *every* node that sees the gossiped transaction.

This mirrors CVE-2024-47217's bug class: a reachable endpoint (here, unauthenticated/unsigned by design) that performs disproportionately expensive server-side work relative to the cost of the request, which can render the service unresponsive if repeated or sustained.

### Impact Explanation
An attacker with no stake, no signature, and no fee obligation can submit `handle_unsigned` transactions engineered to maximize verification cost per byte (e.g., many `Request`/`Response` entries each requiring trie-proof verification, or consensus messages requiring expensive cryptographic checks). Because validation happens on every full/collator node that receives the gossiped transaction, and repeats every block for the transaction's 25-block longevity, a modest stream of such transactions can consume significant CPU on the whole network of ISMP-connected nodes, degrading block production, delaying legitimate message delivery, and potentially halting event processing in the pipeline — consistent with the "render the server unresponsive" impact described in the CVE report, and reachable by any relayer/dispatcher without privilege.

### Likelihood Explanation
Likelihood is high: the call requires no signature, no fee, and no special permission (`ensure_none`), is validated with full-cost proof verification prior to any charge or exclusion mechanism, and is explicitly propagated (`propagate: true`) to the whole network. Any single crafted transaction amplifies its cost across every peer that gossips or re-validates it.

### Recommendation
- Bound the number of messages and per-message proof sizes accepted by `handle_unsigned` (e.g., convert `Vec<Message>` handling in `validate_unsigned` to enforce a small, fixed cap before any cryptographic work is attempted).
- Perform cheap, size/format based rejection first (as already done in other pallets like `pallet-call-decompressor`'s `MaxCallSize` gate) before invoking `Self::execute` in `validate_unsigned`.
- Consider scaling declared weight with the actual batch size/message count rather than using the static `weight()` constant, and rate-limit unsigned submissions per peer at the network layer.
- Evaluate whether `validate_unsigned` needs to fully execute proof verification, or whether a lighter/staged validity check (deferring expensive proof verification to block execution, with fees/slashing on failure) can reduce mempool-stage cost.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned { messages }` where `messages` is a large `Vec<Message::Request>` (up to the runtime's max extrinsic size), each `RequestMessage` containing many `PostRequest`/`GetRequest` entries and a proof designed to require maximal trie-node traversal in `verify_membership`/`verify_state_proof` before failing (or succeeding) verification.
2. Submit this as an unsigned transaction to the network (`submit_and_watch` per the pattern used in [7](#0-6) ).
3. Observe that every peer node receiving the gossiped transaction invokes `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())`, fully running proof verification for the whole batch, repeated for the transaction's `longevity` window (25 blocks) on each node — regardless of whether the transaction is ever included in a block.
4. Repeat with a burst of such transactions (varying `signer`/proof bytes to bypass the `provides` dedup tag) to measure aggregate CPU degradation across the network's validating nodes.

```rust
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
