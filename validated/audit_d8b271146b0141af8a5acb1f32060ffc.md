### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw request body only, then trusts the `shop` value taken from the unauthenticated `x-shopify-shop-domain` HTTP header when it builds `WebhookMetadata` and passes it to the app's registered handler. Because the signed bytes (`raw_body`) and the tenant-identifying field (`shop` header) are decoupled, the shop-binding equality the gem is supposed to enforce — `hmac_verified(shop_used_by_handler) == shop_from_verified_bytes` — does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` however is read straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves integrity of `raw_body`) and then immediately trusts `request.shop` when building `WebhookMetadata` for the handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated string field handed to the app's `WebhookHandler#handle`: [4](#0-3) 

`Utils::HmacValidator.validate` only compares `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e., the body — it has no knowledge of, and does not bind, the shop header: [5](#0-4) 

Because Shopify's webhook HMAC secret (`api_secret_key`) is shared across every shop that has the app installed, any merchant with the app installed receives genuine webhook deliveries (valid `raw_body` + valid HMAC) for their own shop. That same person can replay the identical `raw_body`/HMAC pair to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass (it never inspected the header), yet `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop, with the replayed body content. This breaks the identity binding: verified bytes (`raw_body`, signed by the app's shared secret) are not bound to the `shop` value the handler is told to act on.

### Impact Explanation
Applications built on this gem are expected to trust `WebhookMetadata#shop` as the tenant boundary when storing/dispatching data from `handle`. Since this field bypasses the gem's own HMAC check, one merchant/tenant can inject or replay another tenant's webhook payload under an attacker-chosen shop identity. This is a cross-tenant identity-binding break reachable by any user who has legitimately installed the app (an "unprivileged internet user" relative to other merchants' data) — no access to `api_secret_key`, access tokens, or TLS interception is required, since a legitimate merchant naturally receives valid signed bodies for their own webhooks and only needs to change/replay the request header.

### Likelihood Explanation
Any developer using the gem's documented `Webhooks::Registry.process` API and relying on `data.shop` (as the gem's own struct field is named and intended to be used) is exposed; the vulnerable code path is exercised on every processed webhook, and forging the header requires only capturing one's own genuine webhook delivery (trivially available to any app-installing merchant) and re-sending it with an edited header — no cryptographic material needs to be recovered.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signable string bound by the HMAC, or otherwise cryptographically bind the header-derived `shop` to the verified body before constructing `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a tenant/authorization boundary without independent verification (e.g., cross-checking against a shop already known to be associated with the delivered `webhook_id`/topic via a prior, trusted registration).

### Proof of Concept
1. App has the gem installed for shop A (`shop-a.myshopify.com`) and shop B (`shop-b.myshopify.com`), both sharing the same `api_secret_key`.
2. The operator of shop A captures a genuine webhook delivery Shopify sent them: `raw_body` = `{"id":123,...}`, header `x-shopify-hmac-sha256` = valid HMAC of that body, header `x-shopify-shop-domain: shop-a.myshopify.com`.
3. The operator resends this exact request to the app's webhook endpoint, only changing the header to `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` — [6](#0-5)  — and it still validates successfully.
5. `WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "shop-b.myshopify.com"` and the handler processes shop A's data as if it belonged to shop B, corrupting/leaking cross-tenant state in any app that keys storage or side effects off `data.shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
