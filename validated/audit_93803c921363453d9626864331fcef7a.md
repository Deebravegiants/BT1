## Title
Chainlink oracle price truncated to zero during decimal normalization can zero out `SimplexPaymaster` gas pricing - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` normalizes a Chainlink `answer` to 8 decimals and only validates `answer > 0` **before** the decimal-scaling division, exactly the flaw described in the external report (price checked before, not after, precision reduction). When `oracleDecimals > 8`, the function divides `answer` by `10 ** (oracleDecimals - 8)`, which can floor a small-but-positive `answer` to `0` without any revert. [1](#0-0) 

### Finding Description
`_getOraclePrice` fetches `latestRoundData()`, checks `answer <= 0` and staleness, then rescales:

```solidity
if (oracleDecimals < 8) {
    return uint256(answer) * (10 ** (8 - oracleDecimals));
} else if (oracleDecimals > 8) {
    return uint256(answer) / (10 ** (oracleDecimals - 8));
}
return uint256(answer);
``` [1](#0-0) 

There is no `require(price > 0)` (or equivalent) after the division, unlike the pre-division check on `answer`. For a registered token/oracle with `oracleDecimals > 8` (e.g. an 18-decimal price feed), any `answer` smaller than `10 ** (oracleDecimals - 8)` normalizes to exactly `0` while still passing the `answer > 0` guard.

This feeds directly into `_tokenPrice`, which is the sole pricing function used for every gas-fee charge on the paymaster:

```solidity
function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
    uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
    uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

    return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
}
``` [2](#0-1) 

`_tokenPrice` is used by `estimateTokenCost` (and internally during validation/postOp to charge the ERC-20 fee) to convert gas cost in wei into the ERC-20 fee amount:

```solidity
function estimateTokenCost(address token, uint256 gasAmount, uint256 maxFeePerGas) external view returns (uint256) {
    ...
    uint256 weiCost = gasAmount * maxFeePerGas + _postOpCost() * maxFeePerGas;
    return (weiCost * _tokenPrice(cfg)) / _tokenPriceDenominator();
}
``` [3](#0-2) 

If `nativeUsd` is the value that truncates to zero, `_tokenPrice` returns `0` and any user submitting a UserOperation through this permissionless paymaster is charged **zero ERC-20 tokens** while the paymaster still pays real gas from its EntryPoint deposit — a direct drain vector reachable from any ordinary UserOp submitter (an "unprivileged message dispatcher" equivalent for this paymaster). If instead `tokenUsd` truncates to zero, the division `nativeUsd * ... / (tokenUsd * 10_000)` reverts on divide-by-zero, denying service for that token.

### Impact Explanation
- Free-gas drain: an unprivileged caller submitting ERC-4337 UserOperations through `SimplexPaymaster` can have gas subsidized at zero ERC-20 cost if the native-asset oracle answer normalizes to zero, draining the paymaster's EntryPoint deposit/stake with no compensating token transfer.
- Denial of service: if a registered token's oracle answer normalizes to zero, every gas-payment attempt with that token reverts (division by zero) until governance intervenes, which can be an unprivileged relayer/user-triggered condition once the referenced price feed is in that regime.
- Both outcomes stem directly from the missing post-normalization zero check, mirroring the audited root cause in `LibUbiquityPool.updateChainLinkCollateralPrice`.

### Likelihood Explanation
Requires a registered oracle with more than 8 decimals whose reported `answer` is smaller than `10 ** (oracleDecimals - 8)` — i.e. a legitimate but extremely small or misconfigured price. Governance controls which oracles are registered (`RegisterToken`/native oracle setup is a governed request), which somewhat limits blast radius, but the trigger condition itself (a genuine oracle report crossing the truncation boundary, e.g. during extreme price moves, or a token/oracle pairing where decimals and price scale poorly) is not attacker-privileged — it is a normal market/oracle-reporting condition that any UserOp submitter can then exploit for free gas. No additional exploit primitive besides submitting an ordinary UserOp is needed once the oracle is in that state.

### Recommendation
Add an explicit zero check on the normalized price after the decimal-scaling division in `_getOraclePrice`, mirroring the recommended fix in the source report:
```solidity
uint256 price = oracleDecimals < 8
    ? uint256(answer) * (10 ** (8 - oracleDecimals))
    : uint256(answer) / (10 ** (oracleDecimals - 8));
if (price == 0) revert InvalidOraclePrice(address(oracle), answer);
return price;
```
This prevents both the zero-cost gas drain (`nativeUsd == 0`) and the divide-by-zero DoS (`tokenUsd == 0`) paths in `_tokenPrice`.

### Proof of Concept
1. Governance registers a token whose Chainlink-style oracle reports 18 decimals (`cfg.tokenOracleDecimals = 18`), or the native oracle is configured with `nativeOracleDecimals = 18` (both paths call the same `_getOraclePrice`). [4](#0-3) 
2. The oracle's `latestRoundData()` returns a positive but tiny `answer`, e.g. `answer = 5` (18-decimal precision, representing $0.000000000000000005), which satisfies `answer > 0` in `_getOraclePrice`.
3. `_getOraclePrice` computes `uint256(answer) / (10 ** (18 - 8)) = 5 / 1e10 = 0`, returning `0` with no revert.
4. If this is the `nativeOracle` path, `_tokenPrice` returns `0` (numerator `nativeUsd * ... = 0`), so `estimateTokenCost`/the internal ERC-20 charge computed during `_postOp`/validation is `0` — any UserOp submitter pays nothing in the ERC-20 fee token while the paymaster still funds gas from its EntryPoint stake, confirmed against the existing test pattern in `SimplexPaymasterTest.t.sol` (`testTokenPriceNormalizesOracleDecimals`), which exercises the same 18-decimal-oracle code path but does not assert a floor at zero. [5](#0-4) 
5. If instead the `tokenOracle` path truncates to zero, `_tokenPrice`'s division `(tokenUsd * 10_000)` is zero, causing every gas-charge computation for that token to revert (DoS).

Note: I could not fully verify from the indexed code how `nativeOracleDecimals`/`tokenOracle` registration (`RegisterToken`, native-oracle setup) is validated at governance time, nor the exact `_postOp`/`_validatePaymasterUserOp` charge path invoking `_tokenPrice`, since those sections were not returned by search within the tool-call budget. A Devin session with full repo access could confirm the exact call sites in `_postOp`/validation and whether any additional bounds exist on registrable oracle decimals.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
