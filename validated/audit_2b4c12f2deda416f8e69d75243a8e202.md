Confirmed: the webhook HMAC in this gem covers only the raw body, not the `shop-domain`, `topic`, or `webhook-id` headers, yet the app's handler trusts those headers as the tenant identity.### Title
Webhook `shop`, `topic`, and `webhook_id` headers are unauthenticated and not bound to the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` only signs and verifies the raw body of an incoming webhook, while the `shop`, `topic`, and `webhook_id` fields — which are trusted by the app as the tenant identity and passed unmodified to the app's `WebhookHandler` — are read from HTTP headers that are never covered by the HMAC. This breaks the identity binding "authenticated bytes == shop identity acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. `Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` field, which itself is parsed from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: ` [2](#0-1) `, ` [3](#0-2) `.

However, `shop`, `topic`, and `webhook_id` are all read straight from separate, unsigned headers: ` [4](#0-3) `. `Registry.process` verifies only the HMAC of the body, then dispatches the handler using these unauthenticated header values as-is: ` [5](#0-4) `. The resulting `WebhookMetadata.shop` field, which host applications use as the tenant key to look up/act on shop-specific data, is a plain unauthenticated string: ` [6](#0-5) `.

Because the signature only binds the body bytes, an attacker who owns any shop (an unprivileged internet user, since anyone can install a free Shopify dev/trial store and generate real webhooks) receives genuinely-signed webhook deliveries for that shop. They can capture a raw body + valid HMAC pair from their own shop and replay it to the victim app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) to any value they choose — the signature remains valid because those headers were never part of the signed content. This equality that should hold, `shop authenticated by HMAC == shop acted on by handler`, does not hold: the left side is undefined (not covered at all) while the right side is attacker-controlled.

### Impact Explanation
This is a cross-tenant identity spoofing path: a party controlling one (even free/trial) shop can forge webhook deliveries that the host application will process as if they came from an arbitrary other shop, since `Registry.process` never re-validates that `request.shop` corresponds to the entity that actually produced the signed bytes. Depending on how the host app's handlers key off `data.shop` (e.g., updating stored order/customer/app data, triggering redaction, invalidating sessions), this can lead to cross-tenant data corruption or disclosure using only data the attacker legitimately received about their own shop, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is significant because the prerequisite (owning any real Shopify shop capable of receiving webhooks) is available to any unprivileged internet user at no privileged-credential cost, and no interception of Shopify's own traffic or knowledge of the app's `client_secret`/`api_secret_key` is needed — only a normal HTTP POST to the app's public webhook endpoint with header substitution.

### Recommendation
Include the header fields that the application relies on for identity/routing decisions (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified content, or otherwise cryptographically bind them to the payload (e.g., require the app to independently corroborate `shop` against a value derived from a trusted source, or have `HmacValidator` verify a canonical string that concatenates these header values with the body) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker registers/owns Shop A and receives a legitimate webhook from Shopify for topic `orders/create`, with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's real `api_secret_key`.
2. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC header — `lib/shopify_api/utils/hmac_validator.rb:13-22`, `lib/shopify_api/webhooks/request.rb:35-38`.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` — `lib/shopify_api/webhooks/registry.rb:198-199` — causing the app to process attacker-supplied data under the victim shop's identity.
