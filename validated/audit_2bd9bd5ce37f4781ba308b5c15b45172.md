## Analysis

`SimplexPaymaster` is a permissionless ERC-4337 paymaster that lets any solver/relayer pay UserOp gas in a registered stablecoin, converting cost via two Chainlink feeds (token/USD and native/USD). Every UserOp submission — an action any unprivileged bandwidth purchaser can trigger — invokes `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` during paymaster validation. [1](#0-0) 

`_getOraclePrice` only validates `answer > 0` and staleness against `updatedAt`, but never checks `answeredInRound >= roundId` from `latestRoundData()`, exactly the round-completeness check the referenced Chainlink advisory calls out.

### Title
Missing Chainlink round-completeness check in `SimplexPaymaster._getOraclePrice` allows stale/incomplete-round price usage - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` (used by both the gas-pricing path `_tokenPrice`/`_fetchDetails` triggered on every UserOp, and by the treasury-only `swapAndDeposit`) reads `latestRoundData()` from Chainlink but never verifies `answeredInRound >= roundId`. It only checks `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`.

### Finding Description
`AggregatorV3Interface.latestRoundData()` can return data for a round that has not yet reached consensus: if a round is stalled, Chainlink carries forward the previous round's `answer`/`updatedAt` while `roundId` has already advanced, so `answeredInRound < roundId`. Because this contract's staleness check only compares `updatedAt` against `maxOracleAge`, a carried-forward-but-recent timestamp from an incomplete round passes the check even though the price itself may be stale/incorrect. This is precisely the vulnerability class described in the referenced report for `chainlinkAdaptor#getMarkPrice`: ` [2](#0-1) ` lacks the `answeredInRound >= roundId` guard that the report recommends adding.

This code path is reached by:
- `_fetchDetails`, called from `_validatePaymasterUserOp` on every UserOp any solver/bandwidth purchaser submits: ` [3](#0-2) `
- `swapAndDeposit`, which derives `amountOutMin` from the same unguarded oracle read: ` [4](#0-3) `

### Impact Explanation
An incomplete/stalled Chainlink round can cause `_tokenPrice` to compute a mispriced `tokenPrice`, so the ERC-20 cost charged to a solver via `_prefund`/`_erc20Cost` deviates from the true gas cost — the paymaster can overcharge or undercharge stablecoin gas fees. In `swapAndDeposit`, the same stale price sets `amountOutMin`, weakening the on-chain slippage protection that the contract explicitly relies on to keep the swap execution price un-influenceable (per the contract's own security note). Because this pricing path is exercised by every permissionless UserOp, and the contract holds the EntryPoint deposit, stake, and accrued token surplus, a stalled oracle round translates directly into fund-loss risk (over/undercharging solvers, or an unfavorable forced swap rate), matching a Medium-severity mispricing bug reachable by an unprivileged bandwidth purchaser.

### Likelihood Explanation
Chainlink round staleness/incompleteness is a known, historically observed failure mode (node outages, congestion), not a hypothetical. Because the mint/charge path runs on every UserOp with no round-completeness guard, exploitation requires no special privilege — any solver submitting a UserOp during a stalled round is affected, and the treasury-triggered `swapAndDeposit` is similarly exposed whenever it happens to coincide with a stalled round.

### Recommendation
Add a round-completeness check in `_getOraclePrice`, mirroring the report's suggested fix:
```solidity
(uint80 roundId, int256 answer, , uint256 updatedAt, uint80 answeredInRound) = oracle.latestRoundData();
require(answeredInRound >= roundId, "ROUND_NOT_COMPLETE");
```
in addition to the existing `answer > 0` and staleness checks.

### Proof of Concept
1. Chainlink feed used as `nativeOracle` or a `tokenConfigs[token].tokenOracle` enters a stalled round: `roundId` increments but `answeredInRound` lags behind, while the aggregator forwards the previous round's `answer`/`updatedAt` (which can still be within `maxOracleAge`).
2. A solver submits a UserOp using this paymaster; `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` is called on both feeds.
3. `_getOraclePrice` passes both checks (`answer > 0`, `updatedAt` recent enough) despite the round being incomplete, returning a stale/incorrect price.
4. `_erc20Cost` in `_prefund` charges the solver based on this stale `tokenPrice`, resulting in over- or under-collection of stablecoin relative to true gas cost — with no revert or fallback, since the contract has no mechanism to detect the incomplete round.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
