Audit Report

## Title
CORS wildcard-origin matcher allows subdomain-boundary bypass leading to allowlist bypass - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's user-facing HTTP server supports wildcard CORS entries like `https://*.example.com` in `CORSAllowedOrigins`. The matcher in `isAllowedOrigin` strips the `*.` prefix and performs a raw `strings.HasSuffix` check against the request's `Origin` host without requiring a `.` label boundary, so any origin whose host merely ends with the same characters (e.g. `evilremix.com` for an allowlisted `*.remix.com`) is incorrectly treated as a valid subdomain match.

## Finding Description
In `isAllowedOrigin`, the wildcard branch does: `allowedHost = allowedHost[2:]` (stripping `*.`) then `strings.HasSuffix(originHost, allowedHost)`. This treats `*.` as "any string ending in this text" rather than "any subdomain of this domain," since there is no check that the character immediately preceding the matched suffix in `originHost` is a `.`. As a result, `evilremix.com`, `notremix.com`, or any domain concatenating attacker-controlled bytes directly before `remix.com` passes the check. This function is invoked unconditionally for every request when `CORSEnabled` is true, and on a match the raw attacker-supplied `Origin` header is reflected verbatim into the `Access-Control-Allow-Origin` response header, with no other validation layer catching the flaw.

## Impact Explanation
An attacker who registers or controls a domain sharing the suffix bytes of an allowlisted wildcard domain can have their origin reflected into `Access-Control-Allow-Origin`, allowing a page on the attacker's domain to make authenticated cross-origin browser requests to the Gateway's JSON-RPC endpoint and read responses that should be restricted to the legitimate allowlisted subdomains. This maps to the in-scope "allowlist bypass" / cross-origin response exposure impact category for the Gateway.

## Likelihood Explanation
Exploitation requires only that an operator use the wildcard CORS convenience feature (`*.<domain>`), which is a documented, supported configuration mechanism, not a misuse of the API. Given that configuration, any unauthenticated attacker who controls a suffix-colliding domain can trigger the bypass with an ordinary browser request or cross-origin fetch — no credentials, roles, or host access required, and the behavior is fully deterministic and repeatable.

## Recommendation
Require a `.` boundary immediately before the matched suffix, e.g. compare against `strings.HasSuffix(originHost, "."+allowedHost)` (after stripping only the `*`), or equivalently check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` so that only true subdomains of the allowed domain match.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. Send an HTTP request (or CORS preflight) to the Gateway's user-facing endpoint with header `Origin: https://evilremix.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirming the bypass since `evilremix.com` is not a subdomain of `remix.com`. This can be codified as a Go unit test directly calling `httpServer.isAllowedOrigin("https://evilremix.com")` against a config with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it returns `true`.
