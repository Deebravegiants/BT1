### Title
`createWithdrawMemo` fails to escape/validate colons in `destinationMemo`, allowing malformed XRPL destination-tag memos - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts])

### Summary
`createWithdrawIntentPrimitive` builds the on-chain memo as `["WITHDRAW_TO", address, xrpMemo].join(":")` without validating or escaping the caller-supplied `destinationMemo`. Because `WithdrawalParams.destinationMemo` is an unconstrained `string | undefined` forwarded verbatim from the integrator/user, a memo containing a colon produces an ambiguous, extra-field memo string that a colon-delimited relayer parser will interpret differently from the caller's intent.

### Finding Description
The broken equality is: `caller's intended tag (e.g. "123")` == `tag actually encoded/paid out on XRPL after relayer parses the memo`.

- `createWithdrawIntentPrimitive` ( [1](#0-0) ) passes `params.destinationMemo` straight through to `createWithdrawMemo` as `xrpMemo`.
- `createWithdrawMemo` joins `["WITHDRAW_TO", normalizedAddress, xrpMemo]` with `:` with no escaping ( [2](#0-1) ).
- `WithdrawalParams.destinationMemo` is typed as a free-form optional string with no format constraints documented beyond "included in the transaction memo field" ( [3](#0-2) ).
- `PoaBridge.validateWithdrawal` only checks presence of `destinationMemo` when the XRPL account requires a destination tag (`requireDestinationTag && !args.destinationMemo`); it never validates the memo's content (e.g., that it is purely numeric, or free of `:`), as seen in the full validation flow ( [4](#0-3) ).
- `createWithdrawalIntents` calls `createWithdrawIntentPrimitive` directly with `args.withdrawalParams.destinationMemo`, with no sanitization step in between ( [5](#0-4) ).

With `destinationAddress = "rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv"` and `destinationMemo = "123:evil"`, the produced memo is `"WITHDRAW_TO:rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv:123:evil"` — 4 colon-delimited fields instead of the expected 3, as confirmed by the existing test pattern showing the normal 3-field format for a valid memo ( [6](#0-5) ). None of the existing guards (`validateAddress`, `compareAddresses`, the XRPL `requireDestinationTag`/`depositAuth` checks) inspect or restrict the memo's characters — they only check the address and presence of a memo, not its content.

### Impact Explanation
The relayer that ultimately submits the XRPL payment parses this SDK-controlled memo field to derive the destination tag. If it splits on `:` and takes an unexpected field (or fails to parse a non-numeric/oversized tag), the funds can be sent to the correct XRPL address but with a wrong, missing, or malformed destination tag. On exchanges requiring exact tag matching, this strands funds with no recovery path once withdrawn from `intents.near`, since NEAR-side execution is final. This matches the Critical category ("funds delivered to a wrong address/chain/contract with no recovery").

### Likelihood Explanation
Any ordinary SDK caller/integrator can supply a `destinationMemo` value forwarded from an untrusted upstream party (e.g., a counterparty-supplied tag), and the SDK performs no sanitization before embedding it in a colon-delimited memo. The precondition is simply "withdraw XRP with a memo/tag containing a colon" — no privileged access required, fully repeatable per call, low attacker cost.

### Recommendation
Validate `destinationMemo` for XRPL withdrawals to ensure it is a valid destination tag (e.g., digits only, within `uint32` range) before constructing the memo, and reject/throw on invalid characters (including `:`) in `createWithdrawMemo` or in `validateWithdrawal`. Alternatively, use a delimiter-safe encoding (e.g., fixed-width fields or explicit length-prefixing) instead of naive colon-joining.

### Proof of Concept
```ts
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.test.ts
it("demonstrates ambiguous memo when destinationMemo contains a colon", () => {
  const result = createWithdrawIntentPrimitive({
    assetId: "nep141:xrp.omft.near",
    destinationAddress: "rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv",
    destinationMemo: "123:evil",
    amount: 1000000n,
  });

  const fields = result.memo.split(":");
  // Expected (caller intent): ["WITHDRAW_TO", address, "123"] -> 3 fields
  // Actual: 4 fields due to unescaped colon in destinationMemo
  expect(fields.length).toBeGreaterThan(3);
  expect(result.memo).toBe(
    "WITHDRAW_TO:rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv:123:evil",
  );
});
```

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
