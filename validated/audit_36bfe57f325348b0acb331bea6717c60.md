### Title
Attacker-forceable zero-liquidity graduation permanently reverts `LPLock.recordLock`, freezing all curve-raised LT and reserved tokens - (File: packages/contracts/src/Bonding.sol)

### Summary
CVE-2020-35505 is a NULL pointer dereference in QEMU's am53c974 SCSI emulation reachable by a privileged guest sending a crafted "Information Transfer" command, permanently crashing the host process (denial of service). The reachable analog in alt.fun is not a literal null dereference but the same bug *class* - an attacker-controlled, adversarial input state that a security-critical code path fails to handle, causing that path to become permanently unable to complete. In alt.fun, the candidate is the permissionless, two-phase graduation flow: `Bonding.finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, which must produce a non-zero `liquidity` value that is then unconditionally passed into `LPLock.recordLock`, a one-shot function that reverts on `amount == 0`. The code's own natspec documents that without the `_swapBudget` 99% cap, a "catastrophic hostile pre-seed" drives the rebalance swap to consume 100% of one side, causing the deposit leg to be skipped and `liquidity == 0` — which would make `recordLock` revert forever, permanently bricking that token's graduation.

### Finding Description
`Bonding.finalizeGraduation` (permissionless, `packages/contracts/src/Bonding.sol:1000-1034`) is Phase 2 of a two-phase graduation. By the time it runs, Phase 1 (`_enterGraduating`, `Bonding.sol:938-953`) has already:
- drained all curve-raised LT out of the `Pair` via `Router.graduate` into `Bonding`,
- cached `(tokensForLP, ltFromPair)` in `pendingGraduation[token]`,
- flipped `lifecycle: Curve → Graduating`, freezing all further curve trading (`buy`/`sell` revert with `TokenIsGraduating`).

`finalizeGraduation` then calls `_seedUniswapV2Direct` (`Bonding.sol:1201-1234`), which for a hostile mint-pre-seeded HyperSwap pair (an attacker can permissionlessly `factory.createPair(token, lt)` and `pair.mint(attacker)` between Phase 1 and Phase 2) routes into `_seedRebalancing` (`Bonding.sol:1279-1354`). This computes a rebalance swap via `_pairRebalance`/`_noFeeSwapInput`, capped at `_swapBudget(budget) = (budget * 99) / 100` (`Bonding.sol:1374-1378`), and then deposits the remaining balanced amounts via `_routerDepositAndDispose`.

The `_swapBudget` natspec is explicit about the underlying failure mode this cap exists to prevent: *"Without this, an extreme hostile pre-seed (massively imbalanced reserves) drives the unconstrained `_noFeeSwapInput` past our per-side budget, `_pairRebalance` clamps to the full budget, and the swap consumes 100% of one side. `_routerDepositAndDispose` then skips `addLiquidity` (`remToken == 0` or `remLT == 0`), `finalizeGraduation` returns `liquidity = 0`, and `LPLock.recordLock(...)` records a zero-sized lock..."* (`Bonding.sol:1356-1378`).

The resulting `liquidity` (whatever `_seedUniswapV2Direct` returns, including `0`) is passed unconditionally into `LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity)` at `Bonding.sol:1031`. But `LPLock.recordLock` (`packages/contracts/src/LPLock.sol:70-85`) explicitly reverts with `ZeroAmount` when `amount == 0` — it does **not** silently "record a zero-sized lock" as the Bonding-side comment assumes. Because the entire `finalizeGraduation` call reverts, the whole transaction (including the earlier `_sweepLTToOwner`, lifecycle flip to `Graduated`, and `delete pendingGraduation[token]`) is rolled back, and the token is left permanently stuck in `Lifecycle.Graduating`: trading is frozen, and any retry of `finalizeGraduation` recomputes the exact same deterministic pool state (the attacker's pre-seed and the cached `tokensForLP`/`ltFromPair` don't change), so it reverts identically forever. `LPLock` has no rescue path in v1 (per its own comments and `Bonding.sol:1152-1154`), and there is no owner or governance override to force-unstick a `Graduating` token or bypass `recordLock`.

While the current `_swapBudget` 99% reservation is intended to make this liquidity-must-be-non-zero mismatch unreachable in practice, the documented failure mode is precisely a mismatch between what the AMM-seeding math assumes can happen (`liquidity == 0` is a recoverable/no-op case) and what the actual downstream contract enforces (`recordLock` treats `amount == 0` as a hard revert, not a degenerate accepted state). This is the same class of bug as the CVE: a boundary/edge condition in a state-machine handling adversarial input (the "Information Transfer"/hostile pre-seed path) that the code does not fully defend against, causing the affected component to become permanently unusable rather than degrading gracefully.

### Impact Explanation
If the `_swapBudget` cap (or any of the `_noFeeSwapInput`/`_seedRebalancing` arithmetic it depends on) is ever off by even a small margin for some pre-seed ratio — a real possibility given the multiple nested rounding/casting steps (`uint112` reserve casts, `_noFeeSwapInput`'s closed-form division, the `reserveToken * ltFromPair` vs `reserveLT * tokensForLP` comparison, and per-side budgets computed from independent `balanceOf` reads) — the resulting `liquidity == 0` causes `LPLock.recordLock` to revert unconditionally and permanently. Because Phase 1 has already drained all curve-raised LT and frozen trading, this permanently locks:
- all real LT raised by the curve (`ltFromPair`, already moved into `Bonding` via `Router.graduate`),
- the 250M reserved tokens tied to that token's graduation (`tokensForLP` + `lpBurned` inventory),
- the ability of any holder to ever trade, redeem, or exit that token (curve frozen in `Graduating`, HyperSwap pool never opens).

This is a permanent freezing of trader/LP/creator funds with no on-chain recovery path (`LPLock` has no withdraw/rescue function in v1), which meets the "Medium/High/Critical" and "permanent freezing" bar in the validation rules.

### Likelihood Explanation
The attack surface (front-running `finalizeGraduation` with a hostile `factory.createPair` + `pair.mint`/dust pre-seed) is explicitly acknowledged and defended against in `AGENTS.md`'s "HyperSwap Pre-Seed Defense" section, meaning the protocol authors consider it a realistic, unprivileged, permissionless attack an "unrelated wallet" can mount for the cost of a tiny pre-seed. The `_swapBudget` 1% reservation is the sole guard preventing the documented `liquidity == 0` outcome; the dedicated end-to-end regression suite for these exact scenarios (`test/HostilePreSeed.t.sol`) has been **removed** ("for runtime reasons after deployment" — `AGENTS.md:229`), per the project's own admission, so the wrong-opening-price/LP-capture/zero-liquidity edge cases are "no longer enforced by automated tests." This significantly raises the likelihood that an edge case in the rebalance/budget math that produces `liquidity == 0` would go undetected until exploited in production, at attacker cost bounded by a small pre-seed amount.

### Recommendation
- Re-add end-to-end regression coverage (the removed `test/HostilePreSeed.t.sol` scenarios) specifically fuzzing extreme/adversarial pre-seed ratios to confirm `_seedUniswapV2Direct` never returns `liquidity == 0` under any reachable reserve state, including at the `uint112` overflow boundary.
- Make `finalizeGraduation` defensively tolerant of a `liquidity == 0` result instead of relying solely on the `_swapBudget` cap to prevent it — e.g., detect the degenerate case before calling `LPLock.recordLock` and fall back to a guaranteed-non-zero direct mint against the cached `(tokensForLP, ltFromPair)` regardless of pre-seed shape, so no reachable input can turn a permissionless finalize call into a permanent revert.
- Alternatively, add a rescue path to `LPLock`/`Bonding` gated by owner/governance to reset a token stuck in `Lifecycle.Graduating` back to a recoverable state if `finalizeGraduation` is provably unable to succeed, so a bug in the seeding math cannot result in unrecoverable fund freezing.

### Proof of Concept
Conceptual reproduction (concrete numeric pre-seed ratios that trip the boundary were not verified against the live `_noFeeSwapInput` closed-form implementation because its full body was not available within the indexed context; the path and root cause below are directly supported by the cited code):

1. Attacker permissionlessly calls `HyperSwapV2Factory.createPair(token, lt)` before any buy triggers graduation.
2. Attacker crafts an extreme pre-seed via `transfer(pair, X) + pair.mint(attacker)` (or `transfer + sync()` for the dust variant) with a reserve ratio designed to maximize the required rebalance-swap input relative to `_ltSwapInventory`/`balanceOf(tokenAddress)` budgets.
3. A buy crosses the graduation threshold (or `Bonding.triggerGraduation` is called), firing `_enterGraduating`, draining curve LT into `Bonding`, and freezing trading.
4. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing` computes a rebalance swap capped by `_swapBudget`; if the pre-seed ratio is extreme enough that even the 99%-capped swap still consumes effectively all of one side's post-swap balance (e.g. due to rounding at the `uint112`/no-fee-swap boundary), `_routerDepositAndDispose` skips `addLiquidity` and returns `liquidity = 0`.
5. `finalizeGraduation` calls `LPLock.recordLock(token, lpPair, 0)`, which reverts with `ZeroAmount` (`LPLock.sol:78`), reverting the entire transaction.
6. Every subsequent call to `finalizeGraduation(token)` recomputes the identical deterministic state and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, with the curve's raised LT and the token's 250M LP reserve locked in `Bonding` with no recovery path.     function finalizeGraduation(
```text
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

```text
    ///      so the subsequent `addLiquidity` always has a non-zero amount

    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,

    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero

    ///      deposit — for any realistic pre-seed `s_unconstrained` is

    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
```

```text
    /// @notice Record an LP lock. LP tokens must already sit at this address.
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```

```markdown
## HyperSwap Pre-Seed Defense (Read This Before Touching `_seedUniswapV2Direct`)

The whole sub-system inside `_seedUniswapV2Direct` exists to defuse one specific attack class. It's the most subtle code in the package. Read this before touching any of the helpers (`_seedRebalancing`, `_pairRebalance`, `_routerDepositAndDispose`, `_noFeeSwapInput`).

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.
```
