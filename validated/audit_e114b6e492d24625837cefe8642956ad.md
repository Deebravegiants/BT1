Confirmed: `Registry.process` validates HMAC over the raw body only, then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc. and hands it to the app's handler without any additional cross-check.### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook data attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value acted upon by the host application directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` verifies covers only the raw request body. This breaks the identity binding: `shop attributed to the event` ≠ `shop actually authenticated by the HMAC`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Webhooks::Request#shop` is read straight from a header that is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (body-only) and then, without any further verification of the `shop` field, builds `WebhookMetadata` using `request.shop` and forwards it to the app's handler: [3](#0-2) 

`HmacValidator.validate` only ever signs/compares `verifiable_query.to_signable_string`, i.e., the body for webhooks, never the headers: [4](#0-3) 

`WebhookMetadata` is a plain struct carrying the attacker-controllable `shop` field into the handler with no additional binding to the HMAC-verified content: [5](#0-4) 

**Equality that should hold but doesn't:** `shop authenticated by HMAC == shop acted upon by the handler`. Because the HMAC only covers the body, this equality is never enforced by the gem.

### Impact Explanation
Any merchant who has installed the app on their own store (an unprivileged internet user relative to the app's other tenants) can capture a legitimate webhook Shopify sent them — a valid `(raw_body, hmac)` pair signed with the app's `client_secret` for their own shop's event — and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. Because `Registry.process` never checks that the header-derived `shop` corresponds to any value covered by the HMAC, the host application will process the event believing it originates from the victim shop. Depending on how the host app implements `WebhookHandler#handle` (which is exactly the interface this gem defines and expects apps to trust), this can lead to cross-tenant data contamination/injection — e.g., attacker-controlled order/customer/product data being recorded, mandatory GDPR redaction webhooks being triggered, or app state updated for a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the boundary crossed is the per-tenant `shop` identity that separates one merchant's data from another's within a single app installation.

### Likelihood Explanation
Likelihood is high for any attacker who is a legitimate (even single, low-privilege) merchant user of the app: no `api_secret_key`, access token, or credential theft is required — only the ability to receive one legitimate webhook from their own installation and replay it with a modified header, which is a standard unauthenticated HTTP request to the app's public webhook endpoint. The gem does not document or enforce any requirement for the host app to independently verify `shop` against a known session/tenant list, so apps that trust the `WebhookMetadata#shop` field (the field the gem itself is providing "verified" data through, right after `Utils::HmacValidator.validate`) are directly exposed.

### Recommendation
Ensure the shop-identifying header is bound to the verified signature, e.g. by including `shop-domain` in the material used for signature verification, or by requiring the host app to look up an existing installed session for the header-provided shop and reject unknown/uninstalled shops before trusting `WebhookMetadata#shop`. At minimum, `Registry.process` should not construct `WebhookMetadata` from unauthenticated header data without documenting to consumers that `shop` is unauthenticated and must be independently cross-checked against the recipient shop's session store.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`.
2. Capture a real webhook delivery, e.g., topic `orders/create`, with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC of raw body computed with app's client_secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - raw body: attacker-crafted order JSON (attacker controls order contents on their own store).
3. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [6](#0-5) 
5. `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)` is built with `shop == "victim.myshopify.com"` and passed to the app's `handle` method, which will process attacker-controlled data as though it belongs to `victim.myshopify.com`.
