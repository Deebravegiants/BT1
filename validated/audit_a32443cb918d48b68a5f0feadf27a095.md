### Title
Bad-debt socialization clamps the supply index to a nonzero floor, leaving wiped-out suppliers a residual claim that drains future depositors' cash - (File: contracts/pool/src/interest.rs)

### Summary
When socialized bad debt meets or exceeds a market's total supplied value, `apply_bad_debt_to_supply_index` clamps the supply index *up* to `SUPPLY_INDEX_FLOOR_RAW` (`RAY / 1000`) rather than zeroing or burning the orphaned scaled shares. Existing suppliers keep their full scaled positions, which unscale to a positive asset claim at the floor index. The next honest `supply` credits fresh cash to the market, and the stranded supplier's `withdraw` pays that cash out — a Primitive-style loophole where a permissionless path (`clean_bad_debt`) leaves a claim that silently exfiltrates other users' funds, with no pause or upgrade to stop it.

### Finding Description
`apply_bad_debt_to_supply_index` caps the write-down at `total_supplied_value` and then floors the new index:

```rust
// contracts/pool/src/interest.rs:80-88
let capped = bad_debt.min(total_supplied_value);
let remaining = total_supplied_value.checked_sub(cache.env(), capped);
let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
let new_supply_index = cache.supply_index().mul_floor(cache.env(), reduction_factor);
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

When `bad_debt >= total_supplied_value`, `reduction_factor` is zero, so the index is set to the floor — but the aggregate `supplied` scaled-share count is never reduced. Every supplier's shares then floor-unscale to a positive residual claim (`unscale_supply_floor`, `contracts/pool/src/cache/scale.rs:60-67`). Withdrawal resolves `(burned, gross)` via `resolve_withdrawal` and pays out `gross` against `cache.cash()` after `require_reserves` (`contracts/pool/src/ops/withdraw.rs:93-118`); there is no check that the position's claim was already wiped by socialization.

The pool's own test pins the drain: `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` shows a wipeout leaving `stranded > 0` shares, a second user depositing `c`, and the stranded holder withdrawing exactly `c` — `gross == c`, pool cash drops to zero, and the honest deposit is gone (`contracts/pool/tests/interest.rs:316-369`).

Reachable path, all unprivileged:
1. Wait for (or ride) a collateral price collapse that leaves an account with `total_debt > total_collateral <= $5` dust — the `DustCapped` gate in `socialize_bad_debt` (`contracts/controller/src/positions/liquidation/mod.rs:229-243`).
2. Call `controller::clean_bad_debt(caller, account_id)` — permissionless, no pause/flag block (`process_clean_bad_debt`, `mod.rs:195-200`). `execute_bad_debt_cleanup` burns all debt shares and calls `apply_bad_debt_to_supply_index` with the full debt, driving the debt market's supply index to the floor while `supplied` shares persist.
3. After any user `supply`s into that market (or cash arrives from `repay`/`recapitalize`), the attacker — themselves a wiped supplier — calls `withdraw` and extracts cash their shares no longer honestly back.

### Impact Explanation
Theft of user funds: stranded scaled shares convert into real asset withdrawals that consume later depositors' principal. The market is economically dead (index at floor), yet share balances survive indefinitely, so every future deposit or recapitalization into that hub market is claimable by holders of wiped-out positions. Because the account that triggered cleanup is deleted, there is no debtor to recover against; `recapitalize` refills the shortfall but can itself be drained by the same phantom claims.

### Likelihood Explanation
Medium. Triggering requires bad debt on a market reaching the point where `bad_debt >= total_supplied_value` — i.e., near-total wipeout of that debt market, which needs utilization high and a severe, sustained collateral crash so that a dust-collateral account's debt exceeds the market's entire supplied value. The dust gate ($5) caps collateral, not debt, so an account can carry arbitrarily large debt into cleanup. It also requires pre-existing supply positions in the wiped market to still hold shares (they do — socialization never burns supplier shares). Market conditions make this uncommon but not exceptional for volatile collateral; no privileged access or timing precision is needed once the gate opens.

### Recommendation
When `bad_debt >= total_supplied_value`, burn the orphaned supply shares instead of clamping: set `supplied` (and `revenue` shares' backing) to zero, or record a wiped-market flag that forces `resolve_withdrawal`/`unscale_supply_floor` to return zero until fresh shares are minted against a reset index. Alternatively, mint new suppliers' shares at a rebased index while voiding pre-wipeout positions. At minimum, gate withdrawals on markets whose index sits at `SUPPLY_INDEX_FLOOR_RAW` unless the position was created after the wipeout.

### Proof of Concept
The in-repo test is already a full PoE (`contracts/pool/tests/interest.rs:316-369`):

```rust
apply_bad_debt_to_supply_index(&mut cache, Ray::from(2_000_000 * RAY)); // wipeout: index -> floor
let stranded = cache.unscale_supply_floor(scaled_a); // > 0: phantom claim survives
// user B supplies c
cache.mint_supply(cache.calculate_scaled_supply(c));
cache.credit_cash(c);
// user A withdraws all -> pays exactly c, draining B's deposit
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, scaled_a);
cache.require_reserves(gross); // passes: B's cash backs it
assert_eq!(gross, c);
```

Concrete unprivileged sequence against the deployed contracts: (1) collateral oracle crash pushes account X to `debt >> collateral <= $5`; (2) attacker calls `controller::clean_bad_debt(caller=attacker, account_id=X)` — debt market's supply index is floored; (3) victim calls `controller::supply` on that hub asset; (4) attacker (a pre-wipeout supplier) calls `controller::withdraw(account_id=own, amount=i128::MAX)` and receives the victim's tokens.
