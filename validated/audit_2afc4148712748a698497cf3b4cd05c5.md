### Title
Fee-on-transfer / non-standard ERC20 underlying causes escrow under-collateralization in `WrappedHyperFungibleToken::send` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken::send` locks the underlying ERC20 by transferring the caller-specified `params.amount` via `safeTransferFrom`, but never checks how much the contract actually received. It then dispatches a cross-chain `Message` committing to that same nominal `params.amount`, which the destination side will later honor in full (mint on `HyperFungibleToken::onAccept`, or unlock via `safeTransfer` on `WrappedHyperFungibleToken::onAccept`/refund on timeout). If the underlying token charges a transfer fee or otherwise delivers less than the requested amount, the wrapper locks less than it promises to release, silently under-collateralizing the bridge.

### Finding Description
`send()` performs the lock like this: [1](#0-0) 

It never compares balance-before/after to determine the actual amount received; it simply forwards `params.amount` into the dispatched message body via `_buildDispatchPost`: [2](#0-1) 

On the destination chain (a `HyperFungibleToken` remote deployment) `onAccept` mints `message.amount` unconditionally — this is a burn/mint token backed 1:1 by what this wrapper is supposed to be holding in escrow: [3](#0-2) 

Symmetrically, on refund/timeout or on receiving unlock messages back on the home chain, `WrappedHyperFungibleToken` releases the full `message.amount` from its own balance via `safeTransfer`, without ever re-verifying it actually holds that much: [4](#0-3) [5](#0-4) 

Because `configure()` lets the owner set an arbitrary `underlying` ERC20 (there is no restriction to fee-free, standard-compliant tokens), any unprivileged caller of `send()` who uses (or is forced to use, if the owner configures such a token) a fee-on-transfer/rebasing/deflationary token will cause the wrapper to lock strictly less than `params.amount`. The bridged message nevertheless commits to the full nominal amount, so:
- On the remote `HyperFungibleToken`, the recipient is minted the full nominal amount (over-minted relative to actual backing).
- If that recipient bridges back, the home-chain wrapper is asked to `safeTransfer` the full nominal amount out of a locked balance that is smaller than the sum of all outstanding nominal claims.

Repeated sends compound the shortfall, since escrow is tracked implicitly by the ERC20 balance of the wrapper contract rather than by any accounted/received amount. This is directly analogous to the reported `TokenManager::_transfer` issue (no reconciliation between requested and actually-received transfer amounts for non-standard ERC20s), but here it manifests in a cross-chain lock/mint token bridge, where the impact is compounded: an unbacked mint on the remote chain and eventual insolvency/frozen funds on the home chain wrapper (later, legitimate bridge-back or refund calls will revert with insufficient balance, since `safeTransfer` will fail once the wrapper's real balance is exhausted below cumulative committed amounts).

This is reachable by any unprivileged user simply calling `send()` — no special privilege needed, only requiring the configured `underlying` token to be fee-on-transfer or otherwise non-standard (rebasing, has an owner-fee mechanism, etc.), which is entirely plausible for real-world ERC20 deployments the wrapper might be configured against.

### Impact Explanation
- Unbacked minting on the destination `HyperFungibleToken`: recipients receive full nominal token amounts on the remote chain that are not fully collateralized by locked underlying on the home chain.
- Permanent freezing/loss of funds for later users: once the wrapper's actual token balance falls below the sum of outstanding nominal commitments, subsequent unlock/refund `safeTransfer` calls will revert (insufficient balance), leaving legitimate bridge-back or timeout-refund requests unable to be delivered/completed — a route unable to deliver messages/funds, matching the "route unable to deliver messages" and "unbacked mint" categories.
- This breaks the fundamental 1:1 backing invariant documented for the lock/unlock model: "the WrappedHFT accumulates locked tokens as users bridge out and releases them when users bridge back."

### Likelihood Explanation
Medium-to-High: this requires the underlying configured token to have a transfer fee, rebase, or other non-standard transfer semantics. Many real-world tokens (e.g., certain stablecoins with fee switches, deflationary/reflection tokens) exhibit this behavior, and the wrapper's owner controls which `underlying` is configured without any code path enforcing "no fee-on-transfer" semantics. Any single user transaction (`send`) triggers the discrepancy — no coordination, front-running, or privileged access is needed.

### Recommendation
In `WrappedHyperFungibleToken::send` (and the upgradeable variant `WrappedHyperFungibleTokenUpgradeable::send`), measure the actual amount received before building/dispatching the message:
```solidity
uint256 balanceBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 received = IERC20(_underlying).balanceOf(address(this)) - balanceBefore;
```
Use `received` (not `params.amount`) when constructing the `Message.amount` embedded in the dispatched request, mirroring the pattern already used correctly in `IntentGatewayV2` for fee-on-transfer inputs (`evm/src/apps/IntentGatewayV2.sol`, lines ~320-323, which computes `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore`). This keeps the bridged commitment consistent with what is actually escrowed, preventing over-minting downstream and preserving the wrapper's solvency for unlocks/refunds.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `underlying` = a fee-on-transfer ERC20 (e.g., 1% fee, similar to the `MockTokenWithFee` from the external report).
2. Attacker (or any user) calls `send(SendParams{ amount: 1000e18, dest: <remote HFT chain>, to: attackerOnRemote, ... })`.
3. `safeTransferFrom` only delivers 990e18 to the wrapper (1% fee retained by the token contract), but `_buildDispatchPost` embeds `amount: 1000e18` in the `Message` and the request is dispatched/committed as `keccak256`-hashed with that nominal amount.
4. On the remote chain, `HyperFungibleToken::onAccept` mints `1000e18` to the attacker's remote address — 10e18 more than what is actually backed on the home chain.
5. If the attacker (or any subsequent user) then bridges the received `1000e18` back, the home-chain wrapper's `onAccept`/refund path attempts `safeTransfer(beneficiary, 1000e18)`, but the wrapper only ever held `990e18` from this deposit (plus whatever unrelated balance existed) — eventually, as this is repeated, the wrapper's balance is exhausted below the sum of outstanding nominal claims, and unlock/refund calls begin reverting, freezing funds for other users.
