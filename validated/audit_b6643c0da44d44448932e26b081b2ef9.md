### Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` verify a webhook's authenticity by computing an HMAC over the raw request body only. The `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers are read directly from unauthenticated request headers and are never included in the signed material. Since the `api_secret_key` used to sign webhooks is shared by every shop that installs the app (it is the app's client secret, not a per-shop secret), any shop owner who installs the app can capture a validly-signed `(body, hmac)` pair from their own legitimate webhook deliveries and replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a different (victim) shop. `Registry.process` accepts this as authentic and hands the attacker-chosen `shop` value straight to the app's webhook handler.

### Finding Description
The identity binding that should hold is:
`shop asserted in WebhookMetadata.shop == shop cryptographically bound by the HMAC signature`

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the payload.

`to_signable_string` — the value that actually gets HMAC-verified — is only the raw body: [2](#0-1) 

`HmacValidator` signs/compares exactly that string, so headers (shop, topic, webhook-id, api-version) are outside the signed scope: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then forwards the unauthenticated `request.shop` to the handler as trusted tenant identity: [4](#0-3) 

Because `Context.api_secret_key` is the app's single client secret shared across every merchant that installs the app (not a per-shop secret — see `HmacValidator.validate` using `Context.api_secret_key`/`Context.old_api_secret_key` globally): [5](#0-4) 

...an attacker who is merely an ordinary merchant that installed the app can:
1. Install the app on their own store (unprivileged, self-service action).
2. Trigger a real event (e.g., `orders/create`) with attacker-chosen field content, causing Shopify to deliver a webhook to the app with a valid `x-shopify-hmac-sha256` for that body — signed with the shared `api_secret_key`.
3. Capture that `(body, hmac)` pair.
4. POST it directly to the app's public webhook endpoint, replacing only the `x-shopify-shop-domain` header with the victim shop's domain (and, if desired, `x-shopify-webhook-id`/`x-shopify-topic`).
5. `HmacValidator.validate` succeeds because it only re-hashes the raw body — which is unchanged and still matches — while `request.shop` now reports the victim's domain.

The handler receives `WebhookMetadata` claiming to be for the victim shop, with attacker-controlled body content, despite never having interacted with the victim's shop or the app's secret in any tenant-scoped way.

### Impact Explanation
This breaks the shop/tenant identity boundary the webhook system exists to enforce: an HMAC that is supposed to prove "this event genuinely occurred for shop X" only proves "this body was produced under the app's shared secret" — it says nothing about which shop it belongs to. Any host application that follows the library's documented pattern of keying webhook handling off `WebhookMetadata#shop` (exactly as shown by the `Registry.process` call passing `shop: request.shop` into the handler) is exposed to cross-tenant forgery: an attacker-controlled merchant install can inject fabricated events attributed to a victim shop (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`), corrupting per-tenant state, triggering data deletion/GDPR flows, or otherwise acting on the victim's tenant without ever compromising the victim or the app's secret. This satisfies the Critical "cross-tenant access" bar.

### Likelihood Explanation
High. The only prerequisite is installing the app as an ordinary merchant (no privileged access, no leaked credentials, no TLS interception) and being able to send a normal HTTP POST to the app's public webhook URL — both trivially available to any internet user targeting a Shopify app. Capturing one's own valid `(body, hmac)` pair requires nothing beyond triggering a normal store event.

### Recommendation
Bind the shop identity into the verified material, e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) header in the string that is HMAC-verified, or perform a secondary authenticated check that ties the claimed shop to an installation record (e.g., cross-reference against a stored session for that shop) before trusting `request.shop`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a tenant boundary without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Shopify delivers a real webhook for that shop, e.g.:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
)
# Attacker captures (raw_body, valid_hmac) from the delivery to their own endpoint.

# Attacker now POSTs directly to the app's public webhook URL, forging the
# shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => SecureRandom.uuid,
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    and the registered handler is invoked with
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"hello"}, ...)
# The host app now processes attacker-controlled data as if it belonged to the victim shop.
``` [4](#0-3)
