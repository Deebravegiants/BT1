### Title
Webhook `shop`/`topic` identity not bound to HMAC signature, enabling cross-tenant webhook forgery/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic once the HMAC over the raw body validates, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from HTTP headers to build the `WebhookMetadata` passed to the app's handler. None of those header fields are included in the HMAC-signed content, so the cryptographic check verifies *the body only*, not the shop or topic that the app subsequently acts on.

### Finding Description
The signable content for a webhook request is defined as just the raw body: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` only checks `hmac == HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, @raw_body)`: [2](#0-1) 

`Registry.process` uses this single check as the sole authenticity gate, then reads `request.topic` (to select the handler) and `request.shop` (passed straight into the handler's data) from the same unauthenticated headers: [3](#0-2) 

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop attribution — is authenticated, which is not the case: [4](#0-3) 

**Identity binding broken:** `HMAC-verified bytes (raw body)` ≠ `shop/topic values the handler trusts and acts on (request.shop, request.topic)`.

An unprivileged attacker who installs the app on their own shop (or otherwise obtains one legitimate `(raw_body, hmac)` pair for any topic the app has registered) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. Because the shop header is not part of the signed content, `HmacValidator.validate` still succeeds, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity/data-integrity break: the app's webhook handler will act on data (e.g., updating orders, inventory, deleting records, syncing state) while believing it originates from a different merchant than the one who actually sent it, without needing the app's `api_secret_key`. Depending on the host app's handler logic, this can corrupt another tenant's data, trigger cross-tenant side effects, or be used to inject falsified events for arbitrary shops registered in the app — satisfying the cross-tenant access impact category.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action) receives at least one legitimately signed webhook body/HMAC pair for their own shop. Replaying it with a modified `shop`/`topic` header requires only a single HTTP request with `curl`-level effort; no access to the app's secret or another shop's credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or equivalently, the full header set that the handler relies on) in the value passed to `to_signable_string`, or otherwise cryptographically bind them to the verified body before they are handed to `WebhookMetadata`. At minimum, document that `shop`/`topic` are not authenticated and must not be trusted by host applications without additional verification (e.g., cross-checking against a shop that is otherwise known to have installed the app).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. topic `orders/create` with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Replay to the app's webhook endpoint:
```
curl -X POST https://victim-app.example.com/callback/orders/create \
  -H "x-shopify-topic: orders/create" \
  -H "x-shopify-hmac-sha256: H" \
  -H "x-shopify-shop-domain: victim-shop.myshopify.com" \
  -H "x-shopify-webhook-id: forged-id" \
  -H "x-shopify-api-version: 2024-01" \
  --data-binary "B"
```
3. `Utils::HmacValidator.validate` succeeds because `H` matches `HMAC(secret, B)` regardless of the `shop`/`topic` headers (`lib/shopify_api/webhooks/request.rb` L10-38, `lib/shopify_api/utils/hmac_validator.rb` L12-31).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` L188-199) dispatches the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
