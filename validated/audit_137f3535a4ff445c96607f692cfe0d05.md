### Title
POA Bridge withdrawal status matched only by assetId, causing wrong txHash / status to be reported for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`describeWithdrawal()` in the PoA bridge resolves a withdrawal's on-chain completion status by matching the POA API response purely on `assetId` (via `near_token_id`), ignoring the `index` that identifies which specific withdrawal within a batched NEAR transaction is being queried.

### Finding Description
`PoaBridge.describeWithdrawal` receives a `WithdrawalIdentifier` that includes both `tx.hash` and an `index` (meant to disambiguate multiple withdrawals created by the same NEAR transaction), but it discards the index and instead calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [1](#0-0) . `findMatchingWithdrawal` itself is documented as matching by assetId only, explicitly not supporting multiple withdrawals of the same token in one transaction [2](#0-1) . The equivalent helper in `waitForWithdrawalCompletion.ts` has the identical limitation and the identical equality check [3](#0-2) .

When a caller creates two (or more) withdrawals of the same NEP-141 asset within one NEAR transaction/intent (the SDK's public API supports arrays of `WithdrawalParams` and assigns each an `index` via `createWithdrawalIdentifier`), both `describeWithdrawal({index: 0, ...})` and `describeWithdrawal({index: 1, ...})` will resolve to the *same* array element returned by `Array.prototype.find` — the first withdrawal in the POA API's (explicitly unsorted) response list matching that assetId — regardless of which index was actually requested.

### Impact Explanation
This breaks the equality that should hold: "the status/hash reported for withdrawal N is the on-chain outcome for withdrawal N." Instead, an integrator polling withdrawal index 1 could receive the destination-chain `transfer_tx_hash` that actually belongs to withdrawal index 0 (already completed), and vice versa. Concretely:
- If withdrawal 0 is COMPLETED and withdrawal 1 is still PENDING/not yet processed, the integrator can be told that withdrawal 1 is also `completed` with withdrawal 0's `txHash`, causing the integrator to credit/mark two withdrawals as fulfilled while the second amount was never delivered.
- Conversely, a genuinely completed second withdrawal could be reported using the first withdrawal's hash, corrupting bookkeeping/reconciliation and potentially causing a double credit or a permanent inability to reconcile the second withdrawal's real completion (funds appear "stuck" from the integrator's point of view even though delivered, or credited without ever being delivered).

This matches the "status or hash misreport making an integrator credit or refund twice" bucket under High severity.

### Likelihood Explanation
Likelihood is limited to the specific scenario where a single NEAR transaction contains two or more withdrawal intents for the identical NEP-141 asset id — which the SDK's batched-withdrawal API does not prevent. It requires no malicious actor; a normal unprivileged user/integrator combining multiple withdrawals of the same token in one batch triggers it. The code comments confirm the authors are aware this case is unhandled ("multiple withdrawals of the same token in a single transaction are not supported"), which corroborates the root cause but does not mitigate the impact for any caller that does perform such a batch today.

### Recommendation
Disambiguate withdrawals of the same asset by more than `assetId`: use amount ordering (per the code's own suggestion) or an explicit correlation identifier from the POA API/transaction (e.g., an ordinal per-asset counter, or amount-sorted matching consistent with the order withdrawals were created), and reject/guard batches with duplicate asset withdrawals until the POA API can disambiguate them, rather than silently returning a status that may belong to a different withdrawal.

### Proof of Concept
1. Build a batch of two withdrawals with the same `assetId` (e.g., `nep141:btc.omft.near`) in one NEAR transaction, generating identifiers with `index: 0` and `index: 1` via `PoaBridge.createWithdrawalIdentifier`.
2. The POA `getWithdrawalStatus` API returns an unsorted `withdrawals` array containing two entries, both with `near_token_id: "btc.omft.near"` but different `transfer_tx_hash` values (one COMPLETED, one PENDING).
3. Call `describeWithdrawal` for `index: 0` and `index: 1`. Both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns `withdrawals[0]` in both cases (the same object), regardless of which `index` was passed — confirmed by the existing test comment "Response list is unsorted, so we match by assetId instead of index" [4](#0-3)  and the test suite's assertion that matching is done purely "by assetId, not by index" [5](#0-4) .
4. Result: the second (distinct) withdrawal's status/hash is misreported as identical to the first.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
