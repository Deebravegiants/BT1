### Title
Webhook HMAC only covers the raw body, letting an attacker-controlled `shop`-domain header spoof cross-tenant webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` value that is subsequently handed to the host application's webhook handler (and used to attribute the payload to a tenant) is read from an HTTP header that is never included in the signed bytes, so it can be modified without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate header (`shop-domain`) that plays no part in the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC and then dispatches the handler using `request.shop` straight from that unauthenticated header: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (here, just the body) against the HMAC: [4](#0-3) 

The binding that should hold is:
`hmac == HMAC(secret, body ‖ shop)`

but the gem only enforces:
`hmac == HMAC(secret, body)`

leaving `shop` (the tenant identity) completely outside the authenticated bytes, exactly matching the reported bug class of "a field acted on but not covered by the HMAC."

Because any legitimate merchant who installs the app receives genuine webhook deliveries — with a valid `X-Shopify-Hmac-Sha256` computed over their own event body using the app's real `client_secret` — that merchant (an unprivileged internet user with respect to *other* tenants of the app) can capture one such webhook request and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain, while leaving body and HMAC untouched. `HmacValidator.validate` still returns `true` (body/signature match), yet `Registry.process` will call the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim's domain.

### Impact Explanation
This breaks the identity binding `authenticated_body == shop_the_data_is_attributed_to`. A host application that keys any tenant-scoped action (e.g., updating per-shop state, triggering per-shop side effects, looking up per-shop settings) off `WebhookMetadata#shop` will process attacker-supplied body content under a different tenant's identity — a cross-tenant access/data-integrity violation, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High/likely for any real deployment that accepts webhooks from third parties or where the attacker can install the app on their own store (a normal, unprivileged flow for any public Shopify app): they need no special access beyond installing the app once to obtain valid, freely replayable (body, hmac) pairs, and no `client_secret` or access token is required to mount the attack — only network access to the app's public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is actually verified, e.g. include the shop-domain header in `to_signable_string`, or independently confirm that `request.shop` matches an already-established, trusted session/shop record for the given topic before invoking the handler, rather than trusting the unauthenticated header value.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to.
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent for that delivery (valid, since it was genuinely signed with the app's `client_secret`).
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) returns `true` because only the body is checked.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
