### Title
HOT Bridge API fallback reports withdrawal as "completed" without checking `verified_withdraw` flag - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.describeWithdrawal` falls back to the HOT REST API (`fetchWithdrawalHashFromApi`) to determine whether a withdrawal has landed on the destination chain. The API response schema explicitly parses a `verified_withdraw` boolean field per withdrawal, but that field is never inspected before the SDK reports the withdrawal as `"completed"`.

### Finding Description
`HotApiWithdrawalSchema` declares `verified_withdraw: v.boolean()` as part of the parsed withdrawal object: [1](#0-0) 

`fetchWithdrawalHashFromApi` finds the matching withdrawal by nonce and returns its `hash` as soon as it is present and well-formed hex, without ever reading `withdrawal.verified_withdraw`: [2](#0-1) 

The result is then propagated directly into a `"completed"` `WithdrawalStatus` by the caller in `describeWithdrawal`, both in the EVM/Stellar/TON bridge-indexer-failure fallback branch and in the "other non-EVM networks" fallback branch: [3](#0-2) [4](#0-3) 

This breaks the equality the report's bug class targets: the reported status ("completed") does not necessarily match the true on-chain/verified outcome, since the schema's own `verified_withdraw` flag — which exists specifically to signal whether the withdrawal has been cryptographically/on-chain verified — is discarded. The primary bridge-indexer path (`fetchWithdrawalHashBridgeIndexer`) doesn't have this field at all, so this gap is specific to the HOT-API fallback path used when the indexer errors out or for non-EVM/non-Stellar/non-TON chains.

### Impact Explanation
Callers (integrators, `watchWithdrawal`/`createWithdrawalCompletionPromises`) treat `{status: "completed", txHash}` as the on-chain outcome and typically release/credit funds or mark the flow as done based on it. If the HOT API returns a hash for a withdrawal whose `verified_withdraw` is `false` (i.e., not yet confirmed as executed correctly on the destination chain), the SDK will still report it as completed, matching the report's "status reported that is not the on-chain outcome" pattern and aligning with the High-severity category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path is only reached when the bridge indexer fails/errors (for EVM/Stellar chains) or as a fallback for other non-EVM chains when the contract view returns null/pending — not on the happy path. It also depends on the HOT API actually returning `verified_withdraw: false` together with a non-empty hash, a real-world condition governed by HOT's off-chain relayer/indexer behavior, which I cannot independently confirm ever occurs from this repo alone (out-of-scope trust in the bridge/relayer API per the rules). Root cause (schema parses but never uses the field) is proven directly by the code above.

### Recommendation
Reject the HOT API's hash as evidence of completion unless `withdrawal.verified_withdraw === true`; otherwise treat the withdrawal as still `"pending"`, consistent with how the bridge-indexer path is already treated as the authoritative/verified source.

### Proof of Concept
1. Trigger the fallback path (bridge indexer fails for an EVM asset, or use a non-EVM/non-TON/non-Stellar landing chain where the contract view returns null).
2. Mock `hotSdk.api.requestApi` to return a withdrawals array entry with `hash: "0xDEADBEEF"`, matching `nonce`, and `verified_withdraw: false`.
3. Call `bridge.describeWithdrawal(wid)`.
4. Observe the result is `{status: "completed", txHash: "0xDEADBEEF"}` even though `verified_withdraw` is `false` — identical in effect to the existing passing test at [5](#0-4) 
which only varies `hash`/`chain_id`/format, never `verified_withdraw`, confirming the field is not gating the outcome.

	private async fetchWithdrawalHashFromApi(
		nearTxHash: string,
		nonce: bigint,
		logger?: ILogger,
	): Promise<string | null> {
		try {
			const response = await withTimeout(
				() =>
					this.hotSdk.api.requestApi(
						`/api/v1/evm/bridge_withdrawal_hash?near_trx=${nearTxHash}`,
						{ method: "GET" },
					),
				{ timeout: HotBridge.API_FALLBACK_TIMEOUT_MS },
			);
			const data: unknown = await response.json();

			const parseResult = v.safeParse(HotApiWithdrawalResponseSchema, data);
			if (!parseResult.success) {
				logger?.debug("HOT API response parse failed", {
					issues: parseResult.issues,
				});
				return null;
			}

			const withdrawal = parseResult.output.withdrawals.find(
				(w) => w.nonce === nonce.toString(),
			);

			if (withdrawal?.hash) {
				const hash = withdrawal.hash.replace(/^0x/, "");
				if (isHex(hash)) {
					logger?.info("HOT withdrawal hash found via API fallback", {
						nearTxHash,
						nonce: nonce.toString(),
					});
					return hash;
				}
			}
			return null;
		} catch (error) {
			logger?.debug("HOT API fallback failed", { error, nearTxHash });
			return null;
		}
	}
