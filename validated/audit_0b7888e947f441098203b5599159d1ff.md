### Title
Front-runnable deterministic lockup address permanently blocks legitimate lockup creation for a target owner - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the address of the new lockup account deterministically from the caller-supplied `owner_account_id` and never checks whether that account already exists before issuing `create_account()`. [1](#0-0)  Because `create()` is a public, unprivileged entry point that accepts an arbitrary `owner_account_id`, anyone can pre-claim the exact deterministic subaccount that a victim (e.g. the NEAR Foundation) intends to use for a specific employee/owner, permanently preventing the real, correctly-configured lockup from ever being deployed at that address.

### Finding Description
The lockup account ID is computed purely from a hash of `owner_account_id`, with no randomness, salt, or caller binding:

```rust
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id =
    format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [2](#0-1) 

`create()` is `#[payable]` and callable by any account with the minimum attached deposit; it does not verify that `env::predecessor_account_id()` is related to `owner_account_id`, nor does it track/reserve `lockup_account_id` before attempting creation (unlike `staking-pool-factory`, which explicitly reserves the derived ID with `self.staking_pool_account_ids.insert(&staking_pool_account_id)` before the creation promise [3](#0-2) ). The lockup-factory simply fires the creation promise directly:

```rust
Promise::new(lockup_account_id.clone())
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(b"new".to_vec(), ... )
    .then(ext_self::on_lockup_create(...))
``` [4](#0-3) 

Since NEAR's `CreateAccount` action fails if the target subaccount already exists, whichever call reaches this deterministic address first "wins," and every subsequent `create()` call for the same `owner_account_id` will have its promise fail; the attached deposit is then simply refunded to the caller in `on_lockup_create` [5](#0-4) . The account itself, however, remains permanently occupied by whatever was deployed in the first successful call — there is no `init_if_needed`-equivalent or reuse path, so the legitimate lockup for that owner can never be created afterwards. This is the direct analog of the reported `InitializeNFTAccount` issue: a deterministically-derived, single-use account address with no collision guard, reachable by any unprivileged caller supplying attacker-controlled input (here, `owner_account_id` instead of an NFT mint).

An attacker can exploit this by calling `create()` themselves first, supplying the victim's intended `owner_account_id`, minimal deposit, no vesting schedule, and `lockup_duration = 0` / transfers already enabled, thereby permanently squatting the address before the Foundation's real, correctly-vested lockup transaction lands.

### Impact Explanation
This breaks the "account-binding"/single-execution guarantee of the lockup creation flow: an unprivileged party can bind a specific owner's deterministic lockup address to their own bogus, minimally-funded lockup contract, permanently denying the intended vesting lockup from ever being created for that owner. This matches the in-scope "High" impact category of account-binding failure in pool/lockup-creation flows that breaks single-execution/rightful-creation guarantees, since the legitimate owner/foundation can never redeem the intended lockup+vesting terms at the expected address.

### Likelihood Explanation
Likelihood is high and requires no privilege: `create()` is a public payable method, `owner_account_id` is fully attacker-supplied, and the required deposit is only the `MIN_ATTACHED_BALANCE` (3.5 NEAR) [6](#0-5) . Any observer of a pending/expected lockup creation for a known employee account can front-run it trivially since the derived address is fully predictable off-chain.

### Recommendation
Before issuing `create_account()`, verify uniqueness (e.g., maintain and check a persisted set of already-created/claimed `lockup_account_id`s similar to the staking-pool-factory's `staking_pool_account_ids` guard), and/or bind account creation rights to a trusted caller (e.g., restrict `create()` for accounts with vesting to be callable only by the foundation, or require the caller to equal/authorize `owner_account_id`) so an unrelated unprivileged party cannot pre-claim another user's deterministic lockup address.

### Proof of Concept
1. Foundation intends to create a vesting lockup for `alice.near` via `lockup-factory.create(owner_account_id="alice.near", vesting_schedule=Some(...), ...)`.
2. Before the Foundation's transaction lands, an attacker calls `lockup-factory.create(owner_account_id="alice.near", vesting_schedule=None, lockup_duration=0, ...)` with the minimum deposit.
3. The attacker's call computes the same deterministic address `sha256("alice.near")[..20].lockup-factory.near` [2](#0-1)  and successfully creates it first.
4. When the Foundation's legitimate `create()` call executes, `create_account()` fails because the account already exists; `on_lockup_create` refunds the Foundation's deposit but the address remains permanently occupied by the attacker's bogus lockup [7](#0-6) , so the intended vested lockup for `alice.near` can never be deployed.

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
