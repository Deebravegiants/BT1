## Finding: Webhook `shop` (and topic/webhook_id) fields are not covered by the HMAC signature used to authenticate the webhook

### Title
Webhook shop-domain spoofing via HMAC that only signs the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook using `Utils::HmacValidator.validate`, which recomputes an HMAC over `to_signable_string` and compares it to the `hmac` field. However, `to_signable_string` returns only the raw request body, while the `shop` (and `topic`/`webhook_id`) values that are handed to the app's webhook handler come from separate, unsigned headers. This breaks the identity binding `HMAC(secret, verified_bytes) == received_hmac` versus the `shop` value that downstream code trusts to attribute the payload to a tenant.

### Finding Description
`HmacValidator.validate_signature` computes the signature strictly from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to return only the raw body, while `shop`, `topic`, and `webhook_id` are read from separate headers that are never included in the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (an unsigned field) to the app's handler as the tenant identifier for the webhook: [3](#0-2) 

Because the HMAC only binds the raw body bytes to the secret, it says nothing about which `shop-domain` header accompanied those bytes. Any request whose body+hmac pair is valid for the shared `api_secret_key` can be replayed with an arbitrary `x-shopify-shop-domain` header, and `HmacValidator.validate` will still return `true`, because the equality it checks (`HMAC(secret, raw_body) == received_hmac`) never included `shop` in the first place.

### Impact Explanation
An attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's shared secret (e.g., by installing the app on their own store and capturing a real webhook Shopify sends them) can resend that exact body/hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Registry.process` will treat the HMAC as valid and dispatch `WebhookMetadata` with `shop` set to the victim's domain, causing the app-level handler to process attacker-influenced payload data attributed to a shop the attacker does not control - a cross-tenant confusion/integrity issue, since nothing in the gem's signature verification binds the `shop` claim to the signed bytes.

### Likelihood Explanation
Requires only that the attacker be an ordinary merchant/developer who can install the target app on any shop they control and capture one legitimate webhook delivery for it - no access to `api_secret_key`, access tokens, or privileged accounts is needed. This is a realistic, low-privilege capability for a public app.

### Recommendation
Include the `shop` (and, ideally, `topic`/`webhook_id`) values in the bytes that are HMAC-verified, or independently verify that the `shop` header corresponds to a shop the app actually has an active installation/session for before dispatching to the handler, rather than trusting the header value on its own once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay the exact same request to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (keep body `B` and header `H` unchanged).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only returns `B`, and `HMAC(secret, B) == H` still holds.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's payload as if it originated from the victim shop.
