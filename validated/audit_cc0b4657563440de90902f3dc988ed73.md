Based on the documentation, the gem's own docs explicitly state: "This will verify the request did indeed come from Shopify" [1](#0-0) , and it advertises `data.shop` as a trusted field the handler can safely dispatch business logic on (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [2](#0-1) . This is the exact "field acted on but not covered by the HMAC" binding break the rules call out as in-scope.

### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, never over the `shop-domain` header, yet `ShopifyAPI::Webhooks::Registry.process` trusts that same unauthenticated header as the tenant identity passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload [4](#0-3) . `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it against the `hmac-sha256` header using `OpenSSL.secure_compare` [5](#0-4) . `Registry.process` raises only if the HMAC check on the body fails, then immediately constructs `WebhookMetadata` using `request.shop` — the header value that was never part of the signed material — and hands it to the app's handler as the trusted shop identity [6](#0-5) .

The `api_secret_key` used to verify the HMAC is a single, app-wide secret shared across every shop that installs the app (it's the same value used everywhere in `Context`) — it is not per-shop. Consequently, any actor who can obtain one validly-signed `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store, a trivial free/dev-store action requiring no privileged credential) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. Because the header is outside the signed material, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the app's handler believing the event originated from the victim shop.

### Impact Explanation
This breaks the equality the gem's own documentation promises the host app: "authenticated body signature" == "authenticated shop identity". The docs explicitly tell integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is the safe, verified shop identity to key business logic and job dispatch on [7](#0-6) . An attacker exploiting this gap can attribute forged/replayed webhook events to a victim shop domain, enabling cross-tenant data confusion in any app that follows this documented pattern (e.g., enqueuing jobs keyed by `shop_domain`, updating per-shop state, or triggering shop-specific side effects) without ever needing the victim's access token or credentials.

### Likelihood Explanation
Any unprivileged internet user can install the target app on a store they control (or otherwise obtain one legitimately-signed webhook body/HMAC pair from Shopify for the shared app secret), then replay that same body and HMAC against the app's public webhook endpoint with a forged `shop-domain` header pointing at any victim shop. No access token, `client_secret`, or privileged account is required — only a body+HMAC pair the attacker legitimately received once.

### Recommendation
Bind the shop identity into the verified material: either include the shop domain in the HMAC-signed content (not currently possible since Shopify signs only the body), maintain a per-app allow-list of shops with active installations/sessions and reject webhooks whose `shop-domain` header doesn't match a known, previously-OAuth'd shop, or otherwise document unambiguously (and enforce in `Registry.process`) that `data.shop` must be cross-validated by the host app against its own session store before being trusted for any tenant-scoped action.

### Proof of Concept
1. Install the app (attacker's own store) or otherwise capture one legitimate webhook delivery, e.g. `raw_body = "{...attacker shop event...}"` with header `x-shopify-hmac-sha256: <valid-hmac-of-raw_body-with-shared-secret>`.
2. Replay the request to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` passes because it only checks `raw_body` against the shared secret [8](#0-7) .
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the handler [6](#0-5) , causing the app to act as if the event came from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
```
