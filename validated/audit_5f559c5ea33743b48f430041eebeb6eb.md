### Title
Webhook `shop-domain` header (and `topic`/`webhook-id`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's shared `api_secret_key` [2](#0-1) . The tenant identity used downstream — `request.shop`, taken straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2)  — is never part of what is hashed. `Registry.process` verifies the HMAC and then immediately hands the caller-controlled `request.shop` to the handler as the merchant identity for the payload [4](#0-3) .

### Finding Description
The binding that should hold is:
`hmac_verified(shop) == shop_used_by_handler`

but the actual binding is:
`hmac_verified(raw_body) ; shop_used_by_handler = shopify_header("shop-domain")` — i.e. the shop identity is parsed from bytes that were never verified.

Because `api_secret_key` is a single secret shared by the app across *all* installing shops (it is the app's client secret, not a per-shop secret), any unprivileged merchant who installs the vulnerable app on their own store legitimately receives real webhook deliveries with valid `(body, hmac)` pairs signed by that shared secret. That attacker-merchant can then replay the exact same `raw_body` + `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or the `X-Shopify-Topic` / `X-Shopify-Webhook-Id` headers, which are equally unauthenticated). `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `@raw_body`, which is unchanged [5](#0-4) . `Registry.process` then dispatches to the topic handler with `WebhookMetadata` built from the attacker-chosen `shop`, `topic`, and `webhook_id` values, all "verified" only because the body check passed [4](#0-3) .

This is the same bug class as the analog report: a value is used to make a security-relevant decision (which tenant this data belongs to) after/without being covered by the integrity check that is supposed to authenticate it, exactly the way `GovernanceHYBR` used a not-yet-consistent `totalAssets()` value to compute shares.

### Impact Explanation
A host application built on this gem is expected to trust `WebhookMetadata#shop` as the authenticated tenant for the payload — this is the gem's entire documented purpose for webhook handling. Since the shop identity is forgeable by any unprivileged attacker with a legitimate app install and a valid HMAC/body pair from their own shop, the attacker can inject data attributed to an arbitrary victim shop domain into the host app's per-tenant handler logic (e.g., writing "victim shop's" order/customer records, triggering tenant-scoped side effects, or corrupting per-shop caches/state). This crosses a tenant boundary using no privileged credentials and no interception — a Critical cross-tenant issue per the given rubric.

### Likelihood Explanation
Any account that can install the app (an ordinary, unprivileged Shopify merchant/dev-store owner) can capture a valid `(raw_body, hmac)` pair from their own genuine webhook deliveries, since `api_secret_key` is shared across all shops that install the same app. Forging the HTTP headers (`shop-domain`, `topic`, `webhook-id`) on a replayed POST to the public webhook endpoint requires no cryptographic material at all. Likelihood is high — this requires only normal API use plus a raw HTTP client.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the header values to the verified request, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (if Shopify's signature scheme allows it), or
- Have `Registry.process`/callers cross-check `request.shop` against a shop the app actually has a stored session/access token for before invoking the handler, rejecting shops unknown to the app, or
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** authenticated by the HMAC check and that host apps must independently verify the shop is one they have installed/authorized before trusting the payload's tenant attribution.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. Server calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds [6](#0-5) .
5. The topic handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed(B), ...)` [7](#0-6)  — the host app processes attacker-controlled data as belonging to the victim shop.
