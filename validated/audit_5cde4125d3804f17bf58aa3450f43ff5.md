### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC signature it validates from the raw request body only, while the `shop` value it exposes to the application (and to the app's webhook handler) is taken from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. `Registry.process` accepts the webhook as long as `Utils::HmacValidator.validate(request)` passes, but that check never binds the `shop` value to the signature, so `shop` can be forged independently of a valid HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signed material: [2](#0-1) 

`Registry.process` validates the webhook purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header — the `shop` header plays no role in this comparison: [3](#0-2) [4](#0-3) 

After validation succeeds, `request.shop` is forwarded, unverified against the signature, straight into `WebhookMetadata` and handed to the host application's `WebhookHandler#handle`, which is the only tenant identifier the handler receives: [5](#0-4) [6](#0-5) 

The equality that should hold — "the `shop` value trusted by the handler == the `shop` value cryptographically bound to the signed payload" — does not hold. Before the request: an attacker who owns any (even free/dev) Shopify store can receive a genuine, correctly-HMAC-signed webhook for their own shop. After the request: the attacker resends the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body/hmac pair, unchanged), and `Registry.process` passes `request.shop` == the attacker-supplied victim domain to the handler as if it were authenticated.

### Impact Explanation
This breaks the shop/tenant binding that webhook handlers rely on to decide which merchant's data to read, write, or delete (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific handlers keyed by `data.shop`). An attacker with no privileges beyond controlling one legitimate (even free trial) shop can cause the app to process attacker-controlled webhook bodies under the identity of an arbitrary other shop, resulting in cross-tenant data corruption or disclosure depending on how the host app's handler consumes `WebhookMetadata#shop`. This matches the "cross-tenant access" criticality bucket, since the gem itself supplies no protection against shop spoofing once a valid body/HMAC pair is obtained.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` (the only shop identifier the gem exposes) without independently re-deriving the shop from a signed source. No access token, `client_secret`, or privileged account is required — only the ability to receive one legitimate webhook to the attacker's own shop (trivial to obtain by installing the app, or any app, on a free development store) and the ability to POST directly to the app's public webhook endpoint with custom headers.

### Recommendation
Include the shop domain (and ideally topic/api-version) as part of the signed material that `Utils::HmacValidator` verifies for webhooks, or require host applications to re-verify `request.shop` against a value obtained through an already-authenticated channel (e.g., a shop known from an existing session) before trusting it. At minimum, document explicitly that `WebhookMetadata#shop` is unauthenticated and must not be used as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own (free/dev) Shopify store and triggers any webhook subscription, capturing a real `raw_body` and its corresponding `X-Shopify-Hmac-Sha256` header value.
2. Attacker sends a POST to the app's webhook endpoint with the identical `raw_body` and `hmac-sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC header (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and performs its logic (e.g., record deletion/update) against the victim shop's tenant data, despite the payload having originated from, and been signed for, the attacker's own shop.
