### Title
Webhook shop-domain header not covered by HMAC allows tenant-spoofing of `WebhookMetadata#shop` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw body only (`to_signable_string` returns `@raw_body`), while the shop identity (`shop-domain` header) that `Registry.process` hands to the app's webhook handler is read from a separate, unauthenticated header. Any attacker who can obtain one genuinely-signed `(raw_body, hmac)` pair from Shopify — trivially available by installing the app on their own store and receiving one webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` will report the request as valid because it never inspects the header, and the handler will be invoked with `WebhookMetadata#shop` set to the attacker's chosen victim shop.

### Finding Description
The binding that should hold is: `hmac-signed bytes == bytes used to authorize the security-relevant field`. Here it doesn't:
- `Request#hmac` reads `shopify-hmac-sha256` and `Request#to_signable_string` returns `@raw_body` only [4](#0-3) .
- `Request#shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed string [5](#0-4) .
- `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`, so it authenticates only the body bytes, never the shop header [6](#0-5) .
- `Registry.process` calls `Utils::HmacValidator.validate(request)` and, on success, immediately builds `WebhookMetadata.new(... shop: request.shop ...)` from the untrusted header and dispatches it to the app's handler [2](#0-1) .

Because a single app's `api_secret_key` is shared across every shop that installs it, a genuine `(body, hmac)` pair obtained from a webhook delivered to the attacker's own store passes `validate()` regardless of which `shop-domain` value is presented alongside it. The gem's own webhook guide instructs integrators to treat `data.shop` as the trusted tenant identifier for dispatch/lookup (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not a documented "host app must additionally validate" caveat — the gem's `process` API is presented as already having verified the request came from Shopify for that shop [7](#0-6) .

### Impact Explanation
This breaks the tenant/shop identity binding that `Registry.process`/`WebhookMetadata` is meant to guarantee. An unprivileged attacker who merely installs the vulnerable app on their own store (a normal, credential-free action for any public app) can craft webhook deliveries that are cryptographically valid per this gem's check yet are attributed to a victim shop of the attacker's choosing. Any app that uses `data.shop` from a processed webhook to select which merchant's data/session to update — which is the exact pattern this gem's documentation recommends — is exposed to cross-tenant data corruption or spoofed events attributed to a shop the attacker does not control.

### Likelihood Explanation
High reachability: registering an app instance for the attacker's own store and capturing one legitimate webhook delivery is trivial and needs no special privilege or leaked secret. Replaying the body with a modified header is a basic HTTP replay, no access to `api_secret_key` is required by the attacker.

### Recommendation
Include the shop-domain (and ideally topic/api-version/webhook-id) header value in the signed string, or otherwise cryptographically bind `shop` to the payload before trusting it in `WebhookMetadata`. At minimum, document prominently that `Registry.process`/`WebhookMetadata#shop` is not itself sufficient to establish tenant identity and that callers must independently verify the shop is one they have on record with a matching, currently-active webhook subscription/session before acting on the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with a genuine `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `api_secret_key`, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
4. Attacker sends this identical `(raw_body, hmac)` pair directly to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only validates `raw_body` against the HMAC [8](#0-7) .
6. The registered handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, even though Shopify never sent this event for `victim-shop`.
