### Title
JWT replay guard in `WorkflowMetadataHandler.Authorize` is check-then-act, not atomic, allowing a single-use trigger token to authorize two concurrent workflow executions - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`WorkflowMetadataHandler.Authorize` is the function that authenticates every inbound HTTP-trigger request from an unprivileged workflow caller, verifying the request JWT and enforcing single-use ("replay protection") semantics via `jwtReplayCache`. The check (`isReplay`) and the state update (`recordUsage`) are two separate, independently-locked operations rather than one atomic operation, exactly the same class of bug as the report's root cause: a state-changing action (settling an epoch / consuming a withdrawal) is allowed to proceed a second time because the guard that should block re-use is evaluated against stale state instead of atomically claiming it. [1](#0-0) 

### Finding Description
`Authorize` first checks `h.jwtCache.isReplay(claims.ID)` under the cache's `RLock`, and only much later — after authorized-key lookups — calls `h.jwtCache.recordUsage(claims.ID)` under a separate `Lock`: [2](#0-1) 

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()
	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	cache.cache[jti] = time.Now()
}
``` [3](#0-2) 

If two requests carrying the same JWT (same `jti`) arrive concurrently — trivially achievable by an unprivileged client replaying its own signed trigger request twice in parallel, or by network-level duplication/retry of the HTTP trigger request — both goroutines can execute `isReplay` before either has called `recordUsage`. Both see `exists == false`, both pass the "already used" check, and both proceed to authorize and (via the caller, `HandleUserTriggerRequest` in `http_trigger_handler.go`) dispatch the trigger to the DON, causing the workflow to be executed twice from a single signed authorization. This mirrors the Rio report's root cause: a one-shot state transition (settle-once / use-once) is guarded by a check that is evaluated separately from, and racing against, the write that should make the guard effective — the "aggregateRoot"/`settled` flag check in the Sherlock report versus the `isReplay`/`recordUsage` check here.

Note that a comparable, correctly-atomic guard exists elsewhere in the same codebase — `vault.RequestReplayGuard.CheckAndRecord` performs the check-and-record under a single lock in one function — which supports that the split `isReplay`/`recordUsage` pattern in `jwtReplayCache` is the outlier and the actual defect: [4](#0-3) 

### Impact Explanation
Successful exploitation lets a single signed, single-use trigger JWT authorize more than one workflow execution. Depending on the workflow's side effects (e.g., triggering on-chain actions, fund transfers, or job runs through the HTTP Trigger capability), this results in an unauthorized/duplicate job run stemming purely from an authentication/replay-guard bypass — the exact class of impact this analysis is scoped to accept (unauthorized job run from an authentication bypass). It does not require any privileged or malicious-node behavior; it is achievable entirely from the ordinary unprivileged caller side of the internet-facing gateway path.

### Likelihood Explanation
The race window is small but real: it requires two authorization attempts with identical `jti` to land between the `isReplay` read and the corresponding `recordUsage` write. This is plausible via a client-side double-send (deliberate or a naive retry-on-timeout client), and is trivially reproducible by an attacker deliberately firing the same signed request twice in quick succession over two connections. No cryptographic break or trusted node compromise is needed — likelihood is moderate but the exploit is entirely unprivileged-actor driven.

### Recommendation
Make the check-and-record operation atomic under a single critical section, matching the pattern used by `vault.RequestReplayGuard.CheckAndRecord`:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	if _, exists := cache.cache[jti]; exists {
		return false
	}
	cache.cache[jti] = time.Now()
	return true
}
```
and have `Authorize` call this single atomic method instead of separate `isReplay`/`recordUsage` calls, reserving the `jti` before any further authorization work proceeds.

### Proof of Concept
1. Client obtains one valid, signed HTTP-trigger JSON-RPC request with JWT claim `jti = X` for a registered workflow.
2. Client sends two copies of this exact request concurrently to the gateway (e.g., via two parallel HTTP connections), both reaching `WorkflowMetadataHandler.Authorize`.
3. Goroutine A calls `isReplay(X)` → false (not yet recorded). Before A calls `recordUsage(X)`, Goroutine B also calls `isReplay(X)` → false.
4. Both A and B pass the replay check, pass the authorized-key check, and both call `recordUsage(X)` (idempotent, no error). Both return a valid `*gateway.AuthorizedKey`.
5. The caller in `http_trigger_handler.go` (`HandleUserTriggerRequest`) proceeds to dispatch the trigger to DON nodes twice for what was supposed to be a single-use authorized request, causing duplicate workflow execution from one JWT.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
