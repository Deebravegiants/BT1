### Title
RAY-scaled value multiplication overflows before the borrow-index cap and permanently freezes a large market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts total scaled supply and debt to their original RAY values before the borrow-index ceiling can stop further growth, and each conversion multiplies `scaled * index` in `i128`. For a sufficiently large market, the index can exceed `i128::MAX / scaled` while remaining far below `MAX_BORROW_INDEX_RAY`, so every subsequent accrual panics with `MathOverflow`. [1](#0-0) [2](#0-1) 

### Finding Description
The pool accrues interest by calling `accrue_step` for each elapsed chunk, and `accrue_step` first computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [3](#0-2) [1](#0-0) 

`scaled_to_original` is implemented as `scaled.mul(index)`, which panics when the resulting RAY value cannot fit in `i128`. [4](#0-3) 

The later call to `update_borrow_index` does cap the index, but only after multiplying the old index by the new interest factor and returning the capped result; that cap does not prevent the already-overflowing debt or supply valuation performed earlier in the next accrual. [2](#0-1) 

The static index ceiling is `1e36`, while an `i128` RAY-valued market total can overflow at an effective index of roughly `i128::MAX / scaled`, so a large scaled book reaches its dynamic overflow boundary long before the static index ceiling. [5](#0-4) 

The production path is reachable through the controller’s normal `supply` and `borrow` flows, followed by anyone calling `update_indexes`; the controller forwards that call to the owner-gated pool `update_indexes`, which invokes `ops::market::accrue` and `global_sync`. [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
Once the multiplication overflows, `update_indexes` cannot advance the market because accrual aborts before committing the new state. The same accrual runs before market mutations, so ordinary withdrawals and repayments also revert with `MathOverflow`; the repository’s regression test demonstrates that both paths fail after the cliff. [9](#0-8) [10](#0-9) 

This permanently freezes suppliers’ funds and blocks debt repayment or liquidation through the unprivileged protocol paths. Governance cannot recover by merely lowering the rate model, because `update_params` accrues the old model before writing replacement parameters and therefore hits the same overflow first. [11](#0-10) 

### Likelihood Explanation
Likelihood is conditional rather than trivial because the attacker must create or use a market with extremely large token liquidity and sustain enough interest growth for the index to cross the dynamic `i128` boundary. The existing test uses an 18-decimal market, supplies one billion whole tokens, borrows 98% of that liquidity, repeatedly advances time, and reaches `MathOverflow` before `MAX_BORROW_INDEX_RAY`. [12](#0-11) [13](#0-12) 

An unprivileged borrower or supplier cannot directly choose privileged market parameters, but they can reach this state in any already-supported market whose token supply and caps admit the required position size. The attacker does not need a malicious token, privileged role, leaked key, or external oracle manipulation. [14](#0-13) 

### Recommendation
Make accrual overflow-safe before materializing scaled totals as `i128` values.

- Compute utilization and accrued totals with `I256` intermediates, or compare the scaled product against a market-specific ceiling before converting it to `i128`.
- Clamp the borrow index to `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed.raw())` before calculating supplier rewards, and apply the analogous supply bound using `supply_index` and `supplied`.
- Add a fail-safe early return once the applicable index cap is reached, avoiding utilization and reward computation on a capped market.
- Enforce the same dynamic bound when minting supply or debt shares so a market cannot enter a state whose next accrual is mathematically unrepresentable.
- Extend the existing long-horizon test to assert that `update_indexes`, `repay`, `withdraw`, and liquidation remain executable at the configured index ceiling.

### Proof of Concept
The following sequence is reflected by `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

```text
1. Use an existing 18-decimal market with high utilization allowed.
2. As an unprivileged supplier:
   controller.supply(
       supplier,
       account_id = 0,
       spoke_id,
       [(HubAssetKey { hub_id, asset }, 1_000_000_000 * 10^18)]
   )

3. As an unprivileged borrower with sufficient collateral:
   controller.borrow(
       borrower,
       borrower_account_id,
       [(HubAssetKey { hub_id, asset }, 980_000_000 * 10^18)],
       receiver = None
   )

4. Periodically invoke:
   controller.update_indexes(caller, [HubAssetKey { hub_id, asset }])

5. Eventually `accrue_step` evaluates:
   scaled_to_original(borrowed, borrow_index)
   => borrowed.mul(borrow_index)
   => MathOverflow

6. Subsequent controller operations touching that market, including
   withdraw and repay, run the same accrual first and revert.
```

The test asserts that `update_indexes` fails while `borrow_index < MAX_BORROW_INDEX_RAY`, then confirms `withdraw` and `repay` also fail with `MathOverflow`. [10](#0-9)
