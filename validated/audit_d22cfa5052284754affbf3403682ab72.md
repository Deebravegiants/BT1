### Title
Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the `X-Shopify-Shop-Domain` header value unauthenticated, while `HmacValidator.validate` only checks the HMAC against `to_signable_string`, which is the raw body only. The binding `authenticated_bytes == shop_used_for_tenant_routing` never holds: the shop identity that determines which merchant's session/data a webhook handler dispatches to is not part of the HMAC-verified data.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively; the HMAC verified via `Utils::HmacValidator.validate` (`OpenSSL.secure_compare(computed_signature, received_signature)`) is computed only over that body string. `Request#shop` and `Request#topic`/`webhook_id`/`api_version` are all read straight from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`), which are not included in the signed payload at all. [3](#0-2) [4](#0-3) 

This mirrors the reported bug class: a field ("shop") that application code acts on for tenant identification is not covered by the cryptographic check ("bytes verified" = raw body, "bytes acted on" = header `shop-domain`) — exactly the "bytes verified versus bytes parsed" mismatch called out in the rules. Any component consuming `Request#shop` (e.g., to select which merchant session/token to use, or to route webhook data) is trusting a header that could be set independently of the signed body.

### Impact Explanation
If an app's webhook handler uses `request.shop` to decide which merchant record/session to update (a common integration pattern with this gem, since the gem exposes exactly `shop`, `topic`, and `parsed_body` for that purpose), an attacker who can produce any validly-HMAC'd body (e.g., replaying a legitimately signed payload for their own store, since HMAC secret is the same `client_secret` shared across all shops of the app) can pair it with an arbitrary `X-Shopify-Shop-Domain` header. The signature still validates because the header is not part of the signed bytes, letting the attacker's webhook body be attributed to a different shop — a cross-tenant identity confusion.

### Likelihood Explanation
Exploitability requires the attacker to control or spoof the `X-Shopify-Shop-Domain` header while still supplying a body/HMAC pair that validates for the app's `client_secret`. Since the HMAC secret (`api_secret_key`/`client_secret`) is shared across all shops that install the same app, and Shopify signs webhooks using that same shared secret for every shop, any shop that has legitimately received one signed webhook can reuse that exact `(body, hmac)` pair while forging the `shop-domain` header (headers are attacker-controlled at the HTTP layer, e.g. via a malicious middlebox, replay tooling, or a host application that doesn't independently re-verify headers). This is a plausible if not trivial path, and is entirely inside the gem's own `Request`/`HmacValidator` design rather than a host-app misuse.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header values in the HMAC-covered signable string, or independently verify that the shop-domain header corresponds to a shop session actually provisioned for this `api_secret_key`/app before trusting `Request#shop` for any tenant-scoping decision. At minimum, document that `shop`, `topic`, and other header-derived accessors are unauthenticated and must not be used for authorization/tenant-selection without additional verification.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `hmac-sha256: H`, where `H = HMAC(secret, B)` — this validates via `HmacValidator.validate`. [5](#0-4) 
2. Attacker resends the exact same `(B, H)` pair but sets header `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `Request#hmac` and `Request#to_signable_string` are unaffected by the header change, so `HmacValidator.validate(request)` still returns `true`. [2](#0-1) 
4. `Request#shop` now returns `shop-victim.myshopify.com`, so any application code trusting `request.shop` after HMAC validation attributes the (attacker-controlled/replayed) payload to the victim shop. [1](#0-0)
