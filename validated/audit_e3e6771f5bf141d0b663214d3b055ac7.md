This confirms the identity binding gap: the HMAC signature covers only the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (and `topic`/`webhook-id`) values that `Registry.process` hands to the merchant's handler come from the `x-shopify-shop-domain` HTTP header, which is completely outside the signed bytes.

### Title
Webhook `shop` identity is read from an unauthenticated header while HMAC only signs the body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` validates only the raw JSON body via `to_signable_string`, but `Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id`, which are parsed straight from HTTP headers that are never part of the HMAC computation. Any user who can obtain one genuine, validly-signed webhook delivery (e.g., by installing the app on their own store) can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain, and the signature will still validate.

### Finding Description
`HmacValidator.validate` calls `validate_signature`, which computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are not included in that signable string: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the merchant's handler: [4](#0-3) 

The equality that should hold is: `shop bound by the HMAC signature == shop the handler acts on`. Here, the left side is empty (the HMAC signs zero bytes of the shop header) while the right side is `request.shop`, taken verbatim from an attacker-controllable header. Any party that can produce one valid `(raw_body, hmac)` pair — trivially available to anyone who installs the app on a store they control and receives a real webhook — can resubmit that same body with a forged `x-shopify-shop-domain` (and `topic`/`webhook-id`) header pointing at a different, victim shop. `HmacValidator.validate` will accept it because it never looks at the header values, and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the forged victim domain.

### Impact Explanation
This crosses a tenant boundary: the shop identity that is cryptographically authenticated (implicitly, "whoever the real body belongs to") and the shop identity the handler acts on and typically uses as a lookup/foreign key are not the same field. A host application that keys per-shop side effects (data writes, feature toggles, entitlement checks, deletion, etc. per `WebhookMetadata#shop`) off this value can be made to apply another merchant's webhook body under an arbitrary victim shop domain, which is a cross-tenant confusion/injection vector — matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own store with the app installed (unprivileged, self-service), (2) capturing one legitimate webhook delivery's raw body + HMAC header pair, and (3) POSTing it to the app's public webhook endpoint with a different `x-shopify-shop-domain` header. No secret key, access token, or privileged account is needed — the `client_secret`/`api_secret_key` is used only server-side to validate, never revealed to or required by the attacker.

### Recommendation
Bind the shop (and topic/webhook id) into the signed material, or otherwise cryptographically tie the header-derived identity to the HMAC-verified payload before handing it to handlers — e.g., include the shop domain from the header set explicitly in the signable string, or require callers to independently verify the header-derived shop against a shop known to have subscribed to that specific `webhook_id`/topic. At minimum, document clearly that `Request#shop`/`#topic`/`#webhook_id` are **not** covered by HMAC verification, so consuming apps cannot assume they are authenticated, and treat these fields as attacker-controllable input.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and lets Shopify deliver a genuine webhook (e.g., `orders/create`) to the app's webhook endpoint. Attacker records the exact `raw_body` and the `x-shopify-hmac-sha256` header value from that request.
2. Attacker crafts a new HTTP POST to the same endpoint with:
   - Body: identical `raw_body` bytes captured in step 1 (so the HMAC still validates).
   - Header `x-shopify-hmac-sha256`: unchanged from step 1.
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (arbitrary target instead of the attacker's own shop).
   - Header `x-shopify-topic`/`x-shopify-webhook-id`: optionally modified as desired.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC — see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
4. `Registry.process` then invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `request.shop` returning `"victim-shop.myshopify.com"` from the forged header — see `lib/shopify_api/webhooks/registry.rb:198-199` and `lib/shopify_api/webhooks/request.rb:20-23`. The host application's handler now processes attacker-supplied webhook content under the victim shop's identity.
