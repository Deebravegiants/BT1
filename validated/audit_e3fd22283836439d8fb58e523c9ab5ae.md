### Title
Webhook `shop`, `topic`, and `webhook-id` fields are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while `topic`, `shop`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then dispatches the handler and passes the header-derived `shop` to it as the tenant identifier. Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's secret (e.g. a merchant receiving a legitimate webhook for their own, attacker-controlled shop) can resubmit that exact body/HMAC pair with arbitrary `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which only verifies `to_signable_string`, i.e. the body — and then uses the unauthenticated `request.topic` to select a handler and forwards the unauthenticated `request.shop` directly into `WebhookMetadata` given to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`: [4](#0-3) 

The identity binding that should hold is: `bytes authenticated by HMAC == fields the handler acts on`. Instead, the gem authenticates only the body while the tenant-identifying `shop` header and dispatch-controlling `topic`/`webhook_id` headers are accepted unauthenticated. Any entity capable of producing one valid `(body, hmac)` pair for the app's secret — trivially, a merchant who installs the app and receives one real webhook to their own store — can replay that same body+HMAC to the app's public webhook endpoint while substituting a different `shopify-shop-domain` (impersonating another tenant), a different `shopify-topic` (e.g. escalating to a more sensitive topic such as `shop/redact` or `app/uninstalled` if the body happens to validate as JSON for that handler), or a different `webhook-id` (breaking idempotency/dedup assumptions the host app may build on `webhook_id`). The HMAC check gives false assurance that the whole request, including its identifying headers, originated from Shopify for that shop/topic.

### Impact Explanation
This breaks the tenant/topic binding underlying webhook authenticity: `Utils::HmacValidator.validate(request) == true` no longer implies `request.shop` and `request.topic` are the shop/topic Shopify actually signed the event for. A host application that (correctly, per this gem's documented contract) trusts `WebhookMetadata#shop` and `#topic` for per-tenant business logic once `Registry.process` accepts the request can be made to process cross-tenant events under a forged shop domain, satisfying the "cross-tenant access" bucket, since the tenant identifier field is not bound by the identity mechanism (HMAC) that gates request acceptance.

### Likelihood Explanation
Any developer/merchant who installs the app on their own store receives a legitimate, correctly-signed webhook for at least one topic; capturing that raw body and its `X-Shopify-Hmac-Sha256` value is straightforward (they control the receiving endpoint or can proxy/log it). Replaying it against the app's public webhook endpoint with modified headers requires no secret material — just an HTTP client — making this low-effort and unprivileged.

### Recommendation
Bind the identifying headers into the material used for HMAC computation and verification (or otherwise cryptographically bind `shop`/`topic`/`webhook_id` to the signed payload), so that `Utils::HmacValidator.validate` fails if any of `shop`, `topic`, or `webhook_id` are altered relative to what Shopify actually signed for that delivery. At minimum, `Registry.process` should not treat header-derived `shop`/`topic` as trusted tenant/dispatch identifiers once HMAC validation only covers the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives one legitimate webhook delivery, e.g. `orders/create`, with raw body `B` and header `Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `Shopify-Hmac-Sha256: H`, but sets:
   - `Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `Shopify-Topic: orders/create` (or any topic whose handler doesn't validate body shape against topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds, since `B` and `H` are unchanged: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e. attacker-controlled body content is processed as if it belonged to `victim-shop.myshopify.com`: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
