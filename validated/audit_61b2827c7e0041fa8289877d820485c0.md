Audit Report

## Title
Missing `return` after failed email-claim extraction in OIDC token exchange allows session creation to proceed despite unverified/missing email - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
In `oidcAuthenticator.handleTokenExchange`, the type assertion `email, ok := claims["email"].(string)` at [1](#0-0)  logs an error and writes a 500 response when the assertion fails, but does not `return`, unlike every other error branch in the same function (`ShouldBindJSON`, state mismatch, `Exchange`, `id_token` missing, `Verify`, `Claims`, `ExtractIDClaimValues` all `return` immediately after writing their error response, e.g. [2](#0-1) ). Execution therefore falls through into role mapping and session persistence even though the email extraction failed.

## Finding Description
Because `role, err := oi.IDClaimsToUserRole(idClaims, ...)` at [3](#0-2)  is derived solely from `idClaims` (the configured group claim), it does not depend on `email` at all. So a validly authenticated OIDC user whose token lacks an `email` field but whose group claims map to a role will still succeed at role mapping. The code then inserts a row into `oidc_sessions` with `user_email = ""` and the resolved role at [4](#0-3) , sets the session cookie via `ginSession.Set(webauth.SessionIDKey, clSession.ID)` / `ginSession.Save()`, and finally overwrites the earlier 500 write with a `200 OK` success response at [5](#0-4) . Subsequently, `AuthorizedUserWithSession` will authenticate this session and return a `clsessions.User{Email: "", Role: <mapped role>}` at [6](#0-5) , which downstream node API authorization middleware will accept as valid. This confirms the exact root cause and code path claimed.

## Impact Explanation
This is a genuine node API authentication/authorization logic defect: a required identity-verification step (`ok` check on email claim) is checked, logged, but not enforced, allowing session creation and cookie issuance to proceed with an empty/unverified email while still granting whatever role the group claims map to (including Admin). This falls within the "node API authentication or role bypass" impact category, since an authenticated user missing the email claim still receives a fully valid, role-scoped session that gates access to node API endpoints.

## Likelihood Explanation
The trigger requires only a normal, unprivileged OIDC login flow against the node's configured OIDC provider, followed by receipt of a validly-signed ID token whose claims omit `email` (a common scenario for many providers if `email` scope is not explicitly requested) but include a group/role claim satisfying `AdminClaim()/EditClaim()/etc.`. No malicious IdP, host access, or privileged credential is required — this is purely a code-path defect deterministic on missing-`email`-claim inputs.

## Recommendation
Add `return` immediately after the error response write in the `!ok` branch, matching the pattern of every other error branch in `handleTokenExchange`:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, reject/abort login attempts where `email == ""` prior to inserting into `oidc_sessions`, to avoid multiple distinct users colliding on an empty `user_email` key (which would also corrupt `ClearNonCurrentSessions`-style queries keyed on `user_email`).

## Proof of Concept
1. Configure Chainlink OIDC auth against a test IdP that returns a validly-signed ID token whose claims satisfy the configured group claim (e.g., `AdminClaim()`) but omit the `email` key.
2. As an unprivileged client, initiate the OIDC login redirect and call `handleTokenExchange` (the token-exchange endpoint) with the resulting `code`/`state`.
3. Observe: `claims["email"].(string)` fails (`ok == false`), a 500 body is written but execution continues; `IDClaimsToUserRole` succeeds using only group claims; a row with `user_email = ''` and the mapped role is inserted into `oidc_sessions`; `ginSession.Save()` persists a valid session cookie; the final HTTP response is overwritten to `200 OK` with `{"success": true}`.
4. Using the returned session cookie, call a node API endpoint gated by `AuthenticateBySession`/`AuthorizedUserWithSession` and confirm it authorizes using the mapped role despite the empty/unverified email.

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
