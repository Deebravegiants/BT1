### Title
Webhook `shop-domain`/`topic` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` entirely from HTTP headers, while its `to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw request body. An attacker who can obtain any single genuine webhook (e.g., from a shop they legitimately control, since the app's `api_secret_key`/HMAC secret is shared across every shop that installs the app) can replay that body+HMAC pair while forging the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers to point at a different, victim tenant. The gem accepts this as a validly-signed webhook and dispatches it to the app's handler tagged with the forged shop, breaking the identity binding `shop asserted-by-header == shop actually verified-by-HMAC`.

### Finding Description
`Registry.process` is the only integrity gate for inbound webhooks: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string` and compares it to `request.hmac`: [2](#0-1) 

`Request#to_signable_string` returns **only** `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `api_version`, and `webhook_id` — the fields actually **acted on** — are pulled straight from unauthenticated headers, with no cross-check that they correspond to the body that was signed: [4](#0-3) 

Once `HmacValidator.validate` returns `true` (because the body+HMAC pair is genuinely valid, having been produced by Shopify for *some* shop using this app), `Registry.process` unconditionally trusts `request.shop` and `request.topic` for dispatch: [5](#0-4) 

Equality that should hold but doesn't: `shop bound by HMAC == shop used to route/attribute the payload`. Here, the HMAC only binds the body; the `shop` (tenant identity) is asserted by an untrusted header and never verified against anything cryptographic.

Because a single `api_secret_key` is shared by the app across **every** shop that installs it (this is standard OAuth app architecture, not specific to any one merchant), any unprivileged user who installs the app on their own store can capture one legitimate webhook (valid body + HMAC) delivered to them, then resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `ShopifyAPI::Webhooks::Request` and `Registry.process` will accept it as valid and hand the host application a `WebhookMetadata` object claiming the data belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook body (with a validly-computed HMAC produced against the attacker's own shop payload) can be attributed to an arbitrary victim shop by simply changing the `shop-domain` header. Any host application logic that keys off `WebhookMetadata#shop` — e.g., updating that shop's local records, revoking/creating resources, or triggering shop-scoped side effects — will process attacker-supplied data under a victim tenant's identity. This matches the Critical category of cross-tenant access, since it is the gem's own dispatch code (`Registry.process` / `Request`) that fails to bind the verified content to the asserted tenant.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on any shop (any merchant/developer can do this — no privileged credentials needed), (2) capturing one webhook delivery to that shop, and (3) replaying it with a modified `shop-domain` header to the same public webhook endpoint. No access to the app's `api_secret_key`, access tokens, or the victim's credentials is needed. This is a realistic, low-effort attack path for any unprivileged internet user who is also an app installer.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is actually HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to server-side state (e.g., cross-check `request.shop` against a shop that is known to have an active installation/session before dispatching, and/or include the shop domain in the signed payload comparison at the receiving application layer, documenting this requirement clearly). At minimum, `Registry.process` should not treat header-derived `shop`/`topic` as trusted solely because the raw body's HMAC validates; the library should either require callers to independently confirm `request.shop` against their own session store or should refuse to conflate "body integrity verified" with "sender identity verified."

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, which shares the app's `api_secret_key` with all other installs.
2. Attacker triggers any subscribed webhook topic (e.g., `orders/create`) on their own store and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header — this HMAC is valid because `HMAC(api_secret_key, raw_body)` was computed by Shopify.
3. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create` (or any topic registered by the app)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC (`Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker-controlled data as though it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
