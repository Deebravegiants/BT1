### Title
Webhook `shop-domain` (and `topic`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so `Utils::HmacValidator.validate` only proves the integrity of the JSON payload against the app's shared `client_secret`. The `shop-domain` and `topic` values, which are read from separate HTTP headers and passed straight through to the app's webhook handler, are never part of the signed bytes. Because the webhook HMAC secret is the same for every shop that has installed the app, any merchant who installs the app can capture a legitimate `(body, hmac)` pair from their own store and replay it against the app's public webhook endpoint with a forged `shop-domain` header, causing the host app to process attacker-controlled data as if it originated from a victim shop.

### Finding Description
`Registry.process` only checks the HMAC before dispatching to the handler: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header value: [2](#0-1) 

For webhook requests, `to_signable_string` is defined to be only the raw body — it deliberately excludes `topic` and `shop`, both of which come from separate, independently-controllable headers: [3](#0-2) 

`shop` (and `topic`) are then handed unmodified to the app's handler as trusted identity data: [1](#0-0) 

The identity binding that should hold is: `shop used by the handler == shop that was cryptographically bound to this request`. Instead the gem only guarantees `hmac == HMAC(secret, raw_body)`; the `shop` header is asserted, not verified. Since the webhook secret (the app's `client_secret`) is identical across every shop that installs the app, any Shopify merchant can:
1. Install the target app on their own (attacker-controlled) store.
2. Trigger a webhook so Shopify sends a legitimate `(raw_body, hmac)` pair signed with the app's shared secret.
3. Replay that exact `(raw_body, hmac)` to the app's public webhook endpoint, but swap the `shopify-shop-domain` (and/or `shopify-topic`) header to a victim shop's domain / a different topic.

`HmacValidator.validate` still succeeds because the digest is computed solely over `raw_body`, so `Registry.process` dispatches the handler with `shop: <victim shop>` while the actual signed content only proves it came from *some* shop that has the app installed (namely the attacker's).

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged party who can merely install the app on any store gains the ability to make the host application process events under a different, victim shop's identity. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., updating merchant-specific settings, triggering uninstall cleanup, writing to a per-shop record keyed by `shop`), this can lead to cross-tenant data corruption or state confusion for a shop the attacker never installed the app on — this maps to the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any Shopify store (a normal, unprivileged action available to any merchant/developer) and be able to POST arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no access token, leaked credential, or `client_secret` knowledge is required. This is straightforward to carry out.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the HMAC-signed content, or otherwise cryptographically bind them to the payload (e.g., include them in the signable string, similar to how `Oauth::AuthQuery#to_signable_string` includes `shop`), so that a header value cannot be swapped independently of the signed body.

### Proof of Concept
1. Install the target app on an attacker-controlled shop, trigger any webhook subscription, and capture the resulting `raw_body` and `shopify-hmac-sha256` header — both signed validly with the app's shared secret.
2. Craft a new HTTP POST to the app's webhook endpoint using the captured `raw_body` and `hmac` header unchanged, but replace `shopify-shop-domain` with the victim shop's domain (and optionally change `shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts these headers, `HmacValidator.validate` succeeds because it only checks `raw_body` against the secret: [4](#0-3) 
4. `Registry.process` dispatches to the app's handler with `shop: <victim shop>`, even though the request never actually originated from, or was authorized for, that shop. [5](#0-4)

          received_signature = verifiable_query.hmac
