Audit Report

## Title
Non-atomic check-then-act JWT replay guard allows concurrent request authorization bypass in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks for JWT replay via `jwtCache.isReplay(claims.ID)` and records usage via `jwtCache.recordUsage(claims.ID)` in two separate, independently-locked critical sections, with workflow/signer lookup logic executing in between. Because these are not combined into a single atomic check-and-set operation, concurrent calls to `Authorize` with the same signed JWT can both pass the replay check before either records usage, breaking the single-use guarantee of the token.

## Finding Description
`jwtReplayCache.isReplay` acquires an `RLock`, checks map membership, and releases the lock; `jwtReplayCache.recordUsage` separately acquires a `Lock`, inserts the entry, and releases it. `Authorize` calls `isReplay` first, then performs workflow-ID lookup and signer-authorization checks (unguarded by any handler-level mutex), and only calls `recordUsage` at the very end before returning success. This is a classic TOCTOU pattern: two threads can both execute `isReplay` and observe `false` before either calls `recordUsage`. `HandleUserTriggerRequest` invokes `authorizeRequest`/`Authorize` before any request-ID-based in-flight dedup (`setupCallback`), so that later dedup does not protect the authorization step itself. The codebase demonstrates the correct fix pattern elsewhere via `RequestReplayGuard.CheckAndRecord`, which performs the "seen" check and insertion atomically under one lock — `jwtReplayCache` has no equivalent method.

## Impact Explanation
An unprivileged client holding one valid signed JWT for a workflow-execute request can fire concurrent requests to exploit the race and obtain more than one successful authorization from what is meant to be a strictly single-use token. This undermines the request-impersonation/single-use guarantee of the gateway's JWT-based authorization scheme and could enable duplicate authorization of otherwise single-use signed actions, mapping to the "gateway request impersonation / authorization bypass" impact category.

## Likelihood Explanation
The race window is narrow but real and attacker-controllable: sending several parallel requests with an identical valid JWT increases the odds of winning the race, since intervening map-lookup work in `Authorize` widens the window between the two independently-locked cache operations. No special privilege beyond obtaining one legitimate JWT is required.

## Recommendation
Add an atomic `jwtReplayCache.CheckAndRecord(jti string) error` that performs the existence check and insertion under a single `Lock`/`Unlock` critical section, mirroring `RequestReplayGuard.CheckAndRecord`, and call it as the first step of `Authorize` before any other work.

## Proof of Concept
1. Sign one JWT for a valid workflow-execute request (as in the existing "JWT replay protection" sequential test).
2. Launch two goroutines that call `handler.Authorize(workflowID, tokenString, req)` concurrently with the identical token.
3. Due to the non-atomic `isReplay` → (workflow/signer checks) → `recordUsage` sequence, both goroutines can observe `isReplay == false` before either calls `recordUsage`, so both can return a valid `*gateway.AuthorizedKey` instead of the second failing as the sequential test expects.

	defer g.mu.Unlock()
