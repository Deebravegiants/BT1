This confirms the docs explicitly promise: "This will verify the request did indeed come from Shopify" — but the `shop` field, which the app is told to trust for tenant-scoping (`data.shop`), is never part of what's verified.

### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` method returns only `@raw_body`, so the HMAC never binds the `shop-domain` header [2](#0-1) . Yet `Request#shop` is read directly from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and passed straight into `WebhookMetadata` for the app's handler to use as the tenant identity [3](#0-2) [1](#0-0) .

### Finding Description
The identity binding that should hold is: `shop header used by the app handler == shop that actually produced/authorized this signed body`. Because `to_signable_string` only concatenates `@raw_body` and excludes the shop header, `HmacValidator.validate` (`compute_signature(verifiable_query.to_signable_string, secret)` compared via `OpenSSL.secure_compare`) [4](#0-3)  only proves "this body was signed with the app's `client_secret`" — it proves nothing about which shop the header claims to be from.

Since the same `client_secret` is used to sign webhooks for every shop that installs the app, any merchant who has legitimately installed the app receives real webhook deliveries with valid `body + hmac` pairs for their own shop. That merchant can capture such a payload and replay it to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [5](#0-4) , handing the app attacker-chosen `shop` attribution for a "verified" webhook.

This exactly mirrors the report's root cause class: a value the receiver relies on for identity/authorization (`shop`) is not covered by the cryptographic check (`HMAC` over `raw_body` only), letting an unprivileged party (any installed merchant) forge the association between a valid signature and an arbitrary victim tenant.

### Impact Explanation
This is a cross-tenant access vector: the app's own documentation instructs developers to trust `data.shop` from a "verified" webhook as the tenant scope [6](#0-5) [7](#0-6) . A malicious merchant can inject webhook events attributed to a different, victim shop (e.g. replaying `app/uninstalled`, `shop/update`, `customers/data_request`, or other topic bodies against a different shop's identity), causing the host application to act on/mutate data or session state keyed by the spoofed `shop` value — a cross-tenant boundary break using only their own legitimate app installation, no leaked secrets required.

### Likelihood Explanation
Likelihood is high for any app that relies on `data.shop` from processed webhooks without independently re-validating the shop against a known/authorized list (which is exactly what the gem's own webhook flow is supposed to guarantee, per its documentation). The only capability needed is that of an ordinary merchant who has installed the app — no access to `api_secret_key`, tokens, or privileged access is required.

### Recommendation
Include the `shop` (and `webhook_id`/`topic`, ideally) in the bytes that are HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before trusting it in `WebhookMetadata`. At minimum, `Request#to_signable_string` should not silently exclude a field (`shop`) that the rest of the library and its documentation treat as verified/trustworthy.

### Proof of Concept
1. App installs on Attacker Shop A and Victim Shop B (or attacker only needs to be installed once for their own shop and know/guess the app's registered webhook topics).
2. Shopify sends a legitimate webhook to the app for topic `T` on Shop A: `raw_body = B`, header `x-shopify-shop-domain: shop-a.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays this exact request to the app's webhook endpoint, only rewriting the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` are computed purely from `raw_body`/`hmac-sha256` header [8](#0-7) ; `Utils::HmacValidator.validate` returns `true` since `B` and its HMAC are untouched.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [1](#0-0) , and the handler performs an action scoped to Victim Shop B, believing it was verified by Shopify.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
