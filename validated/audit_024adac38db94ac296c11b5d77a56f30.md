### Title
RAY index-value overflow permanently freezes a heavily borrowed market - (File: common/src/rates/simulate.rs)

### Summary
Interest accrual computes aggregate debt and supply as `scaled_shares * index` in `i128` before updating the indexes; once either product exceeds `i128::MAX`, `accrue_step` panics before state is committed. [1](#0-0)  Every pool mutation loads the market through `interest::global_sync`, so the same overflow also prevents repayment, withdrawal, liquidation, bad-debt cleanup, recapitalization, and further index updates. [2](#0-1) [3](#0-2)  The repository already contains a deterministic regression test showing `update_indexes`, `withdraw`, and `repay` all failing with `MathOverflow` after this state is reached. [4](#0-3) 

### Finding Description
`accrue_step` derives utilization by unscaling the market’s stored `borrowed` and `supplied` RAY-share totals with their current indexes. [5](#0-4)  `scaled_to_original` performs the multiplication in the protocol’s checked `Ray` domain, where an unrepresentable result raises `MathOverflow`. [6](#0-5) [7](#0-6) 

The vulnerable ordering is:

1. `Cache::elapsed_ms()` detects that time has passed and `global_sync` enters accrual. [8](#0-7) [9](#0-8) 
2. `accrue_chunk` invokes `accrue_step` before setting either index. [10](#0-9) 
3. `accrue_step` first evaluates the old aggregate debt and supply values. [5](#0-4) 
4. If `borrowed * borrow_index` or `supplied * supply_index` no longer fits `i128`, the transaction panics before `borrow_index`, `supply_index`, or `last_timestamp` can be updated. [11](#0-10) [12](#0-11) 
5. Because user-facing controller operations call owner-gated pool operations that run this synchronization before reducing balances, no allowed action can first shrink `borrowed` or `supplied` enough to avoid the panic. [13](#0-12) [14](#0-13) 

The permissionless controller entrypoint `update_indexes(caller, assets)` forwards the supplied `HubAssetKey` list to the pool, making the overflow externally triggerable once the market state has crossed the representable-value boundary. [15](#0-14) [16](#0-15) [17](#0-16) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected `(hub_id, asset)` book: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot close unhealthy accounts, and the market cannot accrue normally. [4](#0-3)  The panic happens before any balance-reducing operation executes, and later attempts evaluate an even larger or equal index, so the state does not recover by retrying. [3](#0-2) [11](#0-10)  Once crossed, all cash and outstanding claims on that book remain behind a path that deterministically panics; absent a contract upgrade or equivalent privileged intervention, the funds are permanently inaccessible. [13](#0-12) 

### Likelihood Explanation
The condition requires an extremely large market and enough index growth for a stored share total multiplied by its index to exceed `i128::MAX`; the protocol documentation itself notes that bounded indexes do not guarantee representable aggregate values. [18](#0-17)  A single unprivileged account can nevertheless build the precondition through the allowed `supply` and `borrow` paths when configured caps and available collateral permit the required size, and any signed caller can subsequently trigger accrual through `update_indexes`. [19](#0-18) [15](#0-14)  The checked-in PoC uses a one-billion-whole-token, 18-decimal market with approximately 98% utilization and advances ledger time until the first accrual returns `MathOverflow`. [20](#0-19) 

### Recommendation
Do not require an `i128` aggregate-value multiplication before balances can change. [5](#0-4)  Compute utilization and interest allocation through widened `I256` intermediates, and enforce explicit per-book index ceilings derived from `i128::MAX / scaled_shares` so index updates clamp or halt interest growth before the value calculation becomes unrepresentable. [21](#0-20) [22](#0-21)  Equivalently, store sufficient unscaled principal to update indexes without multiplying historical aggregate shares by the old index. [23](#0-22)  Add a regression assertion that, after the overflow-boundary state is reached, withdrawal and repayment can still execute while accrual is safely capped rather than panicking. [24](#0-23) 

### Proof of Concept
The existing test creates `BIG18`, supplies `1_000_000_000 * 10^18` base units, borrows 98% of it, repeatedly advances the ledger by whole-year intervals, and calls controller `update_indexes` for that `HubAssetKey` until `MathOverflow` is returned. [25](#0-24)  It then proves the book is frozen by showing both `withdraw(Bob, BIG18, 1)` and `repay(Alice, BIG18, 1.0)` fail with the same `MathOverflow`, while the stored borrow index remains below its configured cap. [24](#0-23)  The failure occurs because `update_indexes` reaches pool `update_indexes`, which runs `global_sync`, which reaches `accrue_step`, whose first two calculations unscale aggregate debt and supply before any index is committed. [17](#0-16) [26](#0-25) [27](#0-26) [28](#0-27)

pub fn accrue_step(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    supplied: Ray,
    borrow_index: Ray,
    supply_index: Ray,
    delta_ms: u64,
) -> AccrualStep {
    let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
    let supplied_original = scaled_to_original(env, supplied, supply_index);
    let util = utilization(env, borrowed_original, supplied_original);
    let borrow_rate = calculate_borrow_rate(env, util, params);
    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    let (supplier_rewards, protocol_fee) =
        calculate_supplier_rewards(env, params, borrowed, new_borrow_index, borrow_index);

    let new_supply_index = update_supply_index(env, supplied, supply_index, supplier_rewards);
    let supplier_shortfall = supply_index_reward_shortfall(
        env,
        supplied,
        supply_index,
        new_supply_index,
        supplier_rewards,
    );

    let protocol_reward = protocol_fee.checked_add(env, supplier_shortfall);
    // Shares are valued at the new supply index, which the caller stores for
    // this step.
    let revenue_shares = if protocol_reward == Ray::ZERO {
        Ray::ZERO
    } else {
        protocol_fee_shares(env, protocol_reward, new_supply_index, supplied)
    };

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

**File:** docs/reference/formulas.md (L20-30)
```markdown
Protocol boundaries require non-negative amounts; `Ray`, `Wad` and `Bps`
constructors do not enforce that restriction themselves. Multiply-divide uses
an `i128` fast path or an exact `I256` intermediate. Unrepresentable results
raise `MathOverflow`, except at explicit saturating sites; zero divisors raise
`DivisionByZero`.

Half-up multiply-divide requires non-negative operands and a positive divisor.
Raw floor and ceiling multiply-divide also support signed quotients. Decimal
upscaling uses checked `i128` arithmetic. Downscaling and division by a positive
integer support the signed extremes; signed half-up downscaling rounds exact
halves away from zero.
```
