### Title
Unverified hop pools in `swap_xdr` routes can execute arbitrary token transfers from the caller's wallet under the caller's own authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The swap aggregator executes routes built off-chain and passed as opaque `Bytes` (`swap_xdr`). The router keeps no allowlist of pool or token addresses in the payload, so any contract can be named as a hop venue and invoked with the caller's `require_auth` tree still on the call stack. A malicious venue named in the route can invoke `token.transfer(victim, attacker, amount)` that the Soroban host attributes to the caller's authorization entry. If the user signs the tree produced by a compromised front-end/quote service — which is indistinguishable in effect from an honest route — the attacker drains arbitrary wallet tokens far beyond the routed amount. This is the exact analog of the Maverick Router `exactInput` finding: the encoded path argument is unreadable to the signer and no factory-style verification is performed on hop contracts. [1](#0-0) 

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` authenticates `sender` once and then walks hops calling whatever pool/token addresses the payload registries name. Venue adapters measure balance deltas (`router credits only measured balance changes`), which guarantees the routed amount is accounted for honestly — but it does not constrain what *other* calls the named venues make during execution. [2](#0-1) 

On the controller side, `swap_tokens` authorizes a single exact input transfer to the configured router and checks input-spend bounds and positive measured output — but places no constraint on the route's venue addresses, and passes `swap` through as opaque bytes without decoding it. [3](#0-2) [4](#0-3) 

Because `sender.require_auth()` inside `execute_strategy` resolves against the caller's top-level authorization entry for `execute_strategy` (or `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`), a malicious hop contract's `transfer` call from the caller's address is recorded as a child of that same entry and executes if the caller signs the simulated tree. The repo's own adversarial test proves this end-to-end: `RogueHopPool::swap` performs `token.transfer(alice, attacker, WALLET_BALANCE)` while paying a fair swap output, and the recorded auth tree shows the stolen transfer nested under Alice's `swap_collateral` invocation — the swap itself succeeds and all risk gates pass. [5](#0-4) [6](#0-5) 

The threat model documents the exposure explicitly: "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." It leaves the mitigation to clients ("a client must decode the route it signs and refuse an authorization tree with any other child"), i.e., protection lives entirely in the front-end — the same defense-in-depth gap the original finding identified. [1](#0-0) 

### Impact Explanation
Theft of user funds. Any token held by the caller's wallet — unrelated to the swap, unbounded by `amount_in` or `total_min_out` — can be transferred to the attacker during route execution, provided the user signs the authorization tree a malicious route produces. Both the direct `execute_strategy` path and all controller strategies that take `swap` bytes (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) expose this. [7](#0-6) 

### Likelihood Explanation
Routes are always produced by the off-chain quote service and forwarded as opaque XDR bytes; users cannot meaningfully inspect the hop addresses in a wallet, and the threat model concedes protection is delegated to clients. This mirrors the original Medium severity: an attack vector exists in the code, but exploitation requires the user to be served a malicious route (compromised front-end/quote service or phishing). Medium. [8](#0-7) 

### Recommendation
At minimum, do for venues what the Maverick fix proposed for pools: maintain a governance-managed allowlist of legitimate venue/pool contracts (Aquarius, Comet, Phoenix, Soroswap, Sushi adapters' known pool deployments, or venue addresses) and have the router reject hops whose pool address is not registered. Alternatively/additionally, scope the caller's authorization more narrowly — e.g., have the router pull `total_in` via a dedicated sub-invocification-free transfer so that no legitimate route ever needs a child invocation under the caller's auth entry, then enforce on-chain that hop venue contracts cannot call token contracts with the caller's address as `from` (not directly enforceable on Soroban, so allowlisting venues is the practical mitigation). Document that front-ends must refuse auth trees with unexpected children as a secondary control only. [9](#0-8) 

### Proof of Concept
The repository already contains a working exploit in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. A router double calls whichever `hop_pool` the payload names: `env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), ...)` — no allowlist check. [10](#0-9) 
2. `RogueHopPool::swap` transfers the victim's entire wallet balance of an unrelated token to the attacker while the fair output is still paid. [11](#0-10) 
3. The test asserts the recorded auth tree places the stolen `transfer` as a `sub_invocation` of Alice's `swap_collateral` root entry — meaning a wallet that signs the simulated tree authorizes the theft — and asserts `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the swap still deposits fair output. [6](#0-5) 

No code changes are needed to reproduce; running the test demonstrates the theft vector through the real controller `swap_collateral` entrypoint with owner authorization. [12](#0-11)

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
