### Title
Fee-on-transfer input tokens create under-collateralized escrow in the Tron IntentGatewayV2, draining the shared token pool backing other users' orders - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` records escrow accounting from the user-supplied nominal `order.inputs[i].amount` reduced only by the protocol fee, but never measures the token balance actually received by the contract via `safeTransferFrom`. For any deflationary / fee-on-transfer / asymmetric-burn ERC20 used as an order input (the same bug class SlowMist documented for the Uwerx/WERX token), the contract can record more escrow than it actually holds, corrupting the shared per-token balance pool that backs every other order using that token.

### Finding Description
`placeOrder` in the non-predispatch branch does: [1](#0-0) 

`safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` is called with the *nominal* amount, and no balance-before/after check verifies how much the gateway actually received. The escrow ledger is then incremented with `reducedInputs[i].amount`, computed purely from the nominal amount: [2](#0-1) 

If the input token deducts a transfer fee (or burns extra tokens, as WERX did based on recipient address) larger than `protocolFeeBps`, the actual tokens received by the gateway are strictly less than the amount recorded in `_orders[commitment][token]`. Because `_orders[...][token]` is a bookkeeping map layered over one shared ERC20 balance per token address (not a per-order vault), this under-collateralized entry silently consumes real balance that belongs to *other* orders/commitments denominated in the same token, since all escrow claims are settled from the same pool of `IERC20(token).balanceOf(address(this))`.

This is the direct Tron-network analog of the root cause SlowMist identified in Uwerx: accounting logic that assumes `amount transferred == amount recorded`, when the token's own transfer semantics (fee/burn) make that assumption false, and an attacker can select or influence the token/recipient parameters to widen the gap.

By contrast, the mainline EVM `IntentGatewayV2.placeOrder` was hardened against exactly this class of bug — it snapshots `balanceOf` before and after the transfer and mutates `order.inputs[i].amount` to the actual received delta before computing the commitment and escrow: [3](#0-2) 

confirmed by the dedicated fee-on-transfer regression tests: [4](#0-3) 

The Tron variant lacks this protection entirely, in both the predispatch and direct-escrow code paths.

### Impact Explanation
`_orders[commitment][token]` is not an isolated vault per order — every order that escrows the same token address draws down the same shared `IERC20(token).balanceOf(address(this))`. An attacker can place an order using a fee-on-transfer/deflationary token as input, causing the gateway to record an escrow entry larger than what it actually received. When that order and other legitimate orders sharing the token later settle via `_withdraw`/`RedeemEscrow`/`EscrowRefunded`, the aggregate claims on that token exceed the real balance, so at least one legitimate user's withdrawal reverts (permanent freezing of funds) or, if the attacker's order settles first, it extracts tokens that were actually deposited by other users (theft from the shared pool). This is a Medium-to-High severity accounting/insolvency bug reachable from a single unprivileged `placeOrder` transaction.

### Likelihood Explanation
Any address can call `placeOrder` with an arbitrary ERC20 as the input token, including a token they control or a widely-used deflationary token; the vulnerable code path executes unconditionally whenever a token has any transfer-time deduction exceeding the configured protocol fee. No governance, relayer, or privileged role involvement is required.

### Recommendation
Apply the same balance-before/after accounting used in `evm/src/apps/IntentGatewayV2.sol` (lines 312-329) to `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure the gateway's actual token balance delta after each `safeTransferFrom` (and after each predispatch sweep) and use that measured amount — not the caller-supplied nominal amount — as the basis for `reducedInputs`, the commitment hash, and the `_orders` escrow entry.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 50% transfer fee) and mint balance to an attacker-controlled account.
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with this token as `order.inputs[0].amount = 1000`. The contract only receives ~500 tokens (`safeTransferFrom` is fee-deducted) but records `_orders[commitment][token] += reducedInputs[0].amount` (~970 after a 3% protocol fee) — nearly double the real balance backing that entry.
3. A second, unrelated user separately deposits the same token normally (no fee token trick needed on their side, since the pool is shared by token address) for a different order.
4. When both orders settle (`_withdraw` invoked via `RedeemEscrow`/`EscrowRefunded`/partial fill), the sum of claims against `IERC20(token).balanceOf(address(this))` exceeds the real balance, causing the second (honest) user's withdrawal to revert (frozen funds) or, depending on settlement order, the attacker's order to drain tokens that were actually contributed by the honest user.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
