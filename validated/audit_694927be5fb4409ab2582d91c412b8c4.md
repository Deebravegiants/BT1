### Title
Unbounded HTTP Action Response Cache Growth via Workflow-Controlled Cache Keys - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The `responseCache` used by the CRE gateway's HTTP-action capability handler is an in-process `map[string]*cachedResponse` with no maximum-size bound. Entries are only removed by a TTL-based periodic sweep (`DeleteExpired`), never capped by count. An external, unprivileged actor who can register/deploy a workflow that performs `http-action` capability calls can cause the gateway's DON-facing node message handler to insert an unbounded number of distinct cache entries, exhausting gateway memory — the same "unlimited-size, TTL-only-pruned cache" bug class described in the reference report (timestamp cache growth in shardus-core).

### Finding Description
`responseCache` stores every cacheable HTTP action response keyed by `req.Hash()` (derived from method, URL, headers, body, and workflow owner), with no limit on the number of entries: [1](#0-0) 

The only cleanup mechanism removes *expired* entries on a timer; it does not bound total map size at insertion time: [2](#0-1) 

Entries are created in `makeOutgoingRequest`, which is invoked from `HandleNodeMessage` whenever a workflow DON node relays an `http-action` message to the gateway on behalf of a running workflow. If the workflow sets `CacheSettings.Store = true` (and optionally `MaxAgeMs`), every unique `(method, URL, headers, body, workflowOwner)` combination produces a new cache entry: [3](#0-2) 

Because the cache key includes the full request (URL, headers, body), a workflow author fully controls the key space. A workflow whose `http-action` step varies the URL (e.g., appends a random query parameter or unique path segment) or body on every execution will always produce cache misses, forcing a new, permanent (until TTL expiry) entry to be added on every single invocation — mirroring the shardus-core report where an attacker forces cache misses (via non-existent transaction IDs) to force unbounded cache growth, bypassing the pruning logic by manipulating fields the pruning routine does not validate (there: cycle counter; here: cache key uniqueness with no per-workflow/global size cap).

Rate limiting exists per-node and globally, but it only throttles request *throughput*, not the aggregate number of live cache entries: [4](#0-3) 

Given a default TTL of 10 minutes (`defaultOutboundRequestCacheTTLMs`) and no size ceiling, a sustained stream of uniquely-keyed cached HTTP action requests accumulates in memory faster than the TTL sweep can remove them, growing until the gateway process runs out of memory. [5](#0-4) 

### Impact Explanation
An unprivileged workflow owner (an "external initiator" from the gateway's perspective — not an operator or DON node) can register a workflow that repeatedly performs unique, cacheable `http-action` requests. This forces the internet-facing gateway process to grow its `responseCache` map without bound, consuming increasing amounts of memory over time until the process crashes (denial of service), impacting all workflows served by that gateway/DON shard — consistent with the "Network not being able to confirm new transactions (total network shutdown)" class of impact in the reference report, translated to gateway/DON unavailability here.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only the ability to deploy/own a workflow capable of invoking the `http-action` capability with `CacheSettings.Store = true` and a cache key that varies per call (trivial to construct, e.g., via a random query string) — no elevated privileges, no malicious DON node, and no protocol-level access are required beyond normal workflow authoring. Existing rate limiters bound request throughput but do not bound cache size, so the attack merely needs sustained execution over time to outpace TTL-based cleanup.

### Recommendation
- Enforce a hard maximum entry count (or byte-size budget) on `responseCache`, similar to `requestCache.maxCacheSize` in `core/services/gateway/handlers/common/requestcache.go`, rejecting/evicting (e.g., LRU) new entries once the limit is reached.
- Consider per-workflow-owner cache-entry quotas so a single workflow cannot monopolize/exhaust the shared cache.
- Track and alert on `http_action_cache_size` growth trends to detect this pattern before OOM.

### Proof of Concept
Conceptual PoC (cannot be executed from static analysis; based on confirmed code paths):
1. Register a workflow on the DON that includes an `http-action` step with `CacheSettings.Store = true` and a URL containing a randomly generated query parameter or path segment on every execution (e.g., `https://example.com/api?nonce=<random>`).
2. Trigger the workflow to execute repeatedly (via its normal trigger, e.g., a cron trigger or webhook), each execution producing a unique `req.Hash()` and therefore a fresh `responseCache` entry through `makeOutgoingRequest` → `h.responseCache.Set`/`Fetch`.
3. Because there is no maximum cache size, only TTL-based expiry, the number of live entries grows linearly with the invocation rate as long as it exceeds the expiry+cleanup rate.
4. Monitor the gateway process's memory (or the `http_action_cache_size` metric emitted in `core/services/gateway/handlers/capabilities/v2/metrics/metrics.go`) to observe unbounded growth over the workflow's runtime.

// responseCache is a thread-safe cache for storing HTTP responses.
// It uses a map to store responses keyed by a hash of the request (method, URL, headers, body, workflowOwner).
type responseCache struct {
	cacheMu sync.RWMutex
	cache   map[string]*cachedResponse
	flight  singleflight.Group
	lggr    logger.Logger
	ttl     time.Duration
	metrics *metrics.Metrics
}

type cachedResponse struct {
	response gateway.OutboundHTTPResponse
	storedAt time.Time
}

func newResponseCache(lggr logger.Logger, ttlMs int, metrics *metrics.Metrics) *responseCache {
	return &responseCache{
		cache:   make(map[string]*cachedResponse),
		lggr:    logger.Named(lggr, "ResponseCache"),
		ttl:     time.Duration(ttlMs) * time.Millisecond,
		metrics: metrics,
	}
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}

func (h *gatewayHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	if resp.ID == "" {
		return fmt.Errorf("received response with empty request ID from node %s", nodeAddr)
	}
	h.lggr.Debugw("handling incoming node message", "requestID", resp.ID, "nodeAddr", nodeAddr)
	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementCapabilityNodeThrottled(ctx, nodeAddr, h.lggr)
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementGlobalThrottled(ctx, h.lggr)
		return errors.New("global rate limit exceeded")
	}

	}

		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async

		// not cancelled when parent is cancelled to ensure the goroutine can finish
