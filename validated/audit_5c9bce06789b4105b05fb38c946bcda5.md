### Title
`Oauth.begin_auth` fails to validate `shop` before building the authorization redirect URL - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`Oauth.begin_auth` builds `auth_route` by calling the private `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` for any string that doesn't contain `.my.shop.dev`, without ever calling `Utils::ShopValidator.sanitize!`. In contrast, `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before using the shop value. This means an app that (per the gem's own documented pattern of reading `shop` from an untrusted request parameter/header) passes attacker-controlled input to `begin_auth` will redirect the merchant's browser to an attacker-chosen host.

### Finding Description
The intended binding is: **the host embedded in the OAuth authorization redirect must be a member of `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (or a configured `myshopify_domain`)** — i.e. `URI(auth_route).host ∈ trusted_domains`. This binding is enforced in `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25`) and `RefreshToken.refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24`) via `validated_shop = Utils::ShopValidator.sanitize!(shop)` before the shop is used anywhere.

`Oauth.begin_auth` does not do this: [1](#0-0) 
The unsanitized `shop` flows directly into the private helper: [2](#0-1) 
`auth_base_uri` returns `"https://#{shop}/admin"` unconditionally unless the dev-server branch is taken, so for `shop = "evil.example.com"` the resulting `auth_route` is `https://evil.example.com/admin/oauth/authorize?client_id=...&redirect_uri=<app host>&state=<nonce>`. There is no equivalent of `sanitize!`'s host-allowlist check (`TRUSTED_SHOPIFY_DOMAINS`, see `lib/shopify_api/utils/shop_validator.rb:9-18`) anywhere in this code path.

The root cause is a missing call — `begin_auth` should validate/sanitize `shop` exactly as `client_credentials`/`refresh_access_token` do, but does not.

None of the existing guards catch this: `Context.setup?`/`Context.private?` only check app-level configuration, not the shop value; `HmacValidator.validate` and the `state` comparison only apply later, inside `validate_auth_callback`, and only validate the callback query, not the value used to build the outbound redirect; Sorbet's runtime typing only enforces `shop: String`, not that the string is a trusted domain.

I was unable to fully verify from the index the exact host-app wiring (i.e., that a typical Rails controller built on this gem performs an actual HTTP redirect to `auth_route` using the raw header value without its own validation) since `docs.md`/controller glue code lives in the consuming application, not in this gem, and I could not locate matching text in `docs.md` in this index. The vulnerability as scoped is confined to this gem's own code: `Oauth.begin_auth` computes and returns a URL rooted at attacker-controlled `shop` with no host validation, which is the documented contract of the method.

### Impact Explanation
This is Attacker-controlled host **only if** the host application passes attacker-controlled shop input into `begin_auth` unsanitized, which is exactly the pattern the question's context frames as the gem's documented usage (`shop = request.headers["Shop"]`). The impact is limited to producing an `auth_route`/redirect target pointing at an attacker-chosen host, carrying `client_id` (the app's public API key) and the CSRF `state` nonce — not a merchant access token, refresh token, authorization code, or `client_secret`, since `begin_auth` itself performs no server-side request to `shop`; it just returns data for the caller to redirect with. The chain that the question describes toward stealing `client_secret` (via a subsequent forged `validate_auth_callback` call) requires the host app to *also* pass the same unsanitized, attacker-supplied shop value into `validate_auth_callback`'s flow so that `client.request(...)` in `lib/shopify_api/auth/oauth.rb:81-94` posts `client_id`/`client_secret` to an attacker-controlled host — that is a second, separate unsanitized-input issue at the callback side, not demonstrated end-to-end here, and `validate_auth_callback` does perform `Utils::HmacValidator.validate(auth_query)` and a `state` cookie comparison before proceeding, which are real (though not host-validating) guards. Given this, the concretely demonstrated impact from `begin_auth` alone is a High-severity SSRF/forced-redirect (an unintended host receiving the app's `client_id` and CSRF `state`), not a demonstrated Critical secret-exfiltration, because the secondary chain to leak `client_secret` was not confirmed against this gem's code in this session.

### Likelihood Explanation
Exploiting this requires only that the host application read the `shop` value from attacker-influenceable input (query/header) and pass it straight to `begin_auth` without its own shop validation — which is consistent with common OAuth-initiation patterns shown for this class of Shopify library. No credentials, secrets, or special access are needed; a single unauthenticated HTTP request to the login-initiation endpoint of the app is sufficient, and the exploit is repeatable against any victim who follows the resulting redirect link.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate and sanitize `shop` inside `begin_auth` before it is used to build `auth_base_uri`/`auth_route`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
...
auth_route = auth_base_uri(validated_shop) + "/oauth/authorize?#{query_string}"
```
Raise `Errors::InvalidShopError` (as `sanitize!` already does) when the shop is not a member of `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` or the configured `myshopify_domain`.

### Proof of Concept
```ruby
# test/auth/oauth_begin_auth_shop_validation_test.rb
require "test_helper"

class OauthBeginAuthShopValidationTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret",
      host_name: "app.example.com", scope: "read_products",
      is_embedded: false, is_private: false, api_version: "unstable",
    )
  end

  def test_begin_auth_does_not_sanitize_shop
    ShopifyAPI::Utils::ShopValidator.expects(:sanitize!).never

    result = ShopifyAPI::Auth::Oauth.begin_auth(
      shop: "evil.example.com",
      redirect_path: "/auth/callback",
    )

    # BROKEN BINDING: URI(auth_route).host should be in
    # ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS, but is not.
    assert result[:auth_route].start_with?("https://evil.example.com")
    refute ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS.any? do |d|
      URI(result[:auth_route]).host == d || URI(result[:auth_route]).host&.end_with?(".#{d}")
    end
  end
end
```
This test currently passes (demonstrating the vulnerability); after applying the recommended fix, `begin_auth(shop: "evil.example.com", ...)` should raise `ShopifyAPI::Errors::InvalidShopError` instead.
