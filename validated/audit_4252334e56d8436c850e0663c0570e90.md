Audit Report

## Title
Internal Vault JWT AuthToken Logged in Full at Debug Level - (File: core/services/gateway/handlers/vault/handler.go)

## Summary
`HandleJSONRPCUserMessage` in the gateway's Vault handler logs the entire incoming `jsonrpc.Request[json.RawMessage]` struct at `Debug` level before any authorization check occurs. Since the request struct carries the caller's `Auth` field containing the raw JWT bearer token used for Vault request authorization, enabling debug logging on the gateway causes live authorization tokens to be written verbatim into node logs.

## Finding Description
The vulnerable call is confirmed exactly as claimed: [1](#0-0) 

This line logs the full `req` value via `"request", req` before `h.requestProcessor.ProcessRequest` is invoked for authorization at line 427, meaning the token is captured regardless of whether the request is ultimately authorized. The `Auth` field is confirmed to carry the bearer token used for authorization decisions, as shown by its use in `authorizeRequest` (`req.Auth == ""` to select allowlist vs. JWT-based auth paths) and in `jwtBasedAuth.AuthorizeRequest` (`v.validateToken(ctx, req.Auth)`). The codebase's own authors treat `Auth` as sensitive elsewhere in the very same file and in `authorizer.go`, deliberately logging only a boolean presence indicator (`"hasAuth", req.Auth != ""`) rather than the token value: [2](#0-1)  This inconsistency — redacting `Auth` at one log site in the same function while logging the full struct (which contains the same field) two lines earlier — is a genuine redaction gap, not an intentional design choice.

## Impact Explanation
Any party with read access to gateway logs when debug-level logging is enabled can extract live JWT bearer tokens for Vault requests. These tokens authorize workflow-owner-scoped secret operations (create/update/delete/list), so a leaked, still-valid token allows impersonation of the legitimate workflow owner/org to manipulate Vault DON secrets before token expiry. This maps to the in-scope "key/secret exfiltration" and "gateway request impersonation" impact categories.

## Likelihood Explanation
This requires the gateway to be run with `Debug` log level enabled and requires an actor to obtain read access to the resulting log stream (e.g., via a log aggregation pipeline, misconfigured log storage, or shared log access). It does not require operator/admin/host access to trigger the log write itself — any unprivileged client sending a normal Vault JSON-RPC request with an `Auth` token causes the token to be captured in the log. However, actually exploiting the leak requires a secondary condition (read access to debug logs), which is an operational/configuration factor rather than a code-only exploit path.

## Recommendation
Remove `"request", req` from the debug log at `core/services/gateway/handlers/vault/handler.go:403`, or replace it with a redacted projection such as `"hasAuth", req.Auth != ""`, consistent with the pattern already used at line 432 and in `authorizer.go`.

## Proof of Concept
1. Run the gateway with `Debug` log level enabled.
2. Send a Vault JSON-RPC request (e.g., `vault.secrets.list`) with a valid `Auth` JWT to the gateway's public endpoint, invoking `HandleJSONRPCUserMessage`.
3. Observe the `"handling vault request"` debug log entry at line 403 containing the fully serialized `req` struct, including the raw `Auth` token, emitted prior to any authorization check.
4. Extract the token from the log and replay it against the gateway within its validity window to perform Vault secret operations as the original owner.
