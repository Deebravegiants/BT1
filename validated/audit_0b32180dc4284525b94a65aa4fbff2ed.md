### Title
`remove_state_machines` on the GRANDPA/Tendermint consensus pallets can permanently strand in-flight requests, responses, and unclaimed relayer fees for the de-listed chain - (File: `modules/ismp/clients/grandpa/src/lib.rs`)

### Summary
Governance can call `remove_state_machines` (GRANDPA) or `remove_supported_state_machine` (Tendermint) to drop a `StateMachine` from the pallet's whitelist at any time, with no check for outstanding protocol obligations tied to that chain — mirroring the Telcoin `removePlugin` pattern where a component is deactivated/removed without settling what it already owes users.

### Finding Description
`Pallet::remove_state_machines` simply deletes the entry from `SupportedStateMachines` and emits an event, with no validation of pending state for that chain: [1](#0-0) 

The whitelist check gates `ConsensusClient::state_machine()`, which is the single entry point `validate_state_machine` uses (via `handlers.rs`) to obtain a `StateMachineClient` for verifying any membership/non-membership proof for that chain: [2](#0-1) [3](#0-2) 

Once removed, `state_machine(id)` unconditionally returns `GrandpaError::UnsupportedStateMachine`, regardless of whether:
- Requests/responses were already dispatched to or from that chain and are still awaiting delivery or timeout proof,
- Relayers have already delivered messages to/from that chain but have not yet run `accumulate_fees` (which itself calls `validate_state_machine` to verify the withdrawal proof, per `modules/pallets/relayer/src/accumulate.rs`),
- The relayer already has fees sitting in the `Fees` storage double map awaiting a withdrawal-triggering ISMP dispatch that still needs the destination's `HostParams`/state proofs to settle.

This is structurally identical to the reported `StakingModule::removePlugin` bug: a privileged "remove" action tears down the bookkeeping entity (`pluginsMapping` / `SupportedStateMachines`) that a claim/verification path depends on, without any check or soft-delete/deactivation-first mechanism to let outstanding rewards or in-flight messages be settled first.

### Impact Explanation
Because `validate_state_machine` is the sole gate for verifying any Post/Response/Timeout proof against a given `StateMachineId`, de-listing a state machine (even by mistake, or during a benign migration such as swapping to a different consensus client) makes it impossible to:
- Deliver any already-dispatched but undelivered request/response to or from that chain,
- Prove non-membership for a timeout,
- Verify the withdrawal proof needed for `pallet-ismp-relayer::accumulate_fees` for deliveries already made to/from that chain.

Funds already escrowed as relayer/request fees for that chain, and value locked in in-flight cross-chain messages, become permanently unrecoverable through the normal protocol path — a freezing-of-funds outcome analogous to "user cannot claim rewards after plugin removal."

### Likelihood Explanation
This requires the `RootOrigin`/`AdminOrigin` to call `remove_state_machines`/`remove_supported_state_machine`, so it is not attacker-triggered from an untrusted account. However, unlike a malicious-governance scenario, this is a routine governance/operations action (deprecating a chain, migrating consensus clients, correcting a misconfiguration) that has no safeguard against outstanding obligations — the same "not malicious, just missing a safety check" class as the Telcoin finding, which was also triggered by a legitimate role holder (`PLUGIN_EDITOR_ROLE`) performing ordinary maintenance.

### Recommendation
Mirror the Telcoin recommendation: soft-delete instead of hard-delete. Before removing an entry from `SupportedStateMachines`, either:
- Retain a "deprecated but still verifiable" flag so `state_machine()` continues to serve `StateMachineClient` for already-known state commitments (allowing settlement of pending requests/fees), while blocking new consensus updates/new dispatches to that chain; or
- Require an explicit drain/settlement window (e.g., a delay period plus an on-chain check that no unclaimed `Fees` or pending `RequestCommitments`/`ResponseCommitments` exist for that `StateMachine`) before allowing full removal.

### Proof of Concept
1. A relayer delivers a Post request to/from `StateMachine X` and is entitled to a fee, recorded once accumulated via `pallet-ismp-relayer::accumulate_fees`, which internally calls `validate_state_machine` for `X`.
2. Before the relayer submits the accumulation proof, governance calls `GrandpaPallet::remove_state_machines([X])` (a routine deprecation/migration action) as shown in `modules/ismp/clients/grandpa/src/lib.rs:121-134`.
3. The relayer submits `accumulate_fees` with a valid membership proof for the earlier delivery; `validate_state_machine` now calls `consensus_client.state_machine(X)`, which returns `GrandpaError::UnsupportedStateMachine` per `modules/ismp/clients/grandpa/src/consensus.rs:372-378`.
4. The claim permanently fails — there is no other path to prove the delivery and credit the `Fees` map for `X`, so the relayer's earned fee, and any pending request/response destined to/from `X`, can never be settled.

**Note on completeness:** I was unable to fully trace whether there exists a separate emergency path (e.g., a "malicious/frozen state machine" handler mentioned in `handlers.rs` comments — "Checks for frozen state machine is deprecated and malicious state machine commitment will be deleted instead") that might supersede this concern for GRANDPA specifically; that comment suggests the team is aware of state-machine deprecation edge cases but it's unclear whether it fully covers the "remove-then-claim" gap described here. Consider having a Devin session inspect `modules/ismp/core/src/handlers.rs` and the fishermen/malicious-state-machine deletion path in full to confirm whether accrued relayer fees and in-flight requests are protected by any other mechanism before landing this as a finding.

			T::RootOrigin::ensure_origin(origin)?;

			for state_machine in state_machines.clone() {

			}

			Self::deposit_event(Event::StateMachineRemoved { state_machines });

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
