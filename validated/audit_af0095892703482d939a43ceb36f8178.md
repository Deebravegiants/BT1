## Analysis

`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop and topic identifiers used to route and attribute the webhook are taken from unauthenticated HTTP headers: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature strictly against `to_signable_string`, i.e. only the raw body: [3](#0-2) 

`Registry.process` then trusts `request.topic` (unauthenticated header) to select the handler, and forwards `request.shop` (also unauthenticated) as the tenant identity to the handler, with no binding of either value to the HMAC-covered bytes: [4](#0-3) 

### Title
Webhook shop/topic identifiers are not covered by the HMAC signature, enabling cross-tenant payload attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain` or `topic` headers. `Registry.process` nonetheless uses these unauthenticated headers to select the handler and to attribute the payload to a specific shop (`WebhookMetadata#shop`), breaking the equality that should hold: *bytes verified by the HMAC* == *bytes acted upon for tenant/topic attribution*.

### Finding Description
The signable string used for HMAC verification is `@raw_body` alone: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers with no cryptographic tie to the signed body: [5](#0-4) 

`Registry.process` validates only the body's HMAC, then uses the unauthenticated `topic` header to pick a handler and passes the unauthenticated `shop` header straight into `WebhookMetadata` as the tenant identity the handler will act on: [6](#0-5) 

Because only the body bytes are bound to the HMAC, any two requests with identical bodies produce identical valid signatures regardless of which shop or topic header accompanies them. A party who legitimately receives a genuinely-signed webhook for their own tenant (e.g., they installed the app on their own store and triggered an event) possesses a valid `(raw_body, hmac)` pair they never needed the `api_secret_key` to produce. They can resend that exact body+signature to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and/or the `topic` header rewritten to route to a different handler. `Utils::HmacValidator.validate` will still return `true` because it only checks the body, and the handler will process the payload as if it genuinely originated from — and pertains to — the victim's shop/topic.

### Impact Explanation
This breaks the identity binding *shop authenticated == shop acted upon*: the library asserts cryptographic authenticity for the payload but silently extends that trust to unauthenticated routing/attribution fields. Any host application that keys shop-scoped storage, deduplication, or business logic off `WebhookMetadata#shop` (as the documented API encourages) can have attacker-attributable webhook content injected under another tenant's identity — a cross-tenant data-integrity issue reachable by any user who can install the app on a shop they control.

### Likelihood Explanation
Requires only that the attacker installs the target app on a shop they control (an ordinary unprivileged capability for any Shopify merchant/developer) and can direct arbitrary HTTP requests at the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or the merchant's credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. by validating that headers match a value carried inside the signed body), so that `Utils::HmacValidator.validate` actually authenticates the fields `Registry.process` and downstream handlers act on.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook for `orders/create`.
2. Shopify delivers a genuine webhook: body `B`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
3. Attacker captures `(B, H)` and replays it directly to the app's webhook endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes `HMAC(secret, B)` — still equal to `H` — and returns `true`, since `shop` is never part of the signed string.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to process attacker-controlled content as if it were `victim-shop`'s data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
