### Title
Unrestricted `CallDispatcher.dispatch()` allows any address to execute arbitrary calls as the shared dispatcher identity, enabling theft of any balance it holds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated function that executes an attacker-supplied array of `{to, value, data}` calls using the `CallDispatcher` contract's own identity (`msg.sender == CallDispatcher`), with no restriction on caller, on `to`, or on `data`. This is the same root-cause pattern flagged in the external report: a shared contract that will `.call()` into any attacker-chosen target with attacker-chosen calldata on its own behalf. Any value (native ETH or ERC20 tokens) that is ever present on the `CallDispatcher` — even transiently, between the moment funds are pushed to it and the moment the intended sweep-back happens — is reachable by anyone, since nothing gates who may call `dispatch()`.

### Finding Description
`CallDispatcher.dispatch()` [1](#0-0)  takes a raw ABI-encoded `Call[]` and, for every call, forwards `call.value` and `call.data` to `call.to` via a low-level `.call{value: ...}(...)`, reverting only if the target has no code or the call itself reverts. There is no `onlyGateway`, `onlyOwner`, or any check that the caller is one of the trusted intent-gateway/token contracts. The contract also unconditionally accepts native ETH via `receive() external payable {}` [2](#0-1) .

`CallDispatcher` is deployed once and shared across multiple applications — `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` all reference the same `dispatcher` address [3](#0-2) . Funds are routed through it as part of normal flows:
- Predispatch: order input assets are transferred to the dispatcher, user-authored calldata executes (e.g. a Uniswap swap), and the resulting tokens are moved back to the gateway for escrow.
- Postdispatch: after a fill, output tokens/ETH are routed through the dispatcher, and the `_execute()` sweep step iterates only over `order.output.assets` to reclaim any residual balance and account it as protocol dust [4](#0-3) .
- WETH-mode bridging explicitly documents the dispatcher "holding and forwarding native tokens" mid-flow, i.e. the dispatcher is expected to carry a balance between the unwrap step and the forwarded `Call.value` step.

Because the sweep in `_execute()` only walks the tokens enumerated in `order.output.assets`, and predispatch's "transfer back to gateway" step is entirely user-authored calldata (not enforced by protocol code), any token or native ETH that is not explicitly listed/swept (rounding remainder, positive slippage, an incompletely-drained predispatch swap, or WETH unwrap dust) can be left sitting on the shared `CallDispatcher` after a transaction completes. Since `dispatch()` has no access control, any unrelated address can subsequently call it directly with a `Call` that sends that residual balance (or calls `IERC20.transfer`/`approve` on any token the dispatcher currently holds) to themselves.

### Impact Explanation
Because `CallDispatcher` is a single shared instance used by every order/transfer across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, any leftover balance belonging to *any* user's fill/transfer becomes a pooled attack surface reachable by *any* unprivileged caller — exactly the "attacker can steal all funds" pattern from the reference report, just scoped to whatever balance is transiently present rather than the full dealer balance. Given the dispatcher's `receive()` unconditionally accepts ETH and the documented WETH-mode flow depends on the dispatcher briefly carrying native ETH, and the postdispatch sweep is scoped only to the order's declared output assets, this is a concrete theft vector rather than a purely theoretical one.

### Likelihood Explanation
Exploitation requires the dispatcher to actually be holding a nonzero balance at the moment of attack. The protocol's own sweep logic in `_execute()` reduces (but does not eliminate) this window: it only covers tokens listed in `order.output.assets`, not arbitrary tokens, not un-listed native ETH, and not the predispatch leg at all (which relies on user-supplied calldata to fully drain the dispatcher). Slippage, partial swaps, or a poorly-constructed predispatch/postdispatch `Call[]` can leave dust, and the WETH-mode documentation explicitly relies on the dispatcher holding value mid-flow. The root defect — a completely permissionless arbitrary-call primitive with no caller or target restriction — is unconditionally present regardless of whether a given block currently has exploitable dust, making it a standing latent risk rather than a one-off edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the registered/trusted app contracts (e.g. an `onlyAuthorizedCaller` allow-list of `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` instances), mirroring the report's own recommendation of trusting only whitelisted contracts rather than arbitrary callers. Additionally, ensure every code path that routes funds through the dispatcher performs an unconditional, protocol-enforced sweep of both native ETH and all touched ERC20 balances back to the owning contract before the transaction ends, rather than relying on `order.output.assets` enumeration or user-authored calldata to fully drain it.

### Proof of Concept
1. During a predispatch swap (or WETH-mode forward), slippage or an incompletely draining user-authored `Call[]` leaves a small ERC20/ETH balance on the shared `CallDispatcher` after the encompassing transaction completes.
2. An attacker, with no relationship to the order, calls `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls = [Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(address(dispatcher)))})]` (or, for native ETH, `Call({to: attacker, value: address(dispatcher).balance, data: ""})`).
3. `dispatch()` executes this call with no authentication, transferring the dispatcher's residual balance to the attacker [5](#0-4) .

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

                ++i;
            }
        }
```
