Audit Report

## Title
`pool` extrinsic can silently drop the region while returning success when the per-core `Workplan` is full - (File: substrate/frame/broker/src/dispatchable_impls.rs, function `do_pool`)

## Summary
`do_pool` calls `Self::utilize()`, which unconditionally removes the region from `Regions` (only reinstating it when `Finality::Provisional`), and only conditionally records pool bookkeeping (`Workplan`, `InstaPoolIo`, `InstaPoolContribution`) inside an `if workplan.try_push(...).is_ok()` guard. If `try_push` fails because the bounded `Workplan` entry for `(begin, core)` is already full, the function still unconditionally emits `Event::Pooled` and returns `Ok(())`, even though no pool bookkeeping was written and, for `Finality::Final`, the region was permanently destroyed with no compensation.

## Finding Description
The code matches the claim exactly: [1](#0-0)  shows `do_pool` gating `Workplan`/`InstaPoolIo`/`InstaPoolContribution` writes behind `workplan.try_push(...).is_ok()`, but emitting `Event::Pooled` and returning `Ok(())` unconditionally regardless of that check's outcome.

`utilize()` unconditionally removes the region via `Regions::<T>::remove(&region_id)` and only reinserts it when `finality == Finality::Provisional`, meaning a `Finality::Final` call permanently destroys the region record before `do_pool` even attempts the bookkeeping write: [2](#0-1) .

The extrinsic wrapper `pool` further makes `Finality::Final` calls fee-free (`Pays::No`), compounding the issue since the attacker pays nothing for triggering the loss: [3](#0-2) .

Crucially, I found the `Workplan` bound is `Schedule = BoundedVec<ScheduleItem, ConstU32<{ CORE_MASK_BITS as u32 }>>`, i.e., a fixed, small, attacker-known constant (`CORE_MASK_BITS`, 80 bits per core mask): [4](#0-3) .

Moreover, comparing `do_pool` to the sibling function `do_assign` reveals `do_assign` performs `workplan.retain(|i| (i.mask & region_id.mask).is_void())` before `try_push`, removing conflicting/overlapping entries so the workplan stays bounded to actual disjoint mask fragments: [5](#0-4) . `do_pool` has **no equivalent `retain` call**, so repeated `pool` calls with `Finality::Provisional` on the *same* region (which stays in `Regions` after each call since `Provisional` reinserts it) will keep appending duplicate/overlapping `ScheduleItem { mask: region_id.mask, assignment: Pool }` entries to the same `Workplan` slot. This means an unprivileged owner of a single purchased core can trivially fill the 80-item bound by calling `pool(region_id, payee, Provisional)` 80 times on the exact same region — no need for `interlace` fragmentation at all. Once full, a subsequent `pool(region_id, payee, Final)` call passes `utilize()` (destroying the region permanently), fails `try_push` silently, and still emits `Event::Pooled` and returns success.

## Impact Explanation
This is a real, in-scope broken-accounting bug: a signed, unprivileged account (any core owner) can destroy a coretime region — a valuable, saleable resource — while the pallet's event and dispatch result falsely report success, and for `Finality::Final` the region simply vanishes from `Regions` with no `InstaPoolContribution` ever recorded and no way to reconcile via `claim_revenue` or any other public call. The `Pays::No` fee waiver for `Finality::Final` makes this free to execute, and the existing per-region "no-op if occupied" guard in `do_assign` (the `retain` step) demonstrates the pallet authors were aware of workplan-capacity/overlap concerns for that path but failed to apply an equivalent safeguard or hard error to `do_pool`.

## Likelihood Explanation
Highly likely and fully deterministic: an attacker only needs to own (purchase) a single core and issue up to `CORE_MASK_BITS` (80) plain signed `pool` calls with `Finality::Provisional` on the same region to fill the bound (no race condition, no special privilege, no interlace complexity required), followed by one final `pool` call with `Finality::Final` on a fragment/region sharing that `(begin, core)` key to trigger the destructive silent-drop path. This is reproducible in a single test run or block sequence.

## Recommendation
- In `do_pool`, propagate a hard error (e.g., a new `Error::<T>::TooManyWorkplanItems`) when `workplan.try_push` fails, instead of silently skipping bookkeeping and still returning `Ok(())`.
- Move `Self::deposit_event(Event::Pooled { .. })` inside the successful `try_push` branch only.
- Add a `workplan.retain(...)` step (mirroring `do_assign`) before `try_push` to prevent duplicate/overlapping entries from consuming the bounded capacity unnecessarily, and/or check workplan capacity before calling `utilize()` so the irreversible `Regions::remove` for `Finality::Final` never executes when pooling cannot be completed.

## Proof of Concept
1. `do_start_sales`, then `do_purchase` a core to obtain `region_id` covering `CoreMask::complete()`.
2. Repeatedly call `Broker::pool(signed(owner), region_id, payee, Finality::Provisional)` up to `CORE_MASK_BITS` (80) times — since `Finality::Provisional` reinserts the region into `Regions` after each call and `do_pool` has no `retain` step, each call appends another duplicate `ScheduleItem` to `Workplan::get((region_id.begin, region_id.core))`, filling it to its bounded capacity.
3. Call `Broker::pool(signed(owner), region_id, payee, Finality::Final)`.
4. Assert:
   - The call returns `Ok(_)` and `Event::Pooled { region_id, .. }` is emitted.
   - `Regions::<Test>::get(&region_id)` is `None` (region destroyed).
   - `InstaPoolContribution::<Test>::get(&region_id)` is `None` (no bookkeeping created).
   - `Broker::do_claim_revenue(region_id, ...)` subsequently returns an unknown-contribution error, confirming the region's coretime is unrecoverable despite the reported "success".

	pub(crate) fn do_pool(
		region_id: RegionId,
		maybe_check_owner: Option<T::AccountId>,
		payee: T::AccountId,
		finality: Finality,
	) -> Result<(), Error<T>> {
		if let Some((region_id, region)) = Self::utilize(region_id, maybe_check_owner, finality)? {
			let workplan_key = (region_id.begin, region_id.core);
			let mut workplan = Workplan::<T>::get(&workplan_key).unwrap_or_default();
			let duration = region.end.saturating_sub(region_id.begin);
			if workplan
				.try_push(ScheduleItem { mask: region_id.mask, assignment: CoreAssignment::Pool })
				.is_ok()
			{
				Workplan::<T>::insert(&workplan_key, &workplan);
				let size = region_id.mask.count_ones() as i32;
				InstaPoolIo::<T>::mutate(region_id.begin, |a| a.private.saturating_accrue(size));
				InstaPoolIo::<T>::mutate(region.end, |a| a.private.saturating_reduce(size));
				let record = ContributionRecord { length: duration, payee };
				InstaPoolContribution::<T>::insert(&region_id, record);
			}

			Self::deposit_event(Event::Pooled { region_id, duration });
		}
		Ok(())
	}
