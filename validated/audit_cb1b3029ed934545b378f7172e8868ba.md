## Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` (or `shopify-shop-domain`) header to decide which tenant ("shop") the webhook belongs to. Because the header is not part of the signed material, any party who can obtain one valid `(body, hmac)` pair signed with the app's real `api_secret_key` — for example by installing the app on their own store and receiving a legitimate webhook — can replay that exact body/HMAC pair against the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, and the handler is invoked with attacker-chosen `shop` attribution.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read directly from the (attacker-controlled, if the attacker can reach the endpoint) HTTP header, independent of the signed body: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `to_signable_string`, i.e. the raw body, with the app's `api_secret_key`: [3](#0-2) 

`Registry.process` uses this HMAC validation as its sole authentication check, then forwards `request.shop` (the unsigned header value) straight into the data handed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop used for tenant attribution passed to the handler`

But in this code, the HMAC only authenticates `raw_body` — it never binds `shop`, `topic`, `webhook_id`, or `api_version`. So the equality that actually holds is:
`shop authenticated by HMAC == "" (nothing)`  while  `shop used for tenant attribution == unauthenticated header value`

This lets anyone possessing one legitimate `(raw_body, hmac)` pair for the shared `api_secret_key` (trivially obtained by installing the app themselves) present that same pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming any other merchant. `Utils::HmacValidator.validate` will return `true`, and `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)` will be dispatched to the app's handler tagged with the victim's shop domain.

### Impact Explanation
This breaks the tenant boundary that webhook consumers rely on: any host application that keys persistence, authorization, or side effects (e.g., "look up shop record by `data.shop` and write body contents") off `WebhookMetadata#shop` can be made to write or act on data under an arbitrary victim shop's identity using a signature that is only valid for the attacker's own shop. This is a cross-tenant integrity/confidentiality issue reachable by any unprivileged party who has installed (or can install) the app once, without needing the `api_secret_key`, an access token, or any privileged credential of the victim.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any store (including a free development store) to receive one legitimately-signed webhook, and (2) the ability to POST directly to the app's public webhook endpoint with custom headers — both readily available to any unprivileged internet user, with no dependence on leaked secrets or host-application misconfiguration beyond the documented, expected use of `Registry.process`/`Webhooks::Request` exactly as designed.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the shop returned against a value obtained via an authenticated channel, such as an already-stored session/access token for that shop, rather than trusting the raw header). At minimum, document prominently that `request.shop` is not authenticated by `HmacValidator.validate` so host applications do not treat it as a trusted tenant identifier.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggers a webhook (e.g. `orders/create`), and captures the raw POST body and its `x-shopify-hmac-sha256` header — both are valid under the app's real `api_secret_key`.
2. Attacker POSTs to the app's webhook endpoint, reusing the exact captured `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object where `hmac` validates successfully via `Utils::HmacValidator.validate` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`, which only checks the raw body) because the shop-domain header is never part of `to_signable_string`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host application to process attacker-controlled webhook data as if it belongs to the victim shop.
