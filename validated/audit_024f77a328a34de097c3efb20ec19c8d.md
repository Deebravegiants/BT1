### Title
OAuth callback sends `client_secret` to an unvalidated `shop` host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` derives the token-exchange request host directly from the caller-supplied `auth_query.shop` value without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchanging flow in the gem. The HMAC check that runs beforehand only proves the query string was signed with `api_secret_key`; it does not constrain `shop` to a legitimate `*.myshopify.com`/trusted domain. That unvalidated value becomes the host the app's `client_id`/`client_secret`/authorization `code` are POSTed to.

### Finding Description
`validate_auth_callback` validates the callback's authenticity purely via `Utils::HmacValidator.validate(auth_query)`, then immediately builds a session and HTTP client from the raw `shop` field: [1](#0-0) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (which includes `shop`, but only as signed data, not as a validated domain) and compares it with `OpenSSL.secure_compare`: [2](#0-1) [3](#0-2) 

That check answers "was this string signed with our secret", not "is `shop` a real Shopify store host" - the two are different bindings. The unvalidated `shop` is then used to construct `Auth::Session.new(shop: auth_query.shop)`, which `Clients::HttpClient` turns directly into the request host (`https://#{session.shop}`), and the POST body containing `client_id`, `client_secret`, and `code` is sent there: [4](#0-3) [5](#0-4) 

By contrast, every other credential-exchange entry point in the same gem explicitly sanitizes `shop` through `Utils::ShopValidator.sanitize!` — which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before it is ever used to build a request host: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

`Oauth.begin_auth`, which starts the flow and is the origin of the `shop` value round-tripped through the callback, likewise never calls `ShopValidator` — it only special-cases a dev-server suffix and otherwise uses the raw `shop` string to build the authorize redirect URL: [10](#0-9) [11](#0-10) 

This is the analog called out in the task's bug-class list: "a host validated [by HMAC/signature] versus the host that receives the access token or `client_secret`." The signature check and the host-selection check are two different assertions, and only one of them is enforced on this code path.

### Impact Explanation
If `shop` is not constrained to a genuine Shopify domain, `validate_auth_callback` will POST the app's `client_id` and `client_secret` (plus the OAuth authorization `code`) to whatever host ends up in `auth_query.shop`/`session.shop`. That is SSRF carrying the app's own `client_secret` to an attacker-influenced host — one of the explicitly in-scope High-severity impacts (SSRF with the app's credentials / credential leakage). It is architecturally inconsistent with `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, which all treat `shop` as untrusted input requiring `ShopValidator.sanitize!` before it is allowed to become a request host.

### Likelihood Explanation
I could not fully confirm an end-to-end unprivileged-attacker trigger from within this gem alone. In the standard Authorization Code Grant flow, the `shop`/`hmac` pair in the callback is normally produced by Shopify's own server after HMAC-signing with the app's `api_secret_key`, which an outside attacker doesn't possess, so forging a fresh valid `(shop, hmac)` pair with an attacker-controlled host is not achievable purely from the internet. The realistic risk surface is `begin_auth`, which accepts `shop` before any Shopify-side signing occurs; if a host application forwards an unsanitized `shop` query-string value into `begin_auth`, the constructed authorize URL/host is attacker-influenced, and it is that same unsanitized value that later reappears in the callback. Whether this rises to the "host application ignoring documented API" exclusion depends on whether the gem's docs instruct callers to pre-validate `shop` before calling `begin_auth`/`validate_auth_callback` (I did not find such a rule stated, but the docs are extensive and I could not confirm its absence with full confidence). Given the internal inconsistency — the gem enforces this exact validation in three sibling flows but not in `oauth.rb` — I assess this as a genuine defense-in-depth gap in the gem itself rather than purely a caller error, but with residual uncertainty about the fully unauthenticated end-to-end path through the classic Authorization Code Grant redirect.

### Recommendation
In `Oauth.begin_auth` and `Oauth.validate_auth_callback`, call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) before using `shop` to build the authorize redirect host or the `Auth::Session` passed to `Clients::HttpClient`, mirroring the pattern already used in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`. This ensures `client_secret` can only ever be sent to a trusted Shopify domain.

### Proof of Concept
Not fully constructible from the gem's code alone — the exploit's feasibility depends on whether/how a host application passes attacker-influenced `shop` values into `Oauth.begin_auth` before Shopify signs the callback, which is outside this repository.         def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
