## Finding: Webhook `shop` (and other headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The library validates webhook authenticity via `ShopifyAPI::Utils::HmacValidator.validate`, but the HMAC signature only covers the raw request body — not the `shop-domain`, `topic`, or `webhook-id` headers that the app subsequently trusts as the multi-tenant identity of the event. This breaks the identity binding: *the shop whose HMAC was verified* (implicitly, the shop that generated the signed body) is not equal to *the shop attributed to the resulting data* (`request.shop`, read from an unauthenticated header).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and, on success, immediately trusts `request.shop` as the tenant identity for dispatch: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`, which is identical for every shop that has installed the app: [4](#0-3) 

Because the same `api_secret_key` signs webhooks for *every* shop that installed the app, and the signature never binds to `shop-domain`, a party who has legitimately installed the app on their own (attacker-controlled) shop can:
1. Receive a real, validly-signed webhook for their own shop (e.g. `orders/create`) — HMAC = `HMAC(api_secret_key, raw_body)`.
2. Replay the identical `raw_body` + `x-shopify-hmac-sha256` value to the app's shared webhook endpoint, but substitute `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` still passes, because it only checks the body, not the header.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop` now equal to the victim's domain, so the app processes attacker-controlled data as if it came from the victim tenant.

The binding that is broken: **shop cryptographically authenticated (none — HMAC only covers body) ≠ shop used as the tenant/session key for handling the webhook (`request.shop` header)**.

### Impact Explanation
This directly enables cross-tenant data injection: an attacker with a legitimate (even free/dev) install of the app can forge webhook events that appear to originate from a completely different merchant shop. Depending on the handler's logic (e.g. updating shop-scoped records, triggering shop-scoped side effects, writing to a shop's database row keyed by `shop`), this can corrupt or manipulate a victim tenant's data using an attacker-controlled payload — a cross-tenant access vulnerability.

### Likelihood Explanation
Any app built on this gem exposing a single shared webhook endpoint for multiple shops (the standard multi-tenant SaaS pattern this gem is designed for) is affected. The attacker only needs their own valid app install to obtain a correctly-signed body/HMAC pair, then can freely relabel the `shop-domain` header — no access to the app's `client_secret` or the victim's credentials is required.

### Recommendation
- Include the shop domain (and ideally the topic/webhook-id) in the signed payload used for HMAC verification, or independently verify that the `x-shopify-shop-domain` header corresponds to a shop with a currently valid, stored session/installation before dispatching to handlers.
- Short term: require callers to cross-check `request.shop` against their own record of installed shops (with an access token on file) before trusting webhook data, and document this requirement prominently since the gem does not enforce it.
- Long term: bind the shop identity into the verified signature material rather than trusting an unauthenticated header field.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives a real webhook, e.g.:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker replays it to the shared webhook endpoint with a spoofed shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    handler.handle receives shop: "victim-shop.myshopify.com" with attacker-chosen body.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []

          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
