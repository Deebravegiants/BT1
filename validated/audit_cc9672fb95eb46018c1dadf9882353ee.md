## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and validates only the raw request body via HMAC, while the `shop-domain` header — the value used to attribute the webhook payload to a specific merchant/tenant — is read directly from an unsigned HTTP header and passed straight to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (the body), never over any header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` — taken from the unsigned header — to build the `WebhookMetadata` passed to the app's handler, with no additional binding check between the signed body and the claimed shop: [4](#0-3) 

This breaks the identity binding the gem implicitly promises to the host application: `HMAC-valid(raw_body) == authentic(shop-domain header)`. In reality the binding only proves `HMAC-valid(raw_body)`; the `shop` field can be swapped freely because it sits outside the signed payload.

### Impact Explanation
An unprivileged internet user who owns any shop with the app installed will legitimately receive real Shopify webhooks (valid body + valid HMAC, since Shopify itself computes the signature with the app's shared secret over the body only). That user can capture one such `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain. Because `HmacValidator.validate` never inspects the header, the forged request passes validation, and `Webhooks::Registry.process` dispatches the payload to the app's handler tagged with the attacker-chosen victim shop. Any app logic that trusts `WebhookMetadata#shop` to select which tenant's data/store to update (a common pattern) can be corrupted with attacker-supplied data attributed to another merchant — a cross-tenant data-integrity break reachable by any user with a self-service shop and no access to the app's `client_secret` or any victim credentials.

### Likelihood Explanation
Any developer using an app on Shopify's platform can trivially obtain a real webhook (valid body/HMAC pair) for their own shop, then script a replay with a modified `shop-domain` header against the target app's public webhook URL. No secrets, tokens, or privileged access are required beyond running a standard developer/partner shop, making this readily reachable by an unprivileged internet user.

### Recommendation
Bind the shop identity to the signed payload before trusting it — e.g., include the shop domain (and topic/webhook id) inside the HMAC-signed material, or cross-check `request.shop` against the shop that the topic/webhook_id was registered for, or require that the resolved shop have an active, previously-established session/installation record before dispatching webhook data to handlers.

### Proof of Concept
1. Install the target app on an attacker-controlled development shop `attacker.myshopify.com`; trigger a real event (e.g., `orders/create`) so Shopify sends a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC over `B` using the app's secret), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and `H` from the attacker's own server logs.
3. Send a new POST to the same app webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`), and `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
