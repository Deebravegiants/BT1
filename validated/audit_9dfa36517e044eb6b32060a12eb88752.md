### Title
Retroactive rate application in `update_cost_per_block` causes mis-priced relayer rewards for already-accrued blocks - ([File: modules/pallets/consensus-incentives/src/lib.rs])

### Summary
`update_cost_per_block` in `pallet-consensus-incentives` overwrites `StateMachinesCostPerBlock` immediately, with no step that first settles (pays out) the reward accrued for blocks between the last-rewarded watermark and the current chain height under the *old* rate. The next relayer delivery that triggers `FeeHandler::on_executed` computes the reward for that entire pending span using the *new* rate stored at that time, exactly the same bug class as `setTreasuryWeights` missing `processInterests`: a rate/weight change is applied retroactively to a period that should have accrued value under the previous rate.

### Finding Description
`update_cost_per_block` is governance-gated (`T::IncentivesOrigin`) and simply mutates the stored rate: [1](#0-0) 

There is no call into `process_message`/`calculate_reward` before the mutation to flush the reward owed for blocks already accrued under the old `cost_per_block`. The reward computation itself always reads the *current* `StateMachinesCostPerBlock` value and multiplies it by the full unpaid span since `LastRewardedHeight`: [2](#0-1) 

`process_message`, invoked from `FeeHandler::on_executed` (which fires whenever any relayer successfully delivers a consensus message), reads the *live* `StateMachinesCostPerBlock` at that moment: [3](#0-2) 

So the sequence is:
1. Governance sets `cost_per_block = X` for a state machine. Blocks accrue between the last-rewarded height and the point where governance later changes the rate.
2. Governance calls `update_cost_per_block` again to set `cost_per_block = Y` (raised or lowered) — no settlement happens for the pending span priced at `X`.
3. Any unprivileged relayer delivers the next consensus message. `on_executed` → `process_message` → `calculate_reward` computes `blocks = latest_height - LastRewardedHeight` and multiplies the *entire* span (including blocks that accrued under the old rate `X`) by the new rate `Y`.

This mirrors the reported analog precisely: the weight/rate parameter is changed without first processing (settling) what had already accumulated at the old rate, so the update is retroactively (mis)applied.

### Impact Explanation
If governance raises `cost_per_block`, the treasury overpays: blocks that should have been rewarded at the old, lower rate are paid at the new, higher rate, directly draining `T::TreasuryAccount` for value it never owed. If governance lowers the rate, relayers are underpaid for blocks delivered under the previous (higher) rate, an unbacked loss of yield to relayers. Either direction is a concrete loss of funds triggered by a routine reward-rate change plus the very next ordinary, unprivileged relayer delivery — matching the "loss of yield for the treasury or pool participants" impact of the original finding.

### Likelihood Explanation
This requires no adversarial relayer action; the very next legitimate consensus delivery after any `update_cost_per_block` call exercises the mispriced span. Given that `cost_per_block` is expected to be adjusted periodically by governance as market conditions/incentive targets change, and any window between a rate update and the next relayer delivery contains exactly the mispriced blocks, this is a routine occurrence, not an edge case requiring privileged or malicious behavior.

### Recommendation
Before mutating `StateMachinesCostPerBlock` in `update_cost_per_block` (and in `remove_incentives`), settle the pending reward for the affected `state_machine_id` at the currently stored rate — i.e., compute and pay out (or otherwise checkpoint) `calculate_reward` against the old rate and advance `LastRewardedHeight` to the current `latest_commitment_height`, then apply the new rate. This ensures a rate/weight change only affects blocks accrued from that point forward, analogous to adding the `processInterests` modifier before `setTreasuryWeights`.

### Proof of Concept
1. Governance calls `update_cost_per_block(state_machine_id, X)`.
2. Consensus proofs advance `latest_commitment_height` for `state_machine_id` by `N` blocks with no relayer delivery of a message that triggers `on_executed` in between (e.g., the relayer batches consensus updates before submitting, or simply delays claiming).
3. Governance calls `update_cost_per_block(state_machine_id, Y)` where `Y >> X` (e.g., raising the rate 10x in response to changed market conditions).
4. Any relayer submits a `Consensus` message that results in a `StateMachineUpdated` event; `FeeHandler::on_executed` fires.
5. `calculate_reward` computes `reward = N * Y` instead of the expected `N * X`, and `T::Currency::transfer` pays this out from `T::TreasuryAccount`, i.e., the treasury pays `N * (Y - X)` in excess for blocks that accrued entirely under the old rate `X`. This is verifiable by extending the existing test in `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs` (see `reward_covers_only_unpaid_heights_after_rollback`) to insert an `update_cost_per_block` call between two `store_latest_commitment_height` advances and observing the treasury debit uses the post-update rate for the whole span.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
