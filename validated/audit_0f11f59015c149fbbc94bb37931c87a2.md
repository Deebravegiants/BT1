### Title
Reward-map overwrite loses protocol-treasury reward when the treasury account is also a validator, causing total-supply/ledger divergence - (File: `chain/epoch-manager/src/reward_calculator.rs`)

### Summary
`RewardCalculator::calculate_reward` inserts the protocol-treasury reward into a `HashMap<AccountId, Balance>` keyed by `protocol_treasury_account`, and later inserts each validator's own reward into the same map keyed by `account_id`. If `protocol_treasury_account` is also present in `validator_block_chunk_stats` (i.e. the treasury account is staking as a validator), the second `insert` silently overwrites the first, exactly the "self-referential key collision" root cause described in the Flayer `_distributeFees()` report (where `beneficiaryFee` is dropped because `poolId == _poolKeys[beneficiary].toId()`).

### Finding Description
In `calculate_reward` (`chain/epoch-manager/src/reward_calculator.rs:51-146`):

```rust
res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury); // line 84
...
let mut epoch_actual_reward = epoch_protocol_treasury;                       // line 90
for (account_id, stats) in validator_block_chunk_stats {
    let reward = ...;
    res.insert(account_id, reward);                                          // line 142 — OVERWRITES treasury entry if account_id == protocol_treasury_account
    epoch_actual_reward = epoch_actual_reward.checked_add(reward).unwrap();   // line 143 — correctly sums both parts
}
(res, epoch_actual_reward)
``` [1](#0-0) [2](#0-1) 

If the account id equal to `protocol_treasury_account` is also in `validator_block_chunk_stats` (i.e. it is staking as a normal validator via an ordinary `Stake` action), `res.insert(account_id, reward)` **replaces** the treasury's `epoch_protocol_treasury` entry with just its own validator `reward`, instead of summing them. However, `epoch_actual_reward` (the scalar returned as `minted_amount`) is accumulated correctly and always includes the full `epoch_protocol_treasury + reward`.

This inconsistency propagates downstream:
- `minted_amount`/`epoch_actual_reward` is stored on `EpochInfo` and later added to `total_supply` in `core/primitives/src/block.rs` (`new_total_supply = prev + minted − burnt`), unconditionally including the full treasury share.
- The (corrupted) `res` map becomes `validator_reward` on `EpochInfo`, is returned by `EpochManager::compute_stake_return_info` (`chain/epoch-manager/src/lib.rs:1648-1688`) and flows into `ValidatorAccountsUpdate.validator_rewards`.
- In `Runtime::update_validator_accounts` (`runtime/runtime/src/lib.rs:1663-1759`), because the treasury account is present in `stake_info` (since it's a validator), the loop over `stake_info` credits only the (overwritten, smaller) reward to `account.locked()`. The subsequent block explicitly *skips* crediting the separate treasury balance, with the comment "If protocol treasury stakes, then the rewards was already distributed above" (`runtime/runtime/src/lib.rs:1728-1730`), which assumes the map contains the combined amount — an assumption invalidated by the overwrite bug. [3](#0-2) 

The net effect: `epoch_protocol_treasury` yoctoNEAR are counted in `total_supply` (minted) but never actually credited to any account balance — a silent, permanent token loss and a `total_supply` vs. sum-of-balances divergence.

### Impact Explanation
This breaks the protocol's core supply invariant that `total_supply` equals the sum of all account balances/locked stakes (exercised by tests such as `test_burn_mint` and `calc_total_supply`). Every epoch in which the treasury account is also a staking validator, an amount equal to `epoch_protocol_treasury` is minted into `total_supply` but is unaccounted for in any account — a state/ledger divergence and unrecoverable loss of the treasury's inflation share. This is a concrete accounting/state-divergence bug, not merely cosmetic.

### Likelihood Explanation
The bug triggers whenever `protocol_treasury_account` is also included in the current epoch's validator set. This can happen simply because the entity controlling the treasury account submits an ordinary, unprivileged `Stake` action transaction (no special permission required) — the exact same transaction any account can send. This is realistic on non-mainnet networks (testnets, custom/private chains, sandbox environments) where the treasury account is not specially restricted from staking, and it requires no validator, P2P, or privileged access — only a standard `Stake` transaction from the treasury account.

### Recommendation
Accumulate rather than overwrite the reward for a validator account that coincides with `protocol_treasury_account`:

```rust
res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
...
for (account_id, stats) in validator_block_chunk_stats {
    let reward = ...;
    res.entry(account_id)
        .and_modify(|existing| *existing = existing.checked_add(reward).unwrap())
        .or_insert(reward);
    epoch_actual_reward = epoch_actual_reward.checked_add(reward).unwrap();
}
```
Additionally, `update_validator_accounts` in `runtime/runtime/src/lib.rs` should not assume the "already distributed above" invariant without verifying the combined value actually reflects both components.

### Proof of Concept
1. Configure a genesis/`TestLoopBuilder` where `protocol_treasury_account` is set to one of the validator accounts (e.g. reuse `test1` as `protocol_treasury_account`), similar to how `test_inflation`/`test_validator_reward` in `test-loop-tests/src/tests/stake_nodes.rs` and `chain/chain/src/runtime/tests.rs` set up rewards.
2. Run the network past an epoch boundary so `RewardCalculator::calculate_reward` executes with `test1` present both as `protocol_treasury_account` and in `validator_block_chunk_stats`.
3. Observe:
   - `block.header().total_supply()` increases by `epoch_actual_reward = epoch_protocol_treasury + test1_validator_reward` (per `core/primitives/src/block.rs` supply update).
   - `test1`'s account `locked`/`amount` balance only increases by `test1_validator_reward` (per `update_validator_accounts` in `runtime/runtime/src/lib.rs:1668-1726`), because the treasury-specific credit block at `runtime/runtime/src/lib.rs:1728-1755` is skipped (`stake_info.contains_key(account_id)` is true).
   - Summing all account balances after the epoch boundary is short by exactly `epoch_protocol_treasury`, versus `total_supply`, demonstrating the ledger/supply divergence and lost treasury reward.
