## Analysis Result

I found a concrete analog. `register_token` in `pallet-hyper-fungible-token` can be called again on an `asset_id` that is already registered and already has funds escrowed under its previous custody model, silently flipping the `NativeAssets` custody flag without touching the tokens that are already held in escrow — the same root cause pattern as the reported `ERC20Rebasing` bug (switching a mode/flag while ignoring the balance/state accrued under the old mode).

### Title
Re-registering an existing asset in `register_token` flips custody model and strands/duplicates escrowed funds - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`register_token` unconditionally overwrites `NativeAssets::<T>` for the given `asset_id` with the new `registration.native` flag [1](#0-0) , with no check that the asset is unregistered and no reconciliation of tokens already escrowed/burned under the previous custody model.

### Finding Description
`send()` branches on `NativeAssets::<T>::get(asset_id)`: if `native == true`, it moves the caller's balance into the pallet's escrow account (`Self::pallet_account()`); if `native == false`, it burns the balance outright [2](#0-1) . Symmetrically, `on_accept`/`on_timeout` release from escrow for native assets or mint fresh supply for non-native assets, per the pallet's own documentation of the two custody models [3](#0-2) .

`register_token` is meant to be a one-time setup call for a new asset, but nothing in its implementation checks whether `registration.local_id` is already registered — it just does `NativeAssets::<T>::insert(registration.local_id.clone(), registration.native)` unconditionally [4](#0-3) , and re-inserts `TokenContracts`/`ContractToAsset`/`Precisions` for whatever chains are passed [5](#0-4) . `CreateOrigin` calling `register_token` a second time on the same `local_id` — flipping `native` from `true` to `false` (or vice versa) — instantly changes the custody-model interpretation for any balance that is currently escrowed in `Self::pallet_account()` from prior `send()` calls, exactly like the reported bug where switching yield mode ignores the portion of balance accrued under the prior mode.

Concretely:
- If an asset was registered `native = true` and users escrowed real tokens into the pallet account via `send()`, then `CreateOrigin` re-registers it `native = false`, subsequent `send()` calls will now **burn** user tokens (correct for the new model) while the previously escrowed tokens sitting in the pallet account are never accounted for by `on_accept`/`on_timeout`, which now **mint fresh supply** instead of releasing escrow — the old escrowed balance becomes permanently stranded/unbacked-orphaned in the pallet's account.
- Conversely, flipping `native = false → true` while an inflated remote representation exists (previously backed by burn/mint) suddenly makes new sends escrow into a pallet account that isn't sized to back existing minted-and-not-yet-returned foreign supply, breaking the 1:1 backing invariant described for `BridgeToken`/HFT pairs [6](#0-5) .

### Impact Explanation
This breaks the fund-backing invariant central to the HFT bridging model: escrowed native balances must always back the remote-side minted supply 1:1. A custody-model flip on an already-escrowed asset either strands user-owned escrowed funds permanently (they can never be released because the release path no longer reads/decrements escrow) or de-syncs the mint/burn supply from real backing, allowing over-minting on the EVM side relative to real collateral. Both are Critical-class fund-loss / unbacked-mint outcomes reachable via a single dispatched cross-chain `send` transaction plus a governance re-registration call.

### Likelihood Explanation
`register_token` is gated by `T::CreateOrigin` (governance/root in the reference runtime configs) [7](#0-6) , so this is not directly attacker-triggerable by an unprivileged user; it requires a governance action (intentional or mistaken) to re-register an asset that already has live escrow/mint state. Given no protective check exists in code (`ensure!(!NativeAssets::<T>::contains_key(...))` is absent), an operational mistake by the token administrator — e.g., correcting a registration or adding chains via `register_token` instead of `update_token` — silently corrupts custody accounting with no revert and no warning.

### Recommendation
In `register_token`, reject re-registration of an already-known `asset_id` (`ensure!(!NativeAssets::<T>::contains_key(&registration.local_id), Error::<T>::AssetAlreadyRegistered)`), forcing any custody-model change to go through an explicit migration path that first accounts for existing escrowed/circulating balance (mirroring the report's recommendation to fold the full balance, not just part of it, into the new mode before switching).

### Proof of Concept
1. `CreateOrigin` calls `register_token` with `local_id = X`, `native = true`, registering an EVM `HyperFungibleToken` peer.
2. A user calls `send(asset_id = X, amount = 1000)`; the pallet escrows 1000 units of `X` into `Self::pallet_account()` [8](#0-7) .
3. `CreateOrigin` calls `register_token` again with `local_id = X`, `native = false` (e.g., meaning to just add a chain but using the wrong extrinsic). `NativeAssets::<T>::get(X)` now returns `false`.
4. A new `send(asset_id = X, amount = 500)` now burns the caller's 500 units instead of escrowing them [9](#0-8) .
5. When the corresponding EVM message returns via `on_accept`, the pallet now mints fresh `X` to the beneficiary instead of releasing from the 1000-unit escrow, which remains permanently locked in `Self::pallet_account()` with no code path left that decrements it under the new `native = false` branch — the original users' 1000 units are stranded forever while new supply is minted unbacked.
