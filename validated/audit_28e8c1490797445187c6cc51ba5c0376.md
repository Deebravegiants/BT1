### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, but the HMAC verification only authenticates the raw request body. The `shop` value passed to the handler is read straight from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header and is never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is derived purely from a header, independent of that signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` only checks this body HMAC, then forwards `request.shop` (the unauthenticated header) directly into the data given to the app's handler: [4](#0-3) 

The documented contract for `Registry.process` explicitly claims full request authenticity: [5](#0-4) 

The identity-binding equality this breaks is: `shop authenticated-by-HMAC` (empty set — no shop value is signed) vs. `shop the handler acts on` (`data.shop`, taken from `WebhookMetadata.shop` populated from `request.shop`). An attacker who has legitimately installed the app on a shop they control receives genuine webhooks — plaintext body plus a valid HMAC computed with the app's shared secret — at their own endpoint. Because the HMAC covers only the body, that exact `(body, hmac)` pair remains valid regardless of which `shop`-domain header accompanies it. The attacker can then submit the same body+HMAC to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` value (e.g., a different, real merchant's domain). `HmacValidator.validate` still succeeds because it never checked the shop field, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen domain.

Any application logic that trusts `data.shop` from the handler (e.g., updating per-tenant database rows, triggering per-shop side effects, attributing webhook content to a shop record) can therefore be made to act on/for a shop the attacker does not control, using data whose provenance is actually a different, attacker-owned shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the field used for tenant attribution (`shop`) is fully controllable by an unauthenticated actor even though the request otherwise passes signature verification. Depending on how the host app's `handle` method uses `data.shop` (as virtually every consumer does, per the gem's own documented example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this allows cross-tenant data injection/overwrite attributed to an arbitrary shop domain — a Critical-severity cross-tenant access issue.

### Likelihood Explanation
Exploitability only requires that the attacker have installed the app on any shop they control (a normal, free, unprivileged action for any Shopify merchant/developer) and be able to replay an HTTP request they already legitimately received at their own server, modifying only the `x-shopify-shop-domain` header. No secret key, TLS interception, or privileged access is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the HMAC-signed content, or otherwise cryptographically tie the shop attribution to the signature, so that `Utils::HmacValidator.validate` fails if the shop header is altered relative to what was actually signed by Shopify for that body.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Resend the identical `B`/`H` to the same webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (or `x-shopify-topic` if needed).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied content as though it belongs to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
