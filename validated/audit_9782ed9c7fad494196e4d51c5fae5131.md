## Finding

### Title
Unbounded ownership-chain walk in `Object::root_owner()` enables self-referential object cycles that permanently brick custody logic gated on it - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks an object's ownership chain with **no depth bound**, unlike the sibling function `object::owns()`, which is explicitly capped at `MAXIMUM_OBJECT_NESTING` (8 hops) and asserts on `EMAXIMUM_NESTING`. `root_owner()` is the authoritative function used by `aptos_framework::code::publish_package` and `aptos_framework::init::assert_may_self_initialize` to gate a code-object's lazy self-initialization (i.e., minting a `signer` for the object's address). A user can construct a legitimate 2-hop ownership cycle across two objects they control (using two consecutive, individually-valid `object::transfer` calls), after which any call to `root_owner()` on either object never terminates and aborts on out-of-gas, permanently blocking `internal_maybe_initialize` (and any other code relying on `root_owner`) for that address.

### Finding Description
Compare the two ownership-walk helpers in `object.move`: [1](#0-0) 

`owns()` explicitly bounds the walk with `count < MAXIMUM_OBJECT_NESTING` and aborts with `EMAXIMUM_NESTING` if exceeded. [2](#0-1) 

`root_owner()` has **no such bound** — it loops `while (is_object(obj_owner))` indefinitely following the `owner` field of `ObjectCore`.

This function is the custody gate for lazily-initializing code deployed to an object: [3](#0-2) [4](#0-3) 

**Constructing the cycle:** `transfer_raw` only validates that the destination is *currently* reachable back to the caller at the time of the call (`verify_ungated_and_descendant`), and each transfer is a separate transaction that commits its own state mutation before the next runs: [5](#0-4) [6](#0-5) 

Given two objects `A` and `B` both owned by user `U`:
1. Tx1: `U` calls `transfer(A, to=B)`. `verify_ungated_and_descendant(U, B)` succeeds because `B.owner == U`. Commits `A.owner = B`.
2. Tx2: `U` calls `transfer(B, to=A)`. `verify_ungated_and_descendant(U, A)` walks `A.owner == B`, then `B.owner == U` (still `U`, since Tx2 hasn't mutated `B` yet) — succeeds. Commits `B.owner = A`.

Result: `A.owner = B` and `B.owner = A` — a fully legitimate 2-cycle, with no validation in either individual `transfer` call preventing it, because each call only checks reachability *before* its own mutation is applied.

Once this cycle exists, any call to `root_owner()` on `A` or `B` (directly, or transitively via `init::assert_may_self_initialize`/`code::publish_package`) will loop forever and abort on out-of-gas, since `is_object(obj_owner)` will always be true for the alternating `A`/`B` addresses.

### Impact Explanation
Any code object whose module uses `init::internal_maybe_initialize` for lazy self-init is permanently unable to initialize (or re-initialize after upgrade with `only_once=false`) once its ownership chain becomes cyclic, because `assert_may_self_initialize` → `root_owner()` will never return. If that initializer is responsible for creating the object's `FungibleStore`, minting refs, or other custody-critical state, this results in a **non-recoverable loss/lock of object-held value** — the object's address can never obtain a signer for the guarded module, freezing any assets or capabilities that depend on that initialization path. This satisfies the custody gate's "Permanent lock or non-recoverable loss of object-held ... value." Any other current or future framework/application code that calls `object::root_owner()` on an object under attacker (or even accidental self-)control inherits the same unbounded-loop DoS, which is a broader concern beyond the `init` module specifically.

### Likelihood Explanation
Constructing the cycle requires only two ordinary, individually-authorized `object::transfer` calls by the same signer across two objects they already own — no privileged access or bug in any other module is needed, and both objects can be regular objects created via `object::create_object`. The attack is self-inflicted in the straightforward form (an owner cycling their own objects), but it becomes a genuine custody exploit for lazy-init-gated code objects if the code-object owner (or anyone who can transfer the object, e.g., after an unrelated legitimate transfer sequence, indirect nested-owner transfer, or an application that programmatically re-parents objects) is induced to create such a cycle, either accidentally (e.g., composable DeFi protocols that re-parent objects to each other) or via a crafted sequence of otherwise-valid transfers. Because `root_owner()` is a `#[view]`/public function with no protective bound, the likelihood of hitting this in complex object-composition scenarios (vaults holding other vaults, wrapped NFTs, etc.) is non-trivial for a mainnet with `LAZY_MODULE_INITIALIZATION` enabled.

### Recommendation
Bound `root_owner()`'s traversal identically to `owns()`, asserting `EMAXIMUM_NESTING` (or a dedicated cycle-detection error) after `MAXIMUM_OBJECT_NESTING` hops, so cyclic or excessively deep ownership graphs fail fast and deterministically instead of looping until gas exhaustion. This should be applied consistently everywhere the framework walks object ownership chains (`root_owner`, and any other callers) to avoid the same class of bug recurring.

### Proof of Concept
```move
// Pseudocode illustrating the exploit, mirroring init.move's own test harness style
// (see aptos-move/framework/aptos-framework/sources/init.move test helpers for object setup).

let cref_a = object::create_object(@user);
let addr_a = object::address_from_constructor_ref(&cref_a);
let obj_a = object::object_from_constructor_ref<ObjectCore>(&cref_a);

let cref_b = object::create_object(@user);
let addr_b = object::address_from_constructor_ref(&cref_b);
let obj_b = object::object_from_constructor_ref<ObjectCore>(&cref_b);

// Tx1: A -> B  (A.owner = B)
object::transfer(&create_signer(@user), obj_a, addr_b);

// Tx2: B -> A  (B.owner = A); verify_ungated_and_descendant(user, A)
//      succeeds because at this point B.owner is still @user.
object::transfer(&create_signer(@user), obj_b, addr_a);

// Now A.owner == addr_b and B.owner == addr_a: a 2-cycle.
// Any subsequent call loops forever:
let _ = object::root_owner<ObjectCore>(obj_a); // never returns; aborts on out-of-gas
```

Note: I was not able to further verify (due to tool-call exhaustion) whether any other production module besides `init.move`/`code.move` currently calls `root_owner()` on objects with attacker-influenced ownership, which would broaden the practical blast radius — this would be worth confirming with a full-repo search and an actual Move unit test run (`root_owner` on a constructed 2-cycle) in a follow-up session.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Returns the root owner of an object. As objects support nested ownership, it can be useful
    /// to determine the identity of the starting point of ownership.
    public fun root_owner<T: key>(self: Object<T>): address {
        let obj_owner = self.owner();
        while (is_object(obj_owner)) {
            obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
        };
        obj_owner
    }
