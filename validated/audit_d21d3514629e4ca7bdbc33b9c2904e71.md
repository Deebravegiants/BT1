### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, but the HMAC signature it is verified against (via `Utils::HmacValidator.validate`) only covers the raw request body, not any headers.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [2](#0-1) , while `Request#shop` is derived from the `shop-domain` header, entirely outside the signed material [3](#0-2) . `Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which calls `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac` — and, once that check passes, immediately trusts `request.shop` to build the `WebhookMetadata` passed to the host application's handler [1](#0-0) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against that computed value [4](#0-3)  — the shop header plays no role in the signature at all. This breaks the identity binding `HMAC-verified bytes == bytes acted on`: the byte range verified (body) is not the same as the byte range used to select the tenant (the `shop-domain` header).

### Impact Explanation
Any party capable of relaying a single legitimate Shopify webhook delivery (whose HMAC is valid for the given raw body and the app's `client_secret`) can alter only the `X-Shopify-Shop-Domain` header while keeping the body and HMAC unchanged, and the gem will report it as originating from a different shop. Since `Registry.process` passes `request.shop` straight to the host application's `WebhookHandler#handle` as the trusted tenant identifier [5](#0-4) , this can trick a host application into applying the payload of one merchant's webhook (e.g. `orders/create`, `app/uninstalled`, `shop/redact`) to a different merchant's tenant record — a cross-tenant data confusion. This matches the "cross-tenant access" criterion under Critical impact, provided the host application relies on the gem's `shop` field as the tenant boundary (which is the gem's documented usage pattern, per `WebhookMetadata`).

### Likelihood Explanation
Exploitation requires the attacker to control or replay the header set alongside a body+HMAC pair that Shopify itself sent (e.g., an attacker's own shop's uninstall/redact webhook, or a MITM/proxy positioned to modify headers before they reach the app, or a load balancer/webhook-forwarding proxy that does not pin headers). This is a moderate-likelihood scenario for apps that terminate webhooks behind shared infrastructure or that re-deliver/forward webhook payloads internally, since the header is never part of the cryptographic guarantee even though it is the field the host application typically trusts.

### Recommendation
Include the shop domain (and other Shopify-controlled headers such as `topic`, `api-version`, `webhook-id`) in the signable/verified material, or otherwise cryptographically bind them to the body before `Registry.process` uses `request.shop` for tenant routing. At minimum, document prominently that the `shop` field on `Webhooks::Request` is *not* HMAC-covered so host applications do not implicitly trust it as an authenticated tenant identifier.

### Proof of Concept
1. Attacker's own store receives a legitimate webhook from Shopify: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and a valid `X-Shopify-Hmac-Sha256` computed over `B` with the app's shared secret.
2. Attacker (or a MITM/forwarding proxy under attacker's control) resends the same request to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`, leaving body `B` and the HMAC header untouched.
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` (`B`) and it matches, so `Registry.process` proceeds [6](#0-5) .
4. `request.shop` now returns `"victim-shop.myshopify.com"`, and `WebhookMetadata.new(... shop: request.shop ...)` is delivered to the host app's handler as though it were an authentic webhook for the victim shop, despite the payload actually describing the attacker's own shop's data.
