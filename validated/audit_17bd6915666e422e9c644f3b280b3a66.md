### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then forwards the caller-supplied `shop-domain` header — which is *not* part of the signed content — directly to the handler as the tenant identifier. This breaks the identity binding `signed_bytes == acted_upon_tenant`, exactly analogous to the Chakra `contract_chain_name != to_chain` binding gap: a value used to route/attribute the payload (`shop`) is disjoint from the value actually covered by the cryptographic check (`raw_body`).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` / `validate_signature` compute and compare the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` calls this validator, and on success reads `request.shop` (the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Request#shop` simply reads the header with no cross-check against the signed body: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any tenant that has legitimately installed the app can capture a valid `(raw_body, hmac)` pair from a webhook delivered to their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` (it only checks the body against the shared secret), so `Registry.process` proceeds and calls the handler with `shop: <attacker-chosen victim shop>` alongside attacker-controlled body content — i.e., the equality `hmac_covers(shop) == true` that the host app implicitly relies on for routing is false.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the `shop` value used to select/attribute per-tenant data (sessions, DB records, redaction/compliance actions such as `shop/redact` and `customers/data_request`) is never bound to the HMAC that is supposed to prove the message's origin/authenticity. An attacker who has (or creates) a valid installation of the same app on any shop can forge webhook deliveries "as" another tenant, leading to cross-tenant data corruption or unauthorized triggering of tenant-scoped logic — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant app built on this gem: it requires only that the attacker control one legitimate shop install (a very low bar — dev/trial stores are free) and be able to POST to the app's public webhook endpoint with a custom header, which is standard HTTP client capability, not any privileged credential.

### Recommendation
`ShopifyAPI::Webhooks::Request#to_signable_string` (or `Registry.process`) should bind the `shop-domain` (and ideally `topic`/`webhook-id`) into the value that gets authenticated, or `Registry.process` should require and cross-check the resolved `shop` against an expected/whitelisted shop (e.g., a shop with an existing stored session) before invoking the handler, rejecting mismatches the same way the Chakra fix recommends checking `contract_chain_name == to_chain` before processing.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both signed with the same app `client_secret`.
2. Shopify delivers a legitimate webhook to the attacker's own endpoint for `attacker-shop`: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker replays the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (via `Request#to_signable_string` returning only `B`) and it matches, so validation passes.
5. `Registry.process` looks up the handler and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, i.e., the host application processes attacker-controlled content as if authentically originating from `victim-shop`.           if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
