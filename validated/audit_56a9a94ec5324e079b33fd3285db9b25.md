Based on the investigation, I found a clear identity-binding gap in the webhook verification path.

### Title
Webhook shop/topic identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` binds nothing but the payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read straight from attacker-controllable HTTP headers and forwarded to the app's handler as trusted tenant/session identity, without ever being covered by the signature.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which only returns `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` verifies only the HMAC produced from that signable string (i.e., the body) and then immediately trusts `request.shop`/`request.topic` to dispatch to the app's handler: [3](#0-2) 

Because the app's `api_secret_key` is a single shared secret across every shop/install of the app, `HMAC(secret, body)` is identical regardless of which shop the body is claimed to originate from. This means the equality the code implicitly relies on — "the shop that produced a validly-HMAC'd request" == "the shop stored in `WebhookMetadata`/acted upon by the handler" — does not hold. An unprivileged user who controls one shop that has the app installed can capture a legitimate webhook delivery (body + valid HMAC) from their own store, then replay that exact body/HMAC pair to the same public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value naming a different, victim shop. The HMAC check in `HmacValidator.validate` at [4](#0-3)  still passes because it only recomputes over the body, not the headers. The handler then executes under the spoofed `shop` value: [5](#0-4) 

This directly matches the report's bug class — a field (here, `shop`/`topic`) that the app relies on for tenant identity is "acted on but not covered by the HMAC."

### Impact Explanation
Any app that keys per-shop side effects (data deletion, session invalidation, GDPR redaction flows like `customers/redact`/`shop/redact`, billing state changes, etc.) off `WebhookMetadata#shop` can be tricked into performing those actions against a shop the attacker does not own, using a webhook the attacker legitimately received for their own shop. This is cross-tenant access/action achieved purely by an unprivileged user replaying their own valid webhook with a forged header — no access token, `client_secret`, or privileged credential is required. This satisfies the Critical bar for "cross-tenant access."

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on at least one shop (a normal, unprivileged action for any Shopify merchant) and can reach the app's public webhook endpoint. Crafting the replay only requires copying an intercepted or self-generated webhook body/HMAC pair and changing plaintext headers — no cryptographic secret is needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them to the body before validation, so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` reflects everything the handler subsequently trusts. At minimum, document that consuming apps must independently verify `request.shop` against a known/installed shop list before acting on webhook contents, since the gem itself does not bind shop identity to the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers (or waits for) a webhook delivery, e.g. `app/uninstalled` with body `{}` (or any deterministic/known body).
2. Attacker captures the delivered `x-shopify-hmac-sha256` value, which equals `HMAC-SHA256(api_secret_key, "{}")` — identical for every shop using this app, since the secret is shared.
3. Attacker sends a forged HTTP request to the app's public webhook endpoint with the same raw body `{}` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and desired `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, "{}")` and matches — validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the victim shop never sent this webhook, causing the app to process/act as if it originated from the victim tenant.
