### Title
Unbounded ECDSA signature loop in BEEFY consensus verification enables free-of-charge CPU exhaustion via unsigned `handle_unsigned` extrinsics - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic executes ISMP messages, including BEEFY consensus proofs, "for free" as an unsigned transaction — the whole verification (including `secp256k1_recover`) runs inside `validate_unsigned` in the transaction pool, before any fee is charged. [1](#0-0)  The BEEFY verifier's `verify_mmr_update_proof` only enforces a *lower* bound on the number of signatures (supermajority participation against the trusted authority set), never an *upper* bound, and then unconditionally loops over every submitted signature performing an expensive `secp256k1_recover` for each one. [2](#0-1) 

### Finding Description
`verify_mmr_update_proof` computes `signatures_length = mmr.signed_commitment.signatures.len()` and only checks `check_participation_threshold(signatures_length, authority_set.len)`, i.e. that enough signatures are present — it never rejects a message for carrying *too many* signatures. [3](#0-2)  It then iterates over the full (attacker-controlled) `signatures` vector, calling `H::secp256k1_recover` (a computationally expensive elliptic-curve operation) for every entry, before any merkle-proof verification of authority membership takes place: [4](#0-3) 

This function is reached from an unauthenticated, permissionless path: `pallet_ismp::handle_unsigned` accepts `Vec<Message>` including `Message::Consensus`, is dispatched with `ensure_none(origin)`, and — critically — its `ValidateUnsigned::validate_unsigned` implementation runs `Self::execute(messages.clone())`, which performs full consensus verification (and therefore the entire expensive signature-recovery loop) *before* any transaction fee is applied and merely to decide pool admission. [5](#0-4) [6](#0-5)  This is explicitly documented as by-design "free" execution: "Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free..." [7](#0-6) 

No `BoundedVec` or explicit maximum length constrains `signatures` in the BEEFY primitives (`SignedCommitment`), and no size limit is applied to the number of votes before the recovery loop runs — unlike the analogous "cheap validity check before expensive work" pattern the codebase already applies elsewhere, e.g. `pallet-call-decompressor`'s explicit comment and fix: "a fee-less attacker could ... have a tiny zstd 'bomb' expanded to gigabytes during transaction-pool validation, before any size check. Enforcing it here protects both paths." [8](#0-7)  No equivalent guard exists for the BEEFY signature count.

This is directly analogous to CVE-2023-32699 (MeterSphere): an unauthenticated caller submits an arbitrarily large, attacker-controlled input (there: password length fed to MD5; here: number of ECDSA signatures fed to `secp256k1_recover`), and the target unconditionally performs the expensive cryptographic operation over the full input size before validating it is legitimate, at zero cost to the attacker.

### Impact Explanation
Any external, unauthenticated party can craft a `Message::Consensus` payload (BEEFY variant) with an enormous `signatures` vector (bounded only by extrinsic/block-length limits, e.g. tens of thousands of 65-byte dummy signatures) and gossip it as an unsigned extrinsic. Each collator/validator's transaction pool must run `validate_unsigned`, which executes the full BEEFY verification path and performs `secp256k1_recover` once per signature — an expensive operation — for free, with no per-call fee or stake at risk for the attacker. Submitted repeatedly and/or broadcast to many peers, this can consume disproportionate CPU across the network's transaction-pool validation layer, degrading throughput or delaying legitimate message delivery/relaying (a form of unauthorized resource exhaustion / DoS against message delivery), which maps to the "route unable to deliver messages" impact category.

### Likelihood Explanation
High likelihood of triggerability: `handle_unsigned` is explicitly permissionless (`ensure_none`) and unsigned by design, requiring no stake, gas, or prior relationship with the network — precisely the "no attacker cost" prerequisite that made the MeterSphere bug practical. The only friction is that the message must decode successfully and pass structural checks; padding the `signatures` vector with well-formed (but bogus/duplicate-index) 65-byte entries is trivial and cheap for the attacker while expensive for the verifier.

### Recommendation
Add an explicit upper bound on the number of signatures/votes accepted in a BEEFY `SignedCommitment` (and any other unsigned/free-execution consensus proof types) *before* performing any `secp256k1_recover` calls — e.g., cap `signatures.len()` to some reasonable multiple of the known/trusted `authority_set.len` (or a fixed protocol constant) and reject early with `Error::TooManySignatures` if exceeded. Apply the same "validate cheap bound before expensive work" pattern already used in `pallet-call-decompressor::decompress` for the BEEFY (and other free/unsigned) consensus verification paths.

### Proof of Concept
1. An attacker constructs a `Message::Consensus` (`ConsensusMessage`) wrapping a BEEFY `MmrProof` whose `signed_commitment.signatures` contains, e.g., 50,000 arbitrary/garbage 65-byte ECDSA signatures (duplicated authority indices are fine — the loop does not stop early).
2. The attacker submits this as an unsigned extrinsic to `Ismp::handle_unsigned` on a public RPC/P2P endpoint.
3. Every node's transaction pool calls `ValidateUnsigned::validate_unsigned`, which calls `Pallet::<T>::execute(messages.clone())` → consensus client `verify_consensus` → `beefy_verifier::verify_mmr_update_proof`, which loops `H::secp256k1_recover` 50,000 times before failing (e.g., on the subsequent merkle multi-proof check) — all for a transaction the attacker paid nothing for.
4. Repeating/parallelizing this submission from multiple unsigned senders imposes a compounding CPU cost on every validating node's mempool with no economic cost to the attacker.

Note: I was not able to fully confirm from the index whether any block-length/extrinsic-size limit (`RuntimeBlockLength`) in the parachain runtimes (`gargantua`, `nexus`) would practically cap the maximum number of signatures that fit in one extrinsic; that would only bound the size of *each* attack transaction, not prevent repeated free submissions, so the underlying missing-upper-bound issue in the verifier remains regardless.

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
