### Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook signature verification in `ShopifyAPI::Webhooks::Request` only binds the HMAC to the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` header values — which are trusted downstream as the tenant/event identity — are never included in the signed material, so they can be swapped by anyone able to replay a genuine, previously-observed webhook.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from unauthenticated HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then dispatches the handler using the header-derived `shop`/`topic` as trusted identity: [3](#0-2) 

The resulting `WebhookMetadata` struct — passed to the host application's handler as the authoritative tenant identity for the event — carries this unauthenticated `shop` field verbatim: [4](#0-3) 

This breaks the intended identity binding: **HMAC(secret, raw_body) == received_hmac** is verified, but the equality that the host application actually relies on — **shop_header == shop_that_produced_this_body** — is never checked. The `shop` (and `topic`/`webhook_id`) fields are "acted on but not covered by the HMAC," exactly the analog class called out in scope: a field trusted for tenant routing that isn't bound to the signed bytes.

### Impact Explanation
Any unprivileged internet user can install the target Shopify app on a shop they control (app installation is public/self-service for public apps). Shopify will then send that user genuine, correctly-HMAC-signed webhooks for events on their own shop. Because the signature covers only the body, the attacker can replay the exact same `(raw_body, hmac-sha256)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only recomputes the HMAC over `raw_body`. `Registry.process` then invokes the app's registered handler with `WebhookMetadata(shop: <victim-shop>, topic: ..., body: <attacker-controlled>)`.

If the host application uses `data.shop` (as documented/intended) to select which tenant's session, database record, or resource to update in response to the webhook, the attacker can inject forged event data attributed to a shop they do not own — a cross-tenant confusion/spoofing primitive reachable without any credential belonging to the victim, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any app relying on this gem's webhook helpers exactly as documented: no secret material or privileged access is required beyond the ability to self-install the app (standard for public apps), and the header manipulation is a trivial raw HTTP request forgery once a legitimate webhook has been observed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed string, or otherwise cryptographically bind them (e.g., include them in a canonicalized signable string similar to `Utils::VerifiableQuery#to_signable_string` used for OAuth callbacks) so `HmacValidator.validate` fails if any of these values are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and triggers any registered webhook topic (e.g., `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` sent by Shopify (computed as `HMAC-SHA256(client_secret, B)`).
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and matches `H` — validation passes: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and the host application processes attacker-controlled content as if it belonged to the victim shop.
