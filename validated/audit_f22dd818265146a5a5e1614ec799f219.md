### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` (used by `HmacValidator.validate`) only signs the raw request body. This breaks the identity binding `HMAC-verified bytes == data acted on`: the HMAC proves the body is authentic, but the `shop` value used to attribute/process the webhook is never covered by that same signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, and `shop`, `topic`, `api_version`, `webhook_id` are all read from separate headers — none of which are included in `to_signable_string`, which returns only `@raw_body`.

`Registry.process` verifies the HMAC against the body, then immediately trusts the header-derived `shop`/`topic`/`webhook_id`/`api_version` and passes them straight to the registered handler: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

Because the shop-identifying headers are outside the signed content, a valid `(raw_body, hmac)` pair captured from one legitimate webhook delivery (e.g., addressed to the attacker's own shop) remains valid when replayed with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header pointing at a different, victim shop. The equality that should hold — "the shop the HMAC authenticates" == "the shop the handler is told to act on" — does not hold here.

### Impact Explanation
An unprivileged internet user who controls or has previously observed one legitimate signed webhook payload (trivial for their own installed shop, since they can trigger events like `orders/create` themselves) can replay that exact `raw_body`/`hmac` pair against the app's public webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop domain. Because `Registry.process` only checks the HMAC over the body and unconditionally forwards the header-derived `shop` to `WebhookMetadata`, the host application's webhook handler will process/store the attacker-controlled body attributed to the victim's shop. This is a cross-tenant data-integrity violation: data intended for shop A can be injected/attributed into shop B's records inside the host app, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is High for any app that keys business logic (order/customer records, GDPR redaction handling, inventory updates, etc.) off `WebhookMetadata#shop` as returned by this gem, since:
- The attacker only needs one legitimate signed webhook (easily obtained by triggering an event on their own store).
- No secrets are required — only header manipulation on an HTTP request to the app's public webhook endpoint.
- The vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler) is the gem's documented, standard webhook-processing flow.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material verified against the HMAC, or independently verify that the `shop` header value matches an installation the app has already authenticated (e.g., cross-check against a stored session for that shop before trusting the header). At minimum, `to_signable_string` should not omit fields the application will subsequently trust as the tenant identity.

### Proof of Concept
1. Attacker's own store `attacker-shop.myshopify.com` has the app installed; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 123, ...}`
2. Attacker captures this exact `(body, hmac)` pair.
3. Attacker sends a POST to the app's webhook endpoint reusing the same body and HMAC, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only — which is unchanged — so validation succeeds.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
