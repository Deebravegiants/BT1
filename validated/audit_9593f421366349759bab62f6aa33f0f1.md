### Title
Missing meaningful slippage protection on router strategies — dust `min_out` permits sandwich extraction of collateral and debt proceeds - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller's strategy verbs (`swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, `multiply`) delegate all price protection to the `min_out` value encoded inside the caller-supplied `StrategySwap` route bytes. The controller itself imposes no minimum-output check of its own — only `RouterOverspend` (input not overspent) and `NoSwapOutput` (output > 0). The swap-aggregator only requires `total_min_out > 0`, so a route encoding `min_out = 1` is valid. A user transaction carrying such a route can be sandwiched by an attacker trading on Aquarius/Soroswap, extracting nearly all of the swap's value while the transaction still succeeds — the same bug class as the referenced DODO report (`minReceiveAmount` allowed to be 0).

### Finding Description
The swap leg runs through `swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55`. After executing the route it asserts only that the input-token balance did not increase (`RouterOverspend`), that at most `amount_in` was spent, and that some positive output arrived (`NoSwapOutput`, lines 75-83). There is no controller-side floor on output value.

The only output floor is `total_min_out` inside the router program, checked in `contracts/swap-aggregator/src/execute/mod.rs:67-70` and `:125-128`. That check accepts any strictly positive value, so `min_out = 1` base unit is a valid floor. The routing payload is opaque `Bytes` supplied by the caller (`swap` parameter of `process_swap_collateral` in `contracts/controller/src/strategies/swap_collateral.rs:55-65`, `repay_via_collateral_swap` in `contracts/controller/src/strategies/repay_debt_with_collateral.rs:108-118`, and analogously `swap_debt`/`multiply` via `withdraw_and_swap_from_supply` in `contracts/controller/src/strategies/legs.rs:233-258`), and the controller forwards it to the router without decoding or enforcing a price-based minimum.

The post-swap gate `strategy_finalize` only validates solvency (LTV/health factor against oracle prices). A sandwiched swap that sells collateral at a steep discount but leaves the account above its liquidation threshold passes all checks, so the value loss is silently accepted — e.g. `swap_collateral` converts $50,000 of collateral into $5,000 of the new asset on an account with modest debt, and `repay_debt_with_collateral` burns collateral while leaving most debt outstanding yet still healthy.

### Impact Explanation
A victim account owner (or delegate) submits e.g. `swap_collateral(caller, account_id, current=XLM, amount=A, new=USDC, swap=route_with_min_out_1)`. An attacker observes the transaction, front-runs with their own Aquarius/Soroswap swap pushing the XLM/USDC pool price against the victim, lets the victim's route execute at the manipulated price (output ≥ 1 satisfies the router), then back-runs to restore the pool and pocket the spread. The victim's collateral is converted at a near-worst-case price and the loss is permanent — direct theft of user funds by an unprivileged attacker who only trades on the allowed venues. The same applies to `repay_debt_with_collateral` (collateral consumed, debt barely repaid) and to `multiply`/`swap_debt` outputs.

### Likelihood Explanation
The route bytes and embedded `min_out` are fully caller-controlled, and clients that build routes without slippage (or a dust floor) produce exploitable transactions — exactly the scenario the source report flags. The attack requires only unprivileged Aquarius/Soroswap trades plus normal transaction ordering, both explicitly in scope. No privileged access, leaked key, or oracle manipulation is needed; the pool used by the route is itself the manipulation surface, not an honesty assumption.

### Recommendation
Add a controller-side output floor independent of user-supplied route bytes: after `swap_tokens` returns the measured output, compare its oracle-priced value (using the already-prefetched strict prices in `Context`) against the measured input value and revert if output value falls below `input_value * (1 - max_strategy_slippage_bps)`. Alternatively require a minimum `min_out` enforced as a fraction of the oracle-implied expected output, or document and enforce at the router level that `total_min_out` must be within a sanity band of the route's declared expected output rather than merely `> 0`.

### Proof of Concept
1. Alice owns a healthy account with XLM collateral and calls `swap_collateral` with `from_amount` covering $50,000 of XLM and a `swap` payload whose router program sets `total_min_out = 1`.
2. Bob swaps USDC→XLM on the Aquarius pool the route uses, driving the XLM price up sharply.
3. Alice's transaction executes: the controller measures the withdrawal, hands the XLM to the router, the hop executes at the manipulated rate returning e.g. $5,000 of USDC; `total_out ≥ 1` passes (`execute/mod.rs:126`), `received > 0` passes (`swap.rs:82`), the deposit proceeds, and `strategy_finalize` confirms the account is still above its threshold.
4. Bob swaps back on the same pool, recovering his capital plus the ~$45,000 extracted from Alice's swap. Alice's loss is final; nothing reverted.

Uncertainties: `strategy_finalize`'s exact accounting was not fully read, but the referenced integration test `strategy_solvency_gate_on_low_value_router_output.rs` confirms the gate is purely solvency-based — a swap output of `$26,000` on a `$50,000` input reverted only because it breached the LTV limit, not because the price was bad; accounts that remain solvent keep the loss.
