## Analysis

The report describes a broken invariant: an array (`registeredUnderlyings`) is *acted upon* by a critical function (`refreshStrategies`) without a way to keep it consistent with the ground truth (`Alchemist.supportedUnderlyingTokens`), letting stale/mismatched state permanently block the contract. The instruction set asks me to look for the analogous *identity-binding* pattern in this Ruby gem: a field that is *acted upon* by trust-critical logic but is **not covered by the cryptographic verification** that's supposed to establish authenticity.

That pattern shows up cleanly in the webhook processing pipeline.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns **only the raw HTTP body** — nothing else: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight out of unauthenticated HTTP headers and are **not included** in the signable string: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC over `to_signable_string`, i.e., the body bytes, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately hands `request.shop` — the unverified header value — to the app's webhook handler as the tenant identity, alongside the (HMAC-verified) body: [4](#0-3) 

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted as tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are excluded from the HMAC signable string, while `HmacValidator`/`Registry.process` only authenticate the raw body bytes. Any actor who can obtain one genuine `(body, hmac)` pair for the app (e.g. by installing the app on their own store and observing the webhook their store legitimately receives) can replay that exact body/HMAC pair to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and the library will pass the forged shop identity straight to the app's handler as authenticated.

### Finding Description
The equality that should hold is:
`shop asserted to the handler == shop that Shopify actually generated this signed payload for`

Because `to_signable_string` only returns `@raw_body` [1](#0-0) , the HMAC check performed in `HmacValidator.validate` [5](#0-4)  proves only that the *body* was produced by someone who knows `api_secret_key` — it says nothing about which shop, topic, or webhook ID it belongs to. Yet `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read directly and independently from headers [2](#0-1) , and `Registry.process` forwards `request.shop` unchanged to `WebhookMetadata`, which the host application uses to attribute the payload to a tenant [6](#0-5) .

Attack sequence:
1. Attacker installs the target app on their own store ("shop-A") — an ordinary, unprivileged action.
2. Shopify sends a legitimate webhook to the app for shop-A: `body_A` with `hmac_A = HMAC(secret, body_A)`, headers `shop-domain: shop-A`.
3. Attacker captures `(body_A, hmac_A)` (both are visible to them, since it's their own store's webhook and their own network request).
4. Attacker crafts a new POST to the app's public webhook endpoint with the *same* `body_A`/`hmac_A`, but `x-shopify-shop-domain: shop-B` (any victim shop) and/or a different `x-shopify-topic`.
5. `HmacValidator.validate` succeeds (body/HMAC pair is genuine), so `Registry.process` invokes the handler with `shop: "shop-B"` and `body: body_A`'s content.

Before the attack: `request.shop` for `body_A` should only ever be `"shop-A"`. After the attack: the app's handler receives `body_A` attributed to `"shop-B"` — the binding between authenticated bytes and asserted tenant is broken.

### Impact Explanation
This lets an unprivileged attacker (anyone able to install the app on their own store) inject a webhook event with attacker-chosen (but HMAC-genuine) body content into an arbitrary victim shop's tenant context, since `shop` is fully attacker-controlled and unauthenticated relative to the signed bytes. Depending on how the host app's `WebhookHandler` uses `shop` (most apps key their datastore/session lookup on it directly, per the library's own docs), this enables cross-tenant data injection/corruption — e.g., faking an `orders/create`, `app/uninstalled`, or `customers/redact` event for a shop the attacker doesn't operate. This falls under the High-impact "cross-tenant access" category since it crosses a tenant boundary using only the app's own (non-secret) infrastructure, no `access_token`/`client_secret` leakage or MITM required.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to have installed the app at least once on a store they control (a normal, permissionless action for any Shopify-app installable by any merchant), and the app's webhook endpoint be reachable on the internet (true by design, since Shopify calls it). No secret material, TLS interception, or privileged access is needed — only a replay of previously-observed, genuinely-signed bytes with modified metadata headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the HMAC-covered signable string (or otherwise cryptographically bind them to the payload, e.g., by re-deriving/validating `shop` against the session/access-token store rather than trusting the header), so that the verified bytes and the bytes the application acts on for tenant identification are the same set. At minimum, document prominently that `request.shop` is unauthenticated and that host applications must not use it as a sole tenant-attribution key without additional verification (e.g., matching it against a shop for which the app has a valid, stored `access_token`).

### Proof of Concept
```ruby
# 1. Attacker installs app on their own shop "attacker.myshopify.com"
# and observes a legitimate webhook delivery for it:
body = '{"id":123,"note":"legit order"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
)
# (In reality the attacker doesn't know api_secret_key, but Shopify computed hmac for them
#  and delivered it in the X-Shopify-Hmac-Sha256 header of their own genuine webhook.)

# 2. Attacker replays the identical body+hmac, spoofing the shop-domain header
# to point at a victim shop they do NOT operate:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary!
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# 3. HMAC validation passes because it only checks the body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process hands `shop: "victim-shop.myshopify.com"` to the handler,
#    even though this body was never issued for that shop.
ShopifyAPI::Webhooks::Registry.process(request)
```

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
