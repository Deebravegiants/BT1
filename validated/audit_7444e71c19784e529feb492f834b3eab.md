### Title
Fee-on-transfer tokens cause under-collateralized escrow in Tron `IntentGatewayV2.placeOrder` - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` credits escrow with the user-requested (fee-reduced by protocol fee only) amount instead of the amount actually received by the contract, unlike the primary EVM `IntentGatewayV2.sol`, which was explicitly patched to snapshot balances before/after `safeTransferFrom` and mutate `order.inputs` to the actual received amount.

### Finding Description
In `placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`), the commitment hash and escrow bookkeeping are both computed from `order.inputs[i].amount` reduced only by the protocol fee (`reducedInputs`), never validated against the token's actual balance change:

- Non-predispatch path: `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);` is immediately followed by `_orders[commitment][token] += reducedInputs[i].amount;` with no balance check. [1](#0-0) 

- Predispatch path: dust is computed only as `balance - requiredAmount` (i.e., surplus over the order's stated `requiredAmount`), but the escrow credit is still `reducedInputs[i].amount`, the value computed from the order before any fee-on-transfer deduction was observed. If the token charges a transfer fee during either the `safeTransferFrom` to the dispatcher or the sweep back to the gateway, the gateway's actual holdings for that token fall short of `reducedInputs[i].amount`, yet the same (unreduced) amount is credited to escrow. [2](#0-1) 

By contrast, the primary EVM contract computes `received = IERC20(token).balanceOf(address(this)) - balBefore` and mutates `order.inputs[i].amount` to this actual value before it's used for the commitment hash and escrow, both in the direct-transfer and predispatch/sweep paths — this is the fix directly addressing the fee-on-transfer bug class: [3](#0-2) [4](#0-3) 

The corresponding test suite (`IntentGatewayV2SameChainTest.sol`) confirms this is the exact bug class the team already recognized and fixed for the non-Tron contract, including a dedicated `FeeOnTransferToken` test fixture. [5](#0-4) 

### Impact Explanation
Because the Tron contract's `_orders[commitment][token]` escrow ledger records more than the contract actually holds for a fee-on-transfer input token, any subsequent `fillOrder`/`withdraw`/refund flow that pays out based on this inflated escrow value will attempt to transfer tokens the contract does not have. Depending on execution order, this either (a) causes legitimate order fills/refunds to revert (permanent freezing of the user's committed order and any solver's pre-committed output), or (b) drains real balances belonging to other users' unrelated escrowed orders of the same token, since `_orders` is a shared per-token ledger backed by one aggregate ERC20 balance — a concrete theft/insolvency vector for a widely used fee-on-transfer token such as USDT (once fees are toggled on).

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with an arbitrary fee-on-transfer ERC20 as an input token; no special privileges, races, or admin actions are required. The only precondition is deployment/use of the Tron gateway with a token that has (or later enables) a transfer fee — realistic given popular tokens like USDT support toggling fees.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol`: snapshot `balanceOf(address(this))` (or the dispatcher, for predispatch) before and after each `safeTransferFrom`/sweep, and use the actual delta as `order.inputs[i].amount` before computing `reducedInputs`, the commitment hash, and the escrow credit in the Tron `IntentGatewayV2.sol` contract.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a 1%-fee ERC20 (e.g., a `FeeOnTransferToken` like the one used in `IntentGatewayV2SameChainTest.sol`) as an input token, `protocolFeeBps = 0` for simplicity.
2. User calls `placeOrder` with `inputs[0].amount = 1000e18`. The contract executes `safeTransferFrom(user, address(this), 1000e18)`, but due to the 1% fee, the contract only receives `990e18`.
3. `_orders[commitment][token]` is credited with `reducedInputs[0].amount = 1000e18` (no protocol fee, so unreduced), while the actual token balance backing this order is only `990e18`.
4. When the order is later filled/withdrawn via `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:691-700`), the contract will attempt to release `1000e18` of the token per the escrow record, either reverting (freezing funds) or pulling `10e18` from balances backing other users' unrelated escrowed orders of the same token.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
