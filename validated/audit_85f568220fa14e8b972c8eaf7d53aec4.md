## Analog Found: Off-by-one weakens the BSC supermajority threshold, accepting non-final headers

The Sherlock report's bug class — an off-by-one in a quorum/threshold comparison that mis-computes the required supermajority — has a direct analog in Hyperbridge's BSC consensus verifier.

### Title
BSC light client accepts vote proofs with fewer signers than the required 2/3+1 supermajority - ([File: modules/consensus/bsc/verifier/src/lib.rs])

### Summary
`verify_bsc_header` checks participant count against `(2 * current_validators.len()) / 3` with a strict `<`, omitting the `+1` that every other consensus verifier in this codebase applies (BEEFY, sync-committee, Pharos). This lets a vote set with exactly `floor(2N/3)` signers — which does not meet the actual supermajority requirement of "more than 2/3" — pass validation.

### Finding Description
`verify_bsc_header` computes `participant_count` from the vote bitset and rejects only if it is *strictly less than* `(2 * current_validators.len()) / 3`: [1](#0-0) 

Every other supermajority check in the codebase requires strictly more than 2/3, i.e. `count >= (2*N)/3 + 1`:
- BEEFY: `len >= ((2 * total) / 3) + 1` [2](#0-1) 
- Sync-committee: rejects if `sync_aggregate_participants < ((2 * committee_size as u64) / 3) + 1` [3](#0-2) 
- Pharos: `required = (total_stake * 2 / 3) + 1; participating_stake >= required` [4](#0-3) 

The BSC verifier's check is missing that `+1`, and additionally uses `<` (reject) rather than the equivalent `<=` on the un-incremented bound, so it accepts vote sets that only reach exactly `floor(2N/3)` participants — one signer short of the genuine "more than two-thirds" supermajority that BEP-126/Parlia fast finality (and every other client in this repo) is built to require. For a 21-validator BSC set, `floor(2*21/3) = 14`; the correct threshold requires 15 signers, but this code accepts 14.

### Impact Explanation
This check gates acceptance of `IntermediateState`/state commitments derived from BSC consensus proofs relayed into `pallet-ismp`'s BSC light client (`ismp-bsc`). Any relayer can submit a `BscClientUpdate`; if it clears this weakened threshold with only `floor(2N/3)` colluding/compromised validator signatures — one fewer than the real supermajority — the module will treat the header as validly finalized under BEP-126 fast finality rules and commit its state root. This can enable forged state commitments / unsound message delivery for the BSC state machine into Hyperbridge without the genuine consensus-level supermajority actually having signed off, undermining the safety guarantee described in Hyperbridge's own consensus-proof model (`S ⊆ T, |S| ≥ 2/3|T| + 1`).

### Likelihood Explanation
Reaching this path requires only submitting a relayed consensus update through the standard BSC light-client update flow — no privileged role needed. The gap is exactly one validator's signature below the intended bar, which is a materially easier bar to clear than a genuine +1 supermajority, especially as the active validator set shrinks or under partial validator compromise/collusion scenarios.

### Recommendation
Align the BSC threshold check with the rest of the codebase's supermajority formula:
```rust
if participant_count < ((2 * current_validators.len()) / 3) + 1 {
    Err(Error::NotEnoughParticipants)?
}
```

### Proof of Concept
For `current_validators.len() == 21`:
- Correct required: `(2*21)/3 + 1 = 15`
- Current code rejects only when `participant_count < 14`, i.e., it accepts `participant_count == 14`
- A vote bitset with exactly 14 of 21 validators signing (one below the true supermajority of 15) passes `verify_bsc_header`'s participation check and proceeds to BLS aggregate verification and state-commitment extraction, despite not meeting the genuine 2/3+1 threshold. [5](#0-4)

/// Verify that participating validators have more than 2/3 of total stake.
fn verify_stake_threshold(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let participating_stake = validator_set.participating_stake(participants);
	let total_stake = validator_set.total_stake;
	let required = (total_stake * 2 / 3) + 1;

	if participating_stake >= required {
		Ok(())
	} else {
		Err(Error::InsufficientStake {
			participating: participating_stake,
			required,
			total: total_stake,
		})
	}
}
