### Title
Unbounded `order.inputs` / `order.output.assets` arrays in `placeOrder` can permanently freeze escrowed funds - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` accepts an `Order` with arbitrary-length `inputs` and `output.assets` arrays and escrows the caller's tokens against the resulting commitment hash without imposing any cap on these array lengths. Every subsequent code path that can release or refund that escrow — `fillOrder`/`_fillSameChain`/`_fillCrossChain` and `cancelOrder`/`_cancelSameChain`/`_cancelFromSource`/`_withdraw` — iterates over the full, unbounded `inputs`/`output.assets` array in a single transaction. A large enough array makes every one of those calls exceed the block gas limit, so the order can neither be filled nor cancelled, permanently freezing the escrowed tokens. This mirrors the GovernorAlpha bug class: an on-chain-committed object with an unbounded array that must be processed atomically by loops with no cap, becoming unprocessable once large enough.

### Finding Description
`placeOrder` only checks `order.inputs.length == 0` [1](#0-0) , but never bounds the upper size of `order.inputs` or `order.output.assets`. It escrows tokens for every element of `order.inputs` in a loop [2](#0-1)  and commits the order via `keccak256(abi.encode(order))` [3](#0-2) , so the array sizes are baked permanently into the on-chain commitment used everywhere else.

Every downstream path that can move the escrowed funds re-iterates over these same unbounded arrays in one transaction:
- `fillOrder` reads `order.output.assets.length` and requires `order.inputs.length == outputsLen` before routing to fill logic [4](#0-3) .
- `_fillSameChain` loops over `outputsLen` doing token transfers per iteration [5](#0-4) .
- `_fillCrossChain` similarly loops over `outputsLen` [6](#0-5) .
- `cancelOrder`'s same-chain path, `_cancelSameChain`, loops over `order.inputs.length` to compute remaining escrow before refunding [7](#0-6) , and the shared `_withdraw` helper it calls loops over `body.tokens.length` again to actually transfer each token out [8](#0-7) .
- The cross-chain source-cancel path `_cancelFromSource` also loops over `order.inputs.length` for an existence check before dispatching [9](#0-8) .

Because none of `fillOrder`, `cancelOrder`, or their internal helpers can process a subset of the order's `inputs`/`output.assets` — the order commitment is a hash over the *entire* array, and escrow accounting requires processing every entry — a placer (or an attacker griefing a placer, since `placeOrder` takes an arbitrary `Order` struct) can construct an order whose array lengths are large enough that every one of these functions exceeds the destination chain's block gas limit.

### Impact Explanation
Once such an order is placed and its tokens escrowed, there is no way to reduce the array size retroactively: the commitment hash is fixed, and `fillOrder`/`cancelOrder` both require the exact same `Order` struct that was placed. If both the fill and cancel paths run out of gas, the escrowed input tokens are permanently locked in the `IntentGatewayV2` contract with no recovery path — this is a direct, permanent freezing of user funds, matching the "permanent freezing of funds" impact bar.

### Likelihood Explanation
`placeOrder` is a permissionless, unprivileged entry point reachable by any user in a single transaction; no admin or governance step is required, and no existing check bounds the input/output array lengths. The transaction cost of placing a very large order is borne once by the placer (or paid by an attacker specifically to grief a victim's order, since the `Order` struct's `inputs`/`output` fields are fully attacker-controlled at placement time other than `user`/`source`/`nonce`), while gas-limit exhaustion in `fillOrder`/`cancelOrder` recurs on every future attempt to resolve the order, deterministically once the arrays are large enough relative to the destination chain's block gas limit.

### Recommendation
Enforce a hard cap on `order.inputs.length` and `order.output.assets.length` in `placeOrder` (e.g., reject orders exceeding a small fixed maximum), sized so that the worst-case gas cost of the corresponding `fillOrder` and `cancelOrder` (same-chain and both cross-chain routes, including `_withdraw`) paths stays comfortably below the target chains' block gas limits.

### Proof of Concept
1. Attacker/placer calls `placeOrder` with `order.inputs` containing N distinct ERC-20 tokens (e.g., N = 2,000) and a matching `order.output.assets` array, each with a valid nonzero amount, and provides/approves enough tokens to satisfy every input transfer in `placeOrder`'s escrow loop [10](#0-9) .
2. `placeOrder` succeeds (the loops it runs are within gas limits because it just moves tokens once) and escrows all N inputs under the order's commitment.
3. Any solver attempting `fillOrder(order, options)` must pass an `options.outputs` array of the same length N and the fill logic (`_fillSameChain`/`_fillCrossChain`) iterates all N entries doing a transfer per entry — for sufficiently large N, this reverts out-of-gas on every call.
4. The order's owner attempting `cancelOrder(order, options)` on the same-chain path hits `_cancelSameChain`, which loops over all N inputs, then `_withdraw`, which loops over them again — for sufficiently large N, this also reverts out-of-gas.
5. With both `fillOrder` and `cancelOrder` unable to complete, the escrowed tokens recorded in `_orders[commitment][token]` for all N tokens are permanently stuck in the contract.
