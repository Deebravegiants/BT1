Found a directly analogous, root-cause-supported vulnerability in `EvmHost.dispatch()`.

### Title
Flash-loan manipulation of the Uniswap V2 pool priced by `EvmHost.dispatch()`'s native-fee swap lets an attacker pay near-zero relayer fees, causing dispatched messages to be undeliverable - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)`/`fundRequest()` convert user-supplied native token (`msg.value`) into the protocol `feeToken` via a **spot** call to the configured Uniswap V2 router's `swapETHForExactTokens`, exactly the "use pool reserves/AMM spot price as an oracle" pattern flagged in the external report (there `getReserves()`/DODO pool price was flash-loan manipulated; here it's a live V2 swap executed against the pool's current reserves).

### Finding Description
`dispatch(DispatchPost)` in `evm/src/core/EvmHost.sol` does: [1](#0-0) 
It reads `path[0] = WETH`, `path[1] = feeToken()` and calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` — pricing `post.fee` tokens of `feeToken` entirely off whatever the router's pool reserves currently say, with no minimum-native-in check, no TWAP, and no deviation guard against a trusted reference price. The identical pattern is repeated in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

This is the same root cause as the report: a price is derived from a manipulable AMM pool state at the time of the call, with no sanity check against an independent oracle (e.g. Chainlink) or a stale/TWAP price. An attacker can flash-loan the `WETH/feeToken` V2 pool to push its price so that `swapETHForExactTokens` requires far less native ETH than the fair-value cost of `post.fee` fee-tokens, then dispatch a message (or fund a request) while the pool is skewed, before restoring the pool and repaying the flash loan in the same transaction.

The documentation itself only warns that the *view-style* `HyperApp.quote()` (which calls `getAmountsIn`) is "vulnerable to sandwich attacks" and should be used off-chain only [4](#0-3)  — it does not address that the *on-chain payment path itself*, `EvmHost.dispatch()`, is priced the same way and is directly reachable by any unprivileged caller with `msg.value`.

### Impact Explanation
`post.fee`/`get.fee`/`amount` (the relayer-fee component escrowed in `_requestCommitments[commitment].fee`) is the exact incentive relayers use to decide whether delivering a message is profitable. If an attacker can buy `post.fee` worth of `feeToken` for a fraction of its real native-token cost by manipulating the pool momentarily, the protocol's `feeToken` treasury absorbs the shortfall (an unbacked/underpriced credit — Hyperbridge effectively donates fee tokens at manipulated rates), while the attacker dispatches messages whose committed relayer fee looks adequate on-chain but was paid for with worthless native ETH relative to fair value. Because relayer fee accounting and route deliverability both depend on this `feeToken` amount being honestly priced, this can both drain the fee-token balance the Host holds and — for legitimate future dispatches priced by the same skewed pool at the moment of manipulation — leave insufficient real value behind to reward relayers, undermining message-delivery profitability guarantees. This matches the required impact categories: concrete value drain/theft of the protocol's fee-token holdings and undermining of relayer fee accounting on the dispatch path.

### Likelihood Explanation
Likelihood is high wherever the Host's configured `uniswapV2Router()` points at a thinly-liquid or externally flash-loanable Uniswap V2-compatible pool (which the codebase's own tests and mainnet fork setups show is a real configuration, e.g. `HostParams.uniswapV2`) [5](#0-4) . `dispatch()` is callable by any address with no allowlist or minimum-value guard, and the swap executes atomically within the attacker's own transaction, so a standard flash-loan-and-repay pattern (as demonstrated in the external report's PoC) applies directly.

### Recommendation
Do not price the native→feeToken conversion purely off the live Uniswap V2 pool at call time. Add a sanity/deviation check comparing the implied swap price against a trusted reference (e.g. a Chainlink feed for the native asset and feeToken, or a TWAP oracle) before executing `swapETHForExactTokens`, and revert if the deviation exceeds a configured bound — mirroring the mitigation recommended in the external report (comparing pool-derived price against Chainlink before trusting it). Alternatively, require callers to pre-quote off-chain and enforce a caller-supplied `minFeeTokenOut`/slippage bound checked against an oracle-derived fair price, not just against the pool's own instantaneous state.

### Proof of Concept
1. Attacker identifies `EvmHost.hostParams().uniswapV2` pointing to a WETH/feeToken Uniswap V2 pool with limited liquidity.
2. Attacker flash-loans a large amount of `feeToken` (or WETH) and swaps it into the pool to skew the WETH/feeToken price so that 1 WETH now quotes for far more `feeToken` than fair value.
3. In the same transaction, attacker calls `EvmHost.dispatch(DispatchPost)` (or `fundRequest`) with `msg.value` set just above the manipulated `swapETHForExactTokens` requirement for the desired `post.fee`, per: [1](#0-0) 
4. `_requestCommitments[commitment].fee` is now credited with `post.fee` in `feeToken`, funded by underpriced native ETH.
5. Attacker reverses the pool skew and repays the flash loan within the same transaction, keeping the profit (the difference between fair-value feeToken cost and what was actually paid in ETH).
