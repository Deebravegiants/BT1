## Analysis

The reported bug class — failing to properly validate ERC20 `transfer()` semantics for non-standard tokens — has a concrete analog in the Tron variant of `IntentGatewayV2`.

The mainline `evm/src/apps/IntentGatewayV2.sol` correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` throughout (e.g. escrow input transfers at [1](#0-0) ). However, `evm/tron/contracts/apps/IntentGatewayV2.sol` deliberately replaces high-level `IERC20.transfer()` calls in the fund-release paths (`withdraw()` and the `SweepDust` handler) with raw low-level `.call()` invocations that check **only** whether the call reverted, and never inspect the returned boolean: [2](#0-1) [3](#0-2) [4](#0-3) 

This pattern is presumably intended to accommodate Tron's TRC20/USDT, which (like Ethereum's USDT) does not return a bool from `transfer()` — a `safeTransfer`/strict ABI-decode call would revert on such tokens, which is exactly the failure mode described in the source report. But by switching to a bare `.call()` and only checking `success` (i.e., "did not revert"), the contract loses the ability to detect ERC20 implementations that return `false` on failure instead of reverting (a different but equally common non-standard-ERC20 behavior — e.g., paused tokens, blacklisted recipients, or tokens with silent failure semantics). In that case `success` is `true` (the call didn't revert) even though the tokens were never actually moved, yet `_orders[body.commitment][token]` is decremented and the order is marked filled/refunded in the same function.

## Root cause

`withdraw()` (and the `SweepDust` branch of `onAccept()`) treat "call did not revert" as equivalent to "transfer succeeded," instead of checking the returned boolean when return data is present (the actual `safeTransfer` semantics). This is inconsistent with the escrow accounting, which is unconditionally updated regardless of whether tokens were actually delivered.

### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()`/`SweepDust` permanently locks escrowed funds for non-reverting-failure tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.withdraw()` function and the `SweepDust` handler in `onAccept()` release escrowed ERC20 tokens using a raw low-level `.call()` and only check that the call did not revert, without validating the returned success boolean, unlike the `SafeERC20` library used elsewhere in the same file and in the mainline EVM contract.

### Finding Description
In `withdraw()`, escrowed input tokens and transaction fees are released to the beneficiary via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [5](#0-4) 

`success` here is `true` whenever the target contract's code executes without reverting — it says nothing about the ABI-encoded return value. Any ERC20 implementation that signals failure by returning `false` (rather than reverting) — e.g. a paused token, a token with recipient blacklisting, or any non-strictly-compliant token — will cause `success == true` even though no tokens were transferred. Despite this, the function unconditionally decrements `_orders[body.commitment][token]` and sets `_filled[body.commitment] = beneficiary`, permanently finalizing the order as settled. The same unchecked pattern recurs for `TRANSACTION_FEES` payout and in the `SweepDust` branch of `onAccept()` [6](#0-5) .

This contrasts with the file's own explicit `SafeERC20` usage elsewhere (input escrow via `safeTransferFrom` at lines 405/459) and with the mainline `evm/src/apps/IntentGatewayV2.sol`, which uses `safeTransfer`-style calls throughout for outbound transfers.

### Impact Explanation
Because `_orders[commitment][token]` is zeroed/decremented and `_filled[commitment]` is set regardless of actual token delivery, a failed-but-non-reverting transfer results in permanent loss of the escrowed funds: the beneficiary never receives the tokens, and the accounting no longer reflects any claim on them, so there is no path to recover or re-claim the escrow. This is triggered on the settlement path reached by any relayed `RedeemEscrow`/`RefundEscrow` cross-chain message (i.e., after any user places and a solver fills/cancels an order) — an unprivileged, normal protocol flow, not requiring any special privilege.

### Likelihood Explanation
This requires the underlying ERC20 (or fee token) used in an order to return `false` on failure instead of reverting under some condition (e.g. paused, blacklisted beneficiary, insufficient allowance-adjacent edge cases in non-standard tokens). Such tokens are a well-known category and the protocol advertises support for "any" input/output token. On Tron especially, non-standard token behavior is common (hence the deliberate move away from `safeTransfer`), making the exposure realistic rather than purely theoretical.

### Recommendation
Decode and check the returned boolean when return data is present (mirroring `SafeERC20.safeTransfer`'s logic), e.g.:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success || (data.length > 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```
This preserves compatibility with tokens that omit a return value (Tron USDT) while still catching tokens that explicitly signal failure via a `false` return, and should be applied consistently to `withdraw()`'s token/fee transfers and the `SweepDust` handler.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer()` returns `false` (no revert) when the recipient is blacklisted or the contract is paused — a legitimate non-standard-token pattern.
2. Place and fill an order using this token as an input, causing it to be escrowed in `IntentGatewayV2` (Tron).
3. Trigger the condition causing `transfer()` to return `false` for the beneficiary (e.g. pause the mock token or blacklist the beneficiary) before the `RedeemEscrow`/`RefundEscrow` settlement message is delivered.
4. Deliver the settlement message; `withdraw()` executes `token.call(...)`, which succeeds (no revert) but the mock token's internal balances are unchanged.
5. Observe: `_orders[commitment][token]` is deleted/decremented and `_filled[commitment]` is set, but `token.balanceOf(beneficiary)` did not increase — the escrowed tokens remain trapped in the contract with no accounting path to recover them.
