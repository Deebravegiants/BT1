This confirms the vulnerability. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) validates the HMAC over the request only via `Utils::HmacValidator.validate(request)`, and `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop` value passed downstream to the handler comes from the `shopify-shop-domain` HTTP header (`lib/shopify_api/webhooks/request.rb:20-23`), which is **not included in the HMAC-signed content**.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read from the `X-Shopify-Shop-Domain` HTTP header. `Registry.process` verifies the HMAC of the body only, then passes the unauthenticated header value as the tenant identifier (`shop:`) to the app's `WebhookHandler`. Because the `client_secret` used to compute this HMAC is shared across every shop that installs the app, an unprivileged internet user who installs the app on their own store receives genuine, correctly-signed webhooks and can replay the exact `body`+`hmac` pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the app to process a legitimate signed payload under a victim shop's identity.

### Finding Description
`Registry.process` at `lib/shopify_api/webhooks/registry.rb:188-200`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```
`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) computes the HMAC over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop` accessor pulls straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) with **no cryptographic binding to the signed body**.

The equality that should hold is: `shop authenticated by HMAC == shop used to identify the tenant in WebhookMetadata`. In this code, the left side does not exist at all — only the body is authenticated — so the equality can be broken by any party who can produce one validly-signed request (i.e., any merchant with the app installed, since the app's `client_secret` is the same for all its installations).

### Impact Explanation
This is a cross-tenant identity-binding break: the library authenticates the payload bytes but hands the host application an unauthenticated tenant identifier (`shop`) to key its data processing/storage on. Any app built on top of this library's documented `Registry.process`/`WebhookMetadata` API that uses `shop` to select which merchant's records to update (the intended and expected usage) can be made to apply a genuine webhook event under the wrong shop, corrupting or leaking cross-tenant data — impact matches "cross-tenant access."

### Likelihood Explanation
Likelihood is high for any attacker who is themselves a legitimate, unprivileged merchant with the app installed: they receive real webhooks addressed to their own shop, each with a valid `hmac-sha256` header computed with the app's single shared `client_secret`. They only need to capture one such request and resend it to the app's webhook endpoint with the `shop-domain` header swapped to a victim's domain — no secret material, tokens, or elevated privileges are required beyond normal app installation.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified content, e.g., include them in `to_signable_string`, or independently verify that the `shop-domain` header matches a shop value embedded in and covered by the payload/HMAC before it is trusted as the tenant identifier passed to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers/receives a legitimate webhook (e.g., `orders/create`) addressed to their shop; captures the raw HTTP request, including `raw_body` and the valid `X-Shopify-Hmac-Sha256` header (computed by Shopify using the app's shared `client_secret`).
3. Attacker resends this exact request to the app's webhook endpoint, only replacing the `X-Shopify-Shop-Domain` header value with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `raw_body` against the HMAC — unaffected by the header change (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though the payload was never generated for that shop — the app processes attacker-controlled data as if it belonged to the victim tenant. [1](#0-0) [2](#0-1) [3](#0-2)
