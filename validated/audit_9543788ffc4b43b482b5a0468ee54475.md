### Title
Unbounded `.expect()` panics on attacker-controlled `uint256` fields when converting SP1 BEEFY proofs from Solidity ABI to SCALE — ([File: evm/rust/src/conversions.rs])

### Summary
`pallet-beefy-consensus-proofs::verify_and_apply` accepts a caller-submitted, ABI-encoded `SP1BeefyProof` (Solidity `uint256` fields for `blockNumber` and `validatorSetId`) and converts it into the SCALE `beefy_verifier_primitives::Sp1BeefyProof` type via `Into`. That conversion, implemented in `evm/rust/src/conversions.rs`, narrows `blockNumber`/`validatorSetId`/MMR `leafIndex` from `U256` to `u64`/`u32` using `.try_into().expect(...)`, which panics on out-of-range values instead of returning an error.

### Finding Description [1](#0-0) 

- `From<RelayChainProof> for MmrProof` does `value.latestMmrLeaf.leafIndex.try_into().expect("mmr leaf index out of bounds")`.
- `From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof` does:
  - `value.commitment.blockNumber.try_into().expect("block number out of bounds")`
  - `value.commitment.validatorSetId.try_into().expect("validator set id out of bounds")`

These `U256` values originate from the ABI payload the caller supplies. In `modules/pallets/beefy-consensus-proofs/src/lib.rs::verify_and_apply`: [2](#0-1) 

```rust
types::PROOF_TYPE_SP1 => {
    let abi_proof =
        <ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof as SolType>::abi_decode_params(
            abi_payload,
        )
        .map_err(|_| Error::<T>::AbiDecodeFailed)?;
    let scale_proof: beefy_verifier_primitives::Sp1BeefyProof = abi_proof.into();
    ...
}
```

`abi_decode_params` only validates ABI encoding shape, not the numeric range of `blockNumber`/`validatorSetId` (both plain `uint256` fields in `SP1Beefy.sol`, e.g. `MiniCommitment.blockNumber`). Any value above `u64::MAX` (or `u32::MAX` for `validatorSetId`) decodes successfully as ABI, then panics on the subsequent `.into()` conversion via `.expect(...)`, before any cryptographic proof verification takes place.

The pallet doc header states these proofs are submitted via "signed" extrinsics from off-chain provers, but the submitter only pays the transaction fee — this is the whole point of the attack surface: it is a low-cost, unprivileged, permissionless call path (any signed account can call it), and the panic occurs deterministically before the SP1 zk verification or BEEFY signature checks, so no proof of consensus validity is required to trigger it.

### Impact Explanation
A Rust panic inside runtime `on_initialize`/extrinsic dispatch execution in a Substrate-based chain aborts the block-execution WASM invocation. Depending on how the panic propagates through `frame_support::transactional`/dispatch and the executor's panic-handling, this can manifest as a failed extrinsic (if caught) or — the more concerning class this report is testing for by analogy to the geth `cmd/evm/runner.go` SEGV bug (CVE-2018-19184), where crafted input caused an unrecoverable crash of the executing process — an unrecoverable panic that halts block production/validation for the calling node if the panic unwind is not cleanly caught by the runtime boundary. This is a Denial-of-Service class bug: CWE-476-adjacent (here it is an unchecked numeric-range assumption rather than a null pointer, but the effect — attacker-controlled input driving an unguarded `panic!`/`.expect()` inside consensus-critical proof-processing code — is analogous).

Given this pathway sits directly in the consensus-proof ingestion pipeline for BEEFY (which ultimately drives Hyperbridge's cross-chain message delivery, state commitment updates, and reward payouts), a successful DoS here could stall consensus-state updates for the whole BEEFY light client, which is a shared dependency for message delivery across all connected chains — this would qualify as "a route unable to deliver messages" per the validation criteria.

### Likelihood Explanation
High-likelihood: no privileged role, no valid proof, and no correct cryptographic material is required — an attacker only needs to submit a syntactically valid ABI-encoded `SP1BeefyProof` tuple with `commitment.blockNumber` or `commitment.validatorSetId` set above `u64::MAX`/`u32::MAX` (trivial to construct), signed by any funded account, and call `verify_and_apply` (via whatever public extrinsic wraps it — I was not able to conclusively locate/confirm the exact public dispatchable name that invokes `verify_and_apply` before the tool budget ran out; the code excerpt shows it is called from within the pallet and documented as reachable via signed extrinsics from "off-chain provers", implying a public `submit_proof`-style call). This uncertainty about the exact dispatchable wrapper is the main gap in my verification — I was unable to grep/read the `#[pallet::call]` block of `beefy-consensus-proofs` before running out of iterations to confirm call-site details (call index, weight, and whether it's `pays_fee`-gated in any way that would raise the cost of repeated attempts).

### Recommendation
- Replace all `.try_into().expect(...)` conversions in `evm/rust/src/conversions.rs` (`leafIndex`, `blockNumber`, `validatorSetId`, and any other narrowing `U256 -> u64/u32` conversions in that file) with fallible conversions that propagate a typed error (e.g. `Result`/`TryFrom` returning `beefy_verifier_primitives::Error` or a new `AbiValueOutOfRange` variant) instead of panicking.
- Ensure `verify_and_apply` (and any other caller of these `From`/`Into` impls that processes untrusted, caller-submitted ABI bytes) surfaces this as `Error::<T>::AbiDecodeFailed` (or a new dedicated error) rather than allowing a panic to propagate out of pallet dispatch logic.
- Add regression tests analogous to the existing ones in this codebase (e.g. `modules/consensus/pharos/primitives/src/spv.rs::test_over_deep_proof_rejected`, `modules/consensus/sync-committee/verifier/src/lib.rs` multi-proof length check, `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_leaf` empty-`leaf_indices` fix) that submit an ABI payload with an out-of-range `uint256` and assert a clean `Err` rather than a panic.

### Proof of Concept
1. Construct a `SP1Beefy::SP1BeefyProof` ABI tuple where `commitment.blockNumber = U256::MAX` (or any value `> u64::MAX`), with otherwise well-formed (but unverified) `mmrLeaf`, `headers`, `proof`, and `nonce` fields — the tuple only needs to satisfy `abi_decode_params`, not proof validity.
2. Prefix the encoded bytes with `types::PROOF_TYPE_SP1` and submit it as the `proof` argument to whatever public extrinsic invokes `pallet_beefy_consensus_proofs::Pallet::<T>::verify_and_apply` (documented as callable via a signed extrinsic from any account).
3. Execution reaches:
```rust
let scale_proof: beefy_verifier_primitives::Sp1BeefyProof = abi_proof.into();
```
which internally executes `value.commitment.blockNumber.try_into().expect("block number out of bounds")` in `evm/rust/src/conversions.rs`, panicking before any SP1/BEEFY cryptographic check runs.

I was not able to fully confirm the exact public call-index/name that wraps `verify_and_apply` due to running out of tool iterations, so this PoC step 2 is described at the semantic level (call path confirmed by the code excerpt) rather than pinned to an exact extrinsic signature — flagging this as the one unresolved verification gap.
