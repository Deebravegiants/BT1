## Title
Sender's HRMP deposit is permanently trapped when a pending, unconfirmed `HrmpOpenChannelRequest` is offboarded together with its initiating para - ([File: polkadot/runtime/parachains/src/hrmp.rs])

## Summary
When a para calls `hrmp_init_open_channel` and is deregistered before the recipient confirms the channel, `Hrmp::clean_open_channel_requests` refunds the sender's `sender_deposit` only if the sender is *not* in the `outgoing` list, so a self-deregistering sender's deposit is never unreserved. Since a deregistered `ParaId` can never again dispatch a `Parachain` origin, the reserved funds on its sovereign account become permanently stuck absent governance intervention.

## Finding Description
`clean_open_channel_requests` at [1](#0-0)  refunds the sender's deposit only when `!outgoing.contains(&req_id.sender)`, while the deposit was reserved unconditionally during `init_open_channel` at [2](#0-1) . `HrmpOpenChannelRequests`/`HrmpOpenChannelRequestsList` entries are removed regardless (storage stays consistent), but the reserved balance is orphaned when the sender itself is the offboarding para. This path is invoked from `perform_outgoing_para_cleanup` at session boundaries, triggered by `paras::schedule_para_cleanup` following an unprivileged `paras_registrar::deregister` call.

By contrast, for fully-established channels, `close_hrmp_channel` unconditionally unreserves both `sender_deposit` and `recipient_deposit` irrespective of offboarding status: [3](#0-2) . This confirms the asymmetric/incomplete refund logic is specific to the pending-request cleanup path, not an intentional general policy.

Once deregistered, the para's `ParaId` cannot dispatch a `Parachain` origin again, as `ensure_parachain` only succeeds for `Origin::Parachain(id)` messages actually routed by an active parachain: [4](#0-3) . There is no signed-account extrinsic path to call `unreserve` on funds reserved via the `Currency` trait outside of the pallet's internal logic, so the deposit cannot be recovered without a privileged `force_unreserve`/governance action.

## Impact Explanation
This is a genuine accounting/fund-loss bug reachable through purely unprivileged extrinsics. A para's `hrmp_sender_deposit` becomes permanently and irrecoverably reserved on its sovereign account once the para self-deregisters while it has a pending, unconfirmed outbound HRMP open request. Storage-consistency checks (`assert_storage_consistency_exhaustive`) pass despite this defect, because the bug is purely in the balance accounting, not in the channel-request bookkeeping, making it a subtle self-contained soundness defect in the HRMP deposit lifecycle.

## Likelihood Explanation
The exploit path is fully realizable by any unprivileged para manager: call `hrmp_init_open_channel(A, B, ...)`, then call `Registrar::deregister(A)` before B calls `hrmp_accept_open_channel`, and let the scheduled offboarding session elapse. This requires no governance, no validator collusion, and no race condition beyond normal, deterministic timing that a para manager fully controls — it is trivially and repeatably triggerable.

## Recommendation
In `clean_open_channel_requests`, unconditionally unreserve the sender's own `sender_deposit` when purging a pending request, regardless of whether the sender is in the `outgoing` list, matching the behavior of `close_hrmp_channel`. The recipient-side refund check should remain conditioned on the recipient's own offboarding status only.

## Proof of Concept
Add a test analogous to `refund_deposit_on_offboarding`/`no_dangling_open_requests` at [5](#0-4) : register para_a/para_b with deposits configured, call `Hrmp::init_open_channel(para_a, para_b, ...)`, then `deregister_parachain(para_a)` and advance to the offboarding session without para_b confirming. Assert `Hrmp::assert_storage_consistency_exhaustive()` passes while `Currency::reserved_balance(&para_a.into_account_truncating())` remains equal to `hrmp_sender_deposit` (e.g. 20) and `free_balance` never returns to the original 100, demonstrating the permanently trapped deposit.

#[test]
fn no_dangling_open_requests() {
	let para_a = 2032.into();
	let para_b = 2064.into();

	let mut genesis = GenesisConfigBuilder::default();
	genesis.hrmp_sender_deposit = 20;
	genesis.hrmp_recipient_deposit = 15;
	new_test_ext(genesis.build()).execute_with(|| {
		// Register two parachains and open a channel between them.
		register_parachain_with_balance(para_a, 100);
		register_parachain_with_balance(para_b, 110);
		run_to_block(5, Some(vec![4, 5]));

		// Start opening a channel a->b
		Hrmp::init_open_channel(para_a, para_b, 2, 8).unwrap();
		assert_eq!(<Test as Config>::Currency::free_balance(&para_a.into_account_truncating()), 80);

		// Then deregister one parachain, but don't wait two sessions until it takes effect.
		// Instead, `para_b` will confirm the request, which will take place the same time
		// the offboarding should happen.
		deregister_parachain(para_a);
		run_to_block(9, Some(vec![9]));
		Hrmp::accept_open_channel(para_b, para_a).unwrap();
		assert_eq!(<Test as Config>::Currency::free_balance(&para_b.into_account_truncating()), 95);
		assert!(!channel_exists(para_a, para_b));
		run_to_block(10, Some(vec![10]));

		// The outcome we expect is `para_b` should receive the refund.
		assert_eq!(
			<Test as Config>::Currency::free_balance(&para_b.into_account_truncating()),
			110
		);
		assert!(!channel_exists(para_a, para_b));
		Hrmp::assert_storage_consistency_exhaustive();
	});
}
