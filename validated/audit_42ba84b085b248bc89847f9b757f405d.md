## Analysis

The reported bug class (Issue 94 / M-10) is about an identity-binding value being trusted/acted upon without being covered by the same integrity check that is supposed to authenticate the whole message. The closest reachable analog in `shopify_api` is in the webhook HMAC verification path.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns **only the raw HTTP body**: [1](#0-0) 

and `Utils::HmacValidator.validate` computes/compares the signature over exactly that signable string: [2](#0-1) 

But `Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers (`x-shopify-shop-domain`, etc.), which are **not part of the signed material**: [3](#0-2) 

`Registry.process` only checks the HMAC of the body, then trusts `request.shop` and hands it to the app's handler as the attributed tenant: [4](#0-3) 

Since the HMAC-signing secret (`Context.api_secret_key`, the app's client secret) is the **same for every shop that installs the app**, this breaks the binding: `shop-header-claimed == shop-that-actually-produced-the-signed-body`. Anyone can install the target app on their own (free/dev) store, receive a legitimately HMAC-signed webhook body, then replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. The HMAC check still passes (it never covered the shop header), and the app processes it as if it came from the victim tenant.

### Title
Webhook shop attribution is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated headers and passed downstream as trusted tenant-identifying data.

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC-SHA256 over `verifiable_query.to_signable_string` and compares it to the `hmac` field [5](#0-4) . For webhook requests, `to_signable_string` returns `@raw_body` only [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` come from HTTP headers that are never part of that signed string [6](#0-5) . `Registry.process` validates only the HMAC and then forwards `request.shop` unmodified to the registered handler as the webhook's tenant identity [7](#0-6) .

Because the app's HMAC secret (`Context.api_secret_key`) is shared across all shops installing the app (it is not per-shop), any actor who can install the app on any shop (including a free/trial store they control) can trigger a legitimately signed webhook body, then replay that exact body with a modified `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header pointing at a different, victim shop. `HmacValidator.validate` still returns `true` because the signed material (the body) is unchanged, and the forged `shop` value is delivered to the app's business logic as authenticated tenant context.

### Impact Explanation
This breaks the binding `shop-header-claimed == shop-that-produced-signed-body`, enabling cross-tenant confusion in the host application: webhook payloads can be attributed to the wrong merchant/shop. Any handler logic keyed on `WebhookMetadata#shop` (e.g., updating per-shop records, triggering per-shop side effects) can be made to act on/for a shop the attacker does not control, using data crafted by the attacker. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitability only requires being able to install the target app on any shop (a normal, unprivileged action any developer/merchant can perform to obtain a validly-signed webhook body) and the ability to send arbitrary HTTP requests with custom headers to the app's webhook endpoint — no `api_secret_key`, access token, or privileged account is needed.

### Recommendation
Include the tenant/shop-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the claimed shop to the signed payload, so that `HmacValidator.validate` fails if the `shop` header is altered independently of the body.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook (e.g., `orders/create`) and capture the raw request: body `B`, and header `x-shopify-hmac-sha256` = `H`, which is valid because `H = HMAC-SHA256(secret, B)` per `HmacValidator.validate_signature` [5](#0-4) .
3. Resend the same body `B` and same `H` to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` and `H` [8](#0-7) ; the handler is then invoked with `shop: "victim-shop.myshopify.com"` [9](#0-8) , causing the app to process attacker-controlled data as if it came from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
