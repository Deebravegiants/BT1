### Title
Stale `operator_qr_expiration_time` snapshot allows inconsistent operator-session validity checks across a signup flow - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::run` reads `operator_qr_expiration_time` once from the shared config before entering its outer loop, then reuses that snapshot for `scan_initial_qr_codes` and `idle_wait_for_signup_request` across every signup iteration, while `do_signup` independently re-reads the *same* config field fresh from `orb.config.lock().await` for `scan_remaining_qr_codes`. This mirrors the Nouns `GRACE_PERIOD` bug class: a value that gates whether a previously-established state (an "expired"/no-longer-valid operator QR-code session) should be treated as final is not fixed at the time that state was computed, and can silently change mid-flow, flipping the outcome of a validity check that other parts of the code already treated as settled.

### Finding Description
In `MasterPlan::run`, `operator_qr_expiration_time` is destructured from `*orb.config.lock().await` **before** the `loop { ... }` block begins: [1](#0-0) 
This single snapshot is then passed into `scan_initial_qr_codes` and `idle_wait_for_signup_request` for the lifetime of the `run()` call, even though the orb keeps polling the backend for config updates in the background.

Separately, `do_signup` re-reads the config independently for the same field: [2](#0-1) 
and passes a potentially *different* (fresher) value of `operator_qr_expiration_time` into `scan_remaining_qr_codes`, which re-checks `operator_data.timestamp.elapsed() < operator_qr_expiration_time` to decide whether the previously scanned operator QR-code/location binding is still valid: [3](#0-2) 

The same expiration variable is also used in `scan_initial_qr_codes` for a semantically identical "is this operator session still valid" check: [4](#0-3) 

Because two different code paths within the same overall signup flow use two different snapshots of the same config value to answer the same "is the operator session still fresh" question, the operator-session validity decision is not actually final at the point it appears to be computed — exactly the property the Nouns report calls out about `Expired` not being a true terminal state when a governing time-window parameter can change after the fact.

### Impact Explanation
If the backend pushes a config update that changes `operator_qr_expiration_time` between the outer-loop snapshot and the `do_signup`-local snapshot, an operator QR-code/location binding that should have been treated as stale in one part of the flow can be treated as still valid in another (or vice versa). Since `operator_data` carries the operator's verified location data used for identity/location binding of the subsequent user signup, this inconsistency can extend the effective trust window of an operator session beyond what was intended by the currently-active configuration, allowing a user signup to be bound to operator location data that should have already required re-verification. Impact is limited to identity/location-binding consistency for signup, not credential compromise.

### Likelihood Explanation
Likelihood is low: it requires a backend-pushed config change to `operator_qr_expiration_time` to occur in the narrow window between when `MasterPlan::run` takes its snapshot and when `do_signup` takes its own snapshot for the same signup attempt. This is analogous to the original finding, which was rated Medium despite requiring an "admin action" (there, a `GRACE_PERIOD` change) because the resulting state inconsistency is a genuine design flaw reachable during normal, non-malicious operation (routine config propagation), not an attack requiring a compromised admin.

### Recommendation
Read `operator_qr_expiration_time` (and other config values gating time-window validity checks) exactly once per signup attempt, and thread that single snapshot through every place that checks `operator_data.timestamp.elapsed()` for that attempt (`scan_initial_qr_codes`, `idle_wait_for_signup_request`, and `scan_remaining_qr_codes`), instead of re-reading `orb.config.lock().await` independently in `do_signup`. This guarantees all validity checks within one signup use a consistent expiration threshold, eliminating the possibility of a stale-vs-fresh mismatch flipping the operator session's validity mid-flow.

### Proof of Concept
1. Orb starts `MasterPlan::run`; config snapshot A has `operator_qr_expiration_time = 60s`.
2. Operator QR-code is scanned and `operator_data.timestamp` is recorded; `scan_initial_qr_codes`/`idle_wait_for_signup_request` continue to use snapshot A (60s) for the remainder of `run()`'s lifetime since it was captured outside the loop.
3. Backend pushes a new config with `operator_qr_expiration_time = 300s` (a legitimate update, not requiring any special attacker privilege).
4. A new signup begins; `do_signup` re-reads the config and gets the fresh value (300s), passing it to `scan_remaining_qr_codes`.
5. At `operator_data.timestamp.elapsed() = 90s` (already past the 60s window used elsewhere in the flow, but under the new 300s window), `scan_remaining_qr_codes` treats the stale operator/location binding as still valid, while other parts of the flow using the old 60s snapshot would have required a fresh operator QR-code scan — producing an inconsistent, non-final validity decision for the same operator session.     async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }

    async fn scan_remaining_qr_codes(

        orb: &mut Orb,

        operator_qr_expiration_time: Duration,
    ) -> Result<Option<ResolvedQrCodes>> {
        loop {
            match qr_codes {
