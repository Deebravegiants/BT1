### Title
Integer overflow in `Memory::resize` bypasses `EVM_MEMORY_BYTES` cap on 32-bit `usize` (wasm32 runtime target), leading to unchecked out-of-bounds panic in `slice_len`/`set` - (File: substrate/frame/revive/src/vm/evm/memory.rs)

### Summary
`as_usize_or_halt` only rejects a `U256` offset if its low limb exceeds `usize::MAX`, which on the actual FRAME runtime target (`wasm32`, where `usize` is 4 bytes) allows any offset up to `u32::MAX` (~4.29e9) to pass unmodified. `Memory::resize` then computes `revm::interpreter::num_words(offset.saturating_add(len)) * 32` using plain (non-saturating) `usize` arithmetic inside `num_words`, which can overflow/wrap for such large-but-"valid" offsets, producing an incorrect, too-small `target_len` that trivially satisfies the `EVM_MEMORY_BYTES` cap check while the real `offset` remains huge, so the subsequent unchecked `self.data[offset..offset+len]` indexing in `set`/`slice_len` panics.

### Finding Description
`as_usize_or_halt_with` in [1](#0-0)  only checks `limbs[0] > usize::MAX as u64` and that the higher limbs are zero. On the `wasm32` target that FRAME runtimes (including `pallet-revive`) are actually compiled to, `usize` is 32 bits, so any `U256` value up to `u32::MAX` (≈4.29 × 10⁹) is accepted as a valid offset, even though this is far larger than any sane memory offset and far larger than `EVM_MEMORY_BYTES`.

`mload`/`mstore`/`mstore8` in [2](#0-1)  pass this attacker-controlled `offset` (from ordinary `PUSHx`/`MLOAD`/`MSTORE` EVM opcodes reachable by any unprivileged contract caller) directly into `Memory::resize`.

`Memory::resize` in [3](#0-2)  computes `target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32` and compares `target_len` against `EVM_MEMORY_BYTES`. While `saturating_add` itself cannot overflow, `revm::interpreter::num_words` (typically `(len + 31) / 32`) performs its own internal, non-saturating addition on the same `usize`. When `offset` is close to `usize::MAX` (achievable here because `usize::MAX == u32::MAX` on wasm32 and that boundary passes `as_usize_or_halt`), this internal addition can overflow. Depending on whether overflow checks are active for the arithmetic inside the external `revm` crate:
- If overflow checks fire, the runtime panics/traps directly inside `num_words`.
- If the addition wraps (release arithmetic without checks, which is the default unless a crate/profile explicitly enables `overflow-checks`), `target_len` wraps to a small value that trivially passes the `> EVM_MEMORY_BYTES` cap check, so `resize` reports success (`ControlFlow::Continue`) without actually growing `self.data` to cover the true, huge `offset`.

Either way, execution proceeds to `slice_len`/`set` in [4](#0-3)  and [5](#0-4) , which index `self.data[offset..offset+len]` with **no bounds check** (documented as "Panics on out of bounds"). Since `self.data.len()` is far smaller than `offset`, this indexing panics.

This directly violates the intended invariant: any offset that should be rejected by the `EVM_MEMORY_BYTES` cap must never reach the unchecked slice index in `set`/`slice_len`. The cap check in `resize` is bypassed precisely because of the overflow in its own size computation, not because of a missing check elsewhere.

### Impact Explanation
An unprivileged contract caller can craft EVM-compatible bytecode (via `pallet-revive`'s EVM execution path, reachable through an ordinary signed `call`/deploy extrinsic) containing a single `PUSH4 0xFFFFFFFF` followed by `MSTORE` or `MLOAD`. This offset passes `as_usize_or_halt` unmodified, triggers the overflow path in `Memory::resize`, and reaches an unchecked slice index, causing a Rust panic during on-chain contract execution instead of the intended graceful `Halt::Error(OutOfGas)`. Depending on how (or whether) `pallet-revive` isolates panics from individual contract executions, this can abort the current extrinsic unpredictably (denial of service for that call) or, if not properly caught at a higher boundary, disrupt block execution — a queue/validation-path halting concern explicitly in scope of the core invariants.

### Likelihood Explanation
- Preconditions: only requires the ability to submit an ordinary `call`/deploy extrinsic that executes attacker-supplied EVM bytecode through `pallet-revive`'s EVM-compatibility interpreter — available to any unprivileged account.
- Feasibility: the malicious bytecode is a two/three-instruction snippet (`PUSH4 0xFFFFFFFF; MSTORE`), trivially constructible and requires no special permissions, weight tricks, or race conditions.
- Repeatability: fully deterministic — the same bytecode will trigger the panic every time it is executed on any node compiled for `wasm32` (the standard FRAME runtime target).

### Recommendation
- Fix the overflow at its source: make the size computation in `Memory::resize` fully saturating/checked, e.g. compute `offset.checked_add(len).and_then(|v| v.checked_add(31)).map(|v| v / 32 * 32)` (or equivalent explicit checked arithmetic) instead of delegating to `revm::interpreter::num_words` on a potentially near-`usize::MAX` value, and treat any overflow as `Halt::Error(OutOfGas)` before comparing against `EVM_MEMORY_BYTES`.
- Additionally, tighten `as_usize_or_halt_with` to reject offsets larger than `EVM_MEMORY_BYTES` (or some sane upper bound well below `usize::MAX`) directly, rather than only checking against the full `usize` range, removing any dependency on `usize` width/target architecture.

### Proof of Concept
Rust unit/fuzz test plan in `substrate/frame/revive/src/vm/evm/memory.rs` (or a fuzz harness targeting `mstore`/`mload`):
```rust
#[test]
fn mstore_large_offset_does_not_panic() {
    // Simulate as_usize_or_halt boundary values that pass the usize check
    // but are far beyond EVM_MEMORY_BYTES.
    for offset in [usize::MAX, EVM_MEMORY_BYTES as usize, EVM_MEMORY_BYTES as usize + 1] {
        let mut memory = Memory::<Test>::new();
        let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
            memory.resize(offset, 32)
        }));
        // Assert: resize must either Break(Halt::Error(OutOfGas)) or the harness must
        // catch a panic here — the bug is proven if `result` panics or if `resize`
        // returns Continue(()) despite offset being enormous relative to EVM_MEMORY_BYTES.
        assert!(result.is_ok(), "resize must not panic for boundary offset {offset}");
        if let Ok(ControlFlow::Continue(())) = result {
            // If resize incorrectly succeeded, subsequent slice access must not panic either.
            let slice_result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
                memory.slice_len(offset, 32)
            }));
            assert!(slice_result.is_ok(), "slice_len panicked for offset {offset} — cap bypass confirmed");
        }
    }
}
```
Expected outcome demonstrating the bug: for `offset = usize::MAX` (equivalently `u32::MAX` when compiled for `wasm32`), `resize` either panics internally (overflow-checked build) or returns `Continue(())` with an undersized buffer, and the follow-up `slice_len`/`set` call panics — proving the `EVM_MEMORY_BYTES` cap is bypassed and an unchecked slice index is reached.

pub fn as_usize_or_halt_with(value: U256, halt: impl Fn() -> Halt) -> ControlFlow<Halt, usize> {
	let limbs = value.0;
	if (limbs[0] > usize::MAX as u64) | (limbs[1] != 0) | (limbs[2] != 0) | (limbs[3] != 0) {
		ControlFlow::Break(halt())
	} else {
		ControlFlow::Continue(limbs[0] as usize)
	}
}

	pub fn resize(&mut self, offset: usize, len: usize) -> ControlFlow<Halt> {
		let current_len = self.data.len();
		let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
		if target_len > crate::limits::EVM_MEMORY_BYTES as usize {
			log::debug!(target: crate::LOG_TARGET, "check memory bounds failed: offset={offset} target_len={target_len} current_len={current_len}");
			return ControlFlow::Break(Error::<T>::OutOfGas.into());
		}

		if target_len > current_len {
			self.data.resize(target_len, 0);
		}

		ControlFlow::Continue(())
	}
