### Title
Stale delegate grant silently re-activates when the position NFT returns to the granting owner, restoring a former delegate's full account authority - (File: contracts/controller/src/storage/account.rs)

### Summary
CVE-2019-11739 is a leak class bug: content a user believed was protected/invisible (an encrypted S/MIME part) is silently included when the message is forwarded into a new context (HTML reply). The XOXNO Lending analog is `DelegateGrant` storage: when the position NFT is transferred, `get_delegates` filters grants by `granted_by == current_owner`, so the previous owner's delegates *appear* revoked (the stored list reads as empty), but the grant is not deleted. If the NFT ever returns to the original owner before an intervening owner overwrites or purges the entry, the stale delegate list becomes live again — invisible authorization "plaintext" leaking back into effect on a forward/transfer the owner may not connect to the old grant.

### Finding Description
`DelegateGrant` is stored under `ControllerKey::Delegates(account_id)` and keyed only by the `granted_by` address, with no transfer epoch or generation counter (`common/src/types/controller.rs:63-73`). Liveness is purely a filter:

- `get_delegates` returns the stored list only when `grant.granted_by == *owner` (`contracts/controller/src/storage/account.rs:176-181`).
- On NFT transfer, the old owner's grant is therefore dormant but remains in persistent storage.
- If the NFT is transferred back to `granted_by` and no intervening owner called `add_delegate` (overwrite) or `remove_delegate` (purge, `account.rs:226-247`), the dormant list is live again with its original delegates.

Delegates hold broad economic power: they can `borrow`, `withdraw`, and run all account strategies, choosing external payout recipients, within the account's risk gates (`docs/reference/invariants.md` INV-AUTH-02, `docs/reference/endpoints.md`). The only other requirement — that the delegate still be an active registered position manager — is unchanged by the NFT transfers.

Concretely, a reactivated delegate can call `withdraw(caller=delegate, account_id, withdrawals, to=delegate_controlled_address)` or `borrow(..., to=...)`, draining collateral or loading the account with debt paid out to the delegate.

### Impact Explanation
Theft of user funds. Once the grant resurrects, the former delegate — who needs no further authorization from the owner — can withdraw collateral to an arbitrary recipient or borrow against the account to themselves, up to the health-factor gates. An NFT owner who regains a token (buyback, unwound sale, NFT used as collateral in another protocol and redeemed, marketplace round-trip) has no on-chain signal that a dormant grant exists: `get_delegates` and all views read it as empty while they were not the owner, and nothing warns them on re-acquisition. The exposure is silent exactly like the hidden MIME part.

### Likelihood Explanation
Requires a specific sequence: (1) owner grants a delegate who is an active position manager; (2) NFT leaves the owner; (3) intervening holders never call `add_delegate`/`remove_delegate` (common — passive holders and marketplace escrows have no reason to touch delegates); (4) NFT returns to the original owner. Steps 2–4 occur naturally in NFT trading, lending-against-NFT, or escrow flows. The attacker (former delegate) can also engineer the round trip: buy the NFT through a second address and sell/transfer it back to the original owner, who may accept it (e.g., repurchasing their own position). Medium likelihood; impact is bounded by the account's withdrawable collateral and borrowable headroom.

### Recommendation
Bind grants to a transfer epoch instead of (or in addition to) the owner address: store a per-account transfer counter incremented in the controller's NFT-transfer hook/owner-resolution path, stamp `DelegateGrant` with it, and have `get_delegates` require both `granted_by == owner` and `epoch == current_epoch`. Alternatively, eagerly purge `ControllerKey::Delegates(account_id)` whenever `account_owner` detects an owner change (lazy-delete on first resolution after transfer), so resurrection is impossible regardless of intervening writes.

### Proof of Concept
Sequence (mirrors the existing unit tests in `contracts/controller/tests/storage/account.rs:112-227`, minus the purge):

1. Alice owns account `id`; governance has registered Bob as an active position manager (`set_position_manager(BOB, true)`).
2. Alice calls `add_delegate(alice, id, bob)` → `DelegateGrant{granted_by: alice, delegates: [bob]}` stored.
3. Alice transfers NFT `id` to Carol. `get_delegates(id, carol)` reads empty; Bob cannot act.
4. Carol never touches delegates. Carol transfers NFT `id` back to Alice (round-trip sale/escrow redemption).
5. `get_delegates(id, alice)` now returns `[bob]` again — the stale grant re-arms with no event or warning.
6. Bob calls `withdraw(caller=bob, account_id=id, withdrawals=[...], to=bob)` or `borrow(..., to=bob)`, extracting Alice's collateral/borrow capacity up to the HF gate.

Note: `remove_delegate` called by any intervening owner purges the stale entry (`account.rs:236-238`), which is the only existing mitigation — the bug triggers precisely when no intervening owner ever touches the delegate list, which is the common case for passive/transient holders.
