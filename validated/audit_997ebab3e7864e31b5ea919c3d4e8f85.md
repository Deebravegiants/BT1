This confirms the vulnerability path. The `docs/usage/webhooks.md` explicitly documents `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify" — implying full authentication — while the actual implementation only authenticates the raw body bytes, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that are handed to the app's handler as trusted identity data.

### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body via `Utils::HmacValidator.validate`. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are exposed to the app's webhook handler are read directly from unauthenticated HTTP headers, which are never included in the HMAC-signed payload. This breaks the intended binding: **shop asserted in the header == shop that the HMAC-signed body actually originated from**.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` treats a successful HMAC check as proof the entire request — including these header-derived fields — came from Shopify for that shop, and forwards them unchecked to the app's handler: [3](#0-2) 

Because `HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (the raw body) using the app's `api_secret_key`: [4](#0-3) 

any request whose body+HMAC pair is valid for the app's secret (e.g., one legitimately received from Shopify for the attacker's *own* shop, since every merchant installing the app can trigger webhooks for their own store and thus obtain a valid `(body, hmac)` pair signed with the same shared `client_secret`) can be replayed with an arbitrary `x-shopify-shop-domain` header. The HMAC still validates because the header is not part of the signed content, yet `Registry.process` passes that attacker-chosen `shop` value straight into `WebhookMetadata`, which the docs and handler contract treat as an authenticated tenant identifier: [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding gap: `shop-authenticated (by HMAC) != shop-used (from header)`.

### Impact Explanation
Applications built on this gem are documented to key tenant-scoped processing (job enqueue, data writes, per-shop authorization decisions) off `data.shop` from `WebhookMetadata`, trusting that `Registry.process` already verified the webhook's authenticity end-to-end. Because the shop identity is not bound to the signed content, an attacker who controls one shop that has this same app installed can forge webhooks that are attributed to a victim shop, leading to cross-tenant data confusion/injection in the host application (e.g., writing attacker-supplied order/product data into a victim shop's records, or triggering `customers/redact`-style processing under the wrong tenant). This satisfies the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant with the target app installed on their own store (a low bar — most Shopify apps allow any merchant to install), enabling them to receive a genuinely-signed `(body, hmac)` pair for a webhook topic of their choosing, then replay it with a modified `shop-domain` header directly to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is needed.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` values in the HMAC-signed content (or otherwise cryptographically bind them to the body/HMAC), or independently authenticate the shop by cross-referencing it against a shop known to have installed the app with a matching webhook subscription/secret, rather than trusting the raw header value once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to receive a legitimately signed request with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay this exact `(B, H)` pair to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only and succeeds, since `to_signable_string` never includes the shop header: [6](#0-5) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...)`, and the host application processes attacker-controlled data as if it came from the victim shop.
