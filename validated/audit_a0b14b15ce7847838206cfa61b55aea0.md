### Title
`HinkalHelper.performProoflessDepositChecks` omits an upper bound on `amounts[i]`, permanently freezing on-chain-deposited UTXOs whose amount exceeds the circuit's spendable range - (File: contracts/HinkalHelper.sol)

### Summary
`performProoflessDepositChecks` only requires `amounts[i] > 0` and never checks `amounts[i] < MAX_AMOUNT` (or the tighter bound the spend circuit actually enforces). Any UTXO minted on-chain via `prooflessDeposit` with `amounts[i]` above that bound produces a leaf that can never be consumed as `inAmounts[i][j]` in a valid `transact` proof, because `ConditionalOverflowPreventer`'s `Num2Bits(252)`/`LessThan(252)` constraints (invoked as `OverflowPreventer` in `MainEVMCircuit.circom`) will always fail for it.

### Finding Description
The claimed equality: every on-chain minted UTXO `amount` must satisfy `amount < (2**252 - 1) / inputCount` (the bound the spend circuit's `OverflowPreventer` enforces on `inAmounts[i][j]`), which is at most `MAX_AMOUNT = 2**252` for `inputCount == 1` and strictly smaller for larger `inputCount`. This is currently **not enforced** at deposit time.

Path:
- `Hinkal.prooflessDeposit` (`contracts/Hinkal.sol:263-295`) calls `hinkalHelper.performProoflessDepositChecks(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs)`.
- `performProoflessDepositChecks` (`contracts/HinkalHelper.sol:37-62`) only checks `amounts[i] > 0` [1](#0-0) . There is no `amounts[i] < MAX_AMOUNT` check anywhere in this function.
- `_createProoflessDepositCommitments` then unconditionally creates the leaf with `amount: amounts[i]` [2](#0-1)  and inserts it via `insertCommitments`, regardless of magnitude.
- The bound that *is* enforced later, `CircomDataBuilder.formBasicInput`'s `require(circomData.amountChanges[i] < MAX_AMOUNT ...)` [3](#0-2) , only bounds the *public net delta* (`amountChanges[i]`), not the private per-UTXO `inAmounts[i][j]` that the victim would need to spend as an input in a future `transact`.
- The actual constraint on a spendable input UTXO amount lives in the circuit: `MainEVMCircuit.circom` instantiates `preventInOverflow[i][j] = OverflowPreventer(inputCount); preventInOverflow[i][j].in <== inAmounts[i][j];` [4](#0-3) , which forwards to `ConditionalOverflowPreventer(nCount)` with `enabled = 1`: it decomposes the value with `Num2Bits(252)` and requires `in < (2**252 - 1) / nCount` [5](#0-4) . If `inAmounts[i][j]` does not fit in 252 bits (e.g. an attacker sets `amounts[i]` to `type(uint256).max` or any value ≥ 2**252), witness generation for `Num2Bits(252)` fails outright — no valid proof can ever be produced referencing that UTXO as an input, for any `inputCount`.

Attacker's exact call: as an unprivileged EOA, call `Hinkal.prooflessDeposit(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs, createBlockedUtxos, orderId)` where `stealthAddressStructures[i]` is a victim's known deposit/consolidation stealth address (e.g., a relay/service address that auto-consumes incoming deposits for order fulfillment) and `amounts[i] >= 2**252` (or, more precisely, ≥ `(2**252-1)/inputCount` for the smallest `inputCount` circuit variant in use). The attacker funds this deposit with their own tokens/ETH (`_handleTransfersFromProoflessDeposit`), but the funds land as an unspendable leaf under the victim's stealth address. `checkOnchainCreation`/`dimensionsCheck` in `performHinkalChecks` do not re-validate the amount of a previously-created leaf against the circuit bound when it is later referenced as an input — they only validate structural dimensions and `onChainCreation` semantics, not the magnitude of pre-existing on-chain UTXOs.

None of the existing guards catch this: `performProoflessDepositChecks` has no upper bound; `formBasicInput`'s `MAX_AMOUNT` check only applies to `amountChanges` (the externally visible net delta), not to the individual `inAmounts` witness that must later decompose within 252 bits; and the circuit-side range check (`ConditionalOverflowPreventer`) only fires at proof-generation/verification time, by which point the funds are already irreversibly locked on-chain.

### Impact Explanation
Funds sent to the victim's stealth address become permanently unspendable/frozen — the victim can never construct a valid `transact` proof that references this leaf as an input, since witness generation for `Num2Bits(252)` in `ConditionalOverflowPreventer` cannot succeed for a value that doesn't fit the required bit-width/range. This matches the Critical category "permanent freezing of user funds." The attack is repeatable against any known victim stealth address (e.g., a relay's public deposit address) and costs the attacker only the deposited amount (which is otherwise lost/locked too, but the attacker's goal is to grief/freeze the victim's expected incoming deposit and disrupt the victim's off-chain order/consolidation logic that assumes on-chain deposits are always eventually spendable).

### Likelihood Explanation
No special privileges are required — `prooflessDeposit` is a public, unprivileged entry point. The attacker needs only: (1) a known victim stealth address (public information for any relay/service that publishes a deposit address), (2) enough of the target token/ETH to satisfy the deposit transfer (or use of a token with negligible real value / a custom ERC20 they control, since `Hinkal.prooflessDeposit` places no restriction on token address either), and (3) a single transaction. This is fully feasible and repeatable at will.

### Recommendation
Add an explicit upper bound check in `HinkalHelper.performProoflessDepositChecks` mirroring the circuit's actual spendability constraint, e.g.:
```solidity
require(amounts[i] < uint256(MAX_AMOUNT), "Amount exceeds MAX_AMOUNT");
```
Ideally, bound it more conservatively to the smallest `inputCount`/`(2**252-1)/inputCount` bound used across all deployed circuit configurations, so that any minted UTXO is guaranteed spendable under every supported circuit variant, not just the loosest one.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a mock ERC20 token; whitelist required contracts.
2. As `attacker` (unprivileged EOA), call `hinkal.prooflessDeposit` with a single entry: `erc20Addresses = [token]`, `amounts = [type(uint256).max]` (or `2**252`), `stealthAddressStructures = [victimStealthAddressStructure]`, valid non-empty `onChainEncryptedOutputs`, `createBlockedUtxos = false`.
3. Assert the call succeeds (no revert) and the on-chain commitment/leaf is inserted with `amount == type(uint256).max`, proving the equality `amount < MAX_AMOUNT` was never enforced.
4. Using locally generated witnesses for `MainEVMCircuit` (via `circomlibjs`/`snarkjs`), attempt to build a witness with `inAmounts[0][0] = type(uint256).max` for a `transact` proof spending that leaf as an input; assert witness calculation throws/fails on the `Num2Bits(252)` constraint inside `ConditionalOverflowPreventer` (called from `OverflowPreventer` at `circuits/MainEVMCircuit.circom:121-122`), confirming the leaf can never be referenced by `inAmounts` in any valid proof, and thus `Hinkal.transact` can never be called successfully to spend it - demonstrating permanent freezing.
