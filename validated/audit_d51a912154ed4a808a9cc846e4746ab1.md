### Title
Any authenticated node role (including ReadOnly) can retrieve a Bridge's plaintext OutgoingToken via `GET /v2/bridge_types/:BridgeName` - (File: core/web/router.go)

### Summary
The `/v2/bridge_types/:BridgeName` `Show` route is only gated by `auth.Authenticate` (session or API token), with no `auth.RequiresEditRole`/`RequiresAdminRole` check, unlike the sibling `Create`, `Update`, and `Destroy` routes on the same resource. The handler returns the bridge's `OutgoingToken` in plaintext JSON, exposing a sensitive credential to any authenticated user regardless of role, including `ReadOnly`.

### Finding Description
In `core/web/router.go`, the bridge type routes are registered as: [1](#0-0) 
Only `Create`, `Update`, and `Destroy` are wrapped with `auth.RequiresEditRole`; `Index` and `Show` are reachable by any authenticated principal.

`BridgeTypesController.Show` fetches the bridge from the DB and serializes it without any field filtering based on role: [2](#0-1) 

`presenters.NewBridgeResource` always sets `OutgoingToken` from the underlying `bridges.BridgeType.OutgoingToken` field, which is stored unhashed: [3](#0-2) [4](#0-3) 

By contrast, `IncomingToken`/`IncomingTokenHash` is salted and hashed at rest and only returned once, at creation time (`omitempty` json tag), while `OutgoingToken` is persisted and returned as-is on every `Show`/`Index` call.

### Impact Explanation
The `OutgoingToken` is the credential the Chainlink node itself uses when calling out to bridge/external-adapter endpoints, and it can also be used by the node to authenticate itself for job-run resumption flows tied to that bridge. Any authenticated node user — including a `ReadOnly`-role account that should not be able to modify or fully control the node — can read this token via a simple `GET` request, undermining the role-based access boundary the rest of the bridge API deliberately enforces (`RequiresEditRole` on Create/Update/Destroy). This is a cross-role information disclosure allowing a low-privileged principal to obtain a secret they should not have access to.

### Likelihood Explanation
Any node operator granting `ReadOnly` (or any other authenticated, non-Edit) role access to a user for legitimate dashboard/monitoring purposes inadvertently grants that user the ability to read all bridges' `OutgoingToken` values by iterating `/v2/bridge_types` (`Index`, also unrestricted) and then `Show`. No special conditions or race are required — a normal authenticated API call is sufficient.

### Recommendation
Restrict `GET /v2/bridge_types/:BridgeName` (and consider `Index`) with the same role check applied to mutation routes (e.g. `auth.RequiresEditRole` or a dedicated read scope), or omit `OutgoingToken` from the `BridgeResource` returned to non-privileged roles, mirroring the `omitempty`/create-only exposure pattern already used for `IncomingToken`.

### Proof of Concept
1. Create a Chainlink node user with `ReadOnly` role (or issue a ReadOnly-scoped API token).
2. As that user, call `POST /v2/bridge_types` is blocked (403) — confirming role enforcement works for mutations.
3. As the same ReadOnly user, call `GET /v2/bridge_types` to enumerate bridge names, then `GET /v2/bridge_types/<name>` for each.
4. Observe the JSON response includes `"outgoingToken": "<plaintext token>"` for every bridge, despite the user lacking Edit/Admin privileges.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
