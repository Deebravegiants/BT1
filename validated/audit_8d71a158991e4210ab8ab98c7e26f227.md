### Title
Permanent loss of bridged funds when `HyperFungibleToken`/`WrappedHyperFungibleToken` push-delivers to a reverting/blacklisted beneficiary with no timeout escape hatch - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`onAccept()` in both `HyperFungibleToken` and `WrappedHyperFungibleToken` unconditionally pushes the bridged value to an attacker/user-supplied `beneficiary` address (`_mint(beneficiary, ...)` or `IERC20(_underlying).safeTransfer(beneficiary, ...)`). If that push reverts — e.g. the underlying token blacklists the beneficiary (USDC-style deny-lists) or the beneficiary has a broken/absent receive path — `onAccept` fails every single time it is retried, since `EvmHost.dispatchIncoming` treats a failed callback as retryable rather than resolving it. A `PostRequest` dispatched with `timeout == 0` (a caller-selectable field in `HyperFungibleToken.SendParams`) never expires, so the ISMP timeout path (`onPostRequestTimeout`, which would re-mint/refund the burned or escrowed tokens on the source chain) can never be reached either. The result is funds burned/locked on one side of the bridge with no code path that can ever deliver or refund them — the exact "push over pull, single failure point" bug class flagged in the source report, reachable here by any unprivileged token bridger who sets the recipient/timeout.

### Finding Description
`WrappedHyperFungibleToken.onAccept` performs the payout directly in the callback invoked by the host: [1](#0-0) 

For non-WETH underlying tokens (e.g. USDC), the payout is a bare `safeTransfer` with no `try/catch`: [2](#0-1) 

`HyperFungibleToken.onAccept` similarly mints unconditionally to the decoded beneficiary: [3](#0-2) 

The host's delivery path treats a failing callback as merely retryable, not as a terminal/refundable state: [4](#0-3) 

Because `_requestReceipts[commitment]` is deleted on failure "so that it can be retried," the message is never marked delivered, but it is also never rejected — any relayer resubmitting the exact same proof will hit the exact same revert forever if the underlying failure condition (blacklist, non-payable recipient with no fallback for ERC20, etc.) is permanent.

The only other resolution path is timeout, handled by `HandlerV2.handlePostRequestTimeouts`, which requires `request.timeout() > state.timestamp` to be false (i.e., must have actually expired): [5](#0-4) 

But the request's `timeoutTimestamp` is fully attacker/user controlled at dispatch time via `SendParams.timeout`, and a value of `0` is explicitly treated as "no timeout" at dispatch: [6](#0-5) 

With `timeoutTimestamp == 0`, per the standard ISMP convention used throughout this codebase, the request is defined to never expire, so `handlePostRequestTimeouts` can never process it and `onPostRequestTimeout` (which re-mints/refunds the sender) can never run. Combining a `to` address that will forever revert on receipt of funds (blacklisted by the token issuer, or any other unconditionally-reverting recipient) with `timeout = 0` — both of which are just fields inside `HyperFungibleToken.SendParams`/`HyperFungibleTokenUpgradeable.SendParams` chosen by the calling account — produces a message that:
1. Has already burned/escrowed the value on the source side, and
2. Can never successfully complete `onAccept` on the destination side, and
3. Can never time out and refund the source side.

The value is permanently unrecoverable, mirroring the audited bug class: a single push-based transfer failure (blacklist/callback failure) blocks a critical accounting flow with no pull-based fallback, except here the impact is scoped per-message (a specific bridged transfer) rather than globally freezing the whole contract — the value is nonetheless permanently and unrecoverably lost from circulation (burned supply that is never remin­ted, or escrow that is never released), which is a valid "permanent freezing of funds" outcome per the report's own class.

### Impact Explanation
Any account initiating a `send()` on `HyperFungibleToken`/`WrappedHyperFungibleToken` (an unprivileged, permissionless "token bridger" action) can select a beneficiary and timeout. If the destination-side underlying asset can deny-list an address (a realistic assumption acknowledged industry-wide for USDC-class stablecoins, exactly as called out in the original report) and the `to` address becomes/ is blacklisted, and `timeout` is `0`, the transferred value is burned on the source chain and can never be minted/unlocked on the destination, nor ever refunded via timeout. This is a permanent, unrecoverable loss of user funds triggered by an ordinary bridging transaction — no admin or governance action, and no privileged actor, is required to reach this state.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either (a) a legitimate user's recipient address to later become blacklisted on the underlying asset while `timeout=0` was used (plausible for "send with no expiry" UX defaults), or (b) an attacker deliberately griefing a victim by bridging tokens to a known-blacklisted or unconditionally-reverting address they control, burning the attacker's own principal purely to corrupt cross-chain accounting/liveness for that transfer. The `timeout=0` "no-expiry" choice is fully user-controlled and not blocked by the contracts, so the precondition is trivially satisfiable by any caller.

### Recommendation
- Do not let the destination push directly determine settlement finality. Wrap the payout (`_mint`/`safeTransfer` to `beneficiary`) in a `try/catch` inside `onAccept`; on failure, credit the amount to a claimable mapping (`unclaimedBalances[beneficiary] += amount`) instead of reverting the whole callback, and let the beneficiary (or anyone, permissionlessly) pull it later via a `claim()` function.
- Alternatively/additionally, enforce a maximum timeout ceiling and disallow `timeout == 0` (i.e., reject or clamp to a governance-configured max), guaranteeing that every dispatched transfer has a bounded time after which `onPostRequestTimeout` can refund the sender regardless of destination-side delivery failures.
- Ensure `EvmHost.dispatchIncoming`'s "retry" semantics are paired with a hard upper bound (the timeout) so that a permanently-failing callback is guaranteed to eventually resolve via timeout rather than being retryable forever with no expiry.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` backed by a USDC-like blacklist-capable ERC20, and its peer `HyperFungibleToken` on a remote chain.
2. On the remote chain, call `send()` with `SendParams.to = <address later blacklisted on the home-chain USDC>` and `SendParams.timeout = 0`. This burns the sender's tokens per `HyperFungibleToken.send` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:264-282`) and dispatches a `PostRequest` whose `timeoutTimestamp` is set to `0` per `EvmHost.dispatch` (`evm/src/core/EvmHost.sol:933-944`).
3. Have USDC's issuer blacklist the `to` address (simulate with a mock ERC20 whose `transfer` reverts for that address) before the message is relayed.
4. Relay the message: `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `WrappedHyperFungibleToken.onAccept` → `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` reverts (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:322-324`); `dispatchIncoming` catches this, deletes the receipt, and silently returns (`evm/src/core/EvmHost.sol:809-816`) — the message is never marked delivered.
5. Attempt `HandlerV2.handlePostRequestTimeouts` for this request: it reverts with `MessageNotTimedOut()` forever because `request.timeout()` (derived from `timeoutTimestamp == 0`) never satisfies `request.timeout() <= state.timestamp` (`evm/src/core/HandlerV2.sol:267-284`).
6. The burned tokens are permanently unrecoverable: `onAccept` can never succeed (destination is blacklisted) and the timeout path can never trigger (timeout disabled), demonstrating permanent freezing of the bridged value.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
