### Title
Shop-domain identity in webhook processing is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the request, but the HMAC signable string only covers the raw body — the `shop` identity that the handler acts on is taken from an unauthenticated header field. This breaks the intended binding `hmac_verified_bytes == identity_used_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value that is later handed to the app's webhook handler is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, with no cross-check against anything covered by the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it against the `hmac` field, again never touching the `shop` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request (including tenant identity) is trustworthy, then forwards `request.shop` straight into `WebhookMetadata` for the handler: [4](#0-3) 

`WebhookMetadata.shop` is documented and expected to be the authoritative tenant identifier that apps use to route/act on data (e.g., to look up the shop's session/access token, or to decide which merchant's records to mutate): [5](#0-4) [6](#0-5) 

Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app (it is not shop-specific), any two tenants of the same app produce HMACs computed with the identical secret over the body only. This means the `shop` header is never bound to the HMAC-verified bytes at all — it is fully attacker-controllable metadata riding alongside an otherwise-valid signature, exactly the class of bug described in the report ("a field acted on but not covered by the HMAC"): the router in the external report acted on `ASDUSDC` without the necessary approval binding it to `crocSwapAddress`; here the registry acts on `shop` without any binding to the HMAC that is supposed to authenticate the whole request.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook-processing code path: `Registry.process` reports "Invalid webhook HMAC" is false (i.e., accepts the request as authentic) purely based on body/secret matching, while handing the handler a `shop` value that was never validated as belonging to that body. Any caller able to produce one valid `(raw_body, hmac)` pair for the app (e.g., by replaying/observing a legitimately delivered webhook for their own shop, since the app-level secret is identical for every shop using the app) can resubmit that same body with an arbitrary `shop` header. Since `WebhookMetadata#shop` is the field consuming applications are told to trust to identify the tenant, this can lead to cross-tenant data being attributed to, or acted on behalf of, a different shop — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only one previously-observed valid webhook payload+signature pair for the same app (any shop installing the app can generate this legitimately, and app-level webhook secrets are not shop-scoped), plus the ability to send an HTTP POST to the app's public webhook endpoint with a modified `shop` header, both of which are available to an unprivileged internet user/merchant with no elevated access, no leaked credentials, and no TLS interception. The library itself performs no verification tying `shop` to the signed bytes, so the weakness is fully attributable to this gem's `Webhooks::Request`/`HmacValidator`/`Registry` code, not to host-application misuse.

### Recommendation
Include the tenant-identifying fields (at minimum `shop`, and ideally `topic`/`webhook_id`/`api_version`) in the HMAC-signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the `shop` header to the verified payload before it is exposed via `WebhookMetadata`, so that a valid signature can only be produced for the specific `(shop, body)` pair Shopify actually sent.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both share the same app `api_secret_key`).
2. Shopify sends a legitimate webhook to the app for `shop-a.myshopify.com`; an unprivileged party who can observe/replay this request (e.g., the merchant of shop-a, who legitimately receives copies of their own webhook traffic through their own infrastructure) captures `raw_body` and its `x-shopify-hmac-sha256` value.
3. That party resends the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at `raw_body`; `HmacValidator.validate` recomputes the same valid HMAC (since it's a function of `raw_body` and the shared `api_secret_key`) and returns `true`, per [7](#0-6) .
5. `Registry.process` forwards `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` to the app's handler, which now processes shop-a's webhook body under shop-b's identity — a cross-tenant identity binding failure entirely inside this gem's verification logic.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
