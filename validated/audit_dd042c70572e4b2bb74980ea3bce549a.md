### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used to route and process incoming webhooks from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature only covers the raw request body. This breaks the binding `shop-used-for-processing == shop-that-was-actually-signed`, allowing an attacker who controls any shop installed on the same app to replay a genuine webhook body under a forged shop domain.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then dispatches the handler using `request.shop` taken from that unverified header: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the body) and the app's shared `client_secret`: [4](#0-3) 

Because the `client_secret`/HMAC key is shared by the app across *all* shops that install it, and the shop-domain header is not part of the signed payload, any party that can obtain one genuine, validly-signed webhook (e.g., by installing the same public app on their own store and triggering an event) can replay that exact body to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header. The equality that should hold — `shop claimed by request.shop == shop that Shopify actually signed the payload for` — is broken, since the header is never included in `to_signable_string`.

### Impact Explanation
If the host application uses `request.shop` (as returned by `WebhookMetadata.shop`) to select which tenant's data or session to act on — a documented and expected usage pattern for this gem — an attacker can cause the webhook body (fully attacker-controlled if they run the sending shop) to be processed as belonging to an arbitrary victim shop of the same app. This is a cross-tenant confusion/spoofing vector: the app could write attacker-supplied data into another merchant's records, or trigger merchant-scoped, mandatory topics (e.g., `customers/data_request`, `customers/redact`, `shop/redact`) against the wrong tenant, since none of these identity-critical headers are covered by the signature.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own (attacker-controlled) shop — a normal, unprivileged action for public Shopify apps — can obtain a genuinely HMAC-signed webhook body and replay it with a forged shop-domain header. No access to `client_secret`, access tokens, or any privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload, or independently verify that the shop asserted in the header matches a shop the app actually installed/expects for that specific signed body, before using `request.shop` for any tenant-scoped action. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted for tenant selection without additional binding.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates an order) causing Shopify to POST a webhook to the app, signed with the app's shared `client_secret`:
   - `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `raw_body: {...attacker-controlled JSON...}`
3. Attacker captures this exact request and resends it to the same webhook endpoint, changing only:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` — unchanged — so validation succeeds.
5. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
