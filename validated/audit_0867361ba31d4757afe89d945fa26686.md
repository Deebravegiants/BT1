### Title
Unauthenticated pipeline-run resume endpoint allows any actor to inject task results/errors into another party's job run - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Resume` is mounted with no authentication at all (`unauthedv2.PATCH("/resume/:runID", prc.Resume)`), and forwards attacker-controlled JSON directly into `App.ResumeJobV2`, which finalizes a pending pipeline task (e.g., an external adapter/bridge callback) using only a UUID `runID` supplied in the URL.

### Finding Description
The route is registered outside the authenticated `authv2` group: [1](#0-0) . The handler itself performs no session/API-key/role check and simply decodes the request body into a `pipeline.ResumeRequest` and calls `ResumeJobV2` with the caller-supplied `taskID`: [2](#0-1) . This mirrors the `defaulted()` pattern in the Cooler report — a state-changing action that should only be triggerable by the intended party (the bridge/EA that started the task) is instead callable by "anybody," gated only by knowledge of the `runID` UUID rather than any credential.

### Impact Explanation
Whether this is truly exploitable depends on whether `runID`s are treated as bearer-token-like secrets (unguessable, single-use, tied to a specific outstanding bridge/EA callback) or are otherwise discoverable (e.g., leaked via the authenticated `GET /jobs/:ID/runs/:runID` endpoint, logs, or client-side artifacts). If an attacker can obtain or predict a pending `runID` for a run they are not party to, they can inject an arbitrary `ResumeRequest` result/error, resuming or corrupting someone else's pipeline run — analogous to the unauthorized `defaulted()` call transferring another party's loan collateral. I could not fully verify from the available index how `runID`s are generated, exposed to legitimate external adapters, or whether they are single-use/expiring, which materially affects severity.

### Likelihood Explanation
This design (unauthenticated resume by UUID) appears intentional — the `audit.UnauthedRunResumed` event name explicitly acknowledges it is unauthenticated — suggesting the security model relies entirely on `runID` unguessability as a bearer-secret rather than a session-token. Given I could not confirm UUID generation/exposure guarantees or find any rate-limiting/expiry protecting this endpoint beyond the general rate limiter, likelihood is uncertain and should be validated further.

### Recommendation
Verify that `runID` values used for resume are cryptographically random, single-use, bound to the specific pending task, expire promptly, and are never exposed to third parties. If any of these guarantees do not hold, add authentication/authorization (e.g., require the resume request to include a secret bound to the specific pending task instead of relying on the run UUID alone), and audit for `runID` leakage in logs or authenticated API responses.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
