### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity that is handed to the host application's webhook handler directly from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` validates only covers the raw request body. This breaks the equality that should hold for a verified webhook: `hmac_verified(body) == true` should imply `shop == the tenant the HMAC was computed for`. Because the header is outside the signed payload, any actor who possesses one genuine `(raw_body, hmac)` pair for their own shop (which every installed merchant legitimately receives from Shopify) can resend that exact pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value. The gem's HMAC check still passes, and `ShopifyAPI::Webhooks::Registry.process` forwards the attacker-chosen `shop` to the application handler as if it were authenticated.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; it does not include the `shop`, `topic`, or `webhook_id` header values. `Request#shop` is a plain header read with no binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the whole request, then forwards the header-derived `request.shop` to the handler as the trusted tenant identity: [4](#0-3) 

Because `shop` is never part of `to_signable_string`, the binding "HMAC valid ⇒ shop is authentic" does not hold. The equality that should be enforced is `hmac_signable_payload ⊇ {body, shop}`, but the implementation only enforces `hmac_signable_payload = {body}`.

### Impact Explanation
Any merchant who has installed the app receives genuine webhook deliveries containing a real `(raw_body, x-shopify-hmac-sha256)` pair addressed to their own shop. That merchant is an unprivileged actor with respect to every other tenant of the app. By replaying that exact body+HMAC to the app's webhook endpoint with a different `x-shopify-shop-domain` header, they cause `ShopifyAPI::Webhooks::Registry.process` to pass HMAC validation and invoke the application's handler with `WebhookMetadata#shop` set to an arbitrary/victim shop of the attacker's choosing. Any handler logic that trusts `data.shop` to scope a write, a lookup, or a state transition (billing status, uninstall/reinstall bookkeeping, plan changes, subscription state, GDPR/redact processing, etc.) can be driven with attacker-controlled body content while being falsely attributed to another tenant — a cross-tenant identity confusion rooted entirely in this gem's request-parsing code, not in host-application misuse of an undocumented API. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app author who follows the shipped API and trusts `WebhookMetadata#shop`/`Request#shop` once `HmacValidator.validate` returns true — this is the exact contract the gem documents and enforces internally (`Registry.process` raises `InvalidWebhookError` only when the HMAC check fails, implying "success" should mean the entire request, including the shop, is trustworthy). No secret, token, or privileged access is required — only a legitimate merchant installation of the target app (an unprivileged-from-the-app's-perspective actor) and the ability to send one HTTP POST with modified headers but the original captured body/HMAC.

### Recommendation
Bind the shop (and ideally the topic/webhook-id) to the signed payload before trusting it, e.g., include the `shop-domain` header value as part of the string that is HMAC-verified, or require the caller to separately verify that `request.shop` matches the shop that owns the corresponding access token/session before dispatching to the handler. Concretely, `Request#to_signable_string` should incorporate the authenticated shop context (or the registry should re-derive/validate `shop` from a source that is itself covered by the signature) so that `HmacValidator.validate` cannot succeed while the shop identity has been swapped.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC-SHA256 of `B` under the app's `client_secret`).
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. The application calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (`= B`) and it matches `H`, so validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim.myshopify.com"`, and invokes the application's handler as if Shopify itself had certified that this event belongs to `victim.myshopify.com`, even though the payload was attacker-controlled data originally destined for the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
