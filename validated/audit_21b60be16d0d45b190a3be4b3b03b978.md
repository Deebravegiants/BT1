Audit Report

## Title
`ValidateGetSecretsRequest` wrongfully rejects a `GetSecrets` batch that is exactly at `MaxBatchSize` - (File: `core/capabilities/vault/validator.go`)

## Summary
`RequestValidator.ValidateGetSecretsRequest` compares `len(request.Requests) >= vaulttypes.MaxBatchSize` instead of `>`, so a legitimate batch of exactly `MaxBatchSize` (10) `GetSecret` requests is rejected with "request batch size exceeds maximum of %d" even though it does not exceed the documented maximum. All other batch/length limiters in the same package (`MaxRequestBatchSizeLimiter.Check`, `MaxCiphertextLengthLimiter.Check`, etc.) correctly accept values exactly at the bound via `n > bound` semantics, making this comparison an inconsistent off-by-one outlier.

## Finding Description [1](#0-0)  shows the buggy check: `if len(request.Requests) >= vaulttypes.MaxBatchSize { return fmt.Errorf("request batch size exceeds maximum of %d", vaulttypes.MaxBatchSize) }`, where `vaulttypes.MaxBatchSize = 10` is defined at [2](#0-1) . By contrast, `validateWriteRequest` uses `r.MaxRequestBatchSizeLimiter.Check(ctx, len(encryptedSecrets))` at [3](#0-2) , which relies on strict-greater-than bound semantics that accept values exactly at the limit. `ValidateGetSecretsRequest` is the only batch-size check that manually uses `>=`, introducing the off-by-one rejection for exactly-at-limit requests. This function is called for the `vault.secrets.get`-equivalent `GetSecrets` capability method, reachable by any workflow/gateway caller invoking `Capability.Execute` without requiring elevated privileges.

## Impact Explanation
This is a functional/availability defect: any unprivileged caller submitting a batch of exactly `MaxBatchSize` (10) secret-get requests — a legitimate, in-bound size — is deterministically denied service. It does not cause fund loss, authentication bypass, or secret disclosure, but is a genuine correctness bug that degrades usability/availability of the vault capability's `GetSecrets` method for any client batching up to the documented maximum.

## Likelihood Explanation
High and deterministic: any caller batching exactly `MaxBatchSize` items will always hit this rejection with no special conditions, timing, or attacker capability required beyond normal use of the `GetSecrets` method.

## Recommendation
Change the comparison to `if len(request.Requests) > vaulttypes.MaxBatchSize` to match the semantics used by `MaxRequestBatchSizeLimiter.Check` and the rest of the validators, or refactor `ValidateGetSecretsRequest` to reuse that limiter for consistency.

## Proof of Concept
Construct a `vaultcommon.GetSecretsRequest` with exactly `vaulttypes.MaxBatchSize` (10) `SecretRequest` entries and call `Capability.Execute` with `Method: vault.MethodGetSecrets`; the request is rejected with "request batch size exceeds maximum of 10" despite not exceeding the maximum. This is already demonstrated by the existing test [4](#0-3) , which builds `reqs := make([]*vault.SecretRequest, vaulttypes.MaxBatchSize)` and asserts the batch is rejected with that exact error message.
