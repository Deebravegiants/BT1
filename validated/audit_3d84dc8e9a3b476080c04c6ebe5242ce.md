### Title
Instruction-data cost truncation lets attackers underpay compute-cost accounting by splitting large instruction payloads across many small transactions - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::get_instructions_data_cost` computes the instruction-data component of a transaction's cost using truncating integer division: `transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)`. Because `INSTRUCTION_DATA_BYTES_COST = 140 / COMPUTE_UNIT_TO_US_RATIO = 4` (bytes per compute unit) and the division rounds toward zero, every transaction loses up to `INSTRUCTION_DATA_BYTES_COST - 1` (3) bytes worth of cost credit. This is structurally identical to the reported Eggs.sol bug: splitting one large operation into many small ones systematically loses more to truncation than doing it as a single large operation, letting the actor pay/attribute less in aggregate. ### Finding Description
`get_instructions_data_cost` is used both when estimating a transaction's cost (`CostModel::calculate_cost` / `CostModel::estimate_cost`) and when computing the actually-executed cost (`CostModel::calculate_cost_for_executed_transaction`), and its output (`data_bytes_cost: u16`) is summed into `TransactionCost` alongside signature, write-lock, execution, and loaded-accounts-data-size costs. [3](#0-2) [1](#0-0) 

This aggregated `TransactionCost::sum()` feeds directly into the cost tracker / block-cost-limit accounting (`check_block_cost_limits`, `cost_tracker.block_cost()`), and into per-account write-lock cost limits, which gate how much compute a block or writable account is allowed to consume per slot. [4](#0-3) 

Because the division truncates per-transaction, an actor who wants to push a given total volume of instruction data through the network while minimizing its contribution to the cost-tracker accounting can split it into many transactions each just under a multiple of 4 bytes, discarding the remainder each time, rather than submitting one transaction with the same aggregate data length. E.g., 1,000 transactions each with 3 bytes of instruction data contribute `1000 * (3/4) = 0` to accounted cost, while one transaction with 3,000 bytes contributes `3000/4 = 750`. This under-accounts the true instruction-data cost of processing that many transactions/signatures/write-locks against the block cost limit, in the same way the Eggs interest formula under-accounts interest when loans are split into many short-duration segments.

### Impact Explanation
This causes materially underpriced execution: the cost model is the enforcement mechanism for Agave's block cost limits (`MAX_BLOCK_UNITS`) and per-writable-account limits (`MAX_WRITABLE_ACCOUNT_UNITS`), which exist specifically to bound the resources (bandwidth/verification/storage overhead) a block can consume. Systematic truncation loss when data is fragmented into many small transactions allows more real instruction-data bytes to be pushed through a block than the cost model believes it is accounting for, degrading the accuracy of the resource-accounting invariant the cost model is meant to guarantee. However, the magnitude of the loss is small per-transaction (0–3 bytes ≈ 0 compute units at this ratio, since `INSTRUCTION_DATA_BYTES_COST` computed from `140/30 = 4` truncated integer division itself, and the cost per instruction byte is only fractional compute units), and this cost component is a minor contributor next to signature/write-lock/execution costs, unlike lamport-denominated fees in the original report.

### Likelihood Explanation
Any unprivileged user can trivially construct such transactions client-side (choosing instruction data lengths); no special permissions or validator-side changes are required, and reaching this path only requires normal transaction submission and processing, which happens continuously in `banking_stage`/SVM cost estimation.

### Recommendation
Accumulate raw instruction-data bytes at the block/account level (or use a fixed-point/ceiling scheme, e.g., `div_ceil`, similar to the rounding-up scheme already used for `get_prioritization_fee`) rather than truncating per-transaction, so fragmentation into many small transactions cannot systematically reduce the aggregate accounted cost relative to one large transaction. Compare with `get_prioritization_fee` in `compute-budget/src/compute_budget_limits.rs`, which explicitly rounds up (`saturating_add(MICRO_LAMPORTS_PER_LAMPORT - 1)`) to avoid under-crediting the fee. [5](#0-4) 

### Proof of Concept
Given `INSTRUCTION_DATA_BYTES_COST = 4`:
- One transaction with 4,000 bytes of instruction data: `data_bytes_cost = 4000 / 4 = 1000`.
- 1,000 transactions each carrying 3 bytes of "extra" instruction data (just under the 4-byte boundary), same total ~3,000 bytes of data plus base instructions: each contributes `3 / 4 = 0` to `data_bytes_cost`, for an aggregate accounted cost of `0` versus the `750` that a single combined transaction with 3,000 bytes would have contributed.
- This can be verified directly against `CostModel::get_instructions_data_cost` and the existing unit tests exercising it (e.g., `test_cost_model_calculate_cost_all_default`, `test_vote_transaction_cost`), which confirm the truncating-division formula but do not test or bound the cross-transaction aggregate loss from fragmentation. fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}
