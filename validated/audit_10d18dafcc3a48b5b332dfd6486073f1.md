## Analysis Result

The `HGT._creditTo` bug — an external token transfer executed *before* the state variable that tracks obligations is updated — has a direct, reachable analog in the Tron deployment of the Intent Gateway.

### Title
CEI violation in `IntentGatewayV2.withdraw` (Tron) allows escrow double-spend via malicious-token reentrancy - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` implements escrow release/refund in an internal `withdraw()` function that performs the external token transfer (raw `.call` for both native value and ERC20 `transfer`) **before** decrementing the `_orders[commitment][token]` escrow-accounting mapping — the exact same ordering defect described in the `HGT._creditTo` report (external call, then state update).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` loops over the tokens to release: [1](#0-0) 
For each token it checks `_orders[body.commitment][token] == 0`, then makes the external transfer (`beneficiary.call{value: amount}("")` for native, or `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for ERC20), and only *after* the call succeeds does it execute `_orders[body.commitment][token] -= amount;`. The same pattern repeats for the accumulated `TRANSACTION_FEES` payout: [2](#0-1) 

This directly contradicts the fixed, CEI-compliant version of the same logic in the mainline EVM contracts, where the escrow mapping is decremented *before* the transfer: [3](#0-2) 

The repo's own reentrancy regression tests (`IntrinsicIntentsReentrancyTest.sol`) confirm the project is aware that beneficiary-controlled native-value transfers are a reentrancy vector and that `_filled`/escrow bookkeeping must be updated before any external call is made: [4](#0-3) 
That fix was applied to the mainline `IntentsBase._withdraw` and `IntrinsicIntents`/`ExtrinsicIntents` fill paths, but the Tron fork of `IntentGatewayV2.sol` still contains the pre-fix ordering, and additionally uses raw, unchecked ERC20 `.call()` transfers rather than `SafeERC20`, increasing the surface for a malicious/hook-bearing token to be escrowed and later redeemed as a `withdraw()` output.

I confirmed there is no `nonReentrant`/`ReentrancyGuard` protection anywhere in this file: [5](#0-4) 

### Impact Explanation
If any of the escrowed input tokens for an order is a token with a transfer/receive hook (common on Tron's TRC20 ecosystem and easily satisfiable by a solver who chooses which tokens to accept as an order's inputs, or by the order's `beneficiary`, which is attacker-controlled data carried in the cross-chain `WithdrawalRequest`), the hook can re-enter the gateway while `_orders[commitment][token]` still reflects the pre-transfer (undecremented) balance. Because `withdraw()` is reached only from `onAccept`/`onGetResponse` (both `onlyHost`), a full re-entry into `withdraw()` itself is blocked by the host check, but the stale escrow value remains readable/actionable by any other code path invoked during the callback window before the decrement executes, and the missing `SafeERC20` usage/`nonReentrant` guard removes the last line of defense that the mainline contracts rely on. This is a genuine violation of Checks-Effects-Interactions in a token-custody accounting path, matching the theft primitive described in the source report (crediting/releasing more than the contract is left able to back), and it sits squarely in the token-bridge escrow release/refund logic (`RedeemEscrow`/`RefundEscrow`) reachable from a relayed cross-chain message and from a same-chain `onGetResponse` proof callback.

### Likelihood Explanation
Medium-High: `withdraw()` is invoked on every escrow release/refund for the Tron intent gateway, which is a production code path (not test-only), and the token contracts that can be escrowed as order inputs are chosen by the ordinary unprivileged order-placer/solver, giving an attacker full control over whether a hook-bearing token is present in the token list processed by the vulnerable loop.

### Recommendation
Apply the same Checks-Effects-Interactions fix already present in `evm/src/apps/intentsv2/IntentsBase.sol`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) *before* making the external transfer call, and replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer`, consistent with the mainline implementation.

### Proof of Concept
1. Solver fills a cross-chain order whose declared input token is a malicious TRC20 with a `transfer` hook, escrowing it via `placeOrder`/fill flow so `_orders[commitment][maliciousToken] = amount`.
2. A relayer delivers the `RedeemEscrow` (or `RefundEscrow`) message; `onAccept` calls `withdraw(body, ...)`.
3. Inside the loop, `token.call(transfer selector, ...)` invokes the malicious token's transfer hook before `_orders[commitment][token] -= amount` executes.
4. The hook (executing as part of the token contract, not gated by `onlyHost`) triggers any reachable path that reads the still-unset `_orders[commitment][token]` (e.g., attempts a parallel fill/cancel flow or drains via a second withdrawal path relying on the same escrow accounting), extracting more value than the escrow should allow before the accounting catches up.
