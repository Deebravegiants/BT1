### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain` Header Not Covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the JSON body alone. The `shop` value delivered to the app's webhook handler is read straight from the `x-shopify-shop-domain` header, which is never included in the signed bytes.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which delegates to `Request#to_signable_string`: [1](#0-0) [2](#0-1) 

The HMAC covers `@raw_body` only: [3](#0-2) [4](#0-3) 

But the `shop` value passed on to the app's handler is pulled from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed payload: [5](#0-4) [2](#0-1) 

This breaks the identity binding: `hmac-authenticated bytes (raw_body signed with the app's shared api_secret_key)` ≠ `shop value the handler trusts (arbitrary, attacker-controlled header)`. The same `api_secret_key` is shared by an app across every merchant install, and any merchant that installs the app can legitimately receive real, validly-signed `(raw_body, hmac)` pairs for topics containing merchant-supplied content (e.g. `orders/create`, `products/update`, `app/uninstalled`). Because the shop identity is carried out-of-band in an unsigned header, a malicious/attacker-controlled tenant can capture one of their own legitimately-signed webhook deliveries and replay it directly to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `Utils::HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim's shop, body, and topic: [6](#0-5) 

Any handler logic keyed off `data.shop` (updating per-shop state, writing to a per-shop record, triggering per-shop side effects, marking a shop as uninstalled, etc.) will now execute under the wrong tenant's identity, entirely from an unprivileged/attacker-controlled installation of the app.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who only controls their own (or any) shop's installation can forge a webhook that the library authenticates as belonging to a different merchant, letting them inject attacker-controlled data/events into another tenant's processing path (Critical - cross-tenant access) without ever needing that tenant's or the app's `api_secret_key`/access token.

### Likelihood Explanation
Requires only that the attacker operate one legitimate install of the target app (a normal, unprivileged merchant relationship) and be able to send arbitrary POST requests with custom headers to the app's public webhook endpoint (`Registry.process`/`Request.new` accept caller-supplied headers as-is) — no secrets, tokens, or elevated access needed.

### Recommendation
Bind the shop identity into the signed material the library trusts, or explicitly document/require the host app to verify shop identity against its own session/install records before trusting `WebhookMetadata#shop`. At minimum, `Request#to_signable_string` (or a parallel check in `Registry.process`) should tie the validated HMAC to the specific shop header value it is being used to authorize, e.g. by refusing to trust `shop` unless it matches a shop the host app has separately confirmed is the origin, rather than exposing an unauthenticated `shop` accessor that callers naturally treat as trusted output of a "verified" webhook.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (legitimate, unprivileged action).
2. Attacker triggers/captures a real webhook delivery, e.g. `app/uninstalled`, and records the exact `raw_body` and the valid `x-shopify-hmac-sha256` value Shopify computed with the app's shared `api_secret_key`.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (via `Request#to_signable_string` returning only `@raw_body`) succeeds since the body/HMAC pair is untouched.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so any per-shop logic (e.g., marking `victim-shop` uninstalled, writing to victim's records) executes for the wrong tenant, confirmed by [2](#0-1)  and [7](#0-6) .
