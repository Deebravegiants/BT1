Based on my investigation, I've confirmed the vulnerability. The Shopify webhook HMAC is computed over the raw body only (`Request#to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `api-version`, and `webhook-id` headers are completely excluded from the signature yet are trusted directly by `Registry.process` and passed into the handler.

### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate(request)` verifies solely that the body bytes match a valid HMAC computed with the app's shared `api_secret_key`. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read directly from attacker-controlled HTTP headers and are never included in the signed material, yet `Registry.process` forwards them unmodified into `WebhookMetadata` that host applications use to attribute the event to a specific tenant.

### Finding Description [1](#0-0) 
`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body` — no header is part of the signed content. `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers via `shopify_header`, with no cross-check against the signature. [2](#0-1) 
`Registry.process` validates only `Utils::HmacValidator.validate(request)` (body-vs-secret), then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and dispatches it to the registered handler.

Because the `api_secret_key` is a single shared app secret used for **every shop** that installs the app (not a per-shop key), any entity that can obtain one valid `(raw_body, hmac)` pair signed with the app's secret — for example, a malicious merchant who installs the app on their own store and receives genuine webhook deliveries for their own shop — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with an arbitrary value. `HmacValidator.validate` will still return `true` because it only checks the body against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event originated from a different shop.

This breaks the intended binding: `hmac_signing_context (shop, topic, body) == request.shop header used by handler`. In the actual implementation, the equality only holds for `body`, while `shop` (the tenant identity) is asserted purely from an unauthenticated header.

### Impact Explanation
This is a cross-tenant boundary violation (Critical): a malicious app-installer can forge webhook events "from" any other shop that also uses the app, causing the host application's webhook handler to process attacker-supplied data (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact`) under a victim shop's identity. Depending on how the host app keys billing, GDPR redaction, order processing, or session/data lookups by `data.shop`, this can lead to data corruption, unauthorized triggering of privileged per-tenant workflows, or injection of forged data into another merchant's records — all without ever needing that merchant's credentials.

### Likelihood Explanation
High for any app that has at least one non-adversarial installer alongside a malicious one (the common multi-tenant SaaS app scenario). The attacker only needs their own legitimate app installation to obtain a validly-signed `(body, hmac)` pair; no access to `api_secret_key`, access tokens, or the victim's environment is required. The attack is a simple HTTP replay with one header changed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified against the HMAC, or independently verify that the `shop-domain` header corresponds to a shop with an active, expected session/subscription for that specific `webhook_id`/topic before dispatching to the handler. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as a tenant identity without additional verification (e.g., matching against a known active installation).

### Proof of Concept
1. App installs a webhook subscription and shares one `api_secret_key` across all merchant installations (standard Shopify app model).
2. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., updates a product), receiving a genuine POST from Shopify:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: products/update`, body `B`.
3. Attacker replays the exact same request to the app's public webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks body `B` against the shared secret [3](#0-2) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", body: B, ...)` [4](#0-3) , causing the host app to process attacker-controlled data as if it came from the victim shop.
