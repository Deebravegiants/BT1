## Analog vulnerability confirmed

### Title
Stale config snapshot in `MasterPlan::run` allows backend-issued authorization revocations (self-serve mode / operator-QR expiry) to be silently ignored for the life of the process - ([File: src/plans/mod.rs])

### Summary
`orb-core` mirrors the zAuction class of bug: a security-relevant setting that the backend expects to take *immediate* effect is instead cached once and kept "active" in parallel with the fresh value used elsewhere, exactly like the old `zAuction` contract continuing to accept bids after the accountant was pointed at a new one.

### Finding Description
`MasterPlan::run` destructures the shared, mutex-guarded `Config` **once**, before entering its `loop`, and reuses those values (`self_serve`, `self_serve_button`, `operator_qr_expiration_time`, relay shutdown timings) for every subsequent iteration of that loop without ever re-reading `orb.config`: [1](#0-0) 

That loop can run for the entire lifetime of the process (it only exits on `oneshot` or biometric-input mode), repeatedly calling `scan_initial_qr_codes` and `idle_wait_for_signup_request` with this frozen snapshot: [2](#0-1) 

Meanwhile, the exact same fields are re-fetched **fresh** from the shared `orb.config` mutex inside `do_signup` (called every iteration) and inside independent helper functions such as `verify_operator_qr_code`, `check_signup_conditions`, and `proceed_with_biometric_capture`: [3](#0-2) [4](#0-3) 

Because `orb.config` is a shared `Arc<Mutex<Config>>` that is updated asynchronously in the background (confirmed by the config-download/store logic in `src/config.rs` and its usage in `src/brokers/observer.rs`), a backend admin can push a config update intending it to take effect immediately, exactly as `zAuctionAccountant.SetZauction()` intended immediate effect for the referenced auction contract: [5](#0-4) 

But `MasterPlan::run`'s top-level snapshot never observes that update, so two different "versions" of the same policy (`self_serve` enabled/disabled, or a shorter/longer `operator_qr_expiration_time`) are simultaneously honored within the same process: the stale value drives QR-scan/idle logic while the fresh value drives `do_signup` internals — the same "two contracts active in parallel" condition described in the report.

### Impact Explanation
If an operator backend admin disables `self_serve` (e.g., because unattended/self-serve signups are being abused) or shortens `operator_qr_expiration_time` to immediately revoke a compromised operator QR window, the running Orb continues to use the old, more permissive values for `scan_initial_qr_codes`/`idle_wait_for_signup_request` gating for as long as the process keeps looping. This can let signups keep starting under a policy the backend explicitly tried to revoke, producing signups that are effectively unauthorized relative to the operator's intended real-time control, i.e. a misattributed/unintended-authorization class of impact analogous to the accepted report.

### Likelihood Explanation
This requires no attacker action beyond normal backend-config-update workflows already relied upon for real-time control (disabling self-serve, shrinking QR expiry). Any legitimate admin action to immediately restrict signup conditions is silently delayed until the Orb process restarts, which is a realistic and easily triggered operational scenario, not a contrived edge case.

### Recommendation
Re-read the relevant `Config` fields (`self_serve`, `self_serve_button`, `operator_qr_expiration_time`, and other security-relevant toggles) at the top of each loop iteration in `MasterPlan::run` instead of snapshotting them once outside the loop, so that every part of the signup flow — idle scanning, QR validation, and `do_signup` — observes the same, current configuration. Alternatively, centralize config reads through a single accessor invoked fresh at each decision point to avoid divergent "old vs. new" policy states within one running process.

### Proof of Concept
Not independently verifiable from static analysis of the index alone — the divergence is a logical/config-timing issue reproducible only by: (1) starting `orb-core` with `self_serve=true`/a long `operator_qr_expiration_time`, (2) letting `MasterPlan::run`'s loop begin, (3) pushing a backend config update disabling `self_serve` or shortening the QR expiry, and (4) observing that `scan_initial_qr_codes`/`idle_wait_for_signup_request` keep operating on the old values while `do_signup` (and its sub-calls) use the newly fetched value. I could not fully trace the background config-refresh cadence in `src/brokers/observer.rs` within the available search budget; a Devin session with full file access would be needed to confirm the exact refresh interval and verify runtime behavior end-to-end.

    /// Downloads the latest configuration from the backend, updates the shared
    /// configuration object, and stores the updated configuration to the file
    /// system.
    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
