`PoaBridge.describeWithdrawal` misattributes withdrawal status/txHash across same-asset batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` looks up withdrawal status purely by `assetId`, ignoring `WithdrawalIdentifier.index`. When a single NEAR intent transaction contains two `WithdrawalParams` for the same `assetId` (e.g. two BTC withdrawals to different addresses), both `WithdrawalIdentifier` queries resolve to the same underlying record from the POA bridge API, so both report identical `{status:'completed', txHash}` even though they represent two distinct on-chain payouts.

### Finding Description
The broken equality: for `i in {0,1}`, `(status_i, txHash_i)` returned by `watchWithdrawal`/`describeWithdrawal` should equal the true on-chain outcome of withdrawal `i` specifically. Instead both resolve to the same record.

Code path:
- `withdrawal-watcher.ts` `createWithdrawalIdentifiers` assigns per-bridge sequential `index` (0, 1, ...) to each `WithdrawalParams` entry routed to `PoaBridge`, via `bridge.createWithdrawalIdentifier`, and `watchWithdrawal` calls `bridge.describeWithdrawal({...wid, ...})` independently for each identifier [1](#0-0) [2](#0-1) 
- `PoaBridge.describeWithdrawal` calls `getWithdrawalStatusWithRetry({tx.hash})` — note this call only depends on `args.tx.hash` (the shared NEAR intent tx), not on `args.index` or `destinationAddress` — then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [3](#0-2) 
- `findMatchingWithdrawal` matches solely by `` `nep141:${w.data.near_token_id}` === assetId ``, with an explicit code comment acknowledging: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported"* [4](#0-3) 

Root cause: since `Array.prototype.find` always returns the first matching element, both `index:0` and `index:1` queries deterministically return the **same** array element (the first COMPLETED record for that assetId) from the API response, regardless of which of the two real on-chain payouts it actually corresponds to.

Attacker input: an ordinary user/integrator constructs a NEAR intent with two `ft_withdraw` intents for `nep141:btc.omft.near` (two different `destinationAddress`, `feeInclusive:false` for both), submits it as one transaction. Nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIntents()` blocks two `WithdrawalParams` sharing the same `assetId` in a batch — these all operate per-entry with no batch-level duplicate-asset check. `withdrawalParamsInvariant`/similar checks in other bridges do not apply here.

Existing guards: `validateAddress`, `compareAddresses`, `getUnderlyingFee`, `assert` sanity checks in `createWithdrawalIntents` do not check for duplicate `assetId` across the batch, and `findMatchingWithdrawal` has no `index`-aware disambiguation (no sorting-by-amount fallback described in the comment is implemented). Nothing else in the reachable call path (`sdk.waitForWithdrawalCompletion`, `sdk.createWithdrawalCompletionPromises`, `watchWithdrawal`) corrects for this.

### Impact Explanation
An integrator that credits/clears an internal ledger keyed by withdrawal index will receive `{status:'completed', txHash: X}` for both `index:0` and `index:1`, where `X` is the destination tx hash of only one of the two real withdrawals. This causes the integrator to believe both withdrawals delivered using the same on-chain evidence, enabling double-crediting/double-clearing of an internal ledger entry that never actually received funds — matching the "status or hash misreport making an integrator credit or refund twice" High-severity criterion (arguably Critical if it causes fund double-crediting). This is repeatable on every batch withdrawal containing duplicate `assetId` entries, at zero attacker cost beyond constructing the transaction with their own funds.

### Likelihood Explanation
Preconditions: attacker (or an integrator following straightforward usage) submits a single NEAR intents transaction with ≥2 `WithdrawalParams` sharing the same `assetId` routed through PoA bridge — no privileged access, no docs escape hatch abuse required; this is a natural usage pattern (e.g., paying two recipients the same token). Feasible and cheap: only requires normal user funds and standard SDK calls (`createWithdrawalIntents`, `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`). Fully repeatable.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` beyond `assetId` alone — e.g., match by `(near_token_id, destination address/amount)` when the POA API exposes those fields, or as the existing code comment suggests, sort both the API's withdrawal records and the batch's `WithdrawalParams` (for the same assetId) by amount and correlate by relative order/index. Until the POA bridge API supports disambiguating multiple same-asset withdrawals in one tx, the SDK should detect duplicate `assetId` entries within a single batch destined for `PoaBridge` and either reject them at `createWithdrawalIntents`/`validateWithdrawal` time or clearly document/throw to prevent silent misreporting.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
