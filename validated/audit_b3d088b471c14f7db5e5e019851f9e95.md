### Title
Unchecked `ReputationAsset::mint_into` failure in `pallet-consensus-incentives::on_executed` can revert `pallet-ismp::execute`, blocking all message delivery - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::process_message` performs a treasury transfer and then an unchecked reputation-asset mint, propagating any mint failure as a hard error out of the `FeeHandler::on_executed` hook. Because `pallet-ismp::Pallet::execute` treats any `on_executed` error as fatal for the whole message batch, a single failing mint can prevent all queued ISMP messages — including consensus updates — from being finalized in that call.

### Finding Description
`process_message` first transfers the calculated reward from the treasury to the relayer, then unconditionally mints an equal amount of `ReputationAsset` to the same relayer, converting any mint error into `Error::<T>::ReputationMintFailed` with `?`: [1](#0-0) 

This function is the `FeeHandler` implementation invoked once a batch of ISMP messages (which can include `ConsensusMessage`s alongside ordinary requests/responses) has been executed: [2](#0-1) 

`pallet-ismp` calls `T::FeeHandler::on_executed(...)` inside `Pallet::<T>::execute`, and maps *any* error from it to `Error::<T>::ErrorChargingFee`, aborting the whole `execute` call before the accumulated events (including `PostRequestHandled`, consensus commitments, etc.) are deposited: [3](#0-2) 

`FeeHandler` is composed as a tuple in the runtimes (`(pallet_consensus_incentives::Pallet<Runtime>, pallet_messaging_incentives::Pallet<Runtime>, ...)`), and the tuple's blanket `on_executed` impl short-circuits with `?` on the first pallet that errors: [4](#0-3) [5](#0-4) 

By contrast, `pallet-messaging-incentives` — which performs the analogous per-relayer mint — deliberately treats a failed `mint_into` as non-fatal, logging a warning and letting the rest of the batch continue: [6](#0-5) 

This asymmetry is exactly the analog of the 88mph bug: `distributeFundingRewards` failed to guard against `mph.ownerMint` reverting, which cascaded into unrelated critical functions (`withdraw`, `rolloverDeposit`, `payInterestToFunders`) reverting. Here, `consensus-incentives::process_message`'s unguarded `mint_into` call can revert for reasons entirely outside the relayer's or the message's control (e.g. the `ReputationAsset` implementation enforcing an existential/minimum balance the computed `reward` doesn't meet, the asset being administratively frozen/paused, or the relayer's account being in a state the asset implementation rejects), and that failure is not isolated to the incentive pallet — it aborts `pallet-ismp::execute` for the entire batch, including the consensus messages and application requests bundled with it.

### Impact Explanation
A reverted `execute` call means the relayer who submitted the batch pays gas/weight for a failed extrinsic and none of the batch's messages (consensus updates, POST requests, GET responses) are recorded as delivered. Because `StateMachinesCostPerBlock` and reward calculation are governance-controlled but the underlying `ReputationAsset::mint_into` success is not verified against edge cases (dust rewards below ED, a frozen/paused reputation asset, or an account that can't receive the asset), any of those conditions turns into a full network liveness issue: relayers cannot land consensus proofs or bundled application messages through that call until the pathological condition is fixed by governance. This is a "route unable to deliver messages" condition affecting the whole message pipeline, not just the incentive feature, which is a High-severity liveness/DoS risk to cross-chain message delivery.

### Likelihood Explanation
Likelihood is moderate: it requires a state where `T::ReputationAsset::mint_into` fails for a valid relayer (e.g., reward rounds to an amount the fungible implementation rejects, the asset is paused, or the relayer's account is otherwise blocked from receiving it) at a time when a consensus rotation payment is due. Since `calculate_reward` can legitimately produce very small (even zero-rounding-adjacent, non-zero) balances from `blocks * block_cost`, and pallets composing `fungible::Mutate` commonly enforce a minimum balance/existential deposit, this is a realistic, governance-independent trigger rather than a contrived edge case, unlike a malicious-admin scenario.

### Recommendation
Make the reputation mint in `pallet-consensus-incentives::process_message` non-fatal, mirroring `pallet-messaging-incentives`: log a warning (and/or emit a `ReputationMintFailed` event) on `mint_into` error instead of propagating it with `?`, so a reputation-mint failure never blocks the treasury reward transfer that already succeeded, nor aborts `pallet-ismp::execute` for the rest of the batch.

### Proof of Concept
1. Configure `ReputationAsset` (via `fungible::Mutate`) with a non-zero existential/minimum balance requirement (a realistic asset-pallet configuration).
2. Set `StateMachinesCostPerBlock` for a state machine such that `calculate_reward` yields a non-zero reward smaller than the asset's minimum balance for a fresh/near-zero relayer account.
3. Submit a consensus message batch (via `pallet-ismp::execute`) that advances that state machine's height, triggering `pallet_consensus_incentives::process_message`.
4. `T::Currency::transfer` succeeds, crediting the relayer; `T::ReputationAsset::mint_into` fails because the amount is below the asset's minimum balance, returning `Err(Error::<T>::ReputationMintFailed)`.
5. This error propagates through the `FeeHandler` tuple's `on_executed` to `pallet_ismp::impls::execute`, which maps it to `Error::<T>::ErrorChargingFee` and aborts the whole extrinsic — no events are deposited and no messages in the batch (including the consensus update) are considered delivered, even though the treasury already paid out the reward transfer that gets rolled back with the failed extrinsic.
