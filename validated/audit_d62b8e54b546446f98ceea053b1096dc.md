### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then forwards the `shop-domain` header — which is completely outside the HMAC's protected scope — to the app's handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed material: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, i.e. `HMAC(raw_body, client_secret) == received_hmac`, and — once that passes — trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator` itself only ever checks `to_signable_string` against the secret, agnostic of any other request property: [4](#0-3) 

The identity binding the gem implicitly claims to enforce is:
`shop authenticated by HMAC == shop delivered to the handler`

In reality the equation is:
`bytes verified by HMAC (raw_body only) ≠ bytes the handler treats as the tenant identity (shop-domain header)`

Because the app's `client_secret` is shared across **every** shop that has the app installed, a valid `(raw_body, hmac)` pair only proves "the sender knows this app's secret" (normally true because Shopify itself signs and sends it) — it proves nothing about which shop the payload belongs to. Any party able to receive a legitimate webhook for one shop (e.g., by installing the app on their own store, including a free/dev store) can capture a valid `(raw_body, hmac)` pair and replay it directly against the app's public webhook endpoint with the `shop-domain` header changed to an arbitrary victim shop. `Registry.process` will accept it (HMAC still matches, since it never covered the header) and hand the attacker-chosen `shop` value to the app as if it were authenticated.

### Impact Explanation
This breaks the tenant boundary of the app: an attacker-controlled `shop` value reaches the application's webhook handler as a "verified" field, letting the attacker impersonate another merchant to the app (e.g. trigger data writes/deletes, injected `customers/redact` style flows, or confuse per-shop data association) — a cross-tenant access condition, which is a Critical-impact category under the rules.

### Likelihood Explanation
Exploitation requires only: (1) obtaining any single legitimate `(raw_body, hmac)` pair addressed to the target app — trivially available to anyone who installs the app on any shop (including their own free dev store) and observes/replays the resulting webhook HTTP request — and (2) sending a forged HTTP POST directly to the app's public webhook endpoint with the `shop-domain` header swapped. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed/verified material, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., have `to_signable_string` incorporate `shop`, or cross-check the header value against a shop that was independently resolved/allow-listed by the host app), so that a valid HMAC cannot be replayed under a different tenant's identity.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify dev store and lets a webhook fire, capturing the raw POST body `B` together with its `X-Shopify-Hmac-Sha256` header `H` (valid, since it is computed with the shared `client_secret`).
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object where `hmac` still equals `H` and `to_signable_string` still equals `B`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, client_secret)` and finds it matches `H` — validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the payload actually originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
