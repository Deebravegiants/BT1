Based on my investigation, the strongest concrete analog I found is the missing-`return` bug in the OIDC token exchange handler.

### Title
Missing `return` after failed email-claim extraction lets an OIDC session be created and audit-logged as a successful login despite failed identity validation - ([File: core/sessions/oidcauth/oidc.go])

### Summary
In `handleTokenExchange`, the code extracts the `email` claim from the verified ID token and checks that the type assertion succeeded, but on failure it writes an HTTP 500 response and does **not** `return`, so execution falls through and continues to create a persisted session row and emit a successful-login audit event, exactly mirroring the reported bug class: a failure/zero-condition is detected but the code does not stop, allowing state to be created in an invalid condition.

### Finding Description
`handleTokenExchange` verifies the OIDC ID token, extracts group claims via `ExtractIDClaimValues`, and separately extracts `email`: [1](#0-0) 
If `claims["email"]` is not a string, the handler logs an error and writes an HTTP 500 body via `c.String(...)`, but it does not call `return`. Execution proceeds to:
- compute `role` from `IDClaimsToUserRole` (independent of `email`) [2](#0-1) 
- `INSERT INTO oidc_sessions` with the (empty) `email`, the computed `role`, and a freshly generated session ID [3](#0-2) 
- emit `audit.AuthLoginSuccessNo2FA` recording a successful login [4](#0-3) 
- attempt to set the session cookie and return a `200 OK` JSON success body [5](#0-4) 

This directly parallels the `MultiAccount._deployContract` bug: a failure condition is checked (`!ok` on the email assertion / `contractAddress == 0`), but the code path that should halt processing on that failure is not enforced, so a record representing a "successful" privileged operation (a new PartyA account / an authenticated session with an assigned RBAC role) is created despite the underlying operation having failed.

### Impact Explanation
A persisted `oidc_sessions` row with a valid, non-expired role (potentially `UserRoleAdmin` if the caller's IdP-side group claims map to the admin claim) is created and the audit log falsely records a successful authenticated login, even though the identity (email) of the user could not be established. This creates an authenticated session state inconsistent with the actual validation outcome and corrupts the audit trail used for security review — the RBAC role is bound in the datastore without a properly validated user identity attached to it.

### Likelihood Explanation
Reaching this path requires only that the `email` claim in a token returned by the configured OIDC provider is present but not typed as a plain string (e.g., an object/array, or simply absent from the returned claim set depending on provider/scope configuration) while the group claim used for role mapping is still resolvable. This is reachable by any user who can complete a normal OIDC login flow through `/oidc-login` → `/oidc-exchange`, i.e., an unprivileged external actor, without needing to compromise the IdP's signing keys.

### Recommendation
Add an explicit `return` after writing the error response when the `email` claim assertion fails, so that no session row is inserted and no success audit event is recorded on this failure path:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

### Proof of Concept
1. Configure an OIDC provider with `AdminClaim`/`EditClaim` role-group mapping as usual.
2. As a non-admin user, authenticate through `/oidc-login`, completing the provider redirect flow, using an identity/session where the ID token's `email` claim is not returned as a plain string (some providers omit `email` unless the `email` scope claim is explicitly requested, or return it in a non-string container depending on custom claim configuration), while the configured admin/edit group claim is present.
3. Call `/oidc-exchange` with the resulting authorization code.
4. Observe: `claims["email"].(string)` assertion fails, `c.String(http.StatusInternalServerError, ...)` is written without `return`.
5. Execution continues: `IDClaimsToUserRole` resolves the elevated role from the group claims, `INSERT INTO oidc_sessions` persists a session row with that role and an empty/blank email, and `audit.AuthLoginSuccessNo2FA` is logged as if the login succeeded — despite the identity-validation failure that should have aborted the flow.

Note: I could not fully verify from the index alone whether the subsequent `Set-Cookie` header (from `ginSession.Save()`) is actually delivered to the client once the earlier `c.String(http.StatusInternalServerError, ...)` write has already committed the HTTP response headers in Gin, since header commit ordering could not be traced through Gin's internals from the indexed code alone. If the cookie is not delivered, the primary confirmed impact is the orphaned privileged-session DB row and the falsified `AuthLoginSuccessNo2FA` audit record rather than a direct session-hijack; a Devin session with full repo/runtime access would be needed to confirm the exact header-commit timing and whether the cookie reaches the client.
