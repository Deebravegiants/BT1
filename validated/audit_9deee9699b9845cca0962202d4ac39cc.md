## Analysis Result

### Title
Predispatch escrow credited via unchecked `transfer()` return value in Tron `IntentGatewayV2.placeOrder` allows phantom/unbacked escrow credit - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-chain `IntentGatewayV2.placeOrder()` predispatch flow builds a raw `IERC20.transfer` call (bypassing `SafeERC20`) that is routed through `CallDispatcher.dispatch()`, and credits the order's escrow balance *before* verifying that this transfer actually moved tokens. `CallDispatcher` only checks that the low-level `.call()` did not revert — it never inspects the ABI-decoded boolean return value of `transfer()`. A token whose `transfer()` returns `false` on failure instead of reverting will let this sweep silently no-op while the gateway still records full escrow credit for the order.

### Finding Description
In the predispatch branch of `placeOrder`, the gateway measures the dispatcher's token balance, builds a sweep call using the raw selector, immediately increments the escrow mapping, and only afterwards dispatches the sweep — with no balance re-check: [1](#0-0) 

Note specifically that `transferCalls[i]` is built with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` (raw, unchecked selector, not `safeTransfer`), that `_orders[commitment][token] += reducedInputs[i].amount` happens *inside the same loop that builds the calls* (before the sweep is even dispatched), and that the actual dispatch of the sweep only occurs afterward via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`.

The `CallDispatcher` that executes this call only checks the low-level call succeeded, never the ERC20 boolean return value: [2](#0-1) 

Compare this to the sibling EVM-mainline implementation of the same predispatch flow, which correctly snapshots balances before and after the sweep and mutates `order.inputs[i].amount` to the *actually received* amount before crediting escrow: [3](#0-2) 

The Tron variant omits this balance-diff safety net entirely for the predispatch sweep-back step, so the escrow ledger `_orders[commitment][token]` can be inflated relative to what the contract actually holds whenever the swept token's `transfer()` fails "silently" (returns `false` without reverting).

That inflated escrow entry is fully redeemable later through the shared withdrawal path, which unconditionally transfers real tokens out based on the (possibly phantom) `_orders` balance: [4](#0-3) 

### Impact Explanation
Because escrow accounting is per-`commitment`+`token` but tokens of the same address are fungible and pooled in the gateway's actual balance, phantom credit for one order effectively becomes a real claim against the pooled balance funded by other users' genuinely escrowed deposits. When that phantom order is later filled/cancelled and `_withdraw()` runs, real tokens belonging to other depositors are paid out to satisfy a credit that was never actually backed by an incoming transfer. This is a direct theft/insolvency vector against the shared escrow pool and, once enough phantom credit accumulates, causes permanent inability to redeem legitimately escrowed funds for other users (freezing of funds).

### Likelihood Explanation
Exploitation requires only a single permissionless `placeOrder()` call with a predispatch call/asset configuration that routes into a token contract whose `transfer()` can return `false` without reverting (a documented, common non-standard-ERC20 behavior class, and the exact bug class flagged in the source report). No privileged role, governance, or off-chain component is needed — an attacker fully controls the predispatch call target and can choose or deploy such a token as the swap output.

### Recommendation
- Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` sweep calls with `SafeERC20.safeTransfer`-equivalent semantics, or have `CallDispatcher.dispatch` (or a wrapper used specifically for these ERC20 sweep calls) decode and require the ABI-encoded boolean return value when the call target is a token `transfer`/`transferFrom`.
- More importantly, mirror the mainline EVM `IntentGatewayV2.sol` pattern: snapshot the gateway's own `balanceOf` before dispatching the sweep and compute the actually-received amount afterward, crediting `_orders[commitment][token]` with that verified amount instead of the pre-sweep `balance`/`reducedInputs[i].amount` value.

### Proof of Concept
1. Attacker deploys (or finds) an ERC20 token `EvilToken` whose `transfer()` returns `false` under attacker-chosen conditions instead of reverting (fully EIP-20-legal behavior).
2. Attacker calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.predispatch.call` routing through a Uniswap-style swap (or any call dispatcher target) that results in `EvilToken` balance sitting on the `dispatcher`, and `order.inputs[i].token == EvilToken`.
3. During the sweep-back phase (`evm/tron/contracts/apps/IntentGatewayV2.sol:416-449`), the constructed `transferCalls[i]` invokes `EvilToken.transfer(gateway, balance)`, which the attacker's token implementation makes return `false` while not reverting.
4. `CallDispatcher.dispatch` only checks `success` from the low-level `.call()` (`evm/src/utils/CallDispatcher.sol:59-60`), so it does not detect the failed transfer; execution proceeds normally.
5. `_orders[commitment][EvilToken] += reducedInputs[i].amount` was already set at line 441 prior to the sweep, so the gateway now shows escrow credit for tokens it never actually received.
6. Attacker (or a colluding solver) later triggers the fill/cancel path leading to `_withdraw()` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), which calls `safeTransfer` of real, pooled `EvilToken`/other-token balance out to the beneficiary — draining funds legitimately escrowed by other users for that token.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
