### Title
Unbounded, fee-free `GetRequestsWithProof` triggers full proof verification in `validate_unsigned`, enabling computational-DOS via crafted unsigned extrinsics - (File: modules/pallets/state-coprocessor/src/lib.rs)

### Summary
The referenced GitLab CVE-2020-26411 is a DOS where a crafted, unprivileged search query caused disproportionately expensive backend work (statement timeouts) relative to the cost paid by the requester. The Hyperbridge analog is `pallet-state-coprocessor`'s `validate_unsigned` implementation, which performs the *entire* cryptographic state-proof verification pipeline for every unsigned `handle_unsigned` call that reaches the node — before any fee, weight limit, or transaction-pool cost is enforced — using an input structure (`GetRequestsWithProof`) that has no bound on the number of requests, number of keys per request, or proof byte length.

### Finding Description
`GetRequestsWithProof` is a plain, unbounded structure: [1](#0-0) 

`validate_unsigned` (the transaction-pool gate for the permissionless `handle_unsigned` call) directly invokes `Self::handle_get_requests(message.clone())`, which performs the full verification workload — `validate_state_machine`, `state_machine_commitment` lookups, `verify_membership` over all request commitments, and a per-request `verify_state_proof` (trie/merkle proof walk) for every key in every request: [2](#0-1) [3](#0-2) 

Unlike the sibling `pallet-beefy-consensus-proofs`, which explicitly bounds its unsigned payload via `BoundedVec<u8, T::MaxProofSize>` so oversized inputs are rejected at SCALE-decode time before dispatch (as documented in its own comments), `state-coprocessor`'s `requests: Vec<GetRequest>` and each `GetRequest.keys: Vec<Vec<u8>>`, plus `source`/`response` `Proof` bytes, carry no such bound: [4](#0-3) 

Because `pre_dispatch` is a no-op, and `validate_unsigned` is executed by every node validating the transaction (including gossip-relay validation prior to inclusion), an attacker can submit a `handle_unsigned` call with a large number of `GetRequest`s and/or large `keys`/proof payloads. Each such call forces every validating node to perform the full trie/merkle verification workload synchronously in `validate_unsigned`, yet the extrinsic's declared weight is a flat, trivial constant unrelated to the actual work performed: [5](#0-4) 

This mirrors the GitLab bug class: an unprivileged, cheap-to-submit request triggers disproportionately expensive backend computation (cryptographic proof verification instead of a DB query) with no bound on the amount of work induced, which can be repeated and even fails to charge a fee if verification ultimately rejects the message.

### Impact Explanation
An attacker can flood the network with `handle_unsigned` calls carrying maximal `requests`/`keys`/proof sizes. Every node performs the full verification pipeline before the transaction is even accepted into a block, consuming CPU disproportionate to the (near-zero) cost to the attacker. This can degrade block production and transaction-pool throughput for the coprocessor's message flow, a denial-of-service against a core reachable path (`handle_unsigned` / state proof verification), directly listed as in-scope for this analysis.

### Likelihood Explanation
`handle_unsigned` is explicitly permissionless (`ensure_none(origin)`), reachable by any relayer/attacker submitting a crafted, unsigned extrinsic with no economic cost gate applied prior to the expensive verification work. No existing size bound (`BoundedVec`, `MaxRequests`, `MaxKeys`) was found protecting `GetRequestsWithProof`, unlike the analogous, already-hardened `submit_proof` extrinsic in `pallet-beefy-consensus-proofs`.

### Recommendation
Bound `GetRequestsWithProof.requests` (e.g., `BoundedVec<GetRequest, T::MaxRequests>`), bound the number/size of `keys` per `GetRequest`, and bound `source`/`response` proof byte lengths, so oversized payloads are rejected at SCALE-decode time before `validate_unsigned` ever runs verification logic — mirroring the pattern already used in `pallet-beefy-consensus-proofs`'s `submit_proof`. Additionally, consider computing/charging `validate_unsigned`'s priority/weight proportionally to `requests.len()` and total proof size rather than a flat constant.

### Proof of Concept
1. Construct a `GetRequestsWithProof` with an unbounded `requests: Vec<GetRequest>` containing many entries, each with many large `keys`, and large `source`/`response` proof byte vectors.
2. Submit `Call::handle_unsigned { message }` as an unsigned transaction to the network.
3. Every validating node's `validate_unsigned` executes `handle_get_requests`, performing full `verify_membership`/`verify_state_proof` trie walks over the entire crafted payload — with a trivial declared weight — before the extrinsic is rejected or included, at negligible cost to the attacker.
