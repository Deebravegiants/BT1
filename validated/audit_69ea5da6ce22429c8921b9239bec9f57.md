### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then builds `WebhookMetadata` — including the `shop` attribute host apps use to select the tenant — directly from unauthenticated headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, the raw JSON payload: [2](#0-1) . The `hmac`, `shop`, `topic`, and `webhook_id` values are all pulled from HTTP headers that are never part of the signed material: [3](#0-2) .

`Registry.process` validates the HMAC and, on success, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3) . `HmacValidator.validate_signature` computes the signature exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [5](#0-4) .

This breaks the identity binding: **the shop the HMAC proves the payload came from ≠ the shop the handler is told the payload came from.** Since the signature only proves "this raw body was produced with knowledge of `api_secret_key`" and says nothing about which shop domain, topic, or webhook id accompanies it, an attacker who can obtain one legitimately-signed webhook (e.g., delivered to their own store, which they control as an app installer) can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for an arbitrary victim shop. `HmacValidator.validate` still returns `true` because it never inspects the headers, and `Registry.process` hands the handler a `WebhookMetadata` claiming the forged victim shop.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `#topic`) to select which tenant's database records to create/update/delete — the documented and expected usage pattern (see `docs/usage/webhooks.md`) — can be made to apply an attacker-controlled shop's legitimate webhook body (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) against a different, arbitrary merchant's tenant data. This is a cross-tenant integrity/confidentiality break driven purely by a header value that the cryptographic check never covers, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) attacker controls one shop that has installed the app (trivial — anyone can install a public app or spin up a dev store), so they receive at least one authentically-signed webhook body/HMAC pair for that shop, and (2) attacker can POST arbitrary headers to the app's public webhook endpoint, which is by definition internet-reachable and unauthenticated apart from the HMAC check. No access token, `client_secret`, or privileged account is required — only knowledge that the gem's HMAC check is body-only.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified payload:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (this would be a protocol change requiring Shopify's platform to sign them), or
- At minimum, document/enforce that `WebhookMetadata#shop` must be cross-checked by the host application against a known/expected shop for the given webhook subscription before being trusted, and consider rejecting bodies whose `shop` header does not match an app-tracked expectation (e.g., a shop known to have that specific `webhook_id` registered) inside `Registry.process` itself rather than leaving it entirely to consumers.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own shop "attacker.myshopify.com"
# and receives a real webhook, e.g. for "orders/create", with a valid
# x-shopify-hmac-sha256 computed over the raw body using the app's api_secret_key.

raw_body = '{"id":1,"total_price":"9999.00"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same body/hmac pair, but swaps the shop-domain header
# to a victim shop they do not control.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not the attacker's shop
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes: HMAC only covers raw_body, never the shop header.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# The registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though "victim-shop" never sent this webhook and the attacker has no
# credentials for it — a cross-tenant identity spoof.
```
