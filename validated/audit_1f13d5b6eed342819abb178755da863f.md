The external report describes a missing supply-cap check in a lending protocol's `borrowFor()`/`supply()` flow, where an over-limit deposit could break protocol solvency accounting. This bug class does not have an analogous root cause in the NEAR `core-contracts` repository:

- The `staking-pool/src/lib.rs` `deposit()` and `deposit_and_stake()` functions [1](#0-0)  and `internal_deposit()` [2](#0-1)  intentionally accept any attached deposit amount with no supply cap concept — by design, staking pools pool arbitrary amounts of delegated NEAR, and there is no "supply limit" invariant whose violation would cause insolvency or accounting divergence.
- `lockup/src/owner.rs` `deposit_to_staking_pool()`/`deposit_and_stake()` are owner-only privileged methods bounded by the owner's own lockup balance, not attacker-controlled inputs [3](#0-2) .
- Neither `lockup/src`, `staking-pool/src`, `staking-pool-factory/src`, `whitelist/src`, nor `multisig/src` implement any "total supply/borrow limit" configuration parameter that could be bypassed, so there is no reachable root cause matching the reported bug class (a missing cap check causing over-supply/insolvency).

Since no such limit mechanism exists in scope to be bypassed, and the impact categories (unauthorized transfer, fund freezing, authorization/state-machine bypass, accounting divergence, replay) don't map onto a "missing supply cap" issue here, this does not qualify as a valid analog.

    pub(crate) fn internal_deposit(&mut self) -> u128 {
        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        let amount = env::attached_deposit();
        account.unstaked += amount;
        self.internal_save_account(&account_id, &account);
        self.last_total_balance += amount;

        env::log(
            format!(
                "@{} deposited {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );
        amount
    }
