### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify sends only authenticates the JSON body of a webhook. The `shop`, `topic`, `webhook_id`, and `api_version` fields — which `ShopifyAPI::Webhooks::Registry.process` uses to select the handler and to identify the tenant (`shop`) the webhook data belongs to — are read straight from HTTP headers and are never included in the signed bytes. This breaks the equality `hmac_verified_bytes == bytes_the_app_acts_on`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed from headers, outside the HMAC's coverage: [3](#0-2) 

`Registry.process` trusts these header-derived fields to select the handler and to build the `WebhookMetadata` passed to the app's handler, including the `shop` value used to identify the tenant whose data the payload belongs to: [4](#0-3) 

Because the same `api_secret_key` is used to sign every webhook delivered to an app regardless of which merchant/shop triggered it, a valid `(raw_body, hmac)` pair captured from one legitimate webhook delivery (e.g. for shop A, topic `orders/create`) remains HMAC-valid if replayed with the `shop-domain` header changed to shop B (or the `topic` header changed to a different registered topic). `Utils::HmacValidator.validate` will still pass because it only re-derives the HMAC from `@raw_body`, which is unchanged; it never checks that `shop`/`topic`/`webhook_id` match what was actually signed by Shopify.

### Impact Explanation
This breaks the identity binding "shop authenticated versus shop acted on": the gem authenticates only the body bytes, then hands the caller-supplied `shop` (and `topic`) to the host application's handler as if it had been verified. A host app that uses `data.shop` from `WebhookMetadata` to determine which merchant record to update (the intended and documented usage pattern) can be made to apply a legitimately-signed payload under an attacker-chosen shop identity — a cross-tenant data-integrity issue, and depending on the handler logic, this can also be leveraged to trigger unintended handler dispatch by spoofing `topic`.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid `(raw_body, hmac)` pair for at least one topic/shop combination on the app (e.g. from their own installed shop, or an intercepted delivery to a webserver they control), which is realistic for any merchant/developer who has installed the app. No access to `api_secret_key` is needed — only replay of previously observed, validly-signed traffic with modified headers.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body, e.g. by hashing them together with the body before comparison), so `Utils::HmacValidator.validate` fails if any header consumed by `Registry.process` is altered relative to what was actually signed.

### Proof of Concept
1. Attacker installs the app on Shop A and lets it receive a legitimate `orders/create` webhook, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with `raw_body = B`, `x-shopify-hmac-sha256 = H` unchanged, but `x-shopify-shop-domain` set to Shop B's domain (a different merchant using the same app) and/or the topic header changed to another registered topic.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only — see `to_signable_string` at [2](#0-1)  — and it matches `H`, so `Registry.process` proceeds and invokes the handler with `shop: "Shop B"` even though the body was never signed in association with Shop B, per [4](#0-3) .
