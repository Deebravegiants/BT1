Audit Report

## Title
Unnecessarily broad read access exposes External Initiator `OutgoingToken` secret to any authenticated node role - (File: core/web/router.go)

## Summary
The `GET /v2/external_initiators` route is registered in the `authv2` group with no role-gating wrapper, unlike the sibling `POST`/`DELETE` routes on the same resource which require `auth.RequiresEditRole`. Since `authv2` only requires successful `AuthenticateByToken` or `AuthenticateBySession` (any role), any authenticated user — including the lowest-privileged `view` role — can call `Index` and receive the `OutgoingToken` secret for every configured external initiator.

## Finding Description
`v2Routes` mounts `eia.Index` behind only `paginatedRequest`, with no `RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole` wrapper: [1](#0-0) 

By contrast, `Create` and `Destroy` on the same resource are wrapped in `auth.RequiresEditRole`, confirming the intended privilege tier for managing this resource is at least "edit." [2](#0-1) 

The `authv2` group itself only enforces successful authentication (by token or session) with no minimum role — role checks are applied per-route via wrapper functions such as `RequiresEditRole`, `RequiresAdminRole`, `RequiresRunRole` defined in `core/web/auth/auth.go`, which explicitly reject `UserRoleView` for edit/run-level ops: [3](#0-2) 

`ExternalInitiatorsController.Index` returns every `ExternalInitiator` record mapped through `presenters.NewExternalInitiatorResource`, which includes the `OutgoingToken` field verbatim: [4](#0-3) [5](#0-4) 

`OutgoingToken` is a randomly generated secret assigned at creation time via `utils.NewSecret(utils.DefaultSecretSize)`: [6](#0-5) 

The existing test `TestExternalInitiatorsController_Index` confirms the endpoint returns `OutgoingToken` in the response body and is reachable via a generic authenticated `client.Get`, with no role-based test coverage differentiating privilege levels: [7](#0-6) 

No redaction, filtering, or role check intervenes between authentication and the handler returning the secret, so the broken assumption is that all authenticated users are trusted to read initiator secrets, contradicting the edit-role gate placed on the sibling mutating endpoints for the same resource.

## Impact Explanation
This is a genuine least-privilege violation resulting in secret exfiltration: a low-privileged (`view`-role) authenticated node user can retrieve `OutgoingToken` values for all external initiators, which are meant to be held only by the initiator integration and by operators who manage it (edit/admin tier, per the `Create`/`Destroy` gating). This maps to the in-scope "key/secret exfiltration" impact category via a node API role-bypass — an unprivileged read-only credential holder gains access to secret material outside its intended privilege scope.

## Likelihood Explanation
Likelihood is realistic wherever operators provision `view`-role or `run`-role API users/sessions (e.g., for auditors, dashboards, monitoring, or automation with minimal privileges) alongside `edit`/`admin` operators managing external initiators. The exploit requires no special conditions beyond a normal authenticated `GET` request to a live, exposed endpoint — no operator/admin access is needed to trigger it, only possession of any valid low-privilege credential (view/run), which the API explicitly supports as a distinct, lower trust tier.

## Recommendation
Wrap `GET /v2/external_initiators` in `auth.RequiresEditRole` (or at minimum `RequiresRunRole` if broader read access is intentionally needed for run-tier automation), consistent with `Create`/`Destroy` on the same resource. Alternatively, exclude `OutgoingToken`/`AccessKey` from `ExternalInitiatorResource` for non-privileged roles, or expose secrets only once at creation time (similar to how `ExternalInitiatorAuthentication` is returned only from `Create`).

## Proof of Concept
1. Provision two node users: one `admin`/`edit` (to create the initiator) and one `view`-role user (per `clsessions.UserRoleView`).
2. As the edit/admin user, `POST /v2/external_initiators` to create an initiator; the response includes a generated `OutgoingToken` (per `TestExternalInitiatorsController_Create_success`).
3. As the `view`-role user (via session cookie or API token), send `GET /v2/external_initiators`.
4. Observe HTTP 200 with the initiator's `outgoingToken` field present in the JSON body — reachable because the route at `core/web/router.go:264` has no role wrapper, unlike `core/web/router.go:265-266`.
5. Confirm via a Go handler/integration test analogous to `TestExternalInitiatorsController_Index` but authenticated as a `view`-role session/token instead of the default full-access test client, asserting the response still returns `200 OK` with non-empty `OutgoingToken`.

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// NewExternalInitiator generates an ExternalInitiator from an
// auth.Token, hashing the password for storage
func NewExternalInitiator(
	eia *auth.Token,
	eir *ExternalInitiatorRequest,
) (*ExternalInitiator, error) {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")
	}

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil
}
