### Title
Single-relayer allowlist on `IntentGatewayV2.onAccept`/`onGetResponse` permanently freezes already-escrowed order funds - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` gates delivery of *every* cross-chain settlement message — including escrow redemption (`RedeemEscrow`) and escrow refund (`RefundEscrow`) — behind a single hardcoded relayer address `_relayer`. This mirrors the reported Vault bug: an access-control check (whitelist there, single-relayer allowlist here) is applied uniformly to both privileged governance actions and to the release of user funds that are already locked in escrow, with no bypass for the fund-release path. If that one relayer address stops delivering — key loss, infrastructure failure, or a governance rotation to a new relayer that never resubmits the older in-flight message — a user's or solver's already-escrowed tokens become permanently unrecoverable, exactly as removal from the whitelist trapped a vault depositor's tokens.

### Finding Description
`onAccept` checks the relayer before doing anything else, for every request kind, including the two kinds that release user funds: [1](#0-0) 

and the relayer allowlist itself is documented as a single mutable address gating both `onAccept` and `onGetResponse`: [2](#0-1) 

`RedeemEscrow`/`RefundEscrow` both route to `_withdraw`, which physically transfers the escrowed tokens to the beneficiary: [3](#0-2) 

Likewise, `onGetResponse` — the handler that completes a **source-chain cancellation refund** after Hyperbridge proves the order was never filled — is also behind the same single-relayer check, as confirmed by the changelog note: [4](#0-3) 

At order placement, a user's or solver's input tokens are escrowed in `_orders[commitment][token]` with no direct withdrawal path — the *only* way to move them out is through `_withdraw`, called exclusively from `onAccept` (cross-chain) or the same-chain path. For cross-chain orders, this means the escrowed funds are entirely dependent on messages passing the relayer check. Just as `Vault._beforeTokenTransfer` blocked `requestWithdraw()`'s internal `_transfer(user, address(this), amount)` for any user removed from the whitelist — locking already-deposited funds — here a rotation or failure of `_relayer` blocks `RefundEscrow`/`RedeemEscrow` delivery for any order whose settlement message is in flight or was dispatched under the old relayer, locking already-escrowed order funds with no alternate recovery route.

### Impact Explanation
Escrowed input tokens for cross-chain orders (both cancellations awaiting refund and successful fills awaiting solver redemption) become permanently unreachable if the single authorized relayer address becomes unavailable or is rotated without every pending in-flight message being re-relayed by the new address. This is a **permanent freezing of user/solver funds** — the same fund-class impact as the reported Medium-severity Vault bug — reachable purely by the normal lifecycle of a submitted order (place → cancel/fill → settle), not by any malicious action from the caller.

### Likelihood Explanation
This is not a hypothetical admin-abuse scenario: it is a built-in single point of failure in the message-delivery path for every settlement. Any relayer downtime, key compromise requiring urgent rotation, or a rotation that isn't perfectly synchronized with all outstanding in-flight commitments creates a window (potentially unbounded, since there is no timeout/self-relay fallback in this check) during which legitimate users cannot recover escrowed funds. Given Hyperbridge is a live cross-chain messaging protocol expected to run continuously across many chains, relayer infrastructure incidents are a realistic and recurring operational risk class, not an edge case.

### Recommendation
Do not apply the same single-relayer allowlist to fund-release request kinds (`RedeemEscrow`, `RefundEscrow`) as to governance/administrative kinds (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`). Consider: (1) permitting any relayer (or a wider relayer set) to deliver settlement/refund messages while still restricting governance actions to the single authorized relayer, and/or (2) adding a timeout-based self-relay/escape hatch so that if the authorized relayer fails to deliver a `RefundEscrow`/`RedeemEscrow` message within a bounded window, the beneficiary (or anyone) can submit the proof directly to release the already-escrowed funds.

### Proof of Concept
1. A user places a cross-chain order on the source chain; input tokens are escrowed in `_orders[commitment][token]`.
2. The order is later cancelled from the destination chain (`_cancelFromDest`), dispatching a `RefundEscrow` post request back to the source chain via Hyperbridge — or, symmetrically, a solver fills the order and a `RedeemEscrow` message is dispatched.
3. Before the message is delivered, the gateway's owner/host rotates `_relayer` to a new address (e.g., due to a compromised or retired relayer key), per `RelayerUpdated` in `IntentsBase.sol`.
4. The Hyperbridge relay for the still-pending `RefundEscrow`/`RedeemEscrow` message is submitted by (or only obtainable from) the old relayer identity, which no longer matches `_relayer`; `onAccept`'s `_checkRelayer` check at the top of the function reverts with `Unauthorized` regardless of who calls it or how many times, since the check compares against the current `_relayer` value, not the message's original relayer context.
5. `_withdraw` is never reached, `_orders[commitment][token]` remains funded, and the escrowed tokens are permanently stuck with no user-triggerable recovery path — mirroring the Vault report's `requestWithdraw()` being blocked by `_beforeTokenTransfer`'s whitelist check after removal.

Note: I was unable to fully trace whether `IntentGatewayV2.sol` (the top-level contract, as opposed to `IntentsBase`/`ExtrinsicIntents`) exposes any additional escape hatch (e.g., a timeout path independent of `_relayer`) due to iteration limits — a Devin session with full repo access should verify `evm/src/apps/IntentGatewayV2.sol` and `IntrinsicIntents.sol` in their entirety for any such bypass before finalizing severity.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

# 2026-09-03 — Relayer allowlist on the intent gateway

The gateway now accepts `onAccept` and `onGetResponse` deliveries only from a single authorised
relayer stored at `_relayer` (slot 13, packed behind `_paused`). The check runs before the message
body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are
covered. A refused delivery reverts, which the host records as undelivered, so the authorised
relayer can submit the same message later. `setRelayer(address)` is callable by the immutable
`_owner` and by the host; the host branch exists so a governance `UpgradeContract` can carry the
call as its migration calldata and arm the relayer in the upgrade transaction (`upgradeToAndCall`
delegatecalls that calldata with the host still as `msg.sender`).
