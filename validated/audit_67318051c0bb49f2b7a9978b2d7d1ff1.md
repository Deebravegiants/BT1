## Analysis

Mapping the bug class ("a value used to select/attribute a privileged action is not covered by the cryptographic check that authenticates the request") to this gem's webhook-processing path produces a direct analog.

### Identity binding that should hold
`shop == cryptographically_verified(shop)` for every field used to attribute a webhook event to a tenant. Instead the gem enforces only:

`HMAC(raw_body) == received_hmac`, while `shop` (and `topic`, `webhook_id`, `api_version`) are taken from unauthenticated HTTP headers.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`) are parsed straight from headers with no cryptographic tie to the body/HMAC: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then hands the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever operate on `to_signable_string` (the raw body), never on the shop header: [4](#0-3) 

### Before/after the attacker's request
- Before: attacker's own store (a normal, unprivileged Shopify merchant account, freely creatable) legitimately installs the public app and triggers any webhook. They capture a valid `(raw_body, x-shopify-hmac-sha256)` pair — valid because the HMAC secret (`client_secret`) is shared by all installs of the app, not per-shop.
- Attacker request: POST directly to the app's public webhook endpoint with the captured `raw_body`/`hmac` unchanged, but with `x-shopify-shop-domain` (and optionally `x-shopify-topic`) rewritten to a victim shop's domain.
- After: `HmacValidator.validate` still succeeds (only body bytes are checked), `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with the attacker-chosen `shop`, and dispatches it to the topic handler as if Shopify itself had sent this event for the victim tenant — i.e. `shop_authenticated (none) != shop_used_for_tenant_attribution (attacker-controlled)`.

This is exactly the "field acted on but not covered by the HMAC" pattern, and it crosses a tenant boundary purely through this gem's own verification/dispatch code, independent of how carefully the host app follows Shopify's documented webhook usage.

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC-SHA256 (`Utils::HmacValidator.validate`), while the `shop` domain (and `topic`/`webhook_id`) used to attribute the event to a tenant and route it to a handler are read from plain HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) . All other webhook attributes (`shop`, `topic`, `webhook_id`, `api_version`) are pulled unauthenticated from headers [2](#0-1) . `Registry.process` checks `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds `WebhookMetadata` using `request.shop` and dispatches to the registered handler [3](#0-2) . Because the app's `client_secret` (used as the HMAC key) is identical for every shop that installs the app, any merchant who installs the app can obtain a valid `(raw_body, hmac)` pair for their own shop and replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a different, victim tenant. The gem's own verification logic provides no mechanism to detect this, since the shop identity is simply never part of what is authenticated.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide: the `shop` value handed to the host application's webhook handler — which apps use to determine whose store data to read/write — can be attacker-controlled even though the HMAC check reports success. This is a cross-tenant access vector achievable by any unprivileged internet user who can install the target app on a free/trial store, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the public app on an attacker-controlled shop (available to anyone), (2) the app's webhook endpoint being reachable directly over the internet (true by design, since Shopify calls it over plain HTTPS with no additional caller authentication expected beyond the HMAC), and (3) capturing one legitimate `(body, hmac)` pair, which the attacker can trivially produce by triggering any webhook event on their own store. No secrets need to be leaked and no privileged account is required.

### Recommendation
Bind the tenant/topic identity into the authenticated material, e.g. include `shop`, `topic`, and `webhook_id` header values in `to_signable_string` (or otherwise cryptographically bind them to the signed body), or have `Registry.process`/the consuming app cross-check `request.shop` against an independently verified value (e.g., the shop associated with the currently active/known session, or a per-shop secret) before dispatching to handlers. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as an identity boundary without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g. updates a product) and captures the resulting POST to the app's webhook endpoint, noting `raw_body` and the `X-Shopify-Hmac-Sha256` header value — this passes `HmacValidator.validate` because it was legitimately computed with the shared `client_secret`.
3. Attacker sends a new POST directly to the same public webhook endpoint URL, reusing the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` (body/HMAC unchanged), and `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)` to the app's handler, which acts on `victim-shop.myshopify.com`'s data using attacker-supplied content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
