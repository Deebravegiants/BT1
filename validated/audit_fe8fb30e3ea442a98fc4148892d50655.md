### Title
Unchecked floating-point summation of PSBT amounts causes the Ledger "negative-fee" safety check to be bypassable via overflow/precision loss - (File: `features/hw-ledger/src/module/assets/utils/psbt.ts`)

### Summary
`addDummyInputs()` in the Ledger hardware-wallet PSBT helper sums output and input amounts using plain JavaScript `+=` on raw `Number` values taken directly from a PSBT that may originate from an untrusted third party. This is the same bug class as the report: unchecked accumulator arithmetic (`amount_remaining -=`, `amount_calculated -=`/`+=` in the Uniswap/Seawater swap loop) that is *assumed* to never under/overflow but is never validated, so a crafted input can desynchronize the accumulated value from reality.

### Finding Description
`addDummyInputs` exists specifically to satisfy a Ledger firmware invariant that "the sum of outputs must be ≥ the sum of inputs" (i.e., a non-negative fee), by padding in a dummy input when needed: [1](#0-0) 

The amounts are accumulated with unchecked `+=` on ordinary JS numbers:

```
let outputAmount = 0
for (let i = 0; i < psbt.getGlobalOutputCount(); i++) {
  outputAmount += psbt.getOutputAmount(i)
}

let inputAmount = 0
for (let i = 0; i < psbt.getGlobalInputCount(); i++) {
  const witnessUtxo = psbt.getInputWitnessUtxo(i)
  if (witnessUtxo) {
    inputAmount += witnessUtxo.amount
  }
}
``` [2](#0-1) 

`getOutputAmount`/`witnessUtxo.amount` are read straight from PSBT wire fields, which are 8-byte little-endian integers per the PSBTv2/BIP-370 spec (range up to `2^64-1`), not values that are consensus-bounded before this code runs. The surrounding module explicitly documents that these PSBTs can come from a "third-party (potentially malicious)" source: [3](#0-2) [4](#0-3) 

Just like the Uniswap/Seawater case, the original safety property ("outputs ≥ inputs ⇒ fee ≥ 0") is only correct if the underlying arithmetic is exact. Here it is not: JS `Number` loses integer precision above `2^53` and any output/input amount fields crafted near or above that threshold (attacker fully controls these fields in a third-party-supplied PSBT) will silently corrupt the running sum instead of throwing. Because the check `outputAmount > inputAmount` and the subsequent `amount = outputAmount - inputAmount` both operate on this already-corrupted floating-point value, an attacker can engineer specific large amount values so that:
- the true (integer) input/output totals differ substantially from what `addDummyInputs` computes, and
- the computed dummy-input `amount` (which is what gets attached to the newly injected input and is what the Ledger uses to validate/derive the displayed fee) no longer reflects the real value the user is actually spending.

### Impact Explanation
This routine exists purely to keep the Ledger firmware's fee sanity-check from erroring out, and the dummy-input amount it fabricates directly feeds the value the Ledger's screen uses to compute and display the transaction fee to the user during the on-device confirmation (the trust boundary for authorizing a signature). If the accumulation is corrupted by attacker-chosen amount fields, the value shown/enforced on the hardware device during signing no longer matches the actual value moved on-chain, defeating the very check this function was written to preserve and undermining the integrity of the user's hardware-wallet signing confirmation — a concrete unauthorized/deceptive-signing outcome, not merely a display bug.

### Likelihood Explanation
Reachability requires only that the user's Exodus wallet be asked to co-sign or process a PSBT supplied by an external/third party (explicitly anticipated by the surrounding code, e.g. multi-party or PayJoin-style flows) containing one or more crafted amount fields near/above `2^53`. No privileged access or malicious node/operator is needed — only a counterparty able to hand the user a PSBT, which is the exact scenario the file's own comments describe as untrusted input.

### Recommendation
Perform all PSBT amount accumulation and comparisons with `BigInt` (or the project's existing `@exodus/bigint`/`@exodus/currency` NumberUnit types used elsewhere in the codebase, e.g. `libraries/bigint/src/native-bigint.js`) instead of native `Number` `+=`/`-=`, and explicitly reject/clamp any PSBT amount field that exceeds Bitcoin's consensus maximum (`21_000_000 * 1e8` satoshis) before it is summed in `addDummyInputs`.

### Proof of Concept
1. Construct a PSBT (as would be received from a third party in a multi-party signing flow) with `psbt.getGlobalOutputCount()` outputs whose `getOutputAmount(i)` values are individually valid 64-bit field values but sum, in exact integer arithmetic, to a value requiring more than 53 bits of precision (e.g. several outputs each close to `2^53`).
2. Pass this PSBT into `addDummyInputs(psbt)`.
3. Observe that `outputAmount` (and/or `inputAmount`) computed via the `+=` loop loses precision relative to the true integer sum, causing `amount = outputAmount - inputAmount` to diverge from the real fee/dummy-input value that should have been computed, and that value is what gets written into the PSBT via `psbt.setInputWitnessUtxo(newInputIndex, amount, ...)` and ultimately used in the Ledger fee-sanity/display path. export function addDummyInputs(psbt: PsbtV2) {
  const canAddDummy = canModifyInputs(psbt)
  if (!canAddDummy) {
    return
  }

  let outputAmount = 0
  for (let i = 0; i < psbt.getGlobalOutputCount(); i++) {
    outputAmount += psbt.getOutputAmount(i)
  }

  let inputAmount = 0
  for (let i = 0; i < psbt.getGlobalInputCount(); i++) {
    const witnessUtxo = psbt.getInputWitnessUtxo(i)
    if (witnessUtxo) {
      inputAmount += witnessUtxo.amount
    }
  }

  if (outputAmount > inputAmount) {
    // Add a dummy input to prevent the ledger from
    // throwing an error w.r.t a negative fee.
    const newInputIndex = psbt.getGlobalInputCount()
    const amount = outputAmount - inputAmount
    psbt.setGlobalInputCount(newInputIndex + 1)
    // A little easter egg, we use the very first transaction in the bitcoin
    // blockchain as the dummy input, this should make it abundantly clear
    // to external observers that this is likely not really an input.
    const FIRST_BITCOIN_TXID = '4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b'
    psbt.setInputPreviousTxId(newInputIndex, Buffer.from(FIRST_BITCOIN_TXID, 'hex'))
    psbt.setInputOutputIndex(newInputIndex, 0)
    psbt.setInputWitnessUtxo(newInputIndex, amount, Buffer.from('01', 'hex'))
  }
}
