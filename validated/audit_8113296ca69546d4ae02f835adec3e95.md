## Title
Webhook HMAC Validation Does Not Bind `shop-domain` or `topic` to the Signed Payload, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook signature verification flow in `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body, while the `shop-domain` and `topic` headers used to route and attribute the webhook to a tenant are never covered by that signature. This breaks the identity binding `HMAC-verified bytes == data trusted as belonging to a specific shop`. An unprivileged internet user who has legitimately triggered one signed webhook for their own shop (e.g. by installing the app and creating a test order) can capture the `(raw_body, hmac)` pair and replay it directly against the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header, since neither is part of `to_signable_string`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unsigned HTTP headers: [2](#0-1) 

`HmacValidator.validate_signature` computes and compares the HMAC solely against `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` then trusts `request.shop` and `request.topic` — both unsigned — to route to a handler and construct the tenant-identifying `WebhookMetadata`: [4](#0-3) 

Because a single app-level `api_secret_key` is shared across every shop that installs the app (this is the standard multi-tenant public-app model), any shop's legitimately signed webhook `(raw_body, hmac)` pair remains valid HMAC-wise no matter what `shop-domain`/`topic` header accompanies it on replay. The identity equality that should hold — "the shop/topic the signature was computed for" == "the shop/topic the handler acts on" — never holds, because the signature never covers those fields.

### Impact Explanation
This is a cross-tenant integrity issue: a user who installs the app on their own shop can trigger a legitimate webhook, capture its body+HMAC, and replay it toward the app's webhook receiver while spoofing an arbitrary victim `shop-domain` header (and/or `topic`). Any host application that follows the documented `Registry.process` flow will hand the attacker-chosen `shop` value straight to the webhook handler as `WebhookMetadata#shop`, causing the handler to write/act on data under a victim tenant's identity using content the attacker controls (their own webhook body). This satisfies the "cross-tenant access" impact criterion since it lets one merchant's data cross into another merchant's tenant context purely through header manipulation, without needing the app's credentials.

### Likelihood Explanation
Likelihood is realistic for any consumer of this gem: the webhook endpoint is by design an unauthenticated public HTTP endpoint (Shopify calls into it over the internet), so nothing prevents an attacker from POSTing directly to it with modified headers. The only prerequisite is capturing one previously valid `(body, hmac)` pair, which any user who installs the app on their own store can trivially obtain (e.g. via `orders/create` on their own shop) and then replay against the same endpoint with a forged `shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the data that is verified, not just trusted as a header. Since Shopify's `X-Shopify-Hmac-SHA256` is computed only over the raw body by Shopify itself, the gem cannot change what Shopify signs; however, the gem should not silently expose `request.shop`/`request.topic` as trusted values derived purely from unauthenticated headers. At minimum, document prominently (and enforce where feasible) that host applications must independently corroborate `shop-domain` against a known/registered shop for that specific webhook subscription (e.g., cross-check against the webhook id or a previously registered callback per shop) rather than trusting the header value as an implicit tenant identity once HMAC-over-body passes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any registered webhook topic (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header value sent by Shopify.
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with:
   - the same raw body and `x-shopify-hmac-sha256` value captured in step 1,
   - `x-shopify-shop-domain: victim-shop.myshopify.com`,
   - optionally a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` — unchanged from step 1 [3](#0-2) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is the attacker-forged `victim-shop.myshopify.com` [5](#0-4) , causing the host app to process attacker-controlled data under the victim's tenant identity.
