### Title
PoA bridge `describeWithdrawal` misreports withdrawal status/tx hash for same-asset entries in a batch withdrawal - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` ignores `args.index` entirely and resolves the withdrawal purely via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find(...)` on `assetId` equality only. When a batch withdrawal (a documented, user-facing SDK feature per `docs/design/rfc-batch-withdrawal-granular-control.md`) contains two withdrawal entries for the same `assetId` (e.g., splitting one token to two different destination addresses), both `describeWithdrawal(index=0, ...)` and `describeWithdrawal(index=1, ...)` calls return the identical first-matching entry from the POA indexer's response, misreporting the second withdrawal's destination-chain tx hash.

### Finding Description
The equality claimed broken: `describeWithdrawal({index: 0, assetId: X, ...})` and `describeWithdrawal({index: 1, assetId: X, ...})` should resolve to two *different* completion records (different `transfer_tx_hash`, different destination address), but both resolve to the SAME record because matching is done exclusively by `assetId`, never by `index`: [1](#0-0) 

`findMatchingWithdrawal` uses `Array.prototype.find`, which always returns the first element satisfying the predicate — so for two entries sharing the same `nep141:${near_token_id}`, every caller (regardless of `index`) gets entry `[0]`: [2](#0-1) 

The comment explicitly acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported") but the code does not throw or guard against it — it silently misreports instead of failing safe. This is reachable through a fully legitimate, unprivileged path: `IntentsSDK.createWithdrawalCompletionPromises` / `watchWithdrawal` build one `WithdrawalIdentifier` per withdrawal param via `createWithdrawalIdentifiers`, which assigns a per-route `index` counter but the PoA bridge's `describeWithdrawal` never consults that `index`: [3](#0-2) 

The claimed `near_token_id` string-collision path (different tokens) is not exploitable — the comparison is a strict `===` on the full `nep141:${near_token_id}` string, so `usdt.omft.near` and `tusdt.omft.near` never collide. The real, exploitable break is the same-`assetId`/different-`index` case.

An ordinary user submits a batch withdrawal (e.g., two POA-bridged BTC withdrawals in one intent, to two different destination addresses) and calls `sdk.createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`. Nothing in `supports()`, `validateWithdrawal()`, or the intents contract itself prevents two same-asset PoA withdrawals in one batch — those checks validate address/amount per-item, not cross-item uniqueness.

### Impact Explanation
Both `promises[0]` and `promises[1]` (or `describeWithdrawal` for index 0 and 1) resolve to `{status: "completed", txHash: <first-entry's transfer_tx_hash>}` even though they correspond to genuinely different on-chain payouts to different destination addresses. An integrator using this SDK API to key off the reported `txHash`/`index` to credit, reconcile, or refund a specific leg of a batch withdrawal will attribute the wrong destination-chain transaction to the second withdrawal (and never learn the true tx hash for it), matching the High-severity category "a status or hash misreport making an integrator credit or refund twice." This is repeatable on every same-asset multi-entry batch withdrawal through the PoA route.

### Likelihood Explanation
Preconditions: PoA bridge route, a batch withdrawal (`withdrawalParams` array) containing ≥2 entries with the same `assetId`, both completed by the indexer in the same `getWithdrawalStatus` response. This requires no privilege beyond being a normal SDK user constructing their own batch withdrawal — a supported use case per the batch-withdrawal RFC. Attacker cost is zero beyond normal withdrawal fees; it's deterministic and repeatable on every such batch.

### Recommendation
Sort `withdrawals` and the caller's same-asset `withdrawalParams` by amount (as the code comment already suggests) and match by `(assetId, index-within-that-assetId)` rather than the first assetId match, or throw an explicit unsupported-batch error when duplicate `assetId`s are detected in a batch, rather than silently returning the first match for every index.

### Proof of Concept
Vitest test in `poa-bridge.test.ts` style:
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to resolve `{ withdrawals: [ {status:"COMPLETED", data:{near_token_id:"btc.omft.near", transfer_tx_hash:"hashA", amount:100000, ...}}, {status:"COMPLETED", data:{near_token_id:"btc.omft.near", transfer_tx_hash:"hashB", amount:200000, ...}} ] }`.
2. Call `bridge.describeWithdrawal({..., index:0, withdrawalParams:{assetId:"nep141:btc.omft.near", amount:100000n, ...}})` → expect `{status:"completed", txHash:"hashA"}`.
3. Call `bridge.describeWithdrawal({..., index:1, withdrawalParams:{assetId:"nep141:btc.omft.near", amount:200000n, ...}})` → assert it currently ALSO returns `{status:"completed", txHash:"hashA"}` (should be `"hashB"`), proving the misreport.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
