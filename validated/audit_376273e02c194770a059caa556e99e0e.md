### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, not the shop header. Any party capable of producing one valid `(body, hmac)` pair for a topic (e.g., an attacker who legitimately installed the app on their own shop and receives real webhooks) can replay that same body/HMAC pair while substituting a different shop domain in the header, and `Registry.process` will accept it as authentic and dispatch it to the host app's handler tagged with the attacker-chosen shop.

### Finding Description
`Registry.process` validates authenticity solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC is computed only over `to_signable_string`, which is defined as `@raw_body` — headers, including `shop`, are excluded from the signed content: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against the received HMAC — the shop value never enters the signed bytes: [4](#0-3) 

After passing this check, `Registry.process` builds `WebhookMetadata` using `request.shop` verbatim and passes it to the host application's handler as the authoritative tenant for the event: [5](#0-4) [6](#0-5) 

The identity binding that is broken: `hmac == HMAC(secret, body)` is checked, but the code (and every downstream `WebhookHandler#handle`) treats it as if `hmac == HMAC(secret, body || shop)`. Since `shop` is excluded from the signed bytes, `verified(body) != verified(body, shop)`. Any (body, hmac) pair the attacker legitimately obtained for their own shop's webhook remains fully valid HMAC-wise when replayed with an arbitrary `x-shopify-shop-domain` header value, because `OpenSSL.secure_compare` in `validate_signature` never inspects the shop header.

### Impact Explanation
Because `WebhookMetadata#shop` is the only tenant-scoping signal handlers receive, and it is not cryptographically bound to the payload, a party who owns/installs the app on shop A can forge or replay a body they control (or intercept from their own legitimate webhook) while claiming to be shop B. For mandatory compliance topics like `customers/redact`, `customers/data_request`, and `shop/redact` — and any host-app logic keyed off `data.shop` (e.g., looking up/deleting/mutating the named shop's records, associating billing/order data, or triggering per-tenant workflows) — this enables cross-tenant data manipulation or disclosure without holding shop B's credentials, i.e., cross-tenant access.

### Likelihood Explanation
Exploitation requires only that the attacker obtain one valid `(raw_body, hmac)` pair for any topic under the app's shared `client_secret` (trivially available to any shop that installs the app and receives its own real webhooks) and the ability to POST to the app's public webhook endpoint with a spoofed `x-shopify-shop-domain` header — no access to the target shop, its token, or the app's `client_secret` is needed.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or otherwise cryptographically corroborate the shop header against a known-good identity (e.g., resolve the shop only via a session/token already associated with that shop, or include the shop domain in the signed payload string checked by `to_signable_string`) before trusting `request.shop`/`WebhookMetadata#shop` in the handler.

### Proof of Concept
1. App has two merchant installs: attacker's shop `attacker.myshopify.com` and victim shop `victim.myshopify.com`, both sharing the same app `client_secret`.
2. Shopify sends the attacker a legitimate webhook, e.g. `customers/data_request`, with body `B` and headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker replays the exact same `B` and `H` to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` via `OpenSSL.secure_compare` — this succeeds because `B` is unchanged: [7](#0-6) 
5. `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` is passed to the host app's handler, which now performs shop-B-scoped work (e.g., customer data lookup/deletion) attributed to `victim.myshopify.com` even though Shopify never sent this event for that shop.
