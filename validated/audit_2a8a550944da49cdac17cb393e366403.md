### Title
Webhook shop-domain (and topic/webhook_id) not bound to HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw JSON body, while `shop`, `topic`, `webhook_id`, and `api_version` are taken verbatim from HTTP headers that are never included in the signed content. `HmacValidator` therefore validates only that "some request with this body was signed with the app's secret," not that the encoded shop actually sent it.

### Finding Description
The identity binding that should hold is: `shop_authenticated_by_hmac == shop_delivered_to_handler`. In this gem it does not.

- `Webhooks::Request#to_signable_string` returns `@raw_body` only [5](#0-4) .
- `Webhooks::Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled unconditionally from headers with no cryptographic tie to the signed body [6](#0-5) .
- `Utils::HmacValidator.validate` computes/compares the signature using only `to_signable_string`, i.e., the body [7](#0-6) .
- `Registry.process` trusts this validation and forwards `request.shop` into `WebhookMetadata` given to the host app's handler [4](#0-3) .

Because a Shopify app uses a single `api_secret_key` for all merchant shops that install it, any shop that installs the app can receive a legitimately-signed webhook for its own store (valid `raw_body` + HMAC computed with the shared app secret). An unprivileged attacker who owns/controls such a shop can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a victim shop. `HmacValidator.validate` still succeeds because the header contents are outside the HMAC's scope entirely, and `Registry.process` passes the forged `shop` value straight to the app handler as authenticated metadata.

This is the exact anti-pattern flagged by the report's bug class ("a field acted on but not covered by the HMAC"): here the `shop` tenant identifier is acted upon (used to route/attribute webhook data) but is not part of what the HMAC actually verifies.

### Impact Explanation
Host applications built on this gem are documented to trust `data.shop` from `WebhookMetadata` as the source-of-truth tenant identifier for the delivered `data.body` [8](#0-7) . An attacker who can send arbitrary HTTP requests to the app's public webhook endpoint (no access token or secret needed) can inject a self-forged, arbitrary JSON body — signed only with knowledge that the shared secret produced *some* valid signature they replay — while attributing it to any victim shop domain. Depending on how the host app processes topics like `orders/create`, `app/uninstalled`, `customers/data_request`, etc., this enables cross-tenant data injection/corruption keyed by an attacker-chosen `shop` value, i.e., cross-tenant access as defined in scope.

### Likelihood Explanation
Requires only: (1) the attacker installs the app on any shop they control (a normal, unprivileged action available to any merchant/developer), (2) they trigger any webhook topic on their own shop to obtain one valid `(body, hmac)` pair, and (3) they replay that request to the app's public webhook callback URL with a modified shop-domain header. No access token, `client_secret`, or privileged account is needed beyond ordinary self-service app installation.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise cryptographically tie the header-derived tenant identity to the verified payload — e.g., validate that the shop header corresponds to a shop with a stored session for this app before dispatching, and/or require host apps to independently confirm the `shop` against an existing installation record rather than trusting the header value implicitly. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as the sole tenant-identity source for authorization decisions.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (self-service, unprivileged).
2. Attacker triggers a webhook (e.g., updates a product) causing Shopify to POST to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker intercepts/replays this exact `(B, H)` pair directly to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` and compares to `H` — matches, since `shop` was never part of the signed string [9](#0-8) .
5. `Registry.process` invokes the host handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)` [10](#0-9) , causing the app to act on attacker-supplied data as though it originated from the victim shop.
