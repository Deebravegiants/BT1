### Title
RAY-scaled debt valuation overflows `i128` before `MAX_BORROW_INDEX_RAY` engages, permanently freezing all pool verbs on a large, high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
The integer-overflow bug class from ALPINE-CVE-2020-10543 maps onto XOXNO Lending's RAY index math: `accrue_step` values total debt as `borrowed_scaled × borrow_index / RAY` via `Ray::mul`, which panics with `MathOverflow` when the product's quotient leaves `i128`. The borrow index is only capped at `MAX_BORROW_INDEX_RAY` (10^36) *after* this multiplication succeeds, so on a sufficiently large market the i128 ceiling (~1.7e38, i.e. ~170 RAY-valued units of debt) is hit while the index is still far below its cap. Since `global_sync` runs accrual before every pool verb, once the market crosses this line no repay, withdraw, borrow, liquidate, or `update_indexes` call can ever succeed — all supplied and borrowed funds in that market are permanently frozen.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` before evaluating the borrow rate or updating the index (common/src/rates/simulate.rs:60-64). `scaled_to_original` is `scaled.mul(env, index)` (common/src/rates/scaling.rs:14-16), and `Ray::mul` delegates to `fp_core::mul_div_half_up` (common/src/math/fp.rs:50-52), which raises `MathOverflow` when `borrowed × borrow_index / RAY` does not fit `i128` — a documented behavior in docs/reference/formulas.md:20-24.

The index cap is applied inside `update_borrow_index` only on the *result* of `old_index.mul(env, interest_factor)` (common/src/rates/index.rs:13-19), and `accrue_step` calls it only after the overflow-prone valuation at line 60. Because `MAX_BORROW_INDEX_RAY = 10^36` corresponds to a 10^9× index while i128 only holds ~170× a RAY-valued `borrowed`, any market whose scaled `borrowed` exceeds `i128::MAX / borrow_index` hits the valuation overflow first. `global_sync` in contracts/pool/src/interest.rs invokes `accrue_chunk` → `accrue_step` on every mutation (contracts/pool/src/interest.rs:20-53), so the panic is unrecoverable: it fires before any state is written, on every subsequent call.

The repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361) demonstrates this end-to-end: an 18-decimal market with ~1e9-whole-token supply at 98% utilization on the XLM curve panics with `MATH_OVERFLOW` in `update_indexes` while `borrow_index < MAX_BORROW_INDEX_RAY`, and afterwards `withdraw` and `repay` both fail with the same error.

### Impact Explanation
Permanent freezing of all user funds in the affected (hub, token) book: every entrypoint — `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `update_indexes`, flash and router paths — accrues first via `global_sync` and reverts inside `scaled_to_original`. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and bad debt cannot be cleaned. The freeze applies to the whole market book, not just the attacker's position.

### Likelihood Explanation
Reachable by unprivileged users without any privileged action. An attacker (or organic usage) needs a market where scaled `borrowed × borrow_index` exceeds `i128::MAX × RAY` before the index reaches its cap — e.g., a high-decimals asset with lifted caps, ~1e9 whole tokens supplied, ~98% borrowed, at sustained high-utilization rates. Time does the rest; any subsequent `update_indexes` call by anyone triggers the panic. The in-repo test proves the trajectory exists on a standard curve within a modest number of years; larger principals or steeper curves shorten it. No oracle manipulation, leaked keys, or privileged calls are required, and the state cannot be rolled back because no write precedes the panic.

### Recommendation
Bound the valuation instead of panicking: clamp `borrowed`/`supplied` scaled totals (or the index) so `scaled_to_original` stays inside i128, e.g. compute `borrowed_original` via a saturating mul-div and treat saturation as "debt at cap," or lower `MAX_BORROW_INDEX_RAY` to a value that keeps `MAX_SCALED_BORROWED × MAX_BORROW_INDEX_RAY / RAY ≤ i128::MAX` given the maximum possible scaled borrow (`i128::MAX` shares). At minimum, once the index reaches the point where `borrowed × index` saturates, stop accruing (pin the index) so the market remains operable rather than trapping on every verb.

### Proof of Concept
1. List (or use) a market for an 18-decimal asset with the standard steep-segment curve; lift supply/borrow caps.
2. `supply(hub, BIG18, ~1_000_000_000 × 10^18)` from a whale; `borrow` ~98% of it via a second account with sufficient collateral.
3. Advance ledger time at sustained high utilization. Each `update_indexes` call runs `global_sync` → `accrue_step` → `scaled_to_original(borrowed, borrow_index)`.
4. Once `borrowed × borrow_index / RAY > i128::MAX` — which occurs at borrow_index ≈ 170×, far below `MAX_BORROW_INDEX_RAY = 10^9×` — the call panics with `MathOverflow`.
5. All subsequent `withdraw`, `repay`, `liquidate`, and `update_indexes` calls on that market revert identically; supplier and borrower funds are frozen permanently.

This is reproduced by `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`, which asserts `MATH_OVERFLOW` from `try_update_indexes_for` with `last.borrow_index < MAX_BORROW_INDEX_RAY` and that `try_withdraw_raw` / `try_repay` fail with `MATH_OVERFLOW` afterward.
