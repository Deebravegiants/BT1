This confirms the finding: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers (`lib/shopify_api/webhooks/request.rb:20-32`) and are not part of the HMAC-signed payload. `Utils::HmacValidator.validate` only checks `to_signable_string` against `hmac` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and `Webhooks::Registry.process` passes the unauthenticated `request.shop` straight into the handler as the tenant identifier (`lib/shopify_api/webhooks/registry.rb:188-199`). This is the same class of bug as the report: a field acted on (`shop`) is not covered by the cryptographic check (HMAC), unlike `Auth::Oauth::AuthQuery#to_signable_string`, which does bind `shop` into its signed string (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`).

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by the host application to identify the tenant are taken verbatim from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the body's HMAC and then forwards the unauthenticated `shop` value to the app's webhook handler, breaking the intended binding between "payload verified as authentic" and "shop the payload claims to be for."

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
It returns only `@raw_body`. Meanwhile `shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic verification: [2](#0-1) 
`Utils::HmacValidator.validate_signature` computes the signature strictly from `to_signable_string`: [3](#0-2) 
`Registry.process` validates that HMAC, then immediately hands the unauthenticated `request.shop` to the registered handler as the tenant key: [4](#0-3) 

This is structurally different from `Auth::Oauth::AuthQuery`, where `shop` **is** included in the signed string: [5](#0-4) 

Because the app's `client_secret` (used as the HMAC key) is shared across every merchant that installs the app, and the shop-domain header is excluded from the signature, any party who can obtain one validly-signed `(raw_body, hmac)` pair for the app — trivially available to anyone who installs the app on their own store and receives even a single webhook — can replay that exact body/signature pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The signature check in `Registry.process` still passes because it only re-derives the HMAC from `raw_body`, never touching `shop`. The handler then executes tenant-scoped logic (e.g. session teardown on `app/uninstalled`, GDPR redaction on `shop/redact` or `customers/redact`, state updates on `shop/update`) attributing the request to whichever `shop` the attacker chose in the header, not the shop that actually generated and legitimately signed the body.

### Impact Explanation
This breaks the identity binding: *shop claimed in the unauthenticated header* != *shop the HMAC-signed bytes were actually produced for*. An attacker with only their own (unprivileged) app installation can forge a "verified" webhook event for a completely different, victim shop, causing the host application to mutate or delete that victim's tenant data/session under the belief the event is authentic. This is a cross-tenant access vector consistent with the Critical impact bucket in scope (cross-tenant access via a forged, "verified" cross-tenant webhook).

### Likelihood Explanation
Likelihood is high for any app builder relying on this gem's documented API exactly as shown in `docs/usage/webhooks.md` (`Registry.process` + `Utils::HmacValidator.validate`): the only prerequisite is installing the target app on an attacker-controlled store (an ordinary, unprivileged action any merchant can take) to obtain one legitimate `(body, hmac)` pair, then replaying it to the app's public webhook URL with a substituted `shop-domain` header. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a separate binding check in `Registry.process`) so the tenant-identifying fields, at minimum `shop`, are bound into what is verified — either by requiring the raw body to embed/attest the shop (as Shopify's webhook payloads generally do via a `myshopify_domain`/similar field validated against the header) or, at minimum, by having `Registry.process` cross-check `request.shop` against the shop already known to be associated with the resource contained in `parsed_body`/topic before invoking the handler, rather than trusting the header outright.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `shop/update`) to receive one legitimately Shopify-signed `(raw_body, x-shopify-hmac-sha256)` pair at the app's public webhook endpoint.
2. Replay that exact `raw_body` and `hmac` header to the same public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only from `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — validation succeeds since the body/hmac pair is unchanged.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`) with `shop == "victim.myshopify.com"`, causing the app to execute tenant-scoped logic against the victim shop although the payload was never produced for it.
