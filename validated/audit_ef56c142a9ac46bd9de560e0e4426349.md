## Analog Found

### Title
Backend-pushed config changes are applied mid-signup, allowing fraud/age-safeguard thresholds to change between phases of an already-started signup - (File: `src/config.rs`, `src/brokers/observer.rs`)

### Summary
Analogous to the “new treasury rate applied to an existing loan” bug class, orb-core keeps a single mutable, shared `Config` object (`Arc<Mutex<Config>>`) that is periodically refreshed from the backend in the background and immediately overwrites the previous config in place, without any regard for whether a signup is currently mid-flight. Multiple independent phases of the *same* signup re-read this shared config from scratch, so security-relevant parameters (age/fraud thresholds, self-serve safeguards, QR-validation strictness) that were in effect when the signup began can silently change before the signup completes.

### Finding Description
The `Config` struct carries safety-critical fields such as `child_threshold` (the underage detection threshold), `self_serve_ask_op_qr_for_possibly_underaged` / `..._timeout` (the safeguard requiring an operator QR when a possibly-underage person is detected), `fraud_check_engine_config`, and QR validation strictness flags [1](#0-0) .

This config is downloaded and swapped wholesale in the observer broker on a fixed interval, independent of signup state: [2](#0-1) 

The `before_config_update` hook exists specifically so a `Plan` implementation could gate config swaps during sensitive periods (e.g. an active signup), but the `DefaultPlan` implementation used here simply returns `true` unconditionally, so the update always proceeds: [3](#0-2) [4](#0-3) 

Meanwhile, the signup flow itself does not snapshot the config once at the start of a signup; it re-locks and re-reads `orb.config` fresh at each distinct phase (QR scan, biometric capture, biometric pipeline, etc.), each phase potentially observing a different config value than an earlier phase in the *same* signup, e.g.: [5](#0-4) 

`Config::download_and_store` performs the same unconditional overwrite pattern used elsewhere: [6](#0-5) 

Because the same `Arc<Mutex<Config>>` instance is read independently at each signup phase rather than being captured once as an immutable snapshot for the whole signup transaction, a backend-initiated config change that lands between two phases of one signup changes the rules of that signup after it has already started — exactly the “new rate applied retroactively to an existing agreement” pattern from the referenced report, translated to safety thresholds instead of a fee rate.

### Impact Explanation
If, mid-signup, the backend lowers `child_threshold`, disables `self_serve_ask_op_qr_for_possibly_underaged`, or otherwise loosens `fraud_check_engine_config` between the QR-scan/decision phase and the biometric-capture/pipeline phase, a signup that should have been blocked or escalated to require an operator QR under the original (start-of-signup) policy could instead complete under the new, weaker policy — a fraud/liveness-safeguard bypass for that one, already-in-progress signup. Conversely, a signup could be inconsistently evaluated against two different rule sets across its own phases, producing undefined/inconsistent enforcement (state bleed within a single signup transaction).

### Likelihood Explanation
Config refresh happens automatically on a fixed timer (`CONFIG_UPDATE_INTERVAL`) throughout normal orb operation, so any signup whose duration overlaps a scheduled refresh is exposed; no attacker action is required beyond controlling timing relative to a legitimate backend config push (or, more concerning, the backend itself changing thresholds while orbs are actively mid-signup in the field, matching the exact “admin changes rate on active state” scenario from the report). This is a systemic reachability issue, not a rare race — it will occur on any orb performing a signup whenever a scheduled config refresh coincides with the signup window.

### Recommendation
Snapshot the relevant safety/fraud-relevant config fields (`child_threshold`, `self_serve_ask_op_qr_for_possibly_underaged*`, `fraud_check_engine_config`, QR validation flags) once at signup start and thread that immutable snapshot through all phases of that signup, instead of re-reading the live shared `Config` at each phase. Alternatively, use the existing `before_config_update` hook to defer/reject config swaps while `signup_flag` indicates an active signup, ensuring a signup runs start-to-finish under one consistent policy.

### Proof of Concept
1. Orb begins a signup; QR-scan phase reads `Config` with `self_serve_ask_op_qr_for_possibly_underaged = true` and defers the underage decision, expecting the operator-QR safeguard to trigger later.
2. Backend pushes an updated config (scheduled interval tick) that sets `self_serve_ask_op_qr_for_possibly_underaged = false` and/or lowers `child_threshold`; `config_update` in `src/brokers/observer.rs` overwrites the shared `Config` unconditionally.
3. Biometric-capture/pipeline phase re-reads `orb.config.lock().await` (`src/plans/mod.rs`) and now operates under the new, weaker policy for the *same* signup, bypassing the safeguard that was in effect when the signup started.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
