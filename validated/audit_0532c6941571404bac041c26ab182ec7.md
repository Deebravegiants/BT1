### Title
Webhook `shop` (and topic/webhook-id) identity is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then blindly trusts the `shop-domain` header (along with `topic`/`webhook-id`) as the tenant identity handed to the app's handler. Because the signable string used for HMAC verification is only the raw body, the `shop` field that identifies which merchant/tenant the webhook belongs to is never bound to the signature. Any holder of a single valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own shop and receiving one legitimate webhook — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the library will report it as an authenticated webhook "from" the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from unauthenticated HTTP headers, entirely outside the HMAC computation: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately forwards `request.shop` (and `request.topic`/`request.webhook_id`) to the registered handler as trusted webhook metadata, with no cross-check that the signed body actually originated for that shop: [4](#0-3) 

This breaks the intended identity binding:

`shop authenticated by HMAC` (none — the header is unsigned) **≠** `shop delivered to WebhookMetadata / handler.handle` (attacker-controlled header value)

Since the same `api_secret_key` is shared across every shop that installs the app, and the signature never binds to the shop, a malicious merchant who installs the app on their own store can capture one genuine `(raw_body, hmac)` pair from any webhook topic, then replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the payload to the handler labeled as belonging to the victim shop — a cross-tenant data injection into the app's per-shop processing logic.

### Impact Explanation
This is a cross-tenant confusion inside the gem's own webhook-processing path: an unprivileged attacker (a legitimate merchant of their own shop, without any special access token, secret, or privileged account) can make the library assert that HMAC-authenticated data belongs to a different tenant than the one that actually produced it. Any host application relying on `WebhookMetadata#shop` — the documented, library-provided identity field — to route data, update per-shop records, or make trust decisions is exposed to cross-tenant injection, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
The prerequisite is trivial and available to any unprivileged internet user: install (or already have) the app on one's own shop, trigger any webhook topic, and capture the resulting body + `X-Shopify-Hmac-Sha256` header. No secret material, access token, or privileged position is required — only the ability to receive one webhook the attacker is already entitled to receive.

### Recommendation
Bind the shop identity to the signature verification. Either (a) include the `shop-domain` (and ideally `topic`, `webhook-id`) headers in the signable string used for HMAC computation, matching what Shopify actually signs, or (b) after HMAC validation, independently verify that the delivered `shop` corresponds to a shop with an active, expected session/registration before dispatching to the handler, so a replayed body cannot be relabeled with a different tenant.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a webhook (e.g. `orders/create`). They capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed over `B` using the shared `api_secret_key`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`/`x-shopify-webhook-id` optionally changed as well.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body, believing this authenticated webhook came from the victim's store: [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
