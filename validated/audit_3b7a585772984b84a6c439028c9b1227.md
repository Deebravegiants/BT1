## Analysis Summary

I traced the report's core invariant — "a cached authoritative value (price/fee) is not invalidated when the underlying source of truth changes, allowing accounting to go stale" — to the analogous flow in `coin::maybe_convert_to_fungible_store` in `aptos-move/framework/aptos-framework/sources/coin.move`, where a `CoinStore`'s `frozen` flag is used to overwrite (not merge with) the current `FungibleStore` frozen state during migration, and this migration path is reachable **without any signer authorization** on the target account.

I was not able to fully confirm (due to running out of tool iterations) the exact mechanism by which a `FungibleStore` for a `CoinType`'s paired asset could become frozen independently while the corresponding `CoinStore.frozen` remains `false` (e.g., via a `TransferRef`/`FreezeCapability` applied directly at the FA layer post-pairing) — this is very plausible given `coin::get_paired_transfer_ref`/`return_paired_transfer_ref` expose a `TransferRef` for exactly this purpose, but I could not trace a concrete external call site that does this within the remaining budget. I present the finding with this caveat.

### Title
Permissionless `migrate_coin_store_to_fungible_store` can silently clear the freeze state of a Primary Fungible Store - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin::migrate_coin_store_to_fungible_store` is a fully permissionless `entry` function — it takes a `Vec<address>` with **no signer** — that triggers `maybe_convert_to_fungible_store` for arbitrary accounts. That function reconciles the frozen flag by blindly copying the stale `CoinStore.frozen` value onto the (possibly independently-frozen) `FungibleStore`, without ever reading or merging the FA store's own more up-to-date frozen state, and without any authorization check tying the caller to freeze/compliance authority.

`migrate_coin_store_to_fungible_store` accepts an arbitrary vector of target addresses with **no signer parameter at all** — any account can invoke it against any other account's `CoinStore<CoinType>`. When triggered, `maybe_convert_to_fungible_store` reconciles the frozen flag using a one-directional overwrite: `set_frozen_flag_internal(store, frozen)` sets the `FungibleStore.frozen` field to whatever the (soon-to-be-destroyed) `CoinStore.frozen` was, unconditionally, whenever it differs from the FA store's current frozen state. There is no branch that only *raises* the freeze (i.e. no `OR`-merge of the two frozen states) — a `false` `CoinStore.frozen` always wins and clears an existing `true` frozen flag on the primary fungible store.

Any account holding legacy, non-zero `CoinStore<CoinType>` balance whose primary fungible store was frozen independently (through a `TransferRef`/`FreezeCapability` obtained via `coin::get_paired_transfer_ref`, or directly via `fungible_asset`/`primary_fungible_store` freeze APIs on the paired metadata) can have that freeze silently cleared by anyone calling the permissionless `migrate_coin_store_to_fungible_store`.

### Impact Explanation
This breaks the custody invariant that freeze authority (a compliance/security control tied to `FreezeCapability`/`TransferRef`) must not be revocable by an unprivileged, unrelated caller. If exploited, it allows removal of freeze protection on live fungible-asset holdings, defeating denylist/compliance freeze mechanisms and permitting subsequent unauthorized transfer/withdrawal of the previously frozen balance. This qualifies as "Unauthorized takeover of ... freeze control ... tied to live assets" under the custody impact gate.

### Likelihood Explanation
Medium: it requires (a) a `CoinType` account that still has a non-zero legacy `CoinStore` balance (common for pre-FA-migration accounts) and (b) the associated primary fungible store to have been frozen independently of the `CoinStore.frozen` flag (e.g., issuer applying freeze at the FA layer post-migration-availability, a realistic and increasingly common pattern since `coin`→FA is the framework's intended long-term direction). No special privilege is needed to trigger the call itself.

### Recommendation
In `maybe_convert_to_fungible_store`, never let the migration *unfreeze* the fungible store: only apply `set_frozen_flag_internal(store, true)` when `frozen` (CoinStore) is `true`, and never force it to `false` when the FA store is already frozen (i.e., merge via `is_frozen(store) || frozen` rather than an unconditional overwrite). Additionally, consider whether `migrate_coin_store_to_fungible_store` should require some authorization/relationship to the target `account` rather than being fully permissionless for arbitrary third-party accounts.

### Proof of Concept
1. Token issuer freezes `alice`'s primary fungible store for `CoinType`'s paired FA (e.g., via `TransferRef` obtained by `coin::get_paired_transfer_ref`, then `fungible_asset::set_frozen_flag`/`primary_fungible_store` freeze path) while `alice` still holds a non-zero, unfrozen `CoinStore<CoinType>` balance (`frozen == false`).
2. Any attacker (no relation to `alice`) calls `coin::migrate_coin_store_to_fungible_store<CoinType>(vector[alice_address])`.
3. Inside `maybe_convert_to_fungible_store`, `frozen` (from `CoinStore`, `false`) `!= fungible_asset::is_frozen(store)` (`true`) → `set_frozen_flag_internal(store, false)` executes, clearing the freeze on `alice`'s primary fungible store.
4. `alice` (or anyone with authority over her account) can now freely withdraw/transfer the previously frozen balance, defeating the issuer's freeze control.

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };
    }
