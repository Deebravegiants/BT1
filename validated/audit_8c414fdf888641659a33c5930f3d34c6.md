## Finding: Stale gateway-cached Vault master public key is never invalidated on rotation

### Title
Gateway serves indefinitely-cached, potentially-stale Vault master public key to clients with no TTL/invalidation on rotation - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The Sherlock report's root cause is a two-step update where a derived/cached value (`inflationMultiplier`) can go stale relative to the authoritative source, and unprivileged users end up computing amounts against the wrong value, losing funds. The Vault gateway handler exhibits the same class of bug: it caches the Vault DON's master TDH2 public key returned by `handlePublicKeyGet`/`tryCachePublicKeyResponse`, but the cache has no expiry/invalidation logic tied to the authoritative source (the Vault nodes' actual current key).

### Finding Description
`handler.tryCachePublicKeyResponse` unconditionally stores the first quorum-verified public key response it sees: [1](#0-0) 

`handler.getCachedPublicKey` / `handlePublicKeyGet` then serve this cached value to any subsequent `MethodPublicKeyGet` request from any client, with the only condition being that the cache is non-nil — there is no timestamp comparison, TTL, or expiry check: [2](#0-1) 

A constant `defaultPublicKeyGetCacheDurationSeconds = 300` is declared: [3](#0-2) 

but it is not referenced anywhere else in the cache-read path (`getCachedPublicKey`/`handlePublicKeyGet`), meaning the intended 300-second cache duration is not actually enforced — once populated, `cachedPublicKeyGetResponse`/`cachedPublicKeyObject` are served forever until process restart. This is confirmed by the test `TestVaultHandler_PublicKeyGet`, which shows a request made *long after* the initial cache population still returns the cached key with no re-fetch or freshness check: [4](#0-3) 

This mirrors the reported bug class exactly: the authoritative value (Vault DON's real, possibly-rotated master public key held by the nodes) can diverge from the cached derived value at the gateway, with no mechanism to detect or refresh staleness before it is used by an unprivileged client-facing operation (`vaulttypes.MethodPublicKeyGet`).

### Impact Explanation
If the Vault DON's master public key is ever rotated (key-share refresh, node-set change, disaster recovery, etc.), the gateway will continue to hand out the old, now-invalid public key to every client that calls `PublicKeyGet` — indefinitely, since there is no TTL enforcement. Clients (workflow owners, users) will then encrypt secrets (`EncryptedSecret.EncryptedValue`) against the wrong/stale public key via `core/capabilities/vault/validator.go`'s `verifyEncryptedSecret`/`EnsureRightLabelOnSecret` flow. When these secrets are subsequently submitted for creation, the Vault nodes running the real, current key will fail to decrypt/verify them, silently causing loss/rejection of user secrets analogous to the fund loss in the original report — the user believes they've stored a usable secret, but it is unusable because it was sealed against a public key the network no longer recognizes.

### Likelihood Explanation
This requires an actual key-rotation event on the Vault DON, which is an operational/administrative event rather than something an attacker directly triggers. However, once such a rotation occurs, *every* unprivileged client that queries `PublicKeyGet` through this gateway process (until restart) is silently affected — there's no fallback, no error, no re-fetch trigger. This is a real, concretely reachable path from an unprivileged client request (`MethodPublicKeyGet` has no authorization requirement per the handler flow) and does not depend on malicious peers, mocks, or dependency-only conditions.

### Recommendation
Enforce the already-declared `defaultPublicKeyGetCacheDurationSeconds` (or a configurable equivalent) in `getCachedPublicKey`/`handlePublicKeyGet` by recording the cache-write timestamp in `tryCachePublicKeyResponse` and rejecting/refreshing the cache when `now - cachedAt > cacheDuration`, forcing a fresh `fanOutToVaultNodes` re-fetch and quorum re-verification instead of serving a potentially stale key forever.

### Proof of Concept
1. Gateway node starts; a client calls `PublicKeyGet`; quorum of Vault nodes respond with public key `PK1`; `tryCachePublicKeyResponse` caches `PK1` permanently (see `core/services/gateway/handlers/vault/handler.go:578-581`).
2. Operator rotates the Vault DON's master key to `PK2` (e.g., via key-share ceremony/DKG refresh) — Vault nodes now only accept ciphertexts encrypted under `PK2`.
3. A new client calls `PublicKeyGet` through the same gateway process; `handlePublicKeyGet` returns the still-cached `PK1` (no TTL check, as shown by `getCachedPublicKey` at lines 680-690 and confirmed by `TestVaultHandler_PublicKeyGet` never re-triggering a node fan-out on a second call).
4. Client encrypts a secret against `PK1` and submits `SecretsCreate`; Vault nodes reject/fail verification since they only recognize `PK2`, resulting in silent loss of the secret creation attempt for the unprivileged user — the same "stale authoritative value consumed downstream" failure mode as the original `inflationMultiplier` report.

```go
func (h *handler) tryCachePublicKeyResponse(resp *jsonrpc.Response[json.RawMessage], l logger.Logger) {
	if resp.Result == nil {
		l.Debugw("no result in public key response, not caching")
		return
	}

	r := &vaultcommon.GetPublicKeyResponse{}
	err := h.unmarshal(bytes.NewReader(*resp.Result), r)
	if err != nil {
		l.Debugw("failed to unmarshal public key response, not caching", "error", err)
		return
	}

	if r.PublicKey == "" {
		l.Debugw("no public key in unmarshaled response, not caching", "response", resp, "result", r)
		return
	}
	masterPublicKey := tdh2easy.PublicKey{}
	masterPublicKeyBytes, err := hex.DecodeString(r.PublicKey)
	if err != nil {
		l.Debugw("failed to decode master public key string", "error", err)
		return
	}
	err = masterPublicKey.Unmarshal(masterPublicKeyBytes)
	if err != nil {
		l.Debugw("failed to unmarshal master public key", "error", err)
		return
	}

	h.mu.Lock()
	h.cachedPublicKeyGetResponse = *resp.Result
	h.cachedPublicKeyObject = &masterPublicKey
	h.mu.Unlock()
```

```go
func (h *handler) getCachedPublicKey() ([]byte, *tdh2easy.PublicKey) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	if h.cachedPublicKeyGetResponse == nil {
		return nil, nil
	}
	copied := make([]byte, len(h.cachedPublicKeyGetResponse))
	copy(copied, h.cachedPublicKeyGetResponse)
	cachedPublicKeyCopy := *h.cachedPublicKeyObject
	return copied, &cachedPublicKeyCopy
}

func (h *handler) handlePublicKeyGet(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
	if cachedPublicKey != nil {
		l.Debugw("returning cached public key response")
		return h.sendSuccessResponse(ctx, l, ar, &jsonrpc.Response[json.RawMessage]{
			Version: jsonrpc.JsonRpcVersion,
			ID:      ar.req.ID,
			Method:  ar.req.Method,
			Result:  (*json.RawMessage)(&publicKeyResponseBytes),
		})
	}

	l.Debugw("cache stale: forwarding request to nodes", "now", h.clock.Now())
	return h.fanOutToVaultNodes(ctx, l, ar)
}
```
