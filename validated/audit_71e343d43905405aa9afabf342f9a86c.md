## Title
Updating per-chain asset `Precisions` in `pallet-hyper-fungible-token` mismatches the ERC20-scaled amount already baked into in-flight `send` messages, enabling unbacked mint or fund freezing on delivery - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` stores a mutable, governance-settable `Precisions` map (remote-chain ERC20 decimals per asset) that is read live both when a transfer is dispatched (`send`) and when the corresponding inbound message is later delivered (`on_accept`). The amount carried on the wire is scaled to ERC20 precision once, at `send` time, using whatever `Precisions` value is current then. If governance changes `Precisions` for that `(asset_id, chain)` via `update_token` while the message is still in flight, the receiving side's `convert_to_balance` conversion (run at delivery time) uses the *new* precision instead of the one in effect when the funds were locked/burned, producing a local balance that no longer matches what was actually escrowed/burned on the source side.

### Finding Description
`send()` reads `Precisions::<T>::get(asset_id, destination)` and scales the locally-escrowed/burned amount up to ERC20 units using `convert_to_erc20`, embedding the resulting fixed `U256` amount in the outbound `Message`: [1](#0-0) 

That scaled amount is transmitted as-is; there is no snapshot of the precision that produced it. When the counterpart chain later delivers a `Send` message back to this pallet's `on_accept` (i.e. this pallet as destination for a return/receive), the amount is converted back from ERC20 units to local balance by re-reading `Precisions::<T>::get(local_asset_id, source)` *at that later moment*: [2](#0-1) 

`convert_to_balance` divides by `10^(erc_decimals - local_decimals)`: [3](#0-2) 

`update_token` lets `CreateOrigin` change `config.decimals` (i.e. `Precisions`) for an existing `(asset, chain)` pair at any time, with no check for in-flight messages and no timelock: [4](#0-3) 

This is structurally identical to the `voteFactor` bug: a global scaling factor is applied when a stateful/escrowed action is *initiated* (mint tokens / lock+scale amount) but the *closing* leg of that same action (burn tokens / convert back to local balance on delivery) re-reads the *current* value of the factor instead of the value that was in effect at initiation. Any message dispatched before a precision change and delivered after it is converted with a mismatched divisor:
- If `erc_decimals` is **decreased** by governance after dispatch, the divisor `10^(erc_decimals-local_decimals)` shrinks, so `on_accept` mints/releases **more** local balance than was ever escrowed/burned on the source chain — an unbacked mint against the pallet's escrow account (or unbacked burn-then-overmint for non-native assets).
- If `erc_decimals` is **increased**, the divisor grows and the beneficiary receives **less** than was escrowed, permanently freezing the difference (no accounting path recovers it — the corresponding source-chain escrow debit is already final).

### Impact Explanation
Any decimals/precision correction (a routine, expected governance operation per the docs: "Updates the decimal precision recorded for an asset on specific remote chains") performed while transfers for that `(asset, chain)` pair are in flight causes:
- Unbacked minting/releasing of the native or non-native asset beyond what backing escrow/burn actually occurred (High: theft of pallet-held funds / inflation of a bridged asset's supply), or
- Permanent freezing of the difference for the affected recipient (loss of user funds).

Because native assets are custodied 1:1 in `pallet_account()`, an unbacked-mint scenario can drain the escrow account by having other legitimate withdrawals fail once escrow is insufficient, and for non-native (mint/burn) assets it directly inflates supply beyond what was ever locked cross-chain — both are concrete, permanent loss-of-funds outcomes matching the "unbacked mint or permanent freezing" acceptance criteria.

### Likelihood Explanation
`update_token` is a normal, documented governance/CreateOrigin action (not requiring any malicious intent) used to add chains or correct precision configuration, and there is no invariant preventing it while requests for that pair are outstanding (no drain/quiesce check, no per-message precision snapshot). Any window between a `send` and its `on_accept` delivery — which can span minutes given consensus finality — is enough to trigger the mismatch if governance updates precision in that window, which is a realistic and even routine operational event (fixing a misconfigured decimals value, onboarding a redeployed contract with different decimals, etc.).

### Recommendation
Snapshot the precision used for the amount conversion inside the message itself (or in per-commitment metadata keyed by the request commitment, similar to `FeeMetadata`) at `send` time, and have `on_accept`/`on_timeout` use that snapshotted value rather than re-reading the live `Precisions` map. Alternatively, require `update_token`'s precision change to be blocked or delayed by at least the max timeout window for that chain, or gate it on there being zero pending commitments for the affected `(asset, chain)` pair.

### Proof of Concept
1. Register asset `X` with `Precisions::<T>::get(X, EVM-dest) = 18`.
2. User A calls `send()` for `1_000_000` local units of `X` to `EVM-dest`; the pallet computes `erc20_amount = convert_to_erc20(1_000_000, 18, local_decimals)` and dispatches the message with that fixed `U256` amount. Funds are locked/burned locally now, based on the 18-decimal scaling.
3. Before the message is delivered back (or before the corresponding return leg completes), governance calls `update_token` to change `Precisions::<T>::get(X, EVM-dest)` to `6`.
4. When the `on_accept` path for the return leg (or an analogous inbound message referencing the same `(asset, chain)`) later runs `convert_to_balance` with the now-updated `erc_decimals = 6`, the divisor `10^(6 - local_decimals)` differs from the divisor at step 2 (`10^(18 - local_decimals)`), producing a local amount that no longer matches the value escrowed/burned at step 2 by a factor of `10^12` — either massively over-crediting (unbacked mint) or under-crediting (frozen funds) the beneficiary.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
