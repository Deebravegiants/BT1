### Title
Webhook HMAC only covers the request body, letting an attacker replay a valid webhook payload under a spoofed shop/topic header — cross-tenant webhook confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never covered by the HMAC. `ShopifyAPI::Webhooks::Registry.process` trusts these unsigned headers to route and attribute the webhook (`request.shop`, `request.topic`) after only checking that the body's HMAC is valid. Anyone who can obtain one legitimate `(body, hmac)` pair — trivially available to any merchant who installs the app on their own store and triggers a webhook — can replay that exact body with a forged `shop-domain`/`topic` header to the app's public webhook endpoint, and the signature still validates.

### Finding Description
The bug class from the report is: an owner-supplied value (`_beefyBooster`) is trusted and acted upon without being bound/verified against the thing that actually protects the flow (the vault's approval). The equality that should hold but doesn't here is:

`shop header value trusted by the handler == shop that the HMAC signature actually authenticates`

`ShopifyAPI::Webhooks::Request` builds its authenticated payload from the body only: [1](#0-0) 

- `hmac` is derived from the `hmac-sha256` header.
- `shop`, `topic`, `webhook_id`, `api_version` are derived directly from other headers.
- `to_signable_string` — the only thing actually fed into the HMAC computation — returns `@raw_body`.

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e. the body) and compares it to the `hmac` header using the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` then trusts the (unsigned) `request.shop` and `request.topic` to dispatch to a handler, passing them straight through to app code as authoritative identifiers: [3](#0-2) 

Because `api_secret_key` is one shared secret for the whole app (not per-shop), a valid `(body, hmac)` pair obtained from a webhook delivered to *any* shop that has installed the app remains valid for *any* other `shop-domain`/`topic`/`webhook_id`/`api_version` header combination the attacker chooses to send. The webhook endpoint is a public, unauthenticated HTTP endpoint, so the attacker doesn't need to intercept real Shopify traffic — they only need one legitimate delivery to their own store to harvest a `(body, hmac)` pair, then can freely resubmit it directly to the app's webhook route with a different `shop-domain` header.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: the HMAC is meant to prove "this webhook body genuinely came from Shopify for this app," but the library also implicitly lets host applications treat `request.shop`/`request.topic` as verified. An attacker who controls one legitimate installed shop can cause the app to process arbitrary webhook bodies as if they belonged to a victim shop (e.g. relabeling `shop-domain` to a target store while keeping a body+HMAC pair harvested from their own store, or changing `topic` to trigger a different handler with the same signed body). Depending on the handler logic (e.g. `app/uninstalled`, `shop/redact`, subscription/billing webhooks, or any handler keyed off `data.shop`), this can lead to cross-tenant data corruption, spoofed uninstall/redact actions against a victim shop's stored session, or triggering privileged handler logic under an attacker-chosen shop identity — a cross-tenant access issue.

### Likelihood Explanation
Any user able to install the target app on a shop they control (including a free/dev store) can trigger real webhook deliveries and capture valid `(raw_body, hmac)` pairs from their own genuine webhooks — no access token, `client_secret`, or leaked credential is required. From there, forging headers on a direct POST to the public webhook endpoint is trivial with any HTTP client.

### Recommendation
Bind the trusted headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, `webhook_id`, and `api_version` to the specific delivery instead of trusting them unconditionally once the body HMAC passes. Concretely:
- Include `shop-domain`, `topic`, and `webhook_id` in `to_signable_string` (or verify them against a per-shop record/session lookup) before dispatching to handlers in `ShopifyAPI::Webhooks::Registry.process`.
- At minimum, document/require that host apps independently verify `data.shop` against a known/installed shop list before trusting webhook payloads, since this gem does not bind the shop header to the signature.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook subscribed by the app (e.g. `app/uninstalled`) and capture the raw POST: headers (`x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain`, `x-shopify-webhook-id`, `x-shopify-api-version`) and raw body.
3. Resend that exact raw body and `hmac-sha256` header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally `x-shopify-topic` with another registered topic that accepts the same body shape).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still returns `true` because it only checks the body against the shared `api_secret_key`; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) then invokes the handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this webhook.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
