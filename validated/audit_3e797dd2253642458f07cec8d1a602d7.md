### Title
Oracle `latestRoundData()` lacks `roundId` check, leading to potential staleness - ([Project: listadao] [File: lista-dao-contracts/contracts/oracle/wstETHOracle.sol])

### Summary
The `listadao` project's `wstETHOracle.sol`, `xSolvBtcOracle.sol`, and `BusdOracle.sol` contracts, which implement the `peek()` function, do not check the `roundId` when calling `AggregatorV3Interface(wstETHPriceFeed).latestRoundData()`. This omission can lead to the oracle returning stale price data, as the validity flag is hardcoded to `true` and the `updatedAt` timestamp is discarded.

### Finding Description
The `peek()` function in `wstETHOracle.sol` (and similarly in `xSolvBtcOracle.sol` and `BusdOracle.sol`) retrieves price data from a Chainlink `AggregatorV3Interface` using `latestRoundData()` . However, it explicitly discards the `updatedAt` timestamp and hardcodes the validity flag to `true` . Furthermore, there is no check on the `answeredInRound` or `roundId` to ensure the completeness or freshness of the round . This means that even if the Chainlink feed is stale, the oracle will report the price as valid and current.

### Impact Explanation
The absence of a `roundId` check and the hardcoding of the validity flag to `true` can result in the protocol using stale price data . In a CDP (Collateralized Debt Position) system, if the real price of an asset falls while the oracle provides a stale, higher price, users could borrow against overvalued collateral, leading to bad debt for the protocol . Conversely, if the stale price is artificially low, liquidations might not trigger when they should, also impacting protocol health .

### Likelihood Explanation
The likelihood of this vulnerability being exploited is medium. While it requires a Chainlink feed to become stale, the lack of checks within the oracle contract means that the protocol itself has no internal mechanism to detect and react to such staleness . The `listadao` project's `SCOPE.md` does not include a "Primacy of Impact" clause, and these specific oracle contracts (`wstETHOracle`, `xSolvBtcOracle`, `BusdOracle`) are not listed as in-scope assets . However, the issue is a clear defect, as other in-scope oracles within the same project correctly handle staleness and validity checks .

### Recommendation
Add a `roundId` check to ensure the completeness of the round and validate the `updatedAt` timestamp against a maximum staleness threshold. The validity flag should reflect the actual freshness of the data. An example of a correct implementation can be seen in `listadao`'s `ResilientOracle` or `velvet-capital-v2`'s `PriceOracleL2`, which includes checks for sequencer uptime, grace periods, staleness, and price positivity .

### Proof of Concept
The `peek()` function in `lista-dao-contracts/contracts/oracle/wstETHOracle.sol` demonstrates the vulnerability :

```solidity
function peek() public view returns (bytes32, bool) {
    (
    /*uint80 roundID*/,
      int256 wstETHPrice,
    /*uint startedAt*/,
    /*uint256 updatedAt*/,      // <-- deliberately discarded
    /*uint80 answeredInRound*/
    ) = AggregatorV3Interface(wstETHPriceFeed).latestRoundData();

    return (bytes32(uint256(wstETHPrice * 1e10)), true);   // <-- validity hardcoded
}
``` 

This code snippet shows that `updatedAt` is commented out and effectively discarded, and the function always returns `true` for the validity flag, regardless of the actual freshness of the price data . There is no check for `roundID` or `answeredInRound` to ensure the data is from a complete and recent round .

## Notes
The `issues.md` file in `AuditingProject/AllProjects` explicitly discusses this exact vulnerability as F-18, noting that these specific oracles are out of scope for the `listadao` program but are a clear defect . It also highlights that other in-scope oracles within the same directory correctly implement staleness checks, reinforcing that this is a bug and not an intentional design choice . The `velvetcapital` project's `PriceOracle` (F-19) also had a related issue with incomplete sign checks, which was later corrected in `velvet-capital-v2` to include a more robust validation (`price <= 0`) .
