### Title
POA Bridge withdrawal status/hash misreport when batching multiple withdrawals of the same asset in one intent - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary
The SDK explicitly supports batch withdrawals of multiple assets in a single intent/transaction [1](#0-0) . For the PoA bridge route, `describeWithdrawal()` and `waitForWithdrawalCompletion()` both resolve which entry in the bridge indexer's `withdrawals[]` array corresponds to a given withdrawal identifier by matching **only on `assetId`** (derived from `near_token_id`), never by index, amount, or destination address [2](#0-1) [3](#0-2) . If a single NEAR transaction contains two or more `ft_withdraw` intents for the same underlying token (e.g. two USDC withdrawals to two different destination addresses/amounts within one batch), the matcher returns the **first** withdrawal in the array whose `near_token_id` matches, regardless of which specific withdrawal (by index) the caller is asking about.

### Finding Description
`createWithdrawalIdentifier()` builds a `WithdrawalIdentifier` that carries an `index` field [4](#0-3) , intended to disambiguate multiple withdrawals from the same NEAR transaction. However, `describeWithdrawal()` never uses `args.index` when querying withdrawal status; it only forwards `args.withdrawalParams.assetId` to `findMatchingWithdrawal()`:

```
async describeWithdrawal(...) {
  const response = await this.getWithdrawalStatusWithRetry(args);
  // Response list is unsorted, so we match by assetId instead of index
  const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
  );
  ...
}
``` [5](#0-4) 

```
function findMatchingWithdrawal(withdrawals, assetId) {
  return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [2](#0-1) 

The same pattern exists in the standalone `waitForWithdrawalCompletion` used by `internal-utils`, which also matches only by `assetId` [6](#0-5) [3](#0-2) . The code comment on both copies of `findMatchingWithdrawal` acknowledges the gap directly: *"NOTE: Currently only matches by assetId... This means multiple withdrawals of the same token in a single transaction are not supported."*

The SDK's own batch-withdrawal API (`sdk.processWithdrawal`, `sdk.signAndSendWithdrawalIntent`, `createWithdrawalCompletionPromises`) does allow the caller to submit an array of `withdrawalParams`, each with its own `destinationAddress`/`amount`, in a single intent [7](#0-6) [8](#0-7) , and there is no validation that rejects duplicate `assetId`s within one batch. If a caller submits two PoA-bridge withdrawals of the same token (e.g., splitting a USDC payout between two customers/destinations in one intent), `describeWithdrawal(index=1)` will return the same indexer entry/tx hash that was already returned for `describeWithdrawal(index=0)` — the entry for the *other* withdrawal, not the one actually associated with `index=1`.

### Impact Explanation
This breaks the equality between "the destination hash/status reported for withdrawal N" and "the actual on-chain outcome of withdrawal N". An integrator polling `describeWithdrawal`/`waitForWithdrawalCompletion` per index (as the SDK's own granular batch APIs, e.g. `createWithdrawalCompletionPromises`, encourage) could:
- Report withdrawal #1 (to destination B) as "completed" with the destination tx hash that actually paid destination A, causing the integrator to credit/confirm the wrong customer's payout and potentially also treat destination B's still-pending withdrawal as done.
- This maps to the rule's High-severity category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no privileged access — any normal SDK user constructing a batch withdrawal with two same-asset entries (a legitimate, encouraged use case per the README's batch-withdrawal documentation) triggers the mismatch. It does not require any malicious counterparty; it is a straightforward consequence of the documented batch-withdrawal feature colliding with an acknowledged (but unresolved) matching limitation in `findMatchingWithdrawal`.

### Recommendation
Match withdrawals using more than `assetId`: incorporate `destinationAddress` and `amount` (and/or stable ordering by amount as the existing code comment suggests) so that each `WithdrawalIdentifier.index` maps deterministically to the correct indexer entry when multiple withdrawals share the same asset in one transaction. Until fixed, the SDK should either validate/reject batches containing duplicate `assetId` for PoA-bridge routes, or clearly document this as an unsupported configuration and have `describeWithdrawal` throw rather than silently return a possibly-wrong match.

### Proof of Concept
1. Submit a batch withdrawal via `sdk.signAndSendWithdrawalIntent({ withdrawalParams: [ {assetId:"nep141:usdc.omft.near", amount: A, destinationAddress: addrA}, {assetId:"nep141:usdc.omft.near", amount: B, destinationAddress: addrB} ] })`, both routed through the PoA bridge.
2. After settlement, call `bridge.describeWithdrawal()` for `index: 0` and `index: 1` using the same NEAR tx.
3. Once the indexer's `getWithdrawalStatus` response contains both withdrawal entries, both `describeWithdrawal` calls call `findMatchingWithdrawal(withdrawals, "nep141:usdc.omft.near")`, which returns the **same** (first) entry for both indices — demonstrated directly by the existing unit test "matches withdrawal by assetId, not by index" in `poa-bridge.test.ts` [9](#0-8) , which only differs in that its two withdrawals have different `assetId`s — when both entries instead share the same `assetId`, `.find()` returns the array's first element for every call, misreporting withdrawal #1's status/hash with withdrawal #0's data.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	async processWithdrawal(
		args: ProcessWithdrawalArgs<WithdrawalParams | WithdrawalParams[]>,
	): Promise<WithdrawalResult | BatchWithdrawalResult> {
		const withdrawalParams = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation
					: [args.feeEstimation];
			}

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
			logger: args.logger,
		});

		if (!Array.isArray(args.withdrawalParams)) {
			return {
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				feeEstimation: feeEstimation[0]!,
				intentHash,
				intentTx,
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				destinationTx: destinationTx[0]!,
			};
		}

		return {
			feeEstimation,
			intentHash,
			intentTx,
			destinationTx,
		};
	}
