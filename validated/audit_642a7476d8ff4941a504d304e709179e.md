### Title
Webhook Shop Identity Spoofing via HMAC Validation That Covers Only the Raw Body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` value used to build the `WebhookMetadata` passed to the app's handler is taken from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the signed material. An attacker who owns any shop with the app installed can capture one of their own genuinely-signed webhook deliveries and replay it to the app's webhook endpoint with an arbitrary `shop-domain` header, and the HMAC check will still pass because that header is not part of the signable string.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over that signable string and compares it against the `hmac` header value: [2](#0-1) 

The `shop` accessor used downstream is read directly from the unauthenticated `shop-domain` header: [3](#0-2) 

`Registry.process` validates only the HMAC, then forwards `request.shop` — unauthenticated — straight into the `WebhookMetadata` delivered to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted upon by the handler`. Here the equality is broken: the HMAC binds only `(raw_body, api_secret_key)`, while `shop` is an independent, attacker-controlled header. Because `api_secret_key` is shared by the app across every merchant that installs it, an attacker who legitimately installs the app on a shop they control receives real webhook deliveries signed with that same shared key. They can replay the exact `(raw_body, hmac)` pair while substituting the `shop-domain` header for a victim shop, and `HmacValidator.validate` will still return true since the header plays no role in the signature.

The gem's own documentation guides host apps to trust `data.shop` for shop-scoped follow-up work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and explicitly describes `Registry.process` as verifying "the request did indeed come from Shopify" — which overstates what is actually verified (body integrity only, not shop provenance): [5](#0-4) [6](#0-5) 

### Impact Explanation
This allows an attacker who has installed the app on any shop (including a free/dev store they control) to forge webhook deliveries that appear to originate from an arbitrary victim shop domain, using a validly-signed payload from their own store. Because the gem's documented handler contract exposes `data.shop` as the authoritative shop for the event and the HMAC check passes, a host app following the gem's documented pattern will process attacker-controlled body content under a forged tenant identity — a cross-tenant boundary violation rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` implementation.

### Likelihood Explanation
Likelihood is meaningful: no secret leakage or privileged access is required beyond installing the app on a shop the attacker controls (a normal, often self-serve action for Shopify apps), and only a header substitution is needed on replay — no cryptographic material or additional guessing is required since the shop field is entirely outside the signed scope.

### Recommendation
Bind the shop domain into the signed material or otherwise authenticate it against the topic/session context, e.g.:
- Compute the HMAC signable string over a canonical combination that includes `shop-domain`, `topic`, and `webhook-id` in addition to the raw body (this would require Shopify-side changes) — or, at minimum,
- Cross-check `request.shop` against a shop your app has an active, registered webhook subscription/session for the given `webhook_id`/`topic`, rejecting deliveries for shops that have no such registration.
- Update `docs/usage/webhooks.md` and the `Registry.process` documentation to accurately state that only body integrity (not the shop header) is verified, and explicitly warn implementers not to trust `data.shop` without independently confirming it against known/registered shop sessions.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid_hmac_of_body_with_shared_secret>`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` line 16, `lib/shopify_api/webhooks/request.rb` line 37).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)` (`lib/shopify_api/webhooks/registry.rb` line 198), even though this data never originated from `victim-shop.myshopify.com`.
