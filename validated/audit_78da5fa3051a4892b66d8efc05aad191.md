## Title
Webhook HMAC Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The bug class in the M-1 report is "an action is performed on an identity (the recipient of the mint) without validating that the identity can safely receive it." The direct analog here is that `ShopifyAPI::Webhooks::Registry.process` treats a webhook request as "verified" and trusts its `shop` field for tenant attribution, but the HMAC signature that supposedly proves authenticity never actually covers that `shop` field.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header: [2](#0-1) 

`Registry.process` validates the HMAC only against that signable string, and then immediately builds the `WebhookMetadata` handed to the app's handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are part of the signed bytes: [3](#0-2) 

`Utils::HmacValidator.validate` simply HMACs `verifiable_query.to_signable_string` (the body) and compares it to the header-supplied HMAC: [4](#0-3) 

The equality this breaks is: `shop authenticated by HMAC == shop used as the tenant key passed to the handler`. In reality, the gem only proves `body authenticated by HMAC`; `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header values that ride along unchecked. The docs even claim the opposite — that `Registry.process` "will verify the request did indeed come from Shopify" — reinforcing that host apps are expected to trust `data.shop` as the tenant identity without further checks: [5](#0-4) <br> [6](#0-5) 

Because a single app's `api_secret_key` is shared across every shop that installs it, any unprivileged internet user can self-install the app on their own shop, legitimately receive real webhooks for that shop (valid body + valid HMAC), and then replay that exact (body, HMAC) pair to the app's public webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. `Registry.process` still passes HMAC validation (it never looked at the header), and the handler receives `WebhookMetadata` claiming the attacker's body belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: attacker-controlled data is attributed to a victim shop that the attacker does not control or have credentials for, purely because the gem's "authenticity" check does not bind the header-derived shop to the signed payload. Depending on what the host app does with `data.shop` (queue jobs, write to shop-scoped records, trigger shop-scoped side effects as shown in the docs example `perform_later(topic:, shop_domain: data.shop, webhook:)`), this allows an attacker to inject spoofed events into a victim tenant's data pipeline — a cross-tenant access impact.

### Likelihood Explanation
Requires no secrets, access tokens, or privileged access — only that the attacker install the app on their own shop (a normal, unprivileged action) and know/guess a victim shop's domain, which is public information (`*.myshopify.com`). The webhook endpoint is internet-reachable by design.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the request body before trusting it, e.g., by having `Registry.process` re-derive/validate `shop` against a value that is itself covered by the signature, rather than accepting it as an independent unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because HMAC(secret, B) == H), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — passes.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
