### Title
Webhook HMAC signs only the raw body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` accepts any `shop`/`topic` header pair as long as the (unrelated) body's HMAC checks out. This breaks the identity binding `shop authenticated == shop trusted by the handler`: any unprivileged internet user who legitimately receives one signed webhook (e.g., by installing the app on their own store) can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`) header, and the HMAC check still passes.

### Finding Description
The webhook signature is computed and verified purely from the request body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived values to build the object handed to the app's handler: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) only re-computes the HMAC over `verifiable_query.to_signable_string`, i.e. the raw body, using the shared `Context.api_secret_key`. Because the `api_secret_key` is one value per app (shared across every merchant/shop that has installed the app), and the signed material excludes `shop-domain`/`topic`, the equality the code implicitly relies on is:

`HMAC(secret, body) valid ⇒ (shop, topic) in this request == (shop, topic) Shopify actually sent`

This equality does not hold. An unprivileged user can:
1. Install the target Shopify app on their own store (no special privilege required — any merchant can install a public app).
2. Receive a legitimately-signed webhook `(body B, hmac H)` for their own shop/topic from Shopify.
3. Send an HTTP POST directly to the app's public webhook endpoint with the same `body B` and `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain` set to a victim shop (any other shop that has installed the app) and/or a different `x-shopify-topic`.
4. `HmacValidator.validate` still succeeds because it only checks `B` against `H`; `Registry.process` then dispatches `WebhookMetadata` carrying the attacker-chosen `shop`/`topic` to the handler, which the host app trusts as if Shopify sent it for that tenant.

This is exactly the "field acted on but not covered by the HMAC" pattern: `shop` and `topic` are used by the handler as the tenant/action identity, yet are excluded from the signed bytes.

### Impact Explanation
Any host application handler that keys tenant-scoped actions off `WebhookMetadata#shop` (e.g., "update order status for shop X", "delete data for shop X", "disable subscription for shop X") can be tricked into performing that action against an arbitrary victim shop's tenant record, using body content controlled/obtained by the attacker's own store. This is a cross-tenant access primitive obtainable by any unprivileged merchant who can install the app, satisfying the Critical "cross-tenant access" impact category — no leaked credentials, `api_secret_key`, or access token are needed.

### Likelihood Explanation
Likelihood is high for any app that exposes a webhook endpoint and relies on this gem's `Registry.process`/`Webhooks::Request` for authentication: installing a public app on one's own store and capturing a webhook is trivial and requires no special access; forging the replay request only requires basic HTTP tooling.

### Recommendation
Include `shop-domain` and `topic` (and any other header fields the handler relies on) in the signed/verified material, or otherwise cryptographically bind them to the body before dispatching to handlers — e.g., verify that the HMAC covers a canonical string composed of body + shop + topic, matching what Shopify actually intends to authenticate, instead of trusting header values that sit outside the HMAC-protected payload.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com", has installed the target app,
# and receives a legitimate webhook for it.
raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), shared_api_secret_key, raw_body)

forged_headers = {
  "x-shopify-topic"        => "orders/create",        # attacker-chosen topic
  "x-shopify-hmac-sha256"  => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (only raw_body is verified);
#    handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {"id"=>123})
```
