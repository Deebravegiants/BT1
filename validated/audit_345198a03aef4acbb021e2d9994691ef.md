Webhook Shop/Topic Identity Not Bound by HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC that covers only the raw request body, while the shop identity that the app subsequently trusts (`WebhookMetadata#shop`) comes from an HTTP header that is not part of the signed data. Any party who can obtain one valid `(body, hmac)` pair — such as a merchant who has legitimately installed the app on their own store and receives real webhook deliveries for it — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` (and `topic`/`webhook-id`) header for a different, victim shop. The signature still validates because the signature was never computed over those headers, so the app processes attacker-supplied body content under a spoofed victim tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers with no cryptographic binding to the body or the signature: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then trusts `request.shop`/`request.topic` verbatim to build `WebhookMetadata`, which is handed to the app's handler as the authoritative tenant identity: [4](#0-3) [5](#0-4) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (the raw body) and compares it against the supplied `hmac`: [6](#0-5) [7](#0-6) 

This breaks the identity binding: `shop authenticated (via HMAC) == "no shop at all, only body bytes"`, while `shop stored/used as tenant key == header value, fully attacker-controlled`. The equality the code implicitly assumes — that the header-derived `shop` equals the shop that produced the signed body — does not hold, because the signature never covers the header.

### Impact Explanation
An attacker who has installed the app on their own store (an ordinary, unprivileged merchant — no special credentials, access tokens, or `client_secret` needed) legitimately receives real webhooks with valid `(body, hmac)` pairs for their own shop. Since the HMAC does not cover the `shop-domain` header, the attacker can resend that exact body/HMAC to the app's public webhook callback endpoint with the `shop-domain` header changed to a different, victim shop's domain. `Registry.process` will accept the HMAC as valid (since it is valid for that body) and dispatch to the handler with `WebhookMetadata.shop` set to the victim's domain. Any app logic that uses this to update per-shop state, look up/select the shop's session, or process shop-scoped mutations (e.g., `shop/redact`, `customers/redact`, `customers/data_request`, or product/order sync handlers) will act on the victim tenant using attacker-supplied body content — a cross-tenant integrity/data-confusion issue reachable without any privileged credential.

### Likelihood Explanation
Requires only that the attacker be able to install/run the app on a shop they control (a normal, unprivileged action) to obtain valid `(body, hmac)` samples, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which by definition must be internet-reachable to receive Shopify webhooks). No secret, access token, or elevated privilege is needed to forge the tenant-identifying header. The likelihood is moderated only by the fact that body content is fixed to whatever the attacker's own shop generated (they cannot choose arbitrary JSON payloads, only replay real bodies from their own shop's events), but topic/shop/webhook_id/api_version headers can be freely chosen.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material verified against the HMAC, or otherwise cryptographically bind them (e.g., require the app to independently confirm, via a signed/immutable channel, that the claimed shop actually owns the webhook subscription/`webhook_id` before trusting `WebhookMetadata.shop`). At minimum, document that `WebhookMetadata.shop`/`topic` are not covered by the Shopify signature so integrators do not treat them as authenticated tenant identifiers on their own.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g. updates a product), causing Shopify to deliver a legitimate webhook to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`).
2. Attacker captures `(B, H)` (they own this shop, so this is trivially observable, e.g. via their own logging proxy).
3. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because `to_signable_string` only covers `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `topic`/`webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all header checks pass) and `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B`. [8](#0-7) 
5. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the body content and signature both originate from the attacker's own shop, demonstrating cross-tenant identity confusion driven entirely by an unauthenticated header.
