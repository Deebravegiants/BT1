## Title
Unchecked arithmetic panic in `swap_token_amount_base_out` triggerable by attacker-chosen `amount_out` before bounds validation - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` compute the AMM invariant swap amount via `Calculator::swap_token_amount_base_out` **before** validating that the requested `amount_out` is smaller than the pool's available liquidity. Inside that math routine, the denominator is computed with `checked_sub(amount_out).unwrap()`. Any unprivileged caller can submit a `SwapBaseOut`/`SwapBaseOutV2` instruction with an `amount_out` value greater than or equal to the pool's `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`), causing the subtraction to underflow to `None` and the `.unwrap()` to panic, aborting the transaction with an uncontrolled runtime panic instead of a graceful `AmmError`.

### Finding Description
In `program/src/math.rs`, `Calculator::swap_token_amount_base_out`: [1](#0-0) 
computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (Coin2PC direction) or the analogous coin-side subtraction for PC2Coin — with no bound check on `amount_out` relative to pool totals at the point of the call.

In `program/src/processor.rs::process_swap_base_out`, this function is invoked at: [2](#0-1) 
immediately after determining `swap_direction`, while the actual sanity check `if swap.amount_out >= total_pc_without_take_pnl { return Err(AmmError::InsufficientFunds.into()); }` only happens later, inside the token-transfer `match` block: [3](#0-2) 

The same ordering bug exists in `process_swap_base_out_v2`, which calls the identical math function before its own equivalent bounds check: [4](#0-3) 

Both `SwapBaseOut(SwapInstructionBaseOut)` and `SwapBaseOutV2` instructions are fully unprivileged: only the user's own wallet needs to sign (`user_source_owner.is_signer` check), and `amount_out`/`max_amount_in` are attacker-supplied instruction data with no upper bound enforced prior to reaching the vulnerable math call.

### Impact Explanation
Any user who is allowed to swap against the pool (pool status permits swaps) can submit `amount_out` (or `max_amount_in` derived math for `swap_token_amount_base_out`) larger than the pool's current available token balance for the requested output side. The subtraction inside `swap_token_amount_base_out` underflows and the ensuing `.unwrap()` panics, aborting the instruction with a runtime panic rather than returning `AmmError::InsufficientFunds`/`AmmError::CalculationExRateFailure` as intended. This is a robustness/DoS-class bug analogous to the go-ethereum `GetProofsV2` panic: a value taken directly from an untrusted request is used in an arithmetic operation without first validating it against a safe bound, and the resulting failure mode is an uncontrolled panic instead of the intended graceful error path.

### Likelihood Explanation
Trivial to trigger — no special account permissions, no race condition, and no privileged signer are required. Any swapper can construct a `SwapBaseOut`/`SwapBaseOutV2` instruction with `amount_out` set at or above the pool's current opposite-side balance (easily readable on-chain) and submit it in a single transaction.

### Recommendation
Move the bounds check (`amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) to occur *before* calling `Calculator::swap_token_amount_base_out`, and additionally replace the raw `.unwrap()` in `swap_token_amount_base_out` with a `checked_sub(...).ok_or(AmmError::CalculationExRateFailure)?` (or equivalent) so any residual edge case returns a controlled program error rather than panicking.

### Proof of Concept
1. Attacker identifies a live pool and reads `amm_pc_vault`/`amm_coin_vault` balances (or `total_pc_without_take_pnl`/`total_coin_without_take_pnl` via the accounting formula).
2. Attacker submits a `SwapBaseOut` (or `SwapBaseOutV2`) instruction with `swap.amount_out` set to a value `>= total_pc_without_take_pnl` (for the Coin2PC direction) — direction is chosen simply by setting `user_source`/`user_destination` mints accordingly.
3. Execution reaches `Calculator::swap_token_amount_base_out` at `program/src/processor.rs:2172` before the `amount_out >= total_pc_without_take_pnl` guard at line 2213 is ever evaluated.
4. `total_pc_without_take_pnl.checked_sub(amount_out)` returns `None`; `.unwrap()` panics inside `program/src/math.rs:341`, aborting the transaction with an uncontrolled runtime panic instead of the intended `AmmError`.
