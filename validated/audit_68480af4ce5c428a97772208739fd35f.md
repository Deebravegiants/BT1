## Comparative Summary: Cosmos SDK OCC vs. Aptos Block-STM (Custody-Relevant Differences)

### 1. Abort signaling mechanism

**Cosmos SDK (sei-cosmos)**: Uses Go `panic`/`recover` to signal an OCC abort out of deep call stacks. When `mvkv::Get` encounters an `Estimate` value, it pushes an abort to a channel *and* panics with the abort value, relying on a specific recovery middleware in `runTx` to catch it and route the transaction back to the scheduler.

**Aptos Block-STM**: Uses typed, explicit `Result`/enum propagation instead of panic-based control flow. Dependency/estimate conditions are represented as distinguishable error variants — `MVDataError::Dependency`, `MVGroupError::Dependency`, `MVDelayedFieldsError::Dependency` — that bubble up through ordinary `Result` returns. [1](#0-0) [2](#0-1) 

**Custody implication**: The Cosmos design creates a class of bug where any intermediate `recover()` (e.g., an unrelated EVM panic handler) can intercept and mishandle the abort signal, potentially letting the scheduler treat a legitimate OCC abort as a fatal error or vice versa — corrupting execution ordering and, in the worst case, committed state. Aptos's typed-error approach structurally avoids this failure mode because there is no generic `panic`/`catch_unwind` boundary that unrelated code could intercept.

### 2. Execution status classification

Aptos explicitly distinguishes abort causes via the `ExecutionStatus` enum (`Success`, `SkipRest`, `SpeculativeExecutionAbortError`, `Abort`, `DelayedFieldsCodeInvariantError`), each routed to specific handling logic rather than inferred from a caught panic value. [3](#0-2) 

Speculative aborts due to a stale/Estimate read surface as a specific status code (`StatusCode::SPECULATIVE_EXECUTION_ABORT_ERROR`) rather than an opaque panic payload, so downstream code can't confuse it with an application-level abort. [4](#0-3) 

### 3. Two-phase abort protocol vs. single-shot panic

Aptos's scheduler (both V1 and BlockSTMv2) implements a formal two-step abort: `start_abort` (test-and-set) followed by `finish_abort`, guarded by strict incarnation-matching invariants that return `PanicError` (an internal invariant-violation type, not a Rust panic) if state is inconsistent. [5](#0-4) [6](#0-5) 

This is a stateful, race-checked handshake rather than a single unwind event, making it much harder for an abort to be "lost" or misrouted mid-flight — the exact failure class the Cosmos report describes.

### 4. Cleanup on abort

When Aptos aborts a transaction, cleanup (marking modified keys/groups/delayed fields as `Estimate`, clearing speculative logs) is a dedicated function called deterministically as part of the abort transition, not something that must survive an unwind path. [7](#0-6) 

### Bottom line

The Cosmos SDK bug class hinges on overloading `panic`/`recover` as an abort-signaling channel, which is fragile because any unrelated `recover()` in the call stack can swallow or misinterpret the signal. Aptos's Block-STM avoids this entire bug class by using explicit, strongly-typed status/error propagation (`ExecutionStatus`, `MVDataError`, `PanicError`) with a formal two-phase scheduler state machine, so there is no generic panic-catching boundary through which an OCC abort signal could be intercepted or lost. This is an architectural difference, not merely a patched instance of the same bug — I found no local Aptos code path that reproduces the "panic caught before reaching abort-recovery" pattern with an independently provable custody-grade impact.

    pub(crate) fn finish_abort(
        &self,
        txn_idx: TxnIndex,
        aborted_incarnation: Incarnation,
        start_next_incarnation: bool,
    ) -> Result<(), PanicError> {
        let status = &self.statuses[txn_idx as usize];
        let new_incarnation = aborted_incarnation + 1;
        if status.next_incarnation_to_abort.load(Ordering::Relaxed) != new_incarnation {
            // The caller must have already successfully performed a start_abort, while
            // higher incarnation may not have started until the abort finished (here).

                "Finish abort of incarnation {}, self.next_incarnation_to_abort = {}",
                aborted_incarnation,
                status.next_incarnation_to_abort.load(Ordering::Relaxed),
            )));
        }
