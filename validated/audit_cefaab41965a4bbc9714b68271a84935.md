### Title
Webhook HMAC signs only the request body, allowing replay with a spoofed `shop-domain` header to impersonate any tenant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `topic`, `shop`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are never included in the HMAC-signed material. `Registry.process` treats a passing HMAC check as proof that the *entire* webhook request (including `shop`) is authentic, but the binding only covers the body bytes.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `hmac`, `topic`, `shop`, `api_version`, `webhook_id` are all parsed independently from headers: [2](#0-1) 

`Registry.process` validates only this body-scoped HMAC and then trusts `request.shop`/`request.topic` unconditionally to build `WebhookMetadata` passed to the handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) against `Context.api_secret_key`: [4](#0-3) 

This breaks the identity binding `shop_claimed_by_request == shop_bound_by_HMAC`: the HMAC only proves `body_received == body_signed_by_Shopify`; it says nothing about which shop, topic, or webhook id that signature was originally issued for.

### Impact Explanation
Because the `shop-domain` header is completely outside the HMAC's coverage, a real webhook body+HMAC pair legitimately obtained for one shop can be replayed against the app's webhook endpoint with the `shop-domain` header changed to an arbitrary victim shop. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate` passes) and hand the handler a `WebhookMetadata` claiming the event came from the victim shop, even though it did not. Any host application logic keyed off `data.shop` (e.g., looking up the victim's stored session/access token, updating victim-tenant records, or triggering merchant-facing side effects) can be manipulated into acting on behalf of the wrong tenant. This is a cross-tenant impersonation vector at the gem layer, independent of what the host app does with the data.

### Likelihood Explanation
The prerequisite is only the ability to receive one legitimate webhook of any topic (achievable via a free/dev Shopify store where the attacker installs their own app instance, or is otherwise associated with any shop that has the app installed) and the ability to send arbitrary HTTP POST requests to the app's public webhook endpoint with attacker-chosen headers. No knowledge of `api_secret_key`, access tokens, or any privileged Shopify data is required — only headers are being manipulated by an ordinary internet client with a previously-captured (or self-generated) body/HMAC pair. This is fully reachable by an unprivileged actor.

### Recommendation
Include the identity-relevant fields (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the signature (e.g., have `to_signable_string` concatenate the headers with the body before hashing), so that any header tampering invalidates the signature. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` as authenticated values distinct from what was actually signed.

### Proof of Concept
1. Attacker creates/uses a Shopify dev store `attacker-shop.myshopify.com`, installs the app, and triggers a webhook (e.g., `orders/create`). Shopify sends a legitimate request with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures `B` and the HMAC header value.
3. Attacker sends a new POST request directly to the app's registered webhook endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = captured HMAC (unchanged)
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (changed)
   - `x-shopify-topic` = same or different registered topic
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches — validation passes.
5. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, believing the event genuinely originated from the victim shop, despite no cryptographic binding between the signature and the `shop` value.
