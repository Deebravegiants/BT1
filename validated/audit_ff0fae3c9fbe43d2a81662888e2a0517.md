### Title
Unguarded zero-amount ERC20 transfer in Tron `IntentGatewayV2.withdraw` can permanently freeze escrowed funds on RedeemEscrow/RefundEscrow delivery - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of the Intent Gateway's `withdraw` function transfers every token entry in a `WithdrawalRequest` unconditionally, with no `amount == 0` guard, unlike the parallel EVM implementation. A zero-amount transfer to a "weird" ERC20 (one that reverts on a zero-value `transfer`, per the referenced weird-erc20 catalogue) will cause the entire `withdraw` call, and therefore the entire cross-chain message delivery (`onAccept`), to revert.

### Finding Description
`IntentGatewayV2.withdraw` on the Tron deployment iterates over `body.tokens` and calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for every entry without checking `amount > 0`: [1](#0-0) 

This is different from the canonical EVM implementation of the same logic in `IntentsBase._withdraw`, which explicitly skips zero-amount entries: [2](#0-1) 

`withdraw` is invoked from `onAccept` for both `RedeemEscrow` (delivered after a solver fills an order via `fillOrder`) and `RefundEscrow` (delivered after a user/solver cancels an order), both of which are unprivileged, attacker/solver-reachable paths — any user can construct an order whose input token list includes a zero-value entry (or whose fill/refund path yields a zero-amount escrow release for a given token, e.g., a token that was fully consumed by a prior partial fill leaving nothing left to withdraw, or an order with a multi-token `inputs` array where one token's amount rounds/settles to zero), and the caller of `onAccept` is the trusted relayer forwarding the message — the amount value itself is attacker-influenced through order construction, not the relayer.

If any of the tokens in `body.tokens` is a token from the weird-erc20 class that reverts on transferring `0` (several real ERC20s revert on zero-value transfers), and the amount for that token entry is zero, `token.call(...)` succeeds at the call level, but the ERC20's own revert bubbles up as `success == false`, triggering `revert TransferFailed()`. This reverts the entire `withdraw` execution, which in turn causes `onAccept` (called by the trusted relayer forwarding an ISMP-verified `PostRequest`) to fail.

### Impact Explanation
Because `withdraw` also mutates `_filled[body.commitment]` and decrements all other `_orders[body.commitment][token]` escrow entries in the same call, a revert means **no state changes are persisted at all** — the whole redemption/refund is rolled back. Since `onAccept` is the terminal handler for a delivered ISMP message and Hyperbridge relayers do not retry a message whose commitment/receipt was already recorded by `EvmHost`/`HandlerV2` as delivered, an order containing (or resolving to) a zero-amount token entry towards a revert-on-zero-transfer ERC20 becomes **permanently undeliverable**: the solver who filled the order can never redeem the escrowed input tokens (RedeemEscrow), or the user can never recover a refunded escrow (RefundEscrow). This is a permanent freezing-of-funds condition for the affected order's escrow, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment that lists a revert-on-zero-transfer token as a supported intent asset (a documented, non-exotic subset of the weird-erc20 catalogue referenced in the source report). No admin or governance action is required — an ordinary user/solver simply needs to (a) place/fill an order whose `inputs`/output token list includes a zero-amount entry for such a token, or (b) drive a partial-fill/multi-token scenario where the per-token escrow release resolves to zero for one of the listed tokens while other tokens in the same `WithdrawalRequest` are non-zero. Because the EVM sibling contract already contains the `if (amount == 0) continue;` fix, this is a straightforward divergence/regression in the Tron port rather than a theoretical-only issue.

### Recommendation
Add the same `if (amount == 0) continue;` guard (or equivalent) before performing the native/ERC20 transfer in the Tron `IntentGatewayV2.withdraw` function's token loop, mirroring `IntentsBase._withdraw` in the canonical EVM contracts, so a zero-amount leg cannot cause the entire withdrawal (and therefore the entire cross-chain message delivery) to revert.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a supported input token `T` that reverts on `transfer(to, 0)` (representative of the referenced weird-erc20 class).
2. Construct (or drive via partial fill) an `Order` whose escrow token list resolves to `TokenInfo({token: T, amount: 0})` alongside other non-zero token entries in the same commitment.
3. Have a solver call `fillOrder` (or a user call the cancel path), which dispatches a `RedeemEscrow`/`RefundEscrow` `PostRequest` with a `WithdrawalRequest.tokens` array containing the zero-amount entry for `T`.
4. When the corresponding `onAccept(IncomingPostRequest)` is delivered by the relayer on the source chain, `withdraw` iterates the tokens, reaches the zero-amount entry for `T`, calls `token.call(transfer(beneficiary, 0))`, which reverts inside `T`; `success == false` triggers `revert TransferFailed()`.
5. The entire `withdraw` call reverts; `_filled[commitment]` is never set and none of the other escrowed tokens for this commitment are released. The message is marked delivered by `EvmHost`, so there is no automatic retry — the escrow for this commitment (including the non-zero legs) is permanently stuck. [3](#0-2) [4](#0-3)

            uint256 amount = body.tokens[i].amount;

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                if (!success) revert TransferFailed();

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
