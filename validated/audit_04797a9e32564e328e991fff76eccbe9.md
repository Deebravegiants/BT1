## Finding

### Title
Webhook shop-domain header is trusted for tenant attribution but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body, while the `shop-domain` (and `topic`/`webhook-id`) headers used to attribute a webhook to a specific merchant are never part of the signed material. Since `Registry.process` trusts these headers to identify the shop after a successful HMAC check, an attacker who obtains any one genuinely-signed webhook body (e.g. by installing the app on their own store and receiving a real webhook) can resend it to the app's webhook endpoint with a different `shop-domain` header and have it accepted as coming from a victim shop.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

None of the Shopify-provided headers — `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version` — are included in the signed bytes: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced from unauthenticated headers — to the app's registered handler as trusted metadata: [4](#0-3) 

The equality this breaks is: **bytes covered by the verified HMAC (`raw_body`) == bytes used to attribute the event to a tenant (`shop-domain` header)**. Before the attacker's request: a legitimate Shopify webhook has `hmac = HMAC(body)` and `shop-domain = <shop that triggered it>`, and these two facts are correlated because Shopify itself sets both. After the attacker's substitution: the attacker keeps a genuine `(body, hmac)` pair (obtainable by triggering a webhook on any store they control, including their own free/dev install of the app) but swaps `shop-domain` to a victim shop when POSTing to the app's webhook controller. `HmacValidator.validate` still returns `true` because it only checks `body` against `hmac`; `Registry.process` never notices the header substitution and calls `handler.handle` with `WebhookMetadata.shop` set to the victim's shop.

This is not a case of the host app ignoring documented API — the gem's own `Registry.process` is the exact place that performs "verify HMAC, then hand off trusted shop identity" and the mismatch between what is verified and what is trusted for identity lives entirely inside this gem's code.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant's session/access token/data to act on (e.g. a `customers/redact` or `shop/redact` mandatory-compliance handler, or an app that updates per-shop records keyed by this field) can be made to act on the wrong tenant's data using an attacker-controlled `shop-domain` value paired with attacker-obtained but validly-signed body content. This is a cross-tenant integrity break driven purely by unauthenticated header data, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker still needs at least one genuinely Shopify-signed `(body, hmac)` pair, which they can obtain trivially and repeatedly by installing the target app on a store they control (a normal, unprivileged action any internet user can take for a public Shopify app) and capturing the webhooks Shopify sends them. From there, replaying to the same app's endpoint with a forged `shop-domain` header requires no secret knowledge, no privileged account, and no interaction with the victim.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them for tenant attribution in `Registry.process`. At minimum, `Request#to_signable_string` should incorporate the shop domain so that `HmacValidator.validate` fails if the header is altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives a webhook (e.g. `customers/redact`), capturing the raw POST: body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker sends a new HTTP request directly to the app's public webhook controller endpoint with:
   - `raw_body`: the same `B`
   - `x-shopify-hmac-sha256`: the same `H`
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: unchanged
3. The app's controller builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC_SHA256(api_secret_key, B)` and compares it to `H` — this succeeds because only `B` is signed.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to perform whatever shop-scoped action the handler implements (e.g., redaction/session lookup) against `victim-shop.myshopify.com` instead of the shop that actually generated the event.
