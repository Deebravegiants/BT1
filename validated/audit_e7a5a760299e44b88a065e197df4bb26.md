### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but then trusts the `shop-domain` header — which is never included in the signed material — to attribute the payload to a tenant. Any party who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store) can replay it with a different `shop-domain` header and have the library treat the payload as belonging to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` returns only `@raw_body`. The HMAC is verified with: [2](#0-1) 

Because `to_signable_string` never includes `shop`, `topic`, or `webhook_id`, `Utils::HmacValidator.validate(request)` proves only that the *body* was signed with the app's `api_secret_key` — it says nothing about which shop, topic, or webhook that body was originally signed for. `Registry.process` nevertheless forwards the unsigned `request.shop` straight into the data handed to the app's business logic: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler attributes the payload to`

Here the left side doesn't exist at all — the shop is never covered by the signature — so the equality trivially and silently fails whenever headers are manipulated. Any unprivileged party who can install the target app on their own development/trial store (a normal, unprivileged action available to any internet user for a public Shopify app) will receive genuine webhooks containing a body and HMAC signed with the same `api_secret_key` used for every shop using that app. That attacker can then POST the captured `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` dispatches to the handler with `shop: <victim-shop>` and attacker-controlled `body`.

### Impact Explanation
This breaks the tenant boundary that `Webhooks::Registry.process` is expected to preserve: it lets one merchant/tenant inject fabricated event data (order, customer, GDPR redact, app-uninstalled, etc.) that the host application believes originated from a different, victim shop. Any app logic keyed off `WebhookMetadata#shop` (updating per-shop billing state, redacting/deleting a shop's data, revoking access, writing to a shop-scoped datastore) can be triggered against a shop the attacker never operated. This is a cross-tenant access primitive, matching the Critical severity bucket in the assessment rules.

### Likelihood Explanation
Exploitability requires no privileged credentials, no access token, and no knowledge of the app's `client_secret`: an attacker only needs to install the target Shopify app once (a routine, unprivileged flow for any public app) and then interact with the app's already-public webhook HTTP endpoint. Capturing one legitimate `(raw_body, hmac)` pair from their own shop's webhook delivery is sufficient to forge an unlimited number of "webhooks" for arbitrary other shops.

### Recommendation
- **Short term:** Bind the shop domain (and topic/webhook id) into the signed material, or otherwise cryptographically tie `request.shop` to the specific delivery, before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated relative to the HMAC and must be independently verified by the host app (e.g., cross-checked against a shop that is known to have this webhook/topic registered) before being used for tenant-scoped operations.
- **Long term:** Extend `Utils::VerifiableQuery`/`HmacValidator` so that all identity-bearing fields used downstream (shop, topic, webhook id) are part of `to_signable_string` for every request type, not just the raw body, closing the gap between "bytes verified" and "bytes acted upon."

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers/receives a webhook (e.g. `orders/create`) with the app's endpoint, capturing the raw POST body `B` and header `shopify-hmac-sha256: H` (a valid HMAC of `B` under the shared `api_secret_key`).
2. Attacker sends a new HTTP POST to the same public webhook endpoint with:
   - `shopify-hmac-sha256: H` and body `B` (unchanged, so the signature still validates)
   - `shopify-shop-domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `request.shop == "victim-shop.myshopify.com"`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `@raw_body` and compares to `H` — validation succeeds. [4](#0-3) 
5. `handler.handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host application to act as if the payload came from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
