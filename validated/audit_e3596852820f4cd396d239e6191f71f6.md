### Title
Webhook shop-domain spoofing via HMAC that binds only the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC signature validated in `ShopifyAPI::Webhooks::Registry.process` proves nothing about the `shop-domain` header. The `shop` value that is handed to app handlers as trusted tenant identification is taken straight from an unauthenticated HTTP header.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` by reading the `shopify-shop-domain`/`x-shopify-shop-domain` header directly, with no cryptographic binding to the request: [1](#0-0) 

The value that *is* signed is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string and, once it passes, immediately forwards `request.shop` to the app's registered handler as authenticated tenant data, with no cross-check that the `shop` header matches the shop the body/HMAC actually originated from: [3](#0-2) 

Because `Context.api_secret_key` is a single app-wide secret shared across every shop that installs the app (not a per-shop secret), the HMAC over the body is identical for any shop sending the same payload. The `shop` field is a "field acted on but not covered by the HMAC" — the exact binding-break pattern flagged in the report's bug class (there, `PriceProvider`'s consumers were trusting price data without triggering the update that keeps it bound to real state; here, the gem trusts a `shop` value without binding it to the signed payload).

The gem's own documentation confirms host apps are expected to treat `Registry.process` as doing full authenticity verification and to treat `data.shop` as the trustworthy shop domain of the webhook, with no mention that callers must independently re-verify the shop header: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who legitimately installs the app on their own store (an unprivileged internet user, no special credentials needed) receives real, correctly-HMAC-signed webhook deliveries for their own shop. They can then replay the identical raw body and HMAC header to the app's webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body against the shared `api_secret_key`, and `Registry.process` will invoke the app's handler with `shop` set to the attacker-chosen victim domain. Any host application that uses `data.shop` to select which merchant's data/session to act on (exactly as the documented example demonstrates) can be made to apply attacker-controlled webhook data to another tenant's account — a cross-tenant integrity/authenticity break.

### Likelihood Explanation
Any app that follows the gem's documented `WebhookHandler`/`Registry.process` pattern is affected, since the exploit requires only the ability to install the app on one shop (freely available to any internet user) and to send an HTTP request with a modified header — no access to `api_secret_key`, access tokens, or the victim shop is required.

### Recommendation
Include the `shop` domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise require host applications to independently authenticate the `shop` header against a known/installed shop list before trusting `WebhookMetadata#shop`, and document this requirement explicitly if the binding is not added to `to_signable_string`.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook with body `B` and `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `B` and `H`, then POSTs to the same app's webhook endpoint with `X-Shopify-Shop-Domain: victim.myshopify.com`, same body `B`, same header `H`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` (`to_signable_string`) — validation passes since `B`/`H` are unchanged. [6](#0-5) 
4. `handler.handle` is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim.myshopify.com"`, taken solely from the unauthenticated header. [7](#0-6) 
5. Any host app logic keyed on `data.shop` (as shown in the gem's own documented example) now processes attacker-supplied webhook content attributed to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
