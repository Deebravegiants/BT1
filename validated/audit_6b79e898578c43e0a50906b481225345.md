### Title
Fee-on-transfer output tokens allow solvers to underpay order beneficiaries while claiming full escrow release - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol, evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntentGatewayV2.placeOrder` (source-chain escrow) correctly guards against fee-on-transfer tokens by measuring the actual balance received before crediting escrow [1](#0-0) , and this is explicitly tested for FOT tokens [2](#0-1) . However, the destination-chain fill path — where a solver delivers output tokens to the order beneficiary — never performs this balance check. It blindly assumes `safeTransferFrom` delivers the full nominal amount and then unconditionally releases the entire escrowed input to the solver, matching the "USDT fee-on-transfer" bug class where a fixed nominal amount is assumed to equal the amount actually received.

### Finding Description
In `_fillCrossChain` (cross-chain fill) the solver's output payment is sent with:
```solidity
IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
``` [3](#0-2) 
The recorded fill amount used to authorize escrow release is `totalRequired` from `order.output.assets[i].amount`, not the amount the beneficiary actually received [4](#0-3) . Immediately after, the function dispatches a `RedeemEscrow` message that releases the *entire* escrowed input to the solver regardless of what the beneficiary actually got [5](#0-4) .

The same pattern exists in the same-chain fill path `_fillSameChain`, where `beneficiaryTotal` is transferred via `safeTransferFrom` without checking actual delivery, yet `amountFilled`/`isFullyFilled` and the resulting escrow release via `_withdraw` are computed from the nominal `fillAmount`, not the real balance delta [6](#0-5) .

If the output token is a fee-on-transfer token (present-day or future USDT-style token, or any deflationary/rebasing ERC20), the beneficiary receives `totalRequired - fee` while the protocol still treats the order as fully satisfied and releases 100% of the escrowed input tokens to the filling solver. This mirrors the reported USDT bug class: a component of the protocol (here, the fill/redemption accounting) assumes ERC20 transfers deliver the full nominal amount, causing an accounting mismatch that benefits one unprivileged party (the solver) at the expense of another (the order's beneficiary).

### Impact Explanation
Any solver — an unprivileged, permissionless role that anyone can assume by calling `fillOrder` — can complete an order paying an output asset that charges a transfer fee (either because the order creator specified such a token, or because a currently fee-free token like USDT enables fees in the future) and receive the full escrowed input on the source chain while the beneficiary receives strictly less than the amount the order guaranteed. This is a concrete loss of funds for the order's intended recipient and an unbacked release of escrow relative to what was actually delivered, satisfying the "concrete theft / unbacked value transfer" bar for Medium severity.

### Likelihood Explanation
Likelihood is contingent on the order specifying an output token capable of fee-on-transfer behavior. The codebase already anticipates and specifically guards against FOT tokens on the input/escrow side of `placeOrder` (with dedicated tests), showing the protocol authors are aware of this token class as an expected interaction; the same protection was simply not carried over to the output/fill side of `IntrinsicIntents`/`ExtrinsicIntents`. Given that intents protocols are commonly used with USDT and similar assets on both input and output legs, this is a realistically reachable scenario, not a purely theoretical one.

### Recommendation
Mirror the balance-diff pattern already used in `placeOrder` (measure `balanceOf(beneficiary)` before and after `safeTransferFrom`) in `_fillCrossChain` and `_fillSameChain`, and use the actually-received amount (rather than `totalRequired`/`fillAmount`) both to determine whether the order is fully filled and to size the `RedeemEscrow`/`_withdraw` release to the solver, or reject fill attempts where actual receipt is less than the amount required by the order.

### Proof of Concept
1. Order creator places a cross-chain order whose `output.assets` include a fee-on-transfer token `T` with `totalRequired = 1000`, escrowing `1000` units of input token `I` on the source chain via `placeOrder`.
2. A solver calls `fillOrder` on the destination chain with `options.outputs[i].amount = 1000` (no declared surplus). `_fillCrossChain` executes `IERC20(T).safeTransferFrom(solver, beneficiary, 1000)`; because `T` charges e.g. a 1% fee, the beneficiary's balance only increases by `990`.
3. `outputFills[i]` is recorded as `1000` (the nominal `totalRequired`), and `_post` dispatches a `RedeemEscrow` request for the full `order.inputs` (1000 units of `I`) back to the source chain.
4. On the source chain, `onAccept` processes `RedeemEscrow` and calls `_withdraw`, releasing the full `1000` units of `I` to the solver [7](#0-6) .
5. Net result: solver receives 1000 `I`, having delivered only 990 `T` to the beneficiary — a 1% profit at the beneficiary's expense, with the discrepancy compounding for every fill involving the fee-on-transfer output asset.
