### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` value that `Registry.process` hands to the app's webhook handler is read directly from an HTTP header that is never included in that signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC purely against that signable string and the app's shared secret [2](#0-1) . The `shop` accessor, however, reads the `shopify-shop-domain`/`x-shopify-shop-domain` header verbatim, with no cryptographic tie to the body or the HMAC [3](#0-2) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed into the handler's `WebhookMetadata` [4](#0-3) .

This is precisely the "field acted on but not covered by the HMAC" pattern from the report: the identity binding that should hold is `shop header used for dispatch == shop cryptographically bound to the signed payload`, but the gem only enforces `HMAC(body) == received HMAC`, independent of the `shop` header value.

Because every shop of a given app shares the same `client_secret`/`api_secret_key` used to sign all of that app's webhooks, an unprivileged user who controls their own Shopify store (a legitimate, low-privilege tenant of the app) can capture one authentic webhook delivery to their own endpoint (raw body + valid `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it never inspects the header, so `Registry.process` dispatches the handler believing the event originates from the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to look up per-shop session/access-token records, apply shop-scoped business logic, or write shop-scoped data (which is the intended and documented use of this field), the attacker can inject data or trigger side effects attributed to a victim shop they do not own — a cross-tenant confusion/access issue. This matches the Critical "cross-tenant access" impact category, since the boundary broken is exactly the shop-tenant boundary that HMAC validation is meant to enforce.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own store connected to the same app (a normal, unprivileged capability for any merchant installing a public app) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — both trivially available to any internet user. No access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signable string used for HMAC computation, or otherwise cryptographically verify that the `shop-domain` header matches the shop the webhook was actually issued for (e.g., by validating it against a per-installation record before trusting it), consistent with the report's recommendation to ensure that values acted upon by the application are covered by the authentication check rather than left as unauthenticated, freely-modifiable input.

# 2. Attacker replays the identical body+HMAC to the app's public webhook endpoint,
#    but swaps the shop-domain header to the victim's shop:

  "x-shopify-webhook-id" => "attacker-controlled",
  "x-shopify-api-version" => "2024-01",
}

ShopifyAPI::Webhooks::Registry.process(req)

# and the handler receives WebhookMetadata with shop == "victim-shop.myshopify.com".
