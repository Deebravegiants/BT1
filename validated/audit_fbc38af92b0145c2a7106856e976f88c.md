### Title
Permanent market freeze from unchecked RAY debt-value overflow during accrual - (File: common/src/rates/index.rs)

### Summary
An oversized market can reach a state where every subsequent accrual panics with `MathOverflow`, permanently preventing repayments, withdrawals, liquidations, and index updates for that market. The borrow index is nominally capped, but the cap is applied only after `calculate_supplier_rewards` multiplies the full scaled debt by the new index, so the debt-value calculation can overflow first. [1](#0-0) 

### Finding Description
The permissionless controller entrypoint `update_indexes(caller, assets)` accepts user-selected `HubAssetKey`s and forwards them to the pool. [2](#0-1)  Every existing-market mutation first runs `global_sync`, which calls `accrue_step` before applying the requested operation. [3](#0-2)  During accrual, `calculate_supplier_rewards` computes both `borrowed * old_borrow_index` and `borrowed * new_borrow_index` with `Ray::mul`. [4](#0-3)  `Ray::mul` maps to `mul_div_half_up`, which panics with `GenericError::MathOverflow` when the result exceeds `i128`. [5](#0-4) [6](#0-5) 

The intended `MAX_BORROW_INDEX_RAY` bound is ineffective for this failure because `update_borrow_index` caps the index itself, while the later debt-value multiplication can exceed `i128` before that bound is ever reached. [7](#0-6)  The repository’s own long-horizon test demonstrates that a billion-token, 18-decimal market at 98% utilization reaches this cliff and that subsequent `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW`. [8](#0-7) 

### Impact Explanation
Once `borrowed * borrow_index` crosses the `i128` range during an accrual attempt, the transaction reverts before the new state is committed. Because accrual is reattempted at the beginning of every later operation on the same market, the overflow is persistent rather than a one-call failure. [3](#0-2)  Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate that debt, and recapitalization or revenue processing for the market cannot progress through the normal pool flow. This is a permanent freezing of user funds and protocol insolvency for the affected market.

### Likelihood Explanation
Likelihood is constrained by the need for extreme market scale and sustained debt growth, but the path is unprivileged and does not require malformed storage, a privileged parameter change, or a malicious token. An attacker with sufficient capital can supply a very large asset position and maintain high utilization until the scaled debt value approaches the fixed-point ceiling, then call `update_indexes` on that `HubAssetKey`. [2](#0-1)  The checked arithmetic correctly detects overflow, but detecting it only by reverting leaves no recovery path once legitimate market growth crosses the representable bound. [9](#0-8) 

### Recommendation
Bound the representable debt value before multiplying, not only the index. In `accrue_step`, compute a capped `new_borrow_index` such that `borrowed * new_borrow_index <= i128::MAX`, and derive supplier rewards from that capped value. Alternatively, use a checked/saturating wide-integer path for debt-value and interest calculations and explicitly clamp the stored index to the largest value that keeps both old and new total debt representable. Add a regression test that drives a market to the boundary and proves `update_indexes`, `repay`, `withdraw`, and liquidation remain callable.

### Proof of Concept
1. Create or select a listed market whose rate model can sustain high borrow utilization.
2. Supply a very large amount of the debt asset, then borrow a large fraction of it so `borrowed * borrow_index` is close to `i128::MAX`.
3. Advance ledger time until the next accrual would raise the index enough that `borrowed * new_borrow_index` exceeds `i128::MAX`.
4. Call `update_indexes(caller, [debt_hub_asset])`; `calculate_supplier_rewards` reaches `borrowed.mul(new_borrow_index)` and panics with `MathOverflow`. [10](#0-9) 
5. Reattempt `update_indexes`, `repay`, or `withdraw`; each call re-runs accrual and fails at the same expression, as demonstrated by the repository’s cliff test. [11](#0-10)

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
