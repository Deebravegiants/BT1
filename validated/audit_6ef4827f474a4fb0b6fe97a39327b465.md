### Title
`balanceDif` accounting can be satisfied twice for one real balance via an address-aliased ("double-entry") ERC20, minting shielded value without backing - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact` snapshots `oldBalances`/`newBalances` per `erc20TokenAddresses[i]` using `balanceOf`, then requires `balanceDif == amountChanges[i] + utxoAmount` independently for each index. The circuit only enforces that the address **values** in `erc20TokenAddresses` are pairwise distinct, not that the balances they expose are independent. An attacker can deploy a token where two different addresses (`A`, `B`) read the *same* underlying balance ledger, causing one real transfer to satisfy the balance equation for both indices, letting the attacker mint shielded UTXOs for `2X` while only depositing `X`.

### Finding Description
The claimed equality: `net real tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)`.

In `Hinkal.transact`, balances are read per index with `getBalancesForArray`: [1](#0-0) 
and the post-condition is checked per index independently: [2](#0-1) 

The only defense against duplicate token entries is inside the circuit, which enforces pairwise **address-value** inequality, not semantic balance independence: [3](#0-2) 

An attacker deploys a custom token where two distinct addresses `A` and `B` both read `balanceOf` from one shared storage ledger (e.g., both delegate reads to a common registry), while only `A`'s `transferFrom` performs a real balance mutation and `B`'s `transferFrom` is a no-op that simply returns `true`. Token transfers in `_internalTransact` use `safeTransferFrom`, which only checks the call succeeds/returns true - it never verifies that the caller's or recipient's balance actually changed by the claimed amount: [4](#0-3) 

Exploit flow (single tx, `externalActionId == 0`, deposit path):
1. `erc20TokenAddresses = [A, B]`, `amountChanges = [X, X]`, both deposits (`onChainCreation = [false, false]`).
2. `oldBalances = [balanceOf_A(vault), balanceOf_B(vault)]` - both equal the shared ledger value `V`.
3. `_internalTransact` runs: for index 0 (`A`), a real `transferFrom` moves `X` real tokens from attacker to vault, bumping the shared ledger to `V+X`. For index 1 (`B`), `transferFrom` is attacker-crafted to be a no-op returning `true`; `safeTransferFrom` succeeds despite no value moving: [5](#0-4) 
4. `newBalances = [balanceOf_A(vault), balanceOf_B(vault)]` both now read `V+X` (same shared ledger).
5. `balanceDif[0] = X`, `balanceDif[1] = X`. Both satisfy `balanceDif == amountChanges[i] + utxoAmount` (`0` on-chain UTXO amount, deposit only credits off-chain commitments matched by the circuit's `inTotal + amountChanges[i] === outTotal`).
6. The circuit's `distinctErc20AddressChecks` passes because `A != B` as raw field/address values, even though they alias the same real balance.
7. Result: the prover mints two shielded output commitments worth `X` each (total `2X` shielded value inserted into the tree) while only `X` in real tokens entered the vault.

None of the existing guards catch this: `dimensionsCheck`/`checkOnchainCreation` only validate array lengths and onChainCreation semantics, not token address independence; `verifyProof` only checks proof validity against public inputs that include the (distinct-valued but aliased) addresses; the slippage check (`balanceDif >= slippageValues[i]`) is satisfied trivially since `balanceDif == X > 0`.

### Impact Explanation
The attacker mints shielded UTXOs for `2X` (or more, with more aliased addresses) backed by only `X` in real deposited tokens, directly causing protocol insolvency for that token/ledger - shielded value exists in the tree with no matching on-chain backing. This matches Critical severity: minting shielded value without backing. The attack is fully repeatable by any unprivileged attacker who can deploy their own token and generate proofs for their own UTXOs, and can be scaled by adding more aliased "views" of the same underlying balance in a single `erc20TokenAddresses` array (bounded only by `dimensions.tokenNumber`/circuit dimensioning).

### Likelihood Explanation
No privileged role is required. The attacker only needs to: (1) deploy a custom ERC20-like contract exposing two (or more) addresses that share one balance ledger with independently-crafted `transferFrom` behavior, and (2) generate a valid proof for a deposit-type transaction referencing both aliased addresses with matching `amountChanges`. This requires no cross-transaction or cross-block residual state - it is fully self-contained within a single `transact` call, using only capabilities explicitly available to unprivileged users (arbitrary token deployment, deposit of own funds, proof generation for own UTXOs). Cost to the attacker is just gas plus deployment of a trivial token contract.

### Recommendation
Do not rely solely on `balanceOf` snapshots per listed address for solvency accounting. Either: (a) canonicalize/whitelist accepted `erc20TokenAddresses` so arbitrary attacker-deployed tokens cannot be paired with the protocol's shielded-minting balance checks, or (b) require that each token entry's real value movement be verified independently at the point of transfer (verify `balanceOf` delta immediately around each individual `transferERC20TokenFrom` call rather than only via one aggregate before/after snapshot spanning all indices), so a no-op/aliased `transferFrom` on one index cannot be silently backed by a real transfer performed against a different address.

### Proof of Concept
Foundry test plan:
1. Deploy `SharedLedger` contract holding a single `mapping(address => uint256) balances`.
2. Deploy `TokenA` and `TokenB`, both proxying `balanceOf` to `SharedLedger.balances`; `TokenA.transferFrom` mutates `SharedLedger.balances` normally (real ERC20 semantics); `TokenB.transferFrom` is a no-op returning `true`.
3. Fund attacker with `X` `TokenA`-equivalent balance in `SharedLedger`.
4. Build `CircomData` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, and craft a valid off-chain proof (via test-mode/mock verifier or existing snarkjs test harness) whose `outCommitments` mint `X` for slot 0 and `X` for slot 1.
5. Call `Hinkal.transact(...)`.
6. Assert: `IERC20(TokenA).balanceOf(hinkal) - oldBalanceA == X` (real tokens received == `X`), but the shielded tree now contains new commitments totaling `2X` (assert via `insertCommitments`/emitted events or leaf count/amount), i.e. `mintedShieldedValue (2X) > realTokensReceived (X)`.
