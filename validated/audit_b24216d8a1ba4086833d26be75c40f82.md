### Title
Webhook shop identity not bound by HMAC, allowing shop spoofing in `WebhookMetadata` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that `Utils::HmacValidator.validate(request)` succeeds against the raw body, then forwards `request.shop` — a value taken directly from the unauthenticated `X-Shopify-Shop-Domain` header — to the app's handler as the identity of the tenant that produced the event.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cross-check against the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity, then constructs `WebhookMetadata` using the unauthenticated `request.shop`: [4](#0-3) 

The identity binding the gem should enforce is: `shop that produced the signed body == shop reported to the handler`. Because the HMAC only covers `raw_body` and `api_secret_key` is shared across every shop that has the app installed, any merchant who has installed the app (an "unprivileged" actor from the target's perspective — they only need their own, possibly free/dev, store) can capture one of their own legitimately-signed webhook deliveries and replay the same body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` calls the handler with `shop: <victim-shop>` even though the request did not originate from Shopify on behalf of that shop.

The gem's own documentation reinforces the false guarantee, stating that `process` "will verify the request did indeed come from Shopify" and that `shop` in `WebhookMetadata` is simply "The shop domain of the webhook" — encouraging host apps to trust it as authenticated tenant identity: [5](#0-4) [6](#0-5) 

### Impact Explanation
Applications built on the documented handler contract (`data.shop`) commonly use this value to select the tenant/session/database row to update (e.g., "look up the session/store record for `data.shop` and update order/customer state from `data.body`"). Since the shop identity is forgeable while the body's HMAC remains valid, an attacker controlling any shop with the app installed can inject webhook events attributed to a different, victim merchant, leading to cross-tenant data confusion in any app that follows this gem's documented pattern without independently validating the shop against a byte range covered by the signature. This matches the High-impact category of a scope/identity check that answers permissively across a tenant boundary.

### Likelihood Explanation
The webhook endpoint is a public HTTP route by design (that's the entire point of HTTP webhooks), and the only barrier is possessing one validly-signed payload for the shared `api_secret_key`, which any shop that installs the app can trivially obtain by capturing its own webhook traffic. No access to the app's `client_secret`/`api_secret_key` value itself, no privileged account beyond an ordinary installed shop, and no additional secrets are required.

### Recommendation
Include the shop domain (and ideally topic) inside the bytes that are HMAC-verified, or otherwise cryptographically bind the header-provided `shop` to the signed body before exposing it via `WebhookMetadata`. At minimum, update `Webhooks::Request`/`HmacValidator` so `to_signable_string` incorporates the shop header, and document clearly that `request.shop` is not itself covered by the signature so host apps are not misled by the "verified" framing in `docs/usage/webhooks.md`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures a real `orders/create` webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only, matches `H`, and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: B, ...)`, even though `victim.myshopify.com` never sent this event.
