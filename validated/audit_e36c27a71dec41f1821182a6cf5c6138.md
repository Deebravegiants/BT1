### Title
Router.buy/sell credit the Pair's curve reserves with the nominal transferred amount instead of the actual balance received, desyncing K if either leg is fee-on-transfer - ([File: packages/contracts/src/Router.sol])

### Summary
`Router.buy` and `Router.sell` pull the LT ("asset") or launched `Token` via `safeTransferFrom` into the `Pair`, then unconditionally call `Pair.swap(...)` with the *nominal* amount requested, not the amount the `Pair` actually received. `Pair.swap` in turn updates `_pool.tokenReserve`/`_pool.assetReserve` by adding those nominal deltas. If either transferred asset ever deducts a fee on transfer, the pair's stored reserves would overstate the tokens/LT actually held, permanently desyncing the AMM's internal accounting from real balances.

### Finding Description
`Router.buy` computes `amountInUsed` from `_computeBuy`, pulls LT with `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)`, then calls `IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0)` [1](#0-0) . `Router.sell` mirrors this: it pulls the launched `Token` with `IERC20(token).safeTransferFrom(to, pairAddr, amountIn)` and then swaps using the nominal `amountIn` [2](#0-1) . `Pair.swap` accepts these nominal deltas at face value and updates `_pool.tokenReserve`/`_pool.assetReserve` accordingly, only checking the constant-product invariant against the recorded (not actually-verified) reserves [3](#0-2) .

This is the direct analog of the reported `VaultHelper` bug: neither `Router` nor `Pair` measures the pre/post balance delta of the transferred asset before updating internal accounting — they trust the caller-supplied nominal amount. In the original report, the mismatch caused an immediate revert on the next `deposit`; here, because `Pair.swap`'s only sanity check is the loosened `(newTokenReserve+1)*(newAssetReserve+1) >= k` invariant (not a live balance check), an under-delivery from a fee-on-transfer asset would silently inflate the recorded reserves relative to what the `Pair` truly holds, rather than reverting.

### Impact Explanation
If the launched `Token` or the paired LT ever deducted a transfer fee (whether by a future/rebasing LT variant registered by `Bonding.launch`, or any other reserve asset onboarded later), the `Pair`'s stored `tokenReserve`/`assetReserve` would exceed its real balances after every trade. This breaks the invariant that graduation math (`_graduate()`'s `ltFromPair = reserve1 - virtualLtReserve`, `tokensForLP` calculation) and `Router.graduate`'s `transferAsset` rely on stored reserves, per `docs/contracts-scope.md`'s graduation section [4](#0-3) . An inflated stored `assetReserve` would let `Router.graduate` attempt to pull more real LT out of the `Pair` than it actually holds, reverting graduation, or (depending on the exact desync direction) permanently strand real LT/tokens in the `Pair` unreachable by any function, since `Pair.transferAsset`/`transferToken` are only reachable through `Router`, which is driven entirely by the desynced stored reserves rather than live balances.

### Likelihood Explanation
Currently, `Token.sol` is a plain vanilla `ERC20Upgradeable` clone with no transfer fee [5](#0-4) , and the codebase does not expose (within my search) any evidence that the BounceTech LT itself charges a fee on plain `transfer`/`transferFrom` (as opposed to `mint`/`redeem`). I could not fully verify the LT's own transfer semantics from the available index (the LT is an external BounceTech contract, out of scope per the rules — "bugs inside BounceTech LT... themselves" are explicitly excluded). Given both currently-known reserve assets appear standard (no transfer fee), likelihood under the current configuration is low; this finding is best read as a robustness gap that would only be realized if the pattern of trusting nominal transferred amounts is not corrected before other reserve assets or paired tokens are onboarded.

### Recommendation
Have `Router.buy`/`Router.sell` (or `Pair.swap`) measure the actual balance delta on the `Pair` (or `to`) before and after the transfer, and pass/apply that measured amount to reserve accounting and to the amount credited to the recipient, rather than trusting the nominal `amountIn`/`amountInUsed` value — mirroring the balance-diff pattern the report recommends for `VaultHelper`, and consistent with the balance-based approach already used in `Bonding._routerDepositAndDispose`'s `remToken`/`remLT` computation [6](#0-5) .

### Proof of Concept
1. Assume a future/alternate reserve LT or launched `Token` deducts a 1% fee on `transferFrom` (hypothetical, since current `Token.sol` and the LT as observed are not confirmed fee-on-transfer).
2. A trader calls `Zap.buy` → `Bonding.buy` → `Router.buy(amountIn, token, to)`.
3. `Router.buy` computes `amountInUsed` from `_computeBuy` off the pair's *stored* reserves, then executes `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)` [7](#0-6) ; if a fee applies, `pairAddr` actually receives `amountInUsed × (1 − fee)`.
4. `Router.buy` nonetheless calls `Pair.swap(0, tokensOut, amountInUsed, 0)`, crediting the pair's stored `assetReserve` with the full nominal `amountInUsed`, not the fee-reduced amount actually received [8](#0-7) .
5. Repeated trades widen the gap between stored `assetReserve` and `IPair.assetBalance()`. At graduation, `Router.graduate` attempts `transferAsset(msg.sender, ltFromPair)` computed from the inflated stored reserve [9](#0-8) , which either reverts (freezing graduation) or, if the gap runs the other direction, leaves real LT permanently stuck in the `Pair` since only the stored-reserve-derived amount is ever drained.

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

**File:** docs/contracts-scope.md (L85-90)
```markdown
`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
```
