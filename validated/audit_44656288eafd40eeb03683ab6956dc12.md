### Title
Webhook `shop`, `topic`, `api_version` and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop domain, topic, API version and webhook id are all taken from HTTP headers that are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and `request.topic` from these unauthenticated headers to route and tag the webhook payload, so an attacker who possesses one valid `(raw_body, hmac)` pair can replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook "from" a different shop.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature by computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to `verifiable_query.hmac`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from the (attacker-controlled, at the HTTP layer) headers, none of which are part of the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC and then trusts `request.topic` and `request.shop` to build the dispatched metadata: [4](#0-3) 

This is the exact bug class from the report: a value that is *acted on* (`shop`) is not covered by the value that is *cryptographically verified* (the HMAC over `raw_body` alone). The binding the code implicitly assumes — `hmac_verified(raw_body) == shop_the_handler_will_act_on` — does not actually hold, because `shop` is orthogonal to what the HMAC covers.

### Impact Explanation
Any entity that can obtain one legitimate `(raw_body, hmac)` pair — e.g., the owner of any shop that has this app installed, who receives their own real webhooks — can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. Because the header is not covered by the signature, `HmacValidator.validate` still returns `true`, and `Registry.process` will call the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop. If the host application uses this `shop` value as a tenant key (e.g., to write/update records, cancel subscriptions, or otherwise take webhook-triggered action scoped "per shop"), this allows cross-tenant confusion/spoofing — the attacker forces the app to treat their controlled/replayed data as if it originated from a victim shop.

### Likelihood Explanation
Any merchant who installs the app can trivially generate a valid `(raw_body, hmac)` pair by triggering an event in their own store (e.g., updating a product) and capturing the delivered webhook. Replaying it with a modified shop header requires no secrets beyond that captured request — the `api_secret_key` is never needed since the same body+HMAC combination remains valid. This does not require compromising Shopify's HMAC secret, TLS, or any privileged account.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that's HMAC-verified, or otherwise cryptographically bind them (e.g., verify `shop` against a value looked up from the topic/webhook id via the Admin API, or require the `to_signable_string` to incorporate the normalized headers as Shopify's own webhook signing does for the raw body plus a shop-scoped context). At minimum, document clearly that `WebhookMetadata#shop`/`topic` are not authenticated by the HMAC and must not be used as a tenant-authorization key without additional verification (e.g., cross-checking against the shop associated with the stored `webhook_id`/subscription).

### Proof of Concept
1. App merchant A installs the app; a legitimate webhook fires with body `B` and header `x-shopify-shop-domain: a.myshopify.com`, `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker (merchant A) captures `(B, H)`.
3. Attacker POSTs to the app's webhook endpoint with the same body `B`, same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`== B`) — validation succeeds because it never inspects the shop header: [5](#0-4) 
5. The registered handler receives `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., webhook_id: ...)`, causing the app to act as if the (attacker-controlled) payload originated from `victim.myshopify.com`.
