### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers that are never included in the signed material. Any party who can obtain one valid `(body, hmac)` pair for the shared app `client_secret` (e.g., by installing the app on their own store and capturing/replaying their own genuine webhook) can resend that exact body with a forged `shopify-shop-domain` header claiming to be a different, victim shop. The gem will accept it as authentic and hand the attacker-chosen body to the app's handler tagged with the victim's shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the signable content strictly from the body: [1](#0-0) [2](#0-1) 

`hmac` is derived from the `shopify-hmac-sha256` header, but `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors read straight from the (unauthenticated) headers with no cryptographic binding to the body: [3](#0-2) 

`Registry.process` validates only this body HMAC and then dispatches using `request.shop` and `request.topic` as trusted identity: [4](#0-3) 

`HmacValidator.validate` confirms the signature is computed only over `to_signable_string` (the raw body), never the headers: [5](#0-4) 

The identity binding that should hold is:
`shop_header_value == shop_that_produced(hmac, body)`

But because `hmac = HMAC(client_secret, body)` only, this equality is never checked — the same valid `(body, hmac)` pair is valid for *any* value of `shopify-shop-domain`, since the app's `client_secret` (and hence the HMAC) is identical for every shop that has installed the app. An attacker who installs the app on their own shop receives genuine webhooks with valid HMACs computed with the real, shared `client_secret`. They can then replay that same body/HMAC pair to the app's webhook endpoint while swapping the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers to point at a victim shop. `Registry.process` will pass Shopify's HMAC check (it only checks the body) and will invoke the app's handler with `WebhookMetadata.new(topic: <attacker-controlled>, shop: <victim shop>, body: <attacker-controlled>, ...)`, allowing attacker-controlled data to be injected into the app's per-tenant processing under a victim shop's identity.

### Impact Explanation
This breaks the tenant identity binding the gem is responsible for asserting on inbound webhooks (shop identity should be as trustworthy as the HMAC itself). Any host application that uses `request.shop` from `WebhookMetadata` to look up/update per-shop state (as the gem's own documentation and typical integration pattern expects) can have attacker-controlled webhook payloads attributed to an arbitrary shop, resulting in cross-tenant data injection/corruption. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires an attacker who has legitimately installed the app on their own (or any) Shopify store — a normal, unprivileged action available to anyone able to install a public/custom app — and who can capture one webhook delivery for a chosen topic/body from their own shop. No access to the app's `client_secret`, tokens, or victim credentials is required; only the ability to replay an HTTP POST with modified headers against the app's public webhook endpoint.

### Recommendation
Bind the shop/topic identity into the authenticated material, e.g., include the `shopify-shop-domain` (and ideally `shopify-webhook-id`, `shopify-topic`) header values as part of the string signed/verified by `HmacValidator`, or independently verify that `request.shop` matches a shop with a currently valid, previously established session/access token before dispatching to the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated relative to the HMAC and must not be trusted for tenant-identity decisions without an out-of-band shop verification step.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and captures a legitimate `orders/create` webhook delivery, e.g.:
   - Headers: `shopify-hmac-sha256: <validHmac>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`
   - Body: `{"id": 1, "note": "malicious payload"}`
   Since `hmac = HMAC_SHA256(client_secret, body)` and `client_secret` is identical for all installers, this `<validHmac>` remains valid for this exact body regardless of shop.
2. Attacker sends a new POST to the app's webhook endpoint reusing the same body and `<validHmac>`, but sets:
   - `shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts headers/body; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the body against `<validHmac>` [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {"id"=>1,"note"=>"malicious payload"}, ...)` [7](#0-6) , and the host application processes attacker-controlled data as if it originated from `victim.myshopify.com`.
