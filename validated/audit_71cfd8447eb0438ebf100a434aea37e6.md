Confirmed: `WebhookMetadata.shop` (passed to every host app's `WebhookHandler#handle`) is populated directly from `request.shop` [1](#0-0) , and `WebhookMetadata` is the sole structured object the gem hands to the app's `WebhookHandler` interface [2](#0-1) , while the HMAC signature only ever covers the raw JSON body, never the shop-domain header.

### Title
Webhook shop-domain identity spoofing via HMAC that only signs the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` by defining `to_signable_string` as just the raw request body, while `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers that are never part of the signed content. `Registry.process` accepts any request whose body's HMAC matches, then forwards the caller-supplied, unauthenticated `shop` header value to the app's `WebhookHandler` as trusted tenant identity.

### Finding Description
`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` [3](#0-2) . For webhooks, `to_signable_string` returns `@raw_body` exclusively [4](#0-3) , whereas `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC at all [5](#0-4) .

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` as the tenant identity delivered to the handler: [6](#0-5) 

This breaks the intended identity binding: `shop header == shop that produced/authorized the signed body`. Concretely, before the attack: `HMAC(body_A, secret) == sig_A` was generated by Shopify for shop `A`'s event. After the attack, an unprivileged internet user (who can trivially become a legitimate shop `A` by installing the target app on their own free/dev store, a normal unprivileged action) intercepts one valid `(body_A, sig_A)` pair delivered to their own webhook endpoint, then replays that exact `(body_A, sig_A)` pair to the target app's webhook endpoint while substituting the `shop-domain` header with victim shop `B`'s domain. Because `sig_A` is only a function of `body_A` and the app's single, shop-agnostic `api_secret_key`, `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "B"` even though the body content and originating merchant were actually `A`.

### Impact Explanation
Any downstream logic that uses `data.shop` from `WebhookMetadata` to select which merchant's records to create/update/delete (the gem's own documented pattern for handling webhooks) can be made to write attacker-supplied, arbitrary-body events under another tenant's identity — a cross-tenant data-integrity/confusion primitive reachable by anyone who can install the app on their own store and capture one webhook.

### Likelihood Explanation
Likelihood is moderate-to-high: no possession of `api_secret_key`, access tokens, or any privileged account is required — only the ability to install the target (often public) app on an attacker-owned/dev store to obtain one legitimately signed webhook body, then replay it with a forged `shop-domain` header. The HMAC scheme's exclusion of the shop header from the signed content is unconditional and applies to every webhook topic/handler.

### Recommendation
Bind the shop identity into the signature verification: either include the `shop-domain` (and ideally `topic`/`webhook-id`) header in `to_signable_string`, or have `Registry.process`/host applications independently confirm that `request.shop` corresponds to a shop that is actually subscribed/expected for that `topic`/`webhook_id` (e.g., cross-check against stored webhook registrations per shop) before trusting it as the acting tenant, rather than exposing raw header-derived `shop` as implicitly-authenticated data in `WebhookMetadata`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`; capture one delivered webhook: raw body `body_A` and header `X-Shopify-Hmac-Sha256: sig_A` (valid, since `HMAC(body_A, api_secret_key) == sig_A`).
2. POST to the app's webhook endpoint with headers `X-Shopify-Topic`, `X-Shopify-Hmac-Sha256: sig_A` (unchanged), and `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, body `body_A` (unchanged).
3. `ShopifyAPI::Webhooks::Request.new` accepts the request [7](#0-6) ; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `body_A` against `sig_A` [8](#0-7) .
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <parsed body_A> ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        missing_headers = []

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
      end
