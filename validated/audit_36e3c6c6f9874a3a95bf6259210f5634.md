### Title
Confidential Relay gateway handler keys in-flight requests solely by attacker-controlled `req.ID`, allowing any unprivileged caller to block another user's request - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

### Summary
The SEDA report describes a `requestId` derived without any nonce or `msg.sender`, letting an unprivileged actor front-run and block another user's request because the ID space is shared and collidable. The `confidentialrelay` gateway handler in this repo has the same root cause: it tracks in-flight user requests in a single map keyed purely by the caller-supplied JSON-RPC `req.ID`, with no per-caller/sender namespacing, so any client can pre-claim or collide with another client's ID and cause the legitimate request to be rejected.

### Finding Description
`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `newActiveRequest`: [1](#0-0) 

`newActiveRequest` stores the request in `h.activeRequests` keyed directly by the raw, caller-controlled `req.ID`, and rejects the request outright if that key is already taken: [2](#0-1) 

Unlike the Vault gateway path in the same codebase, which defends against exactly this class of bug by prefixing the request ID with the authenticated/authorized owner before using it as a map key (`authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`) so that different callers can never collide: [3](#0-2) 

the `confidentialrelay` handler applies no such binding of `req.ID` to a caller identity — there is no authorizer, owner, or sender mixed into the key at all in this handler. The existing test (`TestConfidentialRelayHandler_DuplicateRequestID`) confirms the exact behavior: sending the same `req.ID` twice returns `"request ID already exists"` on the second call, with no distinction of who sent it: [4](#0-3) 

This is a direct analog of the SEDA `requestId` collision bug class: the identifier space is shared across all unprivileged callers and lacks any unique per-caller component (nonce or sender), so a malicious caller can deliberately submit requests using the same `req.ID` value as a legitimate caller (observed via prior interactions, predictable client-side ID generation schemes, or brute-forced short strings) to block that caller's in-flight request.

### Impact Explanation
Any unprivileged client interacting with the gateway's `confidentialrelay` handler can deny service to another caller's request simply by using (or racing to use) the same `req.ID` before the legitimate caller's request completes. Because the ID space has no cryptographic binding to the submitter, this is a straightforward allowlist/collision bypass leading to request blocking — matching the "unauthorized job run" / "cross-user response confusion" class called out as in-scope, since a colliding ID can also cause a node's or previous caller's in-flight relay/enclave exchange to be interfered with via the shared `activeRequests` map (e.g., `getActiveRequest`/`HandleNodeMessage` matching by the same `resp.ID`) if an attacker can also inject or replay a request under an ID they don't own.

### Likelihood Explanation
Likelihood is high for the blocking scenario: `req.ID` is fully attacker-supplied, requires no privileged information, and the check-then-set on `h.activeRequests[req.ID]` provides no isolation between tenants. Any user of the gateway API who can guess, observe (e.g., via workflow/execution IDs embedded in logs), or simply race with another `req.ID` can trigger the collision and deny the legitimate request.

### Recommendation
Bind `req.ID` to a verified caller identity before using it as the `activeRequests` map key, mirroring the Vault handler's owner-prefixing approach (e.g., `authenticatedCallerID + separator + req.ID`), so requests from different unprivileged callers can never collide regardless of the raw ID value they choose.

### Proof of Concept
1. Two independent, unrelated unprivileged callers, A (legitimate) and B (attacker), both send JSON-RPC requests to the gateway's `confidentialrelay` handler.
2. Attacker B observes or predicts victim A's about-to-be-used `req.ID` value (e.g., through a predictable client ID scheme, exposed workflow ID, or simple race) and submits a request with the identical `req.ID` first.
3. `newActiveRequest` accepts B's request and inserts it into `h.activeRequests[req.ID]`.
4. When victim A's request with the same `req.ID` subsequently arrives, `newActiveRequest` finds `h.activeRequests[req.ID] != nil` and returns `"request ID already exists: <id>"`, exactly as shown in `TestConfidentialRelayHandler_DuplicateRequestID`: [4](#0-3) 
5. Victim A's legitimate request is denied — a pure DoS/front-running outcome achievable by any unauthenticated/unprivileged client, with no `msg.sender`-equivalent binding in the ID.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
