Confirmed: `to_signable_string` for webhook requests is the raw body only, and `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated headers, then handed to the app's `WebhookHandler` as trusted `WebhookMetadata`.

### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by the HMAC, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) , but the `shop`, `topic`, `api_version`, and `webhook_id` values used afterwards to build `WebhookMetadata` and dispatch the handler are read directly from HTTP headers that are excluded from the signed content [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with the received HMAC [3](#0-2) . For webhook requests, `to_signable_string` returns only `@raw_body` [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read from headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never part of the signed string [5](#0-4) .

`Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` and `request.topic` to route and construct `WebhookMetadata`, which is handed to the app's registered handler as the authoritative tenant/topic for the event [1](#0-0) [6](#0-5) .

Because a single app-wide `api_secret_key` signs webhooks for every shop that installs the app [7](#0-6) , any unprivileged internet user can install the public app on their own (free) development shop, trigger a real event (e.g. `orders/create`), and legitimately receive a `(raw_body, hmac)` pair validly signed with the app's shared secret. Because `shop-domain`, `topic`, and `webhook-id` are not covered by that signature, the attacker can replay the same body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain and/or the `x-shopify-topic`/`x-shopify-webhook-id` headers with different values. `Registry.process` will pass HMAC validation (it only checks the body) and hand the forged `shop`/`topic` values to the handler as if genuinely originating from Shopify for that shop/topic.

This breaks the intended identity binding: `shop authenticated == shop the handler acts on`. The HMAC only proves "signed with this app's secret," not "signed for this specific shop or topic," yet the registry code treats `request.shop`/`request.topic` as trustworthy identity fields once the HMAC check passes.

### Impact Explanation
This is a cross-tenant data/action injection: an attacker-controlled webhook body (attacker's own real order/customer data, or a reused generic payload) can be attributed to an arbitrary victim shop domain inside the host application, since `WebhookMetadata#shop` is taken uncritically from an unauthenticated header. Any app logic keyed off `data.shop` (e.g., looking up and updating that shop's session/store record, writing merchant-specific data, invoking shop-scoped business logic) can be poisoned by a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category, since it lets an unprivileged installer of the app cause the gem to hand off data under a different tenant's identity to the host application, without needing the app's `api_secret_key`, an access token, or any privileged access — only a self-service app install and a forged HTTP request to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is realistic: installing a public Shopify app on one's own store and receiving legitimate webhook deliveries is unprivileged, self-service behavior. Replaying the captured body/HMAC pair with modified `shop-domain`/`topic` headers requires no cryptographic secret and no special access — only the ability to send an arbitrary HTTP POST to the app's already-public webhook receiving endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or independently verify the header-derived `shop` against a store of shops known to have legitimately installed the app (and whose secret/session matches) before constructing `WebhookMetadata` and invoking the handler. At minimum, document/enforce that `request.shop` must be cross-checked by the host application against its own installed-shop registry before being trusted, since the gem's current implementation offers no such binding despite exposing `shop` as if it were verified.

### Proof of Concept
1. Attacker installs the target public Shopify app on their own development store `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g., creates an order) so Shopify delivers a legitimate webhook POST to the app's callback URL, signed with the app's shared `api_secret_key`: headers include `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, plus a JSON body.
3. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, which still matches, so `Registry.process` proceeds [1](#0-0) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-supplied data under the victim tenant's identity.
