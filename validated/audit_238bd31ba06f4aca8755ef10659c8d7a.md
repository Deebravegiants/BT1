## Analysis

The bug-class hint ("state-changing action performed without the event/binding being verified") maps most directly onto `ShopifyAPI::Webhooks::Request`'s HMAC coverage. The HMAC that authenticates a webhook only covers the raw request body, while the `shop` identity that the registry hands off to application handlers is taken from an unsigned HTTP header. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies nothing but the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values used to build `WebhookMetadata` and to route the request to a handler come from HTTP headers (`X-Shopify-Shop-Domain`, etc.) that are entirely outside the signed data.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, request.to_signable_string)` and compares it against the `hmac` header. [4](#0-3) 

`to_signable_string` is defined as just the raw body: [5](#0-4) 

Meanwhile `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are read straight from attacker-controllable headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signed body: [6](#0-5) 

The identity binding that should hold is:
`shop-that-produced-the-HMAC-signed-body == shop-header-value-trusted-by-the-handler`

Because the HMAC secret (`api_secret_key`/`client_secret`) is shared by the app across every shop that has installed it, any shop that has installed the app can legitimately obtain one valid `(raw_body, hmac)` pair (e.g. by triggering a real webhook delivery to its own endpoint, or capturing one sent to the app). That attacker can then POST the same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because only the body bytes are checked, and `Registry.process` passes the forged `shop` value straight into the handler via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`.

### Impact Explanation
This breaks tenant isolation: an app that relies on `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to decide which merchant's data to update, delete, or act upon can be tricked into applying a signed-but-foreign payload to a different shop's record. This is a cross-tenant access/integrity issue — an unprivileged user who merely installs the app on their own shop (no `api_secret_key`, no access token, no privileged account needed) can inject events attributed to another tenant.

### Likelihood Explanation
Likelihood is moderate to high for any app that allows installation by arbitrary merchants (the common case for public/embedded Shopify apps): obtaining one legitimate `(body, hmac)` pair only requires installing the app and triggering any webhook topic once, then replaying it with a modified `shop` header.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material, or otherwise cryptographically bind them to the raw body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document that host applications must independently verify `request.shop` against their own subscription store using the `webhook_id`, since `Request#to_signable_string` — and hence `HmacValidator.validate` — never covers these header-derived values.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`), which is permitted since the app is publicly installable.
2. Attacker triggers any subscribed webhook topic (e.g. `orders/create`) on their own store, causing Shopify to POST a validly HMAC-signed payload to the app's webhook endpoint. Attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` header value from this delivery (e.g. via a debugging proxy they control, since it is their own endpoint).
3. Attacker resends an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes the attacker's payload as if it originated from the victim shop, breaking tenant isolation in any handler logic keyed on `shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
