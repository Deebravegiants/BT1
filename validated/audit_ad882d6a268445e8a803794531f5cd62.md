### Title
Webhook shop-domain (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable content as the raw body only, while the tenant-identifying `shop` value (and `topic`/`webhook_id`) are taken from unauthenticated HTTP headers that are never included in the signed bytes. Any request whose body+HMAC pair is valid for the app's shared `api_secret_key` will be accepted for whatever `shop` value the caller puts in the header, breaking the binding between "bytes verified by HMAC" and "bytes that determine which tenant the webhook belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` only validates the HMAC of the request (i.e., only the body) before dispatching to the handler using `request.shop` and `request.topic` as trusted tenant/topic identity: [3](#0-2) 

The `HmacValidator.validate` call simply recomputes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the supplied `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The binding that should hold is:
`hmac == HMAC(api_secret_key, raw_body ‖ shop ‖ topic ‖ webhook_id)`

but the code actually enforces only:
`hmac == HMAC(api_secret_key, raw_body)`

Because `api_secret_key` is the same for every shop that has installed the app, any shop that legitimately receives a webhook from Shopify possesses a valid `(raw_body, hmac)` pair signed with the app's shared secret. That merchant (an "unprivileged" tenant relative to other tenants of the same app) can capture their own legitimately-delivered webhook and replay it to the app's webhook endpoint after substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` dispatches the handler believing the webhook — including its (attacker-chosen) body content and topic — originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an app built on this gem cannot distinguish "this webhook body was truly sent by Shopify on behalf of shop X" from "this webhook body was sent by Shopify to shop Y but replayed with shop X's domain in the header." Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up the tenant's DB record, trigger data mutations, GDPR redaction flows, or subscription state changes), this enables cross-tenant data corruption or state confusion attributable to the app's trusted webhook channel — matching the "cross-tenant access" class in scope.

### Likelihood Explanation
Exploitation requires only that the attacker control a shop that has installed the same app (a normal, unprivileged merchant/internet user relationship, not a privileged account or leaked secret), and that they can reach the app's public webhook endpoint — both of which are true for any multi-tenant Shopify app built on this gem. No access to `api_secret_key`, tokens, or TLS interception is needed.

### Recommendation
Bind the tenant/topic identity into the signed content, or otherwise cryptographically tie the `shop-domain`/`topic`/`webhook-id` headers to the verified payload before trusting them in `Registry.process` — e.g., include these header values in `to_signable_string`, or require the host application to cross-check `request.shop` against the shop already associated with the session/access token being used to process that webhook, rejecting mismatches before invoking `handler.handle`.

### Proof of Concept
1. App AttackerCo installs `VulnerableApp` on `attacker-shop.myshopify.com` and registers for `orders/create` webhooks.
2. Shopify delivers a legitimate webhook to `VulnerableApp`'s endpoint with body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H = HMAC(api_secret_key, B)`.
3. AttackerCo intercepts/records `(B, H)` (they own this shop, so no privilege needed).
4. AttackerCo replays a new HTTP POST to the same webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which checks `HMAC(api_secret_key, B) == H` — true, since `to_signable_string` only returns `B`. [3](#0-2) 
6. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it came from the victim shop.
