### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Shop Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` identity attribute used to route/attribute the webhook is taken from the unauthenticated `shopify-shop-domain` HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts this header value verbatim to build the `WebhookMetadata` handed to the app's handler, breaking the binding between "bytes verified by HMAC" and "shop the event is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shop-domain` header, which is never included in the HMAC-signed payload: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then immediately trusts `request.shop` to construct the metadata passed to the app's business logic, without any additional binding between the verified body and the claimed shop: [3](#0-2) 

Because the app's webhook secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has installed the app rather than being per-shop, any legitimate webhook delivery an attacker's own shop receives will carry a valid HMAC for that exact body under the app's single shared secret. An attacker who controls a merchant account (or otherwise observes/receives a legitimate webhook for their own shop) can replay that identical `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still succeed because it only re-computes the HMAC over `raw_body`: [4](#0-3) 

The equality broken is: `shop attributed to the event (header, unauthenticated)` ≠ `shop whose data actually produced the HMAC-covered body`. The gem lets these diverge, so any handler logic that keys persistence, authorization, or tenant-scoped side effects off `WebhookMetadata#shop` can be made to act on/for an attacker-chosen victim shop using data whose authenticity was only proven for the attacker's own shop.

### Impact Explanation
This is a cross-tenant confusion primitive: an unprivileged user of one shop (their own store, which is a legitimate installer of the target app) can cause the app to process HMAC-"verified" webhook payloads under a different, victim shop's identity. Any downstream logic in the host app that trusts `WebhookMetadata#shop` for tenant-scoped writes, cache keys, or access-control decisions can be corrupted this way, matching the "cross-tenant access" class of impact called out for this gem.

### Likelihood Explanation
Exploitation only requires being a merchant/admin on any shop that has installed the target Shopify app (to receive a genuine webhook with a valid HMAC) and the ability to send an HTTP request with a forged `shop-domain` header to the app's public webhook endpoint — no access token, `client_secret`, or privileged credentials are needed. The gem provides no additional check binding the header to the signed body.

### Recommendation
Include the shop domain (and ideally webhook id / topic) inside the HMAC-signed content, or otherwise cryptographically bind the claimed shop to the verified body (e.g., cross-check `shop-domain` against a shop that is known/expected to have triggered that specific payload) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker owns/administers `attacker-shop.myshopify.com`, which has installed the target app.
2. Shopify delivers a legitimate webhook to the app's endpoint for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker replays the exact same `B`/`H` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only and succeeds (the header was never part of the signed string), so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to treat attacker-controlled data as if it originated from and applies to the victim shop.
