### Title
Asymmetric decimal-scaling in `pallet-hyper-fungible-token` mints/credits wrong amounts when the local asset has more decimals than the registered remote-chain precision - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s decimal conversion helpers `convert_to_erc20` and `convert_to_balance` compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)` (and the mirror image on the receive path), which silently clamps to `0` whenever `local_decimals > erc_decimals`. This is the same bug class as the reported Ajna analog (a hardcoded/one-directional decimal assumption causing wrong amounts to be transferred), but reachable here by any unprivileged user calling the `send` extrinsic or by any relayer delivering an inbound message, on an asset pair where the local asset uses more decimal places than the paired EVM contract's registered precision.

### Finding Description
`convert_to_erc20` and `convert_to_balance` in [1](#0-0) 
are defined as:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only correctly scale when `erc_decimals >= local_decimals`. `saturating_sub` returns `0` whenever `local_decimals > erc_decimals`, so the exponent silently becomes `10^0 = 1` instead of the negative exponent that should divide (in `convert_to_erc20`) or multiply (in `convert_to_balance`) the amount.

This is used directly in the unprivileged, user-reachable `send` extrinsic: [2](#0-1) 

Here `erc_decimals` is read from `Precisions` storage (the destination-chain EVM contract's decimals, e.g. `6` for a 6-decimal wrapped token) and `decimals`/`local_decimals` is the local asset's `pallet-assets` `Inspect::decimals()` value (which can legitimately be `18`, `12`, or any other value set independently on this chain). If `local_decimals` (e.g. 18) exceeds the destination's registered `erc_decimals` (e.g. 6), `convert_to_erc20` fails to scale the amount down by `10^12` and instead forwards the raw local-precision integer unchanged as the ERC20 `amount` field in the dispatched `Message`.

The symmetric bug exists on the receive side (`on_accept`, using `convert_to_balance`), for the case where an inbound EVM message's `erc_decimals` is smaller than the local asset's decimals.

### Impact Explanation
When `local_decimals > erc_decimals` for a registered `(asset_id, destination_chain)` pair:
- On `send`, the pallet burns/escrows `amount` in local (18-decimal) units, but dispatches an ISMP `Message` whose `amount` field is **not scaled down**, so the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints/releases `10^(local_decimals - erc_decimals)` times more ERC20 tokens than were actually escrowed/burned locally. This is an unbacked-mint / permanent value leak: a user burns a small local amount and receives (or has minted for a chosen recipient) a vastly inflated ERC20 balance on the destination chain, directly draining the destination pallet's escrow or inflating supply of a non-native wrapped asset.
- Symmetrically, on `on_accept` with the mirrored decimal relationship, `convert_to_balance` would under-credit the beneficiary by the same factor, causing permanent freezing/loss of funds for legitimate incoming transfers.

Either direction is a concrete "unbacked mint" or "permanent freezing of funds" outcome directly reachable from a single signed `send` extrinsic or a single relayed inbound message — satisfying the required impact bar.

### Likelihood Explanation
Exploitability depends entirely on governance/config: `register_token`/`update_token` (via `CreateOrigin`) sets each `(asset_id, chain)`'s `Precisions` entry, and the local asset's decimals come from whatever `pallet-assets` asset was registered. The documentation explicitly states `chains[].decimals` is "typically `18` for EVM" but does not enforce that the local asset's decimals must be `<= erc_decimals`. Any token pairing where the substrate-side asset has strictly more decimal places than the paired EVM contract (a plausible and undocumented-as-forbidden configuration, e.g. a locally re-denominated asset, or simple governance/config error) makes every `send` on that pair silently mint/forward the wrong amount, with no revert, no explicit error, and no way for a caller to detect it before funds move. This is a real, not merely theoretical, decimals mismatch — the same class the original report flags as the root cause of financial gain/loss.

### Recommendation
Do not use `saturating_sub` for a value that can conceptually be negative. Compute the exponent as `i32` (`erc_decimals as i32 - local_decimals as i32`) and branch on sign:
- if `erc_decimals > local_decimals`: multiply (in `convert_to_erc20`) / divide (in `convert_to_balance`) by `10^(erc_decimals - local_decimals)` as today.
- if `erc_decimals < local_decimals`: divide (in `convert_to_erc20`) / multiply (in `convert_to_balance`) by `10^(local_decimals - erc_decimals)`.
- if equal: no-op.

Additionally, add unit tests in `modules/pallets/testsuite` covering `local_decimals > erc_decimals` for both `send` and `on_accept` to lock in the corrected round-trip behavior, and consider validating at `register_token`/`update_token` time that resulting conversions cannot silently truncate to a no-op scale factor.

### Proof of Concept
1. Governance (or any misconfiguration) registers a local asset `X` via `register_token` with `native: false` and a `ChainConfig { token_contract: <EVM HFT address>, decimals: 6 }` for destination chain `D`, while asset `X` is a `pallet-assets` asset with `decimals() == 18` (a legitimate independent local configuration; nothing in `register_token` rejects this pairing). [3](#0-2) 
2. A user calls `send(asset_id: X, destination: D, amount: 1_000_000000000000000000 /* 1000 * 1e18 */, ...)`.
3. In `send`, `erc_decimals = 6` (from `Precisions`), `local_decimals = 18` (from `Assets::decimals`). [4](#0-3) 
4. `erc20_amount = convert_to_erc20(1000e18, 6, 18)`. Since `6u8.saturating_sub(18u8) == 0`, this returns `1000e18` unchanged (should have been `1000e18 / 10^12 = 1000e6`). [5](#0-4) 
5. The dispatched `Message.amount` field carries `1000e18` instead of `1000e6`. On delivery, the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract mints/releases `1000e18` raw units of a token whose ERC20 `decimals()` is `6` — i.e., `1e12` times the correct token quantity — while only `1000` tokens' worth (1000e18 local units) were burned/escrowed on the source chain, resulting in massive unbacked inflation of the destination-side token.
