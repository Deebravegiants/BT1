### Title
Webhook `shop` (and `topic`) identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, and `webhook_id` fields entirely from HTTP headers, but `to_signable_string` — the bytes actually authenticated by `HmacValidator` — is defined as only `@raw_body`. This breaks the identity binding: `hmac_authenticated_bytes == raw_body` while `shop_used_by_handler == header["shopify-shop-domain"]`, i.e. the tenant identity used by the host application's webhook handler is never covered by the cryptographic signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via: [1](#0-0) 

The validation call `Utils::HmacValidator.validate(request)` computes the HMAC over `request.to_signable_string`, which is hard-coded to the raw body only: [2](#0-1) 

Meanwhile, the `shop`, `topic`, and `webhook_id` values that get passed into the handler's `WebhookMetadata` (and thus into the host application's tenant-resolution logic) are read directly from attacker-controllable headers, with no cryptographic tie to the signed body: [3](#0-2) 

`HmacValidator.validate` confirms only that *some* valid secret produced the signature over the body — it says nothing about which shop or topic the body is "for": [4](#0-3) 

Because the identity fields (`shop`, `topic`) live outside the signed byte range, any party who can obtain one legitimately-signed `(raw_body, hmac)` pair for their own store (trivially available to any developer who installs the app on a shop they control and captures a real webhook delivery) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Registry.process` will treat the forged request as fully authenticated ("Invalid webhook HMAC." is not raised) and dispatch it to the handler tagged with the attacker-chosen `shop`, since `HmacValidator.validate` never inspects the header values.

### Impact Explanation
This crosses a tenant boundary without any credential belonging to the victim shop: the attacker never possesses the victim's access token, session, or `client_secret`, yet the host application (which trusts `ShopifyAPI::Webhooks::Registry.process` to fully authenticate `shop`) will process attacker-supplied data as if it came from the victim's shop. This matches the "cross-tenant access" Critical-impact category, since applications commonly key their per-tenant persistence (order sync, GDPR redaction handling, inventory updates, etc.) directly off `WebhookMetadata#shop`.

### Likelihood Explanation
Likelihood is High: any developer/merchant who installs the target app on a shop they control (an "unprivileged internet user" with respect to any other tenant of the app) automatically receives real, validly-signed webhook deliveries from Shopify. Capturing one `(raw_body, hmac)` pair requires no special access — it's the normal webhook delivery to their own endpoint/logs — and replaying it with a modified `shop-domain` header requires no cryptographic secret at all, because that header is outside the signed bytes.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified signature before they are trusted:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) headers as part of `to_signable_string`, matching what is actually authenticated, or
- Require the host application/library to cross-check the webhook's shop against an independently known session/shop record before dispatch, rather than trusting the header value implicitly once HMAC validation passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they legitimately control) and registers for a webhook topic, e.g. `orders/create`.
2. Shopify delivers a real webhook to the app's endpoint with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
   and some `raw_body` (JSON payload).
3. Attacker captures this exact `(raw_body, hmac)` pair (e.g., from their own server logs).
4. Attacker replays a request to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`raw_body` only) — this matches, so validation succeeds: [5](#0-4) 
6. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `request.shop` is `"victim-shop.myshopify.com"` — a value the attacker fully controls and that was never covered by the HMAC. The host application's handler now processes attacker data under the victim's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
