### Title
Cross-user response hijacking via attacker-controlled MessageID collision in the WebAPI capabilities gateway handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's `handler.savedCallbacks` map — a piece of shared, process-wide state analogous to the shared `httpx.AsyncClient` in the referenced advisory — is keyed by `msg.Body.MessageID`, a value taken directly and without uniqueness enforcement from the caller-supplied JSON-RPC `ID` field. Any unprivileged external caller reaching the gateway's user-facing endpoint can submit a `web_api_trigger` request with an `ID` that collides with another concurrent in-flight caller's `ID`. The later request silently overwrites the earlier caller's callback entry in the shared map, so when a DON node later replies for the *original* request, the response is delivered to the *second* caller instead — a cross-user response confusion, the same bug class as the cookie leakage across users caused by shared unpartitioned client state.

### Finding Description
`gateway.ProcessRequest` decodes the incoming JSON-RPC request from any external client and, for legacy DON-addressed messages, sets `msg.Body.MessageID = req.ID` before calling into the handler: [1](#0-0) 

This flows into `handler.HandleLegacyUserMessage`, which stores the caller's `Callback` in a package-shared map keyed purely by the user-supplied `MessageID`, with **no duplicate-key check**: [2](#0-1) 

Compare this to the sibling outgoing-connector code path, which explicitly guards against ID reuse (`c.responses.new(messageID)` returns an error "duplicate message received for ID") — showing the maintainers are aware this class of bug exists but the gateway-side `savedCallbacks` map has no equivalent protection: [3](#0-2) 

When a DON node later responds, the gateway looks the response up purely by `MessageID` and dispatches it to whichever `Callback` currently occupies that map slot, deleting it in the same step: [4](#0-3) 

Sequence:
1. Attacker A sends a `web_api_trigger` request with JSON-RPC `ID = "X"`. Gateway stores `savedCallbacks["X"] = CallbackA` and forwards the signed message to all DON members.
2. Before the DON responds, Attacker/legit User B sends another `web_api_trigger` request also with `ID = "X"` (IDs are arbitrary strings up to 200 chars, entirely caller-controlled, and validated only for length/null-suffix, not uniqueness): [5](#0-4) [6](#0-5) 
3. `savedCallbacks["X"]` is now overwritten with `CallbackB`.
4. The DON node responds to the *original* message (still carrying `MessageID = "X"`); `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `CallbackB`, deletes the entry, and delivers A's data/response to B.

This is not gated by any node-side or peer-side trust assumption — it is purely a consequence of a shared, unpartitioned map keyed by attacker-supplied data, reachable from the internet-facing gateway `UserServerConfig` HTTP endpoint that any unprivileged caller can hit.

### Impact Explanation
An unprivileged external caller can cause another caller's trigger-response payload (which may include workflow-node-produced data intended only for the original requester) to be delivered to itself, and conversely can cause its own submitted trigger to silently vanish (no response ever reached, since the slot was reassigned). This is directly analogous in root cause and impact class to "cookie leakage between different users" — sensitive per-request response data crossing between unrelated, unauthenticated principals due to shared unscoped state, satisfying the "cross-user response confusion" acceptance criterion.

### Likelihood Explanation
Exploitation only requires: (1) knowledge or guessing of a currently in-flight `MessageID`/`ID` value (trivially achievable by choosing a short/fixed/common ID such as `"1"` and racing legitimate low-traffic gateways, or observing IDs if any client convention is predictable), and (2) the ability to send two overlapping `web_api_trigger` (or `web_api_target`/`compute_action`/`workflow_syncer`) requests to the same gateway instance within the callback TTL window (`defaultCallbackMaxAgeSec = 120s`). No node compromise, no allowlist bypass, and no cryptographic break are needed — the callback lookup is purely map-key based and the map has global scope across all callers of that DON handler instance.

### Recommendation
- Scope `savedCallbacks` keys to a value that is unique per connection/session in addition to the caller-supplied ID (e.g., combine `MessageID` with the caller's authenticated identity/connection or a server-generated nonce), or reject the request outright if the `MessageID` already exists in `savedCallbacks` (mirroring the `responses.new(messageID)` duplicate-detection pattern already used in `OutgoingConnectorHandler`).
- Apply the same duplicate-ID rejection in `core/services/gateway/handlers/handler.dummy.go`'s `HandleLegacyUserMessage`, which has the identical unguarded pattern.
- Consider deriving `MessageID` server-side (or hashing it together with a per-connection identifier) rather than trusting the raw client-supplied JSON-RPC `ID` as the sole map key for cross-goroutine response routing.

### Proof of Concept
1. Start a gateway with the `web-api-capabilities` handler configured for a DON.
2. Client A sends: `{"jsonrpc":"2.0","id":"X","method":"web_api_trigger","params":{...donID, signature, payload...}}` to the user server endpoint.
3. Before the DON responds, Client B sends: `{"jsonrpc":"2.0","id":"X","method":"web_api_trigger","params":{...different signer/payload...}}`.
4. Observe (via `handler.savedCallbacks`, or by having a DON test-node respond only to A's original signed message) that the HTTP response eventually returned corresponds to B's callback receiving A's DON-originated trigger response, while A's own request either hangs until timeout or also gets B's data if B's request completes first — demonstrated by the map assignment path in `handleWebAPITriggerMessage`/`HandleLegacyUserMessage` shown above with no per-ID collision guard.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
