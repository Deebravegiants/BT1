### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body against the `x-shopify-hmac-sha256` header, but the `shop` value that identifies which tenant a webhook belongs to is read from an unauthenticated header and is never included in the HMAC-verified content. This breaks the identity binding `shop_verified_by_hmac == shop_used_by_handler`, allowing an attacker who can obtain one validly-signed webhook payload (e.g., by triggering an event on their own installed shop) to relabel it as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is completely independent of the signed body and is not covered by the HMAC computation at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which only checks `request.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. the body — and then, once that single check passes, unconditionally trusts `request.shop` and forwards it to the app's handler as the tenant identity: [4](#0-3) [5](#0-4) 

Because `ShopifyAPI::Context.api_secret_key` (the app's `client_secret`) is a single value shared across every shop that has installed the app — not a per-shop secret — any shop that has installed the app can generate a payload with a **valid** HMAC signature (by simply triggering a real event, such as `orders/create`, in their own store, and capturing Shopify's own signed callback). The attacker can then replay that exact `raw_body` + `hmac` header pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is legitimate), and `Registry.process` passes the attacker-chosen `shop` straight into `WebhookMetadata`: [6](#0-5) 

Host applications built on this gem reasonably treat `data.shop` from `WebhookMetadata` as authenticated, since the surrounding HMAC check is the library's only line of defense for webhook authenticity — but the shop identity field itself is never bound to that check.

### Impact Explanation
This is a cross-tenant boundary violation: an attacker with a valid installation of the app on their own store can cause the host application to process/store webhook data (order details, customer data, redact requests, inventory events, etc.) under a victim shop's identity instead of their own. Depending on how the host app uses `data.shop` (e.g., to look up which shop's session/access token to use for follow-up processing, or to write records keyed by shop), this can lead to cross-tenant data corruption, and in cases where the host app uses the webhook shop to select credentials for subsequent actions, escalate to unauthorized actions taken against another tenant's account. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker controls a shop that has installed the target app (a normal, low-privilege action available to anyone), (2) the attacker can trigger any webhook-eligible event on their own store to obtain a validly-signed payload, and (3) the attacker can send an arbitrary HTTP POST to the app's public webhook endpoint with a modified `shop` header. No access to the app's `client_secret`, no interception of TLS, and no access to another merchant's credentials are needed. This is realistically exploitable by any unprivileged app installer.

### Recommendation
Bind the `shop` identity to the HMAC-verified content, or otherwise cryptographically/contextually validate that the `shop` header corresponds to the shop that actually owns the delivered webhook (e.g., cross-check against the webhook subscription/shop registered for the given `webhook_id`, or include shop in the signable string if Shopify's webhook contract is extended to support it). At minimum, document that host applications must not treat `WebhookMetadata#shop` as authenticated on its own, and provide a library-level mechanism (e.g., verifying the topic/shop pairing against previously registered webhook subscriptions) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers an `orders/create` event, capturing Shopify's real POST including `x-shopify-hmac-sha256: <validHmac>` and body `raw_body`.
2. Attacker sends a forged request directly to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <validHmac>      # unchanged, still matches raw_body
   x-shopify-shop-domain: victim-shop.myshopify.com   # attacker-controlled
   x-shopify-webhook-id: <original id>

   <raw_body>   # unchanged, exact bytes from step 1
   ```
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC secret, both of which are unmodified and legitimate. [7](#0-6) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`, causing the host app to process attacker-supplied data under the victim's tenant identity.
