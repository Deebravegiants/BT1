## Title
Webhook `shop` identity is unauthenticated — HMAC only signs the request body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed material. Any party capable of obtaining one validly-signed webhook body (trivially available to anyone who installs the app on their own store) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop, and `Registry.process` will accept it as authentic for the victim tenant.

### Finding Description
The identity binding that should hold is:

`hmac_verified_bytes == bytes_that_determine_the_shop_for_this_webhook`

but in this gem it is broken. `Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is taken straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity for dispatching the payload to the app's handler, with no cross-check that the signature actually vouches for that shop: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that the HMAC matches `verifiable_query.to_signable_string` (the body) against the shared `api_secret_key` — it says nothing about which shop the body belongs to: [4](#0-3) 

Because the app-level secret (`api_secret_key`) is shared across all installations of the app (it is not per-shop), a valid `(body, hmac)` pair generated for one tenant is cryptographically valid for **any** shop header, since the shop is not part of what is hashed.

### Impact Explanation
This crosses a tenant boundary using no privileged material other than being any ordinary user of the app (installing it on any store, including a free/dev store, and triggering an event to receive one legitimate webhook). By capturing a legitimate `(raw_body, hmac)` pair from their own shop and re-POSTing it to the app's webhook endpoint with the `shop-domain` header changed to a victim's shop, the attacker gets the host application's `Registry.process` to accept and dispatch attacker-controlled webhook data as if it originated from the victim shop. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to select which tenant's data/session to update, or to trigger business logic scoped to that tenant), this is a cross-tenant data-injection / cross-tenant access primitive — matching the "cross-tenant access" Critical impact category, since no per-tenant secret protects the shop claim.

### Likelihood Explanation
Any developer/attacker can install the target app on their own (potentially free) Shopify development store, trigger any webhook topic the app subscribes to, and capture the resulting `X-Shopify-Hmac-Sha256` header and raw body from their own server logs — no special access or leaked credentials are required. Replaying it against the same public webhook endpoint with a modified shop-domain header is trivial (a normal HTTP client). No shop-specific secret is needed because the HMAC key is the single app-wide `api_secret_key`.

### Recommendation
Bind the shop identity into the material that is authenticated, not just the body:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) header value in the signed input used for the HMAC comparison, or
- Independently verify that the shop asserted by the header matches a shop known to have a valid, existing session/installation before dispatching to handlers, and reject/flag any mismatch between the claimed shop and any shop-scoped identifiers embedded in the body when applicable.
At minimum, document and enforce that `WebhookMetadata#shop` must not be trusted as authenticated identity by itself — HMAC validation as implemented only proves body integrity under the shared app secret, not shop authenticity.

### Proof of Concept
1. Install the app on `attacker.myshopify.com` and subscribe to a webhook topic (e.g., `products/update`).
2. Trigger the event in the attacker's own store; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks the body against the shared secret) — see `lib/shopify_api/utils/hmac_validator.rb` lines 12-22 — and `Registry.process` dispatches the handler with `data.shop == "victim.myshopify.com"` even though the payload was fabricated by the attacker, per `lib/shopify_api/webhooks/registry.rb` lines 188-199 and `lib/shopify_api/webhooks/request.rb` lines 20-23/35-38.
