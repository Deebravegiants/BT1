### Title
Signup enrollment polling loop resubmits the same `signup_id` after a bounded poll timeout, breaking the "exactly-once" guarantee and enabling duplicate/ambiguous signup state - (File: `src/plans/enroll_user.rs`)

### Summary
`enroll_user::Plan::run` mirrors the same class of bug as the reported `L1CrossDomainMessenger` issue: a bounded local "budget" (gas in the L1 case, poll retries/time here) is assumed to be sufficient to observe the backend's terminal state for an operation, but when that budget is exhausted while the backend is still `InProgress`, the local orb abandons the wait and **resubmits the exact same `signup_id`** to the backend rather than treating the outstanding request as still-pending or replaying/canceling it safely [1](#0-0) . Just like the CrossDomainMessenger scenario where the client-side accounting and the callee's actual gas usage can diverge and break the "replayable" guarantee, here the client-side poll budget (`POLL_STATUS_COUNT * POLL_STATUS_INTERVAL` = 60s) and the backend's actual processing time can diverge, breaking the implicit "one signup attempt maps to one outcome" guarantee.

### Finding Description
The enrollment flow works as follows:
1. `signup_id` is computed once, before any retries [2](#0-1) .
2. The outer loop (`for i in 0..RETRIES_COUNT`) calls `signup_post::request(...)` with that fixed `signup_id` [3](#0-2) .
3. On an "accepted" response, the code enters an inner polling loop (`for i in 0..POLL_STATUS_COUNT`) that sleeps `POLL_STATUS_INTERVAL` and polls `signup_poll::request(&signup_id)` up to 30 times (~60s total) [4](#0-3) .
4. If the backend keeps returning `Status::InProgress`/`Status::Accepted` for the entire 60s window, no `return` is hit in the match arm [5](#0-4) , so control falls out of the inner loop and back to the top of the **outer** retry loop, which unconditionally calls `signup_post::request(...)` again **with the same `signup_id`** [3](#0-2) .

There is no check before resubmitting whether the prior attempt is still being processed server-side. This is exactly the same structural flaw as the reported bug: a fixed, arbitrarily-chosen client-side budget (60s of polling; `_minGasLimit` in the L1 report) is treated as sufficient to always observe the counterpart's terminal state, when in fact the counterpart's actual work duration is not bounded by that budget. If all `RETRIES_COUNT` (3) outer attempts exhaust their 60s poll windows without ever seeing a terminal status, the function gives up and returns `Status::Error` [6](#0-5) , even though the original backend enrollment request(s) may still complete successfully afterward. Meanwhile, `enroll_user`'s caller in `plans/mod.rs` treats this as a failed signup and moves on with the after-signup UI flow, which allows the operator/user to immediately begin a brand-new signup attempt for the same or another QR pairing [7](#0-6) .

### Impact Explanation
Because the client abandoned tracking of the original attempt (which may still complete on the backend) and the operator can immediately start a fresh signup, the same biometric data / same underlying person can end up associated with two distinct `signup_id` submissions being processed concurrently by the backend. This breaks the "one signup, one outcome" invariant that the polling design is meant to enforce, analogous to how the reported bug broke the CrossDomainMessenger's replayability guarantee. Depending on backend-side idempotency handling (which is outside orb-core's code and thus outside this repo's tooling to verify), this can manifest as ambiguous/duplicated signup state ("cross-signup state bleed") for the same real-world individual.

### Likelihood Explanation
This requires the backend to be legitimately slow to reach a terminal status for a full ~60 seconds across all 3 outer retries (up to ~180 seconds total), which is possible under real backend load, degraded connectivity, or backend-side processing delays, and does not require any malicious actor — it is a purely unprivileged, ordinary-user-reachable signup-flow timing condition.

### Recommendation
Before resubmitting `signup_post::request` in the outer retry loop, the code should first check whether the prior submission is still `InProgress`/`Accepted` and, if so, continue polling for that same in-flight request rather than issuing a fresh `signup_post` for the same `signup_id`. Only resubmit when the prior request definitively terminated in a retryable network/client error, not merely because the local poll budget was exhausted while the backend was still working.

### Proof of Concept
1. Orb performs a signup; `signup_post::request` succeeds and returns an "accepted" status [8](#0-7) .
2. Backend keeps the signup in `InProgress`/`Accepted` status for the full 60-second poll window (e.g., due to backend load) [5](#0-4) .
3. The inner poll loop exhausts all 30 iterations without a terminal response and falls through to the outer loop.
4. The outer loop calls `signup_post::request` again with the identical `signup_id`, effectively creating a second concurrent submission attempt for the same enrollment while the first may still be processing [3](#0-2) .
5. If all 3 outer attempts hit this same timeout, `enroll_user::run` returns `Status::Error` [6](#0-5) , the orb UI reports failure, and the operator can immediately start a new signup for the same user while the original backend-side enrollment(s) may still resolve independently later.
