### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` relies on for authenticity only covers the raw request body. Because `client_secret`/`api_secret_key` is shared across every shop that has installed the same app, any merchant who installs the app can capture a legitimately-signed webhook body+HMAC pair delivered to their own endpoint, and replay it while swapping the `shop-domain` header to a victim shop. The signature still validates (it only checks the body), but the app processes the payload attributing it to the victim tenant.

### Finding Description
`Request#shop` reads directly from an unauthenticated header: [1](#0-0) 

`to_signable_string`, which is what actually gets HMAC-verified, only returns the raw body — it never includes the shop, topic, or webhook-id headers: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity for the handler, right after the HMAC check that never touched that field: [4](#0-3) 

This breaks the intended binding `hmac_valid(body) == authentic(shop, body)` down to just `hmac_valid(body) == authentic(body)`. The `shop` value used for tenant routing/data attribution is never verified against the entity that produced/signed the body. Since a single app's `client_secret` is reused to sign webhooks for *every* installing shop, a low-privilege attacker who merely installs the target app on their own store obtains a valid `(raw_body, hmac)` pair for that secret, and can then relabel it as coming from any other shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged app-installer (no special access to any other merchant) can make the app process attacker-supplied webhook data (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact`, etc.) as if it belonged to an arbitrary victim shop, since `WebhookMetadata.shop` is taken verbatim from `request.shop` and handed to the app's business logic keyed by that shop. This can lead to cross-tenant data corruption/injection, forged compliance webhooks (GDPR redact events) against a shop that never requested them, or forged uninstall/lifecycle events that desynchronize a victim's app state — all without needing the victim's credentials, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker be an app-installer on their own shop (a normal, low-privilege position) and be able to capture one legitimate webhook delivery to their own endpoint — both routine capabilities for a merchant using the app. No secret key, access token, or victim-side compromise is needed.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) to the signature verification, not just the raw body — e.g., include `shopify-shop-domain` in the HMAC-signed material used by `to_signable_string`/`HmacValidator`, or require callers to independently confirm that `request.shop` corresponds to a shop session/installation record already known to the app before dispatching to handlers, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a legitimate webhook to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`, and some `raw_body`.
3. Attacker captures `raw_body` and the valid HMAC.
4. Attacker resends the same `raw_body`/HMAC to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the shared `api_secret_key` [5](#0-4) .
6. `Registry.process` dispatches the handler with `shop: request.shop` == `"victim-shop.myshopify.com"` [6](#0-5) , causing the app to process attacker-controlled data under the victim's tenant identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
