Audit Report

## Title
JWT replay guard in `WorkflowMetadataHandler.Authorize` is check-then-act, not atomic, allowing a single-use trigger token to authorize two concurrent workflow executions - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize` verifies JWTs for inbound HTTP-trigger requests and enforces single-use semantics via `jwtReplayCache`, but the replay check (`isReplay`) and the state update (`recordUsage`) are separate, independently-locked operations rather than one atomic critical section. Two concurrent requests carrying the same JWT `jti` can both pass the replay check before either records usage, allowing a single signed token to authorize two workflow-trigger dispatches to the DON.

## Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` under an `RLock` early in the function, and only calls `h.jwtCache.recordUsage(claims.ID)` under a separate `Lock` at the very end, after authorized-key lookups complete: [1](#0-0) . The two cache methods are implemented as independent lock/unlock pairs with no shared critical section: [2](#0-1) .

If two requests with identical `jti` arrive concurrently, both goroutines can execute `isReplay` (each acquiring/releasing its own `RLock`) before either acquires the `Lock` in `recordUsage`. Both observe `exists == false`, both pass the authorized-key checks, and both call `recordUsage` (idempotent) and return a valid `*gateway.AuthorizedKey`. The caller, `httpTriggerHandler.HandleUserTriggerRequest`, then proceeds to dispatch the trigger to DON nodes for each authorized call [3](#0-2) , so a single-use JWT can authorize two independent workflow dispatches. The existing test suite validates that a strictly *sequential* replay (first call succeeds, second call — issued only after the first completes — fails) is rejected, e.g. `TestHttpTriggerHandler_HandleUserTriggerRequest/duplicate_JWT_token_and_request_ID`, but this test does not cover the concurrent case and thus does not demonstrate the race is closed. A correctly-atomic pattern already exists elsewhere in the codebase for the analogous problem — `vault.RequestReplayGuard.CheckAndRecord` — which performs the check and the record under one lock in a single function, underscoring that the split `isReplay`/`recordUsage` design here is inconsistent with the project's own established pattern for this exact problem.

## Impact Explanation
Successful exploitation allows a single signed, single-use trigger JWT to authorize more than one workflow execution dispatch to the DON. Depending on the workflow, duplicate dispatches can cause duplicate job runs or duplicate on-chain/side-effecting actions from a single authorized request — an unauthorized/duplicate job run stemming from a broken authentication/replay-uniqueness guarantee, which is an in-scope impact class.

## Likelihood Explanation
The race requires two authorization attempts with identical `jti` to be in flight concurrently, landing between the `isReplay` read in one goroutine and the `recordUsage` write in either goroutine. This is achievable by any unprivileged caller who deliberately sends two copies of the same signed request over two connections simultaneously, or by a client/proxy performing naive concurrent retries. No cryptographic break, node compromise, or privileged access is required, but the window is narrow (spans key-lookup and authorized-key comparison work only) and each JWT typically has a short validity/TTL, so exploitation requires precise timing and is not guaranteed on every attempt — likelihood is moderate, not high.

## Recommendation
Merge the check and the record into a single atomic operation under one lock, matching the existing `vault.RequestReplayGuard.CheckAndRecord` pattern:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	if _, exists := cache.cache[jti]; exists {
		return false
	}
	cache.cache[jti] = time.Now()
	return true
}
```
Call this from `Authorize` immediately after JWT verification, before any further authorization work, instead of the separate `isReplay`/`recordUsage` calls.

## Proof of Concept
1. Obtain one valid signed HTTP-trigger JSON-RPC request with JWT claim `jti = X` for a registered workflow.
2. Fire two copies of this exact request concurrently against the gateway (two parallel connections), both reaching `WorkflowMetadataHandler.Authorize`.
3. A Go unit test can simulate this directly against `jwtReplayCache`/`Authorize`: spawn two goroutines that call `Authorize` with the same `req`/`token` at the same time (e.g., synchronized with a barrier/channel right before the `isReplay` call, using a test hook or by injecting delay in the authorized-key map lookup), and assert both return `nil` error and a non-nil key — demonstrating that both succeed instead of exactly one succeeding and one returning the "already been used" error, as the sequential test at `http_trigger_handler_test.go` (`duplicate JWT token and request ID`) asserts for the non-concurrent case.
4. Both authorized results, if passed to `HandleUserTriggerRequest`, would result in two separate dispatches to the DON for the same single-use token.
