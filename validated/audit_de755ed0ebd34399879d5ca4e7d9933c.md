### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` only checks that HMAC against that body. The `shop` value that the registry hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain` header, which is completely outside the HMAC's protected surface. Since all webhooks for a given app are signed with the same app-level `api_secret_key` (not a per-shop secret), the HMAC proves only "this body was signed by someone holding this app's secret" — it says nothing about which shop the body belongs to.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read independently from a header that is never part of that signable string: [2](#0-1) 

`Registry.process` only validates the HMAC and then hands `request.shop` straight to the handler as the tenant identifier, with no cross-check between the verified bytes and the shop header: [3](#0-2) 

The binding that should hold is:
`hmac_valid(raw_body) == true` implies `shop_header == shop_that_generated(raw_body)`

But in reality, HMAC validation only proves `hmac_valid(raw_body)`; it says nothing about `shop_header`. The equality actually enforced is:

`compute_signature(raw_body, api_secret_key) == received_signature`

which is independent of `shop_header`. Because the same `api_secret_key` is shared by every shop that installs the app, any merchant who has installed the app can obtain a validly-signed `(raw_body, hmac)` pair simply by triggering a real webhook event in their own store (e.g. creating an order). They can then replay that exact body and HMAC header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` will still pass (the body/HMAC pair is genuine), and `Registry#process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop.

### Impact Explanation
Any app built on this gem that uses `request.shop` (via `WebhookMetadata#shop`) to key persistence, cache invalidation, GDPR/redaction actions, or any tenant-scoped side effect is exposed to cross-tenant data corruption/injection: an attacker-controlled, low-privilege merchant can inject their own (fully attacker-controlled) webhook payload — e.g. order/customer/product data, or `customers/redact`/`shop/redact` mandatory compliance events — under a victim shop's identity. This satisfies the "cross-tenant access" Critical impact category: it breaks the tenant isolation boundary using only the credentials of any installer of the app, without needing the app's `client_secret` or an access token.

### Likelihood Explanation
Likelihood is high for any app that trusts `shop` from `WebhookMetadata` for tenant attribution (this is the gem-documented usage pattern, see `webhooks.md`/`WebhookHandler#handle`). The prerequisite is only that the attacker be able to install the app on their own store (a normal, unprivileged action any Shopify merchant can perform) and be able to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint — both trivially satisfied by an "unprivileged internet user" persona. No knowledge of `api_secret_key` or any access token is required; only the ability to generate one legitimate signed webhook from the attacker's own tenant and replay it with modified headers.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified:
- Include the `shop` (and ideally `webhook_id`/`topic`) in `to_signable_string`, or otherwise cryptographically bind them to the raw body before verification, so that a body signed for shop A cannot be replayed with shop B's header and still validate.
- Alternatively/additionally, require host applications to independently verify that the shop presented in the webhook belongs to a session/install record already known to the app before trusting it, and document this gem limitation prominently since `Registry#process` currently does not perform that binding.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`) by placing an order — Shopify signs the resulting `raw_body` with the app's `api_secret_key` and sends headers including `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb`) computes the HMAC over `raw_body` only and finds it matches — validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker's parsed body, ...)`, causing the app to process attacker-controlled data attributed to the victim tenant.
