This confirms the vulnerability. The docs explicitly state that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (implying full authenticity, including the shop attribution) and instruct developers to trust `data.shop` directly (`shop_domain: data.shop`) without any additional verification. The gem's own documented API and example handler code teach developers to trust the `shop` field as authenticated, when in fact it is not covered by the HMAC.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`/`webhook_id`) values are read from separate, unsigned HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC, then dispatches to the app's handler with `request.shop` as an authenticated fact. Because the webhook signing secret (`api_secret_key`/`client_secret`) is shared across every shop that has installed the app, any merchant who installs the app can legitimately receive a `(body, hmac)` pair for their own shop and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header, causing the app to process data attributed to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` fields are pulled from HTTP headers that are entirely outside the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and hands it to the app's handler: [3](#0-2) 

`HmacValidator.validate` simply recomputes the signature over `verifiable_query.to_signable_string` (the raw body, in this case) and compares it to the received HMAC — it has no visibility into headers such as `shop-domain`: [4](#0-3) 

The binding that is broken is:
`shop_that_produced(hmac, body) == shop_attributed_to_request` — the left side is unconstrained (any shop sharing the app's secret can produce a valid `(body, hmac)` pair), while the right side is taken from an attacker-controlled header. The library treats HMAC-body-validity as proof of `shop` authenticity, but they are independent.

The gem's own documentation reinforces this trust: it states that `Registry.process` "will verify the request did indeed come from Shopify," and its example handler passes `data.shop` straight through as the trusted shop identifier (`shop_domain: data.shop`), with no guidance to cross-check `shop` against anything else: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks tenant isolation (cross-tenant access), one of the accepted Critical impact categories. An attacker who is simply an unprivileged merchant that installs the target app on their own store obtains a valid `(raw_body, hmac)` pair signed with the app-wide secret. By replaying that body with a forged `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header pointing at a victim shop, the attacker causes the app to process/store attacker-controlled data under the victim shop's identity — e.g. injecting fabricated `orders/create` or `app/uninstalled` events, corrupting the victim's data, triggering unwanted side effects (billing, fulfillment, notification logic) keyed off `data.shop`, or, depending on app logic, causing an app to mistakenly disassociate or overwrite a legitimate shop's stored state.

### Likelihood Explanation
Likelihood is high: no leaked credentials, no access token, and no privileged access are required — the attacker only needs to be a merchant who installs the app (a normal, unprivileged action), capture one legitimate webhook, and replay it with a modified header to the app's public webhook endpoint. The gem provides no defense against this because `to_signable_string` never includes the shop identifier.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) in the HMAC-signable content, or independently verify that the `shop` header value corresponds to a shop that is actually expected/registered for that specific webhook delivery (e.g., cross-check against the webhook subscription's target shop from Shopify's API/GraphQL admin, not solely the header). At minimum, `Utils::VerifiableQuery`/`HmacValidator` should be extended so `Webhooks::Request#to_signable_string` binds the shop domain header into what is verified, and `Registry.process` should reject requests where the signed payload does not commit to the claimed shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and the app registers an `orders/create` (or any) webhook for that shop.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - Body: `B` (attacker fully controls the content of `B`, e.g. by placing crafted data in the order they create in their own store)
3. Attacker captures this `(B, hmac)` pair — the HMAC is valid because it's computed with the app's shared secret, which is the same for every installed shop.
4. Attacker crafts a new POST to the same webhook endpoint reusing `B` and the same `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host app exactly as documented in `docs/usage/webhooks.md`.
6. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the HMAC against `B` (per [7](#0-6) ), and then dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `request.shop` is `"victim-shop.myshopify.com"` — attacker-controlled data now flows into the app under the victim's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
