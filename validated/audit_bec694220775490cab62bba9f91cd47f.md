### Title
BEEFY consensus verifiers count duplicate authority-index votes toward the supermajority threshold, enabling a forged finality proof with real-signer participation below 2/3+1 - ([File: modules/consensus/beefy/verifier/src/lib.rs], [File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
The ElectrumSV incident stemmed from a "multisig accumulator" locking script that failed to enforce that the required signature threshold was met by genuinely distinct, independent signers — allowing the effective signer count used by the verification logic to be inflated without a true supermajority of keyholders cooperating. The same bug class exists in Hyperbridge's BEEFY consensus verification: both the Rust verifier (`verify_mmr_update_proof`) and its Solidity counterpart (`EcdsaBeefy.verifyMmrUpdateProof`) compute the participation count directly from the length of the attacker-supplied votes/signatures array and never check that the `authorityIndex`/`sig.index` values are distinct before evaluating the 2/3+1 supermajority threshold.

### Finding Description
In `modules/consensus/beefy/verifier/src/lib.rs`, `verify_mmr_update_proof` takes `signatures_length = mmr.signed_commitment.signatures.len()` and passes it straight to `check_participation_threshold(signatures_length as u32, authority_set.len)` [1](#0-0) . It then recovers an address for every submitted signature and pushes `(authority_leaves, authority_indices)` pairs one-per-signature, feeding them into a single `merkle_proof.verify(...)` call against the authority-set commitment [2](#0-1) . There is no de-duplication of `sig.index` (the claimed authority slot) anywhere in this path, unlike the Pharos verifier which explicitly rejects duplicate participant keys via `verify_validator_membership`'s `deduped.len() != participants.len()` check [3](#0-2) .

The Solidity `EcdsaBeefy.sol` implementation mirrors this: `sigLen = relayProof.signedCommitment.votes.length` is used directly in `checkParticipationThreshold(sigLen, authoritySet.len)`, and the `authorities` array fed to `MerkleMultiProof.VerifyProof` is built by iterating over every vote without checking `vote.authorityIndex` for duplicates [4](#0-3) , and `checkParticipationThreshold` itself only checks `len >= ((2*total)/3)+1` [5](#0-4) .

Because a merkle multi-proof over repeated `(index, hash)` leaf entries at the same tree position is still a cryptographically valid proof of that single authority's membership, a relayer who controls (or has leaked signatures from) even a small minority of the authority set can submit the *same* authority's `(authorityIndex, signature)` pair multiple times. Each duplicate entry increases `sigLen`/`signatures_length` by one and is independently verified as "a valid signature from a member of the authority set," but it does not represent an additional distinct signer. This lets an attacker satisfy the `>= (2/3)*n + 1` threshold check with far fewer than that many genuinely-cooperating authorities, exactly as the ElectrumSV locking script accepted spends without the intended number of distinct cosigners.

### Impact Explanation
A forged BEEFY consensus update that clears the supermajority gate without real supermajority backing allows an attacker to advance `trustedState.latestHeight`/`ConsensusState.latest_beefy_height`, rotate in an attacker-chosen `nextAuthoritySet`, and smuggle in an arbitrary MMR root and parachain header set (`verifyParachainHeaderProof`/`verify_parachain_headers`). Those intermediate state commitments are what `EvmHost`/`pallet-ismp` subsequently trust for proving request/response delivery, state membership, and non-membership across the bridge. A forged consensus update is therefore a direct path to forged message delivery, unsound state commitments, and consequently theft or freezing of funds moved through token bridges, intents escrows, or relayer fee accounting that rely on this consensus client — a Critical-class outcome for any deployment using the ECDSA/BEEFY consensus client.

### Likelihood Explanation
Exploitation requires collecting valid signatures from only a fraction of the authority set (down to whatever minimum makes `sigLen` reach the threshold via duplication) rather than a genuine 2/3+1 majority, which is achievable by a small colluding/compromised subset of validators or by replaying leaked signatures — situationally realistic given BEEFY signatures are gossiped p2p and are not bound to a single unique use. The check is on the hot path of consensus state updates (`verifyMmrUpdateProof`/`verify_mmr_update_proof`), reachable by any relayer submitting a consensus proof, with no privileged access required.

### Recommendation
Reject the proof whenever any `authorityIndex`/`sig.index` value repeats. Concretely, before or while building `authority_leaves`/`authority_indices` (Rust) and `authorities` (Solidity), collect the indices into a set and require the set's cardinality equal `sigLen`, mirroring the `verify_validator_membership` de-duplication already used in the Pharos verifier.

### Proof of Concept
1. Trusted authority set has `n` authorities; supermajority threshold is `(2n/3)+1`.
2. Attacker controls (or has captured) valid signatures from only `k < (2n/3)+1` authorities.
3. Attacker crafts a `RelayChainProof`/`MmrProof` whose `votes`/`signed_commitment.signatures` list repeats each of the `k` genuine `(authorityIndex, signature)` pairs enough times that `sigLen`/`signatures_length` reaches `(2n/3)+1`.
4. `checkParticipationThreshold`/`check_participation_threshold` passes because it only counts array length, not distinct signer indices.
5. Each duplicated `(authorityIndex, keccak256(address))` leaf is individually valid against the authority-set merkle root, so `MerkleMultiProof.VerifyProof`/`merkle_proof.verify` succeeds.
6. The forged commitment (with attacker-chosen MMR root / parachain headers / next authority set) is accepted as the new trusted `BeefyConsensusState`/`ConsensusState`.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
