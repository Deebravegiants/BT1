### Title
Webhook `shop-domain` header trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies only that byte string against the HMAC header. The `shop-domain` (and `topic`) HTTP headers, which `Registry.process` uses to attribute the webhook event to a tenant, are never part of the signed bytes, so the "shop the HMAC authenticates" and "shop the app acts on" are not the same value.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` value with a constant-time compare: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic relationship to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

Because Shopify signs a webhook body with the app's single `api_secret_key` regardless of which installed shop triggered it, any raw_body+HMAC pair that is valid for one shop's webhook delivery remains valid HMAC-wise no matter what `shop-domain`/`topic` header values accompany it. An unprivileged actor who can install the target app on their own store (a normal, non-privileged action requiring no credentials belonging to the app or to any other merchant) can capture one legitimate webhook delivery for that store, then resend the identical body and HMAC header to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the event came from an arbitrary victim shop.

This is exactly the "bytes verified versus bytes parsed" identity-binding break: the bytes cryptographically verified (`@raw_body`) are not the bytes the application actually parses and acts on for tenant attribution (`shop-domain` header).

### Impact Explanation
This breaks cross-tenant isolation: a host application built on this gem uses `WebhookMetadata#shop` as the tenant key to decide which shop's data/session/state a webhook event applies to. An attacker can attribute a forged event to a victim shop domain while carrying a validly-signed body, causing the host app to process attacker-controlled data (order/customer/product payloads, or lifecycle events like `APP_UNINSTALLED`) under a victim shop's identity — e.g., corrupting per-tenant records, triggering unwarranted uninstall/data-erasure cleanup, or invalidating a legitimate merchant's stored session data. This matches the Critical "cross-tenant access" impact category, since a request bound to one tenant's credentials/signature is accepted as if bound to a different tenant.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a Shopify store they control (a normal unprivileged action, not requiring the app's `client_secret`, any merchant's access token, or the victim's credentials) and be able to send arbitrary HTTP POST requests to the app's public webhook endpoint with attacker-chosen headers — both trivially available to any internet user. No interception of TLS, no leaked secrets, and no social engineering are needed.

### Recommendation
Bind the `shop-domain` (and `topic`) values into the signed payload verification, or otherwise cryptographically tie them to the verified body — e.g., require the host application to cross-check `request.shop` against an independently known/registered shop for that webhook subscription, or extend `to_signable_string` (and Shopify's webhook contract usage in this gem) to include the header values that are subsequently trusted for tenant attribution, rejecting the request if they cannot be verified together with the body.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) to capture a real `raw_body` and its valid `X-Shopify-Hmac-Sha256` value signed with the app's `api_secret_key`.
2. Replay that exact `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` [4](#0-3) .
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the host application to process attacker-controlled data as if it originated from the victim shop.
