### Title
Webhook shop/topic/webhook-id headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body (`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only). The `shop`, `topic`, `webhook_id`, and `api_version` values that the gem hands to the app's `WebhookHandler` are read directly from HTTP headers (`shopify_header`) and are never included in the HMAC-signed content. This breaks the intended binding: `shop-header-verified == shop-header-processed`, but neither is bound to `hmac-signed-bytes`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it, via `OpenSSL.secure_compare`, against the `hmac` field of the same object [5](#0-4) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Request#hmac` reads the signature from the `hmac-sha256` header, and `shop`, `topic`, `webhook_id`, `api_version` are all pulled from other headers with no cryptographic linkage to the body or to each other [6](#0-5) .

`Registry.process` trusts these unauthenticated header values wholesale: it validates the HMAC (body-only) and then dispatches using `request.topic`, `request.shop`, and `request.webhook_id` as the tenant/event identity passed to the app's handler [7](#0-6) . Because the HMAC never covers these header fields, any party who can obtain one valid `(raw_body, hmac)` pair for the shared `client_secret` (e.g., by inspecting a legitimately delivered webhook for their own shop, which Shopify exposes to merchants/developers via webhook delivery logs) can replay that exact body+signature to the app's webhook endpoint while substituting an arbitrary `shop-domain`, `topic`, or `webhook-id` header. The HMAC check still passes because it only verifies the body bytes, not the headers that the app's handler will treat as ground truth for which shop/topic the data belongs to.

This is the "field acted on but not covered by the HMAC" class of bug directly analogous to the referenced report, where the check (HMAC validity) and the value acted upon (shop/topic attribution) are decoupled.

### Impact Explanation
This enables cross-tenant data confusion: an app whose webhook handler persists or acts on `WebhookMetadata` (built from `request.shop`, `request.topic`, `request.webhook_id`, `request.parsed_body`) could have data from shop A's legitimately-signed webhook attributed to shop B, since the gem provides no integrity guarantee for the shop identity, only for the body bytes. Depending on the handler's use of `shop`, this can lead to cross-tenant access/write of another merchant's records — matching the High severity "scope or expiry check bypass" / cross-tenant class in the rules, since the authentication boundary the app relies on (per-shop HMAC-bound identity) is not actually enforced by this gem.

### Likelihood Explanation
No secret material is required by the attacker — only a single valid `(body, hmac)` pair tied to the shared `client_secret`, which is obtainable from any shop that has installed the app (webhook payload/HMAC are visible via Shopify's own webhook delivery/test tooling to the merchant). The attacker only needs to modify unauthenticated headers on replay, which requires no privileged access to the app or Shopify's infrastructure.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the HMAC-signable string (e.g., concatenate them with the raw body before computing/verifying the HMAC), or otherwise cryptographically bind the dispatched identity fields to the same signed payload the HMAC certifies, so that changing any of these headers invalidates the signature.

### Proof of Concept
1. App registers a handler for topic `orders/create` via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Attacker (a merchant who has installed the app, or anyone who can view a webhook delivery/replay for shop A) obtains a legitimately-signed `(raw_body, hmac-sha256 header)` pair, e.g., as constructed in [8](#0-7)  where `hmac` is computed only over the raw body `"{}"`.
3. Attacker sends a POST to the app's webhook endpoint with the same body and `shopify-hmac-sha256` header, but sets `shopify-shop-domain` to shop B's domain (a different tenant) instead of shop A's.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body bytes [9](#0-8) .
5. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop` = shop B, even though the signed body actually originated from shop A's event [10](#0-9) .
