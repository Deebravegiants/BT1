### Title
Webhook shop-domain identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks that the *body* matches the HMAC, then passes `request.shop` (an unsigned header value) straight into `WebhookMetadata` for the app's handler to act on as the authoritative tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . Those fields are parsed straight from attacker-controllable HTTP headers with no cryptographic binding to the HMAC [3](#0-2) .

`Registry.process` validates only this body-only HMAC and then immediately builds `WebhookMetadata` using `request.shop` as the tenant identity passed to the app's handler [4](#0-3) .

This breaks the intended binding: `shop_header_used_by_handler == shop_that_the_HMAC_actually_authenticates`. In reality the HMAC only authenticates *that Shopify (or anyone possessing a valid body+HMAC pair) sent this exact body*; it says nothing about which shop the body was originally sent for. Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which does include `shop` in the signed content [5](#0-4)  — showing the library is inconsistent: the OAuth callback path binds `shop` into its HMAC, but the webhook path does not.

Any unprivileged internet user who can legitimately install the target app on a shop they control (a normal, unprivileged app-installation action, not requiring `api_secret_key` or leaked credentials) will receive genuine Shopify-signed webhook deliveries for their own shop — i.e., real `(raw_body, hmac)` pairs signed with the app's `api_secret_key` that they never need to know. They can then replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `topic`/`webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` calls the app's handler with `shop: <victim shop>` and `body: <attacker-controlled content>`, exactly matching the documented, trusted contract described in `docs/usage/webhooks.md:125-135` where the framework is said to "verify the request did indeed come from Shopify."

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook body, verified only as originating from the attacker's own legitimately-signed delivery, is delivered to the app's handler tagged with an arbitrary victim shop's identity. Any app logic that keys per-tenant state, product/order sync, notifications, or other side effects off `data.shop` (as the documentation instructs: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into writing attacker-controlled data into another merchant's tenant context — a cross-tenant access/data-integrity issue.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (an ordinary, unprivileged action) and be able to POST directly to the app's public webhook endpoint with custom headers — no secrets, tokens, or privileged access are needed. The only nontrivial step is capturing one valid `(raw_body, hmac)` pair for a topic of interest, which happens automatically whenever Shopify delivers any webhook to the attacker's own installation.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed content for webhook requests, or otherwise cryptographically bind the shop domain to the payload before trusting it in `WebhookMetadata`. At minimum, cross-check the header-derived `shop` against Shopify's IP ranges/mTLS or against a shop known to have an active, registered webhook subscription with that exact `webhook_id`, rather than trusting the header value once the (unrelated) body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook POST to the app's endpoint with a real `x-shopify-hmac-sha256` computed over `raw_body` using the app's `api_secret_key`, and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this exact `(raw_body, hmac)` pair (e.g., via their own reverse proxy/logging on infrastructure they control, or a controlled webhook receiver print).
3. Attacker crafts a new POST to the app's public webhook route with the *same* `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which passes because it only checks `raw_body` against the HMAC [6](#0-5) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's chosen `body`, and performs tenant-scoped work against the victim shop using attacker-controlled data.
