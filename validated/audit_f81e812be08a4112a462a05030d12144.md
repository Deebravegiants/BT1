## Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers from an HTTP header, but `HmacValidator` only authenticates the raw request body, not this header. An attacker who can obtain any single validly-signed webhook body (e.g. by installing the app on their own store and receiving one legitimate webhook delivery) can replay that body to the app's webhook endpoint with a forged `shop-domain` header naming a victim shop, and the signature check still passes.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw HTTP body: [2](#0-1) 

But the `shop` (and `topic`/`api_version`/`webhook_id`) values consumed by the rest of the library come from separate, un-signed HTTP headers: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.shop` as the tenant identity and forwards it to the application's handler: [4](#0-3) 

The equality that should hold is: **shop asserted to the handler == shop that Shopify's HMAC actually attests to**. Because the signature is computed over the body alone, this equality is never checked — `request.shop` can be swapped for any arbitrary string while the HMAC over the (unchanged) body remains valid. This is structurally the same class of bug as the dividend-gaming report: a value that drives a security-relevant decision (`shop` deciding which tenant's data/session the webhook applies to, analogous to `normalAverageFee` deciding payout) is derived from data that is not covered by the verification mechanism (HMAC, analogous to the trade-fee sampling window), letting an attacker manipulate that value while still passing validation.

### Impact Explanation
An unprivileged attacker who operates or has ever installed the app on their own shop can capture one legitimate, validly-HMAC-signed webhook body (any topic/body is sufficient, since only the raw body is checked). They can then replay that exact body to the app's webhook endpoint any number of times with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header naming a different, victim shop (and forged `shopify-topic` if desired). `Registry.process` will accept it as authentic (`Utils::HmacValidator.validate` only checks the body) and dispatch it to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`. Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's records to create/update/delete (the documented and expected usage pattern) will act on the victim shop's identity using attacker-supplied content — a cross-tenant data/action confusion driven entirely by unauthenticated header data.

### Likelihood Explanation
The only prerequisite is the ability to trigger, or otherwise obtain, one authentic webhook delivery from Shopify for any shop (trivially available to any developer with a Shopify partner/dev account and no app secret is required). The attacker never needs `api_secret_key`, an access token, or any privileged credential — they only need to control the HTTP headers of the request they send to the app's own webhook endpoint, which is fully within reach of an "unprivileged internet user" sending crafted HTTP requests.

### Recommendation
Include the tenant-identifying and topic headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signed material that `HmacValidator` verifies, or otherwise cryptographically bind them to the body (e.g., require the host app to independently confirm the `shop` against a known, already-authenticated session/shop record before trusting the webhook), rather than trusting them as free-standing headers alongside a body-only HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g.:
   - Headers: `shopify-hmac-sha256: <valid-signature-for-body>`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`
   - Body: `{"id":1,...}`
2. Attacker resends the identical body to the app's webhook endpoint but changes only the `shopify-shop-domain` header (and optionally topic) to `victim-shop.myshopify.com`, keeping the same `shopify-hmac-sha256` value (valid because it only ever signed the unchanged body):
   ```ruby
   ShopifyAPI::Webhooks::Request.new(
     raw_body: original_body,
     headers: {
       "shopify-topic" => "orders/create",
       "shopify-hmac-sha256" => original_valid_hmac,
       "shopify-shop-domain" => "victim-shop.myshopify.com",
     },
   )
   ```
3. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `raw_body`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the app processes attacker-controlled content under the victim shop's tenant identity.
