## Finding

### Title
Webhook `shop` and `topic` identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw body only, while the `shop` (and `topic`) values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook to a tenant come from unauthenticated HTTP headers. Any consumer who can obtain one legitimately-HMAC-signed webhook body/signature pair (e.g., by owning a shop that installs the app) can replay that same body+HMAC to the app's shared webhook endpoint while substituting the `shop-domain` header for a victim shop, and the library will accept it as valid and hand it to the handler labeled as belonging to the victim tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only expose/sign the raw JSON body: [1](#0-0) [2](#0-1) 

`shop` and `topic` are read from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`, `shopify-topic` / `x-shopify-topic`) and are never part of `to_signable_string`: [3](#0-2) 

`Utils::HmacValidator.validate` only checks the body-derived signature against `api_secret_key`; it never checks that the signature is bound to a specific shop: [4](#0-3) 

`Webhooks::Registry.process` trusts `request.shop` (and `request.topic`) as the tenant identifier passed to the app's handler, gated only by the body HMAC check: [5](#0-4) 

The binding that should hold is:
`shop_used_for_tenant_attribution == shop_the_signature_was_actually_issued_for`

But the code only verifies:
`HMAC(body, api_secret_key) == received_hmac`

with no cryptographic tie between that HMAC and the `shop` value taken from the header. Since `api_secret_key` is the same app-wide `client_secret` shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app can obtain a validly-signed `(body, hmac)` pair for their own shop from Shopify (their app endpoint receives it), then resend that identical body and HMAC to the shared webhook endpoint with the `shop-domain` (and optionally `topic`) header rewritten to name a different, victim shop that also uses the app. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on `WebhookMetadata#shop` for (e.g., looking up the victim's session/data store and writing the spoofed payload's contents under the victim's tenant). This is a cross-tenant data-injection vector: an unprivileged app installer can inject attacker-controlled webhook data (orders, customers, GDPR requests, app/uninstall events, etc.) attributed to another merchant's shop, without ever needing that merchant's credentials, access token, or `client_secret`. This satisfies the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
Any user who can install the app on their own store (a normal, unprivileged action available to any Shopify merchant) automatically receives real, validly-HMAC-signed webhook deliveries for their own shop and fully controls the destination URL/headers of the replay request, since the endpoint is a public HTTP(S) callback the app exposes. No special access, secrets, or privileged accounts are required — only the ability to install the target app and capture one of its own delivered webhooks.

### Recommendation
Bind the shop (and ideally topic) identity into the material that is authenticated, or otherwise cryptographically verify that the received `shop-domain` header corresponds to the shop the webhook was actually issued for (e.g., cross-check against a known/registered shop record, or require the caller to supply an independently-authenticated shop context) before trusting `request.shop` for tenant attribution in `Registry.process`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; register for topic `customers/data_request` (or any registered topic).
2. Capture the webhook Shopify delivers to the app's public webhook endpoint: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(B, client_secret)`).
3. Replay an HTTP POST to the same public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (body/HMAC match, per `lib/shopify_api/utils/hmac_validator.rb`), `ShopifyAPI::Webhooks::Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, and the app processes attacker-controlled data as if it originated from the victim's store.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
