### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (tenant identifier) is read from the unsigned `x-shopify-shop-domain` header. `Registry.process` validates the HMAC over the body only and then trusts `request.shop` directly when dispatching to the host app's handler, so the tenant binding `shop_authenticated == shop_signed` is never enforced.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value using a constant-time compare: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body, and `shop` is read from a separate header that plays no role in the signature at all: [2](#0-1) [3](#0-2) 

`Registry.process` only checks the HMAC (over the body) and then forwards `request.shop` — taken straight from the attacker-controllable header — to the app's handler as the trusted tenant identifier, with no cross-check that this shop is the one the signature actually vouches for: [4](#0-3) 

The `api_secret_key` used to sign/verify webhooks is a single shared secret for the whole app (all shops that installed it), not a per-shop secret: [5](#0-4) 

This means an unprivileged user who owns/controls **any** shop that has installed the app (or otherwise obtains one legitimate `(raw_body, hmac)` pair produced by Shopify, e.g. from their own store's webhook deliveries) can capture that valid body+hmac pair and POST it directly to the app's public webhook endpoint while swapping only the `x-shopify-shop-domain` header to a victim shop's domain. Since the signature never covered the shop field, `HmacValidator.validate` still succeeds, and `Registry.process` passes the forged `shop` value on to the handler as if it were authenticated data belonging to that shop.

This breaks the identity binding: `shop_verified_by_hmac == shop_delivered_to_handler` does not hold — the byte range actually verified (raw body) is disjoint from the byte range that determines tenant attribution (the header).

### Impact Explanation
Any host application that uses `request.shop`/`WebhookMetadata#shop` from this gem to decide which merchant's data record to create/update/delete (the intended and documented usage pattern) can be made to write/act on a victim shop's data using a payload the attacker fully controls (subject to whatever topic/body the attacker's own store legitimately produced). This is a cross-tenant integrity issue: one merchant can inject or corrupt another merchant's webhook-driven state without ever possessing the victim's credentials. Per the rubric this falls under Critical — cross-tenant access — because the gem's own verification primitive (`HmacValidator`) is what host apps rely on to establish the trust boundary per shop, and it does not actually bind the shop identity into what is cryptographically verified.

### Likelihood Explanation
Exploitation requires only: (1) being an unprivileged user who can install the app on their own store (standard, unprivileged action for any public Shopify app) or otherwise capture one valid delivered webhook, and (2) sending a normal HTTP POST to the app's public webhook URL with a modified `x-shopify-shop-domain` header. No access token, `api_secret_key`, or privileged account is needed — the shared app secret is the only cryptographic material involved, and it's never exposed to the attacker; they only replay bytes they legitimately received. This is a realistic, low-effort attack path.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cross-validate the header-derived shop against an independently trusted source before dispatch. At minimum, `Registry.process` should not treat `request.shop` as authenticated merely because the HMAC validated the body; the gem should document/enforce that host apps must independently confirm the shop belongs to a session/subscription they registered for that specific webhook (e.g., by checking the shop against the webhook registration/subscription they created, rather than trusting the header verbatim).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one delivery: raw body `B` and its valid header `x-shopify-hmac-sha256: H` (where `H = HMAC-SHA256(secret, B)`).
3. Attacker sends a POST directly to the app's public webhook endpoint with:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-hmac-sha256: H`
   - body `B`
4. `ShopifyAPI::Webhooks::Request.new` builds the request object from these headers/body.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation passes because it never considered the shop header.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes body `B` as if Shopify vouched for that shop, even though it was Shopify's message for `attacker-shop.myshopify.com`.
