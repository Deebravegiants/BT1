### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant spoofing of webhook origin - (File: lib/shopify_api/webhooks/request.rb)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body` [1](#0-0) . The HMAC is computed and verified with `Utils::HmacValidator.validate`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header value [2](#0-1) . Since `to_signable_string` is exclusively `@raw_body`, the HMAC binds **only the request body**, not the `shop`, `topic`, `webhook_id`, or `api_version` values, all of which are read directly from unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) [3](#0-2) .

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the `WebhookMetadata` passed to the host application's handler [4](#0-3) . The equality that should hold is: `shop bound by HMAC == shop delivered to handler`. In fact, the HMAC only proves `H(secret, raw_body)` is valid; it says nothing about which shop or topic the body was intended for.

Because a single app has one `Context.api_secret_key` shared across **every merchant/tenant** that installs the app, any merchant who installs the app can receive a legitimately-signed webhook for their own shop (a valid `(raw_body, hmac)` pair). That pair remains cryptographically valid regardless of the `shopify-shop-domain` / `shopify-topic` header values sent alongside it, because those headers are excluded from the signable string. An attacker who controls one tenant of the app can therefore capture a genuine `(body, hmac)` pair from their own installation and re-submit it to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a victim shop (and/or `shopify-topic`/`webhook_id` altered). `HmacValidator.validate` will still return `true` since only the body is checked, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop [5](#0-4) .

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on: `request.shop` from a "verified" webhook is trusted as the authoritative tenant key (this is the entire purpose of the shop field in `WebhookMetadata`) [6](#0-5) . Any host application that uses `WebhookMetadata#shop` to select which merchant's session/data to update — the documented and intended use pattern of this gem's webhook module — can be tricked into attributing an attacker-supplied payload to a different tenant's shop identity, i.e., cross-tenant data corruption/impersonation without ever knowing `Context.api_secret_key`.

### Likelihood Explanation
Any actor who can install the app on at least one shop (a normal, unprivileged action for a public Shopify app) can obtain a validly-signed `(body, hmac)` pair, since Shopify sends legitimate webhooks to installed apps. This gem's own signable-string implementation then makes it possible to reuse that pair while forging the shop/topic headers, since those fields are never part of the signed content on the library side. No leaked secrets, TLS interception, or privileged access are required — only normal app installation, an intercepted or observed webhook payload for one's own store, and the ability to POST to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (not just the body) in the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., verify that Shopify's webhook signature covers header+body per Shopify's documented behavior) so `Utils::HmacValidator.validate` fails if any of those identity fields are altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a real webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared secret), `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `(B, H)` to the app's public webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses headers normally [7](#0-6) ; `hmac` returns the decoded header value and `to_signable_string` returns `B` [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation passes [9](#0-8) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes `B` as if it were genuinely reported for `victim-shop`, even though it was never signed with that shop in mind [10](#0-9) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
