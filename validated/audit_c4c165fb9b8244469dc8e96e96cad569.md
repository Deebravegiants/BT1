### Title
`EmporiumUpgradeable.verifyWallet`'s EIP-712 signature omits `feeStructure.feeToken`, letting the tx submitter drain an arbitrary ERC20 held by the wallet up to `maxFee` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.verifyWallet` recovers an EIP-712 signature (`EMPORIUM_SIGNATURE_TYPEHASH`) that binds `emporiumMessage`, the hashed `ops`, `maxFee`, and `deadline`, and separately requires `feeStructure.flatFee <= stack.maxFee`. It never binds `circomData.feeStructure.feeToken` into the signed digest. `payRelayFees` then calls `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`, moving `feeToken` directly out of the user's `HinkalWallet` contract. Because `feeToken` is unconstrained by the signature and unconstrained by any on-chain equality (it need not even appear in `circomData.erc20TokenAddresses` — the `!foundToken` branch pays `feeStructure.flatFee` of `feeStructure.feeToken` regardless), whoever assembles `circomData` (the relay/transaction submitter, not necessarily `stack.signerAddress`) can choose *which* ERC20 held by the wallet is drained, while the signer only ever agreed to a bare numeric cap (`maxFee`) with no token context.

### Finding Description
The signed payload is:
```solidity
bytes32 hashedMessage = _hashTypedDataV4(
    keccak256(
        abi.encode(
            EMPORIUM_SIGNATURE_TYPEHASH,
            circomData.emporiumMessage,
            _hashEmporiumOps(stack.ops),
            stack.maxFee,
            stack.deadline
        )
    )
);
``` [1](#0-0) 

`feeStructure.feeToken` (and `feeStructure.flatFee`/`variableRate` beyond the single `maxFee` cap check) is not part of `EMPORIUM_SIGNATURE_TYPEHASH`, so the signer's EIP-712 approval says nothing about *which* asset will be moved from their wallet: [2](#0-1) 

The only cap enforced is a raw numeric comparison with no decimal/asset context:
```solidity
if (circomData.feeStructure.flatFee > stack.maxFee) {
    revert FeeExceedsSignedMax();
}
``` [3](#0-2) 

`payRelayFees` then pays `feeStructure.flatFee` of `feeStructure.feeToken` from the wallet even if that token is not among `circomData.erc20TokenAddresses` at all (the fallback branch): [4](#0-3) 

which invokes:
```solidity
function sendToRelayFromWallet(...) internal {
    if (relayFee > 0) {
        IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken);
    }
}
``` [5](#0-4) 

`HinkalWallet.doSendToRelay` is `onlyEmporium`-gated, but performs no token whitelist and blindly transfers whatever `erc20TokenAddress` it's told: [6](#0-5) 

`circomData` (including `feeStructure`) is assembled by whoever submits the `transact` call (the relay/prover), not necessarily `stack.signerAddress`; the wallet owner only pre-signs `(emporiumMessage, ops, maxFee, deadline)` off-chain for a meta-tx-style flow. Because the token identity is missing from that signature, the equality the signer actually intended ("pay at most `maxFee` of token X") is broken: the submitter can substitute any ERC20 as `feeToken`, and the wallet will pay up to the raw `maxFee`/`flatFee` number of that substituted token — draining a token of far greater value or a token the signer never agreed to spend, limited only by the wallet's balance of that token.

### Impact Explanation
This is an unauthorized wallet operation: `doSendToRelay` moves ERC20 assets out of the user's `HinkalWallet` for an asset the signer never approved, based on a signature that is silent on which token is spent. Depending on which token the submitter substitutes and how much of it the wallet holds, this can result in theft of protocol/relay fees far beyond what was authorized, or draining an entirely different (and potentially far more valuable) asset than the one the signer intended to pay fees with — this is "executing calls or moving assets a wallet owner or prover never authorised," classified High (and potentially Critical if the drained asset is user's shielded-adjacent in-flight funds sitting in the wallet).

### Likelihood Explanation
Likelihood is high in any deployment that uses the gasless/meta-tx pattern (a relay submits `circomData` on behalf of a `stack.signerAddress` who only supplied an off-chain EIP-712 signature). Any relay or party capable of assembling and submitting the `transact()` calldata (which is unprivileged — no `onlyRole`/`onlyOwner` gate on `Hinkal.transact` or `EmporiumUpgradeable.runAction` beyond `onlyAllowedRecipient` from the external-action dispatch) can pick `feeStructure.feeToken` freely once they have a valid signature for `(emporiumMessage, ops, maxFee, deadline)`.

### Recommendation
Include `feeStructure.feeToken` (and ideally `flatFee`/`variableRate`) explicitly inside `EMPORIUM_SIGNATURE_TYPEHASH` so the signer's approval is bound to a specific token and fee terms, not just a bare numeric cap decoupled from the asset being spent.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` off-chain with `maxFee = 100` intending to pay 100 units of a low-value/high-decimal stablecoin they hold a small balance of, and hands the signature to a relay to submit.
2. The relay/submitter builds `circomData` with `feeStructure.feeToken` set to a different, high-value ERC20 (e.g., a governance token or a low-decimal token) that the wallet also holds a balance of, and `feeStructure.flatFee = 100` (within `maxFee`, so `verifyWallet` passes).
3. `runAction` → `payRelayFees` sees this token is either the fee-charged token or, if not present in `erc20TokenAddresses` at all, falls into the `!foundToken` branch and unconditionally pays `feeStructure.flatFee` of `feeStructure.feeToken` via `sendToRelayFromWallet`.
4. `HinkalWallet.doSendToRelay` transfers 100 units of the attacker-chosen token from the wallet to `circomData.relay`, an asset and amount the signer never approved in the signed payload.
