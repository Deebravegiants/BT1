### Title
Webhook shop identity spoofing via unsigned `shop-domain` header — HMAC covers only the raw body, not the shop attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant attribution from an HTTP header that is never included in the HMAC signature computation. `Registry.process` validates only the HMAC over the raw body and then trusts the unverified `shop` header for dispatch, breaking the identity binding: `shop that produced a valid HMAC` ≠ `shop attributed to the webhook by the handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from an HTTP header, with no verification against the signature: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (i.e. the body): [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally forwards `request.shop` — the unauthenticated header value — to the handler as the tenant identifier: [4](#0-3) 

Because the HMAC is computed purely from the body and the app's `client_secret`, and the body content and its resulting HMAC are identical for every shop that produces the same body bytes, a valid `(raw_body, hmac)` pair obtained from one shop remains a valid pair regardless of which `shop-domain` header is attached. This breaks the intended identity binding: `shop-domain header == shop that authored the HMAC-signed body`.

### Impact Explanation
Multi-tenant apps built on this gem rely on `WebhookMetadata#shop` (populated from `request.shop`) to determine which merchant record a webhook payload belongs to (e.g., storing/updating data, triggering GDPR redaction actions, or shop-scoped side effects) after `Registry.process` reports the HMAC as valid. Since the shop attribution is never bound to the signature, an attacker who has captured any single legitimate `(raw_body, hmac-sha256, topic)` webhook delivery (trivially available by installing the app on a shop they control themselves, or from any exposed/replayed webhook) can resubmit that exact body and HMAC to the app's webhook endpoint while substituting `shopify-shop-domain` (or `x-shopify-shop-domain`) with an arbitrary target shop domain string. `HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` dispatches the handler with the attacker-chosen `shop`. This is a cross-tenant confusion primitive: the host application, correctly following this gem's documented API (`WebhookMetadata#shop`), processes data under the wrong tenant identity.

### Likelihood Explanation
This requires no privileged access, no leaked secret, and no TLS interception. An unprivileged internet user can obtain a valid body+HMAC pair simply by installing the developer's app on their own store (a normal, permitted action for any Shopify merchant/developer) or capturing any webhook delivery, then POST it directly to the app's public webhook endpoint with a forged `shop-domain` header. The webhook endpoint is by design a public HTTP endpoint reachable from the internet, and the gem provides no mechanism to bind the header to the signature.

### Recommendation
Include the shop domain (and topic/webhook id, ideally) in the signed material, or otherwise cryptographically bind `shop` to the payload before dispatch. Since Shopify's actual HMAC scheme signs only the body by protocol design, the safer mitigation inside this gem is to require callers to supply the shop id via an authenticated channel (e.g., verify the `shop-domain` header value against a known/registered shop list, or require TLS client identity / mutual auth at the transport layer) rather than trusting `request.shop` implicitly. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used for authorization decisions without additional verification (e.g., cross-checking against the session/shop that registered the webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` (a legitimate, unprivileged action) and lets Shopify deliver a real webhook, capturing:
   - `raw_body` = `{"id": 1, ...}`
   - `shopify-hmac-sha256` = `<valid-signature-for-raw_body>`
2. Attacker sends a forged HTTP POST directly to the app's webhook endpoint with:
   ```
   shopify-topic: orders/create
   shopify-hmac-sha256: <the captured valid signature>
   shopify-shop-domain: victim-shop.myshopify.com
   body: <the captured raw_body, byte-identical>
   ```
3. `Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` returns only `raw_body` — the `shop-domain` header is irrelevant to signature verification. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
