### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` uses `request.topic` to select the handler and passes `request.shop` straight into `WebhookMetadata`, trusting both values even though neither is bound by the HMAC that `Utils::HmacValidator.validate` checks.

### Finding Description
The identity binding that should hold is: `hmac(raw_body, client_secret) valid` ⇒ `(shop, topic)` used for routing/tenant attribution are the same `(shop, topic)` Shopify actually signed for. In this gem that binding does not exist:

- `to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `api_version`, `webhook_id` are parsed straight from headers with no relation to the signed bytes: [2](#0-1) 
- `HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) 
- `Registry.process` accepts the request once the body HMAC checks out, then uses the *unverified* `request.topic` to pick a handler and forwards the *unverified* `request.shop` to the handler: [4](#0-3) 

Because a single `client_secret` is shared across all shops that install a public app, any body+HMAC pair that was legitimately produced by Shopify for shop A (or for topic X) remains a **valid** `(body, hmac)` pair when replayed with the `shop-domain` header changed to shop B and/or the `topic` header changed to topic Y. `HmacValidator.validate` will still return `true` because it never inspects those headers, so `Registry.process` will route the (attacker-relabelled) payload to a different handler and attribute it to a different tenant than the one Shopify actually generated it for.

This is the same bug class as the reported analog: a value that is *acted upon* (here, the `shop`/`topic` used for tenant attribution and handler dispatch) is not covered by the authentication check (the HMAC), so the equality `signed_identity == acted_on_identity` silently breaks.

### Impact Explanation
An attacker who controls (or has previously received) a legitimate webhook delivery to their own shop can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair and resend it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. Because the HMAC only proves "Shopify produced this body with the shared secret," not "for this shop/topic," the app will process attacker-controlled shop/topic attribution as if it were verified — leading to cross-tenant data being recorded/acted upon under the wrong shop, or a payload being dispatched to a handler for a topic it was never issued for. This falls under the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to have received at least one genuine webhook to a shop they control (trivial — any merchant with the app installed receives them) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint (also trivial for an unprivileged internet user, since this is the same endpoint Shopify calls). No access token, `client_secret`, or privileged account is required, satisfying the in-scope threat model.

### Recommendation
Include the header fields that drive trust decisions (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material that `HmacValidator` checks, or otherwise independently verify `request.shop` against the shop associated with the session/subscription that the webhook was registered for before dispatching to a handler. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for tenant attribution unless they are cryptographically bound to the payload that was HMAC-verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook delivery (e.g., `orders/create`), capturing the raw body `B` and the `x-shopify-hmac-sha256` header `H` from the request Shopify sends to the app.
2. Attacker crafts a new HTTP request to the same webhook endpoint using body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`).
3. `HmacValidator.validate` recomputes the HMAC over `B` only [1](#0-0)  and it matches `H`, so `Registry.process` accepts the forged request and calls the handler with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` [4](#0-3) , even though Shopify never issued this webhook for that shop.
