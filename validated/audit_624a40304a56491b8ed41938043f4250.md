Confirmed the design: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , while `shop` (the tenant identifier used downstream) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never mixed into the HMAC computation [2](#0-1) . `HmacValidator.validate` verifies only the body/secret pair via `OpenSSL.secure_compare` [3](#0-2) , and `Registry.process` forwards `request.shop` straight into the handler payload once that check passes [4](#0-3) . This is the exact bug class described in the report (a field that drives tenant-scoped behavior is not covered by the authenticator, so state can desynchronize from the true owner), which I'll write up below.

### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant (`shop`) that a webhook is attributed to purely from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature (`HmacValidator.validate`) is computed only over the raw request body. Because the app's `api_secret_key` is a single shared secret used to sign webhooks for *every* shop that has installed the app, a valid `(body, hmac)` pair from one shop's own genuine webhook can be paired with a different `shop-domain` header value and still pass validation — attributing attacker-controlled event data to a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, comes from a header that is not part of that signable string at all: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC solely over `verifiable_query.to_signable_string` (the body) using `Context.api_secret_key` and compares it to the received signature: [5](#0-4) 

Once that check passes, `Registry.process` trusts `request.shop` unconditionally and hands it to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is:
`hmac_verified_bytes == bytes_that_determine_tenant`

but here `hmac_verified_bytes = raw_body` while `bytes_that_determine_tenant = shop-domain header`, so the equality is broken — the header can be swapped for any value without invalidating the signature, since the signature never covered it in the first place.

This mirrors the report's root cause: state (here, "which shop owns this event") is tracked/derived from a channel (`shop-domain` header) that is disjoint from the channel that was actually authenticated (`raw_body` HMAC), permitting the two to desynchronize — just as Morpho's per-user ledger desynchronized from the actual on-chain Aave position after a liquidation that bypassed Morpho's own accounting path.

### Impact Explanation
Any shop that has installed the app receives genuinely-signed webhooks from Shopify (signed with the app's single shared `client_secret`) for its own store's events. Because the signature never binds to the `shop-domain` header, that same `(body, hmac)` pair remains valid when replayed against the app's webhook endpoint with the header rewritten to a different, victim shop's domain. This lets one tenant's data (order, product, customer content controlled by that tenant) be injected into the app's per-shop state for another tenant — a cross-tenant access/data-integrity violation, which is a Critical-impact category per the exploit surface of this gem.

### Likelihood Explanation
Exploitation requires only: (1) being a merchant who has legitimately installed the app on any shop (an ordinary, low-privilege relationship, not a leaked secret or privileged account), and (2) the ability to submit an HTTP POST to the app's public webhook endpoint with a chosen body/header combination — no knowledge of `api_secret_key` or any access token is needed, since the HMAC used is one already legitimately produced by Shopify for the attacker's own shop.

### Recommendation
Include the shop domain (and other webhook-identifying headers such as topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the verified payload (e.g., require the `shop` inside the JSON body to match the header, and additionally verify the shop is one for which the app holds an active session/installation before dispatching to handlers).

### Proof of Concept
1. App has `Registry.add_registration` set up for topic `products/update` with a handler that persists `data.body` keyed by `data.shop`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a `products/update` event with attacker-chosen `body` content; Shopify sends the app a webhook with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_of_body>`.
3. Attacker (having visibility of this outgoing request, e.g. via a webhook delivery/log/replay tool they control for their own shop) resends the identical body and HMAC to the app's webhook endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against `Context.api_secret_key`, which is unchanged. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"`, causing attacker-controlled data to be written into the app's state for the victim tenant.
