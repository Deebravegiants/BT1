### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by computing an HMAC over the raw request body only, while the `shop` field that identifies which tenant the webhook belongs to is taken from an unauthenticated header and is never included in the signed material.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)` [1](#0-0) , and the comparison itself is constant-time and otherwise correct [2](#0-1) .

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read straight from the `hmac-sha256` header [3](#0-2) [4](#0-3) . The `shop` accessor is read from the `shop-domain` header with no cryptographic tie to the HMAC at all [5](#0-4) .

`Registry.process` validates only the HMAC of the body, then immediately hands `request.shop` (the unauthenticated header value) to the app's handler as the tenant identifier for the event, alongside the (authenticated) body: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) .

The identity binding that should hold is: `shop_header == shop_bound_by(hmac)`. In this implementation that never holds — the HMAC only proves `body` is authentic under the app's single, cross-tenant `client_secret` (the same `Context.api_secret_key` is used to verify webhooks for every shop that has the app installed, confirmed by `HmacValidator.validate` using the single `Context.api_secret_key`/`Context.old_api_secret_key` with no per-shop key) [1](#0-0) . Because the same secret authenticates events for *every* tenant, and the `shop` field is excluded from the signed bytes, a valid `(body, hmac)` pair captured from any tenant's traffic can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a different, victim shop — the HMAC still validates because it never covered `shop` in the first place.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as the gem's own webhook flow forwards it) to select which merchant's session/access token to act on, an attacker who can obtain one valid `(body, hmac)` pair for any shop can forge webhook deliveries attributed to an arbitrary other shop, and get the app to process events/dispatch effects (e.g., data writes, notifications, order-linked business logic) under the wrong tenant's identity. This is a cross-tenant identity confusion rooted in the gem's webhook verification contract, not merely an application bug, since the gem provides `request.shop` as if it were verified alongside the body.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimate `(raw_body, hmac)` pair, which is plausible for any shop owner that installs the app (e.g., via Shopify's webhook test/re-delivery tooling, or any means of observing their own shop's webhook traffic to the app), and to be able to POST directly to the app's public webhook endpoint with a modified `shop-domain` header — something within reach of any unprivileged internet user who knows the endpoint URL, no `api_secret_key` or access token required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed material, or otherwise cryptographically or out-of-band bind the asserted `shop` header to the specific installation before trusting it (e.g., require the caller to separately validate `request.shop` against a shop that is actually known/installed and reject unrecognized shops), so that `WebhookMetadata#shop` cannot diverge from the shop the HMAC actually authenticates.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)` and `client_secret` is shared across all installs).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop-domain` header [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H` [8](#0-7) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the event body was never authenticated for that shop [9](#0-8) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
