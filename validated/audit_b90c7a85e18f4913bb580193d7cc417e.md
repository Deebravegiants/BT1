### Title
Stale confirmations from removed multisig members are still counted toward quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` removes a departing member from the `members` set and deletes *their own* pending requests, but it never scans other members' still-open requests to strip that member's prior `confirm` votes out of `self.confirmations`. Because `confirm()` only counts the raw size of the stored confirmation set against `num_confirmations`, a confirmation cast by a member before removal continues to count toward quorum after that member is no longer trusted — directly mirroring the "removed guardian votes still counted" bug described in the external report for `TrustedGuardiansPlugin`.

### Finding Description
`confirm()` performs the quorum check purely on the stored confirmation set size, without validating that every entry in that set still belongs to a current member: [1](#0-0) 

`delete_member` is the only place that mutates confirmation state on member removal, and it only cleans up requests *submitted* by the removed member — it does not touch `self.confirmations` entries for requests submitted by *other* members that the removed member had already confirmed: [2](#0-1) 

`assert_valid_request`, called from both `confirm` and `delete_request`, likewise only checks that the *caller* is currently a member — it never re-validates the members recorded in an existing confirmation set: [3](#0-2) 

As a result, if member `M` confirms request `R` (created by another member) and is later removed from the multisig via `DeleteMember`, `R`'s confirmation set still contains `M`'s entry. When the remaining live members confirm `R`, `M`'s stale vote is counted toward `num_confirmations`, so the request can execute with fewer genuinely-authorized live confirmations than the configured threshold requires. The publicly exposed `get_confirmations`/`get_num_confirmations` view methods also surface this stale, misleading data, matching the second half of the external report.

The legacy `multisig/src/lib.rs` contract has the analogous flaw in its `DeleteKey` action, which only removes confirmations for requests originated by the deleted public key, not confirmations that key cast on other members' requests: [4](#0-3) 

### Impact Explanation
This is a confirmation/quorum-bypass bug in the multisig contract that controls a NEAR account's funds and permissions (transfers, key/member management, arbitrary function calls). A request can be executed after being approved by fewer live, currently-trusted members than `num_confirmations` mandates, because a removed member's historical vote persists and is silently counted. This undermines the core security guarantee of the K-of-N scheme and can let a request pass with an insufficient number of currently-authorized approvers, enabling unauthorized transfer/spend or unauthorized state-transition execution.

### Likelihood Explanation
This requires a normal, expected operational sequence: a member confirms a pending request, and before it accumulates enough confirmations, that member is removed from the multisig (e.g., due to key rotation, offboarding, or compromise response) — none of which is a privileged-attacker action beyond ordinary multisig administration, and it does not require the remaining members to do anything unusual (they simply keep confirming as normal). Once triggered, the removed member's confirmation silently remains in effect for that request without any additional action needed.

### Recommendation
When executing `DeleteMember` (and `DeleteKey` in the legacy contract), iterate over all active requests' confirmation sets and remove any entry belonging to the removed member/public key, not just requests they personally submitted. Alternatively, validate at `confirm()`/execution time that every entry counted in a confirmation set still corresponds to a current member of `self.members` before comparing against `num_confirmations`, and filter stale entries out of `get_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract` with members `[A, B, C]` and `num_confirmations = 2`.
2. Member `B` calls `add_request` to create request `R` (receiver/action arbitrary, e.g. a `Transfer`). `add_request` does not auto-confirm.
3. Member `A` calls `confirm(R)`; `R` now has confirmations `{A}` (1 of 2 required — not yet executed).
4. The group submits and confirms a `DeleteMember { member: A }` request, removing `A` from `self.members` and deleting `A`'s access key via `delete_member` (multisig2/src/lib.rs:356-379). Note this path only cleans up requests *originated by* `A`, not `R`'s confirmation set.
5. `R`'s confirmations set still contains `A`'s stale entry: `{A}`.
6. Member `C` (the only two "should-be" required live confirmers being `B`/`C`, but neither has confirmed `R` besides the now-removed `A`) calls `confirm(R)`. The check `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `1 + 1 >= 2` → true, and `R` executes — even though `A` is no longer a member and only one currently-active member (`C`) has actually approved it.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
