### Title
Missing contract-existence check on low-level token transfers in `withdraw()` and `SweepDust` handling allows fake escrow release/refund without any funds moving - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `RequestKind.SweepDust` branch of `onAccept()` use raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` to move escrowed tokens to a beneficiary, instead of the `SafeERC20` wrapper that the same contract already imports and uses elsewhere (`using SafeERC20 for IERC20;`). A low-level `call` to an address with no deployed code always returns `success = true` with empty return data, so these functions treat a "transfer" to a non-existent contract as successful, permanently mark the escrow as released/refunded, and never revert.

### Finding Description
The contract declares `using SafeERC20 for IERC20;` and uses `safeTransferFrom`/`safeTransfer` for token intake in `placeOrder` and fill flows [1](#0-0) . However, `withdraw()`, which is reached from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse()`, pays out escrowed tokens via a raw `.call` with no check that `token` actually has deployed bytecode:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

The same unguarded pattern is used for fee redemption in the same function [3](#0-2)  and for the `SweepDust` handler that pays `req.beneficiary` from arbitrary `req.outputs[i].token` addresses decoded from a relayed cross-chain message body [4](#0-3) .

`withdraw()` is invoked from `onAccept()`, which is called by the trusted host but processes `WithdrawalRequest`/`SweepDust` payloads whose `token` fields originate from `order.inputs`/`order.output` set by the (untrusted) order-placing user, or GET-response-driven paths via `onGetResponse` [5](#0-4) [6](#0-5) . If a `token` address in the withdrawal/sweep body has no contract code at the time of payout — e.g. it points to an EOA, an address that hasn't been deployed to yet, or a self-destructed contract — the low-level `call` still reports success. The function proceeds to decrement `_orders[body.commitment][token]` and emit `EscrowReleased`/`EscrowRefunded`/`DustSwept` as if the payout succeeded, even though the beneficiary received nothing.

This is the same root-cause bug class as the referenced Surge `Pool.sol` finding: low-level calls return `success = true` against addresses with no code, so the contract updates internal accounting on a false positive.

### Impact Explanation
Funds recorded as escrowed (`_orders[commitment][token]`) get zeroed out / marked as delivered without the beneficiary actually receiving the tokens, resulting in a permanent loss of the escrowed funds for the legitimate order owner or solver — the accounting says the order was filled/refunded/dust-swept, but the tokens remain stuck in the `IntentGatewayV2` contract with no remaining record entitling anyone to reclaim them. This qualifies as concrete permanent freezing/loss of user funds.

### Likelihood Explanation
This path is reachable by any user via the normal escrow lifecycle: placing an order, then having it filled/cancelled/timed-out and driving a `RedeemEscrow`, `RefundEscrow`, or `SweepDust` message through the host. While ordinary well-formed ERC20 addresses have code, edge cases such as pre-deployment / not-yet-deployed token addresses referenced in an order, chains where a token can be `SELFDESTRUCT`-ed (EIP-6780 permits self-destruct within the same transaction of creation, and legacy/older EVM chains still allow full destruction), or attacker-supplied bogus token addresses in cross-chain relayed request bodies make this a realistic misconfiguration/edge-case trigger rather than a purely theoretical one.

### Recommendation
Before performing the low-level `call` for token transfers in `withdraw()` (both the token loop and the fee-redemption branch) and in the `SweepDust` handler, verify the target has deployed code, e.g. `require(token.code.length > 0, "IntentGatewayV2: no code at token");`, or replace the raw `.call` usages with the already-imported `SafeERC20.safeTransfer`, which enforces this check consistently with the rest of the contract.

### Proof of Concept
1. An order is placed with `order.inputs[i].token` (or a sweep/withdrawal body's `tokens[i].token`) set to an address `T` that currently has no deployed contract code (e.g., a CREATE2 address not yet deployed, or a token contract that later self-destructs before the escrow is redeemed).
2. The order proceeds through the normal flow so `_orders[commitment][T]` becomes non-zero (representing escrowed value).
3. A `RedeemEscrow`/`RefundEscrow` message (or `SweepDust` request) is relayed and processed by `onAccept()`, invoking `withdraw()`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is executed against `T`; since `T` has no code, the EVM returns `success = true` with empty `returndata` without executing any actual transfer logic.
5. `withdraw()` treats this as a successful payout, decrements `_orders[body.commitment][token]`, and emits `EscrowReleased`/`EscrowRefunded`. The beneficiary receives no tokens, and the escrow accounting no longer reflects any claim to the funds — resulting in a permanent loss of the escrowed amount.
