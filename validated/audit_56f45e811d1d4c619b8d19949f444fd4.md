Audit Report

## Title
Unprivileged clients can hijack/DoS Web API trigger responses by front-running `MessageID` before the legitimate request in the Gateway's WebAPI capability handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` in the legacy WebAPI trigger handler stores a pending user callback keyed solely by the attacker-controlled `msg.Body.MessageID`, with no check for an existing in-flight entry before the map write. Unlike the sibling HTTP trigger v2 handler and the Vault gateway handler, which explicitly reject a colliding request ID, this handler silently overwrites `h.savedCallbacks[msg.Body.MessageID]`, letting a second unrelated (self-signed) request hijack the response destined for the first caller.

## Finding Description
`HandleLegacyUserMessage` writes to the shared map unconditionally: [1](#0-0) . `msg.Body.MessageID` is validated only for length/format/null-suffix, not uniqueness, in `Message.Validate()`, which is invoked from `ProcessRequest` before dispatch to the handler: [2](#0-1) [3](#0-2) . `ProcessRequest` is the Gateway's public entry point routing legacy (DonID-bearing) requests straight into `HandleLegacyUserMessage`: [4](#0-3) . The handler itself contains a `// TODO: apply allowlist and rate-limiting here` comment right before request forwarding, confirming no sender authorization gate exists at this stage: [5](#0-4) . When a node later responds, `handleWebAPITriggerMessage` looks up and deletes whichever callback currently occupies that `MessageID` slot and delivers the response to it — last writer wins: [6](#0-5) .

This is corroborated by the debug/test tooling: `invoke_trigger.go` shows `MessageID` is a fully caller-chosen CLI flag (`--id`), not derived from any trusted, non-guessable source: [7](#0-6) . Comparable handlers in the same codebase explicitly guard against this exact class of bug: the v2 HTTP trigger handler's `setupCallback` rejects an in-flight duplicate ID with `jsonrpc.ErrConflict`, and this is verified by a dedicated test (`"duplicate request ID"`): [8](#0-7) [9](#0-8) . The Vault handler applies the same defensive pattern: [10](#0-9) . The legacy WebAPI trigger `handler` lacks this guard, which is a genuine, exploitable control gap rather than an intentional design choice.

## Impact Explanation
Any actor who can sign a message with any (self-generated, unpermissioned) ECDSA key can submit a legacy request through the Gateway's public JSON-RPC endpoint using an `MessageID` that collides with a victim's in-flight request. This overwrites the victim's `savedCallback` entry; the node's eventual response is then delivered to the attacker's callback, while the victim's original HTTP call times out via `callback.Wait(ctx)` in `ProcessRequest`. This is a legitimate griefing/DoS and cross-user response-confusion issue, matching the in-scope "cross-user response corruption" impact category.

## Likelihood Explanation
No privileged role, credential, or node compromise is required — only the ability to send a request to the Gateway's public endpoint with a self-signed message, which is by design open to any external caller of the legacy WebAPI trigger path. Exploitability hinges on the attacker being able to guess or observe the victim's `MessageID` and win the race before the legitimate DON response arrives; since `MessageID` is entirely client-supplied (as shown by the CLI tooling and test helpers using simple fixed strings like `"12345"`), this is plausible in real deployments where client-side ID generation is not cryptographically random or is otherwise observable/predictable, making the attack straightforward and repeatable.

## Recommendation
Add a uniqueness/in-flight check in `HandleLegacyUserMessage` before writing to `h.savedCallbacks`, mirroring `httpTriggerHandler.setupCallback` and `vault.handler.newActiveRequest`: if an entry already exists for `msg.Body.MessageID` (and has not expired), reject the new request with an explicit error response instead of overwriting the existing callback.

## Proof of Concept
1. Legitimate client signs and sends a legacy `web_api_trigger` request with `MessageID = "X"` to the Gateway; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = victimCallback` and forwards the request to all DON members.
2. Before a DON node responds, an attacker (using their own arbitrary private key) signs and sends a second legacy request also using `MessageID = "X"`. This reaches `HandleLegacyUserMessage` again and overwrites `savedCallbacks["X"] = attackerCallback` with no collision check.
3. When a node emits a `MethodWebAPITrigger` response tagged `MessageID = "X"`, `handleWebAPITriggerMessage` finds `attackerCallback` in the map, deletes the entry, and delivers the response to the attacker.
4. The victim's original `ProcessRequest` call times out on `callback.Wait(ctx)`, receiving `api.RequestTimeoutError` instead of the real response.

A Go unit test extending `handler_test.go`'s `setupHandler`/`triggerRequest` helpers can directly demonstrate this: call `HandleLegacyUserMessage` twice with the same `MessageID` but two different callbacks/signers, then call `HandleNodeMessage` once, and assert that the second (attacker) callback receives the response while the first (victim) callback never resolves.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
