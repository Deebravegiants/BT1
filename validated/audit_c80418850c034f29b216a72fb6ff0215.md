### Title
No vulnerability: main-resource CSR updates cannot mutate Status via plain Update() - (plugin/pkg/admission/certificates/approval/admission.go)

### Summary
The `Plugin.Validate` in `plugin/pkg/admission/certificates/approval/admission.go` intentionally ignores requests that are not on the `approval` subresource, but this is not a gap because the registry strategy for the main CSR resource independently strips any client-supplied `Status` changes before they can be persisted or validated.

### Finding Description
The admission short-circuit at `plugin/pkg/admission/certificates/approval/admission.go` lines 78-81 only enforces signer-based RBAC (`certauthorization.IsAuthorizedForSignerName`) for `certificatesigningrequests/approval` subresource updates. A plain `Update()` on the main `certificatesigningrequests` resource does reach `csrStrategy.PrepareForUpdate` in `pkg/registry/certificates/certificates/strategy.go`, which unconditionally executes `newCSR.Status = oldCSR.Status` [1](#0-0)  — discarding any attacker-injected `Status.Conditions` (including a forged `Approved` condition) before the object is persisted or even validated. This happens for every main-resource update path, independent of the approval admission plugin. Additionally, even if this reset were bypassed, `validateCertificateSigningRequestUpdate` in `pkg/apis/certificates/validation/validation.go` explicitly forbids adding/removing/modifying `Approved`/`Denied` conditions unless `opts.allowSettingApprovalConditions` is set (only true for the approval-subresource validation path) [2](#0-1) , providing defense in depth.

### Impact Explanation
No exploitable impact exists. The `Status` field, including `Conditions`, cannot be mutated through a main-resource `Update()` regardless of the admission plugin's subresource check, because the registry strategy layer resets it unconditionally prior to persistence.

### Likelihood Explanation
Not applicable — the attack path is blocked deterministically by strategy code that runs on every update request to the main resource, with no configuration or feature-gate dependency.

### Recommendation
No fix required for this specific concern; existing `csrStrategy.PrepareForUpdate` behavior already prevents the described exploit. (Only the dedicated `csrStatusStrategy`/`csrApprovalStrategy` types, reachable via the `/status` and `/approval` subresources respectively, are permitted to touch `Status`, and each has its own strategy/validation restrictions.)

### Proof of Concept
Table test in `pkg/registry/certificates/certificates/strategy_test.go` style: call `Strategy.PrepareForUpdate(ctx, newObj, oldObj)` with `newObj.Status.Conditions` containing an injected `{Type: certapi.CertificateApproved}` condition and `oldObj.Status.Conditions` empty; assert `newObj.Status` equals `oldObj.Status` after the call (i.e., the injected condition is stripped) — this mirrors the pattern of `TestStatusUpdate` at `pkg/registry/certificates/certificates/strategy_test.go` lines 145-231, but using `Strategy` (main resource) instead of `StatusStrategy`/`ApprovalStrategy`.
