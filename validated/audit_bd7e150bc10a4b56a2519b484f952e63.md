### Title
Legacy (unauthenticated) user QR-code format allows biometric signup to be bound to an arbitrary/stolen `user_id` - (File: `src/plans/qr_scan/user.rs`, `src/backend/user_status.rs`, `src/plans/enroll_user.rs`)

### Summary
The orb accepts two user QR-code formats: a modern format that is cryptographically bound to backend-issued `UserData` via `user_data_hash`, and a legacy "V2" format that carries only a bare `user_id` string with no hash/signature binding it to a specific session or possessor. When the legacy format is used, the backend-authenticity check `user_data.verify(user_data_hash)` is entirely skipped, so the `user_id` supplied by whoever presents the QR code is trusted at face value and gets baked into the iris-code signature and the biometric package upload without any proof of legitimate possession, analogous to the Treasury bug where a caller-supplied identifier (`to`/`amount`) is trusted without validating it against the authorized ground-truth value.

### Finding Description
`qr_scan::user::Data::try_parse` first tries `orb_qr_link::decode_qr` (authenticated format, produces `user_data_hash`), and falls back to the plain `QR_CODE_V2` regex format that only extracts a `user_id` and `data_policy`, with `user_data_hash: None`: [1](#0-0) 

In `backend::user_status::request`, the cryptographic verification `user_data.verify(user_data_hash)` is gated by `qr_code.user_data_hash` being `Some`; for the legacy format branch it is skipped entirely and a `UserData` is built straight from the backend's `valid: true` response with no additional binding to the presenter: [2](#0-1) [3](#0-2) 

That same untrusted `user_id` field is then used to compute the iris-code signature via the Secure Element and is submitted with the signup request: [4](#0-3) [5](#0-4) 

The same `user_id` also determines who the personal-custody package (biometric data) is attributed to when uploaded: [6](#0-5) 

Because the legacy path has no cryptographic proof binding the `user_id` to the presenter, the only gate is the backend's session-status lookup by that ID. Anyone who obtains another person's legacy QR code (e.g. by photographing their screen or capturing it from a shared/leaked source) can present that ID as their own and have the orb sign and upload their own biometric scan under the victim's `user_id`/session, exactly the kind of caller-supplied-identifier trust failure described in the report (an attacker-controlled parameter — here `user_id` — determines where sensitive data/attribution goes, without verifying the caller is actually authorized to use that value).

### Impact Explanation
This enables misattributed/hijacked signups: an attacker who captures or intercepts a legitimate user's legacy-format QR code can bind their own iris/face biometric capture to that user's `user_id` and signup session, causing the wrong biometric data to be permanently associated with another individual's identity/session on the backend. This is a concrete cross-signup state bleed / identity-binding failure, not merely theoretical, since the verification step that exists for the modern format is provably absent for the legacy one.

### Likelihood Explanation
Exploitation requires only that the attacker view/capture another person's legacy user QR code (no privileged keys, no operator/admin access, no hardware tampering) and present it to the orb during their own scan — a realistic, low-effort unprivileged-user attack path.

### Recommendation
Require the same authenticated binding (`user_data_hash`/signature verification) for all supported QR-code formats, or deprecate/reject the legacy unauthenticated format in production so that `user_id` can never be trusted for signature and biometric-package attribution without cryptographic proof of possession.

### Proof of Concept
1. Victim generates a legacy-format user QR code (`userid:<uuid>:<data_policy>`) via an old/compatible app version, producing `qr_scan::user::Data { user_id, user_data_hash: None, .. }`.
2. Attacker photographs/obtains this QR code string.
3. Attacker presents this QR code to an orb during their own biometric capture; `handle_user_qr_code` → `verify_user_qr_code` → `backend::user_status::request` accepts it because the backend session with that ID is still valid and no `user_data_hash` check is performed (`src/backend/user_status.rs:245-266`).
4. `enroll_user::make_signature` signs the attacker's iris code together with the victim's `user_id` (`src/plans/enroll_user.rs:290-304`), and the personal custody package is uploaded tagged with the victim's `user_id` (`src/plans/mod.rs:572-636`), completing a signup that misattributes the attacker's biometrics to the victim's identity.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
