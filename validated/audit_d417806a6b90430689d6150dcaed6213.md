### Title
Decimals conversion functions in `pallet-hyper-fungible-token` silently drop scaling when local decimals exceed remote decimals, enabling unbacked cross-chain minting — (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20` and `convert_to_balance`, the helpers that translate amounts between a substrate asset's local decimal precision and a remote EVM `HyperFungibleToken`'s decimal precision, both implicitly assume `erc_decimals >= local_decimals`. They compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`, which silently becomes `0` whenever the local asset has *more* decimals than the registered remote ERC-20 decimals. In that configuration, no scaling is applied at all, producing an amount that is off by a factor of `10^(local_decimals - erc_decimals)` — exactly the class of bug described in WATCHPUG's `ConvexRewardPoolOracle.getPrice()` finding, where an implicit "same decimals" assumption between two related token representations silently breaks the conversion instead of failing safely.

### Finding Description
The conversion helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only handle the case `erc_decimals >= local_decimals` correctly (scaling by `10^(erc_decimals - local_decimals)`). When `local_decimals > erc_decimals`, `saturating_sub` returns `0`, so the multiplier/divisor becomes `10^0 = 1` — i.e. **no scaling is performed** instead of the required inverse scaling (`10^(local_decimals - erc_decimals)`).

These helpers are invoked directly in the unprivileged, user-reachable `send` extrinsic and in the relayer-delivered `on_accept` handler:

- In `send`, the pallet reads the registered remote decimals (`erc_decimals` from `Precisions`) and the local asset's decimals, then calls `convert_to_erc20(amount, erc_decimals, decimals)` to build the cross-chain `Message.amount` that will be minted on the destination `HyperFungibleToken` contract: [2](#0-1) 

- In `on_accept`, the pallet does the inverse with `convert_to_balance(message.amount, erc_decimals, decimals)` to determine how much to mint/release locally for an incoming message: [3](#0-2) 

Per the pallet's own documentation, decimals mismatches between chains are expected and exactly what `Precisions` is meant to reconcile: [4](#0-3) 

The `BridgeToken.sol` doc comment confirms real deployments intentionally register different decimals across the local/EVM boundary (e.g. BRIDGE is 12 decimals on nexus vs 18 on the EVM wrapper): [5](#0-4) 

If any registered token has `local_decimals > erc_decimals` for a given destination chain (a legitimate, foreseeable configuration — e.g. a local asset with 18 decimals bridged to an EVM token registered with 6 decimals), the scaling silently degenerates to a no-op instead of reverting or dividing down.

### Impact Explanation
- On `send`: a user burns/locks `amount` of the local asset (correctly decremented at local precision), but `convert_to_erc20` fails to scale the value down before encoding it into the cross-chain `Message.amount`. The relayed message therefore carries an amount that is `10^(local_decimals - erc_decimals)` times too large. When delivered to the destination `HyperFungibleToken.onAccept`, that contract mints the oversized amount to the recipient — an **unbacked mint** of the wrapped token on the destination chain, directly draining value from the token's fungibility model (any holder can then redeem/sell the excess for real value backed by nothing).
- On `on_accept` (reverse direction): an incoming message's ERC20-denominated amount is under-scaled instead of scaled up, causing this chain to mint or release far less than intended — a **freezing/loss of funds** for the legitimate recipient.

Both are concrete violations of "no unbacked mint" and "no freezing of user funds" and require no privileged actor: any holder of a registered asset can trigger the exploitable direction merely by calling `send` once such a token/chain pair is configured (or misconfigured) with `local_decimals > erc_decimals`.

### Likelihood Explanation
The trigger condition is a token/chain configuration where the local (substrate) asset has more decimals than the destination EVM contract's registered decimals — a normal, expected scenario per the pallet's own design intent (`Precisions` exists specifically to reconcile differing decimals) and per real examples already in the codebase (BRIDGE token 12 vs 18 decimals, in the *opposite* direction which happens to be the safe branch). Any token registered with the vulnerable decimal ordering makes every `send` call by any user immediately exploitable, with no additional preconditions, race, or privileged step needed.

### Recommendation
Fix both helpers to handle both directions of the decimals difference explicitly, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirror image for `convert_to_balance`. Additionally, add a sanity/regression test asserting correct round-tripping for `local_decimals > erc_decimals` configurations (the existing tests only exercise the `erc_decimals >= local_decimals` case, e.g. BRIDGE's 12→18 setup), and consider validating at `register_token`/`update_token` time that the configured decimals combination round-trips without precision loss beyond acceptable dust.

### Proof of Concept
1. Register a local asset `A` with `local_decimals = 18` for destination chain `X`, with `Precisions::<T>::get(A, X) = 6` (a plausible real-world config, e.g. bridging an 18-decimal governance token to a 6-decimal wrapped representation).
2. User calls `send(asset_id = A, amount = 1_000_000_000_000_000_000 /* 1.0 token, 18dp */, destination = X, ...)`.
3. `send` burns/escrows `1e18` units of `A` locally (correct at 18dp), then computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18u8) = 0`, so `convert_to_erc20(1e18, 6, 18) = 1e18 * 10^0 = 1e18`.
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken` contract, which mints `1e18` raw units — but since that contract's `decimals()` (per registration) is `6`, `1e18` raw units represents `1,000,000,000,000 (1 trillion)` whole tokens instead of the intended `1.0` token, a `10^12`-fold over-mint, purely from calling the public, unprivileged `send` extrinsic once.
