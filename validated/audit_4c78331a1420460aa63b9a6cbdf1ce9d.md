### Title
Unprivileged attacker installs a dangling ERC20 approval from Emporium via the zero-dimension Min-circuit path, enabling theft of any token balance later routed through Emporium across separate transactions - (`circuits/MainEVMCircuitMin.circom`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `Hinkal.transact()` is invoked with `dimensions.tokenNumber == 0` for the `HINKAL_EMPORIUM_ACTION_ID` external action, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` to the ZK verifier [1](#0-0) . Because `circomData.erc20TokenAddresses.length == 0`, both `Hinkal.sol`'s balance/slippage-check loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loop iterate zero times [2](#0-1) [3](#0-2) , so an attacker can force Emporium to execute an arbitrary `op.endpoint.call(op.callData)` — e.g. `T.approve(attackerSpender, type(uint256).max)` — with zero balance-invariant enforcement and, when `stack.signerAddress == address(0)`, zero signature verification [4](#0-3) . Because the code itself acknowledges Emporium is stateful across separate transactions ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") [5](#0-4) , a dangling approval installed in one transaction persists to drain any legitimate depositor's funds that transiently sit in Emporium before that depositor's own completing call executes.

### Finding Description
**Broken equality:** tokens present in Emporium's on-chain balance immediately after a legitimate depositor's deposit step == tokens still present in Emporium when that same depositor's own subsequent `runAction` call computes `balancesBefore` for its completion. This equality does not hold if any third party has a live ERC20 approval from Emporium and exercises it in between.

**Root cause / path:**
1. `HinkalHelper.performHinkalChecks` validates `calldataHash` integrity, relay validity, `dimensionsCheck`, and `checkOnchainCreation` [6](#0-5) . None of these require `dimensions.tokenNumber > 0`, and all fields (including `externalActionMetadata`) are attacker-crafted and self-consistent, so all checks pass trivially with `tokenNumber = 0`.
2. `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [7](#0-6) . The corresponding circuit, `MainEVMCircuitMin`, only constrains `outTimeStamp`, `calldataHash`, and a Poseidon-derived `message` — it places **no constraints whatsoever** on `EmporiumStack.ops`, `endpoint`, `callData`, or `value` [8](#0-7) . An attacker can generate a valid proof for this trivial circuit unassisted.
3. `Hinkal.transact()` calls `verifyProof` (passes, trivial circuit) and `rootHashExists` (any valid past root works, since 0 nullifiers/0 outputs are required) [9](#0-8) , then `_externalTransact` → `EmporiumUpgradeable.runAction`, gated only by `onlyAllowedRecipient`, which merely checks `msg.sender == Hinkal` — it does not restrict `op.endpoint`/`op.callData` content [10](#0-9) .
4. Inside `runAction`, `verifyWallet` only enforces an EIP-712 signature check when `stack.signerAddress != address(0)`; for the stateless "Case 2" path (`signerAddress == address(0)`), the only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors — arbitrary other calls (like `approve`) are unrestricted [11](#0-10) [12](#0-11) .
5. Because `circomData.erc20TokenAddresses.length == 0`, the `balancesBefore`/`balancesAfter` loop that would otherwise revert on any unaccounted balance draw-down (`BalanceChangeShouldBePositive`) never executes [13](#0-12) . The `approve()` call succeeds with zero on-chain invariant checking.

**Exploit flow (chained, third-party victim):**
- tx1 (attacker, any EOA): calls `Hinkal.transact()` with `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and one op: `T.approve(attackerSpender, MAX_UINT)`. This installs a live allowance from Emporium to `attackerSpender` at zero cost (no deposit required, since `erc20TokenAddresses` is empty).
- tx2 (any unprivileged victim): performs a normal, correctly-dimensioned Emporium swap/deposit session, moving token `T` into Emporium as part of `_externalTransact`'s pre-`runAction` transfer step [14](#0-13) . If the victim's flow is a multi-step (stateful wallet) session, `T` can sit in Emporium's balance across separate transactions before the victim's own completing call.
- tx3 (attacker): calls `T.transferFrom(emporium, attacker, amount)` using the dangling allowance, draining `T` out of Emporium before the victim's completing call executes.
- Victim's completing call: `runAction`'s `balancesBefore` snapshot now reflects the drained state; `balanceChange` computed in the loop is reduced or negative, either reverting with `BalanceChangeShouldBePositive()` or producing a `utxoOut.amount` smaller than the amount the victim actually deposited [3](#0-2) .

None of the existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, `dimensionsCheck`, `verifyWallet`, `onlyAllowedRecipient`, `BalanceChangeShouldBePositive`) prevent step 1 (installing the approval) because they were designed assuming `tokenNumber > 0` implies balance-diff enforcement, and none of them constrain arbitrary `EmporiumStack.ops` content when `signerAddress == address(0)`.

### Impact Explanation
This allows direct theft of a specific victim's mid-flow deposited ERC20 funds by an unprivileged attacker, meeting the Critical bar (direct theft of in-flight user funds via a proof/authorization-bypass primitive: the Min-circuit path bypasses balance invariants that the "normal" circuit path enforces). The primitive (installing an arbitrary approval from Emporium at zero cost) is fully repeatable per token and per spender, and once installed, is exploitable against any subsequent depositor whose funds transit through Emporium before their own completion call executes, not just the original attacker's own funds.

### Likelihood Explanation
- Preconditions: Emporium must be registered as an external action with a Min-circuit verifier for `HINKAL_EMPORIUM_ACTION_ID`/`tokenNumber=0` (standard, intentional deployment configuration per `formInputEmporiumMin`), and the victim's flow must leave token `T` sitting in Emporium's balance across the deposit and completion steps (true for any stateful/multi-call Emporium session, which the code's own comments assume is a supported/expected condition).
- Attacker cost: one cheap proof generation for a trivial circuit with no real constraints, plus gas for the approve+transferFrom calls. No special role or victim key material needed.
- Feasibility: an attacker only needs to observe a pending/likely deposit into Emporium (mempool monitoring) or simply install approvals proactively and periodically sweep Emporium's balance for any of the target tokens; repeatable indefinitely.

### Recommendation
- Do not allow the zero-dimension Min-circuit path to execute arbitrary `EmporiumStack.ops`; require `verifyWallet`'s EIP-712 signature check unconditionally (do not allow `signerAddress == address(0)` to bypass authorization for stateless calls), or scope stateless ops to an allowlisted target-selector set (e.g., forbid `approve`/other allowance-granting calls entirely from Emporium's own context, or require every `approve` to be immediately consumed atomically with no residual allowance left standing).
- Ensure Emporium never carries a non-zero balance across separate transactions in the first place: force `runAction` to revert if any of the tokens involved have a pre-existing non-zero balance not accounted for by the current call's `deltaAmountChanges`, instead of tolerating this ("funds on emporium before the call") as an expected state.
- Alternatively, have Emporium `approve(spender, 0)` immediately after any single-use interaction requiring an allowance, and disallow long-lived unlimited allowances from being installed by unauthenticated/unsigned ops.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register the Min-circuit verifier for the zero-dimension Emporium verifier ID, and deploy a mintable ERC20 `T`.
2. **tx1 (attacker):** call `Hinkal.transact()` with `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress:0, ops:[{endpoint:address(T), invokeWallet:false, value:0, callData: abi.encodeCall(T.approve,(attackerSpender, type(uint256).max))}]}`, with a locally generated valid proof for `MainEVMCircuitMin`. Assert the call succeeds and `T.allowance(emporium, attackerSpender) == type(uint256).max`.
3. **tx2 (victim):** call `Hinkal.transact()` performing a normal, correctly-dimensioned deposit of `T` into Emporium as the first step of a multi-call/stateful session (do not yet call the completing swap/withdraw step). Assert `T.balanceOf(emporium) == depositAmount`.
4. **tx3 (attacker):** call `T.transferFrom(emporium, attacker, depositAmount)` using the allowance from step 2. Assert it succeeds and `T.balanceOf(emporium) == 0`, `T.balanceOf(attacker) == depositAmount`.
5. **Victim's completing call:** invoke the victim's follow-up `runAction`-triggering call that expects to withdraw/complete the swap. Assert it either reverts with `BalanceChangeShouldBePositive()` or returns a `utxoOut.amount` strictly less than the originally deposited amount, demonstrating the equality break and fund loss for the victim.
