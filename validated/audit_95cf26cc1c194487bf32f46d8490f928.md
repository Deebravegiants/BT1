### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the raw request body against the HMAC signature, but then hands the caller-supplied `shop`, `topic`, `webhook_id`, and `api_version` HTTP headers—none of which are covered by that signature—to the app's webhook handler as if they were verified. This breaks the identity binding "bytes verified == bytes trusted for tenant identity."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are never included in the HMAC-signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then, without any further check binding the header values to the signed body, constructs `WebhookMetadata` directly from these unauthenticated headers and dispatches it to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no additional integrity check: [5](#0-4) 

Because the app secret used to sign webhooks is shared across every shop that installs the app (it is the app's `api_secret_key`, not a per-shop secret), any shop that has installed the app can obtain body+HMAC pairs that are valid under the shared secret, then replay that same body/HMAC pair to the app's webhook endpoint with a forged `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header pointing at a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will pass the attacker-controlled `shop` value straight to the handler as the trusted tenant identifier.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` as the tenant key to write/update data (the intended and documented use per `docs/usage/webhooks.md` and the `WebhookHandler` interface), an attacker who controls one installed shop can inject or mutate data under a different shop's identity by replaying/relaying a validly-HMAC'd payload with a spoofed shop header. This is a cross-tenant identity confusion at the library layer: the gem asserts the webhook is authentic (`Errors::InvalidWebhookError` is not raised) while providing an unauthenticated tenant identifier to the caller.

### Likelihood Explanation
Exploitability requires the attacker to have at least one shop installation of the target app (a merchant of the app, i.e., an "unprivileged" outsider relative to other tenants) to obtain a validly-signed body/HMAC pair, and the ability to send arbitrary HTTP headers to the app's public webhook endpoint (trivial, since only the body needs to match the HMAC). No `api_secret_key`, access token, or privileged credential is required beyond installing the app like any other merchant.

### Recommendation
Bind the trusted identity to the signature: either include `shop`, `topic`, and `webhook_id` in the signable string used for `HmacValidator.validate`, or independently verify that the `shop` header corresponds to a shop session/installation known to have produced this exact webhook (e.g., cross-check against Shopify's webhook `X-Shopify-Webhook-Id` uniqueness combined with a shop-scoped secret, or require the host app to validate `shop` out-of-band). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. App merchant A installs the app; Shopify sends A a webhook with body `B` and header `x-shopify-hmac-sha256` computed as `HMAC-SHA256(api_secret_key, B)`.
2. Attacker (merchant A, or anyone who can capture such a webhook) replays a request to the app's webhook endpoint with the same body `B` and the same valid `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the HMAC and succeeds (`lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim-shop.myshopify.com"` and dispatched to the handler (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the app to process attacker-controlled data as if it belonged to the victim shop.
