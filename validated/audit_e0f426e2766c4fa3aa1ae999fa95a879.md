Audit Report

## Title
NULL Pointer Dereference via Unchecked `req.Params` in Vault `handlePublicKeyGet` - (File: core/capabilities/vault/gw_handler.go)

## Summary
`HandleGatewayMessage` in `core/capabilities/vault/gw_handler.go` dispatches `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without routing through `GatewayVaultRequestProcessor.ProcessRequest`, which is the only place a `req.Params == nil` guard exists for the other Vault methods. `handlePublicKeyGet` unconditionally dereferences `*req.Params`, so a JSON-RPC request for `public_key.get` with `params` omitted causes a nil-pointer-dereference panic.

## Finding Description
In `HandleGatewayMessage`, `MethodSecretsCreate`/`MethodSecretsUpdate` and `MethodSecretsDelete`/`MethodSecretsList` are routed through `h.requestProcessor.ProcessRequest`, whose internal per-method handlers each check `if req.Params == nil` before unmarshalling [1](#0-0) . `MethodPublicKeyGet`, however, bypasses that processor entirely and goes straight to `h.handlePublicKeyGet(ctx, gatewayID, req)` [2](#0-1) , and that function does `json.Unmarshal(*req.Params, r)` with no nil check [3](#0-2) . Dereferencing a nil `*json.RawMessage` panics.

Critically, I also confirmed the message-dispatch path that invokes this handler: `gatewayConnector.readLoop` reads a message off the gateway websocket, unmarshals it into a `jsonrpc.Request`, looks up the registered handler, and calls `handler.HandleGatewayMessage(ctx, ...)` directly inline in that loop's goroutine, with no `recover()` around the call [4](#0-3) . There is no panic-recovery wrapper visible in this file's call chain (`recover()` doesn't appear anywhere under `core/services/gateway/**` for this path), so a panic triggered inside `handlePublicKeyGet` would propagate up through `readLoop` and crash that goroutine — and since `readLoop` is a dedicated per-gateway-connection goroutine with a `defer c.closeWait.Done()`, an unrecovered panic in it is fatal to the whole Go process (Go does not let other goroutines catch a panic from a sibling goroutine), resulting in a full node crash, not just isolated request failure.

## Impact Explanation
This is a legitimate, unauthenticated denial-of-service: a crash of the node process handling the gateway connector, since `MethodPublicKeyGet` requires no authorization, session, or credential and is dispatched before any authorizer/allowlist logic. This maps to an in-scope "node availability/DoS via gateway request" style impact — reachable purely through a syntactically valid but incomplete JSON-RPC message sent to a gateway-registered node capability.

## Likelihood Explanation
High. Any actor capable of reaching the gateway connector and knowing the JSON-RPC method name `vaulttypes.MethodPublicKeyGet` (a public method, part of `vaulttypes.Methods`) can send a request omitting the optional `params` field — a fully spec-compliant JSON-RPC 2.0 request. No secrets, prior session, or elevated privilege are required, and the trigger is deterministic and repeatable.

## Recommendation
Add an explicit `if req.Params == nil { return h.errorResponse(...) }` check at the top of `handlePublicKeyGet`, mirroring `processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest` in `gateway_vault_request_processor.go`. Additionally, audit `handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, and `handleSecretsList` (which also dereference `*req.Params` unconditionally) to confirm they are unreachable with nil `Params` only because `ProcessRequest` is guaranteed to run first — and consider adding defense-in-depth nil checks there too. Separately, wrapping `handler.HandleGatewayMessage` invocations in `connector.go`'s `readLoop` with a panic-recovery boundary (e.g., using the existing `core/recovery` package's `WrapRecoverHandle`) would prevent any single malformed/malicious message — from this or any other future handler bug — from crashing the entire node process.

## Proof of Concept
1. Start a node with the Vault capability's `GatewayHandler` registered against a gateway connector.
2. Establish (or simulate) a gateway connection and send the following JSON-RPC message through it:
```json
{"jsonrpc":"2.0","id":"1","method":"public_key.get"}
```
(field `params` intentionally omitted; verify exact string value of `vaulttypes.MethodPublicKeyGet` in `core/capabilities/vault/vaulttypes/types.go`).
3. `connector.go`'s `readLoop` unmarshals this into `jsonrpc.Request[json.RawMessage]` (with `Params == nil`) and calls `GatewayHandler.HandleGatewayMessage`.
4. `HandleGatewayMessage` routes to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)`, panicking with a nil-pointer dereference.
5. As a Go unit test: construct a `*jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and call `GatewayHandler.HandleGatewayMessage` directly, asserting it does not panic (currently it will).

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
