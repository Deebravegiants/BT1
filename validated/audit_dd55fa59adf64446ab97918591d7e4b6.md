## Finding

### Title
Arithmetic overflow panic in `convert_to_erc20`/`convert_to_balance` breaks bridging for tokens with high decimal precision - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` scales token amounts between the local asset's decimals and the remote ERC20's decimals by computing `10u128.pow(decimals_delta)`. Neither `register_token` nor the conversion helpers cap the decimal delta, so a token whose remote-chain decimals significantly exceed the local asset's decimals (a legitimate, if unusual, ERC20 configuration — `decimals()` is attacker/deployer-controlled up to `u8::MAX = 255`) causes `10u128.pow(...)` to overflow, panicking on every `send`, `on_accept`, and `on_timeout` call for that asset.

### Finding Description
The scaling helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions compute `10u128.pow(delta)` where `delta = erc_decimals - local_decimals` (both `u8`, so `delta` can range up to 255). `u128::pow` overflows for any exponent ≥ 39 (`10^38` is close to `u128::MAX ≈ 3.4×10^38`; `10^39` already exceeds it). Substrate runtimes are typically compiled with `overflow-checks = true`, so this overflow panics rather than silently wrapping.

The only guard against a large delta is in `register_token`, which merely enforces the *direction* of the relationship, not its magnitude: [2](#0-1) 

```rust
ensure!(
    config.decimals >= local_decimals,
    Error::<T>::ErcDecimalsBelowLocal
);
```

There is no upper bound on `config.decimals` (the ERC20-side decimals to be recorded in `Precisions`), and `local_decimals` is read directly from `pallet-assets` metadata (or `T::Decimals` for the native asset) without any sanity bound either. Because ERC20 `decimals()` is a value returned by the destination token contract itself, any token (deployed by anyone, on any supported EVM chain) can freely report a `decimals()` far above 18 — nothing in the Solidity ERC20 standard restricts this to reasonable values (`decimals()` returns a `uint8`, so up to 255).

Once such a token is registered — following the documented flow where the operator faithfully records the token's real `decimals()` into `Precisions` — every subsequent cross-chain operation for that asset invokes `convert_to_erc20` (outbound `send`) or `convert_to_balance` (inbound `on_accept` / `on_timeout`) and panics:

- Outbound: [3](#0-2) 
- Inbound: [4](#0-3) 
- Timeout/refund: [5](#0-4) 

`on_accept` is the dispatch entry point invoked by `pallet-ismp` when *any* relayer delivers a valid cross-chain message for this module — an unprivileged, permissionless action once a valid consensus/state proof is supplied. A panic there means the extrinsic delivering the message (and, depending on the panic-handling wrapper used by the runtime, potentially the whole block containing it) cannot execute successfully.

### Impact Explanation
- Any asset registered with a large decimals delta becomes permanently unusable: `send` (user-initiated outbound teleport), `on_accept` (inbound delivery by any relayer), and `on_timeout` (refund path) all panic deterministically for that asset, since the delta is a fixed registration-time value baked into `Precisions`.
- This is a irrecoverable freeze of user funds already escrowed/burned for that asset (a `send` that panics after escrow/burn but before dispatch would leave funds stuck; more importantly, funds already in flight cannot be delivered because `on_accept` will always panic, and refunds via `on_timeout` will also always panic — permanently locking user funds with no code-level recovery path short of a runtime upgrade).
- Depending on how the pallet-ismp message-dispatch harness handles panics from `IsmpModule::on_accept`, this could also disrupt processing of the message-delivery extrinsic itself for other unrelated messages batched in the same call, widening the blast radius.

### Likelihood Explanation
Reaching this bug does not require a malicious admin: it only requires an operator faithfully registering a legitimate-looking asset whose EVM-side contract reports an unusually high (but standards-compliant) `decimals()` value, or a delta between local and remote decimals ≥ 39. Any token deployer can set an arbitrary `decimals()`, so this is squarely in the "unusual token characteristics break the protocol" bug class from the reference report, adapted to Hyperbridge's `pallet-hyper-fungible-token` decimal-scaling code.

### Recommendation
- Bound the accepted decimals delta in `register_token`/`update_token` (e.g., `ensure!(config.decimals - local_decimals <= 38, ...)`), or use a wider/checked arithmetic type (e.g., `U256::pow` performed entirely in `U256` rather than computing `10u128.pow` and converting) with an explicit `checked_pow`/`checked_mul` that returns a pallet error instead of panicking.
- Replace `10u128.pow(...)` with `10u128.checked_pow(...).ok_or(Error::<T>::PrecisionOverflow)?` (and similarly for the multiplication in `convert_to_erc20`) so that misconfigured or exotic-decimal tokens fail gracefully at registration time or per-call, rather than panicking mid-execution.

### Proof of Concept
1. Operator (or attacker convincing an operator) registers a token via `register_token` with `local_decimals = 0` (e.g., a `pallet-assets` asset created with `decimals = 0`) and remote `ChainConfig.decimals = 40` for an EVM chain (a legitimate value if the real token contract's `decimals()` returns 40 — permitted by the ERC20 spec).
2. `register_token`'s check `config.decimals >= local_decimals` (`40 >= 0`) passes; `Precisions` stores `erc_decimals = 40`.
3. A user calls `send` with any nonzero `amount`. `decimals = 0` (local), `erc_decimals = 40` → `convert_to_erc20` computes `10u128.pow(40)`, which overflows `u128::MAX` and panics.
4. Symmetrically, any relayer delivering a message that reaches `on_accept` for this asset triggers `convert_to_balance`'s `10u128.pow(40)`, panicking there as well — the destination beneficiary can never receive funds, and any timed-out request can never be refunded via `on_timeout`.
