### Title
Large RAY-denominated positions can permanently freeze a market before the borrow-index cap engages - (File: common/src/rates/scaling.rs)

### Summary
A sufficiently large market can reach an `i128` overflow while ordinary interest accrual is still below `MAX_BORROW_INDEX_RAY`. `accrue_step` first reconstructs total debt with `scaled_to_original`, which multiplies scaled debt by the stored borrow index and panics on overflow. Once that boundary is crossed, every state-changing operation that synchronizes the market reverts with `MathOverflow`, preventing repayment, withdrawal, liquidation, index updates, revenue claims, and rate-model updates. The stored index cap does not protect against this because it is applied only after the earlier scaled-value multiplication has already overflowed.

### Finding Description
`interest::global_sync` invokes `accrue_chunk`, which delegates each compound-interest interval to `accrue_step`. [1](#0-0)  `accrue_step` first computes `borrowed_original` as `scaled_to_original(borrowed, borrow_index)`, and `scaled_to_original` is a checked RAY multiplication. [2](#0-1) [3](#0-2) 

For an 18-decimal asset, a market principal of `1_000_000_000 * 10^18` base units corresponds to approximately `10^36` raw RAY-scaled shares. Because `i128::MAX` is approximately `1.70 * 10^38`, multiplying those shares by a borrow index above roughly `170 * RAY` exceeds the representable RAY value domain. `MAX_BORROW_INDEX_RAY` is much higher—`10^36` raw, or one-billion times `RAY`—so this condition can arise long before the configured index ceiling. [4](#0-3) 

The intended cap in `update_borrow_index` is reached only after utilization has already required `borrowed * borrow_index` at the start of `accrue_step`. [5](#0-4)  The repository's harness demonstrates this exact ordering: a market with `10^27` base units supplied and 98% borrowed eventually fails in `update_indexes` with `MathOverflow`, while its stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5) 

The controller exposes the condition through `update_indexes(caller, assets)`, which authorizes an ordinary caller and forwards the requested markets to the pool. [7](#0-6) [8](#0-7)  The pool's accrual entrypoint then loads each market and calls `interest::global_sync`. [9](#0-8) 

### Impact Explanation
This is a market-wide freeze of user funds. Once the scaled debt or supply value crosses the `i128` boundary, subsequent synchronization attempts fail before state can be committed. The regression test confirms that the same `MathOverflow` blocks both a one-unit withdrawal and repayment after the failed index update. [10](#0-9) 

Because ordinary exit, repayment, liquidation, bad-debt cleanup, index update, revenue claim, and pool-parameter replacement all depend on market synchronization or the same accrual path, suppliers cannot withdraw collateral or yield and borrowers cannot reduce debt. Absent a privileged contract upgrade or an exceptional recovery path, the market's token funds remain locked indefinitely.

### Likelihood Explanation
The trigger requires an exceptionally large asset supply and sustained borrowing over enough time for the relevant index to grow beyond the protocol's effective value ceiling rather than its nominal index ceiling. The reference scenario uses a billion whole units of an 18-decimal asset, 98% utilization, and repeated yearly accrual. [11](#0-10) 

Nevertheless, every necessary action is reachable through unprivileged controller entrypoints by an account holding the required assets: `supply`, `borrow`, and later `update_indexes`. No oracle manipulation, leaked key, governance action, faulty token behavior, or privileged operation is required. The extensive capital and time requirements lower the probability, but the resulting state is self-perpetuating and affects all users of the market.

### Recommendation
Bound index growth against the market's actual scaled balances, not only against a global index constant. In particular, calculate the largest index for which `borrowed * index`, `supplied * index`, and downstream reward calculations remain representable, and clamp accrual to that safe index before calling `scaled_to_original`.

Alternatively, perform utilization and index updates with saturating or wider intermediate arithmetic and cap the resulting index atomically. `update_borrow_index` should not be reached with an `old_index` that cannot safely reconstruct current debt. A regression test should retain the existing whale-market scenario and assert that the index cap engages cleanly instead of producing `MathOverflow`.

### Proof of Concept
A single funded account can drive the market into the failing state:

1. Call `Controller::supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18), (COL, sufficient_collateral)])`.
2. Call `Controller::borrow(caller, account_id, [(BIG18, principal * 98 / 100)], None)`.
3. Maintain utilization near the steep portion of `BIG18`'s configured rate curve while ledger time advances.
4. Periodically call `Controller::update_indexes(caller, [BIG18])`.
5. Once `borrowed_scaled * borrow_index` exceeds `i128::MAX`, the call reverts with `MathOverflow` inside `scaled_to_original`, before `update_borrow_index` can clamp the next index.
6. Subsequent `withdraw`, `repay`, liquidation-related calls, `claim_revenue`, and rate-model replacement fail when they attempt the same mandatory accrual.

The repository's executable regression already models this sequence with `principal = 10^27` base units, `debt = principal * 98 / 100`, yearly time advancement, a failing `update_indexes`, and subsequent failed `withdraw` and `repay` calls. [12](#0-11)
