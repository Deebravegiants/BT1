Confirmed the vulnerability path: `HmacValidator.validate` signs only `to_signable_string` (the raw body) via `Request#to_signable_string` returning `@raw_body`, while `Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signable string. `Registry.process` validates the HMAC against the body only and then hands `request.shop` straight to the merchant's handler.### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates an inbound webhook by computing an HMAC over the raw request body only, then forwards the `shop` value taken from an HTTP header — a header that is never part of the signed payload — to the app's webhook handler. Anyone who can obtain one genuinely-signed webhook payload for a shop they control can replay it with a different `x-shopify-shop-domain` header and the gem will treat it as a validly authenticated webhook for the victim shop.

### Finding Description
The HMAC validation binding is:

`computed_hmac(raw_body, api_secret_key) == received_hmac`

but the identity used downstream for tenant routing is:

`shop = header("x-shopify-shop-domain")`

These two values are never bound together. `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` reads directly from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` only ever signs/compares `verifiable_query.to_signable_string`, i.e., the raw body — the shop header is never included in the signable string: [3](#0-2) 

`Registry.process` performs exactly this check and then passes the (unauthenticated) `request.shop` on to the merchant's handler code as the tenant identifier: [4](#0-3) 

Because the `api_secret_key` used for HMAC signing is per-app (shared across all shops that install the app), not per-shop, and because `shop` is excluded from the signed bytes, any actor who installs the app on a shop they control (or otherwise obtains one legitimately-signed webhook body/HMAC pair) can capture that raw body + HMAC and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to any victim shop domain. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand `WebhookMetadata` with the attacker-chosen `shop` straight to the app's business logic.

This exactly matches the bug class in the report: a field that is acted upon by the application (here, `shop`, used by the host app for tenant scoping) is not covered by the authentication check (the HMAC), so the identity binding `hmac_signed(shop) == shop_acted_on` does not hold — instead `hmac_signed(body) == body_acted_on` holds, and `shop` is trusted unconditionally.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker with any valid app installation (which they can obtain themselves as a normal merchant/dev-store owner) can forge or replay webhooks that the gem will accept as authentic for a completely different shop. Any handler that relies on `shopify_api`'s HMAC verification + `WebhookMetadata#shop` to determine which tenant's data/session to act on (e.g., updating orders, redacting customer data, triggering GDPR compliance actions, syncing inventory) can be tricked into operating on/for a shop the attacker does not control. This is a cross-tenant access vulnerability enabled directly by this gem's webhook verification API.

### Likelihood Explanation
Likelihood is high for any application that installs the app on more than one shop (the normal SaaS model) and trusts `WebhookMetadata#shop`/`Request#shop` as the source of truth after `Registry.process` succeeds — which is exactly the documented usage pattern of this gem. An attacker needs no special access: they can install the app on their own store, capture one legitimate signed webhook, and replay it with a modified header against the exact same endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value that is actually verified — Shopify's own webhook design intentionally signs only the raw body because HMAC is meant to authenticate the payload's integrity from Shopify, and shop identity for webhooks should instead be treated as authenticated by TLS/Shopify's delivery infrastructure per-endpoint, or the app should cross-check the delivered `shop` against a known list of installed shops with a valid session for that specific shop before trusting it. At the gem level, the modifier equivalent fix is to have `Registry.process` (or `HmacValidator.validate`) fail closed unless the caller supplies/validates the expected shop domain out-of-band, rather than silently trusting the unauthenticated header value returned by `Request#shop`.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays this exact `raw_body` and `hmac` value to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `request.to_signable_string` (`@raw_body`), which is unchanged — see [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` — see [6](#0-5)  and [2](#0-1) .
5. Any app logic keyed on `data.shop` now acts as though this event genuinely originated from `victim-shop.myshopify.com`, despite the HMAC only ever having authenticated the body contents of a webhook the attacker legitimately received for their own shop.

Note: I was unable to load `lib/shopify_api/webhooks/webhook_metadata.rb` (file not found in index), so the exact field list of `WebhookMetadata` beyond what's referenced in `registry.rb` could not be fully verified; this does not affect the core finding, which is demonstrated directly in `request.rb` and `hmac_validator.rb`.
