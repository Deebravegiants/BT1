### Title
Webhook shop-domain header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers that are never included in the signed material, then handed to the app's webhook handler as trusted identity data. Any party that can obtain one validly-signed `(raw_body, hmac)` pair for the app (e.g., a merchant who has legitimately installed the app and receives real webhooks) can replay that pair with an arbitrary `X-Shopify-Shop-Domain` header to impersonate any other tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` verifies only the HMAC over the body, then forwards `request.shop` (and the other header-derived fields) into `WebhookMetadata` for the app handler to consume as the authoritative tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` only compares the HMAC computed over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) against the received signature — it has no knowledge of, and does not bind, the `shop-domain` header: [4](#0-3) 

The identity binding that should hold is:
`hmac(secret, signed_bytes) == received_hmac` **and** `signed_bytes` includes the shop identity used downstream.

In this gem, the equality that actually holds is only `hmac(secret, raw_body) == received_hmac`, while `shop` (the field the handler acts on to attribute the event to a tenant) is taken from a completely separate, unauthenticated channel (the HTTP header). Because the `api_secret_key` is shared across all shops that have installed a given app (it is not a per-shop secret), any shop that has legitimately received one authentic webhook (and thus possesses one valid `raw_body + hmac` pair) can resend that exact pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. The HMAC check in `Registry.process` still passes because it only re-derives the signature over the (unchanged) body, and the forged `shop` value flows unmodified into the handler via `WebhookMetadata#shop`.

### Impact Explanation
Downstream, per the gem's own documentation, applications are expected to use `data.shop` as the tenant identifier to look up sessions and enqueue tenant-scoped work: [5](#0-4) 

An attacker who is a legitimate (even paying) merchant of the app can therefore inject arbitrary webhook payloads that the host application will process as if they originated from an unrelated victim shop — e.g. triggering `app/uninstalled`, `orders/create`, GDPR/customer data webhooks, or any other subscribed topic under a spoofed `shop` value, causing the app to act on or leak another tenant's data/session state. This is a cross-tenant boundary violation stemming directly from the gem's webhook verification primitive not binding the tenant identifier into the authenticated bytes.

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate installer of the target app on any shop (to obtain one authentic `raw_body`/`hmac` pair — trivial, since installing an app and triggering any subscribed webhook is the normal integration flow), and (2) sending an HTTP POST to the app's public webhook endpoint with that body/hmac unchanged but a different `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value. No access to `api_secret_key`, access tokens, or the victim's credentials is needed. This requires no cooperation or misconfiguration from the host application beyond following the gem's own documented integration pattern (`Registry.process` + a handler that trusts `data.shop`).

### Recommendation
Bind the tenant identity into the authenticated material, or otherwise independently verify it. Options:
- Include `shop-domain` (and ideally `topic`/`webhook_id`) in the HMAC-signed payload used for verification instead of only the raw body, or
- Cross-check the `shop-domain` header against an independently-verified source (e.g., confirm that a webhook subscription/session exists for that `webhook_id`/`shop` combination via the Admin API) before invoking the handler, or
- Document, and enforce in `Registry.process`, that consumers must additionally validate `request.shop` against their own webhook registration/session records (not header text alone) before trusting it for tenant attribution.

### Proof of Concept
1. App developer registers `orders/create` (or any topic) via `ShopifyAPI::Webhooks::Registry.add_registration` and installs the app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Body: `{"id":1,...}`
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
   - The attacker (who controls network traffic to their own server, or simply captures the request in their own test app) records this exact `(body, hmac)` pair.
3. Attacker crafts a new HTTP POST to the same webhook endpoint, reusing the identical `body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers/body (only checks for header *presence*, not header authenticity): [6](#0-5) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) body and succeeds, since only the body is signed: [7](#0-6) 
6. The handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"`, and the app processes/acts on data as belonging to the victim tenant, even though the request never actually originated from Shopify on the victim's behalf.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
