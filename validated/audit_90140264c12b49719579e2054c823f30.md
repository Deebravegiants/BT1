### Title
Webhook `shop` (and `topic`/`webhook_id`) header trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, then dispatches the handler using a `shop` value taken from an unsigned HTTP header, breaking the intended binding `shop-that-signed-the-payload == shop-passed-to-the-handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, entirely outside the HMAC-covered content [2](#0-1) .

`Registry.process` validates only that the body's HMAC is correct, then immediately builds the handler payload using the unauthenticated `request.shop` (and `request.topic`/`request.webhook_id`) fields: [3](#0-2) 

`Utils::HmacValidator.validate` (invoked here) only proves that `to_signable_string` (the raw body) was signed with the app's secret — it says nothing about which shop the header claims to be from [4](#0-3) .

Because the app's `api_secret_key` is shared across all shops that install the app, any party who can install the app on a shop they control (e.g. a free development store) receives genuinely-signed webhook deliveries for that shop — valid `raw_body` + `hmac` pairs. Since `shop-domain`, `topic`, and `webhook-id` are not part of the signed content, that same attacker can replay the identical body+HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header to name a different, victim shop. The signature still validates (it only checks the body), so `Registry.process` proceeds and calls the handler with `shop: <victim-shop>` even though the payload actually originated from, and was signed for, the attacker's own shop.

This breaks the identity binding: `shop that produced/signed this webhook == shop delivered to the handler`. The gem provides no mechanism (e.g., binding the shop into the signed content, or requiring the caller to cross-check `request.shop` against an active, provisioned session/shop before trusting it) to prevent this substitution.

### Impact Explanation
Any application logic keyed off the `shop` value passed into `WebhookMetadata` (tenant-scoped processing such as marking a shop uninstalled, deleting/creating tenant records, processing GDPR `customers/data_request`/`shop/redact` payloads, or triggering shop-specific side effects) can be triggered for an arbitrary target shop domain by an attacker who merely installs the app once on their own store. This is a cross-tenant identity confusion vulnerability: the attacker cannot control the JSON contents (which remain their own shop's legitimate data), but they fully control which shop the host application attributes and acts on that data for, since `Registry.process` never verifies `request.shop` is bound to the signature. Depending on how the host's `WebhookHandler#handle` uses `data.shop`, this can result in cross-tenant state corruption (e.g., forcing a victim shop record to be deleted/flagged as uninstalled, or firing tenant-specific automation against the wrong tenant).

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (trivial and free via a Shopify partner/dev store) and be able to send an arbitrary HTTP request to the app's public webhook endpoint with attacker-chosen headers — no possession of `api_secret_key`, access tokens, or any privileged credential is required. The webhook endpoint is, by design, a public unauthenticated HTTP endpoint that must accept unsolicited requests from "Shopify," so an internet attacker can reach it directly.

### Recommendation
Bind the shop identity to the signed content rather than trusting the unsigned header:
- Do not use `request.shop` (or `topic`/`webhook_id`) for any tenant-scoped decision until it has been independently cross-checked (e.g., verify that a valid, previously-provisioned session/access-token exists for that exact shop, and that the shop found in the JSON body — if present, such as in `payload["shop_domain"]` or similar Shopify-provided body fields — matches the header value).
- Where possible, incorporate the shop domain into the signature verification step so a mismatched header invalidates the HMAC check, rather than deferring entirely to Shopify's existing (header-excluded) signature scheme.
- At minimum, document this trust boundary prominently so integrators know `request.shop` must not be treated as cryptographically authenticated on its own.

### Proof of Concept
1. Attacker creates a Shopify development store and installs the target app, receiving genuine webhook deliveries (e.g. `orders/create`) with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid signature over raw body>`
2. Attacker captures the raw body and the valid HMAC value from this genuine delivery.
3. Attacker sends a new POST request directly to the app's public webhook endpoint, reusing the exact same raw body and `X-Shopify-Hmac-Sha256` value, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. In `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only checks the raw body against the secret [5](#0-4) .
5. The handler is invoked with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process a forged webhook as if it legitimately originated from the victim shop.
