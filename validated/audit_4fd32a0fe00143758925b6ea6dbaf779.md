### Title
Missing relayer-allowlist authorization check in the Tron `IntentGatewayV2.onAccept`/`onGetResponse` allows any relayer to forge escrow redemption/refund deliveries - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2`/`ExtrinsicIntents` contracts gate every incoming `onAccept`/`onGetResponse` delivery behind a single-relayer allowlist (`_checkRelayer`) before any request body is decoded or funds are moved. The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical `onAccept` dispatch logic but never calls `_checkRelayer` (the allowlist mechanism, `_relayer`, `setRelayer`, `UnauthorizedRelayer` do not exist anywhere in `evm/tron/**`), so any relayer that can produce a valid Hyperbridge delivery reaches escrow redemption/refund and governance-adjacent logic unauthenticated by relayer identity.

### Finding Description
`onlyHost` on `EvmHost.dispatchIncoming` (or its Tron equivalent) only proves the call came through the host's handler; the host trusts whatever relayer address the handler forwarded as `incoming.relayer` — that is the exact gap the per-app relayer allowlist was introduced to close, per the design notes: [1](#0-0) 

In the maintained EVM `ExtrinsicIntents.sol`, `onAccept` calls `_checkRelayer(incoming.relayer)` as the very first statement, before the `RequestKind` switch that handles `RedeemEscrow`/`RefundEscrow`/`NewDeployment`/`UpdateParams`/`SweepDust`/`Execute`, and `onGetResponse` likewise gates on `_checkRelayer` before trusting the proof result: [2](#0-1) [3](#0-2) 

The Tron variant of the same gateway implements the identical dispatch surface — `onAccept` decoding `RequestKind`, calling `authenticate`, decoding `WithdrawalRequest`, and branching into `NewDeployment`/`UpdateParams`/`SweepDust` — but with no relayer check at all: [4](#0-3) 

A grep across the entire `evm/tron/**` tree for `_relayer`, `_checkRelayer`, `setRelayer`, and `UnauthorizedRelayer` returns no matches, confirming the allowlist mechanism documented and shipped for the EVM/`BridgeToken` (`sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-hyperfungibletoken-fail-closed-on-the.md`) and the intent gateway (`sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md`) was never ported to the Tron deployment.

This is structurally analogous to BIT-gitlab-2022-3740: the primary access path (GitLab's standard authorization pipeline / Hyperbridge's mainline `ExtrinsicIntents`) enforces an authorization check, but an alternate credential/deployment path (GitLab's Deploy Tokens and Deploy Keys / Hyperbridge's Tron fork of the same application) omits the check entirely, letting an otherwise-unprivileged actor reach the same protected operations.

### Impact Explanation
Once a message is delivered through the Tron host with a valid consensus/membership proof, `authenticate` and `withdraw` execute on the strength of any submitting relayer, not just the authorised one. Because `_checkRelayer` in the mainline contracts exists specifically to prevent an unlisted relayer from forging deliveries (a rejected delivery leaves no receipt and can be resubmitted only by the authorised relayer, per the mainline design), its absence on Tron means escrow redemption/refund deliveries and the `NewDeployment`/`UpdateParams`/`SweepDust` governance-adjacent actions on the Tron gateway are reachable by whichever relayer front-runs the honest one with a race-permitted but otherwise-valid proof, undermining the "single authorised relayer" trust model the rest of the codebase relies on for these callbacks.

### Likelihood Explanation
High reachability: any relayer capable of submitting a normal Hyperbridge delivery to the Tron host can trigger `onAccept`/`onGetResponse` on this gateway; no additional privilege, governance action, or malicious insider role is required — this is a standard external-relayer delivery path, matching the "unprivileged relayer" reachability criterion.

### Recommendation
Port the relayer allowlist (`_relayer` storage, `setRelayer`, `_checkRelayer`, `UnauthorizedRelayer`) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol`/`IntentsBase.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and call `_checkRelayer(incoming.relayer)` as the first statement in both `onAccept` and `onGetResponse`, mirroring the ordering and semantics already shipped for the EVM gateway.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with a live escrow order and a registered peer gateway (`_instances`).
2. Any relayer (not necessarily the one the protocol intends to authorise) submits a valid proof/message through the Tron host such that `dispatchIncoming`/equivalent invokes `onAccept` with `IncomingPostRequest{request, relayer: attackerRelayer}`.
3. Because `onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-643`) never calls `_checkRelayer`, execution proceeds straight to `authenticate(incoming.request)` and `withdraw(...)` for `RedeemEscrow`/`RefundEscrow`, or into the `NewDeployment`/`UpdateParams`/`SweepDust` branches, with no verification that `incoming.relayer` is the address the gateway operator intended to trust — contrast with `ExtrinsicIntents.sol:331` (`_checkRelayer(incoming.relayer)`) which would revert with `UnauthorizedRelayer` for the same call on the mainline EVM gateway.

     * @notice Executes an incoming post request.
     * @dev This function is called when an incoming post request is accepted.
     * It is only accessible by the host.
     * @param incoming The incoming post request data.
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

            emit NewDeploymentAdded({stateMachineId: body.stateMachineId, gateway: body.gateway});
