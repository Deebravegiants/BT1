Confirmed: the gem's own documentation explicitly states `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and hands `data.shop` (from the unauthenticated header) directly to app handlers as the tenant identifier [2](#0-1) . This confirms the root cause is within the gem's own trust contract, not host misuse.

### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` field that identifies *which tenant* the webhook belongs to is taken from an unauthenticated HTTP header and is never included in the signed bytes. This breaks the identity binding: `HMAC-verified bytes (raw_body)` ≠ `shop used to attribute the event (shop-domain header)`.

### Finding Description
`Registry.process` verifies the webhook exclusively via `Utils::HmacValidator.validate(request)` and then immediately constructs `WebhookMetadata` using `request.shop`: [3](#0-2) 

`Request#to_signable_string` returns only `@raw_body` — the shop domain header is not part of the signed material: [4](#0-3) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the HMAC or against any session store: [5](#0-4) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against an HMAC computed over `to_signable_string` (the body), never over the shop header: [6](#0-5) 

Because the same `Context.api_secret_key` is shared across every shop that installs a given app (it is not per-shop), any actor who can obtain one valid `(raw_body, hmac)` pair for a topic they control — e.g., by installing the app on their own store and capturing a webhook Shopify sends them, or by triggering an event via a legitimately owned store — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will report the signature valid (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim shop, per the documented contract in `docs/usage/webhooks.md`: [7](#0-6) [8](#0-7) 

This mirrors the bug class in the reference report: an entity's identity (there, the owner's index; here, the shop) is derived from a source that is disjoint from the data actually being verified/acted upon (there, `contains()`'s off-by-one return value; here, the unauthenticated shop header), corrupting the identity binding the rest of the system relies on.

### Impact Explanation
Downstream host applications are documented to key their session/access-token storage and business logic on `data.shop` (`shop_domain: data.shop` in the doc example). An attacker who can forge the shop attribution of a validly-signed webhook can cause the app to process attacker-supplied webhook content under a victim shop's identity, leading to cross-tenant data corruption/confusion in the host app's data structures (e.g., false order/customer/product events attributed to a shop that never sent them), which meets the "cross-tenant access" bar for a Critical-class finding since it crosses a tenant boundary using only the shared app secret, not any tenant-specific credential.

### Likelihood Explanation
Exploitation requires only that the attacker be an existing/installable merchant of the same app (a normal, unprivileged pathway — any storefront owner can install a public app), and the ability to replay an HTTP POST with modified headers. No access to `api_secret_key`, tokens, or any privileged account belonging to the victim is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or independently verify that the shop asserted in the header corresponds to a shop for which the app currently holds an active session before dispatching to the handler, so identity attribution cannot diverge from what was actually authenticated.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook event (e.g., `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Replay that exact body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `HmacValidator.validate`, which only checks the HMAC over the body (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`) — validation passes.
4. The handler receives `WebhookMetadata#shop == "victim.myshopify.com"` with attacker-controlled body content, and the host app processes/stores it as if `victim.myshopify.com` sent it.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
