### Title
Webhook `shop-domain` and `topic` Headers Are Not Covered by HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shopify-shop-domain` and `shopify-topic` headers to route and tag the webhook payload to a specific merchant. Because these headers are not part of the signed material, an unprivileged internet user who possesses any single valid `(raw_body, hmac)` pair (e.g. by installing the app on their own store and capturing one legitimate webhook delivery) can replay that body with a forged `shopify-shop-domain` header pointing at a victim shop, and the request still passes HMAC validation.

### Finding Description
`Request#to_signable_string` returns only the raw body bytes: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers via `shopify_header`, independent of the signature: [2](#0-1) 

`HmacValidator.validate` only checks that the received HMAC matches `HMAC-SHA256(secret, verifiable_query.to_signable_string)`, i.e. the raw body — it never incorporates `shop`, `topic`, or `webhook_id` into the computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` that is handed to the app's handler as the tenant identity for the webhook: [4](#0-3) 

This breaks the intended identity binding: `shop header == tenant the HMAC-signed payload was actually generated for`. The gem's contract (and the reason apps rely on `HmacValidator.validate`) is that a passing HMAC check proves the *entire* webhook — including which shop it is for — originated from Shopify for that specific shop. In reality, the check only proves the body bytes were signed by Shopify for *some* delivery; the `shop`-domain header can be swapped freely by anyone who controls the HTTP request, since it's outside the MAC.

### Impact Explanation
Any actor who can trigger one legitimate webhook delivery to the app (trivially achievable by installing the app on their own store, a zero-privilege action) obtains a valid `(body, hmac)` pair. They can then send that same pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` still returns `true` because the header is not part of the signed string, and `Registry.process` forwards `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled-JSON>, ...)` to the host application's handler. Any host application that uses this `shop` field to scope database writes, cache invalidation, order/customer processing, etc. (the documented purpose of `WebhookMetadata#shop`) will apply attacker-controlled webhook data under the victim tenant's identity — a cross-tenant data-integrity / cross-tenant access violation achieved without any credentials, purely by exploiting a header not bound by the HMAC.

### Likelihood Explanation
High. The only prerequisite is capturing one's own legitimately delivered webhook (achievable by any developer/attacker who installs the target app on a shop they control, which is normal, unprivileged app-installation flow), then replaying it with a modified header against the shared webhook endpoint. No access token, `client_secret`, or privileged account is needed, and the HMAC check that developers rely on for authenticity gives a false sense of per-shop integrity.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. by validating them against a separately-authenticated channel such as a signed JWT/App Bridge session, or requiring they match a previously registered webhook subscription for that shop) so that the HMAC proves the whole tuple `(shop, topic, body)` was issued by Shopify, not merely the body bytes. At minimum, document that host applications must cross-check `WebhookMetadata#shop` against an independently known, registered shop/webhook-id pair before trusting it as a tenant identifier.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to receive one legitimate delivery with headers `shopify-hmac-sha256: H`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, and raw body `B`.
2. Confirm `Utils::HmacValidator.validate` accepts `(B, H)` — this is expected, since `H = HMAC(secret, B)` per `Request#to_signable_string` and `HmacValidator#validate_signature`.
3. Replay the exact same body `B` and hmac `H` to the app's webhook endpoint, but replace the header with `shopify-shop-domain: victim.myshopify.com`.
4. Observe `Utils::HmacValidator.validate(request)` still returns `true` (it only recomputes over `B`), so `Registry#process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker JSON>, ...))`, injecting attacker-controlled data under the victim tenant's identity.
