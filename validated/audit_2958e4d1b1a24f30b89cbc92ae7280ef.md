### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` in `Registry.process` proves nothing about which shop the webhook belongs to. The `shop` value delivered to the app's handler is read straight from the unauthenticated `shopify-shop-domain` header, so the shop identity used downstream is not the shop bound by the cryptographic proof.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface. Its `to_signable_string` method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all pulled from HTTP headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body, then immediately trusts `request.shop` (the header value) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and it's the value host applications are documented to rely on to identify which tenant/shop the webhook payload belongs to: [4](#0-3) 

This breaks the intended identity binding `shop authenticated == shop the app acts on`. The gem's HMAC only proves "this body was produced/authorized using our `api_secret_key`," but not "this body belongs to shop X." Compare this with the OAuth callback flow, where `shop` is explicitly included in the signable query string and thus covered by the HMAC (confirmed by `hmac_validator_test.rb`, where `shop` is part of the signed hash): [5](#0-4) 

No equivalent binding exists for webhooks — the shop identity is asserted by an untrusted header field while only the body bytes are verified.

### Impact Explanation
An attacker who can obtain one legitimately-signed webhook body+HMAC pair (e.g., by installing the app on their own shop and triggering any webhook-eligible event) can replay that exact raw body and HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a victim shop. `Registry.process` will validate the HMAC successfully (it only checks body integrity against the shared `api_secret_key`) and pass `WebhookMetadata` claiming the payload is from the victim shop. Any host application that uses `WebhookMetadata#shop` to select which tenant's session/data store to write into (a documented, expected usage pattern) will process attacker-controlled webhook content as though it originated from the victim's shop, resulting in cross-tenant data corruption/injection under the app's own trusted webhook channel.

### Likelihood Explanation
Exploitation only requires the attacker to control a Shopify shop that installs the vulnerable app (any developer/partner account can do this for free), trigger a webhook event, capture the raw request body and valid `hmac-sha256` header sent to their own endpoint (or a public test endpoint), and replay it to the target app's real webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret` or any victim credentials is required, and the vulnerable code path (`Registry.process`) is the gem's documented mechanism for verifying and dispatching webhooks.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable content, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it in `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the `shop` header value so `HmacValidator.validate` fails whenever the shop is mismatched, closing the gap between "HMAC-verified bytes" and "shop identity acted upon."

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the exact raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` sent to the attacker's own receiving endpoint.
2. Attacker sends a POST to the target app's real webhook endpoint with:
   - Body: `B` (unmodified)
   - Header `x-shopify-hmac-sha256: H` (unmodified, still valid because it only signs `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`/`x-shopify-webhook-id` set arbitrarily.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) using `Context.api_secret_key` and finds it matches `H` — validation succeeds.
4. `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes attacker-controlled content as if it came from the victim shop.
