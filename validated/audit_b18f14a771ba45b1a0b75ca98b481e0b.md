### Title
`Webhooks::Request#shop` (and `#topic`, `#api_version`, `#webhook_id`) are read from unsigned headers while `HmacValidator` only covers `@raw_body` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` proves nothing about the `x-shopify-shop-domain` (or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) header values. `Registry.process` nonetheless treats `request.shop` as authenticated when building `WebhookMetadata` and dispatching to the app's `handler.handle`.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces: `HmacValidator.validate(request) == true` should imply `request.shop == "the merchant domain that actually produced @raw_body"`. Tracing the code shows this does not hold.

- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from `@headers` via `shopify_header`, with no cross-check against the signed body: [2](#0-1)  and [3](#0-2) 
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it to `verifiable_query.hmac`; it never touches headers other than the HMAC header itself: [4](#0-3) 
- After validation succeeds, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.parsed_body`, and hands it to the app-registered handler as if all fields were authenticated together: [5](#0-4) 

Exploit flow: the attacker owns a real development store and installs the target app, so they legitimately receive a validly-signed webhook (body + `x-shopify-hmac-sha256`) from Shopify for their own store, signed with the app's shared secret. They then POST that exact `raw_body`/HMAC pair to the app's webhook endpoint again, but substitute `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim merchant's domain. `HmacValidator.validate` still succeeds, because it only recomputes the HMAC over the unchanged raw body. `Registry.process` then calls the app's `handler.handle` with `shop: <victim domain>` and `body: <attacker's own webhook payload>`, so the app processes attacker-controlled content as if it were an authenticated event for the victim's shop. No nonce, timestamp, or webhook-delivery-id tracking exists in this class or `Registry` to detect the replay or the header/body mismatch.

None of the existing guards catch this: `ShopValidator.sanitize!` is only used in OAuth/token-exchange paths, never on webhook requests [6](#0-5) ; `HmacValidator` has no knowledge of headers; and the constructor only checks for header *presence*, not header authenticity: [7](#0-6) .

### Impact Explanation
Any app built on this gem that relies on `WebhookMetadata#shop` (i.e., `request.shop`) to attribute a webhook body to a merchant — e.g., to select which tenant's data/session to update, or to satisfy GDPR mandatory webhooks like `shop/redact` — can be made to act on attacker-supplied body content labeled with an arbitrary victim shop domain. This is a cross-tenant trust violation: the value the gem exposes as "the shop for this signed body" is not actually covered by the signature, so downstream code cannot distinguish a legitimately-addressed webhook from a relabeled one. It is repeatable against any victim domain the attacker chooses, and requires no special access beyond receiving one legitimate webhook on the attacker's own store.

### Likelihood Explanation
Preconditions are minimal and fully within the attacker's normal capability: create a free development store, install the target app (a normal, expected flow), trigger any webhook topic that the app subscribes to, capture the resulting body + `x-shopify-hmac-sha256`, and replay it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No secret, token, or elevated privilege is needed. The cost is a single legitimate webhook delivery plus one crafted replay request.

### Recommendation
Do not treat `x-shopify-shop-domain` (or other Shopify headers) as authenticated. Either fold the shop domain (and topic/webhook-id) into the signable string so `HmacValidator` covers them, or require the host application to independently verify `request.shop` against a known, previously-established session/shop record before acting on the payload, and add delivery-id/timestamp based replay protection in `Registry.process`.

### Proof of Concept
```ruby
# test/webhooks/request_shop_header_spoof_test.rb
require_relative "../test_helper"

class WebhookShopHeaderSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  end

  def test_same_signature_different_shop_accepted
    raw_body = '{"id":1,"note":"attacker-controlled"}'
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
    )

    request_victim = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      },
    )

    request_attacker = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      },
    )

    assert(ShopifyAPI::Utils::HmacValidator.validate(request_victim))
    assert(ShopifyAPI::Utils::HmacValidator.validate(request_attacker))
    refute_equal(request_victim.shop, request_attacker.shop)
    # Same signature, same body, both pass validation but resolve to two different shops.
  end
end
```
This demonstrates that one signed body/HMAC pair validates successfully under two different `shop` values, confirming `HmacValidator.validate` provides no binding between the signature and `request.shop`.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
