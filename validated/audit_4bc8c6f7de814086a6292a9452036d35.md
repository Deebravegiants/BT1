### Title
Webhook `shop` domain is not covered by HMAC validation, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" and hands the caller a `shop` field described as "The shop domain of the webhook." In reality, the HMAC signature that `process` validates is computed over the raw request body only — the `shop-domain` header is never part of the signed content. Any party who can obtain one legitimate, validly-signed webhook payload (e.g., by operating their own store connected to the same app, or by using Shopify's "send test notification" feature) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `Registry.process` will accept it as authentic and dispatch it to the app's handler with the attacker-chosen `shop` value, breaking the binding between "HMAC authenticated with the app's secret" and "the shop this data is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and compares it with `secure_compare`: [3](#0-2) 

`Registry.process` only checks this body HMAC before dispatching to the handler using the unauthenticated `shop` header value: [4](#0-3) 

The gem's documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook," implying it is a trustworthy, verified identity field: [5](#0-4) [6](#0-5) 

The broken equality is: `hmac_valid(raw_body, api_secret_key) == true` is treated as implying `request.shop == <the shop that actually generated this payload>`, when in fact `request.shop` is never included in the signed bytes, so the two are independent. This is the "field acted on but not covered by the HMAC" class of bug, applied to the tenant-identifying `shop` field rather than a benign field.

### Impact Explanation
Because `api_secret_key` is shared across all shops installing the same app, any shop connected to the app (an ordinary, unprivileged merchant — not a privileged account, no leaked credentials required) can generate a legitimately-signed webhook body/HMAC pair for itself and then replay it to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. The application handler (built per the gem's documented contract) will process attacker-supplied body content attributed to the victim tenant, since the only integrity check the gem performs (`Registry.process`) never binds `shop` to the signature. This crosses a tenant boundary — one merchant's data can be injected into, or confused with, another merchant's data/session in the host application, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no elevated privileges: an attacker only needs to be a merchant with the app installed (or otherwise able to trigger/capture one real webhook delivery, e.g., via the "send test notification" feature in Shopify admin) and the ability to send an HTTP POST with custom headers to the app's public webhook endpoint. No `api_secret_key`, access token, or social engineering is needed — the HMAC used is one the attacker legitimately obtained for their own store's traffic. The gem's own documentation encourages developers to trust `data.shop` as verified, making this a realistic and directly reachable analog for apps built following the documented usage pattern.

### Recommendation
Bind the shop identity into the authenticated data instead of trusting the `X-Shopify-Shop-Domain` header independently of the HMAC:
- Do not surface `request.shop` (or accept a `shop` HTTP header) as a trusted value in `WebhookMetadata` without independent verification (e.g., cross-checking it against a known, previously-stored shop domain associated with the webhook subscription/registration, or verifying it via a separate authenticated channel).
- At minimum, document prominently that `data.shop` is NOT covered by HMAC and must not be used as a sole tenant-selection key without additional verification, since this contradicts the current documentation's framing.

### Proof of Concept
1. App A is installed on `shop-a.myshopify.com` and `shop-victim.myshopify.com`, sharing the same `api_secret_key`.
2. The attacker, who controls `shop-a.myshopify.com`, triggers (or captures) a legitimate webhook delivery for `orders/create`, obtaining `raw_body` and the correct `X-Shopify-Hmac-Sha256` value computed by Shopify over that body with the app's secret.
3. The attacker POSTs the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header set; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (correctly captured) HMAC — see `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:12-22`.
5. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "shop-victim.myshopify.com", body: <attacker-controlled order JSON> ...)` — see `lib/shopify_api/webhooks/registry.rb:198-199` — causing the app to process attacker-supplied content as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
