Confirmed: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` and, when `Context.api_host` is not set (the default, standard config), the outbound request host is taken directly from `session.shop` — and this same value is echoed into the request body/headers along with `Context.api_key` and `Context.api_secret_key` for every `/admin/oauth/access_token` call.

`ShopifyAPI::Auth::TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-51`) takes `dest_shop = jwt_payload.shop` straight from the JWT's `dest` claim and builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` **without** ever calling `Utils::ShopValidator.sanitize!` on it — unlike every sibling credential-issuing method in the same file/module (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`), which all explicitly sanitize the shop before building the session used for the token request. `JwtPayload#shop` (`lib/shopify_api/auth/jwt_payload.rb:47-50`) is computed as `@dest.gsub("https://", "")` with zero domain restriction — it never checks that `dest` is on `myshopify.com`/`myshopify.io`/etc. The JWT is decoded with `JWT.decode(token, api_secret_key, true, ..., algorithm: "HS256")` and only `aud == Context.api_key` is verified beyond signature/exp — there is no `iss`/`dest` domain allow-list check anywhere in the class.

### Title
Missing shop-domain validation on token-exchange JWT `dest` claim allows client_secret exfiltration to attacker-controlled host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` derives the outbound request host directly from the session token's `dest` claim without validating it is a genuine Shopify domain, then sends `client_id`/`client_secret` to that host.

### Finding Description
`exchange_token` decodes an app-provided `session_token` via `JwtPayload.new` and takes `dest_shop = jwt_payload.shop` ( [1](#0-0) ). `JwtPayload#shop` merely strips `"https://"` from the `dest` claim with no domain restriction ( [2](#0-1) ), and `JwtPayload#initialize` only checks the `aud` claim equals `Context.api_key`; it never validates `iss`/`dest` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` ( [3](#0-2) ). `dest_shop` is then used unsanitized to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` ( [4](#0-3) ), which `HttpClient#initialize` turns directly into the request host: `@base_uri = "https://#{api_host || session.shop}"` ( [5](#0-4) ). The POST body sent to that host includes `client_id` and `client_secret` ( [6](#0-5) ).

This breaks the intended binding: *host that receives the `client_secret` == a Shopify-trusted domain*. Every sibling method that builds a shop-bound session for a `/admin/oauth/access_token` call — `ClientCredentials.client_credentials` ( [7](#0-6) ), `RefreshToken.refresh_access_token` ( [8](#0-7) ), and `TokenExchange.migrate_to_expiring_token` ( [9](#0-8) ) — explicitly call `Utils::ShopValidator.sanitize!(shop)`, which restricts the host to `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev` ( [10](#0-9) ). `exchange_token` is the sole exception.

Because the JWT is only verified for signature validity, expiry, and `aud`, and the `dest` claim content itself is unconstrained, the value that ultimately dictates where the app's `client_secret` is sent is effectively attacker-influenced input reaching the network layer unchecked — this is exactly the "host validated versus host that receives the client_secret" binding failure called out as in-scope.

### Impact Explanation
If a session token with an attacker-controlled `dest` (e.g., `evil.example.com`) is ever presented to `exchange_token` — whether via a compromised/malicious embedded-app iframe context, a host application that forwards a client-supplied token without additional checks, or any code path that constructs/passes through a token whose `dest` isn't independently constrained — the library will POST the app's `client_id` and `client_secret` to that attacker-controlled host. This is a direct `client_secret` exfiltration path (Critical impact per the rubric: theft of the app's `client_secret`), since compromise of `client_secret` allows full impersonation of the app across all merchants.

### Likelihood Explanation
Requires a session token whose signature validates (i.e., signed with the correct `api_secret_key`) but whose `dest` claim is not a real Shopify shop. Whether this is reachable depends on how the host application obtains `session_token` — if Shopify itself is the only party that mints such tokens (App Bridge session tokens are HS256-signed by Shopify with the app's shared secret) then real Shopify would only ever put a genuine `*.myshopify.com`/`*.myshopify.io` value in `dest`. However, this analysis cannot verify what other flows (e.g., custom/test JWT issuance, multi-tenant proxies, or future call sites) might feed into `session_token`; the missing defense-in-depth check is a clear deviation from this gem's own established pattern (every other credential-issuing method validates the shop) and removes a safety net that exists everywhere else in the same file.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` to `dest_shop` in `TokenExchange.exchange_token` before constructing `shop_session`, mirroring `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`:

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

Additionally, consider validating `dest`/`iss` claims against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` inside `JwtPayload#initialize` itself so all consumers of `JwtPayload.shop` get this guarantee for free.

### Proof of Concept
1. Obtain (or construct, if any code path allows attacker influence over the `dest` claim of an otherwise validly-signed session token) a JWT with `aud` = the app's `api_key`, valid `exp`/`nbf`, but `dest = "https://attacker.example.com"`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. `JwtPayload.new` accepts the token (only `aud` is checked against a fixed value; `dest` is unrestricted) — [11](#0-10) .
4. `dest_shop` becomes `"attacker.example.com"`, and `HttpClient` issues `POST https://attacker.example.com/admin/oauth/access_token` with `client_id` and `client_secret` in the body — [12](#0-11) , [5](#0-4) .
5. `attacker.example.com` receives the app's `client_secret`.
