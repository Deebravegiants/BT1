### Title
Donation-triggered underflow crash in `Router._computeBuy`'s overflow cap permanently DoSes large/final curve buys - ([File: packages/contracts/src/Router.sol])

### Summary
CVE-2022-0581 is a crash in Wireshark's CMS dissector triggered by malformed/crafted input, causing a denial of service. The analogous bug class on alt.fun is a crafted on-chain input — a direct ERC20 donation of the launched `Token` into its `Pair` — that drives `Router._computeBuy`'s overflow-cap arithmetic into an underflow/degenerate state, permanently reverting ("crashing") any buy that needs to invoke the cap branch, from a completely unprivileged wallet.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's real token balance whenever the naive AMM math would exceed it, and then back-calculates `amountInUsed` from a `cappedReserveToken = reserveToken - tokensOut`: [1](#0-0) 

`reserveToken` is the *virtual* reserve stored in `Pair` (starts at `totalSupply` = 1e27) while `tokensOut` is capped at `pair.tokenBalance()` — the *real* ERC20 balance of the launched `Token` held by `Pair`. By construction (`_deployAndSeed`), the two are supposed to stay a fixed `LP_RESERVE` (250,000,000e18) apart for the life of the curve, since every buy subtracts the same `tokensOut` from both the virtual reserve and the real balance via `Pair.swap`: [2](#0-1) [3](#0-2) 

However, `Router._computeBuy` reads `pair.tokenBalance()` directly via `IERC20.balanceOf`, which is *not* donation-resistant: any unprivileged wallet can call `Token.transfer(pairAddress, amount)` to inflate the real balance above what the curve's own accounting expects. If enough Token is donated directly into `Pair` to close (or reverse) the fixed 250M-token gap between `reserveToken` and `realBalance`, the next buy whose naive `tokensOut` exceeds `realBalance` hits the cap branch with `tokensOut == realBalance >= reserveToken`. The subtraction `reserveToken - tokensOut` then either produces `0` (caught, reverting with `OverflowCapDegenerate()`) or, if the donation pushes `realBalance` strictly above `reserveToken`, underflows a `uint256` subtraction and reverts with an unhandled Solidity `Panic(0x11)` — an uncontrolled crash, exactly analogous to the crafted-input dissector crash in the CVE.

This is reachable purely through `Zap.buy`/`buyWithPermit`, which routes to `Bonding.buy` → `Router.buy` → `_computeBuy`, with no special privilege required to perform the preceding donation (`IERC20(token).transfer(pairAddress, amount)` is a plain, unprivileged ERC20 transfer named explicitly in scope).

### Impact Explanation
Once the donation closes the gap, every subsequent buy attempt large enough to trip the overflow-cap branch permanently reverts (the donation is irreversible — `Token.burn` is only invoked by `Bonding` at graduation time, not by third parties, and nothing drains a hostile donation out of `Pair` before that). This:
- Permanently freezes the ability of legitimate traders to execute large/final buys on the affected curve (denial of service on trades that hit the cap).
- Blocks the supply-side graduation trigger (`tokenBalance() == 0`), since no buy can ever fully drain the pair once the cap branch is broken, forcing the token to depend solely on the USD-threshold trigger (`triggerGraduation`) for graduation, and in the worst case (a very low-value LT / low `exchangeRate`) may never graduate via the intended supply-exhaustion mechanism.
- Constitutes a permanent freezing of the trading path for legitimate buyers on an unprivileged, single-transaction crafted input, matching the "Medium" bug class in the CVE (crash / DoS via crafted input) mapped onto alt.fun's bonding-curve AMM math.

### Likelihood Explanation
The donation itself requires an attacker to acquire a large (up to 250,000,000e18) amount of the specific launched `Token`, which is capital-intensive on well-traded tokens but only requires the attacker to buy tokens on the curve (a normal permissionless action) and then transfer them directly to `Pair` instead of selling — no special access, and the attack surface is explicitly listed as in-scope ("direct ERC20 transfers of a launched Token ... into Pair"). On lower-liquidity or newly launched tokens with a small curve supply already consumed, the capital requirement to close the gap is proportionally smaller, making the attack more economical.

### Recommendation
`Router._computeBuy`'s overflow-cap branch should not rely on the live, donation-inflatable `pair.tokenBalance()` when deriving `cappedReserveToken`; instead it should clamp/guard the cap using the curve's own accounted values (e.g., treat `realBalance` as `min(realBalance, reserveToken)` before computing `cappedReserveToken`, or explicitly early-return/revert with a clear, non-Panic error before the subtraction can underflow), consistent with the donation-resistance pattern already applied to `canGraduate`'s USD-trigger leg.

### Proof of Concept
1. `Zap.createToken(...)` launches a token; `reserveToken = 1e27`, real `tokenBalance() = 7.5e26` (curveSupply), fixed gap = `LP_RESERVE = 2.5e26`.
2. Attacker buys/accumulates a large amount of the launched `Token` on the curve via `Zap.buy`.
3. Attacker calls `Token.transfer(pairAddress, amount)` directly (bypassing `Zap`/`Bonding`/`Router`) to donate enough Token into `Pair` so that `tokenBalance() >= reserveToken - <small delta>`.
4. Any subsequent buyer whose intended `tokensOut` (uncapped AMM math) exceeds the now-inflated `realBalance` triggers the cap branch in `Router._computeBuy`; `cappedReserveToken = reserveToken - tokensOut` computes `0` or underflows, reverting every such buy from that point forward — the affected curve is permanently unable to process buys at that size, and full curve-drain (supply-trigger graduation) becomes unreachable.

Note: I was not able to fully verify, within the available tool budget, the exact capital threshold at which this becomes economically attractive for a real attacker on a live token, nor whether any off-chain/keeper mitigation exists that could detect and remediate the donation before it causes harm — a Devin session with broader repository/tests access would be needed to confirm exact PoC numbers via Foundry tests.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

This deploys a `Token` clone (1B supply) and creates a `Pair` (token/LT). K is computed per token so every token opens at ~`$3K` market cap regardless of which LT is paired.

**Virtual token reserve.** The pair's `reserve0` is seeded at `totalSupply` (1B) while only `curveSupply = 75%` (750M) of real tokens are actually transferred. The other 250M are held in `Bonding` as `lpReserve`. This virtual-reserve design:

- Extends the curve beyond the sellable supply.
- Gives a deterministic supply trigger (curve exhausts at 750M sold).
- Makes the dynamic-LP-seeding parabola `tokensForLP(sold) = sold·(S−sold)/S` peak at exactly `S/4 = 250M = LP_RESERVE` — so `tokensForLP ≤ lpReserve` is a mathematical invariant, not a runtime guess.
