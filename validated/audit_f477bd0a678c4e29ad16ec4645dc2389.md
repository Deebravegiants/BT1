### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims (per the gem's own docs) to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC check only authenticates the raw body — it never binds the `shop-domain` header that is handed to the handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` as simply the raw request body: [1](#0-0) 
The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from unauthenticated HTTP headers and are never fed into `to_signable_string`: [2](#0-1) 
`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, i.e. only over the body, using `OpenSSL.secure_compare` against `verifiable_query.hmac`: [3](#0-2) 
`Registry.process` gates on that HMAC check and then constructs the tenant-identifying `WebhookMetadata` directly from `request.shop` (the unauthenticated header), passing it to the app's handler: [4](#0-3) 
The security-relevant equality that should hold is: `shop authenticated by the HMAC == shop delivered to the handler for tenant routing`. Because `to_signable_string` never includes the shop header, that equality is never enforced. Since Shopify signs webhooks with the app-wide `client_secret` (the same secret for every shop that has installed the app), any merchant who installs the app can legitimately trigger a webhook for their own shop, capture a `(body, hmac)` pair that is valid for an attacker-chosen body, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` calls the handler with `shop: <victim-shop>` — letting the attacker inject fabricated webhook events attributed to a tenant they don't own.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on: the doc-recommended handler pattern (`docs/usage/webhooks.md`) explicitly uses `data.shop` to key session lookups and background jobs (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). An attacker-controlled shop can forge cross-tenant events (e.g. spoofed `orders/create`, `app/uninstalled`, `customers/data_request`) that the host app will process as if they originated from a different, victim merchant, since the gem's own "verified" webhook object carries an unauthenticated shop identity. This is a cross-tenant identity-binding bypass reachable by any unprivileged merchant/internet user who can install the app once, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high: no access token, `client_secret`, or privileged account is required — only the ability to install the app as an ordinary merchant (which the app already permits to the public) and the ability to POST an HTTP request with attacker-chosen headers to the app's public webhook endpoint. The exploit requires no host-application misconfiguration beyond following the gem's own documented usage.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content that `HmacValidator` verifies, or independently verify `request.shop` against the set of shops that have a known, valid offline session/installation for the app before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked by the host application against its own installed-shop records before being used for tenant routing.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Attacker POSTs to the app's webhook endpoint the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Server calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers))`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` — this matches because `B` is unchanged, so validation succeeds: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, even though the payload/HMAC never originated from `victim-shop.myshopify.com`: [6](#0-5) 
6. The host application processes an event as belonging to `victim-shop.myshopify.com`, achieving cross-tenant event injection.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
