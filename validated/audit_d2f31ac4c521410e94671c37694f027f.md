Audit Report

## Title
Dry-run vs. real-transaction `CREATE1` address mismatch in `pallet-revive` due to missing `ExecContext` check - ([File: substrate/frame/revive/src/exec.rs])

## Summary
`Storage::new_frame` in `substrate/frame/revive/src/exec.rs` derives the `CREATE1` contract address by conditionally subtracting 1 from the sender's account nonce, gated only on the `origin_is_caller` boolean, with no distinction between a real dispatched transaction (where `frame_system`'s nonce has already been incremented pre-dispatch) and an RPC/dry-run simulation (where it has not). The repository's own `prdoc/stable2506/pr_8504.prdoc` documents this exact defect and describes a fix that adds an `ExecContext::Transaction` check to the condition, but that fix is absent from the current code — the code today is identical to the "Before Fix" snippet quoted in the prdoc.

## Finding Description
In `Storage::new_frame`, the `FrameArgs::Instantiate` branch computes the `CREATE1` address as: [1](#0-0) 

```rust
address::create1(
    &deployer,
    if origin_is_caller {
        account_nonce.saturating_sub(1u32.into()).saturated_into()
    } else {
        account_nonce.saturated_into()
    },
)
```

`origin_is_caller` is a plain boolean parameter to `new_frame` [2](#0-1) , and `Storage::new` (used for both dry-run and real dispatch entry points) always passes `true` for `origin_is_caller` when constructing the first frame: [3](#0-2) . There is no `exec_context`/`ExecContext` parameter anywhere in `exec.rs` — a repository-wide search confirms `ExecContext` exists only inside `prdoc/stable2506/pr_8504.prdoc` and nowhere in the actual source.

The prdoc explicitly states the "Before Fix" behavior matches the code quoted above word-for-word, and describes the intended fix as adding `&& matches!(exec_context, ExecContext::Transaction)` to the condition, plus a regression test `nonce_not_incremented_in_dry_run()`. Neither the code change nor the test exists in this repository snapshot, confirming the fix described in the prdoc was never actually applied to `exec.rs`.

## Impact Explanation
Because the subtraction is unconditionally tied to `origin_is_caller=true` regardless of whether the account's nonce has actually been incremented (which happens pre-dispatch only for real transactions, not for RPC/dry-run simulation), a `CREATE1` (no-salt) contract deployment previewed via dry-run returns a different address than the address actually used once the real transaction is dispatched. Any tooling/wallet that relies on dry-run output to predict, whitelist, pre-fund, or reference the to-be-deployed address will be pointed at the wrong address — this is a functional correctness bug in the EVM-compatibility layer's address-prediction guarantee, matching the exact "Before Fix" behavior documented by the project's own prdoc.

## Likelihood Explanation
This is deterministically reachable by any unprivileged user performing the standard dry-run-then-submit workflow for contract creation without a salt — no special privileges, victim mistakes, or unrealistic preconditions are required. The mismatch manifests every time `origin_is_caller` is true in a dry-run context, which is the normal case for top-level `instantiate`/`instantiate_with_code` calls.

## Recommendation
Reintroduce the `ExecContext` (or equivalent) distinction so the nonce-adjustment is applied only when executing inside an actually dispatched transaction:
```rust
if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
    account_nonce.saturating_sub(1u32.into()).saturated_into()
} else {
    account_nonce.saturated_into()
}
```
Restore/add the `nonce_not_incremented_in_dry_run` regression test referenced in `prdoc/stable2506/pr_8504.prdoc` to lock in the fix.

## Proof of Concept
1. For account `A` at nonce `N`, call the dry-run/bare-instantiate path (`salt = None`) for a `CREATE1` deployment. Since this is a simulated call, `frame_system`'s nonce for `A` remains `N`, but `new_frame` (with `origin_is_caller == true`) computes `create1(deployer, N-1)`.
2. Submit the real signed `instantiate`/`instantiate_with_code` extrinsic for the same account `A`. By the time execution reaches `new_frame`, `frame_system` has incremented the nonce pre-dispatch to `N+1`, and the same logic computes `create1(deployer, N)`.
3. Compare the two addresses: `create1(deployer, N-1)` (dry-run) vs. `create1(deployer, N)` (real deployment) — they differ, exactly as described in the "Before Fix" section of `prdoc/stable2506/pr_8504.prdoc`.
