The `shop` field, however, is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) , and `Registry.process` passes that same header-derived value straight into `WebhookMetadata.shop`, which is the tenant identifier handed to the host application's handler, after only checking the body HMAC [3](#0-2) .

### Title
Webhook `shop` field is not covered by HMAC, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant identification from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body` alone). This breaks the intended binding `verified_bytes == acted_on_bytes`: the gem verifies the body but acts on a header that is completely outside the signed material.

### Finding Description
`Webhooks::Registry.process` is the entry point host applications are told to call for every incoming webhook [3](#0-2) . It validates the request solely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to build the string to HMAC [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as just the raw body [1](#0-0) .

Meanwhile, `request.shop` — the value that becomes `WebhookMetadata#shop` passed to the app's handler — is pulled unauthenticated from the `shop-domain` header [2](#0-1) . Since the HMAC is computed over the body only, any request with a body/HMAC pair that is valid for the app's `client_secret` remains valid regardless of what `shop-domain` header value accompanies it. An entity that legitimately receives real webhooks for its own shop (e.g., a merchant who installed the app on their own store) can capture a valid `(body, hmac)` pair from Shopify and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop, and `Registry.process` will accept it as authentic and dispatch it to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the identity binding `shop authenticated == shop the webhook is attributed to`, allowing a shop owner (an unprivileged actor relative to other tenants) to inject forged webhook events attributed to another merchant's shop into the host application's webhook handler. Depending on what the host app's `WebhookHandler#handle` implementation does with `data.shop` (e.g., look up and mutate records, trigger business logic, index by shop), this is a cross-tenant data confusion / cross-tenant access vector, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control an app installation (their own shop) so they can obtain a validly-signed `(body, hmac)` pair, then re-POST it to the same webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or privileged access are required beyond having the app installed on one's own store — a normal, unprivileged capability for any merchant using the app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the verified payload, instead of trusting the `x-shopify-shop-domain` header independently of the HMAC check in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the resulting raw body and `x-shopify-hmac-sha256` header sent by Shopify (both valid for the app's `client_secret`).
2. POST this same body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because the HMAC only covers `@raw_body` [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim.myshopify.com"` [5](#0-4) , causing the app to process attacker-controlled webhook content as if it originated from the victim shop.
