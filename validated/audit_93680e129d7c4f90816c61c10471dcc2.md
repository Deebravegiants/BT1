### Title
Stale `connectedAccountsAtom` cache is not automatically refreshed when wallet accounts are removed/disabled, leaking removed-account addresses to connected origins - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins.updateConnectedAccounts()` is the only mechanism that resynchronizes the `connectedAccountsAtom` cache (addresses exposed to trusted dApps) with the current set of enabled wallet accounts in `enabledWalletAccountsAtom`. This method is not invoked automatically whenever wallet accounts change (e.g. on `disable`/`removeMany` in `@exodus/wallet-accounts`); it must be explicitly called. This mirrors the structural root cause of the Rio Network finding: a privileged/administrative state change (operator cap set to 0 / account removed) is not propagated to a dependent cache (withdrawal queue / connected-accounts cache) used later for a security-relevant decision, allowing stale data to be used.

### Finding Description
`connectedAccountsAtom` explicitly documents itself as an unsafe-storage cache used to serve addresses to origins without requiring the wallet to be unlocked, for "eagerly connecting": [1](#0-0) 

The cache is only rebuilt in two code paths inside `connections.js`: `#setData` (called by `add`, `untrust`, `#setAttributes`, etc.) and the explicit `updateConnectedAccounts()` method: [2](#0-1) 

`updateConnectedAccounts` computes an `xor` between the wallet accounts currently in `enabledWalletAccountsAtom` and the accounts cached in `connectedAccountsAtom`, and only refreshes the cache if a difference is detected — but this method is never triggered automatically by wallet-account mutations. The dedicated tests demonstrate that the module owner must call it manually after mutating `enabledWalletAccountsAtom`: [3](#0-2) 

Meanwhile, `@exodus/wallet-accounts` disables/removes accounts (`disableMany`, `removeMany`) purely against its own atoms, with no call into `connectedOrigins.updateConnectedAccounts()`: [4](#0-3) 

The plugin that wires `connectedOrigins` to platform events only observes `connectedOriginsAtom` to emit port events and calls `connectedOrigins.clear()` on wallet clear — it does not appear (based on its test suite) to observe `enabledWalletAccountsAtom` changes and invoke `updateConnectedAccounts()` reactively: [5](#0-4) 

As a result, `getConnectedAccounts` — the API surface a trusted/connected origin uses to enumerate wallet addresses — reads directly from the (potentially stale) `connectedAccountsAtom` rather than re-deriving from the live `enabledWalletAccountsAtom`: [6](#0-5) 

This is structurally the same class of bug as the Rio finding: a source-of-truth mutation (wallet account removed/disabled) does not propagate to a dependent accounting/cache structure (`connectedAccountsAtom`) that is later trusted for a privileged operation (exposing account addresses to an already-trusted third-party origin), unless a specific, easily-missed reconciliation call (`updateConnectedAccounts`) happens to run first.

### Impact Explanation
If `updateConnectedAccounts()` is not reliably invoked on every wallet-account disable/removal (I was unable to fully enumerate every call site across platform integrations — e.g. `apps/`, browser-extension background, mobile — before exhausting available tool calls), a trusted origin can continue to receive/enumerate the address of a wallet account the user believed they removed or disabled, via `connectedOrigins.getConnectedAccounts`. This is a cross-account/cross-origin privilege-bleed of address data: it violates the user's expectation that disabling/removing an account revokes any dApp-visible association with it, and could be leveraged by a malicious/compromised origin to keep tracking or requesting operations against an account the user intended to disconnect.

### Likelihood Explanation
Moderate. The bug is only exposed on paths that mutate `enabledWalletAccountsAtom` (disable/remove account, or add new account) without every caller remembering to invoke `connectedOrigins.updateConnectedAccounts()`. I confirmed the module itself requires an explicit call and confirmed the wallet-accounts module has no dependency on/reference to `connectedOrigins`, but I could not verify (due to running out of tool-call budget) whether some other central orchestration layer (e.g. an app-level event bus or the SDK background script) reliably calls `updateConnectedAccounts()` on every account mutation across all platforms. This uncertainty should be resolved by a follow-up investigation of all wallet-accounts mutation call sites and background/plugin wiring.

### Recommendation
- Make `connectedOrigins` reactively subscribe to `enabledWalletAccountsAtom` (and `activeWalletAccountAtom`) changes and automatically call `updateConnectedAccounts()` whenever the set of enabled wallet accounts changes, rather than relying on external callers to invoke it.
- Alternatively, have `getConnectedAccounts` derive addresses live from `enabledWalletAccountsAtom`/`addressProvider` at read-time instead of trusting the cached `connectedAccountsAtom`, falling back to the cache only for the "eager connect while locked" scenario explicitly documented in `connected-accounts.js`.
- Add regression tests that disable/remove a wallet account without explicitly calling `updateConnectedAccounts()` and assert that `getConnectedAccounts` no longer returns that account's address.

### Proof of Concept
1. Connect/trust an origin for asset `solana`, exposing `exodus_0` and `exodus_1` addresses (as in `connections.test.js` lines 90-127).
2. Call `walletAccounts.disable('exodus_1')` (or `removeMany(['exodus_1'])`) directly via `@exodus/wallet-accounts`, without calling `connectedOrigins.updateConnectedAccounts()`.
3. Call `connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })`.
4. Because `connectedAccountsAtom` was never refreshed, the removed/disabled `exodus_1` address is still returned to the origin, contrary to the user's action of disabling/removing that account — matching the pattern demonstrated by the module's own test at lines 250-273 which requires an explicit `updateConnectedAccounts()` call to reflect the removal. [3](#0-2)

/**
 * This atom caches addresses of connected accounts so they can be used when eagerly connecting without a user interaction.
 * We cannot use address provider in that case because the wallet may not be unlocked. This atom however sits on top of
 * the unsafe storage.
 */
export default function createConnectedAccountsAtom({ storage }) {
  return dedupe(
    createStorageAtomFactory({ storage })({
      key: 'accounts',
      defaultValue: {},
      isSoleWriter: true,
    })
  )
}

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

  updateConnectedAccounts = async () => {
    const walletAccounts = await this.#enabledWalletAccountsAtom.get()
    const connectedAccounts = await this.#connectedAccountsAtom.get()

    const difference = xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))
    if (difference.length === 0) {
      // up-to-date
      return
    }

    const connectedOrigins = await this.#connectedOriginsAtom.get()
    const assetNames = this.#getConnectedAssets(connectedOrigins)
    const updatedAccounts = await this.#getAccounts(assetNames)

    await this.#connectedAccountsAtom.set(updatedAccounts)
  }

    const currentWalletAccounts = await this.#getInternalWalletAccountsWithFallback()
    walletAccountNames = walletAccountNames.filter(

    )

    if (walletAccountNames.length === 0) return

    const walletAccounts = { ...currentWalletAccounts }

    await this.setActive((oldValue) =>
      walletAccountNames.includes(oldValue) ? WalletAccount.DEFAULT_NAME : oldValue
    )

    for (const walletAccount of walletAccountNames) {
      if (walletAccounts[walletAccount].isHardware) {
        delete walletAccounts[walletAccount]
        delete this.#hardwareWalletPublicKeys[walletAccount]
      } else {
        walletAccounts[walletAccount] = this.#disableWalletAccount(walletAccounts, walletAccount)
      }
    }

    if (equalWalletAccounts(currentWalletAccounts, walletAccounts)) return

    await this.#walletAccountsInternalAtom.set(walletAccounts)
    await this.#savePublicKeys()
    await this.#updateFusion()
  }

        'removeMany can only be used in conjunction with fillIndexGapsOnCreation. Please disable instead.'

    const walletAccounts = { ...currentWalletAccounts }
