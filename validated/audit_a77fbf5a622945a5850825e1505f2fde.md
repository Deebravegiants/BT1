This confirms the vulnerability: `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` come from unsigned headers (`lib/shopify_api/webhooks/request.rb:20-33`), and `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes that unauthenticated `shop` straight into `WebhookMetadata`, which host apps use as the tenant/session key.

### Title
Webhook shop identity spoofing via headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream come from HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then trusts the header-derived `shop` (and `topic`) to build the `WebhookMetadata` that is handed to the app's handler as the identity of the tenant the webhook belongs to: [3](#0-2) [4](#0-3) 

The `api_secret_key` (the HMAC secret) is shared across every shop that has installed the app — it is not per-shop. An attacker who controls any shop that has installed the target app (e.g., a free development store) receives genuinely Shopify-signed webhook deliveries, i.e., legitimate `(raw_body, hmac)` pairs computed with that shared secret. Because the `x-shopify-shop-domain` (and other identity) headers are outside the signed content, the attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `HmacValidator.validate` will still accept it because it only recomputes the signature over the body: [5](#0-4) 

This breaks the identity binding: **shop authenticated by the HMAC ≠ shop the application trusts as the webhook's tenant** (`WebhookMetadata#shop`), letting an attacker impersonate a webhook event as belonging to a different, unrelated shop.

### Impact Explanation
Downstream apps use `data.shop` from `WebhookMetadata` as the authoritative tenant identifier to look up/act on merchant data (per the gem's own documented usage pattern of enqueuing work keyed by `shop_domain`). An attacker can forge cross-tenant webhook events (e.g., claim an `orders/create` or `app/uninstalled` webhook belongs to a victim shop) using only a body/HMAC pair legitimately issued to their own installation of the app, without ever learning `api_secret_key`. This is a cross-tenant integrity/identity issue: the app processes attacker-controlled shop-scoped events as if they originated from the victim tenant.

### Likelihood Explanation
Requires only that the attacker install the target app on any shop they control (trivial for most public apps, e.g. via a free development store) and can capture a real webhook delivery's raw body/HMAC pair, then POST it to the app's callback endpoint with a spoofed `shop-domain` header. No secrets or privileged access are needed beyond ordinary app installation.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind the header values to the signature (Shopify's own webhook signature only covers the body by design, so this must be mitigated by the gem/host app correlating shop-domain against a known/expected value, e.g. validating that `request.shop` matches a shop this app instance has an active session/webhook registration for, before trusting it).

### Proof of Concept
```ruby
# Attacker installs TargetApp on their own shop "attacker.myshopify.com"
# and receives a genuine webhook delivery for "orders/create":
raw_body = '{"id":1,"note":"hi"}'
hmac     = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), shared_api_secret_key, raw_body)

# Attacker replays the same body/hmac to the app's webhook endpoint,
# but swaps the shop-domain header to a victim shop they don't control:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),      # still valid! body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed, not covered by hmac
  "x-shopify-webhook-id"  => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HMAC validation; handler receives WebhookMetadata with shop == "victim-shop.myshopify.com"
```
