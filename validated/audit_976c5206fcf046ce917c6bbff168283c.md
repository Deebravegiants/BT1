### Title
Escrowed order funds can be permanently frozen if the beneficiary address is blacklisted by the input/output token - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (and its tron/legacy counterpart `IntentGatewayV2.withdraw`) releases escrowed order tokens by transferring them directly to a hardcoded `beneficiary` address with no way to redirect the transfer to a different address. If the escrowed token (e.g. USDC) blacklists that beneficiary address after the order was placed but before settlement/cancellation, the transfer reverts and the escrow can never be released.

### Finding Description
Escrow release happens in `_withdraw` for `RedeemEscrow`/`RefundEscrow` (cross-chain) and in `_cancelSameChain`/`fillOrder` (same-chain), all of which end up calling:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
``` [1](#0-0) 
where `beneficiary` is derived from `body.beneficiary` (itself `order.user` for refunds, set immutably at `placeOrder` time to `msg.sender`) or from the solver's address for fills. The same pattern exists in the legacy/tron `IntentGatewayV2.withdraw`: [2](#0-1) 

Both `onAccept` (handling `RedeemEscrow`/`RefundEscrow` from Hyperbridge) and `onGetResponse` (handling the cancel-from-source flow) call `_withdraw`/`withdraw` unconditionally, and any revert inside the token transfer bubbles up and reverts the entire message handling: [3](#0-2) [5](#0-4) 

Because `beneficiary` cannot be changed once an order is placed (`order.user` is fixed to the placer's address at `placeOrder`, and `WithdrawalRequest.beneficiary` in the cross-chain message body is likewise fixed once the cancel/fill is dispatched), if a blacklist-capable token (USDC, USDT, etc.) blacklists that address between order placement and settlement/refund, every future attempt to deliver `onAccept`/`onGetResponse` for that order's commitment will revert. Unlike a normal user balance, there is no alternative unlocking mechanism (e.g., liquidation by a third party in the Sherlock analog) — the only caller of `_withdraw` for a given commitment sends to the same fixed, now-blacklisted address, forever.

Same-chain fills/cancellations have the identical property: [4](#0-3) 

### Impact Explanation
Any escrowed input tokens (and any escrowed relayer/transaction fee token) belonging to a user whose settlement/refund address becomes blacklisted by the escrowed token's issuer are permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` contract. There is no `SweepDust`-style governance path for order-scoped escrow (only for accumulated protocol dust), and no way for the user or anyone else to specify an alternate receiving address. This is a permanent freezing of user funds — the tokens remain stuck in the gateway indefinitely with no recovery path, satisfying "permanent freezing of funds."

### Likelihood Explanation
This requires the escrowed token to have blacklist functionality (e.g., USDC/USDT, both explicitly referenced as supported/expected assets throughout the test suite and docs) and for the specific order's beneficiary address to be blacklisted after order placement/cancellation but before settlement. Given USDC/USDT are the primary quoted assets in the IntentGateway examples and tests, and blacklisting events do occur on these tokens (sanctions, compliance actions), this is a realistic, if not everyday, occurrence — consistent with the same Medium/High rating class as the original report, but strictly worse here due to the complete absence of a fallback recovery path.

### Recommendation
Decouple escrow release from direct pushed transfers to an immutable `beneficiary`:
- Use a pull-based withdrawal pattern where the escrow is credited to an internal balance keyed by `beneficiary`, and a separate `claim`/`withdraw` function lets `beneficiary` (or a party they authorize) pull funds to an address of their choosing, or
- Wrap the `safeTransfer` in a try/catch and, on failure, credit an internal "stuck funds" ledger recoverable by the beneficiary to a different address they control, rather than reverting the whole settlement/refund/cancel message processing.

### Proof of Concept
1. User places a same-chain or cross-chain order via `placeOrder`, escrowing USDC as input; `order.user` is set to the user's address (`msg.sender`) at placement time.
2. Issuer (Circle) blacklists the user's address for compliance reasons after the order is placed but before it is filled or cancelled.
3. User calls `cancelOrder` → `_cancelSameChain`/`_cancelFromDest`/`_cancelFromSource`, which eventually calls `_withdraw`/`withdraw` with `beneficiary = order.user` (the now-blacklisted address).
4. `IERC20(USDC).safeTransfer(beneficiary, amount)` reverts because the recipient is blacklisted; the entire `cancelOrder`/`onAccept`/`onGetResponse` call reverts.
5. Every subsequent attempt (by the user, a relayer, or anyone) to settle/refund/cancel this order's commitment reverts identically, since `beneficiary` cannot be changed. The escrowed USDC is permanently stuck in the gateway contract with no recovery mechanism.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
