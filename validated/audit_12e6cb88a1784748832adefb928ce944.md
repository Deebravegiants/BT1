## Analysis

The reported bug class is: an unprivileged third party can alter an account's balance outside the expected code path, breaking an invariant the calling code assumes (e.g., "balance is 0 before/after an operation"), causing a subsequent operation that depends on that exact-state invariant to permanently revert — a denial of service with no alternate recovery path.

The Agave analog to this exists in the System Program's `create_account` handler.

### Title
Denial of service via account pre-funding griefing in `SystemInstruction::CreateAccount` - (File: `programs/system/src/system_processor.rs`)

### Summary
`create_account` in the system program rejects account creation whenever the target account already holds any lamports, regardless of who put them there. Because Solana's `Transfer` instruction lets *any* unprivileged party send lamports to *any* pubkey (the destination account is never required to sign or be owned by a particular program), an attacker can pre-fund a not-yet-created address (e.g., a PDA a protocol is about to initialize) with as little as 1 lamport. This deterministically and permanently blocks any subsequent `CreateAccount` instruction targeting that address, exactly mirroring the cNote/treasury pattern in the external report: an outside, unprivileged balance mutation breaks an invariant ("account must start at zero lamports") that a critical operation strictly requires, bricking that operation with no remediation other than choosing a different address.

### Finding Description
`create_account` explicitly fails if the destination account has any lamports at all: [1](#0-0) 

The lamports check (`to.get_lamports() > 0` → `SystemError::AccountAlreadyInUse`) has no way to distinguish "pre-funded by a legitimate payer as part of the same transaction" from "griefed by an unrelated third party in a prior slot." Meanwhile, the plain `Transfer` instruction only requires the `from` account to sign; the `to` account's owner or existing state is never validated: [2](#0-1) 

So any unprivileged actor who can predict an address a protocol will later create (very common — PDAs and deterministic seeds are inherently predictable) can send it 1 lamport ahead of time. From that point on, every attempt by the legitimate owner/program to `CreateAccount` at that address fails with `AccountAlreadyInUse`, tested and confirmed by the existing test suite itself: [3](#0-2) 

Notably, Agave's own developers recognized this exact griefing pattern is a real operational problem: a separate instruction, `CreateAccountAllowPrefund`, was introduced specifically to let programs bypass the zero-lamports check when they expect prefunding: [4](#0-3) 

But this is opt-in per caller — any existing or future program/integration that still calls the plain `CreateAccount` instruction (the vast majority of on-chain programs and client tooling) remains fully exposed to the griefing vector.

### Impact Explanation
An unprivileged attacker can permanently deny the creation of any account at a predictable address (vaults, escrow accounts, staking/delegation accounts, program-derived state accounts, etc.) for the cost of a single lamport transfer plus one signature fee. Because `AccountAlreadyInUse` is unconditional on lamports being nonzero, there is no way for the intended creator to "clean up" the griefed balance through the System Program itself — the address is permanently unusable for `CreateAccount`, forcing protocols to either derive a new address (breaking deterministic PDA schemes that rely on a specific seed) or migrate to `CreateAccountAllowPrefund`. This matches the judged severity rationale in the external report: an invariant assumed by the critical operation (zero balance) is broken by an uninvolved party, and the affected functionality is bricked with no in-protocol remedy for that specific address.

### Likelihood Explanation
Trivial and cheap to execute: it requires only knowledge of the target pubkey (frequently deterministic/predictable via seeds or PDAs) and a single `Transfer` instruction costing 1 lamport + a base transaction fee. No special privileges, timing races, or validator/operator access are needed — this is purely an unprivileged end-user action against the SVM's system program instruction-processing path.

### Recommendation
For any protocol-level integration, avoid the plain `CreateAccount` instruction for pubkeys that can be predicted or targeted ahead of time (e.g., PDAs, seed-derived addresses); use `CreateAccountAllowPrefund` (or the `allocate`/`assign` + separate funding pattern) instead so that pre-existing, incidental lamport balances do not block initialization. At the runtime level, no change is proposed to `CreateAccount`'s semantics (the check is intentional to prevent clobbering in-use accounts), but documentation/guidance should make explicit that `CreateAccount` is unsafe against pre-funding griefing for any address whose derivation is public.

### Proof of Concept
1. Attacker observes/derives the address `P` that a victim protocol intends to initialize via `CreateAccount` (e.g., a PDA derived from public seeds).
2. Attacker submits `system_instruction::transfer(attacker_pubkey, P, 1)` — no signature or involvement from `P` or the victim is required, per `transfer`/`transfer_verified`: [5](#0-4) 
3. `P` now holds 1 lamport.
4. Victim's transaction issues `SystemInstruction::CreateAccount { lamports, space, owner }` targeting `P`.
5. `create_account` observes `to.get_lamports() > 0` and returns `Err(SystemError::AccountAlreadyInUse)`, exactly as covered by the existing unit test `test_create_already_in_use` (line 1014-1040 above), permanently blocking creation of `P` via this instruction.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}

fn transfer(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    if !instruction_context.is_instruction_account_signer(from_account_index)? {
        ic_msg!(
            invoke_context,
            "Transfer: `from` account {} must sign",
            instruction_context.get_key_of_instruction_account(from_account_index)?,
        );
        return Err(InstructionError::MissingRequiredSignature);
    }

    transfer_verified(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}
