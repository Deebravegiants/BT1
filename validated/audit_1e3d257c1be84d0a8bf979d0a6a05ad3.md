### Title
Untrusted route bytes let an attacker-named "pool" contract inject a token `transfer` from the caller into the caller's own auth tree, draining the caller's wallet — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The SQL-injection report's class is: unsanitized attacker-controlled input reaches a sensitive execution sink. The lending analog is the strategy-swap path: the `swap` argument in `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`/`flash_position`/`swap_debt` is caller-controlled bytes forwarded verbatim to the router, which invokes whatever `pool`/`token` addresses the payload names with no allowlist. Code inside a route-named contract executes below the caller's `require_auth` frame, so any `token.transfer(caller, attacker, amount)` it issues joins the caller's recorded authorization tree — and executes if the caller signs that tree. The stolen funds are the caller's whole wallet balance of any token, not just the routed amount.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` takes the caller-supplied `swap: &StrategySwap`, authorizes only `token_in.transfer(controller, router, amount_in)` (line 34), then calls `router.execute_strategy(&controller, &amount_in, swap)` (line 37) with no validation of the route's contents. The router dispatches each hop to the `pool` address the payload names via `env.invoke_contract(&ctx.hop.pool, ...)` — e.g., `contracts/swap-aggregator/src/venues/phoenix.rs:23-25` and `sushi.rs:48-50` — and keeps no venue/pool allowlist (`contracts/swap-aggregator/src/venues/mod.rs:34-40`).

Soroban attaches contract-initiated calls that require an existing authorized identity as children of that identity's invocation. A rogue "pool" contract can therefore call `token::Client::transfer(&caller, &attacker, &x)` on any token the caller holds. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-71` demonstrates exactly this: `RogueHopPool::swap` issues `transfer(victim, attacker, WALLET_BALANCE)` for an unrelated wallet token, and the recorded auth tree attaches that transfer as a child of Alice's `swap_collateral` entry (lines 194-227); Alice's full balance is stolen while the swap itself returns a fair output and all controller risk gates pass. The threat model documents the same exposure at `docs/explanation/threat-model.md:154-165` and pushes the defense to the client ("a client must decode the route it signs").

### Impact Explanation
Theft of user funds. A victim calling `swap_collateral` (or any strategy entrypoint that carries route bytes) with an attacker-constructed route — delivered through a compromised or malicious route source, which is realistic since route bytes are opaque XDR produced off-chain — loses arbitrary balances of arbitrary tokens held in their wallet, unbounded by `amount_in`, the payload minimum, or the controller's final health/collateral gates. The swap still settles correctly, so the victim sees a successful trade while other assets are drained.

### Likelihood Explanation
Any unprivileged address can submit such a route; the only precondition is that the victim signs the resulting auth tree, which normal Soroban transaction building does automatically because `simulateTransaction` records the rogue child transfer into the tree the wallet is asked to sign. Exploitation requires the victim to consume an attacker-supplied route (phishing frontend, malicious quoting service, copied route bytes) and not decode the authorization tree — a realistic path, but not fully unilateral, so High rather than Critical.

### Recommendation
Do not rely on clients to decode auth trees. Constrain the payload at the controller or router: maintain a governance-managed allowlist of permissible `pool` (and token) addresses per venue and reject hops targeting unlisted contracts, analogous to the existing Blend-pool approval list used by `migrate_from_blend`. Alternatively, have the router execute hops through a fresh intermediate contract address per hop so a rogue pool's `transfer` cannot attach to the end user's auth entry.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: the test registers an `UnlistedPoolRouter` double plus an attacker-deployed `RogueHopPool` whose `swap` performs `token.transfer(victim, attacker, amount)` on a token the protocol never listed. Alice calls `swap_collateral` with a route naming that pool; the simulation records the stolen `transfer(alice → attacker, 77_770_000_000)` inside Alice's `swap_collateral` auth entry, Alice's wallet balance goes to zero, and her ETH supply credit still increases by the fair swap output.
