### Title
Webhook shop/topic identity spoofing due to headers excluded from HMAC coverage - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw request body only, but then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. This breaks the identity binding `hmac-authenticated bytes == bytes used to identify the tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` and `request.topic` (from headers) to build `WebhookMetadata` and dispatch to the host application's handler: [3](#0-2) 

The equality this code implicitly assumes — `shop authenticated by HMAC == shop delivered to the handler` — does not hold. The HMAC only proves "this body was signed by Shopify with the app's secret at some point," not "this body belongs to this shop/topic." Any request whose body+HMAC pair was validly produced by Shopify (for *any* shop, *any* topic) can have its `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` headers rewritten arbitrarily while the HMAC check in `Utils::HmacValidator.validate` (which only inspects `to_signable_string`, i.e., the raw body) continues to pass: [4](#0-3) 

### Impact Explanation
Because tenant identity (`shop`) is not covered by the signature, an attacker who can supply the app's webhook endpoint with a genuinely-signed (body, HMAC) pair — for example a webhook that Shopify itself delivered for the attacker's own store, and which the attacker relays with a rewritten `shop-domain`/`topic` header — can make the host application believe an event happened on a different, victim, shop. Depending on how the host app's `WebhookHandler` uses `WebhookMetadata.shop`/`.topic` (e.g., mandatory `customers/redact`, `shop/redact`, `app/uninstalled` handling, data deletion, or de-provisioning logic keyed off `shop`), this enables cross-tenant state corruption or data loss without the attacker ever possessing the app's `client_secret` or another shop's access token — satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain at least one valid (raw body, HMAC) pair signed by the app's secret for some shop and deliver it (with modified headers) to the target app's public webhook endpoint. An attacker who legitimately installs the app on their own store (a normal, unprivileged merchant action) will receive/trigger real signed webhook deliveries for topics like `orders/create`, `app/uninstalled`, etc. Whether they can intercept/relay the exact bytes Shopify sends (since delivery goes Shopify → app server directly) is the main practical constraint; this typically requires the attacker to control an intermediary (e.g. their own webhook relay/proxy configured as the delivery target, which Shopify explicitly allows apps' merchants to redirect via custom app configuration in some setups) or replay logged webhook deliveries. This is plausible but not guaranteed in all deployments, so likelihood is assessed as moderate rather than trivial.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (all header-derived identity fields the handler relies on) in the HMAC-covered signable string, or otherwise cryptographically bind them to the signed body (e.g., by including a canonical representation of the headers being trusted). At minimum, document and encourage host apps to cross-check `request.shop` against session/tenant records they independently trust before acting on webhook data — but the safer fix is inside this gem: extend `to_signable_string` to incorporate the header values that `WebhookMetadata` exposes to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures/observes a webhook delivery for topic `customers/redact` (or any topic the app's handler treats specially), obtaining a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real secret.
2. Attacker sends this exact `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/redact`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds: [5](#0-4) 
4. The app's registered `WebhookHandler#handle` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the app to act (e.g., delete data, deactivate) on the victim's tenant instead of the attacker's own.
