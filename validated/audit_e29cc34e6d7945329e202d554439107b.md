### Title

Accrual overflow permanently freezes an oversized high-utilization market - (File: `contracts/pool/src/interest.rs`)

### Summary

Every pool mutation synchronizes interest before applying the requested operation. For a sufficiently large debt book, the debt valuation `borrowed * borrow_index` can exceed `i128::MAX` before `borrow_index` reaches its configured ceiling, causing accrual to revert with `MathOverflow`. Because the failed accrual occurs before withdrawal, repayment, liquidation, bad-debt cleanup, and recapitalization can proceed, the market becomes permanently unusable.

### Finding Description

`global_sync` advances each market in fixed-size accrual chunks and invokes `accrue_chunk` before marking the market synchronized. [1](#0-0)  `accrue_chunk` computes the next index state from the stored scaled debt, scaled supply, and current indexes, then commits those indexes and revenue shares. [2](#0-1) 

The accrual step values both the old and new debt with `borrowed.mul(..., index)`, where `borrowed` and the index are RAY-scaled `i128` values. [3](#0-2)  `Ray::mul` returns an `i128` fixed-point result, so a mathematically representable intermediate that exceeds the `i128` result domain cannot be stored. [4](#0-3) 

The protocol caps `borrow_index` at `10^36` raw RAY, equivalent to one billion times its initial value. [5](#0-4)  However, the cap is applied only after `old_index.mul(interest_factor)` produces a new `i128` index; it does not constrain the subsequent `borrowed * index` market valuation to fit in `i128`. [6](#0-5) 

An unprivileged caller can expose the condition through the controller’s normal `supply`, `borrow`, and `update_indexes` flows: supply a large admitted balance, borrow at sustained high utilization, allow interest to compound, and invoke `update_indexes` with the affected `HubAssetKey`. The pool’s owner-restricted `update_indexes` forwards directly to the same accrual path used by every market mutation. [7](#0-6)  The regression test demonstrates a one-billion-whole-token, 18-decimal market at 98% utilization reverting during `update_indexes`, after which both a one-unit withdrawal and repayment also revert with `MathOverflow`. [8](#0-7) 

### Impact Explanation

This permanently freezes all funds and debt operations for the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot restore account health, and bad-debt processing cannot run because those operations first execute the same accrual path. [1](#0-0)  Once the stored scaled debt and index are large enough for the next debt valuation to overflow, ordinary state transitions cannot advance past synchronization, leaving user deposits and outstanding debt permanently locked absent a privileged code upgrade. [9](#0-8) 

### Likelihood Explanation

The trigger requires an unusually large market and sustained high utilization over an extended accrual period, so it is not reachable with ordinary small balances. [10](#0-9)  The issue is still attacker-reachable when an admitted market configuration permits balances near the protocol’s numeric maximum: users only need to perform normal supply and borrow actions, wait for accrual, and call `update_indexes`; no privileged action is required after market configuration. [11](#0-10)  The severity is therefore Medium: the impact is permanent freezing of market funds, but exploitation depends on extreme admitted scale and time-based interest growth.

### Recommendation

Do not allow accrual arithmetic to reach an unrepresentable debt or supply valuation. Enforce market-level scaled-balance caps derived from `i128::MAX`, `RAY`, token decimals, and the applicable index ceiling, or dynamically clamp the index to `floor(i128::MAX * RAY / scaled_balance)` before evaluating `borrowed * index` and `supplied * index`. Apply equivalent bounds to both debt valuation and supplied-value updates, since `update_supply_index`, `supply_index_reward_shortfall`, and bad-debt socialization also multiply scaled balances by indexes. [12](#0-11)  Add a regression that verifies `update_indexes`, `withdraw`, `repay`, liquidation, and recapitalization remain executable at the configured numeric boundary rather than reverting inside accrual. [11](#0-10) 

### Proof of Concept

1. Configure or use an admitted 18-decimal market with a steep interest-rate curve, a one-dollar price, and caps near `max_cap_for_decimals(18)`.
2. Call controller `supply` for approximately `1_000_000_000 * 10^18` base units of the debt asset.
3. Supply sufficient collateral through controller `supply`, then call controller `borrow` for approximately 98% of the supplied debt asset.
4. Allow the market to remain near that utilization while ledger time advances.
5. Repeatedly call controller `update_indexes` with `hub_assets = [HubAssetKey { hub_id, asset }]` for the debt market.
6. Accrual eventually attempts to evaluate scaled debt at an index whose resulting RAY valuation exceeds `i128::MAX`, and the call fails with `MathOverflow`.
7. Subsequent controller `withdraw`, `repay`, liquidation, and `update_indexes` calls fail before their business logic because each reaches `global_sync` first.

The repository’s regression executes the same sequence: it supplies `1e27` base units, borrows 98%, advances time until `update_indexes` fails, verifies the borrow index remains below `MAX_BORROW_INDEX_RAY`, and confirms that both withdrawal and repayment continue reverting. [8](#0-7)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
