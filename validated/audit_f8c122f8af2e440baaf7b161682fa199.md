## Title
Webhook `shop-domain` (and topic/webhook-id/api-version) headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-signed payload. `Utils::HmacValidator.validate` only checks that the body matches its HMAC; it never binds that signature to the shop the webhook claims to be for. As a result, the tenant identity (`shop`) that `Registry.process` hands to the application's webhook handler is attacker-controlled and unauthenticated, even though the request passes HMAC validation.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from attacker-supplied HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string` and compares it to the supplied HMAC using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` and dispatch to the app's handler, immediately after the HMAC check succeeds: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Because the HMAC only proves "this body was HMAC'd with the app's secret at some point for some shop," and not "this specific shop-domain header is the one Shopify sent this body for," the two sides of that equality diverge. Any party who can obtain one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` — trivially available to any merchant who installs the app and receives genuine webhook deliveries to their own endpoint — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (and `topic`/`webhook-id`/`api-version` headers). `Utils::HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` will invoke the handler with `shop: "victim-shop.myshopify.com"` for data that was never sent by Shopify for that shop.

### Impact Explanation
This is a cross-tenant access vulnerability: a webhook event can be attributed to (and acted upon by the host application for) a shop other than the one for which Shopify actually generated it. Depending on how the host application's webhook handlers key data (session lookups, uninstall/deprovisioning, GDPR redaction, order/customer state changes) by `WebhookMetadata#shop`, this allows an attacker who merely operates their own install of the app to trigger tenant-scoped side effects against a victim merchant's data/session — exactly the class of cross-tenant impact called out as Critical.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that registers webhooks: the attacker only needs to be able to install the app themselves (an ordinary, unprivileged action for any Shopify merchant) and observe one legitimate webhook delivery to their own endpoint, then POST a modified request (same body/HMAC, different `shop-domain` header) directly to the app's public webhook URL. No secret key, access token, or privileged access to the victim's store is required.

### Recommendation
Include the header fields the application relies on for tenant/topic identity (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload, or otherwise cryptographically bind them — e.g. by having `to_signable_string` concatenate these headers with the raw body before hashing, matching the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` in the signed string: [5](#0-4) 

Alternatively, document clearly that `Request#shop` is unauthenticated and require host applications to cross-check it against the shop for which the webhook was registered before acting on it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a genuine webhook (e.g. `app/uninstalled`), capturing the raw JSON body `B` and the corresponding `X-Shopify-Hmac-Sha256: H` header sent by Shopify (both are valid because HMAC is computed only over `B` with the app's shared `api_secret_key`, per `Request#to_signable_string`/`HmacValidator.validate_signature`).
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally an arbitrary `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `@raw_body` (`request.rb` lines 35-38, `hmac_validator.rb` lines 26-31) — identical to step 1.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` and invokes the registered handler as if Shopify had genuinely sent this event for `victim.myshopify.com` (`registry.rb` lines 188-200), even though Shopify never issued this webhook for that shop.
