### Title
Cross-chain signature replay in `pallet-hyper-fungible-token`'s GMP calldata authorization due to missing chain binding - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler authorizes an attached `runtime_call` using a `MultiSignature` computed over `(account_nonce, runtime_call)` only. Nothing in the signed payload binds the authorization to the destination chain (no genesis hash, no `StateMachine` id, no pallet/contract address). Because this pallet is a generic module deployed under the identical fixed `PALLET_ID = b"pall_hft"` on any number of independent substrate chains bridging to the same EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, the exact same signed cross-chain message can be dispatched to multiple destination chains, and the signature will validate identically on each as long as the beneficiary account's local nonce matches (trivially true for a fresh account, which starts at nonce 0 on every chain).

In `on_accept`, when incoming `message.data` carries a signed `SubstrateCalldata`, the pallet builds the signed payload as: [1](#0-0) 

and verifies Ed25519/Sr25519/ECDSA signatures against that payload alone: [2](#0-1) [3](#0-2) 

No chain-specific value — not `source`/`dest` `StateMachine`, not a genesis hash, not the pallet's own address — is folded into `msg`. The only replay protection is `frame_system::account_nonce(beneficiary)`, which is strictly local to a single chain: [4](#0-3) 

This pallet is explicitly designed to be instantiated by many independent runtimes under one hardcoded module id, and the docs confirm the calldata authorization is only over `(account_nonce, runtime_call)`: [5](#0-4) [6](#0-5) 

Since the EVM-side `HyperFungibleToken` contract registers this pallet's fixed module id as a trusted peer per destination `StateMachine`, and the sending user fully controls the `data`/calldata payload sent in `Message.data`, a user (or anyone able to trigger a `send` on the EVM contract, i.e. an unprivileged message dispatcher) can produce the identical `Message` body (same `runtime_call`, same signature) and dispatch it as two separate ISMP `PostRequest`s toward two different destination chains that both run this pallet with the same `PALLET_ID`. Both requests are independently valid ISMP-delivered messages (each with its own consensus/state proof for its own destination), so both reach `on_accept` on their respective chains. On each chain, `account_nonce(beneficiary)` for a freshly-bridged account is 0, so the identical signature over `(0, runtime_call)` verifies successfully on both chains, causing the same authorized dispatch to execute twice — once per chain — under one signature that the user only intended to authorize once (or for one destination).

### Impact Explanation
This is an unauthorized app action / forged authorization: a single off-chain signature intended to authorize a specific runtime call on one destination chain gets replayed and dispatched with full authority as `RawOrigin::Signed(beneficiary)` on other chains hosting this pallet. Depending on what `runtime_call` is filtered/allowed by `BaseCallFilter`, this can duplicate transfers, staking/governance actions, or any dispatchable reachable from a signed origin — all without a fresh signature from the user for that specific chain. This falls squarely in the "unauthorized app action" category called out as acceptable impact.

### Likelihood Explanation
Likelihood is high in the natural deployment model described by this pallet's own documentation: it is meant to be reused verbatim (same `PALLET_ID`) across many substrate chains, each bridging the same EVM token contract. New/first-time users bridging in have `account_nonce == 0` on every new chain they interact with, which is the common case, making nonce-collision-based replay trivial without any special conditions.

### Recommendation
Include a chain-specific/domain value in the signed payload before hashing, e.g. `(genesis_hash_or_local_StateMachine_id, account_nonce, runtime_call)`, so a signature produced for one chain's calldata execution cannot verify on another chain (or another pallet instance) running the same `PALLET_ID`. This mirrors adding `chainId` to the EIP-712/permit domain in the referenced report.

### Proof of Concept
1. Deploy `pallet-hyper-fungible-token` (same `PALLET_ID = b"pall_hft"`) on Chain A and Chain B, both registered as peers of the same EVM `HyperFungibleToken` contract for token X.
2. A user with EVM key `K` bridges token X for the first time to Chain A, attaching `SubstrateCalldata { signature: Some(sig), runtime_call: call }` where `sig` is an ECDSA signature over `keccak256(prefix || (0u32, call).encode())` (nonce 0, since the derived substrate account is new on Chain A).
3. The user (or anyone relaying/crafting the same EVM transaction data) also triggers the equivalent `send` targeting Chain B with the identical `Message.data` (same signature, same `runtime_call`).
4. On Chain B, the beneficiary's derived account is also new (`account_nonce == 0`), so `on_accept` in `module.rs` recomputes the same `msg` and the same signature verifies, dispatching `call` a second time on Chain B under `RawOrigin::Signed(beneficiary)` — authorized by a signature the user only produced once.

The `call_data` field in `SendParams` allows executing arbitrary runtime calls on the destination substrate chain after the tokens are transferred. The calldata is SCALE-encoded as:

```rust lineNumbers
pub struct SubstrateCalldata {
    /// Optional SCALE-encoded MultiSignature of (account_nonce, runtime_call)
    pub signature: Option<Vec<u8>>,
    /// SCALE-encoded runtime call to execute
    pub runtime_call: Vec<u8>,
}
```

If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch. Supported signature types: Ed25519, Sr25519, ECDSA. The account nonce is incremented after dispatch to prevent replay.

If no signature is provided, the origin is derived from the sender address in the cross-chain message.
