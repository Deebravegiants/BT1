### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the HMAC over the raw request body, but the `shop` value that is handed to the app's `WebhookHandler` is read from an HTTP header that is excluded from that signature. This breaks the intended binding "HMAC-verified bytes == data trusted for tenant identification," letting an attacker who can reach the app's webhook endpoint with any HMAC-valid payload (e.g. one legitimately produced for a shop under their own control) relabel it as belonging to an arbitrary victim shop domain.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the registered handler as part of `WebhookMetadata`, without any additional verification that the header matches the shop the payload actually originated from: [4](#0-3) 

`WebhookMetadata` and the gem's own documentation present `shop` as a trustworthy, verified field for host applications to key their tenant data on: [5](#0-4) 

The broken identity binding is:
`HMAC(raw_body, api_secret_key) valid` ⇏ `shop header == shop that produced raw_body`

Since only `raw_body` is authenticated, `shop` is an unauthenticated, attacker-controlled field riding alongside an otherwise-valid signature.

### Impact Explanation
An unprivileged internet user who has access to any legitimately-signed webhook body/HMAC pair (trivial to obtain: install the same app on a shop they control, e.g. a free Shopify dev/partner store, and capture the webhook Shopify sends them) can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header with any victim `*.myshopify.com` value of their choosing. `Utils::HmacValidator.validate` will accept it because the signature only covers the body, and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` and attacker-chosen `body`/`topic`. If the host application uses `data.shop` (as the documentation explicitly instructs) to scope database writes, trigger business logic, or attribute events (e.g. `orders/create`, `app/uninstalled`, `shop/redact`), this results in cross-tenant data injection/manipulation — a merchant's data plane can be poisoned or its events forged by any user, without a session, an access token, or knowledge of the app's `api_secret_key`. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: no secret material is required, the webhook processing endpoint is by design internet-reachable and unauthenticated apart from the HMAC, and obtaining a valid `(body, hmac)` pair is as easy as registering the app on any shop (including the attacker's own free dev store) and capturing one webhook delivery. The only engineering effort is resending the HTTP request with a modified header, which any HTTP client can do.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the header values to the payload before trusting them. At minimum, `Request#to_signable_string` should incorporate the shop-domain header value so that `HmacValidator.validate` fails if it has been altered relative to what Shopify actually signed. Until fixed, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be used as a tenant-identifying key.

### Proof of Concept
1. Register the target app on an attacker-owned shop `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid for that exact body under the app's real `api_secret_key`.
2. Replay the captured request to the app's public webhook endpoint, keeping `raw_body` and the `hmac` header unchanged, but replacing the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the tampered header into `shop`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `raw_body` (`to_signable_string`) and succeeds: [6](#0-5) 
4. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, even though that shop never sent this webhook — demonstrating the cross-tenant identity-binding break.
