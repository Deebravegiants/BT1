Webhook `shop-domain` header not covered by HMAC allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value passed to the app's handler is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the HMAC-signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC of the request and, if it passes, dispatches to the handler using `request.shop`, which is read straight from the (unsigned) header: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`; it never binds the `shop` header into the signed bytes: [4](#0-3) 

The resulting `WebhookMetadata.shop` field, which host applications use as the tenant identifier to route/attribute webhook data, is taken from this unauthenticated header: [5](#0-4) 

This is the same class of bug as the Wildcat report: a field that is *acted upon* (here, `shop`, used as the tenant/session key) is not covered by the same cryptographic binding that authenticates the rest of the payload (the HMAC only covers `raw_body`). The equality that should hold — "the shop asserted to the handler equals the shop whose secret authenticated the request" (`request.shop == shop_that_produced_the_valid_hmac`) — does not hold, because the HMAC does not commit to any shop at all; it commits only to the body bytes and is verified globally against the app's single `api_secret_key` (which is shared across all shops using this app, not shop-specific).

### Impact Explanation
Since one `api_secret_key` is shared by the app across all its installed shops, and the HMAC never binds to a specific shop, an attacker who controls (or has previously captured) one valid `(body, hmac)` pair for their own shop can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop domain. `HmacValidator.validate` will still succeed (it only checks the body signature against the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain. Any host application that uses `data.shop` to select the tenant record, session, or access token to act on (a very common and expected pattern, since `shop` is the only tenant field on `WebhookMetadata`) will now process attacker-controlled webhook data under a different tenant's identity — i.e., cross-tenant data injection through a boundary this gem itself models and offers as its verified webhook API.

### Likelihood Explanation
The gem's own README/API design deliberately provides `WebhookMetadata.shop` for host apps to use as the trusted tenant identifier post-`process`, so the exploitation path only requires an unprivileged internet user capable of sending HTTP requests to the app's public webhook endpoint (webhook endpoints are, by design, public and only protected by the HMAC). No access token, TLS interception, or privileged account is required — only one legitimately-signed body/HMAC pair (from any shop the attacker controls, including their own trial/dev store) plus the ability to alter the header on their forged replay request. This is entirely within scope of the gem's own trust boundary (webhook authenticity), not a misuse of the host app's separate business logic.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) as part of the HMAC-signed data, or otherwise cryptographically bind the shop to the signature verification (e.g., verify the HMAC per-shop using knowledge already established during OAuth/installation) rather than trusting the `shopify-shop-domain` header verbatim once the body-only HMAC passes.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this `(B, HMAC)` pair (they own this shop, so they can simply trigger/observe the webhook themselves).
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches — validation succeeds because `to_signable_string` never included the shop header: [1](#0-0) [6](#0-5) 
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the body/HMAC actually originated from the attacker's own shop: [7](#0-6) 
6. Any host app logic keyed on `data.shop` (e.g., "find session/tenant for this shop and act on their data with attacker-controlled body") now cross-contaminates the victim tenant with attacker-supplied webhook data.
