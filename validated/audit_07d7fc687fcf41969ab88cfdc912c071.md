### Title
Webhook shop identity spoofing via unsigned headers — `HMAC` signs only the body, letting an attacker impersonate any shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook purely by validating the HMAC of the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never covered by that HMAC. Because the app's `api_secret_key` is shared across every merchant that installs the app, any unprivileged user who has installed the app on their own store can capture one of their own legitimately-signed webhook deliveries and replay it to the app's public webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`) header swapped to another merchant's shop domain. The HMAC still validates (it only checks the body bytes), and the handler executes believing the event belongs to the victim shop — a tenant-identity break with no application secret or credential required.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read straight from attacker-controllable HTTP headers, independent of the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which delegates to `to_signable_string`, i.e. body-only), then constructs `WebhookMetadata` directly from the unauthenticated header fields and dispatches it to the host app's handler: [4](#0-3) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the received signature — again, only the body is included for `Request`: [5](#0-4) 

The documented contract confirms host apps are expected to trust `data.shop` as the tenant identifier coming out of `Registry.process`: [6](#0-5) [7](#0-6) 

**Broken equality**: the gem treats "HMAC(secret, raw_body) is valid" as proof that "`shop-domain` header == the shop this event is about." Those are not the same claim — the secret is shared across every tenant of the app, and the header is never part of the signed material, so knowledge of one valid (body, HMAC) pair from *any* shop (including the attacker's own installation) is sufficient to forge the tenant binding for *any other* shop.

### Impact Explanation
Any user who can install the app on their own store (a normal, unprivileged action for a public/multi-tenant Shopify app) can:
1. Trigger a real webhook delivery to their own store (e.g. `orders/create`), capturing the exact raw body and its valid `x-shopify-hmac-sha256`.
2. Replay that same body/HMAC pair to the app's public webhook endpoint, but with `x-shopify-shop-domain` (and, if needed, `x-shopify-topic`/`x-shopify-webhook-id`) rewritten to a victim shop's domain.
3. The gem's `Registry.process` accepts this as authentic (HMAC only checks body bytes) and hands the handler `WebhookMetadata` claiming the event is `data.shop == "victim-shop.myshopify.com"`.

Any host application logic keyed on `data.shop` (looking up the victim's session/access token, writing/updating tenant-scoped records, deduplicating by `webhook_id`, gating by `topic`) is now driven by attacker-controlled data injected under a different tenant's identity — a cross-tenant access/data-integrity break, matching the "cross-tenant access" Critical impact category, achieved with no access token, no `client_secret`, and no privileged account.

### Likelihood Explanation
High: exploitation only requires the attacker to be a legitimate installer of the target app (a normal, unprivileged capability for any public app) and the ability to send an arbitrary HTTP POST with custom headers to the app's known public webhook URL — both trivially available to any internet user who installs the app.

### Recommendation
Do not trust header-derived identity fields (`shop`, `topic`, `webhook_id`) unless they are cryptographically bound to the signed payload. Options:
- Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed material (`to_signable_string`) so any tampering invalidates the signature, or
- Cross-check the header-derived `shop` against the shop embedded in the JSON body (when present) before dispatching to the handler, or
- Document/require callers to independently verify that the `shop` returned in `WebhookMetadata` matches a shop with an active, expected subscription for that specific `webhook_id`/`topic` combination (e.g., via the Shopify webhook ID registered per-shop) rather than trusting the header value as-is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers `orders/create` (or any subscribed topic), capturing the POST body `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>` sent to the app's webhook endpoint.
2. Attacker resends the identical request to the same endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - keeps `raw_body` and `x-shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` is still valid because `to_signable_string` only returns `raw_body`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` passes `Utils::HmacValidator.validate(request)` and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: <attacker's own order data>, ...)`.
5. The host application processes attacker-controlled order data as if it belonged to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
