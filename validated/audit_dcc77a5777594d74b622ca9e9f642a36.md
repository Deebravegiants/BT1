### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` is read from the separate, unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header. `Registry.process` validates the HMAC over the body alone and then trusts `request.shop` to attribute the webhook to a specific merchant. Because the shop identity is never part of the signed data, an attacker who possesses one valid `(body, hmac)` pair for the shared app secret can replay it with an arbitrary `shop-domain` header value and have it accepted as an authentic webhook for a different shop.

### Finding Description
The HMAC verification flow is:
- `HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field [1](#0-0) .
- For webhooks, `to_signable_string` returns only `@raw_body`, never the shop header [2](#0-1) .
- `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material [3](#0-2) .
- `Registry.process` validates only the HMAC (over the body) and then uses `request.shop` to build the `WebhookMetadata` handed to the app's handler [4](#0-3) .

Because a single app's webhook HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, a merchant (an "unprivileged internet user" from the perspective of other tenants of the same app) legitimately receives their own webhooks with valid `(body, hmac)` pairs signed with that shared secret. Since the header carrying the `shop` value is not included in `to_signable_string`, that same `(body, hmac)` pair remains valid no matter what `shop-domain` header is sent alongside it. This breaks the intended identity binding:

`shop authenticated by HMAC == shop attributed to the webhook event`

Before request: the pair `(body, hmac)` is bound only to "some shop using this app's secret." After an attacker's crafted replay with a substituted `shopify-shop-domain` header, `Registry.process` accepts the same valid HMAC and hands the handler a `WebhookMetadata` claiming the event originated from an arbitrary victim shop, even though the shop identity was never authenticated.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who is a legitimate (but malicious) merchant of a multi-tenant app can forge webhook deliveries "from" any other shop that uses the same app, because the shop identity is not cryptographically bound to the HMAC. Depending on how the host application uses webhook data (e.g., `app/uninstalled`, `shop/update`, `orders/create`), this can drive data poisoning or state corruption attributed to a victim tenant — a cross-tenant access/integrity violation within the meaning of "cross-tenant access."

### Likelihood Explanation
Any shop that has installed the app can capture at least one genuine `(body, hmac)` pair from webhooks legitimately delivered to their own endpoint, since the secret is shared across the whole app's install base. Forging the header and replaying the request requires no privileged credentials, access tokens, or knowledge of `api_secret_key` — only network access to the app's public webhook endpoint, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the signed material used for webhook verification — e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the string that is HMAC-verified, or otherwise cryptographically bind them to the body before calling `HmacValidator.validate`, so a signature computed for one shop's payload cannot be replayed while claiming a different shop origin.

### Proof of Concept
1. As a merchant who has installed the target app, capture a real webhook delivery, e.g. `raw_body = '{"id":1}'`, `hmac-sha256 header = H` (valid for the app's shared secret), `shopify-shop-domain: my-shop.myshopify.com`.
2. Replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only [2](#0-1)  and it matches `H`, so `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , even though the request never actually originated from that shop.
