The `ShopifyAPI::Webhooks::Request#hmac` verification only covers the raw HTTP body via `to_signable_string` returning `@raw_body`, while `request.shop` (the `shopify-shop-domain` / `x-shopify-shop-domain` header) is never included in the signed material.### Title
Webhook `shop` domain is trusted by the gem and delivered to handlers without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes its HMAC only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` value (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read separately and passed straight through to the app's webhook handler by `ShopifyAPI::Webhooks::Registry.process`, with no cryptographic binding between the two.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop` accessor, however, is read directly from an HTTP header that is not part of the signed material at all [3](#0-2) .

`Registry.process` validates the HMAC (over the body only) and then constructs `WebhookMetadata` using `request.shop` taken straight from that unauthenticated header, handing it to the app's handler as the trusted tenant identifier: [4](#0-3) .

The gem's own documentation instructs developers to use `data.shop` from the handler as the shop identity for downstream actions (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that `shop` is meant to be treated as an authenticated identifier of the originating tenant: [5](#0-4) .

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_header_used_by_handler == shop_that_actually_produced_and_signed(raw_body)`

Because the HMAC secret (`api_secret_key`) is shared across all shops that install the app (it is not shop-specific), an attacker who legitimately controls one shop with the app installed can obtain a genuinely Shopify-signed `(raw_body, hmac)` pair for their own webhook deliveries. Since the `shop-domain` header is not part of the signed content, that attacker can replay the same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header value. `HmacValidator.validate` will still return `true` (the body/HMAC pair is valid), and `Registry.process` will invoke the handler with `data.shop` set to the attacker-chosen victim shop domain instead of the real originating shop.

### Impact Explanation
This breaks the tenant identity boundary that `Registry.process`/`WebhookMetadata` is meant to provide to consuming applications: `data.shop` is documented and used by host apps to route/attribute webhook data to a specific merchant tenant (e.g., for storage keys, job scoping, per-shop side effects such as data deletion for `shop/redact`/`customers/redact`, or updates keyed by shop domain). An attacker can cause a webhook payload they control (from their own shop) to be attributed to a victim shop of their choosing, since the shop header carries no HMAC protection. Depending on how a host app uses `data.shop` (which the docs explicitly recommend using as a tenant key), this can lead to cross-tenant data corruption/injection — for example, forging a `customers/redact` or `shop/redact` webhook that appears to originate from an arbitrary victim shop, or injecting attacker-controlled `body` content attributed to a victim shop's job queue.

### Likelihood Explanation
Exploitability requires only that the attacker control one shop where the app is installed (a completely unprivileged/normal merchant relationship, not a privileged account) and be able to send an HTTP POST directly to the app's public webhook endpoint with a captured, genuinely-signed `(raw_body, hmac)` pair and an arbitrary `shop-domain` header — no `client_secret`, access token, or TLS interception required. This matches the rule's explicitly listed analog: "a field acted on but not covered by the HMAC."

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version/webhook-id) as part of the HMAC-covered signable content, or otherwise cryptographically bind `shop` to the verified body (e.g., derive/verify shop identity via a mechanism outside the replayable header, or require host apps to cross-check `data.shop` against the shop that owns the specific `webhook_id`/subscription before trusting it for tenant-scoped operations). At minimum, update `ShopifyAPI::Webhooks::Request#to_signable_string` to incorporate the shop header into the signed string so a mismatched/forged `shop-domain` header invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`), which is a normal unprivileged flow.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays this exact request to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` while keeping body `B` and the same HMAC header unchanged.
4. `HmacValidator.validate` computes `HMAC(secret, B)` (from `Request#to_signable_string`, which only returns `@raw_body` [1](#0-0) ) and compares it to the received value — this still matches, since `shop-domain` isn't part of the signed content.
5. `Registry.process` calls the app's handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"` even though the body actually originated from the attacker's own shop [4](#0-3) .
6. Any host-app logic that trusts `data.shop` as the tenant key (as the gem's own docs recommend [5](#0-4) ) now processes attacker-controlled data under the victim shop's identity.
