### Title
`createWithdrawalIntents` builds a withdrawal on an under-checked `feeInclusive` amount, allowing the required fee-vs-amount guard to be bypassed - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = amount - feeEstimation.amount` for fee-inclusive withdrawals, then calls `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents` with that value, but never checks that `feeEstimation.amount < amount`. That guard exists in the sibling method `_estimateWithdrawalFee`, but is missing on this path, mirroring the reported bug class: a required equality/guard check present in sibling functions is silently skipped in one code path, letting a stale/attacker-supplied value flow unchecked into fund-moving logic.

### Finding Description
`_estimateWithdrawalFee` explicitly guards against a fee that meets or exceeds the withdrawal amount before computing `actualAmount`: [1](#0-0) 

`createWithdrawalIntents`, the public API also invoked from `processWithdrawal` when a caller supplies its own `feeEstimation` (skipping `estimateWithdrawalFee` entirely), performs the identical subtraction but without that check: [2](#0-1) [3](#0-2) 

Because `amount` and `feeEstimation.amount` are `bigint`, `amount - feeEstimation.amount` silently yields `0n` or a negative value instead of throwing `FeeExceedsAmountError` when the fee estimate is stale/large (e.g., an old quote reused, or a fee estimation obtained for a different amount/route and passed straight to `processWithdrawal`/`createWithdrawalIntents`). This negative/zero `actualAmount` is then forwarded into `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`, which build the on-chain intents (e.g., `ft_withdraw`/`mt_withdraw` amount, `token_diff` diff) from this unguarded value.

### Impact Explanation
This breaks the equality "amount actually withdrawn = requested amount minus the fee that was actually charged, and never less than a validated positive value." Depending on downstream bridge behavior, a caller (or a client library that caches/reuses `feeEstimation`) can end up requesting a withdrawal with an amount of `0` or negative, producing either a malformed/rejected transaction or, in bridges that add fee back into gross amount (e.g. HOT bridge, `amount = withdrawalParams.amount + feeAmount`), an incorrectly computed on-chain transfer amount. This is a fee/amount overcharge or accounting-drift class of issue on the amount actually placed into signed intents, matching "fee overcharge" impact criteria.

### Likelihood Explanation
Likelihood is moderate: it requires a caller to invoke `createWithdrawalIntents`/`processWithdrawal` with a pre-existing `feeEstimation` (which the SDK explicitly supports as an optimization/orchestration path) that is stale or larger than the withdrawal amount — a realistic scenario for integrators caching quotes or retrying withdrawals with an old fee estimation after the amount was reduced.

### Recommendation
Add the same `FeeExceedsAmountError` guard used in `_estimateWithdrawalFee` to `createWithdrawalIntents` before computing `actualAmount`, so any caller-supplied `feeEstimation` is validated the same way regardless of entry point:
```ts
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
  throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```

### Proof of Concept
1. Call `sdk.estimateWithdrawalFee({ withdrawalParams: { amount: 1000n, ... } })` to get a `feeEstimation` with `amount: 900n`.
2. Later call `sdk.createWithdrawalIntents({ withdrawalParams: { amount: 800n, feeInclusive: true, ... }, feeEstimation })` (or via `processWithdrawal` passing the stale `feeEstimation`), reusing the earlier fee estimation for a smaller amount.
3. `actualAmount = 800n - 900n = -100n` is computed with no error thrown, unlike the guarded path in `_estimateWithdrawalFee`, and is passed to `bridge.validateWithdrawal`/`bridge.createWithdrawalIntents`.
