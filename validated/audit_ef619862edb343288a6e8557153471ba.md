### Title
Missing relayer allowlist check in Tron `IntentGatewayV2.onAccept` allows any relayer to forge escrow settlement delivery - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the same escrow settlement flow as the canonical EVM `ExtrinsicIntents.sol`, but its `onAccept` and `onGetResponse` callbacks omit the `_checkRelayer(incoming.relayer)` gate that the canonical implementation enforces before processing `RedeemEscrow`/`RefundEscrow` withdrawals.

### Finding Description
In the canonical implementation `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `onAccept` calls `_checkRelayer(incoming.relayer)` as the very first line before decoding any request kind, and `onGetResponse` does the same: [1](#0-0) [2](#0-1) 

This gate exists because `IHandlerV2.handlePostRequests`/`handleGetResponses` forward `_msgSender()` as the `relayer` argument on every delivery, and `EvmHost.dispatchIncoming` passes that value straight through to the app's callback — so the relayer identity in `IncomingPostRequest`/`IncomingGetResponse` is only as trustworthy as the handler that is currently installed, and the gateway's `_checkRelayer` is the contract-level defense that restricts *who* may successfully finalize an escrow release/refund: [3](#0-2) 

The Tron port's `onAccept`, however, decodes the `RequestKind` and calls `authenticate`/`withdraw` for `RedeemEscrow`/`RefundEscrow` with no relayer check at all — only the standard `onlyHost` modifier is present: [4](#0-3) 

and its `onGetResponse` likewise withdraws escrow on any empty-proof response without a relayer check: [5](#0-4) 

`withdraw` itself performs no additional relayer authorization — it just finalizes `_filled[commitment]` and transfers tokens to whatever `beneficiary` is encoded in the (attacker-controlled at delivery time) `WithdrawalRequest`: [6](#0-5) 

Note: I could not find a `_relayer` state variable or `_checkRelayer` function definition anywhere in this Tron file (only 7 matches for `relayer|_checkRelayer|onlyHost`, all accounted for by `onlyHost` and `options.relayerFee`/`relayerFee` fields), which is consistent with the gate having been dropped entirely rather than just miscalled elsewhere.

### Impact Explanation
This is directly analogous to the Titra CVE's improper access control: a resource (here, escrow release/refund authority) that is supposed to be gated to a specific authorized principal (the allow-listed relayer) is instead reachable by any principal that can get a message through the host's `onlyHost` boundary. Since `EvmHost.dispatchIncoming` is `restricted to handler` but the handler forwards `msg.sender` unconditionally as the "relayer" for *every* deliverer, any address can call `HandlerV2.handlePostRequests`/`handleGetResponses` permissionlessly and become the reported "relayer" for that delivery. Without the `_checkRelayer` gate, the Tron gateway accepts a `RedeemEscrow`/`RefundEscrow` settlement or a GET-response-based cancellation refund delivered by *any* relayer, not just the one Hyperbridge governance designated. Combined with the fact that `authenticate`/message validity ultimately rests on the correctness of the state/consensus proof pipeline, this removes an intended defense-in-depth layer that the rest of the codebase (BridgeToken, ExtrinsicIntents, HostManager) treats as security-critical against a forged-handler or compromised-proof-pipeline scenario. In the worst case this permits unauthorized parties to trigger escrow disbursement (fund transfer to an attacker-chosen beneficiary) outside the sanctioned relayer allowlist.

### Likelihood Explanation
Under normal operation with an honest handler and correct consensus/state proofs, this gap only matters if the relayer-gate was intended as a genuine second line of defense (as documented for the sibling EVM contract) — which the existing test suite and flow docs indicate it is. Any deployment of this Tron contract is missing that defense entirely, so exploitation requires either a compromised/forged handler, a bug in state-proof verification, or reliance on the assumption that "any relayer may deliver, but only the allow-listed one may finalize a withdrawal" — an assumption that holds for every other app in this repo but not for this file. Given Tron is called out as a distinct deployment target (separate `evm/tron/contracts` tree), this is a live production surface, not dead code.

### Recommendation
Add the same `_checkRelayer(incoming.relayer)` (or equivalent allowlist) call to `IntentGatewayV2.onAccept` for the `RedeemEscrow`/`RefundEscrow` branch and to `onGetResponse` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `evm/src/apps/intentsv2/ExtrinsicIntents.sol`. Introduce the `_relayer`/`relayer()`/`setRelayer()` state and setter if it does not exist in this file's inheritance chain, and add regression tests analogous to `testOnAcceptGovernanceRejectsUnlistedRelayer` / `testOnGetResponseRejectsUnlistedRelayer` in `evm/tests/foundry/IntentGatewayV2Test.sol`.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` and place a cross-chain order, escrowing input tokens.
2. On the destination chain, have the legitimate solver fill the order (or, for the refund path, simulate the GET-response flow), producing a `RedeemEscrow`/`RefundEscrow` `PostRequest` or a `GetResponse` with an empty `_filled` slot addressed to this gateway.
3. Have *any* address (not the intended relayer) call the ISMP handler's `handlePostRequests`/`handleGetResponses` with a valid proof for that message; the handler forwards `msg.sender` as `relayer` to `EvmHost.dispatchIncoming`, which calls `IntentGatewayV2.onAccept`/`onGetResponse`.
4. Observe that `onAccept`/`onGetResponse` proceeds to `withdraw()` and transfers escrow to the `beneficiary` encoded in the message, with no check that the delivering relayer matches an authorized allowlist — unlike the equivalent call path in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, which reverts with `Unauthorized` when `_checkRelayer` fails (see `testOnGetResponseRejectsUnlistedRelayer` in `evm/tests/foundry/IntentGatewayV2Test.sol` for the expected-but-missing behavior on this contract).

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
