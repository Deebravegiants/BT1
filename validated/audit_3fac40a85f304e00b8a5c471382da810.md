### Title
Native-fee dispatch permanently reverts when the host's configured Uniswap wrapper fee tier lacks liquidity for WETH/feeToken - (File: evm/src/core/EvmHost.sol, evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol, evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all route native-token payments through a single, immutably configured `_hostParams.uniswapV2` address via `swapETHForExactTokens`. On chains where the "V2 router" is actually one of the V3/V4 compatibility wrappers, that wrapper hardcodes a single fee tier (`_params.maxFee` in `UniV3UniswapV2Wrapper`, `_params.defaultFee`/`defaultTickSpacing` in `UniV4UniswapV2Wrapper`) for the WETH↔feeToken pool used in every swap. This is the same bug class as the referenced report: relying on one fixed fee tier for pricing/routing, which reverts or mis-prices when that specific pool lacks liquidity or ceases to be the dominant venue.

### Finding Description
`EvmHost.dispatch` swaps `msg.value` for the exact `post.fee`/`get.fee` amount of `feeToken()` via a hardcoded `_hostParams.uniswapV2` router: [1](#0-0) 

The same pattern repeats in `dispatch(DispatchGet)` and `fundRequest`: [2](#0-1) [3](#0-2) 

On chains without a native Uniswap V2 pool for the fee token, the host is configured with a wrapper contract that implements the `IUniswapV2Router02` interface but internally routes through Uniswap V3/V4 using one hardcoded fee tier. For V4: [4](#0-3) [5](#0-4) 

Every ETH→feeToken swap the host performs uses this single `_createPoolKey`-derived pool, with `fee = _params.defaultFee` and `tickSpacing = _params.defaultTickSpacing` fixed at `init()`-time (immutable thereafter — there is no `defaultFee`/`defaultTickSpacing` update path). The equivalent V3 wrapper hardcodes a single `_params.maxFee`: [6](#0-5) 

This mirrors exactly the reported bug class: a protocol-critical swap/pricing path is pinned to one specific fee tier, with no fallback to alternate tiers and no owner-updatable mapping. If liquidity migrates away from that configured tier (a common, expected market dynamic — e.g., liquidity moving from 0.05% to 0.01% or 0.3% as noted in the original report), or if the pool was never deep for that pair, the underlying V3/V4 swap silently fails to fill the exact-output amount and reverts.

### Impact Explanation
`dispatch()` and `fundRequest()` are the core, permissionless entry points every application and end user calls to send cross-chain messages and pay relayer fees natively — this is exactly the "EvmHost dispatch and delivery" reachable path called out as in-scope. If the fixed-fee-tier WETH/feeToken pool loses liquidity or was misconfigured relative to the pair's actual deepest venue, every native-token dispatch call on that chain reverts unconditionally. Since native payment is a first-class, documented payment method (per `docs/content/developers/evm/messaging/post-requests.mdx`), this fully denies message dispatch for all callers using native payment on the affected chain — a protocol-wide, permanent liveness failure of the messaging route until governance redeploys/reconfigures the wrapper. This satisfies the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Likelihood is meaningful wherever the deployment uses a V3/V4-based wrapper instead of a genuine V2 router (the repo explicitly ships `UniV3UniswapV2Wrapper` and `UniV4UniswapV2Wrapper` for chains lacking V2 liquidity, per their existence and the `ConfiguredWrapperForkTest` comment noting per-chain configuration). Fee-tier liquidity shifting over time is a normal, observed market phenomenon (as the original USDT/USDC example shows), and the wrapper's fee tier is fixed at `init()` with no update mechanism, so any drift makes the condition trivially and permanently triggerable by any unprivileged caller attempting a native-token dispatch.

### Recommendation
- Do not hardcode a single fee tier in `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper`; instead, iterate over the standard fee tiers (as already done elsewhere in the codebase, e.g., `sdk/packages/sdk/src/utils/swap.ts`'s `getBestV3Pool`/`COMMON_FEE_TIERS`) and select/attempt the tier with sufficient liquidity for the exact-output swap.
- Alternatively, make the fee tier and tick spacing owner-updatable via governance (mirroring the report's suggested mapping-based fix) so that liquidity migration can be remediated without redeploying and rewiring `_hostParams.uniswapV2` on `EvmHost`.
- Add a feeToken-denominated fallback/self-relay path in `EvmHost.dispatch`/`fundRequest` so a wrapper swap failure degrades to requiring feeToken payment rather than reverting the entire dispatch.

### Proof of Concept
1. Deploy `EvmHost` on a chain where `_hostParams.uniswapV2` points to a `UniV4UniswapV2Wrapper` configured with `defaultFee = 500` (0.05%) for the WETH/feeToken pair.
2. Over time, liquidity for that pair migrates predominantly to the 0.30% or 0.01% tier (a realistic market event, as with USDC/USDT), leaving the 0.05% pool with insufficient liquidity to fill exact-output swaps of the fee size dispatch requires.
3. Any user calls `IDispatcher(host).dispatch{value: msg.value}(post)` with a nonzero `msg.value` intending to pay the relayer fee in native token.
4. `EvmHost.dispatch` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`, which internally calls `UniV4UniswapV2Wrapper.swapETHForExactTokens` → `_createPoolKey` (fixed at `defaultFee`) → the V4 `SWAP_EXACT_OUT_SINGLE` action against the illiquid 0.05% pool, which reverts because the pool cannot supply `post.fee` output tokens for any available input.
5. The entire `dispatch` transaction reverts, and no message can be dispatched with native payment on this host until governance intervenes — no such intervention path currently exists for `defaultFee`/`defaultTickSpacing`.
