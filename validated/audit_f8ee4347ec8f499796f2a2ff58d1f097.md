### Title
Zero-lamport accounts referenced in a transaction perform real accounts-db lookups but are charged zero `loaded_accounts_data_size` cost - (File: `svm/src/account_loader.rs`)

### Finding Description
`accounts-db/src/is_loadable.rs`'s `IsLoadable::is_loadable` treats any account with zero lamports as non-existent, and `AccountsDb::load` filters it out post-lookup: `self.do_load(...).filter(|(account, _)| !account.is_zero_lamport())` [1](#0-0) . Critically, `do_load` still performs the *full* index/storage lookup (accounts index probe, and for on-disk accounts, a real read/deserialize from the AppendVec) before the zero-lamport filter discards the result — the filter is applied after the expensive work, not before it.

In `svm/src/account_loader.rs`, `load_transaction_account` (non-fee-payer path) calls `account_loader.load_transaction_account`, which internally calls `load_account` → `do_load` → ultimately the accounts-db `load()`/cache lookup described above. When the account is zero-lamport (and thus filtered to `None`), the fallback branch is taken:
```
} else {
    let mut default_account = AccountSharedData::default();
    default_account.set_rent_epoch(RENT_EXEMPT_RENT_EPOCH);
    Ok(LoadedTransactionAccount {
        loaded_size: default_account.data().len(),   // == 0
        account: default_account,
    })
}
``` [2](#0-1) 

Compare this to the case where the account is found and non-zero, where `loaded_size = TRANSACTION_ACCOUNT_BASE_SIZE.saturating_add(account.data().len())` [3](#0-2) . Zero-lamport accounts get **0** contribution to `loaded_tx_data_size` (not even the fixed `TRANSACTION_ACCOUNT_BASE_SIZE` per-account overhead that every other real account incurs), via `loaded_tx_data_size.increase_calculated_data_size(loaded_size, error_metrics)` in `collect_loaded_account` [4](#0-3) .

This `loaded_accounts_data_size` is exactly the value the cost model uses to compute CU cost: `CostModel::calculate_loaded_accounts_data_size_cost` turns bytes into "page" CU cost [5](#0-4) , and `calculate_cost_for_executed_transaction` uses `actual_loaded_accounts_data_size_bytes` (derived from `LoadedTransactionDataSize`) to compute the post-execution charged cost [6](#0-5) . Since zero-lamport accounts are effectively free in this accounting, an attacker who references many zero-lamport accounts (drained to zero rather than never created, forcing a genuine accounts-db read/deserialize before the filter discards it) causes real index-lookup/storage-read work per account while the cost model attributes essentially none of it to `loaded_accounts_data_size`.

Existing mitigations only partially cover this: each account slot in a transaction is bounded by `MAX_ACCOUNTS_PER_TRANSACTION = 256` [7](#0-6) , and writable accounts already incur a flat `WRITE_LOCK_UNITS` cost per write lock regardless of size [8](#0-7) . However, read-only account references (which still trigger the same `do_load`/index-lookup path) are not covered by write-lock cost, and neither is covered specifically for the "real do_load + zero-lamport discard" cost. The base per-account cost is only credited for accounts that are actually present with nonzero lamports.

### Impact Explanation
This is a real accounting gap where the cost model can materially underprice the work performed for a subset of referenced accounts (zero-lamport, previously-existing accounts that require an actual do_load and possible storage read before being discarded). This falls into the "underpriced work" / resource-consumption category of the Agave bounty program (cost-model / compute-budget correctness), rather than a fund-loss or consensus-halting bug — it does not break signatures, locks, rent, or settlement invariants, and the attack is bounded by `MAX_ACCOUNTS_PER_TRANSACTION` (256) and normal per-transaction signature/CU/fee costs, limiting the practical scale of resource exhaustion achievable per transaction.

### Likelihood Explanation
Feasible and repeatable by an unprivileged attacker: create N accounts (e.g. via System Program `CreateAccount`/`Transfer`), drain each to 0 lamports in prior transactions (or reuse an existing zero-lamport account from cluster state), then submit one transaction listing up to `MAX_ACCOUNTS_PER_TRANSACTION` such pubkeys as (mostly) read-only account references. Each such reference triggers a genuine `do_load` in accounts-db (including any read-cache miss / disk read) but contributes 0 bytes to `loaded_accounts_data_size`. No signature, lock, nonce, budget, or rent guard currently prevents this, since those guards address different invariants (double-spend, replay, fee sufficiency) and not do_load-vs-accounted-bytes symmetry.

### Recommendation
Charge a minimum accounting size for every account reference that triggers a real `do_load`/index lookup, regardless of whether the result is filtered by `is_loadable`/zero-lamport status — e.g., apply `TRANSACTION_ACCOUNT_BASE_SIZE` (or a comparable "index lookup" cost) in the `else` branch of `load_transaction_account` (svm/src/account_loader.rs, lines 644–651) instead of using only `default_account.data().len()`. Alternatively/also, distinguish "account never existed" (cheap index-miss) from "account existed but is zero-lamport" (requires actual read) at the `AccountsDb`/`AccountLoader` layer, and charge the latter at least the base per-account cost.

// test_load_transaction_accounts_program_success_complete)
#[test]
fn test_zero_lamport_account_undercharged_for_loaded_accounts_data_size() {
    // Setup: mock_bank contains N pubkeys that were previously non-zero (data.len() > 0)
    // but have since been stored with 0 lamports (simulating attacker draining them),
    // so `do_load`/is_loadable would discard them but a real load occurred.
    let mut mock_bank = TestCallbacks::default();
    let fee_payer = Keypair::new();
    let mut fee_payer_account = AccountSharedData::default();
    fee_payer_account.set_lamports(1_000_000);
    mock_bank.accounts_map.insert(fee_payer.pubkey(), (fee_payer_account.clone(), 1));

    let zero_lamport_keys: Vec<Pubkey> = (0..250).map(|_| Pubkey::new_unique()).collect();
    for key in &zero_lamport_keys {
        // Simulate a drained account: previously had data, now zero lamports.
        let mut acct = AccountSharedData::new(0, 512, &Pubkey::default());
        acct.set_lamports(0);
        mock_bank.accounts_map.insert(*key, (acct, 1));
    }

    let message = /* build a message referencing fee_payer + all zero_lamport_keys as read-only */;
    let mut account_loader = (&mock_bank).into();
    let mut loaded_transaction_data_size =
        LoadedTransactionDataSize::with_max_size(MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES.get());

    let result = load_transaction_accounts(
        &mut account_loader,
        &message,
        LoadedTransactionAccount {
            account: fee_payer_account,
            loaded_size: TRANSACTION_ACCOUNT_BASE_SIZE,
        },
        &mut loaded_transaction_data_size,
        &mut TransactionErrorMetrics::default(),
        &Rent::default(),
    ).unwrap();

    // Assertion demonstrating the bug: despite 250 real accounts-db lookups
    // (each involving a 512-byte account load before being zero-lamport-filtered),
    // the accounted loaded_accounts_data_size only reflects the fee payer's base size.
    assert_eq!(
        loaded_transaction_data_size.loaded_accounts_data_size,
        TRANSACTION_ACCOUNT_BASE_SIZE as u32, // 0 contribution from all 250 zero-lamport accounts
    );

    // Expected (fixed) behavior: each zero-lamport lookup should add at least
    // TRANSACTION_ACCOUNT_BASE_SIZE, reflecting the real do_load cost incurred:
    // assert_eq!(
    //     loaded_transaction_data_size.loaded_accounts_data_size,
    //     TRANSACTION_ACCOUNT_BASE_SIZE as u32 * 251
    // );
}
```
This test (with the current implementation) shows that the cost model's `loaded_accounts_data_size` is not incremented for zero-lamport account references despite each one causing a real `AccountsDb::do_load`/index lookup, confirming the underpricing.
