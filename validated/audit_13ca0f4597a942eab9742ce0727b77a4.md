### Title
OAuth callback `shop` parameter is not validated against `ShopValidator`, allowing the app's `client_secret` and authorization `code` to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` directly — without ever calling `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` — to build the OAuth token-exchange request target. Every other credential-exchange flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.exchange_token`) sanitizes the `shop` value through `Utils::ShopValidator` before using it to build the request host, but `Oauth.validate_auth_callback` does not.

### Finding Description
In `validate_auth_callback` [1](#0-0) , the `shop` field comes from `auth_query.shop`, an attacker-controlled query parameter on the OAuth callback URL. This value is:
1. Bound only into `to_signable_string`/HMAC alongside `code`, `host`, `state`, `timestamp` [2](#0-1) , which authenticates that the query as a whole was HMAC-signed by *some* valid request originator using the correct secret, but does **not** constrain `shop` to be an actual `*.myshopify.com` domain — Shopify's HMAC only proves integrity of the query string, not that `shop` is a legitimate Shopify shop.
2. Used to construct `null_session = Auth::Session.new(shop: auth_query.shop)`, which is then passed into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [3](#0-2) .
3. `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no further validation [4](#0-3) .
4. The client then POSTs `client_id`, `client_secret` (`Context.api_secret_key`), and the authorization `code` to `https://#{auth_query.shop}/admin/oauth/access_token` [5](#0-4) .

This breaks the intended binding: `host that receives the access_token/client_secret == a genuine Shopify domain`. Compare with `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which call `Utils::ShopValidator.sanitize!(shop)` first and only use the *validated* shop to build the session/host [6](#0-5) [7](#0-6) . `Oauth.validate_auth_callback` has no equivalent call anywhere in the method [1](#0-0) .

`Utils::ShopValidator.sanitize_shop_domain` exists specifically to restrict the `shop` value to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an app-supplied `myshopify_domain` [8](#0-7) , precisely to prevent this class of host-confusion bug — but `oauth.rb` never invokes it.

### Impact Explanation
If a host application constructs `AuthQuery` directly from raw callback parameters (as the gem's own documentation instructs: `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys.except(:controller, :action))`, per `docs/usage/oauth.md`), and an attacker can get their own domain accepted as `shop` while still producing a valid HMAC for the query, the app's `client_secret` and a first-party authorization `code` would be transmitted to attacker infrastructure. Since HMAC validation only checks the query is well-formed and correctly signed — it does not constrain `shop`'s value to a Shopify domain — the bug is fundamentally a missing-invariant issue in the gem itself: it never enforces that `shop` looks like a Shopify domain before it's used as an HTTP endpoint. This matches the report's SSRF-with-credentials risk category (High, and potentially Critical since `client_secret` exfiltration is possible if HMAC signing conditions can be met, e.g., if state/timestamp is otherwise attacker-influenced or replayed).

### Likelihood Explanation
Exploitability depends on whether an attacker can produce a valid HMAC for a query containing an arbitrary `shop` value, which normally requires knowledge of `api_secret_key`. Under the gem's own documented usage, however, the callback parameters (including `shop` and `hmac`) are taken as-is from the URL Shopify redirects to; if any implementation detail permits an attacker to control or spoof the `shop`+`hmac` pair (e.g., through an old/rotated secret disclosed via other means, or if `hmac_validator`'s dual-secret fallback path is misused), the missing sanitize call is the direct proximate cause of sending credentials to the wrong host — there is no defense-in-depth check on `shop` at all within this gem's OAuth callback path, unlike its sibling flows.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback` (and `begin_auth`), validate `shop` through `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) before constructing `null_session`/`auth_base_uri`, mirroring the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Craft an OAuth callback URL with `shop=attacker-controlled-host.example`, plus `code`, `state`, `timestamp`, `host` values, and an `hmac` value satisfying the app's `HmacValidator` check for that exact query string (this requires the ability to compute a valid signature — the point being that no code path additionally restricts `shop` to a `*.myshopify.com`-style domain).
2. The host app calls `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)` per the documented integration pattern [9](#0-8) .
3. `validate_auth_callback` builds `null_session` from the unvalidated `shop` and calls `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [3](#0-2) .
4. `HttpClient` issues `POST https://attacker-controlled-host.example/admin/oauth/access_token` with body containing `client_id`, `client_secret` (`Context.api_secret_key`), and `code` [10](#0-9) , exfiltrating the app's `client_secret` and authorization code to the attacker's server.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

def callback
  begin
    # Create an AuthQuery object from the request parameters,
    # and pass the list of cookies to `validate_auth_callback`
    auth_result = ShopifyAPI::Auth::Oauth.validate_auth_callback(
      cookies: cookies.to_h,
      auth_query: ShopifyAPI::Auth::Oauth::AuthQuery.new(
        request.parameters.symbolize_keys.except(:controller, :action)
      )
    )

    # Update cookies with the authorized access token from result
    cookies[auth_result[:cookie].name] = {
      expires: auth_result[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_result[:cookie].value
    }

    # Store the Session object if your app has a DB/file storage for session persistence
    # This session object could be retrieved later to make authenticated API requests to Shopify
    MyApp::SessionRepository.store_session(auth_result[:session])

    puts("OAuth complete! New access token: #{auth_result[:session].access_token}")

    head 307
    response.set_header("Location", "<some-redirect-url>")
  rescue => e
    puts(e.message)
    head 500
  end
end
