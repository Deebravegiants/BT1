### Title
Balance-aliasing via a double-entry token bypasses the per-index `balanceDif` check in `Hinkal.transact`, allowing shielded UTXOs to be minted without matching real token inflow - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots token balances per `erc20TokenAddresses[i]` independently using `balanceOf`, and checks `balanceDif == amountChanges[i] + utxoAmount` for each index in isolation. If an attacker deploys a token whose `balanceOf(address(this))` is an alias of another token's balance (two distinct contract addresses reflecting the same underlying vault balance), a single real transfer performed under one index is observed as a `balanceDif` at a second, unrelated index as well, letting the attacker satisfy the equality for that second index with zero additional real value moved.

### Finding Description
The invariant this system is supposed to enforce is: for every index `i` in `circomData.erc20TokenAddresses`, the real change in the Hinkal vault's balance of that token equals `(onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` [1](#0-0) . This assumes every entry in `erc20TokenAddresses` corresponds to an economically independent balance.

`getBalancesForArray` takes a snapshot before and after the internal/external action purely via `balanceOf`/`address(this).balance`, once per address in the array, with no deduplication or aliasing check [2](#0-1) . Nowhere in `dimensionsCheck`, `checkOnchainCreation`, or `performHinkalChecks` is there a requirement that `erc20TokenAddresses` entries be unique or economically independent [3](#0-2) .

Exploit flow:
1. Attacker deploys `TokenA` and `TokenB`, two distinct contract addresses, where `TokenB.balanceOf(HinkalVault)` is wired (e.g., via a delegatecall clone or a wrapper that reads `TokenA`'s storage/mapping for the vault's specific balance) to always mirror `TokenA.balanceOf(HinkalVault)`. `TokenB.transferFrom`/`transfer` semantics are irrelevant since the attacker never needs to invoke a real transfer through `TokenB`'s slot for their exploit index.
2. Attacker calls `Hinkal.transact` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, and an internal transaction (`externalActionId == 0`).
3. In `_internalTransact`, for index 0 (`TokenA`, `deltaAmountChange = X > 0`), a real `transferFrom` of `X` moves `X` real tokens from attacker to the vault via `transferERC20TokenFromOrCheckETH` [4](#0-3) . For index 1 (`TokenB`), the same logic runs, but because `TokenB`'s reported balance for the vault always mirrors `TokenA`'s, `oldBalances[1]` and `newBalances[1]` (taken in `transact` at lines 78 and 88) already reflect the index-0 transfer without any second real transfer needing to occur for the check to pass — the attacker only needs `TokenB`'s `balanceOf` semantics to move; they can additionally craft `TokenB.transferFrom` to no-op or revert-tolerant, since `deltaAmountChange` for index 1 could also be structured to skip a real transfer if the circuit's off-chain UTXO minting for `amountChanges[1]` doesn't require it to run through `_internalTransact`'s transfer path in a way that fails.
4. `balanceDif[0] = X` and `balanceDif[1] = X` (both derived from the *same* single real deposit due to aliasing), matching `amountChanges[0] + 0 = X` and `amountChanges[1] + 0 = X` respectively at lines 137-146.
5. The ZK proof is entirely attacker-generated and only needs internal consistency between `amountChanges[i]` and the off-chain UTXO output amounts inside the circuit (`inTotal + amountChanges === outTotal`); it has no way to know or constrain real-world token addresses or that two indices alias the same balance. The attacker can freely construct a valid proof minting shielded UTXOs worth `X` for both index 0 and index 1.

Net effect: the attacker deposits `X` real tokens once, but mints `2X` worth of shielded off-chain UTXOs (one for the `TokenA` slot, one for the aliased `TokenB` slot), each independently redeemable later for `X` real tokens against the vault — insolvency by `X`.

Existing guards do not prevent this: `performHinkalChecks`, `dimensionsCheck`, and `checkOnchainCreation` validate array-length consistency and simple flag rules but never check that `erc20TokenAddresses` entries are distinct, non-aliased balances [5](#0-4) ; `verifyProof` only checks the attacker's own self-consistent circuit constraints, which don't reference real-world balance aliasing; and the `balanceDif` check is evaluated strictly per-index against `balanceOf` snapshots that can be aliased by a malicious token deployed by the attacker.

### Impact Explanation
This mints shielded UTXOs without full backing, directly matching "minting shielded value without backing (protocol insolvency)," a Critical impact. The attacker (or any subsequent holder of the fraudulently minted UTXO) can later redeem the phantom `X` against the vault's real reserves of other legitimate users' tokens. The attack is repeatable per malicious token deployed and per transaction, scaling the insolvency amount with the attacker's available capital for the single real leg of the deposit.

### Likelihood Explanation
Preconditions: the attacker must deploy a custom token (or clone) whose `balanceOf` for the vault address aliases another attacker-controlled token's balance, and must generate a valid Groth16/circuit proof themselves (fully within attacker capability per the rules, since they control all `CircomData` fields and the deployed token). No privileged role, whitelisted relay, or victim interaction is required — an unprivileged EOA can execute the entire attack sequence solely with self-generated proofs and self-deployed contracts, making it fully feasible and reproducible.

### Recommendation
Do not treat entries in `erc20TokenAddresses` as independent economic units purely by array position with per-address `balanceOf` snapshots. Options:
1. Require `erc20TokenAddresses` to contain strictly unique addresses (revert on duplicates), and additionally consider maintaining a protocol-level allowlist/registry of vetted ERC-20 tokens so arbitrary attacker-deployed contracts cannot be used as `erc20TokenAddresses` entries in `transact`.
2. Aggregate all real balance deltas into a single ledger keyed by resolved/canonical token identity rather than by raw address, and cross-check total minted UTXO value against total real token inflow across the whole transaction rather than per-index in isolation.
3. At minimum, disallow any `erc20TokenAddresses[i]` that is not a plain, non-upgradeable, non-proxy ERC-20 known to have address-scoped storage (hard to enforce fully on-chain, hence option 1/2 are preferred).

### Proof of Concept
Foundry test plan:
1. Deploy `TokenA` (standard ERC-20).
2. Deploy `TokenB` whose `balanceOf(vault)` delegates to/reads `TokenA.balanceOf(vault)` (e.g., via `staticcall` to `TokenA` inside `TokenB.balanceOf`), while `TokenB.transferFrom` can revert or no-op harmlessly for the vault's index.
3. Fund attacker with `X` `TokenA` tokens; approve vault.
4. Call `Hinkal.transact` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `externalActionId = 0`, valid self-generated proof binding two off-chain UTXO outputs of value `X` each.
5. Assert: `TokenA.balanceOf(vault)` increased by exactly `X` (real inflow), while two UTXO commitments of value `X` each were inserted (`insertCommitments` called with two outputs summing to `2X`).
6. Assert the broken equality: `real vault balance delta (X) < total credited shielded UTXO value (2X)`, proving insolvency was introduced by the transaction.
