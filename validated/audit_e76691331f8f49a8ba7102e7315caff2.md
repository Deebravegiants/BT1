The docs explicitly state `Registry.process` "will verify the request did indeed come from Shopify" and pass `data.shop` directly to the handler as the trusted shop identity, documented at [1](#0-0) . This confirms the gem presents `request.shop` as an authenticated tenant identifier of the webhook processing contract.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Registry.process` treats a successful HMAC check on the body as proof that the *entire request*, including these header fields, "did indeed come from Shopify," and forwards `request.shop` into `WebhookMetadata` as the trusted tenant identifier passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Request#shop` is read straight from the `shop-domain` header with no cryptographic binding to the signed body: [3](#0-2) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body only) using `Context.api_secret_key`: [4](#0-3) 

`Registry.process` raises only if the HMAC check fails, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, etc., and dispatches it to the app-supplied handler as authenticated data: [5](#0-4) 

The intended identity binding is: `shop_header_value == shop_that_the_HMAC_actually_authenticates`. Because the HMAC only covers the raw body, this equality never actually holds — the signature authenticates *body bytes*, not the `shop-domain` header. An unprivileged attacker who legitimately receives even one genuine webhook (e.g., by installing the same public app on their own free/dev store, which requires no special privilege or victim credentials) obtains a valid `(raw_body, hmac)` pair signed with the app's shared secret. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value naming a different, victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)`, so the host application processes attacker-supplied body content under the identity of a shop the attacker does not control.

This is the direct structural analog of the M-21 report's bug class: a value used downstream to make trust/identity decisions (`shop`) is not the value actually covered/protected by the cryptographic check (HMAC over body only) — an identity-binding equality that the documentation ("verify the request did indeed come from Shopify") implies is upheld, but which the code never enforces.

### Impact Explanation
Any host application that follows the gem's documented pattern — treating `data.shop` from a validated `Registry.process` call as an authenticated tenant identifier (e.g., to look up which merchant's records to update, enqueue shop-scoped background jobs, or attribute GDPR `customers/redact` / `shop/redact` compliance events) — is exposed to cross-tenant data confusion: an attacker can inject fabricated webhook events attributed to any target shop domain string of their choosing, without ever needing that shop's access token, `client_secret`, or session. Depending on how the host app uses `data.shop`, this can lead to writing/deleting data against the wrong tenant's records or triggering shop-scoped side effects for a shop the attacker doesn't own — a cross-tenant access violation.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the same public app on an attacker-controlled shop (freely available to any developer) to capture one valid `(body, hmac)` pair, and (2) the ability to send a raw HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both are within reach of an unprivileged internet user and require no leaked victim credentials, TLS interception, or social engineering.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is actually verified, rather than trusting the raw header independent of the signature. Options:
- Have the signable string include the shop-domain header value alongside the body, i.e. `to_signable_string` should incorporate `shop-domain` (and other identity-bearing headers) so the HMAC authenticates the full identity tuple, not just the body bytes.
- Alternatively, document/require that host applications independently verify `data.shop` against an existing shop session/installation record before trusting it as a tenant key, and update `Registry.process`'s guarantee language ("verify the request did indeed come from Shopify") to clarify it only authenticates the body, not the shop header.

### Proof of Concept
```ruby
# Attacker legitimately installs the public app on their own dev store "attacker.myshopify.com"
# and receives one genuine webhook, capturing:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
) # this is legitimately computed by Shopify for the attacker's own shop

# Attacker replays the same body/hmac pair to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop they do not control:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,          # still valid, since HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body/hmac match, shop is never checked)
# => handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# => host app processes attacker-controlled data under the victim shop's identity
```

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
