### Title
Third-party dust `supply` force-restamps a foreign account's cached LTV/liquidation parameters without the health-factor floor, pushing it into liquidation - (File: contracts/controller/src/positions/supply.rs)

### Summary
Any unprivileged address may call `supply` against an existing foreign account as long as every asset key is already a supply position of that account (`require_third_party_existing_supply`, `supply.rs:86-96`). Every supply leg then runs `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` (`supply.rs:288-296`), which restamps the position's cached LTV and liquidation parameters to the currently listed spoke-asset values. The sanctioned keeper path for the same restamp, `update_account_threshold` with `has_risks`, reverts unless the account ends at a health factor of at least 1.05 WAD; the supply path applies the same restamp with no such floor. An attacker can therefore downgrade a victim's cached risk parameters — the lending analogue of CVE-2017-12851's "altering form data to change another user's security attributes" — by dust-supplying into their existing markets, then liquidate the account.

### Finding Description
Per-position LTV/liquidation parameters are cached inside each `AccountPosition` and restamped when touched. `process_supply` authorizes only `caller` (`validation::require_authorized_caller`, `supply.rs:47`) and, for `account_id != 0`, requires a spoke match but no owner/delegate check (`AccountGuard::Supply`, `account.rs:100`). The only restriction on strangers is `require_third_party_existing_supply`, which merely asserts the supplied `HubAssetKey`s already exist in `account.supply_positions` — amount is unconstrained beyond positivity, so a dust top-up qualifies (`supply.rs:89-95`).

`process_deposit` then calls `merge_supply_leg` per leg, which unconditionally invokes `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` before merging the new scaled amount (`supply.rs:288-296`). If governance has since listed tighter parameters (lower LTV or liquidation threshold/bonus) for that spoke asset — a routine risk tightening — the victim's cached tuple is silently overwritten with the stricter values, reducing its liquidation-weighted collateral and health factor. Compare `update_account_threshold` (`risk/params.rs` via the keeper entrypoint): with `has_risks` set it requires a post-update HF ≥ 1.05 WAD, explicitly so a restamp "cannot be used to push an account into liquidation" (`scripts/permissionless_entrypoints.txt:76`). The `supply` path lacks that invariant entirely — the only solvency check in `finalize_position_flow` is `PositionSides::Supply` with `check_solvency = false` (`supply.rs:65-72`), which never verifies health factor.

Attack path for a single unprivileged address:
1. Wait for (or anticipate) a risk-parameter tightening on a spoke asset the victim supplies.
2. Call `supply(attacker, victim_account_id, victim_spoke_id, [(victim_asset_key, dust)])`. All checks pass because the asset is an existing supply position.
3. `merge_supply_leg` restamps the position's LTV/threshold tuple; the victim's health factor drops below 1 WAD.
4. Call `liquidate(attacker, victim_account_id, debt_payments, SeizeMode::Transfer)` and seize collateral at the HF-scaled bonus.

### Impact Explanation
Theft of user funds / forced liquidation. The victim's collateral is seized at the liquidation bonus through the standard `liquidate` flow, and the attacker captures the bonus. The attacker needs no privileged role, no leaked key, and no control over the victim — only caller auth and a dust amount of an asset the account already supplies. The victim loses collateral value they would not have lost had their cached parameters only been restamped through `update_account_threshold`, which enforces the 1.05 HF floor.

### Likelihood Explanation
The trigger conditions are ordinary protocol operations: risk parameters are tightened by governance over time, and positions retain their cached tuple until touched. The permissionless supply surface is intentionally broad (INV-AUTH-03), so the attacker needs only to know a victim `account_id` (public) and hold any positive amount of one asset the victim already supplies. The restamp effect compounds across markets — a multi-leg dust supply restamps every listed leg. Likelihood is moderate-to-high whenever a risk downgrade occurs while positions carry stale, looser cached parameters; it does not depend on oracle misbehavior or route quality.

### Recommendation
Gate the risk-parameter restamp so an unauthorized supply cannot alter a foreign account's security parameters. Options:
- Skip `refresh_supply_risk_params` (or use a scope that preserves the cached LTV/liquidation tuple) when `caller` is neither the owner nor an active delegate, matching the `WithdrawKind::Liquidation` precedent in `leg_may_restamp_risk_params` (`supply.rs:379-391`), or
- Apply the same post-condition as `update_account_threshold`: after a third-party-triggered `FullTuple` restamp, require the account's health factor to remain ≥ 1.05 WAD and revert otherwise, or
- Restrict third-party supply to not modify position state at all (e.g., credit it as a separate non-risk-bearing entry), keeping INV-AUTH-03 top-ups purely additive.

### Proof of Concept
```rust
// Preconditions:
//  - Victim account V supplies USDC (existing supply position) and borrows ETH.
//  - V's cached liquidation threshold on USDC is 0.90; HF ~1.10 (not liquidatable).
//  - Governance tightens USDC in V's spoke: liquidation threshold now 0.80.
//    V's cached tuple is untouched until the position is modified.

// Attacker (holds 1 unit of USDC, no delegate grant, not the owner):
let dust = vec![&env, (usdc_hub_key, 1i128)];
client.supply(&attacker, &victim_account_id, &victim_spoke_id, &dust);
// ^ succeeds: require_third_party_existing_supply passes because V already
//   supplies USDC. merge_supply_leg -> refresh_supply_risk_params(FullTuple)
//   restamps the position to threshold 0.80.

assert!(client.get_health_factor(&victim_account_id) < WAD); // now liquidatable

// Profit: seize at the HF-scaled bonus
client.liquidate(
    &attacker,
    &victim_account_id,
    &vec![&env, (eth_hub_key, repay_amount)],
    &SeizeMode::Transfer,
);
// Attacker receives victim USDC collateral worth more than the ETH repaid.
```
