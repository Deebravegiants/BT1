## Analysis Result

I found a directly analogous issue in the `hyper-fungible-token` pallet's decimal-scaling logic.

### Title
Unbounded ERC20/local decimal difference causes `u128::pow` overflow in cross-chain amount conversion, leading to DoS and incorrect (unbacked) mint/burn amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet converts amounts between the local asset's decimals and the EVM-side (`Precisions`) decimals using `10u128.pow(erc_decimals.saturating_sub(local_decimals))`. Neither `register_token` nor `update_token` bound the maximum allowed difference between `erc_decimals` and `local_decimals`, so a difference greater than 38 (since `u128::MAX ≈ 3.4e38`) causes `u128::pow` to overflow — panicking in debug builds and silently wrapping in release builds. This is the same bug class as the referenced LayerZero OFT `sd2ld`/decimal-cap report: an unvalidated decimal delta feeding an unchecked power/multiplication used for amount scaling on every cross-chain transfer.

### Finding Description
`register_token` and `update_token` only enforce a lower bound on the configured EVM decimals: [1](#0-0) 
There is no upper bound on `config.decimals - local_decimals`. That unbounded difference is later used directly as the exponent in: [2](#0-1) 
`convert_to_balance` divides by `10u128.pow(diff)` and `convert_to_erc20` multiplies by the same value. Both are called on every `send`, `on_accept`, and `on_timeout` invocation: [3](#0-2) [4](#0-3) 
Since `erc_decimals` is a `u8` (0–255) with no cap enforced at registration time, an asset registered with, e.g., `local_decimals = 0` and `erc_decimals = 200` produces `diff = 200`, and `10u128.pow(200)` overflows `u128` far below the exponent limit of 38.

### Impact Explanation
- If the runtime is compiled/tested with overflow checks enabled, every `send`/`on_accept`/`on_timeout` call touching this asset panics, permanently bricking the token bridge extrinsic path for that asset (DoS) — reachable by any unprivileged user who calls `send()` or by any relayer delivering a `PostRequest` for that asset.
- If compiled in release mode without overflow checks, `10u128.pow(diff)` silently wraps to an arbitrary small value. Because this scalar is used to both divide (`convert_to_balance`, minting side) and multiply (`convert_to_erc20`, outgoing side), a wrapped small divisor in `on_accept` can inflate the computed local `amount`, causing the pallet to mint or release far more local tokens than were ever locked/burned on the remote side — an unbacked mint / fund-drain condition on the escrow account.

### Likelihood Explanation
This requires only a single `register_token`/`update_token` call configuring a token with a large decimal difference (a plausible misconfiguration, not necessarily malicious governance intent — many chains have exotic ERC20 decimals), after which the vulnerable path is triggered purely by unprivileged actors sending tokens (`send`) or by relayers delivering standard `PostRequest`/timeout messages, matching the pattern flagged in the referenced report.

### Recommendation
Add an explicit cap on the allowed decimal difference in `register_token` and `update_token`, e.g.:
```rust
ensure!(
    config.decimals.saturating_sub(local_decimals) <= 18,
    Error::<T>::DecimalsDeltaTooLarge
);
```
and replace `10u128.pow(...)` with `10u128.checked_pow(...)` (and `checked_mul`/`checked_div` in `convert_to_balance`/`convert_to_erc20`), returning an error instead of panicking or wrapping.

### Proof of Concept
1. Governance calls `register_token` with `local_id` whose local asset has `local_decimals = 0` and a chain config with `config.decimals = 200` (passes the existing `config.decimals >= local_decimals` check).
2. Any user calls `send()` for this asset; `convert_to_erc20(amount, 200, 0)` calls `10u128.pow(200)`, overflowing.
3. Alternatively, a relayer delivers a crafted `PostRequest` to `on_accept` for this asset/chain pair; `convert_to_balance` divides by the overflowed/wrapped `10u128.pow(200)` value, producing a corrupted `amount` that is minted/transferred to the beneficiary.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
