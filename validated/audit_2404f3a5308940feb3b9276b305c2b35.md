### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC computed only over the raw request body, then hands the *unauthenticated* `shop-domain` header straight to the handler as the tenant identifier, breaking the binding `hmac-signed-content == identity-used-downstream`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` — the only data that is ever HMAC-verified — returns exclusively `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers and are never part of `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request purely through `Utils::HmacValidator.validate(request)`, which internally calls `validate_signature`, comparing `computed_signature(verifiable_query.to_signable_string, secret)` (i.e. the body) against the supplied `hmac`: [3](#0-2) 

Once that body-only check passes, `process` immediately trusts `request.shop` as the tenant for the handler: [4](#0-3) 

Because the signature covers only the body, the `shop-domain` header can be swapped for any value without invalidating the HMAC. Any actor capable of delivering an HTTP POST directly to the app's webhook endpoint (bypassing Shopify's own transport) — for example, someone who has legitimately received one genuine, correctly-signed webhook for their own store (all stores sharing the same app/`client_secret` produce HMACs verifiable with that same secret) — can replay that exact body with the `shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will build `WebhookMetadata` with `shop: <attacker-chosen victim shop>` and hand it to the merchant's handler as if Shopify itself certified that shop.

The equality the code should enforce but does not is:
`shop authenticated by the HMAC == shop acted upon by the handler`

Here the left side is undefined (the HMAC authenticates nothing about `shop`), while the right side is fully attacker-controlled.

### Impact Explanation
This breaks the tenant-isolation guarantee that app developers rely on: `Registry.process` promises that a webhook whose HMAC validates originates from, and pertains to, the shop named in `shop-domain`. Since `shop` is unauthenticated, an attacker can make the app process/act on data (e.g. redact-customer webhooks, order/product update webhooks) under an arbitrary victim shop identity, causing cross-tenant confusion in any handler that keys persistence, authorization, or side effects off `WebhookMetadata#shop`. This matches the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires the attacker to be able to send raw HTTP requests directly to the app's public webhook endpoint (not through Shopify's webhook delivery infrastructure) and to possess one genuine, HMAC-valid webhook body (trivially obtainable by installing the app on their own free development store, since the same `client_secret` signs all shops' webhooks for a given app). No access token, `client_secret`, or privileged account is required — only network reachability of the merchant's public webhook URL, which is standard for any webhook endpoint.

### Recommendation
Bind the authenticated identity to the value acted upon: include `shop-domain` (and ideally `webhook-id`/`topic`) inside the signable content, or otherwise cross-check the header value against a fact already tied to the verified session/API context (e.g. reject/flag when the `shop-domain` header does not match a shop the app expects, or require the endpoint to be scoped per-shop). At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures one legitimately-delivered, correctly-signed webhook:
raw_body = '{"id":123}'
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => genuine_base64_hmac_for(raw_body), # signed w/ shared client_secret
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}

# Attacker replays the SAME body+hmac directly to the app's public webhook
# endpoint, only rewriting the shop header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (only raw_body is checked), and the registered
#    handler receives WebhookMetadata with shop: "victim-shop.myshopify.com",
#    even though nothing about that value was ever verified.
```

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
