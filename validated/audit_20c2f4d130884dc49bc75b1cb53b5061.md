The docs confirm the gem's documented flow: `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and the handler is documented to receive `data.shop` as the shop domain to key work like `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. This is exactly the identity-binding gap: the value the gem tells developers to trust as the tenant identifier is not covered by the signature the gem itself validates.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are unauthenticated and can be forged to misattribute a validly-signed payload to another shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in the signed material [2](#0-1) . `Registry.process` accepts the request once the HMAC check passes and then hands `request.shop` (and the other unauthenticated header values) directly to the app's handler as trusted tenant metadata [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop_that_Shopify_signed_the_payload_for == request.shop_used_by_handler`

Root cause: `HmacValidator.validate` only proves that `secret` produced `hmac` over `to_signable_string` (the raw body) [4](#0-3) . It proves nothing about which shop, topic, or webhook id the body belongs to, because those fields live outside the signed string. Since `api_secret_key` is the same for every shop that installs a given app, any shop that has legitimately installed the app can capture one of its own genuine `(raw_body, X-Shopify-Hmac-SHA256)` pairs (Shopify sends webhooks in cleartext HTTPS to the app's public endpoint, so the installer/operator of that shop can see them), then replay the identical body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` still passes because the body and secret are unchanged, and `Registry.process` calls the handler with the attacker-chosen `shop` value [3](#0-2) .

The gem's own documentation instructs developers to trust `data.shop` as the tenant key for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not a case of the host app misusing an undocumented API — it is following the documented contract of `ShopifyAPI::Webhooks::Registry.process` and `WebhookMetadata`.

### Impact Explanation
This breaks cross-tenant isolation: any unprivileged internet user who can install the app on a shop they control (e.g. a free/dev store) can capture a validly-signed webhook body and replay it against the app's public webhook endpoint while asserting it belongs to any other shop, because `shop` is not part of the signed content. Depending on how the host app persists/acts on `data.shop` + `data.body` (order/customer/GDPR data ingestion, inventory updates, uninstall/app-scope changes, etc.), this can be used to inject or corrupt data attributed to a victim shop the attacker does not control — a cross-tenant access violation.

### Likelihood Explanation
Likelihood is moderate-to-high: no access token, `client_secret`, or privileged account is required — only the ability to install the app on any shop (including a free development store the attacker controls) and to send an HTTP request to the app's public webhook endpoint with crafted headers, both of which are available to an ordinary internet user.

### Recommendation
Include the identity-bearing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the payload before they are trusted (e.g., require the caller to additionally verify `shop` against a known/installed-shop allowlist keyed by data actually retrieved from Shopify, not from unauthenticated headers). At minimum, document prominently that `data.shop`/`data.topic`/`data.webhook_id` are unauthenticated and must not be used as sole tenant/topic identifiers without additional server-side verification (e.g., cross-checking against the shop associated with the currently stored session/webhook registration).

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; Shopify sends a webhook to the app's public endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id":1,"note":"hello"}`
2. Attacker (who controls that shop, e.g. via a local proxy/dev store) records the exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker sends a new POST to the same public webhook endpoint with the identical `raw_body`/HMAC but:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses these headers verbatim [5](#0-4) ; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, since `client_secret` and body are unchanged [6](#0-5) .
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's own body [3](#0-2) , causing the host app to process/store data as if it came from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
