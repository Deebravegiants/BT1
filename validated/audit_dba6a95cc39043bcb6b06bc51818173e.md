## Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) trusted from unsigned HTTP headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an HTTP header that is never included in the signed payload. An attacker who can obtain any single valid `(raw_body, hmac)` pair for the app's secret (e.g., by installing the app on their own store and capturing a real webhook delivery) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop, and the request will pass HMAC verification while the app processes it as belonging to the victim tenant.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read straight out of unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against `verifiable_query.hmac` (the header-derived signature) — it never binds any header value into the signed string: [4](#0-3) 

This breaks the identity binding `authenticated_bytes == shop_identity_used_by_app`. The equality that should hold is:

`HMAC_verified_bytes (raw_body) == bytes_that_determine_tenant_identity (shop header)`

but in this implementation the two are disjoint: the HMAC signs the body while the tenant identity (`shop`) is read from a header outside the signed scope. Any attacker who can produce one genuinely-signed `(body, hmac)` pair — trivially achievable by installing the app on their own development/trial store and receiving a real webhook — can reuse that pair verbatim against the app's webhook endpoint while swapping the `shopify-shop-domain` header to point at a different (victim) shop. `Utils::HmacValidator.validate` will report the HMAC as valid (since the body/signature pair is genuinely correct), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

## Impact Explanation
This allows cross-tenant impersonation: a webhook that should only ever attest "this event happened for shop A" can be relabeled to "this event happened for shop B" without invalidating the cryptographic check the library relies on for authenticity. Any host application that uses `WebhookMetadata#shop` to key data lookups, trigger per-merchant side effects, or route to per-tenant storage (a documented, expected usage pattern of this field) can be made to act on attacker-chosen data under a victim tenant's identity. This satisfies the "cross-tenant access" critical-impact criterion, since the gem's own authentication primitive (`Utils::HmacValidator`/`Webhooks::Registry.process`) is what fails to bind the tenant field.

## Likelihood Explanation
The attacker only needs the capability an ordinary unprivileged internet user has: the ability to install the target app on a shop they control (many Shopify apps are installable on any store, including free dev/trial stores) and to send arbitrary HTTP requests to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged account is required — the attacker never needs to know the secret, only to replay bytes and swap a header. This is a low-effort, high-reliability attack once a single valid webhook has been captured.

## Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the string that is HMAC-verified, or otherwise cryptographically bind them to the signed payload, so a valid signature can only be replayed for the exact tuple of body + headers that Shopify originally sent. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside `@raw_body`, and `HmacValidator` (or `Registry.process`) should reject requests where these header-derived fields are not authenticated.

## Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers an event that fires a webhook (e.g., `orders/create`).
2. Attacker captures the genuine webhook HTTP request, in particular the raw body and the `x-shopify-hmac-sha256` header — both correctly computed by Shopify using the app's real secret.
3. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only (per `Request#to_signable_string`, [1](#0-0) ) and finds it matches, since the body/signature pair is unchanged.
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now reads `"victim-shop.myshopify.com"` from the forged header ( [5](#0-4) ), causing the app to process attacker-controlled data under the victim tenant's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
