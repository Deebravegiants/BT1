### Title
Webhook Shop and Topic Identity Not Covered by HMAC Signature Verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` in `Registry.process` cryptographically authenticates the payload bytes but never authenticates the `x-shopify-shop-domain` or `x-shopify-topic` HTTP headers. Those headers are nonetheless trusted afterwards to select the handler and to attribute the webhook data to a specific tenant, breaking the equality between "bytes verified by HMAC" and "bytes relied upon for tenant/topic attribution."

### Finding Description
`Request#hmac` extracts the signature from the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` and `topic` are read straight from unauthenticated headers: [3](#0-2) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the body only) and compares it against the received HMAC using `Context.api_secret_key`: [4](#0-3) 

`Registry.process` then raises only if the body HMAC fails, and afterward dispatches using the unauthenticated `request.topic` to pick a handler and passes the unauthenticated `request.shop` on to the handler as the tenant identity for the event: [5](#0-4) 

Because the HMAC only binds the body, any HTTP client that possesses a single legitimate `(raw_body, hmac)` pair — for example a merchant who received one authentic webhook for their own shop — can resend that exact body and signature to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header. `HmacValidator.validate` still succeeds (it never looks at the headers), and `Registry.process` will process the (attacker-chosen) topic's handler and attribute the payload to the attacker-chosen shop. The equality that should hold — `shop/topic authenticated by HMAC == shop/topic used for tenant/handler attribution` — is broken.

### Impact Explanation
This allows cross-tenant confusion of webhook data: an attacker who has received (or otherwise obtained) any one validly-signed webhook body for the app can cause the host application to process that payload as belonging to a different, victim shop, or under a different topic than what Shopify actually sent. Depending on how the host app's webhook handlers use `shop`/`topic` (e.g., writing order/customer data keyed by shop, or triggering fulfillment/inventory side effects), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant's shop — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Medium: the attacker needs one authentic `(body, hmac)` pair for the target application, which is readily obtainable by any merchant who has legitimately installed the app and received a genuine webhook (no `api_secret_key` or privileged access required), then simply modifies the shop-domain/topic headers when replaying to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook-id` (or all Shopify-controlled headers) in the signable string used for HMAC verification, or otherwise cryptographically bind these header values to the signed payload, so that `HmacValidator.validate` fails if any of these fields are altered independently of the body.

### Proof of Concept
1. App receives a genuine webhook for `shop-a.myshopify.com`, topic `orders/create`, with body `B` and a valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `api_secret_key`).
2. Attacker (any internet client with access to `B` and `H`, e.g. the shop-a merchant themselves) sends a new POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged)
   - `x-shopify-shop-domain`: `shop-victim.myshopify.com` (changed)
   - `x-shopify-topic`: `orders/create` (unchanged or changed to any registered topic)
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`, per `lib/shopify_api/utils/hmac_validator.rb` and `Request#to_signable_string`.
4. The handler registered for `orders/create` is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "shop-victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process shop-a's data under shop-victim's identity.
