### Title
Permanently frozen escrow when a beneficiary is token-blacklisted, because settlement messages are dispatched with `timeout: 0` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The Intent Gateway's cross-chain settlement path releases escrowed funds by pushing a `safeTransfer` directly to a `beneficiary` address inside `_withdraw`, exactly the anti-pattern from the referenced Escrow.sol report. Unlike a normal ISMP timeout flow, the settlement POST request that triggers this transfer is dispatched with a **hardcoded `timeout: 0`** ("no timeout"), so there is no fallback recovery path if the transfer permanently reverts (e.g. the beneficiary is blacklisted by a token like USDC).

### Finding Description
`ExtrinsicIntents.onAccept` decodes `RedeemEscrow`/`RefundEscrow` requests and calls `_withdraw`: [1](#0-0) 

`IntentsBase._withdraw` loops over every escrowed token for the order and pushes tokens directly to `beneficiary` with `IERC20.safeTransfer`, with no isolation between tokens and no alternate withdrawal address: [2](#0-1) 

Both `_fillCrossChain` (RedeemEscrow, beneficiary = solver) and `_cancelFromDest`/`_cancelFromSource` (RefundEscrow, beneficiary = order user) dispatch this settlement message via `_post`, which **hardcodes `timeout: 0`**: [3](#0-2) 

Per protocol semantics, `timeout: 0` means the message never expires and can never be routed through `onPostRequestTimeout`/refund logic: [4](#0-3) 

When `EvmHost.dispatchIncoming` low-level-calls `onAccept` and it reverts, the host simply deletes the receipt so the message stays "retryable" — it does **not** revert the whole batch, and it provides no alternative delivery route: [5](#0-4) 

If the escrow's `order.inputs` includes even one token where `beneficiary` (the solver, on redeem, or the user, on refund) is blacklisted, `safeTransfer` reverts inside the loop, so `onAccept` reverts for the **entire** `WithdrawalRequest` — including any other, unrelated tokens and the escrowed relayer/fee-token amount in the same request (`TRANSACTION_FEES`, lines 472-477). Because the request was dispatched with `timeout: 0`, no relayer can ever submit a timeout proof to trigger any refund path, and permissionless resubmission of `handlePostRequests` will retry the exact same reverting `safeTransfer` forever. The escrow becomes permanently stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract with no participant-settable alternate address and no sweep mechanism for this state.

This mirrors the reported Escrow.sol bug class precisely: a single blacklisted counterparty address bricks a "push" fund-release path used by all downstream participants, and here it is compounded because the underlying cross-chain messaging layer's only safety net (timeouts) is explicitly disabled for this call site.

### Impact Explanation
Any solver filling a cross-chain order, or any user cancelling one, whose settlement `beneficiary` address becomes blacklisted by a fee-vetted token (USDC, etc.) between order placement/fill and settlement delivery results in **permanent loss of the entire escrowed basket for that order** — not just the blacklisted token, since all `order.inputs` and the `TRANSACTION_FEES` amount are released in the same atomic `_withdraw` loop. This is a direct, permanent freezing of user/solver funds with no recovery mechanism (High severity), reachable by any ordinary market participant (a solver bidding on an intent, or a user placing/cancelling an order) without any privileged action.

### Likelihood Explanation
Likelihood is moderate: it requires the beneficiary address to be blacklisted by the specific ERC-20 in use, which is a realistic and previously-exploited real-world event for USDC-class tokens (regulatory blacklisting, address poisoning/spite-blacklisting via reporting, or Tornado-Cash-style sanction listings). No attacker action against the protocol itself is needed — only the ordinary condition that one of the tokens transacted is a blacklist-capable token and one participant's address gets listed, which the protocol's own documentation assumes ("vetted tokens" including USDC) will occur.

### Recommendation
1. In `IntentsBase._withdraw`, do not `safeTransfer` directly to `beneficiary`; instead credit an internal per-beneficiary, per-token balance mapping and expose a separate permissionless `claim`/`pull` function, so a revert on one token/beneficiary cannot block release of other tokens in the same request.
2. Allow participants (or governance-configurable) to register/withdraw to an alternate address, so a blacklisted beneficiary can redirect settlement.
3. Never dispatch settlement-critical `DispatchPost` messages (`RedeemEscrow`/`RefundEscrow` in `ExtrinsicIntents._post`) with `timeout: 0`; give them a finite timeout with a corresponding `onPostRequestTimeout` handler that can safely re-credit escrow for later pull-based withdrawal, restoring a working recovery path even if the initial push fails.

### Proof of Concept
1. User places a cross-chain order with `order.inputs` = [USDC, DAI], filled by solver `S` (via `_fillCrossChain` on the destination chain), dispatching `RedeemEscrow` with `beneficiary = S` and `timeout: 0` (`ExtrinsicIntents._post`, line 133).
2. Before the settlement message is delivered on the source chain, `S`'s address gets added to the USDC blacklist (e.g. via Circle's compliance action).
3. A relayer submits `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `IntentsBase._withdraw`.
4. The loop reaches the USDC leg and calls `IERC20(USDC).safeTransfer(S, amount)`, which reverts because `S` is blacklisted.
5. The whole `onAccept` call reverts; `EvmHost.dispatchIncoming` deletes the receipt (retryable) but the DAI leg and the fee-token amount are never released because they are all inside the same reverted `_withdraw` call.
6. Because the message was dispatched with `timeout: 0`, it can never be routed to a timeout handler; every future resubmission of the same proof hits the identical revert. The USDC, DAI, and fee-token amounts are permanently stuck in the `IntentGatewayV2` contract, unrecoverable by the solver or anyone else.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
