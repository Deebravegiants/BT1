Zero outstanding debt makes the entire declared `repay` amount an "overpayment" refunded out of real pool custody without any transfer in - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay::accounting` resolves a repayment via `Cache::resolve_repay`, which delegates to `common::rates::scaling::resolve_repay`. When the position's ceiled debt value (`current_debt_ceil`) is zero — i.e., a market/position carrying no debt — `resolve_repay` takes its full-close branch (`amount >= current_debt_ceil`) and returns `overpayment = amount - 0 = amount`, so the *entire* declared amount is classified as excess. `net_repay` is then zero, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and `ops::repay::apply` executes `cache.transfer_out(payer, overpayment)`, paying the full declared amount out of the pool's real token custody while crediting nothing to the cash book. This is the same bug class as M-09: a zero-valued baseline variable (`adjustedRectangle` / `current_debt_ceil`) makes the excess equal to the whole minted/paid amount, so nothing is retained and everything is released. The repo's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3589-3610) demonstrates exactly this: `repay(payer, custody_before)` on a market with `borrowed == 0` credits `actual_amount = 0` and drains the full custody balance to the payer.

### Finding Description
In `common/src/rates/scaling.rs:171-191`, `resolve_repay` computes `current_debt_ceil = unscale_borrow_ceil(pos_scaled, borrow_index, decimals)`. For a position with zero scaled debt (or any market where the resolved debt rounds to zero), `current_debt_ceil == 0`, so the condition `amount >= current_debt_ceil` is trivially true and the function returns `(pos_scaled, amount - 0)` — the whole `amount` as excess. In `contracts/pool/src/ops/repay.rs:44-57`, `net_repay = amount - overpayment = 0`; the `net_repay == 0 || burned.raw() > 0` guard passes vacuously, `credit_cash(0)` leaves the book untouched, and `apply` at line 32 refunds `overpayment` via `transfer_out`. The refund is computed from the *declared* `action.amount`, not from a measured inbound transfer — so if the controller did not actually fund `amount` into the pool first (the comment on line 3 documents the assumption, but nothing in the pool enforces it), the "refund" pays out tokens the payer never deposited.

### Impact Explanation
Theft of user funds / protocol insolvency. Every asset unit refunded this way leaves `cash` unchanged while real custody decreases, breaking the book/custody invariant the fixture guards on (`assert_eq!(before.cash, custody_before)`). An attacker can declare `amount` equal to the pool's full token balance on a zero-debt market and receive the entire balance as "overpayment," draining supplier liquidity without repaying anything. The test explicitly asserts the whole `custody_before` was drained and `credited == 0`.

### Likelihood Explanation
A single unprivileged address can submit `repay(payer, amount)` with `amount` set to the pool's token balance against any hub market with no outstanding debt (a freshly listed market, or any market fully repaid). No privileged role, oracle manipulation, or multi-step setup is required — zero debt is a normal, recurring market state. The analogous `recapitalize` path (`contracts/pool/src/ops/recapitalize.rs:52-55`) has the same shape: `applied = amount.min(backing_shortfall)` is zero when there is no shortfall, so `refund = amount`, again refunded from custody without a funding check.

### Recommendation
Measure the actual inbound balance delta for the repay/recapitalize leg (or require the controller's measured-receipt transfer to be proven inside the same call) before honoring any refund, rather than deriving `overpayment`/`refund` purely from the declared `amount`. Alternatively, treat the refund as `min(declared_excess, actual_inbound)` and add an explicit guard that a `repay` on a zero-debt position with no verified inbound transfer cannot produce a positive `transfer_out` — the equivalent of the suggested `require(adjustedRectangle != 0)` is `require(inbound == amount || overpayment == 0)` at the funding boundary.

### Proof of Concept
Conceptual trace (mirroring `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`):
1. Attacker picks a hub market where `borrowed == 0` and pool token custody is `B`.
2. Calls `repay(attacker, PoolAction { amount: B, .. })` without the controller transferring `B` in.
3. `resolve_repay`: `current_debt_ceil = 0` → `overpayment = B`, `burned = pos_scaled = 0`.
4. `net_repay = B - B = 0` → `RepayRoundsToZeroShares` assert passes on `net_repay == 0`; `credit_cash(0)`; commit.
5. `apply` executes `transfer_out(attacker, B)` — the pool's entire real custody moves to the attacker while `cash` still reports `B`, leaving suppliers' shares unbacked.

Note on uncertainty: I did not fully verify whether `pool::repay` is gated to the controller (the test calls it directly, implying it is reachable), and whether the controller always pre-funds the declared amount — if it does, the residual issue is that the pool trusts the declared amount instead of the measured receipt, which still leaves the refund derivable from an unverified parameter in any path that skips the funding step.
