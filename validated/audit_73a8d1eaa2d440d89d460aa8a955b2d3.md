### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator.validate` to authenticate inbound webhooks, but its `to_signable_string` only returns the raw HTTP body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all read from HTTP headers and handed to the merchant's webhook handler as trusted, tenant-identifying data — are never part of the signed material, so they can be forged independently of the HMAC check.

### Finding Description
`HmacValidator.validate` authenticates any `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it (with `OpenSSL.secure_compare`) to the caller-supplied `hmac`: [1](#0-0) 

For `ShopifyAPI::Auth::Oauth::AuthQuery`, `to_signable_string` covers every identity-relevant field, including `shop`: [2](#0-1) 

But `ShopifyAPI::Webhooks::Request`, which implements the same interface, signs only the raw body — `shop`, `topic`, `webhook_id`, and `api_version` are all sourced from unauthenticated HTTP headers and are excluded from the signable string: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts these header-derived values to build the `WebhookMetadata` passed to the app's handler, using `request.shop` and `request.topic` as the tenant/topic identity for whatever business logic the handler implements: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret shared across every merchant installation (not per-shop), any unprivileged attacker who installs the app on their own store receives a genuinely-signed webhook (valid `hmac-sha256` header for a given raw body, computed with the app's secret). The equality the code is implicitly relying on is:
`HMAC-verified(raw_body) == HMAC-verified(raw_body, shop, topic, webhook_id)`
but only the left side is true — `shop`/`topic`/`webhook_id` are parsed from headers, never verified. An attacker can therefore replay that same raw_body + valid hmac header pair to the victim app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim, shop domain. `Utils::HmacValidator.validate(request)` still returns true (body unchanged), yet `Registry.process` dispatches the handler with attacker-chosen `shop`/`topic` values.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to provide: an app receiving webhooks cannot trust `WebhookMetadata#shop` as proof that the event actually originated from that shop. Any handler logic that keys data updates, cache invalidation, order/customer records, or authorization decisions off `data.shop` (as the gem's own docs and `WebhookMetadata` API encourage) can be manipulated into acting on/for a different merchant's tenant using data an attacker fully controls (their own legitimately-obtained, self-signed webhook body), i.e., cross-tenant access facilitated by this gem's failure to bind the header-derived shop/topic to the signed payload.

### Likelihood Explanation
Any internet user can sign up for a free/dev Shopify store, install a target public app, and trigger events to receive genuinely HMAC-signed webhook deliveries for their own shop. Replaying that request to the app's public webhook endpoint with a modified `shop-domain` (or `topic`/`webhook-id`) header requires no secret material, no privileged account, and no interaction with Shopify's servers — only network access to the target app's webhook URL, which is by design internet-reachable.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable material for webhook HMAC verification (or otherwise bind them cryptographically to the body before trusting them), so that tampering with these headers invalidates the HMAC. At minimum, `Webhooks::Registry.process` should not treat header-derived `shop`/`topic` as verified merely because the raw body's HMAC matches.

### Proof of Concept
1. Attacker installs the target public app on their own Shopify dev store (`attacker-shop.myshopify.com`) and triggers an event so the app sends them a legitimate webhook, e.g. body `{}` with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
2. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — unchanged — and returns `true`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the app to process the event as if it belongs to `victim-shop.myshopify.com`. [4](#0-3) [3](#0-2)
