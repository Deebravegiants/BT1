### Title
Missing caller/ownership validation on pipeline run resumption allows any unauthenticated actor to inject arbitrary task results - (File: core/web/pipeline_runs_controller.go)

### Summary
The `PipelineRunsController.Resume` endpoint (`PATCH /v2/jobs/:ID/runs/:runID`) accepts an attacker-supplied `runID` and an attacker-supplied JSON body containing the task result, and calls `prc.App.ResumeJobV2` with no validation that the caller is authorized to resume that specific run. This mirrors the reported Perp depository bug class: a state-mutating function accepts caller-controlled identifiers/parameters (there `account`, here `runID` + result payload) without checking that the caller is entitled to act on that specific entity, enabling cross-user/unauthorized manipulation of protocol state.

### Finding Description
`Resume` parses the `runID` from the URL, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and immediately calls `prc.App.ResumeJobV2(ctx, taskID, result)` — there is no check binding the request to an authenticated identity that owns or is permitted to complete that specific paused task run: [1](#0-0) 

The route is explicitly flagged by the code itself as unauthenticated via the audit event fired right after the resume call:
```go
prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
``` [2](#0-1) 

The corresponding audit event constant is explicitly named `UnauthedRunResumed`, confirming this endpoint is intentionally reachable without authentication: [3](#0-2) 

This is structurally analogous to the Perp depository's `_rebalanceNegativePnlWithSwap`, which accepted an unvalidated `account` parameter and let any caller direct fund transfers involving that account — here, any caller can supply an arbitrary `runID` (task UUID) and result payload to complete any pending pipeline task run they can discover/guess, without proof that they are the legitimate initiator of that task (e.g., the external adapter that was supposed to callback).

### Impact Explanation
A pending pipeline task (e.g., an HTTP/bridge "wait for external callback" step used by webhook/bridge task flows) is normally expected to be resumed only by the external system that was given the task/run identifier. Because there is no authentication or ownership check tied to the specific `runID`, any actor who obtains or guesses a `runID` can:
- Inject a forged/malicious result value into a job run's task, corrupting downstream computation (e.g., a price feed value, or a value later consumed on-chain).
- Force resumption of runs at will, causing job runs to complete with attacker-controlled data, which can affect fund-moving or state-mutating logic that depends on job pipeline outputs.

This is a cross-user/data-integrity confusion analogous to the account-impersonation issue in the reported bug, though the actual severity depends on how `runID` values are distributed/exposed and how sensitive the resuming task's result data is downstream.

### Likelihood Explanation
The endpoint is reachable via a standard HTTP request; the audit constant `UnauthedRunResumed` and the code's lack of any authenticated-user/EI ownership check indicate this pathway is deliberately unauthenticated. Exploitability then hinges primarily on the attacker's ability to learn a valid `runID` (a UUID), which is a secrecy-of-identifier concern rather than a cryptographic barrier — no permission check exists even if it is known.

### Recommendation
Add an authorization check in `Resume` that verifies the caller is entitled to complete the specific `runID` — e.g., require the request to be authenticated as the specific external initiator/bridge that owns the pending task, or bind resumption to a per-run secret/token generated when the task was created, rather than accepting any caller who supplies the run UUID.

### Proof of Concept
1. Create a job with a task that pauses pipeline execution awaiting an external callback (produces a `runID`/task UUID).
2. Without any authentication, send `PATCH /v2/jobs/:ID/runs/:runID` with an attacker-chosen JSON body matching `pipeline.ResumeRequest`.
3. Observe that `ResumeJobV2` executes and the pipeline run resumes/completes using the attacker-supplied data — no ownership or authentication check is performed, only that `runID` parses as a UUID: [4](#0-3) 

**Uncertainty note:** I was unable to directly confirm within the index which downstream task types (e.g., `bridge`, `http` "async" tasks) are commonly paused/resumed via this endpoint in production configs, nor the exact router-level middleware grouping for this route in `core/web/router.go` (the file exists but its route-group/middleware assignment for this specific path wasn't retrievable from the index). This does not affect the core finding — the handler code itself performs no ownership check and self-labels the action as "unauthed" via the audit event — but a full production-config review to confirm whether any outer middleware wraps this specific route would still be advisable before treating this as fully proven end-to-end in a live deployment.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```
