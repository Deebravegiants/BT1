### Title
Webhook shop and topic identity are unauthenticated by the HMAC, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an HMAC-valid webhook request as fully authenticated and trusts the `shop` and `topic` fields taken from HTTP headers when dispatching to the app's handler. However, the HMAC signature only covers the raw request body — never the `shop-domain` or `topic` headers — so those identity fields can be freely substituted on a request that still passes signature validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator` computes and compares the signature strictly against that signable string: [2](#0-1) 

Meanwhile `shop` and `topic` are read straight from headers, independent of the signed body: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the header-derived, unauthenticated `topic`/`shop` values to the host app's handler as the trusted tenant identity: [4](#0-3) 

The broken binding is: `hmac_valid(raw_body)` == true is treated as proof that `(shop, topic, raw_body)` as a triple came from Shopify for that shop/topic, when in fact only `raw_body` is bound to the secret. The gem's own documentation reinforces this false equivalence, stating that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop`/`data.topic`: [5](#0-4) 

Because any Shopify merchant (an unprivileged, non-victim tenant) can install the app on their own store and receive genuinely-signed webhooks for their own shop, they possess valid `(raw_body, hmac)` pairs. Since `shop-domain` and `topic` are excluded from the signed content, that same body+HMAC can be replayed against the app's single shared webhook endpoint with a forged `shop-domain` header pointing at a victim shop (or a forged `topic` to redirect to a different handler). `HmacValidator.validate` still returns `true`, and `Registry.process` will call the handler with attacker-chosen `shop`/`topic` metadata alongside data the attacker controls (their own store's `raw_body` content), which the host app processes as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an unprivileged app-installing merchant can inject fabricated webhook events attributed to a shop they do not own, without any access token, leaked secret, or TLS interception — only the ability to install the app themselves and capture their own legitimate webhook traffic. This is a cross-tenant data-injection vector (Critical: cross-tenant access), since the identity used for tenant routing (`shop`) is not part of the cryptographically verified content.

### Likelihood Explanation
Any developer/tester can install a Shopify app on a free development store, trigger events (e.g. `orders/create`) to receive real signed webhooks, and then replay the captured body/HMAC pair with modified `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers directly to the app's public webhook endpoint. No special privileges beyond ordinary app installation are required, making this practically exploitable by any actor who can install the app.

### Recommendation
Bind the `shop` (and ideally `topic`) identity into the value verified against the HMAC — e.g., recompute/verify the signature using a signable string that incorporates the shop domain and topic, or require the host application (and this gem) to cross-check the `shop-domain` header against a known/expected recipient before trusting it for tenant routing. At minimum, document prominently that `shop`/`topic` are NOT covered by the HMAC and must not be used to make tenant-authorization decisions without independent verification (e.g., checking the shop is one this app is actually installed on and has a stored, currently-registered webhook for that exact topic/id).

### Proof of Concept
1. Install the app on attacker-owned store `attacker.myshopify.com`; trigger an `orders/create` event to receive a legitimate webhook: 
   `raw_body = B`, headers include `x-shopify-hmac-sha256: H = HMAC-SHA256(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the exact same `raw_body = B` and `x-shopify-hmac-sha256: H` to the app's shared webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only — it matches `H`, so validation succeeds.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` calls the registered handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, which the host app (per the gem's documented usage pattern) will persist/act on as data belonging to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
