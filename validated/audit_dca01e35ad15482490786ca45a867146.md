## Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` headers are used for processing decisions but are not bound by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but the identity/routing fields used to dispatch and label the payload (`shop`, `topic`, `api_version`, `webhook_id`) are read directly from HTTP headers that are **not** part of the signed message. This breaks the identity binding `hmac_verified(body) == (shop, topic, webhook_id bound to body)` and allows a party who possesses one genuinely-signed webhook (e.g., a merchant on their own store, which is a legitimate but unprivileged tenant of the app) to relabel that request as coming from a different shop or topic while the HMAC still validates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry#process` trusts this validation and then dispatches using the unauthenticated header-derived `shop`/`topic`/`webhook_id`/`api_version`: [4](#0-3) 

Because the HMAC is computed with the app's `client_secret`, which is shared across **every** shop that installs the app, any tenant that legitimately receives a webhook (with a genuinely valid HMAC over that request's body) can capture that `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting a different `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` header. `HmacValidator.validate` still returns `true` because the body bytes and HMAC are unchanged, but the app's handler processes the body under an attacker-chosen shop/topic identity.

This is the same class of bug as the reference finding: a value used to make a security/identity decision (there, the collateral amount transferred via reentrancy vs. amount to reduce; here, the `shop`/`topic` used for routing) is not covered by the guard that is supposed to make the operation trustworthy (there, `onlyOwner` without `nonReentrant`; here, HMAC validation without covering the header fields).

### Impact Explanation
This crosses a tenant boundary: a shop that has legitimately installed the app can cause the app's webhook handler to process attacker-supplied body content while it's labeled as originating from any other shop domain and any topic of the attacker's choosing, since none of `shop`, `topic`, `webhook_id`, `api_version` are authenticated. Depending on how the host application keys its persistence/business logic off `WebhookMetadata#shop` and `#topic` (which this gem hands directly to the registered handler), this enables cross-tenant data injection or corruption — data intended for shop A's handler logic can be attributed to shop B. This matches the "Cross-tenant access" Critical-tier impact category.

### Likelihood Explanation
Requires only that the attacker control (or previously receive) one genuinely-triggered webhook from their own installed instance of the app — an ordinary, unprivileged capability for any merchant using the app — and be able to send a forged HTTP request to the app's public webhook endpoint with modified headers and the captured `(body, hmac)` pair. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed/verified material (or otherwise cryptographically bind them to the body, e.g. by validating them against Shopify's known webhook delivery metadata rather than trusting client-supplied headers), so that `HmacValidator.validate` fails if any of these routing fields are altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on their own store, `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates an order) and captures the genuine webhook POST, including `@raw_body` and the valid `shopify-hmac-sha256` header (computed by Shopify using the app's shared `client_secret`).
3. Attacker resends this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` and/or a different `shopify-topic`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (body+HMAC still match) as shown in [5](#0-4) .
5. `Registry#process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged header values, causing the app to process attacker-controlled data under the victim shop's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
