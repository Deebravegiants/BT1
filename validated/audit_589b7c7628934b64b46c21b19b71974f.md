### Title
Unchecked UTF-8 conversion of attacker-controlled cross-chain message body creates invalid `String` values and undefined behavior - (File: `modules/pallets/demo/src/lib.rs`)

### Summary
`pallet-ismp-demo`'s `IsmpModule::on_accept` callback converts the raw, attacker-controlled `PostRequest.body` into a `String` using `String::from_utf8_unchecked` whenever the request's source is any `StateMachine::Evm(_)`, without validating that the bytes are well-formed UTF-8. This is the same bug class as ALPINE-CVE-2019-19221 in libarchive: an unchecked/insufficiently-checked multi-byte-to-string conversion on attacker-supplied data, which produces a string value that violates its encoding invariant and leads to out-of-bounds/undefined behavior when consumed downstream.

### Finding Description
`on_accept` dispatches on `request.source`: [4](#0-3) 

For any `StateMachine::Evm(_)` source, the entire `request.body` — fully attacker-controlled via a relayed ISMP `PostRequest` from any EVM chain — is passed to `String::from_utf8_unchecked` and stored directly into the `Event::Request { data: String, .. }` runtime event: [5](#0-4) 

`String::from_utf8_unchecked` is `unsafe` precisely because the Rust standard library, and every safe API built on `str`/`String` (`.len()`, slicing, `chars()`, iteration, SCALE `Encode`/`Decode`, JSON/RPC serialization, indexing), assumes the byte buffer is valid UTF-8. Supplying arbitrary bytes — as any EVM-side dispatcher can, since `body` is fully attacker-chosen application payload — creates a `String` whose invariant is broken. This is the direct structural analog of the libarchive bug: `archive_wstring_append_from_mbs` called `mbrtowc`/`mbtowc` without validating the source bytes as a legal multi-byte sequence for the current encoding, producing out-of-bounds reads when the malformed multi-byte data was subsequently processed as wide characters. Here, the "incorrect encoding conversion" is `from_utf8_unchecked` instead of the checked `String::from_utf8`, and the "subsequent processing that assumes validity" is every consumer of the resulting `Event::Request.data` field (RPC event subscribers, block explorers, indexers, or any future code path that slices/iterates the string by byte offset assuming char-boundary alignment).

The pallet is not test-only scaffolding: `pallet_ismp_demo` is compiled into and wired into both the `gargantua` and `nexus` production parachain runtimes as `IsmpDemo`, receiving dispatch through the standard `pallet-ismp` router for any `PostRequest` addressed to `PALLET_ID` (`b"ismp-ast"`).

### Impact Explanation
Any external EVM chain (an unprivileged message dispatcher on that chain) can relay a `PostRequest` targeting the demo module's `PALLET_ID` with a non-UTF-8 body. Once accepted by `pallet-ismp`'s consensus/proof verification (a legitimate, already-finalized state proof — no privileged actor required), `on_accept` executes `String::from_utf8_unchecked` on that payload, producing a `String` that breaks Rust's UTF-8 invariant. This is undefined behavior at the language level and, depending on how the runtime/indexer/RPC layer subsequently touches this event field (byte-offset slicing, char iteration, re-encoding), can manifest as out-of-bounds reads, panics, or corrupted output — mirroring the CVE's "out-of-bounds read... crafted archive crashes" scenario, but on the parachain's event pipeline. Because the runtime node's RPC/event-subscription surface is externally reachable and any panic there can take down the query path, this is a concrete availability/soundness issue reachable from a single relayed request rather than a purely theoretical or low-impact one.

### Likelihood Explanation
High likelihood of triggering the unsafe invariant violation: any actor controlling an EVM chain that is a valid ISMP source state machine can construct a `PostRequest.body` with arbitrary bytes (e.g. a lone continuation byte or truncated multi-byte sequence) and have it relayed once finalized on that source chain — no special privilege, governance, or malicious-node assumption is needed, only a normal dispatch + relay + proof-verification flow that pallet-ismp already supports.

### Recommendation
Replace `unsafe { String::from_utf8_unchecked(request.body) }` with the checked `String::from_utf8(request.body)`, rejecting (or lossily substituting via `String::from_utf8_lossy`) bodies that are not valid UTF-8 instead of constructing an invariant-violating `String`. Reject the request or emit a distinct bytes-based event when decoding fails, keeping the `on_accept` callback fully safe and total on all attacker-supplied `body` values.

### Proof of Concept
1. On a whitelisted EVM source state machine, dispatch (or fabricate a proof for) a `PostRequest` addressed to `PALLET_ID` (`b"ismp-ast"`) on the target parachain, with `body = [0xC0]` (a lone leading byte of a 2-byte UTF-8 sequence with no continuation byte — invalid UTF-8).
2. Relay the request through the normal ISMP pipeline; `pallet-ismp`'s router verifies the consensus/state proof and calls `IsmpModuleCallback::on_accept`.
3. Because `source_chain` matches `StateMachine::Evm(_)`, the code executes `unsafe { String::from_utf8_unchecked(request.body) }` at [6](#0-5) , producing an invariant-violating `String` and depositing it in `Event::Request`.
