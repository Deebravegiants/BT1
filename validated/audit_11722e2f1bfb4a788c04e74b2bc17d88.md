### Title
Webhook `shop`/`topic` header fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook request by calling `Utils::HmacValidator.validate(request)` and, on success, dispatches the event to the app's handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` taken straight from HTTP headers. The HMAC signature, however, is computed only over the raw request body (`Request#to_signable_string` returns `@raw_body`), so none of these header-derived identity fields are cryptographically bound to the signature that "verifies the request did indeed come from Shopify." An attacker who can trigger one legitimately-signed webhook (e.g., on their own store, which any merchant/developer can freely do) can replay the exact same body/HMAC pair while substituting the `shop-domain` (and `topic`/`webhook-id`) header to impersonate any other shop served by the same multi-tenant app, since a single app-wide `api_secret_key` signs webhooks for every shop.

### Finding Description
`HmacValidator.validate` computes the expected signature as: [1](#0-0) 

and the signable string for a webhook `Request` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all parsed from HTTP headers that are never included in the signed material: [3](#0-2) 

`Registry.process` trusts these unauthenticated header fields once the body HMAC checks out, and forwards them directly to the app's handler as the identity of the event: [4](#0-3) 

The documented binding is: `hmac_valid(body) == true` implies `shop_header == origin_shop`. In reality the HMAC only proves `hmac_valid(body) == true` implies `body == body_signed_by_shopify`; it says nothing about which shop's header the request carries. Because a single app-wide `Context.api_secret_key` signs webhook bodies for *every* shop that installs the app, a valid `(body, hmac)` pair obtained from one shop remains valid when replayed with a different `shop-domain` header pointing at another shop.

The gem's own documentation reinforces the false assumption, stating that calling `Registry.process` "will verify the request did indeed come from Shopify" and showing sample handler code that forwards `data.shop` downstream unconditionally: [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged internet user who is a merchant/developer with the target app installed on their own store can obtain a genuine, correctly-signed webhook body for that store. They can then send an HTTP request directly to the app's public webhook endpoint with that same body/HMAC but with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` invokes the app's handler with `data.shop` set to the victim's domain and attacker-controlled `data.body`. Any host application that follows the gem's documented pattern (attributing/writing data keyed by `data.shop`) will process attacker-controlled content under the victim tenant's identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Likelihood is high: no secrets, access tokens, or privileged accounts are required — only the ability to install the target app on any store (trivial for a developer/merchant) to harvest one valid signed body, and the ability to send an arbitrary HTTP request with modified headers to the app's public webhook route.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, at minimum) in the HMAC-signed material, or independently verify `request.shop` against the shop associated with the webhook subscription/session before trusting it, rather than relying solely on a body-only signature to authenticate header-derived fields. At minimum, document prominently that `data.shop`/`data.topic` are NOT authenticated by the HMAC check and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
```ruby
# 1. Attacker installs target app on their own store "attacker-shop.myshopify.com"
#    and receives a legitimate webhook, capturing:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the exact same body/HMAC to the app's public webhook
#    endpoint, but swaps the shop-domain header to the victim's shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,           # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only body is checked),
#    handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
#    is invoked with attacker-controlled body attributed to the victim shop.
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
