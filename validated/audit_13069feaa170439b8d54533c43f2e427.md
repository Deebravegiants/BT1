### Title
Webhook shop-domain identity spoofing via HMAC not covering `X-Shopify-Shop-Domain` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` value handed to the app's `WebhookHandler` is read from an unauthenticated HTTP header that is never covered by that HMAC. This breaks the identity binding `shop_verified_by_hmac == shop_delivered_to_handler`, allowing a webhook that was legitimately signed for one shop to be replayed with a different, attacker-chosen `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the webhook exclusively against this signable string: [2](#0-1) 

and `HmacValidator.validate` computes/compares the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body), never touching `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signed body: [4](#0-3) 

After HMAC validation succeeds, `Registry.process` builds `WebhookMetadata` directly from this unauthenticated `request.shop` and hands it to the app's registered `WebhookHandler#handle`: [2](#0-1) [5](#0-4) 

The library's own test fixture demonstrates that the HMAC is computed purely from the body (`"{}"`) independent of the `shop-domain` header value, confirming the header can be freely substituted without invalidating the signature: [6](#0-5) 

This means: the equality that should hold — "the shop that Shopify computed the HMAC for" == "the shop passed to the app's business logic" — does not hold. Any party who can obtain one valid `(raw_body, hmac)` pair for *any* shop (e.g., by installing the app on their own store and receiving Shopify's own webhook for that store) can resend that exact body/HMAC pair to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop. `HmacValidator.validate` will still pass because it never inspects the header, and the app's handler will execute business logic under the (forged) victim tenant identity.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability. An unprivileged internet user who has legitimate access to their own Shopify store (and thus receives real, validly-signed webhooks from Shopify for topics with predictable/empty/identical bodies, e.g. `app/uninstalled`, `shop/redact`, `app/scopes_update` or any topic whose payload the attacker can normalize) can replay that valid `(body, hmac)` pair against the target app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop. Any app logic keyed off `WebhookMetadata#shop` (session/token revocation, data deletion, GDPR redaction, entitlement changes, cache invalidation, audit logging, etc.) will be executed against the victim's tenant data using an attacker-controlled identity, i.e. cross-tenant access/manipulation without any credential belonging to the victim. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for topics whose payload is a fixed or attacker-influenceable structure (e.g., `app/uninstalled` typically carries a minimal, near-constant body across installs), since the attacker fully controls when to trigger the topic in their own store and can capture the exact `(raw_body, hmac)` values via a normal webhook delivery to infrastructure they control, then replay them at will with a forged shop header to the target app's public endpoint. No secret material belonging to the victim or the app owner is required — only the ordinary ability to install the target app on the attacker's own shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, or otherwise cryptographically tie the header to the signed payload before trusting it for authorization decisions:
- Include the `X-Shopify-Shop-Domain` header (and topic) in the signable string used by `HmacValidator`, or
- Cross-check the header-derived `shop` against an independent, previously-established mapping (e.g., the shop associated with the specific webhook subscription/`webhook_id` as registered via the Admin API) before invoking the handler, rejecting the webhook if they disagree.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers (or waits for) Shopify to deliver a webhook, e.g. `app/uninstalled`, with body `raw_body` and header `X-Shopify-Hmac-Sha256: HMAC(app_secret, raw_body)` — captured by an endpoint the attacker controls.
3. Attacker sends a direct HTTP POST to the app's public webhook endpoint with:
   - Body: the exact `raw_body` captured in step 2
   - Header `X-Shopify-Hmac-Sha256`: the exact HMAC captured in step 2
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: `app/uninstalled`
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only signs `raw_body`. [2](#0-1) 
5. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and executes uninstall/cleanup/redaction logic against the victim's tenant, even though Shopify never sent this webhook for that shop.

          received_signature = verifiable_query.hmac
