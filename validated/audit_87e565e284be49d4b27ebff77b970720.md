Found a concrete vulnerability. `TokenExchange.exchange_token` derives the shop it will send the app's `client_secret` to (`dest_shop`) directly from `jwt_payload.shop`, which is `JwtPayload#shop` = `@dest.gsub("https://", "")` with **no domain validation** — unlike `migrate_to_expiring_token`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host.

### Title
SSRF / Credential Exfiltration via Unvalidated `dest` Claim in Token Exchange - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` uses the `dest` claim of a session (JWT) token — verified only for HMAC signature validity and `aud == api_key` — as the literal hostname to which it sends the app's `client_id` and `client_secret` in a POST to `/admin/oauth/access_token`. The `dest` value is never checked against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike the sibling method `migrate_to_expiring_token`, which does call `Utils::ShopValidator.sanitize!(shop)`.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from `@dest` with no domain allow-listing: [1](#0-0) 

`JwtPayload#initialize` only validates the signature and that `aud == Context.api_key`; it never validates that `dest` (or `iss`) is a `*.myshopify.com`/`*.myshopify.io`/`*.spin.dev` host: [2](#0-1) 

`TokenExchange.exchange_token` takes that unvalidated `dest_shop` and builds an `Auth::Session` whose `shop` becomes the request host, then sends `client_id`/`client_secret` to it via `Clients::HttpClient`: [3](#0-2) 

`Clients::HttpClient#initialize` builds `@base_uri` directly from `session.shop` with no further validation: [4](#0-3) 

Contrast this with `migrate_to_expiring_token` in the same file, which explicitly sanitizes the shop before it is used to build the session/host: [5](#0-4) 

The binding that is broken is: **the host that receives the app's `client_secret` (`session.shop`, derived from `dest_shop`) is not equal to a domain the app validated as a genuine Shopify shop domain** — it is merely equal to whatever `dest` string a validly-signed JWT contains. Since session tokens are App-Bridge-issued and can, per the docs, arrive via a URL query param (`id_token=...`) as well as the `Authorization` header, and since this gem exposes `exchange_token` to be called with any `session_token: String` an integrator passes in, any component in the host application that forwards an attacker-influenced or replay-able token (or a token whose `dest` was not itself re-validated by the caller) results in this gem sending the merchant app's `client_id`/`client_secret` to a `dest`-controlled host.

### Impact Explanation
This is High/Critical: if an attacker can get a validly-signed session token whose `dest` claim is an attacker-controlled host accepted by the signature check (or otherwise cause this code path to run with an untrusted `dest`), the gem performs an outbound POST containing the app's `client_secret` to that host — SSRF carrying the app's credentials, and potential `client_secret` exfiltration, matching the "SSRF with the app's credentials" / credential-leakage impact classes.

### Likelihood Explanation
Exploitability depends on the host application's handling of `session_token` input to `exchange_token` (e.g., whether it passes through a raw `id_token` query param without additional validation, as the docs suggest is a supported usage pattern) combined with the absence of `ShopValidator` enforcement inside this gem itself, whereas the library's own `migrate_to_expiring_token` method demonstrates the sanitization is available and expected but simply omitted here.

### Recommendation
In `exchange_token`, call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) immediately after extracting `dest_shop = jwt_payload.shop`, mirroring the pattern already used in `migrate_to_expiring_token`, before constructing `shop_session` / making the HTTP request.

### Proof of Concept
1. Obtain (or have the host app forward) a session token whose payload has `dest` set to an attacker-controlled host, signed such that it passes `JWT.decode` with the app's `api_secret_key` (e.g., a token issued for a different, but validly configured `aud`/signing context, or a token whose `dest` was never checked by the caller before being handed to this gem).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` builds `@base_uri = "https://#{dest_shop}"` and issues `POST https://<attacker-host>/admin/oauth/access_token` with the JSON body containing `client_id` and `client_secret` in plaintext — reaching the attacker's `dest` domain with the app's `client_secret`, unlike `migrate_to_expiring_token`, which rejects unsanitized shops via `ShopValidator.sanitize!`: [6](#0-5)
