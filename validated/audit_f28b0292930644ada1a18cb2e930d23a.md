### Title
Relayer rewards for already-completed deliveries can be zeroed before claim, permanently forfeiting earned rewards - (File: `modules/pallets/relayer/src/outbound_request.rs`, `modules/pallets/relayer/src/outbound_consensus.rs`)

### Summary
`OutboundRequestDeliveryReward` and `OutboundConsensusDeliveryReward` are read at **claim time**, not at delivery time. A relayer that has already delivered a hyperbridge-originated request (or a mandatory consensus rotation) to a destination chain — burning gas and completing the on-chain work required to earn the reward — can have that reward permanently zeroed out by a routine governance call before they submit their claim, causing the relayer to lose compensation for work already rendered.

### Finding Description
The claim path for a hyperbridge-originated request looks up the reward amount live, against current storage, rather than a value fixed at delivery time: [1](#0-0) 

The same pattern exists for consensus-rotation delivery rewards: [2](#0-1) 

Both rewards are governance-mutable at any time via unbounded calls that immediately overwrite the map entry with no delay, no snapshot, and no protection for deliveries that already occurred: [3](#0-2) [4](#0-3) 

The flow is: (1) relayer delivers a `PostRequest` or consensus proof to the destination, which is recorded in `RequestCommitments`/`EvmHost._epochs[set_id]`, (2) before the relayer submits `claim_outbound_request_delivery_reward` / `claim_outbound_consensus_delivery_reward`, governance calls `set_outbound_request_delivery_reward(module_id, 0)` or `set_outbound_consensus_delivery_reward(state_machine, 0)` — e.g. to disable a module or rebalance incentives — (3) when the relayer finally submits their claim, `OutboundRequestDeliveryReward::<T>::get(&module_id)` / `OutboundConsensusDeliveryReward::<T>::get(destination)` now returns `0`, causing the claim to be rejected with `OutboundRequestNoRewardConfigured` / `OutboundNoRewardConfigured`, even though the underlying delivery commitment/receipt is still verifiably valid. There is no `OutboundRequestsClaimed`/`OutboundConsensusRotationsClaimed` entry, so the delivery is treated as if it were never rewarded, and the reward the relayer earned is unrecoverable — the same class of loss described in the reference report, where governance clearing a reward configuration destroys a user's ability to claim rewards they already accrued.

### Impact Explanation
Relayers who have already performed the incentivized work (delivering a hyperbridge-originated request or consensus rotation, at real gas cost on the destination chain) can permanently lose the promised treasury payout if governance adjusts the reward table before the claim lands — which can happen at any point in the multi-step off-chain pipeline (waiting for the destination state commitment to land on Hyperbridge, building the claim, submitting it). This is a real loss of relayer compensation/reward accounting funds, and undermines the economic incentive model that the entire outbound-request/consensus delivery incentivization system depends on.

### Likelihood Explanation
Reward parameters are expected to be adjusted routinely by governance (enabling/disabling modules, rebalancing incentive amounts) as described in the outbound-request-incentivization design docs, and the claim pipeline inherently has latency (waiting for state-machine updates, proof construction, submission retries) during which such a change can land. No malicious intent is required — an ordinary governance update timed after a delivery but before its claim is sufficient to trigger the loss.

### Recommendation
Snapshot the reward amount at the time the underlying delivery is recorded (or accept the reward value as part of the claim and validate it against a historical record), rather than reading current governance state at claim time. Alternatively, introduce a timelock/grace period before a reward reduction takes effect, and/or preserve the reward rate that was active at the delivery height for any claim referencing that height.

### Proof of Concept
1. Governance sets `OutboundRequestDeliveryReward[module_id] = X` via `set_outbound_request_delivery_reward`.
2. A relayer delivers a `PostRequest` from that module to a destination chain; `RequestCommitments[commitment]` is populated and the destination records the receipt.
3. Before the relayer submits `claim_outbound_request_delivery_reward`, governance calls `set_outbound_request_delivery_reward(module_id, 0)`.
4. The relayer submits the claim with a valid state proof of delivery; `process_outbound_request_delivery_claim` reaches the allowlist check at [5](#0-4)  and rejects with `OutboundRequestNoRewardConfigured`, even though the delivery is real and provable. The reward for that already-completed delivery is permanently lost — the same failure mode as `outbound_consensus.rs` line 174-175 for consensus-rotation rewards.
