Confirmed vulnerability: `Oauth.begin_auth` builds the OAuth authorization redirect URL from an unsanitized `shop` parameter, with no call to `Utils::ShopValidator.sanitize!` (unlike `TokenExchange.migrate_to_expiring_token` and `RefreshToken`/`ClientCredentials`, which do validate). This breaks the intended binding: `shop` used to route the OAuth authorize request should equal a validated `*.myshopify.com` domain, but here it equals whatever the host application passes through, most commonly straight from an unauthenticated query parameter in a Rails/Sinatra controller.

### Title
OAuth `begin_auth` builds authorization redirect from unvalidated `shop` host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` constructs the OAuth `auth_route` by directly interpolating the caller-supplied `shop` string into a URL (`auth_base_uri(shop) + "/oauth/authorize?..."`), with no domain validation, unlike other credential-bearing flows in this gem.

### Finding Description
`begin_auth` takes `shop:` and forms the redirect target via `auth_base_uri`: [1](#0-0) 
`auth_base_uri` simply does `"https://#{shop}/admin"` with no format check on `shop` at all. [2](#0-1) 

Contrast this with the gem's own `Utils::ShopValidator.sanitize!`, which every other flow that reaches a network request with `client_id`/`client_secret` invokes before trusting a `shop` string, e.g. `TokenExchange.migrate_to_expiring_token`: [3](#0-2) 

`begin_auth` has no such check. The redirect URL also embeds `client_id` and `redirect_uri` (built from `Context.host`), which are attacker-influenceable only indirectly, but the primary issue is that the `shop` value—entirely attacker-controlled if the host app passes a request parameter straight through—determines which external host the merchant's browser is redirected to for OAuth authorization. If a host application (following the gem's own documented pattern of taking `shop` from an incoming request) does not itself re-validate the shop domain, `begin_auth` will happily build `https://<attacker-controlled-string>/admin/oauth/authorize?client_id=...&redirect_uri=...`.

### Impact Explanation
This does not by itself leak `client_secret` (that's only added at `validate_auth_callback`, which does correctly gate on `Utils::HmacValidator.validate` against the callback's own HMAC-covered `shop`). However, `begin_auth`'s `auth_route` carries `client_id` and the app's `redirect_uri`, and directs the merchant/browser to an attacker-chosen host, which enables forced/hijacked OAuth completion: an attacker who controls the `shop` value can redirect a merchant's OAuth begin-flow request to an arbitrary host, potentially phishing merchant approval or capturing the authorization `code` that would otherwise legitimately flow back to the real Shopify authorize endpoint. This is a "session fixation or forced OAuth completion" class issue per the impact criteria.

### Likelihood Explanation
Exploitability depends entirely on the host application passing an unauthenticated `shop` request parameter straight to `begin_auth` without its own validation—the gem itself provides `Utils::ShopValidator` but does not enforce its use here, and every comparable network-calling entry point in this same file/module (`validate_auth_callback`, `TokenExchange`, `RefreshToken`, `ClientCredentials`) either validates the shop or is gated by HMAC, making `begin_auth`'s omission stand out as inconsistent within the gem's own defensive pattern.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or equivalent strict `*.myshopify.com` format validation) at the top of `Oauth.begin_auth`, mirroring `TokenExchange.migrate_to_expiring_token`, before it is used to build `auth_base_uri`.

### Proof of Concept
1. Host application implements the standard Shopify OAuth begin route: `get "/auth", to: -> { ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback") }` (this is the documented usage pattern for this gem).
2. Attacker sends the merchant a link: `https://app.example.com/auth?shop=evil.example.com`.
3. `begin_auth` builds `auth_route = "https://evil.example.com/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=https://app.example.com/auth/callback&state=<nonce>"` with no validation that `evil.example.com` is a genuine `*.myshopify.com` shop.
4. The merchant's browser is redirected to the attacker's host with the app's real `client_id` and `redirect_uri` exposed, enabling phishing of OAuth approval or forced completion against a spoofed authorize page.

            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?

          end

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
