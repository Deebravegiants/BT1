### Title
Unsigned cross-chain calldata execution lets any relayer dispatch arbitrary runtime calls as the token recipient/sender - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`HyperFungibleToken::on_accept` decodes an optional `SubstrateCalldata` payload embedded in the bridged ERC-20 message body and, when no `signature` field is supplied, dispatches the attacker-supplied `runtime_call` using `RawOrigin::Signed` derived directly from the message's `from`/`to` bytes, with no cryptographic proof that the account named in the message actually authorized that specific call.

### Finding Description
`on_accept` first authenticates only that the `PostRequest.from`/`source` pair is a registered bridge contract via `ContractToAsset` [1](#0-0) . It then ABI-decodes the message body, mints/transfers tokens to `beneficiary`, and — if `message.data` is non-empty — decodes a `SubstrateCalldata` struct containing an optional `signature` and a `runtime_call` [2](#0-1) .

When `signature` is `Some(..)`, the code verifies it against `beneficiary_bytes` before dispatching, which is correct. But when `signature` is `None`, the origin is derived purely from `message.from` (mapped via `EvmToSubstrate::convert` for EVM sources, or taken directly as 32 raw bytes for Substrate sources) with zero cryptographic authentication of intent for that specific `runtime_call`: [3](#0-2) . The decoded call is only checked against `BaseCallFilter` and then dispatched as `RawOrigin::Signed(origin)`: [4](#0-3) .

The root problem is a trust-boundary violation: `message.from`/`message.to` are attacker/relayer-controlled ABI fields inside the bridged payload, not values that the pallet independently verifies are tied to the entity that actually authorized the accompanying `runtime_call`. The pallet's only gate on the message-carrying contract is that the *bridge contract address* is registered (`ContractToAsset`), which says nothing about who supplied `data`/`runtime_call` for a given transfer. For any bridging flow where the tokens move via an ERC-20 `transferFrom`/allowance pattern (i.e., anyone with an allowance-triggering call can invoke the bridge on behalf of the token owner), the "no-signature" branch allows a third party (the relayer, or anyone who can trigger the bridge send) to attach an arbitrary `runtime_call` that gets executed as the token owner's mapped Substrate account — an unauthorized app action executed with another user's on-chain privilege, since the pallet accepts any relayed post request from the registered contract as sufficient authorization for the embedded call.

This is a structural analog to CVE-2023-28394's bug class ("remote actor causes arbitrary code/command execution with the privileges of the application/another party") — here, cross-chain message delivery causes arbitrary runtime-call execution under an account that never signed off on that specific call.

### Impact Explanation
An attacker able to trigger the bridging path for a victim's tokens (e.g., via an approved allowance, or any flow where `from`/`to` in the message aren't cryptographically bound to the actual caller) can smuggle an arbitrary `RuntimeCall` that is dispatched with `RawOrigin::Signed(victim_account)`. Subject only to `BaseCallFilter`, this can move the victim's other balances, cancel their orders, alter their permissions, or trigger any dispatchable the runtime doesn't explicitly filter — a direct "unauthorized app action" and potential theft-of-funds vector, satisfying High severity per the validation rubric.

### Likelihood Explanation
Reachable from a single relayed `PostRequest` originating from any address registered in `ContractToAsset` (a legitimate bridge contract), requiring only that the message body's `data` field carries a `SubstrateCalldata` with `signature: None` and a `from`/`to` set to a victim's address — something achievable whenever the bridging entry point isn't strictly `msg.sender`-bound on the source chain (e.g. `transferFrom`-based flows, or any relayer-composed message). No governance, admin, or validator privilege is required on the destination side.

### Recommendation
Require a bound, non-optional signature (or equivalent authenticated origin, e.g., derived strictly from `PostRequest.from`/msg.sender-equivalent on the source side with no attacker-controllable `message.from` override) before dispatching *any* `runtime_call`, and include the token amount/recipient/nonce/replay-domain fields in the signed payload so a call can never be dispatched using an identity the message body merely asserts. At minimum, remove the unsigned fallback branch in `module.rs:176-187` and always require `substrate_data.signature` to be present and verified against the account under which `runtime_call` will be dispatched.

### Proof of Concept
1. Ensure a legitimate `HyperFungibleToken` bridge contract on an EVM source chain is registered in `ContractToAsset` for some `local_asset_id`.
2. As attacker, arrange to trigger that contract's bridging entry point for a victim account (e.g., via an ERC-20 allowance the victim granted for ordinary transfers), setting the ABI-encoded body's `data` field to a `SubstrateCalldata { signature: None, runtime_call: <attacker_call> }`, and `from`/`to` set to the victim's address.
3. Relay the resulting `PostRequest` through ISMP to the destination pallet; `on_accept` executes: [5](#0-4) .
4. `<attacker_call>` is dispatched with `RawOrigin::Signed(victim_account)`, with no signature ever checked, because the `None` branch bypasses cryptographic verification entirely.
