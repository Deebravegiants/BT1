### Title
Storage-deposit cache key collision in `DirectBridge` allows cache poisoning that skips required storage deposit, causing withdrawals to fail on-chain - (`packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue()` builds its LRU cache key by naive string concatenation of `contractId` and `accountId` with no delimiter. Because NEAR account IDs can contain the same character set used to join the two fields, two different `(contractId, accountId)` pairs can produce an identical cache key. An attacker who controls one side of such a collision can poison the shared cache so that a legitimate user's storage-deposit fee estimate for a *different* token/account pair is answered from the attacker's cached (and always "sufficient") entry, causing the fee estimator to report `storageDepositFee: 0n` when a real deposit is actually required.

### Finding Description
`getCachedStorageDepositValue()` computes: [1](#0-0) 

```
const key = `${contractId}${accountId}`;
```

There is no separator between `contractId` and `accountId`, so `contractId1 + accountId1 === contractId2 + accountId2` is possible whenever the split point differs (e.g. `contractId="usdc.ne"`, `accountId="artest.near"` collides with `contractId="usdc.near"`, `accountId="test.near"`). The cache (`this.storageDepositCache`, an `LRUCache` instance-level field, see lines 51-54) is shared across all calls made through the same `DirectBridge` instance, i.e., across all users a relayer/backend serves with one long-lived instance.

Critically, entries are only written into the cache when the balance is already sufficient:

```
if (result[1] >= result[0]) {
    this.storageDepositCache.set(key, result);
}
```

so any cache hit always yields `minStorageBalance <= userStorageBalance`, which `estimateWithdrawalFee()` (lines 194-268) turns into `storageDepositFee: 0n`. An attacker can therefore deploy/own an NEP-141-like account whose id is chosen so that `contractId_attacker + accountId_attacker` (both attacker-controlled and satisfying `result[1] >= result[0]` trivially) equals the concatenation of a real token contract id and a real victim destination account id. Once this poisoned entry is cached, any subsequent legitimate `estimateWithdrawalFee`/withdrawal for the real `(realToken, realDestination)` pair hits the same key and is told no storage deposit is needed, even though the destination account has not actually registered storage on the real token contract.

### Impact Explanation
When the withdrawal is executed with `storageDepositFee: 0n`, `createWithdrawalIntents()` (lines 110-149) builds the withdrawal intent without any `storage_deposit`, via `getUnderlyingFee(...,"storageDepositFee")`. On NEAR, `ft_transfer_call`/`ft_withdraw` to an account lacking storage registration on the token contract will fail. The victim's withdrawal thus reverts/fails on-chain, leaving it stuck until the user manually performs the storage deposit and retries — this matches the "withdrawal stuck until manual intervention" High-impact category.

### Likelihood Explanation
This requires: (1) the `DirectBridge` instance to be shared/long-lived across multiple users (the standard deployment pattern that motivates having the cache at all), (2) an attacker to control or create an account/contract id whose concatenation with a chosen accountId collides with a real `(tokenContractId, victimAccountId)` pair, and (3) the attacker's request to populate the cache before the victim's request. NEAR account-id naming rules make constructing such a collision straightforward (just choose where to split), and deploying an arbitrary account/contract on NEAR is permissionless. No privileged access is required — this is purely a missing-uniqueness-check bug analogous to `addExistingRollup()` overwriting `rollupAddressToID` without verifying uniqueness.

### Recommendation
Use a delimiter that cannot appear ambiguously, or a structured key, e.g.:
```
const key = `${contractId}:${accountId}`;
```
(consistent with how `OmniBridge` already keys its caches with `:`, see `destinationChainAddressCache` key `` `${omniChainKind}:${contractId}` `` in `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:770`). Even with a delimiter, prefer a non-ambiguous encoding (e.g., JSON-stringifying `[contractId, accountId]` or using a `Map<string, Map<string, ...>>`) since NEAR account IDs may contain arbitrary characters allowed in the ID charset including the chosen delimiter.

### Proof of Concept
1. Attacker chooses `contractId = "usdc.ne"`, `accountId = "artest.near"` such that concatenation `"usdc.neartest.near"` equals the concatenation of the real pair `contractId = "usdc.near"`, `accountId = "test.near"`.
2. Attacker deploys/owns an NEP-141-compatible contract at `usdc.ne` and registers storage for `artest.near` on it so `getNearNep141StorageBalance` returns a value `>= getNearNep141MinStorageBalance`.
3. Attacker calls `estimateWithdrawalFee({ withdrawalParams: { assetId: "nep141:usdc.ne", destinationAddress: "artest.near", ... } })` on the shared `DirectBridge` instance. This populates `storageDepositCache` with key `"usdc.neartest.near" -> [min, sufficientBalance]`.
4. A legitimate user later calls `estimateWithdrawalFee({ withdrawalParams: { assetId: "nep141:usdc.near", destinationAddress: "test.near", ... } })`, where `test.near` has NOT registered storage on the real `usdc.near` contract.
5. `getCachedStorageDepositValue("usdc.near", "test.near")` computes the same key `"usdc.neartest.near"`, hits the poisoned cache entry, and returns `storageDepositFee: 0n`.
6. The resulting withdrawal intent omits the storage deposit; the on-chain `ft_transfer_call` to `usdc.near` for `test.near` fails, leaving the withdrawal stuck until the user manually deposits storage and retries.

```typescript
	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
```
