### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is taken from unauthenticated HTTP headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from HTTP headers that are never included in that HMAC computation. This breaks the identity binding between "the bytes Shopify actually signed" and "the tenant (`shop`) the gem hands to the application's webhook handler," analogous to the reported bug class where an unvalidated identity field (`onBehalfOf`) is trusted without being covered by the authorization check that is supposed to bind it.

### Finding Description
`Registry.process` validates a webhook exclusively via: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only the raw HTTP body — never the `shop`, `topic`, or `webhook-id` values: [3](#0-2) 

Those identity fields are instead read straight from attacker-controllable HTTP headers with no cryptographic binding to the body or to each other: [4](#0-3) 

After `HmacValidator.validate` succeeds (which only proves the *body* bytes were signed by Shopify with the app secret), `Registry.process` passes the *header-derived* `shop` straight to the application handler as the tenant identity, with no re-check that this `shop` corresponds to the shop that actually produced the signed body: [1](#0-0) 

Because the app's webhook HMAC secret (`Context.api_secret_key`) is a single **per-app** secret shared across every merchant install — not a per-shop secret — a signature computed over a given raw body is valid regardless of which shop header accompanies it. An attacker who controls (or has installed) their own shop instance of the app can capture one of their own legitimately-signed webhook deliveries (valid `hmac-sha256` over their own body) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop, or crafted `x-shopify-shop-domain`/`x-shopify-topic` values not present in the signed body at all. `HmacValidator.validate` still returns `true` because the header is not part of `to_signable_string`, and the handler receives `WebhookMetadata` claiming the event belongs to the victim shop.

The equality the report's bug class demands: "shop authenticated" (⇔ the bytes actually verified, i.e., `@raw_body`) must equal "shop the code acts on" (⇔ `request.shop`, from `Request#shop`, `lib/shopify_api/webhooks/request.rb:20-23`). These are demonstrably not the same value/scope, breaking the binding.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as documented/intended, e.g. to look up per-shop records, sync inventory, or process merchant data) can be made to attribute a webhook payload to the wrong tenant. This is a cross-tenant access/confusion vector using only bytes the attacker legitimately received for their own shop plus a forged header — no `api_secret_key`, access token, or privileged access is required beyond having the app installed on one's own (possibly free-trial) shop.

### Likelihood Explanation
Requires only an app installation the attacker controls (any developer/merchant can install the target's public Shopify app) and the ability to send arbitrary HTTP headers to the webhook endpoint alongside a captured, validly-HMAC'd raw body from their own store — no cryptographic secret, TLS interception, or social engineering needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string that is HMAC-verified (or otherwise cryptographically bind them to the body), so `Registry.process` cannot be tricked into associating a validly-signed body with an unauthenticated shop/topic pair.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays this exact `(B, HMAC)` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since header changes don't affect `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-controlled data under the victim tenant's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
