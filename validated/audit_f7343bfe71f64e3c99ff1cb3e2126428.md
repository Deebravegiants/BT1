### Title
Accrual `scaled_to_original` overflow permanently freezes a saturated market before the borrow-index cap engages - (File: common/src/rates/scaling.rs)

### Summary
The CVE class is a crash triggered by a specific but legitimate input combination (DISTINCT + window function + ORDER BY → panic). The XOXNO Lending analog: every state-mutating entrypoint on a pool market first runs interest accrual (`interest::global_sync`), and `accrue_step` unconditionally computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. `scaled_to_original` is `Ray::mul`, which panics with `GenericError::MathOverflow` on i128 overflow. A market with a very large scaled book (`supplied`/`borrowed` near the finite RAY value capacity) at sustained high utilization overflows the i128 value ceiling while `borrow_index` is still far below `MAX_BORROW_INDEX_RAY`. Once the stored state crosses the cliff, `accrue_step` panics on every subsequent call, so `withdraw`, `repay`, `liquidate`, `borrow`, `supply`, `flash_loan`, `update_indexes`, and `clean_bad_debt` all revert for that market forever — a complete, permanent freeze of all user funds in the market, reachable entirely through unprivileged `supply` and `borrow` calls plus elapsed time.

### Finding Description
`scaled_to_original` (`common/src/rates/scaling.rs:14-16`) multiplies scaled RAY shares by the index with `scaled.mul(env, index)`, which panics on overflow via `checked_add_raw`/the `Ray` checked ops (`common/src/math/fp.rs:13-25`). `accrue_step` (`common/src/rates/simulate.rs:60-61`) calls it on `borrowed` and `supplied` at the top of every compounding step, before any rate math, and `global_sync` (`contracts/pool/src/interest.rs:20-33`) runs `accrue_step` at the head of every mutating pool verb. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`) demonstrates the failure end-to-end: `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. The borrow-index ceiling (INV-IDX-01) clamps index growth but does not bound `scaled × index`, so the panic path is reached before the cap can arrest accrual. Per-market caps (`enforce_spoke_cap`) bound share count by governance-set caps but do not account for index growth, so caps admitted under `max_cap_for_decimals` do not prevent the cliff.

### Impact Explanation
Permanent freezing of funds. Once `borrowed × borrow_index` (or `supplied × supply_index`) exceeds i128::MAX inside `accrue_step`, every operation on that market reverts because accrual runs first and panics. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and `recapitalize`/`update_indexes` cannot recover the market — the panic is in the accrual prelude itself. All tokens held in that market's pool book are frozen permanently.

### Likelihood Explanation
The trigger requires an outsized book (on the order of 1e36 raw RAY value, e.g., ~1 billion 18-decimal tokens) at high utilization for an extended accrual span. An unprivileged attacker can manufacture the state with `supply` + `borrow` at ~98% utilization on a steep curve segment; governance would have to have admitted caps that large, and natural long-lived whale markets can also drift into it. It is not triggerable instantly, but no privileged action, oracle manipulation, or timing race is needed — only allowed user operations and elapsed time. The protocol's own threat model acknowledges the bound ("Finite RAY value capacity can be exhausted before the index ceiling"), which reduces novelty but does not mitigate the freeze.

### Recommendation
Make accrual value computation saturate instead of panic in `accrue_step`: use a saturating `scaled_to_original` (or clamp `borrowed`/`supplied` to the representable ceiling) for utilization/rate computation so the market continues operating at the effective-max rate rather than freezing. Alternatively, enforce that `scaled × index` stays representable by capping scaled book size against `i128::MAX / MAX_BORROW_INDEX_RAY` at listing/cap-admission time (`require_cap_within_asset_domain`), and add a debt write-down path that can run with accrual skipped so a frozen market remains recoverable.

### Proof of Concept
Reproduced by the in-repo test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`: list an 18-decimal market, supply ~1e9 whole tokens, borrow ~98% of it, advance time on the XLM curve. `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` while the borrow index is below `MAX_BORROW_INDEX_RAY`, confirming a permanent market freeze caused by `scaled_to_original` overflow inside `accrue_step`.
