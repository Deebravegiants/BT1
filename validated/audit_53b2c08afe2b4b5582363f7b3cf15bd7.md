## Finding

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` covers the JSON body alone. The `shop` (and `topic`/`webhook_id`/`api_version`) values are read straight from HTTP headers and are never included in the signed material, so they are not cryptographically bound to the HMAC that the registry treats as proof the request "did indeed come from Shopify."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface: [1](#0-0) 

`hmac` is derived from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate, unsigned headers via `shopify_header`: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, treats the request as authentic, forwarding `request.shop` (the unsigned header value) directly into `WebhookMetadata` for the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body) using the app's `client_secret`: [4](#0-3) 

The identity binding broken here is: `shop header verified by HMAC` ≠ `shop header consumed by the handler as tenant key`. Because the app's `client_secret` is shared across every shop that installs the app, any merchant who receives a legitimate webhook for their own store possesses a body+HMAC pair that is valid under the app's secret. That merchant can resend the same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` only checks the raw body against the secret — it has no way to detect that the `shop` header was swapped — so `Registry.process` passes validation and invokes the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is attacker-controlled data from the attacker's own store.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which implies the full request — including the shop attribution used by the handler — is authenticated: [5](#0-4) 

In practice, only the body bytes are authenticated; the shop identity that downstream application code uses as a tenant key is not.

### Impact Explanation
Any app built on this gem that trusts `WebhookMetadata#shop` as the tenant key for writing/updating merchant data (the exact usage pattern shown in the gem's own documentation, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to process attacker-supplied webhook bodies under another merchant's shop identity. This is a cross-tenant confusion vulnerability: an unprivileged installer of the app (attacker installs the app on their own store, a low bar) can forge webhook events that the app attributes to a victim tenant, using only artifacts (raw body + HMAC) generated for their own store.

### Likelihood Explanation
Likelihood is high for any app that follows this gem's documented processing pattern verbatim. The attacker only needs: (1) their own installation of the target app (any merchant can install an app), (2) to trigger a real webhook to capture a valid raw_body/HMAC pair signed with the app's shared `client_secret`, and (3) to replay that body/HMAC to the app's public webhook endpoint with a modified `shop` header — no access to the app's `client_secret`, no TLS interception, and no privileged account are required.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the material verified by `Utils::HmacValidator`, or otherwise require callers to independently confirm that `request.shop` corresponds to a shop for which the app expects to receive this specific webhook (e.g., cross-check the webhook subscription's registered shop) before invoking the handler in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. App installs webhook handler per `docs/usage/webhooks.md`, storing data keyed by `data.shop`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared `client_secret`).
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim-shop.myshopify.com"` even though the payload came from the attacker's own store, causing the app to process attacker-controlled data under the victim's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
