### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted without HMAC coverage, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from HTTP headers that are never included in the signed material. `Registry.process` verifies only that the body's HMAC is valid, then hands the unauthenticated `shop` header straight to the app's webhook handler as the tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are all pulled from headers that are outside that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authenticating the entire request, then forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the signed bytes — directly to the app's handler as trusted identity fields: [4](#0-3) 

This breaks the intended binding `verified_bytes == acted_upon_identity`: the gem verifies `HMAC(secret, body)` but acts on `header["shop-domain"]`, a byte range the HMAC never covers. Any attacker who can obtain one legitimate `(body, hmac)` pair — for example from a webhook Shopify genuinely delivers to their own development store/app — can replay that exact body and HMAC to the target app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the handler with the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity confusion: a request that Shopify never issued for shop B is delivered to the host application labeled as belonging to shop B, using only credentials (a valid body/HMAC pair) that the attacker legitimately possesses for shop A. Any app whose webhook handler acts on `WebhookMetadata#shop` (e.g., mandatory `shop/redact` or `customers/redact` handlers, or handlers that key data mutations off the reported shop) can be tricked into performing actions attributed to, or affecting, a different merchant than the one that actually sent the data — a direct cross-tenant boundary break.

### Likelihood Explanation
Exploitability requires only that the attacker control one webhook endpoint of their own (any developer can register an app/dev store and receive genuine webhooks with valid HMACs for their own shop's body), then replay that body+HMAC to the victim app's endpoint with forged shop/topic headers — no access to `api_secret_key`, tokens, or the victim's credentials is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them, mirroring how `AuthQuery#to_signable_string` binds `shop`/`host` into the OAuth HMAC), so `HmacValidator.validate` fails if any of these identity-bearing fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker registers a dev app/store and receives a genuine webhook from Shopify: body `B`, header `shopify-hmac-sha256: H = HMAC(secret, B)`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a POST to the victim app's webhook endpoint with the identical body `B` and `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally `shopify-topic: customers/redact`).
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`) — it matches `H`, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though Shopify never generated this webhook for that shop.
