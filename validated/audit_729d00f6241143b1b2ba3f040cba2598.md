### Title
Unbound router calldata + unlimited approval lets any caller drain stranded `inputToken` balance in `LifiExternalAction` left over from a prior partial-fill/refund - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap` computes `swappedAmount` purely from the *output*-token balance delta around `router.call`, and `LifiExternalAction.callRouter` never verifies that the router actually consumed the `inputAmount` of `inputToken` that Hinkal transferred for that specific transaction. Combined with `approveUnlimited(inputToken, router)` and fully attacker-controlled `externalActionMetadata`, any leftover `inputToken` balance sitting in `LifiExternalAction` (e.g., an unspent refund from a prior partial-fill swap) can be pulled into a later, unrelated caller's swap and converted into extra output that gets minted into that caller's own UTXO.

### Finding Description
The equality that should hold per-transaction inside the external action is: *tokens the router consumes from `LifiExternalAction` for `inputToken` == the `inputAmount` Hinkal transferred to it for this call*. This is never checked.

`ExternalActionSwap.swap` computes `inputAmount` [1](#0-0)  and passes it to `callRouter`, but `LifiExternalAction.callRouter` only measures the *output* token balance delta and blindly executes attacker-supplied `externalActionMetadata` against an unlimited allowance for the ERC20 path — the `inputAmount` parameter is not used at all in that branch: [2](#0-1) .

Because `router.call(externalActionMetadata)` is arbitrary calldata fully controlled by whoever built the `CircomData` for that transaction, and `approveUnlimited` grants the router unlimited spend rights over `LifiExternalAction`'s `inputToken` balance, a caller can craft calldata that pulls more `inputToken` than was transferred to it for their own transaction, consuming any residual balance already sitting in the contract (e.g., an unspent refund left over from a prior partial-fill swap where the router only partially executed and refunded the remainder to `LifiExternalAction`, per `ExternalActionSwap.swap`'s `callRouter` call and fee/transfer flow at [3](#0-2) ).

At the `Hinkal.sol` level this is invisible: the per-token balance/utxo equality is self-consistent for each transaction because Hinkal only measures its own balance delta and compares to `amountChanges`/`utxoAmount` for that same transaction [4](#0-3) . Hinkal correctly deducts exactly `inputAmount` from its own balance for the first (partial-fill) transaction and credits exactly the observed `swappedAmount` as that user's UTXO — so the first user's declared accounting checks out even though only part of their principal was actually swapped, and the remainder is stranded in `LifiExternalAction`, uncredited to anyone. It is this stranded balance that a second, unrelated caller can later fold into their own `swappedAmount` via crafted `externalActionMetadata`, since nothing ties the router's actual token consumption to the currently-transacting caller's declared `inputAmount`.

`circomData.slippageValues[1] != 0` at [5](#0-4)  and the `balanceDif >= circomData.slippageValues[i]` check in `Hinkal.sol` are not the root cause — they only bound the attacker's *own* trade's slippage; they do not, and cannot, verify that the input side of the swap consumed exactly the funds attributed to the current transaction. The circuit's `inTotal + amountChanges[i] === outTotal` constraint in `MainEVMCircuit` [6](#0-5)  also does not help: for the swap's output token, `onChainCreation` is required true and `amountChanges` is forced to zero (`checkOnchainCreation`, [7](#0-6) ), meaning the output UTXO amount for swaps is deliberately *not* proof-bound and is instead trusted to equal whatever the on-chain balance delta says — this is by design (since the swap's real output can't be known pre-proof), but it also means nothing in the system verifies that the balance delta itself is attributable solely to the current caller's declared input.

### Impact Explanation
A caller can mint a shielded UTXO backed partly by unspent principal that Hinkal already deducted from a different user's proof in a prior transaction. This is direct theft/insolvency exposure of shielded funds and creation of shielded value not backed by that transaction's own declared input — matching the Critical category ("direct theft of shielded or in-flight user funds, minting shielded value without backing"). It is repeatable any time residual `inputToken` balance accumulates in `LifiExternalAction` (partial fills, dust, or any other reason a nonzero balance remains).

### Likelihood Explanation
Requires: (1) a prior transaction through `LifiExternalAction` that leaves a nonzero `inputToken` balance in the contract (achievable by the attacker themselves in a first transaction using a router/metadata that partially fills and refunds the rest, or naturally via aggregator dust/refund behavior), and (2) the attacker being able to craft `externalActionMetadata` for the real router that pulls more than their own declared `inputAmount`. Both preconditions are within the attacker's control as an unprivileged EOA who fully controls `CircomData.externalActionData.externalActionMetadata` and their own deposit/proof. No privileged role is needed. The main uncertainty is whether the real (non-mock) LI.FI router's calldata format actually permits specifying a swap amount decoupled from what the caller's own funds cover — this needs to be validated against the actual router integration, but nothing in this repo's contracts prevents it.

### Recommendation
In `LifiExternalAction.callRouter` (and any other `ExternalActionSwap` implementation), enforce that the router consumes exactly `inputAmount` of `inputToken`: track `inputToken` balance before/after the router call and require `balanceBefore - balanceAfter == inputAmount` (or `<=` with the remainder refunded back to Hinkal/the caller's UTXO rather than left in the contract). Replace `approveUnlimited` with an approval scoped to `inputAmount` for the current call, reset afterward. Any leftover balance in the contract from partial fills should be swept back to the Hinkal contract (crediting the originating caller) rather than left as free-floating balance available to arbitrary future callers.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction` with a mock router that, on first call, performs a partial fill (transfers only 50% of `inputAmount` worth from `LifiExternalAction` to itself and mints/returns proportional `outputToken`) and leaves the other 50% of `inputToken` sitting in `LifiExternalAction`.
2. User A calls `transact` -> `swap` -> `callRouter` with `inputAmount = 100`; assert `LifiExternalAction`'s `inputToken` balance after the call is `50` (stranded), and confirm User A's balance equation in `Hinkal.sol` still holds with `swappedAmount` reflecting only the 50% actually swapped.
3. User B (any unrelated EOA) generates their own valid proof/UTXO for `inputAmount = 10`, but crafts `externalActionMetadata` for the mock router to pull `60` (`10` declared + `50` stranded) from `LifiExternalAction` via the unlimited allowance, producing `outputToken` proportional to `60`.
4. Assert User B's UTXO (`utxoSet[0].amount`) is credited with output corresponding to `60` input, i.e., strictly greater than the output corresponding to their own declared `10`, while `LifiExternalAction`'s `inputToken` balance drops to `0` — proving User A's stranded `50` was consumed and monetized entirely by User B with no compensating debit against User B's own nullifiers/amountChanges.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
