### Title
Asymmetric decimal-scaling in `convert_to_erc20`/`convert_to_balance` allows unbacked minting or fund loss across the HyperFungibleToken bridge - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
The `pallet-hyper-fungible-token` <-> `HyperFungibleToken.sol` bridge scales token amounts between substrate-side "local" decimals and EVM-side "erc" decimals using `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent for both directions. `saturating_sub` silently clamps to `0` whenever `local_decimals > erc_decimals`, meaning the amount is not scaled down at all in that case — it is treated as unscaled instead of correctly dividing.

### Finding Description
The scaling helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions compute the scale exponent as `erc_decimals.saturating_sub(local_decimals)`, which is correct **only** when `erc_decimals >= local_decimals` (the documented BRIDGE case: local 12 decimals, erc 18 decimals, scale factor 10^6 — matches the doc comment in `evm/src/apps/BridgeToken.sol` lines 34-36). But for any registered asset where `local_decimals > erc_decimals` (e.g. a substrate asset with 18 decimals paired to a common ERC20 stablecoin representation with 6 decimals — a very plausible, non-adversarial registration by governance via `register_token`), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so `10^0 = 1` — i.e., **no scaling is applied in either direction**, when the correct behavior would require dividing by `10^(local_decimals - erc_decimals)`.

This asymmetry is invoked from the `send` extrinsic: [2](#0-1) 

```rust
let sender: [u8; 32] = who.clone().into();
let amount: u128 = params.amount.into();
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
```

`decimals` here is the local asset's decimals (`local_decimals`), and `erc_decimals` comes from the `Precisions` map set at `register_token` time — a governance-configured, but not necessarily malicious, value reflecting real-world ERC20 metadata. If `local_decimals` (e.g. 18) exceeds `erc_decimals` (e.g. 6), the outgoing message will carry `erc20_amount = amount` unscaled (raw 18-decimal value) instead of `amount / 10^12`. The destination `HyperFungibleToken.sol::onAccept` mints exactly this unscaled `message.amount`: [3](#0-2) 

```solidity
Message memory message = abi.decode(request.body, (Message));
address beneficiary = _toAddr(message.to);
_mint(beneficiary, message.amount);
```

producing a mint that is `10^12` times larger than what was actually escrowed/burned on the substrate side. This is an unbacked mint on the destination chain, not merely a display/units-documentation nit as in the Aave M09 report — it is a directly exploitable financial-loss bug once such an asset pairing is registered. The lack of documented units/invariants on the `Precisions` map (which decimal direction is assumed, and the missing symmetric-subtraction guard) is the direct root cause, mirroring the M09 pattern of "sensitive mathematical operations… not explicitly documented," except here it manifests as a concrete arithmetic defect rather than a purely cosmetic one.

### Impact Explanation
If any registered non-native asset pair has `local_decimals > erc_decimals` (a normal, foreseeable configuration for tokens whose canonical ERC20 decimals are lower than the substrate asset's decimals, e.g. 18 vs 6), every `send()` call for that asset mints `10^(local_decimals - erc_decimals)` times too many tokens on the destination EVM chain relative to the amount locked/burned on the source chain. This is an unbacked mint — a direct, permanent value-creation bug enabling theft of bridge liquidity/backing, reachable by any ordinary user submitting a `send` extrinsic once such a token is registered.

### Likelihood Explanation
The trigger condition depends only on the decimals configuration of a registered token pair, set once via `register_token`/`update_token` by `CreateOrigin` (governance) — this is a normal, expected configuration action (not a malicious-governance scenario) since many real-world ERC20 tokens use 6 or 8 decimals while substrate assets commonly use 10, 12, or 18 decimals. Any user can then trigger the bug by calling `send()`. No collusion or privileged/compromised roles are needed beyond the ordinary registration of a legitimately mismatched-decimals asset.

### Recommendation
Fix `convert_to_erc20`/`convert_to_balance` to handle both directions explicitly:
- If `erc_decimals >= local_decimals`: multiply by `10^(erc_decimals - local_decimals)` when converting to ERC20, divide by the same factor when converting back.
- If `local_decimals > erc_decimals`: divide by `10^(local_decimals - erc_decimals)` when converting to ERC20, multiply by the same factor when converting back.

Add explicit unit tests covering `local_decimals > erc_decimals`, `local_decimals == erc_decimals`, and `local_decimals < erc_decimals`, and document the units/invariants of the `Precisions` storage map and the scaling helpers directly in code comments, as recommended by the referenced report's general remediation for undocumented sensitive arithmetic.

### Proof of Concept
1. Governance registers a non-native asset `X` with `local_decimals = 18` (its substrate-side `fungibles::metadata::Inspect` decimals) and calls `register_token`/`update_token` to set `Precisions::<T>::insert(X, dest_chain, 6)` (a legitimate ERC20 with 6 decimals, e.g. mirroring USDC-style precision).
2. A user calls `send(params)` with `params.amount = 1_000_000_000_000_000_000` (1 token at 18 decimals) for asset `X` to `dest_chain`. The pallet burns/locks `1e18` raw units locally.
3. Inside `send`, `erc_decimals = 6`, `decimals = 18`. `convert_to_erc20(1e18, 6, 18)` computes `6u8.saturating_sub(18u8) = 0`, so the scale factor is `10^0 = 1`, yielding `erc20_amount = 1e18` (unchanged) instead of the correct `1e18 / 10^12 = 1_000_000`.
4. The dispatched `Message.amount = 1e18` is delivered to `HyperFungibleToken.sol::onAccept` on the destination chain, which calls `_mint(beneficiary, 1e18)` — minting `1e18` raw ERC20 units (interpreted at whatever decimals the destination contract uses, e.g. 18) instead of the economically correct `1_000_000` units, a 10^12x over-mint relative to the value actually escrowed on the source chain.
