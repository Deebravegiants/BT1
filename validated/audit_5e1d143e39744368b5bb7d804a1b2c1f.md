### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` cause `msg.value` to be credited once per matching index in `Hinkal.transact`, allowing unbacked shielded ETH UTXO minting - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact`'s post-action balance-reconciliation loop adds `int256(msg.value)` independently for **every** index `i` where `circomData.erc20TokenAddresses[i] == address(0)`, rather than crediting the single real ETH deposit once. Because there is no on-chain check anywhere (`dimensionsCheck`, `checkOnchainCreation`, `performHinkalChecks`) forbidding duplicate token addresses across slots, an attacker can list `address(0)` at two indices and satisfy two independent `balanceDif == amountChanges[i] + utxoAmount` equalities from a single real `msg.value` payment, letting them create two off-chain output commitments worth the deposit each - doubling their shielded balance for one real deposit.

### Finding Description
The equality that should hold is: **total real ETH received by the contract in this transaction (`msg.value`, credited exactly once) == sum of all recognized off-chain/on-chain value increases (`Σ amountChanges[i] + Σ utxoAmount[i]`) attributable to that ETH**. Instead, the contract enforces this per-slot with the same `msg.value` term reused: [1](#0-0) 

For each `i` in `circomData.erc20TokenAddresses`, if `erc20TokenAddresses[i]==address(0)`, `balanceDif = newBalances[i] + msg.value - oldBalances[i]`. Since `oldBalances`/`newBalances` are queried from the same `erc20TokenAddresses` array via `getBalancesForArray`, two `address(0)` entries yield `oldBalances[0]==oldBalances[1]` and `newBalances[0]==newBalances[1]` (same real contract ETH balance snapshot), so `balanceDif` is numerically identical at both indices - each independently re-adding the same `msg.value`. The subsequent `require(balanceDif == (onChainCreation[i]?0:amountChanges[i]) + utxoAmount)` at line 137-146 is then checked **twice** against the same `balanceDif`, but with independently attacker-chosen `amountChanges[i]` and independently accumulated off-chain output commitments (`outCommitments[i]`, `inputNullifiers[i]`) per slot.

Root cause: no code path enforces uniqueness of `erc20TokenAddresses` entries (confirmed absent in `dimensionsCheck` and `checkOnchainCreation` in `contracts/HinkalHelper.sol` lines 64-202, and in `performHinkalChecks` lines 208-236). Each slot `i` is treated by both the Solidity reconciliation loop and (per `CircomDataBuilder.formInputForCircom`, `contracts/CircomDataBuilder.sol` lines 203-233) the circuit's public inputs as an independent per-slot conservation check, with no cross-slot linkage forcing that duplicate token addresses share a single real value movement.

Concretely (using the plain internal-transact deposit path, which is the simplest reproduction of the underlying flaw referenced by the question - the swap variant in `ExternalActionSwap.sol` is one specific way to reach the same duplicated-slot state): attacker sends `msg.value = V`, sets `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [V, V]`, `onChainCreation = [false, false]`. In `_internalTransact` (`contracts/Hinkal.sol` lines 172-230), for each index with `deltaAmountChange > 0`, `transferERC20TokenFromOrCheckETH` is called with `_to == address(this)`, which only asserts `msg.value == _value` (line 118-121 in `contracts/Transferer.sol`) and performs **no transfer** - so this check passes trivially at both indices using the same `msg.value`, and the contract's real balance is unchanged by these calls. Then in the outer loop, `balanceDif` at both `i=0` and `i=1` equals `0 + V - 0 = V`, and `amountChanges[i] = V` for both, so both `require` checks pass with `utxoAmount=0` (internal transact never populates `utxoSet`). The attacker then crafts the circuit witness so that slot 0 and slot 1 each independently create a brand-new off-chain output commitment worth `V` (via `outCommitments[0]` and `outCommitments[1]`, each with zero corresponding input nullifiers), since the circuit's public inputs and `dimensionsCheck` never constrain that two slots sharing the same token address must share value. Net effect: attacker deposits `V` once but walks away with two shielded UTXOs each worth `V` (total `2V`), i.e., unbacked minting of shielded ETH value.

None of the existing guards catch this: `performHinkalChecks` (`dimensionsCheck`, `checkOnchainCreation`) checks only that array lengths match `dimensions` and that `onChainCreation` amount/nullifier rules hold - never that `erc20TokenAddresses` entries are distinct; `verifyProof`/`buildVerifierId` only validate that the supplied witness is consistent with the public inputs given, which includes the duplicated address list verbatim; `rootHashExists`, `insertNullifiers`, and the slippage `require` at line 111-114 operate per-slot and don't detect duplicate slots either.

### Impact Explanation
This is a Critical-severity finding: it allows an unprivileged attacker to mint shielded ETH UTXO value with no backing deposit, directly stealing value from the protocol's ETH reserves (funds belonging to other shielded-pool depositors, since the pool is commingled). The attack is repeatable per transaction and scales with however many duplicate `address(0)` (or duplicate ERC20 address) slots the attacker includes in `erc20TokenAddresses` - each additional duplicate slot lets them re-use the same `msg.value` credit to mint another full-value UTXO.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: craft `CircomData` with a duplicated token address across two (or more) `tokenNumber` slots, matching `Dimensions.tokenNumber`, generate a valid proof for their own chosen witness (no privileged data needed, since they control both slots' nullifiers/commitments), and call `Hinkal.transact` directly. No relay, hook, or router cooperation is required for the minimal internal-transact reproduction; the `ExternalActionSwap` path referenced in the question additionally requires a registered external action but is not necessary to trigger the core flaw. Attacker cost is a single real `msg.value` deposit; profit is proportional to the number of duplicated slots used.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` or `performHinkalChecks` (reject transactions with duplicate non-zero-amount token entries), and/or change the `balanceDif` computation in `Hinkal.transact` to add `msg.value` only once total (e.g., accumulate it against the first occurrence of `address(0)` only, or track a `msg.value` consumed to a running total that is checked against a single aggregate `require` rather than per-slot).

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and supporting verifier/circuit artifacts as in existing test fixtures.
2. Have attacker EOA deposit some initial shielded UTXO if needed to obtain valid empty-input nullifiers, or use zero-nullifier off-chain creation directly.
3. Build `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [V, V]`, `onChainCreation = [false, false]`, two independent `outCommitments` rows each encoding a fresh UTXO of value `V`, zero `inputNullifiers` rows.
4. Generate a valid witness/proof for this `CircomData` locally via snarkjs using the project's existing proving key (test-only, not touching `contracts/verifiers/**`).
5. Call `hinkal.transact(a, b, c, dimensions, circomData, { value: V })`.
6. Assert: (a) transaction succeeds; (b) contract's actual ETH balance increased by only `V` (`await ethers.provider.getBalance(hinkal.address)` delta); (c) the two off-chain output commitments together represent `2V` of claimed shielded value (sum of decrypted/opened UTXO amounts from `outCommitments`), i.e., `contractBalanceDelta (V) != mintedShieldedValue (2V)`, proving the equality `balanceDif == amountChanges[i] + utxoAmount` is satisfied twice for one real fund movement.
