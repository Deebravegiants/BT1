### Title
Flash-loan Uniswap V4 pool price manipulation forces the Simplex intent solver to overpay venue-priced fills - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The reported incident is a flash-loan attack that manipulated a pool's spot price to extract value from a contract that trusted that price without slippage/impact protection. Hyperbridge's Simplex intent-solver has the same bug class: for curveless ("venue-priced") trading pairs, `FXFiller` prices fills directly from the live Uniswap V4 pool mid-price (`sqrtPriceX96`), with the only defense being an optional, static-reference deviation guard that bounds *price level*, not *manipulation via a single large trade*, and with no size/impact term applied to the quantity actually being filled.

### Finding Description
When a `TradingPair` has no configured bid/ask curves and `token0` is a USD stable, `resolveLegRates` sources the fill rate from `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the pool's raw mid-price off `sqrtPriceX96` [1](#0-0) . This price is passed straight into `checkPriceGuard`, which only rejects a quote if it deviates from a static, operator-configured `referencePrice` by more than `maxDeviationBps` — and the guard is entirely optional per chain [2](#0-1) .

Once the quote passes (or no guard is configured at all — a documented, supported configuration), `computeLegPolicyOutput` extends that single mid-price **linearly across the entire notional being filled**, with no pool-depth or fee-tier impact term applied [3](#0-2) . This is explicitly documented as a known gap: "there is no size or impact term ... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost" [4](#0-3) .

Additionally, the overfill clamp that would otherwise bound the loss from a "manipulated venue price" is explicitly disabled in the fill path — the code computes an overfill ceiling, warns if it's exceeded, but still pays out the full unclamped amount: "the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested — including venue-priced legs (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price" [5](#0-4) .

An attacker who takes a flash loan to swap heavily against the exotic token's Uniswap V4 position used by the filler (the same position registered under `[vault.uniswapV4]`) can move `sqrtPriceX96` to a favorable level, then immediately submit (or have submitted) an intent order against that pair. The filler reads the manipulated mid-price, the guard either passes it (unconfigured, or the manipulated move stays inside `maxDeviationBps`) and the fill is computed and paid without any per-fill overfill cap, since that cap is disabled.

### Impact Explanation
The solver's wallet and its Uniswap V4 LP inventory are drained at a manipulated exchange rate, directly transferring value from the solver (and by extension the liquidity backing venue-priced pairs) to the attacker. Since the overfill clamp is a documented no-op, there is no runtime backstop once the price guard is bypassed by operating within `maxDeviationBps` (or the guard is left unset, which is explicitly a supported, documented configuration in `docs/content/developers/evm/simplex/pricing.mdx`). This is a concrete theft vector against solver capital reachable by any account able to submit an intent order and manipulate the referenced on-chain pool.

### Likelihood Explanation
Reachable by a single, unprivileged actor: take a flash loan, swap through the exact Uniswap V4 pool the filler prices from (`positions` are public config/on-chain, and the most-liquid qualifying pool is auto-selected), then submit an intent order sized to the notional the pool move justifies. No special privileges, governance, or trusted role is required — only capital for the flash loan and knowledge of the filler's configured position(s), both of which are discoverable from public config examples and on-chain state.

### Recommendation
- Make the price guard mandatory (not optional) for every venue-priced position, and additionally bound the *momentary* deviation using a TWAP/multi-block observation rather than the instantaneous `sqrtPriceX96`.
- Apply a real price-impact/depth term in `computeLegPolicyOutput` for venue-priced legs instead of extending the pool mid linearly across the whole fill notional.
- Re-enable the overfill clamp (or a hard per-fill notional ceiling) specifically for venue-priced (`priceSource === "venue"`) legs, since that clamp is exactly the loss bound the code comments say was designed for "a manipulated venue price."

### Proof of Concept
1. Operator runs Simplex with a curveless USD-stable/exotic pair funded by `[vault.uniswapV4]`, either with no `referencePrice`/`maxDeviationBps` set, or with a wide-enough band (both documented, supported configurations) [6](#0-5) .
2. Attacker flash-loans funds and swaps through the referenced Uniswap V4 pool to shift `sqrtPriceX96` in the direction that inflates the exotic token's USD price (or deflates it, to make the solver's exotic output cheap to obtain relative to the input it collects).
3. Attacker (or a colluding filler-observing bot) submits an intent order against that pair sized to exploit the shifted rate.
4. `resolveLegRates` → `getVenueUsdPrice` reads the manipulated pool mid [7](#0-6) ; `checkPriceGuard` passes (guard absent or band wide enough); `computeLegPolicyOutput` linearly prices the full notional at the manipulated rate [8](#0-7) ; the overfill ceiling is checked but not enforced [9](#0-8) .
5. The solver's `fillOrder` pays out the miscalculated amount; the attacker repays the flash loan and keeps the difference — the same fundamental mechanism as the reported XSDWETHpool flash-loan price-manipulation exploit.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	private computeLegPolicyOutput(
		inputAmount: bigint,
		inputIsToken0: boolean,
		token0Decimals: number,
		token1Decimals: number,
		/**
		 * Token0 left in the pair's per-order exposure budget, or `null` to price the whole
		 * input unbudgeted. Only a price probe passes `null`: it commits no capital, so there
		 * is no exposure to ration, and a clamped quantity would silently misprice it.
		 */
		remainingToken0: Decimal | null,
		rate: Decimal,
	): { token0Used: Decimal; policyMaxOutput: bigint } | null {
		let legMaxToken0: Decimal
		if (inputIsToken0) {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token0Decimals))
		} else {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token1Decimals)).div(rate)
		}

		const token0ForLeg = remainingToken0 === null ? legMaxToken0 : Decimal.min(legMaxToken0, remainingToken0)
		if (token0ForLeg.lte(0)) {
			return null
		}

		let policyMaxOutput: bigint
		if (inputIsToken0) {
			// Output is token1: convert the token0 allocation at the pair rate.
			policyMaxOutput = BigInt(
				token0ForLeg.mul(rate).mul(new Decimal(10).pow(token1Decimals)).floor().toFixed(0),
			)
		} else {
			// Output is token0: pay out the token0 equivalent of the token1 input.
			policyMaxOutput = BigInt(token0ForLeg.mul(new Decimal(10).pow(token0Decimals)).floor().toFixed(0))
		}

		return { token0Used: token0ForLeg, policyMaxOutput }
	}
