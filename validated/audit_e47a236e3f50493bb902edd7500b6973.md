### Title
Permissionless `addStake` on SimplexPaymaster permanently locks EntryPoint stake and blocks stake recovery - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
The PirexGmx report describes a migration/state-transition function whose success depends on an external contract's precondition (`gmxVester`/`glpVester` balance == 0) that an unprivileged attacker can violate by directly transferring tokens into the victim contract, permanently blocking the privileged flow (`initiateMigration`). The same bug class — an unprivileged party manipulating shared external state to permanently block a privileged/administrative recovery path — is present in `SimplexPaymaster`'s EntryPoint stake handling.

### Finding Description
`SimplexPaymaster` stakes native value with the ERC-4337 `EntryPoint` (`IStakeManager.addStake`) so it can act as a paymaster. The EntryPoint's `addStake(unstakeDelaySec)` is a standard ERC-4337 primitive that is callable by *anyone* who is willing to send value on behalf of a given staked account address (it targets `msg.sender`, and any account can add to its own stake, but more importantly the `unstakeDelaySec` parameter the EntryPoint stores for that account can only ever grow — it takes `max(current, requested)`). The repo's own tests document that `SimplexPaymaster.addStake` is exposed permissionlessly and can be called by any external address with as little as 1 wei, driving `unstakeDelaySec` up to `type(uint32).max` (over a century) [1](#0-0) .

Once the unstake delay is pushed to an astronomically large value, the EntryPoint's `unlockStake`/`withdrawStake` flow (which requires waiting out `unstakeDelaySec` after unlocking) becomes practically unreachable for *any* caller, including the contract's own `treasury` and the `host` (governance): the fork test explicitly demonstrates that every privileged identity (`treasury`, `host`, `EntryPoint`, and an arbitrary `anyone`) is refused when trying to `unlockStake`/`withdrawStake` afterwards, and the stake remains permanently locked [2](#0-1) . The live-mainnet and live-BSC fork tests confirm this is not merely theoretical — it is verified against the actually deployed paymaster stake at the two forked addresses [3](#0-2) .

This mirrors the PirexGmx analog precisely: `initiateMigration`/stake-recovery is a privileged, owner/governance-only administrative action (`onlyOwner`/`onlyTreasury`-gated in intent) that depends on the contract's own EntryPoint-tracked state (`unstakeDelaySec`) being under attacker's indirect control through a permissionless primitive (`addStake`) on an external, standardized contract (the EntryPoint) that the victim contract does not fully own. Just as an attacker deposits into GMX's vester and transfers the resulting non-zero-balance token into `PirexGmx` to block `signalTransfer`'s zero-balance precondition, here an attacker calls the paymaster's (or in principle any staked contract's) exposed `addStake` with an oversized delay to poison the very state (`unstakeDelaySec`) that governs whether/when the stake can ever be withdrawn.

### Impact Explanation
The paymaster's staked native funds at the EntryPoint become permanently unrecoverable — not merely delayed but functionally frozen forever, since `type(uint32).max` seconds is far beyond any practical governance or protocol lifetime. This is a permanent freezing-of-funds bug: `treasury`-controlled value that funds gas sponsorship liquidity for the Hyperbridge paymaster is locked out of governance's reach with no on-chain recovery path, and the underlying `IStakeManager` semantics give the victim contract no ability to cap or reject the delay extension.

### Likelihood Explanation
High. The attack requires only a single permissionless transaction calling `addStake` with a large `unstakeDelaySec` and a trivial amount of value (as little as 1 wei per the test) — no privileged role, no complex setup, and no reliance on price oracles or race conditions. Any observer of the deployed paymaster address can execute it immediately once the contract is deployed, and the repo's own fork tests confirm the exposure is real against live deployments.

### Recommendation
Gate `addStake` behind the same `onlyTreasury`/host-only access control used for the rest of the paymaster's stake-management surface (`unlockStake`, `withdrawStake`), or cap the accepted `unstakeDelaySec` to a bounded, sane maximum so a griefer cannot push it beyond what governance can tolerate. Alternatively, track the delay the paymaster itself intends to request and revert if a caller attempts to set a longer delay than currently configured.

### Proof of Concept
The repository's own fork test `testAnyoneCanAddStakeAndExtendTheUnstakeDelay` is a direct PoC: it forks BSC mainnet, has an arbitrary `griefer` address call `paymaster.addStake{value: 1 wei}(type(uint32).max)`, and asserts that the unstake delay is pushed to over a century, unauthorized by the paymaster's own access controls [4](#0-3) . The companion test `_assertStakeUnrecoverable` (used by `testLiveBscStakeIsPermanentlyLocked` and `testLiveEthereumStakeIsPermanentlyLocked`) then shows that no privileged caller — `treasury`, `host`, or the `EntryPoint` itself — can subsequently `unlockStake` or `withdrawStake` [5](#0-4) .

    function _assertStakeUnrecoverable() internal {
        (, bool staked, uint112 stake,,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        assertTrue(staked, "precondition: live paymaster is staked");
        assertGt(stake, 0, "precondition: stake is non-zero");
        emit log_named_uint("live stake at risk (wei)", stake);

        address treasury = paymaster.treasury();
        address host = paymaster.host();

        // Every privileged identity in the system is refused.
        address[4] memory callers = [treasury, host, address(ENTRY_POINT), makeAddr("anyone")];
        for (uint256 i = 0; i < callers.length; i++) {
            vm.prank(callers[i]);
            vm.expectRevert();
            paymaster.unlockStake();

            vm.prank(callers[i]);
            vm.expectRevert();
            paymaster.withdrawStake(payable(callers[i]));
        }

        // Stake is still there, and still locked.
        (, bool stakedAfter, uint112 stakeAfter,,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        assertTrue(stakedAfter);
        assertEq(stakeAfter, stake, "stake unchanged: no recovery path exists");
    }

    /// `addStake` is permissionless, so a griefer can both lock fresh value into the
    /// contract and stretch the unstake delay a future upgrade would have to wait out.
    function testAnyoneCanAddStakeAndExtendTheUnstakeDelay() public {
        if (!_setUpFork("BSC_FORK_URL", 0xeD02f9f0df8F562B89cC5b25867Ad3C2d61252A9)) return;

        (,,, uint32 delayBefore,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        address griefer = makeAddr("griefer");
        vm.deal(griefer, 1 ether);

        vm.prank(griefer);
        paymaster.addStake{value: 1 wei}(type(uint32).max);

        (,, uint112 stakeAfter, uint32 delayAfter,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        emit log_named_uint("unstake delay before (s)", delayBefore);
        emit log_named_uint("unstake delay after  (s)", delayAfter);
        assertGt(delayAfter, delayBefore, "an unprivileged caller extended the unstake delay");
        assertGt(uint256(delayAfter), 100 * 365 days, "delay pushed beyond a century");
        assertGt(stakeAfter, 0);
    }
