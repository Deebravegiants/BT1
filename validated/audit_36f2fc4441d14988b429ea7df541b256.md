## Finding: Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant shop spoofing

### Title
Webhook shop-domain attribution is unauthenticated, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` identity that is handed to application webhook handlers is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in what is signed or otherwise validated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` simply reads the tenant-identifying header with no signature coverage or domain validation: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, and then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` that is delivered to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop attributed to webhook == shop that the HMAC-signed body actually originated from`. Because `to_signable_string` binds the signature only to `@raw_body` and not to the `shop-domain` header, this equality is not enforced — the `shop` value acted upon by `Registry.process` is decoupled from what the HMAC actually authenticates.

### Impact Explanation
Any unprivileged user who can install the app on their own (even free/trial) Shopify store receives legitimate webhook deliveries for that store, each with a valid HMAC computed over the JSON body using the app's `client_secret`. Because the signature never covers the `shop-domain` header, that attacker can replay the exact same signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate(request)` still passes (it only checks the body), and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the victim's domain and `body` set to attacker-controlled content — see the assertions in the test suite that assume `data.shop` is trustworthy input to the handler. Any host application that uses `data.shop` to look up per-tenant sessions or write into per-tenant storage (the documented pattern) can have its per-tenant data model poisoned by another tenant, which is a cross-tenant access violation.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple untrusted merchants: obtaining a signed body + shop pair requires nothing more than installing the app on one's own store (a normal, unprivileged action) and capturing the resulting genuine webhook delivery, then replaying it with a modified header value against the public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) headers into the signable string used for HMAC verification (e.g., include the raw header values in what is signed, matching Shopify's guidance to treat headers as part of the trust boundary), or otherwise cryptographically bind the header to the signed body before exposing it as `WebhookMetadata#shop`. At minimum, run `Utils::ShopValidator.sanitize!` on the shop domain and document that host applications must independently verify the shop against records established during OAuth rather than trusting the webhook header alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the corresponding `x-shopify-hmac-sha256` value `H` that Shopify sent — both valid because `H = HMAC_SHA256(client_secret, B)`.
2. Attacker POSTs `B` to the app's webhook endpoint with headers `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host app to attribute attacker-controlled data to the victim's tenant.
