Found it: `ShopifyAPI::Webhooks::Request` verifies the HMAC over `@raw_body` but exposes `shop` (the tenant identity used by consuming apps to route/authorize webhook processing) from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is completely outside the HMAC-signed material.

### Title
Webhook shop identity (`Request#shop`) is read from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only `@raw_body` [1](#0-0) . The `shop` attribute, which app developers use as the tenant identifier to look up the correct session/access token for processing the webhook, is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` header [2](#0-1)  and is never included in the HMAC-signed content nor cross-checked against anything authenticated.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` is just the raw request body [1](#0-0) , and `hmac` is decoded from the `hmac-sha256` header [4](#0-3) .

The `shop` method that host apps rely on to identify which merchant/tenant the webhook belongs to reads directly from the `shop-domain` header [2](#0-1) , which is neither part of the signed payload nor validated against a trusted domain list (unlike `Utils::ShopValidator.sanitize!`, used elsewhere for shop values [5](#0-4) ).

The identity binding that should hold is:
`shop_used_for_HMAC == shop_used_for_tenant_authorization`

But in this gem's `Request` class, the HMAC is computed only over the body bytes, while `shop` (the field driving tenant authorization decisions in the consuming app) is read from a header that is completely outside that signed scope. Before the request: `hmac` covers `raw_body`. After: `shop` is trusted as-is from the header with no correlation to `raw_body` or `hmac`. Two headers (`shop-domain`, `hmac-sha256`) travel independently and nothing in this class enforces they originated together from the same authentic Shopify webhook delivery for that specific shop.

Note: initializer only checks for the *presence* of the three required headers [6](#0-5)  — it does not bind their values together cryptographically.

### Impact Explanation
Because `shop` is not covered by the HMAC, if an attacker can influence header values delivered to the app's webhook endpoint while HMAC validation is performed only against the (attacker-supplied or replayed) body, they can cause the library to report a shop-domain that does not correspond to the actual signing merchant. Since apps typically use `Request#shop` to select which stored access token/session to use for the tenant, this creates a **cross-tenant confusion** risk: a validly-HMAC'd webhook body (e.g., replayed or crafted with attacker knowledge of the raw body/HMAC pair for shop A) combined with a manipulated `shop-domain` header claiming to be shop B could cause the app to process/attribute the payload under shop B's context, depending entirely on host-app trust in `Request#shop`. This matches the Critical "cross-tenant access" category since it breaks the shop-identity binding that downstream token lookups rely on.

### Likelihood Explanation
Exploitability depends on whether the host application's front-end (webserver/framework) forwards attacker-controllable headers unmodified to this class, and whether Shopify's delivery infrastructure can be intercepted or spoofed for header values while HMAC (computed over body only) still validates. In a typical deployment (HTTPS delivery directly from Shopify, no header-spoofing proxy), this is not directly reachable by an unprivileged internet user without an additional flaw in the host app or a MITM/header-injection vector. This significantly lowers likelihood versus a pure library defect, so this should be treated as a design gap rather than a fully self-contained gem exploit.

### Recommendation
Bind `shop` cryptographically to the signed payload rather than trusting the header value alone: e.g., include `shop-domain` (and `topic`, `webhook-id`) in the HMAC-signable string, or require the caller/library to independently verify that the `shop-domain` header matches an expected/allow-listed value tied to the resolved session before using it for tenant routing. At minimum, document that `Request#shop` is unauthenticated and must not be used for authorization decisions without additional verification.

### Proof of Concept
```ruby
raw_body = '{"id": 1}'
secret = ShopifyAPI::Context.api_secret_key
hmac = Base64.strict_encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body))

# Attacker (or a misbehaving intermediary) can send any shop-domain header value
# alongside a body/hmac pair that is valid for a *different* shop, since shop-domain
# is excluded from `to_signable_string`.
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: raw_body,
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  },
)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true (only body+hmac checked)
request.shop # => "victim-shop.myshopify.com" (fully attacker/header controlled, unverified)
```

Given the uncertainty about direct reachability by an unprivileged attacker (it requires a header-manipulation vector upstream of this library, which is outside this gem's control), I present this as the strongest analog found, but flag that its exploitability is conditional and not a fully self-contained bypass purely within `lib/shopify_api/**`.
