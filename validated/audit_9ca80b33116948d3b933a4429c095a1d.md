Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant spoofing of `WebhookMetadata.shop` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC only over the raw request body, but the `shop` field it exposes (and that `ShopifyAPI::Webhooks::Registry.process` passes on to the app's handler as the tenant identifier) is taken from the `X-Shopify-Shop-Domain` header, which is never included in the signed material. This breaks the intended binding: `hmac_verifies(body) == shop_is_authentic`, when in fact the HMAC only proves `hmac_verifies(body)`, saying nothing about which shop it belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic tie to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` (shared with OAuth callback validation) only recomputes and compares the HMAC over `to_signable_string`, i.e., the body bytes, and has no knowledge of `shop`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately forwards `request.shop` (the unauthenticated header value) as the tenant identity to the app-supplied handler via `WebhookMetadata`: [4](#0-3) 

Because Shopify signs webhooks for an app using the app's single shared `client_secret`/`api_secret_key` across *all* shops that install that app (not a per-shop secret), any merchant who has installed the app receives requests whose HMAC is valid for that shared secret. Since the header carrying `shop` is not part of the signed payload, a malicious installed merchant (Shop A) can take a legitimately-signed webhook body+HMAC pair delivered to the app and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different, victim shop's domain (Shop B). `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will hand the handler `shop: "shop-b.myshopify.com"` even though the payload actually originated from/for Shop A.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value used by the host application to select/scope per-tenant data (session lookup, database records, business logic keyed by `shop`) is not what the HMAC actually authenticates. An attacker who is a legitimate (but malicious) merchant of the app can inject events attributed to another merchant's shop, achieving cross-tenant access/data confusion without needing the app's `client_secret`, an access token, or any privileged access — they only need their own valid app installation, which is the normal unprivileged path any merchant can take. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for apps that trust `WebhookMetadata#shop` (the documented gem output) for tenant scoping without independently correlating it to signature-bound data — which is the expected/only way this gem exposes verified webhook shop identity. No secret material or privileged access is required beyond installing the app as any merchant would.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the verified payload before it is trusted as the tenant identity in `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must be cross-checked against a shop known independently (e.g., from an existing session record) before being used for tenant-sensitive operations.

### Proof of Concept
1. App merchant "shop-a.myshopify.com" installs the app and receives a legitimate webhook: body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker (owner of shop-a) intercepts/replays this request to the app's webhook endpoint but changes the header to `X-Shopify-Shop-Domain: shop-b.myshopify.com`, leaving body `B` and the HMAC header untouched.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares — validation succeeds because only the body is signed. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, causing the app to process attacker-controlled data as if it belonged to shop-b, achieving cross-tenant data injection/confusion.
