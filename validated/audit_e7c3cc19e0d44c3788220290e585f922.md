### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` validate webhook authenticity by computing an HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read from HTTP headers that are never included in the signed content, yet they are trusted and passed straight to the host application's webhook handler as the identity of the originating tenant. This mirrors the reported bug class of a value ("ratio"/transfer-direction) that is acted upon without being covered by the integrity check that is supposed to bind it to the correct context.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers, entirely outside the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the computed HMAC of `verifiable_query.to_signable_string` (i.e. the body) against the secret-keyed signature in the `hmac-sha256` header: [3](#0-2) 

`Registry.process` only asserts that the HMAC (body) is valid, then immediately hands `request.shop` (an unauthenticated header value) to the application's handler as the tenant identity, alongside the topic and other unauthenticated header fields: [4](#0-3) 

Because the api_secret_key used to sign webhooks is a single, application-wide secret (not per-shop), any tenant that has installed the app can generate a legitimately-signed webhook body for their own shop (e.g. by triggering an order/customer event on their own store) and capture the resulting `X-Shopify-Hmac-Sha256` header. That signature remains valid for the same raw body regardless of which `shop-domain`/`topic` headers accompany it, because those headers are never part of the signed payload. The identity binding that should hold is:

`shop header used by the handler == shop whose secret produced the HMAC`

but the implementation only enforces:

`HMAC(body) == HMAC computed with the app secret`

with no binding between that computed HMAC and the `shop-domain` header carried in the same request. This is the same defect pattern as the reported issue: an "acted-upon" field (the ratio in the original report; the shop/topic here) is not covered by the validation that is supposed to make it trustworthy.

### Impact Explanation
This breaks the cross-tenant isolation the gem is expected to provide to host applications. A malicious merchant/tenant of a multi-tenant app can replay a validly-signed webhook body while spoofing the `shop-domain` header to point at a different, victim shop. Because `Registry.process` forwards `request.shop` unauthenticated straight into `WebhookMetadata`/the handler, any host application that uses this "trusted" shop value to look up sessions, update per-shop state, or authorize per-shop actions can be tricked into processing attacker-supplied data (the replayed body) under another tenant's identity — a cross-tenant access/data-integrity violation, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate, unprivileged installer of the target app (to obtain one validly-HMAC'd webhook for their own store) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with forged headers — both are within reach of an ordinary internet-facing merchant/tenant, no possession of `api_secret_key` or another tenant's credentials is needed. Likelihood is moderated by the fact that impact depends on how the *host* application uses `shop`/`topic` from `WebhookMetadata` (the gem's documented contract is "verify + hand off headers"), but the gem itself provides no binding of these header values to the signature, which is squarely inside this library's code (`request.rb`, `hmac_validator.rb`, `registry.rb`).

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body's signature (e.g., verify shop-domain against a known/expected value per registration, or require the signature to cover a canonical string containing headers + body) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. App merchant A (a legitimate but unprivileged tenant) installs the target Shopify app and triggers an event (e.g., updates a product) causing Shopify to POST a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(app_secret, B)`.
2. Merchant A intercepts this request from their own inbox/logging/proxy (their own webhook, their own data — nothing privileged required).
3. Merchant A crafts a new POST to the same webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or a different topic if desired).
4. `Utils::HmacValidator.validate` recomputes `HMAC(app_secret, B)`, which still equals `H` since only the body is signed — validation passes.
5. `Registry.process` proceeds to call the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the app processes attacker-controlled body content under the victim's shop identity.
