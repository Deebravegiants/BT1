### Title
`findMatchingWithdrawal` in `PoaBridge.describeWithdrawal` conflates multiple same-asset withdrawals in one NEAR tx, causing a wrong withdrawal to be reported "completed" with another withdrawal's tx hash - ([File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`])

### Summary
When a user submits two (or more) PoA-bridge withdrawals of the same token in a single NEAR `intentTx` (e.g. two different destination addresses/amounts), `PoaBridge.describeWithdrawal` matches the API response purely on `nep141:${w.data.near_token_id} === assetId`, ignoring `WithdrawalIdentifier.index`, `amount`, and `destinationAddress`. Both withdrawal watchers converge on the same array element, so the second withdrawal can be reported `completed` with the first withdrawal's `transfer_tx_hash` before the second withdrawal has actually landed or even been indexed.

### Finding Description
The broken equality is: **STATUS_TRUTH(withdrawal at index=1) == describeWithdrawal({index:1, assetId, tx}) result**. This should hold per-withdrawal, but the code path breaks it.

- `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns `index` purely as a per-bridge-route counter [1](#0-0) , with no relation to `assetId`, `amount`, or `destinationAddress` uniqueness.
- `PoaBridge.describeWithdrawal` fetches the full `withdrawals` list for the NEAR tx hash and delegates matching to `findMatchingWithdrawal`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [2](#0-1) [3](#0-2) .
- The code comment explicitly acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported" and "Response list is unsorted, so we match by assetId instead of index" [4](#0-3) .
- `watchWithdrawal` polls `describeWithdrawal` per `WithdrawalIdentifier` independently for each withdrawal in the batch [5](#0-4) .

Exploit flow: attacker (an ordinary NEAR Intents user) submits an intent batch containing two PoA-bridge withdrawals of the same `assetId` with different `amount`/`destinationAddress` in one `intentTx`. Both get `WithdrawalIdentifier`s (`index: 0` and `index: 1`) for the `PoaBridge` route. When the integrator calls `waitForWithdrawalCompletion`/`watchWithdrawal` for both, each calls `describeWithdrawal` with the same `tx.hash` but their own `withdrawalParams.assetId` (identical for both). `findMatchingWithdrawal` `.find()`s the *first* array element matching that `assetId`, regardless of which `index` the identifier logically belongs to. If the bridge API has only indexed/completed the first withdrawal record when the second identifier is polled, the second identifier's `describeWithdrawal` call returns `{status: "completed", txHash: <first withdrawal's transfer_tx_hash>}` — a hash and completion status that belongs to a different withdrawal (different amount/destination), not the one actually being tracked.

No existing guard prevents this: `supports()` only checks route/asset support and is agnostic to duplicates [6](#0-5) ; `validateWithdrawal` validates address/amount per single withdrawal, not batch uniqueness [7](#0-6) ; `createWithdrawalIdentifier` does not encode any distinguishing data beyond `index`, which is then discarded by `describeWithdrawal` [8](#0-7) .

### Impact Explanation
The party misled is whichever integrator/application is watching withdrawal completion (via `sdk.waitForWithdrawalCompletion`/`watchWithdrawal`). It can receive a `completed` status and a `txHash` for withdrawal #2 that actually belongs to withdrawal #1's on-chain transfer — a genuine hash/status misreport for a withdrawal with a different amount and/or destination. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice." It is repeatable on every multi-withdrawal-of-same-token batch, and the attacker (the withdrawing user) fully controls when to trigger it by simply crafting such a batch.

### Likelihood Explanation
Preconditions: the user must include ≥2 PoA-bridge withdrawals of the same `nep141` asset in a single NEAR `intentTx` — an ordinary, permitted use of the SDK's batch withdrawal capability, no special access needed. The race window (first record indexed/completed before the second is indexed) is realistic given the PoA bridge API's asynchronous indexing, as acknowledged directly in the code's own comment about unsorted/ambiguous results. Attacker cost is a normal withdrawal transaction; the bug is deterministically triggered whenever such a batch exists and status is polled while API has fewer indexed records than submitted withdrawals of that asset.

### Recommendation
Disambiguate withdrawals by more than `assetId` — sort the API's `withdrawals` array by `data.amount` (and/or `data.created`/address) to align relative ordering with submission order, or extend the PoA bridge API/response to expose a stable per-withdrawal index/nonce so `findMatchingWithdrawal` can select the entry matching not just `assetId` but also `amount` and `destinationAddress` (or reject/serialize batches containing duplicate assetIds for the PoA route until the API supports disambiguation).

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
