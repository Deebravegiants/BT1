### Title
Direct token donation into a curve `Pair` can zero (or underflow) the virtual-reserve gap and permanently brick `Router._computeBuy`'s overflow-cap path, freezing unsold curve supply - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps an oversized buy at the pair's *live* ERC20 balance (`pair.tokenBalance()`) but subtracts that live balance from the *stored* virtual reserve (`reserveToken`) without validating that the live balance can never reach or exceed the stored reserve. An unprivileged actor can inflate `pair.tokenBalance()` by directly `transfer`-ing the launched `Token` into the `Pair` (a plain ERC20 donation, no special role required), shrinking or eliminating the 250M-token gap that the whole cap mechanism depends on. Once the gap is closed, every subsequent capping buy reverts (`OverflowCapDegenerate` or an arithmetic-underflow panic), permanently bricking large/final buys on that curve.

### Finding Description
`Router._computeBuy` (packages/contracts/src/Router.sol:127-148):
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```
`realBalance` comes from `Pair.tokenBalance()`:
```solidity
function tokenBalance() external view returns (uint256) {
    return IERC20(launchedToken).balanceOf(address(this));
}
``` [1](#0-0) 

This is a **live** `balanceOf` read, directly inflatable by anyone via a plain `Token.transfer(pair, amount)`. `reserveToken`, by contrast, is the *stored* virtual reserve mutated only inside `Pair.swap` (buys/sells), which decreases `tokenReserve` and the real balance by the exact same `tokenOut` on every buy: [2](#0-1) 

Because both quantities move in lock-step during normal buys, the gap `reserveToken - realBalance` is a mathematical constant equal to `LP_RESERVE` (250M tokens) for the life of the curve — this is exactly what `test_inv_virtualReserveAlwaysExceedsRealBalance` in `GraduationInvariants.t.sol` asserts, but only under organic buy/sell traffic: [3](#0-2) 

A direct ERC20 donation of the launched `Token` into the `Pair` breaks this invariant: it raises `realBalance` without touching `reserveToken`. Doing this round-trip (buy tokens on the curve, then `transfer` them straight back to `pair`) lets an attacker shrink the gap arbitrarily, up to fully closing it. Once `realBalance >= reserveToken`, the next buy whose curve math wants to cap (`tokensOut > realBalance`) computes `cappedReserveToken = reserveToken - tokensOut` where `tokensOut == realBalance >= reserveToken`, which either:
- equals `0` → explicit `revert OverflowCapDegenerate()`, or
- exceeds `reserveToken` → an unchecked-arithmetic panic (underflow revert) in Solidity 0.8.

Both are unconditional reverts. `_computeBuy` is called from both `Router.buy` (the entry point `Bonding.buy` / `Zap.buy` funnel every curve trade through) and the `previewBuy`/`getAmountOut` views, so once the gap is closed the affected curve can no longer execute (or even quote) any buy that would need the overflow cap — i.e. any buy near the tail of the curve, including the one that would otherwise trip the supply-based graduation trigger (`IPair.tokenBalance() == 0`).

### Impact Explanation
This bricks trading on the affected curve at exactly the point where remaining supply is small: the tail-end buy(s) that would normally cap out and either finish selling the curve or trigger graduation instead revert forever (donated tokens permanently sit in `Pair`; the gap can never widen back since nothing removes donated tokens pre-graduation). Consequences:
- Remaining unsold real tokens on the curve become permanently unsellable via the bonding curve (frozen inventory), and traders attempting to buy the tail of the curve are permanently blocked.
- If the USD trigger is also out of reach (e.g. LT hasn't appreciated enough), the token can never graduate via the supply trigger, since the triggering buy itself reverts — a permanent DoS on graduation for that token, freezing the ability of remaining traders/creator to ever transition the token off the bonding curve.
This satisfies the "permanent freezing of trader ... funds" bar.

### Likelihood Explanation
Fully reachable by a single unprivileged address: `Token.transfer` is a standard ERC20 call requiring no role, and the round-trip (buy real tokens off the curve, then donate them to the `Pair`) costs only the LT/USDC spent acquiring the donated tokens — no privileged action, upgrade, or off-chain dependency is needed. The attack scales with how much of the 250M-token gap the attacker is willing/able to close; even a partial closure bricks any buy whose cap-branch `tokensOut` would exceed the shrunk gap, which is guaranteed to happen as the curve approaches depletion.

### Recommendation
Do not derive the cap subtraction from the live, donation-inflatable `pair.tokenBalance()`. Either:
- Cap `realBalance` itself at `min(realBalance, reserveToken)` before using it in the `tokensOut`/`cappedReserveToken` computation, or
- Track sellable supply via an internal accounting variable that only changes through `Pair.swap`, immune to direct ERC20 donations (mirroring how `_prepareGraduationLiquidity` already treats donated tokens as burnable dust rather than as capacity), and
- Explicitly guard `cappedReserveToken` against underflow (not just `== 0`) and treat any state where `realBalance >= reserveToken` as "unsold dust to be swept," rather than allowing it to revert the trade path outright.

### Proof of Concept
1. Launch a token normally; curve seeds `reserveToken = totalSupply (1e9)`, real `tokenBalance = curveSupply (750M)` — gap = `LP_RESERVE = 250M`.
2. Attacker buys a large chunk of tokens off the curve via `Zap.buy`/`Bonding.buy` (both `reserveToken` and `tokenBalance` decrease by the same amount — gap unchanged).
3. Attacker calls `Token.transfer(pairAddr, tokensJustBought)` directly (no role required) — `tokenBalance()` jumps back up by that amount, `reserveToken` is untouched — gap shrinks by the donated amount.
4. Attacker repeats steps 2-3 (loop of buy-then-donate) until the gap between `reserveToken` and live `tokenBalance()` is fully closed (or nearly so).
5. Any subsequent buy whose `_computeBuy` math would need to cap (`tokensOut > realBalance`) now hits `cappedReserveToken == 0` → `revert OverflowCapDegenerate()`, or underflows and panics — `Router.buy` (and therefore `Bonding.buy`/`Zap.buy`) permanently reverts for that curve's tail-end trades, and the supply-based graduation trigger can never fire.     function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
