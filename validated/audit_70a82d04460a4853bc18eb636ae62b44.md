### Title
Unchecked ERC20 `transfer` Return Value in Tron IntentGatewayV2 Withdrawal/Sweep Path Can Permanently Freeze Escrowed Funds - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of the Intent Gateway, the `withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed ERC20 tokens using a raw low-level `.call()` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`), but never inspecting the ABI-encoded boolean returned by the token's `transfer()` function. This mirrors the exact "unchecked return value" bug class from the external report (`IComptroller.exitMarket`/`enterMarkets`), applied here to ERC20 `transfer()` return data instead of a comptroller error code. If a token returns `false` instead of reverting on failure, the gateway still decrements escrow accounting and marks the order/withdrawal as finalized, even though no tokens were actually delivered.

This contrasts with the main EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`), which correctly uses OpenZeppelin's `SafeERC20.safeTransfer` (which reverts on a falsy or missing return value) for the same escrow-release logic: [5](#0-4) 

The Tron contract is inconsistent even internally: incoming transfers use `safeTransferFrom` (e.g. line 405 `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`), while outgoing releases in `withdraw()`/`SweepDust` use the unchecked raw-call pattern — confirming the return-value check was dropped specifically on the value-release path.

### Impact Explanation
`withdraw()` is reached via `onAccept()`, which is invoked by the ISMP host after delivering a relayed cross-chain `RedeemEscrow`/`RefundEscrow` message from a paired IntentGateway instance — i.e., it is triggered by relayed proofs following a normal solver fill or user cancellation flow, not by any privileged actor. For any escrowed token whose `transfer()` can return `false` without reverting under specific conditions (a class of standard, non-malicious ERC20 tokens; e.g. legacy implementations that signal failure via boolean rather than revert), a failed transfer is silently accepted as successful. The result: escrow accounting is decremented, the order is marked filled/refunded, and the intended beneficiary (solver or user) never receives their tokens — a permanent loss of funds trapped in the contract with no path to re-claim them, since the order is already finalized.

### Likelihood Explanation
Likelihood depends on the specific ERC20 token configured for a given deployment/order (the token address is protocol-configurable per order, not restricted to a fixed safe list), so this is not exploitable against every token, but for any token that follows the boolean-return failure convention (a well-documented ERC20 compatibility issue that OpenZeppelin's `SafeERC20` was created specifically to guard against), a benign transient failure (e.g., temporary pause, allowance/blacklist-style controls that return false instead of reverting) results in silent fund loss without any attacker action required — no special privileges or malicious actor needed, only relaying an already-valid settlement message with a non-standard token type in the pool.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` for all outgoing token releases in the Tron `IntentGatewayV2.sol`, matching the pattern already used in `IntentsBase.sol` (`evm/src/apps/intentsv2/IntentsBase.sol` line 468) and for incoming transfers in the same file. At minimum, decode and require the returned boolean to be `true` (or the return data to be empty, per EIP-20 non-standard tokens) before treating any `transfer` call as successful, exactly as recommended in the external report to require `NO_ERROR`/success codes rather than ignoring them.

### Proof of Concept
1. Deploy (or configure) an ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (a real, standards-permitted implementation pattern).
2. A user places an order escrowing this token via `placeOrder` on the Tron `IntentGatewayV2`.
3. A solver fills the order on the destination chain; the source chain's ISMP host relays a `RedeemEscrow` request and calls `onAccept()` → `withdraw()`.
4. Craft/trigger a condition under which the token's `transfer()` call returns `false` (e.g., a pause flag, internal restriction) but does not revert.
5. `withdraw()` at `evm/tron/contracts/apps/IntentGatewayV2.sol:706` sees `success == true` (the call didn't revert) and proceeds to decrement `_orders[...]`, mark `_filled[...]`, and emit `EscrowReleased`, even though the solver received zero tokens — the escrowed funds are now permanently stuck with no remaining code path to release them again for that commitment.
