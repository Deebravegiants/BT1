### Title
Webhook `shop` (and `topic`) headers are trusted by the gem without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the signable payload from the raw HTTP body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC over the body and then blindly trusts `request.shop`/`request.topic` to route and label the payload passed to the app's handler. Because the identity fields are not bound to the cryptographic signature, an attacker who legitimately receives one signed webhook (e.g. by installing the app on their own store) can replay that exact `(body, hmac)` pair while substituting an arbitrary `shop-domain` header, producing a request that passes HMAC validation but is falsely attributed to a victim shop.

### Finding Description
The equality the gem should enforce is:

`shop reported to the handler == shop that the HMAC-signed bytes originated from`

Instead, the gem only enforces:

`HMAC(secret, raw_body) == received_hmac` [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively, so `shop`, `topic`, `webhook_id`, and `api_version` — all read from headers — are entirely outside the signed data: [2](#0-1) 

`Registry.process` validates the HMAC on the whole request object, then immediately forwards `request.shop` (and `request.topic`) to the handler as trusted identity/tenant data: [3](#0-2) 

Since the HMAC only proves the *body* bytes are authentic Shopify content, but says nothing about which shop or topic they belong to, an attacker holding one legitimately-signed `(raw_body, hmac)` pair (for example, from their own store's webhook delivery, which they are fully entitled to receive) can resend it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` will still succeed because it only recomputes the signature over `@raw_body`: [4](#0-3) 

The gem then hands the app a `WebhookMetadata` claiming the payload is for the victim shop, when the HMAC-authenticated content actually only proves it came from the attacker's own shop.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is supposed to provide: an unprivileged internet user (any merchant/developer who can install the app on their own store, requiring no `api_secret_key`, no access token, and no privileged account) can make the app process attacker-supplied, HMAC-"valid" webhook bodies under an arbitrary shop identity of their choosing. Depending on the topic exploited (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, `orders/create`), this can trigger cross-tenant state changes, data deletion, or data disclosure logic keyed off `WebhookMetadata#shop` for a shop the attacker does not control — this is a cross-tenant access vulnerability rooted entirely in this gem's `Webhooks::Request`/`Webhooks::Registry` code.

### Likelihood Explanation
Moderate-to-high. The attacker does not need to intercept traffic or possess any secret; they only need to (a) install the target app on a store they control to legitimately receive one signed webhook, and (b) replay that untouched body/HMAC pair to the app's public webhook URL with a different `shop-domain` header. Both actions require nothing beyond ordinary, unprivileged use of the Shopify platform.

### Recommendation
Bind the identity fields into the signed payload verification, or otherwise cryptographically/authoritatively re-derive the shop from a source the HMAC does cover. Concretely:
- Extend `to_signable_string` (or add a secondary check in `Registry.process`) to incorporate `shop`, `topic`, and other routing headers into what is verified, or
- Require the host application to independently confirm that `request.shop` corresponds to a shop with an active, previously-stored session/installation before trusting the webhook payload for that shop, and document this requirement prominently since the header itself is not authenticated by this gem.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, giving `raw_body` and a valid `X-Shopify-Hmac-SHA256` value computed by Shopify over that body with the app's `client_secret`.
2. Replay the exact same `raw_body` and `hmac` value to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `raw_body` — [5](#0-4)  — so validation succeeds despite the mismatched shop header.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [6](#0-5)  and performs tenant-scoped actions against the victim shop using attacker-controlled body content.
