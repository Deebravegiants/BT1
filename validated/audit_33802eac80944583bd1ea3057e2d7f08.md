### Title
Zero-length `erc20TokenAddresses` bypasses all value-conservation checks in Emporium external action, enabling theft of any asset held by `EmporiumUpgradeable` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When a `transact()` call targets `HINKAL_EMPORIUM_ACTION_ID` with `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose public input is verified against `MainEVMCircuitMin` — a circuit that only proves `message = Poseidon(messageSeed)` and passes `outTimeStamp`/`calldataHash` through unconstrained. Because the token array is empty, both `Hinkal.transact`'s balance-reconciliation loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loop iterate zero times, so an attacker can embed arbitrary `EmporiumOperation`s (with `signerAddress = address(0)`, which skips the EIP-712 signature check in `verifyWallet`) in `externalActionMetadata` and drain any asset currently held in the Emporium contract's balance with no proof-based or bookkeeping-based constraint whatsoever.

### Finding Description
The broken equality is the value-conservation invariant that should hold for every token moved by an external action: `balanceDif (actual) == amountChanges + utxoAmount (proof-constrained)`. With `erc20TokenAddresses.length == 0` this equality is never even evaluated on either side.

Path:
1. `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`.
2. `formInputEmporiumMin` (`contracts/CircomDataBuilder.sol:150-161`) builds a 3-element public input `[emporiumMessage, timeStamp, calldataHash]`.
3. The corresponding circuit `MainEVMCircuitMin` (`circuits/MainEVMCircuitMin.circom:1-18`) only constrains `message <== Poseidon(messageSeed)` and passes `outTimeStamp`/`calldataHash` through as free public signals — no nullifiers, no root-hash inclusion proof, no amount, no token identity is constrained at all.
4. `Hinkal.transact` verifies this trivial proof, then calls `_externalTransact` (`contracts/Hinkal.sol:234-261`), whose `deltaAmountChanges` array has length 0 and whose reconciliation loop in `transact` (`contracts/Hinkal.sol:97-147`) also iterates 0 times — no `balanceDif` is ever computed or checked.
5. `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) decodes an attacker-supplied `EmporiumStack` from `externalActionData.externalActionMetadata`, and its `balancesBefore`/`balancesAfter` loop and `BalanceChangeShouldBePositive` check are both driven by `circomData.erc20TokenAddresses.length`, i.e. zero iterations — completely skipped.
6. `verifyWallet` (`EmporiumUpgradeable.sol:302-316`) only marks `usedMessages[emporiumMessage] = true` and returns immediately when `stack.signerAddress == address(0)`, performing **no** signature check in that branch.
7. The attacker sets an `EmporiumOperation` with `invokeWallet=false`, `endpoint = victim's token/NFT contract`, and `callData` transferring the asset out of the Emporium contract's own balance to the attacker. This executes via `op.endpoint.call{value: op.value}(op.callData)` (`EmporiumUpgradeable.sol:112`) with no accounting.

Since `calldataHash` (which does include `externalActionData`, hence the malicious `ops`) is only a *pass-through* public signal never algebraically tied to any spend/amount inside the Min circuit, embedding the malicious metadata does not require satisfying any real constraint — the attacker only needs to know a `messageSeed` whose Poseidon hash they freely choose as `emporiumMessage`, which is trivial since they control both values.

None of the standard guards catch this: `performHinkalChecks`/`dimensionsCheck` only require internal-array-length consistency (all zero, which is self-consistent); `checkOnchainCreation` is a no-op on empty arrays; `rootHashExists` merely checks a historical valid root exists, without tying it to a spent leaf for this call; and `BalanceChangeShouldBePositive` is inside the skipped for-loop.

### Impact Explanation
Any asset (ERC20/ERC721/ERC1155) sitting in `EmporiumUpgradeable`'s own token balance from a prior legitimate deposit/op can be moved out by an unprivileged attacker to any address they choose, with zero proof coverage and zero balance bookkeeping. This is direct theft of victim (or protocol-custodied) assets — Critical severity, matching "direct theft of shielded or in-flight user funds ... proof or nullifier verification bypass." It is repeatable for every distinct `emporiumMessage`/token instance an attacker can find residing on the Emporium contract.

### Likelihood Explanation
Preconditions: `HINKAL_EMPORIUM_ACTION_ID` must be a registered external action (standard deployment state) and some victim asset must currently reside in the Emporium contract's balance (a normal, expected state after any prior Emporium-custodied op). The attacker needs no special role — only the ability to call `Hinkal.transact` with a self-generated trivial `MainEVMCircuitMin` proof (Poseidon-hash of a self-chosen seed) and to craft `externalActionMetadata` bytes. Cost is a single transaction and proof generation for a two-input circuit; feasibility is high and the attack is repeatable against every victim asset held on Emporium.

### Recommendation
Do not allow the Emporium-Min path to invoke arbitrary `op.endpoint.call`s that move tokens with no accounting. Either (a) require `erc20TokenAddresses`/dimensions to cover every token touched by `EmporiumStack.ops` even for the "Min" case so `balancesBefore/After` and slippage/utxo checks run, or (b) restrict CASE-2 stateless calls with `signerAddress == address(0)` to non-value-moving/whitelisted selectors, and require a real EIP-712 signature or Hinkal-side authorization for any op capable of transferring Emporium-held assets, regardless of token-array length.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient), register `HINKAL_EMPORIUM_ACTION_ID`.
2. Seed victim asset into Emporium balance (e.g., victim's prior legitimate Emporium op leaves an ERC721 token owned by the Emporium contract, or an ERC20 balance sitting on it).
3. Build `EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: victimTokenAddr, invokeWallet:false, value:0, callData: abi.encodeCall(IERC721.safeTransferFrom/IERC20.transfer, (address(emporium), attacker, tokenIdOrAmount))}]}` and ABI-encode into `externalActionMetadata`.
4. Construct `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` as above, `calldataHash` computed via `getHashedCalldata`, `emporiumMessage = Poseidon(messageSeed)` for an attacker-chosen `messageSeed`.
5. Generate a valid Groth16 proof for `MainEVMCircuitMin` using `messageSeed`, `outTimeStamp`, `calldataHash` as inputs (snarkjs, off-chain).
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
7. Assert: transaction succeeds; victim asset balance in Emporium is now 0 and attacker's balance increased by the stolen amount; assert both sides of the equality `balanceDif (real, measured via `token.balanceOf`) != 0` while `amountChanges + utxoAmount (as computed by the skipped loops) == 0` (since arrays are empty), proving no constraint tied the movement to anything proven.
