### Title
Missing zero-address check on relayer fee withdrawal beneficiary permanently locks relayer fees - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HostManager.sol`, `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The relayer fee withdrawal path lets a relayer specify an arbitrary `beneficiary` address for their accumulated fees. Neither the Substrate `pallet-ismp-relayer` withdrawal logic, nor the destination `HostManager.onAccept`, nor `EvmHost.withdraw()` validate that the beneficiary is non-zero before transferring funds. Combined with the withdrawal message being dispatched with `timeout: 0` (never expires) and the relayer's `Fees` storage being zeroed immediately at dispatch time (not upon confirmed delivery), a zero-address beneficiary permanently locks the withdrawn funds.

### Finding Description
An unprivileged relayer calls `withdraw_fees` with a `WithdrawalInputData` that includes an optional `beneficiary: Option<Vec<u8>>` [1](#0-0) . `Pallet::<T>::withdraw` builds the `WithdrawalParams` from this address with no zero-address validation [2](#0-1) , encodes it, and dispatches a POST request with `timeout: 0`, meaning the request can never be timed out and refunded [3](#0-2) . Immediately after dispatch — before any confirmation that the message was ever delivered or executed successfully — the relayer's `Fees` entry is zeroed, permanently extinguishing their claim [4](#0-3) .

On the EVM destination, `HostManager.onAccept` decodes the `Withdraw` action and forwards it unchecked to `IHostManager(_params.host).withdraw(withdrawParams)` [5](#0-4) . `EvmHost.withdraw()` performs the actual transfer with no check that `params.beneficiary != address(0)`:
```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    if (params.token == address(0)) {
        (bool sent,) = params.beneficiary.call{value: params.amount}("");
        if (!sent) revert WithdrawalFailed();
    } else {
        IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    }
    ...
}
``` [6](#0-5) 

For the native-token branch (`params.token == address(0)`), a low-level `.call{value: ...}("")` to `address(0)` succeeds (no code to revert), so ETH sent there is unrecoverable. For ERC20 fee tokens, OpenZeppelin's `safeTransfer`/`_transfer` will revert on `to == address(0)`, which causes the delivery to fail — but because the request never times out and the `Fees` entry was already zeroed on Hyperbridge, that failed delivery can never be retried into a successful payout nor refunded; the funds sit in the `EvmHost` contract forever, unreachable by the relayer who is owed them.

### Impact Explanation
This results in permanent freezing of relayer fee funds: the relayer's on-chain claim (`Fees` storage) is destroyed at dispatch time regardless of destination outcome, and the corresponding token/ETH balance held by `EvmHost` becomes permanently stuck because the message has no timeout path to trigger a refund. This matches the report's core issue — no zero-address validation before a fund transfer, causing lock-up of funds — reachable through the unprivileged relayer fee withdrawal flow.

### Likelihood Explanation
Likelihood is limited to relayer-supplied input error (accidental zero/garbage beneficiary bytes, or a bug in a relayer's own withdrawal tooling) rather than third-party exploitation of another party's funds, since the withdrawing relayer chooses their own beneficiary. However, no other actor benefits from or can prevent this, and the codebase provides no safety check anywhere along the path to prevent it, so a single malformed extrinsic causes irrecoverable loss.

### Recommendation
Add an explicit zero-address check on `params.beneficiary` in `EvmHost.withdraw()` (and reject in `HostManager.onAccept` before forwarding), and additionally validate `beneficiary_address != [0u8;20]` (and non-empty) in `pallet-ismp-relayer::withdraw` before dispatching, so malformed withdrawal requests fail fast on Hyperbridge before the `Fees` entry is zeroed, rather than silently locking funds downstream.

### Proof of Concept
1. A relayer accrues fees on Hyperbridge for a given destination chain (`Fees::<T>::get(dest_chain, relayer)` > minimum withdrawal amount).
2. The relayer submits `withdraw_fees` with `WithdrawalInputData.beneficiary = Some(vec![0u8; 20])` (or a garbage 20-byte value decoding to `address(0)`).
3. `Pallet::withdraw` dispatches the POST request to `HostManager` with `timeout: 0` and immediately zeroes `Fees::<T>` for that relayer [7](#0-6) .
4. On delivery, `EvmHost.withdraw()` either sends ETH irrecoverably to `address(0)` or reverts on an ERC20 `safeTransfer` to `address(0)` [6](#0-5) .
5. Because the request never times out, it can never be retried into success nor refunded, and the relayer's claim was already erased — the fee amount is permanently unrecoverable.
