### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` (tenant identity) used downstream by `ShopifyAPI::Webhooks::Registry.process` comes from the unauthenticated `X-Shopify-Shop-Domain` header. Because Shopify signs webhooks with the app's single `client_secret` shared across every shop that installs the app, a malicious merchant can capture a validly-signed webhook for their own shop and replay it with a forged shop-domain header to make the host app believe the event belongs to a different (victim) tenant.

### Finding Description
`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed bytes: [3](#0-2) 

`Registry.process` verifies the HMAC and then forwards `request.shop` straight to the app's handler as the authenticated tenant identity: [4](#0-3) 

The documentation explicitly tells integrators that `process` "will verify the request did indeed come from Shopify," and that the handler receives `shop` as "the shop domain of the webhook": [5](#0-4) [6](#0-5) 

The broken identity binding, stated as an equality: `hmac_valid(raw_body, app_secret) == true` is treated as implying `request.shop == originating_shop`, but the two are independent — the shop header is bytes that were never signed. Since Shopify webhook HMACs are computed with the app-level `client_secret` (identical for all shops that install the app, not a per-shop secret), any shop that installs the app can legitimately obtain a validly-signed `(raw_body, hmac)` pair for events in its own store, then resend that exact pair to the app's webhook endpoint while substituting the `shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuine), and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen value, causing the host app — following exactly the documented pattern — to attribute the attacker's data to the victim's tenant.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce ("verify the request did indeed come from Shopify" + per-shop `data.shop`). A host app that keys any per-shop logic (e.g., updating shop-scoped records, triggering shop-specific side effects, looking up which shop's session/settings to use) off `WebhookMetadata`/`data.shop` as supplied by this gem can be made to process attacker-supplied webhook content under a victim shop's identity, i.e. cross-tenant data injection/confusion — a Critical-class impact under the rules (cross-tenant access) reachable purely through this gem's own verification logic.

### Likelihood Explanation
Any actor who can install the target Shopify app on their own store (a normal, unprivileged action for public apps) can trigger real webhooks for that store, capture the raw body and its valid HMAC, and replay them to the app's public webhook endpoint with a modified shop header — no access token, secret, or privileged account is required.

### Recommendation
Include the shop domain (and ideally webhook id / topic) in the signed material used for verification, or cross-check the header-derived `shop` against a value obtained independently (e.g., resolve the webhook subscription/shop via the Shopify API using the `webhook_id`) before dispatching to the handler. At minimum, document prominently that `request.shop` is not authenticated by `Registry.process` and must not be trusted for tenant-sensitive actions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, giving the app access to real webhooks signed with the app's shared `client_secret`.
2. Attacker triggers an event (e.g. `orders/create`) on their own shop and captures the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` sent by Shopify — `H` is a valid HMAC-SHA256 of `B` under the app's `client_secret`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` yields `hmac` matching `H` and `shop == "victim-shop.myshopify.com"`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
6. The app's handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload actually originated from `attacker-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:190-199`).
