## #Vulnerability found

### Title
Webhook `shop-domain` header is not covered by HMAC validation, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` only returns the raw request body, while `shop` (from the `shop-domain` header) is read independently and passed unauthenticated to the webhook handler. Any attacker who can obtain one valid `(body, hmac)` pair — trivially possible by installing the app on their own Shopify shop and triggering an event — can replay that exact body with a forged `shop-domain` header claiming to be a different (victim) merchant, and `HmacValidator.validate` will still succeed because the HMAC never covered the header.

### Finding Description
The HMAC binding equality that should hold is:
`hmac_valid(body, secret) == true` should imply `shop_that_generated(body) == shop_claimed_in(request)`.

In `Request#to_signable_string`, only `@raw_body` is hashed: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header without being part of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies only what `to_signable_string` returns, i.e. the body, against the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC check passes, and then forwards the *unauthenticated* `request.shop` straight to the handler as the tenant identity: [4](#0-3) 

Because Shopify signs webhooks with the app's single `api_secret_key`/`client_secret` shared across every merchant that installs the app (not a per-shop secret), a valid `(body, hmac)` pair generated by triggering an event on *any* shop that has the app installed — including a shop the attacker themselves controls — remains cryptographically valid no matter which `shop-domain` header value is sent with it. `Registry.process` has no other check tying the header's shop back to the body/HMAC, so the field acted upon (`shop`) is disjoint from the field actually covered by the HMAC (`body`).

### Impact Explanation
This breaks the shop/tenant identity binding for webhook processing: an attacker who controls one installed shop (trivial to set up on a development store) can forge webhook deliveries to the host application's endpoint claiming to originate from an arbitrary victim shop, while keeping full control over the JSON body content (since they trigger the source event themselves). Applications built on this gem rely on `WebhookMetadata#shop` (populated from `request.shop`) to select which merchant's session/data to act on, so this allows cross-tenant data manipulation — e.g. spoofing `app/uninstalled`, `shop/redact`, or `customers/redact` for a shop the attacker doesn't own, causing another merchant's data/session/tokens to be deleted or otherwise mutated by application logic that trusts `data.shop`. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) uses `ShopifyAPI::Webhooks::Registry`/`Request` as documented and (b) is installable by arbitrary third parties (the normal Shopify app distribution model), since obtaining a valid `(body, hmac)` pair requires only installing the app on one's own store and triggering the desired event — no secrets, tokens, or privileged access are required.

### Recommendation
Include the shop domain (and ideally webhook id / topic) inside the HMAC-signed content, or otherwise cryptographically bind the claimed shop to the verified payload before trusting `request.shop`/`WebhookMetadata#shop`. At minimum, document that consumers must independently verify the delivered shop is one that has a valid, previously-established session/installation before acting on data keyed by the webhook's `shop-domain` header, since the gem's `HmacValidator` does not authenticate that header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker triggers a webhook event on their own store (e.g. `app/uninstalled`, or crafts arbitrary JSON payload fields on an event they control), and captures the resulting POST: `raw_body` plus the valid `X-Shopify-Hmac-Sha256` header (correctly computed by Shopify using the app's single `api_secret_key`).
3. Attacker replays this exact request to the app's webhook endpoint but replaces the `X-Shopify-Shop-Domain` header value with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `HmacValidator.validate(request)` computes `compute_signature(request.to_signable_string, api_secret_key)` — this only hashes `raw_body`, which is unchanged, so the signature still matches: [5](#0-4) 
5. `Registry.process` invokes the handler with `shop: request.shop` = `"victim.myshopify.com"`, even though the payload actually originated from the attacker's own store, letting the attacker trigger handler logic scoped to the victim's tenant.
