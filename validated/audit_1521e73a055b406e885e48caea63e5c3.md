### Title
Orb-core reports signup success without backend confirmation when `user_centric_signup` is set - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::do_signup` in `src/plans/mod.rs` short-circuits the authoritative backend enrollment call whenever the scanned user QR-code data marks the signup as `user_centric_signup`. In that branch, the orb never invokes `enroll_user` (the function that actually calls the backend's `signup_post`/`signup_poll` endpoints to confirm the identity was uniquely enrolled) and instead derives a local `success` boolean purely from a client-computed `signup_reason`. This is structurally analogous to `ERC1155Fuse::_transfer` silently returning without reverting when the "to" address already matches: the state-changing/verifying step is skipped, yet the surrounding code still reports a positive outcome as if the authoritative operation completed.

### Finding Description
In `do_signup`, after the biometric pipeline runs, the code computes `signup_reason` purely from local pipeline results and `detect_fraud` (which, in this build, always returns `false` because fraud checks were stripped, see lines 1390-1406): [1](#0-0) 

It then branches on `user_centric_signup`: [2](#0-1) 

When `user_centric_signup` is `true` and `ignore_user_centric_signups` is not set, the orb:
- never calls `self.enroll_user(...)`, which is the only code path that actually contacts the backend `signup_post`/`signup_poll` endpoints to confirm the enrollment succeeded server-side [3](#0-2) 
- instead sets `success = signup_reason == SignupReason::Normal`, a value computed entirely from local, client-side fraud/pipeline state.

This mirrors the ERC1155Fuse issue: the function that is supposed to perform/validate the authoritative state transition (`enroll_user` making the backend request, analogous to `_transfer` moving the balance) is skipped, but the caller still proceeds as if the transition succeeded (`result.success` is set, and this value is propagated to `dbus::Signup::signup_finished(dbus_ctx, success)` and to the debug report / operator UI at lines 370-384 and 658-662) without any external confirmation that the identity was actually and uniquely bound on the backend.

### Impact Explanation
Because `success` is asserted locally without the backend round-trip, the orb can report/propagate a "successful signup" (to dbus consumers, debug reports, and UI/operator flow) even when the backend never confirmed unique/authorized enrollment for that identity commitment. This can lead to a misattributed or falsely-confirmed signup state at the orb level, diverging from the ground truth that only the backend (via `enroll_user`/`signup_post`) can authoritatively establish — the same "state changed without validation, but no revert/error reported" pattern as the reference finding.

### Likelihood Explanation
Reachable in the normal, non-test signup flow whenever the backend-issued user QR-code data sets `user_centric_signup: true` (as seen even in the `skip-user-qr-validation` test data shape, confirming the field's presence) and the `ignore_user_centric_signups` config flag is left at its default. No privileged/hardware/malicious-peer conditions are required — it is purely a client (Orb) logic branch taken on standard unprivileged signup input.

### Recommendation
Do not treat `user_centric_signup` as sufficient to mark local success. Require an explicit backend confirmation callback/poll (equivalent to what `enroll_user`/`signup_poll` provides) before setting `result.success = true` and before notifying dbus/UI of a successful signup, so that the reported outcome always reflects the backend's authoritative decision rather than only local pipeline/fraud state.

### Proof of Concept
1. Configure/serve a user QR-code whose backend-provided data sets `user_centric_signup = true` (see `orb_qr_link::UserData::user_centric_signup` populated in `backend::user_status::request`, `src/backend/user_status.rs` lines 203-244).
2. Complete a biometric capture/pipeline such that `pipeline` is `Some(..)` and `detect_fraud` returns `false` (the default in this build since fraud checks are removed, `src/plans/mod.rs` lines 1390-1406).
3. Observe in `do_signup` (`src/plans/mod.rs` lines 639-656) that `enroll_user` (the only code performing the actual backend `signup_post`/poll round trip) is never called, yet `success` is set to `true` purely from local state, propagating a "successful signup" result to `debug_report`, dbus, and UI without backend confirmation.
