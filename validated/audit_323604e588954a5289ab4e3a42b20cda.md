### Title
Unescaped delimiter in POA bridge withdrawal memo allows destination-tag/segment injection - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts)

### Summary
`createWithdrawMemo` builds the on-chain withdrawal memo by naively joining `"WITHDRAW_TO"`, the destination address, and an optional user-supplied `xrpMemo`/`destinationMemo` with the `:` delimiter, without rejecting or escaping `:` inside either field.

### Finding Description
`createWithdrawIntentPrimitive` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts` builds the `memo` field for POA-bridge `ft_withdraw` intents via `createWithdrawMemo`: [1](#0-0) 

The memo is assembled as an array `["WITHDRAW_TO", normalizedAddress]`, optionally appending `xrpMemo`, and finally `.join(":")`. Both `normalizedAddress` and `xrpMemo` (exposed publicly as `WithdrawalParams.destinationMemo`) flow into this join with no check that they don't themselves contain the `:` delimiter used to separate the three logical fields (command, address, tag). [2](#0-1) 

This mirrors the CRLF-injection bug class in the report: a low-trust caller-controlled value (`destinationMemo`, here analogous to the FTP filename) is concatenated raw into a line/segment-oriented protocol format (the colon-delimited `WITHDRAW_TO:<address>:<tag>` memo, analogous to the FTP control line) whose only protection is that the field normally doesn't contain the delimiter. Nothing in `createWithdrawMemo`, nor in `validateWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (which validates address format and XRPL destination-tag *presence*, not memo *content*), rejects a `destinationMemo` containing `:`. [3](#0-2) 

For XRPL/exchange-style destinations that require a numeric destination tag to disambiguate which internal sub-account should be credited from a shared deposit address, this memo is exactly the parsed handoff between the NEAR intents layer and the off-chain bridge/relayer that ultimately writes the on-chain XRP transaction memo/tag. If a caller supplies a `destinationMemo` such as `"1:evilTag"` or one containing additional colons, the resulting memo `WITHDRAW_TO:<address>:1:evilTag` no longer has the expected 3-field shape, and any downstream parser that splits on `:` and takes a fixed index (e.g., "last field is the tag") will resolve a different destination-tag value than the one the caller was authorized/expected to set — potentially routing the credit to a different sub-account behind the same on-chain address.

### Impact Explanation
If the destination-tag segment can be altered by injecting extra `:`-delimited content, funds withdrawn through the POA bridge to a shared deposit address (the common XRPL exchange pattern) could be credited to a different internal account than the one intended/validated — i.e., misdelivery of funds to a wrong (tag-identified) recipient with no on-chain recovery, matching the "funds delivered to a wrong address/chain/contract with no recovery" Critical/High impact bucket.

### Likelihood Explanation
This requires: (1) a caller able to supply an arbitrary `destinationMemo` string (a public SDK parameter, no character restriction enforced anywhere in this repo), and (2) a downstream consumer (POA bridge relayer / exchange) that parses the `WITHDRAW_TO:...` memo by delimiter position rather than by strict format validation. The repo-side root cause — unescaped, unvalidated delimiter-bearing input joined into a structured protocol string — is concretely present and easy to trigger; whether the actual POA relayer's parser is vulnerable to the injected extra segment cannot be confirmed from this repo alone, since that parsing logic lives outside the scanned packages.

### Recommendation
- Reject (throw) if `destinationAddress` or `destinationMemo`/`xrpMemo` contains the `:` delimiter (or any character not in the expected charset) before constructing the memo in `createWithdrawMemo`.
- Alternatively, encode fields unambiguously (e.g., length-prefixed or percent-encoded) so the delimiter cannot be forged by user input, following the same principle as `packages/crosschain-assetid/src/stringify.ts`, which correctly escapes reserved characters with `encodeURIComponent` before joining with `:`. [4](#0-3)

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}

export function stringify1cs(o: OneCsAsset): string {
	const ref = encodeURIComponent(o.reference);
	const sel = o.selector != null ? `:${encodeURIComponent(o.selector)}` : "";
