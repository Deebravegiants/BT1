### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, allowing cross-tenant data confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers without being part of the signed payload. `Registry.process` validates only the body HMAC and then forwards `request.shop` (and `request.topic`) unchecked into `WebhookMetadata`, which host applications use to route/scope data to a specific merchant.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body, and `shop`/`topic`/`webhook_id`/`api_version` are parsed from headers that are entirely outside the HMAC computation: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` (both unauthenticated header values) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further validation: [4](#0-3) 

This breaks the intended identity binding: **HMAC-authenticated body ≠ shop claimed as the tenant identity**. The HMAC only proves "this body byte-sequence was produced with knowledge of the app's `client_secret`" (i.e., it originated from a legitimate Shopify webhook delivery to *this app*, for *some* installed shop). It proves nothing about which shop the `x-shopify-shop-domain` header actually names. Since a Shopify app can be installed on many shops (including one an attacker legitimately controls, e.g. a free/dev store), the attacker can:

1. Install the target app on their own shop and trigger a webhook so Shopify sends a body with a **valid** HMAC (signed with the app's real secret) for a topic they choose.
2. Capture that raw body + valid HMAC header and replay it to the app's webhook endpoint, **but substitute the `x-shopify-shop-domain` header** with a victim shop's domain (and/or swap `x-shopify-topic`).
3. Because `HmacValidator.validate` never includes `shop` or `topic` in `to_signable_string`, the forged headers pass validation unchanged, and `Registry.process` dispatches the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`.

Any host application that follows the documented pattern of using `WebhookMetadata#shop` to select the merchant session/tenant to operate on (e.g., look up the merchant's access token and apply the parsed body's data against that merchant's records) will now write/attribute attacker-controlled body content to the victim tenant's data — a cross-tenant write, using only an unprivileged install of the same public app.

### Impact Explanation
This crosses the tenant boundary the report class targets: "a shop authenticated versus the shop stored as a session key" — the HMAC authenticates that the payload came from *a* legitimate delivery for the app, but the shop identity the handler acts on is taken from an unauthenticated header. This enables cross-tenant access/data injection into another merchant's records without any credential belonging to that merchant, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Requires only that the attacker can install the target app on a shop they control (an unprivileged capability available to any Shopify developer/merchant) and can send an HTTP request with modified headers to the app's public webhook endpoint. No secret material or privileged account for the victim shop is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed payload used for HMAC validation (or independently authenticate the shop domain against the session/store that installed the app, e.g. by validating it exists in the app's own record of installed shops before trusting it) so that the tenant-identifying headers cannot be forged independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., `orders/create`) causing Shopify to POST to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and the JSON body.
3. Attacker replays this exact body/HMAC to the same endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts it; `HmacValidator.validate` succeeds because only `raw_body` is signed: [5](#0-4) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`: [6](#0-5) 
6. Any handler logic keyed on `data.shop` now operates on the victim tenant using attacker-supplied body content.
