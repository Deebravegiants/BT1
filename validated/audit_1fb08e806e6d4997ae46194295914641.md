## Title
Webhook Shop-Domain Spoofing via HMAC Scope Mismatch — Cross-Tenant Webhook Injection - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook using `Utils::HmacValidator.validate`, but the HMAC signature only covers the raw request **body**. The `shop` (and `topic`, `webhook_id`, `api_version`) values that the handler trusts as the tenant identity are read straight from unauthenticated HTTP headers and are never included in the signed payload. This breaks the identity binding `hmac_verified_bytes == bytes_used_for_tenant_identification`, exactly analogous to the reentrancy-guard mismatch in the reference report, where the guard protected one code path while a different, unguarded path acted on the same state.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed independently from HTTP headers that are not part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the *whole request*, then forwards the unauthenticated `request.shop` and `request.topic` values to the app's handler as the tenant/topic identity: [4](#0-3) 

Because Shopify signs webhooks with the app's single `api_secret_key`, which is shared across **every** shop that installs the app, any merchant who installs the app (including an attacker's own free/dev store) can legitimately receive a webhook whose body+HMAC pair is valid for the *shared* secret. That attacker can then replay the exact same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers for a victim shop. `HmacValidator.validate` still returns `true` (it never looked at those headers), so `Registry.process` dispatches the attacker-chosen body to the handler tagged with the victim's shop domain — the app has no way to distinguish this from a genuine webhook for that victim.

This reproduces the reference bug class precisely: a field that is *acted upon* (`shop`, used for tenant routing/session lookup by the host app's handler) is not *covered* by the cryptographic guard (`hmac`, which only binds the body).

### Impact Explanation
This allows cross-tenant request injection: an attacker-controlled shop can forge webhook deliveries that the app's handler will process as if they originated from an arbitrary victim shop domain, since the shop field used for tenant identification is not bound to the HMAC. Depending on the handler logic built on top of `WebhookMetadata#shop` (e.g., updating shop-scoped state, uninstall/GDPR handling, order/customer data ingestion keyed by shop), this can lead to cross-tenant data corruption or disclosure — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires being an app-installing merchant (an unprivileged party with respect to other tenants) capable of triggering any webhook topic on their own store and capturing the raw POST request, then replaying it with a modified shop-domain header to the app's public webhook endpoint. No access token, client_secret, or privileged credential is needed — the attacker's own valid webhook delivery supplies a body+HMAC pair that remains valid under the shared `api_secret_key`.

### Recommendation
Bind the identity fields used for trust decisions into the signed payload, or otherwise cryptographically tie the header-derived `shop`/`topic` to a value verified against the installation record:
- Extend `to_signable_string` (or a dedicated check in `Registry.process`) so the `shop`, `topic`, and `webhook_id` headers are included in what's verified, or
- Require the caller to supply the expected shop/session and assert `request.shop == session.shop` before invoking the handler, rejecting mismatches, rather than trusting the header value implicitly once the body HMAC passes.

### Proof of Concept
1. Install the target app on an attacker-owned dev store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify sends a real webhook: valid `X-Shopify-Hmac-Sha256` computed over the body with the app's shared `api_secret_key`, and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture the raw body and HMAC header from that delivery.
3. Replay the identical body + HMAC to the app's public webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and adjust `X-Shopify-Topic`/`X-Shopify-Webhook-Id` if desired).
4. `Utils::HmacValidator.validate` returns `true` because it only checked the body signature; `Registry.process` dispatches the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the app to process attacker-supplied data under the victim's tenant identity.
