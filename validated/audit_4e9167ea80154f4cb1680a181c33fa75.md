### Title
Webhook shop/topic/webhook-id/api-version headers are trusted but not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the tenant-identifying `shop-domain` header (along with `topic`, `webhook-id`, and `api-version`) is never included in the signed payload. This breaks the intended binding `hmac(secret, signed_bytes) == hmac(secret, bytes_the_app_acts_on)`, since the "bytes acted on" (the `shop` field routed to the app's handler) are a strict superset of the "bytes verified" (only `@raw_body`).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of `@raw_body`) via `Utils::HmacValidator.validate(request)`, then immediately forwards the header-derived `shop` (and other header fields) into `WebhookMetadata`, which is handed to the app's `handle` callback as the trusted tenant identity for the event: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` const with no independent verification against the signed bytes: [4](#0-3) 

`HmacValidator.validate` performs a straightforward `secure_compare` of the computed and received signatures over `to_signable_string` only — it has no visibility into, and does not bind, any header field: [5](#0-4) 

Equality that should hold but doesn't:
`shop_used_by_handler (from x-shopify-shop-domain header) == shop_covered_by_hmac (not present in signable string at all)`.

Because the signature only covers the JSON body, any party who has legitimately received one webhook (with a valid signature) for their own shop can replay the same `raw_body` + `hmac-sha256` header to a target application while substituting the `x-shopify-shop-domain` header (and/or `topic`/`webhook-id`) for a different tenant. `Registry.process` will pass HMAC validation (since only body bytes are checked) and dispatch the request to the handler tagged with the attacker-chosen `shop`, `topic`, and `webhook_id` values.

### Impact Explanation
This crosses the tenant boundary this library is supposed to preserve: a webhook payload can be replayed and re-labeled to impersonate a different Shopify store than the one it actually originated from, while still passing this gem's authenticity check. Host applications that key their DB updates, entitlement changes, or side effects off `WebhookMetadata.shop`/`topic`/`webhook_id` (as documented and expected usage of this API) will process forged/cross-tenant events as if legitimate. This matches the "cross-tenant access" criterion for Critical/High impact in this class of finding, since the identity binding an unprivileged actor can break is exactly "shop field acted upon by the handler" vs. "shop bytes verified by HMAC."

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the attacker needs at least one genuine, validly-signed webhook body+HMAC pair to replay (e.g., from their own store, or from any publicly observable webhook), and (2) the attacker needs the ability to submit an HTTP request to the target app's webhook endpoint with attacker-controlled headers, which the gem's `Webhooks::Request` accepts uncritically from whatever the host framework passes in. Given webhook endpoints are typically internet-reachable POST endpoints and headers are attacker-controlled in a raw HTTP request, this is readily reachable without any privileged credentials, TLS interception, or `client_secret` access — it requires no more than knowledge of one legitimate signed payload (which the attacker can generate for their own store, since HMAC only covers the body they control).

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind them (e.g., by having `HmacValidator`/`Registry.process` verify the header values against a canonicalized string that includes them, matching how Shopify actually derives/HMACs webhook headers on their end if such extended verification is available). At minimum, document to consumers that `WebhookMetadata.shop`/`topic`/`webhook_id` are not covered by the HMAC and must not be trusted for tenant routing without additional verification (e.g., cross-checking `shop` against a known, previously-registered merchant list). Given `HmacValidator.validate` only ever checks `to_signable_string`, the safest gem-level fix is to widen `to_signable_string` for `Webhooks::Request` to canonically include the shop/topic/webhook-id/api-version header values alongside the raw body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), receiving from Shopify a POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the exact same request to the target app's webhook endpoint, keeping `B` and `H` unchanged, but replaces the header `x-shopify-shop-domain` with `victim-shop.myshopify.com` (a store the attacker does not control) and/or edits `x-shopify-topic`/`x-shopify-webhook-id`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` — this still equals `H` because the signature never covered the header values: [6](#0-5) 
4. Validation succeeds, and the handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ..., ...)` — the app processes attacker-supplied data as an authenticated event belonging to `victim-shop.myshopify.com`.
