## Finding

The reported KinoAccount bug class (signatures lacking a domain/chain separator, enabling cross-chain replay) maps to NEAR's NEP-366 meta-transaction (`DelegateAction`) signing scheme.

### Title
Meta-transaction (`DelegateAction`) signatures lack chain/network binding, enabling cross-network replay - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
`DelegateAction`, the meta-transaction primitive introduced by NEP-366, is signed via `get_nep461_hash()`/`SignableMessage`, which only commits to `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. Unlike ordinary `Transaction`/`TransactionV1`, which embed a `block_hash` that anchors the transaction to one specific chain/fork via `check_transaction_validity_period`, the `DelegateAction` payload has no chain-identifying commitment (no `block_hash`, genesis hash, or chain id) baked into the signed bytes.

### Finding Description
`SignedDelegateAction::verify()` hashes the `DelegateAction` together with a fixed `MessageDiscriminant` (NEP number) and checks the ed25519 signature against that hash: [1](#0-0) 

The hash itself is computed purely from the `DelegateAction` fields: [2](#0-1) 

Compare this with an ordinary `TransactionV0`/`TransactionV1`, which carries a `block_hash` field explicitly used to bound validity to one chain/fork and is checked against `transaction_validity_period`: [3](#0-2) [4](#0-3) 

The `DelegateAction`'s only replay defenses are its `nonce` (checked against the sender's on-chain access-key nonce in `validate_delegate_action_key`) and `max_block_height` (a raw integer, not a hash): [5](#0-4) 

Both of these are properties of *account state* (the access key's stored nonce, and the local block height counter), not of a specific chain's identity. If two independently-running networks share the same account/access-key state at some point in time — for example a testnet or private/forked network seeded from a mainnet state snapshot, or a network that is halted and restarted from a genesis state export (a normal, expected NEAR operational scenario) — a relayer's account on both networks will have the same `public_key` with the same-or-lower nonce, and both networks will eventually reach the same `max_block_height` value. A `SignedDelegateAction` signed by a user for use on network A can then be replayed verbatim by anyone (extracted from the relayer's transaction) into a fresh outer `Transaction::Delegate(...)` on network B, since nothing in the signed hash distinguishes the two networks.

This is the direct structural analog of the reported bug: signature verification omits an EIP-712-style domain separator (chain id / genesis hash), relying only on a nonce that is meaningful within one state instance but not unique across cloned/forked instances of that state.

### Impact Explanation
A successful replay lets an attacker re-execute a user's already-authorized delegated actions (transfers, function calls, etc.) on a second network sharing the signer's account state, without the signer's consent on that second network. This can cause unauthorized double-execution of an action the user only intended once (e.g., minting/transferring an asset, or a paid service action), consistent with the "unauthorized state or balance change" impact class.

### Likelihood Explanation
Exploitation requires a scenario where the same signer account/access-key state (and comparable block height) exists on two live networks — most plausibly forked/cloned test networks, disaster-recovery restarts from a state snapshot, or migration/rehearsal networks that intentionally mirror mainnet state. This is a real and documented operational pattern in blockchain networks (state export/import for testnets), making the precondition realistic rather than purely theoretical, though it does not affect two networks with genuinely independent, non-overlapping account state.

### Recommendation
Add a chain-identifying domain separator to the meta-transaction signing scheme, analogous to EIP-712's `chainId`: include the genesis hash (or a network-specific identifier) as part of the `SignableMessage`/`DelegateAction` payload that is hashed and signed in `get_nep461_hash()` / `SignableMessage::sign()`, so that a signature produced for one network's genesis cannot be verified as valid on a different network even when nonce and block-height happen to coincide.

### Proof of Concept
1. Network A and Network B are both instantiated from the same genesis/state snapshot (e.g., a testnet cloned from mainnet, or a disaster-recovery restart), so account `alice.near` has access key `pk` with nonce `N` on both.
2. Alice signs a `DelegateAction{sender_id: alice.near, ..., nonce: N+1, max_block_height: H}` intending it to be relayed only on Network A, per `SignedDelegateAction::sign` at [6](#0-5) .
3. The relayer submits it on Network A inside `Action::Delegate`; `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` accepts it because nonce `N+1 > N` and current block height `< H`.
4. An observer extracts the identical `SignedDelegateAction` bytes and wraps them in a new outer `Transaction` (with a valid outer nonce/block_hash for Network B) and submits it to Network B, where Alice's access key nonce is still `N` and block height `< H`. `validate_delegate_action_key` on Network B accepts the same signature since nothing in `get_nep461_hash()` differs between the two networks — the delegated action executes a second time without Alice's consent on Network B.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }
