### Title
Missing zero-address check on `pairAddr` in `Router.buy` allows unbacked-token mint / freeze via silent call to a non-existent pair - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router.buy` (called by `Bonding._executeBuy`, itself reachable by any unprivileged trader via `Zap.buy`) fetches `pairAddr = factory.getPair(token, asset)` and immediately proceeds to `_computeBuy(pairAddr, amountIn)`, `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)`, `IPair(pairAddr).transferToken(...)` and `IPair(pairAddr).swap(...)` without validating `pairAddr != address(0)`. Every sibling function in the same file (`getAmountOut`, `previewBuy`, `sell`, `graduate`, `addInitialLiquidity`) performs this exact check via `PairNotFound()` [1](#0-0) [2](#0-1) [3](#0-2) , but `buy` omits it [4](#0-3) .

### Finding Description
This mirrors the CVE-2021-47353 bug class: a value obtained from a lookup (`sb_getblk`/`udf_tgetblk` in the kernel; `factory.getPair` here) that *can* legitimately be zero/failed is dereferenced downstream without a guard. In `udf_symlink` the missing check crashes the kernel; here, the missing check means `IPair(address(0)).getReserves()`, `.k()`, `.tokenBalance()`, `.transferToken()` and `.swap()` are all called on `address(0)`. Under Solidity's low-level-call semantics, a call to an address with no code returns `success = true` with empty return data. Every one of those calls returns `(0, 0)` for the tuple-returning calls, and the state-mutating calls (`transferToken`, `swap`) silently no-op instead of reverting.

Trace through `_computeBuy(address(0), amountIn)`: `reserveToken = 0`, `reserveAsset = 0`, `k = 0`; `newReserveAsset = amountIn`; `tokensOut = 0 - (0 / amountIn) = 0`; `realBalance = 0`; since `tokensOut (0) > realBalance (0)` is false, the cap branch is skipped and the function returns `(amountInUsed = amountIn, tokensOut = 0)` [5](#0-4) . Back in `buy`, `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)` moves the caller's real LT to `address(0)` — a permanent, protocol-level burn of funds with no recovery path — and then `IPair(address(0)).transferToken(to, 0)` / `.swap(...)` are no-ops that don't revert [6](#0-5) . The transaction succeeds end-to-end from `Bonding.buy`'s point of view (no revert bubbles up), and `_executeBuy` proceeds to emit a `Trade` event and check `canGraduate` against unrelated state [7](#0-6) .

The precondition — `token` having no registered LT pair — is reachable because `Bonding.buy`/`Zap.buy` take an arbitrary `tokenAddress` argument supplied by the caller; if that address was never passed through `Bonding.launch`/`Factory.createPair` (e.g. a typo'd address, a token from a different/failed launch, or a race where `buy` is called before `Bonding`'s own launch-completion bookkeeping populates `tokenInfo[token].pair`), `factory.getPair(token, asset)` returns `address(0)` and the trader's LT is destroyed silently instead of the call reverting with `PairNotFound()` as it does in every other entry point.

### Impact Explanation
Concrete permanent freezing/theft of trader funds: real LT pulled via `safeTransferFrom` is sent to `address(0)` and is unrecoverable, while the trader receives zero tokens and no revert signals the failure — matching the "concrete theft or permanent freezing of trader ... funds" acceptance bar. It also produces an inconsistent on-chain event trail (`Trade` emitted with `tokensOut = 0` and non-zero `amountInUsed`), which can mislead off-chain accounting/graduation-triggering logic that treats the buy as legitimate.

### Likelihood Explanation
Requires only that `Router.buy` be invoked (directly or via `Zap.buy`/`Bonding.buy`) for a `token` whose pair is not yet registered in `Factory` — a state a single unprivileged caller can trigger by supplying an unregistered/mistyped token address, or by racing a buy against the window before `Bonding`'s launch flow finishes registering the pair. No privileged role or upgrade is needed; every other function in the same contract treats this exact input as a first-class error case (`PairNotFound`), underscoring that it is an expected, reachable condition that `buy` alone fails to guard.

### Recommendation
Add the same guard used by `previewBuy`/`sell`/`graduate` to `buy`: `if (pairAddr == address(0)) revert PairNotFound();` immediately after `address pairAddr = factory.getPair(token, asset);` and before `_computeBuy` is invoked, in `packages/contracts/src/Router.sol`.

### Proof of Concept
1. Deploy `Factory`, `Router`, grant `BONDING_ROLE` to a test caller (as in `test/Factory.t.sol` setup) but do **not** call `factory.createPair(token, asset)` for a given `token`/`asset` pair.
2. From the `BONDING_ROLE` caller, call `router.buy(amountIn, token, to)` with `to` holding `amountIn` of `asset` (LT) and having approved `Router`.
3. Observe: `factory.getPair(token, asset)` returns `address(0)`; `_computeBuy` returns `(amountIn, 0)`; `IERC20(asset).safeTransferFrom(to, address(0), amountIn)` succeeds, burning `to`'s LT; `IPair(address(0)).transferToken`/`.swap` silently no-op; the call returns `(amountInUsed = amountIn, tokensOut = 0)` with no revert — asserting `asset.balanceOf(address(0)) == amountIn` and `tokensOut == 0` confirms the fund loss.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
