### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers that are never included in the signed bytes. Because the HMAC key (`Context.api_secret_key`) is a single app-level secret shared across every shop that installs the app, anyone who can obtain one valid `(raw_body, hmac)` pair for their own shop can replay it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header. The signature still validates, but the shop identity handed to the app's webhook handler is attacker-controlled.

### Finding Description
`HmacValidator.validate` verifies `VerifiableQuery#to_signable_string` against `VerifiableQuery#hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is only the raw body: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are entirely outside the HMAC-signed data: [3](#0-2) 

`Registry.process` only checks the HMAC over the body, then unconditionally trusts `request.shop`/`request.topic` when constructing the metadata passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`HMAC_valid(secret, raw_body) == true` should imply `shop_header == the shop that actually generated raw_body`.

That equality does not hold, because:
1. `secret` (`Context.api_secret_key`) is one value shared by **all** merchant shops that install the app — it is not per-shop.
2. `shop` (and `topic`) live in headers that are not part of the signed bytes.

So a valid `(raw_body, hmac)` pair generated for shop A (e.g. an attacker's own store, which they can freely install the app on) remains valid when replayed with `shop-domain: victim-shop.myshopify.com` in the header. `Registry.process` will pass `shop: "victim-shop.myshopify.com"` to `handler.handle`, even though the body and signature actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce: the `shop` value delivered to the app's webhook handler — which apps commonly use to look up the tenant record and apply the webhook body to that tenant's data — can be forged by any actor who can trigger one legitimately-signed webhook for a shop they control (trivially done by installing the app on a free/dev store and triggering any registered topic). This enables cross-tenant data confusion/corruption in any host application that trusts `WebhookMetadata#shop` for per-tenant routing, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires no privileged credentials: an attacker only needs the ability to install the app on any shop (including their own) — a completely unprivileged, self-service action — and to be able to POST directly to the app's public webhook endpoint (which by design accepts unauthenticated requests aside from the HMAC check). The header manipulation itself is trivial once one valid signed body is captured.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed payload, or derive the shop strictly from a value that is cryptographically bound to the request (e.g., verify the `shop-domain` header against a value embedded in the signed payload, or bind the HMAC computation to `shop + raw_body` rather than `raw_body` alone). At minimum, document that `request.shop`/`request.topic` are unauthenticated headers and must not be trusted as a tenant boundary without an additional out-of-band check (e.g., confirming the shop has an active, matching installation/session before acting on the payload).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a registered webhook topic (e.g. `orders/create`) to receive a legitimate delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed with the app's single `api_secret_key`).
2. Send a POST directly to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (same secret, same raw body), and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the attacker's forged/own order data to be processed under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
