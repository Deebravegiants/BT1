### Title
Webhook HMAC signature does not bind the `shop` (or `topic`) identity, enabling cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw request body, while the shop identity (`shop-domain` header) and topic used to route/process the webhook are taken from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator` only verifies that HMAC against the body, so the `shop` value trusted by `Registry.process`/handlers is never bound to the signature that proves message authenticity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are not part of the signed content: [2](#0-1) 

`Registry.process` only validates the HMAC (over the body) and then dispatches the handler using `request.topic` and passes `request.shop` straight into the handler as the tenant identity, with no additional binding of `shop`/`topic` to the signature: [3](#0-2) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` purely over `verifiable_query.to_signable_string`, i.e. the body only, and never incorporates the headers: [4](#0-3) 

The equality that should be enforced is: `shop_header == shop_bound_by_hmac`. In this implementation, the HMAC only proves `body == hmac_verify(body, secret)`; `shop_header` (and `topic`/`webhook-id`/`api-version`) are never part of that equality, so any value can be substituted in the header without invalidating the signature.

### Impact Explanation
Because the shop identity is not bound to the signature, an attacker who obtains any single valid `(raw_body, hmac)` pair from a real Shopify webhook delivery (e.g., by triggering an event in their own installed shop, which is not privileged access, or from any test/dev store) can replay that exact body+HMAC to the app's public webhook endpoint while forging the `x-shopify-shop-domain` (and `x-shopify-topic`) headers to any other value. `Registry.process` will accept the HMAC as valid and hand the handler a `WebhookMetadata` claiming to be from an arbitrary victim shop and/or arbitrary topic. This crosses the tenant boundary: the handler's business logic (session/token revocation on `app/uninstalled`, data deletion on `shop/redact`/`customers/redact`, or any app-specific state change keyed by `shop`) executes against a shop identity the attacker fully controls, which is a cross-tenant access/manipulation vector.

### Likelihood Explanation
The webhook endpoint is a normal unauthenticated public HTTP endpoint that must accept any well-formed request bearing a valid Shopify HMAC — no access token, `api_secret_key`, or privileged account is needed by the attacker. Obtaining one legitimate `(body, hmac)` pair only requires triggering an event on a store where the app is installed (including the attacker's own store), which is trivial and something a normal external, unprivileged user of this gem's consuming app can do.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api-version) in the signed content that `HmacValidator` verifies, or independently verify that the `shop-domain` header matches an expected/known value (e.g., by cross-checking against a locally stored session or shop registered for that specific delivery) before trusting `request.shop` in `Registry.process`. At minimum, document/require that consuming apps also validate `shop` against session storage before acting on webhook payloads, since the gem currently exposes no binding between the two.

### Proof of Concept
1. App has topic `app/uninstalled` (or `shop/redact`) registered with a handler that revokes/deletes data for `data.shop`.
2. Attacker installs the app on their own store `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's `api_secret_key`).
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or `x-shopify-topic: app/uninstalled`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) , and `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` [3](#0-2) , causing the app to act against the victim shop's tenant data without any Shopify-issued webhook ever having been sent for that shop.
