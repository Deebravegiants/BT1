## Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then hands the caller-controlled `shop` value straight to the app's webhook handler as the trusted tenant identifier. Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any attacker who can install the app on their own store can obtain a validly-signed webhook body/HMAC pair, then replay that exact body with a different `x-shopify-shop-domain` header claiming to be a victim shop. The signature check still passes because the shop header was never covered by the HMAC, so the handler receives data it believes originates from the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a raw header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates HMAC over the body, then passes the unauthenticated `request.shop` value on to the handler as the tenant identity: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

In reality:
`shop authenticated by HMAC` (nothing — the shop is not part of `to_signable_string`) `≠ shop delivered to the handler` (taken verbatim from the `x-shopify-shop-domain`/`shopify-shop-domain` header).

Because `api_secret_key` is a single per-app secret shared by every installed shop (not a per-shop key), a user who installs the app on their own store legitimately receives HMAC-valid webhook deliveries. They can capture one such `(body, hmac)` pair and re-POST it to the app's webhook endpoint with the `shop-domain` header rewritten to any other shop's domain. `HmacValidator.validate` will still succeed because it only recomputes the HMAC over `raw_body`: [4](#0-3) 

The handler then processes the forged event believing it belongs to the victim shop, since `WebhookMetadata.shop` is populated straight from `request.shop`.

### Impact Explanation
This breaks the tenant boundary that HMAC validation is supposed to guarantee: an unprivileged attacker who merely installs the app on their own shop can impersonate any other shop when delivering webhooks to the app's endpoint. If the host application uses `data.shop` to select which tenant's session/access token/database record to act on (the documented and expected usage pattern shown throughout `docs/usage/*`), this allows cross-tenant data injection/access — reading, writing, or triggering business logic under another merchant's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple, independently-controlled shops (the typical public-app model): any one shop owner (fully unprivileged relative to other tenants) can generate this attack merely by installing the app on their own store, capturing one webhook delivery, and replaying it with a modified header — no access token, `client_secret`, or leaked credential is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the signed material, or independently verify that the `shop-domain` header corresponds to a shop the app has legitimately installed/expects, before trusting it in `WebhookMetadata`. At minimum, document and encourage host apps to cross-validate `data.shop` against their own installed-shop registry rather than trusting it implicitly — but the safer fix is for `HmacValidator`/`Request` in this gem to fold the shop header into the signable string or otherwise assert its authenticity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a legitimate event (e.g., `orders/create`) and captures the resulting webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(api_secret_key, B)`).
3. Attacker resends the exact same request to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping `B` and `H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds.
5. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, achieving cross-tenant impersonation.
