### Title
Unchecked-return-value `IERC20.transfer` calls in `IntentGatewayV2.withdraw()`/`SweepDust` allow silent loss of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` pays out escrowed ERC20/TRC20 tokens using a raw low-level `.call` to `IERC20.transfer` and only checks that the call did not revert, never decoding/validating the returned boolean. A token that follows the "no-revert-on-transfer" pattern (returns `false` on failure instead of reverting, e.g. `ZRX`-style tokens) will make the transfer silently no-op while the contract still marks the order as settled and decrements escrow accounting, permanently losing the beneficiary's funds — the exact bug class from the referenced Cally report, but on the payout path instead of the deposit path.

### Finding Description
`withdraw()` releases escrowed tokens with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

The same unchecked pattern is used for fee payout and for the `SweepDust` handler: [2](#0-1) [3](#0-2) 

`success` only reflects whether the external call reverted; it says nothing about the ABI-encoded `bool` return value of `transfer()`. A token that implements `transfer()` to return `false` on failure (insufficient balance, blacklist, paused state, etc.) rather than reverting will cause `success == true` with zero tokens actually moved. Immediately after, the contract still executes:
```solidity
_orders[body.commitment][token] -= amount;
``` [4](#0-3) 
and unconditionally marks the order filled/refunded via `_filled[body.commitment] = beneficiary;` at the top of `withdraw()`. [5](#0-4) 

Note that the contract's own `placeOrder`/`fillOrder` deposit paths correctly use `SafeERC20.safeTransferFrom` (`using SafeERC20 for IERC20;`), showing the developers were aware of return-value hazards for inbound transfers, but the outbound `withdraw`/`SweepDust` paths bypass `SafeERC20.safeTransfer` and instead reimplement the check incompletely with a bare `.call`. [6](#0-5) 

This is reachable from any relayed message: `withdraw()` is invoked from `onAccept` (cross-chain `RedeemEscrow`/refund settlement delivered by any relayer after Hyperbridge consensus verification) and from `onGetResponse` (cancellation path, also relayer-driven), so the vulnerable payout code executes automatically once escrowed input tokens include a non-reverting ERC20/TRC20.

### Impact Explanation
Once `withdraw()` runs against such a token, the escrow ledger entry is destroyed and the order is marked `filled`, but the intended solver/user beneficiary never receives the tokens. Because `_orders[...]` is decremented and `_filled` is set, no further redemption or refund path can recover the tokens for the beneficiary — the tokens remain stuck in the `IntentGatewayV2` contract balance with no accounting entry pointing to them. This is a permanent freezing/loss of escrowed user or solver funds, directly analogous to the referenced Cally finding where a non-reverting ERC20 transfer let accounting proceed as if the transfer succeeded.

### Likelihood Explanation
Any user or solver can supply an ERC20/TRC20 input token address in `placeOrder`/`fillOrder`; whether a given token reverts or returns `false` on failed transfer is a token-level property outside the protocol's control, and several widely-used tokens on both EVM chains and Tron-style TRC20 tokens follow the no-revert-on-failure convention. A transfer can fail for ordinary reasons (paused token, blacklist, insufficient contract balance due to rounding/dust interactions elsewhere in the contract) making this reachable without any privileged action — a single relayed settlement message is enough to trigger the loss.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both token and fee-token payouts) and in the `SweepDust` handler with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the contract (`using SafeERC20 for IERC20;`). This ensures both call-reversion and false-return-value failures cause the whole settlement to revert, preserving the escrow accounting until a real transfer succeeds.

### Proof of Concept
1. Deploy (or use) an ERC20/TRC20 token whose `transfer()` returns `false` on failure instead of reverting (ZRX-style semantics), and configure it as an input token for an `IntentGatewayV2` order.
2. User calls `placeOrder` escrowing this token via `safeTransferFrom` (succeeds normally).
3. A solver fills the order cross-chain, triggering a `RedeemEscrow` message that arrives via `onAccept` → `withdraw()`.
4. Arrange for the token transfer inside `withdraw()` to fail post-condition (e.g., token temporarily paused, or beneficiary blacklisted) so `transfer()` returns `false` without reverting.
5. `token.call(...)` returns `success == true` (call executed without revert) even though no tokens moved; `_orders[commitment][token] -= amount` still executes and `_filled[commitment]` is set to the beneficiary.
6. The beneficiary's tokens remain in the `IntentGatewayV2` contract with no further path to reclaim them, since the order is now marked as filled/refunded.
