### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing tenant/topic spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`), but `to_signable_string` — the value actually verified by `Utils::HmacValidator` — returns only the raw request body. None of these header-derived fields participate in the HMAC computation, breaking the intended identity binding: `hmac == HMAC(secret, body)` is satisfied while `shop`/`topic` can be set to any value by whoever sends the HTTP request to the app's webhook endpoint.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [5](#0-4) , while `shop`, `topic`, `webhook_id`, and `api_version` are read from headers with no participation in the signature [6](#0-5) . `Registry.process` validates only this body-based HMAC and then trusts `request.topic` to select the handler and `request.shop` to populate `WebhookMetadata.shop`, which is handed directly to the host app's handler as the tenant identifier [7](#0-6) . `HmacValidator.validate`/`validate_signature` compare `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — for webhooks this signable string never includes shop or topic [8](#0-7) . Because a single `api_secret_key` is shared across all shops installed on the app, any body+hmac pair a merchant legitimately receives for their own shop (e.g. captured from their own webhook consumer) remains a valid signature no matter which `shopify-shop-domain`/`shopify-topic` header values are subsequently attached when that request is replayed directly to the app's webhook endpoint. `WebhookMetadata.shop` is a plain `String` field with no further validation before being passed to the handler [4](#0-3) , and the documented handler contract instructs implementers to key work off `data.shop` and `data.topic` directly [9](#0-8) .

### Impact Explanation
This breaks the equality the app relies on: `shop authenticated by HMAC == shop attributed to the processed webhook`. An unprivileged actor who can obtain any valid `(body, hmac)` pair for the shared app secret (trivially available to any merchant with the app installed, since they receive genuinely signed webhooks) can relabel the `shopify-shop-domain` header to name a different merchant, and/or relabel `shopify-topic` to trigger a different registered handler, while the HMAC check still passes. Since apps built with this gem are directed by the docs to trust `data.shop`/`data.topic` as the tenant/action identity, this enables cross-tenant data injection or attribution into another merchant's records/handlers without ever needing that merchant's or the app's actual credentials — matching the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs at least one valid `(raw_body, hmac)` pair for the app's shared secret, which any installed merchant of the app can obtain for their own shop by simply receiving Shopify's genuine webhook traffic and forwarding the same POST directly to the app's webhook endpoint with modified `shop`/`topic` headers. No access to `api_secret_key`, access tokens, or any other privileged credential is required — only network access to a previously observed legitimate webhook payload and the app's public webhook URL.

### Recommendation
Include the anti-tenant/anti-replay fields in the signed material, or otherwise cryptographically bind them: e.g., compute the HMAC over `shop + topic + webhook_id + api_version + raw_body` (or require the host app to independently confirm `shop`/`topic` against out-of-band state, such as the webhook registration performed for a specific session) rather than trusting header values that sit entirely outside the signature. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used for tenant-sensitive decisions without independent verification.

### Proof of Concept
1. App registers `orders/create` and `customers/redact` webhooks via `ShopifyAPI::Webhooks::Registry.add_registration` for both topics [10](#0-9) .
2. Attacker (a merchant with the app installed, shop `attacker.myshopify.com`) receives a real Shopify webhook for `orders/create` with body `B` and valid header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker POSTs the exact same `B` and `H` to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: customers/redact`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `to_signable_string` returns `B` unchanged [5](#0-4) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and finds it equal to `H` — validation passes despite the header substitution [11](#0-10) .
6. The app's `customers/redact` handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", body: JSON.parse(B), ...)` [12](#0-11) , causing the host app to process attacker-controlled data as an authenticated action attributed to `victim.myshopify.com` under a topic the attacker chose, despite the attacker never possessing any credential for that shop.

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
