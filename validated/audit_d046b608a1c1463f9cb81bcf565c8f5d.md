The premise doesn't map to an actual exploitable pattern in this codebase. I searched for capability revocation logic that follows the "check `option::is_some` then call `destroy_none`" pattern on `Option<BurnRef>`/`Option<TransferRef>` and found no such construct in custody-relevant modules (`coin.move`, `fungible_asset.move`, `account.move`, `object.move`, token/collection modules). The only `is_some`/`destroy_none`/`destroy_some` pairings that exist are structural (e.g. `collection::create_collection_internal` handling an optional `Supply` object) [1](#0-0)  or unrelated data-structure code in `big_ordered_map.move` and `optional_aggregator.move` — none of which revoke a burn/transfer/mint capability.

Actual capability-holding refs (`BurnRef`, `TransferRef`, `MintRef`) in `fungible_asset.move` and `coin.move` are extracted via `option::extract`/`option::destroy_some` guarded by a prior `is_some` assertion that aborts on failure [2](#0-1) , and token-level revocation (e.g. `aptos_token::burn`, `freeze_transfer`) is gated by `authorized_borrow`, which checks `token::creator(*token) == signer::address_of(creator)` before touching the ref [3](#0-2) .

More fundamentally, the exploit scenario requires a time-of-check/time-of-use gap between `option::is_some` and `option::destroy_none`/`destroy_some` where an unprivileged party could intervene. Move transactions execute atomically with no reentrancy into untrusted code between such a check and the following destructuring call within the same function, so there is no window for "concurrent unprivileged access" to alter the `Option` state between the check and the destroy — `option::destroy_none` itself re-asserts `is_none` (or aborts on `Some`) at the point of the call [4](#0-3) . No custody-relevant module in this codebase exhibits the described check-then-revoke pattern that an unprivileged caller could race or corrupt.

    inline fun authorized_borrow<T: key>(token: &Object<T>, creator: &signer): &AptosToken {
