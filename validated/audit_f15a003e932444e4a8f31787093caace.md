The `to_signable_string` for `ShopifyAPI::Webhooks::Request` is bound only to `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1)  and passed straight into the handler by `Registry.process` after only the body-HMAC is checked [3](#0-2) .

### Title
Webhook tenant identity (`shop`) not covered by HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that the host application relies on to attribute the webhook to a specific merchant/tenant are taken from HTTP headers that are never included in the signed payload. An attacker who owns any shop that has the app installed can capture one of their own genuinely-signed webhook deliveries (valid body + HMAC for their own store) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header changed to a victim shop. `Utils::HmacValidator.validate` will still succeed because it only checks `OpenSSL::HMAC` over `@raw_body` [4](#0-3) , and `Registry.process` will then invoke the registered handler with `WebhookMetadata` built from the attacker-controlled `shop`/`topic`/`webhook_id` header values [5](#0-4) .

### Finding Description
This breaks the identity binding `hmac_signed_bytes == bytes_the_app_trusts_for_tenant_attribution`. The `VerifiableQuery` interface only requires `hmac` and `to_signable_string` [6](#0-5) , and for webhooks `to_signable_string` returns solely `@raw_body`, deliberately excluding all headers [1](#0-0) . Because Shopify computes the HMAC signature the same way (over body bytes only, using the shared `client_secret`), any request with a previously valid `(raw_body, hmac)` pair remains cryptographically valid to this library regardless of which shop domain or topic header accompanies it. The `Request#shop`, `#topic`, and `#webhook_id` accessors simply read whatever header value is present [2](#0-1) , with no cross-check against the body contents or against a session/shop the app expects. `Registry.process` trusts these unauthenticated header values directly when constructing the `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Impact Explanation
This is a cross-tenant integrity issue: a low-privilege actor (any merchant who has installed the app — no special privilege beyond an ordinary Shopify store) can forge webhook events that the app attributes to a different, victim shop. Depending on how the host app's handlers use `WebhookMetadata#shop` (e.g., to look up and mutate per-tenant records, trigger `customers/redact` / `shop/redact` GDPR flows, or update billing/inventory state), this can result in cross-tenant data corruption or spoofed compliance/administrative actions performed against another merchant's tenant record — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that use `ShopifyAPI::Webhooks::Registry`/`Request` as documented: the attacker only needs to (1) install the app on their own store to legitimately receive one signed webhook, and (2) resend that exact body with a modified shop/topic header to the same public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is required — the HMAC secret is shared across all tenants of the app by design, so a validly-signed payload from tenant A is indistinguishable, at the HMAC-verification layer, from one claiming to be from tenant B.

### Recommendation
Bind the tenant/topic identity into the signed material or otherwise cryptographically tie the header claims to the verified request: e.g., include `shop-domain`, `topic`, and `webhook-id` in `to_signable_string` (mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its signature [7](#0-6) ), or require callers to independently verify `request.shop` against a known/installed shop list before dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC-SHA256(client_secret, B)`).
2. Replay the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally `X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present) [8](#0-7) ; `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H` [9](#0-8) .
4. `Registry.process` finds the handler for the topic and calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...))` [3](#0-2)  — the app processes a forged event as if it originated from the victim's store.
