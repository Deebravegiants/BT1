### Title
Emporium EIP-712 signature omits `feeStructure` (feeToken/variableRate) and `erc20TokenAddresses`, allowing unauthorised token to be debited from the signer's persisted HinkalWallet - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet` recovers the wallet-owner's ECDSA signature over only `emporiumMessage`, the hash of `ops`, `maxFee` and `deadline` [1](#0-0) . Neither `feeStructure.feeToken`, `feeStructure.variableRate`, nor `circomData.erc20TokenAddresses` are part of that signed payload; the only fee-related check is `feeStructure.flatFee <= stack.maxFee` [2](#0-1) . This mirrors the AzukiDAO bug class: a signature that is checked, but does not bind all the data that is later used to move value, so the verified signature does not actually authorise the operation that gets executed.

### Finding Description
When `stack.signerAddress != address(0)` (the "stateful"/persisted HinkalWallet path), `payRelayFees` selects `erc20TokenAddress` from `circomData.erc20TokenAddresses[i]` and, if it matches `feeStructure.feeToken`, pays `flatFee` for that token out of the wallet via `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(...)` [3](#0-2) . `HinkalWallet.doSendToRelay` is gated only by `onlyEmporium`, i.e. it fully trusts whatever token/amount Emporium instructs it to send, with no independent check against the owner's intent [4](#0-3) .

The wallet owner's EIP-712 signature is the only mechanism that is supposed to authorise spending from this persisted wallet, since `stack.v/r/s` were produced off-chain by the owner before the transaction was ever built. But that signature commits only to `EMPORIUM_SIGNATURE_TYPEHASH(message, hash(ops), maxFee, deadline)` [5](#0-4) . It never commits to which ERC20 (`feeStructure.feeToken`) or what rate (`feeStructure.variableRate`) will be debited, nor to the full `erc20TokenAddresses` array that the surrounding `circomData` will operate on. Because `circomData` (including `feeStructure` and `erc20TokenAddresses`) is supplied fresh by whoever calls `Hinkal.transact` and is checked only for internal self-consistency (`calldataHash` binds the caller's own payload to itself, not to the owner's off-chain approval) [6](#0-5) , any unprivileged party who has seen a valid, not-yet-consumed `(v,r,s, emporiumMessage)` — e.g. from a pending/broadcast transaction, a relayed request, or a leaked payload before it lands on-chain — can wrap it in their own `circomData` that sets `feeStructure.feeToken` to any token the wallet holds and `feeStructure.flatFee` up to the signed `maxFee`, then submit it first. `verifyWallet` will still validate the signature (it never checked the token), mark the message used, and `payRelayFees` will drain up to `maxFee` of an arbitrary, unauthorised token from the owner's HinkalWallet to the attacker-chosen `relay`.

### Impact Explanation
This lets an unprivileged actor cause the smart-wallet owner's persisted funds to be moved in a token the owner never approved, up to the `maxFee` limit, satisfying "theft ... of protocol/relay fees" / "executing calls or moving assets a wallet owner ... never authorised" (High impact criterion). If the mismatched token has materially higher value than what the user intended to pay as a fee, the effective loss can substantially exceed the nominal fee.

### Likelihood Explanation
Requires only that the attacker observe a signed-but-unconsumed `EmporiumStack` (from mempool, a relay API, or any off-chain channel) and front-run it with attacker-controlled `circomData.erc20TokenAddresses`/`feeStructure`, both fully caller-controlled and outside signature coverage. No relayer/admin privilege is needed — the caller of `Hinkal.transact` (`runAction` is invoked via `onlyAllowedRecipient`, reachable by ordinary users submitting their own valid ZK proof) fully controls these unsigned fields.

### Recommendation
Include `feeStructure` (feeToken, flatFee, variableRate) and the exact `erc20TokenAddresses`/`deltaAmountChanges` set operated on in the EIP-712 typed struct that `stack.signerAddress` signs, so any deviation invalidates the signature.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` off-chain intending to pay a flat fee in `USDC`, `maxFee = 10 USDC`.
2. Attacker observes `(v, r, s, emporiumMessage, ops, maxFee, deadline)` before it is consumed on-chain.
3. Attacker calls `Hinkal.transact` with their own `circomData` where `erc20TokenAddresses` includes `WETH` and `feeStructure = {feeToken: WETH, flatFee: 10, variableRate: 0}` (still `<= maxFee=10`, just in `WETH` units instead of `USDC`).
4. `verifyWallet` succeeds because the signature never referenced `feeToken`; `payRelayFees` calls `sendToRelayFromWallet` which pulls `10 WETH` from the victim's `HinkalWallet` to `circomData.relay`, worth far more than the intended `10 USDC`.
