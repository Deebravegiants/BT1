### Title
`Webhooks::Request` shop attribution is unauthenticated — HMAC signs only `raw_body`, never `shop-domain` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `hmac` accessor only decodes the `hmac-sha256` header — neither includes `shop-domain`. `Utils::HmacValidator.validate` therefore proves only that some entity holding `Context.api_secret_key` produced the given body, not which shop the request is for. Since `x-shopify-shop-domain` is read straight out of unauthenticated headers by `Request#shop` and handed to the handler via `WebhookMetadata`, an attacker who legitimately receives one validly-signed webhook (e.g., for their own installed dev shop) can replay the identical body+HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim's domain, and `HmacValidator.validate` still returns `true`.

### Finding Description
The binding that should hold is: `shop attributed to a processed webhook == shop cryptographically bound to the signed payload`. In this code that binding does not exist.

- `hmac` (`lib/shopify_api/webhooks/request.rb:11-13`) only depends on the `hmac-sha256` header.
- `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns `@raw_body` — nothing else.
- `shop` (`lib/shopify_api/webhooks/request.rb:20-23`) is read directly from `x-shopify-shop-domain`/`shopify-shop-domain`, with no signature coverage, no `Utils::ShopValidator.sanitize!` call anywhere in this file or in `Registry.process` (confirmed by grepping the webhooks module — `ShopValidator` is only used in the OAuth/token-exchange paths, never in webhooks).
- `Utils::HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes `HMAC(secret, to_signable_string)` i.e. `HMAC(secret, raw_body)` and compares it to the decoded `hmac-sha256` header. `secret` is the single app-wide `Context.api_secret_key` (or `old_api_secret_key`), shared across every shop that installs the app — it is not shop-specific.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) does `raise ... unless Utils::HmacValidator.validate(request)` and then calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, trusting `request.shop` as the tenant identity for whatever the handler does next (e.g. loading that shop's session/access token, writing to that shop's records).

Exploit flow: the attacker creates their own development shop, installs the app, and registers a webhook to a URL they control (or simply captures one delivery). Shopify sends a genuinely signed request — valid `raw_body` and valid `hmac-sha256`, computed with the same app-wide secret used for all shops. The attacker then re-POSTs that exact `raw_body` and `hmac-sha256` value to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with the victim merchant's domain. `HmacValidator.validate` still passes because the signature never covered the shop header. `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content. Any handler logic keyed off `request.shop` (looking up the victim's session/access token to act on the victim's store, writing attacker data into the victim's per-shop records, etc.) is now cross-tenant.

None of the existing guards catch this: `HmacValidator.validate` only checks body integrity, not shop identity; `ShopValidator.sanitize!` is never invoked in the webhook path; there is no JWT/session-token check in this flow at all (that only exists in the OAuth/App-Bridge session-token path, which webhooks don't use).

### Impact Explanation
An attacker who is a legitimate (if unprivileged) installer of the app on their own shop can cause the app to process attacker-controlled webhook payloads under the identity of any victim merchant shop of their choosing, by relabeling one header. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (typical usage: look up the shop's stored `Auth::Session`/access token and act on the victim's store, or persist incoming data keyed by shop), this is cross-tenant data confusion/injection — matching the "Critical - cross-tenant access" category. This is fully repeatable against arbitrary victim shop domains (they are public, e.g. visible via storefront `X-Shopid`/theme metadata or simply guessed `*.myshopify.com` names) since the same captured (body, hmac) pair can be replayed with different `shop-domain` values.

### Likelihood Explanation
Preconditions are low-cost and fully within the unprivileged attacker's control: create a free development store, install the app, trigger or wait for one webhook delivery to capture a valid `(raw_body, hmac-sha256)` pair, then send it to the app's public webhook endpoint with a forged `x-shopify-shop-domain`. No secret, no signature forgery, and no interaction with the victim is required. This is trivially repeatable and scriptable against any number of victim shops.

### Recommendation
Do not treat `x-shopify-shop-domain` as trusted tenant identity from the webhook alone. Options: (1) include the shop domain in the signable string / HMAC computation if Shopify's webhook contract allows shop-specific verification, or (2) require host apps to cross-check `request.shop` against an independently-known set of shop domains that legitimately registered that specific `webhook_id`/topic before trusting it (e.g., look up the webhook registration or an active session for that shop and only proceed if consistent), and/or call `Utils::ShopValidator.sanitize!` plus validate the shop is one your app actually has an active install/session for prior to acting on `request.shop`. At minimum, document loudly in `Webhooks::Request` that `shop` is unauthenticated and must not be used as an authorization boundary by itself.

### Proof of Concept
```ruby
# test/webhooks/request_spoof_test.rb
require_relative "../test_helper"

class WebhookShopSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", api_version: "2024-01",
      host_name: "app.example.com", scope: "read_products", is_private: false,
      is_embedded: true,
    )
  end

  def test_shop_header_not_covered_by_hmac
    raw_body = '{"id":1,"note":"attacker payload"}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
    )

    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    }
    victim_headers = attacker_headers.merge(
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
    )

    req_attacker = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
    req_victim = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: victim_headers)

    # SHOP BINDING check: shop should differ, but signature validity must be identical either way
    assert_equal("attacker-shop.myshopify.com", req_attacker.shop)
    assert_equal("victim-shop.myshopify.com", req_victim.shop)

    assert(ShopifyAPI::Utils::HmacValidator.validate(req_attacker))
    assert(ShopifyAPI::Utils::HmacValidator.validate(req_victim),
      "HMAC validated even though shop-domain header was relabelled to a different tenant")

    # to_signable_string is identical for both -> proves shop header is not covered
    assert_equal(req_attacker.to_signable_string, req_victim.to_signable_string)
  end
end
```
Both requests pass `HmacValidator.validate` despite pointing at different shops, proving `request.shop` is unauthenticated and can be freely relabelled by anyone who possesses one valid `(raw_body, hmac)` pair from any shop. [1](#0-0) [2](#0-1) [3](#0-2)
