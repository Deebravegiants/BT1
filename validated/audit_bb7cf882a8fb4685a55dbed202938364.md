### Title
Stale private keys remain usable in `CachedSodiumEncryptor#cache` after `wallet.removeSeed()`/`keychain.removeAllSeeds()` - ([File: features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts])

### Summary
`CachedSodiumEncryptor` caches derived private keys in a private `#cache` Map keyed by `seedId+keyId` with no TTL, eviction, or subscription to keychain/wallet lock/removal events [3](#0-2) . Because `wallet.removeSeed()`/`removeManySeeds()` only deletes the seed from `keychain.#masters`/`#seedLockStatus` and the wallet's own storage, but never notifies `CachedSodiumEncryptor` [4](#0-3) [5](#0-4) , any previously-derived FUSION/WALLET_INFO key for that seedId remains encryptable/decryptable via `encryptSecretBox`/`decryptSecretBox` after removal.

### Finding Description
`#getPrivateKey` only calls `this.#derivePrivateKey` (which calls `keychain.exportKey`) if the cache Map doesn't already contain the `getCacheKey({seedId, keyId})` entry; if it's already cached, it returns the stale buffer directly without ever touching the keychain again [6](#0-5) . `getCacheKey` derives the cache key purely from `seedId` + `keyId` components with no versioning/generation tag tied to keychain seed lifecycle [7](#0-6) . `wallet.removeManySeeds`/`removeSeed` remove the seed from wallet storage and call `keychain.removeSeeds(...)`, which deletes the corresponding entries from `#masters`/`#seedLockStatus` in `Keychain` [4](#0-3) [8](#0-7) , causing subsequent `keychain.exportKey({seedId, ...})` calls to reject with `seed with id "..." is not initialized`, as asserted in wallet tests [9](#0-8) . However, `CachedSodiumEncryptor` never observes this removal — there is no hook, event listener, or wiring between `wallet`/`keychain` removal APIs and `CachedSodiumEncryptor`'s `#cache`. Once a key for `{seedId, keyId}` has been derived once (e.g., via `encryptSecretBox`), it stays in the Map for the lifetime of the module instance, meaning `encryptSecretBox`/`decryptSecretBox` for that removed seedId will keep succeeding using the stale private key.

### Impact Explanation
This allows continued cryptographic operations (encryption/decryption using the FUSION/WALLET_INFO private key) for a seed the user explicitly removed from the wallet, violating the "removed seed material must become unreachable" invariant. Scoped impact is limited to continued use of already-cached key material for `encryptSecretBox`/`decryptSecretBox`/`encryptBox`/`decryptBox` calls on that removed seedId/keyId pair — it does not expose the raw key bytes to the caller and does not affect other seeds' keys. The `CachedSodiumEncryptor` API is also exposed over RPC with attacker-suppliable `seedId`/`keyId` [2](#0-1) [1](#0-0) , so if an unprivileged dapp/RPC caller had earlier triggered key derivation for a seed (via a legitimate FUSION/storage flow) before the user removed that seed, the caller can keep using that stale key indefinitely for encrypt/decrypt operations, even though the keychain itself now correctly rejects direct `exportKey` calls for that seedId.

### Likelihood Explanation
Preconditions are realistic and fully reachable through ordinary wallet flows: (1) a seed must be added as an extra (non-primary) seed via `wallet.addSeed`, (2) a `cachedSodiumEncryptor.encryptSecretBox`/`decryptSecretBox` call must occur for that seedId+FUSION/WALLET_INFO keyId while it exists (populating the cache), (3) `wallet.removeSeed(seedId)` is called. After that, `encryptSecretBox`/`decryptSecretBox` calls for the same `{seedId, keyId}` still succeed with no error, in contrast to `keychain.exportKey` which correctly throws. This is deterministic and repeatable — no timing races or privileged state needed, matching the exact call sequence described in the question.

### Recommendation
Subscribe `CachedSodiumEncryptor` to seed removal/lock events (e.g., via the `application` `Hook.RemoveSeed`/wallet events or a keychain callback) and purge/evict all `#cache` entries whose `seedId` matches the removed seed(s). Alternatively, have `#getPrivateKey` re-validate against the keychain (e.g., a lightweight `keychain.hasSeed(seedId)` check) before returning a cached value, or invalidate the entire cache on any `removeSeed`/`removeAllSeeds`/`lock` call.

### Proof of Concept
Integration test mirroring `features/wallet/module/__tests__/index.test.js`'s "removes a single seed" test [10](#0-9) , wired with a real `CachedSodiumEncryptor` instance sharing the same `keychain`:
1. `wallet.create()`, `wallet.unlock()`.
2. `const seedId = await wallet.addSeed({ mnemonic: otherMnemonic })`.
3. `await cachedSodiumEncryptor.encryptSecretBox({ seedId, keyId: EXODUS_KEY_IDS.FUSION, data })` — succeeds, populates `#cache`.
4. `await wallet.removeSeed(seedId)`.
5. Assert `keychain.exportKey({ seedId, keyId: FUSION, exportPrivate: true })` rejects with `seed with id "${seedId}" is not initialized"` (per existing test pattern) [9](#0-8) .
6. Assert `cachedSodiumEncryptor.encryptSecretBox({ seedId, keyId: EXODUS_KEY_IDS.FUSION, data: data2 })` **currently resolves** (bug) instead of rejecting like step 5 — expected/fixed behavior should be that it rejects with an equivalent "seed not initialized"/cache-invalidated error.

export class CachedSodiumEncryptor {
  readonly #keychain: Keychain
  readonly #cache = new Map<string, Buffer>()

  constructor({ keychain }: Dependencies) {
    this.#keychain = keychain
  }

  async #derivePrivateKey({ keyId, seedId }: KeySource) {
    const { privateKey } = await this.#keychain.exportKey({ keyId, seedId, exportPrivate: true })
    return privateKey
  }

  #checkIfAllowed = ({ keyId }: KeySource) => {
    return ALLOWED_KEY_IDS.some((allowedKeyId) => KeyIdentifier.compare(allowedKeyId, keyId))
  }

  #getPrivateKey = restrictConcurrency(async (params: KeySource) => {
    assert(this.#checkIfAllowed(params), 'Key source not allowed for caching.')

    const cacheKey = getCacheKey(params)
    if (!this.#cache.has(cacheKey)) {
      this.#cache.set(cacheKey, await this.#derivePrivateKey(params))
    }

    return this.#cache.get(cacheKey)
  }) as (keySource: KeySource) => Promise<Buffer>

      ...Object.keys(this.#seedLockStatus),
    ])
    const seedIdsToRemove = seedIds.filter((seedId) => existingSeedIds.has(seedId))

      delete this.#masters[id]
      delete this.#seedLockStatus[id]

export const getCacheKey = ({ keyId, seedId }: CacheParams) => {
  const components = [
    seedId,
    keyId.keyType,
    keyId.derivationAlgorithm,
    keyId.derivationPath,
    keyId.assetName,
  ]

  return components
    .filter(Boolean)
    .map((component) => encodeURIComponent(component!))
    .join('/')
}
