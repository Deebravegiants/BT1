### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows forced-OAuth redirect to an attacker-controlled domain, bypassing the `ShopValidator` trust binding enforced elsewhere in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` string via `auth_base_uri(shop)`, with no domain validation. Every other code path in this gem that turns a `shop` string into an HTTP destination (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, `Clients::Graphql::Storefront.new`) calls `Utils::ShopValidator.sanitize!(shop)` first to enforce the binding "the host that receives the request must be a trusted `*.myshopify.com`/`*.myshopify.io`/`shopify.com` domain." `begin_auth` is missing this check.

### Finding Description
`Utils::ShopValidator` was introduced (per `CHANGELOG.md`, PR #1443) specifically to stop untrusted `shop` values from being turned into request destinations, and is wired into: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) .

`Oauth.begin_auth`, however, takes the `shop:` argument and feeds it straight into `auth_base_uri`, which only special-cases a local dev-server suffix and otherwise blindly interpolates the string into a URL: [5](#0-4) [6](#0-5) 

The intended identity binding is: `shop domain that receives the OAuth authorize request == a trusted Shopify domain`. `begin_auth` never establishes this equality — no call to `Utils::ShopValidator.sanitize!` exists anywhere in `oauth.rb` (confirmed by `grep_search` for `ShopValidator`, which returns matches only in `refresh_token.rb`, `client_credentials.rb`, `token_exchange.rb`, and `storefront.rb`, not `oauth.rb`).

Note `validate_auth_callback` is a separate, already-safe path: the `shop` field it uses is bound to Shopify's HMAC signature over the callback query string [7](#0-6) , so it cannot be forged by an unprivileged party. `begin_auth` has no equivalent binding: nothing proves the `shop` string originates from Shopify.

### Impact Explanation
This fits the "session fixation or forced OAuth completion" High-impact category. Because `begin_auth` sets an anti-CSRF `state` nonce in a cookie on the app's own origin and then redirects the browser to `https://#{shop}/admin/oauth/authorize?...&state=...` with no validation of `shop`, an attacker who can influence the `shop` value passed to `begin_auth` (a very common pattern: apps derive `shop` from an unauthenticated query parameter on their own install/login route, exactly the kind of value `ShopValidator` was added elsewhere to police) can redirect the flow to an attacker-controlled host. That host receives the app's `client_id`, `redirect_uri`, and the freshly generated `state` value in the query string (visible to the destination server and in the Referer header). The attacker can then use that captured `state` to attempt to complete a forced/fixated OAuth flow back to the app's callback for a shop of the attacker's choosing, since `validate_auth_callback` only checks `state == auth_query.state` against the victim's cookie and does not otherwise bind the flow to the originally-requested `shop`.

This is architecturally the same class of bug as the report: `RefreshToken`, `ClientCredentials`, and `TokenExchange.migrate_to_expiring_token` all enforce the shop-domain trust check before treating a `shop` string as a request destination (the "unbonding period"/guard), while `begin_auth` is a sibling entry point in the same module that skips that guard entirely — bypassing the very protection the library introduced for this exact class of input.

### Likelihood Explanation
Likelihood is moderate: it requires the host application to pass an insufficiently-validated `shop` value into `begin_auth` (a documented, expected calling pattern for the OAuth-initiation step, since `begin_auth`'s whole purpose is to kick off OAuth for a shop identified early in the request, typically before any Shopify-signed proof exists). Given that this gem itself decided such values need `ShopValidator.sanitize!` in three sibling methods, its absence in `begin_auth` is plausibly an oversight rather than an intentional design decision left to the host app.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (mirroring `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`) and use the sanitized value when constructing `auth_base_uri`, raising `Errors::InvalidShopError` for any `shop` that isn't a trusted Shopify domain.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(
  api_key: "app_key",
  api_secret_key: "app_secret",
  api_version: "2024-01",
  is_private: false,
  is_embedded: true,
  host_name: "myapp.example.com",
)

# Host app naively forwards an unauthenticated ?shop= query param
# (exactly the kind of input ShopValidator.sanitize! exists to police
# elsewhere in this same gem).
result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "attacker.example",   # not a *.myshopify.com domain
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://attacker.example/admin/oauth/authorize?client_id=app_key&scope=...&redirect_uri=https://myapp.example.com/auth/callback&state=<nonce>&grant_options%5B%5D=per-user"
```
The victim's browser is redirected to `attacker.example`, handing it `client_id`, `redirect_uri`, and the `state` nonce — none of which is possible for the sibling methods (`RefreshToken`, `ClientCredentials`, `TokenExchange.migrate_to_expiring_token`) because they reject `"attacker.example"` with `ShopifyAPI::Errors::InvalidShopError` via `Utils::ShopValidator.sanitize!` [8](#0-7) .

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
