Webhook shop identity spoofing — HMAC signs only the raw body, not the `shop-domain` header used for tenant identification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, but `Request#to_signable_string` returns only `@raw_body`, excluding the `shop` (from `x-shopify-shop-domain`/`shopify-shop-domain` header). The verified HMAC therefore proves nothing about which shop the payload belongs to; `request.shop` is subsequently trusted as the tenant identifier passed into the handler.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` is defined to be the raw body only: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop`, which is read straight from an attacker-modifiable header rather than anything covered by the signature: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:

`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

This binding does not hold, because the HMAC is computed only over `@raw_body`, while `shop` comes from a header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in `to_signable_string`.

Since `api_secret_key` is a single app-level secret shared across every shop that installs the app (not a per-shop secret), any shop that has installed the app can obtain a batch of legitimately Shopify-signed `(raw_body, hmac)` pairs for its own store. The attacker (as an unprivileged operator of their own installed shop, not the victim's tenant) can:
1. Capture a legitimate webhook delivery to their own endpoint (valid body + valid `x-shopify-hmac-sha256`, both computed by Shopify using the shared `api_secret_key`).
2. Replay the exact same body/HMAC to the app's webhook endpoint, but swap the `x-shopify-shop-domain` header to a victim shop's domain (or any arbitrary value).
3. `HmacValidator.validate` still succeeds because the body/HMAC pair are unchanged and valid.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`, delivering the attacker-chosen shop string to the host application's webhook handler as if it were verified.

Host applications built on this gem's documented API are expected to trust `data.shop` for tenant-scoped actions (per the gem's own webhook docs, e.g. looking up a shop record, associating the body with a tenant, or performing per-shop side effects), since the gem asserts it "will verify the request did indeed come from Shopify." [5](#0-4) 

Because the mismatch is intrinsic to the gem's own `Request`/`Registry` classes (not a host-app misuse), and because it lets one tenant's webhook be relabeled as belonging to another tenant, this is an in-gem cross-tenant identity-binding break, not merely a documented-API-misuse issue.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an app operator who legitimately controls one installed shop can forge webhook deliveries that the gem will accept as authentic and attribute to an arbitrary victim shop domain. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., to look up sessions/access tokens, mark app uninstalled, clear/alter tenant-scoped data, or trigger mandatory-compliance flows like `customers/redact` for a shop the attacker doesn't control), this can lead to cross-tenant data corruption or unauthorized actions being attributed to/affecting another merchant's tenant — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High from an implementation standpoint: no secrets beyond a legitimately obtained webhook delivery (something any installed-app operator naturally receives) are needed, and no cryptographic material needs to be forged — only an HTTP header needs to be changed. The only prerequisite is that the attacker's shop has the target app installed (an ordinary unprivileged action), and that the app exposes an HTTP endpoint calling `Registry.process` (the gem's documented usage pattern).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed payload, or otherwise cryptographically bind `shop` to the verified bytes before trusting it — e.g., verify the HMAC over the combination of headers and body, or require the app to look up an existing, previously-established per-shop mapping/session (keyed by an access token or registration ID) rather than trusting an unauthenticated header value directly. At minimum, document prominently that `request.shop`/`data.shop` is NOT covered by the HMAC and must not be trusted for tenant selection without additional verification (e.g., cross-checking against the app's own DB of shops that have valid installations/webhook subscriptions).

### Proof of Concept
```ruby

# 2. Shopify delivers a legitimate webhook to the attacker's registered endpoint, e.g.:
#    POST /callback/customers/redact
#    Headers:
#      x-shopify-topic: customers/redact
#      x-shopify-hmac-sha256: <valid HMAC of raw body, computed by Shopify with the app's shared api_secret_key>
#      x-shopify-shop-domain: attacker-shop.myshopify.com
#    Body: {"shop_id":123,"shop_domain":"attacker-shop.myshopify.com","customer":{...}}

# 3. Attacker replays the SAME raw body and SAME x-shopify-hmac-sha256 value,
#    but swaps only the shop-domain header:
#      x-shopify-shop-domain: victim-shop.myshopify.com
#    to the app's public webhook endpoint.

# 4. Gem-side verification (lib/shopify_api/webhooks/registry.rb:188-200):
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: forged_raw_body, headers: forged_headers)
)
# HmacValidator.validate succeeds because to_signable_string == @raw_body (unchanged),
# and the HMAC is still valid for that body.
# WebhookMetadata.new(shop: request.shop, ...) delivers shop: "victim-shop.myshopify.com"
# to the host app's handler, which believes this webhook (and its body/action) is
# authentically tied to victim-shop.myshopify.com.

This existing test only shows that an *invalid* HMAC is rejected — it does not, and the codebase provides no mechanism to, verify that the `shop` header actually matches the body/HMAC that was validated, confirming the root cause described above.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
