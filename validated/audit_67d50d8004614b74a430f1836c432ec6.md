## Title
Relayer profitability check treats 1 unit of any configurable `feeToken` as worth $1, decimal-scaled but price-unaware — ([File: tesseract/messaging/messaging/src/events.rs])

### Summary
The tesseract relayer's `return_successful_queries` profitability gate compares a message's attached relayer fee (`fee_metadata`, denominated in the source `EvmHost`'s `feeToken`) against the USD-denominated execution cost (`total_gas_to_be_expended_in_usd`) it obtained from a price-oracle gas conversion. To make the comparison, it only rescales `fee_metadata` by the token's decimal count to 18 decimals — it never converts it by the token's actual USD price. This is exactly the `profitFactor` bug class in the report: decimal-aware, price-unaware.

### Finding Description
In `return_successful_queries`: [1](#0-0) 

`total_gas_to_be_expended_in_usd` (`est.execution_cost`) is a true USD figure — it comes from `get_current_gas_cost_in_usd`, which prices native gas through a Uniswap-derived token price: [2](#0-1) 

But `fee_metadata` — the actual fee amount attached to the request in the source chain's `feeToken` — is only decimal-normalized to 18 decimals, with no price conversion:
```rust
let fee_token_decimal = og_source.fee_token_decimals().await?;
let mut fee_metadata: Cost = (fee_metadata * U256::from(10u128.pow(18u32.saturating_sub(fee_token_decimal.into()) as u32))).into();
```
This silently assumes **1 unit of `feeToken` == $1**. `EvmHost.feeToken()` is a governance-configurable address, not hard-pinned to a stablecoin — the docs explicitly note "DAI is the typical choice... though the host stores a configurable `feeToken` address that governance can update without a redeploy": [3](#0-2) 

The comparison itself then blindly trusts this mis-scaled, un-priced value:
```rust
let fee_with_profit: Cost = total_gas_to_be_expended_in_usd + profit;
if fee_metadata < fee_with_profit {
    // skip as unprofitable
} else {
    // relay
}
```

### Impact Explanation
If a host's `feeToken` is not pegged to $1:
- **Token priced below $1**: legitimate, sufficiently-funded requests are perpetually misclassified as "unprofitable" and skipped by every relayer running this profitability logic (`minimum_profit_percentage > 0`), since the assumed $1/unit value overstates the real USD backing. This can starve a request of any relayer willing to deliver it until it times out — a route that is functionally unable to deliver messages, and eventual refund/timeout handling being the only recourse.
- **Token priced above $1**: the check is bypassed too easily — an attacker can pay a minimal nominal amount of an overpriced `feeToken` and still exceed `fee_with_profit`, getting messages relayed even though their true USD-equivalent payment is far below the real execution cost, undermining the intended keeper/reward economics (and inviting relayers to compete uneconomically since the gate no longer reflects real profitability).

Either direction breaks the invariant the profitability gate is meant to enforce, mirroring the reported `profitFactor` defect (decimal-aware, price-unaware condition), and can result in a permanently stuck/undeliverable route for the underpriced case.

### Likelihood Explanation
This triggers whenever a chain's `IsmpHost` fee token is not a $1-stable asset — which the protocol's own docs describe as a governance choice, not an enforced invariant. Any deployment or governance update that sets `feeToken` to a non-stablecoin (e.g., a wrapped native asset, project token, or any token whose market price departs from $1) reaches this path on every relayed request from that chain, with no privileged action required beyond a normal message dispatch.

### Recommendation
Convert `fee_metadata` to USD using the same price-oracle path used for `execution_cost` (e.g., reusing `get_price_from_uniswap_router`/`get_current_gas_cost_in_usd`'s token-price lookup for the `feeToken`), rather than only rescaling by decimals. Alternatively, explicitly document/enforce that `feeToken` must be a $1-pegged stablecoin at the protocol level, and add a guard in the relayer profitability logic that fails safe (treats the message as unprofitable, not auto-approved) when the fee token's price cannot be verified.

### Proof of Concept
1. Governance (or a new EVM host deployment) sets `feeToken()` to a token that is not $1-pegged, e.g. WETH or a project token trading at $2,000/unit.
2. A user dispatches a `PostRequest` attaching a `fee` far below the real dollar cost of delivery in absolute token units, but because `fee_metadata` is rescaled only by decimals (treated as $1/unit) rather than the true $2,000/unit price, `fee_metadata` computed on-chain is astronomically larger than `fee_with_profit`.
3. `return_successful_queries` at `tesseract/messaging/messaging/src/events.rs:530` treats the message as profitable and queues it for relaying even though the actual dollar value transferred does not cover `total_gas_to_be_expended_in_usd`.
4. Symmetrically, deploy a host with `feeToken()` priced well under $1; well-funded requests are rejected by every relayer running the default `minimum_profit_percentage`, and the request can never be delivered until timeout, demonstrating the "route unable to deliver messages" failure mode.

/// Function gets current gas price (for execution) in wei and return the equivalent in USD,
pub async fn get_current_gas_cost_in_usd(
	chain: StateMachine,
	ismp_host_address: H160,
	client: Arc<AlloyProvider>,
) -> Result<GasBreakdown, Error> {
	let mut gas_price = U256::zero();

	match chain {
		StateMachine::Evm(inner_evm) => {
			match inner_evm {
				chain_id if is_orbit_chain(chain_id) => {
					let node_gas_price = client.get_gas_price().await?;
					let arb_gas_info_contract =
						ArbGasInfoInstance::new(Address::from_slice(&ARB_GAS_INFO), client.clone());
					let prices = arb_gas_info_contract
						.getPricesInWei()
						.block(BlockId::latest())
						.call()
						.await?;
					let oracle_gas_price = prices._5;
					gas_price = alloy_u256_to_primitive(std::cmp::max(
						AlloyU256::from(node_gas_price),
						oracle_gas_price,
					));
				},
				// op stack chains
				chain_id if is_op_stack(chain_id) => {
					let node_gas_price = client.get_gas_price().await?;
					let ovm_gas_price_oracle = OvmGasPriceOracleInstance::new(
						Address::from_slice(&OP_GAS_ORACLE),
						client.clone(),
					);
					let ovm_gas_price =
						ovm_gas_price_oracle.gasPrice().block(BlockId::latest()).call().await?;
					gas_price = alloy_u256_to_primitive(std::cmp::max(
						AlloyU256::from(node_gas_price),
						ovm_gas_price,
					));
				},
				_ => {
					gas_price =
						alloy_u256_to_primitive(AlloyU256::from(client.get_gas_price().await?));
				},
			}
		},
		chain => Err(anyhow!("Unknown chain: {chain:?}"))?,
	}
	// A reverting Uniswap pool (e.g. ds-math-sub-underflow on chains whose
	// wrapper has thin liquidity, or a `WETH()` call that returns no data on
	// chains without a canonical WETH on this router) should not poison gas
	// estimation. Fee profitability calculations downstream see a zero USD
	// price for native gas in that case, which is fine for delivery — the
	// raw `gas_price` we just fetched from the node still flows through to
	// the actual transaction submission.
	let token_usd = get_price_from_uniswap_router(ismp_host_address, client)
		.await
		.unwrap_or_default();

	let unit_wei = get_cost_of_one_wei(token_usd);
	let gas_price_cost = convert_27_decimals_to_18_decimals(unit_wei * gas_price)?;
