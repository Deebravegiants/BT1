### Title
Webhook Shop/Topic Identity Not Bound to HMAC-Verified Bytes, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC-over-body signature and then forwards the unauthenticated `shop`/`topic` values straight to the app's handler [3](#0-2) . This breaks the identity binding: "the tenant/topic whose secret produced this HMAC" ≠ "the tenant/topic string the handler is told to act on."

### Finding Description
`HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` field [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors instead read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) which are never included in the signed bytes [2](#0-1) .

`Registry.process` raises only if the body HMAC fails, then immediately builds `WebhookMetadata` from the unauthenticated `request.topic` and `request.shop` and dispatches it to the registered handler [5](#0-4) . Any holder of one genuine `(raw_body, hmac)` pair for their own shop's webhook — which any merchant legitimately receives once they install the app — can resend that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` and/or `shopify-topic` header. `HmacValidator.validate` still succeeds because it only checks the body bytes, but the handler is told the event came from a different shop/topic than the one that actually produced the signature.

### Impact Explanation
Handlers built on this library key their tenant-specific side effects (session/data lookups, per-shop state updates) off `WebhookMetadata#shop` and `#topic`, values the gem asserts are authenticated because HMAC validation passed. Since those fields are not part of the signed bytes, a merchant who legitimately installed the app (no elevated privilege, no access to `api_secret_key`, no TLS interception) can cause the app to process a validated webhook under a victim shop's identity or under a topic it never actually emitted — a cross-tenant identity confusion at the point the gem hands data to the app.

### Likelihood Explanation
Exploitation requires no secrets or special access: any unprivileged party who installs the app on their own store receives real webhook deliveries with valid HMACs for their own body content, and only needs to replay that body with edited `shop`/`topic` headers to the app's webhook endpoint. The gem performs no cross-check between the header-derived `shop`/`topic` and the HMAC-signed content, so this is reliably reproducible.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the bytes that are HMAC-verified (or otherwise cryptographically bind them to the body before comparison), and have `Registry.process` reject requests where header-derived identity fields are not covered by the verified signature, rather than trusting them unconditionally after only the body is validated.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery: raw body `B` with header `shopify-hmac-sha256: H` (valid HMAC of `B` using the app's real `client_secret`), `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`.
2. Attacker resends the exact same request to the app's webhook endpoint but changes `shopify-shop-domain` to `victim.myshopify.com` (and/or changes `shopify-topic` to a different registered topic), keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)` [8](#0-7)  and performs its normal "validated webhook" logic against `victim.myshopify.com`, even though that shop never sent this event.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
