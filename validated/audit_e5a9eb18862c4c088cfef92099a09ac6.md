Confirmed: `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` in `Registry.process` passes the header-derived `shop` value directly to the handler, while HMAC validation only covers the raw body.### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string using the app's shared `api_secret_key` [2](#0-1) . The `shop` value used as the tenant identity for the webhook (`x-shopify-shop-domain` / `shopify-shop-domain` header) is never included in the signed material [3](#0-2) , yet `Registry.process` passes this unverified `request.shop` straight to the app's handler as the authoritative tenant identifier [4](#0-3) [5](#0-4) .

### Finding Description
The broken equality is: `shop authenticated by HMAC` ≠ `shop passed to the app's tenant-scoped handler`.

`Utils::HmacValidator.validate_signature` recomputes an HMAC-SHA256 of `verifiable_query.to_signable_string` with the app's `api_secret_key` and compares it (via `OpenSSL.secure_compare`) to the value in the `hmac-sha256` header [2](#0-1) . For `Webhooks::Request`, `to_signable_string` is defined as simply the raw request body [1](#0-0) . This means the HMAC only proves "this exact body was signed with our shared secret" — it says nothing about which shop the webhook is "for". The `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated HTTP headers [6](#0-5) .

Because the app's `api_secret_key` is the same for every shop that installs the app, any shop that has installed the app can capture a legitimate webhook delivery (a valid `raw_body` + matching `hmac-sha256`), then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to name a different shop. `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body/secret match) before invoking the handler [4](#0-3)  — it performs no check binding the claimed `shop` header to the HMAC. The forged request will pass validation and the handler receives `WebhookMetadata` with an attacker-chosen `shop` [5](#0-4) .

This is precisely "a field acted on but not covered by the HMAC": the tenant-identifying `shop` field is trusted by downstream handler logic (e.g., to look up per-shop records, update per-shop state, or attribute the payload) but is not part of what the HMAC actually authenticates.

### Impact Explanation
Any app built on this gem that uses `request.shop` (via `WebhookMetadata#shop`) to select which tenant's data to read/write is exposed to cross-tenant data corruption/confusion: an attacker who controls one legitimate installation (trivial — installing a free/dev app is unprivileged) can forge webhook events that appear to originate from a shop they do not control, with body content and topic they choose to be internally consistent (e.g. a `shop/redact`, `customers/data_request`, or business webhook payload) but scoped to a target shop's identity. Depending on the handler's implementation, this enables cross-tenant access or cross-tenant state mutation, matching the "cross-tenant access" High/Critical impact category, without requiring the target shop's access token, `client_secret`, or credentials.

### Likelihood Explanation
High: exploitation requires only (1) being able to install the vulnerable app on some shop (unprivileged), (2) capturing one legitimate webhook delivery for that shop (trivial, as the attacker controls that shop's endpoint), and (3) replaying it with a modified `shop-domain` header, which requires no cryptographic secret. No special network position, TLS interception, or leaked credentials are required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered material — e.g., verify the header-asserted shop against a shop the app has installed and independently trust the shop identity from server-side webhook subscription metadata instead of the raw header, or require the signable string to incorporate the shop/topic headers so that tampering with them invalidates the signature. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted as a tenant identity boundary without additional verification (e.g., cross-checking against the shop associated with the specific `webhook_id`/subscription via a signed Admin API lookup).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (H = HMAC-SHA256(B, api_secret_key)) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same body `B` and same header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `raw_body = B`, `shop = "victim-shop.myshopify.com"` [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [9](#0-8) , causing the app to act on data attributed to `victim-shop` even though no data for that shop was ever validated.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
