### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant the event belongs to. Since the header is never included in the signed content, an attacker who controls a legitimately-signed webhook body/HMAC pair (e.g. from their own free/unprivileged Shopify development store using the same app) can resubmit it with an arbitrary `shop-domain` header and have it accepted as coming from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from unauthenticated HTTP headers: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `to_signable_string` (the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs exactly this check and then immediately forwards the unauthenticated `request.shop` value into the `WebhookMetadata` passed to the host application's handler, with no cross-check that the body content or webhook actually originates from that shop: [4](#0-3) 

`WebhookMetadata.shop` is documented and expected to be the trusted tenant identifier that handler code uses to route/act on data: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header claimed == shop the HMAC-signed content actually originated from`. Because the header is excluded from the signable string, this equality is never enforced by the gem — the HMAC only proves "this body was signed with our app secret", not "this body/shop pairing is authentic". Since a single app's `client_secret` is shared across every merchant that installs it, and anyone can create a free Shopify development/partner store and install the app to receive genuinely-signed webhooks for that store, an attacker can capture a valid `(raw_body, hmac)` pair from their own shop and replay it with the `shopify-shop-domain` header (or `x-shopify-shop-domain`) rewritten to point at an arbitrary victim shop domain. `Registry.process` will still accept it as valid, and the handler will receive `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: a webhook payload can be attributed to any shop domain of the attacker's choosing while still passing this gem's own signature check, since `shop` is a field acted upon (used for tenant routing) but not covered by the HMAC. Host applications that trust `data.shop` from `WebhookMetadata` (as the gem's own documentation instructs them to do) to look up/act on per-tenant records can be made to process events under a false tenant identity — a cross-tenant access primitive. This falls under the Critical severity category ("cross-tenant access").

### Likelihood Explanation
Requires no privileged credentials: any attacker can install the target app on their own free development store, capture the resulting genuine `(body, hmac)` pairs (their own webhook events are byte-for-byte usable), and replay them to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or victim credentials are needed — only network access to the app's webhook receiver, which is by design internet-reachable.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header into the value that is authenticated, or otherwise verify that the claimed `shop-domain` corresponds to a shop actually subscribed to that specific webhook topic/id before dispatching to the handler. At minimum, `to_signable_string` should not be the only authenticated value used to establish shop identity — `Registry.process` should validate `request.shop` against known/expected shops (e.g. shops with a stored session) rather than passing it through unchecked.

### Proof of Concept
1. Attacker creates a free Shopify partner/development store `attacker.myshopify.com` and installs the vulnerable app (same `client_id`/`client_secret` as used for all merchants).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over raw body, computed with app's client_secret>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id": 123, ...}
   ```
3. Attacker captures the raw body and the exact HMAC value from this request (both are visible to them since it's their own store/webhook).
4. Attacker resends this exact `(body, hmac)` pair to the app's webhook endpoint, but changes the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the HMAC over `raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches to the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the event never came from that shop — demonstrating the cross-tenant identity confusion.
