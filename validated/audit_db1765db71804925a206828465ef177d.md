### Title
Omni Bridge withdrawal status is matched by raw array index, not by destination/asset, allowing status/txHash misattribution across withdrawals in the same transaction - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` selects the transfer record to report status for by indexing directly into the array returned by the Omni Bridge indexer (`this.omniBridgeAPI.getTransfer({ transactionHash })[args.index]`), without verifying that the returned record actually corresponds to the withdrawal identified by `args.withdrawalParams` (destination address / asset). No equality check is performed between the untrusted, externally-supplied transfer entry and the withdrawal it is supposed to describe.

### Finding Description
In `describeWithdrawal`: [1](#0-0) 

the code takes the `args.index`-th element of the array returned by the indexer API and, if it has a non-null `recipient`, proceeds to derive `destinationChain` and `txHash` from that record and reports it as the outcome of the withdrawal identified by `args.withdrawalParams` (which carries its own `destinationAddress` and `assetId`): [2](#0-1) 

There is no assertion that `transfer.recipient` matches `args.withdrawalParams.destinationAddress`, nor that the transfer's token/asset matches `args.withdrawalParams.assetId`. The correspondence between the caller's withdrawal identifier and the indexer's array position is assumed rather than verified.

This is the direct analog of the reported bug class: in `LineaProofHelper.verifyAccountProof`, the account proof's key was never checked against the expected target address before the data was trusted and returned to the caller. Here, the transfer record returned by an external indexer is never checked against the expected destination/asset before its `status`/`txHash` is trusted and returned to the SDK caller.

Notably, the sibling `PoaBridge.describeWithdrawal` implementation explicitly documents and fixes this exact class of bug for its own indexer response: [3](#0-2) 
The comment "Response list is unsorted, so we match by assetId instead of index" shows the codebase is aware that indexer-returned arrays for a NEAR transaction are not guaranteed to preserve intent order, and that matching by raw index is unsafe. `OmniBridge.describeWithdrawal` does not apply the same safeguard.

### Impact Explanation
If a single NEAR transaction contains multiple Omni Bridge withdrawal intents (e.g., a batch of withdrawals to different destination addresses/chains, or different assets), and the Omni Bridge indexer returns the `getTransfer` array in an order that does not exactly match `args.index` (execution order vs. indexer storage order), `describeWithdrawal` will report the `status`/`txHash` of a *different* withdrawal as if it belonged to the one being queried. This is a status/hash misreport: an integrator polling `describeWithdrawal`/`watchWithdrawal` for withdrawal A could receive `{status: "completed", txHash: X}` where `X` is actually the completion of withdrawal B (potentially to a different destination and amount). Depending on how an integrator uses this result (e.g., to credit a user, close a support ticket, or release custody), this can lead to double-crediting or wrongly confirming settlement for the wrong withdrawal, while the real withdrawal for the queried identifier remains silently unconfirmed.

### Likelihood Explanation
This does not require a malicious actor - only a mismatch between the order encoded in `withdrawalParams`/`args.index` (assigned client-side) and the order the indexer returns transfers for the same NEAR transaction hash. Since the PoA bridge implementation in the same codebase treats this ordering as untrustworthy ("Response list is unsorted"), it's reasonable to conclude the Omni Bridge indexer response ordering is likewise not contractually guaranteed to match intent execution order for multi-withdrawal transactions. The likelihood of triggering it is proportional to how often callers batch multiple Omni Bridge withdrawals in a single NEAR transaction.

### Recommendation
In `OmniBridge.describeWithdrawal`, do not trust `args.index` alone to select the corresponding transfer record. Match the transfer entry against `args.withdrawalParams` (e.g., destination address/chain and asset/token identifier) similarly to how `PoaBridge.describeWithdrawal` matches by `assetId` rather than by raw index, and only report `completed`/`txHash` when the selected record's recipient/asset provably corresponds to the requested withdrawal.

### Proof of Concept
1. Submit a single NEAR transaction containing two Omni Bridge withdrawal intents in one call: withdrawal A → `destinationAddress: addrA` (assetId `T1`), withdrawal B → `destinationAddress: addrB` (assetId `T2`).
2. The SDK assigns `index: 0` to A and `index: 1` to B via `createWithdrawalIdentifier`.
3. The Omni Bridge indexer's `getTransfer({ transactionHash })` returns the two transfer records in an order that doesn't match creation order (e.g., B first, A second) - plausible since, per the analogous PoA bridge comment, such indexer responses are unsorted.
4. `describeWithdrawal({ index: 0, withdrawalParams: A, ... })` picks `transfers[0]`, which is actually B's transfer record (`recipient = addrB`), and returns `{status: "completed", txHash: <B's tx hash>}` for withdrawal A - without ever checking that `transfer.recipient` equals `addrA`.
5. An integrator relying on this result believes withdrawal A (to `addrA`) completed with `txHash`, while in fact that hash/settlement belongs to withdrawal B.
