### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity field `shop` (and `topic`, `webhook_id`, `api_version`) exclusively from HTTP headers that are **not** included in the bytes signed by the webhook HMAC. `to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies the body's integrity but never binds it to the `shop-domain` header that `Registry.process` later trusts to route/act on behalf of a specific merchant.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Yet `Request#shop` (and `topic`/`webhook_id`/`api_version`) is read straight from headers, which participate in no cryptographic check at all: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately uses the unauthenticated `request.shop` value as the tenant identity passed to the app's handler: [3](#0-2) 

The equality the gem is supposed to guarantee is:
`shop authenticated by HMAC == shop acted upon by the handler`

In reality the gem guarantees only:
`body verified by HMAC != shop header acted upon`

Any bytes that produce a valid HMAC for a given body (which any merchant with the app installed on their own store legitimately possesses, since Shopify signs their own webhook deliveries with the app's shared secret) can be replayed against the shared webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim shop. `Utils::HmacValidator.validate` will still return `true` because it only recomputes the signature over `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: victim-shop.myshopify.com` with attacker-chosen body content.

### Impact Explanation
This breaks the tenant boundary that the HMAC check is meant to enforce for a shared, unauthenticated webhook endpoint. A host application that (as documented) relies on `WebhookMetadata#shop` from a `ShopifyAPI::Webhooks::Registry.process` call to select the merchant record to update/delete will process attacker-controlled data under a victim shop's identity — i.e., cross-tenant access/mutation using data the attacker fully controls, without ever holding the victim's access token or secrets. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant using the same app (so they can obtain a validly-HMAC'd raw body from a real webhook delivery to their own shop) and the ability to POST arbitrary headers to the app's public webhook endpoint — both are available to any unprivileged internet user/app installer, with no access token, secret, or privileged account needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signed material checked against the HMAC, or otherwise cryptographically bind the `shop` value to the payload before it is trusted (e.g., verify it against a value derived from a per-shop secret/session store rather than a raw header) inside `Request#to_signable_string` / `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook event, capturing the genuine `raw_body` and its `x-shopify-hmac-sha256` value sent by Shopify (both computed with the app's real `client_secret`, which the attacker never needs to see).
2. Attacker POSTs to the app's shared webhook endpoint with the exact same `raw_body`/`hmac` but sets `x-shopify-shop-domain: victim.myshopify.com` (and any desired `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC per [1](#0-0)  and [4](#0-3) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker-controlled JSON, ...)` per [3](#0-2)  and performs tenant-scoped work against the victim's account using attacker-supplied content.
