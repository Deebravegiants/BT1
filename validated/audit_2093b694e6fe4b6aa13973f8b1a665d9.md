This confirms the design: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the HMAC computation [2](#0-1) . `Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then dispatches `request.shop` straight to the app's handler [3](#0-2) .

### Title
Webhook shop-domain header is not bound by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` bind the signature to `@raw_body` only [4](#0-3) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read separately and are never part of the signed material [2](#0-1) . `Registry.process` trusts `request.shop` for attributing the webhook to a tenant once `Utils::HmacValidator.validate` passes [3](#0-2) .

### Finding Description
The identity binding an app relies on is: `hmac(secret, raw_body) valid` implies `shop-domain header == the actual originating shop`. That equality does not hold, because `hmac` is computed solely over `raw_body` via `HmacValidator.validate_signature` / `compute_signature`, which hash `verifiable_query.to_signable_string` — for webhooks, just the body bytes [5](#0-4) .

All shops installing the same app share a single `Context.api_secret_key` [6](#0-5) . An unprivileged user who installs the app on their own store (shop A) receives genuine webhooks with a valid HMAC computed over the body they control/observe. Because the `shop-domain` header is outside the signed bytes, that same attacker can replay the identical `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting `shop-domain: victim-shop.myshopify.com`. `Request#hmac` recomputes the signature only from `@raw_body`, so validation still succeeds [7](#0-6) , and `Registry.process` forwards `request.shop` (now the forged victim domain) to the handler untouched [3](#0-2) .

The library's own documentation confirms the handler is expected to trust `data.shop` as "The shop domain of the webhook" to key subsequent work (e.g., `perform_later(shop_domain: data.shop, ...)`), so any host app following the documented pattern will process attacker-chosen data under a victim shop's identity.

### Impact Explanation
This crosses a tenant boundary using bytes the gem itself validates as authentic: `hmac verified == true` while `shop == the actual sender` is false. An app that keys database writes, cache entries, or job dispatch by `data.shop` can have webhook data attributed to a different merchant than the one that actually sent it, which is a cross-tenant integrity/confidentiality issue (Critical: cross-tenant access) as scoped by the rules.

### Likelihood Explanation
Requires only an ordinary merchant account that installs the app (any unprivileged internet user meeting the "unprivileged internet user" bar), a genuine webhook received from Shopify to that shop, and the ability to POST an HTTP request with a modified `shop-domain` header to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged access is needed — the attacker never needs to know the secret because they replay a validly-signed body Shopify already sent them.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC verification, or independently verify the header against the shop associated with the originally-registered webhook subscription/session before dispatching to the handler, so the HMAC binds the tenant identity, not only the payload bytes.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) that they fully control the body content of.
2. Shopify sends the webhook with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and the JSON `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header set; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches, so validation passes [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, processing forged data under the victim's identity [9](#0-8) .
