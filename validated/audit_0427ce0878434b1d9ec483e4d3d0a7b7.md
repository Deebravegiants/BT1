### Title
Webhook shop-domain and topic headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are taken from unauthenticated headers. `Utils::HmacValidator.validate` only checks the body against the app's `client_secret`-derived signature, so the shop/topic headers can be altered without invalidating the HMAC check. `Webhooks::Registry.process` then dispatches to the merchant's handler using the attacker-controlled `shop` and `topic` values, breaking the binding: `shop value used for tenant attribution == shop value covered by the verified HMAC`.

### Finding Description
The `Request` class implements `Utils::VerifiableQuery`, exposing `hmac` (parsed from the `x-shopify-hmac-sha256` header) and `to_signable_string`, which is defined to return only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read from HTTP headers that are never mixed into `to_signable_string`: [4](#0-3) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC, so it verifies only that the *body* bytes were signed by someone holding `client_secret` — it says nothing about which shop or topic that signature was originally issued for: [5](#0-4) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` (both header-derived, unsigned) to route the payload to the registered handler as the identity of the originating store: [6](#0-5) 

Because the same HMAC is valid for the same body regardless of which headers accompany it, any request carrying a body/HMAC pair that was valid once (e.g., a body an app developer can trigger for their own shop, or one captured/replayed from a legitimate delivery) remains HMAC-valid when replayed with a different `shopify-shop-domain` or `shopify-topic` header value. This breaks the intended equality: *the shop the handler believes issued the webhook* must equal *the shop whose secret produced the HMAC over this exact request*, but the gem never enforces that the header-derived `shop`/`topic` are part of what was signed.

### Impact Explanation
An unprivileged internet user who can obtain any one valid `(raw_body, hmac)` pair for the target app (for example by operating their own test/development store connected to the same app, which is a routine, unprivileged action) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will pass `Utils::HmacValidator.validate` and dispatch `WebhookMetadata` tagged with the attacker-chosen shop to the app's handler. Depending on how the host application persists or acts on webhook data (e.g., writing to per-shop records, or triggering shop-scoped side effects keyed off `WebhookMetadata#shop`), this allows a cross-tenant data injection/attribution — the classic case in the bug-class hint of "the risk/identity of a resource being decided by an actor other than the one the boundary was drawn around," here manifesting as one shop's signed payload being attributable to a different shop of the attacker's choosing.

### Likelihood Explanation
Likelihood is high for any app that lets outside parties create their own store/app installs (most public apps do, since installing on your own store and receiving webhooks requires no special privilege). Capturing one's own valid webhook body+HMAC is trivial with normal, unprivileged usage of the app; only the header swap is needed, and the gem performs no additional binding check between the verified body and the shop/topic headers it hands off to the handler.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signable string (or otherwise cryptographically bind them, e.g. by having `to_signable_string` incorporate a canonical representation of body + these header values), or independently verify that `shop` corresponds to a shop actually known/authorized for the app before dispatching. At minimum, document that consumers must not trust `WebhookMetadata#shop`/`#topic` without separately confirming shop provenance (e.g., cross-referencing against a stored session for that shop).

### Proof of Concept
1. Attacker installs the target app on their own (or any accessible) development store and triggers a webhook for topic `orders/create`, capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header value `H` (both are visible to the receiving endpoint, which the attacker controls in a test deployment, or can be sniffed from their own inbox/log).
2. Attacker sends a new HTTP request to the target app's real webhook endpoint with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain` set to `victim-shop.myshopify.com` and/or `x-shopify-topic` changed.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only, which matches `H`, so validation succeeds [1](#0-0) .
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with the attacker-supplied `shop`/`topic`, even though those values were never covered by the HMAC that was just verified [3](#0-2) .
