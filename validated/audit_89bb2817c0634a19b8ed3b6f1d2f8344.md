### Title
Webhook processing trusts an unauthenticated `shop-domain` header while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values used to route and process the webhook are read from unauthenticated headers that are never part of the signed content. This breaks the equality `hmac-verified bytes == bytes acted upon`, exactly analogous to the reported `giveReward()` bug where a value used to distribute rewards was not covered by the same accounting the rest of the system relies on.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body) and then unconditionally trusts `request.shop` to build `WebhookMetadata` that is handed to the app's handler as the tenant identity for the event: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`, so any header value not included in that string (here, all of `shop`, `topic`, `webhook_id`, `api_version`) can be freely changed by whoever controls the HTTP request without invalidating the signature: [4](#0-3) 

Because the app's shared `api_secret_key` (client secret) is identical for every shop that installs the app, any merchant that legitimately installs the app receives real, validly-signed webhook deliveries for their own shop. That merchant can capture one such delivery (raw body + valid `X-Shopify-Hmac-Sha256`) and resubmit it to the app's own webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a *different* shop. `HmacValidator.validate` still succeeds, because it only checks the untouched raw body, and `Registry.process` passes the forged `shop` value straight to the handler as if Shopify itself had asserted it. The identity binding that should hold — "the shop whose credentials signed this webhook" == "the shop the handler is told this data belongs to" — is broken.

### Impact Explanation
This allows a merchant with no special privileges beyond a normal app installation to make the app process/attribute webhook data (orders, customer data, redact requests, etc.) under an arbitrary victim shop's identity, i.e., cross-tenant data injection/corruption in any host application that uses `request.shop` from this gem as the trusted tenant key (which is exactly what the gem's own documentation implies `WebhookMetadata#shop` is for). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium: it requires the attacker to be an app installer (unprivileged from the app's perspective) capable of capturing one legitimate webhook delivery and replaying it with a modified header to their target app's public webhook endpoint — no access to `api_secret_key`, tokens, or TLS interception is needed.

### Recommendation
Bind the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed content checked by `HmacValidator`, or otherwise cryptographically bind `shop` to the verified payload (e.g., include it in `to_signable_string`, or require callers to independently confirm the shop domain against a known, previously-established session/shop record before trusting `WebhookMetadata#shop`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared `client_secret`.
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the HMAC — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and dispatches it to the app's handler, which processes/stores the forged order data as belonging to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
