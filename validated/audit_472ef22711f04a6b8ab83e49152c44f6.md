## Finding: View-role users can read External Initiator `OutgoingToken` secrets via unrestricted `GET /v2/external_initiators`

The reported Mattermost CVE is a class of bug where a state/role restriction (read-only) is enforced for the general action space but a specific sensitive action bypasses it due to a missing check. The closest analog in chainlink is a role-check gap on the External Initiator listing endpoint that leaks an authentication secret to the lowest-privilege ('view') role.

### Finding Description
Chainlink's RBAC model defines four roles — `view`, `run`, `edit`, `admin` — enforced via `auth.RequiresRunRole`, `auth.RequiresEditRole`, and `auth.RequiresAdminRole` middleware [1](#0-0) . For External Initiators, mutating routes (`Create`, `Destroy`) correctly require the `edit` role, but the `Index` (listing) route has no role restriction at all — only base authentication: [2](#0-1) 

This means any authenticated user, including one with the lowest `view` role, can call `GET /v2/external_initiators`. The `Index` handler returns `ExternalInitiatorResource`, which includes the `OutgoingToken` field: [3](#0-2) [4](#0-3) 

`OutgoingToken` is a secret credential the Chainlink node uses to authenticate itself when calling out to the external initiator's webhook (paired with `OutgoingSecret`, stored per-record at creation, per the DB schema/model) [5](#0-4) . This is confirmed by the existing test, which asserts the token is returned in the Index response even for unauthenticated-role-agnostic clients: [6](#0-5) . The RBAC test matrix explicitly documents this route as accessible to `view` role: [7](#0-6) .

By contrast, other public-key-listing endpoints intentionally omitted from role checks (ETH/CSA/VRF/OCR keys) only expose public key material, not secrets — the design intent for un-role-gated GETs is that they return non-sensitive data. `OutgoingToken` breaks that pattern by exposing an outbound-authentication secret to any authenticated viewer.

### Impact Explanation
A user granted only the `view` role — intended for read-only dashboard/monitoring access with no ability to create, edit, or manage node resources — can extract `OutgoingToken` values for every configured External Initiator. With this secret, the low-privilege user (or anyone it's leaked to) could forge/replay authenticated requests toward the external initiator's endpoint, impersonating traffic that is supposed to originate only from the Chainlink node, or use the token in requests toward the initiator's own API if it validates that token as proof of node identity. This is a straightforward secret-disclosure / request-impersonation issue, matching the Validate criteria.

### Likelihood Explanation
High likelihood: the endpoint requires only a valid, low-privilege authenticated session (any role, including `view`) — no additional check, no alternate flag/state gating. Any operator who provisions `view`-role API users for read-only monitoring/dashboards (a common, encouraged pattern per Chainlink's RBAC docs) inadvertently grants secret disclosure.

### Recommendation
Add a role gate to the `Index` route consistent with the mutating routes on the same resource, e.g. `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))`, or strip `OutgoingToken`/`OutgoingSecret` from the `ExternalInitiatorResource` returned to `view`/`run` role users, only exposing it once at creation time (as is done for the incoming `Secret`, which is never returned again in `Index`).

### Proof of Concept
1. As an admin, create an External Initiator: `POST /v2/external_initiators {"name":"foo","url":"http://example.com"}` → note that response contains `outgoingToken` once.
2. Create a low-privilege API user with role `view` (`chainlink admin users create --role=view`).
3. As the `view` user, call `GET /v2/external_initiators`.
4. Observe the response includes `outgoingToken` for `foo` (and all other configured initiators), despite the `view` role being intended for read-only, non-sensitive access.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}

			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

	}

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
