## Finding

### Title
Cross-chain token amount truncates to zero on decimal-mismatched transfers, permanently burning bridged funds - (`modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s ERC20-to-local decimal conversion, `convert_to_balance`, performs an integer division that can round the credited amount down to zero (or truncate significant value) whenever the source ERC20 token's decimals exceed the destination asset's decimals by enough that the transferred amount is smaller than the rounding unit. Because the sending side has already escrowed/burned the tokens before this conversion happens on the receiving side, and `on_accept` never checks the converted amount for zero, the beneficiary can receive nothing (or less than intended) while the sender's original tokens are unrecoverably gone — with no revert to trigger the timeout/refund path.

### Finding Description
`convert_to_balance` computes the local balance from an incoming ERC20 `U256` amount via plain integer division: [1](#0-0) 

`on_accept` in the ISMP module implementation calls this directly on the amount decoded from the incoming message and uses the result to either transfer already-escrowed native tokens or `mint_into` a non-native asset for the beneficiary, with no check that the resulting `amount` is non-zero or that it preserves the value the sender actually bridged: [2](#0-1) 

The same unchecked conversion is used on the `on_timeout` refund path as well: [3](#0-2) 

`erc_decimals` (the token's decimals on the *source* EVM chain) is set per `(AssetId, StateMachine)` via the `Precisions` storage map, while `decimals` is the *local* asset's own decimals (native currency decimals, or `pallet_assets` metadata): [4](#0-3) [5](#0-4) 

These two decimal values are independently configured and can differ arbitrarily (e.g., an 18-decimal ERC20 bridged to a 2- or 6-decimal local asset). When `erc_decimals - local_decimals` is large, any transferred amount smaller than `10^(erc_decimals - local_decimals)` raw ERC20 units truncates to exactly `0` after the division in `convert_to_balance`. `on_accept` then proceeds to call `NativeCurrency::transfer`/`Assets::mint_into`/`Assets::transfer` with `amount = 0`, which succeeds without error (these are legitimate zero-value operations), emits `TokenReceived { amount: 0, .. }`, and returns `Ok(..)` — so the ISMP message is marked successfully handled. There is no revert, so the sender is never refunded via the timeout path.

This directly mirrors the reported bug class: an interest/amount computation performs a floor division against a token's decimal precision without guarding against the result rounding to zero, silently costing the counterparty (here, the token bridger) their expected value.

### Impact Explanation
On the EVM sending side (`HyperFungibleToken.send()` per the pallet's counterpart `send()` extrinsic and its EVM analog), tokens are burned/escrowed *before* the destination-side conversion occurs. If the destination local asset has meaningfully fewer decimals than the source ERC20 token, small (but from the user's point of view, legitimate and intentional) transfer amounts are irrecoverably lost: the source tokens are gone and the beneficiary receives zero, with the request considered successfully delivered. Even when the amount doesn't fully truncate to zero, any remainder below the rounding unit is silently destroyed on every single transfer, which is a systemic value leak for any token pair with a decimal-precision gap. This is a direct, permanent loss of user funds triggered by a single ordinary bridging transaction — no privileged actor is required.

### Likelihood Explanation
Any bridged token pair configured with a wide decimals differential (a very plausible governance/registration choice — e.g., an 18-decimal ERC20 on an EVM chain bridged to a 2- or 6-decimal local asset on the substrate side) makes this reachable by an ordinary user simply calling `send()` with typical amounts. No attacker coordination, governance compromise, or unusual conditions are needed — only decimal configuration that is entirely within the range the pallet is documented to support (`Precisions` and per-asset `decimals()` are both fully general `u8` values).

### Recommendation
- In `convert_to_balance`, detect when the computed local amount is zero (or when the division discards a non-zero remainder) and return an error (e.g., `HftError::InvalidAmountConversion` / a new `AmountTooSmall` variant) instead of silently succeeding with `amount = 0`.
- In `on_accept` and `on_timeout`, explicitly reject (bubble up an error, which per ISMP semantics allows retry/refund) whenever the converted `amount` is zero, rather than proceeding to transfer/mint zero.
- Consider tracking and refunding/crediting the truncated remainder (dust) instead of discarding it, or require `erc_decimals`/local `decimals` configurations to guarantee no precision loss for the pallet's supported amount ranges.

### Proof of Concept
1. Register a local substrate asset with `decimals = 2` and its EVM counterpart configured via `Precisions::<T>::insert(asset_id, evm_state_machine, 18)` (18-decimal ERC20, matching the pallet's documented `TokenDecimalsUpdate`/`Precisions` mechanism: [4](#0-3) ).
2. On the EVM chain, a user calls `send()` on the `HyperFungibleToken` contract with an amount such as `500` raw ERC20 units (i.e., `0.0000000000000005` tokens at 18 decimals) — tokens are burned/locked immediately on that side.
3. The ISMP request is delivered to `pallet-hyper-fungible-token::on_accept` on the destination chain. `erc_decimals = 18`, `decimals = 2`, so `convert_to_balance` computes `value / 10^(18-2) = 500 / 10^16 = 0`.
4. `on_accept` proceeds to `mint_into(local_asset_id, &beneficiary, 0)`, which succeeds, emits `TokenReceived { amount: 0, .. }`, and returns `Ok(weight)` — the message is marked delivered.
5. The beneficiary receives `0` tokens while the sender's original tokens remain burned/escrowed on the EVM chain with no timeout/refund triggered, resulting in a permanent loss of the transferred value.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
