Audit Report

## Title
Response cache key omits WorkflowID, causing cross-workflow HTTP response reuse for HTTP Action capability requests - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's HTTP Action response cache (`responseCache`) keys cached responses using `OutboundHTTPRequest.Hash()`, which excludes `WorkflowID` and `CacheSettings`, keying only on method, URL, headers, body, and `WorkflowOwner`. Two different workflows belonging to the same owner that issue identical HTTP action requests will collide on the same cache key, and one workflow's cached HTTP response will be incorrectly served to the other, contradicting the component's documented "Workflow Isolation" guarantee.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` both use `req.Hash()` as the sole cache-map key [2](#0-1) , and `isExpiredOrNotCached` similarly keys off `req.Hash()` alone [5](#0-4) . The struct comment documents the hash as covering "method, URL, headers, body, workflowOwner" — notably omitting WorkflowID [6](#0-5) . The repository's own test suite confirms this behavior directly: `TestRequestHash` asserts `require.Equal(t, hash1, hash2, "Hash should be the same regardless of WorkflowID")` when only `WorkflowID` differs, and likewise for `CacheSettings` [7](#0-6) . This directly contradicts the README's explicit claim that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [4](#0-3) .

The exploit path is reachable through ordinary node-originated HTTP Action traffic: `gatewayHandler.makeOutgoingRequest` unmarshals `OutboundHTTPRequest` from a node message and calls `h.responseCache.Fetch`/`Set` keyed only by `req.Hash()`, based on `req.CacheSettings.MaxAgeMs`/`Store` [8](#0-7) . No workflow-scoping check exists anywhere else in this flow to compensate for the missing `WorkflowID` in the hash.

## Impact Explanation
Because `WorkflowID` (and `CacheSettings`) are excluded from the hash, any two workflows owned by the same address that issue an HTTP Action with identical method/URL/headers/body share the same cache entry. This causes cross-workflow response confusion: a workflow can receive a cached HTTP response that was fetched (and cached) for a different workflow, potentially leaking data intended for another workflow's execution context or causing incorrect data to be acted upon. This falls under the in-scope "cross-user response corruption" impact category, since state that should be scoped per-workflow is shared across distinct logical owners of that state (workflows), not merely per account.

## Likelihood Explanation
This requires no malicious behavior — only an ordinary owner running two or more workflows that call the same external endpoint with the same parameters (e.g., shared price-feed APIs), a common and realistic pattern. It's triggerable via standard unprivileged workflow/HTTP Action usage already reaching the gateway's node-message handling path, with no operator, admin, or host-level access needed.

## Recommendation
Include `WorkflowID` in the value hashed/used as the cache key (and reconsider whether `CacheSettings` should differentiate cache entries), so that cache entries are strictly scoped per workflow as documented, not merely per workflow owner.

## Proof of Concept
The existing test `TestRequestHash` in `response_cache_test.go` already demonstrates the root cause: [1](#0-0) 
1. Construct `req1` with `WorkflowID = "workflow-123"` and `req2` identical except `WorkflowID = "workflow-456"`.
2. Compute `req1.Hash()` and `req2.Hash()` — they are equal.
3. In an integration test, drive two `OutboundHTTPRequest`s with distinct `WorkflowID` but identical owner/method/URL/headers/body through `gatewayHandler.makeOutgoingRequest`/`responseCache.Fetch` — the second request will receive the first workflow's cached response instead of issuing a fresh request, confirming cross-workflow reuse.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
