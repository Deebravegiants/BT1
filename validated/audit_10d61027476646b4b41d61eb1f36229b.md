### Title
`GnosisUniswapV2Interface::swapETHForExactTokens` ignores `amountOut` and wraps the entire `msg.value`, causing user overpayment to be permanently stuck (unrecovered) in `IntentGatewayV2` on Gnosis - (File: `evm/src/utils/uniswapv2/GnosisUniswapV2Wrapper.sol`)

### Summary
On Gnosis, `IntentGatewayV2::placeOrder` swaps native token for the fee token via the configured `uniswapV2Router()`, which is deployed as `GnosisUniswapV2Interface`. Unlike a real exact-out AMM swap, this wrapper's `swapETHForExactTokens` ignores the requested `amountOut` and instead deposits and forwards the *entire* `msg.value` sent to it. `IntentGatewayV2` then assumes the returned `amounts[0]` (which equals the entire native amount sent, not the actual amount needed for `order.fees`) fully accounts for what was consumed, zeroing out `msgValue` and skipping the "refund unspent native" step. Any native token sent above what `order.fees` requires becomes permanently trapped, uncredited fee-token balance sitting in the gateway contract, exactly analogous to the Notional/TradingUtils bug where exact-out ETH→WETH trades over-deposit and never recover the excess.

### Finding Description
`IntentGatewayV2::placeOrder`'s fee-swap branch performs what it believes is an exact-out swap: [1](#0-0) 

It calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)`, expecting the router to consume only as much native value as needed to produce exactly `order.fees` of `feeToken`, and to refund the rest (as real UniswapV2Router02 does, and as `UniV3UniswapV2Wrapper::swapETHForExactTokens` correctly does via its explicit refund logic): [2](#0-1) 

On Gnosis, however, `uniswapV2Router()` points to `GnosisUniswapV2Interface`, whose `swapETHForExactTokens` does not perform any real exact-out logic — it simply wraps and forwards the *entire* `msg.value`, ignoring `amountOut` beyond a sanity check: [3](#0-2) 

Back in `IntentGatewayV2::placeOrder`, the returned `amounts[0]` equals the full `msgValue` sent in, so `msgValue -= amounts[0]` always results in `msgValue == 0`, regardless of how much `order.fees` actually required: [4](#0-3) 

Because `msgValue` is now zero, the subsequent refund check never fires: [5](#0-4) 

Only `order.fees` worth of the wrapped token is credited to `_orders[commitment][TRANSACTION_FEES]`; any native amount sent beyond that is converted into fee-token balance sitting in the `IntentGatewayV2` contract with no accounting entry (it's neither escrow, nor dust, nor refunded to the sender). This directly mirrors the reported bug class: an exact-out trade against a wrap-style pseudo-router over-deposits native token into the wrapped asset and never recovers/refunds the excess, and the caller's own accounting (`msgValue -= amounts[0]`) is fooled into believing the trade consumed exactly what was needed.

### Impact Explanation
Any unprivileged user (or an SDK caller following the documented pattern of sending slightly more native value than strictly required, e.g. as a buffer) who calls `placeOrder` on Gnosis with `order.fees > 0` and pays via native token loses any amount sent beyond the precise `order.fees` requirement — that value is irrecoverably stuck as unaccounted fee-token balance in `IntentGatewayV2`. This is a direct, permanent loss of user funds triggered by a completely permissionless, single-transaction call path (`placeOrder`), not a governance or admin issue.

### Likelihood Explanation
High likelihood: this triggers on every `placeOrder` call on Gnosis that pays `order.fees` in native token unless the caller sends the *exact* wei-precise amount needed, which is unrealistic for callers estimating gas/fee costs with any buffer (the SDK/docs explicitly describe sending amounts with slippage/buffer margins for solver fee estimation elsewhere in the codebase). No attacker cooperation or special conditions are needed — it's a routine self-inflicted loss for any normal user/integrator on this chain.

### Recommendation
In `GnosisUniswapV2Interface::swapETHForExactTokens`, only wrap and forward exactly `amountOut`, and refund the remainder of `msg.value` to `msg.sender` (mirroring the refund pattern already implemented in `UniV3UniswapV2Wrapper::swapETHForExactTokens`), so that the returned `amounts[0]` truthfully reflects the actual amount consumed and `IntentGatewayV2`'s `msgValue` accounting/refund logic works correctly.

### Proof of Concept
1. Deploy `IntentGatewayV2` on Gnosis with `uniswapV2Router()` pointing to `GnosisUniswapV2Interface`, and `feeToken()` set to WXDAI.
2. User calls `placeOrder{value: 5 ether}(order, graffiti)` where `order.fees = 1 ether` and the order's other inputs are zero/ERC20 (so `msgValue` entering the fee-swap branch is `5 ether`).
3. `IntentGatewayV2` calls `swapETHForExactTokens{value: 5 ether}(1 ether, path, address(this), ...)` on `GnosisUniswapV2Interface`.
4. The wrapper wraps the full `5 ether` to WXDAI and returns `amounts[0] = 5 ether`.
5. `msgValue -= amounts[0]` → `msgValue = 0`; only `1 ether` is credited to `_orders[commitment][TRANSACTION_FEES]`.
6. No refund occurs (`msgValue == 0`), and `4 ether` worth of WXDAI remains stuck in `IntentGatewayV2` with no accounting entry, unrecoverable by the user.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }
