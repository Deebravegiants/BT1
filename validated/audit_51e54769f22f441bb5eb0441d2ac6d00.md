### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers that are never included in the HMAC signature, while `Utils::HmacValidator` only verifies the raw request body. This breaks the intended binding "the `shop`/`topic` the handler acts on == the `shop`/`topic` the HMAC signature authenticates," letting a caller who possesses one valid `(body, hmac)` pair reuse it with a different `shop-domain`/`topic` header to make the app process arbitrary webhook data as if it came from another tenant/topic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it against the `hmac` field: [2](#0-1) . But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [3](#0-2) .

`Registry.process` validates the HMAC and then dispatches the handler using these header-derived, unauthenticated fields — most importantly `shop`, which is the tenant identifier the host application will use to look up sessions/data: [4](#0-3) . The resulting `WebhookMetadata` struct that is handed to the app's `WebhookHandler#handle` carries this unauthenticated `shop`/`topic`: [5](#0-4) .

This is directly analogous to the ChainPort "quorum" bug class: a value that is *acted upon* (the effective quorum / here, the effective `shop` and `topic`) is not the value that was *authenticated* (the HMAC only certifies the JSON body bytes, not the header claiming who it belongs to). The identity equality that should hold — "authenticated payload's issuer == shop dispatched to the handler" — does not, because `shop`/`topic` sit outside the signed envelope.

### Impact Explanation
Because `api_secret_key` is shared across all shops/tenants of the same app, any merchant who installs the app (an ordinary, unprivileged action) can capture a legitimately signed `(raw_body, hmac)` pair from a webhook delivered to their own store. They can then replay that exact byte-identical `raw_body`/`hmac` to the app's webhook endpoint while substituting `x-shopify-shop-domain` and/or `x-shopify-topic` headers for a different target shop or topic. `HmacValidator.validate` still returns `true` (it only checks body bytes), so `Registry.process` will invoke the handler with attacker-chosen `shop`/`topic` values. Depending on how the host application keys data lookups off `WebhookMetadata#shop`/`#topic` (as documented/intended usage of this gem), this enables cross-tenant data confusion or spoofed events attributed to a victim shop — meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Medium-to-High: exploitation requires only an ordinary app install (no leaked secrets, no privileged account, no TLS interception) plus the ability to POST arbitrary HTTP headers to the app's public webhook endpoint — both are within reach of an unprivileged internet user/merchant. The main constraint is that the replayed body must be a byte-identical copy of a body the attacker already legitimately received (they cannot fabricate arbitrary new bodies without the secret), which somewhat limits payload content but not the spoofed `shop`/`topic` identity.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them, e.g., via a canonicalized header+body signing scheme), so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` covers everything the handler will act on, not just the JSON body. Alternatively, document explicitly (and enforce in the gem) that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be independently cross-checked by the host app against out-of-band knowledge of the webhook subscription before use.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com" and
# receives a legitimate webhook, capturing (raw_body, hmac) from Shopify.
raw_body = '{"id":123,"note":"legit"}'
hmac_b64 = "<value taken from x-shopify-hmac-sha256 header of the real request>"

# Attacker replays the exact same body/hmac to the app's endpoint but
# swaps the shop-domain and topic headers:
headers = {
  "x-shopify-topic" => "orders/create",          # can differ from original
  "x-shopify-hmac-sha256" => hmac_b64,            # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged tenant
  "x-shopify-webhook-id" => "attacker-controlled",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only checks raw_body.
# The registered handler for "orders/create" now receives
# WebhookMetadata(shop: "victim.myshopify.com", ...) despite the payload
# never having been authenticated for that shop/topic.
```
