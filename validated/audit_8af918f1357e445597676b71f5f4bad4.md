### Title
Missing shop-domain validation in `Oauth.begin_auth` allows OAuth authorize requests (and redirect_uri/client_id) to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` parameter, with no call to `Utils::ShopValidator.sanitize!`. Every sibling credential-exchange method in the same gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and indirectly `TokenExchange`/`Clients::Graphql::Storefront`) validates `shop` through `ShopValidator.sanitize!` before using it to build a URL, specifically to guarantee the equality "host that receives Shopify OAuth traffic == a trusted `*.myshopify.com`/`myshopify.io`/etc. domain". `begin_auth` breaks that established binding.

### Finding Description
`begin_auth` takes `shop:` and immediately uses it, unvalidated, to compute the destination host for the OAuth authorize redirect: [1](#0-0) 

`auth_base_uri(shop)` returns `"https://#{shop}/admin"` with no domain check: [2](#0-1) 

Compare this to the other OAuth-family entry points, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing a request/session tied to that shop: [3](#0-2) [4](#0-3) 

`ShopValidator.sanitize!` exists specifically to reject non-Shopify domains (`TRUSTED_SHOPIFY_DOMAINS` allow-list): [5](#0-4) [6](#0-5) 

The gem's own documentation shows `shop` being taken directly from an unauthenticated request value and passed straight into `begin_auth`: [7](#0-6) 

Because `begin_auth` skips `ShopValidator`, `auth_route` (and the `redirect_uri`, `client_id`, `state` query parameters embedded in it) can be built against an attacker-chosen host, e.g. `evil.example`, instead of a real `*.myshopify.com` shop. The app then sets this value as the `Location` header and redirects the victim's browser to it, per the documented usage flow.

### Impact Explanation
This breaks the binding "the domain that receives the app's OAuth `client_id`, `redirect_uri`, and `state` == a genuine, trusted Shopify domain," which is otherwise enforced consistently across `ClientCredentials`, `RefreshToken`, and `Storefront` in this same codebase. Sending a legitimate app's `client_id`/`redirect_uri`/nonce `state` to an attacker-controlled host enables forced/attacker-directed OAuth flow initiation and phishing that impersonates the real Shopify authorization screen, which falls under the "session fixation or forced OAuth completion" High-severity bucket. It does not by itself leak `client_secret` (the access-token exchange step, `validate_auth_callback`, uses the HMAC-verified `auth_query.shop`, which is bound by the api_secret_key and thus not attacker-forgeable), so the practical blast radius is limited to the initial redirect leg, not credential exfiltration.

### Likelihood Explanation
Exploitability depends on a host application invoking `begin_auth(shop:)` with a value taken from unauthenticated user input, which is exactly the pattern demonstrated in the gem's own documentation (`shop = request.headers["Shop"]`). Any app following that documented example without adding its own shop-domain check is exposed. Given `ShopValidator` is already used as the enforcement mechanism for this exact purpose elsewhere in the gem, its omission here is a library-level gap rather than a misuse of a documented safeguard.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` (and reuse the sanitized value in `auth_base_uri`), raising `Errors::InvalidShopError` for any `shop` value that isn't a trusted Shopify domain, consistent with `ClientCredentials` and `RefreshToken`.

### Proof of Concept
1. A host app implements the login route exactly as shown in `docs/usage/oauth.md`, taking `shop` from an unauthenticated request parameter/header and calling `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. An unprivileged internet user requests that route with `shop=evil.example` (or any non-Shopify host string accepted by `URI`/string interpolation).
3. `begin_auth` computes `auth_route = "https://evil.example/admin" + "/oauth/authorize?client_id=...&redirect_uri=https://app-host.com/auth/callback&state=...&grant_options[]=..."` with no domain check, per [8](#0-7)  and [9](#0-8) .
4. The victim's browser is redirected (307/Location) to `evil.example`, leaking the app's `client_id`, intended `redirect_uri`, and OAuth `state` nonce to the attacker's server, and allowing the attacker to stage a forced/spoofed OAuth completion against the victim.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

```ruby
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```

```markdown
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
```
