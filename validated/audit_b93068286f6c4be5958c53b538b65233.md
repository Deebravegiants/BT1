This confirms the vulnerability. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and presents `data.shop` from `WebhookMetadata` as a trustworthy field the handler should act on (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) — establishing this gem's documented contract that a passing HMAC check binds `shop` to an authentic Shopify-originated event for that shop.### Title
Webhook tenant identity (`shop-domain`) is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the unauthenticated `shop-domain` header as the tenant identity passed to the app's handler. The `shop` field is acted upon (routed to the handler as the authoritative tenant identifier) but is not covered by the HMAC that the gem uses to assert "this request came from Shopify," breaking the equality: *shop bound by the HMAC == shop delivered to the handler*.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` into `WebhookMetadata`, which is passed to the app's handler as the trusted tenant identity: [4](#0-3) [5](#0-4) 

The gem's own documentation states `Registry.process` "will verify the request did indeed come from Shopify," and instructs handlers to act on `data.shop` (e.g., enqueue background work keyed by `shop_domain: data.shop`) as if that field were verified alongside the payload: [6](#0-5) [7](#0-6) 

Because the HMAC secret (`api_secret_key`) is a single shared secret per app across *all* installed shops, any shop that has installed the app receives genuine Shopify-issued webhooks with a valid HMAC over their own body content. Since the header carrying the tenant identity is outside the signed data, an attacker who controls one installed (unprivileged) shop can replay a legitimate webhook they received — with the same raw body and valid HMAC — but with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce: cross-tenant webhook injection. An app built on this gem's documented contract will process attacker-controlled body content under a victim shop's identity, since the library never checks that the header-derived `shop` correlates with anything cryptographically verified. Depending on how the host app keys work off `data.shop` (queued jobs, per-shop upserts, order/customer state changes), this yields cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — a cross-tenant access class issue rooted entirely in this gem's webhook verification primitive.

### Likelihood Explanation
Any merchant/developer that has legitimately installed the app can capture one of their own valid webhook deliveries (trivial with a proxy) and replay it with a modified `shop-domain` header. No secrets, tokens, or elevated access are required beyond having installed the app as a normal unprivileged user — this is a low-effort, highly likely-to-be-attempted attack path.

### Recommendation
Bind the tenant identity into the authenticated material. Options:
- Have `Request#to_signable_string` incorporate the `shop-domain` (and ideally `topic`, `webhook-id`) header values so `HmacValidator` fails if they are altered post-signing (note: this changes what's technically HMAC'd by Shopify server-side, so this specific approach may not be feasible without protocol support).
- More practically, cross-check `request.shop` against the shop associated with the specific webhook subscription/session the app expects for that route/topic before invoking the handler, rather than trusting the header value implicitly.
- At minimum, update the documentation and `WebhookMetadata` contract to explicitly state that `shop` is **not** authenticated by the HMAC and must be independently verified by the host application against known installed shops before being used as a tenant key.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a real webhook (e.g. `orders/create`) to the app's endpoint with body `B`, and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this request and replays it to the same webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only (`to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38`) and it matches `H`, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the app's handler, which processes attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
