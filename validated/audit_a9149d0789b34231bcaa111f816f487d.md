## Finding

### Title
Webhook `shop` identity is trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC of the raw request body, but hands the tenant identity (`shop`) — taken from an unauthenticated HTTP header — straight to the app's webhook handler as if it had been verified together with the signature. The equality the gem implicitly promises is `hmac_valid(body) == webhook_is_from(shop)`, but the code only proves `hmac_valid(body) == signed_with_shared_client_secret(body)`; the `shop` value is never part of the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` reads the tenant identity from an ordinary header (`shopify-shop-domain` / `x-shopify-shop-domain`), which is not part of `to_signable_string` and therefore never enters the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (i.e., the body) against the app's shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` raises only if that body-only HMAC check fails, then constructs `WebhookMetadata` using `request.shop` — the unauthenticated header — as the authoritative tenant identity passed to the host application's handler: [4](#0-3) 

Because Shopify signs webhooks with the app's `client_secret`, which is identical for every shop that installs the same app, any shop that installs the app receives genuinely valid `(body, hmac)` pairs. An attacker who controls one installation (their own, freely-created shop) can capture a legitimately-signed webhook (especially one with a generic/predictable body, e.g. `app/uninstalled` or any topic with an empty or attacker-influenced body) and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will still pass, because it never checks that the header matches the shop whose secret-derived signature is being validated (there is only one shared secret and shop is never bound to the signed bytes), and `Registry.process` will invoke the handler believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: `request.shop` is treated as an authenticated identity by every consumer of `Registry.process`, but it is fully attacker-controlled once any single valid `(body, hmac)` pair for the shared secret is known. A host application that uses `data.shop` to look up per-shop state, trigger per-shop side effects, or associate incoming data with a tenant record can be made to act on behalf of, or write data attributed to, a shop the attacker does not own — a cross-tenant access condition.

### Likelihood Explanation
Exploitation requires only: (1) installing the target public app on any shop the attacker controls (unprivileged, free action available to any internet user via a Shopify Partner/dev store), (2) triggering one webhook delivery to capture a valid `(raw_body, hmac)` pair, and (3) POSTing that same body/HMAC to the app's public webhook endpoint with a spoofed `shop-domain` header. No access token, `api_secret_key`, or privileged credential is required from the attacker.

### Recommendation
Bind the shop identity into the value that is cryptographically verified, or explicitly document/enforce that `shop` must be independently authenticated by the host application before use. Concretely, `Utils::HmacValidator` / `Webhooks::Request` should either include the shop domain in the signed material it checks, or `Registry.process`/`WebhookMetadata` should require the caller to supply an already-authenticated shop (e.g., matched against a stored session for that shop) rather than surfacing the raw header as if it were verified.

### Proof of Concept
1. Install the target public app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook delivery (e.g., `app/uninstalled`) and capture the raw body `B` and header `X-Shopify-Hmac-SHA256: H` sent to the app's callback URL. `H` is `HMAC-SHA256(client_secret, B)` — valid because `client_secret` is shared across all installs of the app.
3. Send a new POST to the same app webhook endpoint with body `B`, header `X-Shopify-Hmac-SHA256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (called from `Registry.process`, `lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks `B` against `H` using the shared secret.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process the event as if it came from `victim.myshopify.com`.
