Audit Report

## Title
CORS wildcard origin allowlist bypass via improper suffix matching (missing dot-boundary check) - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` validates wildcard CORS entries (`*.example.com`) by stripping the `*.` prefix and calling `strings.HasSuffix(originHost, allowedHost)` with no dot-boundary enforcement. An attacker who registers a domain that merely ends with the same characters as the allowed suffix (e.g., `evil-ethereum.org` for an allowlist entry `*.ethereum.org`) is incorrectly treated as an allowed subdomain, letting their page receive `Access-Control-Allow-Origin` clearance to the gateway's HTTP API.

## Finding Description
`isAllowedOrigin` parses the request's `Origin` header and each configured allowed origin via `splitURL` [1](#0-0) , then for wildcard entries does:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [2](#0-1) 

`strings.HasSuffix` only checks that `originHost` ends with the literal characters of `allowedHost`; it does not verify that the preceding character is a `.` (or that the strings are otherwise equal). A domain like `evil-ethereum.org` or `notethereum.org`, which an attacker can freely register, "ends with" `ethereum.org` and is therefore wrongly classified as a subdomain of an allowlisted `*.ethereum.org` entry, even though it has no actual relationship to that domain. This directly parallels the reported Deno `ends_with`-based hostname matching flaw.

The existing exact-match check at line 181 (`originHost == allowedHost`) does not mitigate this, since the vulnerable path is specifically the wildcard branch that follows it.

## Impact Explanation
Once `isAllowedOrigin` returns true, `handleRequest` reflects the attacker-controlled `Origin` value directly into the `Access-Control-Allow-Origin` response header [3](#0-2) , and the request proceeds to `s.handler.ProcessRequest` [4](#0-3) . This grants an attacker-hosted page — running in a victim's browser — CORS access to the gateway's request-processing endpoint (including JWT-authenticated calls) that operators intended to restrict to genuine subdomains of a trusted domain. This maps to the "gateway request impersonation / allowlist bypass" in-scope impact category.

## Likelihood Explanation
Exploitation requires only that the operator configure a wildcard CORS entry (an intended, documented, supported feature, as shown by the existing test using `https://*.ethereum.org` and similar entries) and that the attacker register and host a page on any domain sharing the same character suffix. No elevated credentials, node access, or victim interaction beyond visiting the attacker's page from a browser are needed, making this a low-effort, fully unprivileged, repeatable bypass.

## Recommendation
Replace the raw suffix check with a boundary-aware comparison: `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`, ensuring the matched string boundary is preceded by a dot separator (proper subdomain relationship) rather than an arbitrary shared character suffix.

## Proof of Concept
1. Configure the gateway with `CORSAllowedOrigins: ["https://*.ethereum.org"]`.
2. Send a request to the gateway HTTP endpoint with header `Origin: https://evil-ethereum.org`.
3. `isAllowedOrigin` computes `allowedHost = "ethereum.org"`, and `strings.HasSuffix("evil-ethereum.org", "ethereum.org")` evaluates `true`, so the function returns `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evil-ethereum.org`, confirming the bypass — this can be codified as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` [5](#0-4)  but asserting that a spoofed origin like `https://evil-ethereum.org` incorrectly passes.
