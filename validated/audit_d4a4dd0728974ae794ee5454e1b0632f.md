### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs, and `HmacValidator` verifies, only the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read straight off the unauthenticated HTTP headers and passed to the app's webhook handler as trusted identifiers, even though none of them are covered by the HMAC. This breaks the intended identity binding: `hmac(body) valid` should imply `(topic, shop, body)` as a whole came from Shopify, but the code only proves `body` came from Shopify — `shop` and `topic` are unauthenticated.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` [1](#0-0) , and for webhooks that signable string is defined as just the raw body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are entirely separate from the signed payload:

```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` validates only the HMAC of the body, and then forwards the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` straight to the app's handler as if they were verified:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity binding this breaks (as an equality): `shop_delivered_to_handler == shop_that_Shopify_actually_signed_for`. Before the request: Shopify signs `HMAC(body, api_secret_key)` for a specific `(shop, topic, body)` tuple and sends it with headers describing that tuple. After an attacker's request: the attacker takes any `(body, hmac)` pair that Shopify genuinely produced for a shop the attacker controls (any merchant who installs the app can trigger arbitrary webhooks for their own store — placing orders, creating customers, etc., is unprivileged from the app's perspective), and resends it to the app's webhook endpoint with the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id` headers rewritten to name a different (victim) shop and/or topic. `HmacValidator.validate` still returns true because it only checks the body byte-for-byte against the secret — it never binds the signature to the headers. The app's handler therefore receives `WebhookMetadata` claiming data from `victim-shop.myshopify.com` while it actually originated (and was signed) for the attacker's own shop.

This is a direct instance of the reported bug class translated into this codebase: a value ("shop"/"topic") is *acted on* (routed into the handler dispatch and delivered as the tenant identity in `WebhookMetadata`) but is *not covered by the HMAC* that is supposed to prove the message's authenticity, exactly the "field acted on but not covered by the HMAC" identity-binding failure named in scope.

### Impact Explanation
Any application built on this gem that uses `data.shop` (or `data.topic`) from `WebhookMetadata` to determine which tenant's records to update, look up, or grant access to (the exact pattern shown in the gem's own documentation: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to process attacker-supplied webhook bodies under a spoofed shop domain and/or topic. An unprivileged actor who can install the app on their own store (trivial, since most Shopify apps are installable by any merchant) can obtain a validly-signed `(body, hmac)` pair for content they fully control, then replay it against the app's public webhook endpoint with the shop/topic headers rewritten to target another merchant. Depending on how the host app consumes `data.shop`/`data.body`, this enables cross-tenant data injection or corruption (e.g., writing attacker-controlled order/customer/product data into another merchant's records, or triggering topic-specific business logic — such as app-uninstall or shop-redact handling — under a spoofed shop identity). This satisfies the in-scope "cross-tenant access" impact category.

### Likelihood Explanation
The attack requires no secret material and no privileged account beyond the ability to install the app on one's own (attacker-controlled) Shopify store — a capability any internet user has for most publicly-listed or dev-store-installable apps. It requires only observing/capturing one legitimately delivered webhook (trivial via a logging proxy in front of the attacker's own endpoint) and replaying it with modified, unauthenticated headers to the target app's public webhook route. The gem provides no mitigation (no binding of headers into the signature, no shop allow-list check against the active session/shop registered for the app) at the library layer, so exploitability depends entirely on whether the host application trusts `data.shop`/`data.topic` for tenant routing — which the gem's own documentation explicitly recommends doing.

### Recommendation
Bind the identity fields into the authenticated payload before trusting them:
- Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop` and `topic`) in the value that is HMAC-verified, or
- After HMAC validation of the body, independently confirm that the `shop-domain` header corresponds to a shop for which this specific webhook subscription was registered (e.g., cross-check against a webhook_id ↔ shop record maintained by the app), rather than trusting the header verbatim.
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are NOT covered by the HMAC and must not be used for tenant-authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/receives a legitimate webhook (e.g. `orders/create`) with an attacker-crafted order body.
2. Shopify delivers the webhook with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's real `api_secret_key`.
3. Attacker captures this request and resends it to the same app's webhook endpoint, keeping `raw_body` and the `hmac-sha256` header unchanged, but rewriting `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes/compares the HMAC of `raw_body` [2](#0-1)  — validation succeeds because the body/HMAC pair is unmodified.
5. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_body, ...)` [5](#0-4) , causing the host application to process attacker-controlled data as if it belonged to the victim shop.
