### Title
Webhook `shop` Domain Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor derived from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates is computed only over the raw request body. The tenant-identifying `shop` value is never bound into the signed payload, so it can be forged independently of a valid signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from a header that is not part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. the body only), and then passes `request.shop` — the unverified header — directly to the webhook handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the signature check is against `verifiable_query.to_signable_string`, not the shop header: [4](#0-3) 

This is the exact identity-binding break described by the analog rule: a field (`shop`) is acted upon (used as the tenant key passed to `handler.handle`) but is not covered by the HMAC that authenticates the request. The equality that should hold — `shop authenticated == shop acted upon` — is broken: the gem authenticates only the body bytes, while the host application (via `WebhookMetadata#shop`) is expected to trust `request.shop` as the tenant/session key for storing or processing webhook data.

### Impact Explanation
An attacker who legitimately installs the app on their own store (an unprivileged action available to any internet user who can create a Shopify shop) will receive real webhook deliveries for their own shop, complete with a valid HMAC signature computed by Shopify over the body. Because the header carrying the shop domain is excluded from the signed material, the attacker can replay the exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will accept the HMAC as valid (it only checks the body) and dispatch to the app's handler with `shop` set to the victim's domain, causing the host application to attribute/store the attacker-controlled webhook payload under another merchant's tenant identity — a cross-tenant data confusion/injection primitive.

### Likelihood Explanation
Exploitation only requires the ability to install the app on an attacker-controlled shop (no special privilege, no leaked credentials, no access to `api_secret_key`) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with the reused body/HMAC pair and a modified shop header. No secret material needs to be recovered because the attacker acquires a genuinely-signed body from their own webhook delivery.

### Recommendation
Bind the shop identity into the signed payload before trusting it, e.g. incorporate the `shop-domain` header (or a value independently retrieved from Shopify, such as resolving the shop from a stored, previously-authenticated session/access token tied to the delivery) into `to_signable_string`, or otherwise cross-check `request.shop` against an independently verified source before it is handed to `WebhookHandler#handle`. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid signature over `B`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and re-sends the same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (`H` is valid for `B`) — see: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes `B` as though it originated from the victim shop, despite the victim never having sent this webhook.
