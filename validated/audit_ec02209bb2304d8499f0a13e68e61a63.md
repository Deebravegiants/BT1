Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only this body-only HMAC and then forwards the header-derived `shop` value straight to the app's handler as trusted tenant identity [3](#0-2) , and the gem's own documentation instructs apps to key their business logic off `data.shop` [4](#0-3) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from `@raw_body` only [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body* bytes match a valid HMAC for the app's `client_secret`; it proves nothing about which shop, topic, or webhook id the request is "for." Those identity fields are pulled unauthenticated straight from HTTP headers [5](#0-4) . This is structurally the same class of bug as the reported multisig issue: a value that is *acted upon* (the shop that a webhook is attributed to) is not the same value that is *cryptographically bound* by the verification step (the raw body).

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

`request.shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the HMAC digest [6](#0-5) . The equality that should hold is: `hmac_verified(body) == true` **implies** `shop header == shop that Shopify actually generated this body for`. In this implementation that implication does not hold, because the signed bytes (`@raw_body`) and the trusted identity field (`shop` header) are disjoint.

Because Shopify signs webhooks with the app-level `client_secret` (shared across every shop that installs the app), any unprivileged merchant who installs the app on their own store legitimately receives real webhooks with a valid HMAC over a given body. That merchant can capture such a request and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The HMAC still validates (it never covered the header), so `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled `body`. Since the gem's own documentation tells integrators to key business logic (queueing jobs, updating per-shop state, `shop/redact`-style handling, etc.) off `data.shop` [4](#0-3) , this is a direct tenant-identity break delivered by the gem's verification API itself, not merely an app oversight.

### Impact Explanation
This crosses a tenant boundary (Critical - cross-tenant access): an attacker who is a legitimate but unprivileged app installer on their own shop can make the app believe attacker-controlled webhook data originated from a different, victim shop, with a "verified" HMAC. Depending on handler logic this can lead to cross-tenant data corruption, spoofed mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), or triggering shop-scoped side effects (e.g. app state resets, uninstall handling) against a shop the attacker does not control.

### Likelihood Explanation
Requires only: (1) installing the target app on any shop the attacker controls (a normal, unprivileged flow), (2) capturing one real webhook request/HMAC pair from that install, and (3) replaying it with a modified `shop-domain` header to the app's public webhook endpoint. No secrets, tokens, or elevated access are needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or independently authenticate the header value — e.g. verify the HMAC using `shop`+`raw_body` concatenation if Shopify's delivery format supports it, or require the app to fetch/verify the `shop` against the registered webhook subscription id / an authenticated API instead of trusting the header directly. At minimum, document prominently that `data.shop` in `WebhookMetadata` is NOT authenticated by the HMAC and must not be trusted for tenant-sensitive decisions without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app.
# Shopify sends a real webhook for that shop with a valid HMAC over the body:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_from_shopify, # valid for @raw_body, computed with app client_secret
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
raw_body = captured_real_body

# Attacker replays it, swapping only the shop header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) still returns true,
#    because to_signable_string only ever returns raw_body (request.rb:35-38).
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
