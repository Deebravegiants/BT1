### Title
Coprocessor `update_params`/`sweep_dust`/`update_token_decimals` extrinsics update local shadow state before cross-chain delivery confirmation, permanently desyncing IntentGatewayV2 params on validation failure - (File: modules/pallets/intents-coprocessor/src/lib.rs)

### Summary
The intents-coprocessor pallet's `update_params` call mirrors the L1ECOBridge/L2ECOBridge rebase-desync pattern: it dispatches a cross-chain `UpdateParams` ISMP request to the remote `IntentGatewayV2` gateway and then *unconditionally* commits the same new params into its own local `Gateways` storage, without waiting for (or being able to observe) whether the destination's `onAccept` → `_updateParams` → `_validateParams` actually succeeds.

### Finding Description
`update_params` in `modules/pallets/intents-coprocessor/src/lib.rs` (lines 464-517) merges the governance-supplied `ParamsUpdate` with the currently tracked `gateway_info.params`, dispatches the merged `CompleteParamsUpdate` as an ISMP POST request to the remote gateway contract, and — regardless of dispatch outcome beyond the immediate `Self::dispatch(...)?` call succeeding (i.e., regardless of whether the *message is ever delivered and accepted on the destination*) — immediately overwrites `gateway_info.params` in local storage and emits `GatewayParamsUpdated`: [1](#0-0) 

On the EVM side, `IntentGatewayV2.onAccept` decodes the `UpdateParams` request kind and calls `_updateParams`, which runs `_validateParams(update.params)` before committing: [2](#0-1) 

If `_validateParams` reverts (e.g., invalid `host`/`dispatcher` addresses, `destinationFeeBps >= 10_000`, or any other check baked into `_validateParams`, as exercised in `testRevert_UpdateParams_DestinationFeeBpsTooHigh`), the entire `onAccept` call reverts and the request is never durably applied — the destination gateway's `Params` remain unchanged. Meanwhile, the coprocessor pallet's `Gateways` storage on the Hyperbridge relay chain has already recorded the *new* params as if they took effect, because that write happens unconditionally after `Self::dispatch(...)` merely enqueues the message — `dispatch` returning `Ok` only means the message was successfully queued/committed for relaying, not that it was delivered and accepted on the destination chain.

This is the exact bug class from the referenced report: a governance/parameter-sync action is optimistically mirrored into local state on one side of a cross-chain bridge, while the other side performs additional validation (`validRebaseMultiplier` in the original / `_validateParams` here) that can independently reject the same update, producing a permanent desync between the two representations of "current gateway params."

Because `update_params` merges against the pallet's own (now-stale) `gateway_info.params` on every subsequent call (`gateway_info.params.update(params_update.clone())`, line 491), once the coprocessor's view diverges from the real on-chain `Params`, every future incremental update computed by the pallet is derived from the wrong base state, compounding the divergence (e.g., a `protocol_fee_bps`-only update on the next call will silently re-propose whatever stale `host`/`dispatcher`/`surplus_share_bps` values the pallet still believes are current, potentially reverting or silently changing fields the operator did not intend to touch).

The same unconditional pattern also exists in `sweep_dust` (dispatches then immediately emits `DustSweepInitiated` without any confirmation) and in the paymaster-analog calls, but `update_params` is the most damaging instance because it corrupts the *base state* used for all future merges, not just a one-shot action.

### Impact Explanation
This is a Medium-severity finding, matching the class of the referenced report:
- The coprocessor's tracked `IntentGatewayParams` (host, dispatcher, `surplus_share_bps`, `protocol_fee_bps`, `price_oracle`) can silently diverge from the actual on-chain `Params` in `IntentGatewayV2` if the destination-side `_validateParams` rejects an update that the source-side pallet does not itself validate before committing to local storage.
- Any subsequent `update_params` call from governance is computed against this now-wrong baseline, meaning legitimate follow-up parameter changes can be dispatched with unintended stale fields (e.g. an old `dispatcher` or `host` address), risking misconfiguration of a live, funds-handling contract (`IntentGatewayV2` custodies escrowed order inputs and protocol fee surplus).
- Governance/operators relying on the pallet's on-chain `GatewayInfo::params` to reason about the live protocol/destination fee configuration will be silently working from incorrect data, which can misprice or misroute solver fee/surplus splits (`protocol_fee_bps`, `surplus_share_bps`, `DestinationFee` entries) — a direct path to fee-accounting inconsistency and potential value leakage/arbitrage for solvers who know the destination's real, unchanged params while governance believes something else is in effect.
- No permanent freezing of user escrowed funds occurs directly, but this produces genuine unsound state commitment between the governance control-plane and the deployed contract it is meant to be steering — the core issue category called out as valid ("unauthorized app action" / desync-driven mispricing) in the prompt's rules.

### Likelihood Explanation
Likelihood is moderate: `_validateParams` reverting is not a rare or adversarial-admin scenario — it happens whenever governance submits a well-intentioned but malformed update (e.g. sets `destinationFeeBps >= 10_000`, or any other constraint enforced in `_validateParams`), which the coprocessor pallet does not itself re-validate before mutating `Gateways` storage. Given `update_params` is a routine governance operation expected to be used repeatedly over the gateway's lifetime (as demonstrated by the dedicated `IntentGatewayV2Test.sol` coverage for `UpdateParams` rejections), an eventual mismatch between what the merge-and-validate logic on Substrate assumes is valid and what `_validateParams` on the EVM side actually enforces is a realistic, recurring operational risk — not merely a theoretical one-off.

### Recommendation
- Do not commit the new params into `Gateways::<T>` storage optimistically at dispatch time. Instead, either (a) run the same validation logic that `_validateParams` enforces (destination fee bounds, non-zero addresses, etc.) locally in the pallet *before* dispatch and before mutating storage, mirroring it exactly, or (b) only update local storage upon confirmed delivery/acceptance of the cross-chain message (e.g., via an ISMP response/callback acknowledging successful `onAccept` execution), rather than immediately after `Self::dispatch` returns `Ok`.
- At minimum, keep the pallet's locally-mirrored `params` as a "pending"/"last dispatched" value distinct from a "confirmed" value, and reconcile only once delivery is confirmed, so that a destination-side revert cannot poison the base state used for subsequent merges.
- Apply the same fix to `sweep_dust` and other `dispatch`-then-emit call paths in this pallet that assume successful dispatch implies successful destination-side execution.

### Proof of Concept
1. Governance calls `intents_coprocessor::update_params(state_machine, params_update)` where the merged params (or `params_update.destination_fees`) contain a `DestinationFee { destination_fee_bps: 10_000, .. }` (`>= 10_000`, i.e. 100%+).
2. The pallet merges this into `updated_params`, dispatches the `UpdateParams` ISMP request to the remote `IntentGatewayV2` gateway (`modules/pallets/intents-coprocessor/src/lib.rs:499-504`), and — before the message is even relayed — immediately writes `gateway_info.params = updated_params` into `Gateways::<T>` and emits `GatewayParamsUpdated` (`modules/pallets/intents-coprocessor/src/lib.rs:507-514`).
3. Once relayed, `IntentGatewayV2.onAccept` decodes the request as `RequestKind.UpdateParams` and calls `_updateParams(update)` → `_validateParams(update.params)`, which reverts with `InvalidInput` because `feeBps >= 10_000` (mirrors `IntentGatewayV2Test.testRevert_UpdateParams_DestinationFeeBpsTooHigh`, `evm/tests/foundry/IntentGatewayV2Test.sol:3879-3910`).
4. The `PostRequest` delivery on the destination chain fails/reverts, so `IntentGatewayV2._params` and `_destinationProtocolFees` remain unchanged on-chain.
5. However, `Gateways::<T>::get(state_machine).params` on the Hyperbridge relay chain now reflects the *new, never-applied* params. Any future `update_params` call merges against this incorrect baseline (`gateway_info.params.update(params_update)`, line 491), propagating the stale/incorrect state indefinitely and misleading governance and any off-chain tooling that reads `Gateways` storage as the source of truth for the live gateway configuration. 		/// Update Intent Gateway parameters via cross-chain governance
		///
		/// # Parameters
		/// - `state_machine`: The state machine where the gateway is deployed
		/// - `params_update`: The new parameters to apply
		/// - `fee`: Metadata for paying dispatch fees
		///
		/// # Errors
		/// - `GatewayNotFound`: If no gateway exists for the state machine
		/// - `DispatchFailed`: If cross-chain dispatch fails
		#[pallet::call_index(3)]
		#[pallet::weight(T::WeightInfo::update_params())]
		pub fn update_params(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			params_update: types::ParamsUpdate,
		) -> DispatchResult {
			T::GovernanceOrigin::ensure_origin(origin)?;

			// Get gateway info
			let mut gateway_info =
				Gateways::<T>::get(state_machine).ok_or(Error::<T>::GatewayNotFound)?;

			// Store old params for event
			let old_params = gateway_info.params.clone();

			// Merge update with current params
			let updated_params = gateway_info.params.update(params_update.clone());

			// Create complete params update for cross-chain dispatch
			let complete_update = types::CompleteParamsUpdate {
				params: updated_params.clone(),
				destination_fees: params_update.destination_fees.unwrap_or_default(),
			};

			// Prepare cross-chain request
			let request = RequestKind::UpdateParams(complete_update);
			let body = request.encode_body();

			// Dispatch cross-chain message
			Self::dispatch(state_machine, gateway_info.gateway, body)?;

			// Update local storage
			gateway_info.params = updated_params.clone();
			Gateways::<T>::insert(state_machine, gateway_info);

			Self::deposit_event(Event::GatewayParamsUpdated {
				state_machine,
				old_params,
				new_params: updated_params,
			});

			Ok(())
		}

     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
