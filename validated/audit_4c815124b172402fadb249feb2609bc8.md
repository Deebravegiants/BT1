### Title
Nested `EmporiumUpgradeable.runAction` calls forge unbacked `deltaAmounts=[0]` into `DepositOnChainUtxosExternalAction`, breaking value conservation and minting attacker-controlled shielded UTXOs from victim funds - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` trusts its caller (`onlyAllowedRecipient`) to have derived `deltaAmounts` from a real, proof-verified `CircomData`. When `EmporiumUpgradeable.runAction` is the caller, however, `deltaAmounts` for a nested `op.endpoint.call(op.callData)` is whatever literal the attacker baked into `EmporiumStack.ops[i].callData`, completely decoupled from the `deltaAmountChanges` Hinkal actually computed via `_calculateDeltaAmount` for the outer, proof-verified `circomData`. This lets an attacker pull an arbitrary victim's ERC20 allowance into Emporium and have Emporium's own balance-diff accounting mint it as a legitimate attacker-owned shielded UTXO.

### Finding Description
The broken equality: tokens actually leaving via `transferERC20TokenFrom` (`tokenTotal`, sourced from `userAddress = circomData.originalSender`, an attacker-chosen field in a forged inner `CircomData`) must equal `-deltaAmounts[i]` that Hinkal computed for that token. Instead `deltaAmounts[i]` is hardcoded to `0` in the attacker's `op.callData`, so:
```
tokenTotal (moved) != 0 (declared delta)
``` [1](#0-0) [1](#0-0) 

Path:
1. `Hinkal.transact` verifies the proof for the attacker's own outer `circomData`, then calls `_externalTransact`, which computes real `deltaAmountChanges` via `_calculateDeltaAmount` for `circomData.erc20TokenAddresses` and invokes `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)` — here `externalAddress` is `EmporiumUpgradeable`. [2](#0-1) 
2. Inside `EmporiumUpgradeable.runAction`, `stack.ops` is decoded from `circomData.externalActionData.externalActionMetadata` — arbitrary attacker-supplied bytes, not part of any deltaAmount derivation, and (when `stack.signerAddress == address(0)`) not even signature-checked. For "Case 2: Stateless Interaction" it does a raw `op.endpoint.call{value: op.value}(op.callData)`, only blocking `callHinkalWallet`/`doSendToRelay` selectors. [3](#0-2) 
3. The attacker sets `op.endpoint` = `DepositOnChainUtxosExternalAction` (assumed already whitelisted as an allowed recipient of that action per the stated preconditions) and `op.callData = abi.encodeCall(runAction, (fakeCircomData, [0]))`, where `fakeCircomData.originalSender = victim` and `fakeCircomData.erc20TokenAddresses = [victimToken]` — none of this is bound to the ZK proof Hinkal verified for the outer call.
4. `DepositOnChainUtxosExternalAction.runAction` only checks `msg.sender` via `onlyAllowedRecipient` (satisfied, since caller is Emporium) and `deltaAmounts[i] == 0` (satisfied trivially, since it's a hardcoded literal). It then calls `transferERC20TokenFrom(victimToken, victim, msg.sender=Emporium, tokenTotal)`, pulling the victim's pre-existing ERC20 allowance into Emporium. [4](#0-3) 
5. Back in `EmporiumUpgradeable.runAction`, if `victimToken` is also listed in the *outer* `circomData.erc20TokenAddresses` (attacker's own token list) with a real, proof-verified `deltaAmountChanges[i] == 0`, the top-level balance diff (`balancesAfter[i] - balancesBefore[i] == tokenTotal`) is not offset by `deltaAmountChanges[i] < 0`, so `handleOut` treats the entire stolen `tokenTotal` as a legitimate payout, transferring it to `msg.sender` (Hinkal) and minting a `UTXO` credited to the attacker's own `circomData.stealthAddressStructure`. [5](#0-4) 
6. In `Hinkal.transact`, the final balance/UTXO reconciliation is circular: `utxoAmount` is derived directly from the same `utxoSet` Emporium fabricated, and `balanceDif` equals the same `tokenTotal` that actually moved into Hinkal, so `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` holds trivially regardless of whether the funds were legitimately backed by a spent nullifier. [6](#0-5) 

No existing guard catches this: `onlyAllowedRecipient` only checks `msg.sender`, not that `circomData`/`deltaAmounts` originate from a proof Hinkal verified; `verifyWallet`'s EIP-712 check only applies to `stack.signerAddress != address(0)` and only signs op hashes, not their real-world economic effect; the circuit constraints (`inTotal + amountChanges === outTotal`) apply only to the *outer* circomData's own claimed token list and never see the forged inner `circomData`.

### Impact Explanation
Critical — direct theft of a victim's ERC20 allowance and minting of unbacked shielded value: the attacker walks away with a legitimate-looking shielded UTXO for `tokenTotal` of `victimToken` that was never deposited by them and never backed by a spent nullifier, while the victim's tokens are drained via a pre-existing allowance to `DepositOnChainUtxosExternalAction`. This is repeatable for any victim who has approved that contract, up to their allowance/balance, each transaction the attacker submits.

### Likelihood Explanation
Requires the precondition (per Q1) that `EmporiumUpgradeable` is registered as an allowed recipient on `DepositOnChainUtxosExternalAction`, and that some victim has an outstanding ERC20 approval to `DepositOnChainUtxosExternalAction` (a normal side effect of using the intended on-chain-deposit flow). No signature or privileged role is needed by the attacker beyond crafting their own valid proof for an unrelated (or zero-value) outer transaction and hand-building `EmporiumStack.ops`/`fakeCircomData` — well within an unprivileged EOA's capabilities.

### Recommendation
`DepositOnChainUtxosExternalAction` (and any `IExternalActionV2` implementer) must not treat `msg.sender` alone as sufficient authorization when it can be reached transitively through `EmporiumUpgradeable`. Either (a) prohibit `EmporiumUpgradeable`'s dispatch loop from calling other `IExternalActionV2` implementers (deny-list by checking `externalActionMap` membership of `op.endpoint`, not just the wallet selectors), or (b) require that nested op targets never accept an independently attacker-supplied `CircomData`/`deltaAmounts` pair — i.e., forbid `runAction`-shaped calldata from `EmporiumUpgradeable`'s stateless op path entirely, and require any deposit-style pull to be initiated only directly by `Hinkal._externalTransact` with the proof-verified `circomData`.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction`; configure `DepositOnChainUtxosExternalAction.setAllowedRecipients([EmporiumAddress])` per stated precondition.
2. Victim approves `DepositOnChainUtxosExternalAction` for `tokenTotal` of `victimToken`.
3. Attacker builds an outer `circomData` (own valid proof) whose `erc20TokenAddresses` includes `victimToken` with proof-derived `amountChanges[i]=0`, `onChainCreation[i]=true`, and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with one stateless op: `endpoint = DepositOnChainUtxosExternalAction`, `callData = abi.encodeCall(runAction,(fakeCircomData,[int256(0)]))` where `fakeCircomData.originalSender = victim`, `erc20TokenAddresses=[victimToken]`, metadata specifying `utxoAmounts=[[tokenTotal]]`.
4. Call `Hinkal.transact(...)`.
5. Assert: `deltaAmountChanges` logged from `Hinkal._externalTransact` for `victimToken` index == `0`, while `tokenTotal > 0` was moved via `transferERC20TokenFrom` (log/trace the ERC20 `Transfer` event from victim to Emporium) — the two diverge.
6. Assert victim's `victimToken` balance decreased by `tokenTotal`, and a new UTXO commitment credited to the attacker's `stealthAddressStructure` for `tokenTotal` of `victimToken` was inserted, with no corresponding nullifier for `victimToken` ever spent by the attacker.
