### Title
Webhook shop-domain/topic headers are not covered by HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` checks the HMAC solely against that raw body. The `shop`, `topic`, and `webhook_id` fields — which are trusted by `Registry.process` and forwarded to app handlers as authoritative tenant/context identifiers — come from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header value: [2](#0-1) 

`Registry.process` validates the HMAC (of the body only) and then trusts `request.shop`, `request.topic`, and `request.webhook_id` — all pulled straight from headers — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop header == shop that produced/authorized this signed body`. Because the signature never binds the `shop-domain` (or `topic`/`webhook-id`) header to the body, that equality is not enforced by this gem. Any HTTP client that possesses one valid `(raw_body, hmac)` pair for the app's secret — for example an attacker who owns a shop with the app installed and can trigger a webhook event on their own store — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. `HmacValidator.validate` still returns `true` because it only checks the untouched body bytes, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen shop, even though that shop did not produce this event.

This precisely matches the required bug class: "a field acted on (shop) but not covered by the HMAC (which only signs the body)."

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` (as the documented handler contract does — see the `docs/usage/webhooks.md` example that dispatches work keyed on `data.shop`) to select or mutate per-tenant records, an attacker who legitimately owns one shop installation of the app can forge webhook deliveries that are processed under a victim shop's identity. This is cross-tenant access/data confusion driven entirely by unauthenticated header trust, without needing the app's `client_secret`, `api_secret_key`, or any privileged Shopify credentials — satisfying the "Critical: cross-tenant access" impact bar.

### Likelihood Explanation
The attacker only needs an app installation on any shop they control to obtain one genuine `(body, hmac)` pair for a topic of their choosing (e.g., `app/uninstalled`, `orders/create`), then replay it directly against the app's public webhook endpoint with a forged `shop-domain` header. No secret material, MITM, or social engineering is required — only the ability to send arbitrary HTTP requests to the app's webhook route, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the signed payload verification (or otherwise cryptographically tie them to the body/signature) before `Registry.process` trusts them, e.g., by validating that the shop domain associated with the app installation matches an independently verified source (such as a stored session/access-token record for that shop) rather than trusting the raw header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook event (e.g. updates a product), causing Shopify to send a legitimately signed webhook: body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's secret), along with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H` (their own traffic, no interception needed).
3. Attacker sends a new POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in [4](#0-3)  recomputes HMAC over `B` only and it matches `H`, so validation passes.
5. `Registry.process` in [3](#0-2)  builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the app's handler, which now performs data operations attributing the attacker's event to the victim shop.
