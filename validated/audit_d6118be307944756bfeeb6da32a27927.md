### Title
First-depositor share-inflation attack in `process_deposit` when pool is initialized with a low-decimal coin mint - ([File: program/src/processor.rs])

### Summary
Raydium's pool-creation flow (`process_initialize2`) bakes in a Uniswap‑V2‑style "burned minimum liquidity" defense by permanently withholding `10^lp_decimals` units of LP supply from being minted, where `lp_decimals` is taken directly from the attacker-supplied `coin_mint`'s decimals. Because pool creation is permissionless and the coin mint is fully attacker-controlled, an attacker can create a pool with a `coin_mint` that has very low decimals (e.g. 0 or 1), reducing this protective floor to a negligible value (1 or 10) instead of a robust offset (typically ≥10^6 for normal tokens). Combined with the fact that the deposit-pricing math (`calc_total_without_take_pnl_no_orderbook`) reads live SPL vault balances rather than an internally accounted reserve, an attacker can then donate tokens directly to the vaults to skew the ratio and cause a subsequent depositor's LP mint amount to round down to a negligible or zero value.

### Finding Description
In `process_initialize2`, the LP mint's decimals are set equal to the attacker-chosen `coin_mint`'s decimals: [1](#0-0) 

The initial liquidity is computed as `sqrt(pc_amount * coin_amount)`, and only `liquidity - 10^lp_decimals` is minted to the creator — the remainder is permanently kept in `amm.lp_amount` (the pool's internal LP-supply accounting) but never minted to anyone, functioning as a virtual/burned-liquidity floor: [2](#0-1) 

Because `lp_decimals` is attacker-controlled via `coin_mint.decimals`, a pool creator can pick a coin mint with `decimals = 0` (a valid SPL mint configuration), making this "floor" equal to `1` — the same fragile minimum the DODO GSP report warns about, instead of the intended large offset that make such attacks economically unattractive.

Since the creator is the sole initial LP holder, they can withdraw nearly all of their minted LP tokens, driving `amm.lp_amount` back down toward this tiny floor via the withdraw path's decrement: [3](#0-2) 

Subsequent deposit pricing uses live vault token balances, not an isolated internal reserve variable, so a plain SPL token transfer directly to `amm.coin_vault` / `amm.pc_vault` (no program interaction required) changes the totals used for share pricing: [4](#0-3) 

The deposit's LP-mint amount is computed with `Floor` rounding against `amm.lp_amount` and the (now inflated by direct donation) vault totals: [5](#0-4) [6](#0-5) 

With `amm.lp_amount` at its minimal floor (e.g. `1`) and vault balances hugely inflated by direct donation, a victim's subsequent `Deposit` will have its `mint_lp_amount` rounded down to a value far below fair value (or exactly `0`, which reverts via the explicit zero-mint check), transferring economic value from the depositor to the attacker's existing LP position. [7](#0-6) 

### Impact Explanation
If successfully executed against a coin mint with very low decimals, a victim depositor's real tokens (coin and pc, computed via `exchange_coin_to_pc`/`exchange_pc_to_coin` against the manipulated ratio) are pulled into the vaults while they receive a disproportionately small number of LP shares. The attacker, holding effectively all the real (non-virtual) LP supply, can then withdraw pro-rata and capture the victim's contributed value. This constitutes value theft from an LP depositor and/or unfair/insolvent LP accounting, matching the Medium-severity classification of the analogous DODO GSP finding.

### Likelihood Explanation
Exploitability depends entirely on the attacker being able to create a pool with a low-decimal coin/pc mint (0–2 decimals) and getting an unsuspecting depositor to deposit into that specific pool shortly after the attacker drains/donates. This is a narrower precondition than the generic ERC4626 case (which applies to essentially every vault), since most real-world SPL tokens use 6–9 decimals, which makes the floor (`10^decimals`) large enough to make the attack economically unattractive. The vulnerability is realistic only for pools built on custom/low-decimal tokens, which reduces but does not eliminate likelihood, since pool creation instructions (`Initialize2`) place no restriction on `coin_mint`/`pc_mint` decimals.

### Recommendation
- Enforce a minimum decimals requirement (or a fixed minimum absolute `MINIMUM_LIQUIDITY`, e.g., 1000 units regardless of decimals) in `process_initialize2` instead of deriving the burn floor solely from `coin_mint.decimals`.
- Derive deposit/withdraw pricing from internally tracked reserve amounts that are only mutated by validated program instructions, rather than trusting live SPL vault balances directly, to remove the direct-donation attack surface.
- Consider adding a slippage/minimum-shares-out check on `Deposit` (similar to `other_amount_min` already present for the token side) that also enforces a minimum acceptable `mint_lp_amount`.

### Proof of Concept
1. Attacker calls `Initialize2` with a `coin_mint` created with `decimals = 0` and an arbitrary `pc_mint`, providing `init_coin_amount` and `init_pc_amount` such that `sqrt(init_pc_amount * init_coin_amount)` is large (e.g., worth $2,000). `user_lp_amount = liquidity - 10^0 = liquidity - 1` is minted to the attacker; `amm.lp_amount = liquidity` [8](#0-7) .
2. Attacker calls `Withdraw` for `user_lp_amount - ε` (nearly all of their LP), driving `amm.lp_amount` down toward `1` while draining most real tokens from the vaults back to themselves [9](#0-8) .
3. Attacker performs a plain SPL `Transfer` (outside the AMM program) sending a large amount of coin and pc tokens directly into `amm.coin_vault` and `amm.pc_vault`, inflating `total_coin_without_take_pnl`/`total_pc_without_take_pnl` computed from live vault balances [4](#0-3) .
4. Victim calls `Deposit` with a reasonable amount; `mint_lp_amount` is computed via `Floor` rounding against the inflated totals and the near-`1` `amm.lp_amount`, resulting in a negligible number of LP tokens minted to the victim relative to the value they contributed [5](#0-4) .
5. Attacker calls `Withdraw` again, redeeming their remaining LP (now representing nearly the entire pool value, including the victim's deposit) for a disproportionate share of coin/pc tokens.
