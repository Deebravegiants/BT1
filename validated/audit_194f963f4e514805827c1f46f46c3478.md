## Confirmed Analog

For the OAuth callback flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the signed string, so the shop identity is cryptographically bound to the HMAC [1](#0-0) . But for the webhook flow, `Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers and are never included in the HMAC-signed material [3](#0-2) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` — which validates the raw body against the secret — and then trusts `request.shop`/`request.topic`/`request.webhook_id` as-is when constructing `WebhookMetadata` passed to the handler [4](#0-3) .

### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing shop/topic spoofing via replay - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body. The `shop`, `topic`, and `webhook_id` values, which are read from HTTP headers and passed downstream as trusted tenant/topic identifiers, are excluded from the HMAC-covered bytes.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(client_secret, verifiable_query.to_signable_string)` and compares it against the `hmac` field of the query object [5](#0-4) . For webhook requests, `to_signable_string` returns `@raw_body` only [2](#0-1) . Meanwhile, `Request#shop`, `#topic`, and `#webhook_id` are parsed straight from header values with no cryptographic tie to the HMAC [3](#0-2) .

`Registry.process` validates the HMAC and then builds `WebhookMetadata` directly from `request.topic`, `request.shop`, and `request.webhook_id` before dispatching to the app's handler [4](#0-3) . This breaks the intended binding: `shop-in-signed-bytes == shop-trusted-by-handler`. Instead, the code enforces only `body-in-signed-bytes == body`, but trusts `header.shop != signed-bytes.shop`.

This differs from the OAuth callback path in the same gem, where `AuthQuery#to_signable_string` explicitly folds `shop` into the signed string [1](#0-0) , demonstrating the gem's own precedent that shop identity should be part of the signed payload — a precedent not followed for webhooks.

### Impact Explanation
Since the same app `client_secret` is shared across every merchant install, any actor who can install the app on their own store (an "unprivileged internet user" from the app's perspective — no admin/API credentials of the target shop required) can obtain a validly-HMAC-signed webhook body for their own shop, then replay that request to the app's webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header rewritten to reference a different, victim shop. The HMAC still validates because it only covers the untouched body. The host application's webhook handler receives `WebhookMetadata` claiming to be from the victim shop and will act on it — e.g., triggering shop-scoped side effects (data deletion, order processing, GDPR redaction flows) against the wrong tenant, or spoofing the `topic` to route a benign payload into a sensitive handler (e.g. `shop/redact`). This is a cross-tenant identity-binding bypass reachable purely through this gem's own signature-verification logic.

### Likelihood Explanation
Requires only the ability to install the app on an attacker-controlled shop (a normal, unprivileged action any Shopify merchant/developer can take) and the ability to send an HTTP request to the app's public webhook endpoint — no access to the target's session, access token, or `client_secret` is needed. Likelihood is high for any app that trusts `WebhookMetadata.shop`/`.topic` for authorization or tenant-scoping decisions, which is the documented purpose of that field.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header fields the handler trusts) in the HMAC-signed material, or independently verify that the header-derived `shop` matches an expected/allow-listed value before dispatching to handlers. At minimum, `Webhooks::Request#to_signable_string` should bind the shop domain to the signature the same way `Oauth::AuthQuery#to_signable_string` binds shop for the OAuth callback.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (own shop), completing normal OAuth.
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app, signed with `HMAC-SHA256(client_secret, raw_body)`, with header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same endpoint, only modifying the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (body untouched).
4. `Registry.process` calls `HmacValidator.validate(request)` — passes, because `to_signable_string` only checks `raw_body`, unaffected by the header change [2](#0-1) .
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the app's handler [6](#0-5) , which now processes attacker-supplied data as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
