### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop` (tenant identifier) is read from a separate, unauthenticated HTTP header. Any party in possession of one genuine, HMAC-valid webhook payload (e.g., a merchant on their own store) can replay that exact body against the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header. `Registry.process` accepts the HMAC as valid and dispatches the handler with the attacker-chosen `shop`, breaking the binding between "bytes verified" (the raw body) and "tenant attributed" (the shop header).

### Finding Description
`Request#hmac` and `Request#to_signable_string` compute/validate the signature strictly from `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop` is populated purely from a header value with no cryptographic linkage to the signed body: [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — which checks `to_signable_string` (the body) against `hmac` — and then forwards `request.shop` directly to the app's handler as the authoritative tenant identifier: [4](#0-3) 

The identity-binding equality that should hold is: `shop_that_produced_signed_bytes == shop_attributed_to_handler`. Because the `shop-domain` header sits outside the HMAC-covered content, this equality is not enforced by the gem — the header can be swapped independently of the body/HMAC pair.

### Impact Explanation
All shops that install the same app share the app's single `api_secret_key`, so any shop's genuine webhook (with a valid HMAC over its body) is cryptographically fungible across shops from this gem's point of view. An attacker who controls a real, app-installed shop can capture one legitimate webhook (valid body + valid HMAC) and replay it at the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still returns `true` (body/HMAC pair untouched), and the handler receives `WebhookMetadata` attributing the (attacker-crafted or replayed) payload to the victim shop — i.e., cross-tenant data injection/confusion, since the app has no gem-level assurance that the header-derived `shop` matches the shop that actually produced the signed bytes.

### Likelihood Explanation
Requires only: (1) network access to the app's public webhook endpoint, and (2) ability to obtain one valid webhook signature — trivially available to any unprivileged user who can install the app on a shop they control (e.g., a free/dev store) and capture a real webhook delivery. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop` value into the material that is HMAC-verified (or otherwise cryptographically authenticate it), for example by requiring/validating that the shop domain is included in the signed payload construction, or by rejecting requests where the header-derived shop cannot be corroborated by data inside the verified body. At minimum, document prominently that `request.shop` is unauthenticated relative to the HMAC and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (valid because `HmacValidator.validate` only checks `HMAC(secret, B) == H`, per `to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B`, same `H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the attacker-controlled header (`lib/shopify_api/webhooks/request.rb:20-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `B`/`H` are checked (`lib/shopify_api/webhooks/registry.rb:190`).
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process/attribute attacker-supplied webhook content as belonging to the victim shop.
