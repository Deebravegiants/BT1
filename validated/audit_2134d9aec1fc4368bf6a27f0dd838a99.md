### Title
Webhook shop-domain header is trusted for tenant attribution but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` header, while `Utils::HmacValidator` (invoked by `Registry.process`) only authenticates the raw request body. The header used to attribute a webhook to a specific merchant is never part of the signed material, so the cryptographic guarantee ("this body was signed by our app secret") does not extend to ("this body belongs to shop X").

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (and `request.parsed_body`) to the registered handler: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it against the `hmac` accessor: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` is read from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is disjoint from the signed bytes: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`hmac_verified(raw_body) == true` implies `shop == the tenant the signed body actually belongs to`

but the code only proves the first predicate and then unconditionally trusts the header for the second. Concretely: an app's `api_secret_key` is a single per-app secret shared across every installed shop (it is not scoped per tenant). A merchant who has legitimately installed the app receives real webhooks for their own shop, each with a valid `hmac-sha256` over the body. Because `to_signable_string` ignores the shop header, that same `(raw_body, hmac)` pair remains a cryptographically valid pair no matter what shop-domain header accompanies it. A malicious merchant (an "unprivileged" actor with respect to any other tenant, even though privileged for their own shop) can therefore replay their own genuinely-signed webhook body to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` (body signature checks out), and `WebhookMetadata` is built with the attacker-supplied `shop`: [5](#0-4) 

Any host application that follows this gem's documented pattern — trusting `data.shop`/`request.shop` from the handler callback to select which tenant's record to update — will process attacker-controlled data under another shop's identity.

### Impact Explanation
This breaks the tenant boundary: `shop` (used by host apps as the per-tenant lookup key, analogous to a session key) is not bound to the HMAC-verified content. An attacker who is a legitimate user of the app for their own store can forge webhook events "for" a different shop with a body they control (their own real order/product/customer data, or other topics with attacker-influenced content), causing the host application to write or act on this data keyed to a victim shop. This is a cross-tenant data-integrity/attribution issue arising directly from this gem's own webhook verification logic — not a misuse of documented API contracts, since the library itself hands out `request.shop` as trustworthy metadata post-`HmacValidator.validate`.

### Likelihood Explanation
Requires: (1) attacker has legitimate install of the target app on their own shop (readily obtainable for public apps), (2) attacker can capture a real webhook `raw_body` + `hmac-sha256` pair sent to their own endpoint, and (3) attacker can POST to the app's webhook receiver with a forged `X-Shopify-Shop-Domain` header (trivial, since it's just an HTTP header under attacker control when crafting the replayed request). No access to the `api_secret_key`, access tokens, or another merchant's credentials is needed. This is a realistic, low-effort exploit path for any app built on this gem's `Webhooks::Request`/`Registry.process`.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the HMAC-signed material, or otherwise cryptographically bind the asserted shop to the verified body — e.g., mirror Shopify's actual webhook verification guidance by treating `shop`/`topic` as untrusted unless corroborated against a value derived from data that is itself covered by the signature (or against a shop the app knows it registered this exact callback path/session for). At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host app against known installed shops before being used as a data-attribution key.

### Proof of Concept
1. App developer registers `orders/create` webhook with a handler that does `Order.find_or_create_by(shop: data.shop).update(data.body)`.
2. Attacker installs the app on `attacker-shop.myshopify.com`, places a real order, and captures the resulting POST: `raw_body = B`, header `shopify-hmac-sha256 = H` (valid HMAC of `B` under the shared `api_secret_key`), header `shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker resends the identical `B`/`H` to the app's webhook endpoint but with header `shopify-shop-domain = victim-shop.myshopify.com`.
4. `Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `HmacValidator.validate` recomputes HMAC over `B` only and it matches, so validation succeeds: [6](#0-5) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to attribute attacker-controlled order data to `victim-shop.myshopify.com`.

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
