The documentation explicitly states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — implying the `shop` field is trustworthy once `process` succeeds. This is the exact identity-binding gap needed.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are trusted by handlers without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` (invoked from `Registry.process`) authenticates *only* the body bytes against the app's `client_secret`. All identifying headers — `shop`, `topic`, `webhook_id`, `api_version` — are read directly from attacker-controllable HTTP headers and passed unchanged into the handler, without ever being part of the signed material.

### Finding Description
`Registry.process` is documented to the host application as verifying "the request did indeed come from Shopify": [1](#0-0) 

The actual verification only checks the HMAC over the body: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [3](#0-2) 

For webhooks, `to_signable_string` is bound only to `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding: [4](#0-3) 

The `shop` value is then passed unchanged into the handler's data object, which apps are told to use to identify the tenant for the webhook: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `HMAC-verified(body)` ≠ `HMAC-verified(shop)`. Because the same `client_secret` is shared across every shop that has installed the app, any merchant who has legitimately installed the app can capture one of their own genuine webhook deliveries (valid HMAC over that body) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. The HMAC still validates (it only covers the body), and `Registry.process` passes `shop: <victim-shop>` to the handler even though the payload actually belongs to the attacker's own store.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged app user (a merchant who installed the app, with no elevated access) can make the app process attacker-supplied webhook content while it believes the content originated from an arbitrary other shop. Any host application logic that keys off `data.shop` from `WebhookMetadata` (e.g., looking up the tenant record, applying data to the "shop" indicated by the field, or triggering tenant-scoped side effects) can be manipulated into acting on/for a shop the attacker does not control, which is a cross-tenant impact within the scope described (identity binding broken between the field acted upon and the bytes actually covered by the HMAC).

### Likelihood Explanation
Any merchant who installs the app receives real webhook traffic with valid HMACs signed by the shared `client_secret`. Capturing a legitimate payload/HMAC pair and replaying it with a modified `shopify-shop-domain` (or `shopify-topic`/`shopify-webhook-id`) header requires no secret knowledge and no special privilege beyond ordinary app installation — this is a realistic, low-effort attack path reachable purely through the gem's own webhook verification code path.

### Recommendation
Bind all identifying fields used downstream (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-signable material, or independently authenticate the `shop` value (e.g., cross-check it against the session/tenant the raw body's HMAC was actually generated for) before exposing it via `WebhookMetadata`. At minimum, document prominently that `Registry.process`'s HMAC check only authenticates the body and that `data.shop`/`data.topic` must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on shop "attacker.myshopify.com"
# and captured a real webhook delivery for topic "orders/create":
raw_body    = '{"id": 1, "note": "hello"}'
valid_hmac  = "<hmac Shopify actually sent, computed over raw_body with the app's shared client_secret>"

# Attacker replays it against the app's webhook endpoint, but swaps the shop header:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac,          # still valid: it only signs raw_body
  "x-shopify-shop-domain"  => "victim.myshopify.com", # spoofed, not covered by HMAC
  "x-shopify-webhook-id"   => "attacker-controlled-id",
  "x-shopify-api-version"  => "2024-01",
}

ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
)
# HmacValidator.validate succeeds (see lib/shopify_api/utils/hmac_validator.rb:12-31,
# lib/shopify_api/webhooks/request.rb:35-38 -- to_signable_string is only @raw_body),
# and the handler is invoked with shop: "victim.myshopify.com" even though the
# payload was never generated for that shop.
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
