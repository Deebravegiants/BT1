Found the analog: `WrappedHyperFungibleTokenUpgradeable.configure()` lets the owner change `_underlying` at any time (unlike `_host`, which is only set once), and every accounting path (`send`, `onAccept`, `onPostRequestTimeout`) operates on whatever `_underlying` currently points to with no balance-based invariant check.

### Title
Owner-changeable `_underlying` token in `WrappedHyperFungibleTokenUpgradeable` can brick or drain locked funds - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`WrappedHyperFungibleTokenUpgradeable.configure()` unconditionally overwrites `_underlying` on every call, with no check that the contract's balance of the previous underlying token is zero, mirroring the `Game.sol` `setDerbyToken` bug class where changing the tracked token address after funds are already custodied severs the link between the contract and the tokens it is supposed to account for.

### Finding Description
`_host` is guarded by a one-shot check (`if (_host == address(0)) { _host = options.host; }`), but `_underlying` and `_dispatcher` are reassigned unconditionally on every `configure()` call: [1](#0-0) 

All value-moving logic references `_underlying` directly rather than tracking balances per token:
- `send()` locks tokens into the contract via `IERC20(_underlying).safeTransferFrom(...)` or wraps native ETH into `_underlying` via `IWETH(_underlying).deposit()`: [2](#0-1) 
- `onAccept()` releases funds by calling `IWETH(_underlying).withdraw(...)` / `IERC20(_underlying).safeTransfer(...)`: [3](#0-2) 
- `onPostRequestTimeout()` refunds via the same `_underlying`-based transfer: [4](#0-3) 

If the owner calls `configure()` again after the contract has already locked balance of the original `_underlying` token (e.g., to rotate the dispatcher or toggle `isWeth`), the contract silently starts operating against a new token address. Any tokens of the old underlying that remain locked in the contract become permanently unrecoverable through the intended flows (`onAccept`/`onPostRequestTimeout` will try to transfer the *new* token, which the contract may not hold, causing reverts and stuck cross-chain messages), while `IERC20(newUnderlying).safeTransfer` calls in `onAccept` could also pay out from any balance of the new token the contract happens to hold (e.g. donated or airdropped), independent of what was actually escrowed for that specific transfer. This is the same class of bug as the reported `Game.sol` `setDerbyToken`: reassigning the token address that in-flight accounting depends on, without invariant checks, breaks the correspondence between escrowed balance and the address subsequently used for withdrawals.

Contrast this with `EvmHost.updateHostParamsInternal`, which explicitly guards against exactly this class of bug for the protocol fee token: [5](#0-4) 
No equivalent `balanceOf(address(this)) == 0` guard exists before reassigning `_underlying` (or `_dispatcher`) in `WrappedHyperFungibleTokenUpgradeable.configure()`, nor in the sibling `HyperFungibleTokenUpgradeable.configure()`/`HyperFungibleToken.configure()` for `_dispatcher`.

### Impact Explanation
Because this contract is a real cross-chain custody point (it locks ERC20/WETH on `send()` and releases it on `onAccept`/timeout), an owner rotating `_underlying` while tokens are locked either freezes user funds permanently (in-flight sends can never be completed or refunded against the old token) or lets `onAccept` pay out against an unrelated token balance, decoupling the escrow accounting from actual custody. This matches a Medium-severity "permanent freezing of funds / unsound accounting" class of impact, reachable purely from normal owner-privileged operations combined with a single user-submitted cross-chain transfer already in flight.

### Likelihood Explanation
Requires only that `configure()` be called more than once while a transfer is pending (a plausible operational action, e.g., rotating the `dispatcher` for calldata routing, or fixing a misconfiguration) — no special governance/consensus compromise is needed, only normal use of the exposed `onlyOwner` function.

### Recommendation
Make `_underlying` (and ideally `_dispatcher`) settable only once, mirroring the existing `_host` guard, or require `IERC20(_underlying).balanceOf(address(this)) == 0` before allowing `_underlying` to change, analogous to the `CannotChangeFeeToken` check already implemented in `EvmHost.updateHostParamsInternal`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleTokenUpgradeable`, call `configure({host, dispatcher, underlying: TokenA, isWeth: false})`.
2. User calls `send()`, locking `amount` of `TokenA` in the contract (`safeTransferFrom` in `WrappedHyperFungibleTokenUpgradeable.sol:300`).
3. Before the cross-chain message is delivered or times out, owner calls `configure({host, dispatcher, underlying: TokenB, isWeth: false})` — succeeds unconditionally per `WrappedHyperFungibleTokenUpgradeable.sol:200-207`.
4. When the timeout fires, `onPostRequestTimeout` attempts `IERC20(TokenB).safeTransfer(refundee, message.amount)` — either reverts (if the contract holds no `TokenB`), permanently stalling the timeout/refund, or pays the refundee out of unrelated `TokenB` balance the contract happens to hold, while the originally locked `TokenA` remains stuck in the contract with no code path referencing it anymore.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(incoming.request.body, (HyperFungibleTokenUpgradeable.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }
