Found the analog. `convert_to_erc20` in `pallet-hyper-fungible-token` scales a burned local amount up by `10^(erc_decimals - local_decimals)` when dispatching a cross-chain send, and `convert_to_balance` scales an incoming ERC20 amount back down by the same factor using integer division, i.e. floor rounding, on `on_accept`/`on_timeout`.

### Title
Truncating decimal conversion in `pallet-hyper-fungible-token` lets `send`/`on_accept` roundtrips silently burn precision, breaking the 1:1 backing invariant across repeated small transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` moves tokens between a Substrate chain and paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts by escrowing/burning locally and minting/unlocking on the counterpart chain, and vice versa. When decimals differ between the local asset and the EVM representation, amounts are rescaled with `convert_to_erc20` (scale up, exact) and `convert_to_balance` (scale down, integer division/floor) [1](#0-0) . Because the down-scaling path truncates instead of rejecting or accumulating remainders, dust below the local asset's decimal resolution is silently dropped on every leg that decreases decimals.

### Finding Description
`send` converts the locally escrowed/burned `u128` amount to the ERC20-side `U256` by multiplying by `10^(erc_decimals - local_decimals)` — an exact, lossless operation when `erc_decimals >= local_decimals` [2](#0-1) . The reverse direction, exercised by `on_accept` (mint/unlock a received transfer) and `on_timeout` (refund a burned/escrowed amount), uses `convert_to_balance`, which divides the incoming `U256` by the same power of ten and discards the remainder [3](#0-2) . This function is called on the exact same egress path — an unprivileged holder invokes `send`, and any relayer can later invoke `on_timeout` with a forged or legitimate timeout proof, or the destination `onAccept` mints against the burned amount — through `module.rs`'s `on_accept`/`on_timeout` handlers [4](#0-3) [5](#0-4) .

Whenever the local asset has fewer decimals than the ERC20 side is configured with, a value that scales up cleanly on `send` gets divided back down on `on_timeout`/`on_accept`; any remainder below the local unit's resolution is truncated rather than preserved. A user can repeatedly `send` dust-sized amounts and have the corresponding refund/mint truncate a fraction of each roundtrip to zero, so the effective total minted/refunded across many small operations is strictly less than what was escrowed/burned — the reverse of an unbacked mint, but it is a violation of the same 1:1-backing invariant the escrow/burn design depends on, and it also means that on `on_timeout` refund, the pallet does not restore the exact escrowed/burned amount, permanently stranding the truncated remainder inside the pallet's custody account with no path to recover it. There is no check anywhere in `send`, `on_accept`, or `on_timeout` that the round-tripped amount matches the original amount, analogous to the missing `_before_token_transfer` cap check in the PSP22Capped report — the conversion functions exist but nothing enforces that the value is preserved end-to-end.

### Impact Explanation
This is reachable by any signed account calling `send` and any relayer submitting the corresponding timeout — no privileged role is required. The truncation permanently stranding value inside `Pallet::<T>::pallet_account()` is a form of fund loss for the affected user/timeout-refund path (Medium impact: precision loss/dust, bounded per-transaction by the decimal delta, but compounds without limit across repeated calls and is a genuine invariant break in escrow/burn accounting rather than a purely cosmetic rounding difference).

### Likelihood Explanation
Likely to occur under normal operation whenever a registered asset's local decimals are fewer than the destination chain's configured `Precisions` value (a common, governance-configured, non-adversarial scenario per the pallet's own decimals-scaling design), and can be deliberately amplified by an attacker sending many minimum-unit transfers to maximize cumulative dust loss.

### Recommendation
Either (a) reject `send`/`on_accept`/`on_timeout` amounts that do not round-trip exactly through `convert_to_erc20`/`convert_to_balance` (return an error instead of silently truncating), or (b) track and carry forward truncated remainders per asset/account so no value is destroyed, mirroring how `PSP22Capped` was fixed by enforcing an invariant check in the transfer/mint hook rather than leaving it as an unenforced helper function.

### Proof of Concept
1. Register an asset with `local_decimals = 6` and `Precisions` (erc_decimals) `= 18` for the paired EVM chain.
2. Call `send` with `amount = 1` (the smallest local unit). `convert_to_erc20(1, 18, 6) = 1 * 10^12`, dispatched to the EVM side [6](#0-5) .
3. Suppose this request times out (or, symmetrically, the counterpart later sends back `10^12 - 1` wei, one unit short of the scaled value): `on_timeout`/`on_accept` calls `convert_to_balance(value, 18, 6)`, which divides by `10^12` using integer division [7](#0-6) . Any value in `[0, 10^12)` floors to `0`, so a refund/mint of `0` local units is executed while the original `1` unit remains escrowed/burned in `Pallet::<T>::pallet_account()`, permanently unreachable by the user.
4. Repeating this at scale (many minimum-unit `send` calls followed by timeouts) accumulates unrecoverable dust proportional to the number of transactions, confirmed by the pallet's own test harness pattern in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs`, which already exercises `convert_to_erc20`/round-trip conversions [8](#0-7) .

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
