### Title
Session Fixation via Predictable, Unauthenticated `SessionUtils.current_session_id` Cookie Lookup - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session lookup key for non-embedded apps (and embedded apps without a session token) entirely from the raw, unsigned `shopify_app_session` browser cookie, with no cryptographic verification that the value was actually issued by this app for the requesting shop.

### Finding Description
`SessionUtils.current_session_id` falls back to `cookie_session_id(cookies)` whenever no `shopify_id_token` is supplied, returning `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` verbatim [1](#0-0) . This value is used unmodified by the host application as the key to look up the persisted `Session` object (which contains the merchant's real `access_token`) — the documentation explicitly states that "session persistence... is fulfilled by the web framework middleware," and that the returned cookie value should be used to store/retrieve the session later [2](#0-1) .

Critically, this session id is not a random opaque secret bound to a signature: for offline sessions it is deterministically computed as `"offline_#{shop}"` [3](#0-2) , and for online sessions as `"#{shop}_#{associated_user.id}"` [4](#0-3) . Both `shop` (the merchant's `.myshopify.com` domain) and `associated_user.id` are values an attacker can often observe or guess (e.g., the shop domain is public/discoverable, and admin user IDs are small sequential integers exposed in numerous places). The library sets this exact string as the cookie value with no signature, MAC, or expiry-bound token wrapping it [5](#0-4) .

This breaks the intended identity binding: **`cookie value received == session id that must be proven, cryptographically, to belong to this requester`** is instead satisfied as **`cookie value received == raw unauthenticated bytes accepted with no verification`**. Unlike the OAuth callback flow, which explicitly HMAC-verifies the `AuthQuery` via `HmacValidator.validate` [6](#0-5) , and unlike the state-nonce check that compares the cookie to `auth_query.state` [7](#0-6) , no equivalent binding exists for `cookie_session_id` — the value is simply trusted and handed back to the host app as "the session id," which the host app is expected to use directly for session storage lookup.

### Impact Explanation
If an attacker sets their own browser's `shopify_app_session` cookie to a guessed/predictable value such as `offline_victim-shop.myshopify.com` (offline session id format is fully deterministic and documented by this library), and the host application's session storage naively keys off this attacker-controlled cookie value (as the library's own documentation instructs apps to do), the attacker's requests will be treated as authenticated on behalf of the victim shop. The persisted `Session` object returned contains the victim's real `access_token`, enabling cross-tenant access to the merchant's Admin API data — this is a session-fixation / forced-session vulnerability that can lead to theft of a merchant's access token and cross-tenant access, matching the Critical/High impact criteria (session fixation, cross-tenant access, credential theft).

### Likelihood Explanation
Likelihood is elevated because: (1) the session-id formats (`offline_#{shop}`, `#{shop}_#{user_id}`) are deterministic and documented/derivable directly from this gem's own source, (2) `shop` domains are typically public, and user IDs are small, enumerable integers, (3) the library performs zero verification on the cookie's authenticity before returning it as the trusted session identifier, and (4) the library explicitly instructs downstream apps to treat this value as the session lookup key rather than treating it as an opaque, need-to-verify token. The main mitigating factor is that many apps use the `shopify_app` gem instead, which may add its own protections; but for any app following this gem's own documented flow directly, the exposure is direct.

### Recommendation
Do not expose a raw, predictable session id as the sole trust anchor for session lookup. Bind the session cookie to a signed/HMAC'd or otherwise unguessable random token (as is already done for OAuth `state`), verify it against a value only known to the server (e.g., re-derive/validate a signature over the session id before trusting it in `cookie_session_id`), and avoid deterministic formats like `"offline_#{shop}"`/`"#{shop}_#{user_id}"` being used directly as bearer-style lookup keys without an additional authenticated binding.

### Proof of Concept
1. Attacker learns/guesses a target shop's domain, e.g. `victim-shop.myshopify.com` (publicly discoverable).
2. Attacker sets their own browser cookie `shopify_app_session=offline_victim-shop.myshopify.com` (format derived from `Session.from` / `offline_session_id`, see `lib/shopify_api/auth/session.rb:116`).
3. Attacker calls the app; the app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchecked (`lib/shopify_api/utils/session_utils.rb:68-71`).
4. If the host app's session store (built per this gem's own documented pattern) has an entry under that id — e.g., because the real victim shop is already installed — the attacker's request is serviced using the victim's persisted `Session`, including its real `access_token`, granting cross-tenant access.
