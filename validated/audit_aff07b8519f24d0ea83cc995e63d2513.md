### Title
Attacker-donated LT permanently inflates `protectedLT` escrow accounting, freezing a graduating token's curve-raised LT and skewing its LP away from the curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` treats *any* LT sitting in the `Bonding` contract beyond the current token's own cached `ltFromPair` as belonging to "a concurrent graduation on the same LT ... or stray dust", and unconditionally protects it from being deposited into the new LP or swept to the owner. This `protectedLT` value is a shared, contract-wide "context" (analogous to the duplicated-context object in the Quarkus/Vert.x advisory) that is supposed to isolate one graduation's escrow from another's, but it is derived from the raw `balanceOf(this)` with no way to distinguish a real concurrent escrow from LT an unprivileged attacker simply `transfer`s straight into `Bonding`. That mis-attribution silently "leaks" the attacker's untracked balance into the current graduation's isolation bucket, starving the legitimate deposit/rebalance budget of the token's own curve-raised LT and permanently stranding the shortfall in `Bonding` with no recovery path.

### Finding Description
`finalizeGraduation` snapshots the escrow context once, at the top of the call: [1](#0-0) 

`protectedLT` is then threaded through the whole seeding pipeline as the amount that must be preserved and never touched by *this* graduation:

- `_seedUniswapV2Direct` → `_seedRebalancing` (Regime 3, hostile-pre-seed rebalancing) uses it to size the rebalance swap budget via `_ltSwapInventory`: [2](#0-1) 
and directly as the max-swap input for the LT-in rebalance leg: [3](#0-2) 

- `_routerDepositAndDispose` uses it again to size the actual `addLiquidity` deposit: [4](#0-3) 

- and finally `_sweepLTToOwner` uses the same value to decide what may be recovered by the owner: [5](#0-4) 

The natspec explicitly frames `protectedLT` as isolation between concurrent graduations that happen to share the same LT reserve asset: [6](#0-5) 

The problem is that `Bonding` has no accounting of *whose* LT is actually escrowed — it only knows `balanceOf(this)` and this graduation's own `p.ltFromPair`. Any unprivileged wallet can `IERC20(lt).transfer(bondingAddress, dust)` directly (an explicitly in-scope, unprivileged action). That donation is indistinguishable from a real concurrent graduation's escrow, so it gets folded into `protectedLT` and is *never* released: it cannot be deposited into this graduation's LP (excluded from `remLT`/swap budget), and it cannot be swept to the owner (`_sweepLTToOwner` only sweeps the amount *above* `protectedLT`). The donation, plus any of this graduation's own shortfall that gets shifted below that inflated threshold, is stuck permanently — the same "context" that was meant to protect a different transaction's isolated funds instead swallows and freezes the current transaction's real funds too.

This only bites in Regime 3 (`_seedRebalancing`/`_routerDepositAndDispose`), which is reachable whenever a hostile actor has pre-minted LP in the HyperSwap V2 TOKEN/LT pair ahead of `finalizeGraduation` — an attack surface the codebase itself explicitly acknowledges and defends against for the *undonated* case: [7](#0-6) 

### Impact Explanation
- The shortfall between the token's rightful `ltFromPair` (real, curve-raised trader funds) and what the deposit/rebalance logic is allowed to touch is permanently trapped in `Bonding` — no function in `Bonding` or `LPLock` can ever move it out, since it sits below `protectedLT` on every subsequent computation (and every later graduation sharing the same LT only compounds the mislabeled bucket).
- Because `_pairRebalance`'s swap budget and `_routerDepositAndDispose`'s deposit amount are both capped short, the graduating token's LP can be seeded at a ratio that has drifted from the true curve-close price, and with less total liquidity than the curve actually raised.
- This is a concrete, permanent freeze of trader/LP funds and a price-integrity failure of the new LP, matching the Validate criteria (permanent freezing of trader/LP funds + LP seeded away from curve close price).

### Likelihood Explanation
Both preconditions are cheap, permissionless, single-transaction actions available to any unrelated wallet:
1. Pre-mint the HyperSwap V2 TOKEN/LT pair for a not-yet-graduated token (creating the "hostile pre-seed" Regime 3 condition the contract already anticipates).
2. `transfer` a small amount of the shared LT directly to the `Bonding` contract address.

No special role, timing precision, or governance access is required, and the effect compounds every time `finalizeGraduation` runs for any token sharing that LT thereafter.

### Recommendation
Track escrowed LT per pending graduation explicitly (e.g., accumulate a running `totalPendingLt` in `BondingStorage`, incremented in `_enterGraduating`/`_prepareGraduationLiquidity` and decremented in `finalizeGraduation`), rather than inferring "protected" balance as `balanceOf(this) - p.ltFromPair`. Any LT balance in excess of the sum of genuinely tracked pending escrows should be sweepable/attributable, so a bare `transfer()` donation cannot be perpetually misclassified as another graduation's funds and cannot shrink the current graduation's legitimate deposit/rebalance budget.

### Proof of Concept
1. Attacker mints/acquires LT for a token `T` that is close to graduating (or already `Graduating`).
2. Attacker creates the HyperSwap V2 `T`/LT pair (if not existing) and calls `pair.mint()` against a small self-funded seed — the acknowledged Regime-3 hostile pre-seed.
3. Attacker directly `IERC20(lt).transfer(address(Bonding), dust)`.
4. `finalizeGraduation(T)` is called (permissionlessly, by the keeper or anyone). `protectedLT = balanceOf(Bonding) - p.ltFromPair` now includes the attacker's `dust`, shrinking the swap budget in `_pairRebalance`/`_ltSwapInventory` and the deposit amount in `_routerDepositAndDispose`.
5. The LP for `T` is seeded with less LT than `p.ltFromPair` and/or at a ratio that has drifted from the curve-close price; the shortfall LT remains in `Bonding`, now below the (attacker-inflated) `protectedLT` threshold on every future call, so `_sweepLTToOwner` never releases it — it is permanently stuck.
