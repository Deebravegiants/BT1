## Title
`IntentsBase._withdraw()` does not guard against a paused/blacklisted input token, permanently freezing a solver's escrowed cross-chain fill - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
Cross-chain intent fills irreversibly deliver output tokens to the beneficiary on the destination chain before the escrowed input tokens are released to the solver on the source chain via an ISMP message. The release step, `_withdraw()`, performs an unconditional `IERC20.safeTransfer` with no check that the escrowed token is still transferable (e.g., paused USDC) or that the solver is not blacklisted (e.g., USDT). If either condition holds, the release reverts every time it is attempted, permanently freezing the solver's earned escrow while the solver has already unconditionally given away the output tokens.

### Finding Description
In `_fillCrossChain()`, the solver transfers output tokens to the beneficiary immediately and irreversibly (`IERC20(token).safeTransferFrom(msg.sender, beneficiary, ...)`), then dispatches a `RedeemEscrow` post request back to the source chain: [1](#0-0) 

On the source chain, `onAccept` handles `RedeemEscrow`/`RefundEscrow` by decoding the `WithdrawalRequest` and calling `_withdraw`: [2](#0-1) 

`_withdraw()` releases each escrowed token via a plain `safeTransfer` with no check on the token's pausable state or the beneficiary's blacklist status: [3](#0-2) 

If the escrowed input token (e.g., USDC) is paused, or the solver/beneficiary address is blacklisted by the token (e.g., USDT), `IERC20(token).safeTransfer(beneficiary, amount)` reverts. Since this call is inside `onAccept`, the entire ISMP message delivery reverts and can never be finalized while the condition persists — there is no retry-with-different-outcome path, no alternate withdrawal queue, and no ability for the solver to reclaim the escrow through any other function once `_fillCrossChain` has already unconditionally delivered the output tokens on the destination chain.

This mirrors the reported bug class exactly: an irreversible action (burn / token delivery) is taken on one side, while the corresponding entitlement release on the other side is not defensively checked against external token pausing/blacklisting, so the release can permanently fail leaving the actor's tokens forever locked.

### Impact Explanation
A solver who fills a cross-chain order gives away output tokens on the destination chain unconditionally. If, at the time the settlement message is processed on the source chain, the escrowed input token is paused or the solver is blacklisted, `_withdraw()` will revert every single time it is invoked. Because there is no separate queued/retryable withdrawal mechanism (unlike a two-step request/accept pattern that could be corrected), the solver's escrowed input tokens become permanently stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract, with no code path to recover them — a Medium/High severity permanent freezing of user (solver) funds and an undeliverable ISMP message.

### Likelihood Explanation
USDC has been paused on-chain historically (e.g., during incidents) and USDT actively blacklists addresses; both tokens are explicitly in scope per the target ecosystem (referenced in the original report's chain list). A solver could unknowingly fill an order whose input token later becomes paused/blacklisted before the settlement message is relayed and processed — a realistic, permissionless scenario requiring no malicious actor, just ordinary external token-state changes between fill and settlement.

### Recommendation
Add defensive checks in `_withdraw()` (or in `_fillCrossChain`/`onAccept`) before attempting `safeTransfer`: verify the token is not paused (where introspectable) and/or wrap the transfer in a try/catch that, on failure, records the amount in a per-beneficiary claimable balance instead of reverting the whole withdrawal, allowing the beneficiary to retry the claim later once the token condition is resolved, rather than reverting the entire settlement message indefinitely.

### Proof of Concept
1. User places a cross-chain order escrowing USDC as input on chain A via `IntentGatewayV2`/`ExtrinsicIntents`.
2. Solver fills the order on chain B, delivering the required output tokens to the beneficiary immediately and irreversibly (`_fillCrossChain`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:186-212`), then dispatches `RedeemEscrow`.
3. Before the settlement message is delivered on chain A, Circle pauses USDC (or the solver's receiving address is blacklisted by USDT logic).
4. The relayer submits the proof; `onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`, which calls `IERC20(USDC).safeTransfer(solver, amount)` — this reverts because the token is paused.
5. Every subsequent delivery attempt of the same message reverts identically. The solver's escrowed input tokens remain locked in the gateway contract indefinitely, with the solver having already surrendered the output tokens on chain B.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
