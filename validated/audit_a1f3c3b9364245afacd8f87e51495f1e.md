### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant metadata spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook-id`, and `api-version` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values and hands them to the host app's webhook handler as verified metadata, even though they were never bound to the HMAC that `Utils::HmacValidator` checks.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `Request#topic`, `Request#webhook_id`, and `Request#api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`, i.e. against the body bytes only: [3](#0-2) 

`Webhooks::Registry.process` then relies on the already-passed HMAC check and forwards the *header*-derived `topic` and `shop` directly into `WebhookMetadata`, which is what the host application's handler consumes as the authenticated identity of the webhook sender: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified bytes == raw_body` but the trust decision downstream is made on `request.shop` / `request.topic`, fields that were never part of the bytes the HMAC covers. Equality that should hold — "the shop/topic bound by the signature" == "the shop/topic acted upon" — does not hold, mirroring the report's root cause pattern (`_splitValue` acting on `toIDs[i]` values that were never validated against the account/type they get written into).

Because Shopify apps share one `client_secret` across all shops that install the app, any body+HMAC pair valid for shop A's webhook delivery remains a valid HMAC for the *same body* when replayed with `shop-domain` (and/or `topic`) headers swapped to shop B or to a different topic. `Request.new` and `Registry.process` perform no check that the header values are consistent with anything inside the signed body, so the swapped headers pass validation and are delivered to the handler as if genuinely originating from shop B / topic B.

### Impact Explanation
A malicious app-installing merchant (an unprivileged, uncredentialed actor who never has `api_secret_key` — they only observe webhooks legitimately delivered to their own shop) can capture a valid `(raw_body, hmac)` pair from their own installation and resend it with a forged `shop-domain` header. If the host application's webhook handler keys any per-shop state, authorization, or session lookup off `WebhookMetadata#shop` (which is the gem's documented/intended usage), the attacker can inject data attributed to another tenant, achieving cross-tenant confusion in the host application's persisted state — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Medium: it requires the attacker to already possess one legitimately-delivered `(body, hmac)` pair (obtainable simply by installing the app on any shop they control) and requires the host app to trust `data.shop`/`data.topic` from `WebhookMetadata` without independently cross-checking it against the signed body — which is exactly the API surface this gem exposes and documents for handlers to use.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed payload), so that `Utils::HmacValidator.validate` fails if any of these header-derived fields are altered relative to what Shopify actually signed. Concretely, `Request#to_signable_string` should incorporate these header values, not just `@raw_body`.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; the gem's webhook endpoint receives a legitimate webhook with body `B`, headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256` computed over `B`.
2. Attacker (owner of `shop-a`) records `(B, hmac)`.
3. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and `hmac` unchanged, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, spoofing shop-b's identity in the host application even though shop-b never sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
