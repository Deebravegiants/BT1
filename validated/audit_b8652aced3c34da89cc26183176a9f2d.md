Audit Report

## Title
Unauthenticated LOOP plugin pprof/metrics proxy endpoints allow local disruption and information disclosure - (File: core/web/router.go)

## Summary
`loopRoutes(app, api)` is registered in `NewRouter` on the plain `api` group, which only carries rate-limiting and session-cookie middleware — no `auth.Authenticate` wrapper is applied. This exposes `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*`, and `/plugins/:name/debug/pprof/symbol` to any client able to reach the node's HTTP listener, in contrast to the core node's own `debugRoutes` (wrapped in `auth.Authenticate`) and `metricRoutes` (registered inside the authenticated `authv2` group).

## Finding Description
`NewRouter` builds the `api` group with only rate limiting and `sessions.Sessions(...)`, then calls `loopRoutes(app, api)` directly with no auth middleware: [1](#0-0) 

`loopRoutes` itself registers the four endpoints with no `auth.Authenticate` call anywhere in the function body: [2](#0-1) 

This is inconsistent with `debugRoutes`, which explicitly wraps `/debug/vars` in `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`: [3](#0-2) 

and with `metricRoutes`, which is called only inside the `authv2` group (itself gated by `auth.Authenticate(... auth.AuthenticateByToken, auth.AuthenticateBySession)`), with the comment "Debug routes accessible via authentication": [4](#0-3) [5](#0-4) 

The handlers backing the LOOP routes proxy directly to each plugin's internal pprof/metrics server without any authorization check, forwarding attacker-supplied query parameters (including `seconds` for `pprof/profile` and `/trace`) to the plugin's debug server: [6](#0-5) [7](#0-6) 

I confirmed there is no other auth wrapper applied to `api` before `loopRoutes` is registered — the group only has rate limiting and session middleware (which merely attaches a session store, it does not enforce that a valid session exists) [8](#0-7) . This confirms the claim's core assertion: the LOOP proxy routes are reachable without authentication, unlike the analogous core-node debug/metric routes.

## Impact Explanation
- **Information disclosure**: pprof heap/goroutine/trace dumps and the plugin's `/metrics` output are exposed to any unauthenticated caller who can reach the node's web listener and knows (or enumerates via `/discovery`) a plugin name.
- **Resource exhaustion / disruption**: `/plugins/:name/debug/pprof/*profile` accepts a `seconds` parameter forwarded to the plugin's internal pprof server, which can tie up the plugin's request-handling for extended windows (`PPROFOverheadSeconds` plus caller-controlled `seconds`), degrading or blocking legitimate operations for that LOOP plugin.
- This is real: it maps to an authentication/authorization gap on an operator-facing diagnostic surface, distinct from the general "pure DoS" exclusion — the finding is primarily an authentication-bypass issue (unauthenticated access to an endpoint deliberately gated for the equivalent core-node route), with DoS as a secondary consequence.

## Likelihood Explanation
Exploitation requires only network reachability to the node's configured web server port (default 6688) — no credentials, cookies, or API tokens are needed, since `sessions.Sessions(...)` only wires a cookie store and does not itself enforce authentication, and no `auth.Authenticate` middleware is present on the `loopRoutes` group or the individual routes. Plugin names can be enumerated via the same unauthenticated `/discovery` endpoint. This makes the attack trivially repeatable by any unprivileged network client, consistent with the "unprivileged actor" requirement, whenever the node runs LOOP plugins and its web server is reachable (even from an internal/adjacent network segment, which is a normal deployment topology, not a privileged-access precondition).

## Recommendation
Wrap `loopRoutes` registration with the same `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` (or token) middleware applied to `debugRoutes`, or move its registration into the authenticated `authv2`/session-gated group, so `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` all require a valid session/API token before proxying to plugin internals — consistent with the node's own `/debug/*` and `metricRoutes` treatment.

## Proof of Concept
Against a running node with a LOOP plugin registered (e.g., `median`), issue unauthenticated requests with no `Authorization` header or session cookie:
```
curl http://<node-host>:6688/discovery
curl http://<node-host>:6688/plugins/median/metrics
curl "http://<node-host>:6688/plugins/median/debug/pprof/profile?seconds=30"
```
All three succeed because `loopRoutes(app, api)` (core/web/router.go:91) is registered on the unauthenticated `api` group, unlike `metricRoutes(authv2)` (core/web/router.go:446), which requires a valid session/token. A Go integration test can construct the router via `NewRouter` with a mocked `chainlink.Application`/`LoopRegistry` containing a fake plugin, issue a `httptest` GET to `/plugins/<name>/metrics` and `/plugins/<name>/debug/pprof/heap` without setting any `Authorization`/cookie header, and assert a non-401/403 response is returned (confirming the missing auth gate), matching `core/web/loop_registry_test.go` patterns already present in the repo.

func (l *LoopRegistryServer) pluginMetricHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/metrics", l.loopHostName, p.EnvCfg.PrometheusPort)
	req, err := http.NewRequestWithContext(gc.Request.Context(), http.MethodGet, pluginURL, nil)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error creating plugin metrics request: %s", err))
		return
	}
	res, err := l.promClient.Do(req)
	if err != nil {
		msg := "plugin metric handler failed to get plugin url " + html.EscapeString(pluginURL)
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}
	defer res.Body.Close()
	b, err := io.ReadAll(res.Body)
	if err != nil {
		msg := fmt.Sprintf("error reading plugin %q metrics", html.EscapeString(pluginName))
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}

	gc.Data(http.StatusOK, "text/plain", b)
}

const PPROFOverheadSeconds = 30

func pprofURLVals(gc *gin.Context) (urlVals url.Values, timeout time.Duration) {
	urlVals = make(url.Values)
	if db, ok := gc.GetQuery("debug"); ok {
		urlVals.Set("debug", db)
	}
	if gc, ok := gc.GetQuery("gc"); ok {
		urlVals.Set("gc", gc)
	}
	timeout = PPROFOverheadSeconds * time.Second
	if sec, ok := gc.GetQuery("seconds"); ok {
		urlVals.Set("seconds", sec)
		if i, err := strconv.Atoi(sec); err == nil {
			timeout = time.Duration(i+PPROFOverheadSeconds) * time.Second
		}
	}
	return urlVals, timeout
}

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
