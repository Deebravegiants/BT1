### Title
Program deployment permanently blocked via ProgramData PDA pre-funding griefing - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The external report describes a `WeightedIndex` constructor that deterministically creates a pool at a predictable address; an attacker front-runs pool creation so the address is already in use, causing the legitimate `createV2Pool` call to permanently revert. The Agave analog is the Loader v3 (`bpf_loader_upgradeable`) `DeployWithMaxDataLen` instruction handler, which derives a deterministic ProgramData PDA from the program id and then calls the strict `system_instruction::create_account`, which reverts if the destination already has any lamports.

### Finding Description
`DeployWithMaxDataLen` derives the ProgramData address deterministically as a PDA from `program_id` via `Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)` [1](#0-0) . It then invokes the plain `system_instruction::create_account` via `native_invoke_signed` to fund and initialize that PDA as the ProgramData account [2](#0-1) .

The system program's `create_account` handler explicitly rejects any destination that already has nonzero lamports:
```
if to.get_lamports() > 0 {
    ...
    return Err(SystemError::AccountAlreadyInUse.into());
}
``` [3](#0-2) 

Because the ProgramData address is a deterministic function of the (attacker-visible or predictable) `program_id`, any unprivileged party can send a trivial System `Transfer` of lamports to that PDA before the deploy transaction lands (e.g., after observing the pending deploy transaction in the mempool/gossip, or after learning the intended program keypair). Once the PDA holds any lamports, the internal `create_account` CPI inside `DeployWithMaxDataLen` unconditionally fails with `SystemError::AccountAlreadyInUse`, aborting the whole deploy transaction.

Unlike ordinary account creation where a user can simply pick a different address and retry, the ProgramData address here is not chosen by the deployer — it is a fixed PDA tied 1:1 to the program id. There is no way to "just use a different account"; the specific `program_id` becomes permanently undeployable via `DeployWithMaxDataLen` unless the caller withdraws lamports from an address it does not control (impossible, since it's a PDA owned/controlled by the loader program logic, not by the attacker or the deployer).

Notably, Agave already recognizes and mitigates this exact bug class elsewhere: the system program added `CreateAccountAllowPrefund`/`create_account_allow_prefund`, which skips the zero-lamport check specifically to tolerate pre-funded destinations [4](#0-3) , and the Core BPF migration path (`TargetBpfV2::new_checked`, `TargetBuiltin::new_checked`) explicitly supports an `allow_prefunded` mode for the analogous ProgramData PDA [5](#0-4) . However, the user-facing `DeployWithMaxDataLen` instruction in `bpf_loader/src/lib.rs` still constructs the strict, non-prefund-tolerant `system_instruction::create_account` [6](#0-5) , leaving ordinary program deployers exposed to the griefing pattern that the report describes for `WeightedIndex`.

### Impact Explanation
An unprivileged attacker can permanently deny a specific program id from ever being deployed via `DeployWithMaxDataLen` by pre-funding its ProgramData PDA with a negligible amount of lamports before the legitimate deploy transaction is confirmed. This is a denial-of-service against program deployment infrastructure/tooling (e.g., deterministic deploys, CI/CD pipelines using known program keypairs, or any workflow where the program id is predictable ahead of the deploy transaction landing). It does not cause loss of user funds directly, but it can permanently block deployment for that specific program id, forcing the deployer to generate an entirely new program id/keypair.

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation requires the attacker to learn the intended `program_id` before the `DeployWithMaxDataLen` transaction is committed (e.g., by observing the transaction in the network prior to confirmation, or knowing the deployer's program keypair in advance) and to win the race by landing a `Transfer` to the PDA first. This is analogous in structure and severity/likelihood profile to the referenced Solidity finding (front-running a deterministic address to block a one-time initialization).

### Recommendation
Update the `DeployWithMaxDataLen` (and equivalent) instruction path in `programs/bpf_loader/src/lib.rs` to use the prefund-tolerant creation logic (`SystemInstruction::CreateAccountAllowPrefund` / `create_account_allow_prefund`) for the ProgramData PDA, mirroring the mitigation already applied in the Core BPF migration code path (`allow_prefunded`), so that a griefer pre-funding the deterministic PDA cannot block legitimate deployment.

### Proof of Concept
1. Attacker observes (or otherwise learns) the `program_id` that a deployer intends to use with `DeployWithMaxDataLen` before the deploy transaction is confirmed on-chain.
2. Attacker computes the deterministic ProgramData PDA: `Pubkey::find_program_address(&[program_id.as_ref()], &bpf_loader_upgradeable::id())` (same derivation as `programs/bpf_loader/src/lib.rs:280-281`).
3. Attacker submits (and gets confirmed) a plain System `Transfer` sending 1 lamport to that PDA.
4. When the legitimate `DeployWithMaxDataLen` transaction lands, its internal CPI to `system_instruction::create_account` for the ProgramData account fails with `SystemError::AccountAlreadyInUse` because `to.get_lamports() > 0` (`programs/system/src/system_processor.rs:161-171`), causing the entire deploy transaction to fail.
5. Since the ProgramData address is fixed for that `program_id`, the deployer has no way to retry successfully with the same program id via this instruction path.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
