This confirms the finding. In `lib/shopify_api/auth/oauth/auth_query.rb`, the OAuth callback's `to_signable_string` includes `shop`, `host`, `code`, `state`, `timestamp` in the signed bytes [1](#0-0) , but in `lib/shopify_api/webhooks/request.rb`, `to_signable_string` returns only `@raw_body`, excluding `shop`, `topic`, `webhook_id`, and `api_version` from the HMAC-covered bytes [2](#0-1) . Yet `Registry.process` uses `request.shop` (an unauthenticated header) to construct the tenant-identifying `WebhookMetadata` dispatched to the handler [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook signature verification only authenticates the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any party who can obtain one valid `(body, hmac)` pair signed with the app's `client_secret` for any shop's webhook can replay that same body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will treat the payload as authentic and originating from the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value using `OpenSSL.secure_compare`: [4](#0-3) 

Because `to_signable_string` for webhooks is body-only, the `shop`, `topic`, `webhook_id`, and `api_version` accessors — all parsed straight from HTTP headers — are never part of the signed bytes: [5](#0-4) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`, `request.webhook_id`) directly to build the metadata handed to the app's handler, without any cross-check that this shop is the one that actually owns the signed body: [3](#0-2) 

This breaks the intended identity binding: `hmac == HMAC(client_secret, bytes verified)` should equal `hmac == HMAC(client_secret, bytes acted on)`, but the bytes acted on for tenant routing (`shop` header) are disjoint from the bytes verified (`raw_body` only). By contrast, the OAuth callback path in this same gem correctly folds `shop` into the signed string precisely to prevent this class of confusion: [1](#0-0)  — the webhook path does not follow the same pattern.

In practice this is Shopify's own webhook signature design (HMAC over body only), so real-world exploitability depends on an attacker being able to source a valid `(body, hmac)` pair not intended for the shop they assert — e.g., a merchant with two shops on the same app, or a shop that receives its own webhook and replays it with a different `shop-domain` header value toward the app's endpoint. The library itself performs no verification tying the `shop` header to the entity that was actually signed, so any host application that relies solely on `Registry.process`/`request.shop` for tenant scoping inherits this gap.

### Impact Explanation
If an app's webhook handler uses `WebhookMetadata#shop` to select which merchant's data/session to operate on (a common and encouraged pattern for multi-tenant apps), an attacker who can produce or capture one valid body+HMAC pair can cause the app to process that payload under a different, attacker-chosen shop identity — a cross-tenant data confusion inside the app's webhook processing pipeline, which the gem is supposed to guarantee integrity for via `HmacValidator.validate`.

### Likelihood Explanation
Exploitability requires the attacker to control or observe at least one legitimately-signed webhook body (e.g., operate their own shop with the same app installed, or intercept/replay a webhook to the public endpoint), then resend it with a modified `shop-domain` header. This is plausible for a merchant/attacker who already has the app installed on one shop and wants to impersonate another tenant.

### Recommendation
Include `shop`, `topic`, and any other routing-relevant fields in the signed/verified content for webhooks — or, at minimum, document and enforce that `Registry.process` callers must independently corroborate `request.shop` against a shop known to be entitled to the webhook (e.g., verify shop is an installed/active session before trusting `WebhookMetadata#shop`) rather than trusting the raw header once body-HMAC succeeds.

### Proof of Concept
1. App A shop `victim-a.myshopify.com` has the app installed; Shopify sends a webhook with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: victim-a.myshopify.com`.
2. Attacker, who also operates `attacker-shop.myshopify.com` with the same app installed, or who intercepts webhook traffic to the app's public endpoint, resends the identical body `B` and identical HMAC header value, but sets `X-Shopify-Shop-Domain: victim-a.myshopify.com` while actually wanting the app to attribute events under a shop the attacker controls (or vice versa: replays their own captured `(body, hmac)` for their shop but relabels it as another tenant).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)`; since the body/HMAC pair is genuinely valid, validation passes regardless of the `shop` header value: [6](#0-5) 
4. The handler receives `WebhookMetadata` populated with the attacker-controlled `shop` value, causing the app to act on the wrong tenant's behalf.
