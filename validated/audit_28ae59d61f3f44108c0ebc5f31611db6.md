### Title
Webhook HMAC Signature Does Not Cover `shop`, `topic`, or `webhook_id` Headers, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the webhook HMAC exclusively to the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight to the registered handler as trusted identity fields. This breaks the binding: `hmac == HMAC(body)` but `shop`/`topic` used by the handler are never part of what the signature covers.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [2](#0-1) 

For webhook requests, `to_signable_string` returns only the raw body — it does **not** include `shop`, `topic`, or `webhook_id`: [3](#0-2) 

Yet `Registry.process` uses `request.topic` to select the handler and forwards `request.shop`, `request.webhook_id`, `request.api_version` straight into `WebhookMetadata` as trusted, verified attributes of the event: [1](#0-0) 

This is the same class of bug as the Connext relayer issue: the cryptographic check (the router signature / here, the HMAC) covers a payload that is narrower than what the consuming code treats as authenticated. The router-set was verified but not bound to the specific transfer semantics the reconciler cared about; here the HMAC verifies the body bytes but not the `shop`/`topic` bytes that the handler dispatch and business logic treat as authoritative.

The `api_secret_key` used to sign webhooks is a single, app-wide secret (not per-shop), so any merchant who installs the app receives a legitimately-signed `(body, hmac)` pair. That merchant is an "unprivileged" party with respect to every *other* tenant of the app. Because the signature never binds `shop`, that same `(body, hmac)` pair remains valid when replayed directly against the app's webhook endpoint with an arbitrary `shopify-shop-domain` header (and/or `shopify-topic` header, for topics with attacker-predictable/controlled bodies).

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`: an attacker who is a legitimate installer of the app for their own store can capture one valid `(body, hmac)` pair and replay it with a forged `shop-domain` (and/or `topic`) header pointed at a victim shop. Since `Registry.process` trusts `request.shop`/`request.topic` unconditionally once the body's HMAC checks out, the app's handler will execute business logic attributing the event to the victim shop (e.g. updating records keyed by `WebhookMetadata#shop`), or dispatch the payload to a handler for a topic it was never actually signed for. This matches the Critical/High "cross-tenant access" category called out in the rules.

### Likelihood Explanation
Requires only: (1) being able to install the target app on any shop the attacker controls (a normal, unprivileged action), (2) capturing at least one legitimately delivered webhook `(raw_body, hmac)` pair for that install, and (3) sending a raw HTTP POST directly to the app's public webhook endpoint with forged Shopify headers. No access token, `client_secret`, or TLS interception is required — only knowledge of the gem's own header-parsing/signature-scope behavior, which is fixed and predictable from `lib/shopify_api/webhooks/request.rb`.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify Shopify's documented HMAC scheme strictly as designed — over body only — but additionally require that requests arrive over a channel/IP allowlist Shopify publishes, and/or have the host application independently confirm `shop` against a known, currently-installed session before trusting `WebhookMetadata#shop`). At minimum, document loudly that `WebhookMetadata#shop`/`#topic` are unauthenticated relative to the HMAC and must not be trusted as tenant-identifying without additional verification (e.g., cross-checking against an active session for that shop).

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: forged_headers)

#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/create", ...))

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
