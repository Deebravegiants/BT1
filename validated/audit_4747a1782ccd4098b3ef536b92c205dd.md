### Title
Webhook shop-domain identity is not covered by HMAC verification, allowing shop-header spoofing on otherwise-valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body via HMAC, while the shop identity (`shop-domain` header), topic, webhook id, and API version are read from unauthenticated headers and passed straight through to the app's `WebhookHandler` as trusted `WebhookMetadata`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, never the headers: [1](#0-0) 
`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header: [2](#0-1) 
`Registry.process` only checks this body-only HMAC before dispatching to the handler, and then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id`, all of which come from headers: [3](#0-2) 
`Request#shop` is a pure header read with no cross-check against the HMAC-covered body: [4](#0-3) 

The identity binding that should hold is: `shop-domain header used by the app == shop-domain authenticated by the HMAC`. In this implementation that equality does not hold — the HMAC only authenticates the byte content of the body, not the shop-domain (or topic/webhook-id) header that the host application receives as "verified" `WebhookMetadata.shop`. Any request whose body produces a valid HMAC (e.g., a legitimately-received webhook body for a shop the attacker controls) can be re-delivered to the app's webhook endpoint with an arbitrary `shop-domain` header, and `Registry.process` will accept it as valid and hand off `WebhookMetadata` claiming that arbitrary shop, because the gem never verifies that the header-derived shop is bound to the signed payload.

### Impact Explanation
Applications built on this gem are expected to trust `WebhookMetadata.shop` as the authenticated identity of the merchant that sent the webhook, since `Registry.process` gates delivery on `Utils::HmacValidator.validate`. Because the shop header is outside the HMAC's protection, an attacker who legitimately owns/operates one Shopify shop (and can therefore obtain valid, HMAC-signed webhook bodies for events on that shop) can replay that exact body with a forged `shop-domain` header naming a victim shop. If the host application uses `WebhookMetadata.shop` to select which tenant's data/session to act on (a common and documented pattern, since the gem provides no other authenticated shop signal), this results in cross-tenant data injection under an attacker-chosen shop identity — data appears to originate from, and gets attributed to, a shop that never sent it.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request to the app's public webhook endpoint with a valid Shopify HMAC for some body — attainable by any merchant/developer able to register a webhook for their own store (a normal, unprivileged Shopify merchant capability) and to capture that store's own webhook deliveries. No access token, `client_secret`, or privileged account is needed; only the app's public webhook receiver endpoint. No credential or TLS interception is required.

### Recommendation
Bind the shop identity to the authenticated payload: include the `shop-domain` (and ideally `topic`/`webhook_id`) header value in the signable string used for HMAC computation/verification (or otherwise cryptographically bind them), so that a body with a valid signature cannot be replayed under a different shop identity. At minimum, document clearly that `WebhookMetadata.shop`/`topic`/`webhook_id` are unauthenticated header values and must not be trusted as tenant identity without additional application-level verification.

### Proof of Concept
1. Attacker registers a webhook (e.g., `orders/create`) pointing at the target app, using their own shop `attacker-shop.myshopify.com`.
2. Attacker triggers the event and captures the resulting webhook request: `raw_body` plus the valid `x-shopify-hmac-sha256` header computed by Shopify over that body with the app's `client_secret` (attacker never needs to know the secret — Shopify computes it). [5](#0-4) 
3. Attacker re-sends this exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`. [4](#0-3) 
4. `Registry.process` validates the HMAC successfully (it never inspects `shop`), then invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and the attacker's own event body. [6](#0-5) 
5. Any app logic keyed on `WebhookMetadata.shop` (e.g., "create/update record for this shop") now operates on the victim shop's tenant using attacker-controlled data.
