### Title
`placeOrder` deducts a protocol fee with no caller-side maximum-fee bound - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` computes and deducts a protocol fee from the user's escrowed input tokens using a `protocolFeeBps` value that is read from mutable storage at execution time, with no field in `Order` or `placeOrder` letting the caller cap the fee they are willing to pay. Exactly like the `PanopticPool._forceExercise()` finding — where `exerciseFees` is computed at execution time from mutable oracle/tick state with no caller-side max-fee bound — a user here signs/submits a transaction expecting one fee rate, but the actual bps applied can differ by the time the transaction lands, and there is no on-chain mechanism to cap or reject an unfavorable value.

### Finding Description
In `placeOrder()`, the effective protocol fee rate is resolved per-destination and then applied unconditionally: [1](#0-0) 

`protocolFeeBps` is taken from `_destinationProtocolFees[destinationHash]` (falling back to the global `_params.protocolFeeBps`), both of which are ordinary mutable storage slots updated by the `UpdateParams` cross-chain message handler: [2](#0-1) 

This handler can change `_params.protocolFeeBps` or add/update a `_destinationProtocolFees[stateMachineId]` entry for any destination at any time, driven by a governance message dispatched from Hyperbridge. Once such an update lands in a block before a pending `placeOrder` transaction, the fee actually charged to the user diverges from whatever rate the user observed when constructing and signing their order — the `Order` struct and `placeOrder()` provide no `maxProtocolFeeBps` (or equivalent) parameter for the caller to bound or reject an unfavorable fee, unlike the `validUntil` bound that was later added to `FillOptions` for solver quotes: [3](#0-2) 

The absence of any equivalent guard on `placeOrder()`'s fee deduction means a user's escrowed principal (`reducedAmount = originalAmount - protocolFee`) can be silently reduced by more than expected, with the discrepancy only visible after the order is committed and inputs are already escrowed.

### Impact Explanation
A user placing an order has no way to guarantee the protocol fee bps in effect at inclusion time matches what they intended when signing. If a per-destination fee override is added or the global `protocolFeeBps` is raised between transaction construction and inclusion, the user's escrowed input is reduced more than expected and the difference is retained by the protocol as "dust" (`DustCollected`), effectively an unbacked value loss for the order placer with no recourse — the commitment is already computed from the reduced amount, so the order proceeds at the new, unexpected rate rather than reverting.

### Likelihood Explanation
`protocolFeeBps` and `_destinationProtocolFees` are ordinary configuration values updated through the normal `UpdateParams` governance flow (not an attacker-controlled path), but such updates are a routine, expected operational action (e.g., adjusting fees per destination) rather than a rare event. Any user's in-flight `placeOrder` transaction sitting in the mempool during such an update is exposed, and because `placeOrder` is fully permissionless and reachable by any unprivileged caller in a single transaction, likelihood of at least occasional user impact is realistic whenever fee parameters are adjusted.

### Recommendation
Add a caller-supplied bound to `placeOrder` (e.g., `maxProtocolFeeBps` or `minInputAmountAfterFee`) and revert if the fee resolved at execution time exceeds/violates it, mirroring the pattern later adopted for `FillOptions.validUntil` to bound solver-side price risk. This lets users protect themselves from unexpected fee changes between signing and inclusion.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs[0].amount = 1000 USDC`, having observed `protocolFeeBps = 0` (or some known low value) for the destination.
2. Before the transaction is included, a `ParamsUpdate` cross-chain message from Hyperbridge sets `_destinationProtocolFees[destinationHash]` to, e.g., `500` (5%).
3. The user's transaction is then included: `placeOrder` at [4](#0-3)  reads the new `protocolFeeBps`, computes `protocolFee = 50 USDC`, and escrows only `950 USDC` for the order — 50 USDC more than the user expected is retained as protocol dust, with no revert or bound to protect the user.
