### Title
`PoaBridge.describeWithdrawal` misreports status/txHash for same-`assetId` batched withdrawals via index-agnostic `findMatchingWithdrawal` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`findMatchingWithdrawal` in `poa-bridge.ts` matches a POA API withdrawal record solely by `assetId` (derived from `near_token_id`), ignoring `WithdrawalIdentifier.index` and `destinationAddress`. When a batch contains two withdrawals of the same asset (e.g. two `nep141:btc.omft.near` withdrawals with different `destinationAddress`), `describeWithdrawal` for either index returns `Array.prototype.find`'s first match, so the status/txHash reported for index 1 can actually belong to index 0's on-chain outcome (or vice versa).

### Finding Description
The claimed equality is: for each withdrawal `i` in a batch, `describeWithdrawal(index=i)` must report `(status, txHash)` equal to the actual on-chain outcome of withdrawal `i`'s payout to its own `destinationAddress`.

Code path: `describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry` to fetch all withdrawals for the shared NEAR tx hash, then calls: [1](#0-0) 

`findMatchingWithdrawal` only matches on `nep141:${w.data.near_token_id} === assetId`: [2](#0-1) 

This is explicitly documented as a known limitation in the code comment: "multiple withdrawals of the same token in a single transaction are not supported." [3](#0-2) 

Because `Array.prototype.find` returns the first array element matching `assetId` — regardless of `args.index` or `args.withdrawalParams.destinationAddress` — both `describeWithdrawal({index:0, assetId:X})` and `describeWithdrawal({index:1, assetId:X})` resolve to the same underlying POA record. If withdrawal 0 completed successfully and withdrawal 1 (to a different `destinationAddress`) actually failed, both index-0 and index-1 status queries return the COMPLETED record's `transfer_tx_hash`, so index 1 is falsely reported "completed" with a txHash that belongs to a different destination address's payout.

The same defect exists independently in the internal-utils' `waitForWithdrawalCompletion.ts::findMatchingWithdrawal`, which matches purely by `assetId` criteria without index/destination disambiguation, confirming this is a systemic, intentional (documented) limitation, not an isolated bug: [4](#0-3) 

There is no `destinationAddress` comparison, `compareAddresses` call, or index-based disambiguation anywhere in this matching logic to prevent the divergence — the code comment itself acknowledges the API/SDK do not currently support this case and proposes a future amount-based sort-matching fix that has not been implemented.

### Impact Explanation
For batches with duplicate `assetId` routed to `PoaBridge`, an integrator using `IntentsSDK.signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion`/`withdrawal-watcher` polling per-`WithdrawalIdentifier.index` can receive a `completed` status with a `txHash` for the wrong withdrawal index. This can cause the integrator to credit/refund the user for a withdrawal that never landed at the specified `destinationAddress` (double-credit or crediting the wrong destination), while the failed withdrawal for a different destination is left improperly resolved. This matches the High/Critical category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Preconditions: the caller only needs to submit a batch of ≥2 `WithdrawalParams` with the same `assetId` (same token) both routed to `PoaBridge`, differing only in `destinationAddress`/amount. This is fully within an "ordinary NEAR Intents user with their own funds" scope — no privileged access or contract exploit required, just constructing a normal-looking batch withdrawal request. The bug is deterministic and repeatable every time the POA API returns multiple withdrawal records with the same `near_token_id` for one NEAR tx hash, which is a mainline supported use case (batch withdrawals through one intents transaction) that the code path does not correctly disambiguate.

### Recommendation
Update `findMatchingWithdrawal` in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` to disambiguate among multiple same-`assetId` withdrawals — e.g., additionally match on `destinationAddress`/`amount`, or implement the amount-sorted correlation strategy mentioned in the existing code comment, before allowing `PoaBridge` withdrawals to be batched with duplicate `assetId`. Alternatively, until POA API support lands, explicitly reject/serialize batches containing duplicate `assetId` entries routed through `PoaBridge` at the SDK layer (e.g., in `signAndSendWithdrawalIntent`) rather than silently returning an ambiguous match.

// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts
it("misreports status for index 1 when two withdrawals share assetId with different destinations", async () => {
  vi.mocked(poaBridge.httpClient.getWithdrawalStatus).mockResolvedValue({
    withdrawals: [
      {
        status: "COMPLETED",
        data: {
          tx_hash: "near-tx-hash",
          transfer_tx_hash: "btc-tx-hash-completed",
          chain: "btc",
          defuse_asset_identifier: "nep141:btc.omft.near",
          near_token_id: "btc.omft.near",
          decimals: 8,
          amount: 100000,
          account_id: "test.near",
          address: "ADDRESS_A", // destination for withdrawal index 0
          created: "2024-01-01T00:00:00Z",
        },
      },
      // withdrawal index 1 to ADDRESS_B actually FAILED on-chain but is
      // absent/not represented distinctly because API only returns one
      // record per near_token_id in this mock, simulating ambiguous match
    ],
  });

  const bridge = new PoaBridge({
    envConfig: configsByEnvironment.production,
    xrplRpcUrls: configureXrplRpcUrls(PUBLIC_XRPL_RPC_URLS, {}),
  });

  const resultIndex0 = await bridge.describeWithdrawal({
    landingChain: Chains.Bitcoin,
    index: 0,
    withdrawalParams: {
      assetId: "nep141:btc.omft.near",
      amount: 100000n,
      destinationAddress: "ADDRESS_A",
      feeInclusive: false,
    },
    tx: { hash: "near-tx-hash", accountId: "test.near" },
  });

  const resultIndex1 = await bridge.describeWithdrawal({
    landingChain: Chains.Bitcoin,
    index: 1,
    withdrawalParams: {
      assetId: "nep141:btc.omft.near",
      amount: 50000n,
      destinationAddress: "ADDRESS_B", // different destination, actually failed on-chain
      feeInclusive: false,
    },
    tx: { hash: "near-tx-hash", accountId: "test.near" },
  });

  // BUG: both indices report the SAME completed status/txHash even though
  // index 1's on-chain payout to ADDRESS_B never happened.
  expect(resultIndex0).toEqual({ status: "completed", txHash: "btc-tx-hash-completed" });
  expect(resultIndex1).toEqual({ status: "completed", txHash: "btc-tx-hash-completed" }); // WRONG: should reflect FAILED for index 1
});
```
This demonstrates that `describeWithdrawal(index=1)`'s reported `(status, txHash)` does not equal withdrawal 1's real on-chain outcome, breaking the STATUS TRUTH invariant.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
