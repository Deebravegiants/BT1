### Title
Webhook shop identity is trusted from an unauthenticated header rather than the HMAC-covered payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (the tenant identifier ultimately passed to the app's `WebhookHandler`) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` verifies only covers the raw request body. An attacker who can influence the header value independently of the body (e.g. via a proxy, a misconfigured/duplicated header, or any component in front of the app that forwards attacker-controlled headers) can present a valid HMAC for a legitimately-received body from Shop A while making the library report `shop` as Shop B, or vice versa, causing cross-tenant confusion in the handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC over `request` (i.e., over `raw_body` only via `HmacValidator.validate` → `to_signable_string`), and, once that check passes, unconditionally trusts `request.shop` and forwards it to the app's handler as the tenant identity in `WebhookMetadata`: [4](#0-3) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`: [5](#0-4) 

This is the exact analog called out by the rules: "a field acted on but not covered by the HMAC." The identity binding that should hold is:
`hmac == HMAC(body ‖ shop)` should imply `request.shop` is authentic for that body.
In this gem, the actual binding is only `hmac == HMAC(body)`; `shop` is parsed from headers with no cryptographic tie to the signed bytes. Anything positioned to alter headers independently of the body (e.g., a shared/misconfigured reverse proxy in the host application's infrastructure, or a duplicate `X-Shopify-*` header where the app's HTTP layer picks an attacker-supplied one over Shopify's) can make a validly-signed body be attributed to a different shop than the one that actually sent it. Note this compares favorably to Shopify's own OAuth flow in the same library, `Auth::Oauth::AuthQuery`, where `shop` *is* included in `to_signable_string` and thus is HMAC-bound: [6](#0-5) 
The webhook path does not follow the same pattern.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as returned unmodified by this gem) to select which merchant's data store/session to act on, an attacker able to desynchronize the header from the body can cause cross-tenant data processing — e.g., a webhook payload legitimately signed by Shop A being processed as belonging to Shop B, or triggering `shop/redact`, `customers/redact`, `customers/data_request` handling against the wrong tenant. This matches the in-scope "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability is limited to unprivileged-internet-user reach through this gem's own logic only if there's a network element between Shopify and the app that lets an outside party inject or duplicate the `X-Shopify-Shop-Domain` header without invalidating the HMAC (the HMAC never covers it, so injection is silent). This is plausible in common deployments (load balancers/CDNs that don't strip inbound `X-Shopify-*` headers before appending Shopify's own, Rack header-array coalescing, etc.), but it does require such an environmental condition rather than being exploitable purely by talking to the app directly with no intermediary. The root cause inside the gem, however, is unambiguous: the gem itself never binds `shop` to the signature.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable representation (or otherwise validate that the header-derived `shop` matches an app-known value) so `HmacValidator.validate` cryptographically binds the tenant identity to the signed payload, not just the raw body.

### Proof of Concept
1. A reverse proxy or intermediary in front of the app (not Shopify itself) receives Shopify's genuine webhook POST for `shop-a.myshopify.com` with a valid `X-Shopify-Hmac-Sha256` over the raw body.
2. The intermediary (due to misconfiguration, or an attacker who can reach the app directly and set/duplicate headers while replaying/forwarding a previously observed valid `(body, hmac)` pair for a different shop) sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` while keeping the original body and HMAC header untouched.
3. `Request.new` parses `shop` from the header as `shop-b.myshopify.com`, and `to_signable_string` still returns the original `@raw_body`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since the HMAC only covers `@raw_body`, it validates successfully.
5. `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...)` is delivered to the app's handler, causing shop-b's session/tenant context to be used for data that was actually signed for shop-a.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
