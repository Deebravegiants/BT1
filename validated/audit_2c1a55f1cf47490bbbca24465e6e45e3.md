### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating the HMAC over the raw request body, but the `shop` value that is handed to the application's webhook handler is read from an unauthenticated header. Because Shopify's `X-Shopify-Hmac-Sha256` signature covers only the request body and never the `X-Shopify-Shop-Domain` header, the binding `hmac_signed_bytes == bytes_the_gem_trusts_for_tenant_identity` does not hold. An attacker who can obtain any single valid `(body, hmac)` pair for the app (trivially, by installing the app on their own store and capturing one of their own legitimate webhook deliveries) can replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. The signature still validates, and the forged shop value is passed straight through to the application as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `Request#shop` is read independently from the `shop-domain` header, outside of what's signed: [2](#0-1) 

`Registry.process` validates only this body-based HMAC and then immediately forwards `request.shop` to the registered handler as authenticated tenant context, without any additional binding check between the shop and the signed bytes: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the signature purely from `verifiable_query.to_signable_string` (the body) and compare against the `hmac` field — the shop is never part of the signed material: [4](#0-3) 

This reproduces the report's bug class ("a field acted on but not covered by the HMAC"): the identity equality that should hold is `shop_used_by_handler == shop_that_the_hmac_actually_authenticates`, but since the HMAC authenticates only the body, any header-level `shop` value is accepted as if it were authenticated.

### Impact Explanation
Because `WebhookMetadata.shop` is typically used by host applications as the tenant key to scope webhook side effects (e.g., updating/deleting records, marking an app as uninstalled, applying GDPR redaction, syncing orders) for that shop, an attacker able to produce one valid `(body, hmac)` pair — which requires nothing more than owning/controlling a development store where the app is installed — can forge a webhook that is processed as if it originated from an arbitrary victim shop. This is a cross-tenant integrity/access issue: attacker-chosen webhook content (crafted on their own store) gets attributed to and acted upon for a victim's tenant data.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it directly), so no privileged access is required to reach it. Obtaining a genuine `(body, hmac)` pair only requires installing the app on an attacker-owned/free development store, which is available to any unprivileged internet user with a Shopify partner account. Swapping the `shop-domain` header while replaying the identical body/hmac bytes is trivial.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include the `shop-domain` (and ideally `webhook-id`/`topic`) header value in the signable string used for HMAC verification, or independently cross-check the `shop` header against a shop known/authorized for this app installation (e.g., verify a session/installation record exists for that shop) before trusting `request.shop` in `Registry.process`. At minimum, document that host applications must not treat the header-derived `shop` as authenticated by the HMAC and must independently verify shop ownership.

### Proof of Concept
1. Install the target app on an attacker-controlled store `evil-shop.myshopify.com`.
2. Trigger any webhook topic subscribed by the app (e.g. `orders/create`) so Shopify sends a legitimately signed request: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`), and `X-Shopify-Shop-Domain: evil-shop.myshopify.com`.
3. Capture `B` and `H`.
4. Replay an HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes: [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though the request never actually originated from Shopify for that shop.

          received_signature = verifiable_query.hmac
