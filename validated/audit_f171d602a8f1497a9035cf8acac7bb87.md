### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `WebhookMetadata` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to build the `WebhookMetadata` handed to the app's business logic. Because the app's `api_secret_key` is a single, app-wide secret shared across every merchant/shop that installs the app (not a per-shop secret), a valid HMAC only proves "this body was signed by our app's secret" — it proves nothing about which shop the body belongs to. An attacker who controls one installed shop can capture a legitimate, validly-signed webhook delivery for their own store and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header swapped to a victim shop, and the HMAC check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor reads a separate, unsigned header: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC using only `verifiable_query.to_signable_string` (i.e., the body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then immediately forwards `request.shop` — unvalidated and untied to the HMAC — into the handler: [4](#0-3) 

The identity binding that is broken is: `HMAC(body, api_secret_key) valid` is treated as equivalent to `shop header == originating shop`, when in fact `api_secret_key` is identical across all shops the app serves, so the HMAC only binds the body to "some webhook from this app," not to a specific shop. The `shop` field is a field acted on (used to route/attribute the webhook to a tenant) but not covered by the HMAC.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` from the handler (e.g., `lib/shopify_api/webhooks/webhook_handler.rb`) to decide which merchant's record to update, delete, or redact (this is the documented, intended usage pattern) is exposed to cross-tenant data corruption: an attacker who is a legitimate merchant of the app can forge webhook deliveries that the library reports as belonging to a different, victim shop, while still passing signature validation. This satisfies the "cross-tenant access" impact criterion, since data intended for shop A can be attributed to and processed against shop B purely by header manipulation, without needing shop B's or the app's actual secrets.

### Likelihood Explanation
Any party who can install the app on their own shop (a low bar for public/embedded Shopify apps) automatically receives correctly HMAC-signed webhook payloads from Shopify for topics they control (e.g., `orders/create`, `app/uninstalled`, `customers/redact`), and can immediately replay those bodies to the app's public webhook endpoint with an arbitrary `shop-domain` header — no interception of another shop's traffic or knowledge of `api_secret_key` is required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) in the signable string used for HMAC validation is not possible since Shopify itself does not sign these headers, so the correct mitigation is for `Registry.process`/`WebhookMetadata` (or documentation) to require verifying `request.shop` against the set of shops that have valid, currently-installed sessions for this app (i.e., cross-check with the app's session store) before trusting it, rather than treating a passing body HMAC as proof of the shop identity in the header. At minimum, `lib/shopify_api/webhooks/request.rb`/`registry.rb` should clearly document that `shop` is unauthenticated and must be independently verified by the consuming app.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and legitimately receives a Shopify webhook, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B`, same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present) — `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `B` using the app's shared `api_secret_key` — `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:13-22`.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` — `lib/shopify_api/webhooks/registry.rb:198-199` — causing the app to process attacker-controlled webhook content as if it originated from the victim shop.
