## Finding

Underflow-driven DoS in `Bonding.canGraduate` — analogous to the `freeCollateralBalance()` underflow

### Summary

`Bonding.canGraduate()` computes the USD graduation trigger as `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` without any guard against the subtrahend exceeding the minuend [1](#0-0) . This mirrors the reported bug class exactly: an unguarded subtraction used to compute an "available" value, reachable by ordinary user transactions, that can underflow and permanently DoS the contract's core trading path.

### Finding Description

`canGraduate` is invoked on **every** `buy` (per the natspec, "checked at the end of every buy inside `_executeBuy`") and explicitly on every `sell` [2](#0-1) . Its USD leg subtracts the launch-time virtual LT reserve from the pair's *stored* `assetReserve`:

```solidity
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [3](#0-2) 

This is the exact same pattern as `IUbiquityPool.freeCollateralBalance()`'s `balanceOf(this) - unclaimedPoolCollateral` — a raw subtraction of two independently-evolving state values with no bound enforced between them at the point of the read.

Elsewhere in the same contract, the maintainers *did* recognize this exact hazard and added an explicit guard. `previewLtUntilGraduation` (added specifically to fix a prior donation-driven underflow, per the "Donation attack regression" tests) checks `if (realBalance >= reserveToken)` before subtracting [4](#0-3) , and the test suite documents that the historical unguarded version "previously underflowed... cascading into a `Zap.buy` DoS" [5](#0-4) . `canGraduate`'s USD leg, however, was left with the bare subtraction and no equivalent guard.

The invariant that `assetReserve >= virtualLtReserve` is not enforced at the point of read; it only holds because `Pair.swap` enforces `(newTokenReserve + 1) * (newAssetReserve + 1) >= k` using the pair's fixed nominal `k` [6](#0-5) , while `Router._computeSell`/`_computeBuy` compute trade outputs off that same fixed `k` with floor-rounded division [7](#0-6) . The `+1` slack in `Pair.swap`'s K check permits `assetReserve` to settle at `virtualLtReserve - 1` when `tokenReserve` returns to its maximum (i.e., after enough buy/sell round-trips sell essentially all bought tokens back), because at that point `(tokenReserve+1)*(assetReserve+1) >= k` is satisfied even with `assetReserve` one wei below the launch-time virtual reserve. Once that state is reached, `canGraduate`'s subtraction underflows.

### Impact Explanation

Because `canGraduate` is called unconditionally inside both the buy path (`_executeBuy`) and the sell path (`Bonding.sell`, line 598), an underflow there reverts with an arithmetic panic on **every subsequent buy and sell** for that token. This permanently freezes the curve: traders can no longer buy or sell the token, and `Zap.buy`/`Zap.sell` (the only user-facing entry points) become permanently unusable for that token — a permanent freeze of trader/creator funds locked in that curve, matching the "Freezing of funds" impact bar. This is reachable purely through ordinary `Zap.buy`/`Zap.sell` calls by any unprivileged trader, with no admin or LT-side cooperation required.

### Likelihood Explanation

Reaching the exact underflow boundary (`assetReserve == virtualLtReserve - 1`) requires driving the pair's `tokenReserve` back to its maximum (i.e., a state where essentially all previously-bought real tokens have been sold back) while accumulated floor-rounding slack from repeated buy/sell round-trips has ratcheted `assetReserve` down to the K-invariant floor. This is a narrow, multi-transaction griefing path rather than a single-call exploit, so likelihood is lower than a trivially reachable bug, but it is achievable by a single unprivileged actor executing a sequence of `Zap.buy`/`Zap.sell` calls with no cost beyond gas and the (recoverable) trade fees, since round-tripping approximately preserves principal.

### Recommendation

Guard the subtraction in `canGraduate` (and any other direct `assetReserve - virtualLtReserve` computation) the same way `previewLtUntilGraduation` already does:

```solidity
uint256 virtualLtReserve = _launchTimeVirtualLtReserve(token_, pair);
uint256 realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;
```

Additionally, consider tightening `Pair.swap`'s K-check slack or explicitly clamping `assetReserve` to never fall below the pair's launch-time virtual reserve, closing the root cause rather than just the read-side symptom.

### Proof of Concept

1. A token is launched via `Zap.createToken`, seeding `Pair` with `tokenReserve = TOTAL_SUPPLY`, `assetReserve = virtualLtReserve` [8](#0-7) .
2. An unprivileged trader repeatedly calls `Zap.buy` followed by `Zap.sell` for the same LT amount, each round-trip going through `Router._computeBuy`/`_computeSell`'s floor-rounded division against the fixed `k` [9](#0-8) , each pass permitted by `Pair.swap`'s `+1`-slack K check [6](#0-5) .
3. After enough round-trips ratchet `assetReserve` down to `virtualLtReserve - 1` while `tokenReserve` returns near its ceiling, the next `Zap.buy` or `Zap.sell` call triggers `canGraduate`'s `assetReserve - virtualLtReserve` subtraction, which underflows and reverts with a panic [3](#0-2) .
4. From that point on, every `buy`/`sell` call for the token reverts, permanently freezing the curve and any funds/positions tied to it.

**Note on confidence:** I traced the K-invariant math analytically to argue the underflow boundary is reachable via repeated round-trip trades, but I did not find (nor could I execute) a fuzz/unit test in the repo that drives `assetReserve` to exactly `virtualLtReserve - 1`; the existing `GraduationInvariants.t.sol` and `Router.t.sol` tests cover related invariants (donation resistance, overflow cap) but not this specific rounding-ratchet scenario. A Devin session with test execution capability could confirm or refute reachability precisely by writing a fuzz test that repeats buy/sell round-trips and checks for the underflow panic in `canGraduate`.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
