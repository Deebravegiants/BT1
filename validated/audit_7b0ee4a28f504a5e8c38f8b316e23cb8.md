### Title
Duplicate-message check reverts the entire relayed batch instead of skipping the already-delivered item, enabling griefing of legitimate cross-chain deliveries - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` first verify a Merkle multiproof for an entire batch of leaves, then loop a second time to dispatch each item, reverting the *whole call* with `DuplicateMessage()` if even one leaf in the batch was already delivered. [1](#0-0) [2](#0-1)  This mirrors the mitigated-but-not-resolved M-05 pattern: a check exists (`requestReceipts`/`responseReceipts` lookup) but there is no per-item fallback (skip-and-continue) before the atomic loop, so a single already-processed item aborts delivery for every other, still-undelivered, legitimate item bundled in the same proof/batch.

### Finding Description
`handlePostRequests` builds Merkle leaves and validates destination/timeout for every request in the incoming `PostRequestMessage.requests` array, verifies one combined MMR multiproof for the whole set, and only afterward loops again to check `host.requestReceipts(hash) != address(0)` and call `host.dispatchIncoming(...)` per leaf. [3](#0-2)  If any single leaf has already been delivered by another relayer (racing submission, or a batch resubmitted after partial success), the `DuplicateMessage()` revert at line 207 aborts the entire transaction, discarding the proof-verification work and failing to dispatch the remaining, still-valid requests in the batch. `handleGetResponses` has the identical structure and the identical failure mode for `responseReceipts`. [4](#0-3) 

By contrast, once a message passes this handler-level gate, `EvmHost.dispatchIncoming` already implements a graceful per-item fallback: if the downstream `IApp.onAccept` call fails, the host deletes the receipt and *returns without reverting*, so the rest of the batch still proceeds. [5](#0-4)  That per-item resilience is exactly what is missing one layer up, at the Handler's duplicate check — the same architectural gap the original M-05 report calls out: a batched multi-item operation has a foreseeable, checkable failure condition for individual items, but the code has no mechanism to skip a bad item and continue with the rest, so the whole outer call reverts.

This is amplified by `IHandlerV2.batchCall`, which further composes multiple `handlePostRequests`/`handleGetResponses`/`handleConsensus` calls into one atomic delegatecall loop that reverts entirely on the first failure (`BatchCallFailed`). [6](#0-5)  Tesseract's relayer explicitly relies on batching messages this way for gas efficiency: `submit_batch_messages` packs an entire set of consensus/request/response messages into one `batchCall`, and the code comment states "Atomic: if any inner call reverts, the whole transaction reverts." [7](#0-6)  So a single stale duplicate leaf inside a larger relayer-submitted batch can cause an entire multi-message `batchCall` transaction — potentially bundling consensus updates and many unrelated requests/responses — to fail.

### Impact Explanation
Any relayer (or attacker who is a relayer, or who front-runs by re-relaying just one leaf from an observable pending batch transaction in the mempool) can force delivery-batches submitted by other relayers to revert, wasting their gas and delaying message delivery for every legitimate request/response bundled in that batch. This is a real DoS on the message-delivery path reachable purely by observing and front-running pending relay transactions, not requiring any privileged role — it degrades liveness of the permissionless `handlePostRequests`/`handleGetResponses`/`batchCall` dispatch path that end users depend on for cross-chain message and token-bridge delivery.

### Likelihood Explanation
Likelihood is moderate-to-high in adversarial/competitive relayer environments: batches are frequently large (Tesseract explicitly batches for gas efficiency), so the probability that some leaf in a large batch races with another relayer's independent submission (or is deliberately front-run) grows with batch size. No special privileges or preconditions are required — only visibility of a pending transaction and the ability to submit a smaller transaction delivering one of its leaves first.

### Recommendation
Change the second loop in `handlePostRequests`/`handleGetResponses` (and the equivalent path composed via `batchCall`) to skip already-delivered leaves (`continue`) instead of reverting the whole call on `DuplicateMessage()`, mirroring the graceful non-revert fallback already used in `EvmHost.dispatchIncoming` for downstream `onAccept` failures. Alternatively/additionally, perform the duplicate-receipt check for all leaves in the same first pass (before proof verification) and exclude already-delivered leaves from the Merkle proof set, so partially-stale batches from relayers can still deliver the not-yet-processed items in one transaction.

### Proof of Concept
1. Relayer A constructs a `PostRequestMessage` with requests `[R1, R2, R3]` and a valid MMR multiproof, and broadcasts the transaction to `handlePostRequests`.
2. Relayer B observes the pending transaction in the mempool, extracts `R2` alone with its own (possibly separately obtained) proof for `R2`, and submits a transaction delivering only `R2` with higher gas, landing first.
3. Relayer A's original transaction executes: destination/timeout checks pass, the multiproof verifies successfully (all leaves still committed on Hyperbridge), but in the dispatch loop `host.requestReceipts(R2.hash()) != address(0)` is now true, so `revert DuplicateMessage()` fires. [1](#0-0) 
4. The entire transaction reverts: `R1` and `R3`, which were never delivered by anyone, fail to be dispatched despite having valid, still-fresh proofs, and Relayer A's gas for proof verification is wasted. Relayer A must resubmit `[R1, R3]` in a new transaction, incurring redundant gas cost and delivery delay.

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
