### Title
Webhook `shop-domain` header is trusted for tenant dispatch but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` header is never part of the signed material, so it can be altered without invalidating the HMAC check that `Webhooks::Registry.process` performs before dispatching to the app's handler.

### Finding Description
The identity binding that should hold is: `hmac_verified(raw_body) == true` should imply `shop header used in WebhookMetadata is authentic for that body`. In this gem that binding is broken.

- `Request#to_signable_string` returns only `@raw_body`, excluding all headers: [1](#0-0) 

- `Request#shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`): [2](#0-1) [3](#0-2) 

- `Registry.process` validates the HMAC (over the body only) and then dispatches the handler using the unauthenticated `request.shop` value as the tenant identity for the payload: [4](#0-3) 

Because `shop` is not part of `to_signable_string`, an unprivileged internet user who can obtain any body+HMAC pair that is valid for the app's `api_secret_key` (e.g. by installing the app on their own store and receiving a legitimately signed webhook for a topic they control) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body`: [5](#0-4) 

The resulting `WebhookMetadata` handed to the app's handler will carry the forged `shop` value alongside a validly-signed body, so any app logic that trusts `data.shop` for tenant-scoped operations (looking up a session/access token for that shop, writing to per-shop records, gating mandatory-compliance topics such as `shop/redact` or `customers/data_request`) will act on the wrong tenant.

### Impact Explanation
This breaks the equality `shop-authenticated-by-hmac == shop-used-for-tenant-dispatch`, allowing a cross-tenant confusion: data legitimately generated by shop A can be attributed to shop B in the receiving app purely by header manipulation, without needing shop B's or the app's credentials. This falls under the Critical category of cross-tenant access, since the gem's own webhook-processing API (`Registry.process`) hands out a shop identity to the handler that it never actually authenticated.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must first obtain a validly-HMAC-signed body from Shopify — this typically requires them to install/operate their own shop against the target app to trigger a real webhook delivery (an unprivileged, non-credentialed action) and then replay/proxy that exact request to the app's webhook endpoint with a modified shop header. No secret key, access token, or victim credentials are required.

### Recommendation
Bind the `shop` value into the signed material, or otherwise cryptographically verify it, before it is trusted for tenant dispatch:
- Include the `shop-domain` header (and other identity-bearing headers such as `topic`, `webhook-id`) in `to_signable_string`, matching them against a value independently verifiable by the app (e.g., cross-check against the session/shop the endpoint is scoped to), or
- Document explicitly in `Registry.process`/`WebhookHandler` that `shop`/`topic` headers are unauthenticated and that consuming apps MUST NOT use them as the sole tenant identity without additional verification (e.g., verifying the shop exists in the app's own session store before trusting the payload).

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and has installed the target app.
# Shopify legitimately delivers a real webhook for shop-a with a valid HMAC:
raw_body = '{"id":123,"email":"victim-controlled-data"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body) # computed by Shopify, captured by attacker via their own store

# Attacker replays the exact body+hmac to the app's webhook endpoint,
# only changing the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "customers/data_request",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (it only checks raw_body),
#    handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com"
#    even though the payload actually originated from shop-a.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
