### Title
Webhook `shop-domain` (and `topic`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` (and `topic`) values that the handler receives and acts on come from HTTP headers that are never part of the signed material [2](#0-1) . This breaks the identity binding: *bytes verified* (the JSON body) ≠ *bytes used to determine the tenant* (`shop-domain` header), matching the bug-class hint of "a field acted on but not covered by the HMAC."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that string [4](#0-3) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors, however, are read directly from request headers with no cryptographic binding to the signature [5](#0-4) .

`Registry.process` uses the (unauthenticated) `topic` header to select a handler and forwards the (unauthenticated) `shop` header straight into `WebhookMetadata`, which is delivered to the host application's handler as the tenant identifier: [1](#0-0) .

Because the shop identity is not part of the signed payload, any two (body, HMAC) pairs that are valid for the real secret can be replayed with the `shop-domain` header swapped to a different (victim) shop, and the check in `HmacValidator.validate` will still pass — the identity equality that should hold is `shop authenticated == shop bound in the signed bytes`, but here `shop authenticated` is taken from an out-of-band, unsigned header while the signature only covers the JSON body.

An unprivileged internet user can obtain a genuinely-valid (body, HMAC) pair without needing the app's `client_secret`: anyone can install a public Shopify app on their own (attacker-owned) development/trial store, trigger a real event (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`, etc.), and capture the resulting webhook delivery — which Shopify signs with the real secret for a body the attacker fully controls (they choose the order/customer content in their own store). The attacker then replays that exact body+HMAC to the app's single shared webhook endpoint, only changing the `X-Shopify-Shop-Domain` header to the victim shop's domain (and optionally the topic, which is likewise unsigned).

### Impact Explanation
If the host application trusts `data.shop` from `WebhookMetadata` to select which merchant's records to update/delete/query (the standard usage pattern for Shopify apps, e.g. mandatory GDPR webhooks `customers/redact`, `shop/redact`, or business webhooks like `orders/create`/`app/uninstalled`), an attacker can inject attacker-controlled data attributed to a victim shop, or trigger destructive/administrative actions (data deletion, uninstall cleanup, inventory changes) scoped to a shop the attacker does not control. This is a cross-tenant integrity/action-spoofing issue reachable by any internet user who can install the app once on a store they control — no `api_secret_key`, access token, or privileged access is required.

### Likelihood Explanation
High: the only prerequisite is the ability to install the target app on any Shopify store (including a free/dev store), which is available to any internet user, plus the ability to send an HTTP POST with attacker-chosen headers to the app's public webhook endpoint. No secrets or credentials belonging to the victim are needed.

### Recommendation
Bind the tenant/topic identity into the verified material instead of trusting unsigned headers:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the string that is HMAC-verified (Shopify's actual webhook signature only covers the body, so this must be done as an additional application-level check), or
- After body-HMAC verification succeeds, independently confirm that the `shop-domain` header corresponds to a shop with a valid, previously-established session/installation record for this specific webhook subscription (e.g., match the shop against the shop for which the app most recently registered that webhook ID via the Admin API), rather than accepting the header value at face value.
- At minimum, document/enforce that `WebhookMetadata#shop` must never be treated as authenticated in host applications unless cross-checked against known installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and grants it webhook permissions (or subscribes to a mandatory topic).
2. Attacker triggers an event in their own store (e.g., updates a customer) so Shopify delivers a genuine webhook to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays an HTTP POST to the same public webhook endpoint, keeping `B` and `H` unchanged but setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only [4](#0-3)  — it matches `H`, so `Registry.process` accepts the request and dispatches the handler with `shop: "victim-shop.myshopify.com"` [1](#0-0) , even though the payload actually originated from and was authorized for the attacker's own shop.
