### Title
Webhook `shop-domain` header is trusted for tenant identification but excluded from the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with `api_secret_key` [2](#0-1) . The `shop` used to identify the tenant, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [3](#0-2) , and `Registry.process` passes that same unauthenticated value on to the app's `WebhookHandler` as the tenant identifier without any cross-check against the body or against Shopify's TLS/IP origin [4](#0-3) .

### Finding Description
This matches the requested bug class exactly: "a field acted on but not covered by the HMAC." The equality that should hold is:

`shop authenticated by HMAC == shop acted upon by the handler`

but the code actually enforces only:

`HMAC(raw_body, api_secret_key) == received_hmac`

with the `shop-domain` header carried through completely outside that computation. `Registry.process` verifies the HMAC over the body [5](#0-4) , then builds `WebhookMetadata` using `request.shop`, which is nothing more than a header value [6](#0-5) [7](#0-6) .

Any entity capable of obtaining one genuine, validly-HMAC-signed webhook body (e.g. an unprivileged user who installs the app on their own development/trial store and receives real webhooks for that store, since anyone can create a Shopify store and install a public app) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a victim shop. Because `to_signable_string` never includes the shop, the signature still validates, and `Registry.process` will hand the attacker-controlled body to the handler tagged as belonging to the victim tenant [6](#0-5) . Any host application that uses `WebhookMetadata#shop` (as the gem's own documentation instructs: `shop_domain: data.shop`) to look up per-tenant state, enqueue tenant-scoped jobs, or otherwise gate business logic will process attacker-supplied data under the wrong tenant's identity [8](#0-7) .

### Impact Explanation
This is a cross-tenant access vulnerability: an unprivileged actor can cause the application to attribute and act on webhook data under a shop they do not own/operate, purely by holding one legitimately-signed webhook payload and forging the accompanying header. This satisfies the "Critical – cross-tenant access" impact category, since it breaks the authentication boundary between tenants that `Registry.process` is meant to enforce.

### Likelihood Explanation
High. Any developer/attacker can register a free/trial store, install a public app that uses this gem, and legitimately receive real webhooks (with valid HMACs) for events they trigger themselves. Because the signable string is body-only [1](#0-0) , replaying that exact body with a different `shop-domain` header requires no cryptographic secret and no privileged access — only the ability to send an HTTP POST to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Bind the shop identity into the verified signature computation, or otherwise cryptographically tie `shop-domain` to the payload before trusting it:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in `to_signable_string`, or
- Independently verify that the shop named in the header corresponds to a shop with an active app installation known to the host app (this is effectively what the gem should document/enforce, since it currently ships `request.shop` straight from an untrusted header into `WebhookMetadata` with no correlation check to the signed body).

### Proof of Concept
1. Attacker installs the target app on a shop they control, `attacker-shop.myshopify.com`, and triggers a webhook (e.g. `orders/create`). Shopify sends:
   - Headers: `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `raw_body` (attacker fully controls order contents by creating the order themselves)
2. Attacker captures `raw_body` and the corresponding valid `hmac-sha256` value.
3. Attacker POSTs the same `raw_body` and `hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. In `ShopifyAPI::Webhooks::Request.new`, `hmac` is computed by base64-decoding/hex-encoding the attacker-supplied `hmac-sha256` header value [9](#0-8) , and `to_signable_string` is just `raw_body` [1](#0-0) ; since `raw_body` and its HMAC are unmodified and genuinely valid, `Utils::HmacValidator.validate(request)` returns `true` [2](#0-1) .
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled webhook content as though it originated from the victim's store.
