### Title
Malicious liquidator can leave dust collateral just above the rounding threshold, permanently bypassing bad-debt socialization - (File: `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

### Summary
Zest's `liquidate` function only forces full seizure of a borrower's remaining collateral when the value of the leftover collateral rounds down to **exactly zero** additional repayable debt. Any leftover collateral whose USD value rounds to a nonzero (but economically negligible) debt amount is left in the position untouched, and the `no-collateral-left` flag used to trigger bad-debt socialization is not set. This mirrors the Fraxlend `_newMinCollateralRequiredOnDirtyLiquidation = 0` bug class: there is no minimum dust threshold forcing a liquidator to either take all collateral or trigger bad-debt handling.

### Finding Description
In `liquidate`, after computing the amount of collateral to seize (`coll-final-raw`), the contract computes how much collateral would remain (`coll-remaining`) and whether that remainder could still repay any debt: [1](#0-0) 

If `coll-remaining` is nonzero, `remaining-debt-to-repay` is computed via `div-bps-down` (rounding down) on the USD value of the leftover collateral, then `mul-div-up` back to token units. This is only forced to full seizure (`coll-final = user-coll-balance`) when `remaining-debt-to-repay` computes to exactly `u0`. A liquidator who chooses `debt-amount` such that the resulting `coll-remaining` corresponds to a USD value just above the rounding cutoff (`div-bps-down` threshold, roughly `BPS + liq-penalty-max` in the smallest USD unit) will cause `remaining-debt-to-repay` to be nonzero (e.g. `u1`), so the code takes the `coll-final-raw` branch and intentionally leaves dust collateral in the position.

Later, whether bad-debt is socialized depends entirely on `no-collateral-left`, which requires `coll-removed` to be exactly `u0` (meaning nothing at all was seized) for single-collateral positions, or additionally `other-debt-repayable == u0` for multi-collateral positions: [2](#0-1) 

Because the liquidator seized a nonzero (albeit dust) amount, `coll-removed != u0`, so `no-collateral-left` is `false` and `socialize-debt-asset` (bad-debt write-off) is never invoked, exactly like the Fraxlend `_leftoverCollateral <= 0` branch in the report never firing when a nonzero dust amount is left. The dust threshold here is not configurable/protected by any minimum-collateral check — there is no `MIN-COLLATERAL-REQUIRED`-style constant enforcing that any nonzero leftover must exceed a meaningful minimum before bypassing socialization (confirmed no such constant exists in the market/vault contracts).

### Impact Explanation
If a borrower's position is left with a dust amount of collateral and outstanding debt permanently, no future liquidator has an economic incentive to complete the liquidation (gas/opportunity cost exceeds the dust value), so the debt is never repaid and bad debt is never socialized into the vault's `lindex`/`assets` accounting via `socialize-debt` in `v0-vault-*.clar`: [3](#0-2) 

Because the vault's index (`lindex`) is never written down to reflect this stuck bad debt, the vault continues to report an inflated backing/`total-assets`, while the true recoverable value is lower. This breaks the identity `sum(zToken shares) * pricePerShare == real recoverable backing`, meaning later withdrawers redeem against assets that do not actually exist, i.e., protocol insolvency for the last depositors to withdraw — matching the Critical impact category (protocol insolvency).

### Likelihood Explanation
This requires an attacker acting as liquidator to deliberately choose `debt-amount` (an attacker-controlled parameter of `liquidate`) to leave a specific dust amount of collateral rather than fully liquidating. This is a low-cost, no-special-privilege action available to any liquidator, and it is more attractive on chains with low fees (Stacks), making repeated dust-leaving cheap. The likelihood of triggering the underlying bad-debt condition itself depends on market conditions (price crashes causing undercollateralization) consistent with the existing test `ATK-LG-05` in the repo, which validates the "full collateral wipeout" socialization path but does not test the dust-leftover bypass path: [4](#0-3) 

### Recommendation
Introduce an explicit minimum-collateral-value threshold (denominated in USD, e.g., a fixed dust cutoff well above the `div-bps-down` rounding floor) that a liquidator must either seize entirely or leave above. Concretely: when `coll-remaining`'s USD value is below this threshold, force `coll-final = user-coll-balance` (full seizure) regardless of whether `remaining-debt-to-repay` rounds to a nonzero token amount, and simultaneously ensure `no-collateral-left`/bad-debt socialization is evaluated based on the borrower's actual post-liquidation collateral balance (querying the vault) rather than solely on `coll-removed == 0`.

### Proof of Concept
1. Borrower's position becomes undercollateralized (price drop), entering liquidation range.
2. Attacker calls `liquidate` with a `debt-amount` deliberately chosen so that the resulting `coll-remaining` (per `scale-debt-for-liquidation`) has a USD value just above the `div-bps-down` rounding floor (e.g., a fraction of a cent), so `remaining-debt-to-repay` computed at [5](#0-4)  evaluates to `u1` (nonzero) instead of `u0`.
3. `coll-final` is set to `coll-final-raw` (dust left) instead of `user-coll-balance`, per [6](#0-5) .
4. `coll-removed` returned from `collateral-remove` is nonzero, so `no-collateral-left` is `false` at [7](#0-6) , and `socialize-debt-asset` is never called.
5. The position now has a dust amount of collateral and outstanding debt permanently below any future liquidator's profit threshold; the vault's `lindex` is never adjusted, and vault backing remains overstated versus real recoverable value.

I was unable to independently execute this against the actual Clarinet test suite to numerically confirm the exact dust-value cutoff (this requires running `normalize`/`div-bps-down` with live price data), so the precision of "just above the rounding floor" should be validated with a concrete unit test before remediation.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
