### Title
Header `checkMagic()` validation runs after expensive attacker-controlled `scrypt` cost parameters are executed, allowing structural validation bypass ordering - ([File: libraries/secure-container/src/index.js])

### Summary
In `decrypt()`, the file's `checksum` only covers `metadata` and `blob`, never the `header`, and `conHeader.decode()` (which invokes `checkMagic()`) is called *after* `conMetadata.decryptBlobKey()` has already executed `scrypt` with attacker-controlled `n`/`r`/`p` cost parameters. This lets an attacker who fully controls the imported file bytes make the wallet run expensive/oversized scrypt work — or otherwise proceed past the checksum gate — with a header that is completely garbage and never gets checked before that costly work happens.

### Finding Description
`file.js` defines the container as `header | checksum | metadata | blob`, and `computeChecksum` at [1](#0-0)  hashes only `metadata` + blob-length + `blob` — the `header` bytes are entirely excluded from the checksum. Since `header` and `metadata` are `Buf(HEADER_LEN_BYTES)`/`Buf(METADATA_LEN_BYTES)` fixed-length byte slots in the `vsf`-built struct ( [2](#0-1) ), an attacker who fully controls `encryptedData` can freely craft any 224-byte header (including corrupted magic/version) plus a self-consistent metadata+blob whose checksum they compute themselves, and the checksum equality check will pass.

The actual `decrypt()` control flow is: `conFile.decode()` → checksum check → `conMetadata.decode()` → `conMetadata.decryptBlobKey()` → `conHeader.decode()` (which calls `checkMagic()`) → `conBlob.decrypt()`, as seen at [3](#0-2) . Critically, `decryptBlobKey` (which merges the attacker-supplied `metadata.scrypt` object, including `n`, `r`, `p`, into the scrypt call via `boxDecrypt`) runs at line 50, while `conHeader.decode()` — the only place `checkMagic()` is invoked ( [4](#0-3)  and [5](#0-4) ) — does not run until line 51, *after* the scrypt work has already completed.

`metadata.decode()` performs no semantic validation of `n`/`r`/`p` (it's a raw fixed-size `UInt32BE` triplet, see [6](#0-5) ), and `boxDecrypt`/`stretchPassphrase` pass these values straight into `scrypt(...)` with no upper bound check ( [7](#0-6)  and [8](#0-7) ). So an attacker-crafted file with a corrupted `magic`/`version` in the header, a valid checksum computed only over their own metadata/blob, and an extreme `n` (e.g. `2^30`) in metadata will cause the wallet to run costly scrypt work before the header is ever validated and rejected.

### Impact Explanation
This is a computational resource-exhaustion (DoS-style) issue reachable purely from attacker-fully-controlled import bytes (e.g., a malicious "backup"/import file, deeplink payload, or QR-imported container): the wallet performs expensive, attacker-tunable scrypt work (bound only by whatever the underlying `@exodus/crypto/scrypt` implementation itself enforces, which was not verifiable from this repo) *before* the cheap, authoritative magic/version structural check ever runs and rejects the file. It does not by itself grant unauthorized signing or secret disclosure (the passphrase is still needed to actually decrypt correctly), but it violates the expected order of operations — cheap authenticity/structure checks should gate expensive cryptographic work — and can be used to tie up CPU/memory on the device via a single malformed import attempt, and to a degree undermines confidence that `checkMagic()` acts as an early gate against malformed containers.

### Likelihood Explanation
Fully feasible and repeatable: the attacker only needs to control the raw bytes of the file passed to `decrypt()`/`conFile.decode()`, which matches the stated precondition. No secrets, no privileged state, and no dependency bug are required — the checksum is self-computable by the attacker over their own chosen metadata/blob, and the header is unauthenticated by design (excluded from checksum).

### Recommendation
Reorder `decrypt()` in `libraries/secure-container/src/index.js` so `conHeader.decode()` (and thus `checkMagic()`) runs immediately after `conFile.decode()`/checksum verification and *before* `conMetadata.decryptBlobKey()` is invoked. Additionally, consider including the header bytes in the checksum computation (or otherwise authenticating them), and add explicit upper-bound validation on `scrypt` `n`/`r`/`p` parameters read from untrusted metadata before passing them into `stretchPassphrase`/`scrypt`.

### Proof of Concept
Integration test in `libraries/secure-container/src/__tests__/`:
1. Build a valid metadata object via `conMetadata.create()`/`encryptBlobKey`, but set `metadata.scrypt.n` to an extreme value (e.g. `2**30`).
2. Build a header buffer with corrupted magic bytes (not `SECO`).
3. Compute `checksum = await conFile.computeChecksum(mdBuf, encBlob)` using the attacker's own metadata/blob (this will succeed since checksum only covers metadata+blob).
4. Assemble `fileObj = { header: corruptedHeaderBuf, checksum, metadata: mdBuf, blob: encBlob }` and `conFile.encode(fileObj)`.
5. Call `index.decrypt(encryptedData, passphrase)` and instrument/time `conMetadata.decryptBlobKey` — assert that it is invoked (and scrypt executes) even though `header.magic` is corrupted, i.e., that `checkMagic()`/`header.decode()` has not yet run and rejected the file at that point.
6. Expected (failing) assertion: `decrypt()` should throw from `checkMagic()`/header validation *before* any scrypt work occurs; currently it throws only after `decryptBlobKey` has already run scrypt with the attacker-controlled `n`.

```javascript
export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
```
