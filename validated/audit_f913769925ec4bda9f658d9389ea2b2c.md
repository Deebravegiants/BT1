### Title
Webhook shop-domain (and topic) identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing when a valid webhook body is replayed - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature from the raw request body only, but the `shop` (and `topic`) values that the library hands to the app's `WebhookHandler` are read from unsigned HTTP headers (`x-shopify-shop-domain` / `shopify-shop-domain`). This breaks the identity binding `HMAC-verified content == identity acted upon`: the HMAC proves the *body* came from someone possessing `api_secret_key`, but it proves nothing about which shop the request claims to be from. Any party that can produce one HMAC-valid body/secret pairing (e.g. by having the app installed on their own store and receiving a legitimate webhook) can replay that exact body to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the attacker-controlled shop to the handler as if it were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from headers, none of which participate in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` against the HMAC header, i.e. it verifies the body bytes, not the headers: [3](#0-2) 

`Registry.process` calls this HMAC check and then immediately forwards the unsigned header-derived `request.shop` (and `request.topic`) to the app's handler as trusted metadata: [4](#0-3) 

The resulting `WebhookMetadata` struct presents `shop` as an ordinary, implicitly-trusted field to the handler, with nothing in its type or documentation flagging that it is unauthenticated: [5](#0-4) 

The equality that should hold is: `shop attributed to the webhook by the library == shop that actually produced/authorized the signed body`. Instead the library only enforces `HMAC(body, api_secret_key) == received_hmac`; it never binds `shop`/`topic` into that computation. Because the same `api_secret_key` is shared across all shops that installed the app, and because HMAC-SHA256 of a body computed with a shared secret does not encode "for shop X" unless the shop is part of the signed content, a valid signature obtained from *any* one shop's genuine webhook delivery can be replayed with a forged `shop-domain` header for a different shop and will still validate.

### Impact Explanation
This maps to the "credential leakage/cross-tenant" bug class analogous to the Nextcloud report: an identity (`shop`) that is *acted on* by the consuming application (e.g., to look up per-shop records, disable subscriptions, delete customer data for `customers/redact`, etc.) is not bound to the cryptographic proof used to authorize the request. An attacker who legitimately installs the target app on their own shop (a normal, unprivileged action any merchant/dev can take) can capture one valid webhook body+HMAC pair for their own shop and then send arbitrary numbers of forged requests naming any other shop domain in the header. Any host application that trusts `WebhookMetadata#shop` (which the library's own docs and struct design encourage, since it is presented as verified) will act on data for the wrong tenant — this is a cross-tenant access primitive within the library's own trust boundary (`Registry.process` → handler), independent of how the host app implements the rest of its logic.

### Likelihood Explanation
Likelihood is moderate-to-high for any consuming app that relies on the shop value returned by `Registry.process`/`WebhookMetadata` without separately re-validating it (which the library gives no built-in mechanism to do, since `shop` is not part of what HMAC covers). No access token, `client_secret`, or privileged account is required — only the ability to install the app once on any shop (including the attacker's own store) to harvest one valid signed body.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the HMAC-signable content, or otherwise cryptographically bind them to the payload before exposing them via `WebhookMetadata`. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should compute the signable string from `shop + topic + raw_body` (matching what is actually authorized) so that a captured signature cannot be replayed under a different asserted shop identity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the full raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H` (both are visible to the attacker as the receiving app owner, or via any means of obtaining one valid delivery).
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256`: `H` (unchanged)
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: unchanged or altered
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and compares to `H` — this passes because `B` and `H` are unmodified and genuine.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's `handler.handle(data: ...)`, which now believes it is processing a verified webhook for `victim-shop.myshopify.com`. [4](#0-3)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
