### Title
Permanent market freeze from RAY value overflow during interest accrual - ([File: common/src/rates/index.rs])

### Summary
An unprivileged user can create a sufficiently large, highly utilized market position and repeatedly call `Controller::update_indexes` until `borrowed * borrow_index` exceeds the `i128` fixed-point domain; the resulting `GenericError::MathOverflow` prevents every later pool operation for that market because all mutation paths sync interest before executing. [1](#0-0) [2](#0-1) 

### Finding Description
RAY accounting stores scaled shares separately from indexes, but accrual reconstructs total debt with `borrowed.mul(env, old_borrow_index)` and `borrowed.mul(env, new_borrow_index)`, where `Ray::mul` calls `mul_div_half_up` and panics with `MathOverflow` when the representable result exceeds `i128::MAX`. [3](#0-2) [4](#0-3) 

`LiquidityPool::update_indexes` reaches `ops::market::accrue`, which loads each market and invokes `interest::global_sync`; `global_sync` applies one or more `accrue_step` calculations and commits the resulting indexes. [5](#0-4) [6](#0-5) [7](#0-6) 

The issue is reachable through ordinary controller entrypoints: `supply` creates collateral or liquidity positions, `borrow` creates debt, and `update_indexes` is callable by any authorized caller without a privileged role. [8](#0-7) [1](#0-0) 

After the overflow threshold is crossed, `synced_market` performs the same failing accrual before `supply`, `borrow`, `repay`, `withdraw`, liquidation withdrawals, and other pool mutations, so the panic becomes persistent rather than a one-transaction failure. [9](#0-8) [10](#0-9) [11](#0-10) 

The repository already contains a regression demonstrating the condition: a one-billion-token 18-decimal market at 98% utilization reaches `MATH_OVERFLOW` before `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment fail with the same error. [12](#0-11) 

### Impact Explanation
All supplier cash in the affected `(hub_id, asset)` market becomes permanently frozen because withdrawals cannot pass the mandatory pre-mutation accrual, while borrowers cannot repay and liquidators cannot execute the pool legs needed to rescue underwater accounts. [9](#0-8) [13](#0-12) 

Because the panic occurs before `borrow_index` reaches its configured maximum, the index ceiling does not stop the freeze, and parameter replacement also accrues under the old model before writing new parameters. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The attack requires a very large funded position near the documented token-to-RAY limit and sustained high utilization, so it is capital-intensive and depends on a listed market, sufficient collateral value, and caps that permit the position. [16](#0-15) [17](#0-16) 

Once those market conditions exist, any unprivileged caller can advance accrual through `update_indexes`, and the checked arithmetic predictably panics when reconstructed RAY debt exceeds `i128::MAX`. [1](#0-0) [18](#0-17) 

### Recommendation
Enforce a market-level invariant that both `supplied * MAX_SUPPLY_INDEX_RAY` and `borrowed * MAX_BORROW_INDEX_RAY`, or a tighter configured ceiling, remain representable before every mint, and configure supply and borrow caps below that mathematical bound. [3](#0-2) [16](#0-15) 

Accrual should also clamp or reject new index values before reconstructing a total that cannot fit `i128`, rather than deriving `new_total_debt` and trapping after the safe operating domain has already been crossed. [19](#0-18) [20](#0-19) 

### Proof of Concept
1. Using an active spoke and an 18-decimal listed market `BIG18`, call `supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])` to create the liquidity account. [21](#0-20) [22](#0-21) 
2. From the same unprivileged caller, create a second account with enough listed collateral and call `borrow(caller, collateral_account_id, [(BIG18, principal * 98 / 100)], None)`. [23](#0-22) [24](#0-23) 
3. Advance ledger time and call `update_indexes(caller, [BIG18])`; repeating this permitted accrual eventually makes the reconstructed debt exceed `i128::MAX` and returns `MATH_OVERFLOW`. [1](#0-0) [25](#0-24) 
4. Subsequent `withdraw` and `repay` calls fail with the same `MATH_OVERFLOW` because both pool operations invoke `synced_market` before changing positions. [9](#0-8) [26](#0-25)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"

        t.advance_time(YEAR_SECS);

| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
