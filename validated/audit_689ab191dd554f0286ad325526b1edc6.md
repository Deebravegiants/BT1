### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the HMAC over the raw request body via `Utils::HmacValidator.validate`, whose signable content is defined by `Webhooks::Request#to_signable_string`, which returns only `@raw_body`. The `shop` value passed to the handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed content, so it can be freely set by whoever sends the HTTP request.

### Finding Description
The equality that should hold is: *the shop identity authenticated by HMAC == the shop identity delivered to the handler*. In this gem that equality is broken.

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac`. [1](#0-0) 
- For webhooks, `to_signable_string` returns only the raw body bytes: [2](#0-1) 
- But `shop` is read from a header that is completely outside that signed string: [3](#0-2) 
- `Registry.process` only checks the HMAC before dispatching, then hands the unauthenticated `request.shop` straight to the handler: [4](#0-3) 

Because Shopify signs webhooks using the app's single `api_secret_key`, which is identical for every shop that installs the app, an unprivileged internet user can install the app on their own shop to obtain a *genuinely* HMAC-valid `(body, hmac)` pair for a topic of their choosing, then replay that exact body/HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. The HMAC check still passes (it only checks the body), and `WebhookMetadata#shop` is set to the attacker-chosen victim domain that the handler will trust.

### Impact Explanation
The gem's own documentation for `Registry.process` states it "will verify the request did indeed come from Shopify" and hands the handler a `shop` field described as "The shop domain of the webhook." [5](#0-4) [6](#0-5) 
Host applications reasonably rely on this documented guarantee to key persistence, job dispatch, or authorization decisions on `data.shop` (as shown in the very sample handler code the gem ships, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). [7](#0-6)  Because the `shop` binding is unauthenticated, this enables cross-tenant data confusion/injection: an attacker can cause the host app to process attacker-supplied webhook content under a victim shop's identity, without ever needing the victim's access token, session, or the app's `client_secret`.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action any Shopify merchant/developer can take) and can send arbitrary HTTP requests to the app's public webhook endpoint (which is by definition internet-reachable). No credentials, leaked secrets, or privileged access are needed — likelihood is high for any app built directly against this gem's documented `Registry.process`/`Webhooks::Request` API without adding its own additional shop-binding checks.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` value to the signed body before it is trusted, e.g., extend `to_signable_string` to incorporate the shop header, or have `Registry.process`/`WebhookMetadata` require verification that the shop belongs to a session/registration the app itself created, rather than trusting the raw header verbatim.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a legitimately-signed webhook for topic "orders/create":
body = '{"id": 1, "note": "attacker controlled payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, body)
# (APP_SECRET is the same for every shop installing the app; attacker never
#  needs to know it, they just capture the real header Shopify sent them)

# Attacker replays the exact body + hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (body matches signature).
# => Handler receives data.shop == "victim-shop.myshopify.com" with
#    attacker-controlled body, despite never having produced anything
#    genuinely signed for that shop.
```
