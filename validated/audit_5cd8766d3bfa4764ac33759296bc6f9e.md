### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` (tenant identity) is read from an unauthenticated HTTP header. `Registry.process` passes that unauthenticated `shop` value straight into `WebhookMetadata`, which host applications use to attribute the webhook to a specific merchant/tenant. This breaks the intended binding `hmac == HMAC(shop || body)` down to `hmac == HMAC(body)`, letting the `shop` field be substituted independently of the signature — the same bug class as the external report (an action-relevant field not covered by the integrity check).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac`/`#shop` are both derived from HTTP headers set outside of any cryptographic protection: [1](#0-0) 

`HmacValidator.validate` verifies exactly and only `to_signable_string` (the body) against the secret: [2](#0-1) 

`Registry.process` validates the HMAC, then immediately forwards `request.shop` (an un-covered header value) to the app's handler as the tenant identifier for the webhook, with no cross-check that the shop is consistent with anything covered by the signature: [3](#0-2) 

The documented handler contract explicitly trusts `data.shop` as "The shop domain of the webhook" and shows apps using it to route/attribute background jobs per shop: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that has the app installed, any shop that legitimately receives a webhook (a valid `raw_body` + `hmac-sha256`/`x-shopify-hmac-sha256` pair, both fully within the reach of an unprivileged merchant who installs the app) can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, even though the payload actually originated from — and was HMAC-signed for — the attacker's own shop.

The binding that should hold is:
`verified_identity (shop used by handler) == signed_identity (shop covered by HMAC)`

but the gem instead enforces:
`verified_bytes (raw_body) == signed_bytes (raw_body)`, with `shop` entirely outside that check — an equality mismatch identical in shape to the referenced report's unvalidated/unbound destination field.

### Impact Explanation
This crosses a tenant boundary: an app that keys per-shop state (uninstall handling, data deletion via `shop/redact`/`customers/redact`, order/customer sync, billing, feature flags, etc.) off `WebhookMetadata#shop` can be made to process a webhook body as if it belonged to a different merchant, purely because the gem does not bind the `shop` value to the HMAC. Depending on the topic and how the host app uses `data.shop`, this can lead to cross-tenant data confusion/corruption (e.g., triggering `shop/redact`-style processing, or writing another shop's webhook payload into the attacker-chosen tenant's records). This matches the "Critical - cross-tenant access" impact bucket in scope.

### Likelihood Explanation
Any merchant who installs the app is, by definition, an "unprivileged internet user" relative to other tenants, yet can capture a fully valid `(raw_body, hmac)` pair from their own genuine Shopify-delivered webhooks (e.g. via a proxy, logging the request, or simply resending it). No secret material beyond what Shopify already sends them is required, and no TLS interception or credential theft is needed — only the ability to POST to the app's public webhook endpoint with attacker-controlled headers, which is inherent to how HTTP webhook delivery works. The exploit path is fully reachable through this gem's own `Registry.process`/`Request` API as documented.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) into the value that is HMAC-verified, or otherwise cross-validate the header-supplied `shop` against a value obtained through an authenticated channel (e.g., correlate against the shop associated with the registered webhook/session, not a bare header) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification by the host application.

### Proof of Concept
1. App has two installs: Shop A (attacker-controlled) and Shop B (victim), both under the same `api_secret_key`.
2. Shopify delivers a legitimate webhook to Shop A's app instance: `raw_body = B`, header `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: H = HMAC_SHA256(secret, B)`.
3. Attacker captures `B` and `H` (both delivered to their own endpoint/logs — no secret needed).
4. Attacker replays a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` (`to_signable_string`) — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
6. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app handler, which now believes body `B` belongs to Shop B — despite it having been generated and signed for Shop A.

          received_signature = verifiable_query.hmac
