Based on the code, this reported attack path does not hold up.

### Analysis

`SchedulingStateMachine::create_task` (`do_create_task`) builds `lock_contexts: Vec<LockContext>` **once**, by iterating `transaction.message().account_keys()` and computing each key's `RequestedUsage` from `transaction.message().is_writable(index)` at task-creation time: [1](#0-0) 

This single `Vec<LockContext>` is stored inside the immutable `TaskInner`/`Task` (an `Arc`), and both `try_lock_usage_queues` and `unlock_usage_queues` iterate the **same** `task.lock_contexts()` list — they never recompute `RequestedUsage` from the message a second time: [2](#0-1) 

Since the requested usage for a given `LockContext`/`UsageQueue` pair is fixed at task creation and reused verbatim at both lock and unlock time, there is no code path by which the *same task* could present `Readonly` at `try_lock_usage_queues` and `Writable` at `unlock_usage_queues` (or vice versa) for the same `UsageQueue`. The `unreachable!()` panics in `UsageQueueInner::unlock` (e.g. `test_unreachable_unlock_conditions3`) are only reachable via direct, artificial misuse of the private `unlock`/`update_current_usage` test helpers, not through the public `schedule_task`/`deschedule_task` API driven by attacker-supplied transactions: [3](#0-2) 

The scenario also requires the same pubkey to appear twice in one message with different privilege flags (e.g. as nonce authority and separately as a writable account). `SanitizedMessage::account_keys()` is a deduplicated key list, and duplicate account keys are explicitly rejected pre-scheduling by `validate_account_locks()` (`AccountLoadedTwice`), which the code comments in `do_create_task` explicitly call out as a required precondition enforced by `replay_stage`/`blockstore_processor` and `DefaultTransactionHandler::handle()`: [4](#0-3) [5](#0-4) [6](#0-5) 

There is even a regression test, `test_enfoced_get_account_locks_validation`, specifically covering the "duplicate account key" mangling attempt described in the question, confirming it is caught (`AccountLoadedTwice`) before/at handler execution rather than reaching the scheduler's internal lock bookkeeping: [7](#0-6) 

A durable-nonce "authority" reference does not create a second, differently-privileged entry for the same pubkey in `account_keys()` — nonce authority is just a `Pubkey` field read from account data during instruction processing, not a separate message-level account slot with its own writability bit. The single writability bit per unique key (`message.is_writable(index)`) is computed once from the compiled message header and reused identically for lock and unlock.

    fn try_lock_usage_queues(&mut self, task: Task) -> Option<Task> {
        let mut blocked_usage_count = ShortCounter::zero();

        for context in task.lock_contexts() {
            context.with_usage_queue_mut(&mut self.usage_queue_token, |usage_queue| {
                let lock_result = usage_queue
                    .prepare_lock(&mut self.count_token, &task, context.requested_usage)
                    .and_then(|()| usage_queue.try_lock(&task, context.requested_usage));
                if let Err(()) = lock_result {
                    blocked_usage_count.increment_self();
                    let usage_from_task = (context.requested_usage, task.clone());
                    usage_queue.push_blocked(usage_from_task);
                }
            });
        }

        // no blocked usage count means success
        if blocked_usage_count.is_zero() {
            Some(task)
        } else {
            task.set_blocked_usage_count(&mut self.count_token, blocked_usage_count);
            None
        }
    }

    fn unlock_usage_queues(&mut self, task: &Task) {
        for context in task.lock_contexts() {
            context.with_usage_queue_mut(&mut self.usage_queue_token, |usage_queue| {
                let mut newly_lockable = usage_queue.unlock(task, context.requested_usage);
                while let Some((lockable_usage, lockable_task)) = newly_lockable {
                    usage_queue
                        .try_lock(&lockable_task, lockable_usage)
                        .unwrap();

                    // When `try_unblock()` returns `None` as a failure of unblocking this time,
                    // this means the task is still blocked by other active task's usages. So,
                    // don't push task into unblocked_task_queue yet. It can be assumed that every
                    // task will eventually succeed to be unblocked, and enter in this condition
                    // clause as long as `SchedulingStateMachine` is used correctly.
                    if let Some(unblocked_task) = lockable_task.try_unblock(&mut self.count_token) {
                        self.unblocked_task_queue.push_back(unblocked_task);
                    }

                    // Try to further schedule blocked task for parallelism in the case of readonly
                    // usages
                    newly_lockable = matches!(lockable_usage, RequestedUsage::Readonly)
                        .then(|| usage_queue.pop_lockable_readonly())
                        .flatten();
                }
            });
        }
    }
