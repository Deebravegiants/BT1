## Finding: Webhook `shop` identity is not bound to the HMAC-authenticated payload

### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value used downstream to identify the tenant is read directly from an HTTP header that is *not* included in the signed material. This breaks the equality that host applications implicitly rely on: `shop asserted by HMAC == shop used for tenant-scoped processing`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC using the app's single, shop-independent `client_secret` over `to_signable_string` (i.e. the body only): [3](#0-2) 

`Registry.process` then trusts this validation and forwards `request.shop` — taken straight from the unauthenticated header — to the handler as the tenant identifier: [4](#0-3) 

Because the app's `client_secret` (and thus the HMAC key) is identical for every shop that has installed the app, any legitimate merchant that receives a genuine, validly-signed webhook for their own shop can capture the `raw_body` + `hmac-sha256` header pair and replay it to the same endpoint while substituting an arbitrary `shop-domain` header value (e.g. a victim shop). `HmacValidator.validate` will still succeed, because it only checks that the body was signed with a secret it knows, but never checks that the header-supplied shop matches the shop the payload was actually generated for.

### Impact Explanation
This allows an unprivileged internet user who is merely a legitimate merchant of the app on shop A to make the gem attribute a forged/replayed webhook event to a different shop B. Any host application that follows the gem's documented `WebhookMetadata.shop` for tenant-scoped side effects (e.g. looking up the session/store for shop B and updating its data based on the replayed body) will process cross-tenant data under the wrong tenant's identity — a cross-tenant access/data-confusion condition rooted entirely in this gem's `HmacValidator`/`Webhooks::Request` design, since the gem is the one asserting `shop` as a trustworthy, HMAC-validated field via `Registry.process`.

### Likelihood Explanation
Requires only: (1) being a legitimate/unprivileged merchant with any topic subscription that yields a predictable/replayable body (or simply capturing one's own legitimate webhook traffic), and (2) sending an HTTP POST to the app's webhook endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged access is needed — the attacker only needs a webhook they legitimately received.

### Recommendation
Include the `shop` (and `topic`/`webhook_id` if used for authorization decisions) in the HMAC-signed material, or independently verify that the header-supplied `shop` matches an expectation bound to the request (e.g. via a per-shop secret, or by validating the shop domain appears consistently in the payload itself before it is exposed as `WebhookMetadata.shop`). At minimum, document prominently that `request.shop` is **not** authenticated by the HMAC check and must not be used as a sole tenant-selection key without additional verification.

### Proof of Concept
1. App is installed on Shop A (attacker-controlled) and Shop B (victim), sharing the same app `client_secret`.
2. Attacker receives a legitimate Shopify webhook for Shop A: raw body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` (only checks body vs `H`) — see [5](#0-4) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, so the host application processes Shop A's replayed event data under Shop B's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
