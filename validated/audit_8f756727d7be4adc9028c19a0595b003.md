### Title
Unchecked length truncation and arithmetic overflow in Pharos BLS string-slot decoding causes an unrecoverable panic reachable from a single relayed consensus proof - ([File: modules/consensus/pharos/verifier/src/state_proof.rs])

### Summary
The Pharos consensus-client's validator-set state proof decoder derives a "string length" for the on-chain BLS public key field directly from an attacker/relayer-supplied storage value, using `U256::low_u64()` truncation and unchecked `usize` addition before allocating a buffer sized by that length. This mirrors the FreeType bug class described in the report: an untrusted length value is narrowed/mis-widened and used in arithmetic that can wrap or mismatch, producing a buffer whose size is inconsistent with the amount of data subsequently processed against it.

### Finding Description
`bls_data_slots_from_header` and `decode_bls_key_from_string_slot` in `modules/consensus/pharos/verifier/src/state_proof.rs` compute a "long string" length from a raw 256-bit storage value supplied as part of `ValidatorSetProof.storage_values`: [1](#0-0) 

```

...
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
Ok((str_len + 31) / 32)
```

and, in `decode_bls_key_from_string_slot`: [2](#0-1) 

`length.low_u64()` silently discards any bits above bit 63 of a full `U256` value with no check that the upper 192 bits are zero. A legitimate Solidity string length never needs more than 64 bits, so a value that has been faithfully derived should already fit; instead of validating this invariant, the code truncates. `str_len` is then used both to size `Vec::with_capacity(str_len)` at line 258 and, separately (in `bls_data_slots_from_header`), fed into `(str_len + 31) / 32` computed as plain `usize` arithmetic with no `checked_add`/`saturating_add`. If a crafted 256-bit storage value causes `str_len` to be near `usize::MAX`, `str_len + 31` overflows: in a `panic=abort`/WASM runtime (the default for Substrate release builds, where `overflow-checks` is normally disabled) this silently wraps to a tiny `slots_needed`, while the earlier `Vec::with_capacity(str_len)` call (still using the un-wrapped huge `str_len`) triggers Rust's built-in "capacity overflow" panic. This value enters the decoder from `ValidatorSetProof::storage_values`, which is attacker-supplied input carried in the unsigned consensus update message processed by `verify_validator_set_proof` → `decode_validator_set_from_storage` → `bls_data_slots_from_header`/`decode_bls_key_from_string_slot`: [3](#0-2) [4](#0-3) 

Note that the header value is only checked to fit into 32 padded bytes when it is verified against the trie in `verify_all_storage_proofs`, i.e. the parsing/`low_u64()` truncation and the subsequent `Vec::with_capacity` sizing happen inside `decode_validator_set_from_storage`, which is invoked before or independently of a full byte-exact validation of the "reasonable string length" invariant — the code never asserts that bits 64..256 of the header value are zero, so any 32-byte value with those upper bits set will still parse without an explicit rejection prior to reaching the capacity/arithmetic step.

### Impact Explanation
Unlike FreeType's C heap corruption, Rust's built-in bounds/allocation checks generally convert this class of bug into a hard `panic!`/abort rather than silent memory corruption. However, Substrate WASM runtimes cannot unwind panics — a panic inside consensus-client verification logic invoked from `pallet-ismp`'s unsigned extrinsic dispatch path aborts execution of that block for every node that tries to process it. Because the state root and validator-set proof arrive via an unsigned, permissionlessly-relayable consensus update message, a single malicious relayer can craft this payload and have it processed by all collators/validators executing that block, producing a deterministic, network-wide halt on that message rather than a graceful proof-rejection — i.e., "a route unable to deliver messages" in the worst case, or a full node crash on the Pharos consensus-client path if invoked in the runtime's state-transition logic.

### Likelihood Explanation
Medium-to-High: the attacker must get a crafted "header" storage value to satisfy the merkle/state proof check in `verify_all_storage_proofs`, which normally binds `storage_values` to genuine on-chain state. If the underlying Pharos staking contract allows any influence over the raw bytes written to the BLS-public-key string slot (e.g., a permissionless-validator-registration write path that does not itself enforce the Solidity string invariant on write), an attacker-controlled validator registration could plant the malicious raw value once, after which any relayer (malicious or not) submitting the corresponding proof triggers the crash deterministically.

### Recommendation
- Reject any header value whose upper 192 bits (`length.0[1..]` / anything beyond `low_u64()`) are non-zero before using `low_u64()`, instead of silently truncating.
- Replace unchecked `str_len + 31` with `checked_add`/`saturating_add` and propagate an `Error` on overflow instead of proceeding.
- Cap `str_len` against a small sane maximum (e.g. 128 bytes, matching the expected 96/98-character BLS key encoding) before calling `Vec::with_capacity`.
- Ensure any panic-capable path in a consensus-client crate used by `pallet-ismp`'s unsigned dispatch returns a `Result`/`Err` instead of allocating or panicking on attacker-controlled sizes.

### Proof of Concept
Not independently executable from the index alone (would require constructing a Pharos storage proof); the following pseudo-flow demonstrates the trigger, subject to the caveat above about needing the underlying staking-contract state to actually contain the crafted bytes:
1. Get (or place, if the staking contract's write path allows it) a raw 32-byte value at the validator's `blsPublicKey` string-header slot where bit 0 = 1 (marks "long string") and bits 64..256 are non-zero, e.g. `0xFFFFFFFF_FFFFFFFF_00000000_00000000_....._01`.
2. Submit a `ValidatorSetProof` whose `storage_values` include this raw value along with a valid trie inclusion proof for it (as produced honestly by the chain).
3. Have the proof relayed as part of an unsigned consensus-update extrinsic to `pallet-ismp`.
4. `decode_validator_set_from_storage` → `bls_data_slots_from_header` computes `str_len` via truncated `low_u64()`, and `decode_bls_key_from_string_slot`'s `Vec::with_capacity(str_len)` panics with "capacity overflow", aborting the runtime call on every node processing that block. pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
```rust
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
```
