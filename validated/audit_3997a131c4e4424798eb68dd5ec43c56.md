## Finding

### Title
Omni Bridge withdrawal status/hash misreport due to unvalidated array-index matching - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal()` selects the transfer record to report on purely by numeric array index into the response of `omniBridgeAPI.getTransfer({ transactionHash })`, without validating that the entry actually corresponds to the withdrawal being described (no check against `destinationAddress`, asset/token, or amount). The exact same bug class was previously identified and fixed for the sibling `PoaBridge` implementation, but the fix was never applied to `OmniBridge`.

### Finding Description
In batch withdrawals, a single NEAR intent transaction can contain multiple withdrawal legs routed through the same bridge. `createWithdrawalIdentifiers()` assigns each leg a sequential `index` per bridge route [1](#0-0) , and `OmniBridge.createWithdrawalIdentifier()` just carries that `index` through unchanged [2](#0-1) .

`describeWithdrawal()` then does:
```
const transfer = (await this.omniBridgeAPI.getTransfer({ transactionHash: args.tx.hash }))[args.index];
```
and, once `transfer.recipient` is non-null, unconditionally returns `{ status: "completed", txHash }` derived from that record [3](#0-2) . There is no comparison of `transfer.recipient` against `args.withdrawalParams.destinationAddress`, nor of the transferred asset against `args.withdrawalParams.assetId`.

Compare this to `PoaBridge.describeWithdrawal()`, which explicitly documents and works around the fact that indexer responses are unordered:
```
// Response list is unsorted, so we match by assetId instead of index
const withdrawal = findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId);
``` [4](#0-3) . The project's own `CHANGELOG.md` records this as a fixed regression: "Fix POA bridge withdrawal matching to use assetId instead of index" [5](#0-4) , and a dedicated regression test locks in assetId-based matching for PoA [6](#0-5) . `OmniBridge` has no equivalent test or safeguard — its own test suite only ever exercises single-transfer arrays at index 0 [7](#0-6) , never a multi-leg batch where the indexer's array order could differ from submission order.

### Impact Explanation
`describeWithdrawal()`'s reported `{status, txHash}` is the trust boundary integrators rely on to mark a withdrawal complete and release credit/refund (documented as the "source of truth" for the withdrawal outcome, see `WithdrawalStatus` doc comment) [8](#0-7) , and it feeds directly into `watchWithdrawal()` and the SDK's batch completion promises used by `sdk.processWithdrawal()` / `createWithdrawalCompletionPromises()` [9](#0-8) [10](#0-9) . If the Omni Bridge indexer returns transfers for a multi-leg NEAR transaction in an order that does not match submission order (the exact condition the PoA fix addressed), leg *N*'s status query can be satisfied by a different leg's completed transfer and destination `txHash`. This breaks the equality "status/hash reported == on-chain outcome for the requested withdrawal," matching the "a status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
This requires no privileged action by the attacker or operator — it is triggered purely by the Omni Bridge indexer returning array order different from submission order for a batch withdrawal transaction, a condition the codebase already acknowledges can occur (per the PoA "unsorted" comment/fix) and that is entirely outside the caller's control. Any integrator using batch withdrawals through Omni Bridge is exposed.

### Recommendation
Match the returned transfer to the specific withdrawal leg using invariant identifying fields (destination address/recipient, asset/token, and amount) rather than raw array index — mirroring the fix already applied to `PoaBridge.describeWithdrawal()` via `findMatchingWithdrawal()`. At minimum, assert `transfer.recipient` corresponds to `args.withdrawalParams.destinationAddress` (chain-normalized) before treating a transfer as the match for that `index`.

### Proof of Concept
1. Submit a batch withdrawal intent with two Omni Bridge legs in one NEAR transaction: leg 0 → address A (asset X), leg 1 → address B (asset Y).
2. Assume/mock `omniBridgeAPI.getTransfer({transactionHash})` returning the two transfers in reversed order relative to submission (as already documented as possible for the sibling PoA API).
3. Call `describeWithdrawal` for `index: 0` (expected: leg to address A). Because indexing is positional only, it receives the transfer for leg 1 (address B) instead, and since `transfer.recipient != null`, it returns `{status: "completed", txHash: <B's tx>}`.
4. An integrator watching leg 0 sees it "completed" with B's destination hash — crediting/reconciling the wrong outcome — while the still-pending leg for A is separately reported at `index: 1` using A's actual data, or vice versa, corrupting the completion record for both legs.

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };

/**
 * Represents the current state of a withdrawal as returned by bridge adapters.
 *
 * Error handling follows AWS SDK "describe" API patterns:
 * - **Thrown errors**: Infrastructure failures (network, auth, service unavailable).
 *   Meaning: "I couldn't check the status."
 * - **`failed` status**: Job-level failure reported by the bridge.
 *   Meaning: "I checked, and the withdrawal failed."

 */
export type WithdrawalStatus =
	| { status: "pending" }
	| { status: "completed"; txHash: string | null }
	| { status: "failed"; reason: string };

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
