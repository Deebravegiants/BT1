### Title
Unchecked arithmetic panics in pnl accounting can permanently brick Deposit/Withdraw/WithdrawPnl - (File: program/src/processor.rs)

### Summary
The GPAC CVE describes an unhandled NULL-pointer dereference reachable from a crafted/malformed input that aborts processing with no graceful error path. The closest reachable analog in this program is the pnl-accounting code path shared by `process_deposit`, `process_withdraw` and `process_withdrawpnl`, where several `checked_sub`/`checked_mul` results are resolved with bare `.unwrap()` instead of being propagated as a `ProgramError`. Because the values being subtracted are derived from pool state that a normal, unprivileged account can influence (direct SPL transfers into the AMM vaults, which are plain token accounts), a crafted pool state can make these subtractions underflow, causing a Rust panic that aborts the transaction — the same "unhandled crash on attacker-influenced data" bug class as the CVE, but manifesting as a Solana program panic rather than a C NULL dereference.

### Finding Description
`Processor::calc_take_pnl` computes pnl deltas using several `.unwrap()`-guarded operations on values derived from `target.calc_pnl_x`/`calc_pnl_y` (persisted in `TargetOrders`) and the *live* vault balances passed in as `x1`/`y1`: [1](#0-0) 

Notably `x1.checked_sub(x2).unwrap()` and `y1.checked_sub(y2).unwrap()` at: [2](#0-1) 

and the pnl bookkeeping in `process_withdraw`, which also uses bare `.unwrap()` instead of returning `AmmError`: [3](#0-2) 

`x1`/`y1` are the normalized, live vault balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) coming from `calc_total_without_take_pnl_no_orderbook`: [4](#0-3) 

`amm_coin_vault_info`/`amm_pc_vault_info` are ordinary SPL token accounts owned by the AMM authority PDA; their `amount` field can be increased by *anyone* sending tokens directly to them via `spl_token::instruction::transfer`, entirely outside of the `Deposit` instruction. This does not go through any AMM-side validation of proportional invariants. Because `target.calc_pnl_x`/`calc_pnl_y` are persisted from the *previous* call and not re-derived, a sequence of (1) an unprivileged direct token transfer into a vault followed by (2) a `Withdraw`/`Deposit`/`WithdrawPnl` call can produce values where `x1 < x2` or where the second `checked_sub` in `process_withdraw` underflows, causing an immediate panic instead of the intended `Err(AmmError::CalcPnlError)`/`Err(AmmError::CheckedSubOverflow)` path that exists elsewhere in the same file (e.g. `calc_total_without_take_pnl_no_orderbook` correctly uses `.ok_or(...)`, showing the intended error-handling pattern that was not applied consistently to `calc_take_pnl` and the withdraw pnl update).

Because `target.calc_pnl_x`/`calc_pnl_y` and `amm.state_data.need_take_pnl_*` are durable on-chain state that do not self-correct, once the pool enters this state, every subsequent `Deposit`, `Withdraw`, and `WithdrawPnl` call re-executes the same arithmetic and panics again, permanently bricking those instructions for the pool (LP tokens can no longer be redeemed and swap-derived pnl can never be withdrawn), which is a permanent freeze of user/LP funds.

### Impact Explanation
A pool that is pushed into this arithmetic state can no longer process `Deposit`, `Withdraw`, or `WithdrawPnl` — every call panics on-load before any state mutation, so there is no way for the AMM owner or LPs to self-heal the corrupted `target_orders`/`amm` fields through the public instruction set. LP funds already deposited become permanently unrecoverable, and the pool owner permanently loses the ability to collect pnl fees. This matches the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
The precondition — an unprivileged party moving the ratio between live vault balances and the persisted `calc_pnl_x`/`calc_pnl_y` targets far enough to trigger underflow — requires only a plain SPL token transfer to the vault token accounts (no signer authority over the AMM program is needed) followed by any of the three affected instructions in a single subsequent transaction. This is reachable with attacker-chosen accounts/data from a single submitted transaction, matching the required threat model, though the precise numeric conditions needed depend on the pool's fee ratios and current pnl deltas, so it is not trivially triggerable on every pool state.

### Recommendation
Replace the bare `.unwrap()` calls in `Processor::calc_take_pnl` (program/src/processor.rs:190-226) and in the `target_orders.calc_pnl_x`/`calc_pnl_y` update inside `process_withdraw` (program/src/processor.rs:1818-1838) with `checked_*` combinators that propagate a proper `AmmError` (consistent with the pattern already used in `Calculator::calc_total_without_take_pnl_no_orderbook`), so malformed/adversarial pool states fail the instruction gracefully instead of panicking and permanently bricking the account.

### Proof of Concept
1. Create a pool via `Initialize2` and perform normal `Deposit`/swap activity so `target_orders.calc_pnl_x`/`calc_pnl_y` and `amm.state_data.need_take_pnl_*` are populated.
2. As any unprivileged account, submit an `spl_token::instruction::transfer` (or `sync_native`) directly into `amm_coin_vault`/`amm_pc_vault` to skew the live vault balance relative to the pool's tracked pnl baseline, without going through `Deposit`.
3. Submit a `Withdraw` (or `Deposit`/`WithdrawPnl`) instruction; `x1`/`y1` computed from the now-skewed vault balances combined with the stale `target.calc_pnl_x`/`calc_pnl_y` can cause `x1.checked_sub(x2).unwrap()` in `calc_take_pnl`, or the `checked_sub(...).unwrap()` chain in `process_withdraw`, to underflow and panic.
4. Because the underlying persisted state (`target_orders`, `amm.state_data`) is unchanged by the aborted transaction, every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call reproduces the same panic, permanently freezing the pool's LP funds and pnl.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
