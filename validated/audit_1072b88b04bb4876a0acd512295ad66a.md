### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted by handlers but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking that `OpenSSL::HMAC.hexdigest(secret, raw_body)` matches the `X-Shopify-Hmac-Sha256` header, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers. None of those header fields are part of the signed material, so the identity binding "the HMAC-verified sender == the shop/topic the handler is told to act on" does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the raw body) and secret-compares it against the received HMAC: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.topic` and `request.shop` — values that were never covered by the signature — to route the request and to construct `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality the code implicitly assumes is:
`shop_header == shop_authenticated_by_HMAC`

but in reality:
`shop_authenticated_by_HMAC == raw_body_authenticated_by_HMAC` (headers are excluded)

Because the HMAC secret (`Context.api_secret_key`) is identical for every shop that installs the app, any party that has ever received one legitimately signed webhook body (e.g., because they are a genuine merchant/user of the app) possesses a valid `(raw_body, hmac)` pair. They can resend that exact body to the same endpoint while substituting arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header values — the signature check in `HmacValidator.validate` will still pass, since it only rehashes `raw_body`.

### Impact Explanation
Applications built on this SDK are expected to key data/session lookups and business logic off `WebhookMetadata#shop` and `#topic`, since those are the only shop/topic values the SDK exposes on an already-"validated" webhook. An attacker who possesses one valid signed payload (e.g., from their own shop's webhook traffic) can cause the handler to execute with a spoofed `shop` value belonging to a different tenant, or under a different `topic` than what was actually signed, leading to cross-tenant data attribution/processing. This matches the "cross-tenant access" class of Critical-impact issues.

### Likelihood Explanation
The attacker needs a genuine `(body, hmac)` pair, which is trivially obtainable by any actual (even trial/free) installer of the target app — no leaked secret or privileged access is required, only observation of one's own legitimately delivered webhook. Replaying it with different headers to the app's public webhook endpoint is a standard unauthenticated HTTP request.

### Recommendation
Bind the trust-relevant headers into the signed material actually verified, or otherwise re-derive/verify `shop` and `topic` independently of client-supplied headers (e.g., by requiring the caller to supply and separately verify shop/topic as part of a canonical signed string, similar to how `AuthQuery#to_signable_string` includes `shop` in the OAuth HMAC computation). At minimum, document that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. As a legitimate (even free-tier) merchant, install the app and let Shopify deliver a real webhook, e.g., `orders/create`, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both are visible to the receiving app; an attacker who controls a test integration/logging endpoint upstream of `ShopifyAPI::Webhooks::Registry.process` can capture these).
2. Re-POST the identical body `B` and header `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or change `X-Shopify-Topic` to a different registered topic.
3. `HmacValidator.validate` in [3](#0-2)  recomputes the HMAC over `raw_body` only, so it matches `H` regardless of the modified headers.
4. `Registry.process` in [4](#0-3)  proceeds to invoke the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen topic, even though neither value was ever authenticated.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
