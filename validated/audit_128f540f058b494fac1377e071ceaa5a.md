## Analysis

The CVE's bug class is a proprietary, unvalidated parameter that triggers a sensitive automatic action (attaching arbitrary local content) with no authorization/consent check on the party performing that action. The closest reachable analog in Hyperbridge is the shared `CallDispatcher` contract used by `IntentGatewayV2`/`ExtrinsicIntents` and the `HyperFungibleToken*` apps for "calldata execution" — its `dispatch()` entrypoint has no access control at all, and the callers that route funds through it do so via a two-step "dispatch, then sweep" pattern within the same transaction. [1](#0-0) 

### Title
Unrestricted `CallDispatcher.dispatch()` allows draining transiently-held funds via reentrant calls - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with no caller restriction and no reentrancy guard [2](#0-1) . It is a single shared singleton (`_params.dispatcher` in `IntentGatewayV2`/`ExtrinsicIntents`, `_dispatcher` in `HyperFungibleToken*`) that transiently holds escrowed inputs, order outputs, or minted tokens between the moment assets are transferred to it and the moment the caller "sweeps" the residual balance back out.

### Finding Description
In `IntentGatewayV2`/`ExtrinsicIntents`, predispatch and postdispatch flows transfer user/solver funds to the dispatcher, invoke `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` or `dispatch(order.output.call)`, and only afterward compute balances and sweep them back via a second `dispatch(...)` call with transfer calldata: [3](#0-2) [4](#0-3) 

Similarly, `HyperFungibleToken*.onAccept` mints/unlocks tokens to `to` (which can be the dispatcher itself) and then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`: [5](#0-4) 

Because `dispatch()` performs `to.call{value: call.value}(call.data)` with a caller-supplied `to`/`data` pair and no `onlyOwner`/allow-list check, and because `to` can be any contract with code (including one controlled by the attacker, or a malicious/ERC777-style token with transfer hooks), an attacker can arrange one of the `Call` targets executed inside `dispatch()` (e.g., a malicious token used as an order input/output, or a malicious router in `order.predispatch.call`/`order.output.call`) to reenter `CallDispatcher.dispatch()` itself before the legitimate sweep step runs. That reentrant call can instruct the dispatcher to transfer out whatever balance it is currently holding — the escrowed order inputs, the solver's output tokens, or minted HFT tokens — to an attacker-controlled address, since the dispatcher has no notion of "whose funds these are" and no reentrancy guard.

### Impact Explanation
Because the `CallDispatcher` is shared across all orders/messages routed through `IntentGatewayV2`, `ExtrinsicIntents`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, and it never verifies the caller of `dispatch()`, an attacker who controls a call target reachable from `order.predispatch.call`, `order.output.call`, or an HFT `Message.data` payload can hijack the two-phase "dispatch-then-sweep" pattern to redirect in-flight escrowed funds (input tokens, solver-provided outputs, minted/unlocked HFT tokens) to themselves. This is concrete theft of funds reachable by an ordinary, unprivileged intent placer/solver or message sender — no admin/governance/relayer privilege is required.

### Likelihood Explanation
Likelihood is high for any integration that allows placing orders/messages with attacker-chosen call targets (e.g., `order.predispatch.call`, `order.output.call` in `IntentGatewayV2`/`ExtrinsicIntents`, or `SendParams.data` in `HyperFungibleToken*`) that touch tokens with transfer hooks (ERC777, or custom tokens with `onTokenReceived`-style callbacks) or route through external protocols like Uniswap routers that can be coerced into calling back into the transaction. Since `CallDispatcher.dispatch()` is unrestricted, any contract that can be named as a `Call.to` target effectively gets an opportunity to call `dispatch()` again mid-flow.

### Recommendation
Add access control to `CallDispatcher.dispatch()` so it can only be invoked by the specific app contract(s) that are supposed to own the transiently-held funds (e.g., an `onlyCaller`/allow-listed-caller pattern configured per deployment), and/or add a reentrancy guard to `dispatch()` so it cannot be re-entered while a previous `dispatch()` call for the same order/message is still executing. Consider also scoping dispatcher usage per-order (ephemeral dispatcher/proxy) rather than a single global shared singleton, so unrelated funds can never coexist in the same contract instance.

### Proof of Concept
1. Attacker crafts an `Order` for `IntentGatewayV2.placeOrder`/`fillOrder` (or `ExtrinsicIntents`) whose `output.call` (or `predispatch.call`) includes a `Call` to a malicious ERC20-like token contract that the attacker controls.
2. When `_execute` calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` [6](#0-5) , the malicious token's `transfer`/hook callback re-enters and calls `CallDispatcher.dispatch(encoded)` directly with `encoded` describing a transfer of the dispatcher's current token/ETH balance to the attacker's address.
3. Because `CallDispatcher.dispatch()` has no caller restriction [2](#0-1) , this reentrant call succeeds and drains the dispatcher's balance before the legitimate sweep in `_execute` runs.
4. The legitimate sweep subsequently finds a reduced (or zero) balance, and the order's rightful beneficiary/solver receives less than expected while the attacker walks away with the diverted funds.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        ICallDispatcher(dispatcher).dispatch(order.output.call);
