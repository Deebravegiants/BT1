### Title
Excess native-token overpayment to `EvmHost.dispatch()`/`fundRequest()` is refunded to the host contract instead of the caller and becomes permanently stuck - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap it via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard `UniswapV2Router02.swapETHForExactTokens` implementation refunds any unused (dust) ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Since `EvmHost` itself is the caller of the router (not the original transaction sender), that dust refund lands back on `EvmHost`, not on the user who originally overpaid. `EvmHost` has no logic afterward to forward this leftover ETH back to the caller, and no withdrawal path exists for stray native ETH balance, so any overpayment above the exact swap cost is permanently trapped in the contract.

### Finding Description
In `dispatch(DispatchPost memory post)`:
```solidity
// evm/src/core/EvmHost.sol:921-932
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}

The identical pattern is repeated in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` only requires `amounts[0] <= msg.value` (the exact input to reach the requested `amountOut`); any surplus `msg.value` is by design refunded by the router to its immediate caller, which in this call chain is `EvmHost` (`msg.sender` from the router's perspective), since `EvmHost` itself invokes the router with `{value: msg.value}`. There is no code in `EvmHost` after the `swapETHForExactTokens` call that captures this refund and forwards it to `_msgSender()` (the actual dispatcher/user who sent the overpayment). No `receive()`/fallback accounting or subsequent sweep-to-caller logic exists in `EvmHost.sol` for native ETH. Because callers frequently cannot predict the exact router execution price at call time (slippage, pool state changes between quote and execution), sending a safety margin of native token — exactly the documented pattern shown in Hyperbridge's own docs (`docs/content/developers/evm/messaging/post-requests.mdx`, "Native Token" payment flow) and exercised in `IntentGatewayV2Test.sol`'s `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` — is a normal calling pattern. Unlike `IntentGatewayV2.sol`, which explicitly tracks `msgValue -= amounts[0]` and refunds the remainder to the caller (`evm/src/apps/IntentGatewayV2.sol:377-397`), `EvmHost.sol`'s dispatch/fundRequest paths never track or forward the router's refund, causing the overpaid ETH to be absorbed by and stuck in the host contract.

This is directly analogous to the keep-tecdsa finding: value sent by an unprivileged caller beyond what is strictly consumed by the intended operation is not tracked/returned and is effectively burned/frozen in the contract, with no governance or admin path shown in `EvmHost.sol` to recover stray native ETH.

### Impact Explanation
Any unprivileged caller of `EvmHost.dispatch()` (POST or GET) or `fundRequest()` who sends `msg.value` greater than what the Uniswap swap actually consumes permanently loses the difference — it becomes native ETH balance on `EvmHost` with no mechanism to withdraw or credit back to the sender. This is a direct, reachable loss-of-funds vector for any application or end user dispatching messages with native-token payment (the documented and tested primary payment method for `dispatch`), and can occur on every single dispatch call where the caller doesn't send the exact minimal amount (which is effectively unknowable in advance for callers using conservative slippage/safety buffers, exactly as demonstrated by Hyperbridge's own IntentGatewayV2 tests needing explicit refund logic to solve the same problem). This is a Medium-High severity permanent freezing/loss-of-funds bug affecting the primary message-dispatch entrypoint.

### Likelihood Explanation
High likelihood: sending `msg.value` with headroom above the exact expected swap input is a normal, encouraged usage pattern (as shown by Hyperbridge's own SDK/documentation guidance and IntentGatewayV2's analogous test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, where 5 ETH is sent for a swap costing far less). Every caller using native-token payment without computing the exact router quote at the same block will overpay to some degree, making fund loss the common case rather than an edge case.

### Recommendation
Track the actual amount consumed by `swapETHForExactTokens` (its `amounts[0]` return value) in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund the difference (`msg.value - amounts[0]`) to `_msgSender()`, following the same pattern already implemented in `IntentGatewayV2.sol` (`msgValue -= amounts[0]; ... _sendValue(msg.sender, msgValue);`).

### Proof of Concept
1. Caller A calls `EvmHost.dispatch{value: 5 ether}(post)` with `post.fee` requiring only 0.01 ETH worth of the fee token via the configured Uniswap V2 pool.
2. `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` executes, consuming ~0.01 ETH worth of ETH and refunding the remaining ~4.99 ETH via `TransferHelper.safeTransferETH(msg.sender, ...)`, where `msg.sender` (from the router's perspective) is `EvmHost`.
3. `EvmHost`'s balance increases by ~4.99 ETH; the function proceeds to emit `PostRequestEvent` and returns, with no logic to forward the ~4.99 ETH back to caller A.
4. Caller A has permanently lost ~4.99 ETH, and `EvmHost` has no exposed function to withdraw stray native ETH back to any account.
