### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while `x-shopify-shop-domain` (and `topic`, `webhook-id`, `api-version`) are read directly from unauthenticated headers. `Registry.process` verifies only the body HMAC and then forwards the untrusted `shop` header value straight to the app's webhook handler as the trusted tenant identity, breaking the binding `hmac-authenticated bytes == request.shop`.

### Finding Description
The verification flow is:
1. `Request#to_signable_string` returns `@raw_body` exclusively — no header, including `shop`, is folded into the signed string [1](#0-0) .
2. `HmacValidator.validate_signature` recomputes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the received `hmac` header, so it only proves "this exact body was signed with `api_secret_key`" — it makes no statement about which shop the body belongs to [5](#0-4) .
3. `Registry.process` gates entirely on that body HMAC, then builds `WebhookMetadata` using `request.shop`, which is read straight off the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload [3](#0-2) , [6](#0-5) .

Because the `shop` value is not part of the signed material, a `(raw_body, hmac)` pair that is valid for shop A remains valid — and indistinguishable to `HmacValidator` — when replayed with the `shop` header rewritten to shop B. An attacker who installs the target app on their own store (a fully unprivileged, self-service action) legitimately receives real webhooks from Shopify for their own shop, each with a correctly signed `(raw_body, hmac-sha256)` pair. Nothing in this gem prevents that attacker from POSTing the same raw body and HMAC directly to the app's public webhook endpoint (its path is typically fixed/predictable and is not itself secret) while substituting an arbitrary `x-shopify-shop-domain` header naming a different, victim shop. `Registry.process` will accept it as valid and dispatch the handler with `data.shop` equal to the attacker-chosen victim shop, alongside attacker-controlled `data.body` content (since the attacker can also shape the body of their own genuine webhook to some degree, e.g. by editing a resource's title on their own store, or by choosing which webhook topic/resource to trigger). Any app logic that uses `data.shop` to select which tenant's records to create, update, or delete (the exact pattern the gem's own documentation recommends) can therefore be made to act cross-tenant, using events forged to look like they came from a shop the attacker does not control.

### Impact Explanation
This crosses the tenant boundary that Shopify's webhook signature is meant to enforce: apps are documented and expected to trust `WebhookMetadata#shop` as the authenticated origin shop for a webhook event [7](#0-6) . Since the HMAC never binds `shop` to the body, an unprivileged attacker (merely a self-service app installer on their own store) can make the gem report an event as originating from any other shop, letting them inject/forge webhook events attributed to a victim tenant. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any host app that relies on `data.shop` from `WebhookMetadata` for tenant scoping (which is exactly what the gem's own docs recommend, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). Exploitation requires no leaked secrets or elevated access — only a normal, free app installation by the attacker on their own store to harvest one legitimately signed `(body, hmac)` sample, and knowledge of the app's webhook callback URL, which is not treated as a secret.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) into the value that is HMAC-verified, or independently authenticate the shop domain, before trusting `request.shop`/`WebhookMetadata#shop`. Options include: verifying that the shop-domain header matches a shop known to have received this specific `webhook_id` from Shopify's own delivery record, or maintaining a per-shop webhook secret/subscription registry key rather than trusting the header value directly once the shared-secret body HMAC passes.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g. `products/update`) so Shopify delivers a real request to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` header for that specific raw body.
2. Capture the raw request body and the `x-shopify-hmac-sha256` value from that delivery (attacker fully controls their own server/logs receiving it).
3. Replay an HTTP POST to the same app webhook endpoint with the identical raw body and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a chosen `x-shopify-topic`/`x-shopify-webhook-id`, which are equally unauthenticated).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the raw body [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [9](#0-8) , causing the host application to process attacker-supplied data as if it originated from the victim shop.
