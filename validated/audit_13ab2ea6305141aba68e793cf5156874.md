### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` trusts the unsigned `shop`/`shop-domain` header to attribute the webhook to a specific merchant. Because `HmacValidator.validate` only proves that the *body* was signed by Shopify's shared secret and never binds that signature to the shop the webhook claims to be for, any attacker who is a legitimate installed merchant (and can therefore harvest one valid `(raw_body, hmac)` pair from their own webhook deliveries) can replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, causing the host application to process the webhook as if it belonged to a different (victim) tenant.

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and implements:
```ruby
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

`shop` is a separate accessor pulled straight from request headers, with no relationship to the signed payload:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` verifies the HMAC over the request, then unconditionally forwards `request.shop` to the handler as the tenant identity for the webhook:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC purely from `to_signable_string` (i.e., the raw body) and compares it to the header-supplied `hmac`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

The identity binding the app relies on is effectively: `hmac_valid(raw_body) == true` implies `shop header == the shop that produced this body`. That equality does not hold: the HMAC only authenticates *that Shopify produced this exact JSON body with this app's shared secret at some point*, not *which* installed shop it was for. Since the shop domain is not part of the signed bytes, any accepted `(raw_body, hmac)` pair is valid for **every** shop-domain header value.

### Impact Explanation
This breaks the tenant isolation the gem is documented to provide via `Webhooks::Registry.process`/`Utils::HmacValidator`. A malicious but legitimately-installed merchant (an unprivileged, non-credentialed external actor with respect to any other tenant) can:
1. Install the app on their own shop and receive a legitimate webhook, capturing the raw body and its valid `hmac` header (this pair is deterministic/replayable and not tied to their identity).
2. Replay that exact `(raw_body, hmac)` to the app's public webhook endpoint, substituting the `shop-domain`/`x-shopify-shop-domain` header with any other tenant's `myshopify.com` domain.
3. `Utils::HmacValidator.validate` still succeeds (it never looked at the shop header), so `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the victim shop and the attacker-controlled body content.

Because host applications are documented to trust `data.shop` from `WebhookMetadata` as the authoritative tenant identity (see `docs/usage/webhooks.md`), this allows cross-tenant data injection/corruption (e.g., forcing app-uninstalled/app-installed lifecycle events, fake order/product/customer updates, or other business logic tied to shop identity) without any credentials belonging to the victim shop — a cross-tenant access violation.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action, no special access needed) can trivially capture one valid webhook body+HMAC pair from their own store's webhook deliveries (e.g. via `orders/create`, `app/uninstalled`, etc.) and replay it with a forged shop header using any HTTP client. No secret key, access token, or privileged access is required — only the ability to receive one webhook for their own shop and then send an HTTP POST to the app's public webhook URL.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified, or independently authenticate the shop header against the verified webhook. Concretely:
- Include the `shop-domain` header value inside `Webhooks::Request#to_signable_string` (or otherwise cryptographically bind header and body together) so that `HmacValidator.validate` fails if the shop header is altered relative to what Shopify signed.
- Alternatively, since Shopify does not itself sign the shop-domain header value together with the body, the gem should not expose `request.shop` as a trusted identity without documenting to consumers that it is unauthenticated, and should instead recommend/require correlating the webhook against a known registered shop/session before trusting it.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_app_secret",
  host_name: "app.example.com",
  scope: "read_products",
  is_embedded: true,
  api_version: "2024-01",
)

# Step 1: attacker installs the app on their own shop "attacker.myshopify.com"
# and Shopify legitimately delivers a webhook for it.
raw_body = '{"id":123,"note":"hi"}'
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key,
  raw_body,
)

# Step 2: attacker replays the exact same body+hmac, but swaps the shop-domain
# header to point at a victim shop they do not own/operate.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not the attacker's shop!
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation even though the shop-domain header was never signed:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
```
This demonstrates that `HmacValidator.validate(request)` returns `true` regardless of the `shop-domain` header value, because `to_signable_string` never includes it, letting the attacker attribute an arbitrary, attacker-crafted webhook body to any shop domain of their choosing.
