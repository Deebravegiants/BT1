Confirmed: `ShopifyAPI::Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`) exposes a `shop` accessor read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header [1](#0-0) , while `to_signable_string` — the value actually HMAC-verified — is only the raw request body [2](#0-1) . `Utils::HmacValidator.validate` computes the signature purely over that signable string and compares it to the `hmac` header, never touching `shop`, `topic`, `webhook_id`, or `api_version` [3](#0-2) . `Registry.process` gates entirely on that HMAC check and then forwards `request.shop` unmodified into `WebhookMetadata`, which is the tenant-identifying field host apps use to route/scope work [4](#0-3) [5](#0-4) . The documented handler pattern trusts `data.shop` directly for tenant dispatch (e.g. `perform_later(shop_domain: data.shop, ...)`) [6](#0-5) .

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, but `Registry.process` trusts the separate, unauthenticated `shop`-domain header when constructing `WebhookMetadata` for the handler. This breaks the equality "shop authenticated by HMAC == shop acted on by the handler," letting anyone who can obtain one valid `(body, hmac)` pair for a shop replay it while claiming a different shop's identity.

### Finding Description
`Request#hmac`/`#to_signable_string` is computed solely from `@raw_body` [7](#0-6) . `HmacValidator.validate_signature` recomputes the HMAC over that same signable string and compares it via `OpenSSL.secure_compare` against the `hmac-sha256` header [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled straight from HTTP headers with no cryptographic tie to the body or to each other [8](#0-7) . `Registry.process` only checks the HMAC before dispatching, then hands `request.shop` (the unauthenticated header) to the handler as the trusted tenant identifier [4](#0-3) .

Because the gem's own controller-integration pattern posts `request.headers.to_h` straight into `Request.new` [9](#0-8) , an attacker who controls the raw HTTP request to the app's webhook endpoint (which is a public, unauthenticated endpoint by design, reachable by anyone on the internet) can send any header values alongside a body/HMAC pair. If that attacker obtains one valid `(raw_body, hmac)` pair — trivially possible by installing the same app on their own shop and capturing a real webhook Shopify sends them — they can replay that exact body and HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop. `HmacValidator.validate` still returns `true`, since it never inspected the shop header, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <attacker-chosen victim domain>, ...)`.

### Impact Explanation
This crosses a tenant boundary: an authenticated-looking (HMAC-valid) webhook can be attributed to any `shop` value the attacker chooses, even though the actual signed content originated from the attacker's own store. Any host application that follows the gem's documented pattern of trusting `data.shop` to route/scope background work, upsert shop-keyed records, or invalidate/refresh per-shop state will process attacker data under another tenant's identity — a cross-tenant access primitive.

### Likelihood Explanation
Low barrier: the webhook endpoint is public and unauthenticated by design (Shopify itself calls it over plain HTTP posts). Obtaining a valid `(body, hmac)` pair requires only installing the target app on an attacker-owned/development store (a normal, no-privilege action for any user of an app that is public or has open installs), then replaying the captured request with a forged shop header.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-covered `to_signable_string` (or otherwise cryptographically bind them, e.g. by validating the shop against Shopify's HMAC-signed OAuth/session data rather than the raw header), so a captured body+hmac cannot be replayed under a different shop identity.

### Proof of Concept
1. Install the target app on an attacker-controlled/development shop `attacker.myshopify.com` and capture a legitimate webhook POST, e.g. `orders/create`, including its raw body and its valid `x-shopify-hmac-sha256` header.
2. Replay that exact body and HMAC header to the app's public webhook endpoint, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) HMAC [10](#0-9) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)` and performs whatever tenant-scoped action the app implements (e.g. queuing a job keyed by `shop_domain: data.shop`), acting on the victim shop using attacker-supplied data.
