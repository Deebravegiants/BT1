## Finding



### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `request.shop` (the tenant identifier passed to app handlers) is read from an unauthenticated header and never covered by the HMAC check performed in `Registry.process`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery` by HMAC-comparing `compute_signature(verifiable_query.to_signable_string, secret)` against the received signature: [1](#0-0) 

For `ShopifyAPI::Auth::Oauth::AuthQuery` (the OAuth callback), `to_signable_string` explicitly includes `shop` in the signed parameter set, so the shop value is cryptographically bound to the signature: [2](#0-1) 

But for `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw request body — `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are completely outside the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` object that is handed to the app's registered handler as the identity of the tenant the event belongs to: [4](#0-3) 

The equality the gem is implicitly assuming — `shop_header == shop_the_body_actually_belongs_to` — is never enforced. Because the HMAC only proves "this body byte sequence was produced with the app's secret at some point," not "this body belongs to shop X," an unprivileged user who has ever received one legitimate webhook delivery for their own shop (any merchant who installs the app can trivially obtain a valid `(raw_body, hmac)` pair from their own shop's webhook traffic) can replay that exact body+hmac pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The HMAC check still passes (it never looked at the header), and the app processes the payload as if it originated from the victim shop named in the forged header.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to establish for webhook consumers: `request.shop` is the only tenant-scoping signal `Registry.process` supplies to `WebhookMetadata`, and it is fully attacker-controlled while still passing HMAC validation. Depending on how the host application keys sessions/data by `WebhookMetadata#shop` (which is the gem's documented usage pattern, e.g. as shown in `docs/usage/webhooks.md`), an attacker can cause webhook-driven state changes, cache updates, or business logic to be applied under another merchant's tenant identity — a cross-tenant access issue.

### Likelihood Explanation
Any user who can install the app on their own store (i.e., any unprivileged Shopify merchant using the app) can capture a real `(raw_body, hmac)` pair from their own webhook deliveries without needing the app's `api_secret_key`, an access token, or any privileged account. Replaying that pair with a modified `shop-domain` header against the app's public webhook callback URL requires no special access — the endpoint is, by design, unauthenticated except for the HMAC check.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed payload verification, or otherwise cryptographically tie the header-derived tenant identity to the verified body (e.g., by including the shop domain from the header as part of the HMAC signable string, mirroring what `AuthQuery#to_signable_string` already does for OAuth), so a replayed body cannot be relabelled to a different shop.

### Proof of Concept
1. As a merchant who has installed the target app on `attacker-shop.myshopify.com`, trigger any webhook event (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged header (`lib/shopify_api/webhooks/request.rb:45-63`), and `Registry.process` validates successfully because `HmacValidator.validate` only checks the raw body (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) even though the payload actually originated from `attacker-shop.myshopify.com`, confirming the tenant-binding break.
