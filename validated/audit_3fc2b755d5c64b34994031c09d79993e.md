### Title
Webhook `shop`/`topic`/`webhook-id` headers are trusted for tenant routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop`, `topic`, `api_version`, and `webhook_id` HTTP headers to the app's handler unverified. Because the HMAC never covers these headers, any party capable of producing one valid `(body, hmac)` pair for their own shop can replay that exact body/HMAC combination while substituting an arbitrary `shop-domain` header, causing the host application to process the payload under a different, attacker-chosen tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` computes and compares the signature exclusively against `verifiable_query.to_signable_string` (i.e., only the body): [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the app's handler — with no separate validation that this header-derived shop matches the tenant whose secret validated the body: [4](#0-3) 

Since the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across *all* merchants who install the app, any merchant with the app installed can trigger events on their own store to obtain a legitimately-signed `(body, hmac)` pair, then resend that exact body and signature to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header for an arbitrary other shop domain. The signature still validates (it never covered the header), and the handler receives `WebhookMetadata` claiming to originate from the victim shop.

This breaks the identity binding: shop asserted (`request.shop`, used for tenant routing/session lookup in the handler) ≠ shop whose secret actually authenticated the bytes (there is no shop binding in the HMAC at all — only the raw body is authenticated, which is shop-agnostic).

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which merchant's stored access token/session to act on (a common and documented pattern, since `Registry.process` explicitly hands `shop` to the handler for that purpose), an attacker who is merely a user/owner of their own shop with the app installed can forge webhook deliveries that are processed under a different tenant's identity — a cross-tenant confusion/access primitive, without needing the app's `client_secret`, any merchant's access token, or any privileged access.

### Likelihood Explanation
Any of the many merchants who have installed the app can trivially generate their own valid `(body, hmac)` pairs (simply by triggering real store events), and nothing in this gem prevents replaying that pair with a substituted `shop-domain` header value against the app's public webhook endpoint. No secret material beyond what an ordinary merchant already legitimately possesses (a working, signed webhook of their own) is required.

### Recommendation
Bind the trusted identity fields into the HMAC computation (or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the signed payload), and/or require `Registry.process` to independently corroborate `request.shop` against a value obtained through an authenticated channel (e.g., the session/shop the body itself references) before it is passed to handlers as trusted routing information.

### Proof of Concept
1. Attacker owns/operates `attacker-shop.myshopify.com` with the target app installed, and receives a legitimate webhook: body `B` with header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC(secret, B)`, per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker POSTs the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B`/`H` are unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop-domain` header value `victim-shop.myshopify.com`, and invokes the app's handler with this metadata as if it genuinely originated from the victim shop.
