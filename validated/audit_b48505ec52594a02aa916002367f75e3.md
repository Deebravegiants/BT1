### Title
Webhook shop identity (`X-Shopify-Shop-Domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body; none of the trusted-looking headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) are included in the signed material. The `shop` value taken from the `x-shopify-shop-domain` header is nonetheless treated as the authoritative tenant identity and handed to the application's webhook handler.

### Finding Description
The HMAC validation binding is:
`HMAC_valid == true` should imply `body == the body Shopify actually sent for shop S`.

In this gem the equality that is actually checked is only:
`HMAC(secret, raw_body) == received_hmac`

The `shop` field is read independently and not fed into the signable string: [1](#0-0) [2](#0-1) 

The registry's `process` method verifies only the HMAC of the body, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header value and passes it to the app's handler: [3](#0-2) 

Because Shopify webhook HMACs are computed with the app's single `client_secret` (shared across every merchant that installed the app) and the signature never covers the shop-identifying header, `HMAC_valid` says nothing about *which* shop the body belongs to. An entity that has legitimately received one authentic webhook for their own store (a normal, unprivileged app-installing merchant) can capture that exact `raw_body` + `x-shopify-hmac-sha256` pair — which will remain valid forever, since it doesn't depend on the shop — and replay it to the same webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to point at a different merchant's shop domain. The `process` method's HMAC check passes unchanged, and the handler receives `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant-isolation binding that host applications rely on: `canonical_shop_of(hmac_verified_body) == request.shop`. Any application that uses `data.shop` from the webhook handler (as the gem's own documentation instructs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) to route webhook effects to a specific tenant's stored session/state can be tricked into applying attacker-supplied (their own shop's) data under a victim shop's identity — a cross-tenant data-integrity/confusion issue. Depending on the webhook topic (e.g. `app/uninstalled`, `customers/redact`, `shop/update`), this can trigger destructive or state-changing actions attributed to a shop the attacker does not control, without ever needing that shop's access token or credentials.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must already be a legitimate, if unprivileged, installer of the app to capture one genuine `(raw_body, hmac)` pair for at least one topic/body shape they can reuse, and (2) exploitation requires sending a raw HTTP POST directly to the app's public webhook endpoint with forged headers, bypassing Shopify's platform — which is straightforward once a valid body/HMAC pair is obtained, since nothing in `Registry.process` or `HmacValidator` binds the signature to the shop header.

### Recommendation
Include the shop-identifying header (and ideally topic/api-version) in the material that is HMAC-verified, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header value (mirroring how `AuthQuery#to_signable_string` includes `shop`), and/or `Registry.process` should cross-check the shop against a known/registered webhook subscription before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with:
   - body: `{"id":1,...}`
   - `x-shopify-hmac-sha256: <valid HMAC of body under app's client_secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
2. Attacker replays the exact same raw body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — this still matches, since the shop header is not part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's own order data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-controlled data as though it originated from the victim's shop.
