### Title
Accrual arithmetic overflow permanently freezes a high-value market — no repay, withdraw, or liquidation possible - (File: common/src/rates/scaling.rs)

### Summary
The bug class in the external report is an unchecked assertion (`CHECK`-fail) reachable on untrusted input that causes denial of service. The direct analog in XOXNO Lending is an arithmetic panic in `accrue_step`: `scaled_to_original(borrowed, borrow_index)` multiplies two RAY values via `Ray::mul` (`mul_div_half_up`), which panics with `GenericError::MathOverflow` when `borrowed * borrow_index` exceeds `i128::MAX`. Because `interest::global_sync` runs at the top of every pool mutation (`supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `flash_loan`, `recapitalize`, `claim_revenue`, `update_indexes`), once the market's debt value crosses the i128 value ceiling the market is permanently bricked. The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW`, and the borrow index never reaches `MAX_BORROW_INDEX_RAY` before the cliff, so the documented cap does not save it.

### Finding Description
`accrue_step` at `common/src/rates/simulate.rs:60-61` computes:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `scaled.mul(env, index)`, i.e., `mul_div_half_up(env, scaled, index, RAY)`, which widens to `I256` but then converts back via `to_i128`, panicking with `GenericError::MathOverflow` if the result does not fit `i128` (`common/src/math/fp_core.rs:108-118`, `300-303`).

The stored `borrowed`/`supplied` are scaled RAY shares, so `borrowed_original ≈ borrowed * borrow_index` grows without bound as the index compounds. `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY = 10^36` (`common/src/rates/index.rs:13-19`), but the *debt value* `borrowed * borrow_index` overflows `i128::MAX` well before the index reaches that cap for a whale-sized market — the harness test hits the cliff at roughly index ×170 on a 1-billion-token 18-decimal market, far below the cap.

`global_sync` (`contracts/pool/src/interest.rs:20-33`) is invoked unconditionally by every market mutation (the documented flow is `Cache::load → global_sync → mutate → guards → commit`, per `contracts/pool/README.md:159-168`), so the panic in `accrue_step` bricks every entrypoint touching that market, including `update_indexes` itself — the state can never be advanced past the failing step because `accrue_chunk` panics before `mark_accrued` runs. The test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-361` confirms `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW`.

### Impact Explanation
Permanent freezing of funds, satisfying the acceptance criteria. Once `borrowed * borrow_index > i128::MAX`:

- Suppliers cannot `withdraw` — every withdrawal accrues first.
- Borrowers cannot `repay` — repayment also accrues first.
- Liquidators cannot clear the now-underwater debt (`seize_positions` accrues), so positions that go unhealthy cannot be resolved, converting a freeze into eventual protocol insolvency as prices move.
- `recapitalize`, `claim_revenue`, and `clean_bad_debt`-style paths also accrue and panic, so the admin has no on-chain escape either; only an upgrade unsticks the market.
- All cash held by the pool for that `(hub, asset)` book is stuck.

The panic is triggered by ledger time advancing, not by a special call — anyone reaching the cliff first (e.g., a keeper calling `update_indexes`, or any user's `repay`) hits it, and after that every call hits it forever.

### Likelihood Explanation
Likelihood is moderate. The attack/economic path is fully unprivileged: an attacker only needs a high-decimal listed asset (e.g., 18 decimals) with lifted caps, a large supply, and a borrow at high utilization sustained over time — exactly what the harness test sets up with `xlm_curve()` at 98% utilization (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`). It requires a whale-scale principal (≈1e9 whole tokens at 18 decimals → `1e36` raw RAY units) and the steep segment of the rate curve for a few years of compounding, which is capital-heavy but feasible on a market that genuinely attracts size. Alternatively, no attacker is needed at all: any organic market that grows large enough at high utilization drifts into the cliff, since `borrow_index` grows monotonically and is never decreased. The mitigation ceiling (`MAX_BORROW_INDEX_RAY`) provably does not engage first — the test asserts `borrow_index < MAX_BORROW_INDEX_RAY` at failure.

Note on uncertainty: the test names a "bound in docs/reference/formulas.md" as wrong, suggesting the team is aware of the cliff; if this is a formally accepted ADR limitation it could be argued out of scope, but nothing in the code or docs marks it as an accepted risk — the test itself frames it as a bound violation, and the freeze is not fail-closed by design (no pause flag is set; the state is simply unrecoverable).

### Recommendation
Make the accrual arithmetic saturate rather than panic so the index cap — not the i128 ceiling — is the operative bound:

1. In `accrue_step` (`common/src/rates/simulate.rs:60-61`), compute `borrowed_original` and `supplied_original` through a saturating multiply (e.g., `mul_div_floor_saturating`-style value computation or a checked path that clamps `borrow_index` at `MAX_BORROW_INDEX_RAY` before valuation), so oversized valuations degrade to the cap instead of trapping.
2. Alternatively, short-circuit in `update_borrow_index`/`accrue_step`: once `borrow_index` hits `MAX_BORROW_INDEX_RAY`, stop accruing (the cap already implies this) — but the ordering bug is that the value multiplication happens before/at the same step the cap is applied; hoist the cap check ahead of `scaled_to_original` so a capped index yields a bounded product.
3. More fundamentally, store/compare the debt ceiling directly: enforce `borrowed * borrow_index <= i128::MAX` as a borrow-time invariant in `calculate_scaled_borrow`/`borrow` so a market can never enter the poisoned region, matching the spirit of `require_cap_within_asset_domain` used for caps (`common/src/rates/scaling.rs:20-33`).

### Proof of Concept
The in-repo harness test is already a working PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);          // 1e9 whole tokens
t.supply_raw(BOB, "BIG18", principal);             // unprivileged supply
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // unprivileged borrow @98% util

loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // eventually MathOverflow
}
// now permanently frozen:
t.try_withdraw_raw(BOB, "BIG18", 1);   // Err(MATH_OVERFLOW)
t.try_repay(ALICE, "BIG18", 1.0);      // Err(MATH_OVERFLOW)
// borrow_index still < MAX_BORROW_INDEX_RAY: the cap never engaged
```

Any unprivileged `controller.borrow`/`controller.repay`/`controller.withdraw`/`pool.update_indexes` call against the market hits the same panic inside `interest::global_sync → accrue_chunk → accrue_step → scaled_to_original`, and no call ordering can advance `last_timestamp` past the overflowing step.
