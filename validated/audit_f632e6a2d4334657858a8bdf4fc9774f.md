Confirmed: the `shop` value passed to `handler.handle` in `Registry.process` comes directly from `request.shop` (the `shopify-shop-domain` header), which is never part of the HMAC-covered signable string.### Title
Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` is computed only over the raw request body. `Registry.process` passes this unauthenticated `shop` value straight into the `WebhookMetadata` struct delivered to the host app's `WebhookHandler#handle` implementation, without ever proving that the shop that signed the payload is the same shop named in the header.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop` is read from a header that is never part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. against the body bytes alone: [3](#0-2) 

`Registry.process` checks the HMAC and then forwards the header-derived `shop` (unauthenticated) to the app's handler as if it were verified: [4](#0-3) 

The identity binding that should hold is: `shop delivered to handler == shop whose secret produced the HMAC over the payload`. Because the `shop-domain` header is outside the HMAC-covered bytes, this binding is never established by the gem — the only cryptographic guarantee is "some request signed with this app's shared secret for *some* shop produced this body." An attacker who can obtain one valid `(body, hmac)` pair for their own shop (trivial — they can install the app on a shop they control and capture a legitimate webhook), can replay that exact `raw_body` + `hmac` pair while substituting an arbitrary `shopify-shop-domain` header naming a victim shop. The signature still validates because the header is not part of `to_signable_string`, and `WebhookMetadata.shop` will report the attacker-chosen victim shop to the app's handler.

This mirrors the M-18 pattern: a check is validated over one basis (raw body / internal-precision balance) while a materially different, security-relevant field (`shop` / external-token-decimals) is treated as trusted without actually being covered by that check.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which merchant/tenant's data/session/access-token to act on (a documented and expected usage pattern per `docs/usage/webhooks.md`, since `Registry.process` is the gem's sanctioned way to authenticate and dispatch webhooks), an attacker can forge the tenant identity associated with an HMAC-genuine payload. This allows cross-tenant data confusion: writing/deleting/using data or actions under one shop's identity while the payload actually originated (and was signed) for another. Depending on how the app persists data keyed by `WebhookMetadata.shop`, this can lead to cross-tenant access — one of the qualifying Critical impacts.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate, unprivileged Shopify store to receive one real webhook (any topic they've configured) — no access token, `client_secret`, or privileged account of the victim is needed; and (2) the ability to POST an HTTP request with attacker-controlled headers to the app's public webhook endpoint, which is exactly the documented integration surface (`ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`). Because `shop` is never part of `to_signable_string`, the check that "did indeed come from Shopify" (per the gem's own doc comment) does not actually authenticate the shop field, only the body.

### Recommendation
Include the shop-identifying data in the HMAC-covered signable string (or independently verify the `shop-domain` header against a value derived from the signed payload/registered webhook subscription), so that `to_signable_string` binds `shop` to the signature the same way `AuthQuery#to_signable_string` binds `shop`, `code`, `state`, etc. for OAuth callbacks. At minimum, document prominently that `WebhookMetadata.shop` is not covered by the HMAC and must not be trusted for tenant selection, and provide/require an out-of-band shop verification (e.g., against the app's own webhook registration records) before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook, capturing `raw_body` and the valid `x-shopify-hmac-sha256` value (computed by Shopify using the app's real secret over that body).
2. Attacker POSTs to the victim app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)` — the forged shop header is irrelevant to this check: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, spoofing the victim's identity in an HMAC-"verified" webhook: [6](#0-5) 

Note: I could not fully verify from the indexed files how every downstream consumer (host apps built on top of this gem, e.g. `shopify_app`) uses `WebhookMetadata.shop` in practice, since that logic lives outside this gem's `lib/shopify_api/**` scope; the impact statement assumes the documented/intended usage of `shop` for tenant-scoped processing.
