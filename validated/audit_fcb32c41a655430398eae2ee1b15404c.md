### Title
SSRF leaking the app's `client_secret` via unvalidated `shop` domain in OAuth callback - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the POST request that exchanges the OAuth `code` for an access token using `auth_query.shop` as the request host, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling grant flows (`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) which explicitly validate the shop domain before using it to build the credential-bearing request.

### Finding Description
In `validate_auth_callback`, the code is: [1](#0-0) 

`auth_query.shop` is taken straight from the `AuthQuery` value object and used to instantiate the `null_session`, which in turn determines the host that `Clients::HttpClient` will send the POST containing `client_id`, `client_secret`, and `code` to (`https://#{shop}/admin/oauth/access_token`). The only check on the query is `Utils::HmacValidator.validate(auth_query)`, and `AuthQuery#to_signable_string` does include `shop`: [2](#0-1) 

So the HMAC binds `shop` to the app's own `api_secret_key` — this is the equality the gem relies on: *host that receives client_secret == shop bound by the HMAC*. This holds as long as the HMAC can only be produced by a party who has the app's secret. In contrast, `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` do not rely on any external HMAC to establish the destination host — they take `shop` directly as a caller-supplied parameter with no signature at all, and they compensate by calling `Utils::ShopValidator.sanitize!(shop)` before building the session/host: [3](#0-2) [4](#0-3) 

The OAuth callback path is the odd one out: it neither validates that `shop` is a `*.myshopify.com`/trusted domain via `ShopValidator`, nor does anything stop the calling application from constructing `auth_query.shop` from a source that hasn't gone through HMAC validation before this call (e.g., an app could — following the gem's own docs — build `AuthQuery` straight from `request.parameters`, and mistakenly reuse a `shop`/host value from an untrusted source elsewhere in its flow). More importantly, this is the only credential-transmitting OAuth entry point in the gem lacking the `ShopValidator.sanitize!` domain allow-list check that its sibling flows apply, meaning the binding "the host that gets the `client_secret` is a legitimate Shopify domain" is enforced only indirectly (via HMAC) here, and not defensively re-verified as in the other two flows.

### Impact Explanation
If `shop` ever reaches this method without being constrained to a genuine Shopify domain (the gem provides no `ShopValidator` guard here, unlike its sibling grant flows), the app's `client_secret` and the OAuth `code` are sent via HTTP POST to an attacker-controlled host, resulting in SSRF that exfiltrates the app's `client_secret` — a Critical-severity credential theft.

### Likelihood Explanation
Exploitability is limited because `Utils::HmacValidator.validate` does bind `shop` to the app's `api_secret_key`, so a fully external, unauthenticated attacker cannot forge a `shop` value on their own for a normal callback. However, the inconsistency with `client_credentials.rb`/`refresh_token.rb` — which both defensively call `ShopValidator.sanitize!` even for parameters they treat as more trusted — indicates this code path is missing a hardening layer that the gem's own design pattern elsewhere considers necessary, and any host application error in query construction (which the gem's docs directly encourage: `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys...)`) removes the last line of defense.

### Recommendation
Add a `Utils::ShopValidator.sanitize!(auth_query.shop)` call in `validate_auth_callback` before constructing `null_session`/building the `access_token` request, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, so the host receiving `client_secret` is always constrained to the trusted Shopify domain allow-list regardless of how `shop` was derived upstream.

### Proof of Concept
1. A host application builds `ShopifyAPI::Auth::Oauth::AuthQuery` from callback parameters as shown in the gem's own docs (`docs/usage/oauth.md`), without any additional domain check of its own.
2. If any component upstream of `validate_auth_callback` supplies a `shop` value that is not constrained to `*.myshopify.com` (e.g., a bug in HMAC verification order, or a caller who constructs `AuthQuery` directly with attacker-influenced `shop` for testing/alternate flows and mistakenly still passes HMAC — since `shop` is caller supplied to the `AuthQuery` constructor, not derived by the gem itself from a trusted transport), `validate_auth_callback` will POST `{client_id, client_secret, code, expiring}` to `https://<attacker-host>/admin/oauth/access_token`, leaking the `client_secret` — confirmed by tracing `null_session = Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient.new(session: null_session, ...)` → POST to `access_token` path with `client_secret` in the body, with no `ShopValidator` gate present in this call chain, unlike its sibling flows.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
