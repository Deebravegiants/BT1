Audit Report

## Title
Unauthenticated-role disclosure of External Initiator `AccessKey`/`OutgoingToken` via `GET /v2/external_initiators` - (File: `core/web/router.go`)

## Summary
`GET /v2/external_initiators` is registered without any role-gating middleware, so any authenticated node user with the lowest-privilege `view` role can enumerate every External Initiator's `AccessKey` and `OutgoingToken`, while sibling `POST`/`DELETE` routes for the same resource require `auth.RequiresEditRole`. This is a real, verified inconsistency in role gating, but the disclosed data does not by itself enable forging incoming authentication or hijacking outbound webhook validation, which limits the concrete impact.

## Finding Description
In `v2Routes`, the index route is mounted with no role wrapper: `authv2.GET("/external_initiators", paginatedRequest(eia.Index))`, while `POST`/`DELETE` use `auth.RequiresEditRole` [1](#0-0) . `ExternalInitiatorsController.Index` returns `presenters.NewExternalInitiatorResource` for every stored initiator, which serializes `AccessKey` and `OutgoingToken` [2](#0-1) [3](#0-2) . The RBAC test table confirms this is currently exercised/expected behavior: `{"GET", "/v2/external_initiators", true, true, true}` vs. `{"POST", ..., false, false, true}` / `{"DELETE", ..., false, false, true}` [4](#0-3) .

However, verifying the actual authentication mechanism shows the impact is narrower than claimed:
- Incoming External Initiator authentication (`AuthenticateExternalInitiator`) requires **both** `AccessKey` and `Secret`, comparing a hash of `Secret` against the stored `HashedSecret` via `bridges.AuthenticateExternalInitiator` [5](#0-4) [6](#0-5) . The `Secret` is never returned by `Index` (only `AccessKey`/`OutgoingToken` are serialized), and it is only ever returned once, at creation time, via `NewExternalInitiatorAuthentication` in the `Create` handler [7](#0-6) [8](#0-7) . So leaking `AccessKey` alone from `Index` does **not** let an attacker forge the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` pair needed to authenticate as the initiator and trigger webhook job runs.
- `OutgoingToken` is fully disclosed by `Index`. Its actual runtime consumption path (where the node sends `OutgoingToken` to the initiator's remote endpoint, or where a remote party is expected to validate it) was not found in the indexed code beyond the struct fields and presenters/CLI renderers; no handler was found that validates an inbound request against `OutgoingToken`. Its use appears to be for the node to authenticate itself when notifying the external initiator (an outbound HTTP client concern), not for gating access to the Chainlink node's own API.

## Impact Explanation
The confirmed issue is an inconsistent authorization boundary: `GET /v2/external_initiators` is reachable by `view`-role users while the mutating routes for the same resource require `edit`. This does expose `AccessKey` (half of a two-factor credential pair) and `OutgoingToken` to lower-privileged users than intended, which is a legitimate secret-exposure/least-privilege defect. However, it does **not** result in the ability to forge incoming EI authentication (the `Secret` is never exposed here) and no code path was found in-repo confirming that leaking `OutgoingToken` alone enables an attacker to impersonate the node to the initiator's remote service or to trigger unauthorized job runs/fund movement. The impact is therefore best characterized as unnecessary secret/credential-material exposure to a lower-privileged role than intended, rather than a full authentication bypass or fund-movement vulnerability.

## Likelihood Explanation
High for the disclosure itself: any authenticated `view`-role session or API token can call this endpoint with a single unauthenticated-role GET, no additional steps required. However, exploitation into a further concrete impact (e.g., forging EI auth to trigger job runs) is not supported by the current code because the `Secret` needed for the second authentication factor is never included in this or any other admin-facing list response.

## Recommendation
Wrap `GET /v2/external_initiators` with `auth.RequiresEditRole` (matching `POST`/`DELETE` for the same resource) to close the least-privilege gap. Separately, consider whether `AccessKey`/`OutgoingToken` need to be included in list responses at all, since they are already exposed once at creation time via `ExternalInitiatorAuthentication`.

## Proof of Concept
1. Create a node user with role `view`.
2. Authenticate as that user and call `GET /v2/external_initiators`.
3. Observe the response includes `accessKey` and `outgoingToken` for every configured initiator, confirmed by the RBAC test expectation `{"GET", "/v2/external_initiators", true, true, true}` [9](#0-8) .
4. Note that this alone does not allow constructing a valid `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` pair to authenticate as the initiator, since `Secret` is not part of the `Index` response and is only returned once at `Create` time.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {

	ei bridges.ExternalInitiator,

	var result = &ExternalInitiatorAuthentication{
		Name:           ei.Name,
		AccessKey:      ei.AccessKey,
		Secret:         eia.Secret,
		OutgoingToken:  ei.OutgoingToken,
		OutgoingSecret: ei.OutgoingSecret,
	}
	if ei.URL != nil {
		result.URL = *ei.URL
	}
	return result
}

// AuthenticateExternalInitiator authenticates an external initiator request.
//
// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
