### Title
Webhook `shop`, `topic`, and `api_version` headers are trusted without HMAC coverage, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC solely against that raw body. The `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers that are never included in the signed payload, so `Registry.process` dispatches to the handler with an attacker-controllable `shop` identity while still reporting a "valid" HMAC.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac` header:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers, which are entirely outside the signed material:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
def api_version
  T.cast(shopify_header("api-version"), String)
end
def webhook_id
  T.cast(shopify_header("webhook-id"), String)
end
``` [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then hands the (unauthenticated) `shop`, `topic`, `webhook_id`, and `api_version` straight to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The equality the gem is implicitly asserting is: `HMAC(secret, body) == received_hmac ⇒ (shop, topic, body) originated together from Shopify for that shop`. In reality the mac only binds `body`; it does **not** bind `shop`, `topic`, `api_version`, or `webhook_id`. Any party that has observed one legitimately-signed webhook body/HMAC pair (webhooks are frequently logged, proxied, or visible via browser dev tools/support tooling, and payload+HMAC combinations are not treated as secret by the platform) can resubmit the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (and/or `topic`/`webhook-id`). `HmacValidator.validate` will still report success because it never inspected those headers, and the handler will receive `WebhookMetadata` claiming the payload belongs to a different, attacker-chosen shop.

### Impact Explanation
Applications built on this gem's `Webhooks::Registry` API rely on `request.shop`/`WebhookMetadata#shop` to key which merchant/tenant the webhook body applies to (e.g., persisting order/product/customer records under that shop's session or scoping billing/inventory updates). Because the shop identity is not bound by the HMAC, an attacker can cause a legitimately-signed payload to be attributed to a shop it was never actually sent for, injecting or overwriting another tenant's data — a cross-tenant access/data-integrity break stemming directly from the gem's signature-verification API.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid `(raw_body, hmac-sha256)` pair for any topic (their own store's webhook, or one captured/leaked in transit/logs), which is a modest bar since webhook deliveries are plain HTTP POSTs routinely visible to server operators, proxies, and logging middleware. No knowledge of `api_secret_key` is needed — the attacker replays previously valid bytes and only forges the unauthenticated `shop-domain` header.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, and ideally `webhook_id`) in the material that is HMAC-verified, e.g., have `to_signable_string` canonicalize and include these headers alongside the body, or have `HmacValidator`/`Registry.process` cross-check the header-derived `shop` against a shop known independently (e.g., via the session/app installation record) before dispatching to handlers.

### Proof of Concept
```ruby
# 1. Attacker captures (or owns) one legitimately signed webhook delivery:
raw_body = '{"id":123,"note":"legit order for shop-a"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), real_secret, raw_body)
b64_hmac = Base64.encode64(hmac)

# 2. Attacker resubmits the SAME body+hmac but swaps the shop-domain header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => b64_hmac,        # unchanged, still verifies against raw_body
  "x-shopify-shop-domain" => "victim-shop-b.myshopify.com", # forged, NOT covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) returns true (it only checks raw_body),
# handler.handle receives WebhookMetadata(shop: "victim-shop-b.myshopify.com", ...)
# -- the app now attributes shop-a's order payload to shop-b.
```
