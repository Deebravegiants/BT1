### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying `Utils::HmacValidator.validate(request)` against the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to application handlers as the merchant identity are taken from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate_signature` computes/compares the HMAC exclusively over that signable string using `Context.api_secret_key` (or `old_api_secret_key`) [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body or to each other [3](#0-2) .

`Registry.process` only checks the HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` as the tenant identity: [4](#0-3) 

This is exactly the identity-binding gap the report's "pull based oracle" analogy describes: the value that is trusted and acted upon (`shop`) is not one of the bytes that the signature covers. The equality that should hold — `shop authenticated == shop acted on` — is broken because the HMAC binds `raw_body` only, while `shop` (the tenant discriminator) is asserted out-of-band via a header nobody signs.

### Impact Explanation
Because the HMAC is computed with the app's single shared `api_secret_key`, any request whose body carries a valid signature for that key will pass `Registry.process`'s HMAC check regardless of which shop's header is attached. A party who can obtain one genuinely-signed webhook body for their own shop (a normal, unprivileged merchant using the app — no `api_secret_key` needed) can replay that same body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header for another tenant. The handler (`WebhookMetadata`, built from `request.shop`) will believe the payload belongs to the victim shop, letting an attacker inject or spoof events attributed to a different merchant — a cross-tenant identity confusion inside the host application's webhook-driven business logic (e.g., order/customer data processing, GDPR webhooks, app-uninstall handling keyed by shop).

### Likelihood Explanation
Exploitability depends on the attacker being able to capture a legitimately-signed webhook (trivial for any merchant using the app, since Shopify delivers signed webhooks to the app for every event on their own shop) and then re-POST it with a modified shop header to the app's public webhook endpoint. No possession of `api_secret_key` or any credential is required beyond being a legitimate, if malicious, tenant of the app — squarely an "unprivileged internet user" analog once the attacker has installed the app on any shop.

### Recommendation
Include the shop domain (and topic/webhook id) in the signed content, or otherwise cryptographically bind them: e.g., verify `shopify-shop-domain` against session/shop storage that was itself derived from OAuth, or require and check a canonical string containing shop+body when computing the HMAC comparison, so verification fails if any header used for tenant dispatch was altered from what was actually signed by Shopify for that request.

### Proof of Concept
1. Legitimate merchant A installs the app; the app receives a real Shopify webhook: body `B`, headers `{shopify-shop-domain: "a.myshopify.com", shopify-hmac-sha256: HMAC(secret, B)}`.
2. Attacker captures `B` and the valid `hmac`.
3. Attacker POSTs to the app's webhook endpoint with headers `{shopify-shop-domain: "victim.myshopify.com", shopify-hmac-sha256: HMAC(secret, B)}` and the same body `B`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC [5](#0-4)  — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled data under the victim's tenant identity.
