### Title
Single-solver `exact_amount_out` quote allows arbitrarily inflated `amount_in`, overcharging the user for the fee-token swap - (File: `packages/internal-utils/src/solverRelay/getQuote.ts`)

### Summary
`matchesRequest()` in `getQuote.ts` only validates the side of the quote fixed by the request (`amount_out` for `exact_amount_out`), leaving `amount_in` completely unconstrained. When `getFeeQuote()` is called from `estimateWithdrawalFee()` in `HotBridge`/`OmniBridge`/`AuroraEngineBridge`/`DirectBridge` with `exact_amount_out=feeAmount`, a single permissionless solver can return a valid-looking quote with a correct `amount_out` but an arbitrarily large `amount_in`, and since `sortQuotes` has nothing to compare it against, it becomes `bestQuote` unchallenged.

### Finding Description
The equality that should hold is: `feeEstimation.amount` (`BigInt(quote.amount_in)`) ≈ real market cost to acquire `feeAmount` of the fee asset. Instead, the code only guarantees `BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out)`: [1](#0-0) 

`handleQuoteResult` filters candidates through `matchesRequest`, then picks the best via `sortQuotes`, which sorts ascending by `amount_in` for `exact_out` — but with exactly one valid quote in the list, sorting is a no-op and that quote is returned as-is: [2](#0-1) [3](#0-2) 

`getFeeQuote()` in `estimate-fee.ts` forwards `exact_amount_out: feeAmount.toString()` to `solverRelay.getQuote()` with no further bound-check on the returned `amount_in` in the exact-out path (the 1.2x sanity check only exists in the fallback `exact_amount_in` branch, not the primary path): [4](#0-3) 

Each of the four bridges then takes `feeQuote.amount_in` directly as `feeEstimation.amount`: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

That `feeEstimation.amount` is subsequently subtracted from the user's withdrawal amount and embedded verbatim into the `token_diff` intent (e.g. in `AuroraEngineBridge.createWithdrawalIntents`, lines 92-103 of that file), which the user then signs. This amount also feeds into `IntentsSDK.createWithdrawalIntents`, where `actualAmount = withdrawalParams.amount - feeEstimation.amount` when `feeInclusive` is set: [9](#0-8) 

There is a `FeeExceedsAmountError` check elsewhere in `sdk.ts`/`errors.ts` that caps the fee at the withdrawal amount, but that only prevents `feeEstimation.amount` from exceeding the total withdrawal amount — it does not prevent an inflated-but-still-under-the-cap `amount_in` from draining a large, non-bounded fraction of the withdrawal for a fee-token swap that should have cost only `feeAmount`'s worth of tokens.

### Impact Explanation
A single malicious/permissionless solver, with no competing quote to be undercut by, can set `feeEstimation.amount` to any value up to the full withdrawal amount while still returning a technically "matching" quote (correct `amount_out`, inflated `amount_in`). This is embedded into the signed `token_diff` intent and debited from the user, i.e., "a fee overcharge / solver overpaid" against the calling user, matching the High-severity category. Since `estimateWithdrawalFee()` is called per withdrawal and the solver can answer every time it is the sole responder, the attack is repeatable across withdrawals.

### Likelihood Explanation
Preconditions: exactly one solver responds to the relay's quote broadcast for the fee-token swap (no competing quote to be beaten in `sortQuotes`), which is entirely plausible for a low-liquidity or thinly-solved fee-asset pair. The attacker's cost is zero beyond running/controlling a solver instance that answers the relay; no privileged access is required, matching the "permissionless solver" attacker model explicitly allowed by the rules.

### Recommendation
Bound the accepted `amount_in` for `exact_amount_out` quotes against an independent reference price (e.g., the same `tokens()` price oracle already used in the `exact_amount_in` fallback path of `getFeeQuote`), rejecting or falling back when a lone quote's implied rate deviates beyond a sane multiple (mirroring the existing 1.5x check used in the fallback branch) even when only one solver responds.

```ts
import * as quoteWithLogModule from "../utils/quoteWithLog";
import { getQuote } from "../getQuote";

describe("getQuote exact_amount_out with single inflated solver", () => {
  it("accepts a quote with correct amount_out but arbitrarily large amount_in", async () => {
    const feeAmount = "1000"; // exact_amount_out requested
    vi.spyOn(quoteWithLogModule, "quoteWithLog").mockResolvedValue([
      {
        defuse_asset_identifier_in: "nep141:token.near",
        defuse_asset_identifier_out: "nep141:wrap.near",
        amount_in: "999999999999999999", // inflated, no competing quote
        amount_out: feeAmount,           // matches request -> passes matchesRequest
        quote_hash: "hash1",
        expiration_time: Date.now() + 60_000,
      },
    ]);

    const result = await getQuote({
      quoteParams: {
        defuse_asset_identifier_in: "nep141:token.near",
        defuse_asset_identifier_out: "nep141:wrap.near",
        exact_amount_out: feeAmount,
      },
      config: { baseURL: "http://localhost", logBalanceSufficient: false },
    });

    // Broken equality: amount_in should stay within a sane multiple of feeAmount,
    // but nothing enforces that when only one solver responds.
    expect(BigInt(result.amount_in)).toBe(999999999999999999n);
    // A hardened implementation should instead reject or clamp this quote,
    // e.g.: expect(getQuote(...)).rejects.toThrow(QuoteError)
  });
});
```

```typescript
function sortQuotes(
	quotes: Quote[],
	quoteKind: "exact_in" | "exact_out",
): Quote[] {
	return quotes.slice().sort((a, b) => {
		if (quoteKind === "exact_in") {
			// For exact_in, sort by `amount_out` in descending order
			if (BigInt(a.amount_out) > BigInt(b.amount_out)) return -1;
			if (BigInt(a.amount_out) < BigInt(b.amount_out)) return 1;
			return 0;
		}

		// For exact_out, sort by `amount_in` in ascending order
		if (BigInt(a.amount_in) < BigInt(b.amount_in)) return -1;
		if (BigInt(a.amount_in) > BigInt(b.amount_in)) return 1;
		return 0;
	});
}
```

```typescript
function matchesRequest(
	quote: Quote,
	quoteParams: GetQuoteParams["quoteParams"],
): boolean {
	if (
		quote.defuse_asset_identifier_in !==
			quoteParams.defuse_asset_identifier_in ||
		quote.defuse_asset_identifier_out !==
			quoteParams.defuse_asset_identifier_out
	) {
		return false;
	}

	// Only the side fixed by the request is verified; the other side is what the
	// solver competes on (max amount_out for exact_in, min amount_in for
	// exact_out). Compare as BigInt so formatting differences don't matter.
	if (quoteParams.exact_amount_in != null) {
		return BigInt(quote.amount_in) === BigInt(quoteParams.exact_amount_in);
	}
	return BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out);
}
```
