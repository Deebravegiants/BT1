### Title
Webhook shop identity spoofing due to HMAC covering only the body, not the shop-domain header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, but `to_signable_string` — the data actually covered by the HMAC signature — only includes the raw request body. `Webhooks::Registry.process` validates the HMAC and then dispatches to the handler using this unauthenticated `shop` value, breaking the binding `authenticated_bytes == acted_upon_shop`.

### Finding Description
`Webhooks::Request#shop` reads directly from the request header: [1](#0-0) 

but the HMAC verification only signs the raw body: [2](#0-1) 

`Webhooks::Registry.process` validates that the body's HMAC is correct, then immediately trusts `request.shop` to build the `WebhookMetadata` object passed to the host application's handler, without the header ever being covered by the signature: [3](#0-2) 

`Utils::HmacValidator.validate` compares only `verifiable_query.to_signable_string` against the HMAC, which for webhooks is the raw body only: [4](#0-3) 

Because the shop header is excluded from the signed content, a party who has legitimately received one valid `(body, hmac)` pair for their own shop can resend the exact same body and HMAC to the app's webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain`. The signature still validates (it never depended on that header), but `handler.handle` is invoked with `shop: request.shop` set to the attacker-chosen tenant. Any host application that uses this `shop` field to select which tenant's session/data to update (the intended and documented use, per `WebhookMetadata`) will attribute/act on the wrong tenant, i.e. the equality `hmac-authenticated shop == shop used for handler dispatch` does not hold.

### Impact Explanation
This is a cross-tenant integrity issue: an entity in possession of one valid signed webhook payload (e.g., a malicious merchant receiving their own app's webhooks) can cause a victim shop's data path to be exercised inside the host application by merely changing an HTTP header, without ever knowing the app's `client_secret`. This matches the Critical category of cross-tenant access via a binding the report’s bug class describes (field acted upon but not covered by the HMAC).

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one legitimately-issued `(body, hmac)` pair, which any merchant installing the app can obtain for themselves (e.g., trigger a webhook event on their own store). No secret material, privileged account, or additional infrastructure access is required beyond normal use of the app as an unprivileged merchant/internet-facing endpoint.

### Recommendation
Bind the shop identity into the signed material, or otherwise authenticate it independently of the raw body: e.g., include `shop-domain`/`webhook-id`/`api-version` headers in `to_signable_string`, or after HMAC validation, independently verify that `request.shop` matches a shop the app has installed/registered a session for before invoking the handler, and reject mismatches.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a legitimate webhook to the app's endpoint with body `B`, headers including `X-Shopify-Shop-Domain: shop-a.myshopify.com` and `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (merchant A, or anyone who can capture this request) resends the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`, unaffected by the header change) and succeeds. [5](#0-4) 
4. `handler.handle` is invoked with `shop: "shop-victim.myshopify.com"`, even though the payload `B` was never actually generated for that shop, causing the host app to act on/attribute data to the wrong tenant.
