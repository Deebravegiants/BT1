## Title
Webhook `shop`, `topic`, and `webhook_id` identity headers are not covered by the HMAC signature verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler `request.shop`, `request.topic`, and `request.webhook_id` as trusted identity fields. However, the HMAC signature covers only the raw request body — none of the identifying headers are part of the signed material. This breaks the intended binding `verified(shop/topic) == authenticated(shop/topic)`: only the body is authenticated, while the tenant/topic identity used by the handler is taken from unauthenticated header bytes.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers, which are never mixed into `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the body-derived HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` header values and dispatches it to the app's handler as if it were verified identity data: [4](#0-3) 

Contrast this with the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` (and `host`) in the signed payload, correctly binding the shop identity to the HMAC: [5](#0-4) 

No equivalent binding exists for webhooks. An unprivileged internet user who legitimately receives (or otherwise obtains) one valid `(raw_body, hmac)` pair for their own shop's webhook can resend the exact same body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header for any other tenant. `HmacValidator.validate` still returns `true` because it only checks the body against the secret — it never inspects the headers — so the forged shop/topic identity flows unchecked into the app's business logic via `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant identity-binding failure inside the gem's own webhook verification API: the gem presents `shop`/`topic`/`webhook_id` as if they were verified alongside the HMAC-authenticated body, but they are not bound to the signature at all. Any app built on top of `ShopifyAPI::Webhooks::Registry.process` that uses `data.shop` to select per-tenant state (session, credentials, database row) can be made to apply attacker-controlled body content to a victim shop's context, or vice versa — a cross-tenant access primitive achieved purely by header substitution on an otherwise validly-signed webhook payload.

### Likelihood Explanation
Exploitability requires only one legitimately delivered webhook (body + HMAC pair), which an attacker who runs their own shop and app installation can obtain trivially and then replay with modified headers against the same publicly reachable webhook endpoint. No access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise validate them out-of-band before trusting them:
- Change `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) to require that `shop`, `topic`, and `webhook_id` are consistent with data recoverable only after HMAC validation (e.g., re-derive expected values from the parsed/trusted body, or maintain a separate authenticated channel for shop identity such as comparing against the shop stored for the delivered `webhook_id` via the Admin API).
- At minimum, document/enforce that `data.shop`/`data.topic` in `WebhookMetadata` must not be treated as cryptographically verified by `Registry.process`, and provide an API that verifies them together with the body.

### Proof of Concept
1. App has two shops installed: `attacker.myshopify.com` (attacker-controlled) and `victim.myshopify.com`.
2. Shopify delivers a legitimate webhook to the attacker's shop:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body under app secret>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id": 1, ...attacker-crafted order payload...}
   ```
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, replacing only the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `HmacValidator.validate` recomputes HMAC over `@raw_body` only and it matches — `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker-crafted body>, ...)`.
5. Any app logic keyed off `data.shop` (e.g., writing attacker-controlled order data into the victim tenant's records) executes under the victim's tenant context despite the payload never being signed for that shop. [4](#0-3) [2](#0-1)
