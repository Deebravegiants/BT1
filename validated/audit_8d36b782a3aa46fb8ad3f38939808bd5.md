### Title
Unrestricted `new()` initializer in `staking-pool`, `lockup`, and `whitelist` contracts can be front-run to hijack ownership - (`staking-pool/src/lib.rs`, `lockup/src/lib.rs`, `whitelist/src/lib.rs`)

### Summary
The `#[init]` `new()` constructors of `staking-pool/src/lib.rs`, `lockup/src/lib.rs`, and `whitelist/src/lib.rs` only guard against re-initialization via `assert!(!env::state_exists(), ...)`. None of them verify that the caller (`predecessor_account_id`/`signer_account_id`) is the legitimate deployer/owner. When these contracts are deployed following the officially documented multi-transaction flow — first `near create_account`/`near deploy` to put the WASM on-chain, and only afterwards a separate `near call <account> new ...` transaction — there is a window during which the contract exists with code but without state. Any unprivileged account can race to call `new()` in that window and set itself as `owner_id`/`foundation_account_id`, gaining full administrative control of the contract before the legitimate operator's initialization transaction lands. This is directly analogous to the "Gorples Bridge Program Initializer Can Be Front-Run" finding: an unauthenticated `Initialize`/`new` instruction that configures trust-critical fields with no restriction on the caller.

### Finding Description
- `staking-pool/src/lib.rs` `new()` (lines 173-206) sets `owner_id`, `stake_public_key`, and `reward_fee_fraction` with no check that the caller is the account that deployed the code: [2](#0-1) 
- `lockup/src/lib.rs` `new()` (lines 180-243) sets `owner_account_id`, `staking_pool_whitelist_account_id`, and `foundation_account_id`, again with no caller check: [3](#0-2) 
- `whitelist/src/lib.rs` `new()` sets `foundation_account_id`, the account trusted to whitelist staking pools/factories, with the same missing check: [1](#0-0) 

The documented deployment flows for these contracts explicitly split account-creation/code-deployment and initialization into separate transactions, e.g. `staking-pool/README.md`: [4](#0-3) 
and the equivalent multi-step CLI flow in `scripts/tests/test_voting.sh`: [5](#0-4) 

This is in contrast to the factory contracts in scope (`staking-pool-factory/src/lib.rs` and `lockup-factory/src/lib.rs`), which bundle `create_account`, `deploy_contract`, `transfer`, and `function_call("new", ...)` into a single atomic `Promise` chain (one receipt), closing the front-run window: [6](#0-5) 

Because `staking-pool`, `lockup`, and `whitelist` are meant to also be deployable directly (not only through their factories), and their own `new()` performs no caller/deployer authentication, an unprivileged attacker monitoring the network for a `deploy_contract` action on one of these target accounts can submit a competing `new()` call before the legitimate owner's transaction executes.

### Impact Explanation
- For `staking-pool`: an attacker who wins the race becomes `owner_id`, gaining exclusive rights to `update_staking_key`, `pause_staking`/`resume_staking`, `vote`, and `update_reward_fee_fraction`. Delegators who later deposit funds believing the pool is controlled by the intended validator are exposed to fee manipulation and stake mismanagement by the attacker-controlled owner — matching the "Critical: unauthorized transfer/spending... reachable by an unprivileged user" and "High: unauthorized execution... beyond intended authority" impact classes.
- For `lockup`: an attacker who wins the race becomes `owner_account_id` (and can set an arbitrary `foundation_account_id`), gaining control of all owner-only methods over the locked/vesting NEAR balance held by the contract — matching "Critical: permanent freezing/irrevocable loss of user or protocol funds in lockup release... flows" since there is no ownership-transfer mechanism to reverse this once the legitimate deployer's `new()` reverts with "Already initialized".
- For `whitelist`: an attacker who wins the race becomes `foundation_account_id`, gaining the ability to whitelist arbitrary (potentially malicious) staking pools/factories that downstream lockup/factory logic trusts.

In all three cases, the vulnerability is irreversible: once state exists, the legitimate deployer's `new()` transaction permanently fails, and there is no owner-transfer path recovered from that state.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to observe a `deploy_contract` action for one of these contracts landing on-chain and to quickly submit a `new()` call before the legitimate operator's follow-up transaction is included. NEAR's transaction pool and block production timing make this a realistic (if narrow) race window, especially since the officially documented usage flow for `staking-pool` explicitly separates `near deploy` and `near call new` into distinct commands, giving attackers a predictable target and window.

### Recommendation
- Restrict `new()` in `staking-pool/src/lib.rs`, `lockup/src/lib.rs`, and `whitelist/src/lib.rs` so it can only be called by the account itself (`assert_eq!(env::predecessor_account_id(), env::current_account_id())`), ensuring initialization can only happen via a self-call bundled atomically with `create_account`/`deploy_contract` (as already done in the factory contracts), or otherwise document and enforce that these contracts must only ever be deployed through their respective factories.
- Alternatively/additionally, bundle `create_account`, `deploy_contract`, and `function_call("new", ...)` into a single atomic transaction/receipt in all documented and scripted deployment flows, eliminating the separate-transaction pattern shown in `staking-pool/README.md` and `scripts/tests/test_voting.sh`.
- Consider adding an ownership-transfer mechanism controlled by a known higher authority so a hijacked initialization can be recovered, mirroring the remediation recommendation from the referenced Solana report.

### Proof of Concept
1. Operator runs `near create_account my_validator --masterAccount=owner` then `near deploy --accountId=my_validator --wasmFile=res/staking_pool.wasm` (per `staking-pool/README.md` line 203-204), leaving `my_validator` with code deployed but `env::state_exists()` still false.
2. Before the operator's subsequent `near call my_validator new '{"owner_id": "owner", ...}'` transaction lands, an attacker submits `near call my_validator new '{"owner_id": "attacker", "stake_public_key": "<attacker key>", "reward_fee_fraction": {...}}' --accountId attacker`.
3. `staking-pool/src/lib.rs::new()` (lines 173-206) only checks `!env::state_exists()`; since no state exists yet, the attacker's call succeeds and sets `owner_id = "attacker"`.
4. The operator's legitimate `new()` transaction subsequently fails with `"Already initialized"`, permanently leaving the attacker as `owner_id` of the staking pool, with the same race applicable to `lockup::new()` (owner/foundation takeover) and `whitelist::new()` (foundation takeover).
