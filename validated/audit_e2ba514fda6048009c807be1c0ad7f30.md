### Title
`IsmpCallFilter` on Nexus only pattern-matches `Message::Consensus`, letting a `Message::FraudProof` targeting the BEEFY consensus state slip through `handle_unsigned` unfiltered - (File: `parachain/runtimes/nexus/src/lib.rs`)

### Summary
The Nexus runtime's base call filter blocks raw BEEFY consensus updates submitted through `pallet_ismp::Call::handle_unsigned`, forcing all BEEFY state advances through the SP1-zkVM-gated `pallet-beefy-consensus-proofs` path. The filter's detection logic, however, only recognizes one specific `ismp::messaging::Message` variant (`Message::Consensus`). Any other message variant carrying a `consensus_state_id` that resolves to the BEEFY client — most notably `Message::FraudProof` (`FraudProofMessage`) — is treated as "not BEEFY" and passed straight through to the pallet-ismp message handler, bypassing the protection the filter was written to provide.

### Finding Description
`IsmpCallFilter::contains` is the sole guard preventing unsigned `handle_unsigned` batches from touching the BEEFY consensus client directly: [1](#0-0) 

The match statement only inspects `Message::Consensus(consensus)`; the wildcard arm `_ => false` means every other `Message` variant is reported as "does not carry a BEEFY consensus message" regardless of its actual `consensus_state_id`. The `ismp::messaging` module defines `FraudProofMessage`, which independently carries its own `consensus_state_id` field and is dispatched to the same consensus-client machinery as a `ConsensusMessage`: [2](#0-1) 

Because `FraudProofMessage` is a distinct enum variant from `ConsensusMessage`, submitting `Message::FraudProof` with a `consensus_state_id` that the host maps to `ismp_beefy::BEEFY_CONSENSUS_ID` is never caught by the `.any()` predicate in `IsmpCallFilter`, even though it drives the exact same BEEFY consensus client (`host.consensus_client_id(...)`) that the filter's own doc comment says must go exclusively through the zk-verified `pallet-beefy-consensus-proofs` pipeline: [3](#0-2) 

This is structurally the same bug class as the OPA advisory: a security control enumerates a fixed, named set of "unsafe" constructs (builtin function references / `Message::Consensus`) but a different syntactic path reaching the identically protected resource (the `with` mocking construct / the `Message::FraudProof` variant) is not accounted for, so the filter can be routed around entirely by choosing the alternate message type instead of the blocked one.

### Impact Explanation
The filter's entire purpose is to prevent any unsigned message from mutating BEEFY consensus state outside of the SP1-verified proof path, because an unchecked mutation could let an attacker either invalidate the client's trusted state (freezing the route that carries every cross-chain message relying on BEEFY-verified state, i.e. "a route unable to deliver messages") or otherwise manipulate consensus-derived state commitments that downstream apps and the token bridge rely on for membership/non-membership proofs. Since fraud-proof handling operates on the same `ConsensusClient` trait implementation as consensus updates, reaching it through the unfiltered path reintroduces exactly the risk the filter and the underlying `pallet-beefy-consensus-proofs` gate were built to close off.

### Likelihood Explanation
`handle_unsigned` is a pallet-ismp extrinsic reachable by any unprivileged party submitting a transaction/batch containing ISMP messages — no special origin or governance action is required to construct a `Message::FraudProof` payload targeting the BEEFY `consensus_state_id`. The bypass requires no cryptographic break, only choosing a different, already-defined message-enum variant that the filter's `match` statement never enumerates.

### Recommendation
Change `IsmpCallFilter::contains` to check every message's `consensus_state_id` against the BEEFY client id regardless of variant (e.g., match both `Message::Consensus` and `Message::FraudProof`, or extract the `consensus_state_id` generically before comparing), so that any message type capable of resolving to the BEEFY consensus client is rejected from `handle_unsigned`, consistent with the filter's documented intent.

### Proof of Concept
1. Construct an `ismp::messaging::Message::FraudProof(FraudProofMessage { proof_1, proof_2, consensus_state_id: <BEEFY_STATE_ID>, signer })`.
2. Wrap it in a `pallet_ismp::Call::handle_unsigned { messages: vec![fraud_proof_message] }` call.
3. Submit it as a signed extrinsic (per the existing test harness pattern in `parachain/simtests/src/base_call_filter.rs`), observing that `IsmpCallFilter::contains` returns `true` (not filtered) because the match arm for `Message::FraudProof` falls into `_ => false` in the `.any()` closure — unlike the equivalent `Message::Consensus` case, which is correctly caught as shown in the existing `ismp_call_filter_blocks_only_beefy_consensus_and_fund_message` test: [4](#0-3) 
4. The call reaches the pallet-ismp dispatch body instead of being rejected with `System::CallFiltered`, exercising fraud-proof handling on the BEEFY client outside the SP1-gated update path.

pub struct IsmpCallFilter;
impl Contains<RuntimeCall> for IsmpCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		use ::ismp::{host::IsmpHost, messaging::Message};
		match call {
			RuntimeCall::Ismp(pallet_ismp::Call::fund_message { .. }) => false,
			RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages }) => {
				let host = Ismp::default();
				!messages.iter().any(|message| match message {
					Message::Consensus(consensus) =>
						host.consensus_client_id(consensus.consensus_state_id) ==
							Some(ismp_beefy::BEEFY_CONSENSUS_ID),
					_ => false,
				})
			},
			_ => true,
		}
	}
}
