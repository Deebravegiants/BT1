### Title
Accrual-time `i128` overflow in `scaled_to_original` permanently freezes a large market before the borrow-index cap engages - (File: common/src/rates/index.rs)

### Summary
The CVE-2018-16839 bug class is an integer overflow that corrupts a computation and knocks the system into a denial of service. The same shape exists in XOXNO Lending's rate engine: every market verb first runs interest accrual, and accrual computes `borrowed_shares * borrow_index` and `supplied * supply_index` in RAY-scaled `i128` fixed point. When a market's total debt value in RAY exceeds `i128::MAX` (~1.7e38, i.e. ~1.7e11 whole-token units of value) while the borrow index is still below `MAX_BORROW_INDEX_RAY`, `Ray::mul` → `mul_div_half_up`/`mul_div_floor` panics with `GenericError::MathOverflow`. Because `global_sync` is invoked at the top of every state-changing entrypoint, the panic bricks the market: no repay, no withdraw, no liquidation, no borrow — permanently.

### Finding Description
Accrual is driven by `global_sync` → `accrue_chunk` → `accrue_step` in `contracts/pool/src/interest.rs:20-53`. Inside `accrue_step`, `calculate_supplier_rewards` evaluates `borrowed.mul(env, old_borrow_index)` and `borrowed.mul(env, new_borrow_index)` (`common/src/rates/index.rs:80-81`), and `update_supply_index` evaluates `supplied.mul(env, old_index)` (`common/src/rates/index.rs:34`). Each of these is `x * y / RAY` computed via `fp_core`'s `i128` fast path with `I256` widening only for the *intermediate* product — the *result* must still fit `i128`, or `to_i128`/`mul_div_*` raises `MathOverflow` (`common/src/math/fp_core.rs:108-143`).

The protective bound that exists, `MAX_BORROW_INDEX_RAY`, is applied to the *index* after multiplication (`common/src/rates/index.rs:13-19`), but nothing bounds the *product of shares and index*. The debt value `borrowed * borrow_index` can exceed `i128::MAX` while `borrow_index < MAX_BORROW_INDEX_RAY`, so the cap never engages before the value overflows. `docs/reference/formulas.md` documents a bound on this ceiling; the in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362`) demonstrates empirically that the bound is wrong: after enough years at ~98% utilization on a steep interest-rate curve, `update_indexes` itself reverts with `MATH_OVERFLOW`, and every subsequent verb that accrues (withdraw, repay, borrow, liquidate, `clean_bad_debt`, etc.) reverts identically.

There is no recovery path: `set_supply_index`/`set_borrow_index` are internal, accrual is mandatory and monotonic, and no admin function can roll the index back or skip accrual. `apply_bad_debt_to_supply_index` can shrink the supply index but is itself only reachable through a call that accrues first.

### Impact Explanation
Permanent freezing of all funds in the affected market book. Once `supplied * supply_index` or `borrowed * borrow_index` crosses `i128::MAX`, every controller/pool entrypoint that touches that market aborts in `global_sync`. Suppliers cannot withdraw, borrowers cannot repay or be liquidated, bad debt cannot be cleaned, and revenue cannot be claimed. The pool's physical token balance for that market is locked in the contract forever. Because books share one physical pool balance, freezing a whale-scale market can also trap other markets' liquidity against the same balance.

### Likelihood Explanation
Reachable by a single unprivileged address through ordinary entrypoints: `supply` a very large position (order of 10^9+ tokens on a high-decimals listing), `borrow` near the utilization maximum against separate collateral, then let time pass (or wait for the steep utilization curve to compound). No privileged role, oracle manipulation, or leaked key is needed — only capital and time, both of which the attacker fully controls since they choose the market, the size, and can fund the interest themselves. The trigger requires an unusually large position and a long horizon, so it is not opportunistic; that places it at Medium severity rather than High. Notably, the protocol's own test suite already proves the panic is reachable and asserts the documented safety bound is incorrect.

### Recommendation
Bound the value side, not just the index side. Options:

- Cap total debt/supply *value* in RAY terms: enforce at `supply`/`borrow` that `scaled * index <= i128::MAX - margin`, so no reachable state can overflow accrual. The existing cap validation (`require_cap_within_asset_domain`) checks the raw cap, not the RAY-valued ceiling.
- Make accrual saturate instead of panic: use `mul_div_floor_saturating`/`mul_div_ceil_saturating` (already used in `calculate_scaled_cap` and `protocol_fee_shares`) inside `calculate_supplier_rewards` and `update_supply_index`, so the market degrades to a clamped index rather than bricking.
- Alternatively, scale shares/index representation (e.g. store indexes modulo a bounded range) so the value ceiling is unreachable by construction.

### Proof of Concept
The in-repo test is a direct reproduction (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`):

```rust
let principal = BILLION * 10i128.pow(18);          // 1e9 tokens, 18 decimals
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                    // 98% utilization
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// → ContractError(MATH_OVERFLOW) while last.borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Manual trace: `update_indexes` → pool accrual → `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards` → `borrowed.mul(env, borrow_index)` → `try_mul_div_half_up` — the widened `I256` product `borrowed * borrow_index` divided by `RAY` yields a quotient that does not fit `i128`, so `to_i128` returns `None` and the call panics with `GenericError::MathOverflow` (`common/src/math/fp_core.rs:122-143`). Every later verb repeats the same accrual first, so the panic is permanent.
