### Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers and forwarded to the application's webhook handler as trusted identity data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are parsed directly from HTTP headers with no cryptographic binding to those header values: [3](#0-2) 

`HmacValidator.validate` only checks that the received `hmac` matches `HMAC(secret, verifiable_query.to_signable_string)`, i.e., only the body bytes: [4](#0-3) 

`Registry.process` treats HMAC success as proof of authenticity for the *entire* request, including `request.shop`, and forwards it unchanged into `WebhookMetadata`: [1](#0-0) 

The identity binding that should hold is: `shop asserted to handler == shop that produced the HMAC-verified bytes`. Because the `shop-domain` header is outside the signed data, this equality is never actually checked — only the body bytes are authenticated, not the shop/topic metadata describing whose data it is.

An unprivileged actor who controls their own Shopify store (a normal, unprivileged app installer) can:
1. Receive a legitimate webhook delivery from Shopify to the app's endpoint for their own shop (a valid `raw_body` + valid `hmac` computed by Shopify with the real `client_secret`, which the attacker never needs to know).
2. Replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header changed to a different, victim shop's domain.
3. Because `to_signable_string` never included the shop header, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

Any host application that uses `data.shop` from the handler to route the payload to per-tenant state (the intended and documented use of `WebhookMetadata#shop` per `lib/shopify_api/webhooks/webhook_metadata.rb`) will attribute attacker-controlled webhook content to the wrong tenant, breaking the multi-tenant isolation this gem is meant to help enforce.

### Impact Explanation
This breaks the tenant identity binding (`shop` field acted upon vs. `shop` bytes actually authenticated by the HMAC), allowing a shop-authenticated request for one tenant to be misattributed to another tenant purely by header manipulation — a cross-tenant data-integrity/access issue, which the rules classify as Critical (cross-tenant access).

### Likelihood Explanation
The attacker only needs to be an ordinary, unprivileged merchant installing the app on their own store (to obtain one genuine `raw_body`/`hmac` pair) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which by design must accept unauthenticated POSTs from the internet, since webhook auth is exactly this HMAC check). No access token, `client_secret`, or privileged account is required, and no host-application misuse beyond following this gem's documented `WebhookMetadata#shop` API is needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload, so that `Registry.process` cannot be fed a verified body paired with an attacker-chosen shop/topic.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and installed the app.
# Shopify delivers a genuine webhook for that shop:
raw_body = '{"id":1,"title":"my product"}'
hmac     = "<hmac Shopify computed with the real client_secret over raw_body>"

# Attacker replays the same body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop they do not own/control:
headers = {
  "x-shopify-topic"       => "products/update",
  "x-shopify-hmac-sha256" => hmac,          # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true, because
#    to_signable_string only covers raw_body.
# => handler.handle receives WebhookMetadata with shop == "victim-shop.myshopify.com",
#    even though the body actually came from the attacker's own shop.
```
