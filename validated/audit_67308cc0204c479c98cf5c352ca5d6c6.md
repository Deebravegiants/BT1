### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` (and `topic`) headers from the value that is HMAC-verified in `Utils::HmacValidator.validate`. The `shop` value is nevertheless trusted downstream and handed to the app's webhook handler as the tenant identifier. This breaks the intended identity binding: *"the shop the signature was computed for" ≠ "the shop the application acts on."*

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`: [2](#0-1) 

The signable string used for that check is defined on the `Request` object as just `@raw_body`: [3](#0-2) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers: [4](#0-3) 

`Registry.process` then forwards `request.shop` directly into the `WebhookMetadata` object passed to the app's handler as the tenant identifier, without any additional binding to the HMAC-verified payload: [1](#0-0) 

Because the HMAC only signs the body, any `(raw_body, hmac)` pair that was legitimately produced by Shopify for one shop remains cryptographically valid no matter what `shop-domain` header value accompanies it. An attacker who can capture (or otherwise obtain) one valid `(body, hmac)` pair — e.g., a webhook payload/signature pair delivered to a multi-tenant app they operate under their own installed shop, or leaked/logged webhook traffic — can replay that exact body+signature to the same endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the forged `shop` value to the application's handler as if it were authentic. This is a "field acted on but not covered by the HMAC" identity-binding break as called out in the analog rules: the equality that should hold — `shop used to compute/authorize the signature == shop delivered to the handler` — does not hold.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor holding one valid signed webhook body can cause the host application to process arbitrary webhook events labeled with a different shop's domain. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up a shop record, trigger shop-scoped side effects, or write shop-scoped data), this enables cross-tenant data corruption or spoofed events attributed to a shop that never sent them — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to first obtain a single valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`-derived HMAC. This is realistically achievable by any merchant who installs the app on their own shop (an unprivileged actor from the perspective of other tenants) and observes/replays their own webhook deliveries with a substituted `shop-domain` header, since nothing in this gem binds the header to the signed content. No access to the `api_secret_key` itself, and no privileged account beyond a standard app installation, is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the string that is HMAC-verified, or otherwise cryptographically bind the shop identity to the verified payload before it is passed to `WebhookMetadata`/application handlers. At minimum, document and enforce that consumers must independently verify `request.shop` against a known/installed shop record rather than treating it as authenticated by `HmacValidator.validate`.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (e.g., the operator of `shop-a`, who legitimately received this webhook) resends a POST to the app's webhook endpoint with the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop-b.myshopify.com` as `request.shop`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(secret, B)` (since `to_signable_string` ignores headers) and it still equals `H` → validation passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, causing the application to process an event as if it originated from `shop-b`, even though it was replayed by an actor associated with `shop-a`.
