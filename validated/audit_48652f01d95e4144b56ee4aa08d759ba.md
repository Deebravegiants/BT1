### Title
`is_face_detected()` only checks for NaN, not Infinity or out-of-bounds coordinates, allowing degenerate eye landmarks to pass as "face detected" - ([File: src/agents/python/rgb_net.rs])

### Summary
`EstimatePredictionOutput::is_face_detected()` at `src/agents/python/rgb_net.rs:280-285` verifies liveness only by calling `.is_nan()` on the left/right eye coordinates, but does not check for `Infinity`/`-Infinity` or whether the coordinates fall within valid image bounds (e.g. `[0.0, 1.0]`, similar to `Rectangle::is_correct()`). Since RGB-Net landmark output is derived from Python inference results that this Rust layer trusts, an attacker-influenced or degenerate detection (e.g. from a zero/near-zero user distance edge case) could produce `Infinity` or wildly out-of-range eye coordinates while `is_face_detected()` still reports `true`.

### Finding Description
`is_face_detected()` is defined as: [1](#0-0) 

It only guards against `NaN` via `f64::is_nan()`, with no bounds or finiteness check. Compare this to `Rectangle::is_correct()`, which does bound bbox coordinates to `[0.0, 1.0]`: [2](#0-1) 

There is no equivalent bounds/finiteness check for `Point`/landmark coordinates anywhere in this file. The landmark values are extracted directly from Python dict values via `extract_point`, with no validation: [3](#0-2) 

`user_distance()` uses the same eye coordinates to compute iris distance, and if `left_eye` and `right_eye` coincide, `iris_distance_in_percent` is `0.0`, producing `Infinity`: [4](#0-3) 

If an `Infinity` value ends up on `left_eye.x`/`.y` or `right_eye.x`/`.y` themselves (not just in `user_distance()`'s derived output), `is_face_detected()` would still return `true` because `Infinity.is_nan()` is `false` in IEEE-754 semantics.

### Impact Explanation
Given the stated call chain (`rgb_net_estimate` → `is_face_detected()` → `eye_tracker::Input::track` / `ir_auto_focus`), a `true` result gates downstream systems into treating garbage/degenerate coordinates as a valid detected face. This could steer eye-tracking or auto-focus state incorrectly and potentially wedge the capture loop, matching a liveness/fraud signal degradation rather than a direct signup bypass. I was not able to fully verify within available context whether `eye_tracker::Input::track` or `ir_auto_focus` perform their own independent bounds/finiteness validation on the coordinates before consuming them — that would materially affect actual exploitability, and I could not confirm this from the code retrieved. If such downstream validation exists, the practical impact is limited to a missing defensive check at this layer rather than an actual bypass.

### Likelihood Explanation
The precondition (attacker can induce a degenerate coincident/near-coincident eye landmark output influencing the RGB-Net model output through the presented scene) is plausible in principle for physical-world adversarial input to a face-detection/landmark model, but this audit could not verify from the retrieved code whether RGB-Net's own model output is bounded/clamped before being handed to Rust, nor could it verify the downstream consumers' handling. This limits confidence in real-world feasibility.

### Recommendation
Add finiteness and bounds checks to `is_face_detected()`, e.g. require `x.is_finite() && y.is_finite()` and bound checks against the normalized image range (matching the pattern used by `Rectangle::is_correct()`), for both `left_eye` and `right_eye` (and ideally all landmarks used downstream).
