### Title
Missing zero-address check on `feeStructure.feeRecipient` allows permanent burning of protocol/relay ETH fee - (File: `contracts/HinkalWrapper.sol`)

### Summary
`HinkalWrapper.prooflessDeposit` accepts a caller-supplied `ProoflessFeeStructure calldata feeStructure` and forwards it unchecked to `_settleFee`, which sends the ETH fee to `feeStructure.feeRecipient` via a raw `call`. Because `feeRecipient` is never validated to be non-zero, and a low-level `call{value: ...}("")` to `address(0)` succeeds without reverting, any unprivileged EOA can set `feeRecipient = address(0)` to permanently burn the protocol/relay's fee while their deposit still proceeds normally.

### Finding Description
`prooflessDeposit` is a fully public, unprivileged entry point: [1](#0-0) 

It calls `_settleFee`, which for the ETH-fee case transfers `feeStructure.feeAmount` directly to `feeStructure.feeRecipient` with no zero-address check: [2](#0-1) 

`transferETH` performs a raw low-level `call` with value and only checks `success`: [3](#0-2) 

A `call{value:_value}("")` to `address(0)` succeeds (it behaves like sending ETH to an EOA with no code), so `require(success, ...)` never trips. Unlike the ERC20 branch — where `safeTransferFrom` to `address(0)` would revert inside a standards-compliant token — the ETH branch has no such implicit protection. `feeStructure` is a raw, un-signed, uncommitted calldata argument chosen entirely by `msg.sender`; it is not part of any ZK proof's public inputs and is not checked anywhere else in the call path (`_pullAndApproveDepositTokens` and `IHinkal(hinkal).prooflessDeposit` never touch `feeRecipient`). This exactly matches the reported bug class: an unchecked `_to`-style parameter that silently accepts `address(0)` and leads to funds being unrecoverably lost instead of reverting.

### Impact Explanation
Any depositor can set `feeRecipient = address(0)` in `feeStructure` while still paying `feeAmount` out of `msg.value`; the fee ETH is sent to the zero address and permanently lost rather than reaching the protocol/relay. This is a permanent freezing of protocol/relay fees, matching the High-severity bullet "theft or permanent freezing of protocol/relay fees."

### Likelihood Explanation
High likelihood: `feeStructure` is a plain calldata struct supplied directly by any unprivileged EOA calling `prooflessDeposit`; no signature, proof, or on-chain registry constrains `feeRecipient`. Triggering the bug requires a single, ordinary transaction with `feeRecipient = address(0)`.

### Recommendation
Add a zero-address check on `feeStructure.feeRecipient` in `_settleFee` before transferring the fee, e.g. `require(feeStructure.feeRecipient != address(0), "HinkalWrapper: zero feeRecipient")`, mirroring the checks already present elsewhere in the contract (e.g. the constructor and `setHinkalAddress`).

### Proof of Concept
1. Attacker calls `HinkalWrapper.prooflessDeposit(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs, false, feeStructure, orderId)` with `feeStructure = { feeRecipient: address(0), feeToken: address(0), feeAmount: X }` and `msg.value >= X`.
2. `_settleFee` computes `ethForHinkal = msg.value - X` and executes `transferETH(address(0), X)`, which succeeds silently. [4](#0-3) 
3. The deposit continues normally via `IHinkal(hinkal).prooflessDeposit`, so the attacker's deposit is unaffected, but the `X` ETH intended for the protocol/relay is burned forever at `address(0)`.
