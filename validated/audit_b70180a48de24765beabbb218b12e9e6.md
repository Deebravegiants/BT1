Confirmed: `placeOrder` in `evm/src/apps/IntentGatewayV2.sol:194-211` checks only `order.inputs.length == 0` and rejects duplicate output tokens — it never bounds `order.inputs.length` or `order.output.assets.length`. Those user-controlled array lengths flow unchecked into `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`, looping `for (uint256 i; i < body.tokens.length; i++)`) and `_execute` (`IntentsBase.sol:498-510`, looping over `outputsLen`), and into the same-chain fill/cancel paths in `IntrinsicIntents.sol` (`_fillSameChain`-style loop at lines 61-119, `_cancelSameChain` at 159-180).

### Title
Unbounded order input/output array length in IntentGatewayV2 lets a user permanently lock their own escrow via out-of-gas withdrawal loop - (File: evm/src/apps/IntentGatewayV2.sol / evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder` accepts an `Order` whose `inputs` and `output.assets` arrays have no maximum length check [1](#0-0) . These same arrays are later iterated by `_withdraw` (escrow release/refund) and `_execute` (output-call sweep) with a `for` loop whose bound is exactly `body.tokens.length` / `outputsLen` [2](#0-1) [3](#0-2) , and by the same-chain fill/cancel loops in `IntrinsicIntents.sol` [4](#0-3) [5](#0-4) . This is structurally the same bug class as the reported `_updateRewards`/`recoverClaim`/`claim` issue: a dynamic, user-controllable array is looped over with no cap, so the loop's gas cost grows linearly (each iteration does a `SLOAD`, arithmetic, and either a `CALL`/native transfer or an `ERC20.transfer`) with attacker-controlled array size.

### Finding Description
A user calling `placeOrder` fully controls the number of entries in `order.inputs` and `order.output.assets`. Both counts are copied verbatim into escrow accounting and later replayed by:
- `_withdraw`, invoked on cancellation, refund, and fill finalization, which loops `body.tokens.length` times doing an `SLOAD` + `SSTORE` + a native/`ERC20` transfer per token [2](#0-1) .
- `_execute`, invoked on a full fill with output calldata, building a sweep array of size `outputsLen` and looping over it [3](#0-2) .
- `_cancelSameChain`, which loops `order.inputs.length` times to compute `remainingTokens` before calling `_withdraw` (a second loop) [5](#0-4) .
- The same-chain fill loop over `order.output.assets`, which does an `ERC20.safeTransferFrom` or native transfer per output token [4](#0-3) .

There is no `MAX_INPUTS`/`MAX_OUTPUTS`-style bound anywhere in this contract (confirmed via search — no such constant or length guard exists in `IntentGatewayV2.sol`/`IntentsBase.sol`/`IntrinsicIntents.sol`). A user (or an integrator building an order on a user's behalf) can construct an order with an arbitrarily large `inputs`/`output.assets` array. Escrowing the tokens at `placeOrder` time only needs enough gas to loop once per token during the deposit phase, which the placer pays for and controls. But cancellation/refund/fill-finalization is performed later (by the user themselves for cancel, or by a solver/relayer for fill), and if the array is large enough that the withdrawal loop's gas cost exceeds the block gas limit, `_withdraw`/`_execute`/`_cancelSameChain` can never complete successfully — the transaction always reverts out-of-gas, regardless of how much gas the caller supplies.

### Impact Explanation
Because `_withdraw` is the only code path that releases escrowed tokens (via `cancelOrder`, `fillOrder`, or the cross-chain settlement `onAccept` withdrawal), an order with enough distinct input/output tokens permanently locks the escrowed funds — for both the user's refund path and any solver's fill path. This is a **permanent freezing of funds** (escrowed tokens/native value become irrecoverable) triggerable by a single `placeOrder` transaction from an unprivileged, malicious or careless user. It is reachable without any privileged role, directly through the public `placeOrder` entrypoint.

### Likelihood Explanation
Medium: an attacker (or accidental misuse via a buggy integrator/SDK) simply has to submit `placeOrder` with a sufficiently long `inputs`/`output.assets` array — no special conditions, no race, no pre-existing state needed. The main uncertainty is the exact array length needed to exceed typical block gas limits given the per-iteration cost (`SLOAD` + `SSTORE` + external `call`/`safeTransfer`), which depends on the target EVM chain's gas limit; on chains with lower per-block gas limits this is easier to trigger. This mirrors the report's characterization as "Medium" severity for an unbounded loop over a dynamic array causing gas-exhaustion risk, escalated here to concrete fund-freezing impact since these arrays gate escrow release rather than a pure informational/reward claim.

### Recommendation
Add an explicit upper bound (e.g. `MAX_ORDER_TOKENS`) on `order.inputs.length` and `order.output.assets.length` in `placeOrder`'s validation (alongside the existing `order.inputs.length == 0` check at `evm/src/apps/IntentGatewayV2.sol:195`), sized so that `_withdraw`'s and `_execute`'s worst-case loop, plus surrounding fill/cancel logic, comfortably fits within the gas limit of every supported destination/source chain. Mirror the bound documented as best practice in the external report ("check on the max length the array can take").

### Proof of Concept
1. Call `placeOrder` with an `Order` whose `inputs` array contains N distinct ERC-20 tokens (each with a nonzero `amount`), where N is chosen so that N × (approx. cost of one `SLOAD` + `SSTORE` + `ERC20.transfer`) exceeds the chain's block gas limit — no length check rejects this at `evm/src/apps/IntentGatewayV2.sol:194-211`.
2. Approve and fund all N tokens; the deposit-side loop in `placeOrder`/predispatch runs once per token but the placer supplies gas for exactly one call, so deposit succeeds.
3. Attempt to cancel the order: `cancelOrder` → `_cancelSameChain` (loop over `inputsLen`) → `_withdraw` (second loop over the same length) at `evm/src/apps/intentsv2/IntrinsicIntents.sol:159-180` and `evm/src/apps/intentsv2/IntentsBase.sol:451-470`. The combined loops' gas cost exceeds the block gas limit; the transaction reverts out-of-gas no matter how it is submitted.
4. Attempt a fill via `fillOrder`/`IntrinsicIntents` fill path with N output assets — the same-chain fill loop at `evm/src/apps/intentsv2/IntrinsicIntents.sol:61-119` plus the `_withdraw` call it triggers exceed the gas limit as well, so no solver can ever fill the order.
5. Result: the escrowed tokens/native value from step 2 are permanently unrecoverable — neither refund nor fill can execute.
