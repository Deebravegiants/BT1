### Title
Persistent upload queue reuses numeric directory IDs while queued-but-unpopped `Pcp` entries still occupy those IDs on disk, causing cross-signup custody-package overwrite - ([File: src/agents/data_uploader.rs])

### Finding Description
`Queue::Persistent` assigns each pushed `Pcp` a directory name from a monotonically increasing `next_id` counter [1](#0-0) . The queue tracks in-flight (popped-but-not-committed) work with `in_progress`, incremented in `pop` [2](#0-1)  and decremented in `commit`, which resets `next_id` to `0` whenever `in_progress` reaches zero after a successful directory removal [3](#0-2) .

The reset logic is incorrect: `in_progress == 0` only guarantees that every previously *popped* id has been committed. It says nothing about ids that were *pushed* but never popped yet (still sitting at the tail of the in-memory `queue: VecDeque<u64>`, with their `meta.json`/`data.bin` still fully present on disk, waiting for an upload slot). Because `pop` is strictly FIFO (`queue.pop_front()`), any id still resident in `queue` is necessarily higher than every id that has ever been popped/committed in that "epoch."

Exploitable sequence (achievable simply by pushing tier1/tier2 `Pcp`s faster than the fixed `PARALLEL_UPLOAD_STREAMS = 4` upload slots can drain them, e.g., via rapid repeated signups):
1. `push(A)` → id 0, `push(B)` → id 1, `push(C)` → id 2. `queue=[0,1,2]`.
2. `pop()` pops A (id 0), `pop()` pops B (id 1); both begin uploading (`in_progress=2`). C (id 2) stays queued/unpopped — its `data.bin`/`meta.json` remain on disk untouched.
3. A's upload completes → `commit(0)`: `in_progress=1`, dir 0 removed; no reset (in_progress != 0).
4. B's upload completes → `commit(1)`: `in_progress=0`, dir 1 removed → **`next_id` reset to 0**, even though C's directory (id 2) is still fully populated and unpopped.
5. Subsequent pushes `D`, `E`, `F` are assigned ids `0`, `1`, `2` respectively. When `F` is pushed with id `2`, `push` calls `fs::create_dir_all` (no-op, dir exists) then unconditionally `fs::write`s `meta.json` and `data.bin`, silently overwriting C's still-queued, unuploaded custody-package files with F's data.

C's entry remains referenced at id 2 in `queue`, so when eventually popped, it will read back F's overwritten data under C's slot — C's tier1/tier2 personal custody package (potentially biometric material) is irretrievably lost/replaced by another signup's data, with no error surfaced anywhere. `commit`/`push`/`pop` never validate that a target directory is free of an unrelated live entry before writing/removing.

### Impact Explanation
This causes silent cross-signup data corruption of the personal-custody-package (PCP) upload pipeline: one user's tier1/tier2 biometric custody bytes can be overwritten by another signup's package before upload, and the original signup's `Pcp` is lost without any error or retry, while the overwriting signup's data gets uploaded under the wrong association context still tracked as "id 2" in-memory. This matches a cross-signup state bleed / biometric data integrity impact category — data intended to remain bound to one signup ends up corrupted/replaced by unrelated signup data on the local upload queue.

### Likelihood Explanation
This requires no privileged access — only that a normal self-serve user (or automated rapid-signup flow) generate PCP pushes faster than the fixed 4 concurrent upload streams can drain them (easily done with fast repeated signups on a slow/degraded network link, which increases in-flight upload duration and queue backlog). No thread-level race or timing attack precision is needed: it depends only on ordinary out-of-order completion of concurrent HTTP uploads (`FuturesUnordered` in `Agent::run`) while a queue backlog exists, which is a normal, repeatable operating condition, not a rare race.

### Recommendation
Do not reset `next_id` to `0` based solely on `in_progress == 0`. The reset must also confirm the in-memory `queue` (pending, unpopped entries) is empty, e.g. `if *in_progress == 0 && queue.is_empty() { *next_id = 0; }`, or better, avoid the reset heuristic altogether and instead always increment `next_id` and only reclaim it by scanning existing directory entries on `Queue::new`, or use a UUID-per-`Pcp` directory name instead of a reused numeric counter so ids can never collide regardless of in-flight/queued state.

### Proof of Concept
Add an invariant test to `src/agents/data_uploader.rs`'s test module:
```rust
#[tokio::test]
async fn test_persistent_queue_id_reuse_corrupts_unpopped_entry() {
    let tempdir = tempdir().unwrap();
    let mut queue = Queue::new(tempdir.path().to_path_buf()).await;

    let mk = |b: u8| Pcp {
        signup_id: SignupId::default(),
        user_id: "test".to_string(),
        data: vec![b],
        checksum: vec![b],
        tier: 0,
    };

    queue.push(mk(1)).await; // id 0 -> A
    queue.push(mk(2)).await; // id 1 -> B
    queue.push(mk(3)).await; // id 2 -> C (will remain unpopped)

    let (_a, id_a) = queue.pop().await.unwrap(); // pops id 0
    let (_b, id_b) = queue.pop().await.unwrap(); // pops id 1
    // C (id 2) intentionally left un-popped, simulating upload-slot backlog.

    queue.commit(id_a).await; // in_progress: 2 -> 1
    queue.commit(id_b).await; // in_progress: 1 -> 0 -> BUG: next_id reset to 0

    queue.push(mk(4)).await; // reassigned id 0
    queue.push(mk(5)).await; // reassigned id 1
    queue.push(mk(6)).await; // reassigned id 2 -> collides with still-unpopped C!

    // Popping should now yield C's original signup data intact, but it is
    // overwritten by the newly-pushed value 6.
    let (pcp_at_slot_2, id) = queue.pop().await.unwrap();
    assert_eq!(id, 2);
    assert_eq!(pcp_at_slot_2.data, vec![3], "C's data must not be overwritten by a later push");
}
```
Expected: the assertion fails on current code (`pcp_at_slot_2.data == vec![6]` instead of `vec![3]`), demonstrating the cross-signup overwrite; after applying the fix (`queue.is_empty()` guard or unique directory ids), the assertion passes.
