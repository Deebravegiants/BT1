### Title
`process_deposit` never validates that user-supplied coin/pc token accounts have the pool's mints, allowing unbacked LP minting - (File: `program/src/processor.rs`)

### Summary
`process_deposit` verifies that the vault accounts passed in are the AMM's real `coin_vault`/`pc_vault`, but it never checks that the *user-supplied* `user_source_coin_info` / `user_source_pc_info` accounts actually hold the pool's `coin_vault_mint` / `pc_vault_mint`. This is the same bug class as the reported Zap `redeem()` finding: the function accepts an attacker-chosen token account without validating which token it actually represents, before moving value based on that account.

### Finding Description
In `Self::process_deposit` (`program/src/processor.rs`), the only checks performed on the user source accounts are key-equality/anti-vault checks: [1](#0-0) 
There is no subsequent check such as `user_source_coin.mint == amm_coin_vault.mint` or `user_source_pc.mint == amm_pc_vault.mint`. Compare this to `process_withdraw` and the swap handlers in the same file, which explicitly enforce mint equality before moving funds: [2](#0-1) [3](#0-2) 

After computing `deduct_coin_amount`/`deduct_pc_amount` from the pool's normalized reserves, `process_deposit` transfers straight from the unchecked user accounts into the real vaults and mints LP tokens proportional to the deposit: [4](#0-3) 

`Invokers::token_transfer` invokes the SPL token program's basic `Transfer` instruction, which (unlike `TransferChecked`) does not take or validate a mint account — it only checks signer/delegate authority and that `amount <= source.amount`. It does **not** verify that the source and destination token accounts share the same mint. Because `process_deposit` never separately checks `user_source_coin.mint`/`user_source_pc.mint` against the pool's expected mints, an attacker can supply their own token account of an arbitrary (e.g. worthless) SPL mint as `user_source_coin_info` or `user_source_pc_info`. The transfer will still succeed and will increase the raw `amount` field of `amm_coin_vault`/`amm_pc_vault`, since SPL Token's plain transfer path only manipulates the `amount` field of the two accounts without mint cross-validation.

The pool's internal reserve accounting used to compute LP minting is based directly on this raw vault `amount`: [5](#0-4) [6](#0-5) 

so an attacker who deposits an arbitrary/worthless-mint token as the "coin" (or "pc") side receives real, legitimate LP tokens minted against the pool's genuine reserves.

### Impact Explanation
This directly causes insolvent pool accounting and unbacked LP minting: the attacker's deposit does not add real backing value into the pool's actual coin/pc mints, yet mints LP tokens that represent a claim on the pool's genuine reserves. Subsequent withdrawal by the attacker (which does correctly validate mints on the way out) would let them redeem real coin/pc tokens for worthless deposited tokens, draining value from other LPs — a permanent freezing/theft of LP funds.

### Likelihood Explanation
The `Deposit` instruction is reachable by any unprivileged user in a single transaction with attacker-chosen accounts (the user picks `user_source_coin_info`/`user_source_pc_info`), matching the constraint that only the user needs to control the accounts; no privileged signer or off-chain component is required. The missing check is a straightforward omission relative to the mint checks present in the sibling `process_withdraw` and swap handlers in the same file, making the vulnerable code path easy to identify and exploit if the underlying assumption about `Invokers::token_transfer` (plain SPL `Transfer`, no mint validation) holds.

### Recommendation
Add explicit mint validation for `user_source_coin_info` and `user_source_pc_info` in `process_deposit`, mirroring the checks already present in `process_withdraw`:
```rust
if user_source_coin.mint != amm_coin_vault.mint || amm.coin_vault_mint != user_source_coin.mint {
    return Err(AmmError::InvalidCoinMint.into());
}
if user_source_pc.mint != amm_pc_vault.mint || amm.pc_vault_mint != user_source_pc.mint {
    return Err(AmmError::InvalidPCMint.into());
}
```

### Proof of Concept
1. Attacker creates a new SPL mint `M` and mints themselves a large balance in a token account `A` of mint `M`.
2. Attacker calls the `Deposit` instruction, passing `A` as `user_source_coin_info` (or `user_source_pc_info`) alongside the real `amm_coin_vault`/`amm_pc_vault` and a legitimate `user_source_pc_info` (or vice versa) for the other leg.
3. `process_deposit` only checks that the vault account key equals `amm.coin_vault`/`amm.pc_vault` and that the user source account isn't literally the vault key [1](#0-0) ; it performs no mint check on the user source accounts.
4. `Invokers::token_transfer` moves `deduct_coin_amount` raw units from account `A` (mint `M`) into `amm_coin_vault`, increasing the vault's tracked `amount` even though the transferred tokens are not the pool's real coin mint.
5. `process_deposit` then mints real LP tokens to the attacker based on this inflated reserve calculation [7](#0-6) , giving the attacker a claim on the pool's genuine assets in exchange for worthless tokens.
