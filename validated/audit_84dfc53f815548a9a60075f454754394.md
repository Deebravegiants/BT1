This confirms the vulnerability. The docs explicitly state that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" via HMAC, and that `data.shop` is documented as "The shop domain of the webhook" for host apps to key their tenant logic on [1](#0-0) [2](#0-1) . But the HMAC signable string used for verification is only the raw body, never the shop-domain header [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop` from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, but the HMAC signature that `HmacValidator.validate` checks is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` field is passed on as the trusted tenant identifier to the app's webhook handler, but it is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `HMAC(api_secret_key, raw_body)` against the `X-Shopify-Hmac-Sha256` header [4](#0-3) . The `AuthQuery`/webhook `VerifiableQuery` implementation for `Request` defines `to_signable_string` as simply `@raw_body`, excluding `topic`, `shop`, `webhook_id`, and `api_version` [5](#0-4) . After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using `request.shop`, which is read straight from the (attacker-controllable, unauthenticated-by-HMAC) header `shopify-shop-domain` [6](#0-5) [7](#0-6) .

This breaks the intended identity binding: `shop header value == cryptographically-authenticated tenant`. In reality the equality only holds for `raw_body`; `shop`, `topic`, and `webhook_id` are unauthenticated companions to a valid signature. Since the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it's an app-level secret, not a per-shop secret), any unprivileged user who installs the app on their own store can generate a genuinely-signed webhook payload (e.g. a predictable-body topic like `app/uninstalled`, or any topic where the JSON body is attacker-influenced/predictable), then replay those exact bytes to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the shared secret — it does not bind the signature to the shop that produced it.

### Impact Explanation
The host application, following the gem's own documented contract, uses `data.shop` from `WebhookMetadata` as the trusted tenant key (e.g. to look up/update/delete records for "that shop", or to act on `app/uninstalled`, `shop/redact`, `customers/redact` for "that shop") [8](#0-7) . An attacker who merely installs the app on their own shop (no access token theft, no `client_secret` access, no privileged account) can forge the shop identity attached to an otherwise validly-signed webhook and cause the app to execute tenant-scoped business logic against a different (victim) shop's data — a cross-tenant access/confusion vulnerability that maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate to high in practice: the attacker only needs unprivileged self-service access (install the app on their own store), the ability to capture/replay the resulting HTTP webhook request to the app's public callback endpoint, and knowledge/control of a topic with a predictable or attacker-influenced body (many topics qualify, e.g. `app/uninstalled` typically has a minimal, predictable body). No secret keys, tokens, or social engineering are required — only the gem's own webhook-processing surface, exactly as documented.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them, e.g. by validating the shop against a shop-scoped secret/registration record) so that `HmacValidator.validate` fails whenever these header fields are altered after signing. At minimum, document that `data.shop`/`data.topic` in `WebhookMetadata` are not authenticated by the HMAC and must be independently cross-checked (e.g. against the shop for which the app registered that specific webhook subscription) before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker triggers/waits for a webhook with a predictable body, e.g. `app/uninstalled` with body `{}`, and captures the request: headers include a valid `X-Shopify-Hmac-Sha256` computed as `HMAC-SHA256(api_secret_key, "{}")`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same raw body `{}` and the same valid `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged request; `HmacValidator.validate` computes `HMAC(api_secret_key, "{}")` and it matches, per [3](#0-2)  and [9](#0-8) .
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` [4](#0-3) , causing the host app to execute uninstall/data-cleanup logic for `victim.myshopify.com` even though it never uninstalled the app.
