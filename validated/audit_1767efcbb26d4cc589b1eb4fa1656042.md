### Title
IntentGatewayV2.cancelOrder requires order owner even after expiry on the source-chain (GET-proof) branch, unlike the destination-chain branch — ([File: evm/src/apps/IntentGatewayV2.sol](evm/src/apps/IntentGatewayV2.sol))

### Summary
`cancelOrder` has two branches depending on whether it is invoked on the order's source chain or on its destination chain. On the destination-chain branch, once `order.deadline < block.number` the owner check is skipped and the call becomes permissionless. On the source-chain branch, which dispatches a `GET` request to verify non-fill on the destination and ultimately drives the escrow refund, the code unconditionally requires `msg.sender == order.user`, *even though it also requires the order to already be expired* (`options.height <= order.deadline` reverts with `NotExpired()`). This mirrors the reported Union Finance bug class: a flow that is meant to become publicly triggerable once a time-based condition (expiry/overdue) is met is actually still internally gated by an owner-only check, so the "public after timeout" path is unreachable by anyone but the order owner.

### Finding Description
`cancelOrder` in `IntentGatewayV2.sol` branches on `currentChain`:

- Source-chain branch (querying the destination for fill status via a `GET` request): [1](#0-0) 
```
// source chain: fetch storage proof from destination
// only owner can cancel order
if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

// order has not yet expired
if (options.height <= order.deadline) revert NotExpired();
```
This requires the order to be expired (`options.height > order.deadline`) to proceed, but *still* unconditionally requires `msg.sender == order.user`.

- Destination-chain branch (marking the order cancelled and dispatching the refund body to the source chain): [2](#0-1) 
```
} else if (currentChain == orderDest) {
    // destination chain: dispatch RefundEscrow request to source chain
    // If order hasn't expired, only owner can cancel
    if (order.deadline >= block.number) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }

    // Mark as cancelled locally to prevent fills
    _filled[commitment] = address(uint160(uint256(order.user)));
```
Here the owner check is explicitly scoped to "not yet expired" — post-expiry, anyone can call it.

The inconsistency means that when a user's order is on chain A and its `dest` is chain B, cancelling it from chain A (the branch that fetches the storage proof of non-fill from chain B and is the entry point of the refund-escrow flow) can never be triggered by anyone except `order.user`, no matter how long past the deadline. If the order owner is unresponsive, has lost keys, or simply has no incentive to spend gas to unlock their own already-forfeited escrow (e.g., dust amounts, or they expect fillers/relayers to do it), no other party — filler, relayer, or protocol keeper — can permissionlessly drive the expired order's refund path from the source chain, unlike the symmetric destination-chain branch which is intentionally made public after expiry.

### Impact Explanation
This creates a route where cross-chain intent escrow can become permanently stuck: the source-chain-side cancellation of an expired order is the entry point for the GET-proof/refund flow, and its owner-only restriction blocks any relayer, keeper, or third party from ever completing this leg once the user is unwilling or unable to act. Funds locked in escrow for an expired, un-filled order can remain frozen indefinitely absent the specific `order.user` address's action, which is a freezing-of-funds condition consistent with a Medium severity per the analog bug class.

### Likelihood Explanation
Likelihood is moderate: it requires an order to expire without being filled (a routine occurrence for intents that go unfilled), and the order owner to be unwilling/unable to submit the cancellation transaction (lost keys, low economic incentive relative to gas, or address is a contract without the ability to call). Given intents systems commonly rely on keepers/relayers for lifecycle management, this asymmetry is likely to matter in practice whenever the owner doesn't self-serve the cancellation.

### Recommendation
Mirror the destination-chain branch's logic in the source-chain branch: only enforce the `order.user == msg.sender` check when the order has **not** yet expired, and allow any caller to trigger the GET-request-driven cancellation once `options.height > order.deadline`, e.g.:
```solidity
if (options.height <= order.deadline) revert NotExpired();
if (order.deadline >= /* corresponding time reference */) {
    if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
}
```
This makes the permission model consistent across both branches and ensures that after expiry, escrow can be permissionlessly unlocked by anyone (relayers/keepers), removing the single point of failure on `order.user`'s cooperation.

### Proof of Concept
1. User dispatches an order on chain A (`orderDest` = chain B) with `deadline = D`.
2. Order is never filled on chain B.
3. Block height (or timestamp, per implementation) on chain A/B passes `D`.
4. Any third party (relayer/keeper) attempts to call `cancelOrder` on chain A to initiate the GET proof of non-fill and drive the refund — this reverts with `Unauthorized()` because `msg.sender != order.user`, even though `NotExpired()` would not have reverted (order is indeed expired).
5. Only `order.user` can call this function to unlock their own escrow; if they never do, the escrowed funds are permanently stuck on chain A. [3](#0-2) [4](#0-3)
