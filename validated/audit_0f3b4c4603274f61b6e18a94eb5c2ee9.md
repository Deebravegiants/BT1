## Title
Webhook `shop` and `topic` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that is computed **only over the raw request body**, yet it forwards the `shop` and `topic` values — which come from HTTP headers that are **not included in the signed bytes** — straight to the app's webhook handler as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed directly from HTTP headers, with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the *body* bytes were signed with `api_secret_key`) and then immediately treats `request.shop`/`request.topic` as authenticated tenant/topic identity, passing them into `WebhookMetadata` for the app's handler: [3](#0-2) 

Because `shop` is never part of `to_signable_string`, the equality the gem implicitly claims — "HMAC-verified request" == "`shop` header can be trusted as the tenant" — does not hold. Any two requests with identical raw bodies (e.g. a nearly-empty payload, which is common for several webhook topics, or a payload an attacker fully controls from their own shop's genuine webhook deliveries) produce the same valid `hmac`, regardless of which `shop-domain`/`topic` header accompanies them. An unprivileged user who legitimately installs the app on their own store receives real, validly-signed webhook deliveries (Shopify signs with the app's own `api_secret_key`, which the gem's consumer never exposes to the attacker). That user can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different merchant's domain and/or a different `x-shopify-topic`. `Utils::HmacValidator.validate` still succeeds because it only checks the body against the secret, and the forged `shop`/`topic` are passed through unchanged to the handler.

### Impact Explanation
Apps built on this gem are documented to key their business logic off `WebhookMetadata#shop` (e.g. looking up the tenant's session, updating the tenant's stored order/product data) — see the docs' own example handler passing `data.shop` straight into application logic. Because that field is unauthenticated, a user who is a legitimate (but unprivileged) merchant on the platform can cause the app to process webhook data under a **different tenant's identity**, i.e. cross-tenant access/data corruption, without ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim shop.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to operate their own shop with the app installed (an ordinary, unprivileged capability) and to know or guess a target `shop-domain` (public information, since it's the store's `myshopify.com` handle) and a raw body that collides with a payload they can legitimately obtain a signature for (trivial for topics with empty/near-empty bodies).

### Recommendation
Bind `shop` (and ideally `topic`) into the HMAC-signed material, or otherwise verify the header-supplied shop against Shopify out-of-band (e.g. cross-check against the mandatory `verify webhook` API, or require the shop to already exist in the app's known-installed-shops set as an offline session lookup before trusting `data.shop`). At minimum, update `Request#to_signable_string` to incorporate the `shop-domain` and `topic` headers so a mismatched/forged header invalidates the HMAC.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`, receiving genuine webhook deliveries signed by Shopify with the app's real `api_secret_key`.
2. Attacker captures a delivery whose body is empty/minimal, e.g. `raw_body = "{}"`, `hmac = H(secret, "{}")` (valid, since it's their own legitimate webhook).
3. Attacker POSTs to the app's webhook endpoint with the same body/hmac but headers rewritten:
```
x-shopify-topic: shop/redact
x-shopify-hmac-sha256: <same valid hmac for "{}">
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `Utils::HmacValidator.validate` passes (only `"{}"` is checked), and `Registry.process` invokes the handler with `data.shop == "victim-shop.myshopify.com"`, `data.topic == "shop/redact"`, despite neither ever having been produced/authorized by Shopify for that shop or topic. [4](#0-3) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
