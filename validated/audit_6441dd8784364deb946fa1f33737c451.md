### Title
`EmporiumUpgradeable.runAction`'s Stateless Interaction branch lets an attacker forge a nested `CircomData` to steal a victim's ERC20 allowance via `DepositOnChainUtxosExternalAction` - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s "Stateless Interaction" branch (CASE 2) only blacklists the `IHinkalWallet.callHinkalWallet`/`doSendToRelay` selectors before doing a raw `op.endpoint.call(op.callData)`, but places no restriction on calling any other allowed `IExternalActionV2.runAction` with an attacker-supplied, unverified nested `CircomData`. When the nested target is `DepositOnChainUtxosExternalAction` and Emporium is one of its allowed recipients, the attacker can set `forgedCircomData.originalSender = victim` to pull the victim's pre-approved ERC20 tokens directly into Emporium's balance, then have Emporium's own post-call accounting mint that increase as a UTXO to the attacker.

### Finding Description
Equality that should hold in `EmporiumUpgradeable.runAction`: for each token `i`, `balanceChange_i` (Emporium's own balance delta) must equal `-deltaAmountChanges[i]` (funds legitimately routed to Emporium through the outer, proof-verified `CircomData`) plus whatever the invoked op legitimately moved on Emporium's behalf. Concretely the contract computes:
```solidity
int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
if (deltaAmountChanges[i] < 0) {
    balanceChange -= deltaAmountChanges[i];
}
...
UTXO memory utxoOut = handleOut(balanceChange, circomData, i);
``` [1](#0-0) 

This equation implicitly assumes any positive balance increase on Emporium came either from the outer proof's `deltaAmountChanges` or from an op that legitimately transferred funds "for" the caller. That assumption is broken because CASE 2 of the op loop performs no validation of what the called contract actually does or whose funds it moves:
```solidity
else {
    bytes4 selector = bytes4(op.callData);
    if (selector == IHinkalWallet.callHinkalWallet.selector ||
        selector == IHinkalWallet.doSendToRelay.selector) {
        revert UnauthorizedWalletCall();
    }
    (success, err) = op.endpoint.call{value: op.value}(op.callData);
}
``` [2](#0-1) 

The attacker's exact call:
1. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)` with a self-generated valid proof where `circomData.erc20TokenAddresses = [victimToken1, victimToken2]`, `circomData.amountChanges = [0,0]`, `circomData.originalSender = attacker` (or `address(0)` with a relay), `circomData.externalActionData.externalAddress = Emporium`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encodes an `EmporiumStack` with one `EmporiumOperation{invokeWallet:false, endpoint: DepositOnChainUtxosExternalAction, callData: abi.encodeCall(runAction,(forgedCircomData,[0,0]))}`. `performHinkalChecks` only validates the outer `circomData` fields (`originalSender==sender`, `dimensionsCheck`, `checkOnchainCreation`, `calldataHash`); it never inspects the opaque bytes of `externalActionMetadata`, so `forgedCircomData` (a second, independent `CircomData` struct nested inside the call data) is completely unchecked. [3](#0-2) 
2. `Hinkal._externalTransact` computes `deltaAmountChanges = [0,0]` (since outer `amountChanges` are 0) and calls `Emporium.runAction(circomData, [0,0])` — `msg.sender` at Emporium is `Hinkal`. [4](#0-3) 
3. Inside `Emporium.runAction`, the loop hits CASE 2 for the single op, selector is `IExternalActionV2.runAction.selector` (not blacklisted), so Emporium does `DepositOnChainUtxosExternalAction.call(runAction(forgedCircomData,[0,0]))`, making `msg.sender` at `DepositOnChainUtxosExternalAction` equal to **Emporium's address**.
4. `DepositOnChainUtxosExternalAction.runAction` passes its own `onlyAllowedRecipient` check because Emporium is a listed allowed recipient (precondition), reads `userAddress = forgedCircomData.originalSender = victim`, and pulls the victim's pre-approved tokens: `transferERC20TokenFrom(tokenAddress, victim, msg.sender=Emporium, tokenTotal)` for both tokens. [5](#0-4) 
5. Back in `Emporium.runAction`, `balancesAfter[i] - balancesBefore[i] = tokenTotal_i` for both tokens; since `deltaAmountChanges[i] == 0` (not `<0`), the `-=` correction never fires, so `balanceChange = tokenTotal_i` is treated as a legitimate deposit and `handleOut` mints a real UTXO of `tokenTotal_i` under the **attacker's** `circomData.stealthAddressStructure`, transferring the tokens from Emporium to `msg.sender` (Hinkal). [6](#0-5) 
6. Hinkal's outer accounting (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied trivially because `amountChanges[i]=0` and `utxoAmount=tokenTotal_i` matches Hinkal's own balance increase from Emporium forwarding the stolen tokens. [7](#0-6) 

Existing guards fail to catch this because: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only run on the outer `CircomData`, never on `forgedCircomData` hidden in `externalActionMetadata`; the `calldataHash` integrity check only proves the *attacker's own* calldata is self-consistent, not that the nested `originalSender` is legitimate; `onlyAllowedRecipient` on `DepositOnChainUtxosExternalAction` only checks that the immediate caller (Emporium) is whitelisted, with no notion of "on whose behalf"; and the Emporium selector blacklist only excludes the two `IHinkalWallet` functions, not arbitrary `IExternalActionV2.runAction` calls.

### Impact Explanation
Direct, permissionless theft of any ERC20 balance a victim has approved to `DepositOnChainUtxosExternalAction` (a standard, expected approval for normal Hinkal deposit users), across multiple tokens in a single transaction, with the stolen value minted as a spendable shielded UTXO for the attacker. This is theft of user funds and creation of a UTXO backed entirely by someone else's tokens — Critical severity. The attack is repeatable against every victim address with a live approval and nonzero balance, and across every token pair, until either the misconfiguration (Emporium listed as allowed recipient on `DepositOnChainUtxosExternalAction`) is fixed or all such approvals are revoked.

### Likelihood Explanation
Requires: (a) `DepositOnChainUtxosExternalAction` to list Emporium as an allowed recipient — plausible given Emporium's designed purpose of chaining calls to other allowed action endpoints for compound operations; (b) a victim who has approved `DepositOnChainUtxosExternalAction` (an ordinary consequence of using the on-chain-UTXO deposit flow) and left an allowance/balance available. Attacker cost is a single self-generated proof for a trivial zero-amount, two-token pass-through transaction plus gas — no privileged role, no victim signature, and no cooperation from any other party is needed.

### Recommendation
In `EmporiumUpgradeable.runAction`'s Stateless Interaction branch, do not permit calling any `IExternalActionV2.runAction` (or any function whose ABI accepts a `CircomData`) via arbitrary op `callData`. Either restrict `op.endpoint` targets to a strict allowlist of non-`CircomData`-consuming functions, or require that any embedded `CircomData` passed to a nested action be structurally bound to (and validated against) the outer, proof-verified `circomData` — in particular `originalSender` must be forced to equal the outer `circomData.originalSender`/`msg.sender`, and `erc20TokenAddresses`/amounts must be re-derived rather than trusted from attacker-supplied metadata.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction` with `DepositOnChainUtxosExternalAction`'s allowed recipients including Emporium's address (the assumed misconfiguration).
2. Deploy two ERC20 mocks (`victimToken1`, `victimToken2`); mint balances to `victim`; have `victim` call `approve(DepositOnChainUtxosExternalAction, MAX)` for both tokens.
3. Attacker builds outer `circomData` with `erc20TokenAddresses=[victimToken1, victimToken2]`, `amountChanges=[0,0]`, `externalActionData.externalAddress = Emporium`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` encoding an `EmporiumStack` with one op `{invokeWallet:false, endpoint: DepositOnChainUtxosExternalAction, value:0, callData: abi.encodeCall(IExternalActionV2.runAction, (forgedCircomData, [0,0]))}` where `forgedCircomData.originalSender = victim`, `forgedCircomData.erc20TokenAddresses=[victimToken1,victimToken2]`, and `externalActionData.externalActionMetadata` encoding `uint256[][] utxoAmounts` for both tokens with `attacker`'s `stealthAddressStructure`.
4. Attacker generates a valid proof for this trivial 2-token, zero-amount, zero-nullifier transaction and calls `Hinkal.transact(...)`.
5. Assert: `victimToken1.balanceOf(victim)` and `victimToken2.balanceOf(victim)` each drop by the full `tokenTotal`; assert the emitted on-chain UTXO commitments (from `utxoSet`) under attacker's stealth address sum to exactly the two `tokenTotal` amounts stolen; assert no negative `deltaAmountChanges` or nullifier was ever recorded to account for this outflow, proving the equality `tokens leaving action (0) == -deltaAmountChanges received (0)` is violated by the actual `tokenTotal1 + tokenTotal2` gained by Emporium/attacker.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
