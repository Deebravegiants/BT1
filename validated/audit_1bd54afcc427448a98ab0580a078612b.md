### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated HTTP headers while only the raw body is covered by the HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC signature it validates is computed only over the raw request body. The `shop`, `topic`, and `webhook_id` values that are handed to the app's handler as the trusted tenant/event identity come from HTTP headers that are never included in the signed material, breaking the equality `HMAC-verified bytes == bytes the handler trusts as (shop, topic)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled straight from caller-supplied headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC of `request` (i.e. the body) and then immediately trusts `request.topic` and `request.shop` to route and label the payload for the handler: [3](#0-2) 

The identity binding that should hold is: `HMAC(secret, signed_bytes) valid ⇒ signed_bytes were sent by Shopify for shop X, topic Y`. In this implementation the binding actually enforced is only `HMAC(secret, raw_body) valid`, with `shop`/`topic`/`webhook_id` carried outside the MAC. Any actor who can obtain one genuine, validly-signed webhook delivery for a topic (e.g. a merchant who installs the app on their own store and receives real Shopify webhooks to a URL they control) can capture the `(raw_body, hmac)` pair and replay it to the app's webhook controller with the `shop-domain`/`topic`/`webhook-id` headers changed to any values they choose. `Utils::HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `raw_body`, and `Registry.process` will hand the (attacker-chosen) `shop` and `topic` straight to the app's handler: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" analog: the shop/topic identity that downstream handlers rely on for tenant separation is not part of the authenticated bytes, even though the gem's own documentation states this call "will verify the request did indeed come from Shopify" — implying the full identity, not just the payload bytes, is verified: [5](#0-4) 

### Impact Explanation
Because `client_secret`/`api_secret_key` is shared per-app across all installed shops (not per-shop), a single valid signed webhook obtained from any shop where the app is installed can be replayed with a forged `shop-domain` header to make the app process attacker-supplied data as if it came from a different, victim shop. Depending on the handler's logic (order creation, fulfillment, customer data updates, app-uninstalled/GDPR flows, etc.), this enables cross-tenant data injection or corruption without possessing the victim's credentials — meeting the "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on any shop (which is typically self-serve for public apps) to receive one legitimate signed webhook, and (2) replaying that body+HMAC to the app's public webhook endpoint with modified `shop-domain`/`topic` headers. No access to `api_secret_key` or any victim credential is needed, making this practically reachable by any unprivileged user of a public app built on this gem.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the authenticated material used by `Registry.process`/`HmacValidator`, or otherwise cryptographically tie the header values to the verified body (e.g., include them in `to_signable_string`, or independently verify that the `shop` claimed in the header matches a shop for which the app has an active, previously-established session/registration) before dispatching to the handler.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com`; register for a webhook topic (e.g. `orders/create`) pointing at an attacker-controlled endpoint or proxy in front of the real app endpoint.
2. Capture a genuine delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because Shopify signed it with the app's shared `client_secret`).
3. Replay a new HTTP request to the real app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` accepts it; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`; `Registry.process` dispatches to the handler with `data.shop == "victim-shop.myshopify.com"`, causing the app to act on attacker data under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
