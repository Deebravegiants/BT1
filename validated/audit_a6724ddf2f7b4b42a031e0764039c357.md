## Title
Missing chain_id domain separator in `SignerCapabilityOfferProofChallengeV2` enables cross-network replay of signer-capability grants - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` authorizes delegation of full custody of an account (and any resource account signer it controls) to a `recipient_address`, based on an off-chain signature over `SignerCapabilityOfferProofChallengeV2`. Unlike the sibling `RotationCapabilityOfferProofChallengeV2` struct, which was explicitly upgraded to include a `chain_id` field "to prevent replaying the challenge message," `SignerCapabilityOfferProofChallengeV2` was never given the same treatment and only binds `sequence_number`, `source_address`, and `recipient_address`.

### Finding Description
In `account.move`, the two "V2" proof-challenge structs are defined back-to-back: [1](#0-0) 

The doc comment on `RotationCapabilityOfferProofChallengeV2` is explicit about the security rationale for adding `chain_id`: "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message." No equivalent field or comment exists for `SignerCapabilityOfferProofChallengeV2`.

`offer_signer_capability` builds the challenge purely from on-chain state, signs/verifies it, and then unconditionally overwrites the account's `signer_capability_offer.for`: [2](#0-1) 

The only anti-replay binding is `sequence_number` (which prevents replay on the *same* chain after the sequence number advances) and `source_address`/`recipient_address`. There is no `chain_id`, so a signature that authorizes granting signer capability is valid on any Aptos network (mainnet, testnet, devnet, or any future/forked network) where the same account address exists with a matching sequence number and the same intended recipient address is present. This is precisely the missing-binding pattern flagged in the external report: a Fiat-Shamir/challenge-style commitment omits a value (network/context identifier) that an attacker can hold constant across different execution contexts to reuse a signature outside its intended scope.

The verification path (`verify_signed_message`) only checks the signature against the struct contents and the current auth key — it has no independent chain-id check to compensate for the missing field: [3](#0-2) 

By contrast, `rotate_authentication_key`'s `RotationProofChallenge` includes `sequence_number` bound to the account being rotated as well as `current_auth_key`, and `RotationCapabilityOfferProofChallengeV2` deliberately adds `chain_id`, showing that the framework authors treat missing chain binding as a real replay vector elsewhere in this exact file, but the fix was not applied consistently to the signer-capability offer path.

### Impact Explanation
`SignerCapability` is a root-of-custody primitive: whoever holds it can call `create_signer_with_capability` and act with the full authority of the source account, including any resource account, code object, or asset-holding account built on top of it (see `resource_account.move`, `package_manager.move`, `common_account.move`, all of which store and later exercise a `SignerCapability`). A replayed `offer_signer_capability` grant therefore hands an attacker-controlled `recipient_address` unrestricted custody of the source account and everything it owns — APT balances, fungible asset stores, objects, and any resource/contract accounts derived from it — satisfying the "Unauthorized takeover of ... resource-account control ... tied to live assets" and "Theft ... of APT, fungible assets, token objects" custody-impact criteria.

### Likelihood Explanation
Exploitation requires an attacker to obtain a validly-signed `SignerCapabilityOfferProofChallengeV2` message (e.g., from a devnet/testnet interaction, a wallet demo, or a leaked/observed transaction) and then find or cause the same account address + sequence number + recipient address to exist on a different live network. This is a real but narrower condition than a same-chain replay, so likelihood is lower than the missing-`chain_id` bug would be for `RotationCapabilityOfferProofChallengeV2` (which the team already fixed); nonetheless it is a genuine, code-provable inconsistency in domain separation on a custody-critical capability grant, not a theoretical restatement of the original KZG report.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (matching `RotationCapabilityOfferProofChallengeV2`), populate it from `chain_id::get()` in `offer_signer_capability`, and bump/version the struct so existing off-chain signing flows are updated. This makes the challenge message bind to every value the verifier relies on and the account owner intends, consistent with the rationale already documented for the rotation-capability variant.

### Proof of Concept
Conceptual PoC (would require two live networks sharing an account-derivation scheme, e.g. a devnet reset producing address collisions with sequence number 0):
1. Victim signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: V, recipient_address: R }` intending to grant capability to `R` on network A.
2. Attacker captures the signature bytes (public calldata) and observes that on network B, the same address `V` also exists with `sequence_number == 0`.
3. Attacker (or a colluding/attacker-controlled address equal to `R`) calls `offer_signer_capability` on network B with the same `signer_capability_sig_bytes`, `account_scheme`, `account_public_key_bytes`, and `recipient_address`.
4. `verify_signed_message` succeeds because the reconstructed challenge is byte-identical (no `chain_id` differentiates network A from B), and `account_resource.signer_capability_offer.for` is set to `R` on network B, granting custody without the victim's on-network-B consent. [4](#0-3)

    /// Offers signer capability on behalf of `account` to the account at address `recipient_address`.
    /// An account can delegate its signer capability to only one other address at one time.
    /// `signer_capability_key_bytes` is the `SignerCapabilityOfferProofChallengeV2` signed by the account owner's key
    /// `account_scheme` is the scheme of the account (ed25519 or multi_ed25519).
    /// `account_public_key_bytes` is the public key of the account owner.
    /// `recipient_address` is the address of the recipient of the signer capability - note that if there's an existing
    /// `recipient_address` in the account owner's `SignerCapabilityOffer`, this will replace the
    /// previous `recipient_address` upon successful verification (the previous recipient will no longer have access
    /// to the account owner's signer capability).
    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
