## Finding: Webhook shop identity not bound by HMAC — cross-tenant webhook spoofing

### Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `X-Shopify-Shop-Domain` header straight to the handler as the trusted tenant identifier. Because the shop domain is never part of the signed material, any actor who can obtain one validly-signed webhook body (signed with the app's single, shared `client_secret`) can replay it with a different `shop` header and have it accepted as originating from an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Registry.process` validates the request using `Utils::HmacValidator.validate`, which computes the HMAC exclusively from that signable string (i.e. the body) and compares it against the received `hmac` value: [2](#0-1) [3](#0-2) 

Once the HMAC (body-only) check passes, `request.shop` — read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no further verification — is forwarded into `WebhookMetadata` and given to the app's handler as the authoritative tenant identifier: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header value == shop the HMAC was computed for`. Because the HMAC only covers the body, this equality is never checked — the `shop` header is a field "acted on but not covered by the HMAC," directly matching the described bug class. The webhook HMAC is computed with the app's single `Context.api_secret_key`, shared across every shop that installs the app — not a per-shop secret — so any merchant that legitimately installs the app can receive a real, validly-signed webhook for their own store, capture `(raw_body, hmac)`, and resend it to the app's webhook endpoint with the `shop-domain` header swapped to a different (victim) shop.

### Impact Explanation
`Registry.process` will accept the tampered request as authentic (HMAC check passes because the body is unchanged) and invoke the app's webhook handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any host application that uses `data.shop` from the callback to look up per-tenant state, trigger tenant-scoped side effects, or otherwise trust the shop as the authenticated source of the event will process attacker-controlled data under the wrong tenant's identity — a cross-tenant confusion/impersonation primitive rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on their own store (a normal, unprivileged action) to obtain one legitimately HMAC-signed webhook body, then replay that request to the app's public webhook endpoint with a modified shop header — no access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Bind the shop domain into the authenticated material, e.g. include `shop-domain` (and ideally `topic`, `webhook-id`) in the string that is HMAC-verified, or independently verify that the shop asserted in the header matches a shop known to have a valid, active session/installation before dispatching to the handler.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store; capture a real webhook delivery, e.g. `orders/create`, including its raw body and the `X-Shopify-Hmac-Sha256` header.
2. Resend the exact same body and HMAC header to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over the (unchanged) body and matches the attacker's signature — validation succeeds.
4. The app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` [5](#0-4)  and processes attacker-supplied data as if it originated from the victim tenant.
