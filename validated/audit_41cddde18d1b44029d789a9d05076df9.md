### Title
Index growth overflows debt valuation and permanently freezes a large market - ([File: common/src/rates/index.rs])

### Summary
A sufficiently large, highly utilized market can become permanently unusable when accrued debt value exceeds `i128::MAX` before `MAX_BORROW_INDEX_RAY` is reached. The repository’s integration test demonstrates that `update_indexes` traps, after which repayments, withdrawals, and other interest-accruing paths cannot execute. [1](#0-0) 

### Finding Description
Pool markets store supply and debt as scaled RAY shares and multiply those shares by the current index through `scaled_to_original`. [2](#0-1) 

During accrual, `calculate_supplier_rewards` computes `borrowed * old_borrow_index` and `borrowed * new_borrow_index`; either multiplication panics when its result exceeds `i128::MAX`. [3](#0-2) 

`update_borrow_index` caps the index only after performing the growth multiplication, and the configured cap is `1e36` raw units—far above the approximately `173x` index at which a `1e36` scaled balance overflows. [4](#0-3) [5](#0-4) 

Every accrual call enters `global_sync`, applies all elapsed chunks through `accrue_step`, and only marks the market accrued after the loop completes. [6](#0-5) [7](#0-6) 

An unprivileged account can reach the vulnerable state through `Controller::supply(caller, account_id, spoke_id, assets)` and `Controller::borrow(caller, account_id, borrows, to)`, while anyone can trigger the failing accrual through `update_indexes`; `withdraw`, `repay`, liquidation, and other market mutations subsequently encounter the same accrual failure. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
Once `scaled_debt * borrow_index` no longer fits in `i128`, the transaction panics before a capped index or updated timestamp can be committed. [11](#0-10) [12](#0-11) 

The checked-in integration test explicitly observes that the market reaches this condition before `MAX_BORROW_INDEX_RAY`, then confirms both `withdraw` and `repay` fail with `MATH_OVERFLOW`. [13](#0-12) 

Because repayment, withdrawal, liquidation, and ordinary updates all require the same accrual to finish first, supplier principal and borrower collateral can remain permanently frozen in that market. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The exploit requires a large high-decimal market, sustained high utilization, and enough elapsed time for the borrow index to cross the value-overflow threshold. [16](#0-15) 

The scenario does not require privileged execution after market configuration: the test uses ordinary supply and borrow flows, then permissionless index updates until accrual traps. [17](#0-16) 

The substantial capital and market-state prerequisites make this less likely than a direct theft path, but the consequence is a permanent market freeze rather than a bounded transaction failure. [11](#0-10) [18](#0-17) 

### Recommendation
Use widening or saturating arithmetic for `borrowed * index` before comparing against configured caps, or impose a combined `scaled_balance * MAX_*_INDEX_RAY <= i128::MAX` invariant. [19](#0-18) 

The accrual path should clamp or safely bound the new index before calculating `new_total_debt`, rather than calculating a value that is already known to exceed the representable range. [20](#0-19) 

The same bound should be applied consistently to `scaled_to_original`, utilization calculation, supply-index distribution, and debt unscale paths so no entrypoint can trap solely from a representable stored balance and index. [21](#0-20) [22](#0-21) 

### Proof of Concept
The repository already contains a deterministic harness for the failure:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs

    .with_max_utilization_disabled_all_markets()

lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break e;
    }
}
```

The loop terminates with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, showing that the representable debt-value ceiling is reached before the configured index ceiling. [23](#0-22) 

Afterward, both `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` fail with the same error, demonstrating permanent freezing of the market rather than a one-off rejected input. [24](#0-23)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index

    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();

    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
