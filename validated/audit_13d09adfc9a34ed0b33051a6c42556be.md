### Title
Unbounded declared-length array preallocation in `Codec.DecodeHeader` allows gas-amplification DoS of BEEFY consensus updates - ([File: evm/src/consensus/Codec.sol])

### Summary
`Codec.DecodeHeader` decodes a SCALE-encoded digest count directly from attacker-supplied header bytes and immediately allocates a memory array sized to that untrusted value — `new Digest[](length)` — before any check that the underlying byte slice actually contains that many digest items. This mirrors the ion-java CVE-2026-75935 bug class: a declared-length field drives preallocation before the parser has confirmed the input actually backs that length.

### Finding Description
`Codec.DecodeHeader` reads a SCALE compact integer as the digest count and allocates memory for it before validating the remaining bytes: [1](#0-0) 

The compact-integer decoder (`decodeUintCompact`) supports mode 3, which can decode up to an 8-byte unsigned integer (i.e., values up to `2^64-1`) directly from attacker-controlled input: [2](#0-1) 

Crucially, `Digest[] memory digests = new Digest[](length);` allocates memory proportional to `length` *before* any of the digest bytes are read or bounds-checked. Only once the loop begins does `Bytes.readByte`/`decodeDigestItem` start consuming bytes and eventually revert once the slice is exhausted — but the (attempted) memory allocation for the array has already been paid for/attempted at the top.

This function is reachable from `EcdsaBeefy.verifyParachainHeaderProof`, which decodes **every** parachain header in the submitted proof via `Codec.DecodeHeader` *before* the Merkle multiproof (`MerkleMultiProof.VerifyProof`) is checked: [3](#0-2) 

Because the multiproof check happens only after the loop that calls `Codec.DecodeHeader(para.header)` on every attacker-supplied `para.header`, the header bytes are fully unauthenticated at the point of decoding — nothing constrains the digest-count field to a realistic value for a real Substrate header. `EcdsaBeefy.verify` is externally reachable, unauthenticated, through `ConsensusRouter.verify`: [4](#0-3) 

`ConsensusRouter`/`EcdsaBeefy` implement `IConsensusV2`, the interface used by the host's consensus-update path (permissionless — any relayer/user can submit a consensus proof to update consensus state).

### Impact Explanation
An attacker can craft a `ParachainProof.parachains[i].header` blob whose leading bytes decode (via `Codec.decodeUintCompact`) to a very large digest count (up to ~2^64), forcing `new Digest[](length)` to attempt an enormous memory allocation. Solidity memory expansion cost is quadratic in the number of 32-byte words, so even moderately large declared lengths (tens of thousands to millions) become disproportionately expensive to allocate relative to the tiny amount of calldata the attacker paid for, and sufficiently large values exhaust the block gas limit / revert with out-of-gas, before the Merkle multiproof validity is even checked. This lets an attacker grief the BEEFY consensus-update path: submitted consensus-update transactions (or relayers attempting legitimate updates that get front-run/griefed in this manner) can be made prohibitively expensive or reliably fail, denying service to the route's ability to deliver messages (consensus updates block all downstream request/response processing for the affected state machine). This satisfies the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High: the input (`para.header` bytes) is fully attacker-controlled in the calldata of a permissionless external call (`ConsensusRouter.verify` → `EcdsaBeefy.verify` → `verifyParachainHeaderProof` → `Codec.DecodeHeader`), and no consistency check (declared digest count vs. remaining slice length) occurs before the allocation. Constructing the crafted 2-3 byte SCALE compact-integer prefix to set an arbitrarily large digest count requires no special privileges or cryptographic material — it is a pure parsing-order bug.

### Recommendation
Bound the declared digest count against the remaining slice length before allocating, e.g., reject if `length` exceeds `(encoded.length - slice.offset)` (each digest requires at minimum a few bytes), or impose an explicit sane maximum digest count constant and validate against it prior to `new Digest[](length)`. Additionally, move the Merkle multiproof verification in `verifyParachainHeaderProof` ahead of the loop that calls `Codec.DecodeHeader`, so headers are only fully parsed after their inclusion is cryptographically confirmed against a trusted `headsRoot`.

### Proof of Concept
1. Construct a `ParachainProof` with one `Parachain` entry whose `header` bytes are: 32 bytes (parentHash) + a valid SCALE compact blockNumber + 32 bytes (stateRoot) + 32 bytes (extrinsicsRoot) + a SCALE compact-mode-3 length prefix encoding a large value (e.g., `0xFFFFFFFFFFFFFFFF`-scale via mode-3 8-byte encoding) as the digest count, followed by no (or minimal) digest bytes.
2. Submit this proof via `ConsensusRouter.verify(previousState, 0x00 || abi.encode(RelayChainProof, ParachainProof))` (Ecdsa path), or directly to `EcdsaBeefy.verify`.
3. Observe that `Codec.DecodeHeader` executes `new Digest[](length)` with the crafted large `length` before the Merkle multiproof is checked, consuming disproportionate gas relative to the small calldata payload, causing the transaction to revert with out-of-gas or become economically prohibitive to include — before any cryptographic validity of the parachain header/proof is established.

        internal

        uint256 len = proof.parachains.length;
        MerkleMultiProof.Leaf[] memory leaves = new MerkleMultiProof.Leaf[](len);
        IntermediateState[] memory intermediates = new IntermediateState[](len);

        for (uint256 i = 0; i < len; i++) {

            Header memory header = Codec.DecodeHeader(para.header);
            if (header.number == 0) revert IllegalGenesisBlock();

                para.index,
