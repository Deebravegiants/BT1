### Title
Emporium's `runAction` lets arbitrary ops sweep untracked/dust token balances into a declared output token, stealing value beyond `-deltaAmountChanges` — (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only measures balance deltas for the tokens the attacker chooses to list in `circomData.erc20TokenAddresses`, while the ops it executes (`op.endpoint.call{value: op.value}(op.callData)`) are completely unconstrained arbitrary calls. Any ERC20/ETH balance the shared Emporium contract is holding but that is *not* included in the attacker's `erc20TokenAddresses` array (dust, un-swept slippage remainder from a prior transaction, or any other stranded value) can be routed by a crafted op into a token that *is* declared, and `handleOut` will pay the resulting increase to the attacker as if it were legitimate swap proceeds of their own deposit.

### Finding Description
The invariant that should hold is:
`tokens leaving the action in tx T == -deltaAmountChanges[T]` (the amount Hinkal itself moved into the action for tx T).

`runAction` enforces this only for tokens present in `circomData.erc20TokenAddresses`: [1](#0-0) 

- `balancesBefore`/`balancesAfter` are captured only for the caller-chosen `erc20TokenAddresses` array.
- The ops loop (`stack.ops`) is fully attacker-controlled data decoded from `circomData.externalActionData.externalActionMetadata`; in the "stateless" branch (`stack.signerAddress == address(0)`) the only restriction is that the call is not `callHinkalWallet`/`doSendToRelay` — the attacker can target *any* `op.endpoint` with *any* `op.callData`: [2](#0-1) 

- `handleOut` unconditionally pays out any positive balance delta of a declared token to `msg.sender`: [3](#0-2) 

Since `EmporiumUpgradeable` is a single, shared, upgradeable contract registered once via `Hinkal.registerExternalAction` for all users, any token balance it happens to hold from a prior transaction (dust remaining because a router returned slightly more/less than expected, a partial fill, or any other stranded/refunded amount) sits in its balance across transactions. That balance is invisible to the delta-accounting as long as it belongs to a token the current attacker chooses **not** to list in `erc20TokenAddresses`.

An attacker who has any real, valid UTXO to spend (even a trivial dust deposit/withdraw of a token `B`) can generate a fully valid, self-consistent proof (no proof reuse needed — the `calldataHash` binding via `CircomDataBuilder.getHashedCalldata`, which includes `circomData.externalActionData`, only requires that the submitted calldata matches what the attacker used when generating the proof, not that the ops be benign): [4](#0-3) [5](#0-4) 

The attack:
1. Attacker observes/knows the Emporium contract is holding a residual balance of token `A` (untracked leftover from any prior tx by any user).
2. Attacker builds `circomData` with `erc20TokenAddresses = [B]` (their own legitimately owned UTXO of token `B`, `amountChanges[0]` near 0 or whatever they legitimately control), and `externalActionMetadata` encoding an `EmporiumStack` whose stateless op calls a DEX/router (or the token contract directly) to swap/transfer the Emporium's entire stranded balance of token `A` into token `B` (or directly to the attacker).
3. Attacker generates a fully valid ZK proof for this self-consistent `circomData` (nothing about `A` is constrained by the circuit, since `A` never appears in `erc20TokenAddresses`/`amountChanges` public inputs).
4. Submits via `Hinkal.transact` → `performHinkalChecks` passes, proof verifies, `EmporiumUpgradeable.runAction` executes the op, converting/moving the untracked `A` dust into `B`'s balance increase, which `handleOut` pays entirely to the attacker as `utxoOut`/direct transfer — value that was never part of this transaction's `deltaAmountChanges`.

None of the existing guards catch this: `dimensionsCheck` and `checkOnchainCreation` only validate array-length consistency of what the attacker declares; `verifyProof`/`buildVerifierId` only bind the values actually placed in the public-input vector (which excludes token `A` entirely); the `balanceChange < 0` revert in `runAction` only protects declared tokens, and here `B`'s balance strictly increases, so it passes.

### Impact Explanation
The attacker directly steals value that legitimately belongs to the protocol/other users (stranded slippage remainders, un-swept partial-fill proceeds, or any other balance the Emporium contract is holding that is not the current transaction's own deposit). This is a direct theft of in-flight/parked user or protocol funds via a completely unprivileged, repeatable operation — matching the Critical category ("direct theft of shielded or in-flight user funds"). It is repeatable any time the shared Emporium contract accumulates any leftover balance of any token, and the attacker's cost is only gas plus a trivial real UTXO to anchor a valid proof.

### Likelihood Explanation
Preconditions: the shared `EmporiumUpgradeable` contract must be holding some non-zero balance of a token not declared by the attacker in that transaction. Such dust can realistically arise from slippage-tolerant swaps, partial DEX fills, rounding, or any transaction whose `handleOut` skipped a tiny/leftover amount. The attacker needs no special privilege — only a normal Hinkal UTXO and the ability to encode arbitrary `EmporiumOperation`s (fully permitted for `stack.signerAddress == address(0)`), making this feasible for any unprivileged user and trivially repeatable whenever residual balances exist.

### Recommendation
- Track and account for the full set of tokens the Emporium contract can ever touch during ops execution, not just the caller-declared `erc20TokenAddresses`. At minimum, snapshot balances of all tokens referenced anywhere in `stack.ops` (or restrict ops to an allow-listed, non-arbitrary router interface) and fold every affected token into the delta-accounting/`handleOut` invariant.
- Alternatively, require that any token balance increase paid out via `handleOut` be provably sourced only from tokens deposited via `deltaAmountChanges` in the same transaction, e.g., by disallowing raw arbitrary `.call` targets/calldata and instead exposing a constrained "swap" interface that only allows spending the exact just-deposited amounts.
- Sweep or burn any pre-existing balance to a protocol-owned sink at the start of each `runAction` call so it can never be attributed to the current caller.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register it as the Emporium external action.
2. Seed residual: perform a legitimate Emporium transaction (or directly `deal`/`transfer`) that leaves token `A` dust sitting in the `EmporiumUpgradeable` contract (simulate a prior partial-fill/slippage remainder).
3. Attacker deposits a small real UTXO of token `B` into Hinkal and generates a valid proof with:
   - `erc20TokenAddresses = [B]`
   - `externalActionMetadata` = `EmporiumStack` with one stateless op that swaps/transfers the entire dust balance of `A` held by Emporium into `B` (e.g., via a mock router or direct `IERC20(A).transfer(attacker, dustAmount)` then a genuine swap `A->B`, or directly to attacker's EOA).
4. Call `Hinkal.transact` with this proof/circomData.
5. Assert: attacker's resulting UTXO/output for `B` (or direct balance) equals `dustAmount(A-converted-to-B)` plus their own legitimate `deltaAmountChanges`, i.e., strictly greater than `-deltaAmountChanges[B]` — violating `tokens leaving action == -deltaAmountChanges`.
6. Assert Emporium's balance of `A` dropped to zero/attacker-controlled amount, confirming the parked value left the contract uncounted by `deltaAmountChanges`.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
