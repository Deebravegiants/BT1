### Title
Suppliers can front-run a known bad-debt write-down and withdraw at the un-written-down supply index, concentrating the full loss on remaining suppliers - (File: contracts/pool/src/interest.rs)

### Summary
The external report describes a token whose holders watch its value silently depreciate while redemption is still possible at the stale rate. XOXNO Lending reproduces that exact shape: the supply index only reflects bad debt when `apply_bad_debt_to_supply_index` runs inside a `liquidate` or `clean_bad_debt` call. Between the moment an account becomes insolvent (public, oracle-driven state) and the moment anyone executes the write-down, `withdraw` pays suppliers out at the pre-crash index. A supplier who exits during that window escapes the loss entirely, and the entire haircut is concentrated pro-rata onto whoever stays — including suppliers who had no way to dodge. The harness test `supplier_can_exit_ahead_of_bad_debt_writedown` in `tests/test-harness/tests/controller/bad_debt_index.rs` demonstrates a ~4x loss amplification onto a passive 25% supplier.

### Finding Description
Bad debt is not booked at the moment it becomes real — it is booked when a seize entry of side `Borrow` executes `interest::apply_bad_debt_to_supply_index`, which scales `supply_index` down to socialize the loss (`contracts/pool/src/ops/seize.rs:24-28`, `contracts/pool/src/interest.rs:73-89`). Until that call, `backing_shortfall` values the insolvent account's unrecoverable debt at face (`guards.rs:60-66`), and the supply index still reflects full value.

Withdrawal path: `withdraw` is gated only by `require_reserves` (cash availability) and the liquidation buffer applies only to debt-minting operations (`guards.rs:36-47` — "Exits do not"). There is no gate that marks a market "pending write-down" or reprices a withdrawer's shares at the post-socialization index. The crash is publicly observable: a price update makes an account's `total_debt` exceed `weighted_collateral`, and anyone can see the coming write-down before a liquidator or keeper acts.

Concrete sequence (mirrors the harness test):
1. Alice supplies USDC collateral and borrows ETH; Bob and Carol supply ETH (75% / 25%).
2. Oracle price of USDC crashes. Alice's debt is now unrecoverable, but `supply_index` for ETH is unchanged.
3. Bob calls `withdraw` for all his ETH shares. He is paid at the un-written-down index (`unscale_supply_floor` / `resolve_withdrawal`), recovering his full deposit plus accrued interest.
4. `LIQUIDATOR` calls `liquidate` (or any address calls `clean_bad_debt` for a dust-gated account). `seize` burns Alice's debt and calls `apply_bad_debt_to_supply_index`, dropping the ETH supply index.
5. Carol alone now absorbs the loss Bob dodged. The test measures `carol_loss_after_dodge / carol_loss_passive > 3.0`, roughly the full 4x concentration factor for a 25%-share supplier.

### Impact Explanation
Theft of user funds via loss transfer. Every unit a dodging supplier withdraws above the post-write-down value is a unit that remaining suppliers — and, in a wipeout, the floored-index residual and protocol revenue shares — can never recover. This is not a rounding leak; it transfers the full realized bad debt away from the informed withdrawer onto passive suppliers. It also creates a perverse incentive for every supplier to race for the exit on any liquidation-eligible price move, turning each bad-debt event into a bank run that drains `cash` at the stale rate (only bounded by `require_reserves`), which can leave too little cash for honest withdrawers afterward — temporary freezing of funds for the remaining suppliers.

### Likelihood Explanation
Medium. Requirements: (a) a borrow position that goes underwater fast enough that liquidation/cleanup has not yet run — normal in volatile markets and guaranteed whenever the liquidator/keeper is slower than the price update; (b) a supplier monitoring account risk off-chain — `assert_liquidatable`-style reads and index views are all public; (c) enough pool `cash` to pay the withdrawal — `require_reserves` is the only check and it uses face-value debt, so the pre-write-down book always looks backed. The attacker is a single unprivileged address calling `withdraw` on its own position and needs no cooperation. Historical behavior is symmetric in reverse: suppliers who cannot react (smart-contract depositors, passive users) systematically bear the loss, so the wealth transfer is real every time this window opens.

### Recommendation
Make the write-down atomic with insolvency recognition, or make exits pay the post-write-down value:

- Apply the pending bad-debt reduction inside `synced_market`/`global_sync` before processing a `withdraw`: any seize-eligible debt on the market's books should first be reflected in `supply_index` so a withdrawer cannot exit at the stale rate.
- Alternatively, in the withdraw path compute the claim against an index that already deducts debt the risk engine currently values at zero collateral (a "haircut-adjusted" index), even before the debt shares are burned.
- Short of that, gate `withdraw` when a liquidation plan exists against the market (`backing_shortfall` computed with insolvent-account debt valued at its liquidation-adjusted, rather than face, value), so the exit queue cannot drain cash ahead of socialization.

### Proof of Concept
Encoded as `supplier_can_exit_ahead_of_bad_debt_writedown` in `tests/test-harness/tests/controller/bad_debt_index.rs:401-473`:

```rust
// Identical setups A and B. In B, Bob withdraws after the crash but
// before `liquidate` runs the write-down.
b.set_price("USDC", usd_cents(10));   // Alice insolvent; index still stale
b.assert_liquidatable(ALICE);
b.withdraw_all(BOB, "ETH");           // exits at un-written-down index
b.liquidate(LIQUIDATOR, ALICE, "ETH", 0.001); // now supply_index drops

// Measured: Bob recovers >= his full deposit; Carol's loss grows >3x
// versus the no-dodge baseline (~4x expected for a 25% supplier).
```

Root cause: `apply_bad_debt_to_supply_index` is the only writer that lowers `supply_index` (`contracts/pool/src/interest.rs:73-89`), it runs only inside `seize` (`contracts/pool/src/ops/seize.rs:24-28`), and the withdraw path (`contracts/pool/src/ops/supply.rs` sibling ops, guarded by `require_reserves` in `guards.rs:39-47`) never accounts for debt that is already unbacked at current prices.
