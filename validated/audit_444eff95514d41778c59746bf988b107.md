Audit Report

## Title
XCMP messages silently and permanently dropped when weight meter is exhausted mid-page, while HRMP watermark still advances past them - ([File: cumulus/pallets/xcmp-queue/src/lib.rs], [File: cumulus/pallets/parachain-system/src/lib.rs])

## Summary
`Pallet::enqueue_xcmp_messages` in `cumulus-pallet-xcmp-queue` drops the unaffordable tail of a batch when the weight meter cannot cover `T::WeightInfo::enqueue_xcmp_messages` for the full batch, returning `Err(())` and causing the `handle_xcmp_messages` inner loop to `break` and abandon the remainder of that sender's page. `Pallet::enqueue_inbound_horizontal_messages` in `cumulus-pallet-parachain-system` then unconditionally advances `HrmpWatermark::<T>::put(last_processed_block)`, where `last_processed_block` is derived purely from the `sent_at` metadata of messages present in the inherent, independent of the `Weight` value returned by `handle_xcmp_messages` or any success/failure signal.

## Finding Description
In `cumulus/pallets/xcmp-queue/src/lib.rs`, `enqueue_xcmp_messages` computes the largest affordable batch via `batches_footprints.search_best_by(...)` against the `WeightMeter`, and if `best_batch_footprint.msgs_count < xcms.len()`, only enqueues the affordable prefix and returns `Err(())`: [1](#0-0) 

This propagates up through `handle_xcmp_messages`'s per-sender batch loop, where `Err(())` triggers `break`, abandoning any remaining batches for that sender in the current page without re-processing them: [2](#0-1) 

Critically, `enqueue_inbound_horizontal_messages` in `cumulus/pallets/parachain-system/src/lib.rs` computes `last_processed_block` solely from the `sent_at` field of messages iterated in the `messages`/`hashed_messages` loops — with no dependency on the `Weight` return value of `handle_xcmp_messages` — and then unconditionally writes `HrmpWatermark::<T>::put(last_processed_block)`: [3](#0-2) 

The relay chain's `check_hrmp_watermark` only enforces monotonic advancement and that the new watermark lands on a block with recorded messages via `HrmpChannelDigests`; it has no visibility into whether the parachain's own runtime actually enqueued the messages it claims to have processed: [4](#0-3) 

Since the relay chain will not re-deliver HRMP messages once the recipient's watermark has advanced past the block in which they were sent, any messages dropped by `enqueue_xcmp_messages` due to weight exhaustion are unrecoverable. The existing test `xcm_enqueueing_starts_dropping_on_out_of_weight` confirms and accepts the drop-on-out-of-weight behavior at the `xcmp-queue` level, but does not test watermark interaction, confirming this is an unaddressed gap rather than an intentionally tested/handled tradeoff: [5](#0-4) 

Additionally, `messages_collection_size_limit`, used to size the inherent page for `do_create_inherent`, is purely PoV/size-based (1/6 of max block proof size) and has no correlation with the weight-based `ReservedXcmpWeight` budget consumed by `handle_xcmp_messages`: [6](#0-5) 

## Impact Explanation
When a page's XCMP content exceeds the `ReservedXcmpWeight`/weight-meter budget mid-page, the tail of that page — potentially including legitimate messages from other senders sharing the page, such as `ReserveAssetDeposited`/`DepositAsset` instructions — is dropped without being enqueued into the message queue for execution. Because `HrmpWatermark` still advances past the block containing those messages, the relay chain will never re-present them, resulting in silent, permanent loss of the intended cross-chain state transition (e.g., an asset deposit that a sender-side reserve/burn was meant to back). This is an accounting/asset-safety impact intrinsic to the SDK's parachain-system/xcmp-queue interaction, not caused by a malicious external node or dependency.

## Likelihood Explanation
Triggering this requires a page of concatenated XCMP messages whose true weight cost (per `T::WeightInfo::enqueue_xcmp_messages`, driven by `msgs_count`, `size_in_bytes`, `new_pages_count`) exceeds the `ReservedXcmpWeight` budget mid-processing — achievable either adversarially (crafting many small messages to inflate per-message enqueue overhead) or simply through a heavy but legitimate burst of ordinary user-driven XCM traffic (e.g., several `pallet-xcm` reserve-transfer calls in the same block from unrelated senders). No privileged access, governance, or victim mistake is required; a normal unprivileged user's transaction volume shaping the page composition is sufficient to reach the vulnerable path. This is a genuine, reachable defect rather than a purely theoretical concern.

## Recommendation
Track how many messages/bytes were actually enqueued (versus dropped due to out-of-weight) per sender in `handle_xcmp_messages`, and have `enqueue_inbound_horizontal_messages` advance `HrmpWatermark`/`LastProcessedHrmpMessage` only up to the point verified to have been successfully processed, deferring the remainder to a subsequent block — analogous to how DMP's `ProcessedDownwardMessages` reflects the true processed count rather than the full inherent content. Alternatively, ensure `messages_collection_size_limit()` is provably bounded relative to `ReservedXcmpWeight` so that any page admitted by the collator can always be fully processed within the available weight budget.

## Proof of Concept
1. Configure `ReservedXcmpWeight` to a bound smaller than what is needed to fully process a page.
2. Construct a single HRMP page with N XCM messages from one sender, sized so `T::WeightInfo::enqueue_xcmp_messages` for the full batch exceeds the configured weight limit, forcing `enqueue_xcmp_messages` (`cumulus/pallets/xcmp-queue/src/lib.rs` L701-722) to return `Err(())` partway through.
3. Invoke `enqueue_inbound_horizontal_messages` (`cumulus/pallets/parachain-system/src/lib.rs` L1435-1519) with this page as inherent data.
4. Assert the message queue does not contain all N messages (confirming drop) while `HrmpWatermark::<T>::get()` equals the relay-parent block number for that page (confirming the watermark advanced past the dropped messages), and that `LastProcessedHrmpMessage` provides no mechanism to re-include the dropped tail in a future `do_create_inherent` call — confirming permanent, unrecoverable message loss.

```rust
	/// Check that the candidate of the given recipient controls the HRMP watermark properly.
	pub(crate) fn check_hrmp_watermark(
		recipient: ParaId,
		relay_chain_parent_number: BlockNumberFor<T>,
		new_hrmp_watermark: BlockNumberFor<T>,
	) -> Result<(), HrmpWatermarkAcceptanceErr<BlockNumberFor<T>>> {
		// First, check where the watermark CANNOT legally land.
		//
		// (a) For ensuring that messages are eventually processed, we require each parablock's
		//     watermark to be greater than the last one. The exception to this is if the previous
		//     watermark was already equal to the current relay-parent number.
		//
		// (b) However, a parachain cannot read into "the future", therefore the watermark should
		//     not be greater than the relay-chain context block which the parablock refers to.
		if new_hrmp_watermark == relay_chain_parent_number {
			return Ok(());
		}

		if new_hrmp_watermark > relay_chain_parent_number {
			return Err(HrmpWatermarkAcceptanceErr::AheadRelayParent {
				new_watermark: new_hrmp_watermark,
				relay_chain_parent_number,
			});
		}

		if let Some(last_watermark) = HrmpWatermarks::<T>::get(&recipient) {
			if new_hrmp_watermark < last_watermark {
				return Err(HrmpWatermarkAcceptanceErr::AdvancementRule {
					new_watermark: new_hrmp_watermark,
					last_watermark,
				});
			}

			if new_hrmp_watermark == last_watermark {
				return Ok(());
			}
		}

		// Second, check where the watermark CAN land. It's one of the following:
		//
		// (a) The relay parent block number (checked above).
		// (b) A relay-chain block in which this para received at least one message (checked here)
		let digest = HrmpChannelDigests::<T>::get(&recipient);
		if !digest
			.binary_search_by_key(&new_hrmp_watermark, |(block_no, _)| *block_no)
			.is_ok()
		{
			return Err(HrmpWatermarkAcceptanceErr::LandsOnBlockWithNoMessages {
				new_watermark: new_hrmp_watermark,
			});
		}
		Ok(())
```

```rust
#[test]
fn xcm_enqueueing_starts_dropping_on_out_of_weight() {
	// Our mocked queue enqueues 1 message per page.
	// Let's make sure we don't hit the drop threshold.
	new_test_ext().execute_with(|| {
		<QueueConfig<Test>>::set(QueueConfigData {
			suspend_threshold: 300,
			drop_threshold: 300,
			resume_threshold: 300,
		});

		let mut total_size = 0;
		let xcms = encode_xcm_batch(generate_mock_xcm_batch(0, 10), XcmEncoding::Simple);
		for (idx, xcm) in xcms.iter().enumerate() {
			EnqueuedMessages::set(vec![]);
			total_size += xcm.len();
			let required_weight = <<Test as Config>::WeightInfo>::enqueue_xcmp_messages(
				0,
				&BatchFootprint {
					msgs_count: idx + 1,
					size_in_bytes: total_size,
					new_pages_count: idx as u32 + 1,
				},
				true,
			);

			let mut weight_meter = WeightMeter::with_limit(required_weight);
			let res = XcmpQueue::enqueue_xcmp_messages(
				1000.into(),
				&xcms.iter().map(|xcm| xcm.as_bounded_slice()).collect::<Vec<_>>(),
				true,
				&mut weight_meter,
			);
			if idx < xcms.len() - 1 {
				assert!(res.is_err());
			} else {
				assert!(res.is_ok());
			}

			assert_eq!(
				EnqueuedMessages::get(),
				xcms[..idx + 1]
					.iter()
					.map(|xcm| (1000.into(), xcm.to_vec()))
					.collect::<Vec<_>>()
			);
		}
	})
}
```
