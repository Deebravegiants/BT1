## Finding: Webhook shop/topic/metadata headers are not covered by the HMAC signature - shop identity spoofing via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the shop, topic, webhook id, and API version that the app relies on for identity/routing are taken from unauthenticated HTTP headers that are never included in the signature. `Registry.process` trusts these header-derived fields once the body-only HMAC check passes, allowing a replayed body+HMAC pair to be attributed to an arbitrary shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but the class exposes `shop`, `topic`, `webhook_id`, and `api_version` read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (i.e. the body), never over the headers: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check, then trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unsigned) to build the metadata handed to the app's handler: [4](#0-3) 

This is exactly the identity-binding break described by the report's bug class: a field (`shop`, `topic`, `webhook_id`) is acted on by the application but not covered by the authenticity check (the HMAC). The equality that should hold — "the shop the HMAC authenticates" == "the shop the handler acts on" — does not hold, because the HMAC only authenticates the body bytes, not the shop header.

By contrast, the OAuth `AuthQuery` analog in this same gem does this correctly: every field it acts on (`code`, `host`, `shop`, `state`, `timestamp`) is included in `to_signable_string` and therefore covered by the HMAC: [5](#0-4) 

The webhook path lacks this equivalent binding for its headers.

### Impact Explanation
The app's `client_secret` is shared across every shop that installs the app — it is not per-shop. Any merchant who has installed the app can legitimately trigger a real webhook delivery for their own store and thereby obtain a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the signature never covers the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers, that attacker can resend the exact same body and HMAC to the app's public webhook endpoint while substituting a different shop's domain in the `shop-domain` header (and/or a different topic/webhook id). `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim shop, not the shop that actually produced the signed body. Any app logic that keys authorization, tenant isolation, or state changes off `request.shop`/`data.shop` (e.g. per-shop mandatory webhooks like `shop/redact`, `customers/redact`, `customers/data_request`, or shop-scoped side effects in custom handlers) can be fooled into acting under the wrong tenant's identity — a cross-tenant confusion originating purely from this gem's verification logic.

### Likelihood Explanation
Exploitation requires only the ability to (a) install the app on at least one shop the attacker controls (trivial for any public/multi-tenant Shopify app) to harvest a valid body+HMAC pair, and (b) send a crafted HTTP POST to the app's public webhook endpoint with attacker-chosen headers — no access to `client_secret`, no privileged account, and no TLS interception is required. This is reachable by any unprivileged internet user who can install the app once.

### Recommendation
Include the security-relevant, acted-upon headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., by having `to_signable_string` incorporate a canonical representation of the headers alongside the body), so that `HmacValidator.validate` fails if any of these fields are altered independently of the signed payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and performs an action that causes Shopify to send a real webhook (e.g. updates a product), yielding a valid `raw_body` and `shopify-hmac-sha256` header signed with the app's shared `client_secret`.
2. Attacker replays that exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate(request)` recomputes the signature over `to_signable_string` (the unchanged `raw_body`) and returns true, since the body/HMAC pair is genuinely valid for the shared secret.
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: request.parsed_body, ...))`, so the app processes attacker-controlled body content under the victim shop's identity.
