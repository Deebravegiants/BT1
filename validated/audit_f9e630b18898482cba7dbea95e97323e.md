Based on my investigation, I found a strong analog to the reported integer-overflow-from-unchecked-decimals bug class in the `hyper-fungible-token` pallet's cross-chain amount conversion, which is directly reachable by an unprivileged user via the `send` extrinsic and by the EVM counterpart via `on_accept`.

### Title
Unchecked ERC20/local decimals mismatch causes miscalculated cross-chain mint/burn amounts - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The `hyper-fungible-token` pallet converts amounts between a local Substrate asset's decimals and a remote EVM token's decimals using `convert_to_erc20`/`convert_to_balance`, both of which compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)` (or vice versa). When `erc_decimals < local_decimals`, the `saturating_sub` silently clamps to `0`, producing a scaling factor of `10^0 = 1` instead of the correct division/multiplication factor. The pallet declares an `Error::ErcDecimalsBelowLocal` variant documenting exactly this precondition ("Configured ERC decimals are less than the local asset's decimals; precision conversion requires erc_decimals >= local_decimals"), but neither the `send` extrinsic nor the `on_accept` handler actually checks for or raises this error before calling the conversion helpers.

### Finding Description
`convert_to_erc20` and `convert_to_balance` in [1](#0-0)  use `10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)` (or the symmetric `local_decimals.saturating_sub(erc_decimals)` in the balance direction) to scale amounts between decimal precisions. `saturating_sub` returns `0` whenever the subtrahend exceeds the minuend, which silently disables scaling instead of erroring.

In the `send` extrinsic, [2](#0-1)  reads `erc_decimals` from `Precisions` and the live asset decimals, then calls `convert_to_erc20(amount, erc_decimals, decimals)` directly — no check compares `erc_decimals` against `decimals` and no `ErcDecimalsBelowLocal` error is ever raised in this path, even though the error variant exists for exactly this precondition in [3](#0-2) .

Symmetrically, `on_accept` in [4](#0-3)  calls `convert_to_balance` with the same unchecked decimals pair before minting or releasing funds to the beneficiary.

If a token is registered with `erc_decimals < local_decimals` (e.g., a local asset with 18 decimals paired with a 6-decimal EVM token contract — a completely ordinary configuration, not requiring any malicious actor), the scaling factor silently becomes `1` instead of `10^12`. This means:
- On `send`, the amount encoded into the outbound `Message.amount` field is not scaled down, so the EVM contract receives an amount that is `10^(local_decimals - erc_decimals)` times too large relative to its own decimals.
- On `on_accept` (inbound), the reverse mismatch causes the locally minted/released balance to be scaled incorrectly relative to what was actually locked/burned on the remote side.

### Impact Explanation
This breaks the 1:1 backing invariant of the cross-chain token bridge. Depending on which side is misconfigured, this can result in an EVM contract minting an amount many orders of magnitude larger than what was escrowed/burned on the Substrate side (unbacked mint), or the Substrate pallet crediting an incorrect (inflated or deflated) balance relative to the EVM-side escrow. Either direction constitutes theft/unbacked-mint or permanent value loss for the bridge, matching the "unbacked mint" and "token bridge mint/burn" categories explicitly in scope.

### Likelihood Explanation
Reachability requires only a normal `send` call by any signed account once a token pair with `erc_decimals < local_decimals` is registered — this is a routine decimals configuration (many EVM tokens use 6 or 8 decimals while Substrate assets commonly use 10-18), not an adversarial governance action. The missing check is entirely on the code path exercised by every ordinary user transaction, and the dedicated (but unused) `ErcDecimalsBelowLocal` error variant indicates the developers recognized this exact failure mode but did not wire the guard into the actual conversion call sites I inspected.

### Recommendation
Enforce the `erc_decimals >= local_decimals` invariant (or handle both directions symmetrically and safely) at the point of use in `send` and `on_accept`, returning `Error::ErcDecimalsBelowLocal` instead of silently saturating, or make `convert_to_erc20`/`convert_to_balance` return a `Result` that errors when `saturating_sub` would have clamped the exponent. If the invariant is intended to be enforced only once, at `register_token`, note that both `send` and `on_accept` re-read the live decimals from the assets pallet at call time rather than trusting a fixed value, so a registration-time-only check does not protect against decimals drift and the per-call check should be added regardless.

### Proof of Concept
1. Governance (or whoever holds `CreateOrigin`) registers a non-native asset with `local_decimals = 18` and configures `Precisions::<T>::insert(asset_id, dest_chain, 6)` for a legitimate EVM token that has 6 decimals — an unremarkable, non-malicious registration.
2. Any user calls `send(params)` with `amount = 1 * 10^18` (i.e., "1 token" in local units).
3. Inside `send`, `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18u8) as u32) = 10u128.pow(0) = 1`, so `erc20_amount = 1e18 * 1 = 1e18` instead of the correct `1e18 / 10^12 = 1e6`.
4. The outbound `Message.amount` field encodes `1e18` as the amount for a 6-decimal EVM token — i.e., `1,000,000,000,000` tokens instead of `1` token — and the paired EVM contract mints/releases accordingly, a 10^12x amplification, while only 1 token's worth was escrowed/burned locally.

Note: I could not verify the contents of the `register_token` extrinsic (tool access ended before I could load it), so I cannot fully rule out that a registration-time check independently prevents this specific decimals pairing from ever being registered. However, based on the `send` and `on_accept` code I did inspect, no such guard exists at the transaction-processing call sites, and decimals for non-native assets are re-read live from the assets pallet rather than pinned at registration, so even a registration-time check would not fully close this gap.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
