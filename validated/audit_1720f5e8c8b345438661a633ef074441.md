### Title
`wallet.create()`/`wallet.import()` can silently overwrite an existing seed, permanently losing access to the previous wallet's funds - (File: features/wallet/module/wallet.js)

### Summary
The `Wallet` module's public `create()` and `import()` API methods, which are directly exposed on the `exodus.wallet` API surface, contain no check for whether a wallet/seed already exists before writing a brand-new seed into storage. Calling either method a second time (e.g. via the exposed `exodus.wallet.create({ passphrase })` or `exodus.wallet.import({ mnemonic, passphrase })` API) overwrites the single `SEED_KEY` storage slot that holds the user's mnemonic, permanently destroying the only copy of the previous seed unless the user separately backed it up. This is the same bug class as the `veRAACToken.lock()` report: a state-creating entry point unconditionally overwrites an existing "position" (there, a token lock; here, the wallet's seed) without preserving or migrating the prior state, causing irreversible loss of user assets.

### Finding Description
`Wallet#create` builds a brand-new mnemonic/seed and calls `#setSeed({ seed, passphrase })`, which writes directly to `walletStorage` under the fixed key `SEED_KEY = 'seed'`: [1](#0-0) 

`create()` performs no check such as `await this.exists()` before calling `#setSeed`, and `import()` simply delegates to `create()`: [2](#0-1) 

Both methods are exposed verbatim on the public wallet API surface consumed by SDK integrators/UI: [3](#0-2) 

`exists()` reads exactly this same key and is documented as the way to check whether a wallet has already been created, confirming that `SEED_KEY` is a singleton slot per wallet instance: [4](#0-3) 

Because the seed (mnemonic) is the sole cryptographic root from which all of a user's private keys/addresses for every supported asset are derived, overwriting `SEED_KEY` with a new mnemonic destroys the only reference needed to regenerate the old private keys. Unlike `addSeed`, which explicitly guards against clobbering ("Seed already present"), `create`/`import` have no equivalent guard for the primary seed: [5](#0-4) 

The official usage example even shows `create()` being called unconditionally as the first step of onboarding, with no defensive check against a pre-existing wallet before it: [6](#0-5) 

### Impact Explanation
If `wallet.create()` or `wallet.import()` is invoked while a wallet already exists (e.g., due to a UI bug, a duplicated onboarding call, a race in app initialization, or a consumer application mistakenly re-invoking the create/import flow instead of `changePassphrase`/`addSeed`), the previous mnemonic is irrecoverably overwritten in `walletStorage`. Since the mnemonic is the only key material stored and there is no backup/rotation of the old seed, all funds/assets derived from the previous seed become permanently inaccessible — this is a direct wallet-compromise/fund-loss impact, matching the report's "permanent loss of funds" pattern where an overwrite operation destroys the only reference to previously secured value.

### Likelihood Explanation
Low-to-medium: this requires the consuming application (or a user-triggered flow) to call `create()`/`import()` again after a wallet has already been created — analogous to the original report's precondition of calling `lock()` a second time. It does not require a malicious actor; a simple double-invocation of onboarding logic, a broken "restore" UI flow, or user confusion between "create new wallet" and "restore wallet" is sufficient to trigger the loss, since nothing in the module prevents it.

### Recommendation
Add a guard in `create()` (and therefore `import()`, which delegates to it) that checks `await this.exists()` before writing a new seed, and reject the call (or require an explicit `overwrite: true`/prior `clear()` call) if a seed is already present:

```js
create = makeConcurrent(
  async ({ mnemonic, passphrase } = {}) => {
    if (await this.exists()) {
      throw new Error('Wallet already exists. Use clear() or addSeed() instead of create()/import().')
    }
    // ... existing logic
  },
  { concurrency: 1 }
)
```

### Proof of Concept
1. Instantiate the `wallet` module (as wired in `sdks/headless`) with a working `seedStorage`.
2. Call `await exodus.wallet.create({ passphrase: 'pw1' })` and record the returned `seedId`; note `await exodus.wallet.exists()` is now `true`.
3. Fund/derive addresses from this seed (conceptually — the seed is the only reference to any keys/funds tied to it).
4. Call `await exodus.wallet.create({ passphrase: 'pw2' })` again (or `exodus.wallet.import({ mnemonic: newMnemonic, passphrase: 'pw2' })`).
5. Observe that `#setSeed` in `features/wallet/module/wallet.js` overwrites `SEED_KEY` with the new seed; `await exodus.wallet.getMnemonic({ passphrase: 'pw1' })` now fails/returns the new mnemonic, and the original mnemonic (and all funds derivable from it) is unrecoverable because it was never retained anywhere else in the module.

    if (this.#usePassword) {
      if (passphrase) {
        await this.walletStorage.delete(GENERATED_PASSPHRASE_KEY)
        await this.walletStorage.set(HAS_USER_SET_PASSPHRASE_KEY, true)
      } else {
        if (this.#useAutoGeneratedPassword) {
          passphrase = genPassphrase()
          await this.walletStorage.set(GENERATED_PASSPHRASE_KEY, passphrase)
        }

        await this.walletStorage.set(HAS_USER_SET_PASSPHRASE_KEY, false)
      }
    }

    await this.walletStorage.set(SEED_KEY, seed, { passphrase })
