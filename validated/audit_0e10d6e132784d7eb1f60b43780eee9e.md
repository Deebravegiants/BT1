### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's webhook handler as the trusted tenant identifier. Because the `shop` value is never included in the signed material, any two requests whose bodies produce the same HMAC (trivially achievable, since many webhook topics have static or attacker-influenced bodies for the requester's own shop) can be replayed with an arbitrary `shop-domain` header and will pass verification, letting an unprivileged internet user impersonate a different tenant to the host application's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely separate from the signed content: [2](#0-1) 

`Registry.process` verifies the request using only `Utils::HmacValidator.validate(request)` — i.e., only the body — and then constructs `WebhookMetadata` using `request.shop` taken directly from the unauthenticated header, dispatching it to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the body) matches the HMAC computed with `Context.api_secret_key`; it has no knowledge of, and does not bind, the `shop` header: [4](#0-3) 

The identity binding that should hold is:
`shop_header == shop_bound_by_HMAC`

but in reality:
`shop_header ∈ {arbitrary attacker-chosen value}` while `HMAC` only proves `body == signed_body`.

**Attack path (unprivileged internet user):**
1. Attacker installs the target public app on their own store (or otherwise legitimately triggers a webhook, e.g. `app/uninstalled`, whose body is empty/static `"{}"` or otherwise predictable/attacker-influenced) and captures the resulting `(raw_body, hmac)` pair delivered by Shopify to the app's webhook endpoint.
2. Attacker replays that exact `raw_body` + `hmac` to the app's webhook endpoint, but substitutes the `x-shopify-shop-domain` header with a victim shop's domain.
3. `Utils::HmacValidator.validate` succeeds because the HMAC only ever covered `raw_body`.
4. `Registry.process` calls the app's `handler.handle` with `shop: <victim-shop>`, `topic`, and the attacker-controlled body, exactly as if the victim shop had generated that event.

Because host applications key their tenant data/actions off `WebhookMetadata#shop` (per the library's own contract, this is the "necessary information to identify the session"), the attacker can trigger tenant-scoped side effects (e.g., re-triggering `app/uninstalled` cleanup logic, GDPR redact-style handlers, or any handler that writes/deletes data keyed by `shop`) against a shop they do not control.

### Impact Explanation
This breaks the tenant boundary between shops using the same app (cross-tenant access), which is explicitly listed as a Critical-severity impact. An attacker who controls only their own (legitimately installed) shop can cause the host application to process a forged event as if it originated from an arbitrary victim shop, with no access token, secret, or privileged account required beyond running the app on their own store.

### Likelihood Explanation
Any merchant/developer can install a public app for free and receive genuine webhook deliveries for their own store — this satisfies the "unprivileged internet user" bar. Several mandatory/common webhook topics (e.g. `app/uninstalled`) have empty or highly predictable bodies, making a valid `(body, hmac)` pair trivial to obtain and replay against a different `shop-domain` header. No cryptographic secret needs to be recovered; only the header needs to be changed, which is entirely within the attacker's control when crafting the HTTP request to the app's endpoint.

### Recommendation
- Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) to the authenticated material, e.g., by requiring the host application to independently confirm the `shop` header corresponds to a shop with a known/active session/installation before trusting `WebhookMetadata#shop`, or by including these header values in the value that is HMAC-verified where feasible.
- At minimum, document prominently in `Registry.process`/`WebhookMetadata` that `shop` is unauthenticated relative to the HMAC and must not be used as the sole tenant-identification source for security-sensitive operations; require handlers to cross-check `shop` against the app's own installation records.
- Consider validating `shop` with `ShopifyAPI::Utils::ShopValidator` and rejecting unknown/uninstalled shops before invoking the handler, closing the gap between "body is authentic" and "the claimed origin shop is authentic."

### Proof of Concept
```ruby
# Attacker legitimately installs the app on "attacker-shop.myshopify.com"
# and receives a genuine app/uninstalled webhook with an empty body:
raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), REAL_APP_SECRET, raw_body)
# (attacker captures this exact hmac from the real webhook delivery to their endpoint)

# Attacker now replays the same body/hmac but swaps the shop header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HMAC validation (Utils::HmacValidator.validate only checks raw_body)
# => handler.handle invoked with shop: "victim-shop.myshopify.com"
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
