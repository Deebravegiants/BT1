### Title
Webhook `shop` identity is derived from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (tenant) attribute that host applications use to route/act on the webhook is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. This breaks the identity binding "shop acted upon == shop authenticated by the HMAC," letting an attacker who controls one valid `(body, hmac)` pair relabel it as belonging to any other shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` decodes the `hmac-sha256` header and is validated against that signable string via `HmacValidator.validate`, which computes `HMAC(secret, to_signable_string)` and compares it to the received value: [2](#0-1) 

Meanwhile `Request#shop` — the field the host application relies on to know which merchant/tenant the webhook is for — is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed payload: [3](#0-2) 

Because `shop` is never part of `to_signable_string`, the HMAC only proves "this body was signed by someone who knows `client_secret`" — it proves nothing about which shop the body/header combination refers to. An attacker who owns a shop (e.g., a free development store) will receive genuine, correctly-signed webhooks from Shopify for their own store. They can capture one such `(raw_body, hmac header)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Request#shop` now returns the attacker-chosen victim domain, even though the *content* of `raw_body` was generated by/for the attacker's own shop.

This is the same bug class as the report: a field that is acted upon (`shop`, used to select which tenant the webhook pertains to) is not covered by the cryptographic verification (`hmac` over `raw_body` only) — "bytes verified versus bytes parsed" and "a field acted on but not covered by the HMAC."

### Impact Explanation
Applications built on this gem typically use `request.topic`, `request.shop`, and `request.parsed_body` from `Webhooks::Request` to decide which merchant record to mutate (e.g. `app/uninstalled` disabling a shop's session, `shop/update`, `customers/data_request`, `customers/redact`, `shop/redact`). Because `shop` is forgeable independently of the HMAC-protected body, an attacker with a valid signed webhook for their own shop can make the host application believe the event pertains to a different, victim shop — a cross-tenant identity-binding bypass. Depending on how the host app wires up handlers, this can drive cross-tenant state changes (e.g., forcing an uninstall/data-redaction flow against a shop the attacker doesn't own), which falls under "cross-tenant access."

### Likelihood Explanation
Any internet user can obtain an account/development store on Shopify and receive legitimate signed webhooks for it — no privileged credentials, no access to the target app's `client_secret`, and no interception of the victim's traffic are required. The only requirement is the ability to send an HTTP request to the app's public webhook endpoint with attacker-controlled headers and Shopify-issued signed body — both of which are attacker-controlled inputs to `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)`.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the value that is actually verified, e.g. include the shop-domain header in `to_signable_string`, or better, require the caller to supply the expected shop out-of-band (from the OAuth/session context) and assert it matches `request.shop` before trusting it, rather than trusting an unauthenticated header as the sole source of tenant identity.

### Proof of Concept
1. Attacker installs the app on their own (attacker-owned) shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `app/uninstalled`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(client_secret, B)`.
2. Attacker POSTs to the victim app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. Host application does:
   ```ruby
   request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)
   ShopifyAPI::Utils::HmacValidator.validate(request) # => true, since to_signable_string only checks B
   request.shop # => "victim.myshopify.com" (attacker-controlled, unauthenticated)
   ``` [4](#0-3) [1](#0-0) 
4. The HMAC check passes even though `shop` is forged, because `shop` was never part of the signed bytes, allowing the attacker to make the app process a webhook event as if it came from `victim.myshopify.com`.
