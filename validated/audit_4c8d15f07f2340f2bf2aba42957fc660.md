This confirms the vulnerability: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the request via `Utils::HmacValidator.validate(request)`, but `HmacValidator.validate` only checks the signature against `Request#to_signable_string`, which returns `@raw_body` alone [1](#0-0) . The `shop` value passed downstream into `WebhookMetadata` comes straight from the unsigned `shopify-shop-domain` header [2](#0-1) , and `Registry.process` forwards this attacker-controllable `request.shop` to the handler as the tenant identifier without any binding to the HMAC [3](#0-2) .

### Title
Webhook tenant (shop) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop` (tenant identifier) is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed content. `Registry.process` trusts `request.shop` as the tenant identity for dispatching to the app's webhook handler after only checking the body HMAC.

### Finding Description
The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` AND `shop ∈ signed_bytes`. In this gem it instead holds: `HMAC(secret, raw_body) == received_hmac`, with `shop` taken from an out-of-band header that is never part of `signed_bytes`.

- `Request#hmac` decodes the `hmac-sha256` header [4](#0-3) .
- `Request#shop` reads the `shop-domain` header directly, with no cryptographic tie to the body or the HMAC [2](#0-1) .
- `Request#to_signable_string` signs only `@raw_body` [1](#0-0) .
- `HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` and compares to the received HMAC [5](#0-4) .
- `Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatching `request.shop` (the untrusted header value) to the app's handler as the tenant identity [3](#0-2) .

Because the same request body can be legitimately delivered to any shop that installs the app (each shop's app installation causes Shopify to emit webhooks with that shop's `shop-domain` header, but the HMAC is computed with the *app's single shared* `client_secret`, not per-shop), a body captured from one tenant's genuine webhook delivery remains valid — HMAC-wise — with any other `shop-domain` header substituted, since the header is never part of the signed bytes. Any unprivileged actor who can install the app on their own store (a normal, unprivileged flow) can capture a validly-signed webhook body/HMAC pair from their own tenant, then replay that exact body+HMAC to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a different, victim tenant. `Registry.process` will accept it as valid (since HMAC validation only checks the body) and dispatch it to the handler tagged with the victim's shop, breaking the tenant boundary the host app relies on `request.shop` to enforce.

### Impact Explanation
This crosses the tenant boundary: an app relying on this gem's `request.shop`/`WebhookMetadata#shop` to select which merchant's data to update (a documented, intended usage pattern) can be made to apply a replayed payload under another shop's identity, since the header carrying that identity is unauthenticated. This matches the "Critical - cross-tenant access" impact category, analogous to the original bug class where a state transition/identity check answered permissively because the field it should have gated on (`isLastAttempt` there, `shop` here) was not actually bound into the verification the code performs.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a store they control (a normal, unprivileged onboarding action) and capture one legitimately delivered webhook body/HMAC pair — no access to `api_secret_key`, tokens, or the victim's credentials is needed. The replay is a simple HTTP request with a substituted header.

### Recommendation
Bind the tenant identity into the verified bytes: include `shop` (and ideally `topic`/`webhook_id`) in the signed content that `HmacValidator` checks, or independently verify that `request.shop` matches a shop for which the app has an active, previously-established installation/session before trusting it as the dispatch key, rather than trusting the unauthenticated header directly.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B`, header `shopify-hmac-sha256: H` (computed as `HMAC-SHA256(client_secret, B)`), and `shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and `H` from that request.
3. Send a new POST to the app's webhook endpoint with the identical body `B` and identical `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and matches `H` — validation passes because the shop header was never part of the signed bytes [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to process attacker-supplied data under the victim shop's tenant identity [7](#0-6) .
