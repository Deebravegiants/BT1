### Title
Partial-fill escrow release in `_fillSameChain` rounds to zero for skewed order ratios, letting a solver's output payment go uncompensated - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` computes the proportional input-escrow amount released to a solver for a non-completing partial fill as `(order.inputs[i].amount * fillAmount) / totalRequired`. When the order's requested output amount (`totalRequired`) is very large relative to the escrowed input amount and the solver's fill size, this integer division truncates to `0`, so the solver transfers real output tokens to the beneficiary but is refunded zero input tokens — an unrecoverable loss for that solver, identical in mechanism to the reported UpDown-game rate-truncation bug.

Only the fill that exactly completes the order (`amountFilled == totalRequired`) sweeps the full remaining escrow balance (this is the existing "rounding dust" fix for the *final* filler). Every other, non-completing partial fill uses the raw ratio `order.inputs[i].amount * fillAmount / totalRequired`, with no minimum-output check. Meanwhile the solver's payment to the beneficiary is computed unconditionally right before this: [2](#0-1) 

If `order.inputs[i].amount * fillAmount < totalRequired`, `escrowedAmount` truncates to `0` while `fillAmount` (and the corresponding `beneficiaryTotal` transfer of output tokens) is still strictly positive — exactly the same rounding pattern as `calculateUpDownRate`/`calculateSetupRate` in the reported bug: a legitimate, nonzero contribution is priced at a `0` rate due to insufficient precision in a lopsided ratio.

### Impact Explanation
A solver who partially fills a heavily skewed order (large `totalRequired` output vs. small escrowed input, or a very small fill relative to `totalRequired`) pays real ERC20/native tokens to the order's beneficiary via `safeTransferFrom`/`.call{value:...}` but receives `escrowedAmount = 0` back from escrow. This is a direct, unrecoverable loss of solver funds reachable via a single unprivileged `fillOrder` transaction — matching the "concrete theft" bar, since value is transferred out with no corresponding release, and the withheld share is later distributed to whichever solver happens to complete the order rather than to the solver who was shorted.

### Likelihood Explanation
Order composition (input/output token amounts and decimals) is fully user (order-creator) controlled, and fill sizing is solver controlled, so the skew needed to trigger truncation (e.g., an 18-decimal output requirement many orders of magnitude larger than a 6-decimal input escrow) is trivially constructible on any order with disparate decimals or intentionally large `output.assets[i].amount`. No privileged role or special network condition is required — only that a solver picks (or is tricked into) a fill size that produces `inputAmount * fillAmount < totalRequired`.

### Recommendation
Require sufficient precision/minimum output for partial (non-final) escrow releases, e.g. revert if the computed `escrowedAmount == 0` while `fillAmount > 0`, or scale intermediate values up before dividing (analogous to `lostTeamTotal *= 10**decimals` in the referenced report) so the ratio cannot silently collapse to zero for legitimate nonzero fills. Alternatively, enforce a minimum fill/escrow ratio so partial fills that would round to zero are rejected rather than executed at a loss to the solver.

### Proof of Concept
1. User places an order with `order.inputs[0] = {token: USDC, amount: 100e6}` (100 USDC, 6 decimals) and `order.output.assets[0] = {token: DAI, amount: 1e12 * 1e18}` (an extremely large, but permissible, requested DAI amount — user-controlled).
2. Solver calls `fillOrder` with `options.outputs[0].amount = 1e18` (1 DAI), a legitimate partial fill (`fillAmount = 1e18 < remaining`).
3. In `_fillSameChain`: `amountFilled (1e18) != totalRequired (1e30)`, so `escrowedAmount = (100e6 * 1e18) / 1e30 = 1e26 / 1e30 = 0`.
4. The solver's `beneficiaryTotal = 1e18` DAI is transferred to the beneficiary via `safeTransferFrom`, while `escrowedInputs[0].amount = 0` is withdrawn to the solver — the solver receives nothing for a real 1 DAI payment, and the withheld 100 USDC share remains in escrow to be claimed disproportionately by whichever solver later completes the order.
