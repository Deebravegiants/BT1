### Title
Stale in-memory account overwrite after unguarded refund token transfers in `flash_position` enables double withdrawal — (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The libsoup UAF is a missing-state-synchronization defect: an object freed by an asynchronous callback is then touched again by code holding a stale reference. The direct analog in the controller is `process_flash_position`, which mutates an `Account` struct purely in memory, performs **unguarded** external token transfers to the caller (`refund_listed_assets`), and only afterwards persists the stale struct via `strategy_finalize`. A listed refund asset with a transfer hook (the test suite itself exercises such a market via `with_transfer_hook_market`) lets a caller reenter `withdraw`/`borrow` on the same account, which loads the pre-flash state from storage, pays out collateral, and persists — after which the outer call writes back the stale in-memory copy that still contains the withdrawn supply, letting the attacker withdraw it twice.

### Finding Description
The critical ordering is visible in `contracts/controller/src/strategies/flash_position.rs`:

- Line 120-143: `storage::with_flash_guard` wraps only the mint/forward/callback window. Baselines are snapshotted inside it.
- Line 145-146: collateral deltas are deposited into the **in-memory** `account` via `process_deposit`.
- Line 148: `refund_listed_assets` runs **after the guard closes** — confirmed by the test comment at `tests/test-harness/tests/strategy/flash_position_adversarial.rs:170-172` ("The refund `balance` and `transfer` calls run after `with_flash_guard` closes") and by `docs/reference/invariants.md` INV-FLASH-02 noting the windows "do not wrap every token call."
- Line 153: only then does `strategy_finalize(env, account_id, &mut account, &mut cache)` persist the mutated struct.

During `refund_controller_balance_delta` (`contracts/controller/src/payments.rs`), the controller transfers listed assets back to `caller`. If that token invokes a hook, the caller (or its receiver contract, which is already authorized as the account owner) reenters `withdraw(caller, account_id, …)`. `withdraw` loads `account` from storage — which does **not** yet contain the in-flight flash mutations — validates solvency against the pre-flash balances, pays out supply collateral, and writes its own result to storage. The outer call then resumes and `strategy_finalize` overwrites that stored account with its stale in-memory `account` that still holds the withdrawn `supply_positions`. The collateral is now on the books a second time and can be withdrawn again.

This is exactly the reported class: an external operation at a specific timing point invalidates state that a stale internal reference subsequently "uses" again — here, the freed/mutated queue item is the persisted `Account` record, and the stale pointer is `&mut account`.

### Impact Explanation
An unprivileged attacker controlling a receiver contract (permitted by the rules: own flash receiver) can:

1. Open or reuse a `Multiply` account with pre-existing supply collateral.
2. Call `flash_position` declaring a listed hook-bearing asset in `refund_assets`.
3. From the refund transfer hook, call `withdraw` to drain the account's entire supply balance.
4. Let the outer `strategy_finalize` resurrect the withdrawn `supply_positions`.
5. Call `withdraw` again on the same account.

The same supply shares are paid out twice — direct theft of pooled user funds, since the second withdrawal is backed by other suppliers' deposits. This meets the theft-of-user-funds acceptance criterion.

### Likelihood Explanation
- `flash_position` is permissionless; the caller need only own the account (or be a delegate), which it does for an account it created.
- `refund_assets` entries must merely be "listed active" assets (`validate_refund_assets`, lines 240-247) — no allowlist excludes hook-bearing tokens, and the codebase explicitly supports transfer-hook markets in tests.
- The attacker needs the refund transfer to reach them, which is automatic: refunds go to `caller`.
- The only mitigating uncertainty is whether some intermediate code (e.g., inside `borrow_into_controller` or `process_deposit`) eagerly persists account state before line 148; I could not fully trace persistence boundaries in this pass. If any persistence occurs earlier without re-validation, the overwrite primitive still applies to whichever fields remain buffered; the `docs` invariant language and the deliberate placement of `strategy_finalize` after refunds strongly suggest persistence is deferred to finalization, consistent with "persistence removes empty accounts" (line 151).

### Recommendation
Either extend `with_flash_guard` to cover the `refund_listed_assets` transfers, or persist the finalized `account` (and re-load it) before making any external calls outside the guard. The minimal fix is to reorder: run `strategy_finalize` (persistence + risk gates) before `refund_listed_assets`, or perform refunds via balance-delta accounting that credits the account rather than transferring tokens to a hook-capable recipient.

### Proof of Concept
```text
Setup: market lists HOOK (a token whose transfer invokes a receiver hook) plus
USDC and ETH. Attacker deploys Receiver R (a wasm contract). R calls
flash_position(caller=R, account_id=A [pre-funded with USDC supply],
    spoke_id, Multiply, debt=ETH-hub-asset, amount, receiver=R, data,
    collaterals=[(USDC, min)], refund_assets=[HOOK]).

1. flash_position mints ETH debt on account A (in memory), forwards ETH to R.
2. R's execute_flash_position callback transfers USDC collateral to controller.
3. Guard closes. collect_collateral_deposits credits USDC supply to in-memory A.
4. refund_listed_assets transfers the controller's HOOK balance delta to R.
5. HOOK's transfer hook (executing as R) calls controller.withdraw(R, A, USDC-all).
   withdraw loads A from storage (no flash mutations), pays out USDC, persists A'.
6. Outer call resumes; strategy_finalize(A, stale_account) writes the stale copy
   that still contains the USDC supply positions, overwriting A'.
7. R calls withdraw(R, A, USDC-all) again — second payout of the same shares.
```
