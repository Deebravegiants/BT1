### Title
Phantom price snapshot's liquidity-weighted median can be skewed by manipulating a solver's live `balanceOf()`, poisoning the published `LiquidityPool` rate used to price real intents - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` sets a leg's published price to a **liquidity-weighted median** of solver bids, where a bid's weight is the solver's live, unauthenticated `balanceOf()` of the leg's output token (read on-chain at aggregation time), not a value committed at bid time. Because a solver controlling >50% of a leg's total weight makes `weightedMedian` return its own quoted price verbatim, temporarily inflating a wallet's balance before the bid window closes lets an attacker/solver dictate the published rate. That rate is persisted as `LiquidityPool.sellRate`/`buyRate` and consumed by `IndexedRateIntentQuoteStrategy`/`quoteIntent` to size real, fund-moving `IntentGateway` orders — the same "balanceOf()-driven, capital-inflow-manipulable value feeds a downstream financial decision" root cause as the referenced USSD rebalancer report.

### Finding Description
`aggregatePhantomBids` → `runAggregation` weights each solver's quote by `getBalance(destUrl, chain, outputToken, solver)`, which is a raw `eth_call` to `balanceOf(address)` at (approximately) "latest" for the destination chain: [1](#0-0) 

The weight computed this way directly determines the selection made by `weightedMedian`, which is a *selection*, not a blend — the winner's exact price is emitted verbatim once its cumulative weight crosses half the total: [2](#0-1) 

The project's own flow documentation states the consequence explicitly: *"a solver holding over half the leg's weight sets the published price verbatim"*: [3](#0-2) 

Nothing authenticates or time-locks that balance against the bid: `getTotalSolverBalance`/`getBalance` is a plain, spot `balanceOf` read (plus vault `maxWithdraw`), taken well after the bid was signed, when `handlePhantomOrderPrices` runs on `PhantomBidWindowExhausted`: [4](#0-3) [5](#0-4) 

Because the balance is read at (or near) aggregation time — after the bid window has closed, potentially several blocks after the bid itself — a solver only needs to hold inflated capital in its wallet across that window, not within a single atomic transaction (unlike a strict flash-loan attack). This is exactly the "large capital inflow, not necessarily flash-loan" manipulation vector the referenced report describes for `balanceOf()`-derived rebalancing inputs.

The resulting median price is written unchanged into `LiquidityPool.sellRate`/`buyRate` via `updateLiquidityPools`, and it is this pool rate — not a real order book — that `IndexedRateIntentQuoteStrategy` and `LiquidityEngine.getBuyAndSellRates` use by default to construct real `IntentGateway` orders' `inputs`/`output.assets` amounts: [6](#0-5) [7](#0-6) 

This mirrors the reported vulnerability class precisely: an on-chain `balanceOf()` value that any unprivileged actor can push up with capital they control feeds directly into a price/ratio computation (`vol1`/`vol2` → `getSupplyProportion` in the original report; solver weight → `weightedMedian` here) that in turn drives real value transfers (rebalance buy/sell in USSD; real intent order sizing here).

### Impact Explanation
A solver can:
1. Move (borrow, transfer in, or otherwise acquire) a large balance of a leg's output token into its own wallet on the destination chain before or during the bid window.
2. Submit a phantom bid quoting a favorable (mispriced) rate for that leg.
3. Because its balance now dominates the leg's weight, `weightedMedian` publishes that solver's exact quoted price as the pool's `sellRate`/`buyRate`, unconditionally (the docs confirm `lowestPrice`/`highestPrice` are also overwritten with this value so downstream consumers cannot detect the manipulation as an outlier).
4. Any user who subsequently calls `quoteIntent` with the default `indexed_rates` strategy gets a swap quote built entirely from this poisoned rate, and places a real, fund-escrowing `IntentGateway` order at that bad rate.
5. The manipulating solver (or a colluding solver) then fills that mispriced order, extracting value from the user, or simply the published market data misdirects arbitrage-based liquidity for a window, since "solvers arbitrage away per-chain drift" is the design's own correctness assumption.

This is a real loss-of-funds vector for users trusting the indexed rate to build orders, not merely a griefing/DoS issue, satisfying the Medium+ bar (mispriced value transfer stemming from an unauthenticated, attacker-controllable state read).

### Likelihood Explanation
The precondition — holding a large balance of a specific ERC-20 in one's own wallet for the duration of a bid window — is realistic and cheap relative to a strict single-block flash loan requirement, since normal lending/borrowing or self-funded capital works. The attack requires no special privilege: it only needs an address that can be delegated as (or is already) a configured solver account submitting a phantom bid, and phantom bids are explicitly an open, permissionless price-discovery mechanism ("solvers compete", "bid window"). The system's own documentation already flags this precise weighting property as intentional design ("a solver holding over half the leg's weight sets the published price verbatim") without any mitigating floor, deviation cap, or time-weighting on the balance read, which is a red flag that this manipulation path was not defended against.

### Recommendation
- Do not weight quotes by a spot, unauthenticated `balanceOf()` read taken after the bid; instead require the balance to be attested/locked at bid-submission time (e.g., snapshot balance in the same block the bid is signed, or require an escrow/stake proportional to claimed weight).
- Apply a maximum-influence cap per solver per leg (e.g., no single solver's weight may exceed some fraction of total, analogous to a deviation/outlier guard), so no single balance can force `weightedMedian` to return its own price verbatim.
- Cross-check the published median against an independent reference price (as already done for the Uniswap V4 venue price guard via `checkPriceGuard`/`maxDeviationBps`) before it is written into `LiquidityPool.sellRate`/`buyRate`, and reject/flag snapshots that deviate too far from recent history or from other chains' samples (the existing `warnOnDivergentSample` only warns, it does not reject).
- Consider time-averaging (TWAP-like) the weight or the resulting rate across multiple windows before it is trusted by `quoteIntent`, rather than using a single-window liquidity-weighted median as the authoritative price for constructing real orders.

### Proof of Concept
1. Attacker controls/derives a delegated SolverAccount and monitors for a `PhantomOrderV2` on a target chain/leg (e.g., cNGN/USDC).
2. Before the bid window closes, attacker temporarily moves a large balance of the leg's output token (e.g., USDC) into the SolverAccount's EVM wallet on the destination chain — via a loan, a treasury transfer, or any capital source; no atomicity with the bid tx is required since the balance is read later, at `PhantomBidWindowExhausted`.
3. Attacker submits a phantom bid quoting an artificially favorable price for that leg (`aggregatePhantomBids` will apply only the standard 5-10bps haircut, per `applyProtocolFeeHaircut`/`applyUniswapQuoteHaircut`, not a market check).
4. When `handlePhantomOrderPrices` fires, `runAggregation` reads the attacker's inflated balance via `getBalance`/`getTotalSolverBalance`, computes a dominant weight, and `weightedMedian` returns the attacker's exact quoted price as `medianPrice`/`lowestPrice`/`highestPrice`.
5. `updateLiquidityPools` persists this as the pool's `sellRate`/`buyRate`.
6. Attacker withdraws/returns the temporary capital.
7. A victim calls `IntentGateway.quoteIntent` (default `indexed_rates` strategy), receives amounts computed from the poisoned rate, and places a real order escrowing tokens at the manipulated price — realizing a loss when filled, exactly analogous to the cited report's manipulated `vol1`/`vol2` triggering an incorrect `rebalance()`.

Note: full verification of the exact time gap between bid submission and the aggregation-triggering block (which bounds how long the inflated balance must be held) was not completed within available tool calls; this depends on the pallet's phantom-order bid-window configuration, which lives outside the indexed/SDK code inspected here.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

	 * Returns the indexed pool's aggregate buy and sell rates in less-valued
	 * quote-token units per one base token.
	 *
	 * The indexer depth-weights fresh per-chain samples into the pool rates. The
	 * source and destination chains remain part of the result because they define
	 * the cross-chain route whose configured token symbols were resolved.
	 */
	async getBuyAndSellRates(params: {
		sourceChain: Chains
		destinationChain: Chains
		tokenInSymbol: ConfiguredAssetSymbol
		tokenOutSymbol: ConfiguredAssetSymbol
	}): Promise<BuyAndSellRates | undefined> {
		const pool = resolveLiquidityPool(params.tokenInSymbol, params.tokenOutSymbol)
		const response = await this.queryClient.request<BuyAndSellRatesResponse>(BUY_AND_SELL_RATES, {
			poolId: pool.poolId,
		})
		if (!response?.liquidityPools?.nodes) {
			throw new InvalidLiquidityIndexerResponseError("liquidity pool connection is missing")
		}
		const indexedPool = response.liquidityPools.nodes[0]
		if (!indexedPool) return undefined
		validateIndexedPool(indexedPool, pool)

		const sell = readIndexedRate(indexedPool.sellRate, indexedPool.lastUpdatedAt, "pool sell rate")
		const buy = readIndexedRate(indexedPool.buyRate, indexedPool.lastUpdatedAt, "pool buy rate")
		const inputIsToken0 = params.tokenInSymbol.toLowerCase() === pool.token0Symbol.toLowerCase()
		const direct = inputIsToken0 ? sell : buy
		const reverse = inputIsToken0 ? buy : sell
		if (!direct && !reverse) return undefined

		const quoteTokenSymbol = resolveQuoteTokenSymbol(
			params.tokenInSymbol,
			params.tokenOutSymbol,
			direct?.scaledRate,
			reverse?.scaledRate,
		)
		const quoteIsTokenOut = quoteTokenSymbol === params.tokenOutSymbol
		const orientedBuy = quoteIsTokenOut ? direct : reverse
		const orientedSell = quoteIsTokenOut ? reverse : direct

		return {
			baseTokenSymbol: quoteIsTokenOut ? params.tokenInSymbol : params.tokenOutSymbol,
			quoteTokenSymbol,
			sourceChain: params.sourceChain,
			destinationChain: params.destinationChain,
			buyRate: orientedBuy ? formatUnits(orientedBuy.scaledRate, INDEXER_FIXED_POINT_DECIMALS) : null,
			sellRate: orientedSell
				? formatUnits(reciprocalRate(orientedSell.scaledRate, "sell rate"), INDEXER_FIXED_POINT_DECIMALS)
				: null,
			buyRateUpdatedAt: orientedBuy?.updatedAt ?? null,
			sellRateUpdatedAt: orientedSell?.updatedAt ?? null,
		}
	}
