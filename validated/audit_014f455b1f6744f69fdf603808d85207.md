### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted by the handler without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC over the raw body only, but hands `shop`, `topic`, and `webhook_id` — all taken directly from unauthenticated HTTP headers — to the handler as trusted identity data. This breaks the binding `shop authenticated-by-HMAC == shop acted-on-by-handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from the (attacker-controllable, in the sense that they are ordinary HTTP headers not covered by any signature) `shopify-*` / `x-shopify-*` headers: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body was signed with the app's secret at some point) and then dispatches the handler with `request.shop`, `request.topic`, and `request.webhook_id` as trusted metadata: [3](#0-2) 

The `WebhookMetadata` struct passed to the handler bundles this unauthenticated `shop` value alongside the authenticated body, presenting it to host applications as if it were verified: `data.shop`, `data.topic`, `data.webhook_id` are consumed directly by app-provided handlers (see test usage confirming this is the intended, documented API surface) [4](#0-3) .

Because the HMAC is computed only over the JSON body and the shared secret, any two webhook deliveries with identical (or attacker-obtainable) `raw_body` bytes produce the same valid HMAC regardless of which shop the headers claim to be for. An unprivileged attacker who can obtain one valid `(raw_body, hmac)` pair — e.g., by installing the app on their own shop and receiving a legitimate webhook, since apps typically expose a public webhook endpoint — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain. The library's `HmacValidator.validate` only checks the body signature and will accept the request as valid: `validate(verifiable_query)` never inspects `shop`: [5](#0-4) [6](#0-5) 

The equality that should hold but does not is: `shop bound by HMAC == shop delivered to WebhookMetadata.shop`. In fact no shop value is bound by the HMAC at all — the signable string never includes `shop`.

### Impact Explanation
Host applications built on this gem are told (per the library's own webhook API contract, exercised directly in the gem's own test suite) that `WebhookMetadata#shop` is an authenticated identifier they can use to route/attribute webhook data to a specific tenant (shop). Because `shop` is not covered by the HMAC, an attacker can forge the shop-identity of an otherwise-legitimate HMAC-signed payload, causing the host app to process/store attacker-supplied body data under a victim shop's identity — i.e., cross-tenant data confusion/injection through the gem's own trusted API. This matches the Critical "cross-tenant access" impact category, since it lets an attacker cause the app to attribute (and potentially act upon/persist) content for a shop that is not theirs.

### Likelihood Explanation
Likelihood is bounded by the practical need for the attacker to obtain at least one valid `(raw_body, hmac)` pair signed with the target app's `api_secret_key`. This is achievable without any privileged credentials: the attacker installs the target app on a shop they control (a normal, unprivileged action for any Shopify developer) and receives real webhook deliveries from Shopify for their own shop, each carrying a valid HMAC for a body they can fully control the shape of (JSON keys/values within Shopify's schema). They then replay that body+HMAC to the app's public webhook endpoint with the `shop-domain` header swapped to the victim shop. No secret, token, or victim credential is required — only observation of headers on requests the attacker already legitimately receives.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., require the app to independently confirm the shop via a previously-stored, authenticated session rather than trusting the header value in `WebhookMetadata`). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be treated as authenticated by consuming applications.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid signature of `B` with the app's secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `B` and the shared secret — this passes because `shop` is never part of the signed string: [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is `"victim-shop.myshopify.com"`, even though the payload was never actually sent by/for that shop: [3](#0-2) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
