## Title
Reentrancy in `IntentGatewayV2.withdraw()` (Tron deployment) — escrow transfer executes before accounting update, reintroducing the ERC-777/malicious-token reentrancy pattern already patched on the EVM mainline - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` still contains the exact checks-effects-interactions violation the referenced report warns about: escrowed input tokens (or native ETH) are pushed to the beneficiary via a raw `.call` *before* the `_orders[commitment][token]` accounting is decremented. The mainline EVM version of this contract was already hardened for this class of bug (CEI-ordered `_withdraw` in `IntentsBase.sol`, `nonReentrant` on `placeOrder`, and a dedicated `IntrinsicIntentsReentrancyTest.sol` regression suite), but the Tron copy was not updated to match, leaving a reachable reentrancy window during escrow settlement.

### Finding Description
`IntentGatewayV2.withdraw()` in the Tron contracts performs the external transfer first and mutates state after: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

Compare with the fixed mainline EVM logic in `IntentsBase.sol::_withdraw`, which decrements escrow **before** calling `safeTransfer`/`_sendValue`: [2](#0-1) 

`withdraw()` is reachable from two unprivileged/relayer-driven paths that any user or relayer can trigger:

1. `cancelOrder` (same-chain branch), user-callable directly, with no `nonReentrant` guard: [3](#0-2) 

2. `onAccept` for `RedeemEscrow`/`RefundEscrow`, invoked by the host when a relayer delivers the corresponding cross-chain message: [4](#0-3) 

The gateway accepts **arbitrary ERC-20 tokens** as order inputs/collateral (`token.call(transfer...)` on an attacker-chosen address), exactly the precondition the original report calls out for ERC-777-style/malicious tokens. Additionally, `placeOrder` credits escrow with `+=` rather than rejecting duplicate input tokens (unlike the mainline `IntentGatewayV2.sol::placeOrder`, which explicitly reverts on duplicate input tokens via `_orders[commitment][token] != 0`): [5](#0-4) [6](#0-5) 

and neither `placeOrder` nor `cancelOrder`/`withdraw` carry a `nonReentrant` modifier, unlike the hardened mainline `placeOrder`: [7](#0-6) 

The `_orders[commitment][token] == 0` check in `withdraw()` also only guards against an *empty* balance, not against amount sufficiency, so it does not compensate for the reentrancy window.

### Impact Explanation
Because the external call happens while `_orders[commitment][token]` for every token in the `WithdrawalRequest` (including tokens not yet reached in the loop) is still fully credited, an attacker-controlled token contract (used as an order input) or an attacker-controlled beneficiary contract (for the native-ETH branch) gains an execution window with stale escrow accounting mid-settlement, before any decrement is applied for that or subsequent tokens in the same call. This is the same class of bug as the referenced Inverse Finance M-04 (collateral withdrawn twice against one stale balance check), and can result in the same outcome here — unbacked release of escrowed order funds beyond what should be paid out for a single settlement, i.e., concrete theft/drain of escrowed user or protocol funds on the Tron deployment.

### Likelihood Explanation
Reachable by any unprivileged user: placing a same-chain order with a self-deployed malicious ERC-20 as an input token and then calling `cancelOrder` requires no special permissions and no proof/relaying. The cross-chain path (`onAccept`→`withdraw`) is reachable by any relayer delivering a legitimately-authenticated `RedeemEscrow`/`RefundEscrow` message for an order that used a malicious token, which is also permissionless from the attacker's perspective (they simply choose the input token when placing the order). No governance or admin compromise is required — matching the "single submitted transaction / relayed proof" reachability bar.

### Recommendation
Port the CEI fix already applied to the mainline EVM contracts into the Tron deployment:
- In `withdraw()`, decrement `_orders[body.commitment][token] -= amount` (and clear `TRANSACTION_FEES`) **before** performing the external `.call`/native transfer, mirroring `IntentsBase.sol::_withdraw`.
- Reject duplicate input tokens in `placeOrder` (`_orders[commitment][token] != 0 → revert`) instead of using `+=`.
- Add `nonReentrant` to `placeOrder`, `cancelOrder`, and the `onAccept`/`withdraw` entry points, consistent with the mainline gateway and the report's recommended mitigation.
- Port or adapt `IntrinsicIntentsReentrancyTest.sol` to the Tron contract to lock in the fix.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer(to, amount)` implementation, on being invoked by the gateway, re-enters the gateway (e.g., attempts to trigger further withdrawal-adjacent logic or drain the shared `ICallDispatcher` while `_orders[commitment][...]` for this and other tokens in the same `WithdrawalRequest` remain un-decremented).
2. Attacker calls `placeOrder` with `order.inputs = [EvilToken: X, USDC: Y]`, escrowing both into `_orders[commitment]`.
3. Attacker calls `cancelOrder` (same-chain branch) for this order; `_filled[commitment]` is unset, so it proceeds to `withdraw(body, true)` with `body.tokens = order.inputs`.
4. Inside `withdraw()`, the loop reaches `EvilToken` first: `_orders[commitment][EvilToken] == 0` check passes (still `X`), then `EvilToken.call(transfer(attacker, X))` executes attacker code **before** `_orders[commitment][EvilToken] -= X` runs and **before** the `USDC` entry later in the same loop is decremented.
5. During this callback window, `_orders[commitment][EvilToken]` and `_orders[commitment][USDC]` both still read their pre-withdrawal (stale) values, giving the attacker's reentrant code a window to act on/extract value against accounting that has not yet been settled — the same "stale balance during reentrant hook" primitive described in the referenced report, present here because the transfer-then-decrement ordering was never fixed in this contract copy.
