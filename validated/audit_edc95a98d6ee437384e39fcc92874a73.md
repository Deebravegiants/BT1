## Analog Found

### Title
Tron `IntentGatewayV2.cancelOrder`/`withdraw` reverts entirely and permanently freezes remaining escrow when any single input token's balance is already zero - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The reported keep-tecdsa bug is a class of "loop-over-N-entries reverts on the first already-zero entry, blocking recovery of the remaining N-1 legitimate entries" issue. The Tron variant of the Intent Gateway's escrow-release path exhibits the identical pattern: `withdraw()` iterates the token list of a `WithdrawalRequest` and unconditionally `revert`s with `UnknownOrder` if `_orders[commitment][token] == 0` for **any** token in the batch, with no per-item skip for tokens that legitimately no longer carry escrow. Unlike the hardened EVM (`evm/src/apps/intentsv2`) implementation, this Tron `withdraw()` has no `if (amount == 0) continue;` guard, and `cancelOrder`'s same-chain branch feeds it the order's *original* `order.inputs` amounts instead of the live `_orders[commitment][token]` balances.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the same-chain cancellation path builds the withdrawal request straight from the order's static input list: [1](#0-0) 

and `withdraw()` then loops over that token list: [2](#0-1) 

Note the check `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` runs for every token in the loop with **no skip when `amount == 0`**, and critically no skip based on whether the escrow for that particular token has already been legitimately drained (e.g. via a prior partial fill of that specific input/output pair). Compare this to the corrected, hardened pattern in the EVM implementation's `_withdraw`, which explicitly tolerates a zero-balance entry: [3](#0-2) 

and whose `_cancelSameChain` deliberately re-reads the *live* escrow per token (not the static order amount) so that already-drained tokens are passed through as `amount == 0` and skipped rather than triggering a revert: [4](#0-3) 

The Tron contract does neither of these things: it passes the original `order.inputs` (non-zero, pre-fill amounts) directly into `withdraw()`, and `withdraw()` has no tolerance for a token whose escrow balance is already zero. If any one of a multi-token order's input balances has already been fully consumed by a prior operation on that token (analogous to a keep member's bond already being fully seized/reassigned), the entire `withdraw()` call — and therefore the entire `cancelOrder` transaction — reverts. Because `_filled[commitment]` is only set at the top of `withdraw()` in memory/storage within the same reverting transaction, the revert discards that write too, so the order can never be finalized: every future call to `cancelOrder` for that commitment hits the same zero-balance token and reverts again, permanently freezing the remaining (non-zero) escrow of the other input tokens in that same order.

### Impact Explanation
This is a direct, permanent freezing-of-funds bug reachable via a single user-submitted `cancelOrder` transaction, matching the required severity bar (permanent freezing of funds). Once one input token's escrow for a multi-token order commitment reaches zero while other input tokens for the same order still hold escrowed value, the order becomes permanently un-cancellable and un-finalizable on Tron — the remaining tokens are stuck in the contract with no code path able to release them (every call reverts identically).

### Likelihood Explanation
Likelihood depends on how a per-token escrow balance for one input of a multi-token order can reach zero while sibling input tokens for the same commitment remain non-zero, prior to a terminal `cancelOrder`/`withdraw` call. The Tron file could not be fully read within available iterations to confirm whether its `fillOrder`/partial-fill logic mutates `_orders[commitment][token]` per-token (as the EVM `IntrinsicIntents._fillSameChain` does via `_partialFills`), so I cannot verify with certainty the exact operational trigger for the Tron contract producing this pre-condition. This is a structural/code-review-level finding based on direct comparison against the hardened EVM twin of the same contract, not a fully traced end-to-end exploit.

### Recommendation
Mirror the EVM `IntentsBase._withdraw` / `IntrinsicIntents._cancelSameChain` pattern in the Tron contract:
1. In `withdraw()`, add `if (amount == 0) continue;` before checking/decrementing `_orders[body.commitment][token]`, and only revert with `UnknownOrder` when the whole withdrawal request nets to zero escrow across all tokens (not per-item).
2. In `cancelOrder`'s same-chain branch, build the `WithdrawalRequest.tokens` from the *live* `_orders[commitment][token]` balances rather than the static `order.inputs`, so already-drained tokens are represented as `amount == 0` and safely skipped.

### Proof of Concept
Conceptual reproduction (contingent on a code path that legitimately zeroes one input token's escrow for a multi-input-token order while leaving others funded, e.g. through partial-fill or fee/dust accounting differing per token on Tron):
1. Place a same-chain order with two distinct input tokens, `A` and `B`, both escrowed under the same commitment.
2. Drive token `A`'s escrow for that commitment to zero through whatever legitimate flow zeroes it while token `B` remains escrowed (this is the part not fully confirmed for the Tron contract due to file-size/iteration limits).
3. Call `cancelOrder(order, options)` on the same chain. `withdraw()` iterates `[A, B]`; hitting `A` with `_orders[commitment][A] == 0` reverts the whole transaction with `UnknownOrder`, even though `B` still holds refundable escrow.
4. Every subsequent `cancelOrder` call for this commitment reverts identically — token `B`'s escrow is permanently stuck.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
