### Title
Webhook shop-domain identity is not covered by the HMAC binding, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by checking the HMAC over the raw request body only, then trusts the `shopify-shop-domain` header as the tenant identity that is handed to the app's `WebhookHandler`. Because the HMAC signature never covers the shop-domain header, the tenant binding `hmac_signed_bytes == bytes_that_determine_shop` does not hold, mirroring the analog bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) .

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, and then immediately forwards `request.shop` (the unauthenticated header value) to the registered handler as the tenant context: [3](#0-2) .

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the app secret, and compares it against the `hmac` header decoded via `Digest.hexencode(Base64.decode64(...))`: [4](#0-3) . Nowhere in this validation path is the `shop-domain` header included in the signed material.

This means: for a fixed `(raw_body, hmac)` pair that legitimately validates for the app's secret (i.e., a genuine webhook delivery that an unprivileged holder of that webhook payload can capture/replay, e.g. from their own shop, from a webhook debugging/logging endpoint, or from a load balancer/proxy that forwards the same request to multiple app instances), the `shop-domain` header can be freely modified without invalidating the HMAC check, since the header is not part of the signed bytes. The equality that should hold — "the shop identity handed to app logic == the shop identity implicitly authenticated by the HMAC" — is broken because the HMAC only authenticates the body, not the tenant-identifying header.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (populated from `request.shop`) to select which merchant's stored session/access token to act on, to which merchant's local records a webhook payload is attributed, or to authorize follow-up API calls, an attacker who can influence or replay the `shop-domain` header on an otherwise-validly-signed webhook request can cause the app to process data under, or take actions attributed to, a different tenant than the one that actually owns the signed payload — a cross-tenant integrity/confusion issue. This matches the "cross-tenant access" class in the accepted Critical impact category, since the shop binding that gatekeeps tenant-scoped processing is not authenticated by the same mechanism (`HmacValidator`) that is supposed to establish trust in the request.

This is a library-level design gap: the gem hands the unauthenticated `shop` header straight to consuming code as if it were verified, alongside a `hmac` accessor that gives the false impression the whole `Request` object (including `shop`) has been validated once `HmacValidator.validate(request)` passes.

### Likelihood Explanation
Exploitability requires the attacker to possess or intercept one legitimately-signed webhook body/HMAC pair reachable by an unprivileged actor — for example, from their own installed shop's webhook deliveries, which Shopify sends to any app the actor installs, or via an environment where the same raw body/HMAC could be replayed with a different header set (e.g., multi-tenant proxy misconfiguration, shared webhook endpoint across environments). Because `shop` is not part of `to_signable_string`, no additional secret knowledge is needed to vary it. The likelihood is moderate: it depends on how the host app uses `WebhookMetadata#shop`, but the gem provides no protection or documentation warning that this field is unauthenticated, making misuse likely for typical implementers who assume `HmacValidator.validate` covers the whole `Request`.

### Recommendation
Either (a) document explicitly that `Webhooks::Request#shop` (and `topic`, `api_version`, `webhook_id`) are NOT covered by the HMAC and must not be trusted for tenant-scoped authorization without independently verifying the shop against the caller's own registered/expected shop list, or (b) extend `to_signable_string` / add a secondary binding check that ties the shop-domain header into the trust decision (e.g., requiring the caller to supply the expected shop and comparing it before dispatch), so `Registry.process` cannot dispatch a body validated for one shop under another shop's identity.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `hmac = HMAC(secret, B)`.
2. Attacker (who owns `shop-a` themselves, as any developer can install their own app) captures `(B, hmac)`.
3. Attacker resends the same `(B, hmac)` to the app's webhook endpoint but with `shopify-shop-domain: shop-victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` still passes because `to_signable_string` returns `B` only [1](#0-0) .
5. `Registry.process` calls the handler with `shop: request.shop` == `"shop-victim.myshopify.com"` [5](#0-4) , even though the signed payload was never authenticated for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
