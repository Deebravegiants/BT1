### Title
Duplicate `erc20TokenAddresses` entries cause double-counting of a single UTXO and duplicate on-chain commitment insertion - (contracts/Hinkal.sol)

### Summary
In `Hinkal.transact`, the outer loop over attacker-supplied `circomData.erc20TokenAddresses` reruns the inner `utxoSet` scan for every occurrence of the same token address, with no marking of already-matched `utxoSet[j]` entries. When the same `erc20Address` appears at two indices `i` and `k`, a single returned UTXO satisfies the balance equation at both indices and is written into `onChainCommitments` twice, producing two identical spendable leaves from one real balance movement.

### Finding Description
Equality that should hold: **total value inserted into the Merkle tree as on-chain commitments == the real balance movement backing them (one UTXO of amount X → one leaf of value X)**. The bug breaks this into: one balance movement of `X` → two leaves each worth `X`.

Path: `Hinkal.transact` [1](#0-0)  calls `hinkalHelper.performHinkalChecks` (calldata-hash / dimensions checks only — no uniqueness constraint on `erc20TokenAddresses`) [2](#0-1) , then `checkOnchainCreation`, which only enforces `amountChanges[i] == 0` when `onChainCreation[i]` is true — again with no dedup check across indices [3](#0-2) .

`oldBalances`/`newBalances` are captured once for the whole `erc20TokenAddresses` array via `getBalancesForArray`, which just re-reads the same on-chain balance for a repeated address, so `oldBalances[i] == oldBalances[k]` and `newBalances[i] == newBalances[k]` whenever `erc20TokenAddresses[i] == erc20TokenAddresses[k]` [4](#0-3) [5](#0-4) . Consequently `balanceDif` computed at index `i` is identical to `balanceDif` at index `k` (line 98-109) — both equal to the single real balance change `X` caused by one deposit.

The inner loop, for each outer `i`, rescans the *entire* `utxoSet` and matches by `erc20Address` with no removal/marking of consumed entries: [6](#0-5) 
So the same `utxoSet[j]` (amount `X`, `erc20Address == tokenA`) is matched again at index `k`, adding `X` to `utxoAmount` at `k` as well, and appending a second, identical `OnChainCommitment` into `onChainCommitments[onChainCommitmentCounter++]`.

The balance-equation check at line 137-146 then independently verifies, for both `i` and `k`:
`balanceDif (X) == (onChainCreation[idx] ? 0 : amountChanges[idx]) + utxoAmount(idx)`.
If the attacker sets `onChainCreation[i] = onChainCreation[k] = true` (forcing `amountChanges[i] = amountChanges[k] = 0` per `checkOnchainCreation`), both equations reduce to `X == X`, which trivially holds — even though only one real UTXO of value `X` was ever produced/deposited.

The resulting `onChainCommitments` array (length 2, both identical) is passed into `insertCommitments`, so two identical leaves worth `X` each are inserted into the Merkle tree, whereas only `X` was actually deposited. No existing guard (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, or the balance/slippage `require`s) checks for duplicate `erc20TokenAddresses` entries or marks consumed `utxoSet` entries, so the divergence is not caught.

Attacker's call: submit `transact` with an external action (e.g. an on-chain UTXO deposit action) whose `utxoSet` return value contains one UTXO of amount `X` for `tokenA`, and craft `circomData.erc20TokenAddresses = [tokenA, tokenA]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, `slippageValues` satisfied by the single real deposit of `X`.

### Impact Explanation
This mints one extra spendable, shielded leaf of value `X` for every real deposit of `X`, i.e., shielded value created without backing — a direct value-minting / double-spend precursor. This matches the "Critical" category: minting shielded value without backing / double spend of a leaf that was never actually funded twice.

### Likelihood Explanation
The attacker only needs to be an unprivileged depositor: deposit `X` of `tokenA` through any external action that returns a `utxoSet` entry for `tokenA`, and duplicate `tokenA` in `circomData.erc20TokenAddresses` with matching `onChainCreation`/`amountChanges` entries. No special role, relay, or victim funds are needed — the attack is self-funded (repayable X deposit → 2X of leaves), and repeatable indefinitely (attacker can duplicate the token address N times to mint N×X worth of leaves from one X deposit, subject to array-length/gas practicalities, which are out of scope but do not block feasibility for small N).

### Recommendation
- Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck`/`performHinkalChecks` (reject duplicates), or
- Mark/remove `utxoSet[j]` entries once matched (e.g., delete/zero them or track a `bool[] consumed` array) so each UTXO can only be attributed to a single outer index `i`, and
- Ensure `onChainCommitmentCounter` cannot exceed the number of distinct UTXOs actually returned by the external action per unique token.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` + a mock external action that returns a `UTXO[]` with a single entry `{erc20Address: tokenA, amount: X, ...}` when invoked, backed by an actual ERC20 transfer of `X` into the Hinkal contract.
2. Craft `circomData` with `erc20TokenAddresses = [tokenA, tokenA]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, valid `calldataHash`/proof for these public inputs (proof only needs to attest to circuit-checked fields; `erc20TokenAddresses` content itself is not canonically pinned).
3. Call `Hinkal.transact(...)`.
4. Assert:
   - `balanceDif` computed at index 0 equals `balanceDif` at index 1 (both equal `X`).
   - `onChainCommitments.length == 2` and `onChainCommitments[0]` (hash4 leaf) `== onChainCommitments[1]` (identical hash), both derived from the single `utxoSet[0]`.
   - After `insertCommitments`, the Merkle tree contains two distinct leaf indices with the identical commitment hash.
   - Using `MerkleRootCalculator`, both leaf indices independently produce a valid inclusion proof against the tree root, confirming two spendable leaves of value `X` exist despite only one `X` deposit having occurred (`contract balance increased only by X`, `sum of leaves inserted == 2X`).
