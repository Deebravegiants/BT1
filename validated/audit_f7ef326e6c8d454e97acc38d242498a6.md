**No vulnerability found for this question.**

The question's premise does not match the actual code. In `packages/intents-sdk/src/sdk.ts`, `createWithdrawalIntents` computes:

```
const actualAmount = args.withdrawalParams.feeInclusive
    ? args.withdrawalParams.amount - args.feeEstimation.amount
    : args.withdrawalParams.amount;
``` [1](#0-0) 

The subtraction `amount - feeEstimation.amount` only executes when `feeInclusive` is `true`. The question explicitly states `feeInclusive: false`, in which case `actualAmount` is simply `args.withdrawalParams.amount`, unmodified — no subtraction occurs, and `actualAmount` cannot become `0n` from this path.

Tracing through to `HotBridge.createWithdrawalIntents`, with `feeInclusive: false` the `amount` passed in equals the user's original `withdrawalParams.amount`. For a native fee asset, `feeAmount` is added on top (`amount = withdrawalParams.amount + feeAmount`), and the resulting `mt_withdraw` intent debits `amount + feeAmount` from the user while the destination `receiver` still receives the full `amount` specified by the user (the fee is paid *in addition to*, not subtracted from, `amount`). For non-native fee assets, the fee is instead settled via a separate `token_diff` intent against `feeEstimation.quote`, again without touching the withdrawal `amount`. [2](#0-1) 

So for `feeInclusive: false`, the invariant the question itself defines — `sum(debits) == amount + fee` and `destination receives amount` — holds exactly as implemented; there is no divergence to exploit in this specific case.

The distinct scenario where `FeeExceedsAmountError` is genuinely bypassed and `actualAmount` can underflow/hit zero requires `feeInclusive: true` with an attacker-supplied `feeEstimation.amount >= amount` via `signAndSendWithdrawalIntent`/`createWithdrawalIntents` skipping `_estimateWithdrawalFee`'s guard [3](#0-2) . That is a different precondition than the one specified in this question (`feeInclusive: false`), so it is out of scope for this specific Q5813 analysis.
