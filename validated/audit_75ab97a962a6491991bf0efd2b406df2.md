Unchecked empty request body causes out-of-bounds panic in `ExtrinsicIntents.onAccept`, allowing a permissionless message to grief batched Hyperbridge message delivery - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` reads the first byte of the incoming ISMP POST request body to select a `RequestKind` **before** validating that the body is non-empty. A source-chain caller can permissionlessly dispatch a `PostRequest` with `body = ""` targeted at the deployed `IntentGatewayV2`/`ExtrinsicIntents` contract. Once relayed and proven, delivery of that single request causes a Solidity out-of-bounds `Panic(0x32)`, which propagates up through `HandlerV2.handlePostRequests` and reverts the entire batched delivery transaction — including any unrelated, legitimate `RedeemEscrow`/`RefundEscrow` messages bundled in the same relayer transaction.

`incoming.request.body` is a `calldata bytes` slice fully controlled by whoever originally called the permissionless `IDispatcher(host).dispatch(...)` on the *source* chain with `to` set to this contract's address. Indexing `body[0]` when `body.length == 0` reverts with an index-out-of-bounds panic — the Solidity equivalent of the mishandled zero-length field in the Dovecot RPA advisory, where a length of zero was not checked before being used to index/parse the input.

Unlike the many other adversarial-input hardening fixes present elsewhere in this codebase (e.g. `modules/trees/ethereum/src/node_codec.rs`'s `empty_hp_prefix_returns_error_not_panic`, `modules/consensus/pharos/primitives/src/spv.rs`'s `nibble_at_depth` bound, `modules/consensus/beefy/verifier/src/lib.rs`'s `leaf_indices.len() != 1` check) — all of which explicitly guard against zero-length/short adversarial inputs before indexing — `ExtrinsicIntents.onAccept` has no analogous guard on `incoming.request.body`.

`HandlerV2.handlePostRequests` verifies the merkle multiproof for the whole batch and then dispatches each leaf without isolating per-leaf failures:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [2](#0-1) 

There is no try/catch around this dispatch (contrast with the LayerZero endpoint adapter elsewhere in the codebase, which explicitly isolates the downstream call specifically to prevent a single bad payload from reverting the whole delivery): [3](#0-2) 

So a single crafted zero-body `PostRequest` addressed to the `ExtrinsicIntents` contract, once included in a batch, panics and reverts the *entire* `handlePostRequests` call.

### Impact Explanation
Any account on any Hyperbridge-connected source chain can permissionlessly dispatch an ISMP POST request with an empty body to the `IntentGatewayV2` deployment on a destination chain, at the cost of only the dispatch fee. Once that message is included by a relayer in a batched `handlePostRequests` delivery (a common relayer optimization to amortize gas), the malformed message's `onAccept` call panics and reverts the whole batch — including delivery of legitimate `RedeemEscrow`/`RefundEscrow` messages for real, filled/cancelled cross-chain intents bundled alongside it. This can be used to repeatedly grief relayers and delay or deny timely delivery of escrow-release/refund messages to the intent gateway, matching the "route unable to deliver messages" acceptance criterion — a genuine availability impact on the intents settlement path reachable from a single unprivileged submitted transaction, directly analogous to the Dovecot CVE's unprivileged crash from a mishandled zero-length field.

### Likelihood Explanation
High. Dispatching an arbitrary-body ISMP POST request is a normal, permissionless, low-cost operation exposed by every `IDispatcher.dispatch` on every supported chain; producing an empty body requires no special crafting. Whether the batch is disrupted depends on relayer batching behavior, but since `HandlerV2.batchCall`/`handlePostRequests` explicitly support and are advertised for batching multiple messages together for gas efficiency, hitting this path only requires an attacker to send one cheap malicious message and wait for a relayer to include it alongside real traffic.

### Recommendation
In `ExtrinsicIntents.onAccept`, validate `incoming.request.body.length != 0` (and, ideally, validate the length is sufficient for the full expected payload of each `RequestKind`) before indexing `body[0]`, reverting with a typed error (e.g. `InvalidInput()`) instead of allowing an out-of-bounds panic. Additionally, consider isolating each leaf's `dispatchIncoming` call in `HandlerV2` (or at the host level) with a try/catch, consistent with the pattern already used in `HyperbridgeLzEndpoint.onAccept`, so that a single malformed downstream module call cannot revert an entire batch of otherwise-valid message deliveries.

### Proof of Concept
1. On any source chain registered with the target `ExtrinsicIntents`/`IntentGatewayV2` deployment, call `IDispatcher(host).dispatch(DispatchPost{ dest: <destChain>, to: abi.encodePacked(<ExtrinsicIntentsAddress>), body: "", timeout: 0, fee: 0, payer: msg.sender })`. This is permissionless and requires no prior registration as a gateway peer.
2. Wait for state finalization/consensus update on the destination chain.
3. A relayer (or the attacker themselves, since `handlePostRequests` is permissionless) submits a `PostRequestMessage` batch to `HandlerV2.handlePostRequests` that includes this leaf together with other pending legitimate `PostRequestLeaf` entries destined for the same or other apps.
4. `host.dispatchIncoming` invokes `ExtrinsicIntents.onAccept` for the crafted leaf; `incoming.request.body[0]` on the empty `body` triggers `Panic(0x32)`, which is not caught anywhere in the call stack, reverting the entire `handlePostRequests` transaction and failing delivery of every other message in that batch.

*Note: I was unable to directly inspect `IsmpHost.dispatchIncoming`'s implementation in this pass to confirm with 100% certainty that it contains no try/catch around the module callback; the absence of such isolation is inferred from (a) the code shown for `HandlerV2.handlePostRequests` calling `dispatchIncoming` with no error handling, and (b) the explicit comment in `HyperbridgeLzEndpoint.sol` stating that *it* adds try/catch specifically to prevent a downstream revert from bubbling up — implying the host-level call into `onAccept` does not already provide that isolation. Confirming this fully would require reviewing the `EvmHost.dispatchIncoming` source directly.*
