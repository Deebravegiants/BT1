### Title
Stale DelegateGrant Resurrects Revoked Delegate Authority When the Position NFT Returns to a Prior Owner - (File: contracts/controller/src/storage/account.rs)

### Summary
`removeRole`-analog: the controller's delegate authorization mirrors the bug class where removing authority from one index leaves a live authorization entry behind. Delegates are stored in a `DelegateGrant { granted_by, delegates }` entry keyed by `ControllerKey::Delegates(account_id)` (`common/src/types/controller.rs:63-73`). An NFT transfer implicitly "removes" the grant — `get_delegates` filters on `granted_by == current owner` (`contracts/controller/src/storage/account.rs:176-181`) — but the grant entry itself is never deleted on transfer. If the NFT later returns to `granted_by` before any intervening owner performs an `add_delegate`/`remove_delegate` write, the stale grant silently re-arms and the old delegate regains full owner-gated power over the account.

### Finding Description
`is_owner_or_delegate` resolves authority by reading the stored `DelegateGrant` and checking `grant.granted_by == owner`. Because nothing purges the entry at transfer time, revocation-by-transfer is only a read-time mask:

- `get_delegates` returns `grant.delegates` whenever `granted_by` equals the current NFT owner, so dormant grants become live again on return (`storage/account.rs:176-181`).
- `DelegateGrant`'s own doc comment states: "If the NFT returns to `granted_by` before such a write, the original delegate list is live again" (`common/src/types/controller.rs:63-67`).
- Only a subsequent `add_delegate` (overwrite) or `remove_delegate` by the new owner purges the stale grant (`storage/account.rs:226-247`); the position NFT README confirms "the stale grant stays in storage and re-arms if the token returns to `granted_by`".
- A live delegate can invoke owner-gated verbs — `borrow`, `withdraw` — to a recipient of its choosing ("Delegates can borrow/withdraw to their chosen recipient", threat model), constrained only by account risk gates, not by the owner's economic interest. Revived authority additionally requires the delegate to still be an active global position manager (`set_account_delegate` enforces `is_active` only at grant time; `is_owner_or_delegate` checks it at call time per `delegate_revocation_between_legs.rs`).

Reachable path for a single unprivileged actor (a position-manager contract that was once a delegate): wait for the NFT to be transferred back to the original grantor (or acquire and return it via `transfer`/`transfer_from` after being approved), then call `controller.withdraw(caller=delegate, account_id, withdrawals, to=delegate)` or `borrow(..., to=delegate)` — no owner signature required once `granted_by == owner` again.

### Impact Explanation
Theft of user funds. Upon resurrection, the formerly-removed delegate can withdraw all withdrawable collateral to itself and borrow up to the account's LTV limits to its own address, leaving the owner with a debt-encumbered or drained account — equivalent to the report's "formerly authorized entities can still perform sensitive operations".

### Likelihood Explanation
Medium. Exploitation requires the NFT to return to `granted_by` with no intervening `add_delegate`/`remove_delegate` by intermediate holders, and requires the delegate's global position-manager registration to remain active. Both conditions are plausible for round-trip transfers (e.g., NFT used as collateral elsewhere, sold and repurchased, or moved between a user's own wallets where intermediate holders never touch delegate state). The threat model itself flags the revival behavior, but no mechanism prevents it absent an explicit delegate write.

### Recommendation
Delete (or epoch-stamp) the `Delegates` entry atomically on ownership change rather than masking it by `granted_by`. Since the NFT cannot hook the controller on transfer, a cheaper fix is to include a transfer epoch or owner-sequence in the grant stamp — e.g., store the NFT owner's authorization/transfer nonce and bump it on first owner interaction — so grants are permanently invalidated at transfer rather than merely dormant. At minimum, have `account_owner`/first post-transfer touch purge a mismatched `granted_by` entry as `remove_delegate` already does (`storage/account.rs:236-238`).

### Proof of Concept
1. Alice owns account NFT `id`; governance has activated manager `M` via `set_position_manager(M, true)`.
2. Alice calls `controller.add_delegate(alice, id, M)` — `DelegateGrant{granted_by: alice, delegates: [M]}` stored.
3. Alice transfers NFT to Bob (`position_nft.transfer(alice, bob, id)`). Grant is dormant but still in storage; Bob never calls `add_delegate`/`remove_delegate`.
4. Bob transfers the NFT back to Alice (or Alice repurchases it). `granted_by == alice == owner` again — the grant is live.
5. `M` calls `controller.borrow(caller=M, account_id=id, ..., to=M)` and `controller.withdraw(..., to=M)`, succeeding because `is_owner_or_delegate` resolves through the resurrected grant, draining collateral/borrowing against Alice's account without any new authorization from her.

Contrast with the fix already applied to revocation (`remove_delegate` purges stale grants to prevent resurrection, `storage/account.rs:226-238` and test `remove_delegate_purges_stale_grant_preventing_resurrection`) — the transfer path lacks an equivalent purge.
