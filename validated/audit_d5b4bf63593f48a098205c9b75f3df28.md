## Finding

### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are used unauthenticated because the HMAC only signs the raw body — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — none of the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material, yet those exact header values are what get handed to the app's handler as trusted identifiers.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute and compare the signature strictly against `to_signable_string` (i.e., the raw body), never touching the headers: [3](#0-2) 

`Registry.process` gates handling on that same HMAC check, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the `WebhookMetadata` passed to the app-registered handler: [4](#0-3) 

This breaks the intended identity binding: `shop == HMAC-verified shop`. In reality, the HMAC proves only "this body was produced with knowledge of `client_secret`" — it says nothing about which shop, topic, or webhook the body belongs to. Because the same `client_secret` is shared across every shop that installs a given app, any merchant who legitimately installs the app can receive a genuinely-signed webhook body+HMAC pair for their own store, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and the gem hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to look up the victim's stored session/access token and apply the (attacker-controlled) body's data (e.g., write order/customer/inventory data, trigger `app/uninstalled` cleanup, etc.) under that shop's identity, this yields cross-tenant data injection/corruption — an unprivileged merchant of one tenant can make the app act on data attributed to a different tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be an ordinary merchant who installs the app on their own store (no `api_secret_key`, no stolen token, no privileged access) to obtain one genuinely-signed webhook body/HMAC pair, then craft a raw HTTP POST to the app's public webhook endpoint with a forged `shop-domain`/`topic` header. This is fully reachable through the gem's own `Webhooks::Registry.process`/`Webhooks::Request` API as documented, not a misuse of an undocumented feature.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify the shop domain against a value obtained independently of the header, and treat the header as merely a routing hint rather than a trusted identity). At minimum, document that `Webhooks::Request#shop`/`#topic` are NOT authenticated by the HMAC check and must not be trusted for tenant/session lookups without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers a real event (e.g., `orders/create`), and captures the resulting webhook POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `client_secret`).
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only (`to_signable_string`), matches `H`, and returns `true`.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` from the forged header, and invokes the app's handler as if the (attacker-controlled) body belonged to `victim-shop`.
