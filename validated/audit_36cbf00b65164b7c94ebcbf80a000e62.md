### Title
Account authority bound to the stale stored owner instead of the current position-NFT holder lets the previous owner keep full control (withdraw collateral, repay, delegate) after the NFT is transferred — (File: contracts/controller/src/account.rs)

### Summary
The Electron-Cash-SLP bug class is "capability routed to the wrong address": the mint baton was sent to an attacker/wrong party, permanently transferring minting authority. The analog in XOXNO Lending is account authority routed to the wrong party: the `Account` struct stores `owner` at NFT mint time, and the privileged position operations (`withdraw`, `repay`, `multiply`, `migrate_from_blend`, strategies) authorize via `require_owner_or_delegate(caller, &account.owner)` against that stored field, while a separate, correct path (`require_account_owner`) reads live ownership from the position-NFT contract via `storage::account_owner`. If the stored `owner` is not re-synced on NFT transfer, the prior owner remains the effective authority — the same "baton went to the wrong address" shape.

### Finding Description
`create_account_with` mints the NFT to `owner` and persists `owner` inside `Account` once, at creation. There is no update of `account.owner` on NFT transfer:

- Mint-time-only assignment: `contracts/controller/src/account.rs:63-70` — `nft_mint_call(env, &nft, owner)` then `Account { owner: owner.clone(), .. }`. The only NFT interactions are `nft_mint_call`, `nft_burn_call`, `nft_renew_call` (lines 12, 63, 162, 225); no ownership-sync hook exists.
- Privileged-path auth uses the stored field: `process_withdraw` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (`contracts/controller/src/positions/supply.rs:150`) and then pays out to `to.unwrap_or(caller)` (line 152) — so the stale owner can both pass auth and name their own payout address.
- `require_owner_or_delegate` accepts `caller == owner` outright (`account.rs:121-127`) and also honors the stale owner's delegate list (`storage::get_delegates(env, account_id, owner)`), so pre-transfer delegate grants to an active manager survive as well.
- The codebase itself acknowledges NFT ownership is the source of truth elsewhere: `require_account_owner` (`account.rs:143-148`) checks `storage::account_owner(env, account_id)` (the NFT's `owner_of`) for `renew_account` and delegate management. Two different notions of "owner" are used for auth on the same account — stored `account.owner` for fund-moving ops, live NFT owner for admin ops.

Concretely: Alice supplies collateral, the account NFT is transferred to Bob (the position-nft contract exposes transfer/approve per `contracts/position-nft/src/contract.rs`). `account.owner` still equals Alice. Bob cannot `withdraw` (fails `caller == account.owner` and is not in Alice's delegate set), while Alice — no longer the NFT holder — can still call `withdraw(account_id, withdrawals, to: Some(Alice))` and drain the collateral Bob acquired. The mint baton equivalent (control over the position) remained with the old address.

Caveat: I could not fully verify whether the position-NFT `transfer` implementation (or a controller hook) rewrites `account.owner` or blocks transfers of accounts with open positions; `contracts/position-nft/src/contract.rs` and `storage::account_owner` internals were not fully read in the available iterations. The finding stands if no such sync exists — which the coexistence of `require_account_owner` strongly suggests.

### Impact Explanation
Theft of user funds. After any NFT transfer (sale, OTC trade, or transfer to a vault contract), the previous owner retains the ability to withdraw all supply collateral of the account to an arbitrary `to` address, and delegates registered under the stale owner keep access. The new rightful owner is simultaneously locked out of `withdraw`, creating both theft and denial of control — matching the "wrong party gains the capability" impact of the reference advisory. Reachable by any unprivileged address via `position-nft` `transfer` plus controller `withdraw`.

### Likelihood Explanation
Medium. Exploitation requires (a) the NFT to be transferable while the account holds positions and (b) a transfer occurring — both plausible given `transfer`/`approve` are exposed entrypoints and liquidations/migrations incentivize NFT mobility. The stored-vs-live owner divergence is confirmed in the controller code; the only open question is whether an external sync closes it.

### Recommendation
Make live NFT ownership the single source of truth on every fund-moving path: in `require_owner_or_delegate`, resolve `owner` via `storage::account_owner(env, account_id)` instead of the persisted `account.owner`, or drop the stored `owner` field entirely. Alternatively, have the position-NFT contract invoke a controller sync hook on `transfer`/`approve` that rewrites `account.owner` and clears `storage::get_delegates` entries granted by the previous owner, so stale delegate grants cannot survive a transfer.

### Proof of Concept
1. Alice calls `supply`, creating `account_id = A` with collateral USDC; `account.owner = Alice`, NFT `A` minted to Alice.
2. Alice (optionally) registers an active manager M via `add_delegate`.
3. Alice calls `position_nft.transfer(Alice -> Bob, A)`.
4. Alice calls `withdraw(Alice, A, vec![(USDC, 0)], to: Some(Alice))`:
   - `require_owner_or_delegate(A, Alice, account.owner=Alice)` passes (`account.rs:121`).
   - Pool pays Alice; Bob's NFT `A` is emptied of collateral.
5. Alternatively M calls `withdraw` — `is_owner_or_delegate` still sees M in `get_delegates(A, Alice)`.
6. Bob's own `withdraw` reverts with `NotAuthorized` despite holding NFT `A`.
