### Title
Webhook `shop-domain` Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` field — used by `ShopifyAPI::Webhooks::Registry.process` to identify which tenant a webhook belongs to — is read from an HTTP header that is never included in the signed material. This breaks the equality that the docs and library implicitly promise: `hmac_valid(request) == true` should imply `request.shop` is authentic, but in fact `hmac_valid` only proves `raw_body` is untampered, not `shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived independently from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which plays no part in the signature computation: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `to_signable_string` (the body) against the header-provided `hmac-sha256` value: [3](#0-2) 

`Registry.process` performs this HMAC check and then unconditionally trusts `request.shop` as the tenant identity when building `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is a direct analog of the "Stake Mint Differentiation" bug class: in the Solana report, `set_stake` updated a value without binding it to the specific token mint identity, so two different mints could collide under one scale. Here, the HMAC "stakes" (authenticates) the webhook body, but never binds the `shop` identity to that same authenticated computation — so two different shops' identities can collide under one valid signature. The broken identity binding as an equality is:

`HMAC-SHA256(client_secret, raw_body) == header(hmac-sha256)` proves body integrity, but **does not** imply `header(shop-domain) == <shop the body actually originated from>`.

Because Shopify webhook signatures use the app's single, shop-independent `client_secret` (not a per-shop secret), any merchant who has installed the app (an "unprivileged" external party w.r.t. other tenants) can capture a genuine `(raw_body, hmac)` pair delivered to their own webhook endpoint for their own shop, then replay that exact same body+hmac to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header value to name a *different* shop. `HmacValidator.validate` still returns `true` (the body/hmac pair is genuine and untouched), and `Registry.process` forwards the attacker-chosen `shop` value straight to the app's handler as trusted tenant context.

### Impact Explanation
Per the docs (`docs/usage/webhooks.md`), the `shop` value returned to handlers is explicitly relied upon by host applications to scope side effects — e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. Any host app that follows this documented pattern (which is the intended/only usage pattern this gem exposes) will process data belonging to shop A under the identity of shop B, because the gem hands back an unauthenticated `shop` value alongside an authenticated body. This is a cross-tenant identity confusion: data intended for/about one merchant gets attributed to and potentially merged into another merchant's stored state (e.g., triggering `customers/redact` or order-processing side effects against the wrong tenant's records), which falls under "cross-tenant access" impact.

### Likelihood Explanation
Exploitation requires only: (1) the attacker to be a legitimate/unprivileged installer of the target app on their own store to receive real, validly-signed webhooks (standard, no special privilege), and (2) the app's webhook endpoint to be internet-reachable (a documented requirement of this gem's webhook flow). No access token, `client_secret`, or TLS interception is needed — the attacker only replays bytes they legitimately received and modifies a header that this library never protects.

### Recommendation
Include the shop identity in the material that is verified, e.g., bind `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) into `to_signable_string`, or independently verify the `x-shopify-shop-domain` header against a known/expected registered shop for that webhook subscription before trusting it in `WebhookMetadata`. At minimum, document (and enforce in-library) that `request.shop` is unauthenticated and must not be used for tenant-scoping decisions without additional verification.

### Proof of Concept
1. App installs on `Shop-A.myshopify.com`; Shopify sends a real webhook to the app's public endpoint:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `{"id":123,...}`
2. Attacker (a legitimate merchant using the same app, e.g., operating `shop-a.myshopify.com`) captures this raw request (body + `hmac-sha256` header) via their own logging/network tooling.
3. Attacker POSTs the identical `raw_body` and identical `x-shopify-hmac-sha256` value to the same app webhook endpoint, but with `x-shopify-shop-domain: shop-b.myshopify.com` (a header they fully control, since it's just an HTTP header on their own outbound request to the app's public URL, not something Shopify re-validates on inbound replays).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` at [5](#0-4) 
returns `true` because it only checks `raw_body` against the HMAC.
5. `Registry.process` calls the app handler with `WebhookMetadata` containing `shop: "shop-b.myshopify.com"` even though the payload actually originated from `shop-a.myshopify.com`, causing the host app to apply shop A's order data under shop B's tenant context.
