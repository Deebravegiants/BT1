### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong withdrawal (and destination tx hash) to be reported for batched same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific withdrawal (identified by NEAR tx hash + `index`) by delegating to `findMatchingWithdrawal`, which matches purely on `assetId` and ignores both `index` and `destinationAddress`/`amount`. When a single NEAR transaction contains two or more withdrawal intents for the same token (a legitimate, supported case via batched intents), every `describeWithdrawal` call for that tx returns the *first* API record matching the asset, regardless of which of the batched withdrawals is actually being queried.

### Finding Description
`createWithdrawalIntents` builds one `ft_withdraw` intent per `WithdrawalParams` [1](#0-0) , and the SDK's intent-payload builder allows multiple withdrawal intents to be signed and submitted in one NEAR transaction, each addressable later via `WithdrawalIdentifier.index` [2](#0-1) . `describeWithdrawal` is meant to report the on-chain outcome of the specific withdrawal at `args.index` for `args.tx.hash`, but it never uses `index` (or destination/amount) to disambiguate: it only calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [3](#0-2) [4](#0-3) . This is explicitly acknowledged in the code's own comment: "multiple withdrawals of the same token in a single transaction are not supported" [5](#0-4) .

The equality broken: the txHash/status reported for withdrawal `index=1` (destination B, amount B) is not the on-chain outcome for that withdrawal — it is instead the outcome of a different withdrawal (`index=0`, destination A, amount A) that happens to share the same `assetId` and the same NEAR transaction. `withdrawal-watcher.ts` treats `status === "completed"` as authoritative and terminates the poll, surfacing `{hash: status.txHash}` to the caller as the finalized destination transaction for that specific withdrawal identifier [6](#0-5) . An integrator (or the SDK's own `waitForWithdrawalCompletion`) consuming this per-index result has no way to detect the misattribution.

### Impact Explanation
An unprivileged user who structures a single NEAR transaction with two withdrawal intents of the same POA-bridged token to two different destination addresses/amounts can cause the SDK to report the second withdrawal as "completed" with the first withdrawal's destination tx hash (or vice versa) while the second withdrawal is still pending, failed, or refunded. Any integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` per-`index` result to credit an off-chain balance, close a support ticket, or release custody upon "completed" status can be misled into crediting/releasing for a withdrawal whose actual on-chain leg has not landed at the address the integrator expects — a status/hash misreport that can lead to double crediting or crediting the wrong destination, matching the High-severity class ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
Reachability requires only that a user (unprivileged) submit a batch of withdrawal intents for the same token in one transaction — this is a normal, supported feature of the intents SDK (batched intents in one NEAR tx), not an admin/relayer/bridge-operator action. The bug is deterministic given that scenario, since `.find()` always returns the first matching record irrespective of `index`.

### Recommendation
Disambiguate withdrawals within `findMatchingWithdrawal` using more than `assetId` — e.g., also match on `destinationAddress`/`amount`/`account_id`, or (once POA API supports it) an explicit per-intent identifier/index, and fail closed (keep "pending"/throw) rather than reporting a possibly-wrong match when multiple candidates share the same `assetId` for a given `tx.hash`.

### Proof of Concept
1. User submits one NEAR transaction containing two `ft_withdraw` intents for `nep141:usdc.omft.near`: withdrawal A to address `0xAAAA...` (amount 100), and withdrawal B to address `0xBBBB...` (amount 200).
2. POA bridge processes A first (completes, `transfer_tx_hash = "0xA-hash"`), while B is still pending.
3. Caller invokes `bridge.describeWithdrawal({ tx: {hash: near_tx}, index: 1, withdrawalParams: { assetId: "nep141:usdc.omft.near", destinationAddress: "0xBBBB...", amount: 200n, ... } })`.
4. `getWithdrawalStatusWithRetry` returns both withdrawal records for `near_tx`; `findMatchingWithdrawal` filters only by `assetId` and returns the first entry — withdrawal A's record (status `COMPLETED`, `transfer_tx_hash: "0xA-hash"`).
5. `describeWithdrawal` returns `{ status: "completed", txHash: "0xA-hash" }` for withdrawal B (destination `0xBBBB...`), even though B's actual funds have not moved and A's `0xA-hash` corresponds to a different address/amount entirely.

		// Response list is unsorted, so we match by assetId instead of index

			args.withdrawalParams.assetId,

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
