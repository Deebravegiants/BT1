Audit Report

## Title
Unbounded nested loop over attacker-controlled `Topics` array in web-api trigger gateway handler enables CPU-exhaustion DoS - (File: core/capabilities/webapi/trigger/trigger.go)

## Summary
`triggerConnectorHandler.processTrigger` iterates over every registered trigger nested inside a loop over `payload.Topics`, a field fully controlled by the sender of a `web_api_trigger` gateway message, with no upper bound on the number of topics enforced anywhere in the handler, the JSON-RPC message validation path, or the `TriggerRequestPayload` schema.

## Finding Description
`HandleGatewayMessage` unmarshals the JSON-RPC request body into `webapicap.TriggerRequestPayload` after only generic structural validation via `hc.ValidatedMessageFromReq`, and passes the payload straight to `processTrigger`: [1](#0-0) , [2](#0-1) 

Inside `processTrigger`, the only check performed on `topics := payload.Topics` is a non-empty check — there is no `MaxTopics`/length cap: [3](#0-2) 

The event trigger JSON schema for `TriggerRequestPayload.topics` likewise declares only `"type": "array", "items": {"type": "string"}` with no `maxItems` constraint: [4](#0-3) 

The handler then executes a nested loop over every currently registered workflow trigger crossed with every attacker-supplied topic, with authorization (`allowedSenders`) and rate-limiting (`rateLimiter.Allow`) checks only applied after a topic already matches `allowedTopics`, meaning they bound dispatch but not iteration cost: [5](#0-4) 

I confirmed there is no `MaxTopics`-style limiter analogous to `vaulttypes.MaxBatchSize` applied anywhere along this path. I also confirmed a `MaxRequestBodyBytes`-style limit exists at the gateway's HTTP/WS transport layer (`core/services/gateway/network/httpserver.go`, `wsserver.go`), which caps overall message size, but this is a generic body-size limiter, not a semantic cap on the number of topic strings — an attacker can still pack a very large number of short topic strings within that body-size budget.

## Impact Explanation
This maps to a legitimate CPU-exhaustion / denial-of-service concern in a gateway message-handling path reachable by any sender who can produce a validly-signed gateway message (self-asserted signer identity, not gated by DON membership or admin role). The cost of `processTrigger` scales as `O(len(triggers) × len(topics))` map lookups, so a single oversized-`Topics` message can force substantial synchronous CPU work on the node's gateway dispatch goroutine, delaying processing of legitimate trigger/gateway traffic. This is a real, code-confirmed gap, though its practical severity is moderated by the existing overall message-size limiter at the transport layer, which the report itself acknowledges as an area of uncertainty regarding the exact achievable topic count.

## Likelihood Explanation
Medium, as characterized in the original report: any client capable of reaching the gateway's `web_api_trigger` method and producing a body with a valid signature (self-signed, not requiring any special allowlist membership) can attempt this; the actual worst-case cost depends on the (unverified in this pass, but present) `MaxRequestBodyBytes` transport-layer cap and on how many workflows are registered on the target node at the time.

## Recommendation
Add an explicit upper bound (e.g., `MaxTopics`) on `len(payload.Topics)` in `processTrigger` (and ideally in the `event_trigger-schema.json` via `maxItems`), rejecting oversized requests before entering the nested loop, mirroring the `MaxRequestBatchSizeLimiter` pattern used for vault requests (`core/capabilities/vault/validator.go`). Consider iterating over the smaller of `topics`/`allowedTopics` to cap worst-case cost independent of registered trigger count.

## Proof of Concept
1. Register one or more `web-api-trigger` workflows via `RegisterTrigger` with a non-trivial `allowedTopics` set.
2. As any sender able to sign a gateway message body, submit a `web_api_trigger` JSON-RPC message whose `TriggerRequestPayload.Topics` contains a very large number of short, distinct strings, staying within the transport-level `MaxRequestBodyBytes` cap.
3. Submit repeatedly to `HandleGatewayMessage` / the gateway HTTP or WS endpoint.
4. Observe CPU time in `processTrigger`'s nested loop scaling with `len(triggers) × len(topics)`, delaying handling of other gateway messages on that node — verifiable via a Go benchmark/unit test instantiating `triggerConnectorHandler` with several registered triggers and a large `Topics` slice, measuring wall-clock time of `processTrigger`.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
