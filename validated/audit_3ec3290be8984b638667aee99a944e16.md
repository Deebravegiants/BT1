### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body, never the headers. This breaks the identity binding `hmac(shop, body) == verified(shop, body)` down to `hmac(body) == verified(body)`, so an attacker who can produce any body/HMAC pair signed with the app's shared `client_secret` can attach an arbitrary `shop-domain` header and have it accepted as authentic.

### Finding Description
The webhook processing pipeline is:
1. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop` to build `WebhookMetadata`: [1](#0-0) 

2. `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` only: [2](#0-1) 

3. For `Webhooks::Request`, `to_signable_string` returns solely the raw request body — the `shop` attribute (read from the `shopify-shop-domain` header) is completely excluded from what is signed: [3](#0-2) 

By contrast, in the OAuth flow the analogous `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, showing the gem's own pattern for correctly binding the tenant identifier to the signature: [4](#0-3) 

Because Shopify apps use one `client_secret` shared across every installed shop, any merchant who has installed the app receives real, validly-signed webhooks (body + HMAC) from Shopify. That merchant can capture a body/HMAC pair from their own shop and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (it only checks the body against the same shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` equals the attacker-controlled value: [5](#0-4) 

Host applications built on this gem are expected to use `data.shop` from `WebhookMetadata` as the tenant key (e.g., to look up the victim's session/access token and act on their data), so this identity binding failure allows cross-tenant impersonation of webhook events.

### Impact Explanation
This falls under "Critical - cross-tenant access": an authenticated app installer can forge a webhook that the gem accepts as belonging to a different, victim shop, because the shop identity is verified independently of (and disconnected from) the cryptographic signature that supposedly authenticates the whole request. Any host application logic that trusts `WebhookMetadata#shop` post-`HmacValidator.validate` (which is the documented, intended usage pattern of this gem) is exposed to cross-tenant data corruption or disclosure.

### Likelihood Explanation
Likelihood is elevated because the only prerequisite is installing the target app as any shop (a normal, unprivileged, internet-accessible action) and capturing one legitimate webhook body/HMAC pair — both are gem's documented and reachable code paths. The `hmac-sha256` used to authenticate is computed with the app's single shared `client_secret`, valid across all tenants, so no per-shop secret needs to be broken; only the header, which is unauthenticated, needs to be swapped.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`, `api-version`) values in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the shop-domain header to the signature (e.g., verify that the `shop` header for the current request matches an expected/registered shop before trusting it), matching the approach already used for `AuthQuery#to_signable_string`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a real webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(client_secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the same body `B` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body: [6](#0-5) 
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` (matching, since body `B` is unchanged) and returns `true`, ignoring the forged shop header entirely: [7](#0-6) 
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` as if it were an authentic webhook from the victim, despite the shop value never being part of the verified signature.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
