### Title
Shared `CallDispatcher` allows a permissionless order/bridge calldata to plant a persistent ERC20 approval that later drains any token balance the dispatcher legitimately holds - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` blindly forwards attacker-supplied `Call[]` arrays with `to.call{value}(data)` [1](#0-0) . This single `CallDispatcher` instance is intentionally shared across multiple apps and multiple orders — `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` all configure the same deployed `CallDispatcher` address [2](#0-1) , and documentation explicitly instructs reusing "existing `CallDispatcher` deployments" rather than deploying a fresh one per app [3](#0-2) . Because ERC20 `approve()` calls executed through this dispatcher persist indefinitely on-chain (unlike the transient token custody the dispatcher is designed for), any unprivileged user can submit an `IntentGatewayV2` order whose `predispatch.call` or `output.call` contains `token.approve(attackerSpender, type(uint256).max)` targeting the dispatcher itself. This is fully permissionless — `placeOrder` accepts arbitrary `predispatch.call`/`output.call` from any caller [4](#0-3) , and `_execute` forwards `order.output.call` straight into `ICallDispatcher(dispatcher).dispatch(...)` [5](#0-4) .

### Finding Description
The maintainers themselves flag the danger in the docs: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [6](#0-5)  — but this is advisory only; nothing in `CallDispatcher.sol` enforces exact-amount approvals or resets allowances after execution.

Because the same `CallDispatcher` address is reused across:
1. `IntentGatewayV2` predispatch/postdispatch calldata (`order.predispatch.call`, `order.output.call`), fully attacker-controlled per order [7](#0-6) , and demonstrated in tests using `approve(..., type(uint256).max)` [8](#0-7) 
2. `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept`, which mints/unlocks bridged tokens directly to the `CallDispatcher` address and then forwards attacker-influenced `data` to it [9](#0-8) 

an attacker can, in one cheap self-authored order, plant an unlimited approval from the shared `CallDispatcher` to an address they control for a specific ERC20 token. That approval is a persistent piece of on-chain state and outlives the transaction that created it. Any later, completely unrelated legitimate transaction that causes that same ERC20 token to transiently sit in the `CallDispatcher` (e.g., another user's intent predispatch/postdispatch swap routing that token through the dispatcher for a swap-then-sweep, per `_execute`'s sweep logic [10](#0-9) , or an HFT/WrappedHFT calldata-execution mint that sends the token `to` the dispatcher before the calldata spends it [11](#0-10) ) exposes those balances to the attacker's pre-planted approval. The attacker can then call `transferFrom(dispatcher, attacker, amount)` to steal the funds, exactly mirroring Spectra's root cause: an arbitrary-call router that lets an attacker drain "all tokens approved by the contract."

### Impact Explanation
This is a direct, permissionless path to theft of third-party user funds routed through the shared `CallDispatcher` — any token balance that legitimately transits the dispatcher for any app sharing that deployment (intents, HFT, WrappedHFT) is at risk once an attacker has planted an approval for that specific token. Given `CallDispatcher` deployments are explicitly meant to be reused/shared across apps, the blast radius covers every app on that chain configured with the same dispatcher.

### Likelihood Explanation
Likelihood is high: planting the malicious approval costs only the gas for one `placeOrder`/bridge call with attacker-chosen predispatch/postdispatch calldata — no special privilege, no timing precision, and no cooperation from other users is required. The attacker only needs to wait for any subsequent legitimate flow to route the targeted ERC20 through the same dispatcher, which is a normal, expected usage pattern (swap-then-sweep, calldata-triggered mint-and-swap).

### Recommendation
Do not allow persistent ERC20 approvals to survive a `CallDispatcher.dispatch()` call: after executing the `Call[]` batch, iterate over any tokens approved during the batch (or restrict `Call[]` semantics to disallow `approve` to non-zero, non-reset amounts) and force-reset allowances to zero. Alternatively, deploy a fresh, single-use `CallDispatcher` (e.g., via `CREATE2`/minimal proxy) per dispatched message/order rather than reusing one long-lived shared instance, so no state (including approvals) can persist across unrelated calls.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `predispatch.call` (or `output.call`) encoding a single `Call{ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attackerContract, type(uint256).max) }`, per the pattern already used in `testPostdispatchTokenSweep` [8](#0-7) . This routes through `CallDispatcher.dispatch` [1](#0-0) , granting `attackerContract` unlimited USDC allowance on the shared dispatcher.
2. Wait for any other user's order or HFT bridge transfer that routes USDC through the same `CallDispatcher` (e.g., another `testPostdispatchTokenSweep`-style flow, or an HFT calldata-execution mint targeting the dispatcher as `to` [12](#0-11) ).
3. As soon as USDC balance is nonzero on the dispatcher, `attackerContract` calls `USDC.transferFrom(dispatcher, attacker, balance)`, draining the victim's in-transit funds using the persistent approval set in step 1.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
