## Title
Webhook shop-domain (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an inbound webhook by validating only the HMAC of the raw request **body**. The `shop-domain` (as well as `topic`, `webhook-id`, and `api-version`) headers are read directly from the unauthenticated HTTP headers and are never included in the signed payload. Any entity that legitimately receives one valid `(body, hmac)` pair from Shopify (e.g. a merchant who has installed the app) can resend that exact body/hmac pair while substituting a different `shop-domain` header, and the gem will accept it as an authentic webhook for the spoofed shop.

### Finding Description
The identity binding that should hold is:

`shop attributed to the webhook by the handler == shop that Shopify actually signed the request for`

Instead, the gem breaks this binding: **bytes verified (`hmac` over `@raw_body`) != identity fields acted on (`shop`, `topic`, `webhook_id`)**.

`Request#hmac` and `Request#to_signable_string` show that only the raw body participates in signature verification: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` (used identically for both OAuth callbacks and webhooks) simply recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field — for webhooks this is the raw body only: [3](#0-2) 

`Registry.process` performs exactly this body-only HMAC check, then dispatches the handler using the **unauthenticated** `request.shop`, `request.topic`, and `request.webhook_id` as the tenant/identity context for the payload: [4](#0-3) 

Because `Context.api_secret_key` is a single, global secret for the whole app (not per-shop), the same secret validates webhooks for every merchant that has installed the app. Consequently, a `(raw_body, hmac)` pair that Shopify legitimately generated for shop A's webhook remains **cryptographically valid** even when replayed with the `shopify-shop-domain` header changed to shop B. The gem has no mechanism to detect this because the shop identifier was never part of what was signed.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce (cross-tenant access). Any consuming application that trusts `WebhookMetadata#shop` (as returned by `Registry.process`) to select which merchant's records to create/update/delete — the intended and documented use of this field — can be made to apply another shop's genuine, signature-valid webhook body under an attacker-chosen shop identity. Depending on the topic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, orders/product webhooks), this can lead to a victim merchant's data being mutated, deleted, or misattributed using content that was never actually sent for that merchant — a cross-tenant integrity/access violation rooted entirely in this gem's signature verification design.

### Likelihood Explanation
Any user who can legitimately install the app on a shop they control (a normal, unprivileged interaction, no leaked secrets or elevated access required) automatically receives real webhooks with valid `(body, hmac)` pairs for that shop. They can immediately capture and replay one of those requests against the app's public webhook endpoint with a forged `shopify-shop-domain` header. No knowledge of `Context.api_secret_key` is needed since the header is never covered by the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed/verifiable content, or otherwise cryptographically bind them, before trusting `request.shop` for tenant routing. At minimum, `HmacValidator`/`Request` should be extended so that `to_signable_string` incorporates the `shopify-shop-domain` header (and other identity-bearing headers) alongside the body, and `Registry.process` should reject webhooks whose header-derived shop cannot be tied to the signed payload — analogous to how `AuthQuery#to_signable_string` already includes `shop` in its signed parameters for OAuth callbacks.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop "attacker-shop.myshopify.com"
# and receives one legitimate webhook from Shopify, e.g.:
raw_body = '{"id":123,"note":"legit content for attacker-shop"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Step 2: Attacker replays the exact same body+hmac to the app's webhook
# endpoint, but swaps the shop-domain header to the victim shop.
forged_headers = {
  "shopify-topic" => "orders/updated",
  "shopify-hmac-sha256" => valid_hmac,          # still valid: HMAC only covers raw_body
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "shopify-webhook-id" => "any-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: Registry.process accepts it — HMAC validation passes because it only checks raw_body.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though Shopify never signed anything for victim-shop.
``` [5](#0-4)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
