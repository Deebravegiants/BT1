### Title
Webhook HMAC validation does not bind the `shop-domain` (or `topic`/`webhook-id`) header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the shop identity (`shop-domain` header) that the rest of the library treats as authoritative is read from an unsigned HTTP header. Any actor who can obtain one genuine `(body, hmac)` pair issued by Shopify for the app (e.g., because they operate a shop that has the app installed and thus legitimately receives signed webhooks) can resubmit that same body/HMAC pair to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator` will report the request as valid, and `Webhooks::Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field is the attacker-chosen value, not the value that was actually signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled straight from HTTP headers, none of which are covered by that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the received HMAC: [3](#0-2) 

`Registry.process` trusts this validation and then forwards the unauthenticated `request.shop` value straight into the handler as the tenant identity: [4](#0-3) 

The identity binding the library implicitly claims to enforce is:
`HMAC_valid(body) == true` implies `shop header == shop that Shopify actually signed for`

In reality the equality that holds is only `HMAC(secret, body) == received_hmac`; the `shop-domain` header is never an input to that computation, so it can be swapped freely by anyone who can replay a validly-signed body. This is the same class of bug as the report's oracle scenario: a value the code treats as fully verified (the dAPI median / here, the shop that "owns" the webhook) is actually only partially anchored by the cryptographic check, letting a single unprivileged party skew the attributed identity within the range the check doesn't cover.

### Impact Explanation
A merchant/attacker who installs the app on their own shop legitimately receives real, correctly-signed webhooks (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`) for their own shop. Because the HMAC never covers the `shop-domain` header, that attacker can replay the exact same signed body to the app's webhook receiver while substituting a victim shop's domain in the header. Any host application built on this gem's documented API (`Webhooks::Registry.process`) that uses `WebhookMetadata#shop` to key its per-tenant data (uninstall handling, GDPR data requests, order records, billing state, etc.) will process the payload as though it originated from the victim shop — a cross-tenant data confusion/corruption primitive achieved without ever possessing the victim's credentials or the app's secret.

### Likelihood Explanation
Any developer/merchant who can install the target app on a shop they control automatically gains a stream of validly-signed webhook bodies and can immediately attempt header spoofing against the shared endpoint; no secret leakage, TLS interception, or privileged access is required — only the ability to send an HTTP request with a modified header, which fits squarely within the "unprivileged internet user" threat model in scope.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) header values in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed body (e.g., verify it against a shop the app already knows is associated with that specific webhook/body, or require it to be re-derived from data inside the signed body rather than from a header) before exposing it via `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives a real webhook, capturing the raw body `B` and the valid header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(app_secret, B)`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(app_secret, B) == H`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though Shopify never signed anything for `victim-shop.myshopify.com`.
