### Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC verification exclusively to the raw request body, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop-domain` header to decide which tenant a webhook belongs to. Because the header is never included in the signed material, a valid `(body, hmac)` pair produced for one shop can be replayed with a different `shop-domain` header and will still pass verification, letting an attacker attribute a webhook to a victim shop.

### Finding Description
`Registry.process` authenticates a webhook solely via:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC(client_secret, verifiable_query.to_signable_string)` and compares it to the `hmac` supplied in the request: [2](#0-1) 

For webhooks, `to_signable_string` is defined to return only the raw body bytes:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

The `shop` value, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

Once the HMAC check passes, `Registry.process` forwards this untrusted `shop` value directly to the host application's handler:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

The broken identity binding is:
```
HMAC_valid(body) == true  ⇏  shop_header == shop_that_actually_produced(body)
```
The gem's own documentation instructs host apps to key their per-tenant work off `data.shop` directly from the `WebhookMetadata` returned by `process`, treating it as authenticated: [6](#0-5) 

Since `client_secret` (the HMAC key) is shared across *all* shops installing a given app, any unprivileged attacker who installs the app on their own shop can obtain a legitimately-signed `(raw_body, hmac)` pair for a webhook they control (e.g. a `shop/redact` or `products/update` payload with body content they influence, or simply any generic-content webhook), then replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed because it never inspects the header, and `Registry.process` will hand the forged `shop` to the handler as if it came from Shopify for that victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: an attacker can make the host application believe a Shopify-originated, HMAC-verified webhook event came from an arbitrary victim shop instead of the shop that actually generated the body. Depending on how the host app uses `data.shop` (e.g., to look up the tenant's session/access token, to write records against the tenant's data model, or to trigger tenant-scoped side effects such as GDPR redaction), this enables cross-tenant data corruption or spoofed tenant-scoped actions, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
No credentials, TLS interception, or privileged access are required — only the ability to install the target app on an attacker-controlled shop (a normal, unprivileged action any merchant can take) in order to harvest one valid `(body, hmac)` pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a modified header. The vulnerable code path (`Request#to_signable_string`, `Registry.process`) is exercised on every inbound webhook, and the mismatch between the signed content (body only) and the trusted-but-unsigned header (`shop-domain`) is deterministic and always reachable.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signed material, or independently verify that the `shop-domain` header matches a shop actually associated with the delivered payload before trusting it in `WebhookMetadata`. At minimum, document/require host apps not to trust `data.shop` without corroborating it against known installed shops, but the safer fix is architectural: bind the header into `to_signable_string`, matching Shopify’s documented HMAC scheme, or validate the `shop-domain` against the app's own store of shops with active webhook subscriptions before dispatch.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app,
# so they can receive a legitimately Shopify-signed webhook for their own shop.

raw_body = '{}'  # attacker-controlled/observed body content
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key,  # the app's shared client_secret
  raw_body,
)

# Attacker replays the same (body, hmac) but swaps the shop-domain header
forged_headers = {
  "shopify-topic"        => "shop/redact",
  "shopify-hmac-sha256"  => Base64.encode64(valid_hmac),
  "shopify-shop-domain"  => "victim-shop.myshopify.com", # unauthenticated, attacker-chosen
  "shopify-webhook-id"   => "attacker-chosen-id",
  "shopify-api-version"  => "2024-01",
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate only checks HMAC(secret, raw_body) == valid_hmac -> true
# Registry.process happily dispatches with data.shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(forged_request)
```
Because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) never incorporates the `shop-domain` header, this request passes `Utils::HmacValidator.validate` and is dispatched to the registered handler with an attacker-controlled `shop`, as also demonstrated by the existing test helper pattern in [7](#0-6) , which shows how trivially a `(raw_body, hmac)` pair combined with arbitrary header values is accepted by `Registry.process`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
