## Analysis Result

The go-f3 bug class (cached verification results reused across a different message context than the one they were validated for) does have a concrete analog in this codebase's HTTP outbound-request response cache.

### Title
Cross-workflow HTTP response cache key omits `WorkflowID`, allowing cached response reuse across different workflow contexts - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The gateway's `responseCache` for outbound HTTP action requests keys cached entries by `req.Hash()`, and the codebase's own test suite documents that this hash deliberately excludes `WorkflowID` and `CacheSettings` while including only method/URL/headers/body/`WorkflowOwner`.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` key the cache purely on `req.Hash()`: [1](#0-0) . `response_cache_test.go` explicitly asserts that two requests with different `WorkflowID` produce the *same* hash ("Hash should be the same regardless of WorkflowID") [2](#0-1) , and that different `CacheSettings` (`MaxAgeMs`/`Store`) also collapse to the same hash [3](#0-2) . Only `WorkflowOwner` differentiates the key [4](#0-3) .

This is directly analogous to the go-f3 issue: a value is cached/validated once in one context (one workflow's request, with its own `CacheSettings`), and then transparently reused in a *different* context (a different workflow belonging to the same owner, or a request that itself set `Store:false`/`MaxAgeMs:0`) because the cache key does not bind the cached entry to that context. The call site `makeOutgoingRequest` reads `req.CacheSettings.MaxAgeMs`/`Store` per-request to decide whether to read/write the shared cache [5](#0-4) , but the underlying cache entry is shared across any request producing the same `Hash()`, regardless of which workflow or per-request cache policy created it.

The package doc comment itself is inconsistent with the actual behavior — it states the key is "a hash of the request (method, URL, headers, body, workflowOwner)" [6](#0-5) , i.e. workflow-ID is knowingly omitted, while the project's own `README.md` separately claims "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [7](#0-6)  — a claim the code and tests contradict.

### Impact Explanation
Because the cache is scoped only to `WorkflowOwner` (not per-workflow, and not per-`CacheSettings`), one workflow belonging to an owner can populate the shared cache entry (via `Store:true`) for a given method/URL/headers/body combination, and a second, unrelated workflow under the same owner that issues a structurally-identical outbound request (even with `Store:false` or a different `MaxAgeMs`) will silently receive that cached response instead of making its own fresh HTTP call. This breaks the isolation the README claims exists between workflows and allows one workflow's cached HTTP action result to leak into another workflow's execution — a cross-workflow response-confusion analogous to the justification being replayed into an unintended context in go-f3.

### Likelihood Explanation
This requires an owner running (or an attacker controlling) two workflows under the same `WorkflowOwner` where request shapes (method, URL, headers, body) coincide, which is a plausible occurrence for multi-workflow owners using common HTTP endpoints/templates; no special network-layer or malicious-peer capability is needed, only ordinary workflow submission through the gateway's HTTP action path (`gatewayHandler.makeOutgoingRequest`).

### Recommendation
Include `WorkflowID` (and ideally the relevant `CacheSettings` fields, since `Store`/`MaxAgeMs` change the caching contract for that specific call) in the cache key computation used by `req.Hash()`, or otherwise namespace the `responseCache` map by `WorkflowID` in addition to `WorkflowOwner`, so a cached entry can only be read back by the same logical workflow/request context that produced it. Align the package documentation and README with the corrected, enforced scoping.

### Proof of Concept
1. Workflow `A` (owner `0xabc`) issues an HTTP action request to `https://svc.example.com/data` with `CacheSettings{Store: true, MaxAgeMs: 600000}`; the gateway fetches and stores the response keyed by `Hash()` (method+URL+headers+body+owner) [5](#0-4) .
2. Workflow `B` (different `WorkflowID`, same owner `0xabc`) issues a structurally identical request to the same URL, method, headers, and body, with its own `CacheSettings{MaxAgeMs: 600000}` (or even `Store:false`).
3. Because `Hash()` ignores `WorkflowID` and `CacheSettings` [8](#0-7) , `responseCache.Fetch` returns workflow A's cached response to workflow B without performing a new HTTP call, demonstrating cross-workflow cache reuse.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

## 3. HTTP Action Message Handling

### 3.1 Process Flow

1. **Request Reception**: Gateway receives HTTP action request from a workflow node
2. **Rate Limiting**: Validates node rate limits
3. **Request Parsing**: Extracts `OutboundHTTPRequest` from the JSON-RPC message
4. **Cache Check**: Determines if request should use cached response or fetch fresh data
5. **HTTP Execution**: Makes actual HTTP request to external endpoint
6. **Response Caching**: Stores cacheable responses (2xx, 4xx status codes) only if `CacheSettings.Store` is `true`
7. **Node Response**: Sends HTTP response back to requesting node

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
