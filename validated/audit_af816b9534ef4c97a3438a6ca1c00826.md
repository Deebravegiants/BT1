The report exposes a real identity-binding gap in the webhook processing path.

### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  , while the `shop`, `topic`, and `webhook_id` values are read directly from HTTP headers that are never included in the signable string [2](#0-1) . `Registry.process` validates the HMAC and then dispatches the handler using these unauthenticated header values [3](#0-2) . This is the same bug class as the report: an identity field (`shop`) that is acted upon (used to build `WebhookMetadata` and route the event) is not covered by the cryptographic check (the HMAC), so the two can be mismatched by an attacker.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` are parsed straight from headers with no cryptographic linkage to the body or to each other [2](#0-1) .

Crucially, the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not shop-specific. Any shop that installs the app is a legitimate, unprivileged recipient of real, validly-signed webhooks for its own store (e.g. `orders/create` with an empty or attacker-controlled-shape body, or a mandatory-topic webhook like `customers/data_request`). Because the signature only binds the body, an attacker who controls one installed shop can:
1. Trigger (or simply receive) a legitimate webhook for their own shop, capturing `raw_body` and its valid `hmac`.
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` and/or `topic` headers to claim it originated from a different (victim) shop or a different event type.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the secret [5](#0-4) .
4. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the forged headers and invokes the app's registered handler as if the event genuinely came from the victim shop/topic [6](#0-5) .

This breaks the binding "shop authenticated (by valid HMAC) == shop acted upon (`request.shop` passed to the handler)". The gem treats a validly-signed body as proof of shop/topic identity, when in fact those fields travel outside the signed material.

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged attacker who is a legitimate (even free/trial) installer of the app can cause the app's own webhook-handling logic to execute against a different, victim shop identifier and/or trigger unintended topic handlers (including mandatory topics such as `customers/data_request`, `customers/redact`, `shop/redact`), without ever needing the app's `client_secret`. Depending on what the app does inside `handler.handle` (e.g. writing to the victim shop's records, triggering data exports/deletions keyed by the spoofed `shop` field), this can result in cross-tenant data corruption or disclosure — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High: exploitation requires only (a) being an installer of the target app on any shop (readily available to any unprivileged internet user who installs a public app), and (b) the ability to POST directly to the app's public webhook endpoint with forged headers and a captured/replayed body+HMAC pair — no access to `api_secret_key`, tokens, or the victim's credentials is required. The complexity is in obtaining a body whose content is useful/predictable (e.g., empty-body topics or known JSON shapes), which is feasible for several standard Shopify webhook topics.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC-verified payload:
- Include `shop`, `topic`, and `webhook_id` (in canonical form) in `to_signable_string` so the HMAC covers them, or
- Verify server-side that the `shop` header corresponds to a shop with an active, matching webhook subscription/session before dispatching, rather than trusting the header value directly, or
- At minimum, document/enforce that consumers of `WebhookMetadata#shop` must not treat it as authenticated beyond "some shop signed with this app's secret" and re-validate shop identity via an independent trusted channel (e.g., cross-check against the session store) before performing any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) any real webhook delivery to their own shop, e.g. a `carts/update` event, and captures the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because Shopify computed it with the shared app secret).
3. Attacker sends a new POST request directly to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: customers/data_request`.
4. `ShopifyAPI::Webhooks::Request.new` parses these forged headers [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `B` [5](#0-4) .
5. The registered handler for `customers/data_request` (or whichever topic was forged) is invoked with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to act as though the victim shop sent this event.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
