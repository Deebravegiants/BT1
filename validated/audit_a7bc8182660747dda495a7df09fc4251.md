### Title
Webhook `shop-domain` (and `topic`) header is not covered by the HMAC signature, allowing shop spoofing on replayed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight to the app's handler as the tenant identifier. The `shop`, `topic`, `api-version`, and `webhook-id` values are never included in the HMAC-signed material, so they can be freely modified without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/verifies the HMAC purely against that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient authorization to hand the request, including `request.shop`, to the topic handler: [3](#0-2) 

`request.shop` is read directly from the `shop-domain` HTTP header with no cross-check against the signed body: [4](#0-3) 

The binding that is broken: the gem authenticates `HMAC(body)` but acts on `shop-domain header` as the tenant identity — i.e. it verifies `HMAC == HMAC(body)` but trusts `shop == header["shop-domain"]` without that header being part of the signed material. This is precisely the "field acted on but not covered by the HMAC" class from the report (an analog of the VUSD zero-amount field that bypasses a check meant to bind state).

By contrast, the OAuth callback in this same gem does this correctly — `AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, and `timestamp` in the signed payload, so the shop identity used later cannot be swapped without invalidating the HMAC: [5](#0-4) 

That is the correct pattern the webhook path fails to follow.

### Impact Explanation
Any party who can obtain one genuine, correctly-HMAC'd webhook delivery for a shop where the app is installed (e.g. a merchant installing the vulnerable app on their own store and capturing/replaying the HTTP request to the app's webhook endpoint) can resend that exact body with an altered `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) header. Because the HMAC only covers the raw body, the forged headers pass `Utils::HmacValidator.validate` unchanged, and `Registry.process` forwards the attacker-chosen `shop` value to the host application's handler as if it were an authenticated webhook from that shop. If the host application uses `WebhookMetadata#shop` to select which tenant's data/session to act on (the intended and documented use, per `docs/usage/webhooks.md`), this enables cross-tenant confusion: actions or data intended for one merchant can be attributed to, or triggered against, a different merchant's tenant context, without possession of that merchant's access token or secret. This satisfies the "cross-tenant access" High/Critical impact bucket in scope.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (or otherwise obtain one valid webhook delivery) and replay it to the app's public webhook endpoint with modified headers — no access token, `api_secret_key`, or privileged access is needed. This is a realistic and low-cost attack path, limited only by the host app's use of `data.shop` to key tenant lookups (which is the gem's documented pattern), not by anything the gem itself enforces.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material used by `Utils::HmacValidator`, or otherwise cryptographically bind them to the body before verification, so that any modification to `shop-domain` invalidates the signature — mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`. At minimum, document that the `shop` field on `Webhooks::Request`/`WebhookMetadata` is not authenticated and must not be trusted as a tenant identity by consuming applications without an additional authenticated source (e.g., cross-referencing against a stored, session-bound shop).

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a correct `x-shopify-hmac-sha256` computed as `HMAC_SHA256(secret, B)`.
2. Attacker captures this HTTP request and resends it to the same endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (body `B` and the HMAC header are left untouched).
3. `ShopifyAPI::Webhooks::Request.new` parses the modified headers; `to_signable_string` still returns body `B`.
4. `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(secret, B)` and compares to the untouched HMAC header — validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the request never originated from Shopify on behalf of `victim-shop.myshopify.com`. [3](#0-2) [6](#0-5)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
