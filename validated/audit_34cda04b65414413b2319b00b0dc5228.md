### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, ...)` without ever refunding unspent native tokens to the original caller, permanently locking the difference between `msg.value` and the actual swap cost in the `EvmHost` contract.

### Finding Description
Any unprivileged user or application dispatching a POST/GET request (or funding a pending request) with native token payment supplies `msg.value` and Hyperbridge performs an exact-output swap for the required `feeToken` amount: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `swapETHForExactTokens` is called with the *full* `msg.value`, but only `post.fee` / `get.fee` / `amount` worth of tokens is required. A standard `UniswapV2Router02.swapETHForExactTokens` implementation (and the project's own custom wrapper routers, e.g. `UniV3UniswapV2Wrapper.swapETHForExactTokens` and `UniV4UniswapV2Wrapper.swapETHForExactTokens`) refund unspent ETH to `msg.sender` of that call — but from the router's perspective, `msg.sender` is `EvmHost` itself, not the original transaction sender (`_msgSender()`), since `EvmHost` is the direct caller of the router: [4](#0-3) [5](#0-4) 

As a result, the refund lands as native ETH balance inside `EvmHost`, but `EvmHost.dispatch`/`fundRequest` never forward that refund back to `_msgSender()` — there is no post-swap balance check or `.call{value: refund}` back to the caller in these functions.

This is the exact same bug class flagged in the external report (`_afterAllocate`/`_transferAmountFrom` failing to return `msg.value - amount` to the user), just manifested in Hyperbridge's fee-swap dispatch path.

By contrast, other parts of this same codebase correctly implement this refund pattern (e.g. `IntentGatewayV2` tests explicitly verify excess-ETH refunds on `placeOrder`/`fillOrder`, and `WrappedHyperFungibleToken.send` carefully tracks and forwards only the remainder of `msg.value`), confirming that the protocol's intended behavior is to refund overpayment — but `EvmHost`'s own dispatch/fundRequest functions omit this safeguard.

### Impact Explanation
Any user or integrating application that calls `dispatch()` (POST/GET) or `fundRequest()` with more native token than strictly required for the fee swap (which is the normal case, since callers typically cannot predict the exact optimal swap input and must over-provision `msg.value` to avoid reverts on price slippage) will have the excess amount permanently stuck in the `EvmHost` contract, unrecoverable by them. Given `dispatch()` is the primary unprivileged entry point used by every app built on Hyperbridge (token bridges, intents, LayerZero endpoint, generic messaging apps) that chooses native-token fee payment, this affects a broad and continuously reachable code path, resulting in a permanent loss of user funds — meeting the High severity threshold for freezing/loss of user funds.

### Likelihood Explanation
High likelihood: dispatching with native token payment is a documented, first-class user flow (see `docs/content/developers/evm/messaging/post-requests.mdx`), and precise fee estimation is inherently imprecise (fee quotes can shift between quote-time and execution due to AMM price movement), so users routinely send `msg.value` greater than the exact swap cost to avoid reverts. Every such call results in fund loss with no attacker action required — it's a direct, always-present functional bug rather than an edge case.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, after performing the `swapETHForExactTokens` call, compute the actual ETH spent (or capture the returned `amounts[0]`) and refund `msg.value - spent` back to `_msgSender()` via a low-level call, reverting on failure. Alternatively, require the caller to pre-compute the exact input via `getAmountsIn` and pass it explicitly, or expose a `sweep`/`withdrawExcess` mechanism scoped per-caller (less ideal, since it introduces custody risk). The safest fix mirrors the pattern already used in `IntentGatewayV2` and `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper`: track pre/post balances around the swap and immediately forward any residual ETH back to the transaction's `_msgSender()`.

### Proof of Concept
1. Deploy `EvmHost` configured with a real `UniswapV2Router02` (or the project's `UniV3UniswapV2Wrapper`) as `_hostParams.uniswapV2`.
2. Caller `Alice` invokes `EvmHost.dispatch(DispatchPost{fee: 1e18, ...})` with `msg.value = 5 ether` (over-provisioning to avoid slippage revert), expecting only the ETH-equivalent of `1e18` feeToken to be spent.
3. Internally, `IUniswapV2Router02.swapETHForExactTokens{value: 5 ether}(1e18, path, address(this), block.timestamp)` spends only what's needed (e.g. 0.5 ETH) and refunds the remaining ~4.5 ETH to `msg.sender` of that call, which is `EvmHost`.
4. `EvmHost`'s ETH balance increases by ~4.5 ETH; `dispatch()` returns normally with no error.
5. Alice has no function to reclaim this ~4.5 ETH — `EvmHost.dispatch`/`fundRequest` contain no refund-back-to-caller logic, and there is no public method allowing Alice to recover it, permanently locking her overpayment. This can be verified by adding a Foundry test analogous to the existing `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` in `evm/tests/foundry/IntentGatewayV2Test.sol`, but targeting `EvmHost.dispatch` directly and asserting `msg.sender.balance` after the call — it will show the full 5 ETH deducted, not just the swap cost.
