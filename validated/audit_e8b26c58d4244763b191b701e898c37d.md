### Title
On-chain UTXO commitments minted via `EmporiumUpgradeable.handleOut` can be duplicated across separate `transact` calls, producing two leaves that collapse to one spendable nullifier - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.handleOut` stamps an on-chain-created UTXO with the fully caller-controlled `circomData.timeStamp` and `circomData.stealthAddressStructure`, with no binding to `block.timestamp` or any per-call nonce. Because the output leaf is `hash4(amount, token, stealthAddress, timeStamp)` and the later-computed spending nullifier is a pure function of `(commitment, nullifyingPrivateKey)` with no dependency on tree position, two separate `Hinkal.transact` calls that reproduce the same `(amount, token, stealthAddress, timeStamp)` tuple create two distinct leaves that share exactly one nullifier.

### Finding Description
Equality claimed broken: `hash4(amount, token, stealthAddress, timeStamp)` for deposit #1 == same hash for deposit #2, and therefore `nullifier(commitment, nullifyingPrivateKey)` for leaf #1 == nullifier for leaf #2.

Path traced:
1. `EmporiumUpgradeable.runAction` computes `balanceChange` from attacker-controlled `op.callData`/endpoint (attacker can deploy their own endpoint), then calls `handleOut(balanceChange, circomData, i)` at `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:146,162-184`, which builds `UTXO(amount, token, circomData.stealthAddressStructure, circomData.timeStamp)`. Neither field is checked against `block.timestamp` or any nonce anywhere in `Hinkal.sol`/`HinkalHelper.sol`.
2. Back in `Hinkal.sol:97-146`, when `circomData.onChainCreation[i]` is true, `createOnchainCommitment` (`contracts/HinkalBase.sol:52-70`) computes `commitment = hash4(utxo.amount, token, stealthAddress, utxo.timeStamp)` and it is inserted via `insertMany` (`contracts/Merkle.sol:37-71`) with no dedup check against existing leaves.
3. `HinkalHelper.checkOnchainCreation` (`contracts/HinkalHelper.sol:173-202`) and `HinkalBase.insertNullifiers` (`contracts/HinkalBase.sol:135-151`) explicitly *skip* nullifier logic entirely for `onChainCreation[i]==true` — no nullifier is created or checked at deposit time, only at future spend time.
4. When later spent as an input UTXO in `MainEVMCircuit`, the nullifier is `Poseidon2(commitment, Poseidon2(nullifyingPrivateKey, commitment))` (`circuits/Signature.circom:1-14`, `circuits/NullifierCalculator.circom:1-19`) — a function of only `commitment` and the spender's private key, never of the leaf's Merkle index/siblings. Two identical commitments owned by the same stealth-address key thus yield the identical nullifier value.
5. `insertNullifiers` marks `nullifiers[value] = true` on first spend (`contracts/HinkalBase.sol:143-147`). Any later attempt (same tx or a future tx) to spend the second identical leaf recomputes the same nullifier and reverts with `"Nullifier cannot be reused"`, permanently stranding that leaf's value.

Root cause: `EmporiumUpgradeable.handleOut` has no protection against the caller repeating the same `(amount, stealthAddress, timeStamp)` tuple across two separate `transact` calls — contrast with `DepositOnChainUtxosExternalAction.sol:70`, which explicitly offsets `timeStamp + utxoIndex` per UTXO within a single batch to avoid exactly this collision, but that protection does not extend across separate external calls/transactions, and Emporium has no analogous protection at all.

Existing guards checked and found insufficient: `performHinkalChecks`/`dimensionsCheck` only validate array-length/structural invariants, not cross-transaction uniqueness of `timeStamp`; `checkOnchainCreation` only forces `amountChanges[i]==0` and `inputNullifiers[i][j]==0` for onChainCreation branches, it does not touch `timeStamp` or dedupe commitments; `rootHashExists`/proof verification only bind circuit-declared outputs for that single proof, they cannot see across separate proofs/transactions; `insertMany`/`insertCommitments` never check for duplicate leaf values.

### Impact Explanation
Category: Critical — permanent freezing of user funds via a leaf/nullifier collision, matching the rubric's "permanent freezing" and "double spend"-adjacent class explicitly listed as Critical. In the minimal case the attacker only freezes their own second deposit, but since `stealthAddressStructure` and `timeStamp` are attacker-chosen values that need not correspond to actual randomness, an attacker who can predict/observe a victim's forthcoming deposit parameters (e.g., a service or wallet that derives `timeStamp`/stealth address deterministically) can front-run with a matching Emporium deposit to make the victim's future leaf permanently unspendable once either leaf's shared nullifier is consumed. Repeatable per pair of colliding deposits; each pair costs one wasted deposit's worth of Emporium round-trip gas plus the frozen value of the second leaf.

### Likelihood Explanation
Preconditions: attacker must control both the Emporium `op.callData`/endpoint (trivial — attacker deploys their own endpoint) to reproduce an identical `balanceChange`, and must supply identical `circomData.timeStamp` and `circomData.stealthAddressStructure` across two `transact` calls — both are plain calldata fields with no on-chain freshness check. No privileged role, whitelisted relay, or victim cooperation required. Feasible with a simple Foundry test using two `Hinkal.transact` calls through Emporium with matched calldata. Fully attacker-controlled and repeatable at will for self-inflicted freezing; requires prediction of victim parameters for a victim-targeted variant.

### Recommendation
Bind the on-chain-created UTXO's `timeStamp` (and/or the commitment) to a value the caller cannot arbitrarily repeat, e.g., derive it from `block.timestamp` combined with a monotonically increasing on-chain nonce/leaf index (similar to `DepositOnChainUtxosExternalAction`'s `timeStamp + utxoIndex` pattern, but extended to be globally unique across calls, e.g., incorporate `m_index`), or explicitly reject insertion of a leaf value that already exists in the tree/leaf-set before calling `insertMany`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a test ERC20, and a trivial "PassThrough" endpoint contract the attacker deploys that just no-ops or transfers a fixed amount to the Emporium contract when called.
2. Craft `CircomData` #1 and a valid proof for an Emporium `transact` call with `externalActionMetadata` encoding an `EmporiumStack` whose single op calls the PassThrough endpoint to move exactly `1000` tokens into Emporium, `circomData.timeStamp = T`, `circomData.stealthAddressStructure = S` (attacker's own), `onChainCreation[0] = true`. Call `Hinkal.transact`; capture emitted `NewCommitment(commitment1, index1, ...)`.
3. Craft `CircomData` #2 identical in every field that feeds `hash4` (`amount=1000`, `token`, `S`, `T`), but via a differently-encoded `op.callData`/endpoint interaction that nets the same `balanceChange`. Call `Hinkal.transact` again; assert `NewCommitment` emits `commitment2 == commitment1` at a different tree index (`index2 != index1`).
4. Generate a spend proof for leaf #1 using the real `nullifyingPrivateKey` for `S`; submit `transact` to spend it — assert success and `Nullified(nullifierX)`.
5. Generate a spend proof for leaf #2 (same commitment, same key) — assert the computed nullifier equals `nullifierX`, and that submitting it reverts with `"Nullifier cannot be reused"`, proving leaf #2's value is now permanently unspendable.     function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }

include "../../node_modules/circomlib/circuits/comparators.circom";

template NullifierCalculator() {
  signal input commitment;
  signal input signature;
  signal output out;

  component calcOriginalNullifier = Poseidon(2);
  calcOriginalNullifier.inputs[0] <== commitment;
  calcOriginalNullifier.inputs[1] <== signature;

  component calcCommitmentIsZero = IsZero();
  calcCommitmentIsZero.in <== commitment;

  out <== calcOriginalNullifier.out * (1 - calcCommitmentIsZero.out);
}
