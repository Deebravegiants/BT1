### Title
Webhook shop identity is not cryptographically bound to the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an unauthenticated header. Because the `shop` identity is never included in the signed material, an attacker who owns a legitimate installation of the app (an "unprivileged" merchant who installed the app on their own store) can capture one of their own genuinely-signed webhook deliveries and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, without invalidating the HMAC.

### Finding Description
`Registry.process` validates the webhook using only the body-derived HMAC: [1](#0-0) 

```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `to_signable_string`, which for a webhook `Request` is just the raw body — the `shop` value is not part of the signed data at all: [2](#0-1) [3](#0-2) 

The identity binding that should hold is:
`shop asserted in X-Shopify-Shop-Domain header == shop cryptographically committed inside the HMAC-signed payload`

That binding does not exist. The HMAC only proves "this body byte-string was signed with the app secret" — it says nothing about which shop the body/event belongs to. `request.shop` is read straight from an attacker-controllable HTTP header and passed unchecked into `WebhookMetadata`, which the host application's handler uses to key data storage/business logic per tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: bytes verified (`raw_body` HMAC) are not the bytes that determine tenant identity (`shop` header). An attacker who has installed the app on their own store (unprivileged, no special access needed) can:
1. Trigger a webhook delivery to their own store (e.g. update a product/customer field with attacker-chosen content), receiving a validly-HMAC-signed request.
2. Replay that exact body/HMAC to the app's public webhook endpoint, substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain.
3. `Utils::HmacValidator.validate` still passes because it never inspected the shop header, and the handler runs with `shop` set to the victim's domain and attacker-controlled body content.

Depending on how the host app's registered handler uses `WebhookMetadata#shop` (virtually all real integrations use it to select/write per-tenant records), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" high/critical impact bucket.

### Likelihood Explanation
Any developer that installs the app on a shop they control can produce a validly-signed webhook body at will (by performing normal actions in their own store) and then replay it with a modified shop header using ordinary HTTP tooling; no access to `api_secret_key`, TLS interception, or privileged accounts is required. The only requirement is that the app expose a webhook endpoint that calls `Registry.process`, which is the SDK's own documented usage pattern.

### Recommendation
Bind the shop identity into the HMAC-verified material (e.g. require the `WebhookHandler`/host app to compare `request.shop` against the shop of the currently active/looked-up session before trusting it, or extend `to_signable_string`/validation flow to fail closed when the header shop cannot be corroborated against an app-known installed shop). At minimum, document explicitly and loudly that `request.shop` is unauthenticated header data and must never be trusted for tenant selection without an independent installed-shop lookup.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" with the app installed.
# Step 1: attacker triggers a webhook on their own shop, capturing raw body + valid HMAC.
raw_body = '{"id":123,"title":"pwned"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Step 2: attacker replays it against the app's webhook endpoint, spoofing the shop header.
headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
  "x-shopify-webhook-id" => "attacker-controlled",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (it only checks raw_body), handler runs with
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON)
```
