### Title
Webhook shop-domain header not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` identifier that is handed to the host application's webhook handler as the tenant key comes from an HTTP header that is never included in the signed content. Because Shopify apps share a single `api_secret_key` across every shop that installs them, any merchant who installs the app can generate a genuine `(body, hmac)` pair for their own store and replay it with a forged `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled webhook data as if it originated from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e. it only ever signs/verifies the body — and then immediately builds `WebhookMetadata` using the unverified `request.shop`, which is passed to the app-supplied handler as the trusted tenant identifier: [3](#0-2) [4](#0-3) 

This is the exact identity-binding break called out in the report's rules: a field (`shop`) is *acted on* (used as the tenant key by the handler) but is *not covered by the HMAC* that authenticates the request. The gem's own documentation instructs host apps to key their per-tenant processing off this same unauthenticated field: [5](#0-4) 

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any unprivileged merchant/attacker can:
1. Install the target app on their own (attacker-owned) shop.
2. Trigger a real webhook delivery for a topic the app has registered (e.g. `orders/create`), giving them a genuine `raw_body` and a matching, Shopify-computed `X-Shopify-Hmac-Sha256` value.
3. Replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to a victim shop's domain.

`Utils::HmacValidator.validate` will still pass (it only checks the body against the shared secret), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the body content is entirely attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: `shop` is the field host applications use to attribute webhook data and often to look up per-shop credentials/sessions, per the gem's own documented usage. An attacker can forge cross-tenant events — e.g. injecting fabricated data attributed to a victim shop, or corrupting a victim shop's downstream processing (order/customer records, GDPR `customers/redact` payloads, etc.) — without ever needing the victim's credentials. This matches the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Any Shopify merchant can install a public app for free (or a private/dev store attacker can install their own app instance), which is sufficient to obtain a genuine `(body, hmac)` pair signed with the app's shared `api_secret_key`. No access to the app's `client_secret`, API tokens, or the victim's credentials is required — only the ability to send an arbitrary HTTP request with a spoofed header to the app's public webhook endpoint, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting the header in isolation:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or
- Cross-check the header-supplied `shop` against a shop identifier embedded in and covered by the signed body, or a value already associated with the delivery (e.g. requiring the host app to have an existing registered webhook subscription id per shop and validating it), and
- At minimum, document/enforce that `data.shop` from `WebhookMetadata` must not be treated as authenticated unless it is corroborated by data covered by the HMAC.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Step 1: Attacker triggers a legit webhook delivery for their own shop and
# captures the raw body + valid HMAC that Shopify computed with the app's
# single shared api_secret_key.
captured_body = '{"id":1,"note":"hello"}'
captured_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, captured_body)

# Step 2: Attacker replays the same body+hmac to the app's public webhook
# endpoint, spoofing the shop-domain header to point at the victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(captured_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unverified
  "x-shopify-webhook-id" => "spoofed-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# Step 3: HmacValidator.validate(request) succeeds because it only checks
# `raw_body` against the shared secret — it never checks `shop`.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1,...}, ...))
# The host app now processes attacker-controlled data as belonging to the victim shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
