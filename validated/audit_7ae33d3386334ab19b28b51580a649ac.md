### Title
Opaque router routes can hide a victim-signed token transfer beneath an approved collateral swap - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept the route as opaque `Bytes`, defined as the encoded `StrategySwap` forwarded to the configured aggregator. [1](#0-0) [2](#0-1) 

The controller authorizes only one controller-owned input-token transfer to the configured router, invokes `execute_strategy`, and then checks input spending, output receipt, and final account risk. [3](#0-2) 

Because the route can place third-party contracts on the call stack, a malicious venue can add a caller-authorized token transfer beneath the caller’s `swap_collateral` authorization entry, and that transfer executes if the resulting authorization tree is signed. [4](#0-3) 

### Finding Description
`swap_collateral` authenticates the caller and verifies account ownership or delegation before forwarding the caller-supplied opaque route through `withdraw_and_swap_from_supply`. [5](#0-4) 

`swap_tokens` snapshots input and output balances, authorizes `token_in.transfer(controller, router, amount_in)`, and invokes the configured router, but it does not constrain which contracts the encoded route invokes or which additional caller authorizations those contracts request. [6](#0-5) 

The post-router checks only reject controller-input gains or overspending, refund unused controller-held input, and require a positive output delta. [7](#0-6) 

The project’s threat model confirms that routed pool and token addresses are not allowlisted and that a token transfer made from the caller by routed third-party code becomes a child of the caller’s signed authorization tree. [8](#0-7) 

The semantic-drift analog is therefore that the operation presented as a collateral conversion can carry an additional signed action transferring unrelated wallet funds to the attacker. [9](#0-8) 

### Impact Explanation
A crafted route can steal unrelated tokens directly from the victim’s wallet rather than being limited to the routed collateral amount. [10](#0-9) 

The loss can include the victim’s full balance of any token for which the malicious child invocation is included in the signed tree, while the route still returns enough output to satisfy the controller’s positive-output and final-risk checks. [7](#0-6) [9](#0-8) 

This constitutes theft of user funds and is reachable by an unprivileged route submitter through `swap_collateral`, with the same authorization shape also exposed by `swap_debt`, `multiply`, and `repay_debt_with_collateral`. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Exploitation requires the victim to submit or sign an attacker-constructed route and requires the approval interface to display the strategy as a normal swap without clearly forcing review of the extra child authorization. [13](#0-12) 

No privileged role, leaked key, controller compromise, oracle manipulation, or failed protocol gate is required because the malicious invocation is made possible by the caller signing a simulated authorization tree whose displayed meaning differs from its complete execution semantics. [5](#0-4) [13](#0-12) 

The need for a crafted route and user signing makes this less likely than a purely permissionless protocol invariant break, but the absence of an on-chain callee allowlist makes the exposure directly reachable. [4](#0-3) 

### Recommendation
Replace or supplement opaque route bytes with a typed route manifest that identifies the permitted venue contracts and pool addresses, and enforce a governed venue or pool allowlist before dispatch. [1](#0-0) [14](#0-13) 

Clients should render every child authorization and reject a controller strategy whose authorization tree contains anything beyond the expected strategy invocation and any explicitly declared token pull. [9](#0-8) 

If arbitrary venues remain supported, provide a signed human-readable route summary binding the expected callee set, token pulls, and authorization children so that an approval cannot be represented as only a harmless swap. [15](#0-14) 

### Proof of Concept
1. Deploy or control a venue contract that, when reached by the router, invokes `TOKEN.transfer(victim, attacker, victim_balance)`.
2. Construct an opaque `swap` route for `swap_collateral` that reaches that venue while still returning a positive amount of the requested output asset.
3. Have the victim invoke `swap_collateral(controller, victim, account_id, current, amount, new, malicious_route)`; the controller authenticates the victim and forwards the opaque route through its swap path. [16](#0-15) [5](#0-4) 
4. Simulation records the victim’s `swap_collateral` authorization with a child `TOKEN.transfer(victim, attacker, victim_balance)` entry because routed third-party code can request caller authorization. [8](#0-7) 
5. If the victim signs while the interface presents only the collateral swap, the venue’s additional transfer is authorized and transfers the victim’s wallet tokens to the attacker. [9](#0-8) 
6. The router can still spend no more than the controller-authorized input and return positive output, so the controller-side checks and final account risk validation do not prevent the wallet loss. [7](#0-6)
